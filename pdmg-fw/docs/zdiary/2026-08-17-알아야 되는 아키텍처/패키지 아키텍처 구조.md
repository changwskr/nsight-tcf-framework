# 9. 패키지 아키텍처 구조

현재 PDMG 실제 소스를 기준으로 보면 패키지 아키텍처는 크게 **Framework 영역(`nhnis.fw`)**과 **업무 영역(`nhnis.mg`)**으로 분리됩니다. 업무 프로그램은 다시 **업무코드 → 세부업무코드 → 책임 계층** 순으로 내려가는 구조입니다. 이는 앞에서 확인한 `Handler → Facade → Service → DAO → Mapper` 계층 구조와 직접 연결됩니다.

가장 먼저 전체 모습을 보면 다음과 같습니다.

```text
PDMG
│
├─ pdmg-ui
│    └─ nhnis.mg.ui.*
│
├─ pdmg-jwt
│    └─ nhnis.mg.jw.a.*
│
├─ pdmg-fw
│    ├─ nhnis.fw.commons.*
│    └─ nhnis.fw.tcf.*
│
└─ pdmg-service
     └─ nhnis.mg.co.a.*
          │
          ├─ entry
          ├─ application
          ├─ dto
          ├─ persistence
          ├─ client
          ├─ config
          └─ support
```

프로젝트 기준상 PDMG의 실제 구현은 NSIGHT TCF의 목표 패키지를 덮어씌우지 않고 **PDMG 자체 AS-IS 패키지를 우선해서 판단해야 합니다.**

---

## 9.1 패키지 구조의 가장 중요한 원칙

PDMG 업무 패키지는 다음 공식으로 이해하면 됩니다.

```text
nhnis.mg.[업무구분].[세부업무구분].[책임계층].[세부패키지]
```

현재 `CO/A`를 적용하면:

```text
nhnis.mg.co.a
         │  │
         │  └──── 세부업무 A
         └─────── 업무 CO
```

그리고 그 아래에 책임 계층이 붙습니다.

```text
nhnis.mg.co.a.entry.handler
nhnis.mg.co.a.entry.aspect

nhnis.mg.co.a.application.controller
nhnis.mg.co.a.application.facade
nhnis.mg.co.a.application.service

nhnis.mg.co.a.dto

nhnis.mg.co.a.persistence.dao

nhnis.mg.co.a.client
nhnis.mg.co.a.config
nhnis.mg.co.a.support
```

따라서 클래스 이름을 보기 전에 **패키지만 보고도 역할을 판단할 수 있도록 만드는 것**이 핵심입니다.

---

# 9.2 ServiceId와 패키지는 같은 업무 축을 사용한다

PDMG에서 특히 잘 연결되어 있는 부분입니다.

예를 들어:

```text
ServiceId
mgcoa8888S0
```

를 나누면:

```text
mg | co | a | 8888 | S | 0
│    │    │     │    │   │
│    │    │     │    │   └─ 거래 순번
│    │    │     │    └──── 조회
│    │    │     └───────── 프로그램 식별번호
│    │    └─────────────── 세부업무 A
│    └──────────────────── 업무 CO
└───────────────────────── MG
```

Java 패키지는:

```text
nhnis.mg.co.a
```

Mapper 리소스도 같은 축을 사용합니다.

```text
rdw.mg.co.a/
```

즉 중요한 관계는:

```text
ServiceId       mgcoa8888S0
                   │
                   │ mg + co + a
                   ▼
Java Package     nhnis.mg.co.a
                   │
                   ▼
Mapper Resource   rdw.mg.co.a
```

입니다.

이것은 PDMG의 매우 중요한 **추적성 규칙**입니다.

# 9.4 `entry` 패키지

`entry`는 **Framework와 업무 Application이 만나는 경계**라고 보면 됩니다.

```text
nhnis.mg.co.a.entry
│
├─ handler
│    ├─ mgcoa5530Handler
│    ├─ mgcoa8888Handler
│    ├─ mgcoa9000Handler
│    ├─ mgcoa9001Handler
│    └─ ...
│
└─ aspect
     ├─ BizPrePostAspect
     └─ PdmgBizTxFlowAspect
```

### `entry.handler`

TCF ON 거래의 업무 진입점입니다.

```text
TransactionDispatcher
       │
       │ ServiceId
       ▼
entry.handler
       │
       ▼
Facade
```

Handler 책임은:

```text
ServiceId 확인
      ↓
해당 Use Case 선택
      ↓
Facade 호출
```

입니다.

Handler에서 다음을 해서는 안 됩니다.

```text
Handler → DAO        X
Handler → Mapper     X
Handler → SQL        X
Handler → DB         X
```

---

## 9.5 `entry.aspect`

업무 공통 선·후처리 영역입니다.

```text
Handler
   ↓
Facade
   ↓
BizPrePostAspect
   │
   ├─ Before
   ↓
Service
   │
   └─ AfterReturning
```

즉 TCF의 STF/ETF와 구분해야 합니다.

```text
TCF STF / ETF
= Framework 공통 선·후처리

entry.aspect
= Business 공통 선·후처리
```

앞서 확인한 PDMG의 공통 선·후처리 구조도 이 경계를 사용합니다.

---

# 9.6 `application` 패키지

업무 Use Case의 핵심입니다.

```text
application
│
├─ controller
├─ facade
└─ service
```

### `application.controller`

현재 PDMG에서는 주로 **TCF OFF 경로**의 HTTP 진입점으로 이해하는 것이 좋습니다.

```text
TCF ON

OnlineTransactionController
      ↓
Dispatcher
      ↓
Handler

────────────────────

TCF OFF

업무 Controller
      ↓
Facade
```

따라서 TCF ON인데 별도로 업무 Controller를 다시 통과하는 구조로 이해하면 안 됩니다.

---

# 9.7 `application.facade`

Facade는 하나의 Use Case 경계입니다.

```text
Handler
   ↓
Facade
   │
   ├─ Object → DTO 변환
   ├─ Use Case 조립
   ├─ Transaction 선언
   └─ Service 호출
```

예:

```text
nhnis.mg.co.a.application.facade
└─ mgcoa9001Facade
      │
      ├─ mgcoa9001S0()
      ├─ mgcoa9001C0()
      ├─ mgcoa9001U0()
      └─ mgcoa9001D0()
```

Facade를 한 문장으로 표현하면:

> **“이번 거래를 어떤 업무 기능들로 구성할 것인가?”**

입니다.

---

# 9.8 `application.service`

실제 업무 처리의 중심입니다.

```text
nhnis.mg.co.a.application.service
│
├─ mgcoa5530Service
├─ mgcoa8888Service
├─ mgcoa9000Service
├─ mgcoa9001Service
├─ mgcoa9100Service
└─ ...
```

Service 책임:

```text
입력 검증
   ↓
업무 판단
   ↓
업무 처리 순서
   ↓
DAO 호출
   ↓
결과 DTO 생성
```

즉:

```text
Facade
= Use Case 조립

Service
= 실제 Business Logic
```

입니다.

---

# 9.9 `rule` 패키지는 현재 AS-IS가 아니다

이 부분은 특히 주의해야 합니다.

목표 구조는 자연스럽게:

```text
Service
 ├─ Rule
 ├─ DAO
 └─ Integration
```

으로 발전할 수 있습니다.

그러나 **현재 실제 `pdmg-service` 소스에는 독립적인 `application.rule` 패키지가 존재하지 않습니다.**

현재는:

```text
[AS-IS]

Service
  ├─ 업무 흐름
  ├─ 업무 검증
  ├─ 업무 Rule
  └─ DAO 호출
```

입니다.

향후 복잡한 업무 Rule을 분리한다면:

```text
[TO-BE]

application
│
├─ facade
├─ service
└─ rule
     ├─ TransactionControlRule
     ├─ CustomerValidationRule
     └─ ...
```

형태가 가능합니다.

따라서 **문서 그림에 `rule`이 있다고 해서 현재 구현에도 있다고 설명하면 안 됩니다.**

# 9.10 `dto` 패키지

DTO는 application 밑이 아니라 업무축 바로 아래에 있습니다.

```text
nhnis.mg.co.a.dto
```

예:

```text
mgcoa9001S0DTOin
mgcoa9001S0DTOout

mgcoa9001C0DTOin
mgcoa9001C0DTOout
```

관계는:

```text
ServiceId
mgcoa9001S0
      │
      ├─ mgcoa9001S0DTOin
      └─ mgcoa9001S0DTOout
```

입니다.

권장하지 않는 구조:

```text
nhnis.mg.co.a.application.dto   X
```

현재 표준:

```text
nhnis.mg.co.a.dto               O
```

입니다.

# 9.11 `persistence.dao`

DB 접근 경계입니다.

```text
nhnis.mg.co.a.persistence.dao
│
├─ mgcoa5530DAO
├─ mgcoa8888DAO
├─ mgcoa9000DAO
├─ mgcoa9001DAO
└─ ...
```

전체 관계:

```text
Service
   ↓
persistence.dao
   ↓
MyBatis
   ↓
Mapper XML
   ↓
SQL
   ↓
DB
```

예를 들어:

```text
mgcoa9001Service
       ↓
mgcoa9001DAO
       ↓
rdw.mg.co.a/mgcoa9001-ORA.xml
       ↓
TB_MG_TX_CONTROL
```

입니다.

DAO가 업무 흐름을 결정해서는 안 됩니다.

```text
DAO에서 ServiceId 분기     X
DAO에서 업무 Rule 판단     X
DAO에서 Transaction 통제   X
```

# 9.12 Mapper는 Java 패키지가 아니라 리소스 축이다

PDMG에서 Mapper XML은:

```text
src/main/resources/
└─ rdw.mg.co.a/
```

에 위치합니다.

그리고 Java DAO:

```text
nhnis.mg.co.a.persistence.dao.mgcoa9001DAO
```

와 XML:

```text
rdw.mg.co.a/mgcoa9001-ORA.xml
```

이 연결됩니다.

구조적으로:

```text
Java

nhnis.mg.co.a.persistence.dao
       │
       └─ mgcoa9001DAO
                │
                │ namespace
                ▼

Resource

rdw.mg.co.a
       │
       └─ mgcoa9001-ORA.xml
```

입니다.

따라서 업무 패키지를 변경한다면 최소한 다음을 같이 봐야 합니다.

```text
Java Package
+ @MapperScan
+ Mapper XML 경로
+ XML namespace
+ AOP Pointcut
```

하나만 바꾸면 안 됩니다.

# 9.13 `client`

외부 시스템 호출 전용 영역입니다.

```text
nhnis.mg.co.a.client
```

장기적으로 다음과 같은 구조입니다.

```text
Service
  │
  ├──────── DAO ─────────→ DB
  │
  └──────── Client ──────→ 외부 시스템
```

즉 외부 API/EAI를 DAO로 처리하지 않는 것이 중요합니다.

```text
DAO
= DB

Client
= External Integration
```

입니다.

# 9.14 `config`

애플리케이션 조립 영역입니다.

현재:

```text
nhnis.mg.co.a.config
```

에는 다음 성격의 코드가 위치합니다.

```text

TransactionManager
MyBatis
Mapper Scan
Interceptor
Properties
Spring Configuration
```

구조:

```text
config
 │
 ├─ RDW DataSource
 ├─ SqlSessionFactory
 ├─ SqlSessionTemplate
 ├─ MapperScan
 └─ TransactionManager
```

따라서 업무 로직을 넣는 곳이 아닙니다.

# 9.15 `support`

업무축 내부 공통 보조 기능입니다.

```text
nhnis.mg.co.a.support
```

주의할 점은 `support`를 또 다른 `common` 쓰레기통으로 만들면 안 된다는 것입니다.

적합:

```text
순수 변환
공통 Validator 보조
업무축 한정 Helper
```

부적합:

```text
CustomerService        X
TransactionService     X
SQL                    X
업무 Use Case          X
```

```text
nhnis.fw

│   ├─ configuration
│   ├─ context
│   ├─ dto
│   ├─ exception
```

# 9.19 `pdmg-om`은 현재 ZIP의 Java AS-IS로 확인되지 않는다

현재 분석한 업로드 ZIP에서는:

```text
pdmg-om/src/main/java
```

에 해당하는 Java 구현을 확인하지 못했습니다.

따라서 지금 시점에서는:

```text
pdmg-om package architecture
= UNKNOWN / 미확인
```

으로 두는 것이 정확합니다.

운영 기능 자체는 현재 `pdmg-service`의 `mgcoa9001`, `mgcoa9100` 등의 ServiceId와 `pdmg-fw` Runtime/Transaction Control 기능에 분산되어 있습니다. 앞서 분석한 운영·통제 구조도 이 AS-IS를 기준으로 합니다.

# 9.20 패키지 의존 방향

가장 중요한 규칙입니다.

```text
                         Framework
                            │
                            ▼

                      entry.handler
                            │
                            ▼
                     application.facade
                            │
                            ▼
                     application.service
                        │           │
                        │           │
                        ▼           ▼
                     client    persistence.dao
                                     │
                                     ▼
                                  Mapper
                                     │
                                     ▼
                                    DB
```

DTO는 여러 계층에서 데이터 전달용으로 사용합니다.

```text
             dto
          ↗   ↑   ↖
Handler   Facade  Service
```

반대로 다음 방향은 금지하는 것이 맞습니다.

```text
DAO ───────→ Service        X
DAO ───────→ Facade         X

Service ───→ Handler        X
Service ───→ Controller     X

Facade ────→ Controller     X

Mapper ────→ Service        X
```

즉 원칙은:

> **상위 계층이 하위 계층을 사용하고, 하위 계층은 상위 계층을 알지 않는다.**

```text
nhnis.mg.ic.b
│
├─ entry
│   ├─ handler
│   └─ aspect
│
├─ application

│   ├─ facade
```

# 9.23 현재 AS-IS와 향후 확장 구조

정리하면 현재 PDMG는:

```text
[AS-IS]

entry.handler
      ↓
application.facade
      ↓
application.service
      ↓
persistence.dao
      ↓
Mapper
      ↓
DB
```

입니다.

업무가 커질 경우 권장되는 확장은:

```text
[TO-BE]

entry.handler
      ↓
application.facade
      ↓
application.service
      │
      ├──── application.rule
      │
      ├──── persistence.dao → DB
      │
      └──── client → External
```

입니다.

**Rule을 추가하더라도 Handler/Facade/Service/DAO의 기존 책임을 깨지 않는 방향**이어야 합니다.

### 꼭 기억할 7가지

1. **`nhnis.fw.*`는 Framework**, `nhnis.mg.*`는 업무/애플리케이션 영역입니다.
2. 업무 패키지는 **`nhnis.mg.[업무].[세부업무]`** 축을 사용합니다.
3. `entry.handler`는 **ServiceId → Use Case 진입**입니다.
4. `application.facade → service → persistence.dao` 방향으로만 내려갑니다.
5. Java 패키지 `nhnis.mg.co.a`와 Mapper `rdw.mg.co.a`는 같은 업무축이어야 합니다.
6. **현재 PDMG AS-IS에는 독립적인 `rule` 패키지가 없습니다.** Rule 분리는 TO-BE 확장입니다.
7. ServiceId, Java Package, DAO Namespace, Mapper 경로를 **하나의 추적 체계로 관리**하는 것이 PDMG 패키지 아키텍처의 핵심입니다.
