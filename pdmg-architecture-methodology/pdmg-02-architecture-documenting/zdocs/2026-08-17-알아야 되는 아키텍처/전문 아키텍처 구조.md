# 전문 아키텍처 구조

현재 PDMG/NSIGHT에서 **전문(Message)** 은 단순 JSON 포맷이 아니라, **화면 → Framework → TCF → 업무 → 응답까지 하나의 거래를 전달하고 추적하는 표준 Envelope**입니다.

현재 PDMG 기준 전문은 크게 **`hdr_nhnis + dto`**, 오류 시 **`hdr_nhnis + result`** 구조이며, 공통 헤더는 Framework가 관리하고 업무 데이터는 업무 애플리케이션이 관리하는 방식입니다.

---


# 2. 요청 전문 구조

현재 요청 전문은 개념적으로 다음 구조입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID-20260817-000001",
      "rms_svc_c": "mgcoa9000S0",
      "tr_sysid": "PDMG",
      "scid": "mgcoa9000",
      "tr_brc": "10001",
      "tr_trm_ipadr": "10.10.10.10",
      "optr_eno": "E0000001"
    }
  },
  "dto": {
    "pageNo": 1,
    "pageSize": 20,
    "searchKeyword": "홍길동"
  }
}
```

논리적으로는 두 부분입니다.

```text
Standard Request
│
├─ hdr_nhnis
│    │
│    └─ sys_comm
│         ├─ 거래 식별
│         ├─ 추적 정보
│         ├─ 사용자 정보
│         ├─ 점/단말 정보
│         └─ ServiceId
│
└─ dto
     │
     └─ 실제 업무 입력 데이터
```

# 3. `hdr_nhnis`와 `dto`의 책임을 분리한다

이것이 전문 아키텍처에서 가장 중요합니다.

| 영역        | 소유 영역      | 책임                  |
| ----------- | -------------- | --------------------- |
| `hdr_nhnis` | `pdmg-fw`      | 시스템 공통 전문      |
| `sys_comm`  | `pdmg-fw`      | 거래·추적·사용자 정보 |
| `dto`       | `pdmg-service` | 업무별 입력/출력      |
| `result`    | `pdmg-fw`      | 표준 오류정보         |

즉 업무 개발자는 다음처럼 생각하면 됩니다.

```text
Framework가 관리
─────────────────
GUID
ServiceId
사용자
점코드
단말 IP
시스템
화면정보


업무가 관리
─────────────────
고객번호
상품번호
조회조건
금액
기간
pageNo
pageSize
```

업무 Service가 `hdr_nhnis` 전체를 계속 넘겨받아 처리하는 방식은 권장 구조가 아닙니다.

# 4. 전문은 Framework 진입 시 Context와 DTO로 분리된다

외부에서는 하나의 JSON이지만 내부에서는 계속 하나의 거대한 객체로 전달하지 않습니다.

```text
                 HTTP Standard Request
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
          hdr_nhnis                dto
              │                     │
              ▼                     ▼
       ServiceContext         Business DTO
              │                     │
              │                     ▼
              │                  Handler
              │                     │
              │                     ▼
              │                  Facade
              │                     │
              │                     ▼
              └─────────────────► Service
```

현재 구조에서 `ServiceContext`는 HTTP 요청 한 건의 공통 실행정보를 담는 역할을 합니다.

따라서:

```text
표준전문
   ↓
Parsing
   ↓
┌──────────────────────┐
│                      │
▼                      ▼
ServiceContext     Business DTO
Framework용         업무용
```

으로 분리됩니다.

# 5. `ServiceContext`

`ServiceContext`는 **HTTP 요청 한 건에 대한 공통 실행 문맥**입니다.

```text
ServiceContext
│
├─ GUID
├─ ServiceId
├─ Header
├─ 사용자
├─ 점코드
├─ Client IP
├─ Application
├─ Profile
├─ Request
├─ Response
├─ Request Body
└─ 기타 Framework 공통정보
```

현재 구조에서는 `ServiceContextHolder`를 통해 요청 Thread에서 접근할 수 있습니다.

중요한 것은:

```text
ServiceContext ≠ 업무 DTO
```

라는 점입니다.

예를 들어:

```text
ServiceContext
────────────────
GUID
ServiceId
UserId
Branch
IP

DTO
────────────────
customerNo
startDate
endDate
pageNo
pageSize
```

입니다.

# 6. `TransactionContext`

TCF로 들어가면 한 단계 더 좁은 **거래 실행용 Context**가 만들어집니다.

```text
ServiceContext
HTTP Request 전체 문맥
       │
       ▼
OnlineTransactionController
       │
       ▼
TcfFacade
       │
       ▼
TransactionContext
       │
       ├─ ServiceId
       ├─ 거래 시작시간
       ├─ Deadline
       ├─ 실행상태
       └─ ServiceContext 참조
```

따라서 Context는 두 층으로 이해하면 쉽습니다.

```text
┌───────────────────────────────────────────┐
│ ServiceContext                            │
│ HTTP 요청 전체 Lifetime                  │
│                                           │
│ Filter → Interceptor → Controller → 응답 │
│                                           │
│    ┌─────────────────────────────────┐    │
│    │ TransactionContext              │    │
│    │ TCF 거래 실행 Lifetime          │    │
│    │                                 │    │
│    │ STF → Timeout → Dispatcher      │    │
│    │       → Handler → ETF           │    │
│    └─────────────────────────────────┘    │
└───────────────────────────────────────────┘
```

# 7. ServiceId가 전문과 실행 아키텍처를 연결한다

전문의 가장 중요한 필드 중 하나가 `ServiceId`입니다.

예:

```text
rms_svc_c = mgcoa9000S0
```

이 값 하나가 다음 구조를 관통합니다.

```text
표준전문
hdr_nhnis.sys_comm.rms_svc_c
              │
              ▼
        mgcoa9000S0
              │
              ▼
      TransactionDispatcher
              │
              ▼
       mgcoa9000Handler
              │
              ▼
       mgcoa9000Facade
              │
              ▼
       mgcoa9000Service
              │
              ▼
        mgcoa9000DAO
              │
              ▼
     mgcoa9000-ORA.xml
              │
              ▼
             DB
```

PDMG Dispatcher 자체도 ServiceId를 Handler Registry의 Key로 사용합니다.

따라서 전문 아키텍처에서는:

> **ServiceId = 전문과 실제 프로그램 실행을 연결하는 논리적 거래 주소**

라고 정의하는 것이 가장 중요합니다.

# 8. 정상 응답 전문

정상 처리에서는:

```text
업무 Service
    ↓
업무 DTO 반환
    ↓
Handler
    ↓
TCF
    ↓
Response Resolver
    ↓
hdr_nhnis + dto
```

형태가 됩니다.

예:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID-20260817-000001",
      "rms_svc_c": "mgcoa9000S0"
    }
  },
  "dto": {
    "totalCount": 2,
    "items": [
      {
        "customerNo": "C001",
        "customerName": "홍길동"
      },
      {
        "customerNo": "C002",
        "customerName": "김농협"
      }
    ]
  }
}
```

즉:

```text
정상 응답
=
hdr_nhnis
+
dto
```

입니다.

# 9. 오류 응답 전문

업무 코드에서는 오류 응답 전문을 직접 만들지 않습니다.

```text
Service
   │
   ├─ 정상 → DTO
   │
   └─ 오류
        │
        ▼
    BizException
        │
        ▼
GlobalExceptionHandler
        │
        ▼
      result
```

최종 전문은:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID-20260817-000001",
      "rms_svc_c": "mgcoa9000S0"
    }
  },
  "result": {
    "stdErrCode": "MP0404",
    "stdErrMsgCntn": "요청한 데이터를 찾을 수 없습니다.",
    "addMsgContents": "조회 조건을 확인하세요.",
    "errType": "BIZ"
  }
}
```

구조입니다. 현재 PDMG 오류처리에서도 **정상은 `dto`, 오류는 `result`**로 분리합니다.

```text
정상
hdr_nhnis + dto

오류
hdr_nhnis + result
```

# 11. 전문과 TCF의 관계

전문 자체가 업무를 실행하는 것은 아닙니다.

역할을 정확히 나누면:

```text
전문
"무슨 거래인가?"
        │
        │ ServiceId
        ▼
TCF
"이 거래를 실행해도 되는가?"
        │
        ▼
Dispatcher
"누가 처리해야 하는가?"
        │
        ▼
Handler
"어떤 Use Case인가?"
        │
        ▼
Service
"무엇을 처리해야 하는가?"
```

따라서 각 책임은 다음처럼 분리됩니다.

| 영역               | 핵심 질문                          |
| ------------------ | ---------------------------------- |
| 전문               | 어떤 요청인가?                     |
| ServiceContext     | 누가/어디서 요청했는가?            |
| TransactionContext | 이 거래는 어떤 상태로 실행 중인가? |
| STF                | 실행 가능한 거래인가?              |
| Dispatcher         | 어떤 Handler인가?                  |
| Handler            | 어떤 Use Case인가?                 |
| Service            | 어떤 업무를 수행할 것인가?         |
| ETF                | 거래를 어떻게 종료할 것인가?       |

TCF는 `Controller → TcfFacade → STF → Timeout/Transaction → Dispatcher → Handler → ETF`라는 거래 실행 생명주기를 관리합니다.

# 12. 전문에서 지켜야 할 아키텍처 Rule

전문 구조는 다음 규칙을 기준으로 관리하는 것이 좋습니다.

| Rule        | 기준                                      |
| ----------- | ----------------------------------------- |
| **MSG-001** | 전문은 `Header + Business Payload`로 분리 |
| **MSG-002** | ServiceId는 공통 Header에서 관리          |
| **MSG-003** | GUID는 모든 거래에서 유지                 |
| **MSG-004** | 업무 계층에 전체 전문 전달 금지           |
| **MSG-005** | 업무에는 필요한 DTO만 전달                |
| **MSG-006** | Framework 공통정보는 Context 사용         |
| **MSG-007** | 업무 프로그램의 응답 JSON 직접 조립 금지  |
| **MSG-008** | 오류는 Exception으로 전달                 |
| **MSG-009** | 정상은 `dto`, 오류는 `result`             |
| **MSG-010** | 요청/응답의 GUID와 ServiceId 추적성 유지  |
| **MSG-011** | 민감정보는 전문로그에서 마스킹            |
| **MSG-012** | 전문 버전 변경은 하위호환 정책 적용       |

### 핵심

PDMG 전문 아키텍처는 단순히 **“JSON 형식을 통일한다”**가 아닙니다.

```text
표준전문
   +
ServiceId
   +
ServiceContext
   +
TransactionContext
   +
DTO
   +
표준 오류
   +
GUID / Logging
```

을 묶어 **거래 한 건을 처음부터 끝까지 동일한 Identity로 관리하는 아키텍처**입니다.

특히 가장 중요한 추적축은:

```text
GUID
   +
ServiceId
      ↓
Header
      ↓
TCF
      ↓
Dispatcher
      ↓
Handler
      ↓
Business
      ↓
```
