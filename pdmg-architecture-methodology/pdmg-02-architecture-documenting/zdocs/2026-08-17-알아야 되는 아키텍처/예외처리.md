현재 **PDMG 실제 소스 기준**으로 보면, 에러처리는 다음 구조로 이해하는 것이 가장 정확합니다. PDMG와 NSIGHT TCF의 AS-IS를 섞지 않고 실제 구현을 우선해야 한다는 프로젝트 기준에도 맞습니다.

## PDMG 에러처리 전체 구조

TCF ON + Timeout ON 기준입니다.

```text
[HTTP 요청]
    │
    ▼
DefaultFilter / Interceptor
    │
    ▼
OnlineTransactionController
    │
    ▼
TcfFacade
    │
    ├─ STF
    │
    ▼
OnlineTimeoutExecutor
    │
    ▼
Worker Thread
    │
    ▼
TransactionTemplate
    │
    │  TX BEGIN
    ▼
Dispatcher
    ▼
Handler
    ▼
Facade
    ▼
Service
    ▼
DAO / Mapper / DB
    │
    ├──────── 정상 ───────────────┐
    │                             ▼
    │                          COMMIT
    │
    └──────── 예외 ───────────────┐
                                  ▼
                              ROLLBACK
                                  │
                                  ▼
                              TcfFacade
                                  │
                              ETF finally
                                  │
                                  ▼
                        GlobalExceptionHandler
                                  │
                     exceptionCode.yml 조회
                                  │
                                  ▼
                          NH_NIS_ERR_DTO
                                  │
                                  ▼
                    ResponseBodyArgumentResolver
                                  │
                                  ▼
                     hdr_nhnis + result
```

핵심은 **업무 프로그램이 에러 응답 JSON을 직접 만드는 것이 아니라 예외만 던지고, `pdmg-fw`가 최종 오류 전문을 만든다**는 것입니다.

### 1. 업무 오류는 `BizException`

`pdmg-service`의 Service에서 예상할 수 있는 업무 오류는 다음처럼 던집니다.

```java
if (customer == null) {
    throw new BizException("MP0404");
}
```

또는 메시지 인자가 필요하면:

```java
throw new BizException("FW0410", controlType, businessCode);
```

메시지는 Java에 하드코딩하지 않고 `exceptionCode.yml`에 둡니다.

```yaml
nhnis:
  exception:
    MP0401: "필수 입력값이 누락되었습니다."
    MP0403: "입력값 형식이 올바르지 않습니다."
    MP0404: "요청한 데이터를 찾을 수 없습니다."
    MP0409: "동일한 기본키의 데이터가 이미 존재합니다."

  exception-action:
    MP0404: "조회 조건을 확인하거나 데이터가 존재하는지 확인하세요."
```

현재 실제 `GlobalExceptionHandler`는 `ExceptionCodeProperties`를 사용하고 있기 때문에:

```java
throw new BizException("MP0404");
```

가 발생하면 단순히 `"MP0404"`라는 문자열을 보내는 것이 아니라 실제 메시지를 조회합니다.

```text
stdErrCode    = MP0404
stdErrMsgCntn = 요청한 데이터를 찾을 수 없습니다.
addMsgContents
              = 조회 조건을 확인하거나 데이터가 존재하는지 확인하세요.
errType       = BIZ
```

즉, 일부 과거 PDMG 문서에 적힌 **“exceptionCode.yml이 GlobalExceptionHandler와 연결되지 않았다”는 설명은 현재 소스 기준으로는 이미 해결된 과거 내용**입니다.

## 예외 종류별 현재 처리

| 상황                  | 발생 예외                 | 오류코드              |     HTTP |
| --------------------- | ------------------------- | --------------------- | -------: |
| 업무 검증/미존재/중복 | `BizException`            | `MP04xx`, `FW04xx` 등 | 현재 500 |
| ServiceId 없음/미지원 | `ServiceHandlerNotFound`  | `E9999`               |      500 |
| 온라인 타임아웃       | `OnlineTimeoutException`  | `FW_TIMEOUT`          |  **504** |
| Worker Pool 포화      | `OnlineOverloadException` | `FW_OVERLOADED`       |  **503** |
| 레거시 공통 예외      | `NhBaseException`         | 보유 코드             |      500 |
| 일반 NPE/DB 장애 등   | 기타 Exception            | **현재 보완 필요**    | 500 계열 |

특히 Timeout의 경우 단순히 HTTP 에러만 만드는 것이 아닙니다.

```text
Worker Thread
    │
    ▼
TransactionTemplate
    │
    ├─ BizException
    ├─ RuntimeException
    ├─ Checked Exception
    └─ Timeout
          │
          ▼
    status.setRollbackOnly()
          │
          ▼
       ROLLBACK
```

`DefaultOnlineTimeoutExecutor`를 보면 RuntimeException뿐 아니라 checked Exception도 내부 래퍼를 통해 **rollbackOnly로 만든 후 바깥으로 다시 원래 예외를 전달**합니다.

따라서 최근에 이야기한 PDMG 트랜잭션 구조와 연결하면:

```text
BizException 발생
      ↓
TransactionTemplate이 예외 감지
      ↓
ROLLBACK
      ↓
예외가 Request Thread까지 전달
      ↓
GlobalExceptionHandler
      ↓
오류 응답
```

입니다.

**에러 응답을 먼저 보내고 나중에 rollback하는 것이 아닙니다.**

## 실제 오류 응답

현재 `ResponseBodyArgumentResolver`는 성공과 실패를 구분합니다.

성공:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "...",
      "rms_svc_c": "mgcoa9001S0"
    }
  },
  "dto": {
    "data": "..."
  }
}
```

오류:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "...",
      "rms_svc_c": "mgcoa9001S0"
    }
  },
  "result": {
    "stdErrCode": "MP0404",
    "stdErrMsgCntn": "요청한 데이터를 찾을 수 없습니다.",
    "addMsgContents": "조회 조건을 확인하거나 데이터가 존재하는지 확인하세요.",
    "errType": "BIZ",
    "errClassName": "nhnis.mg.co.a.application.service.mgcoa9001Service",
    "errMethodName": "...",
    "errFileName": "mgcoa9001Service.java",
    "errLineNo": 137
  }
}
```

즉 PDMG 표준은 명확하게:

```text
정상 → dto
오류 → result
```

로 분리되어 있습니다.

## ETF는 에러를 먹지 않습니다

`TcfFacade`의 현재 구현도 중요합니다.

```java
try {
    stf.preProcess(context);

    return onlineTimeoutExecutor.execute(
        () -> dispatcher.dispatch(...)
    );

} catch (Exception e) {
    primary = e;
    throw e;

} finally {
    etf.postProcess(context);
}
```

즉 Service에서 발생한 `BizException`을 TCF가 성공으로 바꾸지 않습니다.

그리고 이미 업무 예외가 발생한 상태에서 ETF에서도 예외가 발생하면:

```text
원래 업무 예외
   +
ETF 예외
   ↓
원래 업무 예외가 Primary
ETF 예외는 Suppressed
```

처리합니다.

이 구조는 좋습니다. **원래 장애 원인을 ETF 오류가 덮어쓰지 않기 때문입니다.**

## ImageLog도 오류를 기록합니다

`ImageLogHandler`는 다음 오류를 구분할 수 있게 되어 있습니다.

```text
NhBaseException       → 해당 오류코드
BizException          → BizException.code
OnlineTimeoutException
                     → FW_TIMEOUT
OnlineOverloadException
                     → FW_OVERLOADED
기타 Exception        → Exception Type / Message
```

따라서 최종적으로:

```text
GUID
ServiceId
Request
Response
ExceptionType
ExceptionCode
ExceptionMsg
```

를 이용해 장애 거래를 추적할 수 있습니다.

# 그런데 현재 PDMG 에러처리에는 중요한 GAP이 있습니다

가장 큰 것은 **`GlobalExceptionHandler`에 최종 `Exception.class` 처리기가 없다는 것**입니다.

현재는 대략:

```java
@ExceptionHandler(ServiceHandlerNotFound.class)
@ExceptionHandler(BizException.class)
@ExceptionHandler(OnlineTimeoutException.class)
@ExceptionHandler(OnlineOverloadException.class)
```

까지만 있습니다.

따라서 예를 들어:

```java
NullPointerException
DataAccessException
SQLException 계열
IllegalStateException
예상하지 못한 RuntimeException
```

이 발생하면 `FW9999` 표준 오류로 확실하게 정규화되지 않고 Spring 기본 오류 처리 경로로 갈 가능성이 있습니다.

제가 PDMG에서 가장 먼저 보완할 부분입니다.

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<NH_NIS_ERR_DTO> handleUnexpectedException(Exception e) {

    log.error("[GlobalExceptionHandler] unexpected exception", e);

    return error(
        "FW9999",
        exceptionCodes.message("FW9999"),
        TYPE.RUNTIME,
        HttpStatus.INTERNAL_SERVER_ERROR,
        exceptionCodes.actionMessage("FW9999"),
        e
    );
}
```

그러면 최종적으로 어떤 시스템 에러가 발생해도:

```text
예상 가능한 업무오류
→ BizException
→ 업무코드

예상하지 못한 시스템오류
→ Exception
→ FW9999
```

라는 명확한 구조가 됩니다.

## 두 번째 GAP은 Filter/Interceptor입니다

현재 `DefaultFilter`와 JWT `ServicePreventionInterceptor` 일부는:

```java
response.sendError(...)
```

를 직접 사용합니다.

예:

```text
Header 없음
→ sendError(400)

Access Token 없음
→ sendError(401)

Token Invalid
→ sendError(401)
```

문제는 이것들이 Controller 전에 끝나므로:

```text
GlobalExceptionHandler
        X

ResponseBodyArgumentResolver
        X 또는 보장 안 됨
```

이 될 수 있다는 것입니다.

결과적으로 PDMG 오류 전문이:

```json
{
  "hdr_nhnis": {},
  "result": {
    "stdErrCode": "...",
    ...
  }
}
```

형태가 아니라 Spring/Tomcat 기본 에러 응답이 될 수 있습니다.

**PDMG의 에러처리를 완성하려면 Filter/Interceptor 오류도 동일한 Error Response Writer를 사용하도록 통일하는 것이 좋습니다.**

# 최종 권장 책임 분리

제가 PDMG 표준으로 잡는다면 아주 단순합니다.

```text
pdmg-service
────────────────────────────
Service
  │
  └─ 문제가 있으면
     throw BizException

DAO
  │
  └─ 기술 예외는 그대로 전파

Handler
  │
  └─ 잘못된 serviceId만
     ServiceHandlerNotFound


pdmg-fw
────────────────────────────
TimeoutExecutor
  └─ rollback / timeout

GlobalExceptionHandler
  └─ 모든 Exception → 표준 오류 모델

ExceptionCodeProperties
  └─ 코드 → 메시지/조치

ResponseBodyArgumentResolver
  └─ result 조립

ImageLogHandler
  └─ 오류 증적 저장
```

즉 **업무 개발자는 사실 세 가지만 알면 됩니다.**

```java
// 1. 예상 가능한 업무 오류
throw new BizException("MP0404");

// 2. catch 해야 한다면 반드시 다시 던진다
catch (BizException e) {
    saveHistory();
    throw e;
}

// 3. 응답 JSON을 직접 만들지 않는다
```

그리고 절대로 이렇게 해서는 안 됩니다.

```java
try {
    dao.update(...);
} catch (Exception e) {
    return successDto;       // 금지
}
```

왜냐하면 이것은:

```text
Exception
 ↓
catch
 ↓
정상 return
 ↓
TransactionTemplate 입장에서는 정상
 ↓
COMMIT 가능
 ↓
화면도 성공으로 인식
```

하게 만들 수 있기 때문입니다.

### PDMG 최종 에러처리 목표

```text
                    Exception
                        │
         ┌──────────────┼───────────────┐
         ▼              ▼               ▼
    BizException    Framework       Unknown
                       Error          Error
         │              │               │
         └──────────────┼───────────────┘
                        ▼
              Transaction Rollback
                        │
                        ▼
              GlobalExceptionHandler
                        │
                        ▼
                ErrorCode Resolver
                        │
                        ▼
                 NH_NIS_ERR_DTO
                        │
                        ▼
            hdr_nhnis + result
                        │
                 ┌──────┴──────┐
                 ▼             ▼
               Client       ImageLog
```

**현재 PDMG는 이 구조의 약 80~90%는 이미 구현되어 있습니다. 핵심 보완은 `일반 Exception → FW9999`의 최종 안전망과 Filter/Interceptor 오류의 표준 `result` 통합입니다.**
