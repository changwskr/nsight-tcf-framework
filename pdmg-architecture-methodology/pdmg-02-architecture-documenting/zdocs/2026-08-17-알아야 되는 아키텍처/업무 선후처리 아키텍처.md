# 업무 선·후처리 아키텍처 구조

현재 **PDMG 실제 구조**에서 업무 선·후처리는 `pdmg-service`의 **Service 실행 경계**에 AOP를 적용하는 방식입니다. 핵심 구현은 `BizPrePostAspect`이며, `Handler → Facade → Service` 흐름 중 **Service 실행 직전과 정상 종료 직후**를 공통으로 관찰합니다.

가장 먼저 시스템/TCF/업무 선후처리를 분리해서 보면 구조가 명확합니다.

```text
┌──────────────────────────────────────────────────────────────┐
│ ① SYSTEM 선·후처리                                          │
│                                                              │
│ Filter → Interceptor → Resolver                              │
│                                                              │
│ JWT / Header / GUID / Context / 전문 / ImageLog             │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ ② TCF 거래 선·후처리                                        │
│                                                              │
│ TcfFacade                                                    │
│   ├─ STF.preProcess()        ← 거래 선처리                   │
│   │                                                          │
│   ├─ Timeout / Transaction                                   │
│   ├─ Dispatcher                                              │
│   └─ ETF.postProcess()       ← 거래 후처리                   │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ ③ BUSINESS 업무 선·후처리                                   │
│                                                              │
│ Handler                                                      │
│    ↓                                                         │
│ Facade                                                       │
│    ↓                                                         │
│ BizPrePostAspect                                             │
│    ├─ @Before            ← 업무 선처리                       │
│    ↓                                                         │
│ Service                                                      │
│    ├─ 업무 Rule                                              │
│    ├─ DAO                                                    │
│    └─ Integration                                            │
│    ↓                                                         │
│ @AfterReturning          ← 정상 업무 후처리                 │
└──────────────────────────────────────────────────────────────┘
```

TCF 자료에서도 `Handler → Facade → BizPrePostAspect → Service → DAO → Mapper/SQL → DB`를 별도의 Business 공통 선·후처리 영역으로 구분하고 있습니다.

---

## 1. 업무 선·후처리의 정확한 위치

현재 PDMG 업무 실행은 다음 순서입니다.

```text
ServiceId
   ↓
TransactionDispatcher
   ↓
Handler
   ↓
Facade
   │
   │  이미 Transaction이 존재할 수 있음
   ▼
════════════════════════════════
      업무 Service Proxy
════════════════════════════════
   │
   ├─ PdmgBizTxFlowAspect
   │     @Around
   │
   ├─ BizPrePostAspect
   │     @Before
   │
   ▼
Business Service
   │
   ├─ 입력 검증
   ├─ 업무 판단
   ├─ Rule
   ├─ DAO
   │   ↓
   │ Mapper
   │   ↓
   │ DB
   │
   └─ 결과 DTO 생성
   │
   ▼
BizPrePostAspect
@AfterReturning
   │
   ▼
Facade Return
   │
   ▼
Handler Return
```

현재 `BizPrePostAspect`는 Service 계층을 Pointcut으로 잡습니다.

실제 Pointcut은 다음 구조입니다.

```java
@Pointcut(
    "execution(public * nhnis.mg.co.a.application.service..*(..))"
)
public void mgBizBoundary() {
}
```

따라서 적용 범위는 단순히 이름이 `Service`로 끝나는 클래스가 아니라:

```text
nhnis.mg.co.a.application.service..
```

아래의 **public 메서드**입니다.

# 2. 업무 선처리 — `@Before`

업무 Service가 실행되기 직전에 `BizPrePostAspect`가 호출됩니다.

```text
Facade
   ↓
Service Proxy
   ↓
┌──────────────────────────────┐
│ BizPrePostAspect @Before     │
│                              │
│ ① 업무 선처리 START          │
│ ② GUID                       │
│ ③ ServiceId                  │
│ ④ Service Class / Method     │
│ ⑤ BRC                        │
│ ⑥ 업무 선처리 END            │
│ ⑦ 업무 처리 START            │
└─────────────┬────────────────┘
              │
              ▼
           Service
```

현재 AS-IS에서 선처리가 하는 핵심은 **업무 실행 추적과 로그**입니다.

대표 정보는 다음과 같습니다.

| 정보          | 의미                     |
| ------------- | ------------------------ |
| GUID          | 전체 요청 추적 ID        |
| ServiceId     | 어떤 거래인지            |
| Service Class | 어느 업무 Service인지    |
| Method        | 어떤 메서드를 실행하는지 |
| BRC           | 관련 업무/점 정보        |
| Start Log     | 업무 처리 시작 시점      |

중요한 점은 현재 선처리에서 다음 기능은 **하지 않는다는 것**입니다.

```text
업무 입력 Validation         X
거래통제                     X
DB INSERT                    X
거래이력 저장                X
Transaction 시작             X
Timeout 시작                 X
예외 응답 생성               X
```

즉 현재 `BizPrePostAspect`는 **업무 제어 엔진보다는 업무 실행 관찰 경계**에 가깝습니다.

# 3. 실제 업무 처리는 Service

선처리가 정상적으로 끝나면 실제 Service 메서드가 실행됩니다.

```text
BizPrePostAspect.before()
           │
           ▼
       Business Service
           │
           ├─ 업무 입력 검증
           │
           ├─ 업무 처리순서
           │
           ├─ 업무 Rule
           │
           ├─ DAO 호출
           │
           ├─ 외부 연계
           │
           └─ 결과 DTO 생성
```

현재 계층 구조상 실제 PDMG AS-IS는 독립적인 Rule 패키지가 일반화되어 있지 않아 상당수 업무 규칙이 Service에 존재합니다.

```text
[현재 AS-IS]

Service
 ├─ Validation
 ├─ Business Rule
 ├─ Processing
 └─ DAO


[권장 TO-BE]

Service
 ├─ Use Case 흐름
 ├─ Rule
 ├─ DAO
 └─ Integration
```

# 4. 정상 업무 후처리 — `@AfterReturning`

Service가 **예외 없이 정상적으로 반환된 경우에만** 후처리가 실행됩니다.

```text
Service
   │
   │ 정상 return
   ▼
┌──────────────────────────────────┐
│ BizPrePostAspect                 │
│ @AfterReturning                  │
│                                  │
│ ① 업무 처리 END                  │
│ ② 업무 후처리 START              │
│ ③ Response DTO Logging           │
│ ④ 업무 후처리 END                │
└───────────────┬──────────────────┘
                │
                ▼
             Facade
```

현행 코드에서 후처리도 **DB UPDATE나 이력 INSERT가 아니라 정상 종료 로그와 응답 DTO 관찰**이 중심입니다.

따라서:

```text
bizPostEnd
```

로그가 있다고 해서:

```text
DB COMMIT 완료
```

를 의미하지는 않습니다.

정확하게는:

```text
bizPostEnd
=
Service가 정상적으로 반환되었다.
```

라는 의미입니다.

최종 Commit은 그보다 바깥 Transaction 경계가 결정합니다.

---

# 5. Service에서 예외가 발생하면

이 부분이 중요합니다.

현재 후처리는:

```java
@AfterReturning
```

이므로 예외가 발생하면 **정상 후처리가 실행되지 않습니다.**

```text
BizPrePostAspect @Before
        │
        ▼
      Service
        │
        X BizException / RuntimeException
        │
        ▼
 @AfterReturning 실행 안 함
        │
        ▼
      예외 전파
        │
        ▼
 Transaction ROLLBACK
        │
        ▼
 GlobalExceptionHandler
        │
        ▼
 표준 오류 응답
```

로그로 보면:

```text
정상

업무 선처리 START
업무 선처리 END
업무 처리 START

Service 처리

업무 처리 END
업무 후처리 START
업무 후처리 END
```

반면 오류 발생 시에는:

```text
업무 선처리 START
업무 선처리 END
업무 처리 START

Service 처리
     ↓
Exception

업무 처리 END 없음
업무 후처리 START 없음
업무 후처리 END 없음
```

이런 식으로 나타날 수 있습니다.

# 6. 오류 후처리는 별도로 생각해야 한다

현재 `BizPrePostAspect`의 정상 후처리는 `@AfterReturning`입니다.

따라서 다음과 같은 **오류 업무 후처리**를 필요로 한다면 별도의 설계가 필요합니다.

```text
Service
   │
   X Exception
   │
   ▼
@AfterThrowing / @Around
   │
   ├─ 오류 업무 이력
   ├─ 업무 실패 Metric
   └─ 업무 실패 Audit
```

그러나 이것을 무조건 현재 Transaction에 넣으면 문제가 생깁니다.

예:

```text
TX BEGIN
   │
   ├─ 업무 UPDATE
   │
   X Exception
   │
   ├─ 오류이력 INSERT
   │
   ▼
ROLLBACK
```

그러면:

```text
업무 UPDATE      ROLLBACK
오류이력 INSERT  ROLLBACK
```

이 되어 **오류 기록까지 사라질 수 있습니다.**

따라서 반드시 남겨야 하는 실패 이력이라면:

```text
Main TX
   │
   X Exception
   │
   ▼
Error History Service
   │
   └─ REQUIRES_NEW
          │
          ├─ TX #2 BEGIN
          ├─ 오류이력 INSERT
          └─ COMMIT
   │
   ▼
Main TX ROLLBACK
```

처럼 별도 Transaction을 고려할 수 있습니다.

다만 현재 자료에서는 이러한 오류 이력 INSERT가 `BizPrePostAspect`에 구현되어 있는 것은 아닙니다. **TO-BE 설계 영역**입니다.

# 7. Transaction과 업무 선후처리 관계

업무 Aspect 자체가 Transaction을 만드는 것은 아닙니다.

```text
BizPrePostAspect
      ≠
Transaction Manager
```

현재 구조에서는 Timeout ON이면 바깥 Worker의 `TransactionTemplate`이 Transaction을 시작할 수 있습니다.

```text
Request Thread
     ↓
Timeout Executor
     ↓
Worker Thread
     ↓
TransactionTemplate
     ↓
========================== TX BEGIN
     ↓
Dispatcher
     ↓
Handler
     ↓
Facade
     ↓
BizPrePostAspect @Before
     ↓
Service
     ↓
DAO / Mapper / DB
     ↓
BizPrePostAspect @AfterReturning
     ↓
Facade Return
     ↓
========================== COMMIT
```

즉 같은 Worker Thread에 있는 경우 업무 선·후처리는 기존 TX 안에서 실행됩니다.

중요한 것은:

```text
Aspect가 TX에 참여한다
             ≠
Aspect가 TX를 시작한다
```

입니다.

# 8. 후처리에 DB UPDATE를 추가하면 어떻게 되는가

향후 다음과 같은 업무 후처리를 넣는다고 가정해 보겠습니다.

```text
Service
    ↓
업무처리
    ↓
BizPostProcess
    ↓
업무 처리상태 UPDATE
```

같은 Thread, 같은 DataSource, 같은 TransactionManager라면:

```text
TX BEGIN
 │
 ├─ Service INSERT
 ├─ Service UPDATE
 ├─ DAO SQL
 │
 ├─ 업무 후처리 UPDATE
 │
 └─ 정상
      ↓
    COMMIT
```

모두 같은 Transaction에 참여합니다.

후처리에서 문제가 발생하면:

```text
Service 성공
     ↓
후처리 UPDATE
     X
Exception
     ↓
ROLLBACK
```

되어 **본 업무까지 함께 Rollback**될 수 있습니다.

이것은 매우 중요한 아키텍처 결정입니다.

따라서 후처리는 성격에 따라 나누는 것이 좋습니다.

| 후처리 종류        | 권장 방식           |
| ------------------ | ------------------- |
| 업무 정합성에 필수 | Main TX 참여        |
| 업무 상태 UPDATE   | Main TX 참여 검토   |
| 단순 로그          | 비 DB/관찰 중심     |
| Metric             | Main TX와 분리      |
| Audit              | 별도 저장 전략 검토 |
| 실패이력           | `REQUIRES_NEW` 검토 |
| 외부 메시지 전송   | Outbox 등 검토      |

# 9. `PdmgBizTxFlowAspect`와의 관계

현재 업무 Service 주변에는 `BizPrePostAspect` 외에 `PdmgBizTxFlowAspect`도 존재합니다.

개념적인 실행 순서는:

```text
PdmgBizTxFlowAspect
@Order(50)
     │
     │ Around START
     ▼
BizPrePostAspect
@Order(100)
     │
     │ @Before
     ▼
Service
     │
     ▼
BizPrePostAspect
@AfterReturning
     │
     ▼
PdmgBizTxFlowAspect
Around END
```

역할은 다릅니다.

```text
PdmgBizTxFlowAspect
=
Handler / Facade / Service / DAO
계층 전체 실행 흐름 관찰


BizPrePostAspect
=
Business Service 실행
선·후처리
```

즉 하나는 **계층 흐름 추적**, 하나는 **업무 Service 경계 관찰**입니다.

# 10. 세 종류 선·후처리를 최종 비교하면

| 구분              | System             | TCF                 | Business                |
| ----------------- | ------------------ | ------------------- | ----------------------- |
| 대표 구현         | Filter/Interceptor | STF/ETF             | `BizPrePostAspect`      |
| 대상              | HTTP 요청 전체     | 거래 전체           | Service                 |
| 시작 질문         | 요청이 유효한가?   | 거래 실행 가능한가? | 어떤 업무가 실행되는가? |
| JWT               | O                  | X                   | X                       |
| GUID/Context      | O                  | 사용                | 사용                    |
| 거래통제          | X                  | **O**               | X                       |
| Timeout           | X                  | **O**               | X                       |
| ServiceId Routing | X                  | Dispatcher          | X                       |
| 업무 Validation   | X                  | X                   | Service/Rule            |
| 업무 로그         | 일부               | 거래로그            | **O**                   |
| 업무 DTO          | 전달               | 전달                | **사용**                |
| DB 업무처리       | X                  | X                   | **O**                   |
| 표준응답 생성     | System Post        | 결과 전달           | X                       |

한 문장씩 표현하면:

```text
SYSTEM PRE
"이 HTTP 요청이 정상적인가?"

TCF STF
"이 ServiceId 거래를 지금 실행해도 되는가?"

BUSINESS PRE
"실제 업무 Service 실행을 시작한다."

BUSINESS SERVICE
"업무를 수행한다."

BUSINESS POST
"업무 Service가 정상적으로 끝났다."

TCF ETF
"거래 실행을 종료한다."

SYSTEM POST
"외부에 표준 응답을 반환한다."
```

# 11. 권장 TO-BE 업무 선·후처리 구조

현재 구조를 발전시킨다면 `BizPrePostAspect` 하나에 모든 기능을 몰아넣기보다는 **관찰과 업무 공통처리를 분리**하는 것이 좋습니다.

```text
                     Business Boundary

Handler
   │
   ▼
Facade
   │
   │ Transaction Boundary
   ▼
┌────────────────────────────────────────┐
│ Business Observability Aspect          │
│                                        │
│ GUID / ServiceId / Method / Metrics    │
└────────────────┬───────────────────────┘
                 │
                 ▼
┌────────────────────────────────────────┐
│ Business Pre Processor                 │
│                                        │
│ 업무 공통 Validation                   │
│ 업무 Context                           │
│ 공통 업무 정책                         │
└────────────────┬───────────────────────┘
                 │
                 ▼
             Service
           ┌─────┼─────┐
           ▼     ▼     ▼
         Rule   DAO  Integration
                 │
                 ▼
                DB
                 │
                 ▼
┌────────────────────────────────────────┐
│ Business Post Processor                │
│                                        │
│ 업무상태 / 결과 후처리                 │
│ 필요한 경우 Main TX 참여               │
└────────────────┬───────────────────────┘
                 │
                 ▼
┌────────────────────────────────────────┐
│ Business Observability Aspect          │
│                                        │
│ Result / Elapsed / Metric              │
└────────────────────────────────────────┘
```

이렇게 하면 **“로그를 위한 Aspect”와 “업무 결과를 변경하는 Processor”**를 분리할 수 있습니다.

## 12. 현재 PDMG 기준 결론

현재 AS-IS는 이렇게 기억하면 가장 정확합니다.

```text
Dispatcher
    ↓
Handler
    ↓
Facade
    ↓
────────────────────────────────────
BizPrePostAspect @Before
    ↓
Service
    ↓
DAO → Mapper → DB
    ↓
BizPrePostAspect @AfterReturning
────────────────────────────────────
    ↓
Facade
    ↓
Handler
```

그리고 핵심 원칙은 5가지입니다.

1. **업무 선·후처리의 기준점은 Service 경계**입니다.
2. 현재 `BizPrePostAspect`는 **주로 로그·추적 목적**이며 업무 Validation/DB 후처리를 수행하지 않습니다.
3. `@AfterReturning`이므로 **Service 예외 시 정상 후처리는 실행되지 않습니다.**
4. Aspect는 Transaction을 시작하지 않으며 **바깥 Worker/Facade Transaction이 있으면 그 안에서 실행**됩니다.
5. 향후 DB 후처리를 추가할 경우 **본 업무와 동일 TX로 묶을 것인지, `REQUIRES_NEW` 등 별도 TX로 분리할 것인지 반드시 명시적으로 설계**해야 합니다.

따라서 PDMG의 선·후처리 전체 구조를 최종적으로 연결하면 **`System Pre/Post → TCF STF/ETF → Business Pre/Post`의 3단계 아키텍처**로 보는 것이 가장 정확합니다.
