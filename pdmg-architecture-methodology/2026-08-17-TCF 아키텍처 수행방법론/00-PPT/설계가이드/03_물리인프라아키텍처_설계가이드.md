# 03. 물리 인프라 아키텍처 — 설계가이드

> **기준**: [`NSIGHT_아키텍처_정의서_통합본_20260825_분석.md`](../NSIGHT_아키텍처_정의서_통합본_20260825_분석.md)
> **PPT 장**: 3장 · 슬라이드 63~77
> **방법론 폴더**: `04-PHYSICAL`
> **작성일**: 2026-08-26

---

## 1. 목적

논리 노드를 센터·서버·소프트웨어로 매핑하고, 운영/DR/개발/선도 환경의 하드웨어·소프트웨어 구성과 목록을 설계한다.

## 2. 적용 범위

- **포함**: HW 구성도(운영·DR·개발·선도), SW 구성도, HW/SW 목록, 센터(의왕·안성 등) 배치
- **제외**: DB 이중화·OGG 상세(4장), 호스트명명·FS·계정·포트(5장) — 단, 물리도와 정합은 필수
- **독자**: 인프라, 클라우드/IaaS, SA

## 3. 설계 원칙

1. **논리→물리 1:N 명시**: 논리 시스템 그룹이 어떤 Hostname 집합에 매핑되는지 표로 남긴다.
2. **센터 분리**: 주센터(의왕)·DR센터(안성) 역할을 물리도에 고정한다.
3. **이중화 가시화**: 운영 WEB/WAS 등 Active 쌍(#1,#2)과 DR 대응(#51,#52 등)을 대응표로 관리한다.
4. **SW 버전 고정**: 운영 SW 목록(종·버전)을 변경관리 대상으로 둔다.
5. **용량은 별도 근거**: Capacity 수치는 `시스템용량` 분석·인벤토리를 근거로 인용한다.

## 4. 설계 기준 (결정 규칙)

- 서버 Type(IaaS/x86/Linux 등)·시스템 그룹·Hostname·한글 서버명을 한 행에 기입한다.
- 운영 SW 구성도와 DR/개발/선도 구성을 환경별로 분리해 작성한다.
- 논리 컴포넌트(예: 마케팅플랫폼 WEB) 없는 물리 서버를 신설하지 않는다(예외는 ADR).
- DR 서버는 운영 역할 대응 관계를 명시한다.

## 5. 구성·경계

```text
센터
├─ 의왕 (주) : 운영·개발·선도
└─ 안성 (DR) : DR

물리 산출물
├─ HW 구성도 × 환경
├─ SW 구성도 × 환경
├─ HW 목록
└─ SW 목록 (버전)
```

## 6. Do / Don't

| Do | Don't |
|---|---|
| 논리 시스템 그룹명으로 물리 서버를 라벨링 | Hostname만 있고 업무 그룹이 불명 |
| SW 버전을 목록·구성도에 동기화 | 구성도와 목록의 제품·버전이 불일치 |
| 용량·인벤토리 문서를 교차 참조 | 장표에만 수치를 넣고 근거 파일 없음 |

## 7. 설계 체크리스트

- [ ] 운영/DR/개발/선도 HW·SW 구성도가 존재하는가?
- [ ] Hostname·시스템 그룹·센터가 목록과 일치하는가?
- [ ] 운영↔DR 서버 대응이 정의되었는가?
- [ ] SW 목록 종·버전이 현행인가?
- [ ] 용량 근거 문서가 연결되어 있는가?
