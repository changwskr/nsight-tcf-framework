# 09. 아키텍처 구성 요소 — 설계가이드

> **기준**: [`NSIGHT_아키텍처_정의서_통합본_20260825_분석.md`](../NSIGHT_아키텍처_정의서_통합본_20260825_분석.md)
> **PPT 장**: 9장 · 슬라이드 139~162
> **방법론 폴더**: `05-MECHANISM`
> **작성일**: 2026-08-26

---

## 1. 목적

단말·온라인·배치 프레임워크와 Upload/Download·RD·Inbound·SSO·예외·거래로그·Master Solution 등 동작 가능한 구성 요소의 책임과 연계를 설계한다.

## 2. 적용 범위

- **포함**: 단말 FW, 온라인(NH Cloud FW), 단말↔App 연계(xFrame↔Nhins), 배치 FW(Control-M 등), 연계 메커니즘
- **제외**: 업무 솔루션 기능 사양(10장), NFR/DR 운영(11장)
- **독자**: 프레임워크·공통 개발, 업무 개발 리더

## 3. 설계 원칙

1. **진입점 단일화**: UI→`/ins/{ServiceId}` 등 공식된 Controller 진입을 사용한다.
2. **데이터셋 변환 계약**: xDataSet ↔ Map 변환·Service Context 저장 규칙을 지킨다.
3. **관심사 분리**: Upload/Download/RD/Inbound/SSO/Exception/거래로그를 업무 코드에 인라인하지 말고 메커니즘을 재사용한다.
4. **배치 운영 계약**: 등록·조회·모니터링·스케줄(Control-M Agent) 흐름을 지킨다.
5. **상용 FW 대비**: 자체/상용 기능 경계를 표로 관리하고 중복 구현을 피한다.

## 4. 설계 기준 (결정 규칙)

- 단말-Application 연계는 PT/BT 역할과 ServiceId 인식 절차를 설계서에 포함한다.
- 파일 업/다운로드는 FOS 표준(6장)과 메커니즘 문서를 함께 인용한다.
- Inbound·SSO·RD는 통합개발환경·형상배포 문서와 경로를 맞춘다.
- 예외·거래로그는 GUID(8장)와 상관관계를 유지한다.
- 배치 작업은 자동화 관리 UI·스케줄러·실행정보 모델을 따른다.

## 5. 구성·경계

```text
구성 요소
├─ 단말 프레임워크 (xFrame 등)
├─ 온라인 프레임워크 (NH Cloud / Nhins Controller)
├─ 배치 프레임워크 (Control-M 등)
└─ 연계 메커니즘
   ├─ File Upload / Download
   ├─ RD (레포팅)
   ├─ Inbound
   ├─ SSO
   ├─ 선후처리 · Exception · 거래로그
   └─ Master Solution / 상용 FW 대비
```

## 6. Do / Don't

| Do | Don't |
|---|---|
| ServiceId·표준 Controller 경로 사용 | WAS에 임의 서블릿/우회 URL 난립 |
| 메커니즘 컴포넌트 재사용 | 업/다운로드·SSO를 업무마다 재구현 |
| 배치를 스케줄·모니터링 계약에 등록 | 서버 crontab만으로 운영 배치 운용 |

## 7. 설계 체크리스트

- [ ] 단말↔온라인 연계 계약이 문서화되었는가?
- [ ] Upload/Download/RD/Inbound/SSO 설계가 메커니즘 MD와 맞는가?
- [ ] 예외·거래로그·GUID 상관관계가 있는가?
- [ ] 배치 등록·스케줄·모니터링 경로가 정의되었는가?
- [ ] 형상배포·통합개발환경과 충돌 없는가?
