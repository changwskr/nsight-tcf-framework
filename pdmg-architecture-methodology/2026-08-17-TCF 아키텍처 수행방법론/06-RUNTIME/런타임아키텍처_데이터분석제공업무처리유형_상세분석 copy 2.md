# 런타임 아키텍처 — 데이터 분석/제공 업무 처리 유형 상세 분석

## 1. 핵심 결론

이 장표는 차세대 정보계의 전체 런타임 아키텍처 가운데 **데이터 수집·동기화·변환·분석·제공**에 해당하는 업무 처리 유형을 상세화한 자료다.

원본 장표가 정의한 핵심 처리 유형은 다음 3가지다.

```text
⑧ CDC 실시간 데이터 동기화
⑨ ETL 연계
⑩ 데이터 분석 기반 의사결정 지원
```

장표 상단의 설명은 다음과 같은 업무 목적을 제시한다.

> **계정 처리 업무 데이터와 단위 시스템, 레거시 시스템 정보를 수집하고 분석하여 전략적 업무 판단의 근거가 되는 지표를 확인할 수 있도록 레포트로 서비스를 제공하는 업무 처리 유형**

즉 이 장표는 데이터 처리 전체 흐름을 다음 3단계로 나눈다.

```text
[1. 실시간 데이터 확보]
코어뱅킹 DB
   → CDC
   → RDW

[2. 배치형 데이터 통합]
대내/Legacy/File
   → ETL
   → RDW / ADW

[3. 데이터 분석·제공]
RDW / ADW
   → BI Portal / 신용실적 / Self BI / OLAP
   → 분석 결과 / 레포트
   → 의사결정 지원
```

핵심 아키텍처 메시지는 다음과 같다.

| 유형 | 핵심 역할 | 처리 성격 |
|---|---|---|
| ⑧ CDC | 코어뱅킹 거래 데이터를 RDW로 실시간/준실시간 복제 | 실시간 데이터 동기화 |
| ⑨ ETL | 대내·Legacy·DB·파일 데이터를 변환·적재 | 배치 데이터 통합 |
| ⑩ 분석/제공 | 데이터플랫폼의 데이터를 BI로 분석·제공 | 동기형 정보 제공 |

따라서 이 장표는 단순한 DW 적재 구조가 아니라,

```text
운영 데이터 생성
   ↓
실시간/배치 데이터 통합
   ↓
RDW / ADW 저장
   ↓
BI / 분석 도구
   ↓
전략적 의사결정
```

이라는 **End-to-End Data Runtime Architecture**를 설명한다.

---

## 2.2 상단 설명

원본에서 확인되는 설명:

```text
계정 처리 업무 데이터와 단위 시스템,
레거시 시스템 정보를 수집하고 분석해서
전략적 업무 판단의 근거를 위한 지표를 확인할 수 있도록
레포트로 서비스를 제공하는 업무 처리 유형
```

### 의미

이 문장은 데이터 분석/제공 업무가 단순 조회가 아니라 다음 전체 생명주기를 포함함을 뜻한다.

```text
원천 데이터
  → 수집
  → 동기화
  → 변환
  → 적재
  → 분석
  → 보고
  → 의사결정
```

# 3. 업무 처리 유형 ⑧ — CDC 실시간 데이터 동기화 FACT

원본 우측 설명:

- **코어뱅킹에서 생성되는 고객 거래 정보를 코어뱅킹DB에서 CDC솔루션 기반 (준)실시간으로 정보계 RDW DB에 데이터 동기화**
- **동기(Sync), CDC, 데이터 복제**

장표의 강조선은 다음 구조를 보여준다.

```text
코어 DB
   │
   ▼
 CDC
   │
   ▼
RDW / 실시간 DBMS
```

---

# 4. 업무 처리 유형 ⑨ — ETL 연계 FACT

원본 우측 설명:

- **대내 시스템과 정보계 시스템 간 데이터 변환 동기화 작업을 ETL 솔루션 기반 배치 처리**
- **DB 또는 파일 데이터를 변환 처리**
- **파일 데이터 처리는 FOS를 연계해서 처리**
- **미리 지정된 시간에 Control-M 등 배치 처리 자동화 솔루션을 통해 실행**
- **배치, Control-M, 데이터 적재/변환**

장표의 강조선은 ETL이 데이터플랫폼과 Legacy 영역 사이의 배치형 데이터 이동을 담당함을 보여준다.


## 9.3 CDC의 아키텍처적 의미

이 구조에서 CDC는 단순 DB Copy가 아니라 **운영계와 정보계 사이의 실시간 데이터 공급 파이프라인**이다.

핵심 역할:

- 고객 거래 데이터의 빠른 정보계 반영
- 배치 적재 이전에 Near Real-time 활용 가능
- 마케팅 / 조회 / BI를 위한 최신 데이터 확보

### 구조적 경계

```text
코어뱅킹
   ≠
정보계 RDW
```

직접 DB 조회가 아니라 CDC를 사이에 둠으로써 다음 효과를 기대할 수 있다.

- 운영계 조회 부하 최소화
- 시스템 간 결합도 완화
- 정보계 독립 데이터 활용
- 실시간/준실시간 분석 기반 확보

# 10. CDC 운영 기준

원본 장표는 CDC 상세 운영 항목을 직접 기술하지 않는다.

다만 **ANALYSIS / 권고** 관점에서는 다음 운영 항목이 필요하다.

```text
Capture Position
Apply Position
Replication Lag
Error Count
Retry Count
Checkpoint
```

### 필수 모니터링

| 지표 | 의미 |
|---|---|
| Capture Lag | 원천 변경 감지 지연 |
| Apply Lag | RDW 반영 지연 |
| Replication Error | 복제 실패 |
| Queue Backlog | 적체량 |
| Last Applied Position | 마지막 정상 복제 위치 |


# 12. Control-M / 배치 실행 구조

원본은 `미리 지정된 시간에 Control-M 등 배치 처리 자동화 솔루션을 통해 실행`이라고 명시한다.

```text
[Control-M / Batch Scheduler]
        │
        │ 지정 시간 / 선후행 조건
        ▼
      [ETL Job]
        │
        ├─ Extract
        ├─ Transform
        └─ Load
        │
        ▼
     [RDW / ADW]
```

### 런타임 의미

ETL은 사용자 요청으로 즉시 실행하는 온라인 서비스가 아니라 **스케줄과 선후행 관계를 갖는 배치 런타임**이다.

# 13. ETL과 FOS의 관계

원본은 **파일 데이터 처리는 FOS를 연계해서 처리**한다고 명시한다.

따라서 파일성 ETL은 다음 구조로 해석할 수 있다.

```text
외부/Legacy File
    ↓
   FOS
    ↓
Landing / Input
    ↓
   ETL
    ↓
RDW / ADW
```

### 의미

- FOS는 파일 전송/수신
- ETL은 파일 내용의 데이터 변환/적재
- 두 컴포넌트의 책임을 분리

# 14. CDC와 ETL 비교

| 항목 | ⑧ CDC | ⑨ ETL |
|---|---|---|
| 목적 | 실시간 데이터 동기화 | 대량 데이터 변환/적재 |
| 원천 | 코어 DB 변경정보 | DB / 파일 / Legacy |
| 처리 | 실시간/준실시간 | 배치 |
| 대상 | 주로 RDW | RDW / ADW |
| 변환 | 최소/복제 중심 | 변환/집계 가능 |
| 실행 | 지속형 | 스케줄형 |
| 주요 도구 | CDC Solution | ETL + Control-M |
| 파일 | 대상 아님 | FOS 연계 |

핵심 원칙:

```text
CDC = 빠른 복제
ETL = 계획된 변환/적재
```

두 역할을 섞으면 안 된다.

```text
    → ADW
```

# 20. 데이터 정합성 아키텍처

CDC와 ETL을 동시에 사용하는 구조에서는 정합성 기준이 중요하다.

```text
Source
  │
  ├─ CDC → RDW
  │
  └─ ETL → RDW / ADW
```

동일 데이터가 양 경로로 중복 유입될 경우 기준이 없으면 다음 문제가 발생할 수 있다.

- 데이터 중복
- 최신값 역전
- 기준 시점 불일치
- BI 숫자 불일치

### 권고

- 데이터별 Master Path 정의
- CDC 대상과 ETL 대상 분리
- 동일 데이터 중복공급 금지
- 업무일자/기준시점 정의
- Source/Target 대사

---

# 21. 처리유형별 Timeout / SLA 성격

| 처리유형 | SLA 성격 |
|---|---|
| ⑧ CDC | 데이터 Freshness / Replication Lag |
| ⑨ ETL | Batch Window / Completion Time |
| ⑩ BI | 사용자 응답시간 / Query Time |

즉 세 유형은 같은 “데이터 처리”이지만 SLA가 완전히 다르다.

```text
CDC → 얼마나 빨리 따라왔는가?
ETL → 정해진 시간 안에 끝났는가?
BI  → 사용자가 얼마나 빨리 결과를 받는가?
```

```text
   ↓

   ↓
```

즉 사용자가 본 숫자가 **어디서 왔는지 역추적 가능**해야 한다.

# 25. 성능 및 용량 관점

세 처리 유형은 자원 사용 특성이 서로 다르다.

```text
CDC
 → 지속형 I/O + 네트워크

ETL
 → 배치성 CPU + I/O + DB Write

BI / OLAP / Self BI
 → 대량 Query + CPU + Memory + Temp
```

### 핵심 원칙

```text
CDC 부하 ≠ ETL 부하 ≠ BI 분석 부하
```

따라서 동일 자원에서 무제한 경쟁하면 안 된다.

### 권고

- CDC 전용 처리자원
- ETL Batch Window 관리
- ADW 분석자원 격리
- Self-BI Resource Group
- 장기 SQL 제한
- 대량 Query Timeout

- 데이터 계보 ID
- 재처리 시나리오 상세

따라서 본 문서에서는 원본 장표의 설명을 **FACT**로 유지하고, 운영·설계 보강 내용은 **ANALYSIS / 권고**로 구분한다.

## 32.1 CDC·ETL 데이터 파이프라인 공통 통제

| 통제 항목 | CDC 적용 기준 | ETL 적용 기준 |
|---|---|---|
| Watermark | Source Commit 위치 또는 SCN을 Watermark로 보존한다. | 업무일자·증분키·최종변경시각을 Watermark로 관리한다. |
| 체크포인트 | Capture·전송·Apply 단계의 체크포인트를 분리하여 장애 위치를 식별한다. | 추출·변환·적재 단계별 체크포인트와 Job Run ID를 기록한다. |
| 멱등 | 동일 트랜잭션 재수신 시 Target에 중복 반영되지 않도록 원천 키와 위치정보를 사용한다. | 동일 배치 재실행 시 Merge·교체 적재 등으로 결과가 한 번만 존재하게 한다. |
| 정합성 | Source/Target 건수·합계·해시와 누락 구간을 대사한다. | 입력·Reject·출력 건수 및 주요 금액 합계를 대사한다. |
| 재처리 | 보존된 로그 위치부터 안전하게 재개하고 Gap을 별도 추적한다. | 영향 파티션·업무일자 범위를 한정하여 재실행한다. |
| 데이터 최신성 | Capture Lag·Apply Lag과 RDW 반영시각을 공개한다. | 예정 완료시각, 실제 완료시각, ADW/마트 기준시각을 공개한다. |

```text
Source Commit
   │ Watermark / Capture 체크포인트
   ▼
CDC 또는 ETL
   │ Apply·Job 체크포인트 / 멱등 처리
   ▼
RDW · ADW
   │ 정합성 대사 / 데이터 최신성 표시
   ▼
BI Dataset · Report · 의사결정
```

운영 대시보드에는 최소한 `Capture Lag`, `Apply Lag`, ETL 시작·종료시각, 처리·오류·Reject 건수, 최종 성공 Watermark와 보고서 데이터 기준시각을 함께 표시해야 한다.

> 이 통제표는 원본 장표의 CDC·ETL 구조를 운영 가능한 수준으로 구체화한 분석·권고 사항이다.

# 33. 최종 평가

이 장표는 데이터 분석/제공 업무를 다음 3단계로 매우 명확하게 나눈다.

```text
⑧ CDC
= 실시간 데이터 확보

⑨ ETL
= 배치 데이터 통합/변환

⑩ BI 분석
= 데이터 활용/의사결정 지원
```

즉 전체 구조는 다음과 같다.

```text
Operational Data
     │
     ├─ CDC ───────────────▶ RDW
     │
     └─ ETL / FOS ─────────▶ RDW / ADW
                               │
                               ▼
                     BI Portal / OLAP / Self BI
                               │
                               ▼
                       Report / Indicator
                               │
                               ▼
                        Business Decision
```

이 아키텍처의 핵심 장점은 다음과 같다.

1. **실시간 복제와 배치 변환의 책임을 분리한다.**
2. **RDW와 ADW를 데이터 활용 목적에 따라 분리한다.**
3. **데이터 적재와 분석/제공을 명확히 구분한다.**
4. **Control-M, FOS, ETL 등 운영자동화 경로까지 포함한다.**
5. **최종 데이터 활용 목적을 ‘의사결정 지원’으로 연결한다.**

후속 상세설계에서는 반드시 다음이 이어져야 한다.

```text
Source Data
   ↓
CDC / ETL Contract
   ↓
RDW / ADW Data Ownership
   ↓
Quality / Lineage / Reconciliation
   ↓
BI Dataset / Report
   ↓
Security / Performance / Operation
```

결론적으로 이 장표는 **차세대 정보계의 데이터 생성부터 분석결과 제공까지를 연결하는 핵심 Data Runtime Architecture**이며, 향후 CDC 설계서, ETL 설계서, RDW/ADW 데이터 흐름도, BI 인터페이스 정의서, 데이터 계보 및 운영표준의 기준점으로 활용할 수 있다.
