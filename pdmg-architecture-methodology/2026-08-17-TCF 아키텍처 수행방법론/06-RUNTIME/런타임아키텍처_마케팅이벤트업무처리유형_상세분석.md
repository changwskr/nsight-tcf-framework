# 런타임 아키텍처 — 마케팅 이벤트 업무 처리 유형 상세 분석

## 1. 핵심 결론

이 장표는 고객의 비대면 채널 행동을 실시간으로 수집하고, 분석·규칙 판단을 거쳐 SMS·App Push·e-Mail 등의 고객 접점으로 오퍼를 전달하는 **이벤트 기반 마케팅 런타임 구조**를 정의한다.

원본이 구분한 업무 유형은 다음 두 가지다.

```text
⑥ 실시간 고객 반응형 정보 수집
⑦ 실시간 고객 오퍼링 제공
```

전체 흐름은 다음과 같이 해석할 수 있다.

```text
인터넷뱅킹·스마트뱅킹 고객행동
            │ 비대면 로그/이벤트
            ▼
      Wise Collector
            │ Publish
            ▼
   Kafka 고객행동 데이터
            │ Subscribe
            ▼
 고객상태·행동정보 처리 Daemon
            │ 이벤트 정보
            ▼
       실시간 처리 EBM ──────┐
            ▲                │ 오퍼 결정
            │ RDW 분석정보    ▼
            └────────────── RDW
                             │
                             ▼
                            UMS
                             │
                  SMS · PUSH · e-Mail
```

핵심은 **⑥ 수집 파이프라인과 ⑦ 실행 파이프라인을 분리**하는 것이다. Kafka가 양자를 시간적으로 분리해 순간 트래픽을 완충하고, EBM은 고객 상태·분석정보·마케팅 규칙을 조합하여 오퍼를 결정하며, UMS는 실제 메시지 전달 채널을 추상화한다.

---

## 2. 원본 장표 FACT 전사

### 2.1 상단 설명

> 고객 마케팅을 위해 고객 서비스 사용 정보를 수집·분석하고, 마케팅 대상 규칙을 설정하여 고객 접점을 통해 마케팅 이벤트를 실행하는 업무 처리 유형

### 2.2 ⑥ 실시간 고객 반응형 정보 수집

- 비대면 고객채널(인터넷뱅킹, 스마트뱅킹)의 서비스 사용 정보를 `Wise Collector`로 저장한다.
- `Wise Collector`로부터 Publish/Subscribe Streaming 방식으로 전송받는다.
- Kafka를 기반으로 인증된 채널이 Topic을 Subscribe하여 처리한다.
- 비동기(Async), JSON/HTTP, 스트리밍 수집 방식이다.

### 2.3 ⑦ 실시간 고객 오퍼링 제공

- 고객채널에서 수집한 서비스 이용정보를 기반으로 사전 정의한 규칙에 따라 실시간 분석한다.
- 사용자 접점(SMS, App Push, e-Mail)으로 마케팅을 수행한다.
- RDW 분석정보를 주기적으로 조회하여 대상을 식별한다.
- UMS를 통해 사용자 접점으로 마케팅 메시지를 전송한다.
- 준실시간·비동기(Async), UMS API, 메시지 발송 요청 방식이다.

> 표기된 제품명과 처리 방식은 장표의 FACT이며, 구체적인 Topic명·API·주기는 별도 상세설계에서 확인해야 한다.

## 3. 구성요소와 책임

| 구성요소 | 주 책임 | 입력 | 출력 |
|---|---|---|---|
| 인터넷/스마트뱅킹 | 고객 행동 발생 원천 | 사용자 행위 | 비대면 로그·이벤트 |
| Wise Collector Proxy | 채널 접근 수집·중계 | 채널 로그 | 수집 이벤트 |
| Wise Collector | 이벤트 정규화 및 Publish | 수집 이벤트 | Kafka 메시지 |
| Kafka | 내구성 있는 이벤트 버퍼·분배 | 고객행동 이벤트 | 구독자별 이벤트 |
| 고객상태 | 고객별 처리 상태 관리 | 행동 이벤트 | 최신 고객 상태 |
| 행동정보 처리서버/Daemon | 이벤트 검증·가공·상태 갱신 | Kafka 이벤트 | 행동정보·이벤트 정보 |
| RDW | 실시간/준실시간 데이터 및 분석정보 제공 | 행동정보·분석 결과 | 고객 분석정보·대상군 |
| 실시간 처리서버 EBM | 규칙 평가와 오퍼 결정 | 이벤트·고객상태·분석정보 | 발송 요청 |
| UMS | 채널별 메시지 발송 추상화 | 발송 요청 | SMS·Push·e-Mail |

### 책임 경계

- 수집 계층은 고객 행동을 잃지 않고 표준 이벤트로 만드는 데 책임을 진다.
- Kafka는 생산자와 소비자의 처리속도 차이를 흡수한다.
- 행동정보 처리 계층은 이벤트 의미 해석과 고객상태 갱신에 책임을 진다.
- EBM은 대상·시점·콘텐츠·빈도를 판단한다.
- UMS는 실제 채널 전송과 채널별 결과 반환을 담당한다.

## 4. ⑥ 실시간 고객 반응형 정보 수집

### 4.1 런타임 흐름

```text
[고객 행위]
    │
    ▼
[인터넷/스마트뱅킹]
    │ 비대면 로그
    ▼
[Wise Collector Proxy]
    │
    ▼
[Wise Collector]
    │ Publish(JSON 이벤트)
    ▼
[Kafka Topic]
    │ Subscribe
    ▼
[행동정보 처리 Daemon]
    ├── 스키마 검증
    ├── 중복 판정
    ├── 고객/세션 식별
    ├── 고객상태 갱신
    └── 이벤트 정보 생성
```

### 4.2 이벤트 최소 계약

| 필드 | 목적 |
|---|---|
| `eventId` | 중복 제거와 추적을 위한 유일 ID |
| `eventType` | 로그인·조회·클릭·이탈 등 행동 유형 |
| `occurredAt` | 고객 행위가 실제 발생한 시각 |
| `receivedAt` | 수집 계층이 수신한 시각 |
| `channel` | 인터넷·모바일 등 발생 채널 |
| `customerKey` | 토큰화 또는 가명처리한 고객 식별자 |
| `sessionId` | 동일 방문 흐름 연결 |
| `traceId` | Wise Collector부터 EBM까지 종단 추적 |
| `schemaVersion` | 이벤트 스키마 버전 |
| `consentCode` | 활용 가능한 동의 범위 |
| `payload` | 행동별 확장 데이터 |

### 4.3 전달 보장

Kafka 기반 구조는 일반적으로 `at-least-once` 전달을 전제로 설계하는 편이 안전하다. 따라서 소비자는 같은 `eventId`를 다시 받아도 결과가 한 번만 반영되도록 멱등성을 가져야 한다.

```text
수신 → 스키마 검증 → 중복 확인 → 업무 처리 → 상태 저장 → Offset Commit
             │ 오류
             ├── 재시도 Topic
             └── DLQ(격리) + 운영 알림
```

- Offset은 업무 상태 저장이 성공한 뒤 Commit한다.
- Poison Message는 무한 재시도하지 않고 DLQ로 격리한다.
- 파티션 키는 고객 단위 순서가 필요하면 `customerKey`를 사용한다.
- 재처리 시 원본 이벤트와 재처리 이력을 보존한다.

## 5. ⑦ 실시간 고객 오퍼링 제공

### 5.1 런타임 흐름

```text
[행동 이벤트/고객상태]       [RDW 분석정보·대상군]
          │                         │ 주기 조회
          └──────────┬──────────────┘
                     ▼
             [실시간 처리 EBM]
                ├── 동의 확인
                ├── 대상 규칙 평가
                ├── 제외/빈도 정책
                ├── 우선순위·충돌 조정
                └── 콘텐츠/채널 결정
                     │ UMS API
                     ▼
                    [UMS]
              ┌──────┼────────┐
              ▼      ▼        ▼
             SMS   App Push  e-Mail
                     │
                     ▼
              발송·도달·실패 결과
```

### 5.2 오퍼 결정 순서

1. 이벤트와 고객상태를 결합한다.
2. 수신동의·목적동의·채널동의를 확인한다.
3. RDW의 분석정보 또는 대상군을 조회한다.
4. 캠페인 대상 규칙과 제외 규칙을 평가한다.
5. 동일 고객의 접촉 빈도와 메시지 충돌을 조정한다.
6. 적합한 콘텐츠와 전달 채널을 선택한다.
7. UMS API로 발송을 요청한다.
8. 발송 결과와 고객 반응을 다시 피드백한다.

### 5.3 준실시간 의미

⑥은 이벤트 도착 직후 처리되는 스트리밍 경로지만, ⑦에는 RDW 분석정보의 주기 조회와 UMS 발송이 포함된다. 따라서 종단 지연은 다음 합으로 관리해야 한다.

```text
수집 지연 + Kafka 대기 + 행동처리 + 규칙평가 + RDW 조회 + UMS 접수/발송
```

`실시간`이라는 명칭만 사용하지 말고 서비스별 목표 지연을 수치화해야 한다. 예를 들어 수집 P95, 판단 P95, UMS 접수 P95와 종단 P95를 각각 정의한다.

## 6. 데이터·제어 흐름 분리

| 흐름 | 경로 | 특성 |
|---|---|---|
| 행동 데이터 | 채널 → Wise Collector → Kafka → 처리서버 | 대량·비동기·스트리밍 |
| 분석 데이터 | 처리서버/ETL → RDW | 실시간 또는 준실시간 적재 |
| 의사결정 데이터 | RDW → EBM | 고객 속성·점수·대상군 조회 |
| 발송 제어 | EBM → UMS | API 기반 명령 |
| 결과 피드백 | UMS/채널 → 이벤트 파이프라인 | 발송·도달·클릭·전환 이벤트 |

메시지 본문 전체를 제어 로그에 복제하지 않고, 이벤트 ID·캠페인 ID·콘텐츠 버전·결과 코드 중심으로 관측하는 것이 바람직하다.

## 7. 오류·재처리 메커니즘

| 실패 구간 | 처리 기준 |
|---|---|
| Wise Collector 수집 실패 | 로컬 버퍼·재전송 및 유실 알림 |
| Kafka Publish 실패 | 제한된 지수 백오프, 중복 가능한 eventId 유지 |
| 스키마 오류 | DLQ 격리, 원문·오류사유·스키마 버전 기록 |
| 행동 처리 실패 | 재시도 Topic 후 한도 초과 시 운영 개입 |
| RDW 조회 실패 | 짧은 캐시 또는 해당 오퍼 보류; 오래된 정보 사용 여부를 정책화 |
| EBM 규칙 오류 | 캠페인 비활성화, 룰 버전 롤백 |
| UMS 호출 실패 | 멱등한 발송 요청 ID로 제한 재시도 |
| 채널 발송 실패 | 채널 대체 여부를 동의·정책 범위 안에서 결정 |

발송 재시도는 중복 메시지로 고객 불편을 만들 수 있으므로 `messageRequestId`의 멱등성을 UMS와 공동 보장해야 한다.

## 8. 개인정보·동의·보안

- 고객 식별자는 Kafka와 로그에서 원문 주민번호·계좌번호 대신 토큰화 키를 사용한다.
- 이벤트 수집 목적과 보유기간을 명시하고 만료 데이터를 삭제한다.
- 마케팅 수신동의, 매체별 동의, 야간 발송 제한을 EBM 판단 전에 확인한다.
- UMS로 전달하는 속성은 템플릿 치환에 필요한 최소 데이터로 제한한다.
- Topic 생산·소비 권한은 애플리케이션별 최소 권한으로 분리한다.
- 전송구간 암호화, Secret 중앙관리, 감사 로그 위변조 방지를 적용한다.
- 고객의 동의 철회가 캐시와 대상군에 신속히 반영되는지 검증한다.

## 9. 관측성 지표

### 수집 파이프라인

- 초당 이벤트 수와 Publish 성공률
- Kafka Consumer Lag 및 파티션 편중
- 이벤트 발생시각 대비 수신·처리 지연
- 스키마 오류·중복·DLQ 건수
- 고객상태 갱신 성공률

### 오퍼링 파이프라인

- 규칙 평가 건수·대상 선정률·제외율
- RDW 조회 지연과 데이터 최신성
- UMS 접수 성공률 및 채널별 발송 성공률
- 발송·도달·클릭·전환율
- 고객별 접촉 빈도 초과 차단 건수
- 캠페인·채널별 종단 P95/P99 지연

모든 지표는 `traceId`, `eventId`, `campaignId`, `messageRequestId`로 연결할 수 있어야 한다.

## 10. 용량 및 성능 설계

- 최대 이벤트 TPS, 평균·최대 메시지 크기와 보존기간으로 Kafka 용량을 산정한다.
- 파티션 수는 목표 처리량뿐 아니라 고객별 순서, 소비자 병렬성과 재처리 시간을 함께 고려한다.
- EBM 규칙은 캠페인 수 증가에 따라 평가 복잡도가 급증하지 않도록 인덱싱한다.
- RDW 조회는 개별 고객 반복 조회보다 사전 계산된 점수·대상군 또는 캐시 사용을 검토한다.
- UMS 장애 시 무제한 적체되지 않도록 큐 상한·만료시간·백프레셔를 둔다.

## 12. 테스트 기준

1. 같은 `eventId`를 반복 전송해도 고객상태가 중복 반영되지 않는다.
2. Kafka 소비자 중단 후 재기동 시 미처리 이벤트부터 복구된다.
3. 잘못된 스키마는 DLQ로 격리되고 정상 이벤트는 계속 처리된다.
4. 고객별 순서가 필요한 이벤트가 동일 파티션에서 순서대로 처리된다.
5. 동의 철회 고객은 캐시·대상군에 남아 있어도 발송되지 않는다.
6. 같은 `messageRequestId` 재요청 시 UMS가 중복 발송하지 않는다.
7. RDW 지연·장애 시 오퍼 보류 또는 대체 정책이 의도대로 작동한다.
8. 캠페인 우선순위와 접촉 빈도 제한이 충돌 상황에서 적용된다.
9. 순간 트래픽 급증 시 Consumer Lag이 복구 목표시간 안에 해소된다.
10. traceId로 수집부터 발송 결과까지 종단 추적할 수 있다.

## 14. 최종 평가

이 장표는 단순 메시지 발송 구조가 아니라 다음의 폐루프를 표현한다.

```text
행동 수집 → 상태/분석 → 오퍼 결정 → 메시지 전달 → 반응 재수집
    ▲                                                   │
    └────────────────── 지속적 피드백 ──────────────────┘
```

구조의 강점은 Kafka로 고객행동 수집과 후속 처리를 분리하고, EBM과 UMS로 의사결정과 전달 책임을 구분한 점이다. 실제 운영 품질은 이벤트 계약, 중복 방지, Consumer Lag, RDW 최신성, 동의정보, UMS 멱등성 및 발송 결과 피드백을 얼마나 명확히 표준화하는지에 달려 있다.
