# 런타임 아키텍처 — 채널 업무 처리 유형 상세 분석

## 1. 핵심 결론

이 장표는 차세대 정보계의 전체 업무 처리 유형 가운데 **채널 업무 처리 유형 3가지**를 상세화한 런타임 아키텍처다.

원본 장표가 정의한 채널 업무 유형은 다음과 같다.

```text
① 정보계 단말 거래
② 통합업무시스템 거래
③ 미니 싱글뷰
```

장표 상단의 설명은 다음 의미를 가진다.

> **정보단말 기반의 차세대 정보계 업무 처리와 통합업무시스템의 미니 싱글뷰·싱글뷰 업무를 HTTP 웹 기반 요청/응답 거래로 처리하는 업무 유형**

즉 세 유형은 화면 형태와 진입 경로는 다르지만, 최종적으로는 **정보계 애플리케이션에 동기식 요청/응답 방식으로 접근한다**는 공통점을 가진다.

| 유형 | 사용자/화면 | 주요 진입 경로 | 통신 특성 | 핵심 포인트 |
|---|---|---|---|---|
| ① 정보계 단말 거래 | 웹 기반 전용 브라우저 / Package UI | 정보계 단말 → 정보계 애플리케이션 | Sync, JSON/HTTP | GUID 기반 거래추적 |
| ② 통합업무시스템 거래 | C/S 기반 업무화면 | 통합업무시스템 → 영업점 MCA → 애플리케이션 | Sync, JSON/HTTP | MCA 경유 거래 |
| ③ 미니 싱글뷰 | C/S 화면 내부 WebView | 통합업무시스템 → WebView → 미니 싱글뷰 | Sync, JSON/HTTP | C/S와 웹 클라이언트 결합 |

이 장표에서 가장 중요한 런타임 원칙은 다음과 같다.

```text
화면 형태는 다르더라도
        ↓
HTTP/JSON 기반 동기 요청/응답
        ↓
차세대 정보계 애플리케이션
        ↓
필요 시 대내연계 / 데이터플랫폼
        ↓
응답 반환
```

또한 ① 정보계 단말 거래에서는 장표가 **거래별 유일 식별자(GUID)를 로그에 기록**한다고 명시하고 있어, GUID가 채널 거래 추적의 핵심 표준임을 확인할 수 있다.

## 2.3 업무 처리 유형 ① — 정보계 단말 거래

원본 우측 설명:

- **웹 기반 전용 브라우저 업무 화면에서 어플리케이션 시스템으로 거래를 요청하고 응답 받는 업무 처리**
- **Json/http 기반 통신으로 클라이언트와 서버간 거래 처리**
- **거래 별 유일한 식별자(GUID)를 로그에 기록**
- **동기(Sync), Json/Http, 요청/응답**

---

## 2.4 업무 처리 유형 ② — 통합업무시스템 거래

원본 우측 설명:

- **C/S 기반 업무 화면에서 어플리케이션 시스템으로 거래를 요청하고 응답 받는 업무 처리**
- **영업점MCA 인터페이스 시스템을 경유해서 거래 요청**
- **동기(Sync), Json/Http, 요청/응답**

---

원본 우측 설명:

- **Json/http 기반 통신으로 클라이언트와 서버간 거래 처리**
- **동기(Sync), Json/Http, 요청/응답**

## 5.3 거래 추적 구조

원본은 ① 유형에서 **“거래별 유일한 식별자(GUID)를 로그에 기록”**한다고 명시한다.

따라서 런타임 추적은 다음처럼 구성해야 한다.

```text
사용자 화면
   │
   ├─ GUID = G-2026-...
   ▼
정보계 단말
   │
   ├─ Request Log(GUID)
   ▼
Application
   │
   ├─ Transaction Log(GUID)
   ├─ Service Log(GUID)
   ├─ Error Log(GUID)
   ▼
DB / 연계
   │
   ├─ SQL Trace / Interface Trace(GUID)
   ▼
Response
   │
   └─ 응답로그(GUID)
```

### 설계 의미

- GUID는 단순 화면 ID가 아니다.
- 거래의 전체 생명주기를 추적하는 **Correlation Key** 역할을 한다.
- 장애 분석에서 사용자 화면 → 애플리케이션 → DB/연계까지 하나의 거래로 추적할 수 있어야 한다.

## 6.3 MCA 역할 분석

이 장표에서 MCA는 통합업무시스템의 핵심 중계점이다.

```text
C/S 업무화면
   ↓
통합업무시스템
   ↓
영업점 MCA
   ↓
정보계 애플리케이션
```

### MCA의 구조적 의미

- 기존 C/S 업무화면과 차세대 정보계 웹/서비스 영역의 경계
- 채널 업무 요청을 표준 방식으로 전달
- 통합업무시스템이 정보계 내부 구현에 직접 결합되는 것을 완화

### 확인 필요

장표는 MCA의 구체적 기능을 모두 설명하지 않는다.

따라서 다음은 상세 인터페이스 정의서 확인이 필요하다.

- 전문 변환 여부
- 인증/인가 처리 여부
- GUID 생성 주체
- Timeout / Retry
- 장애 시 우회/차단 정책

## 7.3 미니 싱글뷰의 아키텍처적 의미

미니 싱글뷰는 일반 통합업무 거래와 다르게 **C/S 화면 안에 웹 클라이언트(WebView)를 삽입하는 하이브리드 채널 패턴**이다.

```text
기존 C/S
   +
WebView
   +
웹 기반 정보계 서비스
```

### 장점

- 기존 C/S UI를 완전히 교체하지 않고 웹 기능을 점진적으로 통합 가능
- 정보계 화면을 웹 기술로 독립 개발 가능
- C/S와 웹 시스템의 단계적 전환에 유리

### 위험

- C/S ↔ WebView 간 사용자 Context 동기화
- 세션/토큰 전달
- 창/화면 종료 시 세션 정리
- GUID/사용자정보 전파
- 브라우저 보안정책
- WebView 버전 관리

# 13. 동기 거래 Timeout 계층

세 유형 모두 동기 요청/응답이므로 Timeout 계층이 중요하다.

```text
사용자/브라우저 Timeout
        >
채널/MCA Timeout
        >
Application Transaction Timeout
        >
대내 API Timeout
        >
DB Query Timeout
```

### 원칙

내부 작업 Timeout이 외부 사용자 Timeout보다 짧아야 한다.

잘못된 예:

```text
Client Timeout        3초
Application Timeout   5초
DB Query Timeout      10초
```

이 경우 사용자는 이미 응답을 포기했는데 서버 작업은 계속될 수 있다.

```text
   └──────────┴────────────┴───────────┴──────────┘
               감사 로그 및 종단 모니터링
```

> 위 표는 원본 장표의 확정 사실이 아니라, 장표에 나타난 동기식 JSON/HTTP 채널 구조를 안정적으로 운영하기 위한 분석·권고 사항이다.

---

# 22. 장표 해석 시 유의사항

이 장표에서 붉은 강조선은 ①·②·③ 채널 업무 처리 경로를 강조하고 있지만, 모든 실제 네트워크 홉과 호출대상을 정확히 그린 상세 Sequence Diagram은 아니다.

특히 다음은 별도 상세설계가 필요하다.

- MCA 내부 처리
- Package UI와 BI포탈의 정확한 호출관계
- 미니 싱글뷰 WebView의 실제 URL/도메인
- 인증/SSO/JWT/Session
- API Gateway를 경유하는 채널 거래 범위
- 데이터플랫폼 직접조회 여부
- 거래 Header 구조
- GUID 생성 및 재사용 규칙

따라서 본 문서는 **장표의 FACT를 기반으로 채널 런타임 구조를 상세화한 분석 문서**이며, 확인되지 않은 세부 구현은 확정 사실로 취급하지 않는다.

# 23. 최종 평가

이 장표는 차세대 정보계 채널 거래를 화면 기술에 따라 3개로 분류한다.

```text
① 웹 기반 정보계 단말
② 기존 C/S 통합업무시스템 + MCA
③ C/S 통합업무시스템 + WebView 미니 싱글뷰
```

그러나 런타임 처리 관점에서는 세 유형 모두 다음 공통 모델을 가진다.

```text
Client
  → JSON/HTTP
  → Synchronous Request
  → Information Application
  → Business/Data Processing
  → Synchronous Response
```

이 구조의 가장 중요한 아키텍처 기준은 다음이다.

1. **채널 기술과 업무 애플리케이션을 분리한다.**
2. **JSON/HTTP 요청·응답을 공통 온라인 프로토콜로 사용한다.**
3. **GUID를 종단 거래 추적 기준으로 사용한다.**
4. **MCA와 WebView라는 서로 다른 채널 어댑터를 표준화한다.**
5. **사용자 대면 동기 거래이므로 Timeout과 응답시간을 엄격히 관리한다.**

특히 `미니 싱글뷰`는 기존 C/S 업무환경을 유지하면서 웹 기반 차세대 정보계 기능을 삽입하는 **Transition Architecture**로서 의미가 크다.

후속 상세설계에서는 다음이 반드시 확정되어야 한다.

```text
Channel
   ↓
Authentication / Context / GUID
   ↓
MCA or WebView
   ↓
HTTP/JSON Contract
   ↓
Application / Service
   ↓
Integration / Data
   ↓
Standard Response / Error
```

결론적으로 이 장표는 **차세대 정보계의 사용자 대면 온라인 거래 런타임을 3개의 채널 패턴으로 표준화한 핵심 Channel Runtime Architecture**다.
