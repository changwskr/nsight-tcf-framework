# 빅픽처 — 어플리케이션 분류체계 구성 정의 상세 아키텍처 분석

## 1. 문서 개요

본 문서는 원본 장표 **「어플리케이션 분류 체계 (1/5) ~ (5/5)」**를 기준으로 차세대 정보계의 애플리케이션 분류체계를 상세하게 전사·구조화하고, 이를 Application Architecture / Naming / ServiceId / Package / Interface / Governance 관점에서 분석한 자료다.

원본은 애플리케이션을 다음 3단계로 분류한다.

```text
대구분
(Application Group)
      ↓
업무구분
(Application)
      ↓
세부 업무 구분
(Function)
```

각 단계는 다시 다음 속성을 갖는다.

```text
대구분
 ├─ 한글명
 ├─ 코드
 └─ 영문

업무구분
 ├─ 한글명
 ├─ 코드
 └─ 영문명

세부 업무 구분
 ├─ 한글명
 ├─ 코드
 └─ 영문명
```

원본 장표에서는 세부 업무 구분(Function)은 아직 구체화되지 않았으며 다음 문구가 반복적으로 표시되어 있다.

```text
업무개발팀
분석, 설계 단계 시 반영
```

또한 세부 업무 코드 영역에는 반복적으로 다음 표기가 존재한다.

```text
1 byte
```

따라서 현재 장표는 다음과 같은 상태로 해석하는 것이 적절하다.

```text
대구분              : 정의 완료
업무구분            : 정의 완료
세부 업무 구분      : 업무 분석/설계 단계 확정 예정
세부 업무 코드 길이 : 1 byte 기준
```

# 2. 전체 분류체계 Big Picture

원본 5개 장표를 통합하면 최상위 Application Group은 다음 5개 체계로 구성된다.

```text
차세대 정보계 Application Classification
│
├─ MP : 상호금융_마케팅플랫폼
│      Marketing Platform
│
├─ RD : 상호금융_데이터플랫폼_RDW
│      Real-time Data Warehouse
│
├─ AD : 상호금융_데이터플랫폼_ADW
│      Analytical Data Warehouse
│
├─ BI : 상호금융_BI포탈(사용자분석)
│      Business Intelligence
│
├─ DG : 상호금융_데이터거버넌스
│      Data Governance
│
└─ IM : 상호금융_IT서비스 및 업무지원
       Information Management
```

> 주의: 원본은 데이터플랫폼을 `RD`, `AD`의 두 대구분으로 분리하므로, 최상위 그룹 코드는 실질적으로 6개다.

이를 기능 유형별로 다시 분류하면 다음과 같다.

```text
Business / Marketing
 └─ MP

Data Platform
 ├─ RD
 └─ AD

Analytics
 └─ BI

Data Governance
 └─ DG

Common Technical / IT Support
 └─ IM
```

# 3. 코드 계층 구조 분석

원본에서 확인되는 코드 형식은 다음과 같다.

```text
대구분 코드
= 2자리 영문 코드
예: MP, RD, AD, BI, DG, IM

업무구분 코드
= 2자리 영문 코드
예: CO, IC, PT, BM, AM

세부 업무 코드
= 1 byte
```

이를 계층형 분류키로 해석하면 다음 구조가 가능하다.

```text
<Application Group 2>
+
<Application 2>
+
<Function 1>

예시(ANALYSIS)
MP + IC + A
= MPICA

RD + SR + A
= RDSRA
```

다만 **원본에는 실제로 코드를 연결하여 5자리로 만든다는 규칙이 명시되어 있지 않다.**

따라서 다음을 구분해야 한다.

| 항목 | 상태 |
|---|---|
| 대구분 코드 2자리 | FACT |
| 업무구분 코드 2자리 | FACT |
| 세부 업무 코드 1 byte | FACT |
| 2+2+1을 연결한 5자리 코드 | ANALYSIS / 확인 필요 |
| 해당 코드가 ServiceId/패키지/URL에 그대로 적용 | 확인 필요 |

# 9. 마케팅플랫폼 세부업무(Function) 정의 상태

원본 세부 업무 구분 영역은 모든 Application에 대해 공란이며 다음이 표시되어 있다.

```text
업무개발팀
분석, 설계 단계 시 반영
```

따라서 예를 들어 `IC 통합고객`은 다음처럼 후속 정의되어야 할 가능성이 있다.

```text
MP
└─ IC 통합고객
    ├─ A : ?
    ├─ B : ?
    ├─ C : ?
    └─ ...
```

세부 코드는 원본 기준:

```text
1 byte
```

즉 A/B/C 또는 0~9 등 1-byte 표현을 사용하는 구조일 수 있으나 실제 허용문자 규칙은 **확인 필요**다.

# 16. RD와 AD 비교

| 구분 | RD | AD |
|---|---|---|
| 목적 | 실시간/준실시간 활용 | 분석/대용량 활용 |
| 대구분 코드 | RD | AD |
| Common | CO | CO |
| SoR | SR | SR |
| 요약집계 | ZD | ZD |
| 보고서마트 | RM | RM |
| 피드백 | FA | FA |
| 단위업무마트 | 없음 | UM |
| 분석지원 | 없음 | DA |

### 중요한 구조적 특징

동일 업무 코드가 RD와 AD에서 반복된다.

```text
RD-CO
AD-CO

RD-SR
AD-SR

RD-ZD
AD-ZD

RD-RM
AD-RM

RD-FA
AD-FA
```

따라서 **업무구분 코드만으로는 유일 식별이 불가능하다.**

반드시 최소 다음이 필요하다.

```text
Application Group Code
+
Application Code
```

예:

```text
RD + SR
AD + SR
```

# 35. 분류체계와 배포 단위 연결

Application Classification은 배포 단위와 반드시 동일할 필요는 없다.

예를 들어:

```text
MP
 ├─ IC
 ├─ PC
 ├─ BC
 └─ MS
```

가 각각 별도 WAR인지,

```text
mp.war
 ├─ IC
 ├─ PC
 ├─ BC
 └─ MS
```

인지 원본에는 나타나지 않는다.

따라서 다음은 후속 Physical/Application Architecture에서 결정해야 한다.

- Application Code = WAR인가?
- 여러 Application이 하나의 WAR에 묶이는가?
- 기능 코드가 Module인가?
- 배포단위는 업무코드와 독립인가?

```text

B

...
```

또는:

```text

1
2
```

### 확인 필요

- 영문 대문자만 허용?
- 숫자 허용?
- 소문자 허용?
- 한글 불가?
- 코드 고갈 시 확장 방법?
- 1 byte가 실제 DB CHAR(1)인지 논리 표기인지?

# 37. 업무개발팀 역할

```text
   │

          │
          ▼
Architecture Review / Baseline
```

이 프로세스가 필요하다.

# 60. Function 코드 할당 위험

세부 코드가 1 byte이면 코드 공간이 제한된다.

예를 들어 영문 대문자만 사용하면:

```text
A~Z
= 26개
```

숫자 포함이면:

```text
0~9 + A~Z
= 36개
```

ASCII 범위를 넓히면 더 많지만 가독성이 떨어진다.

따라서 Function이 많은 Application에서는 코드 고갈 정책을 미리 정의해야 한다.

# 74. 최종 평가

이 5개 장표는 차세대 정보계 Application Architecture의 **가장 직접적인 분류코드 사전**이다.

핵심 구조는 다음과 같다.

```text
Application Group
       2-char
          │
          ▼
Application
       2-char
          │
          ▼
Function
       1-byte
```

원본 기준 현재 정의된 Application Group / Application은 다음과 같다.

```text
MP Marketing Platform
 └─ 16 Applications

RD Real-time Data Warehouse
 └─ 5 Applications

AD Analytical Data Warehouse
 └─ 7 Applications

BI Business Intelligence
 └─ 5 Applications

DG Data Governance
 └─ 4 Applications

IM Information Management
 └─ 13 Applications

Total
= 50 Application Entries
```

이 체계의 가장 중요한 아키텍처적 의미는 다음과 같다.

1. **업무영역을 코드 기반으로 표준 분류한다.**
2. **Application Group과 Application을 분리한다.**
3. **세부 Function은 업무개발팀 분석/설계 단계에서 확정한다.**
4. **Function Code는 1-byte라는 제약을 가진다.**
5. **동일 Application Code가 여러 Group에서 재사용되므로 Group Context가 필수다.**
6. **대구분 코드와 하위 Application Code 간에도 문자열 충돌이 존재할 수 있다.**
7. **분류체계는 향후 ServiceId, Package, URL, Interface, Data Ownership, Runtime Monitoring의 기준키로 확장할 수 있다.**
8. **코드 변경은 반드시 Architecture Governance와 Baseline 관리 대상이 되어야 한다.**

특히 다음 구조를 최종 기준 모델로 권고할 수 있다.

```text
Domain / Application Group
        ↓
Application
        ↓
Function
        ↓
ServiceId
        ↓
Source
        ↓
Interface
        ↓
Data
        ↓
Runtime
        ↓
Deployment
```

결론적으로 본 장표는 **차세대 정보계의 업무·애플리케이션·기능을 코드체계로 계층화하는 Application Classification Architecture Baseline**이며, 향후 개발표준·네이밍·ServiceId·패키지·URL·인터페이스·운영관측성의 공통 기준으로 연결되어야 한다.
