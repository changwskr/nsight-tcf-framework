# 빅픽처 — 시스템 그룹 정의 상세 아키텍처 분석

## 1. 문서 개요

본 문서는 원본 장표 **「시스템 그룹 업무 구분 (1/6) ~ (6/6)」**을 기준으로 차세대 정보계의 **Application Group → System Group → 대상서버 → 업무구분코드 → 서버명 → 적용 솔루션/미들웨어** 관계를 상세하게 전사하고 분석한 자료다.

이번 6개 장표는 앞선 **어플리케이션 분류체계**보다 한 단계 더 물리·런타임에 가까운 정보를 제공한다.

앞선 분류체계가 다음을 정의했다면,

```text
Application Group
      ↓
Application Code
      ↓
Function
```

이번 시스템 그룹 정의는 이를 다음과 같이 실제 실행환경에 연결한다.

```text
Application Group
      ↓
System Group
      ↓
Target Server Role
      ↓
Application Code(s)
      ↓
Server Name
      ↓
Middleware / Solution
```

즉 이번 장표는 **Application Architecture와 Technical/Physical Architecture 사이를 연결하는 Deployment Mapping Baseline**으로 볼 수 있다.

# 3. 전체 시스템 그룹 Big Picture

원본 6개 장표를 통합하면 다음 시스템 그룹이 정의된다.

```text
차세대 정보계 시스템 그룹
│
├─ MP : Marketing Platform
│   └─ 마케팅플랫폼 시스템 그룹
│
├─ RD : Real-time Data Warehouse
│   ┐
│   ├─ 데이터플랫폼 시스템 그룹
│   ┘
│
├─ AD : Analytical Data Warehouse
│   └─ 데이터플랫폼 시스템 그룹
│
├─ BI : Business Intelligence
│   └─ BI포탈 시스템 그룹
│
├─ DG : Data Governance
│   └─ 데이터거버넌스 시스템 그룹
│
└─ IM : Information Management
    ├─ IT서비스 및 업무지원 시스템 그룹
    └─ 이행용 임시장비 / 인프라 임시 시스템 그룹
```

핵심적인 점은 다음과 같다.

1. **Application Group과 System Group이 항상 1:1은 아니다.**
2. RD와 AD는 서로 다른 Application Group이지만 하나의 `데이터플랫폼 시스템 그룹`으로 묶인다.
3. IM은 영구 운영 시스템뿐 아니라 `이행용 임시 시스템 그룹`까지 포함한다.
4. 하나의 서버 그룹에 여러 업무구분코드가 함께 배치될 수 있다.
5. 일부 Application Code는 독립 서버를 가지지 않고 공용 서버에 함께 배치된다.

# 8. 마케팅플랫폼 서버 분리 원칙 분석

앞선 Application Classification의 MP 업무코드는 총 16개다.

```text
CO IC PC BC MS SA PD CM EB EP BP BD SS CS CT MG
```

이번 시스템 그룹 장표에서는 이를 다음처럼 물리/런타임 그룹으로 분리한다.

```text
공용 Marketing WEB/WAS
 ├─ CO
 ├─ IC
 ├─ PC
 ├─ BC
 ├─ SA
 ├─ PD
 ├─ CM
 ├─ EB
 ├─ SS
 ├─ CS
 ├─ CT
 └─ MG

독립 Mini Single View
 └─ MS

독립 Real-time/Event
 ├─ EP
 ├─ BP
 └─ BD
```

### 구조적 의미

마케팅플랫폼은 모든 Application Code가 독립 서버를 가지는 방식이 아니다.

```text
Application Classification
        ≠
Physical Server 1:1
```

특히 다음이 명확하다.

- 일반 마케팅 업무는 `sbmpco` 공용 WEB/WAS 그룹에 통합
- Mini SingleView는 `sbmpms`로 별도 분리
- 실시간 이벤트 처리 영역 EP/BP/BD는 독립 런타임으로 분리

이는 **업무 분류와 런타임 분리를 서로 다른 축으로 관리**한다는 중요한 근거다.

```text

= 실시간 처리

= Behavior Information Processing
= 행동정보 처리

= Customer Behavior Data
```

Runtime 관점:

```text
Customer / Channel Behavior
       ↓
BD 고객 행동 데이터
(Kafka 기반)
       ↓
BP 행동정보 처리
       ↓
EP 실시간 처리
       ↓
Marketing Action / EBM
```

> 실제 처리 방향은 장표에 화살표로 명시되지 않으므로 위 순서는 **ANALYSIS**이다.

# 14. 데이터플랫폼 Appliance 구조 분석

장표에서 RDW와 ADW 모두 `서버(어플라이언스)`로 표현된다.

```text
RDW
→ RDW Appliance

ADW
→ ADW Appliance
```

### 중요한 구조적 의미

RD/AD의 개별 Application Code들은 별도 서버가 아니라 각각 하나의 Appliance 영역에 통합된다.

```text
RD-SR
RD-ZD
RD-RM
RD-FA
RD-CO
       └→ sbrdco

AD-SR
AD-ZD
AD-UM
AD-FA
AD-CO
AD-RM
AD-DA
       └→ sbadco
```

따라서 데이터플랫폼에서는 Application Code가 **논리 데이터영역/기능영역**이고, 서버는 Appliance 단위로 통합되는 구조다.

# 23. 데이터거버넌스 코드 충돌/불일치

여기에는 매우 중요한 Source Conflict가 존재한다.

앞선 **어플리케이션 분류체계 (4/5)** 에서는 다음과 같이 정의되었다.

```text
DG
├─ CO Common
├─ BM Biz-Meta system
├─ DQ Data Quality
└─ DL Data Lineage
```

하지만 현재 **시스템 그룹 업무 구분 (4/6)** 에서는 데이터흐름 서버의 업무구분코드가 다음과 같다.

```text
DF
```

또한 용어에도:

```text
df = 데이터 흐름 어플리케이션 코드
```

라고 명시되어 있다.

따라서 현재 소스 세트에는 다음 충돌이 있다.

```text
Application Classification
DG-DL = Data Lineage

System Group Definition
DG-DF = 데이터 흐름
```

### 판정

```text
CONFLICT / 확인 필요
```

원본을 임의로 하나로 통일해서는 안 된다.

확인해야 할 항목:

- 최종 승인 코드는 `DL`인가 `DF`인가?
- `DL`은 논리 Application Code이고 `DF`는 시스템/서버용 별도 코드인가?
- 과거/신규 버전간 변경인가?
- `sbdfdl` 서버명의 `df`와 `dl`은 각각 무엇을 의미하는가?

# 24. 데이터거버넌스 서버명 특이점

일반적인 패턴처럼 보이는 이름:

```text
sbdgdq
≈ sb + dg + dq
```

하지만 데이터흐름 서버는:

```text
sbdfdl
```

이다.

이는 `DG` 그룹의 일반 prefix와 일관되지 않는다.

따라서 `sbdfdl`은 다음 중 하나일 가능성이 있다.

- 기존 서버 네이밍 유지
- 별도 솔루션 네이밍
- DF/DL 전환과정의 혼합명
- 문서상 표기 오류

원본만으로는 결정할 수 없으므로 **확인 필요**다.

# 30. XM/XD 코드와 서버명 토큰 불일치

원본의 중요한 특이점:

```text
업무구분코드 XM
서버명 sbimum
용어 um = 단말관리 어플리케이션 코드
```

그리고:

```text
업무구분코드 XD
서버명 sbimud
용어 ud = 단말배포 어플리케이션 코드
```

즉 서버명에 사용되는 토큰은 Application Classification Code와 다르다.

```text
XM ≠ UM
XD ≠ UD
```

### 의미

서버명 네이밍에서 사용하는 `um`, `ud`는 업무구분코드를 그대로 lower-case한 것이 아니다.

따라서 다음 가정을 하면 안 된다.

```text
server suffix == application code
```

이것은 서버 네이밍 기준서와 애플리케이션 코드 기준서를 별도로 관리해야 한다는 강한 근거다.

# 36. 서버 네이밍 패턴 분석

```text
sb + mp + co = sbmpco
sb + mp + ms = sbmpms
sb + bi + pt = sbbipt
sb + bi + sb = sbbisb
```

```text

DG-DF → sbdfdl
```

따라서 `sb` 및 각 토큰의 공식 의미는 **서버 네이밍 기준서 확인 필요**다.

```text
Server Role
      ↓
Physical Server
```

### System Group이 필요한 이유

- 여러 Application을 하나의 Runtime으로 묶음
- 동일 운영정책 적용
- 동일 솔루션/미들웨어 적용
- 동일 HA/Scale 단위 관리
- 배포/모니터링 범위 정의

---

# 40. Application Group과 System Group의 차이

| 구분 | Application Group | System Group |
|---|---|---|
| 중심 | 업무/기능 분류 | 실행/운영 분류 |
| 예 | BI, MP, IM | BI포탈 시스템 그룹 |
| 목적 | Application Ownership | Runtime/Server Grouping |
| 관계 | 논리 기능 | 논리 실행 단위 |
| 물리 연계 | 간접 | 직접적 |

따라서:

```text
Application Group
≠
System Group
≠
Physical Server
```

이 세 계층을 혼용하면 안 된다.

```text
SYS-RULE-003
공동 서버에 배치되는 Application Code 목록을 Baseline으로 관리한다.

SYS-RULE-004
임시 이행 서버는 운영 Baseline과 분리하고 종료일을 가져야 한다.

SYS-RULE-005
Classification Code와 System Group Code 불일치는 Conflict Register로 관리한다.

SYS-RULE-006
Middleware/Solution 버전은 Server Inventory와 연결한다.
```

# 82. 최종 평가

이번 6개 장표는 차세대 정보계의 Application Classification을 **실제 실행 서버와 기술 스택으로 연결하는 핵심 Mapping 자료**다.

전체 구조를 가장 압축해서 표현하면 다음과 같다.

```text
Application Domain
       ↓
Application Code
       ↓
System Group
       ↓
Target Server
       ↓
Server Name
       ↓
Middleware / Solution
       ↓
Physical Infrastructure
```

대표 예:

```text
MP-IC
→ 마케팅플랫폼 시스템 그룹
→ Marketing WEB/WAS
→ sbmpco
→ Apache / Tomcat / NH Cloud Framework

BI-SB
→ BI포탈 시스템 그룹
→ Self BI AP/WEB/WAS
→ sbbisb
→ BI-Matrix

DG-DQ
→ 데이터거버넌스 시스템 그룹
→ 비즈메타/품질 WAS
→ sbdgdq
→ GT-One DQ Miner

IM-BJ
→ IT서비스 시스템 그룹
→ 배치 AP
→ sbimbj
→ NH Cloud Framework Batch
```

이 장표의 중요한 아키텍처적 의미는 다음과 같다.

1. **애플리케이션 분류와 서버 배치를 분리하여 관리한다.**
2. **여러 업무코드가 하나의 공용 Runtime을 공유할 수 있다.**
3. **일부 업무는 성능/솔루션 특성에 따라 독립 서버로 격리된다.**
4. **WEB/WAS/AP/Appliance 등 서버 역할이 명확하게 구분된다.**
5. **Application Code와 서버 Naming Token이 항상 동일하지 않다.**
6. **BI/Data Governance 영역은 솔루션 제품 단위의 런타임 경계가 중요하다.**
7. **IM은 DevOps/Batch/CDC/ETL/Terminal 등 공통 플랫폼 역할을 담당한다.**
8. **이행용 임시 인프라는 영구 운영환경과 분리되어 있다.**
9. **DG의 DL/DF 코드 불일치와 IM 일부 미매핑은 Baseline 확정 전 반드시 해결해야 한다.**

따라서 본 자료는 향후 다음 Traceability의 기준으로 사용하는 것이 적절하다.

```text
Requirement
  ↓
Application Classification
  ↓
System Group
  ↓
Server / Middleware
  ↓
Physical Inventory
  ↓
Interface / Runtime
  ↓
Capacity / HA / Security
  ↓
Runtime Validation
```

결론적으로 이번 장표는 **차세대 정보계 Application Architecture를 실제 System/Server/Middleware Architecture로 변환하는 Deployment Mapping Architecture Baseline**이다.
