# 물리기술아키텍처 — 시스템 표준 — 서버 호스트 명명규칙 분석

## 1. 핵심 결론

서버 호스트명은 **영문 소문자와 숫자로 구성된 고정 12자리 식별자**이며, 다음 여섯 영역을 결합한다.

```text
┌────────┬──────────────────┬────────┬────────┬────────┬────────┐
│ 법인   │ 애플리케이션     │ 서버   │ 환경   │ 용도   │ 순번   │
│ 2자리  │ 4자리(2+2)       │ 1자리  │ 1자리  │ 2자리  │ 2자리  │
├────────┼──────────────────┼────────┼────────┼────────┼────────┤
│ sb     │ mpco             │ l      │ o      │ wb     │ 01     │
└────────┴──────────────────┴────────┴────────┴────────┴────────┘
                         ↓
                   sbmpcolowb01
```

```text
hostname = 법인(2) + 대구분(2) + 업무구분(2) + 서버(1) + 환경(1) + 용도(2) + 순번(2)
         = 2 + 2 + 2 + 1 + 1 + 2 + 2 = 12자리
```

이 체계는 호스트명만으로 소유 법인, 업무 시스템, 하드웨어 계열, 환경, 서버 역할 및 인스턴스 번호를 식별하게 한다. 다만 애플리케이션 4자리 코드는 별도 코드 사전이 필수이며, 명칭 변경보다 코드의 불변성과 중앙 통제가 중요하다.

## 2. 명명 구조

| 번호 | 위치 | 길이 | 의미 | 예시 | 해석 |
|---:|---:|---:|---|---|---|
| ① | 1~2 | 2 | 법인 코드 | `sb` | 상호금융 |
| ② | 3~6 | 4 | 대구분 코드(2) + 업무구분 코드(2) | `mpco` | 마케팅플랫폼 관련 애플리케이션 코드 |
| ③ | 7 | 1 | 서버/플랫폼 코드 | `l` | Linux |
| ④ | 8 | 1 | 환경 코드 | `o` | 운영 |
| ⑤ | 9~10 | 2 | 용도 코드 | `wb` | WEB 서버 |
| ⑥ | 11~12 | 2 | 순번 | `01` | 주센터 첫 번째 서버 |

### 위치 기반 파싱

```text
sbmpcolowb01
│││  ││ │ └─ 01 : 순번
│││  ││ └─── wb : WEB
│││  │└───── o  : 운영
│││  └────── l  : Linux
││└───────── mpco : 대구분(mp) + 업무구분(co)
└┴────────── sb : 상호금융
```

고정 길이이므로 구분자를 쓰지 않아도 기계적으로 파싱할 수 있다. 반대로 어느 한 코드라도 정의된 길이를 위반하면 이후 필드의 위치가 모두 어긋나므로 생성 단계에서 길이 검증이 필요하다.

## 3. 코드 사전

### 3.1 법인 코드 — 2자리

| 법인 | 코드 |
|---|---|
| 상호금융 | `sb` |
| 중앙회(상호금융 제외) | `nh` |
| 은행 | `nb` |
| 금융지주 | `fg` |
| 경제지주 | `ag` |

법인 코드는 서버의 자산 소유·운영 책임 범위를 나타내는 최상위 분류다. 조직 개편 시에도 기존 호스트명의 일괄 변경을 피할 수 있도록 코드의 수명주기 정책이 필요하다.

### 3.2 애플리케이션 코드 — 4자리

```text
애플리케이션 코드 = 대구분 코드(2) + 업무구분 코드(2)
```

장표는 상세 값 대신 **애플리케이션 코드 정의 참조**를 지시한다. 따라서 이 4자리 코드의 정확한 의미는 중앙 애플리케이션 코드 사전(CMDB 또는 표준 코드 관리 시스템)을 기준으로 해석해야 한다.

필수 관리 속성은 다음과 같다.

- 코드, 공식 시스템명, 약어 및 설명
- 소유 조직과 운영 조직
- 적용 시작일·종료일 및 상태(예약/사용/폐기)
- 중복 금지 여부와 대체 코드
- 관련 서비스·DB·배치·인터페이스 식별자

> `mpco`, `rdco`의 정확한 세부 확장은 장표만으로 확정할 수 없다. 본 문서는 예시가 각각 마케팅플랫폼과 RDW 어플라이언스를 가리킨다는 사실까지만 사용한다.

### 3.3 서버/플랫폼 코드 — 1자리

| 플랫폼 | 코드 | 분석 |
|---|---|---|
| Unix–IBM | `i` | IBM UNIX 계열 |
| Unix–HP | `h` | HP UNIX 계열 |
| Unix–Oracle | `o` | Oracle UNIX 계열 |
| Linux(EMC/HP) | `l` | Linux 서버 계열 |
| Windows(EMC/HP) | `w` | Windows 서버 계열 |
| Exadata(Oracle) | `x` | Oracle Exadata 어플라이언스 |

이 필드는 OS와 하드웨어 계열이 혼합된 분류다. 향후 클라우드·컨테이너·신규 어플라이언스가 추가되면 1자리 코드 공간이 부족하거나 의미가 중첩될 수 있으므로 확장 정책이 필요하다.

### 3.4 환경 코드 — 1자리

| 환경 | 코드 | 적용 의미 |
|---|---|---|
| 운영 서버 | `o` | 고객 서비스를 제공하는 운영 환경 |
| 검증 서버 | `v` | 통합·검증·시험 환경 |
| 개발 서버 | `t` | 개발 환경 |

장표의 예시에서 DR 서버는 별도 환경 코드가 아니라 운영 코드 `o`를 유지하고 순번 `51~99`로 구분한다. 즉 DR은 운영 서비스의 재해복구 인스턴스라는 모델이다.

### 3.5 용도 코드 — 2자리

| 용도 | 코드 | 일반적 배치 계층 |
|---|---|---|
| AP 서버 | `ap` | 애플리케이션/처리 서버 |
| DB 서버 | `db` | 데이터베이스 서버 |
| WEB 서버 | `wb` | 웹 서버 |
| WAS 서버 | `ws` | 웹 애플리케이션 서버 |
| 백업 서버 | `bk` | 백업 처리·저장 관리 |
| 배치 서버 | `bt` | 배치 실행 서버 |
| ETL 서버 | `tl` | 데이터 추출·변환·적재 서버 |

용도 코드는 논리 역할을 표시한다. 하나의 물리/가상 서버가 복수 역할을 수행하면 대표 역할을 명확히 정하고 CMDB에서 부가 역할을 별도 속성으로 관리해야 한다.

### 3.6 순번 — 2자리

| 센터/목적 | 허용 대역 | 의미 |
|---|---:|---|
| 주센터(의왕) | `01~49` | 운영·개발·검증의 주센터 인스턴스 |
| DR센터(안성) | `51~99` | 운영 서비스의 DR 인스턴스 |

`00`과 `50`은 정의된 대역에서 제외된다. 예약 번호인지 단순 미사용 값인지는 표준 관리 문서에서 명시해야 하며, 임의 할당해서는 안 된다.

## 4. 장표 예시 역분해

| 구분 | 호스트명 | 분해 | 해석 |
|---|---|---|---|
| 운영 마케팅플랫폼 WEB #01 | `sbmpcolowb01` | `sb`+`mpco`+`l`+`o`+`wb`+`01` | 상호금융, 마케팅플랫폼, Linux, 운영, WEB, 의왕 #01 |
| DR 마케팅플랫폼 WEB #51 | `sbmpcolowb51` | `sb`+`mpco`+`l`+`o`+`wb`+`51` | 동일 운영 서비스의 안성 DR WEB #51 |
| 개발 마케팅플랫폼 WEB #01 | `sbmpcoltwb01` | `sb`+`mpco`+`l`+`t`+`wb`+`01` | 상호금융, 마케팅플랫폼, Linux, 개발, WEB #01 |
| 운영 RDW 어플라이언스 #01 | `sbrdcoxodb01` | `sb`+`rdco`+`x`+`o`+`db`+`01` | 상호금융, RDW, Exadata, 운영 DB #01 |
| DR RDW 어플라이언스 #51 | `sbrdcoxodb51` | `sb`+`rdco`+`x`+`o`+`db`+`51` | 동일 RDW 운영 DB의 안성 DR #51 |
| 개발 RDW 어플라이언스 #01 | `sbrdcoxtdb01` | `sb`+`rdco`+`x`+`t`+`db`+`01` | 상호금융, RDW, Exadata, 개발 DB #01 |

### 운영–DR 대응 관계

```text
운영: sbmpcolowb01 ── 역할·플랫폼·환경 유지, 순번 대역 전환 ──> DR: sbmpcolowb51
개발: sbmpcoltwb01 ── 환경 코드 t                                  └─ DR 아님
```

운영과 DR 호스트는 법인·애플리케이션·플랫폼·환경·용도 코드가 같고 순번만 `01~49`에서 `51~99`로 대응하는 구조다. 다만 `01↔51`, `02↔52`와 같은 50 차이의 1:1 대응이 의무인지는 장표에서 명시하지 않으므로 별도 할당 정책으로 확정해야 한다.

## 5. 유효성 검증 규칙

### 5.1 기본 형식 정규식

애플리케이션 코드가 영문 소문자 4자리라는 전제의 1차 형식 검사는 다음과 같다.

```regex
^(sb|nh|nb|fg|ag)[a-z]{4}[iholwx][ovt](ap|db|wb|ws|bk|bt|tl)(0[1-9]|[1-4][0-9]|5[1-9]|[6-9][0-9])$
```

이 정규식은 길이·문자종류·공통 코드만 검사한다. 실제 등록 시에는 `[a-z]{4}` 대신 승인된 애플리케이션 코드 사전과 대조해야 한다.

### 5.2 교차 검증

단순 정규식 외에 다음 의미 검사가 필요하다.

1. 전체 길이는 정확히 12자리여야 한다.
2. 문자는 영문 소문자와 숫자만 허용한다.
3. 법인·애플리케이션·플랫폼·환경·용도 코드는 활성 코드 사전에 존재해야 한다.
4. `51~99`는 DR센터 자산에만 할당한다.
5. DR 호스트는 장표 기준 운영 환경 코드 `o`를 사용해야 한다.
6. 개발 `t` 또는 검증 `v` 호스트가 DR 순번을 사용하지 못하도록 차단한다.
7. 동일 호스트명은 DNS, CMDB, IaaS, 모니터링, 백업 시스템 전체에서 유일해야 한다.
8. 플랫폼 코드와 실제 OS/장비 유형이 일치해야 한다.
9. 용도 코드와 설치 소프트웨어 역할이 일치해야 한다.

### 5.3 권장 판정 의사코드

```text
parse(hostname)
  assert length == 12
  assert lowercase_alphanumeric

  corp     = hostname[1..2]
  app      = hostname[3..6]
  platform = hostname[7]
  env      = hostname[8]
  role     = hostname[9..10]
  seq      = integer(hostname[11..12])

  assert corp/platform/env/role in active_code_dictionary
  assert app in active_application_dictionary
  assert seq in 01..49 or 51..99

  if seq >= 51:
      assert datacenter == '안성'
      assert env == 'o'
  else:
      assert datacenter == '의왕'

  assert hostname is globally_unique
```

## 6. 운영 적용 메커니즘

### 6.1 생성 절차

```text
자산/서비스 요청
  → 법인·애플리케이션 코드 조회
  → 플랫폼·환경·용도 확정
  → 센터별 가용 순번 예약
  → 12자리 조합 및 자동 검증
  → CMDB 선등록
  → DNS/IaaS/OS 프로비저닝
  → 모니터링·백업·보안 도구 동기화
  → 사용 상태 전환
```

호스트명은 사람이 임의 입력하기보다 CMDB 또는 프로비저닝 포털에서 생성해야 한다. 순번 예약과 DNS 생성 사이에는 중복 할당을 방지하는 잠금 또는 단일 트랜잭션이 필요하다.

### 6.2 변경 원칙

- 구축 후 호스트명 변경은 인증서, DNS, 미들웨어, 모니터링, 배치, 방화벽 규칙에 연쇄 영향을 주므로 예외 절차로 제한한다.
- 조직명이나 시스템 표시명이 바뀌어도 기존 애플리케이션 코드를 즉시 재사용하거나 개명하지 않는다.
- 폐기된 호스트명과 순번은 감사·로그 추적 기간 동안 재사용 금지 상태로 보존한다.
- 운영–DR 쌍은 CMDB 관계 속성으로 연결하고 이름의 유사성에만 의존하지 않는다.

## 7. 아키텍처적 장점

- **즉시 식별성**: 이름만으로 업무, 플랫폼, 환경, 역할과 센터 대역을 파악할 수 있다.
- **자동화 적합성**: 고정 위치 파싱으로 배포·모니터링·백업 정책을 자동 연결할 수 있다.
- **장애 대응성**: 운영과 DR 자산의 대응 관계를 빠르게 좁힐 수 있다.
- **자산 거버넌스**: CMDB 및 보안 정책의 표준 키로 활용할 수 있다.
- **확장 일관성**: 동일 업무의 WEB/WAS/AP/DB 서버를 공통 접두부로 묶을 수 있다.

## 8. 한계와 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 12자리 고정 길이 | 신규 플랫폼·역할 코드 부족 | 예약 코드와 확장 버전 정책 수립 |
| 애플리케이션 코드 별도 참조 | 이름만으로 업무 해석 불가 | 중앙 코드 사전 API/조회 화면 제공 |
| OS와 하드웨어 의미 혼합 | 가상화·클라우드 전환 시 모호 | 플랫폼 분류 정의와 예외 기준 문서화 |
| DR을 순번으로만 구분 | 잘못된 센터 배치 가능 | 센터–순번–환경 교차 검증 |
| 순번 수동 배정 | 중복 호스트명·DNS 충돌 | 중앙 예약 및 원자적 할당 |
| 이름에 기술 상세 내장 | 마이그레이션 시 실제 구성과 불일치 | CMDB 정합성 검사와 변경 영향평가 |
| 코드 재사용 | 로그·감사 이력 혼동 | 폐기 코드와 순번의 유예기간 적용 |

## 9. 개선 권고

1. 명명 규칙을 CMDB의 **생성 규칙**으로 구현하고 단순 문서 표준에 머물지 않게 한다.
2. 애플리케이션 코드 사전을 API로 제공하고 중복·폐기·예약 상태를 관리한다.
3. 운영–DR 페어 ID를 별도 속성으로 두어 순번 추정에 의존하지 않는다.
4. DNS A/PTR 레코드, 인증서 SAN, 모니터링 대상, 백업 정책과 자동 정합성 검사를 수행한다.
5. 플랫폼 코드가 현재 구성과 맞는지 정기 점검한다.
6. Kubernetes, 퍼블릭 클라우드, 관리형 DB 등 신규 자원은 기존 1자리 플랫폼 코드에 억지로 끼우지 말고 차기 규칙에서 다룬다.
7. 모든 코드와 순번에 소유자, 승인자, 유효기간 및 변경 이력을 둔다.

- [ ] 법인 코드가 승인된 2자리 값인가?
- [ ] 대구분+업무구분 4자리가 애플리케이션 코드 사전에 존재하는가?
- [ ] 서버/플랫폼 코드가 실제 장비 및 OS와 일치하는가?
- [ ] 환경 코드가 운영 `o`, 검증 `v`, 개발 `t` 중 하나인가?
- [ ] 용도 코드가 실제 설치 역할과 일치하는가?
- [ ] 의왕은 `01~49`, 안성 DR은 `51~99` 대역을 사용하는가?
- [ ] 개발·검증 서버가 DR 순번을 잘못 사용하지 않는가?
- [ ] DNS·CMDB·IaaS 전체에서 호스트명이 유일한가?
- [ ] 운영–DR 대응 관계가 CMDB에 명시되어 있는가?
- [ ] 폐기된 이름과 순번의 재사용 통제가 적용되는가?

## 11. 최종 평가

이 명명 표준은 제한된 12자리 안에 자산의 핵심 분류를 압축한 **위치 기반 구조화 식별 체계**다. 기존 운영 환경에서는 검색성과 자동화 효율이 높지만, 정확성은 애플리케이션 코드 사전, 순번 중앙 할당, 센터·환경 교차 검증이 보장할 때만 유지된다. 따라서 호스트명 자체를 진실의 원천으로 삼기보다 CMDB의 표준 식별 결과로 생성하고, DNS·프로비저닝·운영 도구에 배포하는 방식이 적합하다.
