# 물리기술아키텍처 — 시스템 표준 — 사용자 계정 분석

## 1. 핵심 결론

장표는 서버 접속 및 소프트웨어 설치·운영을 위한 계정을 다음 세 유형으로 표준화한다.

1. **엔진 계정** — Apache WEB, Tomcat WAS 등 미들웨어 프로세스 실행 계정
2. **업무 계정** — 애플리케이션 코드 기반의 업무팀 사용 계정
3. **솔루션 계정** — Nexus, SQL 품질, ETL/DataStage·DB2, Oracle 등 제품 전용 계정

표준화의 목적은 동일 역할의 계정이 여러 서버에서 일관된 소유권과 실행 권한을 갖도록 하는 것이다. 그러나 “전 시스템에 동일하게 부여”한다는 문구는 **계정명·UID/GID·역할·권한 기준의 일관성**으로 해석해야 한다. 비밀번호, SSH 개인키 또는 광범위한 관리자 권한을 여러 시스템에서 공용으로 사용하는 방식은 보안·감사·사고 확산 측면에서 부적절하다.

```text
사용자 계정 표준
├─ 엔진 계정
│  ├─ apache : apache   → Apache WEB 프로세스
│  └─ tomcat : tomcat   → Tomcat WAS 프로세스
│
├─ 업무 계정
│  └─ <애플리케이션 코드 4자리> : <관련 역할 그룹>
│
└─ 솔루션 계정
   ├─ nexus   : ci/cd     → Nexus
   ├─ openpop : openpop   → SQL 품질
   ├─ dsadm   : dstage    → DataStage 관리자
   ├─ wasadm  : dstage    → WebSphere 관리자
   ├─ db2inst : db2grp    → DB2 Instance 소유자
   ├─ db2fenc : db2grp    → DB2 Fenced
   ├─ xmeta   : db2grp    → Metadata Repository 소유자
   ├─ xmetasr : db2grp    → Metadata Repository 사용자
   ├─ dsodb   : db2grp    → Operation Database 소유자
   └─ oracle  : oragrid   → Oracle Database
```

## 2. 장표 원문 전사

### 2.1 엔진 계정

| 계정 구분 | 계정명 | 그룹명 | 설명 |
|---|---|---|---|
| WEB 서버(apache) 엔진 계정 | `apache` | `apache` | Apache WEB 서버 엔진 계정 |
| WAS 서버(tomcat) 엔진 계정 | `tomcat` | `tomcat` | Tomcat WAS 서버 엔진 계정 |

### 2.2 업무 계정

| 계정 구분 | 계정명 | 그룹명 | 설명 |
|---|---|---|---|
| 업무팀 사용 계정 | `<애플리케이션 코드 4자리>` | `<관련 그룹>` | 계정명은 대구분 코드(2)+업무구분 코드(2), 그룹은 업무 역할에 따라 할당 |

장표의 네모 4개는 판독 가능한 계정명이 아니라 **4자리 애플리케이션 코드 자리표시자**로 해석한다. 예시는 다음 원칙을 제시한다.

- WEB 업무 계정은 `apache` 그룹에 할당
- WAS 업무 계정은 `tomcat` 그룹에 할당
- 정확한 4자리 값은 “애플리케이션 코드 정의”를 참조
- 업무 구분과 특성에 따라 시스템 사용자 계정 명명 규칙은 변경될 수 있음

### 2.3 솔루션 계정

| 계정 구분 | 계정명 | 그룹명 | 설명 |
|---|---|---|---|
| Nexus 오픈소스 저장소 계정 | `nexus` | `ci/cd` | 라이브러리 소프트웨어 설치 및 관리 계정 |
| SQL 품질 계정 | `openpop` | `openpop` | SQL 품질 프로그램 설치 및 관리 계정 |
| ETL 계정 | `dsadm` | `dstage` | DataStage 관리자 계정 |
| ETL 계정 | `wasadm` | `dstage` | WebSphere Application Server 관리자 계정 |
| ETL 계정 | `db2inst` | `db2grp` | DB2 Instance 소유자 계정 |
| ETL 계정 | `db2fenc` | `db2grp` | DB2 Fenced 계정 |
| ETL 계정 | `xmeta` | `db2grp` | Metadata Repository 소유자 계정 |
| ETL 계정 | `xmetasr` | `db2grp` | Metadata Repository 사용자 계정 |
| ETL 계정 | `dsodb` | `db2grp` | Operation Database 소유자 계정 |
| 오라클 계정 | `oracle` | `oragrid` | Oracle Database 계정 |

> `ci/cd`는 장표에 표시된 문자열을 그대로 전사한 값이다. 일반적인 Linux 로컬 그룹명에는 `/` 문자를 사용할 수 없으므로, 실제 그룹명이 `cicd`, `ci_cd` 또는 디렉터리 서비스의 표시명인지 구축 계정 목록에서 반드시 확인해야 한다.

## 3. 계정 유형별 책임 분리

| 유형 | 주 용도 | 대화형 로그인 | 파일 소유 | 프로세스 실행 | 권장 인증 |
|---|---|---:|---:|---:|---|
| 엔진 계정 | WEB/WAS 런타임 | 원칙적 차단 | 엔진·런타임 일부 | 필수 | systemd/서비스 전환, 비밀번호 잠금 |
| 업무 계정 | 배포·운영·업무 파일 처리 | 승인된 경우만 | 업무 프로그램·데이터 | 업무별 | 개인계정→sudo/su, PAM/MFA |
| 솔루션 계정 | 제품 설치·관리·실행 | 제품 요구 범위 | 제품 디렉터리 | 제품별 | Vault/PAM, 서비스 인증 |
| 개인 관리자 계정 | 추적 가능한 운영 작업 | 허용 | 원칙적 최소화 | 직접 실행보다 역할 전환 | 개인 인증서/키+MFA |

### 핵심 원칙

- 사람은 공유 서비스 계정으로 직접 로그인하지 않고 개인 계정으로 인증한 후 승인된 역할로 전환한다.
- 서비스 계정은 프로세스 실행과 파일 소유에만 필요한 최소 권한을 갖는다.
- 설치 계정, 실행 계정, 운영 조회 계정, 배포 계정과 DB 소유자 계정을 가능한 범위에서 분리한다.
- root 직접 접속은 금지하고 `sudo` 또는 PAM을 통해 명령 단위로 통제·기록한다.

## 4. 엔진 계정 분석

### 4.1 `apache:apache`

- Apache WEB 프로세스의 실행 및 필요한 파일 소유에 사용한다.
- 시스템 포트 바인딩은 root로 지속 실행하기보다 systemd capability 또는 master/worker 모델을 사용한다.
- 웹 콘텐츠는 읽기 위주, 로그는 지정 로그 경로에만 쓰도록 권한을 제한한다.
- CGI·업로드·임시 파일 경로는 별도 소유권과 마운트 옵션으로 격리한다.
- 로그인 셸은 `/sbin/nologin` 또는 `/bin/false`, 비밀번호는 잠금 상태를 권장한다.

### 4.2 `tomcat:tomcat`

- Tomcat WAS 프로세스를 실행하고 배포·런타임 경로에 제한적으로 접근한다.
- 애플리케이션 배포 권한과 프로세스 실행 권한을 분리하면 무단 변경 위험이 줄어든다.
- JMX, 관리 콘솔, keystore, 데이터소스 비밀정보 접근 권한을 최소화한다.
- WEB 계정과 UID/GID 또는 쓰기 그룹을 공유하지 않는다.
- 로그인 셸과 비밀번호를 잠그고 systemd가 해당 계정으로 프로세스를 실행하게 한다.

## 5. 업무 계정 분석

업무 계정명은 호스트 명명규칙과 동일한 애플리케이션 코드 사전의 4자리 코드를 사용한다.

```text
업무 계정 = 대구분 코드(2) + 업무구분 코드(2)
```

### 권장 권한 모델

```text
개인 운영자
  └─ PAM/MFA 인증
      └─ sudo 또는 역할 전환
          └─ <업무계정 4자리>
              ├─ WEB 역할 필요 시 보조 그룹: apache
              ├─ WAS 역할 필요 시 보조 그룹: tomcat
              └─ 업무 파일 경로: /pgm*, /aplog*, /userdir*
```

업무 계정을 `apache` 또는 `tomcat` 그룹에 넣으면 엔진 소유 파일에 접근할 수 있으므로 다음을 지켜야 한다.

- 그룹 쓰기 권한은 필요한 배포·운영 경로에만 적용한다.
- 엔진 바이너리와 전역 설정에 대한 쓰기 권한은 부여하지 않는다.
- WEB과 WAS를 모두 운영하는 계정이라도 불필요한 교차 권한은 피한다.
- 애플리케이션 코드가 폐기되면 계정도 잠그되 감사·파일 소유권 이력을 보존한다.
- 동일 애플리케이션 코드라도 운영·개발·검증 권한은 서버 그룹 또는 접근 정책으로 분리한다.

## 6. 솔루션 계정 분석

### 6.1 `nexus`

- Nexus Repository 설치·실행·관리 전용 계정이다.
- 아티팩트 저장소 데이터, blob, 설정, 로그의 소유권을 구분한다.
- CI/CD 도구의 배포 토큰과 관리자 인증정보는 계정 홈에 평문으로 두지 않는다.
- 실제 그룹명은 장표의 `ci/cd` 표기를 기준 시스템에서 재확인한다.

### 6.2 `openpop`

- SQL 품질 도구 설치 및 운영 계정이다.
- 분석 대상 DB의 접속 권한은 읽기 중심의 별도 DB 계정을 사용한다.
- OS 계정 권한과 데이터베이스 권한을 동일 개념으로 혼합하지 않는다.

### 6.3 DataStage·WebSphere 계정

| 계정 | 책임 | 주의사항 |
|---|---|---|
| `dsadm` | DataStage 관리자 | 일반 Job 실행자와 분리, 강한 감사 적용 |
| `wasadm` | WebSphere 관리자 | WAS 관리 권한 최소화, DataStage 관리자와 자격증명 분리 |

두 계정이 `dstage` 그룹을 공유하더라도 개인별 작업 추적이 가능하도록 PAM 전환 기록과 제품 감사 로그를 남겨야 한다.

### 6.4 DB2 계정군

| 계정 | 책임 | 분리 목적 |
|---|---|---|
| `db2inst` | DB2 Instance 소유자 | 인스턴스 기동·관리 |
| `db2fenc` | DB2 Fenced 프로세스 | 외부 코드 실행을 인스턴스 소유자와 격리 |
| `xmeta` | Metadata Repository 소유자 | 메타데이터 DB 소유 |
| `xmetasr` | Metadata Repository 사용자 | 소유자보다 제한된 사용 권한 |
| `dsodb` | Operation Database 소유자 | 운영 DB 소유권 분리 |

장표에서는 모두 `db2grp` 그룹으로 표시되지만, 실제 DB2 제품 요구사항과 최소 권한 기준에 따라 primary/secondary group을 구분할 필요가 있다. 모든 계정에 동일 그룹 권한을 일괄 부여하면 fenced 계정 분리 효과가 약화될 수 있다.

### 6.5 `oracle:oragrid`

- 장표상 Oracle Database 계정과 그룹 매핑이다.
- 일반적인 Oracle RAC 구성은 `oracle`, `grid` 계정과 `oinstall`, `dba`, `oper`, `asmadmin` 등의 그룹을 역할별로 구분할 수 있다.
- 따라서 `oragrid` 하나만으로 실제 Grid Infrastructure와 DB Home 권한을 모두 표현한다고 단정하지 않는다.
- 구축 시 Oracle 설치 설계서, 제품 버전, 패치·백업 운영 요건과 대조하여 primary/secondary groups를 확정해야 한다.

## 7. “전 시스템 동일 부여”의 올바른 해석

### 일관되게 유지할 항목

- 계정명과 그룹명
- UID/GID 및 primary/secondary group 구조
- 홈 디렉터리와 로그인 셸
- 파일 소유권과 기본 umask
- sudo/PAM 역할 및 명령 정책
- 계정 잠금·만료·감사 기준

### 동일하게 공유하면 안 되는 항목

- 계정 비밀번호
- 개인 SSH private key
- 장기 고정 API 토큰과 DB 비밀번호
- 모든 서버에 대한 무제한 sudo 권한
- 운영·개발·DR 간 동일한 비밀정보
- 개인 식별 없이 사용하는 대화형 공용 세션

```text
표준 계정 정의 ── 동일 ──> 여러 서버의 이름·UID/GID·역할
자격증명       ── 분리 ──> 환경·시스템별 Vault/PAM Secret
개인 작업      ── 추적 ──> 개인 ID → 승인 → 서비스 계정 전환
```

## 8. UID/GID 표준

공유 스토리지와 HA 노드에서는 동일 파일이 모든 노드에서 같은 소유자로 보이도록 UID/GID를 일치시켜야 한다.

```yaml
account: tomcat
uid: <중앙할당값>
primary_group: tomcat
gid: <중앙할당값>
home: /userdir/tomcat
shell: /sbin/nologin
account_type: engine
interactive_login: false
credential_source: none
owner: <담당조직>
```

- UID/GID는 수동으로 빈 번호를 선택하지 않고 중앙 사전에서 예약한다.
- 로컬 `/etc/passwd`와 LDAP/AD/SSSD 계정의 이름·ID 충돌을 차단한다.
- 이미지 복제와 자동 확장 시에도 동일한 ID가 재현되도록 구성관리 도구를 사용한다.
- 계정 삭제 후 UID/GID를 즉시 재사용하지 않는다.

## 9. 계정 수명주기

```text
계정 요청
  → 소유자·목적·대상 환경 확인
  → 계정 유형과 코드 사전 검증
  → UID/GID 중앙 예약
  → 최소 권한·홈·셸·만료일 정의
  → 승인
  → 자동 생성 및 PAM/Vault/모니터링 등록
  → 정기 재인증
  → 잠금
  → 의존 파일·프로세스 정리
  → 보존기간 후 삭제/ID 재사용 금지
```

### 필수 계정 속성

| 속성 | 설명 |
|---|---|
| 계정 유형 | 엔진·업무·솔루션·개인관리자 |
| 소유자 | 업무/플랫폼 책임 조직과 담당자 |
| 목적 | 실행·설치·배포·조회·DB 소유 등 |
| 대상 | 서버 그룹, 환경, 애플리케이션 |
| UID/GID | 중앙 할당 식별자 |
| 로그인 정책 | 셸, PAM, MFA, 접속 원천 |
| 권한 | sudo 명령, 그룹, 파일 경로 |
| 자격증명 | Vault/PAM Secret ID, 회전 주기 |
| 유효기간 | 시작일, 만료일, 재인증일 |
| 상태 | 요청·활성·잠금·폐기 |

## 10. 인증과 비밀정보 관리

- 서비스 계정 비밀번호는 잠그고 비대화형 프로세스 실행을 우선한다.
- 대화형 전환이 필요하면 개인 계정에서 PAM 또는 `sudo -u`를 사용한다.
- SSH는 개인 키 또는 인증서를 사용하고 서비스 계정의 공유 private key를 금지한다.
- 애플리케이션·DB 비밀번호는 Vault에서 동적으로 조회하거나 단기 자격증명을 사용한다.
- 정적 비밀번호가 불가피하면 환경별로 분리하고 자동 회전한다.
- `/etc/shadow`, 계정 홈의 `.ssh`, keystore, wallet 권한과 접근 로그를 감시한다.
- CI/CD 계정은 사용자용 비밀번호 대신 범위가 제한된 machine identity를 사용한다.

## 11. sudo·PAM 및 접근통제

권한은 서버 전체가 아니라 작업 단위로 정의한다.

```text
예: WEB 운영 역할
  허용: systemctl status/reload <승인된 web service>
        승인된 로그 조회
        승인된 배포 스크립트 실행
  제한: 임의 shell 획득
        /etc/sudoers 수정
        다른 업무 파일 접근
        root 비밀번호 사용
```

- `/etc/sudoers.d`에서 역할별 정책을 관리하고 형상관리한다.
- `NOPASSWD: ALL`, wildcard 인자, 편집기·셸 탈출 가능한 명령을 금지한다.
- PAM 세션 기록, 명령 로그와 사유/작업번호를 중앙 수집한다.
- 운영·개발·DR 서버 그룹을 분리하고 접근 승인 범위를 독립 관리한다.

## 12. 파일시스템 연계

앞선 AP·DB 파일시스템 표준과 계정의 책임 관계는 다음과 같다.

| 경로 | 대표 소유 계정/그룹 | 권한 원칙 |
|---|---|---|
| `/pgm*` | 업무 계정 또는 배포 계정 + 엔진 그룹 | 배포 주체 쓰기, 엔진 읽기·실행 |
| `/aplog*` | 엔진 계정 | 엔진 쓰기, 관제·업무 운영 읽기 |
| `/userdir*` | 업무 계정 | 업무별 읽기·쓰기, 타 업무 차단 |
| Apache 영역 | `apache:apache` | WEB 엔진 최소 권한 |
| Tomcat 영역 | `tomcat:tomcat` | WAS 엔진 최소 권한 |
| `/nhod` | `oracle` 및 확정 Oracle 그룹 | DB 엔진·패치 책임 분리 |
| 솔루션 경로 | 각 솔루션 계정 | 제품별 전용 소유, 공용 쓰기 금지 |

공유 파일시스템에서는 계정 이름보다 숫자 UID/GID가 소유권 판단에 사용되므로 HA 모든 노드에서 일치 여부를 선검증해야 한다.

## 13. 감사·모니터링

### 계정 상태

- 신규·삭제·잠금·잠금해제·그룹 변경
- UID/GID, 홈, 셸, sudo 정책 변경
- 휴면, 만료 임박, 소유자 부재 계정
- 비밀번호 또는 키의 장기 미회전
- 승인 목록에 없는 로컬 계정과 중복 UID/GID

### 사용 행위

- 서비스 계정의 직접 SSH 로그인
- root 직접 로그인과 `su`/`sudo` 전환
- 실패 로그인, 비정상 접속지·시간대
- 엔진/솔루션 계정의 예상 외 명령 실행
- `.ssh/authorized_keys`, sudoers, cron 변경
- 중요 파일의 소유권·권한 변경

### 프로세스 정합성

- Apache가 `apache`, Tomcat이 `tomcat`으로 실행되는지
- DB2 fenced 프로세스와 인스턴스 프로세스의 계정 분리
- Oracle/Grid 프로세스 소유 계정과 그룹이 설계와 일치하는지
- 정지된 서비스의 계정이 불필요하게 활성 상태인지

## 14. 자동화 및 정책 검사

```yaml
accounts:
  - name: apache
    primary_group: apache
    type: engine
    shell: /sbin/nologin
    password_locked: true
    interactive_login: false

  - name: tomcat
    primary_group: tomcat
    type: engine
    shell: /sbin/nologin
    password_locked: true
    interactive_login: false

  - name: dsadm
    primary_group: dstage
    type: solution_admin
    login_via_pam: true
    owner: <담당조직>
```

자동 검사는 다음을 확인해야 한다.

1. 승인 계정 사전에 존재하는가?
2. 모든 대상 노드의 UID/GID가 일치하는가?
3. 셸·홈·그룹·잠금 상태가 표준과 일치하는가?
4. 엔진 계정이 대화형 로그인 가능한 상태가 아닌가?
5. 승인되지 않은 SSH 키와 sudo 규칙이 없는가?
6. 계정 소유자와 유효기간이 존재하는가?
7. 실제 실행 프로세스의 OS 계정이 설계와 일치하는가?

## 15. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 동일 계정의 공용 비밀번호 | 사용자 추적 불가·전 서버 침해 확산 | 개인 인증→PAM/sudo 전환, Secret 분리 |
| 엔진 계정의 대화형 로그인 | 애플리케이션 권한으로 우회 접근 | nologin·비밀번호 잠금·직접 SSH 차단 |
| UID/GID 불일치 | 공유 스토리지 권한 오류 | 중앙 할당·자동 정합성 검사 |
| 업무 계정에 엔진 그룹 쓰기 과다 | 바이너리·설정 변조 | 경로별 ACL과 배포 역할 분리 |
| `db2grp` 권한 집중 | DB2 역할 분리 약화 | primary/secondary 그룹 재검토 |
| `oracle:oragrid` 단순화 | Grid/DB 권한 과다 또는 설치 실패 | Oracle 역할별 계정·그룹 설계 대조 |
| `ci/cd` 그룹명 불확실 | 자동 생성 실패 | 실제 OS/디렉터리 그룹명 확인 |
| 퇴직·조직 변경 후 계정 존속 | 미승인 접근 | 소유자 기반 정기 재인증·자동 잠금 |
| 계정 삭제 후 UID 재사용 | 과거 파일이 새 사용자 소유로 표시 | 유예기간·폐기 레지스트리 운영 |

## 16. 검증 체크리스트

## 17. 최종 평가

이 사용자 계정 표준은 WEB/WAS 엔진, 업무 애플리케이션 및 주요 솔루션의 파일 소유권과 실행 주체를 일관되게 만드는 기초 통제다. 실효성을 확보하려면 동일 계정을 여러 서버에 생성하는 데 그치지 않고 **중앙 UID/GID, 개인 인증 기반 역할 전환, 서비스 계정 로그인 차단, 환경별 비밀정보 분리, 최소 권한 그룹 및 계정 수명주기**를 함께 적용해야 한다. 특히 장표의 `ci/cd`, `db2grp`, `oragrid`는 실제 OS·제품 설치 설계와 대조하여 유효성과 권한 범위를 확정하는 것이 필요하다.
