# 물리기술아키텍처 — 소프트웨어 구성도 — 개발환경 분석

> 원본 범위: `3. 물리 기술 아키텍처 > 3.2 소프트웨어 구성도`  
> 원본 장표: 76쪽, 개발 소프트웨어 구성도  
> 분석 원칙: 이미지에 표시된 노드·수량·소프트웨어·OS를 우선 기록한다. `@`가 붙은 명칭과 제품 표기는 원문을 유지하고, 불명확한 제품·버전은 임의 확정하지 않는다.

---

## 1. 핵심 결론

개발환경은 대부분의 업무 구성요소를 **노드별 1식**으로 배치하고, 개발·검증에 필요한 소스관리, SQL 품질, 단말 개발도구와 라이브러리를 추가한 통합 개발 구조다.

- 마케팅, BI, Self-BI, 신용실적, 데이터거버넌스, 단말, 배치·ETL·출력물 기능을 개발환경에 폭넓게 구성한다.
- 대부분 `Linux (RHEL9)`와 `Default S/W`를 공통 기반으로 사용한다.
- 실시간·행동정보 AP는 `Spring Boot + JDK`, 고객행동데이터 AP는 `Kafka(Kraft) + JDK`를 사용한다.
- 단말개발도구는 `WebSquareStudio`, 소스관리 AP는 `GitLab Runner + GitLab`, 라이브러리는 `NEXUS`를 사용한다.
- SQL품질/이행 임시 노드는 `SQL Canvas@ + SQL Cavas Adaptor + Open POP + DBMS Client`로 구성된다.
- RDW/ADW Appliance는 2개 노드이며 `OGG + DB Safer + DBMS`를 사용한다.

```text
개발 업무·도구
   ↓
WEB / WAS / AP / 전용 솔루션
   ↓
JDK · Kafka · Spring Boot · GitLab · Data Stage · OGG
   ↓
Default S/W
   ↓
Linux(RHEL9) / Linux
```

### 분석

- 실시간처리와 행동정보처리는 Spring Boot 기반 독립 AP로 구성된다.
- 고객행동데이터 AP의 Kafka는 실시간 이벤트 스트림의 저장·전달 기반이다.
- 장표의 `Kraft` 표기는 일반적으로 Kafka KRaft 모드를 의미할 수 있으나 버전과 실제 quorum 구성은 확인해야 한다.

## 14. 개발환경 고유 아키텍처 메커니즘

```text
개발자
  ↓ source push
GitLab
  ↓ pipeline
GitLab Runner
  ↓ dependency / artifact
NEXUS
  ↓ deploy
WEB · WAS · AP 개발 노드
  ↓ test data access
RDW / ADW Appliance
```

```text
실시간 이벤트
  ↓
Kafka(KRaft)
  ↓
실시간처리 AP / 행동정보처리 AP
  ↓
RDW·ADW 또는 연계 시스템
```

핵심은 개발 산출물의 버전 추적성과 운영 승격 일관성이다. Git commit, pipeline, NEXUS artifact, 배포 버전을 하나의 식별자로 연결해야 한다.

## 15. 운영환경 대비 주요 차이

| 관점 | 개발환경 | 운영환경 영향 |
|---|---|---|
| 노드 수 | 대부분 1식 | 이중화·부하·failover 동작을 그대로 재현하기 어려움 |
| 개발 도구 | GitLab, Runner, NEXUS, WebSquareStudio | 운영에는 직접 배치하지 않고 승인된 artifact만 승격 |
| 데이터 | 개발 RDW/ADW | 운영 데이터 반입 시 마스킹·접근통제 필요 |
| 임시 노드 | SQL품질/이행 | 프로젝트 종료 후 폐기·계정 회수 필요 |
| 스케줄 | 개발 Control-M | 운영 스케줄과 endpoint·calendar·agent 분리 필요 |
| Kafka | 단일 고객행동데이터 AP 표기 | 운영 quorum·replication·partition 차이 검증 필요 |
| DB | RDW/ADW 통합 표기 | 운영 Appliance 분리·용량·HA 차이 반영 필요 |

## 16. 주요 위험과 확인사항

| 위험 | 영향 | 대응 방향 |
|---|---|---|
| 단일 노드 의존 | 개발 중단 및 테스트 병목 | 백업·복구, VM 재생성, 중요 저장소 이중화 검토 |
| 개발·운영 버전 차이 | 승격 후 런타임 오류 | 기술 스택 버전 기준선과 호환성 매트릭스 관리 |
| 운영 데이터 반입 | 개인정보·기밀정보 유출 | 마스킹, 최소 샘플, 반출 승인, 보존기간 통제 |
| GitLab·Runner 동거 | 저장소와 빌드 장애 동시 발생 | 자원 격리, Runner 권한 최소화, 백업 검증 |
| NEXUS 오염 | 취약·변조 artifact 배포 | immutable repository, checksum·서명·SBOM 적용 |
| 개발 스케줄 오접속 | 운영 작업 오기동 | 네트워크·계정·Control-M 도메인 격리 |
| 임시 노드 장기 존치 | 보안 사각지대 | 종료일·소유자·폐기 증적 관리 |
| Default S/W 불명확 | 보안·관제 누락 | Agent·제품·버전·정책 목록 별도 관리 |

- [ ] 개발 데이터는 마스킹되고 정기적으로 초기화되는가?

- [ ] Kafka KRaft controller·broker·replication 설정이 시험 목적에 적합한가?
- [ ] SQL품질/이행 임시 서버의 종료일과 폐기 책임자가 지정되어 있는가?
- [ ] Default S/W의 보안·백업·관제 Agent가 정상 등록되었는가?
- [ ] 단일 노드 장애 후 개발환경 복원 절차를 시험했는가?

## 18. 최종 평가

개발환경은 서비스 전 영역을 단일 노드 위주로 제공하면서 소스관리, artifact 저장소, UI 개발도구, SQL 품질과 데이터 처리 도구까지 포함한 **통합 개발·검증 플랫폼**이다. 운영과 유사한 기술 스택을 사용한다는 장점이 있지만, 노드 수·데이터·스케줄·HA 구성은 운영과 다르므로 환경 차이를 명시적으로 관리해야 한다.

특히 `GitLab → Runner → NEXUS → 배포` 공급망, 운영 데이터 마스킹, Control-M·DB 계정 격리, 임시 이행 노드 폐기가 개발환경 통제의 핵심이다.
