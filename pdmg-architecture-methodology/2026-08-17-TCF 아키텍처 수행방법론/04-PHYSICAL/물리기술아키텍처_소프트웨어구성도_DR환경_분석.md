# 물리기술아키텍처 — 소프트웨어 구성도 — DR환경 분석

> 원본 범위: `3. 물리 기술 아키텍처 > 3.2 소프트웨어 구성도`  
> 원본 장표: 75쪽, DR 소프트웨어 구성도  
> 분석 원칙: 이미지에 명시된 노드·수량·소프트웨어·OS를 사실로 기록하고, 복구 절차·제품 버전·복제 방식은 별도 확인사항으로 구분한다.

---

## 1. 핵심 결론

DR 환경은 운영환경 전체를 동일하게 복제하는 구조가 아니라, 재해 시 우선 복구할 **마케팅 채널, 단말관리·배포, 마스터솔루션, RDW**를 선택적으로 구성한 축소형 복구 환경이다.

- 마케팅플랫폼과 미니싱글뷰는 WEB/WAS 각각 2개 노드로 구성된다.
- 단말관리 WEB/WAS는 각각 4개, 단말배포 WEB/WAS는 각각 6개 노드로 구성된다.
- 마스터솔루션은 테크시스템뷰 영역의 단일 노드로 표시된다.
- RDW Appliance는 2개 노드이며 `OGG + DB Safer + DBMS` 스택을 사용한다.
- 애플리케이션 서버는 `Linux (RHEL9)`, RDW Appliance는 `Linux`로 구분되어 있다.
- 장표의 `Default S/W`는 시스템 S/W·서버보안·백업·OS백업 계열 공통 소프트웨어를 의미하지만 개별 제품명은 표시되지 않는다.

```text
DR 서비스 복구 범위
  ├─ 마케팅 서비스
  │   ├─ 마케팅플랫폼 WEB/WAS
  │   └─ 미니싱글뷰 WEB/WAS
  ├─ 단말 운영
  │   ├─ 단말관리 WEB/WAS
  │   └─ 단말배포 WEB/WAS
  ├─ 공통 프레임워크
  │   └─ 마스터솔루션
  └─ 데이터 복구
      └─ RDW Appliance + OGG
```

## 2. 근거 수준

| 수준 | 내용 |
|---|---|
| 확인 사실 | DR 장표에 애플리케이션 노드 9종과 DB Appliance 1종이 표시됨 |
| 확인 사실 | 마케팅플랫폼·미니싱글뷰 WEB/WAS는 각각 `#51, #52` |
| 확인 사실 | 단말관리 WEB/WAS는 각각 `#51~#54` |
| 확인 사실 | 단말배포 WEB/WAS는 각각 `#51~#56` |
| 확인 사실 | 마스터솔루션은 `#51`, RDW Appliance는 `#51, #52` |
| 확인 사실 | 애플리케이션 노드는 Linux(RHEL9), RDW Appliance는 Linux로 표기 |
| 설계 해석 | 운영환경의 전체 기능이 아닌 핵심 서비스 중심의 선택적 DR 구성 |
| 설계 해석 | OGG는 운영 RDW에서 DR RDW로 변경 데이터를 전달하는 복제 계층 |
| 미확정 | OGG의 Extract·Data Pump·Replicat 실제 배치와 복제 방향 |
| 미확정 | DR 전환이 Active-Standby인지, 상시 기동 또는 콜드 대기인지 여부 |
| 미확정 | WEB/WAS 제품명, JVM 버전, DBMS 종류와 버전 |
| 미확정 | `Default S/W`에 포함되는 실제 제품과 DR 라이선스 |

        ↓
       WEB
        ↓
  Default S/W
        ↓

## 7. 데이터베이스 노드 세로 목록

### 7.1 RDW Appliance `#51, #52`

```text
[RDW Appliance]
        ↓
       OGG
        ↓
    DB Safer
        ↓
       DBMS
        ↓
  Default S/W
        ↓
      Linux
```

- 역할: DR 분석·업무 데이터 저장과 운영 RDW 변경 데이터 수신

- `DBMS`: 실제 DB 제품과 버전은 장표에서 확인되지 않는다.
- 확인사항: 복제 지연 허용치, 장애 시점 정합성, 미적용 트랜잭션 처리, 양방향 복제 여부, 승격·역복제 절차

## 9. 운영환경 대비 DR 구성 차이

| 영역 | 운영환경 | DR환경 | 분석 |
|---|---|---|---|
| 마케팅 | 마케팅·미니싱글뷰·실시간·행동정보·고객행동 | 마케팅·미니싱글뷰 WEB/WAS | 실시간/행동 AP는 DR 장표에 없음 |
| BI·실적 | BI포탈·신용실적·Self-BI | 미표시 | DR 복구 범위 또는 별도 대책 확인 필요 |
| 거버넌스 | 비즈메타·데이터품질·데이터흐름 | 미표시 | 복구 우선순위가 낮거나 별도 구성일 가능성 |
| 단말 | 단말관리·단말배포 | 동일 기능군 존재 | DR에서 다중 노드로 구성 |
| 배치·ETL·CDC | 배치 AP, ETL, CDC중계 DB | RDW OGG만 표시 | 배치·ETL 재개 위치 및 CDC 경로 확인 필요 |
| DB | ADW·RDW Appliance | RDW Appliance만 표시 | ADW 의존 서비스의 DR 데이터 확보 방식 확인 필요 |
| 이행 임시노드 | 변환·이행·SQL품질·추출 | 미표시 | 재해복구 상시 대상에서 제외된 것으로 해석 가능 |

운영환경에 존재하지만 DR 장표에 보이지 않는 구성요소를 곧바로 “DR 미구축”으로 단정할 수는 없다. 별도 센터, 외부 공용 인프라, 백업 복구 또는 문서 범위 제외 가능성이 있으므로 DR 범위표와 대조해야 한다.

## 10. DR 전환 메커니즘 해석

```text
[정상 운영]
의왕 센터 서비스 ──업무 처리──> 운영 RDW
                         │
                         └── OGG 변경복제 ──> DR RDW

[재해 발생]
장애 감지
   ↓
재해 선언 및 데이터 복제 상태 확인
   ↓
DR RDW 승격·쓰기 정책 적용
   ↓
마스터솔루션 → 단말관리/배포 → 마케팅 WAS → WEB 기동
   ↓
GSLB/L4/DNS 또는 연계 endpoint를 DR로 전환
   ↓
기능·데이터 정합성 검증 후 서비스 개방
```

위 순서는 장표에서 직접 제시된 절차가 아니라 구성요소 의존성을 바탕으로 한 권고 흐름이다. 실제 Runbook의 순서는 DB 역할, 인증·연계 시스템, 네트워크 전환 구조에 따라 달라질 수 있다.

## 11. 주요 아키텍처 위험

| 위험 | 영향 | 확인·대응 방향 |
|---|---|---|
| DR 범위 축소 | 운영 서비스 일부를 DR에서 제공하지 못함 | 업무별 RTO/RPO와 DR 포함 여부 매핑 |
| 마스터솔루션 단일 노드 | 공통 관리 기능 단일 실패점 | 이중화 또는 신속 재기동·복원 검증 |
| OGG 복제 지연 | DR 데이터 유실 또는 시점 불일치 | lag 임계치, 알람, 재동기화 절차 수립 |
| ADW 미표시 | ADW 의존 서비스 복구 불가 가능성 | ADW 백업·원격복제·대체 조회 경로 확인 |
| 설정 불일치 | 기동은 되지만 연계·인증 실패 | WEB/WAS/인증서/endpoint 구성 비교 자동화 |
| Default S/W 불명확 | 보안·백업·관제 누락 | 제품·Agent·정책·라이선스 명세화 |
| 배포 작업 중 전환 | 중복·부분 배포 발생 | 트랜잭션·멱등성·재시도 기준 정의 |
| 외부 연계 미표시 | DR 전환 후 상대 시스템 접속 실패 | 방화벽, DNS, 인증서, allowlist 사전 점검 |

## 12. 검증 체크리스트

- [ ] 운영·DR 애플리케이션 버전과 배포 checksum이 일치하는가?
- [ ] WEB/WAS 설정, 인증서, 계정, 암호화 키가 안전하게 동기화되는가?
- [ ] OGG 복제 lag와 오류를 24시간 탐지하는가?
- [ ] DR RDW 승격과 운영 복귀 시 역복제 절차가 있는가?
- [ ] 마케팅플랫폼·미니싱글뷰의 DB 및 외부 연계 주소가 DR용으로 전환되는가?
- [ ] 단말관리·배포 작업의 중단·재시작·중복방지 절차가 있는가?
- [ ] 마스터솔루션 단일 노드 장애 복구가 RTO 안에 가능한가?
- [ ] Default S/W의 보안·백업·관제 Agent가 DR에도 등록되어 있는가?
- [ ] 장표에 없는 BI·ADW·배치·ETL 서비스의 DR 대책이 별도 정의되어 있는가?
- [ ] 정기 DR 훈련에서 실제 업무 검증과 데이터 대사까지 수행하는가?

## 13. 최종 평가

DR 소프트웨어 구성은 마케팅 채널과 단말 운영, RDW 데이터 계층을 중심으로 복구 자원을 집중한 구조다. 다중 WEB/WAS 노드와 2노드 RDW Appliance는 기본적인 서비스 복구 기반을 제공하지만, 마스터솔루션 단일 노드와 운영환경 대비 다수의 미표시 영역은 복구 범위와 의존성을 명확히 해야 할 지점이다.

따라서 이 장표는 **DR에 무엇이 설치되는지**를 설명하는 배치 기준으로는 유효하지만, 실제 재해복구 능력을 입증하려면 `RTO/RPO`, OGG 복제 상태, 전환 Runbook, 네트워크·인증 전환, 운영 복귀 절차와 정기 훈련 결과가 함께 관리되어야 한다.
