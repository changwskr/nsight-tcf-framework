# 메커니즘·아키텍처 표준 — 미들웨어 아키텍처 거래 처리 구조 분석

## 1. 문서 목적

본 문서는 제공된 5개 아키텍처 이미지를 기준으로 차세대 정보계의 미들웨어 거래 처리 경로를 분석한다. 분석 범위는 다음과 같다.

- 전체 거래 처리 경로
- 미니 싱글뷰 거래 처리 경로
- 마케팅플랫폼 거래 처리 경로
- BI 포털 신용실적 거래 처리 경로
- BI 포털·OLAP·Self-BI 업무 솔루션 거래 처리 경로
- L4, WEB, WAS의 역할과 이중화 방식
- 도메인·URL·컨텍스트·WAR 배포 단위의 대응 관계
- 장애 처리, 세션, 보안 및 운영 관점의 설계 시사점

> 구분 원칙: 이미지에서 직접 확인되는 내용은 **원본 사실(FACT)**, 구조로부터 도출한 설명은 **분석(ANALYSIS)**, 추가 검증이 필요한 내용은 **확인 필요**로 표시한다.

## 2. 핵심 결론

이 미들웨어 아키텍처는 업무별 전용 도메인과 내부망 L4를 진입점으로 사용하고, WEB 2대와 WAS 2대를 교차 연결하는 수평 이중화 구조다.

```text
사용자 Client
    │
    │ http://{업무도메인}/{컨텍스트 또는 패키지 URL}
    ▼
내부망 L4 (VIP, 부하분산, 헬스체크)
    ├───────────────┐
    ▼               ▼
WEB #1           WEB #2
    ├───────┬───────┤
    ▼       ▼       ▼
WAS #1           WAS #2
    │               │
    └── 동일 WAR/업무 서비스 배포 ──┘
```

핵심 특성은 다음과 같다.

1. **업무별 도메인 분리**: `ms`, `mp`, `cr`, `pt`, `oa`, `sb` 도메인으로 서비스 경계를 구분한다.
2. **L4 기반 확장·가용성**: 내부망 L4가 2대의 WEB 서버로 요청을 분산한다.
3. **WEB–WAS 완전 교차 연결**: 특정 WEB 또는 WAS 장애 시 잔여 노드로 우회할 수 있다.
4. **WAR 기반 애플리케이션 분리**: 마케팅플랫폼은 업무 코드별 WAR를 동일 WAS 군에 배포한다.
5. **업무 솔루션별 독립 스택**: BI 포털, OLAP, Self-BI는 각각 전용 WEB/WAS 군과 도메인을 갖는다.

## 3. 전체 거래 처리 구조

### 3.1 원본 전체 구성

| 서비스 영역 | 호출 주체 | 운영 도메인·URL | WEB 계층 | WAS 계층 |
|---|---|---|---|---|
| 미니 싱글뷰 | 통합업무시스템 | `http://ms.prod.nacf/ms/{서비스코드}` | 미니싱글뷰 WEB #1, #2 | 미니싱글뷰 WAS #1, #2 |
| 마케팅플랫폼 | 정보단말 | `http://mp.prod.nacf/{업무코드}/{서비스코드}` | 마케팅플랫폼 WEB #1, #2 | 마케팅플랫폼 WAS #1, #2 |
| 신용실적 | BI 포털 정보단말 | `http://cr.prod.nacf/cr/{서비스코드}` | 신용실적 WEB #1, #2 | 신용실적 WAS #1, #2 |
| BI 포털 | BI 포털 패키지 UI | `http://pt.prod.nacf/{패키지 URL}` | BI포털 WEB #1, #2 | BI포털 WAS #1, #2 |
| OLAP | OLAP 패키지 UI | `http://oa.prod.nacf/{패키지 URL}` | OLAP WEB #1, #2 | OLAP WAS #1, #2 |
| Self-BI | Self-BI 패키지 UI | `http://sb.prod.nacf/{패키지 URL}` | Self-BI WEB #1, #2 | Self-BI WAS #1, #2 |

모든 영역은 내부망에 배치되며 각 업무 도메인 뒤에 내부망 L4가 존재한다.

### 3.2 공통 요청·응답 흐름

```text
[1] Client가 업무 도메인으로 HTTP 요청
      │
[2] DNS가 업무 도메인을 내부망 L4 VIP로 해석
      │
[3] L4가 가용 WEB #1 또는 WEB #2로 분산
      │
[4] WEB가 URL/컨텍스트 기준으로 요청을 해석
      │
[5] WEB가 가용 WAS #1 또는 WAS #2로 전달
      │
[6] WAS의 해당 WAR/솔루션이 서비스 코드 처리
      │
[7] 처리 결과가 WAS → WEB → L4 → Client 역순으로 반환
```

### 3.3 계층별 책임

| 계층 | 주요 책임 | 장애 시 기대 동작 |
|---|---|---|
| 업무 도메인/DNS | 업무별 논리 주소 제공, 물리 주소 은닉 | VIP 전환 또는 DNS/GSLB 정책 적용 |
| 내부망 L4 | WEB 부하분산, 헬스체크, 장애 노드 제외 | 정상 WEB로 신규 요청 우회 |
| WEB | 정적 콘텐츠, 프록시·라우팅, WAS 연결 | 다른 WEB가 서비스 지속 |
| WAS | 세션·업무 로직·프레임워크 실행, WAR 호스팅 | 다른 WAS가 요청 처리 |
| WAR/업무 솔루션 | 컨텍스트별 업무 기능 및 서비스 코드 처리 | 동일 산출물이 양 WAS에 배포되어야 함 |

## 4. 미니 싱글뷰 거래 처리 경로

### 4.1 원본 구조

```text
미니 싱글뷰(통합업무시스템)
    │  http://ms.prod.nacf/ms/{서비스코드}
    ▼
내부망 L4
    ├──────────────────┐
    ▼                  ▼
미니싱글뷰 WEB #1   미니싱글뷰 WEB #2
    ├──────────┬────────┤
    ▼          ▼        ▼
미니싱글뷰 WAS #1   미니싱글뷰 WAS #2
  /ms.war           /ms.war
```

### 4.2 URL–배포 단위 대응

| 항목 | 값 |
|---|---|
| 업무 도메인 | `ms.prod.nacf` |
| 컨텍스트 경로 | `/ms` |
| 서비스 경로 | `/{서비스코드}` |
| 최종 패턴 | `http://ms.prod.nacf/ms/{서비스코드}` |
| 배포 산출물 | `/ms.war` |
| 배포 대상 | 미니싱글뷰 WAS #1, #2 |

### 4.3 분석

- `/ms` 컨텍스트는 `ms.war`의 애플리케이션 컨텍스트로 해석된다.
- 동일한 `ms.war`가 두 WAS에 배포되므로 애플리케이션 버전과 설정의 동기화가 필수다.
- WEB 두 대가 WAS 두 대 모두에 연결되므로 WEB–WAS 간 단일 종속점이 없다.
- 통합업무시스템의 미니 싱글뷰는 브라우저 직접 접속보다 시스템 간 웹 거래 성격이 강하다.

## 5. 마케팅플랫폼 거래 처리 경로

### 5.1 전체 경로

```text
마케팅플랫폼 정보단말
    │  http://mp.prod.nacf/{업무코드}/{서비스코드}
    ▼
내부망 L4
    ├──────────────────────┐
    ▼                      ▼
마케팅플랫폼 WEB #1    마케팅플랫폼 WEB #2
    ├────────────┬─────────┤
    ▼            ▼         ▼
마케팅플랫폼 WAS #1    마케팅플랫폼 WAS #2
    └─ 업무 코드별 동일 WAR 세트 배포 ─┘
```

### 5.2 업무 코드·WAR·기능 대응

| 업무 코드 | 배포 파일 | 원본 표기 기능 | URL 패턴 |
|---|---|---|---|
| `ws` | `/ws.war` | SSO 인증 | `http://mp.prod.nacf/ws/{서비스코드}` |
| `ic` | `/ic.war` | 통합고객 | `http://mp.prod.nacf/ic/{서비스코드}` |
| `pc` | `/pc.war` | 개인고객 | `http://mp.prod.nacf/pc/{서비스코드}` |
| `bc` | `/bc.war` | 기업고객 | `http://mp.prod.nacf/bc/{서비스코드}` |
| `sa` | `/sa.war` | 상담 판매 | `http://mp.prod.nacf/sa/{서비스코드}` |
| `pd` | `/pd.war` | 통합상품 | `http://mp.prod.nacf/pd/{서비스코드}` |
| `cm` | `/cm.war` | 캠페인 | `http://mp.prod.nacf/cm/{서비스코드}` |
| `eb` | `/eb.war` | EBM | `http://mp.prod.nacf/eb/{서비스코드}` |
| `ss` | `/ss.war` | 영업지원 | `http://mp.prod.nacf/ss/{서비스코드}` |

### 5.3 컨텍스트 기반 디스패치

```text
요청 URL
  http://mp.prod.nacf/cm/MPCM0001
                   │   └─ 서비스 코드
                   └───── 업무 컨텍스트
                         │
                         ▼
                     cm.war
                         │
                         ▼
              Controller → Service → DAO
```

### 5.4 분석

- 단일 마케팅플랫폼 WAS 클러스터 안에서 업무 도메인을 WAR 단위로 격리한다.
- 업무 코드가 URL 컨텍스트, WAR 이름 및 패키지 대구분 코드와 일관되게 연결되는 구조다.
- 특정 WAR만 재배포할 수 있으나, 공통 라이브러리 또는 프레임워크 변경 시 전체 WAR 호환성 검증이 필요하다.
- `ws.war`는 SSO 인증을 담당하므로 일반 업무 WAR보다 보안·세션 의존성이 크다.
- 원본의 전체 거래 경로 이미지에는 일부 URL만 예시로 보이지만, 상세 이미지에서는 12개 컨텍스트가 확인된다.

## 6. BI 포털 신용실적 거래 처리 경로

### 6.1 원본 구조

```text
BI 포털(정보단말)
    │  http://cr.prod.nacf/cr/{서비스코드}
    ▼
내부망 L4
    ├──────────────────┐
    ▼                  ▼
신용실적 WEB #1     신용실적 WEB #2
    ├──────────┬────────┤
    ▼          ▼        ▼
신용실적 WAS #1     신용실적 WAS #2
  /ws.war           /ws.war
  /cr.war           /cr.war
```

### 6.2 컨텍스트 구성

| 컨텍스트 | 배포 파일 | 역할 |
|---|---|---|
| `/ws` | `/ws.war` | SSO 인증 |
| `/cr` | `/cr.war` | 신용실적 업무 |

### 6.3 분석

- `cr.prod.nacf`는 신용실적 업무 전용 운영 도메인이다.
- 거래 URL의 `/cr`은 `cr.war`로 라우팅된다.
- 인증용 `ws.war`와 업무용 `cr.war`가 동일 WAS 군에 함께 배포된다.
- 두 WAS에서 인증·업무 애플리케이션 버전이 일치해야 한다.

## 7. 업무 솔루션 거래 처리 경로

### 7.1 통합 구조

```text
BI 포털 패키지 UI       OLAP 패키지 UI          Self-BI 패키지 UI
        │                       │                       │
 pt.prod.nacf/{URL}      oa.prod.nacf/{URL}      sb.prod.nacf/{URL}
        │                       │                       │
     L4(VIP)                 L4(VIP)                 L4(VIP)
     ┌──┴──┐                 ┌──┴──┐                 ┌──┴──┐
 BI WEB1  WEB2           OLAP WEB1 WEB2          Self-BI WEB1 WEB2
     ╲    ╱                  ╲    ╱                  ╲    ╱
     ╱    ╲                  ╱    ╲                  ╱    ╲
 BI WAS1  WAS2           OLAP WAS1 WAS2          Self-BI WAS1 WAS2
```

### 7.2 서비스별 비교

| 구분 | 운영 도메인 | 요청 단위 | 전용 WEB/WAS | 비고 |
|---|---|---|---|---|
| BI 포털 | `pt.prod.nacf` | 패키지 URL | 각 2대 | BI 포털 패키지 UI |
| OLAP | `oa.prod.nacf` | 패키지 URL | 각 2대 | OLAP 패키지 UI |
| Self-BI | `sb.prod.nacf` | 패키지 URL | 각 2대 | Self-BI 패키지 UI |

### 7.3 분석

- 프레임워크 서비스와 달리 `{서비스코드}` 대신 솔루션 고유의 `{패키지 URL}`을 사용한다.
- 솔루션마다 독립 도메인, L4, WEB, WAS 군을 사용하여 장애와 자원 경합을 격리한다.
- WEB–WAS 교차 연결은 세 솔루션 모두 동일한 고가용성 패턴을 따른다.
- 배포·패치·라이선스·세션 구성은 솔루션별로 독립 관리할 가능성이 높다.

## 8. 이중화 및 장애 처리 메커니즘

### 8.1 정상 상태

```text
L4
 ├─ WEB #1 ─┬─ WAS #1
 │          └─ WAS #2
 └─ WEB #2 ─┬─ WAS #1
            └─ WAS #2
```

### 8.2 WEB #1 장애

```text
L4 ──X WEB #1
 └──── WEB #2 ──┬─ WAS #1
                └─ WAS #2
```

L4 헬스체크가 WEB #1을 제외하고 신규 요청을 WEB #2로 전달해야 한다.

### 8.3 WAS #1 장애

```text
WEB #1 ──X WAS #1
   └────── WAS #2
WEB #2 ──X WAS #1
   └────── WAS #2
```

두 WEB 모두 WAS #2를 통해 서비스를 지속할 수 있어야 한다.

### 8.4 운영 필수 조건

- L4 헬스체크는 단순 포트 확인뿐 아니라 애플리케이션 상태 URL을 사용하는 것이 바람직하다.
- WEB의 WAS 연결 풀에서 장애 노드를 신속히 제외하고 복구 후 자동 편입해야 한다.
- 두 WAS의 WAR, 설정, 공통 라이브러리, 인증서 버전이 동일해야 한다.
- 세션을 WAS 메모리에만 저장하면 장애 시 유실될 수 있으므로 세션 복제, 외부 세션 저장소 또는 무상태 설계를 검토해야 한다.
- 배포 시 한 노드씩 교체하는 롤링 배포와 L4 드레인 절차가 필요하다.

## 9. URL 라우팅 표준

### 9.1 프레임워크형 서비스

```text
http://{업무코드}.prod.nacf/{애플리케이션코드}/{서비스코드}
```

예시:

```text
http://ms.prod.nacf/ms/{서비스코드}
http://mp.prod.nacf/ic/{서비스코드}
http://cr.prod.nacf/cr/{서비스코드}
```

### 9.2 패키지 솔루션형 서비스

```text
http://{솔루션코드}.prod.nacf/{패키지 URL}
```

예시:

```text
http://pt.prod.nacf/{패키지 URL}
http://oa.prod.nacf/{패키지 URL}
http://sb.prod.nacf/{패키지 URL}
```

### 9.3 권고 사항

- 운영 거래는 평문 HTTP보다 HTTPS 적용을 원칙으로 한다.
- 외부에 WAR 파일명이나 물리 노드명이 노출되지 않도록 논리 URL을 유지한다.
- 서비스 코드는 중앙 레지스트리에서 중복과 폐기 상태를 관리한다.
- URL의 업무 코드와 배포 WAR 이름을 일치시켜 추적성을 높인다.
- 인증, 인가, GUID, 거래 로그 정책을 모든 컨텍스트에 공통 적용한다.

## 10. 배포 구조와 변경 관리

### 10.1 배포 정합성

| 점검 항목 | 기준 |
|---|---|
| 산출물 버전 | WAS #1과 #2에 동일 버전 배포 |
| 컨텍스트 경로 | URL 업무 코드와 WAR 컨텍스트 일치 |
| 설정 파일 | 환경별 값만 분리하고 구조는 동일 |
| DB 스키마 | 애플리케이션 배포 버전과 호환 |
| 인증서·키 | 노드 간 동일 정책과 유효기간 관리 |
| 롤백 | 직전 정상 WAR와 설정을 즉시 복원 가능 |

### 10.2 권장 배포 순서

```text
1. L4에서 WAS 연계 대상 노드 드레인
2. 대상 WAS의 기존 산출물 백업
3. 신규 WAR 배포 및 기동
4. 상태·서비스 코드·DB 연결 점검
5. L4/WEB 경로에 재편입
6. 반대편 WAS에 동일 절차 수행
7. WEB 설정 변경이 있으면 WEB도 순차 반영
8. 전체 경로와 장애 우회 시험
```

## 11. 보안·관측성·성능 관점

### 11.1 보안

- L4 또는 WEB에서 TLS를 종료하더라도 내부 구간 암호화 필요성을 별도 평가한다.
- `ws.war`의 SSO 인증 결과가 다른 업무 WAR에 안전하게 전달되는지 검증한다.
- 서비스 코드별 권한, 입력 검증, 호출자 식별 및 감사 로그를 적용한다.
- 관리·상태 확인 URL은 업무망에서만 접근하도록 제한한다.

### 11.2 관측성

각 요청에는 동일한 거래 식별자(GUID)를 유지하는 것이 바람직하다.

```text
L4 access log
  → WEB access/error log
    → WAS transaction/APM log
      → Controller/Service log
        → DB session/SQL trace
```

필수 지표:

- L4 노드별 연결 수, 제외 횟수, 응답 시간
- WEB 요청률, 4xx/5xx, WAS 연결 실패율
- WAS 스레드·힙·GC·세션·커넥션 풀
- 컨텍스트/WAR별 TPS, 오류율, 지연시간
- 서비스 코드별 성공·업무 오류·시스템 오류 비율

### 11.3 성능

- 정적 자원은 WEB 또는 캐시 계층에서 처리하여 WAS 부하를 줄인다.
- WEB–WAS 연결 풀과 타임아웃을 L4 타임아웃보다 짧게 조정해 장애 전파를 제어한다.
- 업무 WAR별 자원 사용량을 측정해 특정 컨텍스트가 전체 WAS를 고갈시키지 않도록 한다.
- 장시간 처리 거래는 동기 HTTP 요청과 분리하는 방안을 검토한다.

## 12. 원본 사실과 확인 필요 사항

### 12.1 원본 사실(FACT)

- 모든 거래 경로는 내부망으로 표시되어 있다.
- 각 업무 영역은 내부망 L4, WEB 2대, WAS 2대로 구성된다.
- WEB와 WAS 사이에는 교차 연결이 표시되어 있다.
- 마케팅플랫폼의 두 WAS에는 동일한 12개 WAR가 배포된다.
- 신용실적의 두 WAS에는 `/ws.war`, `/cr.war`가 배포된다.
- BI 포털, OLAP, Self-BI는 각각 전용 도메인과 WEB/WAS 군을 사용한다.

### 12.2 분석(ANALYSIS)

- 교차 연결은 특정 WEB–WAS 쌍의 장애가 전체 서비스 장애로 확대되는 것을 방지한다.
- 업무 코드별 WAR 분리는 배포 단위와 장애 분석 단위를 명확히 한다.
- L4는 WEB 계층의 고가용성을 제공하지만 WAS 장애 감지는 WEB의 커넥터 설정에도 의존한다.
- 무상태 또는 외부 세션 저장소가 보장되지 않으면 노드 장애 시 사용자 세션이 영향을 받을 수 있다.

### 12.3 확인 필요

1. L4의 실제 부하분산 방식(Round Robin, Least Connection 등)
2. L4 및 WEB의 헬스체크 URI와 실패·복구 임계값
3. WEB–WAS 연결 기술과 커넥터(AJP, HTTP 등)
4. 세션 스티키 여부, 세션 복제 또는 외부 세션 저장소 사용 여부
5. TLS 종료 위치와 내부 구간 암호화 여부
6. 각 업무의 WEB/WAS 제품 및 버전
7. BI 포털·OLAP·Self-BI의 실제 패키지 URL 규칙
8. 마케팅플랫폼 목록의 `ws`가 도메인 정의 문서의 애플리케이션 분류에 포함되는지 여부
9. 재시도·타임아웃·서킷 브레이커 기준
10. DR 전환 시 도메인/VIP 및 세션 처리 방식

## 14. 운영 체크리스트

### 배포 전

- [ ] 도메인, 컨텍스트, 서비스 코드 등록이 완료되었다.
- [ ] 두 WAS에 배포할 WAR의 해시와 버전이 동일하다.
- [ ] DB·외부 연계·SSO 설정이 환경에 맞다.
- [ ] 롤백 산출물과 절차가 준비되었다.

### 배포 후

- [ ] L4 → WEB → WAS 전체 경로를 점검했다.
- [ ] 모든 컨텍스트의 대표 서비스 코드를 호출했다.
- [ ] WEB/WAS 각 노드의 로그와 APM에 거래가 기록된다.
- [ ] 노드별 버전, 설정, 인증서가 일치한다.

### 장애 훈련

- [ ] WEB 단일 노드 장애 우회를 검증했다.
- [ ] WAS 단일 노드 장애 우회를 검증했다.
- [ ] 세션 유지 또는 재인증 동작을 검증했다.
- [ ] L4 복구 노드 재편입 시 트래픽 급증이 통제된다.

## 15. 최종 평가

본 구조는 업무 도메인 분리와 WEB/WAS 이중화를 통해 확장성, 장애 격리 및 운영 독립성을 확보한 전형적인 엔터프라이즈 미들웨어 아키텍처다. 마케팅플랫폼은 업무 코드별 WAR로 기능을 세분화하고, BI 계열 패키지 솔루션은 서비스별 독립 WEB/WAS 군으로 격리한다.

다만 실제 고가용성은 그림의 노드 수만으로 보장되지 않는다. L4·WEB 헬스체크, WEB–WAS 장애 제외, 세션 외부화, 노드 간 배포 정합성, 표준 거래 식별자 및 롤링 배포 절차가 함께 구현되어야 한다. 특히 `도메인 → 컨텍스트 → WAR → 서비스 코드` 대응표를 구성관리 대상으로 관리하는 것이 이 구조의 운영 안정성을 좌우한다.
