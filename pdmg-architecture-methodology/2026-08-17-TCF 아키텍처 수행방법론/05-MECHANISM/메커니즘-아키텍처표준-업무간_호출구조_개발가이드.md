# 업무 간 호출 구조 개발 가이드

## 1. 목적

이 문서는 온라인 업무 컴포넌트 사이의 허용 호출과 금지 호출을 정의한다. 개발자는 이 규칙을 통해 다음을 보장해야 한다.

- Controller·Service·DAO의 책임 분리
- 기능과 애플리케이션의 캡슐화
- 업무 데이터 소유권 보호
- 순환 의존성과 변경 영향 최소화
- 로컬 및 원격 거래의 일관된 예외·트랜잭션 처리

---

## 2. 적용 범위

호출 범위는 다음 다섯 단계로 구분한다.

1. 같은 기능 내부
2. 같은 애플리케이션의 타 기능
3. 업무 공통 유틸리티
4. 타 애플리케이션
5. 타 애플리케이션 그룹 또는 외부 시스템

```text
애플리케이션 그룹
└─ 애플리케이션
   └─ 기능
      ├─ Controller
      ├─ Service
      ├─ DAO
      └─ 소유 테이블
```

---

## 3. 핵심 원칙

### 원칙 1 — 내부 호출은 계층 방향을 지킨다

```text
Controller → Service → DAO → Database
```

계층을 건너뛰거나 역방향으로 호출하지 않는다.

### 원칙 2 — 경계를 넘으면 공식 진입점을 사용한다

- 타 기능: 상대 기능의 Service 계약
- 공통 유틸리티: Utility Service 계약
- 타 애플리케이션: 상대 애플리케이션의 공개 Controller/API
- 타 그룹: API Gateway, 표준 HTTP API 또는 메시지 계약

### 원칙 3 — 상대 업무의 DAO와 테이블을 직접 접근하지 않는다

데이터는 이를 소유한 업무의 Service를 통해서만 조회·변경한다.

### 원칙 4 — 호출자는 구현이 아니라 계약에 의존한다

호출자는 상대 Controller 구현 클래스, DAO, 엔티티가 아니라 공개 인터페이스와 DTO에 의존한다.

### 원칙 5 — 원격 호출은 로컬 트랜잭션으로 묶지 않는다

애플리케이션 또는 그룹 경계를 넘는 호출에는 멱등성, 타임아웃, 재시도, 보상 처리를 적용한다.

## 5. 범위별 구현 가이드

### 5.1 같은 기능 내부 호출

Controller는 요청 검증과 흐름 제어만 담당하고 업무 규칙은 Service에 위임한다.

```java
public class CampaignController {
    private final CampaignService campaignService;

    public CampaignResponse create(CampaignRequest request) {
        CampaignCommand command = CampaignMapper.toCommand(request);
        CampaignResult result = campaignService.create(command);
        return CampaignMapper.toResponse(result);
    }
}
```

Service는 업무 규칙과 트랜잭션 단위를 정의한다.

```java
public class CampaignService {
    private final CampaignDao campaignDao;

    @Transactional
    public CampaignResult create(CampaignCommand command) {
        validate(command);
        Campaign campaign = Campaign.create(command);
        campaignDao.insert(campaign);
        return CampaignResult.from(campaign);
    }
}
```

DAO는 영속성 처리만 담당한다.

```java
public class CampaignDao {
    public void insert(Campaign campaign) {
        sqlSession.insert("Campaign.insert", campaign);
    }
}
```

### 5.2 타 기능 호출

Controller가 상대 기능의 공개 Service 인터페이스를 호출한다.

```java
public class CampaignController {
    private final CampaignService campaignService;
    private final CustomerQueryService customerQueryService;

    public CampaignResponse create(CampaignRequest request) {
        CustomerSummary customer =
            customerQueryService.findSummary(request.customerId());

        CampaignResult result =
            campaignService.create(request.toCommand(customer));

        return CampaignResponse.from(result);
    }
}
```

금지 사항:

- A Service가 B Service를 직접 호출
- A Controller가 B DAO를 직접 호출
- A DAO가 B DAO를 호출
- A 기능이 B 기능의 테이블을 직접 조회·갱신

타 기능 호출이 반복적으로 필요하면 두 기능의 책임 경계를 재검토하거나 명시적인 오케스트레이션 Service 도입을 아키텍처 검토 대상으로 올린다.

### 5.3 공통 유틸리티 호출

공통 유틸리티는 독립 거래가 아닌 재사용 기능을 제공한다.

적합한 예:

- 공통 코드 조회
- 기준일·영업일 계산
- 공통 식별자 생성
- 공통 포맷 변환
- 애플리케이션 공통 기준정보 조회

부적합한 예:

- 특정 업무만 사용하는 상태 전이
- 업무별 조건문이 다수 포함된 처리
- 화면별 편의 로직
- 소유자가 불명확한 공용 테이블 갱신

```java
public interface BusinessCalendarService {
    LocalDate nextBusinessDay(LocalDate baseDate);
}
```

공통 유틸리티의 API는 작고 안정적으로 유지하며, 요청 상태를 인스턴스 필드에 보관하지 않는다.

### 5.4 타 애플리케이션 호출

상대 애플리케이션의 공개 API 계약을 호출한다. 구현 Controller 클래스를 직접 생성하거나 상대 Service·DAO를 import하지 않는다.

```java
public interface MessageApplicationClient {
    SendMessageResult send(SendMessageCommand command);
}
```

```java
public class HttpMessageApplicationClient
        implements MessageApplicationClient {

    private final MessageApi messageApi;

    @Override
    public SendMessageResult send(SendMessageCommand command) {
        return messageApi.send(command);
    }
}
```

동일 프로세스에 배포되더라도 `Client/Port` 인터페이스를 통해 호출하면 향후 원격 분리 시 변경 영향을 줄일 수 있다.

### 5.5 타 그룹 및 외부 시스템 호출

타 그룹 호출에는 다음을 필수 적용한다.

- API Gateway 또는 표준 메시지 채널
- 서비스 간 인증·인가
- 연결·응답 타임아웃
- 제한된 재시도와 지수 백오프
- Circuit Breaker와 Bulkhead
- 멱등키 및 중복 처리 방지
- 표준 오류코드와 `traceId`
- API 버전 및 폐기 정책

동기 처리가 꼭 필요하지 않으면 메시지 기반 비동기 호출을 우선 검토한다.

## 6. 금지 호출 사례

### 6.1 Controller에서 DAO 직접 호출

```java
// 금지
public CampaignResponse create(CampaignRequest request) {
    campaignDao.insert(request);
    return CampaignResponse.ok();
}
```

문제점:

- 업무 검증과 트랜잭션 규칙을 우회한다.
- Controller가 DB 구조에 결합된다.
- 재사용과 단위 테스트가 어려워진다.

### 6.2 타 업무 테이블 직접 접근

```sql
-- 금지: 캠페인 DAO가 신용실적 소유 테이블을 직접 조회
SELECT *
  FROM TB_BLCRE_RESULT
 WHERE CUSTOMER_ID = :customerId;
```

대신 신용실적 애플리케이션의 공개 조회 API를 사용한다.

### 6.3 Service 간 연쇄 호출

```text
AService → BService → CService → AService
```

순환 의존, 긴 트랜잭션, 장애 전파와 호출 경로 불투명성이 발생한다. 업무 조합은 Controller 또는 별도의 승인된 오케스트레이터가 담당한다.

### 6.4 DAO 간 호출

DAO가 다른 DAO를 호출하면 데이터 접근 계층에 업무 흐름이 숨는다. 여러 DAO 조합은 Service에서 수행한다.

### 6.5 타 애플리케이션 구현 클래스 의존

```java
// 금지
import bl.credit.internal.CreditServiceImpl;
import bl.credit.dao.CreditDao;
```

외부에는 `api` 패키지의 Client/DTO만 공개한다.

## 7. 패키지 및 모듈 구성

권장 구조:

```text
application-group
├─ application-a
│  ├─ api
│  │  ├─ ApplicationAClient.java
│  │  ├─ ApplicationARequest.java
│  │  └─ ApplicationAResponse.java
│  └─ internal
│     ├─ controller
│     ├─ service
│     ├─ dao
│     └─ mapper
└─ application-b
   ├─ api
   └─ internal
```

규칙:

- 타 애플리케이션은 `api`만 참조할 수 있다.
- `internal`은 동일 애플리케이션 밖으로 공개하지 않는다.
- DAO와 SQL Mapper는 항상 `internal`에 둔다.
- DTO도 내부 DTO와 공개 API DTO를 구분한다.

## 8. 트랜잭션 가이드

### 8.1 같은 기능

Service 메서드를 로컬 트랜잭션 경계로 사용한다.

### 8.2 타 기능

같은 프로세스와 DB를 사용하더라도 트랜잭션 전파 속성을 명시한다.

| 속성 | 사용 기준 |
|---|---|
| `REQUIRED` | 호출자 거래에 함께 성공·실패해야 함 |
| `REQUIRES_NEW` | 독립 커밋이 반드시 필요한 제한적 상황 |
| `readOnly` | 조회 전용 서비스 |

`REQUIRES_NEW`는 외부 거래가 롤백되어도 내부 결과가 남으므로 감사 기록 등 명확한 사례에만 사용한다.

### 8.3 타 애플리케이션 및 그룹

원격 호출을 분산 DB 트랜잭션으로 묶지 않는 것을 기본으로 한다.

```text
호출자 로컬 거래 Commit
  → Transactional Outbox
    → 메시지 발행
      → 피호출자 로컬 거래
```

동기 원격 호출에서는 부분 성공에 대비해 보상 거래와 상태 추적을 구현한다.

## 9. 예외 처리 가이드

### 9.1 계층별 예외

| 계층 | 처리 방식 |
|---|---|
| DAO | DB 예외를 표준 `DataAccessException`으로 변환 |
| Service | 업무 오류와 시스템 오류를 분류하고 업무 오류코드 부여 |
| Controller | 표준 응답 코드·메시지로 변환 |
| 원격 Client | HTTP/메시지 오류를 호출자 표준 예외로 변환 |

### 9.2 외부 노출 금지 정보

- SQL 및 테이블명
- 내부 패키지와 클래스명
- 스택 추적
- DB 연결 정보
- 인증 토큰과 개인정보

응답에는 공개 오류코드, 사용자 메시지, `traceId`만 포함한다.

## 10. 동기·비동기 호출 선택

| 판단 기준 | 동기 호출 | 비동기 호출 |
|---|---|---|
| 즉시 결과 필요 | 적합 | 부적합 |
| 느슨한 결합 | 낮음 | 높음 |
| 장애 격리 | 낮음 | 높음 |
| 사용자 응답 경로 | 포함 | 분리 |
| 재처리 | 호출자 재시도 | 소비자 재처리/DLQ |
| 대표 기술 | HTTP/API Gateway | Kafka/메시지 브로커 |

알림, 통계, 감사, 후속 처리처럼 즉시 결과가 필요하지 않은 작업은 비동기를 우선 검토한다.

## 11. 성능 및 안정성 기준

- 동기 호출 체인은 원칙적으로 3단계를 넘기지 않는다.
- 모든 원격 호출에 연결·응답 타임아웃을 설정한다.
- 재시도는 멱등한 요청에만 적용한다.
- 동일 요청을 식별할 멱등키를 전달한다.
- 대량 데이터는 온라인 API가 아니라 배치·파일·스트리밍 방식을 검토한다.
- 다건 조회는 N+1 호출이 되지 않도록 벌크 API를 제공한다.
- 호출 대상별 TPS, 오류율, p95/p99 지연시간을 수집한다.

---

## 12. 보안 가이드

- 호출자는 서비스 계정 또는 토큰으로 인증한다.
- 피호출 Service에서 업무 객체 수준 권한을 다시 검증한다.
- DB 계정에는 소유 스키마에 필요한 최소 권한만 부여한다.
- 타 업무 테이블에 대한 직접 권한을 부여하지 않는다.
- 요청·응답 DTO에 허용 필드 목록을 적용한다.
- 로그의 개인정보·계좌번호·인증정보를 마스킹한다.
- 호출 주체, 대상 서비스, 결과를 감사 로그로 남긴다.

## 13. 정적 분석 규칙

다음 규칙을 ArchUnit 또는 사내 정적 분석 도구로 자동 검증한다.

```text
1. controller 패키지는 dao 패키지를 참조할 수 없다.
2. service 패키지는 controller 패키지를 참조할 수 없다.
3. dao 패키지는 controller/service/다른 dao를 참조할 수 없다.
4. 애플리케이션 외부에서는 internal 패키지를 참조할 수 없다.
5. 애플리케이션 간 순환 의존은 허용하지 않는다.
6. 외부 API DTO는 DB Entity를 참조할 수 없다.
```

ArchUnit 개념 예시:

```java
noClasses()
    .that().resideInAPackage("..controller..")
    .should().dependOnClassesThat()
    .resideInAPackage("..dao..");
```

## 14. 코드 리뷰 체크리스트

### 호출 구조

- [ ] Controller → Service → DAO 순서를 지켰는가?
- [ ] Controller가 DAO를 직접 호출하지 않는가?
- [ ] Service와 DAO가 다른 기능을 직접 호출하지 않는가?
- [ ] 타 업무 테이블을 직접 조회·갱신하지 않는가?
- [ ] 타 애플리케이션의 공개 API 계약만 참조하는가?
- [ ] 순환 의존 또는 과도한 연쇄 호출이 없는가?

### 계약

- [ ] 공개 DTO와 내부 엔티티가 분리되어 있는가?
- [ ] API 버전과 하위 호환성을 고려했는가?
- [ ] 오류코드와 `traceId` 전달 규칙을 지켰는가?
- [ ] 벌크 호출이 필요한 곳에서 N+1 호출을 만들지 않았는가?

### 트랜잭션과 장애

- [ ] Service의 트랜잭션 경계가 명확한가?
- [ ] 원격 호출을 로컬 트랜잭션으로 묶지 않았는가?
- [ ] 타임아웃·재시도·Circuit Breaker가 정의되어 있는가?
- [ ] 재시도 요청이 멱등한가?
- [ ] 부분 실패 시 보상 또는 재처리 방안이 있는가?

### 보안과 운영

- [ ] 서비스 인증과 업무 권한 검증이 있는가?
- [ ] 민감정보가 로그나 오류 응답에 노출되지 않는가?
- [ ] 호출 지연·오류율·결과를 관측할 수 있는가?
- [ ] 데이터 소유팀과 API 소유팀이 명확한가?

---

## 15. 예외 승인 절차

표준 호출 구조를 지킬 수 없는 경우 임의 구현하지 않고 아키텍처 검토를 요청한다.

예외 요청에는 다음을 포함한다.

1. 필요한 호출과 현재 금지 규칙
2. 표준 방식으로 해결할 수 없는 이유
3. 데이터 및 트랜잭션 영향
4. 보안·성능·장애 전파 영향
5. 대안 비교
6. 적용 기간과 제거 계획
7. 소유팀과 승인자

예외는 영구 규칙 변경이 아니라 만료일이 있는 기술 부채로 관리한다.

## 16. 빠른 판단표

| 하고 싶은 작업 | 올바른 호출 방식 |
|---|---|
| 내 기능 데이터를 처리 | Controller → 내 Service → 내 DAO |
| 같은 앱의 다른 기능 사용 | Controller → 타 기능 공개 Service |
| 공통 코드·기준일 사용 | Controller → Utility Service |
| 다른 애플리케이션 업무 사용 | Controller → 상대 공개 API/Controller |
| 다른 그룹·시스템 연계 | API Gateway 또는 메시지 계약 |
| 다른 업무 데이터 조회 | 해당 업무 공개 조회 API 호출 |
| 여러 업무 결과 조합 | Controller/승인된 Orchestrator에서 조합 |
| 비동기 후속 처리 | Outbox → 메시지 브로커 → 소비자 |

## 17. 최종 요약

```text
내부는 계층으로 보호한다.
기능 경계는 Service 계약으로 보호한다.
애플리케이션 경계는 공개 API로 보호한다.
그룹 경계는 표준 연계 채널로 보호한다.
데이터는 소유 업무를 통해서만 접근한다.
```

이 가이드의 목적은 호출을 제한하는 데 그치지 않는다. 업무의 책임과 데이터 소유권을 분명히 하여 한 영역의 변경이 다른 영역으로 무분별하게 확산되지 않게 하고, 장애·보안·트랜잭션 문제를 경계 안에서 통제하는 데 있다.
