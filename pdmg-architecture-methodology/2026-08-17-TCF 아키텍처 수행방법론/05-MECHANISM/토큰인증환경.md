네. 올려주신 **「SSO 기반 JWT 인증/인가 시스템 구현 가이드(KMS 기동 시 로드 방식)」 6장 자료**를 기준으로 보면, 이 설계는 단순 JWT 로그인이라기보다 **SSO 인증 + KMS 키관리 + JWT Access/Refresh Token + Spring Security + pdmk-ui 토큰 갱신**을 결합한 구조입니다.

## 1. 전체 인증 구조

사진의 내용을 하나의 흐름으로 합치면 다음과 같습니다.

```text
┌──────────────────────┐
│       사용자          │
└──────────┬───────────┘
           │
           │ ① SSO Login
           ▼
┌──────────────────────┐
│     SSO / IdP         │
│                      │
│ SSO 인증 완료         │
└──────────┬───────────┘
           │ callback
           ▼
┌─────────────────────────────────────────────┐
│              pdmk-jwt                       │
│                                             │
│ ② SSO Callback                             │
│                                             │
│ ③ KMS Private Key                          │
│    └─ 애플리케이션 기동 시 1회 로드         │
│                                             │
│ ④ JWT 발급                                 │
│    ├─ Access Token                          │
│    └─ Refresh Token                         │
│                                             │
│ ⑤ Refresh Token 저장                       │
│    └─ Repository / DB                       │
└──────────┬──────────────────────────────────┘
           │
           │ Access + Refresh
           ▼
┌──────────────────────┐
│       pdmk-ui         │
│                      │
│ Access Token 사용    │
│ Refresh Token 관리   │
└──────────┬───────────┘
           │
           │ Authorization:
           │ Bearer <Access Token>
           ▼
┌─────────────────────────────────────────────┐
│       Spring Security / Backend             │
│                                             │
│ Access Token 검증                           │
│ Signature / exp / claim                     │
│                                             │
│ 정상 → 업무 서비스                         │
│ 만료 → 401                                 │
└─────────────────────────────────────────────┘
           ▲
           │
           │ Access Token 만료 시
           │ /api/jwt/refresh
           │
┌──────────┴───────────┐
│       pdmk-ui         │
│ Refresh → 재발급      │
└──────────────────────┘
```

이 구조에서 가장 중요한 것은 **SSO와 JWT의 역할이 다르다**는 것입니다.

| 구성요소        | 책임                                      |
| --------------- | ----------------------------------------- |
| SSO/IdP         | 최초 사용자 인증                          |
| `pdmk-jwt`      | SSO 인증결과를 받아 JWT 발급              |
| KMS             | JWT 서명키 관리                           |
| Private Key     | JWT 서명                                  |
| Public Key      | JWT 서명 검증                             |
| Access Token    | 업무 API 접근 인증                        |
| Refresh Token   | Access Token 재발급                       |
| Spring Security | API 요청의 Access Token 검증              |
| `pdmk-ui`       | Access Token 사용 및 만료 시 Refresh 수행 |

# 2. 사진의 인증 Flow를 단계별로 해석

첫 번째 사진에 인증 흐름이 상당히 명확하게 정의되어 있습니다.

### T0 — SSO 로그인

```text
사용자
 ↓
SSO 로그인
 ↓
IdP 인증
```

이 단계에서는 아직 JWT 자체가 핵심이 아닙니다.

**사용자가 누구인가를 SSO가 확인**합니다.

---

### T1 — SSO Callback

SSO 인증 성공 후:

```text
GET /callback?code=xxx
```

형태로 `pdmk-jwt` 쪽으로 돌아옵니다.

즉:

```text
SSO
 ↓
Authorization Code
 ↓
pdmk-jwt
```

입니다.

여기에서 Authorization Code 검증/교환이 반드시 들어가야 합니다.

# 3. 가장 중요한 부분 — KMS Key Loading

두 번째 사진의 핵심입니다.

자료에는 애플리케이션 시작 시:

```text
@PostConstruct
    ↓
KMS API
    ↓
Key 조회
    ↓
Private Key / Public Key
    ↓
메모리에 보관
```

하는 구조가 제시되어 있습니다.

즉 요청이 올 때마다:

```text
JWT 발급
 ↓
KMS 호출
 ↓
Private Key 획득
 ↓
서명
```

하는 방식이 아닙니다.

### 설계 의도

```text
Application Startup
       │
       ▼
   KMS 호출
       │
       ▼
Private/Public Key Load
       │
       ▼
Memory Cache
       │
       ├──────────────┐
       ▼              ▼
 JWT Issue         JWT Verify
```

따라서 **KMS 장애가 매 거래의 JWT 발급 장애로 직접 전파되는 것을 줄일 수 있다는 장점**이 있습니다.

다만 이 부분은 보안 측면에서 추가 검토가 필요합니다.

**Private Key를 애플리케이션 메모리에 로드하는 방식은 가능하지만, KMS의 핵심 장점인 “Private Key 비반출” 모델보다 보안 수준이 낮아질 수 있습니다.**

가능하다면 TO-BE는:

```text
JWT Payload
    ↓
Hash
    ↓
KMS Sign API
    ↓
Signature
    ↓
JWT
```

처럼 **Private Key 자체를 AP로 가져오지 않고 KMS 내부에서 서명**하는 모델도 비교 검토하는 것이 좋습니다.

# 4. JWT 발급 구조

자료의 `JwtKeyPairUtil` 형태를 보면 개념적으로:

```java
private final RSAPrivateKey privateKey;
private final RSAPublicKey publicKey;
```

를 가지고 JWT를 생성합니다.

흐름은:

```text
SSO 인증 성공
      ↓
사용자 정보 확인
      ↓
JWT Claim 구성
      ↓
Private Key
      ↓
RS256 Sign
      ↓
Access Token
      +
Refresh Token
```

입니다.

여기서 **Private Key는 발급 서버만 보유**해야 합니다.

```text
                    Private Key
                         │
                         ▼
                   pdmk-jwt
                         │
                         ▼
                     JWT 서명
                         │
                         ▼
                    Access Token
                         │
           ┌─────────────┴─────────────┐
           ▼                           ▼
      Backend #1                  Backend #2
      Public Key                  Public Key
           │                           │
           └──────── JWT 검증 ─────────┘
```

이것이 RSA JWT의 핵심입니다.

# 5. Access Token과 Refresh Token

사진에서는 두 토큰을 명확히 분리하고 있습니다.

### Access Token

용도:

```text
업무 API 호출 인증
```

예:

```http
Authorization: Bearer <access-token>
```

특징:

- 짧은 만료시간
- API 요청마다 사용
- 서버에서 서명 검증
- 만료되면 `401`

### Refresh Token

용도:

```text
새 Access Token 발급
```

흐름:

```text
Access Token 만료
        ↓
      HTTP 401
        ↓
pdmk-ui Interceptor
        ↓
POST /api/jwt/refresh
        ↓
Refresh Token 검증
        ↓
새 Access Token
        ↓
기존 요청 Retry
```

이 부분은 사진 5의 `pdmk-ui` 처리와 연결됩니다.

---

# 6. Refresh Token Repository

자료에서 좋은 점은 Refresh Token을 완전히 Stateless하게 취급하지 않고 **Repository에서 관리**하려는 것입니다.

개념적으로:

```text
Refresh Token
      ↓
RefreshTokenRepository
      ↓
DB

user_id
token_hash
expires_at
created_at
revoked
```

정도로 관리할 수 있습니다.

이렇게 하면:

```text
로그아웃
   ↓
Refresh Token revoke

관리자 강제 로그아웃
   ↓
Refresh Token revoke

Refresh Token 탈취 의심
   ↓
Token revoke
```

가 가능합니다.

PDMG의 기존 Reference Security Model도 JWT Security를 별도 Security Plane으로 보고 `JwtTokenIssuer → Private Key → RS256 JWT`, `JwtTokenStore → Refresh/Revoke`, `JWKSetController → Public Key/JWKS` 구조로 분리하고 있습니다.

# 7. Spring Security 검증 구조

사진 4에서 중요한 부분입니다.

업무 API 요청이 들어오면:

```text
Client
  │
  │ Authorization: Bearer JWT
  ▼
Spring Security
  │
  ▼
JWT Authentication Filter
  │
  ├─ Token 존재?
  ├─ Signature 정상?
  ├─ exp 정상?
  ├─ issuer 정상?
  ├─ audience 정상?
  └─ 필요한 Claim 정상?
       │
       ▼
SecurityContext
       │
       ▼
Controller
       ↓
Service
```

이 구조가 되어야 합니다.

즉 JWT 검증을 Controller마다:

```java
if(token...)
```

식으로 구현하면 안 됩니다.

**Spring Security Filter Chain에서 공통 처리**하는 것이 맞습니다.

# 8. pdmk-ui의 401 처리

사진 5의 UI 구조도 중요한 부분입니다.

정상 요청:

```text
UI
 ↓
HTTP API
 ↓
Access Token
 ↓
200 OK
```

Access Token 만료:

```text
UI
 ↓
API
 ↓
401
 ↓
Interceptor
 ↓
Refresh API
 ↓
새 Access Token
 ↓
원 요청 Retry
```

그런데 여기에는 반드시 **동시 Refresh 제어**를 넣는 것이 좋습니다.

예를 들어 화면에서 동시에 10개 API가 호출된 상태에서 Access Token이 만료되면:

```text
API 1 → 401
API 2 → 401
API 3 → 401
...
API 10 → 401
```

10개 요청이 각각 Refresh를 수행하면 안 됩니다.

권장 구조는:

```text
          401
           │
     Refresh 진행중?
       /       \
     NO         YES
     │           │
Refresh 1회    Queue 대기
     │           │
     └─────┬─────┘
           ▼
    New Access Token
           │
           ▼
      요청 일괄 Retry
```

입니다.

# 9. 사진 자료에서 특히 보완해야 할 부분

현재 설계의 방향은 맞지만 운영 아키텍처 관점에서는 아래 항목을 추가 확정해야 합니다.

| 항목               | 현재 자료            | 권장                            |
| ------------------ | -------------------- | ------------------------------- |
| SSO                | 있음                 | 유지                            |
| Authorization Code | 있음                 | PKCE/state/nonce 검토           |
| Access Token       | 있음                 | 짧은 TTL                        |
| Refresh Token      | 있음                 | DB에는 원문보다 Hash 저장 권장  |
| RSA Private Key    | KMS에서 기동 시 로드 | **KMS Sign 방식 비교 검토**     |
| Public Key         | 사용                 | JWKS 기반 배포 권장             |
| `kid`              | 명확하지 않음        | **필수 권장**                   |
| Key Rotation       | 부족                 | **추가 필요**                   |
| Refresh Rotation   | 부족                 | **추가 권장**                   |
| Refresh Revoke     | Repository 구조      | 명시적으로 구현                 |
| 401 Refresh        | 있음                 | 동시 Refresh Lock 필요          |
| Retry              | 있음                 | 원 요청 1회만 Retry             |
| 로그아웃           | `/api/jwt/logout`    | Refresh revoke 포함             |
| HTTPS              | 적용                 | 필수                            |
| XSS                | 언급                 | Access/Refresh 저장 위치 재검토 |
| CSRF               | 언급                 | Cookie 사용 방식과 연계 검토    |
| 감사로그           | 부족                 | 로그인/발급/Refresh/Revoke 기록 |

특히 **Key Rotation**이 중요합니다.

```text
KMS
 ├─ Key v1 → kid=key-2026-01
 └─ Key v2 → kid=key-2026-02
                 │
                 ▼
             JWT Header
        {
          "alg": "RS256",
          "kid": "key-2026-02"
        }
```

검증 서버는 `kid`를 보고 적절한 Public Key를 선택해야 합니다.

# 10. NSIGHT/PDMG 구조에 대입하면

기존 PDMG 구조에서는 Framework 계층의 `ServicePreventionInterceptor`가 JWT, User, ServiceId 등 시스템 공통정보를 확인하는 위치로 정의되어 있습니다.

따라서 이번 자료를 NSIGHT/PDMG 구조와 합치면 다음과 같이 정리하는 것이 좋습니다.

```text
                       [ SSO / IdP ]
                            │
                            ▼
                     Authorization Code
                            │
                            ▼
┌──────────────────────────────────────────────────┐
│                   JWT SERVICE                    │
│                                                  │
│ SSO Callback                                     │
│      ↓                                           │
│ User Authentication                              │
│      ↓                                           │
│ JWT Token Issuer                                 │
│      │                                           │
│      ├─ KMS / Private Key                        │
│      ├─ Access Token                             │
│      └─ Refresh Token → Token Repository         │
└────────────────────────┬─────────────────────────┘
                         │
                         ▼
                      pdmg-ui
                         │
                Authorization Bearer
                         │
                         ▼
════════════════════════════════════════════════════
                  PDMG SYSTEM LAYER
════════════════════════════════════════════════════
                         │
                    DefaultFilter
                         │
                         ▼
              JWT Authentication Filter
                         │
                         ├─ signature
                         ├─ exp
                         ├─ iss
                         ├─ aud
                         └─ claims
                         │
                         ▼
              ServicePreventionInterceptor
                         │
                         ├─ User Context
                         ├─ ServiceId
                         ├─ GUID
                         └─ 권한/거래 공통정보
                         │
                         ▼
════════════════════════════════════════════════════
                        TCF
════════════════════════════════════════════════════

              OnlineTransactionController
                         ↓
                     TcfFacade
                         ↓
                       STF
                         ↓
                 Timeout Executor
                         ↓
                    Dispatcher
                         ↓
                      Handler
                         ↓
                      Facade
                         ↓
                      Service
```

여기서 **JWT 인증과 TCF 거래통제를 분리**해야 합니다.

`JWT = 사용자가 누구인가/유효한가`이고, `STF/거래통제 = 이 사용자가 이 ServiceId 거래를 지금 실행할 수 있는가`입니다. PDMG의 기존 Validation 구조 역시 System 계층에서 JWT/User/ServiceId를 확인한 뒤 TCF/STF에서 거래통제를 수행하도록 책임을 분리합니다.

## 최종 평가

이 자료의 전체 설계는 **방향상 적절합니다.** 특히 `SSO → JWT 발급 → Access/Refresh 분리 → Refresh Repository → Spring Security 검증 → UI 401 Refresh`라는 큰 골격은 좋습니다.

다만 NSIGHT의 최종 인증 아키텍처로 확정하기 전에 **① KMS Private Key 반출 여부, ② `kid`/JWKS/Key Rotation, ③ Refresh Token Rotation·Revoke, ④ UI Token 저장 위치, ⑤ 동시 401 Refresh 제어, ⑥ JWT 인증과 ServiceId 권한/거래통제의 책임 분리**를 반드시 설계서에 추가하는 것이 좋습니다.

특히 저는 **`SSO 인증 → JWT 발급 → JWT 검증 → ServiceId 권한검증 → STF 거래통제 → 업무실행 → Refresh/Revoke → 감사로그`까지를 하나의 “NSIGHT 인증·인가 표준 아키텍처”로 묶는 것**을 권장합니다. 이렇게 해야 현재 사진의 JWT 설계가 기존 TCF 아키텍처와 정확히 연결됩니다.
