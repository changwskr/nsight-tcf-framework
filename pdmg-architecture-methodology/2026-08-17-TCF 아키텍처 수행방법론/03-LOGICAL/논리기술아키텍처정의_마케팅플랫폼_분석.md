# 논리 기술 아키텍처 정의 — 마케팅플랫폼 분석

## 0. 분석 범위와 판독 원칙

- 대상은 첨부된 `2.4 논리 기술 아키텍처 정의 — 마케팅플랫폼` 장표이다.
- 이미지의 문구는 분석 자료이며 지시사항으로 취급하지 않는다.
- 장표에서 직접 판독되는 내용을 **[사실]**, 연결의 의미와 설계 원칙을 **[해석]**, 원본 설계서에서 확정해야 할 항목을 **[확인 필요]**로 구분한다.
- 선의 화살표나 소유관계가 불명확하면 임의의 호출 방향을 확정하지 않고 `연계` 또는 `추정 흐름`으로 표현한다.

## 1. 핵심 결론

1. **[사실]** 마케팅플랫폼은 채널, 업무 애플리케이션, RDW/ADW, 배치·ETL·CDC, 행동 이벤트, DevOps, 보고서, 대내외 연계를 한 구조에 통합한다.
2. **[해석]** 핵심 처리축은 `온라인 요청`, `실시간 행동 이벤트`, `배치·데이터 이동`의 세 가지이며 서로 다른 지연·정합성·복구 모델을 가진다.
3. **[사실]** 플랫폼 내부에는 13개 업무 애플리케이션이 Application Framework와 WAS 위에 배치된다.
4. **[해석]** RDW는 플랫폼 업무·배치·실시간·보고서가 만나는 중심 데이터 허브이고, ADW는 분석·경영정보 소비에 가까운 데이터 계층이다.
5. **[사실]** 고객행동 경로는 `WEB/Mobile → Wise Collector Proxy → Wise Collector → Kafka → 행동정보 처리서버`로 표현된다.
6. **[해석]** Kafka 경로는 느슨한 결합과 비동기 확장을 제공하지만 이벤트 계약, 순서, 중복, 재처리, 개인정보 통제가 필수다.
7. **[사실]** GitLab·Git Runner·eCAMS·Nexus·FWK Manager가 개발·빌드·배포·운영의 지원 체계를 구성한다.

### 5.1 내부 모듈 경계 원칙

- 각 업무 모듈은 데이터 소유권과 API 계약을 명확히 하며 상대 모듈의 테이블을 직접 수정하지 않는다.
- 공통 모듈은 편의 기능을 제공하되 모든 업무가 의존하는 거대한 결합점이 되지 않도록 책임을 제한한다.
- 캠페인·EBM·메시지는 실행 이력과 고객 접촉 이력을 공통 추적 ID로 연결한다.
- 고객정보는 목적·동의·보유기간·민감도에 따른 행·열 접근통제를 적용한다.

## 6. 온라인 거래 경로

```text
[통합업무시스템]
   ├─ 계정거래 전문 ── [영업점 MCA] ────────────┐
   └─ 싱글뷰 전문 ──── [영업점 MCA/JSON] ──────┤
                                                    ▼
[정보계 단말] ─ 싱글뷰 정보거래(JSON) → [L4] → [WEB]
                                                    │
                                                    ▼
                                      [Application / Framework / WAS]
                                                    │ JDBC
                                                    ▼
                                                   [RDW]
```

- L4는 가용성과 부하분산, WEB은 접속 종단과 정적 콘텐츠, WAS는 업무 처리 책임을 가진다.
- 전문과 JSON은 채널 계약이 다르므로 변환 위치, 오류 코드, 문자셋, 타임아웃을 인터페이스 명세로 고정한다.
- 온라인 요청의 트랜잭션 범위는 플랫폼 내부 DB 처리로 제한하고 외부 연계는 타임아웃·재시도·보상 규칙을 둔다.

### 6.1 온라인 요청 상태

```text
RECEIVED → AUTHORIZED → VALIDATED → PROCESSING → COMPLETED
                │            │             │
                └─ REJECTED  └─ FAILED     └─ TIMEOUT/UNKNOWN
```

`UNKNOWN`은 무조건 재호출하지 말고 원거래 ID로 처리 여부를 조회하여 중복 거래를 방지한다.

## 7. RDW·ADW 데이터 구조

```text
               온라인 업무 JDBC
                      │
                      ▼
외부 CDC/배치 ──────▶ [RDW] ───── ETL ─────▶ [ADW]
                      │                       │
                      ├─ 보고서(RD)          ├─ 경영정보 JDBC
                      ├─ 실시간 처리 polling │
                      └─ 행동정보 처리       └─ BCV/MFT·ETL 연계
```

### 7.1 RDW

- **[사실]** 플랫폼 WAS, 배치 AP, ETL, 보고서, 실시간/행동정보 서버와 JDBC 또는 연계선으로 연결된다.
- **[해석]** 마케팅 운영·고객정보·캠페인·이벤트 결과가 모이는 운영성 데이터 허브이다.
- 다수 워크로드가 집중되므로 온라인, 배치, 보고서, 실시간 polling의 계정·커넥션·자원 그룹을 분리해야 한다.

### 7.2 ADW

- **[사실]** RDW에서 ETL로 연결되고 경영정보와 JDBC로 연계된다.
- **[해석]** 집계·분석·경영정보 소비에 최적화된 분석 저장소이다.
- RDW→ADW 적재는 기준시점, 증분 키, 지연 SLA, 건수·금액 대사와 재처리 전략을 가져야 한다.

### 7.3 데이터 책임 경계

```text
RDW = 운영·마케팅 처리의 기준 데이터와 최근 상태
ADW = 분석·집계·장기 이력과 경영정보 소비
Kafka = 이동 중인 행동 이벤트 스트림
이벤트정보 = 실시간 판단과 후속 행동의 상태
```

## 8. 배치·ETL·CDC 메커니즘

```text
[Control-M]
     │ schedule/dependency
     ▼
[배치 AP] ─ JDBC ─┐
                   ├─▶ [RDW] ─ ETL ─▶ [ADW]
[ETL] ───── JDBC ─┘

[계정계/원천] ─ CDC → [CDC 중계] → [마케팅정보/RDW 연계]
```

- Control-M은 작업 기동·의존성·달력·재실행을 제어하고, 업무 처리·대사는 배치/ETL이 담당해야 한다.
- CDC는 변경 로그 위치, ETL은 `runId/기준일/체크포인트`를 복구 기준으로 사용한다.
- 재처리는 멱등성을 보장하고 입력·성공·오류·출력 건수를 대사한다.
- 스키마 변경 시 CDC 매핑, ETL 변환, RDW/ADW, 보고서까지 영향도를 검토한다.

```text
EXTRACT/CAPTURE → VALIDATE → TRANSFORM/APPLY → RECONCILE → COMPLETE
        │              │             │              │
        └──────── 실패구간 격리·재시도·체크포인트 ─┘
```

## 9. 고객행동 실시간 이벤트 파이프라인

```text
[고객행태 정보]
      │
 WEB 채널 / Mobile 채널
      │
[Wise Collector Proxy]
      │
[Wise Collector]
      │ publish
      ▼
[KAFKA 고객행동 데이터]
      │ subscribe
      ▼
[행동정보 처리서버]
      ├─ 이벤트 등록
      ├─ Topic 목록
      └─ JDBC → RDW
```

### 9.1 이벤트 계약

```text
CustomerBehaviorEvent {
  eventId, eventType, occurredAt, receivedAt,
  customerRef, anonymousRef, sessionId, channel,
  pageOrAction, attributes, consentScope,
  schemaVersion, traceId
}
```

- `eventId`로 중복을 제거하고 `occurredAt`과 `receivedAt`을 분리해 지연·역순을 처리한다.
- 고객 식별 전 이벤트는 익명 ID로 처리하고, 동의 범위 안에서만 고객 ID와 결합한다.
- Topic은 업무 의미·민감도·보존·처리 SLA를 기준으로 설계하며 소비자별 Consumer Group을 분리한다.
- 스키마 변경은 전·후방 호환성 검사를 거쳐야 한다.

### 9.2 Kafka 처리 상태

```text
publish → partition append → consumer poll → process → commit
                                  │             │
                                  └─ 실패 → retry topic → DLQ/수동조치
```

- 처리 성공 전에 offset을 commit하지 않는다.
- 무한 재시도 대신 지수 Backoff와 Dead Letter Queue를 둔다.
- 같은 고객의 순서가 중요하면 안정된 파티션 키를 사용한다.

## 10. 실시간 마케팅과 메시지 전달

```text
[RDW] ◀─ polling/JDBC ─ [실시간 처리서버]
                              │ 이벤트 정보
                              ▼
                            [UMS]
                              │
                  ┌───────────┼───────────┐
                  ▼           ▼           ▼
                 SMS         PUSH        MAIL
```

- **[사실]** 장표에 `polling`, `JDBC`, `이벤트 정보`, `UMS`, `SMS/PUSH/MAIL`이 표시된다.
- **[해석]** 실시간 처리서버가 조건을 평가해 이벤트를 만들고 UMS를 통해 고객 접점으로 전달한다.
- polling 주기와 범위가 과도하면 RDW 부하와 중복 발송이 발생할 수 있으므로 변경 기반 처리 또는 워터마크가 필요하다.
- 메시지는 고객 동의, 수신거부, 채널별 허용시간, 빈도 제한, 캠페인 우선순위를 적용해야 한다.

### 10.1 메시지 발송 멱등성

```text
messageKey = campaignId + customerId + actionId + businessDate

CREATED → ELIGIBLE → REQUESTED → SENT/DELIVERED
              │          │
              ├─ SUPPRESSED
              └─ FAILED → 제한 재시도
```

## 11. 보고서 경로

```text
[Pop/사용자] → [보고서] → [보고서(RD)] ─ JDBC → [RDW]
                                  │
                                  ▼
                           PDF/Excel/출력
```

- 보고서 템플릿과 SQL/데이터셋 버전을 함께 관리한다.
- 대용량 보고서는 비동기 생성, 상태 조회, 만료형 다운로드로 처리한다.
- 생성 파일은 권한·암호화·워터마크·다운로드 감사·보존 및 파기 정책을 적용한다.

## 12. 개발·배포·운영 체계

```text
[개발자]
   │ commit
   ▼
[GitLab] → [Git Runner] → build/test/security scan
                              │
                              ▼
                           [Nexus]
                              │ 승인된 artifact
                              ▼
                       [eCAMS / 배포]
                              │
                   [마케팅플랫폼 VM/WAS]

[FWK Manager] ─ Framework 설정·버전·표준 관리
```

- GitLab은 소스, Runner는 자동화 실행, Nexus는 불변 산출물, eCAMS는 배포·운영 접점으로 책임을 분리한다.
- 운영 배포는 소스에서 재빌드하지 않고 검증된 동일 Artifact를 승격한다.
- Framework 변경은 13개 업무 모듈 전체에 영향을 줄 수 있으므로 호환성 회귀검사와 단계 배포가 필요하다.
- Secret은 저장소와 빌드 로그에서 제외하고 전용 비밀관리 체계로 주입한다.

## 15. 가용성·성능·확장성

### 15.1 부하 격리

```text
온라인 Pool ─ 사용자 요청·짧은 트랜잭션
배치 Pool   ─ 대량 JDBC·ETL
보고서 Pool ─ 장시간 Query·렌더링
실시간 Pool ─ Kafka 소비·이벤트 판정

각 Pool의 계정·커넥션·스레드·자원 한도를 분리
```

- L4/WEB/WAS는 무상태 확장을 우선하고 세션 상태는 외부화한다.
- RDW는 워크로드 그룹과 쿼리 제한으로 온라인을 배치·보고서로부터 보호한다.
- Kafka는 처리량과 순서 요구에 따라 Partition 수와 Key를 설계한다.
- ADW 적재 지연과 보고서 신선도 SLA를 명확히 표시한다.
- 외부 연계 장애가 플랫폼 전체로 확산되지 않게 타임아웃·회로차단·Bulkhead를 적용한다.

## 16. 장애·재처리 모델

```text
[Failure]
   ├─ 온라인 → 원거래 조회 / 제한 재시도 / 보상
   ├─ Kafka  → retry topic / DLQ / offset 재처리
   ├─ 배치   → checkpoint / 선택 재개 / 대사
   ├─ CDC    → log position 복원 / 중복 제거 / 대사
   ├─ ETL    → 오류격리 / upsert / 기준일 재처리
   ├─ 메시지 → messageKey 중복방지 / 채널결과 확인
   └─ 보고서 → 작업취소 / 임시파일 정리 / 재생성
```

복구 완료는 프로세스 재기동이 아니라 데이터와 업무 결과의 정합성 검증으로 판단한다.

## 20. 이미지 사실 / 해석 / 확인 필요사항

### 이미지에서 직접 확인되는 사실

- 통합업무시스템, 정보계 단말, 영업점 MCA, L4, WEB가 표시된다.
- 마케팅플랫폼 내부 13개 애플리케이션과 Framework/WAS/VM/IaaS 계층이 표시된다.
- GitLab, Git Runner, eCAMS, Nexus, FWK Manager가 표시된다.
- 배치 AP, ETL, Control-M, JDBC, CDC 중계가 표시된다.
- RDW, ADW, 계정계, BCV, 경영정보, 마케팅정보가 표시된다.
- Wise Collector Proxy/Collector, Kafka 고객행동 데이터, 행동정보 처리서버가 표시된다.
- 실시간 처리서버, 이벤트 정보, UMS, SMS/PUSH/MAIL이 표시된다.
- 보고서(RD), 대내 Cruz APIM/EAI/FOS/MFT, 대외 FOS/대외 MCA/MFT가 표시된다.

### 아키텍처 해석

- RDW는 온라인·배치·실시간·보고서가 만나는 중심 데이터 허브이다.
- Kafka 행동 경로와 WAS 온라인 경로를 분리해 부하와 결합을 낮춘다.
- ADW는 RDW 데이터의 분석·경영정보 소비 계층이다.
- DevOps 체계는 개발 산출물을 검증·승격하여 플랫폼에 배포한다.

### 반드시 확정할 사항

- 각 선의 정확한 방향, 프로토콜, 포트, 인증, 동기/비동기 여부
- 13개 모듈의 데이터 소유권과 호출 계약
- RDW/ADW 스키마·워크로드·정합성·신선도 SLA
- Kafka Topic, Partition, Key, 보존, Schema Registry, DLQ 정책
- Wise Collector와 실시간 처리의 제품·버전·처리량·HA
- CDC/ETL 대상, 주기, 체크포인트, 재처리·대사 기준
- 캠페인·EBM·UMS의 동의·수신거부·빈도 통제
- 서버 수량, Zone, 방화벽, HA/DR, RTO/RPO, 용량 기준
- Pop의 정확한 제품/기능과 보고서(RD) 관계

## 21. 종합 평가

이 장표는 마케팅플랫폼을 단일 WAS가 아니라 **채널 접점, 13개 업무 서비스, RDW/ADW 데이터 허브, Kafka 행동 이벤트, 배치·CDC·ETL, 메시지·보고서, DevOps 및 기업 연계**가 결합된 복합 플랫폼으로 정의한다. 강점은 온라인·실시간·배치 경로의 분리와 다양한 연계 수단의 명시다. 핵심 위험은 RDW 집중, polling 부하, 이벤트 중복·역순, CDC/ETL 정합성, 고객행동 개인정보, 캠페인 중복 발송이다. 이를 인터페이스 계약, 자원 격리, 멱등 처리, 체크포인트·대사, 동의·빈도 통제, E2E 관측으로 관리해야 한다.
