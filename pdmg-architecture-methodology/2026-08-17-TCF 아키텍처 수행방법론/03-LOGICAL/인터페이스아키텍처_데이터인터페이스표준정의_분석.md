# 인터페이스 아키텍처 — 데이터 인터페이스 표준 정의 분석

## 1. 핵심 결론

장표는 데이터 인터페이스를 처리 시급성과 원천 특성에 따라 두 방식으로 표준화한다.

- **CDC(실시간)**: 코어뱅킹 DB의 변경 데이터를 정보계 DW로 실시간 동기화한다.
- **ETL(배치)**: BCV, RDW, ADW 및 타 시스템 DB 사이의 대량 데이터 추출·변환·적재를 담당한다.

```text
실시간 경로
코어뱅킹 DB ── CDC(실시간) ──> 정보계 DW

배치 경로
코어뱅킹 DB BCV ── ETL ──> 정보계 DW
RDW              ── ETL ──> ADW
DW               ── ETL ──> 타 시스템 DB
타 시스템 DB      ── ETL ──> DW
```

따라서 이 아키텍처의 본질은 단순한 데이터 복사가 아니라 **실시간 변경 전파와 배치 데이터 이동을 분리**하고, 각 경로에 서로 다른 정합성·복구·SLA 기준을 적용하는 데 있다.

## 2. 장표 원문 전사

| No. | 구분 | 소스 | 인터페이스 시스템 | 타깃 | 설명 |
|---:|---|---|---|---|---|
| 1 | 데이터 | 코어뱅킹DB | CDC (실시간) | 정보계 DW | 계정계 데이터 실시간 동기화 인터페이스 |
| 2 | 데이터 | 코어뱅킹DB BCV | ETL | 정보계 DW | 계정계 데이터 동기화 인터페이스 |
| 3 | 데이터 | RDW | ETL | ADW | 정보계 데이터 동기화 인터페이스 |
| 4 | 데이터 | DW | ETL | 타 시스템 DB | 정보계 데이터 동기화 인터페이스 |
| 5 | 데이터 | 타 시스템 DB | ETL | DW | 정보계 데이터 동기화 인터페이스 |

> `정보계 DW`, `DW`, `RDW`가 장표에서 함께 사용된다. 이 문서는 이를 임의로 같은 DB로 단정하지 않는다. 실제 설계에서는 논리 DB명, 물리 서비스명, 스키마 및 소유 시스템을 인터페이스 등록부에서 명확히 매핑해야 한다.

## 4. 경로별 상세 분석

### 4.1 코어뱅킹 DB → CDC(실시간) → 정보계 DW

이 경로는 계정계 트랜잭션의 변경분을 낮은 지연으로 정보계에 전달한다. 원천 업무 트랜잭션에 추가 조회 부하를 주지 않도록 DB 로그 기반 캡처가 적합하다.

주요 처리 단계는 다음과 같다.

1. 원천 DB의 redo 또는 변경 로그에서 커밋 완료 변경을 캡처한다.
2. 트랜잭션 순서와 커밋 경계를 보존한다.
3. 중계 큐나 Trail을 통해 변경 이벤트를 전달한다.
4. 정보계 DW의 대상 테이블에 Insert·Update·Delete를 반영한다.
5. 체크포인트를 저장하여 장애 후 마지막 정상 지점부터 재개한다.

핵심 통제 항목은 캡처 지연, 적용 지연, 로그 보존, DDL 변경 대응, 재기동 체크포인트, 중복 적용 방지다.

### 4.2 코어뱅킹 DB BCV → ETL → 정보계 DW

BCV는 운영 원본 대신 복제·스냅샷 계열 소스를 사용하여 계정계 DB 부하를 분리하는 경로다. 주로 초기 적재, 대량 보정, 일 마감 데이터 및 CDC 누락 복구에 적합하다.

- 추출 기준 시점을 명시해야 한다.
- BCV 생성 완료와 ETL 시작 사이의 선후 관계가 보장돼야 한다.
- 전체 적재와 증분 적재를 구분해야 한다.
- CDC 경로와 중복되는 데이터의 우선순위 및 정합 시점을 정의해야 한다.

### 4.3 RDW → ETL → ADW

RDW의 운영·통합 데이터를 ADW의 분석 모델로 변환하는 경로다. 단순 복제보다 업무 코드 정규화, 차원·사실 모델 구성, 집계, 이력 관리가 중심이다.

- RDW는 신뢰 가능한 상세·통합 데이터 공급원 역할을 한다.
- ETL은 정제, 표준화, 파생값 계산과 데이터 품질 검사를 수행한다.
- ADW는 분석 및 보고 성능에 맞춘 모델을 제공한다.
- 적재 완료 후 통계정보 갱신과 집계 검증이 필요하다.

### 4.4 DW → ETL → 타 시스템 DB

정보계 데이터를 타 시스템에 제공하는 아웃바운드 경로다. 제공 데이터의 목적 제한과 최소화가 중요하다.

- 제공 대상 테이블·컬럼·조건을 계약으로 고정한다.
- 개인정보와 민감정보는 마스킹·가명처리 또는 제외한다.
- 전체·증분 전달 방식과 기준 시각을 정의한다.
- 타깃 반영 완료 여부를 회신받아 송수신 건수를 대사한다.

### 4.5 타 시스템 DB → ETL → DW

외부 업무 시스템 데이터를 정보계에 수집하는 인바운드 경로다. 원천마다 코드·날짜·키 체계가 다를 수 있으므로 스테이징과 품질 검증이 필수다.

- 원천 데이터를 스테이징 영역에 우선 적재한다.
- 스키마, 타입, 필수값, 참조 무결성을 검사한다.
- 표준 코드 및 기준정보로 변환한다.
- 오류 레코드는 격리하고 정상 건만 본 테이블에 반영한다.

## 5. CDC와 ETL의 책임 경계

| 항목 | CDC(실시간) | ETL(배치) |
|---|---|---|
| 목적 | 변경분의 저지연 전파 | 대량 추출·변환·적재 |
| 입력 | DB 변경 로그 | 테이블, 뷰, BCV, 파일 |
| 처리 단위 | 트랜잭션·변경 이벤트 | 배치·파티션·업무일자 |
| 변환 수준 | 최소 변환 권장 | 복합 정제·집계·모델 변환 |
| 복구 기준 | 로그 위치·체크포인트 | Job·Step·파티션 체크포인트 |
| 정합성 | 순서·커밋 경계·지연 | 건수·금액·해시·업무일자 |
| SLA | 초·분 단위 지연 | 배치 윈도 및 완료 시각 |
| 주요 장애 | 로그 단절, 지연 누적 | Job 실패, 부분 적재, 시간 초과 |

CDC를 복잡한 분석 변환 엔진으로 사용하거나 ETL을 준실시간 반복 실행으로 대체하면 결합도와 운영 복잡도가 커진다. 두 방식의 책임을 명확히 유지해야 한다.

## 6. 표준 데이터 인터페이스 계약

각 연계는 다음 메타데이터를 중앙 인터페이스 등록부에서 관리해야 한다.

| 분류 | 필수 항목 |
|---|---|
| 식별 | Interface ID, 명칭, 업무 도메인, 담당 조직 |
| 경로 | Source 시스템·DB·스키마, Target 시스템·DB·스키마 |
| 방식 | CDC/ETL, Push/Pull, 전체/증분, 단방향/양방향 |
| 데이터 | Source/Target 테이블, 컬럼 매핑, PK·업무키, 코드 매핑 |
| 일정 | 주기, 기준 시각, 업무일자, 선행·후행 Job |
| 품질 | 필수값, 허용 범위, 참조 무결성, 중복 기준 |
| 정합성 | 건수, 합계, 해시, 체크포인트, 허용 오차 |
| 보안 | 계정, 권한, 암호화, 마스킹, 감사 로그, 보존 기간 |
| 운영 | SLA, 재시도, 재처리, 알림, RACI, DR 절차 |

```yaml
interfaceId: DATA-RDW-ADW-001
type: ETL
source:
  system: RDW
  schema: SRC_OWNER
  object: CUSTOMER_TX
target:
  system: ADW
  schema: DW_OWNER
  object: FACT_CUSTOMER_TX
load:
  mode: incremental
  watermarkColumn: UPDATED_AT
  businessKey: [TX_ID]
  schedule: "0 30 2 * * *"
reconciliation:
  checks: [row_count, amount_sum, key_duplicate]
  tolerance: 0
recovery:
  checkpoint: business_date_and_partition
  retryCount: 3
security:
  credentialRef: vault://data-rdw-adw
  maskingPolicy: PII-DEFAULT
```

## 7. 표준 처리 파이프라인

```text
[Source]
   │
   ├─ 추출 시점/로그 위치 확정
   v
[Landing 또는 Staging]
   ├─ 스키마 검사
   ├─ 건수·해시 기록
   ├─ 중복·필수값 검사
   v
[Transform]
   ├─ 표준 코드 변환
   ├─ 개인정보 처리
   ├─ 업무 규칙 적용
   v
[Target Load]
   ├─ 임시 테이블 적재
   ├─ Merge/교체
   ├─ Commit
   v
[Reconciliation]
   ├─ Source ↔ Target 대사
   ├─ 품질 결과 저장
   └─ 완료 이벤트·알림
```

스테이징과 본 적재를 분리하면 검증 실패 데이터가 운영 테이블에 섞이는 것을 막고 재처리 범위를 명확히 할 수 있다.

## 8. 증분 추출과 워터마크

ETL 증분 기준은 다음 우선순위로 선택할 수 있다.

1. 변경 로그 또는 CDC 위치
2. 단조 증가 Sequence/SCN
3. 신뢰할 수 있는 수정 시각
4. 업무일자와 파티션
5. 원천이 제공하는 변경 플래그

수정 시각만 사용하는 경우 동일 타임스탬프, 지연 커밋, 서버 시간 차이로 누락될 수 있다. `(수정 시각, PK)` 복합 워터마크와 겹침 구간 재조회 후 멱등 Merge를 적용하는 것이 안전하다.

## 9. 적재 원자성과 멱등성

부분 적재가 정상 데이터로 노출되지 않도록 다음 패턴을 사용한다.

```text
1. 작업 실행 ID 생성
2. 임시/Staging 테이블에 적재
3. 품질 및 대사 검증
4. 트랜잭션 단위 Merge 또는 파티션 Exchange
5. 성공 체크포인트 갱신
6. 완료 상태 기록
```

멱등 키는 `Interface ID + 업무일자 + Source Key + Version/SCN` 조합으로 관리한다. 동일 실행을 반복해도 결과가 변하지 않아야 안전한 재처리가 가능하다.

## 10. 정합성 및 데이터 품질

### 10.1 기술 정합성

- 원천 추출 건수와 타깃 반영 건수
- Insert·Update·Delete 유형별 건수
- PK 중복 및 Null 건수
- 합계·최솟값·최댓값
- 파티션·업무일자별 해시
- CDC 캡처 위치와 적용 위치

### 10.2 업무 정합성

- 거래 금액 합계와 잔액
- 고객·계좌·상품 기준정보 참조 여부
- 업무일자 및 마감 상태
- 코드 체계와 유효기간
- 삭제·취소·정정 거래 반영 여부

대사 실패는 단순 경고가 아니라 `FAILED_RECONCILIATION` 상태로 분리하고 본 데이터 공개를 중단해야 한다.

## 11. 상태 모델과 체크포인트

```text
REGISTERED
    ↓
EXTRACTING → EXTRACTED → VALIDATING → TRANSFORMING
    ↓                                      ↓
FAILED_EXTRACT                         FAILED_TRANSFORM
                                           ↓
LOADING → LOADED → RECONCILING → COMPLETED
   ↓                       ↓
FAILED_LOAD       FAILED_RECONCILIATION
```

체크포인트에는 실행 ID, 업무일자, 마지막 키/SCN, 추출·반영 건수, 시작·종료 시각, 오류 코드와 재처리 횟수를 기록한다.

## 12. 장애 복구 및 재처리

### CDC

- 마지막 적용 체크포인트부터 재개한다.
- 로그 유실 전에 보존 기간과 최대 중단 시간을 감시한다.
- 장시간 단절 시 BCV/ETL 기반 재동기화 후 CDC를 재연결한다.
- DDL 변경은 사전 등록하고 호환성 검사를 수행한다.

### ETL

- Job 전체가 아니라 실패 Step·파티션 단위로 재처리한다.
- 임시 적재 데이터와 체크포인트를 이용해 중복 반영을 방지한다.
- 수동 SQL 수정은 금지하고 승인된 재처리 Job으로 이력을 남긴다.
- 데이터 보정은 원천 재추출과 타깃 직접 보정을 구분한다.

## 13. 보안 아키텍처

- DB 계정은 인터페이스별 서비스 계정으로 분리한다.
- Source는 필요한 테이블·컬럼의 읽기 권한만 부여한다.
- Target은 지정 스키마와 프로시저에 한정해 쓰기 권한을 부여한다.
- 비밀번호는 코드나 Job 파일에 저장하지 않고 Vault에서 참조한다.
- 전송 구간은 TLS 또는 DB Native Encryption을 적용한다.
- 개인정보는 목적에 따라 제외·마스킹·가명처리한다.
- 조회·추출·다운로드·재처리 행위를 감사 로그로 보존한다.

운영과 개발 환경 사이의 실데이터 직접 복제는 원칙적으로 금지하고, 필요한 경우 비식별화와 승인 절차를 적용한다.

## 14. 성능 및 부하 분산

- CDC 캡처가 원천 DB의 로그 처리와 체크포인트를 방해하지 않도록 용량을 산정한다.
- 대량 추출은 BCV 또는 읽기 전용 복제본을 우선 사용한다.
- ETL은 업무일자·파티션 단위 병렬성을 적용하되 DB 동시성 한도를 준수한다.
- Direct Path, Partition Exchange 등 대량 적재 기법은 복구·감사 요구와 함께 검토한다.
- 통계 갱신과 인덱스 유지 시간을 배치 윈도에 포함한다.
- CDC와 대량 ETL의 네트워크·스토리지 I/O 경합을 분리한다.

## 15. 스키마 변경 관리

Source 컬럼 추가·삭제·타입 변경은 인터페이스 장애를 유발할 수 있다.

```text
변경 요청
  → 영향도 분석
  → Source/Target 매핑 버전 등록
  → 하위 호환성 검사
  → 개발·검증 환경 리허설
  → 배포 순서 승인
  → CDC/ETL 일시 정지 또는 Rolling 반영
  → 대사 후 재개
```

계약에는 `schemaVersion`, 적용일, 호환 가능 버전과 롤백 절차를 포함해야 한다.

## 16. 운영 관측성

### CDC 지표

- Capture Lag, Apply Lag
- 초당 변경 건수 및 적용 건수
- Trail/Queue 사용량
- 마지막 캡처·적용 SCN 또는 시각
- 오류·재시도·중복 건수

### ETL 지표

- Job/Step 상태와 소요 시간
- 추출·변환·적재 처리량
- Source/Target 건수 차이
- 품질 규칙 위반 건수
- 배치 윈도 초과 여부
- 재처리 횟수와 실패 파티션

모든 지표는 `Interface ID`, 실행 ID, 업무일자, Source/Target으로 검색 가능해야 한다.

## 17. 환경 및 DR 기준

- 개발·검증·운영·DR의 엔드포인트와 계정을 분리한다.
- 인터페이스 정의는 동일 형식을 사용하되 환경별 값은 외부 설정으로 관리한다.
- DR 전환 시 CDC 캡처·적용 방향과 중복 실행 방지 Lock을 검증한다.
- ETL 스케줄러는 주센터와 DR센터가 동시에 Job을 기동하지 않도록 한다.
- RPO는 CDC 로그 보존과 적용 지연, RTO는 재연결·재적재 시간으로 검증한다.
- 정기 DR 훈련에서 전환뿐 아니라 원복 후 데이터 대사까지 수행한다.

## 21. 최종 평가

장표의 표준 방향은 명확하다. **실시간 계정계 변경은 CDC**, **대량·변환 중심 데이터 이동은 ETL**로 분리하고, RDW와 ADW 및 타 시스템 간 데이터 흐름을 표준 도구로 통제한다. 이는 원천 부하와 처리 목적을 고려한 합리적인 책임 분리다.

다만 실제 운영 가능한 표준이 되려면 경로 표만으로는 부족하다. DB·스키마 식별, 데이터 계약, 체크포인트, 원자성, 멱등성, 정합성 대사, 스키마 변경, 보안, SLA 및 DR 기준을 함께 적용해야 한다. 특히 장표에 혼재된 `정보계 DW`·`DW`·`RDW`의 관계와 CDC/ETL 중복 공급 구간을 선결 설계 항목으로 관리해야 한다.
