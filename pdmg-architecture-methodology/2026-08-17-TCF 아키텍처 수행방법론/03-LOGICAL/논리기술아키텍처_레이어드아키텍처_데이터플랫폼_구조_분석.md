# 논리기술아키텍처 — 레이어드 아키텍처 — 데이터플랫폼 구조 분석

## 1. 분석 개요

첨부 장표의 **데이터플랫폼 표준 아키텍처 구성**을 기준으로 데이터플랫폼을 다음 4개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer

데이터플랫폼은 Oracle Exadata 기반의 RDW·ADW Appliance와 CDC 중계, ETL 실행·스케줄링 체계를 중심으로 구성된다. RDW는 원천 변경 데이터의 준실시간 수집과 운영성 데이터 제공을, ADW는 분석·요약·집계와 외부 제공을 담당한다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 장표의 `Oracle Exadata 26 ai` 표기는 원문을 따른 것이며, 정확한 제품명·버전·라이선스·노드 수와 실제 연계 프로토콜은 구축 명세에서 재확인해야 한다.

## 2. 핵심 결론

- **RDW와 ADW의 목적 분리**: RDW는 준실시간 SoR·집계·운영지원을, ADW는 대용량 분석·마트·피드백을 담당한다.
- **실시간과 배치 경로 분리**: 계정계 변경은 CDC로 RDW에 반영하고, 대량 변환·적재는 ETL 작업으로 처리한다.
- **스케줄 제어 표준화**: Control-M과 ETL Scheduler가 Job Shell을 통해 배치 실행을 통제한다.
- **Appliance 내부 서비스 노드화**: RDW와 ADW를 Exadata Database의 논리 서비스 노드로 분리해 부하와 장애 영향을 격리한다.
- **연계 방식의 다중화**: CDC, JDBC, ETL, FOS/MFT가 각각 실시간 복제, 온라인 접근, 데이터 변환, 파일 전달을 담당한다.
- **표준 I/F 계층 적용**: SSO·FOS·MFT·ETL·CDC·대외 MCA·통합관제·IT 메타가 업무와 데이터 저장소의 직접 결합을 줄인다.
- **데이터 제품 분리**: RDW의 실시간 SoR/집계/로그와 ADW의 분석 SoR/통합·요약/업무·보고 마트가 목적별로 분리된다.
- **운영 통제 필요**: 재처리, 중복 방지, 정합성 검증, 계보, SLA 및 데이터 품질 통제가 전체 경로에 공통 적용되어야 한다.

## 4. 레이어별 상세 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 통제 대상 |
|---|---|---|
| Control-M | 전사 배치 일정, 선후행, 재기동 및 결과 통제 | ETL·배치 Job |
| ETL Scheduler | ETL 도구 내부 실행계획과 세부 작업 통제 | 추출·변환·적재 흐름 |
| Job Shell | 스케줄러와 DB/ETL 실행체 사이의 표준 실행 진입점 | 환경 설정, 파라미터, 반환코드, 로그 |

이 계층은 일반적인 사용자 UI가 아니라 **운영 제어 접점**이다. 스케줄러가 DB 프로시저나 ETL 엔진을 직접 호출하지 않고 Job Shell을 경유하면 실행환경, 인증, 표준 로그, 오류코드와 재처리 정책을 일관되게 적용할 수 있다.

### 4.2 Service Layer — RDW Appliance

| 구성요소 | 책임 |
|---|---|
| RDW Service Node | 실시간 및 준실시간 데이터 수집·조회 서비스 제공 |
| Oracle Exadata Database | 대량 데이터 저장, 병렬 SQL, RAC 기반 가용성 제공 |
| CDC 수신 경로 | 코어뱅킹·연계뱅킹·카드승인의 변경분 수신 |
| JDBC 경로 | 행동정보처리·실시간처리 서버의 직접 입출력 |
| ETL Job | BCV 및 타 시스템 데이터의 주기 적재, RDW 내부 가공 |

RDW는 원천계의 최신 상태를 빠르게 수용하는 **운영형 데이터 허브**다. 온라인 원장 그 자체라기보다 분석·서비스가 참조할 수 있도록 변경 데이터를 통합한 준실시간 저장소로 해석하는 것이 적절하다.

### 4.3 Service Layer — ADW Appliance

| 구성요소 | 책임 |
|---|---|
| ADW Service Node | 분석·요약·집계·마트 처리 서비스 제공 |
| Oracle Exadata Database | 대량 스캔·조인·집계와 분석 워크로드 수행 |
| RDW→ADW ETL | 정제·변환·이력화된 분석 데이터 공급 |
| 대외/대내 제공 Job | 경영관리, 리스크관리, 마이데이터, 대외계로 결과 제공 |
| Feedback 경로 | 분석 결과와 대상군을 운영계·마케팅 영역으로 환류 |

ADW는 분석 워크로드를 RDW의 준실시간 처리와 분리한다. 이 분리는 대량 집계가 실시간 수집과 운영성 조회를 방해하지 않게 하며, 분석 모델과 마트의 변경 주기를 독립적으로 관리하게 한다.

### 4.4 Service Layer — 공통 실행 서비스

장표 중앙의 세로 컴포넌트는 데이터플랫폼을 사용하는 공통 실행 주체를 나타낸다.

| 실행 주체 | 데이터플랫폼 사용 방식 |
|---|---|
| ETL | 원천 추출, RDW→ADW 변환·적재, 외부 제공 |
| 마케팅플랫폼 | 고객·행동·캠페인 데이터를 RDW/ADW에서 조회하고 결과를 환류 |
| BI 포털 | RDW·ADW의 지표, 실적, 분석마트 조회 |
| 데이터거버넌스 | 메타데이터, 품질, 흐름 및 표준 관리 |
| CDC 중계 | 원천 변경분 수신을 중계하여 원천 DB 부하와 결합도 완화 |

### 4.5 I/F Layer

| 인터페이스 | 용도 | 권장 통제 |
|---|---|---|
| SSO | 운영·관리 화면 인증 | 중앙 인증, 최소권한, 세션 만료 |
| CDC | 원천 DB 변경분의 실시간/준실시간 동기화 | 체크포인트, 순서 보장, 지연 감시 |
| ETL | 대량 데이터 추출·변환·적재 | 워터마크, 재시작점, 건수·합계 검증 |
| JDBC | 애플리케이션의 DB 접근 | 풀 크기, 타임아웃, 계정 분리, SQL 통제 |
| FOS | 표준 파일 송수신 | 파일명·완료표시·무결성 규칙 |
| MFT | 대내외 보안 파일 전송 | 암호화, 재전송, 감사 로그 |
| 대외 MCA | 대외기관 전문·파일 중계 | 전문 검증, 타임아웃, 장애 격리 |
| 통합관제 | Job·DB·연계 상태 감시 | GUID/Job ID 기반 상관분석 |
| IT 메타 | 기술·업무 메타 수집 | 계보, 스키마 변경 영향도 |
| 배치작업관리 | 일정·선후행·결과 관리 | 중복 기동 방지, 재처리 승인 |

### 4.6 Data Layer

#### RDW 데이터 영역

| 영역 | 성격 | 주요 이용자 |
|---|---|---|
| 실시간 SoR | 원천 변경의 통합 최신 상태 | 실시간 서비스, 운영 분석 |
| 실시간 집계·분석 | 짧은 주기의 집계·판단 데이터 | 마케팅·모니터링 |
| 업무지원 | 온라인·업무 애플리케이션 참조 데이터 | 마케팅플랫폼, BI 포털 |
| 로그분석 | 거래·행동·시스템 로그 | 운영관제, 분석 |

#### ADW 데이터 영역

| 영역 | 성격 | 주요 이용자 |
|---|---|---|
| 분석 SoR | 정제·이력화된 분석 기준 데이터 | 분석가, BI |
| 통합·요약·집계 | 전사 공통 지표와 요약 데이터 | 경영·리스크 관리 |
| 통합마트 | 공통 주제 중심 데이터마트 | BI 포털 |
| 분석 단위업무마트 | 업무별 상세 분석 데이터 | 개별 분석 업무 |
| 분석 보고서마트 | 정형 보고서 제공 데이터 | 경영정보·보고서 |
| 송신마트 | 외부 시스템 제공용 데이터 | 마이데이터·대외계 |
| Feedback | 모델 결과·대상군 환류 데이터 | RDW·마케팅플랫폼 |

## 5. 주요 데이터 처리 흐름

### 5.1 계정계 변경의 준실시간 수집

```text
코어/연계뱅킹·카드승인
  → 원천 Redo/변경분
  → CDC 중계
  → RDW 실시간 SoR
  → 실시간 집계·업무지원·로그분석
```

핵심 통제는 지연시간, 재처리 위치, 트랜잭션 순서, 중복 반영 방지와 원천 대비 정합성이다.

### 5.2 RDW에서 ADW로 분석 데이터 적재

```text
Control-M / ETL Scheduler
  → Job Shell
  → ETL 추출(RDW)
  → 정제·변환·이력화
  → 적재(ADW)
  → 통합·요약·업무마트·보고서마트
```

대량 적재는 증분 기준과 워터마크를 명시하고, 실패 시 전체 재실행보다 체크포인트 이후 재시작이 가능해야 한다.

### 5.3 파일 기반 대내외 연계

```text
BCV / 대내외 시스템
  ↔ FOS 또는 MFT
  ↔ 수신 영역
  → ETL 검증·변환
  → RDW 또는 ADW
```

파일 도착과 데이터 적재 완료를 구분해야 한다. 임시 파일, 완료 마커, 해시·건수·금액 합계 검증 후에만 후속 Job을 기동하는 것이 안전하다.

### 5.4 분석 결과 Feedback

```text
ADW 분석·모델 결과
  → Feedback/송신마트
  → ETL 또는 MFT/FOS
  → RDW·마케팅플랫폼·대외 서비스
```

Feedback 데이터는 생성 기준시각, 모델·규칙 버전, 유효기간, 재전송 여부를 함께 관리해야 결과 재현성이 확보된다.

## 6. 레이어 간 호출·접근 원칙

```text
허용
스케줄러 → Job Shell → ETL/DB Job
원천계 → CDC 중계 → RDW
업무 AP → 표준 JDBC 계정 → 허용된 RDW/ADW 서비스
RDW → ETL → ADW
대내외 시스템 ↔ FOS/MFT ↔ 수신·송신 영역

지양
원천 업무 DB → ADW 직접 갱신
외부 시스템 → RDW/ADW DB 직접 접속
분석 Job → RDW 온라인 서비스와 무제한 자원 경쟁
애플리케이션 계정으로 DDL 또는 광범위 스키마 접근
스케줄러를 우회한 수동 운영 Job 상시 실행
```

## 7. 비기능 아키텍처 분석

### 7.1 성능

- RDW는 CDC 수신과 온라인 조회를 우선하고, 대량 배치는 별도 서비스·자원그룹으로 제한한다.
- ADW는 대량 스캔과 병렬 처리에 최적화하되 동시성 상한을 둔다.
- JDBC 연결 풀, SQL 타임아웃, 병렬도, I/O 소비량을 워크로드별로 분리한다.

### 7.2 가용성

- Exadata RAC 노드 장애 시 서비스 재배치와 연결 재시도 정책을 검증한다.
- CDC·ETL 체크포인트와 Trail/Stage 파일을 이중화한다.
- 스케줄러, CDC 중계, FOS/MFT도 DB와 동일한 수준으로 장애전환 절차를 마련한다.

### 7.3 정합성

- 원천·RDW·ADW 단계별 건수, 키 중복, 금액 합계 및 기준시각을 검증한다.
- CDC와 ETL 경로가 동일 데이터를 중복 반영하지 않도록 소유 경로를 정의한다.
- 지연 도착과 소급 변경을 위한 재처리·이력화 정책이 필요하다.

### 7.4 보안

- 시스템·업무·운영 계정을 분리하고 최소권한을 적용한다.
- 개인정보는 저장·전송 암호화, 마스킹, 접근 이력과 보유기간을 관리한다.
- 대외 파일은 악성코드 검사, 전자서명 또는 해시 검증을 거친다.

### 7.5 관측성

- `source_system`, `interface_id`, `job_id`, `batch_date`, `extract_watermark`, `load_id`를 공통 추적키로 사용한다.
- CDC 지연, ETL 처리량, 실패·재처리 횟수, RDW/ADW 자원 사용량을 통합 대시보드로 관제한다.

## 9. 구현·운영 점검표

- [ ] RDW와 ADW의 데이터 소유권 및 갱신 주체가 정의되어 있는가?
- [ ] CDC 대상 테이블, 지연 SLA, 체크포인트와 재동기화 절차가 있는가?
- [ ] ETL 증분 키, 워터마크, 재시작점과 정합성 검증 기준이 있는가?
- [ ] Control-M과 ETL Scheduler의 책임 및 선후행 소유권이 중복되지 않는가?
- [ ] Job Shell의 표준 파라미터, 반환코드, 로그 형식이 정의되어 있는가?
- [ ] JDBC 계정과 DB 서비스가 업무·환경·읽기/쓰기 권한별로 분리되어 있는가?
- [ ] FOS/MFT 파일명, 임시파일, 완료마커, 보관·재전송 정책이 있는가?
- [ ] RDW/ADW 워크로드 자원그룹과 병렬도 제한이 적용되어 있는가?
- [ ] 데이터 품질, 계보, 메타데이터와 개인정보 통제가 자동화되어 있는가?
- [ ] 운영·DR 환경에서 CDC·ETL·DB 장애전환과 복구 리허설을 수행했는가?

## 10. 종합 평가

이 아키텍처는 **RDW의 준실시간 운영 데이터 처리**와 **ADW의 대용량 분석 처리**를 Appliance 단위로 분리하고, CDC·ETL·FOS/MFT를 표준 인터페이스로 배치한 데이터 허브 구조다. Control-M과 ETL Scheduler를 통한 중앙 통제, Exadata 기반의 처리 성능, 데이터거버넌스 연계는 장점이다.

성공적인 구현을 위해서는 단순한 물리 분리보다 데이터 소유권, CDC와 ETL의 경계, 멱등 재처리, 워크로드 자원 통제, 계보·품질 검증을 명확히 해야 한다. 특히 RDW와 ADW 사이의 ETL 및 Feedback 경로를 표준 데이터 계약으로 관리해야 운영 안정성과 분석 신뢰성을 동시에 확보할 수 있다.
