# 운영환경 데이터플랫폼 시스템 구성 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `운영환경 데이터플랫폼 시스템 구성` 이미지
- 원본 분류: 환경별 Physical Architecture
- 이미지 설명: 데이터플랫폼은 `서비스 제공 Zone`에 배치되며, 채널·채널통합·대내통합 Zone은 업무 연계 대상을 표시한다.
- 판독 원칙:
  - `RDW 어플라이언스`, `ADW 어플라이언스` 및 주변 시스템 명칭은 **이미지 사실**로 취급한다.
  - 화살표가 없는 배치도이므로 유입·반출 방향, 프로토콜, 주기는 **해석**으로 분리한다.
  - `어플라이언스`는 일반적으로 통합 장비/플랫폼을 의미하지만, 제품·노드·사양은 이미지만으로 확정하지 않는다.
  - 외부 Zone의 API G/W·MCA·FOS·MFT·CDC·ETL은 데이터플랫폼 내부 DB 컴포넌트가 아니라 연계 경계다.

---

## 1. 핵심 결론

1. 데이터플랫폼의 핵심 소유 경계는 **RDW와 ADW라는 두 데이터 처리계의 책임·부하·장애 격리**다.
2. RDW는 온라인·준실시간·싱글뷰 조회를 우선 보호하고, ADW는 BI·OLAP·통계·대량 이력 분석을 담당하는 구조로 해석한다.
3. 대외 온라인 경로는 `API G/W·대외 MCA`, 파일 경로는 `FOS·MFT`, 대내 데이터 경로는 `CDC·ETL`로 분리된다.
4. CDC는 변경데이터를 준실시간으로 RDW에 반영하는 Fast Path, ETL은 정제·변환·집계 후 ADW를 갱신하는 Deep Path로 구분하는 것이 타당하다.
5. RDW→ADW 전환은 단순 DB 복제가 아니라 스키마·품질·시간·코드·재처리 규칙을 가진 **Data Flow Contract**로 관리해야 한다.
6. 공통 인프라는 SSO, Control-M, NH Cloud FWK Master Solution, eCAMS, 단말관리/배포, RD, 배치, UNO Dashboard로 구성되며 데이터플랫폼 운영 제어면을 지원한다.
7. 이 이미지는 논리/물리 영역 배치도이지 테이블·뷰·계정·노드·용량 정의서가 아니다. 운영 확정에는 별도의 Runtime/Data Evidence가 필요하다.

## 3. 전체 아키텍처 텍스트 그림

### 3.1 Zone 구조

```text
┌────────────┐  ┌────────────────┐  ┌───────────── 서비스 제공 Zone ───────────────────┐  ┌────────────┐
│ 채널 Zone   │  │ 채널통합 Zone   │  │                                                 │  │ 대내통합    │
│             │  │                │  │  ┌─ 데이터플랫폼 소유 경계 ─────────────┐  │  │ Zone         │
│ 대내/고객    │  │ API G/W        │  │  │                                             │  │  │ 온라인통합   │
│ 채널(미상세) │  │ 대외 MCA       ├→│  │  [RDW 어플라이언스]  [ADW 어플라이언스]   │  │←├─│ FOS / MFT    │
│             │  │ FOS / MFT      │  │  │                                             │  │  │ CDC / ETL    │
│ 중앙회·경제  │  │ 데이터통합    │  │  └─────────────────────────────────────────────┘  │  └────────────┘
│ 유통·농협자산│  └────────────────┘  │                                                 │
│ 신용보증·AgriX│                        │  ┌─ 공통 인프라·운영 제어면 ─────────────────────┐  │
└────────────┘                        │  │ SSO | Control-M | NH Cloud FWK Master | eCAMS   │  │
                                      │  │ 단말관리/배포 | RD | 배치 AP | UNO Dashboard  │  │
                                      │  └─────────────────────────────────────────────┘  │
                                      └─────────────────────────────────────────────────┘
```

### 3.2 Fast Path와 Deep Path

```text
[원천 업무 DB / 채널 / 대외]
       │
       ├─ 변경이벤트·CDC ─────→ [RDW]
       │                              │
       │                              └─→ 온라인·싱글뷰·준실시간 활용
       │
       └─ 파일·배치·ETL ──────→ [ADW]
                                      │
                                      └─→ BI·OLAP·통계·대량 이력 분석

선택 경로:
  RDW ── ETL/정제 ──→ ADW
  원천 ── Direct Batch/ETL ──→ ADW
```

### 3.3 대외·파일 흐름

```text
온라인: 대외기관 ↔ 대외 MCA/API G/W ↔ 서비스/API ↔ RDW/ADW
파일  : 대외기관 ↔ MFT ↔ FOS ↔ Stage/ETL ↔ RDW/ADW
대내CDC: 내부 원천 DB → CDC → RDW
대내ETL: 내부 원천/RDW → ETL → ADW
```

> 데이터플랫폼은 API 어플리케이션 실행계를 세부 표시하지 않았다. API G/W가 RDW/ADW에 직접 접속한다고 해석하지 말고, 소유 Service/API 계층을 통해 접근하도록 해야 한다.

## 4. RDW·ADW 핵심 컴포넌트 분석

### 4.1 책임 비교

| 구분 | RDW 어플라이언스 | ADW 어플라이언스 |
|---|---|---|
| 주요 목적 | 온라인/준실시간 업무 조회 | 분석·집계·통계·대량 조회 |
| 데이터 신선도 | 높음; 초/분 단위 목표 | 적재 주기/SLA 기반 |
| 주요 유입 | CDC, Event, 준실시간 적재 | ETL, Batch, File, RDW 정제 결과 |
| 주요 소비자 | 업무 WAS, 미니 싱글뷰, 실시간 AP | BI 포털, OLAP, Self-BI, 보고서, 분석 배치 |
| Query 특성 | 짧고 선택도 높은 조회 | 대량 Scan, Join, Aggregate |
| 우선 보호 지표 | p95/p99, connection, CDC lag | ETL SLA, throughput, workload queue |
| 장애 영향 | 온라인·싱글뷰 저하 | BI·분석·보고서 지연 |

### 4.2 물리 분리의 의미

- 노드·CPU·Memory·Storage·I/O·DB Session 자원 경합을 분리한다.
- 분석 Query 폭증이 온라인 조회 SLA를 침해하지 않도록 한다.
- RDW와 ADW의 장애·패치·백업·용량 확장 주기를 독립적으로 관리한다.
- 분리는 같은 장비의 스키마만 나누는 논리 분리보다 강한 격리를 의미하지만, 실제 클러스터/노드 구성은 자산원장으로 확정해야 한다.

### 4.3 접근 원칙

```text
채널/API Gateway ─X→ RDW/ADW 직접 접속
타 도메인 DAO     ─X→ 소유 테이블 직접 갱신
임의 BI Query       ─X→ RDW 무제한 대량 Scan

채널/API → 소유 Service → DAO/Mapper → 승인된 RDW View/Table
BI/OLAP  → 의미계층/승인 Dataset → ADW
CDC/ETL  → 전용 계정/스테이지 → 소유 영역
```

## 5. 데이터 연계 메커니즘

### 5.1 CDC

| 항목 | 필수 규칙 |
|---|---|
| Source | DB/Table Owner, Log Position/SCN, Capture 방식 |
| Delivery | 순서, At-least-once/멱등성, Partition Key |
| Target | RDW Schema/Table, Upsert/Delete 규칙 |
| Recovery | Checkpoint, Replay 범위, 중복 제거 |
| Quality | 건수·합계·지연·누락 대사 |
| Security | 전용 계정, 암호화, 민감컬럼 필터 |

CDC 장애는 온라인 원천을 중단시키기보다 RDW 신선도를 저하시키는 형태로 나타날 수 있다. 소비 시스템은 `last-updated-at`과 신선도 임계치를 인지해야 한다.

### 5.2 ETL

```text
Extract → Stage → Validate → Transform → Load → Reconcile → Publish
             │          │          │          │
             └─ Schema  └─ Code/PII  └─ Partition └─ Dataset Version
```

| 통제 | 설명 |
|---|---|
| 영업일/기준시각 | 원천 마감, 적재 기준일, 시간대 통일 |
| 재시작 | Job/Step 체크포인트와 멱등 Load |
| 품질 | Null, Domain, Referential, Duplicate, Balance 규칙 |
| 스키마 변경 | 호환성 검증과 Consumer 통지 |
| 배포 | ETL Code·Mapping·SQL·Parameter 버전 단일화 |
| 발행 | 검증 완료 전 Dataset을 BI에 노출하지 않음 |

### 5.3 FOS·MFT 파일 파이프라인

```text
대외 기관
  → MFT(전송·재전송·스케줄)
  → FOS(파일 보관·식별·무결성)
  → Landing/Stage
  → 악성코드·해시·포맷·건수 검증
  → ETL
  → RDW 또는 ADW
```

파일명을 처리 완료 판단으로 사용하지 말고 File ID, 해시, 사이즈, 영업일, Source, Schema Version, 처리 상태를 하나의 Manifest로 관리해야 한다.

### 5.4 API·대외 MCA

- API는 소량·즉시성 조회/전송에, MFT/ETL은 대량·재처리 중심 전송에 사용한다.
- 대외 MCA/API G/W는 기관 인증, 전문 변환, Rate Limit, timeout, GUID, 오류 표준화를 담당한다.
- API Gateway의 DB 직접 접속은 금지하고, 데이터 소유 Service/API를 경유한다.
- 수신·응답·재전송·보상 상태를 기관별 대사할 수 있어야 한다.

## 6. RDW→ADW Data Flow Contract

| 계약 항목 | 정의 내용 |
|---|---|
| Owner | Source Domain, Table/View Owner, Data Steward |
| Dataset | 논리/물리명, 버전, 설명, 민감도 |
| Schema | Column, Type, Null, Key, Code, Timezone |
| Transfer | CDC/ETL/File/API, 주기, 기준시각, 순서 |
| SLO | Freshness, Completeness, Accuracy, Availability |
| Recovery | Checkpoint, Replay, Backfill, Duplicate 처리 |
| Reconciliation | 건수, 합계, Hash, 표본, 승인자 |
| Consumer | BI/OLAP/Service, 사용 목적, Query 제한 |
| Retention | 보존, Archive, Purge, 파기 증적 |

```text
[RDW Snapshot N]
       │ ETL Contract v3
       ▼
[ADW Load Staging]
       │ Validation PASS
       ▼
[ADW Dataset v2026-08-22]
       │ Publish Atomic Switch
       ▼
[BI / OLAP / Analytics]
```

중간 적재가 실패한 상태에서 ADW Dataset을 부분 갱신하면 보고서 간 수치가 달라질 수 있다. 검증 완료본을 버전 단위로 원자적 발행해야 한다.

## 8. 보안·가용성·용량 원칙

### 8.1 보안

- API G/W·MCA·ETL·CDC·BI 등 접근 주체별로 전용 계정을 분리한다.
- 운영자 계정과 애플리케이션 계정을 공유하지 않는다.
- RDW/ADW의 Read/Write, DDL, Export, DBA 권한을 분리하고 승인·감사한다.
- 개인정보는 저장·전송 암호화, 마스킹, 목적별 접근, 보존/파기를 적용한다.
- MFT/FOS 파일은 악성코드·해시·전송구간·소유자·보존기간을 통제한다.

### 8.2 가용성·DR

- RDW와 ADW는 각각 HA Peer, Backup, DR Target, RPO/RTO를 독립 정의한다.
- RDW 복구는 온라인/싱글뷰 영향 때문에 ADW 분석 복구보다 우선순위가 높을 수 있다.
- CDC/ETL은 DB 복구 후 어디서부터 재개할지 Checkpoint를 복구해야 한다.
- DR 전환 후 신선도·건수·합계·Consumer 접속을 함께 검증해야 한다.

### 8.3 용량

```text
소스 발생량
  → CDC/ETL Throughput
    → RDW/ADW Write IOPS
      → Query Concurrency / Temp / PGA
        → Storage Growth / Backup Window
          → DR Replication Bandwidth
```

- RDW는 온라인 동시성·Query timeout·DB Session을, ADW는 대량 처리량·Temp·I/O·Workload Queue를 중점 산정한다.
- 데이터 증가량, 인덱스, 파티션, 압축, 보존기간, 백업 창을 하나의 용량 모델로 연결한다.

## 9. 현재 TCF 저장소와의 대응

| 영역 | 저장소 근거 | 판정 |
|---|---|---|
| RDW | 업무 WAR Primary DS, DAO/MyBatis, 운영 Oracle RDW 목표 | 설계 정합; 현재 샘플는 H2 중심 |
| ADW | 분석·집계 외부 DB, Service의 ADW DS 참조 원칙 | 설계 정합; 샘플 단계 |
| DB 선택 | 실시간 업무→RDW, 분석·통계·대량→ADW 결정 트리 | 문서 확정 |
| 대외/API | `tcf-gateway`, `tcf-eai`, serviceId/HTTP | 구조 대응; 대외 MCA 제품 동일성 미확인 |
| 파일 | `tcf-om` UD, Object Storage/FOS 연계 설계 | 구조 대응; MFT 운영 구성 미확인 |
| 배치 | `tcf-batch`, Spring Batch/Job Repository | 부분 대응 |
| 모니터링 | `tcf-batch`의 DB Pool/Health 수집, `tcf-om` 대시보드 | UNO와 개념 대응, 제품 동일성 미확인 |
| 데이터 거버넌스 | `47-data-governance.md`, ADR-DATA-001 | 원칙 정합 |

### 9.1 현행과 목표 차이

```text
현재 샘플:
  업무 WAR → H2 Primary DS / RDW·ADW Mapper hook

목표 운영:
  온라인 Service → 업무별 Oracle RDW Schema
  분석 Service/Batch → 별도 Oracle ADW
  CDC/ETL → 전용 계정·스테이지·체크포인트
```

### 9.2 미확정 운영 매핑

- 실제 RDW/ADW Appliance 제품·노드·서버·스토리지 구성
- Host/JVM/WAR별 Datasource URL·Pool·Service Account
- Domain/Table/View Owner와 Read/Write Matrix
- CDC/MFT/ETL 실제 제품·토폴로지·스케줄·Checkpoint
- HA/DR Node, Replication, Backup, RPO/RTO

`code-understand` 자동 추출기는 로컬 설정 권한 문제로 이전 실행에서 사용할 수 없었으며, 본 분석은 `rg` 교차 검색과 근거 문서 열람으로 대체했다.

## 12. 사실·해석·미확인 분리

### 12.1 이미지에서 확정 가능한 사실

- 데이터플랫폼은 서비스 제공 Zone에 배치된다.
- 서비스 영역에 RDW 어플라이언스와 ADW 어플라이언스가 별도로 표시된다.
- 대외 채널·채널통합과 대내통합 대상 시스템이 주변 Zone에 표시된다.
- 대내 데이터 통합에 CDC와 ETL이 표시된다.

### 12.2 아키텍처 해석

- RDW는 온라인/준실시간, ADW는 분석/대량 책임이다.
- CDC→RDW는 Fast Path, ETL→ADW는 Deep Path다.
- API/MCA, FOS/MFT, CDC/ETL은 서로 다른 용량·시간성·재처리 요구를 가진 연계 경로다.

### 12.3 추가 증적 없이 확정할 수 없는 항목

- RDW/ADW 제품·노드·서버·사양·용량·클러스터 구성
- 실제 API·파일·CDC·ETL 유입/반출 방향과 토폴로지
- Domain/Table/View Owner, Read/Write Matrix, Schema, Data Catalog
- 계정·Datasource·Pool·Timeout·쿼터·자원그룹
- 품질규칙·리니지·보존·파기·마스킹 실제 설정
- HA/DR·Backup·Replication·RPO/RTO·Failover Runbook

---

## 13. 최종 평가

이 구성은 **대외 온라인·파일 수집, 대내 CDC·ETL 통합, RDW 준실시간 제공, ADW 분석 제공, 공통 운영 제어**를 분리한 데이터 아키텍처다. 핵심은 RDW와 ADW를 단순히 두 DB로 나누는 것이 아니라, 신선도·부하·SLA·장애·복구 책임을 분리하는 데 있다.

운영 승인 전에 `Source→CDC/ETL→RDW/ADW→Consumer`, `Domain→Table/View Owner`, `Application→Datasource/Account`, `Primary→HA/DR`의 실제 매핑을 닫아야 한다. 특히 RDW/ADW Read/Write Matrix는 데이터 오너십과 장애 반경을 결정하는 P0 통제 산출물이다.
