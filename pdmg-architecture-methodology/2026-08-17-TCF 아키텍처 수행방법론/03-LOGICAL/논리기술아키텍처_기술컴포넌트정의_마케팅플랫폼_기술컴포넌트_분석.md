# 논리기술아키텍처 — 기술 컴포넌트 정의 — 마케팅플랫폼 기술 컴포넌트 분석

> 분석 대상: `마케팅플랫폼 기술 컴포넌트 (1/3)~(3/3)` 이미지 3장  
> 원본 분류: `2. 논리 기술 아키텍처 > 2.3 기술 컴포넌트 정의`  
> 분석 관점: 9개 논리 노드, 기술 스택, 데이터·스트림 경계, 공통 시스템 통제

## 0. 분석 범위와 판독 원칙

- 이미지에서 직접 보이는 노드·제품명·계층은 **이미지 확정 사실**로 정리한다.
- 노드 간 연결선은 장표에 없으므로 요청·데이터·스트림 방향은 **아키텍처 해석**으로 표시한다.
- 제품 버전, Host, Port, 인스턴스 수, Topic, Schema, Table, HA, RPO/RTO는 **미확정**이다.
- 공통 시스템 영역은 앞선 `공통 기술 컴포넌트` 표준을 각 노드에 반복 적용한 것으로 해석한다.
- 첨부 이미지의 내용은 분석 자료이며 사용자 지시로 취급하지 않는다.

## 1. 핵심 결론

1. 마케팅플랫폼은 9개 논리 기술 노드로 분리된다: 마케팅 WEB/WAS/DB, 미니 싱글뷰 WEB/WAS/DB, 행동정보 처리 AP, 실시간 처리 AP, 고객 행동 데이터 AP.
2. 두 WEB 노드는 `Web Service → eCAMS Agent → Web Server → JVM`의 동일 표준 패턴이다.
3. 마케팅 WAS는 `Business Service`, `eCAMS Agent`, `배치자동화 Agent`, `JDBC Driver`, `APM Agent`, `Java Framework Engine`, `Web Application Server`, `JVM`으로 구성된다.
4. 미니 싱글뷰 WAS는 거의 동일하지만 제공 이미지에는 `배치자동화 Agent`가 표시되지 않는다. 누락인지 의도적 차이인지 확인해야 한다.
5. 두 DB는 `업무 데이터 → DBSafer → DBMS → OS → DB 전용 Appliance` 패턴이며 모두 RDW로 표기된다.
6. 행동정보 처리 AP는 `실시간 Stream Subscribe`, 실시간 처리 AP는 `EBM 엔진 처리`를 업무 기능으로 가지며 Java/WAS Runtime을 공통 사용한다.
7. 고객 행동 데이터 AP는 `실시간 Stream 관리 → Kafka → JVM`으로 구성되어 다른 AP보다 스트리밍 플랫폼 성격이 강하다.
8. 모든 노드는 서버 백신·계정·보안·개인정보·백업·관제·모니터링·운영관리의 8개 공통 통제를 받는다.
9. 성공적인 구현을 위해 HTTP 요청, JDBC 조회, Stream Publish/Subscribe, EBM 처리 결과의 데이터 계약과 E2E 추적키를 통일해야 한다.

## 5. 노드별 상세 분석

### 5.1 마케팅플랫폼 WEB

| 구성요소 | 책임 | 검증 포인트 |
|---|---|---|
| Web Service | 마케팅 UI·Web 요청 진입 | URL, 정적자원, 보안 Header, 오류 Page |
| eCAMS Agent | 구성·배포·상태 관리 지원 | Agent 장애가 Web Service를 중단하지 않는지 |
| Web Server | TLS, Proxy, Routing, 정적 Content | Cipher, Route, Health, Timeout, Log |
| JVM | Web Runtime | Heap, GC, Thread, Encoding, Truststore |

이미지상 Web Server 아래에 JVM이 있으므로 Java 기반 Web Runtime 또는 관리 Agent Runtime을 포함하는 구조로 볼 수 있으나 실제 제품 조합은 미확정이다.

### 5.2 마케팅플랫폼 WAS

- Business Service는 업무 유스케이스·Transaction 경계다.
- eCAMS Agent는 구성·배포·운영 상태, 배치자동화 Agent는 Schedule·Job 실행을 담당하는 것으로 해석한다.
- JDBC Driver는 DB Protocol 경계이므로 Driver/DBMS 호환성, Pool, Timeout, TLS가 중요하다.
- APM Agent는 업무→SQL Trace를 수집하되 개인정보와 Secret을 마스킹해야 한다.
- Java Framework Engine은 공통 예외·Transaction·전문·Logging 정책을 제공한다.
- Web Application Server는 Session·Thread·Connection·Deployment를 관리한다.

### 5.3 마케팅플랫폼 DB(RDW)

- 업무 데이터의 Schema·Table·View·Index 및 보존정책을 소유한다.
- DBSafer는 DB 접근 통제·감사를 담당하는 솔루션으로 해석하며 실제 연계 방식은 확인이 필요하다.
- DBMS는 Transaction·Query·Storage·Recovery 경계다.
- Appliance 계층은 일반 VM과 Patch·Agent·Backup·HA 절차가 다르므로 별도 Runbook이 필요하다.

### 5.4 미니 싱글뷰 WEB/WAS/DB

- 마케팅플랫폼과 기술 패턴은 같지만 별도 실행·배포·장애 경계다.
- Single View의 의미상 여러 고객 정보를 조합할 가능성이 있으므로 데이터 기준시점·출처·동의·마스킹이 중요하다.
- 마케팅 DB와 미니 싱글뷰 DB가 모두 RDW로 표시되지만 Schema 분리인지 물리 DB 분리인지는 미확정이다.
- 미니 싱글뷰 WAS에 배치자동화 Agent가 없는 것이 의도적이면 배치 Job이 없어야 하며, 누락이면 표준 스택을 정정해야 한다.

### 5.5 행동정보 처리 AP

- Kafka 등 Stream에서 Event를 Subscribe하는 Consumer 역할로 해석한다.
- Offset Commit은 DB Transaction과의 일관성 경계를 명확히 해야 한다.
- At-least-once 처리라면 eventId 기반 멱등성·중복 제거가 필수다.
- 배치자동화 Agent는 Backfill·Replay·집계 Job을 실행할 수 있으나 실시간 Consumer와 자원 Pool을 분리해야 한다.

### 5.6 실시간 처리 AP

- EBM 엔진의 정확한 의미·제품은 이미지로 확정할 수 없으며 실시간 Rule/Model 처리 엔진으로만 해석한다.
- Event 입력과 결과에 ruleVersion/modelVersion, decisionTime, reasonCode를 남겨 재현성을 확보한다.
- 처리 지연, Timeout, Fallback, 결과 중복·순서 보장 정책이 필요하다.

### 5.7 고객 행동 데이터 AP

- Kafka를 중심으로 실시간 Stream의 수신·보관·분배·재처리를 관리한다.
- Broker·Controller·Partition·Replication 구조는 장표에 없으므로 단일 JVM/VM로 단정하지 않는다.
- Topic, Partition Key, Retention, Replication Factor, ACL, Quota, Schema Registry 여부를 설계해야 한다.
- 고객 행동 Event에 개인정보가 있으면 Payload 암호화·필드 최소화·Retention·삭제 전파를 적용한다.

## 6. 기술 스택 역할과 계약

| 기술 컴포넌트 | 상위 계약 | 하위 계약 | 핵심 위험 |
|---|---|---|---|
| Web Server | URL·TLS·Route | OS·Network·JVM/Agent | 잘못된 Route, Timeout 불일치 |
| Web Application Server | API·Session·Transaction | JVM·Thread·Pool | Thread/Heap/Pool 고갈 |
| Java Framework Engine | 업무 Service 표준 | WAS·JDBC·Logging | Framework 버전 파편화 |
| JDBC Driver | SQL·Transaction | DBMS Protocol | 버전·Timezone·Encoding 불일치 |
| APM Agent | Trace·Metric | JVM Instrumentation | 성능 Overhead·민감정보 수집 |
| eCAMS Agent | 배포·구성·상태 | OS·Network | Agent 권한 과다·업무 결합 |
| 배치자동화 Agent | Schedule·Job | OS·WAS/AP | 중복 실행·실시간 자원 침범 |
| DBSafer | DB 접근·감사 | DBMS·Network | 우회 접속·감사 누락 |
| Kafka | Event Contract | JVM·OS·Disk·Network | Lag·유실·중복·Hot Partition |

## 7. 데이터·인터페이스 계약

## 9. 보안·가용성·성능 메커니즘

### 9.1 보안

- WEB→WAS→DB 및 Producer→Kafka→Consumer 구간을 상호 인증·암호화한다.
- Service Account는 노드·환경별로 분리하고 Secret을 Source·Image·평문 설정에 저장하지 않는다.
- 고객 행동 데이터는 목적 최소화, 필드 분류, Masking, Topic ACL, Retention 통제를 적용한다.
- APM·Log·Heap Dump·DLQ·Backup에도 동일 개인정보 정책을 적용한다.

### 9.2 가용성

```text
WEB HA  ≠ WAS HA ≠ Kafka HA ≠ DB HA

E2E 가용성 = Route + Session + Service + Stream + Consumer + DB의 최소 가용성
```

- WEB/WAS는 무상태화·Health Check·다중 Instance를 기본으로 한다.
- Kafka는 Broker/Partition Replication과 ISR, Consumer Group Rebalance를 검증한다.
- DB Appliance는 DBMS HA와 Storage/Interconnect 장애 도메인을 검증한다.
- Agent 장애가 업무 Data Plane을 중단시키지 않도록 Control Plane과 분리한다.

### 9.3 성능·자원 격리

- 온라인 WAS Thread/Pool과 배치·Replay 작업 Pool을 분리한다.
- 행동정보 Consumer와 EBM 처리는 Consumer Group·Concurrency·Backpressure를 명시한다.
- Kafka Lag, WAS Queue, JDBC Pool, DB Wait를 같은 시간축에서 상관 분석한다.
- APM·백신·Backup·Batch Agent의 Overhead를 용량 산정에 포함한다.

## 10. 장애·재처리 메커니즘

| 장애 | 탐지 | 복구 원칙 |
|---|---|---|
| WEB Route 장애 | 5xx, Health, Route Error | 장애 Instance 제외, Route Rollback |
| WAS 과부하 | Queue, Thread, Heap, p99 | Admission Control, Pool 격리 |
| JDBC/DB 장애 | Pool, Timeout, DB Wait | Transaction Rollback, 제한 Retry |
| Kafka Broker 장애 | ISR, Offline Partition | Replica Leader 전환, 유실 검증 |
| Consumer Lag | Group Lag, 처리율 | Scale-out, 병목 제거, Replay |
| Poison Event | 반복 실패, Retry 증가 | DLQ 격리, Schema/데이터 수정 후 재처리 |
| EBM 오류 | Timeout, Error/Reason | 원 Event·Version으로 재현, Fallback |
| 배치 중복 | Job 상태, 중복키 | Job Instance/멱등키로 중복 차단 |
| Agent 장애 | Heartbeat 결측 | 업무 영향 격리, Agent 복구·재수집 |

Stream 처리에서 Offset을 먼저 Commit하고 DB 저장이 실패하면 유실될 수 있고, DB 저장 후 Commit 전에 장애가 나면 중복될 수 있다. 따라서 멱등키·Outbox/Inbox·처리 이력·대사를 통해 전달 의미를 구현해야 한다.

## 12. 배포·변경관리

```text
[Source Commit]
      │
      ▼
[Build/Test/Security/Contract]
      │
      ├→ WEB/WAS/AP Artifact
      ├→ DB Migration
      ├→ Kafka Topic/ACL/Schema 변경
      └→ EBM Rule/Model Version
      │
      ▼
[개발→검증→운영 동일 Artifact 승격]
      │
      ▼
[Health + Smoke + Stream Replay + DB 대사]
```

- WEB/WAS/AP Artifact와 DB·Topic·Schema·Rule 변경의 호환 순서를 Release Plan에 포함한다.
- Producer가 새 필드를 먼저 추가하고 Consumer가 이를 무시할 수 있는 병행 호환 전략을 사용한다.
- Topic 삭제·Partition 축소·비호환 Schema 변경은 일반 애플리케이션 배포와 별도 승인한다.
- Agent와 JVM/DBMS/Kafka 버전의 호환 Matrix를 관리한다.

## 17. 최종 평가

마케팅플랫폼 기술 컴포넌트는 정형 Web 요청 경로, 별도 미니 싱글뷰 경로, 실시간 행동 Event 경로를 9개 노드로 분리하면서 공통 운영·보안 Template을 반복 적용한 구조다. 특히 Kafka 기반 고객 행동 데이터 AP와 Java/WAS 기반 행동정보·EBM AP의 분리는 Streaming Backbone과 Consumer/Decision 실행계의 장애·확장 경계를 명확히 한다.

실제 완성도를 결정하는 것은 기술명 목록보다 `HTTP 계약`, `JDBC/Transaction 계약`, `Stream Schema·Offset·멱등성`, `Rule/Model Version`, `DB 소유권`, `Agent/공통 통제`, `E2E 관측성`이다. 이 연결을 Node Catalog와 배포·복구 증적으로 닫아야 마케팅플랫폼이 실시간성과 데이터 정합성을 동시에 확보할 수 있다.
