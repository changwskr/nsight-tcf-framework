# VISION — 차세대 정보계 개편 기본 방향 아키텍처 분석

> **문서 성격:** 원본 장표(`차세대 정보계 개편 기본 방향`) 기준 분석본이다.  
> **목차(§1~§37)는 유지**하고, 설명 보강·부족한 항목은 각 절 내부와 ANALYSIS 표기로 추가했다.  
> FACT(원본)와 ANALYSIS(해석·보완)를 섞어 단정하지 않는다.  
> 관련 개요: [`VISION_개요_아키텍처정의_분석.md`](./VISION_개요_아키텍처정의_분석.md)

## 1. 핵심 결론

이 장표는 차세대 정보계의 세부 기술구조를 설명하는 문서가 아니라, **향후 모든 Application / Data / Technical / Interface / Operation 아키텍처 설계가 따라야 할 상위 VISION과 설계 방향을 4개 축으로 고정하는 장표**다.

원본이 제시하는 최상위 목표는 다음과 같다.

> **데이터 기반의 실시간 의사결정을 지원하는 유연하고 확장 가능한 지능형 플랫폼을 구축하고, 고객 중심 채널 경험 강화 및 비즈니스 민첩성 확보를 위한 차세대 아키텍처를 구현함**

이를 아키텍처 관점으로 구조화하면 다음과 같다.

```text
                           차세대 정보계 VISION
                                   │
          ┌────────────────────────┼────────────────────────┐
          │                        │                        │
          ▼                        ▼                        ▼
   데이터 기반 실시간        고객 중심 채널 경험        비즈니스 민첩성
      의사결정 지원               강화                    확보
          │                        │                        │
          └────────────────────────┼────────────────────────┘
                                   ▼
                     유연하고 확장 가능한 지능형 플랫폼
                                   │
                                   ▼
                        차세대 아키텍처 구현
```

그리고 이를 실현하기 위한 기본 방향은 다음 4개다.

```text
1. 고객 중심 서비스 강화
2. 데이터 기반 의사결정 강화
3. 통합 정보 활용 기반 마련
4. 유연하고 안정적인 운영체계 확보
```

이 네 방향은 서로 독립된 목표가 아니라 다음처럼 연결되는 하나의 구조다.

```text
고객 중심 서비스
        ↓
통합 정보 기반
        ↓
실시간 데이터 활용
        ↓
의사결정 고도화
        ↓
표준화·확장성·운영 안정성
```

따라서 이 장표는 이후 상세 아키텍처에서 반드시 다음 질문으로 변환되어야 한다.

- 고객 경험 강화를 위해 어떤 Application/Channel 구조가 필요한가?
- 실시간 의사결정을 위해 어떤 Data/Streaming/Analytics 구조가 필요한가?
- 통합 정보 활용을 위해 어떤 데이터 통합·조회·연계 구조가 필요한가?
- 민첩성과 안정성을 동시에 확보하기 위해 어떤 표준화·확장성·운영통제가 필요한가?

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 (VISION 수준) | 답하지 않는 것 (후속 설계) |
|---|---|
| 개편의 최상위 목표 문장 | 제품·미들웨어·서버 사양 |
| 4대 기본 방향과 하위 bullet | Layer/패키지/API 명세 |
| 방향이 Application·Data·Technical 등에 주는 의미 | Timeout·CDC·HA의 구현 방식 |
| 후속 ADR·NFR·KPI로 넘길 질문 | 정량 SLA 수치의 확정값 |

### 읽는 순서 권장

```text
§1 핵심 결론 → §2~§4 VISION 문장·구조
        │
        ├─ 4대 방향 상세: §6~§20
        ├─ 영역 매핑: §22~§27
        ├─ 원칙·의사결정: §30~§31
        └─ GAP·검증: §32~§34 → §37 최종 평가
```

한 문장으로 말하면, 이 장표는 **“차세대 정보계가 어디로 가야 하는가”** 를 고정하고,  
**“어떤 제품·구성으로 갈 것인가”** 는 후속 Architecture Design에 위임한다.

### VISION 문장의 구조적 읽기 (ANALYSIS)

한 문장을 **수단 → 목적 → 결과** 로 나누면 설계 추적에 유리하다.

| 구분 | VISION 조각 | 후속에서 묻는 것 |
|---|---|---|
| 수단 | 유연·확장 가능한 지능형 플랫폼 | 플랫폼 경계·표준·확장 단위 |
| 능력 | 데이터 기반 실시간 의사결정 지원 | Freshness·분석·의사결정 경로 |
| 가치 | 고객 중심 채널 경험 강화 | 채널 연계·UX·경험 KPI |
| 가치 | 비즈니스 민첩성 확보 | 변경 용이성·배포·표준 준수 |
| 결과 | 차세대 아키텍처 구현 | Target Architecture + Validation |

“지능형”은 원본에 있으나 **AI/ML 제품·범위를 확정하지 않는다.**  
후속에서 “지능형 = 규칙/스코어링/추천/생성형” 중 무엇을 포함하는지 별도 합의가 필요하다. (§35 확인 필요)

# 5. VISION → Architecture Capability 변환

원본의 4대 방향을 아키텍처 역량으로 변환하면 다음과 같다.

```text
VISION 1
고객 중심 서비스 강화
     ↓
Channel Integration
Customer Context
Unified Experience
UI/UX Standard

VISION 2
데이터 기반 의사결정 강화
     ↓
Real-time Data
Analytics
BI
Timely Information Delivery

VISION 3
통합 정보 활용 기반 마련
     ↓
Integrated Customer/Product/Channel Data
Unified Query
Information Integration

VISION 4
유연하고 안정적인 운영체계 확보
     ↓
Standard Architecture
Scalable Platform
Stable Operations
```

> 위 영문 Capability 명칭은 원본 내용을 기술적으로 구조화한 **ANALYSIS**다.

### Capability → 후속 산출물 대응 (ANALYSIS)

| Capability | 최소 후속 산출물 | 품질 질문 |
|---|---|---|
| Channel Integration / Customer Context | 채널·고객 Context 설계 | 채널 전환 시 Context가 유지되는가? |
| Real-time Data / Analytics | 데이터 흐름·Freshness 정의 | “실시간”의 허용 지연은? |
| Unified Query / Integration | 통합 조회 Scope·SoT | 충돌 시 우선 데이터는? |
| Standard / Scalable / Stable Ops | 표준 Catalog·확장·운영 기준 | 표준 준수·HA를 어떻게 검증하는가? |

Capability 표만 있고 산출물·품질 질문이 없으면, VISION은 **구호**로 남고 설계로 내려가지 못한다.

# 6. 방향 ① 고객 중심 서비스 강화 — 상세 분석

## 6.2 아키텍처적 의미

이 방향은 단순 UI 개선이 아니라 **채널·고객정보·업무흐름을 고객 중심으로 재조직하는 것**을 의미한다.

```text
기존 관점
채널 A     채널 B     채널 C
  │          │          │
각자 정보   각자 화면   각자 서비스


              ↓


차세대 관점
         Customer Context
               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
   채널 A    채널 B    채널 C
     │         │         │
     └─────────┼─────────┘
               ▼
       일관된 고객 경험
```

---

## 6.3 “채널 간 정보 연계 강화”의 의미

원본 표현:

```text
채널 간 정보 연계 강화
```

이는 다음과 같은 Architecture Question으로 변환된다.

```text
채널 A에서 시작한 고객 Context를
채널 B에서도 이어서 사용할 수 있는가?

고객/상품/상담/캠페인 정보가
채널별로 단절되지 않는가?
```

### ANALYSIS

필요한 설계 관점은 다음과 같다.

- 채널 공통 고객 식별
- 공통 Context
- 채널 간 정보 전달
- 채널별 중복 서비스 최소화
- 서비스 API 표준화
- 세션/인증 연속성

### 실패하면 생기는 증상 (ANALYSIS)

- 채널마다 고객 식별자·마스터가 달라 동일 고객이 여러 명처럼 보임
- A채널 상담 내용이 B채널에서 보이지 않음
- 같은 상품/한도 정보가 채널별 화면마다 다름
- 채널마다 비슷한 API·화면을 중복 개발

후속 설계의 **합격선 초안:** “고객이 채널을 바꿔도 동일 Context·동일 기준 정보를 이어서 쓸 수 있다.”

# 7. “고객경험 개선”의 아키텍처적 의미

고객경험 개선은 단순 화면 디자인보다 넓은 개념이다.

```text
고객 경험
 =
응답속도
 + 정보 일관성
 + 채널 연속성
 + 개인화
 + 장애 최소화
 + 사용 편의성
```

따라서 Application/Runtime 관점에서는 다음이 중요해진다.

- 빠른 응답
- 고객정보 최신성
- 채널별 결과 일관성
- 중복 입력 최소화
- 오류 메시지 일관성
- 장애 시 서비스 연속성

> 위 세부 항목은 **ANALYSIS**다.

고객경험은 UI팀만의 과제가 아니다. Application Runtime(응답·오류·Timeout), Data Freshness, Interface 연계 품질이 함께 결정한다.  
따라서 §7의 항목은 **NFR(§27)·운영(§26)·Application Runtime** 문서와 교차 추적해야 한다.

# 8. “사용자 중심 UI/UX”의 아키텍처적 의미

원본은 `사용자 중심 UI/UX`를 명시한다.

이를 아키텍처 관점으로 풀면 다음과 같다.

```text
업무 시스템 구조
       ↓
사용자 작업 흐름
       ↓
화면 / 메뉴 / 조회 / 처리
```

즉 기술 구조가 사용자의 실제 업무를 방해해서는 안 된다.

### 후속 검토 관점

- 화면 일관성
- 공통 UI Component
- 역할 기반 화면
- 접근성
- 사용자 작업 단계 최소화
- 반응형 또는 채널별 UI 전략

### UI/UX와 백엔드 경계 (ANALYSIS)

```text
UI/UX 표준이 담당
  └─ 화면 패턴, 컴포넌트, 접근성, 작업 단계

Application / Data가 담당
  └─ 조회 API 일관성, 오류코드, 응답시간, 데이터 의미 통일
```

화면만 바꿔 “사용자 중심”을 달성했다고 보기 어렵다.  
**동일 업무·동일 의미의 데이터가 동일 API/조회 경로로 제공되는가**가 아키텍처 측 합격 조건이다.

---

# 9. 방향 ② 데이터 기반 의사결정 강화 — 상세 분석

## 9.1 원본 FACT

```text
2. 데이터 기반 의사결정 강화

• 실시간 데이터 수집·활용
• 분석 정보의 적시 제공
• 현업 중심 정보 활용 확대
```

방향 ②의 세 bullet은 각각 **수집 → 제공 → 소비** 단계다. (**ANALYSIS**)

```text
실시간 수집·활용     → 데이터가 플랫폼에 들어온다
분석 정보의 적시 제공 → 의사결정에 쓸 형태로 나간다
현업 중심 활용 확대   → 현업이 실제로 쓴다
```

한 단계라도 비면 “데이터 기반”이 성립하지 않는다.  
특히 수집만 강화하고 현업 소비 경로가 없으면 **저장만 늘고 의사결정은 그대로**인 전형적 실패가 된다.

# 10. 실시간 데이터 수집·활용 구조

원본의 `실시간 데이터 수집·활용`은 차세대 정보계에서 매우 핵심적인 방향이다.

텍스트 구조:

```text
Operational Event / Transaction
          │
          ▼
   Real-time Collection
          │
          ▼
    Data Platform
          │
          ▼
Analysis / Decision / Action
```

### Architecture Implication

- 데이터 최신성 확보
- Batch-only 구조의 한계 보완
- 이벤트/거래 발생 시 빠른 정보계 반영
- 최신 데이터를 활용한 조회·분석

> 구체 기술수단은 현재 장표에 없다. CDC/Kafka 등을 적용할지 여부는 후속 설계에서 확인해야 한다.

### “실시간”을 설계어로 바꾸기 (ANALYSIS)

원본의 “실시간”을 한 가지 기술로 단정하면 안 된다. 후속에서 최소 다음을 구분한다.

| 구분 | 의미 | 설계에 필요한 합의 |
|---|---|---|
| Hard real-time | 밀리초급 제어 | 정보계 일반 목표로는 드묾 |
| Near real-time | 초~수분 지연 | 이벤트/CDC/스트림 후보 |
| Business real-time | 업무가 “지금”으로 느끼는 수준 | SLA·화면·의사결정 주기와 맞춤 |
| Batch 병행 | 대량·정합·이력 | 온라인/분석 부하 격리 |

개요 VISION은 **“배치만으로 부족한 구간이 있다”** 를 선언한다.  
어느 데이터가 몇 초/몇 분 Freshness인지는 **Data/NFR 상세**에서 확정한다.

또한 온라인 조회 성능과 대량 분석이 같은 자원을 다투지 않도록,  
후속 Technical은 **FAST(온라인)와 DEEP(분석) 분리** 여부를 검토한다. (프로젝트 Architecture Vision과 정합)

# 11. “분석 정보의 적시 제공” 상세 해석

이 표현의 핵심은 **분석 자체보다 Timing**이다.

```text
데이터가 있음
      ≠
의사결정에 유효함

적시에 제공되는 데이터
      =
의사결정 가치가 있는 데이터
```

즉 데이터 플랫폼은 다음을 함께 만족해야 한다.

```text
Freshness
Correctness
Availability
Response Time
```

### 후속 NFR 후보

- 데이터 최신성
- 보고서 생성 주기
- BI 응답시간
- 실시간 이벤트 반영 지연
- 분석 데이터 가용성

# 12. “현업 중심 정보 활용 확대” 상세 해석

원본의 `현업 중심 정보 활용 확대`는 분석을 IT 전용 영역에 가두지 않는다는 의미다.

```text
IT 중심 정보 생산
        ↓
현업 사용자 직접 활용
```

### 구조적 의미

- 현업용 BI
- 업무화면 내 정보 제공
- 통합 조회
- Self-Service 분석 가능성
- 의사결정과 실행의 연결

> `Self-Service BI`는 원본 문구에서 직접 나오지 않으며 **ANALYSIS 예시**다.

### 현업 활용이 “확대”되려면 필요한 최소 조건 (ANALYSIS)

| 조건 | 설명 |
|---|---|
| Persona | 누가 쓰는가 (영업·마케팅·관리자·IT 등) |
| Use Case | 어떤 의사결정/업무에 쓰는가 |
| Access Path | 업무화면 / BI / 리포트 / API 중 어디인가 |
| Trust | 데이터 출처·갱신시각·권한이 보이는가 |
| Action Link | 조회 후 바로 실행(캠페인·상담·승인)으로 이어지는가 |

IT가 만든 리포트가 현업 화면에 안 붙고, 권한·신뢰·실행 연결이 없으면 “활용 확대”는 선언에 그친다.

# 13. 방향 ③ 통합 정보 활용 기반 마련 — 상세 분석

## 13.1 원본 FACT

```text
3. 통합 정보 활용 기반 마련

• 고객·상품·채널 정보 통합
• 통합 조회 기반 마련
• 연계 정보 활용 강화
```

방향 ③은 방향 ①(고객 경험)·②(의사결정)의 **공통 기반**이다. (**ANALYSIS**)

```text
통합되지 않은 정보
   → 채널마다 다른 고객 경험 (방향 ① 실패)
   → 분석·조회 결과가 어긋남 (방향 ② 실패)
```

따라서 통합 정보 기반은 “있으면 좋은 부가기능”이 아니라,  
**앞선 두 방향이 성립하기 위한 전제 인프라**로 읽어야 한다.

# 14. 고객·상품·채널 정보 통합 구조

```text
고객 정보 ─┐
상품 정보 ─┼─▶ Integrated Information
채널 정보 ─┘
                  │
                  ▼
          Unified Business View
```

### 핵심 의미

정보계의 핵심 데이터 객체를 채널 또는 시스템 단위로 분리하지 않고 통합 활용한다는 뜻이다.

### 후속 Architecture Question

- 고객 기준정보는 무엇인가?
- 상품 기준정보는 무엇인가?
- 채널 정보는 어떤 식별체계를 사용하는가?
- 동일 고객이 여러 채널에서 동일하게 식별되는가?
- 데이터 중복/충돌은 어떻게 관리하는가?

### 통합의 단계 (ANALYSIS)

“통합”을 한 번에 물리 DB 병합으로만 해석하면 위험하다. 후속에서 단계를 구분한다.

```text
1) 식별 통합     — 동일 고객/상품/채널을 같은 키로 인식
2) 의미 통합     — 동일 용어·코드·상태값
3) 조회 통합     — 단일/표준 조회 경로 (Unified Query)
4) 저장 통합     — 필요 시 물리 통합·복제·허브 (선택)
```

개요 VISION이 요구하는 최소선은 보통 **1~3**이다.  
4는 비용·소유권·성능 이슈가 크므로 Data Architecture ADR로 결정한다.

---

# 15. “통합 조회 기반 마련” 상세 분석

통합 조회는 다음 구조를 요구한다.

```text
User / Channel
      │
      ▼
Unified Query Service
      │
      ├─ Customer
      ├─ Product
      ├─ Channel
      ├─ Activity
      └─ Analysis
```

### 주의

통합 조회는 다음과 같지 않아야 한다.

```text
화면
 ├─ DB A 직접조회
 ├─ DB B 직접조회
 ├─ DB C 직접조회
 └─ DB D 직접조회
```

이는 강한 결합과 성능문제를 만들 수 있다.

> 위 금지 구조는 **ANALYSIS / Architecture Recommendation**이다.

### 통합 조회 Scope를 정하는 질문 (ANALYSIS)

- 1차 Scope에 넣을 업무/화면은 무엇인가? (전부 한꺼번에가 아님)
- 조회 전용인가, 조회 후 갱신까지 포함하는가?
- 허용 응답시간·동시사용자는? (§27 NFR)
- Source of Truth와 캐시/복제본의 관계는?
- 권한·개인정보 마스킹은 어느 계층에서 하는가?

Scope 없이 “통합 조회 플랫폼”만 만들면 서비스가 난립하고,  
화면 직접 멀티 DB 조회(위의 금지 구조)가 이름만 바꿔 재등장한다.

---

# 16. “연계 정보 활용 강화” 상세 분석

원본은 정보 통합 외에 `연계 정보 활용 강화`를 별도로 제시한다.

이는 내부 정보만이 아니라 **대내/대외/타 시스템 정보까지 업무에 활용**한다는 방향으로 볼 수 있다.

```text
Internal Data
       +
Connected Information
       ↓
Integrated Business Context
```

### 후속 설계 관점

- Interface Catalog
- API/파일/데이터 연계
- 외부기관 정보
- 연계 결과 캐시/저장 여부
- 실시간 vs 배치 연계 기준

### 연계와 통합의 차이 (ANALYSIS)

| 구분 | 초점 | 실패 시 |
|---|---|---|
| 통합 정보 | 내부 고객·상품·채널의 일관된 관점 | 채널·화면마다 다른 “진실” |
| 연계 정보 | 대내외 시스템에서 가져오는 부가 Context | 업무 판단에 외부 정보가 빠지거나 지연 |

연계는 Interface Architecture(§25)와 Timeout·장애격리·추적성 원칙이 함께 필요하다.  
“일단 붙이기”만 하면 통합 조회·의사결정의 신뢰가 연계 장애에 끌려간다.

# 17. 방향 ④ 유연하고 안정적인 운영체계 확보 — 상세 분석

## 17.1 원본 FACT

```text
4. 유연하고 안정적인 운영체계 확보

• 표준화된 구조 마련
• 확장 가능한 플랫폼 기반 확보

```

이 방향은 앞의 1~3번 목표를 실제 운영환경에서 지속 가능하게 만드는 기반이다.

방향 ④의 세 bullet은 **유연성(표준·확장)과 안정성**을 동시에 요구한다. (**ANALYSIS**)

```text
표준화 없이 확장   → 복제된 파편 구조가 커짐
확장 없이 표준만   → 성장·채널 증가를 못 받음
안정성 없이 둘 다  → 장애·배포 때마다 VISION이 멈춤
```

“유연”과 “안정”은 대립처럼 보이지만,  
**표준화된 확장 단위 + 운영 통제**가 둘을 동시에 성립시키는 방법이다.

# 18. “표준화된 구조 마련”의 의미

```text
Project A 방식
Project B 방식
Developer별 방식

       ↓ 제거

Standard Architecture
       │
       ├─ Standard Layer
       ├─ Standard Interface
       ├─ Standard Naming
       ├─ Standard Error
       ├─ Standard Logging
       └─ Standard Operation
```

> 세부 표준 항목은 **ANALYSIS 예시**다.

### 핵심 목적

- 개발 편차 감소
- 운영 편차 감소
- 유지보수성 향상
- 장애 분석 단순화
- 확장 시 동일 패턴 재사용

### 표준이 “마련”된 상태의 최소 정의 (ANALYSIS)

표준 문서 PDF만 있으면 부족하다. 다음이 있어야 “마련”으로 본다.

| 요소 | 내용 |
|---|---|
| Catalog | 표준 항목 목록 (Naming, Layer, Interface, Error, Logging, TX 등) |
| Definition | 항목별 Do/Don't |
| Example | 준수 예시 / 금지 예시 |
| Gate | 리뷰·테스트·정적분석 등 검증 방법 |
| Owner | 표준 소유 조직 |

Catalog 없이 프로젝트마다 표준을 새로 쓰면, 원본의 “표준화된 구조”와 반대 결과가 난다.

# 19. “확장 가능한 플랫폼 기반 확보” 상세 분석

확장성은 단순 서버 증설만 의미하지 않는다.

```text
확장성
 ├─ 사용자 증가
 ├─ 데이터 증가
 ├─ 업무 증가
 ├─ 채널 증가
 ├─ 시스템 연계 증가
 └─ 분석 요구 증가
```

### 필요한 아키텍처 성격

- 모듈화
- 느슨한 결합
- 표준 인터페이스
- 수평 확장 가능한 런타임
- 데이터 분리/확장
- 자원 격리

> 위 항목은 원본의 `확장 가능한 플랫폼 기반`을 구조화한 **ANALYSIS**다.

### 확장 단위를 먼저 정하라 (ANALYSIS)

“확장 가능”을 설계하려면 **무엇을 단위로 늘리는지**를 먼저 합의한다.

| 확장 축 | 예시 단위 | 후속 문서 |
|---|---|---|
| 서비스/앱 | AP/VM/Pod Scale-out | Technical |
| 데이터 | 파티션·샤드·스토리지 | Data / Technical |
| 채널 | 채널 어댑터 추가 | Interface |
| 업무 | 도메인 모듈 추가 | Application |
| 분석 | 분석 클러스터 분리 | Data / Technical |

온라인과 분석이 같은 자원을 키우면 확장이 서로를 방해한다.  
후속에서 **확장 축별 격리**가 VISION의 “유연·확장”과 직결된다.

# 20. “안정적 운영체계 마련” 상세 분석

안정적 운영은 다음 요소를 포함해야 한다.

```text
Availability
Reliability
Monitoring
Recovery
Backup
Change Control
Incident Response
```

### 후속 확인 항목

- HA
- DR
- Backup
- Monitoring
- Logging
- Capacity
- Performance
- Release
- Rollback

> 상세 항목은 **ANALYSIS**이며, 원본에는 `안정적 운영체계 마련`만 명시된다.

### 안정성을 VISION에서 오해하지 않기

이 장표는 HA 제품명을 정하지 않는다. 다만 후속이 비워두면 안 되는 **질문**은 고정한다.

- 가용성 목표는 어디에 수치로 있는가? (SLA/NFR)
- 장애 시 고객 경험(방향 ①)은 어디까지 유지되는가?
- 데이터 Freshness(방향 ②)와 통합 조회(방향 ③)는 장애 시 어떻게 열화(degrade)되는가?
- 배포·롤백이 표준 구조(방향 ④)를 깨지 않는가?

안정 운영은 Technical·Operation만의 주제가 아니라, **4대 방향 전체의 지속 가능성**이다.

# 21. 4대 방향 간 관계

이 장표의 4대 방향은 다음처럼 연결된다.

```text
┌─────────────────────────┐
│ 1. 고객 중심 서비스 강화│
└─────────────┬───────────┘
              │
              ▼
┌─────────────────────────┐
│ 3. 통합 정보 활용 기반  │
└─────────────┬───────────┘
              │
              ▼
┌─────────────────────────┐
│ 2. 데이터 기반 의사결정 │
└─────────────┬───────────┘
              │
              ▼
┌─────────────────────────┐
│ 4. 유연·안정 운영체계   │
└─────────────────────────┘
```

이는 다음 논리를 의미한다.

```text
통합된 정보가 있어야
      ↓
고객 서비스를 개선할 수 있고

실시간 데이터가 있어야
      ↓
빠른 의사결정이 가능하며

표준화·확장·안정 운영이 있어야
      ↓
이 구조를 지속할 수 있다.
```

### 의존 관계로 읽기 (ANALYSIS)

| 방향 | 선행 의존 | 없으면 |
|---|---|---|
| ① 고객 중심 | ③ 통합 정보 + 채널 연계 | 채널별 파편 경험 |
| ② 데이터 기반 | ③ 통합 + 실시간 수집 | 늦은·어긋난 의사결정 |
| ③ 통합 정보 | 식별·의미·조회 기준 | ①②가 구호로 남음 |
| ④ 운영체계 | 표준·확장·안정 | ①②③이 운영에서 무너짐 |

설계 우선순위를 잡을 때 “고객 화면만 먼저” 가면 ③이 비어 재작업이 난다.  
**통합·표준의 뼈대를 먼저 잡고 채널·분석 경험을 얹는 순서**가 VISION 관계도와 맞다.

# 22. VISION → Application Architecture 매핑

| VISION 방향 | Application Architecture 의미 |
|---|---|
| 고객 중심 서비스 | 채널/업무 애플리케이션의 고객 중심 재구성 |
| 실시간 의사결정 | 실시간 데이터 소비 서비스 |
| 통합 정보 활용 | 통합 조회/통합 고객/상품/채널 서비스 |
| 유연·안정 운영 | 표준 Layer/Module/Runtime 구조 |

### 텍스트 그림

```text
Channel
   ↓
Application Service
   ↓
Integrated Business View
   ↓
Data / Interface
```

### Application에서 빠지기 쉬운 것 (ANALYSIS)

- 채널 Context·인증 연속성
- 통합 조회를 호출하는 **표준 Service 경계** (화면→멀티 DB 우회 금지)
- 실시간/분석 결과를 소비하는 Application API
- 오류·Timeout·재처리 등 Runtime 동작원리 (개요 문서 §25.1과 동일 원칙)

Application 매핑은 “모듈 이름 붙이기”가 아니라 **VISION 방향이 런타임에서 지켜지는가**를 묻는 일이다.

# 25. VISION → Interface Architecture 매핑

원본에는 Interface Architecture라는 제목이 직접 나오지 않지만, `채널 간 정보 연계 강화`, `연계 정보 활용 강화`는 인터페이스 설계를 요구한다.

```text
Channel ↔ Application
Application ↔ Data
Application ↔ Internal System
Application ↔ External System
```

### 필요한 원칙

- 표준 Interface
- API/Message/File/Data 구분
- 연계 소유권
- 추적성
- 장애격리

> 위 원칙은 **ANALYSIS**다.

개요 문서(`VISION_개요_아키텍처정의_분석`)에서 Interface가 Scope 3축 밖 GAP으로 남아 있다면,  
본 장표의 “채널 연계·연계 정보 활용”이 **Interface Domain을 정식으로 요구하는 근거**가 된다.  
후속에서 Application에 흡수할지 별도 Domain으로 둘지 ADR로 닫는다.

# 27. VISION → NFR 후보 매핑

이 장표의 VISION을 비기능 요구사항으로 변환하면 다음과 같은 후보가 나온다.

| VISION Keyword | NFR 후보 |
|---|---|
| 실시간 | Freshness / Latency |
| 고객 경험 | Response Time / Availability |
| 적시 제공 | Data SLA / Report SLA |
| 통합 조회 | Query Performance / Consistency |
| 유연성 | Modularity / Changeability |
| 확장성 | Scalability / Capacity |
| 안정성 | Availability / Reliability |
| 표준화 | Conformance |

> 위 NFR 명칭은 원본 VISION을 구현 가능한 품질속성으로 변환한 **ANALYSIS**다.

### NFR 확정 전에 채울 템플릿 (ANALYSIS)

| NFR 후보 | 측정 대상(초안) | 아직 비어 있는 값 |

| Scalability | 확장 단위별 용량 | 기준 부하 |
| Usability | 현업 작업 단계·오류율 | Persona별 |

수치가 비어 있어도 된다. 다만 **어느 문서(NFR/SLA)가 수치의 정식 소유자인지**는 개요 Governance에서 정해야 한다.

# 29. VISION과 기존/차세대 구조의 차이 개념

원본 장표가 직접 AS-IS를 표현하지는 않지만, VISION 관점의 변화 방향은 다음처럼 해석할 수 있다.

```text
분산된 채널 정보
      ↓
채널 간 정보 연계 강화

사후/배치 중심 정보
      ↓
실시간 수집·활용

시스템별 고객/상품/채널 정보
      ↓
통합 정보 활용

개별 구조/개별 운영
      ↓
표준화·확장형 플랫폼·안정 운영
```

> 위 AS-IS 표현은 원본에 직접 명시되지 않은 **ANALYSIS**이며, “개편 방향”을 이해하기 위한 대비 구조다.

### AS-IS를 문서화할 때 주의

원본에 AS-IS 표가 없으므로, 인터뷰·현황 조사 결과를 이 장표에 **FACT처럼 쓰지 말 것**.  
현황은 별도 AS-IS 문서에 두고, 본 장표는 **To-Be 방향**만 고정한다.  
대비가 필요하면 “ANALYSIS 대비”임을 명시한다.

# 30. 핵심 Architecture Principle 도출

VISION에서 다음 Architecture Principle을 도출할 수 있다.

## AP-01 Customer Centric

```text
채널 또는 시스템 중심보다 고객 중심
```

## AP-02 Data Driven

```text
업무 판단은 가능한 한 최신 데이터와 분석정보를 활용
```

## AP-03 Integrated Information

```text
고객·상품·채널 데이터를 통합 관점으로 활용
```

## AP-04 Standardization

```text
개별 구현보다 표준 구조 우선
```

## AP-05 Scalability

```text
업무/사용자/데이터 증가를 구조적으로 수용
```

## AP-06 Operational Stability

```text
운영 안정성은 설계 단계부터 확보
```

> 원칙명(AP-01 등)은 **ANALYSIS / 문서화 제안**이며 원본에 번호로 존재하지 않는다.

### 원칙 사용법 (ANALYSIS)

ADR·설계 리뷰에서 다음처럼 쓴다.

```text
결정 안: …
충돌하는 원칙: AP-0x …
채택 이유 / 기각 이유: …
검증 방법: …
```

원칙이 문서에만 있고 리뷰 질문에 안 나오면, VISION과 구현이 다시 갈라진다.

| 원칙 | 위반 신호 예시 |
|---|---|
| AP-01 | 채널별 고객 화면·마스터가 제각각 |
| AP-02 | 의사결정이 전일 배치 리포트에만 의존 |
| AP-03 | 고객·상품·채널을 화면마다 따로 조립 |
| AP-04 | 프로젝트마다 Layer·오류·로그 규칙이 다름 |
| AP-05 | 증설 시 전체 재배포·강한 결합 |
| AP-06 | 모니터링·복구·배포 롤백이 사후 대응만 |

# 31. Architecture Decision 질문 목록

VISION을 실제 설계 의사결정으로 바꾸기 위해 다음 질문에 답해야 한다.

## 고객 중심

- 고객 식별자는 전 채널에서 일관적인가?
- 채널 간 Context를 어떻게 전달하는가?
- 고객 화면에서 사용하는 정보는 동일한 기준인가?

## 데이터 기반

- 실시간 데이터의 정의는 무엇인가?
- 허용 가능한 데이터 지연은 얼마인가?
- 분석 결과는 어느 화면/업무에서 사용되는가?

## 통합 정보

- 고객·상품·채널 Master는 어디인가?
- 통합 조회의 Source of Truth는 무엇인가?
- 정보 충돌 시 어느 데이터가 우선하는가?

## 운영

- 확장 단위는 무엇인가?
- 장애 시 어느 계층까지 Failover되는가?
- 표준 준수는 어떻게 검증하는가?

### 의사결정 기록 최소 항목 (ANALYSIS)

각 질문에 답할 때 ADR/회의록에 남길 최소 필드:

| 필드 | 내용 |
|---|---|
| 질문 | §31 항목 |
| 선택지 | A/B/C |
| 결정 | 채택안 |
| 근거 | VISION 방향·원칙 번호 |
| 영향 | Application/Data/Technical/Interface |
| 미결 | 후속 확인 |
| 검증 | 시험·리뷰·지표 |

질문만 나열하고 답이 문서에 없으면 VISION 실행이 시작되지 않은 것과 같다.

# 32. 주요 위험과 GAP

| 위험/GAP | 영향 | 후속 필요사항 | 보완 방향 (ANALYSIS) |
|---|---|---|---|
| VISION은 명확하지만 정량 KPI가 없음 | 성공기준 모호 | KPI/NFR 정의 | §33 후보를 NFR/SLA 문서 소유로 이전·수치화 |
| “실시간”의 기준 미정 | 설계 편차 | 초/분 단위 Freshness 정의 | §10의 실시간 유형(Hard/Near/Business) 중 선택 |
| 고객 중심의 데이터 기준 미정 | 채널별 불일치 | Customer 360 기준 | 고객 식별·SoT·Context 전달 ADR |
| 통합 조회 범위 미정 | 조회 서비스 난립 | 통합조회 Scope | 1차 Scope·금지 패턴(§15) 고정 |
| 플랫폼 확장 단위 미정 | 용량설계 모호 | Scale-out 단위 정의 | §19 확장 축표로 Technical 합의 |
| 안정적 운영의 수준 미정 | HA/DR 편차 | Availability/RTO/RPO | SLA와 Operation 문서에 수치 소유 |
| 표준화 범위 미정 | 표준 난립 | Standard Catalog | §18 Catalog+Gate+Owner |
| 현업 중심 활용의 사용자 범위 미정 | BI/UX 설계 불명확 | Persona/Use Case 정의 | §12 Persona·Access Path |
| “지능형”의 범위 미정 | AI/규칙 혼동 | 지능형 기능 Scope | 규칙/스코어링/추천/생성형 포함 여부 ADR |
| Interface Domain 소속 미정 | 채널·연계 책임 공백 | Domain 결정 | Application 흡수 vs 별도 Interface |
| VISION↔개요(3축) Traceability 약함 | 문서 이중 기준 | 개요·본 장표 매핑 | 방향→Application/Data/Technical 추적표 |

### GAP을 방치하면 생기는 실패 패턴

```text
1) 채널 UX만 바꾸고 고객·상품 SoT는 그대로 → 경험 개선 착시
2) 스트림/CDC만 도입하고 Freshness SLA 없음 → “실시간” 논쟁 지속
3) 통합 조회 플랫폼을 먼저 만들고 Scope 없음 → API 난립
4) 표준 PDF만 배포하고 Gate 없음 → 프로젝트별 재해석
5) HA 구성은 있으나 고객경험·데이터 열화 정책 없음 → 장애 시 VISION 붕괴
```

| 방향 | KPI 후보 | 측정 아이디어 (ANALYSIS) |
|---|---|---|
| 고객 중심 | 화면 응답시간, 채널 간 정보 일치율, 고객 작업단계 | P95 응답, 동일 고객 키 일치율, 클릭/입력 수 |
| 데이터 기반 | 데이터 Freshness, 분석정보 제공시간 | 이벤트→반영 지연, 리포트/지표 SLA |
| 통합 정보 | 통합조회 적용률, 데이터 중복 감소율 | 대상 화면 중 통합경로 비율, 중복 마스터 건수 |
| 운영체계 | 가용성, 배포시간, 장애복구시간, 표준준수율 | SLA%, 배포 lead time, RTO, 리뷰 Pass율 |

> KPI는 **ANALYSIS / 제안**이다. 확정 수치·소유 문서는 NFR/SLA에서 관리한다.

### KPI 선정 원칙

- VISION 방향과 **직접 연결**되지 않는 지표는 넣지 않는다.
- 측정 불가 지표(“고객 만족”만 있는 경우)는 대리 지표를 명시한다.
- 방향 ④ 지표 없이 ①~③만 보면, 성공이 **일시적 데모**로 끝날 수 있다.

# 36. 장표 해석 시 유의사항

이 장표는 **VISION / Direction 장표**이므로 구체적인 기술제품이나 상세 구현방식을 직접 지시하지 않는다.

따라서 다음을 이 장표만으로 확정해서는 안 된다.

- 특정 DBMS
- 특정 Kafka/CDC/ETL 제품
- 특정 UI Framework
- 특정 API Gateway
- 특정 서버 사양
- 특정 HA/DR 방식
- 특정 AI/ML 제품
- Freshness·가용성 등의 **확정 수치**
- 통합 조회의 **전체 업무 목록**

원본이 확정하는 것은 **목표와 방향**이다.

```text
무엇을 달성할 것인가?  → 원본 FACT
어떻게 구현할 것인가? → 후속 Architecture Design
성공을 어떻게 볼 것인가? → NFR / KPI / Validation
```

따라서 세부 기술은 이후 Application / Data / Technical / Interface / Runtime Architecture 장표에서 확인해야 한다.

### 해석 시 추가 주의

- “지능형”을 곧바로 생성형 AI로 단정하지 말 것
- “실시간”을 밀리초 Hard real-time으로 단정하지 말 것
- AS-IS 대비 그림(§29)을 원본 FACT로 인용하지 말 것
- 개요 문서의 Technical/Application/Data 3축과 본 장표의 Interface/Operation 언급을 **충돌이 아니라 보완 관계**로 읽을 것 (소속은 ADR)

# 37. 최종 평가

이 장표는 차세대 정보계 개편의 방향을 다음 한 문장으로 요약할 수 있다.

```text
고객 중심 서비스와 통합된 데이터를 기반으로
실시간 의사결정을 지원하며,
표준화·확장성·운영 안정성을 갖춘
지능형 정보계 플랫폼으로 전환한다.
```

전체 Architecture Vision을 다시 그리면 다음과 같다.

```text
                        ┌───────────────────────────┐
                        │     고객 중심 서비스      │
                        │ 채널연계 / UX / 경험개선  │
                        └─────────────┬─────────────┘
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │       통합 정보 기반      │
                        │ 고객 / 상품 / 채널 통합   │
                        └─────────────┬─────────────┘
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │   데이터 기반 의사결정    │
                        │ 실시간 수집 / 분석 / 제공 │
                        └─────────────┬─────────────┘
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │ 유연하고 안정적인 플랫폼  │
                        │ 표준화 / 확장 / 안정운영  │
                        └───────────────────────────┘
```

이 장표의 가장 중요한 아키텍처적 가치는 다음과 같다.

1. **기술 구축 자체가 아니라 고객과 업무 가치를 최상위 목표로 둔다.**
2. **데이터를 사후 보고용이 아니라 실시간 의사결정 수단으로 정의한다.**
3. **고객·상품·채널 정보 통합을 정보계의 핵심 기반으로 정의한다.**
4. **확장성과 안정성을 동시에 요구한다.**
5. **표준화된 플랫폼 구조를 비즈니스 민첩성 확보의 수단으로 본다.**
6. **방향만 선언하지 않고 Application·Data·Technical·Interface·Operation·NFR로 추적할 질문 목록을 남긴다.** (ANALYSIS 보완)
7. **정량 KPI·제품 선정은 후속에 위임하되, 비워 두면 안 되는 GAP을 명시한다.** (ANALYSIS 보완)

### 이 장표의 한계 (명확히)

- 4대 방향의 **실명 시스템·제품·수치**는 없다
- “지능형·실시간”의 **기술 해법**은 없다
- 다만 후속이 채워야 할 **Capability·원칙·Decision·GAP·검증 항목**은 제공한다

후속 설계에서는 반드시 이 VISION이 다음과 같이 추적되어야 한다.

```text
VISION
  ↓
Architecture Principle
  ↓
Target Architecture
  ↓
NFR / KPI
  ↓
Application / Data / Technical / Interface Design
  ↓
Runtime / Operation
  ↓
Verification
```

결론적으로 이 장표는 **차세대 정보계가 어떤 기술을 사용할 것인지보다, 어떤 방향으로 진화해야 하는지를 선언하는 최상위 Architecture Vision**이며, 이후 모든 상세 아키텍처 판단의 기준점으로 사용되어야 한다.
