쉽게 말하면 **모델(Model)은 “실제 시스템을 컴퓨터가 이해할 수 있게 정리한 지도”**입니다.

소스코드는 너무 복잡합니다.

```text
Java 파일
YAML
Mapper XML
SQL
설정
Controller
Handler
Service
DAO
...
```

사람이 전체 소스를 볼 때는 이렇게 생각합니다.

> “아, `mgcoa9001S0`이라는 거래는 Handler를 거쳐 Service로 가고 DAO를 통해 DB를 조회하는구나.”

그런데 컴퓨터는 이런 의미를 자동으로 이해하기 어렵습니다.

그래서 **소스에서 중요한 것만 뽑아서 관계를 정리해 놓는 것**이 Model입니다.

---

예를 들어 실제 소스가 이렇게 있다고 해보겠습니다.

```text
mgcoa9001S0
      ↓
mgcoa9001Handler.java
      ↓
mgcoa9001Facade.java
      ↓
mgcoa9001Service.java
      ↓
mgcoa9001DAO.java
      ↓
mgcoa9001-ORA.xml
      ↓
TB_MG_TX_CONTROL
```

이것이 **실제 Source**입니다.

그런데 Model에서는 이렇게 단순화합니다.

```text
[ServiceId]
mgcoa9001S0
      │
      ▼
[Handler]
mgcoa9001Handler
      │
      ▼
[Facade]
mgcoa9001Facade
      │
      ▼
[Service]
mgcoa9001Service
      │
      ▼
[DAO]
mgcoa9001DAO
      │
      ▼
[Table]
TB_MG_TX_CONTROL
```

바로 이것이 **Architecture Model**입니다.

즉,

> **소스 전체를 복사한 것이 아니라, 아키텍처적으로 중요한 대상과 관계만 뽑아 놓은 것**입니다.

---

자동차로 비유하면 더 쉽습니다.

실제 자동차에는 수만 개의 부품이 있습니다.

```text
자동차 실제 모습

엔진
볼트
배선
센서
ECU
브레이크
타이어
연료펌프
...
```

하지만 정비 매뉴얼에서는 이렇게 그립니다.

```text
엔진
  ↓
변속기
  ↓
구동축
  ↓
바퀴
```

이 그림은 자동차 그 자체가 아닙니다.

**자동차를 이해하기 쉽게 중요한 구조만 표현한 모델**입니다.

NSIGHT도 같습니다.

```text
실제 PDMG Source
        ↓
엄청나게 많은 Java/XML/YAML/SQL

        ↓ 중요한 것 추출

Architecture Model
        ↓

ServiceId
→ Handler
→ Facade
→ Service
→ DAO
→ Mapper
→ Table
```

입니다.

---

그렇다면 왜 굳이 Model을 만드느냐가 중요합니다.

예를 들어 오늘 실제 구조가:

```text
mgcoa9001S0
   ↓
Handler A
   ↓
Service A
   ↓
DAO A
```

였다고 하겠습니다.

Model에는 이것을 기억해 둡니다.

```text
Model

mgcoa9001S0
→ Handler A
→ Service A
→ DAO A
```

그런데 한 달 뒤 개발자가 코드를 바꿨습니다.

```text
실제 Source

mgcoa9001S0
→ Handler A
→ Service B
→ DAO B
```

그러면 컴퓨터가 비교할 수 있습니다.

```text
기존 Model               현재 Source

Service A        ≠       Service B
DAO A            ≠       DAO B

              ↓

          DRIFT 발생
```

이것이 Model을 만드는 가장 큰 이유입니다.

---

그래서 현재 디렉터리를 아주 쉽게 번역하면 이렇습니다.

```text
00-SOURCE
```

는

> **“실제로 소스에 뭐가 있지?”**

입니다.

```text
10-DOCUMENT
```

는

> **“사람에게 설명하면 우리 아키텍처는 어떻게 생겼지?”**

입니다.

```text
20-MODEL
```

은

> **“그 아키텍처를 컴퓨터가 비교할 수 있게 구조화하면 어떻게 생겼지?”**

입니다.

그리고

```text
30-CONFORMANCE
```

는

> **“우리 규칙대로 만들어졌나?”**

입니다.

---

`reference-baseline-draft.json`도 이름을 어렵게 생각할 필요가 없습니다.

제가 오히려 초보자 관점에서는 이름을 이렇게 이해하시는 것을 권합니다.

```text
reference-baseline-draft.json
```

=

```text
현재_아키텍처_지도_초안.json
```

입니다.

즉:

```text
"현재 소스를 조사해 보니까
 우리 시스템은 대충 이렇게 연결되어 있네요."

라는 것을 JSON으로 저장한 파일
```

입니다.

예를 들어:

```json
{
  "serviceId": "mgcoa9001S0",
  "handler": "mgcoa9001Handler",
  "facade": "mgcoa9001Facade",
  "service": "mgcoa9001Service",
  "dao": "mgcoa9001DAO",
  "table": "TB_MG_TX_CONTROL"
}
```

이 JSON을 보고 사람이 아니라 **Agent나 검증 프로그램도 구조를 이해할 수 있게 하는 것**입니다.

NSIGHT Closed Loop에서도 Model 단계는 ServiceId, Handler, Facade, Service, DAO, Mapper, SQL, Table 등의 Entity와 관계를 기계가 읽을 수 있게 만드는 단계로 정의되어 있습니다.

가장 중요한 한 문장만 기억하시면 됩니다.

> **Source는 실제 집이고, Document는 집 설명서이고, Model은 집의 도면입니다.**

```text
실제 집
= SOURCE

집을 글로 설명
= DOCUMENT

방, 문, 전기, 수도의 관계를 도면으로 표현
= MODEL

도면과 실제 집이 같은지 검사
= CONFORMANCE / TEST

도면과 실제 집이 달라짐
= DRIFT
```

그래서 `20-MODEL`은 **새로운 프로그램을 만드는 곳이 아니라, 현재 시스템의 구조를 “도면”으로 만드는 곳**이라고 이해하시면 거의 정확합니다.
