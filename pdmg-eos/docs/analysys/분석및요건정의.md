# 농협상호금융 정보계 EOS 자원관리 시스템 요구사항 정의서

## 1. 도입 전 안내말

본 요구사항은 `NH_상호금융정보계_EOS_자원관리_샘플양식.xlsx`의 다음 8개 관리영역을 분석하여 도출하였다.

| Excel 영역       | 시스템화 대상                       |
| ---------------- | ----------------------------------- |
| `00_Dashboard`   | EOS 현황 통합 Dashboard             |
| `01_EOS관리대장` | EOS 자원 기준정보 및 Lifecycle 관리 |
| `02_위험도평가`  | EOS 위험도 평가                     |
| `03_조치계획`    | Upgrade·Replace·Remove 등 조치계획  |
| `04_예외승인`    | EOS 예외 신청·승인·종료 관리        |
| `05_월간보고`    | 월간 현황 및 경영·PMO 보고          |
| `06_코드기준표`  | 자원·상태·위험·조치 코드 기준정보   |
| `07_점검명령어`  | EOS 현황 조사·자동수집 기준         |

현재 샘플에서 관리대상은 단순 서버에 한정되지 않는다.

```text
채널/단말
GSLB / L4 / Firewall
Apache / Nginx
RHEL
OpenJDK
Tomcat
Spring Boot / Spring Framework / MyBatis
Oracle DB / JDBC Driver
CruzAPIM / MFT
Kafka / CDC
DataStage
BI
SSO / WAF / DB 접근제어
APM / Log Platform
GitLab / Jenkins / Nexus / SonarQube
Log4j / Jackson / Netty
Backup Solution
```

따라서 EOS 시스템의 자원 모델은 서버 중심이 아니라 **제품·소프트웨어·미들웨어·라이브러리·보안장비·운영도구까지 포괄하는 기술자원 Lifecycle 모델**이어야 한다.

# 2. 문서 개요

## 2.1 목적

본 시스템의 목적은 농협상호금융 정보계에서 사용하는 기술자원의 EOS/EOL 현황을 통합 관리하고, EOS 도래에 따른 서비스·보안·운영 위험을 사전에 식별하여 개선계획, 예외승인 및 사후 종료까지 관리하는 것이다.

핵심 목표는 다음과 같다.

```text
무엇을 사용하고 있는가
        ↓
현재 버전은 무엇인가
        ↓
언제 지원이 종료되는가
        ↓
얼마나 위험한가
        ↓
무엇으로 전환할 것인가
        ↓
언제 조치할 것인가
        ↓
즉시 조치하지 못하면 누가 승인했는가
        ↓
실제로 조치가 끝났는가
```

## 2.2 적용범위

EOS 관리 대상은 최소 다음 자원구분을 지원해야 한다.

| 코드      | 자원구분         |
| --------- | ---------------- |
| `CHANNEL` | 채널/단말        |
| `NET`     | 네트워크         |
| `WEB`     | Web Server       |
| `WAS`     | WAS              |
| `OS`      | 운영체제         |
| `JDK`     | Java Runtime     |
| `FMW`     | Framework        |
| `DBMS`    | Database         |
| `MW`      | Middleware       |
| `ETL`     | ETL/Batch        |
| `SEC`     | 보안             |
| `LIB`     | Library          |
| `TOOL`    | 운영·DevOps 도구 |

향후 Backup/DR 등 신규 분류를 코드관리에서 확장 가능해야 한다.

# 3. 문제 정의 및 설계 배경

현재 Excel 관리방식에서는 하나의 자원에 관한 정보가 여러 시트로 분산된다.

```text
EOS 관리대장
   ↓
위험도 평가표
   ↓
조치계획
   ↓
예외승인
   ↓
월간보고
```

이 구조에서는 다음 문제가 발생할 수 있다.

| 문제                            | 시스템 요구                |
| ------------------------------- | -------------------------- |
| 동일 자원정보 중복 입력         | 자원ID 기준 단일 원장 필요 |
| EOS 일자 변경 시 다수 시트 수정 | Lifecycle 정보 중앙관리    |
| 위험도 수기 산정                | 규칙 기반 자동산정         |
| 조치상태와 Dashboard 불일치     | 실시간 집계                |
| 예외기간 만료 누락              | 자동 경보                  |
| 월간보고 수작업                 | 자동 보고서 생성           |
| 벤더 근거 확인 어려움           | 근거자료 관리              |
| 현재 설치버전 조사 반복         | 점검정보 자동·반자동 수집  |

# 6. Lifecycle 관리 요구사항

샘플에서 핵심 Lifecycle 날짜는 세 가지다.

```text
EOS 일자
EOL 일자
계약 종료일
```

이를 별개의 정보로 관리해야 한다.

| ID            | 요구사항                                                                               |
| ------------- | -------------------------------------------------------------------------------------- |
| `EOS-LFC-001` | 제품별 EOS 일자를 관리해야 한다.                                                       |
| `EOS-LFC-002` | 제품별 EOL 일자를 관리해야 한다.                                                       |
| `EOS-LFC-003` | 유지보수 계약 종료일을 별도로 관리해야 한다.                                           |
| `EOS-LFC-004` | EOS/EOL 정보의 출처를 관리해야 한다.                                                   |
| `EOS-LFC-005` | 벤더 Lifecycle 문서 또는 계약서 등 확인자료를 관리해야 한다.                           |
| `EOS-LFC-006` | Lifecycle 정보의 최종 확인일을 관리해야 한다.                                          |
| `EOS-LFC-007` | Lifecycle 정보 확인 담당자를 기록해야 한다.                                            |
| `EOS-LFC-008` | EOS 일자 변경 이력을 보존해야 한다.                                                    |
| `EOS-LFC-009` | 동일 제품·버전을 사용하는 여러 설치자원에 Lifecycle 정보를 공통 적용할 수 있어야 한다. |

특히 `제품 Lifecycle`과 `설치 자원`은 분리하는 것이 필요하다.

```text
Apache Tomcat 8.5.x
      │
      └─ Product Lifecycle
              │
       EOS / EOL / 근거
              │
       ┌──────┴──────┐
       ↓             ↓
싱글뷰 AP        다른 업무 AP
```

# 8. 위험도 평가 요구사항

샘플의 위험평가는 다음 **7개 평가항목**을 사용한다.

```text
업무중요도
운영환경
외부노출
보안취약점
장애영향도
대체난이도
EOS상태
```

각 항목은 1~5점이고 합산하여 총점을 계산한다.

| 위험등급 | 샘플 기준 |
| -------- | --------: |
| Critical | 32점 이상 |
| High     |     26~31 |
| Medium   |     20~25 |
| Low      |   19 이하 |

| ID            | 요구사항                                                     |
| ------------- | ------------------------------------------------------------ |
| `EOS-RSK-001` | 7개 평가항목별 점수를 입력·관리해야 한다.                    |
| `EOS-RSK-002` | 평가항목의 점수범위는 1~5점이어야 한다.                      |
| `EOS-RSK-003` | 평가 총점을 자동 계산해야 한다.                              |
| `EOS-RSK-004` | 총점에 따라 위험등급을 자동 결정해야 한다.                   |
| `EOS-RSK-005` | 위험등급 기준은 관리자가 변경 가능해야 한다.                 |
| `EOS-RSK-006` | 평가의견을 기록할 수 있어야 한다.                            |
| `EOS-RSK-007` | 평가일과 평가자를 기록해야 한다.                             |
| `EOS-RSK-008` | 재평가 이력을 보존해야 한다.                                 |
| `EOS-RSK-009` | Critical 자원은 즉시 개선계획 대상으로 식별해야 한다.        |
| `EOS-RSK-010` | High 자원은 3개월 이내 조치계획 수립 대상으로 관리해야 한다. |

# 21. 샘플 자료에서 확인된 데이터 품질 요구사항

### 21.1 Dashboard 집계 정합성

샘플에는 다음 값이 존재한다.

```text
전체 36
Critical 7
High 28
Medium 1
Low 0
```

위험등급 합계는 36건이다.

그러나 Dashboard의 `위험 상태` 값은 27건으로 별도 표시되어 있다.

따라서 시스템에서는 다음을 명확히 정의해야 한다.

```text
“위험 상태”의 정의
≠ High + Critical인지
≠ 현재상태=위험인 자원인지
```

각 KPI 산정식을 기준정보로 명시해야 한다.

### 21.2 날짜 검증

Dashboard의 `금월 목표조치` 값이 날짜형식 문제로 `1899-12-31`로 표현되는 부분이 있다.

### 21.3 예외기간 검증

샘플의 한 예외건에는 다음과 같은 기간이 있다.


종료일이 시작일보다 빠르므로 시스템에서는 다음 검증이 필수다.

```text

```

### 21.4 EOS와 조치계획 날짜 정합성

목표조치일, EOS일자, 예외기간, 실제완료일 사이의 선후관계를 검증해야 한다.

# 25. 핵심 아키텍처 판단

현재 Excel에서 가장 중요한 설계 단위는 `자원ID`다.

그러나 실제 시스템에서는 이를 다음 세 개로 분리하는 것이 필요하다.

```text
제품
Product
  ↓
제품버전
Product Version
  ↓
실제 설치자원
Resource Instance
```

예를 들면:

```text
Apache Tomcat
      ↓
Tomcat 8.5.x
      ↓
sv-ap-prd-01
sv-ap-prd-02
sv-ap-prd-03
...
```

이 구조가 되어야 EOS 날짜를 한 번 변경했을 때 해당 버전을 사용하는 모든 설치자원의 위험상태와 영향도를 동시에 갱신할 수 있다.

또한 장기적으로는 다음 관계가 필요하다.

```text
EOS Product Version
        ↓
설치 자원
        ↓
서버/WAR
        ↓
업무서비스
        ↓
사용 화면·ServiceId
```

이 단계까지 발전하면 EOS 시스템은 단순 EOS 관리대장이 아니라 **“EOS 발생 시 농협상호금융 정보계의 실제 업무 영향도를 자동 식별하는 기술 Lifecycle 관리 플랫폼”**이 된다.

---

# 26. 시사점

## 핵심 판단

현재 Excel은 이미 EOS 업무의 기본 프로세스를 상당히 잘 정의하고 있다.

따라서 신규 시스템은 Excel 화면을 그대로 Web 화면으로 옮기는 방식보다 다음 구조로 재설계해야 한다.

```text
단일 EOS 자원원장
     ↓
Lifecycle
     ↓
자동 상태판정
     ↓
위험도
     ↓
조치
     ↓
예외
     ↓
검증
     ↓
보고
```

## 주요 위험

가장 큰 위험은 `EOS관리대장`, `위험평가`, `조치계획`, `예외관리`를 각각 독립 메뉴와 독립 데이터로 구현하는 것이다.

모든 영역은 반드시 하나의 `자원ID`와 Lifecycle을 기준으로 연결해야 한다.

## 우선 보완 과제

가장 먼저 확정해야 하는 것은 다음 네 가지다.

```text
1. 자원ID와 Product/Version/Instance 모델
2. EOS 현재상태 산정 Rule
3. 위험점수 산정 Rule
4. 예외 승인 Workflow
```

이 네 가지가 확정되면 화면·서비스·DB 설계가 상당 부분 자연스럽게 결정된다.

# 27. 마무리말

업로드한 샘플을 분석한 결과 EOS 시스템의 1차 성격은 다음과 같이 정의하는 것이 가장 정확하다.

```text
EOS 자원관리 시스템
=
기술자원 원장
+ Product Lifecycle
+ EOS 위험평가
+ 개선계획
+ 예외승인
+ 월간점검
+ 경영/PMO 보고
+ 감사·이력
```

그리고 이후 단계에서 다음을 결합한다.

```text
EOS 관리
+
시스템/업무서비스 자원관계
+
서버/WAS/DB 자동수집
+
장애·변경 영향도
```

이렇게 발전시키는 것이 현재 샘플양식의 목적을 유지하면서도 실제 운영 가능한 EOS 자원관리 플랫폼으로 확장하는 가장 자연스러운 방향이다.
