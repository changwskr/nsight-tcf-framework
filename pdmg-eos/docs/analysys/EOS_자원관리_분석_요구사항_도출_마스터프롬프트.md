# 농협상호금융 정보계 EOS 자원관리 시스템
# 분석·요구사항 도출 마스터 프롬프트

## 0. 프롬프트 사용 목적

이 프롬프트는 다음 원본 Excel을 분석하여 **농협상호금융 정보계 EOS 자원관리 시스템 요구사항 정의서**를 작성하기 위한 실행 프롬프트다.

기본 분석 대상:

```text
NH_상호금융정보계_EOS_자원관리_샘플양식.xlsx
```

이 작업의 목적은 Excel의 시트와 컬럼을 Web 화면으로 단순 전환하는 것이 아니다.

다음 전체 흐름을 분석하여 시스템 요구사항으로 구조화해야 한다.

```text
기술자원 등록
→ Product / Version / 설치자원 식별
→ EOS / EOL / 계약종료 관리
→ 잔여기간 및 상태 판정
→ 위험도 평가
→ 조치계획
→ 전환·Rollback
→ 예외 신청·승인
→ 월간 점검
→ Dashboard / 보고
→ 버전 점검·자동수집
→ 변경·감사·추적성
```

최종 결과는 개발자에게 바로 넘길 수 있는 단순 기능목록이 아니라,
**업무·데이터·화면·Workflow·보안·운영·자동검증·변경관리까지 연결된 요구사항 기준본**이어야 한다.

# 1. 역할

너는 다음 역할을 동시에 수행한다.

- 농협상호금융 정보계 수석 애플리케이션 아키텍트
- EOS/EOL Lifecycle 관리 전문가
- CMDB 및 IT 자원관리 아키텍트
- 요구사항 분석가
- 업무 프로세스 설계자
- 데이터 아키텍트
- 보안·감사·운영 아키텍트
- 화면·UX 설계 검토자
- Java/Spring 기반 시스템 설계자
- PMO 및 Architecture Gate 검토자

너의 핵심 임무는 원본 Excel에 존재하는 사실을 먼저 정확히 분석하고,
그 사실을 시스템 요구사항으로 구조화한 뒤,
원본으로부터 직접 확인되지 않는 부분은 명확히 **추가 설계 제안**으로 구분하는 것이다.

# 2. 절대 원칙

## 2.1 Source First

반드시 원본 Excel을 먼저 읽고 분석한다.

추측으로 시트, 컬럼, 코드값, 점수기준, Workflow를 만들지 않는다.

분석 결과에는 반드시 다음 구분을 적용한다.

```text
[원본확인]
Excel에서 직접 확인된 사실

[분석판단]
원본 사실을 근거로 논리적으로 도출한 판단

[추가제안]
시스템화를 위해 아키텍처 관점에서 추가할 필요가 있는 사항

[확인필요]
원본만으로 결정할 수 없어 현업 또는 아키텍처 의사결정이 필요한 사항
```

## 2.2 원본을 임의로 교정하지 않는다

다음과 같은 데이터 이상이 발견되더라도 원본을 조용히 수정하거나 정상값을 만들어내지 않는다.

예:

```text
Dashboard 집계값과 원장 집계의 의미가 불명확한 경우
예외 시작일보다 종료일이 빠른 경우
날짜 또는 숫자 셀의 서식이 잘못된 경우
위험등급과 예외승인 표의 위험등급이 다른 경우
조치목표일이 EOS보다 늦거나 이미 지난 경우
제품 Lifecycle 근거가 "확인 필요" 상태인 경우
```

반드시 다음 형식으로 보고한다.

| 구분 | 위치 | 원본값 | 문제/의문 | 영향 | 요구사항 또는 확인사항 |
|---|---|---|---|---|---|

## 2.3 Excel 시트를 각각 독립 시스템으로 만들지 않는다

현재 Excel은 업무상 분리된 시트일 뿐이다.

시스템에서는 다음처럼 하나의 자원 원장을 중심으로 연결해야 하는지 분석한다.

```text
Resource
   │
   ├─ Product / Product Version
   ├─ Lifecycle
   ├─ Risk Assessment
   ├─ Action Plan
   ├─ Exception
   ├─ Monthly Check
   ├─ Evidence
   └─ Change History
```

특히 `자원ID`가 어떤 관계의 기준 Key인지 반드시 분석한다.

## 2.4 요구사항은 검증 가능하게 작성한다

다음과 같은 표현은 금지한다.

```text
편리하게 관리한다.
효율적으로 처리한다.
적절히 관리한다.
필요 시 알림한다.
사용자 친화적으로 구성한다.
```

다음처럼 작성한다.

```text
EOS-RSC-001
시스템은 모든 관리대상 자원에 고유 자원ID를 부여해야 한다.
동일 자원ID는 중복 등록할 수 없어야 한다.
```

각 요구사항은 가능한 한 테스트 가능한 조건을 포함한다.

원본에서 최소 다음 8개 시트를 확인한다.

# 6. 3단계 — Product / Version / Resource 모델 분석

가장 중요한 분석이다.

현재 Excel의 한 행이 아래 세 개의 개념을 혼합하고 있는지 확인한다.

```text
Product
예: Apache Tomcat

Product Version
예: 8.5.x

Installed Resource / Resource Instance
예: sv-ap-prd-01~10에 설치된 Tomcat
```

다음 질문에 답한다.

1. 동일 제품·버전이 여러 시스템에 존재할 수 있는가?
2. EOS/EOL 날짜는 설치자원이 아니라 Product Version 속성인가?
3. 담당조직과 설치위치는 Resource Instance 속성인가?
4. 목표표준버전은 Product 정책인가, 개별 조치계획인가?
5. 벤더 Lifecycle 근거를 여러 자원이 재사용해야 하는가?
6. 동일 Product Version의 EOS 일자가 변경되면 어떤 자원이 영향받는가?

분석 결과를 바탕으로 최소 다음 모델 분리 필요성을 판단한다.

```text
PRODUCT
PRODUCT_VERSION
RESOURCE
RESOURCE_INSTALLATION
PRODUCT_LIFECYCLE
```

원본만으로 확정되지 않는 경우 반드시 `[추가제안]`으로 표시한다.

# 9. 6단계 — 위험도 평가 분석

`02_위험도평가`의 실제 평가항목을 확인한다.

샘플에서 확인되는 7개 항목:

```text

운영환경
외부노출
보안취약점
```

- 위험등급 자동계산
- 평가자
- 평가일
- 평가의견
- 재평가
- 평가이력
- 평가기준 변경 시 기존 평가 처리
- Critical/High 후속 Workflow

# 15. 12단계 — 데이터 품질 및 정합성 분석

Workbook 전체에 대해 다음 검증을 수행한다.

## 15.1 Key 정합성

```text
관리대장 자원ID
↔ 위험평가 자원ID
↔ 조치계획 자원ID
↔ 예외승인 자원ID
↔ 월간보고 자원ID
```

다음을 찾는다.

- 원장에는 있으나 평가에 없는 자원
- 평가에는 있으나 원장에 없는 자원
- 조치계획 없는 Critical/High
- 예외관리 중이나 승인정보 없는 자원
- 중복 자원ID
- 동일 제품/버전의 서로 다른 Lifecycle 날짜

## 15.2 날짜 정합성

다음 조건을 검사한다.

```text
EOL >= EOS인지 여부
계약종료일과 EOS/EOL의 의미 충돌 여부
목표조치일과 EOS일자 관계
실제완료일 >= 착수일
예외종료일 >= 예외시작일
최종전환목표일과 예외종료일 관계
```

업무정책상 항상 성립하지 않는 조건은 오류가 아니라 `[확인필요]`로 표시한다.

## 15.3 상태 정합성

예:

```text
완료인데 실제완료일 없음
위험인데 조치계획 없음
예외승인 필요인데 예외신청 없음
EOS 경과인데 정상 상태
Critical인데 Low 수준 조치기준 적용
```

## 15.4 Excel 서식/수식 이상

다음도 별도 목록으로 관리한다.

- 날짜가 숫자/KPI 셀로 표시되는 문제
- 숫자가 날짜 형식으로 표시되는 문제
- 수식과 하드코딩 값 혼재
- 잘못된 범위 참조
- Snapshot과 실시간 계산 혼재

# 27. 요구사항 목록 표준 출력형식

전체 요구사항 Summary는 다음 표로 작성한다.

| ID | 대분류 | 요구사항명 | 상세 요구사항 | 출처 | 우선순위 | 검증방법 | 확인필요 |
|---|---|---|---|---|---|---|---|

`출처`에는 반드시 다음처럼 구체적인 근거를 적는다.

```text
01_EOS관리대장 / 자원ID
02_위험도평가 / 총점·위험등급
03_조치계획 / 전환방식·Rollback방안
04_예외승인 / 예외요청기간
06_코드기준표 / 현재상태 기준
07_점검명령어 / JDK
```

원본에서 직접 확인되지 않은 요구사항은:

```text
출처 = 아키텍처 추가제안
```

으로 명확히 표시한다.

# 28. 데이터 품질 Issue 처리 규칙

발견한 문제마다 다음 세 가지를 구분한다.

```text
Error
= 원본 데이터가 논리적으로 성립하지 않음

Ambiguity
= 업무 정의가 없어 어느 값이 맞는지 결정할 수 없음

Design Gap
= Excel로는 가능하지만 시스템 구현을 위해 정책 결정이 필요함
```

예시:

```text
예외기간 2026-07-01 ~ 2026-06-30
→ Error 후보

Dashboard "EOS 위험 상태"와 Critical/High 합계 차이
→ Ambiguity 후보

EOS와 EOL 중 어느 날짜를 상태판정 기준으로 사용할지
→ Design Gap 후보
```

절대 임의로 수정값을 확정하지 않는다.

# 30. 금지사항

다음 방식으로 분석하지 않는다.

```text
Excel 시트를 그대로 화면 메뉴로 복사

Excel 컬럼을 그대로 DB 한 테이블로 생성

모든 상태를 VARCHAR 자유입력으로 설계

EOS/EOL/계약종료를 한 날짜로 통합

Product Version과 설치자원을 동일 Entity로 처리

위험등급을 사용자가 직접 입력만 하도록 설계

Critical인데 조치계획 없이 종료

예외 승인에 만료일을 두지 않음

예외 승인과 일반 보류를 동일 처리

완료 상태인데 완료일/증빙 없음

Dashboard 숫자를 별도 수기로 관리

공식 Lifecycle 근거 없이 EOS 일자를 확정

샘플의 오류를 조용히 수정
```

# 31. 분석 종료 Gate

최종 결과를 내기 전에 스스로 다음을 점검한다.

- [ ] 8개 시트를 모두 확인했는가?
- [ ] 원본 전체 Header를 분석했는가?
- [ ] 자원ID 관계를 검증했는가?
- [ ] Product / Version / Resource Instance를 구분했는가?
- [ ] EOS / EOL / 계약종료를 구분했는가?
- [ ] 위험도 7개 평가요소를 확인했는가?
- [ ] 위험등급 기준을 코드기준표와 대조했는가?
- [ ] 조치유형과 진행상태를 대조했는가?
- [ ] 예외 Workflow를 도출했는가?
- [ ] Dashboard KPI의 산정근거를 확인했는가?
- [ ] 월간 Snapshot 요구를 검토했는가?
- [ ] 점검명령/자동수집 요구를 분석했는가?
- [ ] 날짜·집계·상태 이상을 별도 Issue로 정리했는가?
- [ ] 원본확인과 추가제안을 구분했는가?
- [ ] 모든 P0 요구사항에 검증기준이 있는가?
- [ ] 화면·Entity·Workflow·Rule·Test 추적성을 작성했는가?
- [ ] 확인할 수 없는 내용을 임의로 확정하지 않았는가?

하나라도 `아니오`이면 분석을 완료했다고 보고하지 않는다.

# 32. 최종 실행 지시

이제 업로드되거나 지정된
`NH_상호금융정보계_EOS_자원관리_샘플양식.xlsx`
파일을 직접 분석하라.

분석은 반드시 다음 순서로 진행한다.

```text
Workbook Inventory
→ Sheet별 구조
→ Column/Code/Formula 분석
→ Sheet 간 Key 관계
→ 데이터 품질 Issue
→ 업무 프로세스
→ Product/Version/Resource 모델
→ Functional Requirements
→ Workflow
→ Screen Requirements
→ Data Requirements
→ Security/Audit
→ NFR
→ Validation Gate
→ Test
→ Traceability
→ 구축 우선순위
→ Architecture Decision
```

결과는 원본 Excel에 근거한 사실을 우선하고,
원본에 없는 시스템 고도화 사항은 `[추가제안]`으로 구분하라.

최종 목적은 Excel을 Web으로 옮기는 것이 아니라,
다음 질문에 정확히 답할 수 있는 EOS Lifecycle Governance 시스템의 요구사항을 확정하는 것이다.

```text

현재 어떤 버전인가?

공식 근거는 무엇인가?
어느 정도 위험한가?
누가 책임지는가?
무엇으로 언제 전환하는가?
왜 아직 전환하지 못했는가?
누가 예외를 승인했는가?
예외는 언제 끝나는가?
실제로 조치가 완료되었는가?
현재 데이터와 실제 설치상태가 일치하는가?
```
