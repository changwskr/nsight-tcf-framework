# 농협상호금융 정보계 EOS 자원관리 시스템
# 화면설계서 작성 마스터 프롬프트

## 0. 프롬프트 사용 목적

이 프롬프트는 농협상호금융 정보계의 **EOS 자원관리 시스템 요구사항**과
원본 Excel 샘플을 분석하여 실제 개발·검토에 사용할 수 있는
**EOS 화면설계서**를 작성하기 위한 실행 프롬프트다.

기본 입력자료는 다음을 우선 사용한다.

```text
1. NH_상호금융정보계_EOS_자원관리_샘플양식.xlsx
2. EOS_자원관리_분석_요구사항_도출_마스터프롬프트.md
3. 위 프롬프트를 통해 작성된 EOS 요구사항 정의서
4. 추가로 제공되는 업무규칙, 데이터모델, 화면표준, 권한정책
```

원본 Excel에는 다음 8개 업무영역이 존재한다.

```text
00_Dashboard
01_EOS관리대장
02_위험도평가
03_조치계획
04_예외승인
05_월간보고
06_코드기준표
07_점검명령어
```

하지만 **Excel 시트 1개를 화면 1개로 단순 변환해서는 안 된다.**

화면은 실제 사용자의 업무 흐름을 기준으로 재구성한다.

```text
현황 파악
→ 위험 대상 식별
→ 자원 상세 확인
→ 위험 평가
→ 조치계획 수립
→ 예외 신청/승인
→ 월간 점검
→ 완료 검증
→ 보고
→ 기준정보/자동수집 관리
```

최종 산출물은 단순 Wireframe이 아니라 다음을 모두 포함하는
**실제 개발 가능한 화면설계서**여야 한다.

```text
화면 목적
+ 사용자/권한
+ 화면 Layout
+ 조회조건
+ Grid/List
+ 상세 Form
+ 버튼
+ 이벤트
+ 입력 Validation
+ 상태전이
+ 업무규칙
+ API/Service 연계
+ 데이터 항목
+ 오류/예외 처리
+ 권한 통제
+ 감사로그
+ 화면 간 Navigation
+ 테스트 시나리오
+ 요구사항 추적성
```

# 1. 역할

너는 다음 역할을 동시에 수행한다.

- 농협상호금융 정보계 수석 애플리케이션 아키텍트
- EOS/EOL Lifecycle 관리 전문가
- IT 자원관리/CMDB 아키텍트
- 업무 요구사항 분석가
- UX/UI 정보구조 설계자
- 기업용 관리시스템 화면설계 전문가
- 데이터 아키텍트
- Java/Spring 기반 백엔드 설계자
- 보안·권한·감사 아키텍트
- 운영·PMO·Architecture Gate 검토자

화면을 예쁘게 그리는 것이 목표가 아니다.

운영자와 담당자가 다음 질문에 빠르게 답할 수 있도록
업무 흐름을 시각적으로 정리하는 것이 목표다.

```text
현재 가장 위험한 자원은 무엇인가?
왜 위험한가?
언제 EOS인가?
누가 담당하는가?
조치계획이 있는가?
목표일까지 완료 가능한가?
예외가 필요한가?
누가 승인했는가?
예외는 언제 종료되는가?
실제 설치버전과 관리대장이 일치하는가?
```

# 2. 화면설계 절대 원칙

## 2.1 Source First

반드시 제공된 Excel과 요구사항 정의서를 먼저 분석한다.

확인되지 않은 데이터를 실제 확정사항처럼 만들지 않는다.

화면설계 내용은 다음 네 가지로 구분한다.

```text
[원본확인]
Excel 또는 요구사항에서 직접 확인된 내용

[설계반영]
확정 요구사항을 화면으로 구현한 내용

[추가제안]
사용성·운영성·아키텍처 관점에서 새로 제안한 내용

[확인필요]
현업/아키텍처 의사결정이 필요한 내용
```

---

## 2.2 Excel Sheet ≠ Screen

다음 방식은 금지한다.

```text
00_Dashboard → 화면1
01_EOS관리대장 → 화면2
02_위험도평가 → 화면3
...
```

사용자의 업무 목적을 중심으로 화면을 재구성한다.

예:

```text
Dashboard
   ↓ Drill-down
EOS 자원 통합조회
   ↓
EOS 자원 상세
   ├─ 기본정보
   ├─ Lifecycle
   ├─ 위험평가
   ├─ 조치계획
   ├─ 예외
   ├─ 점검결과
   └─ 변경이력
```

즉, 여러 Excel 시트의 정보가 **하나의 자원 상세화면에서 Tab으로 통합**될 수 있다.

---

## 2.3 사용자가 목록을 직접 관리하기 쉽게 설계

EOS 자원은 수십~수천 건까지 확대될 수 있다.

따라서 관리화면은 다음 원칙을 사용한다.

```text
상단    : 핵심 조회조건
중앙    : 결과 Grid
우측/하단: 선택 자원 요약
상세    : 별도 상세화면 또는 Drawer
```

다음 형태는 피한다.

```text
한 화면에 26개 컬럼 전부 표시
한 화면에 모든 입력필드 노출
좌우 스크롤을 과도하게 사용
업무 상태가 텍스트 컬럼에 섞여 있음
버튼이 화면 곳곳에 흩어져 있음
```

Grid에는 의사결정에 필요한 핵심 컬럼만 표시하고,
나머지는 상세화면에서 관리한다.

---

## 2.4 “현황 → 원인 → 조치” 흐름을 유지

EOS 화면은 단순 CRUD가 아니다.

화면 이동은 다음 사고 흐름을 따라야 한다.

```text
무엇이 문제인가?
    ↓
왜 문제인가?
    ↓
어느 정도 위험한가?
    ↓
누가 책임지는가?
    ↓
무엇을 언제 할 것인가?
    ↓
예외인가 정상조치인가?
    ↓
완료되었는가?
```

---

## 2.5 위험상태는 시각적으로 즉시 구분

다음 상태는 화면상 명확히 구분한다.

```text
정상
주의
경고
위험
예외
```

위험등급:

```text
Critical
High
Medium
Low
```

단, 화면설계서에서는 특정 색상코드를 임의로 확정하기보다
**Badge/Tag/Status Indicator 사용**을 정의하고,
최종 색상은 UI 디자인가이드가 있으면 그 기준을 적용한다.

Dashboard는 “많은 그래프”가 목적이 아니다.

사용자가 접속 후 30초 안에 다음을 파악해야 한다.

```text

위험한 자원 수
Critical/High
예외 필요
조치 진행중
이번달 처리해야 할 대상
가장 먼저 조치해야 할 자원
어느 영역이 위험한가
```


```text
Product
Vendor

Release Date

확인일
```

# 11. EOS-050 위험도 평가 화면 설계지시

```text
업무중요도

보안취약점
장애영향도
```

각 항목은 1~5점 범위이며,
총점과 위험등급은 자동계산한다.

## 11.1 권장 Layout

```text
┌─────────────────────────────────────────────────────────────┐
│ 자원: EOS-... / Apache HTTP Server / 2.4.x                  │
├─────────────────────────────────────────────────────────────┤
│ 평가항목          점수     평가기준/설명                     │
│ 업무중요도        [4 ▼]    핵심업무 여부                     │
│ 운영환경          [5 ▼]    PROD/DR 여부                      │
│ 외부노출          [5 ▼]    외부/대외 노출 수준               │
│ 보안취약점        [5 ▼]    CVE/패치 위험                     │
│ 장애영향도        [4 ▼]    장애 파급범위                     │
│ 대체난이도        [3 ▼]    변경복잡도                        │
│ EOS상태           [5 ▼]    EOS 경과/잔여기간                 │
├─────────────────────────────────────────────────────────────┤
│ 총점: 31                     위험등급: HIGH                  │
├─────────────────────────────────────────────────────────────┤
│ 평가의견 [                                             ]    │
│ [임시저장] [평가완료] [재평가]                              │
└─────────────────────────────────────────────────────────────┘
```

## 11.2 Validation

```text
각 점수 1~5
총점 사용자 수정 금지
위험등급 사용자 임의수정 금지
평가완료 시 평가의견 필수 여부 검토
Critical/High 완료 시 조치계획 생성 유도
```

```text
EOS-020-EVT-001 조회
EOS-020-EVT-002 초기화
```

# 28. 데이터 품질 Issue를 화면에 반영

원본 샘플에서 다음 사례가 확인되었다.

## 28.1 Dashboard 날짜/숫자 서식 이상

`금월 목표조치`가 `1899-12-31`처럼 날짜로 표시되는 사례가 있다.

따라서 KPI는 데이터타입을 명확히 정의한다.

```text
KPI Count = Number

```


종료일이 빠르면 저장 자체를 차단한다.

## 28.3 Dashboard 위험수치 정의

```text
지금 어떤 조치를 하고 있는가?
목표일은 언제인가?
예외승인은 필요한가?
예외는 언제 만료되는가?
실제 조치는 끝났는가?
관리대장과 실제 설치정보는 일치하는가?
```

최종 산출물은 Markdown 형식의 화면설계서로 작성하며,
각 핵심 화면에는 반드시 **TEXT 기반 UI Mockup**을 포함하라.
