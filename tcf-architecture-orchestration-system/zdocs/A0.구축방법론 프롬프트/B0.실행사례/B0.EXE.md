“사용자의 요청을 NSIGHT Architecture Orchestration Mission으로 정규화하라. 먼저 목표, System Scope, 대상 시스템/업무/ServiceId, 검증 범위, 기대 결과, Runtime 필요 여부를 판단하라. 요청을 QUICK_CHECK / VERTICAL_SLICE / DECISION_REVIEW / RELEASE_VALIDATION 중 하나로 분류하고 필요한 Agent를 선택하라. 각 Agent를 선택한 이유와 실행순서, 필요한 Gate를 작성하고 `MISSION.md`, `RUN-MANIFEST`, `EXECUTION-PLAN`을 생성하라. 확인되지 않은 정보는 UNKNOWN으로 유지하고 추정하지 마라.”

이 명령을 받으면 저는 **바로 소스 분석이나 설계를 시작하지 않습니다.** 먼저 “이 요청을 어떤 방식으로 처리해야 하는가”를 결정하는 **오케스트레이션 준비 단계**를 수행합니다. 실제 Master Prompt도 `USER GOAL → MISSION NORMALIZATION → SYSTEM SCOPE → RUN MANIFEST → TEAM SELECTION → EXECUTION PLAN` 순서를 먼저 수행하도록 정의되어 있습니다.

구체적으로는 아래 순서로 움직입니다.

| 순서 | 제가 하는 일                                              | 결과                                                                |
| ---: | --------------------------------------------------------- | ------------------------------------------------------------------- |
|    1 | 사용자의 실제 요청에서 **목표** 추출                      | 무엇을 확인/설계/검증하려는지                                       |
|    2 | **System Scope** 판별                                     | NSIGHT_TCF / BUSINESS_SERVICE / OM / GATEWAY / PDMG 등              |
|    3 | 대상 **시스템·업무·Component·ServiceId** 식별             | 아는 것은 기록, 모르면 `UNKNOWN`                                    |
|    4 | 검증 깊이 판단                                            | 단순 점검인지 E2E 검증인지                                          |
|    5 | Source/Config/Runtime 자료 가용성 확인                    | 실제 검증 가능한 범위 결정                                          |
|    6 | **Run Type** 판정                                         | QUICK_CHECK / VERTICAL_SLICE / DECISION_REVIEW / RELEASE_VALIDATION |
|    7 | 필요한 Agent 차출                                         | Baseline, Document, Source, Model, Test, Runtime 등                 |
|    8 | 각 Agent의 **선택 이유** 기록                             | 왜 이 Agent가 필요한지                                              |
|    9 | Agent 실행순서와 병렬 가능 작업 결정                      | Execution Plan                                                      |
|   10 | 필요한 Gate 결정                                          | G00~HG90                                                            |
|   11 | `MISSION.md` 작성                                         | Mission 공식화                                                      |
|   12 | `RUN-MANIFEST` 작성                                       | 이번 실행의 ID/Scope/Baseline                                       |
|   13 | `EXECUTION-PLAN` 작성                                     | 누가, 어떤 순서로, 무엇을 만드는지                                  |
|   14 | 그 다음에야 **STEP 00 Source/Baseline Verification** 시작 | 실제 Closed Loop 실행                                               |

즉 내부적으로는 이렇게 됩니다.

```text
사용자의 원래 요청
      ↓
Mission 정규화
      ↓
System Scope
      ↓
Run Type
      ↓
Agent Team
      ↓
Execution Plan
      ↓
Gate Plan
      ↓
MISSION.md
RUN-MANIFEST
EXECUTION-PLAN
      ↓
STEP 00 시작
```

예를 들어 사용자가 실제 요청으로:

> **“TCF Transaction Boundary를 실제 Source와 Runtime 기준으로 검증해줘.”**

라고 했다면 저는 대략 이렇게 판단합니다.

```text
[ARCHITECTURE ORCHESTRATION START]

Mission:
TCF Transaction Boundary를
실제 Source와 Runtime 기준으로 검증

System Scope:
NSIGHT_TCF

Target Component:
TCF / Timeout / Transaction

ServiceId:
UNKNOWN
→ Source에서 대표 ServiceId를 확인해야 함

Validation Scope:
Document
+ Source
+ Configuration
+ Test
+ Runtime Evidence

Runtime Required:
YES

Run Type:
DECISION_REVIEW
또는
VERTICAL_SLICE

Selected Agents:
1. Baseline Agent
2. Document Agent
3. Source Agent
4. Model Agent
5. Code Rule Agent
6. Test Agent
7. Deploy Agent
8. Runtime Evidence Agent
9. Drift Agent
10. GAP/ADR Agent
11. Gate Manager

First Action:
Source/Baseline Verification
```

Master Prompt도 Orchestrator가 목표, Scope, 관심 Component/ServiceId, Source/Runtime 가용성, 의사결정 필요 여부와 성공조건을 먼저 추출하도록 되어 있습니다.

그리고 Agent 선택도 무조건 전부 선택하는 것이 아닙니다.

예를 들어 단순 요청이:

> “Handler가 DAO를 직접 호출하는 소스가 있는지 점검해줘.”

라면:

```text
Run Type
QUICK_CHECK

Selected Agents

Baseline Agent
      ↓
Source Agent
      ↓
Code Rule Agent
      ↓
Gate Manager
```

정도로 줄입니다.

반대로:

> “ServiceId 하나를 화면부터 SQL과 Runtime까지 추적해줘.”

라면:

```text
Run Type
VERTICAL_SLICE

Baseline
  ↓
Document ──┐
           ├→ Model
Source ────┘
  ↓
Code Rule
  ↓
Test
  ↓
Deploy
  ↓
Runtime Evidence
  ↓
Drift
  ↓
GAP/ADR
  ↓
Gate
```

가 됩니다. 첫 Run은 실제로 대표 ServiceId를 E2E로 추적하는 Vertical Slice가 권장되어 있습니다.

중요한 점은 **모르는 값을 제가 임의로 채우지 않는다는 것**입니다.

예를 들어 사용자가 ServiceId를 말하지 않았다면:

```yaml
serviceId: UNKNOWN
```

으로 둡니다.

Branch를 확인할 수 없다면:

```yaml
branch: UNKNOWN
```

Runtime 환경이 없다면:

```yaml
runtime:
  available: false
```

로 둡니다.

그리고 Runtime이 필요한 Mission인데 실행환경이 없다면:

```text
G00~G40
→ 가능한 범위까지 수행

G50
→ HOLD

HG90
→ PASS 금지
```

로 처리합니다. 이것도 현재 Orchestration 규칙에 명시돼 있습니다.

### 실제로 만드는 3개 파일은 이런 역할입니다

**`MISSION.md`**

```text
무엇을 왜 하는가?
어느 시스템인가?
무엇을 검증하는가?
성공조건은 무엇인가?
```

**`RUN-MANIFEST`**

```yaml
runId: ACL-RUN-20260817-001
missionId: MISSION-001
systemScope:
  - NSIGHT_TCF

runType: DECISION_REVIEW

serviceIds:
  - UNKNOWN

sourceAvailable: true
runtimeAvailable: UNKNOWN
```

**`EXECUTION-PLAN`**

```text
01 Baseline Agent
   이유: Source 기준선이 먼저 필요

02 Document Agent
   이유: 기존 Transaction 설계 주장 확인

03 Source Agent
   이유: 실제 TX 구현 확인

04 Model Agent
   이유: Document와 Source 관계 구조화

05 Test Agent
   이유: TX Boundary 검증

06 Runtime Agent
   이유: 실제 Worker/TX 동작 확인

07 Drift Agent
   이유: Model과 Runtime 비교

08 GAP/ADR Agent
   조건: AS-IS != TO-BE인 경우

09 Gate Manager
   최종 판정
```

즉 이 프롬프트의 핵심은 **“작업을 수행하라”가 아니라 “작업을 수행할 팀과 절차를 먼저 설계하라”**입니다.

```text
잘못된 방식

사용자 요청
 ↓
AI가 곧바로 소스 분석
 ↓
결론


현재 방식

사용자 요청
 ↓
Mission 정의
 ↓
Scope 정의
 ↓
Run Type
 ↓
Agent Team
 ↓
Execution Plan
 ↓
Evidence Plan
 ↓
Gate Plan
 ↓
실제 분석 시작
```

그래서 이 명령은 **Architecture Orchestration System의 팀장에게 내리는 첫 번째 명령**이라고 이해하면 가장 정확합니다.
