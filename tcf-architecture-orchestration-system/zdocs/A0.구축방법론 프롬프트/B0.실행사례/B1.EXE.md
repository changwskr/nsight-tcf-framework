“현재 Mission의 System Scope를 기준으로 Repository를 조사하라. Source, Configuration, Document, Test, Runtime Evidence를 분류하고 build/, bin/, .gradle/, target/, logs/, generated/history/duplicate 자료를 현재 Source of Truth에서 분리하라. Branch, Commit, Java/Spring/Gradle 기준, 모듈 목록을 확인하고 Source Inventory와 Config Inventory를 생성하라. 확인할 수 없는 Branch/Commit은 UNKNOWN으로 기록하라. 현재 분석의 기준이 되는 SOURCE-BASELINE.md를 만들고 G00을 PASS / CONDITIONAL PASS / HOLD / REJECT로 판정하라.”

이 명령어로 너는 무엇을 수행하니

이 명령을 받으면 저는 **아키텍처 내용을 본격적으로 분석하기 전에, “이번 분석에서 무엇을 진짜 기준 소스로 사용할 것인가”를 확정하는 작업**을 수행합니다.

즉 이 명령은 `Architecture Orchestration System`의 **STEP 00 — Bootstrap / Source Baseline 단계**입니다. 여기서는 아직 `Document → Model → Code → Test`를 본격 수행하지 않습니다. **그 뒤 단계들이 잘못된 자료를 기준으로 일하지 않도록 Repository를 정리하고 기준선을 만드는 것**이 목적입니다.

| 순서 | 실제 수행 작업                | 제가 확인하는 것                                                      | 만들어지는 결과                           |
| ---: | ----------------------------- | --------------------------------------------------------------------- | ----------------------------------------- |
|    1 | **Mission Scope 읽기**        | 이번 Run이 `NSIGHT_TCF`, PDMG, OM, Gateway 등 어디를 대상으로 하는지  | Scope 확인 결과                           |
|    2 | **Repository Root 확인**      | 실제 분석할 저장소 위치가 어디인지                                    | Repository Root                           |
|    3 | **전체 파일 Inventory**       | Java, XML, YAML, SQL, Gradle, Markdown, Test, Log 등                  | 전체 파일 인벤토리                        |
|    4 | **Source 분류**               | 실제 구현 Java/Resource/Mapper/SQL 등이 무엇인지                      | Source Inventory                          |
|    5 | **Configuration 분류**        | `application.yml`, properties, `server.xml`, Apache 설정, Gradle 등   | Config Inventory                          |
|    6 | **Document 분류**             | Architecture/ADR/Guide/README/Book/History 구분                       | Document Inventory                        |
|    7 | **Test 분류**                 | `src/test`, ArchUnit, Contract, Integration Test 등                   | Test Inventory                            |
|    8 | **Runtime Evidence 분류**     | 로그, Metric, Trace, Runtime DB, Evidence 자료 구분                   | Runtime Inventory                         |
|    9 | **Generated 자료 제외**       | `build/`, `bin/`, `.gradle/`, `target/` 등을 SoT에서 제외             | Exclusion 목록                            |
|   10 | **History/중복자료 분리**     | 과거자료·복제문서·Generated Help 등이 현재 기준으로 섞이지 않게 함    | Reference/History 목록                    |
|   11 | **Git 기준 확인**             | Branch, Commit, Git 여부 확인                                         | `branch`, `commit`                        |
|   12 | **기술 Baseline 확인**        | Java, Spring Boot, Gradle 등의 실제 사용 버전                         | Technology Baseline                       |
|   13 | **모듈 구조 확인**            | `tcf-core`, `tcf-web`, 업무서비스 등 실제 Module 목록                 | Module Inventory                          |
|   14 | **Source of Truth 후보 결정** | 무엇을 1순위 근거로 사용할지                                          | SoT Priority                              |
|   15 | **불확실성 기록**             | 확인하지 못한 Branch/Commit/Version 등을 추정하지 않고 `UNKNOWN` 처리 | Unknown Register                          |
|   16 | **SOURCE-BASELINE 작성**      | 이번 Run의 분석 기준을 공식화                                         | `SOURCE-BASELINE.md`                      |
|   17 | **G00 Gate 판정**             | 다음 Document/Model 단계로 넘어갈 만큼 기준선이 신뢰 가능한가         | `PASS / CONDITIONAL PASS / HOLD / REJECT` |

핵심 흐름은 이렇게 됩니다.

```text
현재 Mission
    │
    ▼
System Scope 확인
    │
    ▼
Repository Root 확인
    │
    ▼
전체 Repository Scan
    │
    ├─ Source
    ├─ Configuration
    ├─ Document
    ├─ Test
    ├─ Runtime Evidence
    └─ Generated / History / Duplicate
           │
           └── 현재 SoT에서 분리
    │
    ▼
Git / Branch / Commit 확인
    │
    ▼
Java / Spring / Gradle 확인
    │
    ▼
Module 구조 확인
    │
    ▼
Source Inventory
Config Inventory
Document Inventory
Test Inventory
Runtime Inventory
    │
    ▼
SOURCE-BASELINE.md
    │
    ▼
G00
```

예를 들어 지금의 `nsight-tcf-framework` 같은 Repository에 적용하면, 단순히 “파일이 있다”를 세는 것이 아니라 **어떤 파일을 현재 사실의 근거로 인정할 것인가**를 판단합니다.

가령 Repository에 아래처럼 있다고 하면:

```text
nsight-tcf-framework/
│
├─ tcf-core/
│   └─ src/main/java/...        ← SOURCE
│
├─ tcf-web/
│   └─ src/main/java/...        ← SOURCE
│
├─ sv-service/
│   ├─ src/main/java/...        ← SOURCE
│   ├─ src/main/resources/
│   │   └─ application.yml      ← CONFIG
│   ├─ src/test/java/...        ← TEST
│   ├─ build/                   ← GENERATED / 제외
│   └─ logs/                    ← RUNTIME DATA
│
├─ zarchitecture/               ← DOCUMENT
├─ zdocs/                       ← DOCUMENT / 시점 확인
├─ ztcfbook/                    ← REFERENCE
├─ .gradle/                     ← GENERATED / 제외
└─ history/                     ← HISTORY
```

저는 이것을 다음처럼 분리합니다.

```text
[SOURCE OF TRUTH 후보]

실제 Source
    tcf-core/src/main/**
    tcf-web/src/main/**
    sv-service/src/main/**
            │
            ▼
현재 Configuration
    application.yml
    Mapper XML
    Gradle
            │
            ▼
현재 Architecture Baseline
            │
            ▼
ADR


[REFERENCE]

zarchitecture
zdocs
Guide
Book


[CURRENT SoT에서 제외]

build/
bin/
.gradle/
target/
generated/
history/
duplicate/
```

이 분리가 매우 중요합니다. 현재 NSIGHT 저장소는 실제로 많은 Markdown과 생성·복제 자료가 함께 존재하기 때문에, 전수점검에서도 **현재 Source of Truth를 그대로 결정하기 어렵다는 문제가 확인된 바 있습니다.**

그리고 이 명령에서 가장 중요한 산출물이 `SOURCE-BASELINE.md`입니다.

예를 들면 이런 내용이 됩니다.

```yaml
---
baseline-id: SOURCE-20260817-001
run-id: ACL-RUN-20260817-001

system-scope:
  - NSIGHT_TCF

repository-root: /workspace/nsight-tcf-framework

git:
  branch: UNKNOWN
  commit: UNKNOWN

technology:
  java: 21
  spring-boot: VERIFIED_FROM_BUILD
  gradle: 8.10.1

source-of-truth:
  priority:
    - actual-source
    - current-configuration
    - approved-architecture-baseline
    - approved-adr
    - latest-design

excluded:
  - build/**
  - bin/**
  - .gradle/**
  - target/**
  - generated/**
  - history/**
  - duplicate/**

runtime-data:
  available: true
  architecture-evidence-qualified: false

verified-at: 2026-08-17
---
```

여기서 중요한 것은 다음처럼 **모르면 그대로 UNKNOWN**으로 둔다는 것입니다.

```text
잘못된 방식

branch:
  main              ← 그냥 추정

commit:
  latest            ← 의미 없음


올바른 방식

branch: UNKNOWN
commit: UNKNOWN
reason:
  현재 제공된 ZIP에는 Git metadata가 없어 확인 불가
```

그리고 G00은 “소스가 완벽한가?”가 아니라 **“다음 Architecture 분석을 신뢰할 수 있는 기준선이 확보됐는가?”**를 판단합니다.

```text
G00 PASS

Repository Root        확인
System Scope           확인
현재 Source            확인
Config                 확인
Generated 분리         완료
Module 구조            확인
Branch/Commit           확인 또는 UNKNOWN 사유 명확
SoT 우선순위           확정
```

일부가 부족하지만 분석은 가능하다면:

```text
G00
CONDITIONAL PASS
```

예를 들어:

```text
Source       확인됨
Config       확인됨
Modules      확인됨
Branch       UNKNOWN
Commit       UNKNOWN

→ 구조분석은 가능
→ Release Evidence는 불가능

G00 = CONDITIONAL PASS
```

반대로 현재 Source와 과거 복제본을 구별할 수 없다면:

```text
G00 = HOLD
```

가 됩니다.

특히 현재 NSIGHT처럼 **Root Gradle baseline이 불완전하거나 여러 시점의 문서가 혼재하는 경우**, Source가 존재한다고 해서 무조건 `PASS`를 주지는 않습니다. 이런 기준선 혼재 문제는 기존 점검에서도 주요 GAP으로 확인됐습니다.

그리고 **이 단계에서는 하지 않는 작업**도 분명합니다.

```text
G00에서는 하지 않음

Architecture Model 생성       X
Handler → DAO 위반판정        X
Transaction 설계 최종판단      X
ADR 확정                      X
Runtime Drift 최종판정         X
HG90 Release                  X
```

그것들은 다음 단계에서 합니다.

```text
G00 Source Baseline
       ↓
G10 Document
       ↓
G20 Model
       ↓
G30 Code
       ↓
G40 Test
       ↓
G50 Runtime
       ↓
...
```

따라서 한 문장으로 정리하면,

> **이 명령을 받으면 저는 Repository를 “읽기 시작하는 것”이 아니라, 앞으로 모든 Agent가 믿고 읽어야 할 Source의 범위와 우선순위를 먼저 확정합니다.**

그리고 최종적으로는:

```text
Repository
     ↓
무엇이 Source인가?
무엇이 Config인가?
무엇이 문서인가?
무엇이 Test인가?
무엇이 Runtime인가?
무엇이 생성물/과거/중복인가?
     ↓
SOURCE-BASELINE
     ↓
G00
     ↓
다음 Agent가 안전하게 작업 시작
```

을 만드는 작업입니다. 이것이 Architecture Orchestration System에서 **첫 번째 품질통제 단계**입니다.
