“현재 Run에서 확보한 Document, Model, Code, Config, Test, Runtime Evidence를 상호 비교하라. Document↔Model, Model↔Code, Model↔Config, Code↔Runtime, Config↔Runtime, Test↔Runtime의 차이를 탐지하라. 각각 expected, actual, sourceEvidence, runtimeEvidence, severity를 기록하라. Evidence가 없는 차이는 FACT로 확정하지 말고 UNKNOWN 또는 Candidate로 남겨라. CRITICAL/HIGH/MEDIUM/LOW로 분류하고 DRIFT-REGISTER와 DRIFT-REPORT를 생성한 뒤 G60을 판정하라.”

이 명령을 받으면 저는 **G00~G50에서 만들어진 모든 결과를 서로 교차 비교해서, “설계한 것·구현한 것·설정한 것·테스트한 것·실제로 실행된 것” 사이의 차이를 찾아내는 작업**을 수행합니다.

즉 G60은 단순 오류검색 단계가 아니라 **Architecture Drift Detection 단계**입니다.

```text
G10 Document
      │
G20 Model
      │
G30 Code / Config
      │
G40 Test
      │
G50 Runtime Evidence
      │
      ▼
     G60
Architecture Drift Detection
```

## G60에서 실제 수행하는 작업

| 순서 | 수행 작업            | 핵심 질문                                              | 결과                                    |
| ---: | -------------------- | ------------------------------------------------------ | --------------------------------------- |
|    1 | 현재 Run 산출물 수집 | 비교할 Evidence가 무엇인가?                            | Evidence Inventory                      |
|    2 | Document↔Model 비교  | 문서의 Architecture가 Model에 정확히 반영됐는가?       | D1 Drift                                |
|    3 | Model↔Code 비교      | Model대로 실제 Source가 구현됐는가?                    | D2 Drift                                |
|    4 | Model↔Config 비교    | 정책 Model과 실제 설정이 같은가?                       | D3 Drift                                |
|    5 | Code↔Runtime 비교    | 작성된 코드가 실제 Runtime에서도 그 경로로 실행되는가? | D4 Drift                                |
|    6 | Config↔Runtime 비교  | 설정값이 실제 Runtime에 적용되고 있는가?               | D5 Drift                                |
|    7 | Test↔Runtime 비교    | Test에서 증명한 동작이 실제 Runtime에서도 동일한가?    | D6 Drift                                |
|    8 | 차이별 Evidence 연결 | 무엇을 근거로 차이라고 판단했는가?                     | Evidence Link                           |
|    9 | 신뢰도 판정          | FACT인가, Candidate인가, UNKNOWN인가?                  | Evidence Status                         |
|   10 | Severity 산정        | 얼마나 위험한 차이인가?                                | CRITICAL/HIGH/MEDIUM/LOW                |
|   11 | Drift Register 생성  | 모든 Drift를 관리 가능한 항목으로 등록                 | `DRIFT-REGISTER`                        |
|   12 | Drift Report 생성    | 전체 Architecture 상태 요약                            | `DRIFT-REPORT`                          |
|   13 | G60 판정             | G70 의사결정 단계로 진행 가능한가?                     | PASS / CONDITIONAL PASS / HOLD / REJECT |

핵심 구조는 다음입니다.

```text
Document
   ↕
Model
   ↕
Code
   ↕
Config
   ↕
Test
   ↕
Runtime

각 층 사이의 차이
        ↓
     DRIFT
        ↓
Evidence
        ↓
Severity
        ↓
GAP / ADR 후보
```

### 1. Document ↔ Model

먼저 G10 문서가 G20 Model에 제대로 반영됐는지 봅니다.

예를 들어 문서에는:

```text
[TO-BE]

ServiceId Timeout
= 3초
```

라고 되어 있는데 Model은:

```yaml
timeoutSeconds: 5
```

라면:

```text
D1 DOCUMENT_MODEL_DRIFT

expected:
3 sec

actual:
5 sec

documentEvidence:
CURRENT-ARCHITECTURE.md

modelEvidence:
timeout-policy.yaml

severity:
HIGH
```

로 등록합니다.

이 경우 아직 실제 Runtime은 관계없습니다.

**문서와 모델 자체가 불일치**한 것입니다.

---

## 2. Model ↔ Code

G20 Model과 G30 Source Map을 비교합니다.

Model:

```text
ServiceId
 ↓
Handler
 ↓
Facade
 ↓
Service
 ↓
DAO
```

실제 Source:

```text
ServiceId
 ↓
Handler
 ├────────→ DAO
 ↓
Facade
```

라면:

```text
D2 MODEL_CODE_DRIFT

expected:
Handler → Facade → Service → DAO

actual:
Handler → DAO 직접 호출

rule:
R-HANDLER-NO-DAO

severity:
HIGH
```

입니다.

이 경우 Architecture Model과 실제 구현이 다릅니다.

---

## 3. Model ↔ Config

NSIGHT에서는 이 비교가 특히 중요합니다.

예를 들어 Model:

```yaml
serviceId: svcoa0001S0
timeout: 3
```

실제 `application.yml`:

```yaml
timeout: 5
```

이면:

```text
D3 MODEL_CONFIG_DRIFT

Expected
3 sec

Actual Config
5 sec
```

입니다.

또는 Model에서는:

```text
Session Strategy
Spring Session JDBC
```

인데 `server.xml`에서는:

```text
DeltaManager
```

가 실제 활성화되어 있다면 상당히 중요한 Drift입니다.

---

## 4. Code ↔ Runtime

이 단계부터 G50 Runtime Evidence가 필요합니다.

예를 들어 Source에서는:

```text
Facade
@Transactional
```

이 확인됐습니다.

그래서 예상 실행 구조가:

```text
Worker
 ↓
Handler
 ↓
Facade
 ↓
TX BEGIN
```

인데 Runtime Evidence가:

```text
Worker
 ↓
TransactionTemplate
 ↓
TX BEGIN
 ↓
Dispatcher
 ↓
Handler
 ↓
Facade
```

라면:

```text
D4 CODE_RUNTIME_DRIFT
```

후보가 됩니다.

다만 이때 중요한 것은 **Runtime Evidence가 실제로 있어야 한다는 것**입니다.

Stack trace도 없고 Transaction Event도 없다면:

```text
Code에서는 Facade TX로 보인다.
하지만 실제 Runtime TX Owner는 확인 불가.

status:
UNKNOWN
```

으로 처리합니다.

이 원칙이 매우 중요합니다.

---

# 5. Config ↔ Runtime

설정파일에 적힌 값과 실제 동작값을 비교합니다.

예:

```text
Config
Timeout = 3초

Runtime
Timeout 발생 = 약 5초
```

이면:

```text
D5 CONFIG_RUNTIME_DRIFT

expected:
3 sec

actual:
5.02 sec

configEvidence:
application.yml

runtimeEvidence:
EVD-TIMEOUT-0082

severity:
HIGH
```

입니다.

이 Drift는 운영에서 특히 중요합니다.

왜냐하면:

```text
파일은 3초인데
실제 서버에서는 5초
```

라는 의미이므로 다음 가능성이 있기 때문입니다.

```text
환경변수 Override
OM Policy Override
다른 application profile
배포 artifact 불일치
설정 reload 실패
잘못된 서버에 배포
```

하지만 G60에서 바로 원인을 단정하지 않습니다.

**차이를 확정하고 원인 후보를 기록**합니다.

---

# 6. Test ↔ Runtime

이것은 Architecture Closed Loop에서 매우 중요한 비교입니다.

예를 들어 G40에서:

```text
Timeout Test
PASS

Expected:
3초 이내 Timeout
```

이었는데 Runtime에서는:

```text
5초 후 Timeout
```

이라면:

```text
D6 TEST_RUNTIME_DRIFT
```

입니다.

즉:

```text
테스트 환경에서는 PASS
        ↓
운영/실행 환경에서는 다름
```

입니다.

이 경우 단순 코드 오류보다 더 심각할 수 있습니다.

```text
Test Config ≠ Runtime Config
Test Build ≠ Deployed Build
환경변수 차이
DB/Network 차이
Artifact Drift
```

등을 의심할 수 있기 때문입니다.

---

# 7. 모든 Drift는 같은 형식으로 기록합니다

예를 들면:

```yaml
driftId: DRIFT-20260817-0042

type: MODEL_CONFIG

systemScope: NSIGHT_TCF

subject:
  type: TimeoutPolicy
  serviceId: svcoa0001S0

expected:
  value: 3
  unit: seconds

actual:
  value: 5
  unit: seconds

sourceEvidence:
  - model: timeout-policy.yaml
  - config: application-sit.yml

runtimeEvidence:
  - EVD-TIMEOUT-0082

status: CONFIRMED

severity: HIGH
```

즉 Drift 하나마다 최소:

```text
무엇이 달랐는가?
expected는 무엇인가?
actual은 무엇인가?
어디서 확인했는가?
Runtime Evidence가 있는가?
얼마나 심각한가?
```

를 기록합니다.

# 8. 가장 중요한 원칙: Evidence가 없으면 FACT가 아닙니다

예를 들어:

```text
Document:
Transaction Owner = Facade

Source:
Facade에 @Transactional 존재

Runtime:
자료 없음
```

이라면 저는 다음처럼 쓰지 않습니다.

```text
[FACT]
Runtime TX Owner = Facade
```

이렇게 씁니다.

```text
[AS-IS SOURCE]
Facade @Transactional 확인

[UNKNOWN]
실제 Runtime TX 시작 위치 확인 불가

[DRIFT CANDIDATE]
Model/Runtime 비교는 Runtime Evidence 확보 후 확정
```

즉:

```text
Evidence 충분
   ↓
CONFIRMED DRIFT

Evidence 일부
   ↓
DRIFT CANDIDATE

Evidence 없음
   ↓
UNKNOWN
```

입니다.

---

# 9. Severity도 기준을 두고 판정합니다

단순 느낌으로 HIGH를 붙이지 않습니다.

| 등급         | 기준 예                                                                                               |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| **CRITICAL** | 보안위반, 데이터 무결성, 잘못된 TX 경계, 운영 중단, Private Key 노출, Critical Architecture Gate 우회 |
| **HIGH**     | Timeout/TX/Session/JWT 정책 불일치, 핵심 ServiceId Trace 불일치, 잘못된 배포 Artifact                 |
| **MEDIUM**   | 문서와 Source 차이, 비핵심 설정 차이, 일부 Trace 누락                                                 |
| **LOW**      | 명칭, 설명, 비운영 영향 문서 Drift                                                                    |

예를 들어:

```text
문서
OM Handler = 24

Source
OM Handler = 25
```

라면 보통:

```text
MEDIUM
```

정도로 볼 수 있습니다.

반면:

```text
Model
JWT Private Key는 Issuer만 보유

Source
Gateway WAR에 Private Key 포함
```

이라면:

```text
CRITICAL
```

후보입니다.

# 10. Drift 유형을 표준화합니다

저라면 G60에서 적어도 다음 6종을 기본 Drift Type으로 관리합니다.

| ID     | Drift Type     | 비교             |
| ------ | -------------- | ---------------- |
| **D1** | DOCUMENT_MODEL | Document ↔ Model |
| **D2** | MODEL_CODE     | Model ↔ Code     |
| **D3** | MODEL_CONFIG   | Model ↔ Config   |
| **D4** | CODE_RUNTIME   | Code ↔ Runtime   |
| **D5** | CONFIG_RUNTIME | Config ↔ Runtime |
| **D6** | TEST_RUNTIME   | Test ↔ Runtime   |

여기에 필요하면:

```text
D7 DOCUMENT_SOURCE
D8 BUILD_DEPLOY
D9 MODEL_RUNTIME
D10 OM_RUNTIME
```

등을 확장할 수 있습니다.

특히 저는 **BUILD_DEPLOY Drift를 추가하는 것이 중요**하다고 봅니다.

예를 들어:

```text
G40에서 테스트한 WAR Hash
abc123

실제 배포된 WAR Hash
xyz999
```

이면 이것은 매우 심각합니다.

```text
테스트한 것 ≠ 배포한 것
```

이기 때문입니다.

# 11. DRIFT-REGISTER를 만듭니다

예:

| Drift ID  | Type           | 대상       | Expected | Actual  | Evidence     | Severity | 상태      |
| --------- | -------------- | ---------- | -------- | ------- | ------------ | -------- | --------- |
| DRIFT-001 | DOCUMENT_MODEL | OM Handler | 24       | 25      | Doc+Source   | MEDIUM   | CONFIRMED |
| DRIFT-002 | MODEL_CONFIG   | Timeout    | 3s       | 5s      | Model+Config | HIGH     | CONFIRMED |
| DRIFT-003 | CODE_RUNTIME   | TX Owner   | Facade   | UNKNOWN | Runtime 없음 | HIGH     | CANDIDATE |
| DRIFT-004 | TEST_RUNTIME   | Timeout    | 3s       | 5s      | Test+Runtime | HIGH     | CONFIRMED |
| DRIFT-005 | BUILD_DEPLOY   | WAR Hash   | abc      | xyz     | Build+Deploy | CRITICAL | CONFIRMED |

이것이 **현재 Architecture의 불일치 원장**입니다.

처럼 보여줍니다.

# 14. G60은 무엇을 판정하나

G60의 핵심 질문은:

> **“Architecture의 각 표현층 사이에 어떤 차이가 존재하는지 충분한 Evidence로 식별했는가?”**

입니다.

여기서 중요한 점은 **Drift가 0이어야 G60 PASS인 것은 아니라는 것**입니다.

G60은 Drift를 **찾는 Gate**이기 때문입니다.

예를 들어:

```text
Drift 12건 발견

모두 Evidence 있음
Severity 분류 완료
Critical 0
GAP/ADR 대상으로 전달 가능

        ↓

G60 PASS
```

가 가능합니다.

반면:

```text
Runtime Evidence 없음
중요 차이의 actual 확인 불가
Critical 후보가 있는데 근거 부족
Source/Model 자체가 불완전
```

이면:

```text
G60 = CONDITIONAL PASS
또는 HOLD
```

입니다.

# 15. G60과 G70의 역할은 반드시 분리합니다

G60에서는 **차이를 찾습니다.**

```text
Expected ≠ Actual
        ↓
DRIFT
```

하지만 아직 해결방법을 확정하지 않습니다.

그것은 G70의 일입니다.

```text
G60
"무엇이 다른가?"
       ↓
DRIFT

G70
"왜 다르며 무엇을 바꿀 것인가?"
       ↓
GAP / ADR / Code Fix / Config Fix / Document Fix
```

예를 들어:

```text
Model Timeout = 3초
Runtime Timeout = 5초
```

G60은:

```text
DRIFT CONFIRMED
HIGH
```

까지만 합니다.

G70에서 비로소:

```text
Case A
Model이 잘못됨
→ Model 수정

Case B
Config가 잘못됨
→ Config 수정

Case C
3초→5초 정책 변경이 승인됨
→ ADR 작성 + Model 변경

Case D
환경별 예외
→ Exception 승인
```

을 결정합니다.

# 16. 지금까지 전체 흐름은 이렇게 됩니다

```text
G00
무엇을 믿을 것인가?
        ↓
SOURCE BASELINE

G10
현재 Architecture는 무엇인가?
        ↓
DOCUMENT BASELINE

G20
기계가 이해할 수 있는가?
        ↓
ARCHITECTURE MODEL

G30
실제 Source와 일치하는가?
        ↓
ARCHITECTURE AS CODE

G40
Test로 증명되는가?
        ↓
ARCHITECTURE AS TEST

G50
실제로 그렇게 동작하는가?
        ↓
RUNTIME EVIDENCE

G60
그 모든 것 사이에
무엇이 다른가?
        ↓
DRIFT DETECTION

G70
그 차이를
어떻게 처리할 것인가?
        ↓
GAP / ADR
```

따라서 **G60은 NSIGHT Architecture Closed Loop의 “비교 엔진”**입니다.

G50까지는 각각의 사실을 수집하는 단계이고, **G60에서 처음으로 Document·Model·Code·Config·Test·Runtime을 한곳에 놓고 “말한 것과 만든 것과 실제 동작한 것이 정말 같은가?”를 계산합니다.**

이 단계가 제대로 작동해야 Architecture가 시간이 지나면서 Source와 Runtime에서 어긋나는 **Architecture Drift**를 자동으로 발견할 수 있습니다.
