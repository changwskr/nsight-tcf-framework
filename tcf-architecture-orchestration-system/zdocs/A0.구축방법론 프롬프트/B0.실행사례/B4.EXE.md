“Architecture Model을 실제 Source와 비교하라. Java, Gradle, YAML, Properties, XML, Mapper XML, SQL, DDL, OM Catalog, Apache/Tomcat 설정을 스캔하라. ServiceId → Handler → Facade → Service → Rule → DAO → Mapper → SQL → Table 경로를 실제 Source에서 추출하라. Model에만 있고 Source에 없는 항목, Source에만 있고 Model에 없는 항목을 Drift Candidate로 등록하라. Handler→DAO 직접 호출 금지, Controller→DAO 금지, ServiceId Unique, Mapper SQL ID Unique, JWT Private Key 위치, Transaction/Timeout 정책 등의 Architecture Rule을 Policy-as-Code 후보로 생성하라. G30을 판정하라.”

이 명령을 받으면 저는 **G20에서 만든 Architecture Model이 실제 Repository의 코드·설정·SQL과 정말 일치하는지를 검증하고, 문서 수준의 아키텍처 규칙을 “실행 가능한 규칙 후보”로 바꾸는 작업**을 수행합니다.

즉 단계 관계는 다음과 같습니다.

```text
G20
Architecture Model
"설계상 이렇게 되어 있어야 한다"
        ↓
G30
Actual Source Inspection
"실제 코드도 정말 그렇게 되어 있는가?"
        ↓
Architecture Rule / Policy-as-Code Candidate
        ↓
G40
실제 Test/Evaluator로 자동 검증
```

현재 NSIGHT에서도 Model과 Code를 연결하는 기반은 존재하지만, Architecture Rule이 실제 자동검증 코드까지 완전히 내려가지 않은 부분이 확인되어 있으므로, G30은 그 간극을 메우는 핵심 단계입니다.

| 순서 | 제가 실제 수행하는 작업             | 확인 내용                                                            | 주요 산출물                        |
| ---: | ----------------------------------- | -------------------------------------------------------------------- | ---------------------------------- |
|    1 | **G20 Model 로딩**                  | 어떤 Entity/Relation/Policy가 기대되는지 확인                        | Expected Architecture              |
|    2 | **Source Scope 고정**               | NSIGHT_TCF / BUSINESS_SERVICE / PDMG 등을 혼합하지 않음              | Scan Scope                         |
|    3 | **Java Source Scan**                | Controller, Handler, Facade, Service, Rule, DAO, Mapper, Client 구조 | Java Inventory                     |
|    4 | **Build Scan**                      | Gradle module, dependency, plugin, Java version                      | Build Map                          |
|    5 | **Configuration Scan**              | YAML/Properties/XML 환경설정                                         | Config Map                         |
|    6 | **Mapper/SQL Scan**                 | Mapper namespace, sqlId, SQL, Table/View 접근                        | Persistence Map                    |
|    7 | **DDL Scan**                        | Table/View/Index 정의                                                | Data Object Map                    |
|    8 | **OM Catalog Scan**                 | ServiceId, Timeout, 거래통제 등 기준정보                             | OM Map                             |
|    9 | **Apache/Tomcat Scan**              | WAR, Context, Port, Connector, Proxy 설정                            | Deployment Map                     |
|   10 | **ServiceId E2E Source Trace 추출** | ServiceId→Handler→Facade→Service→DAO→SQL→Table                       | Source Trace                       |
|   11 | **Model↔Source 비교**               | Model only / Source only / mismatch                                  | Drift Candidate                    |
|   12 | **Architecture Rule 추출**          | Handler→DAO 금지 등                                                  | Rule Catalog                       |
|   13 | **Policy-as-Code 후보 생성**        | ArchUnit/Scanner/Semgrep 등으로 실행 가능한 규칙 정의                | Rule Implementation Map            |
|   14 | **보안/Transaction/Timeout 검사**   | JWT Key, TX owner, Timeout 정책 위치 확인                            | Policy Findings                    |
|   15 | **G30 판정**                        | 실제 Source가 Model과 검증 가능한 수준으로 연결됐는지                | PASS / CONDITIONAL / HOLD / REJECT |

가장 중요한 작업은 실제 Source에서 다음 경로를 복원하는 것입니다.

```text
ServiceId
   ↓ HANDLED_BY
Handler
   ↓ CALLS
Facade
   ↓ CALLS
Service
   ├─ Rule
   ├─ Integration
   └─ DAO
        ↓
      Mapper
        ↓
       SQL
        ↓
    Table / View
```

예를 들어 G20 Model이 이렇게 되어 있다고 가정하겠습니다.

```yaml
serviceId: svcoa0001S0
handler: SvCustomerHandler
facade: SvCustomerFacade
service: SvCustomerService
dao: SvCustomerDao
mapper: SvCustomerMapper
sqlId: selectCustomerSummary
table:
  - CUSTOMER_MASTER
```

G30에서는 이것을 믿고 끝내는 게 아니라 실제 Java와 Mapper를 찾아갑니다.

```text
Source Scan

TransactionDispatcher
      ↓ ServiceId
SvCustomerHandler.java
      ↓
SvCustomerFacade.java
      ↓
SvCustomerService.java
      ↓
SvCustomerDao.java
      ↓
SvCustomerMapper.xml
      ↓
<select id="selectCustomerSummary">
      ↓
CUSTOMER_MASTER
```

그리고 실제 소스가 일치하면:

```text
MODEL
svcoa0001S0
 → SvCustomerHandler
 → SvCustomerFacade
 → SvCustomerService
 → SvCustomerDao
 → selectCustomerSummary
 → CUSTOMER_MASTER

SOURCE
svcoa0001S0
 → SvCustomerHandler
 → SvCustomerFacade
 → SvCustomerService
 → SvCustomerDao
 → selectCustomerSummary
 → CUSTOMER_MASTER

              ↓

MATCH
```

로 기록합니다.

반대로 G20에는:

```text
Model
Service → CustomerDao
```

라고 되어 있는데 실제 코드는:

```java
CustomerHandler
    → CustomerDao
```

처럼 되어 있다면 이것은 중요한 결과입니다.

```text
[MODEL]
Handler
  ↓
Facade
  ↓
Service
  ↓
DAO

       ≠

[SOURCE]
Handler
  ─────────→ DAO

       ↓

DRIFT-CANDIDATE
R-HANDLER-NO-DAO 위반 후보
```

여기서 중요한 표현은 **“위반 확정”보다 우선 “위반 후보”**라는 점입니다. G30은 Source 구조를 추출하고 규칙 후보를 적용하는 단계이며, 실제 자동 Evaluator를 통해 PASS/FAIL을 강제하는 것은 G40이기 때문입니다.

## Model에만 존재하는 것도 찾습니다

예를 들어 G20에는:

```text
CustomerEligibilityRule
```

이 있는데 실제 Source에서는 찾을 수 없다면:

```yaml
driftId: DRIFT-G30-001
type: MODEL_ONLY

entity:
  type: Rule
  name: CustomerEligibilityRule

expected:
  exists: true

actual:
  exists: false

status: CANDIDATE
severity: MEDIUM
```

처럼 기록합니다.

가능성은 여러 가지입니다.

```text
설계는 했지만 구현 안 됨
과거 Class Name
삭제됨
Rename 됨
Model 오류
Source Scope 밖에 존재
```

그래서 바로 “코드 누락”이라고 단정하지 않고 Evidence를 기록합니다.

반대도 찾습니다.

```text
SOURCE

LegacyCustomerService
```

가 실제로 존재하지만 Architecture Model 어디에도 없다면:

```text
SOURCE_ONLY
```

Candidate가 됩니다.

이것이 중요한 이유는 **Shadow Architecture**를 찾기 위해서입니다.

```text
Document/Model에는 없음
        ↓
하지만 Source에는 존재
        ↓
실제 운영에서는 사용
```

되는 코드가 있을 수 있기 때문입니다.

## ServiceId Unique도 검사합니다

예를 들어 실제 Source Scan 결과:

```text
svcoa0001S0
   ├─ SvCustomerHandler
   └─ SvProductHandler
```

가 확인되면:

```text
RULE
R-SERVICEID-UNIQUE

Expected:
ServiceId 1개 → Handler 매핑 1개

Actual:
ServiceId 1개 → Handler 2개

Result:
VIOLATION_CANDIDATE

Severity:
HIGH
```

로 등록합니다.

반대로 ServiceId가 등록되어 있는데 Handler가 하나도 발견되지 않으면:

```text
UNRESOLVED SERVICE ROUTE
```

입니다.

## Mapper SQL ID도 검사합니다

예를 들어:

```xml
<select id="selectCustomer">
```

가 여러 Mapper에서 동일 Namespace 아래 중복되거나 등록 구조가 비정상이라면:

```text
R-MAPPER-SQLID-UNIQUE
```

검사 후보가 됩니다.

그리고 Mapper XML에서 SQL을 분석해서:

```text
Mapper
  ↓
SQL ID
  ↓
SELECT / INSERT / UPDATE / DELETE
  ↓
Table / View
```

관계도 추출합니다.

그래서 최종적으로:

```text
ServiceId
→ Java
→ Mapper
→ SQL
→ DB Object
```

가 하나의 Source Trace로 연결됩니다.

## Transaction 구조도 실제 코드로 확인합니다

예를 들어 Model에:

```text
TransactionPolicy
TX Owner = Facade
```

라고 되어 있다면 실제 Source에서:

```java
@Transactional
public Result inquiry(...) {
```

같은 위치를 조사합니다.

그리고 다음도 함께 봅니다.

```text
TransactionTemplate
PlatformTransactionManager
@Transactional
TransactionInterceptor
Propagation
readOnly
timeout
rollbackFor
```

특히 NSIGHT에서는 이 부분이 매우 중요합니다.

현재 분석 기준에서는 **NSIGHT_TCF와 PDMG의 AS-IS Transaction 구조를 동일하게 취급하면 안 됩니다.** NSIGHT_TCF 주요 거래 경로에서는 Facade의 Spring Transaction/AOP가 확인된 반면, PDMG에서는 Timeout Worker 내부 `TransactionTemplate` 최외곽 TX 구조가 확인된 바 있습니다. 따라서 G30에서는 반드시 `system-scope`를 먼저 고정합니다.

즉 이런 실수를 하지 않습니다.

```text
PDMG Source에서 TransactionTemplate 발견
        ↓

"NSIGHT 전체가 TransactionTemplate 구조다"

        X
```

올바른 처리는:

```text
[PDMG]
TransactionTemplate 확인

[NSIGHT_TCF]
별도 Source Trace 확인

        ↓

각각 AS-IS Model 유지
```

입니다.

## Timeout 정책도 추적합니다

예를 들어:

```text
OM Timeout Policy = 3초
application.yml = 5초
Annotation = 4초
Runtime Context = 3초
```

처럼 여러 위치가 있다면 G30에서는 어떤 코드와 설정이 존재하는지 구조를 만듭니다.

```text
ServiceId
   │
   ▼
TimeoutPolicy
   │
   ├─ OM
   ├─ Config
   ├─ TimeoutContext
   ├─ @Transactional timeout
   └─ TimeoutExecutor
```

아직 어느 값이 실제 Runtime 값인지는 G50에서 최종 검증할 수 있습니다.

G30에서는:

```text
MODEL EXPECTED: 3
CONFIG FOUND: 5

→ MODEL_CONFIG_DRIFT_CANDIDATE
```

를 생성합니다.

## JWT Private Key 위치도 검사합니다

Architecture Rule:

```text
JWT Private Key
= Token Issuer / KMS / HSM boundary only
```

라고 되어 있을 때 Source/Config에서:

```text
private-key.pem
jwt.private-key
PKCS8EncodedKeySpec
KeyPairGenerator
signWith(privateKey)
```

같은 사용 위치를 찾습니다.

정상 후보:

```text
Token Issuer
   ↓
Private Key
```

위험 후보:

```text
Gateway
   ↓
Private Key 존재

또는

Business WAR
   ↓
Private Key 포함

또는

frontend/static/
   ↓
private-key.pem
```

같은 구조입니다.

G30에서는 이것을 **Security Architecture Rule Candidate**로 등록하고 G40 Security Test 대상으로 넘깁니다.

## Apache/Tomcat/WAR 구조도 Source Model에 연결합니다

예:

```text
Apache
  ↓ ProxyPass
Tomcat
  ↓ Context
sv.war
  ↓
sv-service
```

를 추출해서:

```yaml
- from: SV_SERVICE
  relation: DEPLOYED_AS
  to: sv.war

- from: sv.war
  relation: RUNS_ON
  to: TOMCAT-01
```

같은 Deployment Relation을 구성합니다.

그러면 이후 Runtime Evidence에서:

```text
ServiceId
→ WAR
→ Tomcat
→ JVM
→ Thread
```

까지 연결할 수 있습니다.

## Policy-as-Code 후보를 만듭니다

G30의 두 번째 핵심 결과입니다.

문서에:

> Handler는 DAO를 직접 호출하면 안 된다.

라고 써 두는 것만으로 끝내지 않습니다.

다음 단계에서 자동검증할 수 있게 변환합니다.

예:

```yaml
ruleId: R-HANDLER-NO-DAO

description: Handler must not depend directly on DAO

scope:
  - NSIGHT_TCF
  - BUSINESS_SERVICE

source:
  type: Java

selector:
  fromPackage: "*.handler.."
  forbiddenDependency: "*.dao.."

candidateExecutor:
  - ArchUnit
  - JavaParser

severity: HIGH
```

비슷하게:

```text
R-CONTROLLER-NO-DAO
R-SERVICEID-UNIQUE
R-MAPPER-SQLID-UNIQUE
R-JWT-PRIVATE-KEY
R-TX-OWNER
R-TIMEOUT-POLICY
```

등을 생성합니다.

현재 NSIGHT Ontology에도 Handler→DAO 금지, TX Owner 등 Architecture Rule 정의가 있으나 기존 점검에서는 `implemented:false`, `executor: NOT_YET` 형태의 규칙이 확인됐습니다. 그래서 G30의 중요한 목적 중 하나가 바로 **“문서 규칙 → 실행 가능한 규칙 계약”**으로 변환하는 것입니다.

## G30 Gate는 무엇을 판단하는가

질문은 하나입니다.

> **“Architecture Model을 실제 Source에서 검증할 수 있을 정도로 Code Mapping이 확보되었는가?”**

정상적인 구조는:

```text
Model Entity
     ↓
Actual Source
     ↓
Source Evidence
     ↓
Architecture Rule
     ↓
Executable Rule Candidate

     ↓

G30 PASS
```

가 됩니다.

대표적으로 다음을 봅니다.

```text
Critical ServiceId Trace     확보
Model↔Source Mapping         가능
Source-only Critical Entity  없음 또는 설명됨
Model-only Critical Entity   없음 또는 GAP 관리
ServiceId 중복               없음
Core Layer Rule              정의됨
Transaction Policy           위치 식별
Timeout Policy               위치 식별
JWT Key Boundary             위치 식별
Mapper/SQL/Table             추적 가능
```

일부 Rule은 아직 자동화되지 않았지만 Source Mapping 자체는 충분하면:

```text
G30 = CONDITIONAL PASS
```

가 가능합니다.

반대로:

```text
ServiceId→Handler 연결 불가
Module Source 기준 불명확
핵심 Model 대부분 Source에서 찾을 수 없음
Mapper/SQL 추적 불가
System Scope가 섞여 있음
```

이면:

```text
G30 = HOLD
```

입니다.

그리고 여기서도 **하지 않는 작업**이 있습니다.

```text
G30
Actual Source Scan                  O
Model↔Source 비교                   O
Rule Candidate 생성                 O
Source Trace 생성                   O

G40
ArchUnit 실제 실행                  X → 다음 단계
Unit/Integration Test 실제 판정     X
Coverage Gate                       X
Security Test                       X

G50
실제 Runtime Transaction 확인       X
실제 SQL elapsed                    X
Thread/JVM Evidence                 X
```

따라서 지금까지 단계를 가장 간단히 표현하면:

```text
G00
"무엇을 믿을 것인가?"
Source Baseline

       ↓

G10
"현재 Architecture가 무엇인가?"
Document Baseline

       ↓

G20
"Architecture를 기계가 읽을 수 있는가?"
Architecture Model

       ↓

G30
"실제 Code가 그 Architecture와 일치하는가?"
Architecture as Code

       ↓

G40
"그 일치 여부를 자동 Test로 증명할 수 있는가?"
Architecture as Test
```

결국 **G30은 ‘설계 그림’과 ‘실제 소스’가 처음으로 정면으로 만나는 단계**입니다.

여기서부터 NSIGHT Architecture Orchestration System이 단순 문서 관리 시스템이 아니라 **실제 Source를 근거로 Architecture를 통제하는 시스템**이 됩니다.
