“현재 Source Baseline을 기준으로 Requirement, Architecture Document, ADR, Standard, Decision, Guide를 분석하라. 각 주장을 CONFIRMED / FACT / AS-IS / TO-BE / PROPOSED / GAP / DEPRECATED / UNKNOWN으로 분류하라. 과거 문서를 현재 기준으로 자동 승격하지 마라. 문서 주장과 현재 Source/Configuration을 비교하여 불일치 후보를 등록하라. 현재 Architecture의 공식 진입점이 되는 CURRENT-ARCHITECTURE.md, Requirement Register, ADR Register, Decision Register를 생성하고 G10을 판정하라.”

이 명령을 받으면 저는 **G00에서 확정한 Source Baseline을 기준으로, 흩어져 있는 문서들을 “현재 아키텍처 기준”으로 재분류하고 공식 Architecture Baseline 문서로 승격하는 작업**을 수행합니다.

즉 G00이 **“무엇을 믿고 볼 것인가?”**를 정했다면, G10은 **“그 자료들이 현재 아키텍처에 대해 무엇을 주장하고 있으며, 그중 무엇을 공식 기준으로 인정할 것인가?”**를 정하는 단계입니다.

| 순서 | 실제 수행 작업                      | 제가 판단하는 내용                                                           | 주요 결과                               |
| ---: | ----------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------- |
|    1 | **G00 Source Baseline 읽기**        | 이번 Run의 System Scope, Repository, Source/Config 우선순위 확인             | 분석 기준 고정                          |
|    2 | **문서 수집**                       | Requirement, Architecture, ADR, Standard, Decision, Guide 식별               | Document Inventory                      |
|    3 | **문서 상태 분류**                  | 현재/과거/제안/폐기/미확정 구분                                              | Document Classification                 |
|    4 | **문서 내 Architecture Claim 추출** | 각 문서가 실제로 무엇을 주장하는지 문장·표·설정값 단위로 추출                | Architecture Claims                     |
|    5 | **Claim 상태 판정**                 | CONFIRMED / FACT / AS-IS / TO-BE / PROPOSED / GAP / DEPRECATED / UNKNOWN     | Claim Register                          |
|    6 | **Source와 대조**                   | 문서 주장과 Java/Config/Mapper/Gradle 등을 비교                              | Evidence Mapping                        |
|    7 | **문서 간 충돌 탐지**               | 예: 22 Module vs 24 Module, DeltaManager vs JDBC Session                     | Conflict Register                       |
|    8 | **Source와 문서 불일치 탐지**       | 문서 24 Handler vs Source 25 Handler 같은 차이                               | Drift Candidate                         |
|    9 | **Requirement 정리**                | 요구사항 ID, 내용, 출처, 상태, 관련 Architecture 연결                        | Requirement Register                    |
|   10 | **ADR 정리**                        | 승인/제안/폐기 ADR 및 근거 정리                                              | ADR Register                            |
|   11 | **Decision 정리**                   | 이미 확정된 결정과 아직 OPEN인 결정 분리                                     | Decision Register                       |
|   12 | **Current Architecture 구성**       | 현재 공식적으로 읽어야 할 Architecture Entry Point 작성                      | `CURRENT-ARCHITECTURE.md`               |
|   13 | **G10 판정**                        | 현재 Architecture 문서 기준선이 다음 Model 단계로 갈 만큼 신뢰 가능한지 판단 | PASS / CONDITIONAL PASS / HOLD / REJECT |

핵심 흐름은 이렇게 됩니다.

```text
SOURCE-BASELINE.md
        ↓
Requirement / Architecture / ADR
Standard / Decision / Guide 수집
        ↓
문서별 주장(Claim) 추출
        ↓
상태 분류
        │
        ├─ CONFIRMED
        ├─ FACT
        ├─ AS-IS
        ├─ TO-BE
        ├─ PROPOSED
        ├─ GAP
        ├─ DEPRECATED
        └─ UNKNOWN
        ↓
현재 Source / Configuration과 비교
        ↓
문서↔문서 충돌
문서↔Source 불일치
        ↓
Requirement Register
ADR Register
Decision Register
        ↓
CURRENT-ARCHITECTURE.md
        ↓
G10
```

예를 들어 문서에 이런 내용이 있다고 하겠습니다.

```text
"OM에는 24개의 Handler가 존재한다."
```

그런데 현재 Source Baseline에서 실제 코드를 확인했더니:

```text
Om*Handler.java = 25개
```

라면 저는 다음처럼 처리합니다.

```text
문서 Claim:
OM Handler = 24

Source Evidence:
OM Handler = 25

판정:
[AS-IS] 25
[GAP] 문서가 Source보다 뒤처짐

조치:
DRIFT-CANDIDATE 등록
CURRENT-ARCHITECTURE에는 25를 AS-IS로 반영
24라는 과거 주장은 폐기하지 않고 출처와 함께 보존
```

중요한 것은 **문서에 적혀 있다는 이유만으로 사실로 인정하지 않는다는 것**입니다.

또 다른 예로:

```text
문서 A:
Spring Session JDBC 사용

문서 B:
DeltaManager 사용
```

처럼 충돌하면 바로 하나를 선택하지 않습니다.

```text
SESSION STRATEGY

문서 A     Spring Session JDBC
문서 B     DeltaManager
Config     현재 적용값 확인 필요

결과
UNKNOWN / OPEN
```

으로 둡니다.

즉 G10에서는 **“가장 그럴듯한 문서 하나를 고르는 것”이 아니라, 근거 수준을 붙이는 작업**을 합니다.

상태는 이렇게 사용합니다.

| 상태           | G10에서의 의미                                |
| -------------- | --------------------------------------------- |
| **FACT**       | Source/Config 등 객관적 근거로 확인           |
| **CONFIRMED**  | 프로젝트 공식 기준으로 승인된 내용            |
| **AS-IS**      | 현재 구현 상태                                |
| **TO-BE**      | 승인된 목표 구조                              |
| **PROPOSED**   | 아직 승인되지 않은 제안                       |
| **GAP**        | AS-IS와 TO-BE 또는 문서와 Source의 차이       |
| **DEPRECATED** | 더 이상 현재 기준으로 사용하지 않는 과거 기준 |
| **UNKNOWN**    | 현재 Evidence로 확인 불가                     |

그리고 실제로 만드는 가장 중요한 파일이 **`CURRENT-ARCHITECTURE.md`**입니다.

이 파일은 모든 설계서를 합친 거대한 문서가 아니라, **“현재 Architecture를 이해하려면 무엇을 기준으로 읽어야 하는가”를 알려주는 공식 진입점**입니다.

예를 들면:

```markdown
# CURRENT ARCHITECTURE

## 1. Architecture Baseline

- Baseline ID: ARCH-20260817-001
- System Scope: NSIGHT_TCF
- Source Baseline: SOURCE-20260817-001

## 2. Current Runtime Flow

HTTP
→ OnlineTransactionController
→ TCF
→ STF
→ TimeoutExecutor
→ Dispatcher
→ Handler
→ Facade
→ Service
→ DAO/Mapper
→ ETF

## 3. Confirmed Architecture

- ServiceId 기반 Dispatcher
- TCF 공통 진입
- Handler → Facade → Service 구조
- Mapper 기반 DB 접근

## 4. AS-IS

- 현재 Source로 확인된 구현

## 5. TO-BE

- 승인된 목표구조

## 6. Open Decisions

- Session Strategy
- Transaction Boundary
- ...

## 7. Current GAP

- Document ↔ Source
- Model ↔ Source
- ...

## 8. References

- Requirement Register
- ADR Register
- Decision Register
```

그리고 **Requirement Register**는 예를 들어:

| Requirement ID | 요구사항                     | 출처             | 상태      | 관련 ServiceId | Evidence |
| -------------- | ---------------------------- | ---------------- | --------- | -------------- | -------- |
| REQ-001        | 거래 Timeout 제공            | Architecture Doc | CONFIRMED | 공통           | Source   |
| REQ-002        | Handler는 DAO 직접 호출 금지 | Standard         | TO-BE     | 전체           | Rule     |
| REQ-003        | Runtime Evidence 수집        | Closed Loop      | TO-BE     | 전체           | 미구현   |

처럼 만듭니다.

**ADR Register**는:

| ADR ID  | 주제                 | 상태      | 결정        | 근거              | 영향    |
| ------- | -------------------- | --------- | ----------- | ----------------- | ------- |
| ADR-001 | Transaction Boundary | OPEN      | 미확정      | Source 분석 필요  | TCF     |
| ADR-002 | JWT Validation 위치  | CONFIRMED | Gateway/WAR | Security Standard | Gateway |

처럼 구성합니다.

**Decision Register**는 ADR보다 더 넓게, 프로젝트에서 확정된 Architecture 결정과 미결정사항을 관리합니다.

```text
DECISION
  ↓
왜 그렇게 결정했는가
  ↓
어떤 Source/Config에 반영됐는가
  ↓
어떤 Test가 검증하는가
```

까지 연결합니다.

G10 판정 기준도 중요합니다.

```text
G10 PASS
```

가 되려면 최소한:

```text
Current Architecture 진입점 존재
Requirement 출처 확인
ADR/Decision 상태 구분
AS-IS와 TO-BE 분리
중요 문서의 Source 대조 완료
Critical 충돌 없음
UNKNOWN이 관리되고 있음
```

정도가 필요합니다.

예를 들어 문서 일부가 오래됐지만 실제 Source를 기준으로 현재 구조를 확정할 수 있다면:

```text
G10 = CONDITIONAL PASS
```

가 될 수 있습니다.

반대로:

```text
어느 문서가 최신인지 모름
+
Source와 문서가 크게 충돌
+
중요 Decision의 상태를 알 수 없음
+
AS-IS와 TO-BE 구분 불가능
```

이면:

```text
G10 = HOLD
```

입니다.

그리고 이 단계에서 아직 **Architecture Model을 만들지는 않습니다.**

```text
G10에서 하는 것
-------------------------
문서 분석
Claim 분류
Source 대조
Requirement 정리
ADR 정리
Decision 정리
Current Architecture 확정

G10에서 아직 하지 않는 것
-------------------------
Entity/Relation Model 생성      X
JSON Schema 작성                 X
ArchUnit 실행                    X
Runtime Evidence 수집            X
Drift 최종 확정                  X
Baseline Release                 X
```

그것은 다음 G20부터 진행합니다.

따라서 G00과 G10의 차이를 한 문장으로 정리하면:

```text
G00
"무엇을 믿을 것인가?"

        ↓

G10
"그 자료를 근거로 현재 Architecture는 무엇인가?"

        ↓

G20
"그 Architecture를 기계가 읽을 수 있는 Model로 어떻게 표현할 것인가?"
```

즉 이 명령을 받으면 저는 **기존 문서들을 단순 요약하는 것이 아니라, Source Evidence를 이용해 문서의 신뢰도를 판별하고 현재 Architecture의 공식 기준선을 만드는 작업**을 수행합니다.
