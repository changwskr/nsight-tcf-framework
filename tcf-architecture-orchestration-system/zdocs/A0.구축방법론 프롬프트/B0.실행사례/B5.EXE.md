“G30에서 정의한 Architecture Rule을 실행 가능한 Test로 변환하고 수행하라. ArchUnit 또는 Source Scanner로 Layer/Dependency/Package/ServiceId Rule을 검사하고, Contract Test로 Standard Request/Response/JWT/Gateway/OM 계약을 검증하라. Unit, Integration, Security, Timeout/Transaction Policy Test의 존재와 결과를 확인하라. 사람이 임의로 PASS 값을 입력하는 방식은 금지하고 Evaluator → Measured Value → Threshold → Result 구조로 판정하라. Build/Test/Architecture/Security/Traceability Evidence를 생성하고 G40을 판정하라.”

이 명령을 받으면 저는 **G30에서 정의한 “아키텍처 규칙”을 실제로 실행 가능한 테스트로 바꾸고, 그 결과를 증적으로 남긴 뒤 G40 Gate를 판정**합니다.

즉 G30이 **“어떤 규칙을 검사해야 하는가?”**를 정의했다면, G40은 **“그 규칙을 실제로 실행해서 PASS/FAIL을 측정하는 단계”**입니다.

| 순서 | 제가 실제 수행하는 작업        | 확인 내용                                                                                      | 주요 산출물                             |
| ---: | ------------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------------------- |
|    1 | **G30 Rule Catalog 로딩**      | 검사 대상 Architecture Rule 확정                                                               | Rule Set                                |
|    2 | **Rule → Test 유형 매핑**      | ArchUnit / Source Scanner / Contract / Unit / Integration / Security 중 무엇으로 검사할지 결정 | Test Mapping                            |
|    3 | **Build 가능 여부 확인**       | Gradle/Maven/Wrapper/Dependency가 실제 실행 가능한지 확인                                      | Build Evidence                          |
|    4 | **Architecture Test 실행**     | Layer, Package, Dependency, ServiceId 규칙 검사                                                | Architecture Test Report                |
|    5 | **Contract Test 실행**         | Request/Response/JWT/Gateway/OM 계약 검증                                                      | Contract Evidence                       |
|    6 | **Unit Test 확인/실행**        | 핵심 클래스와 정책 테스트 존재 및 결과                                                         | Unit Test Evidence                      |
|    7 | **Integration Test 확인/실행** | TCF→Handler→Service→DB/외부연계 통합 검증                                                      | Integration Evidence                    |
|    8 | **Security Test 실행**         | JWT, Key, 인증/인가, 민감정보 규칙 검증                                                        | Security Evidence                       |
|    9 | **TX/Timeout Policy Test**     | Transaction Boundary와 Timeout 정책 검증                                                       | Policy Test Evidence                    |
|   10 | **Traceability Test**          | ServiceId E2E 연결 완전성 검사                                                                 | Traceability Evidence                   |
|   11 | **Evaluator 실행**             | 실제 측정값 계산                                                                               | Measured Value                          |
|   12 | **Threshold 비교**             | Rule별 기준과 측정값 비교                                                                      | PASS/FAIL                               |
|   13 | **Evidence Hash/Run ID 생성**  | 결과 위변조와 추적성 관리                                                                      | `testRunId`, Evidence                   |
|   14 | **G40 판정**                   | 다음 Runtime 단계로 갈 수 있는지 판단                                                          | PASS / CONDITIONAL PASS / HOLD / REJECT |

핵심 흐름은 다음과 같습니다.

```text
G30
Architecture Rule
     ↓
Executable Test Definition
     ↓
Build
     ↓
┌─────────────────────────┐
│ Architecture Test       │
│ Contract Test           │
│ Unit Test               │
│ Integration Test        │
│ Security Test           │
│ Transaction/Timeout Test│
│ Traceability Test       │
└────────────┬────────────┘
             ↓
         Evaluator
             ↓
     Measured Value
             ↓
         Threshold
             ↓
       PASS / FAIL
             ↓
          Evidence
             ↓
            G40
```

예를 들어 G30에서 이런 규칙을 만들었다고 하겠습니다.

```text
R-HANDLER-NO-DAO

Handler는 DAO를 직접 호출하면 안 된다.
```

G40에서는 이 문장을 다시 읽고 사람이 판단하지 않습니다. 가능하면 ArchUnit 같은 실행 규칙으로 바꿉니다.

개념적으로는:

```java
noClasses()
    .that().resideInAPackage("..handler..")
    .should().dependOnClassesThat()
    .resideInAPackage("..dao..");
```

그리고 실제 Source에 대해 테스트합니다.

결과가:

```text
Handler Classes       : 27
DAO 직접 의존 Handler : 0

Threshold:
0

Measured:
0

Result:
PASS
```

라면 규칙은 PASS입니다.

반대로:

```text
Handler Classes       : 27
DAO 직접 의존 Handler : 2

Threshold:
0

Measured:
2

Result:
FAIL
```

이라면 G40에서 실제 위반으로 확정할 수 있습니다.

여기서 가장 중요한 것이 사용자가 명령에 넣은:

> **Evaluator → Measured Value → Threshold → Result**

구조입니다.

예를 들어:

| Rule                  | Evaluator        |     Measured Value | Threshold | Result   |
| --------------------- | ---------------- | -----------------: | --------: | -------- |
| R-HANDLER-NO-DAO      | ArchUnit         |                  0 |       = 0 | PASS     |
| R-CONTROLLER-NO-DAO   | ArchUnit         |                  1 |       = 0 | **FAIL** |
| R-SERVICEID-UNIQUE    | Source Scanner   |        0 duplicate |       = 0 | PASS     |
| R-MAPPER-SQLID-UNIQUE | XML Scanner      |        3 duplicate |       = 0 | **FAIL** |
| R-JWT-PRIVATE-KEY     | Security Scanner | 1 invalid location |       = 0 | **FAIL** |
| R-TRACE-COMPLETE      | Trace Evaluator  |                93% |     ≥ 95% | **FAIL** |

즉 절대로 이런 방식이면 안 됩니다.

```text
"대충 확인해 보니 괜찮다."

decision = PASS
```

대신:

```text
Rule
 ↓
실제 실행
 ↓
측정값
 ↓
기준값
 ↓
결과
```

여야 합니다.

이 부분이 현재 NSIGHT Harness에서 특히 중요합니다. 기존 점검에서도 Gate rule 자체는 존재하지만 실제 evaluator 구현이 충분하지 않고, 수동 `decision=PASS` 방식으로 우회할 수 있는 GAP이 확인되었습니다.

또 ServiceId Unique는 예를 들어 Source 전체에서 실제 ServiceId 등록을 추출합니다.

```text
Source Scan

svcoa0001S0 → SvCustomerHandler
svcoa0002S0 → SvAccountHandler
svcoa0001S0 → SvLegacyHandler
```

그러면:

```text
R-SERVICEID-UNIQUE

Total ServiceId:
3

Unique:
2

Duplicate:
1

Threshold:
duplicate = 0

Result:
FAIL
```

가 됩니다.

```text

→ Handler
→ Facade
→ Service
→ DAO
→ Mapper
→ SQL
→ Table
```

라면 각 ServiceId마다 실제 완전성을 계산할 수 있습니다.

예:


이렇게 됩니다.

그러면 전체 Traceability Metric을 계산하여 G40 기준과 비교합니다.

```text
       ↓

       ↓
```

```text

```

Transaction/Timeout Test는 특히 NSIGHT에서 중요합니다.

예를 들어 Model과 G30 Source 분석 결과가:

```text
Transaction Owner:
Facade

Timeout:
3 sec
```

라고 되어 있다면 G40에서는 테스트 가능한 범위에서:

```text
@Transactional 적용 여부
Propagation
Rollback
Timeout override
TimeoutContext 전달
Worker Thread 경계
Exception 시 Rollback
```

을 검증합니다.

PDMG라면 별도 Scope에서:

```text
Worker Thread
→ TransactionTemplate
→ TX Begin
→ Dispatcher
```

구조를 검증해야 하고, NSIGHT_TCF와 같은 테스트 규칙을 무조건 적용하지 않습니다.

이것은 프로젝트의 Scope 분리 원칙과 같습니다.

Security Test에서는 예를 들어:

```text
JWT Private Key

Allowed:
Token Issuer / KMS / HSM

Forbidden:
Gateway
Business WAR
Frontend
static resources
Git repository plaintext
```

같은 Rule을 실제 Source/Config Scan 결과와 연결합니다.

예:

```text
Private Key candidate files: 2

Issuer directory: 1
Business WAR resource: 1

Forbidden location count: 1

Threshold: 0

Result: FAIL
```

처럼 판정합니다.

G40에서 중요한 또 하나는 **“테스트가 존재하지 않는다”도 결과라는 것**입니다.

예를 들어:

```text
tcf-jwt

Main Java: 46
Test Java: 0
```

라면:

```text
JWT Unit Test
NOT_EXECUTABLE / MISSING
```

으로 기록하지:

```text
PASS
```

라고 하지 않습니다.

기존 분석에서도 JWT, Gateway, OM 등 핵심 모듈의 테스트 부족이 확인되어 Architecture as Test 단계가 HOLD로 판정된 바 있습니다.

Build 자체도 증적입니다.

예를 들어:

```text
Command:
./gradlew clean test

Exit Code:
0

Source Commit:
a8f27c1

Build ID:
BUILD-20260817-001
```

같은 실제 결과가 있어야 합니다.

만약 Wrapper나 root Gradle baseline이 없어서 실행할 수 없다면:

```text

NOT EXECUTABLE

Reason:
root Gradle build baseline incomplete

HOLD
```

처럼 처리합니다.

즉 **테스트를 실행하지 못했다는 사실을 숨기지 않습니다.**

```text
40-TEST/
│
├─ architecture/
│   ├─ archunit-report.md
│   ├─ layer-rule-result.yaml
│   └─ dependency-rule-result.yaml
│
├─ contract/
│   ├─ request-response-report.md
│   ├─ jwt-contract-report.md
│   ├─ gateway-contract-report.md
│   └─ om-contract-report.md
│
├─ unit/
│   └─ unit-test-report.md
│
├─ integration/
│   └─ integration-test-report.md
│
├─ security/
│   └─ security-test-report.md
│
├─ policy/
│   ├─ transaction-test-report.md
│   └─ timeout-test-report.md
```

특히 `evaluator-result.yaml`은 중요합니다.

예:

```yaml
testRunId: TEST-20260817-001

rules:
  - ruleId: R-HANDLER-NO-DAO
    evaluator: ArchUnit
    measuredValue: 0
    threshold: 0
    operator: EQ
    result: PASS

  - ruleId: R-SERVICEID-UNIQUE
    evaluator: ServiceIdScanner
    measuredValue: 1
    threshold: 0
    operator: EQ
    result: FAIL

  - ruleId: R-TRACE-COMPLETE
    evaluator: TraceabilityEvaluator
    measuredValue: 93
    threshold: 95
    operator: GTE
    unit: percent
    result: FAIL
```

이런 결과를 기반으로 G40을 판정합니다.

G40의 핵심 질문은:

> **“Architecture가 실제 Test로 검증되었고, 그 결과를 객관적 Evidence로 증명할 수 있는가?”**

입니다.

대략 다음 조건이면 PASS입니다.

```text
Build                         PASS
Critical Architecture Rule    PASS
ServiceId Uniqueness          PASS
Critical Contract             PASS
Security Critical             PASS
Transaction/Timeout Critical  PASS
Traceability                  Threshold 충족
Test Evidence                 존재
Evaluator Result              존재
수동 PASS                     없음

                ↓

G40 PASS
```

일부 비핵심 테스트가 빠져 있고 후속 조치가 명확하면:

```text
G40 = CONDITIONAL PASS
```

가 가능합니다.

하지만 다음 같은 경우에는:

```text
Build 실행 불가
Critical Architecture Test 미실행
Security Test 미실행
Transaction Boundary 검증 불가
Evaluator 없음
사람이 PASS 직접 입력
Critical Rule FAIL
```

```text
G40 = HOLD
```

또는 심각한 정책 위반이면 `REJECT`도 가능합니다.

그리고 G40에서도 아직 Runtime은 검증하지 않습니다.

```text
G40
Architecture Test              O
Build/Test Evidence            O
Policy Test                    O
Security Test                  O

G50
실제 Tomcat 동작               X
실제 Thread                    X
실제 SQL elapsed               X
실제 Hikari 상태               X
실제 Transaction Runtime       X
실제 Timeout 발생              X
```

그건 바로 다음 단계 G50의 책임입니다.

따라서 지금까지 단계의 의미를 한 줄씩 연결하면:

```text
G00
무엇을 믿을 것인가?
        ↓
Source Baseline

G10
현재 Architecture는 무엇인가?
        ↓
Document Baseline

G20
Architecture를 기계가 읽을 수 있는가?
        ↓
Architecture Model

G30
실제 Code가 그 Model과 일치하는가?
        ↓
Architecture as Code

G40
그 일치 여부를 실제 Test로 증명할 수 있는가?
        ↓
Architecture as Test

G50
실제 Runtime에서도 그렇게 동작하는가?
```

즉 **G40은 “아키텍처 규칙을 문장에서 테스트 코드와 측정값으로 바꾸는 단계”**입니다.

여기서부터 `Handler는 DAO를 호출하면 안 된다` 같은 문장이 단순 개발 가이드가 아니라 **실제로 위반하면 Gate를 통과하지 못하는 Architecture Policy**가 됩니다.
