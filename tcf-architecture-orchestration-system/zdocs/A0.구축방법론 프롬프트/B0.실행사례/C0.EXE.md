“현재 Run 결과를 최종 Architecture Baseline으로 승격 가능한지 검증하라. Document Baseline, Model Schema, Model↔Source, Architecture Rule, Build, Test, Security, Deployment, Runtime Evidence, Drift, GAP/ADR, Human Approval을 확인하라. Runtime Evidence 없음, Critical GAP OPEN, Critical Drift OPEN, Artifact Hash 없음, 필수 Approval 없음 중 하나라도 있으면 HG90 PASS를 금지하라. 모든 조건을 충족하면 새로운 architectureBaselineId와 architectureModelVersion을 발급하고 BASELINE-RELEASE, Gate Result, Evidence Package를 생성하라. 이전 Baseline은 삭제하지 말고 SUPERSEDED/DEPRECATED 상태로 보존하라.”

이 명령을 받으면 저는 **G00~G80까지의 전체 결과를 마지막으로 다시 검증해서, 이번 Run의 결과를 “새로운 공식 Architecture Baseline”으로 승격해도 되는지 판정**합니다.

즉 HG90은 단순히 마지막 보고서를 만드는 단계가 아니라 **Architecture Closed Loop의 최종 Release Gate**입니다. 앞 단계에서 하나라도 중요한 증적이 빠졌다면 새 Baseline을 발급하지 않습니다. 현재 Orchestration 단계 정의에서도 Runtime Evidence, Critical GAP/Drift, Artifact Hash, Human Approval을 최종 승격의 강제 조건으로 두고 있습니다.

| 순서 | 제가 수행하는 작업     | 핵심 질문                                     | 결과                       |
| ---: | ---------------------- | --------------------------------------------- | -------------------------- |
|    1 | 현재 Run 고정          | 어떤 Run을 Release하려는가?                   | `runId`                    |
|    2 | G00 확인               | Source Baseline이 신뢰 가능한가?              | Source 검증                |
|    3 | G10 확인               | Current Architecture가 확정됐는가?            | Document 검증              |
|    4 | G20 확인               | Model/Schema가 유효한가?                      | Model 검증                 |
|    5 | G30 확인               | Model↔Source가 검증됐는가?                    | Code 검증                  |
|    6 | G40 확인               | Architecture/Test/Security가 실제 PASS했는가? | Test Evidence              |
|    7 | Build 확인             | 검증한 Source가 실제 Artifact가 되었는가?     | Build Evidence             |
|    8 | Deployment 확인        | 해당 Artifact가 실제 배포됐는가?              | Deployment Evidence        |
|    9 | G50 확인               | Runtime Evidence가 확보됐는가?                | Runtime Evidence           |
|   10 | G60 확인               | Critical Drift가 남아 있는가?                 | Drift 상태                 |
|   11 | G70 확인               | Critical GAP/ADR가 해결됐는가?                | GAP/ADR 상태               |
|   12 | G80 확인               | 필수 Human Approval이 유효한가?               | Approval 검증              |
|   13 | Artifact Hash 재확인   | 승인·시험·배포한 Artifact가 동일한가?         | Integrity 검증             |
|   14 | Hard Blocker 검사      | 하나라도 있으면 HG90 PASS 금지                | Release Eligibility        |
|   15 | 새 Baseline ID 발급    | 공식 Architecture 버전 생성                   | `architectureBaselineId`   |
|   16 | 새 Model Version 발급  | Model 공식 버전 생성                          | `architectureModelVersion` |
|   17 | Baseline Release 작성  | 무엇이 새 기준인지 기록                       | `BASELINE-RELEASE`         |
|   18 | Evidence Package 생성  | 승격 근거 전체 패키징                         | Evidence Package           |
|   19 | 이전 Baseline 상태변경 | 삭제하지 않고 이력 보존                       | SUPERSEDED/DEPRECATED      |
|   20 | HG90 최종 판정         | 공식 기준 승격 여부                           | PASS / HOLD / REJECT       |

전체 흐름은 다음과 같습니다.

```text

        ↓
G10 Document Baseline
        ↓
G20 Architecture Model
        ↓
G30 Model ↔ Source
        ↓
G40 Architecture/Test/Security
        ↓
Build
        ↓
Artifact Hash
        ↓
Deployment
        ↓
G50 Runtime Evidence
        ↓
G60 Drift
        ↓
G70 GAP / ADR
        ↓
G80 Human Approval
        ↓
      HG90
        │
        ├─ 조건 충족 → NEW BASELINE
        │
        └─ 조건 미충족 → HOLD / REJECT
```

### 가장 먼저 “Hard Blocker”를 검사합니다

사용자가 준 명령에서 다음 5개는 **하나라도 존재하면 무조건 HG90 PASS를 금지**합니다.

```text
① Runtime Evidence 없음
② Critical GAP OPEN
③ Critical Drift OPEN
④ Artifact Hash 없음
⑤ 필수 Human Approval 없음
```

즉 다음처럼 처리합니다.

| 조건              | 상태     | HG90 영향 |
| ----------------- | -------- | --------- |
| Runtime Evidence  | 없음     | **BLOCK** |
| Critical GAP      | OPEN 1건 | **BLOCK** |
| Critical Drift    | OPEN 1건 | **BLOCK** |
| Artifact Hash     | 없음     | **BLOCK** |
| Required Approval | PENDING  | **BLOCK** |

이 경우 결과는:

```text
HG90 = HOLD
```

입니다.

중요한 것은 다른 항목이 아무리 좋아도 상쇄되지 않는다는 것입니다.

```text
Build PASS
Test PASS
Security PASS
Architecture Rule PASS

하지만

Runtime Evidence 없음

        ↓

HG90 PASS 금지
```

입니다.

## 1. Document Baseline 검증

G10에서 만든:

```text
CURRENT-ARCHITECTURE.md
Requirement Register
ADR Register
Decision Register
```

가 현재 Run 결과와 일치하는지 다시 봅니다.

예를 들어 G70/G80에서 Transaction 정책이 바뀌었는데 `CURRENT-ARCHITECTURE.md`에는 이전 정책이 남아 있으면:

```text
Document Baseline
OUT OF DATE

→ HG90 HOLD
```

입니다.

즉 최종 Baseline은 단순 코드 상태가 아니라:

```text
Document
↔ Model
↔ Code
↔ Config
↔ Test
↔ Runtime
```

이 모두 일치해야 합니다.

## 2. Model Schema와 Semantic Validation 재검증

G20의 모델을 다시 검사합니다.

예:

```text
Architecture Model Schema      PASS
Service Model Schema           PASS
Traceability Schema            PASS
Semantic Validation            PASS
Duplicate ServiceId            0
Critical Orphan                0
```

이어야 합니다.

만약 ADR 승인 후 Model을 수정했는데 Schema Validation을 다시 돌리지 않았다면:

```text
Model changed after validation

→ Revalidation Required
```

입니다.

즉 **과거 PASS를 그대로 재사용하지 않습니다.**

## 3. Model ↔ Source 최종 정합성 확인

예를 들어 최종 Model은:

```text
ServiceId
→ Handler
→ Facade
→ Service
→ DAO
→ Mapper
→ SQL
→ Table
```

인데 Source가 아직:

```text
Handler
→ DAO 직접 호출
```

이라면:

```text
Model ≠ Source

→ Critical/High GAP OPEN
→ HG90 차단
```

할 수 있습니다.

## 4. Architecture Rule 결과를 다시 확인합니다

예:

| Rule                     | Result |
| ------------------------ | ------ |
| Handler→DAO 금지         | PASS   |
| Controller→DAO 금지      | PASS   |
| ServiceId Unique         | PASS   |
| Mapper SQL ID Unique     | PASS   |
| JWT Private Key Boundary | PASS   |
| Transaction Policy       | PASS   |
| Timeout Policy           | PASS   |

중 Critical Rule이 하나라도 FAIL이라면 최종 Release를 막습니다.

특히 결과는 반드시:

```text
Evaluator
→ Measured Value
→ Threshold
→ Result
```

에서 나온 것이어야 합니다.

사람이 직접:

```text
decision=PASS
```

를 입력한 결과는 최종 증적으로 인정하지 않는 것이 원칙입니다.

## 5. Build와 Artifact Hash를 고정합니다

예를 들어:

```text
sourceCommit
a8f27c1

        ↓

buildId
BUILD-20260817-0142

        ↓

artifact
sv.war

        ↓

SHA-256
8f3a0b...
```

를 고정합니다.

이 Hash는 이후 Test/Deploy/Approval Evidence와 모두 같은 Artifact를 가리켜야 합니다.

### 매우 중요한 검사

```text
테스트한 WAR
SHA256 = AAA

배포한 WAR
SHA256 = BBB
```

이면:

```text
TESTED ARTIFACT
      ≠
DEPLOYED ARTIFACT

      ↓

HG90 BLOCK
```

입니다.

이것은 매우 중요한 Architecture Evidence Chain입니다.

## 6. Deployment Evidence를 확인합니다

최종적으로:

```text
artifactHash
        ↓
deploymentId
        ↓
environment
        ↓
Tomcat / WAR
```

가 연결되어 있어야 합니다.

예:

```text
Artifact

SHA256: 8f3a...

Deployment
DEPLOY-SIT-20260817-009

Environment
SIT

Tomcat

```

입니다.

## 7. Runtime Evidence를 반드시 확인합니다

HG90에서 가장 중요한 항목 중 하나입니다.

최소한 Mission에 해당하는 실제 거래가:

```text
Architecture Baseline
        ↓
Model Version
        ↓
Source Commit
        ↓
Build
        ↓
Artifact Hash
        ↓
Deployment
        ↓
ServiceId
        ↓
TraceId
        ↓
Runtime Evidence
```

까지 연결되어야 합니다.

예를 들어:

```text
ARCH-20260817-003
      ↓
MODEL-3.2.0
      ↓
a8f27c1
      ↓
BUILD-142
      ↓
sv.war / sha256:8f3a...
      ↓
DEPLOY-SIT-009
      ↓
svcoa0001S0
      ↓
traceId=ABC123
      ↓
EVD-RUNTIME-031
```

입니다.

단순:

```text
로그 파일 존재
```

만으로는 부족합니다.

## 8. Drift를 확인합니다

G60 Register를 다시 봅니다.

예:

```text
Total Drift      12

CRITICAL          0
HIGH              2
MEDIUM            6
LOW               4
```

여기서 HIGH가 존재한다고 무조건 HG90을 막는 것은 아닙니다.

예를 들어:

```text
HIGH
→ 해결 완료
→ 재검증 PASS
```

라면 괜찮습니다.

하지만:

```text
CRITICAL OPEN = 1
```

이면:

```text
HG90 PASS 금지
```

입니다.

## 9. GAP/ADR도 같은 방식입니다

예:

| GAP             | Severity | 상태     |
| --------------- | -------- | -------- |
| GAP-TX-001      | HIGH     | RESOLVED |
| GAP-SESSION-001 | HIGH     | RESOLVED |
| GAP-JWT-001     | CRITICAL | **OPEN** |

이면:

```text
Critical GAP OPEN
        ↓
HG90 HOLD
```

입니다.

ADR도:

```text
ADR-JWT-001
Decision = PENDING
```

이라면 해당 Critical GAP을 해결한 것으로 인정하지 않습니다.

## 10. Human Approval을 재검증합니다

G80에서 승인받은 Artifact를 다시 Hash로 확인합니다.

예:

```text
Approval
ADR-TX-001
Hash = AAA111

현재 ADR-TX-001
Hash = AAA111

→ VALID
```

반대로:

```text
Approval Hash
AAA111

Current Artifact Hash
BBB222

→ INVALID
→ 재승인 필요
→ HG90 HOLD
```

입니다.

즉 HG90에서는 **“승인 기록이 있는가?”뿐 아니라 “현재 Release하려는 바로 그 내용이 승인됐는가?”**를 검사합니다.

같은 정책을 둘 수 있습니다.

# 17. HG90의 의미

지금까지 단계가 모두 여기로 모입니다.

```text
G00
무엇을 믿을 것인가?

G10
현재 Architecture는 무엇인가?

G20
기계가 읽을 수 있는가?

G30
실제 Code와 일치하는가?

G40
Test로 증명되는가?

G50
실제로 그렇게 동작하는가?

G60
무엇이 다른가?

G70
무엇을 고칠/결정할 것인가?

G80
누가 승인했는가?

HG90
────────────────
이 모든 결과를
새로운 공식 Architecture라고
선언할 수 있는가?
```

따라서 **HG90은 단순 “프로젝트 완료” Gate가 아니라 “Architecture의 공식 진실(Source of Truth)을 변경하는 Gate”**입니다.

그리고 이 단계가 PASS되면 Closed Loop가 끝나는 것이 아니라 새로운 기준점이 생깁니다.

```text
OLD BASELINE
     ↓
변경
     ↓
Document
→ Model
→ Code
→ Test
→ Runtime
→ Drift
→ GAP/ADR
→ Approval
     ↓
HG90
     ↓
NEW BASELINE
     │
     └───────────────┐
                     ↓
              다음 변경 발생
                     ↓
                NEW RUN
```

즉 **HG90 PASS란 “이번 Run이 끝났다”보다 더 정확하게는 “이번 Run의 결과가 다음 Run이 믿고 시작할 새로운 공식 기준선이 되었다”는 의미**입니다.
