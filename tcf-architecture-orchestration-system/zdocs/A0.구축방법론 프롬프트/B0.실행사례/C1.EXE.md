“새 Requirement, Source 변경, Configuration 변경, Deployment, Incident 또는 Architecture Decision이 발생했는지 확인하라. 이전 Baseline을 변경하지 말고 새로운 Run ID를 생성하라. 변경 영향범위를 ServiceId 중심 Traceability로 계산하여 전체 실행이 필요한지 부분 재검증이 가능한지 결정하라. 영향받는 Agent만 재구성하고 새로운 Architecture Closed Loop Cycle을 시작하라.”

이 명령을 받으면 저는 **새로운 변경이 발생했는지 감지하고, 그 변경이 기존 Architecture Baseline에 어떤 영향을 주는지 계산한 뒤, 필요한 범위만 다시 Closed Loop로 검증하는 “Continuous Architecture 재실행 단계”**를 수행합니다.

즉 HG90에서 새 Baseline이 확정된 뒤, 시스템은 끝나는 것이 아니라 **변경이 생길 때마다 새로운 Run을 시작**합니다.

| 순서 | 제가 수행하는 작업              | 핵심 결과                                                         |
| ---: | ------------------------------- | ----------------------------------------------------------------- |
|    1 | 변경 이벤트 확인                | Requirement / Source / Config / Deploy / Incident / ADR 변경 여부 |
|    2 | 현재 공식 Baseline 확인         | 영향 분석의 출발점 고정                                           |
|    3 | 기존 Baseline 불변 처리         | 기존 Architecture를 덮어쓰지 않음                                 |
|    4 | 새로운 `RUN-ID` 생성            | 변경 검증용 신규 Cycle                                            |
|    5 | 변경 Artifact 식별              | 어떤 파일·ServiceId·정책·테이블 등이 바뀌었는지                   |
|    6 | ServiceId 중심 영향도 계산      | 화면→서비스→코드→DB→Runtime 영향                                  |
|    7 | 영향 수준 분류                  | LOCAL / CROSS-SERVICE / PLATFORM / BASELINE                       |
|    8 | 전체 재검증 vs 부분 재검증 결정 | Full Run 또는 Incremental Run                                     |
|    9 | 필요한 Agent만 재선정           | Agent Team 재구성                                                 |
|   10 | 필요한 Gate만 선택              | G00~HG90 중 영향 Gate                                             |
|   11 | 새 Execution Plan 생성          | 이번 변경에 대한 실행계획                                         |
|   12 | Closed Loop 재실행              | 필요한 단계부터 다시 검증                                         |
|   13 | 새로운 Drift/GAP 탐지           | 기존 Baseline과 변경 결과 비교                                    |
|   14 | 필요 시 ADR/Human Approval      | Architecture 의미 변경 시                                         |
|   15 | HG90 통과 시 새 Baseline 생성   | 이전 Baseline은 보존                                              |

전체 흐름은 다음과 같습니다.

```text
현재 공식 Baseline
        │
        ▼
변경 발생
        │
        ├─ Requirement
        ├─ Source
        ├─ Configuration
        ├─ Deployment
        ├─ Incident
        └─ Architecture Decision
        │
        ▼
새 RUN-ID 생성
        │
        ▼
Change Detection
        │
        ▼
ServiceId 중심 Impact Analysis
        │
        ▼
재검증 범위 결정
   ┌────┴─────┐
   ▼          ▼
부분 재검증   전체 재검증
   │          │
   └────┬─────┘
        ▼
Agent Team 재구성
        ↓
필요 Gate 실행
        ↓
Drift / GAP / ADR
        ↓
Approval
        ↓
HG90
        ↓
New Baseline
```

### 가장 중요한 원칙은 기존 Baseline을 수정하지 않는 것입니다

예를 들어 현재 공식 Baseline이:

```text
ARCH-2026.08.17-03
MODEL-3.2.0
```

인데 새로운 Source 변경이 발생했다고 하겠습니다.

잘못된 방식은:

```text
ARCH-2026.08.17-03
        ↓
파일 직접 수정
        ↓
같은 Baseline ID 유지
```

입니다.

이렇게 하면 과거 시점의 Architecture가 사라집니다.

올바른 방식은:

```text
ARCH-2026.08.17-03
        │
        │ 변경 발생
        ▼
ACL-RUN-20260818-001
        │
        ▼
Impact Analysis
        │
        ▼
재검증
        │
        ▼
HG90 PASS
        │
        ▼
ARCH-2026.08.18-04
MODEL-3.2.1
```

입니다.

기존 것은:

```text
ARCH-2026.08.17-03
status = SUPERSEDED
```

로 보존합니다.

## 변경 종류도 먼저 분류합니다

예를 들어:

| 변경유형      | 예시                 | 예상 영향                      |
| ------------- | -------------------- | ------------------------------ |
| Requirement   | 고객조회에 필드 추가 | Screen/ServiceId/DTO/SQL/Test  |
| Source        | Handler 코드 변경    | ServiceId 실행경로             |
| Configuration | Timeout 3→5초        | Policy/Test/Runtime            |
| Deployment    | 새로운 WAR 배포      | Artifact/Runtime               |
| Incident      | Timeout 장애         | Runtime/Policy/Capacity        |
| ADR           | Session 전략 변경    | Application/Infra/Test/Runtime |

변경 종류에 따라 같은 Closed Loop 전체를 매번 다시 돌릴 필요는 없습니다.

---

# 1. ServiceId 중심으로 영향도를 계산합니다

예를 들어:

```text
CUSTOMER_MASTER
```

Table 컬럼이 변경됐다고 하겠습니다.

기존 G20 Traceability Model을 이용해서 역방향으로 계산합니다.

```text
CUSTOMER_MASTER
      ↑
selectCustomerSummary
      ↑
SvCustomerMapper
      ↑
SvCustomerDao
      ↑
SvCustomerService
      ↑
SvCustomerFacade
      ↑
SvCustomerHandler
      ↑
svcoa0001S0
      ↑
SV-A-0100
      ↑
REQ-SV-001
```

그러면 이번 변경의 영향범위는:

```text
Affected Table
CUSTOMER_MASTER

Affected SQL
selectCustomerSummary

Affected ServiceId
svcoa0001S0

Affected Screen
SV-A-0100

Affected Tests
TC-SV-001
TC-SV-002
```

처럼 계산할 수 있습니다.

이것이 **ServiceId 중심 Impact Analysis**입니다.

---

# 2. 정방향 영향분석도 합니다

새 Requirement가:

```text
REQ-SV-105
"고객 요약조회에 등급정보 추가"
```

라면:

```text
Requirement
    ↓
Screen
    ↓
ServiceId
    ↓
Handler
    ↓
Facade
    ↓
Service
    ↓
DAO
    ↓
Mapper
    ↓
SQL
    ↓
Table
```

방향으로 영향범위를 계산합니다.

따라서 Architecture Traceability는 단순 조회용이 아니라 **변경 영향도 계산 엔진**으로 사용됩니다.

---

# 3. 변경의 크기를 분류합니다

예를 들어 다음처럼 구분할 수 있습니다.

```text
LEVEL-1 LOCAL
하나의 클래스/SQL/ServiceId

LEVEL-2 SERVICE
하나의 업무서비스/WAR

LEVEL-3 CROSS-SERVICE
여러 ServiceId/WAR

LEVEL-4 PLATFORM
TCF/Gateway/JWT/Session/공통정책

LEVEL-5 ARCHITECTURE
Architecture Baseline 자체 변경
```

이 수준에 따라 Closed Loop 실행범위를 바꿉니다.

---

# 4. 단순 변경이면 부분 재검증합니다

예를 들어:

```text
SvCustomerMapper.xml
SQL 하나 변경
```

이고 Architecture 구조와 정책 변화가 없다면:

```text
G00 전체 Baseline 재구축 X
G10 전체 문서분석 X
G20 전체 Model 재생성 X
```

대신:

```text
Change Detection
      ↓
Affected ServiceId 확인
      ↓
G30 Source Mapping
      ↓
G40 해당 Test
      ↓
G50 해당 Runtime Scenario
      ↓
G60 Drift
      ↓
HG90 Release Validation
```

처럼 줄일 수 있습니다.

이것이 **Incremental Architecture Validation**입니다.

---

# 5. 반대로 핵심 Architecture 변경이면 전체 Cycle을 실행합니다

예를 들어:

> Transaction Boundary를 Facade에서 Timeout Worker로 변경한다.

면 하나의 Java Class 수정으로 끝나는 문제가 아닙니다.

영향은:

```text
Transaction Model
     ↓
TCF
     ↓
TimeoutExecutor
     ↓
Thread
     ↓
Handler
     ↓
Facade
     ↓
Service
     ↓
DB Connection
     ↓
Rollback
     ↓
Test
     ↓
Runtime Monitoring
```

전체로 퍼집니다.

따라서:

```text
Run Type
RELEASE_VALIDATION
또는 DECISION_REVIEW

G00
 ↓
G10
 ↓
G20
 ↓
G30
 ↓
G40
 ↓
G50
 ↓
G60
 ↓
G70
 ↓
G80
 ↓
HG90
```

를 다시 수행해야 합니다.

---

# 6. Agent도 영향받는 Agent만 다시 구성합니다

예를 들어 SQL만 바뀌었다면:

```text
Selected Agent

Baseline Agent           필요 시
Source Agent             O
Model Agent              영향부분만
Test Agent               O
Runtime Agent            O
Drift Agent              O
Gate Manager             O
```

Transaction Boundary 변경이라면:

```text
Baseline Agent
Document Agent
Model Agent
Source Agent
Code Rule Agent
Test Agent
Deploy Agent
Runtime Evidence Agent
Drift Agent
GAP/ADR Agent
Gate Manager
```

까지 필요할 수 있습니다.

즉 **Agent Pool은 고정되어 있지만 Run마다 Team이 달라집니다.**

---

# 7. Gate도 영향범위에 맞게 선택합니다

예를 들어 Documentation 오탈자만 수정했다면:

```text
G10
→ 문서 검증

HG90
→ 필요한 경우 Baseline metadata 갱신
```

정도로 끝날 수 있습니다.

하지만 JWT 정책 변경이면:

```text
G10 Document
G20 Model
G30 Code/Security
G40 Security/Contract Test
G50 Runtime Token Validation
G60 Drift
G70 ADR
G80 Security Approval
HG90
```

를 거쳐야 합니다.

---

# 8. Incident가 발생해도 새로운 Run을 만들 수 있습니다

예를 들어 운영 장애가 발생했다고 하겠습니다.

```text
INCIDENT
ServiceId=svcoa0001S0
Timeout 급증
```

그러면:

```text
Incident
    ↓
새 RUN-ID
    ↓
Runtime Evidence 수집
    ↓
ServiceId Trace 조회
    ↓
TimeoutPolicy
    ↓
Config
    ↓
Code
    ↓
SQL
    ↓
Thread / Hikari / JVM
```

순서로 역추적합니다.

예를 들어:

```text
Architecture Model
Timeout = 3 sec

Config
Timeout = 3 sec

Runtime
Timeout = 8 sec

Slow SQL
7.4 sec
```

가 확인되면:

```text
INCIDENT
      ↓
CONFIG DRIFT 아님
      ↓
SQL Runtime Problem
      ↓
Capacity / Query GAP
```

으로 원인을 좁힐 수 있습니다.

즉 Incident도 Architecture Closed Loop의 입력이 됩니다.

---

# 9. Deployment 변경도 중요합니다

Source가 하나도 바뀌지 않았더라도 Deployment가 달라질 수 있습니다.

예:

```text
기존
sv.war Hash AAA

신규 Deploy
sv.war Hash BBB
```

그러면 새 Run을 생성해야 합니다.

특히:

```text
Source Commit 동일
      +
Artifact Hash 다름
```

이면:

```text
Build Reproducibility 문제
```

일 가능성이 있습니다.

따라서 Deployment 자체가 변경 이벤트입니다.

---

예를 들어:

```yaml
  - SvCustomerMapper.xml

    - svcoa0001S0

  components:

    - TC-SV-002

```

같이 구조화할 수 있습니다.

이렇게 하면 **어느 Baseline에서 어떤 변경 때문에 파생된 Run인지** 알 수 있습니다.

# 13. 부분 검증과 전체 검증을 결정하는 기준

예를 들어 다음과 같이 정할 수 있습니다.

| 변경                       | 검증 방식                        |
| -------------------------- | -------------------------------- |
| 문서 오탈자                | 부분                             |
| SQL 내부 변경              | 부분                             |
| Service 구현 변경          | ServiceId Vertical Slice         |
| Config Timeout 변경        | Policy + Test + Runtime          |
| 신규 ServiceId             | Document→Model→Code→Test→Runtime |
| JWT 정책 변경              | Security 중심 Full               |
| Transaction Boundary 변경  | **Full Closed Loop**             |
| Session 방식 변경          | **Full Closed Loop**             |
| TCF 공통 모듈 변경         | **다수 ServiceId 재검증**        |
| Architecture Baseline 변경 | **Full Release Validation**      |

---

# 14. 중요한 것은 “영향받지 않은 것은 다시 하지 않는 것”입니다

Architecture Closed Loop를 매번 전체 실행하면 현실적으로 너무 무겁습니다.

예를 들어:

```text
SQL 1개 수정
```

할 때마다:

```text
수천 개 문서 재분석
전체 Model 재생성
모든 WAR Test
모든 Runtime Scenario
```

를 수행하면 실무에서 사용할 수 없습니다.

그래서 최종적으로는:

```text
CHANGE
   ↓
TRACEABILITY
   ↓
IMPACT SET
   ↓
ONLY AFFECTED
   ↓
REVALIDATION
```

구조가 되어야 합니다.

이것이 **Continuous Architecture**의 핵심입니다.

---

# 15. 다만 일부 변경은 부분검증을 금지해야 합니다

예를 들어:

```text
TCF Transaction
JWT Security Boundary
Session
Global Timeout
Gateway
Common Message
ServiceId Routing
Database Transaction Policy
```

같은 것은 여러 업무에 영향을 미칩니다.

따라서:

```text
Platform Critical Change
        ↓
Incremental Validation 금지 또는 제한
        ↓
Broad / Full Validation
```

정책을 두는 것이 맞습니다.

---

# 16. 전체 Closed Loop가 이제 완성됩니다

처음부터 연결하면:

```text
Mission
 ↓
G00 Source Baseline
 ↓
G10 Document
 ↓
G20 Model
 ↓
G30 Code
 ↓
G40 Test
 ↓
G50 Runtime Evidence
 ↓
G60 Drift
 ↓
G70 GAP / ADR
 ↓
G80 Human Approval
 ↓
HG90 Baseline Release
 ↓
┌─────────────────────────┐
│   OFFICIAL BASELINE     │
└───────────┬─────────────┘
            │
       변경 발생
            ↓
        NEW RUN
            ↓
      Impact Analysis
            ↓
    Agent Team 재구성
            ↓
     필요한 단계 재실행
            ↓
          HG90
            ↓
      NEXT BASELINE
```

즉 마지막 명령은 Closed Loop의 끝이 아니라 **다음 Closed Loop를 자동으로 시작시키는 규칙**입니다.

한 문장으로 정리하면:

> **변경이 발생하면 기존 Architecture를 직접 수정하는 것이 아니라, 기존 Baseline을 출발점으로 새 Run을 만들고 ServiceId Traceability로 영향범위를 계산한 뒤 필요한 Agent와 Gate만 다시 실행하여 새로운 Baseline을 만든다.**

이 단계까지 있어야 NSIGHT Architecture Orchestration System이 단발성 아키텍처 점검 도구가 아니라 **지속적으로 변화하는 시스템을 따라가는 Continuous Architecture Governance 체계**가 됩니다.
