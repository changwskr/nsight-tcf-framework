“Human Approval이 필요한 GAP/ADR/Exception을 정리하라. 업무규칙, 데이터 소유권, 개인정보, 보안정책, Transaction Boundary, Session/JWT 정책, 장애전파, Architecture Exception, Baseline 승격은 자동 승인하지 마라. Approval 대상 Artifact의 ID와 Hash를 고정하고 Approver, Role, Decision, ApprovedAt, Comment, Expiration을 기록하라. Approval Object와 실제 Artifact Hash가 일치할 때만 승인으로 인정하라. 미승인 중요사항이 있으면 G80을 HOLD로 판정하라.”

이 명령을 받으면 저는 **G70에서 만들어진 GAP/ADR/Exception 중 “사람이 반드시 승인해야 하는 것”만 골라서, 승인 대상을 위변조할 수 없도록 Artifact ID와 Hash로 고정하고, 실제 승인 여부를 검증한 뒤 G80을 판정**합니다.

즉 G70이:

> **“무엇을 결정해야 하는가?”**

를 정리하는 단계라면, G80은:

> **“누가, 어떤 결과물에 대해, 어떤 결정을, 언제 승인했는가?”**

를 증명하는 단계입니다.

현재 Closed Loop 마스터 프롬프트도 업무규칙·데이터 소유권·개인정보·보안정책·Transaction Boundary·Session/JWT·장애전파·아키텍처 예외·운영 Risk·Baseline 승격을 사람 승인 대상으로 두고, Approval ID와 Artifact Hash가 일치해야 승인으로 인정하도록 정의하고 있습니다.

| 순서 | 제가 수행하는 작업                          | 결과                                    |
| ---: | ------------------------------------------- | --------------------------------------- |
|    1 | G70 산출물 읽기                             | GAP/ADR/Exception 목록                  |
|    2 | Human Approval 대상 선별                    | Approval Required 목록                  |
|    3 | 대상 Artifact 확정                          | ADR/GAP/Exception ID                    |
|    4 | Artifact 내용 고정                          | SHA-256 등 Hash 생성                    |
|    5 | 승인 요청 객체 생성                         | `APPROVAL-REQUEST`                      |
|    6 | 승인자 역할 확인                            | Architect/Security/Data/Business 등     |
|    7 | 승인결과 수집                               | APPROVE / REJECT / CONDITIONAL          |
|    8 | 승인시각 기록                               | `ApprovedAt`                            |
|    9 | 조건·의견 기록                              | `Comment`                               |
|   10 | 예외 만료일 확인                            | `Expiration`                            |
|   11 | Approval의 Hash와 현재 Artifact Hash 재비교 | 위변조 검사                             |
|   12 | 필수 승인 누락 확인                         | Missing Approval                        |
|   13 | `APPROVAL-RECORD` 생성                      | 승인 증적                               |
|   14 | G80 판정                                    | PASS / CONDITIONAL PASS / HOLD / REJECT |

핵심 흐름은 이렇습니다.

```text
G70
GAP / ADR / Exception
        ↓
Human Approval 필요?
        │
        ├─ NO → 다음 처리
        │
        └─ YES
             ↓
        Artifact ID 고정
             ↓
        Artifact Hash 계산
             ↓
        Approval Request
             ↓
          승인자 판단
        ┌────┼─────┐
        ▼    ▼     ▼
    APPROVE REJECT CONDITIONAL
        │
        ▼
Approval Object
        │
        ▼
Artifact Hash 재검증
        │
        ▼
       G80
```

예를 들어 G70에서 다음 ADR이 만들어졌다고 하겠습니다.

```text
ADR-TX-001
Transaction Boundary 결정

Option A
Facade @Transactional

Option B
Timeout Worker + TransactionTemplate
```

G80에서 저는 이 ADR을 임의로 승인하지 않습니다. 먼저 해당 ADR 문서 자체를 고정합니다.

```text
Artifact ID
ADR-TX-001

Artifact Hash
SHA256:a8f31d....
```

그 다음 승인 요청을 만듭니다.

```yaml
approvalId: APR-TX-001
gateRunId: G80-RUN-20260817-001

artifactIds:
  - ADR-TX-001

artifactHashes:
  ADR-TX-001: "sha256:a8f31d..."

requiredRole:
  - ApplicationArchitect
  - TCFArchitect

decision: PENDING
```

사람이 승인하면:

```yaml
approvalId: APR-TX-001
gateRunId: G80-RUN-20260817-001

artifactIds:
  - ADR-TX-001

artifactHashes:
  ADR-TX-001: "sha256:a8f31d..."

decision: APPROVED

approver: architecture-owner
role: TCFArchitect

approvedAt: 2026-08-17T14:20:00+09:00

comment: "Option B 승인. Timeout/TX 통합시험 후 적용."

expiresAt: null
```

처럼 기록합니다.

## 가장 중요한 것은 Hash 검증입니다

승인자가 `ADR-TX-001`을 승인한 뒤 누군가 ADR 내용을 수정했다고 하겠습니다.

승인 당시:

```text
ADR-TX-001
Hash = AAA111
```

현재 파일:

```text
ADR-TX-001
Hash = BBB222
```

라면 기존 승인은 무효입니다.

```text
Approval
Hash AAA111

        ≠

Current Artifact
Hash BBB222

        ↓

APPROVAL INVALID
        ↓
재승인 필요
```

즉 단순히:

```text
"홍길동이 승인했다"
```

가 중요한 것이 아니라:

> **“홍길동이 정확히 어떤 버전의 ADR을 승인했는가?”**

를 증명하는 구조입니다.

이 원칙은 마스터 프롬프트에 정의된 `approvalId / gateRunId / artifactIds / artifactHashes / decision / approver / role / approvedAt / comment / expiresAt` 구조와 동일합니다.

## 승인 대상은 종류별로 다르게 봅니다

예를 들어:

| 대상                   | 대표 승인 Role                   |
| ---------------------- | -------------------------------- |
| 업무규칙               | Business Owner                   |
| 데이터 소유권          | Data Architect / Data Owner      |
| 개인정보               | Privacy/Security                 |
| 보안정책               | Security Architect               |
| Transaction Boundary   | Application/TCF Architect        |
| Session/JWT            | Security + Application Architect |
| 장애전파               | Application/Operation Architect  |
| Architecture Exception | Architecture Board               |
| Baseline 승격          | Architecture Owner / Governance  |

즉 승인자가 있다는 것만으로 충분하지 않습니다.

```text
잘못된 예

DBA가 JWT 보안정책 승인
→ Role mismatch
```

라면 승인으로 인정하지 않는 구조가 바람직합니다.

## Conditional Approval도 관리합니다

예를 들어:

```text
"Session은 Spring Session JDBC로 승인하되,
SIT Failover 테스트 통과 조건"
```

이라면:

```yaml
decision: CONDITIONAL_APPROVAL

conditions:
  - SIT failover test PASS
  - session loss = 0
  - DB failover evidence 확보

expiresAt: 2026-09-30
```

로 관리합니다.

조건을 충족하지 않았다면 완전 승인으로 바꾸지 않습니다.

```text
CONDITIONAL APPROVAL
       ↓
조건 검증
       │
       ├─ 충족 → APPROVED
       └─ 미충족 → HOLD
```

## Exception은 Expiration을 특히 엄격하게 봅니다

예:

```text
Handler → DAO 직접 호출 금지
```

라는 표준이 있는데 Legacy Service만 임시 예외를 받는다면:

```yaml
exceptionId: EXC-LEGACY-001
ruleId: R-HANDLER-NO-DAO

reason: "2026년 전환 전까지 Legacy 유지"

approvedBy: ArchitectureBoard

expiresAt: 2026-12-31
```

처럼 만료일을 반드시 둡니다.

G70 규칙에서도 예외에는 만료일이 필수라고 정의되어 있습니다.

만료일이 지났다면:

```text
Exception
EXPIRED

        ↓

Architecture Rule 재적용
        ↓
G80 / HG90 차단 가능
```

입니다.

## G80에서 만드는 핵심 산출물

대략 다음 구조입니다.

```text
80-GATE/
├─ approvals/
│   ├─ APR-TX-001.yaml
│   ├─ APR-SESSION-001.yaml
│   ├─ APR-JWT-001.yaml
│   └─ APR-EXCEPTION-001.yaml
│
├─ requests/
│   ├─ APPROVAL-REQUEST-TX.md
│   └─ APPROVAL-REQUEST-SESSION.md
│
├─ validation/
│   ├─ artifact-hash-check.yaml
│   ├─ approver-role-check.yaml
│   └─ expiration-check.yaml
│
├─ APPROVAL-REGISTER.yaml
└─ G80-RESULT.yaml
```

Approval Register는 예를 들면:

| Approval ID | 대상            | Decision | Approver Role      | Hash 일치 | Expiration | 상태        |
| ----------- | --------------- | -------- | ------------------ | --------- | ---------- | ----------- |
| APR-001     | ADR-TX-001      | APPROVED | TCF Architect      | YES       | -          | VALID       |
| APR-002     | ADR-JWT-001     | PENDING  | Security           | -         | -          | OPEN        |
| APR-003     | EXC-001         | APPROVED | Architecture Board | YES       | 2026-12-31 | VALID       |
| APR-004     | ADR-SESSION-001 | APPROVED | App Architect      | **NO**    | -          | **INVALID** |

처럼 관리할 수 있습니다.

## G80 판정

G80의 핵심 질문은:

> **“중요 Architecture Decision을 적절한 사람이, 정확한 Artifact 버전에 대해 승인했는가?”**

입니다.

예를 들어:

```text
필수 Approval 4건

APPROVED       4
Hash Match     4
Role Match     4
Expired        0

        ↓

G80 PASS
```

가 됩니다.

하지만:

```text
Transaction Boundary
→ PENDING

JWT 정책
→ 미승인
```

처럼 중요한 항목이 남아 있으면:

```text
G80 = HOLD
```

입니다.

사용자가 준 명령도 **“미승인 중요사항이 있으면 G80을 HOLD”**하도록 명시합니다.

## 중요한 차이

G80은 사람이 직접 내용을 처음부터 검토하게 만드는 단계가 아니라, **앞 단계에서 충분히 정리한 의사결정 패키지를 사람이 최종 승인하는 단계**입니다.

```text
AI / Agent
────────────────────
문제 분석
Evidence 수집
대안 비교
Risk 분석
추천안 작성
ADR Draft 작성

          ↓

Human
────────────────────
Decision
Approval
Risk Acceptance
Exception 승인

          ↓

G80
────────────────────
승인 무결성 검증
```

따라서 AI가:

```text
"제가 판단해서 Option B를 최종 승인했습니다."
```

라고 하는 것은 금지됩니다. 프로젝트 연속성 지침에서도 업무규칙·데이터 소유권·보안·개인정보·트랜잭션 경계·장애전파·대안 선택·예외 승인·운영 위험은 사람 판단 영역으로 명시되어 있습니다.

마지막으로 전체 흐름에서 G80의 의미는 이렇게 정리됩니다.

```text
G60
무엇이 다른가?
      ↓
DRIFT

G70
무엇을 바꿀 것인가?
      ↓
GAP / ADR / Exception

G80
그 결정을 누가 승인했는가?
정확한 Artifact에 대한 승인인가?
      ↓
HUMAN APPROVAL

G90 / HG90
그 승인된 결과를
새로운 Architecture Baseline으로
승격해도 되는가?
```

즉 **G80은 NSIGHT Architecture Closed Loop의 “사람의 책임을 기계적으로 증명하는 단계”**입니다.

승인 버튼 하나를 누르는 것이 아니라, **Decision + Approver + Role + Timestamp + Artifact Hash + Expiration**을 묶어서 감사 가능한 Architecture Governance 증적으로 만드는 것입니다.
