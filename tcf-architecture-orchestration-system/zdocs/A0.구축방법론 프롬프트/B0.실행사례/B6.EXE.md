“검증된 Source를 Build/Deploy 가능한 경우 실제 환경에서 실행하고 Runtime Evidence를 수집하라. architectureBaselineId → architectureModelVersion → sourceCommit → buildId → artifactHash → deploymentId → serviceId → traceId → evidenceId 연결을 유지하라. ServiceId, GUID, TraceId, Thread, TX Begin/Commit/Rollback, Mapper/SqlId, SQL elapsed, Timeout, Hikari Pool, Tomcat Thread, JVM/GC, EAI, Error/Audit 정보를 수집하라. 단순 로그 존재를 Runtime Evidence로 간주하지 마라. Evidence Manifest와 Hash를 생성하라. Runtime 실행환경이 없으면 증적을 만들었다고 가정하지 말고 G50=HOLD로 기록하되 이후 분석은 가능한 범위까지 계속하라.”

이 명령을 받으면 저는 **G40에서 테스트까지 통과한 Architecture가 실제 실행환경에서도 정말 그렇게 동작하는지를 “증거”로 확인하는 작업**을 수행합니다.

즉 지금까지가 설계·코드·테스트의 검증이었다면 G50부터는 **Architecture as Runtime Evidence** 단계입니다.

```text
G30
Model ↔ Code
      ↓
G40
Code ↔ Test
      ↓
G50
Test 결과
      ↓
실제 Build
      ↓
실제 Artifact
      ↓
실제 Deploy
      ↓
실제 ServiceId 실행
      ↓
실제 Runtime Trace
      ↓
Architecture Runtime Evidence
```

| 순서 | 제가 실제 수행하는 작업        | 확인 내용                                          | 주요 산출물                             |
| ---: | ------------------------------ | -------------------------------------------------- | --------------------------------------- |
|    1 | **G40 결과 확인**              | Build/Test/Security/Architecture Test 상태         | G40 Input                               |
|    2 | **Runtime 환경 가용성 확인**   | DEV/SIT/UAT/LOCAL 등에 실제 실행 가능한지          | Runtime Availability                    |
|    3 | **Source Commit 고정**         | 어떤 소스를 실행하는 것인지                        | `sourceCommit`                          |
|    4 | **Build 수행**                 | 실제 WAR/JAR 생성 여부                             | `buildId`                               |
|    5 | **Artifact Hash 계산**         | 생성된 WAR/JAR의 SHA-256 등                        | `artifactHash`                          |
|    6 | **Deployment 식별**            | 어느 환경/서버에 어떤 Artifact를 배포했는지        | `deploymentId`                          |
|    7 | **테스트 대상 ServiceId 선정** | Mission 범위의 실제 거래                           | `serviceId`                             |
|    8 | **실제 거래 실행**             | HTTP → TCF → Handler → 업무 처리                   | Runtime Transaction                     |
|    9 | **Trace 식별**                 | GUID / TraceId와 ServiceId 연결                    | `traceId`, `guid`                       |
|   10 | **Thread 확인**                | 어느 Tomcat/Worker Thread에서 실행됐는지           | Thread Evidence                         |
|   11 | **Transaction 확인**           | TX Begin / Commit / Rollback, 실제 TX 경계         | TX Evidence                             |
|   12 | **Mapper/SQL 확인**            | 실행 Mapper, SqlId, SQL, elapsed                   | SQL Evidence                            |
|   13 | **Timeout 확인**               | 적용 정책과 실제 Timeout 동작                      | Timeout Evidence                        |
|   14 | **DB Pool 확인**               | Hikari active/idle/pending 등                      | Pool Evidence                           |
|   15 | **Tomcat/JVM 확인**            | Busy Thread, Heap, GC 등                           | Runtime Resource Evidence               |
|   16 | **외부연계 확인**              | EAI/HTTP Client 호출, elapsed, 오류                | Integration Evidence                    |
|   17 | **Error/Audit 확인**           | 오류코드, 감사로그, 사용자/거래 추적성             | Audit Evidence                          |
|   18 | **Evidence 정규화**            | 모든 Evidence를 동일 식별자 Chain에 연결           | Evidence Records                        |
|   19 | **Evidence Hash 생성**         | 증적 파일 무결성 확보                              | `evidenceHash`                          |
|   20 | **Evidence Manifest 생성**     | 어떤 Architecture를 어떤 Runtime이 증명했는지 기록 | `EVIDENCE-MANIFEST`                     |
|   21 | **G50 판정**                   | 실제 Runtime Evidence가 충분한지                   | PASS / CONDITIONAL PASS / HOLD / REJECT |

핵심은 **“로그를 찾는 것”과 “Runtime Evidence를 만드는 것”이 다르다**는 점입니다.

예를 들어 이런 로그가 있다고 하겠습니다.

```text
2026-08-17 12:30:15
ServiceId=svcoa0001S0
traceId=ABC123
elapsed=387ms
result=SUCCESS
```

이것만으로는 G50 Runtime Evidence라고 인정하지 않습니다.

왜냐하면 이 로그가 다음 중 어느 것인지 알 수 없기 때문입니다.

```text
어느 Architecture Baseline?
어느 Architecture Model?
어느 Git Commit?
어느 Build?
어느 WAR?
어느 Deployment?
어느 Test 결과?
```

그래서 반드시 다음 **Evidence Chain**을 만듭니다.

```text
architectureBaselineId
        │
        ▼
architectureModelVersion
        │
        ▼
sourceCommit
        │
        ▼
buildId
        │
        ▼
artifactHash
        │
        ▼
deploymentId
        │
        ▼
serviceId
        │
        ▼
traceId / guid
        │
        ▼
evidenceId
        │
        ▼
evidenceHash
```

예를 들면:

```text
ARCH-20260817-003
        ↓
MODEL-3.2.0
        ↓
Git Commit a8f27c1
        ↓
BUILD-20260817-0142
        ↓
sv.war
SHA256=8f3a...
        ↓
DEPLOY-SIT-20260817-009
        ↓
ServiceId=svcoa0001S0
        ↓
TraceId=ABC123
        ↓
EVIDENCE-RUNTIME-00031
        ↓
SHA256=77bc...
```

이 연결이 만들어져야 제가:

> **“이 Runtime 결과는 ARCH-20260817-003 아키텍처를 구현한 Git Commit a8f27c1의 sv.war가 SIT에서 실제 실행된 결과다.”**

라고 증명할 수 있습니다.

### Transaction은 특히 중요하게 봅니다

G20 모델이:

```text
TX Owner
= Facade
```

라고 되어 있고, G30 Source에서도 Facade에 `@Transactional`이 확인됐다면 G40까지는:

```text
Model
    ↓
Source
    ↓
Test

TX Owner = Facade
```

라고 볼 수 있습니다.

하지만 G50에서 실제 Stack/Transaction Evidence가:

```text
Worker Thread
   ↓
Handler
   ↓
Facade
   ↓
TransactionInterceptor
   ↓
TX BEGIN
```

으로 나타나야 최종적으로 Runtime에서 확인할 수 있습니다.

만약 실제 Runtime이:

```text
Worker Thread
   ↓
TransactionTemplate
   ↓
TX BEGIN
   ↓
Dispatcher
   ↓
Handler
   ↓
Facade
```

라면 Model과 실제 Runtime이 다른 것입니다.

G50에서는 이것을 숨기지 않고 다음 G60으로 넘깁니다.

```text
Expected
TX Owner = Facade

Observed
TX Owner = Timeout Executor / TransactionTemplate

        ↓

RUNTIME DRIFT CANDIDATE
```

### Timeout도 같은 방법으로 확인합니다

Model:

```text
TimeoutPolicy
3 sec
```

Config:

```text
5 sec
```

Runtime:

```text
실제 Timeout 발생
5.01 sec
```

이라면 G50 결과는:

```text
MODEL      3 sec
CONFIG     5 sec
RUNTIME    약 5 sec

Runtime Evidence:
5 sec 정책이 실제 적용됨
```

입니다.

어느 것이 맞는 Architecture인지는 G50에서 임의 결정하지 않고 **G60 Drift → G70 GAP/ADR**로 넘깁니다.

```text
   ↓

   ↓

   ↓
```

그러면 나중에 특정 SQL이 느려졌을 때:

```text

 ↓

 ↓

 ↓
화면
```

역추적도 가능해집니다.

### Thread / Pool / JVM도 같은 거래와 연결해야 합니다

단순히:

```text

GC Pause = 120ms
```

라고 저장하는 것보다:

```text
Deployment
   ↓

   ↓

   ↓
ServiceId
   ↓
TraceId
   ↓
Worker Thread
   │
   ├─ Hikari

   └─ SQL
```

관계가 중요합니다.

그래야 운영 시:

```text

 ↓

 ↓
```

를 찾을 수 있습니다.

## Runtime 환경이 없다면 어떻게 하느냐

이 명령의 중요한 부분이 바로 이것입니다.

만약 저에게 제공된 것이:

```text
Source ZIP
Architecture 문서
Config
Test 결과
```

뿐이고 실제 Tomcat/DB/외부연계가 실행되지 않는다면 저는 절대로:

> “Runtime 검증 완료”

라고 하지 않습니다.

결과는:

```text
Runtime Environment
NOT AVAILABLE

Runtime Scenario
NOT EXECUTED

Runtime Evidence
NOT CAPTURED

G50
HOLD
```

입니다.

하지만 **전체 분석을 중단하지는 않습니다.**

```text
G50 = HOLD
     │
     ├─ 확보 가능한 Static Evidence 정리
     ├─ 필요한 Runtime Scenario 정의
     ├─ 필요한 Evidence 목록 작성
     ├─ Missing Evidence 등록
     │
     ▼
G60
현재 확보된 Evidence 범위에서
Drift 분석 계속
```

즉 `HOLD`는:

> “아무것도 하지 못했다”

가 아니라,

> **“Runtime으로 확인되지 않았으므로 최종 Architecture 완료 판정은 할 수 없다.”**

라는 의미입니다.

현재 NSIGHT 점검에서도 바로 이 부분이 중요한 GAP으로 확인됐습니다. Runtime 모니터링과 로그 기반은 상당히 존재하지만, 이를 Git Commit→Build→Artifact→Deployment→Trace와 연결한 Architecture Runtime Evidence는 아직 충분히 닫혀 있지 않았습니다.

## G50 PASS는 꽤 엄격해야 합니다

단순히:

```text
서버 기동 성공
로그 있음
HTTP 200
```

이라고 해서 PASS하면 안 됩니다.

최소한 다음 구조가 실제로 연결되어야 합니다.

```text
Architecture Baseline
        ↓
Model Version
        ↓
Source Commit
        ↓
Build
        ↓
Artifact Hash
        ↓
Deployment
        ↓
ServiceId
        ↓
Trace
        ↓
Runtime Evidence
```

그리고 Mission에서 요구한 핵심 Runtime 항목이 증명되어야 합니다.

예를 들어 Transaction Boundary 검증 Mission이라면:

```text
TX Evidence 없음
→ G50 PASS 불가
```

Timeout 검증 Mission이라면:

```text
실제 Timeout Scenario 없음
→ G50 PASS 불가
```

JWT 검증 Mission이라면:

```text
실제 Token 검증 Evidence 없음
→ 해당 Runtime 검증 PASS 불가
```

입니다.

그래서 G50의 핵심 질문은 다음 하나입니다.

> **“우리가 테스트한 Architecture가 실제 배포된 시스템에서도 동일하게 동작했다는 사실을 추적 가능한 증거로 증명할 수 있는가?”**

지금까지 단계를 연결하면 훨씬 명확합니다.

```text
G00
무엇을 믿을 것인가?
→ Source Baseline

G10
현재 Architecture는 무엇인가?
→ Document Baseline

G20
기계가 읽을 수 있는가?
→ Architecture Model

G30
실제 Code와 일치하는가?
→ Architecture as Code

G40
Test로 증명 가능한가?
→ Architecture as Test

G50
실제 실행에서도 그러한가?
→ Architecture as Runtime Evidence

G60
Model/Code/Config/Runtime 사이에
무엇이 다른가?
→ Drift Detection
```

따라서 **G50은 NSIGHT Architecture Orchestration에서 “설계가 현실을 만나는 단계”**라고 볼 수 있습니다.

G40까지는 *“이렇게 동작해야 한다”*를 검증하는 것이고, **G50에서는 “실제로 그렇게 동작했다”를 증명합니다.**
