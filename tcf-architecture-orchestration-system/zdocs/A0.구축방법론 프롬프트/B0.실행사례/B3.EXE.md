“G10에서 확인된 Architecture Baseline을 기계 판독 가능한 모델로 변환하라. System, Business, Domain, Function, Program, Screen, ServiceId, Handler, Facade, Service, Rule, DAO, Mapper, SQL, Table, Integration, TransactionPolicy, TimeoutPolicy, SessionPolicy, TestCase, RuntimeTrace 등의 Entity를 정의하라. HAS, CALLS, HANDLED_BY, EXECUTES, ACCESSES, TESTED_BY, DEPLOYED_AS, OBSERVED_BY 등의 Relation을 작성하라. ServiceId 중심 정방향·역방향 Traceability Matrix를 생성하고 JSON Schema와 Semantic Validation 규칙으로 검증하라. 고아 Entity와 중복 ServiceId를 탐지하고 G20을 판정하라.”

이 명령을 받으면 저는 **G10에서 사람 중심으로 정리한 `CURRENT-ARCHITECTURE`를, Agent·검증도구·Harness가 읽고 비교할 수 있는 “Architecture Model”로 변환하는 작업**을 수행합니다.

즉 단계 관계는 이렇게 됩니다.

```text
G00
무엇을 믿을 것인가?
Source Baseline

        ↓

G10
현재 Architecture는 무엇인가?
Document Baseline

        ↓

G20
그 Architecture를
기계가 읽고 검증할 수 있게
어떻게 구조화할 것인가?

        ↓

Architecture Model
```

NSIGHT가 지향하는 `Architecture as Document → Architecture as Model → Architecture as Code → Architecture as Test → Runtime Evidence` 흐름에서 바로 **Architecture as Model 단계**입니다.

| 순서 | 제가 실제 수행하는 일                                    | 핵심 결과                               |
| ---: | -------------------------------------------------------- | --------------------------------------- |
|    1 | G10 산출물과 System Scope 확인                           | Model 대상 범위 확정                    |
|    2 | Architecture Claim을 Entity 후보로 변환                  | Entity Inventory                        |
|    3 | System/Business/ServiceId/Class/DB/Policy 등 Entity 생성 | Architecture Entity Model               |
|    4 | Entity 사이 관계 정의                                    | Relation Model                          |
|    5 | ServiceId 중심 E2E 경로 구성                             | Service Model                           |
|    6 | 정방향 Traceability 생성                                 | Requirement → Runtime 방향              |
|    7 | 역방향 Traceability 생성                                 | Table/SQL → Screen 방향                 |
|    8 | AS-IS/TO-BE/CONFIRMED 상태를 Model 속성에 유지           | 상태 혼합 방지                          |
|    9 | Model 자체를 검증할 JSON Schema 생성                     | Structural Validation                   |
|   10 | Architecture 의미 규칙 생성                              | Semantic Validation                     |
|   11 | 중복 ServiceId 탐지                                      | Duplicate Report                        |

## 1. 먼저 G10 결과를 읽습니다

예를 들어 G10 결과에 다음 내용이 있다고 하겠습니다.

```text
[CONFIRMED]
온라인 거래는 ServiceId를 사용한다.

[AS-IS]
ServiceId SVXXXX는
SvCustomerHandler가 처리한다.

[AS-IS]
SvCustomerHandler
→ SvCustomerFacade
→ SvCustomerService

[AS-IS]
SvCustomerService
→ SvCustomerDao
→ SvCustomerMapper
→ CUSTOMER_MASTER

[TO-BE]
Handler는 DAO를 직접 호출하면 안 된다.

[OPEN]
Session 방식은 최종 확정 필요
```

G20에서는 이것을 그냥 Markdown 문장으로 남겨두지 않습니다.

**객체와 관계로 분해**합니다.

# 2. Entity를 만듭니다

예를 들어 다음과 같은 Entity Catalog를 생성합니다.

```text
Architecture Entity

System
 └─ NSIGHT_TCF

Business
 └─ SV

Domain
 └─ Customer

Function
 └─ CustomerSummary

Program
 └─ CustomerSummaryInquiry

Screen
 └─ SV-A-0100

ServiceId
 └─ svcoa0001S0

Handler
 └─ SvCustomerHandler

Facade
 └─ SvCustomerFacade

Service
 └─ SvCustomerService

Rule
 └─ CustomerEligibilityRule

DAO
 └─ SvCustomerDao

Mapper
 └─ SvCustomerMapper

SQL
 └─ selectCustomerSummary

Table
 └─ CUSTOMER_MASTER
```

여기서 중요한 것은 단순 이름만 만드는 것이 아닙니다.

각 Entity에 식별자와 상태를 붙입니다.

예를 들면:

```yaml
id: SERVICEID-SV-0001
type: ServiceId
name: svcoa0001S0

systemScope: NSIGHT_TCF
businessCode: SV

status: AS_IS

source:
  document: CURRENT-ARCHITECTURE.md
  evidence: SOURCE-MAP-001

verified: true
```

따라서 나중에 AI가:

> 이 ServiceId는 실제 구현입니까, 목표안입니까?

라고 물어도 구분할 수 있습니다.

# 3. Relation을 만듭니다

Entity만 있으면 아직 Architecture가 아닙니다.

그 사이의 관계를 만들어야 합니다.

예:

```text
NSIGHT_TCF
   │ HAS
   ▼
SV Business
   │ HAS
   ▼
Customer Domain
   │ HAS
   ▼
CustomerSummary Function
   │ PROVIDES
   ▼
ServiceId
   │ HANDLED_BY
   ▼
Handler
   │ CALLS
   ▼
Facade
   │ CALLS
   ▼
Service
   │ USES
   ▼
DAO
   │ EXECUTES
   ▼
Mapper / SQL
   │ ACCESSES
   ▼
Table
```

Machine-readable 형태라면 예를 들어:

```yaml
relations:
  - from: svcoa0001S0
    type: HANDLED_BY
    to: SvCustomerHandler

  - from: SvCustomerHandler
    type: CALLS
    to: SvCustomerFacade

  - from: SvCustomerFacade
    type: CALLS
    to: SvCustomerService

  - from: SvCustomerService
    type: USES
    to: SvCustomerDao

  - from: SvCustomerDao
    type: EXECUTES
    to: selectCustomerSummary

  - from: selectCustomerSummary
    type: ACCESSES
    to: CUSTOMER_MASTER
```

이렇게 되면 Architecture가 **Graph**가 됩니다.

# 4. Runtime Policy도 Entity로 만듭니다

NSIGHT에서는 프로그램 구조뿐 아니라 정책도 Architecture입니다.

예:

```text
ServiceId
   │
   ├─ TransactionPolicy
   ├─ TimeoutPolicy
   ├─ SessionPolicy
   ├─ AuthenticationPolicy
   ├─ AuthorizationPolicy
   └─ TransactionControlPolicy
```

예:

```yaml
id: TIMEOUT-SV-0001
type: TimeoutPolicy

serviceId: svcoa0001S0

timeoutSeconds: 3

status: TO_BE

source:
  decisionId: DEC-023
```

그리고:

```yaml
- from: svcoa0001S0
  type: GOVERNED_BY
  to: TIMEOUT-SV-0001
```

처럼 연결합니다.

이것이 중요한 이유는 이후 G30/G40/G50에서:

```text
Architecture Model
Timeout = 3초

         VS

application.yml
Timeout = 5초

         VS

Runtime
실제 Timeout = 5초
```

를 비교할 수 있기 때문입니다.

# 7. JSON Schema를 만듭니다

YAML 파일이 존재한다고 해서 올바른 Architecture Model은 아닙니다.

예를 들어 ServiceId 모델에는 최소한:

```text
id
type
systemScope
serviceId
status
handler
source
```

가 있어야 한다고 정의할 수 있습니다.

JSON Schema는 개념적으로:

```json
{
  "required": ["id", "type", "systemScope", "serviceId", "status"]
}
```

처럼 구조를 강제합니다.

따라서:

```yaml
serviceId: svcoa0001S0
handler: SvCustomerHandler
```

만 있고 `systemScope`가 빠져 있다면:

```text
Schema Validation
FAIL
```

입니다.

특히 NSIGHT_TCF와 PDMG를 혼합하지 않기 위해 `systemScope`는 중요한 필수 속성이 됩니다.

---

# 8. Semantic Validation도 수행합니다

JSON Schema는 구조만 검사합니다.

하지만 Architecture에서는 **의미 검증**이 더 중요합니다.

예를 들어 이런 규칙입니다.

```text
RULE-001
모든 ServiceId는 정확히 하나 이상의 Handler와 연결되어야 한다.

RULE-002
ServiceId는 동일 System Scope 내에서 Unique해야 한다.

RULE-003
Mapper는 최소 하나의 SQL ID를 가져야 한다.

RULE-004
SQL은 접근 Table/View가 식별되어야 한다.

RULE-005
AS-IS Entity는 Source Evidence가 있어야 한다.

RULE-006
CONFIRMED Decision은 ADR 또는 Decision Evidence가 있어야 한다.

RULE-007
RuntimeTrace는 존재하지 않으면 UNKNOWN이어야 한다.

RULE-008
NSIGHT_TCF Entity와 PDMG Entity를 근거 없이 동일 Entity로 병합하지 않는다.
```

이걸 Semantic Validator가 검사합니다.

# 13. G20은 무엇을 판정하는가

핵심 질문은:

> **“현재 Architecture Baseline이 기계가 이해하고 검증할 수 있을 정도로 충분히 구조화되었는가?”**

입니다.

`PASS`는 대략 다음 상태입니다.

```text
Entity Schema Valid
        ✓

Relation Valid
        ✓

ServiceId Unique
        ✓

Critical Orphan 없음
        ✓

Forward Trace 가능
        ✓

Reverse Trace 가능
        ✓

AS-IS Evidence 존재
        ✓

System Scope 구분
        ✓

Critical Semantic Error
        0

        ↓

G20 PASS
```

일부 추적성이 아직 UNKNOWN이지만 다음 Source 분석으로 해결 가능하면:

```text
G20 = CONDITIONAL PASS
```

가 가능합니다.

하지만 예를 들어:

```text
ServiceId 중복 다수
Entity 타입 자체 불명확
AS-IS/TO-BE 혼합
System Scope 혼합
핵심 Relation 누락
Schema Validation 실패
```

라면:

```text
G20 = HOLD
```

입니다.

# 14. G20에서 아직 하지 않는 일

이 부분도 매우 중요합니다.

G20은 **Model 생성 단계**이지 실제 Source를 전수 검사해 Model과 비교하는 단계는 아닙니다.

```text
G20에서 수행

Document → Model          O
Entity/Relation           O
Traceability Model        O
Schema Validation         O
Semantic Validation       O
Orphan/Duplicate 탐지     O


G20에서 아직 본격 수행하지 않음

Java 전체 Source Scan     X
ArchUnit 실행             X
Mapper 실제 전수 대조     X
Build                     X
Test                      X
Runtime Evidence          X
Model↔Runtime Drift       X
```

그 작업은 다음 단계로 넘어갑니다.

```text
G20
Architecture Model

        ↓

G30
Model ↔ Actual Code

        ↓

G40
Architecture as Test

        ↓

G50
Architecture Runtime Evidence
```

현재 NSIGHT에는 이미 Ontology/Harness를 통해 `System`, `Business`, `Function`, `Program`, `ServiceId`, `JavaClass`, `MapperXml`, `SqlId`, `Table` 등의 모델 개념과 `HANDLED_BY`, `CALLS`, `EXECUTES`, `ACCESSES` 같은 관계를 표현하려는 기반이 존재하지만, 아직 NSIGHT 전체의 공통 Model SoT와 엄격한 Schema/Semantic Validation은 완성 단계가 아니라는 점도 기존 점검에서 확인됐습니다.

그래서 G20은 그 부분을 **정식 Architecture Model Baseline으로 만드는 단계**라고 보면 됩니다.

핵심을 가장 간단히 표현하면:

```text
G10

사람:
"이 ServiceId는 이 Handler가 처리하고
 이 Service가 이 Table을 사용한다."

             ↓

G20

Machine:

(ServiceId)
    │ HANDLED_BY
    ▼
(Handler)
    │ CALLS
    ▼
(Facade)
    │ CALLS
    ▼
(Service)
    │ USES
    ▼
(DAO)
    │ EXECUTES
    ▼
(SQL)
    │ ACCESSES
    ▼
(Table)
```

즉 **G20을 지나면서 Architecture가 ‘설명문서’에서 ‘계산하고 검증할 수 있는 데이터’로 바뀝니다.**

이 단계가 제대로 만들어져야 이후 G30부터 **“설계상 그래야 한다”와 “실제 코드가 그렇게 되어 있다”를 자동 비교**할 수 있습니다.
