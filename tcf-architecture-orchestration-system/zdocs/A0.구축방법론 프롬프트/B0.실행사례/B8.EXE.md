“G60에서 발견된 Drift를 분석하여 단순 문서오류, Code Defect, Configuration Drift, Architecture GAP, ADR 필요사항, Exception으로 분류하라. AS-IS ≠ TO-BE이면 GAP을 생성한다. Transaction Boundary, Timeout, Retry, Session, JWT Validation, Gateway, WAR Split, Cache, DB Pool, Logging/Audit 등 중요한 선택은 ADR 후보로 등록하라. ADR에는 Problem, Context, Requirements, Constraints, Alternatives, Comparison, Decision, Rationale, Impact, Risk, Implementation, Test, Runtime Evidence, Migration, Deprecation Condition을 포함하라. AI가 중요 결정을 임의 확정하지 말고 Human Approval 대상으로 넘겨라.”

이 명령을 받으면 저는 **G60에서 발견한 Drift를 “어떻게 처리해야 하는 문제인지” 분류하고, Architecture 변경이 필요한 사항은 GAP과 ADR로 정식 관리한 뒤, 사람이 결정해야 하는 항목을 Human Approval 단계로 넘기는 작업**을 수행합니다.

즉 G60이:

> **“무엇이 서로 다른가?”**

를 찾는 단계라면, G70은:

> **“왜 다른가, 무엇을 고쳐야 하는가, 누가 결정해야 하는가?”**

를 정리하는 단계입니다.

## 1. 전체 처리 순서

| 순서 | 제가 수행하는 작업          | 핵심 결과                                                     |
| ---: | --------------------------- | ------------------------------------------------------------- |
|    1 | `DRIFT-REGISTER` 읽기       | G60 Drift 전체 확보                                           |
|    2 | Drift별 Evidence 재확인     | Confirmed / Candidate / UNKNOWN 구분                          |
|    3 | 원인·성격 분류              | 문서오류 / Code Defect / Config Drift / GAP / ADR / Exception |
|    4 | `AS-IS ↔ TO-BE` 비교        | 차이가 있으면 GAP 생성                                        |
|    5 | 단순 수정 가능 여부 판단    | 문서/코드/설정 수정 Task 생성                                 |
|    6 | Architecture 선택 문제 판별 | ADR 필요 여부 결정                                            |
|    7 | 대안 수집                   | Alternative A/B/C                                             |
|    8 | 대안 비교                   | 비용·성능·보안·운영·장애·전환 등                              |
|    9 | 권고안 작성                 | AI Recommendation은 가능                                      |
|   10 | 중요 결정 여부 판단         | Human Approval 대상 지정                                      |
|   11 | Risk/Impact 분석            | 영향 System/ServiceId/WAR/DB 등                               |
|   12 | 구현·시험·전환계획 작성     | Implementation/Test/Migration                                 |
|   13 | GAP Register 작성           | 해결해야 할 Architecture 차이 원장                            |
|   14 | ADR Draft 작성              | Architecture Decision 후보                                    |
|   15 | Exception Register 작성     | 한시적 예외                                                   |
|   16 | Approval Request 작성       | 사람이 결정해야 할 항목                                       |
|   17 | G70 판정                    | 다음 G80으로 이동 가능 여부                                   |

흐름은 다음과 같습니다.

```text
G60
DRIFT 발견
   │
   ▼
원인/성격 분석
   │
   ├─ 문서가 틀림 ─────────→ Document Fix
   │
   ├─ 코드가 틀림 ─────────→ Code Defect
   │
   ├─ 설정이 틀림 ─────────→ Configuration Fix
   │
   ├─ AS-IS ≠ TO-BE ───────→ GAP
   │
   ├─ 선택이 필요함 ───────→ ADR
   │
   └─ 당장 표준 준수 불가 ─→ Exception
                              │
                              ▼
                     Human Approval
```

# 2. 가장 먼저 Drift를 6종류로 분류합니다

예를 들어 G60에서 다음 Drift들이 발견됐다고 가정하겠습니다.

| Drift         | Expected       | Actual                  |
| ------------- | -------------- | ----------------------- |
| OM Handler    | 25             | 문서 24                 |
| Handler Layer | Handler→Facade | Handler→DAO             |
| Timeout       | 3초            | Config 5초              |
| Session       | JDBC           | DeltaManager            |
| JWT Key       | Issuer only    | Gateway에도 Private Key |
| Legacy API    | 표준 위반      | 기존 고객 때문에 유지   |

G70에서는 이를 이렇게 분류할 수 있습니다.

| Drift               | G70 분류                           | 처리                    |
| ------------------- | ---------------------------------- | ----------------------- |
| OM Handler 24↔25    | **단순 문서오류**                  | 문서 수정               |
| Handler→DAO         | **Code Defect / Architecture GAP** | 코드 개선               |
| Timeout 3↔5         | **Configuration Drift 또는 ADR**   | 정책 확인 필요          |
| JDBC↔DeltaManager   | **Architecture GAP + ADR**         | 전략 결정               |
| Gateway Private Key | **Security Architecture GAP**      | 긴급 개선 + ADR 가능    |
| Legacy API 유지     | **Exception**                      | 기간/범위/만료조건 승인 |

즉 모든 Drift를 ADR로 만드는 것이 아닙니다.

# 3. 단순 문서오류

예:

```text
CURRENT-ARCHITECTURE
OM Handler = 24

Actual Source
OM Handler = 25
```

그리고 현재 목표구조도 25가 맞다면:

```text
AS-IS = 25
TO-BE = 25

문서만 = 24
```

이므로 Architecture Decision 문제가 아닙니다.

결과:

```yaml
classification: DOCUMENT_ERROR
action: UPDATE_DOCUMENT
adrRequired: false
```

입니다.

즉:

```text
Drift
→ Document Fix
→ 재검증
```

으로 끝낼 수 있습니다.

# 4. Code Defect

예를 들어 Architecture Rule이:

```text
Handler
→ Facade
→ Service
→ DAO
```

인데 실제 Source가:

```text
Handler
────────→ DAO
```

라고 하겠습니다.

이미 TO-BE가 확정되어 있고 선택할 대안도 없다면:

```text
AS-IS
Handler → DAO

TO-BE
Handler → Facade → Service → DAO

        ↓
Architecture GAP

그리고 원인
Code Defect
```

가 됩니다.

즉 하나의 문제에 두 속성이 같이 붙을 수도 있습니다.

```yaml
classification:
  - CODE_DEFECT
  - ARCHITECTURE_GAP
```

# 5. Configuration Drift

예:

```text
Architecture Model
Timeout = 3 sec

application.yml
Timeout = 5 sec

Runtime
5 sec
```

그런데 공식 Decision이 이미:

```text
Timeout = 3 sec
```

로 승인되어 있다면 새 ADR은 필요하지 않습니다.

```text
Approved Policy
3 sec

        ≠

Config/Runtime
5 sec

        ↓

CONFIGURATION DRIFT
```

이므로:

```text
Config 수정
→ Deploy
→ G40 재시험
→ G50 Runtime 재검증
```

으로 보내면 됩니다.

반대로 **3초와 5초 중 어느 것이 올바른지 결정되지 않았다면** ADR 대상입니다.

# 6. `AS-IS ≠ TO-BE`이면 GAP을 만듭니다

이게 G70의 핵심 규칙입니다.

예를 들어:

```text
[AS-IS]
Facade @Transactional

[TO-BE]
Timeout Worker에서
TransactionTemplate로 최외곽 TX
```

라면:

```text
AS-IS ≠ TO-BE
       ↓
GAP 생성
```

합니다.

GAP 하나는 예를 들어 다음처럼 기록합니다.

```yaml
gapId: GAP-TX-001

title: Transaction Boundary 불일치

systemScope: NSIGHT_TCF

asIs: Facade Spring @Transactional

toBe: Timeout Worker outer Transaction

difference: Transaction 시작 위치와 책임 주체가 다름

impact:
  - rollback
  - timeout
  - DB connection lifecycle
  - thread boundary

severity: HIGH

adrRequired: true

status: OPEN
```

여기서 중요한 것은 **GAP은 문제이고 ADR은 결정**이라는 차이입니다.

```text
GAP
"현재와 목표가 다르다."

ADR
"그래서 어떤 방식을 선택할 것인가?"
```

---

# 7. 어떤 항목은 ADR 후보로 올립니다

특히 사용자 명령에 있는 다음 항목들은 단순 구현 디테일이 아니라 Architecture 선택에 해당할 가능성이 높습니다.

| 주제                 | ADR이 필요한 이유                  |
| -------------------- | ---------------------------------- |
| Transaction Boundary | TX 소유자와 rollback 책임 변경     |
| Timeout              | 거래종료·DB TX·Thread 정책 영향    |
| Retry                | 중복처리·Idempotency·장애확산 영향 |
| Session              | 클러스터·Failover·운영구조 영향    |
| JWT Validation       | 보안 경계 결정                     |
| Gateway              | 인증/라우팅/장애영역 결정          |
| WAR Split            | JVM/배포/장애격리 결정             |
| Cache                | 일관성/TTL/장애대응 결정           |
| DB Pool              | 처리량/장애확산/자원관리 결정      |
| Logging/Audit        | 보안·개인정보·운영증적 결정        |

예를 들어 Session 문제가:

```text
Option A
DeltaManager

Option B
Spring Session JDBC
```

이면 제가 임의로 B를 확정하지 않습니다.

ADR Draft를 만듭니다.

---

# 8. ADR을 상세하게 작성합니다

예를 들어:

```text
ADR-SESSION-001
NSIGHT Session 저장 방식
```

이라면 최소 다음 구조를 만듭니다.

| 항목                  | 내용                           |
| --------------------- | ------------------------------ |
| Problem               | 현재 Session 전략이 혼재       |
| Context               | 다중 Tomcat/WAR, Failover 요구 |
| Requirements          | 60분 Session, 장애복구 등      |
| Constraints           | 기존 Tomcat, DB, 운영환경      |
| Alternative A         | DeltaManager                   |
| Alternative B         | Spring Session JDBC            |
| Alternative C         | Stateless/JWT 중심             |
| Comparison            | 성능/운영/장애/복잡도 비교     |
| Decision              | **PENDING HUMAN APPROVAL**     |
| Rationale             | 선택 시 근거                   |
| Impact                | WAS/DB/Application/운영 영향   |
| Risk                  | DB 집중, replication 비용 등   |
| Implementation        | 적용 위치                      |
| Test                  | failover/session test          |
| Runtime Evidence      | 어떤 증적을 확보할지           |
| Migration             | 기존 Session 전환              |
| Deprecation Condition | 기존 방식 폐기조건             |

중요한 부분은:

```text
Decision:
PENDING
```

입니다.

AI는 대안을 비교하고 **Recommendation**은 할 수 있지만:

```text
APPROVED
```

로 바꿀 수 없습니다.

# 9. 대안 비교표도 만듭니다

예를 들어 Transaction Boundary라면:

| 비교항목                 | A. Facade `@Transactional` | B. Worker `TransactionTemplate` |
| ------------------------ | -------------------------- | ------------------------------- |
| 구조 단순성              | 높음                       | 중간                            |
| Timeout Thread와 TX 정렬 | 제한적                     | 높음                            |
| Spring 표준성            | 높음                       | 높음                            |
| TX 범위                  | 업무 중심                  | 거래 전체                       |
| DB Connection 점유       | 상대적 짧음                | 길어질 수 있음                  |
| Timeout 취소 연계        | 별도 고려                  | 밀접                            |
| 기존 Source 영향         | 작음                       | 큼                              |
| 운영 추적성              | 보완 필요                  | 설계 가능                       |
| Migration 비용           | 낮음                       | 높음                            |
| Risk                     | Timeout/TX 경계            | 장기 TX/자원점유                |

그리고:

```text
AI Recommendation:
Option B가 목표 Architecture와 더 적합할 가능성이 있음.

그러나
Transaction Boundary는 Architecture 핵심 결정이므로
Human Approval 필요.
```

처럼 처리합니다.

# 10. Exception도 별도로 관리합니다

표준 위반이지만 당장 고칠 수 없는 경우입니다.

예:

```text
표준:
Handler → DAO 직접 호출 금지

Legacy Service:
2026년 말까지 변경 불가
```

이럴 때 규칙을 없애버리지 않습니다.

```text
Architecture Rule
그대로 유지

        +

Exception
LegacyService만 한시 허용
```

으로 합니다.

Exception에는 최소:

```text
Exception ID
대상
위반 Rule
사유
영향
Risk
보완통제
Owner
승인자
시작일
만료일
재검토일
폐기조건
```

을 둡니다.

특히 **Expiration 없는 Exception은 원칙적으로 허용하지 않는 구조**가 좋습니다.

# 11. Risk도 등록합니다

예를 들어:

```text
GAP-TX-001
```

이 해결되지 않으면:

```text
Risk
├─ Timeout 시 DB TX 지속 가능성
├─ Connection 장기 점유
├─ 예상치 못한 Commit/Rollback
├─ Thread 종료와 DB 작업 비동기화
└─ 운영 추적성 부족
```

등을 기록합니다.

따라서 G70의 산출물은 단순 GAP 목록이 아니라:

```text
Drift
  ↓
GAP
  ↓
Decision 필요?
  ├─ NO → Fix
  └─ YES
       ↓
      ADR
       ↓
      Risk
       ↓
    Approval
```

입니다.

# 15. GAP Register는 이런 모습입니다

| GAP ID  | 대상          | AS-IS               | TO-BE           | Severity | ADR     | Approval | 상태    |
| ------- | ------------- | ------------------- | --------------- | -------- | ------- | -------- | ------- |
| GAP-001 | Transaction   | Facade TX           | Worker Outer TX | HIGH     | ADR-001 | 필요     | OPEN    |
| GAP-002 | Session       | DeltaManager        | JDBC            | HIGH     | ADR-002 | 필요     | OPEN    |
| GAP-003 | Handler Layer | Handler→DAO         | Handler→Facade  | HIGH     | 불필요  | 불필요   | FIX     |
| GAP-004 | OM 문서       | 24 Handler          | 25 Handler      | MEDIUM   | 불필요  | 불필요   | DOC FIX |
| GAP-005 | JWT Key       | Gateway Private Key | Issuer Only     | CRITICAL | ADR-003 | 필요     | OPEN    |

# 16. G70 판정은 어떻게 하나

G70의 질문은:

> **“발견된 Drift를 모두 처리 가능한 Action, GAP, ADR 또는 Exception으로 분류했고, 사람이 결정할 사항을 정확히 분리했는가?”**

입니다.

즉 모든 GAP이 해결되어야 G70 PASS인 것은 아닙니다.

예를 들어:

```text
Drift 15
        ↓
Document Error      3 → Fix Plan
Code Defect         4 → Fix Plan
Config Drift        2 → Fix Plan
Architecture GAP    4 → GAP 생성
ADR Required        2 → ADR Draft
Exception           1 → Approval Request

분류되지 않은 Drift
0

        ↓
G70 PASS
```

가 가능합니다.

반대로:

```text
Critical Drift 있는데
원인/조치 미분류

또는

Architecture 선택인데
AI가 임의로 Decision 확정

또는

Exception인데
Owner/Expiration 없음
```

이면:

```text
G70 = HOLD
```

입니다.

# 17. G70에서 중요한 것은 “고치는 것”보다 “통제하는 것”입니다

예를 들어 Drift가 하나 발생했습니다.

```text
Runtime Timeout = 5 sec
Model Timeout = 3 sec
```

나쁜 방식은:

```text
"Model을 5초로 바꾸면 되겠네."

        ↓

Model 변경
```

입니다.

이렇게 하면 실제 정책이 3초였는데 **잘못된 Runtime을 기준으로 Architecture를 역으로 오염**시킬 수 있습니다.

올바른 방식은:

```text
Runtime 5초
       ≠
Model 3초
       ↓
DRIFT
       ↓
왜 다른가?
       ↓
승인된 Decision 확인
       │
       ├─ 3초가 공식 기준
       │       ↓
       │   Config/Code Fix
       │
       └─ 정책 변경 필요
               ↓
              ADR
               ↓
         Human Approval
               ↓
        Model 변경 가능
```

입니다.

이 원칙이 Architecture Closed Loop에서 매우 중요합니다.
