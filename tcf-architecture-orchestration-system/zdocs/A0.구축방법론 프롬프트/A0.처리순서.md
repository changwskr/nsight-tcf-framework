현재 업로드한 **NSIGHT Architecture Orchestration System** 기준으로 보면 처리 절차는 아래 순서로 정리하는 것이 가장 명확합니다.

| 순서 | 단계                                      | 핵심 질문                                        | 주요 수행 내용                                                                                                                  | 핵심 산출물                                                  | Gate     |
| ---: | ----------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------- |
|    0 | **Mission 접수 / Orchestration 시작**     | 무엇을 점검하거나 만들 것인가?                   | 사용자 목표 해석, Run Type 분류, System Scope 결정, 필요한 Agent 선정                                                           | Mission, Agent Team, Execution Plan                          | -        |
|    1 | **STEP 00 — Bootstrap / Source Baseline** | 무엇을 기준으로 분석할 것인가?                   | Run Manifest 생성, Source/Config/Document/Test/Runtime Inventory, Generated/History/중복 분리, Source Baseline 확정             | `RUN-MANIFEST`, `SOURCE-BASELINE`, Inventory, Execution Plan | **G00**  |
|    2 | **STEP 10 — Architecture as Document**    | 현재 아키텍처는 무엇을 약속하는가?               | Requirement/ADR/Standard/Decision 정리, `AS-IS/TO-BE/GAP/DEPRECATED` 구분, Current Architecture 확정                            | `CURRENT-ARCHITECTURE`, Requirement/ADR/Decision Register    | **G10**  |
|    3 | **STEP 20 — Architecture as Model**       | 문서의 아키텍처를 기계가 이해할 수 있는가?       | System/Business/ServiceId/Component/Data/Policy 모델 생성, Entity/Relation 정의, Traceability Matrix 작성, Schema/Semantic 검증 | Architecture Model, Traceability Matrix, Model Schema        | **G20**  |
|    4 | **STEP 30 — Architecture as Code**        | 실제 Source가 Model과 일치하는가?                | Java/Gradle/YAML/XML/Mapper/SQL/DDL/OM 분석, ServiceId Source Map 생성, Architecture Rule을 Policy-as-Code로 연결               | Source Map, Config Map, Policy-as-Code Map                   | **G30**  |
|    5 | **STEP 40 — Architecture as Test**        | Architecture Rule을 자동 검증할 수 있는가?       | ArchUnit, Source Scanner, Contract, Unit, Integration, Security, Runtime Policy Test 실행                                       | `TestRunId`, Test Report, Evaluator Result                   | **G40**  |
|    6 | **STEP 50 — Runtime Evidence**            | 실제 Runtime도 설계대로 동작하는가?              | Build/Deploy 증적 연결, ServiceId/TraceId/TX/SQL/Thread/Hikari/JVM/Timeout/Audit 수집                                           | Evidence Manifest, Runtime Evidence Report                   | **G50**  |
|    7 | **STEP 60 — Drift Detection**             | 설계·코드·설정·실행 사이에 차이가 있는가?        | Document↔Model, Model↔Code, Model↔Config, Code↔Runtime, Config↔Runtime, Test↔Runtime 비교                                       | Drift Register, Drift Report                                 | **G60**  |
|    8 | **STEP 70 — GAP / ADR**                   | 발견한 차이를 어떻게 처리할 것인가?              | Drift를 오류수정/문서정정/GAP/ADR/Exception으로 분류, 대안 비교와 의사결정 준비                                                 | GAP Register, ADR, Approval Request                          | **G70**  |
|    9 | **STEP 80 — Human Approval**              | 사람이 반드시 결정해야 할 사항은 승인되었는가?   | 중요 ADR, 보안, TX 경계, Session, 예외 등을 Artifact Hash와 함께 승인                                                           | Approval Record                                              | **G80**  |
|   10 | **STEP 90 — Baseline Release**            | 이 결과를 새로운 공식 기준으로 승격할 수 있는가? | GAP 해결, ADR 승인, Model 갱신, Schema/Test/Runtime 재검증, Critical Drift 0 확인                                               | Baseline Release, Release Evidence Package                   | **HG90** |
|   11 | **다음 Cycle 시작**                       | 변경된 Architecture가 계속 유지되는가?           | 새로운 요구/변경/배포 발생 시 다시 Mission부터 실행                                                                             | 신규 Run                                                     | 반복     |

이 흐름을 한 줄로 줄이면 다음입니다.

```text
사용자 Mission
   ↓
Orchestrator
   ↓
Scope / Agent Team 선정
   ↓
Source Baseline
   ↓ G00
Architecture Document
   ↓ G10
Architecture Model
   ↓ G20
Architecture as Code
   ↓ G30
Architecture as Test
   ↓ G40
Runtime Evidence
   ↓ G50
Drift Detection
   ↓ G60
GAP / ADR
   ↓ G70
Human Approval
   ↓ G80
Baseline Release
   ↓ HG90
NEW ARCHITECTURE BASELINE
   │
   └──────────────→ 다음 변경 시 다시 반복
```

특히 **0~2단계가 매우 중요합니다.** 처음부터 Source 분석이나 Model 생성을 하는 것이 아니라 먼저 `Mission → Scope → Source Baseline → Current Document Baseline`을 확정해야 합니다. 현재 시스템의 Master Prompt도 Mission을 받으면 곧바로 설계를 시작하지 않고 `MISSION NORMALIZATION → SYSTEM SCOPE → RUN MANIFEST → TEAM SELECTION → EXECUTION PLAN`을 먼저 수행하도록 정의되어 있습니다.

또 실제 실행에서는 모든 단계가 항상 필요한 것은 아닙니다. Mission 유형에 따라 Orchestrator가 작업량을 조절합니다.

| Run Type               | 사용 예                    | 주로 수행하는 단계                                  |
| ---------------------- | -------------------------- | --------------------------------------------------- |
| **QUICK_CHECK**        | 패키지/네이밍/의존성 점검  | 00 → 30 → 40                                        |
| **VERTICAL_SLICE**     | ServiceId 하나 E2E 검증    | **00 → 10 → 20 → 30 → 40 → 50 → 60 → 70 → 80 → 90** |
| **DECISION_REVIEW**    | TX/Session/JWT 결정        | 00 → 10 → 20 → 30 → 40/50 → 60 → 70 → 80            |
| **RELEASE_VALIDATION** | 최종 아키텍처 Release 검증 | 전체 단계                                           |

제가 보기에는 **첫 실제 작업은 `VERTICAL_SLICE`로 시작하는 것이 맞습니다.** 대표 ServiceId 1~3건을 골라 `Document → Model → Code → Test → Runtime Evidence`까지 한 번 완주시키고, 이 Pilot이 성공하면 전체 NSIGHT로 범위를 확대하는 방식이 가장 안전합니다.
