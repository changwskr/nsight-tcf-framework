이 표를 실제 프로젝트 운영 관점으로 다시 압축하면 **4개의 큰 업무 구간**으로 이해하면 쉽습니다.

```text
① 무엇을 할 것인가?
──────────────────────────────
Mission
→ Scope
→ Agent Team
→ Source Baseline

            ↓

② 무엇이 맞는 구조인가?
──────────────────────────────
Document
→ Model
→ Code
→ Architecture Test

            ↓

③ 실제로 그렇게 동작하는가?
──────────────────────────────
Build / Deploy
→ Runtime Evidence
→ Drift Detection

            ↓

④ 차이가 있으면 어떻게 할 것인가?
──────────────────────────────
GAP
→ ADR
→ Human Approval
→ New Baseline
→ 다음 Cycle
```

그리고 실제 사용자는 매번 긴 단계별 프롬프트를 직접 입력할 필요가 없습니다. **최상위 Orchestrator에 Mission 하나만 입력하고, 위 표의 프롬프트는 내부 Stage Prompt로 호출**하는 구조가 맞습니다.

예를 들어 사용자는 단순히:

```text
TCF Timeout과 Transaction Boundary를
실제 Source와 Runtime 기준으로 검증해줘.
```

라고 입력합니다.

그러면 내부에서는:

```text
Mission Prompt
      ↓
STEP 00 Prompt
      ↓ G00
STEP 10 Prompt
      ↓ G10
STEP 20 Prompt
      ↓ G20
STEP 30 Prompt
      ↓ G30
STEP 40 Prompt
      ↓ G40
STEP 50 Prompt
      ↓ G50
STEP 60 Prompt
      ↓ G60
STEP 70 Prompt
      ↓ G70
STEP 80 Prompt
      ↓ G80
STEP 90 Prompt
      ↓
HG90
```

순으로 실행되는 것입니다.

이 구조라면 **사용자에게는 “업무 절차”가 보이고, 내부 Agent에게는 “단계별 실행 프롬프트”가 보이는 이중 구조**가 완성됩니다. 다음에는 이 표를 기준으로 각 단계 프롬프트를 실제 `STEP-00.md ~ STEP-90.md` 형식의 **완성형 상세 프롬프트 파일**로 만드는 것이 가장 자연스럽습니다.
