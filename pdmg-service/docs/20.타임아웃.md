# 20. 타임아웃 (PDMG)

기준일: 2026-08-09  
대상: `pdmg-service` · `pdmg-fw` · `pdmg-ui`  
관련: [20.Tranaactional-rdwTransactionManager-Begin.md](./20.Tranaactional-rdwTransactionManager-Begin.md) · [19.Business-Facade.md](./19.Business-Facade.md) · [성능감시.md](./성능감시.md) · [롤백아키텍처 4초지나면롤백되나.md](./롤백아키텍처%204초지나면롤백되나.md) · `pdmg-fw/docs/timeout/01.timeout.md`

> **번호 안내:** 같은 `20`에 [Transactional BEGIN](./20.Tranaactional-rdwTransactionManager-Begin.md) 문서가 있다.  
> 본 문서는 **시간 제한(timeout) 전 계층**을 정리한다.

---

## 0. 한 줄 요약

**PDMG에는 “온라인 요청 전체를 N초에 끊는” 통합 타임아웃이 없다.**  
강제 중단·롤백이 필요하면 **Business Facade `@Transactional(timeout = 초)`** 를 **명시**해야 한다.  
현재 샘플 Facade(`5530`/`8888`/`9000`/`9999`)에는 **`timeout` 미지정**이다.

```text
느린 거래 감지(로그·ImageLog)  ≠  타임아웃(강제 중단/롤백)
```

---

## 1. 계층별 현황

| 계층 | 설정/코드 | 현행 |
|------|-----------|------|
| HTTP 요청 전체 (`pdmg-service`) | MVC async timeout / Filter 타이머 | **없음** — 끝날 때까지 대기 |
| TCF / STF 거래 timeout | (구 NSIGHT STF) | **없음** — PDMG TCF는 라우팅만 |
| **DB TX** | Facade `@Transactional(timeout=…)` | **미지정** (샘플). 넣으면 TX 구간만 제한 |
| MyBatis statement | `defaultStatementTimeout` / XML `timeout` | **없음** |
| Hikari pool | `connection-timeout` 등 | `application.yml`에 **명시 없음** → 라이브러리 기본 |
| `pdmg-ui` relay | `pdmg.ui.timeout-ms: 10000` | 설정·API config로 노출. **`RestClient`에는 미적용** |
| 외부 APIGW/FOS 등 | (fw 구문서) | 업무 온라인 경로와 별개 — 사용 시 개별 확인 |
| Gradle | `networkTimeout` | 빌드만 |

앞단 API GW / LB / WAS / 브라우저가 먼저 끊을 수 있다.  
그 경우 **서버 스레드·Facade TX는 계속 진행**될 수 있다.

---

## 2. 요청 전체 타임아웃 (없음)

```text
Filter → Interceptor → OnlineController → TcfFacade → Handler
  → Facade(TX) → Service → DAO
  → Advice → afterCompletion
```

위 파이프라인을 N초에 강제 종료하는 Filter/`Future.get`/`orTimeout`은 **없다**.

확인되지 않은 예:

```yaml
spring.mvc.async.request-timeout: …
```

따라서 “화면이 10초면 서버도 멈춘다”는 **성립하지 않는다** (UI 설정도 relay에 미연결).

---

## 3. DB 트랜잭션 타임아웃 (넣을 곳)

### 3.1 위치

**`nhnis.mg.co.a.application.facade.*`만.**  
Service/Handler/TcfFacade에 두지 않는다 ([19](./19.Business-Facade.md) · [20 BEGIN](./20.Tranaactional-rdwTransactionManager-Begin.md)).

```java
@Transactional(
        transactionManager = "rdwTransactionManager",
        timeout = 4,                         // 초
        rollbackFor = Exception.class)
public mgcoa8888D0DTOout mgcoa8888D0(Object dtoBody) throws Exception {
    …
}
```

조회:

```java
@Transactional(
        transactionManager = "rdwTransactionManager",
        readOnly = true,
        timeout = 10)
public mgcoa8888S0DTOout mgcoa8888S0(Object dtoBody) throws Exception {
    …
}
```

### 3.2 동작 의미

```text
Facade @Transactional BEGIN
  → BizPrePost → Service → DAO …
  → (제한 시간 초과)
  → 이후 DB 접근 또는 TX 완료 검사 시점
  → TransactionTimedOutException
  → ROLLBACK
```

| 사실 | 설명 |
|------|------|
| HTTP 전체가 아님 | Filter~Advice 바깥·이후는 별개 |
| “딱 4.000초 강제 kill” 아님 | Spring TX timeout — 주로 **다음 동기화/DB 작업** 때 감지 |
| 순수 CPU 루프 | DB를 안 치면 즉시 안 끊길 수 있음 |
| 조회 timeout | 롤백할 변경은 없어도 예외로 실패 응답 가능 |
| 쓰기 timeout | 해당 Facade TX 변경 **롤백** |

상세 예시: [롤백아키텍처 4초지나면롤백되나.md](./롤백아키텍처%204초지나면롤백되나.md).

### 3.3 현행 샘플

| Facade 메서드 | TX | timeout |
|---------------|-----|---------|
| `*S0` 조회 | `readOnly=true` | **없음** |
| `*C0`/`U0`/`D0` 쓰기 | `rollbackFor=Exception` | **없음** |

임의로 4초를 코드에 넣지 말 것. 업무·SLA가 정해진 뒤 Facade에만 기입 ([CRUD프롬프트](./CRUD서비스프롬프트가이드.md)).

## 4. SQL · 커넥션 풀

### 4.1 MyBatis

`RdwDataSourceConfig`의 MyBatis `Configuration`에는:

- `JdbcTypeForNull`, `callSettersOnNulls`만
- **`setDefaultStatementTimeout` 없음**
- Mapper XML에도 statement `timeout` **없음**

느린 SQL → JDBC/DB 쪽 제한까지 대기 가능.

필요 시:

```java
mybatisConfig.setDefaultStatementTimeout(30); // 초
```

또는

```xml
<select id="…" timeout="10">…</select>
```

### 4.2 Hikari

`spring.datasource.rdw`에 pool timeout 키가 **명시되어 있지 않다.**  
`connection-timeout`은 **SQL 실행 제한이 아니라** 풀에서 커넥션을 **빌리기** 기다리는 시간이다.

---

## 5. pdmg-ui relay

```yaml
# pdmg-ui application.yml
pdmg:
  ui:
    timeout-ms: 10000
```

- `PdmgUiProperties.timeoutMs` → UI config API로 내려줄 수 있음  
- `TransactionRelayService`의 `RestClient`는 **타임아웃 미설정** (기본 무기한에 가까움)

UI에 10초가 보여도 **중계 HTTP가 10초에 끊기지 않는다.**  
적용하려면 `ClientHttpRequestFactory`/JDK HttpClient 등에 connect·read timeout을 붙어야 한다.

---

## 6. 감시 vs 타임아웃

| | 감시 ([성능감시](./성능감시.md)) | 타임아웃 |
|--|--------------------------------|----------|
| 수단 | `PdmgTxFlowLog`, ImageLog, SQL debug ms | `@Transactional(timeout)`, (선택) MyBatis/JDBC |
| 효과 | 로그·추적 | 예외·롤백·중단(해당 계층) |
| 기본 | **동작 중** | **미적용**(샘플) |

ImageLog `REQUEST_TIME`/`RESPONSE_TIME`으로 소요를 볼 수 있으나 **자동 롤백하지 않는다.**

---

## 7. 권장 운영 방침

```text
1. 요청 전체 강제 중단이 필요하면
   → 인프라(GW/WAS) + (선택) UI relay HTTP timeout을 명시적으로 연결
2. 업무 DB 일관성 제한이 필요하면
   → Facade @Transactional(timeout=N) 만 (거래별로 다르게)
3. 특정 쿼리만 제한하면
   → MyBatis statement timeout
4. “4초면 무조건 롤백”을 Filter/Interceptor/TCF에 넣지 말 것
5. timeout 값을 추측해 커밋하지 말 것 — SLA 확정 후
```

구 STF “거래 Timeout 정책” 자리는 PDMG에 **없다**.  
DB 구간은 Facade, HTTP 구간은 인프라/클라이언트로 나눈다.

---

## 8. 하지 말 것

1. Service에 `@Transactional(timeout=…)`만 올리고 Facade는 빼기  
2. Filter/Interceptor에서 sleep 감시로 “타임아웃” 흉내 내기  
3. UI `timeout-ms`만 보고 서버도 끊긴다고 가정  
4. Hikari `connection-timeout`을 SQL timeout으로 오해  
5. 샘플에 없는 4초를 문서 없이 전 거래 기본값으로 박기

## 10. 요약

```text
PDMG 통합 요청 timeout = 없음
DB TX timeout        = Facade에 명시할 때만 (샘플 미사용)
SQL timeout          = MyBatis 미설정
UI timeout-ms        = 설정만, relay 미적용
감시 로그            = 중단 아님

다음: TX BEGIN 상세 → 20.Tranaactional-…
     4초 롤백 예시 → 롤백아키텍처 4초지나면롤백되나.md
```
