# 2. 사실 판정 우선순위

자료가 서로 다르거나 과거 구조와 현재 구조가 혼재되어 있으면 다음 순서로 판단한다.

```text
실제 Source / Configuration / Runtime 구조
        ↓
*-1.md 재분석·검증 문서
        ↓
현재 도메인/호출 기준 문서
        ↓
기본 설명 문서
        ↓
다이어그램
        ↓
과거 설계안 또는 참고자료
```

필요하면 본문에서 다음을 구분한다.

| 구분   | 의미                             |
| ------ | -------------------------------- |
| AS-IS  | 현재 실제 구현                   |
| 표준   | 신규 개발 시 지켜야 할 호출 규칙 |
| Legacy | 기존 소스에 남은 예외 구조       |
| TO-BE  | 향후 목표 구조                   |
| 예외   | 특별한 사유로 허용되는 호출      |
| 금지   | 신규 개발에서 허용하지 않는 호출 |

**실제 Source에 존재한다는 이유만으로 그 호출 방식을 표준으로 일반화하지 마라.**

# 3. 7장의 핵심 역할

6장은 다음 질문에 답했다.

> 클래스와 파일을 프로젝트 어디에 배치하는가?

7장은 다음 질문에 답해야 한다.

> **그렇게 분리한 업무와 도메인 사이를 누가, 누구에게, 어떤 방식으로 호출해야 하는가?**

즉 7장의 중심은 다음이다.

```text
Domain Boundary
      ↓
Allowed Dependency
      ↓
Call Path
      ↓
Protocol
      ↓
Context Propagation
      ↓
Transaction Boundary
      ↓
Failure Boundary
```

독자가 7장을 읽은 후 다음을 판단할 수 있어야 한다.

- 이것은 같은 도메인 내부 호출인가?
- 다른 도메인 호출인가?
- 직접 Java 호출이 가능한가?
- Facade를 호출해야 하는가?
- Client를 통해 호출해야 하는가?
- HTTP를 사용해야 하는가?
- TCF를 경유해야 하는가?
- 동기 호출인가?
- 비동기 호출이어야 하는가?
- 다른 도메인의 DAO를 직접 호출해도 되는가?
- 호출 실패 시 어느 영역까지 영향이 가는가?

# 8. 7.1 PDMG에서 도메인의 의미

일반적인 DDD 교과서 설명으로 시작해서 PDMG와 무관한 이야기를 길게 하지 마라.

최소 다음 관점을 구분한다.

```text
시스템
   ↓
업무
   ↓
세부업무
   ↓
프로그램
   ↓
거래
```

그리고 각 단계가 다음과 어떤 관계를 가지는지 설명한다.

- 업무 코드
- 프로그램 ID
- Service ID
- Package
- Handler
- Facade
- Service
- DAO
- URL
- 거래 로그

# 9. 도메인과 패키지를 동일시하지 않는다

다음 오해를 반드시 설명한다.

> "패키지가 다르면 무조건 다른 도메인인가?"

> "같은 패키지 아래 있으면 같은 도메인인가?"

패키지는 물리적 구조이며 도메인은 논리적 업무 경계일 수 있다.

실제 PDMG 기준을 확인하여 둘의 관계를 설명한다.

```text
업무 Domain
     │
     ├─ 프로그램 A
     │    ├─ Handler
     │    ├─ Facade
     │    ├─ Service
     │    └─ DAO
     │
     └─ 프로그램 B
          ├─ Handler
          ├─ Facade
          ├─ Service
          └─ DAO
```

# 10. 시스템 도메인을 설명한다

7.2에서는 시스템 공통 기능과 업무 기능의 차이를 설명한다.

예를 들어 실제 PDMG에서 확인 가능한 다음 영역을 검토한다.

- TCF
- 시스템 선처리
- 시스템 후처리
- JWT
- ServiceContext
- GUID
- Transaction
- Timeout
- Exception
- Logging

다만 이것들을 모두 업무 도메인이라고 표현하지 않는다.

다음 관계를 설명한다.

```text
System Domain
       │
       ├─ Request Control
       ├─ Transaction Control
       ├─ Security
       ├─ Context
       └─ Common Runtime

Business Domain
       │
       └─ 실제 업무 기능
```

실제 PDMG 구조에 맞게 조정한다.

# 12. 프로그램 도메인

프로그램 단위의 책임을 설명한다.

다음 관계를 보여준다.

```text
업무 Domain
     ↓
Program
     ↓
Service ID
     ↓
Handler / Controller
     ↓
Facade
     ↓
Service
```

프로그램이 단순 Java Class 하나가 아니라 **업무 기능의 실행 단위**라는 점을 설명한다.

# 13. 거래 도메인

프로그램과 거래의 차이를 설명한다.

하나의 프로그램이 여러 거래 유형을 가질 수 있다면 실제 기준으로 설명한다.

예:

```text
Program
  │
  ├─ S : 조회
  ├─ C : 등록
  ├─ U : 수정
  ├─ D : 삭제
  ├─ A : 업무 실행
  └─ R : 보고서
```

실제 PDMG Service ID 규칙을 확인하여 표현한다.

4장의 Service ID 내용을 반복하지 말고 **도메인/호출 단위 관점**으로 설명한다.

# 14. 7.6 도메인 간 의존 관계는 7장의 핵심 절이다

단순히

> "도메인 간 결합도를 낮춘다."

라고 쓰지 마라.

반드시 호출 허용/금지 규칙을 구체적으로 설명한다.

예를 들어 실제 PDMG 기준을 검증한 후 다음과 같은 표를 작성한다.

| Caller            | Callee           |   허용 여부 | 권장 호출 방식        | 이유           |
| ----------------- | ---------------- | ----------: | --------------------- | -------------- |
| 같은 업무 Service | 같은 업무 Rule   |           O | Java 호출             | 내부 업무 규칙 |
| Service           | 같은 업무 DAO    |           O | Interface 호출        | DB 접근        |
| 업무 A            | 업무 B DAO       | X 또는 제한 | Client/공개 Interface | 내부 구현 침범 |
| Controller        | DAO              |           X | Facade 경유           | 계층 위반      |
| 업무 A            | 업무 B 내부 Rule |           X | 공개 경계 사용        | 도메인 침범    |

실제 기준과 맞게 수정한다.

# 15. 허용 의존 방향을 시각화한다

예:

```text
Domain A
   │
   ├─ Entry
   │    ↓
   ├─ Facade
   │    ↓
   ├─ Service
   │    ├─ Rule
   │    ├─ DAO
   │    └─ Client
   │
   │               Domain B
   │                   │
   └──── Client ───────► Public Boundary
```

다른 도메인의 내부 DAO나 Rule을 직접 참조하는 구조와 비교한다.

```text
Domain A Service
       │
       └──────── X ───────► Domain B DAO
```

왜 문제가 되는지 설명한다.

- 데이터 소유권
- Transaction 경계
- 변경 영향
- 재사용 착각
- 업무 결합
- 테스트 어려움
- 장애 영향

# 16. 같은 JVM이라고 해서 직접 호출이 항상 정답은 아니다

매우 중요한 부분이다.

다음 질문을 다룬다.

> 두 업무가 같은 WAR 또는 같은 JVM에 있으면 Service Bean을 직접 주입해도 되는가?

기술적으로 가능하다는 것과 아키텍처적으로 허용된다는 것은 다르다.

다음을 구분한다.

```text
Technical Possibility
        ≠
Architecture Permission
```

실제 PDMG 표준에 따라 판단한다.

# 17. TCF ON 호출

```text
Caller
  ↓
HTTP / online 요청
  ↓
Filter
  ↓
Interceptor
  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
STF
  ↓
TransactionDispatcher
  ↓
TransactionHandler
  ↓
Business Facade
  ↓
Business Service
```

다만 12장에서 TCF를 상세 설명하므로 여기서는 **도메인 호출 방식 관점**에 집중한다.

반드시 설명한다.

- Service ID가 호출 대상을 어떻게 결정하는가
- Handler Registry가 어떤 역할을 하는가
- 호출자가 상대 구현 Class를 알아야 하는가
- 호출 경계에서 Context는 어떻게 전달되는가

# 18. TCF OFF 호출

TCF OFF를 단순히

> "TCF를 거치지 않는다."

라고 설명하지 않는다.

실제 Source를 확인하여 다음을 비교한다.

```text
TCF ON

Request
 → /online
 → TCF
 → Handler
 → Facade


TCF OFF

Request
 → Business Controller
 → Facade
```

그리고 다음을 설명한다.

- 공통으로 유지되는 계층
- 달라지는 진입점
- Handler 사용 여부
- 시스템 선후처리 변화
- Transaction 영향
- Timeout 영향
- 예외 처리 영향

상세 트랜잭션은 22장, Timeout은 23장에서 다루므로 여기서는 호출 구조의 차이에 집중한다.

---

# 19. TCF ON/OFF에서도 업무 구조를 최대한 공통화해야 한다

중요한 아키텍처 원칙으로 설명한다.

잘못된 구조:

```text
TCF ON
Handler
  ↓
Service A


TCF OFF
Controller
  ↓
Service B

서로 다른 업무 구현
```

권장 개념:

```text
TCF ON
Handler
   │
   ▼

        Business Facade
              ↓
           Service

   ▲
   │
TCF OFF
Controller
```

실제 PDMG 구조와 맞게 조정한다.

핵심은 **진입점은 달라도 업무 핵심 로직은 공유한다**는 것이다.

---

# 20. UI 직접 호출

7.9에서는 UI가 어느 모듈을 직접 호출하는지 실제 구성을 확인한다.

다음을 설명한다.

```text
Browser
   ↓
pdmg-ui
   ↓
Business API
```

다음 질문에 답한다.

- UI가 어떤 URL을 알고 있는가?
- Service ID는 누가 구성하는가?
- 인증 Token은 어떻게 전달되는가?
- 직접 호출의 장점은 무엇인가?
- 직접 호출의 제약은 무엇인가?

전문 상세는 8장으로 넘긴다.

---

# 21. UI Relay 호출

Relay라는 이름만 설명하지 않는다.

다음 구조를 보여준다.

```text
Browser
   ↓
pdmg-ui
   ↓
Relay
   ↓
Target Service
```

직접 호출과 비교한다.

| 기준        | 직접 호출     | Relay           |
| ----------- | ------------- | --------------- |
| 목적        | 직접 업무 API | 중계            |
| Target 인지 | UI            | Relay           |
| CORS 영향   | 큼            | 상대적으로 단순 |
| 보안 경계   | 직접          | 중계 가능       |
| 운영 추적   | 직접          | Relay 포함      |
| 장애 구간   | 짧음          | 한 단계 증가    |

실제 PDMG 구현을 확인하여 정확하게 수정한다.

---

# 22. 외부 시스템 호출

내부 도메인 호출과 외부 시스템 호출을 명확히 구분한다.

예:

```text
PDMG Business Service
         ↓
       Client
         ↓
Protocol Adapter
         ↓
External System
```

다음 책임을 Client 쪽에서 고려해야 함을 설명한다.

- URL/Endpoint
- Authentication
- Connection Timeout
- Read Timeout
- Request 변환
- Response 변환
- Error 변환
- GUID/Trace 전달
- Logging
- Retry 여부

단, 현재 실제 구현에서 확인되지 않은 기능을 적용되어 있다고 단정하지 않는다.

---

# 23. 다른 도메인 호출과 외부 시스템 호출을 비교한다

다음 차이를 설명한다.

```text
Domain Internal Call

PDMG
 └─ Domain A
       ↓
    Domain B


External Call

PDMG
 └─ Domain A
       ↓
     Client
       ↓
External System
```

호출 경계가 달라지면

- 실패 모델
- Timeout
- Transaction
- 보안
- 데이터 계약

도 달라진다는 것을 설명한다.

---

# 24. 동기 호출

다음 구조를 설명한다.

```text
Caller Thread
      ↓
Call
      ↓
Wait
      ↓
Response
      ↓
Continue
```

동기 호출의 장점을 설명한다.

- 즉각적인 결과
- 간단한 오류 전파
- 순차 처리

그리고 위험도 설명한다.

- 응답 지연 전파
- Timeout 연쇄
- Thread 점유
- 장애 전파

---

# 25. 비동기 호출

단순히 `@Async`를 사용한다고 설명하지 않는다.

다음을 설명한다.

```text
Request Thread
     │
     │ submit
     ▼
Worker Thread / Queue
     │
     ▼
Async Task
```

특히 PDMG에서는 다음을 반드시 확인한다.

- ServiceContext
- ThreadLocal
- MDC
- GUID
- Transaction
- Security Context
- Exception
- Timeout

Thread가 달라질 경우 자동으로 이어지는 것과 이어지지 않는 것을 실제 구현 기준으로 설명한다.

---

# 26. 동기와 비동기 선택 기준

실제 판단표를 작성한다.

| 기준                  |            동기 |           비동기 |
| --------------------- | --------------: | ---------------: |
| 즉시 결과 필요        |            적합 |      부적합 가능 |
| 업무 Transaction 연계 |            단순 |        별도 고려 |
| 대기 시간             |            발생 | Caller 감소 가능 |
| Context 전달          | 상대적으로 단순 |   별도 전파 필요 |
| 오류 전달             |            직접 |        별도 처리 |
| 재처리                |     호출자 중심 |   별도 설계 가능 |

그리고 다음 질문을 던진다.

> 시간이 오래 걸리면 무조건 비동기로 바꾸는 것이 옳은가?

아니다.

업무 일관성과 결과 요구사항을 먼저 판단해야 한다.

---

# 27. 호출과 Transaction 경계를 혼동하지 않는다

중요한 설명이다.

```text
Java Method Call
      ≠
Transaction Boundary

HTTP Call
      ≠
Distributed Transaction

Async Call
      ≠
기존 Transaction 지속
```

예를 들어 HTTP로 다른 시스템을 호출한다고 해서 하나의 Spring DB Transaction이 자동으로 이어지지 않는다.

실제 PDMG Transaction 구조와 연결하되 상세는 21~23장으로 넘긴다.

---

# 28. ServiceContext와 GUID 전달을 설명한다

도메인 호출에서 Trace 정보가 왜 필요한지 설명한다.

```text
Domain A
 GUID = X
    │
    ▼
Domain B
 GUID = X
    │
    ▼
External System
 Trace Header = X
```

실제 구현에서 GUID가 어디까지 전달되는지 확인한다.

확인되지 않으면 TO-BE 또는 권장안으로 구분한다.

---

# 29. 오류 전파를 설명한다

다음처럼 정상 호출만 설명하지 않는다.

```text
A → B → 성공
```

다음도 설명한다.

```text
Domain A
   ↓
Domain B
   ↓
Exception
   ↓
Error Mapping
   ↓
Domain A
   ↓
Standard Error Response
```

다음 질문에 답한다.

- 상대 도메인의 내부 Exception을 그대로 노출하는가?
- 오류 코드를 변환하는가?
- 외부 시스템의 HTTP 오류를 그대로 사용하는가?
- Timeout은 어떤 예외로 변환되는가?

실제 구현을 확인한다.

---

# 30. 금지 호출 패턴을 별도 절 또는 박스로 설명한다

대표적인 Anti Pattern을 다룬다.

## Anti Pattern 1 — 다른 업무 DAO 직접 호출

```text
IC Service
    │
    X
    ▼
SV DAO
```

문제:

- 데이터 소유권 침범
- 업무 규칙 우회
- 결합도 증가
- 변경 영향 확대

---

## Anti Pattern 2 — Controller 간 호출

```text
Controller A
     ↓
Controller B
```

Web Entry를 내부 Business API처럼 사용하지 않는다.

---

## Anti Pattern 3 — 다른 도메인 Rule 직접 사용

```text
Domain A Service
       ↓
Domain B Rule
```

Rule이 공개 계약인지 내부 구현인지 판단해야 한다.

---

## Anti Pattern 4 — 순환 의존

```text
Domain A
   ↓
Domain B
   ↓
Domain C
   ↓
Domain A
```

어떤 문제를 만드는지 설명한다.

---

## Anti Pattern 5 — 외부 호출을 Service마다 직접 구현

```text
Service A ──► HTTP
Service B ──► HTTP
Service C ──► HTTP
```

Client/Adapter 경계를 사용하는 이유를 설명한다.

---

# 31. 순환 의존을 반드시 다룬다

도메인 간 호출에서 특히 중요하다.

```text
IC
 ↓
SV
 ↓
MG
 ↓
IC
```

순환 의존이 생기면 다음 문제가 발생할 수 있음을 설명한다.

- 변경 영향
- 테스트
- Bean 의존
- 업무 책임 혼란
- 장애 전파

PDMG에서 어떤 구조로 방지하는 것이 적절한지 실제 기준과 권장안을 구분한다.

---

# 32. 공개 경계와 내부 구현을 구분한다

도메인마다 다음 개념을 설명한다.

```text
Domain
 │
 ├─ Public Boundary
 │
 └─ Internal Implementation
```

예:

```text
External Allowed
      ↓
Facade / Client / Contract
      ↓
-------------------------
Domain Boundary
-------------------------
      ↓
Service
Rule
DAO
Mapper
```

실제 PDMG에서 Facade가 외부 공개 경계인지, Client가 별도 필요한지는 소스를 확인한다.

추측하지 않는다.

# 34. 하나의 실제 호출 사례를 장 전체에서 사용한다

가능하면 실제 PDMG 업무 두 개를 선정한다.

예:

```text
Domain A
   ↓
Domain B
```

그리고 장 전체에서 동일 사례로 다음을 추적한다.

```text
UI
 ↓
Domain A Entry
 ↓
Domain A Facade
 ↓
Domain A Service
 ↓
Domain B 호출 필요
 ↓
호출 경계 선택
 ↓
Domain B
 ↓
Result
 ↓
Domain A
 ↓
UI
```

실제 Source로 확인되지 않는 업무명이나 호출 관계는 사실처럼 작성하지 않는다.

가상 예제라면 명확하게 표시한다.

- [ ] AS-IS / 표준 / Legacy / TO-BE를 구분했는가?
- [ ] 실제 Source에서 확인하지 않은 구조를 사실처럼 쓰지 않았는가?
- [ ] 제목 + 불릿 몇 개로 끝난 절이 없는가?
- [ ] 앞 장보다 설명 깊이가 낮아지지 않았는가?

하나라도 부족하면 보고만 하지 말고 본문을 직접 수정하여 보강한다.

# 40. 7장 최종 완료 기준

7장이 완료되었다는 것은 7.1~7.13까지 텍스트가 존재한다는 뜻이 아니다.

독자가 다음 설계 문제를 해결할 수 있어야 한다.

> 업무 A가 업무 B의 기능을 사용해야 한다.
>
> 같은 Java 프로세스에 있으니 업무 B의 DAO 또는 Service를 직접 호출할 것인지,
> Facade를 사용할 것인지,
> Client를 둘 것인지,
> HTTP/TCF를 경유할 것인지,
> 동기 또는 비동기로 처리할 것인지 판단하고,
> Transaction, Timeout, Context, GUID, Exception까지 고려하여
> 올바른 호출 구조를 설계하라.

독자가 이 문제를 스스로 판단할 수 있을 정도로 구체적으로 작성한다.

# 41. 최종 집필 명령

**도메인의 정의만 설명하지 마라.**

**도메인 사이의 경계를 설명하라.**

**호출할 수 있다는 것과 호출해도 된다는 것을 구분하라.**

**다른 업무의 DAO를 공유 API처럼 사용하지 못하도록 호출 원칙을 명확히 하라.**

**TCF ON/OFF의 진입 경로 차이를 보여주되 업무 핵심 구조가 어떻게 공통화되는지 설명하라.**

**UI 직접 호출, Relay, 내부 도메인, 외부 시스템을 하나의 호출 아키텍처 안에서 연결하라.**

**동기/비동기를 단순 성능 선택으로 설명하지 말고 Transaction, Thread, Context, 오류 모델까지 설명하라.**

**호출 경계와 Transaction 경계를 혼동하지 마라.**

**실제 PDMG Source에서 확인하지 않은 호출 구조를 현재 표준처럼 만들어내지 마라.**

작성 → Source 검증 → 자체검수 → 부족한 절 보강 → 최종 파일 저장까지 완료하라.
