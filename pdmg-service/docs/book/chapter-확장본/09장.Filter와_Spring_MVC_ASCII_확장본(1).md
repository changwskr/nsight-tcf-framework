# 제9장. Filter와 Spring MVC

> **집필 기준**
>
> 이 장은 `book.zip`의 제9장 「Filter와 Spring MVC」와 `13.Filter-DefaultFilter`, `14.Spring MVC`, 각 재분석본, `30.왜 Filter와 Interceptor을 합치면 안되는가`, `54.http호출 다이어그램`을 기준으로 확장한다.
>
> 제8장까지 확정한 HTTP 전문을 서버에서 누가 가장 먼저 읽고, 어떤 시점에 Spring MVC로 넘어가며, 요청·응답·오류·Context가 어느 계층에서 처리되는지를 Runtime 순서대로 설명한다.
>
> **AS-IS 핵심 판단**
>
> - `DefaultFilter`는 Servlet/MVC 경계 앞에 있다.
> - Filter는 Body 캐시, 비-local JWT, 공통 Header 파싱/합성, ServiceContext, MDC를 담당한다.
> - Filter는 DB Transaction을 시작하지 않는다.
> - 현재 multipart 분기가 JWT 검증보다 먼저 실행될 수 있어 인증 우회 가능성이 P0 Gap이다.
> - Spring MVC는 DispatcherServlet 이후 HandlerMapping, Interceptor, ArgumentResolver, Controller, ResponseBodyAdvice를 조정한다.
> - 현재 `TCF ON + legacy-web ON`에서 공통 `OnlineTransactionController`와 `ServicePreventionInterceptor`가 활성화된다.
> - Service ID 우선순위는 `ServiceContext Header → JSON Header → Path`이며 불일치 검증은 개선 대상이다.
> - 성공은 `dto`, 표준 오류는 `result`; Filter 조기 오류는 표준 봉투를 보장하지 않는다.
> - Spring MVC 계층에 업무 Transaction을 넣지 않는다.
> - Filter·Interceptor·Advice·TCF는 통합 대상이 아니라 책임 경계가 다른 협력 계층이다.

## 이 장을 시작하며

제8장에서는 브라우저가 보내는 HTTP 요청과 `{ hdr_nhnis, dto }` 표준 전문의 구조를 살펴보았다. 이제 질문은 “서버가 그 요청을 받았을 때 가장 먼저 누가 무엇을 하는가?”로 바뀐다.

PDMG의 HTTP 요청은 곧바로 Controller로 들어가지 않는다.

```text
HTTP Request
  ↓
DefaultFilter
  ↓
Spring SecurityFilterChain
  ↓
DispatcherServlet
  ↓
HandlerMapping
  ↓
ServicePreventionInterceptor
  ↓
Controller
  ↓
TCF / Business
  ↓
ResponseBodyAdvice
  ↓
Interceptor.afterCompletion
  ↓
Filter finally
  ↓
HTTP Response
```

이 장에서는 **Servlet Filter와 Spring MVC 사이의 실행 경계**, **Body·JWT·GUID·ServiceContext·MDC의 생성 시점**, **TCF ON/OFF Controller 선택**, **ArgumentResolver와 ResponseBodyAdvice**, **오류가 발생한 위치에 따른 증적 차이**, **Filter와 Interceptor를 합치면 안 되는 이유**를 하나의 실행선으로 연결한다.

# 9.1 Filter와 Spring MVC의 경계를 먼저 이해한다

Servlet Filter는 DispatcherServlet보다 앞에서 동작하고, Spring MVC는 DispatcherServlet 이후에 Controller·Resolver·Advice를 조정한다. 이 경계를 이해해야 Body 캐싱, 조기 인증 실패, Handler 매핑과 응답 조립 책임을 올바르게 배치할 수 있다.

이 구간은 요청이 아직 업무 코드에 도달하기 전의 **HTTP 진입 경계**다. 여기에서 실패하면 Controller·TCF·업무 SQL을 의심하기 전에 Filter 등록, 요청 Body, 인증, 전문 구조와 CORS를 먼저 확인해야 한다.


### 그림 9-1. Filter와 Spring MVC의 경계를 먼저 이해한다 — 구조


```text
HTTP Request
   ↓
[Servlet Filter]
 DefaultFilter
   ↓
DispatcherServlet
   ↓
[Spring MVC]
 HandlerMapping → Interceptor → Controller → Advice
```


### 그림 9-2. Filter와 Spring MVC의 경계를 먼저 이해한다 — 실행·검증 관점


```text

   ↓

   ↓
```

**아키텍처 판단**


이 책임이 어느 Lifecycle Hook에 있어야 하는지 먼저 판단하고, 다른 계층으로 이동시키기 전에 요청 순서·오류 경로·관측성·ThreadLocal 정리 영향을 확인한다.

# 9.4 DefaultFilter는 업무 Transaction을 시작하지 않는다

DefaultFilter의 책임은 HTTP 진입 환경 준비다. Body 보존, 비-local JWT 검증, hdr_nhnis 파싱, ServiceContext와 MDC 생성은 수행하지만 업무 SQL과 DB Transaction은 실행하지 않는다.

이 구간은 요청이 아직 업무 코드에 도달하기 전의 **HTTP 진입 경계**다. 여기에서 실패하면 Controller·TCF·업무 SQL을 의심하기 전에 Filter 등록, 요청 Body, 인증, 전문 구조와 CORS를 먼저 확인해야 한다.
