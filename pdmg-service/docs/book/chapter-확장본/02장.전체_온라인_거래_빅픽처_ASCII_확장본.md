# 제2장. 전체 온라인 거래 빅픽처

> **집필 기준**
>
> 이 장은 현재 PDMG 온라인 거래의 실제 호출 흐름을 기준으로 한다.
> 주 흐름은 다음 설정이 활성화된 상태다.
>
> ```yaml
> nhnis:
>   fw:
>     tcf:
>       enabled: true
>     timeout:
>       enabled: true
>       milliseconds: 5000
>       pool-size: 20
>       queue-capacity: 100
>     commons:
>       legacy-web:
>         enabled: true
>       filter:
>         enabled: true
> ```
>
> 원본 다이어그램과 현재 구현이 충돌하는 경우 현재 실행 소스와 설정을 우선한다.
> `STF`, `ETF`, `Rule`처럼 설계상 존재하지만 현재 주 호출선에 연결되었다고 확인되지 않은 요소는 실제 실행 흐름에 임의로 포함하지 않는다.

---

# 2.1 제1장의 정적 지도를 이제 시간순으로 펼쳐 본다

제1장은 PDMG를 구성하는 모듈과 컴포넌트를 하나의 지도로 보았다.  
제2장에서는 그 지도 위에서 **온라인 요청 한 건이 실제로 움직이는 시간 순서**를 따라간다.

제1장에서 다음 구조를 보았다.

```text
Browser
  ↓
Filter
  ↓
Interceptor
  ↓
TCF
  ↓
Handler
  ↓
Facade
  ↓
Service
  ↓
DAO
  ↓
DB
```

그러나 이 그림만 알고 있어서는 PDMG의 실제 동작을 충분히 설명할 수 없다.

왜냐하면 실제 온라인 거래에서는 다음과 같은 질문이 더 중요하기 때문이다.

```text
Filter와 Service는 같은 Thread에서 실행되는가?

DB Transaction은 HTTP 요청이 들어오는 순간부터 시작되는가?

Handler는 Transaction 안인가 밖인가?

Facade @Transactional은 언제 실제 BEGIN을 만드는가?

Timeout 5초가 지나면 SQL도 정확히 5초에 끝나는가?

HTTP 504가 나간 시점과 DB Rollback 시점은 같은가?

업무가 Rollback되면 ImageLog도 같이 Rollback되는가?

Filter에서 401이 발생하면 표준 오류 전문이 만들어지는가?
```

이 장에서 가장 먼저 버려야 할 오해는 다음이다.

> **온라인 거래 한 건의 생명주기와 DB Transaction의 생명주기는 같은 것이 아니다.**

또 하나는 다음이다.

> **TCF ON + Timeout ON에서는 HTTP Request Thread와 실제 업무 Worker Thread가 다르다.**

이 두 사실을 이해하면 이후의 Filter, Interceptor, TCF, Transaction, Timeout, Exception 장을 훨씬 쉽게 읽을 수 있다.

# 2.2 가장 먼저 전체 흐름을 본다

현재 기본 경로는 브라우저가 `pdmg-service`를 직접 호출하는 방식이다. `pdmg-ui`의 Relay 경로는 호환용으로 남아 있지만, 일반 화면의 주 경로로 단정하지 않는다.

### 그림 2-1. PDMG 온라인 거래 전체 흐름

```text
┌──────────────────────────────────────────────────────────────┐
│                         pdmg-ui                              │

  │                                         │        BEGIN            │
  │                                         │          ↓              │
  │                                         │ TransactionDispatcher   │
  │                                         │          ↓              │
  │                                         │ TransactionHandler      │
  │                                         │          ↓              │

  │                                         │          ↓              │

  │ 알려진 예외인 경우
```

다음 세 개의 경계다.

```text
① HTTP Request Thread 경계

② Worker Thread 경계

③ DB Transaction 경계
```

PDMG의 현재 Timeout ON 구조에서는 이 세 경계가 서로 같지 않다.

# 2.3 한 건의 거래를 세 개의 생명주기로 나누어 본다

온라인 요청을 이해하기 쉽게 만드는 방법은 한 거래를 다음 세 개의 생명주기로 분리하는 것이다.

### 그림 2-2. 한 건의 거래에 존재하는 세 개의 생명주기

```text
시간 ──────────────────────────────────────────────────────────────>

HTTP Request Lifecycle
├─────────────────────────────────────────────────────────────────┤
Request 수신                                                Response 종료


Online Transaction Lifecycle
      ├─────────────────────────────────────────────────────┤
      공통 준비 → 거래 식별 → 업무 실행 → 응답/감사


DB Transaction Lifecycle
                           ├────────────────────────────┤
                           BEGIN                    COMMIT/ROLLBACK
                           Dispatcher → Handler → Facade
                                      → Service → DAO
```

세 생명주기의 의미는 다음과 같다.

| 생명주기 | 시작 | 종료 | 핵심 관심사 |
|---|---|---|---|
| HTTP 요청 | Servlet 요청 수신 | HTTP 응답/Filter 종료 | Network, CORS, Header, Status |
| 온라인 거래 | 공통 진입/거래 식별 | 시스템 후처리 완료 | Service ID, GUID, TCF, 오류 |
| DB Transaction | TX BEGIN | COMMIT/ROLLBACK | 데이터 원자성 |

따라서 다음 표현은 정확하지 않다.

```text
"요청이 시작되었으므로 Transaction도 시작됐다."
```

정확한 그림은 다음이다.

### 그림 2-3. HTTP 요청과 DB Transaction은 같은 박스가 아니다

```text
┌────────────────────── HTTP Request ──────────────────────────────┐
│                                                                  │
│ Filter                                                           │
│   ↓                                                              │
│ Interceptor                                                      │
│   ↓                                                              │
│ Controller                                                       │
│   ↓                                                              │
│ TcfFacade                                                        │
│   ↓                                                              │
│ Executor                                                         │
│             ┌────────── DB Transaction ──────────────┐           │
│             │ BEGIN                                  │           │
│             │ Dispatcher → Handler → Facade          │           │
│             │              → Service → DAO → DB      │           │
│             │                              COMMIT/RB │           │
│             └────────────────────────────────────────┘           │
│   ↓                                                              │
│ Response Advice                                                  │
│   ↓                                                              │
│ afterCompletion                                                  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

이 그림은 이후 21~23장의 핵심 전제가 된다.

# 2.4 UI에서 HTTP 요청이 만들어지는 구간

실제 사례로 거래 파라미터 목록 조회 거래를 생각해 보자.

예:

```text
Service ID = mgcoa9000S0
```

화면은 Service ID를 선택하고 요청 전문을 만든다.

### 그림 2-4. UI에서 온라인 요청 생성

```text

  │
  │ "조회" 클릭

              │

              ▼
       service-client.js
              │
              │ HTTP POST
              ▼
      pdmg-service :8080
```

현재 일반 화면의 주 호출 구조는 다음과 같이 본다.

### 그림 2-5. 직접 호출과 Relay 호환 경로

```text
[현재 일반 화면 주 경로]

Browser :8090
    │
    │ CORS
    ▼
pdmg-service :8080
    │
    ▼

    │
```

```text

```

이 차이는 장애 분석에서 중요하다.

# 2.5 HTTP 요청 전문은 Header와 업무 DTO를 함께 운반한다

PDMG의 온라인 HTTP Body는 시스템 공통정보와 업무 데이터를 한 봉투에 담는다.

### 그림 2-6. 요청 전문 구조

```text
┌──────────────────────────────────────────┐
│               HTTP Body                  │
├──────────────────────────────────────────┤
│ hdr_nhnis                                │
│   └─ sys_comm                            │
│        ├─ std_gbl_id   : GUID            │
│        ├─ rms_svc_c    : Service ID      │
│        ├─ optr_eno     : 사용자          │
│        ├─ tr_brc       : 점코드          │
│        ├─ tr_trm_ipadr : 단말/IP          │
│        └─ ...                            │
├──────────────────────────────────────────┤
│ dto                                      │
│   ├─ pageNo                              │
│   ├─ pageSize                            │
│   └─ 업무별 입력 필드                    │
└──────────────────────────────────────────┘
```

온라인 Controller 이후에는 `dto`만 업무 실행 입력으로 전달된다.

### 그림 2-7. 공통 Header와 업무 DTO의 분리

```text
                전체 전문
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
     hdr_nhnis             dto
          │                 │
          ▼                 ▼
   ServiceContext       TcfFacade
          │                 │
          │                 ▼
          │              Handler
          │                 ▼
          │              Facade
          │                 ▼
          │              Service
          │
          └───── 시스템 공통정보
```

업무 Service가 HTTP 전체 JSON을 직접 해석하지 않는 이유도 여기에 있다.

# 2.6 CORS는 업무 실행 이전에 실패할 수 있다

브라우저가 `pdmg-ui:8090`에서 `pdmg-service:8080`을 직접 호출하면 Origin이 다르다.

```text
http://localhost:8090
        ≠
http://localhost:8080
```

따라서 브라우저는 CORS 정책의 영향을 받는다.

### 그림 2-8. 브라우저 직접 호출의 CORS 흐름

```text
Browser
   │
   │ OPTIONS /mgcoa9000S0
   ▼
CORS 처리
   │
   ├─ 허용 ─────────────────┐
   │                        ▼
   │                POST /mgcoa9000S0
   │                        │
   │                        ▼
   │                 DefaultFilter
   │
   └─ 거부
        │
        ▼
   Browser에서 차단
   업무 Controller 미실행
```

따라서 브라우저 화면에서 “요청 실패”가 보였다고 반드시 업무 Service가 실패한 것은 아니다.

```text
Browser 오류
   ├─ CORS
   ├─ Network
   ├─ 400/401 Filter
   ├─ 503 Executor
   ├─ 504 Timeout
   └─ 500 업무/시스템
```

오류의 위치를 먼저 알아야 한다.

# 2.7 DefaultFilter는 온라인 거래 실행 환경을 만든다

HTTP 요청이 서버로 들어오면 가장 먼저 중요한 공통 작업을 수행하는 곳이 `DefaultFilter`다.

### 그림 2-9. DefaultFilter의 처리 순서

```text
HTTP Request
    │
    ▼
┌──────────────────────────────┐
│       DefaultFilter          │
├──────────────────────────────┤
│ 1. OPTIONS 제외 여부         │
│ 2. Multipart 여부            │
│ 3. 요청 Body Cache           │
│ 4. 비-local JWT 확인         │
│ 5. JSON 파싱                 │
│ 6. hdr_nhnis 확인/합성       │
│ 7. GUID / Service ID 보강    │
│ 8. ServiceContext 생성       │
│ 9. MDC 설정                  │
│10. filterChain.doFilter      │
│11. finally Context 정리      │
└──────────────────────────────┘
    │
    ▼
Spring MVC
```

Filter의 책임은 “업무 실행”이 아니다.

### 그림 2-10. Filter가 하는 일과 하지 않는 일

```text
DefaultFilter

[한다]
  Body Cache
  Header 처리
  JWT 검증
  ServiceContext
  GUID / MDC

[하지 않는다]
  Business Service 호출
  DAO 호출
  SQL 실행
  업무 Transaction 시작
  업무 오류 판단
```

Filter에서 실패하면 TCF까지 도달하지 않는다.

### 그림 2-11. Filter 조기 실패

```text
DefaultFilter
    │
    ├─ Token 없음 ───────> 401 sendError
    │
    ├─ Token 실패 ───────> 401 sendError
    │
    ├─ Body 없음 ────────> 400 sendError
    │
    ├─ JSON 오류 ────────> 400 sendError
    │
    ├─ Header 오류 ──────> 400 sendError
    │
    └─ 정상
         │
         ▼
      MVC 진입
```

이 경우 `GlobalExceptionHandler`와 표준 오류 전문 조립을 항상 기대할 수 없다.

# 2.8 ServiceContext가 Request Thread의 공통 상태를 만든다

Filter는 요청 한 건의 공통 정보를 `ServiceContext`에 보관한다.

### 그림 2-12. Request Thread의 ServiceContext

```text
Request Thread

ServiceContextHolder
      │
      ▼
┌──────────────────────────────┐
│ ServiceContext               │
├──────────────────────────────┤
│ applicationName              │
│ active profile               │
│ GUID                         │
│ hdr_nhnis                    │
│ HTTP Header Snapshot         │
│ requestBody                  │
│ responseBody                 │
│ userContext                  │
└──────────────────────────────┘

ThreadContext(MDC)
      │
      ├─ guid
      ├─ serviceId
      ├─ userId
      └─ ip
```

여기서 중요한 점은 `ServiceContextHolder`가 `ThreadLocal`이라는 사실이다.

```text
Request Thread에 존재
      ≠
Worker Thread에 자동 존재
```

Thread가 바뀌면 Context 전달 문제가 발생한다.

# 2.9 Interceptor가 시스템 선처리를 시작한다

Spring MVC가 대상 Controller를 선택한 뒤 실제 Controller 실행 전에 `ServicePreventionInterceptor.preHandle()`이 호출된다.

### 그림 2-13. Interceptor의 위치

```text
DefaultFilter
    │
    ▼
DispatcherServlet
    │
    ▼
HandlerMapping
    │
    ▼
ServicePreventionInterceptor.preHandle
    │
    ▼
OnlineTransactionController
```

현행 `preHandle()`의 실제 역할은 차단보다 공통정보 보강과 감사 시작 기록에 가깝다.

### 그림 2-14. 시스템 선처리

```text
preHandle
   │
   ├─ Header/sys_comm 보장
   │
   ├─ GUID 보장
   │
   ├─ Service ID/IP/User 보완
   │
   ├─ 요청 전문 로그
   │
   ├─ ImageLog INSERT
   │
   └─ return true
         │
         ▼
     Controller 실행
```

이름이 `ServicePreventionInterceptor`라고 해서 현재 실제 거래통제가 모두 이곳에서 수행된다고 단정해서는 안 된다.

# 2.10 ImageLog는 업무 DB Transaction과 별개다

시스템 선처리에서 요청 전문을 감사하기 위한 ImageLog가 기록된다.

### 그림 2-15. ImageLog와 업무 DB Transaction의 관계

```text
Request Thread

Interceptor.preHandle
    │
    └─ ImageLog INSERT
           │
           │ 업무 TX와 별도
           ▼

             Worker Thread

             TX BEGIN
                │
                ▼
             Service
                │
                ▼
               DAO
                │
             ROLLBACK
                │
                ▼

Request Thread
afterCompletion
    │
    └─ ImageLog UPDATE
```

따라서 다음 관계가 성립한다.

```text
업무 Rollback
    ≠
ImageLog 자동 Rollback
```

오히려 업무가 실패했을 때도 요청 기록이 남아 있어야 장애를 추적할 수 있다.

# 2.11 OnlineTransactionController는 거래를 실행하지 않고 입구를 통일한다

TCF ON에서는 공통 `OnlineTransactionController`가 거래 진입점 역할을 한다.

### 그림 2-16. OnlineTransactionController의 책임

```text
HTTP POST
   │
   ▼
OnlineTransactionController
   │
   ├─ Service ID 결정
   │
   ├─ 요청 전체 JSON 확인
   │
   ├─ dto 추출
   │
   └─ TcfFacade.process(...)
          │
          ▼
        TCF
```

```text

  X SQL
  X 업무 계산

  X Transaction Commit
  X Timeout Worker 직접 관리
```

# 2.15 ThreadLocal Context는 명시적으로 전달한다

`ServiceContextHolder`와 Log4j2 `ThreadContext`는 자동으로 새 Worker Thread로 이동하지 않는다.

### 그림 2-21. Worker Context 전달

```text
Request Thread

Holder = ServiceContext A
MDC    = { guid, serviceId, userId, ip }

        │
        │ capture()
        ▼

   ├─ ServiceContext 참조
   └─ MDC Snapshot

        ▼
```

# 2.16 현재 Worker Context는 같은 ServiceContext 참조를 공유한다

현행 Context 전달에서 한 가지 중요한 구조적 주의점이 있다.

### 그림 2-22. 같은 mutable ServiceContext 참조 공유

```text
                    ServiceContext A
                    ┌──────────────┐
Request Thread ─────┤              ├───── Worker Thread
                    │ header       │
                    │ responseBody │
                    │ userContext  │
                    │ request/ref  │
                    └──────────────┘
```

즉 완전히 독립된 immutable Snapshot을 만드는 것이 아니라 같은 `ServiceContext` 객체 참조를 Worker에서 다시 설치하는 구조가 포함될 수 있다.

정상적으로 Worker가 먼저 끝나면 문제가 잘 보이지 않지만 Timeout 후 Worker가 즉시 끝나지 않는다면 Request Thread와 Worker Thread가 동일 mutable 객체를 보는 시간이 생길 수 있다.

따라서 업무 Worker에서는 Servlet Request/Response 객체를 직접 사용하는 패턴을 피해야 한다.

Timeout ON의 현재 기본 흐름에서 실제 외곽 DB Transaction은 Worker에서 시작된다.

### 그림 2-23. Worker TransactionTemplate

```text
Worker Thread

╔══════════════════════════════════════════════╗
║ TransactionTemplate                         ║
║ rdwTransactionManager                       ║
║                                              ║
║ BEGIN                                        ║
║   │                                          ║
║   ▼                                          ║
║ TransactionDispatcher                        ║
║   │                                          ║
║   ▼                                          ║
║ TransactionHandler                           ║
║   │                                          ║
║   ▼                                          ║
║ Business Facade                              ║
║   │                                          ║
║   ▼                                          ║
║ BizPrePostAspect                             ║
║   │                                          ║
║   ▼                                          ║
║ Service → DAO → Mapper → DB                  ║
║   │                                          ║
║   ▼                                          ║
```

# 2.20 Facade는 외곽 Worker Transaction에 참여한다

Facade에 `@Transactional`이 있어도 Timeout ON에서는 Facade가 항상 새 Transaction을 만드는 것이 아니다.

### 그림 2-26. Timeout ON에서 Facade의 Transaction 참여

```text
Worker TransactionTemplate
        │
        │ BEGIN
        ▼
   Dispatcher
        │
        ▼
     Handler
        │
        ▼
┌──────────────────────────────┐
│ Facade Proxy                 │
│ @Transactional(REQUIRED)     │
└──────────────┬───────────────┘
               │
               │ 기존 TX 존재
               ▼
          같은 TX 참여
               │
               ▼
            Service
```

정확한 표현은 다음이다.

```text
TransactionTemplate
  = 외곽 물리 Transaction 시작점

Facade @Transactional(REQUIRED)
  = 기존 Transaction 참여
```

Facade는 여전히 중요한 유스케이스 경계이며 Timeout OFF나 TCF OFF 권장 경로에서는 Transaction 시작점이 될 수 있다.

```text
│
```

# 2.29 cancel(true)는 “즉시 강제 종료”가 아니다

### 그림 2-35. Timeout 취소의 실제 의미

```text
Request Thread
   │
   ├─ Future.cancel(true)
   │
   ▼
Worker Thread
   │
   ├─ Interrupt 요청 받음
   │
   ├─ Java 코드가 반응할 수도 있음
   │
   ├─ JDBC Driver가 즉시 SQL을 취소할 수도/못할 수도 있음
   │
   └─ SQL이 나중에 반환할 수도 있음
```

따라서 Timeout 방어는 cancel 하나에만 의존하지 않는다.

```text
Future Timeout
   ↓
cancel(true)
   ↓
Worker 복귀
   ↓
deadline / interrupted 재검사
   ↓
late COMMIT 차단
   ↓
ROLLBACK
```

# 2.30 Deadline 검사는 늦게 끝난 업무의 COMMIT을 막는다

### 그림 2-36. 늦은 결과의 COMMIT 차단

```text
Worker SQL
   │
   │ 오래 실행
   ▼
SQL 결과 반환
   │
   ▼
"업무 결과는 정상 데이터"
   │
   ▼
Deadline 확인
   │
   ├─ 제한시간 안
   │      │
   │      ▼
   │    COMMIT
   │
   └─ 제한시간 초과
          │
          ▼
     rollbackOnly
          │
          ▼
       ROLLBACK
```

즉 “SQL이 성공했다”와 “거래가 Commit된다”는 같은 말이 아니다.

```text
SQL 성공
   +
Deadline 초과
   =
Transaction Rollback 가능
```

Worker 결과가 Request Thread로 돌아오면 응답 조립과 감사 완료가 이어진다.

### 그림 2-37. 시스템 후처리

```text
Worker
  │
  │ COMMIT / ROLLBACK 완료
  ▼
Request Thread
  │
  ▼
Controller Return / Exception
  │
  ▼
ResponseBodyAdvice
  │
  ├─ hdr_nhnis

  │
  ▼

  │
  ├─ 정상 → postImagelog
```

```text
  ≠ DB Transaction afterCommit
```

# 2.32 ImageLog의 완료 시점을 Commit과 혼동하지 않는다

### 그림 2-38. Business TX와 ImageLog 시간 관계

```text
     │
     ▼
     [업무 TX BEGIN]
          │
          │ Service / SQL
          │
```

# 2.43 현재 구조에서 중요한 아키텍처 판단

## 2.43.1 시스템 선처리는 Transaction 밖에 둔다

```text
Request 감사
   ↓
업무 TX
   ↓
업무 실패
   ↓
Rollback

그래도
Request 감사 기록은 남아야 함
```

따라서 ImageLog와 시스템 추적을 업무 Transaction에 무조건 묶는 것은 적절하지 않다.

---

## 2.43.2 Timeout은 HTTP 기능이 아니라 실행 경계 기능이다

```text
Timeout
   =
Request 대기시간
+ Worker 실행
+ Interrupt
+ Deadline
+ Transaction Rollback
```

단순히 Controller에 `setTimeout(5000)`을 설정하는 문제와 다르다.

---

## 2.43.3 Transaction 경계는 설정 모드별로 설명해야 한다

다음과 같이 하나의 규칙으로 단정해서는 안 된다.

```text
X "PDMG TX는 Facade에서 시작한다."
```

정확한 설명:

```text
TCF ON + Timeout ON
  → Worker TransactionTemplate

TCF ON + Timeout OFF
  → Facade Proxy

TCF OFF
  → 실제 Controller 호출 구조에 따라 다름
```

---

## 2.43.4 Context는 Thread 전환을 인식해야 한다

```text
ThreadLocal
  = 같은 Thread 안에서는 편리

Thread 전환
  = 명시적 전파 필요
```

Worker Context 캡처는 PDMG Timeout 구조의 필수 구성요소다.

---

## 2.43.5 HTTP 응답만으로 데이터 상태를 판단하지 않는다

```text
HTTP 200
  → Commit 확인 필요

HTTP 504
  → Worker Rollback 완료 확인 필요

HTTP 500
  → Handler/Business/System 위치 확인 필요

ImageLog 존재
  → 업무 Commit 증거 아님
```

# 2.48 제2장에서 반드시 기억할 여섯 가지

첫째, **온라인 거래의 HTTP 생명주기와 DB Transaction 생명주기는 다르다.**

둘째, **TCF ON + Timeout ON에서는 Request Thread와 Worker Thread가 분리된다.**

셋째, **외곽 DB Transaction은 Worker의 `TransactionTemplate`에서 시작하며 Dispatcher와 Handler도 그 기술적 Transaction 안에서 실행된다.**

넷째, **Facade의 `@Transactional(REQUIRED)`는 Timeout ON에서는 기존 Worker Transaction에 참여한다.**

다섯째, **HTTP 504는 Worker와 DB가 이미 완전히 종료됐다는 뜻이 아니다.** Worker 종료와 Rollback을 별도로 확인해야 한다.

여섯째, **시스템 ImageLog와 업무 DB Transaction은 같은 원자성 경계가 아니다.** 업무가 Rollback되어도 감사 기록은 남을 수 있다.
