# 제9장. Filter와 Spring MVC — ASCII 확장본 상세 목차

> **목차 작성 기준**
>
> 이 장은 `book.zip`의 제9장 원문과 `13.Filter-DefaultFilter`, `14.Spring MVC`, 각 재분석본, `30.왜 Filter와 Interceptor을 합치면 안되는가`, `54.http호출 다이어그램`을 기준으로 확장한다.
>
> 현재 구현(AS-IS), 프로젝트 책임 원칙(STANDARD), 개선 방향(TO-BE), 설계 예시를 분리한다.
>
> 특히 다음 사실을 고정한다.
>
> - `DefaultFilter`는 DispatcherServlet 이전 Servlet 영역에서 Body 캐시·비-local JWT·`hdr_nhnis`·ServiceContext·MDC를 준비한다.
> - 현재 Filter는 `/*`, `DispatcherType.REQUEST`, `Ordered.HIGHEST_PRECEDENCE + 20` 기준으로 사실상 대부분의 HTTP 요청에 적용된다.
> - OPTIONS는 Filter를 건너뛰지만, multipart는 현재 JWT 검증보다 먼저 분기되어 비-local 인증 우회 가능성이 있는 P0 Gap으로 본다.
> - Spring MVC는 DispatcherServlet 이후 HandlerMapping·Interceptor·ArgumentResolver·Controller·ResponseBodyAdvice를 조정한다.
> - 현재 실행 모드는 `TCF ON + Legacy MVC ON`이며, TCF ON에서는 `OnlineTransactionController`, OFF에서는 업무 Controller가 조건부로 활성화된다.
> - Service ID 결정은 `ServiceContext Header → 요청 JSON Header → URL path` 순으로 해석되며 불일치 검증은 보완 대상이다.
> - 성공 응답은 `hdr_nhnis + dto`, 표준 오류는 `hdr_nhnis + result`가 현재 기준이며 Filter `sendError()` 조기 오류는 이 봉투를 보장하지 않는다.
> - Spring MVC 자체는 업무 DB Transaction을 시작하지 않는다. TCF ON+Timeout ON에서 Worker Thread의 TransactionTemplate이 최외곽 Transaction이다.
> - Filter·Interceptor·Advice·TCF를 하나로 합치지 않는다. 실행 위치와 접근 가능한 정보, 실패 방식이 서로 다르다.
