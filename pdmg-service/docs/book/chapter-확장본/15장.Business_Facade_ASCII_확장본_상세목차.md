# 제15장. Business Facade — ASCII 확장본 상세 목차

> **목차 작성 기준**
>
> 이 장은 `book.zip`의 제15장 원문, `19.Business-Facade-1.md`, `20.Tranaactional-rdwTransactionManager-Begin-1.md`, `20.타임아웃-1.md`, `01.트랜잭션처리 변경-1.md`, `65.트랜잭션 다이어그램.md`를 중심으로 확장한다.
>
> 다음 사실을 고정한다.
>
> - Facade 전용 재분석 Snapshot은 `mgcoa5530Facade`, `mgcoa8888Facade`, `mgcoa9999Facade`, `mgcoa9000Facade` **4개**를 현재 구성으로 검증한다.
> - 기본 제15장에는 `mgcoa9001Facade`, `mgcoa9100Facade` 추가 사례가 있으므로 자료 시점 차이를 명시하고 총개수를 억지로 단정하지 않는다.
> - 검증 Snapshot Facade의 핵심 책임은 `dtoBody null 처리 → ObjectMapper.convertValue → 거래별 DTOin → Transaction 선언 → 업무 Service 호출 → DTOout 반환`이다.
> - Facade는 Service ID Routing, SQL/DAO 직접호출, 응답 Envelope, ImageLog, JWT 검증을 담당하지 않는다.
> - 조회 Method는 `rdwTransactionManager + readOnly=true`, 주요 쓰기는 `rdwTransactionManager + rollbackFor=Exception.class` 패턴을 사용한다.
> - `@Transactional` 선언 위치와 실제 최외곽 BEGIN 위치는 다를 수 있다.
> - TCF ON + Timeout ON에서는 Worker `TransactionTemplate`이 먼저 TX를 시작하고 Facade `REQUIRED`는 참여한다.
> - TCF ON + Timeout OFF에서는 외부 TransactionTemplate가 없으므로 Facade Proxy가 실제 BEGIN 후보가 된다.
> - TCF OFF는 Controller의 실제 Callee에 따라 Facade TX, Service TX, 무Transaction 가능성을 거래별로 판단한다.
> - Timeout ON의 외부 일반 Transaction은 내부 Facade `readOnly=true`를 물리 TX 속성으로 다시 정의하지 못하는 P1 Gap이 있다.
> - 현재 Facade Snapshot에는 Bean Validation/필수필드 검증이 부족하고 C/U/D의 null Body가 빈 DTO로 진행될 수 있는 P1 위험이 있다.
> - Spring `@Transactional`은 Proxy를 통과해야 하며 self-invocation의 `REQUIRES_NEW/readOnly/timeout`은 적용되지 않을 수 있다.
> - Facade의 예외는 상위로 전파해 실제 Rollback과 Web 표준 오류 처리가 원인을 볼 수 있게 한다.
