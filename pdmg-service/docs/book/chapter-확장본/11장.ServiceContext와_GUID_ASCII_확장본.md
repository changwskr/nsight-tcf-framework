# 제11장. ServiceContext와 GUID

> **집필 기준**
>
> 이 장은 온라인 요청 한 건의 공통 문맥이 생성되고 사용되고 Thread 경계를 넘어가며 제거되는 전체 생명주기를 설명한다.
>
> **AS-IS 핵심 판단**
>
> - ServiceContext는 `DefaultFilter`가 생성한다.
> - ServiceContextHolder는 단순 `ThreadLocal<ServiceContext>`이며 값이 없으면 null이다.
> - ServiceContext는 Servlet Request/Response, 표준 Header, GUID, 요청·응답 원문과 전체 HTTP Header Snapshot을 보유한다.
> - GUID는 Header·Context·MDC·ImageLog·TransactionContext·외부 연계를 연결하지만 DB Transaction ID가 아니다.
> - JWT 검증 결과는 Request Attribute `ssoId`로 저장되는 경로가 확인되며 Header/userContext 자동 반영은 현재 구현 사실로 쓰지 않는다.
> - TransactionContext는 ServiceContext의 Snapshot이 아니라 기존 객체 참조를 보유한다.
> - Timeout Worker에서 MDC는 복사되지만 ServiceContext는 원본 객체를 그대로 설치한다.
> - 따라서 Timeout 뒤 Worker가 살아 있으면 Request Thread와 Worker가 동일 mutable Context와 Servlet 참조를 공유할 수 있다.
> - Request Thread와 Worker Thread는 각각 자기 ThreadLocal과 MDC를 finally에서 정리한다.
>
> **TO-BE 핵심**
>
> - Worker에는 Servlet 객체가 없는 불변 Context Snapshot 또는 필요한 값의 명시적 인자만 전달한다.
> - 인증 사용자 Context를 명시적 타입으로 만들고 Client Header와 정합성을 검증한다.
> - GUID 생성·검증·동기화 규칙을 단일화한다.
> - 민감 Header·Body·Token의 로그·직렬화·장기보관을 차단한다.


---

## 이 장을 시작하며

제10장에서는 Interceptor가 GUID와 Header를 보완하고 Pre/Post ImageLog를 남기는 흐름을 살펴보았다. 이제 더 근본적인 질문이 남는다.

```text
그 GUID와 Header는 어디에 저장되는가?
왜 Controller와 Worker Thread에서 같은 값을 읽을 수 있는가?
Thread가 바뀌면 왜 자동으로 사라지는가?
Timeout 뒤 Request Thread와 Worker가 동시에 남으면 어떤 문제가 생기는가?
JWT로 검증한 사용자는 Context 어디에 들어가는가?
거래 종료 뒤 왜 반드시 remove() 해야 하는가?
```

PDMG의 답은 `ServiceContext`, `ServiceContextHolder`, `ThreadContext(MDC)`, `TransactionContext`, `OnlineTimeoutWorkerContext`의 조합이다.

그러나 이들을 하나의 “Context”라고 뭉뚱그리면 중요한 차이를 놓친다.

```text
ServiceContext
= 요청 공통 데이터 객체

ServiceContextHolder
= 현재 Thread의 ServiceContext 보관소

MDC / ThreadContext
= 로그용 문자열 문맥

GUID
= 거래 실행 상관관계 키

TransactionContext
= TCF 실행 문맥

Spring DB Transaction
= TransactionManager가 관리하는 별도 실행 경계
```

이 장에서는 이 다섯 개를 명확히 분리한 뒤, 다시 하나의 End-to-End 실행 흐름으로 연결한다.

# 11.1 ServiceContext와 GUID를 왜 별도 장으로 배우는가

PDMG의 온라인 거래는 Filter, Interceptor, Controller, TCF, Worker Thread, 업무 계층, Response Advice와 ImageLog를 지난다. 이 전 구간에서 동일한 요청 식별정보와 공통 Header를 공유하기 위해 ServiceContext와 GUID가 필요하다.

이 구간은 Context의 **정의와 데이터 구조**를 고정한다. 무엇을 담는지보다 더 중요한 것은 무엇을 담지 말아야 하는지와 각 필드의 생명주기다.


### 그림 11-1. ServiceContext와 GUID를 왜 별도 장으로 배우는가 — 구조


```text
HTTP Request                          Request Thread
   ↓
DefaultFilter
   ├─ ServiceContext 생성
   ├─ Holder.set
   └─ MDC 설정
   ↓
Interceptor → Controller → TCF
   │
   ├─ Timeout ON → Worker Thread
   │                 ├─ Context install
   │                 └─ Handler/Service
   │
   ↓
Response Advice → afterCompletion
   ↓
Filter finally
   └─ Holder/MDC clear
```


### 그림 11-2. ServiceContext와 GUID를 왜 별도 장으로 배우는가 — 실행·검증 관점


```text
Context = 요청 공통문맥
GUID    = 추적 식별자
MDC     = 로그 문맥
TxContext = TCF 실행 문맥
DB TX   = TransactionManager 책임
```


**아키텍처 판단**


GUID는 추적의 중심키지만 인증·멱등·DB Transaction 의미를 자동으로 부여하지 않는다. 각 의미의 식별자를 분리한다.

| `active` | Profile | Filter / 환경판단 |
| `requestHeaders` | HTTP Header Snapshot | Filter |
| `httpServletRequest` | Servlet 참조 | Filter |
| `httpServletResponse` | Servlet 참조 | Filter |
| `header` | `hdr_nhnis` | Filter·Interceptor |

Service ID는 거래 종류, GUID는 그 거래의 한 번의 실행 Instance를 식별한다.

```text

          ↓
        MDC guid
          ↓
 TransactionContext
          ↓
 ImageLog / Error / External Trace
```

```text

[ ] GUID·MDC·ImageLog 정합성 Gate가 있는가
[ ] AS-IS / STANDARD / TO-BE를 분리했는가
```
