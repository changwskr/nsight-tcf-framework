# 제1장. PDMG 시스템 개요

> **집필 기준**
>
> 이 장은 지금까지 제공된 PDMG/NSIGHT/TCF 원본 문서, 소스 분석 자료, 현재 책 원고를 기준으로 재구성한 제1장이다.
> 현재 구현에서 확인되는 사실과 설계 의도, 향후 권고 구조를 섞지 않는다.
> 구현이 확인되지 않은 내용은 현재 실행 구조처럼 표현하지 않는다.

---

## 1.1 PDMG를 처음 볼 때 가장 먼저 이해해야 할 것

PDMG를 처음 접하면 화면 프로젝트, 업무 서비스, 공통 프레임워크, JWT 서버가 서로 별개의 시스템처럼 보인다. 실제 소스를 열어 보면 `Filter`, `Interceptor`, `Controller`, `Handler`, `Facade`, `Service`, `DAO`, `Mapper`가 연속해서 등장하고, 그 사이에 `Service ID`, `GUID`, `ServiceContext`, `TCF`, `Timeout`, `Transaction` 같은 용어가 다시 나타난다.

이 구조를 클래스 이름부터 외우려고 하면 PDMG는 매우 복잡해 보인다. 그러나 전체 구조를 한 문장으로 정리하면 생각보다 단순하다.

> **PDMG는 하나의 온라인 요청을 표준 형식으로 받아, 거래를 식별하고, 공통 시스템 처리를 수행한 뒤, 정해진 업무를 트랜잭션과 타임아웃 경계 안에서 실행하고, 그 결과를 다시 표준 형식으로 돌려주는 온라인 거래 실행 구조다.**

즉 PDMG를 이해하는 출발점은 “클래스가 몇 개인가?”가 아니라 다음 질문이다.

```text
사용자의 요청은 어디에서 시작되고
어떤 경계를 지나
어디에서 업무가 실행되며
어디에서 DB Transaction이 시작되고
어떤 방식으로 응답되는가?
```

이 장에서는 세부 코드를 깊게 파고들기보다 앞으로 2장부터 33장까지 계속 확대해서 보게 될 전체 지도를 먼저 만든다.

## 1.2 왜 이런 구조가 필요한가

단순한 CRUD 하나만 만든다면 다음 구조로도 충분히 동작할 수 있다.

### 그림 1-1. 가장 단순한 웹 업무 구조

```text
┌──────────────┐
│   Browser    │
└──────┬───────┘
       │ HTTP
       ▼
┌──────────────┐
│ Controller   │
└──────┬───────┘
       ▼
┌──────────────┐
│ Service      │
└──────┬───────┘
       ▼
┌──────────────┐
│ DAO / Mapper │
└──────┬───────┘
       ▼
┌──────────────┐
│      DB      │
└──────────────┘
```

프로그램이 몇 개 되지 않을 때는 이 구조도 충분하다. 그러나 프로그램이 수십 개, 수백 개로 증가하면 업무별로 서로 다른 방식이 만들어지기 시작한다.

```text
프로그램 A
  Controller에서 인증 확인
  Service에서 Transaction 시작
  자체 오류 JSON 사용

프로그램 B
  Filter에서 인증 확인
  Facade에서 Transaction 시작
  다른 로그 형식 사용

프로그램 C
  Timeout 없음
  GUID 없음
  SQL 오류를 그대로 반환

프로그램 D
  Controller → DAO 직접 호출
```

각 프로그램은 “동작”할 수 있다. 하지만 시스템 전체는 예측하기 어려워진다.

PDMG가 해결하려는 문제는 바로 이 지점이다.

### 그림 1-2. PDMG가 표준화하려는 온라인 거래

```text
                  ┌─────────────────────────────┐
                  │        온라인 요청          │
                  └──────────────┬──────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │      시스템 공통 진입 규칙          │
              │ Header / GUID / JWT / Context       │
              └──────────────────┬──────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │      거래 식별 및 실행 통제         │
              │ Service ID / TCF / Timeout          │
              └──────────────────┬──────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │          업무 실행 경계             │
              │ Handler / Facade / Service          │
              └──────────────────┬──────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │         데이터 변경 경계            │
              │ Transaction / DAO / Mapper / DB     │
              └──────────────────┬──────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │       표준 응답·운영 추적           │
              │ Response / Error / ImageLog         │
              └─────────────────────────────────────┘
```

PDMG는 결국 다음 세 가지를 함께 달성하려는 구조다.

| 관점 | 목표 |
|---|---|
| 개발 | 누구나 동일한 구조와 이름으로 프로그램을 만든다. |
| 실행 | 모든 거래가 공통 진입·통제·트랜잭션 규칙을 따른다. |
| 운영 | GUID와 Service ID를 이용해 요청부터 DB 처리까지 추적한다. |

# 1.3 PDMG 전체 시스템 컨텍스트

PDMG는 하나의 거대한 단일 모듈이 아니다. 사용자 접점, 업무 실행, 공통 프레임워크, 인증이라는 책임을 나누어 구성한다.

### 그림 1-3. PDMG 전체 시스템 컨텍스트

```text
┌───────────────────────────────────────────────────────────────┐
│                    사용자 / Browser / API Client              │
└──────────────┬───────────────────────────────┬────────────────┘
               │                               │
               │ 화면 사용                     │ 로그인/토큰
               ▼                               ▼
┌─────────────────────────┐       ┌────────────────────────────┐
│        pdmg-ui          │       │         pdmg-jwt           │
│                         │       │                            │
│ 화면                    │       │ Access Token 발급          │
│ 요청 전문 생성          │       │ Refresh Token 관리         │
│ 서비스 호출             │       │ JWKS 제공                  │
└────────────┬────────────┘       └────────────────────────────┘
             │
             │ HTTP / JSON
             ▼
┌───────────────────────────────────────────────────────────────┐
│                        pdmg-service                           │
│                                                               │
│  ┌──────────────────── pdmg-fw ────────────────────────────┐  │
│  │ Filter / Context / MVC 확장 / TCF / Timeout / Error    │  │
│  └──────────────────────────┬──────────────────────────────┘  │
│                             │                                 │
│  ┌──────────────────────────▼──────────────────────────────┐  │
│  │ Handler / Facade / BizPrePostAspect / Service / DAO   │  │
│  └──────────────────────────┬──────────────────────────────┘  │
└─────────────────────────────┼─────────────────────────────────┘
                              │ MyBatis / JDBC
                              ▼
                    ┌──────────────────────┐
                    │     RDW / DB         │
                    └──────────────────────┘
```

여기서 가장 중요한 점은 `pdmg-fw`를 별도의 원격 업무 서버처럼 이해하지 않는 것이다. 온라인 업무 실행 관점에서 `pdmg-fw`의 Filter, TCF, Context, Timeout 등의 컴포넌트는 `pdmg-service` 애플리케이션 안에서 Spring Bean 또는 Servlet/MVC 확장점으로 함께 동작한다.

반면 `pdmg-ui → pdmg-service`, `Browser → pdmg-jwt`와 같은 관계는 HTTP를 통한 프로세스 경계다.

따라서 장애를 볼 때도 경계를 구분해야 한다.

### 그림 1-4. PDMG에서 구분해야 할 세 가지 경계

```text
[프로세스 경계]
Browser ─────HTTP─────> pdmg-ui / pdmg-service / pdmg-jwt
   │
   └─ CORS / URL / Network / Authorization 문제

[모듈·JVM 경계]
pdmg-service
   └─ pdmg-fw
      │
      └─ Bean / Filter / Interceptor / AOP / Configuration 문제

[데이터 경계]
pdmg-service ─── MyBatis/JDBC ───> DB
   │
   └─ DataSource / Transaction / SQL / Lock 문제
```

같은 “호출 실패”라도 어느 경계에서 실패했는지에 따라 확인할 대상이 완전히 달라진다.

# 1.4 네 개 주요 모듈의 책임

## 1.4.1 pdmg-ui — 사용자와 온라인 거래의 접점

`pdmg-ui`는 사용자가 거래를 실행하는 화면을 제공하고, 사용자의 입력을 온라인 요청 전문으로 만들어 서버에 보낸다.

### 그림 1-5. UI의 역할

```text
사용자 입력
   │
   ▼
┌───────────────────┐
│     pdmg-ui       │
│                   │
│ 화면              │
│ 거래 선택         │
│ Service ID 선택   │
│ 요청 전문 작성    │
└─────────┬─────────┘
          │
          │ POST /{serviceId}
          │ { hdr_nhnis, dto }
          ▼
      pdmg-service
```

현재 자료에서는 일반 화면의 브라우저 직접 호출과 Relay 호환 경로가 함께 존재한다. 따라서 Relay를 PDMG의 유일한 호출방식처럼 설명해서는 안 된다.

```text
[현행 일반 화면]
Browser
   └───────────────> pdmg-service
          직접 HTTP 호출
          CORS 필요

[호환 Relay]
Browser
   └──> pdmg-ui
          └──> pdmg-service
```

직접 호출 방식은 구조가 단순하지만 CORS와 JWT Authorization 전달 문제를 함께 해결해야 한다.

---

## 1.4.2 pdmg-service — 업무 거래의 실행 주체

`pdmg-service`는 마케팅 업무 로직을 실제로 수행하는 핵심 업무 모듈이다.

### 그림 1-6. pdmg-service 업무 계층

```text
┌─────────────────────────────┐
│          Handler            │
│ Service ID 분기             │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│          Facade             │
│ Use Case 경계               │
│ DTO 변환                    │
│ Transaction 선언            │
└──────────────┬──────────────┘
               ▼
       ┌───────────────┐
       │ BizPrePost    │
       │ Aspect        │
       └───────┬───────┘
               ▼
┌─────────────────────────────┐
│          Service            │
│ 업무 절차·업무 판단        │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│       DAO / Mapper          │
│ 데이터 접근                │
└──────────────┬──────────────┘
               ▼
              DB
```

중요한 정정 사항이 하나 있다.

`BizPrePostAspect`는 시스템 공통 Filter처럼 `pdmg-fw` 책임으로 보아서는 안 된다. 현재 업무 선후처리는 `pdmg-service` 업무 패키지에 위치하며 Service 실행 지점을 대상으로 한다.

또한 현재 소스 기준으로 `Rule` 계층은 일반화된 실행 경로에 실제 구현되어 있다고 단정하지 않는다. Rule은 설계 확장 방향으로 설명할 수 있지만, AS-IS에서는 Service가 많은 업무 책임을 직접 수행하는 구조가 존재한다.

---

## 1.4.3 pdmg-fw — 온라인 거래의 공통 실행 기반

`pdmg-fw`는 개별 마케팅 업무를 구현하는 모듈이 아니라, 모든 온라인 거래가 일정한 방식으로 실행되도록 공통 실행 환경을 제공한다.

### 그림 1-7. pdmg-fw의 핵심 책임

```text
┌──────────────────────────────────────────┐
│                pdmg-fw                   │
├──────────────────────────────────────────┤
│ HTTP 진입                                │
│   └─ DefaultFilter                       │
│                                          │
│ MVC 공통                                 │
│   └─ ServicePreventionInterceptor        │
│   └─ ResponseBodyAdvice                  │
│                                          │
│ 요청 컨텍스트                            │
│   └─ ServiceContext                      │
│                                          │
│ TCF                                      │
│   └─ OnlineTransactionController         │
│   └─ TcfFacade                           │
│   └─ TransactionDispatcher               │
│                                          │
│ 실행 제어                                │
│   └─ OnlineTimeoutExecutor               │
│                                          │
│ 공통 오류/로그/ImageLog 지원             │
└──────────────────────────────────────────┘
```

`pdmg-fw`의 역할은 업무 로직을 대신하는 것이 아니다.

```text
pdmg-fw가 알아야 하는 것
  Service ID
  요청 Context
  Timeout
  Handler Registry
  Error/Response
  Logging

pdmg-fw가 몰라야 하는 것
  특정 고객의 업무 규칙
  특정 마케팅 계산식
  특정 프로그램 SQL 조건
  특정 화면의 업무 판단
```

이 경계를 지키는 것이 공통 프레임워크를 업무 코드로부터 독립시키는 핵심이다.

## 1.4.4 pdmg-jwt — 인증과 토큰의 생명주기

`pdmg-jwt`는 Access Token과 Refresh Token을 발급하고 공개키 정보를 제공하는 인증 영역이다.

### 그림 1-8. JWT 발급·사용의 개념 구조

```text
사용자
  │
  │ 로그인
  ▼
┌──────────────────────┐
│      pdmg-jwt        │
│                      │
│ 인증                 │
│ Access Token 발급    │
│ Refresh Token 관리   │
│ JWKS 공개            │
└──────────┬───────────┘
           │
           │ Access Token
           ▼
        Browser
           │
           │ Authorization: Bearer ...
           ▼
┌──────────────────────┐
│    pdmg-service      │
│  DefaultFilter       │
│  Token 검증          │
└──────────────────────┘
```

여기서 반드시 구분해야 할 AS-IS Gap이 있다.

```text
pdmg-jwt
   └─ RS256 기반 발급 구조

pdmg-fw의 현행 JwtProvider
   └─ HMAC 기반 검증 구조

결론
   └─ 발급과 검증이 하나의 완성된 인증 체계로
      자동 연결된 상태라고 단정할 수 없음
```

따라서 이 장에서는 JWT가 “있다”는 사실과 “업무 서비스까지 완전히 연결되었다”는 사실을 구분한다. 상세 내용은 JWT 장에서 다룬다.

# 1.5 한 건의 온라인 요청은 어떻게 이동하는가

이제 가장 중요한 전체 호출 경로를 본다.

### 그림 1-9. 온라인 거래 기본 실행 흐름

```text
Browser
   │
   │ POST /{serviceId}
   ▼
DefaultFilter
   │
   ▼
ServicePreventionInterceptor
   │
   ▼
OnlineTransactionController
   │
   ▼
TcfFacade
   │
   ▼
OnlineTimeoutExecutor
   │
   ▼
TransactionDispatcher
   │
   ▼
Business Handler
   │
   ▼
Business Facade
   │
   ▼
BizPrePostAspect
   │
   ▼
Business Service
   │
   ▼
DAO / Mapper
   │
   ▼
DB
   │
   ▼
ResponseBodyAdvice
   │
   ▼
Interceptor.afterCompletion
   │
   ▼
HTTP Response
```

이 그림을 외우는 것이 목표는 아니다. 중요한 것은 각 구간의 책임이 다르다는 사실이다.

```text
HTTP 준비
  Filter

MVC 시스템 선처리
  Interceptor

거래 공통 진입
  OnlineTransactionController

거래 실행
  TcfFacade / TimeoutExecutor / Dispatcher

업무
  Handler / Facade / Service / DAO

응답·운영 후처리
  Advice / Interceptor
```

2장에서는 이 흐름을 Request Thread와 Worker Thread, Transaction, 정상/오류 흐름까지 포함하여 더 확대한다.

# 1.6 Service ID는 거래의 이름표이자 라우팅 키다

PDMG 온라인 거래는 Service ID를 중심으로 실행된다.

예를 들어 다음과 같은 값이다.

```text
mgcoa8888S0
mgcoa8888D0
mgcoa9000S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
```

### 그림 1-10. Service ID가 시스템 전체를 연결하는 방식

```text
               mgcoa9000C0
                    │
      ┌─────────────┼─────────────┐
      │             │             │
      ▼             ▼             ▼
 HTTP Path       전문 Header    UI Catalog
 /mgcoa9000C0    rms_svc_c       transaction id
      │             │             │
      └─────────────┴──────┬──────┘
                           ▼
                OnlineTransactionController
                           │
                           ▼
                 TransactionDispatcher
                           │
                           ▼
                   mgcoa9000Handler
                           │
                           ▼
                 facade.mgcoa9000C0()
                           │
                           ▼
                 service.mgcoa9000C0()
                           │
                           ▼
                   DAO / SQL ID
```

Service ID는 단순히 URL 문자열이 아니다.

```text
Service ID
   = 온라인 거래 식별자
   = Dispatcher 라우팅 키
   = Handler 분기 키
   = 개발 산출물 추적 키
   = 운영 로그의 거래 식별 정보
```

현재 Controller에서는 Service ID를 하나의 위치에서만 읽지 않는다. Context와 전문 헤더, URL이 관여한다. 따라서 다음과 같은 불일치는 위험하다.

### 그림 1-11. URL과 전문 Service ID 불일치 위험

```text
HTTP Path
/mgcoa8888S0
     │
     │ 조회 거래라고 생각
     ▼

전문 Header
rms_svc_c = mgcoa8888D0
     │
     │ 현재 우선순위에 따라
     ▼

실제 Dispatcher
mgcoa8888D0
     │
     ▼
삭제 Handler 분기 가능
```

업무 표준은 다음 세 값이 같아야 한다.

```text
URL Service ID
      =
hdr_nhnis.sys_comm.rms_svc_c
      =
Handler Registry Key
```

향후에는 세 값이 동시에 존재할 경우 불일치를 명시적으로 거부하는 검증이 필요하다. 이는 TO-BE 권고다.

# 1.7 GUID는 “어떤 거래인가”가 아니라 “이번 호출인가”를 나타낸다

Service ID와 GUID는 자주 함께 등장하지만 목적이 다르다.

```text
Service ID
  어떤 업무를 실행하는가?

GUID
  이번 한 번의 호출은 무엇인가?
```

### 그림 1-12. Service ID와 GUID의 관계

```text
Service ID: mgcoa9000S0
             │
             ├── 호출 #1  GUID = A001...
             ├── 호출 #2  GUID = A002...
             ├── 호출 #3  GUID = A003...
             └── 호출 #4  GUID = A004...
```

같은 Service ID는 하루에도 수천 번 실행될 수 있다. 운영자가 특정 장애 요청 한 건을 찾으려면 GUID가 필요하다.

### 그림 1-13. GUID 중심 운영 추적

```text
                    GUID
                     │
        ┌────────────┼─────────────┐
        │            │             │
        ▼            ▼             ▼
   Request Log    ImageLog      App Log
        │            │             │
        └────────────┼─────────────┘
                     ▼
                 Service ID
                     │
                     ▼
                 Handler
                     │
                     ▼
                 SQL / DB
```

운영 추적에서 Service ID와 GUID는 다음처럼 함께 사용된다.

```text
Service ID
  → 어떤 종류의 거래가 문제인가?

GUID
  → 그 거래 중 정확히 어느 한 건이 문제인가?
```

# 1.8 ServiceContext는 요청 한 건의 공통 가방이다

HTTP 요청을 처리하면서 여러 계층에서 공통 헤더, GUID, 사용자, 요청 원문 등을 필요로 한다. 이 정보를 모든 메서드 인자로 계속 전달하면 업무 메서드가 시스템 공통 데이터에 오염된다.

PDMG는 이를 `ServiceContext`로 관리한다.

### 그림 1-14. ServiceContext의 생명주기

```text
HTTP Request
    │
    ▼
DefaultFilter
    │
    ├─ Header
    ├─ GUID
    ├─ Request Body
    ├─ Profile
    └─ HTTP 정보
    │
    ▼
ServiceContext 생성
    │
    ▼
ServiceContextHolder(ThreadLocal)
    │
    ├─ Interceptor
    ├─ Controller
    ├─ TCF
    ├─ BizPrePost
    └─ Response Advice
    │
    ▼
HTTP Request 종료
    │
    ▼
removeInstance()
```

여기서 가장 중요한 단어는 `ThreadLocal`이다.

```text
ServiceContextHolder
     │
     └─ 현재 Thread에 종속
```

즉 새로운 Worker Thread로 실행을 넘기면 Request Thread의 ThreadLocal 값이 자동으로 따라가지 않는다.

이 문제는 11장과 Timeout 장에서 상세히 다룬다.

# 1.9 시스템 처리와 업무 처리를 구분한다

PDMG를 이해할 때 가장 많이 혼동하는 부분 중 하나가 “시스템 선후처리”와 “업무 선후처리”다.

둘은 이름은 비슷하지만 위치와 목적이 다르다.

### 그림 1-15. 시스템 공통 처리와 업무 처리의 경계

```text
┌─────────────────────────────────────────────┐
│              시스템 공통 영역               │
│                                             │
│ DefaultFilter                               │
│ ServicePreventionInterceptor                │
│ OnlineTransactionController                 │
│ TcfFacade                                   │
│ OnlineTimeoutExecutor                       │
│ TransactionDispatcher                       │
│ ResponseBodyAdvice                          │
│ ImageLog                                    │
└─────────────────────┬───────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────┐
│                업무 영역                    │
│                                             │
│ Handler                                     │
│ Facade                                      │
│ BizPrePostAspect                            │
│ Service                                     │
│ DAO / Mapper                                │
└─────────────────────────────────────────────┘
```

이 그림은 **논리적 책임 경계**를 나타낸다.

실제 Transaction 범위와 동일한 그림이 아니다. 예를 들어 TCF ON + Timeout ON에서는 Dispatcher와 Handler가 Worker Transaction 내부에서 실행될 수 있다. 그러나 Dispatcher는 여전히 프레임워크의 라우팅 책임이고 Handler부터 업무 프로그램 책임이 시작된다고 볼 수 있다.

## 1.9.2 업무 선후처리

```text
Handler
   │
   ▼
```

# 1.10 TCF는 무엇을 하는가

TCF는 Service ID 중심의 공통 거래 실행 구조다.

### 그림 1-18. TCF의 핵심 역할

```text
             OnlineTransactionController
                        │
                        ▼
                  TcfFacade
                        │
                        ▼
               TimeoutExecutor
                        │
                        ▼
             TransactionDispatcher
                        │
       ┌────────────────┼────────────────┐
       │                │                │
       ▼                ▼                ▼
 mgcoa5530Handler  mgcoa8888Handler  mgcoa9000Handler
       │                │                │

                        ▼
                      Facade
```

Dispatcher는 등록된 Handler와 Service ID 관계를 기반으로 실행 대상을 찾는다.

```text

   ↓
Handler Registry
   ↓
TransactionHandler
   ↓

```

현재 TCF의 실제 주 호출선을 설명할 때 STF/ETF를 실행 중인 컴포넌트처럼 임의로 끼워 넣으면 안 된다. 관련 클래스나 설계 개념이 존재하더라도 현재 `TcfFacade`의 주 실행 경로에 연결된 사실과는 구분해야 한다.

# 1.11 Request Thread와 Worker Thread

PDMG Transaction을 이해하기 전에 반드시 Thread를 먼저 이해해야 한다.

TCF ON + Timeout ON에서는 HTTP 요청을 받은 Request Thread가 그대로 DB 업무를 끝까지 수행하는 구조가 아니다.

### 그림 1-19. Request Thread와 Worker Thread

```text
Request Thread
──────────────────────────────────────────────
DefaultFilter
    ↓
Interceptor
    ↓
OnlineTransactionController
    ↓
TcfFacade
    ↓
OnlineTimeoutExecutor.submit()
    │
    ├─────────────────────────────────────┐
    │                                     │
    │ Future.get(timeout)                 │
    │                                     │
    │                            Worker Thread
    │                     ─────────────────────────
    │                            Context 설치
    │                                ↓
    │                      TransactionTemplate
    │                                ↓
    │                          Dispatcher
    │                                ↓
    │                            Handler
    │                                ↓
    │                            Facade
    │                                ↓
    │                            Service
    │                                ↓
    │                          DAO / Mapper
    │                                ↓
    │                          COMMIT/ROLLBACK
    │                                     │
    └──────────────── Result ──────────────┘
```

이 구조가 중요한 이유는 세 가지다.

1. `ThreadLocal` Context는 자동으로 Worker에 전달되지 않는다.
2. Spring Transaction은 Thread-bound이므로 Transaction을 시작한 Thread가 중요하다.
3. Request Timeout 응답 시점과 Worker의 실제 종료 시점이 같지 않을 수 있다.

# 1.12 Transaction은 항상 Facade에서 시작하지 않는다

PDMG에서 가장 중요한 사실 중 하나다.

“Facade에 `@Transactional`이 있으므로 항상 Facade가 Transaction을 시작한다”라고 이해하면 TCF ON + Timeout ON 구조를 잘못 이해하게 된다.

### 그림 1-20. TCF ON + Timeout ON의 실제 Transaction 경계

```text
Request Thread
────────────────────────────────────────────
Filter
Interceptor
Controller
TcfFacade
Executor.submit()
Future.get()

        업무 DB Transaction 밖
──────────────────────┬─────────────────────
                      │ Thread 전환
                      ▼

Worker Thread

╔══════════════════════════════════════════╗
║ TransactionTemplate BEGIN               ║
║                                          ║
║ TransactionDispatcher                    ║
║        ↓                                 ║
║ Handler                                  ║
║        ↓                                 ║
║ Facade @Transactional(REQUIRED)          ║
║        ↓                                 ║
║ BizPrePostAspect                         ║
║        ↓                                 ║
║ Service                                  ║
║        ↓                                 ║
║ DAO / Mapper / SQL                       ║
║                                          ║
║ COMMIT 또는 ROLLBACK                     ║
╚══════════════════════════════════════════╝
```

여기서 Facade의 `@Transactional(REQUIRED)`는 새 Transaction을 여는 것이 아니라 이미 Worker Thread에서 시작된 Transaction에 참여한다.

즉 다음과 같다.

```text
Timeout ON

TransactionTemplate
     │
     └─ 물리 TX 시작
          │
          ▼
Facade REQUIRED
     │
     └─ 기존 TX 참여
```

# 1.14 Timeout은 단순한 HTTP 응답시간 제한이 아니다

Timeout ON 구조에서는 Request Thread와 Worker Thread가 분리되어 있기 때문에 “5초가 지나면 모든 것이 정확히 5초 시점에 종료된다”고 생각하면 안 된다.

### 그림 1-22. Timeout 시 시간 흐름

```text
시간 ───────────────────────────────────────────────────────>

0ms
│ HTTP 요청
▼

20ms
│ Worker submit
│ Transaction BEGIN
▼

100ms
│ SQL 실행
▼

5000ms
│ Request Thread Future.get() TIMEOUT
│
├───────────────> Client : HTTP 504
│
└─ cancel(true)

5300ms
│ Worker의 SQL이 뒤늦게 반환될 수도 있음
▼

5310ms
│ deadline 재확인
▼

5320ms
│ COMMIT 차단
│ ROLLBACK
▼
```

핵심은 다음이다.

```text
HTTP 504 반환
   ≠
Worker 즉시 종료
   ≠
DB 작업 즉시 취소
```

따라서 Timeout 설계는 HTTP 응답, Thread cancel, JDBC cancel, Transaction rollback을 서로 다른 문제로 본다.

```text

────────────────────────────────────

 ↓

 ↓

 ↓

 ↓
```

# 1.18 STF/ETF는 “존재”와 “실행 연결”을 구분한다

PDMG/TCF 자료에는 STF와 ETF 개념이 등장한다.

개념적으로는 다음처럼 이해할 수 있다.

### 그림 1-28. STF/TCF/ETF 개념 모델

```text
┌──────────────────────┐
│ STF                  │
│ System Front         │
│ 시스템 선처리 개념   │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ TCF                  │
│ 거래 실행            │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ ETF                  │
│ System End           │
│ 시스템 후처리 개념   │
└──────────────────────┘
```

그러나 현재 실행 경로를 설명할 때는 다음처럼 구분해야 한다.

```text
[현재 실제 주 흐름]

Filter
  ↓
Interceptor
  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
TimeoutExecutor
  ↓
Dispatcher
  ↓
Handler
  ↓
Facade / Service / DAO
  ↓
ResponseBodyAdvice
  ↓
Interceptor.afterCompletion
```

STF/ETF 클래스 또는 설계 구조가 있다는 사실만으로 위 호출선에 자동으로 연결되었다고 표현하지 않는다.

# 1.20 아키텍처를 이해할 때 자주 하는 오해

## 오해 1. “TCF ON이면 Transaction은 Facade에서 시작한다.”

아니다.

```text
TCF ON + Timeout ON
  Worker TransactionTemplate BEGIN
  → Facade REQUIRED 참여

TCF ON + Timeout OFF
  Facade가 Transaction 시작 가능
```

---

## 오해 2. “Filter와 Interceptor는 비슷하니 하나로 합치면 된다.”

둘은 실행 위치와 책임이 다르다.

```text
Servlet Filter
    │
    │ DispatcherServlet 밖
    ▼
Spring MVC
    │
    ▼
HandlerInterceptor
```

Filter는 Body 캐시, JWT, Context 준비에 적합하고 Interceptor는 MVC Handler 실행 전후의 시스템 처리에 적합하다.

---

## 오해 3. “ServiceContext는 전역 객체이므로 어느 Thread에서나 읽을 수 있다.”

아니다.

```text
Request Thread
 ServiceContextHolder = O

Worker Thread
 ServiceContextHolder = 자동으로 O가 아님
```

Worker로 이동할 때 명시적인 Context 전달이 필요하다.

---

## 오해 4. “JWT 서버가 있으므로 인증은 완성됐다.”

아니다.

```text
토큰 발급
   ≠
UI 전달
   ≠
서비스 검증
   ≠
업무 사용자 Context 확정
```

발급·전달·검증·업무 Principal 연결이 모두 맞아야 한다.

---

## 오해 5. “STF/ETF 클래스가 존재하면 거래가 그 클래스를 반드시 통과한다.”

아니다.

```text
Class 존재
   ≠
Spring Bean 존재
   ≠
Runtime 호출 연결
```

실행 경로는 실제 호출 소스를 확인해야 한다.

# 1.22 제1장의 아키텍처 판단

제1장에서 가장 중요한 판단은 특정 클래스를 외우는 것이 아니다.

첫째, **PDMG는 업무 코드와 공통 실행 코드를 분리한다.** `pdmg-service`는 업무를, `pdmg-fw`는 공통 온라인 실행 메커니즘을 담당한다. `BizPrePostAspect`처럼 업무 실행 지점의 횡단 관심사는 현재 업무 패키지 책임으로 보아야 한다.

둘째, **Service ID와 GUID의 역할을 구분해야 한다.** Service ID는 어떤 거래인지 결정하고, GUID는 그 거래의 수많은 실행 중 이번 한 건을 추적한다.

셋째, **Thread 경계와 Transaction 경계를 같은 것으로 보면 안 된다.** TCF ON + Timeout ON에서는 Request Thread에서 Worker Thread로 실행이 이동하고, Worker가 `TransactionTemplate`으로 최외곽 DB Transaction을 시작한다.

넷째, **TCF ON/OFF는 단순히 Controller 하나를 바꾸는 설정이 아니다.** Handler/Dispatcher/Timeout과 Transaction 시작점까지 영향을 줄 수 있다. OFF 경로가 Facade를 우회하면 Transaction 의미도 달라질 수 있다.

다섯째, **현재 구현과 목표 아키텍처를 섞어 설명하면 안 된다.** STF/ETF, Rule, JWT 통합처럼 설계 방향은 존재하지만 실제 실행 연결 여부는 별도로 확인해야 한다.
