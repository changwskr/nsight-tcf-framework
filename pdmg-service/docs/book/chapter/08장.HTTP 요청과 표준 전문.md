# 제3부 온라인 요청과 TCF 프레임워크

# 8장. HTTP 요청과 표준 전문

사용자가 PDMG 화면에서 거래 파라미터 조회 버튼을 클릭했다고 가정하자. 사용자에게 보이는 것은 버튼 하나지만 서버가 업무를 실행하려면 어느 서버로 보낼지, 어떤 거래를 실행할지, 요청 한 건을 어떻게 추적할지, 누가 어떤 채널에서 요청했는지, 실제 조회 조건은 무엇인지가 하나의 HTTP 요청 안에 구분되어 전달되어야 한다.

PDMG는 이 문제를 HTTP 전송 계약과 표준 JSON 전문으로 해결한다. HTTP Method와 URL은 요청을 서버의 진입점으로 운반하고, HTTP Header는 Content-Type과 Authorization 같은 전송·인증 정보를 전달한다. JSON Body의 `hdr_nhnis.sys_comm`은 거래의 공통 문맥을, `dto`는 Service ID마다 다른 업무 입력을 전달한다. 이 구분을 이해해야 화면, Relay, Filter, Controller와 업무 Service가 동일 메시지를 서로 다른 책임으로 처리하는 이유가 보인다.

```text
HTTP Request
   = Transport                 URL, Method, Status
   + Authentication           Authorization Header
   + Transaction Identity     Service ID
   + Trace                    GUID
   + Common Context           hdr_nhnis.sys_comm
   + Business Contract        dto
```

여기서 Transaction Identity는 “어떤 온라인 거래인가”를 뜻한다. 데이터베이스의 BEGIN/COMMIT/ROLLBACK을 HTTP 메시지가 직접 제어한다는 뜻이 아니다. DB 트랜잭션 경계는 뒤의 TCF와 Facade 실행 구조가 결정한다.

## 이 장에서 해결하려는 문제

화면에서 전송한 JSON이 업무 Service에 도착하기까지는 여러 변환 경계를 지난다. 브라우저는 HTTP Header와 JSON Body를 만들고, `DefaultFilter`는 Body를 캐싱하면서 공통 Header를 `ServiceContext`로 옮긴다. Spring MVC는 Controller를 선택하며, TCF ON에서는 공통 Controller가 `dto`를 범용 객체로 분리한다. 업무 Facade는 그 객체를 거래별 `DTOin`으로 바꾸고, 반환된 `DTOout`은 다시 표준 응답 봉투로 조립된다.

이 과정을 모르면 다음과 같은 장애를 만들기 쉽다.

- URL은 `mgcoa9000S0`인데 전문에는 다른 Service ID를 넣어 예상하지 않은 거래가 실행된다.
- 업무 DTO에 공통 Header 필드를 중복 선언해 사용자·GUID 값의 출처가 둘로 나뉜다.
- Filter가 먼저 읽은 Body를 MVC가 다시 읽지 못해 Controller 입력이 비어 버린다.
- TCF ON과 OFF에서 서로 다른 `@RequestBody`를 사용해 입력 변환이 달라진다.
- 정상 응답과 오류 응답을 같은 구조라고 가정해 UI가 오류 내용을 읽지 못한다.
- 브라우저의 CORS 오류를 서버 업무 오류나 timeout으로 오인한다.

이 장은 PDMG의 전문을 단순 JSON 형식이 아니라 **HTTP 경계에서 시스템 정보와 업무 정보를 분리하고 다시 결합하는 실행 계약**으로 설명한다.

## 이 장의 전체 흐름

```text
pdmg-ui / Client
  │ HTTP Header + { hdr_nhnis, dto }
  ▼
DefaultFilter
  │ Body Cache, Header 파싱, ServiceContext
  ▼
ServicePreventionInterceptor
  │ GUID·Header 보완, 요청 이미지로그
  ▼
Spring MVC
  ├─ TCF ON  : OnlineTransactionController → dto Object → TcfFacade
  └─ TCF OFF : mgcoa*Controller → RequestBodyArgumentResolver → DTOin
  ▼
Handler / Facade / Service / DAO
  │ DTOout 또는 예외
  ▼
ResponseBodyArgumentResolver
  ├─ 성공: { hdr_nhnis, dto }
  └─ 실패: { hdr_nhnis, result }
```

## 8.1 HTTP 호출 구조

### HTTP는 업무 호출의 외부 경계다

PDMG 온라인 거래는 JSON을 담은 HTTP POST 요청이다. 조회 거래도 Service ID의 거래구분이 `S`일 뿐 HTTP GET을 사용한다는 뜻은 아니다. 공통 전문과 업무 입력을 Body에 함께 전달하기 때문에 조회·등록·수정·삭제 모두 POST 형태를 사용한다.

현재 TCF ON 공통 Controller는 세 가지 Mapping을 제공한다.

| 요청 URL | Service ID의 주 출처 | 용도 |
|---|---|---|
| `POST /online` | `rms_svc_c` | 공통 온라인 URL |
| `POST /{businessCode}/online` | `rms_svc_c` | 업무코드 포함 호환 URL |
| `POST /{serviceId}` | Header·JSON·path | PDMG 직접 URL 스타일 |

세 URL은 서로 다른 업무 구현으로 가지 않는다. `OnlineTransactionController.handle(...)`로 모인 후 `TcfFacade.process(serviceId, dtoBody)`를 호출한다.

### 요청을 구성하는 두 종류의 Header

```text
HTTP Header
├─ Content-Type: application/json
├─ Authorization: Bearer <token>
└─ Origin: http://localhost:8090

JSON Body
├─ hdr_nhnis       시스템 공통 전문 Header
└─ dto             업무 입력
```

HTTP Header는 전송·인증·브라우저 정책에 사용된다. `hdr_nhnis`는 거래 추적과 시스템 공통 정보를 전달한다. 둘은 이름만 Header일 뿐 서로 다른 계층의 계약이다.

### 실제 호출 예

```http
POST /mgcoa9000S0 HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Authorization: Bearer <access-token>
Origin: http://localhost:8090
```

Token 원문은 설명을 위해서도 문서·로그에 실제 값으로 남기지 않는다.

### 실패를 진단하는 순서

HTTP 호출 자체가 실패하면 업무 소스부터 보지 않는다. DNS·포트·context path, CORS preflight, 인증, JSON 파싱, Controller Mapping 순으로 경계를 좁힌다. Controller 시작 로그가 없다면 Service나 DAO는 아직 실행되지 않은 것이다.

## 8.2 표준 요청 전문

PDMG 요청 전문은 공통 Header와 업무 Body를 하나의 JSON 봉투에 담는다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000S0",
      "std_gbl_id": "추적용-GUID",
      "tr_sysid": "PDMG",
      "std_tgrm_rqr_rsp_dsc": "Q",
      "std_tgrm_lclc": "KO",
      "tr_trm_ipadr": "127.0.0.1",
      "scid": "mgcoa9000"
    }
  },
  "dto": {
    "pageNo": 1,
    "pageSize": 20
  }
}
```

### 왜 봉투를 분리하는가

GUID, Service ID, 사용자와 채널 같은 값은 모든 거래에서 공통으로 필요하다. 반면 조회 조건과 등록 데이터는 거래마다 다르다. 이를 하나의 DTO에 섞으면 모든 업무 DTO가 Framework 필드를 중복 선언해야 하고, Header 스키마 변경이 모든 업무 계약 변경으로 번진다.

| 영역 | 변경 책임 | 대표 소비자 |
|---|---|---|
| `hdr_nhnis` | Framework·시스템 계약 | Filter, Interceptor, Context, 로그 |
| `dto` | 업무 거래 계약 | Facade, Service, DAO |

### local 편의와 표준 계약

local Profile에서는 `DefaultFilter`가 `{"dto": {...}}`만 받은 경우 합성 Header를 만들 수 있다. 이것은 개발 편의다. 통합·운영 호출의 표준은 완전한 `hdr_nhnis.sys_comm`을 보내는 것이다. local 성공만으로 운영 전문이 올바르다고 판단하면 안 된다.

### 잘못된 전문

```json
{
  "serviceId": "mgcoa9000S0",
  "body": { "pageNo": 1 }
}
```

이 구조는 `hdr_nhnis`와 `dto` 계약을 지키지 않는다. TCF Controller가 `request.get("dto")`를 수행하므로 업무 Body가 null이 되며, Service ID도 정해진 탐색 위치에서 발견되지 않는다.

## 8.3 `hdr_nhnis` 구조

`hdr_nhnis`는 `nhnis.fw.commons.dto.header.hdr_nhnis`로 표현되는 공통 Header 루트다. 현재 핵심 하위 객체는 `sys_comm`이다.

```text
hdr_nhnis
└─ sys_comm
   ├─ 거래 식별
   ├─ 추적 식별
   ├─ 요청/응답 구분
   ├─ 단말·IP
   ├─ 화면·채널
   └─ 조작자·영업점 정보
```

`DefaultFilter`는 JSON의 `hdr_nhnis` Map을 `ObjectMapper.convertValue(..., hdr_nhnis.class)`로 바꿔 `ServiceContext`에 저장한다. 이후 계층은 원시 JSON을 반복 파싱하기보다 Context의 typed Header를 사용한다.

### Header의 생명주기

```text
Client JSON
  → DefaultFilter 파싱 또는 local 합성
  → ServiceContext.header
  → Interceptor 누락값 보완
  → OnlineTransactionController Service ID/IP 보완
  → ResponseBodyAdvice가 응답 hdr_nhnis로 직렬화
```

Header는 단순 echo가 아니다. 서버가 GUID, IP와 Service ID를 보완할 수 있다. 따라서 응답 Header는 요청 원문과 완전히 동일한 문자열이라고 가정하지 않는다.

### 보안 판단

Header에 사용자 식별값이 있다는 사실만으로 인증되었다고 판단해서는 안 된다. 권한 판단은 검증된 JWT Claim이나 신뢰 가능한 시스템 경계에서 전달된 값을 기준으로 해야 한다. 클라이언트가 임의로 입력 가능한 값은 업무 권한의 단독 근거가 될 수 없다.

## 8.4 `sys_comm` 공통 Header

`sys_comm`은 온라인 거래의 시스템 문맥을 담는다. 실제 전체 필드는 `sys_comm.java`가 기준이며 문서의 샘플 목록을 전체 스키마로 오해하지 않는다.

| 필드 | 역할 | 주요 사용처 |
|---|---|---|
| `rms_svc_c` | Service ID | Controller, Dispatcher, 거래 통제 |
| `std_gbl_id` | GUID | MDC, ImageLog, 장애 추적 |
| `tr_sysid` | 거래 시스템 | 시스템 구분 |
| `std_tgrm_rqr_rsp_dsc` | 요청/응답 구분 | 전문 처리 |
| `tr_trm_ipadr` | 단말 IP | 로그·거래 통제 |
| `tr_brc` | 취급점 | 거래 통제·감사 |
| `scid` | 화면·프로그램 | 화면 추적 |
| `optr_eno` | 조작자 식별 | 감사·사용자 통제 |

### IP 보완

`OnlineTransactionController.enrichClientIp()`는 Header의 IP가 비었을 때 `X-Forwarded-For` 첫 값 또는 `request.getRemoteAddr()`를 사용한다. Proxy Header는 신뢰 경계를 설정하지 않으면 위조될 수 있으므로 운영 환경에서 승인된 Proxy가 덮어쓰는 구조와 함께 사용해야 한다.

### 값 불일치 문제

Service ID, 사용자, IP가 HTTP 경로·JWT·전문에 중복될 수 있다. 중복값이 다를 때 어느 값을 신뢰할지 명시해야 한다. 현재 Service ID는 Context Header가 가장 높은 우선순위를 가진다. 사용자와 IP도 동일한 규칙이라고 추정하지 말고 각 구현을 확인한다.

## 8.5 업무 DTO Body

`dto`는 한 Service ID의 업무 입력이다. 예를 들어 `mgcoa9000S0`의 페이지 번호와 검색 조건은 `mgcoa9000S0DTOin`으로 변환된다.

```text
JSON dto
  → TCF ON: Map/Object → Facade ObjectMapper.convertValue → DTOin
  → TCF OFF: RequestBodyArgumentResolver.treeToValue → DTOin
```

### 필드 규칙

- JSON 필드는 Java DTO와 같은 camelCase를 사용한다.
- 공통 Header 필드를 업무 DTO에 중복하지 않는다.
- 입력 DTO와 출력 DTO를 분리한다.
- 목록 행은 `DTOSub0` 같은 반복 DTO로 표현한다.
- 필수값·길이·범위는 업무 계약으로 검증한다.

### AS-IS Resolver의 특징

TCF OFF Controller는 Spring 표준 `org.springframework.web.bind.annotation.RequestBody`가 아니라 `nhnis.fw.commons.resolver.RequestBody`를 import한다. `RequestBodyArgumentResolver`는 전체 JSON에서 `dto` 노드만 꺼내 Controller 파라미터 타입으로 변환한다. `dto`가 없으면 빈 ObjectNode를 사용하며, 알 수 없는 필드는 무시하도록 ObjectMapper를 설정한다.

알 수 없는 필드를 무시하면 구버전 호환에는 유리하지만 클라이언트 오타가 조용히 사라질 수 있다. 필수값 검증으로 이를 보완해야 한다.

## 8.6 GUID와 Service ID

GUID와 Service ID는 자주 함께 로그에 나타나지만 역할이 다르다.

| 구분 | GUID | Service ID |
|---|---|---|
| 질문 | 어떤 요청 한 건인가? | 어떤 거래를 실행하는가? |
| 동일 값의 반복 | 재시도마다 새 값 권장 | 같은 거래면 동일 |
| 사용 | 추적·ImageLog·MDC | Handler 선택·정책 |

```text
mgcoa9000S0 호출 1회 → GUID G1
같은 화면 재조회       → GUID G2
Service ID는 두 요청 모두 mgcoa9000S0
```

GUID는 요청 경계를 추적하고 Service ID는 실행 코드를 선택한다. GUID로 Handler를 선택하거나 Service ID만으로 개별 요청을 추적하지 않는다.

### 일관성 조건

```text
sys_comm.std_gbl_id = ServiceContext GUID = MDC GUID = ImageLog GUID
sys_comm.rms_svc_c  = 선택된 Service ID = Handler Registry 키
```

외부 시스템 호출에서는 GUID를 합의된 Header로 전파한다. 새로운 GUID를 만들 필요가 있다면 원 GUID와의 상관관계를 남긴다.

## 8.7 TCF ON `/online` 호출

TCF ON은 `nhnis.fw.tcf.enabled=true`일 때 활성화된다. `/online`은 path에 Service ID가 없으므로 전문 Header가 필수적인 호출 방식이다.

```text
POST /online
  → DefaultFilter가 hdr_nhnis를 Context로 변환
  → OnlineTransactionController.handleRoot
  → resolveServiceId(null, request)
  → Context rms_svc_c 우선 선택
  → request.get("dto")
  → TcfFacade.process(serviceId, dtoBody)
```

`/{businessCode}/online`의 `businessCode`는 현재 `handle()`로 전달되지만 Service ID 선택 자체는 Header 중심이다. businessCode와 Service ID의 업무축이 일치하는지 강제 검증한다고 가정하지 않는다.

### 정상 예

Header와 path가 없는 `/online` 요청에서 `rms_svc_c=mgcoa9000S0`이면 Dispatcher는 해당 Handler를 찾는다. Facade가 `dto`를 `mgcoa9000S0DTOin`으로 바꾸고 조회 결과를 반환한다.

### 오류 예

`rms_svc_c`가 비고 path도 없으면 Service ID가 null이다. Dispatcher는 `ServiceHandlerNotFound`를 발생시킨다. 이 오류는 DAO나 SQL 문제가 아니라 온라인 거래 식별 실패다.

## 8.8 TCF OFF 직접 URL 호출

TCF OFF에서는 공통 Controller와 Handler가 생성되지 않고 업무 `mgcoa*Controller`가 활성화된다.

```text
POST /mgcoa9000S0
  → mgcoa9000Controller.mgcoa9000S0(DTOin)
  → mgcoa9000Service.mgcoa9000S0(input)
```

AS-IS Controller는 `RequestBodyArgumentResolver`로 `dto`를 typed DTO로 받는다. 현재 `mgcoa9000Controller`는 Facade가 아니라 Service를 직접 호출하므로 TCF ON의 Facade 트랜잭션 경계를 우회한다. 전문 형식이 같아도 실행 의미가 완전히 같지는 않다.

TCF OFF에서 `/online`을 그대로 호출할 수 있다고 가정해서는 안 된다. 업무 Controller에 선언된 직접 Mapping만 사용할 수 있다.

### 개발 판단

ON/OFF 호환성을 유지하려면 두 진입점 아래에서 Facade를 공유하는 구조가 유리하다. 그러나 이것은 권장 방향이며 현재 모든 Controller가 그렇게 구현되어 있다는 뜻은 아니다.

## 8.9 JSON 역직렬화

PDMG 요청은 한 번이 아니라 단계별로 변환된다.

| 단계 | 입력 | 출력 |
|---|---|---|
| Filter | 원시 InputStream | 캐시된 요청 + Header DTO |
| TCF Controller | 전체 JSON Map | `dto` Object |
| TCF Facade | Object/Map | 거래별 DTOin |
| OFF Resolver | 전체 JSON Tree | 거래별 DTOin |
| Response Advice | DTOout | JSON ObjectNode |

### Body 캐싱의 필요성

Servlet 요청 Body는 기본적으로 한 번 읽으면 소모된다. Filter가 Header를 파싱한 뒤 원 요청을 그대로 넘기면 MVC가 읽을 데이터가 없어질 수 있다. `CachedBodyHttpServletRequest`는 Filter, Interceptor와 MVC가 같은 Body를 다시 읽게 한다.

### 변환 실패 유형

- JSON 문법 오류: Tree/Map 파싱 전 실패
- `dto` 위치 오류: 빈 DTO 또는 null Body
- 숫자·날짜 타입 오류: DTO 변환 실패
- 필수값 누락: 업무 검증 단계 실패
- 알 수 없는 필드: OFF Resolver에서는 무시될 수 있음

각 오류는 발생 계층이 다르므로 “전문 오류” 하나로 묶지 않고 Controller 진입 여부와 로그 단계로 구분한다.

---

## 8.10 표준 응답 전문

업무 계층은 `DTOout`을 반환하지만 HTTP 응답은 `ResponseBodyArgumentResolver`가 표준 봉투로 조립한다. 이 클래스는 이름과 달리 `ResponseBodyAdvice<Object>`다.

### 성공 응답

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000S0",
      "std_gbl_id": "추적용-GUID"
    }
  },
  "dto": {
    "totalCount": 25,
    "size": 20
  }
}
```

Advice는 Context Header를 `hdr_nhnis`에 넣고 정상 Body를 `dto`에 넣는다. `dtoLogicalName`, `fieldPropertyMap`, 이름이 `List`나 `Array`로 끝나는 내부 보조 필드는 재귀적으로 제거한다.

### 오류 응답

Body가 `NH_NIS_ERR_DTO`이면 `dto` 대신 `result`를 사용한다.

```text
{ hdr_nhnis, result: NH_NIS_ERR_DTO }
```

정상과 실패를 모두 `dto`로 읽는 UI는 오류 메시지를 잃는다. HTTP 상태와 함께 `result.stdErrCode`, 메시지와 오류 유형을 해석해야 한다.

### 중요한 조건

Response Advice는 `nhnis.fw.commons.legacy-web.enabled=true`일 때 생성된다. 이 설정을 끄면 표준 봉투 조립도 사라질 수 있으므로 단순한 “레거시 로그 옵션”으로 취급하지 않는다.

---

## 8.11 HTTP 상태 코드

HTTP 상태는 전송 결과이고 전문 오류 코드는 업무·Framework 결과다. 둘을 함께 사용해야 한다.

| 상황 | 대표 상태 | 확인 내용 |
|---|---:|---|
| 정상 | 2xx | `dto` |
| 잘못된 JSON·바인딩 | 400 계열 | 요청 구조·타입 |
| 인증 실패 | 401 | Token 누락·만료·서명 |
| 권한 실패 | 403 | 사용자 권한 |
| Mapping 없음 | 404 | TCF ON/OFF·URL |
| 업무/Framework 예외 | 현재 Handler 정책 | `result` 오류 DTO |
| timeout·overload | 공통 예외 정책 | Service ID·GUID·경과시간 |

AS-IS `ResponseBodyArgumentResolver.errorProcessor(NhBaseException)`는 HTTP 500과 `NH_NIS_ERR_DTO`를 반환한다. 모든 업무 오류가 4xx로 세밀하게 구분된다고 가정하면 안 된다.

클라이언트는 2xx 여부만 보지 말고 응답 봉투도 확인하되, HTTP 오류인데 Body가 비어 있거나 표준 형식이 아닐 가능성도 방어해야 한다.

## 8.12 CORS 처리

CORS는 브라우저가 다른 Origin으로 요청할 때 적용하는 보안 정책이다. `pdmg-ui:8090`에서 `pdmg-service:8080`을 직접 호출하면 포트가 달라 서로 다른 Origin이다.

```text
Browser
  → OPTIONS /mgcoa9000S0       preflight
  ← Access-Control-Allow-*
  → POST /mgcoa9000S0          실제 전문
```

### 설정과 소스 연결

```yaml
spring:
  mvc:
    cors:
      allowed-origins:
        - http://localhost:8090
        - http://127.0.0.1:8090
      allowed-methods: [GET, POST, OPTIONS]
      allowed-headers: ["*"]
```

`CorsProperties`가 이 값을 바인딩하고 `WebMvcConfig`가 `/**`에 MVC Mapping과 `CorsConfigurationSource`를 등록한다. Origin 목록이 비면 CORS 설정을 등록하지 않는다. 온라인 URL이 `/api/**`가 아니라 `/{serviceId}`이므로 Mapping 범위는 `/**`다.

`DefaultFilter`는 Body가 없는 OPTIONS를 건너뛰어야 한다. 그렇지 않으면 실제 POST 전에 preflight가 JSON Body 오류로 차단된다.

### 흔한 오진

curl과 Postman은 성공하지만 브라우저만 실패하면 업무 Service보다 CORS를 먼저 확인한다. 브라우저 개발자 도구에서 OPTIONS 상태, 응답의 Allow-Origin, 요청 Origin과 허용 목록의 정확한 일치를 본다.

운영에서는 `*` Origin과 credentials를 무분별하게 조합하지 않고 승인된 UI Origin만 허용한다.

## 8.13 UI Relay와 직접 호출 비교

직접 호출과 Relay는 같은 전문을 전달할 수 있지만 네트워크 경계가 다르다.

```text
직접 호출
Browser → pdmg-service

Relay
Browser → pdmg-ui /api/relay/{id} → pdmg-service
```

| 판단 기준 | 직접 호출 | Relay |
|---|---|---|
| CORS | Service가 UI Origin 허용 | 브라우저 구간 단순화 |
| HTTP 홉 | 1 | 2 |
| timeout | 브라우저·Service | 브라우저·UI Client·Service |
| Token 전달 | 브라우저가 직접 | Relay 전달 정책 필요 |
| 대상 URL 보호 | UI 설정 노출 가능 | 서버 Catalog로 제한 가능 |
| 장애 지점 | 비교적 단순 | UI 중계 장애 추가 |

Relay는 CORS를 피하기 위한 무조건적인 우회가 아니다. 대상 서버를 사용자 입력 URL로 자유롭게 만들면 SSRF 위험이 생긴다. Service Catalog나 허용 목록으로 목적지를 제한하고 Authorization, GUID, Content-Type과 Body를 의도대로 전달해야 한다.

### 선택 기준

브라우저가 서비스 API를 직접 사용하도록 설계했고 서비스가 승인된 Origin을 관리할 수 있다면 직접 호출이 단순하다. UI 서버에서 인증·대상 라우팅·감사를 중앙화해야 한다면 Relay가 적합할 수 있지만 추가 timeout과 장애 지점을 운영해야 한다.

### timeout을 구분하는 방법

UI의 Abort timeout, Relay HTTP Client timeout, PDMG `OnlineTimeoutExecutor`, JDBC query timeout은 서로 다른 제한이다. 화면에 “시간 초과”라고 표시되더라도 어느 계층의 예외인지 GUID와 각 서버 로그로 판별한다.

---

## 전체 정상 시나리오: 거래 파라미터 목록 조회

```text
1. 화면이 mgcoa9000S0 요청 전문을 생성한다.
2. 브라우저가 필요하면 OPTIONS preflight를 수행한다.
3. POST Body가 DefaultFilter에 도착한다.
4. Filter가 Body를 캐싱하고 Header를 ServiceContext에 저장한다.
5. Interceptor가 GUID와 요청 이미지로그를 준비한다.
6. OnlineTransactionController가 Context의 rms_svc_c를 선택한다.
7. dto Object가 TcfFacade와 Handler를 거쳐 Facade로 전달된다.
8. Facade가 mgcoa9000S0DTOin으로 변환한다.
9. Service가 count와 목록 SQL을 실행해 DTOout을 만든다.
10. ResponseBodyAdvice가 hdr_nhnis와 dto를 조립한다.
11. Filter가 Context와 MDC를 정리한다.
12. UI가 dto의 목록·건수 정보를 화면에 표시한다.
```

## 전체 오류 시나리오: Service ID 불일치

```text
path                = /mgcoa9000S0
sys_comm.rms_svc_c  = mgcoa9000D0

Controller 우선순위
  → Context Header의 mgcoa9000D0 선택
  → 삭제 Handler 분기 가능
```

이 사례는 path를 보고 안전한 조회라고 단정하면 안 되는 이유다. 호출자는 값을 동일하게 맞추고, 쓰기 거래에서는 서버가 불일치를 거부하도록 강화할지 검토해야 한다.

## 잘못된 구현 패턴

1. Controller에서 JSON 전체를 매번 수동 파싱한다.
2. 업무 DTO에 `hdr_nhnis` 필드를 포함한다.
3. Filter가 읽은 원 요청을 Wrapper 없이 넘긴다.
4. path와 Header Service ID가 달라도 무조건 허용한다.
5. OPTIONS에 JWT·Body 필수 검사를 수행한다.
6. Controller가 표준 응답 Map을 직접 조립한다.
7. 오류 응답도 항상 `dto`에 있다고 가정한다.
8. Relay 대상 URL을 요청 파라미터 그대로 사용한다.
9. 전문·Token 원문을 마스킹 없이 로그에 남긴다.
10. local 합성 Header를 운영 표준으로 사용한다.

## 메시지 계약의 실전 심화

앞의 8.1~8.13은 HTTP 요청과 표준 전문의 각 부분을 설명했다. 이제 이 요소들을 신규 거래를 실제로 호출하고 장애를 판별할 수 있는 하나의 계약으로 연결한다.

### HTTP Header와 전문 Header를 혼동하지 않는다

PDMG에서 Header라는 말은 두 번 등장한다. 첫 번째는 HTTP Protocol Header이고 두 번째는 JSON Body 내부의 공통 전문 Header다. 이 둘은 전송 위치와 소비자가 다르다.

```text
HTTP Header                       JSON Body 내부 Header

Authorization: Bearer ...         "hdr_nhnis": {
Content-Type: application/json       "sys_comm": {
Accept: application/json               "rms_svc_c": "mgcoa9000S0",
                                         "std_gbl_id": "..."
                                       }
                                     }
```

HTTP Header는 Servlet Container와 인증·콘텐츠 협상 계층이 먼저 해석한다. `Authorization`은 Token 전달 통로이고 `Content-Type`은 Body가 JSON임을 알린다. `hdr_nhnis`는 JSON 속성으로서 Jackson으로 파싱된 뒤 PDMG Framework가 사용한다. JSON에 `Authorization` 필드를 추가해도 HTTP 인증 Header가 되지 않으며, HTTP Header에 `rms_svc_c`를 넣는다고 전문 내부 Service ID를 대체한다고 보장할 수 없다.

Token은 업무 DTO나 `sys_comm`에 복제하지 않는다. Body에 넣으면 전문 로그, ImageLog와 오류 캡처를 통해 노출 범위가 넓어진다. 인증은 HTTP Header, 거래 공통정보는 `hdr_nhnis`, 업무 입력은 `dto`라는 분리를 유지한다.

### 표준 전문은 시스템 간 계약이다

HTTP/JSON을 사용하는 이유는 UI와 업무 서버를 Java 클래스 의존으로 묶지 않고 공개 메시지 계약으로 연결하기 위해서다. 브라우저, 테스트 도구, Relay와 다른 시스템은 Java DTO를 직접 로딩하지 않아도 같은 Endpoint를 호출할 수 있다. 텍스트 기반 JSON은 장애 분석에 유리하고 Spring MVC/Jackson 생태계를 사용할 수 있다. 반면 컴파일러가 Client와 Server의 불일치를 즉시 잡아주지 않으므로 필드·타입·필수값·호환성을 계약 테스트로 관리해야 한다.

표준 봉투는 모든 거래의 공통 식별·추적 정보를 업무 DTO마다 복제하지 않게 한다. 고객 조회 조건과 GUID는 변경 주체와 소비자가 다르다. 전자는 업무 개발자가 설계하고 Service가 사용하며, 후자는 Framework와 운영 도구가 사용한다. 두 영역을 분리하면 업무 DTO 변경이 공통 실행 코드에 번지지 않고 공통 Header 확장도 모든 Service 시그니처를 바꾸지 않고 처리할 수 있다.

```text
Request Root
  ├─ hdr_nhnis                    공통 전문 영역
  │    └─ sys_comm
  │         ├─ rms_svc_c          Service ID
  │         ├─ std_gbl_id         GUID
  │         ├─ tr_sysid           거래 시스템
  │         ├─ tr_trm_ipadr       단말 IP
  │         ├─ tr_brc             취급점
  │         ├─ scid               화면·프로그램
  │         └─ optr_eno           조작자 식별
  └─ dto                          업무 계약 영역
       └─ Service ID별 DTOin 필드
```

`sys_comm`이 최상위에 따로 놓이거나 업무 데이터가 `data`, `body`라는 임의 이름에 들어가는 구조가 아니다. 예제 필드가 존재한다는 것과 모든 실행 경로에서 정책 판단에 사용된다는 것은 다르다. 영업점·채널 값이 Header에 있어도 거래통제가 실제로 그 값을 읽는지 별도로 확인해야 한다.

### Client가 보낸 공통값의 신뢰 경계

`optr_eno`, `tr_brc`, `tr_trm_ipadr`가 전문에 있다고 해서 인증·권한 검증이 끝난 것은 아니다. Browser가 값을 변경할 수 있다면 그 값만으로 사용자나 접근 가능한 영업점을 결정해서는 안 된다.

```text
Client Provided Data
        │
        ▼
JWT / Session / Trusted Proxy 검증
        │
        ▼
Trusted Server Context
        │
        ▼
거래통제와 업무 권한 판단
```

인증된 Claim·Session·Gateway Context와 전문값을 비교하고 불일치를 차단해야 한다. 현행 코드에서 전체 검증 정책이 확인되지 않은 필드는 “서버가 신뢰한다”고 단정하지 않고 TO-BE 보안 요구로 남긴다. `X-Forwarded-For`도 승인된 Proxy가 덮어쓰는 신뢰 구간 없이 외부 입력을 그대로 사용하면 IP 기반 통제가 우회될 수 있다.

### Service ID, URL과 GUID의 관계

URL은 어느 HTTP Entry Point로 갈지를 결정하고 Service ID는 그 Entry 안에서 어느 거래를 실행할지 결정한다. GUID는 같은 거래가 여러 번 호출될 때 한 건을 구분한다.

```text
URL        : 어느 입구인가?
Service ID : 무슨 거래인가?
GUID       : 이 요청 한 건은 무엇인가?
```

같은 사용자가 조회 버튼을 세 번 누르면 Service ID는 같아도 GUID는 세 개여야 한다. 반대로 한 호출이 Filter, Interceptor, TCF와 DAO를 이동하는 동안 GUID는 유지돼야 한다. Relay나 외부 시스템 경계를 넘을 때 자동 보존되지 않으므로 합의된 Header 또는 전문 전달 정책이 필요하다.

현행 `OnlineTransactionController.resolveServiceId()`는 Context Header, 요청 JSON Header, URL Path 순으로 값을 찾지만 서로 다른 값이 동시에 존재할 때 거절하지 않는다. `/mgcoa9000S0` Path에 `rms_svc_c=mgcoa9000D0`을 보내면 Header 거래가 선택될 가능성이 있다. 호출자는 모든 위치의 값을 일치시키고 TO-BE 서버는 불일치를 400 계열로 조기에 거절하는 정책을 검토해야 한다.

### TCF ON/OFF의 HTTP 계약과 실행 의미

현행 TCF ON Controller는 `/online`, `/{businessCode}/online`, `/{serviceId}` POST Mapping을 제공한다. `/online`의 핵심은 URL이 공통 입구이고 `rms_svc_c`가 업무 거래를 식별한다는 점이다. 일반 REST URL만 보아 업무를 이해하는 방식과 달리 Service ID Catalog가 필요하다.

| 구분 | TCF ON | TCF OFF AS-IS |
|---|---|---|
| 대표 URL | `/online`, `/{businessCode}/online`, `/{serviceId}` | 업무 Controller의 `/{serviceId}` |
| Entry | OnlineTransactionController | `mgcoa*Controller` |
| 거래 선택 | Header/JSON/Path Service ID | Spring URL Mapping |
| Handler | 사용 | 사용하지 않음 |
| DTO 변환 | Map/Object→Facade DTO | Resolver→Controller DTO |
| 업무 Facade | 사용 | 현행 Controller는 Service 직접 호출 |
| 표준 Body | `hdr_nhnis` + `dto` | 같은 봉투 사용 가능 |

두 모드는 동일 DTO 계약을 사용할 수 있지만 실행 의미까지 같지는 않다. OFF 경로는 Handler, Facade와 OnlineTimeoutExecutor를 건너뛰므로 트랜잭션·Timeout은 ON과 다를 수 있다. HTTP Body 공통성과 Runtime 공통성을 구분해야 한다.

TCF ON의 공통 Entry는 Service ID에 통제·로그·Timeout 정책을 연결하기 유리하다. 반면 URL만으로 업무 의미를 알기 어렵고 UI Catalog, Header와 Handler Registry를 함께 관리해야 한다. TCF OFF 직접 URL은 이해하기 쉽지만 공통 라우팅 기능을 우회한다.

### 업무 DTO와 역직렬화 계약

DTO는 네트워크와 업무 계층 사이의 계약이다. JSON 필드가 DTOin으로 변환되면 Facade와 Service는 임의 Map Key 대신 타입이 있는 입력을 다룰 수 있다. 처리 결과는 DTOout으로 만들고 정상 응답 `dto`에 들어간다. DB Row 전체를 그대로 노출하면 Schema 변경이 HTTP 계약 변경이 되므로 유스케이스에 필요한 입력·출력만 정의한다.

TCF ON에서는 공통 Controller가 전체 JSON을 Map으로 받은 뒤 Facade가 거래별 DTOin으로 변환한다. OFF에서는 커스텀 Resolver가 `dto` 노드를 Controller DTOin으로 변환한다. 변환 위치는 다르지만 같은 DTO 타입과 필드 계약을 사용할 수 있다.

JSON Syntax 오류는 DTO가 만들어지기 전의 메시지 오류다. 숫자 자리에 문자열이 들어가거나 객체 자리에 배열이 오면 타입 변환 오류가 발생한다. `dto`가 없을 때 ON은 null이 전달될 수 있고 OFF Resolver는 빈 객체를 만들 수 있으므로 역직렬화 성공과 업무 입력 유효성 검증을 구분한다. 알 수 없는 필드를 무시하는 ObjectMapper 정책은 하위 호환에는 유리하지만 오타 탐지를 약화한다.

Servlet Body는 일반적으로 한 번 소비된다. Filter가 공통 Header를 읽고 MVC가 DTO를 다시 만들려면 Body 재사용 장치가 필요하다. 이 장에서는 같은 메시지를 여러 계층이 소비한다는 문제만 이해하고 Wrapper 구현은 9장에서 다룬다.

### Response와 HTTP Status를 함께 해석한다

요청과 응답은 공통 Header 문맥을 공유하지만 `dto` 의미는 다르다. 요청 `dto`는 DTOin이고 정상 응답 `dto`는 DTOout이다. 서버는 요청 Header를 그대로 echo하기보다 GUID·Service ID·IP가 보완된 Context를 직렬화할 수 있다. 오류에서는 정상 업무 데이터 대신 `result`가 들어간다.

Filter에서 발생한 빈 Body·JSON·JWT 오류는 MVC Advice에 도달하지 않고 `sendError()`로 끝난다. 모든 오류 응답이 `{hdr_nhnis,result}`라고 가정할 수 없다. Client는 다음 순서로 응답을 해석한다.

```text
1. 네트워크 자체 성공 여부
2. HTTP Status
3. Content-Type과 Body 존재 여부
4. 표준 봉투의 dto/result 구분
5. 업무 오류 코드와 메시지
6. GUID를 이용한 서버 추적
```

HTTP Status는 전송·서버 처리 결과이고 업무 오류 코드는 어떤 업무·Framework 규칙이 실패했는지 표현한다. 현행 레거시 처리기는 `NhBaseException`을 HTTP 500과 오류 DTO로 반환할 수 있다. 따라서 모든 업무 오류가 HTTP 200이라는 규칙도, 모두 400이라는 규칙도 현재 사실로 일반화하지 않는다. 운영 지표는 두 값을 함께 집계해야 한다.

### CORS와 Authorization

Origin은 Protocol, Host, Port의 조합이다. 하나라도 다르면 Browser는 교차 Origin 요청으로 본다. CORS는 Server 간 HTTP를 막는 Network 규칙이 아니라 Browser가 응답을 Page JavaScript에 공개할지 결정하는 정책이다. 같은 요청이 Postman에서는 성공하고 Browser에서만 막힐 수 있다.

Authorization 같은 Header를 보내면 Browser가 실제 POST 전에 OPTIONS Preflight를 보낼 수 있다. 서버는 Origin, Method와 Header가 허용됐음을 응답해야 한다. 현행 설정은 허용 Header에 `*`를 두므로 Authorization을 포함할 수 있지만 운영에서는 승인 Origin과 필요한 Header를 명시하는 것이 명확하다. `allowCredentials` 활성화는 현재 확인되지 않았으므로 Cookie Credential이 지원된다고 단정하지 않는다.

### UI 직접 호출과 Relay의 실제 메시지 차이

현행 `TransactionRelayService`는 Content-Type과 Accept를 기본 Header로 지정하고 Body 문자열을 대상 서비스로 POST한다. 대상 응답은 transaction ID, target URL, HTTP status, elapsed time과 Body를 가진 `RelayResult`로 감싼다. Byte 단위로 투명하게 전달하는 단순 Proxy가 아니다.

현재 Relay 코드에서는 Browser 요청의 Authorization Header를 대상 요청으로 복사하는 처리가 확인되지 않는다. GUID는 JSON Body에 포함되면 유지될 수 있지만 Relay가 별도로 검증·보완하지 않는다. 비-local 대상 서비스가 Bearer Token을 요구하면 현행 Relay가 인증에 실패할 수 있으므로 “Relay가 JWT를 전달한다”고 추측해서는 안 된다.

| 메시지 관점 | 직접 호출 | Relay 호출 AS-IS |
|---|---|---|
| Browser 대상 | pdmg-service | pdmg-ui Relay |
| Body | 표준 전문 직접 전송 | Body 문자열 재전송 |
| Authorization | Browser가 Service에 직접 전송 | 대상 전달 코드 확인되지 않음 |
| GUID | 전문에 넣어 직접 전달 | Body에 있으면 유지, 별도 보완 없음 |
| 응답 | Service 응답 직접 수신 | `RelayResult`로 래핑 |
| CORS | Service가 UI Origin 허용 | Browser→UI 구간 단순화 가능 |
| Timeout | Browser + Service | Browser + Relay Client + Service |
| 대상 URL | Browser 설정이 인지 | Relay가 계산하나 요청 Override 가능 |

Relay는 요청 `baseUrl`로 URI를 구성할 수 있고 임의 Path 중계 메서드도 갖는다. 운영 Host 허용 목록이 없다면 SSRF 위험이 생긴다. TO-BE에서는 설정된 Target만 선택하고 Scheme, Host, Port와 Path를 검증해야 한다.

### 전문 변경 영향도와 버전 관리

표준 전문은 DTO 파일 하나가 아니라 여러 모듈 사이의 계약이다. `rms_svc_c` 이름이나 타입을 바꾸면 UI 요청 생성, Filter 변환, ServiceContext, Controller 라우팅, 거래통제와 로그 검색이 영향을 받는다. `dto` 변경은 화면, Facade, Service와 테스트에 파급된다. 응답 봉투 변경은 UI Parser와 Relay 결과 처리에 영향을 준다.

```text
표준 전문 변경
  → pdmg-ui 요청/응답 처리
  → pdmg-service Controller/DTO
  → pdmg-fw Filter/Context/Advice
  → Handler Registry와 거래 통제
  → 로그/ImageLog/운영 검색
  → 외부 Client와 계약 테스트
```

현행 전문에서 명시적 Version 필드는 표준으로 확인되지 않았다. 버전 자동 협상을 가정하지 않는다. 필드 추가는 기존 Consumer의 Unknown Field 정책을 확인하고, 삭제·이름 변경·타입 변경은 호환 기간과 UI/Server 배포 순서를 정해야 한다. 공개 계약 변경에는 Rollback 방법과 양쪽 버전 공존 계획이 필요하다.

### 민감정보와 전문 로그

표준 전문 전체 기록은 장애 분석에 유리하지만 Token, 개인정보와 업무 Secret이 함께 저장될 수 있다. Authorization Header는 전문 로그에서 제외하고 `dto` 민감 필드는 필드 기반으로 Masking하며 요청 크기 제한, 보존 기간과 조회 권한을 적용한다. GUID를 이용하면 전체 민감 원문 없이도 계층별 로그를 연결할 수 있다. 책과 테스트의 예제에도 실제 비밀번호, JWT, Refresh Token, 계좌번호와 개인정보를 사용하지 않는다.

### 새로운 HTTP 요청을 만드는 12단계

1. 요구사항과 업무 소유 도메인을 확인하고 실행할 Service ID를 결정한다.
2. TCF ON/OFF 설정과 Controller Mapping을 확인해 Target URL을 선택한다.
3. Controller가 허용하는 HTTP Method가 POST인지 소스로 확인한다.
4. 비-local이면 Bearer Access Token의 발급·전달 주체를 확인한다.
5. `Content-Type: application/json`과 필요한 `Accept`를 설정한다.
6. 실제 계약에 따라 `hdr_nhnis.sys_comm`을 구성한다.
7. 요청 한 건의 GUID를 생성하거나 서버 보완 정책을 확인한다.
8. Service ID와 URL·화면 선택값을 일치시킨다.
9. 거래별 DTOin에 맞춰 `dto`를 구성하고 민감정보를 제외한다.
10. 직렬화한 JSON의 필드 이름·타입·필수값을 실제 DTO와 대조한다.
11. 호출 후 HTTP Status를 확인하고 `dto` 또는 `result`를 해석한다.
12. 실패하면 GUID로 Browser, Relay, Filter, TCF와 업무 로그를 추적한다.

Postman이나 curl에서는 CORS가 재현되지 않는다는 점을 기록한다. Browser 통합 테스트에서는 OPTIONS와 Authorization 허용 여부를 별도로 확인한다. local Header 합성에 의존한 테스트와 완전한 운영형 전문 테스트도 구분한다.

## Request에서 Runtime까지의 추적표

| Request 정보 | 실제 위치 | 제공·생성 주체 | 서버 사용처 | 신뢰 원칙 |
|---|---|---|---|---|
| Authorization | HTTP Header | UI/호출 시스템 | JWT 검증 | Token 원문 로그 금지 |
| Content-Type | HTTP Header | HTTP Client | Body 해석 | JSON과 multipart 분기 |
| Service ID | `hdr_nhnis.sys_comm.rms_svc_c`·Path | UI/Framework | Controller, Dispatcher | 위치 간 일치 검증 필요 |
| GUID | `hdr_nhnis.sys_comm.std_gbl_id` | UI/Framework 보완 | Context, 로그, ImageLog | 호출 한 건 동안 유지 |
| 사용자 | `optr_eno` 및 인증 Context | Client/인증 시스템 | 감사·통제 | Client 값 단독 신뢰 금지 |
| IP | `tr_trm_ipadr`·HTTP 연결 | Proxy/Framework | 통제·감사 | Trusted Proxy 정책 필요 |
| 업무 입력 | 최상위 `dto` | UI | Facade, Service | DTO 검증 필요 |

## 메시지 경계별 정상·실패 판정

온라인 거래의 성공 여부는 한 지점에서만 결정되지 않는다. Browser가 요청을 만들었어도 CORS에서 중단될 수 있고, HTTP 연결이 성공했어도 인증이나 JSON 파싱에서 거절될 수 있다. DTO가 만들어진 뒤에도 Service ID 라우팅과 업무 검증이 남아 있다. 따라서 운영자는 다음 경계를 순서대로 확인한다.

```text
Browser 요청 생성
  → Preflight/CORS
  → HTTP 연결
  → Authorization 검증
  → 표준 전문 JSON 파싱
  → Service ID 선택
  → DTO 역직렬화·입력 검증
  → 업무 실행
  → 표준 응답 조립
  → Browser 응답 해석
```

정상 거래에서는 URL과 `rms_svc_c`가 일치하고, GUID가 요청·응답과 로그에서 유지되며, `dto`가 DTOin으로 변환된다. 업무 결과는 DTOout이 되어 응답 `dto`로 돌아오고 HTTP Status도 성공 범위다.

실패 거래에서는 마지막으로 성공한 경계를 찾는다. Browser Network 탭에 OPTIONS만 있으면 CORS를, 401이면 Authorization을, 400이면 JSON과 공통 Header를 확인한다. Filter와 Controller 로그는 있지만 Handler 로그가 없으면 Service ID를, Handler 이후 실패하면 DTO 검증·Service·DAO를 확인한다. Relay 경로라면 Browser가 받은 Status와 `RelayResult` 내부의 대상 Status를 구분한다.

이 방식은 “화면에 오류가 보인다”는 하나의 증상을 네트워크, 메시지, 라우팅과 업무 실패로 분해한다. 모든 구간에서 GUID를 유지해야 같은 요청을 정확하게 연결할 수 있으며, GUID가 없다면 시각·Service ID·사용자 식별값을 보조 단서로 사용하되 개인정보를 로그에 추가하지 않는다.

## 운영 및 모니터링

운영에서는 최소한 다음 값을 연결해 볼 수 있어야 한다.

```text
timestamp, guid, serviceId, HTTP status,
selected controller, elapsedMs, result/errorCode,
client channel, masked user, client IP
```

브라우저 장애에는 Origin과 preflight, 서버 장애에는 Controller 진입 여부, 거래 장애에는 Service ID와 GUID, 응답 장애에는 Advice 적용 여부를 확인한다. 전문을 저장할 때는 크기 제한·보존 기간·마스킹을 적용한다.

## 아키텍처 판단 포인트

전문 설계의 핵심은 모든 정보를 한 DTO에 모으는 것이 아니라 **공통 문맥과 업무 계약의 변경 이유를 분리하는 것**이다. Filter와 Context는 공통 문맥을 관리하고, Resolver와 Facade는 업무 DTO를 만든다. Response Advice는 두 영역을 다시 표준 응답으로 결합한다.

TCF ON과 OFF는 같은 JSON을 받을 수 있지만 Controller, DTO 변환과 트랜잭션 경계가 다르다. 직접 호출과 Relay도 같은 전문을 전달할 수 있지만 CORS, 인증 전달과 timeout 경계가 다르다. 아키텍처 판단은 JSON 모양만 비교하지 말고 전체 실행 경계를 비교해야 한다.

## 이 장의 핵심 정리

PDMG 전문은 `hdr_nhnis`와 `dto`로 구성된다. `hdr_nhnis`는 GUID·Service ID·사용자·채널 같은 시스템 문맥이고, `dto`는 Service ID별 업무 입력이다. Filter가 Body와 Context를 준비하고, TCF Controller 또는 업무 Resolver가 `dto`를 분리하며, 업무 결과는 Response Advice가 `{hdr_nhnis, dto}` 또는 `{hdr_nhnis, result}`로 조립한다.

가장 중요한 운영 규칙은 path와 `rms_svc_c`를 일치시키고 GUID를 전 구간에서 유지하는 것이다. 브라우저 직접 호출에서는 CORS를, Relay에서는 추가 HTTP 홉과 전달 정책을 관리해야 한다.
