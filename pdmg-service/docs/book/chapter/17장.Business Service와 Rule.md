# 제4부 업무 진입과 유스케이스 경계

# 17장. Business Service와 Rule

Business Facade가 입력 DTO와 트랜잭션 의도를 준비하면 실제 업무 순서는 Service에서 실행된다. Service는 DAO를 한 번 호출하는 얇은 포장지가 아니다. 입력을 업무 관점으로 확인하고, 필요한 규칙을 적용하며, 하나 이상의 데이터 접근이나 외부 호출을 순서대로 조정하고, 호출자가 사용할 결과를 조립하는 애플리케이션 핵심 계층이다.

Rule은 Service와 다르다. Rule은 여러 유스케이스에서 다시 사용할 수 있는 검증·계산·판정 정책을 표현한다. Service가 “무엇을 어떤 순서로 실행할 것인가”를 담당한다면 Rule은 “어떤 조건이 유효하고 어떤 값을 계산할 것인가”를 담당한다. 다만 현재 `nhnis.mg.co.a.application` 아래에는 별도의 `rule` 패키지와 Rule 구현이 확인되지 않는다. 따라서 이 장은 실제 Service 구조를 AS-IS로 설명하고, Rule 분리는 목표 책임 모델로 명확히 구분한다.

## 이 장에서 해결할 질문

- PDMG Business Service는 Facade와 DAO 사이에서 무엇을 책임지는가?
- 입력 형식 검증과 업무 규칙 검증은 어디에서 나뉘는가?
- ServiceContext는 어떤 공통 정보를 제공하며 어떻게 의존해야 하는가?
- 조회·등록·수정·삭제 Service의 실행 흐름은 무엇이 다른가?
- Rule을 분리할 기준은 무엇이며 현재 구현에는 실제 Rule이 있는가?
- 여러 DAO와 외부 Client의 실패를 어떻게 조정하는가?
- 결과 DTO는 어느 계층에서 어떤 근거로 조립하는가?

## 전체 실행 위치

```text
Handler / Controller
        │
        ▼
Business Facade
   ├─ 외부 본문 → 입력 DTO
   └─ Transaction 선언
        │
        ▼
BizPrePostAspect
        │
        ▼
Business Service
   ├─ 입력·Context 확인
   ├─ 업무 순서 조정
   ├─ Rule 호출(설계 경계)
   ├─ DAO / Client 호출
   └─ 결과 DTO 조립
        │
        ▼
DAO → Mapper → DB
```

AS-IS Service는 `nhnis.mg.co.a.application.service` 패키지에 있고 Spring `@Service` Bean이다. `mgcoa5530Service`, `mgcoa8888Service`, `mgcoa9000Service`, `mgcoa9001Service`, `mgcoa9100Service`, `mgcoa9999Service`가 확인된다. 구현은 DTO를 받아 `Map<String,Object>` 조건을 만들고 DAO 결과 Map을 출력 DTO로 옮기는 형태가 많다.

## 17.1 Service의 책임

Service의 첫 책임은 업무 실행 순서를 명시하는 것이다. 예를 들어 조회에서는 검색 조건 정규화, 페이지 값 확정, 건수 조회, 목록 조회, DTO 변환, 페이지 메타데이터 계산이 한 흐름이다. 어느 단계가 먼저인지와 한 단계 실패 시 다음 단계를 실행하지 않는다는 계약이 Service 메서드에 드러난다.

두 번째 책임은 업무 의미를 가진 입력과 결과를 유지하는 것이다. DAO가 Map을 반환하더라도 Service는 그 Map을 외부로 그대로 노출하지 않고 거래별 `DTOout`과 `DTOSub0`으로 바꾼다. 생성·수정·삭제에서는 처리 건수에 따라 결과 코드와 메시지를 채운다.

세 번째 책임은 Rule·DAO·Client의 조정이다. 현행 주요 Service는 단일 DAO를 직접 호출하며 별도 Rule이나 외부 Client 사용은 확인되지 않는다. 이것이 “Service는 항상 DAO 하나만 호출해야 한다”는 규칙은 아니다. 복합 유스케이스에서는 여러 협력자를 조정하되 원자성, 호출 순서와 실패 의미를 분명히 해야 한다.

Service는 HTTP URL, 상태 코드, Servlet Request를 알 필요가 없다. 이러한 독립성 덕분에 TCF Handler, OFF Controller의 Facade, 테스트가 같은 업무 메서드를 호출할 수 있다.

## 17.2 입력값 확인

Facade의 `ObjectMapper.convertValue`가 성공했다고 입력이 업무적으로 유효한 것은 아니다. Service는 필수 식별자, 허용 범위, 상태 조합과 같은 업무 조건을 확인해야 한다. 현행 조회 Service는 null 입력을 허용하고 기본 검색과 페이지 값을 사용한다. 이 동작은 조회 편의에는 맞을 수 있지만 생성·수정·삭제 키까지 같은 방식으로 허용해서는 안 된다.

`mgcoa8888D0`는 입력이나 GUID 목록이 없으면 처리 건수 0, 결과 코드 `0001`, 메시지 `NO_DATA`를 반환한다. 목록에서는 null·공백을 제거하고 trim·distinct를 적용한다. 이는 삭제 대상 정규화의 실제 사례다. 반면 예외를 던질지 결과 코드로 표현할지는 거래 계약 전체에서 일관되어야 한다.

페이지 입력은 여러 조회에서 1 이하 pageNo를 1로, 0 이하 pageSize를 기본값으로 바꾸고 최대 100으로 제한한다. 같은 규칙이 반복되는 만큼 공통 PageRequest나 Rule 후보가 될 수 있다. 다만 기본 pageSize가 Service별로 10 또는 20인 사례가 있어 무조건 하나의 값으로 통합해서는 안 된다.

검증 실패 뒤 DAO를 호출하지 않는다는 것을 테스트해야 한다. 특히 수정·삭제 식별자 누락은 WHERE 조건 약화로 이어질 수 있으므로 Mapper 방어만 믿지 않고 Service 이전 또는 Service에서 명확히 차단한다.

## 17.3 ServiceContext 활용

ServiceContext는 GUID, 표준 Header, 사용자·채널 등 요청 공통 정보를 Thread 범위에서 제공한다. 업무 Service가 감사 사용자나 영업점처럼 인증·전문에서 온 값을 필요로 할 때 HTTP Request를 직접 읽는 대신 검증된 Context 계약을 사용할 수 있다.

```text
HTTP/TCF 앞단 → ServiceContext 생성·보완
                    │
                    ▼
             ServiceContextHolder
                    │
                    ▼
Business Service → 필요한 공통값 조회
```

그러나 현행 주요 CRUD Service에서 `ServiceContextHolder`를 직접 사용하는 코드는 검색되지 않았다. 업무 선후 Aspect가 GUID와 Service ID를 읽는 것이 대표 사용처다. 따라서 “모든 Service가 Context에서 사용자 ID를 꺼내 DAO에 전달한다”고 AS-IS로 단정하지 않는다.

Context가 없을 때의 정책도 필요하다. 단위 테스트, 배치, OFF 우회 경로에서는 null일 수 있다. 필수 감사 정보라면 명시적으로 실패시키고, 선택적 로그 정보라면 null을 안전하게 처리한다. mutable Context를 업무 Service가 변경하면 뒤 계층 로그와 정리 과정이 왜곡될 수 있으므로 읽기 위주로 사용한다.

## 17.4 업무 처리 순서

Service 메서드는 다음 순서를 읽을 수 있어야 한다.

```text
입력 확인·정규화
   → 업무 규칙 판정
   → DAO/Client 호출 준비
   → 핵심 처리
   → 후속 처리
   → 결과 DTO 조립
   → 정상 반환 또는 예외 전파
```

현행 `mgcoa9000S0`는 검색 조건을 Map에 넣고 페이지를 계산한 뒤 count DAO, list DAO를 순서대로 호출한다. 결과 각 행을 `mgcoa9000S0DTOSub0`으로 변환하고 size·pageNo·pageSize·totalCount·totalPages를 설정한다. 이 전체가 조회 유스케이스의 업무 순서다.

코드의 순서는 실패 의미도 나타낸다. count가 실패하면 목록을 실행하지 않는다. 목록이 실패하면 부분 DTO를 반환하지 않고 예외가 전파된다. 정상 반환 뒤에만 BizPrePostAspect의 정상 후처리가 실행된다.

## 17.5 Rule 호출

Rule은 입력과 현재 상태를 받아 검증 결과, 계산값 또는 판정을 반환하는 재사용 가능한 정책 객체다. 가능하면 DB·HTTP·ThreadLocal에 의존하지 않는 순수 로직으로 두어 빠르게 단위 테스트한다.

```text
Service
   ├─ DAO로 현재 상태 조회
   ├─ Rule.validate(input, current)
   ├─ Rule.calculate(input, current)
   └─ DAO로 결과 반영
```

위 흐름은 권장 책임 모델이며 현행 별도 Rule 구현은 확인되지 않는다. 현재 Service의 페이지 상한, 시간 범위 상한, 결과 판정과 같은 코드 중 재사용·변경 빈도가 높은 규칙은 Rule 후보다. 단순 문자열 trim이나 Map 키 변환까지 모두 Rule로 만들면 작은 Helper가 난립한다.

Rule 분리 기준은 업무 언어로 이름 붙일 수 있는가, 여러 유스케이스에서 재사용되는가, 독립된 입력·결과와 테스트 사례가 있는가이다. DAO 호출 순서와 Transaction 조정은 Rule이 아니라 Service에 남긴다.

## 17.6 조회 Service

조회 Service는 조건 정규화, 페이지 정책, count와 목록의 정합성, 결과 변환을 책임진다. `mgcoa5530S0`는 `trtBrc`, `basDt`가 유효할 때만 조건에 넣고 pageNo 기본 1, pageSize 기본 20, 최대 100을 적용한다. count와 목록 DAO를 호출한 뒤 행 Map의 대소문자 키 차이를 흡수해 Sub DTO를 만든다.

이 메서드에는 여러 번의 `Thread.sleep`과 `System.out.println`이 남아 있다. 총 지연 주석과 실제 sleep 횟수도 면밀히 대조해야 한다. 이는 Timeout 시험용 코드로 보이지만 운영 조회 경로의 AS-IS에 존재하므로 성능과 Timeout에 직접 영향을 준다. 업무 Service의 정상 기능으로 정당화할 수 없으며 제거 또는 테스트 전용 대체가 필요한 위험 요소다.

조회 Transaction은 Facade의 readOnly 또는 상위 Worker 거래에 따라 달라진다. Service는 readOnly라고 해서 결과 조립을 생략하지 않지만 DB 변경을 섞어서는 안 된다. count와 list 사이 데이터가 변할 수 있는 격리 수준의 의미도 요구사항에 맞게 판단한다.

## 17.7 등록 Service

등록 Service는 필수키와 중복 정책을 확인하고 DAO INSERT 결과를 업무 출력으로 바꾼다. 현행 `mgcoa9000C0`과 `mgcoa9001C0` 같은 메서드는 거래별 입력 DTO를 받고 Map을 구성해 DAO를 호출한다. 상세 필드 계약은 실제 DTO와 Service를 함께 확인해야 한다.

등록 성공은 SQL이 예외 없이 실행됐다는 사실만으로 정의하지 않는다. 처리 건수가 기대값인지, 생성 식별자를 반환해야 하는지, 중복을 표준 업무 오류로 바꿀지 결정한다. 등록 뒤 이력이나 다른 테이블 작업이 필요하면 같은 유스케이스의 Facade/Service Transaction 안에서 순서를 조정한다.

요청 사용자 ID를 클라이언트 필드 그대로 신뢰하지 않는다. 인증된 Context 값과의 관계를 정의하고 감사 필드는 서버가 결정하는 것이 안전하다. 현행 소스에서 일괄 적용을 확인하지 못했으므로 신규 설계 시 검증할 항목이다.

## 17.8 수정 Service

수정은 대상 식별자와 변경 가능 필드를 분리해야 한다. 먼저 식별자가 필수인지 확인하고, 필요하면 현재 행을 조회해 존재·상태·버전 조건을 판정한 다음 UPDATE한다. 처리 건수 0은 “성공했지만 변화 없음”, “대상 없음”, “동시 수정 충돌” 중 무엇인지 업무 계약으로 구분한다.

여러 필드를 부분 수정할 때 null의 의미가 중요하다. null이 변경하지 않음인지 값을 null로 설정함인지 DTO와 Mapper가 같은 해석을 해야 한다. Service가 Map에 값이 있는 필드만 넣는다면 그 규칙을 명시적으로 테스트한다.

낙관적 잠금을 사용한다면 version 조건과 처리 건수 판정이 Service 책임에 포함된다. 현행 CRUD Service에서 공통 version 정책은 확인되지 않으므로 TO-BE 검토 사항이다.

## 17.9 삭제 Service

삭제 Service는 물리 삭제와 논리 삭제, 단건과 다건, 존재하지 않는 대상의 결과를 구분한다. `mgcoa8888D0`는 GUID 목록을 정제한 뒤 DAO에 전달하고 처리 건수와 결과 코드를 조립하는 다건 삭제 사례다.

대량 ID를 한 SQL에 전달할 때 허용 개수와 SQL 파라미터 한계도 정해야 한다. 빈 목록을 Mapper까지 넘겨 잘못된 `IN ()` SQL을 만들지 않도록 Service에서 차단한다. 중복 ID 제거는 처리 건수 해석을 안정화한다.

삭제 이력과 참조 데이터가 있다면 실행 순서와 Rollback 범위를 설계한다. 업무 예외를 빈 성공 DTO로 바꾸면 일부 삭제가 커밋될 수 있으므로 예외를 경계 밖으로 전파한다.

## 17.10 여러 DAO 호출

여러 DAO 호출은 하나의 업무 성공 조건을 구현할 때 Service 또는 Facade에서 조정한다. 같은 유스케이스 내부의 밀접한 상태 변화는 Service가 순서를 보여 주는 것이 자연스럽다. 서로 독립적인 하위 유스케이스의 결합은 Facade가 조정할 수 있다.

```text
TX BEGIN
Service
   ├─ DAO A: 현재 상태 조회
   ├─ Rule: 변경 가능 판정
   ├─ DAO A: 본 테이블 UPDATE
   └─ DAO B: 업무 이력 INSERT
정상 COMMIT / 하나라도 실패하면 ROLLBACK
```

동일 TransactionManager와 DataSource, 같은 Thread에서 실행되어야 원자적으로 묶인다. DAO B 예외를 catch해 무시하면 DAO A만 커밋될 수 있다. 반대로 이력 실패가 본 업무 성공을 막지 않아야 한다면 독립 거래·이벤트 정책을 명시한다.

## 17.11 외부 Client 호출

현행 주요 업무 Service에서 별도 `client` 계층 호출은 검색되지 않았다. 외부 연계가 추가되면 저장소 규칙에 따라 client 계층과 `tcf-eai` 사용을 우선한다. HTTP 라이브러리를 Service에 직접 흩뿌리지 않는다.

외부 호출은 JDBC Transaction의 Rollback 대상이 아니다. 원격 성공 뒤 로컬 Rollback이 발생할 수 있으므로 멱등키, 호출 순서, 재시도, 보상, Outbox를 결정한다. Timeout도 온라인 전체 deadline과 외부 Client timeout을 계층적으로 맞춘다.

외부 오류를 모두 같은 RuntimeException으로 바꾸면 재시도 가능 여부와 표준 오류 코드가 사라진다. 인증 실패, 연결 실패, 원격 업무 거절을 구분하되 내부 URL과 Token을 응답·로그에 노출하지 않는다.

## 17.12 결과 DTO 조립

현행 Service는 DAO가 반환한 `List<Map<String,Object>>`를 반복하며 Sub DTO를 만들고 출력 DTO에 추가한다. DB 컬럼의 대문자 키와 camelCase 키를 모두 확인하는 `asString` helper도 여러 클래스에 있다. H2·Oracle·MyBatis 환경별 키 차이를 흡수하려는 목적이다.

이 반복 변환은 Service가 외부 계약을 완성한다는 장점이 있지만 Map 키 오타가 컴파일 때 잡히지 않는다. Mapper resultMap 또는 typed row 객체를 사용하면 타입 안전성을 높일 수 있다. 변경 시 Mapper, DTO, Service와 테스트를 함께 바꿔야 한다.

페이징 출력에는 현재 페이지 목록 size와 전체 건수, 전체 페이지를 구분한다. `totalPages = (totalCount + pageSize - 1) / pageSize` 계산은 overflow와 0 정책을 고려한다. DTO의 상세 계약은 다음 장에서 다룬다.

## 17.13 Service 예외 처리

Service는 복구할 수 없는 예외를 로그만 남기고 정상 결과로 바꾸지 않는다. DAO·MyBatis 예외와 업무 검증 예외는 표준 예외 계층으로 전파되어 최외곽 Transaction이 Rollback을 판단하고 공통 Handler가 응답을 만든다.

catch가 필요한 경우는 interrupt 복원, 자원 정리, 의미 있는 업무 예외 변환처럼 목적이 분명해야 한다. `mgcoa5530Service`는 sleep 중 `InterruptedException`을 잡아 interrupt flag를 다시 설정하지만 이후 DAO 실행을 계속한다. Timeout 취소 의도라면 interrupt 뒤 즉시 종료하거나 deadline 검사를 존중해야 늦은 DB 실행을 막을 수 있다. 현행 Worker가 실행 후 deadline을 재검사해 커밋 방지를 시도하지만 불필요한 DB 작업 자체는 일어날 수 있다.

예외 메시지에는 SQL, 개인정보, 내부 구조를 노출하지 않는다. 원인 체인은 서버 로그와 표준 코드로 추적하며 GUID를 연결한다.

## 17.14 Service가 담당하지 않는 영역

Service는 Service ID를 등록·분기하지 않는다. HTTP Request와 Response, CORS, JWT 파싱, GUID 생성, ImageLog, 공통 Timeout Executor도 담당하지 않는다. SQL 문자열과 DB 세부 매핑은 DAO·Mapper로 내린다.

ServiceContext를 사용할 수 있지만 Servlet API를 직접 참조하지 않는다. Transaction 시작 위치를 Service로 무조건 통일하지도 않는다. 일부 Service Annotation이 있더라도 TCF Timeout ON의 외부 Worker TX와 Facade 경계를 함께 읽어야 한다.

Rule을 잡다한 문자열 Helper나 Mapper 변환 유틸의 보관소로 만들지 않는다. 업무 언어로 설명할 수 없는 코드는 일반 변환 컴포넌트 또는 계층 내부 helper가 더 적합할 수 있다.

## End-to-End 사례: `mgcoa5530S0`

```text
Facade: Object → mgcoa5530S0DTOin
   → Service Aspect 선처리
   → mgcoa5530Service
      ├─ 현행 sleep 시험 코드
      ├─ trtBrc·basDt 정규화
      ├─ pageNo·pageSize·offset 계산
      ├─ DAO count
      ├─ DAO list
      ├─ row Map → Sub DTO
      └─ 페이지 출력 조립
   → 정상 Aspect 후처리
   → 최외곽 TX 완료
```

sleep 중 interrupt가 발생해도 현행 코드는 flag를 복원한 뒤 DAO로 진행한다. 이는 Timeout 장에서 다시 다룰 중요한 AS-IS 위험이다. 조회 결과 조립이 끝나도 Worker deadline이 지나면 Rollback과 Timeout 예외가 발생할 수 있다.

## 책임과 경계

| 계층 | 핵심 책임 | 입력 | 출력 | 금지 책임 |
|---|---|---|---|---|
| Facade | 입력 변환·유스케이스/TX 경계 | 일반 본문 | 거래 DTO | 상세 규칙·SQL |
| Service | 업무 순서·협력자 조정·결과 조립 | 입력 DTO | 출력 DTO | HTTP·Service ID 라우팅 |
| Rule | 재사용 검증·계산·판정 | 업무 값 | 판정·계산값 | DAO 순서·ThreadLocal |
| DAO | Mapper 호출과 데이터 접근 계약 | 조건 | 행·건수 | 업무 결과 조립 |
| Client | 외부 연계 계약 | 요청 모델 | 응답 모델 | 로컬 DB 원자성 가정 |

## 정상과 실패 비교

정상 조회는 조건과 페이지를 확정하고 count·list를 모두 얻은 뒤 DTO를 반환한다. 등록·수정·삭제는 기대 처리 건수를 판정하고 출력 계약을 만든다. 정상 반환 뒤 업무 후처리가 실행되고 최외곽 경계가 커밋한다.

입력 실패는 DAO 이전에 중단해야 한다. Rule 실패는 상태 변경 전에 업무 예외로 전파한다. DAO 실패는 부분 변경을 Rollback하도록 숨기지 않는다. 외부 Client 실패는 원격 처리 여부를 알 수 없는 경우가 있으므로 멱등 조회와 재처리 정책이 필요하다.

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | Service 패키지의 Spring `@Service`가 DTO→Map→DAO→DTO 흐름을 수행 |
| AS-IS | 별도 `application.rule` 구현은 확인되지 않음 |
| AS-IS | 주요 CRUD Service는 단일 DAO 사용, 일부 Service 자체 TX 선언 |
| AS-IS 위험 | `mgcoa5530Service`에 sleep·표준 출력 시험 코드와 interrupt 후 계속 실행 |
| 제약 | Map 기반 DAO 결과와 반복 변환으로 타입 안전성이 낮음 |
| TO-BE | 재사용 업무 정책을 Rule로 분리하고 순수 단위 테스트 |
| TO-BE | typed persistence result와 공통 페이지 모델 검토 |
| TO-BE | 외부 연계는 client/tcf-eai와 멱등·보상 정책 사용 |

## Anti Pattern

Service가 DAO를 한 줄 호출하고 Map을 그대로 반환하면 업무 계약과 결과 조립이 상위 계층으로 새어 나간다. 반대로 모든 규칙, SQL, HTTP 처리를 한 Service에 넣으면 거대한 클래스가 된다. 책임별 협력자로 분리하되 실행 순서는 Service에서 읽혀야 한다.

Rule을 static Util 모음으로 만들거나 Context·DAO에 직접 의존시키면 재사용 가능한 정책이라는 장점이 사라진다. 예외를 catch해 빈 DTO를 반환하면 Rollback과 표준 오류가 깨진다. 조회 경로에 sleep·System.out 같은 시험 코드를 남기면 Timeout과 운영 처리량이 왜곡된다.

## 실전 검증 시나리오

조회는 null·빈 조건, 최대 페이지, 0건, 여러 행, count/list 실패를 검증한다. 등록·수정·삭제는 필수키 누락, 처리 건수 0·1·복수, 중복과 DAO 예외의 Rollback을 확인한다. Map 키 대소문자와 null 컬럼도 DTO 변환 결과를 검증한다.

Rule을 분리하면 경계값과 조합을 DB 없이 테스트하고 Service에서는 호출 순서와 실패 전파를 검증한다. 여러 DAO는 두 번째 실패 시 첫 번째 변경이 롤백되는 통합 테스트가 필요하다. 외부 Client는 성공, 명시적 거절, 연결 Timeout, 결과 불명, 중복 재시도를 다룬다.

Timeout 시험에서는 `mgcoa5530S0`의 interrupt 뒤 DAO 진입 여부와 최종 Rollback을 관찰한다. 시험용 지연 제거 후에는 제어 가능한 Fake 또는 테스트 전용 Hook으로 바꾼다.

## 개발자 체크리스트

- Service 메서드에서 업무 실행 순서가 읽히는가?
- 입력 DTO 변환 성공과 업무 검증 성공을 구분했는가?
- 수정·삭제 식별자를 DAO 전에 검증하는가?
- 조회 pageNo·pageSize·상한과 0건 정책이 명확한가?
- 재사용 업무 계산을 Rule 후보로 검토했는가?
- Rule에 DAO·HTTP·ThreadLocal을 넣지 않았는가?
- 여러 DAO 실패가 의도한 Transaction에 참여하는가?
- 외부 호출에 timeout·멱등·재시도·보상 정책이 있는가?
- DAO Map 키와 DTO 필드 매핑 테스트가 있는가?
- 예외를 빈 성공 DTO로 바꾸지 않는가?
- Service에서 Servlet API와 Service ID 라우팅을 하지 않는가?
- 시험용 sleep과 표준 출력이 운영 경로에 남지 않았는가?

## 아키텍처 판단 포인트와 다음 장

Service와 Rule의 분리 기준은 코드 길이가 아니라 변경 이유다. 유스케이스 순서와 I/O 조정은 Service, 여러 유스케이스에서 반복되는 업무 판정과 계산은 Rule에 둔다. 작은 규칙을 무조건 클래스로 나누기보다 업무 언어, 재사용성과 독립 테스트 가치로 판단한다.

여러 DAO·Client를 어디서 조정할지는 원자성의 범위와 하위 흐름의 독립성으로 결정한다. 같은 업무 상태 변화는 Service, 여러 독립 유스케이스의 결합은 Facade가 자연스럽다. 외부 시스템은 로컬 TX가 되돌리지 못하므로 분산 실패를 별도로 설계한다.

Service는 DTO를 받아 DTO를 반환함으로써 계층 계약을 유지한다. 다음 장에서는 이 입력·출력 DTO, Sub DTO, 표준 전문과 Map 변환이 어떤 데이터 계약을 만들며 필드 변경 시 어느 범위를 함께 수정해야 하는지 구체적으로 다룬다.
