# 제4부 업무 진입과 유스케이스 경계

# 14장. Handler와 Controller

온라인 요청이 업무 로직에 들어가는 첫 지점은 실행 모드에 따라 달라진다. TCF ON에서는 공통 Controller와 Dispatcher가 Service ID로 `TransactionHandler`를 선택한다. TCF OFF에서는 Spring MVC가 업무 URL과 Controller Method를 직접 연결한다. 두 컴포넌트는 기술적으로 다르지만 외부 요청을 내부 유스케이스로 바꾸는 Inbound Adapter라는 공통 목적을 가진다.

Inbound Adapter의 품질은 코드 양이 아니라 경계의 명확성으로 판단한다. Handler는 이미 확정된 Service ID와 `dtoBody`를 받아 대응 Facade Method로 연결해야 한다. Controller는 HTTP URL과 요청 DTO를 받고 Web 수준의 입력 오류를 처리한 뒤 Facade로 위임해야 한다. 업무 계산, 여러 Service의 조정, DAO 호출과 Transaction 정책이 이 경계로 올라오면 ON/OFF가 서로 다른 업무를 갖게 된다.

현행 PDMG Handler 6개는 모두 대응 Facade만 생성자 주입하고 Service ID를 Facade Method로 분기한다. 반면 OFF Controller 6개 중 `mgcoa9100Controller`만 Facade를 호출하며 나머지 5개는 Service를 직접 호출한다. `mgcoa9999Controller`에는 업무 개별 선후처리를 Controller에 작성하도록 보이는 주석까지 있다. 이 장은 이 상태를 표준으로 복제하지 않고 AS-IS 기술부채와 목표 Adapter 구조를 구분한다.

## 이 장에서 해결할 질문

- Handler와 Controller를 왜 Inbound Adapter라고 부르는가?
- `serviceIds()`는 언제 누가 읽고 어떤 Registry Key가 되는가?
- `handle()`은 무엇을 분기하고 어디까지 처리해야 하는가?
- 등록 목록과 switch Case가 달라지면 어떤 단계에서 실패하는가?
- OFF Controller의 URL과 typed DTO Binding은 Handler 경로와 무엇이 다른가?
- 입력 검증은 Controller, Facade와 Service 중 어디에 둬야 하는가?
- Controller가 Service를 직접 호출하면 어떤 유스케이스·Transaction 경계를 우회하는가?
- Handler나 Controller에 `@Transactional`을 붙이면 실행 범위와 유지보수성이 어떻게 달라지는가?
- ON/OFF 진입점이 달라도 Facade 아래 업무 구조를 어떻게 하나로 유지하는가?

## 두 Inbound Adapter의 전체 위치

```text
TCF ON
HTTP → OnlineController → Dispatcher Registry
  → TransactionHandler.handle(dtoBody, context)
  → Business Facade → Service → DAO

TCF OFF
HTTP → Business Controller.method(typed DTO)
  → Business Facade                        권장
  → Service → DAO
```

Handler는 HTTP Request를 직접 받지 않고 Dispatcher가 전달한 Object와 TransactionContext를 받는다. Controller는 Spring MVC Annotation과 Request Binding에 직접 의존한다. 이 차이 때문에 같은 클래스로 합치는 것이 아니라, 두 Adapter가 같은 Facade Port를 호출하도록 정렬해야 한다.

## 14.1 Inbound Adapter의 역할

Inbound Adapter는 외부 호출 규약을 애플리케이션 유스케이스 호출로 변환하는 경계다. HTTP URL, TCF Service ID, JSON DTO처럼 외부에서 보이는 표현을 내부 Facade Method와 연결한다. Adapter는 어떤 유스케이스를 실행할지 결정하지만 유스케이스 자체를 구현하지 않는다.

TCF Handler는 Service ID Protocol에 종속된다. Dispatcher가 선택한 프로그램 단위 Handler가 `context.getServiceId()`로 S0/C0/U0/D0 거래를 구분한다. OFF Controller는 HTTP Method, URL과 typed `@RequestBody`에 종속된다. 두 Adapter의 입력 형태는 달라도 출력은 Business Facade 호출과 그 반환값이어야 한다.

```text
외부 표현                   내부 경계
Service ID + Object  ─┐
                      ├→ Business Facade → Use Case
URL + typed DTO      ─┘
```

Adapter가 얇아야 하는 이유는 교체 가능성이다. TCF ON/OFF, REST, Batch 또는 Message Consumer가 추가돼도 Facade 아래 업무를 재사용할 수 있다. Handler에 DAO를 넣으면 OFF Controller에서 복제해야 하고, Controller에 여러 Service 조정을 넣으면 TCF Handler 경로가 다른 결과를 낸다.

얇다는 것은 검증이 없다는 뜻이 아니다. Adapter는 자신이 소유한 Protocol 검증을 책임진다. Handler는 지원 Service ID와 Context 정합성을 확인하고, Controller는 JSON Binding, 필수 HTTP 입력과 형식 Validation을 수행할 수 있다. 고객 상태, 등록 가능 여부와 같은 업무 Rule은 Service/Rule 계층으로 내려간다.

## 14.2 TransactionHandler

공통 계약 `TransactionHandler`는 단일 거래용 `serviceId()`, 등록 목록을 반환하는 `serviceIds()`와 실행 Method `handle(Object, TransactionContext)`를 제공한다. 업무 Handler는 `@Component`이면서 `nhnis.fw.tcf.enabled=true` 조건을 사용하므로 TCF ON에서만 Registry 후보가 된다.

```java
public interface TransactionHandler {
    default String serviceId() { return null; }
    default Collection<String> serviceIds() { ... }
    Object handle(Object dtoBody, TransactionContext context)
            throws Exception;
}
```

`dtoBody`는 전체 표준 전문이 아니라 공통 Controller가 추출한 `dto` Node다. Header와 GUID는 TransactionContext가 참조하는 ServiceContext를 통해 접근할 수 있다. Handler가 Servlet Request나 원문 JSON을 다시 파싱하면 TCF Web 경계와 업무 Entry가 뒤섞인다.

현행 Handler는 프로그램 식별번호 단위다. `mgcoa9000S0`, C0, U0와 D0는 `mgcoa9000Handler` 하나에 들어간다. 거래마다 Handler Class를 만들지 않아 프로그램별 Facade와 분기 관계가 한 파일에 모인다.

| Handler | 등록 거래 |
|---|---|
| mgcoa5530Handler | S0 |
| mgcoa8888Handler | S0, D0 |
| mgcoa9000Handler | S0, C0, U0, D0 |
| mgcoa9001Handler | S0, C0, U0, D0 |
| mgcoa9100Handler | S0 |
| mgcoa9999Handler | S0 |

모든 현행 Handler는 대응 Business Facade 하나만 주입한다. DAO, Mapper와 Service 직접 의존이 없다는 점은 목표 Architecture와 일치한다.

## 14.3 `serviceIds()` 등록

`serviceIds()`는 이 Handler가 처리할 수 있다고 선언하는 Service ID Catalog다. Spring이 Dispatcher를 만들 때 모든 TransactionHandler Bean을 주입하고 이 목록을 순회해 `Map<String,TransactionHandler>`를 구성한다. 따라서 요청 시 등록하는 것이 아니라 애플리케이션 기동 시 실행 계약을 확정한다.

```text
Handler Bean 생성
  → serviceIds() 반환
  → Dispatcher handlerMap.put(serviceId, handler)
      ├─ 최초 ID: 등록
      ├─ 빈 목록: Warning 후 Skip
      └─ 중복 ID: IllegalStateException, 기동 실패
```

중복을 기동 실패로 처리하는 것은 안전장치다. 두 Handler가 같은 ID를 주장하는 상태에서 마지막 등록이 이기도록 두면 배포 순서에 따라 다른 업무가 실행될 수 있다. 운영자는 실패를 우회하지 말고 Service Catalog에서 올바른 소유 Handler를 확정해야 한다.

등록 문자열은 URL, Header `rms_svc_c`, UI Transaction Catalog와 Facade Method 의미까지 연결된다. 대소문자, 숫자와 처리구분이 한 글자라도 다르면 다른 Key다. 문자열 상수를 사용해 `serviceIds()`와 `handle()` Case에서 같은 값을 재사용하는 현재 방식은 오타를 줄인다.

그러나 목록과 분기는 여전히 이중 관리된다. `serviceIds()`에 A0를 추가하고 switch를 누락하면 등록은 성공하지만 실행 시 Handler Default 오류가 난다. switch만 추가하고 목록을 누락하면 Dispatcher에서 미등록 오류가 발생해 switch까지 오지 못한다. Parameterized Test로 모든 등록 ID가 실제 분기되는지 확인한다.

## 14.4 `handle()` 거래 분기

`handle()`은 Dispatcher가 선택한 프로그램 Handler 안에서 구체 거래를 Facade Method로 연결한다. 다중 거래 Handler는 `context.getServiceId()` switch를 사용하고 단일 거래 Handler는 equals 검사 후 Facade를 호출한다.

```java
return switch (context.getServiceId()) {
    case S0 -> facade.mgcoa9000S0(dtoBody);
    case C0 -> facade.mgcoa9000C0(dtoBody);
    case U0 -> facade.mgcoa9000U0(dtoBody);
    case D0 -> facade.mgcoa9000D0(dtoBody);
    default -> throw new ServiceHandlerNotFound(...);
};
```

Facade가 반환한 DTOout을 그대로 Dispatcher로 돌려주고 예외도 임의로 삼키지 않는다. 응답 Envelope는 ResponseBodyAdvice, 업무 Transaction은 Facade 또는 Worker 경계의 책임이다. Handler에서 Object를 typed DTO로 변환하지 않는 현행 구조에서는 Facade가 변환 책임을 가진다.

Dispatcher는 Method Parameter `serviceId`로 Handler를 찾고 Handler는 TransactionContext의 ID로 다시 분기한다. 정상 TcfFacade는 같은 값으로 둘을 만들지만 Dispatcher API만 보면 서로 다르게 전달할 수 있다. 불일치하면 Dispatcher는 조회 Handler를 선택하고 Handler는 삭제 Method를 실행하는 식의 위험이 있다. Dispatcher 또는 Handler에서 두 ID의 일치 검증을 추가하는 TO-BE를 검토할 수 있다.

Handler 실패는 Facade 호출 전과 후로 나뉜다. 등록·분기 불일치는 업무 DML 전 실패할 가능성이 높다. Facade 호출 뒤 발생한 업무 예외는 Handler가 원인을 보존해 밖으로 전달해야 Worker/Facade Transaction이 Rollback을 판단할 수 있다.

## 14.5 Handler Registry

Handler Registry의 소유자는 `TransactionDispatcher`다. Handler가 스스로 전역 Map을 수정하지 않고 Spring이 수집한 Bean 목록으로 Dispatcher 생성자가 Map을 만든다. 이 구조는 Registry 변경 시점을 기동으로 제한하고 Runtime 안정성을 높인다.

```text
Controller selected serviceId
  → TcfFacade
  → Dispatcher.handlerMap[serviceId]
      → Handler.handle(dto, context)
```

Registry 오류를 장애 위치별로 구분한다. Handler Bean 조건이나 Component Scan 문제는 기동 등록 로그 부재로 보인다. 빈 목록은 Warning과 미등록 요청으로 이어진다. 중복은 기동을 막는다. 존재하지 않는 ID 요청은 `ServiceHandlerNotFound`다. Registry 선택 후 Default 오류는 목록과 분기 불일치다.

운영 진단은 UI URL만 보지 않고 Controller가 최종 결정한 Service ID, 기동 등록 Key와 Handler Class를 비교한다. Header가 Path보다 우선할 수 있으므로 실제 선택 ID를 로그에서 확인한다. Registry Map의 진단 노출은 인증된 관리 기능으로 제한하고 내부 Class 정보를 외부 일반 사용자에게 노출하지 않는다.

신규 거래 완료 조건에는 기동 Test가 포함돼야 한다. 정상 등록, 중복 실패, 등록 ID별 Handle 성공과 미지원 ID 예외를 검증한다. 단위 Test에서 Dispatcher를 직접 만들면 실제 Spring 조건부 Bean과 Component Scan도 별도 Context Test로 확인한다.

## 14.6 업무 Controller

업무 Controller는 TCF OFF의 HTTP Inbound Adapter다. `@RestController`, Service ID별 `@PostMapping`과 `@ConditionalOnProperty(...havingValue="false", matchIfMissing=true)`를 사용한다. Spring MVC가 요청 Body를 거래별 DTOin으로 Binding한다.

```text
POST /mgcoa9000C0
  → mgcoa9000Controller.mgcoa9000C0(DTOin)
  → Business Facade                           권장
```

AS-IS는 Controller마다 다르다. `mgcoa9100Controller`는 생성자 주입으로 Facade를 호출하지만 나머지 다섯 Controller는 `@Autowired` Service를 직접 호출한다. 일부 Controller는 업무 Start/End 로그와 `output.toString()`을 남긴다. DTO 전체 로그에는 개인정보가 포함될 수 있으므로 공통 Masking 정책 없이 출력하지 않는다.

`mgcoa9999Controller`에는 “업무 개별 선처리/후처리 작성” 주석이 있다. 이 위치에 DB 변경이나 업무 조정을 추가하면 ON Handler 경로에는 적용되지 않고 Controller Transaction 여부에 따라 원자성도 달라진다. 개별 업무 선후처리는 Facade/Service/Rule의 명시적 유스케이스로 옮기고 공통 업무 Aspect와 책임을 구분한다.

Controller는 HTTP Status, Binding/Validation과 Facade 호출을 담당한다. Service ID Registry나 TransactionContext를 흉내 내지 않는다. OFF에서도 표준 Filter와 Response Advice가 켜져 있다면 Header/Envelope를 Controller가 중복 조립하지 않는다.

## 14.7 TCF ON/OFF 진입점 비교

| 비교 축 | TCF ON Handler | TCF OFF Controller |
|---|---|---|
| 선택 기준 | Dispatcher Registry의 Service ID | Spring MVC URL Mapping |
| 입력 | Object dtoBody + TransactionContext | typed DTOin + HTTP Binding |
| 활성 조건 | tcf.enabled=true | false/missing |
| Caller | TransactionDispatcher | DispatcherServlet |
| 권장 Callee | Business Facade | Business Facade |
| HTTP 의존 | 없음 | 있음 |
| Registry | 있음 | 없음 |
| Timeout | TcfFacade 경로 | TCF Executor 우회 |

두 Adapter를 같은 Class로 통합하면 Handler에 MVC Annotation이 들어가거나 Controller가 TransactionContext와 Registry를 알아야 한다. 대신 공통 Facade Interface를 기준으로 각각 얇게 유지한다. 모드 분기는 Bean Configuration과 Entry에서 끝나야 하며 Service 아래까지 전파하지 않는다.

동등성 Test는 같은 업무 입력이 두 Adapter를 통해 같은 Facade Method와 DB 결과로 이어지는지 확인한다. 내부 Input Type이 Object와 DTO로 달라도 Facade 경계에서 같은 typed 유스케이스로 변환돼야 한다. Timeout과 오류 Handler 같은 Infrastructure 차이는 별도 계약으로 비교한다.

## 14.8 Controller 입력 검증

Controller 검증은 JSON 형식, 필수 Field, 길이와 단순 범위처럼 요청 계약 자체에 가까운 항목에 적합하다. Bean Validation Annotation과 `@Valid`를 사용할 수 있지만 현행 Controller에 표준적으로 적용됐는지는 소스별 확인이 필요하다. `nhnis.fw.commons.resolver.RequestBody`라는 Custom Annotation을 사용하므로 일반 Spring `@RequestBody`와 같은 동작이라고 추정하지 않고 Resolver를 검증해야 한다.

```text
Controller/Web 검증
  JSON Binding, null/형식, 길이, 허용 Enum

Service/Rule 업무 검증
  고객 상태, 중복 등록, 한도, 권한, DB 현재값
```

같은 유스케이스를 TCF ON Handler도 호출하므로 업무 검증을 Controller에만 두면 ON에서 우회된다. 반대로 모든 형식 오류를 Service에서 늦게 검사하면 불필요한 Transaction과 DB 접근이 생긴다. 외부 계약 검증은 각 Adapter에서 동일 규칙을 공유하거나 Facade 입력 Port 앞 공통 Validator로 구성하고, 업무 Rule은 Service에 둔다.

Validation 실패의 HTTP Status와 표준 오류 Body도 ON/OFF에서 비교한다. OFF의 MVC Binding 예외와 ON의 ObjectMapper 변환 예외가 다른 단계에서 발생할 수 있다. UI가 같은 오류 Code를 필요로 한다면 공통 예외 Translation을 정의한다.

입력 로그에는 Token, 개인정보와 전체 DTO를 그대로 남기지 않는다. 검증 오류는 Service ID, GUID, Field 이름과 허용 가능한 사유만 기록하고 실제 값은 Masking한다.

## 14.9 Controller와 Facade 관계

Controller와 Handler가 공유해야 할 다음 경계가 Business Facade다. Facade는 Object/DTO 변환, 유스케이스 조정과 Transaction을 소유하며 Service를 호출한다. 이 장에서는 Facade 내부 구현보다 Adapter가 왜 Facade를 호출해야 하는지에 집중한다.

```text
Handler ─────┐
             ├→ Facade → Service → DAO
Controller ──┘
```

Facade를 공유하면 ON/OFF의 Transaction과 업무 조정이 일치한다. Controller는 typed DTO를 넘기고 Handler는 Object dtoBody를 넘길 수 있지만 Facade가 이를 동일 DTOin으로 정규화한다. Facade Method Signature가 Object인 현재 구현은 유연하지만 Compile-time Type 안전성이 낮으므로 변환 실패 Test가 필요하다.

Controller에서 Facade로 전환할 때는 HTTP 계약을 바꾸지 않고 주입 대상과 호출 Method를 교체한다. 동일 입력의 Service 호출 횟수, 출력 DTO, DB 상태와 오류를 비교한다. Facade가 Servlet Request를 요구하게 만들면 Handler 재사용이 깨지므로 인증 사용자나 Header 값은 명시적 Context/Value Object로 전달한다.

다음 장에서는 Facade의 DTO 변환, 유스케이스 조정과 Transaction 경계를 더 깊게 다룬다.

## 14.10 Controller에서 Service 직접 호출 문제

Service 직접 호출은 코드 한 줄이 짧지만 Architecture 비용이 크다. Facade의 DTO 정규화, 여러 Service 조정과 Transaction을 우회한다. ON Handler는 Facade를 호출하므로 같은 Service ID가 모드에 따라 다른 경로를 갖는다.

```text
ON  Handler → Facade(TX) → Service
OFF Controller ─────────→ Service       AS-IS 다수
```

현행 `mgcoa9001Service`처럼 Service 자체에 Transaction이 있으면 OFF에도 Service 범위 Transaction은 생길 수 있다. 다른 Service에 Transaction이 없으면 여러 DAO 호출이 원자적으로 묶이지 않을 수 있다. 이는 직접 호출을 정당화하는 것이 아니라 모드별 경계가 불일치한다는 증거다.

Service 직접 호출 Controller를 Facade로 바꿀 때 Service Method를 중복 호출하지 않도록 주의한다. 기존 Controller 전후 처리도 Facade/Service 책임에 맞게 재배치한다. 쓰기 거래는 두 번째 SQL 실패 시 첫 SQL까지 Rollback되는지 실제 DB로 검증한다.

Batch나 Message Consumer도 같은 Facade를 호출할 수 있어야 한다. Service에 HTTP 입력 보완이나 Controller 전용 분기를 넣으면 재사용성이 떨어진다. Adapter는 Protocol, Facade는 Use Case, Service는 Business 흐름이라는 방향을 유지한다.

## 14.11 Controller에 트랜잭션을 선언할 때의 영향

Spring은 Controller Bean도 Proxy로 만들 수 있으므로 Method에 `@Transactional`을 선언하는 것이 기술적으로 가능하다. Controller 진입 직전에 Transaction이 시작되고 Service, DAO와 Controller 반환까지 포함된다.

```text
Interceptor.preHandle                    TX 밖
Controller Proxy: TX BEGIN
  Controller 입력 처리
  Service/Facade
  응답 DTO 생성
Controller return: COMMIT/ROLLBACK
ResponseBodyAdvice / afterCompletion      TX 밖
```

이 방식은 업무 선후처리를 같은 Transaction에 포함할 수 있지만 HTTP Adapter가 Transaction 정책을 소유하고 Connection 점유 범위를 넓힌다. Controller가 여러 Service를 직접 조정하게 되는 유혹도 커진다. ON Handler는 같은 Controller Transaction을 사용할 수 없어 모드 공통화가 깨진다.

Service에 Transaction을 붙이는 방식은 Controller보다 좁지만 여러 Service를 조정하는 전체 유스케이스를 묶지 못할 수 있다. Facade Transaction은 두 Entry Adapter가 공유하며 업무 원자성 경계를 명확히 표현한다. 그러므로 Controller Transaction은 표준이 아니라 호환·비상 상황의 검토안으로 취급한다.

Annotation을 옮기기 전에 Advisor Order, checked Exception rollback, TransactionManager와 Self-invocation을 검증한다. Controller가 예외를 잡아 정상 응답으로 반환하면 Rollback이 되지 않을 수 있다. Response Advice와 ImageLog는 Controller 반환 뒤라 Controller Transaction에 자동 포함되지 않는다.

## 14.12 Handler·Controller에서 금지하는 처리

Handler와 Controller에는 DAO, Mapper와 SQL을 직접 넣지 않는다. 업무 상태 검증, 금액 계산, 여러 Entity 변경과 재시도 정책도 Facade/Service/Rule 책임이다. Transaction Annotation을 Adapter 표준으로 두지 않으며 응답 Envelope와 ImageLog를 중복 구현하지 않는다.

```text
금지
Handler/Controller
  → DAO.insert
  → 여러 Service 업무 조정
  → 업무 Rule 계산
  → @Transactional 유스케이스 소유
  → Header/응답 봉투 수동 조립

권장
Handler/Controller
  → 입력 선택·검증
  → Facade Method 1회 호출
  → 결과/예외 전달
```

Adapter에서 예외를 무조건 catch해 Error DTO를 직접 만드는 것도 피한다. 원 예외를 보존해 Transaction 경계가 Rollback을 판단하게 하고 Web Advice에서 표준 오류로 변환한다. 복구 가능한 Protocol 오류만 명확한 Code로 변환한다.

Controller와 Handler 로그는 시작·종료, GUID와 Service ID처럼 추적에 필요한 Metadata에 제한한다. DTO `toString()` 전체 출력은 개인정보와 대용량 응답 위험이 있다. 업무 상세 로그는 Masking된 구조화 로그와 ImageLog 정책을 따른다.

## `mgcoa9000C0` 한 건으로 보는 두 Adapter

등록 거래 `mgcoa9000C0`이 TCF ON으로 들어오면 공통 Controller가 Header와 Path에서 Service ID를 결정하고 `dto` Node를 추출한다. Dispatcher는 Registry Key로 `mgcoa9000Handler`를 선택한다. Handler는 Context ID의 C0 Case를 선택해 `mgcoa9000Facade.mgcoa9000C0(dtoBody)`를 호출한다. Facade는 Object를 C0 DTOin으로 정규화하고 Transaction 안에서 Service를 호출한다.

```text
TCF ON
POST /mgcoa9000C0
  → OnlineTransactionController
  → Dispatcher[mgcoa9000C0]
  → mgcoa9000Handler
      case C0
  → mgcoa9000Facade.mgcoa9000C0(Object)
  → mgcoa9000Service.mgcoa9000C0(DTOin)
```

TCF OFF에서는 Spring MVC가 `/mgcoa9000C0`을 `mgcoa9000Controller.mgcoa9000C0()`에 연결하고 Custom RequestBody Resolver가 typed DTOin을 준비한다. AS-IS Controller는 Facade가 아니라 `mgcoa9000Service.mgcoa9000C0(input)`을 직접 호출한다. Service에는 자체 Transaction Annotation이 확인되지 않아 ON Facade의 쓰기 Transaction을 우회할 수 있다.

```text
TCF OFF AS-IS
POST /mgcoa9000C0
  → mgcoa9000Controller.mgcoa9000C0(DTOin)
  → mgcoa9000Service.mgcoa9000C0(DTOin)
  → Facade Transaction 우회
```

이 두 흐름의 업무 Method 이름이 같아 보여도 실행 계약은 같지 않다. ON은 Registry 등록과 Handler switch, Facade 변환과 Transaction을 통과한다. OFF는 MVC Binding을 얻지만 Registry와 Facade를 우회한다. 목표 구조는 OFF Controller가 동일 Facade를 호출하도록 바꿔 차이를 HTTP Binding과 TCF Routing으로 제한하는 것이다.

```text
TCF OFF TO-BE
POST /mgcoa9000C0
  → mgcoa9000Controller(DTOin)
  → mgcoa9000Facade.mgcoa9000C0(input)
  → 동일 Service와 Transaction
```

이 사례를 Test할 때 정상 등록만 보면 경계 차이를 발견하기 어렵다. Service가 첫 INSERT 후 두 번째 INSERT에서 checked Exception을 던지게 하고 ON/OFF의 DB 최종 상태를 비교한다. ON은 Facade 또는 Worker Transaction으로 모두 Rollback되어야 한다. OFF AS-IS에서 첫 INSERT가 남으면 Adapter가 Facade를 우회한 영향이 증명된다.

## 등록 목록과 실행 분기의 정합성 보장

Handler는 같은 Service ID를 상수, `serviceIds()` 반환 목록과 switch Case에서 사용한다. 상수를 재사용해 철자 오류는 줄지만 목록에 추가하는 작업과 Case를 추가하는 작업은 여전히 별도다. 리뷰어가 눈으로만 비교하면 신규 거래가 많을수록 누락 가능성이 커진다.

가장 직접적인 Test는 Handler의 모든 등록 ID를 순회해 `handle()`을 호출하고 대응 Facade Method가 정확히 한 번 호출되는지 검증하는 것이다. Facade를 Mock으로 두고 거래별 최소 dtoBody와 TransactionContext를 제공한다. 반환값이 그대로 전달되고 다른 Facade Method가 호출되지 않는지도 확인한다.

```text
for each handler.serviceIds()
  context.serviceId = id
  handler.handle(dto, context)
  assert expected facade method called once
  assert no unexpected facade method
```

반대 방향도 검사해야 한다. Handler가 문서상 지원해야 하는 Service Catalog ID 전체가 `serviceIds()`에 있는지 확인한다. switch Case를 Reflection으로 읽는 방식은 Java 문법에 의존하므로 권장하지 않는다. 업무별 기대 목록을 Test Data로 두고 등록 목록과 Set 비교를 수행한 뒤 각 ID를 실행한다.

미지원 ID Test에서는 `ServiceHandlerNotFound`와 Message에 안전한 Service ID만 포함되는지 확인한다. null TransactionContext, null Service ID와 Dispatcher Argument/Context ID 불일치도 방어 계약을 정해야 한다. 현재 Handler는 Context null이면 NPE가 날 수 있고 불일치 검증이 없으므로 Test는 현행 동작을 기록한 뒤 TO-BE 정책을 별도로 정의한다.

기동 Context Test는 두 Handler가 같은 ID를 등록했을 때 `IllegalStateException`으로 실패하는지 검증한다. 단위 Test의 Map 등록 성공만으로는 `@ConditionalOnProperty`와 Component Scan을 확인할 수 없으므로 TCF ON/OFF ApplicationContext Test도 필요하다.

## Adapter 입력 검증을 계층화하는 방법

입력 검증은 “Controller에서 한다” 또는 “Service에서 한다” 중 하나로 끝나지 않는다. 검증의 근거가 Protocol인지 Business 상태인지에 따라 위치가 달라진다. JSON을 숫자로 변환할 수 있는지, 문자열 길이가 계약을 넘는지와 필수 Field가 빠졌는지는 Adapter 또는 공통 입력 Validator가 빠르게 거절할 수 있다. 고객이 거래 가능한 상태인지, 동일 Key가 DB에 존재하는지와 한도를 넘는지는 Service/Rule이 판단한다.

| 검증 유형 | Handler/Controller | Facade | Service/Rule |
|---|---|---|---|
| JSON 형식·Binding | Controller/MVC | ON Object 변환 보완 | 아님 |
| 필수·길이·Enum | 공통 Contract 검증 | 공통 정규화 가능 | 방어 검증 가능 |
| Service ID 지원 | Handler/Registry | 아님 | 아님 |
| DTO 변환 | 현행 Handler는 안 함 | 현행 Facade | 아님 |
| 고객 상태·중복 | 아님 | 유스케이스 조정 | 주 책임 |
| DB 현재값 기반 Rule | 아님 | 아님 | Service/Rule |

TCF ON Handler가 Object dtoBody를 그대로 넘기기 때문에 OFF Controller의 Bean Validation만 적용하면 모드별 검증이 달라진다. 공통 DTO Constraint를 Facade 변환 뒤 Validator로 실행하거나 두 Adapter가 같은 Validation Service를 호출하는 설계를 고려할 수 있다. 다만 Validator가 DB를 조회하며 업무 판단까지 수행하면 다시 Layer가 흐려진다.

Validation 실패를 표준 오류로 변환하는 위치도 중요하다. OFF MVC Binding은 Controller Method 진입 전 발생할 수 있고 ON ObjectMapper 변환은 Facade Transaction 안에서 발생할 수 있다. 같은 잘못된 Field가 한 모드에서는 400, 다른 모드에서는 500이 되지 않도록 Exception Translation과 오류 Code를 통합 Test한다.

오류 로그에는 Field 이름과 오류 Rule을 남기되 실제 주민번호, 계좌번호나 Token 값을 출력하지 않는다. DTO 전체 `toString()`은 검증 실패 진단에 편리해 보여도 민감정보를 대량 복제한다. GUID와 Service ID로 접근통제된 ImageLog를 찾는 방식을 우선한다.

## Controller에서 Facade로 전환하는 실무 절차

Service 직접 호출 Controller를 Facade 호출로 바꾸는 작업은 주입 Type만 교체하는 것처럼 보이지만 입력 Type, 예외 Signature, Transaction과 응답이 모두 영향을 받는다. 한 거래씩 작은 단위로 전환하고 ON/OFF 동등성 Test를 통과시켜야 한다.

첫 단계는 Controller Method, Service Method와 ON Handler의 Facade Method를 연결하는 표를 만드는 것이다. Facade가 Object를 받아 `ObjectMapper.convertValue()`를 사용한다면 이미 typed DTOin을 넘겨도 Field가 유지되는지 확인한다. Custom DataObject, 날짜와 중첩 List는 단순 Map과 다른 변환 결과를 낼 수 있다.

두 번째는 Controller의 개별 코드 이동이다. 단순 시작·종료 로그는 공통 Logging 정책으로 통합하고, 업무 개별 선후처리는 Facade/Service/Rule 중 목적에 맞는 위치로 옮긴다. HTTP Header 보완은 Controller나 Framework에 남긴다. 이 과정에서 같은 업무를 Controller와 Facade 양쪽에서 두 번 실행하지 않는다.

세 번째는 Transaction Test다. 조회는 readOnly, 쓰기는 `rdwTransactionManager`, checked Exception rollback을 검증한다. Controller Test Method 자체의 Transaction이 결과를 가리지 않도록 실제 HTTP 호출 뒤 새 Connection으로 DB 상태를 확인한다. 업무 Aspect가 Facade Transaction 안에서 실행되는지도 관찰한다.

네 번째는 공개 계약 비교다. URL, Request Body, HTTP Status와 Response Envelope를 변경하지 않는다. ON과 OFF에서 같은 업무 오류 Code가 나오는지 비교한다. Facade 변환 Exception이 새로 발생하면 내부 Stack Trace가 Client에 노출되지 않게 표준화한다.

마지막으로 Service 직접 호출을 Architecture Test로 금지할 수 있다. `application.controller` Package가 `application.service`를 의존하지 않고 `application.facade`만 의존한다는 규칙을 정적 분석으로 검사하면 신규 회귀를 막을 수 있다. 기존 예외가 남는 동안에는 허용 목록과 제거 기한을 관리한다.

## Handler와 Controller의 Transaction 참여를 정확히 읽기

Handler에 `@Transactional`이 없어도 Timeout ON에서는 Worker의 TransactionTemplate 안에서 실행될 수 있다. 이 경우 Handler 분기 자체도 Transaction Context 안에 있지만 DB를 호출하지 않으므로 Connection을 사용할 이유는 없다. Timeout OFF에서는 Handler가 Facade를 호출하기 전까지 Transaction 밖이고 Facade Proxy에서 시작한다.

```text
ON + timeout ON
Worker TX BEGIN
  Dispatcher → Handler → Facade REQUIRED → Service
COMMIT/ROLLBACK

ON + timeout OFF
Dispatcher → Handler
  → Facade TX BEGIN → Service → COMMIT/ROLLBACK
```

Controller에 Transaction을 붙이면 OFF Request Thread에서 Controller Method 전체가 Transaction이 된다. 입력 보완, 업무 호출과 DTO 생성이 같은 경계에 들어가지만 ResponseBodyAdvice와 afterCompletion은 반환 뒤라 제외된다. 긴 JSON 처리나 불필요한 Controller 작업 동안 Connection을 점유할 수 있다.

Handler Transaction은 더 큰 문제가 있다. 같은 프로그램의 조회와 쓰기 Case가 한 Method에 있으므로 Annotation 하나로 readOnly와 Write 속성을 구분하기 어렵다. Handler가 선택되기 전 Registry 오류와 시스템 정책의 경계도 불분명해진다. 거래별 Facade Method가 readOnly와 rollback 규칙을 소유하는 현재 구조가 더 세밀하다.

Transaction을 Adapter에 두면 다른 Adapter가 같은 정책을 재현해야 한다. Controller와 Handler에 같은 Annotation을 복제해도 Timeout ON Worker 외곽 Transaction 때문에 실제 속성이 다를 수 있다. Facade를 공통 경계로 두고 외곽 Worker Transaction과의 참여 관계를 명시하는 편이 일관적이다.

예외를 Adapter가 catch할 때는 Rollback 시점도 확인한다. Facade가 예외를 던져 이미 Proxy가 Rollback을 결정한 뒤 Controller가 오류 DTO로 바꾸는 경우와, Handler가 Facade 내부 예외를 잡아 정상 반환하게 만드는 경우는 결과가 다를 수 있다. 원인을 숨기지 않고 공통 Advice로 전달하는 것을 기본으로 한다.

## 신규 프로그램과 신규 거래 추가 절차

같은 프로그램 식별번호에 거래를 추가하면 기존 Handler에 상수, 등록 목록과 switch Case를 추가한다. Facade Method와 DTO, Service, DAO/Mapper, UI Catalog와 샘플 요청도 같은 변경 단위다. OFF를 지원하면 Controller Mapping과 Method도 추가한다.

```text
신규 mgcoa9000A0
  Handler: A0 상수 + serviceIds + switch
  Facade: mgcoa9000A0
  Service/Rule/DAO/Mapper
  DTOin/DTOout
  OFF Controller Mapping
  UI Transaction Catalog
  Contract/Transaction Test
```

새 프로그램 식별번호라면 새 Handler와 Facade 계열을 만든다. `mgcoa9000S0Handler`처럼 거래마다 Handler를 나누지 않는다. 프로그램 단위 Handler가 너무 커질 정도로 거래가 늘면 프로그램 분류 자체가 적절한지 먼저 검토한다.

추가 후 기동 로그에서 Registry 등록을 확인하고 모든 ID를 호출한다. ON만 성공하고 OFF Mapping이 없거나, OFF만 성공하고 Handler 목록이 빠지는 비대칭을 Build Gate에서 찾는다. Service Catalog를 단일 Source로 삼아 Handler와 Controller 계약 Test를 생성하는 TO-BE도 고려할 수 있다.

변경 검토자는 Adapter 코드만 보지 않는다. Facade가 실제 Transaction을 갖는지, Service 직접 호출이 새로 생기지 않았는지, DTO 변환과 오류 응답이 양 모드에서 호환되는지 확인한다. 신규 거래 완료는 URL 200 한 번으로 판정하지 않는다.

## Adapter 보안과 로그

Handler는 HTTP Authorization Header를 직접 받지 않으므로 인증이 완료됐다고 무조건 가정해서는 안 된다. Filter와 Context 경계가 비활성인 Test나 내부 호출에서는 사용자정보가 없을 수 있다. 권한이 필수인 유스케이스는 인증된 Principal을 명시적으로 전달하고 Facade/Service에서 필요한 인가를 검증한다.

Controller는 `X-Forwarded-For`, Header 사용자와 Body Field를 Client가 보낸 값으로 볼 수 있다. 신뢰 Proxy와 JWT Subject로 검증하지 않은 값을 권한 판단에 사용하지 않는다. Web 입력을 파일 경로, URL, SQL 동적 문자열로 전달하기 전 Allowlist와 Binding을 적용한다.

Handler/Controller 시작 로그에는 GUID, Service ID, Adapter 이름과 결과 상태가 충분하다. 입력 DTO와 출력 DTO 전체를 문자열 결합으로 남기면 Log Level 평가 전에 `toString()`이 실행되고 개인정보가 노출된다. Parameterized Logging과 Masking된 Summary를 사용한다.

예외 Message에 dtoBody 전체를 포함하지 않는다. 미지원 Service ID는 허용 가능한 ID 문자열만 기록하고 내부 Class와 Stack Trace는 Client 응답에서 제거한다. 운영자는 GUID로 상세 로그와 ImageLog를 조회한다.

```text
TCF ON
Service ID
  → Dispatcher Registry
  → Program Handler
      serviceIds() 등록 계약
      handle() 거래 분기
  → Business Facade

TCF OFF
HTTP URL
  → Business Controller
      typed DTO Binding/Validation
  → Business Facade                  목표

공통 이후
Facade → Service → Rule/DAO → Mapper → DB
```

## 책임과 경계 표

| 구성요소 | Caller | 책임 | Callee | 금지 책임 |
|---|---|---|---|---|
| Dispatcher | TcfFacade | Registry Lookup | Handler | 업무 분기 |
| Handler | Dispatcher | Service ID→Facade 분기 | Facade | DTO 변환·Service/DAO |
| Controller | Spring MVC | URL·Binding·Web 검증 | Facade | 업무 조정·SQL |
| Facade | Handler/Controller | 입력 정규화·Use Case·TX | Service | HTTP Mapping |
| Service | Facade | 업무 흐름·Rule·DAO | DAO/Rule | 모드 분기 |

## 정상·실패 비교

| 시나리오 | Handler 경로 | Controller 경로 |
|---|---|---|
| 정상 | Registry→분기→Facade | Mapping→Binding→Facade 권장 |
| ID 미등록 | Dispatcher 오류 | Mapping 없음 404 |
| 분기 누락 | Handler Default 오류 | 해당 Method 자체 없음/구현 오류 |
| 입력 형식 오류 | Facade 변환 단계 가능 | MVC Binding 단계 가능 |
| 업무 오류 | Facade/Service 예외 | Facade/Service 예외 |
| Transaction | Worker/Facade | Facade 권장, AS-IS 상이 |
| Timeout | TCF Executor 가능 | TCF Executor 우회 |

## 운영 장애 추적

TCF ON에서 미등록 오류가 나면 Controller가 결정한 ID, Registry 등록 로그와 Handler `serviceIds()`를 비교한다. Handler Default 오류면 목록에는 있으나 switch Case가 누락됐는지 본다. Facade Method가 호출됐는지는 Mock/Test와 Method 로그로 확인한다.

OFF에서 404면 Controller Bean 조건과 Mapping을 확인한다. Controller 로그 뒤 Facade 로그가 없고 Service로 바로 이동하면 AS-IS 직접 호출 경로다. 부분 Commit이 발생하면 Controller 주입 대상과 Service Transaction Annotation을 먼저 본다.

입력 오류가 모드마다 다르면 ON Object 변환 단계와 OFF MVC Binding 단계의 예외 Type을 비교한다. 응답 Advice와 조건부 Global Handler의 차이도 함께 본다. HTTP Status만 맞추고 오류 Code·Field 경로가 다르면 UI가 잘못된 안내를 할 수 있다.

### 증상에서 Adapter 위치를 찾는 순서

요청이 404이면 업무 Service부터 조사하지 않는다. ON에서는 `tcf.enabled`, Online Controller Mapping과 최종 Service ID를 확인한다. OFF에서는 업무 Controller Bean과 `@PostMapping`을 확인한다. 같은 URL이 Profile마다 다른 Controller에 연결될 수 있으므로 기동 Bean Graph와 조건부 Property가 첫 근거다.

`ServiceHandlerNotFound`가 나면 두 단계로 나눈다. Dispatcher에서 “등록되지 않은 ID”라면 Handler `serviceIds()` 또는 Bean 생성 문제다. Handler Class 이름이 포함된 “미지원 ID”라면 Registry에는 있지만 `handle()` 분기가 빠졌을 가능성이 높다. 기동 등록 로그, Handler 상수 목록과 switch Case를 같은 배포 Artifact에서 비교한다.

Controller 진입 로그는 있는데 업무 Transaction이 시작되지 않으면 주입 대상이 Service인지 Facade인지 본다. Field Type과 실제 호출 Method를 확인한 뒤 해당 Bean의 Transaction Annotation을 찾는다. Controller Class에 Annotation을 임시로 붙여 증상을 가리기 전에 ON Handler가 호출하는 Facade와 경계를 공통화한다.

업무는 성공했지만 응답 형태가 다르면 Handler/Controller 반환값을 임의로 고치지 않는다. ResponseBodyAdvice 활성 조건, 반환 Type과 예외 Handler를 확인한다. Adapter는 DTOout을 반환하고 표준 Envelope는 Web 후처리가 담당해야 한다. Controller가 이미 `{hdr_nhnis,dto}` Map을 만들면 Advice가 다시 감싸는 중복 구조가 생길 수 있다.

잘못된 거래가 실행된 의심이 있으면 Path, Context Header, Dispatcher Argument와 TransactionContext Service ID를 모두 수집한다. 현재 Controller는 Header 값을 Path보다 우선할 수 있고 Dispatcher와 Context의 ID 일치 방어가 없다. GUID별로 선택 과정과 최종 Facade Method를 연결해야 한다. 단순 URL Access Log만으로 삭제·조회 분기를 판정하지 않는다.

### Adapter 완료 판정표

| 점검 대상 | 완료 증거 | 실패 징후 |
|---|---|---|
| Handler 등록 | 기동 Registry와 기대 ID Set 일치 | 누락·중복·빈 목록 |
| Handler 분기 | ID별 예상 Facade 1회 호출 | Default 오류·다른 Method |
| Controller Mapping | OFF URL Contract Test 성공 | 404·Mapping 충돌 |
| Controller 의존 | Facade만 주입 | Service/DAO 직접 의존 |
| 입력 검증 | ON/OFF 동일 업무 오류 의미 | 400/500 무질서 |
| Transaction | 중간 실패 전체 Rollback | 부분 반영 |
| 로그 보안 | GUID·ID 중심 Summary | DTO/Token 원문 |

이 판정표는 신규 코드뿐 아니라 기존 Controller 전환에도 적용한다. 한 거래가 완료됐다고 말하려면 정상 응답, 실패 응답과 DB 상태를 모두 검증해야 한다. Handler Unit Test, MVC Slice Test와 실제 Transaction Integration Test는 서로 다른 결함을 찾으므로 하나로 대체하지 않는다.

운영 변경 후에는 첫 요청만 확인하지 말고 S/C/U/D 대표 거래와 동시 요청을 실행한다. Registry는 정적이지만 Controller Mapping, Facade Proxy와 TransactionManager는 Spring Context 구성에 의존한다. Profile별 Context Test를 남기면 다음 설정 변경에서 Adapter 회귀를 빠르게 찾을 수 있다.

장애 보고서에는 “Controller 오류”처럼 넓은 표현 대신 실패한 경계를 적는다. MVC Mapping, DTO Binding, Registry Lookup, Handler 분기, Facade 변환과 Service 업무 오류는 대응 담당자와 재현 방법이 다르다. GUID, Service ID, 실행 모드, Adapter Class와 실패 단계를 함께 기록하면 Framework 문제와 업무 문제를 빠르게 분리할 수 있다.

또한 수정 후에는 반대 모드를 반드시 회귀 Test한다. OFF Controller만 고쳐 정상화했더라도 ON Handler가 같은 Facade를 호출하는지 확인하고, Handler에 거래를 추가했다면 OFF Mapping 존재 여부를 확인한다. 두 Adapter는 별개 소스지만 하나의 공개 업무 계약을 구성한다.

## Anti Pattern

1. Handler에서 DAO나 Mapper를 직접 호출한다.
2. Handler에 Object→DTO 변환과 업무 Validation을 모두 넣는다.
3. `serviceIds()`와 switch Case 중 한쪽만 수정한다.
4. 프로그램 거래마다 Handler Class를 별도로 만든다.
5. Controller에서 Service 여러 개를 조정하고 업무 선후처리를 작성한다.
6. AS-IS Service 직접 호출을 신규 표준으로 복제한다.
7. Controller에 Transaction을 붙여 Facade를 대체한다.
8. Handler와 Controller를 한 Class로 합쳐 MVC와 TCF에 동시에 의존한다.
9. 예외를 Adapter에서 삼키고 정상 DTO를 반환한다.
10. DTO 전체와 Token을 로그로 출력한다.
11. Header/Path/Context ID 불일치를 검증하지 않는다.
12. ON/OFF가 다른 Facade Method를 호출하도록 방치한다.

## 개발자·운영자 체크리스트

- [ ] 새 Service ID가 UI, Header, Handler 상수와 Facade Method 의미에 일치하는가?
- [ ] `serviceIds()`와 `handle()` Case가 동일한가?
- [ ] 한 프로그램에 Handler 하나 원칙을 지켰는가?
- [ ] Handler가 Facade 하나만 의존하는가?
- [ ] Handler에 SQL·업무 Rule·Transaction이 없는가?
- [ ] OFF Controller Mapping과 typed DTO가 존재하는가?
- [ ] Controller가 Service가 아니라 Facade를 호출하는가?
- [ ] Web 검증과 업무 검증을 분리했는가?
- [ ] ON/OFF가 같은 Facade Method를 호출하는가?
- [ ] checked/runtime 예외가 Transaction 밖으로 전파되는가?
- [ ] Adapter 로그가 민감정보를 노출하지 않는가?
- [ ] 정상·미등록·분기 누락·Binding 실패·Rollback을 Test했는가?

## 아키텍처 판단 포인트

새 진입 기능을 어디에 둘지 결정할 때 Protocol에 종속되는지 묻는다. Service ID 선택은 Handler, HTTP Binding은 Controller다. 두 경로에 공통인 DTO 정규화와 유스케이스 조정은 Facade, 업무 규칙은 Service/Rule에 둔다.

Handler 분기 구현은 현재 거래 수에서 상수+목록+switch가 읽기 쉽다. 거래가 크게 늘어 이중 관리 오류가 반복되면 Service ID와 실행 함수를 하나의 immutable Map으로 합치는 설계를 검토할 수 있다. 복잡성을 늘리기 전에 Parameterized Test로 현재 계약을 보호한다.

Controller Transaction은 기술적으로 가능하지만 원자성의 자연 경계인지로 판단한다. HTTP Adapter가 아니라 두 Entry가 공유하는 Business Facade가 일반적으로 더 적합하다. 예외 Controller가 남으면 이유와 종료 계획을 기록한다.

입력 Type 안전성과 공통성도 균형이 필요하다. OFF Controller의 typed DTO는 Compile-time 이점이 있고 ON Handler의 Object 계약은 공통 라우팅에 유연하다. Facade에서 명확히 변환하고 오류를 표준화하며 Schema 기반 Contract Test를 두는 것이 현재 구조의 현실적인 보완이다.

## 핵심 정리

Handler와 Controller는 서로 다른 Protocol을 받는 Inbound Adapter다. Handler는 TCF Service ID와 TransactionContext를 받아 Facade로 분기하고, Controller는 HTTP URL과 typed DTO를 받아 Facade로 위임해야 한다.

현행 Handler 6개는 모두 Facade만 호출해 목표 경계를 지킨다. `serviceIds()` 등록과 `handle()` switch가 이중 관리되므로 등록·분기 일치 Test가 필요하다. Registry는 중복 ID를 기동 실패로 막고 미등록 ID를 요청 시 거절한다.

현행 OFF Controller는 5개가 Service를 직접 호출하고 하나만 Facade를 호출한다. 이는 Facade Transaction과 유스케이스 조정을 우회해 ON/OFF 차이를 만든다. 신규 표준은 Controller→Facade이며 기존 Controller도 거래별 검증 후 전환해야 한다.

Handler나 Controller에는 DAO, 업무 Rule, 복잡한 조정과 Transaction 소유권을 두지 않는다. 두 Adapter는 입력 선택·검증과 Facade 호출에 집중하고 결과와 예외를 보존한다.

다음 장에서는 이 두 Adapter가 공통으로 호출해야 하는 Business Facade를 다룬다. DTO 변환, 유스케이스 조정과 `rdwTransactionManager` Transaction 경계가 왜 Facade에 모여야 하는지 실제 소스로 살펴본다.
