# 제4부 업무 진입과 유스케이스 경계

# 15장. Business Facade

Handler가 Service ID를 해석해 올바른 거래를 선택했다면, 그다음 질문은 “선택된 거래를 어떤 단위로 실행할 것인가”이다. 하나의 온라인 거래는 단순히 Service 메서드 하나를 호출하는 일로 끝나지 않는다. 느슨한 요청 본문을 업무 DTO로 바꾸고, 필요한 업무 단계를 순서대로 조정하며, 여러 변경을 하나의 원자적 결과로 묶어야 한다. PDMG에서 이 책임을 맡는 계층이 Business Facade다.

Facade를 단순 전달자로 보면 중요한 경계를 놓친다. 반대로 모든 업무 규칙과 SQL을 Facade에 넣으면 Service와 DAO의 역할이 무너진다. 이 장은 Facade를 **하나의 유스케이스를 시작하고 끝내는 애플리케이션 경계**로 읽는다. 특히 `@Transactional`이 붙었다는 사실과 실제 최외곽 트랜잭션 시작점이 항상 같지는 않다는 점을 TCF·Timeout 조합별로 구분한다.

## 이 장에서 해결할 질문

- Facade는 Handler 또는 Controller와 Service 사이에서 무엇을 조정하는가?
- `Object`나 `Map` 형태의 본문은 어디에서 타입이 있는 DTO로 변환되는가?
- 여러 Service 호출을 하나의 유스케이스와 트랜잭션으로 묶으려면 경계를 어디에 두어야 하는가?
- Facade의 `@Transactional`은 언제 새 트랜잭션을 시작하고, 언제 기존 트랜잭션에 참여하는가?
- TCF ON·OFF와 Timeout ON·OFF에 따라 Facade의 의미는 어떻게 달라지는가?
- 같은 Facade 내부의 자기 호출이 왜 별도 트랜잭션 속성을 적용하지 못하는가?
- Facade에 두면 안 되는 로직은 무엇이며, 운영자는 어떤 증거로 경계 문제를 찾는가?

## 전체 아키텍처에서의 위치

```text
HTTP 요청
   │
   ├─ TCF ON  → OnlineTransactionController → TcfFacade
   │                                      → Dispatcher → Handler
   │
   └─ TCF OFF → 업무 Controller
                                            │
                                            ▼
                                  Business Facade
                                  ├─ 입력 DTO 변환
                                  ├─ 유스케이스 순서 조정
                                  ├─ Transaction 선언
                                  └─ 결과 반환
                                            │
                                            ▼
                                   Business Service
                                   ├─ Rule
                                   └─ DAO → Mapper → DB
```

TCF ON 경로에서 Handler는 Service ID를 보고 어떤 Facade 메서드를 호출할지 결정한다. Facade는 이미 선택된 거래의 입력을 구체화하고 실행 단계를 조직한다. 즉 Handler의 질문은 “어느 거래인가”이고, Facade의 질문은 “그 거래를 어떤 원자적 순서로 완수할 것인가”이다. Service는 그 안에서 업무 정책과 처리를 수행한다.

AS-IS 소스의 Facade는 `nhnis.mg.co.a.application.facade` 패키지에 있으며 `mgcoa5530Facade`, `mgcoa8888Facade`, `mgcoa9000Facade`, `mgcoa9001Facade`, `mgcoa9100Facade`, `mgcoa9999Facade`가 확인된다. 대부분 `ObjectMapper`로 요청 본문을 DTO로 바꾼 뒤 같은 업무 코드의 Service를 호출한다. 다만 런타임 진단용 `mgcoa9100Facade`에는 `@Transactional`이 없다. 따라서 “모든 Facade가 트랜잭션 경계다”라는 문장은 현행을 정확히 표현하지 못한다.

## 15.1 Facade의 목적

Facade의 첫 번째 목적은 외부 진입 계약과 내부 업무 계약을 분리하는 것이다. Handler가 받는 `dtoBody`는 Dispatcher가 전달한 일반 객체다. 이 객체를 Service까지 그대로 흘려보내면 Service가 `Map` 키, Jackson 변환, 누락 필드 처리 같은 전송 형식의 문제까지 알아야 한다. PDMG Facade는 이 느슨한 입력을 거래별 `DTOin`으로 변환함으로써 Service가 타입이 있는 계약을 기준으로 동작하게 한다.

두 번째 목적은 유스케이스를 조정하는 것이다. 조회 한 건은 Service 하나를 곧바로 호출할 수 있지만, 실제 업무는 검증 Service, 상태 변경 Service, 이력 Service, 외부 연계 Client를 순서대로 실행할 수 있다. 이 순서와 성공 조건은 개별 계산 규칙보다 상위 개념이다. Facade는 “등록 유스케이스가 어떤 단계로 완성되는가”를 보여 주고, Service는 각 단계의 업무 의미를 구현한다.

세 번째 목적은 원자성 정책을 선언하는 것이다. 쓰기 유스케이스의 여러 DB 작업이 모두 성공해야 한다면 Facade 메서드에 `rdwTransactionManager`와 롤백 규칙을 선언한다. 이 선언은 TCF ON + Timeout OFF에서는 실제 시작 경계가 될 수 있고, Timeout ON에서는 이미 Worker가 시작한 거래에 참여하는 계약이 된다. 어느 경우든 Facade는 유스케이스가 기대하는 트랜잭션 정책을 소스에 드러낸다.

Facade가 책임지지 않는 것도 분명하다. URL과 HTTP 상태를 결정하는 일은 Controller·공통 웹 계층의 책임이고, Service ID 라우팅은 Handler의 책임이다. 필드 간 업무 규칙과 계산은 Service·Rule, 영속화는 DAO·Mapper가 맡는다. Facade는 이 요소를 소유하지 않고 조정한다.

## 15.2 Handler와 Service 사이의 경계

`mgcoa9000Handler`는 `S0`, `C0`, `U0`, `D0` 거래 구분에 따라 대응하는 `mgcoa9000Facade` 메서드를 호출한다. Handler가 넘기는 값은 `Object dtoBody`이며, Facade가 반환하는 값은 거래별 출력 DTO다. Handler에는 DTO의 필드를 해석하는 코드도, DAO 호출도 없다. 이 단순함은 의도된 것이다.

```text
mgcoa9000Handler.handle(serviceId, dtoBody)
   │
   ├─ S0 → mgcoa9000Facade.mgcoa9000S0(dtoBody)
   ├─ C0 → mgcoa9000Facade.mgcoa9000C0(dtoBody)
   ├─ U0 → mgcoa9000Facade.mgcoa9000U0(dtoBody)
   └─ D0 → mgcoa9000Facade.mgcoa9000D0(dtoBody)
                                      │
                                      ▼
                               mgcoa9000Service
```

이 경계는 변경 이유를 분리한다. 새 Service ID를 추가하거나 거래 코드 분기를 바꾸면 Handler가 영향을 받는다. 요청 필드를 DTO로 묶는 방식이나 한 유스케이스의 단계가 바뀌면 Facade가 영향을 받는다. 업무 규칙과 데이터 상태 전이가 바뀌면 Service·Rule이 영향을 받는다. SQL과 스키마 접근이 바뀌면 DAO·Mapper가 영향을 받는다.

TCF OFF의 레거시 Controller가 Service를 직접 호출하면 이 경계가 사라진다. 입력 변환을 Controller가 떠안고 Facade의 트랜잭션 선언도 우회한다. 현행 OFF Controller별 호출 대상은 일률적이지 않을 수 있으므로 “TCF OFF도 자동으로 Facade를 통과한다”고 가정해서는 안 된다. OFF 호환 경로를 유지할 때는 Controller가 동일 Facade를 호출하도록 맞추는 것이 ON/OFF 동등성을 높이는 TO-BE다.

## 15.3 Object·Map에서 DTO 변환

AS-IS Facade의 대표 변환은 다음 구조다.

```java
private <T> T convert(Object dtoBody, Class<T> type) {
    Object source = dtoBody == null ? Collections.emptyMap() : dtoBody;
    return objectMapper.convertValue(source, type);
}
```

이 코드는 전송 계층의 일반 객체를 거래별 입력 DTO로 바꾼다. `mgcoa9000C0`는 `mgcoa9000C0DTOin`, `mgcoa9000U0`는 `mgcoa9000U0DTOin`으로 변환된다. 같은 도메인이라도 행위마다 계약이 다르기 때문에 하나의 만능 Map을 공유하지 않는다. 변환이 성공한 다음부터 Service는 DTO getter와 타입을 사용할 수 있다.

`dtoBody == null`이면 빈 Map을 사용하는 것은 NullPointerException을 피하는 방어 장치이지, 필수 입력이 유효하다는 보장은 아니다. Jackson은 빈 Map으로 DTO를 만들 수 있으므로 필드가 모두 null인 객체가 Service에 전달될 수 있다. 따라서 생성·수정·삭제 거래는 Bean Validation 또는 명시적 업무 검증으로 필수값을 거부해야 한다. “DTO 객체가 만들어졌다”와 “유효한 요청이다”는 서로 다른 판정이다.

변환 실패도 정상적인 계약 실패로 다뤄야 한다. 숫자 필드에 해석할 수 없는 문자열이 들어오거나 객체 구조가 맞지 않으면 `convertValue`가 런타임 예외를 낼 수 있다. Facade가 이를 빈 출력으로 바꿔 반환하면 쓰기 작업의 롤백 신호와 표준 오류 응답이 사라진다. 예외는 공통 예외 계층까지 전파하되, 클라이언트에는 내부 클래스명이나 스택 트레이스를 노출하지 않아야 한다.

현재 여러 Facade가 거의 같은 `convert` 메서드를 반복한다. 중복 제거는 가능하지만 공통 Binder를 만들 때 허용 필드, 알 수 없는 필드 정책, 날짜·숫자 변환, 검증 실행 시점을 함께 표준화해야 한다. 단지 한 줄을 줄이기 위한 추상화가 변환 실패의 위치를 감추어서는 안 된다.

## 15.4 유스케이스 조정

유스케이스 조정은 한 요청의 성공을 구성하는 단계를 순서대로 배치하는 일이다. 예를 들어 “고객 상태 변경”이 입력 검증, 현재 상태 조회, 변경 가능성 판정, 상태 UPDATE, 이력 INSERT로 이루어진다면 Facade는 이 단계가 하나의 요청 결과로 묶인다는 사실을 표현할 수 있다. 세부 변경 가능성 계산은 Rule에, 각 상태 처리와 이력 생성은 Service에 둘 수 있다.

```text
Facade.changeCustomer(input)
   ├─ validationService.validate(input)
   ├─ customerService.change(input)
   ├─ historyService.record(result)
   └─ outputAssembler.toOutput(result)
```

위 그림은 구조 설명을 위한 개념 예제이며 현행 PDMG의 특정 메서드를 의미하지 않는다. AS-IS Facade 대부분은 DTO 변환 후 단일 Service를 호출한다. 따라서 “현재 모든 Facade가 여러 Service를 조정한다”고 단정하면 안 된다. 현행은 조정 경계를 마련한 상태이고, 복합 유스케이스가 추가될 때 그 경계가 본격적으로 사용될 수 있다.

조정과 업무 로직의 구분 기준은 재사용과 표현력이다. “등록 후 이력을 남긴다”는 유스케이스 순서이며 Facade에 어울린다. “한도 금액이 고객 등급별 상한을 넘는가”는 업무 규칙이며 Rule 또는 Service에 어울린다. Facade 메서드가 수십 개의 조건문과 필드 계산으로 채워지면 조정자가 정책 구현자로 변질된 것이다.

## 15.5 여러 Service 호출

여러 Service를 호출할 때 가장 중요한 것은 호출 개수가 아니라 실패 의미다. A Service가 성공한 뒤 B Service가 실패했을 때 A의 변경도 취소되어야 한다면 두 호출은 같은 트랜잭션에 참여해야 한다. 반대로 외부 알림처럼 핵심 변경과 원자적으로 묶을 수 없는 작업은 커밋 이후 이벤트나 별도의 보상 전략을 검토해야 한다.

```text
TX BEGIN
   Facade
     ├─ Service A → DAO A → UPDATE
     ├─ Service B → DAO B → INSERT
     └─ Service C → 검증 실패
TX ROLLBACK
```

`REQUIRED` 전파와 같은 `rdwTransactionManager`를 사용한다면 내부 Service·DAO의 DB 작업은 기존 거래에 참여한다. 그러나 다른 DataSource나 TransactionManager를 사용하거나 `REQUIRES_NEW`를 선언하면 물리 경계가 달라질 수 있다. Facade라는 이름만으로 동일 트랜잭션이 보장되는 것이 아니다. 사용하는 자원과 전파 속성을 확인해야 한다.

외부 HTTP 호출은 DB 트랜잭션과 같은 방식으로 롤백되지 않는다. DB 변경 뒤 외부 시스템 호출이 성공하고 이후 로컬 오류가 발생하면 외부 결과만 남을 수 있다. 이런 유스케이스는 호출 순서, 멱등키, Outbox, 재처리, 보상 거래를 설계해야 한다. Facade는 그 정책을 조정하되 원격 호출을 JDBC 트랜잭션이 자동 취소한다고 오해해서는 안 된다.

## 15.6 `@Transactional` 선언

현행 `mgcoa9000Facade`와 `mgcoa9001Facade`는 조회 메서드에 다음과 같은 선언을 사용한다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
```

생성·수정·삭제 메서드는 다음 정책을 사용한다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

트랜잭션 이름을 명시한 이유는 PDMG의 RDW DataSource에 대응하는 관리자를 선택하기 위해서다. `rollbackFor = Exception.class`는 checked Exception까지 롤백 대상으로 넓힌다. 기본 규칙만 사용하면 일부 checked Exception이 커밋으로 끝날 가능성이 있으므로 쓰기 유스케이스의 실패 계약을 명시한 것이다.

그러나 Annotation 위치와 물리적 BEGIN 위치를 동일시해서는 안 된다. 기본 전파는 `REQUIRED`다. 호출 시점에 같은 관리자의 트랜잭션이 없으면 Facade 프록시가 새 트랜잭션을 시작하지만, 이미 있으면 그 트랜잭션에 참여한다. 내부 선언은 외부 거래의 `readOnly`, isolation, timeout을 뒤늦게 다시 정의하지 못한다.

예외를 잡아 정상값으로 반환하는 코드는 롤백 계약을 깨뜨린다.

```java
try {
    return service.execute(input);
} catch (Exception ex) {
    log.error("business failed", ex);
    return new Output();
}
```

프록시 입장에서는 메서드가 정상 반환했으므로 커밋할 수 있다. 복구 가능한 예외만 명확한 정책으로 처리하고, 유스케이스 실패라면 다시 던지거나 트랜잭션을 rollback-only로 표시해야 한다. 오류 로그를 남겼다는 사실은 롤백 신호를 대체하지 않는다.

## 15.7 TCF ON Facade

TCF ON에서는 Handler가 Facade의 외부 호출자다. 다만 Timeout 설정에 따라 최외곽 트랜잭션이 달라진다.

```text
TCF ON + Timeout ON

Request Thread                         Worker Thread
TcfFacade → submit ──────────────────▶ TransactionTemplate
                                        TX BEGIN
                                          Dispatcher
                                          Handler
                                          Facade @Transactional(REQUIRED)
                                          Service
                                          DAO
                                        COMMIT / ROLLBACK
```

`DefaultOnlineTimeoutExecutor`는 Worker에서 `TransactionTemplate`을 실행하고, `action.call()`의 예외 또는 deadline 초과를 만나면 rollback-only로 만든다. 이때 Facade의 `@Transactional`은 새 물리 거래를 만들지 않고 Worker의 기존 거래에 참여한다. 따라서 최외곽 시작점은 Facade가 아니라 Timeout Executor다.

조회 Facade의 `readOnly = true`도 주의해야 한다. Worker가 이미 일반 `TransactionTemplate`을 시작했다면 내부 Facade가 기존 물리 거래를 읽기 전용으로 바꾸지 못한다. 조회 최적화를 보장하려면 외부 실행기가 거래 메타데이터를 알고 적절한 TransactionDefinition을 선택하는 설계가 필요하다. 이는 TO-BE 검토 사항이지 현재 Facade Annotation만으로 해결된 AS-IS가 아니다.

Timeout OFF에서는 `SyncOnlineTimeoutExecutor`가 같은 요청 Thread에서 작업을 직접 실행하며 외부 `TransactionTemplate`을 시작하지 않는다. 이 경우 Handler가 Spring 프록시를 통해 Facade에 진입할 때 Facade가 실제 BEGIN 지점이 된다.

```text
TCF ON + Timeout OFF

Request Thread
  TcfFacade → Sync Executor → Dispatcher → Handler
      → Facade Proxy
          TX BEGIN
          Service → DAO
          COMMIT / ROLLBACK
```

두 흐름에서 Facade 소스는 같지만 실행 의미는 다르다. 운영 문서와 로그를 해석할 때 설정 조합과 Thread를 함께 봐야 하는 이유다.

## 15.8 TCF OFF Facade

TCF OFF는 공통 `OnlineTransactionController`와 Dispatcher·Handler를 우회하는 호환 경로다. 이 경로가 Facade를 호출한다면 Facade의 변환과 트랜잭션 정책을 그대로 재사용할 수 있다. 그러나 Controller가 Service를 직접 호출하면 Facade가 실행되지 않으며 Facade Annotation도 아무 효과가 없다.

```text
권장 OFF 경로
Controller → Facade Proxy → Service → DAO
               TX BEGIN             COMMIT/ROLLBACK

Facade 우회 경로
Controller → Service → DAO
             Facade의 TX 선언 적용 안 됨
```

현행 소스에는 Service 자체에 `@Transactional`이 선언된 사례도 있으므로 OFF에서 모든 거래가 무조건 무트랜잭션이라고 단정해서도 안 된다. 예컨대 `mgcoa9001Service`에는 조회와 쓰기 메서드별 트랜잭션 선언이 확인된다. 정확한 판정은 각 Controller의 실제 호출 대상과 대상 Service Annotation을 함께 봐야 한다. 핵심은 Facade를 우회하면 **Facade가 의도한 경계**는 사라진다는 것이다.

ON/OFF 호환성을 높이려면 두 진입점이 동일한 Facade 메서드에 수렴해야 한다. 그래야 DTO 변환, 유스케이스 순서, 트랜잭션 선언, 예외 전파가 동일해진다. HTTP 경로만 다르고 업무 실행 경로는 같아지는 구조가 바람직하다.

## 15.9 Facade 자기 호출 문제

Spring의 기본 프록시 기반 AOP는 Bean 외부에서 프록시를 통과할 때 적용된다. 같은 객체 안에서 `this.inner()`를 호출하면 프록시를 우회한다.

```java
public void outer() {
    this.inner();
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void inner() {
    // 별도 트랜잭션을 기대해도 자기 호출에서는 적용되지 않는다.
}
```

이 문제는 `@Transactional`이 무시된 것처럼 보이지만 실제로는 `inner()` 호출이 프록시에 도달하지 않은 것이다. `REQUIRES_NEW`, 별도 timeout, readOnly 전환 같은 속성도 적용되지 않는다. 현행 주요 Facade에서 이런 자기 호출 패턴은 확인되지 않지만 복합 유스케이스를 확장할 때 쉽게 생길 수 있다.

별도 트랜잭션 경계가 정말 필요하면 책임을 다른 Spring Bean으로 분리해 프록시를 통한 외부 호출로 만든다. 자기 자신을 주입하거나 `AopContext`로 프록시를 억지로 찾아 호출하는 방식은 구조를 불투명하게 만든다. 먼저 해당 단계가 별도 유스케이스인지, 실패 독립성이 필요한지 판단한 다음 Bean 경계를 설계해야 한다.

## 15.10 Facade에서 처리하지 않아야 할 것

Facade에 SQL을 직접 쓰거나 Mapper를 호출하면 데이터 접근 계층을 우회한다. SQL 변경 이유와 유스케이스 변경 이유가 한 클래스에 섞이고, Mapper 테스트와 재사용이 어려워진다. DB 접근은 DAO·Mapper로 내려보내야 한다.

대규모 업무 계산과 필드별 정책도 Facade에 두지 않는다. Facade가 수백 줄의 if 문을 가지면 다른 유스케이스에서 같은 규칙을 재사용하기 어렵고 단위 테스트도 비대해진다. 순수 검증·계산은 Rule, 상태를 사용하는 업무 흐름은 Service가 담당한다.

HTTP 객체에 의존해서도 안 된다. `HttpServletRequest`, 응답 상태, 세션을 Facade 계약으로 사용하면 TCF Handler나 배치·테스트에서 재사용하기 어렵다. 공통 요청 정보가 필요하면 검증된 `ServiceContext` 계약을 사용하되, Context의 부재와 Thread 전파 조건을 고려해야 한다.

마지막으로 시스템 공통 관심사를 복제하지 않는다. 인증, GUID 생성, 이미지로그, 공통 예외 응답, Timeout 실행은 Framework 계층의 책임이다. Facade가 이 기능을 거래마다 다시 구현하면 정책이 분산되고 ON/OFF 경로의 동작이 달라진다.

## End-to-End 실행 흐름

쓰기 거래 `mgcoa9000C0`를 기준으로 현재 구조를 읽으면 다음과 같다.

```text
1. Handler가 serviceId의 C0를 판별한다.
2. Handler가 mgcoa9000Facade.mgcoa9000C0(dtoBody)를 호출한다.
3. Spring Transaction Interceptor가 Facade 진입을 가로챈다.
4. 외부 TX가 없으면 rdwTransactionManager로 BEGIN한다.
   외부 Worker TX가 있으면 기존 TX에 참여한다.
5. Facade가 Object를 mgcoa9000C0DTOin으로 변환한다.
6. Facade가 mgcoa9000Service.mgcoa9000C0(input)을 호출한다.
7. Service 포인트컷의 업무 선처리가 실행된다.
8. Service와 DAO·Mapper가 업무 변경을 수행한다.
9. Service가 정상 반환하면 업무 후처리가 실행된다.
10. Facade가 출력 DTO를 Handler에 반환한다.
11. 최외곽 TX 경계가 COMMIT한다.
12. 예외가 전파되면 최외곽 경계가 ROLLBACK한다.
```

5단계의 DTO 변환 실패도 Transaction 프록시 안에서 발생한다. 따라서 Facade가 새 거래를 시작한 흐름에서는 변환이 실패하면 거래가 롤백된다. 대개 아직 SQL을 실행하기 전이지만, 이 사실은 변환도 유스케이스 경계의 일부임을 보여 준다.

## 실행 조건별 트랜잭션 판정

| 실행 조건 | 외부 호출 | 최외곽 BEGIN 후보 | Facade의 의미 | 업무 선후처리 참여 |
|---|---|---|---|---|
| TCF ON, Timeout ON | Handler | Worker `TransactionTemplate` | 기존 TX 참여 | Service가 Worker TX 안에서 호출되면 참여 |
| TCF ON, Timeout OFF | Handler | Facade 프록시 | 새 TX 시작 가능 | Facade TX 안에서 참여 |
| TCF OFF, Controller→Facade | Controller | Facade 프록시 | 새 TX 시작 가능 | Facade TX 안에서 참여 |
| TCF OFF, Controller→Service | Controller | Service 선언에 따라 다름 | 실행되지 않음 | Service TX 유무에 따라 다름 |

이 표의 “후보”라는 표현이 중요하다. 이미 상위 계층이 같은 TransactionManager로 거래를 열었다면 기본 `REQUIRED`는 참여한다. 실제 여부는 Transaction 로그, Thread 이름, Spring Transaction 상태를 함께 확인해야 한다.

## 현행 Facade를 거래별로 읽는 방법

Facade 구조가 같아 보여도 각 클래스가 표현하는 거래 계약은 다르다. 소스 검토는 Annotation 개수만 세는 방식이 아니라 입력 타입, 행위 코드, 다음 Service, 반환 타입, 예외 선언을 한 줄로 연결하는 방식이어야 한다.

`mgcoa5530Facade`는 조회 `S0` 하나를 제공한다. null 본문을 빈 Map으로 바꾸고 `mgcoa5530S0DTOin`으로 변환한 뒤 `mgcoa5530Service.mgcoa5530S0`을 호출한다. 메서드는 `readOnly=true`를 선언한다. 이 사례는 단일 조회 Facade의 최소 구조를 잘 보여 준다. Facade가 Service 하나만 호출하더라도 외부의 일반 본문과 내부 DTO를 분리하고 조회 트랜잭션 의도를 표현한다.

`mgcoa8888Facade`는 이미지로그 조회 `S0`과 삭제 `D0`를 함께 가진다. 조회에는 readOnly, 삭제에는 `rollbackFor=Exception.class`가 적용된다. 동일 도메인의 행위마다 트랜잭션 의미가 달라질 수 있음을 보여 준다. 클래스 수준에 쓰기 정책 하나를 붙이지 않고 메서드 수준에서 분리한 이유도 여기서 찾을 수 있다.

`mgcoa9000Facade`와 `mgcoa9001Facade`는 각각 거래 파라미터 관리와 거래통제 관리의 `S0/C0/U0/D0`를 제공한다. 조회와 생성·수정·삭제의 입력·출력 DTO가 모두 분리되어 있고, 공통 private `convert`가 각 DTO Class를 받는다. 행위가 추가될 때 Handler의 분기, Facade 메서드, 입력·출력 DTO, Service 메서드가 함께 정합성을 가져야 한다.

`mgcoa9999Facade`는 샘플 조회 구조이며 `mgcoa5530Facade`와 유사하게 단일 `S0`과 readOnly를 사용한다. 샘플이라고 해서 운영 계약과 다른 예외 처리나 임의 Map 반환을 허용해서는 안 된다. 신규 개발자가 이 코드를 복사하므로 표준 구조의 정확성이 더 중요하다.

`mgcoa9100Facade`는 다른 사례다. 입력 DTO를 만들지만 출력은 `Map<String,Object>`이고 Transaction Annotation이 없다. `includeDetails`가 null이면 `Y`를 기본값으로 채운 다음 진단 Service의 `inquiry`를 호출한다. 이는 현행 예외 사례이며, 모든 Facade가 거래별 출력 DTO와 트랜잭션 선언을 가진다는 일반화를 막는다. 이 기본값이 단순 표현 기본값인지 운영 정책인지는 진단 유스케이스의 계약으로 관리해야 한다.

| Facade | 확인된 행위 | 입력 변환 | 트랜잭션 선언의 특징 |
|---|---|---|---|
| `mgcoa5530Facade` | S0 | 전용 DTO | readOnly |
| `mgcoa8888Facade` | S0, D0 | 행위별 DTO | 조회와 삭제 정책 분리 |
| `mgcoa9000Facade` | S0, C0, U0, D0 | 행위별 DTO | 조회 readOnly, 쓰기 checked 예외 롤백 |
| `mgcoa9001Facade` | S0, C0, U0, D0 | 행위별 DTO | 조회 readOnly, 쓰기 checked 예외 롤백 |
| `mgcoa9100Facade` | S0 | DTO 후 Map 조립 | Annotation 없음 |
| `mgcoa9999Facade` | S0 | 전용 DTO | readOnly |

이 목록은 작성 시점의 AS-IS다. 새 Facade가 추가되면 정적 목록을 진실의 원천으로 삼지 말고 패키지 검색과 Handler 등록을 다시 대조해야 한다. 특히 동일한 메서드명이라도 구 패키지와 신규 패키지가 공존하면 어떤 Bean이 실제 주입되는지 Component Scan과 기동 로그까지 확인해야 한다.

## Facade 프록시와 호출 시점을 해석하기

`@Transactional`은 Facade 객체 자체에 마법처럼 들어가는 코드가 아니다. Spring은 대상 Bean 주위에 프록시를 구성하고, 외부 호출이 프록시를 통과할 때 Transaction Interceptor가 메서드의 속성을 읽는다. 이 구조를 이해하면 여러 오해가 풀린다.

```text
Handler
   │
   ▼
Facade Spring Proxy
   ├─ Transaction 속성 조회
   ├─ 기존 TX 탐색
   ├─ BEGIN 또는 JOIN
   ▼
실제 Facade 객체
   ├─ DTO 변환
   └─ Service 호출
   │
   ▼
Proxy 정상 반환/예외 수신
   └─ COMMIT 또는 ROLLBACK 판단
```

Facade 객체가 Spring Bean이 아니거나 `new`로 직접 생성되면 프록시가 없다. private 메서드에 Annotation을 붙이거나 자기 호출하면 외부 프록시 진입이 없다. Handler가 생성자 주입으로 Spring이 관리하는 Facade를 받는 현재 패턴은 이 조건을 충족한다. 테스트에서도 Facade를 직접 `new`로 만들고 트랜잭션 동작까지 검증했다고 생각하면 안 된다. 순수 변환 단위 테스트와 Spring Transaction 통합 테스트의 목적을 분리해야 한다.

프록시는 예외가 밖으로 나오는 것을 보고 완료 상태를 결정한다. Facade 내부에서 예외를 다른 checked Exception으로 감싸면 `rollbackFor` 규칙이 그 타입을 포함하는지 봐야 한다. 현재 주요 쓰기 Facade의 `Exception.class`는 넓은 범위를 포함하지만, Error 처리나 별도 `noRollbackFor`를 추가하면 결과가 달라진다. 반대로 조회 메서드에는 `rollbackFor=Exception.class`가 명시되지 않았으므로 checked Exception 정책을 쓰기와 같다고 가정해서는 안 된다.

## 업무 선후처리와 Facade 경계

현행 `BizPrePostAspect`의 포인트컷은 Facade가 아니라 `nhnis.mg.co.a.application.service..*`의 public 메서드다. 따라서 실행 순서는 Facade 프록시와 Service Aspect를 함께 놓고 읽어야 한다.

```text
Facade Transaction Proxy
   ├─ BEGIN 또는 JOIN
   ├─ Facade DTO 변환
   └─ Service 호출
        ├─ 업무 선처리 @Before
        ├─ Service 본문
        └─ 정상 반환 시 업무 후처리 @AfterReturning
   └─ COMMIT 또는 상위 TX로 반환
```

Facade가 트랜잭션을 새로 시작하는 경로라면 Service의 선처리와 정상 후처리는 그 안에서 실행된다. Timeout ON에서는 Facade보다 더 바깥의 Worker TX가 이미 있으므로 역시 같은 거래 안에서 실행된다. OFF Controller가 Service를 직접 부르더라도 Service 자체 Transaction Proxy가 먼저 시작되는 메서드라면 Aspect 순서와 Advisor 우선순위까지 검증해야 한다. Annotation이 어느 클래스에 있는지만 보고 선후처리의 안팎을 결정하면 안 된다.

현재 Aspect의 후처리는 `@AfterReturning`이다. Service가 예외를 던지면 정상 후처리가 실행되지 않는다. 따라서 Facade가 예외를 잡아 다른 Service를 계속 호출하는 설계를 넣으면 실패 흐름과 후처리 의미가 복잡해진다. 오류 이력을 반드시 저장해야 한다면 정상 후처리와 분리하고, 원거래 롤백과 독립시킬지 같은 거래에 참여시킬지를 명시적으로 결정해야 한다. 상세한 Advice 순서와 오류 이력의 `REQUIRES_NEW` 판단은 다음 장에서 다룬다.

## 복합 유스케이스 설계 절차

새 Facade가 여러 Service를 조정해야 한다면 먼저 유스케이스의 성공 조건을 문장으로 쓴다. 예를 들어 “고객 기본정보와 동의정보가 모두 저장되어야 성공이며, 알림 발송 실패는 재처리 대상으로 남긴다”처럼 원자적 부분과 비원자적 부분을 나눈다. 이 구분 없이 단순 호출 순서부터 코딩하면 트랜잭션이 너무 넓거나 부분 성공을 복구하지 못한다.

다음으로 로컬 DB 자원을 식별한다. 같은 RDW DataSource를 쓰는 변경은 하나의 `rdwTransactionManager`에 참여시킬 수 있다. 다른 DB, 메시지 브로커, 외부 HTTP는 같은 로컬 트랜잭션으로 자동 묶이지 않는다. 호출 대상별 실패 유형과 재시도 가능성, 멱등성을 기록한다.

그다음 Facade의 입력과 출력을 설계한다. 외부 본문을 그대로 여러 Service에 나누어 주기보다 거래 입력 DTO를 만든 뒤 필요한 Command 또는 하위 DTO로 명확히 전달한다. 출력도 Service의 영속 객체를 그대로 노출하지 않고 유스케이스 결과 계약으로 조립한다. 현행은 대부분 Service 출력 DTO를 그대로 반환하지만, 여러 Service 결과를 합치는 경우 Facade가 출력 조립 지점이 될 수 있다.

마지막으로 실패 테스트를 먼저 정의한다. 두 번째 DB 변경 실패, checked Exception, 외부 호출 지연, Timeout deadline 초과, Worker interrupt, 중복 요청을 포함한다. “정상 호출 결과가 맞다”만으로는 유스케이스 경계가 검증되지 않는다. 롤백된 행 수와 남아야 할 독립 이력, 재처리 레코드까지 확인해야 한다.

## 트랜잭션 관찰성을 확보하는 법

운영 환경에서 Spring 내부 로그를 항상 DEBUG로 켤 수는 없다. 따라서 애플리케이션 로그에는 GUID, Service ID, Thread, 유스케이스 메서드가 연결되어야 한다. 다만 BEGIN·COMMIT을 업무 코드가 가짜 문자열로 출력해 실제 트랜잭션 로그처럼 보이게 해서는 안 된다. 로그 메시지는 “Facade 진입”과 “Facade 반환”을 나타낼 뿐 물리 커밋 완료의 증거가 아닐 수 있다.

Timeout ON에서 특히 그렇다. Facade가 반환한 뒤 Worker Executor가 deadline을 검사하고 rollback-only를 설정할 수 있다. 따라서 Facade 종료 로그 뒤에 Timeout과 ROLLBACK이 나타나는 것은 모순이 아니다. 요청 Thread의 Timeout 로그와 Worker Thread의 거래 완료 로그를 GUID로 묶어 시간순으로 봐야 한다.

DB의 실제 커밋 여부는 테스트 데이터, 트랜잭션 동기화 이벤트, DataSource 프록시 로그 같은 근거로 확인한다. 로그 한 줄만으로 “Facade에서 커밋됐다”고 결론 내리지 않는다. 서로 다른 TransactionManager가 섞였다면 manager 이름과 Connection 식별 정보도 안전한 범위에서 구분해야 한다.

## 책임과 경계 표

| 구성 요소 | 핵심 책임 | 입력 | 다음 호출 | 맡지 않아야 할 책임 |
|---|---|---|---|---|
| Handler | Service ID 등록·분기 | 일반 본문 | Facade | DTO 필드 업무 처리, SQL |
| Controller | HTTP 바인딩·호환 진입 | HTTP 요청 | Facade 권장 | 장기 업무 흐름, DAO 직접 호출 |
| Business Facade | DTO 변환·유스케이스 조정·TX 정책 | `Object`/DTO | Service | 상세 규칙, SQL, HTTP 응답 조립 |
| Business Service | 업무 흐름과 상태 변화 | 입력 DTO | Rule·DAO | Service ID 라우팅 |
| Rule | 검증과 계산 | 업무 값 | 보통 없음 | I/O 조정과 HTTP 처리 |
| DAO·Mapper | 영속화 | 조회·변경 조건 | DB | 유스케이스 순서 결정 |

## 정상과 실패 흐름 비교

정상 흐름에서는 입력 DTO 변환, 모든 Service 호출, 업무 후처리가 끝난 뒤 최외곽 경계가 커밋한다. Facade가 내부 거래에 참여했다면 Facade 반환 시점이 곧 물리 커밋 시점은 아니다. Worker `TransactionTemplate`이 Facade 이후 deadline을 다시 검사한 뒤 커밋할 수 있다.

실패 흐름은 실패 위치에 따라 관찰 지점이 다르다. DTO 변환 실패는 Service에 진입하기 전에 발생한다. 업무 검증 실패는 Service 또는 Rule에서 올라온다. SQL 실패는 DAO·Mapper에서 시작하지만 Facade 밖까지 전파되어야 롤백 계약이 유지된다. Timeout은 요청 Thread가 `future.cancel(true)`를 호출한 뒤 Worker가 interrupt 또는 deadline을 확인해 rollback-only로 끝내려 한다. 클라이언트가 Timeout 응답을 받은 시점과 DB 롤백 완료 시점은 같다고 단정할 수 없다.

| 실패 위치 | Service 실행 | DB 변경 가능성 | 필요한 처리 |
|---|---:|---:|---|
| DTO 변환 | 아니요 | 낮음 | 표준 입력 오류로 변환, 예외 전파 |
| 업무 검증 | 일부 | 앞 단계에 따라 있음 | 같은 TX 롤백 |
| DAO·SQL | 예 | 있음 | 원인 보존, 예외 전파 |
| 외부 호출 | 예 | 있음 | 멱등·보상·재처리 정책 |
| Timeout | Worker 상태에 따라 다름 | 있음 | cancel 요청과 Worker rollback 완료를 구분 |

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | 주요 Facade가 `ObjectMapper.convertValue`로 입력 DTO를 만들고 Service를 호출한다. |
| AS-IS | 조회는 `readOnly=true`, 주요 쓰기는 `rollbackFor=Exception.class`를 선언한다. |
| AS-IS | Timeout ON에서 Worker `TransactionTemplate`이 외부 TX를 시작하며 Facade는 참여한다. |
| AS-IS 예외 | `mgcoa9100Facade`에는 트랜잭션 Annotation이 없다. 일부 Service에도 자체 TX 선언이 있다. |
| 제약 | null 본문을 빈 Map으로 바꾸므로 필수 입력 검증 없이는 null 필드 DTO가 실행될 수 있다. |
| 제약 | Timeout ON의 외부 일반 TX에서는 내부 Facade의 `readOnly=true`가 물리 TX 속성을 바꾸지 못한다. |
| TO-BE | ON/OFF 진입을 같은 Facade로 수렴시켜 실행 계약을 일치시킨다. |
| TO-BE | 거래 메타데이터로 외부 Worker TX의 readOnly·timeout 정책을 선택한다. |
| TO-BE | 공통 변환·검증 정책과 Facade 통합 테스트를 마련한다. |

## Anti Pattern

### Facade를 이름만 있는 전달 클래스로 만들기

모든 메서드가 타입 계약도 트랜잭션 정책도 없이 Service 한 줄만 호출하면 계층 비용만 늘어난다. 반대로 현재처럼 변환과 경계 선언이 있다면 단일 Service 호출이어도 유스케이스 경계로 의미가 있다.

### Facade에서 DAO를 직접 호출하기

빠르게 구현할 수 있어 보이지만 업무 흐름과 데이터 접근이 결합된다. Service 테스트와 재사용성이 떨어지고 트랜잭션 안의 업무 의미를 읽기 어려워진다.

### 모든 예외를 잡아 성공 DTO 반환하기

표준 오류와 롤백 신호가 사라진다. 일부 SQL이 반영된 상태에서 성공처럼 응답할 수 있으므로 가장 위험한 패턴 중 하나다.

### `@Transactional`이 보이면 그 줄에서 항상 BEGIN한다고 기록하기

상위 `TransactionTemplate`, 기본 `REQUIRED`, TCF·Timeout 모드를 무시한 설명이다. 실제 Thread와 최외곽 경계를 확인해야 한다.

### 내부 메서드 호출에 `REQUIRES_NEW`를 붙여 독립 거래라고 믿기

자기 호출은 프록시를 통과하지 않아 속성이 적용되지 않는다. 독립 경계가 필요하면 별도 Bean과 명확한 실패 계약으로 분리한다.

### null 본문을 빈 DTO로 만들었으므로 안전하다고 판단하기

변환 성공은 유효성 검증 성공이 아니다. 특히 수정·삭제 키가 null이면 광범위 변경이나 예상하지 못한 SQL 조건으로 이어질 수 있으므로 DAO 이전에 차단해야 한다.

## 실전 검증 시나리오

Facade 통합 테스트는 단순히 Service가 한 번 호출됐는지만 확인해서는 부족하다. 첫째, 정상 쓰기 요청에서 DB 변경과 이력이 함께 커밋되는지 확인한다. 둘째, Service의 RuntimeException과 checked Exception 각각에서 모든 변경이 롤백되는지 확인한다. 셋째, DTO 타입 불일치와 필수값 누락이 DAO 호출 전에 거부되는지 확인한다.

TCF 모드 검증은 별도로 수행한다. Timeout ON에서는 Worker Thread에서 실제 트랜잭션이 활성화되어 있는지, Facade가 동일 거래에 참여하는지 확인한다. Timeout OFF에서는 Facade 진입 시 거래가 시작되는지 확인한다. OFF Controller가 Facade를 호출하는 거래와 Service를 직접 호출하는 거래를 목록화하고 결과·롤백 차이를 테스트해야 한다.

조회는 반환 결과만 보지 말고 readOnly 적용 위치를 확인한다. Facade가 새 TX를 시작할 때와 Worker 외부 TX에 참여할 때 TransactionSynchronizationManager의 상태가 어떻게 다른지 검증하면 문서와 실행의 차이를 빠르게 찾을 수 있다. 외부 호출을 포함한 복합 유스케이스는 부분 성공, 재시도, 중복 호출 시나리오까지 포함한다.

## 운영 장애 추적

거래가 일부만 반영되었다면 GUID와 Service ID로 요청 로그를 모은 뒤 실행 모드부터 확인한다. TCF 활성 여부, Timeout Executor 종류, Worker Thread 이름을 확인하고 Facade 진입 로그와 Service 진입 로그를 비교한다. Facade 로그가 없고 Service만 보이면 OFF Controller 직접 호출 또는 다른 우회 경로를 의심한다.

트랜잭션 문제는 Annotation 목록보다 실제 경계로 추적한다. 사용한 TransactionManager가 `rdwTransactionManager`인지, 예외가 Facade 또는 Worker 밖까지 전파됐는지, 내부에서 정상 DTO로 바뀌지 않았는지 본다. Timeout이면 요청 응답 시각과 Worker 종료·ROLLBACK 시각을 분리한다.

입력 변환 오류는 원문 전체를 민감정보와 함께 로깅해서 해결하면 안 된다. GUID, Service ID, DTO 타입, 안전하게 마스킹한 필드와 표준 오류 코드로 추적한다. Jackson 예외 메시지가 내부 클래스 구조를 외부 응답에 노출하지 않도록 공통 예외 처리도 확인한다.

## 개발자·운영자 체크리스트

- Handler와 OFF Controller가 의도한 Facade 메서드를 호출하는가?
- Facade 메서드명과 Service ID의 행위 코드가 일치하는가?
- 일반 요청 본문이 정확한 거래별 `DTOin`으로 변환되는가?
- null 본문과 필수 필드 누락을 별도로 검증하는가?
- 조회와 쓰기의 트랜잭션 정책이 구분되어 있는가?
- `rdwTransactionManager`가 실제 DAO DataSource와 일치하는가?
- checked Exception까지 롤백해야 하는 쓰기에 정책이 선언되어 있는가?
- 예외를 잡아 성공값으로 바꾸는 코드가 없는가?
- 여러 Service 호출이 같은 자원과 전파 속성을 사용하는가?
- 외부 호출 실패에 멱등·보상·재처리 정책이 있는가?
- TCF ON/OFF, Timeout ON/OFF 조합별 통합 테스트가 있는가?
- 자기 호출로 별도 트랜잭션을 기대하는 메서드가 없는가?
- Facade에 SQL, HTTP 세부 처리, 대규모 업무 규칙이 섞이지 않았는가?
- GUID와 Service ID로 Facade 진입부터 커밋·롤백까지 추적할 수 있는가?

## 아키텍처 판단 포인트

Facade를 둘 것인지는 “Service 호출이 하나인가”로 결정하지 않는다. 외부 입력을 내부 타입으로 바꿔야 하는가, 유스케이스 단위의 원자성 선언이 필요한가, ON/OFF 여러 Adapter를 같은 실행 계약으로 수렴시켜야 하는가가 판단 기준이다. 이 중 하나라도 필요하면 Facade는 의미 있는 경계가 된다.

트랜잭션의 최외곽 위치는 응답 시간 제한과 원자성 범위를 함께 고려한다. Timeout Executor가 Dispatcher부터 전체 실행을 묶으면 늦은 커밋을 방지하기 쉽지만, 조회의 readOnly 같은 거래별 속성을 외부 실행기가 알아야 한다. Facade가 항상 시작하면 정책은 가까이 있지만 Worker deadline과 하나의 경계로 묶는 설계가 필요하다. 어느 쪽이든 문서, 설정, 소스, 테스트가 같은 모델을 말해야 한다.

Facade 공통화도 목적 중심으로 판단한다. 반복되는 변환 코드를 줄이는 것은 유용하지만 모든 거래를 반사 기반 범용 실행기로 만들면 타입과 흐름이 숨는다. 독자가 메서드 하나를 보고 입력 DTO, 호출 Service, 트랜잭션 정책을 알 수 있는 명시성을 보존하는 편이 운영 시스템에서는 더 중요할 수 있다.

## 핵심 정리

Business Facade는 Handler·Controller가 선택한 거래를 타입이 있는 유스케이스로 바꾸는 경계다. AS-IS 주요 Facade는 `Object` 본문을 거래별 DTO로 변환하고 Service를 호출하며 조회와 쓰기의 트랜잭션 의도를 Annotation으로 선언한다. 세부 업무 규칙과 SQL을 소유하는 계층은 아니다.

Facade의 `@Transactional`은 항상 최외곽 BEGIN을 의미하지 않는다. TCF ON + Timeout ON에서는 Worker의 `TransactionTemplate`이 먼저 시작하고 Facade는 참여한다. Timeout OFF 또는 OFF Controller가 Facade를 직접 호출하는 경로에서는 Facade 프록시가 시작점이 될 수 있다. Facade를 우회하면 그 경계의 변환·조정·트랜잭션 계약도 함께 우회된다.

정상적인 Facade는 예외를 숨기지 않고 유스케이스 실패를 최외곽 경계까지 전달한다. 여러 Service와 외부 시스템을 조정할 때는 물리 트랜잭션의 범위, 원격 호출의 비원자성, 자기 호출 프록시 우회까지 고려해야 한다. 다음 장에서는 Facade가 Service를 호출하는 순간 그 전후에 개입하는 `BizPrePostAspect`와 업무 선후처리가 어떤 조건에서 같은 트랜잭션에 참여하는지 살펴본다.
