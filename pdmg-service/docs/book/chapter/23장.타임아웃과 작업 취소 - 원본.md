# 제5부 트랜잭션과 타임아웃

# 23장. 타임아웃과 작업 취소

타임아웃은 “일정 시간이 지나면 모든 처리가 즉시 사라진다”는 기능이 아니다. UI 타이머는 화면의 대기를 끝내고, HTTP Client timeout은 Socket 대기를 끝내며, 서버 Executor timeout은 Future 대기를 끝낸다. JDBC Statement와 DB 세션이 실제로 멈추는지는 Driver, Statement 설정과 SQL 상태에 따라 별도로 결정된다.

PDMG의 온라인 Executor는 Request Thread와 Worker Thread를 분리하고 Worker 안에서 Transaction을 시작한다. Request Thread가 제한시간을 넘기면 `future.cancel(true)`로 interrupt를 요청한다. Worker는 업무 반환 뒤 deadline과 interrupt를 다시 검사해 늦은 Commit을 막으려 한다. 이 장은 “응답 timeout”과 “작업 종료”, “Rollback 완료”를 분리해 설명한다.

## 이 장에서 해결할 질문

- UI·HTTP Client·서버 Worker·DB Statement timeout은 각각 무엇을 제한하는가?
- PDMG 공통 timeout, Pool과 Queue 설정은 실제 어디에 연결되는가?
- 현재 서비스 ID별 timeout 우선순위가 구현되어 있는가?
- `Future.cancel(true)`는 Worker와 JDBC에 어떤 신호를 보내는가?
- 클라이언트가 Timeout 오류를 받은 순간 DB Rollback도 완료됐다고 볼 수 있는가?
- Pool 포화와 Queue 대기는 왜 Timeout과 다른 Overload 오류인가?
- ETF의 사후 시간검사가 작업 취소를 대신할 수 있는가?

## 전체 시간선

```text
Request Thread
  ├─ Context capture / 시작시각
  ├─ Worker Pool submit
  └─ Future.get(timeout)
       ├─ 정상 결과 → 반환
       ├─ 제한 초과 → cancel(true) → Timeout 예외
       └─ Pool 거절 → Overload 예외

Worker Thread
  ├─ Context install
  ├─ TransactionTemplate BEGIN
  ├─ Dispatcher → Handler → Facade → Service → DAO/JDBC
  ├─ 반환 뒤 deadline/interrupt 재검사
  ├─ COMMIT 또는 ROLLBACK
  └─ Context clear
```

## 23.1 타임아웃의 목적

온라인 timeout은 한 요청이 서버 자원을 무한히 점유하지 못하게 하고 사용자에게 예측 가능한 실패를 돌려주는 보호 장치다. 그러나 제한할 대상을 명확히 해야 한다. 화면의 기다림, 네트워크 연결, Worker 실행, SQL 실행과 Transaction 완료는 서로 다른 수명이다.

서버 Timeout의 핵심 목적은 Request Thread가 무한 대기하지 않게 하고, 늦게 끝난 Worker가 업무 변경을 Commit하지 못하도록 방어하는 것이다. 이를 위해 PDMG는 단순 ETF 사후 검사보다 Worker Transaction 바깥의 Future 대기와 내부 deadline 재검사를 사용한다.

Timeout 값이 너무 짧으면 정상 업무를 실패시키고 재시도 폭증을 만든다. 너무 길면 Worker·DB Connection이 고갈된다. 실제 지연 분포와 하위 시스템 timeout을 기준으로 정한다.

## 23.2 UI 타임아웃

UI timeout은 화면 Spinner, Promise 또는 요청 취소 정책을 끝낸다. 사용자가 더 기다리지 않게 할 뿐 서버 Worker와 DB가 자동 중단되는 것은 아니다. 브라우저가 연결을 끊어도 서버가 이미 업무를 실행 중일 수 있다.

UI는 Timeout 뒤 무조건 같은 쓰기 요청을 재전송하면 안 된다. 첫 요청의 결과가 불명일 수 있으므로 GUID·멱등키로 상태를 조회하거나 서버의 중복 방지 계약을 사용한다. 조회는 재시도가 비교적 안전하지만 부하가 높은 상태에서 즉시 반복하면 장애를 확대한다.

UI timeout은 서버보다 약간 길게 두어 서버 표준 Timeout 응답을 받을 기회를 주는 것이 일반적이다. 구체 값은 네트워크 지연과 응답 직렬화 시간을 포함해 측정한다.

## 23.3 HTTP Client 타임아웃

PDMG가 외부 시스템을 호출할 때의 connect timeout은 연결 수립, read/response timeout은 응답 대기를 제한한다. 이것들은 온라인 Executor의 전체 거래 deadline과 별개다. 외부 Client timeout이 전체 deadline보다 길면 Worker가 이미 취소 요청을 받은 뒤에도 Socket 대기가 남을 수 있다.

하위 timeout은 상위 deadline 안에 들어오도록 budget을 나눈다. 연결, 응답, 재시도와 로컬 DB 후처리 시간을 모두 합친다. 원격 요청이 timeout됐다고 상대 시스템이 처리하지 않았다고 단정할 수 없으므로 쓰기 외부 호출은 멱등성을 가져야 한다.

현행 주요 업무 Service의 외부 Client 호출과 공통 Client timeout 정책은 이 장의 소스 범위에서 확인되지 않았다. 따라서 구체 HTTP 값은 AS-IS로 만들지 않는다.

## 23.4 OnlineTimeoutExecutor

`TcfFacade.process`는 `OnlineTimeoutExecutor.execute`에 Dispatcher Callable을 넘긴다. `nhnis.fw.timeout.enabled=true`이면 `DefaultOnlineTimeoutExecutor`, false이거나 키가 없으면 `SyncOnlineTimeoutExecutor` Bean이 생성된다.

Default Executor는 Context와 MDC를 캡처하고 시작 시각·deadline을 계산한 뒤 고정 크기 Pool에 submit한다. Request Thread는 `future.get(milliseconds, MILLISECONDS)`로 기다린다. Worker는 동일 `rdwTransactionManager`의 TransactionTemplate 안에서 Callable을 실행한다.

Sync Executor는 현재 Thread에서 `action.call()`만 수행한다. Timeout 대기, Pool, cancel과 외부 TransactionTemplate가 없다. 설정을 끄면 단순히 제한시간만 사라지는 것이 아니라 Thread와 Transaction 시작 위치도 바뀐다.

## 23.5 공통 타임아웃 설정

`application.yml`의 현행 공통값은 다음과 같다.

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
      milliseconds: 5000
      pool-size: 20
      queue-capacity: 100
```

`OnlineTimeoutProperties` 기본값도 5000ms, Pool 20, Queue 100이며 `@PostConstruct`에서 milliseconds≥1, poolSize≥1, queueCapacity≥0을 검증한다. 설정 오류는 요청 시점이 아니라 기동 시 실패시킨다.

시간은 submit 이전에 계산되므로 Queue 대기 시간도 전체 5초 budget에 포함된다. Worker가 늦게 시작하면 실제 업무 실행에 남는 시간이 줄어든다.

## 23.6 서비스별 타임아웃

현재 `OnlineTimeoutProperties`에는 공통 `milliseconds`만 있고 서비스별 Map이나 `resolveMilliseconds(serviceId)` 메서드가 없다. Default Executor도 `properties.getMilliseconds()`만 사용한다. 따라서 현재 실행 가능한 AS-IS는 공통값 방식이다.

그런데 `etf` 소스는 `timeoutProperties.resolveMilliseconds(serviceId)`를 호출한다. 현재 Properties와 API가 일치하지 않으므로 이 소스 조합은 컴파일 정합성 확인이 필요하다. 또한 `TcfFacade`는 ETF를 직접 호출하지 않는다. ETF 설명을 서비스별 timeout이 이미 작동하는 근거로 사용하면 안 된다.

서비스별 10초 같은 정책을 도입하려면 기본값, exact Service ID override, 업무군 override의 우선순위를 명시하고 Executor와 ETF가 같은 Resolver를 사용하게 해야 한다. 설정 오타와 미등록 ID는 공통값으로 fallback할지 기동 실패시킬지 결정한다. 이는 TO-BE다.

## 23.7 요청 Thread와 Worker Thread

Request Thread는 Worker 작업을 제출하고 결과를 기다린다. Worker는 Context를 설치하고 DB Transaction을 소유한다. 두 Thread는 같은 GUID로 연결되지만 같은 ThreadLocal이나 JDBC Connection을 자동 공유하지 않는다.

```text
Request: Future.get(5000ms) ─────────┐
                                     │
Worker : queue → Context/TX → 업무 ──┘
```

Worker Context는 finally에서 clear된다. Request Thread가 Timeout 응답을 준비하는 동안 Worker가 아직 JDBC에서 실행 중일 수 있다. 운영 로그는 Thread와 시각을 함께 봐야 한다.

## 23.8 작업 취소 요청

Request Thread가 `TimeoutException`을 받으면 `future.cancel(true)`를 호출한다. true는 실행 중인 Worker Thread에 interrupt를 전달하려는 요청이다. Future가 아직 Queue에 있으면 실행을 막을 수 있고, 실행 중이면 코드가 interrupt에 협조해야 한다.

interrupt는 강제 Thread kill이 아니다. `Thread.sleep`, `wait`처럼 interruptible API는 예외로 반응할 수 있지만 CPU loop가 flag를 확인하지 않으면 계속 실행한다. catch한 `InterruptedException`을 복원만 하고 업무를 계속하면 취소가 지연된다.

현행 `mgcoa5530Service`의 시험용 sleep은 InterruptedException을 catch해 flag를 복원한 뒤 DAO로 계속 진행한다. Worker의 반환 후 재검사가 Commit을 막을 수 있지만 불필요한 SQL 실행은 생길 수 있는 AS-IS 위험이다.

## 23.9 JDBC 작업 중단의 한계

Thread interrupt가 JDBC Driver의 실행 중 Statement를 즉시 취소한다는 보장은 없다. Driver가 interrupt에 반응하지 않거나 DB 서버가 SQL을 계속 실행하면 Worker는 Statement 반환을 기다린다. `Future.cancel(true)` 성공값도 DB 세션 종료 완료를 의미하지 않는다.

SQL 중단을 강화하려면 JDBC query timeout, Driver socket/read timeout, DB Resource Manager와 Statement cancel 지원을 실제 Driver로 검증한다. 각 기능은 적용 범위와 오류가 다르다. 현재 Mapper별 SQL timeout 설정은 확인되지 않았다.

DB에서 변경 SQL이 끝난 뒤 Worker가 deadline을 발견하면 Transaction rollback으로 결과를 취소할 수 있다. 하지만 외부 시스템 호출은 JDBC rollback 대상이 아니다.

## 23.10 트랜잭션 롤백 조건

Worker TransactionTemplate는 정상 Callable 반환 뒤 deadline 초과 또는 interrupt 상태를 검사한다. 해당되면 rollback-only를 설정하고 OnlineTimeoutException을 던진다. OnlineTimeoutException·OverloadException, RuntimeException, checked Exception wrapper에도 rollback-only를 표시한다.

```text
업무 반환
  ├─ deadline 전 & not interrupted → COMMIT
  └─ deadline 초과 또는 interrupted
       → rollbackOnly → Timeout 예외 → ROLLBACK
```

따라서 SQL이 늦게 정상 반환해도 늦은 Commit을 막는 방어가 있다. 그러나 Request Thread가 Timeout 응답을 만든 순간 Worker Rollback이 이미 완료됐다고 단정할 수 없다. Worker가 제어권을 되찾아 검사하고 Transaction을 종료해야 한다.

Worker 코드가 영원히 반환하지 않으면 이 재검사도 실행되지 않는다. DB와 네트워크 계층의 하위 timeout이 필요한 이유다.

## 23.11 ETF 사후 타임아웃의 한계

ETF의 경과시간 검사는 업무가 끝난 뒤 “이미 오래 걸렸다”는 사실을 발견한다. 작업 실행 중 Request 대기를 끊거나 Statement를 취소하지 못한다. ETF가 Transaction 안에서 예외를 던진다면 Commit 전 rollback 신호가 될 수 있지만 호출 위치가 중요하다.

현재 `TcfFacade` 호출선에는 ETF 호출이 없고 ETF의 resolver API도 Properties와 불일치한다. 따라서 현행 강제 timeout은 Default Executor를 기준으로 설명한다. ETF는 구현 정합성을 보완한 뒤 사후 안전망으로 사용할 수 있는 설계 요소다.

사후 검사만 두고 “5초에 작업 중단”이라고 설명하면 운영자가 실제 Worker 잔존을 놓친다.

## 23.12 TimeoutExecutor와 트랜잭션 경계

Timeout과 Transaction을 결합한 핵심은 Worker의 Callable 전체를 TransactionTemplate 안에 넣은 것이다. Dispatcher, Handler, Facade, Service, DAO와 정상 업무 후처리가 같은 Worker TX에 참여한다.

Request Thread는 이 DB TX를 소유하지 않는다. Timeout 예외를 HTTP 오류로 바꾸는 일과 Worker Rollback은 서로 다른 Thread에서 진행될 수 있다. 시스템 Response 후처리와 ImageLog도 일반적으로 업무 Worker TX 밖이다.

Timeout disabled 시 이 외부 경계가 사라지고 Facade/Service Proxy가 Transaction 시작점이 된다. 설정 전환은 성능 기능뿐 아니라 Transaction topology 변경이다.

## 23.13 Pool과 Queue 관리

현행 Executor는 core=max=`pool-size`인 고정 Pool, bounded Queue와 AbortPolicy를 사용한다. 20개가 실행 중이고 Queue 100개가 가득 차면 새 submit이 거절되고 `OnlineOverloadException`으로 변환된다.

Overload는 제한시간을 기다린 Timeout과 다르다. 실행 자리를 받지 못한 즉시 실패이며 GlobalExceptionHandler도 별도 handler를 가진다. 클라이언트는 무차별 즉시 재시도 대신 backoff와 jitter를 사용해야 한다.

Queue가 너무 크면 거절은 늦어지지만 작업이 Queue에서 timeout budget을 소비해 시작 직후 deadline을 넘긴다. 너무 작으면 순간 burst를 흡수하지 못한다. Pool 크기는 DB Connection Pool, 평균·p99 실행시간과 하위 시스템 수용량에 맞춘다.

shutdown에서는 작업 완료를 기다리고 최대 30초 termination을 설정한다. 배포 시 장기 JDBC 작업이 있으면 종료 동작을 관찰한다.

## 23.14 권장 타임아웃 조합

상위 제한은 하위 제한보다 길게 배치해 서버가 먼저 표준 실패를 만들 여유를 둔다. 예시는 다음 원칙이지 현행 고정값이 아니다.

```text
DB Statement / 외부 Client timeout
       < 서버 온라인 deadline
       < Gateway/HTTP Client timeout
       < UI 사용자 대기 한계
```

각 계층 사이에는 Queue, 네트워크와 응답 직렬화 margin을 둔다. 쓰기 재시도에는 멱등키가 필요하다. 서비스별 값은 실제 p99와 업무 SLA로 결정하되 Pool 보호를 해치지 않도록 상한을 둔다.

## End-to-End 정상·Timeout·Overload

```text
정상: submit → Worker TX → 업무 → deadline 통과 → COMMIT → Future 결과

Timeout: submit → Worker 실행/JDBC 대기
         Request future.get 초과 → cancel(true) → Timeout 응답
         Worker가 나중에 복귀 → interrupt/deadline → ROLLBACK

Overload: Pool busy + Queue full → submit 거절
          Worker/TX 시작 안 함 → Overload 응답
```

## 책임과 경계

| 계층 | 끊는 대상 | DB 중단 보장 |
|---|---|---|
| UI | 사용자·화면 대기 | 없음 |
| HTTP Client/Gateway | 네트워크 응답 대기 | 없음 |
| Online Executor | Request의 Future 대기·Worker 취소 요청 | 간접적 |
| Thread interrupt | 협조적 Java 실행 | Driver 의존 |
| JDBC timeout/cancel | Statement 실행 | Driver·DB 검증 필요 |
| Transaction rollback | 완료된 DB 변경의 Commit 방지 | Worker 제어 복귀 필요 |

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | 공통 5000ms, Pool 20, Queue 100, AbortPolicy |
| AS-IS | Queue 대기 포함 deadline과 Future.get timeout |
| AS-IS | cancel(true), Worker 반환 후 deadline/interrupt 재검사 |
| AS-IS | 공통 timeout만 구현, 서비스별 resolver 없음 |
| AS-IS 결함 | ETF가 존재하지 않는 `resolveMilliseconds` 호출, TcfFacade 미연결 |
| 제약 | JDBC 즉시 중단·SQL별 timeout 보장 없음 |
| TO-BE | 단일 Resolver로 공통/서비스별 우선순위 통합 |
| TO-BE | JDBC·Client 하위 timeout, 멱등·재시도, Pool 부하 테스트 |

## Anti Pattern

“5초 후 DB가 무조건 중단되고 Rollback 완료”라고 문서화하지 않는다. UI Abort를 서버 취소로, interrupt를 Thread kill로, Future cancel 반환값을 DB 종료 증거로 해석하면 안 된다.

Queue를 무한대로 키우거나 Timeout마다 즉시 재시도하면 장애를 증폭한다. Service에서 InterruptedException을 삼키고 SQL을 계속하는 것도 취소 협력을 깨뜨린다. ETF 사후 검사만으로 실행 중단을 보장한다고 생각하지 않는다.

## 실전 검증 시나리오

Sleep처럼 interrupt에 반응하는 작업, CPU loop, 느린 SQL과 외부 Socket을 각각 시험한다. Request 응답 시각, cancel 시각, Worker 제어 복귀, Rollback 완료와 DB 행 상태를 따로 기록한다. 늦게 정상 반환한 작업이 Commit되지 않는지 확인한다.

Pool 20과 Queue 100을 채워 121번째 수준의 요청에서 Overload가 발생하는지, Queue 대기가 timeout에 포함되는지 부하 테스트한다. 실제 동시 타이밍에 따라 순번은 달라질 수 있으므로 활성·Queue metric으로 판정한다.

설정 0·음수 기동 실패, enabled false의 Sync 경로, checked/runtime 예외 rollback도 검증한다. ETF는 현재 컴파일/API 정합성과 호출 연결을 별도 확인한다.

## 개발자·운영자 체크리스트

- UI·Gateway·서버·JDBC timeout 값을 각각 문서화했는가?
- 공통 milliseconds와 실제 Executor Bean을 확인했는가?
- Queue 대기가 전체 deadline에 포함됨을 반영했는가?
- 서비스별 설정이 실제 구현된 것인지 설계안인지 구분했는가?
- interrupt catch 뒤 즉시 중단 또는 재전파하는가?
- SQL Driver의 query/socket timeout을 실제 검증했는가?
- Timeout 응답과 Worker Rollback 완료를 별도 지표로 보는가?
- Overload와 Timeout 오류를 구분하는가?
- Pool 크기가 DB Pool을 과도하게 경쟁하지 않는가?
- 쓰기 재시도에 GUID·멱등 정책이 있는가?
- 늦은 Commit 방지 통합 테스트가 있는가?

## 아키텍처 판단 포인트와 다음 장

Timeout 설계는 숫자 하나가 아니라 계층별 시간 budget, 취소 협력과 원자성의 조합이다. 온라인 Executor는 늦은 Commit을 방어하지만 하위 I/O를 즉시 죽이는 장치는 아니다. Pool과 Queue는 처리량보다 하위 자원 보호를 기준으로 정한다.

서비스별 timeout을 추가할 때 Executor와 ETF가 서로 다른 값을 계산하지 않도록 단일 Resolver를 둔다. 설정 우선순위와 fallback을 테스트로 고정한다.

다음 장에서는 요청이 Worker로 들어가기 전에 사용자를 인증하는 JWT 전체 구조, 서명 주체와 Public Key 검증, Access·Refresh Token의 책임을 다룬다. 인증 HTTP 호출 자체에도 이 장에서 구분한 Client timeout이 별도로 필요하다.
