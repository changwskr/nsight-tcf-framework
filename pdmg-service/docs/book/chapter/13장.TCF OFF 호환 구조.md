# 제3부 온라인 요청과 TCF 프레임워크

# 13장. TCF OFF 호환 구조

TCF를 끈다는 말은 PDMG Framework 전체를 끈다는 뜻이 아니다. `nhnis.fw.tcf.enabled=false`는 공통 Online Controller, TcfFacade, Dispatcher와 Handler Registry를 사용하지 않고 업무별 Spring MVC Controller로 진입점을 바꾸는 선택이다. Filter, ServiceContext, Interceptor, ResponseBodyAdvice, DataSource와 TransactionManager는 각각의 조건이 켜져 있으면 그대로 남을 수 있다.

이 구분이 중요한 이유는 TCF OFF가 단순한 개발 편의 스위치가 아니라 실행 Architecture를 바꾸기 때문이다. ON에서는 Handler가 업무 Facade를 호출하고, Timeout ON이면 Worker의 TransactionTemplate가 최외곽 Transaction을 연다. OFF에서는 업무 Controller가 Facade 또는 Service를 직접 호출한다. 어느 객체를 호출하는지에 따라 Transaction 시작점, DTO 변환, Timeout, 예외 응답과 업무 선후처리의 포함 범위가 달라진다.

현행 PDMG OFF Controller도 하나의 방식으로 통일돼 있지 않다. `mgcoa9100Controller`는 Facade를 호출하지만 `mgcoa5530`, `mgcoa8888`, `mgcoa9000`, `mgcoa9001`, `mgcoa9999Controller`는 Service를 직접 주입한다. 이 가운데 `mgcoa9001Service`에는 메서드별 `@Transactional`이 있지만 다른 Service에는 같은 선언이 확인되지 않는다. 따라서 “TCF OFF의 Transaction은 항상 Facade 또는 항상 Service에서 시작한다”는 설명은 현재 사실이 아니다.

이 장은 OFF를 ON의 축소판으로 설명하지 않는다. 실제 조건부 Bean, Controller별 호출선과 유지되는 공통 Web 처리를 기준으로 호환 구조를 분석하고, 두 모드가 동일한 업무 핵심 계층을 공유하도록 만드는 권장 경계를 제시한다.

## 이 장에서 해결할 질문

- TCF OFF에서 사라지는 Bean과 그대로 남는 공통 처리는 무엇인가?
- 업무 URL은 어떤 Controller로 연결되고 DTO는 어떻게 전달되는가?
- Controller가 Facade를 호출할 때 Transaction은 어디서 시작되는가?
- Controller가 Service를 직접 호출하면 무엇을 우회하며 실제 Transaction은 존재하는가?
- BizPrePostAspect는 OFF에서도 실행되고 같은 Transaction에 포함되는가?
- `nhnis.fw.timeout.enabled=true`여도 OFF 요청에는 왜 TCF Timeout이 적용되지 않는가?
- TCF 조건부 `GlobalExceptionHandler`가 사라지면 오류 응답은 어떻게 달라질 수 있는가?
- ON/OFF 업무 로직을 중복하지 않고 하나의 Facade·Service·DAO를 공유하려면 어떻게 해야 하는가?

## ON/OFF 실행 지도

```text
TCF ON
HTTP → Filter/Interceptor → OnlineTransactionController
  → TcfFacade → TimeoutExecutor → Dispatcher → Handler
  → Business Facade → Service → DAO
  → Response Advice / afterCompletion

TCF OFF AS-IS
HTTP → Filter/Interceptor → Business Controller
  ├─ 대부분: Service → DAO
  └─ mgcoa9100: Facade → Service
  → Response Advice / afterCompletion
```

진입 Adapter는 다르지만 업무 핵심을 공유하는 목표 구조는 다음과 같다.

```text
ON : OnlineController → Handler ─┐
                                 ├→ Business Facade → Service → DAO
OFF: Business Controller ────────┘
```

## 13.1 TCF OFF의 목적

TCF OFF는 공통 Service ID Registry와 Handler 라우팅 없이 기존 업무별 URL과 typed Controller를 사용하는 호환 경로다. 레거시 Controller를 유지하거나 TCF 전환 전후 결과를 비교하고, Framework Core 장애를 분리해 업무 계층을 확인하는 데 사용할 수 있다. 하지만 운영에서 사용할 경우 ON과 같은 보안·Transaction·Timeout·오류 계약을 별도로 검증해야 한다.

설정은 다음과 같으며 Spring Bean 구성이 바뀌므로 재기동이 필요하다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: false
```

OFF의 핵심은 “업무를 실행하지 않는다”가 아니라 “다른 Entry Adapter로 같은 업무를 실행한다”는 것이다. 따라서 Controller 아래 Facade·Service·DAO를 ON과 공유해야 호환 가치가 생긴다. OFF 전용 Service나 SQL을 별도로 만들면 두 경로가 시간이 지나며 다른 결과를 내고, 전환 Test도 신뢰할 수 없게 된다.

OFF를 Local 개발 전용으로 사용할지 운영 비상 경로로 허용할지도 먼저 정한다. 개발 전용이라면 운영 Profile에서 OFF 기동을 막고 문서화할 수 있다. 운영 비상 경로라면 인증, 거래통제, Timeout, 용량 제한, Transaction과 오류 응답을 ON과 동등하게 갖춰야 한다. “비상”이라는 이름은 검증을 생략할 근거가 아니다.

## 13.2 비활성화되는 컴포넌트

TCF Core Bean들은 `@ConditionalOnProperty(name="nhnis.fw.tcf.enabled", havingValue="true")` 조건을 사용한다. OFF에서는 OnlineTransactionController, TcfFacade, TransactionDispatcher, STF, ETF와 업무 TransactionHandler가 생성되지 않는다. TCF 조건의 `GlobalExceptionHandler`도 비활성화된다.

| 구성요소 | ON | OFF | 영향 |
|---|---:|---:|---|
| OnlineTransactionController | 생성 | 미생성 | `/online` 공통 진입 사라짐 |
| TcfFacade | 생성 | 미생성 | Context·Executor 연결 우회 |
| TransactionDispatcher | 생성 | 미생성 | Service ID Registry 없음 |
| 업무 Handler | 생성 | 미생성 | Handler 분기 없음 |
| STF·ETF | 생성, 현재 미연결 | 미생성 | TCF 확장점 자체 없음 |
| TCF GlobalExceptionHandler | 생성 | 미생성 | 오류 변환 경로 변화 가능 |
| 업무 Controller | 미생성 | 생성 | 직접 URL 활성화 |

반면 Filter와 Interceptor는 TCF Property가 아니라 `nhnis.fw.commons.filter.enabled`, `nhnis.fw.commons.legacy-web.enabled` 같은 별도 조건에 따른다. ResponseBodyAdvice도 legacy-web 조건을 사용한다. DataSource와 `rdwTransactionManager`, Service, DAO와 Mapper 역시 TCF OFF만으로 사라지지 않는다.

```text
TCF OFF ≠ commons OFF

남을 수 있음:
DefaultFilter → JWT/Body/ServiceContext
Interceptor → Header/GUID/ImageLog
ResponseBodyAdvice → 표준 응답
BizPrePostAspect → Service 선후 로그
DataSource/TransactionManager → 선언된 TX 지원
```

Bean 존재와 요청 적용도 구분해야 한다. Timeout Executor Bean이 timeout Property에 따라 생성돼도 OFF Controller가 TcfFacade를 우회하면 그 Executor는 업무 요청을 감싸지 않는다. TransactionManager가 존재해도 호출선에 `@Transactional` Proxy가 없으면 유스케이스 Transaction은 시작되지 않는다.

## 13.3 직접 Controller 호출

OFF 업무 Controller는 `havingValue="false", matchIfMissing=true` 조건으로 생성된다. `/mgcoa9000S0`, `/mgcoa9000C0`처럼 Service ID별 `@PostMapping`이 HTTP 진입점이다. Spring MVC가 요청 JSON을 typed DTO로 변환하고 Controller Method가 업무 객체를 호출한다.

```text
POST /mgcoa9000C0
  → mgcoa9000Controller.mgcoa9000C0(DTOin)
  → mgcoa9000Service.mgcoa9000C0(input)   AS-IS
```

TCF ON 공통 Controller는 최상위 Map에서 `dto` Node를 추출해 Handler/Facade에 Object로 넘긴다. OFF Controller는 `@RequestBody mgcoa9000C0DTOin`처럼 typed DTO를 바로 받는다. 따라서 같은 Wire JSON을 ON/OFF 양쪽에서 사용할 수 있는지 실제 Body 계약을 비교해야 한다. Filter와 Advice가 표준 `{hdr_nhnis,dto}` 봉투를 처리하더라도 Controller Parameter가 어느 Node로 변환되는지는 Mapping과 Resolver 구현에 따라 확인해야 한다.

직접 URL은 Dispatcher Registry 검사를 거치지 않는다. Mapping이 없으면 404이고, 같은 Mapping 충돌은 Spring MVC 기동 문제로 나타날 수 있다. 신규 Service ID를 ON Handler에만 추가하면 OFF에서는 호출할 Controller Method가 없다. 두 모드를 지원한다면 Service Catalog, Handler 등록과 Controller Mapping을 함께 검증해야 한다.

Controller는 HTTP Adapter다. Request Binding, Validation, 응답 Status와 Facade 호출까지만 담당하고 업무 계산·SQL·Transaction 정책을 넣지 않는 편이 좋다. 상세 역할은 다음 장에서 다룬다.

## 13.4 Controller에서 Facade 호출

권장 OFF 경로는 Controller가 ON Handler와 같은 Business Facade를 호출하는 구조다. Facade가 DTO 변환, 유스케이스 조정과 Transaction 경계를 소유하면 진입 Adapter만 달라지고 업무 핵심은 같다.

```text
Controller
  → Facade Proxy
      TX BEGIN
      → Service
          → BizPrePostAspect
          → Rule/DAO
      COMMIT / ROLLBACK
```

현행 `mgcoa9100Controller`는 Facade를 직접 주입하는 사례다. 다만 `mgcoa9100Facade` 메서드 자체에는 현재 `@Transactional`이 확인되지 않으므로 “Facade를 호출한다”는 사실만으로 Transaction이 시작된다고 단정하면 안 된다. 조회·진단 성격이라 DML Transaction이 필요 없는지 업무 요구와 소스를 함께 본다.

다른 업무 Facade에는 `rdwTransactionManager`와 readOnly 또는 `rollbackFor=Exception.class` 선언이 있다. OFF Controller가 이 Facade Proxy를 호출하도록 바꾸면 Handler를 거치는 ON과 같은 업무 경계를 재사용할 수 있다. Facade Method가 Object를 받아 ObjectMapper로 typed DTO를 만드는 구조라면 OFF typed DTO를 직접 넘겨도 변환 가능한지 Test해야 한다.

Controller에 `@Transactional`을 붙이는 것도 기술적으로 가능하지만 HTTP Adapter가 Transaction 정책을 소유하고 Controller 반환까지 Connection을 점유한다. Interceptor Pre는 Controller보다 앞이고 Response Advice와 afterCompletion은 뒤이므로 Controller Transaction에도 포함되지 않는다. ON/OFF 공통화를 위해서는 Facade 경계가 더 일관적이다.

## 13.5 Service 직접 호출의 문제

현행 OFF Controller 중 `mgcoa5530`, `mgcoa8888`, `mgcoa9000`, `mgcoa9001`, `mgcoa9999`는 Service를 직접 주입한다. 이 경로는 ON Handler가 사용하는 Facade를 우회한다. 결과적으로 Facade의 DTO 변환, 유스케이스 조정과 `@Transactional`이 적용되지 않는다.

| OFF Controller | AS-IS 호출 | Service 자체 TX | Facade TX 우회 영향 |
|---|---|---:|---|
| mgcoa5530 | Service | 확인 안 됨 | 조회 Facade readOnly 우회 |
| mgcoa8888 | Service | 확인 안 됨 | 조회/삭제 Facade TX 우회 |
| mgcoa9000 | Service | 확인 안 됨 | C/U/D 유스케이스 TX 부재 가능 |
| mgcoa9001 | Service | 있음 | Service TX로 동작, ON과 경계 차이 |
| mgcoa9999 | Service | 확인 안 됨 | 조회 Facade readOnly 우회 |
| mgcoa9100 | Facade | Facade TX 없음 | Facade 경유지만 TX 별도 판단 |

`mgcoa9001Service`는 조회 readOnly와 쓰기 rollback Transaction이 메서드에 선언돼 있어 Service 직접 호출에서도 Transaction이 시작될 수 있다. 반대로 `mgcoa9000Service`에 같은 선언이 없다면 등록 과정의 여러 DAO 호출이 하나의 업무 Transaction으로 묶이지 않을 수 있다. 이 차이가 “OFF Transaction 시작점은 Controller 또는 Service”처럼 하나로 말할 수 없는 이유다.

Service 직접 호출은 업무 선후 Aspect를 우회하지는 않는다. Pointcut이 Service public Method이므로 Proxy 호출이면 Aspect가 적용될 수 있다. 그러나 Aspect 실행과 Transaction 존재는 별개다. 상위 Facade TX가 없고 Service에도 TX가 없다면 Aspect 전후에 DML을 추가해도 하나의 원자적 경계가 되지 않는다.

## 13.6 TCF OFF 트랜잭션

TCF OFF는 Spring Transaction 기능을 끄는 스위치가 아니다. `rdwTransactionManager`는 남아 있으며 실제 BEGIN은 호출선에서 처음 만나는 유효한 `@Transactional` Proxy가 결정한다.

```text
OFF + Controller → Facade(@Transactional)
  → Facade 진입 시 BEGIN

OFF + Controller → Service(@Transactional)
  → Service 진입 시 BEGIN

OFF + Controller → Service(TX 없음)
  → 유스케이스 전체 TX 없음
```

AS-IS에서는 Controller별로 두 번째와 세 번째 유형이 섞여 있고 `mgcoa9100`은 Facade를 경유하지만 Facade Annotation 여부를 별도 판단해야 한다. 따라서 설정표만 보고 Transaction을 설명하지 말고 실제 Controller Field, 호출 Method와 대상 Annotation을 순서대로 추적한다.

쓰기 거래에서는 SELECT 후 INSERT, Header 저장 후 Detail 저장처럼 두 SQL 사이에 예외를 발생시키고 모두 Rollback되는지 통합 Test해야 한다. Test Method의 상위 `@Transactional`이 결과를 자동 Rollback하면 운영 경계 결함을 숨길 수 있으므로 HTTP 또는 비 Transaction Test에서 별도 Connection으로 결과를 확인한다.

Controller Transaction은 업무 선후처리를 포함할 수 있지만 Web Adapter에 정책을 둔다는 비용이 있다. Service Transaction은 Service Method만 감싸므로 Facade의 여러 Service 조정 전체를 하나로 묶지 못할 수 있다. 공통 Business Facade가 유스케이스 Transaction을 소유하는 구조가 ON/OFF 차이를 가장 줄인다.

## 13.7 TCF OFF 업무 선후처리

`BizPrePostAspect`의 Pointcut은 `application.service` 아래 public Method다. TCF ON/OFF와 직접 연결된 조건이 아니라 legacy-web 설정에 의존한다. 따라서 OFF Controller가 Service Proxy를 호출하면 업무 선처리와 정상 반환 후처리 로그가 실행될 수 있다.

```text
Controller → Service Proxy
  → BizPrePostAspect.before
  → Service
  → BizPrePostAspect.afterReturning
```

예외가 발생하면 `@AfterReturning` 후처리는 실행되지 않는다. 그리고 Aspect가 Transaction 안인지 밖인지는 Advisor 순서와 상위 Transaction 경계에 달려 있다. Facade Transaction 안에서 Service를 호출하면 업무 선후처리가 같은 Transaction 범위에 들어갈 수 있다. Service 자체에서 Transaction을 시작하면 Aspect와 Transaction Advisor의 Order에 따라 포함 범위를 검증해야 한다.

현행 Aspect는 주로 GUID, Service ID, Method와 BRC 및 응답 DTO를 로그에 남긴다. 향후 업무 후처리에 UPDATE를 추가한다면 OFF의 Service 직접 호출 경로에서도 앞선 DML과 같은 Transaction인지 반드시 Test한다. 로그가 같은 HTTP 요청에 찍힌다는 사실은 같은 DB Transaction의 증거가 아니다.

## 13.8 시스템 선후처리 변화

Filter와 Interceptor, ResponseBodyAdvice는 TCF와 독립된 MVC 확장점이다. 각 설정이 활성화돼 있으면 OFF에서도 요청 Body Cache, JWT 검증, ServiceContext와 GUID, Pre/Post ImageLog와 표준 응답 조립이 유지될 수 있다.

```text
TCF OFF + commons ON
DefaultFilter
  → ServicePreventionInterceptor
  → Business Controller
  → Service/Facade
  → ResponseBodyAdvice
  → afterCompletion
```

STF와 ETF는 TCF ON Bean이므로 OFF에서 사라진다. 다만 앞 장에서 확인한 것처럼 ON에서도 현행 TcfFacade 호출선에 연결되지 않았다. 따라서 OFF 전환으로 실제 실행 중이던 STF 거래통제가 없어졌다고 표현하기보다, TCF 확장 Bean 자체가 생성되지 않는다고 정확히 말해야 한다.

Filter를 별도로 끄면 Context가 없고 Interceptor가 Warning 후 허용할 수 있다. legacy-web을 끄면 Interceptor와 ResponseBodyAdvice도 달라진다. `tcf.enabled=false` 하나만으로 이 결과를 추론하지 말고 Profile별 Property 조합과 Bean 목록을 확인한다.

## 13.9 타임아웃 처리

OFF Controller는 TcfFacade를 호출하지 않으므로 `OnlineTimeoutExecutor.execute()`를 거치지 않는다. `nhnis.fw.timeout.enabled=true`이고 Executor Bean이 존재해도 직접 Controller 요청에는 Worker Pool, Queue 용량, Future 제한시간과 Worker TransactionTemplate가 적용되지 않는다.

```text
ON + timeout ON
Request Thread → TcfFacade → Worker + Deadline + TX

OFF
Request Thread → Business Controller → Facade/Service
                         TCF Executor 우회
```

OFF에도 다른 제한시간은 존재할 수 있다. Servlet Container, Reverse Proxy, UI HTTP Client, JDBC Query Timeout와 `@Transactional(timeout=...)`은 별도다. 그러나 이 값들은 같은 구간을 제한하지 않는다. Client가 응답 대기를 중단해도 Server 업무가 계속될 수 있고, Transaction Timeout이 설정돼도 실행 중인 SQL이 Driver 수준에서 즉시 중단된다고 보장할 수 없다.

OFF 운영을 허용한다면 공통 Timeout 부재를 의도된 차이로 둘지 별도 Adapter로 보완할지 결정한다. TCF Executor를 Controller마다 직접 호출하도록 복제하기보다 Facade 앞 공통 실행 Adapter 또는 ON 경로 사용을 우선 검토한다. ON/OFF에서 제한시간과 overload 응답이 다르면 UI 계약에도 반영해야 한다.

## 13.10 예외처리 영향

TCF `GlobalExceptionHandler`는 TCF ON 조건부 Bean이므로 OFF에서 생성되지 않는다. legacy-web의 `ResponseBodyArgumentResolver`가 가진 `NhBaseException` Handler나 다른 Advice가 남을 수 있지만, 모든 예외 Type이 ON과 동일한 HTTP Status와 `result` 구조로 변환된다고 단정할 수 없다.

| 예외 위치 | ON | OFF 영향 |
|---|---|---|
| Registry 미등록 | TCF Handler가 표준화 | Registry 자체 없음 |
| 업무 BizException | TCF Global Handler 경로 | 남은 Advice 적용 여부 확인 |
| Runtime Exception | 공통 TCF 변환 가능 | MVC 기본 오류로 갈 수 있음 |
| Timeout/Overload | TCF 전용 예외 | TCF Executor 미적용 |
| Filter sendError | TCF 전후 모두 MVC 이전 | Advice 미통과 가능 |

오류 응답 차이는 UI에서 치명적일 수 있다. ON에서는 `{hdr_nhnis,result}`인데 OFF에서는 `/error` 기본 Body나 다른 Status가 나오면 동일 화면이 처리하지 못한다. 정상 응답만 비교하지 말고 Validation, checked Exception, Runtime Exception, DB 오류와 인증 실패를 모드별로 호출해 Wire JSON과 Status를 비교한다.

예외를 OFF Controller에서 잡아 정상 DTO로 바꾸면 Service Transaction이 예외를 이미 밖으로 던진 뒤인지, Controller가 Rollback 원인을 숨기는지 확인한다. Transaction 경계 안에서 예외를 삼키면 Commit 위험이 있다. 오류 표준화는 Transaction 완료와 원인 보존 뒤 Web Advice에서 수행하는 편이 안전하다.

## 13.11 TCF ON/OFF 공통 구조 유지 방법

가장 중요한 원칙은 Entry Adapter만 다르고 Business Facade 아래를 공유하는 것이다. ON Handler와 OFF Controller가 같은 Facade Method를 호출하면 DTO 변환, Transaction, Service, Rule와 DAO가 하나의 구현에 모인다.

```text
TCF ON
OnlineController → Handler ─────────┐
                                    ▼
                              Business Facade
                                    │
TCF OFF                             ▼
Business Controller ─────────────→ Service → DAO
```

전환 순서는 먼저 현재 OFF Controller별 Service 호출을 목록화하고 대응 Facade Method가 있는지 확인한다. typed DTO가 Facade의 Object 변환과 호환되는지 Test한 뒤 Controller 주입 대상을 Facade로 바꾼다. 읽기 `readOnly`, 쓰기 rollbackFor와 TransactionManager를 확인하고 ON/OFF 동일 입력의 업무 결과와 DB 상태를 비교한다.

Facade를 공유해도 Timeout과 Registry, 공통 예외는 자동으로 같아지지 않는다. 이 차이는 명시적인 모드 계약으로 남기거나 공통 Adapter로 보완한다. 모든 차이를 업무 코드에 if 문으로 넣지 않는다. 환경별 분기는 진입 Configuration과 Adapter에 한정해야 한다.

### 마이그레이션 절차

1. OFF Controller의 Mapping과 호출 Service를 Inventory로 만든다.
2. ON Handler가 호출하는 대응 Facade Method를 찾는다.
3. Facade 입력이 typed DTO와 Map/Object를 모두 안전하게 처리하는지 검증한다.
4. Controller를 Facade 호출로 변경하고 Controller의 업무 로직을 제거한다.
5. 조회 readOnly와 쓰기 rollback 규칙을 통합 Test한다.
6. 업무 선후처리가 Facade Transaction 안에 들어가는지 확인한다.
7. 정상·오류 응답의 ON/OFF Wire 계약을 비교한다.
8. Timeout 부재와 예외 Handler 차이를 운영 정책에 기록한다.

## 설정 조합별 실행 결과

TCF OFF의 결과는 `tcf.enabled` 하나가 아니라 commons 설정과 함께 결정된다. 같은 OFF라도 Filter와 legacy-web 값에 따라 인증, Context, Interceptor와 응답 봉투가 달라진다. 운영자는 “OFF 환경”이라는 이름 대신 실제 Property 조합을 기록해야 한다.

| TCF | Filter | legacy-web | 주요 실행 결과 |
|---:|---:|---:|---|
| OFF | ON | ON | 업무 Controller + JWT/Context + Interceptor/Advice |
| OFF | OFF | ON | 업무 Controller + Interceptor, Context null 가능 |
| OFF | ON | OFF | Filter Context는 있으나 legacy Interceptor/Advice 변화 |
| OFF | OFF | OFF | 업무 Controller 중심 최소 MVC, 공통 계약 대폭 축소 |

두 번째 조합에서는 Interceptor가 Context null Warning 후 Controller 진입을 허용할 수 있다. HTTP 200이 반환돼도 GUID와 ImageLog가 없는 거래가 된다. 세 번째 조합에서는 Filter가 JWT와 Context를 준비해도 표준 Response Advice가 생성되지 않아 Wire Body가 달라질 수 있다. 설정 변경 Test는 Bean 존재만 보지 말고 실제 요청·응답과 로그를 함께 확인한다.

Profile Override도 중요하다. 공통 `application.yml`에서 TCF가 true여도 Local 또는 Dev 파일, 환경변수와 Command Line Argument가 false로 덮을 수 있다. Spring Environment의 최종 값을 Actuator나 기동 로그로 확인하고, 배포 Artifact에 어떤 Profile이 활성화됐는지 남긴다. 잘못된 OFF 기동은 `/online` 404, Handler 등록 로그 부재와 업무 Controller 활성화로 드러난다.

Timeout Property도 독립적이다. OFF + timeout ON은 Executor Bean 생성을 의미할 수 있지만 업무 Controller가 이를 호출하지 않으므로 Worker 실행은 없다. 반대로 OFF Controller 또는 Service에 `@Transactional(timeout=10)`이 있으면 Spring Transaction Timeout은 적용될 수 있다. 두 설정의 이름에 Timeout이 들어간다는 이유로 같은 기능으로 취급하지 않는다.

## Controller별 Transaction 판정 절차

OFF 거래의 Transaction을 판단할 때 다음 순서를 반복한다. 먼저 URL Mapping을 가진 Controller Bean을 찾는다. Controller가 주입한 실제 Type과 호출 Method를 확인하고, 그 객체가 Spring Bean Proxy인지 본다. 호출 Method 또는 Class의 `@Transactional`, Manager, readOnly, rollbackFor와 Propagation을 확인한다. 마지막으로 자기 호출이나 직접 생성처럼 Proxy를 우회하는지 검사한다.

```text
URL / Service ID
  → OFF Controller Method
  → 주입 대상 Facade 또는 Service
  → 호출 Method의 @Transactional
  → Spring Proxy 통과 여부
  → 실제 Manager와 Thread
  → 예외 전파
  → COMMIT / ROLLBACK
```

예를 들어 `mgcoa9000C0`은 OFF Controller가 `mgcoa9000Service`를 직접 호출하고 Service에는 Transaction Annotation이 확인되지 않는다. ON에서는 Handler가 `mgcoa9000Facade.mgcoa9000C0()`을 호출하며 Facade에는 `rdwTransactionManager`, `rollbackFor=Exception.class`가 있다. 동일 등록 거래라도 모드에 따라 유스케이스 Transaction 경계가 달라질 수 있다.

반면 `mgcoa9001C0`은 OFF Controller가 Service를 직접 호출하지만 Service Method 자체에도 쓰기 Transaction이 있다. Facade는 우회하지만 최소한 Service Method 범위 Transaction은 시작될 수 있다. ON Timeout OFF에서는 Facade Transaction이 바깥 경계가 되고 Service Transaction은 참여할 가능성이 크며, Timeout ON에서는 Worker TransactionTemplate가 더 바깥일 수 있다. 동일 Annotation 수가 아니라 최외곽 유효 경계를 찾는다.

`mgcoa9100S0`은 Controller가 Facade를 호출하는 권장 형태와 가깝지만 Facade Method에 Transaction Annotation이 없다. 진단 조회가 DML을 하지 않는다면 문제가 아닐 수 있다. “Facade를 호출하면 무조건 Transaction”이라는 규칙보다 유스케이스가 Transaction을 필요로 하는지와 실제 선언을 함께 본다.

Transaction 활성 여부는 Test에서 `TransactionSynchronizationManager.isActualTransactionActive()` 같은 관측을 사용할 수 있지만 운영 코드에 진단 로직을 섞지 않는다. Test Profile의 AOP와 실제 Profile이 같아야 하고, Mock 객체를 직접 new로 만들면 Proxy가 없어 잘못된 결론을 낼 수 있다.

## `mgcoa9000` 쓰기 거래로 보는 부분 반영 위험

등록 거래가 중복 확인 SELECT, Master INSERT와 Detail INSERT를 순서대로 수행한다고 가정하자. Facade Transaction 안에서는 Detail INSERT가 실패하면 앞선 Master INSERT도 Rollback되어야 한다. OFF에서 Service를 직접 호출하고 Transaction이 없다면 각 Mapper 호출이 독립 Connection 또는 Auto-commit으로 완료돼 Master만 남을 수 있다.

```text
ON 또는 OFF 권장
Facade TX BEGIN
  중복 확인
  Master INSERT
  Detail INSERT ← 실패
ROLLBACK → 둘 다 없음

OFF Service 직접, TX 없음
  중복 확인
  Master INSERT → 반영 가능
  Detail INSERT ← 실패
  Master 고아 데이터 위험
```

이 위험은 코드 리뷰로만 확인하지 않는다. 두 번째 SQL이 확실히 실패하도록 Constraint 위반이나 Test Double을 구성하고, 요청 종료 뒤 새 Connection으로 두 Table을 조회한다. Exception Type과 HTTP Status뿐 아니라 DB 상태를 Assert한다. 첫 번째 SQL이 남으면 Controller를 Facade로 전환하거나 Service에 임시 Transaction을 붙이는 선택을 검토하되 최종 표준은 Facade 공통화다.

삭제도 동일하다. 자식 삭제 후 부모 삭제가 실패하거나 ImageLog 삭제와 업무 삭제를 함께 수행한다면 원자성 요구를 먼저 정의한다. 감사 ImageLog처럼 업무 Rollback과 분리돼야 하는 데이터는 같은 Transaction에 넣지 않는다. OFF 공통화를 이유로 서로 다른 일관성 목표까지 억지로 묶으면 안 된다.

## Facade 공통화 전환 사례

`mgcoa5530Controller`가 Service를 직접 호출하는 AS-IS를 Facade 호출로 전환할 때 Controller Method의 HTTP 계약은 유지하고 주입 대상만 바꾸는 것이 가장 작은 변경이다. 다만 Facade는 `Object dtoBody`를 받아 ObjectMapper로 typed DTO로 변환하므로 이미 typed인 `mgcoa5530S0DTOin`을 넘겼을 때 같은 값이 유지되는지 Test한다.

> 아래 코드는 목표 구조를 설명하는 예시이며 현행 Controller 구현이 아니다.

```java
@RestController
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true)
public class mgcoa5530Controller {
    private final mgcoa5530Facade facade;

    public mgcoa5530Controller(mgcoa5530Facade facade) {
        this.facade = facade;
    }

    @PostMapping("/mgcoa5530S0")
    public mgcoa5530S0DTOout search(
            @RequestBody mgcoa5530S0DTOin input) throws Exception {
        return facade.mgcoa5530S0(input);
    }
}
```

변경 전후에는 네 가지를 비교한다. 첫째, 요청 DTO Field와 Validation 결과가 같은가. 둘째, 응답 DTO와 표준 Envelope가 같은가. 셋째, Service 호출 횟수와 DAO 결과가 같은가. 넷째, Transaction active/readOnly 상태와 예외 Rollback이 목표대로 바뀌는가. 조회 거래라도 readOnly Transaction이 Driver와 DB에 미치는 영향이 있으므로 성능과 호환성을 확인한다.

Controller에서 기존에 로그나 추가 입력 보완을 했다면 Facade 전환 과정에서 사라지지 않게 한다. HTTP Header와 Servlet 정보는 Controller 또는 Framework Context에서 인증된 값만 추출하고, Facade에는 명시적인 업무 입력으로 전달한다. Facade가 Servlet Request에 의존하도록 만들면 ON Handler 재사용이 깨진다.

전환은 업무 하나씩 수행하고 ON/OFF Parameterized Integration Test를 만든다. 모든 Controller를 한 번에 기계적으로 바꾸면 Object 변환, 예외 Signature와 응답 차이가 겹쳐 원인을 찾기 어렵다. 조회부터 시작한 뒤 쓰기 Rollback 검증이 끝난 거래만 확장한다.

## ON/OFF 동등성 테스트 설계

호환의 목표는 내부 호출선이 똑같은 것이 아니라 공개 업무 결과가 동등하고 의도된 Infrastructure 차이만 남는 것이다. 동일 Test Dataset과 인증 사용자를 준비하고 ON URL과 OFF URL을 각각 호출한다. 정상 응답 DTO, DB 변경, 오류 Code와 GUID 추적을 비교한다.

| 검증 축 | ON 요청 | OFF 요청 | 동등성 기준 |
|---|---|---|---|
| 입력 | 공통 Controller Map/dto | typed Controller DTO | 업무 Field 동일 |
| 업무 결과 | Handler→Facade | Controller→Facade 권장 | DTO 값 동일 |
| DB 변경 | Worker/Facade TX | Facade TX | 최종 상태 동일 |
| 업무 오류 | TCF Handler | OFF Advice | Code·Message 계약 결정 |
| Timeout | TCF Executor | 별도 정책 | 차이를 명시 |
| 추적 | GUID/Registry 로그 | GUID/Controller 로그 | 상관관계 유지 |

등록 성공 Test 뒤에는 같은 Key 재등록, Validation 실패, 첫 DML 후 예외와 checked Exception을 실행한다. 수정은 대상 없음, 낙관적 잠금 충돌과 처리 건수 불일치를 본다. 삭제는 자식 존재와 이미 삭제된 대상의 정책을 비교한다. 조회는 빈 결과, 대용량 결과와 readOnly 여부를 확인한다.

응답 비교에서 Timestamp, GUID처럼 매번 달라지는 Field는 의미 기반으로 검사한다. 오류 Stack Trace나 내부 Class 이름은 외부 계약에 포함하지 않는다. ON과 OFF가 다른 Status를 의도한다면 Test에 그 차이를 명시하고 UI가 두 경우를 처리하는지 확인한다.

Timeout 차이는 동등하게 만들 수 없는 현재 구조의 대표 사례다. ON Timeout Test가 504와 Worker rollback을 기대한다면 OFF Test는 같은 시간을 넘겨도 TCF Timeout이 없음을 증명한다. 운영에서 이 차이를 허용하지 않는다면 OFF를 운영 경로에서 제외하거나 공통 실행 정책을 추가해야 한다.

## OFF 운영 전환과 롤백 절차

설정 전환은 재기동과 Bean Graph 변경을 동반한다. 배포 전 OFF Controller Mapping 목록, Transaction 검증 결과와 오류 응답 차이를 승인받는다. Canary 인스턴스에서 기동 로그와 Health를 확인하고 직접 URL Smoke Test를 수행한다. UI나 Gateway가 `/online`만 호출한다면 Routing 변경 없이는 OFF 서비스에 도달하지 못한다.

```text
전환 전
  Property/Profile 확인
  OFF Mapping + Facade 경계 검증
  UI/Gateway URL 준비
  정상/실패 Smoke Test

전환
  tcf.enabled=false
  재기동
  Bean Graph/로그 확인

문제 발생
  요청 유입 차단
  tcf.enabled=true 복원
  재기동
  Registry/Handler 정상 확인
```

설정만 원복하면 데이터 부분 반영이 자동 복구되는 것은 아니다. OFF Transaction 결함으로 생성된 고아 데이터는 별도 보정 절차가 필요하다. 전환 전 쓰기 거래 Rollback Test가 중요한 이유다. 운영 Feature Flag처럼 무중단 즉시 변경된다고 가정하지 않고 Spring Context 재구성 시간을 포함한다.

관측 지표도 모드에 맞춘다. ON에서는 Registry 등록 수, Worker Active/Queue와 Timeout을 보고, OFF에서는 Controller별 호출량, Request Thread 실행시간과 Transaction 부재 위험을 본다. 공통 지표인 GUID, Service ID, 오류율과 DB 시간은 같은 Dashboard에서 비교할 수 있다.

```text
TCF OFF
Client
  → DefaultFilter                  별도 설정 시
  → ServicePreventionInterceptor   별도 설정 시
  → Business Controller            OFF 조건부 Bean
      ├─ AS-IS 다수: Service 직접
      └─ 권장: Business Facade
          → @Transactional BEGIN
          → BizPrePostAspect + Service
          → Rule/DAO/Mapper/DB
          → COMMIT/ROLLBACK
  → ResponseBodyAdvice             별도 설정 시
  → afterCompletion/ImageLog

미사용: OnlineController, TcfFacade, Dispatcher,
        Handler Registry, STF, ETF, TCF Timeout 호출선
```

## 책임과 경계 표

| 구성요소 | OFF 상태 | 책임 | 금지 책임 |
|---|---|---|---|
| Business Controller | 활성 | HTTP Binding·Validation·Facade 호출 | SQL·업무 TX 정책 |
| Business Facade | 유지 | DTO 변환·유스케이스·Transaction | HTTP Header 처리 |
| Service | 유지 | 업무 흐름·Rule·DAO 조정 | 모드 분기 |
| Filter/Interceptor | 별도 설정 | 인증·Context·시스템 선처리 | 업무 계산 |
| BizPrePostAspect | legacy 설정 | Service 공통 선후 로그 | TX 존재 가정 |
| Response Advice | 별도 설정 | 응답 봉투 | 업무 Commit 결정 |
| TCF Core/Handler | 비활성 | OFF에서는 없음 | 직접 호출 우회 복제 |

## 정상·실패 비교

| 정상 쓰기 | Facade TX Commit | Service TX Commit | SQL별 반영 위험 |

| 업무 Aspect | Facade TX 안 가능 | Advisor 순서 확인 | 실행돼도 원자성 없음 |
| TCF Timeout | 미적용 | 미적용 | 미적용 |
| TCF Registry | 미적용 | 미적용 | 미적용 |

## 운영 장애 추적

OFF에서 `/online`이 404면 정상일 수 있다. 직접 URL도 404면 Controller Bean 조건, Mapping과 Profile Property를 확인한다. Controller 로그 이후 Handler 로그가 없는 것은 OFF에서는 정상이며, Service 또는 Facade 로그로 다음 단계를 추적한다.

쓰기 일부만 반영되면 먼저 Controller가 어느 객체를 호출하는지 확인한다. Facade를 우회하고 Service에 Transaction이 없다면 SQL별 Commit 가능성을 조사한다. Aspect 로그가 존재하는 것을 Transaction 증거로 사용하지 않는다.

timeout 설정이 무시되는 증상은 OFF가 TcfFacade를 우회하는 구조에서 예상된다. UI·Proxy·JDBC 중 실제로 발생한 Timeout Type을 구분한다. 예외 JSON이 다르면 TCF GlobalExceptionHandler 비활성화와 남은 Advice의 처리 Type을 확인한다.

### 증상별 조사 순서

직접 URL이 동작하지만 데이터가 일부만 반영됐다면 가장 먼저 GUID로 Controller와 Service 로그를 묶는다. 같은 GUID에 Facade 진입 로그가 있는지 확인하고 없으면 Controller Source의 주입 Type을 본다. Service Method의 Transaction Annotation과 TransactionManager를 확인한 뒤, 오류 직전 실행된 SQL과 Commit 시점을 DB Log로 비교한다. 예외가 발생했다는 사실만으로 Rollback됐다고 판단하지 않는다.

응답은 성공인데 ImageLog가 없으면 TCF OFF 자체보다 Filter와 legacy-web 설정을 확인한다. OFF에서도 공통 Web Bean이 활성화되면 Pre/Post ImageLog는 남을 수 있다. Context null Warning, multipart Skip과 ImageLog DB 오류를 순서대로 확인한다. Handler 등록 로그가 없는 것은 OFF에서는 정상이며 장애 단서가 아니다.

업무 선후처리 로그는 있는데 응답 DTO가 ON과 다르면 Aspect보다 호출 대상 차이를 본다. OFF Controller가 Service를 직접 호출하면 ON Facade의 ObjectMapper 변환이나 유스케이스 조정이 빠질 수 있다. 동일 입력을 Facade 단위 Test에 넣어 결과를 비교하고, Controller에서 별도 가공한 코드가 있는지 검색한다.

CPU와 DB 사용량이 ON보다 급증했다면 OFF에서 Worker Pool·Queue 제한을 우회해 Servlet Thread 수만큼 업무가 DB로 유입되는지 확인한다. ON의 Overload 방어가 OFF에는 없으므로 단순히 Timeout 값을 늘리는 대응은 더 많은 동시 SQL을 만들 수 있다. Gateway Rate Limit, Web Thread Pool과 DB Connection Pool의 관계를 함께 본다.

### 릴리스 승인 기준

OFF를 배포 가능한 상태로 판정하려면 모든 Controller가 뜬다는 것만으로 부족하다. 지원 Service ID 전부에 Mapping이 있고, 쓰기 거래의 중간 실패 Rollback이 증명돼야 한다. ON/OFF 정상 DTO와 DB 결과가 동일하고, 의도적으로 다른 Timeout·오류 응답은 UI와 운영 절차에 문서화돼야 한다.

```text
OFF 릴리스 Gate
  [ ] 공개 Service ID Mapping 100% 확인
  [ ] Controller → Facade 공통화 또는 예외 승인
  [ ] 모든 쓰기 거래 Rollback Test
  [ ] checked/runtime 예외 Wire 계약
  [ ] Filter/JWT/Context 설정 조합 Test
  [ ] Timeout·Overload 대체 정책
  [ ] ON 복귀 절차와 데이터 보정 절차
```

Controller가 Service를 직접 호출해야 하는 예외가 남는다면 이유, Transaction 시작점과 종료 계획을 기록한다. “기존 코드라서”는 Architecture 예외의 충분한 근거가 아니다. 조회 전용인지, Facade 변환과 호환되지 않는지, 전환 위험이 무엇인지 구체적으로 남기고 담당자와 검증 Test를 연결한다.

OFF 운영 중 ON으로 복귀할 때도 같은 데이터와 요청으로 Smoke Test한다. Handler Registry가 최신 Service ID를 포함하는지, UI Route가 다시 공통 URL을 향하는지와 Timeout Worker가 정상 동작하는지 확인한다. 모드 전환은 단순 Property 원복이 아니라 Entry Adapter와 운영 제어의 복원이다.

운영 Runbook에는 모드 식별 방법도 넣는다. 기동 Property, 활성 Controller Bean, 대표 URL의 응답과 Handler 등록 로그를 한 묶음으로 확인해야 한다. 서버 이름이나 배포 작업자의 기억에 의존하면 일부 Instance만 OFF로 기동된 혼합 Cluster를 놓칠 수 있다. Load Balancer 뒤에서 ON과 OFF Instance가 섞이면 같은 요청이 Node마다 404, 다른 Timeout과 다른 오류 JSON을 반환할 수 있다.

혼합 Cluster 검증에는 응답 Header나 안전한 진단 Endpoint로 실행 모드를 식별하는 방법을 사용할 수 있다. 단, 내부 설정 전체를 외부에 노출하지 않는다. Instance별 요청 수, 오류율과 Service ID를 비교하고 Routing이 의도한 Pool로만 전달되는지 확인한다. 모드 전환 완료 후에는 이전 Pool을 즉시 제거하기보다 진행 중 요청과 Worker 종료를 기다리고, DB 상태와 ImageLog의 마지막 GUID를 대조한다.

이처럼 OFF 호환성은 Source가 Compile되는 것으로 끝나지 않는다. Bean Graph, HTTP Routing, 업무 Transaction, 공통 Web 처리와 운영 관측이 함께 맞아야 실제 대체 경로가 된다.

## Anti Pattern

1. TCF OFF를 Filter, JWT, Context와 Interceptor까지 모두 꺼진 상태로 설명한다.
2. 모든 OFF Controller가 Facade를 호출한다고 문서만 보고 단정한다.
3. 모든 OFF Transaction이 Service에서 시작한다고 일반화한다.
4. Service 직접 호출을 신규 개발 표준으로 복제한다.
5. Controller에 SQL과 여러 업무 Service 조정을 넣는다.
6. Aspect 로그가 있으므로 같은 Transaction이라고 판단한다.
7. timeout.enabled가 true라서 OFF에도 Worker Timeout이 적용된다고 생각한다.
8. ON 정상 응답만 비교하고 오류 Status·Body 차이를 무시한다.
9. ON Handler와 OFF Controller에 업무 로직을 각각 구현한다.
10. Controller에 넓은 Transaction을 붙여 Facade 경계를 대체한다.
11. OFF Mapping을 추가하지 않고 Handler만 등록한다.
12. Filter·legacy-web Property 조합을 확인하지 않고 TCF 설정 탓으로 돌린다.

## 아키텍처 판단 포인트

OFF를 유지할지 결정할 때 호환 가치와 검증 비용을 비교한다. 운영 경로가 하나면 ON에 집중하는 편이 단순하다. OFF를 비상 경로로 유지하면 Transaction, Timeout, 오류 응답과 Mapping을 별도로 Test해야 한다. 사용하지 않는 비상 경로는 안전망이 아니라 미검증 코드가 된다.

공통화의 중심은 Facade다. Handler와 Controller는 서로 다른 Entry Adapter이며 Facade 아래 동일 유스케이스를 호출해야 한다. Service 직접 호출은 단순해 보여도 Transaction과 DTO 조정 경계를 갈라놓는다.

Transaction 위치는 Annotation을 어디에 붙이기 쉬운지가 아니라 하나의 업무 원자성이 어디까지인지로 결정한다. 여러 Service·DAO를 묶는 유스케이스라면 Facade가 자연스럽다. Controller Transaction은 Web 경계를 오염시키고 Service Transaction은 상위 조정을 포함하지 못할 수 있다.

Timeout과 예외 표준은 모드별 차이를 숨기지 않는다. 동일하게 만들어야 한다면 공통 Adapter로 구현하고, 다르게 둘 이유가 있다면 UI와 운영 계약에 명시한다.

## 핵심 정리

TCF OFF는 공통 TCF 실행 계층을 비활성화하고 업무 Controller로 직접 진입하는 호환 구조다. Filter, ServiceContext, Interceptor, Response Advice, DataSource와 TransactionManager는 별도 설정에 따라 유지될 수 있으므로 Framework 전체 OFF와 같지 않다.

현행 OFF Controller는 호출 방식이 혼재한다. 다섯 Controller는 Service를 직접 호출하고 `mgcoa9100Controller`는 Facade를 호출한다. Service 자체 Transaction도 `mgcoa9001Service`처럼 선언된 경우와 그렇지 않은 경우가 있어 Transaction 시작점을 모드 하나로 단정할 수 없다.

OFF에서는 TcfFacade와 OnlineTimeoutExecutor 호출선을 우회하므로 TCF Worker Timeout과 외부 TransactionTemplate가 적용되지 않는다. TCF 조건의 GlobalExceptionHandler도 사라져 오류 Status와 Wire Body가 달라질 수 있다. 업무 Aspect는 실행될 수 있지만 Transaction 존재를 보장하지 않는다.

권장 호환 구조는 ON Handler와 OFF Controller가 같은 Business Facade를 호출하는 것이다. Facade 아래 Service·Rule·DAO를 공유하고 Transaction을 한 곳에서 관리하면 모드 차이는 Entry, Registry, Timeout과 오류 Adapter로 제한된다.

다음 장에서는 두 Entry Adapter인 Handler와 Controller를 자세히 비교한다. Handler가 Service ID 분기와 Facade 위임만 담당하고 Controller가 HTTP Binding과 Facade 호출에 집중해야 하는 이유를 실제 구현 패턴으로 살펴본다.
