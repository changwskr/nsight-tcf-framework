# 25장. 업무 요청의 JWT 검증

로그인으로 Access Token을 얻었다고 업무 요청이 자동으로 인증되는 것은 아니다. UI가 토큰을 HTTP Header에 실어 보내고, 서버가 업무 코드보다 앞에서 이를 꺼내 서명과 유효기간을 검사하며, 검증된 신원을 후속 처리에 전달해야 비로소 인증 경로가 닫힌다. PDMG에서는 이 진입점이 Spring Security Resource Server가 아니라 `pdmg-fw`의 `DefaultFilter`와 `JwtProvider`다.

현행에는 세 가지 중요한 단절이 있다. 일반 업무용 UI 클라이언트는 Authorization Header를 추가하지 않는다. 비-local Filter는 HMAC 공유 비밀키로 검증하지만 `pdmg-jwt`는 RS256으로 발급한다. 마지막으로 검증 후 `sub`는 request attribute `ssoId`에만 저장되고 `ServiceContext.userContext`나 업무 Header, MDC로 복사되지 않는다. 따라서 이 장은 “의도한 전체 흐름”과 “실제로 이어진 코드”를 분리해 읽어야 한다.

## 25.1 UI의 Access Token 저장

JWT 관리 UI의 `jwt-admin.js`는 로그인 응답의 Access Token과 Refresh Token을 `sessionStorage`의 `pdmg.jwt.session`에 저장한다. 같은 탭 세션에서 `getSession()`으로 꺼낼 수 있고, `exp`를 디코딩하여 화면 이동 전 만료를 예상한다. 이 검사는 UX를 위한 사전 판단이지 보안 검증이 아니다. 브라우저는 서명 신뢰의 최종 주체가 아니며 사용자가 저장값과 JavaScript를 바꿀 수 있기 때문이다.

업무 화면이 사용하는 `_shared/service-client.js`는 별도 구현이다. 실제 `fetch()` Header는 Content-Type과 Accept만 포함하며 JWT 세션을 읽지 않는다. 관리 UI에 토큰이 저장되어 있다는 사실만으로 일반 업무 요청에 토큰이 전파되지는 않는다. 또한 `sessionStorage`는 JavaScript가 읽을 수 있어 XSS에 취약하므로 운영 저장 전략은 24장의 위협 모델과 함께 정해야 한다.

## 25.2 Authorization Header

Bearer Token의 표준 전달 형태는 다음과 같다. 실제 토큰 값을 문서나 로그 예제에 넣지 않는다.

```http
Authorization: Bearer <access-token>
```

Header는 표준 전문의 `hdr_nhnis`와 책임이 다르다. Authorization은 전송 계층의 인증 자격 증명이고, `hdr_nhnis.sys_comm`은 GUID, Service ID, 단말 IP, 조작자 번호 같은 거래 메타데이터다. 클라이언트가 전문에 사용자 ID를 적었다고 인증된 것은 아니다. 서버는 검증된 Claim과 클라이언트 제공 Header가 다를 때 거부하거나 검증값으로 덮는 명확한 정책을 가져야 한다.

## 25.3 DefaultFilter 토큰 추출

`DefaultFilter`는 `nhnis.fw.commons.filter.enabled=true`일 때 등록되는 `OncePerRequestFilter`다. OPTIONS 요청은 CORS preflight를 위해 제외한다. 일반 JSON 요청이면서 활성 프로파일 문자열이 `local`이 아닐 때 Authorization Header가 정확히 `Bearer `로 시작하는지 검사하고, 앞의 7글자를 제거해 토큰을 얻는다. Header가 없거나 접두사가 다르면 HTTP 401 `Access Token이 없습니다.`를 즉시 보낸다. Controller와 TCF는 호출되지 않는다.

그러나 면제 범위가 넓다. local 프로파일에서는 `jwt.enabled` 값과 무관하게 JWT 블록 전체를 건너뛴다. 소스에는 `jwt.enabled`를 읽는 코드가 없다. multipart 요청도 별도 분기로 들어가 JWT 검사를 수행하지 않는다. OPTIONS 면제는 타당하지만 local과 multipart 면제는 운영 배포·파일 업로드의 보안 경계로 명시하고 테스트해야 한다. 활성 프로파일 값 하나로 판단하므로 복수 프로파일 문자열에 대한 동작도 주의가 필요하다.

```text
DefaultFilter
  ├─ OPTIONS                    → 필터 미실행
  ├─ multipart/*                → Context만 생성, JWT 검사 없음
  ├─ active == local            → JWT 검사 없음
  └─ 그 밖의 일반 요청
       ├─ Bearer 없음           → 401
       ├─ validate 실패         → 401
       ├─ type != ACCESS        → 401
       └─ sub 추출              → request.ssoId
```

## 25.4 토큰 서명 검증

AS-IS `JwtProvider.init()`은 설정 `jwt.secret`의 바이트로 HMAC `SecretKey`를 만든다. `validate()`는 JJWT parser에 이 키를 넣고 signed claims를 파싱한다. 서명이 위조되었거나 키가 다르거나 토큰 형식이 깨지면 예외를 잡아 `false`를 반환한다. Filter는 이를 401로 바꾼다.

이 검증기는 Public Key를 사용하지 않으며 JWKS를 조회하지 않는다. HMAC에서는 생성자와 검증자가 같은 비밀키를 공유한다. 반면 RS256은 발급자만 Private Key를 가지고 검증자는 Public Key를 가진다. Public Key는 JWT를 복호화하는 키가 아니라 전자서명의 수학적 유효성을 확인하는 키다.

## 25.5 만료·타입 검증

JJWT의 signed claims 파싱은 유효한 `exp`가 과거이면 예외를 발생시키므로 `validate()` 결과가 false가 된다. 이어 `isAccessToken()`은 같은 토큰을 다시 파싱하고 `type` Claim이 정확히 `ACCESS`인지 검사한다. Refresh Token은 현행 구현상 JWT가 아닌 불투명 문자열이지만, 다른 유형의 JWT를 업무 API에 쓰는 것도 이 단계에서 막는다.

반면 현행 코드에는 issuer, audience, `nbf`, clock skew 정책, denylist의 명시적 검사가 없다. `pdmg-jwt`가 Claim을 발급한다는 사실과 `pdmg-fw`가 그 Claim을 검증한다는 사실을 혼동하면 안 된다. 또한 `validate()`, `isAccessToken()`, `getSsoId()`가 각각 토큰을 다시 파싱하므로 한 번의 검증 결과를 불변 객체로 전달하는 구조도 아니다.

## 25.6 사용자 ID 추출

서명과 타입 검사를 통과하면 `getSsoId()`가 JWT `sub`를 반환한다. Filter는 이를 원본 request의 `ssoId` attribute에 저장한다. `sub`가 비어 있는지 별도로 검사하지 않으며, `userId`, `branchId`, `channelId`, `authGroupId` 같은 다른 Claim은 추출하지 않는다.

더 중요한 것은 후속 코드 사용처다. 저장소 검색 결과 `ssoId` request attribute를 읽어 업무 신원으로 변환하는 구현이 확인되지 않았다. 즉 토큰의 subject는 request에 놓이지만, 업무 Header의 `optr_eno`나 MDC `userId`를 대체하지 않는다. 인증 성공과 업무 신원 반영 사이에 연결 코드가 빠진 상태다.

## 25.7 ServiceContext 저장

일반 JSON 흐름에서 Filter는 JWT 처리 뒤 요청 본문을 읽고 `hdr_nhnis`를 변환한다. GUID, IP, 조작자 번호, Service ID는 Header에서 MDC로 복사한 다음 `ServiceContext`를 생성한다. Context는 원본 HttpHeaders, request/response, 표준 Header, request body와 빈 `userContext` Map을 가진다.

AS-IS에서는 검증된 `ssoId`가 `ServiceContext.userContext`에 들어가지 않는다. 오히려 MDC `userId`는 클라이언트가 보낸 `sys_comm.optr_eno`에서 온다. 그러므로 로그와 거래통제가 “JWT로 검증된 사용자”를 사용한다고 단정할 수 없다. TO-BE에서는 검증기가 반환한 불변 인증 객체를 Context에 저장하고, 사용자 식별 필드는 검증 Claim을 권위값으로 사용해야 한다. 클라이언트 Header와 불일치는 감사 후 거부하는 정책이 안전하다.

Thread 경계도 고려해야 한다. ServiceContext는 ThreadLocal에 저장되고 Filter finally에서 제거된다. 타임아웃 Worker로 넘어갈 때 기존 Worker Context 전파 메커니즘에 인증 객체도 포함되어야 하며, 모든 종료 경로에서 정리해야 한다.

## 25.8 인증과 인가의 차이

인증은 “이 토큰이 신뢰된 발급자가 만든 유효한 사용자 증표인가”를 답한다. 인가는 “이 사용자가 이 기능을 실행할 수 있는가”를 답한다. 거래통제는 서비스·사용자·IP·영업점·시간대 등의 운영 규칙으로 현재 거래를 허용할지 답한다. 세 판단은 입력을 공유할 수 있지만 대체 관계가 아니다.

Spring Security 설정이 `anyRequest().permitAll()`인 것은 인증이 Filter에 위임되었다는 의미이지 모든 사용자가 모든 거래를 수행해도 된다는 보안 설계가 아니다. Filter에서 JWT가 통과해도 권한 그룹과 Service ID의 매핑을 확인하지 않으면 인가는 수행되지 않는다. 반대로 거래통제가 열려 있다고 토큰 위조를 허용해서도 안 된다.

## 25.9 거래 통제와 JWT Claim

`ServicePreventionInterceptor`의 거래통제 요청은 Service ID, 업무 코드, 사용자, 채널, 영업점, IP 같은 값을 조립한다. 현행 사용자 값은 Header 또는 MDC에서 가져올 수 있으나 앞 절에서 본 것처럼 JWT subject와 자동 연결되지 않는다. 따라서 공격자가 전문의 조작자 번호를 바꿀 때 사용자별 통제 기준이 흔들릴 수 있는지 검증해야 한다.

TO-BE 우선순위는 검증된 인증 객체가 사용자·영업점·권한 그룹의 권위값이고, 표준 Header는 거래 표시·호환 정보로 교차 검증하는 것이다. Claim이 오래된 권한 정보를 담을 수 있으므로 고위험 거래의 인가는 서버 권한 저장소를 재조회하거나 매우 짧은 토큰 수명과 폐기 정책을 사용한다.

## 25.10 현재 HMAC 검증 구조

현재 구조를 한 문장으로 말하면 “비-local 일반 요청에 한해 `DefaultFilter`가 공유 비밀키로 signed JWT를 검증한다”이다. `jwt.enabled` 설정은 Filter 활성 여부를 제어하지 않고, `nhnis.fw.commons.filter.enabled`와 `spring.profiles.active`가 실제 분기를 결정한다. 기본 설정 파일과 애플리케이션 프로파일에는 개발용 secret fallback이 존재하므로 운영에서 이를 그대로 쓰면 안 된다.

HMAC 자체가 항상 잘못된 것은 아니다. 단일 신뢰 경계에서 발급·검증 주체가 모두 비밀을 안전하게 공유한다면 사용할 수 있다. 그러나 PDMG 목표처럼 중앙 발급기와 여러 업무 검증기를 분리할 때는 모든 검증 서비스가 토큰 위조 능력까지 갖게 된다는 문제가 있다.

## 25.11 RS256과 HMAC 불일치

`pdmg-jwt.JwtTokenIssuer`는 RS256과 RSA Private Key로 발급한다. 현행 `pdmg-fw.JwtProvider`는 HMAC SecretKey로 검증한다. 이 토큰은 동일한 비밀 문자열을 설정해도 호환되지 않는다. 알고리즘과 키 종류 자체가 다르기 때문이다. 정상적인 RS256 토큰이 “유효하지 않은 Token” 401로 거부되는 것이 현재 예상 결과다.

| 항목 | 발급 AS-IS | 업무 검증 AS-IS |
|---|---|---|
| 알고리즘 | RS256 | HMAC 계열 parser |
| 키 | 발급기 메모리 Private Key | `jwt.secret` SecretKey |
| 키 배포 | JWKS Public Key endpoint | JWKS 미사용 |
| issuer/audience | Claim에 포함 | 명시 검증 없음 |
| denylist | DB 기능 존재 | 요청 경로 미연결 |

이 문제를 피하려고 `pdmg-jwt`의 Private Key를 서비스에 복사하면 안 된다. 검증기를 JWKS Public Key 방식으로 전환해야 한다.

## 25.12 JWKS 기반 검증 전환

TO-BE 검증기는 Authorization Header에서 토큰을 한 번 파싱해 `kid`를 읽고, 신뢰하도록 설정한 JWKS endpoint의 대응 Public Key로 RS256 서명을 확인한다. 이어 허용 알고리즘, issuer, audience, 만료·발급시각과 clock skew, `type=ACCESS`, 필수 subject를 검증한다. 마지막으로 신뢰된 `jti`로 denylist를 확인하고 인증 객체를 만든다.

```text
Bearer token
  → alg 허용 목록과 kid 확인
  → JWKS 캐시에서 Public Key 선택
  → RS256 서명 검증
  → iss / aud / exp / type / sub 검증
  → denylist(jti) 확인
  → AuthenticatedPrincipal 생성
  → ServiceContext.userContext + MDC 반영
```

JWKS 장애 때 기존 캐시를 언제까지 쓸지, 알 수 없는 `kid`에서 한 번 재조회할지, denylist 장애를 fail-open 또는 fail-closed로 할지 운영 정책이 필요하다. 키 회전 테스트는 새 키 발급, 이전 토큰 검증, 이전 키 제거의 세 시점을 포함해야 한다.

## 25.13 UI Authorization Header 보완

일반 `service-client.js`는 요청마다 JWT 세션을 읽어 유효한 Access Token이 있으면 Authorization Header를 추가해야 한다. 토큰이 없거나 클라이언트가 예상한 만료를 지났다면 로그인 또는 갱신 흐름으로 보내고, 서버 401은 한 번만 갱신 후 원 요청을 재시도하는 식으로 무한 루프를 막아야 한다.

로그인·갱신 endpoint까지 동일한 interceptor가 무조건 Bearer를 요구하면 최초 로그인이 불가능해진다. 공개 endpoint와 인증 endpoint의 분리는 URL 문자열의 임의 예외 목록보다 서버 정책으로 명확히 관리하는 편이 안전하다. CORS의 allowed headers에도 Authorization이 허용되어야 하며, 현재 `allowed-headers: "*"`는 이를 포괄한다.

## 25.14 Token·Secret 로그 금지

Authorization Header 전체, Access/Refresh Token 원문, HMAC secret, RSA Private Key는 어떤 로그 레벨에서도 출력하지 않는다. 예외 객체나 requestHeaders를 통째로 직렬화하는 공통 로그도 점검해야 한다. 추적에는 GUID, Service ID, 검증 결과 코드, 안전하게 관리되는 `jti`, issuer, 실패 단계 정도면 충분하다. 사용자 ID도 개인정보 로그 정책에 따라 마스킹·접근통제를 적용한다.

오류 메시지는 위조, 만료, 키 불일치 같은 내부 판정을 클라이언트에 과도하게 설명하지 않고 공통 401로 응답하되, 서버 내부에는 비밀값 없이 구분 가능한 원인 코드를 남긴다. 현재 Filter의 `sendError()`는 표준 PDMG 오류 전문보다 앞에서 컨테이너 오류 응답을 만들 수 있다. 상세 예외 변환과 응답 일관성은 다음 장의 주제다.

### End-to-End 실행 흐름

```text
[AS-IS 실제]
업무 UI service-client.js ── Authorization 없음
  → local: JWT 생략 → Header 기반 Context/거래통제 → 업무 실행 가능
  → non-local: DefaultFilter → 401

[토큰을 수동 첨부한 non-local]
Bearer RS256 token → HMAC JwtProvider → 키/알고리즘 불일치 → 401

[TO-BE]
UI → Bearer RS256 token → DefaultFilter/JWKS verifier
  → 서명·Claim·denylist → 인증 객체 → ServiceContext/MDC
  → 인가 → 거래통제 → TCF/업무 실행
```

### 책임과 정상·실패 경계

| 주체 | 책임 | 정상 | 실패 |
|---|---|---|---|
| 업무 UI client | Bearer 첨부, 401 흐름 제어 | 요청 전달 | 로그인/단일 갱신 |
| DefaultFilter | 선행 추출과 인증 차단 | Context 준비 | Controller 전 401 |
| JWT verifier | 서명·Claim 검증 | 인증 객체 반환 | 위조·만료·키 불일치 거부 |
| Context adapter | 신뢰 Claim 전달 | Worker까지 일관된 신원 | Header와 불일치 거부 |
| 인가/거래통제 | 기능 권한·운영 규칙 판단 | 업무 진입 | 표준 권한/통제 오류 |

### Anti Pattern

- JWT Payload를 디코딩한 사용자 ID만 믿는다. 공격자가 임의 Payload를 만들 수 있다.
- local 면제를 운영 프로파일에 남긴다. 모든 요청이 인증 없이 업무에 진입한다.
- multipart는 파일 업로드이므로 안전하다고 보고 계속 면제한다. 보호 API의 우회 경로가 된다.
- 검증된 `sub` 대신 클라이언트 전문의 사용자 ID로 거래통제한다. 사용자별 통제가 위조 가능해진다.
- HMAC 문제를 Private Key 복사로 해결한다. 업무 서비스가 토큰 발급 능력을 얻게 된다.
- 토큰 파싱 실패 때 원문을 debug 로그에 남긴다. 로그를 읽는 주체가 토큰을 재사용할 수 있다.

### 개발자·운영자 체크리스트

- [ ] 일반 업무 `fetch()`가 Authorization Header를 실제 추가하는가?
- [ ] OPTIONS 외 면제 경로가 승인된 최소 범위인가?
- [ ] local 면제가 운영 배포에서 절대 활성화되지 않는가?
- [ ] multipart 보호 API도 동일 인증을 거치는가?
- [ ] 허용 알고리즘, issuer, audience, exp, type, sub를 모두 검증하는가?
- [ ] `kid` 미발견과 JWKS 장애 정책을 테스트했는가?
- [ ] denylist가 실제 업무 요청 경로에서 호출되는가?
- [ ] 검증된 신원이 ServiceContext와 MDC의 권위값인가?
- [ ] Worker Thread 전파와 finally 정리가 보장되는가?
- [ ] 토큰·Secret·Private Key가 로그와 오류 응답에 없는가?
- [ ] 위조, 만료, 키 회전, Refresh 오용 테스트가 존재하는가?

### 아키텍처 판단과 다음 장

PDMG에서 검증 위치는 모든 진입 경로를 덮으면서 업무 실행보다 앞이어야 한다. Filter를 유지하든 Spring Security Resource Server로 옮기든 중요한 기준은 단일 검증, 명시적 면제, 불변 인증 객체, Context 전파와 일관된 오류 응답이다. 인증 후에는 신뢰된 Claim과 서버 권한 데이터를 조합해 인가하고, 그 결과를 거래통제 입력으로 사용해야 한다.

현재 Filter는 인증 실패를 `sendError()`로 즉시 끝내고, 업무 계층은 `BizException`과 공통 예외 처리기를 사용한다. 다음 장에서는 이처럼 서로 다른 위치에서 발생한 오류가 어떤 응답으로 바뀌는지, 표준 오류 코드와 rollback·로그 경계를 어떻게 일관되게 설계해야 하는지 살펴본다.
