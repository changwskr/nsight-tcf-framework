# 3장. 레이어드 아키텍처와 컴포넌트

2장은 PDMG 온라인 요청 한 건을 시간순으로 추적했다. 같은 시스템을 이번에는 구조의 관점에서 바라본다. Handler, Facade, Service와 DAO가 단지 호출 순서대로 나뉜 클래스인지, 아니면 서로 다른 변경 이유와 의존 규칙을 가진 경계인지가 이 장의 주제다.

레이어는 폴더를 보기 좋게 나누는 규칙이 아니다. HTTP 계약이 바뀌어도 SQL이 흔들리지 않고, 데이터 저장 방식이 바뀌어도 업무 규칙이 다시 작성되지 않도록 변경의 파급 범위를 제한하는 장치다. 컴포넌트는 그 레이어 안에서 구체적인 책임을 수행하는 클래스 유형이다. 같은 호출 흐름이라도 이 두 관점을 구분하면 코드가 어디에 있어야 하는지와 왜 그곳에 있어야 하는지를 설명할 수 있다.

> **현행 기준**
> 이 장은 현재 `pdmg-service`의 `nhnis.mg.co.a.*` 패키지와 `pdmg-fw` 소스를 AS-IS로 설명한다. 저장소 공통 아키텍처가 요구하는 `entry/facade`, `application/rule` 구조는 TO-BE로 분리한다. 실제 패키지에 없는 레이어를 이미 구현된 것처럼 표현하지 않는다.

### 이 장에서 해결할 질문

- Framework, Entry, Application, Rule, Contract와 Persistence는 각각 무엇을 책임지는가?
- Handler, Controller, Facade와 Service는 왜 하나의 클래스로 합치지 않는가?
- DTO는 어떤 경계를 건너며 어디까지 의존해도 되는가?
- 외부 시스템 호출은 왜 DAO가 아니라 Client에 두는가?
- 허용되는 의존 방향은 무엇이며 역방향 의존은 왜 위험한가?
- 현행 PDMG와 저장소 목표 구조는 어디가 다른가?
- 구조를 개선할 때 무엇을 한 번에 바꾸지 말아야 하는가?

## 3.1 PDMG 레이어 구성

레이어는 비슷한 기술을 모아 둔 분류가 아니라 비슷한 변경 이유를 가진 코드의 경계다. HTTP 진입 코드는 채널과 프로토콜 변화에 반응하고, Application은 유스케이스 변화에 반응하며, Persistence는 데이터 저장 방식과 SQL 변화에 반응한다. 변경 이유가 다른 코드를 분리해야 한 요구사항이 전체 애플리케이션으로 번지는 것을 막을 수 있다.

현재 PDMG를 실제 패키지 기준으로 펼치면 다음과 같다.

```text
Channel
  pdmg-ui / API Client
       │ HTTP + { hdr_nhnis, dto }
       ▼
Framework Infrastructure                    pdmg-fw / nhnis.fw.*
  Filter · Interceptor · TCF · Context · Timeout · Response
       │ Service ID + dtoBody
       ▼
Entry                                       nhnis.mg.co.a.entry.*
  handler · aspect
       │
       ▼
Application                                 nhnis.mg.co.a.application.*
  controller(TCF OFF) · facade · service
       │                 │
       │                 ├──── Contract      nhnis.mg.co.a.dto
       │                 └──── Support       nhnis.mg.co.a.support
       ▼
Persistence                                 nhnis.mg.co.a.persistence.dao
  DAO interface → Mapper XML(rdw.mg.co.a) → DB

Side/Assembly
  config · client(현재 package-info만 존재)
```

여기서 세로 화살표는 런타임 호출 방향과 대체로 일치하지만 모든 패키지가 세로 스택에 들어가는 것은 아니다. Config는 Bean을 조립하고, DTO는 여러 경계가 공유하는 계약이며, Support는 특정 기술 경계에 속하지 않는 순수 도우미다. Client는 DB 아래가 아니라 외부 시스템으로 나가는 옆 방향 포트다.

현행과 목표 구조를 먼저 구분하면 이후 설명이 명확해진다.

| 관심사 | AS-IS 패키지 | TO-BE 패키지 방향 |
|---|---|---|
| HTTP Controller | `application.controller` | `entry.web` |
| TCF Handler | `entry.handler` | `entry.handler` 유지 |
| Facade | `application.facade` | `entry.facade` |
| Service | `application.service` | `application.service` 유지 |
| Rule | 없음 | `application.rule` |
| DTO/Contract | 최상위 `dto` | 명시적 Contract 경계 유지 또는 정비 |
| Persistence | `persistence.dao` + XML | `persistence.dao` 또는 `persistence.mapper` |
| Client | package-info만 존재 | 실제 외부 연동 Adapter |

이 표는 즉시 패키지를 이동하라는 지시가 아니다. AS-IS 코드는 현재의 실행 계약이고, TO-BE는 신규 개발과 점진적 정비에서 판단할 기준이다. 클래스 이동은 Spring Scan, AOP Pointcut, Mapper Scan, 테스트와 문서에 영향을 주므로 패키지명만 바꾸는 작업이 아니다.

## 3.2 Framework 레이어

Framework 레이어는 업무가 공통 실행 계약 안에서 동작하도록 둘러싸는 인프라다. `pdmg-fw`의 Filter, Interceptor, TCF Controller, Dispatcher, Context, Timeout Executor, 응답 Advice와 예외 처리기가 여기에 속한다. 업무 개발자가 고객 조회나 거래통제 규칙을 작성하기 전에 요청의 형식, 실행 제한과 추적 방식이 이미 결정되는 구간이다.

Framework가 필요한 이유는 공통 기능의 복제를 막기 위해서다. 각 업무 Controller가 GUID 생성, JWT 검증, 타임아웃, Handler 탐색과 오류 봉투를 각각 구현하면 기능이 같은 것처럼 보여도 예외와 종료 경로가 달라진다. FW는 이 공통 관심사를 하나의 실행 기반으로 제공한다.

```text
pdmg-fw
├─ commons.filter.DefaultFilter
├─ commons.interceptor.ServicePreventionInterceptor
├─ commons.context.ServiceContext / ServiceContextHolder
├─ commons.imagelog.ImageLogHandler
├─ commons.resolver.ResponseBodyArgumentResolver
├─ tcf.web.OnlineTransactionController
├─ tcf.core.facade.TcfFacade
├─ tcf.core.dispatch.TransactionDispatcher
├─ tcf.timeout.OnlineTimeoutExecutor
└─ exception.GlobalExceptionHandler
```

FW의 책임은 요청 준비, 공통 검증, 거래 라우팅 기반, 실행 제한, Context 전달, 표준 응답과 운영 관측성이다. 반대로 특정 마케팅 조건, DTO 필드 계산과 업무 SQL은 책임지지 않는다. FW에 `mgcoa9000Service`나 `mgcoa9000DTO` 참조를 추가하면 공통 모듈이 업무 모듈을 알아야 하므로 의존 방향이 뒤집힌다.

그렇다면 FW의 Dispatcher가 업무 Handler를 어떻게 호출할 수 있을까? FW는 구체 Handler 클래스를 import하지 않고 공통 `TransactionHandler` 인터페이스와 Spring이 주입한 구현 목록만 안다. 업무 모듈이 인터페이스를 구현하고 자신의 Service ID를 등록한다. 이는 제어 역전의 실제 사례다.

```text
pdmg-fw가 아는 것
  TransactionHandler 인터페이스
        ▲
        │ implements
pdmg-service가 제공하는 것
  mgcoa9000Handler, mgcoa8888Handler, ...
```

이 경계 덕분에 신규 업무를 추가할 때 FW 소스를 수정하지 않아도 된다. Handler 미등록과 중복 Service ID는 Dispatcher 구성 또는 호출 단계에서 실패하며, FW는 이를 공통 오류 경로로 전달한다. Framework의 실패는 특정 업무 실패보다 영향 범위가 넓으므로 변경 시 `pdmg-service`뿐 아니라 FW를 사용하는 다른 모듈까지 검증해야 한다.

AS-IS에서 시스템 전후처리는 Filter, Interceptor와 ResponseBodyAdvice에 분산되어 있고 TcfFacade가 STF/ETF를 직접 호출하지 않는다. 목표 다이어그램의 STF/TCF/ETF를 현재 클래스 호출과 동일시하지 않는 것이 중요하다.

## 3.3 Entry 레이어

Entry는 외부 요청을 Application 유스케이스 호출로 바꾸는 경계다. 외부 형식과 내부 실행 모델을 연결하되 업무 규칙과 데이터 접근을 수행하지 않는다. PDMG에는 TCF ON의 Handler와 TCF OFF의 Controller라는 두 진입 방식이 있다.

현행 `entry` 패키지에는 `handler`와 `aspect`가 있다. `mgcoa9000Handler`는 `TransactionHandler`를 구현하고 `serviceIds()`에서 S0, C0, U0, D0를 등록한다. `handle()`은 TransactionContext의 Service ID를 보고 해당 Facade 메서드를 호출한다.

```text
TransactionDispatcher
  → mgcoa9000Handler.handle(dtoBody, context)
      ├─ mgcoa9000S0 → facade.mgcoa9000S0(dtoBody)
      ├─ mgcoa9000C0 → facade.mgcoa9000C0(dtoBody)
      ├─ mgcoa9000U0 → facade.mgcoa9000U0(dtoBody)
      └─ mgcoa9000D0 → facade.mgcoa9000D0(dtoBody)
```

Handler는 Service ID를 업무 메서드로 연결하는 Adapter다. 입력 검증과 SQL을 넣지 않는 이유는 진입 방식이 바뀌어도 같은 유스케이스를 재사용하기 위해서다. Handler가 Service를 직접 호출하면 Facade의 DTO 변환과 트랜잭션 계약을 우회하고, Handler가 DAO를 호출하면 진입 경계가 영속 기술에 결합된다.

`entry.aspect`의 `BizPrePostAspect`는 Service public 메서드를 Pointcut으로 업무 선후처리를 적용한다. Aspect는 호출 흐름에 개입하지만 업무 거래를 선택하지 않는다. 로깅과 공통 업무 전후작업을 담당하는 배선 요소이며 commit/rollback을 직접 결정하는 TransactionManager도 아니다.

TCF OFF Controller는 의미상 Entry지만 AS-IS에서는 `application.controller`에 있다. 대부분의 현행 Controller는 Service를 직접 주입하며, `mgcoa9100Controller`는 Facade를 호출한다. 저장소 목표 구조는 Controller를 `entry.web`으로 옮기고 Controller → Facade → Service 경계를 일관되게 유지하는 것이다.

| 진입 방식 | AS-IS 진입 컴포넌트 | 다음 호출 | 구조상 주의점 |
|---|---|---|---|
| TCF ON | `entry.handler` | `application.facade` | 표준 경로 |
| TCF OFF | `application.controller` | 주로 Service 직접 호출 | Facade TX 우회 가능 |
| TO-BE 직접 HTTP | `entry.web` | `entry.facade` | 외부 Adapter 책임 명확화 |

Controller를 Application에 둔다고 실행이 즉시 실패하는 것은 아니다. 문제는 구조적 의미다. HTTP Annotation, Servlet 계약과 CORS 같은 외부 관심사가 유스케이스 계층에 섞이면 Application을 다른 채널에서 재사용하기 어려워진다.

## 3.4 Application 레이어

Application 레이어는 한 유스케이스가 어떤 순서로 수행되는지를 조정한다. “거래 파라미터를 조회한다”, “통제 정책을 등록한다”와 같은 업무 목적을 구현하되 HTTP와 SQL의 세부사항을 직접 소유하지 않는 것이 원칙이다.

AS-IS Application에는 Facade, Service와 TCF OFF Controller가 함께 있다. 이 가운데 실제 유스케이스 중심은 Facade와 Service다.

### Facade: 진입 계약과 유스케이스 경계

`mgcoa9000Facade`는 TCF가 넘긴 `Object dtoBody`를 구체 DTOin으로 변환하고 Service를 호출한다. 조회에는 `readOnly=true`, 쓰기에는 `rollbackFor=Exception.class`인 `@Transactional`을 선언한다. Timeout ON에서는 Worker TransactionTemplate이 연 기존 RDW 트랜잭션에 `REQUIRED`로 참여하고, Timeout OFF에서는 Facade 프록시가 트랜잭션을 시작한다.

Facade가 필요한 이유는 Handler와 Service 사이에서 외부 입력 형태, 유스케이스 단위와 트랜잭션 계약을 고정하기 위해서다. Facade가 없으면 Handler 또는 Controller마다 변환과 트랜잭션 선언이 흩어진다. 반대로 Facade 안에 SQL이나 상세 계산을 넣으면 얇은 조정 경계가 또 하나의 거대한 Service가 된다.

### Service: 업무 절차의 서술

`mgcoa9000Service`는 검색 조건과 페이징 값을 만들고 DAO의 count와 목록 조회를 호출한 뒤 결과 DTO를 조립한다. C/U/D 메서드는 필수 입력과 데이터 존재 여부를 확인하고 적절한 DAO 작업을 순서대로 수행한다. Service는 유스케이스 흐름을 읽을 수 있는 곳이어야 한다.

```text
Facade
  입력 DTO 변환 · TX 계약
      ↓
Service
  검증 → 조건 계산 → DAO 호출 → 결과 조립
      ↓
Persistence
```

Service에 HTTP 요청 객체나 `ResponseEntity`를 전달하면 Application이 웹 기술에 결합된다. Mapper statement ID를 여러 곳에서 직접 호출하면 Persistence 경계가 사라진다. Service는 필요한 DAO 또는 Client 인터페이스를 통해 외부 자원을 사용하고, 실패는 상위 경계가 rollback과 오류 응답을 결정할 수 있도록 전파해야 한다.

AS-IS에서는 Service가 검증, 계산, 흐름과 DTO 조립을 모두 맡는다. 규모가 작은 유스케이스에는 이해하기 쉽지만 규칙이 늘어나면 Service가 변경의 집중점이 된다. 이때 다음 절의 Rule 분리가 필요하다.

## 3.5 Domain Rule 레이어

Domain Rule은 입력값 검증, 자격 판단, 계산과 상태 전이처럼 업무 의미를 가진 규칙을 분리하는 영역이다. Service가 “무엇을 어떤 순서로 수행하는가”를 말한다면 Rule은 “어떤 조건이 유효하고 결과를 어떻게 판단하는가”를 말한다.

현재 `pdmg-service`에는 `application.rule` 패키지와 Rule 클래스가 없다. 거래 파라미터의 필수값·중복·존재 검증은 `mgcoa9000Service`에 있고, 거래통제 행 변환 규칙 일부는 `support.MgTxControlRowSupport`에 있다. 따라서 아래 구조는 TO-BE이며 AS-IS 호출로 읽어서는 안 된다.

```text
TO-BE 개념
Service
  ├─ Rule.validate(input)
  ├─ Rule.calculateCriteria(input)
  ├─ DAO.load(...)
  └─ Rule.decide(rows)
```

Rule을 분리하는 이유는 재사용보다 **업무 판단의 가시성**에 있다. 하나의 Service 메서드에 null 검사, 코드 변환, 날짜 계산, 권한 판단과 DAO 호출이 섞이면 무엇이 정책이고 무엇이 절차인지 구분하기 어렵다. 순수한 Rule은 DB와 HTTP 없이 단위 테스트할 수 있고 정책 변경의 영향을 좁힐 수 있다.

모든 `if` 문을 Rule 클래스로 옮기는 것은 과도하다. 한 메서드 안에서만 쓰이고 의미가 단순한 검사는 Service에 남길 수 있다. 여러 유스케이스가 공유하거나 변경 빈도가 높고 독립적으로 설명·시험해야 하는 판단을 Rule 후보로 삼는다.

Rule은 Controller, Handler와 DAO를 호출하지 않는다. 필요한 데이터는 Service가 조회하여 인자로 넘기고, Rule은 값 또는 판단 결과를 반환한다. Rule이 DAO를 직접 호출하면 업무 판단과 I/O가 다시 결합되어 순수 테스트와 의존 방향의 장점을 잃는다.

실패 모델도 구분해야 한다. 잘못된 사용자 입력과 정책 위반은 의미 있는 업무 예외로 표현할 수 있지만, Rule이 SQL 예외나 HTTP 상태를 만들어서는 안 된다. 외부 기술 오류는 해당 Adapter에서 Application이 이해할 수 있는 실패로 변환해야 한다.

## 3.6 Contract·DTO 레이어

Contract는 경계 사이에서 주고받는 데이터의 모양을 정의한다. PDMG의 `nhnis.mg.co.a.dto`에는 `*DTOin`, `*DTOout`, 목록 요소인 `*DTOSub0`와 일부 MsgJson 클래스가 있다. Service ID별 입출력이 명시된다는 점에서 온라인 거래 계약의 핵심이다.

```text
HTTP JSON dto
  → Facade의 ObjectMapper 변환
  → mgcoa9000S0DTOin
  → Service
  → mgcoa9000S0DTOout
  → ResponseBodyAdvice
  → JSON dto
```

DTO는 Entry와 Application 사이를 건너고 응답 경계까지 돌아온다. 현행 Service와 Controller도 같은 DTO를 직접 사용한다. Persistence DAO는 주로 `Map<String,Object>`를 사용하므로 DTO가 Mapper까지 일관되게 전달되는 구조는 아니다. 이는 현재 계약과 DB 파라미터 모델이 분리되어 있음을 뜻한다.

DTO에는 Bean 주입, DAO 호출과 트랜잭션 제어를 넣지 않는다. DTO가 Service를 호출하기 시작하면 데이터 계약이 실행 객체가 되고 직렬화·복제·테스트 시 예측하기 어려워진다. 출력 DTO가 HTTP 상태나 Response 객체를 소유하는 것도 Contract를 웹 기술에 묶는다.

AS-IS DTO는 공통 `DataObject`를 상속하고 `FieldProperty` 등 전문 직렬화 메타데이터를 포함한다. 따라서 완전히 기술 독립적인 Domain Entity는 아니다. 이를 순수 도메인 객체로 부르는 대신 “PDMG 전문 계약 객체”로 정의하는 편이 정확하다.

계약 변경은 호출자에게 영향을 준다. 필드 추가는 대체로 호환 가능하지만 필드명·타입 변경과 삭제는 UI, 샘플 전문, MsgJson 변환과 Service를 함께 확인해야 한다. 4장과 이후 전문 장에서 Service ID 및 DTO 네이밍과 계약을 더 구체적으로 다룬다.

## 3.7 Persistence 레이어

Persistence는 데이터를 저장하고 조회하는 기술 세부사항을 캡슐화한다. 현행 PDMG는 `persistence.dao`의 MyBatis Mapper 인터페이스와 `src/main/resources/rdw.mg.co.a`의 Mapper XML을 사용한다.

`mgcoa9000DAO`는 `@RDWMapper`가 붙은 인터페이스이며 조회, count, 존재 확인, 등록, 수정과 삭제 메서드를 선언한다. Mapper XML의 namespace는 DAO의 FQCN과 연결되고 statement ID는 DAO 메서드명과 대응한다.

```text
mgcoa9000Service
  → mgcoa9000DAO.mgcoa9000S0_S0(param)
      → namespace nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
          → statement mgcoa9000S0_S0
              → SQL
                  → RDW DataSource
```

DAO와 Mapper의 책임은 SQL 선택, 파라미터 바인딩과 결과 매핑이다. “고객이 우대 대상인가”, “중복 등록을 허용할 것인가” 같은 판단은 Persistence가 맡지 않는다. SQL에 업무 판단을 모두 숨기면 Service 코드만 읽어서는 규칙을 알 수 없고 데이터베이스 제품을 바꾸거나 Rule을 단위 테스트하기 어렵다.

반대로 성능상 DB에서 수행해야 하는 필터, 집계와 정렬까지 Java로 옮기는 것도 바람직하지 않다. 데이터 처리의 위치는 업무 의미와 데이터 규모를 함께 보고 결정한다. Persistence가 계산을 수행할 수는 있지만 그 계산의 업무 의미와 호출 순서는 Application이 소유해야 한다.

현재 DAO는 업무 Config 패키지의 `RDWMapper` Annotation을 import한다. 실행상 필요한 Mapper 식별 방식이지만 엄격한 클린 아키텍처 관점에서는 Persistence가 조립 패키지에 의존하는 형태다. TO-BE에서는 Annotation을 Persistence 내부 또는 공통 인프라로 이동하거나 표준 Mapper Scan 방식으로 결합을 줄이는 선택을 검토할 수 있다.

SQL 예외는 DAO에서 정상 결과로 위장하지 않고 상위로 전달해야 한다. 같은 `rdwTransactionManager`에 참여한 변경은 Application의 트랜잭션 경계에서 rollback된다. DAO가 자체 commit을 수행하면 Facade와 Worker의 원자성 보장을 깨뜨린다.

## 3.8 Client와 외부 연계

Client는 다른 WAS, REST API, 메시징 시스템 또는 외부 서비스를 호출하는 Adapter다. 데이터베이스를 호출하는 DAO와 네트워크 서비스를 호출하는 Client는 모두 외부 I/O를 다루지만 실패 모델과 계약이 다르므로 분리한다.

현재 `pdmg-service`의 `nhnis.mg.co.a.client`에는 `package-info.java`만 있고 실제 업무 Client 구현은 없다. 따라서 PDMG Service의 외부 연동 흐름을 AS-IS로 단정할 수 없다. `pdmg-ui`에는 Service Relay를 위한 `TransactionRelayService`가 있지만 이는 UI 모듈의 Client이며 마케팅 업무 Client의 구현 사례와는 경계가 다르다.

업무 외부 호출이 추가되면 Application Service가 Client의 명시적 계약을 호출하는 구조가 적합하다.

```text
Application Service
  ├─ DAO ───────→ 업무 DB
  └─ Client ────→ 외부 Service / tcf-eai
```

Client는 URL 조립, HTTP Header, 직렬화, 연결·읽기 타임아웃과 원격 오류 변환을 책임진다. 업무 Service는 “어느 외부 기능이 필요한가”를 결정하지만 RestClient나 WebClient의 세부 사용법을 직접 소유하지 않는다. 운영 Secret과 Token을 Service 로그에 출력하지 않는 것도 Client 경계의 기본 원칙이다.

외부 호출은 로컬 DB 트랜잭션과 원자적으로 commit되지 않는다. DB 변경 후 외부 호출이 실패하거나 외부 호출 성공 후 DB가 rollback될 수 있다. 단순히 Facade `@Transactional` 안에 Client 호출을 넣는다고 분산 트랜잭션이 되는 것이 아니다. 재시도, 멱등성, 보상 처리와 호출 순서는 별도의 아키텍처 결정이 필요하다.

저장소 공통 규칙은 외부 업무 서비스 호출에 `client` 계층과 `tcf-eai` 사용을 우선한다. 실제 Client가 생길 때는 timeout, 예외 매핑, 추적 Header와 테스트 대역을 함께 설계해야 한다.

## 3.9 Config와 Support

Config와 Support는 수직 업무 흐름의 한 단계라기보다 애플리케이션을 조립하고 반복 코드를 줄이는 보조 경계다. 둘을 같은 “공통” 폴더로 취급하면 역할이 다시 섞인다.

### Config: 기술 객체를 조립하는 곳

현행 `config`에는 `RdwDataSourceConfig`, `SecurityConfig`, `WebMvcConfig`, `CorsProperties`, `MybatisLogInterceptor`와 `RDWMapper`가 있다. `RdwDataSourceConfig`는 `spring.datasource.rdw` 설정으로 DataSource, SqlSessionFactory, SqlSessionTemplate과 `rdwTransactionManager`를 만든다. `@MapperScan`은 `persistence.dao`를 이 SqlSessionTemplate에 연결한다.

Config는 Bean 생성과 기술 연결을 책임지며 업무 순서를 실행하지 않는다. Config 클래스가 Service 메서드를 호출해 업무 데이터를 초기화하면 애플리케이션 기동과 유스케이스 실행이 결합된다. 조건부 Bean과 Profile 변경은 실행 경로 전체에 영향을 줄 수 있으므로 설정 키와 실제 생성 Bean을 함께 검토해야 한다.

### Support: 작고 순수한 도우미

`support.MgTxControlRowSupport`는 거래통제 유형 상수와 DB 행 변환 도우미를 제공하며 `mgcoa9001Service`가 사용한다. 외부 I/O나 Spring Bean 상태가 없는 도우미이므로 Support의 취지에 부합한다.

Support가 커지면 이름 없는 Domain Layer가 될 위험이 있다. 업무 판단이 중요한 클래스를 모두 `Utils`나 `Support`에 넣으면 변경 책임과 테스트 목적이 보이지 않는다. 여러 업무에서 설명 가능한 정책은 Rule로, 외부 I/O는 Client나 Persistence로, 기술 조립은 Config로 이동해야 한다.

Support가 Framework 내부 클래스나 Controller를 호출하는 것도 피한다. 아래 레이어 어디서나 사용할 수 있다는 편의 때문에 의존성의 우회로가 되기 쉽기 때문이다. 순수 입력을 받아 순수 결과를 반환하는 작은 범위로 유지하는 것이 안전하다.

## 3.10 컴포넌트별 책임

레이어가 변경 방향을 정한다면 컴포넌트는 실제 클래스가 무엇을 해야 하는지를 정한다. `mgcoa9000S0` 요청을 기준으로 각 컴포넌트의 책임을 한 번 더 연결해 보자.

```text
OnlineTransactionController(FW)
  Service ID와 dtoBody 추출
    ↓
TransactionDispatcher(FW)
  등록 Handler 선택
    ↓
mgcoa9000Handler(Entry)
  S0 → Facade 메서드 분기
    ↓
mgcoa9000Facade(Application AS-IS)
  Object → DTOin · Transaction 계약
    ↓
mgcoa9000Service(Application)
  검증 · 페이징 · DAO 호출 · DTOout 조립
    ↓
mgcoa9000DAO + Mapper XML(Persistence)
  SQL 바인딩 · 실행 · 결과 반환
```

| 컴포넌트 | 해야 하는 일 | 하지 말아야 할 일 | 대표 실패 |
|---|---|---|---|
| Controller | HTTP 요청 수신·외부 형식 변환 | SQL·업무 규칙 | 잘못된 Body/매핑 |
| Handler | Service ID 등록·Facade 분기 | DTO 조립·DAO 호출 | 미등록 거래 |
| Facade | 입력 변환·유스케이스 호출·TX 계약 | 상세 SQL·대규모 규칙 | 변환/트랜잭션 실패 |
| Service | 업무 절차와 조정 | HTTP 응답 조립·직접 commit | 업무 예외 |
| Rule | 검증·계산·판단 | Controller·DAO 호출 | 정책 위반 |
| DTO | 입출력 데이터 계약 | Bean 주입·실행 로직 | 역직렬화/계약 불일치 |
| DAO/Mapper | 데이터 접근과 매핑 | 채널 판단·업무 흐름 | SQL/연결 오류 |
| Client | 외부 호출과 기술 오류 변환 | 로컬 DB 역할 혼합 | 원격 timeout/오류 |
| Config | Bean과 기술 연결 조립 | 유스케이스 실행 | Bean/설정 오류 |
| Support | 작은 순수 도우미 | 잡다한 업무 로직 집적 | 잘못된 변환 |

이 표는 컴포넌트를 최대한 얇게 만들라는 뜻이 아니다. 각 컴포넌트가 자신의 책임을 충분히 수행하되 다른 변경 이유를 흡수하지 않게 하라는 기준이다. Service가 길어졌다는 이유만으로 무조건 분할하기보다, 길어진 원인이 정책·I/O·변환 중 무엇인지 찾아 해당 경계로 이동해야 한다.

정상 흐름에서는 각 컴포넌트가 아래 경계의 결과를 받아 자신의 결과로 변환한다. 실패 흐름에서는 예외를 의미 없이 잡아 정상 값으로 바꾸지 않고 상위 트랜잭션과 예외 처리기가 판단할 수 있도록 전달한다. 책임 분리는 오류의 소유권도 분리한다.

## 3.11 허용되는 의존 방향

의존 방향은 “누가 누구를 호출하는가”뿐 아니라 “어느 패키지의 타입을 import하는가”를 포함한다. 상위 정책이 하위 기술 세부사항에 직접 묶이지 않도록 위에서 아래로 흐르게 한다.

AS-IS의 핵심 의존은 다음과 같다.

```text
pdmg-ui ─HTTP→ pdmg-service

pdmg-fw interface
       ▲ implements
entry.handler ─→ application.facade ─→ application.service
                                              ├─→ dto
                                              ├─→ persistence.dao ─→ Mapper XML
                                              └─→ support

application.controller(TCF OFF) ─→ service 또는 일부 facade
config ─creates→ DataSource / TransactionManager / MyBatis / MVC
```

현행 DTO와 Persistence는 별도의 가지다. Service가 DTO와 DAO를 모두 사용하지만 DAO가 Service를 import하지 않는다. DTO 역시 Application이나 Persistence를 호출하지 않는다. `rg`로 확인한 현재 코드에는 DTO 또는 DAO가 Handler·Controller·Service를 역참조하는 구조가 없다.

목표 구조에서는 외부 Adapter를 Entry에 모으고 Application의 정책을 더 분명히 한다.

```text
entry/handler 또는 entry/web
  → entry/facade
    → application/service
      → application/rule
      → persistence/dao | persistence/mapper
      → client
```

여기서 “아래로만”이라는 표현을 물리적 층 번호로만 읽으면 Client와 Contract를 설명하기 어렵다. 핵심 규칙은 업무 정책이 외부 Adapter의 구체 기술에 역으로 종속되지 않는 것이다. Service가 필요한 포트를 인터페이스로 정의하고 외부 구현을 주입하는 방식은 런타임 호출이 밖으로 향하더라도 소스 의존을 안쪽으로 유지할 수 있다.

Framework와 업무의 관계도 같다. Dispatcher는 업무 Handler를 실행하지만 구체 업무 클래스를 의존하지 않는다. 공통 인터페이스를 업무가 구현함으로써 호출 방향과 소스 의존 방향을 분리한다.

## 3.12 금지되는 역방향 의존

역방향 의존은 낮은 수준의 기술 또는 내부 데이터가 상위 채널과 유스케이스를 알게 되는 구조다. 처음에는 메서드 하나를 재사용하는 편리한 선택처럼 보이지만, 테스트와 변경의 연쇄 비용을 만든다.

```text
금지 또는 강하게 피해야 하는 흐름

DAO ─X→ Service / Controller
Rule ─X→ Controller / Handler / DAO
Service ─X→ Handler / Controller
DTO ─X→ Service / DAO Bean
Handler ─X→ DAO
pdmg-fw ─X→ pdmg-service의 구체 업무 클래스
```

### Handler가 DAO를 직접 호출하는 경우

라우팅 코드가 SQL과 결합되고 Facade의 트랜잭션·DTO 변환을 우회한다. Timeout OFF나 TCF OFF에서 데이터 변경이 기대한 트랜잭션에 들어가지 않을 수 있으며 같은 업무를 다른 채널에서 재사용하기 어렵다.

### DAO가 Service를 호출하는 경우

데이터 접근 중 업무 흐름이 다시 시작되어 순환 의존과 재진입을 만들 수 있다. Mapper 테스트가 Spring Application 전체를 필요로 하게 되고 SQL 실패와 업무 실패의 경계가 사라진다.

### Service가 Controller 타입을 반환하는 경우

`ResponseEntity`, Servlet Request 또는 화면 모델을 Application에 넣으면 HTTP가 아닌 호출자가 Service를 사용하기 어려워진다. 업무 결과 DTO와 HTTP 상태 결정은 분리해야 한다.

### Framework가 업무 구현을 참조하는 경우

공통 FW를 배포하려면 특정 업무 모듈이 필요해지고 모듈 의존 방향이 순환한다. 신규 업무마다 FW를 바꾸게 되어 공통 안정성이 낮아진다. 해결책은 구체 클래스를 import하는 것이 아니라 Handler와 같은 추상 계약을 제공하는 것이다.

역방향 의존은 컴파일 오류로 즉시 드러나지 않을 수 있다. Spring의 넓은 Component Scan과 Bean 주입은 잘못된 방향도 실행 가능하게 만든다. 코드 리뷰, 패키지 규칙과 아키텍처 테스트로 의존 방향을 지속적으로 확인해야 한다.

## 3.13 PDMG와 클린 아키텍처 비교

PDMG는 레이어드 아키텍처를 사용하지만 엄격한 의미의 클린 아키텍처가 완성된 상태는 아니다. 클린 아키텍처의 핵심은 원형 다이어그램 자체가 아니라 중요한 업무 정책이 웹, DB와 Framework 세부사항에 의존하지 않는다는 의존성 규칙이다.

PDMG 구성요소를 클린 아키텍처 언어로 대응하면 다음과 같이 볼 수 있다.

| PDMG 구성 | 클린 아키텍처 관점 | 비고 |
|---|---|---|
| Controller·Handler | Inbound Adapter | 외부 요청을 유스케이스로 변환 |
| Facade·Service | Use Case | 트랜잭션과 업무 절차 조정 |
| Rule | Domain Policy | AS-IS에는 별도 패키지 없음 |
| DAO/Mapper | Outbound Adapter | DB 기술 구현 |
| Client | Outbound Adapter | AS-IS 실제 구현 없음 |
| DTO | Boundary Model | 현재 `DataObject` 기술 의존 포함 |
| pdmg-fw | Framework/Driver | 웹·TCF·Context·Timeout 인프라 |

현행 Service는 구체 DAO 인터페이스와 DTO를 직접 사용하고, DAO는 업무 Config의 `RDWMapper` Annotation을 사용한다. Controller와 Facade의 패키지도 목표 Entry 경계와 다르다. 따라서 “PDMG는 클린 아키텍처다”라고 단정하기보다 “레이어드 구조를 기반으로 의존성 규칙을 강화하는 중”이라고 표현하는 편이 정확하다.

클린 아키텍처를 도입한다고 모든 기술을 인터페이스로 감쌀 필요는 없다. 변경 가능성과 테스트 가치가 낮은 단순 Mapper까지 과도하게 추상화하면 코드만 늘어난다. 외부 시스템, 저장소 교체, 복잡한 Rule처럼 변경과 테스트 격리가 중요한 경계부터 포트를 도입한다.

PDMG에서 실용적인 판단 기준은 다음과 같다. 업무 정책을 Spring MVC 없이 시험할 수 있는가, Service가 SQL statement와 HTTP 세부사항을 동시에 알고 있지 않은가, FW를 수정하지 않고 신규 업무를 추가할 수 있는가, 외부 연동 실패를 Application 의미로 바꿀 수 있는가를 본다.

## 3.14 현재 구조와 목표 구조

현재 구조는 실제 샘플 거래를 실행하기에 완결되어 있다. Handler, Facade, Service, DAO/Mapper와 DTO가 존재하고 TCF ON 흐름이 동작한다. 목표 구조는 이 실행 기능을 부정하는 것이 아니라 신규 업무가 늘어날 때 변경 비용과 의존 혼선을 줄이기 위한 방향이다.

```text
AS-IS
entry.handler
  → application.facade
    → application.service
      → persistence.dao
      → dto / support

TCF OFF: application.controller → 주로 service 직접 호출
Rule: 없음
Client: package-info만 존재

TO-BE
entry.handler | entry.web
  → entry.facade
    → application.service
      ├─ application.rule
      ├─ persistence.dao | mapper
      └─ client
Contract: 외부 전문과 내부 모델의 경계 명확화
```

| 차이 | AS-IS 제약 | 목표 | 변경 시 영향 |
|---|---|---|---|
| Controller 위치 | Application에 HTTP 관심사 혼재 | `entry.web` | Component Scan, import, 테스트 |
| Facade 위치 | 유스케이스와 진입 조정의 의미 혼재 | `entry.facade` | Handler/Controller import, AOP/TX |
| Rule | Service에 규칙 집중 | `application.rule` 분리 | Service 테스트와 예외 계약 |
| TCF OFF | Service 직접 호출 다수 | Facade 경유 | TX와 DTO 변환 동작 변화 |
| Client | 구현 없음 | 명시적 외부 Adapter | timeout, 인증, 오류 변환 |
| Contract | 전문 DTO와 내부 모델이 동일 | 필요 시 경계 모델 분리 | 변환 코드와 호환성 |
| DAO Annotation | Config 패키지 의존 | 인프라 경계 정비 | Mapper Scan과 Bean 이름 |

구조 개선은 빅뱅 패키지 이동보다 거래 단위의 점진적 전환이 안전하다. 신규 거래는 목표 구조로 만들고, 기존 거래는 변경 필요가 생길 때 Controller → Facade → Service 경계를 먼저 통일한다. 다음으로 복잡한 정책만 Rule로 추출하고 실제 외부 연동이 생길 때 Client 계약을 만든다.

패키지를 이동할 때는 단순 컴파일만 확인해서는 부족하다. `PdmgApplication`이 `nhnis` 전체를 스캔하므로 구·신 클래스를 동시에 두면 동일 Bean 이름 충돌이 날 수 있다. `BizPrePostAspect`의 Service Pointcut, `@MapperScan`, Mapper namespace, TCF Handler 등록과 조건부 Controller 생성도 함께 검증해야 한다.

### 정상 구조를 확인하는 업무 시나리오

신규 조회 거래가 추가됐다고 가정하자. Handler는 Service ID를 등록하고 Facade만 호출한다. Facade는 입력 계약을 변환하고 트랜잭션 정책을 선언한다. Service는 Rule로 검색 조건을 검증한 뒤 DAO를 호출한다. DAO는 파라미터를 바인딩해 SQL을 실행한다. 어느 단계에서도 하위 컴포넌트가 상위 웹 타입을 참조하지 않는다. 이 구조라면 같은 Service를 배치나 다른 Adapter가 호출할 수 있다.

### 구조 위반을 찾는 실패 시나리오

Handler가 DAO를 직접 호출해 등록한 경우 TCF ON과 Timeout ON에서는 우연히 Worker 트랜잭션에 참여할 수 있다. 그러나 Timeout OFF 또는 TCF OFF에서는 같은 원자성이 보장되지 않는다. 실행이 된다는 사실이 올바른 레이어라는 증거가 아닌 이유다. 아키텍처는 특정 설정에서의 우연한 성공이 아니라 모든 지원 경로에서의 예측 가능성을 목표로 한다.

### 개발자 체크리스트

- 새 클래스의 변경 이유를 한 문장으로 설명할 수 있는가?
- Handler와 Controller가 Facade만 호출하도록 진입 경계를 유지했는가?
- Service가 HTTP 타입과 Mapper 세부사항을 직접 소유하지 않는가?
- 반복되거나 독립 시험이 필요한 업무 판단을 Rule 후보로 검토했는가?
- DTO에 Bean 주입과 실행 로직을 넣지 않았는가?
- DAO/Mapper가 업무 분기와 commit을 수행하지 않는가?
- 외부 API 호출을 DAO가 아닌 Client 경계에 두었는가?
- Config가 업무 유스케이스를 실행하지 않는가?
- Support가 이름 없는 대형 업무 계층으로 자라지 않았는가?
- 하위 패키지가 Entry나 웹 패키지를 import하지 않는가?

### 아키텍처 판단 포인트

AS-IS 패키지를 유지할지 목표 구조로 이동할지는 일관성, 호환성, 변경 빈도와 테스트 비용을 함께 보고 결정한다. 이름만 깨끗한 구조보다 호출 계약과 트랜잭션 의미가 일관된 구조가 우선이다. 이동한다면 Controller와 Facade의 물리적 위치뿐 아니라 TCF ON/OFF 호출, AOP Pointcut, Spring Transaction 프록시와 Mapper Scan을 하나의 변경 단위로 검증해야 한다.

### 핵심 정리

1. 레이어는 폴더 분류가 아니라 변경과 의존의 방향을 통제하는 경계다.
2. Framework는 공통 실행 기반을 제공하지만 구체 업무 규칙과 DTO를 알아서는 안 된다.
3. Entry는 외부 요청을 유스케이스 호출로 변환하며 Handler와 Controller가 여기에 해당한다.
4. Application은 Facade와 Service를 통해 입력 변환, 트랜잭션 계약과 업무 절차를 조정한다.
5. Domain Rule은 변경·재사용·독립 시험 가치가 있는 업무 판단을 분리하지만 AS-IS에는 별도 패키지가 없다.
6. DTO는 PDMG 전문 계약이며 순수 Domain Entity와 동일하지 않다.
7. Persistence는 SQL과 매핑을 책임지고 업무 흐름과 HTTP 응답을 소유하지 않는다.
8. Client는 외부 서비스 Adapter이며 로컬 DB 트랜잭션만으로 원격 호출 원자성을 보장할 수 없다.
9. Config는 기술 객체를 조립하고 Support는 작은 순수 도우미로 유지한다.
10. 목표 구조로의 전환은 거래 단위로 수행하고 Scan, Pointcut, Transaction과 Mapper를 함께 검증한다.
