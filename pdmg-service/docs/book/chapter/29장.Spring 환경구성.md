# 29장. Spring 환경구성

PDMG의 실행 구조는 코드만으로 결정되지 않는다. Spring Environment가 설정을 합성하고 바인딩과 조건부 Bean 평가를 거쳐 TCF, Filter, Timeout, DataSource와 JWT 경로를 선택한다. 이 장은 저장소에서 확인된 AS-IS와 운영 권고를 분리한다.

## 29.1 Spring Environment

Environment는 YAML, 외부 설정, 환경변수와 실행 인자를 하나의 조회 공간으로 합친다. `PdmgApplication`과 JWT 애플리케이션의 `@ConfigurationPropertiesScan("nhnis")`가 타입 안전한 설정 객체를 찾는다. 같은 바이너리도 최종 Property 값에 따라 Bean graph가 달라진다.

## 29.2 PropertySource 우선순위

프로젝트에서 확인된 흐름은 기본 `application.yml`, 활성 Profile 문서, Import된 파일, 외부 주입이다. 정확한 Spring Boot 우선순위는 실행 명령까지 함께 검증해야 한다. 운영값이 적용됐는지는 파일 내용이 아니라 시작 로그와 Environment 검사로 판정한다.

```text
application.yml → profile 문서/import → 외부 환경·실행 인자
→ Environment → binding/condition → Bean → Runtime
```

## 29.3 공통 설정

서비스 공통 문서에는 애플리케이션명, CORS, RDW H2, SQL 초기화, TCF ON, Timeout과 공통 Web/Filter ON이 있다. 이 값은 Profile 문서 밖이므로 모든 Profile의 기반이 된다. 특히 H2 설정이 공통에 있어 운영 외부 설정이 누락되면 잘못된 DB로 기동할 위험이 있다.

## 29.4 Local Profile

공통에서 `spring.profiles.active`를 local로 고정한다. local JWT 설정은 검증 비활성 의도를 담지만 실제 `DefaultFilter`는 `jwt.enabled`가 아니라 active 문자열이 local인지로 우회한다. 개발 편의가 운영에 승격되지 않도록 배포 시 활성 Profile을 명시적으로 덮어써야 한다.

## 29.5 Dev Profile

서비스에는 dev JWT 문서가 있지만 검증 활성값은 false다. DataSource·TCF·Timeout은 공통값을 상속한다. dev라는 이름만으로 운영 유사 보안을 기대할 수 없으며 최종 Environment를 검증해야 한다.

## 29.6 Prod Profile

AS-IS `application.yml`에는 prod Profile 문서가 없다. 따라서 운영 DB, Secret, JWT 검증과 로그 레벨이 저장소 안 prod 블록에서 제공된다고 설명할 수 없다. TO-BE는 승인된 외부 설정과 Secret Store를 사용하고 필수값 누락 시 기동 실패시킨다.

## 29.7 `@Value`

`DefaultFilter`는 active Profile과 application name을, `JwtProvider`는 `jwt.secret`을, 거래통제는 enabled 값을 `@Value`로 읽는다. 단일 값에는 간단하지만 그룹 검증과 IDE 지원이 약하다. Secret에는 fallback 실제값을 두지 않는다.

## 29.8 `@ConfigurationProperties`

`spring.datasource.rdw`, `nhnis.fw.timeout`, CORS, JWT 정책, 내부 호출 정책과 메시지 설정이 타입 객체로 바인딩된다. 관련 값은 한 클래스에 모으고 범위·필수값 검증을 추가하는 방식이 적합하다.

## 29.9 `@ConditionalOnProperty`

TCF ON이면 단일 Controller, Dispatcher, Handler, TCF Advice가 생성되고 업무별 직접 Controller는 사라진다. Timeout ON은 Worker Executor와 TransactionTemplate 구현을, OFF 또는 누락은 동기 구현을 만든다. Filter와 Legacy Web도 별도 조건이다. 설정 변경은 숫자 하나가 아니라 호출 graph 변경이다.

## 29.10 `application-fw-defaults.yml`

파일에는 JWT와 Storage 기본값이 있지만 저장소 검색에서 `spring.config.import`, PropertySource 또는 EnvironmentPostProcessor 연결을 찾지 못했다. classpath에 존재한다고 자동 적용된다고 볼 수 없다. 사용할 경우 애플리케이션이 명시적으로 Import하고 우선순위를 테스트해야 한다.

## 29.11 `exceptionCode.yml` Import

서비스와 JWT `application.yml`은 `spring.config.import: classpath:exceptionCode.yml`로 오류 사전을 연결한다. `ExceptionCodeProperties`가 `nhnis.exception`을 받는다. 다만 26장에서 확인했듯 모든 Exception Handler가 이 Properties를 소비하는 것은 아니다.

## 29.12 DataSource 설정

`RdwDataSourceConfig`의 `rdwDataSource()`는 `spring.datasource.rdw`를 HikariDataSource에 바인딩한다. 이어 Mapper XML, MyBatis Interceptor, SqlSessionTemplate과 `rdwTransactionManager`를 만든다. URL·Driver·계정 누락은 기동 또는 첫 연결 실패로 드러난다. 비밀번호는 외부 주입한다.

## 29.13 TCF 설정

`nhnis.fw.tcf.enabled=true`는 `/online` 중심 Handler 경로를 활성화한다. false 또는 일부 Controller의 matchIfMissing은 직접 Controller를 활성화한다. 전환 테스트에는 URL, Service ID dispatch, 예외 응답과 Transaction 경계를 함께 포함한다.

## 29.14 Filter·Interceptor 설정

Filter는 `nhnis.fw.commons.filter.enabled=true`에서 등록된다. Legacy Web 설정은 Response Advice와 업무 Aspect 등에 영향을 준다. Interceptor 자체 등록은 WebMvcConfig도 함께 확인해야 한다. Filter를 끄면 JWT뿐 아니라 GUID와 ServiceContext 생성도 사라진다.

## 29.15 타임아웃 설정

`nhnis.fw.timeout`의 enabled, milliseconds, pool-size, queue-capacity가 `OnlineTimeoutProperties`에 바인딩된다. ON이면 고정 크기 Worker Pool과 AbortPolicy Queue, `rdwTransactionManager` 기반 Executor가 생성된다. 값 변경은 처리량·거부·DB Connection 점유를 함께 바꾼다.

## 29.16 JWT 설정

발급 정책은 `nsight.security.jwt`의 issuer, audience, 수명, algorithm, JWKS, rotation과 denylist 값이다. 업무 검증기는 별도 `jwt.secret`을 사용한다. 두 설정군은 현재 RS256/HMAC 불일치 상태이므로 이름이 JWT라는 이유로 같은 계약이라 보면 안 된다.

## 29.17 UI 대상 서버 설정

UI는 자체 `application.yml`과 브라우저 config를 통해 업무·JWT 대상 URL을 제공하며 JavaScript에는 localhost fallback도 있다. 환경별 URL은 빌드 산출물 하드코딩보다 서버 제공 config로 관리하고 CORS allowed origins와 함께 변경한다.

## 29.18 Secret 외부 주입

DB 비밀번호, JWT Secret, 내부 호출 공유키와 RSA Private Key는 Git YAML에 실제값을 두지 않는다. 환경변수 또는 승인된 Secret Store로 주입하고 로그·Actuator·오류 응답에서 숨긴다. 개발 fallback도 운영 Profile에서는 허용하지 않는다.

## 29.19 시작 시 설정 검증

기동 시 활성 Profile, TCF/Filter/Timeout 모드, DataSource 식별자, Pool 크기와 JWT 알고리즘을 비밀값 없이 요약한다. 필수 URL·Secret·양수 범위를 Bean Validation으로 검사하고 모순 조합은 시작 실패시킨다.

### 설정 로딩을 실제 실행으로 읽는 법

Spring 설정을 검토할 때 첫 단계는 파일 이름이 아니라 최종 Environment를 만드는 입력을 식별하는 것이다. 저장소의 `application.yml`은 공통 문서와 local·dev Profile 문서를 포함한다. 여기에 OS 환경변수, JVM System Property, 명령행 인자 또는 배포 플랫폼의 외부 설정이 더해질 수 있다. 그러므로 “dev 파일을 배포했다”는 설명만으로는 충분하지 않다. 실행 명령과 배포 Manifest에서 활성 Profile과 외부 키를 확인하고, 기동 후에는 비밀값을 제외한 유효 설정 요약으로 교차 검증한다.

현재 공통 문서가 `spring.profiles.active: local`을 선언한다는 사실은 특히 중요하다. 외부에서 Profile을 명시하지 않으면 local이 선택되고, `DefaultFilter`는 `jwt.enabled`가 아니라 active 문자열이 local인지에 따라 JWT 검증 전체를 건너뛴다. 이 때문에 운영 Pipeline은 “Profile 값이 존재한다”만 확인하지 말고 local이 아닌 승인된 값인지 검사해야 한다. 복수 Profile을 사용할 계획이라면 문자열 동등 비교가 의도대로 동작하는지도 테스트한다.

공통 영역의 H2 DataSource와 `spring.sql.init.mode=always`도 같은 위험을 가진다. 운영 DB 외부 주입이 누락되었는데 애플리케이션이 H2로 정상 기동하면 실패가 조기에 드러나지 않는다. TO-BE에서는 H2, Schema·Sample Data 초기화를 local 전용 문서로 이동하고, 운영은 JDBC URL, Driver, 사용자와 Secret이 없으면 시작 실패하도록 한다. prod 문서가 저장소에 없다는 사실은 외부 구성 방식이 잘못이라는 뜻은 아니지만, 외부 계약의 필수키·값 범위·소유자·회전 절차가 별도 배포 명세로 존재해야 한다.

Property 우선순위 장애는 “어떤 값이 이겼는가”와 “누가 그 값을 소비했는가”를 나눠 조사한다. 예를 들어 dev 문서의 `jwt.enabled`를 바꿔도 `DefaultFilter`는 그 키를 읽지 않는다. 반면 `nhnis.fw.commons.filter.enabled`는 Conditional Bean 등록 자체를 제어한다. 설정값이 Environment에 존재하는 것과 실행 흐름에 영향을 주는 것은 다른 문제다. `rg`로 키를 검색해 `@Value`, `@ConfigurationProperties`, `@ConditionalOnProperty` 소비자를 확인하고, Bean 존재와 실제 요청 결과를 검증해야 한다.

### 바인딩 방식과 실패 형태

`@Value`는 `spring.application.name`이나 단일 Timeout처럼 작은 값에 적합하지만, fallback은 누락을 숨긴다. `JwtProvider`의 `jwt.secret`처럼 필수 보안값에는 실제 형태의 기본값을 두어서는 안 된다. `DefaultFilter`가 Profile을 직접 문자열 비교하는 방식처럼 여러 값이 함께 정책을 이루면 전용 Properties와 검증 메서드로 캡슐화하는 편이 안전하다.

`@ConfigurationProperties`는 `spring.datasource.rdw`, `nhnis.fw.timeout`, CORS, JWT 발급 정책과 내부 호출 정책을 타입 객체로 묶는다. 이 방식은 키 목록을 한곳에 모으지만 자동으로 안전성을 보장하지 않는다. Timeout milliseconds와 Pool 크기가 양수인지, issuer와 audience가 비어 있지 않은지, 운영에서 Secret fallback이 금지되는지를 Bean Validation 또는 기동 Validator로 검사해야 한다. 잘못된 키 철자가 무시되어 Java 기본값으로 실행되는 사례도 Startup Test에 포함한다.

조건부 Bean은 실행 graph를 바꾼다. 주요 조합은 다음과 같다.

```text
TCF=true + timeout=true
  OnlineTransactionController → TcfFacade
    → Worker Executor + TransactionTemplate → Handler

TCF=true + timeout=false 또는 누락
  OnlineTransactionController → TcfFacade
    → SyncOnlineTimeoutExecutor → Handler

TCF=false
  업무별 Controller → Facade/Service

filter=false
  위 경로 앞의 JWT·GUID·ServiceContext 생성 없음
```

TCF 핵심 Bean은 enabled=true에서 생성되지만 여러 직접 Controller는 false이거나 키가 없을 때 생성된다. 따라서 키 오타가 조용히 TCF OFF 경로를 선택할 수 있다. `legacy-web`은 ResponseBody Advice, 공통 Web 설정과 업무 Aspect에 영향을 준다. TCF, Filter, Timeout, legacy-web은 독립 스위치이므로 지원 조합을 표로 고정하고, 지원하지 않는 조합은 시작 시 거부해야 한다. Filter만 끄면 인증뿐 아니라 GUID와 Context도 사라지고, legacy-web만 끄면 표준 응답 조립과 업무 선후처리가 달라질 수 있다.

### 설정 파일에서 Bean과 자원까지

RDW 경로는 비교적 명확하다. `spring.datasource.rdw`가 `RdwDataSourceConfig.rdwDataSource()`의 HikariDataSource에 바인딩되고, 같은 DataSource로 MyBatis SqlSessionFactory, SqlSessionTemplate과 `rdwTransactionManager`가 생성된다. 이 DataSource는 `@Primary`이므로 ImageLog와 Runtime Monitor의 단순 DataSource 주입에도 사용된다. DB Pool 장애는 업무 SQL뿐 아니라 이미지로그와 운영 조회까지 영향을 줄 수 있다. 검증은 JDBC 연결, Mapper XML 로딩, TransactionManager Bean 이름과 SQL init 모드를 포함한다.

Timeout ON에서는 `OnlineTimeoutProperties`의 milliseconds, pool-size, queue-capacity가 고정 크기 `ThreadPoolTaskExecutor`와 AbortPolicy를 만든다. Pool을 Hikari maximum보다 과도하게 키우면 Worker가 Connection을 기다리고, Queue를 크게 잡으면 overload 대신 오래 기다린 요청이 timeout된다. 정상 단건 테스트만으로는 설정을 검증할 수 없고 동시 요청, Queue 포화, 503, interrupt와 rollback을 확인해야 한다.

`application-fw-defaults.yml`은 파일이 존재하지만 검색 결과 명시적 Import, PropertySource, EnvironmentPostProcessor 연결이 없다. 따라서 classpath에 있다는 이유로 자동 적용된다고 설명할 수 없다. 이 파일의 JWT나 Storage 기본값을 신뢰하면 필수 Property 누락 또는 다른 개발 fallback 사용을 놓칠 수 있다. 사용하려면 애플리케이션에서 명시적으로 Import하고 애플리케이션 값이 기본값을 덮는 테스트를 작성한다.

반면 `exceptionCode.yml`은 서비스와 JWT `application.yml`의 `spring.config.import`로 명시 연결된다. 이것은 Property 로딩의 근거다. 그러나 오류 코드가 파일에 존재해도 모든 Handler가 `ExceptionCodeProperties`를 소비하지는 않는다. 설정 추적은 “파일 로드됨”에서 멈추지 않고 예외 생성, 메시지 조회와 응답 변환까지 이어져야 한다. DB `MessageCache`는 별도 메시지 체계이므로 YAML Import와 같은 흐름으로 합치지 않는다.

### JWT·UI·Secret의 환경 경계

JWT 발급과 업무 검증은 다른 설정군이다. `pdmg-jwt`의 `nsight.security.jwt`는 issuer, audience, Access/Refresh 수명, algorithm, JWKS, rotation과 denylist를 `JwtSecurityProperties`·RuntimePolicy로 전달한다. `pdmg-fw.JwtProvider`는 별도의 `jwt.secret`만 읽는다. JWKS URI를 설정했다고 업무 서비스가 RS256으로 검증하는 것은 아니다. 현재 발급 RS256과 검증 HMAC의 불일치는 설정 추가가 아니라 검증기 구현 전환과 통합 테스트로 해결해야 한다.

UI의 업무·JWT·Ontology 대상 URL도 환경 계약이다. 브라우저 config 조회가 실패하면 JavaScript의 localhost fallback이 사용될 수 있다. 운영에서 이를 허용하면 사용자는 잘못된 Target으로 요청하거나 단순 Network 오류만 보게 된다. TO-BE는 서버가 환경별 config를 제공하고 누락 시 화면을 차단하며, CORS allowed origins를 동일 배포 단위에서 관리한다.

환경변수 치환은 비밀이 아닌 설정에는 기본값을 둘 수 있지만 DB 비밀번호, JWT Secret, 내부 호출 공유키와 RSA Private Key에는 실제 기본값을 두지 않는다. 운영 Secret은 승인된 Store에서 주입하고 필수값 누락 시 시작 실패한다. 기동 로그에는 키 이름, 적용 여부와 키 버전 같은 비민감 정보만 남긴다. 실제값, 일부 문자열, Hash와 길이처럼 추정을 돕는 정보도 출력하지 않는다.

### 정상·실패 진단과 AS-IS/TO-BE

| 상황 | AS-IS 가능 결과 | 운영 진단 | TO-BE |
|---|---|---|---|
| Profile 외부 지정 누락 | local 활성, JWT 우회 | active Profile·Filter 분기 확인 | local 운영 배포 차단 |
| 운영 DB 덮어쓰기 누락 | 공통 H2와 init 사용 가능 | DataSource URL은 마스킹된 식별자로 확인 | 운영 필수키 미존재 시 실패 |
| TCF 키 오타 | 직접 Controller 경로 선택 가능 | Bean 목록·매핑과 호출 로그 확인 | 모순/누락 설정 Validator |
| Timeout 값 과소 | 504 증가, 취소 후 Worker 잔존 가능 | Queue·Worker·Hikari 함께 확인 | 범위 검증과 부하 테스트 |
| fw-defaults 적용 가정 | 실제 Property 누락 | Property 원천과 Import 확인 | 명시 Import 또는 제거 |
| JWKS만 설정 | HMAC 검증기는 변하지 않음 | 실제 JwtProvider Bean 확인 | RS256 Decoder 배포·검증 |

기동 성공의 정의도 강화해야 한다. 기대 Profile, TCF/Filter/Timeout mode, DataSource 연결, Handler Catalog, Mapper, TransactionManager와 JWT 필수정책이 준비된 상태여야 한다. 오류 메시지는 누락된 설정 키와 해결 방향을 보여주되 Secret 값은 포함하지 않는다. Readiness는 외부 자원 의존성과 지원 Bean 조합을 확인하고, 단순히 HTTP Port가 열렸다는 이유로 성공하지 않는다.

### 실행 경계와 점검표

| 설정 | 소비자 | AS-IS 영향 |
|---|---|---|
| `spring.datasource.rdw` | RdwDataSourceConfig | DB·MyBatis·TX 생성 |
| `nhnis.fw.tcf.enabled` | TCF/Controller 조건 | 진입 graph 교체 |
| `nhnis.fw.timeout.*` | TimeoutConfiguration | 동기/Worker 경로 |
| `nhnis.fw.commons.filter.enabled` | Filter | JWT·GUID·Context |
| `nsight.security.jwt.*` | pdmg-jwt | RS256 발급 정책 |
| `jwt.secret` | pdmg-fw | 현행 HMAC 검증 |

- prod 설정이 존재한다고 가정하지 않는다.
- fw-defaults가 자동 로딩된다고 가정하지 않는다.
- 활성 Profile을 파일명만으로 판단하지 않는다.
- Secret fallback과 실제값을 로그에 출력하지 않는다.
- TCF/Timeout 변경 후 Bean 목록과 호출 흐름을 통합 테스트한다.

다음 장에서는 이 지도를 사용해 설정 키 하나에서 Properties, 조건부 Bean, 호출부, 로그와 테스트까지 실제로 역추적하는 절차를 다룬다.
