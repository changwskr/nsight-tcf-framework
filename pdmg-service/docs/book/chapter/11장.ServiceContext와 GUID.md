# 제3부 온라인 요청과 TCF 프레임워크

# 11장. ServiceContext와 GUID

온라인 거래 한 건은 여러 계층을 지난다. Filter는 HTTP 요청을 읽고, Interceptor는 공통 정보를 보완하며, Controller와 TCF는 거래를 식별하고, 업무 계층은 Service와 DAO를 실행한다. 응답이 만들어지면 시스템 후처리와 ImageLog가 거래를 마감한다. 이 구간마다 Header, 사용자, Service ID와 추적값을 메서드 인자로 반복 전달하면 공통 코드가 업무 코드 전체를 침범한다. 반대로 어디서나 접근할 수 있는 전역 변수에 넣으면 요청끼리 데이터가 섞인다.

PDMG의 `ServiceContext`는 이 문제를 해결하기 위한 요청 단위 공통정보 저장소다. `ServiceContextHolder`는 현재 Thread가 처리하는 요청의 Context를 `ThreadLocal`에 보관한다. GUID는 Context, 표준 Header, MDC와 ImageLog를 연결하는 추적키다. 다만 Context가 있다고 해서 인증, DB Transaction 또는 Thread 전파가 자동으로 해결되는 것은 아니다. Context는 정보를 담을 뿐이고, 각 값의 신뢰 출처와 생명주기, Thread 전환과 정리를 호출 코드가 책임져야 한다.

현행 PDMG에는 특히 주의할 경계가 있다. Timeout Executor는 Request Thread의 Context와 MDC를 Worker에 명시적으로 설치하지만, 별도 불변 Snapshot을 만드는 대신 같은 `ServiceContext` 객체를 공유한다. JWT 검증으로 얻은 SSO Subject도 Request Attribute `ssoId`에 저장될 뿐 Header의 조작자나 `userContext`로 자동 연결되지 않는다. 이 장은 문서의 의도와 실제 코드를 분리해 이 경계를 설명한다.

## 이 장에서 해결할 질문

- `ServiceContext`는 어느 시점에 생성되고 누가 값을 보완하며 언제 제거하는가?
- Header, 요청·응답 원문, Servlet 객체와 `userContext`는 어디에서 오는가?
- `ServiceContextHolder`의 ThreadLocal과 로그 MDC는 무엇이 같고 무엇이 다른가?
- JWT로 검증한 사용자와 Client Header의 조작자는 현재 어떻게 연결되는가?
- GUID는 누가 생성하고 Context·Header·MDC·ImageLog에서 어떻게 일치시키는가?
- `TransactionContext`와 `ServiceContext`는 왜 별개이며 DB Transaction과는 어떤 관계인가?
- Worker 또는 임의 Async Thread로 이동할 때 무엇이 자동 전파되지 않는가?
- Context 정리를 누락하면 Thread Pool에서 어떤 보안·운영 장애가 생기는가?

## 전체 생명주기 지도

```text
HTTP Request                                      Request Thread
  │
  ▼
DefaultFilter
  ├─ Header/Body/JWT 검사
  ├─ ServiceContext 생성
  ├─ requestBody 저장
  ├─ ServiceContextHolder.setInstance
  └─ MDC(guid/ip/userId/serviceId) 설정
       │
       ▼
ServicePreventionInterceptor
  ├─ Header/sys_comm 보장
  ├─ GUID 보완: Context + Header + MDC
  └─ Pre ImageLog
       │
       ▼
Controller → TcfFacade
  └─ TransactionContext.fromCurrent
       │ ServiceContext 참조 캡처
       ▼
OnlineTimeoutWorkerContext.capture               Thread 경계
       │ submit
       ▼
Worker Thread
  ├─ install: Holder + MDC
  ├─ Handler → Facade → Service/DAO
  └─ finally clear: Holder + MDC
       │
       ▼
Request Thread
ResponseBodyAdvice → responseBody 저장
Interceptor.afterCompletion → Post/Exception ImageLog
DefaultFilter.finally → Holder.remove + MDC.clearAll
```

이 그림에서 GUID는 흐름을 연결하지만 실행을 제어하지 않는다. Transaction은 Worker의 `TransactionTemplate` 또는 업무 Facade가 관리하고, Timeout은 Executor가 관리한다. Context는 이 기능들이 같은 거래를 식별하도록 정보를 제공한다.

## 11.1 ServiceContext의 목적

`ServiceContext`는 HTTP 요청 한 건에서 Framework 계층들이 공유해야 하는 정보를 모은 객체다. 애플리케이션 이름과 Profile, HTTP Header Snapshot, Servlet Request/Response, 표준 `hdr_nhnis`, GUID, 요청 원문과 응답 원문을 담는다. 업무 DTO를 대체하거나 DB 상태를 보관하기 위한 객체가 아니다.

이 구분이 필요한 이유는 공통정보와 업무정보의 생명주기가 다르기 때문이다. GUID와 표준 Header는 Filter부터 응답 ImageLog까지 필요하다. 반면 조회 조건이나 등록 데이터는 특정 업무 메서드에서만 의미가 있다. 모든 업무 DTO를 Context에 넣으면 숨은 입력이 늘어나 테스트와 재사용이 어려워지고, 대용량 List가 요청 종료까지 살아 있어 Memory 사용도 커진다.

```text
ServiceContext가 전달하는 것
  ├─ 요청 식별: GUID, Service ID가 포함된 Header
  ├─ 접속 정보: HTTP Header, Request/Response 참조
  ├─ 환경 정보: applicationName, active profile
  ├─ 감사 정보: requestBody, responseBody
  └─ 확장 정보: userContext Map

ServiceContext가 관리하지 않는 것
  ├─ Spring DB Transaction
  ├─ JDBC Connection / SqlSession
  ├─ 업무 DTO의 생명주기
  ├─ 인증 정책 자체
  └─ Thread 전환의 자동 전파
```

Framework 개발자는 Context를 공통 계약으로 보고 필드를 추가할 때 모든 생성·복사·정리 경로를 검토해야 한다. 업무 개발자는 가능한 한 명시적인 DTO와 메서드 인자를 사용하고, GUID나 인증된 조작자처럼 요청 전역에서 일관돼야 하는 정보만 Context에서 읽는다. Context 접근이 많아질수록 코드의 입력이 소스에 드러나지 않는다는 비용이 생긴다.

## 11.2 ServiceContext 데이터 구조

현행 `ServiceContext`는 Lombok `@Getter`로 모든 필드의 Getter를 제공한다. 변경 가능한 Setter는 GUID, Header, 요청 원문과 응답 원문 네 개다. `userContext`에는 Setter가 없지만 반환된 `HashMap` 자체는 변경할 수 있다. 나머지 필드는 생성자에서 받아 이후 같은 참조를 유지한다.

| 필드 | 타입·성격 | 주 입력자 | 주요 소비자 |
|---|---|---|---|
| `applicationName` | 애플리케이션 이름 | DefaultFilter의 Spring Property | 진단·확장 코드 |
| `guid` | 거래 추적 문자열 | Filter, Interceptor 보완 | 로그·TCF·ImageLog |
| `active` | 활성 Profile 문자열 | DefaultFilter | 환경별 처리 판단 |
| `requestHeaders` | HTTP Header Snapshot | DefaultFilter | 공통 연계·진단 |
| `httpServletRequest` | Servlet Request 참조 | DefaultFilter | Controller/Framework 보조 |
| `httpServletResponse` | Servlet Response 참조 | DefaultFilter | 응답 관련 공통 처리 |
| `header` | 표준 `hdr_nhnis` | Body 파싱·Local 합성·Interceptor | Service ID, GUID, 감사 |
| `userContext` | mutable `Map<String,Object>` | 현재 명시적 표준 입력자 없음 | 확장 사용 가능 |
| `requestBody` | 요청 JSON 원문 | DefaultFilter | Interceptor·Pre ImageLog |
| `responseBody` | 응답 JSON 원문 | ResponseBodyAdvice | Post/Exception ImageLog |

`requestHeaders`는 Spring `HttpHeaders`에 복사한 값이지만 `httpServletRequest`와 `httpServletResponse`는 Servlet 객체의 직접 참조다. 따라서 ServiceContext 전체를 직렬화하거나 Cache, Session, Queue에 저장해서는 안 된다. Worker Thread로 전달할 때도 Servlet 객체의 Thread 안전성과 Request 완료 이후 유효기간을 고려해야 한다.

`userContext`는 문자열 Key에 Object를 넣을 수 있어 편리하지만 계약이 컴파일 시점에 보이지 않는다. `branchCode`와 `brc`처럼 Key가 갈리거나 타입이 달라지면 Runtime 오류가 난다. 표준 사용자정보가 필요하다면 명시적 immutable 타입으로 정의하고 출처·필수값·Masking 규칙을 함께 두는 편이 안전하다. 현행 Map을 사용한다면 Framework 소유 Key Namespace와 허용 타입을 문서화해야 한다.

요청·응답 원문은 장애 추적에 유용하지만 같은 Payload가 byte 배열, 문자열, JSON Tree와 DB ImageLog에 중복될 수 있다. Context에 저장한다는 선택은 최대 크기, Masking, 보존과 Memory 영향을 동반한다. Context를 일반적인 데이터 보관함처럼 사용하면 안 되는 이유다.

## 11.3 생성 시점

일반 JSON 요청에서 `DefaultFilter`는 Body를 읽을 수 있는 `CachedBodyHttpServletRequest`를 만들고 JSON을 파싱한다. 비 Local Profile이면 JWT를 먼저 검증한다. 표준 Header가 없으면 비 Local 요청은 거절하고, Local에서는 합성 Header를 만든다. 이후 GUID와 공통 Header 정보를 얻어 `ServiceContext`를 생성하고 요청 원문을 저장한 뒤 Holder에 등록한다.

```java
ServiceContext context = new ServiceContext(
        applicationName, guid, active, requestHeaders,
        wrapper, response, header);
context.setRequestBody(requestBody);
ServiceContextHolder.setInstance(context);
```

Holder 등록 전 오류와 등록 후 오류를 구분해야 한다. Token 누락·위조, 빈 Body 또는 JSON 파싱 오류는 Context가 만들어지기 전에 응답될 수 있다. Header 파싱 이후 Context가 등록된 뒤 하위 Chain에서 예외가 나면 Filter의 `finally`가 제거한다. 따라서 “모든 HTTP 오류에 Context와 GUID가 존재한다”고 가정할 수 없다.

multipart 요청은 일반 JSON과 다른 경로다. Filter가 `X-GUID` HTTP Header를 읽어 최소 `sys_comm`과 Header를 만들고 Context를 등록하지만 요청 원문은 저장하지 않는다. 앞 장에서 본 것처럼 Interceptor도 multipart 선처리 대부분을 건너뛴다. 파일 거래에 GUID와 감사가 필수라면 일반 거래와 동일하다고 가정하지 말고 별도 통합 테스트가 필요하다.

생성 시점은 Filter 활성 조건의 영향을 받는다. `nhnis.fw.commons.filter.enabled=true`로 Bean이 활성화돼야 표준 요청 경로에서 Context가 준비된다. Filter가 꺼진 Controller Test나 내부 호출에서는 Holder가 null일 수 있다. 업무 코드가 Context를 필수로 요구한다면 null일 때의 오류 계약을 명확히 하고, 단위 Test에서는 Fixture로 Context를 설치·정리해야 한다.

## 11.4 ServiceContextHolder

`ServiceContextHolder`는 정적 `ThreadLocal<ServiceContext>` 하나와 세 메서드만 가진다. `setInstance()`는 현재 Thread에 저장하고, `getInstance()`는 현재 Thread의 값을 반환하며, 없으면 null이다. `removeInstance()`는 현재 ThreadLocal Entry를 제거한다.

```java
ServiceContextHolder.setInstance(context);
ServiceContext current = ServiceContextHolder.getInstance();
ServiceContextHolder.removeInstance();
```

Holder가 단순하다는 것은 생명주기 책임도 호출자에게 있다는 뜻이다. Spring Request Scope처럼 Container가 자동으로 객체를 생성·파기하는 구조가 아니며, 자식 Thread에 자동 상속되는 `InheritableThreadLocal`도 아니다. Filter와 Worker Executor가 각각 자신의 Thread에서 설치와 제거를 명시적으로 수행한다.

정적 접근은 공통 코드에서 인자를 줄이지만 의존성을 숨긴다. Service 메서드 Signature만 봐서는 Context가 필요한지 알 수 없다. Filter 밖에서 Service를 호출하는 Batch, Test 또는 Message Consumer에서는 null이 된다. 업무 핵심값을 Holder에서 암묵적으로 읽는 대신 Facade에서 필요한 값을 추출해 명시적 인자로 전달하면 경계가 더 분명해진다.

Holder를 직접 사용하는 코드에서는 최소한 세 가지를 점검한다. Context null이 정상 가능한 경로인지, 읽은 값이 인증된 출처인지, 현재 Thread 종료 경로에서 반드시 제거되는지다. `getInstance()`가 null을 반환한다는 사실을 무시하고 연쇄 Getter를 호출하면 비 HTTP 경로에서 NPE가 발생한다.

## 11.5 ThreadLocal 저장

ThreadLocal은 “요청별 저장소”가 아니라 정확히는 “현재 Thread별 저장소”다. Servlet Container가 보통 요청 하나를 Thread 하나에서 처리하므로 요청 단위처럼 사용할 수 있을 뿐이다. Thread가 바뀌거나 한 Thread가 다음 요청에 재사용되면 결과가 달라진다.

```text
Request A → pool-thread-17
  Holder[A]
  처리 종료 후 remove

Request B → 같은 pool-thread-17 재사용
  Holder는 비어 있어야 함
```

Request A가 제거하지 않으면 Request B가 같은 Thread에서 A의 Header, GUID와 사용자 정보를 볼 수 있다. 이는 단순 로그 오염이 아니라 개인정보 노출, 잘못된 거래통제와 감사 오류로 이어질 수 있다. `ThreadLocal.set(null)`보다 `remove()`가 중요한 이유는 ThreadLocal Map의 Entry 자체를 제거하기 때문이다.

Log4j2 `ThreadContext`도 Thread에 연결되지만 목적이 다르다. ServiceContext는 Framework와 업무 코드가 읽는 구조화된 객체이고, MDC는 로그 Pattern에 GUID, Service ID, IP와 사용자 같은 문자열을 노출해 한 거래의 로그를 묶는다. Context에 값이 있어도 MDC에 넣지 않으면 로그 Pattern에는 나타나지 않고, MDC에 값이 있어도 Header가 자동 변경되지는 않는다.

| 구분 | ServiceContextHolder | Log4j2 ThreadContext |
|---|---|---|
| 저장 대상 | `ServiceContext` 객체 | 문자열 Key/Value Map |
| 주요 목적 | 코드 간 공통정보 전달 | 로그 상관관계 |
| 조회 방식 | `getInstance()` | `get`, Log Pattern `%X{}` |
| Thread 전파 | 자동 아님 | 자동 아님 |
| 정리 | `removeInstance()` | `clearAll()` |

두 저장소의 GUID가 어긋나면 업무 코드는 Context GUID를 사용하고 로그는 MDC GUID를 출력하는 불일치가 생긴다. 생성·보완 시 함께 갱신하고 Thread 전환 시 함께 캡처해야 한다.

## 11.6 계층별 Context 활용

Context는 모든 계층이 마음대로 쓰는 공유 Map이 아니다. 각 계층의 책임에 맞춰 제한적으로 사용한다. Filter는 생성자이며, Interceptor는 공통 Header와 GUID 보완 및 ImageLog 시작을 담당한다. Controller는 Service ID와 접속정보를 확인하고, TCF는 `TransactionContext`를 만들 때 현재 Context 참조를 캡처한다. 응답 Advice는 Header를 Echo하고 응답 원문을 저장한다.

```text
DefaultFilter                 생성·요청 원문
ServicePreventionInterceptor  GUID/Header 보완·ImageLog
OnlineTransactionController   Service ID 해석·Header 보조
TcfFacade                     TransactionContext 생성
BizPrePostAspect              GUID/Service ID 진행 로그
ResponseBodyAdvice            응답 Header·responseBody
afterCompletion               완료/예외 ImageLog
```

업무 Aspect는 현재 Context에서 GUID와 Header의 Service ID를 읽어 업무 선처리 진행 로그에 남긴다. Service나 DAO가 Context를 직접 읽지 않아도 같은 Worker Thread에 Context가 설치돼 있기 때문에 Aspect 로그가 가능하다. 그러나 이 편의성을 업무 데이터 조회로 확대하면 Layer 의존 방향이 흐려진다.

조작자와 영업점처럼 Audit에 필요한 값은 Facade에서 인증된 Context로부터 추출해 DTO 또는 명시적 Audit Value Object로 Service에 넘기는 방식을 고려할 수 있다. DAO가 Holder를 직접 호출하면 SQL 입력이 Method Signature에 보이지 않고 Batch 재사용도 어렵다. Framework Context의 소비는 Entry와 조정 계층에 가까울수록 안전하다.

Context가 null인 경로도 계층별로 다르게 처리해야 한다. Interceptor는 Warning 후 허용하고, `TransactionContext`는 null ServiceContext를 담을 수 있으며 `getHeader()`와 `getGuid()`는 null을 반환한다. 업무 로직이 인증 사용자 없이는 실행되면 안 되는 거래라면 이런 관대한 Framework 동작에 기대지 말고 진입 경계에서 명시적으로 거절해야 한다.

## 11.7 JWT 사용자정보 연계

비 Local JSON 요청에서 DefaultFilter는 Authorization Bearer Token의 서명과 Token Type을 `JwtProvider`로 검사한다. 검증이 성공하면 Subject를 `ssoId`로 얻어 Servlet Request Attribute에 저장한다.

```java
String ssoId = jwtProvider.getSsoId(token);
request.setAttribute("ssoId", ssoId);
```

여기까지가 현행 자동 연계 범위다. `ServiceContext.userContext`에 `ssoId`를 넣거나 Header의 `sys_comm.optr_eno`를 검증된 Subject로 덮어쓰는 코드는 DefaultFilter에 없다. Header의 조작자는 요청 전문에서 읽은 값이며, 비어 있을 때 공통 보완 로직이 `LOCAL` 등을 넣을 수 있다. 따라서 “JWT 검증 사용자와 Header 조작자가 동일함이 보장된다”고 말할 수 없다.

| 정보 | 출처 | AS-IS 저장 위치 | 신뢰 의미 |
|---|---|---|---|
| `ssoId` | 검증된 JWT Subject | Request Attribute | Token 검증 결과 |
| `optr_eno` | 요청 Header 또는 Local 보완 | `hdr_nhnis.sys_comm`·MDC | 자동으로 JWT와 대조되지 않음 |
| `userId` MDC | Header의 `optr_eno` | ThreadContext | 로그용 복사값 |
| `userContext` | 표준 입력 코드 없음 | 빈 mutable Map | 인증정보로 간주 불가 |

TO-BE에서는 인증된 Principal을 단일 신뢰 원천으로 정하고, Client가 보낸 조작자와 일치 검증하거나 서버 값으로 대체해야 한다. Header에 원 요청값을 보존해야 한다면 `claimedOperator`와 `authenticatedSubject`를 분리해 Audit에 남길 수 있다. 사용자정보를 Context에 넣을 때는 Token 전체나 Claim 전체를 복제하지 말고 필요한 최소 필드만 typed 객체로 보관한다.

JWT의 서명 알고리즘과 Key 관리 상세는 보안 장의 영역이다. 이 장에서 중요한 것은 검증 결과가 어느 저장소로 이동하고, 이동하지 않는 값은 무엇인지다. Token 문자열을 Context, MDC 또는 ImageLog에 저장하지 않는 원칙도 지켜야 한다.

## 11.8 GUID 생성 규칙

GUID는 HTTP 거래 한 건을 여러 로그와 ImageLog에서 연결하는 상관관계 식별자다. DB Transaction ID, Service ID 또는 업무 Primary Key와는 다르다. 한 HTTP 거래 안에서 DB Transaction이 여러 개 생길 수도 있고, 한 업무 요청이 외부 시스템의 여러 GUID로 분기될 수도 있다.

현행 일반 JSON 경로에서는 Header의 `sys_comm.std_gbl_id`를 우선 사용한다. Local에서 Header가 없으면 `syntheticLocalHeader()`가 하이픈을 제거한 UUID 문자열을 만든다. Header가 있지만 GUID가 비어 있는 경우 Interceptor가 `UUID.randomUUID().toString()` 형태로 보완할 수 있어 하이픈 유무가 경로별로 달라질 수 있다. multipart는 `X-GUID`를 그대로 가져오며 비어 있어도 Filter 자체가 새 값을 만들지 않는다.

```text
일반 Header GUID 존재 → 그 값 사용
Local Header 없음     → UUID 생성, 하이픈 제거
Interceptor까지 공백  → UUID 생성, 일반 문자열
multipart             → X-GUID 사용, 별도 생성 보장 없음
```

Interceptor의 `ensureGuid`는 선택된 값을 `ServiceContext.guid`, Header `std_gbl_id`와 MDC `guid`에 맞춘다. 이 세 위치가 같아야 요청 로그와 Pre/Post ImageLog가 같은 거래로 연결된다. Response Header도 Context Header를 기반으로 조립되므로 Client가 응답 GUID를 확인할 수 있다.

GUID의 형식보다 더 중요한 것은 유일성, 불변성과 신뢰 경계다. Client가 제공한 GUID를 그대로 신뢰하면 중복 또는 악의적 재사용으로 ImageLog 행이 갱신될 수 있다. 현행 ImageLog는 같은 GUID에 UPDATE를 우선하기 때문에 충돌이 최초 요청 증거를 덮을 가능성이 있다. 운영 표준은 서버 발급 여부, 허용 형식과 길이, 중복 처리, 외부 Correlation ID와 내부 GUID 분리를 결정해야 한다.

## 11.9 TransactionContext와의 관계

`TransactionContext`는 TCF 처리 구간에 필요한 얇은 실행 Context다. `TcfFacade.process()`가 `TransactionContext.fromCurrent(serviceId)`를 호출하면 현재 Thread의 `ServiceContextHolder`에서 객체 참조를 가져와 Service ID와 시작 시각과 함께 저장한다.

| 구분 | ServiceContext | TransactionContext |
|---|---|---|
| 생명주기 | Filter 진입 이후부터 응답 종료 | TcfFacade가 만든 뒤 TCF 실행 구간 |
| 전달 방식 | ThreadLocal Holder | 메서드 인자 |
| 주요 내용 | HTTP, Header, GUID, 전문 | Service ID, ServiceContext 참조, 시작 시각 |
| Thread 독립성 | 자동 전파 안 됨 | 객체 인자로 전달 가능 |
| DB Transaction | 관리하지 않음 | 관리하지 않음 |

`TransactionContext.getGuid()`와 `getHeader()`는 내부의 ServiceContext 참조를 통해 값을 반환한다. 즉 두 Context가 별도의 GUID 사본을 각각 관리하는 구조는 아니다. ServiceContext의 mutable 값이 변경되면 TransactionContext를 통해 보이는 값도 바뀔 수 있다.

이름에 Transaction이 포함돼도 Spring Transaction 상태나 JDBC Connection을 담지 않는다. `startedAtNanos`는 경과시간 계산 기준일 뿐 Commit/rollback 식별자가 아니다. 실제 Transaction은 Timeout Worker의 `TransactionTemplate` 또는 업무 Facade의 `@Transactional`이 시작한다. GUID로 동일한 로그를 찾을 수는 있지만 GUID가 같다는 사실만으로 같은 DB Transaction에 참여했다고 결론내리면 안 된다.

다음 장에서는 TransactionContext가 Dispatcher와 Handler에 어떻게 전달되는지를 자세히 본다. 여기서는 ServiceContext가 Web 생명주기의 넓은 범위를, TransactionContext가 TCF 호출의 좁은 범위를 표현한다는 차이를 기억하면 된다.

## 11.10 이미지로그와의 관계

ImageLog는 GUID를 Key로 요청과 응답, 예외 기록을 연결한다. Interceptor의 Pre 단계는 Context Header와 요청 원문을 `ImageLogHandler.preImagelog()`에 전달한다. ResponseBodyAdvice가 Context에 응답 원문을 저장하면 `afterCompletion`이 Post 또는 Exception ImageLog를 갱신한다.

```text
Context.guid / Header.std_gbl_id
          │
          ├─ Pre ImageLog: requestBody, 요청 시각
          ├─ Post ImageLog: responseBody, 결과
          └─ Exception ImageLog: 오류 정보
```

Context는 ImageLog의 데이터 공급자지만 저장 성공을 보장하지 않는다. ImageLogHandler는 여러 DB 오류를 내부에서 기록하고 업무를 계속하는 fail-open 성격이 있다. 업무가 Commit돼도 Post ImageLog가 실패할 수 있고, 업무가 Rollback돼도 Pre와 Exception ImageLog는 남을 수 있다. GUID는 이 독립된 결과를 묶어 조사하게 해줄 뿐 원자성을 만들지 않는다.

응답 원문은 ResponseBodyAdvice가 실행돼야 채워진다. multipart, Streaming 또는 응답 변환 이전 예외에서는 null일 수 있다. Pre만 남은 행을 즉시 업무 실패로 판정하지 말고 Filter/Interceptor 로그, Transaction 결과와 응답 처리 상태를 함께 본다.

민감정보 관점에서는 Context의 원문이 곧 ImageLog 입력이 된다는 점이 중요하다. Masking을 ImageLog 조회 화면에서만 하면 DB에는 원문이 남는다. 저장 전에 Field 기반 Masking과 크기 제한을 적용하고, GUID 검색 권한도 업무 권한과 별도로 통제해야 한다.

## 11.11 외부 시스템으로 GUID 전파

GUID의 가치가 PDMG 내부 로그에만 머물면 외부 API나 EAI 호출 이후 추적이 끊긴다. 외부 시스템 호출 시 Correlation Header 또는 표준 전문 Header로 GUID를 전달하고, 상대 시스템이 응답과 로그에 같은 값을 남기면 종단 간 추적이 가능하다.

그러나 현행 `ServiceContext`와 Filter 코드만으로 모든 외부 Client가 GUID를 자동 전파한다고 확인할 수는 없다. `requestHeaders`에 원 요청 Header가 있다는 사실과 outbound Client가 그 값을 사용하는 것은 별개다. 외부 전파는 `client` 계층이나 `tcf-eai` Adapter의 실제 코드와 계약으로 검증해야 하며, 확인되지 않은 자동 전파를 AS-IS로 기술해서는 안 된다.

```text
PDMG 내부 GUID
  ├─ 내부 Log/ImageLog 상관키
  └─ outbound adapter가 명시적으로 전달
        → External Correlation Header
        → 상대 시스템 Log
```

외부가 자체 Trace ID를 요구하면 내부 GUID를 무조건 대체하지 말고 Mapping을 남긴다. 하나의 내부 요청이 여러 외부 호출을 만들 때는 Parent GUID와 Call ID를 분리하면 재시도와 병렬 호출을 구분할 수 있다. 외부에서 받은 임의 GUID를 DB Key로 직접 신뢰하지 않고 형식·길이와 허용 문자를 검증해야 한다.

운영 Test는 Mock Server에서 실제 outbound Header를 캡처하고, 재시도 시 동일 Correlation ID를 유지할지 Call ID를 새로 만들지 확인해야 한다. 로그에 “전파했다”는 메시지만 남기는 것은 실제 Wire 전송의 증거가 아니다.

## 11.12 비동기 Thread에서의 Context

일반 `ThreadLocal`과 Log4j2 ThreadContext는 Executor Worker로 자동 이동하지 않는다. 현행 Timeout 경로는 이를 해결하기 위해 `OnlineTimeoutWorkerContext.capture()`를 Request Thread에서 호출한다. 이 객체는 현재 ServiceContext 참조, MDC 복사본, 진단용 GUID와 Service ID를 보관한다. Worker가 시작되면 `install()`이 Holder와 MDC를 설치하고, `finally`의 `clear()`가 둘을 제거한다.

```text
Request Thread
  Holder = ServiceContext A
  MDC = {guid, serviceId, ...}
        │ capture + submit
        ▼
Worker Thread
  install(A, copied MDC)
  TransactionTemplate → Handler/Service
  finally clear()
```

이것은 자동 전파가 아니라 Executor가 구현한 명시적 전파다. 따라서 개발자가 `CompletableFuture.supplyAsync`, `@Async`, 새 Thread 또는 다른 Scheduler를 직접 사용하면 같은 보장이 없다. 그 경로에서는 Holder가 null이고 MDC도 비어 있을 수 있다. 공통 TaskDecorator나 명시적 Snapshot 전달 없이 업무 코드가 Holder에 의존하면 비동기 환경에서만 재현되는 장애가 난다.

### AS-IS 공유 객체 위험

`OnlineTimeoutWorkerContext`의 주석은 Servlet Request/Response를 보관하지 않는다고 설명하지만 실제 필드는 원래 `ServiceContext` 객체 참조다. 새로운 안전한 Context를 만들지 않으므로 그 객체 안의 Servlet Request/Response와 mutable Header, `userContext`, request/responseBody도 함께 공유된다.

```text
Request Thread ─┐
                ├─ 같은 ServiceContext A
Worker Thread ──┘
```

정상적으로 Worker가 먼저 끝난 뒤 Request Thread가 응답을 만들면 경합이 드러나지 않을 수 있다. 그러나 Timeout에서 `cancel(true)` 이후 Worker가 Interrupt를 즉시 따르지 않으면 Request Thread는 Timeout 응답과 Context 후처리를 진행하는 동안 Worker가 같은 객체를 계속 볼 수 있다. Servlet 객체는 Worker에서 사용하지 않는 원칙이 필요하고, mutable 필드 동시 변경은 피해야 한다.

TO-BE에서는 Worker에 필요한 최소값만 immutable Snapshot으로 만든다. GUID, Service ID, 인증 사용자와 필요한 Header 사본을 전달하고 Servlet Request/Response와 원문 수정 권한은 Request Thread에 남긴다. Worker 결과는 명시적 반환값으로 Request Thread에 전달한다. 이 변경은 Context 필드 추가 때 Snapshot 누락을 막는 Test와 함께 수행해야 한다.

## 11.13 Context 정리

Request Thread의 최종 정리 소유자는 `DefaultFilter.finally`다. Holder가 존재하면 `removeInstance()`를 호출하고 MDC가 비어 있지 않으면 `ThreadContext.clearAll()`을 호출한다. Filter Chain의 정상 반환과 예외 모두 finally를 통과한다. Interceptor의 예외 `afterCompletion`에도 보조 제거가 있지만 Filter 전 단계에서 거절된 요청에는 Interceptor가 실행되지 않을 수 있으므로 Filter 정리가 필수다.

Worker Thread에서는 `DefaultOnlineTimeoutExecutor.runInWorker()`의 finally가 `workerContext.clear()`를 호출한다. 업무 정상, Runtime Exception, checked Exception Wrapper와 Deadline 초과 모두 이 경로에서 정리돼야 한다. Pool Thread는 재사용되므로 Worker 쪽 제거도 Request Thread 제거와 똑같이 중요하다.

| 실행 Thread | 설치 주체 | 주 정리 주체 | 누락 영향 |
|---|---|---|---|
| Servlet Request | DefaultFilter | DefaultFilter finally | 다음 HTTP 요청 오염 |
| Timeout Worker | WorkerContext.install | Worker Executor finally | 다음 업무 작업 오염 |
| 임의 `@Async`/Future | 개발자가 정의 | 개발자가 정의 | null 또는 이전 작업 유출 |

정리 Test는 작업 내부에서 Context가 존재하는지만 확인하면 부족하다. 요청 또는 Task가 끝난 뒤 같은 Pool Thread를 재사용하는 두 번째 작업에서 Holder와 MDC가 비어 있는지 확인해야 한다. 예외와 Timeout 경로도 각각 재현한다.

정리 순서에서 원인을 가리지 않는 것도 중요하다. cleanup 자체가 예외를 던져 원 업무 예외를 덮지 않도록 단순하고 안전하게 유지한다. Context 전체를 Error 로그로 출력한 뒤 제거하는 방식은 민감정보를 남기므로 금지한다.

## 11.14 Context 정보 보안

ServiceContext에는 단순 기술정보뿐 아니라 요청 Header, 사용자 식별자, IP, 전문 원문과 Servlet 객체가 들어 있다. 따라서 Context는 보안 경계 안의 민감한 요청 상태로 취급해야 한다. Debug 편의를 위해 객체 전체를 직렬화하면 Authorization Header, 개인정보와 업무 데이터가 로그에 노출될 수 있다.

보안의 첫 기준은 출처 구분이다. JWT 검증 Subject는 인증된 값이고, Client Header의 조작자·영업점·IP는 별도 검증이 필요하다. `X-Forwarded-For`는 신뢰 Proxy가 제거·재작성하는 배포 환경에서만 접속 IP 근거가 된다. `userContext`에 값이 있다는 사실만으로 권한 판단에 사용해서는 안 된다.

두 번째 기준은 최소 수집이다. Token 원문, Secret, 전체 Claim과 불필요한 개인정보를 Context에 복제하지 않는다. 요청·응답 원문은 Masking과 크기 제한을 거친다. `requestHeaders`를 외부 호출에 그대로 전달하면 Authorization이나 내부 Header까지 유출될 수 있으므로 outbound Allowlist를 사용한다.

세 번째 기준은 수명 제한이다. Context를 Singleton Field, Static Collection, Session, Cache 또는 비동기 Queue에 저장하지 않는다. 요청이 끝나면 ThreadLocal과 MDC를 제거하고, Worker Snapshot도 실행 종료와 함께 참조를 놓는다. Memory Dump에는 살아 있는 Context가 포함될 수 있으므로 장시간 Worker와 무제한 Queue도 보안 표면을 넓힌다.

| 위험 | 잘못된 사용 | 안전한 방향 |
|---|---|---|
| 인증 혼동 | Header 사용자=JWT 사용자로 가정 | 검증 Subject와 Claim 값 대조 |
| 로그 노출 | Context 전체 `toString()` | GUID·Service ID 등 허용 필드만 기록 |
| 외부 유출 | 모든 Request Header 복사 | outbound Header Allowlist |
| Thread 누수 | Holder/MDC 정리 누락 | 모든 종료 경로 finally 제거 |
| 공유 경합 | mutable Context를 Async에서 수정 | immutable 최소 Snapshot |
| 원문 과수집 | Body 무제한 저장 | Masking·크기·보존 정책 |

## 정상·실패 End-to-End 비교

### 정상 JSON 거래

```text
Filter: JWT/Header/Body 확인 → Context + MDC 설치
Interceptor: GUID 일치 → Pre ImageLog
Controller/TCF: TransactionContext 생성
Worker: Context/MDC 설치 → 업무 TX Commit → 정리
Advice: responseBody 저장
afterCompletion: Post ImageLog
Filter: Request Context/MDC 정리
```

### 인증 실패

```text
Filter: Token 누락/위조 발견
  → Context 생성 전 401 가능
  → Controller/Worker/ImageLog 미진입
  → Filter finally에서 남은 MDC 정리
```

### 업무 예외

```text
Pre ImageLog 완료
Worker: Service 예외 → 업무 TX Rollback → Worker Context 정리
Request Thread: 공통 오류 응답과 Exception ImageLog
Filter: Request Context 정리
```

### Timeout과 늦게 끝나는 Worker

```text
Request Thread: timeout 감지 → cancel(true) → 오류 응답 진행
Worker Thread: Interrupt를 늦게 인지하면 같은 Context 참조를 계속 보유
  → 종료 시 Rollback/clear가 이뤄지는지 별도 확인
Request Thread: afterCompletion + Filter cleanup
```

실패 유형마다 Context가 생성됐는지, 어느 Thread에 설치됐는지와 제거 주체가 다르다. GUID 검색 결과가 없다고 요청 자체가 없었다고 단정하지 않는다. Filter 조기 거절은 ImageLog 이전일 수 있다.

## 책임과 경계 표

| 구성요소 | Caller | 책임 | 전달·소비 | 금지 책임 |
|---|---|---|---|---|
| DefaultFilter | Servlet Container | Context/MDC 생성·Request 정리 | Interceptor/MVC | 업무 DTO 저장 |
| ServiceContext | Filter | 요청 공통정보 보유 | Framework 계층 | TX·Timeout 실행 |
| ServiceContextHolder | Filter/Worker | 현재 Thread Context 연결 | 호출 코드 | 자동 Thread 전파 |
| ThreadContext(MDC) | Filter/Worker | 로그 상관정보 | Log Pattern | 인증 원천 |
| Interceptor | Spring MVC | GUID/Header 보완 | ImageLog/Controller | 업무 데이터 변경 |
| TransactionContext | TcfFacade | TCF 최소 실행정보 | Dispatcher/Handler | DB Transaction 관리 |
| WorkerContext | Timeout Executor | Holder/MDC 명시 전파·정리 | Worker Action | Servlet 안전성 자동 보장 |
| ResponseBodyAdvice | Spring MVC | 응답 전문 Context 저장 | afterCompletion | 업무 성공 판정 |

## Anti Pattern

1. ThreadLocal이면 `@Async`와 Executor에도 자동으로 값이 전달된다고 생각한다.
2. `ServiceContext`를 Spring Transaction 또는 DB Session으로 취급한다.
3. GUID가 같으면 모든 SQL이 같은 DB Transaction이라고 결론낸다.
4. JWT Subject와 Header 조작자가 현재 자동 일치한다고 가정한다.
5. `userContext`의 임의 문자열 값을 인증·권한 판단에 사용한다.
6. 업무 DTO, 조회 List 또는 대용량 Binary를 Context에 넣는다.
7. Context와 MDC 중 하나만 Worker에 전파해 로그와 업무 식별값을 어긋나게 한다.
8. Timeout Worker와 Request Thread가 같은 mutable Context를 동시에 수정한다.
9. Servlet Request/Response를 Worker나 비동기 Queue에 장기간 보관한다.
10. Context 전체, Token 또는 요청 원문을 Masking 없이 로그로 출력한다.
11. `setInstance()`만 호출하고 Test·Batch·Worker 종료에서 제거하지 않는다.
12. 외부 호출 시 모든 inbound Header를 그대로 복사한다.
13. Client 제공 GUID의 중복·길이·문자를 검증하지 않는다.
14. Filter 이전 인증 실패도 ImageLog에 반드시 존재한다고 가정한다.

## 실전 검증 시나리오

| 시나리오 | 주입 조건 | 검증할 결과 |
|---|---|---|
| 정상 요청 | Header/GUID/JWT 유효 | Context·Header·MDC·ImageLog GUID 일치 |
| GUID 누락 | `std_gbl_id` 공백 | Interceptor 생성값과 응답값 일치 |
| JWT 사용자 불일치 | Subject와 `optr_eno` 다름 | AS-IS 자동 차단되지 않음을 확인 |
| Filter 비활성 | Context 생성 안 함 | Holder null 경로와 명시적 오류 정책 |
| Worker 실행 | Timeout Executor 활성 | Worker 내부 Holder/MDC 존재 |
| Worker 정리 | 같은 Pool Thread 재사용 | 두 번째 Task 시작 시 Holder/MDC 없음 |
| 업무 예외 | Service에서 예외 발생 | Rollback 뒤 Worker와 Request Context 정리 |
| Timeout | Interrupt에 늦게 반응하는 작업 | 응답 이후 Worker 상태와 공유 Context 영향 |
| multipart | 파일 요청 | 최소 Context와 GUID/ImageLog Skip 범위 |
| 응답 변환 실패 | Advice 처리 중 예외 | responseBody null 가능성과 Exception ImageLog |
| GUID 중복 | 같은 GUID로 두 요청 | ImageLog UPDATE와 감사 영향 |
| 외부 연계 | Mock Server 호출 | Wire Header에 실제 GUID가 있는지 확인 |

Test가 상위 `@Transactional`로 감싸져 있으면 ImageLog와 업무 Transaction 경계를 왜곡할 수 있다. Thread 전파 Test는 서로 다른 Thread 이름과 동일 GUID를 함께 기록하고, 정리 Test는 반드시 Pool Thread 재사용까지 확인한다.

## 운영에서 Context 장애를 추적하는 방법

Context 문제는 대개 업무 오류 코드 하나로 드러나지 않는다. 요청은 성공했는데 ImageLog UPDATE 대상이 없거나, Request Thread의 GUID와 Worker 로그의 GUID가 다르거나, 특정 사용자 로그에 직전 사용자의 Service ID가 섞이는 형태로 나타난다. 따라서 장애 조사도 Context의 생명주기 순서대로 진행해야 한다.

먼저 진입 로그에서 Filter가 기록한 Thread 이름, GUID와 Service ID를 확인한다. 같은 Request Thread의 Interceptor Pre 로그가 동일한 GUID를 갖는지 비교하고 Pre ImageLog 행을 조회한다. 다음으로 TCF와 Worker 로그에서 Thread 이름이 바뀌었는지, 바뀌었다면 GUID와 Service ID가 유지됐는지 본다. 업무 Commit 또는 Rollback 이후 Request Thread로 돌아온 응답 로그와 Post/Exception ImageLog가 같은 GUID를 사용하는지 확인한다.

```text
1. Filter 진입: Request Thread + 최초 GUID
2. Interceptor: 보완된 Context/Header/MDC GUID
3. Pre ImageLog: 저장 Key
4. Worker: Thread 전환 후 MDC/Context GUID
5. 업무 TX: Commit 또는 Rollback
6. Response Advice: responseBody와 응답 Header
7. afterCompletion: Post/Exception ImageLog Key
8. 다음 Pool 작업: 이전 Context 잔존 여부
```

Pre 행은 있는데 Post 행이 갱신되지 않았다면 단순히 업무 실패로 결론내리지 않는다. 응답 Advice가 실행되지 않은 유형인지, Context의 GUID가 중간에 변경됐는지, afterCompletion이 호출됐는지, ImageLog DB가 실패했는지를 차례로 확인한다. Worker 로그만 GUID가 없다면 `OnlineTimeoutWorkerContext.capture()` 이전에 MDC가 준비됐는지와 해당 작업이 표준 Timeout Executor를 거쳤는지 본다. 개발자가 별도 `@Async`나 `CompletableFuture`를 사용했다면 표준 전파가 적용되지 않는다.

서로 다른 사용자 요청이 같은 GUID 또는 Service ID로 찍히는 현상은 우선 Pool Thread 재사용 누수를 의심한다. 정상 요청만 반복하면 finally가 실행되기 때문에 재현되지 않을 수 있다. 예외, Timeout, Task 거절과 Client 연결 종료를 섞고 Pool 크기를 작게 만들어 같은 Thread의 재사용 확률을 높인다. 첫 번째 Task에 식별 가능한 Test 값으로 Context와 MDC를 설치하고 실패시킨 뒤, 두 번째 Task 시작 시 두 저장소가 모두 비어 있는지 Assert한다.

운영 로그를 늘릴 때도 Context 전체를 출력해서는 안 된다. Thread 이름, GUID, Service ID, Context 존재 여부, 전파 단계와 cleanup 결과처럼 최소 Metadata만 구조화한다. 사용자 ID와 IP는 필요 시 Masking하고 요청·응답 원문은 별도 접근통제된 ImageLog에서 확인한다. 장애 진단 가능성과 정보 최소화는 동시에 충족해야 한다.

마지막으로 로그의 동일 GUID는 상관관계를 보여줄 뿐 동시성 안전성이나 Transaction 원자성을 증명하지 않는다. Timeout 이후 Request와 Worker가 같은 객체를 공유했는지는 시각과 Thread 이름, Context 변경 지점을 함께 봐야 한다. DB 변경이 Rollback됐는지는 TransactionManager 로그와 실제 데이터로 별도 확인한다. GUID 검색을 출발점으로 사용하되 결론은 각 경계의 증거로 내린다.

## 아키텍처 판단 포인트

Context에 새 값을 추가할 때는 “요청 전체에서 정말 필요한가”를 먼저 묻는다. 특정 Service 한 곳만 사용하는 값은 Method Parameter가 더 적합하다. 공통 Audit 또는 인증값이라면 출처, 불변성, Masking과 Worker Snapshot까지 하나의 변경 범위로 본다. Field만 추가하고 전파·정리·Test를 빠뜨리면 실행 경로마다 값이 달라진다.

Thread 전파 방식은 복사와 공유 중 선택해야 한다. 현행 공유 참조는 구현이 단순하고 Header 변경을 즉시 볼 수 있지만 Timeout 경합과 Servlet 참조 위험이 있다. 비동기 실행이 늘어날수록 immutable 최소 Snapshot이 안전하다. Snapshot에는 업무에 필요한 값만 넣고 응답 원문처럼 Request Thread 소유 정보는 결과 반환으로 합친다.

GUID 정책은 Client 편의보다 감사 무결성을 기준으로 결정한다. 외부 Correlation ID를 수용하더라도 내부 유일 GUID를 별도로 발급해 Mapping할 수 있다. ImageLog가 GUID 하나로 UPDATE되는 구조라면 중복 재사용 정책을 더 엄격히 해야 한다.

인증정보는 단일 신뢰 원천을 가져야 한다. JWT Subject, Header 조작자, MDC 사용자와 `userContext`가 각각 독립적으로 존재하는 AS-IS에서는 값의 우선순위와 불일치 처리가 필요하다. 단순히 Context에 더 많은 값을 넣는 것으로 인증 통합이 완성되지는 않는다.

## 핵심 정리

`ServiceContext`는 Filter부터 응답 종료까지 HTTP 거래의 공통정보를 보관하고, `ServiceContextHolder`는 그 객체를 현재 Thread에 연결한다. Header, GUID, 요청·응답 원문과 Servlet 참조를 담지만 DB Transaction, Timeout 또는 인증정책 자체를 관리하지 않는다.

GUID는 Context, Header, MDC와 ImageLog를 연결하는 거래 추적키다. 생성 경로에 따라 형식이 다를 수 있고 Client 제공값의 중복 위험도 있으므로 유일성·불변성 정책이 필요하다. GUID는 DB Transaction ID가 아니며 같은 GUID 아래 여러 Transaction 결과가 존재할 수 있다.

JWT 검증 Subject는 현재 Request Attribute `ssoId`에만 저장된다. Header의 조작자, MDC 사용자와 `userContext`가 자동으로 인증 Subject와 일치하지 않는다. 보안 판단은 값의 존재가 아니라 검증된 출처와 일치 정책을 기준으로 해야 한다.

ThreadLocal과 MDC는 Worker로 자동 전파되지 않는다. Timeout 경로는 `OnlineTimeoutWorkerContext`가 명시적으로 설치·정리하지만 같은 mutable ServiceContext 객체를 공유한다. Timeout 이후 Worker가 계속 실행할 수 있는 상황에서는 경쟁과 Servlet 참조 위험이 있으므로 최소 immutable Snapshot이 개선 방향이다.

다음 장에서는 이 Context를 받아 TCF가 Service ID 기반으로 Dispatcher와 Handler를 실행하는 구조를 다룬다. ServiceContext가 HTTP 거래의 넓은 생명주기를 표현한다면 TransactionContext는 TCF 파이프라인의 실행 정보를 표현한다. 두 범위를 구분해야 TCF, Thread와 Transaction 흐름을 정확히 읽을 수 있다.
