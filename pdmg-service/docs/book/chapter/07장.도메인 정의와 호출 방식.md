# 7장. 도메인 정의와 호출 방식

PDMG에서 기능을 구현하는 일은 클래스를 어느 패키지에 넣을지 정하는 것으로 끝나지 않는다. 더 중요한 질문은 기능의 소유자가 누구인지, 다른 기능이 그것을 어떤 경계로 호출해야 하는지, 그 호출이 기존 거래의 컨텍스트와 트랜잭션을 어디까지 유지하는지 결정하는 일이다. 같은 JVM 안에 있는 Spring Bean은 기술적으로 서로 주입할 수 있지만, 주입할 수 있다는 사실이 곧 호출해도 된다는 뜻은 아니다.

이 장은 PDMG에서 사용하는 도메인이라는 말을 시스템, 업무, 세부업무, 프로그램, 거래의 다섯 관점으로 나누어 정의한다. 이어서 TCF ON/OFF, UI 직접/Relay, 내부 Java 호출과 외부 HTTP 호출, 동기와 비동기 호출을 하나의 판단 체계로 연결한다. 목표는 독자가 새로운 요구를 받았을 때 단순히 동작하는 호출이 아니라 변경과 장애를 견딜 수 있는 호출 경계를 선택하게 하는 것이다.

## 이 장에서 해결할 질문

- PDMG에서 도메인은 DDD의 도메인 모델이나 Java 패키지와 같은 뜻인가?
- 다른 프로그램의 Service나 DAO를 직접 호출해도 되는가?
- TCF ON과 OFF에서 실제 진입 경로와 트랜잭션 경계는 어떻게 다른가?
- UI 직접 호출과 UI Relay 호출은 무엇을 기준으로 선택하는가?
- Java 호출, HTTP 호출, 비동기 호출에서 GUID와 ServiceContext는 어떻게 이어지는가?
- 호출 경계와 트랜잭션 경계는 왜 같은 개념이 아닌가?
- 신규 도메인을 추가할 때 어떤 순서로 설계하고 무엇을 검증해야 하는가?

## 7.1 PDMG에서 도메인의 의미

일반적인 도메인 주도 설계에서는 도메인을 특정 업무 문제와 그 문제를 표현하는 모델의 영역으로 설명한다. Entity, Value Object, Aggregate, Domain Service 같은 개념이 중심이 된다. 그러나 현행 PDMG 소스에서 `domain` 패키지나 Aggregate 중심 모델은 확인되지 않는다. 현재 업무 코드는 프로그램 ID를 중심으로 Handler, Facade, Service, DTO, DAO, Mapper를 묶고, Service ID로 실행할 거래를 선택하는 트랜잭션 스크립트 성격이 강하다. 따라서 이 책에서 말하는 PDMG 도메인은 DDD 구성요소가 이미 구현되어 있다는 뜻이 아니다.

PDMG의 도메인은 **기능의 업무적 소유권과 호출 경계를 판단하기 위한 분류 단위**다. 물리적인 패키지는 그 분류를 코드로 표현하는 수단이며, Service ID는 실행 시점에 거래를 식별하는 계약이다. 세 개념은 서로 연결되지만 동일하지 않다.

```text
업무적 책임과 소유권
        │
        ▼
     도메인 경계
        │
        ├── 물리적 표현 ── 패키지 / 모듈
        │
        └── 실행 계약 ─── 프로그램 ID / Service ID
```

패키지가 다르다는 이유만으로 반드시 다른 도메인은 아니다. 같은 업무를 계층별로 나누면 `entry`, `application`, `persistence` 패키지는 달라도 하나의 업무 경계에 속한다. 반대로 같은 상위 패키지 아래에 있더라도 프로그램별 데이터와 변경 책임이 다르면 내부 구현을 함부로 공유해서는 안 된다. 도메인은 디렉터리 이름이 아니라 “누가 이 규칙과 데이터를 변경할 권한을 갖는가”라는 질문으로 판정한다.

PDMG의 분류는 다음처럼 좁혀진다.

```text
PDMG 시스템
  ├─ 시스템 도메인: TCF, Context, 보안, 예외, Timeout, Logging
  └─ 업무 도메인
       └─ 세부업무 도메인
            └─ 프로그램 도메인
                 └─ 거래 도메인(Service ID)
```

상위 분류는 조직과 책임을 설명하고, 아래로 갈수록 실행 단위가 구체화된다. 프로그램은 관련 거래와 클래스 집합을 묶으며, 거래는 한 번의 요청으로 수행되는 유스케이스를 뜻한다. 이 구분 덕분에 “같은 업무인가?”, “같은 프로그램인가?”, “별도 거래인가?”를 순서대로 질문할 수 있다.

## 7.2 시스템 도메인

시스템 도메인은 특정 업무 결과를 계산하지 않고 모든 업무 거래가 안전하고 일관되게 실행되도록 공통 실행 환경을 제공한다. `pdmg-fw`의 Filter, Interceptor, TCF Dispatcher, ServiceContext, Timeout, 트랜잭션 보조 기능과 `pdmg-jwt`의 인증·토큰 기능이 대표적이다. 이 기능들은 여러 업무에 공통으로 적용되지만, 그렇다고 업무 Service가 프레임워크 내부 구현을 자유롭게 호출해도 된다는 뜻은 아니다.

시스템 도메인의 핵심 책임은 다음과 같이 나뉜다.

| 영역 | 대표 책임 | 업무 코드가 기대하는 계약 |
|---|---|---|
| 요청 통제 | Filter, Interceptor, 접근·거래 통제 | 요청이 업무 진입 전에 검증됨 |
| 거래 라우팅 | TCF, Dispatcher, Handler Registry | Service ID가 올바른 Handler로 연결됨 |
| 실행 컨텍스트 | ServiceContext, TransactionContext, GUID | 한 거래의 식별·추적 정보가 유지됨 |
| 실행 제어 | Timeout, TransactionManager | 정해진 시간과 트랜잭션 정책 안에서 실행됨 |
| 보안 | JWT 발급·검증 및 인증 연계 | 검증된 사용자·권한 정보만 업무로 전달됨 |
| 오류·관측 | 예외 변환, MDC, ImageLog와 로그 | 실패가 표준화되고 GUID로 추적 가능함 |

업무 도메인은 이런 기능을 복제하지 않는다. 예를 들어 각 Service가 자체 GUID를 생성하거나, 각 Controller가 별도 Timeout Executor를 만들거나, 업무별로 JWT 서명을 검증하면 정책이 분산된다. 공통 기능의 변경이 모든 업무에 파급되고 종료 경로에서 ThreadLocal 정리가 누락될 위험도 커진다. 업무 코드는 공개된 컨텍스트와 TCF 계약을 사용하고 시스템 도메인의 생명주기를 존중해야 한다.

`pdmg-jwt`는 별도 애플리케이션이지만 PDMG 전체 관점에서는 인증 시스템 도메인이다. 토큰을 발급하는 주체와 토큰을 소비·검증하는 주체의 책임은 분리된다. 다른 업무가 JWT 내부 DAO나 키 관리 Service를 직접 주입하는 구조는 경계를 무너뜨린다. 다른 프로세스라면 공개 HTTP 계약을, 같은 애플리케이션 내부라면 명시적으로 공개된 인터페이스를 통해야 한다.

시스템 도메인과 업무 도메인의 관계는 상하 호출 관계라기보다 실행 틀과 실행 내용의 관계다.

```text
┌──────────────── PDMG 시스템 실행 틀 ────────────────┐
│ Filter → Interceptor → TCF → Timeout → TX → Error │
│             ServiceContext / GUID / MDC            │
│                         │                           │
│                         ▼                           │
│              업무 Handler / Facade                 │
│                  Service / DAO                     │
└─────────────────────────────────────────────────────┘
```

## 7.3 업무·세부업무 도메인

업무 도메인은 고객, 계약, 마케팅처럼 사용자가 해결하려는 업무 문제의 큰 축이다. 세부업무 도메인은 그 큰 축을 변경 책임과 데이터 소유권이 비교적 응집된 단위로 더 나눈 것이다. PDMG 네이밍에서 업무·세부업무 코드는 프로그램 ID와 패키지 경로에 반영된다. 현행 `pdmg-service`에서 확인되는 대표 업무 축은 `co.a`이며, 그 아래에 여러 프로그램이 배치되어 있다.

업무 코드가 패키지에 포함된 이유는 이름만 보고 소유 영역을 추적하게 하기 위해서다. 그러나 코드 한 글자가 곧 완전한 경계 보장을 제공하지는 않는다. Java 접근 제한이나 빌드 모듈이 세부업무 간 의존을 자동 차단하지 않으면 개발자는 다른 프로그램의 클래스를 주입할 수 있다. 아키텍처 규칙과 테스트가 필요한 이유다.

같은 세부업무 안의 호출도 목적에 따라 달라진다. 한 프로그램 안에서 Service가 자기 DAO를 호출하는 것은 정상적인 계층 호출이다. 다른 프로그램이 가진 계산이 필요하다면 먼저 그 계산이 정말 상대 프로그램의 내부 규칙인지, 여러 프로그램이 공동 소유해야 할 공통 규칙인지 판단해야 한다. 공동 규칙이라면 상위 업무 경계의 명시적 공통 Service나 Rule로 승격하는 편이 낫다. 상대 프로그램의 유스케이스를 실행해야 한다면 공개 Application 경계를 정의해야 한다.

다른 세부업무의 테이블을 읽기 위해 DAO를 직접 주입하는 방식은 가장 피해야 할 선택이다. DAO는 데이터 접근 구현이며 업무 계약이 아니다. 이 호출은 상대 업무의 검증, 권한, 상태 전이, 후처리를 건너뛰고 데이터 소유권을 침범한다. SQL이나 스키마가 바뀌면 호출자까지 동시에 수정해야 하며, 어느 도메인이 정합성을 책임지는지 불분명해진다.

다음 질문으로 업무 경계를 판정할 수 있다.

1. 이 기능의 업무 규칙을 승인하고 변경하는 주체는 누구인가?
2. 이 기능이 실패했을 때 복구와 운영 책임은 어느 팀에 있는가?
3. 데이터의 생성·변경 규칙을 어느 영역이 소유하는가?
4. 호출자가 필요한 것은 데이터인가, 완결된 유스케이스인가?
5. 호출 대상이 독립 배포되거나 프로토콜로 분리될 가능성이 있는가?

이 질문의 답이 다르면 같은 저장소 안에 있어도 다른 도메인 경계로 취급해야 한다.

## 7.4 프로그램 도메인

프로그램은 업무·세부업무 아래에서 관련 거래와 구현 클래스를 묶는 개발·운영 단위다. 현행 소스에는 `mgcoa5530`, `mgcoa8888`, `mgcoa9000`, `mgcoa9001`, `mgcoa9100`, `mgcoa9999` 프로그램이 확인된다. 프로그램 ID는 화면 번호와 닮을 수 있지만 화면과 항상 일대일인 것은 아니다. 한 화면이 여러 프로그램의 거래를 호출할 수 있고, 한 프로그램이 조회·등록·수정·삭제 거래를 함께 가질 수도 있다.

프로그램 경계는 다음 클래스 집합을 응집시킨다.

```text
mgcoa9000 프로그램
  ├─ entry/handler/mgcoa9000Handler
  ├─ entry/facade/mgcoa9000Facade
  ├─ application/service/mgcoa9000Service
  ├─ dto/mgcoa9000*DTO*
  ├─ persistence/dao/mgcoa9000DAO
  └─ resources/mapper/.../mgcoa9000*.xml
```

현행 TCF ON 구조는 프로그램별 Handler가 자신이 지원하는 Service ID 집합을 `serviceIds()`로 등록하고, `handle()`에서 Service ID에 따라 Facade 메서드로 분기한다. 따라서 Handler는 프로그램의 실행 입구이지만 업무 로직을 소유하지 않는다. DTO 변환과 유스케이스 조정은 Facade, 업무 흐름은 Service, 데이터 접근은 DAO/Mapper가 담당한다.

프로그램 사이에서 기능을 공유할 때는 클래스 이름이 비슷하다는 이유로 직접 호출하지 않는다. 조회 로직이 우연히 같더라도 데이터 소유자와 변경 주기가 다르면 중복보다 결합이 더 큰 비용을 만들 수 있다. 반대로 동일 규칙을 여러 프로그램이 계속 복제한다면 프로그램 외부의 명시적인 공통 업무 컴포넌트로 추출할 근거가 된다. 중요한 것은 “중복 제거”가 아니라 “변경 이유가 같은 코드의 응집”이다.

## 7.5 거래 도메인

거래는 클라이언트의 한 요청이 의미 있는 업무 결과로 끝나는 실행 단위다. PDMG에서는 Service ID가 거래의 대표 식별자다. 예를 들어 `mgcoa9000S0`, `mgcoa9000C0`, `mgcoa9000U0`, `mgcoa9000D0`은 같은 프로그램에 속하지만 조회, 등록, 수정, 삭제라는 서로 다른 유스케이스다.

```text
프로그램 mgcoa9000
  ├─ mgcoa9000S0 : 조회 거래
  ├─ mgcoa9000C0 : 등록 거래
  ├─ mgcoa9000U0 : 수정 거래
  └─ mgcoa9000D0 : 삭제 거래
```

Service ID는 단순 URL 문자열이 아니다. Dispatcher의 라우팅 키이며, ServiceContext와 로그에서 거래를 구분하는 운영 식별자이고, 화면 카탈로그와 샘플 전문을 연결하는 계약이다. Service ID를 추가하거나 바꾸면 Handler만 수정해서는 안 된다. UI 카탈로그, Controller 호환 경로, 샘플 요청, 테스트, 도움말과 운영 로그 기준도 함께 확인해야 한다.

현행 `pdmg-service` Handler에서 등록되는 거래는 13개다. `5530S0`, `8888S0/D0`, `9000S/C/U/D`, `9001S/C/U/D`, `9100S0`, `9999S0` 계열이 존재한다. 반면 현행 `pdmg-ui`의 `TransactionCatalog`는 일부 기존 거래만 등록하고 있어 백엔드 등록 목록과 완전히 일치하지 않는다. 이는 Service ID가 여러 모듈에 중복 관리될 때 생기는 AS-IS 위험이다. 신규 거래 검증은 서버 기동 성공만으로 끝내지 말고 UI 노출과 호출 가능성까지 확인해야 한다.

TCF ON에서 Service ID를 찾지 못하면 `TransactionDispatcher`는 `ServiceHandlerNotFound`를 발생시킨다. 같은 Service ID를 둘 이상의 Handler가 등록하는 것도 허용해서는 안 된다. 거래 식별자의 유일성은 애플리케이션 시작 시점에 검증되어야 한다. UI 카탈로그 역시 중복 등록을 조용히 덮어쓰는 방식보다 실패를 명확히 드러내는 편이 안전하다.

거래 경계는 트랜잭션 경계와 관련되지만 동일하지 않다. 하나의 Service ID 요청 안에서 데이터베이스 트랜잭션이 시작될 수 있으나, 외부 시스템 호출까지 같은 로컬 DB 트랜잭션이 자동 확장되지는 않는다. 또한 TCF OFF처럼 같은 거래를 다른 진입점으로 실행하면 트랜잭션 시작 위치가 달라질 수 있다.

## 7.6 도메인 간 의존 관계

호출 설계의 첫 원칙은 의존 방향을 안쪽으로 유지하는 것이다. PDMG 업무 코드는 `entry/handler → entry/facade → application/service → application/rule → persistence` 방향을 따른다. 실제 프로그램에 Rule이 없을 수는 있지만, 계층의 책임을 역전시켜도 된다는 뜻은 아니다.

```text
외부 요청
   │
   ▼
Handler / Controller
   │
   ▼
Facade ──────────────→ Client / 공개 Application Port
   │                              │
   ▼                              ▼
Service                       다른 도메인/시스템
   ├─ Rule
   └─ DAO → Mapper → DB
```

같은 프로그램 내부에서는 Handler가 Facade를, Facade가 Service를, Service가 자기 Rule과 DAO를 호출한다. Controller가 DAO를 직접 호출하거나 Handler가 SQL 결과를 조립하는 것은 계층을 위반한다. Web 진입점은 전문 해석과 라우팅만 담당해야 하며, 데이터 접근 세부사항을 알아서는 안 된다.

다른 프로그램 또는 도메인을 호출할 때의 권장 판단은 다음과 같다.

| 호출자 → 대상 | 허용 판단 | 권장 경계 | 이유 |
|---|---:|---|---|
| Service → 같은 프로그램 Rule | 허용 | Java 인터페이스 | 동일 업무 규칙 |
| Service → 같은 프로그램 DAO | 허용 | DAO 인터페이스 | 자기 데이터 접근 |
| Handler/Controller → DAO | 금지 | Facade·Service 경유 | 계층·정합성 보호 |
| 도메인 A → 도메인 B DAO/Mapper | 금지 | B의 공개 계약 | 데이터 소유권 침해 방지 |
| 도메인 A → 도메인 B 내부 Rule | 원칙상 금지 | 공통 규칙 승격 또는 공개 Port | 내부 구현 결합 방지 |
| 도메인 A → 도메인 B Service | 제한적 허용 | 명시적 공개 Application 인터페이스 | 기술 가능성과 허용을 구분 |
| 별도 애플리케이션 → PDMG | 허용 | HTTP/TCF 공개 거래 | 프로세스 경계 |
| PDMG → 외부 시스템 | 허용 | Client/Adapter | 프로토콜·오류 격리 |

Facade를 무조건 도메인 간 공개 API로 해석해서도 안 된다. 현행 Facade는 Handler가 넘긴 비정형 `dtoBody`를 업무 DTO로 변환하고 유스케이스를 조정하는 inbound 성격이 강하다. 다른 업무가 이 Facade를 호출하면 웹·전문 변환 책임에 결합될 수 있다. 내부 도메인 간 호출이 필요하다면 타입이 명확한 공개 Application 인터페이스를 별도로 정의하고, 어떤 트랜잭션에 참여하는지 계약에 포함하는 편이 낫다.

다른 Service를 직접 주입하는 방식은 다음 조건을 모두 만족할 때만 검토한다. 두 기능이 같은 배포 단위에 있고, 호출 대상이 내부 구현이 아니라 공개된 업무 계약이며, 호출 방향이 단방향이고, 같은 트랜잭션에 참여하는 것이 의도와 일치해야 한다. 이 조건을 충족하지 못하면 Client/API 경계를 사용하거나 공통 책임을 재배치한다.

### 호출 경계와 트랜잭션 경계

같은 Thread에서 Spring 프록시를 거친 Java 호출은 이미 시작된 트랜잭션에 참여할 수 있다. 그러나 메서드를 호출했다는 사실 자체가 트랜잭션을 만들지는 않는다. `@Transactional` 프록시, `TransactionTemplate`, TransactionManager와 전파 속성이 실제 경계를 결정한다.

HTTP 호출은 새로운 요청이며 대개 다른 Thread 또는 다른 JVM에서 실행된다. 호출자 트랜잭션의 JDBC Connection은 HTTP를 넘어가지 않는다. 호출자 DB 변경과 피호출자 DB 변경을 하나의 Spring 로컬 트랜잭션으로 원자화할 수 없다. 비동기 호출도 새 Thread에서 시작되므로 기존 Spring 트랜잭션을 상속하지 않는다. 이런 경계에서는 보상, 멱등성, 재처리와 상태 확인을 설계해야 한다.

### 금지해야 할 호출 패턴

다른 도메인의 DAO 직접 호출은 상대 도메인의 업무 규칙을 우회한다. Controller 간 호출은 HTTP 진입 계층을 업무 API처럼 오용한다. 다른 도메인의 내부 Rule 사용은 상대 구현 변경을 호출자 변경으로 확산한다. A→B→C→A의 순환 의존은 초기화 문제뿐 아니라 업무 책임과 장애 원인을 불명확하게 만든다. 외부 HTTP 호출을 각 Service에서 직접 구현하면 인증, Timeout, 오류 변환과 로깅 정책이 분산된다.

경계가 불명확할 때는 편한 클래스를 먼저 주입하지 말고 소유권을 먼저 결정해야 한다. 공개 계약을 만들기 어렵다면 도메인 분리가 잘못되었거나 호출 방향이 뒤집혔다는 신호일 수 있다.

## 7.7 TCF ON 호출

`nhnis.fw.tcf.enabled=true`이면 온라인 단일 진입점과 Service ID 라우팅이 활성화된다. 현행 실행 경로는 다음과 같다.

```text
Browser 또는 HTTP Client
        │
        ▼
DefaultFilter                       Request Thread
        │  ServiceContext/GUID 생성·바인딩
        ▼
ServicePreventionInterceptor
        │
        ▼
OnlineTransactionController
        │  serviceId 결정, dto 노드 추출
        ▼
TcfFacade
        │  TransactionContext.fromCurrent(serviceId)
        ▼
OnlineTimeoutExecutor
        │
        ├─ Timeout 비활성: 현재 Thread에서 다음 단계 수행
        │
        └─ Timeout 활성: Worker Thread로 제출
                         ServiceContext/MDC 복원
                         TransactionTemplate로 TX 시작
                                │
                                ▼
TransactionDispatcher
        │  serviceId → Handler 조회
        ▼
TransactionHandler
        │  serviceId별 Facade 메서드 분기
        ▼
Business Facade → Service → DAO/Mapper → DB
```

Controller는 Service ID를 ServiceContext의 헤더 값, 요청 JSON 헤더, URL 경로 순으로 판정한다. 현행 구현은 이 여러 값이 서로 다를 때 불일치를 거부하는 검증까지 수행하지 않는다. 따라서 클라이언트는 모든 위치에 일관된 Service ID를 사용해야 하며, TO-BE에서는 불일치를 조기에 차단하는 정책을 검토할 필요가 있다.

`TcfFacade`는 현재 ServiceContext에서 `TransactionContext`를 만들고 `OnlineTimeoutExecutor`에 Dispatcher 호출을 넘긴다. 오래된 흐름도에는 STF가 이 사이에 표시될 수 있지만, 현행 `TcfFacade.process()`에서 STF 직접 호출은 확인되지 않는다. STF 관련 컴포넌트가 존재한다는 사실과 현재 주 실행 경로에 연결되어 있다는 주장을 구분해야 한다.

Timeout이 활성화되면 Request Thread와 업무 Worker Thread가 달라진다. `OnlineTimeoutWorkerContext`는 ServiceContext와 MDC를 캡처하고 Worker에 설치한 뒤 종료 경로에서 정리한다. Spring 트랜잭션은 Thread에 결합되므로 Worker Thread 안에서 `TransactionTemplate`이 트랜잭션을 시작한다. Request Thread가 가진 ThreadLocal이나 트랜잭션이 자동으로 넘어가는 것이 아니다.

Dispatcher는 시작 시 모든 `TransactionHandler`의 `serviceIds()`를 수집해 Registry를 구성한다. 호출자는 실제 Handler 클래스 이름을 알 필요가 없다. 등록되지 않은 ID면 업무 Service까지 진입하지 않고 라우팅 오류가 발생한다. Handler에서 발생한 업무 예외는 상위 경계로 전파되어 트랜잭션 롤백 판단과 공통 예외 변환의 입력이 된다. 예외를 Handler나 Service에서 삼키고 정상 객체로 바꾸면 상위 계층은 실패를 알 수 없어 커밋될 수 있다.

정상 흐름에서는 동일한 TransactionContext가 Dispatcher와 Handler로 전달되며 Service ID, GUID, 시작 시각을 조회할 수 있다. 성공 결과는 다시 Request Thread로 전달되어 응답 후처리를 거친다. Timeout이 나면 Request Thread는 제한 시간에 따라 오류를 반환할 수 있지만, JDBC 드라이버와 작업 코드가 interrupt에 즉시 반응한다는 보장은 없다. 호출 설계 단계에서 느린 외부 호출과 DB 작업의 자체 Timeout도 함께 고려해야 한다.

## 7.8 TCF OFF 호출

`nhnis.fw.tcf.enabled=false`는 TCF 기능 하나만 끄는 단순 스위치가 아니다. 조건부 Bean 구성이 달라지고 업무별 호환 Controller가 활성화된다. 현행 `pdmg-service`의 실제 경로는 다음과 같다.

```text
HTTP Client
   │
   ▼
DefaultFilter → ServicePreventionInterceptor
   │
   ▼
업무별 Controller
   │
   ▼
Business Service
   │
   ▼
DAO / Mapper / DB
```

중요한 AS-IS 사실은 업무별 Controller가 Business Facade가 아니라 Service를 직접 호출한다는 점이다. 따라서 TCF ON의 `OnlineTransactionController`, `TcfFacade`, `OnlineTimeoutExecutor`, `TransactionDispatcher`, `TransactionHandler`와 업무 Facade를 건너뛴다. Service에 적용되는 업무 선후처리 Aspect는 Spring 프록시를 통해 호출되므로 여전히 실행될 수 있지만, 진입점과 외곽 트랜잭션·Timeout 경계는 ON과 동일하지 않다.

TCF OFF 경로에 별도의 `@Transactional` 또는 TransactionTemplate이 없다면 단지 DAO를 호출한다는 이유로 ON과 같은 거래 단위 트랜잭션이 생기지 않는다. 데이터 접근 기술의 개별 자동 커밋 동작에 의존할 수 있으므로 복수 변경의 원자성을 기대해서는 안 된다. 이 차이는 호환 모드 테스트에서 반드시 검증해야 한다.

| 항목 | TCF ON AS-IS | TCF OFF AS-IS |
|---|---|---|
| 업무 진입점 | 공통 OnlineTransactionController | 업무별 Controller |
| Service ID Registry | 사용 | 사용하지 않음 |
| Handler | 사용 | 사용하지 않음 |
| 업무 Facade | 사용 | 현행 Controller 경로는 건너뜀 |
| OnlineTimeoutExecutor | 사용 | 건너뜀 |
| 외곽 TX | Executor/Facade 구성에 따름 | 별도 선언이 없으면 동일 경계 없음 |
| Service Aspect | 실행 | Service 프록시 호출 시 실행 |
| 공통 Filter/Interceptor | 조건에 따라 공통 적용 | 조건에 따라 공통 적용 |

TO-BE 권장 방향은 ON과 OFF가 진입 방식만 다르고 동일한 Business Facade 이하를 공유하게 하는 것이다. 즉 OFF Controller도 타입이 명확한 Facade를 호출하게 만들면 DTO 변환, 트랜잭션 경계와 유스케이스 조정이 수렴한다. 다만 이것은 현행 사실이 아니라 변경안이며, 적용할 때 기존 URL 계약과 트랜잭션 중첩, 업무 선후처리 위치를 회귀 테스트해야 한다.

## 7.9 UI 직접 호출

현행 `pdmg-ui`의 주요 화면은 브라우저가 `pdmg-service`를 직접 호출하는 구조다. 화면 초기화 시 UI 서버의 `/api/transactions`와 `/api/config`에서 거래 카탈로그와 대상 기본 URL을 읽고, 사용자가 선택한 Service ID와 요청 전문으로 대상 URL을 구성한다.

```text
Browser
  ├─ GET pdmg-ui /api/transactions
  ├─ GET pdmg-ui /api/config
  │
  └─ POST pdmg-service /{serviceId}
          Authorization / 업무 Header / DTO
```

직접 호출의 장점은 중계 서버를 한 번 덜 거치므로 구조가 단순하고 Relay의 연결·처리 비용이 없다. 브라우저 개발자 도구에서 요청과 응답을 직접 확인하기도 쉽다. 반면 브라우저가 업무 API 주소를 알고 있어야 하고, `pdmg-ui`와 `pdmg-service` Origin이 다르면 CORS 정책이 정확해야 한다. 인증 토큰과 표준 헤더 구성도 브라우저 코드의 책임이 된다.

UI는 Service ID를 단순 화면 라벨로 취급해서는 안 된다. 카탈로그의 ID, URL 경로, 전문 헤더의 서비스 코드가 백엔드 Handler 등록과 일치해야 한다. 현재 UI 카탈로그가 모든 백엔드 거래를 포함하지 않는 점은 신규 프로그램 추가 시 동시 변경이 필요하다는 실제 사례다.

직접 호출 실패는 크게 세 구간에서 구분한다. 브라우저 단계의 CORS·네트워크 오류, TCF 진입 전 인증·통제 실패, Service ID 라우팅 이후 업무 실패다. 모두 화면에서는 “호출 실패”로 보일 수 있지만 서버 로그 존재 여부와 GUID를 기준으로 구간을 좁혀야 한다. 브라우저가 GUID를 생성하거나 받은 값을 표준 헤더로 전달하지 않으면 서버가 만든 GUID와 화면 추적값을 연결하기 어렵다.

## 7.10 UI Relay 호출

UI Relay는 브라우저가 업무 서비스를 직접 호출하지 않고 `pdmg-ui`의 중계 API로 요청을 보내는 방식이다. 현행에는 `PdmgUiApiController`와 `TransactionRelayService`가 존재하며, Relay Service는 `RestClient`로 대상 서비스에 POST한다. 다만 소스 주석이 명시하듯 현재 일반 화면의 주 경로는 직접 호출이고 Relay는 카탈로그·대상 URL 계산과 하위 호환 중계 목적으로 유지된다.

```text
Browser
   │ POST /api/relay/{transactionId}
   ▼
pdmg-ui PdmgUiApiController
   │
   ▼
TransactionRelayService
   │ RestClient POST
   ▼
pdmg-service /{serviceId}
```

Relay는 브라우저에서 본 CORS 문제를 줄이고 백엔드 주소를 서버 쪽에서 통제하며 공통 인증·감사 정책을 넣을 지점을 제공할 수 있다. 반면 네트워크 홉과 장애 지점이 하나 늘고, Relay의 Thread와 Connection Pool이 업무 서비스 지연의 영향을 받는다. 브라우저가 받은 응답도 대상 서비스의 원문과 동일하지 않을 수 있다. 현행 Relay는 대상 ID, URL, HTTP 상태, 경과 시간, 응답 Body를 `RelayResult`로 감싸 반환한다.

현행 `TransactionRelayService`는 요청에서 전달된 `baseUrl`이 있으면 설정의 기본 URL 대신 사용할 수 있고, 임의 경로를 중계하는 기능도 갖는다. 운영 환경에서 입력 URL의 허용 목록과 내부망 접근 제한이 없다면 서버 측 요청 위조 위험이 생길 수 있다. 따라서 이 기능을 공개할 때는 scheme, host, port와 path를 설정 기반 허용 목록으로 검증하고 외부 입력을 그대로 `URI.create()`에 넘기지 않아야 한다.

Relay를 선택한다고 기존 요청의 Spring 트랜잭션이나 ServiceContext가 대상 서비스까지 이어지는 것은 아니다. Relay HTTP 요청과 대상 HTTP 요청은 서로 다른 요청이다. GUID와 인증 정보를 계속 사용하려면 허용된 표준 헤더를 명시적으로 복사해야 하며, 민감한 헤더를 무차별 전달해서도 안 된다. Relay Timeout은 대상 서비스 Timeout보다 약간 큰 외곽 예산으로 설계하되 무한 대기를 허용하지 않는다.

## 7.11 외부 시스템 호출

외부 시스템 호출은 다른 PDMG 프로그램의 Java 메서드를 부르는 것과 다르다. 프로세스, 네트워크, 인증, 데이터 계약과 장애 모델이 모두 분리된다. 따라서 업무 Service가 `RestClient`나 `WebClient`를 즉석에서 생성하지 않고 `client` 또는 Adapter 경계를 통해 호출하는 것이 원칙이다.

```text
Business Service
      │ 업무 의미가 있는 메서드
      ▼
Client Interface
      │ 요청/응답 변환, 인증, Timeout, 오류 매핑
      ▼
Protocol Adapter / tcf-eai
      │ HTTP, 메시징 등
      ▼
External System
```

현행 `pdmg-service`의 `client` 패키지에서는 실제 업무 Client 구현이 확인되지 않는다. `pdmg-fw`에는 API Gateway나 Object Storage 연계 성격의 구현이 있으나 현재 `pdmg-service` 주요 업무 흐름에서 호출된다고 단정할 근거는 없다. 따라서 이 절의 Client 구조는 신규 외부 연계의 권장 경계이며, 존재하지 않는 AS-IS 호출을 만들어 설명하지 않는다.

Client는 URL 호출만 담당하지 않는다. 업무 DTO를 외부 계약으로 변환하고, 인증 Header를 안전하게 구성하며, 연결·응답 Timeout과 재시도 정책을 적용하고, 외부 오류를 내부에서 이해할 수 있는 예외로 변환해야 한다. 로그에는 토큰이나 개인정보를 남기지 않고 GUID 또는 별도의 상관 ID만 기록한다. 재시도는 조회처럼 멱등한 요청에 우선 적용하며 등록·결제 성격의 요청은 멱등 키나 상대 시스템의 중복 방지 계약 없이 자동 재시도하지 않는다.

외부 호출을 포함한 로컬 트랜잭션에서는 특히 주의해야 한다. DB 변경 후 외부 호출이 성공하고 로컬 커밋이 실패할 수도 있고, 외부 호출 Timeout 뒤 실제 상대 처리는 성공했을 수도 있다. 로컬 `@Transactional`은 외부 시스템을 롤백하지 못한다. 호출 순서, 상태 저장, 보상 거래, Outbox 또는 비동기 후속 처리 중 무엇을 사용할지 업무 일관성 수준에 따라 결정해야 한다.

GUID도 네트워크 경계를 자동으로 넘지 않는다. Client가 표준 추적 헤더에 값을 넣고 상대 시스템이 이를 수용해야 이어진다. 상대가 다른 추적 규약을 사용하면 내부 GUID와 외부 Trace ID의 매핑을 로그에 남기되 민감 정보는 제외한다.

## 7.12 동기·비동기 호출

동기 호출은 호출자가 결과나 예외를 받을 때까지 기다리는 방식이다. PDMG 온라인 거래의 기본 경로는 동기다. Timeout Executor가 Worker Thread를 사용하더라도 Request Thread는 Future 결과를 기다린 뒤 응답하므로 업무 완료 관점에서는 동기 요청이다. “Thread가 바뀐다”와 “비동기 업무로 접수한다”는 서로 다른 개념이다.

```text
동기 온라인 거래

Request Thread ── submit ──▶ Worker Thread
       │                           │
       │          wait             ├─ TX / 업무 / DB
       ◀───────────────────────────┘
       │ 결과 또는 Timeout 응답
```

비동기 호출은 요청이 작업 완료를 기다리지 않고 접수 결과를 반환하는 구조다. 긴 작업이라는 이유만으로 `@Async`를 붙이는 것은 충분하지 않다. 작업 상태 저장, 중복 접수 방지, 재시도, 최종 실패 처리, 사용자의 결과 조회 방법과 운영 모니터링이 함께 있어야 한다.

Thread 경계별 전파 특성은 다음과 같다.

| 경계 | ServiceContext/MDC | Spring TX | 오류 전달 | 설계 책임 |
|---|---|---|---|---|
| 같은 Thread Java 호출 | 현재 Thread 값 유지 | 기존 TX 참여 가능 | 직접 전파 | 프록시·전파 속성 확인 |
| OnlineTimeout Worker | 명시적 캡처·설치 | Worker에서 새로 시작/참여 | Future를 통해 전달 | 종료 시 Context 정리 |
| 일반 `@Async` | 자동 보장 안 됨 | 기존 TX 상속 안 됨 | 호출자에게 직접 전달 안 됨 | TaskDecorator, 상태·재처리 |
| HTTP 호출 | 새 요청 Context | 로컬 TX 공유 안 됨 | HTTP 계약으로 변환 | Header, Timeout, 멱등성 |
| 메시지/Queue | 소비 시 새 Context | 소비자 로컬 TX | DLQ·재시도 | 상관 ID, 순서, 중복 |

같은 Thread 호출에서는 `ServiceContextHolder`의 값이 보이지만 호출이 끝나기 전에 다른 Thread로 작업을 넘기면 자동 상속되지 않는다. `InheritableThreadLocal`로 해결하려는 접근은 Thread Pool 재사용에서 이전 요청 값이 섞일 수 있어 안전하지 않다. 캡처할 값을 명시하고, 설치와 `finally` 정리를 한 쌍으로 만들어야 한다.

트랜잭션 역시 Thread에 결합된다. 비동기 작업은 요청 트랜잭션이 커밋되기 전에 시작되어 아직 확정되지 않은 데이터를 읽을 수 있고, 요청이 롤백돼도 비동기 작업은 이미 외부 효과를 만들 수 있다. 커밋 후에만 수행해야 하는 작업은 트랜잭션 이벤트, Outbox 등 커밋과 연계된 구조를 사용한다.

오류 모델도 다르다. 동기 호출은 예외를 상위로 전파해 현재 거래를 롤백시킬 수 있다. 비동기 호출은 이미 응답이 끝났으므로 예외를 클라이언트에 돌려줄 수 없다. 실패 상태, 재시도 횟수, 최종 포기 기준과 알림 주체를 별도로 설계해야 한다. 따라서 선택 기준은 처리 시간이 아니라 “호출자가 즉시 결과를 필요로 하는가”와 “실패를 누가 언제 책임지는가”다.

## 7.13 신규 도메인 추가 절차

신규 도메인은 패키지를 만든 다음 클래스를 복사하는 방식으로 추가하지 않는다. 업무 책임에서 실행·장애 경계까지 순서대로 결정해야 한다. 다음 15단계는 신규 업무뿐 아니라 기존 기능을 분리할 때도 적용할 수 있다.

### 1단계: 업무 범위와 소유자 정의

요구사항, 데이터 소유권, 변경 승인자와 운영 책임자를 적는다. 산출물은 한 문장으로 설명 가능한 도메인 책임이다. “여러 화면에서 쓴다”는 책임 정의가 아니다.

### 2단계: 기존 도메인과 중복 여부 판정

기존 Service ID, 프로그램, DB 접근과 UI 기능을 검색한다. 기존 도메인의 새 거래인지 별도 도메인인지 판단한다. 같은 변경 이유를 가진 기능을 불필요하게 분리하지 않는다.

### 3단계: 업무·세부업무 코드 결정

네이밍 기준과 코드 분류표에 따라 업무 축을 결정한다. 코드는 임의 생성하지 않고 운영·개발 조직이 공통으로 이해하는 분류를 사용한다.

### 4단계: 프로그램 ID와 응집 범위 결정

함께 변경되는 조회·등록·수정·삭제를 어떤 프로그램으로 묶을지 정한다. 화면 번호와 기계적으로 일치시키지 않는다. 하나의 Handler가 관리할 거래 집합이 명확해야 한다.

### 5단계: 거래와 Service ID 정의

각 유스케이스의 입력, 결과, 부작용과 실패를 정의한 뒤 Service ID를 부여한다. 기존 Handler와 UI 카탈로그에서 중복 여부를 검사한다.

### 6단계: Inbound 방식 결정

TCF ON 공통 진입을 기본으로 할지, TCF OFF 호환 Controller가 필요한지, 외부 공개 API인지 결정한다. ON/OFF 양쪽이 필요하면 동일한 업무 핵심을 공유할 경계를 먼저 설계한다.

### 7단계: 공개 경계와 내부 구현 분리

Handler, Facade 또는 공개 Application Port 중 누가 도메인 진입 계약인지 정한다. Service, Rule, DAO, Mapper는 기본적으로 내부 구현으로 둔다. 다른 도메인에서 DAO를 가져다 쓸 가능성을 공개 API 요구로 착각하지 않는다.

### 8단계: 도메인 간 의존 방향 정의

필요한 기존 기능마다 데이터 복제, 공통 Rule, 공개 Java 인터페이스, Client/API 중 적합한 방식을 선택한다. A→B와 B→A가 동시에 필요하면 책임 재분리를 검토한다.

### 9단계: 외부 연계와 장애 계약 정의

외부 시스템이 있다면 Client 경계를 만들고 인증, Timeout, 재시도, 멱등성, 오류 변환과 보상 방식을 정한다. 외부 성공을 로컬 트랜잭션 롤백으로 되돌릴 수 있다고 가정하지 않는다.

### 10단계: 동기·비동기 결정

즉시 결과가 필요한지, 지연을 허용하는지, 실패를 누가 확인하는지 결정한다. 비동기라면 작업 ID, 상태 저장, 재시도와 결과 조회 계약까지 설계한다.

### 11단계: Context와 GUID 전파 정의

같은 Thread, Worker Thread, HTTP, 메시지 경계마다 전달할 값을 정한다. 사용자·토큰 전체를 무분별하게 복사하지 않고 업무 수행에 필요한 최소 정보와 추적 ID만 전달한다. 모든 종료 경로에서 ThreadLocal과 MDC를 정리한다.

### 12단계: 트랜잭션 경계 정의

누가 어떤 TransactionManager로 BEGIN하는지, 업무 선후처리와 DAO가 어디까지 참여하는지, 어떤 예외에서 롤백하는지 적는다. HTTP와 비동기 경계를 로컬 트랜잭션에 포함시키지 않는다.

### 13단계: Timeout 예산 배분

전체 온라인 제한 안에서 DB, 외부 Client, Relay와 Worker의 시간 예산을 정한다. 외곽 Timeout만 두고 내부 호출을 무한 대기시키지 않는다. 취소와 interrupt의 한계도 실패 시나리오에 포함한다.

### 14단계: 오류·관측 계약 정의

업무 예외, 라우팅 실패, 외부 오류와 Timeout을 어떤 경계에서 변환할지 정한다. Service ID와 GUID로 호출 구간을 추적할 로그를 설계하고 토큰·개인정보는 제외한다.

### 15단계: 전체 연결과 금지 의존 검증

Handler 등록, UI 카탈로그, 샘플 전문, Controller, Facade, Service, DAO, Mapper, 설정과 테스트를 함께 검증한다. ArchUnit 또는 의존성 테스트로 Controller→DAO, 도메인 A→도메인 B DAO와 순환 의존을 차단한다. TCF ON/OFF와 정상·실패·Timeout 시나리오를 각각 실행한다.

### 호출 방식 결정 트리

```text
필요한 기능이 현재 프로그램 내부에 있는가?
  ├─ 예 → Service가 자기 Rule/DAO 호출
  └─ 아니오
       │
       ├─ 여러 프로그램이 동일하게 소유할 공통 규칙인가?
       │    ├─ 예 → 상위 업무 경계의 명시적 공통 컴포넌트
       │    └─ 아니오
       │
       ├─ 같은 배포 단위의 다른 도메인인가?
       │    ├─ 예 → 공개 Application Port 검토
       │    │         직접 DAO/내부 Rule 호출 금지
       │    └─ 아니오
       │
       └─ 다른 프로세스/외부 시스템인가?
            └─ Client/Adapter + HTTP/메시지 계약

그 다음 공통 질문
  → 즉시 결과가 필요한가?
  → 기존 TX에 참여해야 하는가, 참여할 수 있는가?
  → Context/GUID를 어떻게 전달하는가?
  → Timeout·오류·재시도·보상의 책임자는 누구인가?
```

### 실제 거래에 적용해 보기

`mgcoa9000S0` 조회를 TCF ON과 UI 직접 호출로 실행한다고 보자. 화면은 UI 카탈로그와 설정에서 대상 주소를 얻고 `/{serviceId}`로 요청한다. Filter가 ServiceContext와 GUID를 준비하고, Controller가 Service ID를 판정한다. TcfFacade는 TransactionContext를 만들고 Timeout Executor에 작업을 맡긴다. Dispatcher는 `mgcoa9000Handler`를 찾고 Handler는 `mgcoa9000Facade`의 조회 메서드로 분기한다. Facade가 DTO를 변환한 뒤 Service가 자기 DAO를 호출한다. 여기까지는 한 프로그램 내부의 정상 호출이다.

이 조회에 다른 업무의 고객 상태가 필요하다고 가정하자. 아래는 구조 설명을 위한 가상 요구다. `mgcoa9000Service`가 상대 DAO를 직접 주입하는 선택은 금지한다. 먼저 고객 상태의 소유 도메인이 공개 조회 계약을 제공하는지 확인한다. 같은 배포 단위의 안정된 공개 Application Port라면 타입이 명확한 Java 호출을 사용할 수 있다. 별도 서비스라면 Client로 HTTP 호출하고 GUID, Timeout, 오류 변환을 정의한다. 이때 외부 조회는 로컬 DB 트랜잭션과 원자적으로 묶이지 않으며, 실패하면 현재 조회 전체를 실패시킬지 대체값을 사용할지 업무 정책으로 결정한다.

### AS-IS와 TO-BE 판단

| 구분 | 내용 |
|---|---|
| AS-IS | 프로그램 ID 중심 Handler/Facade/Service/DAO 구조, Service ID Registry 기반 TCF ON 호출 |
| AS-IS | TCF OFF Controller가 Service를 직접 호출하여 ON과 Facade·Timeout·TX 경계가 비대칭 |
| AS-IS | UI 일반 화면은 직접 호출이 주 경로이며 Relay는 하위 호환 중계로 존재 |
| AS-IS 제약 | UI 카탈로그와 백엔드 Handler 거래 목록의 동기화가 자동 보장되지 않음 |
| TO-BE 권장 | ON/OFF가 동일 Business Facade 이하를 공유하고 차이는 진입 Adapter에 한정 |
| TO-BE 권장 | 도메인 간 공개 Application Port와 Client 계약을 명시하고 DAO 직접 의존을 자동 검사 |
| TO-BE 권장 | Service ID의 단일 원천 또는 생성·검증 체계로 UI/서버 불일치를 조기에 탐지 |

## 핵심 정리

PDMG의 도메인은 DDD 모델이나 패키지 이름 하나를 뜻하지 않는다. 기능의 소유권과 호출 경계를 정하기 위한 시스템·업무·세부업무·프로그램·거래의 분류 체계다. 패키지는 그 경계를 물리적으로 표현하고 Service ID는 실행할 거래를 식별한다.

같은 프로그램에서는 Handler에서 Facade, Service, Rule, DAO 방향을 따른다. 다른 도메인의 DAO나 Mapper는 공개 업무 계약이 아니므로 직접 호출하지 않는다. 다른 Service의 직접 호출은 기술적 가능성이 아니라 공개 계약, 단방향 의존, 트랜잭션 의도를 기준으로 제한적으로 판단한다. 프로세스가 다르면 Client와 프로토콜 경계를 사용한다.

TCF ON은 Service ID Registry, Handler, Timeout Executor와 TransactionContext를 사용하는 공통 경로다. TCF OFF의 현행 업무 Controller는 Service를 직접 호출하므로 ON과 동일한 트랜잭션·Timeout 경계라고 가정할 수 없다. UI 직접 호출과 Relay 호출도 네트워크 위치만 다른 것이 아니라 CORS, 인증, Header 전파, 장애 지점과 보안 책임이 다르다.

호출 경계는 트랜잭션 경계가 아니다. Java 호출은 기존 트랜잭션에 참여할 수 있지만 자동으로 시작하지 않으며, HTTP와 비동기 호출은 기존 로컬 트랜잭션을 공유하지 않는다. Thread가 바뀌면 ServiceContext, MDC와 GUID를 명시적으로 전파하고 반드시 정리해야 한다.

## 아키텍처 판단 포인트

호출 방식을 고를 때 가장 먼저 볼 것은 속도가 아니라 소유권이다. 소유권이 같고 같은 트랜잭션이 필요한 내부 규칙이면 Java 호출이 자연스럽다. 소유권은 다르지만 같은 배포 단위라면 공개 Application Port를 검토한다. 독립 배포, 보안 경계 또는 장애 격리가 필요하면 Client/API가 맞다. 즉시 결과가 필요하지 않고 재처리 가능한 업무라면 비동기를 검토하되, 단순 `@Async`가 아니라 상태와 실패 모델을 함께 설계한다.

다음 장에서는 이 장에서 선택한 HTTP 경계를 실제 요청 메시지로 구체화한다. Service ID와 GUID가 표준 전문 안에서 어디에 놓이는지, 공통 Header와 업무 DTO가 어떻게 분리되는지, 요청·응답 계약을 어떤 기준으로 검증하는지 살펴본다.
