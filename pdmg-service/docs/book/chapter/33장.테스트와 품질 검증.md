# 33장. 테스트와 품질 검증

테스트는 구현 뒤에 붙이는 확인 절차가 아니라 아키텍처의 경계를 실행 가능한 증거로 만드는 일이다. Service Mock 테스트가 통과해도 실제 Mapper SQL, Transaction rollback, Filter와 TCF 분기, Worker 취소 또는 UI 계약은 틀릴 수 있다. PDMG의 최종 품질 Gate는 작은 단위의 빠른 피드백에서 시작해 실제 DB 상태, HTTP 응답, WAR 산출물과 문서 정합성까지 단계적으로 넓혀야 한다.

현재 저장소의 AS-IS 테스트 자산은 제한적이다. `pdmg-service`에는 Service, DTO binding, Security MockMvc, exceptionCode binding 테스트가 있고 `pdmg-fw`에는 timeout 설정과 Executor 테스트가 있다. `pdmg-jwt`와 `pdmg-ui`에는 테스트 소스가 확인되지 않는다. 따라서 이 장의 일부는 이미 존재하는 증거이고, 나머지는 릴리스 전에 갖춰야 할 TO-BE 검증 기준이다.

## 33.1 테스트 전략

좋은 전략은 위험과 경계를 기준으로 테스트 층을 나눈다. Rule과 DTO는 빠른 단위 테스트로 조합을 넓게 검사하고, Service는 DAO를 Mock해 분기와 출력 조립을 확인한다. Mapper는 실제 DB와 유사한 통합 환경에서 SQL을 실행하며, Facade는 실제 TransactionManager를 통해 commit과 rollback 뒤의 행 상태를 확인한다. Controller·Filter·Interceptor·TCF는 MockMvc 또는 기동된 서버로 HTTP 계약을 검증한다. 마지막 E2E는 UI 요청부터 DB와 응답까지 대표 거래 하나를 관통한다.

```text
Unit(DTO/Rule/Service) → Slice(HTTP/Mapper) → Integration(TX/TCF/JWT)
                     → E2E(UI→WAR→DB) → Build·문서 Gate
```

AS-IS Gradle 설정은 네 모듈 모두 JUnit Platform을 사용하며 Spring Boot test 의존성을 둔다. `pdmg-service`와 `pdmg-jwt`는 WAR, `pdmg-fw`는 일반 JAR, `pdmg-ui`는 실행 JAR을 만든다. 테스트 수만 세지 말고 핵심 위험이 어느 층에서 증명되는지 추적표를 유지해야 한다.

## 33.2 Handler 테스트

Handler는 Service ID 등록과 Facade 분기만 담당하므로 복잡한 업무 Mock을 반복하지 않는다. `serviceIds()`가 계약한 ID 전체를 반환하는지, 알려진 ID가 올바른 Facade 메서드로 한 번 전달되는지, 미등록 ID가 표준 오류로 끝나는지 확인한다. 입력 DTO 형변환 실패도 성공 경로와 분리한다.

단위 테스트에서는 Facade를 Mock하고 호출 인자와 반환 전달을 검증한다. 통합 테스트에서는 Spring Context에 Handler가 Bean으로 등록되고 Dispatcher가 Catalog에서 찾는지 확인한다. 같은 Service ID를 두 Handler가 등록하거나 UI의 ID와 대소문자가 다르면 컴파일은 성공해도 런타임 라우팅이 실패하므로 Catalog 중복 검사도 Build Gate가 되어야 한다. 현재 이 전용 테스트는 확인되지 않아 TO-BE다.

## 33.3 Facade 트랜잭션 테스트

Facade Transaction 테스트의 판정 기준은 메서드 반환이 아니라 DB 상태다. 정상 C/U/D 후 새 Transaction에서 행이 commit됐는지 조회한다. Service가 RuntimeException 또는 `rollbackFor=Exception` 대상 checked exception을 던지면 이전 INSERT까지 사라져야 한다. 예외를 catch하고 성공 DTO로 바꾸는 사례는 commit될 수 있으므로 별도 실패 테스트로 드러낸다.

`rdwTransactionManager` 선택도 검증 대상이다. 다른 Manager를 기본 주입한 테스트는 실제 운영 경계를 증명하지 못한다. Facade와 Service 양쪽 Annotation, TCF Worker의 TransactionTemplate이 REQUIRED로 참여하는 구조에서는 Transaction synchronization으로 동일 자원 참여 여부를 기록하고, 업무 후처리 INSERT가 같은 rollback에 포함되는지도 확인한다. AS-IS에 실제 DB rollback 통합 테스트는 확인되지 않는다.

## 33.4 Service와 Rule 단위 테스트

Service 테스트는 입력 정규화, Rule 호출 순서, DAO 인자, 0·1·다건 판정, 출력 DTO 조립을 빠르게 검증한다. 현재 `mgcoa5530ServiceTest`는 Mockito로 기본/지정 paging과 결과 조립을 확인한다. 이는 의미 있는 단위 증거지만 Mapper SQL이나 Transaction을 증명하지는 않는다. `mgcoa8888D0DTOinBindTest`는 문자열과 배열 형태의 GUID binding 계약을 확인한다.

Rule은 경계값과 오류 코드를 parameterized test로 넓게 다룬다. 빈 문자열, 공백, 최대 길이, 잘못된 Y/N과 허용되지 않은 업무 코드가 각각 어떤 BizException을 만드는지 검증한다. Service가 예외를 삼키지 않는지, DAO가 0 또는 2를 반환했을 때 단건 계약이 실패하는지도 포함한다.

## 33.5 DAO·Mapper 통합 테스트

Mapper 테스트는 namespace와 statement ID, `#{}` binding, Result alias, 동적 WHERE, 정렬과 paging을 실제 실행한다. 목록 count와 list에 같은 조건을 넣어 totalCount와 rows가 일치하는지 확인한다. 등록 Unique, 수정 0·1·다건, 물리 삭제와 FK 실패도 DB 상태로 판정한다.

로컬 runtime에는 H2가 있지만 Oracle ROWNUM과 함수·타입 차이는 H2 성공만으로 해소되지 않는다. 가능한 SQL은 호환 모드에서 빠르게 확인하고, 배포 전 Oracle 통합 환경에서 실행계획과 paging 경계를 다시 검증한다. 현재 Mapper 전용 통합 테스트는 확인되지 않는다. TO-BE에서는 운영 Schema migration과 동일한 제약조건을 Test fixture에 적용해야 동시 등록 방어까지 증명할 수 있다.

## 33.6 Controller API 테스트

Controller/API 테스트는 URL, HTTP method, JSON 전문 binding, status, 공통 결과 형식과 Content-Type을 검증한다. 잘못된 JSON, 필수값 누락, 미등록 Service ID, BizException과 시스템 예외가 내부 Stack Trace 없이 표준 응답으로 변환되는지도 확인한다. Service만 Mock한 MVC slice와 실제 Filter/Interceptor를 포함한 SpringBootTest의 목적을 구분한다.

현재 `SecurityConfigTest`는 MockMvc로 보호 경로의 인증 상태를 확인한다. 그러나 업무 Controller 한 건의 전체 성공 전문과 오류 전문을 증명하는 테스트는 별도로 필요하다. Test가 보안 Filter를 임의로 끄면 빠르지만 실제 요청 경계의 품질 증거로 사용할 수 없다.

## 33.7 TCF ON 테스트

TCF ON에서는 요청이 OnlineTransactionController, Dispatcher, Handler, Facade와 ETF까지 통과한다. 테스트는 STF에서 ServiceContext·GUID가 설정되는지, 거래통제가 거부를 중단하는지, 업무 선후처리와 ImageLog 시점, timeout Executor와 Transaction 경계를 함께 관찰한다. 성공 시 ETF와 Context 정리까지 끝나고 응답 전문이 유지돼야 한다.

TCF 관련 Bean을 모두 Mock하면 연결 오류를 놓친다. 최소 한 대표 조회와 쓰기를 기동 Context에서 실행하고 GUID로 로그와 DB 변경을 연결한다. 현재 TCF ON 전체 경로를 관통하는 테스트 자산은 확인되지 않으므로 릴리스 Gate에 추가해야 한다.

## 33.8 TCF OFF 테스트

TCF OFF는 단지 설정 한 줄의 기동 성공이 아니다. 조건부 Bean이 빠진 상태에서도 Legacy Controller 또는 호환 진입점이 업무 Facade에 도달하고, 인증·표준 오류·Transaction 계약이 유지되는지 확인해야 한다. 반대로 TCF 전용 STF/ETF, timeout 또는 ImageLog가 실행됐다고 기대해서는 안 된다.

같은 업무 입력을 ON과 OFF로 실행해 업무 결과는 동등하고 부가 기능 차이는 의도한 것인지 비교한다. Conditional Bean graph를 ContextRunner나 ApplicationContext 테스트로 확인하면 누락 Bean과 중복 Mapping을 조기에 찾을 수 있다. 현재 두 모드의 쌍 테스트는 확인되지 않는다.

## 33.9 예외와 Rollback 테스트

예외 테스트는 발생 위치별로 나눈다. Filter 예외는 MVC Handler에 닿지 않을 수 있고, Interceptor preHandle 실패는 Controller를 실행하지 않는다. 업무 BizException은 표준 코드로 변환돼야 하며 DAO 예외는 SQL 상세를 숨긴다. `ExceptionCodePropertiesTest`는 `MP0404`, `MP0409` 메시지 binding을 확인하지만 실제 Global Handler 응답까지 증명하지는 않는다.

```text
정상: validate → write A → write B → commit → 성공 응답
실패: validate → write A → B 예외 → rollback → 표준 오류
오류: validate → write A → catch/성공 반환 → commit 위험
```

checked exception, RuntimeException, rollback-only, 예외 삼킴을 각각 실행하고 새 Connection에서 A와 B의 행 수를 확인한다. 로그 문자열의 “rollback”만으로 성공 판정하지 않는다.

## 33.10 타임아웃 테스트

현재 `OnlineTimeoutPropertiesTest`는 공통값, Service ID override와 잘못된 설정 검증을 다룬다. `DefaultOnlineTimeoutExecutorTest`는 정상 commit, 작업 예외 rollback, Thread 이름과 timeout/interrupt 뒤 rollback 관찰을 Fake TransactionManager로 확인한다. 이는 Executor 계약의 좋은 단위 증거다.

그러나 Future가 timeout 예외를 냈다는 사실은 JDBC 작업이 끝났다는 뜻이 아니다. 통합 테스트에서는 장시간 Query 또는 제어된 blocking DAO를 실행해 응답 시각, Worker interrupt 관찰, Connection 반환, DB commit 부재를 따로 측정한다. Driver가 interrupt에 반응하지 않는 상황과 Spring Transaction timeout의 Statement 적용도 확인한다. 늦게 완료된 Worker가 사후 commit하면 가장 위험한 실패다.

## 33.11 JWT 성공·실패·만료 테스트

JWT 테스트는 정상 서명과 필수 claim뿐 아니라 변조, 만료, 잘못된 token type, issuer/audience 불일치, 키 회전과 누락 Authorization을 검사한다. 공개키 방식 발급자와 Service 검증 Algorithm이 실제로 호환되는지 같은 Token으로 통합 검증해야 한다. 비밀키나 Token 원문은 Test 로그에 남기지 않는다.

현재 `pdmg-jwt`에는 테스트 소스가 없고 Service의 Security MockMvc만으로 발급·검증 연결을 증명할 수 없다. 특히 앞 장에서 판정한 RSA 발급과 HMAC 검증 비호환은 E2E 실패 사례로 고정해야 한다. claim이 MDC와 ServiceContext로 전달되고 요청 종료 후 정리되는지도 별도 Thread 재사용 테스트가 필요하다.

## 33.12 UI 요청 테스트

UI 테스트는 화면 이벤트가 올바른 URL, Service ID, Header와 DTO 구조를 보내는지 확인한다. 정상 응답의 `dto/result`, 빈 목록, 표준 오류, 401·403, timeout과 중복 클릭을 각각 사용자 상태로 검증한다. Contract fixture는 Service DTO 변경 시 함께 실패해야 한다.

`pdmg-ui`에는 현재 테스트 소스가 없다. TO-BE는 HTTP client 단위 테스트와 기동된 Service를 향한 대표 화면 E2E를 나눈다. 오류 응답을 성공 DTO로 렌더링하거나 재시도로 중복 등록하지 않는지 확인하며, 화면에서 Token·개인정보를 Console에 출력하지 않는다.

## 33.13 빌드와 WAR 검증

모듈별 최소 명령은 `pdmg-fw`의 test와 jar, `pdmg-service`와 `pdmg-jwt`의 test와 war, `pdmg-ui`의 test와 bootJar다. Service의 `bootWar`는 비활성이고 일반 WAR가 활성화되어 있으므로 산출물 이름·크기뿐 아니라 WEB-INF classes, 설정 Resource와 의존 JAR을 검사한다. FW는 실행 Boot JAR이 아니라 소비 가능한 Library JAR이어야 한다.

```powershell
.\gradlew.bat :pdmg-fw:test :pdmg-fw:jar
.\gradlew.bat :pdmg-service:test :pdmg-service:war
.\gradlew.bat :pdmg-jwt:test :pdmg-jwt:war
.\gradlew.bat :pdmg-ui:test :pdmg-ui:bootJar
```

실제 프로젝트가 독립 settings를 사용하면 각 모듈 디렉터리의 Wrapper와 해당 task를 실행한다. Build 성공 후 UTF-8 Resource, profile별 기동, 외부 Tomcat 배포와 Health 확인을 수행한다. 이 장 집필에서는 Build를 실행했다고 단정하지 않으며 현재 설정에서 정의된 task와 자산을 판정했다.

산출물 회귀 검사는 이전 승인본과 의존성·파일 목록을 비교한다. 예상하지 못한 Private Key, 개발용 설정, Test fixture가 WAR에 포함되면 Build 성공이어도 배포를 중단한다. Dependency 보고서로 알려진 취약점과 중복 Logging 구현을 확인하고, 기동 Smoke Test에서는 실제 배포 Profile, 외부 DataSource 연결 실패와 필수 환경변수 누락을 의도적으로 재현한다. 성능 기준은 대표 조회의 응답시간 하나가 아니라 처리량, DB Connection 점유, timeout 수와 오류율을 함께 기록한다. 수치 기준은 운영 용량과 SLA에서 정하며 근거 없는 고정값을 책의 AS-IS로 만들지 않는다.

## 33.14 문서와 구현 정합성 확인

최종 Gate는 책의 주장마다 Source, 설정 또는 Test 근거를 연결한다. 클래스명·설정 키·Service ID·Mapper statement가 실제로 존재하는지 검색하고, ON/OFF와 profile 조합을 표로 실행한다. 문서와 Test가 충돌하면 Test를 억지로 문서에 맞추지 않고 Source 동작을 재판정해 수정 대상 장을 기록한다.

AS-IS에서 특히 남은 공백은 Mapper 실제 DB, TCF ON/OFF E2E, 실제 Transaction rollback, JWT 발급-검증, UI 계약과 WAR 배포다. 이것은 “실패”가 아니라 아직 증명되지 않은 범위다. 출시 승인표에는 통과·실패·미실행과 환경을 구분해 기록한다.

회귀 결과에는 실행 명령, Commit 식별자, Profile, Java와 DB 버전, 시작·종료 시각을 남긴다. 같은 Test 이름도 환경이 다르면 같은 증거가 아니다. 실패를 간헐 오류로 분류할 때에는 Thread dump, GUID, SQL 상태처럼 재현 근거를 보존하고 단순 재실행 성공으로 닫지 않는다. 보안 Test의 위조 Token과 개인정보 fixture는 운영값이 아닌 테스트 전용 값이어야 하며 결과물과 로그의 보존 범위도 제한한다.

### End-to-End 품질 흐름

```text
UI fixture → JWT → Filter/Interceptor → TCF ON|OFF → Handler
 → Facade TX → Service/Rule → DAO/Mapper → DB
 → ETF/응답 → DB·로그·Context 검증 → WAR·문서 Gate
```

### 책임과 경계

| 대상 | 검증 책임 | Caller/Callee | 금지 판단 |
|---|---|---|---|
| Handler | ID 등록·분기 | Dispatcher/Facade | 업무 계산 |
| Facade | TX·유스케이스 | Handler/Service | Mock 반환만으로 rollback 통과 |
| Service/Rule | 분기·검증 | Facade/DAO | SQL 실행 성공 단정 |
| DAO/Mapper | Binding·행 수 | Service/DB | H2만으로 Oracle 호환 단정 |
| HTTP/TCF | Filter부터 응답 | UI/업무 계층 | 보안 Filter 제거 후 E2E 판정 |
| Build Gate | Test·산출물·문서 | 개발/배포 | Compile 성공만으로 출시 승인 |

### Anti Pattern

- Mock 단위 테스트 수가 많다는 이유로 DB와 HTTP 통합 검증을 생략한다.
- TCF ON만 실행하고 OFF 호환을 추측한다.
- timeout 응답만 보고 Worker와 DB commit 여부를 보지 않는다.
- rollback 로그만 확인하고 새 Transaction에서 행을 조회하지 않는다.
- JWT 서명 Algorithm과 키 종류가 다른데 각 모듈 테스트만 통과시킨다.
- 실패한 문서 주장을 유지하려고 Test 기대값을 변경한다.

### 개발·출시 체크리스트

- [ ] 변경된 Rule과 Service의 정상·경계·오류 조합이 있는가?
- [ ] Mapper SQL을 목표 DB에서 실행했는가?
- [ ] commit과 rollback을 최종 DB 상태로 확인했는가?
- [ ] TCF ON/OFF 대표 거래가 모두 통과하는가?
- [ ] timeout 뒤 Worker·Connection·DB 상태를 확인했는가?
- [ ] JWT 변조·만료·type·claim·키 불일치를 검사했는가?
- [ ] UI와 API Contract fixture가 같은가?
- [ ] profile별 Context와 조건부 Bean graph를 기동했는가?
- [ ] JAR/WAR 내용과 배포 기동을 검증했는가?
- [ ] 문서의 AS-IS 문장이 Source/Test 근거와 일치하는가?

검증 깊이는 변경 위험으로 결정한다. 문자열 Rule 수정은 단위 테스트 중심으로 충분할 수 있지만 Transaction, 인증, timeout, Mapper 또는 조건부 Bean 변경은 통합과 E2E가 필요하다. 이 장은 본문의 마지막 장이다. 부록은 명령, 설정표와 참조 자료를 빠르게 찾도록 돕지만, 여기서 정의한 실행 가능한 품질 Gate를 대신하지 않는다.
