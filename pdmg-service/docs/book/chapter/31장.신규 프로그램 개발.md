# 31장. 신규 프로그램 개발

신규 프로그램 개발은 Controller와 SQL을 연결하는 작업이 아니다. 요구사항을 PDMG 식별 체계로 번역하고, TCF ON/OFF 진입점과 공통 업무 계층을 만들며, DTO·오류·UI·테스트까지 하나의 변경 단위로 완성하는 일이다. 이 장은 실제 거래통제 프로그램 `mgcoa9001`의 구조를 참조한다. 예제의 동작을 그대로 복제하는 것이 아니라 현재 저장소가 어떤 연결 규칙을 사용하는지 증거로 삼는다.

실제 호출선은 UI `txcontrol.js`의 S0/C0/U0/D0 경로에서 시작해, TCF ON이면 `mgcoa9001Handler`, `mgcoa9001Facade`, `mgcoa9001Service`, `mgcoa9001DAO`, `mgcoa9001-ORA.xml`로 이어진다. TCF OFF이면 조건부 `mgcoa9001Controller`가 Service를 직접 호출한다. 이 두 진입점의 차이를 이해하지 못하면 한 모드에서만 동작하는 프로그램을 만들게 된다.

## 31.1 요구사항 분석

첫 산출물은 클래스 목록이 아니라 유스케이스 계약이다. 누가 어떤 조건에서 어떤 데이터를 조회·변경하며, 성공과 실패를 어떻게 판단하는지를 서술한다. 거래통제 예제라면 서비스·사용자·IP·영업점·시간대 규칙을 조회하고 등록·수정·삭제한다는 기능 외에도 복합키, 중복 처리, 미존재 처리, 페이지 크기와 권한을 정해야 한다.

요구사항을 입력, 처리, 출력, 오류, 비기능으로 분해한다. 입력에는 필수값·길이·허용값과 공통 Header를 포함한다. 처리에는 조회 조건, 정렬, Transaction 경계와 동시성 정책을 적는다. 출력에는 목록·건수와 변경 결과를 정의한다. 오류에는 미존재, 중복, 권한과 DB 실패를 구분한다. 비기능에는 timeout, 로그 마스킹, 대용량 범위와 TCF ON/OFF 지원을 포함한다.

요구사항이 모호한 채 샘플 코드를 복사하면 DB 컬럼을 DTO에 그대로 노출하고, 사용자 입력을 감사 사용자로 신뢰하거나, 화면이 필요로 하지 않는 삭제 API를 만들기 쉽다. 개발 전에 정상 시나리오 하나와 실패 시나리오 최소 세 개를 요청·응답 수준으로 합의한다.

## 31.2 업무축 결정

업무축은 패키지와 Service ID의 소유권을 결정한다. `mg.co.a`는 현재 거래통제와 관리성 프로그램이 위치한 축이며 DAO Mapper 경로도 `rdw.mg.co.a`로 연결된다. 새 기능이 기존 축의 책임인지, 별도 도메인 축이 필요한지 먼저 판단한다. 단지 비어 있는 번호가 있다는 이유로 관리 기능을 다른 업무축에 넣으면 권한, 배포와 Mapper 탐색이 분산된다.

결정 근거에는 데이터 소유자, 변경 주기, 운영 담당자, Transaction 경계와 다른 도메인 의존성을 기록한다. Framework 계층이 업무 모듈을 참조하거나 도메인 간 순환 의존을 만들지 않는다. 외부 연계가 핵심이면 DAO가 아니라 client 계층을 별도로 설계한다.

## 31.3 프로그램 번호 결정

프로그램 ID는 화면, Java 타입, Service ID, Mapper statement와 운영 로그를 연결하는 추적 키다. `mgcoa9001`처럼 업무축 prefix와 프로그램 번호를 결합한다. 기존 번호, UI route, Service Catalog와 문서 색인을 검색해 충돌하지 않는 번호를 선택한다. 숫자를 정한 뒤 파일을 만들기보다 번호 소유권을 등록한 후 개발을 시작한다.

번호를 바꾸는 비용은 클래스명 변경에 그치지 않는다. Handler의 `serviceIds()`, URL, DTO, DAO 메서드, Mapper id, UI Header의 `rms_svc_c`, 화면 `data-program-id`, 샘플 전문과 테스트 fixture가 모두 영향받는다. 초기 결정과 변경 영향표를 코드 리뷰에 포함한다.

## 31.4 Service ID 정의

Service ID는 프로그램 ID 뒤에 행위 코드와 순번을 붙인다. 실제 예제는 목록 `mgcoa9001S0`, 등록 `mgcoa9001C0`, 수정 `mgcoa9001U0`, 삭제 `mgcoa9001D0`을 사용한다. S/C/U/D 의미는 API 목적과 일치해야 하며 하나의 ID가 여러 행위를 요청 Body 값으로 분기하게 만들지 않는다.

```text
mgcoa9001S0 → 조회
mgcoa9001C0 → 등록
mgcoa9001U0 → 수정
mgcoa9001D0 → 삭제
```

TCF ON에서는 Handler가 이 네 ID를 `serviceIds()`로 등록하고 `handle()` switch가 Facade 메서드로 보낸다. 등록 누락은 Handler not found로, 중복 등록은 Catalog 충돌로 이어질 수 있다. TCF OFF에서는 각 ID가 `@PostMapping` URL이 된다. UI URL과 전문 Header의 Service ID가 다르면 Controller의 우선순위 규칙 때문에 예상하지 않은 거래가 선택될 수 있으므로 동일성을 테스트한다.

## 31.5 화면·API 계약 정의

화면 필드와 API DTO를 바로 일대일로 만들지 않는다. 화면의 표시값, 검색조건, 변경 가능한 값과 서버가 계산하거나 인증 Context에서 얻을 값을 구분한다. 등록 사용자, 영업점과 권한을 클라이언트 입력으로 신뢰하지 말고 검증된 Context에서 채우는 것이 목표다. 현행 일부 Service는 `LOCAL` fallback을 사용하므로 AS-IS와 보안 TO-BE를 구분한다.

API 계약에는 URL, Method, Service ID, 표준 Header, `dto` 입력, 성공 `dto`, 실패 `result`, 정렬과 페이지 규칙을 기록한다. 필드의 null·빈 문자열 의미와 날짜 형식도 정한다. UI는 목록 응답의 `rows` 또는 기존 생성 DTO 배열처럼 실제 직렬화 이름을 사용해야 한다. 같은 화면이 TCF ON/OFF를 지원한다면 요청 전문은 두 모드에서 호환되는지 확인한다.

## 31.6 DTO 작성

거래별로 입력과 출력을 분리한다. 조회 입력은 검색·페이지 조건, 조회 출력은 totalCount·page 정보·행 목록을 갖는다. 등록·수정·삭제 입력은 서로 다른 필수값을 가지므로 하나의 거대한 DTO를 재사용하지 않는다. 실제 `mgcoa9001`에는 C0/U0/D0별 DTO와 S0 행 DTO가 각각 존재한다.

DTO는 HTTP 계약이므로 DB Map의 컬럼 이름을 그대로 전파하지 않는다. 길이, enum 후보, 시간 형식과 민감정보 여부를 명시한다. TCF Handler의 Facade는 ObjectMapper로 `dtoBody`를 구체 DTO로 변환하므로 알 수 없는 필드, 숫자 변환과 null 처리 실패도 테스트한다. 출력 컬렉션은 null 대신 빈 목록을 반환하는 정책을 일관되게 적용한다.

## 31.7 Handler 작성

Handler는 TCF ON의 거래 Catalog이자 분기기다. `TransactionHandler`를 구현하고 조건부 Bean으로 true일 때만 등록한다. 책임은 지원 Service ID 선언, ID별 Facade 호출과 미지원 ID 거부까지다. 입력 검증, SQL, Transaction 정책을 Handler에 넣지 않는다.

```text
TransactionDispatcher
  → mgcoa9001Handler.handle(serviceId, dtoBody, context)
  → switch serviceId
  → mgcoa9001Facade의 동일 행위 메서드
```

Handler 테스트는 `serviceIds()`의 완전성과 중복, 각 ID가 올바른 Facade를 호출하는지, 미지원 ID가 실패하는지를 확인한다. 신규 ID를 상수에는 추가했지만 Collection이나 switch에 빠뜨리는 실수가 흔하다. Service ID 변경 때 UI와 샘플 요청을 함께 검색한다.

## 31.8 Controller 작성

Controller는 TCF OFF 호환 진입점이다. 예제 Controller는 `nhnis.fw.tcf.enabled=false`, matchIfMissing 조건에서 등록되고 각 `/mgcoa9001*` URL을 Service에 연결한다. AS-IS 예제는 Facade가 아니라 Service를 직접 호출하므로 TCF ON Handler→Facade 경로와 Transaction 위치가 다를 수 있다.

신규 프로그램은 지원할 ON/OFF 계약을 먼저 정한다. 두 모드를 모두 지원한다면 공통 업무 흐름이 한 계층으로 수렴하도록 만들어 동작 차이를 줄여야 한다. Controller는 HTTP binding과 위임만 담당하고 `@Transactional`, DAO 호출, 업무 검증을 넣지 않는다. Mapping 중복과 TCF 조건별 ApplicationContext를 테스트한다.

## 31.9 Facade 작성

Facade는 Object 형태의 TCF Body를 DTO로 바꾸고 유스케이스를 조정하며 Transaction 경계를 둔다. `mgcoa9001Facade`는 S0 readOnly, C0/U0/D0 rollbackFor Exception의 `rdwTransactionManager`를 선언한다. 이는 Handler와 Service 사이에서 업무 선후처리를 포함하는 경계를 형성한다.

Facade가 단순 위임처럼 보여도 제거하면 안 되는 이유는 진입 방식과 업무 계층 사이의 안정된 경계이기 때문이다. 변환 실패도 Transaction 시작·응답 오류 계약과 관련된다. self-invocation을 피하고 public 메서드가 Spring Proxy를 통해 호출되는지 확인한다. Controller OFF 경로가 Service를 직접 부르는 현행 차이는 테스트하고 TO-BE 정합화 대상으로 기록한다.

## 31.10 Service와 Rule 작성

Service는 유스케이스 순서, 입력 의미 검증, DAO 조합과 출력 DTO 조립을 담당한다. 거래통제 예제는 등록 전 exists를 확인해 중복 오류를 내고, 수정·삭제 전 미존재를 확인하며 DAO 결과 건수를 검증한다. 단순 필수값 검증과 복합키 구성도 Service에 있다.

반복 가능한 순수 검증·계산이 복잡해지면 Rule로 분리한다. Rule은 Spring Web이나 MyBatis에 의존하지 않고 단위 테스트하기 쉽게 만든다. 반면 DB 존재 확인은 DAO가 필요한 Service orchestration이다. 예외를 catch하고 성공 DTO로 바꾸지 않으며, `BizException`을 재전파해 rollback과 표준 오류 변환을 유지한다.

---

이 전반부까지의 파일 생성 순서는 요구사항 → 업무축·번호 → Service ID → API/DTO → Handler/Controller → Facade → Service/Rule이다. 후반부에서는 DAO/Mapper, 오류 코드, UI 거래 등록, 샘플 요청, 테스트, 빌드와 완료 Gate를 이어서 다룬다.

## 31.11 DAO 작성

DAO는 persistence package에 두고 MyBatis Mapper와 동일한 메서드 계약을 선언한다. `mgcoa9001DAO`는 목록, count, exists, insert, update, delete를 각각 다른 메서드로 제공한다. Service가 SQL 문자열이나 SqlSession statement ID를 알지 않게 하고, 입력 Map의 키와 반환형을 명시한다. 조회는 목록 또는 count, 변경은 영향 행 수를 반환해 Service가 0건·다건을 판단할 수 있게 한다.

DAO 이름과 패키지는 Mapper namespace의 정확한 계약이다. 인터페이스 이동이나 이름 변경 시 XML namespace도 함께 바꾸지 않으면 기동 또는 첫 호출에서 binding 오류가 난다. 신규 개발자는 Mapper Scan 범위 `nhnis.mg.co.a.persistence.dao` 안에 있는지, `rdwSqlSessionTemplate`에 연결되는지 확인한다. 동적 SQL 값은 문자열 치환이 아니라 `#{}` 바인딩을 사용한다.

## 31.12 Mapper XML 작성

Mapper는 `rdw.<업무 패키지>` Resource 경로에 두고 namespace를 DAO FQCN과 일치시킨다. statement id는 DAO 메서드명과 같아야 한다. 거래통제 예제의 `mgcoa9001S0_S0`, `_count`, `_exists`, `C0_C0`, `U0_U0`, `D0_D0`가 이 규칙을 보여준다. SQL 주석에도 statement id를 넣으면 SQL 로그와 소스를 연결하기 쉽다.

조회 SQL은 검색조건, 정렬, 페이지 범위와 count 조건이 일치해야 한다. 등록은 모든 복합키와 감사 필드를 바인딩하고, 수정·삭제는 WHERE 누락으로 전체 행에 영향을 주지 않도록 키를 검증한다. Mapper XML Parse, namespace, statement 존재와 parameter key를 자동 테스트한다. Oracle SQL과 Local H2 호환이 필요하다면 두 DB의 날짜·페이징·문자열 함수 차이를 명시한다.

## 31.13 오류 코드 추가

예상 가능한 실패는 안정된 오류 코드로 표현한다. 예제는 미존재, 중복과 권한 실패를 `BizException`으로 던진다. 새 코드는 기존 prefix와 번호 범위를 확인한 뒤 `exceptionCode.yml`에 메시지를 등록하고 인자 위치를 테스트한다. 사용자에게는 내부 Table·SQL을 드러내지 않는 해결 가능한 문구를 제공한다.

코드를 YAML에 추가하는 것만으로 완료되지 않는다. 현재 TCF Global Handler가 새 BizException 메시지 사전을 완전히 연결하지 않는 AS-IS가 있으므로 실제 HTTP 응답을 확인한다. Filter 입력·인증 실패는 MVC 오류 경로를 우회한다. 신규 프로그램의 오류 계약은 throw 지점, rollback, HTTP 상태, `result.stdErrCode`, UI 표시까지 end-to-end로 검증한다.

## 31.14 UI 거래 등록

UI에는 화면 route, 프로그램 metadata, Service ID별 endpoint와 표준 Header 생성이 필요하다. `txcontrol.js`는 list/create/update/delete URL과 `rms_svc_c`를 같은 `mgcoa9001*` 값으로 만든다. Shell의 정적 프로그램 Set과 route Map도 `mgcoa9001`을 등록한다. 한 위치만 추가하면 직접 URL은 열리지만 메뉴에서 보이지 않거나 잘못된 Service ID가 전송될 수 있다.

업무 요청은 공통 `service-client.js`를 사용하고 Target Base URL, timeout, CORS와 Authorization Header 정책을 확인한다. 현재 일반 Client에는 JWT Header 연결이 부족하므로 보안 AS-IS를 숨기지 않는다. 응답은 HTTP status와 표준 `dto`/`result`를 모두 해석하고 서버 메시지를 무검증 HTML로 출력하지 않는다.

## 31.15 샘플 요청 작성

샘플은 문서 장식이 아니라 실행 가능한 계약 Fixture다. TCF ON `/online` 요청과 `/{serviceId}` 요청에서 `hdr_nhnis.sys_comm.rms_svc_c`, GUID, 화면 ID와 `dto`를 포함한다. 등록·수정·삭제 샘플은 실제 운영 데이터를 바꾸지 않는 Local Seed를 사용한다. Token, 비밀번호와 개인정보 실제값을 넣지 않는다.

정상 샘플 외에 필수값 누락, 중복 등록, 미존재 수정, 잘못된 Service ID와 페이지 경계를 준비한다. Sample 결과가 현재 DTO 필드와 Mapper 조건에 맞는지 CI에서 검증하면 문서 노후화를 줄일 수 있다.

## 31.16 테스트 작성

테스트는 가장 작은 계층에서 시작한다. Rule은 순수 단위 테스트, Service는 DAO Stub/Mock으로 정상·중복·미존재와 영향 행 수를 검사한다. Handler는 Service ID Collection과 Facade 분기를 확인한다. Mapper는 Local DB에서 namespace, binding, count/list 조건과 변경 SQL을 실행한다.

통합 테스트는 TCF ON/OFF Context를 각각 띄워 기대 Controller와 Handler만 존재하는지 확인한다. Filter ON에서 GUID·Context, Timeout ON에서 rollback, 오류 응답의 code와 UI 요청 전문도 포함한다. 쓰기 테스트는 테스트 Transaction 또는 격리 DB로 반복 가능하게 만든다. 단순 Compile은 Spring Proxy, Mapper XML과 HTTP 계약 오류를 찾지 못한다.

## 31.17 빌드와 검증

변경 파일을 확인한 뒤 대상 모듈 테스트와 빌드를 실행한다. `pdmg-service`는 Java뿐 아니라 Mapper XML, exceptionCode, UI 연계 계약과 WAR 산출물을 검증한다. UI 정적 파일은 route와 요청 생성 Smoke Test를 수행한다. 설정을 바꿨다면 local·dev 차이와 TCF/Timeout 조합도 확인한다.

실패한 테스트를 무시하고 빌드 성공만 보고하지 않는다. 실행 명령, 결과, 실행하지 못한 범위와 원인을 기록한다. 기존 사용자 변경을 보존하고 자동 생성 Diff에 불필요한 포맷 변경이 없는지 검토한다. 배포 전에는 rollback 가능한 이전 설정과 Schema 호환성을 준비한다.

## 31.18 완료 체크리스트

완료는 소스 파일 존재가 아니라 요구사항 추적성이 닫힌 상태다. 업무축·번호·Service ID가 등록되고, UI에서 Mapper까지 같은 식별자를 추적할 수 있어야 한다. 정상과 실패에서 Transaction·오류·로그가 예상대로 동작하며 TCF 지원 모드가 명확해야 한다.

```text
요구사항
→ mgcoa9001 + S0/C0/U0/D0
→ UI Header/URL
→ TCF ON Handler 또는 OFF Controller
→ Facade TX → Service/Rule
→ DAO namespace.statement → SQL
→ dto/result 응답 → UI
```

### 정상·실패 및 AS-IS·TO-BE 비교

| 사례 | 정상/실패 흐름 | 확인점 |
|---|---|---|
| 목록 조회 | S0 → count/list → rows | count 조건·정렬·페이징 동일 |
| 등록 | C0 → exists=0 → insert | 중복이면 BizException·rollback |
| 수정 | U0 → exists>0 → update 1건 | 미존재·0건이면 실패 |
| 삭제 | D0 → exists>0 → delete 1건 | 키 누락·다건 삭제 방지 |
| TCF ON | Handler → Facade TX → Service | 업무 선후처리·timeout 포함 |
| TCF OFF AS-IS | Controller → Service 직접 | Facade TX와 동작 차이 검증 |

TO-BE의 핵심은 두 진입 모드가 공통 Facade 또는 동일 유스케이스 경계로 수렴하는 것이다. 현행 Controller가 Service를 직접 호출하는 패턴을 무조건 복사하면 Transaction과 DTO 변환 차이가 반복된다. 신규 프로그램은 지원 모드를 명시하고 차이를 제거하거나 테스트로 계약화한다.

### Anti Pattern

- 기존 프로그램 폴더를 복사한 뒤 이름만 치환한다. 남은 Service ID와 namespace가 다른 거래를 호출한다.
- Controller가 DAO를 직접 호출한다. 업무 검증, Transaction과 ON/OFF 공통 경계가 사라진다.
- 하나의 DTO로 S/C/U/D를 모두 처리한다. 필수값과 공개 필드가 불명확해진다.
- Mapper에 문자열 치환을 사용하거나 UPDATE WHERE 키를 생략한다.
- 오류코드와 UI·샘플·테스트 없이 Compile 성공을 완료로 본다.
- 클라이언트의 사용자·영업점 값을 검증 없이 감사값으로 저장한다.

### 개발·검증 체크리스트

- [ ] 업무축과 프로그램 번호의 소유권·충돌을 확인했는가?
- [ ] 모든 Service ID가 Handler, URL, UI Header와 일치하는가?
- [ ] 거래별 입력·출력 DTO와 필드 제약이 정의됐는가?
- [ ] TCF ON/OFF 진입점과 공통 업무 경계가 명확한가?
- [ ] Facade TransactionManager, readOnly, rollback 규칙이 적절한가?
- [ ] Service와 Rule의 책임이 분리되고 예외가 재전파되는가?
- [ ] DAO FQCN과 Mapper namespace, method와 statement id가 일치하는가?
- [ ] SQL이 파라미터 바인딩과 안전한 WHERE를 사용하는가?
- [ ] 오류 코드가 실제 표준 응답과 UI에 연결되는가?
- [ ] 정상·실패 샘플과 단위·Mapper·통합 테스트가 있는가?
- [ ] GUID, Token, 개인정보 로그 정책과 Timeout을 확인했는가?
- [ ] 대상 빌드와 WAR/정적 UI Smoke Test 결과를 기록했는가?

### 아키텍처 판단과 다음 장

신규 프로그램의 핵심 판단은 코드 재사용량이 아니라 경계의 일관성이다. 조회와 변경의 Transaction, 인증된 Context, 도메인 검증, Persistence 계약과 오류 변환이 계층별 책임에 맞아야 한다. 실제 예제를 참고하되 AS-IS 결함까지 복제하지 않는다.

이 장은 요구사항 한 건을 배포 가능한 프로그램으로 닫는 전체 절차를 다뤘다. 다음 장에서는 그중 반복 빈도가 높은 목록·단건·등록·수정·삭제를 분리하여, 각 CRUD 행위의 DTO·SQL·동시성·오류와 테스트 차이를 정형화한다.
