# 제5부 트랜잭션과 타임아웃

# 21장. Spring 트랜잭션 기초

여러 SQL을 하나의 업무 성공으로 묶으려면 동일한 JDBC Connection에서 BEGIN 이후의 변경을 모두 실행하고 마지막에 Commit 또는 Rollback해야 한다. PDMG는 이 저수준 절차를 업무 코드가 직접 다루지 않고 Spring `PlatformTransactionManager`, MyBatis `SqlSessionTemplate`과 `@Transactional` Proxy에 맡긴다.

`@Transactional`을 메서드에 붙였다는 사실만으로 트랜잭션을 이해할 수는 없다. 어떤 TransactionManager를 선택했는지, 호출이 Spring Proxy를 통과했는지, 현재 Thread에 기존 거래가 있는지, 예외가 경계 밖으로 전파됐는지를 함께 봐야 한다. 이 장은 PDMG의 RDW Bean 연결과 Spring 기본 원리를 설명한다. TCF·Timeout 조합별 실제 최외곽 시작 위치는 다음 장에서 확장한다.

## 이 장에서 해결할 질문

- RDW DataSource, SqlSessionFactory, SqlSessionTemplate과 TransactionManager는 어떻게 같은 자원에 연결되는가?
- TransactionInterceptor는 Proxy 진입과 반환·예외 시점에 무엇을 하는가?
- 현재 Thread와 JDBC Connection의 결합은 왜 중요한가?
- 기본 `REQUIRED`는 새 거래와 기존 거래를 어떻게 선택하는가?
- RuntimeException과 checked Exception의 기본 Rollback 규칙은 무엇인가?
- PDMG 쓰기 Facade의 `rollbackFor=Exception.class`는 무엇을 보강하는가?
- 예외를 catch해 정상 반환하면 왜 부분 Commit이 생길 수 있는가?

## Bean과 실행의 큰 그림

```text
spring.datasource.rdw 설정
          ▼
rdwDataSource(HikariDataSource)
   ├─ rdwSqlSessionFactory
   │     ├─ Mapper XML
   │     └─ MybatisLogInterceptor
   ├─ rdwSqlSessionTemplate
   │     └─ DAO Proxy가 사용
   └─ rdwTransactionManager
         └─ DataSourceTransactionManager

호출 Thread
  → Transaction Proxy
  → TransactionManager가 Connection 결합
  → Service → DAO → SqlSessionTemplate
  → 같은 Connection 사용
  → 정상 Commit / 예외 Rollback
```

## 21.1 PDMG의 트랜잭션 원칙

트랜잭션 경계는 SQL 한 문장이 아니라 유스케이스의 성공 조건에 맞춘다. 등록 본문과 이력 INSERT가 모두 성공해야 한다면 둘은 같은 거래에 참여한다. 두 번째 SQL이 실패했는데 첫 번째만 남으면 업무 상태가 불완전해진다.

PDMG 업무 코드가 사용하는 대표 관리자는 `rdwTransactionManager`다. 주요 Facade의 조회는 `readOnly=true`, 쓰기는 `rollbackFor=Exception.class`를 명시한다. 일부 `mgcoa9001Service` 메서드에도 같은 관리자의 Annotation이 존재한다.

DAO는 거래를 직접 시작하지 않고 상위 경계에 참여한다. 이 원칙은 Transaction 정책을 Service ID 유스케이스 단위로 읽게 한다. 다만 Timeout ON에서는 더 바깥 Worker TransactionTemplate가 있을 수 있으므로 Facade Annotation이 항상 실제 BEGIN이라는 뜻은 아니다.

## 21.2 RdwDataSourceConfig

`RdwDataSourceConfig`는 RDW Persistence에 필요한 네 Bean을 한 Configuration에서 만든다.

```text
rdwDataSource
   ├─ rdwSqlSessionFactory
   ├─ rdwSqlSessionTemplate
   └─ rdwTransactionManager
```

또한 `@MapperScan`으로 `nhnis.mg.co.a.persistence.dao`를 스캔하고 `rdwSqlSessionTemplate`을 지정한다. 따라서 DAO Proxy, MyBatis Session과 TransactionManager가 같은 DataSource 축에 놓인다.

이 연결에서 이름은 중요하다. `@Transactional(transactionManager="rdwTransactionManager")`와 Timeout Configuration의 `@Qualifier("rdwTransactionManager")`가 해당 Bean을 선택한다. Bean 이름을 바꾸면 Annotation, Qualifier와 테스트를 함께 변경해야 한다.

## 21.3 RDW DataSource

`rdwDataSource`는 `@ConfigurationProperties("spring.datasource.rdw")`로 환경 값을 받고 HikariDataSource로 만들어진다. URL, 사용자, Pool 크기 같은 설정은 Connection을 어디서 어떻게 공급할지 결정한다. 소스 코드에 Secret을 넣지 않고 환경변수나 승인된 Secret Store로 주입해야 한다.

DataSource는 단순 접속 정보가 아니라 Transaction 자원 식별의 기준이다. `DataSourceTransactionManager`가 관리하는 DataSource와 MyBatis Factory가 사용하는 DataSource가 같아야 DAO 작업이 그 거래에 참여한다. 이름이 비슷한 별도 DataSource는 같은 물리 거래가 아니다.

Connection Pool의 auto-commit 설정만으로 유스케이스 원자성을 설명하지 않는다. Spring Manager가 Transaction 시작 시 Connection 상태를 준비하고 완료 시 Commit/Rollback·복원·반납을 관리한다.

## 21.4 SqlSessionFactory

`rdwSqlSessionFactory`는 RDW DataSource, MyBatis Configuration, Mapper XML과 Plugin을 결합한다. 현행 설정은 `jdbcTypeForNull=NULL`, `callSettersOnNulls=true`를 사용하고 `classpath*:rdw.*/*.xml`을 Mapper 위치로 로드한다.

Factory는 SQL Statement와 TypeHandler를 포함한 Session 생성 규칙이다. Transaction마다 새 Factory를 만드는 것이 아니다. Bean은 애플리케이션 수명 동안 공유되고 실제 Session·Connection 사용은 호출 흐름에서 조정된다.

Factory가 다른 DataSource를 가리키면 `rdwTransactionManager`가 결합한 Connection을 사용하지 못할 수 있다. 구성 테스트는 Bean 이름뿐 아니라 실제 DataSource 객체 동일성을 확인해야 한다.

## 21.5 SqlSessionTemplate

`rdwSqlSessionTemplate`은 MyBatis를 Spring Transaction과 안전하게 연계하는 Thread-safe Template이다. DAO Mapper Proxy가 SQL을 실행할 때 현재 Transaction에 결합된 SqlSession을 사용하고, 거래가 없으면 호출 조건에 맞는 Session을 처리한다.

업무 코드가 SqlSession을 직접 열고 닫지 않는 이유는 이 때문이다. 직접 Session과 Connection을 만들면 Spring 거래 밖에서 자동 Commit되거나 자원이 누수될 수 있다. DAO Proxy와 Template 경로를 유지한다.

Template이 같은 Thread의 Transaction 자원을 찾는다는 점이 핵심이다. 임의 새 Thread에서 DAO를 호출하면 원 Thread의 SqlSession과 Connection이 자동 전달되지 않는다.

## 21.6 `rdwTransactionManager`

Configuration의 Bean은 다음 구현을 반환한다.

```java
return new DataSourceTransactionManager(rdwDataSource);
```

이 관리자는 Transaction Definition을 받아 Connection을 획득하고 현재 Thread에 자원을 결합하며 Commit·Rollback 후 정리한다. `PlatformTransactionManager` 인터페이스로 노출되므로 Annotation 기반 Interceptor와 `TransactionTemplate`이 같은 Bean을 사용할 수 있다.

`@Primary`가 붙어 있지만 주요 업무 Annotation은 manager 이름을 명시한다. 여러 관리자가 생길 때 암묵적 선택에 의존하지 않는 편이 안전하다. 다른 DataSource의 관리자를 선택하면 RDW Mapper 작업과 기대한 원자성이 달라진다.

## 21.7 Spring TransactionInterceptor

Spring은 `@Transactional` Bean 주위에 Proxy와 TransactionInterceptor를 구성한다. 외부 Bean이 Proxy 메서드를 호출하면 Interceptor가 Annotation의 manager, propagation, readOnly와 rollback 규칙을 읽는다.

```text
Caller
  → Transaction Proxy
      ├─ Transaction 속성 조회
      ├─ 기존 TX 탐색
      ├─ BEGIN 또는 참여
      ▼
    실제 Facade/Service
      ▼
    정상 반환 또는 예외
      └─ Commit/Rollback 판단
```

같은 객체의 `this.inner()` 호출은 Proxy를 다시 통과하지 않으므로 inner Annotation이 별도 적용되지 않는다. Spring이 관리하지 않는 객체를 `new`로 만들고 호출해도 Proxy가 없다. private 메서드에 붙인 Annotation을 외부 경계처럼 기대해서도 안 된다.

## 21.8 현재 Thread와 Connection

Spring JDBC Transaction은 보통 현재 Thread에 자원을 결합한다. TransactionSynchronizationManager가 DataSource와 ConnectionHolder의 관계를 관리하고 SqlSessionTemplate이 이를 이용한다.

```text
Thread A
  └─ RDW TX / Connection #1
       ├─ DAO A
       └─ DAO B

Thread B
  └─ Thread A의 Connection 자동 공유 안 됨
```

따라서 `@Async`, CompletableFuture나 임의 Executor로 분리하면 같은 Spring Transaction이 자동 전달되지 않는다. 동일 Connection을 여러 Thread가 공유하도록 억지로 구현하는 것도 JDBC Thread safety와 완료 순서를 깨뜨린다. 새 Thread는 독립 거래 또는 명시적 작업 모델을 가져야 한다.

Timeout Executor는 Worker Thread 안에서 TransactionTemplate를 시작하므로 DAO는 Request Thread가 아니라 Worker에 결합된 Connection을 사용한다. 상세 경계는 다음 장에서 다룬다.

## 21.9 `@Transactional` 실행 과정

기본 propagation은 `REQUIRED`다. 현재 Thread에 같은 Manager의 Transaction이 없으면 새 거래를 시작하고, 있으면 기존 거래에 참여한다.

```text
외부 TX 없음
Facade @Transactional(REQUIRED)
  → 새 TX 시작
  → Service/DAO
  → 완료

외부 TX 있음
Facade @Transactional(REQUIRED)
  → 기존 TX 참여
  → 반환해도 물리 Commit은 외부 경계가 결정
```

조회 Facade의 readOnly는 새 Transaction을 만들 때 Definition에 반영될 수 있다. 이미 외부 일반 Transaction에 참여하면 내부 선언이 물리 거래 속성을 바꾸지 않는다. readOnly도 DB에 절대 쓰기 불가능을 보장하는 보안 장치가 아니라 드라이버·Framework에 대한 Hint 성격을 포함하므로 쓰기 방어를 별도로 설계한다.

`@Transactional`이 DB에 문자 그대로 `BEGIN` SQL을 항상 전송한다고 단순화하지 않는다. Manager와 JDBC Driver가 auto-commit과 Connection 상태를 조정하며 DB별 실제 wire 동작은 다를 수 있다.

## 21.10 Commit

새 Transaction을 시작한 Proxy 메서드가 정상 반환하면 TransactionManager가 Commit한다. 참여 중인 내부 Facade가 반환했다고 즉시 물리 Commit하는 것은 아니다. 가장 바깥 소유 경계가 정상 완료되어야 한다.

Commit 과정에서 DB 오류가 날 수도 있다. 지연된 제약, 연결 장애가 Commit 시 드러나면 성공 DTO를 이미 외부로 확정하지 않아야 한다. Spring Proxy는 메서드 반환을 가로챈 뒤 Commit하고 최종 호출자에게 결과를 돌려준다.

Transaction 완료 후 Connection은 Thread에서 해제되고 상태가 복원되어 Pool로 돌아간다. ThreadLocal 업무 Context 정리는 별도 책임이며 DB Transaction 정리가 대신하지 않는다.

## 21.11 Rollback

Rollback은 대상 메서드에서 예외가 발생했다는 사실만이 아니라 rollback rule에 맞는 예외가 Proxy 밖으로 전달될 때 결정된다. 내부 참여자가 rollback-only를 표시하면 외부가 정상 반환을 시도해도 최종 완료에서 Rollback될 수 있다.

RuntimeException과 Error는 Spring 기본 규칙에서 Rollback 대상이다. Mapper·JDBC 오류는 일반적으로 런타임 DataAccess 계열로 전파되므로 숨기지 않으면 Rollback 흐름으로 간다.

Timeout Worker는 OnlineTimeoutException, RuntimeException, checked Exception wrapper에서 명시적으로 `status.setRollbackOnly()`를 호출한다. 이것은 Annotation 기본 규칙과 별개의 Programmatic 방어다.

## 21.12 Checked Exception 롤백

Spring 기본 규칙에서는 일반 checked Exception이 자동 Rollback 대상이 아니다. 따라서 “Exception이면 종류와 상관없이 항상 Rollback”이라는 설명은 틀리다.

PDMG 주요 쓰기 Facade는 다음처럼 범위를 넓힌다.

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
```

이 선언은 메서드 밖으로 전파된 checked Exception도 Rollback하게 한다. 조회 Facade는 주로 readOnly만 선언하므로 동일한 rollbackFor가 있다고 가정하지 않는다. 외부 Worker TransactionTemplate는 checked Exception을 Runtime wrapper로 바꾸고 rollback-only로 처리한다.

checked Exception을 다른 타입으로 변환할 때 cause를 보존한다. `noRollbackFor`를 추가한다면 부분 Commit이 업무상 안전하다는 명확한 근거와 테스트가 필요하다.

## 21.13 예외를 삼킬 때 발생하는 문제

가장 위험한 코드는 SQL 실패를 catch하고 빈 성공값을 반환하는 것이다.

```java
try {
    dao.updateA(param);
    dao.insertB(param);
    return success();
} catch (Exception ex) {
    log.error("failed", ex);
    return emptyResult();
}
```

두 번째 호출이 실패했더라도 예외가 TransactionInterceptor에 도달하지 않으면 Proxy는 정상 반환으로 보고 Commit할 수 있다. 로그를 남긴 것은 Rollback 신호가 아니다. 복구할 수 없는 업무 실패는 예외를 다시 던지거나 명시적으로 rollback-only로 표시해야 한다.

catch 자체가 금지는 아니다. interrupt flag 복원, 예외 코드 변환, 자원 정리를 위해 필요할 수 있다. 하지만 원인과 실패 상태를 유지해야 한다. 오류 이력을 별도 거래로 남긴 뒤에도 원래 예외를 재전파해야 원 업무가 Rollback된다.

## End-to-End 정상·실패 흐름

```text
정상
Caller → Proxy → Manager/Connection bind → Facade
       → Service → DAO A → DAO B
       → 정상 반환 → COMMIT → Connection unbind

RuntimeException
Caller → Proxy → TX → DAO 실패
       → 예외 전파 → ROLLBACK → 표준 오류

Checked Exception + rollbackFor
Caller → Proxy → TX → checked 예외 전파
       → 규칙 일치 → ROLLBACK

예외 삼킴
Caller → Proxy → TX → 내부 실패 → catch/정상 반환
       → Rollback 신호 없음 → COMMIT 가능
```

## 책임과 경계

| 구성 요소 | 책임 | 금지 오해 |
|---|---|---|
| DataSource | Connection 공급 | 자체로 유스케이스 TX 정의 |
| SqlSessionFactory | MyBatis Session 설정 | 호출마다 Bean 생성 |
| SqlSessionTemplate | Spring TX와 Session 연계 | 다른 Thread TX 자동 공유 |
| TransactionManager | Connection 시작·완료·정리 | 모든 DataSource 동시 관리 |
| TransactionInterceptor | Annotation 해석·완료 판정 | 자기 호출에도 자동 적용 |
| Facade/Service | 예외 전파·업무 성공 조건 | 로그만 남기면 Rollback |

## AS-IS와 일반 원리

| 구분 | 내용 |
|---|---|
| AS-IS | Hikari RDW DataSource와 DataSourceTransactionManager Bean |
| AS-IS | MyBatis Factory·Template·Mapper가 같은 RDW DataSource 축 사용 |
| AS-IS | 주요 Facade가 manager 이름 명시, 쓰기는 rollbackFor=Exception |
| AS-IS | mgcoa9001 Service에도 Transaction Annotation 존재 |
| AS-IS | Timeout Executor는 같은 manager로 TransactionTemplate 사용 |
| 일반 원리 | RuntimeException/Error 기본 Rollback, checked Exception 기본 Commit 가능 |
| 일반 원리 | Transaction 자원은 Thread-bound이며 Proxy 외부 호출이 필요 |

## Anti Pattern

Controller나 DAO 메서드마다 Transaction을 붙여 유스케이스 경계를 분산시키거나, 모든 Manager를 `@Primary` 선택에 맡기는 방식은 피한다. `@Transactional` 메서드를 직접 `new`로 만든 객체에서 호출하거나 자기 호출하면서 적용됐다고 믿는 것도 흔한 오류다.

비동기 Thread가 원 거래에 참여한다고 가정하거나 Connection 객체를 직접 전달하지 않는다. checked Exception이 항상 Rollback된다고 믿거나 catch 후 정상 DTO를 반환하는 것도 부분 Commit의 원인이 된다.

## 실전 검증 시나리오

Spring 통합 테스트에서 실제 Bean Proxy를 호출하고 Transaction 활성 여부와 DB 결과를 검증한다. 정상 두 SQL은 함께 Commit되고, 두 번째 RuntimeException 및 checked Exception에서 첫 번째 변경도 Rollback되는지 확인한다. 같은 테스트를 Manager 이름이 다른 잘못된 구성과 비교하면 연결 오류를 발견할 수 있다.

self-invocation 테스트는 외부 Proxy 호출과 `this.inner()` 호출의 속성 차이를 확인한다. 별도 Executor에서는 Transaction이 비활성 또는 독립임을 검증한다. 예외 삼킴 테스트는 실제 부분 Commit 가능성을 DB 행으로 보여 주어야 한다.

## 개발자·운영자 체크리스트

- `rdwDataSource`, Factory, Template와 Manager가 같은 DataSource를 사용하는가?
- Annotation과 Qualifier가 정확한 manager 이름을 가리키는가?
- 호출 대상이 Spring Bean이며 Proxy를 통과하는가?
- 유스케이스 쓰기에 `rollbackFor` 정책이 충분한가?
- 예외를 정상 DTO로 바꾸는 catch가 없는가?
- 여러 DAO가 같은 Thread와 RDW 자원에서 실행되는가?
- 비동기 작업은 독립 Transaction 정책을 가지는가?
- 내부 readOnly가 외부 TX 속성을 바꾼다고 가정하지 않는가?
- Commit/Rollback 통합 테스트가 실제 DB 결과를 확인하는가?
- 로그에 Connection 정보나 Secret을 과도하게 노출하지 않는가?

## 아키텍처 판단 포인트와 다음 장

Transaction 경계는 Annotation을 붙이기 쉬운 위치가 아니라 실패 시 함께 되돌려야 하는 업무 범위에 둔다. Manager는 대상 DataSource와 일치해야 하고, Thread 전환이 있으면 새 경계를 명시한다. 예외 정책은 Java checked/runtime 분류보다 업무 실패 의미를 기준으로 명문화한다.

이 장의 원리는 모든 PDMG 경로에 적용되지만 실제 BEGIN 소유자는 실행 모드에 따라 달라진다. 다음 장에서는 TCF ON/OFF와 Timeout ON/OFF 조합에서 Worker TransactionTemplate, Facade와 Service Proxy 중 누가 최외곽 경계를 소유하는지 소스 흐름으로 판정한다.
