# 1장. PDMG 시스템 개요

PDMG를 처음 접하면 화면, 업무 서비스, 공통 프레임워크, 인증 서버가 각각 별도의 프로젝트처럼 보인다. 그러나 실제 온라인 거래 한 건은 이 네 모듈의 책임이 이어져 완성된다. 사용자가 화면에서 조회 버튼을 누르면 UI가 요청 전문을 만들고, 서비스가 요청을 받아 거래를 식별하며, 프레임워크가 공통 처리와 업무 진입 경로를 제공한다. 인증이 필요한 환경에서는 JWT가 요청 주체를 증명한다. 이후 업무 로직이 데이터베이스를 조회하거나 변경하고, 처리 결과가 다시 표준 응답으로 조립되어 화면에 돌아간다.

이 장의 목적은 이 전체 과정을 세부 구현보다 한 단계 높은 시점에서 조망하는 것이다. 독자는 이 장을 통해 “어느 모듈이 무엇을 책임지는가”, “거래 한 건을 어떤 값으로 식별하고 추적하는가”, “TCF를 켜고 끄면 진입 경로가 어떻게 달라지는가”를 이해하게 된다. Filter, Interceptor, Dispatcher, 트랜잭션 경계와 스레드 전환의 상세 순서는 2장부터 다룬다.

> **현행 기준**
> 이 장의 AS-IS 설명은 저장소의 `pdmg-ui`, `pdmg-service`, `pdmg-fw`, `pdmg-jwt` 소스와 설정을 기준으로 한다. 설계 의도와 현행 구현이 다른 부분은 사실을 섞지 않고 **AS-IS**와 **TO-BE**로 구분한다.

## 1.1 PDMG의 목적

PDMG는 마케팅 도메인의 온라인 업무를 일관된 방식으로 개발하고 실행하기 위한 애플리케이션과 공통 실행 기반의 집합이다. 여기서 “온라인”은 단순히 HTTP를 사용한다는 의미가 아니다. 화면 또는 API 클라이언트가 서비스 단위의 요청을 보내고, 서버가 요청 한 건의 컨텍스트를 유지하면서 정해진 업무를 동기적으로 수행한 뒤 결과를 돌려주는 거래 방식을 뜻한다.

**PDMG가 왜 존재하는가?** 한 문장으로 답하면, 서로 다른 마케팅 업무를 하나의 실행·통제·추적 원칙 안에서 안전하게 운영하기 위해서다. PDMG는 업무 기능 자체뿐 아니라 업무가 운영 환경에서 예측 가능하게 실행되기 위한 공통 경계까지 제품의 일부로 다룬다.

업무마다 Controller부터 오류 응답까지 독자적으로 만들면 초기 개발은 빨라 보인다. 하지만 서비스가 늘어날수록 인증, 거래 식별, 로그, 타임아웃, 예외 형식과 트랜잭션 경계가 서로 달라진다. 장애가 발생했을 때 같은 사용자의 같은 요청을 화면 로그, 서버 로그, 데이터베이스 처리 내역에서 연결하기도 어려워진다. PDMG는 이 반복 문제를 공통 프레임워크에 모으고, 업무 개발자가 도메인 규칙과 데이터 처리에 집중하도록 한다.

PDMG가 해결하려는 문제는 다음 세 관점으로 정리할 수 있다.

첫째, **개발 관점의 표준화**다. 업무는 Service ID로 식별되고 Handler, Facade, Service, DAO/Mapper라는 공통 구조로 배치된다. 신규 업무가 기존 업무와 같은 진입 방식, 응답 형식, 예외 처리 방식을 사용하므로 코드를 찾고 변경하는 비용이 낮아진다.

둘째, **실행 관점의 통제**다. 요청이 업무 코드에 도달하기 전에 공통 헤더, GUID, 사용자 정보와 JWT를 다룰 수 있고, 거래 수행 중에는 타임아웃과 트랜잭션을 적용할 수 있다. 업무 전후에는 공통 로깅과 후처리를 수행한다. 각각의 기능을 모든 Controller에 복제하지 않아도 되는 이유다.

셋째, **운영 관점의 추적성**이다. GUID를 중심으로 요청과 응답, ImageLog, 예외와 처리 시간을 연결한다. 운영자는 “어떤 URL이 실패했는가”에서 멈추지 않고 “어떤 Service ID의 거래가 어느 사용자 요청에서 실패했는가”까지 좁힐 수 있다.

PDMG는 하나의 거대한 서버가 아니다. 사용자 접점, 업무 실행, 공통 프레임워크, 인증이라는 책임을 분리한 구성이다. 이 분리는 각 모듈을 독립적으로 이해하게 해 주면서도, 온라인 거래라는 하나의 목적 아래 연결한다.

## 1.2 전체 시스템 구성

PDMG의 전체 구조는 다음과 같다. 실선 화살표는 런타임 호출을, 포함 관계는 같은 JVM 안에서 공통 라이브러리를 사용하는 관계를 나타낸다.

```text
┌──────────────────────────────────────────────────────────────┐
│                       Browser / API Client                   │
└───────────────┬──────────────────────────┬───────────────────┘
                │ 화면·Relay               │ 로그인·토큰
                ▼                          ▼
┌──────────────────────────┐   ┌───────────────────────────────┐
│ pdmg-ui                  │   │ pdmg-jwt                      │
│ 화면, 요청 전문 생성     │   │ 로그인, Access/Refresh Token │
│ 직접 호출 및 Relay       │   │ JWKS 공개                     │
│ local port: 8090         │   │ local port: 8110              │
└───────────────┬──────────┘   └──────────────┬────────────────┘
                │ HTTP/JSON                   │ pdmg-fw 포함
                ▼                             │
┌─────────────────────────────────────────────┴────────────────┐
│ pdmg-service                                                │
│ 온라인 진입점, Handler, Facade, Service, DAO/Mapper, DTO    │
│ local port: 8080                                            │
│                                                             │
│   ┌──────────────────────────────────────────────────────┐   │
│   │ pdmg-fw                                              │   │
│   │ Filter, Interceptor, TCF, Context, Timeout, Exception│   │
│   │ 업무 선후처리, ImageLog, 공통 전문                  │   │
│   └──────────────────────────────────────────────────────┘   │
└──────────────────────────────┬───────────────────────────────┘
                               │ MyBatis / JDBC
                               ▼
                     ┌─────────────────────┐
                     │ RDW DataSource / DB │
                     └─────────────────────┘
```

사용자가 실제로 접속하는 서버는 `pdmg-ui`, `pdmg-service`, `pdmg-jwt`다. 반면 `pdmg-fw`는 독립 포트를 가진 서버가 아니라 `pdmg-service`와 `pdmg-jwt`의 클래스패스에 포함되는 공통 JAR다. 따라서 “서비스가 프레임워크를 호출한다”는 말은 대개 원격 HTTP 호출이 아니라 같은 JVM 안의 Spring Bean, Filter, Interceptor 또는 AOP 호출을 의미한다.

이 구성을 이해할 때는 세 종류의 경계를 구분해야 한다.

| 경계 | 연결 방식 | 대표 사례 | 장애 원인 |
|---|---|---|---|
| 프로세스 경계 | HTTP | UI → Service, UI → JWT | 포트, CORS, 네트워크, 인증 헤더 |
| 모듈 경계 | Gradle 의존성 | Service → FW, JWT → FW | 빌드 의존성, Bean 구성, 버전 불일치 |
| 데이터 경계 | JDBC/MyBatis | Service → DB | DataSource, SQL, 잠금, 트랜잭션 |

같은 “호출 실패”라도 경계에 따라 점검 지점이 달라진다. 브라우저에서 요청 자체가 차단되면 UI의 대상 URL과 CORS를 먼저 보고, 애플리케이션 시작 시 Bean 생성이 실패하면 FW 자동 구성과 의존성을 본다. SQL 실행 후 데이터가 남지 않으면 Controller보다 트랜잭션 경계와 Mapper를 확인해야 한다.

## 1.3 주요 모듈

### 1.3.1 pdmg-ui: 사용자와 온라인 거래의 접점

`pdmg-ui`는 화면을 제공하고 사용자의 입력을 PDMG 요청 전문으로 변환한다. 목록 조회, 등록, 변경과 같은 화면 행위를 Service ID와 요청 데이터로 연결하며, 응답 전문에서 업무 결과를 꺼내 화면 상태에 반영한다.

현행 UI에는 두 가지 서비스 호출 형태가 공존한다. 브라우저가 `pdmg-service`를 직접 호출하는 방식과, `pdmg-ui` 서버의 Relay API를 거쳐 호출하는 호환 방식이다. 직접 호출은 경로가 짧지만 브라우저의 CORS 정책과 인증 헤더 구성에 영향을 받는다. Relay는 브라우저와 업무 서버 사이에 UI 서버가 한 단계 더 들어가므로 대상 서버 주소와 오류 전달 규칙을 함께 관리해야 한다.

AS-IS 직접 호출 코드의 공통 헤더는 `Content-Type`과 `Accept` 중심이며 `Authorization`을 자동으로 붙이지 않는다. 따라서 로컬처럼 JWT 검증을 끈 환경에서는 동작하더라도, JWT 검증이 활성화된 환경에서는 별도 연계 없이 401 응답을 받을 수 있다. 이는 UI 화면의 문제가 아니라 인증 계약이 아직 하나로 연결되지 않은 현행 제약이다.

### 1.3.2 pdmg-service: 업무 거래의 실행 주체

`pdmg-service`는 마케팅 업무를 실제로 수행하는 Spring Boot WAR 모듈이다. 요청을 받아 Service ID에 해당하는 Handler를 찾고, Facade와 Service를 통해 유스케이스를 실행하며, DAO와 Mapper로 데이터베이스에 접근한다. 입출력 계약은 DTO가 담당한다.

업무 계층의 기본 방향은 다음과 같다.

```text
Controller 또는 TransactionHandler
        → Facade
            → Service
                → Rule 또는 DAO
                    → Mapper XML / DB
```

Handler는 Service ID 분기와 Facade 호출에 집중한다. Facade는 DTO 변환과 유스케이스 조정, 트랜잭션 경계를 담당한다. Service는 업무 흐름을 표현하고 DAO/Mapper는 데이터 접근을 담당한다. 이 책임 분리는 단순한 폴더 규칙이 아니라, 거래 경로와 트랜잭션 범위를 예측 가능하게 만드는 장치다.

### 1.3.3 pdmg-fw: 공통 실행 기반

`pdmg-fw`는 온라인 거래가 업무 코드에 들어가기 전부터 응답이 끝날 때까지 필요한 공통 기능을 제공한다. 대표 기능은 다음과 같다.

| 영역 | 대표 구성요소 | 역할 |
|---|---|---|
| HTTP 진입 | `DefaultFilter` | 요청 Body 캐시, 공통 컨텍스트 준비, 조건부 JWT 검증 |
| 시스템 전후처리 | `ServicePreventionInterceptor` 등 | 요청·응답 시점의 공통 처리와 ImageLog 연계 |
| TCF | `OnlineTransactionController`, `TcfFacade`, `TransactionDispatcher` | Service ID 해석과 Handler 라우팅 |
| 컨텍스트 | `ServiceContext`, `TransactionContext` | 요청 공통정보와 거래 실행정보 전달 |
| 실행 제한 | `OnlineTimeoutExecutor` | 설정된 시간 안에서 거래 작업 실행 |
| 업무 전후처리 | `BizPrePostAspect` | 업무 수행 전후의 공통 관심사 적용 |
| 오류·응답 | 예외 처리기와 응답 Advice | 알려진 오류의 표준 결과 조립 |

FW는 업무 로직을 대신하지 않는다. 예를 들어 고객 조회 조건이나 한도 계산은 Service 또는 Rule의 책임이다. FW는 그 업무가 동일한 진입 규칙, 컨텍스트, 로그와 오류 체계 안에서 실행되도록 둘러싼다.

### 1.3.4 pdmg-jwt: 인증과 토큰 생명주기

`pdmg-jwt`는 로그인 후 Access Token과 Refresh Token을 발급하고, 갱신과 로그아웃을 처리하며, 공개키 정보를 JWKS 형식으로 제공하는 인증 모듈이다. 현행 설정은 RS256 서명, Access Token 15분, Refresh Token 8시간을 기본으로 한다. Refresh Token은 회전과 폐기 상태를 관리한다.

로컬 AS-IS에서 RSA 2048비트 키 쌍은 애플리케이션 시작 시 메모리에서 생성된다. 서버가 재시작되면 키가 바뀌므로 재시작 전에 발급한 토큰을 새 공개키로 검증할 수 없다. 운영 환경에서는 Private Key를 소스나 로그에 두지 않고 승인된 Key Store, Vault 또는 KMS에 보관하고, 검증자는 안정된 JWKS를 통해 공개키를 얻는 구조가 필요하다.

또 하나의 중요한 AS-IS가 있다. `pdmg-jwt`는 RS256 토큰을 발급하지만, `pdmg-service`의 `DefaultFilter`가 사용하는 `pdmg-fw.JwtProvider`는 공유 비밀키 기반 HMAC 검증 구성이다. 두 구현은 현재 하나의 발급·검증 체계로 직접 연결되어 있지 않다.

| 구분 | AS-IS | TO-BE 방향 |
|---|---|---|
| 발급 | `pdmg-jwt`가 RS256으로 발급 | 유지 가능 |
| 서비스 검증 | `pdmg-fw`의 HMAC 검증 | RS256/JWKS 검증기로 통합 |
| 키 관리 | 시작 시 메모리 키 생성 | 영속 Key Store/Vault/KMS |
| UI 전달 | 직접 호출에 Authorization 자동 구성 없음 | 로그인 결과를 안전하게 보관하고 요청에 전달 |

이 표의 TO-BE는 현행 동작을 설명하는 것이 아니라 통합 시 지향할 경계를 제시한다. 인증 상세와 보안 결정은 인증 장에서 다시 다룬다.

## 1.4 모듈 간 의존 관계

PDMG의 관계는 빌드 의존성과 런타임 호출을 분리해서 읽어야 한다.

```text
[빌드·포함 관계]
pdmg-service ── implementation project(':pdmg-fw') ──▶ pdmg-fw
pdmg-jwt     ── implementation project(':pdmg-fw') ──▶ pdmg-fw
pdmg-ui      ── 독립 애플리케이션

[런타임 관계]
Browser ──▶ pdmg-ui ── HTTP ──▶ pdmg-service
   └──────────────── HTTP ─────▶ pdmg-jwt
pdmg-service ── MyBatis/JDBC ──▶ DB
```

`pdmg-service`가 `pdmg-fw`를 의존하기 때문에 FW의 조건부 Bean과 컴포넌트가 Service 애플리케이션 컨텍스트에 함께 올라온다. `OnlineTransactionController`가 FW 소스에 있어도 8080 포트로 노출되는 이유다. 반대로 FW는 업무 모듈의 클래스를 직접 참조하지 않는다. Spring이 업무 Handler 목록을 수집하여 Dispatcher에 제공하는 방식으로 의존 방향을 유지한다.

이 방향을 뒤집어 FW가 특정 마케팅 Service나 DTO를 알게 만들면 공통 모듈이 업무 모듈에 종속되고 순환 의존성이 생긴다. 신규 업무는 FW를 수정해서 등록하는 것이 아니라 `pdmg-service`에 Handler를 추가하고 정해진 Service ID를 선언해야 한다.

모듈 경계는 변경 책임도 정한다.

| 변경 내용 | 우선 변경 모듈 | 함께 확인할 모듈 |
|---|---|---|
| 화면 입력·표시 | `pdmg-ui` | 요청/응답 DTO가 있는 Service |
| 업무 규칙·SQL | `pdmg-service` | FW 공통 계약, UI 전문 |
| 공통 Filter·Context·TCF | `pdmg-fw` | Service와 JWT의 회귀 영향 |
| 토큰 발급·키 정책 | `pdmg-jwt` | UI 전달과 Service 검증 |
| Service ID | `pdmg-service` | UI, Handler 등록, 샘플 요청과 문서 |

---

## 1.5 기술 스택

PDMG 네 모듈의 현행 빌드는 Java 21과 Spring Boot 3.5.14를 사용한다. 저장소 상위 지침이나 과거 문서의 버전보다 각 모듈의 실제 `build.gradle` 선언을 AS-IS 기준으로 삼는다.

| 계층 | 기술 | PDMG에서의 쓰임 |
|---|---|---|
| 언어·빌드 | Java 21, Gradle 멀티프로젝트 | 모듈 빌드와 의존 관계 관리 |
| 웹 | Spring Boot, Spring MVC, Servlet API | Controller, Filter, Interceptor, 응답 처리 |
| 공통 관심사 | Spring AOP | 업무 선후처리와 실행 계측 |
| 보안 | Spring Security, JWT/JJWT | 인증 진입 제어와 토큰 처리 |
| 데이터 | MyBatis, JDBC | DAO/Mapper와 SQL 실행 |
| 트랜잭션 | Spring Transaction | `rdwTransactionManager` 기반 commit/rollback |
| 로컬 DB | H2 Oracle 호환 모드 | 로컬 업무 실행과 예제 데이터 |
| 로그 | SLF4J, Log4j2 | 시스템 로그와 거래 추적 로그 |
| 배포 | 실행 가능 WAR | 내장 또는 외부 Servlet Container 배포 |

이 스택은 서로 독립적으로 나열된 도구가 아니다. Spring MVC가 HTTP 요청을 Controller까지 전달하고, FW의 Filter와 Interceptor가 그 앞뒤를 감싼다. AOP는 업무 계층의 전후 지점에 개입한다. Facade의 Spring Transaction이 MyBatis와 같은 DataSource 연결을 묶어 commit 또는 rollback을 결정한다. JWT는 HTTP 요청이 업무 실행 경계에 들어오기 전에 요청 주체를 검증하는 데 사용된다.

로컬 H2는 Oracle 호환 모드를 사용하지만 Oracle과 완전히 같은 데이터베이스는 아니다. 운영 SQL을 검증할 때는 함수, 날짜 처리, 페이징 문법과 잠금 동작의 차이를 별도로 확인해야 한다.

## 1.6 로컬 실행 포트와 호출 관계

로컬 환경에서는 세 개의 실행 프로세스와 하나의 라이브러리 모듈을 구분한다.

| 모듈 | 포트 | 실행 성격 | 기본 호출 대상 |
|---|---:|---|---|
| `pdmg-ui` | 8090 | 화면·Relay 서버 | Service 8080, JWT 8110 |
| `pdmg-service` | 8080 | 업무 API 서버 | 로컬 H2 또는 설정된 RDW |
| `pdmg-jwt` | 8110 | 인증·토큰 서버 | 로컬 인증 저장소, JWKS 제공 |
| `pdmg-fw` | 없음 | 공통 JAR | Service/JWT JVM 내부에서 실행 |

권장 기동 순서는 데이터 저장소, `pdmg-jwt`, `pdmg-service`, `pdmg-ui`다. 다만 로컬에서 JWT 검증이 비활성화되어 있고 인증 화면을 사용하지 않는다면 Service와 UI만으로 일부 업무 거래를 확인할 수 있다. 이 편의 구성을 운영 인증 구조와 동일하다고 해석해서는 안 된다.

```text
사용자 화면:       http://localhost:8090
업무 직접 호출:   http://localhost:8080/{serviceId}
TCF 공통 호출:    http://localhost:8080/online
JWT/JWKS:          http://localhost:8110/.well-known/jwks.json
```

`pdmg-service`는 `server.port`를 별도로 지정하지 않아 Spring Boot 기본값인 8080을 사용한다. UI 설정의 업무 대상 기본 URL도 8080을 가리킨다. 포트를 바꾸면 서버 설정만 고칠 것이 아니라 UI의 대상 URL, CORS 허용 Origin, 샘플 요청과 운영 점검 주소도 함께 맞춰야 한다.

로컬 호출이 실패하면 다음 순서가 유용하다. 먼저 각 프로세스가 해당 포트에서 실행 중인지 확인한다. 다음으로 브라우저 개발자 도구에서 실제 요청 URL, CORS와 HTTP 상태를 본다. 401이면 토큰 발급 여부뿐 아니라 UI가 Authorization 헤더를 보냈는지, 서비스 검증 방식과 토큰 알고리즘이 같은지 확인한다. 404이면 포트보다 TCF ON/OFF에 따른 Controller 생성 조건과 요청 경로를 먼저 본다.

## 1.7 PDMG가 처리하는 온라인 거래

PDMG의 온라인 거래는 “Service ID로 식별되는 한 번의 업무 요청과 응답”이다. HTTP 요청 한 건과 거의 함께 시작하지만, HTTP 자체나 데이터베이스 트랜잭션과 같은 개념은 아니다.

```text
HTTP 요청 범위
└─ Filter → Interceptor → Controller → 응답 직렬화
   └─ 온라인 거래 범위
      └─ Service ID 식별 → Handler/Facade/Service 실행
         └─ DB 트랜잭션 범위
            └─ SQL 실행 → commit 또는 rollback
```

HTTP 범위는 요청 수신부터 응답 완료까지다. 온라인 거래 범위는 그 안에서 특정 Service ID의 업무가 실행되는 구간이다. DB 트랜잭션 범위는 `rdwTransactionManager`가 실제 데이터 변경의 원자성을 보장하는 구간이다. 요청 로그가 정상적으로 끝났다고 해서 반드시 DB가 commit되었다는 뜻은 아니며, 타임아웃 응답이 반환되었다고 작업 스레드와 DB 작업이 즉시 멈췄다고 단정할 수도 없다.

Service ID는 프로그램을 거래 단위로 나눈 식별자다. 예를 들어 `mgcoa9000S0`에서 `mgcoa9000`은 프로그램 영역, `S`는 조회 성격, 마지막 숫자는 거래 일련 구분으로 읽는다. 정확한 네이밍 규칙은 별도 장에서 다루지만, 1장에서는 Service ID가 URL 문자열 이상의 라우팅 키라는 점이 중요하다.

TCF ON의 공통 Controller는 Service ID를 다음 우선순위로 결정한다.

1. `ServiceContext`에 반영된 공통 헤더의 서비스 코드(`rms_svc_c`)
2. JSON 요청 본문에서 해석한 Service ID
3. URL Path의 Service ID

AS-IS는 둘 이상의 위치에 값이 있을 때 불일치를 거부하지 않고 우선순위가 높은 값을 사용한다. 클라이언트는 혼선을 피하도록 하나의 규칙으로 값을 보내야 하며, TO-BE에서는 헤더·본문·경로 값이 함께 존재할 때 일치 여부를 검증하는 정책을 고려할 수 있다.

정상 응답은 대체로 공통 헤더와 업무 DTO를 결합한 `{hdr_nhnis, dto}` 형태이며, 프레임워크가 인식한 업무 오류는 `{hdr_nhnis, result}` 형태로 조립된다. 그러나 Filter에서 Body 또는 인증 검증이 조기에 실패하면 Servlet `sendError(400/401)`로 끝날 수 있어 표준 result와 CORS 헤더가 항상 보장되는 것은 아니다. 모든 일반 `Exception`도 동일 형식으로 변환된다고 가정해서는 안 된다.

## 1.8 두 가지 실행 경로: TCF ON과 OFF

TCF는 Service ID를 중심으로 공통 진입점과 Handler 라우팅을 제공하는 실행 체계다. 설정 `nhnis.fw.tcf.enabled`에 따라 애플리케이션의 진입 구조가 달라진다.

### TCF ON

TCF가 켜지면 FW의 `OnlineTransactionController`와 업무 `TransactionHandler`가 활성화된다. 공통 Controller가 Service ID를 해석하고 `TcfFacade`와 `TransactionDispatcher`가 해당 ID를 등록한 Handler로 요청을 보낸다.

```text
HTTP 요청
  → 시스템 선처리
  → OnlineTransactionController
  → TcfFacade / TimeoutExecutor
  → TransactionDispatcher
  → 업무 TransactionHandler
  → Facade(@Transactional)
  → 업무 선후처리
  → Service → DAO/Mapper
  → 공통 응답·시스템 후처리
```

장점은 거래 등록, 라우팅, 타임아웃과 컨텍스트 전달을 공통 경로에서 관찰할 수 있다는 것이다. 신규 거래는 Controller를 늘리기보다 Handler에 Service ID를 등록하고 Facade로 연결한다.

### TCF OFF

TCF가 꺼지면 공통 TCF Controller와 TCF용 Handler가 생성되지 않고, 조건부로 선언된 업무 Controller가 직접 HTTP 진입점이 된다.

```text
HTTP 요청
  → 활성화된 Filter/Interceptor
  → 업무 Controller
  → 업무 코드가 선택한 Facade 또는 Service
  → DAO/Mapper
  → 공통 응답·시스템 후처리
```

TCF OFF는 FW 전체가 사라진다는 뜻이 아니다. Filter, Interceptor, JWT와 응답 Advice는 각각의 별도 설정 조건에 따라 계속 동작할 수 있다. 또한 업무 Controller가 Service를 직접 호출하면 Facade에 선언된 트랜잭션 경계를 우회할 수 있으므로, OFF 경로에서도 Controller → Facade → Service 책임을 유지해야 실행 의미가 같아진다.

| 관점 | TCF ON | TCF OFF |
|---|---|---|
| HTTP 진입점 | 공통 `OnlineTransactionController` | 업무별 Controller |
| 거래 선택 | Dispatcher가 Service ID로 Handler 선택 | URL 매핑으로 Controller 선택 |
| Handler | 사용 | 사용하지 않음 |
| 공통 FW 기능 | 개별 설정에 따라 적용 | 개별 설정에 따라 적용 |
| 트랜잭션 | Facade 진입 시 시작 | Facade를 호출해야 같은 경계 유지 |
| 적합한 용도 | 표준 온라인 거래 | 호환·단순 직접 경로 |

### STF와 ETF의 현행 위치

개념적으로 STF(System Transaction Front)는 거래 실행 전 시스템 공통 처리를, ETF(System Transaction End)는 실행 후 공통 처리를 나타낸다. 그러나 AS-IS 소스에서 `TcfFacade`가 `stf.preProcess()` 또는 `etf.postProcess()`를 직접 호출하지 않는다. 실제 HTTP 시스템 선후처리는 주로 Filter, Interceptor와 ResponseBodyAdvice에 분산되어 있다.

따라서 다음 두 문장을 구분해야 한다.

- **개념 모델:** STF → TCF → ETF라는 세 구간으로 거래 생명주기를 설명할 수 있다.
- **AS-IS 호출 모델:** TCF 앞뒤의 실제 처리는 Filter·Interceptor·Advice가 수행하며 STF/ETF Bean의 명시적 연결은 확인되지 않는다.

TO-BE에서 STF/ETF를 단일 오케스트레이션 경계로 만들려면 기존 Filter와 Interceptor 기능을 중복 실행하지 않도록 책임, 호출 순서, 예외 시 ETF 보장 여부와 컨텍스트 정리 주체를 먼저 결정해야 한다.

## 1.9 핵심 용어

이 절은 용어 사전이 아니라 온라인 거래를 함께 구성하는 값과 처리 지점의 관계를 설명한다.

### Service ID: 실행할 업무를 정하는 키

Service ID는 한 온라인 거래를 식별하고 Handler 또는 Controller로 라우팅하는 키다. 화면번호와 같지 않다. 한 화면이 조회와 등록 등 여러 Service ID를 호출할 수 있고, 같은 Service ID를 화면이 아닌 API 클라이언트가 호출할 수도 있다. Service ID를 변경하면 Handler 등록, UI 호출, 샘플 전문과 문서 색인을 함께 확인해야 한다.

### GUID: 요청 한 건의 추적 키

GUID는 시스템에 들어온 요청 한 건을 여러 처리 계층과 로그에서 연결하는 전역 식별자다. 공통 헤더의 `sys_comm.std_gbl_id`에 해당하며, 요청에 없으면 진입 과정에서 생성하거나 보정된다. 운영자는 GUID로 Filter 로그, 업무 로그, ImageLog와 오류 응답을 연계한다. GUID는 업무를 선택하는 Service ID와 달리 “이번 호출”을 식별한다.

### ServiceContext: HTTP 요청의 공통 상태

`ServiceContext`는 요청·응답 전문, 공통 헤더, GUID, 사용자와 프로파일 같은 요청 수준 정보를 보관한다. `ServiceContextHolder`를 통해 현재 실행 스레드에서 접근하는 ThreadLocal 기반 컨텍스트이므로, 요청 시작 시 설정하고 성공·실패를 포함한 모든 종료 경로에서 반드시 정리해야 한다. 정리하지 않으면 스레드 풀의 다음 요청이 이전 사용자의 정보를 보게 될 수 있다.

### TransactionContext: TCF 실행에 필요한 거래 상태

`TransactionContext`는 Service ID, 현재 `ServiceContext`, 거래 시작 시각 등 Dispatcher와 Handler가 필요로 하는 실행 정보를 묶는다. ServiceContext가 HTTP 요청 전체의 공통 상태라면 TransactionContext는 그 요청 안에서 실행되는 TCF 거래의 관점이다. 현행 `TcfFacade`는 현재 ServiceContext와 Service ID로 TransactionContext를 만든 뒤 타임아웃 실행기 안에서 Dispatcher에 전달한다.

```text
요청 한 건
├─ GUID: 이번 호출을 추적
├─ ServiceContext: HTTP·전문·사용자 공통정보
└─ TransactionContext: Service ID·시작시각·TCF 실행정보
```

### 시스템 선후처리와 STF/ETF

시스템 선처리는 업무와 무관하게 모든 요청에 필요한 준비 작업이다. Body 캐시, 공통 헤더와 GUID 준비, JWT 검증, 요청 로그가 여기에 해당한다. 시스템 후처리는 응답 조립, 처리 결과 기록, ImageLog 완료와 컨텍스트 정리를 담당한다. STF/ETF는 이 전후 구간을 설명하는 개념 및 컴포넌트 이름이며, 현행 실제 호출은 앞 절에서 설명한 것처럼 여러 웹 확장 지점에 분산되어 있다.

### 업무 선후처리

업무 선후처리는 시스템 전후처리보다 업무 실행 지점에 가깝다. AS-IS의 `BizPrePostAspect` 포인트컷은 마케팅 애플리케이션 Service 패키지의 public 메서드를 대상으로 하며, 그 실행 전과 정상 반환 후에 공통 관심사를 적용한다. 따라서 이 지점은 Controller와 Facade보다 안쪽의 Service 경계다. 업무 감사 기록이나 업무 공통 검증을 둘 수 있지만, 데이터 변경을 같은 트랜잭션으로 묶으려면 Aspect의 실행 위치와 Facade의 `@Transactional` 경계를 함께 확인해야 한다.

업무 선후처리가 있다는 사실만으로 후처리 SQL이 자동으로 같은 트랜잭션에 참여하는 것은 아니다. 동일 스레드, 동일 DataSource/TransactionManager, 활성 트랜잭션 내부라는 조건을 만족해야 한다. 구체적인 포인트컷과 트랜잭션 순서는 뒤 장에서 다룬다.

### ImageLog

ImageLog는 요청과 응답 전문, 처리 결과와 시각을 GUID 중심으로 남겨 거래의 입력과 출력을 재구성할 수 있게 하는 기록이다. 일반 애플리케이션 로그가 개발자 메시지와 스택 흐름을 설명한다면, ImageLog는 거래 한 건의 표준 전문과 결과를 운영 관점에서 연결한다.

```text
요청 수신
  → GUID 확정
  → ImageLog 선처리 기록
  → 업무 실행
  ├─ 정상: 응답·성공 결과 기록
  └─ 예외: 오류 결과 기록
  → 완료 시각·소요시간 반영
```

ImageLog에 Access Token, Refresh Token, Private Key, 비밀번호와 개인정보를 그대로 남겨서는 안 된다. 전문 전체를 기록하는 기능일수록 마스킹 정책과 저장 기간, 조회 권한이 아키텍처의 일부가 된다.

### TransactionManager: DB 변경의 원자성을 지키는 관리자

`rdwTransactionManager`는 같은 DataSource 연결에서 수행되는 SQL을 하나의 commit/rollback 단위로 관리한다. 이름에 Transaction이 들어가는 `TransactionContext`와 역할이 다르다. TransactionContext는 거래 실행 정보를 전달하는 객체이고, TransactionManager는 데이터베이스 변경의 원자성을 제어하는 Spring 인프라다.

### 용어를 한 장으로 연결하기

```text
사용자 요청
  │
  ├─ GUID ─────────────────────── 장애 추적의 축
  ├─ ServiceContext ───────────── 요청·헤더·사용자 공통 상태
  │    └─ TransactionContext ──── Service ID와 TCF 실행 상태
  │          └─ Handler/Facade/Service
  │                └─ TransactionManager ── DB commit/rollback
  │
  ├─ 시스템 선처리(STF 개념) ─── 요청 준비·인증·로그
  ├─ 업무 선후처리 ───────────── 업무 실행 주변의 공통 처리
  └─ 시스템 후처리(ETF 개념) ─── 응답·ImageLog·컨텍스트 정리
```

## 1장 정리: 이후 장을 읽기 위한 지도

PDMG는 `pdmg-ui`라는 사용자 접점, `pdmg-service`라는 업무 실행 주체, `pdmg-fw`라는 공통 실행 기반, `pdmg-jwt`라는 인증 모듈로 구성된다. UI와 서버는 HTTP로 통신하지만 FW는 Service와 JWT 안에 포함되어 같은 JVM에서 동작한다. 이 차이를 알아야 CORS 장애와 Bean 구성 장애, SQL 장애를 서로 다른 경계에서 진단할 수 있다.

온라인 거래는 Service ID로 선택되고 GUID로 추적된다. ServiceContext가 HTTP 요청의 공통 상태를, TransactionContext가 TCF 실행 상태를 전달한다. 시스템 선후처리는 요청 전체를 감싸고, 업무 선후처리는 업무 실행 지점에 개입하며, TransactionManager는 그 안의 DB 변경을 commit 또는 rollback한다. ImageLog는 이 과정을 GUID 중심의 거래 기록으로 남긴다.

현행에서 특별히 기억할 아키텍처 사실은 네 가지다.

1. TCF ON은 공통 Controller와 Handler/Dispatcher 경로를, OFF는 업무 Controller 직접 경로를 사용한다.
2. TCF OFF여도 Filter와 Interceptor가 자동으로 모두 꺼지는 것은 아니다.
3. STF/ETF는 개념과 Bean이 존재하지만 현행 TCF 호출 경로에 명시적으로 결합되어 있지 않다.
4. `pdmg-jwt`의 RS256 발급과 `pdmg-service`의 HMAC 검증은 아직 하나의 인증 체계로 통합되지 않았다.

2장에서는 이 지도를 바탕으로 Browser에서 DB까지 요청 한 건이 이동하는 실제 순서, 정상·예외 흐름, HTTP 요청과 DB 트랜잭션의 경계, 타임아웃 실행 시 요청 스레드와 작업 스레드의 관계를 추적한다.

### 아키텍트 확인 질문

- 변경하려는 기능은 UI, 업무, 공통 FW, 인증 중 어느 책임에 속하는가?
- 문제 지점은 HTTP 프로세스 경계, JVM 모듈 경계, DB 경계 중 어디인가?
- 요청을 선택하는 Service ID와 요청을 추적하는 GUID를 구분했는가?
- TCF ON/OFF에서 동일한 Facade와 트랜잭션 경계를 유지하는가?
- ServiceContext가 모든 종료 경로에서 정리되는가?
- ImageLog에 비밀정보와 개인정보가 기록되지 않는가?
