# 제3부 온라인 요청과 TCF 프레임워크

# 12장. TCF 온라인 거래 프레임워크

PDMG에서 온라인 거래가 늘어날 때마다 Controller가 Service ID를 해석하고, 업무 클래스를 찾아 호출하며, 제한시간과 오류 처리를 각각 구현한다면 거래 수만큼 실행 방식도 늘어난다. 새로운 거래 하나가 추가될 때 Framework 코드를 수정해야 한다면 공통 계층은 확장 지점이 아니라 변경 병목이 된다. TCF는 공통 HTTP 진입과 Service ID 기반 라우팅을 제공하고, 업무 Handler를 Spring Bean으로 수집해 이 문제를 해결하려는 온라인 거래 실행 Framework다.

그러나 TCF를 하나의 상자로 보면 실제 동작을 오해하기 쉽다. `OnlineTransactionController`, `TcfFacade`, `TransactionContext`, `OnlineTimeoutExecutor`, `TransactionDispatcher`와 업무 `TransactionHandler`는 서로 다른 책임을 가진다. 이름에 Transaction이 들어가도 모두 DB Transaction을 시작하는 것이 아니며, 시스템 선후처리라는 이름의 STF·ETF가 Bean으로 존재해도 자동 실행되지는 않는다.

현행 소스에서 실제 요청 경로는 다음과 같다.

```text
OnlineTransactionController
  → TcfFacade
    → OnlineTimeoutExecutor
      → TransactionDispatcher
        → TransactionHandler
          → Business Facade
            → Service → DAO
```

과거 문서와 의도된 구조에는 STF가 Dispatcher 앞에, ETF가 업무 실행 뒤에 놓인다. 하지만 현재 `TcfFacade`는 Dispatcher와 Timeout Executor만 주입받고 STF·ETF를 호출하지 않는다. 따라서 이 장은 “구현된 컴포넌트”와 “실제로 연결된 실행 단계”를 분리한다. TCF의 가치를 과장하지 않고, 현재 무엇을 보장하며 무엇을 보장하지 않는지 실제 호출선으로 설명한다.

## 이 장에서 해결할 질문

- TCF ON 요청은 어떤 URL에서 시작해 어떤 업무 Handler에 도달하는가?
- Service ID는 어디에서 결정되고 Registry Key로 어떻게 사용되는가?
- `TransactionContext`는 무엇을 전달하며 DB Transaction과 어떤 차이가 있는가?
- `TcfFacade`와 업무 Facade는 이름이 같은데 책임과 Transaction은 어떻게 다른가?
- STF와 ETF는 현재 실행되는가, 아니면 구현만 존재하는가?
- Handler Registry는 언제 만들어지고 중복·누락 Service ID를 어떻게 처리하는가?
- Timeout ON/OFF에서 Thread와 Transaction 경계는 어떻게 달라지는가?
- 정상·업무 예외·미등록 Service ID·Timeout에서 응답 경로는 어떻게 달라지는가?
- TCF가 담당해야 할 공통 실행 제어와 업무 계층 책임의 경계는 어디인가?

## 실제 파이프라인과 의도된 파이프라인

```text
[AS-IS 실제 호출선]

HTTP POST
  → Filter / Interceptor
  → OnlineTransactionController
  → TransactionContext 생성
  → TcfFacade
  → OnlineTimeoutExecutor
  → TransactionDispatcher
  → Registry에서 Handler 선택
  → TransactionHandler.handle
  → Business Facade → Service → DAO
  → ResponseBodyAdvice / afterCompletion
```

```text
[문서·설계상 확장 흐름]

Controller → TcfFacade
  → STF.preProcess
  → TimeoutExecutor / Dispatcher / Handler
  → ETF.postProcess
  → Response

현재: STF와 ETF 호출 연결 없음
```

두 그림의 차이가 이 장의 핵심이다. 클래스, Bean과 메서드가 존재하는지만 확인해서는 실행 Architecture를 알 수 없다. Caller에서 실제 호출되는지까지 확인해야 한다.

## 12.1 TCF의 책임

TCF는 TCF ON 모드에서 여러 온라인 거래를 하나의 공통 실행 형식으로 수렴시킨다. 공통 Controller가 요청에서 Service ID와 `dto`를 분리하고, `TcfFacade`가 실행 Context를 만든다. Dispatcher는 시작 시 구성한 Registry로 Service ID에 대응하는 Handler를 찾고, Handler는 업무 Facade를 호출한다. Timeout 설정이 활성화되면 Dispatcher 아래는 별도 Worker와 TransactionTemplate 경계에서 실행된다.

```text
TCF가 현재 담당하는 것
  ├─ 공통 온라인 HTTP 진입점
  ├─ Service ID 결정과 전달
  ├─ TransactionContext 생성
  ├─ Timeout Executor 호출
  ├─ Service ID → Handler Registry
  ├─ 미등록·중복 Service ID 오류
  └─ Handler 실행 결과·예외 전달
```

이 책임은 업무를 대신 구현한다는 뜻이 아니다. TCF는 고객, 계좌, 상품과 같은 DTO 의미를 모르며, 등록 가능 여부나 조회 조건을 판단하지 않는다. SQL과 업무 Transaction 정책도 업무 Facade·Service·DAO가 소유한다. 인증은 앞선 Filter, 시스템 요청·응답 ImageLog는 Interceptor와 ResponseBodyAdvice가 담당한다.

TCF를 단순 Controller Wrapper로 설명해도 부족하다. Registry를 통한 확장, 조건부 Bean, 공통 Timeout·Worker 실행과 오류 전파가 핵심이기 때문이다. 반대로 “모든 공통 정책을 TCF가 보장한다”고 설명해도 틀리다. 현행 STF 거래통제와 ETF 사후 검사는 호출선에 없고, Filter·Interceptor·Advice는 TCF 밖의 MVC 생명주기에서 실행된다.

Architecture 판단은 기능 목록보다 경계로 해야 한다. 모든 거래에서 같은 방식으로 적용돼야 하고 Service ID를 기준으로 실행 전후를 제어하는 정책은 TCF 확장점 후보다. 업무 한 종류에만 필요한 검증과 DML은 Handler 아래 업무 계층에 둔다. HTTP Header와 Servlet Request를 다루는 책임은 Web Adapter에 남긴다.

## 12.2 OnlineTransactionController

`OnlineTransactionController`는 `nhnis.fw.tcf.enabled=true`일 때 만들어지는 TCF ON 공통 Controller다. 세 개의 POST Mapping을 제공하지만 모두 내부 `handle()`로 수렴한다.

| Mapping | Service ID 후보 | 목적 |
|---|---|---|
| `POST /online` | Header/Body | 공통 Root 호환 |
| `POST /{businessCode}/online` | Header/Body/Path | 업무코드 포함 호환 |
| `POST /{serviceId}` | Header/Body/Path | PDMG 직접 Service ID URL |

Controller는 요청을 `Map<String,Object>`로 받고 최상위 `dto` Node만 `TcfFacade.process(serviceId, dtoBody)`에 넘긴다. 업무별 DTO Class를 공통 Controller가 알지 않는 구조다. Header 전체는 Filter가 이미 `ServiceContext`에 구성했으며 Controller는 Context Header, 요청 JSON Header와 Path에서 Service ID를 해석한다.

현행 우선순위는 다음과 같다.

```text
1. ServiceContext.header.sys_comm.rms_svc_c
2. 요청 JSON hdr_nhnis.sys_comm.rms_svc_c
3. Path Variable
4. 모두 없으면 null
```

Path가 `/mgcoa9000S0`이어도 Context Header에 `mgcoa9001D0`이 있으면 Header 값이 선택될 수 있다. Controller는 두 값의 불일치를 거절하지 않는다. 운영 표준은 Path, Header와 Service Catalog가 같은 ID를 가리키도록 해야 하며, TO-BE에서는 복수 위치에 값이 있으면 일치 검증을 고려할 수 있다.

Controller는 Client IP가 Header에 없을 때 `X-Forwarded-For` 첫 값 또는 Remote Address를 보완하고, 선택된 Service ID가 Context Header에 비어 있으면 `rms_svc_c`에 넣는다. 이것은 값 보완이지 신뢰성 검증이 아니다. Proxy 신뢰 정책과 인증 사용자 결합은 별도 보안 책임이다.

Service ID가 null이거나 `dto`가 없더라도 Controller 자체가 모든 입력을 거절하지 않는다. null Service ID는 Dispatcher에서 `ServiceHandlerNotFound`가 되고, null DTO는 Handler나 업무 변환 단계에서 실패할 수 있다. 오류를 어느 단계에서 만들지 결정할 때는 공통 오류 코드와 Client가 이해할 수 있는 메시지를 함께 고려한다.

## 12.3 TransactionContext

`TransactionContext`는 TCF 처리 한 건에 필요한 최소 실행 정보를 담는다. `serviceId`, 현재 `ServiceContext` 참조와 `startedAtNanos`를 보관하며 Handler가 Service ID로 거래를 분기하거나 Header와 GUID를 참조하고 경과시간을 계산할 수 있게 한다.

```java
TransactionContext context =
        TransactionContext.fromCurrent(serviceId);
```

`fromCurrent()`는 `ServiceContextHolder.getInstance()`를 읽어 새 TransactionContext에 넣는다. 이 Context는 메서드 인자로 Dispatcher와 Handler에 전달된다. 앞 장에서 설명한 ServiceContext의 HTTP 생명주기를 대체하는 것이 아니라 TCF 실행에 필요한 좁은 View를 제공한다.

이름에 Transaction이 있어도 Spring `TransactionStatus`, JDBC Connection 또는 TransactionManager를 담지 않는다. `startedAtNanos`는 실행 경과시간 측정 기준이며 DB Begin 시각과 같지 않을 수 있다. TransactionContext가 만들어진 뒤 Timeout Executor가 Worker Transaction을 시작하기 때문에 둘의 시작 시점도 다르다.

| 항목 | TransactionContext 의미 | 의미하지 않는 것 |
|---|---|---|
| `serviceId` | Dispatcher Registry Key | DB Transaction ID |
| `serviceContext` | Header/GUID 접근 참조 | 독립 복사본 보장 |
| `startedAtNanos` | TCF 경과시간 기준 | Commit 시각 |
| `elapsedMs()` | 생성 이후 소요시간 | DB Query Timeout |

ServiceContext가 null인 상태에서도 TransactionContext는 만들어진다. `getHeader()`와 `getGuid()`는 null을 반환할 수 있지만 Dispatcher는 Service ID만으로 Handler를 찾을 수 있다. 인증·감사상 Context가 필수인 운영 거래라면 Controller나 앞선 정책 경계에서 명시적으로 거절해야 한다.

## 12.4 TcfFacade

`TcfFacade`는 공통 Controller와 Dispatcher 사이의 TCF Core 진입점이다. 이름 때문에 업무 Facade와 혼동하기 쉽지만 책임이 다르다. 현행 생성자는 `TransactionDispatcher`와 `OnlineTimeoutExecutor`만 주입받는다.

```java
TransactionContext context = TransactionContext.fromCurrent(serviceId);
Object result = onlineTimeoutExecutor.execute(
        () -> dispatcher.dispatch(serviceId, dtoBody, context));
return result;
```

이 짧은 코드가 실제 Pipeline을 결정한다. Context를 만들고, Dispatcher 호출을 Callable로 감싸 Timeout Executor에 넘기며, 결과를 그대로 반환한다. SQL, DTO 변환, ImageLog, 응답 봉투와 업무 검증은 수행하지 않는다. 클래스 자체에 `@Transactional`도 없다.

Timeout이 비활성화되면 `SyncOnlineTimeoutExecutor`가 현재 Thread에서 Callable을 직접 실행한다. 활성화되면 `DefaultOnlineTimeoutExecutor`가 Request Context를 캡처하고 Worker Pool에 제출한 뒤 `TransactionTemplate` 안에서 Dispatcher를 실행한다. 따라서 같은 TcfFacade 코드라도 설정에 따라 Thread와 최외곽 Transaction 경계가 달라진다.

```text
Timeout OFF
Request Thread → Dispatcher → Handler → Facade TX

Timeout ON
Request Thread → submit → Worker Thread
                         → TransactionTemplate TX
                           → Dispatcher → Handler → Facade REQUIRED
```

Worker Transaction이 이미 `rdwTransactionManager`로 시작됐다면 업무 Facade의 기본 REQUIRED는 같은 Worker Thread Transaction에 참여한다. 업무 Facade가 다른 Manager나 Propagation을 사용하면 경계는 달라진다. 자세한 Timeout과 Transaction 조건은 후속 장에서 다루지만, TCF Pipeline을 이해하려면 Thread가 바뀌는 위치를 숨겨서는 안 된다.

## 12.5 STF 시스템 선처리

STF는 TCF 실행 전 공통 정책을 배치하기 위한 시스템 선처리 컴포넌트다. 현행 `stf.preProcess(TransactionContext)` 구현은 Context Header를 가져와 `MgTxControlService.check()`를 호출한다. 거래통제는 GLOBAL, 업무, 서비스, 채널, 영업점, 사용자와 IP Rule을 조회하고 차단 또는 저장소 오류를 표준 예외로 표현하려는 구조다.

그러나 `stf`가 `@Component`이고 TCF ON 조건으로 Bean이 생성된다는 사실은 실행을 의미하지 않는다. 현행 `TcfFacade`에는 STF Field, 생성자 Parameter와 `preProcess()` 호출이 없다. Controller와 Dispatcher도 STF를 호출하지 않는다.

```text
[존재하는 코드]
stf.preProcess(context)
  → MgTxControlService.check(header)

[실제 TcfFacade]
context 생성
  → OnlineTimeoutExecutor
    → dispatcher.dispatch

STF 연결: 없음
```

따라서 거래통제 Rule을 DB에 등록해도 현재 TCF 요청이 그 Rule 때문에 차단된다고 보장할 수 없다. 운영 적용 여부는 Bean 목록이 아니라 `[stf] transaction control check` 로그, Mock 호출 횟수와 차단 통합 Test로 증명해야 한다.

STF를 연결할 때는 위치를 결정해야 한다. Timeout Executor 밖에 두면 빠른 정책 차단은 가능하지만 통제 조회시간이 온라인 Timeout 예산에 포함되지 않는다. Worker 안, TransactionTemplate 안에 두면 제한시간과 Context 전파를 공유하지만 통제 DB 조회가 업무 Transaction에 참여할 수 있다. 정책 DB 장애가 전체 업무를 막는 fail-close인지, TCF OFF에도 같은 통제가 필요한지도 함께 정해야 한다.

STF는 Interceptor와 다르다. Interceptor는 Spring MVC가 Handler 호출 전에 실행하며 Header/GUID 보완과 ImageLog를 담당한다. STF는 TCF가 직접 호출해야 하는 Service ID 기반 실행 정책 확장점이다. 두 이름에 모두 선처리가 들어가도 호출 주체와 책임이 다르다.

## 12.6 TransactionDispatcher

`TransactionDispatcher`는 Service ID를 `TransactionHandler` Bean으로 연결하는 Router다. Request마다 Spring Context에서 Handler를 검색하지 않고, 생성자에서 주입받은 `List<TransactionHandler>`를 순회해 Map을 만든다. 요청 시에는 Map Lookup으로 Handler를 선택한다.

`dispatch()`는 먼저 Service ID가 비어 있는지 검사하고, Registry에서 Handler를 찾는다. 없으면 `ServiceHandlerNotFound`를 발생시킨다. 찾으면 `handler.handle(dtoBody, context)`를 호출하고 반환값을 그대로 상위로 돌려준다.

```text
dispatch(serviceId, dto, context)
  ├─ serviceId blank → ServiceHandlerNotFound
  ├─ handlerMap[serviceId] 없음 → ServiceHandlerNotFound
  └─ handler.handle(dto, context)
       ├─ 정상 Object 반환
       └─ 예외 상위 전파
```

Dispatcher는 Service ID와 Handler의 대응만 안다. `S0`, `C0`, `U0`, `D0`의 업무 의미나 DTO Type, Facade Method와 SQL을 알지 않는다. 이 정보를 Dispatcher의 if/switch에 넣으면 거래 추가 때 Framework Core를 수정해야 하고 모듈 의존 방향도 깨진다.

`handlers()`는 현재 Map의 불변 복사본을 반환한다. 진단 Endpoint나 Test가 등록 상태를 확인하는 데 사용할 수 있지만 Runtime에 Registry를 임의 변경하는 API는 아니다. Handler Registry는 애플리케이션 기동 시 확정되는 정적 실행 계약으로 보는 편이 안전하다.

## 12.7 TransactionHandler Registry

Registry는 애플리케이션 시작 시 Dispatcher 생성자에서 조립된다. 각 Handler의 `serviceIds()` 결과를 순회해 `ConcurrentHashMap`에 등록한다. 빈 목록이나 null을 반환한 Handler는 Warning 후 건너뛴다. 같은 Service ID를 두 Handler가 선언하면 `IllegalStateException`으로 기동이 실패한다.

```text
Spring Bean Scan
  → List<TransactionHandler>
  → handler.serviceIds()
  → serviceId별 Map 등록
      ├─ 최초 등록: 성공 로그
      ├─ 빈 목록: Warning + Skip
      └─ 중복 ID: 기동 실패
```

중복을 시작 단계에서 막는 것은 중요하다. Runtime에 어느 Handler가 선택될지 비결정적으로 두면 같은 URL이 배포 순서에 따라 다른 업무를 실행할 수 있다. 기동 실패는 불편해 보이지만 잘못된 라우팅으로 데이터가 변경되는 것보다 안전하다.

`TransactionHandler` Interface는 단일 ID용 `serviceId()`와 복수 ID용 `serviceIds()` 기본 메서드를 제공한다. PDMG 업무 Handler는 보통 한 프로그램·도메인의 S/C/U/D 거래 목록을 `serviceIds()`로 반환한다. 신규 거래를 추가하려면 Handler 목록과 내부 분기를 동시에 갱신해야 한다.

등록 성공은 세 단계로 확인한다. Handler Bean이 TCF ON 조건에서 실제 생성됐는지, 기동 로그에 Service ID 등록이 있는지, `handlers()` 또는 통합 Test에서 정확한 Handler Instance로 연결되는지를 본다. UI Catalog와 URL만 추가하고 Registry를 누락하면 요청 시 미등록 오류가 난다.

현재 저장소에는 Timeout Executor Test는 있지만 Dispatcher Registry의 중복·누락을 포괄하는 전용 Test가 충분한지는 별도 확인이 필요하다. 핵심 Core 계약이므로 빈 ID, 중복 ID, 미등록 요청과 정상 등록을 자동화하는 것이 권장된다.

## 12.8 Handler 선택과 실행

업무 `TransactionHandler`는 Entry Adapter다. Dispatcher가 어느 업무 묶음을 호출할지 결정하면 Handler는 `context.getServiceId()`를 기준으로 세부 거래를 분기하고 업무 Facade를 호출한다. Handler가 받은 `dtoBody`는 Object 또는 Map이므로 업무 Facade의 변환 책임과 입력 계약을 따라야 한다.

```text
handler.handle(dtoBody, context)
  → switch(context.getServiceId())
      S0 → facade.search(dtoBody)
      C0 → facade.create(dtoBody)
      U0 → facade.update(dtoBody)
      D0 → facade.delete(dtoBody)
      default → 미지원 거래 예외
```

Handler의 책임은 분기와 위임이다. 입력 DTO를 조립하고 여러 Service를 조정하는 유스케이스 책임은 업무 Facade에 두며, 업무 검증과 계산은 Service/Rule, 데이터 접근은 DAO/Mapper에 둔다. Handler에 SQL이나 업무 Transaction을 넣으면 TCF OFF와 다른 진입 Adapter에서 재사용하기 어렵다.

Registry에 ID가 있다고 Handler 내부 switch가 반드시 그 ID를 처리하는 것은 아니다. `serviceIds()`에 등록했지만 switch Case를 빠뜨리면 Dispatcher 선택은 성공한 뒤 Handler가 미지원 오류를 낸다. 반대로 switch Case만 추가하고 `serviceIds()`에 넣지 않으면 Handler까지 도달하지 않는다. 두 계약을 Test로 묶어야 한다.

업무 Facade의 `@Transactional`은 Handler가 Spring Bean Proxy를 통해 Facade를 호출할 때 적용된다. Timeout ON에서 외부 TransactionTemplate가 이미 Transaction을 열었다면 REQUIRED Facade는 참여할 수 있다. Handler가 `new Facade()`로 직접 만들거나 자기 호출로 Proxy를 우회하면 Transaction 기대가 깨진다.

## 12.9 ETF 시스템 후처리

ETF는 TCF 업무 실행 뒤의 공통 사후 정책 확장점이다. 현행 `etf.postProcess(TransactionContext)`는 Timeout Property가 활성화됐을 때 Context의 경과시간과 제한시간을 비교하고, 초과하면 `OnlineTimeoutException`을 발생시키려는 구현을 가진다. GUID와 Service ID를 로그에 남겨 사후 진단도 지원한다.

그러나 STF와 마찬가지로 현행 TcfFacade는 ETF를 주입하거나 호출하지 않는다. Dispatcher가 정상 반환하면 Timeout Executor 결과가 곧바로 TcfFacade의 반환값이 된다. Handler나 Facade 예외가 나도 ETF를 `finally`에서 실행하는 코드가 없다.

```text
현행 정상
Handler return → Executor return → TcfFacade return

현행 실패
Handler throw → Executor rollback/unwrap → TcfFacade throw

ETF.postProcess
  → 두 경로 모두 호출 없음
```

따라서 “정상에서 ETF 실행, 실패에서 ETF Skip”이라고 AS-IS를 설명할 수도 없다. 현재는 정상과 실패 모두 ETF가 실행되지 않는다. 실제 시스템 후처리는 Spring MVC의 ResponseBodyAdvice와 Interceptor `afterCompletion`이 담당하며, 업무 후처리는 Service Pointcut의 `BizPrePostAspect`가 정상 반환 시 실행한다. ETF와 이 컴포넌트를 혼합하면 실행 순서와 Transaction 포함 범위를 잘못 판단하게 된다.

ETF를 연결한다면 성공 전용 정책인지, 예외에도 실행할 cleanup인지 분리해야 한다. 성공 결과 검증은 Dispatcher 반환 뒤에 둘 수 있지만 감사 cleanup은 `finally`가 필요하다. 이미 Worker Executor가 Deadline과 Interrupt를 검사하므로 ETF의 사후 Timeout 검사와 중복되는 부분도 정리해야 한다. 같은 Timeout을 두 곳에서 서로 다른 시점과 오류 코드로 판단하면 운영 로그가 혼란스러워진다.

## 12.10 정상 거래 흐름

정상 거래 한 건을 `mgcoa9000S0` 예로 추적하면 다음과 같다. Filter와 Interceptor가 Context와 GUID를 준비한 뒤 공통 Controller가 Service ID를 확정하고 `dto`를 추출한다. TcfFacade는 TransactionContext를 만들고 Executor에 Dispatcher Callable을 넘긴다. Registry가 Handler를 찾고 Handler가 조회 Facade를 호출한다. 업무가 정상 반환하면 결과가 같은 호출선을 거슬러 Controller로 돌아가고 MVC Advice가 표준 응답을 만든다.

```text
Request Thread
  OnlineTransactionController
    → serviceId = mgcoa9000S0
    → dtoBody 추출
    → TcfFacade.process
      → TransactionContext 생성

Timeout OFF: 같은 Request Thread
Timeout ON : Worker Thread + TransactionTemplate
      → Dispatcher.handlerMap[mgcoa9000S0]
      → mgcoa9000Handler.handle
      → mgcoa9000Facade.mgcoa9000S0
      → Service → DAO → Mapper
      → 정상 반환
      → Commit

Request Thread
  → ResponseBodyAdvice
  → Post ImageLog
```

조회 Facade의 readOnly와 쓰기 Facade의 rollback 설정은 업무 메서드에 따라 다를 수 있다. TCF가 S0이면 자동 readOnly, C0이면 자동 Write Transaction을 선택하는 구조는 아니다. Handler가 어떤 Facade 메서드를 호출하고 그 메서드가 어떤 Transaction Annotation을 갖는지가 중요하다.

정상 응답은 업무 DTO가 Controller로 돌아온 뒤 ResponseBodyAdvice에서 `{hdr_nhnis, dto}` 형태로 조립된다. TcfFacade나 ETF가 응답 봉투를 만드는 것이 아니다. 이 경계를 알아야 응답 Field를 변경할 때 수정 위치를 올바르게 선택할 수 있다.

## 12.11 실패 거래 흐름

실패는 발생 위치에 따라 업무 실행 여부와 Transaction 상태가 다르다. Service ID가 비어 있거나 Registry에 없으면 Dispatcher가 Handler 호출 전에 `ServiceHandlerNotFound`를 던진다. Handler 분기 누락은 Handler 내부에서 발생한다. 업무 검증·DAO 예외는 Facade 아래에서 발생하며 Worker 또는 Facade Transaction의 Rollback 후보가 된다.

| 실패 위치 | Handler 실행 | 업무 DML | 주요 결과 |
|---|---:|---:|---|
| JWT/Filter | 미실행 | 없음 | MVC/TCF 미진입 가능 |
| Service ID null | 미실행 | 없음 | `ServiceHandlerNotFound` |
| Registry 미등록 | 미실행 | 없음 | `ServiceHandlerNotFound` |
| Handler switch 누락 | 진입 | 대개 없음 | 미지원 거래 예외 |
| Facade/Service 검증 | 진입 | 이전 작업 가능 | 예외 전파·Rollback 판단 |
| DAO/SQL | 진입 | 일부 실행 가능 | TX Rollback 필요 |
| Pool 포화 | Worker 미시작 가능 | 없음 | Overload 예외 |
| Timeout | 이미 실행 가능 | 진행 중일 수 있음 | 취소 요청·Rollback 확인 |

Timeout ON의 Worker는 Runtime Exception과 checked Exception Wrapper에서 `status.setRollbackOnly()`를 호출하고 밖으로 전파한다. Request Thread의 제한시간이 초과되면 `future.cancel(true)`로 Interrupt를 요청한다. 그러나 JDBC Driver나 외부 호출이 Interrupt를 즉시 따르지 않을 수 있으므로 Client가 Timeout 응답을 받았다는 사실만으로 DB 작업이 물리적으로 멈췄다고 단정하지 않는다.

예외를 Service나 Handler에서 잡고 정상 DTO로 반환하면 TransactionTemplate와 `@Transactional`이 실패를 인지하지 못해 Commit할 수 있다. 복구 가능한 예외만 명시적으로 변환하고, Rollback이 필요한 원인은 Transaction 경계 밖으로 전파하거나 rollback-only를 설정해야 한다.

ETF는 실패 시 cleanup을 담당하지 않는다. 현재 호출되지 않기 때문이다. MVC 공통 예외 Handler와 ResponseBodyAdvice, Interceptor afterCompletion의 동작은 예외 Type과 응답 Commit 시점에 따라 달라질 수 있다. TCF 오류와 시스템 ImageLog 실패를 같은 Transaction으로 오해해서는 안 된다.

## 12.12 TCF ON/OFF 조건부 Bean

`nhnis.fw.tcf.enabled=true`는 TCF 실행 계층의 조건부 Bean을 활성화한다. 공통 Controller, TcfFacade, Dispatcher, STF, ETF와 업무 Handler들이 이 조건을 사용한다. `GlobalExceptionHandler`도 같은 TCF 조건을 사용한다. OFF용 업무 Controller는 `havingValue=false`, `matchIfMissing=true` 조건으로 반대 경로를 제공한다.

| 구성요소 | TCF ON | TCF OFF |
|---|---:|---:|
| `OnlineTransactionController` | 생성 | 미생성 |
| `TcfFacade` | 생성 | 미생성 |
| `TransactionDispatcher` | 생성 | 미생성 |
| 업무 `TransactionHandler` | 생성 | 미생성 |
| `stf` / `etf` | 생성, 현재 미호출 | 미생성 |
| TCF `GlobalExceptionHandler` | 생성 | 미생성 |
| 업무 직접 Controller | 미생성 | 생성 가능 |
| Filter/Interceptor | 별도 설정 | 별도 설정 |
| DataSource/TransactionManager | 별도 구성 | 별도 구성 |

Timeout Executor Bean 선택은 `nhnis.fw.timeout.enabled`라는 별도 Property에 따른다. TCF ON이더라도 Timeout이 false면 Sync 구현을 사용한다. TCF OFF에서는 Executor Bean이 존재할 수 있어도 TcfFacade 호출선을 우회하므로 온라인 업무에 적용되지 않을 수 있다. Bean 존재와 요청 경로 적용을 다시 구분해야 한다.

```yaml
nhnis:
  fw:
    tcf:
      enabled: true
    timeout:
      enabled: true
```

설정 전환은 Controller 하나만 바꾸는 기능이 아니다. Registry, Handler, 공통 예외와 Timeout 적용 경로가 함께 달라진다. OFF 상세 구조와 호환 전략은 다음 장에서 다룬다.

## 12.13 TCF가 담당하지 않는 영역

TCF의 경계를 분명히 하지 않으면 공통 Framework에 업무 코드가 쌓인다. TCF는 Service ID로 Handler를 찾고 실행을 조정하지만 업무 데이터의 의미를 판단하지 않는다. DTO Field 검증, 업무 Rule, 여러 Service의 유스케이스 조정과 SQL은 업무 계층 책임이다.

TCF는 인증을 직접 수행하지 않는다. 비 Local JWT 검증은 DefaultFilter의 현재 책임이며, 권한과 거래통제는 별도 정책으로 연결해야 한다. STF 구현에 거래통제가 있다는 이유로 현재 모든 요청이 통제된다고 간주해서는 안 된다.

TCF는 모든 Transaction을 무조건 보장하지 않는다. Timeout ON Worker의 TransactionTemplate와 업무 Facade Annotation이 실제 경계를 만들며, Manager·Propagation·Thread와 예외 전파에 따라 결과가 달라진다. 외부 시스템까지 원자적으로 Rollback하는 분산 Transaction도 제공하지 않는다.

TCF는 응답 JSON과 ImageLog의 최종 소유자도 아니다. ResponseBodyAdvice와 Interceptor가 MVC 생명주기에서 처리한다. TCF OFF에서도 별도 설정이 켜져 있으면 이 시스템 처리는 유지될 수 있다.

```text
TCF Core                    Business / Web / Operation
Service ID Routing          DTO 의미·업무 Rule
Handler Registry            SQL·Mapper
Context + Executor 연결      JWT 검증
공통 실행 오류 전파          응답 봉투·ImageLog
                             외부 분산 Transaction
```

공통 기능이라는 이유만으로 TCF에 넣지 않는다. 해당 기능이 Service ID 실행 전후에 있어야 하는지, HTTP 기술에 종속되는지, 업무별로 달라지는지와 Transaction 경계를 기준으로 배치한다.

## Service ID 한 건을 Registry까지 추적하기

새로운 `mgcoa5530S0` 조회 거래가 추가됐다고 하자. UI가 이 ID를 Path와 Header에 넣어 요청하더라도 TCF가 자동으로 Java Method 이름을 추론하지는 않는다. 애플리케이션 시작 시 `mgcoa5530Handler` Bean이 생성되고 `serviceIds()`가 `mgcoa5530S0`을 반환해야 Dispatcher Map에 Key가 생긴다. 요청 시 Controller가 선택한 문자열이 이 Key와 문자 단위로 같아야 Handler가 선택된다.

```text
UI/Service Catalog: mgcoa5530S0
  ↓ HTTP Path/Header
Controller resolved ID: mgcoa5530S0
  ↓ TcfFacade/Dispatcher
Registry Key: mgcoa5530S0
  ↓
mgcoa5530Handler
  ↓ context.getServiceId() switch
mgcoa5530Facade.mgcoa5530S0
```

이 연결의 어느 한 곳에 오타가 있으면 증상이 달라진다. Handler Bean이 생성되지 않으면 기동 등록 로그가 없다. `serviceIds()`에서 빠지면 Dispatcher가 미등록 오류를 낸다. Registry에는 있지만 switch Case가 다르면 Handler에 진입한 뒤 미지원 오류가 발생한다. Facade Method가 잘못 연결되면 요청은 성공적으로 다른 업무를 실행할 수도 있어 더 위험하다. 따라서 단순 200 응답이 아니라 예상 Facade 호출과 반환 DTO를 검증해야 한다.

운영 장애에서는 GUID와 함께 `Controller resolved serviceId`, Dispatcher 등록 Key와 선택된 Handler Class를 비교한다. Header 우선순위 때문에 Path만 보고 원인을 판단하면 안 된다. 애플리케이션 기동 로그의 등록 목록을 배포 Artifact별로 보존하면 Service Catalog와 실제 Runtime Registry의 차이를 빠르게 찾을 수 있다.

신규 거래 Test는 Handler의 `serviceIds()`와 switch 지원 범위가 같다는 불변조건을 검사해야 한다. Interface가 switch Case 목록을 직접 노출하지 않으므로 각 등록 ID로 `handle()`을 호출해 미지원 예외가 없는지 확인하거나, 업무별 Parameterized Test를 작성한다. UI Catalog의 Service ID와 Registry를 Build 단계에서 비교하면 URL만 추가하고 Handler를 누락하는 배포를 막을 수 있다.

## Timeout ON/OFF에서 Transaction 경계를 증명하기

TCF의 Transaction을 이해할 때 Annotation 목록만 보면 안 된다. Timeout OFF에서는 Sync Executor가 Request Thread에서 Dispatcher를 바로 호출하고, 업무 Facade Proxy 진입 시 Transaction이 시작될 수 있다. Timeout ON에서는 Worker가 `TransactionTemplate`을 먼저 시작한 뒤 Dispatcher와 Handler를 호출한다. 내부 업무 Facade의 REQUIRED는 같은 Manager와 Thread라면 기존 Worker Transaction에 참여한다.

```text
Timeout OFF
Request Thread
  Controller → TcfFacade → Dispatcher → Handler
    → Facade Proxy: TX BEGIN
      → Service/DAO
    → COMMIT/ROLLBACK

Timeout ON
Request Thread → Future submit
Worker Thread
  Context install
  TransactionTemplate: TX BEGIN
    → Dispatcher → Handler → Facade REQUIRED 참여
      → Service/DAO
  COMMIT/ROLLBACK
  Context clear
```

이를 증명하려면 고정 GUID 한 건에 Thread 이름, Transaction 활성 여부와 Connection 식별 정보를 구간별로 기록한다. Timeout OFF에서는 Controller와 Service Thread가 같고 Facade 직전까지 Transaction이 비활성일 수 있다. Timeout ON에서는 Worker 이름으로 바뀌고 Dispatcher 진입 전에 Transaction이 활성인지를 확인한다. 단, 운영 로그에 Connection 문자열이나 민감한 DB 정보를 그대로 남기지 말고 Test 전용 관측을 사용한다.

Facade가 다른 `transactionManager`를 지정하거나 `REQUIRES_NEW`를 사용하면 위 참여 관계가 달라진다. 조회 Facade의 readOnly가 이미 시작된 외부 Transaction 속성을 소급 변경하지 못할 수도 있다. 어떤 Annotation이 더 안쪽에 있다는 이유만으로 최종 Transaction 속성이 그 Annotation과 같다고 단정하지 않는다. 실제 외곽 시작 위치와 Manager를 먼저 확인한다.

업무 예외 Test에서는 한 건 이상의 DML 뒤 checked Exception과 Runtime Exception을 각각 발생시키고 데이터가 남지 않는지 확인한다. Handler가 예외를 변환하거나 삼키는 경우도 별도로 검증한다. Test Method 자체에 `@Transactional`을 붙이면 Test Framework Rollback이 운영 Transaction 결함을 가릴 수 있으므로, 운영과 같은 호출선에서 독립 조회로 결과를 확인한다.

Timeout Test는 HTTP 응답만 Assert해서는 부족하다. 제한시간 직전과 직후, Interrupt를 따르는 작업과 무시하는 작업, 느린 JDBC를 분리한다. Request Thread가 Timeout을 반환한 후에도 Worker가 살아 있는지, Worker가 Deadline 재검사에서 rollback-only가 되는지와 실제 DB Commit 여부를 기다려 확인한다. Pool 포화 Test는 Callable이 시작되지 않은 Overload와 시작 후 제한을 넘긴 Timeout을 별도 오류로 검증한다.

## STF·ETF를 연결할 때의 실행 순서 설계

STF와 ETF를 단순히 TcfFacade 앞뒤에 한 줄씩 추가하면 실행은 되지만 운영 의미가 불분명할 수 있다. 먼저 STF 실패가 Handler를 차단하는지, 통제 조회시간이 Timeout 예산에 포함되는지, 통제 조회가 업무 Transaction에 참여하는지 결정해야 한다. ETF는 정상 결과에서만 실행할 정책과 예외에도 실행할 cleanup을 분리해야 한다.

| 선택 | 장점 | 주의점 |
|---|---|---|
| STF를 Executor 밖에 배치 | Worker·DB 자원 전에 빠른 차단 | 통제 지연이 Timeout 예산 밖 |
| STF를 Worker TX 밖·Worker 안에 배치 | Worker Context와 Deadline 공유 | 별도 호출 구조 필요 |
| STF를 TransactionTemplate 안에 배치 | 한 실행 단위에서 오류 전파 | 통제 DB가 업무 TX에 참여 가능 |
| ETF를 정상 반환 뒤 배치 | 결과 검증 의미가 선명 | 예외 Cleanup에는 사용 불가 |
| Cleanup을 finally에 배치 | 모든 종료 경로 실행 | 원 예외를 덮지 않아야 함 |

권장 판단은 정책의 목적부터 시작한다. 거래통제는 업무 DML 전에 실패해야 하지만 업무 데이터와 원자적으로 Commit될 필요는 대개 없다. 따라서 별도 짧은 조회와 명확한 fail-close/fail-open 정책이 적합할 수 있다. ETF의 사후 Timeout 검사는 Worker Executor의 Deadline 재검사와 기능이 중복되므로 하나를 권위 있는 판정자로 정해야 한다.

연결 후에는 정상뿐 아니라 STF 차단, 통제 DB 장애, Handler 예외, ETF 예외와 Timeout을 조합해 Test한다. STF가 차단했을 때 Handler와 업무 DML 호출 횟수가 0인지, ETF 실패가 이미 Commit된 업무를 Rollback할 수 있는 위치인지 확인한다. Transaction 종료 뒤 ETF를 실행하면 예외를 던져도 앞선 Commit은 되돌릴 수 없다. 실행 순서가 곧 일관성 계약이다.

TCF OFF 적용 여부도 같은 설계에 포함한다. TCF ON의 TcfFacade에만 STF를 연결하면 직접 업무 Controller는 우회한다. 정책이 전 채널 필수라면 ON/OFF 공통 Entry Policy 또는 더 앞선 보안 Gateway가 필요하다. 다음 장의 OFF 구조와 함께 결정해야 한다.

## End-to-End 실행 흐름도

```text
Browser / pdmg-ui
  │ POST /{serviceId}, {hdr_nhnis,dto}

DefaultFilter ── JWT/Body/ServiceContext
  ▼
ServicePreventionInterceptor ── GUID/Pre ImageLog
  ▼
OnlineTransactionController

  └─ dto 추출
  ▼
TcfFacade
  ├─ TransactionContext.fromCurrent
  └─ OnlineTimeoutExecutor
       ├─ Sync: Request Thread

  ▼
TransactionDispatcher
  ├─ handlerMap[serviceId]
  └─ 미등록 → ServiceHandlerNotFound
  ▼
TransactionHandler
  └─ serviceId switch → Business Facade
  ▼
Business Facade(@Transactional)
  → Service → Rule/DAO → Mapper → DB
  ▼

  ▼
ResponseBodyAdvice / Exception Handler
  ▼

STF·ETF: Bean은 있으나 위 AS-IS 호출선에 없음
```

## 운영 장애 추적

Service ID 요청이 404라면 TCF ON 여부와 Controller Mapping부터 확인한다. Controller 로그는 있는데 Dispatcher 등록 로그가 없다면 Handler Bean 조건, Component Scan과 `serviceIds()`를 본다. `ServiceHandlerNotFound`가 발생하면 Header·Body·Path 중 실제로 선택된 ID와 Registry Key를 비교한다.

기동 실패 메시지에 Duplicate Service ID가 있으면 두 Handler 선언을 검색한다. Map에 마지막 Handler를 남기도록 우회하지 않는다. 어느 거래가 올바른 소유자인지 Service Catalog와 업무 코드를 기준으로 하나만 등록한다.

Timeout 응답은 GUID로 Request Thread와 Worker Thread 로그를 나눠 본다. Client 응답 시각, `future.cancel(true)`, Worker Deadline 검사, Transaction rollback과 실제 DB 상태를 비교한다. Pool 포화는 업무가 시작되지 않았을 수 있으므로 느린 SQL과 같은 대응을 하면 안 된다.

STF나 ETF 로그가 없을 때 Log Level부터 바꾸기 전에 호출선 부재를 확인한다. Bean 생성 로그는 실행 증거가 아니다. `TcfFacade` 생성자와 `process()`의 직접 의존성을 확인하고, 통합 Test에서 Spy 호출 횟수를 측정한다.

## Anti Pattern

1. TCF를 단순 Controller Wrapper로만 설명한다.
2. STF·ETF Bean이 있으므로 자동 실행된다고 가정한다.
3. Interceptor를 STF, ResponseBodyAdvice를 ETF라고 혼용한다.
4. Dispatcher에 S/C/U/D 업무 switch와 SQL을 추가한다.
5. Handler에 DTO 변환·업무 계산·DAO를 모두 넣는다.
6. Registry 등록과 Handler 내부 switch 중 한쪽만 변경한다.
7. Header와 Path Service ID가 달라도 우선순위에 맡긴다.
8. `TransactionContext`를 DB Transaction 객체로 취급한다.
9. TcfFacade에 무조건 `@Transactional`을 붙여 HTTP 실행 전체를 넓힌다.
10. Timeout 응답이 오면 Worker와 DB가 즉시 중단됐다고 단정한다.
11. Handler에서 예외를 삼키고 정상 DTO를 반환해 Rollback을 막는다.
12. TCF ON Property 하나가 Filter·JWT·DataSource까지 모두 끈다고 생각한다.
13. ETF와 Worker Deadline 검사를 중복 연결하면서 오류 정책을 정의하지 않는다.
14. 신규 Service ID를 UI와 URL에만 추가하고 Registry 등록을 누락한다.

## 아키텍처 판단 포인트

TCF 확장 기능을 추가할 때는 모든 거래에 동일한지, Service ID 실행 전후에 위치해야 하는지와 실패가 업무 실행을 막아야 하는지를 묻는다. HTTP 기술에 종속된 기능은 Filter/Interceptor/Advice, 업무별 기능은 Facade/Service/Rule에 둔다. TCF Core는 라우팅과 실행 제어에 집중한다.

STF 연결 위치는 Timeout 예산과 Transaction 참여를 결정한다. 빠른 정책 차단이 목적이면 Worker 제출 전에 실행할 수 있고, 실행시간 제한과 Worker Context가 필요하면 Executor 안에 둘 수 있다. 정책 DB 장애의 fail-open/fail-close와 TCF OFF 우회도 함께 설계하지 않으면 위치만 바꿔도 완성되지 않는다.

ETF는 성공 정책과 cleanup 정책을 분리해 생각한다. 성공 결과를 검사하는 로직은 정상 반환에만 적용할 수 있지만 Context 정리와 감사는 예외에도 필요하다. 현행 MVC 후처리와 Timeout Deadline 검사와의 중복을 제거한 뒤 연결해야 한다.

Registry는 정적이고 결정적인 계약이어야 한다. Runtime 등록·교체가 꼭 필요하지 않다면 기동 시 중복을 실패시키고 불변 Map으로 운영하는 현재 방향이 안전하다. Service Catalog, UI 호출 정보와 Handler 목록을 자동 비교하면 누락을 배포 전에 찾을 수 있다.

## 핵심 정리

TCF ON의 실제 실행선은 `OnlineTransactionController → TcfFacade → OnlineTimeoutExecutor → TransactionDispatcher → TransactionHandler → Business Facade`다. Controller는 Service ID와 dto를 추출하고, TcfFacade는 TransactionContext와 Executor를 연결하며, Dispatcher는 Registry에서 Handler를 찾는다.

TransactionContext는 Service ID, ServiceContext 참조와 경과시간을 담지만 DB Transaction을 관리하지 않는다. 실제 Transaction은 Timeout Worker의 TransactionTemplate와 업무 Facade의 `@Transactional`이 Thread와 Propagation 조건에 따라 만든다.

STF와 ETF는 구현과 TCF ON Bean이 존재하지만 현행 TcfFacade 호출선에는 없다. 따라서 거래통제와 ETF 사후 Timeout 검사를 AS-IS 실행 기능으로 표현해서는 안 된다. 시스템 요청·응답 후처리는 Interceptor와 ResponseBodyAdvice, 업무 선후처리는 BizPrePostAspect라는 별도 실행점이다.

Registry는 기동 시 Service ID와 Handler를 연결하고 중복을 기동 실패로 막는다. 신규 거래는 Service ID 등록, Handler 분기와 업무 Facade 호출을 함께 변경하고 정상·미등록·중복·예외를 Test해야 한다.

다음 장에서는 `nhnis.fw.tcf.enabled=false`일 때 공통 Controller, Dispatcher와 Handler가 사라지고 업무 Controller가 직접 진입하는 호환 구조를 다룬다. OFF는 단순히 TCF 이름만 끄는 것이 아니라 Timeout, Registry, 공통 예외와 업무 Transaction 경로를 바꿀 수 있으므로 별도의 실행 Architecture로 이해해야 한다.
