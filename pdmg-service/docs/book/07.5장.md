# 5장 집필 지시 — 네이밍 규칙

5장을 집필하라.

대상 장:

**5장. 네이밍 규칙**

이 작업은 요약, 초안, 목차 채우기가 아니다.

**「PDMG 애플리케이션 아키텍처와 개발 가이드」의 실제 출판 가능한 5장 본문을 작성하는 작업이다.**

---

# 1. 집필 전 반드시 수행할 작업

본문부터 작성하지 마라.

다음 순서로 먼저 자료를 확인한다.

```text
AGENTS.md
   ↓
BOOK-WRITING-RULE.md
   ↓
BOOK-TOC.md
   ↓
SOURCE-MAP.md의 5장
   ↓
3장
   ↓
4장
   ↓
5장 관련 원천자료
   ↓
6장 목차
   ↓
실제 PDMG Source / Package / Mapper 구조 검증
```

특히 다음 관련 자료를 우선 확인한다.

- `MG-NAMING_CONVENTION.md`
- `00.MG-NAMING_CONVENTION.md`
- `06.네이밍 형식.md`
- `06.네이밍 형식-1.md`
- `53.네이밍 아키텍처 다이어그램.md`
- `네이밍원칙.md`

`MG-NAMING_CONVENTION(원본).md`가 존재한다면 최종 규칙의 직접 근거로 무조건 채택하지 말고 편집 이력 또는 참고자료인지 판단한다.

문서 간 규칙이 충돌하면 임의로 하나를 선택하지 않는다.

다음 우선순위를 적용한다.

```text
현재 실제 Source / 설정 / 프로젝트 구조
        ↓
재분석·검증 문서
        ↓
현재 적용 네이밍 기준 문서
        ↓
기본 설명 문서
        ↓
다이어그램
        ↓
과거 원본·편집 이력
```

충돌 사항은 필요하면 본문에서 다음과 같이 구분한다.

- 현재 적용 기준
- 과거 기준
- 예외
- TO-BE 권장안
- 확인 필요 사항

# 2. 5장의 역할

5장의 목표는 단순히 이름 규칙을 나열하는 것이 아니다.

독자가 5장을 읽고 나면 다음을 할 수 있어야 한다.

```text
업무 요구사항
   ↓
업무 코드 결정
   ↓
프로그램 ID 결정
   ↓
Service ID 생성
   ↓
패키지 결정
   ↓
Handler 이름 결정
   ↓
Controller 이름 결정
   ↓
Facade 이름 결정
   ↓
Service / Rule 이름 결정
   ↓
DTO 이름 결정
   ↓
DAO 이름 결정
   ↓
Mapper / SQL ID 결정
   ↓
오류 코드 결정
```

즉,

> **신규 PDMG 프로그램 하나의 이름 체계를 처음부터 끝까지 스스로 설계할 수 있도록 만드는 장**

이어야 한다.

---

# 3. 4장과 5장의 역할을 구분한다

4장은 다음을 설명한다.

> "PDMG에서 프로그램과 거래를 어떻게 식별하는가?"

5장은 다음을 설명한다.

> "그 식별체계를 실제 Java, Package, DTO, DAO, Mapper 등의 이름으로 어떻게 표현하는가?"

따라서 4장의 Service ID 체계를 그대로 반복하지 않는다.

필요한 부분만 연결한 뒤 네이밍 관점으로 심화한다.

예:

```text
4장
애플리케이션 코드
 + 업무 코드
 + 프로그램 번호
 + 거래 구분
        ↓
Service ID

5장
Service ID
        ↓
Package
        ↓
Handler
        ↓
Controller
        ↓
Facade
        ↓
Service
        ↓
DTO
        ↓
DAO
        ↓
Mapper
```

---

# 4. 6장과의 경계도 지켜라

6장은 패키지와 프로젝트 구조를 상세히 설명하는 장이다.

따라서 5장에서는

- 패키지 이름을 어떻게 정하는가
- 패키지 이름에 어떤 코드가 들어가는가
- 계층별 이름은 어떻게 구분하는가

까지 설명한다.

하지만

- 전체 패키지 디렉토리 구조
- Component Scan 상세
- Mapper Scan 상세
- Aspect Pointcut와 패키지 구조

등은 6장에서 심화할 수 있도록 과도하게 침범하지 않는다.

# 7. 5.1 네이밍 규칙의 목적

단순히

> "일관성을 위해 네이밍 규칙이 필요하다."

라고 쓰고 끝내지 마라.

최소 다음 관점에서 설명한다.

- 개발 생산성
- 코드 탐색
- 업무 식별
- 계층 식별
- Service ID 추적
- 운영 장애 추적
- 로그 검색
- 영향도 분석
- 신규 개발자 학습
- 자동화 및 정적 검증
- LLM/Codex를 이용한 코드 생성

특히 다음 관계를 설명한다.

```text
이름
 ↓
업무 식별
 ↓
프로그램 식별
 ↓
계층 식별
 ↓
Source 추적
 ↓
SQL 추적
 ↓
운영 장애 추적
```

---

# 8. 네이밍을 개별 규칙이 아니라 하나의 Chain으로 설명한다

5장의 핵심 다이어그램으로 다음과 같은 구조를 제시하라.

```text
업무 요구사항
      │
      ▼
애플리케이션 코드
      │
      ▼
업무 코드
      │
      ▼
프로그램 ID
      │
      ▼
Service ID
      │
      ├───────────────┐
      ▼               ▼
Java Package        거래/운영 식별
      │
      ▼
Handler
      │
      ▼
Controller
      │
      ▼
Facade
      │
      ▼
Service / Rule
      │
      ▼
DTO
      │
      ▼
DAO
      │
      ▼
Mapper XML
      │
      ▼
SQL Statement ID
```

그 후 각 이름이 왜 연결되는지 본문으로 설명한다.

다이어그램만 제시하고 끝내지 않는다.

# 9. 실제 하나의 프로그램을 관통하는 예제를 사용한다

네이밍 규칙을 각각 별개의 예제로 설명하지 말고 가능하면 **하나의 동일 프로그램**을 장 전체 예제로 사용한다.

예를 들어 실제 PDMG에서 검증 가능한 프로그램을 하나 선정한다.

반드시 실제 Source를 먼저 확인한다.

가상의 이름을 사실처럼 사용하지 않는다.

예제는 다음과 같은 추적 구조를 보여준다.

```text
업무
 ↓
프로그램 ID
 ↓
Service ID
 ↓
Package
 ↓
Handler
 ↓
Controller
 ↓
Facade
 ↓
Service
 ↓
DTOin
 ↓
DTOout
 ↓
DAO
 ↓
Mapper XML
 ↓
Statement ID
```

이를 통해 독자가

> "하나의 거래가 이름 체계 전체에서 어떻게 연결되는가"

를 이해하도록 한다.

---

# 10. Service ID는 반드시 구조적으로 설명한다

Service ID 문자열만 보여주지 않는다.

다음처럼 구성 요소를 해체해서 설명한다.

```text
Service ID
    │
    ├─ 업무 식별
    ├─ 프로그램 식별
    └─ 거래유형 식별
```

현재 실제 규칙에 따라 각 자리 또는 각 영역의 의미를 표로 정리한다.

예:

| 구성         | 의미              | 예          | 판단 기준 |
| ------------ | ----------------- | ----------- | --------- |
| 업무코드     | 업무 영역         | 실제 값     | 분류체계  |
| 프로그램번호 | 프로그램 식별     | 실제 값     | 관리 규칙 |
| 거래유형     | 조회/등록/수정 등 | S/C/U/D/A/R | 처리 성격 |

실제 규칙과 맞지 않는 가상 패턴은 만들지 않는다.

---

# 11. 클래스 네이밍은 계층 책임과 함께 설명한다

다음처럼 단순 표만 만들지 마라.

| 클래스     | 접미어     |
| ---------- | ---------- |
| Controller | Controller |
| Service    | Service    |

각 계층에 대해 반드시 설명한다.

```text
이 이름을 사용하는 이유
        ↓
어떤 계층인가
        ↓
누가 호출하는가
        ↓
무엇을 담당하는가
        ↓
무엇을 담당하면 안 되는가
        ↓
동일 프로그램에서 다른 클래스와 어떻게 연결되는가
```

특히 다음을 비교한다.

- Handler
- Controller
- Facade
- Service
- Rule
- DAO

---

# 12. Handler와 Controller의 네이밍 차이를 설명한다

PDMG에는 TCF ON/OFF 구조가 있으므로 이름만 소개하지 않는다.

가능하면 다음 구조와 함께 설명한다.

```text
TCF ON
/online
  ↓
TransactionHandler

TCF OFF
업무 URL
  ↓
Controller
```

동일 업무에서 Handler와 Controller가 존재한다면 이름의 공통 부분과 차이점을 설명한다.

---

# 13. Service와 Rule 네이밍은 책임 차이까지 설명한다

다음 질문에 답하라.

- Service 이름은 어떤 Use Case를 표현하는가?
- Rule은 어떤 업무 규칙을 표현하는가?
- Service와 Rule을 같은 이름 체계로 만들면 안 되는 이유는 무엇인가?
- Rule을 `Util`, `Helper`, `Manager` 같은 모호한 이름으로 만드는 것이 왜 문제인가?

---

# 14. DTO 네이밍은 데이터 흐름과 함께 설명한다

다음 구조를 사용한다.

```text
Request
  ↓
DTOin
  ↓
Business Processing
  ↓
DTOout

공통/반복 구조
  ↓
DTOSub
```

DTO 이름에 다음이 어떻게 반영되는지 실제 기준으로 설명한다.

- 프로그램 식별자
- 입력/출력
- 하위 구조
- Request/Response와의 관계

---

# 15. DAO와 Mapper는 반드시 연결해서 설명한다

별개의 규칙처럼 나누지 않는다.

다음 관계를 설명한다.

```text
DAO Interface
     │
     │ FQCN
     ▼
Mapper namespace
     │
     │ Method Name
     ▼
Statement ID
     │
     ▼
SQL
```

특히 다음을 확인한다.

- DAO Interface 이름
- DAO Package
- DAO FQCN
- Mapper namespace
- DAO Method
- Statement ID

이 관계가 깨지면 MyBatis에서 어떤 문제가 발생하는지도 설명한다.

단, Mapper 내부 SQL 구현 상세는 19장 영역을 과도하게 침범하지 않는다.

---

# 16. Java Field와 DB Column 네이밍

단순 camelCase / snake_case 설명에 그치지 않는다.

PDMG 실제 설정을 확인하여

```text
DB_COLUMN
   ↓
MyBatis Mapping
   ↓
javaField
   ↓
DTO
```

관계를 설명한다.

자동 Mapping 설정이 존재한다면 실제 설정을 확인해서 설명한다.

확인되지 않았다면 추측하지 않는다.

---

# 17. 오류 코드 네이밍

다음 관점에서 설명한다.

```text
오류 발생 계층
   ↓
업무/시스템 구분
   ↓
오류 코드
   ↓
exceptionCode.yml
   ↓
Message
   ↓
표준 오류 응답
```

단, 예외처리 전체 구조는 26장에서 상세하게 다루므로 5장에서는 **오류 코드의 명명 원칙**에 집중한다.

---

# 18. 금지 이름을 강하게 설명한다

5.16에서는 단순히 금지어 목록만 만들지 않는다.

예를 들어 다음 종류를 검토한다.

```text
Common
Util
Utils
Helper
Manager
Processor
Data
Info
Temp
Test
New
Old
Etc
Object
Map
```

무조건 금지라고 단정하지 말고 실제 네이밍 문서의 기준을 확인한다.

금지 또는 지양 대상이라면 **왜 문제가 되는지** 설명한다.

예:

```text
CustomerManager

문제:
무엇을 관리하는지 알 수 없음.

조회?
등록?
검증?
Transaction 조정?
외부연계?

책임이 이름에서 드러나지 않는다.
```

---

# 19. 좋은 이름과 나쁜 이름을 비교한다

중요한 규칙에서는 비교표를 적극 사용한다.

예:

| 잘못된 이름    | 문제            | 권장 방향               |
| -------------- | --------------- | ----------------------- |
| DataService    | 업무 의미 없음  | Use Case 표현           |
| CommonUtil     | 책임 불명확     | 구체적 책임 표현        |
| ProcessManager | 처리내용 불명확 | 업무 행위를 이름에 표현 |

단, 실제 PDMG 규칙으로 확인된 사례와 일반적인 설명을 구분한다.

---

```text
   ↓

   ↓
STEP 7

   ↓
STEP 8
Facade 이름 결정
   ↓

   ↓
STEP 11
DAO 이름 결정
   ↓
STEP 12
Mapper 및 Statement ID 결정
   ↓
STEP 13
오류 코드 결정
   ↓
STEP 14
전체 네이밍 정합성 검증
```

각 단계별로

- 입력
- 판단
- 결과
- 검증 방법

을 설명한다.

---

# 21. 장 마지막에는 "한 거래의 전체 네이밍 추적표"를 만든다

하나의 실제 프로그램을 기준으로 다음 표를 작성한다.

| 구분         | 실제 이름 | 의미 |
| ------------ | --------- | ---- |
| 업무코드     | ...       | ...  |
| 프로그램 ID  | ...       | ...  |
| Service ID   | ...       | ...  |
| Package      | ...       | ...  |
| Handler      | ...       | ...  |
| Controller   | ...       | ...  |
| Facade       | ...       | ...  |
| Service      | ...       | ...  |
| Rule         | ...       | ...  |
| DTOin        | ...       | ...  |
| DTOout       | ...       | ...  |
| DAO          | ...       | ...  |
| Mapper       | ...       | ...  |
| Statement ID | ...       | ...  |
| 오류 코드    | ...       | ...  |

실제 Source에서 존재하지 않는 항목은 임의 생성하지 말고 `해당 없음`, `미확인`, 또는 예시임을 분명하게 표시한다.

---

# 22. AS-IS와 표준 권장안을 분리한다

현재 Source에 표준과 다른 과거 이름이 존재할 수도 있다.

이를 임의로 정답으로 일반화하지 않는다.

필요하면 다음처럼 설명한다.

| 구분       | 내용                               |
| ---------- | ---------------------------------- |
| 표준       | 신규 개발 시 적용할 규칙           |
| AS-IS 예외 | 기존 소스에 남아 있는 형태         |
| 적용 원칙  | 기존 유지 또는 신규 표준 적용 여부 |
| TO-BE      | 향후 정비 방향                     |

**Legacy 코드가 존재한다고 해서 그것을 네이밍 표준으로 정의하지 마라.**

---

# 23. 네이밍 규칙과 자동 검증을 연결한다

가능하면 다음 가능성도 설명한다.

- Code Review
- 정적 분석
- Gradle 검증
- ArchUnit
- CI
- 템플릿 기반 코드 생성
- Codex/LLM 기반 CRUD 생성

다만 현재 구현되어 있지 않다면 `현재 적용`이라고 표현하지 말고 **TO-BE 또는 자동화 가능 영역**으로 구분한다.

---

# 24. 문체 규칙

다음 형식을 반복하지 마라.

```text
### Controller 명명법

Controller는 Controller 접미사를 사용한다.

예:
- xxxController
```

이런 내용은 책이 아니라 규칙 요약표다.

최소 다음 수준으로 확장한다.

```text
명명 규칙
 ↓
왜 필요한가
 ↓
전체 계층에서의 위치
 ↓
실제 이름
 ↓
다른 클래스 이름과 관계
 ↓
잘못된 사례
 ↓
개발자가 결정하는 방법
```

---

# 25. 표와 본문의 균형

네이밍 장 특성상 표가 많아질 수 있다.

하지만 표만 연속해서 배치하지 않는다.

권장 패턴:

```text
개념 설명
 ↓
규칙 표
 ↓
실제 예
 ↓
해설
 ↓
잘못된 사례
 ↓
개발 판단 기준
```

---

# 26. 장 도입부

5장을 다음 질문으로 자연스럽게 시작하라.

예를 들어:

> 새로운 업무 프로그램 하나를 개발한다고 가정해 보자. Service ID는 무엇으로 정하고, Handler와 Controller는 어떤 이름을 써야 하며, Service·DTO·DAO·Mapper까지 어떻게 하나의 규칙으로 연결해야 할까?

이 질문을 통해 네이밍을 단순 코딩 스타일이 아니라 **PDMG 전체 추적성 체계**로 설명한다.

---

# 27. 장 마지막

최소 다음을 포함한다.

## 핵심 정리

단순 개념 요약이 아니라 개발 시 반드시 지킬 원칙을 정리한다.

## 신규 프로그램 네이밍 체크리스트

실제 개발자가 사용할 수 있도록 작성한다.

## 아키텍처 판단 포인트

예:

- 이름에 계층 책임이 드러나는가?
- Service ID와 프로그램 ID가 일관되는가?
- DAO와 Mapper namespace가 추적 가능한가?
- 범용적이고 모호한 이름을 사용하지 않았는가?
- 기존 Legacy 이름을 신규 표준으로 복제하지 않았는가?

## 다음 장과의 연결

5장에서 정의한 이름이 6장에서 실제 디렉토리와 패키지 구조에 어떻게 배치되는지 자연스럽게 연결한다.

# 28. 작성 후 반드시 자체 검수한다

작성 완료 후 BOOK-WRITING-RULE의 품질 Gate와 함께 다음을 추가로 검사한다.

- [ ] 네이밍 목록만 나열한 장이 되지 않았는가?
- [ ] 왜 해당 이름을 사용하는지 설명했는가?
- [ ] 4장 내용을 불필요하게 반복하지 않았는가?
- [ ] 6장의 패키지 구조 상세까지 침범하지 않았는가?
- [ ] Service ID에서 Mapper까지 연결성이 보이는가?
- [ ] 동일 실제 프로그램을 이용한 End-to-End 예제가 있는가?
- [ ] 기본 문서와 `-1.md`의 차이를 확인했는가?
- [ ] Legacy 명칭을 표준이라고 잘못 판단하지 않았는가?
- [ ] 실제 Source와 네이밍 문서가 다른 부분을 확인했는가?
- [ ] AS-IS와 TO-BE를 구분했는가?
- [ ] 금지 이름에 이유가 설명되어 있는가?
- [ ] 신규 개발자가 5장만 보고 이름을 직접 결정할 수 있는가?
- [ ] 표만으로 본문을 대신한 절이 없는가?
- [ ] 앞 장보다 설명 밀도가 낮아지지 않았는가?

하나라도 부족하면 보고만 하지 말고 본문을 직접 수정하여 보강한다.

# 29. 완료 기준

5장이 완료되었다는 것은 단순히 5.1~5.17까지 텍스트가 존재한다는 뜻이 아니다.

독자가 다음 과제를 스스로 수행할 수 있어야 한다.

> "새로운 PDMG 조회 프로그램 하나를 개발하려고 한다.
> 업무 코드를 결정하고 프로그램 ID와 Service ID를 만든 뒤
> Handler, Controller, Facade, Service, Rule, DTO, DAO, Mapper, SQL Statement ID, 오류 코드까지 표준에 맞게 이름을 설계하라."

이 과제를 수행할 수 있을 정도로 설명되어 있을 때만 5장 집필이 완료된 것으로 판단한다.

**목차를 채우지 마라.**

**네이밍 규칙을 암기표로 만들지 마라.**

**PDMG의 식별체계가 Source 전체로 어떻게 이어지는지를 설명하라.**

**이름만 보고 업무와 프로그램과 계층을 추적할 수 있는 구조를 독자에게 이해시켜라.**

작성 → 자체검수 → 부족한 절 보강 → 최종 파일 저장까지 완료하라.
