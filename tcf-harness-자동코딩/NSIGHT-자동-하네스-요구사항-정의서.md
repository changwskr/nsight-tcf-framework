## 1. 도입 전 안내말

NSIGHT 자동 하네스는 사용자가 입력한 요구사항을 단순히 LLM 프롬프트에 전달하여 코드를 생성하는 도구가 **아니다**.

자동 하네스는 다음 **전체 생명주기**를 관리하는 **개발 실행·통제 플랫폼**이다.

```text
입력자료 수집
→ 기준원 확정
→ 요구사항 분석
→ 업무·도메인 모델링
→ 아키텍처 의사결정
→ 화면·거래·프로그램·데이터 설계
→ 구현계획 생성
→ 소스·설정·SQL·테스트 구현
→ 자동 빌드·검증
→ 산출물·코드 정합성 확인
→ 사람 승인
→ 결과 패키징
→ 변경·Drift 관리
```

NSIGHT 개발은 다음 **추적관계**를 유지해야 한다.

```text
업무 요구사항
→ 화면·이벤트
→ ServiceId·거래코드
→ Handler
→ Facade
→ Service
→ Rule
→ DAO
→ Mapper·SQL
→ DB 객체
→ OM 기준정보
→ 테스트
→ 거래로그·감사로그
```

기존 NSIGHT 방법론도 설계 의도를 구조화된 모델로 관리하고, Baseline 승인 후 코드와 문서를 생성하며, 구현 이후 As-Built와 Drift를 검증하는 흐름을 요구한다. 화면 이벤트부터 ServiceId, 프로그램, SQL, DB 객체까지 **정방향·역방향 추적**이 가능해야 한다.

### 1.1 하네스가 달성해야 할 목적

| 목적 | 설명 |
| --- | --- |
| 요구사항 구조화 | 비정형 문서와 사용자 설명을 구조화된 요구사항으로 변환 |
| 설계 자동화 | 업무·화면·거래·프로그램·데이터 설계 초안 생성 |
| 구현 자동화 | NSIGHT TCF 표준에 따른 소스·SQL·설정·테스트 생성 |
| 추적성 확보 | 요구사항부터 코드·테스트·운영 기준까지 연결 |
| 품질 통제 | 생성 결과의 구조·빌드·테스트·보안·표준 준수 검증 |
| 사람 승인 | 중요 의사결정과 운영 반영 전 승인 Gate 적용 |
| 재현성 확보 | 동일 입력과 기준 버전으로 동일 결과를 재생성 |
| 변경관리 | 요구사항·설계·코드 간 Drift 탐지 및 영향 분석 |

## 2. 문서 개요

### 2.1 목적

입력된 업무 요건을 분석하여 설계·구현·검증 산출물로 변환하는 NSIGHT 자동 하네스의 **기능, 책임, 처리 흐름 및 품질 기준**을 정의한다.

### 2.2 적용범위

자동 하네스는 다음 영역을 대상으로 한다.

- NSIGHT TCF 신규 업무 모듈
- 기존 업무 기능 변경
- CRUD 및 조회·등록·변경·삭제 거래
- 화면 이벤트와 ServiceId 설계
- 표준 요청·응답 전문
- Handler·Facade·Service·Rule·DAO·Mapper 구현
- Mapper XML·SQL·DDL
- OM Service Catalog 및 거래통제 기준정보
- 단위·통합·계약·아키텍처 테스트
- 개발 문서와 추적성 산출물
- 빌드·실행·검증 증적
- As-Designed와 As-Built 비교

**초기 버전 제외:** 운영 서버 자동 배포, 운영 DB DDL 직접 실행.

### 2.3 대상 독자

| 대상 | 활용 목적 |
| --- | --- |
| 업무 분석가 | 요구사항 등록 및 분석 결과 검토 |
| 애플리케이션 아키텍트 | 구조·계층·ServiceId·트랜잭션 결정 |
| 데이터 아키텍트 | 데이터 소유권·테이블·SQL 검토 |
| 보안 아키텍트 | 인증·권한·개인정보·감사 검토 |
| 개발자 | 생성 소스 검토·보완·실행 |
| 테스트 담당자 | 테스트 시나리오와 검증 결과 확인 |
| 품질 담당자 | Gate 및 표준 준수 확인 |
| 운영 담당자 | 운영 기준정보·로그·Runbook 검토 |
| PMO | 진행상태·승인·결함·증적 관리 |

### 2.4 선행조건

- NSIGHT TCF 기준 소스와 문서에 접근할 수 있어야 한다.
- 적용할 Branch와 Commit SHA가 확정되어야 한다.
- 업무코드·도메인·대상 시스템이 식별되어야 한다.
- 생성 결과를 저장할 Git 작업공간이 존재해야 한다.
- Gradle·JDK·테스트 환경이 준비되어야 한다.
- LLM이 참조할 수 있는 문서·소스 검색 기능이 제공되어야 한다.
- 운영 반영은 별도 승인 절차를 거쳐야 한다.

| 용어 | 정의 |
| --- | --- |
| 자동 하네스 | 분석·설계·구현·검증 도구와 Agent를 순차적으로 실행하는 통제 엔진 |
| Run | 하나의 요구사항 처리 실행 단위 |

| Artifact | 요구사항서·설계서·소스·SQL·테스트·보고서 등의 결과물 |

| Drift | 요구사항·설계·코드·설정·OM 정보 간 불일치 |
| Human-in-the-loop | 자동화 결과를 사람이 검토·승인하는 운영 방식 |

## 3. 본문

### 3.1 문제 정의 및 설계 배경

현재 개발 절차는 요구사항, 설계서, 코드, SQL, OM 등록정보와 테스트가 **서로 다른 문서와 도구**에서 관리된다.

```text
요구사항 문서
  ├─ 화면 설계서
  ├─ 거래 설계서
  ├─ 프로그램 설계서
  ├─ DB 설계서
  ├─ Java 소스
  ├─ Mapper XML
  ├─ OM 등록 SQL
  └─ 테스트 결과
```

이로 인해 다음 문제가 발생한다.

- 요구사항이 코드에 누락된다.
- 화면 이벤트와 ServiceId가 일치하지 않는다.
- Handler 등록값과 OM Catalog가 다르다.
- 프로그램 설계서와 실제 클래스 구조가 달라진다.
- SQL 변경에 영향을 받는 화면과 거래를 찾기 어렵다.
- 코드 생성은 되었지만 빌드·실행되지 않는다.
- 테스트 결과가 요구사항과 연결되지 않는다.
- LLM이 확인되지 않은 클래스·테이블·API를 생성한다.
- 동일 요구사항을 다시 실행했을 때 결과가 달라진다.
- 개발 완료 여부를 코드 파일 존재만으로 판단한다.

자동 하네스는 이러한 단절을 **하나의 상태 모델과 추적성 원장**으로 통합해야 한다.

### 3.2 현행 구조와 문제점

| 현행 문제 | 영향 | 자동 하네스 대응 |
| --- | --- | --- |
| 비정형 요구사항 | 해석 차이와 누락 | 구조화 분석 및 질문·가정 기록 |
| 문서별 독립 관리 | 산출물 불일치 | 단일 메타모델과 Artifact Registry |
| 수작업 코드 복사 | 표준 위반·결함 전파 | 기준 모듈 기반 생성 |
| LLM 단독 코드 생성 | 환각·미검증 코드 | 소스 근거와 검증 Gate 강제 |
| 사후 테스트 | 구조 결함 늦게 발견 | 단계별 테스트 선행 생성 |
| 수동 영향 분석 | 변경 누락 | 양방향 추적 그래프 |
| 결과 덮어쓰기 | 기존 코드 유실 | Diff·Patch·승인 기반 반영 |
| 실행 증적 부재 | 완료 여부 불명확 | Build·Test·Run Evidence 저장 |

### 3.3 요구사항과 제약조건

#### 3.3.1 업무 요구사항 (BR)

| ID | 요구사항 |
| --- | --- |
| BR-001 | 사용자는 문서·표·텍스트·소스·DB 정의를 입력할 수 있어야 한다. |
| BR-002 | 하네스는 입력 자료에서 기능·비기능·업무규칙·제약조건을 분리해야 한다. |
| BR-003 | 분석 결과에서 불명확한 항목은 가정으로 표시하고 확정사항과 구분해야 한다. |
| BR-004 | 요구사항은 화면·거래·프로그램·데이터·테스트로 추적되어야 한다. |
| BR-005 | 중요한 아키텍처 결정은 자동 확정하지 않고 승인 대상으로 등록해야 한다. |
| BR-006 | 생성 결과는 실제 빌드·테스트를 통과해야 완료로 판단해야 한다. |
| BR-007 | 기존 소스 변경 시 영향 범위와 변경 Diff를 제공해야 한다. |
| BR-008 | 실행 과정과 판단 근거를 재현할 수 있어야 한다. |

#### 3.3.2 기술 제약조건

- Java 21, Spring Boot, Gradle, MyBatis 기반을 우선 적용한다.
- 업무 구조는 Handler → Facade → Service → Rule → DAO → Mapper를 따른다.
- 공통 OnlineTransactionController와 ServiceId Dispatcher를 사용한다.
- 실제 프로젝트 Branch와 Commit을 기준으로 분석한다.
- 확인되지 않은 클래스와 테이블은 설계 예시 또는 미확정으로 표시한다.
- 운영 데이터와 개인정보를 LLM에 원문으로 제공하지 않는다.
- 자동 생성 결과를 운영 환경에 직접 반영하지 않는다.
- Git Commit과 배포는 사용자 또는 승인자의 통제를 받아야 한다.

NSIGHT CRUD 자동화도 요구사항부터 OM 등록정보와 실행 증적까지 **하나의 개발 단위**로 생성하도록 정의되어 있다.

### 3.4 설계 원칙

| 원칙 | 적용 기준 |
| --- | --- |
| 근거 우선 | 실제 소스·문서·설정에 존재하는 사실을 우선 사용 |
| 단일 기준선 | Branch·Commit·문서 버전을 Run 시작 시 고정 |
| 설계 후 구현 | 요구사항과 설계 Gate 통과 전 코드 생성 금지 |
| 책임 분리 | 분석·설계·구현·검증 Agent를 분리 |
| 사람 승인 | 보안·데이터 소유권·트랜잭션·외부계약은 사람 승인 |
| 추적성 우선 | 모든 Artifact에 요구사항 ID와 Work Item ID 부여 |
| 변경 최소화 | 기존 파일 전체 재작성보다 Patch 방식 우선 |
| 검증 우선 | 생성보다 빌드·테스트·구조검증을 완료 기준으로 사용 |
| 재실행 가능 | 입력·규칙·모델·Tool 버전을 저장 |
| 실패 안전 | 일부 단계 실패 시 기존 정상 결과를 훼손하지 않음 |
| 관찰 가능 | 단계별 상태·입력·출력·오류·소요시간 기록 |
| 단계적 자동화 | 초기에 승인형으로 운영하고 검증된 영역만 자동화 확대 |

### 3.5 대안 비교 및 의사결정

| 대안 | 설명 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. 완전 자율형 | 요구 입력부터 코드 반영까지 자동 | 처리속도 빠름 | 오판·보안·데이터 손상 위험 |
| B. 단순 보조형 | 문서와 코드 초안만 생성 | 도입이 쉬움 | 추적성·검증·자동 실행 부족 |
| **C. 승인 Gate형** | 단계별 자동 실행 후 주요 지점에서 사람 승인 | 통제·품질·자동화 균형 | 승인 절차 설계 필요 |

#### 최종 결정

**C. 승인 Gate형 자동 하네스**를 적용한다.

```text
자동 수행
- 자료 검색
- 요구사항 구조화
- 추적성 초안
- 설계 초안
- 반복 코드 생성
- 테스트 생성
- 빌드·정적검증
- 문서 생성
- Drift 탐지

사람 결정
- 업무 규칙 확정
- 데이터 소유권
- 트랜잭션 경계
- 보안·권한
- 외부 연계 계약
- 운영 반영
- 예외 승인
```

수동 설계방법론과 자동화 절차는 경쟁 관계가 아니라 **설계 의도 → 정형 모델 → 생성 → 구현 → 검증**으로 결합해야 한다.

### 3.12 오류·Timeout·장애 흐름

#### 분석 실패

```text
파일 손상 또는 형식 미지원
→ 해당 입력 격리
→ Run 전체를 즉시 폐기하지 않음
→ 실패 원인과 미분석 범위 기록
→ 사용자 검토 상태로 전환
```

#### LLM 응답 실패

```text
응답 Timeout·형식 오류
→ 동일 입력으로 제한 횟수 재시도
→ 대체 모델 또는 규칙 기반 처리
→ 계속 실패하면 수동검토 전환
```

#### 구현 실패

```text
코드 생성
→ Compile 실패
→ 오류 로그 분석
→ 허용 횟수 내 수정 Patch 생성
→ 재빌드
→ 반복 실패 시 원본 보존 후 Gate 반려
```

#### 테스트 실패

```text
Test 실패
→ 요구사항 또는 구현 결함 분류
→ 기존 정상 테스트를 임의 수정하지 않음
→ 결함 Work Item 생성
→ 조치 후 전체 영향 테스트 재실행
```

#### 상태 저장소 장애

- Run 상태는 원자적으로 저장해야 한다.
- 마지막 성공 Checkpoint부터 재개할 수 있어야 한다.
- 중복 실행 방지를 위한 Run Lock을 사용해야 한다.
- 완료되지 않은 임시 파일은 최종 OUT에 포함하지 않아야 한다.

#### 상태모델

### 3.18 보안·개인정보·감사

- 사용자와 Agent별 최소 권한을 적용한다.
- 개발·검증·운영 환경의 자격증명을 분리한다.
- Private Key와 비밀번호는 Secret Store에서만 조회한다.
- 프롬프트·로그·Artifact에 Secret 원문을 저장하지 않는다.
- 개인정보 입력 시 자동 탐지·마스킹해야 한다.
- 외부 LLM 사용 여부와 반출 가능 범위를 정책으로 통제한다.
- Agent별 파일 접근범위를 작업 디렉터리로 제한한다.
- 임의 Shell 실행과 네트워크 접근은 Allowlist로 통제한다.
- 모든 파일 읽기·변경·명령·승인 행위를 감사로그로 기록한다.
- 감사로그는 Agent가 수정하거나 삭제할 수 없어야 한다.
- 생성 결과에 적용된 모델명·버전·프롬프트·규칙 버전을 기록한다.
- 보안 Gate 실패 시 결과를 OUT 디렉터리로 승격하지 않는다.

### 3.23 변경·호환성·폐기 관리


#### 호환성 기준

- OM Catalog 변경은 배포 버전과 함께 관리한다.
- 생성기 버전 변경 시 회귀 테스트를 수행한다.

#### 폐기 기준

- 사용 중인 화면·ServiceId·프로그램·SQL이 없는지 확인한다.
- 운영로그의 최근 사용 이력을 확인한다.
- 폐기 예정·사용중지·삭제 상태를 구분한다.
- Rollback 기간이 지난 후 최종 삭제한다.

```text
입력 문서를 코드로 바꾸는 생성기          ×
```

이 선도 거래가 반복적으로 성공한 이후 등록·변경·삭제, 신규 업무 WAR, 외부 연계와 배치 영역으로 확장한다.
