# 농협 상호금융 NSIGHT Architecture Rules

---

# 1. 도입 전 안내말

본 문서는 농협 상호금융 NSIGHT 정보계에서 아키텍처를 설계·개발·검증·운영할 때
모든 Architecture Agent, Framework 개발자, 업무 개발자, 데이터 담당자,
보안 담당자, 인프라 담당자, 운영 담당자가 공통으로 따라야 하는
**최상위 아키텍처 규칙**을 정의한다.

`AGENTS.md`가 다음을 정의한다면,

```text
누가
→ 어떤 순서로
→ 어떤 Evidence를 확인하고
→ 어떤 Gate를 거쳐
→ 어떤 산출물을 만드는가
```

본 `03.ARCHITECTURE-RULES.md`는 다음을 정의한다.

```text
NSIGHT에서
무엇을 반드시 지켜야 하는가
→ 무엇을 허용하는가
→ 무엇을 금지하는가
→ 무엇을 자동검증할 것인가
→ 예외는 어떻게 승인할 것인가
```

이 문서의 목적은 “좋은 설계 권고안”을 제시하는 것이 아니다.

다음 항목을 코드·설정·DB·배포·운영까지 일관되게 강제하는 것이다.

```text
Architecture Principle
→ Design Rule
→ Implementation Rule
→ Configuration Rule
→ Deployment Rule
→ Runtime Rule
→ Operations Rule
→ Validation Rule
```

# 2. 문서 개요

## 2.1 목적

본 규칙의 목적은 다음과 같다.

| 목적 | 설명 |
|---|---|
| 아키텍처 일관성 | 업무·플랫폼·데이터·보안·운영 구조를 동일한 원칙으로 통제 |
| 구현 정합성 | 설계서와 실제 Source·Configuration·Runtime 간 Drift 최소화 |
| 책임 분리 | TCF, 업무 WAR, Gateway, JWT, OM, DB, 외부연계의 책임 경계 명확화 |
| 추적성 확보 | 요구사항에서 화면·ServiceId·프로그램·SQL·운영로그까지 연결 |
| 장애 격리 | Transaction, Timeout, Thread, DB Pool, 외부연계 장애전파 통제 |
| 보안 강화 | 인증·인가·키·개인정보·감사 규칙 일관 적용 |
| 자동검증 | 사람이 반복 검토해야 하는 규칙을 CI/CD Gate로 전환 |
| 변경 통제 | Architecture Decision, Exception, Deprecation을 공식 관리 |

```text
R01 Evidence First

R06 Dependency Direction
R07 Transaction Boundary Explicit

R10 Failure as First-Class Design
R11 Traceability End-to-End
R12 Configuration as Architecture
R13 Runtime Evidence Required
R14 Automation Before Manual Inspection
R15 Exception Must Expire
R16 As-Built Before Closure
```

# 4. 사실판단 규칙

## RULE-001. 근거 없는 아키텍처 단정 금지

모든 중요한 판단은 다음 중 하나로 분류한다.

```text
FACT
DOCUMENTED
INFERRED
PROPOSED
DECIDED
DEPRECATED
UNKNOWN
```

금지:

```text
문서에 있으므로 현재 운영 중이다.
소스에 있으므로 호출되고 있다.
설계안이므로 이미 적용되었다.
```

---

## RULE-002. 근거 우선순위

정보가 충돌할 경우 기본 우선순위는 다음과 같다.

```text
Runtime Evidence
→ 배포 Configuration
→ 현재 Source
→ DB Actual Schema
→ Test Evidence
→ 공식 Baseline 문서
→ 과거 문서
→ 회의자료
→ 추론
```

단, Source에 구현되었다는 사실과 해당 구현이 올바른 아키텍처라는 판단은 분리한다.

# 5. 전체 시스템 아키텍처 규칙

## RULE-010. 논리·물리·배포·런타임 구조를 분리한다

하나의 구성도로 모든 것을 설명하지 않는다.

반드시 다음 View를 구분한다.

```text
Context View
Logical View
Application View
Integration View
Data View
Security View
Deployment View
Runtime View
Operations View
```

---

## RULE-011. 업무 WAR는 업무 경계다

업무 WAR는 단순 배포파일이 아니다.

다음을 함께 표현하는 경계로 본다.

```text
업무코드
+ 실행모듈
+ Package
+ ServiceId
+ Data Access
+ Configuration
+ Log
+ DB Pool
+ 운영책임
```

# 6. NSIGHT TCF 실행 구조 규칙

## RULE-020. 온라인 거래는 공통 진입점과 TCF를 통과한다

기준 흐름은 다음과 같다.

```text
Client
↓
Apache / Gateway
↓
Business WAR
↓
Filter
↓
OnlineTransactionController
↓
TCF
↓
STF
↓
TimeoutExecutor
↓
TransactionDispatcher
↓
TransactionHandler
↓
Facade
↓
Service
├─ Rule
├─ DAO
└─ Client
↓
Mapper
↓
DB
↓
ETF
↓
Standard Response
```

실제 Branch에서 구조가 다르면 먼저 As-Is를 기록하고 Gap을 판정한다.

---

## RULE-021. 업무별 Controller를 임의 생성하지 않는다

TCF ON 표준 거래는 공통 Controller + ServiceId Dispatcher를 기준으로 한다.

금지 예:

```text
CustomerController
→ CustomerService
→ CustomerMapper
```

권장:

```text
OnlineTransactionController
→ TCF
→ Dispatcher
→ CustomerHandler
→ Facade
→ Service
```

단, TCF OFF 호환 Controller 등 공식 예외 구조는 별도 ADR 또는 기준문서에 따라 관리한다.

---

## RULE-022. STF 실패 시 업무 실행 금지

다음 검증이 실패한 경우 Handler 이하를 실행하지 않는다.

예:

```text
Header Validation
Authentication Context
Authorization
Transaction Control
Timeout Policy
Duplicate Request
Mandatory Metadata
```

---

## RULE-023. ETF는 거래 종료 표준화를 담당한다

ETF 또는 동등 공통 종료처리는 다음을 일관되게 처리해야 한다.

```text
정상
업무 오류
시스템 오류
Timeout
거래로그 종료
오류 표준화
Trace 정보
```

# 7. ServiceId 규칙

## RULE-030. ServiceId는 거래의 핵심 실행 식별자다

다음 연결의 기준키로 사용한다.

```text
화면 이벤트
→ ServiceId
→ Handler
→ 거래통제
→ Timeout
→ 거래로그
→ OM Catalog
→ 테스트
→ 운영 추적
```

---

## RULE-031. ServiceId는 중복될 수 없다

모든 업무 WAR 전체에서 ServiceId 중복을 금지한다.

자동검증 대상:

```text
ServiceId Format
ServiceId Duplicate
Handler Registration
Handler Dispatch Branch
OM Catalog Registration
```

---

## RULE-032. Handler 등록값과 실제 분기값은 일치해야 한다

기본 검증 관계:

```text
Controller / Request가 결정한 ServiceId
=
Handler.serviceIds() 등록값
=
Handler.handle() 분기값
```

Facade / Service / DTO 이름의 동일성은 개발 표준일 수 있으나
Dispatcher 런타임 조건과 구분해서 검증한다.

# 8. 패키지 구조 규칙

## RULE-040. BASE Package는 프로젝트 기준에 따라 고정한다

NSIGHT 표준 패키지 체계는 Baseline 문서에 정의된 값을 기준으로 한다.

개념 구조:

```text
기관 / 시스템
→ 플랫폼 또는 업무영역
→ 업무코드
→ 도메인
→ 계층
```

업무 코드는 가능하면 다음 축을 유지한다.

```text
업무코드
→ 도메인
→ 책임 계층
```

---

## RULE-041. 패키지는 책임 경계를 표현해야 한다

기술명만으로 모든 코드를 전역 분류하지 않는다.

금지 방향:

```text
common.service
common.dao
common.mapper
util.business
misc
temp
```

공통 모듈은 실제 공통 책임이 있을 때만 사용한다.

---

## RULE-042. 패키지 의존방향은 단방향이어야 한다

기본 방향:

```text
Entry
↓
Application
↓
Domain / Rule
↓
Persistence / Integration
```

역방향 참조를 금지한다.

예:

```text
Mapper → Service       금지
DAO → Handler          금지
Rule → Controller      금지
Service → UI           금지
```

# 9. 업무 계층 책임 규칙

## RULE-050. Handler 책임

허용:

- ServiceId 분기
- 입력 변환
- Facade 호출
- 최소한의 거래 진입 조정

금지:

- 직접 SQL
- Mapper 직접 호출
- 복잡한 업무 규칙
- 다른 업무 DB 직접 접근
- 외부 시스템 직접 호출

---

## RULE-051. Facade 책임

허용:

- Use Case 조립
- 여러 Service 조정
- 도메인 호출 순서 제어
- Transaction 정책 참여
- 업무 Orchestration

금지:

- Mapper 직접 호출
- SQL 작성
- HTTP 기술처리

---

## RULE-052. Service 책임

허용:

- 업무 처리
- Rule 호출
- DAO 호출
- Client 호출
- 업무 상태 변경

금지:

- Controller 책임 수행
- HTTP Request 직접 참조
- 다른 도메인의 Mapper 직접 사용
- UI 상태 의존

---

## RULE-053. Rule 책임

Rule은 가능한 한 부작용 없는 업무 판단으로 유지한다.

허용:

```text
Validation
Calculation
Eligibility
Policy Decision
Business Condition
```

금지:

```text
DB 직접 접근
HTTP 호출
Message 발행
파일 쓰기
Thread 생성
```

예외는 별도 설계 근거가 필요하다.

---

## RULE-054. DAO / Mapper 책임

```text
DAO
= 데이터 접근 추상화

Mapper
= SQL 실행
```

금지:

```text
DAO에 복잡한 업무 정책
Mapper XML에 업무 흐름 제어
SQL 결과에 따라 외부 호출
```

# 11. Transaction 규칙

## RULE-070. Transaction 실제 시작점을 코드로 확인한다

`@Transactional` 위치만 보고 Transaction 경계를 판단하지 않는다.

반드시 확인:

```text
TransactionTemplate
PlatformTransactionManager
@Transactional
Propagation
Worker Thread
Exception
Commit
Rollback
```

---

## RULE-071. Timeout ON 구조에서 최외곽 Transaction을 별도 확인한다

Worker Thread + `TransactionTemplate` 구조에서는
Handler·Facade·Service가 이미 외곽 Transaction에 포함될 수 있다.

따라서 다음 표현을 자동으로 가정하지 않는다.

```text
Facade @Transactional
= 항상 TX BEGIN 위치
```

---

## RULE-072. Transaction 범위 내 장시간 외부 호출을 최소화한다

다음 구조는 주의한다.

```text
TX BEGIN
→ DB 변경
→ 외부 시스템 장시간 호출
→ DB 변경
→ COMMIT
```

필요 시 다음을 검토한다.

```text
Transaction 분리
Outbox
Saga
보상처리
Idempotency
비동기화
```

---

```text
ServiceContext
```

## RULE-091. ThreadLocal은 반드시 정리한다

# 14. 인증·JWT 규칙

## RULE-100. JWT 발급과 검증 책임을 분리한다

기본 책임:

```text
Token Issuer
→ JWT 발급·서명

Gateway 또는 업무 WAR Filter
→ JWT 서명·만료·issuer·audience 검증

STF / Application
→ 인증문맥 정합성·권한·거래권한
```

---

## RULE-101. Private Key는 클라이언트에 존재하면 안 된다

금지:

```text
Browser
WebTop UI
React Source
WAR Resource
application.yml
Git Repository
Plain DB Column
Shell Script
Log
```

권장:

```text
KMS
HSM
Vault / Secret Management
보안 승인 Key Store
```

---

## RULE-102. Public Key 검증은 서버에서 수행한다

브라우저의 JWT 검증 결과를 신뢰하지 않는다.

```text
Client Validation
= UI 편의

Server Validation
= 보안 판단
```

---

## RULE-103. JWT Claim과 요청 Header 충돌 시 검증된 인증정보를 우선한다

예:

```text
JWT userId
vs
Client Header userId
```

서버는 검증된 Token Claim 또는 신뢰 경계에서 생성한 AuthenticationContext를 기준으로 한다.

---

## RULE-104. Gateway 우회경로를 설계에서 제거하거나 방어한다

Gateway가 필수 구조라면 네트워크 레벨에서 직접 WAR 접근을 차단한다.

Gateway가 없거나 우회 가능하다면 업무 WAR에서 공통 JWT Filter를 적용한다.

# 39. 체크리스트

## Architecture

- [ ] As-Is와 Target이 구분되어 있는가
- [ ] 논리·물리·배포·런타임 View가 분리되어 있는가
- [ ] 주요 판단은 ADR로 기록되었는가
- [ ] Gap과 Exception이 관리되고 있는가

## TCF

- [ ] 모든 표준 온라인 거래가 TCF 흐름을 따르는가
- [ ] STF 실패 시 Handler가 실행되지 않는가
- [ ] Timeout 및 Transaction 경계가 확인되었는가
- [ ] Worker Thread Context 전파·정리가 검증되었는가

## Application

- [ ] Handler·Facade·Service·Rule·DAO·Mapper 책임이 분리되어 있는가
- [ ] 금지 의존성이 없는가
- [ ] 업무 간 직접 Mapper 접근이 없는가

## ServiceId

- [ ] 중복이 없는가
- [ ] Handler 등록값과 분기값이 일치하는가
- [ ] OM Catalog와 일치하는가
- [ ] 거래통제·Timeout·로그와 연결되는가

## Data

- [ ] 데이터 소유 도메인이 정의되어 있는가
- [ ] 다른 도메인 데이터 변경이 통제되는가
- [ ] SQL·Mapper·Table 역추적이 가능한가

## Security

- [ ] JWT 발급·검증 책임이 분리되어 있는가
- [ ] Private Key가 안전하게 관리되는가
- [ ] Gateway 우회 방어가 있는가
- [ ] 권한을 서버에서 검증하는가
- [ ] 민감정보가 로그에 노출되지 않는가

## Capacity

- [ ] TPS 근거가 있는가
- [ ] Thread 근거가 있는가
- [ ] JVM 산정 근거가 있는가
- [ ] WAR별 DB Pool 합계가 DB Session 한도를 넘지 않는가
- [ ] DR 상황을 반영했는가

## Operations

- [ ] ServiceId 기준 장애 추적이 가능한가
- [ ] Thread/JVM/Pool/SQL 연계 진단이 가능한가
- [ ] 주요 장애 Runbook이 있는가
- [ ] Audit Trail이 있는가

## Validation

# 40. 시사점

## 40.1 핵심 아키텍처 판단

NSIGHT Architecture의 핵심은 특정 Framework 기술 하나가 아니다.

다음 연결이 끊기지 않는 것이 핵심이다.

```text
업무 요구사항
→ 거래 식별
→ TCF 공통 통제
→ 업무 책임 분리
→ 데이터 소유권
→ 보안
→ 운영 통제
→ 자동검증
→ Runtime Evidence
```

---

## 40.2 주요 위험

가장 큰 위험은 다음과 같다.

```text
설계는 존재하지만 Source가 다름

Source는 맞지만 Configuration이 다름

Configuration은 맞지만 운영에서 사용되지 않음

업무별 예외 구현이 표준처럼 확산됨

문서와 실제 Runtime 사이의 Drift가 누적됨
```

---

## 40.3 우선 보완 과제

P0 우선순위로 다음을 점검한다.

```text
1. Transaction 실제 경계
2. Timeout 실제 동작
3. JWT / SSO 책임
4. Gateway / 직접 WAR 접근
5. ServiceId 원장
6. Package 및 계층 의존
7. 업무 간 데이터 접근
8. 개인정보 마스킹 / 암호화
9. DB Pool / Thread / JVM
10. 거래로그 / 감사로그 / 장애추적
```

---

## 40.4 중장기 발전 방향

NSIGHT Architecture Rules는 장기적으로 다음 구조로 발전시킨다.

```text
Architecture Rules
↓
Machine Readable Rules
↓
Architecture Test
↓
CI/CD Quality Gate
↓
Runtime Compliance
↓
Architecture Drift Detection
```

최종 목표는 아키텍처 문서를 사람이 기억하는 방식이 아니라,
코드·설정·배포·운영에서 지속적으로 검증되는 구조다.

---

# 41. 마무리말

본 규칙은 개발자를 제약하기 위한 규칙집이 아니다.

NSIGHT처럼 여러 업무 WAR, 공통 TCF, 데이터 플랫폼,
보안·운영·외부연계가 결합된 대형 정보계에서는
작은 구현 차이가 프로젝트 후반의 큰 구조적 비용으로 확대될 수 있다.

따라서 다음 원칙을 프로젝트 전체에 적용한다.

```text
Evidence before Opinion

As-Is before To-Be

ServiceId before Program Guess

Common Control before Business Logic

Ownership before Direct Access

Transaction before Annotation

Timeout before Assumption

Security before Convenience

Failure before Production

Traceability before Completion

Automation before Repetitive Review

As-Built before Closure
```

NSIGHT Architecture Rules의 최종 성공기준은
규칙 문서가 존재하는 것이 아니다.

다음 상태가 되어야 한다.

```text
규칙이 설계에 반영되고,
설계가 코드에 반영되고,
코드가 설정과 배포에 반영되고,
실제 Runtime이 이를 증명하며,
위반을 자동으로 탐지할 수 있는 상태
```

이 상태를 NSIGHT Architecture Baseline의 완료 기준으로 사용한다.
