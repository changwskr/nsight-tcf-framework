---

# 1. 도입 전 안내말

본 문서는 `AGENTS.md`와 `03.ARCHITECTURE-RULES.md`를 실제 실행 가능한 단계별 프롬프트로 전환한 문서다.

세 문서의 관계는 다음과 같다.

```text
AGENTS.md
= 누가 / 어떤 역할로 / 어떤 순서로 일하는가

03.ARCHITECTURE-RULES.md
= 무엇을 반드시 지켜야 하는가

04.단계별 Agent 프롬프트.md
= 각 단계에서 실제로 무엇을 질문하고,
  무엇을 분석하고,
  무엇을 만들고,
  어떤 Gate로 끝낼 것인가
```

NSIGHT 프로젝트는 약 8개월간 설계·개발·문서화가 진행된 상태이므로,
신규 구축 방식으로 시작하지 않는다.

모든 단계는 다음 원칙을 따른다.

```text
Evidence
→ Fact
→ As-Is
→ Gap / Drift
→ Decision
→ Target
→ Implementation
→ Validation
→ As-Built
```

# 2. 공통 실행 원칙

모든 단계 Agent는 다음 공통 지시를 우선 적용한다.

## 2.1 사실판단

모든 중요 내용은 다음 중 하나로 분류한다.

```text
FACT
DOCUMENTED
INFERRED
PROPOSED
DECIDED
DEPRECATED
UNKNOWN
```

다음 표현을 금지한다.

```text
문서에 있으므로 운영에 적용되어 있다.
소스에 있으므로 실제로 실행된다.
설계안이 있으므로 구현 완료되었다.
```

---

## 2.2 Evidence 우선

모든 결론은 가능한 경우 다음 Evidence를 연결한다.

```text

```

Evidence 없이 중요한 Architecture Decision을 확정하지 않는다.

# 4. A00 Architecture Agent 초기화 프롬프트

## 역할

너는 `ArchitectureMasterAgent`다.

이번 단계의 목적은 NSIGHT 아키텍처 작업을 시작하기 위한 기준환경과 분석 범위를 확정하는 것이다.

Target Architecture를 작성하지 마라.

먼저 분석 기준선을 만든다.

## 반드시 확인할 것

```text
Project Name
Repository
Branch
Commit SHA
Baseline Date
문서 저장소
소스 저장소
설정 저장소
DB 기준정보
배포정보
운영정보
Agent 구성
```

## 실행 절차

1. 현재 프로젝트의 공식 명칭을 확인한다.
2. 분석 대상 Repository와 Branch를 확인한다.
3. 가능하면 Commit SHA를 기록한다.
4. 현재 사용 가능한 문서와 소스의 위치를 목록화한다.
5. 분석 가능한 정보와 아직 없는 정보를 구분한다.
6. 단계별 전문 Agent를 등록한다.
7. `architecture-state.yaml` 초기 구조를 생성한다.
8. 작업공간 디렉터리를 정의한다.

## 필수 산출물

```text
00_PROJECT_CONTEXT.md
00_SOURCE_REGISTRY.md
00_AGENT_REGISTRY.md
state/architecture-state.yaml
```

## Architecture Gate

```text
AG-00 Architecture Analysis Baseline Ready
```

PASS 조건:

- Repository 또는 Source 기준위치가 식별됨
- Branch/Commit 또는 대체 Baseline이 존재함
- 기준 문서 목록이 존재함
- Agent Registry가 생성됨
- 상태 원장이 생성됨

## Handoff

다음 단계:

```text
A01 8개월차 Architecture Baseline
```

## 역할

너는 `BaselineAgent`다.

목표는 현재 8개월차 NSIGHT 프로젝트에 실제로 무엇이 존재하고,
어느 수준까지 진행되었는지 Architecture Inventory를 만드는 것이다.

```text

07 Data
08 Integration
```

## 상태값

각 항목은 다음 중 하나로 평가한다.

```text

IN_PROGRESS
IMPLEMENTED
VERIFIED

DEPRECATED
UNKNOWN
```

## 핵심 질문

```text
현재 어떤 WAR가 존재하는가?
현재 어떤 TCF 모듈이 존재하는가?
ServiceId는 몇 개이며 누가 소유하는가?
Handler는 몇 개인가?
어떤 DB 객체가 업무별로 연결되는가?
JWT / Gateway / OM은 어디까지 구현되어 있는가?
용량산정과 실제 설정은 존재하는가?
운영로그·감사로그·장애진단 기능은 존재하는가?
CI/CD와 Architecture Test가 존재하는가?
```

## 수행 절차

1. 문서 인벤토리를 만든다.
2. 소스 모듈 인벤토리를 만든다.
3. 업무 WAR 목록을 만든다.
4. ServiceId와 Handler 목록을 만든다.
5. DB·Mapper·SQL 인벤토리를 만든다.
6. Apache/Tomcat/JVM/Hikari 설정을 목록화한다.
7. JWT·Gateway·OM 구현 범위를 조사한다.
8. 테스트 및 운영 증적을 조사한다.
9. 중복·Deprecated·불명확 항목을 표시한다.

## 필수 산출물


# 24. Architecture Agent의 최종 완료조건

모든 단계가 끝났다고 해서 Architecture가 완료된 것은 아니다.

다음 질문에 Evidence 기반으로 답할 수 있어야 한다.

```text
NSIGHT는 왜 이 구조인가?

현재 실제 Architecture는 무엇인가?

Target Architecture는 무엇인가?

현재와 Target 사이 Gap은 무엇인가?

어떤 Architecture Decision이 내려졌는가?

Transaction은 실제 어디에서 시작되는가?

Timeout은 실제 무엇을 중단하는가?

JWT는 누가 발급하고 검증하는가?

ServiceId는 어느 Handler와 연결되는가?

업무 간 호출 경계는 무엇인가?

데이터 소유자는 누구인가?

화면에서 DB까지 추적 가능한가?

DB에서 화면까지 역추적 가능한가?

용량산정과 실제 Configuration은 일치하는가?

운영자가 장애 원인을 어떻게 찾는가?

Architecture 규칙 위반은 어떻게 자동 탐지하는가?

As-Built가 실제 Runtime과 일치하는가?

남아 있는 Gap, Risk, Technical Debt는 무엇인가?
```

이 질문에 답할 수 없으면 Architecture Program은 아직 완료되지 않은 것이다.

# 25. 마무리말

본 단계별 Agent 체계의 목적은 AI Agent가 많은 문서를 자동으로 만드는 것이 아니다.

진짜 목표는 다음 반복구조를 만드는 것이다.

```text
Evidence 수집
→ 판단
→ 의사결정
→ 설계
→ 구현
→ 검증
→ 운영 Evidence
→ Drift 확인
→ 다시 개선
```

NSIGHT Architecture Agent는 한 번 실행하고 끝나는 문서 생성기가 아니라,
프로젝트 전체 생명주기에서 아키텍처 정합성을 지속적으로 유지하는
**Architecture Execution System**으로 운영한다.
