## 들어가며 — 왜 “조회 한 건”이 표준 샘플인가

NSIGHT TCF에서 가장 먼저 손에 익혀야 할 거래 유형은 **단건 조회(INQ)** 이다. 등록·변경보다 트랜잭션·멱등·보상 이슈가 적고, 그래도 Header 검증·ServiceId 라우팅·6계층·OM 등록·거래로그까지 **온라인 거래의 뼈대**는 모두 지나간다.

이 장이 다루는 `SV.Customer.selectSummary` / `SV-INQ-0001` 은 매뉴얼과 가이드에서 반복해서 가리키는 **복제용 기준 구현**이다. 목표는 “예제 JSON 하나 돌려보기”가 아니다. **요청이 어떤 클래스를 어떤 순서로 스치고, 어디서 검증·SQL·응답 조립이 일어나는지**를 머릿속에 그리는 것이다.

읽는 순서 제안:

1. §22.1 에서 거래 정체성(ServiceId·포트·원칙)을 고정한다.
2. §22.2 에서 **실제 `sv-service` 코드**를 계층별로 산책한다.
3. §22.3 에서 기동·호출·로그·테스트로 “됐는지”를 확인한다.
4. 장 요약의 체크리스트로 동료에게 설명해 본다.

> **설계서 ↔ 코드 Gap을 미리 말해 둔다.**  
> 일부 매뉴얼 흐름도는 Handler 이름을 `SvCustomerSummaryHandler` 로 적는다.  
> **현재 코드**는 도메인 Handler `SvCustomerHandler` 가 `serviceIds()` 로 `SV.Customer.selectSummary` 를 등록한다 (`zman/00-설계서-코드베이스-대조표.md` 의 Handler 단위 Gap과 동일).  
> 이 장은 **코드 SoT** 를 따른다.

## 22.1 요건·ServiceId·거래코드 — 거래의 신분증

### 22.1.1 한 줄 정의

**SV 고객요약조회**는 Single View 업무 WAR(`sv-service`)가 고객번호로 요약 카드를 읽어 표준 응답 `body`에 실어 주는 **조회 거래**이다.

### 22.1.2 거래 신분증 (고정값)

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 업무코드 | `SV` | Context·WAR·명명의 축 |
| 모듈 | `sv-service` | Gradle `:sv-service` |
| 로컬 포트 | `8086` | bootRun |
| Context | `/sv` | Endpoint = `/sv/online` |
| HTTP | `POST` only | GET 조회 URL 금지 (표준 전문) |
| ServiceId | `SV.Customer.selectSummary` | Dispatcher 키 |
| 거래코드 | `SV-INQ-0001` | Header · 통제 · 통계 |
| 처리유형 | 조회 (INQ) | Facade `readOnly` |
| DB 역할 | RDW (로컬은 H2 테이블 `SV_CUSTOMER`) | Mapper 주석 참고 |
| Timeout | 3초 | Facade `@Transactional(timeout=3)` · SQL `timeout="3"` |
| 감사 | Y (정책) | OM·ETF 설정과 함께 |
| 배포 | `sv.war` | ztomcat 시 `/sv` |

이 표의 값은 “문서에만 있는 약속”이 아니다. ServiceId 문자열은 Handler 상수와 **문자 단위로 같아야** 하고, 포트·Context는 `application` 설정·`zarchitecture/16` 과 맞아야 한다. 하나라도 어긋나면 “코드는 있는데 404 / Handler not found / 거래통제 차단”으로 나타난다.

### 22.1.3 왜 Controller를 만들지 않는가

일반 Spring 습관은 `@RestController` + `@PostMapping("/customers/summary")` 이다. TCF는 그 습관을 의도적으로 끊는다.

- URL은 **업무 Context 진입점**일 뿐이고 (`POST /sv/online`)
- **무엇을 실행할지**는 Header `serviceId` 가 정한다
- 공통 STF/ETF(검증·GUID·로그·표준 오류)를 우회하는 개인 Controller는 Gateway·OM·감사에서 **유령 거래**가 된다

따라서 업무 개발자의 첫 산출물은 Controller가 아니라 **Handler + 아래 5계층**이다. 이 원칙은 [제1장](../제01편/01-NSIGHT-TCF란-무엇인가.md)·[제4장](../제01편/04-애플리케이션-6계층.md)과 같은 이야기이지만, 이 장에서는 **손가락으로 집을 수 있는 클래스**로 증명한다.

### 22.1.4 OM에 먼저 올려야 하는 것들

코드를 밀기 전에(또는 최소한 통합 환경 전에) OM 쪽에 다음이 있어야 한다. 로컬에서 `jwt`·거래통제를 느슨히 켠 채로 “일단 된다”고 넘어가면, 통합에서 한꺼번에 막힌다.

| OM / 통제 | 내용 |
| --- | --- |
| Service Catalog | `SV.Customer.selectSummary` · Handler 매핑 |
| 거래코드 | `SV-INQ-0001` |
| 거래통제 Allow | `businessCode=SV` 등 Header 정책 |
| Timeout Policy | 3초 |
| 오류코드 | `E-SV-VAL-0001`, `E-SV-VAL-0002`, `E-SV-BIZ-0001` 등 Rule이 던지는 코드 |

등록 절차의 상세는 [제47 절 매뉴얼](../../znsight-man/47-ServiceId-등록-절차.md)을 따른다. **코드만 있고 Catalog가 없으면** “개발 PC에선 성공, 통합에선 차단”이 전형적인 증상이다.

### 22.1.5 이 장이 지키는 여섯 원칙 (실무 언어)

1. **진입은 tcf-web** — `OnlineTransactionController` 를 업무가 재구현하지 않는다.
2. **Handler는 도메인 단위** — `SvCustomerHandler` 하나가 `SV.Customer.*` 를 받는다.
3. **트랜잭션 경계는 Facade** — 조회도 `@Transactional(readOnly=true)`.
4. **검증·판단은 Rule** — 필수값·길이·“없음” 판정.
5. **SQL은 Mapper/DAO만** — Service에 문자열 SQL 금지.
6. **표준 응답 껍질은 ETF** — Handler/Facade는 업무 `body` 맵(또는 DTO)에 집중.

## 22.2 Handler~Mapper 구현 — 코드로 걷는 한 건의 조회

### 22.2.1 한 건이 지나가는 길

```text
Client (tcf-ui / curl / WebTop)
   │  POST http://localhost:8086/sv/online
   │  Content-Type: application/json
   │  StandardRequest { header, body }
   ▼
tcf-web  OnlineTransactionController
   ▼
tcf-core TCF.process()
   ├─ STF   Header·GUID·세션·권한·통제·Timeout·PROCESSING 로그
   ├─ Dispatcher  serviceId → SvCustomerHandler
   ▼
SvCustomerHandler.doHandle
   ▼
SvCustomerFacade.selectCustomerSummary   @Transactional(readOnly, timeout=3)
   ▼
SvCustomerService.selectCustomerSummary
   ├─ SvCustomerRule.buildSummaryCriteria
   ├─ SvCustomerDao.selectCustomerSummary
   │     └─ SvCustomerMapper.xml selectCustomerSummary
   └─ SvCustomerRule.validateSummaryResult
   ▼
CustomerSummaryResponse.toMap()  →  (ETF가 StandardResponse로 포장)
```

매뉴얼의 “SummaryHandler” 그림과 달리, **화살표의 끝은 `SvCustomerHandler`** 이다. 이름을 외우기보다 `sv-service/.../entry/handler` 패키지를 IDE에서 열어 확인하는 편이 안전하다.

### 22.2.2 패키지 지도 (실경로)

| 계층 | 클래스 | 경로 |
| --- | --- | --- |
| Handler | `SvCustomerHandler` | `sv-service/src/main/java/com/nh/nsight/marketing/sv/entry/handler/` |
| Facade | `SvCustomerFacade` | `.../entry/facade/` |
| Service | `SvCustomerService` | `.../application/service/` |
| Rule | `SvCustomerRule` | `.../application/rule/` |
| Request/Response DTO | `CustomerSummaryRequest` 등 | `.../application/dto/customer/` |
| DAO | `SvCustomerDao` | `.../persistence/dao/` |
| Mapper | `SvCustomerMapper` + XML | `.../persistence/mapper/` · `resources/mapper/sv/SvCustomerMapper.xml` |

신규 조회를 만들 때는 이 표를 **복제 체크리스트**로 쓰면 된다. 같은 도메인이면 Handler에 `serviceIds()` case만 추가하고, 새 도메인이면 Handler 클래스를 하나 더 만든다.

### 22.2.3 Handler — 라우팅만, 업무는 Facade로

```java
// sv-service/.../entry/handler/SvCustomerHandler.java
@Component
public class SvCustomerHandler implements TransactionHandler {

    private static final String SELECT_SUMMARY = "SV.Customer.selectSummary";
    private final SvCustomerFacade facade;

    @Override
    public Collection<String> serviceIds() {
        return List.of(SELECT_SUMMARY);
    }

    @Override
    public Object doHandle(StandardRequest<Map<String, Object>> request, TransactionContext context) {
        String serviceId = context.getHeader().getServiceId();
        return switch (serviceId) {
            case SELECT_SUMMARY -> facade.selectCustomerSummary(request.getBody(), context);
            default -> throw new BusinessException(ErrorCode.SERVICE_NOT_FOUND,
                    "SvCustomerHandler 미지원 serviceId: " + serviceId);
        };
    }
}
```

읽을 포인트:

- `serviceIds()` 반환값이 Dispatcher 등록 키이다. **오타 한 글자**면 다른 Handler로 가거나 not found가 난다.
- `doHandle` 은 Body를 해석하지 않고 `Map` 그대로 Facade에 넘긴다. JSON→DTO 변환 책임은 Facade/Request 쪽에 모여 있다.
- `default` 분기는 “같은 Handler에 새 ServiceId를 등록해 놓고 switch를 안 단” 실수를 런타임에 드러낸다.

### 22.2.4 Facade — 트랜잭션과 타임아웃의 울타리

```java
// sv-service/.../entry/facade/SvCustomerFacade.java
@Transactional(readOnly = true, timeout = 3)
public Map<String, Object> selectCustomerSummary(Map<String, Object> body, TransactionContext context) {
    CustomerSummaryRequest inquiryRequest = CustomerSummaryRequest.fromMap(body);
    return service.selectCustomerSummary(inquiryRequest, context).toMap();
}
```

조회라도 Facade에서 트랜잭션을 연다. 이유:

- 읽기 일관성·커넥션 수명·Timeout을 **한곳**에서 건다
- Service/DAO가 트랜잭션 어노테이션을 난발하지 않게 한다
- `timeout = 3` 은 OM Timeout 정책·SQL `timeout="3"` 과 **같은 숫자**를 말하는 것이 운영에서 읽기 쉽다

`CustomerSummaryRequest.fromMap` 은 `customerNo`, `baseDate` 키를 읽는다. 예제 JSON에 `customerId` 를 쓰면 **필수 검증 실패**로 떨어진다. (구 문서/습관의 대표적인 함정)

### 22.2.5 Service · Rule — 오케스트레이션과 판단

```java
// SvCustomerService.selectCustomerSummary
var criteria = rule.buildSummaryCriteria(request);
CustomerSummaryRow customer = dao.selectCustomerSummary(criteria);
rule.validateSummaryResult(customer);
return CustomerSummaryResponse.of(context, customer);
```

Rule이 하는 일 (`SvCustomerRule`):

| 상황 | 코드 | 메시지 |
| --- | --- | --- |
| 요청 null / 고객번호 공백 | `E-SV-VAL-0001` | 고객번호는 필수입니다. |
| 길이 > 20 | `E-SV-VAL-0002` | 고객번호 길이가 올바르지 않습니다. |
| 조회 결과 없음 | `E-SV-BIZ-0001` | 조회된 고객 정보가 없습니다. |

Service는 “순서만” 지휘한다. **없으면 예외**를 DAO `Optional` 한 줄로 때우지 않고 Rule에 모아 두면, 메시지·코드·테스트가 한곳으로 모인다.

### 22.2.6 DAO · Mapper — 로컬 H2와 운영 RDW를 같은 SQL_ID로

```xml
<!-- sv-service/src/main/resources/mapper/sv/SvCustomerMapper.xml -->
<select id="selectCustomerSummary"
        parameterType="...CustomerSummaryCriteria"
        resultType="...CustomerSummaryRow"
        timeout="3">
    /* SQL_ID: SV.Customer.selectSummary */
    SELECT
          CUSTOMER_NO AS customerNo
        , CUSTOMER_NAME AS customerName
        , CUSTOMER_GRADE AS customerGrade
        , BRANCH_CODE AS branchCode
        , BRANCH_NAME AS branchName
        , TOTAL_BALANCE AS totalBalance
        , LOAN_BALANCE AS loanBalance
        , PRODUCT_COUNT AS productCount
        , LAST_TRANSACTION_DATE AS lastTransactionDate
      FROM SV_CUSTOMER
     WHERE CUSTOMER_NO = #{customerNo}
</select>
```

XML 주석이 말하듯, 운영 RDW에서는 여러 테이블 JOIN이 될 수 있고 로컬은 단일 `SV_CUSTOMER` 로 같은 응답 컬럼을 맞춘다. **로컬에서 컬럼을 맘대로 줄이면** 운영 SQL과 DTO가 어긋난다. 샘플을 복제할 때 “로컬 전용 필드”를 Response에 굳히지 말 것.

바인드 변수는 `#{customerNo}` 만 쓴다. 문자열 접합 SQL은 TCF 보안·리뷰 기준에서 즉시 반려 대상이다.

### 22.2.7 요청·응답 JSON (코드 필드와 일치)

요청 예:

```json
{
  "header": {
    "businessCode": "SV",
    "serviceId": "SV.Customer.selectSummary",
    "transactionCode": "SV-INQ-0001",
    "channelId": "WEBTOP",
    "userId": "dev01",
    "branchId": "001",
    "guid": ""
  },
  "body": {
    "customerNo": "C001",
    "baseDate": "20260805"
  }
}
```

- `guid` 가 비어 있으면 STF가 채번하는 흐름이 일반적이다 (환경·정책에 따라 확인).
- `baseDate` 는 선택이다. 없으면 Rule이 `baseDate=null` criteria를 만든다.
- 응답 `body` 에는 Rule/DTO가 채운 `customerNo`, `customerName`, `customerGrade`, 잔액·상품수·최근거래일 등과 함께, Response가 넣는 `businessCode`·`serviceId`·`guid` 힌트가 포함될 수 있다 (`CustomerSummaryResponse.toMap()`).

민감 항목 마스킹은 ETF·정책 쪽 이야기다. 이 샘플 Response에 비밀번호·주민번호 원문을 넣지 말 것.

### 22.2.8 실수하기 쉬운 점 (증상 → 원인)

| 증상 | 의심 |
| --- | --- |
| 404 `/online` | Context `/sv` 누락 (`:8086/online`) |
| Handler not found | Catalog/등록 ServiceId ≠ `serviceIds()` 문자열 |
| `E-SV-VAL-0001` | body 키를 `customerId` 로 보냄 |
| `E-SV-BIZ-0001` | H2에 `C001` 없음 · 데이터 시드 확인 |
| Timeout | Facade/SQL 3초 · 느린 JOIN · Pool 고갈 |
| 트랜잭션 롤백 이상 | `@Transactional` 을 Service에만 두고 self-invocation |

## 22.3 OM 등록·거래 테스트 — “된다”를 증거로 남기기

### 22.3.1 로컬에서 최소 성공 경로

```bash
# 터미널 1
./gradlew :sv-service:bootRun

# 터미널 2
curl -X POST http://127.0.0.1:8086/sv/online \
  -H "Content-Type: application/json" \
  -d @tcf-ui/src/main/resources/sample-requests/sv-sample-inquiry.json
```

샘플 JSON 파일이 구 필드(`customerId`)를 쓰면 **본장 기준에 맞게 `customerNo` 로 고친 뒤** 호출한다. UI로 보려면 `tcf-ui` 기동 후 `http://localhost:8099/sv/` 계열 페이지를 사용한다 (`zguide/sv-service-개발가이드.md`).

ztomcat 통합:

```text
8080 + Context /sv  →  POST http://localhost:8080/sv/online
Gateway 경유 검증은 tcf-uj → :8100 경로 (제2장·제16장 참고)
```

### 22.3.2 눈으로 볼 증거 목록

| # | 확인 | 기대 |
| --- | --- | --- |
| 1 | HTTP 200 + 표준 응답 | `result` 성공 코드, body에 고객 요약 |
| 2 | 응답 header.guid | 비어 있지 않음 |
| 3 | 거래로그 | PROCESSING → SUCCESS (환경에 따라 TCF_TX_LOG) |
| 4 | 고객번호 누락 | `E-SV-VAL-0001` 계열 표준 오류 |
| 5 | 없는 고객 | `E-SV-BIZ-0001` |
| 6 | 잘못된 serviceId | Dispatcher/통제 실패 (성공 body 없음) |
| 7 | 3초 초과 강제 | Timeout 오류 코드 |

“테스트 통과 스크린샷”보다 **명령 + exit + 응답 JSON 일부**를 MR/일지에 남기는 편이 TCF 팀 리뷰에 잘 맞는다.

### 22.3.3 자동 테스트가 있으면 좋은 것

통합 테스트 스케치(프로젝트에 동일 클래스가 있으면 그걸 우선):

```java
// (예시) MockMvc로 /sv/online 호출
mockMvc.perform(post("/sv/online")
        .contentType(APPLICATION_JSON)
        .content(jsonWithCustomerNo("C001")))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.body.customerNo").value("C001"));
```

단위 테스트는 Rule에 모은 예외 코드를 **테이블 형식**으로 고정해 두면 회귀에 강하다.

### 22.3.4 다음 확장 — 같은 WAR, 다른 거래

- 같은 고객 도메인에 목록 조회를 추가한다면: `SvCustomerHandler.serviceIds()` 에 ID를 추가하고 switch case·Facade 메서드를 늘린다 → [제23장](./23-목록-페이징-등록-변경.md)
- IC WAR를 호출한다면: Java 모듈 의존이 아니라 **tcf-eai** (`SV.Integration.icSample` 샘플 Handler 참고)

## 디버깅 메모 — 막혔을 때 5분 순서

1. URL에 `/sv` 가 있는가
2. Header `serviceId` 문자열이 Handler 상수와 같은가
3. body 키가 `customerNo` 인가
4. H2 `SV_CUSTOMER` 에 데이터가 있는가
5. 로그에 STF 진입·Dispatcher 선택·SQL_ID 가 찍히는가

이 다섯이 통과하면 나머지는 OM·보안·Gateway 이슈로 범위를 좁히면 된다.

---

## 장 요약

- SV 고객요약조회는 TCF **단건 조회의 표준 손맛**을 익히는 장이다.
- 실코드 기준 Handler는 `SvCustomerHandler` 이며 ServiceId는 `SV.Customer.selectSummary` 이다.
- Facade가 `readOnly` 트랜잭션·3초 timeout을 잡고, Rule이 검증·없음 판정·오류코드를 소유한다.
- Mapper는 `SV_CUSTOMER` / RDW JOIN을 같은 응답 형상으로 맞춘다.
- 요청 body는 **`customerNo`** (legacy `customerId` 습관 주의).
- 증거는 curl·로그·오류코드·guid로 남긴다.

복습 질문: *“동료에게 Handler에서 Service까지 호출 순서를 화이트보드에 그릴 수 있는가?”* — 가능하면 이 장은 끝난 것이다.
