# Java 네이밍 및 코딩 표준서 목차

## 문서 정보

- 기준 문서: `Java_네이밍_및_주석_통합_표준서.docx`
- 문서 목적: 프로젝트 전반에 적용할 Java 네이밍, 구현, 주석, 품질관리 표준서의 집필 구조 정의
- 작성 상태: 목차 및 집필 기준 수립
- 적용 표기
  - **[원문]**: 기준 문서에서 직접 확인된 규칙 또는 계약
  - **[결정]**: 기준 문서 안의 충돌이나 프로젝트 선택이 필요한 항목
  - **[보완]**: 일반적인 Java 코딩 표준서로 완성하기 위해 추가할 항목

> 기준 문서는 네이밍, 주석 및 프레임워크 결합 규칙을 상세히 다루지만, 포맷팅·컬렉션·동시성·보안 등 일반 코딩 규칙은 상대적으로 적다. 따라서 본 목차는 원문의 계약을 보존하면서 부족한 코딩 표준 영역을 별도 표기하여 확장한다.

| 영역 | 원문 충실도 | 목차 처리 |
|---|---:|---|
| 식별자·패키지·컴포넌트 네이밍 | 높음 | 원문 중심으로 구성 |
| Service ID·URL·DTO·Mapper | 높음 | 계약과 예외를 상세화 |
| 주석·JavaDoc | 높음 | 기존 규칙을 독립 장으로 구성 |
| 예외·로그·트랜잭션·AOP | 중간 이상 | 프레임워크 결합 규칙을 보존 |
| 소스 포맷·클래스 설계 | 낮음 | 일반 Java 표준으로 보완 |
| Null·컬렉션·Stream·동시성 | 낮음 | 별도 보완 장으로 신설 |
| 보안·테스트·품질 게이트 | 낮음 | 실행 가능한 검증 기준으로 보완 |

## 우선 결정이 필요한 쟁점

1. 업무 클래스 이름을 기존 소문자 시작 형식으로 유지할지 UpperCamelCase로 전환할지
2. `DAO`와 `Dao` 중 표준 접미사
3. `DTOin/DTOout`과 `Request/Response` 중 신규 표준
4. Service ID와 Java 메서드 이름을 1:1로 강제할지 의미 기반 메서드를 허용할지
5. 공통 응답 Envelope 적용 범위
6. Facade 패키지를 `application.facade` 또는 `entry.facade` 중 어디로 통일할지
7. SQL 건수 조회 접미사를 `Count`, `Cnt` 등에서 무엇으로 통일할지
8. 자동 생성 DTO 필드의 대소문자 보존 여부
9. 오류 코드 구조와 중앙 관리 방식
10. Spring Bean 기본 이름과 레거시 Bean 이름의 호환 방식
