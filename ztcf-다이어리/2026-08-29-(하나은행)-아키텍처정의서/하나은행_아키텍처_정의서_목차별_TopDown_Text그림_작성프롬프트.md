# 하나은행 아키텍처 정의서 목차별 작성 프롬프트
## Top-down + Text/ASCII Architecture 중심 버전

> 기준문서: `하나은행_아키텍처_정의서_목차.md`  
> 목적: 하나은행 아키텍처 정의서의 각 목차를 작성할 때 사용할 **복사·실행 가능한 개별 프롬프트**를 제공한다.  
> 핵심 작성방식: **Top-down 설명 + Text/ASCII 그림 우선 + 사실/분석/제안 분리 + 협업/TBD/GAP 명시**

# 0. 사용 방법

각 절을 작성할 때 해당 절의 프롬프트를 그대로 복사한 뒤, 마지막의 `[입력자료]`에 분석할 문서·소스·구성도·표준·요구사항을 붙인다.

모든 프롬프트는 다음 순서를 공통으로 강제한다.

```text
[왜 / 목표]
    ↓
[전체 Context / Boundary]
    ↓
[영역 / 계층 / 시스템 분해]
    ↓
[구성요소 / 책임]
    ↓
[정상 End-to-End 흐름]
    ↓
[세부 메커니즘 / 규칙 / 패턴]
    ↓
[예외 / 장애 / 보안 / 운영]
    ↓
[GAP / TBD / ADR / 검증 체크리스트]
```

## 0.1 공통 작성 원칙

1. **Text 그림 우선**: Mermaid보다 ASCII/Text Diagram을 우선 사용한다.
2. **Top-down**: 반드시 전체 → 영역 → 구성요소 → 상세흐름 → 규칙 순서로 내려간다.
3. **원본 명칭 보존**: 문서/소스/그림에 나온 시스템명, 모듈명, 프로토콜, 업무코드, 화살표 방향을 임의 변경하지 않는다.
4. **사실과 해석 분리**:
   - `[FACT]` 근거자료에서 확인됨
   - `[ANALYSIS]` 확인된 사실에 대한 아키텍처 해석
   - `[TO-BE/PROPOSED]` 제안 또는 목표설계
   - `[GAP]` 기준 대비 미충족/불명확
   - `[TBD/확인필요]` 자료만으로 확정 불가
5. **자료에 없는 값 금지**: 제품 버전, 서버 수량, CPU/Memory, Timeout, 암호알고리즘, 포트, 프로토콜 등을 임의로 채우지 않는다.
6. **협업표시 유지**: `[TA협의필요]`, `[DA협의필요]`, `[프레임워크 협업 필요]`, `[Hydra 협업 필요]`, `[은행보안팀 협업필요]`, `[2사업 협업필요]`를 삭제하지 않고 별도 협의사항으로 정리한다.
7. **운영 가능성까지 설명**: 구성도만 그리지 말고 장애, 로그, 모니터링, 변경, 배포, 복구 관점을 해당 절의 범위에서 점검한다.
8. **Traceability**: 가능하면 `요구사항/정책/기준 → 설계결정 → 구성요소/메커니즘 → 검증방법` 연결표를 작성한다.
9. **텍스트 그림은 충분히 상세하게**: 단순 박스 3~4개로 끝내지 말고, 원본의 영역·박스·연결선·방향·데이터·프로토콜을 최대한 보존한다.
10. **결론 선제시**: 각 절 첫 부분에 5~10줄의 핵심결론을 먼저 제시한다.

## 0.2 모든 절의 기본 산출 구조

```text
1. 핵심 결론
2. 작성 목적과 범위

5. 구성요소 정의표

7. 규칙 / 표준 / 책임 / 제약
8. 예외 / 오류 / 장애 / 보안 / 운영 관점
9. 요구사항·정책 Traceability
10. GAP / TBD / 협의필요 / ADR 후보
11. 검증 체크리스트

```

# 1. 전체 아키텍처 정의서 생성용 마스터 프롬프트

```text
너는 은행권 대형 프로젝트의 Chief Enterprise Architect이자 Application/Data/Technical/Interface/Security/Operation Architect다.

제공된 하나은행 아키텍처 정의서 목차와 프로젝트 자료를 기준으로 전체 아키텍처 정의서를 작성하라.

[최우선 작성방식]
- Top-down으로 작성한다: 사업목표 → Context → 시스템영역 → 업무시스템 → Application → Logical Node → Software/DB → Runtime/Interface/Security/CI-CD.
- 시각적 설명은 이미지보다 Text/ASCII Architecture Diagram을 우선한다.
- 각 장의 첫 그림은 반드시 상위 전체그림이어야 하고, 이후 상세그림으로 Drill-down한다.
- 그림의 화살표에는 방향과 의미를 적고, 근거가 있을 경우 Protocol/Data/Sync-Async를 표시한다.
- 원본 자료의 명칭을 보존한다.
- 자료에 없는 내용을 일반론으로 확정하지 않는다. 불명확하면 [TBD/확인필요]로 둔다.
- FACT / ANALYSIS / TO-BE(PROPOSED) / GAP을 명확히 구분한다.
- TA/DA/Framework/Hydra/Security/2사업 등 협업 필요사항은 별도 표로 관리한다.

[작성 순서]
I. 개요
  1. 시스템 구축 배경 및 목적
  2. 아키텍처 정의 수행 Approach
  3. 아키텍처 정의 범위
  4. 아키텍처 설계 원칙 정의
  5. 시스템 Context 다이어그램
II. 시스템 구성
  1. 시스템 영역 구분
  2. 목표 업무시스템 구성도
  3. 어플리케이션 구성
  4. 논리노드 구성
  5. 목표 IT시스템 구성도
III. 마케팅플랫폼 및 데이터허브 아키텍처
  1. 온라인어플리케이션
  2. 배치어플리케이션
  3. 어플리케이션 표준화 방안
  4. 시스템 간 연계 방안
  5. 고객 행동데이터 수집 및 활용 방안
  6. 컨테이너 실행환경 구축 방안
  7. 데이터 암/복호화 처리 방안
  8. CI/CD 지원 방안
IV. 기타 시스템 아키텍처
  1. BI포탈
  2. BIZ메타
  3. Self BI
  4. 데이터흐름관리
  5. 비표준단말 SSO/EAM 연계 방안

각 절은 반드시 다음으로 끝내라.
- 확정사항
- 협의필요사항
- GAP/TBD
- ADR 후보
- 검증 체크리스트

[입력자료]
여기에 프로젝트 자료를 제공한다.
```

```text
너는 은행권 아키텍처 정의서를 작성하는 Enterprise/Solution Architect다.

[작성 대상]
I. 개요

[작성 목적]
아키텍처 정의서의 출발점으로서 구축 배경, 정의 접근법, 범위, 설계원칙, 시스템 경계를 하나의 논리로 연결한다.

[작성 원칙]
1. 전체 → 영역 → 구성요소 → 상세흐름 → 규칙/예외 순서의 Top-down 구조로 작성하라.
2. 첫 번째 산출은 반드시 상위 Text/ASCII 그림으로 제시하라. Mermaid를 기본값으로 사용하지 마라.
3. 원본 자료에 있는 명칭, 박스, 방향, 데이터명, 프로토콜, 계층명을 가능한 한 그대로 유지하라.
4. 확인된 사실은 [FACT], 해석은 [ANALYSIS], 목표/제안은 [TO-BE/PROPOSED], 미충족은 [GAP], 미확정은 [TBD/확인필요]로 구분하라.
5. 자료에 없는 제품명·수량·스펙·버전·Timeout·포트·알고리즘을 임의 확정하지 마라.
6. 해당 절에서 발견되는 협업/승인 의존성은 별도 '협의 필요사항' 표로 작성하라.

[이 절에서 반드시 다룰 내용]
- 배경/목표 → 아키텍처 정의 Approach → 정의 범위 → 설계원칙 → 시스템 Context의 연결관계

[Text 그림 작성 규칙]

- 시스템/영역 경계는 ┌─┐ 또는 [Boundary]로 분명히 표현한다.
- 호출/데이터 이동 방향은 →, ←, ↔로 표시한다.
- 근거자료가 있으면 화살표 위/옆에 Protocol, Data, Sync/Async, Trigger를 표시한다.

[출력 구조]
1. 핵심 결론
2. 목적 / 범위 / 전제

8. 제약 / 예외 / 장애 / 보안 / 운영 고려사항
9. 요구사항·정책·기준 Traceability
10. 확정사항 / 협의필요 / GAP / TBD / ADR 후보
```

# 5. Text Architecture 작성 품질 기준

## 5.1 좋은 Text 그림의 예

```text
┌──────────────────────────── 사용자 / 채널 ────────────────────────────┐
│ 영업점 단말 | 포탈 | 내부업무 | Batch Trigger                       │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ Request / Event
                                ▼
┌────────────────────────── 정보전달 / 접점 영역 ───────────────────────┐
│ [실제 자료에서 확인된 Gateway / UI Engine / Interface Component]     │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ Standard Contract / Context
                                ▼
┌──────────────────── Application / Service 영역 ──────────────────────┐
│ Service Group A → Application(Lv3) → Business/Domain/Data Access      │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ Query / Command / Event
                                ▼
┌──────────────────────── Data / Integration 영역 ─────────────────────┐
│ Database | CDC/ETCL/BC | External System | Batch/Data Hub             │
└───────────────────────────────────────────────────────────────────────┘
```

좋은 그림은 단순히 박스가 많은 그림이 아니라, **Boundary와 책임, 흐름의 방향, 무엇이 이동하는지, 어느 구간에서 설계규칙이 적용되는지**가 읽혀야 한다.

## 5.2 피해야 할 결과

```text
사용자 → 서버 → DB
```

위와 같이 원본의 아키텍처 정보를 지나치게 축약한 그림은 사용하지 않는다.

또한 다음을 피한다.
- 근거 없는 제품명/버전 삽입
- AS-IS와 TO-BE 혼합
- Logical/Physical View 혼합 후 범례 누락
- 모든 연계를 단순 화살표 하나로 표현
- 표만 나열하고 End-to-End 흐름을 설명하지 않음
- '안정성 확보', '확장성 향상'처럼 근거와 메커니즘이 없는 추상적 표현

# 7. 최종 사용 권장 방식

1. 먼저 **전체 아키텍처 정의서 생성용 마스터 프롬프트**로 전체 골격을 작성한다.
2. 이후 각 목차별 프롬프트로 상세화한다.
3. 상세화 결과에서 확인된 사실을 상위 그림으로 다시 Roll-up한다.
4. 상위/하위 그림의 시스템명·경계·호출방향이 일치하는지 최종 Conformance 점검한다.
5. 협의가 끝나지 않은 항목은 문서에서 숨기지 말고 `[TBD/확인필요]` 상태로 유지한다.

```text
Level 0 : Enterprise / System Context
   ↓
Level 1 : System Area / Business Service
   ↓
Level 2 : Application / Service Group
   ↓
Level 3 : Runtime / Logical Node / Software / DB
   ↓
Level 4 : Request / Transaction / Batch / Data / Security / CI-CD Flow
   ↓
Level 5 : Rule / Exception / Operation / Verification
```

이 계층을 유지하면 아키텍처 정의서가 단순한 구성도 모음이 아니라, **왜 이렇게 설계했는지부터 실제 실행·운영·검증까지 추적 가능한 Top-down 설계서**가 된다.
