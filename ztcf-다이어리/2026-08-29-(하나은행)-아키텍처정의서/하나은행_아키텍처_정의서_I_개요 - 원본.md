# I. 개요 — 장 연결

## 1. 핵심 결론

이 장은 아키텍처 정의서의 출발점이다. **왜 구축하는가(I.1) → 어떤 TASK 순서로 정의하는가(I.2) → 어디까지가 정의 범위인가(I.3) → 무엇으로 의사결정하는가(I.4) → 시스템의 경계와 상대는 누구인가(I.5)** 를 한 논리로 고정한다.

`[FACT]` 대상 시스템은 『프로젝트ONE』 1단계 **마케팅플랫폼 및 데이터허브**이며, 전행 5개 도메인 중 **고객, 경영 관리 및 지원, 공통정보 및 인프라**와 관련되고 **전사 정보계 어플리케이션**에 해당한다.

`[FACT]` 목차가 이 장에서 확정하라고 한 것은 Approach 3단계, 2사업 제약 포함 범위, 설계원칙(선정근거 포함), Context(Boundary·연계데이터·사용자 역할)이다.

`[GAP]` I.1의 「기 작성내용」과 2사업 R&R 원문이 없어, 사업 KPI·2사업 책임경계는 TBD로 둔다. 후속 장(II~IV)으로 넘기는 상세(논리노드 스펙, 거래패턴, 컨테이너 R/F, 암복호화)는 이 장에서 확정하지 않는다.

## 2. 목적 / 범위 / 전제

- **목적:** 이후 장에서 쓰는 명칭·경계·원칙·협업점을 이 장에서 고정한다.
- **범위:** I.1~I.5. II의 5개 영역 이름과 III/IV 시스템명은 Context에서 **위치만** 표시한다.
- **전제:** 원문 명칭을 보존한다. 국민은행·산업은행 IF 원문과 NSIGHT 방법론은 하나은행 FACT가 아니다.

# I.1 시스템 구축 배경 및 목적

**원문 작성 방향:** 기 작성내용 참조 · `[GAP]` 기작성 원문 미입수

## 1. 핵심 결론

`[FACT]` 1단계 과제는 마케팅플랫폼 및 데이터허브 구축이다. DBMS는 **Oracle Exa로 교체**되며, 이에 따라 **신규 도입 영역**과 **현행 부분개선(XDA SQL 변경)** 이 동시에 발생한다.

`[FACT]` 부분개선 대상은 현행 **운영CRM, 분석CRM, BSA**의 XDA SQL 변경 업무이다. 채널은 **정보단말·계정단말**, 프레임워크는 **MCA, EIC, Neoworks**, DBMS 축은 **RDW**로 적혀 있다.

`[FACT]` 개발환경은 계정단말 / 정보단말 / Neoworks / Devon **4종**이 필요하며, 부분개선(XDA SQL)과 관련된 것은 앞의 3종이다. Runtime은 정보단말이 Neoworks와 **직접 통신**, 계정단말은 **EIC/MCA 중계** 후 Neoworks 통신이다.

`[FACT]` 요구사항 원문: 기존 아키텍처를 최대한 유지하고, 현행 업무 영향 없이 1단계 개발과 협업 가능한 개발 아키텍처를 마련한다. 변경 영역은 **XDA SQL (RDW DB 도입)** 이다.

`[GAP]` 목차가 가리키는 「기 작성내용」(사업 배경 장표)이 없어, 정량 목표·일정·투자 근거는 만들지 않는다.

## 2. 목적 / 범위 / 전제

- **목적:** AS-IS 제약, 변화요인, 사업/시스템/아키텍처 목표를 층으로 분리한다.
- **범위:** 1단계 마케팅플랫폼·데이터허브와 부분개선 접점. 디지털뱅킹 MVP 전체는 범위가 아니다.
- **전제:** 회의록·의사결정 발언·캐릭터셋·물리 장표만 사용한다.

## 6. End-to-End 처리/데이터 흐름

이 절의 E2E는 **구축 이유의 흐름**이다. 거래 시퀀스는 III.

```text
[Trigger] Oracle Exa(RDW) 도입
    │
    ├─(1) 신규 영역 SQL/앱 설계 ──► 마케팅플랫폼·데이터허브 구축
    ├─(2) 현행 CRM/BSA XDA SQL 변경 ──► 부분개선 개발환경 필요
    └─(3) 신·구 공존 ──► 통합개발환경 1안 제안 (장비/서비스 비분리)
              │
              ▼
[종료] 현행 유지보수 비영향 + 1단계 협업 가능한 개발 아키텍처
```

# I.2 아키텍처 정의 수행 Approach

**원문 작성 방향:** 원본 검토표시 중요 · 작성담당 이용한

## 1. 핵심 결론

`[FACT]` 목차가 정한 TASK 순서는 다음 3단계이다.

1. **아키텍처 정의 범위 선정**
2. **아키텍처 설계 원칙 도출** (기능/비기능 요구사항 참조, 은행 정책 및 기준)
3. **아키텍처 상세화** (운영 정책 및 기준 준수, 관련 규정 및 법규 준수, 도입 솔루션 제안사항 반영)

인쇄본 I.2 항목 전체에 검토 동그라미가 있다. `[FACT]` 목차 수기.

## 2. 목적 / 범위 / 전제

- **전제:** 3단계를 중심축에서 빼지 않는다.

# I.3 아키텍처 정의 범위

**원문 작성 방향:** 전체 과업 중 분석으로 정의 범위를 지정. **2사업 역할 분담 제약사항** 기술

## 1. 핵심 결론

`[FACT]` 정의 범위는 「전체 대상 과업 중 분석을 통하여 아키텍처를 정의하는 범위」이다. 2사업 역할 분담에 따른 제약을 **반드시** 기술한다.

`[FACT]` 목차가 In-Scope로 올려 둔 큰 덩어리:

- **I~II:** 개요, 시스템 영역 5종, 업무시스템, 앱맵, 논리노드(VM/Container/베어메탈 Baseline), 환경(개발/테스트/운영/DR), SW, DB, 목표 IT구성
- **III:** 마케팅플랫폼·데이터허브의 온라인/배치/표준화/연계/고객행동/컨테이너/암복호/CI·CD
- **IV:** BI포탈, BIZ메타, Self BI, 데이터흐름관리, 비표준단말 SSO/EAM

`[FACT]` 명시 협업으로 **정의는 하되 단독 확정 불가**인 것: TA 논리노드/SW, DA DB·CDC/ETCL/BC, FW 레이아웃·계층·호출·실행제어, Hydra 고객행동, 2사업 컨테이너, 은행보안 암복호, IV 업무담당파트.

`[GAP]` 2사업 계약/R&R 원문이 없다. 제약은 목차 문장과 협업 태그로만 적는다.

## 2. 목적 / 범위 / 전제

- **목적:** In / Out / Interface / Dependency 를 교차 검증한다.
- **범위:** 아키텍처 **정의** 범위. 구축 과업 전체와 같지 않을 수 있다.
- **전제:** 디지털뱅킹 플랫폼 코드정책(2023-05)은 인접 AA이지 1단계 중심 과제가 아니다.

## 6. End-to-End (범위 결정 흐름)

```text

  → 2사업 단독 구축인가? → Dependency (상세 TBD)
  → 계정계 원장/상품코어인가? → Out, 연계만 IF
  → 목차 협업 태그 있음 → In-Scope이되 단독 확정 금지
```

## 7. 설계 규칙 및 표준

1. 목차에 있는 절은 기본적으로 In-Scope이다. 비우는 것은 GAP이지 Out이 아니다.
2. 협업 태그가 있는 절은 In-Scope + Dependency이다.
3. 인접 시스템(상품처리, 디지털뱅킹, 대외)은 Context에 그리되 내부 아키텍처를 이 정의서가 소유하지 않는다.

# I.4 아키텍처 설계 원칙 정의

**원문 작성 방향:** 설계 원칙 선정, **선정 근거 포함**

## 1. 핵심 결론

`[GAP]` 하나은행이 이미 확정한 **원칙 ID 목록 원문**은 본 다이어리에 없다. 이 절은 목차가 명시한 투입(기능/비기능, 은행 정책, 규정)과 **이미 적혀 있는 제약 문장**을 원칙 후보로 승격한다.

`[FACT]`에서 바로 원칙화할 수 있는 것:

- 현행 아키텍처 최대한 유지, 유지보수 비영향, 변경은 XDA SQL로 제한
- 시스템코드 3자리 · 서비스그룹 3자리 · 상호 1:n 연관 · EAI/형상 기준
- 환경은 개발/테스트/운영/DR
- 논리노드는 PMO VM/Container/베어메탈 Baseline
- 매체별 Character Set이 다르며, 불일치 시 명시적 지정
- JSON 표준전문, 정보단말 EUC-KR 등 매체 값 (기본 CS 단일값은 미확정)

`[TO-BE/PROPOSED]` IF-01~IF-10은 다이어리 최상위 인터페이스 원칙이며 **하나은행 원문이 아니다.** 채택 시 ADR로 승격한다.

## 2. 목적 / 범위 / 전제

- **목적:** 이후 장의 충돌을 원칙 표로 판결한다.
- **범위:** 원칙 후보. III의 거래패턴·호출규칙은 원칙의 적용이지 이 절에서 메커니즘을 쓰지 않는다.
- **전제:** 강제수준은 원문에 “원칙”으로 적힌 것만 Must에 가깝게 둔다.

## 3. 상위 Text Architecture


# I.5 시스템 Context 다이어그램

**원문 작성 방향:** Boundary 정의, 연계 시스템·데이터 종류, 사용자 역할 및 사용 이유 · 원본 검토 동그라미

## 1. 핵심 결론

`[FACT]` Target Boundary의 이름은 **마케팅플랫폼 및 데이터허브** (프로젝트ONE 1단계)이다. 소비 측에는 계정/정보단말, BI 포털, 분석도구, 데이터 가상화가 장표에 있다.

`[FACT]` 원천은 ECV/BCV, 채널(대면/비대면) 상품처리·로그, 기간계/레거시, 외부기관(공공·신용정보·금융공동망·Open API)이다. 유입 수단 이름은 **CDC · ETCL · HYDRA-K · D-0/D-1** 이다.

`[FACT]` Runtime 사용자 경로: 정보단말 → Neoworks 직접. 계정단말 → EIC/MCA → Neoworks.

`[FACT]` 캐릭터셋 Context는 내부를 EUC-KR 영역과 UTF-8 영역으로 나눌 수 있음을 보여 준다. 기본값 단일 확정은 아니다.

`[ANALYSIS]` 솔루션-서버 매핑의 클라우드(Con) 행(디지털뱅킹AP, 마케팅AP, 사용자분석AP, ETL, API G/W, MCA, FEP, EAI 등)은 **인접/공유 실행 위치**이지, 모두 Target 내부라고 단정할 수 없다 (I.3 ADR-SC-01).

프로토콜·포트·Timeout은 자료에 없으면 적지 않는다.

## 2. 목적 / 범위 / 전제

- **목적:** 한 장으로 내부/외부, 사용자, 데이터 종류를 합의한다.
- **범위:** 논리 Context. 물리 이중화·스펙은 II.
- **전제:** 원본 명칭 유지 (RTW, ADW, BSA, HDW, BDP, HYDRA-K, DataEye Portal, SAP BO는 현행 OLAP).

| BI포탈·비즈메타 | IV, 정보계 인접 | 분석 제공 | 업무담당 |
| Q-Track | 거버넌스 | 흐름관리 | IV.4 |
| 상품처리 | 외부 | 원장 | IF only |

## 6. End-to-End 정상 흐름 (대표 2본)

### 6.1 온라인 (정보단말)

```text
① 정보단말 사용자
② 정보단말 (EUC-KR)
③ Neoworks 직접 통신
④ 마케팅플랫폼 서비스
⑤ JDBC (CS 지정 가능) → RTW/ADW/BSA 등
⑥ 응답 단말 표시
```

계정단말은 ③ 앞에 EIC/MCA가 삽입된다. `[FACT]`

### 6.2 데이터 적재 (To-Be 정보계)

```text
① 원천 변경/배치 시점 (D-0 / D-1)
② CDC 또는 ETCL 또는 HYDRA-K
③ RTW / ADW / BSA / HDW / BDP 적재
④ JDBC 또는 데이터 가상화
⑤ 단말 · BI포털 · 분석도구 · 상품처리/채널 소비
```

`[FACT]` 장표 6. 동기/비동기 값은 수단 이름만 있고 Timeout은 없음.

## 7. 설계 규칙 및 표준

1. Context 상자 안에 상품처리 원장을 넣지 않는다 (P-02).
2. 화살표에 프로토콜을 쓸 때는 원문에 있는 이름만 (EAI, JDBC, CDC, ETCL, HYDRA-K). HTTP/포트 창작 금지.
3. IV 시스템은 내부 협업으로 그리되, 상세 아키텍처는 IV 장.
4. 시스템코드·서비스그룹은 EAI 등록 키이다. `[FACT]` Context 액터 식별에 사용. 구체 코드값은 앱맵(II.3)에서.
