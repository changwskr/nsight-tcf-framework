# II. 시스템 구성 — 장 연결

## 1. 핵심 결론

이 장은 I.5 Context를 **서비스 뷰 → 애플리케이션 뷰 → 논리노드 뷰 → SW/DB 뷰 → 목표 IT 뷰**로 내린다.

`[FACT]` 분해 축은 목차 II.1의 다섯 영역이다: 정보전달, 데이터 분석 및 정보제공, 데이터 저장소, 데이터 수집 및 연계, 인프라.

`[FACT]` 논리노드 Baseline은 PMO가 정한 **VM / Container / 베어메탈**이다. 구성환경은 **개발 / 테스트 / 운영 / DR**이다.

`[GAP]` PMO 매트릭스 원문과 1단계 전용 TO-BE 앱맵 장표가 없어, 노드 목록·앱 ID는 기존 장표에서 **후보**로만 올린다. 스펙은 장표에 적힌 것만 표로 옮긴다.

## 2. 목적 / 범위 / 전제

- **목적:** 업무 상자(II.2)와 기술 상자(II.5)를 같은 이름으로 추적 가능하게 만든다.
- **범위:** II.1~II.5. 거래패턴·호출규칙·CI/CD 파이프라인은 III.
- **전제:** 디지털뱅킹 DPN/PaaS 구성은 은행 IT 분류 **참조**이지 1단계 내부 맵이 아니다 (I.3 P-02).

```text

│  분석·정보제공            │
```

3. **책임:** II.1~3 = 아키텍처(업무). II.4~5 = TA/DA 공동.
4. **종료점:** II.5가 III의 실행 배경이 된다.

# II.1 시스템 영역 구분

**원문 작성 방향:** 원본 5개 영역 기준

## 1. 핵심 결론

`[FACT]` 구축 시스템의 Tier는 다음 다섯이다. 이름을 바꾸거나 6번째 영역을 만들지 않는다.

1. 정보전달 영역  
2. 데이터 분석 및 정보제공 영역  
3. 데이터 저장소 영역  
4. 데이터 수집 및 연계 영역  
5. 인프라 영역  

`[ANALYSIS]` I.5의 단말·Neoworks는 ①, BI/가상화/OLAP 소비는 ②, RTW·ADW·BSA·HDW·BDP는 ③, CDC·ETCL·HYDRA-K·EAI·MCA는 ④, OS·VM/Con/BM·관제는 ⑤에 대응한다.

영역 간 **금지된 직접호출** 문장은 목차·장표에 없다. `[GAP]` 우회 금지는 원칙 후보 P-06/P-07로만 제안한다.

## 2. 목적 / 범위 / 전제

- **목적:** 이후 절이 같은 다섯 칸에 상자를 넣게 한다.
- **범위:** 역할·입출력·의존. 제품 버전은 이 절에서 확정하지 않는다.
- **전제:** 인프라는 하단에 깔리며 다른 네 영역의 실행 기반이다.

4. **종료점:** 사용자 응답 또는 하류 적재. 원천 상품처리 원장은 ④의 바깥(I.3 Out).

# II.2 목표 업무시스템 구성도

**원문 작성 방향:** 서비스 관점 · 인쇄본 우측 화살표(검토 표시)

## 1. 핵심 결론

`[FACT]` 1단계가 제공하는 업무 덩어리는 **마케팅플랫폼**, **데이터허브(정보계 저장·적재)**, **부분개선(운영CRM·분석CRM·BSA)**, 그리고 목차 IV의 **BI포탈·BIZ메타·Self BI·데이터흐름관리**이다.

이 절은 제품명보다 **누가 어떤 업무를 받는가**를 그린다. CPU·JEUS는 II.4 이후.

`[GAP]` 「목표 업무시스템 구성도」원본 장표는 미입수. 아래 그림은 Context+정보계 TO-BE+회의록을 서비스 관점으로 재배치한 `[ANALYSIS]`이다.

## 2. 목적 / 범위 / 전제

- **목적:** 서비스 단위 전체 구성.
- **범위:** 1단계 In-Scope 서비스. 디지털뱅킹 MVP POD는 외부업무.
- **전제:** 기술 노드는 최소화.

## 3. 상위 Text Architecture

```text

        │
        ▼
┌────────────── 업무서비스군 (1단계) ──────────────┐
│  마케팅 서비스                                    │
```

# II.3 어플리케이션 구성

**원문 작성 방향:** 상위 묶음 (맵 + 정의)

## 1. 핵심 결론

`[FACT]` 은행 IT관리 식별 키는 **시스템코드(3자리)** 와 **서비스그룹 코드(3자리, AA Lv2)** 이다. 앱은 시스템코드에 묶이고, 서비스그룹은 반드시 하나 이상의 시스템코드와 연관된다.

`[FACT]` 디지털뱅킹 분류기준(2023-05, V0.6)은 현행 AA 트리(채널/상품/고객)와 DPN 신설 코드를 보여 준다. 1단계 중심 도메인은 회의록의 **고객·경영관리지원·공통정보인프라**이다.

`[GAP]` 마케팅플랫폼·데이터허브의 **공식 시스템코드 값**과 TO-BE 앱맵 전장은 없다. 아래는 공식 트리 위에 1단계 상자를 **겹친** 후보 맵이다.

## 2. 목적 / 범위 / 전제

- **목적:** 업무서비스 → 관리 가능한 앱 단위.
- **범위:** 맵(3.1)과 정의(3.2). Lv3 명명 표준 세부는 III.1.6.
- **전제:** 임의 재분류 금지. 없는 코드는 만들지 않는다.

## 3. 상위 Text Architecture

```text
업무영역(도메인)
    → Application Group
        → Application (LEVEL1)
            → Service Group (LEVEL2)
                → (LEVEL3 / 컨테이너 또는 프로그램)  → III
```

**그림 해설:** 시작=도메인, 순서=은행 AA 계층, 책임=코드정책+앱맵, 종료=II.3.2 정의 행.

## 4~12.

상세는 II.3.1, II.3.2. 이 묶음 절의 규칙은 다음과 같다.

- 공통 앱 vs 전용 앱: EIC/MCA/Neoworks는 **실행 FW**, DPN SIF는 **디지털뱅킹 전용**. 마케팅 모듈은 **1단계 전용**.
- 의존: 마케팅 앱 → Neoworks → (계정 시) EIC/MCA. 적재 앱 → ETCL/TeraStream.

# II.3.2 어플리케이션 정의

**그림 해설:** 시작=앱, 순서=업무→연계→데이터→실행, 책임=정의 표, 종료=노드 매핑 입력.
