# III. 장 연결

## 1. 핵심 결론

이 장은 APP-MKT·APP-ETCL을 **실행 가능한 계약**으로 내린다. 순서:

```text
III.1 온라인 → III.2 배치 → III.3 명명 → III.4 연계
 → III.5 행동데이터 → III.6 컨테이너 → III.7 보안 → III.8 전달
```

`[FACT]` 온라인 Runtime 뼈대는 정보단말→Neoworks **직접**, 계정단말→**EIC/MCA**→Neoworks이다.

`[FACT]` 목차가 온라인에 올린 설계 항목: 정보단말(엔진·EIC/EIMS·UI·전달패턴), Context/업무로그, 계층, 서비스그룹 호출, 실행제어(Timeout·로그레벨·중복거래), Lv3 명명, 거래패턴 8종, JSON 표준전문.

업무흐름(단말 거래)과 Runtime/운영흐름(배치 적재, CI/CD, 암복호)을 한 파이프로 그리지 않는다.

## 2. 목적 / 범위 / 전제

- **목적:** II의 앱·노드를 거래·배치·연계·운영 메커니즘에 연결한다.
- **범위:** III.1~8. IV 포탈/SSO는 여기서 소유하지 않는다.
- **전제:** Timeout 초, 암호 알고리즘, EIMS 제품 역할을 창작하지 않는다.

## 3. 상위 Text Architecture

```text
[업무흐름]
 사용자/정보단말/계정단말
        │
        ▼

        │ JDBC
        ▼
 II.4.6 저장 (RTW/ADW/BSA…)

[데이터 유입 흐름]
 원천 → III.4 CDC/ETCL/BC · III.2 배치(DevOn/ETCL/Shell·SP)
      → III.5 HYDRA-K / 고객행동
      → 동일 저장

[운영·보안·전달]
 III.6 컨테이너 R/F   III.7 암복호·마스킹   III.8 CI/CD (VM vs Con)
        │                    │                      │
```

**그림 해설**

1. **시작점:** 사용자 요청 또는 원천 변경/스케줄.
2. **처리순서:** 온라인을 먼저 고정하고, 배치·연계가 저장을 채우며, 컨테이너/보안/배포는 가로지른다.
3. **책임:** 1.2~1.5=FW, 4=DA, 5=Hydra, 6=2사업, 7=보안팀, 1.7=임채정, 2.1=허준, 2.2=연제학.
4. **종료점:** 응답 또는 적재 완료. 개통 승인은 III.8 밖.

**원문 작성 방향:** 상위 묶음 · 인쇄본 III.1 / 1.1 / 1.2 / 1.3 번호 동그라미

## 1. 핵심 결론

온라인은 **정보단말 UI → (계정은 EIC/MCA) → Neoworks → 서비스그룹 앱 → JDBC/연계** 이다.

1.1~1.8은 이 한 줄의 Drill-down이다. Context·계층·호출·실행제어는 FW 없이 확정하지 않는다.

단말에서 서비스 실행까지. 배치는 III.2.

```text
정보단말 (EUC-KR) ──직접──► ┐
계정단말 ──EIC/MCA──►      ├─ Neoworks
                           │      │
                           │      ▼
                    III.1.2 Context / 업무로그
                           │      │
                           │      ▼
                    III.1.3 App Layer (모듈·호출)
                           │      │
                           │      ▼
                    III.1.4 Service Group 경계
                           │      │
                           │      ▼

                           │      │
```

**그림 해설:** 시작=단말, 순서=진입→Context→계층→그룹→제어→패턴/전문, 책임=FW+앱, 종료=DB 또는 외부 I/F.

## 4~12.

상세는 1.1~1.8. 이 묶음의 규칙: Runtime 화살표를 회의록과 다르게 그리지 않는다. 패턴 이름을 목차 8종 밖으로 늘리지 않는다.

# III.1.1 정보단말 활용

**원문 작성 방향:** 엔진 업그레이드 · EIC/EIMS · UI 주의 · 정보전달 패턴

## 1. 핵심 결론

`[FACT]` 정보단말은 마케팅플랫폼 **안의** 정보단말이며, Neoworks와 **직접** 통신한다. 계정단말은 이 절의 주 대상이 아니고 EIC/MCA 중계를 탄다.

`[FACT]` 목차가 이 절에 요구한 작업: 표준/추가정의 항목, **엔진 업그레이드**, **EIC/EIMS 도입에 따른 변경 기능 식별**, UI 주의사항, **정보전달영역 패턴 분류**.

`[GAP]` 엔진 제품·버전, EIMS의 역할, UI 가이드 원문, 전달패턴 분류표가 없다. EIC는 회의록에 프레임워크로 존재한다.

## 2. 목적 / 범위 / 전제

정보단말 변경점과 전달 패턴. 계정단말 Push는 1.7 패턴으로 위임.

## 3. 상위 Text Architecture

```text
User
  → 정보단말 / UI   (EUC-KR)     ← UI 주의 · 마스킹은 III.7
        │
        │ AS-IS: Neoworks 직접
        │ TO-BE 변경 후보: 엔진 업그레이드 [TBD]
        │                 EIC/EIMS 도입 영향 [TBD — 정보단말 경로에 EIC가
        │                 끼는지는 회의록과 불일치 가능, 확인필요]
        ▼
 정보전달 영역 (II.1 ①)
        │
        ▼
 온라인 서비스 (Neoworks)
```

**그림 해설:** 시작=사용자, 순서=UI→전달→서비스, 책임=단말표준+FW, 종료=서비스 진입(1.2).

## 4. AS-IS / TO-BE 변경 식별

| 항목 | AS-IS `[FACT]` | TO-BE 목차 요구 | 확정 |

| 전달패턴 | 없음 | 분류 정의 | GAP → 1.7과 교차 |

# III.1.2 서비스 Context 레이아웃 정의

**원문 작성 방향:** `[프레임워크 협업 필요]` · 업무로그 포함 · 이용한

## 1. 핵심 결론

`[FACT]` 정의 대상은 온라인 **Service Context 레이아웃**과 **업무로그 레이아웃**이다.

`[GAP]` 필드 목록 원문이 없다. Header/Control 등 일반 구조를 **확정으로 쓰지 않는다.**

캐릭터셋 `[FACT]`: 전문 변환은 FW/공용모듈, 앱 영향 없음(또는 앱별 정의 가능). Context가 전문 봉투와 붙는지는 FW 확인.

## 2. 목적 / 범위 / 전제

요청 수신부터 로그/응답까지 Context가 무엇이 남는가. 값은 FW 산출 전 TBD.

## 3. 상위 Text Architecture

```text
Request (단말 EUC-KR / JSON UTF-8)
        │
        ▼
 Context 생성 · 보강     ← FW  [필드 TBD]
        │
        ▼
 공통처리 (1.5 제어와 접점)
        │
        ▼
 업무계층 전달 (1.3)
        │
        ├─ 업무로그 기록  ← 레이아웃 TBD, Context와 키 공유 여부는 FW
        └─ 응답
```

**그림 해설:** 시작=요청, 순서=생성→공통→업무→로그/응답, 책임=FW, 종료=로그 적재 또는 응답.

## 4. 필드 표 (템플릿 — 값 없음)

프롬프트가 금지하므로 칸만 둔다.

| 필드 | 생성주체 | 변경 | 전달범위 | 로그연계 | 근거 |
|------|----------|------|----------|----------|------|
| `[TBD]` | FW/단말/앱 | | 전 계층 / 앱만 | Y/N | 원문 없음 |

추적에 쓰일 **이름 후보** (하나 원문 아님, 비교): NSIGHT는 Service ID가 Handler·로그에 동일 문자열. 하나 채택은 III.3.

## 5. 구성요소 및 책임

| 구성 | 책임 | 태그 |
|------|------|------|
| Context | 거래 수행 상태 | FW |
| 업무로그 | 감사·추적 | FW + 앱 |
| 전문 봉투 | JSON 1.8 | FW |

## 6. End-to-End

```text
수신 → Context 생성 → 1.5 전처리 → 1.3 실행 → 로그 → 응답
오류 시 Context 상관 ID로 로그 연결  [구현 TBD]
```

## 7. 설계 규칙

필드 창작 금지. CS 변환은 전문 경계 1회 (캐릭터셋 보완 CS-R1, ANALYSIS).

## 8. 제약 / 예외 / 장애 / 보안 / 운영

로그에 중요정보 평문 → III.7. Timeout 시 로그 남김 여부는 1.5와 함께 TBD.

## 9. Traceability

# III.1.4 서비스그룹 간 호출 규칙

**원문 작성 방향:** `[프레임워크 협업 필요]` · 타 그룹 제약/DTO/Remote · 이용한

Lv2 경계. 동일 그룹 내부는 제약이 목차에 없다(내부는 허용으로 단정하지 않고 “목차 비대상”).

```text
               │ 허용 방식 [TBD]

        공통계약 / 공개 API / 복제 DTO / Remote
               │
┌──────────────▼───────────────────┐
│ Service Group B (프로젝트 B)       │
│  컴포넌트 · DTO-B                  │
└──────────────────────────────────┘
```

# III.8 CI/CD 지원 방안

**원문 작성 방향:** 절차·Tool · VM vs 컨테이너 · 개발/테스트/**이행** · 담당란 X, 팀장 확인

## 1. 핵심 결론

`[FACT]` 구분 축 두 개: **VM vs 컨테이너**, **개발단계 / 테스트단계 / 이행단계**.

II.4.2 환경 이름은 개발/테스트/운영/DR이다. 이 절은 **이행**을 쓴다. 운영=이행인지 별도인지는 TBD.

Tool 확정 없음. TRM 후보는 Jenkins, Gitlab Runner, Bamboo, Spinnaker, ArgoCD, Harbor, Nexus 등. Bitbucket/Gitlab EE는 형상.

형상관리 기준은 시스템코드 `[FACT]`.

## 2. 목적 / 범위 / 전제

앱 전달. 인프라 GitOps 전체는 2사업 가능.

## 3. 상위 Text Architecture

```text
개발단계          테스트단계         이행단계
 소스+빌드          검증 배포          운영 이관
   │                  │                  │
   ├──── VM 파이프 (ETL VM, 기존 WAS…) ───┤
   └──── 컨테이너 파이프 (III.6, S09…) ───┘
Tool [TRM 후보, 미선정]
```

**그림 해설:** 시작=개발, 순서=3단계×2런타임, 책임=앱CM+TA+2사업, 종료=이행 완료.
