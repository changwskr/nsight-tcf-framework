### Orchestrator의 동작 방식

이제 사용자는 내부 Agent를 직접 선택할 필요가 없습니다.

```text
사용자 Mission
      ↓
ORCHESTRATOR
      │
      ├─ System Scope 판단
      ├─ Run Type 판단
      ├─ 필요한 Agent 선택
      ├─ 선택 이유 기록
      ├─ 실행순서 결정
      └─ Gate 결정
      ↓
Agent Team
      ↓
Closed Loop 실행
```

예를 들어:

```text
"TCF Transaction Boundary를 검증해줘"
```

라고 하면 기본적으로:

```text
Baseline Agent
      ↓
Document Agent ─┐
                ├→ Model Agent
Source Agent ───┘
      ↓
Code Rule Agent
      ↓
Test Agent
      ↓
Deploy Agent
      ↓
Runtime Evidence Agent
      ↓
Drift Agent
      ↓
GAP / ADR Agent
      ↓
Gate Manager
```

가 구성됩니다.

### 첫 작업은 `PILOT-01`입니다

전체 NSIGHT를 한꺼번에 대상으로 하지 않도록 했습니다.

```text
NSIGHT_TCF
   +
대표 Business WAR 1개
   +
실제 Source에서 확인한
ServiceId 1~3개
```

로 시작합니다.

그리고 하나의 ServiceId를:

```text
Requirement
 ↓
Screen/Event
 ↓
ServiceId
 ↓
Handler
 ↓
Facade
 ↓
Service
 ↓
DAO
 ↓
Mapper / SQL
 ↓
Table
 ↓
Test
 ↓
Build
 ↓
Deploy
 ↓
TraceId
 ↓
Runtime Evidence
```

까지 관통시키는 것이 **첫 번째 성공 기준**입니다.

### 사용자 화면도 7개 View로 정의했습니다

```text
01 Mission
      ↓
02 Orchestrator Plan
      ↓
03 Agent Catalog
      ↓
04 Execution Board
      ↓
05 Traceability
      ↓
06 Drift / GAP
      ↓
07 Baseline Release
```

따라서 향후 실제 UI를 만들 때도 이 구조를 그대로 사용할 수 있습니다.

### 현재 NSIGHT의 실제 GAP Seed도 넣었습니다

기존 전수점검에서 확인한 문서/Source 혼재 문제를 초기 검증 대상으로 포함했습니다. 현재 저장소는 대량의 build/generated 복제 문서와 서로 다른 시점의 자료가 혼재되어 있어 Source Scope와 Baseline 통제가 우선 필요합니다.

예를 들어:

```text
Root Gradle Baseline
22 / 24 Module 차이
OM Handler 24 / 25 차이
Transaction Boundary
DeltaManager / Spring Session JDBC
Gate Evaluator
Runtime Evidence
Critical Module Test
Sensitive Logging
```

을 첫 Drift 후보로 넣었습니다.
