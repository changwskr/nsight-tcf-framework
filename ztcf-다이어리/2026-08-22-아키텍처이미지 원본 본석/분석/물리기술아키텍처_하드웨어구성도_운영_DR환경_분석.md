# 물리기술아키텍처 — 하드웨어 구성도 — 운영/DR 환경 분석

> 원본 범위: `3. 물리 기술 아키텍처 > 3.1 하드웨어 구성도`  
> 원본 페이지/이미지: 71쪽, `85737/25.png`  
> 분석 원칙: 이미지에서 식별되는 센터, 역할, 서버 번호와 연결을 우선한다. 흐릿한 Hostname, RPO/RTO, 자동전환 여부는 확정하지 않는다.

---

## 1. 결론

운영/DR 환경은 **의왕 센터(주 센터)**와 **안성 센터(DR 센터)**를 `DCI`로 연결하고, 상단의 `내부 GSLB`가 센터 수준 서비스 진입점을 전환하는 이중 센터 구조다.

- 의왕에는 마케팅, 실적/분석, 데이터거버넌스/운영관리, 데이터 처리/이행, 저장소/DB가 폭넓게 배치된다.
- 안성에는 마케팅 WEB/WAS, 미니싱글뷰 WEB/WAS, 단말관리·배포 WEB/WAS, 마스터솔루션, RDW Standby가 선택적으로 배치된다.
- RDW는 `Data Guard` 원격지 복제와 `Standby`가 명시되어 있다.
- ADW, BI, 데이터거버넌스, ETL/CDC 및 실시간 AP의 DR 노드는 표시되지 않는다. 이는 “DR 불필요”가 아니라 **장표상 미표시**다.

```text
                            [내부 GSLB]
                   ┌────────────┴────────────┐
                   ▼                         ▼
       ┌──── 의왕 센터(주 센터) ────┐   ┌── 안성 센터(DR) ──┐
       │ 마케팅 / 실적·분석          │   │ 마케팅 WEB/WAS      │
       │ 거버넌스 / 운영관리         │   │ 단말관리·배포        │
       │ 데이터 처리·이행            │   │ 마스터솔루션          │
       │ ADW DB / RDW DB             │   │ RDW DB Standby       │
       └────────────┬────────────────┘   └─────────┬───────────┘
                    └────────── DCI ───────────────┘
                         RDW Data Guard 복제
```

## 2. 근거 수준

| 수준 | 내용 |
|---|---|
| 확인 사실 | 의왕 센터(주 센터), 안성 센터(DR 센터), 내부 GSLB, DCI가 표시됨 |
| 확인 사실 | 의왕 5개 영역과 안성 3개 영역이 표시됨 |
| 확인 사실 | RDW 원격지 복제(Data Guard), 안성 RDW Standby가 표시됨 |
| 확인 사실 | 다수 WEB/WAS는 #1,#2 또는 #51,#52로 이중 노드가 표시됨 |
| 설계 해석 | GSLB는 센터 진입점 전환, DCI는 센터 간 통신 경로로 해석 |
| 설계 해석 | 운영 번호대 `#1~`, DR 번호대 `#51~`는 센터별 자산 식별 규칙으로 해석 가능 |
| 미확정 | GSLB 자동/수동 전환, Health Check, DNS TTL |
| 미확정 | Data Guard 보호모드, 동기/비동기, 최대 허용 Lag |
| 미확정 | ADW 및 장표에 없는 업무의 DR 구현 방식 |
| 미확정 | 일부 흐릿한 Hostname과 물리 사양(CPU, Memory, Disk, NIC) |

## 3. 전체 물리 배치

```text
┌────────────────────────── 의왕 운영 ──────────────────────────┐
│ IaaS                                                        │
│  1) 마케팅       WEB/WAS + 실시간/행동정보/고객행동 AP       │
│  2) 실적/분석    BI포탈 + Self-BI + 신용실적                 │
│  3) 거버넌스/운영 비즈메타·품질 + 흐름 + RD + 배치 + 단말     │
│  4) 처리/이행    ETL + CDC중계DB + 변환/이행/SQL품질/추출DB   │
│  5) 저장소/DB    정보계·백업·ZFS + ADW/RDW Appliance         │
└───────────────────────────┬──────────────────────────────────┘
                            │ DCI
┌───────────────────────────┴──── 안성 DR ─────────────────────┐
│ IaaS                                                        │
│  1) 마케팅       마케팅플랫폼/미니싱글뷰 WEB/WAS             │
│  2) 운영관리     단말관리/단말배포 WEB/WAS + 마스터솔루션     │
│  3) 저장소/DB    정보계·백업·ZFS + RDW Appliance Standby     │
└──────────────────────────────────────────────────────────────┘
```

범례상 색은 AP, DB, WEB, WAS, ETL, 베어메탈, IaaS 역할을 구분한다. 색 자체보다 박스의 역할명과 센터 배치를 운영 기준으로 삼아야 한다.

## 4. 의왕 센터 — 마케팅

| 역할 | 노드 번호 | 수량 |
|---|---:|---:|
| 마케팅플랫폼 WEB | #1, #2 | 2 |
| 마케팅플랫폼 WAS | #1, #2 | 2 |
| 미니싱글뷰 WEB | #1, #2 | 2 |
| 미니싱글뷰 WAS | #1, #2 | 2 |
| 실시간처리 AP | #1, #2 | 2 |
| 행동정보처리 AP | #1, #2 | 2 |
| 고객행동데이터 AP | #1, #2, #3 | 3 |

```text
                  ┌─ 마케팅플랫폼 WEB #1,#2 ─ WAS #1,#2
[내부 GSLB/L4] ───┤
                  └─ 미니싱글뷰 WEB #1,#2 ─ WAS #1,#2
                                      │
             ┌────────────────────────┼─────────────────────┐
             ▼                        ▼                     ▼
       실시간처리 AP ×2        행동정보처리 AP ×2      고객행동데이터 AP ×3
```

WEB/WAS의 2노드 구성은 센터 내 HA 기반을 제공하지만, 실제 Active-Active 여부와 세션 저장 방식은 장표에 없다. 고객행동데이터 AP가 3노드인 것은 처리량·분산 요구가 상대적으로 크다는 신호로 해석할 수 있다.

## 5. 의왕 센터 — 실적/분석

| 역할 | 노드 번호 | 수량 |
|---|---:|---:|
| BI포탈 WEB/WAS | 각 #1, #2 | 각 2 |
| Self-BI WEB/WAS | 각 #1, #2 | 각 2 |
| Self-BI AP | #1 | 1 |
| 신용실적 WEB/WAS | 각 #1, #2 | 각 2 |

```text
[BI포탈 WEB ×2] ─ [BI포탈 WAS ×2] ─┐
[Self-BI WEB ×2] ─ [Self-BI WAS ×2] ├─ [RDW / ADW]
                        │ AP ×1      │
[신용실적 WEB ×2] ─ [신용실적 WAS ×2]┘
```

Self-BI AP가 단일 노드로 표시되므로, 장애 시 기능 저하 여부와 애플리케이션 자체 클러스터링을 확인해야 한다. 이 전체 영역은 안성 DR에 표시되지 않는다.

## 6. 의왕 센터 — 데이터거버넌스/운영관리

| 역할 | 노드 번호 | 수량 |
|---|---:|---:|
| 비즈메타/데이터품질 WAS | #1, #2 | 2 |
| 데이터흐름 WAS | #1 | 1 |
| 출력물(RD) WAS | #1, #2 | 2 |
| 배치 AP | #1 | 1 |
| 마스터솔루션 | #1 | 1 |
| 단말관리 WEB/WAS | 각 #1~#4 | 각 4 |
| 단말배포 WEB/WAS | 각 #1~#6 | 각 6 |
| UNO Dashboard | #1 | 1 |

```text
거버넌스: [비즈메타/품질 WAS ×2] [데이터흐름 WAS ×1]
출력/배치: [RD WAS ×2] [배치 AP ×1]
운영제어: [마스터솔루션 ×1] [UNO Dashboard ×1]
단말관리: [WEB ×4] ─ [WAS ×4]
단말배포: [WEB ×6] ─ [WAS ×6]
```

단말관리·배포는 사용자 규모와 배포 집중 부하를 반영해 다른 시스템보다 많은 노드를 가진다. 데이터흐름, 배치, 마스터솔루션, UNO Dashboard는 단일 노드로 보이므로 별도의 제품 HA 또는 재기동 전략 확인이 필요하다.

## 7. 의왕 센터 — 데이터 처리/이행

| 역할 | 노드 번호 | 수량/플랫폼 |
|---|---:|---|
| ETL AP | #1, #2 | 2, 물리(x86) 표기 |
| CDC중계 DB | #1, #2 | 2, 물리(UNIX) 표기 |
| 변환 AP | #1~#6 | 6 |
| 이행 AP | #1 | 1 |
| SQL품질 | #1 | 1 |
| 추출 DB | #1 | 1 |

```text
[원천 DB/FOS]
      │
      ├─ CDC → [CDC중계 DB ×2]
      └─ 추출 → [추출 DB ×1]
                    │
          [변환 AP ×6] → [SQL품질 ×1] → [이행 AP ×1]
                    │
                 [ETL AP ×2]
                    ▼
                RDW / ADW
```

점선의 `원천 데이터 이행 영역/임시`는 상시 서비스 노드와 수명주기가 다를 수 있다. 이행 완료 후 폐기·격리·재사용 여부를 별도 결정해야 한다.

## 8. 의왕 센터 — 저장소/DB와 원천

```text
[정보계 스토리지] [백업 스토리지] [ZFS: ADW #1 / RDW #1]
           │                │
 [ADW DB Appliance #1~#6] [RDW DB Appliance #1,#2]
           ▲                ▲
           └──── 원천: 디지털금융 / 코어뱅킹 원천DB·복제DB / FOS
```

| 구성 | 노드 |
|---|---:|
| ADW DB Appliance | #1~#6 |
| RDW DB Appliance | #1, #2 |
| 정보계 스토리지 | 수량 미표시 |
| 백업 스토리지 | 수량 미표시 |
| ZFS | ADW #1, RDW #1 표기 |

ADW는 6개 노드, RDW는 2개 노드로 용량·처리 특성이 분리되어 있다. DB Appliance 내부의 RAC/클러스터 토폴로지와 스토리지 중복도는 이 장표만으로 확정할 수 없다.

## 9. 안성 센터 — DR 배치

### 9.1 마케팅

| 역할 | 노드 번호 | 수량 |
|---|---:|---:|
| 마케팅플랫폼 WEB/WAS | 각 #51, #52 | 각 2 |
| 미니싱글뷰 WEB/WAS | 각 #51, #52 | 각 2 |

```text
[DR 마케팅플랫폼 WEB #51,#52] ─ [WAS #51,#52]
[DR 미니싱글뷰 WEB #51,#52]   ─ [WAS #51,#52]
```

### 9.2 운영관리

| 역할 | 노드 번호 | 수량 |
|---|---:|---:|
| 단말관리 WEB/WAS | 각 #51~#54 | 각 4 |
| 단말배포 WEB/WAS | 각 #51~#56 | 각 6 |
| 마스터솔루션 | #51 | 1 |

```text
[단말관리 WEB ×4] ─ [WAS ×4]
[단말배포 WEB ×6] ─ [WAS ×6]
                 └─ [마스터솔루션 ×1]
```

### 9.3 저장소/DB

```text
의왕 [RDW DB Appliance #1,#2]
                 │ redo/복제(Data Guard)
                 ▼
안성 [RDW DB Appliance #51,#52] ─ Standby
     [정보계 스토리지] [백업 스토리지] [ZFS RDW #1]
```

RDW Standby는 확인 사실이지만, 복제 모드·전송 암호화·Apply Lag·Failover 자동화는 미확정이다.

## 10. 센터 전환 메커니즘

자산 역할을 분리해서 보면 운영·DR 양쪽에는 `단말관리 WEB`, `단말관리 WAS`, `단말배포 WEB`, `단말배포 WAS` 노드군이 존재한다. 의왕 하단 원천 영역에는 `디지털금융`, `코어뱅킹 원천DB`, `코어뱅킹 복제DB`, `FOS`가 표시된다.

```text
평상시
Client → 내부 GSLB → 의왕 VIP → WEB → WAS → 의왕 RDW Primary
                                             │ Data Guard
                                             ▼
                                      안성 RDW Standby

DR 선언 후(목표 흐름)
Client → 내부 GSLB → 안성 VIP → DR WEB → DR WAS → 승격 RDW
```

### 전환 제어면

```text
장애 감지 → 영향 평가 → DR 선언 → 복제상태 확인
 → RDW 승격 → DR 애플리케이션 기동/검증
 → GSLB 전환 → 업무 Smoke Test → 서비스 공지
```

GSLB가 표시됐다고 자동 DR이 보장되지는 않는다. DB 승격, 애플리케이션 기동 순서, 외부 연계 주소, 배치 중지, 데이터 정합성 확인이 오케스트레이션되어야 한다.

## 11. 운영과 DR의 범위 차이

| 영역 | 의왕 | 안성 | 판단 |
|---|:---:|:---:|---|
| 마케팅·미니싱글뷰 WEB/WAS | O | O | 명시적 DR 대상 |
| 실시간·행동정보·고객행동 AP | O | 미표시 | 대체/복구 방식 확인 필요 |
| BI포탈·Self-BI·신용실적 | O | 미표시 | DR 우선순위 확인 필요 |
| 데이터거버넌스 | O | 미표시 | 복구/재구축 방식 확인 필요 |
| RD·배치·UNO | O | 미표시 | 기능별 복구 기준 필요 |
| 단말관리·단말배포 | O | O | 명시적 DR 대상 |
| 마스터솔루션 | O | O | DR 제어 기능 유지 |
| ETL·CDC·이행 | O | 미표시 | 재개점·중복 방지 필요 |
| RDW DB | O Primary 추정 | O Standby | Data Guard 명시 |
| ADW DB | O | 미표시 | DR 전략 미확정 |

> `Primary`는 Standby의 상대 역할로 해석한 것이며 이미지에 Primary라는 글자가 직접 표시된 것은 아니다.

## 12. 가용성·데이터보호 분석

```text
센터 내 HA: WEB/WAS 다중 노드 + DB Appliance 내부 HA(상세 미확정)
센터 간 DR: 내부 GSLB + DCI + RDW Data Guard
백업 복구: 백업 스토리지 + ZFS(정책/보존기간 미확정)
```

- WEB/WAS 다중 노드는 프로세스/VM 장애를 흡수할 수 있어야 한다.
- GSLB Health Check는 단순 포트가 아니라 업무 종속성까지 확인하는 합성 점검이 바람직하다.
- DCI 이중 경로와 대역폭은 복제 트래픽 및 DR 전환 트래픽을 감당해야 한다.
- 백업은 복제와 다르다. 논리 삭제·랜섬웨어·오염 데이터는 Standby에도 전파될 수 있다.
- 정기 복구 테스트로 백업의 실제 복구 가능성을 검증해야 한다.

## 13. 세션·배치·연계 고려사항

```text
세션: 주센터 로컬 세션 → DR 전환 시 재로그인/공유저장소 여부 결정
배치: 신규 실행 차단 → 실행중 작업 종료/중단 → Checkpoint 보존 → DR 재개
파일: 송수신 완료점 확인 → 중복 키 확인 → 미완료 파일 재전송
CDC/ETL: 마지막 적용 시점 확인 → Gap 보정 → 정합성 대사 → 재개
```

장표에는 세션 저장소, Kafka/메시지 복제, ETL Job Repository, 파일 송수신 큐가 보이지 않는다. 이 상태들의 DR 정책이 없으면 WEB/WAS가 살아도 업무 복구는 완료되지 않는다.

## 14. 네트워크·보안 경계

```text
사용자/내부망
   │
[내부 GSLB]
   ├─ 의왕 WEB Zone ─ WAS Zone ─ AP/DB Zone
   └─ 안성 WEB Zone ─ WAS Zone ─ DR DB Zone
                         │
                        DCI (허용 포트·암호화·대역폭 통제)
```

- 센터별 WEB, WAS, AP, DB 보안구간과 ACL을 동일 정책으로 관리한다.
- DR 계정·인증서·비밀정보의 최신성을 정기 검증한다.
- Data Guard, 백업, 관리 트래픽을 업무 트래픽과 논리적으로 분리한다.
- DR 센터가 장기간 대기하더라도 패치·백신·취약점 수준이 운영과 같아야 한다.

## 15. 관측과 용량

| 대상 | 핵심 지표 |
|---|---|
| GSLB | Health Check, 응답시간, 전환 상태, DNS TTL |
| DCI | 대역폭, 지연, 손실, 경로 상태 |
| WEB/WAS | 노드 가용성, 요청량, 오류율, 세션, JVM |
| AP/ETL | 작업량, 큐 적체, 재처리, Checkpoint |
| Data Guard | Transport Lag, Apply Lag, Gap, 보호모드 |
| DB Appliance | CPU, Memory, IOPS, 세션, 장기 SQL |
| Storage/ZFS | 사용률, 지연, Snapshot, 복구 성공률 |
| Backup | 성공률, 보존기간, 불변성, 복구시간 |

DR 용량은 평상시 저사용률이 아니라 전환 후 핵심 업무의 예상 동시 부하를 기준으로 산정해야 한다.

## 17. 확정해야 할 설계 항목

1. 업무별 RTO/RPO와 DR Tier
2. 내부 GSLB의 자동/수동 전환 및 복귀 정책
3. DCI 이중 경로·대역폭·QoS·암호화
4. Data Guard 보호모드, 동기/비동기, Lag 임계치
5. ADW·BI·거버넌스·AP·ETL/CDC의 DR 방식
6. 세션, 메시지, 파일, 스케줄러 상태의 복구 방식
7. DR 센터 용량 및 라이선스
8. 백업 불변성, 보존기간, Off-site 사본, Restore 주기
9. Failover/Failback Runbook과 승인권자
10. 일부 Hostname과 정확한 자산 인벤토리

```text
설계완료의 기준
= 서버가 존재함
+ 데이터가 복구됨
+ 연계가 재개됨
+ 업무가 검증됨
+ 운영·보안·관제가 유지됨
+ 원센터 복귀가 가능함
```

## 18. 최종 평가

이 구성은 의왕에 전체 운영 기능을 집중하고 안성에는 우선순위가 높은 일부 WEB/WAS·운영관리와 RDW Standby를 배치한 **선택적 DR 아키텍처**다. `내부 GSLB`, `DCI`, `Data Guard`가 각각 트래픽 전환, 센터 연결, RDW 데이터 보호를 담당하는 구조는 명확하다.

반면 장표에 없는 ADW·분석·거버넌스·실시간/배치 상태는 별도 복구 설계가 필요하다. 실제 DR 완성도는 서버 수보다 RTO/RPO, 복제 Gap, 세션·스케줄·파일 재개점, 데이터 대사, Failback을 반복 검증하는 데 달려 있다.
