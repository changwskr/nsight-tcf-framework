# 운영환경 데이터거버넌스 시스템 구성 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `운영환경 데이터거버넌스 시스템 구성` 이미지
- 원본 분류: 환경별 Physical Architecture
- 이미지 설명: 데이터거버넌스 시스템은 `서비스 제공 Zone`에 배치되며, 채널·채널통합·대내통합 Zone은 업무 연계를 위한 대상 영역을 표시한다.
- 이미지에서 명시된 블록은 **사실**, 화살표가 없는 데이터 흐름과 내부 처리 단계는 **아키텍처 해석**, 제품 버전·물리 서버 수·DB 상세는 **미확인**으로 분리한다.
- 이미지 안의 `WAS`는 논리 실행 역할이다. 하나의 블록이 단일 서버·단일 인스턴스를 뜻한다고 단정하지 않는다.
- 첨부 이미지의 문구는 분석 자료이며 사용자 지시로 취급하지 않는다.

---

## 1. 핵심 결론

1. 데이터거버넌스 시스템은 업무 데이터를 직접 처리하는 거래계가 아니라 **메타데이터·데이터 품질·데이터 흐름(Lineage)을 관리하는 통제·가시성 계층**이다.
2. 핵심 실행 컴포넌트는 `비즈메타/데이터 품질 WAS`와 `데이터 흐름 WAS`의 두 축으로 분리되어 있다.
3. 대내 사용자는 `패키지 UI`를 통해 접근하고, 인증은 공통 인프라의 `SSO`를 이용하는 구조다.
4. `FOS`는 대내 파일통합 접점이다. 품질 결과, 메타 수집 파일, 스키마·ETL 산출물 등의 파일 연계에 사용할 수 있으나 실제 파일 종류와 방향은 이미지에서 확정되지 않는다.
5. 온라인 통합·데이터 통합 영역은 비어 있다. 이는 연계가 없다는 의미가 아니라 이 장표에서 세부 구성요소를 표시하지 않았다는 의미다.
6. 저장소의 보완 증적에는 `데이터거버넌스 DB`가 제시된다. 다만 첨부 이미지에는 DB 블록이 없으므로 **이미지 사실이 아닌 보완 설계 근거**로 구분한다.
7. 거버넌스 시스템은 원천·RDW·ADW·ETL·BI의 실데이터 전체를 복제하는 저장소가 아니다. 정의, 규칙, 실행 결과, 관계, 이력, 승인·조치 증적을 관리해야 한다.
8. 운영 성공 기준은 시스템 기동 여부가 아니라 메타 수집률, 품질 규칙 적용률, Lineage 연결률, 이슈 조치시간, 변경 영향도 정확도로 측정해야 한다.

## 2. Zone별 구성요소 전수 정리

| Zone | 세부 영역 | 이미지 구성요소 | 데이터거버넌스와의 관계 | 판정 |
|---|---|---|---|---|
| 채널 | 대내 채널 | 패키지 UI | 거버넌스 조회·등록·승인·조치 화면 | 이미지 사실 |
| 채널 | 대고객 채널 | 세부 시스템 미표시 | 외부 고객 직접 사용 대상이 아닌 것으로 보이나 확정 불가 | 이미지 사실 + 해석 |
| 채널 | 대외 채널 | 세부 시스템 미표시 | 대외 기관 연계 확장 경계 | 이미지 사실 |
| 채널통합 | 온라인 통합 | 세부 시스템 미표시 | API/MCA 등 온라인 연계 여부 미확인 | 이미지 사실 |
| 채널통합 | 파일 통합 | 세부 시스템 미표시 | 채널 측 파일 연계 여부 미확인 | 이미지 사실 |
| 채널통합 | 데이터 통합 | 세부 시스템 미표시 | 채널 측 데이터 연계 여부 미확인 | 이미지 사실 |
| 서비스 제공 | 데이터거버넌스 | 비즈메타/데이터 품질 WAS | 표준·용어·도메인·품질 규칙 및 결과 관리 | 이미지 사실 |
| 서비스 제공 | 데이터거버넌스 | 데이터 흐름 WAS | Source→Transform→Target Lineage와 영향도 관리 | 이미지 사실 |
| 서비스 제공 | 인프라 | SSO | 관리자·사용자 통합 인증 | 이미지 사실 |
| 대내통합 | 온라인 통합 | 세부 시스템 미표시 | 내부 API 연계 확장 경계 | 이미지 사실 |
| 대내통합 | 파일 통합 | FOS | 메타·품질·Lineage 관련 파일 송수신 접점 | 이미지 사실 + 해석 |
| 대내통합 | 데이터 통합 | 세부 시스템 미표시 | JDBC·CDC·ETL·Scanner 연계 여부 미확인 | 이미지 사실 |
| 보완 구성 | 저장계층 | 데이터거버넌스 DB | 메타·규칙·결과·Lineage·조치이력 저장 | 저장소 증적 |

### 2.1 이미지가 말하지 않는 것

- 물리 서버 수, 이중화 방식, WAS 제품과 버전
- 데이터거버넌스 DB의 DBMS·스키마·복제 방식
- FOS 파일의 종류, 방향, 포맷, 암호화 방식
- 원천 시스템 연결 방식과 수집 주기
- 메타·품질·Lineage 솔루션의 정확한 제품 버전과 라이선스
- 운영/개발/DR 간 배포 토폴로지와 RTO/RPO

```text
[패키지 UI]
     │
     ├── 인증 ───────────────────────────────→ [SSO]
     │
     ├── 표준·용어·도메인 조회/승인 ────────→ [비즈메타 WAS]
     │                                            │
     ├── 품질 규칙·실행결과·이슈 조회 ───────→ [데이터 품질 WAS]
     │                                            │
     └── Lineage·변경 영향도 조회 ───────────→ [데이터 흐름 WAS]
                                                  │
             ┌────────────────────────────────────┤
             ▼                                    ▼
      [데이터거버넌스 DB]                 [FOS / 수집 인터페이스]
      - 표준/용어/도메인                  - 스키마·메타 파일

      - Lineage 관계                      - ETL·배치 산출물
      - 승인/조치/감사이력                - 수집 실패 재처리

※ 데이터거버넌스 DB는 저장소 보완 증적이며 원본 이미지에는 직접 표시되지 않음.
```

                     │ 정상                                      │ 위반
                     ▼                                           ▼

                                                                 │

### 3.5 데이터 흐름(Lineage) 처리 흐름

```text
[Source Table/File/API]
          │
          ▼
[CDC / ETL / Batch / SQL Transformation]
          │
          ▼
[RDW / ADW / Data Mart / Dataset]
          │
          ▼
[BI포탈 / Self-BI / OLAP / Report]

Lineage Edge:
Source Column ──transform rule──> Target Column ──used by──> Report Metric

변경 요청 발생
   └─→ 하류 영향도 탐색
       ├─ 영향 테이블·컬럼
       ├─ 영향 ETL/배치
       ├─ 영향 BI Dataset/Report
       └─ 데이터 오너·담당자 통보
```

### 3.6 FOS 파일 수집의 안전한 처리

```text
[대내 시스템]
     │ 파일 생성
     ▼
   [FOS]
     │ 수신 식별자·파일명·크기·해시
     ▼
[격리 Landing]
     │ 백신/확장자/인코딩/무결성 검증
     ▼
[Parser·Schema Validation]
     ├─ 성공 → [Staging] → [메타/품질/Lineage 반영]
     └─ 실패 → [Quarantine] → 오류 통보 → 수정/재처리

처리 완료 후: 원본 보존·파기 정책 + 처리 건수 + 해시 + 재처리 이력 기록
```

## 4. 핵심 컴포넌트 상세 분석

### 4.1 비즈메타/데이터 품질 WAS

이미지는 하나의 WAS 블록으로 표현하지만 논리적으로 두 기능군을 가진다.

| 기능군 | 주요 책임 | 대표 관리 객체 | 핵심 통제 |
|---|---|---|---|
| 비즈메타 | 업무 용어와 기술 데이터 연결 | 표준어, 용어, 도메인, 코드, 데이터셋, 오너 | 중복·동의어, 승인, 버전 |
| 표준 관리 | 명명·타입·길이·코드 기준 | 표준 단어, 컬럼 표준, 데이터 분류 | 표준 위반 탐지 |
| 데이터 품질 | 규칙 정의·실행·결과·이슈 관리 | Rule, Threshold, Result, Issue | 오탐, 임계치, 재검증 |
| 스튜어드십 | 책임자와 승인 흐름 관리 | Owner, Steward, Approver | 역할 분리, 대리 승인 |
| 검색·카탈로그 | 데이터 검색과 활용 문맥 제공 | Dataset, Report, Term, Tag | 민감정보 노출 통제 |

**분리해야 하는 책임**

- 규칙을 정의·승인하는 Control Plane과 대량 품질 SQL을 실행하는 Execution Plane
- 운영자가 사용하는 관리 기능과 일반 사용자의 조회 기능
- 메타 변경 트랜잭션과 장시간 품질 점검 작업

### 4.2 데이터 흐름 WAS

| 책임 | 설명 | 필요한 입력 | 산출물 |
|---|---|---|---|
| 기술 Lineage | 테이블·컬럼·파일·Job 간 관계 구성 | SQL, ETL 메타, 배치 정의, 파일 스키마 | Node/Edge 그래프 |
| 업무 Lineage | 업무 용어·지표와 기술 객체 연결 | 비즈메타, Dataset, Report | 업무 관점 흐름 |
| 영향도 분석 | 변경 대상의 상·하류 영향 탐색 | Lineage Graph, 버전 | 영향 객체·담당자 목록 |
| 흐름 비교 | 배포 전후 관계 변화 탐지 | 이전/신규 Snapshot | 추가·삭제·변경 Edge |
| 가시화 | Source부터 BI까지 경로 표시 | 그래프·권한 정보 | 사용자별 Lineage View |

Lineage는 단순한 그림이 아니라 변경관리 판단 자료다. `Column → Transform → Column → Dataset → Report` 수준의 연결과 수집 시각·버전·신뢰도를 보존해야 한다.

### 4.3 패키지 UI

- 비즈메타 검색·등록·승인
- 품질 규칙·실행 결과·이슈·조치 현황 조회
- Lineage 탐색·변경 영향도 확인
- 관리자 기능과 조회 전용 기능의 권한 분리
- 대량 결과는 화면에서 직접 생성하지 않고 비동기 Job·파일 다운로드 방식 고려

### 4.4 SSO

- 사용자의 신원을 인증하고 그룹·조직·역할 Claim을 전달한다.
- SSO 로그인 성공이 모든 거버넌스 데이터 접근 허용을 뜻하지 않는다.
- `관리자`, `메타 오너`, `스튜어드`, `품질 담당`, `감사자`, `조회자` 권한을 분리해야 한다.
- 민감 메타·품질 오류 샘플·접속정보는 객체 단위 또는 속성 단위로 추가 통제한다.

### 4.5 FOS

- 파일 송수신 접점이며 메타와 품질을 직접 판정하는 주체가 아니다.
- 전달 보장, 재전송, 파일 식별, 무결성 확인, 보관·파기 이력을 제공해야 한다.
- 파일명만으로 중복을 판정하지 말고 업무키·생성시각·해시·순번을 조합한다.
- 수신 파일은 즉시 반영하지 않고 Landing·검증·Staging 단계를 거친다.

### 4.6 데이터거버넌스 DB — 저장소 보완 구성

| 데이터 영역 | 예시 | 운영 원칙 |
|---|---|---|
| 비즈메타 | 용어·도메인·코드·데이터셋·오너 | 승인·버전·유효기간 |
| 기술메타 | 시스템·DB·Schema·Table·Column·Job | 수집원·수집시각·신뢰도 |
| 품질 | 규칙·대상·실행·결과·이슈·조치 | 원본 결과와 조치 이력 분리 |
| Lineage | Node·Edge·Transformation·Snapshot | 버전별 그래프 재현 |
| 보안 | 분류등급·민감도·접근정책 | 최소권한·마스킹 |
| 감사 | 변경 전후값·승인자·처리시각 | 운영 직접 DML 금지 |

이 DB에는 업무 원천의 전체 레코드를 복제하지 않는다. 품질 오류 표본이 필요하면 최소 범위·마스킹·보존기간·접근권한을 별도로 정의한다.

---

## 5. BM·DQ·DL 논리 업무 분류

저장소의 시스템 그룹 정의는 데이터거버넌스를 다음과 같이 분류한다.

| 코드 | 업무 | 논리 소유 컴포넌트 | 설명 |
|---|---|---|---|
| `CO` | Common | 공통/비즈메타·품질 WAS | 공통 관리 기능 |
| `BM` | Biz-Meta | 비즈메타/데이터 품질 WAS | 비즈니스 메타 관리 |
| `DQ` | Data Quality | 비즈메타/데이터 품질 WAS | 데이터 품질 규칙·점검·이슈 |
| `DL` | Data Lineage | 데이터 흐름 WAS | 데이터 흐름·영향도 |

다른 저장소 증적에는 데이터 흐름 서버 업무코드가 `DF`로도 나타난다. `DL`과 `DF`의 최종 표준 코드는 서버 인벤토리·CMDB·배포명세를 대조해 확정해야 한다.

## 6. 연계 메커니즘 분석

### 6.1 권장 연계 매트릭스

| Source | Target | 전달 내용 | 권장 방식 | 판정 |
|---|---|---|---|---|
| 패키지 UI | 두 WAS | 조회·등록·승인·조치 요청 | HTTPS + SSO | 이미지 사실 + 해석 |
| 원천/RDW/ADW | 비즈메타·품질 | Schema/Table/Column, 품질 대상 | Scanner/JDBC/API | 해석 |
| ETL/CDC/배치 | 데이터 흐름 WAS | Job·Step·Source/Target·변환식 | API/File/Metadata Adapter | 해석 |
| BI포탈/Self-BI/OLAP | 데이터 흐름 WAS | Dataset·Metric·Report 의존관계 | API/File | 해석 |
| 대내 시스템 | FOS | 메타·품질·Lineage 파일 | Managed File Transfer | 이미지 사실 + 해석 |
| 두 WAS | 데이터거버넌스 DB | 정의·규칙·결과·관계·이력 | 전용 DB 계정 | 저장소 증적 + 해석 |

### 6.2 동기와 비동기 경계

- 화면 검색·단건 승인·Lineage 탐색은 동기 API가 적합하다.
- 전사 스키마 수집, 대량 품질 점검, 전체 Lineage 재구성은 비동기 Job으로 처리한다.
- 긴 작업은 `요청 → Job ID → 진행상태 → 결과` 계약을 사용한다.
- 재실행 시 동일 결과가 중복 등록되지 않도록 Source ID·Snapshot ID·Rule Run ID를 멱등키로 사용한다.

### 6.3 실패와 재처리

```text
수집 요청
  ├─ 연결 실패      → Retry(제한) → 실패 큐 → 운영 통보
  ├─ 인증 실패      → 즉시 중단 → 계정/권한 조치
  ├─ Schema 불일치  → Quarantine → Mapping 보정
  ├─ 일부 객체 실패 → 성공/실패 분리 저장 → 실패 객체만 재처리
  └─ 전체 성공      → Snapshot 확정 → 검색/Lineage 게시
```

## 7. 운영·보안·가용성 분석

### 7.1 보안

- SSO 인증 뒤 역할기반 접근제어와 데이터 객체별 권한을 적용한다.
- DB 접속정보·개인정보 분류·품질 오류 샘플은 암호화 또는 마스킹한다.
- 메타 변경, 품질 규칙 변경, 승인, 다운로드, Lineage 수정은 감사로그를 남긴다.
- Scanner 계정은 읽기 전용·대상 Schema 제한·접속시간 제한을 기본으로 한다.
- FOS 파일은 전송 암호화, 해시 검증, 악성코드 검사, 보존·파기 정책을 적용한다.

### 7.2 가용성과 장애 격리

- 비즈메타/품질 WAS 장애와 데이터 흐름 WAS 장애가 서로 전파되지 않도록 프로세스·Pool·Job Queue를 분리한다.
- 품질 대량 SQL이 원천 DB와 RDW/ADW 운영 부하를 침해하지 않도록 전용 계정, Resource Group, 실행창, 타임아웃을 둔다.
- Lineage 전체 재수집 중에도 마지막 확정 Snapshot 조회가 가능해야 한다.
- DB 백업에는 데이터뿐 아니라 규칙, Lineage 버전, 승인·감사이력이 포함되어야 한다.
- 상위 Zone 기준상 DR 즉시 기동 대상에서 제외될 수 있지만 백업·사후 복구까지 제외된다는 뜻은 아니다.

### 7.3 관측 지표

| 영역 | 핵심 지표 | 대표 경보 |
|---|---|---|
| 메타 수집 | 대상 대비 수집률, 실패 객체 수, 최신성 | 수집률 하락, SLA 초과 |
| 품질 | Rule 성공률, 위반 건수/비율, 미조치 이슈 | 임계치 초과, 장기 미조치 |
| Lineage | 연결률, 고아 Node, 미해석 변환식 | 연결률 급락, Snapshot 실패 |
| WAS | TPS, p95/p99, 오류율, Thread/Heap | 지연·오류·메모리 임계치 |
| DB | Pool, Slow Query, 저장량, 백업 | Pool 고갈, 백업 실패 |
| FOS | 수신 지연, 중복, 검증 실패, 재처리 | 파일 미수신·해시 불일치 |
| 보안 | 인증 실패, 권한거부, 관리자 변경 | 반복 실패, 비인가 변경 |

## 8. 현재 TCF 저장소와의 대응

| 관점 | 저장소 근거 | 대응 해석 |
|---|---|---|
| 거버넌스 목적 | `zdocs-1/architecture/47-data-governance.md` | 데이터 소유·접근·품질·보존·변경 원칙 |
| 논리 DB 분리 | RDW/ADW/SESSIONDB/LOGDB/OMDB | 거버넌스가 각 DB의 소유·접근 정책을 횡단 관리 |
| 기준정보 SoT | OM Catalog·Control·Code·Message | 메타 등록·승인·이력 원칙과 정합 |
| 데이터 품질 | 정확성·완전성·일관성·적시성·유일성 | DQ Rule·결과·Issue 모델로 확장 가능 |
| 파일 거버넌스 | `UD_FILE_META`, 다운로드 감사 | FOS 파일의 메타·감사·보존 정책과 연결 |
| 시스템 분류 | DG / CO·BM·DQ·DL | 두 WAS의 논리 업무 경계 보완 |

### 8.1 중요한 경계

- TCF의 `OMDB`는 서비스 Catalog·거래통제·운영 기준정보의 SoT다.
- 본 이미지의 `데이터거버넌스 시스템`은 전사 비즈메타·품질·Lineage를 다루는 별도 시스템이다.
- 두 시스템은 메타데이터를 다룬다는 공통점이 있지만 동일 시스템으로 합쳐 해석하면 안 된다.
- OM 기준정보를 전사 거버넌스에 연계할 경우 Source of Truth, 동기화 방향, 변경 승인권자, 충돌 해결 규칙이 필요하다.

### 8.2 현재 확인되는 공백

- 거버넌스 DB의 물리 구성과 스키마
- 원천별 Scanner/Adapter와 접속계정 정책
- BM·DQ·DL 간 공통 식별자와 객체 모델
- 품질 실행 Engine 및 Scheduling 위치
- ETL/BI Lineage 수집 정확도와 수동 보정 절차
- 운영·개발·DR별 구성, 복제, RTO/RPO

## 9. 설계·운영 검증 시나리오

1. SSO 로그인 후 사용자 역할별 메뉴와 데이터 객체가 정확히 제한되는지 확인한다.
2. SSO 장애 시 기존 세션과 신규 로그인 정책이 정의대로 동작하는지 확인한다.
3. 표준 용어 등록→검토→승인→게시→폐기 이력이 재현되는지 확인한다.
4. 동일 의미의 중복 용어와 금지어가 등록 단계에서 탐지되는지 확인한다.
5. 기술 메타 수집 후 Schema/Table/Column 수가 원천과 대사되는지 확인한다.
6. 일부 객체 수집 실패 시 전체 Snapshot을 오염시키지 않고 실패 객체만 재처리되는지 확인한다.
7. DDL 변경 후 변경된 Column과 하류 영향 객체가 탐지되는지 확인한다.
8. Source Column부터 BI Report Metric까지 Column-level Lineage가 연결되는지 확인한다.
9. 해석할 수 없는 동적 SQL·Stored Procedure가 불명확 상태로 표시되는지 확인한다.
10. 품질 Rule 버전 변경 전후 결과를 각각 재현할 수 있는지 확인한다.
11. 품질 임계치 위반 시 이슈 생성·담당자 배정·조치·재검증·종결이 이어지는지 확인한다.
12. 품질 대량 점검이 RDW/ADW 온라인 SLA를 침해하지 않는지 부하 시험한다.
13. FOS 중복 파일 수신 시 멱등 처리되고 이력이 남는지 확인한다.
14. FOS 해시 불일치·악성 파일·Schema 오류가 Quarantine 되는지 확인한다.
15. 민감 Column과 품질 오류 표본이 비인가 사용자에게 마스킹되는지 확인한다.
16. 관리자 메타 수정과 다운로드가 감사로그에 변경 전후값으로 남는지 확인한다.
17. 데이터 흐름 WAS 재수집 실패 중 마지막 확정 Snapshot 조회가 가능한지 확인한다.
18. 거버넌스 DB 복구 후 메타·규칙·Lineage·승인·감사이력이 함께 복원되는지 확인한다.
19. OM 기준정보와 전사 거버넌스 메타 연계 시 충돌·중복·순환 동기화가 방지되는지 확인한다.
20. DR 즉시 기동 대상 제외 여부와 무관하게 백업·복구·사후 기동 절차가 검증되었는지 확인한다.

## 10. 사실·해석·미확인 분리

### 10.1 이미지에서 확인된 사실

- 데이터거버넌스 시스템은 서비스 제공 Zone에 배치된다.
- 대내 채널에 `패키지 UI`가 있다.
- 핵심 컴포넌트는 `비즈메타/데이터 품질 WAS`, `데이터 흐름 WAS`이다.
- 인프라 영역에 `SSO`가 있다.
- 대내통합 파일 영역에 `FOS`가 있다.
- 나머지 채널·채널통합·대내통합 영역은 세부 시스템이 표시되지 않았다.

### 10.2 저장소 증적으로 보완된 사실

- 데이터거버넌스 시스템 그룹 코드는 `DG`다.
- 업무는 `CO`, `BM`, `DQ`, `DL`로 분류된 자료가 있다.
- 서버 분류에는 비즈메타/데이터품질관리 WAS와 데이터흐름관리 WAS가 있다.
- 통합 분석 자료에는 `데이터거버넌스 DB`가 구성요소로 제시된다.

### 10.3 아키텍처 해석

- 패키지 UI는 두 WAS의 관리·조회 접점이다.
- FOS는 메타·품질·Lineage 파일의 송수신 경계로 활용될 수 있다.
- 두 WAS는 공통 DB를 사용하더라도 실행 자원과 대량 Job을 격리해야 한다.
- 원천→ETL/CDC→RDW/ADW→BI 연결을 수집하여 Lineage와 영향도를 제공해야 한다.

### 10.4 미확인 사항

- 제품명·버전·라이선스, Hostname, IP, Port, 물리 서버 수
- WAS/DB 이중화, Load Balancer, Session 처리
- 실제 API·JDBC·File 연계 계약
- 데이터거버넌스 DB가 첨부 이미지에서 생략된 이유
- `DL`과 `DF` 코드 중 최종 표준
- 운영 용량, 보존기간, RTO/RPO, DR 복구 우선순위

---

## 11. 최종 평가

이 구조는 데이터거버넌스를 서비스 제공 Zone의 독립 시스템으로 배치하고, `비즈메타/데이터 품질`과 `데이터 흐름`을 별도 WAS 책임으로 나눈다. 대내 사용자는 패키지 UI와 SSO를 이용하며 FOS가 파일 연계 접점으로 제시된다.

실행 가능한 운영 아키텍처로 완성하려면 이미지에 생략된 거버넌스 DB, 원천별 Metadata Adapter, 품질 실행 Engine, Lineage 수집 계약, 객체 식별체계, 권한·감사, 자원격리, 백업·복구 기준을 확정해야 한다. 가장 중요한 원칙은 거버넌스 시스템을 원천 데이터의 대체 저장소로 만들지 않고, **정의·책임·품질·흐름·변경을 검증 가능한 증적으로 연결하는 통제 계층**으로 운영하는 것이다.
