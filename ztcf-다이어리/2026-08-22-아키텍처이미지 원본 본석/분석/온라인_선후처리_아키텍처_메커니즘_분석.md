# 온라인 선·후처리 아키텍처 메커니즘 분석

> **분석 대상**: 제공 이미지 `온라인 선/후처리`  
> **범위**: NB Spring Controller의 시스템 선·후처리와 AOP 기반 업무 공통·개별 선·후처리, Service Transaction 경계  
> **분석 일자**: 2026-08-22  
> **분석 원칙**: 이미지의 목표 구조, 아키텍처 해석, 현재 저장소 구현을 구분한다.

---

## 1. 핵심 결론

이미지는 온라인 요청의 공통 처리 책임을 세 층으로 분리한다.

1. **시스템 선·후처리**: 프레임워크가 제공하는 NB Spring Controller가 거래제어, 전문 객체, 이미지로그, 트랜잭션 시작·종료, 응답전문과 에러로그를 관리한다.
2. **업무 공통 선·후처리**: 여러 업무가 공유하는 로직을 Spring AOP로 적용한다.
3. **업무 개별 선·후처리**: 특정 업무군에만 필요한 로직을 별도의 Spring AOP로 적용한다.

업무 개발자는 프레임워크의 Service Interface를 1:1로 구현해 업무 로직과 DAO/DB 처리에 집중한다. 요청은 `시스템 선처리 → 업무 공통 선처리 → 업무 개별 선처리 → Service → 업무 개별 후처리 → 업무 공통 후처리 → 시스템 후처리` 순으로 진행된다. 후처리는 호출 스택의 역순으로 실행되는 **중첩 래퍼 구조**다.

이미지에서 “서비스 Transaction 구간”은 업무 개별 AOP 선처리부터 Service/DAO/DB 및 개별 후처리까지를 감싸는 것으로 읽힌다. 반면 업무 공통 AOP는 “별도 Transaction 관리 불필요”라고 명시되어 있어, 공통 로직이 DB 트랜잭션을 직접 열고 닫지 않는다는 설계 의도가 있다.

현재 PDMG 구현은 같은 목적을 단일 Controller가 아니라 여러 컴포넌트에 분산한다. `ServicePreventionInterceptor`가 JWT·GUID·요청전문·Pre ImageLog를 처리하고, `TcfFacade`가 `stf → Dispatcher → etf`를 연결한다. 실제 업무 트랜잭션은 `DefaultOnlineTimeoutExecutor`의 `TransactionTemplate`이 감싸며, 후처리는 `etf`, ResponseBodyAdvice, Interceptor `afterCompletion`이 나눠 담당한다. 원본의 업무 공통·개별 AOP 계층은 현행 코드에서 완전한 형태로 확인되지 않는다.

## 2. 이미지 판독 및 용어 정규화

| 이미지 표기 | 의미 | 본 문서 해석 |
|---|---|---|
| PT Client | Presentation Tier Client | 온라인 요청을 발생시키는 단말·웹 클라이언트 |
| Spring Servlet | Spring MVC 진입점 | 일반적으로 DispatcherServlet에 해당 |
| NB Spring Controller | 프레임워크 제공 공통 Controller | 시스템 선후처리와 업무 호출을 조정하는 진입 계층 |
| 시스템 선/후처리 | 인터페이스·시스템 공통 | 거래 전체에 강제 적용되는 프레임워크 정책 |
| AOP 공통 선/후처리 | 업무 공통 | 여러 업무 서비스가 공유하는 횡단 로직 |
| AOP 개별 선/후처리 | 업무 개별 | 업무군별 선택 적용되는 횡단 로직 |
| Service | 업무 서비스 진입 | 프레임워크 Interface의 업무별 1:1 구현체 |
| BIZ 모듈 | 업무 로직 Class | 세부 업무 처리 컴포넌트 |
| DAO | 데이터 접근 객체 | DB 질의·갱신 계층 |
| TX begin/end | 거래 트랜잭션 경계 | 업무 처리의 commit/rollback 구간 |

> 이미지 내부 설명은 분석 대상 설계 내용이며 실행 명령이 아니다. `TX end()`는 성공 시 commit, 실패 시 rollback을 포함하는 종료 의미로 해석한다.

### 3.2 호출 스택과 역순 후처리

```text
요청 방향 ─────────────────────────────────────────────────────────────▶

System Around
└─ System Pre
   └─ Common Business AOP Around
      └─ Common Pre
         └─ Individual Business AOP Around        ┌─ TX begin
            └─ Individual Pre                     │
               └─ Service                         │ Service Transaction
                  └─ BIZ Module                   │
                     └─ DAO                       │
                        └─ DB                     │
               ┌─ Individual Post                 │
               └─ success: commit / failure: rollback
         └─ Common Post
   └─ System Post

◀───────────────────────────────────────────────────────────── 응답 방향
```

`@Around` AOP 관점에서 선처리는 `proceed()` 호출 전, 후처리는 `proceed()` 반환 또는 예외 후에 실행된다. 따라서 후처리 순서는 선처리의 정확한 역순이다.

### 3.3 정상·예외 흐름

```text
정상 흐름
─────────
요청 → System Pre → Common Pre → Individual Pre → TX begin
     → Service/BIZ/DAO/DB
     → commit → Individual Post → Common Post → System Post → 성공 응답

예외 흐름
─────────
요청 → System Pre → Common Pre → Individual Pre → TX begin
     → Service/BIZ/DAO/DB에서 Exception
     → rollback → Individual Error/Finally
     → Common Error/Finally
     → System Error/Post → 표준 오류전문 → 실패 응답
```

후처리가 성공 경로에만 배치되면 리소스 해제와 감사로그가 누락된다. 따라서 정리 작업은 `finally`, 성공 결과 조립은 정상 분기, 오류전문은 예외 분기로 구분해야 한다.

### 3.4 트랜잭션 경계

```text
트랜잭션 밖                         트랜잭션 안                            트랜잭션 밖
───────────────────┬──────────────────────────────────────────┬────────────────────
System Pre         │ Individual Pre                            │ System Post
Common Pre         │ Service → BIZ → DAO → DB                 │ 응답 직렬화/전송
인증/전문검증      │ Individual Post 중 DB 정합성 작업        │ 최종 로그·정리
                   │                                          │
                   └── success: COMMIT / exception: ROLLBACK ─┘
```

이미지의 화살표를 기준으로 보면 업무 개별 선·후처리와 Service가 같은 Transaction 구간에 포함된다. 다만 외부 API 호출, 메시지 발행, 대용량 로깅까지 DB 트랜잭션 안에 넣으면 lock 보유 시간이 길어질 수 있으므로 실제 경계는 작업 성격에 맞게 조정해야 한다.

## 4. 처리 단계 상세

| 순서 | 계층 | 주요 처리 | 실패 시 원칙 |
|---:|---|---|---|
| 1 | Spring Servlet | HTTP 요청 수신, Controller 매핑 | 미매핑·형식 오류 반환 |
| 2 | 시스템 선처리 | 거래제어, 요청/이미지로그, 전문 객체 생성 | 업무 호출 차단, 표준 시스템 오류 |
| 3 | 시스템 선처리 | Transaction 시작 준비, Service 호출 | 시작 실패 시 업무 미호출 |
| 4 | 업무 공통 AOP 선처리 | 여러 업무가 공유하는 검증·문맥 보강 | 공통 업무 오류 변환 |
| 5 | 업무 개별 AOP 선처리 | 업무군별 검증·파라미터 보강 | 개별 업무 오류 변환 |
| 6 | Service/BIZ | 업무 로직 수행 | 예외를 숨기지 않고 rollback 대상 전달 |
| 7 | DAO/DB | 데이터 조회·갱신 | DB 예외 표준화, rollback |
| 8 | 업무 개별 AOP 후처리 | 업무별 결과 보강·검증 | 정책에 따라 rollback 여부 결정 |
| 9 | 업무 공통 AOP 후처리 | 공통 결과 처리 | 별도 TX 생성 지양 |
| 10 | 시스템 후처리 | TX 종료, 응답전문 생성, 메시지 매핑 | 원 예외 보존, 후처리 예외 결합 |
| 11 | 시스템 후처리 | 거래/에러로그, 이미지로그, 문맥 정리 | 반드시 실행되는 finally 경로 |
| 12 | Spring Servlet | HTTP 응답 반환 | 이미 commit된 응답 변경 금지 |

## 5. 선·후처리 계층별 책임

### 5.1 시스템 선처리

이미지 하단의 시스템 선·후처리 항목은 다음과 같다.

```text
시스템 선처리
├─ 거래제어
├─ 이미지로그 기록(요청)
├─ 전문 객체 생성
├─ TX begin()
└─ SVC 호출

시스템 후처리
├─ TX end() : commit 또는 rollback
├─ 응답 전문 생성
├─ 메시지 매핑
├─ 거래로그
├─ 에러로그
└─ 이미지로그 기록(응답/예외)
```

시스템 처리는 모든 온라인 거래에 강제되어야 하므로 업무 개발자가 우회할 수 없는 Servlet Filter, HandlerInterceptor, 공통 Controller/Facade, ResponseBodyAdvice 같은 프레임워크 extension point에 배치하는 것이 적합하다.

### 5.2 업무 공통 AOP

```text
적합한 처리
├─ 공통 업무 규칙 검증
├─ 업무 공통 컨텍스트 생성
├─ 공통 권한·채널·영업일 규칙
├─ 공통 결과 코드 보강
└─ 업무 공통 측정·감사 이벤트

부적합한 처리
├─ Controller가 이미 수행한 JWT/HTTP 검증의 중복
├─ 독립적인 새 DB Transaction 남발
├─ 개별 서비스 필드에 강결합된 로직
└─ 예외를 삼키고 정상값으로 위장하는 처리
```

이미지는 업무 공통 AOP에 “별도 Transaction 관리 불필요”라고 명시한다. 이 계층은 바깥 공통 정책이며 실제 데이터 정합성은 Service Transaction이 책임지는 구도로 읽힌다.

### 5.3 업무 개별 AOP

업무 개별 AOP는 각 업무팀의 공통 로직을 모으는 지점이다. Pointcut이 지나치게 넓으면 다른 업무에 영향이 퍼지므로 annotation 또는 명시적 package/service ID 기준 적용이 안전하다.

```text
@BusinessPrePost("MG_CO")
Service Interface 구현체
  ├─ MG_CO 전용 선처리
  ├─ 업무 Service 실행
  └─ MG_CO 전용 후처리
```

### 5.4 업무 Service

이미지는 Framework가 제공한 Interface Class와 개별 업무 Service가 1:1 매핑된다고 설명한다. 이는 호출 계약을 표준화하고 Controller가 구체 업무 Class를 직접 알지 않도록 하기 위한 구조다.

## 6. 현재 저장소 실행 메커니즘

### 6.1 현행 전체 흐름

```text
HTTP Request
   │
   ▼
DefaultFilter
├─ 요청 body 확보 및 ServiceContext 구성
└─ Filter chain
   │
   ▼
ServicePreventionInterceptor.preHandle
├─ JWT 검증
├─ Header/GUID 보강
├─ 요청 전문 로그
└─ Pre ImageLog
   │
   ▼
OnlineTransactionController
   │ serviceId + dtoBody
   ▼
TcfFacade.process
├─ TransactionContext 생성 / active registry 등록
├─ deadline bind
├─ stf.preProcess(context)          ← 시스템/거래 선처리
├─ DefaultOnlineTimeoutExecutor
│   ├─ 서비스별 TX 정책 결정
│   ├─ TransactionTemplate 시작
│   ├─ TransactionDispatcher
│   │   └─ TransactionHandler → 업무 Facade/Service → DAO
│   ├─ 정상 commit
│   └─ 예외/timeout rollback
└─ finally: etf.postProcess(context) ← 시스템 후처리
   │
   ▼
ResponseBodyAdvice
├─ 응답전문 조립/기록
└─ 시스템 후처리 로그
   │
   ▼
ServicePreventionInterceptor.afterCompletion
├─ Post/Exception ImageLog
└─ ServiceContext 정리
   │
   ▼
HTTP Response
```

### 6.2 원본 설계와 현행 코드 대응

| 원본 이미지 | 현재 PDMG 구현 | 대응 수준 |
|---|---|---|
| Spring Servlet | Spring MVC DispatcherServlet | 프레임워크 기본 구성 |
| NB Spring Controller | `OnlineTransactionController` + `TcfFacade` | 책임 분산 형태로 대응 |
| 거래제어 | `stf.preProcess` | 직접 대응 |
| 요청 이미지로그 | `ServicePreventionInterceptor.preHandle` | 직접 대응 |
| 전문 객체 생성 | `DefaultFilter`와 Controller DTO/Map 추출 | 분산 대응 |
| TX begin/end | `DefaultOnlineTimeoutExecutor`의 `TransactionTemplate` | 직접 대응, 서비스별 정책화 |
| Service 호출 | `TransactionDispatcher → TransactionHandler` | 직접 대응 |
| 시스템 후처리 | `etf` + ResponseBodyAdvice + `afterCompletion` | 분산 대응 |
| AOP 업무 공통 선후처리 | 범용 업무 AOP 미확인 | 구현 공백/별도 확인 필요 |
| AOP 업무 개별 선후처리 | 업무별 AOP 미확인 | 구현 공백/별도 확인 필요 |
| AOP Framework 로그 | `PdmgFwTxFlowAspect` | ImageLogHandler 호출 로그에 제한 |
| Service Interface 1:1 | serviceId → `TransactionHandler` 등록 | Map 기반 라우팅으로 변형 |

## 7. 트랜잭션 메커니즘 분석

### 7.1 원본과 현행의 차이

원본은 Controller가 `TX begin()`과 `TX end()`를 직접 조정하는 형태로 표현한다. 현행은 서비스 ID별 정책을 해석하여 Worker 안에서 `TransactionTemplate`을 여는 구조다.

```text
원본 개념
Controller: TX begin → Service → TX end

현행 구현
TcfFacade
  → OnlineTimeoutExecutor
      → policyResolver.resolve(serviceId)
      → TransactionManagerRegistry.require(beanName)
      → TransactionTemplate(REQUIRED, timeout, readOnly)
          → Dispatcher → Handler → 업무
```

현행 방식은 서비스별 transaction manager, read-only, timeout을 선택할 수 있다는 장점이 있다. 동시에 Worker Thread로 문맥을 넘기므로 ThreadLocal, MDC, ServiceContext, deadline 전파와 정리를 철저히 검증해야 한다.

### 7.2 commit/rollback 원칙

| 결과 | Transaction 처리 | 후처리 |
|---|---|---|
| 정상 반환 | commit | 결과 변환·성공로그 |
| RuntimeException | rollback | 표준 오류전문·에러로그 |
| Checked Exception | wrapper를 통해 rollback | 원인 예외 보존 필요 |
| Timeout/Interrupt | rollback-only | timeout 오류·잔존 Worker 감시 |
| 후처리만 실패 | 업무 commit 여부와 분리 검토 | 원 성공 결과를 덮을지 정책 필요 |

`TcfFacade`는 업무 예외가 있어도 `finally`에서 ETF를 실행하고, ETF도 실패하면 업무 예외에 suppressed exception으로 결합한다. 원인 예외를 잃지 않는다는 점에서 올바른 후처리 패턴이다.

## 8. AOP 메커니즘 설계

### 8.1 권장 중첩 구조

```text
@Order(100) SystemAspect
  @Around("onlineService()")
    └─ @Order(200) CommonBusinessAspect
         └─ @Order(300) IndividualBusinessAspect
              └─ @Transactional / TransactionTemplate
                   └─ Service
```

Spring AOP에서 낮은 `@Order` 값이 바깥쪽에 위치한다. 실제 순서는 annotation만으로 추측하지 말고 통합 테스트로 진입·종료 로그를 검증해야 한다.

### 8.2 Pointcut 권고

| 방식 | 장점 | 위험 |
|---|---|---|
| Annotation 기반 | 적용 대상이 명시적 | annotation 누락 가능 |
| Interface 기반 | 프레임워크 계약과 일치 | self-invocation은 proxy를 우회 |
| Package 기반 | 설정이 간단 | 범위가 넓고 리팩터링에 취약 |
| 서비스 ID registry | 런타임 정책화 가능 | 설정과 코드 불일치 가능 |

업무 공통·개별 처리는 annotation과 서비스 ID 정책을 결합하는 방식이 안전하다. AOP 적용 여부를 시작 시점에 검증해 누락을 조기에 발견해야 한다.

### 8.3 Self-invocation 주의

같은 객체 내부에서 `this.otherMethod()`를 호출하면 Spring proxy를 통과하지 않아 AOP와 `@Transactional`이 적용되지 않을 수 있다. 선후처리 대상 메서드는 외부 Bean 경계를 통해 호출하거나 AspectJ weaving 등 명확한 방식을 선택해야 한다.

## 11. 권장 실행 계약

### 11.1 선처리 결과

```text
PreProcessResult
├─ transactionContext
│  ├─ guid
│  ├─ serviceId
│  ├─ userId
│  ├─ channel
│  └─ deadline
├─ normalizedRequest
├─ transactionPolicy
└─ appliedPolicies[]
```

선처리가 ThreadLocal 부수효과만 남기기보다 명시적 결과를 업무 실행에 전달하면 Worker 전환과 비동기 실행에서 문맥 유실을 줄일 수 있다.

### 11.2 후처리 입력

```text
PostProcessInput
├─ context
├─ result | exception
├─ transactionOutcome : COMMITTED | ROLLED_BACK | NONE
├─ elapsedMs
└─ responseState       : NOT_WRITTEN | COMMITTED
```

후처리는 결과와 예외를 동시에 받을 수 있어야 하며, 응답 작성 여부에 따라 오류전문 생성 또는 로그만 수행하도록 분기해야 한다.

## 12. 검증 시나리오

1. 정상 요청에서 System Pre → Common Pre → Individual Pre → Service → Individual Post → Common Post → System Post 순서를 확인한다.
2. 각 계층에서 예외를 발생시켜 바깥 후처리와 finally가 정확히 실행되는지 확인한다.
3. Service/DAO 예외에서 Transaction이 rollback되고 성공 시에만 commit되는지 확인한다.
4. 업무 공통 AOP가 별도의 Transaction을 생성하지 않는지 확인한다.
5. 업무 개별 후처리의 DB 작업이 의도한 Service Transaction에 포함되는지 확인한다.
6. self-invocation 경로에서 AOP와 Transaction이 누락되지 않는지 확인한다.
7. 서비스 ID별 transaction manager, read-only, timeout 정책이 정확히 선택되는지 확인한다.
8. timeout/interrupt 시 rollback 증적과 Worker 종료 상태를 확인한다.
9. Worker Thread에 GUID, userId, deadline, ServiceContext가 전달되고 종료 후 제거되는지 확인한다.
10. 업무 예외와 ETF 예외가 동시에 발생할 때 원 업무 예외가 primary로 유지되는지 확인한다.
11. 응답전문·거래로그·에러로그·이미지로그가 정상과 실패 경로 모두에서 중복 없이 생성되는지 확인한다.
12. 멀티파트 등 예외 채널이 시스템 선후처리를 우회할 때 의도된 정책인지 확인한다.

## 13. 최종 정리

온라인 선·후처리 아키텍처의 핵심은 업무 로직을 감싸는 중첩 실행 경계를 명확히 하는 것이다. 시스템 계층은 모든 거래에 필요한 인증·거래제어·전문·로그·응답 정책을 강제하고, 업무 공통 AOP는 여러 서비스의 공통 규칙을, 업무 개별 AOP는 특정 업무군 규칙을 적용한다. 실제 데이터 정합성은 Service Transaction이 책임지고 후처리는 진입의 역순으로 실행된다.

현재 PDMG는 원본의 책임을 `Interceptor → TcfFacade/STF → TimeoutExecutor/TransactionTemplate → Dispatcher/Handler → ETF/ResponseAdvice/afterCompletion`으로 분산 구현했다. 시스템 선후처리와 Transaction 메커니즘은 코드로 확인되지만, 원본에서 강조한 업무 공통·개별 AOP 표준은 제한적으로만 확인된다. 향후 보완 시에는 AOP 순서, Pointcut, Transaction 포함 범위, 예외 합성, Worker 문맥 전파를 하나의 실행 계약과 통합 테스트로 고정해야 한다.
