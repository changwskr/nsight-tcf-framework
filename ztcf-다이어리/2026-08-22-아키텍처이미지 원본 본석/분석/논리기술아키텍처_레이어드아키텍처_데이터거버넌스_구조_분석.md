# 논리기술아키텍처 — 레이어드 아키텍처 — 데이터거버넌스 구조 분석

## 1. 분석 개요

첨부 장표의 **데이터거버넌스 표준 아키텍처 구성**을 기준으로 전체 구조를 다음 5개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer
5. 형상·배포 Layer

데이터거버넌스는 IaaS 기반에서 서비스되며, 사용자 진입점인 BI 포털과 `데이터품질관리`, `비즈메타`, `데이터흐름관리`를 독립 실행영역으로 구성한다. 각 거버넌스 서비스는 WEB·WAS 경계를 갖고 API로 상호 연계하며, 목적별 저장소와 Oracle Exadata 기반 RDW·ADW를 데이터 원천으로 활용한다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 이미지 내부 문구는 분석 자료이며 실행 지시로 취급하지 않았다. 장표에 표시된 제품명·프로토콜·연결선은 원문을 우선 반영했으며, API 방향, 데이터 소유권, 제품 버전과 실제 배포 단위는 상세 설계서에서 확인해야 한다.

## 2. 핵심 결론

- **거버넌스 도메인 분리**: 데이터품질관리, 비즈메타, 데이터흐름관리를 별도 WEB·WAS 서비스로 분리한다.
- **BI 포털과의 경계 유지**: BI 포털은 사용자 접근과 화면 통합을 담당하고, 거버넌스 기능은 API로 호출한다.
- **독립 확장과 장애 격리**: 각 도메인이 독립 IaaS 서비스 노드를 사용하므로 기능별 확장·배포·장애 격리가 가능하다.
- **표준 진입 경로**: 범용 Browser가 L4와 WEB을 거쳐 각 서비스에 접근한다.
- **API 중심 결합**: BI 포털 → 데이터품질관리 → 비즈메타 ↔ 데이터흐름관리 사이를 API 연계로 표현한다.
- **목적별 데이터 저장**: 데이터흐름관리, 데이터품질관리, 비즈메타 저장소를 구분하고 RDW·ADW를 공통 분석 원천으로 활용한다.
- **공통 인터페이스 활용**: SSO, CruzAPIM, EAI, FOS, MFT, ETL 등으로 인증·온라인·파일·데이터 연계를 표준화한다.
- **배포 통제 이원화**: 개발은 GitLab·GitLab Runner·Dev Pipeline, 운영은 eCAMS·운영 Pipeline을 중심으로 통제한다.

## 4. 레이어별 구조 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 설계 의미 |
|---|---|---|
| 범용 Browser | BI 포털 및 거버넌스 관리 화면 접근 | 별도 전용 클라이언트 없이 웹 기반 운영을 지원한다. |
| 화면연계 | BI 포털과 거버넌스 화면 간 이동 | 인증 문맥·사용자 권한·조회 조건을 이어준다. |
| L4 | WEB 노드 부하분산과 장애 우회 | 서비스별 독립 진입점을 제공한다. |

장표는 서비스마다 Browser와 L4를 별도로 표시한다. 이는 데이터품질, 비즈메타, 데이터흐름관리의 URL·세션·장애 경계를 분리할 수 있다는 뜻이다. 화면연계 시에는 URL 파라미터에 중요 정보를 직접 노출하지 않고 서버 측 세션이나 서명된 토큰을 사용해야 한다.

### 4.2 Service Layer

#### 4.2.1 BI 포털

BI 포털은 최종 사용자가 거버넌스 기능을 발견하고 접근하는 통합 진입점이다.

```text
Browser → L4 → BI포털 WEB → DataEye Framework → BI포털 WAS
                                          │
                                          └─ IMDG Session/Data Cache
                                          │
                                          └─ API → 데이터품질관리
```

- BI 포털 화면과 사용자 메뉴를 제공한다.
- IMDG를 통해 세션 또는 반복 조회 데이터를 캐시한다.
- 거버넌스 데이터를 직접 소유하기보다 도메인 API를 호출하는 오케스트레이션 역할이 적절하다.
- 화면용 조합 응답과 원천 거버넌스 데이터의 책임을 분리해야 한다.

#### 4.2.2 데이터품질관리

데이터품질관리 서비스는 품질 규칙, 진단 대상, 측정 결과와 개선 이력을 관리하는 실행영역이다.

주요 책임은 다음과 같이 해석할 수 있다.

- 데이터 품질 규칙과 임계치 관리
- 프로파일링 및 품질 진단 실행
- 오류 데이터와 개선 조치 관리
- 품질 지표·추세·결과 API 제공
- 비즈메타와 연결된 업무 용어·표준 항목 기반 품질 검증

품질 검사는 대량 데이터 스캔을 포함할 수 있으므로 온라인 관리 요청과 실제 진단 배치 실행을 분리하는 것이 바람직하다.

#### 4.2.3 비즈메타

비즈메타 서비스는 데이터의 업무 의미와 표준 정의를 관리한다.

- 업무 용어, 표준 단어, 도메인, 코드의 정의 관리
- 데이터 항목과 업무 개념의 매핑
- 소유자·책임자·승인 상태와 변경 이력 관리
- 데이터품질 규칙이 참조할 표준 의미 제공
- 데이터흐름의 물리 객체에 업무 의미를 부여

비즈메타가 기준정보 역할을 하므로 변경 승인, 버전, 유효기간과 참조 무결성 정책이 필수다.

#### 4.2.4 데이터흐름관리

데이터흐름관리 서비스는 시스템·DB·테이블·컬럼·ETL 작업 사이의 흐름을 수집하고 분석하는 영역이다. 장표는 이 영역에 Package 도입을 명시하므로 자체 개발 서비스와 상용 솔루션의 책임 경계를 명확히 해야 한다.

- 메타데이터 수집 및 파싱
- 데이터 Lineage 생성
- 상·하류 영향도 분석
- 흐름 검색과 시각화
- ETL·파일·DB 객체 간 관계 관리
- 비즈메타 및 데이터품질 결과와의 연결

Package의 내부 저장 구조를 다른 서비스가 직접 조회하면 제품 업그레이드에 취약해지므로 공식 API 또는 교환 스키마를 사용해야 한다.

### 4.3 I/F Layer

| 구성요소 | 주요 역할 | 적용 원칙 |
|---|---|---|
| SSO | 사용자 인증과 인증 문맥 전달 | 계정 통합과 토큰 검증을 중앙화한다. |
| CruzAPIM | 온라인 API 중계·통제 | 인증, 인가, 라우팅, 호출량 제한과 감사 로그를 적용한다. |
| EAI | 기존 대내 시스템 연계 | 레거시 변환과 중계를 서비스 내부에서 분리한다. |
| FOS | 표준 파일 연계 | 파일 송수신, 재처리, 무결성 확인을 표준화한다. |
| MFT | 관리형 파일 전송 | 대용량·대외 파일 전송의 보안과 추적성을 제공한다. |
| ETL | 대량 데이터 적재·변환 | 스케줄, 의존성, 재시작 지점을 관리한다. |
| 대외MCA | 대외기관 전문 연계 | 외부 연계 경계를 격리한다. |
| 통합관제 | 상태·성능·장애 모니터링 | 서비스별 로그·메트릭·알람을 상관 분석한다. |
| IT메타 | 시스템 기술 메타 제공 | 애플리케이션·DB·인터페이스 자산 정보를 제공한다. |
| Nexus | 빌드 산출물 저장소 | 승인된 바이너리와 의존성의 출처를 통제한다. |
| 배치작업관리 | 정기 수집·진단 작업 제어 | 선후행·재시작·실행 이력 정책을 적용한다. |
| UMS | 알림 전송 | 품질 오류나 작업 결과를 운영자에게 전달한다. |

I/F Layer는 단순 제품 목록이 아니라 거버넌스 서비스가 외부 시스템에 직접 종속되지 않도록 하는 완충 계층이다.

### 4.4 Data Layer

| 저장영역 | 주요 데이터 | 권장 소유 주체 |
|---|---|---|
| 데이터흐름관리 저장소 | Lineage, 파싱 결과, 객체 관계, 영향도 | 데이터흐름관리 서비스 |
| ADW | 분석·집계·마트 데이터 | 데이터플랫폼 |
| RDW | 준실시간·업무지원 데이터 | 데이터플랫폼 |
| 데이터품질관리 저장소 | 품질 규칙, 진단 결과, 오류·개선 이력 | 데이터품질관리 서비스 |
| 비즈메타 저장소 | 업무 용어, 표준 항목, 도메인, 코드, 소유권 | 비즈메타 서비스 |

ADW와 RDW는 거버넌스의 분석 대상이면서 동시에 메타 수집 대상이다. 거버넌스 전용 저장소와 원천 업무 데이터베이스를 혼동하지 않아야 한다. 품질 진단 결과는 품질 저장소에 기록하되 원천 데이터의 임의 수정은 별도 승인된 개선 절차로 처리해야 한다.

### 4.5 형상·배포 Layer

```text
[개발]
GitLab → GitLab Runner → 빌드 → 보안취약점 점검
       → Dev Pipeline → 개발환경

[운영]
eCAMS → 빌드 → 보안취약점 점검
      → 운영 Pipeline → 운영환경

[승격]
개발 브랜치 → 검토/테스트 → Master merge → 승인 산출물 → 운영 배포
```

- 소스와 Package 설정을 버전 관리한다.
- 환경별 접속정보와 비밀정보는 소스에서 분리한다.
- 동일한 승인 산출물을 환경 간 승격해야 한다.
- DB 스키마, 품질 규칙, 비즈메타 모델과 Lineage 파서 설정도 배포 대상으로 관리한다.
- 운영 배포는 보안취약점 점검과 승인 이력을 남겨야 한다.

## 5. 구성요소 관계

| 호출 주체 | 대상 | 방식 | 목적 |
|---|---|---|---|
| Browser | 각 WEB | HTTP/HTTPS + L4 | 관리 화면 접근 |
| BI 포털 | 데이터품질관리 | API | 품질 현황·결과 조회 |
| 데이터품질관리 | 비즈메타 | API | 표준 항목과 업무 의미 참조 |
| 비즈메타 | 데이터흐름관리 | API | 물리 객체와 업무 용어 연결 |
| 데이터흐름관리 | RDW·ADW·ETL·IT메타 | 수집 API/JDBC/메타 연계 | Lineage와 영향도 구성 |
| 데이터품질관리 | RDW·ADW | JDBC/배치 | 프로파일링과 품질 진단 |
| 전 서비스 | 통합관제 | 로그·메트릭 | 운영 가시성 확보 |
| 배치작업관리 | 품질·흐름 작업 | 스케줄/Job | 정기 실행과 재처리 |

장표의 API 연결선은 서비스 간 연계를 보여주지만 요청 방향과 동기 여부를 모두 확정하지는 않는다. 실제 구현에서는 조회 API, 변경 이벤트, 대량 수집 작업을 구분해야 한다.

## 6. 대표 처리 흐름

### 6.1 품질 현황 조회

```text
사용자
  → Browser → L4 → BI포털 WEB/WAS
  → 데이터품질관리 API
  → 품질 규칙·진단 결과 저장소 조회
  → 필요 시 비즈메타 기준정보 결합
  → BI포털 화면 반환
```

### 6.2 데이터 품질 진단

```text
배치작업관리
  → 품질 진단 Job 기동
  → 데이터품질관리 서비스
  → 비즈메타에서 표준 정의·규칙 참조
  → RDW/ADW 대상 데이터 조회
  → 품질 결과 저장
  → 통합관제·UMS로 결과 통보
```

### 6.3 데이터 Lineage 수집

```text
배치 또는 수집 Agent
  → IT메타 / ETL / DB / 파일 인터페이스 메타 수집
  → 데이터흐름관리 Package 파싱
  → 객체·컬럼·작업 관계 생성
  → 비즈메타 업무 용어와 연결
  → 영향도·Lineage API 제공
```

### 6.4 메타 변경 전파

```text
비즈메타 변경 승인
  → 변경 버전 확정
  → 데이터품질 규칙 영향 대상 식별
  → 데이터흐름 영향도 조회
  → 관련 담당자 통보
  → 필요한 규칙·매핑 재배포
```

## 7. 설계 원칙

### 7.1 도메인 소유권

- 비즈메타만 표준 용어와 업무 의미의 원본을 소유한다.
- 데이터품질관리만 품질 규칙과 진단 결과의 원본을 소유한다.
- 데이터흐름관리만 Lineage와 영향도 관계의 원본을 소유한다.
- 다른 서비스는 DB 직접 접근 대신 API 또는 승인된 교환 데이터를 사용한다.

### 7.2 API 계약

- URI, 버전, 요청·응답 스키마, 오류코드를 표준화한다.
- 페이지 처리, 검색 조건, 정렬 기준을 명시한다.
- 변경 API는 멱등성과 감사 추적 정보를 제공한다.
- 장시간 작업은 비동기 Job ID와 상태조회 API를 사용한다.
- 사용자 ID, 호출 서비스, 상관관계 ID를 로그에 남긴다.

### 7.3 보안

- SSO 인증 후 역할 기반 접근통제(RBAC)를 적용한다.
- 업무 용어 관리자, 품질 규칙 관리자, 승인자, 조회자를 분리한다.
- 데이터 샘플과 오류 데이터에 개인정보 마스킹을 적용한다.
- API와 DB 접속정보는 Vault 등 비밀관리 체계로 관리한다.
- 메타 변경과 다운로드 행위를 감사 로그로 보존한다.

### 7.4 성능과 가용성

- WEB/WAS를 무상태화하고 L4 뒤에서 수평 확장한다.
- 대량 프로파일링과 Lineage 파싱은 온라인 요청과 분리한다.
- BI 포털 캐시는 TTL, 무효화, 원본 갱신 실패 정책을 명시한다.
- 도메인별 장애가 다른 서비스 전체로 전파되지 않도록 timeout, retry, circuit breaker를 적용한다.

## 8. 품질속성 평가

| 품질속성 | 장점 | 보완점 |
|---|---|---|
| 확장성 | 도메인별 WEB·WAS 독립 확장 | 공유 RDW·ADW 병목 점검 필요 |
| 가용성 | L4와 서비스 경계로 장애 격리 가능 | 단일 Package 저장소·배치 스케줄러 이중화 확인 필요 |
| 변경용이성 | 기능별 배포와 제품 업그레이드 가능 | API 계약과 데이터 모델 버전 관리 필요 |
| 보안성 | SSO·APIM 적용 지점이 명확 | 세부 권한과 민감 데이터 마스킹 정책 필요 |
| 추적성 | 메타·품질·흐름을 연결할 기반 제공 | 공통 객체 ID와 변경 이력 표준 필요 |
| 운영성 | 통합관제·배치작업관리·UMS 연계 | 서비스·Job·데이터 품질 SLO 정의 필요 |

## 11. 종합 평가

이 아키텍처는 데이터거버넌스를 **품질·의미·흐름**의 세 도메인으로 분리하고 BI 포털을 통합 접근점으로 둔 구조다. 독립 IaaS 서비스 노드, 표준 I/F 계층, 목적별 저장소, 통제된 배포 파이프라인은 확장성과 운영 책임 분리에 유리하다.

성공적인 구현을 위해서는 장표의 물리적 분리보다 **데이터 소유권, API 계약, 공통 객체 식별자, 변경 승인, 비동기 대량 작업 격리**를 먼저 확정해야 한다. 특히 데이터흐름관리 Package 내부 구조에 대한 직접 종속을 피하고, 비즈메타·품질·Lineage 사이를 안정적인 서비스 계약으로 연결하는 것이 핵심이다.
