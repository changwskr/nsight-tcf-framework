# 인터페이스 아키텍처 — 표준 인터페이스 관계도 분석

## 1. 핵심 결론

장표는 전체 시스템을 다음 5개 관계 영역으로 구분한다.

```text
[채널] → [채널 통합] → [차세대 정보계 업무 시스템]
                              ↕
                    [대내 통합 인터페이스]
                              ↕
                       [대내 연계업무]
```

차세대 정보계는 네 개의 핵심 업무영역으로 구성된다.

1. **마케팅 플랫폼**: 온라인 업무와 행동정보·실시간 마케팅 처리
2. **데이터 플랫폼**: RDW·ADW 기반 실시간 및 분석 데이터 제공
3. **BI 포탈**: 신용실적, BI 포탈, OLAP, Self-BI 제공
4. **데이터거버넌스**: 비즈메타, 데이터 품질, 데이터 흐름 관리

연계 방식은 목적에 따라 다음과 같이 분리된다.

| 연계 유형 | 표준 중계 | 대표 관계 |
|---|---|---|
| 온라인 | 영업점 MCA, MCI, API G/W, EAI, GSE | 채널·대내 업무 ↔ 정보계 |
| 이벤트 | Kafka, EBM, UMS | 고객 행동 수집 → 분석·오퍼링·메시지 |
| 파일 | FOS, MFT, 대외 MCA | 정보계 ↔ 대내·대외 시스템 |
| 데이터 | ETL | RDW·ADW ↔ 업무·외부 데이터 |
| 직접 조회 | 채널 Agent 등 | IT 직원의 승인된 조회 |

이 관계도의 핵심은 모든 시스템을 직접 연결하는 것이 아니라 **채널 통합, 대내 통합, 파일 통합, 데이터 통합이라는 표준 경계**를 두어 결합도를 통제하는 데 있다.

## 2. 장표의 영역 및 구성요소 전사

### 2.1 채널 영역

```text
채널
├─ 대내 채널
│  ├─ 업무 시스템
│  └─ 정보 단말
├─ Package UI(MSTR)
├─ 대고객 채널
│  ├─ 인터넷 뱅킹
│  ├─ 스마트 뱅킹
│  ├─ 비대면 로그
│  └─ SMS·PUSH·e-Mail
├─ IT 직원(작업조회)
└─ 대외 채널
   ├─ 농협자산관리
   ├─ 농협신용보증
   ├─ 농정원(AgriX)
   └─ 기타 기관
```

### 2.2 채널 통합 영역

- 영업점 MCA: 싱글뷰와 표준전문 경유
- MCI: 대고객 채널 온라인 통합
- Wise Collector Proxy / Wise Collector: 고객 행동 수집
- UMS: SMS·PUSH·e-Mail 통합 발송
- 아리룩 / 채널 Agent: IT 직원 작업조회 연계
- 대외 MCA / MFT / FOS: 대외 채널 파일 연계

### 2.3 차세대 정보계 업무 시스템

#### ① 마케팅 플랫폼

온라인 애플리케이션:

- 미니 싱글뷰
- 공통
- 상담판매
- 통합상품
- 통합고객
- 개인고객
- 기업고객
- 행동정보
- 캠페인
- 컨텐츠
- 메시지
- 영업지원
- CS
- EBM

행동정보 처리:

- 고객 행동 데이터
- 행동정보처리

#### ② 데이터 플랫폼

RDW:

- 비즈메타
- 데이터 품질
- 데이터 흐름

### 2.4 대내 통합 영역

온라인 통합:

- API G/W + EAI

- GSE

파일 통합:

- FOS
- FOS + MFT
- FOS + MFT + CDC로 표기된 연계선

데이터 통합:

- ETL

### 2.5 대내·외 연계업무

- 계정계 AP, 코어뱅킹
- 계정계 Online DB
- 계정계 BCV DB
- e뱅킹, e정보계
- 카드 정보계, 카드 DW
- Big Data
- 회계관리, 리스크 관리, 경제, 로우코드, 아리오피스
- 외부 연계, 지도 GIS

> 장표의 일부 작은 글자와 `FOS-MFT-CD…` 표기는 이미지 해상도상 완전한 확정이 어렵다. 본 분석은 명확히 판독되는 관계를 기준으로 하며, 불명확한 제품명과 연결선은 상세 인터페이스 목록에서 확인해야 한다.

## 4. 관계 축별 상세 분석

### 4.1 채널 → 마케팅 플랫폼

| 소스 | 중계 | 타깃 | 방식 |
|---|---|---|---|
| 업무 시스템 | 영업점 MCA | 미니 싱글뷰 | JSON/HTTP 또는 표준전문 |
| 정보 단말 | 직접 온라인 접점 | 온라인 애플리케이션 | JSON/HTTP |
| Package UI(MSTR) | 직접 온라인 접점 | BI/OLAP 계열 | JSON/HTTP |
| 인터넷·스마트뱅킹 | MCI | 마케팅·BI 기능 | 온라인 통합 |

채널 요청은 최초 접점에서 GUID를 발급·수용하고 이후 모든 서비스, DB, 이벤트에 전파해야 한다. 영업점 MCA와 MCI는 채널별 프로토콜 차이를 흡수하지만 업무 규칙을 소유해서는 안 된다.

### 4.2 대고객 채널 → 행동정보 처리

```text
인터넷/스마트뱅킹
   → 비대면 로그
   → Wise Collector Proxy
   → Wise Collector
   → Kafka
   → 고객 행동 데이터
   → 행동정보처리
       ├→ RDW/ADW 분석 데이터
       └→ 실시간 처리 EBM → UMS → SMS/PUSH/e-Mail
```

이 경로는 온라인 거래 응답과 분리된 비동기 이벤트 파이프라인이어야 한다. 행동 로그 수집 실패가 고객 거래 실패로 이어져서는 안 되며, 백프레셔와 로컬 버퍼 또는 재전송 정책이 필요하다.

### 4.3 마케팅 플랫폼 ↔ 데이터 플랫폼

마케팅 플랫폼은 RDW의 실시간·준실시간 데이터와 ADW의 분석 결과를 소비하고, 캠페인·반응·행동 결과를 다시 Feedback으로 적재한다.

- 조회성 온라인 서비스는 RDW 또는 전용 마트에 접근한다.
- 분석·캠페인 대상 선정은 ADW의 분석 마트를 활용한다.
- 결과 Feedback은 원거래·캠페인·고객 키로 추적한다.
- 온라인 쿼리와 대량 분석 쿼리의 DB 서비스·자원 그룹을 분리한다.
- 애플리케이션이 임의로 데이터 플랫폼 내부 스키마를 갱신하지 않도록 소유권을 정한다.

### 4.4 BI 포탈 ↔ 데이터 플랫폼

BI 포탈의 신용실적·BI 포탈·OLAP·Self-BI는 RDW/ADW의 데이터 소비 계층이다.

| BI 기능 | 우선 데이터 성격 | 고려사항 |
|---|---|---|
| 신용실적 | 준실시간·정형 | 마감 기준과 실적 확정 시점 |
| BI 포탈 | 통합 조회 | 사용자 권한·행 수준 보안 |
| OLAP | 다차원 집계 | 큐브·마트 갱신 주기 |
| Self-BI | 사용자 분석 | 쿼리 자원 제한·데이터 반출 통제 |

BI 사용자가 운영 RDW에 무제한 쿼리를 수행하지 않도록 ADW·전용 마트와 Resource Manager를 활용해야 한다.

### 4.5 데이터거버넌스 ↔ 데이터 플랫폼

데이터거버넌스는 데이터 자체를 소유하기보다 데이터 플랫폼의 의미·품질·흐름을 통제한다.

- 비즈메타: 용어, 코드, 지표, 데이터 소유자 관리
- 데이터 품질: 프로파일링, 규칙, 오류·개선 이력
- 데이터 흐름: Source-to-Target, Job, 컬럼 수준 Lineage

ETL, CDC, API, 파일, Kafka의 메타데이터를 수집해야 종단 Lineage가 완성된다. 설계 문서만 관리하고 실제 실행 메타를 수집하지 않으면 현행성이 빠르게 떨어진다.

### 4.6 정보계 ↔ 대내 온라인 통합

```text
정보계 서비스
   ↔ API G/W
       ├↔ EAI ↔ 계정계 AP/코어뱅킹
       ├↔ 대내 온라인 시스템
       └↔ 표준 API 소비자

정보계 서비스
   ↔ GSE ↔ 계정계 Online DB 관련 서비스 또는 표준 전산망
```

API G/W는 인증·인가·라우팅·Rate Limit·API 버전을 담당하고, EAI는 레거시 전문 변환과 중재를 담당한다. 실제 GSE 연결 대상은 상세 설계에서 확정해야 한다.

### 4.7 정보계 ↔ 대내 파일 통합

장표는 시스템 성격에 따라 FOS 단독, FOS+MFT 등 복수 패턴을 사용한다.

```text
정보계 ↔ FOS ↔ 대내 시스템
정보계 ↔ FOS ↔ MFT ↔ 중요/원격 시스템
정보계 ↔ FOS ↔ MFT ↔ 대외 MCA ↔ 대외 채널
```

- FOS: 정보계 파일 인터페이스의 표준 접점
- MFT: 전송 통제, 암호화, 재개, 추적이 필요한 구간
- 대외 MCA: 외부 기관별 접속·전문·망 경계 처리

파일 전송 완료와 업무 반영 완료는 별도 상태로 관리해야 한다.

### 4.8 정보계 ↔ 데이터 통합

ETL은 정보계 데이터 플랫폼과 대내·외 DB 사이의 표준 대량 데이터 이동 수단이다.

- 계정계 BCV DB → 정보계 DW/RDW
- RDW → ADW
- 정보계 DW → 카드·회계·리스크·Big Data 등
- 외부·대내 DB → 정보계 DW

각 경로는 Source/Target 매핑, 전체·증분 방식, 업무일자, 워터마크, 정합성 대사, 재처리 기준을 계약으로 관리해야 한다.

### 4.9 IT 직원 작업조회

IT 직원은 아리룩과 채널 Agent를 통해 승인된 작업조회 기능에 접근하는 것으로 표현된다.

- 일반 사용자와 운영자 권한을 분리한다.
- 조회 대상·기간·개인정보 항목을 최소화한다.
- 모든 조회와 다운로드를 감사한다.
- 운영 DB 직접 접속 대신 통제된 Agent/API를 사용한다.

## 5. 연계 방향 매트릭스

| Source | Target | 경유 | 방향 | 데이터 성격 |
|---|---|---|---|---|
| 업무 시스템 | 마케팅 플랫폼 | 영업점 MCA | 주로 요청/응답 | 싱글뷰·표준전문 |
| 정보 단말 | 마케팅/BI | HTTP 접점 | 요청/응답 | 온라인 조회·거래 |
| Package UI | BI/OLAP | HTTP 접점 | 요청/응답 | 분석·리포팅 |
| 대고객 채널 | 행동정보 | MCI/Wise/Kafka | 단방향 이벤트 | 행동 로그 |
| EBM | 고객 채널 | UMS | 단방향 발송 | 메시지 |
| 마케팅 플랫폼 | RDW/ADW | DB/API/배치 | 양방향 | 조회·Feedback |

| 거버넌스 | 전 시스템 | 메타·품질 Agent | 수집/통제 | 메타·품질·Lineage |
| 정보계 | 계정계/대내 | API G/W/EAI/GSE | 양방향 | 온라인 전문 |

| 정보계 | 대내·외 DB | ETL | 양방향 | 배치 데이터 |

## 6. 표준 인터페이스 책임 경계

| 컴포넌트 | 소유 책임 | 제외할 책임 |
|---|---|---|
| 영업점 MCA/MCI | 채널 수용, 프로토콜 표준화 | 업무 데이터 소유 |
| API G/W | 인증, 정책, 라우팅, 버전 | 핵심 업무 로직 |
| EAI | 레거시 전문 변환·중재 | API 상품 관리 |
| GSE | 지정 표준망·기관 연계 | 정보계 업무 처리 |
| Kafka | 이벤트 내구 전달 | 장기 업무 상태 |
| EBM | 실시간 판단·오퍼링 | 범용 메시지 전송 |
| UMS | 채널별 메시지 발송 | 캠페인 판단 |
| FOS | 파일 표준 접수·전달 | 업무 데이터 변환 |
| MFT | 안전한 전송·재개·추적 | 파일 업무 처리 |
| ETL | 대량 추출·변환·적재 | 동기 온라인 거래 |
| RDW | 실시간·통합 데이터 | 무제한 분석 부하 |
| ADW | 분석·집계·마트 | 계정계 OLTP |
| 거버넌스 | 메타·품질·Lineage | 원천 업무 데이터 소유 |

## 7. 종단 추적 모델

모든 관계는 공통 Correlation ID를 중심으로 연결해야 한다.

```text
GUID / Correlation ID
├─ 채널 요청 ID
├─ MCA/MCI 전문번호
├─ API Gateway Request ID
├─ EAI 원·응답 전문번호
├─ WAS Trace ID
├─ DB Client Identifier
├─ Kafka Event ID
├─ ETL/Batch Execution ID
├─ File ID / Transfer ID
└─ UMS Message ID
```

하위 처리 단위는 자체 ID를 갖되 `parentGuid`로 상위 거래와 연결한다. 이를 통해 고객 요청에서 DB·파일·이벤트·메시지까지 종단 장애 분석이 가능하다.

## 8. 공통 인터페이스 계약

```yaml
interfaceId: IF-REL-MKT-001

  system: branch-channel
  component: mca
target:
  system: next-info
  component: mini-single-view
type: online

tracking:
  correlationHeader: X-GUID
security:
  authentication: mTLS
  authorization: service-policy

  timeoutMs: 3000
  retryPolicy: none-for-non-idempotent
  idempotencyKey: requestId
```

파일·데이터·이벤트 계약은 같은 공통 식별·소유·보안·SLA 필드에 Layout, Source-to-Target, Topic Schema 등 유형별 항목을 확장한다.

각 계약에는 업무 소유자, 송신·수신 시스템 담당자, 중계 플랫폼 운영자와 장애 승인자를 **RACI**로 지정해 장애 위치와 무관하게 의사결정 책임이 분명하도록 해야 한다.

## 9. 신뢰성 및 재처리

### 온라인

- Timeout, Circuit Breaker, Bulkhead 적용
- 결과 미확정 거래의 상태조회 또는 멱등 키 제공
- 읽기·멱등 호출에만 제한된 재시도 적용
- 표준 기술 오류와 업무 오류 분리

### 이벤트

- Consumer Offset과 처리 체크포인트 관리
- Retry Topic과 DLQ 분리
- 동일 Event ID의 중복 소비 방지
- 스키마 호환성 검사

### 파일

- Atomic Rename 또는 Manifest 완료 신호
- Checksum과 건수 검증
- File ID 기반 중복 방지
- Quarantine과 승인된 재전송

### 데이터

- 증분 워터마크와 배치 체크포인트
- Staging 후 원자적 Merge/Partition Exchange
- Source/Target 건수·합계·해시 대사
- 실패 Step·파티션 단위 재처리

## 10. 보안 및 개인정보

- 채널·API: 강한 인증, mTLS, 토큰 검증, Rate Limit
- 운영자 조회: 역할 분리, 사유 입력, 조회·다운로드 감사
- DB: 인터페이스별 최소 권한 계정과 암호화
- Kafka: Topic ACL, 민감 필드 최소화, 보존 기간 제한
- 파일: 암호화, 악성코드, 압축 폭탄·Zip Slip 검사
- UMS: 수신 동의, 발송 빈도, 개인정보 노출 방지
- Self-BI: 행·열 수준 보안과 대량 반출 승인
- 대외 연계: 기관 인증서, 허용 IP, 전문 서명과 감사

## 11. 가용성 및 DR 관계

- 채널 통합과 대내 통합 컴포넌트는 다중화한다.
- API G/W·EAI·Kafka·FOS·MFT·ETL 스케줄러의 Active 주체를 관리한다.
- DR 전환 시 동일 이벤트·파일·배치의 이중 처리를 방지한다.
- RDW·ADW의 복구 순서와 애플리케이션 개방 순서를 정의한다.
- 외부 기관별 DR 엔드포인트와 인증서를 사전 검증한다.
- 원복 후 CDC 위치, ETL 체크포인트, Kafka Offset, 파일 상태를 대사한다.

## 17. 최종 평가

표준 인터페이스 관계도는 채널과 차세대 정보계, 데이터 플랫폼, 대내 통합 및 연계업무를 계층화하고 온라인·이벤트·파일·데이터 통합을 목적별로 분리한 구조다. 특히 차세대 정보계를 마케팅 플랫폼, 데이터 플랫폼, BI 포탈, 데이터거버넌스의 네 영역으로 나누고 표준 중계점을 통해 외부와 연결한 것은 결합도와 운영 책임을 통제하는 데 유리하다.

운영 가능한 아키텍처로 완성하려면 모든 선을 Interface ID 기반의 등록 정보로 전환해야 한다. Source·Target·방향·계약·SLA·책임자를 확정하고, GUID 종단 추적, 멱등성, 정합성 대사, 보안, 관측성 및 DR을 모든 관계에 공통 적용해야 한다. 판독이 불명확한 제품명과 연결선은 상세 인터페이스 목록과 원본 설계서로 교차 검증해야 한다.
