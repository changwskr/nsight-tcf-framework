# File Download 연계 아키텍처 분석

> **분석 대상**: 제공 이미지 `File Download` — UI F/W(xFrame) ↔ 클라우드 프레임워크(Nhins Controller) 파일 다운로드
> **분석 일자**: 2026-08-22
> **분석 원칙**: 이미지에서 확인되는 목표 구조와 현재 저장소 구현을 구분해 기술한다.

---

## 1. 핵심 결론

이미지는 xFrame이 다운로드할 파일명을 `Map`으로 `/download/{serviceId}`에 전달하면, 공통 `NhFileController(Download)`가 서비스 ID 식별과 시스템 선처리를 수행하고 Service를 호출하는 구조다. Service는 Map에서 파일 식별자를 꺼내 Object Storage에서 파일을 GET하여 `InputStream`으로 받고, Controller는 이를 HTTP Response의 `OutputStream`으로 전달한 후 시스템 후처리를 수행한다. Controller 메서드의 논리적 반환값은 `void`이고, 실제 결과는 HTTP Response Body의 바이너리 스트림이다.

현재 저장소에는 목표 구조의 구성 요소가 부분적으로 존재한다.

- `pdmg-fw`의 `ObjectStorageHandler.get(...)`은 FOS/Object Storage GET과 `InputStream` 반환 기능을 제공한다.
- `tcf-om`의 `OmUpdownloadFileController`와 `OmUpdownloadService`는 실제 파일 다운로드 Endpoint, 메타데이터 조회, 감사기록을 구현한다.
- 그러나 공통 `/download/{serviceId}`·`NhFileController`·파일명 Map 계약은 현재 소스에서 확인되지 않는다.
- 실제 OM 구현은 FOS가 아닌 로컬 파일시스템에서 전체 파일을 `byte[]`로 읽어 `ResponseEntity<byte[]>`로 반환한다. 이미지의 스트리밍 구조와 다르며 대용량 파일에서 메모리 부담이 발생한다.

## 2. 이미지에서 확인되는 구성요소

| 영역 | 구성요소 | 역할 |
|---|---|---|
| UI | UI F/W(xFrame) | 파일 Download 요청, 다운로드 파일 Map 전달 |
| Framework | `NhFileController(Download)` | `/download/{serviceId}` 진입, 서비스 ID 식별, 선·후처리 |
| Framework | Input Map | 다운로드할 파일명 또는 파일 식별자 전달 |
| Framework | Output Map | HTTP `OutputStream` 보유 또는 응답 스트림 연결 |
| Service | Download Service | Map에서 파일명을 추출하고 Object Storage 조회 |
| 외부 저장소 | Object Storage | File GET 후 `InputStream` 반환 |

### 2.1 입출력 모델

```text
Input
└─ Map
   ├─ serviceId
   ├─ fileName 또는 fileId/objectKey
   └─ 부가 요청정보

Output
└─ HTTP Response
   ├─ Content-Type
   ├─ Content-Disposition
   ├─ Content-Length 또는 chunked
   └─ OutputStream ← Object Storage InputStream
```

이미지에는 파일명이 입력 키로 표현되지만, 실제 설계에서는 사용자가 제공한 원본 파일명을 저장소 경로로 직접 사용하지 않고 권한 검증된 `fileId` 또는 `objectKey`로 조회해야 한다.

## 3. 이미지 기준 처리 흐름

| 단계 | 처리 주체 | 처리 내용 |
|---:|---|---|
| 1 | xFrame | 다운로드할 파일 정보를 Map으로 전달 |
| 2 | NhFileController | URL `/download/{serviceId}`에서 서비스 ID 인식 |
| 3 | Framework | 인증·권한·거래제어·로깅 등 시스템 선처리 |
| 4 | Controller → Service | 다운로드 파일명 또는 식별자를 Map으로 전달 |
| 5 | Service | Map에서 파일 식별자를 추출하고 저장소 위치 결정 |
| 6 | Service → Object Storage | File GET 수행 |
| 7 | Object Storage → Service | 파일 `InputStream` 반환 |
| 8 | Service → Controller | InputStream 또는 스트리밍 응답 모델 반환 |
| 9 | Controller | InputStream을 HTTP Response OutputStream으로 복사 |
| 10 | Framework | 시스템 후처리·감사로그·리소스 정리 |
| 11 | Controller → xFrame | 메서드는 `void`로 종료하고 HTTP Response Body로 파일 전달 |

### 3.1 시퀀스

```text
xFrame
  │ GET/POST /download/{serviceId}
  │ Map(fileId 또는 fileName)
  ▼
NhFileController
  │ serviceId 식별·권한 검증·시스템 선처리
  ▼
Download Service
  │ fileId → objectKey·메타데이터 조회
  ▼
Object Storage
  │ File GET
  └─ InputStream
       ▼
Download Service → Controller
  │ InputStream → HttpServletResponse.OutputStream
  │ 시스템 후처리·감사로그
  └─ HTTP binary response → xFrame
```

## 4. 설계 의도

### 4.1 바이너리 응답과 일반 온라인 전문의 분리

다운로드 응답은 JSON 업무 전문이 아니라 파일 바이너리다. 따라서 공통 JSON 응답 래퍼를 적용하지 않고, 전용 Controller가 `Content-Type`, `Content-Disposition`, 파일 길이와 캐시 정책을 설정한 뒤 스트림을 직접 전달하는 구조가 적합하다.

### 4.2 InputStream과 OutputStream 연결

파일 전체를 메모리에 적재하지 않고 다음과 같이 제한된 버퍼로 복사하면 메모리 사용량은 파일 크기가 아니라 버퍼 크기에 비례한다.

```text
Object Storage InputStream
       │ 64 KiB buffer
       ▼
HTTP Response OutputStream
```

스트림의 소유권과 종료 책임은 명확해야 한다. 저장소 응답과 HTTP Client를 파일 전송이 끝나기 전에 닫으면 스트림이 무효화될 수 있으므로 Controller의 스트리밍 콜백이 완료될 때까지 원격 리소스가 유지되어야 한다.

### 4.3 파일 식별자와 표시 파일명의 분리

| 값 | 용도 |
|---|---|
| `fileId` | 외부 요청과 권한 확인에 사용하는 불투명 식별자 |
| `objectKey` | 서버 내부에서 Object Storage 객체를 찾는 키 |
| `originalName` | `Content-Disposition`에 표시할 사용자 친화적 파일명 |

## 6. 주요 Gap과 위험

| Gap/위험 | 영향 | 권고 |
|---|---|---|
| 공통 `NhFileController` 없음 | 업무별 권한·응답·감사 정책이 달라질 수 있음 | 공통 다운로드 진입 계약 정의 |
| `{serviceId}` 라우팅 없음 | TCF 서비스 정책과 통합 제어하기 어려움 | Path 또는 Header 기반 serviceId 규칙 확정 |
| GET이 `DefaultFilter`에서 전부 제외됨 | GUID·ServiceContext·공통 인증/선처리 누락 가능 | 공개 GET만 명시적으로 제외하고 다운로드는 적용 |
| OM이 `readAllBytes` 사용 | 동시 대용량 다운로드 시 Heap 고갈 위험 | `StreamingResponseBody` 또는 직접 스트림 복사 |
| OM은 로컬 파일시스템 사용 | 다중 인스턴스에서 파일 일관성·가용성 저하 | FOS/Object Storage Adapter 연결 |
| FOS GET 스트림 수명주기 | `ObjectStorageHandler.get`이 HTTP Client try-with-resources 안에서 InputStream을 반환 | 응답·Client 수명까지 포함하는 스트리밍 Resource 객체로 변경 |
| 파일명 직접 조회 가능성 | 경로 조작·타 사용자 파일 접근 위험 | fileId→권한검증→objectKey 서버 측 해석 |
| Range/재개 다운로드 없음 | 대용량 파일 재시도 비용 증가 | HTTP Range·206 Partial Content 지원 검토 |
| 무제한 Timeout | 연결 장애 시 요청·스레드 장기 점유 | 운영 환경 유한 Timeout·취소 전파 적용 |

### 6.1 FOS InputStream 수명주기 주의

현재 `ObjectStorageHandler.get(...)`은 `CloseableHttpClient`를 try-with-resources로 열고 응답 Entity의 `InputStream`을 DTO에 넣은 뒤 반환한다. 메서드 반환 시 HTTP Client가 닫히므로, 호출자가 이후 스트림을 소비할 때 이미 연결 리소스가 종료되었을 가능성이 있다.

권장 방식은 다음 중 하나다.

- 스트리밍 콜백 내부에서 HTTP Client·Response·InputStream을 열고 복사를 완료한 뒤 닫는다.
- Client를 애플리케이션 공용 Bean으로 관리하고, 응답 Resource가 InputStream 종료 책임을 가진다.
- 파일 크기가 작다는 명시적 제한이 있을 때만 메서드 내부에서 `byte[]`로 완전히 읽은 뒤 반환한다.

## 7. 운영·보안 점검사항

- 다운로드 전 사용자·업무·파일별 접근권한을 검증한다.
- 원본 파일명이 아니라 불투명한 `fileId`를 외부 계약으로 사용한다.
- `Content-Disposition` 파일명에서 CR/LF와 경로 문자를 제거하고 RFC 5987 인코딩을 적용한다.
- `X-Content-Type-Options: nosniff`와 안전한 Content-Type을 설정한다.
- 민감 파일은 `Cache-Control: no-store, private` 정책을 적용한다.
- 다운로드 성공은 파일 전송 완료 후 기록하고, Client Disconnect는 실패/중단으로 구분한다.
- GUID, userId, serviceId, fileId, 전송 byte 수, 소요시간과 결과를 감사로그에 남긴다.
- 동시 다운로드 수, 사용자별 Rate Limit, 대역폭 제한을 적용한다.
- FOS 오류 본문과 Authorization Token을 로그에 노출하지 않는다.
- Object Storage와 HTTP 응답 모두에 Deadline·취소 신호를 전파한다.

## 8. 권장 논리 인터페이스

```java
public record DownloadCommand(
        String serviceId,
        String fileId,
        String guid,
        String userId
) {}

public record DownloadResource(
        String originalName,
        String contentType,
        long contentLength,
        InputStream inputStream
) implements AutoCloseable {
    @Override
    public void close() throws IOException {
        inputStream.close();
    }
}
```

Spring MVC에서는 `StreamingResponseBody`를 사용해 제한된 버퍼로 전송할 수 있다.

```java
StreamingResponseBody body = output -> {
    try (DownloadResource resource = service.open(command)) {
        resource.inputStream().transferTo(output);
    }
};
```

실제 구현에서는 전송 완료·중단을 구분하는 감사기록, 버퍼 크기, Deadline 확인과 예외 변환을 스트리밍 콜백에 포함해야 한다.

## 9. 최종 평가

이미지는 다운로드를 일반 JSON 온라인 거래와 분리하고, 서비스 ID 기반 공통 Controller에서 권한·선후처리를 수행한 뒤 Object Storage의 InputStream을 HTTP OutputStream으로 직접 연결하는 구조다. 이 방식은 대용량 파일에 적합하며 Controller 반환값과 실제 HTTP Body를 명확히 분리한다.

현재 저장소는 FOS GET Client, 파일 메타데이터 조회, 로컬 다운로드, HTTP Header 조립과 감사로그 기능을 갖추고 있지만 하나의 공통 스트리밍 파이프라인으로 통합되지 않았다. 우선순위는 다운로드 GET에 공통 보안 Context 적용, `fileId→objectKey` 권한 모델 확정, OM의 FOS Adapter 연결, `byte[]`에서 스트리밍으로 전환, FOS 응답 스트림 수명주기 수정 순이다.
