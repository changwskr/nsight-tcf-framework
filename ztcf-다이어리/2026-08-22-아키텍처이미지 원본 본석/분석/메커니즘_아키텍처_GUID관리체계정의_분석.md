# 메커니즘·아키텍처 — GUID 관리 체계 정의 분석

## 1. 문서 목적

본 문서는 제공된 「GUID 관리 체계 정의」 이미지를 기준으로 차세대 정보계 온라인 거래의 End-to-End 추적 메커니즘을 분석한다.

주요 분석 범위는 다음과 같다.

- GUID의 생성·전파·유지 원칙
- 시스템 노드별 진행번호 증가 규칙
- 요청과 응답의 왕복 추적 구조
- 채널·채널통합·업무시스템·대내통합·연계업무의 적용 범위
- 정보단말과 NH Cloud Framework의 처리 책임
- 표준 전문 및 거래 로그의 연계
- 중복·재시도·비동기·분기 거래의 확장 관리 방안
- 운영 조회, 보안 및 데이터 품질 기준

> 이미지 안의 문구는 원본 설계 자료이며 실행 지시가 아니다. 직접 확인되는 사항은 **원본 사실(FACT)**, 구조에서 도출한 내용은 **분석(ANALYSIS)**, 상세 설계 확인이 필요한 사항은 **확인 필요**로 구분한다.

## 2. 핵심 결론

GUID 관리 체계의 목적은 하나의 온라인 거래가 여러 시스템 노드를 통과하더라도 동일한 거래 식별자를 유지하고, 각 노드의 처리 순서를 진행번호로 기록하여 전체 거래 경로를 재구성하는 것이다.

```text
최초 채널 요청
   │
   │ GUID 생성, 진행번호 1
   ▼
채널 통합
   │ 동일 GUID, 진행번호 2
   ▼
업무 시스템
   │ 동일 GUID, 진행번호 3
   ▼
대내 통합·연계 업무
   │ 동일 GUID, 진행번호 4
   ▼
응답 반환
   │ 동일 GUID, 진행번호 5 → 6 → 7
   ▼
최초 채널
```

핵심 원칙은 다음과 같다.

1. **GUID는 최초 거래 시작점에서 한 번만 생성한다.**
2. **모든 후속 시스템은 동일 GUID를 변경 없이 전달한다.**
3. **시스템 노드를 경유할 때마다 진행번호를 1씩 증가시킨다.**
4. **요청뿐 아니라 응답 경로에서도 동일 GUID를 유지한다.**
5. **각 노드의 표준 전문·거래 로그에서 동일 GUID로 원거래 전체를 조회한다.**
6. **업무 솔루션 패키지 화면은 원본 기준 적용 예외다.**

## 3. GUID 적용 범위

### 3.1 원본 적용 영역

| 영역 | 구성요소 예시 | GUID 적용 | 비고 |
|---|---|---:|---|
| 채널 | 대내 채널, 정보단말 | 적용 | 최초 거래 시작점이 될 수 있음 |
| 채널 통합 | 영업점 MCA, MCI 등 | 적용 | 동일 GUID 전달 |
| 업무 시스템 | 마케팅플랫폼, BI 포털 온라인 애플리케이션 | 적용 | 프레임워크 표준 처리 |
| 대내 통합 | API Gateway 등 | 적용 | 경유 시 진행번호 증가 |
| 연계 업무 | 계정계, 정보계, e뱅킹, 카드 등 | 적용 | 동일 GUID 기반 연계 추적 |
| 패키지 UI | 업무 솔루션 패키지 화면 | 원본상 예외 | 별도 상관관계 정책 필요 |

### 3.2 적용 범위 텍스트 구성도

```text
┌──────── 채널 ────────┐
│ 대내 채널            │
│ 정보단말             │
└──────────┬───────────┘
           │ GUID
           ▼
┌────── 채널 통합 ─────┐
│ 영업점 MCA / MCI     │
└──────────┬───────────┘
           │ 동일 GUID
           ▼
┌────── 업무 시스템 ───┐
│ 마케팅플랫폼 온라인 AP│
│ BI 포털 온라인 AP    │
└──────────┬───────────┘
           │ 동일 GUID
           ▼
┌────── 대내 통합 ─────┐
│ API Gateway          │
└──────────┬───────────┘
           │ 동일 GUID
           ▼
┌────── 연계 업무 ─────┐
│ 계정계·정보계·카드 등 │
└──────────────────────┘

※ Package UI는 원본 기준 예외
```

## 4. GUID와 진행번호의 역할

### 4.1 식별자 역할 분리

| 항목 | 역할 | 거래 중 변경 여부 |
|---|---|---|
| GUID | 하나의 원거래를 End-to-End로 묶는 전역 식별자 | 변경하지 않음 |
| 진행번호 | 원거래가 시스템 노드를 통과한 순서 또는 처리 단계를 표시 | 노드 경유 시 증가 |
| 서비스 코드 | 실행할 업무 기능 식별 | 호출 단계별로 달라질 수 있음 |
| 시스템 코드 | 현재 처리 노드 식별 | 노드마다 다름 |
| 요청·응답 구분 | 메시지 방향 또는 종류 식별 | 단계별로 다름 |

### 4.2 식별 키 예시

```text
원거래 식별 키 : GUID
노드 처리 식별 : GUID + 진행번호
세부 로그 식별 : GUID + 진행번호 + 시스템코드 + 이벤트유형
```

GUID만으로 원거래 전체를 조회하고, GUID와 진행번호 조합으로 특정 노드 처리 내역을 정확하게 식별하는 방식이 적절하다.

## 5. 생성·전파·증가 규칙

### 5.1 GUID 생성 규칙

원본은 채널 시스템이 최초 거래 시작 시 표준 전문의 GUID 항목을 규칙에 따라 생성하여 거래를 요청한다고 명시한다.

권장 규칙:

- 최초 진입 채널에서 GUID가 없을 때만 생성한다.
- 이미 GUID가 포함된 연계 요청은 검증 후 그대로 사용한다.
- 모든 시스템과 시간대에서 중복되지 않아야 한다.
- 애플리케이션 재기동이나 다중 노드 환경에서도 충돌하지 않아야 한다.
- 의미가 포함된 예측 가능한 일련번호보다 UUID/ULID 계열 등 충돌 방지 형식을 검토한다.
- 외부 기관 GUID를 내부 GUID로 교체해야 한다면 원본·내부 식별자 매핑을 별도 보존한다.

### 5.2 전파 규칙

```text
if 요청.GUID 존재:
    GUID 형식 검증
    같은 GUID 유지
else if 현재 노드가 최초 진입점:
    신규 GUID 생성
else:
    표준 전문 오류 처리
```

- 중간 노드는 정상적인 기존 GUID를 재발급하거나 변경하지 않는다.
- HTTP Header, 표준 전문 Header, 애플리케이션 Context, 로그 Context 간 값이 일치해야 한다.
- 하위 호출 시 GUID를 명시적으로 전달한다.
- 스레드 전환·비동기 실행 시 실행 컨텍스트가 자동으로 사라지지 않도록 전달 장치를 둔다.

### 5.3 진행번호 증가 규칙

원본은 시스템 노드를 경유할 때 표준 전문 내 GUID의 진행 일련번호 식별자(진행상황)를 `+1` 증가시켜 다음 노드에 전달한다고 명시한다.

```text
다음 진행번호 = 수신 진행번호 + 1
```

기본 기준:

- 최초 거래 생성 시 `1`로 시작한다.
- 논리 시스템 경계를 넘을 때 1 증가한다.
- 동일 시스템 내부 Controller→Service→DAO 호출은 별도 진행번호보다 span으로 관리하는 것이 적합하다.
- 요청과 응답 모두 노드 경유를 기록할 경우 응답에서도 계속 증가한다.
- 재시도는 같은 진행번호를 재사용할지 새 번호를 부여할지 표준으로 명확히 해야 한다.

## 6. 원본 진행번호 1→7 흐름 분석

### 6.1 텍스트 시퀀스

```text
요청 방향

[1] 채널
    표준전문 { GUID=G, 진행번호=1 }
        │
        ▼
[2] 채널 통합
    표준전문 { GUID=G, 진행번호=2 }
        │
        ▼
[3] 차세대 정보계 업무 시스템
    표준전문 { GUID=G, 진행번호=3 }
        │
        ▼
[4] 대내 통합/연계 업무
    표준전문 { GUID=G, 진행번호=4 }

응답 방향

[5] 대내 통합/업무 시스템 복귀
    표준전문 { GUID=G, 진행번호=5 }
        │
        ▼
[6] 채널 통합 복귀
    표준전문 { GUID=G, 진행번호=6 }
        │
        ▼
[7] 최초 채널 응답
    표준전문 { GUID=G, 진행번호=7 }
```

### 6.2 해석

- `G`는 전체 요청·응답 과정에서 변하지 않는다.
- 진행번호는 왕복 경로를 시간 순서로 재구성할 수 있게 한다.
- 각 단계의 로그를 진행번호 순으로 정렬하면 전체 거래 흐름을 확인할 수 있다.
- 원본 그림의 번호는 논리 노드의 진행 상태를 표현하며 실제 시스템 구성에 따라 단계 수는 달라질 수 있다.

## 7. 표준 전문 내 GUID 구조

### 7.1 권장 필드

```text
StandardMessage.Header
├─ guid                  원거래 글로벌 식별자
├─ progressNo            진행번호
├─ parentGuid            상위 거래 식별자(분기 시 선택)
├─ requestId             개별 요청 식별자(선택)
├─ systemCode            현재 시스템 코드
├─ channelCode           최초 채널 코드
├─ serviceCode           서비스 코드
├─ messageType           요청/응답/이벤트
├─ timestamp             메시지 생성 시각
└─ version               표준 전문 버전
```

> 위 필드 명칭과 구조는 구현 권고 예시다. 원본 이미지에는 GUID와 진행번호 외의 상세 필드가 제시되지 않았다.

### 7.2 JSON 예시

```json
{
  "header": {
    "guid": "01JEXAMPLE8R7R4M7C3X9V0ABC",
    "progressNo": 3,
    "systemCode": "MP",
    "channelCode": "TERM",
    "serviceCode": "MPCM0001",
    "messageType": "REQUEST",
    "timestamp": "2026-08-25T10:30:00+09:00",
    "version": "1.0"
  },
  "body": {}
}
```

### 7.3 HTTP Header 병행 예시

```http
X-Transaction-Guid: 01JEXAMPLE8R7R4M7C3X9V0ABC
X-Progress-No: 3
X-Service-Code: MPCM0001
```

전문 Header와 HTTP Header를 병행할 경우 두 값의 불일치 처리 정책이 필요하다. 일반적으로 표준 전문을 원본으로 삼거나, 진입 계층에서 일치 여부를 검증한 뒤 내부에서는 하나의 표준 Context로 통일한다.

## 8. 구성요소별 책임

### 8.1 채널 시스템

- 최초 거래 시작 시 GUID 생성
- 진행번호 1 설정
- 표준 전문에 GUID 삽입
- 응답 GUID와 요청 GUID의 일치 여부 검증
- 사용자 화면 또는 단말 로그에 추적 키 제공

### 8.2 정보단말(WebTopSuite)

원본은 정보단말(WebTopSuit)과 업무 시스템 프레임워크(NH Cloud Framework)가 표준 전문의 GUID 생성 처리 규칙에 따라 거래를 구현한다고 명시한다.

정보단말 책임:

- 거래 요청 시 GUID Context 초기화
- 동일 화면의 후속 호출을 새 원거래로 볼지 하위 거래로 볼지 정책 적용
- 요청·응답 GUID 보존
- 브라우저·단말 로그의 최소 추적 정보 기록

### 8.3 채널 통합(MCA/MCI)

- 수신 GUID 검증 및 동일값 전달
- 진행번호 증가
- FLAT↔JSON 변환 시 GUID 손실 방지
- 프로토콜 변환 전후의 동일 거래 로그 연결
- 중복·재전송 요청 식별

### 8.4 NH Cloud Framework

- 인바운드 전문에서 GUID와 진행번호 추출
- Thread/Request Context 또는 MDC에 저장
- Controller·Service·DAO 로그에 자동 반영
- 아웃바운드 연계 호출에 GUID 전파
- 시스템 경계 통과 시 진행번호 증가
- 응답 전문에 GUID·진행번호 설정
- 예외 처리 시에도 GUID 유지

### 8.5 API Gateway·대내 통합

- GUID Header/Body 검증
- 호출자별 라우팅 후 동일 GUID 전달
- 진행번호 증가 및 Gateway 접근 로그 기록
- 차단·인증 실패·타임아웃에도 GUID 포함 오류 반환
- EAI 경유 시 상관관계 ID 매핑

### 8.6 연계 업무 시스템

- 수신 GUID 보존
- 자체 로그와 DB 세션에 GUID 연결
- 응답 시 동일 GUID 반환
- 하위 거래 분기 시 부모 GUID 관계 기록

## 9. 프레임워크 처리 메커니즘

### 9.1 인바운드 처리

```text
HTTP/표준전문 수신
  → GUID·진행번호 추출
  → 형식·필수값 검증
  → TransactionContext 생성
  → MDC/로그 Context 설정
  → 진행번호 정책 적용
  → Controller 호출
```

### 9.2 내부 처리

```text
Controller
  → Service
    → DAO
      → DB

모든 로그에 GUID 자동 포함
```

동일 프로세스 내부의 메서드 호출마다 진행번호를 증가시키면 번호가 과도하게 커지고 시스템 경계 의미가 흐려질 수 있다. 내부 호출은 `spanId` 같은 별도 식별자를 쓰고, 진행번호는 논리 노드 경계에 사용하는 것이 적절하다.

### 9.3 아웃바운드 처리

```text
TransactionContext에서 GUID 조회
  → 다음 진행번호 계산
  → 표준 전문/HTTP Header에 주입
  → 외부 시스템 호출
  → 응답 GUID 검증
  → 결과 로그 기록
```

### 9.4 종료 처리

- 성공·실패 여부와 최종 진행번호 기록
- 처리 시간과 대상 시스템 기록
- MDC와 ThreadLocal Context 정리
- 비동기 작업이 남아 있다면 명시적으로 Context 복제 또는 종료 관계 기록

## 10. 거래 로그 관리

### 10.1 원본 조회 원칙

원본은 각 시스템별로 기록된 표준 전문 로그에서 **원거래글로벌ID** 항목을 거래의 유일한 식별자로 조회한다고 명시한다.

### 10.2 권장 로그 항목

| 항목 | 용도 |
|---|---|
| GUID/원거래글로벌ID | 원거래 전체 검색 |
| 진행번호 | 노드 처리 순서 정렬 |
| 시스템 코드 | 처리 노드 식별 |
| 인스턴스·호스트명 | 물리 처리 위치 식별 |
| 서비스 코드 | 수행 기능 식별 |
| 요청·응답 구분 | 방향 식별 |
| 시작·종료 시각 | 처리 시간 계산 |
| 결과·오류 코드 | 성공·실패 분석 |
| 대상 시스템 | 외부 호출 관계 확인 |
| 재시도 번호 | 중복·재처리 분석 |

### 10.3 로그 재구성 예시

```text
GUID = G 검색

진행  시스템   방향      결과   처리시간
1     TERM     REQUEST   OK     2ms
2     MCA      REQUEST   OK     8ms
3     MP       REQUEST   OK     35ms
4     CORE     REQUEST   OK     20ms
5     MP       RESPONSE  OK     4ms
6     MCA      RESPONSE  OK     7ms
7     TERM     RESPONSE  OK     3ms
```

이 표를 통해 어느 구간에서 지연·오류·누락이 발생했는지 식별할 수 있다.

## 11. 분기·병렬 호출 관리

단일 거래가 여러 하위 시스템을 병렬 호출하면 단순 진행번호만으로 완전한 인과관계를 표현하기 어렵다.

```text
GUID G / 진행 3
       ├─ 하위호출 A: span A / 진행 4
       └─ 하위호출 B: span B / 진행 4 또는 5
```

권장 확장:

- GUID: 원거래 전체를 묶는다.
- Parent Span ID: 호출 부모를 나타낸다.
- Span ID: 각 하위 호출을 구분한다.
- 진행번호: 논리 노드 경유 순서 또는 이벤트 순서를 나타낸다.
- 병렬 호출에서는 단일 정수 증가의 원자성을 보장하거나 분기 번호 체계를 둔다.

예시:

```text
G / progress=3 / span=MP
G / progress=4 / span=CORE-A / parent=MP
G / progress=5 / span=CARD-B / parent=MP
```

## 12. 비동기·이벤트 거래 관리

비동기 메시지·Kafka·배치 전환에서는 HTTP 요청 Context가 자동 유지되지 않으므로 GUID를 메시지 Header에 명시적으로 저장해야 한다.

```text
온라인 요청 GUID=G
  → 이벤트 발행 { guid=G, parentGuid=G, eventId=E }
  → Consumer 처리 { guid=G, eventId=E }
```

정책 선택:

1. 원거래 연속 처리이면 동일 GUID를 유지한다.
2. 독립된 후속 업무이면 신규 GUID를 생성하고 `parentGuid`로 연결한다.
3. 재처리는 동일 eventId 또는 별도 retryId로 중복 여부를 구분한다.
4. Dead Letter Queue에도 GUID와 원문 메타데이터를 보존한다.

## 13. 재시도·중복·멱등성

### 13.1 재시도 식별

| 항목 | 권고 |
|---|---|
| 원거래 GUID | 동일하게 유지 |
| 재시도 횟수 | 별도 `retryNo` 증가 |
| 요청 ID | 개별 전송마다 새 값 또는 정책에 따라 유지 |
| 업무 멱등키 | 업무 식별자 또는 GUID 조합 사용 |

### 13.2 중복 처리 방지

```text
중복 키 = 서비스 코드 + GUID + 업무 멱등키
```

- 동일 GUID 재수신 시 이전 처리 상태를 조회한다.
- 이미 성공한 변경 거래는 다시 실행하지 않고 기존 결과를 반환한다.
- 진행 중 거래는 잠금 또는 처리 중 응답을 사용한다.
- 실패 거래는 오류 유형에 따라 재처리 가능 여부를 구분한다.

### 13.3 타임아웃 불확실성

호출자가 타임아웃을 받았더라도 대상 시스템은 성공했을 수 있다. 따라서 단순 재호출보다 GUID 기반 거래 상태 조회가 필요하다.

## 14. Package UI 예외 관리

### 14.1 원본 사실

업무 솔루션 패키지 화면은 GUID 표준 적용 예외로 표시되어 있다.

### 14.2 위험

- 표준 거래와 패키지 내부 로그의 연결이 끊길 수 있다.
- 장애 시 End-to-End 원인 분석이 어려워질 수 있다.
- 패키지 고유 세션 ID와 표준 GUID가 서로 다른 체계를 가질 수 있다.

### 14.3 보완 방안

- 패키지 진입 어댑터에서 GUID를 생성 또는 수신한다.
- 패키지 고유 Transaction ID와 GUID 매핑 로그를 기록한다.
- 패키지 외부 연계 시 표준 GUID를 반드시 전달한다.
- 사용자 화면 오류에 운영 추적용 GUID를 노출하되 민감정보는 노출하지 않는다.
- 예외 대상과 사유·유효기간·책임자를 관리한다.

## 16. 보안 및 개인정보 보호

- GUID 자체에 주민번호, 계좌번호, 사용자 ID 등 의미 있는 개인정보를 넣지 않는다.
- 예측 가능한 단순 순번만으로 생성하지 않는다.
- 외부 입력 GUID의 길이·문자 집합을 검증해 로그 인젝션을 방지한다.
- GUID는 추적자이지 인증 수단이 아니므로 권한 검증에 사용하지 않는다.
- 로그 조회 권한과 보존 기간을 통제한다.
- 전문 원문 로그에는 민감정보 마스킹을 적용한다.
- 사용자에게 GUID를 제공할 경우 내부 구조나 시스템 정보를 노출하지 않는 형식을 사용한다.

## 20. 운영 체크리스트

### 설계

- [ ] GUID 형식·길이·생성 알고리즘이 정의되어 있다.
- [ ] 생성 주체와 누락 시 정책이 정의되어 있다.
- [ ] 진행번호 증가 경계가 정의되어 있다.
- [ ] 분기·병렬·비동기·재시도 정책이 정의되어 있다.
- [ ] Package UI 예외 보완 방식이 정의되어 있다.

### 구현

- [ ] 채널에서 최초 GUID를 한 번만 생성한다.
- [ ] 모든 중계·업무 노드가 동일 GUID를 전달한다.
- [ ] Framework가 MDC와 아웃바운드 전문에 GUID를 자동 반영한다.
- [ ] 예외·타임아웃 응답에도 GUID가 유지된다.
- [ ] ThreadLocal/MDC가 요청 종료 후 정리된다.

### 운영

- [ ] GUID 하나로 전 구간 로그를 검색할 수 있다.
- [ ] 진행번호 순서로 거래 경로를 재구성할 수 있다.
- [ ] GUID 누락·중복·역행 경보가 있다.
- [ ] 로그 보존·마스킹·접근 통제가 적용된다.
- [ ] 장애 훈련에서 마지막 정상 진행 노드를 찾을 수 있다.

## 21. 원본 사실·분석·확인 필요

### 21.1 원본 사실(FACT)

- 표준 전문 기반 온라인 거래에 GUID를 적용한다.
- GUID와 노드 간 진행 일련번호 증가로 End-to-End 거래 추적 기반을 구축한다.
- 차세대 정보계 온라인 거래의 각 시스템 노드는 표준 전문 내 GUID를 적용한다.
- 업무 솔루션 패키지 화면은 예외다.
- 채널 시스템은 최초 거래 시작 시 GUID 항목을 규칙에 맞게 생성한다.
- 정보단말과 NH Cloud Framework는 GUID 생성·처리 규칙에 따라 거래를 구현한다.
- 시스템 노드 경유 시 진행번호를 1 증가시켜 다음 노드에 전달한다.
- 각 시스템의 표준 전문 로그에서 원거래글로벌ID를 유일한 식별자로 조회한다.
- 원본 그림은 진행번호 1부터 7까지 요청·응답 왕복을 표현한다.

### 21.2 분석(ANALYSIS)

- GUID는 원거래, 진행번호는 노드 처리 순서를 표현한다.
- 동일 프로세스 내부 호출은 진행번호보다 span 식별자를 사용하는 편이 적합하다.
- 병렬·비동기·재시도 거래는 GUID와 진행번호만으로 부족하므로 부모·span·event·retry 식별자가 필요하다.
- GUID 표준화는 로그 검색뿐 아니라 중복 방지, 장애 구간 식별, 성능 분석에도 활용할 수 있다.

### 21.3 확인 필요

1. GUID의 실제 길이·문자 집합·생성 알고리즘
2. 원본 명칭인 `원거래글로벌ID`와 GUID의 정확한 필드명
3. 진행번호의 자료형·최댓값·초기값
4. 진행번호 증가 기준이 요청·응답 모두인지 여부
5. 동일 시스템 재진입·재귀 호출의 증가 규칙
6. 병렬 호출 시 진행번호 할당 방식
7. 재시도 시 진행번호와 GUID 유지 정책
8. 비동기·Kafka·배치 전환 시 상관관계 정책
9. HTTP Header와 전문 Header의 권위 원본
10. 외부 기관 GUID와 내부 GUID의 매핑 방식
11. Package UI의 추적 보완 체계
12. 로그 보존 기간, 마스킹 및 중앙 수집 시스템

## 22. 최종 평가

본 GUID 관리 체계는 하나의 원거래 식별자를 채널에서 연계 업무까지 유지하고 진행번호로 처리 순서를 기록함으로써 분산된 온라인 거래의 End-to-End 추적성을 확보하는 구조다. 이는 장애 분석, 거래 모니터링, 성능 측정 및 고객 문의 대응의 공통 기반이 된다.

실제 구현에서는 GUID를 단순 로그 문자열로 취급하지 않고 표준 전문, HTTP Header, Framework Context, MDC, 연계 메시지 및 DB 세션에 일관되게 전파해야 한다. 또한 병렬 호출·비동기 이벤트·재시도까지 추적하려면 GUID에 부모·span·event·retry 관계를 보완하여 현대적인 분산 추적 체계로 확장하는 것이 바람직하다.
