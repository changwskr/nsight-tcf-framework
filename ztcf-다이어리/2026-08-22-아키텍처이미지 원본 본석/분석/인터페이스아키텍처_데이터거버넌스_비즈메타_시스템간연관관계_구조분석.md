# 인터페이스 아키텍처 — 데이터거버넌스·비즈메타 시스템 간 연관관계 구조 분석

## 1. 분석 개요

첨부 장표의 **데이터거버넌스 - 비즈메타** 구성을 기준으로, 비즈메타 애플리케이션·저장소와 주변 시스템 사이의 **연계 경계·프로토콜·데이터 흐름**을 분석한다.

장표 중심에는 **데이터거버넌스 비즈메타**(애플리케이션)와 **BI 포탈/비즈메타**(DB)가 있고, 주변으로 OLAP(MSTR), BI 포탈 배치(IaaS), 데이터허브·HR, Object Storage, CruzAPIM·코어뱅크, 데이터품질관리·IT 메타가 배치된다.

레이어드 문서의 데이터거버넌스(품질·비즈메타·흐름관리 분리)와 맞물려, 본 장표는 **비즈메타를 중심으로 한 시스템 간 연관관계 축약도**다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 화살표 방향의 소유권(푸시/풀), DB Batch 주기, Rest API 쓰기 여부, `BI 포탈/비즈메타` DB의 물리 분리 여부는 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **비즈메타 = 앱 + DB 이중 표현**: 상단 애플리케이션 박스와 하단 `BI 포탈/비즈메타` DB를 한 경계 안에 둔다.
- **연계 방식 4종**: UI Link · 실시간 · Rest API · DB Batch 로 성격이 구분된다.
- **OLAP은 UI Link**: MSTR과 비즈메타는 화면·세션 문맥 연계다.
- **BI 포탈 배치로 실시간 전달**: “실시간 배치 필요에 따라” 주석과 함께 비즈메타 → BI 포탈 배치(IaaS) **실시간** 흐름이 있다.
- **원천·관리계는 DB Batch**: 데이터허브·HR(좌)와 데이터품질관리·IT 메타(우)가 비즈메타 DB와 **DB Batch**로 연결된다.
- **Object Storage·코어뱅크는 Rest**: Storage는 직결 Rest, 코어뱅크는 **CruzAPIM 경유 Rest**다.
- **API와 Batch의 분리**: 온라인/파일성 Rest와 메타·원천 동기화 Batch를 섞지 않는다.

## 3. 장표 구성요소 전사

### 3.1 중심 — 데이터거버넌스 비즈메타

| 구성요소 | 표기 | 역할(해석) |
|---|---|---|
| 애플리케이션 | 데이터거버넌스 비즈메타 | 비즈니스 메타 등록·조회·관리 로직 |
| 데이터베이스 | BI 포탈/비즈메타 | 비즈메타·포탈 연계 메타 저장소 |

> DB 명칭이 `BI 포탈/비즈메타`이므로, 포탈과 메타가 **논리·물리적으로 동일 DB를 공유**하는지, 스키마만 공존하는지는 명세 확인이 필요하다.

### 3.2 좌측 연계

| 대상 | 프로토콜 | 역할(해석) |
|---|---|---|
| OLAP (MSTR) | UI Link | 분석 UI에서 메타·용어·계보 문맥 연결 |
| BI 포탈 배치 (주기적, 실시간) — IaaS | 실시간 | 포탈/배치 측으로 메타·변경 실시간 반영 |
| 데이터허브 | DB Batch | 통합·허브 데이터 → 메타 DB 적재 |
| HR시스템 | DB Batch | 조직·인사 속성 → 메타 DB 적재 |

### 3.3 우측 연계

| 대상 | 프로토콜 | 중계 | 역할(해석) |
|---|---|---|---|
| Object Storage | Rest API | (직결) | 메타 관련 파일·객체 저장/조회 |
| 코어뱅크 | Rest API | CruzAPIM | 계정계 정보 조회·연계 |
| 데이터품질관리 | DB Batch | — | 품질 결과·규칙 메타 동기화 |
| IT 메타 | DB Batch | — | IT 기술 메타와 비즈메타 정합 |

## 5. 인터페이스 매핑 (시스템 간)

| # | 출발 | 프로토콜 | 중계 | 도착 | 설계 의미 |
|---|---|---|---|---|---|
| 1 | OLAP (MSTR) | UI Link | — | 비즈메타 App | 분석 화면↔메타 문맥. 제품 UI 종속성 |
| 2 | 비즈메타 App | 실시간 | — | BI 포탈 배치(IaaS) | 변경 메타의 준실시간/실시간 반영 |
| 3 | 데이터허브 | DB Batch | — | BI 포탈/비즈메타 DB | 허브 원천 → 메타 적재 |
| 4 | HR시스템 | DB Batch | — | BI 포탈/비즈메타 DB | 조직·인사 속성 동기화 |
| 5 | 비즈메타 App | Rest API | — | Object Storage | 객체·파일형 메타 자산 |
| 6 | 비즈메타 App | Rest API | CruzAPIM | 코어뱅크 | 계정계 정보 표준 API 호출 |
| 7 | 데이터품질관리 | DB Batch | — | BI 포탈/비즈메타 DB | 품질 메타·결과 동기화 |
| 8 | IT 메타 | DB Batch | — | BI 포탈/비즈메타 DB | 기술 메타↔비즈 메타 정합 |

### 5.1 매핑에서 읽히는 설계 의도

1. **사람·화면 경로(UI Link)** 와 **시스템 데이터 경로(Batch/Rest)** 를 분리한다.
2. **메타 DB 동기화는 Batch**, **스토리지·코어는 Rest** 로 매체 특성을 맞춘다.
3. 포탈 배치는 IaaS에 두고, 비즈메타가 **필요 시 실시간으로 밀어 주는** 구조를 허용한다.
4. 품질·IT 메타는 비즈메타와 **형제 거버넌스 계열**로 Batch 정합을 유지한다.
5. 코어뱅크 접근은 APIM으로 표준화해 비즈메타가 계정계에 직접 붙지 않게 한다.

## 6. 주요 처리 흐름

### 6.1 OLAP UI Link

```text
사용자(OLAP MSTR)
  → UI Link
  → 데이터거버넌스 비즈메타
  → (필요 시) BI 포탈/비즈메타 DB 조회
  → 용어·계보·오너십 등 메타 문맥 제공
```

- URL·토큰·권한 문맥과 위변조 방지가 필요하다.
- OLAP 장애와 비즈메타 장애의 영향 범위를 격리한다.

### 6.2 비즈메타 → BI 포탈 배치 (실시간)

```text
비즈메타 App
  → 실시간 인터페이스
  → BI 포탈 배치 (IaaS)
  → 포탈/배치 측 캐시·인덱스·검색 반영
```

- “필요에 따라”이므로 **상시 스트리밍인지 이벤트 트리거인지**를 명세로 확정한다.
- 실패 시 재처리·DLQ·배치 보정(주기적) 경로가 필요하다.

### 6.3 DB Batch 동기화

```text
데이터허브 / HR / 데이터품질관리 / IT 메타
  → DB Batch
  → BI 포탈/비즈메타 DB
```

- 주기, 증분/전체, 키, 충돌 시 우선순위(원천 승자)를 정의한다.
- 양방향이면 루프·덮어쓰기를 방지하는 소유권 규칙을 둔다.
- Batch 실패가 온라인 메타 조회에 주는 영향(최신성 SLA)을 명시한다.

### 6.4 Rest — Object Storage

```text
비즈메타 App ↔ Rest API ↔ Object Storage
```

- 버킷·경로·암호화·보존·권한을 거버넌스 정책과 맞춘다.
- APIM 미경유라면 Storage 접근 감사를 강화한다.

### 6.5 Rest — CruzAPIM — 코어뱅크

```text
비즈메타 App → Rest API → CruzAPIM → 코어뱅크
```

- 읽기 중심·최소 필드·쿼터·타임아웃·차단기를 적용한다.
- 메타 보강 목적의 계정계 호출과 거래성 API를 혼동하지 않는다.

## 7. 인터페이스 설계 원칙

1. **비즈메타 App은 코어뱅크 DB에 직접 접속하지 않는다.** Rest+APIM만 사용한다.
2. **원천·품질·IT 메타 동기화는 DB Batch 계약**으로 관리하고, 온라인 Rest와 섞지 않는다.
3. **UI Link는 문맥 전달용**이며 대량 데이터 적재 경로로 쓰지 않는다.
4. **실시간 → BI 포탈 배치**는 실패 보정용 주기 Batch와 쌍으로 설계한다.
5. **Object Storage와 메타 DB의 역할**을 분리한다(객체 vs 구조화 메타).
6. 전 구간 **GUID/Trace ID**(Rest)와 **배치 Job ID**(Batch)를 남겨 E2E 추적이 가능하게 한다.
7. `BI 포탈/비즈메타` DB 공유 시 **스키마·계정·백업 단위**를 문서화한다.
8. 레이어드 거버넌스의 품질·흐름관리 WAS와 본 비즈메타의 **API/Batch 계약**을 일치시킨다.

## 8. 프로토콜별 특성 요약

| 방식 | 장점 | 위험 | 통제 포인트 |
|---|---|---|---|
| UI Link | 사용자 문맥 유지, 제품 UX | 세션 위변조, 제품 종속 | 토큰·허용 URL·로그아웃 연동 |
| 실시간 | 메타 변경 즉시 반영 | 유실·중복·포탈 부하 | 재처리, 백프레셔, 보정 Batch |
| Rest API | 표준·보안 정책화 | 타임아웃·쿼터 | APIM 정책, 멱등, 감사 |
| DB Batch | 대량·안정적 동기화 | 지연·충돌 | SLA, 증분키, 소유권, 모니터링 |

## 9. 품질·위험과 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| 포탈/비즈메타 DB 공유 모호 | 장애·배포 결합 | 스키마·인스턴스 분리 여부 확정 |
| 실시간 유실 | 포탈 메타 불일치 | 이벤트 재처리 + 일 배치 정합 |
| Batch 양방향 충돌 | 메타 오염 | 원천 시스템별 마스터 지정 |
| Storage APIM 우회 | 감사 공백 | 게이트웨이 또는 Storage 정책 강화 |
| 코어뱅크 과도 호출 | 계정계 부하 | 캐시·허브 경유·쿼터 |
| UI Link만으로 권한 의존 | 데이터 권한 우회 | 비즈메타에서 권한 재검증 |
| 품질·IT 메타 Batch 지연 | 거버넌스 지표 왜곡 | SLA·지연 알람·임시 표시 |

## 10. 점검 체크리스트

- [ ] 비즈메타 App과 `BI 포탈/비즈메타` DB의 배포·백업·계정 경계가 정의되어 있는가?
- [ ] OLAP UI Link의 인증·세션·파라미터 허용 목록이 있는가?
- [ ] “실시간 배치 필요에 따라”의 트리거·SLA·실패 보정이 문서화되어 있는가?
- [ ] 데이터허브·HR·품질·IT 메타 각 Batch의 주기·증분·충돌 규칙이 있는가?
- [ ] Object Storage Rest의 권한·암호화·감사가 있는가?
- [ ] CruzAPIM에 코어뱅크 API Product·쿼터·타임아웃이 등록되어 있는가?
- [ ] Rest/실시간/Batch 각각 추적 ID(GUID/Job ID)가 남는가?
- [ ] 레이어드 거버넌스(품질·흐름관리)와 비즈메타 간 API/Batch 계약이 일치하는가?
- [ ] BI포탈 시스템구조도의 거버넌스↔Storage 경로와 본 도의 정합이 확인되었는가?

## 11. 종합 평가

이 장표의 비즈메타 연관관계는 **애플리케이션·DB를 중심에 두고, UI Link·실시간·Rest·DB Batch를 매체별로 분리한 구조**다. OLAP 문맥 연계, 포탈 배치 실시간 반영, 허브·HR·품질·IT 메타의 Batch 정합, Storage·코어뱅크 Rest가 한 그림에 정리되어 있다.

운영 품질은 **DB 공유 범위 확정, 실시간+Batch 이중화, Batch 소유권, APIM 코어 보호, Storage 감사**에 좌우된다. 데이터거버넌스 레이어드 아키텍처·BI포탈 시스템구조도와 함께 읽어야 포탈·품질·메타·스토리지의 전체 I/F가 닫힌다.
