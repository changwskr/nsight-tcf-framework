## 1. 한 줄 요약

**서비스 제어 처리 구조**는 Layered Architecture 위에서 **Controller → Service → DAO** 단방향 계층 호출을 강제하고, 5가지 호출 시나리오마다 **허용(O)/금지(X)** 를 규정한다. **서비스 제어의 핵심**은 Service가 아니라 **Controller(④)가 0~n Service 호출을 orchestration**하고, 경계가 멀수록 **Controller→Controller**로 승격한다는 점이다 (→ §6).

## 4. 호출 구조 TEXT 표그림

### 4.1 5가지 호출 시나리오 요약

| No | 시나리오 | From → To | 허용 Caller | 허용 Callee | 금지 패턴 |
|---:|---|---|---|---|---|
| **①** | **기능 內** | 동일 기능 A | Controller→Service, Service→DAO | Service, DAO | C→DAO, C→C, S→S |
| **②** | **타 기능** | CM-A → CM-B | Controller→**타 기능 Service** | Service | C→C, S 직접 호출 |
| **③** | **업무 공통 유틸** | CM-A → CO 공통 | Controller→**공통 Service** | 공통 Service | Service/DAO 직접 |
| **④** | **타 어플리케이션** | CO-C → MG-D | **Controller→Controller** | Controller | C→타 Service/DAO |
| **⑤** | **타 어플 그룹** | MP → BL (CR-E) | **Controller→Controller** | Controller | 그룹 간 S/DAO 직접 |

### 4.3 Caller × Callee O/X 매트릭스 (하단 표)

피호출(Callee) 레이어: **Controller / Service / DAO** 순. `O`=허용, `X`=금지.

| Caller ↓ \ 시나리오 → | ① 기능 內 | ② 타 기능 | ③ 업무 공통 | ④ 타 어플 | ⑤ 타 그룹 |
|---|---|---|---|---|---|
| **Controller** | X / **O** / X | X / **O** / X | **O** / X / X | **O** / X / X | **O** / X / X |
| **Service** | X / X / **O** | X / X / X | X / X / X | X / X / X | X / X / X |
| **DAO** | X / X / X | X / X / X | X / X / X | X / X / X | X / X / X |

### 4.4 매트릭스 해석표 (Caller 관점)

| Caller | ① 기능 內 | ② 타 기능 | ③ 공통 | ④ 타 어플 | ⑤ 타 그룹 |

## 5. 핵심 규칙 분석

### 5.1 계층 내 (①) — 기능 內

```text
Controller ──O──> Service ──O──> DAO ──> DB
     │X              │X
     └── DAO         └── Service / Controller
```

- **Controller**는 **Service만** 호출 (DAO 직접 호출 금지)
- **Service**는 **DAO만** 호출 (Service→Service 금지)
- **DAO**는 **어떤 레이어도 호출하지 않음** (말단)

### 5.2 기능 간 (②) — 타 기능

- **Controller** → **다른 기능의 Service** 호출 **허용**
- **Controller** → **다른 Controller** **금지** (Facade/HTTP 경유 필요)

### 5.3 업무 공통 (③)

- **Controller** → **업무공통 유틸리티(CO) Service** **허용**
- Service/DAO가 공통 유틸을 **직접** 호출하는 패턴은 **금지**

### 5.4 타 어플리케이션 (④) · 타 그룹 (⑤)

- **반드시 Controller → Controller**
- 타 어플/그룹의 **Service·DAO 직접 호출 엄격 금지**
- 경계 넘을수록 **진입점을 Controller로 승격** — API·TCF ServiceID 경계와 정합

## 6. 서비스 제어 원칙 (Principles)

「서비스 제어」는 Biz Service 클래스 하나의 CRUD를 말하는 것이 아니라, **누가·어디서·어떤 경로로·몇 개의 Service를 호출할 수 있는지**를 아키텍처가 강제하는 **실행 통제(Execution Control)** 를 의미한다. 호출구조 정의(17번)는 그 통제 규칙을, 거래 처리 구조(15번)는 **Controller가 통제 주체**임을, 선/후 범위(16번)는 **통제 Scope**를 각각 보여 준다.

### 6.1 제어의 3축

| 축 | 질문 | 담당 장표 | 핵심 답 |
|---|---|---|---|
| **When** | 언제 통제하나 | [거래 처리 구조](./거래_처리_구조_분석.md) | ①~⑧ 파이프라인 · ④ Controller가 본 처리 orchestration |
| **Where** | 어디까지 적용하나 | [선/후 처리 범위](./선후_처리_범위_분석.md) | L1~L5 Scope 중첩 · 경계가 넓을수록 상위 훅 |
| **Who→Whom** | 누가 누구를 호출하나 | **본 장표** | C→S→DAO · 경계↑ = C→C 승격 |

### 6.2 7대 서비스 제어 원칙

| No | 원칙 | 내용 | 근거 |
|---:|---|---|---|
| **P1** | **단일 오케스트레이션** | 업무 흐름·복수 Service 조합(0~n)은 **Controller(④)만** 수행 | 15번 ④ · 17번 ②③ |
| **P2** | **서비스ID = 통제 키** | 서비스ID ↔ Controller Method **1:1** — 거래·로그·Evidence·Timeout의 식별자 | 15번 ④ |
| **P3** | **계층 단방향** | Controller→Service→DAO **만** 허용 · 역방향·횡단 금지 | 17번 ① · 매트릭스 |
| **P4** | **Service 비연쇄** | Service→Service **금지** — 재사용은 Controller가 다시 호출 | 17번 ① S→S X |
| **P5** | **경계 승격** | 타 기능·타 어플·타 그룹으로 갈수록 **Controller→Controller**로만 | 17번 ④⑤ |
| **P6** | **DAO 말단화** | DAO는 **호출 주체 불가** · Persistence만 | 17번 DAO 행 전체 X |
| **P7** | **DTO 경계** | 계층 간 데이터는 **DTO**로 전달 — Service 내부 상태 직접 노출 금지 | 15번 ④⑤ |

### 6.3 제어 주체 · 피제어 대상

```text
[제어 계층 — 바깥에서 안으로]

NH Cloud Framework (①⑧)
  · 거래 통제 · 자원 · TX Commit/Rollback · 입출력 로그
       │
       ▼
Controller (④)  ← ★ 서비스 제어의 유일한 업무 오케스트레이터
  · ServiceID 해석
  · 0~n Service 호출 순서·조합 결정
  · 타 기능/공통/타 어플 Service 호출 (17번 ②③)
  · 타 Controller 호출 (17번 ④⑤)
       │
       ▼
Service (⑤)  ← ★ 피제어 — Biz Logic만, 호출권 없음(타 Service/Controller)
  · DTO in/out
  · DAO 호출만
       │
       ▼
DAO  ← ★ 말단 — SQL 실행만, 어떤 레이어도 호출하지 않음
```

**해석**: Service는 **실행 단위**이지 **제어 단위**가 아니다. 「어떤 Service를 몇 번 부를지」는 항상 Controller(또는 TCF Handler/Facade를 거친 Controller 역할)의 책임이다.

### 6.4 경계별 제어 강도 (Escalation)

| 호출 거리 | 시나리오 | 허용 패턴 | 제어 강도 | 이유 |
|---|---|---|---|---|
| 최소 | ① 기능 內 | C→S→DAO | 낮음 | 동일 패키지·동일 TX |
| 중간 | ② 타 기능 | C→타 S | 중간 | 기능 경계 — Orchestrator 유지 |
| 중간 | ③ 공통 | C→CO S | 중간 | 공통 유틸 — 진입점 통제 |
| 높음 | ④ 타 어플 | **C→C** | 높음 | 업무구분 경계 · API/TCF |
| 최고 | ⑤ 타 그룹 | **C→C** (MP↔BL) | 최고 | 그룹 경계 · CruzAPIM/HTTP |

**원칙**: 경계가 멀어질수록 **Service를 직접 노출하지 않고 Controller(API)로 승격** — 배포 단위·TX·보안·Deadline 전파 지점을 명확히 한다.

### 6.5 Service 0~n 호출 제어 (15번 + 17번 통합)

거래 처리 ④에서 Controller는 **0~n개 Biz Service**를 호출한다. 호출구조 17번과 합치면 다음 제약이 붙는다.

| Controller 호출 대상 | 허용 | 금지 |
|---|---|---|
| 동일 기능 Service | O (0~n) | — |
| 타 기능 Service (②) | O | C→타 C |
| 공통 Service (③) | O | S→공통 S |
| 타 어플 Service | **X** | C→타 C만 (④) |
| DAO 직접 | **X** | C→DAO |
| Service끼리 연쇄 | **X** | S→S |

```text
Controller (서비스ID = mpcma0001S0)
  │
  ├─①─> mpcma0001Service     (동일 기능)
  ├─②─> mpcmb0002Service     (CM-B 타 기능)
  ├─③─> mpcoc0000Service     (CO 공통)
  │
  ├─④─X─> mpmgd0001Service   (타 어플 직접 — 금지)
  │       └── mpmg Controller ──> mpmgd0001Service  (C→C 후 허용)
  │
  └─⑤─X─> blcre0001Service   (타 그룹 직접 — 금지)
          └── bl Controller ──> blcre0001Service    (C→C 후 허용)
```

### 6.6 TCF 런타임 제어층 (PDMG AS-IS)

NSIGHT 장표(15·17) 위에 PDMG TCF가 **추가 제어층**을 둔다.

| 제어 기능 | TCF 컴포넌트 | 장표 대응 |
|---|---|---|
| ServiceID 라우팅 | `TransactionDispatcher` + Handler Registry | P2 서비스ID |
| 거래 통제·선처리 | `stf.preProcess()` | ① 시스템 선 |
| Timeout·Deadline | `ExecutionDeadline` + `OnlineTimeoutExecutor` | ① 거래 통제 |
| Worker·TX 경계 | Timeout ON 시 Worker Thread | ⑧ Commit/Rollback 전제 |
| 후처리·Evidence | `etf.postProcess()` | ⑧ 시스템 후 |
| Handler→업무 | `TransactionHandler` → Facade → Service | ④⑤ 본 처리 |

```text
HTTP → OnlineTransactionController
         → TcfFacade (ServiceID + dto)
              → stf (①)
              → Dispatcher → Handler (P2 라우팅)
                   → Facade → Service → DAO  (④⑤, P3·P4)
              → etf (⑧)
         → Response
```

**원칙**: TCF ON에서는 **Controller 다음에 바로 Service가 오지 않는다**. ServiceID 기반 **Dispatcher→Handler**가 ④ Controller 역할의 일부를 Framework가 대신한다. 호출구조 17번 규칙은 Handler/Facade 이후 **Service·DAO 계층에 동일 적용**된다.

### 6.7 원칙 위반 Anti-Pattern

| Anti-Pattern | 위반 원칙 | 위험 |
|---|---|---|
| Controller → DAO 직접 | P3 | 계층 붕괴 · TX/Timeout 추적 불가 |
| Service → Service | P4 | 오케스트레이션 분산 · 순환 의존 |
| 타 어플 Service 직접 `@Autowired` | P5 | 경계 침범 · 배포·TX 분리 실패 |
| ServiceID 없이 내부 호출 | P2 | 로그·Evidence·Timeout 미적용 |
| DAO에서 다른 DAO/Service 호출 | P6 | Persistence 계층 오염 |
| Entity/Map을 계층 간 직접 전달 | P7 | DTO 계약 붕괴 |

### 6.8 원칙 한눈에 (체크리스트)

개발·리뷰 시 확인:

- [ ] 새 연계는 **17번 매트릭스** ①~⑤ 중 어디에 해당하는가?
- [ ] Service 조합은 **Controller(또는 Handler/Facade)** 에만 있는가?
- [ ] 타 어플/그룹 호출은 **C→C**(HTTP/TCF/API GW)인가?
- [ ] ServiceID가 **Method 1:1**로 등록·추적되는가?
- [ ] Service 내부에 **다른 Service 호출**이 없는가?
- [ ] DAO는 **SQL/ORM만** 수행하는가?

## 7. 아키텍처 관점 핵심 정리

| 관점 | 규칙 |
|---|---|
| Layer Dependency | Controller → Service → DAO (단방향) |
| Same Function | C→S→DAO only |
| Cross Function | C→other S |
| Common Utility | C→common S (CO 등) |
| Cross Application | C→C only (MG, CO …) |
| Cross Group | C→C only (MP↔BL) |
| DAO Role | Persistence 말단 · 호출 불가 |
| Anti-Pattern | C→DAO, S→S, cross-boundary S/DAO |

## 9. PDMG/TCF 프레임워크 연관 시사점

| 규칙 | PDMG 구현 시사점 |
|---|---|
| C→S→DAO | Facade·Service·MyBatis 표준 stack |
| ④⑤ C→C | TCF `TransactionHandler` / HTTP API / CruzAPIM 경유 |
| 타 기능 S 호출 | 동일 JVM 내 `@Autowired` Service — **Controller에서만** |
| 금지: C→DAO | MyBatis를 Controller에서 직접 호출하지 않음 |
| 금지: cross S | Domain Service 직접 연계 → **Facade or Controller 경유** |
| Phase 5 Deadline | **Controller 경계** 넘는 호출에 ExecutionDeadline 전파 후보 |
