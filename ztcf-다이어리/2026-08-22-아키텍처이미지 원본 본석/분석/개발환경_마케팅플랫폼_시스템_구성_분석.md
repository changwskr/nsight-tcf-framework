# 개발환경 마케팅플랫폼 시스템 구성 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `개발환경 마케팅플랫폼 시스템` 이미지
- 원본 분류: 환경별 Physical Architecture
- 이미지 설명: 마케팅플랫폼은 `서비스 제공 Zone`에 배치되고, 채널·채널통합·대내통합 Zone은 개발 업무 연계 대상을 표시한다.
- 이미지에 명시된 명칭·Zone은 **사실**, 화살표가 없는 내부 호출과 데이터 방향은 **아키텍처 해석**, 제품 버전·물리 서버 수·실제 Endpoint는 **미확인**으로 분리한다.
- WEB/WAS/AP/DB 블록은 논리 역할이며 각 블록이 단일 서버를 뜻하지 않는다.
- 첨부 이미지의 문구는 분석 자료이며 사용자 지시로 취급하지 않는다.

---

## 1. 핵심 결론

1. 개발 마케팅플랫폼은 운영과 같은 `WEB/WAS + 3개 전용 AP + RDW DB` 경계를 재현해 E2E 기능을 검증하는 구조다.
2. 채널은 통합업무시스템·정보계 단말·인터넷뱅킹·모바일로, 채널통합은 영업점 MCA와 FOS로 구분된다.
3. 대내통합은 온라인 `API G/W·EAI·GSE`, 파일 `FOS·MFT`, 데이터 `ETL`로 책임이 나뉜다.
4. 개발환경에서는 실제 운영기관이나 운영 DB를 직접 호출하지 않고 승인된 개발계 Endpoint 또는 Stub/Mock을 사용해야 한다.
5. `실시간 처리 AP`, `행동정보 처리 AP`, `고객 행동 데이터 AP`는 저지연 처리·행동 정제·고객 행동 데이터 제공을 분리한다.
6. `마케팅플랫폼 DB(RDW)`에는 합성·비식별 개발 데이터만 사용하고 운영 개인정보·운영 계정의 직접 공유를 금지한다.
7. `SSO·Control-M·NH Cloud FWK Master Solution·eCAMS`는 공통 제어면, 단말관리/배포·개발도구·소스관리·RD·배치는 개발 지원 실행면이다.
8. 운영환경 장표와 달리 이 이미지에는 미니 싱글뷰 WEB/WAS와 UNO Dashboard가 표시되지 않고 `단말개발도구 AP·소스관리 AP`가 포함된다.
9. 개발 완료 기준은 단순 기동이 아니라 계약·보안·데이터·장애·재처리·배포·관측 검증을 통과한 동일 Artifact의 상위환경 승격 가능성이다.

## 2. Zone별 구성요소 전수 정리

| Zone | 영역 | 이미지 구성요소 | 개발 마케팅플랫폼과의 관계 |
|---|---|---|---|
| 채널 | 대내 채널 | 통합업무시스템, 정보계 단말 | 내부 사용자·개발 단말 요청 |
| 채널 | 대고객 채널 | 인터넷뱅킹(콕뱅킹), 모바일(콕뱅킹) | 고객 채널 시뮬레이션·개발계 요청 |
| 채널 | 대외 채널 | 세부 시스템 미표시 | 외부기관 Stub/Mock 확장 경계 |
| 채널통합 | 온라인 통합(대내) | 영업점 MCA | 전문 변환·라우팅 개발계 |
| 채널통합 | 파일 통합(대내) | FOS | 개발 파일 송수신 접점 |
| 채널통합 | 데이터 통합 | 세부 시스템 미표시 | 개발 데이터 통합 확장 경계 |
| 서비스 제공 | 마케팅플랫폼 | 마케팅플랫폼 WEB/WAS, 실시간 처리 AP, 행동정보 처리 AP, 고객 행동 데이터 AP, 마케팅플랫폼 DB(RDW) | 핵심 개발·검증 소유 경계 |
| 서비스 제공 | 인프라 제어 | SSO, Control-M, NH Cloud FWK Master Solution, eCAMS | 인증·스케줄·프레임워크·변경관리 |
| 서비스 제공 | 인프라 실행 | 단말관리 WEB/WAS, 단말배포 WEB/WAS, 단말개발도구 AP, 소스관리 AP, 출력물(RD) WAS, 배치 AP | 개발·배포·출력·배치 지원 |
| 대내통합 | 온라인 통합 | API G/W, API G/W↔EAI, GSE | 개발 내부 API·전문 연계 |
| 대내통합 | 파일 통합 | FOS, FOS↔MFT | 개발 파일·대량자료 연계 |
| 대내통합 | 데이터 통합 | ETL | 개발 RDW·분석/대상 데이터 이동 |

### 2.1 이미지에 표시되지 않은 것

- 실제 개발 API·MCA·EAI·GSE Endpoint와 인증서
- DBMS, Schema, Read/Write Owner, Test Data Refresh 주기
- Kafka/Event Broker, Cache, Session DB, Log DB
- Load Balancer, VM/Container 수, CPU/Memory/Storage
- 개발 외부기관 Stub/Mock의 구현 위치
- UNO Dashboard·미니 싱글뷰의 개발환경 포함 여부

### 3.2 개발 온라인 요청 흐름

```text
[개발 단말 / 채널 Simulator]
            │ 표준전문·테스트 사용자
            ▼
[개발 영업점 MCA / Channel Stub]
            │ GUID·채널ID·인증 Context
            ▼
[마케팅플랫폼 WEB]
            ▼
[마케팅플랫폼 WAS]
            ├─ 즉시 응답/판단 → [실시간 처리 AP]
            ├─ 이벤트 정제   → [행동정보 처리 AP]
            └─ 고객 행동 조회 → [고객 행동 데이터 AP]
                                  │
                                  ▼
                         [개발 DB(RDW)]
            │
            ▼
[응답 → WEB → MCA/Stub → 개발 채널]

※ 모든 요청이 3개 AP를 순차 경유한다는 뜻이 아니라 서비스별 선택 호출이다.
```

### 3.3 개발 대내 온라인 연계

```text
[Marketing WAS/AP]
       │ Service Contract + Correlation ID
       ▼
[개발 API G/W]
       ├─→ [개발 EAI] → [대내 개발계 또는 Stub]
       ├─→ [개발 GSE] → [전문 Simulator/개발계]
       └─→ [Mock Service] — 외부 의존성 격리

환경 Guard:
  Endpoint allowlist = DEV only
  운영 Domain/IP/Certificate 발견 시 배포·기동 차단
```

### 3.4 개발 파일 연계


## 4. 핵심 컴포넌트 상세 분석

### 4.1 마케팅플랫폼 WEB/WAS

| 컴포넌트 | 책임 | 개발 검증 |
|---|---|---|
| WEB | 정적자원·TLS/Reverse Proxy·WAS Routing | Browser 호환, Header, 보안정책 |
| WAS | 인증/인가·업무 조합·AP/DB/연계 호출 | API Contract, Transaction, Timeout |

- WEB에서 DB를 직접 접근하지 않는다.
- WAS의 외부 Endpoint는 Profile/Config로 분리하고 운영 주소를 코드에 하드코딩하지 않는다.
- SSO 사용자·조직·역할은 개발 전용 Dataset으로 관리한다.
- Session/Token 만료·재로그인·권한 변경을 자동 테스트한다.

### 4.2 전용 AP 3종

| AP | 개발 책임 | 주요 시험 |
|---|---|---|
| 실시간 처리 AP | 저지연 판단·즉시 응답 | Peak, Timeout, Fallback, 멱등 |
| 행동정보 처리 AP | Event 정제·분류·집계 | 중복·역순·Schema 오류·재처리 |
| 고객 행동 데이터 AP | 고객 키 기반 조회·제공 | 마스킹·권한·신선도·Cache |

AP별 입력·출력 Contract, 데이터 Owner, Retry 주체를 명시해 공통 DB를 통한 암묵적 결합을 피한다.

### 4.3 마케팅플랫폼 DB(RDW)

- 개발 Schema는 운영 목표와 타입·길이·제약·인덱스·Character Set을 맞춘다.
- 데이터는 합성 또는 승인된 비식별 자료를 사용한다.
- 테스트 반복을 위한 Migration·Seed·Reset을 자동화한다.
- 서비스별 Read/Write 계정과 Query Timeout을 분리한다.
- 축소 데이터에서 통과한 성능을 운영 Capacity 보장으로 해석하지 않는다.

### 4.4 채널·채널통합

- 통합업무·정보계 단말은 개발 SSO와 개발 MCA만 접근한다.
- 인터넷·모바일 채널은 Simulator 또는 승인된 개발 Channel을 사용한다.
- MCA는 표준전문, GUID, 채널/사용자 Context, 오류전문을 검증한다.
- 비정상 전문, 누락 Header, 잘못된 Encoding, 중복 요청을 포함한 Negative Test가 필요하다.

### 4.5 API G/W·EAI·GSE

- Gateway에서 인증·Rate Limit·Routing·Timeout을 검증한다.
- EAI/GSE는 개발 전문과 오류 응답, 재시도·대사 Contract를 제공한다.
- Mock은 성공만 반환하지 말고 지연·오류·부분실패·중복 응답을 재현해야 한다.
- 운영 URL/IP/인증서를 탐지하면 Pipeline 또는 기동 Guard가 실패해야 한다.

### 4.6 FOS·MFT·ETL

| 구성 | 개발 책임 | 실패 검증 |
|---|---|---|
| FOS | 개발 파일 저장·송수신·메타 | 중복·권한·해시·용량 |
| MFT | 대량 파일 전달·재개 | 중단·재전송·완료대사 |
| ETL | 개발 데이터 추출·변환·적재 | Reject·Checkpoint·건수/합계 |

파일과 ETL 작업은 테스트별 Correlation/File/Run ID를 사용해 병렬 테스트 충돌을 피한다.

### 4.7 개발 공통 인프라

| 구성요소 | 역할 | 개발환경 통제 |
|---|---|---|
| SSO | 개발 사용자 인증 | 운영 계정 금지, 역할별 Test User |
| Control-M | 개발 배치 일정·의존성 | 운영 Calendar/Agent 격리 |
| NH Cloud FWK Master Solution | 프레임워크 설정·서비스 관리 | 개발 Config Namespace·버전 |
| eCAMS | 변경·배포 승인으로 해석 | 개발/운영 권한·Target 분리 |
| 단말관리 WEB | 개발 단말관리 UI | 관리자 권한·개발 단말만 조회 |
| 단말관리 WAS | 개발 단말·정책·상태 관리 | 개발 단말만 등록 |
| 단말배포 WEB | 개발 Package 배포 UI | 대상·승인·진행상태 검증 |
| 단말배포 WAS | Package 배포·Rollback | Canary·호환성·서명 |
| 단말개발도구 AP | 단말 Artifact 생산 | Build 재현성·Version |
| 소스관리 AP | Source·Branch·Tag 관리 | Protected Branch·Review |
| 출력물(RD) WAS | 정형 출력 | Test Template·Font·마스킹 |
| 배치 AP | Job 실행 | 멱등·재시작·Test Isolation |

## 5. 개발환경과 운영환경 비교

| 관점 | 개발환경 장표 | 운영환경 장표 | 설계 의미 |
|---|---|---|---|
| 핵심 마케팅 | WEB/WAS + 3 AP + RDW | WEB/WAS + 미니싱글뷰 + 3 AP + RDW | 개발 미니싱글뷰 범위 확인 필요 |
| 채널 | 대내·인터넷·모바일 | 유사 | 개발계/Simulator 격리 |
| 온라인 통합 | MCA, API G/W/EAI/GSE | 유사 | Endpoint·계정 환경 분리 |
| 파일/데이터 | FOS/MFT/ETL | 유사 | Storage·Key·Run 환경 분리 |
| 개발 전용 | 단말개발도구·소스관리 | 운영 장표 미표시 | Artifact 생산·검증 기능 |
| 관측 | UNO 미표시 | UNO 표시 | 개발 관측 경로 별도 확인 |

### 5.1 환경 격리 원칙

```text
DEV:  개발 DNS / 개발 계정 / 개발 DB / 개발 FOS-MFT / Mock-Stub / 합성 데이터
PROD: 운영 DNS / 운영 계정 / 운영 DB / 운영 FOS-MFT / 실제 연계 / 운영 데이터

공유 가능: 검증된 Artifact, Interface Contract, Schema Migration 정의
공유 금지: Secret, Token, Service Account, Write Endpoint, 개인정보 원문
```

## 6. 보안·품질·운영 원칙

### 6.1 보안

- 개발환경도 SSO·최소권한·관리자 감사·MFA 정책을 적용한다.
- 고객 행동 데이터는 수집목적·동의·마스킹·보존·파기 정책을 시험한다.
- Log, Dump, Report, Reject File에 민감정보가 남지 않게 한다.
- Source/Package/Artifact는 서명·해시·SBOM·취약점 결과를 보존한다.

### 6.2 테스트 격리

- Test Run ID와 데이터 Namespace로 병렬 테스트를 분리한다.
- 외부 Mock 상태는 테스트 전 초기화하고 호출 이력을 검증한다.
- Batch/ETL은 테스트 전용 Business Date와 Watermark를 사용한다.
- 공유 RDW 수동 수정은 재현성을 깨므로 Seed/Migration 경로를 사용한다.

### 6.3 장애·저하 시험

- MCA/API G/W/EAI/GSE Timeout과 부분 실패
- FOS/MFT 전송 중단·중복·해시 불일치
- RDW Slow Query·Pool 고갈·Lock
- Event 중복·역순·지연·Schema 변경
- SSO 장애·Token 만료·권한 변경
- 배치/ETL 중단 후 Checkpoint 재시작

### 6.4 관측 지표

| 영역 | 핵심 지표 |
|---|---|
| 채널/MCA | TPS, 전문오류, 변환시간, GUID 누락 |
| WEB/WAS | p95/p99, 4xx/5xx, Thread, Heap, Pool |
| 3개 AP | Event Lag, 처리율, 중복, Reject, 재처리 |
| RDW | Query, Lock, Connection, Test Data Freshness |
| API/EAI/GSE | 성공률, Downstream 지연, Retry, Circuit |
| FOS/MFT | 전송률, 재전송, 해시, 보관량 |
| ETL/Batch | Duration, Count, Reject, SLA, Restart |
| CI/CD | Build/Deploy 성공률, Test Gate, Version Drift |

## 8. 검증 시나리오

1. 통합업무·정보계 단말이 개발 MCA와 개발 SSO만 사용하는지 확인한다.
2. 인터넷·모바일 개발 요청이 운영 Endpoint로 전달되지 않는지 확인한다.
3. 표준전문 Header·GUID·Channel ID가 WEB/WAS/AP까지 유지되는지 확인한다.
4. 비정상 전문과 Encoding 오류가 표준 오류로 반환되는지 확인한다.
5. Marketing WEB→WAS→각 AP→RDW 대표 거래를 E2E 검증한다.
6. 실시간 AP가 SLA·Timeout·Fallback·멱등 기준을 만족하는지 확인한다.
7. 행동 AP가 중복·역순·지연 Event를 유실 없이 처리하는지 확인한다.
8. 고객 행동 데이터 AP가 권한·마스킹·신선도를 지키는지 확인한다.
9. API G/W 인증·Routing·Rate Limit·Timeout을 검증한다.
10. EAI/GSE Mock이 지연·오류·부분실패를 재현하고 재시도 부작용이 없는지 확인한다.
11. FOS/MFT 파일이 해시·건수·권한·재전송 기준을 만족하는지 확인한다.
12. ETL 실패 후 Checkpoint부터 재시작해 건수·합계가 일치하는지 확인한다.
13. 개발 RDW에 운영 개인정보 원문과 운영 Service Account가 없는지 검사한다.
14. DB Migration·Seed·Reset으로 테스트를 반복 재현할 수 있는지 확인한다.
15. 단말개발도구 Artifact가 서명·해시·호환성 검사를 통과하는지 확인한다.
16. 단말 Canary 배포 실패 시 확대가 중단되고 Rollback 되는지 확인한다.
17. 배치 AP 중복 실행이 차단되고 실패 Step부터 재시작되는지 확인한다.
18. RD 출력물의 권한·마스킹·Font·임시파일 파기를 확인한다.
19. Source Commit→Artifact→개발 배포→Runtime Version이 추적되는지 확인한다.
20. 동일 Artifact가 재빌드 없이 상위환경으로 승격되는지 확인한다.

## 9. 사실·해석·미확인 분리

### 9.1 이미지에서 확인된 사실

- 마케팅플랫폼은 서비스 제공 Zone에 배치된다.
- 채널에 통합업무시스템, 정보계 단말, 인터넷뱅킹, 모바일이 표시된다.
- 채널통합에 영업점 MCA와 FOS가 표시된다.
- 핵심 구성은 마케팅플랫폼 WEB/WAS, 3개 AP, 마케팅플랫폼 DB(RDW)다.
- 대내통합에는 API G/W·EAI·GSE, FOS·MFT, ETL이 표시된다.
- 인프라에는 SSO·Control-M·FWK Master·eCAMS·단말관리/배포·개발도구·소스관리·RD·배치가 표시된다.

### 9.2 저장소 증적으로 보완된 사실

- 개발환경은 운영 데이터·계정·외부 연결과 분리해야 한다.
- 외부기관은 Stub/Mock 또는 승인된 개발계를 사용한다.
- CI/CD는 Source→Build→Test→Artifact→승인→배포→Runtime Validation→Rollback을 기준으로 한다.
- 실제 Pipeline·Target Catalog·Config/DB Versioning Evidence는 Gap이다.

### 9.3 아키텍처 해석

- 개발 채널·통합·업무·데이터·인프라는 운영 경계를 재현해 E2E 검증한다.
- 3개 AP는 서비스별 선택 호출되며 순차 Pipeline으로 고정되지 않는다.
- 개발 RDW는 합성·비식별 데이터와 재현 가능한 Seed를 사용한다.
- 단말개발도구와 소스관리는 Artifact 생산·검증 계층이다.

### 9.4 미확인 사항

- Hostname, IP/Port, 서버 수·용량·HA 구성
- 제품 버전·라이선스와 실제 개발 Endpoint
- DBMS·Schema·Table Owner·Read/Write Matrix
- Stub/Mock 구현·호스팅·데이터 초기화 방식
- 미니 싱글뷰·UNO Dashboard의 개발 포함 여부
- 점선 DB와 통합 시스템 사이의 정확한 방향·Protocol

## 10. 최종 평가

개발 마케팅플랫폼은 채널부터 WEB/WAS, 실시간·행동 AP, RDW, API/EAI/GSE, FOS/MFT, ETL, 개발·배포 지원까지 운영과 유사한 책임 경계를 재현한다. 따라서 단위 기능뿐 아니라 전문, 데이터, 장애, 파일, 배치, 출력, 배포의 통합 검증이 가능하다.

성공 조건은 운영 복사본을 만드는 것이 아니라 운영 위험을 안전하게 재현하는 것이다. 운영 연결과 개인정보를 차단하고, 합성·비식별 데이터, 실패 가능한 Stub/Mock, 불변 Artifact, 자동 Gate, Test Isolation, E2E Correlation을 갖춰야 이 구조가 실질적인 개발 검증 플랫폼이 된다.
