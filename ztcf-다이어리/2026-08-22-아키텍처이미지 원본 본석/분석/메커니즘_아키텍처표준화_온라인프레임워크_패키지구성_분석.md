# 메커니즘·아키텍처 표준화 — 온라인 프레임워크 패키지 구성 분석

## 1. 핵심 결론

이 장표는 온라인 업무 구현을 **업무 분류 코드와 기술 계층을 결합한 Java 패키지 표준**으로 정의한다.

```text
nhnis                         Top
└── mp                        애플리케이션 그룹(대구분)
    └── co                    애플리케이션(업무 구분)
        └── a                 기능(세부 업무 구분)
            ├── controller    요청 접수·흐름 제어
            ├── service       비즈니스 로직·트랜잭션
            ├── dao           데이터 접근
            └── dto           입출력 데이터 계약

resource
└── mp/co/a                   동일 업무 코드 구조
    ├── mpcoa0001-ORA.xml     SQL Mapper
    └── mpcoa0002-ORA.xml
```

핵심은 화면이나 개발자 편의가 아니라 **대구분→업무→세부업무라는 동일한 업무 분류를 Java 코드와 SQL 리소스에 함께 적용**하는 것이다. 이를 통해 클래스·SQL·서비스 ID의 소유 업무를 경로만으로 식별하고 변경 영향과 배포 단위를 추적할 수 있다.

## 2. 원본 장표 FACT 전사

### 2.1 업무 분류 계층

| 계층 | 원본 예시 | 의미 |
|---|---|---|
| Top | `nhnis` | 최상위 패키지 |
| 애플리케이션 그룹 | `mp` | 대구분 |
| 애플리케이션 | `co` | 업무 구분 |
| 기능 | `a`, `b` | 세부 업무 구분 |
| 업무 구현 | `controller`, `service`, `dao`, `dto` | 기술 계층 |

### 2.2 Java 패키지와 클래스 예시

| 영역 | 패키지 | 예시 파일 |
|---|---|---|
| Controller | `nhnis.mp.co.a.controller` | `mpcoaController.java` |
| Service | `nhnis.mp.co.a.service` | `mpcoa0001Service.java` |
| DAO | `nhnis.mp.co.a.dao` | `mpcoa0001DAO.java` 계열 |
| DTO | `nhnis.mp.co.a.dto` | `mpcoa0001S0DTOin.java`, `mpcoa0001S0DTOout.java`, `mpcoa0001S0DTOio.java` |

> DAO 영역에는 이미지상 같은 파일명이 두 차례 보인다. 인터페이스/구현체 구분인지 단순 중복 표기인지는 원본 설계서 또는 실제 소스로 확인해야 한다. DTO의 `S0`도 숫자 0인지 영문 O인지 확인이 필요하다.

### 2.3 SQL 리소스 예시

```text
resource/
└── mp/
    └── co/
        └── a/
            ├── mpcoa0001-ORA.xml
            └── mpcoa0002-ORA.xml
```

### 2.4 원본 책임 설명

#### Controller

- 서비스 ID는 Controller Class Method에 대응한다.
- 업무 본 처리에 해당하는 거래 처리 흐름 제어 역할을 수행한다.
- Service Method를 호출한다.

#### Service

- 서비스 ID는 Service Class와 연결된다.
- 업무 처리를 위한 Biz 로직 구현체다.
- DTO와 DAO 객체를 사용해 로직을 처리한다.

#### DAO

- 서비스 ID는 DAO Class와 연결된다.
- DB Access의 C/R/U/D 로직 구현체다.
- SQL ID를 호출하여 OR Mapper를 통해 DB Data Access를 수행한다.

#### DTO

- 서비스 입력과 출력 값을 처리하는 데이터 구현체다.
- 입력과 출력이 같거나 동일 데이터셋을 공유하는 경우를 구분해 처리한다.

            │       └── mpcoa0001S0DTOio.java

## 4. 온라인 요청 처리 메커니즘

```text
Client / Controller Adapter
          │ Service ID + Input Data
          ▼
┌─────────────────────────────┐
│ Controller                  │
│ - 서비스 ID 매핑            │
│ - 입력 검증·권한 컨텍스트   │
│ - 업무 흐름 진입            │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ Service                     │
│ - 비즈니스 규칙             │
│ - 트랜잭션 경계             │
│ - DTO 조합                  │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ DAO                         │
│ - SQL ID 호출               │
│ - C/R/U/D                   │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ OR Mapper XML               │
│ resource/mp/co/a/*-ORA.xml │
└──────────────┬──────────────┘
               ▼
              DB
               │
               └── DAO → Service → Controller → Response
```

정상 의존 방향은 `Controller → Service → DAO → Mapper/DB`다. 역방향 참조와 Controller의 직접 DAO 호출은 금지하는 것이 바람직하다.

## 5. 계층별 상세 책임

### 5.1 Controller

담당:

- Service ID 또는 URI를 메서드에 매핑한다.
- 요청 DTO 변환과 형식 검증을 수행한다.
- 인증된 사용자·채널·추적 ID를 Service에 전달한다.
- 표준 응답·오류 형식으로 변환한다.

비담당:

- 핵심 업무 규칙
- 직접 SQL 호출
- 장기 트랜잭션
- 다수 DAO의 복잡한 조합

Controller는 얇아야 하며 채널 프로토콜을 업무 로직과 분리해야 한다.

### 5.2 Service

- 업무 규칙과 처리 순서를 구현한다.
- 여러 DAO·외부 서비스를 조합한다.
- 트랜잭션 시작·Commit·Rollback 경계를 소유한다.
- 업무 예외를 의미 있는 코드로 생성한다.
- 중복 요청 방지와 상태 전이를 통제한다.

서비스 클래스가 특정 화면의 데이터 포맷에 과도하게 의존하면 재사용성이 낮아지므로 입력 DTO를 업무 명령으로 변환하는 경계를 둔다.

### 5.3 DAO

- SQL Mapper의 Statement ID를 호출한다.
- DB 접근 기술과 Result Mapping을 캡슐화한다.
- 한 메서드는 명확한 데이터 접근 의도를 가진다.
- Commit·Rollback을 직접 수행하지 않고 Service 트랜잭션에 참여한다.

`selectData`, `updateData` 같은 모호한 이름보다 `findCustomerSummary`, `updateConsentStatus`처럼 의도를 드러내는 이름이 바람직하다.

### 5.4 DTO

| 유형 | 목적 |
|---|---|
| `DTOin` | 서비스 입력 계약 |
| `DTOout` | 서비스 출력 계약 |
| `DTOio` | 입출력 공용 구조가 필요한 경우 |

- DTO는 외부 계약이므로 필드 의미·필수 여부·길이·형식·버전을 관리한다.
- DB Entity를 그대로 노출하지 않는다.
- 민감정보의 로그 출력과 직렬화를 제한한다.
- 입출력 모델을 무조건 통합하지 말고 변경 주기가 다르면 분리한다.

## 6. 서비스 ID와 클래스 명명 분석

장표 예시는 다음 조합을 암시한다.

```text
mp + co + a + 0001
│    │    │    └─ 서비스/일련번호
│    │    └────── 세부 업무
│    └─────────── 업무 구분
└──────────────── 대구분
```

예:

```text
패키지       nhnis.mp.co.a.service
서비스       mpcoa0001Service
DAO          mpcoa0001DAO
DTO          mpcoa0001S0DTOin/out/io
Mapper       mpcoa0001-ORA.xml
```

권고 자동 검증:

- 패키지 코드와 클래스 접두부가 일치해야 한다.
- Service ID는 저장소 전체에서 유일해야 한다.
- Service·DAO·DTO·Mapper가 동일 업무 ID로 추적되어야 한다.
- 대소문자, 숫자 자리수와 접미사를 고정한다.
- 폐기된 ID는 재사용하지 않는다.

## 7. SQL Mapper 표준

- Mapper namespace는 DAO 또는 업무 ID와 일치시킨다.
- Statement ID는 CRUD와 업무 의미를 함께 표현한다.
- `SELECT *`를 금지하고 컬럼을 명시한다.
- 바인드 변수를 사용하고 문자열 치환 SQL을 제한한다.
- 대량 조회에는 최대 건수·Paging·Timeout 기준을 적용한다.
- SQL 주석에 업무 ID·변경 사유를 남기되 개인정보는 기록하지 않는다.
- Oracle 전용 SQL은 `-ORA.xml` 접미사 정책과 함께 관리한다.

```text
mpcoa0001DAO.method()
      │
      └── namespace.statementId
                 │
                 └── resource/mp/co/a/mpcoa0001-ORA.xml
```

## 8. 트랜잭션과 예외 처리

### 트랜잭션

- 트랜잭션 경계는 원칙적으로 Service에 둔다.
- 조회는 Read-only 속성을 적용한다.
- 외부 API 호출을 DB 트랜잭션 안에 오래 유지하지 않는다.
- 갱신 서비스는 멱등 키 또는 업무 유일키로 중복 반영을 방지한다.
- 여러 DB/외부 시스템을 묶는 경우 보상·Outbox 등 별도 패턴을 검토한다.

### 예외

```text
DB/기술 예외
   ↓ DAO에서 기술 컨텍스트 부여
업무 처리 예외
   ↓ Service에서 업무 오류코드 변환
표준 오류 응답
   ↓ Controller에서 채널 응답 생성
Client
```

- 내부 Stack Trace와 SQL을 사용자에게 노출하지 않는다.
- traceId·Service ID·오류코드로 로그를 연결한다.
- 예외 발생 시 트랜잭션 Rollback 정책을 명확히 한다.

## 9. 보안 표준

- Controller에서 인증정보 존재 여부와 권한 컨텍스트를 확인한다.
- 실제 업무 권한은 Service의 업무 규칙으로 검증한다.
- DTO 입력 길이·형식·허용값을 검증한다.
- DAO는 Prepared/Bound Parameter를 사용해 SQL Injection을 방지한다.
- 개인정보는 DTO·로그·오류 메시지에서 마스킹한다.
- 서비스 ID별 호출 권한과 감사 로그를 남긴다.
- 패키지 외부에 노출할 클래스와 메서드를 최소화한다.

## 10. 테스트 전략

| 계층 | 테스트 초점 |
|---|---|
| Controller | Service ID 매핑, 입력 검증, 표준 응답·오류 |
| Service | 업무 규칙, 상태 전이, 트랜잭션, 멱등성 |
| DAO | SQL 바인딩, Result Mapping, CRUD 정확성 |
| DTO | 직렬화, 필수값, 길이·형식, 하위 호환성 |
| Mapper | 실행계획, 인덱스, 경계값, 대량 데이터 |
| 통합 | Controller→Service→DAO→DB 종단 흐름 |

필수 구조 검증:

1. Controller가 DAO를 직접 참조하지 않는다.
2. Service가 Controller 패키지를 참조하지 않는다.
3. DAO가 Service 트랜잭션 경계를 침범하지 않는다.
4. Java 업무 경로와 Resource 업무 경로가 일치한다.
5. Service ID와 클래스·Mapper 연결이 유일하다.
6. DTO의 민감정보가 로그에 출력되지 않는다.

## 11. 빌드·배포·관측성

- ArchUnit 또는 정적 분석으로 계층 의존 규칙을 검사한다.
- Service ID 중복, Mapper 누락, Statement ID 오류를 빌드에서 차단한다.
- 애플리케이션 빌드와 Resource Mapper를 하나의 버전으로 패키징한다.
- 서비스별 호출 건수, 성공률, P95/P99, DB 시간, 오류코드를 관측한다.
- `traceId → Service ID → DAO Method → SQL ID`로 종단 추적한다.
- 배포 Manifest에 업무 코드와 변경 Service ID 목록을 포함한다.

## 14. 최종 평가

이 구조는 업무 분류와 기술 계층을 결합해 코드의 위치와 책임을 예측 가능하게 만든다. 표준의 실효성을 높이려면 패키지·클래스 이름만 통일하는 데 그치지 않고 **계층 의존성, Service 트랜잭션, DTO 계약, DAO/Mapper 연결, 서비스 ID 중복과 종단 관측성**을 빌드 단계에서 자동 검증해야 한다.
