# 논리기술아키텍처 정의 — 데이터거버넌스 분석

> 분석 대상: 첨부 이미지 `데이터거버넌스 논리 기술 아키텍처`  
> 원본 근거: `85737/22.png`, 원본 문서 68쪽  
> 분석 원칙: 이미지의 문구·배치·연결선을 **확인 사실**로 우선 기록하고, 설계상 해석과 미확정 사항을 분리한다.

---

## 1. 핵심 결론

이 구조는 데이터거버넌스를 하나의 단일 기능으로 보지 않고 다음 세 업무 도메인으로 분리한 논리 아키텍처다.

1. **비즈메타**: `업무 용어`, `표준 계수`를 관리한다.
2. **데이터 품질**: `CTQ`, `DQI`, `프로파일링`, `업무규칙(BR)`을 관리·실행한다.
3. **데이터 흐름**: `흐름 수집/파싱`, `흐름 분석/검색`을 담당한다.

세 도메인은 각각 WAS 계층을 가지며 공통 `VM → IaaS` 기반에서 실행된다. 데이터 계층은 `JDBC`로 `RDW`, `ADW`와 연계되고, `RDW → ETL → ADW` 흐름이 별도로 표현된다. `FOS`, `MFT`, `Cruz APIM`, `EAI`, `대외 MCA`가 대내·대외 메타 수집 경계를 형성한다.

```text
[인증 관리]
     │
[정보계 단말 / 패키지 단말]
     │ HTTP
     ▼
    [L4] → [WEB]
              │
              ▼
┌──────────────── 데이터거버넌스 ────────────────┐
│ [비즈메타 WAS]   [데이터 품질 WAS]   [데이터 흐름 WAS] │
│ 업무용어          CTQ / DQI           수집/파싱       │
│ 표준계수          프로파일링/BR       분석/검색       │
│                     VM → IaaS                         │
└──────────┬──────────────────┬─────────────────┘
           │ JDBC             │ JDBC/연계
           ▼                  ▼
         [RDW] ─── ETL ───▶ [ADW]
           │                  │
           ├─ FOS ─ IT 메타  ├─ 대내: APIM/EAI/FOS/MFT
           └─────────────────┴─ 대외: FOS/대외 MCA/MFT
```

## 2. 근거 수준

| 구분 | 내용 |
|---|---|
| 확인 사실 | 인증 관리, 정보계 단말, 패키지 단말, HTTP, L4, WEB이 표시됨 |
| 확인 사실 | 비즈메타·데이터 품질·데이터 흐름과 각 WAS가 표시됨 |
| 확인 사실 | VM, IaaS, JDBC, RDW, ETL, ADW가 표시됨 |
| 확인 사실 | IT 메타/FOS, 대내 시스템, 대외 시스템 및 연계 제품명이 표시됨 |
| 확인 사실 | GitLab, Git Runner, eCAMS, Nexus, FWK Manager가 개발자 영역에 표시됨 |
| 설계 해석 | `흐름 수집/파싱`과 `흐름 분석/검색`은 데이터 Lineage 및 영향도 분석 기반으로 해석 가능 |
| 설계 해석 | 세 WAS의 분리는 기능 책임과 장애영향도를 분리하기 위한 도메인 경계로 해석 가능 |
| 미확정 | `표준 계수`의 정확한 업무 정의와 관리 단위는 이미지로 확정할 수 없음 |
| 미확정 | 거버넌스 자체 저장소/DB는 이미지에 명시되지 않음 |
| 미확정 | 일부 연결선의 요청·응답 방향, 동기/비동기 여부, 프로토콜 상세는 확정할 수 없음 |

> `표준 계수`는 이미지의 원문을 그대로 사용한다. 이를 표준 코드, 계정계수, 산식계수 등 특정 개념으로 임의 치환하지 않는다.

## 3. 논리 계층과 책임

```text
L1 채널       : 정보계 단말 / 패키지 단말
       ↓
L2 접근       : HTTP / L4 / WEB / 인증 관리
       ↓
L3 업무       : 비즈메타 | 데이터 품질 | 데이터 흐름
       ↓
L4 실행       : WAS | VM | IaaS
       ↓
L5 데이터     : JDBC | RDW | ETL | ADW
       ↓
L6 통합       : FOS | MFT | Cruz APIM | EAI | 대외 MCA
       ↓
L7 개발운영   : GitLab | Git Runner | eCAMS | Nexus | FWK Manager
```

| 계층 | 주 책임 | 금지해야 할 결합 |
|---|---|---|
| 채널 | 사용자 요청·표시 | DB 직접 접속 |
| 접근 | 분산, 인증 연계, WEB 전달 | 품질규칙 직접 실행 |
| 거버넌스 업무 | 메타·품질·흐름 정책 | 물리 인프라 제어 |
| 데이터 | 조회·적재·분석 데이터 제공 | UI 세션 의존 |
| 통합 | 시스템 경계 변환·전송 | 업무 정의의 중복 보유 |
| 개발운영 | 형상·빌드·배포·관측 | 운영 데이터 무통제 반출 |

## 4. 사용자 접근과 인증

```text
[사용자]
   │
   ├─ [정보계 단말]
   └─ [패키지 단말]
          │ HTTP
          ▼
         [L4]
          │
         [WEB] ── 인증/권한 확인 ── [인증 관리]
          │
          └─ 업무별 WAS 라우팅
```

- L4는 가용한 WEB 노드로 요청을 분산하는 접근 경계로 해석한다.
- WEB은 정적 자원·접근 관문이며, 거버넌스 규칙 실행은 WAS 책임으로 둔다.
- 인증 관리의 제품, 토큰 형식, SSO 세션 저장소는 도면에 없다.
- 권한은 최소한 조회자, 등록자, 승인자, 관리자, 감사자로 분리하는 것이 적절하다.

## 5. 비즈메타 도메인

```text
┌──────────── 비즈메타 ────────────┐
│ [업무 용어]       [표준 계수]     │
│      └──────┬─────────┘          │
│             ▼                    │
│        [비즈메타 WAS]            │
└──────────────────────────────────┘
```

### 5.1 권장 생명주기

```text
후보 등록 → 중복/유사어 검사 → 담당자 검토 → 승인
   → 유효기간 적용 → 배포/참조 → 변경 또는 폐기 → 이력 보존
```

| 관리 객체 | 필수 관리 속성 |
|---|---|
| 업무 용어 | 불변 ID, 명칭, 정의, 동의어, 금칙어, 소유 부서, 담당자, 상태, 버전, 유효기간 |
| 표준 계수 | 불변 ID, 명칭, 정의, 단위, 산정 기준, 소유자, 상태, 버전, 유효기간 |

업무 용어의 이름이 변경되어도 식별자는 유지해야 참조 관계가 끊기지 않는다. 승인 전 객체가 운영 시스템에 노출되지 않도록 상태 기반 배포가 필요하다.

## 6. 데이터 품질 도메인

```text
┌────────────── 데이터 품질 ──────────────┐
│ [CTQ] ── 중요 품질 대상                 │
│ [DQI] ── 품질 측정 지표                 │
│ [프로파일링] ── 분포·Null·중복·패턴 탐색 │
│ [업무규칙(BR)] ── 업무 조건 검증         │
│                    ↓                     │
│              [데이터 품질 WAS]           │
└──────────────────────────────────────────┘
```

### 6.1 객체 관계

```text
[CTQ]
  └─ 중요 데이터 항목
       ├─ [DQI] 측정지표
       ├─ [프로파일링] 현황 탐색
       └─ [업무규칙(BR)] 적합성 검증
                  │
                  ▼
        품질 결과 → 이슈 → 개선 → 재측정
```

### 6.2 실행 파이프라인

```text
대상선정 → 스냅샷/조회 → 프로파일링 → BR 실행
 → DQI 계산 → 임계치 판정 → 이슈 발행 → 담당자 조치 → 재검증
```

예시 산식은 다음과 같이 정의할 수 있으나, 실제 산식은 별도 품질 표준으로 확정해야 한다.

```text
적합률(%) = 적합 건수 / 전체 검사 건수 × 100
오류율(%) = 오류 건수 / 전체 검사 건수 × 100
개선율(%) = (이전 오류 - 현재 오류) / 이전 오류 × 100
```

- 규칙은 SQL 문자열만 저장하지 말고 소유자, 목적, 대상, 버전, 임계치, 실행주기, 예외정책을 함께 관리한다.
- 대용량 프로파일링은 사용자 요청 스레드와 분리해 비동기 배치로 수행하는 편이 안전하다.
- 원천 오류와 플랫폼 실행 오류를 구분해야 잘못된 품질 경보를 막을 수 있다.

## 7. 데이터 흐름 도메인

```text
┌──────────── 데이터 흐름 ────────────┐
│ [흐름 수집/파싱]                    │
│       ↓ 표준 노드·엣지 변환         │
│ [흐름 분석/검색]                    │
│       ↓                             │
│ [데이터 흐름 WAS]                   │
└─────────────────────────────────────┘
```

### 7.1 Lineage 해석

```text
[원천 테이블.컬럼]
       │ ETL/SQL 변환
       ▼
[RDW 테이블.컬럼] ── ETL ──▶ [ADW 테이블.컬럼]
       │                         │
       └──── 보고서/지표/화면 ──┘
```

`Lineage`와 `영향도 분석`이라는 용어 자체는 이미지에 직접 표시되지 않는다. 다만 수집/파싱한 흐름을 분석/검색한다는 기능은 기술·업무 계보와 변경 영향도 분석을 구현하는 기반으로 해석할 수 있다.

### 7.2 권장 그래프 모델

```text
노드: System / DB / Schema / Table / Column / Job / API / Report
엣지: READS / WRITES / TRANSFORMS / CALLS / PRODUCES / CONSUMES
속성: source, version, collectedAt, validFrom, confidence, owner
```

수집 결과는 동일 객체를 중복 생성하지 않도록 안정된 식별 키와 멱등 Upsert를 사용해야 한다. 삭제 감지는 즉시 물리 삭제보다 `미관측/비활성` 상태 전환 후 유예 삭제가 안전하다.

## 8. 세 도메인의 협업 구조

```text
[비즈메타: 의미·소유권]
       │ 표준 객체 연결
       ▼
[데이터 흐름: 위치·이동·변환] ── 영향 대상 제공
       │ 품질 대상 연결
       ▼
[데이터 품질: 측정·판정·개선]
```

| 질문 | 주 도메인 | 협업 도메인 |
|---|---|---|
| 이 컬럼의 업무 의미는 무엇인가? | 비즈메타 | 데이터 흐름 |
| 어디서 생성되어 어디로 전달되는가? | 데이터 흐름 | 비즈메타 |
| 신뢰 가능한가? | 데이터 품질 | 비즈메타·데이터 흐름 |
| 변경 시 무엇이 영향받는가? | 데이터 흐름 | 비즈메타·품질 |
| 누가 승인하고 개선하는가? | 비즈메타/품질 | 인증·조직정보 |

## 9. RDW·ADW 데이터 연계

```text
                  ┌─ JDBC ─ [비즈메타]
[원천] → [RDW] ───┼─ JDBC ─ [데이터 품질]
          │       └─ JDBC ─ [데이터 흐름]
          │ ETL
          ▼
        [ADW] ───── JDBC/연계 ─── [거버넌스]
```

- 도면은 `RDW`, `ETL`, `ADW`, `JDBC`를 명시한다.
- RDW와 ADW의 구체 스키마, 읽기/쓰기 권한, 커넥션 풀, 접속 방향은 미확정이다.
- 품질·메타 조회 계정과 결과 적재 계정을 분리하고 최소 권한을 적용해야 한다.
- 대량 조회는 운영 부하를 피하도록 스냅샷, 읽기 복제본, 실행 시간대 통제를 검토한다.
- 거버넌스 자체 저장소/DB는 도면에 보이지 않으므로 별도 논리·물리 설계 확인이 필요하다.

## 10. IT 메타와 대내·대외 통합

```text
                     [IT 메타]
                         ▲
                        FOS
                         │
[데이터거버넌스] ────────┼──────── [RDW / ADW]
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
 [대내 시스템]                    [대외 시스템]
 Cruz APIM                       FOS
 EAI                             대외 MCA
 FOS                             MFT
 MFT
```

| 방식 | 적합한 용도 | 핵심 통제 |
|---|---|---|
| JDBC | DB 메타·품질 대상 조회 | 최소권한, 타임아웃, 부하 제한 |
| Cruz APIM | 내부 API 연계 | 인증, 스키마 버전, 호출량 제한 |
| EAI | 대내 메시지·서비스 중계 | 재처리, 순서, 중복 방지 |
| FOS | 파일 기반 교환 | 원자적 완료표시, 체크섬, 보관주기 |
| MFT | 관리형 파일 송수신 | 암호화, 송수신 증적, 재전송 |
| 대외 MCA | 대외 전문 연계 | 전문 표준, 상관키, 타임아웃 |

### 파일 수집 상태 모델

```text
RECEIVED → VALIDATED → PARSED → APPLIED → ARCHIVED
              └──────── 실패 ───────▶ QUARANTINED
```

## 11. 개발·배포·운영 도구

```text
[개발자]
   ├─ GitLab ─ 소스/리뷰/브랜치
   ├─ Git Runner ─ 빌드·테스트·배포 파이프라인
   ├─ Nexus ─ 불변 배포 산출물
   ├─ eCAMS ─ 변경·배포 통제
   └─ FWK Manager ─ 프레임워크/구성 관리
                │
                ▼
       WEB / WAS / VM / IaaS
```

### 배포 흐름

```text
Commit → Review → Build → Unit/Contract Test → Artifact Signing
 → Nexus 저장 → 승인 → 배포 → Smoke Test → 관측 → 완료/롤백
```

이미지는 도구 존재를 보여주지만 실제 파이프라인 순서와 자동화 수준은 보여주지 않는다. 운영 변경은 소스 버전, 산출물 해시, 승인번호, 배포자, 배포시간을 연결해 추적해야 한다.

## 12. 보안·개인정보·감사

```text
사용자 ─ 인증 ─ 권한정책 ─ 거버넌스 기능 ─ 데이터 접근
  │                  │                         │
  └──────────── 감사 이벤트 ──────────────────┘
```

- 메타 조회 권한과 원천 데이터 조회 권한은 분리한다.
- 프로파일링 표본에 개인정보가 포함될 수 있으므로 마스킹·표본 제한·반출 통제가 필요하다.
- 업무 용어·품질규칙·Lineage 변경은 변경 전후 값과 승인자를 감사 로그로 남긴다.
- 서비스 계정은 개인 계정과 분리하고 주기적으로 비밀정보를 회전한다.
- 로그에는 접속 비밀번호, 토큰, 개인정보 원문을 기록하지 않는다.

## 13. 신뢰성·재처리·관측

```text
요청/작업 생성 → correlationId 발급 → 실행 → 단계별 checkpoint
      │                                  │
      └─ 실패 → 재시도 가능성 판정 ─────┤
                    ├─ 일시 오류: backoff 재시도
                    └─ 영구 오류: 격리 + 운영자 조치
```

### 필수 관측 지표

| 영역 | 지표 예시 |
|---|---|
| WEB/WAS | 요청량, 오류율, p95/p99 지연, 활성 세션 |
| 메타 | 승인 대기, 변경 건수, 미매핑 객체 비율 |
| 품질 | 규칙 성공률, 오류율, 임계치 초과, 조치 SLA |
| 흐름 | 수집 성공률, 파싱 실패, 최신성, 고아 노드/엣지 |
| JDBC | 풀 사용률, 대기시간, 타임아웃, 장기 쿼리 |
| 파일 | 수신 지연, 체크섬 실패, 격리 파일, 재전송 |
| 배포 | 성공률, 롤백률, 버전 불일치 |

## 14. 주요 처리 시퀀스

### 14.1 업무 용어 승인

```text
등록자 → WEB → 비즈메타 WAS: 후보 등록
검토자 → 비즈메타 WAS: 중복/정합 검토
승인자 → 비즈메타 WAS: 승인
비즈메타 WAS → 연계 대상: 승인 버전 배포
```

### 14.2 데이터 품질 측정

```text
Scheduler → 품질 WAS: 규칙 실행
품질 WAS → RDW/ADW: 대상 조회(JDBC)
품질 WAS → 품질 계산: 프로파일링/BR/DQI
품질 WAS → 담당자: 임계치 초과 이슈
담당자 → 품질 WAS: 조치 및 재검증
```

### 14.3 흐름 수집

```text
Collector → FOS/MFT/API/JDBC: 메타 수집
흐름 WAS → Parser: 구문 분석
Parser → Graph Model: 노드·엣지 Upsert
사용자 → 흐름 WAS: 검색/영향도 조회
```

### 14.4 RDW→ADW 변경 영향 검토

```text
변경요청 → 흐름 검색 → 하류 ADW/보고서 후보 산출
        → 비즈메타 소유자 확인 → 품질규칙 영향 확인
        → 승인/보완 → 배포 → 수집 재실행 → 결과 대사
```

## 16. 설계 결정과 확인 필요 사항

### 16.1 우선 결정할 항목

1. `표준 계수`의 공식 정의, 소유 조직, 승인 절차
2. 거버넌스 저장소의 논리·물리 구성과 HA/백업 정책
3. RDW·ADW별 읽기/쓰기 책임과 접속 계정
4. CTQ·DQI·BR의 객체 모델과 버전 정책
5. 흐름 노드·엣지 표준 모델과 식별 키
6. FOS/MFT 파일명, Manifest, 체크섬, 완료표시 계약
7. APIM/EAI/MCA 메시지 스키마와 오류·재처리 계약
8. 인증·인가·감사 정책 및 개인정보 마스킹 범위
9. 수집·품질 실행의 주기, SLA, 자원 제한
10. 운영/개발/DR 환경별 데이터와 구성 동기화 방식

### 16.2 대표 위험

```text
용어 ID 불안정  → 참조 단절
규칙 무버전     → 결과 재현 불가
수집 비멱등     → 중복 Lineage
DB 무제한 조회  → RDW/ADW 운영 부하
파일 완료계약 없음 → 부분 파일 처리
권한 과다       → 개인정보·메타 유출
관측 부족       → 최신성 저하를 정상으로 오인
```

## 17. 최종 평가

이 아키텍처의 강점은 거버넌스의 `의미(비즈메타)`, `신뢰(데이터 품질)`, `이동·영향(데이터 흐름)`을 분리하면서 RDW·ADW 및 대내외 통합과 연결한 점이다. 실제 구축 완성도는 세 기능의 화면 구현보다 **식별자·버전·승인·연계 계약·재처리·감사**를 일관되게 정의하는 데 달려 있다.

도면만으로는 `표준 계수`, 거버넌스 저장소, 연결 방향, 인증 제품을 확정할 수 없다. 따라서 본 문서는 논리 기준으로 사용하되, 이 네 항목은 상세설계에서 반드시 원본 정의서와 담당 조직 확인을 거쳐 확정해야 한다.
