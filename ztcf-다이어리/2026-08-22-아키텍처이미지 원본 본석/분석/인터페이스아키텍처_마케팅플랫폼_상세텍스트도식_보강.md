# 인터페이스 아키텍처 — 마케팅플랫폼 분석

## 1. 핵심 결론

장표는 마케팅플랫폼을 하나의 독립 애플리케이션이 아니라, **채널 · 이벤트 · 데이터 플랫폼 · 대내통합 · 파일통합 · BI/거버넌스와 연결된 인터페이스 허브**로 배치한다.

특히 구조상 핵심은 다음 5가지다.

| 구분 | 핵심 의미 | 아키텍처 판단 |
|---|---|---|
| 채널 연계 | 영업점 MCA, 정보단말, Package UI, 인터넷/스마트뱅킹이 마케팅플랫폼으로 유입 | **온라인 채널 입력 경계** |
| 실시간 이벤트 | Wise Collector, Kafka, 행동정보처리, EBM | **고객행동 기반 실시간 반응 구조** |
| 대내 통합 | API Gateway, EAI, GSE | **코어/계정계/대내 시스템과의 표준 연계 경계** |
| 데이터 플랫폼 | RDW/ADW | **온라인 활용 데이터와 분석 데이터의 분리 저장 구조** |
| 파일·배치 연계 | FOS, MFT, ETL | **대량 데이터·파일 인터페이스 경계** |

따라서 이 장표의 핵심 설계원칙은 다음과 같이 정리할 수 있다.

```text
채널 → 마케팅플랫폼 → 데이터플랫폼 → 대내/대외 연계
                  └→ 행동정보처리 → 실시간 EBM → UMS
```

즉, **마케팅플랫폼은 단순 조회 시스템이 아니라, 고객행동을 수집하고, 실시간 판단을 수행하고, 데이터플랫폼과 연계하며, 코어·레거시와 표준 방식으로 통신하는 반응형 플랫폼**으로 정의되어 있다.

## 2. 장표 구성요소 전사

장표는 크게 다음 영역으로 나뉜다.

```text
좌측  : 채널 / 채널통합
중앙  : 차세대 정보계
        ① 마케팅플랫폼
        ② 데이터플랫폼
        ③ BI포탈
        ④ 데이터거버넌스
우측  : 대내통합 / 파일통합 / 데이터통합 / 연계업무
```

## 4. 마케팅플랫폼 인터페이스 상세 분석

## 4.1 채널 → 마케팅플랫폼 온라인 인터페이스

장표에는 `json/http`, `온라인 거래 처리`, `표준전문`, `싱글뷰` 등의 표기가 존재한다. 이를 기준으로 보면 마케팅플랫폼은 채널과 다음 방식으로 연결된다.

### 주요 유입 경로

| 채널 | 유입 경로 | 용도 |
|---|---|---|
| 통합업무 시스템 | 영업점 MCA | 영업점 업무 연계, 표준전문 처리 |
| 정보 단말 | json/http | 온라인 조회·처리 |
| Package UI(MSTR) | json/http | UI 기반 온라인 거래 |
| 인터넷/스마트뱅킹 | MCI / Wise Collector 연계 | 고객행동 수집 및 일부 서비스 연계 |

### 아키텍처 판단

- 영업점 MCA는 **전문 기반 대내 채널 표준 진입점** 역할을 수행한다.
- 정보 단말 및 Package UI는 **HTTP/JSON 기반 온라인 인터페이스**로 보인다.
- 채널과 마케팅플랫폼 사이의 인터페이스는 **동기식 온라인 처리**가 중심이다.
- 채널 경계에서 인증·권한·전문검증·GUID 생성이 수행되어야 한다.

### 권고 원칙

- 채널별로 서로 다른 포맷이 들어오더라도 내부 진입 계약은 표준화한다.
- 고객·직원·채널 식별자를 공통 Context로 변환한다.
- 채널 오류코드와 마케팅플랫폼 업무 오류코드를 분리한다.
- UI/채널이 내부 DB를 직접 조회하지 않고 서비스 인터페이스를 경유해야 한다.

## 4.2 고객행동 수집 및 이벤트 인터페이스

장표의 가장 중요한 특징 중 하나는 `Wise Collector Proxy → Wise Collector → kafka → 고객행동 데이터 → 행동정보처리 → 실시간 처리 → EBM` 흐름이다.

```text
인터넷뱅킹 / 스마트뱅킹 / 비대면 로그
        │
        ▼
Wise Collector Proxy
        ▼
Wise Collector
        ▼
Kafka
        ▼
고객행동 데이터
        ▼
행동정보처리
        ▼
실시간 처리
        ▼
EBM
```

### 아키텍처 의미

- 고객행동 이벤트는 업무조회 인터페이스와 분리된 **비동기 이벤트 파이프라인**으로 처리된다.
- 마케팅플랫폼은 단순 조회/등록 시스템이 아니라 **행동 기반 반응형 플랫폼**이다.
- Kafka는 채널 이벤트를 마케팅플랫폼 내부 처리와 느슨하게 결합시키는 역할을 한다.
- 행동정보처리와 실시간 EBM은 **이벤트 판단과 오퍼링 실행 영역**으로 분리되어 있다.

### 설계 포인트

- 이벤트 스키마와 토픽 정책을 표준화해야 한다.
- 고객 단위 순서 보장 요구가 있다면 Key 설계를 명확히 해야 한다.
- 중복 이벤트와 지연 이벤트를 고려한 멱등 처리가 필요하다.
- 실시간 처리와 후행 적재를 분리해도 GUID/Correlation ID는 연결해야 한다.

## 4.3 UMS 및 메시지 인터페이스

장표상 `UMS`는 채널 통합 쪽에 배치되어 있고, 마케팅플랫폼의 `메시지`, `컨텐츠`, `캠페인`, `EBM`과 간접 연결되는 구조로 보인다.

### 역할 해석

- UMS는 SMS, PUSH, e-Mail 발송을 담당하는 **메시지 채널 통합 컴포넌트**다.
- 마케팅플랫폼의 캠페인/메시지/EBM은 발송 정책과 콘텐츠를 결정한다.
- 실제 발송은 UMS가 수행하고 결과를 다시 플랫폼으로 회신해야 한다.

### 권고 구조

```text
캠페인/메시지/EBM
   → 발송요청 생성
   → UMS
   → SMS / PUSH / e-Mail
   → 발송결과 회신
```

### 필수 통제

- 수신동의, 수신거부, 발송빈도 제한
- 중복 발송 방지
- 메시지 템플릿 버전관리
- 발송실패 재시도와 만료정책
- 개인정보 마스킹 및 감사로그

---

## 4.4 마케팅플랫폼 ↔ 데이터플랫폼 인터페이스

장표에서 마케팅플랫폼 하단에 데이터플랫폼이 직접 배치되어 있고, RDW/ADW가 명확히 구분되어 있다.

### 구조 해석

| 플랫폼 | 역할 | 인터페이스 성격 |
|---|---|---|
| RDW | 실시간/준실시간 활용 데이터 | 온라인 활용, 실시간 피드백 중심 |
| ADW | 분석/집계/보고 데이터 | 분석/배치/마트 중심 |

### 핵심 판단

- 마케팅플랫폼의 온라인 처리와 고객행동 처리는 **RDW 중심의 실시간 활용**에 가까운 구조다.
- ADW는 실시간 트랜잭션 처리 대상이 아니라, **분석·집계·보고용 후행 데이터 플랫폼**이다.
- 따라서 RDW와 ADW를 동일하게 접근하면 안 되며 인터페이스 목적이 구분되어야 한다.

### 인터페이스 원칙

- 온라인 업무는 RDW 우선
- 분석/집계/보고는 ADW 우선
- 피드백 데이터는 Feed back 구조를 통해 상호 반영
- 대량 추출은 ETL이나 승인된 배치 경로를 사용
- 서비스가 타 시스템 스키마를 직접 변경하는 구조는 금지

---

## 4.5 마케팅플랫폼 ↔ BI 포탈 / 데이터거버넌스 인터페이스

중앙 장표에서 BI 포탈과 데이터거버넌스는 마케팅플랫폼과 같은 차세대 정보계 안에 배치되어 있으나 역할은 분리되어 있다.

### BI 포탈 연계 의미

- 신용실적, BI포탈, OLAP, Self BI는 **분석·조회·의사결정 영역**이다.
- 마케팅플랫폼은 고객반응과 업무실행의 영역이고, BI포탈은 **결과 활용 및 의사결정 시각화 영역**이다.
- 따라서 두 영역은 동일 애플리케이션이 아니라, 데이터와 요약정보를 연계하는 관계로 보는 것이 적절하다.

### 데이터거버넌스 연계 의미

- 비즈메타, 데이터품질, 데이터흐름은 **통제와 관리의 영역**이다.
- 마케팅플랫폼에서 생성·가공·전달되는 데이터는 이 거버넌스 체계의 통제를 받아야 한다.

### 원칙

- BI는 업무처리 로직을 소유하지 않는다.
- 데이터거버넌스는 운영데이터를 직접 처리하지 않고 메타/품질/흐름을 관리한다.
- 데이터 정의와 품질규칙은 인터페이스 계약에 반영되어야 한다.

---

## 4.6 마케팅플랫폼 ↔ 대내통합 인터페이스

우측 `대내통합` 영역에는 `API G/W`, `EAI`, `API G/W`, `GSE`가 보인다.

### 역할 구분

| 컴포넌트 | 역할 | 주의사항 |
|---|---|---|
| API Gateway | 대내 서비스 표준 API 진입점 | 업무로직 집중 금지 |
| EAI | 레거시/기존 전문 중계 및 변환 | 변환 로직 과다 집중 주의 |
| GSE | 은행/그룹 표준 연계 경계 | 연계표준 계약 필요 |

### 해석

- 계정계 AP, 코어뱅킹, Online DB, BCV DB 등과 직접 붙지 않고, **표준 중계 계층을 통해 연결**하려는 의도가 읽힌다.
- 마케팅플랫폼이 레거시를 직접 호출하기보다 대내통합 계층을 경유하는 구조로 보는 것이 적절하다.

### 아키텍처 원칙

- 채널용 API와 레거시 전문중계를 혼합하지 않는다.
- Gateway는 정책·인증·라우팅 중심, 실제 업무는 서비스가 담당한다.
- EAI는 전문 변환과 중재에 집중한다.
- 연계 Timeout과 Circuit Breaker를 통해 코어장애가 플랫폼 전체로 전파되지 않도록 해야 한다.

---

## 4.7 마케팅플랫폼 ↔ 파일통합 인터페이스

우측 `파일통합` 영역에는 `FOS`, `MFT`, `CDC` 조합이 보인다.

### 의미

- 온라인 API로 처리하기 어려운 대량 파일, 정산성 파일, 외부 수신 파일, 배치 파일을 위한 경로로 보인다.
- 내부 파일중계는 FOS, 통제된 전송은 MFT, 데이터 동기화 보조는 CDC와 조합될 수 있다.

### 표준 원칙

- 파일명 규칙, 전송단위, 완료신호, 암호화, 체크섬 표준화
- File ID/Transfer ID 기반 추적
- 미완료 파일 소비 금지
- 재전송과 중복수신 처리정책 정의
- 대외 파일은 별도의 보안·승인·감사 통제 필요

---

## 4.8 마케팅플랫폼 ↔ 데이터통합(ETL) 인터페이스

장표 하단 우측에는 데이터 통합 영역으로 `ETL`이 별도로 존재한다.

### 해석

- 실시간 거래는 온라인/이벤트 경로로, 대량 적재와 분석성 변환은 ETL로 분리하는 구조다.
- ETL은 RDW/ADW 및 연계업무 사이의 정형 데이터 이동을 담당한다.

### 원칙

- ETL은 대량 추출·변환·적재 중심
- 온라인 서비스 호출과 ETL 배치를 혼합하지 않음
- 워터마크, 증분 기준, 재처리 기준, 대사 기준을 정의
- ETL 오류는 데이터 품질체계와 연결해야 함

## 7. GUID 및 추적성 아키텍처

마케팅플랫폼은 채널·이벤트·데이터·메시지·파일을 모두 연결하므로 **GUID 기반 종단 추적**이 필수다.

```text
채널 요청 GUID
 ├─ API / 서비스 로그
 ├─ 행동이벤트 Header
 ├─ Kafka 이벤트 ID
 ├─ EBM 판단 ID
 ├─ UMS 발송 ID
 ├─ RDW/ADW 적재 실행 ID
 └─ 파일 / ETL 실행 ID
```

### 표준 원칙

- 최초 진입점에서 GUID 생성
- 비동기 경로는 parentGuid 유지
- Event ID, Message ID, Job ID는 별도 부여하되 상위 GUID 연결
- 모니터링 도구는 GUID 기준 조회 가능해야 함

- 고객식별정보 평문 로그 저장
- 이벤트 토픽에 과도한 개인정보 적재
- 파일 인터페이스를 통한 우회 데이터 수정

## 12. 성능 및 용량 고려사항

### 핵심 포인트

- 온라인 조회/처리와 이벤트 처리 부하를 분리해야 한다.
- Kafka 소비량 급증이 온라인 처리에 영향을 주지 않도록 자원격리가 필요하다.
- UMS 발송폭주 시 백프레셔 및 Rate Limit이 필요하다.
- RDW는 실시간 활용 부하, ADW는 분석성 부하 기준으로 각각 튜닝해야 한다.
- API Gateway, EAI, 파일전송, ETL이 모두 동시에 RDW/ADW에 부하를 주지 않도록 운영창을 조정해야 한다.

### 권고 구조

```text
온라인 사용자 부하   ≠  이벤트 수집 부하
이벤트 판단 부하     ≠  메시지 발송 부하
실시간 조회 부하     ≠  분석/ETL 부하
```

## 16. 장표 해석 시 유의사항

이 장표는 **마케팅플랫폼 중심 인터페이스 청사진**으로는 유용하지만, 선만으로 모든 세부사항을 확정할 수는 없다.

특히 다음은 상세설계 확인 대상이다.

- API Gateway와 EAI의 정확한 역할 구분
- GSE의 실제 연계 범위
- FOS / MFT / CDC 각각의 구체적 적용 시나리오
- RDW와 ADW 간 Feed back의 실제 데이터 흐름
- UMS와 캠페인/메시지 모듈의 호출 주체
- Wise Collector와 채널 사이의 실제 로그 수집 범위
- EBM의 규칙엔진/실행엔진 분리 여부

따라서 본 문서는 **이미지에서 식별 가능한 FACT를 우선 정리하고, 일반적인 인터페이스 아키텍처 원칙에 따라 분석을 보강한 문서**로 해석해야 한다.

## 17. 최종 평가

이 장표는 마케팅플랫폼을 **채널 연계, 고객행동 이벤트 처리, 실시간 EBM, 데이터플랫폼, 대내통합, 파일/ETL 연계가 결합된 반응형 인터페이스 플랫폼**으로 정의하고 있다.

가장 중요한 강점은 다음과 같다.

1. **온라인 인터페이스와 이벤트 인터페이스를 함께 고려했다.**  
2. **RDW/ADW를 분리해 실시간 활용과 분석 활용을 구분했다.**  
3. **API Gateway / EAI / GSE / FOS / MFT / ETL 등 연계 유형별 경계를 의도적으로 분리했다.**  
4. **마케팅 실행(캠페인/메시지/EBM)과 고객행동 기반 판단 구조를 하나의 플랫폼 관점으로 묶었다.**

반면 실제 구축 시 반드시 보강해야 할 부분은 다음이다.

- Interface ID 기반 등록부 작성
- GUID 종단 추적 표준 확정
- 이벤트 계약·파일 계약·ETL 계약 명문화
- 채널 / 이벤트 / 파일 / 배치 / 메시지 경계의 운영표준 수립
- 실시간 처리와 분석 처리의 자원 격리

최종적으로 이 장표는 **마케팅플랫폼이 단순한 화면 시스템이 아니라, 정보계 전체의 실시간 반응·고객행동 활용·대내 통합을 담당하는 핵심 인터페이스 허브**라는 점을 잘 보여준다.
