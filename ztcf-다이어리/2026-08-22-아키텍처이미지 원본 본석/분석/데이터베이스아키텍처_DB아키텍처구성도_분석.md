# 데이터베이스 아키텍처 — DB 아키텍처 구성도 분석

> 원본 범위: `4. 데이터베이스 아키텍처 > 4.1 DB 아키텍처 구성도`  
> 원본 핵심 문구: `RDW, ADW는 EXADATA RAC 각 1식 이중화 구성`  
> 분석 원칙: 장표의 논리 업무 영역과 물리 DB 경계를 구분한다. 박스 하나를 독립 DB Instance로 단정하지 않고 schema·tablespace·업무 데이터 영역일 가능성을 함께 고려한다.

---

## 1. 핵심 결론

DB 아키텍처는 데이터를 목적에 따라 `RDW`와 `ADW`로 분리한 2계층 데이터웨어하우스 구조다.

- **RDW**는 계정계·채널에서 들어오는 실시간·준실시간 데이터를 수용하고 마케팅 업무를 직접 지원한다.
- **ADW**는 RDW 및 연계계 데이터를 분석용으로 재구성하여 BI포탈, Self-BI, OLAP, 데이터거버넌스에 제공한다.
- 계정계 코어뱅킹 데이터는 CDC 중계를 통해 RDW의 실시간 SoR로 유입된다.
- RDW 내부에는 데이터플랫폼 실시간 영역과 마케팅플랫폼 업무 영역이 공존한다.
- ADW 내부에는 분석 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스·업무지원 영역이 배치된다.
- RDW와 ADW는 각각 Exadata RAC 1식으로 구성되어 DB 노드 장애에 대한 이중화를 제공한다.

```text
계정계·채널·연계업무
         │
         ├─ CDC / 실시간 수집
         ▼
┌────────────────── RDW ──────────────────┐
│ 실시간 SoR · 준실시간 집계 · 마케팅 업무│
└──────────────────┬───────────────────────┘
                   │ ETL·분석 적재
                   ▼
┌────────────────── ADW ──────────────────┐
│ 분석 SoR · 분석마트 · BI · 거버넌스     │
└──────────────────────────────────────────┘
```

## 2. 근거 수준

| 수준 | 내용 |
|---|---|
| 확인 사실 | RDW와 ADW가 별도 DB 경계로 표시됨 |
| 확인 사실 | 두 DB 모두 Exadata RAC 각 1식 이중화 구성이라고 명시됨 |
| 확인 사실 | 코어뱅킹에서 CDC 중계를 거쳐 RDW 실시간 SoR로 유입되는 선이 표시됨 |
| 확인 사실 | RDW에 데이터플랫폼 RDW와 마케팅플랫폼 영역이 배치됨 |
| 확인 사실 | ADW에 데이터플랫폼 ADW, BI포탈, 데이터거버넌스, IT서비스·업무지원 영역이 배치됨 |
| 설계 해석 | RDW는 운영·실시간 중심, ADW는 분석·조회 중심의 워크로드 분리 구조 |
| 설계 해석 | 피드백 영역은 분석 결과를 마케팅·업무 실행으로 환류하는 폐루프 구조 |
| 미확정 | RDW→ADW의 정확한 적재 도구, 주기, 증분 방식과 SLA |
| 미확정 | 각 업무 박스가 schema, tablespace, 사용자 또는 논리 데이터마트 중 무엇인지 |
| 미확정 | RAC 노드 수, DB Service, SCAN, ASM Disk Group, Data Guard 구성 |

## 4. RDW 아키텍처

### 4.1 RDW의 역할

RDW는 실시간 유입과 업무 활용 사이의 운영 데이터 허브다. 계정계 원천을 수용하는 SoR(System of Record 성격의 저장영역), 준실시간 집계·마트, 마케팅 업무 데이터를 함께 관리한다.

```text
원천 거래
   ↓ CDC
실시간 SoR
   ↓ 정제·집계
준실시간 요약집계
   ↓
준실시간 보고서마트
   ↓
마케팅플랫폼·피드백
```

### 4.2 데이터플랫폼 RDW 영역

| 논리 영역 | 역할 해석 | 주요 관리사항 |
|---|---|---|
| 공통 | 코드·기준·공통 데이터 | 기준정보 정합성, 변경 이력 |
| 실시간 SoR | CDC·실시간 원천 데이터 저장 | 중복·순서·재처리, 보존기간 |
| 준실시간요약집계 | 빠른 업무 조회용 집계 | 집계 지연, 증분 기준, 재산출 |
| 준실시간보고서마트 | 준실시간 보고·조회 데이터 | 보고시점, cutoff, 동시성 |
| 피드백 | 분석·업무 결과 환류 | 결과 버전, 적용 이력, 멱등성 |

### 4.3 마케팅플랫폼 영역

```text
공통
개인고객
통합고객
기업고객
미니싱글뷰
통합상품
상담판매
캠페인
EBM
실시간처리
행동정보처리
고객행동데이터
영업지원
CS
콘텐츠
메시지
```

| 분류 | 구성요소 | 분석 |
|---|---|---|
| 고객 | 개인고객, 통합고객, 기업고객 | 고객 단위 식별·통합·세분화 |
| 상품 | 통합상품 | 상품 기준과 고객 보유상품 연결 |
| 접점 | 미니싱글뷰, 상담판매, 영업지원, CS | 고객 접점 조회·상담·영업 지원 |
| 캠페인 | 캠페인, EBM, 실시간처리 | 이벤트 기반 제안·캠페인 실행 |
| 행동 | 행동정보처리, 고객행동데이터 | 채널 행동 수집·가공·활용 |
| 콘텐츠 | 콘텐츠, 메시지 | 메시지·콘텐츠 생성 및 전달 이력 |

### 4.4 RDW 설계 특성

- 실시간 적재와 마케팅 조회가 동일 RDW RAC를 공유하므로 Resource Manager, DB Service, schema 권한으로 워크로드를 격리해야 한다.
- 실시간 SoR는 원본 재처리를 위한 이력성과 업무 조회 성능을 동시에 고려해야 한다.
- 준실시간 집계·마트는 데이터 신선도 SLA와 집계 완료시각을 명시해야 한다.
- 마케팅 개인정보는 암호화, 접근통제, 마스킹, 보존·파기 정책을 적용해야 한다.

## 5. ADW 아키텍처

### 5.1 ADW의 역할

ADW는 RDW와 기타 원천을 분석 목적에 맞게 통합하고, 정형 보고·다차원 분석·Self-BI·거버넌스 서비스를 지원하는 분석 데이터 허브다.

```text
RDW·외부원천
    ↓ ETL
분석 SoR
    ↓
분석통합요약집계
    ├─ 분석단위업무마트
    ├─ 분석보고서마트
    ├─ BI포탈 / OLAP / Self-BI
    └─ 데이터품질 / 메타 / 흐름
```

### 5.2 데이터플랫폼 ADW 영역

| 논리 영역 | 역할 해석 | 주요 관리사항 |
|---|---|---|
| 공통 | 분석 공통 코드·차원·기준 | conforming dimension, SCD 정책 |
| 분석SoR | 분석용 원천 통합 저장 | 원천 추적성, 적재시점, 정합성 |
| 분석통합요약집계 | 전사 공통 집계 | 지표 정의, 중복 집계 방지 |
| 분석단위업무마트 | 업무 주제별 분석마트 | 소유자, grain, refresh SLA |
| 분석보고서마트 | 정형 보고 최적화 | 보고서 기준시점, 재현성 |
| 피드백 | 분석 결과의 업무 환류 | 적용 대상, 점수 버전, 이력 |
| 분석지원 | 분석가·모델·도구 지원 | sandbox, quota, 개인정보 통제 |

### 5.3 BI포탈 영역

```text
BI포탈
신용실적
OLAP
Self BI
신포털 UI/UX
```

- BI포탈은 공통 조회와 보고 진입점이다.
- 신용실적은 별도의 실적 데이터마트와 업무 화면을 사용한다.
- OLAP은 다차원 집계·탐색 워크로드를 담당한다.
- Self BI는 사용자가 직접 분석을 수행하므로 query quota와 민감정보 통제가 중요하다.
- 신포털 UI/UX는 DB 데이터 영역이라기보다 포털 기능 또는 관련 설정·메타 영역일 수 있다.

### 5.4 데이터거버넌스 영역

```text
공통
  ├─ 비즈메타
  ├─ 데이터품질
  └─ 데이터흐름
```

| 영역 | 핵심 데이터 | 기능 |
|---|---|---|
| 비즈메타 | 용어, 지표, 모델, 소유자 | 데이터 의미와 책임 관리 |
| 데이터품질 | 품질규칙, 측정결과, 오류 | 품질 진단·개선·추적 |
| 데이터흐름 | source-target, job, lineage | 영향도·계보·변경 분석 |

거버넌스 메타가 ADW에 위치하므로 ADW 장애는 BI뿐 아니라 품질·계보 조회에도 영향을 준다.

### 5.5 IT서비스 및 업무지원 영역

```text
아키텍처 관리     시스템 공통        배포
프레임워크        라이브러리         소스코드 버전관리
정보단말 관리     정보단말 배포      배치작업 처리
실시간 중계       데이터 치환 적재   보고서 디자이너
```

이 영역은 업무 데이터 외에도 배포·배치·프레임워크·단말관리용 설정과 이력을 ADW 내에 저장하는 것으로 보인다. 실제로 ADW 업무 schema인지 관리 솔루션 repository인지 구분해야 한다.

## 6. 데이터 유입 및 전달 메커니즘

### 6.1 계정계 CDC 유입

```text
코어뱅킹
   ↓ 변경 데이터 캡처
CDC 중계
   ↓ 순서·재처리 제어
RDW 실시간 SoR
```

- 소스 transaction의 commit 순서와 target 적용 순서를 보장해야 한다.
- 장애 시 checkpoint와 미적용 transaction을 기준으로 재시작해야 한다.
- DDL 변경, 대량 배치, 로그 보존 부족은 CDC 중단 위험이다.

### 6.2 기타 원천 유입

```text
연계뱅킹 / BCV / 연계업무
인터넷뱅킹 / 스마트뱅킹 / 비대면채널
                 ↓
        RDW 마케팅·실시간 영역
```

장표는 모든 화살표를 상세히 표시하지 않으므로 실제 인터페이스가 CDC, API, Kafka, MFT, FOS, ETL 중 무엇인지 인터페이스 목록으로 확정해야 한다.

### 6.3 RDW에서 ADW로의 분석 적재

```text
RDW 실시간·업무 데이터
          ↓ 추출
      정제·표준화
          ↓
ADW 분석 SoR
          ↓
요약집계·업무마트·보고서마트
```

이 흐름은 장표의 역할 분리를 바탕으로 한 설계 해석이다. 적재 도구와 주기는 별도 배치·ETL 설계에서 확인해야 한다.

### 6.4 피드백 폐루프

```text
ADW 분석·모델 결과
        ↓ feedback
RDW 피드백 영역
        ↓
캠페인 / EBM / 상담 / 메시지
        ↓ 반응 데이터
RDW → ADW 재학습·분석
```

피드백 데이터에는 모델 버전, 점수 산출시각, 대상 고객, 적용 정책, 결과 이력을 포함해야 재현성과 감사가 가능하다.

## 7. Exadata RAC 물리 구조 해석

```text
RDW Exadata RAC 1식
  ├─ RAC Node 1
  ├─ RAC Node 2
  ├─ ASM / Shared Storage
  └─ RDW DB Services

ADW Exadata RAC 1식
  ├─ RAC Node 1
  ├─ RAC Node 2
  ├─ ASM / Shared Storage
  └─ ADW DB Services
```

RAC는 노드 장애에 대한 고가용성을 제공하지만 데이터 손상·센터 재해·논리 오류를 막는 백업 또는 DR 자체는 아니다.

| 보호 대상 | RAC 제공 여부 | 추가 수단 |
|---|---|---|
| DB 노드 장애 | 제공 | 서비스 failover 시험 |
| Storage Cell 장애 | Exadata 구성에 따라 제공 | redundancy 확인 |
| 센터 전체 장애 | 미제공 | Data Guard·원격복제·DR |
| 사용자 오삭제 | 미제공 | RMAN·Flashback·PITR |
| 잘못된 ETL/DDL | 미제공 | 배포통제·백업·복구 |

확인해야 할 물리 항목:

- RAC 노드 수와 VIP·SCAN 구성
- RDW/ADW DB Service 분리 기준
- ASM Disk Group과 redundancy
- Exadata Quarter/Full Rack 실제 배치
- Data Guard mode와 standby 위치
- RMAN 백업, FRA, archive log 보존
- patching 및 rolling upgrade 절차

## 8. 워크로드 분리 원칙

| 워크로드 | 권장 위치 | 이유 |
|---|---|---|
| CDC·실시간 원천 | RDW 실시간 SoR | 낮은 지연과 원천 추적성 |
| 마케팅 실행 | RDW 마케팅 영역 | 실시간 고객·행동 데이터 근접성 |
| 준실시간 보고 | RDW 보고서마트 | 빠른 최신 데이터 제공 |
| 전사 분석·집계 | ADW | 대량 스캔과 집계 격리 |
| 정형 BI·OLAP | ADW BI 영역 | 분석 최적화와 공통 지표 |
| Self-BI | ADW | 운영 워크로드 보호 |
| 거버넌스 | ADW | 분석 메타·품질·계보 통합 |

RAC 내부에서도 업무별 DB Service, Resource Consumer Group, schema, tablespace, connection pool로 자원을 통제해야 한다.

## 9. 데이터 모델 및 관리 기준

```text
원천 계층  : 실시간 SoR / 분석 SoR
통합 계층  : 공통 / 고객 / 상품 / 통합요약
마트 계층  : 준실시간마트 / 업무마트 / 보고서마트
소비 계층  : 마케팅 / BI / OLAP / Self-BI
거버넌스   : 메타 / 품질 / 흐름
```

각 영역에 다음 메타데이터가 필요하다.

- 업무 소유자와 데이터 관리자
- 데이터 grain과 PK·business key
- 원천 시스템과 적재 lineage
- 적재 주기, cutoff, SLA
- 보존기간과 파티션 정책
- 민감정보 분류와 암호화·마스킹
- 품질 규칙과 오류 처리
- 접근 역할과 승인 절차

## 12. 최종 평가

이 DB 아키텍처는 RDW를 실시간·업무 실행 허브로, ADW를 분석·BI·거버넌스 허브로 분리해 워크로드 목적을 명확히 한 구조다. 계정계 CDC, 마케팅 실행, 분석마트, 피드백의 순환 구조를 통해 실시간 데이터 활용과 분석 결과의 업무 환류를 모두 지원한다.

Exadata RAC 이중화는 노드 수준 가용성을 높이지만, 성공적인 운영을 위해서는 **논리영역–schema 매핑, CDC·ETL SLA, workload 격리, Data Guard·백업, 개인정보 통제, 피드백 이력관리**가 함께 구체화되어야 한다.
