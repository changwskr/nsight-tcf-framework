# 운영환경 구축 대상 시스템 및 주요 구성요소 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `운영환경 구축 대상 시스템 및 주요 구성요소` 이미지
- 원본 분류: 환경별 Physical Architecture
- 분석 범위: 이미지에 표시된 5개 상시 시스템과 1개 이행용 임시 구성
- 판독 원칙:
  - 상자 내 명칭은 **이미지 사실**로 처리한다.
  - 점선은 **연계 존재 표시**로만 읽고, 방향·프로토콜·주기는 확정하지 않는다.
  - WEB/WAS/AP/DB는 논리 역할이며, 각 블록이 단일 서버 1대를 의미하지는 않는다.
  - 저장소 소스·문서 비교는 `설계 정합`, `부분 구현`, `미확인`으로 분리한다.

---

## 1. 핵심 결론

1. 운영환경은 **마케팅플랫폼, 데이터플랫폼, BI포털, 데이터거버넌스, IT서비스 및 업무지원**의 5개 상시 시스템으로 구성된다.
2. `이행용 임시 구성`은 제6의 상시 서비스가 아니라, 데이터 전환·추출·이행·SQL 품질 검증을 위한 **시한부 이행 제어면**이다.
3. 마케팅플랫폼은 사용자 서비스와 실시간/행동데이터 처리를, 데이터플랫폼은 RDW·ADW를, BI포털은 조회·OLAP·Self-BI를 담당한다.
4. RDW와 ADW는 단순 이중화가 아니라 **준실시간/운영성 조회와 분석/대량 조회의 부하·책임 분리**로 해석하는 것이 타당하다.
5. 데이터거버넌스는 데이터 처리 시스템의 대체물이 아니라 메타데이터·품질·흐름을 관리하는 **통제·가시성 계층**이다.
6. IT서비스 및 업무지원은 단말, 배치, CDC, ETL, RD 출력, 운영 대시보드를 포함하는 **공통 운영 제어면**이다.
7. 장표는 구성요소 목록이지 실제 Host·JVM·WAR·Datasource 배치도가 아니다. 운영 확정에는 별도의 Runtime Evidence가 필요하다.

## 2. 이미지 구성요소 전수 정리

| # | 시스템 | 주요 구성요소 | 주요 책임 |
|---:|---|---|---|
| 1 | 마케팅플랫폼 | 마케팅 WEB/WAS, 미니 싱글뷰 WEB/WAS, 실시간 처리 AP, 행동정보 처리 AP, 고객 행동 데이터 AP, 마케팅 DB | 마케팅 업무·고객 뷰·실시간 반응·행동데이터 처리 |
| 2 | 데이터플랫 | RDW Appliance, ADW Appliance | 준실시간 및 분석 데이터 저장·제공 |
| 3 | BI포털 | BI 포털 WEB/WAS, 신용실적 WEB/WAS, OLAP AP/WEB/WAS, Self-BI AP/WEB/WAS, 경영실적 DB, BI포털 DB | 정형·비정형 분석, OLAP, Self-Service BI, 포털 제공 |
| 4 | 데이터거버넌스 | 비즈메타/데이터 품질 WAS, 데이터 흐름 WAS, 거버넌스 DB | 메타데이터·품질·리니지 관리 |
| 5 | IT서비스 및 업무지원 | 단말관리 WEB/WAS, 단말배포 WEB/WAS, 배치 AP, CDC 중계 DB, ETL, UNO Dashboard, 출력물(RD) WAS, 단말관리 DB | 운영·배포·집계·이송·출력 공통 기능 |
| T | 이행용 임시 구성 | 전환 AP, 추출 DB, 이행 AP, SQL 품질 AP | 개통 전후 데이터 이행과 검증 |

> 원본 상단 설명은 운영환경을 5개 시스템으로 정의한다. `T` 구성은 운영 자원을 임시 할당하는 이행 영역이므로 상시 시스템 수에 포함하지 않는 것이 정합적이다.

**원본 라벨 보존 메모**

- 이미지의 DB 라벨은 `BI포탈 경영실적 DB`, `BI포탈 DB`로 표시되며, 본문의 `BI 포털`은 동일 시스템을 가리킨다.
- IT서비스 영역의 WAS는 원본에서 `단말관리 WAS`, `단말배포 WAS`로 각각 분리되어 있다.

### 3.2 데이터 생명주기

```text
[원천/채널/업무]
        │
        ├─ 실시간·CDC ──→ [RDW] ──→ 미니 싱글뷰 / 실시간 마케팅
        │
        └─ 배치·ETL  ──→ [ADW] ──→ BI 포털 / OLAP / Self-BI
                                 │
                                 ├─→ 비즈메타·품질·흐름 관리
                                 └─→ 경영·신용실적 분석
```

> 위 생명주기의 RDW/ADW 책임 분리는 이미지의 점선과 저장소 아키텍처 문서를 결합한 **해석**이다. 실제 Table/View 단위 Read/Write Matrix로 확정해야 한다.

## 4. 시스템별 상세 분석

### 4.1 마케팅플랫폼 시스템

| 구성요소 | 역할 | 주요 입력 | 주요 출력/의존 |
|---|---|---|---|
| 마케팅플랫폼 WEB | HTTP 종단, 정적 콘텐츠, WAS 라우팅 | 사용자 요청 | WAS 요청 |
| 마케팅플랫폼 WAS | 마케팅 업무·관리 로직 | WEB/API 요청 | DB·데이터플랫·연계 결과 |
| 미니 싱글뷰 WEB/WAS | 고객 통합 요약 제공 | 고객 식별자, 조회 요청 | 고객·계좌·행동 요약 |
| 실시간 처리 AP | 실시간 이벤트/응답 처리 | 채널·이벤트 | 실시간 판단·저장 |
| 행동정보 처리 AP | 행동 이벤트 정제·집계 | 행동 로그/이벤트 | 행동 지표·파생 데이터 |
| 고객 행동 데이터 AP | 고객 단위 행동 데이터 서비스 | 정제/집계 결과 | 조회·마케팅 입력 |
| 마케팅플랫폼 DB | 마케팅 운영 데이터 보관 | 캠페인·관리·처리 결과 | WAS/AP 조회 |

**분리 이유**

- WEB/WAS 분리: 외부 접점과 업무 로직의 보안·스케일 경계
- 마케팅/미니 싱글뷰 분리: 관리·업무 기능과 고객 통합 조회의 SLA/부하 차이
- AP 세분화: 실시간 응답, 행동 정제, 고객 단위 서비싱의 확장·장애 반경 분리

### 4.2 데이터플랫폼 시스템

| 구성요소 | 권고 책임 | 지양할 사용 |
|---|---|---|
| RDW Appliance | 온라인·준실시간 조회, 신선도가 중요한 정보계 읽기 | 대량 전체 스캔, 장기 이력 집계로 온라인 SLA 침해 |
| ADW Appliance | 대량 적재, 이력, BI·OLAP·Self-BI 분석 | 온라인 거래가 ADW 지연/부하에 직접 의존 |

**필수 통제**

- Domain/Table/View Owner
- RDW/ADW Read·Write Matrix
- CDC/ETL 지연·재처리·정합성 기준
- 시간 기준, 스키마, 코드, 개인정보 마스킹 정합성
- BI 질의가 운영성 워크로드를 침해하지 않도록 자원 그룹·쿼터·타임아웃 분리

### 4.3 BI포털 시스템

```text
BI 포털 WEB → BI 포털 WAS ─┐
신용실적 WEB → 신용실적 WAS ─├→ BI포털 DB / 경영실적 DB
OLAP WEB → OLAP WAS → OLAP AP ───├→ RDW/ADW
Self-BI WEB → Self-BI WAS → AP ───┘
```

| 영역 | 분석 |
|---|---|
| BI 포털 | 대시보드·보고서·권한·콘텐츠를 통합 제공하는 접점 |
| 신용실적 | 신용/실적 전용 화면과 업무 로직. 권한·개인정보 통제가 필요 |
| OLAP | 다차원 집계·탐색. AP는 분석 엔진/세션, WEB/WAS는 접점/제어로 해석 |
| Self-BI | 사용자 자율 분석. 표준 의미계층·승인 데이터셋·쿼리 제한이 필요 |
| 경영실적 DB | 경영실적 전용 저장·집계 영역 |
| BI포털 DB | 포털 설정·권한·메타데이터·운영정보 영역 |

BI포털 DB와 경영실적 DB를 RDW/ADW와 혼동하면 안 된다. 전자는 BI 서비스 운영/전용 데이터, 후자는 전사 데이터 제공 플랫폼으로 책임을 분리해야 한다.

### 4.4 데이터거버넌스 시스템

| 구성요소 | 책임 | 핵심 통제 |
|---|---|---|
| 비즈메타/데이터 품질 WAS | 용어·도메인·오너십·품질 규칙·점검 결과 관리 | 표준어/코드, 품질 임계치, 승인 흐름 |
| 데이터 흐름 WAS | Source→ETL/CDC→RDW/ADW→BI 리니지 추적 | 영향도 분석, 변경 전파, 오너 확인 |
| 데이터거버넌스 DB | 메타데이터·품질·리니지·조치이력 보관 | 이력 불변성, 권한, 감사 |

거버넌스는 데이터 흐름을 관찰·통제하지만, 원천에서 BI까지의 실데이터를 모두 복제·보관하는 시스템으로 해석하면 안 된다.

### 4.5 IT서비스 및 업무지원 시스템

| 구성요소 | 책임 | 주요 운영 위험 |
|---|---|---|
| 단말관리 WEB/WAS/DB | 단말 등록·상태·정책·배포이력 관리 | 관리자 권한 오남용, 전체 단말 오배포 |
| 단말배포 WEB/WAS | 단말 소프트웨어/정책 배포·롤백 | 파일 무결성, 버전 착오, 대규모 동시 배포 |
| 배치 AP | 스케줄 기반 대량 작업 수행 | 중복 실행, 재시작 오류, 온라인 부하 침해 |
| CDC 중계 DB | 변경데이터 중계·체크포인트·재처리 지원 | 지연 누적, 중복/유실, 소스 로그 보존 |
| ETL | 추출·변환·적재, RDW/ADW 갱신 | 스키마 불일치, 재처리, 데이터 정합성 |
| UNO Dashboard | 운영상태·작업·장애 가시화로 해석 | 모니터링 누락, 개인/민감정보 노출 |
| 출력물(RD) WAS | 보고서 렌더링·출력 | 대용량 출력, 임시파일, 출력물 접근통제 |

### 4.6 이행용 임시 구성

```text
[기존 원천]
    │ 추출
    ▼
[임시 추출 DB] → [변환 AP] → [이행 AP] → [신규 대상 DB]
                           │                    │
                           └──→ [SQL 품질 AP] ─┘
                                      │
                                      ▼
                              [건수/합계/품질 대사]
```

**운영 원칙**

- 상시 운영 자원과 계정·스토리지·네트워크를 분리한다.
- 이행 기간, 책임자, 용량, 폐기 승인, 임시 데이터 파기 일자를 사전 확정한다.
- 건수·합계·해시·표본 대사를 통해 완전성과 정확성을 분리 검증한다.
- 본이행 전 최소 1회 이상 전체 리허설과 롤백 절차를 검증한다.
- 개통 후 임시 자원이 영구 운영 경로로 남지 않도록 종료 조건을 둔다.

## 5. 연계 메커니즘 분석

### 5.1 주요 흐름

| 흐름 | Source | Target | 의미 | 판정 |
|---|---|---|---|---|
| 온라인/행동 수집 | 마케팅 AP·DB | RDW | 신선도가 중요한 고객·행동 정보 제공 | 해석 |
| 분석 적재 | 원천/RDW | ADW | 대량 분석용 정제·이력 적재 | 해석 |
| BI 조회 | RDW/ADW | BI포털·OLAP·Self-BI | 신선도/질의 특성에 따른 소스 선택 | 이미지 연계 + 해석 |
| 거버넌스 수집 | 데이터플랫·BI·ETL | 거버넌스 | 메타데이터·품질·리니지 관리 | 해석 |
| CDC/ETL/배치 | 원천·중계 | RDW/ADW/업무 DB | 실시간과 배치 데이터 이동 | 구성요소 사실 + 해석 |
| 이행 | 기존 시스템 | 임시 추출/변환/이행 | 개통 데이터 전환 | 이미지 사실 |

### 5.2 실시간·CDC·ETL·배치의 구분

| 방식 | 시간성 | 처리 단위 | 주요 사용처 | 핵심 지표 |
|---|---|---|---|---|
| 실시간 AP | 즉시/초단위 | 이벤트·요청 | 실시간 마케팅 | 응답시간, TPS, 오류율 |
| CDC | 준실시간 | DB 변경 로그/레코드 | RDW 동기화 | Replication lag, 유실/중복 |
| ETL | 주기/스케줄 | 대량 데이터셋 | ADW·BI 적재 | 소요시간, 처리건수, 품질 |
| 배치 AP | 주기/이벤트 | Job/Step | 업무처리·집계·정리 | 완료시간, 재시작성, 중복방지 |

---

## 6. 배치·보안·가용성 원칙

### 6.1 배치 원칙

- WEB은 외부/사용자 접점에만 두고 DB에 직접 접근하지 않는다.
- WAS는 업무·세션·권한 제어를 담당하고, 전용 AP와 DB를 통제된 경로로 호출한다.
- AP는 실시간, OLAP, Self-BI, 배치, 이행 등 워크로드 특성에 따라 자원풀과 장애 반경을 분리한다.
- DB는 시스템 오너십을 명확히 하고, 타 시스템의 직접 테이블 쓰기를 금지한다.
- RDW/ADW는 물리 자원과 쿼리 워크로드를 분리하고, 데이터 복제·정합성 책임을 문서화한다.

### 6.2 보안 원칙

| 통제 | 적용 대상 | 기준 |
|---|---|---|
| 인증·인가 | 모든 WEB/WAS, BI, 단말관리 | SSO/MFA, RBAC, 업무분리 |
| 서비스 계정 | AP·ETL·CDC·배치 | 개별 식별자, 최소권한, 주기적 교체 |
| DB 접근 | 전 DB/RDW/ADW | 접속원 제한, Read/Write 분리, 감사로그 |
| 개인정보 | 싱글뷰·행동데이터·BI | 암호화, 마스킹, 반출통제, 보존기간 |
| 이행 자료 | 추출 DB·이행 AP | 시한부 권한, 전송/보관 암호화, 종료 파기 |
| 출력물 | RD WAS | 워터마크, 저장/다운로드 통제, 임시파일 정리 |

### 6.3 가용성·장애 격리

- WEB/WAS/AP는 단일 장애점이 되지 않도록 복수 인스턴스와 헬스체크를 둔다.
- RDW 지연은 실시간/싱글뷰를, ADW 지연은 BI/OLAP를 우선 열화시킨다. 서비스별 저하 모드를 분리한다.
- CDC와 ETL은 중단 후 체크포인트 기반 재개, 멱등성, 누락/중복 대사를 지원해야 한다.
- BI 질의 폭증이 마케팅 온라인 응답을 침해하지 않도록 커넥션풀·자원그룹·타임아웃을 분리한다.
- 임시 이행 구성 장애가 상시 운영 서비스로 전이되지 않도록 네트워크·DB 세션·I/O 쿼터를 분리한다.

## 7. 현재 저장소와의 대응

### 7.1 확인된 논리 대응

| 이미지 영역 | 저장소 근거 | 판정 |
|---|---|---|
| 마케팅플랫폼 WAS/AP | `sv-service`, `ic-service`, `mg-service` 등 독립 업무 WAR, `tcf-core`, `tcf-web` | 부분 구현 |
| 연계 | `tcf-gateway`, `tcf-eai` | 부분 구현 |
| 배치 AP | `tcf-batch`, Spring Batch/Job Repository 설계 | 구조 정합 |
| UNO Dashboard 유사 운영 가시성 | `tcf-om`, `tcf-batch`, `/ui/om/admin/dashboard.html` | 개념 정합, 제품 동일성 미확인 |
| 출력물(RD) WAS | `/rd/{serviceId}` 보고서 연계 설계 | 구조 정합 |
| 데이터 통제 | `zdocs-1/architecture/47-data-governance.md` | 문서 정합 |
| RDW/ADW 분리 | ADR-DATA-001, Master Architecture | 원칙 정합 |

### 7.2 물리 배치 확정 한계

저장소 증적에서 시스템 그룹은 `마케팅플랫폼 15`, `신BI포털 16`, `데이터거버넌스 4`, `IT서비스 및 업무지원 28`, `데이터플랫 8`로 재검증되었다. 다만 현재 증적만으로는 다음 연결을 전수 확정할 수 없다.

```text
Hostname → Apache Instance/Route → WAS → Tomcat JVM
         → WAR/Application → ServiceId → RDW/ADW/DB → HA/DR
```

| 미확정 관계 | 필요 증적 |
|---|---|
| WEB→WAS 실제 라우팅 | `httpd.conf`, Proxy/LB 설정 |
| WAS→JVM/Connector | `server.xml`, `setenv.sh`, `CATALINA_BASE` 목록 |
| JVM→WAR | 실제 `webapps` 또는 배포 Manifest |
| WAR→ServiceId | Runtime Service Catalog |
| WAS/AP→DB | 운영 Datasource 설정, 비밀정보 제거본 |
| 실제 RDW/ADW 소유권 | Domain/Table/View Read·Write Matrix |
| HA/DR | L4/GSLB Pool, 자산원장, Failover Runbook |

`code-understand` 자동 추출기는 로컬 설정 파일에 대한 권한 문제로 실행되지 않아, `rg` 교차 검색과 원문 열람으로 대체했다.

## 10. 사실·해석·미확인 분리

### 10.1 이미지에서 확정 가능한 사실

- 5개 상시 시스템과 이행용 임시 구성이 존재한다.
- 각 시스템별 WEB/WAS/AP/DB 논리 구성요소는 제2절의 표와 같다.
- 데이터플랫은 RDW Appliance와 ADW Appliance로 구분된다.
- 이행용 구성은 운영환경 내 임시 자원 할당이다.

### 10.2 아키텍처 해석

- RDW는 준실시간/운영성, ADW는 분석/대량 책임으로 분리한다.
- 점선은 각 DB와 RDW/ADW, BI, 거버넌스, IT 지원 간 데이터 연계를 표현한다.
- IT서비스 영역은 상시 업무보다 운영 제어면의 성격이 강하다.

### 10.3 추가 증적 없이 확정하면 안 되는 항목

- 각 블록의 실제 서버 대수·Hostname·CPU·Memory·Storage
- WEB/WAS/AP 제품·버전·인스턴스 수
- 점선의 방향·프로토콜·주기·인증 방식
- 실제 RDW/ADW 테이블·뷰·사용자별 Read/Write 권한
- 자원 이중화, L4/GSLB, Cluster, Backup, RPO/RTO
- 이행용 임시 자원의 실제 폐기 일정과 잔존 데이터 처리

---

## 11. 최종 평가

본 구성은 **마케팅 실행계, RDW/ADW 데이터 계층, BI 활용계, 거버넌스 통제계, IT 운영 제어계**를 분리한 정보계 운영 아키텍처다. 핵심은 서버 목록 그 자체가 아니라, 온라인·실시간·분석·배치 워크로드의 책임과 장애 반경을 분리하는 데 있다.

다만 이 장표만으로 실제 Production Deployment를 확정할 수는 없다. 운영 승인 전에 `Server → JVM → WAR → ServiceId → DB/RDW/ADW → HA/DR`을 실행 설정과 자산 증적으로 닫아야 한다.
