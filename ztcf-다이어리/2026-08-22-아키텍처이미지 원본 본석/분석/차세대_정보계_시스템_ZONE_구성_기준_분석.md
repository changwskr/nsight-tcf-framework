# 차세대 정보계 시스템 Zone 구성 기준 분석

> **분석 대상**: 제공 이미지 `차세대 정보계 시스템 Zone 구성 기준`  
> **범위**: 전사 IT 6개 Zone의 책임과 연결 기준, 운영·개발·DR 환경별 서비스 제공 Zone 구축 대상  
> **분석 일자**: 2026-08-22  
> **분석 원칙**: 이미지에서 확인되는 기준, 아키텍처 해석, 현재 저장소 구현을 구분한다.

---

## 1. 핵심 결론

이미지는 전사 IT 시스템을 기술 제품이나 조직이 아니라 **서비스 요청의 유입·중계·처리·내부 연계 책임**에 따라 6개 논리 Zone으로 구분한다.

1. **대내 채널 Zone**: 내부 사용자가 고객 업무를 처리하기 위해 접근하는 영역
2. **대고객 채널 Zone**: 고객 채널에서 업무 요청이 유입되는 영역
3. **대외 채널 Zone**: 외부 기관과 업무를 연계하는 영역
4. **채널 통합 Zone**: 대내·대외 채널 요청을 통합·중계하는 영역
5. **서비스 제공 Zone**: 업무 로직과 데이터를 처리·저장하는 핵심 시스템 영역
6. **대내 통합 Zone**: 내부 시스템 간 인터페이스 통합을 지원하는 영역

중심은 서비스 제공 Zone이며 나머지 Zone은 사용자·기관의 요청을 안전하게 유입하고 표준화해 핵심 서비스에 전달하거나 내부 서비스 간 연계를 중개한다. 따라서 채널 시스템이 업무 원장 DB에 직접 접근하거나 서비스가 다른 서비스의 DAO/DB를 공유하는 연결은 Zone 경계를 무너뜨리는 것으로 보아야 한다.

이 Zone 체계는 운영·개발·DR 모든 환경에 공통 적용된다. 다만 환경별 구축 범위는 동일하지 않다.

- **운영**: 마케팅플랫폼, 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원 전체를 구축한다.
- **개발**: 운영과 같은 대상 시스템을 개발·기능시험 목적으로 구축한다.
- **DR**: 마케팅플랫폼, 데이터플랫폼, IT서비스 및 업무지원만 우선 구축하고 BI포탈·데이터거버넌스는 그림의 DR 대상에서 제외한다.

즉 DR은 운영환경 전체 복제가 아니라 고객 서비스 복구 우선순위에 따른 **선택적·축소 구성**이다. 다만 이미지에 RTO, RPO, 용량, 데이터 복제, failover/failback 기준은 없으므로 DR 완결성을 이 장표만으로 판단할 수 없다.

현재 저장소는 `tcf-gateway`, `tcf-eai`, 독립 업무 WAR, 운영관리·배치·JWT·UI 모듈로 논리 책임이 분리되어 있어 일부 Zone 원칙과 대응한다. 그러나 `tcf-cicd`에는 `local/dev/prod`만 있고 독립 `dr` 프로파일·배포 구성이 없으므로, 원본의 DR Zone 구축 기준이 코드·설정으로 완전히 구현되었다고 볼 수 없다.

## 2. Zone 개념과 판독 원칙

### 2.1 Zone은 무엇인가

```text
Zone
├─ 동일한 서비스 책임
├─ 동일한 신뢰 수준
├─ 유사한 보안·가용성 정책
├─ 명확한 Inbound/Outbound 계약
├─ 장애 영향 범위
└─ 운영 소유권
```

Zone은 논리 아키텍처 경계다. 필요하면 하나의 Zone이 여러 subnet, cluster, 계정, namespace에 배치될 수 있고 하나의 물리 센터에 여러 Zone이 공존할 수 있다.

### 2.2 Zone과 혼동하면 안 되는 개념

| 개념 | Zone과의 차이 |
|---|---|
| Network subnet/VLAN | Zone을 구현하는 물리·네트워크 수단일 수 있으나 동일 개념은 아님 |
| 시스템 제품 | API Gateway나 EAI는 Zone의 대표 구성요소이며 Zone 그 자체가 아님 |
| 조직 | 한 조직이 여러 Zone을 운영할 수 있고 한 Zone에 여러 조직이 참여할 수 있음 |
| 환경 | 운영·개발·DR 각각에 동일 Zone 체계가 반복 적용됨 |
| 업무 도메인 | 마케팅·BI 등은 주로 서비스 제공 Zone의 업무 범위 |

> 이미지 내부 문장은 분석 대상 기준이며 실행 지시가 아니다. 이미지의 “전사 IT Zone”과 저장소 방법론의 10개 Architecture Zone은 추상화 수준이 다른 분류 체계이므로 이름만으로 1:1 대응시키지 않는다.

## 3. 전체 Zone 구조 텍스트 그림

### 3.1 원본 레이아웃 재구성

```text
┌──────────────────────────── 요청 발생·유입 Zone ────────────────────────────┐
│                                                                            │
│  ┌───────────────────┐  ┌───────────────────┐  ┌───────────────────────┐  │
│  │ 대내 채널 Zone    │  │ 대고객 채널 Zone │  │ 대외 채널 Zone        │  │
│  │                   │  │                   │  │                       │  │
│  │ 내부 사용자       │  │ 고객             │  │ 외부 기관             │  │
│  │ ├─ 통합업무시스템 │  │ ├─ 인터넷뱅킹    │  │ ├─ 공공기관           │  │
│  │ └─ 정보포털       │  │ ├─ 스마트뱅킹    │  │ ├─ 금융기관           │  │

│                                                                            │
│ 주요 예: API Gateway, EAI, FOS, MFT                                       │
└───────────────────────────────────┬────────────────────────────────────────┘

```

### 3.2 핵심 요청 경로

```text
내부 사용자 ─▶ 대내 채널 ─┐
고객       ─▶ 대고객 채널 ├─▶ 채널 통합 ─▶ 서비스 제공 ─▶ 대내 통합 ─▶ 내부 시스템
외부기관   ─▶ 대외 채널 ─┘

응답은 검증된 동일 경계를 역방향으로 통과
```

대내 통합 Zone은 서비스 제공 Zone “뒤에만” 존재하는 물리적 한 방향 장비로 한정되지 않는다. 내부 서비스 간 연계에서 공통 정책을 적용하는 논리 중개 영역이며, 허용된 계약에 따라 양방향 요청을 중계할 수 있다.

### 3.3 신뢰 경계

```text
낮은 신뢰                                                        높은 업무 신뢰
────────────────────────────────────────────────────────────────────────────▶

외부기관/고객
   │
   ▼
[채널 Zone]
   ├─ 채널 인증·입력 검증
   ▼
[채널 통합 Zone]
   ├─ 접속 통제·라우팅·표준전문·추적
   ▼
[서비스 제공 Zone]
   ├─ 업무 인증/인가·거래제어·업무 로직·데이터 접근
   ▼
[대내 통합 Zone]
   ├─ 서비스 간 인증·계약·timeout·파일/메시지 전달
   ▼
내부 대상 시스템
```

네트워크 내부에 있다는 이유만으로 대내 통합 요청을 신뢰해서는 안 된다. Zone 간에는 서비스 ID, 발신 주체, 권한, payload schema와 추적 ID를 다시 검증해야 한다.

## 4. Zone별 상세 분석

### 4.1 대내 채널 Zone

> 내부 사용자가 고객의 업무 처리를 위해 접근하는 영역

| 항목 | 분석 |
|---|---|
| 대표 시스템 | 통합업무시스템, 정보포털 등 |
| 사용자 | 직원, 상담원, 운영·업무 담당자 |
| 주요 입력 | 고객 조회·변경·승인 요청, 내부 업무 명령 |
| 주요 출력 | 업무 결과, 고객 정보, 승인 상태 |
| 핵심 통제 | 사번 SSO, 직무/조직 기반 권한, 단말·망 식별, 화면별 접근통제 |
| 주요 위험 | 내부자 오남용, 과도한 권한, 고객정보 대량 조회 |

대내 채널은 내부망이므로 안전하다는 가정 대신 사용자·단말·직무를 함께 검증해야 한다. 조회와 변경, 승인과 실행의 권한을 분리한다.

### 4.2 대고객 채널 Zone

> 고객 채널을 통해 업무 요청이 유입되는 영역

| 항목 | 분석 |
|---|---|
| 대표 시스템 | 인터넷뱅킹, 스마트뱅킹, 콕뱅킹 등 |
| 사용자 | 개인·기업 고객 |
| 주요 입력 | 로그인, 조회, 신청, 동의, 거래 요청 |
| 핵심 통제 | MFA, WAF/DDoS, bot·fraud 탐지, rate limit, device binding |
| 가용성 | 24×365 고객 SLA, 무중단·다중화 우선 |
| 주요 위험 | 계정 탈취, 대량 공격, replay, 개인정보 노출 |

대고객 채널은 서비스 제공 Zone의 DB를 직접 조회하지 않고 채널 통합/표준 API를 통해 업무 서비스를 호출해야 한다.

### 4.3 대외 채널 Zone

> 대외기관과 업무 연계를 수행하는 영역

| 항목 | 분석 |
|---|---|
| 대표 기관 | 공공기관, 금융기관, 농협자산관리, 농정원, 농협신용보증 등 |
| 프로토콜 | 기관별 API, 전문, 파일, MFT 등 |
| 핵심 통제 | 기관 인증서/mTLS, IP allowlist, 전문 서명, 송수신 대사 |
| 운영 | 기관별 SLA·점검시간·재전송·문의 창구 관리 |
| 주요 위험 | 기관별 계약 차이, timeout 전파, 중복 전문·파일 |

기관 고유 계약을 서비스 제공 Zone에 직접 확산하지 말고 대외 adapter에서 내부 표준 계약으로 변환한다.

### 4.4 채널 통합 Zone

> 대내·대외 채널 요청을 통합·중계하는 영역

이미지의 주요 예는 영업점 MCA, MCI, 대외 MCA다.

```text
채널 통합 책임
├─ 채널 접속점 통합
├─ 외부 Interface ID → 내부 serviceId 라우팅
├─ 표준 헤더/GUID 생성·전파
├─ 인증·접속·트래픽 정책
├─ 프로토콜·전문 수용
├─ timeout·오류 표준화
└─ 채널별 응답 반환
```

업무 데이터의 의미 변환을 어디서 할지는 별도 책임표가 필요하다. 앞서 분석한 INBOUND 설계처럼 Gateway는 body를 무변환 전달하고 Service가 FLD/JSON을 Map으로 바꾸는 구조도 가능하다.

### 4.5 서비스 제공 Zone

> 업무 로직 및 데이터를 처리·저장하는 핵심 시스템 영역

| 대상군 | 핵심 역할 | DR 관점 |
|---|---|---|
| 마케팅플랫폼 | 고객 마케팅·행동정보·업무 서비스 | DR 포함 |
| 데이터플랫폼 | 데이터 수집·저장·가공·제공 | DR 포함, 세부 데이터 범위 확인 필요 |
| BI포탈 | 분석·리포팅·사용자 BI | 이미지 DR 대상에서 제외 |
| 데이터거버넌스 | 메타·표준·품질·lineage | 이미지 DR 대상에서 제외 |
| IT서비스 및 업무지원 | 인증·운영·공통 업무지원 | DR 포함 |

이 Zone은 시스템별로 DB를 소유하고 업무 서비스 인터페이스를 제공해야 한다. 다른 업무가 DB/DAO를 직접 공유하면 데이터 ownership과 장애 격리가 깨진다.

### 4.6 대내 통합 Zone

> 내부 시스템 간 인터페이스 통합을 지원하는 영역

| 구성요소 | 책임 | 주의점 |
|---|---|---|
| API Gateway | API 인증·라우팅·rate limit·관측 | 업무 로직·DB 접근 금지 |
| EAI | 시스템 간 전문·동기/비동기 연계 | timeout·재시도·중복 정책 |
| FOS | 파일/object 저장 연계 | 악성코드·암호화·보존·권한 |
| MFT | 대용량·대외 파일 전송 | 체크섬·재전송·대사·암호화 |

대내 통합 Zone은 연결 편의를 위해 모든 시스템을 무제한 연결하는 버스가 아니다. 소비자·제공자·계약·권한이 등록된 인터페이스만 허용해야 한다.

## 5. Zone 간 허용·금지 연결

### 5.1 권장 흐름 매트릭스

| 출발 → 도착 | 허용 | 조건 |
|---|---:|---|
| 대내 채널 → 채널 통합 | O | 내부 사용자·단말 인증, 화면/업무 권한 |
| 대고객 채널 → 채널 통합 | O | 고객 인증, WAF, rate limit, 표준 API |
| 대외 채널 → 채널 통합 | O | 기관 인증, 계약 전문, allowlist |
| 채널 통합 → 서비스 제공 | O | serviceId, schema, timeout, trace/GUID |
| 서비스 제공 → 대내 통합 | O | 등록된 API/EAI/FOS/MFT 계약 |
| 대내 통합 → 서비스 제공 | O | 내부 callback/연계 계약과 상호 인증 |
| 서비스 제공 → 자기 소유 DB | O | 최소권한, transaction ownership |
| 채널 → 서비스 제공 직접 | 제한 | 승인된 예외 외에는 통합 경유 |
| 채널 → 원장 DB 직접 | X | 업무·보안·감사 경계 위반 |
| 업무 A → 업무 B DB/DAO | X | API/EAI 계약 사용 |
| 외부기관 → 서비스 DB | X | 대외/채널 통합 경유 |

### 5.2 텍스트 정책 그림

```text
ALLOW
Channel → Channel Integration → Service API → Owned DB
Service A → Internal Integration → Service B API
Service → FOS/MFT through registered interface

DENY
Internet/External → Service DB
Channel UI → DAO
Service A → Service B schema/table
Gateway/EAI → business table update
DEV → PROD DB
DR standby → PROD write before promotion
```

## 6. 환경별 구축 대상 분석

### 6.1 이미지 표 재구성

| 환경 | 서비스 제공 Zone 구축 대상 | 운영 목적 |
|---|---|---|
| 운영 | 마케팅플랫폼, 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원 | 고객 서비스 제공을 위한 운영 환경 |
| 개발 | 마케팅플랫폼, 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원 | 신규/변경 개발 및 기능 테스트를 위한 개발 환경 |
| DR | 마케팅플랫폼, 데이터플랫폼, IT서비스 및 업무지원 | 재해복구를 위한 DR 환경 |

### 6.2 환경별 Zone 반복 구조

```text
PROD
대내/대고객/대외 채널 → 채널통합 → 서비스제공(전체) → 대내통합

DEV
개발용 채널/Mock       → 개발 채널통합 → 서비스제공(전체 기능) → 개발 대내통합/Stub

DR
DR 채널 진입점         → DR 채널통합 → 서비스제공(핵심 선별) → DR 대내통합
                                      ├─ 마케팅플랫폼
                                      ├─ 데이터플랫폼
                                      └─ IT서비스·업무지원
```

개발환경이 동일 시스템군을 갖는다는 것은 운영 데이터·계정·외부 연결을 그대로 공유한다는 뜻이 아니다. 데이터는 비식별·합성하고 외부기관은 Stub/Mock 또는 승인된 개발계로 격리해야 한다.

### 6.3 DR 선택적 구성의 의미

```text
운영 전체 서비스
├─ Tier 1: 고객 거래 지속 필수
│  ├─ 마케팅플랫폼 핵심
│  ├─ 데이터플랫폼 운영 데이터
│  └─ 인증·IT서비스·업무지원
├─ Tier 2: 업무 운영 지원
└─ Tier 3: 분석·거버넌스
   ├─ BI포탈
   └─ 데이터거버넌스

DR 우선 복구 = Tier 1 중심
```

BI포탈과 데이터거버넌스가 그림의 DR 구축 대상에서 빠졌다고 해서 백업·복구가 불필요한 것은 아니다. 서비스 기동 우선순위에서 제외되었을 뿐 데이터·메타데이터의 백업과 사후 복구는 별도 정의가 필요하다.

## 7. DR 설계에 추가로 필요한 기준

| 항목 | 필요한 결정 |
|---|---|
| 서비스 Tier | 어떤 기능을 DR에서 제공·제한·중단할지 |
| RTO | 서비스별 목표 복구시간 |
| RPO | DB·파일·캐시·로그별 허용 데이터 손실 |
| 용량 | 운영 대비 DR CPU/MEM/동시사용자/TPS 비율 |
| 데이터 복제 | 동기/비동기, archive log, snapshot, object replication |
| 네트워크 | DNS/L4 전환, 기관 allowlist, 인증서·방화벽 |
| Session | 재로그인 또는 DR SESSIONDB 복제 |
| Secret/Key | HSM·Vault·JWT key·인증서의 DR 준비 |
| 기동 순서 | DB → 공통서비스 → 대내통합 → 서비스 → 채널 |
| Failback | Primary 복구 후 데이터 역동기화·트래픽 환원 |
| 훈련 | 정기 전환 리허설과 RTO/RPO 실측 |

### 7.1 권장 전환 순서

```text
재해 선언/승인
   ▼
DR 네트워크·DNS/L4 준비
   ▼
DB/파일 저장소 promote 및 무결성 확인
   ▼
인증·Config·Secret·공통 IT서비스 기동
   ▼
대내 통합(API Gateway/EAI/FOS/MFT) 기동
   ▼
서비스 제공 Zone 핵심 시스템 기동
   ▼
채널 통합 및 대내/고객/대외 채널 연결
   ▼
Smoke/업무 대사 → 제한 운영 → 정상화
```

서비스 제공 Zone만 켜도 채널과 통합·인증이 준비되지 않으면 고객 서비스는 복구되지 않는다. 환경별 표는 서비스 제공 Zone만 보여주므로 전체 DR 의존관계를 별도로 관리해야 한다.

## 8. 현재 저장소와 Zone 대응

### 8.1 모듈 매핑

| Zone | 저장소 구성 | 대응 판단 |
|---|---|---|
| 대내 채널 | `tcf-ui`, `tcf-uj`, OM 관리 UI | 개발·운영 UI의 개념 대응 |
| 대고객 채널 | 인터넷/모바일 채널 애플리케이션 미포함 | 저장소 외부 영역 |
| 대외 채널 | 기관별 adapter/전용 MCA 미확인 | 제한적 또는 저장소 외부 |
| 채널 통합 | `tcf-gateway`, `tcf-web`, 공통 HTTP 진입 | API 기반 개념 대응, MCA/MCI는 미포함 |
| 서비스 제공 | 9개 `*-service`, `tcf-om`, `tcf-batch`, 업무 DB | 직접 대응 |
| 대내 통합 | `tcf-gateway`, `tcf-eai`, 파일 기능 | API/EAI/파일 일부 대응; MFT 전용 구현 미확인 |
| 인증 공통 | `tcf-jwt`, Gateway token 검증 | IT서비스·업무지원 일부 대응 |
| 운영·배포 | `tcf-oc`, `tcf-cicd`, runtime monitor | IT서비스·업무지원 일부 대응 |

`tcf-gateway`는 접근·채널 통합과 내부 API 통합 양쪽 성격을 가질 수 있다. 실제 Zone 배치는 endpoint, 신뢰수준, 네트워크 정책별로 인스턴스를 분리하거나 route 정책을 분리해야 한다.

### 8.2 현행 논리 흐름

```text
tcf-ui / 외부 Client
         │
         ▼
tcf-gateway (/gw)
├─ SESSIONDB/JWT 관문
├─ 업무 route
└─ 표준 요청 전달
         │
         ▼
독립 업무 WAR (ic/pc/ms/sv/pd/eb/ep/ss/mg)
├─ tcf-web/core 공통 pipeline
├─ Handler/Service/Repository
└─ 소유 업무 DB
         │
         ▼
tcf-eai 기반 다른 업무 API 호출
```

업무 WAR끼리 Gradle 의존을 금지하고 `tcf-eai + HTTP`로 연동하는 저장소 원칙은 서비스 제공 Zone과 대내 통합 Zone의 경계를 지키는 방향이다.

### 8.3 환경 구성 현황

```text
tcf-cicd
├─ local
├─ dev
└─ prod

독립 dr profile/directory: 확인되지 않음
```

현재 DR 설계 문서는 존재하지만 배포 구성의 독립 `dr` SoT가 없다. prod 설정을 복사해 DR에 수동 적용하는 방식은 연결 문자열·endpoint·용량·secret 오류를 유발할 수 있으므로 환경별 선언형 설정이 필요하다.

## 9. Zone 배치 판단 규칙

### 9.1 시스템 분류 질문

```text
1. 누가 최초 요청하는가?
   ├─ 내부 직원 → 대내 채널
   ├─ 고객      → 대고객 채널
   └─ 외부기관  → 대외 채널

2. 요청을 통합·중계하는가?
   └─ 예 → 채널 통합

3. 업무 로직을 실행하고 데이터를 소유하는가?
   └─ 예 → 서비스 제공

4. 내부 시스템 간 API/전문/파일 전달을 제공하는가?
   └─ 예 → 대내 통합
```

하나의 제품이 여러 질문에 “예”라면 배포 instance나 endpoint를 역할별로 분리하고 각 경계의 정책을 다르게 적용한다.

### 9.2 배치 결정 표

| 특성 | 권장 Zone |
|---|---|
| 고객 UI/BFF | 대고객 채널 |
| 직원 업무 화면 | 대내 채널 |
| 기관 프로토콜 adapter | 대외 채널 |
| MCA/MCI 채널 router | 채널 통합 |
| 업무 Service/DB | 서비스 제공 |
| 공통 API Gateway/EAI/File transfer | 대내 통합 |

## 10. 보안 기준

| 경계 | 필수 통제 |
|---|---|
| 고객 → 대고객 채널 | WAF, DDoS, MFA, bot/fraud, TLS |
| 내부 사용자 → 대내 채널 | SSO, RBAC/ABAC, 단말·망 통제, 행위감사 |
| 기관 → 대외 채널 | mTLS/기관 인증서, IP allowlist, 서명·대사 |
| 채널 → 채널 통합 | client identity, rate limit, schema/크기 검증 |
| 채널 통합 → 서비스 | service identity, audience, serviceId 권한, timeout |
| 서비스 → 대내 통합 | mTLS, API catalog, circuit breaker, retry/idempotency |
| 서비스 → DB | 계정 분리, 최소권한, 암호화, 감사, schema ownership |
| DEV ↔ PROD/DR | 기본 차단, 승인된 제한 경로만 허용 |

Zone 경계마다 deny-by-default를 적용하고 방화벽 규칙뿐 아니라 애플리케이션 계층의 서비스 인증과 인가를 함께 사용해야 한다.

## 11. 가용성·장애 격리 기준

| Zone | 대표 장애 | 격리 수단 |
|---|---|---|
| 대내/대고객 채널 | 사용자 폭주·세션 장애 | autoscale, rate limit, session isolation |
| 대외 채널 | 기관 지연·전문 오류 | 기관별 pool/bulkhead, timeout, queue |
| 채널 통합 | Gateway/MCA 병목 | active-active, route별 quota, circuit breaker |
| 서비스 제공 | 업무·DB 장애 | 도메인별 WAR/DB 격리, transaction·timeout |
| 대내 통합 | EAI/FOS/MFT 장애 | adapter별 bulkhead, durable queue, 재전송 |

한 Zone의 장애가 전체 서비스로 전파되지 않도록 connection pool, thread pool, timeout, retry budget을 대상 시스템별로 분리해야 한다.

## 14. 검증 시나리오

1. 모든 시스템과 endpoint가 하나의 주 책임 Zone에 등록되어 있는지 확인한다.
2. 대내·대고객·대외 채널에서 원장 DB로 직접 연결되는 경로가 없는지 확인한다.
3. 업무 WAR가 다른 업무 WAR의 DB/DAO에 직접 의존하지 않는지 확인한다.
4. 채널 통합에서 서비스 ID별 호출 권한과 schema·크기 제한이 적용되는지 확인한다.
5. 대내 통합의 API Gateway/EAI/FOS/MFT 인터페이스가 catalog와 일치하는지 확인한다.
6. 고객·직원·기관 identity가 서비스 제공 Zone까지 위·변조 없이 전달되는지 확인한다.
7. 기관별 timeout과 retry가 별도 bulkhead로 격리되는지 확인한다.
8. 운영과 개발 사이의 DB·Session·Queue·Secret·외부기관 연결이 격리되는지 확인한다.
9. 개발 데이터가 비식별/합성 데이터 정책을 따르는지 확인한다.
10. 운영 대상 6개 서비스군과 개발 대상 6개 서비스군의 기능 매핑이 유지되는지 확인한다.
11. DR에 마케팅플랫폼·데이터플랫폼·IT서비스/업무지원이 실제 배포 가능한 상태인지 확인한다.
12. DR 제외 BI포탈·데이터거버넌스의 데이터 백업과 사후 복구 정책이 존재하는지 확인한다.
13. 서비스별 RTO/RPO와 운영 대비 DR 용량을 부하·전환 시험으로 검증한다.
14. DNS/L4, 인증서, 기관 allowlist, Gateway route, DB endpoint가 DR 전환되는지 확인한다.
15. SESSIONDB 미복제 시 재로그인 정책과 고객 영향이 승인되어 있는지 확인한다.
16. DR 전환 후 요청·응답·거래로그·GUID 추적·배치가 정상 동작하는지 확인한다.
17. Primary 복구 후 failback과 데이터 역동기화 절차를 시험한다.
18. `tcf-cicd`의 배포 설정에 독립 DR profile 또는 DR용 선언적 override가 있는지 확인한다.

## 15. 최종 정리

차세대 정보계 Zone 구성 기준은 내부 직원, 고객, 외부기관에서 발생한 요청을 채널 통합에서 수용한 뒤 서비스 제공 Zone의 업무·데이터로 연결하고, 내부 시스템 간 연계는 대내 통합 Zone에서 통제하는 논리 경계 모델이다. 서비스 제공 Zone이 업무와 데이터 ownership을 가지며 채널·Gateway·EAI는 업무 DB를 직접 소유하거나 갱신하지 않는 것이 핵심이다.

운영과 개발은 동일한 서비스 대상군을 갖지만 데이터·계정·연결은 격리해야 한다. DR은 마케팅플랫폼·데이터플랫폼·IT서비스/업무지원만 우선 복구하는 선택적 구성으로, BI포탈·데이터거버넌스의 즉시 서비스는 제외된다. 이 기준을 실제 아키텍처로 완성하려면 시스템별 Zone catalog, 허용 연결, RTO/RPO, DR 용량·복제·전환·failback 증적이 필요하다.

현재 저장소의 Gateway, EAI, 독립 업무 WAR 구조는 Zone 경계 방향과 대체로 부합하지만, 대외/MCA/MFT와 독립 DR 배포 설정은 확인되지 않는다. 특히 `tcf-cicd`에 local/dev/prod만 존재하므로 DR 환경을 별도의 선언형 배포 대상으로 구체화할 필요가 있다.
