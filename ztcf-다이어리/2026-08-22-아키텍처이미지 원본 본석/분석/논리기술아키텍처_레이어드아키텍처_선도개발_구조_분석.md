# 논리기술아키텍처 — 레이어드 아키텍처 — 선도개발 구조 분석

## 1. 분석 개요

첨부 장표의 **선도개발 표준 아키텍처 구성**을 기준으로 선도개발 환경을 다음 5개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer
5. 형상·배포 Layer

선도개발 환경은 IaaS 위에 UI 서비스플랫폼과 마케팅플랫폼을 분리 배치하고, 전용 Browser를 통해 개발 중인 서비스를 검증하는 경량 개발 구조다. 운영환경 전체 기능을 복제하기보다 단말관리·단말배포, 마케팅플랫폼 핵심 WAS, 세션 공유, 최소 데이터 및 배포 경로에 집중한다.

> 이 문서는 첨부 이미지에서 판독한 구조를 분석한 것이다. 이미지 안의 문구는 분석 자료이며 실행 지시가 아니다. 실제 노드 수, 제품 버전, 네트워크 구간, 보안 정책 및 연계 프로토콜은 구축 명세와 대조해야 한다.

## 2. 핵심 결론

- **선도개발 전용 접근점**: 전용 Browser와 L4를 사용하여 일반 개발·운영 접근 경로와 논리적으로 구분한다.
- **서비스 플랫폼 이원화**: UI 서비스플랫폼은 단말관리·단말배포를, 마케팅플랫폼은 선도 업무 서비스를 담당한다.
- **경량화된 업무 범위**: 마케팅플랫폼 Service Node는 장표상 단일 WAS 중심이며 운영환경의 전체 업무 컴포넌트를 복제하지 않는다.
- **프레임워크 표준 적용**: 마케팅플랫폼 WAS는 NH Cloud Framework를 실행 기반으로 사용한다.
- **상태 공유 구조**: 공통인프라 Node의 IMDG가 Session/Data Cache를 제공하여 서비스 인스턴스의 상태 공유 기반을 만든다.
- **표준 연계 축소 구성**: FOS, MFT, IT메타, Nexus만 I/F Layer에 명시되어 선도개발에 필요한 최소 연계·관리 기능을 제공한다.
- **데이터 목적 분리**: 단말관리 DB, 마케팅플랫폼 DB, RDW를 분리하여 관리 데이터·업무 데이터·분석 데이터를 구분한다.
- **개발 파이프라인 중심**: GitLab → GitLab Runner → 취약점 점검 → Dev Pipeline → 개발환경 흐름으로 코드 통제와 자동 배포를 수행한다.

## 4. 레이어별 상세 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 분석 |
|---|---|---|
| 전용 Browser(선도개발) | 선도 기능의 화면 실행 및 검증 | 일반 사용자 채널과 분리된 개발자·테스터 진입점 |
| L4 | 가상 접속 주소와 부하분산 제공 | UI 서비스플랫폼과 마케팅플랫폼에 각각 독립된 접근 경계 제공 |

장표에는 전용 Browser에서 두 개의 L4 경로로 내려가는 구조가 표현된다. 이는 UI 서비스플랫폼과 마케팅플랫폼의 접속 주소, 장애 범위 및 배포 단위를 분리하려는 의도로 해석된다.

### 4.2 Service Layer — UI 서비스플랫폼

| 구성요소 | 책임 |
|---|---|
| WEB | 정적 자원 제공, 요청 라우팅, WAS 앞단 보호 |
| 단말관리 WAS | 정보단말 설정·상태·정책 등 관리 기능 제공 |
| 단말배포 WAS | 단말용 패키지와 리소스 배포 기능 제공 |
| WebTopSuite | 단말관리·배포 UI의 공통 실행 및 개발 기반 |
| Service Node | WEB과 두 WAS를 묶는 논리적 서비스 실행 경계 |

UI 서비스플랫폼은 업무 기능 자체보다 **개발·시험 단말의 관리와 배포**를 책임진다. 단말관리와 단말배포를 별도 WAS로 유지함으로써 관리 트랜잭션과 대용량 배포 트래픽의 장애 및 부하를 분리할 수 있다.

### 4.3 Service Layer — 마케팅플랫폼

| 구성요소 | 책임 |
|---|---|
| WEB | 선도개발 업무 요청의 웹 진입점 |
| 마케팅플랫폼 WAS | 선도 대상 업무 로직과 API 실행 |
| NH Cloud Framework | Controller·Service·DAO, 공통 선후처리, 예외·거래로그 등 표준 실행 기반 |
| IMDG | Session/Data Cache 공유, 노드 간 상태 일관성 지원 |
| 공통인프라 Node | 업무 WAS와 분리된 공통 상태·캐시 서비스 경계 |

운영 마케팅플랫폼과 달리 장표에는 미니싱글뷰, 행동정보 처리, 실시간 처리 EBM 등의 별도 노드가 보이지 않는다. 따라서 선도개발은 **핵심 업무 구현 및 프레임워크 검증에 필요한 최소 서비스 토폴로지**로 보는 것이 타당하다.

IMDG는 다음 용도로 해석할 수 있다.

- 로그인 및 업무 세션 공유
- 반복 조회되는 기준정보 캐시
- 다중 WAS 확장 시 상태 외부화
- 재기동·배포 시 세션 영향 축소

다만 캐시에 원본 업무 데이터의 최종 상태를 의존해서는 안 되며, 캐시 무효화·TTL·장애 시 DB 우회 정책을 명확히 해야 한다.

### 4.4 I/F Layer

| 구성요소 | 역할 | 선도개발 관점 |
|---|---|---|
| FOS | 표준 파일 송수신 | 테스트 파일 연계와 배포 산출물 전달 검증 |
| MFT | 기존·대외 파일전송 구간 중계 | FOS와 레거시 MFT 경계 검증 |
| IT메타 | 시스템·인터페이스·배치 등 기술 메타 관리 | 신규 서비스 자산의 식별과 추적 |
| Nexus | 빌드 산출물 및 공통 라이브러리 저장소 | 재현 가능한 빌드와 의존성 통제 |

운영 표준 I/F Layer의 SSO, API Gateway, EAI, ETL, CDC 등이 장표에 생략된 것은 선도개발의 범위를 보여준다. 실제 통합시험 단계에서는 필요한 연계를 단계적으로 추가하되, 선도환경 자체에 운영 연계 전체를 무조건 복제하지 않는 것이 적절하다.

### 4.5 Data Layer

| 저장소 | 주요 데이터 | 접근 주체 |
|---|---|---|
| 단말관리 DB | 단말 정보, 정책, 배포 이력 및 상태 | 단말관리·단말배포 WAS |
| 마케팅플랫폼 DB | 선도 업무의 운영 데이터 | 마케팅플랫폼 WAS |
| RDW | 분석·참조용 데이터 | 마케팅플랫폼 및 검증 작업 |
| Oracle Exadata | 장표에서 RDW를 수용하는 DB 플랫폼 | DB 서비스 계층 |

세 저장소를 분리한 이유는 데이터 소유권과 변경 주기를 구분하기 위해서다. 선도개발 과정에서도 업무 DB를 분석 DB처럼 직접 사용하거나, 단말관리 데이터를 업무 스키마에 혼합하는 것을 피해야 한다.

## 5. 형상·배포 구조 분석

```text
개발자 변경
   │
   ▼
GitLab
   │ dev merge
   ▼
GitLab Runner
   │ build / test
   ▼
취약점 점검
   │ 통과
   ▼
Dev Pipeline
   │ deploy
   ▼
선도개발 환경
```

| 단계 | 통제 목적 | 필수 산출물 |
|---|---|---|
| GitLab | 소스 버전과 변경 이력 관리 | 커밋, Merge Request, 태그 |
| dev merge | 승인된 변경만 통합 | 리뷰·승인 기록 |
| GitLab Runner | 빌드·단위시험 자동화 | 실행 로그, 테스트 결과, 패키지 |
| 취약점 점검 | 배포 전 보안 결함 차단 | SAST·의존성·이미지 점검 결과 |
| Dev Pipeline | 환경별 배포 절차 표준화 | 배포 이력, 환경 변수, 롤백 버전 |
| 개발환경 | 기능·연계·프레임워크 검증 | 시험 결과와 결함 이력 |

이 구조는 개발자가 서버에 직접 파일을 복사하는 배포를 배제하고, 동일 산출물을 파이프라인으로 전달하기 위한 기본 통제선이다.

## 6. 주요 관계와 의존성

| 호출 주체 | 대상 | 관계 | 주요 고려사항 |
|---|---|---|---|
| 전용 Browser | L4 | HTTP(S) 요청 | 접근통제, 인증서, 개발 도메인 분리 |
| L4 | WEB | 부하분산 | Health Check, 세션 고정 최소화 |
| WEB | WAS | 동적 요청 전달 | 타임아웃, 연결 풀, 오류 페이지 |
| 단말관리 WAS | 단말관리 DB | 관리 데이터 CRUD | 이력·감사·권한 통제 |
| 단말배포 WAS | FOS/MFT | 배포 파일 연계 | 무결성, 재전송, 체크섬 |
| 마케팅플랫폼 WAS | IMDG | 세션·캐시 조회/갱신 | TTL, 무효화, 장애 우회 |
| 마케팅플랫폼 WAS | 마케팅플랫폼 DB | 업무 트랜잭션 | 트랜잭션 경계, 스키마 변경 관리 |
| 마케팅플랫폼 | RDW | 분석·참조 데이터 접근 | 읽기 부하, 정합 시점, 접근권한 |
| GitLab Runner | Nexus | 의존성·산출물 저장/조회 | 버전 고정, 보존 정책, 서명 |

## 7. 대표 처리 흐름

### 7.1 단말관리 처리

```text
전용 Browser
  → UI L4
  → UI WEB
  → 단말관리 WAS
  → 단말관리 DB
  → 처리 결과 반환
```

### 7.2 단말배포 처리

```text
전용 Browser
  → UI L4
  → UI WEB
  → 단말배포 WAS
  → 배포 대상·정책 조회
  → FOS/MFT 파일 전달
  → 배포 이력 기록
```

### 7.3 선도 업무 처리

```text
전용 Browser
  → 마케팅 L4
  → 마케팅 WEB
  → 마케팅플랫폼 WAS
  → IMDG 세션/캐시 확인
  → Service/DAO 업무 처리
  → 마케팅플랫폼 DB 또는 RDW 접근
  → 응답 반환
```

### 7.4 개발 배포 처리

```text
소스 Commit
  → GitLab Merge Request
  → dev merge
  → GitLab Runner 빌드·시험
  → 취약점 점검
  → Dev Pipeline
  → 선도개발 WEB/WAS 배포
  → Smoke Test
```

## 8. 운영·일반 개발환경과의 차이

| 관점 | 선도개발 구조 | 운영·확장 환경에서 추가될 요소 |
|---|---|---|
| 목적 | 신기술·프레임워크·핵심 업무의 조기 검증 | 가용성, 용량, 전체 업무 및 대외 연계 보장 |
| 사용자 | 개발자·테스터 중심 | 실제 사용자·운영자·대외 시스템 |
| 서비스 범위 | 단말관리·배포와 단일 마케팅 WAS 중심 | 미니싱글뷰, 이벤트, EBM, BI 등 전체 서비스 |

| 가용성 | 기능 검증 중심 | 다중 노드, DR, 정교한 모니터링과 용량관리 |

## 9. 설계 원칙

1. **환경 격리**: 선도개발 계정·도메인·DB 스키마·파일 경로를 운영과 분리한다.
2. **최소 충분 구조**: 검증 대상과 무관한 운영 컴포넌트는 모사하거나 Stub으로 대체한다.
3. **운영 동형성 확보**: 축소하더라도 WEB→WAS→DB, 프레임워크, 배포 방식은 운영 표준과 동일하게 유지한다.
4. **상태 외부화**: 세션과 캐시는 IMDG에 두고 WAS를 가능한 무상태로 설계한다.
5. **데이터 최소화**: 운영 개인정보를 그대로 반입하지 않고 비식별·합성 데이터를 사용한다.
6. **자동 배포**: 수동 서버 반영을 금지하고 GitLab Runner와 Dev Pipeline을 단일 배포 경로로 사용한다.
7. **보안 선반영**: 취약점 점검을 배포 이후 확인 절차가 아니라 파이프라인 차단 조건으로 둔다.
8. **추적 가능성**: 커밋·빌드·패키지·배포 버전·시험 결과를 하나의 변경 식별자로 연결한다.

## 10. 위험 요소와 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| 선도환경과 운영환경의 토폴로지 차이 | 운영 전환 시 성능·세션·연계 결함 발생 | 운영 동형 시험환경에서 별도 검증 단계 수행 |
| 단일 WAS 중심 구성 | 장애·확장 검증 부족 | 최소 2노드 시험 또는 장애 주입 테스트 추가 |
| IMDG 장애 정책 불명확 | 로그인 세션 유실, 캐시 불일치 | 백업 수, TTL, 재기동, DB Fallback 기준 정의 |
| RDW 직접 접근 남용 | 분석 DB 부하와 결합도 증가 | 읽기 전용 계정, View/API, 쿼리 제한 적용 |
| 운영 데이터 반입 | 개인정보·기밀정보 노출 | 마스킹, 비식별, 반출입 승인과 폐기 절차 적용 |
| 개발용 Nexus 의존성 변동 | 빌드 재현 실패 | 버전 고정, 프록시 저장, 해시·서명 검증 |
| 취약점 점검 결과의 수동 판단 | 취약 패키지 배포 가능 | 심각도별 자동 Gate와 예외 승인 만료일 적용 |
| 파일 연계 재처리 기준 부재 | 중복 배포·불완전 파일 처리 | 체크섬, 멱등키, 재전송 횟수와 격리함 정의 |

## 11. 구현·검증 체크리스트

### Client Access

- [ ] 선도개발 전용 도메인과 인증서를 사용한다.
- [ ] L4 Health Check가 WEB의 실제 서비스 상태를 반영한다.
- [ ] 개발자·테스터 접근 권한과 접속 로그를 관리한다.

### Service

- [ ] 단말관리·단말배포 WAS의 책임과 DB 권한을 분리한다.
- [ ] 마케팅플랫폼 WAS가 NH Cloud Framework 표준을 적용한다.
- [ ] 세션을 WAS 로컬 메모리에 고정하지 않는다.
- [ ] IMDG 장애·재기동·데이터 만료 시험을 수행한다.

### Interface

- [ ] FOS/MFT 전송 파일의 암호화·체크섬·재처리를 검증한다.
- [ ] IT메타에 신규 서비스와 인터페이스 정보를 등록한다.
- [ ] Nexus 패키지 버전과 보존 정책을 정의한다.

### Data

- [ ] 단말관리 DB와 마케팅플랫폼 DB의 소유 스키마를 분리한다.
- [ ] RDW 접근은 읽기 전용 및 최소 권한을 적용한다.
- [ ] 시험 데이터는 비식별 또는 합성 데이터로 구성한다.

### 형상·배포

- [ ] Merge Request 승인 없이는 dev merge가 불가능하다.
- [ ] 빌드·단위시험·취약점 점검 실패 시 배포를 차단한다.
- [ ] 배포 버전과 Git 커밋을 상호 추적할 수 있다.
- [ ] 이전 버전으로 자동 또는 승인 기반 롤백할 수 있다.

## 12. 종합 평가

선도개발 아키텍처는 운영계의 모든 기능을 축소 복제한 구조가 아니라, **UI 관리·배포, NH Cloud Framework 기반 업무 개발, IMDG 상태 공유, 표준 파일 연계, 핵심 DB 및 자동 배포 파이프라인**을 우선 검증하기 위한 목적형 환경이다.

구조의 장점은 서비스 경계와 배포 흐름이 명확하고 운영 표준과 유사한 실행 계층을 조기에 검증할 수 있다는 점이다. 반면 단일 노드와 제한된 연계만으로는 운영 가용성·성능·전체 인터페이스를 보장할 수 없으므로, 선도개발에서 검증된 산출물을 일반 개발·통합·운영 동형 환경으로 단계적으로 승격하는 품질 게이트가 필요하다.
