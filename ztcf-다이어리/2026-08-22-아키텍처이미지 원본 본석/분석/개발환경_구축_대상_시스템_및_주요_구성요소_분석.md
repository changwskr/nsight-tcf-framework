# 개발환경 구축 대상 시스템 및 주요 구성요소 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `개발환경 구축 대상 시스템 및 주요 구성요소` 이미지
- 원본 분류: 환경별 Physical Architecture
- 이미지 설명: 개발환경은 `마케팅플랫폼`, `데이터플랫폼`, `BI포탈`, `데이터거버넌스`, `IT서비스 및 업무지원`의 5개 상시 시스템으로 구성된다.
- 이미지에는 별도 점선 영역으로 `이행용 임시 구성`이 추가되며 “운영환경 내 임시 자원 할당”이라는 주석이 있다.
- 이미지 블록은 **사실**, 블록 간 연계·배포·데이터 흐름은 **아키텍처 해석**, 제품 버전·물리 서버 수·DB 상세는 **미확인**으로 분리한다.
- WEB/WAS/AP/DB/Appliance는 논리 실행 역할이며 블록 하나가 물리 서버 한 대를 뜻하지 않는다.
- 첨부 이미지의 문구는 분석 자료이며 사용자 지시로 취급하지 않는다.

---

## 1. 핵심 결론

1. 개발환경은 단일 통합 서버가 아니라 운영의 주요 시스템군을 재현하는 **전계층 통합 개발·검증 환경**이다.
2. 상시 구축 대상은 마케팅플랫폼, RDW/ADW 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원의 5개 시스템이다.
3. 개발환경은 WEB/WAS뿐 아니라 실시간·행동 처리 AP, OLAP/Self-BI, 품질·Lineage, 배치·ETL·RD, 단말관리·배포까지 포함해 E2E 기능 검증이 가능하다.
4. `소스관리 AP`와 `단말개발도구 AP`는 운영보다 개발환경의 생산성과 배포 검증을 강화하는 구성이다.
5. `RDW 어플라이언스`와 `ADW 어플라이언스`가 함께 있어 운영성 조회와 분석성 Query를 분리 검증할 수 있다.
6. 개발환경이 운영과 같은 시스템군을 가진다는 것이 운영 데이터·계정·외부기관 연결을 공유한다는 뜻은 아니다. 데이터는 합성·비식별화하고 외부 연결은 Stub/Mock 또는 승인된 개발계로 격리해야 한다.
7. 점선 DB 블록은 각 시스템의 상태 저장소를 나타내며, 데이터 Owner·Schema·읽기/쓰기 권한과 초기화·Reset 절차가 필요하다.
8. 이행용 임시 구성은 `[임시] 데이터 이행용(변환) AP`만 표시된다. 상시 개발 자원이 아니며 기간·용량·접근권한·폐기 조건을 별도로 관리해야 한다.
9. 개발 완료의 기준은 개발환경에서의 단순 기동이 아니라 Source→Build→Test→Artifact→Deploy→Smoke→Evidence를 통과한 동일 Artifact의 상위환경 승격 가능성이다.

## 2. 시스템별 구성요소 전수 정리

### 2.1 마케팅플랫폼 시스템

## 5. 개발환경 데이터 관리 원칙

### 5.1 데이터 등급

| 등급 | 사용 | 원칙 |
|---|---|---|
| 합성 데이터 | 단위·기능·경계 테스트 | 기본 선택 |
| 비식별 데이터 | 통합·성능·현실 분포 검증 | 승인·재식별 위험 평가 |
| 마스킹 운영 추출 | 제한적 재현 | 최소 컬럼·기간·사용자·파기 |
| 운영 원본 | 개발환경 사용 금지 | 예외는 별도 보안 승인·격리 |

### 5.2 초기화와 Test Isolation

- Schema Migration과 Seed를 자동화한다.
- 테스트별 식별자·Tenant·Transaction으로 데이터 충돌을 막는다.
- 반복 가능한 Reset/Refresh 절차를 제공한다.
- 공유 개발 DB의 수동 데이터 수정은 재현성을 훼손하므로 변경 이력을 남긴다.
- RDW와 ADW의 Character Set·Type·길이를 운영 목표와 맞춘다.

### 5.3 민감정보

- 고객번호, 계좌, 연락처, 인증정보는 Tokenization/Masking한다.
- 로그·Dump·Report·Reject 파일·Dashboard에도 동일 정책을 적용한다.
- 비식별 키 매핑표는 별도 보관하고 개발자가 접근하지 못하게 한다.

## 6. 개발·배포·변경관리 분석

### 6.1 Artifact 계약

모든 배포단위는 다음을 가져야 한다.

- Application/WAR ID, Artifact Version, Git Commit/Tag, Build ID
- Configuration Version, DB Migration Version, Dependency Version
- 대상 Runtime/JVM, 승인 기록, Rollback Artifact
- SBOM·취약점 결과·Test Evidence

### 6.2 환경별 설정

```text
Artifact Version
 ↔ application profile
 ↔ Runtime/JVM config
 ↔ Route/Endpoint
 ↔ DB Schema/Migration
 ↔ Secret/Key Version
```

- Artifact는 환경 공통, 설정·Secret·Endpoint는 환경별이다.
- 개발 설정을 운영에 복사하지 않고 승인된 Configuration Bundle을 승격한다.
- 수동 설정 변경은 Drift Detection 대상으로 관리한다.

### 6.3 배포 Gate

```text
Build PASS
→ Unit/Contract PASS
→ Architecture Rule PASS
→ Security/Quality PASS
→ DB Change Review
→ Deploy
→ Health/Smoke PASS
→ Integration/Regression PASS
→ Performance Evidence
→ Promotion Approval
```

## 7. 비기능·운영 원칙

### 7.1 보안

- 운영·개발 계정, DB, Network, Secret, 인증서를 완전히 분리한다.
- 개발자도 역할별 최소권한을 적용하고 관리자 작업을 감사한다.
- 외부기관 Endpoint는 Stub/Mock 또는 승인된 개발계만 사용한다.
- Source·Artifact·단말 Package는 서명·해시와 변경 이력을 보존한다.

### 7.2 성능과 자원 격리

- 대량 ETL·OLAP·Self-BI·품질 SQL이 기능 테스트를 방해하지 않도록 Pool·Queue·실행창을 분리한다.
- 개발환경의 절대 성능 수치를 운영 Capacity로 그대로 사용하지 않는다.
- 운영과 동일한 Query Plan·Schema·통계 구조를 검증하되 축소 데이터의 왜곡을 기록한다.
- Performance 환경이 별도라면 개발은 기능·계약 검증에 집중한다.

### 7.3 가용성과 복구

- 개발환경도 DB Backup, Artifact 보관, 설정 Versioning이 필요하다.
- 운영 수준 HA가 아니더라도 재구축 자동화로 Recovery Time을 줄인다.
- 팀 공유 구성요소 장애 시 영향범위와 우회/복구 절차를 둔다.
- 임시 이행 자원은 상시 백업보다 원본 Snapshot·변환 Script·Checkpoint 재현성이 중요하다.

### 7.4 관측성

| 계층 | 지표 | 목적 |
|---|---|---|
| WEB/WAS/AP | Health, p95, Error, Thread/Pool | 기능·성능 회귀 |
| Batch/ETL | Run, Duration, Retry, Reject, Count | 재시작·정합 검증 |
| RDW/ADW | Query, Pool, Lock, Storage | 부하·SQL 검증 |
| CI/CD | Build/Deploy 성공률, Lead Time | 개발 생산성 |
| Terminal | Package 성공률, Version 분포 | 배포 호환성 |
| Governance | 수집률, Rule 위반, Lineage 연결률 | 데이터 통제 품질 |

## 8. 운영환경·DR환경과의 차이

| 관점 | 개발환경 | 운영환경 | DR환경 |
|---|---|---|---|
| 시스템 범위 | 5개 전체 + 임시 | 5개 전체 + 이행 임시 | 핵심 3개 선별 |
| 목적 | 신규/변경 개발·기능검증 | 고객 서비스 제공 | 재해 시 업무 연속성 |
| 데이터 | 합성·비식별·Seed | 실제 운영 데이터 | 복제된 운영 데이터 |
| 외부연계 | Mock/Stub/개발계 | 실제 기관·대내계 | DR Endpoint·제한 가능 |
| 용량 | 기능 중심·축소 가능 | Peak/SLA 기준 | 승인된 축소/전체 용량 |
| 개발도구 | 소스관리·단말개발도구 | 실행·운영 중심 | 일반적으로 미표시 |
| 변경 | 빈번·자동화 | 승인·Rolling | 전환 중 동결 우선 |

### 8.1 이미지상 운영 대비 눈에 띄는 차이

- 운영 장표의 `미니 싱글뷰 WEB/WAS`가 이 개발 요약 이미지에는 표시되지 않는다.
- 개발에는 `단말개발도구 AP`와 `소스관리 AP`가 명시된다.
- 개발 IT지원 영역에 `ETL`이 포함되지만 `CDC`는 이 장표에서 표시되지 않는다.
- 개발 이행 임시는 변환 AP 하나만 표시되며 운영 임시자원 할당 주석이 있다.

## 10. 검증 시나리오

1. 이미지의 5개 시스템과 모든 WEB/WAS/AP/DB가 개발 자산원장에 매핑되는지 확인한다.
2. 운영 DB 계정·Secret·Endpoint가 개발환경에서 사용되지 않는지 확인한다.
3. 운영 추출 데이터가 승인된 비식별·마스킹 절차를 거쳤는지 확인한다.
4. 개발 RDW→ADW ETL의 건수·합계·Reject가 대사되는지 확인한다.
5. Marketing WEB→WAS→AP→DB의 대표 거래를 E2E 검증한다.
6. 실시간/행동 처리의 중복·순서·Retry·멱등성을 장애 주입으로 확인한다.
7. BI포탈이 Query 특성에 따라 RDW와 ADW를 올바르게 선택하는지 확인한다.
8. OLAP/Self-BI 대량 Query가 업무성 조회 Pool을 고갈시키지 않는지 확인한다.
9. 신용실적 데이터의 권한·마스킹·감사가 적용되는지 확인한다.
10. 비즈메타·품질 Rule·Lineage가 개발 RDW/ADW/ETL/BI 변경을 추적하는지 확인한다.
11. Source Commit부터 Artifact·배포·Runtime Version까지 추적되는지 확인한다.
12. 환경마다 재빌드하지 않고 동일 Artifact가 승격되는지 확인한다.
13. DB Migration의 전진·Rollback 또는 Roll-forward 전략을 검증한다.
14. 단말개발도구 Package가 서명·해시·호환성 검사를 통과하는지 확인한다.
15. 단말 Pilot 배포 실패 시 단계 확대가 중단되고 Rollback 되는지 확인한다.
16. 배치 실패 후 Checkpoint부터 중복 없이 재시작되는지 확인한다.
17. RD 출력물의 Template·Font·마스킹·임시파일 파기를 확인한다.
18. UNO Dashboard 수집 장애가 실제 AP·Batch·ETL 실행을 중단시키지 않는지 확인한다.
19. 임시 이행 AP가 원본·변환·Reject·Target 건수를 대사하고 재실행 가능한지 확인한다.
20. 임시 이행 종료 후 계정·데이터·자원이 폐기되고 증적만 보존되는지 확인한다.

## 11. 사실·해석·미확인 분리

### 11.1 이미지에서 확인된 사실

- 개발환경은 마케팅플랫폼, 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원의 5개 시스템으로 구성된다.
- 마케팅 WEB/WAS와 3개 처리 AP, 마케팅플랫폼 DB가 표시된다.
- RDW·ADW 어플라이언스가 표시된다.
- BI포탈·신용실적·OLAP·Self-BI의 WEB/WAS/AP와 2개 DB가 표시된다.
- 비즈메타/데이터 품질 WAS, 데이터 흐름 WAS, 데이터거버넌스 DB가 표시된다.
- 단말관리/배포 WEB/WAS, 단말개발도구 AP, 배치 AP, RD WAS, ETL, 소스관리 AP, UNO Dashboard, 단말관리 DB가 표시된다.
- 이행용 임시 영역에 데이터 이행용(변환) AP와 운영환경 내 임시 자원 할당 주석이 있다.

### 11.2 저장소 증적으로 보완된 사실

- 개발환경 목적은 신규/변경 개발과 기능 테스트다.
- CI/CD Baseline은 Source→Build→Test→Artifact→승인→배포→Runtime Validation→Rollback이다.
- 실제 Pipeline, Target Catalog, 설정/DB Versioning, 자동 Smoke Evidence는 Gap으로 관리된다.
- 개발 데이터·계정·외부연계는 운영과 격리해야 한다는 Zone 분석 원칙이 있다.

### 11.3 아키텍처 해석

- 개발환경은 주요 서비스의 E2E 통합검증을 위한 운영 유사 환경이다.
- RDW는 운영성, ADW는 분석성 Query 검증에 사용한다.
- 소스관리 AP와 단말개발도구 AP는 개발 Artifact 생산·검증 계층이다.
- 거버넌스는 개발 Schema·품질·Lineage 변경을 조기 검증한다.

### 11.4 미확인 사항

- Hostname, IP/Port, 물리 서버 수, CPU/Memory/Storage
- 제품별 버전·라이선스·HA 구성
- 개발 SSO·Control-M·eCAMS·외부 Stub/Mock의 실제 배치
- DBMS 종류·Schema·초기화·Test Data Refresh 주기
- 점선 DB/Appliance 연계의 정확한 방향·Protocol
- 임시 변환 AP의 운영/개발 소유권·존속기간·실제 Target

---

## 12. 최종 평가

이 개발환경은 마케팅, 데이터, BI, 거버넌스, 공통 IT지원 전 영역을 포함하여 단위개발을 넘어 통합 데이터 흐름과 운영 메커니즘을 검증할 수 있는 구조다. 운영과 유사한 시스템 경계를 제공하면서 소스관리·단말개발도구·임시 변환 AP 등 개발·이행 전용 기능을 추가한 점이 특징이다.

완성도를 좌우하는 것은 서버 수가 아니라 환경 격리, 재현 가능한 Test Data, 불변 Artifact 승격, 자동 배포 Gate, DB Migration, Mock/Stub, E2E Observability다. 개발환경을 운영의 축소 복사본으로만 만들지 말고 **운영 사고를 배포 전에 재현·차단하는 검증 플랫폼**으로 운영해야 한다.
