# 메커니즘·아키텍처 표준화 — 전문 표준화 분석

## 1. 문서 목적

본 문서는 제공된 「전문 표준화」 이미지를 기준으로 차세대 정보계의 온라인 거래 전문 표준, 적용 범위, 인터페이스별 처리 경로 및 예외 정책을 분석한다.

분석 대상은 다음과 같다.

- 표준 전문의 적용 범위와 제외 범위
- 정보단말 거래
- 영업점 MCA 연계
- MCI 연계
- API Gateway(CruzAPIM) 연계
- GSE 연계
- FLAT 전문과 JSON/HTTP 구간의 관계
- 패키지 UI 비표준 예외의 관리 원칙

> 이미지의 설명은 분석을 위한 원본 자료이며 별도의 실행 지시로 취급하지 않는다. 이미지에서 직접 확인되는 내용은 **원본 사실(FACT)**, 구조로부터 도출한 내용은 **분석(ANALYSIS)**, 추가 설계 확인이 필요한 항목은 **확인 필요**로 구분한다.

## 2. 핵심 결론

차세대 정보계의 온라인 거래는 채널과 연계 방식이 달라도 **논리적으로 동일한 표준 전문 모델**을 사용하도록 설계되어 있다. 다만 물리 전송 형식은 구간별로 다르다.

```text
채널/대내외 시스템
        │
        │ FLAT 또는 JSON/HTTP
        ▼
채널통합·대내통합 계층
  (영업점 MCA / MCI / API G/W / GSE)
        │
        │ 표준전문
        ▼
차세대 정보계 온라인 애플리케이션
```

핵심 원칙은 다음과 같다.

1. **표준 전문 우선**: 차세대 정보계 온라인 애플리케이션 거래는 표준 전문을 사용한다.
2. **채널 독립성**: 정보단말, 영업점, 비대면 채널, 대내·대외 시스템이 동일한 논리 전문 규격을 공유한다.
3. **구간별 표현 분리**: 일부 구간은 FLAT, 정보계 진입 구간은 주로 JSON/HTTP를 사용한다.
4. **통합 계층 책임**: MCA, MCI, API Gateway, GSE가 채널·기관별 차이를 흡수한다.
5. **예외 통제**: 업무 솔루션 패키지 UI는 표준 전문 적용 예외로 개별 처리한다.

## 3. 표준 전문 적용 범위

### 3.1 영역별 구성

| 대영역 | 구성요소 | 표준 전문 적용 | 주요 형식 |
|---|---|---:|---|
| 채널 | 통합업무시스템 | 적용 | MCA 앞단 FLAT, 이후 JSON/HTTP |
| 채널 | 정보단말 | 적용 | JSON/HTTP |
| 채널 | 패키지 UI | 예외 | 비표준 JSON/HTTP |
| 대고객 채널 | 비대면 채널 | 적용 | MCI 이후 JSON/HTTP |
| 채널 통합 | 영업점 MCA | 적용·중계 | FLAT ↔ JSON/HTTP |
| 채널 통합 | MCI | 적용·중계 | JSON/HTTP |
| 업무 시스템 | 마케팅플랫폼 온라인 애플리케이션 | 적용 | 표준 JSON/HTTP |
| 업무 시스템 | BI 포털 온라인 애플리케이션 | 적용 | 표준 JSON/HTTP |
| 대내 통합 | API Gateway | 적용·중계 | JSON/HTTP 중심 |
| 대내 통합 | GSE | 적용·중계 | FLAT 중심 |
| 연계 업무 | 대내 업무시스템 | 적용 | 연계 유형별 표준 전문 |

## 4. 표준 전문의 개념

### 4.1 논리 전문과 물리 형식

전문 표준화에서 반드시 구분해야 할 것은 **논리 전문 규격**과 **물리 전송 형식**이다.

| 구분 | 의미 | 예시 |
|---|---|---|
| 논리 전문 | 거래에 필요한 공통 헤더, 업무 데이터, 오류 정보의 표준 구조 | 거래 GUID, 서비스 코드, 응답 코드 |
| 물리 표현 | 논리 전문을 네트워크에서 직렬화하는 방식 | FLAT, JSON |
| 전송 프로토콜 | 직렬화된 전문을 전달하는 통신 규약 | HTTP |
| 중계 계층 | 서로 다른 채널·표현·프로토콜을 연결 | MCA, MCI, API G/W, GSE |

따라서 이미지의 `표준전문 FLAT`과 `표준전문 JSON/HTTP`는 서로 다른 전문이 아니라, 동일한 표준 개념을 구간별 표현에 맞게 전달하는 구조로 해석할 수 있다.

### 4.2 권장 논리 구조

```text
표준 전문
├─ Header
│  ├─ 전문 버전
│  ├─ 거래 GUID
│  ├─ 채널·기관 코드
│  ├─ 서비스 코드
│  ├─ 요청 일시
│  ├─ 사용자·단말 식별 정보
│  └─ 전문 길이·페이지·연속거래 정보
├─ Body
│  └─ 서비스별 요청 또는 응답 데이터
└─ Result/Error
   ├─ 성공 여부
   ├─ 표준 응답 코드
   ├─ 업무 오류 코드
   └─ 사용자 메시지·추적 정보
```

> 위 필드 구조는 이미지에 상세 필드가 없으므로 일반적인 표준 전문 설계 관점의 분석이다. 실제 필드 정의서는 별도로 확인해야 한다.

## 5. 정보단말 거래

### 5.1 원본 경로

```text
정보단말
   │ 표준전문 / JSON / HTTP
   ▼
차세대 정보계
   ├─ 마케팅플랫폼 온라인 애플리케이션
   └─ BI 포털 온라인 애플리케이션
```

### 5.2 처리 메커니즘

1. 정보단말이 서비스 코드와 요청 데이터를 표준 JSON 전문으로 생성한다.
2. HTTP를 통해 차세대 정보계 애플리케이션을 호출한다.
3. 애플리케이션의 프레임워크가 공통 헤더와 거래 식별자를 검증한다.
4. 서비스 코드에 해당하는 Controller/Service가 업무를 수행한다.
5. 처리 결과를 표준 응답 전문으로 반환한다.

### 5.3 분석

- 정보단말은 별도의 MCA/MCI 중계가 표시되지 않은 직접 온라인 거래 경로다.
- 직접 호출이라도 인증·인가, GUID, 오류 전문 및 거래 로그 규칙은 동일하게 적용되어야 한다.
- 정보단말과 서버가 같은 표준 전문 버전을 공유해야 한다.

## 6. 영업점 MCA 연계

### 6.1 원본 경로

```text
통합업무시스템
    │ 표준전문 / FLAT
    ▼
영업점 MCA
    │ 표준전문 / JSON / HTTP
    ▼
차세대 정보계 애플리케이션
    └─ 마케팅플랫폼 미니 싱글뷰 거래
```

### 6.2 표준화 내용

이미지는 다음 경로를 명시한다.

```text
통합업무시스템 → 영업점 MCA → 차세대 정보계 AP
```

주요 대상은 마케팅플랫폼의 싱글뷰 거래다.

### 6.3 MCA의 책임

| 책임 | 설명 |
|---|---|
| 채널 접점 | 통합업무시스템의 거래 요청 수신 |
| 형식 변환 | FLAT 전문을 JSON 구조로 매핑 |
| 프로토콜 변환 | 기존 채널 방식에서 HTTP 호출로 전환 |
| 라우팅 | 서비스 코드에 따라 차세대 정보계 AP 선택 |
| 공통 헤더 유지 | GUID, 채널, 사용자, 단말 정보를 손실 없이 전달 |
| 오류 변환 | 정보계 오류를 채널이 이해하는 FLAT 응답으로 변환 |

### 6.4 왕복 흐름

```text
[요청]
통합업무시스템
  → FLAT 요청 전문
  → 영업점 MCA
  → JSON/HTTP 표준 요청 전문
  → 차세대 정보계 AP

[응답]
차세대 정보계 AP
  → JSON/HTTP 표준 응답 전문
  → 영업점 MCA
  → FLAT 응답 전문
  → 통합업무시스템
```

## 7. MCI 연계

### 7.1 원본 경로

```text
비대면 채널
    │
    ▼
MCI
    │ 표준전문 / JSON / HTTP
    ▼
차세대 정보계 AP
```

이미지의 예시는 다음과 같다.

- 비대면 채널 → MCI → 차세대 정보계 AP
- 영업점 방문 예약
- 실시간 이용 내역 조회

### 7.2 분석

- MCI는 인터넷·모바일 등 비대면 채널의 통합 진입점 역할을 한다.
- MCI에서 인증·채널 식별·라우팅·트래픽 제어를 수행할 가능성이 높다.
- 정보계 구간은 JSON/HTTP 표준 전문으로 통일되어 채널 구현과 업무 서비스가 분리된다.
- 비대면 거래는 사용자 트래픽 변동이 크므로 타임아웃, 동시성, 재시도 정책이 중요하다.

## 8. API Gateway(CruzAPIM) 연계

### 8.1 원본 경로

```text
차세대 정보계 AP
    ⇄ 표준전문 / JSON / HTTP
API Gateway(CruzAPIM)
    ⇄ 표준전문
대내 업무 AP
```

### 8.2 적용 거래

- 차세대 정보계 AP와 대내 업무 AP 간 Inbound 거래
- 차세대 정보계 AP와 대내 업무 AP 간 Outbound 거래
- API Gateway 단독 경유
- API Gateway ↔ EAI 복합 경유

### 8.3 Inbound·Outbound 구분

| 구분 | 호출 방향 | 예시 |
|---|---|---|
| Inbound | 대내 시스템 → API G/W → 정보계 AP | 대내 시스템이 정보계 서비스 호출 |
| Outbound | 정보계 AP → API G/W → 대내 시스템 | 정보계가 계정계·정보계·카드 등 호출 |

### 8.4 API Gateway의 책임

- API 인증과 호출자 식별
- URI·서비스 코드 기반 라우팅
- 요청량 제한과 과부하 보호
- 표준 헤더·GUID 전달
- 스키마·필수값 검증
- 공통 오류 응답과 감사 로그
- 버전 관리와 API 폐기 정책
- EAI 연계가 필요한 경우 내부 인터페이스 솔루션으로 전달

### 8.5 단독·EAI 경유 구조

```text
[단독 경유]
정보계 AP ⇄ API Gateway ⇄ 대내 업무 AP

[EAI 경유]
정보계 AP ⇄ API Gateway ⇄ EAI ⇄ 대내 업무 AP
```

API Gateway가 외부 계약과 보안 정책을 담당하고 EAI가 내부 메시지 변환·오케스트레이션을 담당하도록 책임을 구분하는 것이 바람직하다.

## 9. GSE 연계

### 9.1 원본 경로

```text
차세대 정보계 BI 포털 온라인 애플리케이션
    │ 표준전문 / FLAT
    ▼
GSE
    │ 표준전문
    ▼
은행(법인)
```

이미지에서는 은행(법인) 클릭포 업무 요청 거래를 GSE 연계 예시로 제시한다.

### 9.2 분석

- GSE는 은행 또는 법인 시스템과 정보계 간 전용 연계 채널이다.
- API Gateway의 JSON/HTTP 경로와 달리 GSE 구간은 FLAT 전문을 사용한다.
- GSE는 기관별 전문 레이아웃과 정보계 표준 전문 간 매핑 책임을 가져야 한다.
- 기관 오류 코드와 내부 표준 오류 코드 간 변환표가 필요하다.

## 10. 패키지 UI 예외 처리

### 10.1 원본 사실

이미지는 다음 정책을 명시한다.

> 차세대 정보계는 표준 전문을 적용하되 업무 솔루션 패키지 화면은 예외로 한다.

패키지 UI → BI 포털 온라인 애플리케이션 경로는 `비표준 JSON/HTTP`로 표시되어 있다.

### 10.2 예외 발생 이유 분석

- 상용 패키지가 고유 API와 데이터 모델을 요구할 수 있다.
- 제품 업그레이드 호환성을 위해 표준 전문 강제 적용이 어려울 수 있다.
- 화면과 솔루션 엔진 간 전용 계약이 이미 존재할 수 있다.

### 10.3 예외 통제 원칙

| 통제 항목 | 권고 기준 |
|---|---|
| 예외 등록 | 대상, 사유, 책임자, 유효기간 기록 |
| 경계 격리 | 비표준 전문을 패키지 내부 경계에 한정 |
| 외부 연계 | 패키지 밖으로 나갈 때 표준 전문으로 변환 |
| 보안 | 인증·인가·암호화·감사 로그는 표준과 동일 적용 |
| 관측성 | GUID 또는 상관관계 ID를 유지 |
| 변경 관리 | 패키지 업그레이드 시 인터페이스 회귀 시험 |
| 종료 계획 | 표준 전환 가능성을 정기적으로 검토 |

## 11. 전문 변환 및 매핑 원칙

### 11.1 변환 계층

```text
외부/채널 전문
    │
    ▼
[Adapter]
  - 전문 파싱
  - 코드·타입·길이 검증
  - 채널 필드 → 표준 필드 매핑
    │
    ▼
내부 표준 전문
    │
    ▼
업무 서비스
```

### 11.2 필드 매핑 기준

- 원본 필드와 표준 필드 간 1:1 매핑표를 관리한다.
- 코드값은 공통 코드 또는 변환 테이블로 관리한다.
- 날짜·숫자·금액·문자 인코딩 규칙을 명시한다.
- FLAT의 길이·패딩·정렬 규칙을 명시한다.
- JSON의 필수 여부, 자료형, 최대 길이, `null` 허용 여부를 정의한다.
- 알 수 없는 필드, 누락 필드, 버전 차이에 대한 처리 정책을 둔다.
- 요청과 응답의 오류 코드 변환을 양방향으로 정의한다.

### 11.3 변환 금지 원칙

- 업무 의미를 중계 계층에서 임의 변경하지 않는다.
- 금액·식별자·코드의 정밀도를 손실시키지 않는다.
- GUID를 중간 계층에서 새로 발급해 원거래 연결을 끊지 않는다.
- 민감정보를 로그에 평문으로 남기지 않는다.

## 12. 전문 버전 관리

### 12.1 권장 버전 정책

```text
전문 버전 = Major.Minor

Major: 하위 호환이 깨지는 변경
Minor: 선택 필드 추가 등 하위 호환 변경
```

### 12.2 변경 유형별 처리

| 변경 | 호환성 | 처리 원칙 |
|---|---|---|
| 선택 필드 추가 | 대체로 호환 | Minor 증가 |
| 필수 필드 추가 | 비호환 가능 | Major 증가 또는 병행 운영 |
| 필드 삭제 | 비호환 | Major 증가 |
| 자료형·길이 변경 | 비호환 | 신규 버전 분리 |
| 코드값 추가 | 조건부 호환 | 소비자 수용 여부 확인 |
| 의미 변경 | 비호환 | 신규 필드·버전 사용 |

### 12.3 병행 운영

- 구버전과 신버전의 종료 일정을 명시한다.
- API Gateway/MCA/MCI/GSE에서 버전별 라우팅을 지원한다.
- 버전 사용 현황을 모니터링하고 미사용 버전을 폐기한다.
- 소비자 시스템별 전환 완료 증적을 관리한다.

## 20. 원본 사실·분석·확인 필요

### 20.1 원본 사실(FACT)

- 차세대 정보계 온라인 거래는 표준 전문을 기반으로 한다.
- 표준 전문은 각 연계 시스템 간 거래에 동일하게 적용한다.
- 업무 솔루션 패키지 UI는 예외로 개별 처리한다.
- 통합업무시스템과 영업점 MCA 사이는 FLAT으로 표시된다.
- 영업점 MCA·MCI와 차세대 정보계 사이는 JSON/HTTP로 표시된다.
- API Gateway와 GSE 연계가 표준화 범위에 포함된다.
- API Gateway 단독 또는 API Gateway와 EAI를 함께 경유할 수 있다.

### 20.2 분석(ANALYSIS)

- 표준 전문은 전송 형식 그 자체가 아니라 채널과 업무 간 논리 계약이다.
- MCA, MCI, API Gateway, GSE는 채널별 차이를 흡수하는 어댑터·중계 경계다.
- 패키지 UI 예외는 전체 표준을 약화시키지 않도록 패키지 내부에 국한해야 한다.
- 성공적인 표준화는 스키마뿐 아니라 버전, 오류, 보안, 추적, 재처리 정책까지 포함해야 한다.

### 20.3 확인 필요

1. 표준 전문의 실제 Header·Body·Error 필드 정의
2. FLAT 전문의 길이, 인코딩, 패딩 및 정렬 규칙
3. JSON 스키마와 `null`·선택 필드 정책
4. 전문 버전 전달 위치와 호환성 기준
5. MCA/MCI/GSE의 실제 변환 책임과 제품 구성
6. API Gateway와 EAI를 구분하는 경유 조건
7. Inbound·Outbound별 인증 및 권한 정책
8. GSE 대상 기관과 거래별 전문 변환표
9. Package UI 예외 목록과 승인 절차
10. GUID 생성 주체, 길이 및 전 구간 전달 규칙
11. 타임아웃, 재시도, 중복 방지 및 보상 거래 기준
12. 운영 환경의 암호화·전자서명 적용 범위

## 21. 최종 평가

본 아키텍처는 채널별 물리 형식의 차이를 통합 계층에서 흡수하고 차세대 정보계 애플리케이션에는 동일한 표준 전문 계약을 제공하려는 구조다. 이를 통해 채널과 업무 서비스의 결합도를 낮추고, 거래 모니터링·오류 처리·보안 정책을 일관되게 적용할 수 있다.

표준화의 실효성을 확보하려면 단순히 JSON 구조를 통일하는 데 그치지 않고 `서비스 코드 → 전문 버전 → 필드 정의 → 오류 코드 → 권한 → GUID → 재처리 정책`을 하나의 관리 대상처럼 운영해야 한다. 또한 패키지 UI 예외는 명시적으로 등록하고 외부 경계에서는 표준 전문으로 전환하도록 제한해야 한다.
