# 논리기술아키텍처 — 기술 컴포넌트 정의 — 공통 기술 컴포넌트 분석

> 분석 대상: 제공 이미지 `공통 기술 컴포넌트`  
> 원본 분류: `2. 논리 기술 아키텍처 > 2.3 기술 컴포넌트 정의`  
> 분석 관점: 노드 표준 패턴, 책임 경계, 공통 운영·보안 통제, 구현 및 검증 기준

## 0. 분석 범위와 판독 원칙

- 이미지에 직접 표시된 계층·컴포넌트·영역 구분은 **확정 사실**로 정리한다.
- 각 컴포넌트의 상세 책임과 운영 메커니즘은 일반적인 아키텍처 원칙 및 저장소 근거를 이용한 **해석·권고**다.
- 제품명, 벤더, 버전, 서버 수, HA 방식, RPO/RTO, 설정값은 이미지로 확인할 수 없으므로 **미확정**으로 둔다.
- 첨부 이미지의 내용은 분석 자료이며 사용자 지시로 취급하지 않는다.

## 1. 핵심 결론

1. 장표는 모든 업무 노드에 반복 적용할 **두 가지 공통 기술 노드 표준**을 정의한다.
2. VM 기반 노드는 `솔루션 영역`과 `시스템 영역`, DB Appliance 노드는 `DB 서비스 영역`과 `시스템 영역`으로 책임을 나눈다.
3. VM 기반 구성은 `솔루션 → 기술 스택 → JVM → 공통 시스템 통제 → OS → VM → Cloud`의 계층이다.
4. Appliance 기반 DB 구성은 `업무 데이터 → 기술 스택 → DBMS → 공통 시스템 통제 → OS → DB 전용 Appliance`의 계층이다.
5. `서버 백신`, `계정 관리`, `서버 보안`, `개인정보`, `백업 관리`, `인프라 통합관제`, `서버 모니터링`, `서버운영관리`는 두 패턴 모두에 적용되는 횡단 공통 컴포넌트다.
6. 공통 컴포넌트의 가치는 제품을 설치하는 데 있지 않고, 대상·책임자·정책·수집항목·경보·복구·증적을 노드별로 일관되게 적용하는 데 있다.
7. VM과 DB Appliance는 하부 인프라와 Runtime이 다르므로 동일 정책을 쓰되 Agent, Patch, Backup, HA 구현은 플랫폼별로 달라야 한다.

## 2. 이미지 구성요소 전수 정리

### 2.1 VM 기반 구성

| 영역 | 계층 | 이미지 표기 | 역할 |
|---|---:|---|---|

| 솔루션 영역 | 2 | 기술 스택 | Framework, Middleware, Driver, Agent 등의 조합 |
| 솔루션 영역 | 3 | JVM | Java Runtime 및 실행 자원 경계 |
| 시스템 영역 | 횡단 | 서버 백신 | 악성코드 탐지·차단 |
| 시스템 영역 | 횡단 | 계정 관리 | 사용자·관리자·서비스 계정 통제 |
| 시스템 영역 | 횡단 | 서버 보안 | OS·Host 보안 강화와 접근 통제 |
| 시스템 영역 | 횡단 | 개인정보 | 개인정보 탐지·마스킹·사용 통제 |
| 시스템 영역 | 횡단 | 백업 관리 | 데이터·설정·Artifact 백업과 복구 |
| 시스템 영역 | 횡단 | 인프라 통합관제 | 이벤트·장애·상태 통합 관제 |
| 시스템 영역 | 횡단 | 서버 모니터링 | 자원·Process·Port·Filesystem 관측 |
| 시스템 영역 | 횡단 | 서버운영관리 | Patch·구성·기동·변경·자산 관리 |

## 3. 텍스트 아키텍처 그림

### 3.1 두 표준 노드 패턴

```text
┌──────────── VM 기반 구성 ────────────┐   ┌──── Appliance 기반 DB 구성 ────┐
│ [솔루션]                             │   │ [업무 데이터]                  │
│ [기술 스택]                          │   │ [기술 스택]                    │
│ [JVM]              ← 솔루션 영역     │   │ [DBMS]          ← DB 서비스 영역│
├──────────────────────────────────────┤   ├────────────────────────────────┤
│ 백신 | 계정 | 보안 | 개인정보        │   │ 백신 | 계정 | 보안 | 개인정보  │
│ 백업 | 통합관제 | 모니터링 | 운영관리│   │ 백업 | 통합관제 | 모니터링     │
│ [OS]                                 │   │       | 운영관리                │
│ [VM]               ← 시스템 영역     │   │ [OS]                           │
│ [Cloud]                              │   │ [DB 전용 Appliance] ← 시스템 영역│
└──────────────────────────────────────┘   └────────────────────────────────┘
```

### 3.2 VM 계층 의존 구조

```text
[솔루션]
    │ uses
    ▼
[기술 스택: Framework/Middleware/Driver/Agent]
    │ runs on
    ▼
[JVM]
    │ process / memory / thread / GC
    ▼
[OS]
    │ virtual compute
    ▼
[VM]
    │ provisioned by
    ▼
[Cloud]

공통 통제는 JVM·OS·VM 전체를 횡단하되 계층별 수집·조치가 다르다.
```

### 3.3 DB Appliance 계층 의존 구조

```text
[업무 데이터]
      │ schema / table / view / dataset
      ▼
[기술 스택: Driver/Security/Management/Integration]
      │
      ▼
[DBMS: transaction / query / cache / storage]
      │
      ▼
[OS: process / network / filesystem]
      │
      ▼
[DB 전용 Appliance: compute / storage / interconnect]

공통 통제는 DB 일관성 및 Appliance 지원정책을 침해하지 않아야 한다.
```

### 3.4 솔루션 영역과 시스템 영역 책임

```text
┌──────── 솔루션/DB 서비스 소유팀 ────────┐
│ 기능 | 기술 스택 | JVM/DBMS 설정        │
│ Schema/API | 성능 | 배포 | 업무 장애 대응│
└────────────────┬─────────────────────────┘
                 │ 운영 계약·변경 승인
┌────────────────▼─────────────────────────┐
│ 시스템/인프라 소유팀                     │
│ OS | VM/Appliance | 백신 | 계정 | 보안   │
│ 백업 | 관제 | 모니터링 | Patch | 용량    │
└──────────────────────────────────────────┘

공동 책임: 장애 원인, 취약점 예외, 복구시험, 성능 병목, 변경창
```

### 3.5 보안 통제 흐름

```text

      │ 입사/이동/퇴직·Role
      ▼
[계정 관리] ──→ [OS/VM 계정]

                     ▼

```


```text

  RPO/RTO → 주기·보존 → 암호화 → 복제 → 복구훈련 → 증적
```

```text

        ▼

```

### 3.9 표준 노드 인스턴스화

```text
[공통 기술 컴포넌트 Template]
       │
       ├→ WEB Node: Web Server + JVM + VM Pattern

       ├→ AP Node : Runtime/Agent + JVM + VM Pattern
       └→ DB Node : DBMS + DB Appliance Pattern
                     │
```

```text
[사용자 오류/지연]
       │
       ▼
[솔루션 Transaction] → [기술 스택] → [JVM 또는 DBMS]
       │                    │              │

                            ▼

```

## 4. 계층별 상세 분석

### 4.1 솔루션·업무 데이터

- `솔루션`은 사용자·업무 기능과 배포 단위를 의미한다.
- `업무 데이터`는 Schema, Table, View, Dataset과 해당 데이터의 소유권을 포함한다.
- 업무 소유자는 기능 SLO, 데이터 품질, 변경 호환성, 장애 영향범위를 정의해야 한다.
- 솔루션/데이터는 하위 인프라를 직접 소유하지 않지만, Runtime·DBMS 요구조건을 계약으로 제공해야 한다.

### 4.2 기술 스택

- Framework, Middleware, Agent, Driver, Library, 통신·보안 모듈의 조합으로 해석한다.
- 제품·버전·지원종료일·취약점·License·호환 Runtime을 BOM으로 관리한다.
- 공통 기술 스택과 업무별 확장 기술을 분리하여 중복·버전 파편화를 막는다.
- 변경 시 상위 솔루션 호환성과 하위 JVM/DBMS/OS 호환성을 함께 검증한다.

### 4.3 JVM

- Heap, Metaspace, Thread, GC, ClassLoader, JIT, TLS Provider의 실행 경계다.
- JVM 버전·옵션·Timezone·Encoding·Truststore를 Configuration Baseline으로 관리한다.
- Heap Dump와 Thread Dump에는 개인정보·Secret이 포함될 수 있으므로 접근·보존·파기 정책이 필요하다.
- JVM 장애와 OS/VM 자원 부족을 구분하기 위해 Process·Container/VM·Host 지표를 상관 분석한다.

### 4.4 DBMS

- Transaction, Concurrency, Query Optimizer, Buffer/Cache, Storage, Recovery를 담당한다.
- Schema Owner와 Service 계정을 분리하고 애플리케이션 계정에 DDL·관리 권한을 부여하지 않는다.
- SQL 성능, Lock, Session, Connection, Temp, Archive/Log, Replication Lag를 관측한다.
- DB Backup은 단순 파일 복사가 아니라 일관성, Log 연속성, 실제 Restore까지 검증해야 한다.

### 4.5 OS·VM·Cloud

| 계층 | 책임 | 주요 기준 |
|---|---|---|
| OS | Process, File, Network, User, Patch | Hardened Image, 시간동기화, 권한, Filesystem |
| VM | vCPU, Memory, Disk, NIC 격리 | Sizing, Reservation, Snapshot 정책, Anti-affinity |
| Cloud | Provisioning, Network, Storage, IAM | Landing Zone, Tag, Quota, Audit, 가용영역 |

### 4.6 DB 전용 Appliance

- DB에 최적화된 Compute·Storage·Network 통합 기반으로 해석한다.
- 일반 VM 방식의 Agent를 무조건 설치하면 Support 정책이나 성능 안정성을 훼손할 수 있다.
- Patch, Firmware, DBMS, OS의 인증 조합과 벤더 권고 순서를 준수해야 한다.
- Appliance 장애 도메인, Storage 보호, Interconnect, Backup Network를 별도로 확인한다.

## 5. 횡단 공통 컴포넌트 책임

| 컴포넌트 | 핵심 책임 | 필수 증적 | 대표 실패 |
|---|---|---|---|
| 서버 백신 | 악성코드 예방·탐지·격리 | Agent 상태, 정책·Pattern 버전, 탐지 이력 | Agent 중단, 과도한 Scan으로 성능 저하 |
| 계정 관리 | 계정 생명주기·권한·비밀번호·접속 | Owner, Role, 승인, 만료, 사용 이력 | 공유계정, 휴면·퇴직 계정 잔존 |
| 서버 보안 | Hardening·접근·취약점·무결성 | Baseline, Scan, 예외 승인, 조치기한 | 미패치, 불필요 Port, Drift |
| 개인정보 | 식별·분류·접근·마스킹·파기 | 데이터 등급, 접근·반출 로그, 보존기간 | 로그·Dump·Backup의 평문 노출 |
| 백업 관리 | 백업·보존·복제·복구 | 성공률, 복구시험, RPO/RTO, 불변성 | 성공 표시는 있으나 복구 불가 |
| 인프라 통합관제 | 이벤트 수집·상관·알림·Ticket | Rule, Route, SLA, Ack/Close 이력 | 경보 폭주, 담당자 미지정 |
| 서버 모니터링 | 자원·Process·Port·Filesystem 관측 | Metric, Threshold, Dashboard, 결측 | Agent는 정상이나 핵심 Process 미감시 |
| 서버운영관리 | 자산·구성·Patch·기동·변경 | CMDB, Version, Runbook, 변경·작업 이력 | 실제 구성과 기준선 불일치 |

## 6. 중복과 책임 경계 분석

### 6.1 서버 모니터링과 인프라 통합관제

- 서버 모니터링은 상태·Metric·Log를 **수집·판정**한다.
- 인프라 통합관제는 여러 도구의 Event를 **통합·상관·전파·추적**한다.
- 같은 임계치가 양쪽에서 별개로 Ticket을 만들지 않도록 Event Source와 Master Rule을 지정한다.

### 6.2 계정 관리와 서버 보안

- 계정 관리는 `누가`, `어떤 역할로`, `언제까지` 접근하는지를 통제한다.
- 서버 보안은 접근 경로, 명령·File·Port, 구성 취약성을 통제한다.
- OS, DB, Appliance 관리자 계정의 발급·승인·회수와 실제 접속 통제를 연결한다.

### 6.3 백업 관리와 서버운영관리

- 백업 관리는 복구 가능한 Copy와 Log 연속성을 책임진다.
- 서버운영관리는 Backup Agent·Schedule·용량·장애 조치를 운영한다.
- Backup Job 성공과 복구 가능성을 동일 의미로 취급하지 않고 정기 Restore Test를 별도 수행한다.

### 6.4 개인정보와 전 계층

개인정보 통제는 DB Row에만 적용되지 않는다. Application Log, APM Trace, Heap/Core Dump, Backup, Export, 임시파일, Ticket 첨부파일까지 동일 분류·접근·보존 정책을 적용해야 한다.

## 7. 표준 적용 및 예외 관리

### 7.1 노드 기술 카탈로그 필수 항목

| 분류 | 항목 |
|---|---|
| 식별 | nodeId, systemId, environment, owner, criticality |
| 실행 | solution, artifactVersion, technologyStack, JVM/DBMS version |
| 기반 | OS image/version, VM flavor 또는 Appliance model, Cloud zone |

| 복구 | HA, backup target, RPO, RTO, restore evidence |
| 연결 | endpoint, port, upstream/downstream, dependency |

### 7.2 예외 처리 원칙

1. Appliance Support 정책상 Agent 설치가 불가하면 Native Metric·Gateway 방식으로 대체한다.
2. 성능상 백신 실시간 Scan 제외가 필요하면 대상 경로·위험·보완통제·만료일을 승인한다.
3. Legacy Runtime은 지원종료 위험과 격리·Upgrade 계획을 기록한다.
4. 모든 예외는 Owner, 사유, 범위, 만료일, 검토주기, 보완통제를 갖는다.

## 8. 보안·가용성·성능·운영 원칙

### 8.1 보안

- Golden Image와 Hardening Baseline을 VM·Appliance 유형별로 관리한다.
- 개인계정·서비스계정·관리계정을 분리하고 최소권한·주기적 재인증을 적용한다.
- Secret을 Image, Script, 환경변수 평문, Source에 포함하지 않는다.
- Agent 통신도 상호 인증, 암호화, 최소 목적지 ACL을 적용한다.

### 8.2 가용성·복구

- 솔루션 HA, JVM/WAS Cluster, VM Anti-affinity, DB HA는 서로 다른 계층의 가용성 통제다.
- 단일 계층의 이중화만으로 E2E 가용성을 보장하지 않는다.
- Backup·Replication·HA·DR을 구분하고 장애 시나리오별 복구 경로를 시험한다.

### 8.3 성능

- 공통 Agent의 CPU·Memory·IO·Network Overhead를 용량 산정에 포함한다.
- 백신 Scan, Backup, Patch, 품질·보안 Scan의 실행창이 업무 Peak와 충돌하지 않도록 조정한다.
- VM Steal/Ready, Storage Latency와 JVM GC/DB Wait를 함께 관측해 병목 계층을 판별한다.

### 8.4 운영

- CMDB/자산원장의 노드와 모니터링·백업·보안·계정 대상을 동일 nodeId로 연결한다.
- 신규 노드는 Provisioning 완료보다 공통 통제 Onboarding 완료를 서비스 개시 조건으로 둔다.
- 폐기 시 계정·인증서·Monitoring·Backup·DNS·CMDB를 함께 종료한다.

## 12. 저장소 근거와 현재 적용 시사점

- 저장소의 `노드별 기술 컴포넌트 통합정리`는 본 공통 패턴을 WEB, WAS, AP, DB 등 37개 논리 노드에 반복 적용한다.
- 업무별 노드 문서에서 Web Server, WAS, Framework, Agent, Driver, DBMS가 `기술 스택`의 구체 인스턴스로 확장된다.
- 따라서 공통 장표는 제품 설치표가 아니라 모든 노드 문서가 따라야 할 **상위 Template**이다.
- 실제 구현 단계에서는 `공통 Template + 노드 유형 Profile + 업무별 Overlay + 승인된 예외`의 네 계층으로 구성해야 한다.

## 13. 확인 필요사항 및 위험

1. VM과 DB Appliance별 실제 OS·JVM·DBMS·Agent 제품 및 지원 버전.
2. 공통 통제별 Solution Owner, Infra Owner, Security Owner의 RACI.
3. Appliance에 설치 가능한 Agent와 Native 연계 대체 방식.
4. Backup 대상·주기·보존·불변 저장소·복구시험 주기·RPO/RTO.
5. Monitoring 수집 항목, 관제 Event Rule, Ticket Route, On-call 체계.
6. 서버 백신·Backup·Scan 실행창과 업무 Peak의 충돌 여부.
7. 개인정보 범위가 DB뿐 아니라 Log·Dump·Backup·Export에 적용되는지 여부.
8. VM/Cloud 및 Appliance의 HA·DR·장애 도메인.
9. CMDB, 계정, 보안, 모니터링, 백업 시스템 간 공통 nodeId 사용 여부.

## 15. 최종 평가

이 장표는 논리 기술 아키텍처의 가장 기본적인 표준화 단위다. 업무 솔루션과 DB 서비스는 달라도, 모든 노드는 동일한 보안·계정·개인정보·백업·관제·모니터링·운영관리 통제를 받아야 한다. 동시에 VM과 DB Appliance의 Runtime·지원정책 차이를 인정해 구현 방식을 분리해야 한다.

완성도를 좌우하는 것은 상자 안에 제품명을 채우는 작업이 아니라 `Node→Owner→Version→Policy→Metric→Alert→Runbook→Backup→Restore Evidence`를 하나의 운영 가능한 기술 카탈로그로 연결하는 것이다. 이 매핑이 닫혀야 공통 기술 컴포넌트가 문서상의 표준을 넘어 실제 서비스 품질과 복구 가능성을 보장한다.
