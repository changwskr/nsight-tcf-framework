# 예외처리 아키텍처 메커니즘 분석

> **분석 대상**: 제공 이미지 `Exception Handling (1/2)`, `Exception Handling (2/2)`  
> **범위**: Service 예외 생성, Controller rollback, 공통 ErrorProcess, 표준 오류전문 및 xFrame 오류 표시  
> **분석 일자**: 2026-08-22  
> **분석 원칙**: 이미지의 설계 사실, 보안·운영 해석, 현재 저장소 구현을 구분한다.

---

## 1. 핵심 결론

두 이미지는 업무 Service에서 발생한 예외를 프레임워크 표준 `NhBaseException`으로 정규화하고, Controller가 공통 `ErrorProcess`에 위임하여 **표준 오류전문과 사용자 표시 메시지**를 생성한 뒤 xFrame에 반환하는 구조를 설명한다.

전체 메커니즘은 다음 다섯 단계다.

1. Service가 오류를 감지하거나 하위 예외를 catch하면 `NhBaseException`을 생성해 장애종류코드, 오류 서비스·메서드·파일·라인 정보를 설정하고 다시 throw한다.
2. Controller는 예외를 수신하면 Service Transaction을 rollback하고 공통 ErrorProcess를 호출한다.
3. ErrorProcess는 예외의 표준 오류코드와 메시지 사전을 이용해 표준 오류전문을 생성한다.
4. ErrorProcess는 xFrame에 표시할 사용자 오류 메시지를 별도로 만든다.
5. Controller는 오류코드와 상세 메시지를 화면 모델에 설정하고 UI는 거래 오류 팝업을 표시한다.

설계의 핵심은 **예외 발생 위치의 기술 진단정보**, **외부 계약인 표준 오류전문**, **사용자용 안내 메시지**를 한 객체에서 수집하되 표현 단계에서는 분리하는 것이다. 트랜잭션 rollback은 오류 응답 생성보다 먼저 확정되어야 하며, 오류 처리 중 발생한 2차 예외가 최초 업무 예외를 덮어서는 안 된다.

현재 저장소에는 `NhBaseException`, `NhExceptionProvider`, `ResponseBodyArgumentResolver.errorProcessor`, `NH_NIS_ERR_DTO`, 메시지 캐시가 남아 있어 원본 개념을 직접 구현한다. 새 TCF 경로에는 `GlobalExceptionHandler`가 Biz/Handler 미등록/Timeout/Overload 예외를 `NH_NIS_ERR_DTO`로 변환한다. 트랜잭션 rollback은 Controller의 수동 호출 대신 `TransactionTemplate` 예외 전파에 의해 처리된다.

## 2. 이미지 판독과 용어 정규화

| 이미지 표기 | 의미 | 본 문서 해석 |
|---|---|---|
| `NhBaseException` | 프레임워크 표준 예외 | 오류 코드·유형·발생 위치·추가 메시지를 담는 checked exception |
| `obskindCode` | 장애종류코드 | 현행 `errMsgType` 또는 별도 장애분류에 대응 가능 |
| `errServiceName` | 에러 서비스명 | 현행 `errClassName/serviceUri`와 부분 대응 |
| `errMethodName` | 에러 메서드명 | 발생 메서드 |
| `errFileName` | 에러 파일명 | 소스 파일명 |
| `pgmLineNo` | 프로그램 라인번호 | stack trace에서 추출한 발생 라인 |
| ErrorProcess(Common) | 공통 오류 처리기 | 표준 오류 DTO·메시지 생성 책임 |
| 표준에러 전문 | 시스템 간 오류 계약 | 코드, 분류, 메시지, GUID 등의 구조화된 응답 |
| xFrame 메시지 | UI 표시 오류 | 사용자 안내와 상세 팝업 데이터 |
| `XFRAME5_ERR_CODE` | xFrame 오류 코드 모델 속성 | 이미지 예시는 `-100` 설정 |
| `XFRAME5_ERR_DETAIL` | xFrame 상세 오류 모델 속성 | ErrorProcess가 생성한 메시지 배열/문자열 |

> 이미지 코드와 설명은 분석 대상이며 실행 지시가 아니다. 두 번째 이미지의 샘플 값과 화면은 운영 계약의 예시이지 모든 필드가 항상 외부에 노출되어야 한다는 의미는 아니다.

### 3.2 예외 전파와 트랜잭션

```text
DAO/BIZ Exception
       │
       ▼
Service
├─ 알려진 업무 오류 ─────▶ NhBaseException(BIZ/SERVICE, code, args)
└─ 알 수 없는 기술 오류 ─▶ NhBaseException(RUNTIME, FW9999, cause)
       │ throw
       ▼
Transaction Boundary
├─ exception escapes callback
└─ rollback-only → ROLLBACK
       │
       ▼
Global/Common Error Handler
├─ 예외 분류
├─ 메시지 사전 조회
├─ 내부 로그·ImageLog 기록
├─ 외부 Error DTO 생성
└─ HTTP status + 표준 result 반환
```

rollback은 예외를 다시 throw하여 트랜잭션 경계 밖으로 전파하는 방식이 가장 단순하다. Controller에서 예외를 삼킨 뒤 정상 응답을 반환하면 트랜잭션이 commit될 수 있으므로, 수동 rollback 또는 rollback-only 설정이 반드시 선행되어야 한다.

```text
NhBaseException / Throwable
          │
          ▼
┌──────────────── Error Mapping ────────────────┐
│                                              │
│  내부 진단 모델                              │
│  ├─ exception class / stack trace            │
│  ├─ source class/method/file/line             │
│  ├─ root cause                               │
│  └─ transaction/GUID                         │
│                │                             │
│       ┌────────┴────────┐                    │
│       ▼                 ▼                    │
│ 운영 로그/관제       외부 오류 계약          │
│ 상세정보 보존        ├─ code                 │
│                      ├─ safe message         │
│                      ├─ type                 │
│                      ├─ action message       │
│                      └─ correlationId/GUID   │

```

원본 화면은 서비스 Class, 파일, 메서드, 라인까지 표시한다. 개발 환경에서는 유용하지만 운영 사용자에게 노출하면 내부 구조가 유출되므로 환경별 노출 정책이 필요하다.

### 3.4 정상과 예외 응답의 형태

```text
정상 응답                              오류 응답
────────────────────────              ────────────────────────────
{
  "hdr_nhnis": { ... },              {
  "dto": { 업무 결과 }                 "hdr_nhnis": { ... },
}                                       "result": {
                                          "stdErrCode": "FW9999",
                                          "stdErrMsgCntn": "시스템 오류...",
                                          "errType": "RUNTIME",
                                          "addMsgContents": "조치 안내"
                                        }
                                      }
```

업무 성공 데이터와 오류 결과를 `dto`와 `result`로 분리하면 클라이언트가 계약을 안정적으로 해석할 수 있다. HTTP status와 업무 오류코드의 의미도 함께 표준화해야 한다.

## 4. 이미지 번호 기준 처리 단계

| 단계 | 주체 | 처리 | 핵심 데이터 |
|---:|---|---|---|
| 1 | Service | 예외를 `NhBaseException`으로 변환·보강 후 throw | 장애종류, 서비스/메서드/파일/라인, 오류코드 |
| 2 | Controller | Service 예외를 받아 rollback하고 Common ErrorProcess 호출 | 원 예외, HTTP 500, transaction 상태 |
| 3 | ErrorProcess | 예외 기반 표준 오류전문 생성 | 표준코드, 메시지, 유형, GUID, 진단정보 |
| 4 | ErrorProcess/Controller | xFrame 전달용 오류 메시지 생성·모델 설정 | `XFRAME5_ERR_CODE`, `XFRAME5_ERR_DETAIL` |
| 5 | UI | 거래 오류 메시지 표시 | 사용자 메시지 및 허용된 상세정보 |

## 5. 원본 코드 흐름 해석

두 번째 이미지의 코드를 정규화하면 다음 의사코드다.

```java
// Service
try {
    Map<String, Object> result = executeBusinessLogic();
    if (result == null) {
        throw new Exception("FWIN01027");
    }
    return result;
} catch (Exception e) {
    StackTraceElement source = e.getStackTrace()[0];
    NhBaseException exception = new NhBaseException(e.getMessage());
    exception.setObskindCode("AAE");
    exception.setErrServiceName(source.getClassName());
    exception.setErrMethodName(source.getMethodName());
    exception.setErrFileName(source.getFileName());
    exception.setPgmLineNo(source.getLineNumber());
    throw exception;
}

// Controller
try {
    output = service.service(input);
    commit(serviceTx);
} catch (Throwable t) {
    rollback(serviceTx);
    responseStatus = 500;
    errorMsgs = systemProcessor.insErrorProcess(t);
    model.addAttribute("XFRAME5_ERR_CODE", "-100");
    model.addAttribute("XFRAME5_ERR_DETAIL", errorMsgs);
}
```

이 코드는 설계 의도를 보여주는 샘플이다. 실제 구현에서는 `catch(Throwable)`보다 `Exception` 중심 처리, 원인 예외 연결(`cause`), 안전한 stack frame 선택, 선언적 트랜잭션 또는 TransactionTemplate 사용을 권장한다.

## 6. `NhBaseException` 논리 모델

### 6.1 권장 필드 구분

```text
NhBaseException
├─ 외부 계약
│  ├─ stdErrCode
│  ├─ errMsgType : RUNTIME | COMMON | BIZ | AUTH | SERVICE
│  ├─ messageValue[]
│  └─ errorPageUrl
├─ 사용자 메시지
│  ├─ stdErrMsgContents
│  └─ addMsgContents
├─ 내부 진단
│  ├─ serviceUri
│  ├─ errClassName
│  ├─ errMethodName
│  ├─ errFileName
│  └─ pgmLineNo
└─ Throwable cause
```

오류코드는 안정적인 계약이어야 하고 파일명·라인번호는 빌드마다 바뀔 수 있는 진단정보다. 두 범주를 같은 UI 계약으로 취급하지 않는 것이 중요하다.

### 6.2 오류 유형

| 유형 | 의미 | 예시 | 권장 HTTP status |
|---|---|---|---|
| BIZ | 업무 규칙 위반 | 잔액 부족, 처리 대상 없음 | 400/409 또는 조직 표준 |
| AUTH | 인증·인가 실패 | 토큰 만료, 권한 없음 | 401/403 |
| SERVICE | 서비스 식별·연계 문제 | 미등록 serviceId | 404/502 등 |
| COMMON | 공통 제어 오류 | timeout, overload | 429/503/504 |
| RUNTIME | 예상하지 못한 시스템 오류 | NPE, DB 장애 | 500 |

이미지 샘플은 모든 오류에 HTTP 500을 설정한다. 단순한 legacy 계약으로는 가능하지만 현대 API에서는 오류 분류에 맞는 status를 사용하는 것이 관측성과 재시도 판단에 유리하다.

## 8. 현재 구현에서 확인된 주의점

### 8.1 안전하지 않은 예외 캐스팅

`NhExceptionProvider.nhExceptionBuilder(Exception e, TYPE type)`는 전달된 `e`를 확인 없이 `NhBaseException`으로 cast한다. 일반 Exception이 들어오면 오류 정규화 과정에서 `ClassCastException`이 발생해 최초 예외를 가릴 수 있다.

또한 `NhBaseException.getErrClassInfo(Throwable e)`도 `Throwable`을 `NhBaseException`으로 강제 cast한다. 생성자 이름만 보면 임의 cause를 받을 수 있지만 실제로는 동일 타입만 안전하다.

```text
원 예외: SQLException
   │
   ▼
nhExceptionBuilder((Exception) sqlException, TYPE.RUNTIME)
   │ 강제 cast
   ▼
ClassCastException  ← 원 장애가 가려짐
```

권장 방식은 `instanceof NhBaseException` 분기 후 기존 객체를 보강하고, 그 외 예외는 cause를 보존하는 새 `NhBaseException(FW9999, cause)`으로 감싸는 것이다.

### 8.2 Stack trace 외부 노출

legacy errorProcessor는 최대 15개의 stack trace 문자열을 `NH_NIS_ERR_DTO`에 설정한다. 이 DTO가 외부 응답에 직렬화되면 패키지·클래스·서버 구조가 노출된다. 운영 응답에서는 제거하고 GUID/correlation ID만 제공하며, 상세 stack은 서버 로그나 관제 시스템에만 저장해야 한다.

### 8.3 이중 예외 처리 경로

legacy `@ControllerAdvice`와 TCF `@RestControllerAdvice`가 조건에 따라 함께 활성화될 수 있다. 처리 대상이 명확히 분리되지 않으면 handler 선택과 응답 status가 경로별로 달라질 수 있다. 구성 프로파일별 활성 조건과 예외 소유권을 테스트해야 한다.

### 8.4 메시지 조회 실패

legacy 처리에서 property template이 없거나 `errMsgType`이 null인 상태로 switch에 진입하면 2차 오류가 날 가능성이 있다. 메시지 사전 미등록은 항상 FW9999 안전 메시지로 fallback되어야 한다.

## 9. 오류 계약 설계

### 9.1 외부 응답 권장 모델

```json
{
  "result": {
    "code": "FW_TIMEOUT",
    "type": "COMMON",
    "message": "처리 시간이 초과되었습니다.",
    "action": "잠시 후 다시 시도하세요.",
    "correlationId": "GUID",
    "retryable": true
  }
}
```

다음 정보는 운영 외부 응답에서 제외하는 것이 안전하다.

- Java class와 package 전체 이름
- 메서드·파일·라인 번호
- stack trace
- SQL 및 DB 오류 원문
- 내부 서버·경로·IP
- 사용자 개인정보가 포함된 cause message

### 9.2 내부 진단 이벤트

```text
ErrorEvent
├─ timestamp
├─ guid / traceId / spanId
├─ serviceId / screenId / userId(마스킹)
├─ errorCode / type
├─ exceptionClass
├─ sourceClass / method / file / line
├─ rootCause / stackTrace
├─ transactionOutcome
├─ elapsedMs
└─ request/response image-log reference
```

외부 응답과 내부 진단 이벤트가 동일 DTO를 공유하면 민감정보가 실수로 노출되기 쉽다. 별도 모델을 사용하는 편이 안전하다.

## 10. 예외 분류와 처리 정책

| 예외 분류 | rollback | 로그 수준 | 클라이언트 메시지 | 재시도 |
|---|---|---|---|---|
| 입력 검증 | 보통 불필요 | INFO/WARN | 구체적인 안전 메시지 | 수정 후 가능 |
| 업무 규칙 | 변경 발생 전이면 불필요, 아니면 rollback | INFO/WARN | 업무 코드·안내 | 보통 불필요 |
| 인증/인가 | rollback | WARN | 인증 또는 권한 오류 | 재인증 가능 |
| 미등록 서비스 | rollback | WARN | 서비스 처리 불가 | 설정 수정 전 불가 |
| DB/외부 연계 | rollback | ERROR | 일반화된 시스템 오류 | 정책에 따라 가능 |
| Timeout | rollback-only | WARN/ERROR | 시간 초과 | 멱등성 보장 시 가능 |
| Overload | 처리 시작 전이면 TX 없음 | WARN | 일시적 혼잡 | backoff 후 가능 |
| 알 수 없는 Runtime | rollback | ERROR | FW9999 | 기본적으로 자동 재시도 금지 |

재시도 가능 여부는 HTTP status만으로 결정하지 말고 오류 계약의 `retryable`과 거래 멱등성 정책을 함께 사용해야 한다.

## 11. 권장 예외 처리 메커니즘

### 11.1 예외 정규화

```text
normalize(Throwable t, ErrorContext ctx)
  ├─ 이미 FrameworkException이면 메타데이터 보강
  ├─ 업무 Exception이면 등록 코드로 변환
  ├─ timeout/overload이면 전용 공통 코드로 변환
  └─ 그 외이면 FW9999 + cause 보존
```

### 11.2 처리 순서

```text
1. 원 예외 포착
2. Transaction rollback 확정
3. Framework 예외로 정규화
4. 내부 ErrorEvent 및 ImageLog 기록
5. 외부 ErrorResponse 생성
6. HTTP status 결정
7. 응답 반환
8. ThreadLocal/MDC/ServiceContext 정리
```

오류 로그 저장 실패가 외부 오류 응답 생성을 방해해서는 안 된다. 감사로그가 필수인 금융 거래라면 별도 영속화 실패 정책과 비동기 보상 경로를 정의해야 한다.

### 11.3 최초 예외 보존

```text
primary = 업무/DB 예외
rollbackFailure = rollback 중 예외
mappingFailure  = 오류전문 생성 중 예외
loggingFailure  = 이미지로그 저장 중 예외

throw/return primary-derived response
primary.addSuppressed(rollbackFailure)
primary.addSuppressed(mappingFailure)
primary.addSuppressed(loggingFailure)
```

최초 예외가 장애 원인이고 나머지는 후속 실패다. 운영 로그에는 모두 남기되 클라이언트 응답은 안전한 단일 코드로 제한한다.

## 12. 검증 시나리오

1. Service가 명시적 업무 오류코드를 throw하면 동일 코드와 메시지가 `result`에 생성되는지 확인한다.
2. 일반 RuntimeException이 FW9999로 변환되면서 원 cause가 내부 로그에 보존되는지 확인한다.
3. 예외 발생 시 DB 변경이 rollback되고 오류전문 생성 후 commit되지 않는지 확인한다.
4. Timeout, Overload, 인증, 업무, 미등록 서비스별 HTTP status와 오류코드를 검증한다.
5. 메시지 사전에 코드가 없을 때 안전한 기본 오류와 조치 문구로 fallback되는지 확인한다.
6. `errMsgType`이 null이어도 errorProcessor 자체가 실패하지 않는지 확인한다.
7. 일반 Exception을 `NhExceptionProvider`에 전달해도 ClassCastException 없이 정규화되는지 확인한다.
8. 원 예외와 후처리/로그 예외가 동시에 발생할 때 원 예외가 primary로 유지되는지 확인한다.
9. 운영 프로파일의 응답에 stack trace, class, method, file, line, SQL이 노출되지 않는지 확인한다.
10. GUID로 응답 오류와 서버 ErrorEvent/ImageLog를 정확히 연결할 수 있는지 확인한다.
11. legacy와 TCF Advice가 동시에 활성화될 때 각 예외에 하나의 handler만 적용되는지 확인한다.
12. 정상 응답은 `dto`, 실패 응답은 `result`에만 값이 들어가는지 확인한다.
13. xFrame이 표준 오류코드와 사용자 메시지를 안정적으로 표시하고 내부 상세정보 없이도 고객 대응이 가능한지 확인한다.
14. 오류 응답 직렬화 실패 시 최소 안전 JSON과 correlation ID를 반환하는지 확인한다.

---

## 13. 최종 정리

원본 예외처리 아키텍처는 Service가 예외 발생 정보를 `NhBaseException`에 표준화하고, Controller가 rollback과 공통 ErrorProcess를 거쳐 표준 오류전문 및 xFrame 메시지를 반환하는 중앙집중형 구조다. 이 구조는 업무 개발자가 화면별 오류 응답을 임의로 만들지 않게 하고, 코드·메시지·장애 위치·거래 추적을 공통화한다.

현재 저장소는 이 개념을 legacy `NhBaseException/ResponseBodyArgumentResolver`와 새로운 `GlobalExceptionHandler` 경로로 구현한다. `NH_NIS_ERR_DTO`와 `result` 계약, 메시지 사전, 발생 위치 추출, 트랜잭션 rollback이 확인된다. 다만 강제 타입 캐스팅, stack trace 외부 노출, handler 경로 중복 가능성은 보완이 필요한 위험이다. 향후 표준은 외부 안전 응답과 내부 상세 진단 모델을 분리하고, 모든 예외를 cause 보존 방식으로 정규화하는 방향이 적합하다.
