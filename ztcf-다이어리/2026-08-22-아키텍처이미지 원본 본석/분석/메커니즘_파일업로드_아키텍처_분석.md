# File Upload 연계 아키텍처 분석

> **분석 대상**: 제공 이미지 `File Upload` — UI F/W(xFrame) ↔ 클라우드 프레임워크(Nhins Controller) 파일 업로드
> **분석 일자**: 2026-08-22
> **분석 원칙**: 이미지에서 직접 확인되는 목표 구조와 현재 저장소 구현을 분리해 기술한다.

---

## 1. 핵심 결론

이미지는 xFrame이 파일과 업무 데이터를 `multipart/form-data`로 `/upload/{serviceId}`에 전송하면, 공통 `NhFileController(Upload)`가 서비스 ID 식별과 시스템 선·후처리를 수행하고, 요청을 `Map(List, Body)`으로 정규화해 Service에 전달하는 구조를 제시한다. Service는 파일 본문은 Object Storage에 `PUT`하고, Body의 업무 메타데이터는 Database에 기록한 뒤 성공·실패 문자열을 UI에 반환한다.

현재 저장소에는 이 목표 구조를 구성하는 기능이 부분적으로 존재한다.

- `pdmg-fw`의 `DefaultFilter`는 Multipart 요청에 대한 `ServiceContext`를 생성한다.
- `pdmg-fw`의 `ObjectStorageHandler`는 FOS/Object Storage의 HTTP PUT·GET·DELETE를 제공한다.
- `tcf-om`의 `OmUpdownloadFileController`는 실제 Multipart 업로드와 DB 메타데이터 저장 예제를 제공한다.
- 그러나 이미지와 동일한 공통 `/upload/{serviceId}`·`NhFileController`·`Map(List, Body)` 계약은 현재 소스에서 확인되지 않는다.
- `tcf-om` 예제는 FOS가 아니라 로컬 파일시스템을 사용하므로 이미지의 Object Storage 목표 구조와는 차이가 있다.

---

## 2. 이미지에서 확인되는 구성요소

| 영역 | 구성요소 | 역할 |
|---|---|---|
| UI | UI F/W(xFrame) | 파일 Upload 요청과 파일·데이터 전송 |
| Framework | `NhFileController(Upload)` | `/upload/{serviceId}` 진입, ID 식별, 선·후처리, 반환 |
| Framework | 파일 및 전문처리 | HTTP Multipart 요청을 `Map(List, Body)`으로 변환 |
| Service | `Map(List, Body)` | File 1~n과 Body 데이터를 분리해 처리 |
| 외부 저장소 | Object Storage | 파일 바이너리 저장(`File PUT`) |
| 외부 저장소 | Database | Body 또는 파일 메타데이터 저장 |

### 2.1 요청 데이터 모델

```text
HTTP Request (multipart/form-data)
├─ files / list
│  ├─ File 1
│  ├─ File 2
│  └─ File n
└─ body
   └─ 업무 데이터·파일 메타데이터
```

이미지의 `Map(List, Body)`는 파일 목록과 업무 Body를 하나의 서비스 입력 계약으로 묶기 위한 중간 모델로 해석된다. 파일 바이너리와 구조화된 업무 데이터의 생명주기는 다르지만, 동일 업로드 요청 단위로 처리 상태를 관리한다.

## 3. 이미지 기준 처리 흐름

| 단계 | 처리 주체 | 처리 내용 |
|---:|---|---|
| 1 | xFrame | 파일과 데이터를 Multipart 요청으로 전달 |
| 2 | NhFileController | URL `/upload/{serviceId}`에서 서비스 ID 인식 |
| 3 | Framework | 인증·거래제어·로깅 등 시스템 선처리 |
| 4 | 파일/전문 처리 | Multipart의 파일들을 List로, 나머지 데이터를 Body로 변환하여 Map 구성 |
| 5 | Controller → Service | `Map(List, Body)`를 서비스에 전달 |
| 6 | Service | Map에서 File 1~n과 Body를 분리 |
| 7 | Service → Object Storage | 각 파일을 FOS/Object Storage에 PUT |
| 8 | Service → Database | Body와 파일 식별자·메타데이터를 DB에 기록 |
| 9 | Framework | Service 완료 후 시스템 후처리와 예외 변환 수행 |
| 10 | Controller → xFrame | Upload 성공·실패 여부를 문자열 또는 표준 응답으로 반환 |

> 이미지 하단 설명은 번호 `5`가 두 번 표기되어 있으므로, 본 문서에서는 논리적 순서에 따라 1~10으로 재구성했다.

### 3.1 시퀀스

```text
xFrame
  │ POST /upload/{serviceId}
  │ multipart(files[], body)
  ▼
NhFileController
  │ serviceId 식별
  │ 시스템 선처리
  │ Multipart → Map(List, Body)
  ▼
Upload Service
  ├─ files[] ── PUT ──> Object Storage
  └─ body + file key ─> Database
  │
  ▼
시스템 후처리
  │
  └─ 성공/실패 응답 ──> xFrame
```

## 4. 설계 의도

### 4.1 일반 온라인 전문과 파일 채널의 분리

파일 바이너리는 JSON 표준전문에 Base64로 넣기보다 Multipart 전용 Endpoint에서 스트리밍하는 편이 메모리 사용량과 전송 크기 측면에서 유리하다. 따라서 일반 `OnlineTransactionController`와 파일 Controller를 분리하고, 인증·GUID·로깅·거래제어 같은 공통 선·후처리만 공유하는 구조다.

### 4.2 파일과 메타데이터의 저장소 분리

| 데이터 | 저장 위치 | 이유 |
|---|---|---|
| 파일 바이너리 | Object Storage/FOS | 대용량·내구성·수평 확장·파일 수명주기 관리 |
| 파일 메타데이터 | Database | 조회·검색·권한·업무 관계·상태 관리 |

DB에는 원본 파일명, 크기, MIME Type, 업로더, 업무코드, 저장소 Object Key, 체크섬, 상태 등을 기록하고, 파일 자체는 Object Storage Key로 참조하는 방식이 적합하다.

### 4.3 공통 Controller의 역할 경계

Controller는 Multipart 파싱, 서비스 ID 식별, 공통 검증과 응답 규격화까지만 담당해야 한다. 파일 저장 정책, DB 갱신, 보상처리와 업무 권한 판단은 Service 책임으로 두는 것이 바람직하다.

## 5. 현재 저장소 구현과의 매핑

| 이미지 목표 구조 | 현재 구현 | 판정 |
|---|---|---|
| `/upload/{serviceId}` | `tcf-om`의 `/ud/files/upload` | URL·서비스 라우팅 계약 차이 |
| `NhFileController(Upload)` | `OmUpdownloadFileController` | 업무 모듈 전용 구현 존재 |
| Multipart 수신 | `MultipartFile file` + 개별 RequestParam | 단일 파일 기준 구현 |
| `Map(List, Body)` | Controller 파라미터를 Service 인자로 직접 전달 | 공통 중간 모델 없음 |
| 시스템 선처리 | `DefaultFilter` Multipart 분기에서 GUID·ServiceContext 생성 | 부분 구현 |
| Object Storage PUT | `ObjectStorageHandler.put(...)` | FW 기능 존재, OM 업로드와 연결되지 않음 |
| DB 메타데이터 | `UD_FILE_META` INSERT | 구현 존재 |
| 다중 File 1~n | `@RequestParam("file") MultipartFile` | 현재 예제는 단일 파일 |
| 성공·실패 응답 | `OmUpdownloadResponseSupport.success/fail` | 구현 존재 |

## 6. 목표 구조와 현재 구현의 주요 Gap

| Gap | 영향 | 권고 |
|---|---|---|
| 공통 `NhFileController` 없음 | 업무별 Endpoint·검증·응답이 달라질 수 있음 | 공통 Multipart 진입 계약 정의 |
| `{serviceId}` 라우팅 없음 | 업로드 업무를 TCF 서비스 카탈로그와 일관되게 제어하기 어려움 | URL 또는 Header 기반 serviceId 규칙 확정 |
| 단일 파일만 지원 | 이미지의 File 1~n 요구와 불일치 | `List<MultipartFile>`와 부분 실패 정책 정의 |
| `Map(List, Body)` 계약 없음 | 파일·Body 파싱 방식이 업무별로 분산 | 명시적 `UploadCommand` 타입 권장 |
| OM은 로컬 저장소 사용 | 다중 인스턴스·Pod 환경에서 파일 공유/내구성 문제 | ObjectStorage 포트와 FOS Adapter 연결 |
| FOS Handler와 업무 Service 미연결 | 프레임워크 기능이 실제 업로드 경로에 적용되지 않음 | 저장소 인터페이스로 로컬/FOS 구현 교체 가능하게 구성 |
| 저장소·DB 원자성 없음 | 파일 저장 성공 후 DB INSERT 실패 시 고아 파일 발생 | 보상 DELETE 또는 Outbox/Saga 상태 모델 적용 |
| 체크섬·악성파일 검사 미확인 | 무결성·보안 위험 | SHA-256, 확장자/MIME 검증, 백신 검사 추가 |

## 7. 운영·보안 관점 점검사항

### 7.1 트랜잭션과 보상

Object Storage와 관계형 DB는 하나의 로컬 트랜잭션으로 묶을 수 없다. 권장 상태 흐름은 다음과 같다.

```text
RECEIVED → FILE_STORED → META_COMMITTED → COMPLETED
                      └→ FAILED → 보상 DELETE / 재처리
```

Object Key는 먼저 생성하되 DB 상태를 `UPLOADING`으로 기록하고, PUT과 메타데이터 확정을 단계적으로 수행해야 장애 시 재처리·정리가 가능하다.

### 7.2 필수 검증

- 서버 측 최대 파일·요청 크기와 프록시/Gateway 제한을 일치시킨다.
- 파일명은 표시용으로만 보존하고 저장 Object Key에 직접 사용하지 않는다.
- 확장자, 선언 MIME Type, 실제 Content Signature를 함께 검증한다.
- SHA-256 체크섬과 파일 크기를 DB에 저장해 무결성을 확인한다.
- 허용되지 않은 실행 파일, 경로 문자열, 압축폭탄을 차단한다.
- 업로드·다운로드 권한과 감사로그에 사용자, GUID, serviceId, Object Key를 남긴다.
- FOS Token·URL·응답 본문은 민감정보 마스킹 정책을 적용한다.
- 무제한 Timeout(`-1`)은 운영 환경에서 유한한 값으로 재정의한다.

### 7.3 대용량 파일

현재 OM 예제의 `file.getBytes()`와 `Files.write(byte[])`는 파일 전체를 메모리에 적재한다. 대용량 파일은 `InputStream` 기반 스트리밍, Object Storage Multipart Upload, 재시도 가능한 Part 단위 체크섬을 적용하는 편이 안전하다.

## 8. 권장 논리 인터페이스

```java
public record UploadCommand(
        String serviceId,
        List<MultipartFile> files,
        Map<String, Object> body,
        String guid,
        String userId
) {}

public interface FileObjectStorage {
    StoredObject put(String objectKey, InputStream stream, long size, String contentType);
    void delete(String objectKey);
}
```

응답은 단순 문자열보다 파일별 결과를 포함한 표준 구조가 운영에 유리하다.

```json
{
  "success": true,
  "serviceId": "sampleUploadS0",
  "guid": "...",
  "files": [
    {
      "fileId": "...",
      "originalName": "sample.pdf",
      "objectKey": "...",
      "size": 12345,
      "status": "COMPLETED"
    }
  ]
}
```

## 9. 최종 평가

이미지는 파일 업로드를 일반 온라인 JSON 거래와 분리하되, 서비스 ID·시스템 선후처리·Service 호출 체계는 프레임워크로 표준화하려는 구조다. 파일 바이너리는 Object Storage, 검색 가능한 업무 메타데이터는 DB로 분리하는 방향도 적절하다.

현재 저장소는 Multipart Context, FOS Client, 실제 업로드 Controller, 로컬 파일 저장, DB 메타데이터 기록이라는 핵심 부품을 보유하지만 하나의 공통 업로드 파이프라인으로 통합되지는 않았다. 우선순위는 `UploadCommand` 계약 정의, 저장소 포트 추상화, OM의 FOS Adapter 연결, 파일·DB 간 보상처리, 다중 파일·보안검증 표준화 순이다.
