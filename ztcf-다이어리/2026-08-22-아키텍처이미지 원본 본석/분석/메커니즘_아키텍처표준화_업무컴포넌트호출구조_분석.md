# 메커니즘·아키텍처 표준화 — 업무 컴포넌트 호출 구조 정의 분석

## 1. 핵심 결론

이 장표는 Controller·Service·DAO의 호출을 자유 연결 방식으로 허용하지 않고, **호출 범위마다 접근 가능한 진입점을 제한하는 의존성 규칙**을 정의한다.

```text
같은 기능 내부
  Controller → Service → DAO → 자기 기능 테이블

타 기능 호출
  Controller → 타 기능 Service

업무 공통 유틸리티 호출
  Controller → 공통 Utility Service

타 애플리케이션 호출
  Controller → 타 애플리케이션 Controller

타 애플리케이션 그룹 호출
  Controller → 타 그룹 Controller
```

이를 한 문장으로 요약하면 다음과 같다.

> 내부에서는 계층 순서를 따르고, 경계를 넘을수록 상대 영역의 공식 진입점만 호출한다.

Service와 DAO를 외부에 노출하지 않음으로써 데이터 소유권과 업무 규칙을 보호하고, 타 애플리케이션·타 그룹 연계는 Controller 계약을 통해서만 수행한다.

## 2. 원본 그림 FACT 전사

### 2.1 업무 분류와 예시

| 범위 | 그림의 예시 | 내부 구성 또는 테이블 |
|---|---|---|
| 애플리케이션 그룹 | `MP = 마케팅 플랫폼` | 여러 애플리케이션과 업무 공통 유틸리티 |
| 애플리케이션 | `CM = 캠페인` | `A 업무`, `B 업무` |
| 업무 공통 유틸리티 | 공통 Utility | Service, DAO, `TB_MPCOC*` |
| 타 애플리케이션 | `CO = 공통` | `C 업무`, `TB_MPCOC*` |
| 타 애플리케이션 | `MG = 메시지` | `D 업무`, `TB_MPMGD*` |
| 타 애플리케이션 그룹 | `BL = BI 포털` | `CR = 신용실적`, `E 업무`, `TB_BLCRE*` |

캠페인 애플리케이션 내부의 테이블 예시는 `A 업무 → TB_MPCMA*`, `B 업무 → TB_MPCMB*`로 표시된다.

### 2.2 기호 해석

- 파란 화살표와 하단 표의 `○`는 허용 호출이다.
- 회색 선과 `×`는 금지 호출이다.
- 숫자 1~5는 호출 범위를 나타낸다.
  1. 기능 내
  2. 타 기능
  3. 업무 공통 유틸리티
  4. 타 애플리케이션
  5. 타 애플리케이션 그룹

## 3. 원본 호출 허용 매트릭스

### 3.1 기능 내 호출

| 호출자 \ 피호출자 | Controller | Service | DAO |
|---|:---:|:---:|:---:|
| Controller | × | ○ | × |
| Service | × | × | ○ |
| DAO | × | × | × |

의미:

- Controller는 같은 기능의 Service만 호출한다.
- Service는 같은 기능의 DAO만 호출한다.
- Controller가 DAO를 직접 호출하는 것은 금지한다.
- Service 간 직접 호출과 DAO 간 호출도 금지한다.

### 3.2 타 기능 호출

| 호출자 \ 피호출자 | Controller | Service | DAO |
|---|:---:|:---:|:---:|
| Controller | × | ○ | × |
| Service | × | × | × |
| DAO | × | × | × |

의미:

- 같은 애플리케이션의 다른 기능은 Controller가 상대 기능의 Service를 호출한다.
- 타 기능의 Controller와 DAO는 직접 호출하지 않는다.
- Service가 타 기능 Service나 DAO를 호출하는 것도 금지한다.

### 3.3 업무 공통 유틸리티 호출

공통 유틸리티는 그림상 Controller 없이 Service와 DAO로 구성된다.

| 호출자 \ 피호출자 | Service | DAO |
|---|:---:|:---:|
| Controller | ○ | × |
| Service | × | × |
| DAO | × | × |

의미:

- Controller만 공통 Utility Service를 호출한다.
- 공통 Utility DAO에 대한 직접 호출은 금지한다.
- Service와 DAO가 공통 유틸리티를 직접 호출하는 것도 표준상 허용되지 않는다.

### 3.4 타 애플리케이션 호출

| 호출자 \ 피호출자 | Controller | Service | DAO |
|---|:---:|:---:|:---:|
| Controller | ○ | × | × |
| Service | × | × | × |
| DAO | × | × | × |

의미:

- 애플리케이션 경계를 넘을 때는 상대 Controller만 공식 진입점이다.
- 상대 Service·DAO 또는 테이블에 직접 접근하지 않는다.

### 3.5 타 애플리케이션 그룹 호출

| 호출자 \ 피호출자 | Controller | Service | DAO |
|---|:---:|:---:|:---:|
| Controller | ○ | × | × |
| Service | × | × | × |
| DAO | × | × | × |

의미:

- `MP → BL`처럼 그룹 경계를 넘는 호출은 Controller 간 계약만 허용한다.
- 상대 그룹의 Service·DAO·테이블은 비공개 구현이다.

## 4. 상세 텍스트 관계도

```text
애플리케이션 그룹 MP
│
├─ 애플리케이션 CM(캠페인)
│  │
│  ├─ 기능 A
│  │  ├─ Controller.method #1 ─┐
│  │  ├─ Controller.method #2 ─┼─○→ A Service ─○→ A DAO ─○→ TB_MPCMA*
│  │  └─ 금지: Controller→DAO, Service→Service, DAO→타 계층
│  │
│  └─ 기능 B
│     └─ B Controller.method ─○→ B Service ─○→ B DAO ─○→ TB_MPCMB*
│
│  기능 간 허용: A Controller ─○→ B Service
│  기능 간 금지: A Service/DAO ─×→ B Controller/Service/DAO
│
├─ 업무 공통 유틸리티
│  └─ Utility Service ─→ Utility DAO ─→ TB_MPCOC*
│     호출 허용: 기능 Controller ─○→ Utility Service
│
├─ 애플리케이션 CO(공통)
│  └─ C Controller ─→ C Service ─→ C DAO ─→ TB_MPCOC*
│     호출 허용: CM Controller ─○→ C Controller
│
└─ 애플리케이션 MG(메시지)
   └─ D Controller ─→ D Service ─→ D DAO ─→ TB_MPMGD*
      호출 허용: CM/CO Controller ─○→ D Controller

애플리케이션 그룹 BL(BI 포털)
└─ 애플리케이션 CR(신용실적)
   └─ E Controller ─→ E Service ─→ E DAO ─→ TB_BLCRE*
      호출 허용: MP Controller ─○→ E Controller
```

이 구조에서 검은 상자는 업무 소유 영역이고, 외부 호출자는 상대 영역 내부의 Service·DAO·테이블 구조를 알지 않아야 한다.

## 5. 범위별 호출 메커니즘

### 5.1 기능 내 — 정방향 계층 호출

```text
Controller → Service → DAO → DB
```

Controller는 요청과 응답의 오케스트레이션, Service는 업무 규칙, DAO는 영속성 접근을 담당한다. 계층을 건너뛰거나 역방향으로 호출하지 않는다.

#### 허용 이유

- 책임과 트랜잭션 경계가 명확하다.
- Controller 테스트에서 Service를 대체할 수 있다.
- Service는 DB 구현을 DAO 뒤로 숨길 수 있다.
- SQL과 테이블 변경이 Controller까지 전파되지 않는다.

#### 금지 예시

```text
Controller ─×→ DAO
Service    ─×→ Controller
DAO        ─×→ Service/Controller
```

### 5.2 타 기능 — Controller가 상대 Service 사용

같은 애플리케이션 안에서는 Controller가 타 기능 Service를 직접 호출할 수 있다. 이는 기능 간 조합을 Controller가 담당한다는 의미다.

```text
A Controller
  ├─→ A Service
  └─→ B Service
```

타 기능 DAO 직접 접근은 상대 기능의 업무 규칙을 우회하므로 금지한다.

#### 주의점

- A와 B가 서로의 Service를 호출하도록 확장하면 순환 의존이 생긴다.
- 호출 방향을 기능 의존성 그래프로 관리해야 한다.
- B Service의 입력·출력 DTO를 안정적인 내부 계약으로 정의해야 한다.

### 5.3 업무 공통 유틸리티 — 재사용 전용 Service

공통 유틸리티는 Controller 없이 Service를 공식 진입점으로 제공한다.

```text
Feature Controller → Common Utility Service → Utility DAO → DB
```

공통 코드 조회, 기준정보, 공통 계산처럼 다수 기능이 쓰지만 독립된 사용자 거래로 노출할 필요가 없는 로직에 적합하다.

공통 Utility Service가 업무별 조건 분기의 집합이 되면 안 된다. 순수한 공통 규칙 또는 명확한 공통 데이터 서비스만 포함해야 한다.

### 5.4 타 애플리케이션 — Controller 계약 호출

애플리케이션 경계를 넘으면 상대 Controller가 공개 API 역할을 한다.

```text
CM Controller → CO Controller → CO Service → CO DAO
CM Controller → MG Controller → MG Service → MG DAO
```

그림은 논리 호출 구조를 보여주므로 실제 구현은 동일 프로세스 메서드 호출, 프레임워크 서비스 디스패치 또는 HTTP/API Gateway 호출일 수 있다. 어떤 방식이든 상대 애플리케이션의 공식 서비스 ID와 DTO 계약을 사용해야 한다.

### 5.5 타 애플리케이션 그룹 — 독립 시스템 경계

그룹 경계는 가장 강한 캡슐화가 필요하다.

```text
MP Controller → BL Controller → BL Service → BL DAO
```

권장 구현은 직접 Java 의존성보다 API Gateway/HTTP 또는 표준 메시지 계약이다. 상대 그룹의 배포와 장애가 독립적이기 때문이다.

## 6. 호출 규칙을 통한 데이터 소유권 보호

그림의 테이블 접두어는 각 업무 영역의 데이터 소유권을 드러낸다.

| 데이터 | 소유 기능/영역 | 외부 접근 원칙 |
|---|---|---|
| `TB_MPCMA*` | MP/CM/A | A DAO만 직접 접근 |
| `TB_MPCMB*` | MP/CM/B | B DAO만 직접 접근 |
| `TB_MPCOC*` | MP 공통 또는 CO | 해당 소유 DAO를 통해 접근 |
| `TB_MPMGD*` | MP/MG/D | MG/D Controller 계약을 통해 접근 |
| `TB_BLCRE*` | BL/CR/E | BL/CR/E Controller 계약을 통해 접근 |

타 기능 또는 타 애플리케이션 테이블을 직접 조회하면 소유 영역의 검증, 보안, 감사, 캐시와 상태 전이 규칙을 우회한다. 따라서 **테이블 공유가 아니라 서비스 계약 공유**가 표준의 핵심이다.

## 7. Controller 호출과 내부·외부 API 구분

장표에서 타 애플리케이션 Controller 호출이 허용되지만, Controller 클래스를 Java로 직접 참조해야 한다는 뜻으로만 해석하면 결합도가 높아진다.

권장 추상화는 다음과 같다.

```text
호출 Controller
   → Port/Client Interface
      ├─ 동일 프로세스: Framework Service Dispatcher
      ├─ 타 배포 단위: HTTP/API Gateway Client
      └─ 비동기 업무: Message Producer
           → 상대 Controller/Application Entry Point
```

호출자는 전송 방식이 아니라 서비스 계약에 의존하고, 어댑터가 로컬·원격 호출 차이를 처리한다.

## 8. 트랜잭션 경계

### 8.1 기능 내

Controller가 호출한 하나 이상의 Service 작업을 단일 로컬 트랜잭션으로 묶을 수 있다. 실제 트랜잭션 속성은 Service에서 선언하고 프레임워크가 Commit/Rollback을 통제한다.

### 8.2 타 기능

동일 DB와 동일 프로세스라면 로컬 트랜잭션 참여가 가능하지만, 기능 간 결합을 줄이기 위해 전파 속성(`REQUIRED`, `REQUIRES_NEW`, read-only)을 계약에 명시해야 한다.

### 8.3 타 애플리케이션·그룹

원격 호출을 하나의 DB 트랜잭션으로 묶지 않는다.

- 각 애플리케이션은 자신의 로컬 트랜잭션을 소유한다.
- 중복 요청을 막기 위한 멱등키를 사용한다.
- 상태가 여러 시스템에 걸치면 Saga/보상 거래를 사용한다.
- 이벤트 전달은 Transactional Outbox를 적용한다.
- 타임아웃, 재시도, Circuit Breaker를 명시한다.

## 9. 의존성 및 순환 참조 통제

### 9.1 허용 의존성 방향

```text
Controller package → Service contract
Service package    → DAO contract
DAO package        → SQL Mapper/DB driver
```

### 9.2 범위 간 의존성

```text
기능 A Controller → 기능 B Service contract
기능 Controller   → Utility Service contract
애플리케이션 A    → 애플리케이션 B public API contract
그룹 A            → 그룹 B external API contract
```

### 9.3 빌드 시 검증 권고

- Controller가 DAO 패키지를 import하면 실패
- Service가 Controller 또는 타 기능 패키지를 import하면 실패
- DAO가 다른 DAO나 Service를 import하면 실패
- 타 애플리케이션의 `internal` 패키지 참조 시 실패
- 순환 기능 의존성이 발견되면 실패

ArchUnit 또는 정적 분석 규칙으로 자동화할 수 있다.

## 10. DTO와 계약 관리

호출 범위가 넓어질수록 계약 안정성 요구가 커진다.

| 범위 | 계약 성격 | 권장 버전 정책 |
|---|---|---|
| 기능 내 | 구현 내부 DTO | 기능 배포와 함께 변경 가능 |
| 타 기능 | 애플리케이션 내부 계약 | 하위 호환 또는 동시 배포 |
| 공통 유틸리티 | 공유 라이브러리 계약 | Semantic Versioning |
| 타 애플리케이션 | 내부 API 계약 | 명시적 API 버전·계약 테스트 |
| 타 그룹 | 외부 시스템 계약 | 장기 하위 호환·폐기 정책 |

DB 엔티티나 DAO 결과 객체를 외부 계약으로 직접 노출하지 않는다. 공개 DTO는 소유 영역 내부 모델과 분리한다.

## 11. 예외·보안·관측성

### 11.1 예외 변환

```text
DAO Exception
  → DataAccessException
  → Service Business/System Exception
  → Controller Standard Error Response
```

경계를 넘을 때 내부 클래스명, SQL, 테이블명, 스택 추적을 노출하지 않고 표준 오류코드와 `traceId`만 전달한다.

### 11.2 보안

- 동일 기능이라도 Service에서 객체 수준 권한을 검증한다.
- 타 애플리케이션·그룹 호출에는 서비스 인증과 호출자 권한을 적용한다.
- DAO는 바인드 변수와 최소 권한 DB 계정을 사용한다.
- 상대 테이블 직접 접근 권한을 애초에 부여하지 않는다.
- 공통 Utility도 입력 검증과 민감정보 마스킹을 수행한다.

### 11.3 관측성

호출마다 다음 정보를 구조화 로그와 span에 기록한다.

```text
traceId, callerGroup, callerApplication, callerFunction,
calleeGroup, calleeApplication, calleeFunction,
serviceId, callType(local/http/message), elapsedMs, resultCode
```

타 기능과 타 애플리케이션 호출 그래프를 서비스 맵으로 가시화하면 순환 호출과 병목을 조기에 발견할 수 있다.

## 13. 장점과 위험

### 장점

- 업무 규칙과 데이터 소유권을 기능 경계 안에 보호한다.
- 호출자가 상대 DAO·테이블 구조에 결합되지 않는다.
- 범위가 넓어질수록 더 안정적인 공식 계약을 사용한다.
- Controller가 업무 조합을 담당해 Service의 단일 책임을 유지한다.
- 정적 분석으로 상당수 위반을 자동 검출할 수 있다.

### 위험

- Controller에 조합 로직이 과도하게 집중될 수 있다.
- 타 기능 Service 직접 호출은 기능 간 컴파일 의존성을 만든다.
- 타 애플리케이션 Controller를 Java로 직접 참조하면 배포 독립성이 약해진다.
- 연쇄 Controller 호출이 깊어지면 지연·장애 전파·순환 호출 위험이 커진다.
- 공통 Utility가 모든 업무 규칙을 흡수하는 공유 모놀리스가 될 수 있다.

## 14. 개선 권고

### 우선순위 1 — 호출 규칙 자동화

ArchUnit/정적 분석으로 하단 호출 매트릭스를 빌드 규칙으로 구현한다.

### 우선순위 2 — 공개 계약과 내부 구현 분리

각 기능·애플리케이션에 `api`와 `internal` 패키지를 두고 외부는 `api`만 참조하도록 한다.

### 우선순위 3 — 원격 호출 추상화

타 애플리케이션·그룹 호출은 Controller 클래스 직접 참조 대신 Port/Client와 API Gateway 계약으로 구현한다.

기능·애플리케이션 간 방향성 그래프를 생성하고 순환 의존, 과도한 fan-out, 긴 호출 체인을 배포 전에 차단한다.

### 우선순위 5 — 분산 정합성 표준

멱등키, Outbox, Saga, 재시도·타임아웃·Circuit Breaker 기준을 타 애플리케이션 호출 표준에 포함한다.

## 15. FACT·ANALYSIS·확인 필요

### FACT — 그림에서 직접 확인되는 내용

- 호출 범위는 기능 내, 타 기능, 업무 공통 유틸리티, 타 애플리케이션, 타 애플리케이션 그룹의 5가지다.
- 기능 내에서는 Controller→Service, Service→DAO만 허용된다.
- 타 기능과 공통 유틸리티는 Controller→Service만 허용된다.
- 타 애플리케이션과 타 그룹은 Controller→Controller만 허용된다.
- Service와 DAO가 범위를 넘어 다른 컴포넌트를 호출하는 것은 모두 금지된다.
- 마케팅플랫폼과 BI포털의 업무·테이블 예시가 표시되어 있다.

### ANALYSIS — 구조로부터 도출한 해석

- 범위별 공개 진입점을 제한하는 계층형 캡슐화 규칙이다.
- 테이블 접두어는 업무 데이터 소유권과 연결된다.
- 타 애플리케이션 Controller는 논리적 공개 API로 해석해야 결합도를 낮출 수 있다.
- 원격 경계에서는 로컬 ACID 대신 멱등·보상·Outbox가 필요하다.

### 확인 필요

- 파란색·회색 선과 `○`·`×`의 공식 범례
- 타 기능 Service 호출 시 인터페이스 패키지와 DTO 소유 규칙
- 타 애플리케이션 Controller 호출이 로컬 Java 호출인지 프레임워크 디스패치인지 HTTP인지
- 업무 공통 유틸리티를 Service가 호출할 수 없도록 제한한 구체적 설계 배경
- 같은 기능 내 Service→Service 호출을 금지한 예외 없는 절대 규칙인지
- 공통 CO 애플리케이션과 업무 공통 Utility의 역할 및 `TB_MPCOC*` 소유권 구분
- 타 그룹 호출의 인증, 타임아웃, 재시도와 버전 정책

## 16. 최종 평가

이 호출 구조는 단순 코딩 가이드가 아니라 **업무 모듈의 캡슐화, 데이터 소유권, 배포 경계를 보호하는 아키텍처 의존성 정책**이다. 기능 내부에서는 Controller→Service→DAO의 정방향 계층을 지키고, 기능·애플리케이션·그룹 경계를 넘을수록 상대 영역의 더 공식적인 진입점만 사용한다.

실효성을 확보하려면 문서에만 두지 말고 정적 분석, API 계약 테스트, 서비스 맵과 DB 권한으로 함께 강제해야 한다. 특히 타 애플리케이션 Controller 호출을 물리 클래스 참조가 아닌 안정적인 서비스 계약으로 구현하면, 그림이 의도한 업무 독립성과 변경 영향 통제를 실제 시스템에서도 유지할 수 있다.
