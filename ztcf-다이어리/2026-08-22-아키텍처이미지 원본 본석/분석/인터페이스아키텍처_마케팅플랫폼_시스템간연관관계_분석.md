# 인터페이스 아키텍처 — 마케팅플랫폼 시스템 간 연관관계 분석

## 1. 분석 개요

첨부 장표의 **마케팅플랫폼** 시스템 간 연관관계를 기준으로, 내부 업무 모듈(MP MC / MP MB)과 주요 연계 시스템·Object Storage 사이의 **연계 경계·프로토콜·중계 경로**를 분석한다.

장표는 좌측 **마케팅플랫폼 내부 모듈**, 중앙 **인터페이스 방식(Rest API · API G/W · UI Link · GSE)**, 우측 **주요 연계 시스템·Object Storage**로 구성된다.

기존 [`인터페이스아키텍처_마케팅플랫폼_연관관계도_분석.md`](./인터페이스아키텍처_마케팅플랫폼_연관관계도_분석.md)가 채널·업무코드·ETL/FOS/JDBC까지 넓게 펼친 **연관관계 맵**이라면, 본 장표는 BI포탈 시스템구조도와 같이 **모듈 묶음 ↔ 외부 시스템 프로토콜**을 단순화해 보여 주는 **시스템 간 연관관계도**다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. `MP MC`/`MP MB`의 배포 단위, 모듈 코드(MC~MV)와 기존 CO/IC/PC… 코드의 대응, CruzAPIM·GSE 제품 정책은 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **업무 모듈 다중화**: 마케팅플랫폼을 단일 앱으로 보지 않고, 공통·상담판매·상품·고객·행동·캠페인·컨텐츠·메시지·영업지원·CS 등 **다수 업무 모듈(MP MC)** 로 분리한다.
- **미니싱글뷰 분리(MP MB)**: 마케팅 미니싱글뷰(MB)는 MC 묶음과 별도 박스로 두고, **Object Storage와 Rest API**로 연결한다.
- **Rest + CruzAPIM이 주 경로**: 채널·대외 기관·코어뱅크와의 연계는 **Rest API가 API G/W(CruzAPIM)를 경유**하는 형태가 중심이다.
- **UI Link 병행**: 코어뱅크(또는 행동정보 쪽)와 **UI Link**가 함께 표기되어, Rest 데이터 연계와 **화면·세션 문맥 연계**를 구분한다.
- **상호금융은 GSE**: 상호 금융 연계는 Rest/APIM이 아니라 **GSE** 방식으로 표기된다.
- **프로토콜 이원화·삼원화**: `Rest(APIM)` / `UI Link` / `GSE` / `Rest(Storage 직결)` 로 연계 성격을 나눈다.

## 3. 장표 구성요소 전사

### 3.1 마케팅플랫폼 내부 — MP MC

| 모듈 | 코드 | 역할(해석) |
|---|---|---|
| 마케팅 공통 | MC | 공통 기능·공통 API |
| 마케팅 상담판매 | MS | 상담·판매 지원 |
| 마케팅통합상품 | MO | 통합 상품 |
| 마케팅통합고객 | MN | 통합 고객 |
| 마케팅개인고객 | MR | 개인 고객 |
| 마케팅기업고객 | MU | 기업 고객 |
| 마케팅행동정보 | ME | 고객 행동정보 |
| 마케팅캠페인 | MA | 캠페인 |
| 마케팅컨텐츠 | MT | 컨텐츠 |
| 마케팅메시지 | MM | 메시지 |
| 마케팅영업지원 | ML | 영업지원 |
| 마케팅 CS | MV | 고객서비스(CS) |

> 기존 연관관계도의 CO/IC/PC/BC/MS/SA… 코드와 **표기 체계가 다르다.** 본 장표는 `M*` 계열 약어를 쓴다. 동일 업무의 재코딩인지 별도 분류인지는 매핑표로 확정해야 한다.

### 3.2 마케팅플랫폼 내부 — MP MB

| 모듈 | 코드 | 역할(해석) |
|---|---|---|
| 마케팅 미니싱글뷰 | MB | 통합업무·경량 고객 단일뷰 |

미니싱글뷰를 MC와 분리한 것은 **채널·계정계 문맥의 조회성 서비스**를 캠페인·메시지 등 온라인 마케팅 묶음과 장애·배포·연계 경로 측면에서 나누려는 의도로 해석된다.

| 방식 | 표기 | 역할 |
|---|---|---|
| API Gateway | API G/W (CruzAPIM) | Rest API 중계·인증·라우팅·할당량 |
| Rest API | Rest API | HTTP API 호출 |
| UI Link | UI Link | 화면·세션 문맥 연계 |
| GSE | GSE | 상호금융 등 전문·표준 연계 경로(장표 표기) |

### 3.4 주요 연계 시스템·저장소

| 대상 | 역할(해석) |
|---|---|
| 채널 | 대고객·대내 채널 시스템 |

## 5. 인터페이스 매핑 (시스템 간)

| # | 출발(마케팅) | 프로토콜 | 중계 | 도착 | 설계 의미 |
|---|---|---|---|---|---|
| 1 | MP MC (다수 모듈) | Rest API | CruzAPIM | 채널 | 채널 시스템 API 표준화 |
| 2 | MP MC (다수 모듈) | Rest API | CruzAPIM | 대외 기관 | 대외 API 정책·보안 일원화 |
| 3 | MP MC (다수 모듈) | Rest API | CruzAPIM | 코어뱅크 | 계정계 조회·거래성 API(권한·쿼터 필수) |
| 4 | MP MC (행동정보 ME 인접) | UI Link | (직접 UI) | 코어뱅크 등 | 화면·세션 문맥 연계. Rest와 분리 |
| 5 | MP MC (캠페인 MA 인접) | GSE | GSE | 상호 금융 | 상호금융 전용 연계 방식 |
| 6 | MP MB 미니싱글뷰 | Rest API | (장표상 직결) | Object Storage | 뷰·파일·객체 자원 접근 |

### 5.1 매핑에서 읽히는 설계 의도

1. **온라인 마케팅 업무(MC)** 의 외부 API는 **CruzAPIM으로 수렴**시킨다.
2. **상호금융**은 일반 Rest 경로와 분리해 **GSE**로 특화한다.
3. **코어뱅크**는 Rest(APIM)와 **UI Link**가 공존할 수 있어, 데이터 API와 화면 연계를 혼동하지 않아야 한다.
4. **미니싱글뷰**는 마케팅 본모듈과 분리되고, Storage Rest로 **조회·산출물 성격**의 경로를 갖는다.
5. 채널·대외·코어를 한 APIM으로 묶되, **대상별 API 제품·쿼터·타임아웃**은 분리 운영해야 한다.

## 6. 주요 처리 흐름

### 6.1 채널·대외·코어뱅크 Rest (APIM)

```text
마케팅 모듈(MC~MV 등)
  → Rest API
  → API G/W (CruzAPIM)
  → 채널 / 대외 기관 / 코어뱅크
  → 응답 → 업무 처리
```

- 인증(토큰/MTLS), 라우팅, 버전, 할당량, 차단기, Trace ID를 APIM에서 강제한다.
- 코어뱅크 호출은 읽기/쓰기 API를 구분하고, 쓰기·이체성 API는 별도 승인·한도를 둔다.

### 6.2 UI Link

```text
마케팅 모듈(행동정보 등)
  → UI Link
  → 코어뱅크(또는 연계 UI)
  → 화면/세션 문맥 공유
```

- URL·토큰·로그아웃 연동, 파라미터 허용 목록이 필요하다.
- Rest API 결과와 UI Link 문맥의 **사용자·권한 일치**를 검증한다.

### 6.3 상호금융 GSE

```text
마케팅 모듈(캠페인 등)
  → GSE
  → 상호 금융
```

- GSE 전문·타임아웃·재시도·장애 전환을 Rest 정책과 별도 정의한다.
- 캠페인·오퍼가 상호금융 고객에 미치는 영향의 감사로그를 남긴다.

### 6.4 미니싱글뷰 → Object Storage

```text
마케팅 미니싱글뷰(MB)
  → Rest API
  → Object Storage
  → 객체 조회/저장
```

- APIM 미경유(장표 표현)라면 Storage 접근 인증·암호화·감사를 스토리지 계층에서 보완한다.
- 미니싱글뷰 장애가 MC 캠페인·메시지 전체에 전파되지 않도록 배포·풀을 분리한다.

## 7. 인터페이스 설계 원칙

1. **외부 Rest 호출의 기본 경로는 CruzAPIM**이다. 모듈별 임의 URL 하드코딩을 금지한다.
2. **상호금융은 GSE 전용 계약**으로 관리하고, APIM Rest와 정책을 섞지 않는다.
3. **UI Link와 Rest를 동일 연계로 취급하지 않는다.** 문맥 전달·세션·감사 요구가 다르다.
4. **미니싱글뷰(MB)와 MC 모듈의 배포·장애 경계를 유지**한다.
5. **코어뱅크 API는 최소 권한·쿼터·개인정보 마스킹**을 적용한다.
6. Object Storage 계정은 **미니싱글뷰 전용**으로 분리한다.
7. 전 구간 **GUID/Trace ID**를 전파한다(APIM·GSE·Storage 로그 연결).
8. 기존 연관관계도의 채널 MCA·Kafka·UMS·ETL 경로는 본 장표에 없으므로, **본 도는 시스템 간 축약도**로 보고 상세 채널 흐름은 별도 문서를 병행한다.

## 8. 기존 문서와의 관계

| 문서 | 초점 | 본 장표와의 관계 |
|---|---|---|
| 마케팅플랫폼 연관관계도 분석 | 채널·업무코드·API/EAI·ETL/FOS/JDBC | 상위·상세 맵. 본 도는 APIM 중심 축약 |
| 마케팅플랫폼 분석 | 온라인 vs 행동정보(Kafka/EBM) | 행동·실시간은 본 도에 약함. 병행 참조 |
| 레이어드 마케팅플랫폼 구조 | Client~배포 계층 | I/F Layer의 시스템 간 상세가 본 도 |
| BI포탈 시스템구조 분석 | BL BP/BC · APIM · Storage | **동일 패턴**(모듈↔프로토콜↔외부시스템) |

### 8.1 모듈 코드 매핑(초안·미확정)

| 본 장표 | 기존 연관관계도(참고) | 비고 |
|---|---|---|
| MC | CO 공통 | 확인 필요 |
| MN/MR/MU | IC/PC/BC 고객 | 통합·개인·기업 |
| MO | PD 통합상품 | |
| MS | SA 상담판매 | 코드 충돌 주의(기존 MS=미니싱글뷰) |
| MB | MS 미니싱글뷰 | **표기 충돌**: 본 장표 MB vs 기존 MS |
| MA | CM 캠페인 | |
| ME | 행동정보 | |
| MT/MM/ML/MV | CT/MG/SS/CS | |

> 특히 기존 문서의 **MS=미니싱글뷰**와 본 장표 **MS=상담판매**, **MB=미니싱글뷰**는 혼동 위험이 크다. 공식 코드표를 하나로 고정해야 한다.

- [ ] 본 축약도와 채널·Kafka·UMS·ETL 상세도의 관계가 명시되어 있는가?
- [ ] 캠페인(MA)–상호금융(GSE) 장애 시 고객 영향과 롤백 절차가 있는가?

## 11. 종합 평가

이 장표는 마케팅플랫폼을 **MP MC(다업무 모듈) + MP MB(미니싱글뷰)** 로 나누고, 외부와는 **Rest(CruzAPIM) · UI Link · GSE · Storage Rest** 로 연결하는 **시스템 간 연관관계 축약도**다. 표준 API 중계와 상호금융·화면·스토리지 특수 경로를 분리한 점이 강점이다.

다만 모듈 코드 체계가 기존 문서와 충돌할 수 있고, 채널·실시간(Kafka/EBM) 상세는 본 도에 없다. 운영 품질은 APIM 정책 분리, 코어뱅크 이중 경로(Rest/UI) 정합, GSE 신뢰성, 미니싱글뷰–Storage 감사, **코드표 단일화**에 달려 있다.
