# 논리기술아키텍처 — 데이터거버넌스 기술 컴포넌트 분석

## 0. 분석 범위와 판독 기준

- 요청 문구에는 `데이터플랫폼`이 있으나, 첨부 이미지의 제목과 상위 영역명은 모두 **데이터거버넌스**이다. 따라서 본 문서는 이미지에 근거해 데이터거버넌스 기술 컴포넌트를 분석한다.
- 이미지에 직접 표시된 내용을 **[사실]**, 구조상 합리적인 해석을 **[해석]**, 설계 확정이 필요한 내용을 **[확인 필요]**로 구분한다.
- 이미지 속 왼쪽 노드명은 `비즈메타/데이터품질 WAS`이다. 일부 기존 추출 문서의 `비정형/데이터품질` 표기는 이미지와 불일치하므로 채택하지 않는다.
- 제품 버전, 서버 수량, 네트워크 구간, DB 종류, 연계 대상과 데이터 보존기간은 이 이미지로 확정할 수 없다.

## 1. 핵심 결론

1. **[사실]** 데이터거버넌스 영역은 `비즈메타/데이터품질 WAS`와 `데이터 흐름 WAS`의 두 실행 노드로 분리된다.
2. **[사실]** 두 노드는 동일한 기술 스택과 동일한 8개 공통 운영 통제를 사용한다.
3. **[해석]** 동일 표준을 재사용하면서도 업무 책임과 장애 범위를 분리한 **표준화된 이원화 구조**이다.
4. **[해석]** 비즈메타/데이터품질 WAS는 용어·표준·메타데이터·품질 규칙과 결과를, 데이터 흐름 WAS는 계보(Lineage)·변환 경로·영향도를 담당한다.
5. **[해석]** 대량 메타데이터 수집, 품질 스캔, 계보 계산은 WAS 요청 스레드에서 장시간 실행하지 않고 `배치자동화 Agent`를 통한 비동기 작업으로 분리해야 한다.
6. **[확인 필요]** 거버넌스 저장소 DB와 원천 시스템 접속 위치는 이미지에 표시되지 않는다. `JDBC Driver`는 DB 연계 가능성을 나타낼 뿐 실제 접속 대상을 확정하지 않는다.

## 2. 전체 논리 구조

```text
┌────────────────────────────── 데이터거버넌스 ──────────────────────────────┐
│                                                                            │
│ ┌────── 비즈메타/데이터품질 WAS ──────┐  ┌──────── 데이터 흐름 WAS ────────┐ │
│ │ Business Service                    │  │ Business Service                 │ │
│ │ eCAMS Agent | 배치자동화 Agent      │  │ eCAMS Agent | 배치자동화 Agent   │ │
│ │ JDBC Driver | APM Agent             │  │ JDBC Driver | APM Agent          │ │
│ │ Java Framework Engine               │  │ Java Framework Engine            │ │
│ │ Web Application Server              │  │ Web Application Server           │ │
│ │ JVM                                 │  │ JVM                              │ │
│ ├─────────────────────────────────────┤  ├──────────────────────────────────┤ │
│ │ 백신·계정·보안·개인정보·백업        │  │ 백신·계정·보안·개인정보·백업     │ │
│ │ 통합관제·모니터링·운영관리          │  │ 통합관제·모니터링·운영관리       │ │
│ │ OS → VM → Cloud                     │  │ OS → VM → Cloud                  │ │
│ └─────────────────────────────────────┘  └──────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────────┘
```

두 노드는 물리적으로 동일한 템플릿을 사용하지만 논리적으로는 다음처럼 책임이 갈린다.

```text
정의·통제 축                                      가시성·분석 축
┌────────────────────────┐                     ┌────────────────────────┐
│ 비즈메타/데이터품질 WAS │ ── 메타 식별자 ──▶ │ 데이터 흐름 WAS         │
│ 용어·표준·품질규칙      │ ◀─ 계보·영향도 ─── │ 수집·연결·경로 분석     │
└────────────────────────┘                     └────────────────────────┘
            │                                             │
            └──────────── 일관된 거버넌스 관점 ───────────┘
```

## 3. 노드별 컴포넌트 명세

| 계층 | 비즈메타/데이터품질 WAS | 데이터 흐름 WAS | 역할 분석 |
|---|---|---|---|
| 업무 | Business Service | Business Service | 각 도메인의 API, 규칙, 오케스트레이션 구현 |
| 운영 에이전트 | eCAMS Agent | eCAMS Agent | 배포·구성·운영 제어 연계로 해석; 정확한 기능은 제품 명세 확인 필요 |
| 작업 에이전트 | 배치자동화 Agent | 배치자동화 Agent | 수집·스캔·계산 등 장시간 작업의 스케줄 실행 |
| 데이터 접속 | JDBC Driver | JDBC Driver | 저장소 또는 대상 DB와의 Java 표준 접속 |
| 관측 | APM Agent | APM Agent | 응답시간·호출·오류·자원 사용 추적 |
| 프레임워크 | Java Framework Engine | Java Framework Engine | 공통 트랜잭션·예외·로그·설정 기반 제공 |
| 미들웨어 | Web Application Server | Web Application Server | 요청 라우팅, 세션/스레드/커넥션 관리 |
| 런타임 | JVM | JVM | Java 실행, 메모리·GC·스레드 관리 |
| 시스템 공통 | 8개 통제 | 8개 통제 | 보안·운영·복구의 공통 기준 적용 |
| 기반 | OS → VM → Cloud | OS → VM → Cloud | 클라우드 위 VM, OS 위 애플리케이션 런타임 |

## 4. 공통 WAS 기술 스택

```text
요청/스케줄
    │
    ▼
┌──────────────────────────────┐
│ Business Service            │  업무 규칙·API·오케스트레이션
├───────────────┬──────────────┤
│ eCAMS Agent   │ 배치자동화   │  운영 제어 / 비동기 작업
├───────────────┼──────────────┤
│ JDBC Driver   │ APM Agent    │  데이터 접속 / 관측
├──────────────────────────────┤
│ Java Framework Engine       │  공통 애플리케이션 기반
├──────────────────────────────┤
│ Web Application Server      │  웹 컨테이너·자원 풀
├──────────────────────────────┤
│ JVM                          │  Java 런타임
├──────────────────────────────┤
│ OS                           │
│ VM                           │
│ Cloud                        │
└──────────────────────────────┘
```

### 4.1 Business Service

- **[사실]** 두 노드 최상단의 업무 컴포넌트이다.
- **[해석]** 화면/API 요청을 받아 메타 등록, 품질 규칙 실행, 계보 조회 같은 유스케이스를 수행한다.
- 트랜잭션 경계, 권한 검사, 감사 이벤트 생성의 시작점으로 삼는 것이 적절하다.
- 원천 스캔과 계보 계산처럼 오래 걸리는 작업은 작업 ID를 반환하고 비동기 실행해야 한다.

### 4.2 eCAMS Agent

- **[사실]** 두 WAS에 공통 배치된 에이전트이다.
- **[해석]** 배포, 설정, 상태 확인 등 중앙 운영관리의 실행 접점이다.
- **[확인 필요]** 구성 배포, 프로세스 제어, 패치, 인벤토리 중 실제 지원 범위를 제품 명세로 확정해야 한다.

### 4.3 배치자동화 Agent

- 메타데이터 수집, 품질 측정, 계보 재계산을 스케줄 또는 이벤트로 기동하는 실행 접점이다.
- 작업 중복을 막기 위해 `jobType + target + 기준시각`을 멱등 키로 사용할 수 있다.
- 재시도 횟수, 타임아웃, 부분 성공, 체크포인트, 재개 지점을 작업 메타데이터로 보존해야 한다.

```text
[Scheduler]
     │ jobId/parameters
     ▼
[배치자동화 Agent] ──▶ [Business Service Worker] ──▶ [JDBC/Adapter]
     │                         │                          │
     └──── 상태·종료코드 ◀─────┴──── 결과/체크포인트 ◀───┘
```

### 4.4 JDBC Driver

- Java 계층과 관계형 데이터 저장소 사이의 접속 표준이다.
- 커넥션 풀, 읽기 타임아웃, 쿼리 타임아웃, 최소 권한 계정, TLS를 적용해야 한다.
- 거버넌스 저장소와 원천 DB 계정을 분리하고, 원천 탐색 계정은 기본적으로 읽기 전용이어야 한다.
- **[확인 필요]** 이미지에는 실제 DB/스키마/접속 방향이 없다.

### 4.5 APM Agent

- 서비스/SQL 지연, 오류율, JVM 자원과 호출 추적을 수집하는 관측 계층이다.
- 메타데이터 값, SQL 바인드 값, 개인정보가 트레이스에 노출되지 않도록 마스킹해야 한다.
- 대량 배치 트레이스는 샘플링과 별도 서비스명으로 온라인 요청과 분리한다.

### 4.6 Java Framework Engine · WAS · JVM

```text
Business Service
       │ 공통 API/정책
       ▼
Java Framework Engine ── 예외·로그·트랜잭션·설정
       │
Web Application Server ─ HTTP·스레드·세션·DataSource
       │
JVM ──────────────────── Heap·GC·Thread·ClassLoader
```

- 프레임워크는 업무 코드가 공통 기술을 직접 재구현하지 않게 한다.
- WAS의 요청 스레드 풀과 배치 작업 풀을 분리하여 장시간 작업이 온라인 조회를 고갈시키지 않게 한다.
- JVM은 힙, GC 정지시간, 스레드 수, 클래스 로딩, OOM을 핵심 지표로 관리한다.

## 5. 비즈메타/데이터품질 WAS 상세

### 5.1 책임

- 비즈니스 용어, 표준 단어·도메인, 데이터 사전과 소유자 관리
- 물리 메타데이터와 비즈니스 정의의 매핑
- 데이터 품질 규칙의 등록·승인·배포·실행·결과 관리
- 품질 이슈, 예외 승인, 개선 조치와 이력 관리
- 메타데이터 검색·조회와 권한 기반 편집

### 5.2 비즈메타 수명주기

```text
[후보 등록] → [검토] → [승인] → [표준 발행] → [시스템 매핑] → [변경/폐기]
     │           │        │           │              │             │
  제안자      Steward   승인자      버전/시점       물리컬럼       영향도
```

핵심 계약은 `metaId`, `name`, `definition`, `owner`, `status`, `version`, `effectiveFrom/To`이다. 이름만으로 연결하지 않고 불변 식별자와 버전을 사용해야 한다.

### 5.3 데이터 품질 실행

```text
[품질 규칙]
 ruleId / target / expression / threshold
          │ 승인·배포
          ▼
[배치자동화 Agent] → [대상 데이터 판독] → [측정] → [품질 결과]
                                                    │
                             PASS ──────────────────┤
                             FAIL → [이슈/담당/조치] ┘
```

- 측정값에는 기준시각, 대상 스냅샷, 규칙 버전, 전체/오류 건수, 오류율을 함께 보존한다.
- 동일 규칙도 실행 시점과 데이터 스냅샷이 다르면 결과가 달라지므로 재현 정보를 필수화한다.
- 품질 오류 원문에는 개인정보가 포함될 수 있어 샘플값 암호화·마스킹·보존기간이 필요하다.

## 6. 데이터 흐름 WAS 상세

### 6.1 책임

- DB, ETL, 배치, 파일, API 등에서 기술 메타데이터 수집
- 소스→변환→타깃 관계를 정규화하여 계보 그래프로 구성
- 상향/하향 계보, 변경 영향도, 장애 파급 범위 조회
- 수집 실패·미연결 객체·고아 노드의 관리
- 비즈메타 식별자와 물리 객체의 연결

### 6.2 계보 수집 파이프라인

```text
[DB/ETL/Batch/File/API]
          │ connector별 원본
          ▼
[수집] → [파싱] → [정규화] → [객체 식별/병합] → [Edge 생성] → [계보 저장]
   │         │         │              │                │
 수집시각   SQL/Job   공통 모델       중복·이름변경     source→target
```

### 6.3 영향도 분석

```text
변경 후보: CUSTOMER.GRADE 컬럼
                 │
                 ▼
       [하향 계보 탐색 / cycle 방지]
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
     ETL Job   ADW Mart   BI Dataset
                              │
                              ▼
                         Report/User
```

- 영향도 결과에는 탐색 방향, 깊이, 경로, 객체 유형, 마지막 수집시각을 표시해야 한다.
- 계보의 최신성이 낮으면 영향도 판단도 부정확하므로 `lastCollectedAt`과 수집 성공률을 함께 노출한다.

## 7. 두 업무 영역의 협력 메커니즘

```text
비즈메타/품질                                      데이터 흐름
┌─────────────────────┐                        ┌─────────────────────┐
│ metaId, 표준, 소유자 │ ── 객체 매핑 정보 ───▶ │ physicalObjectId    │
│ 품질 규칙·결과       │ ◀─ 영향 경로/최신성 ── │ lineage edge        │
└─────────────────────┘                        └─────────────────────┘
             │                                          │
             └────── 공통 식별자·버전·감사시각 ─────────┘
```

결합 원칙은 다음과 같다.

- 상호 DB 테이블을 직접 수정하기보다 버전이 있는 API/이벤트 계약을 사용한다.
- 메타 식별자, 물리 객체 식별자, 시스템 식별자 사이의 매핑을 명시적으로 관리한다.
- 상대 노드 장애 시 조회 가능한 마지막 성공 스냅샷을 유지하고, 갱신은 재처리 큐로 넘긴다.
- 순환 호출을 피하고 계보 계산 결과는 이벤트 또는 작업 완료 상태로 전달한다.

## 8. 온라인과 배치 실행 분리

```text
온라인 경로                              배치 경로
[UI/API] → [WAS] → 조회/등록 → 즉시 응답   [Scheduler] → [Agent] → 대량 수집/계산
                    │                                         │
                    └──── jobId 발행 ─────────────────────────▶│
                    ◀──── 상태/결과 조회 ──────────────────────┘
```

- 온라인은 짧은 조회·등록·작업접수에 집중한다.
- 배치는 대량 스캔, 품질 측정, 계보 재구축과 재처리를 담당한다.
- 큐 깊이, 실행 대기시간, 처리량, 실패/재시도, 마지막 성공시각을 별도 지표로 관리한다.

## 9. 공통 시스템 영역 분석

| 컴포넌트 | 통제 목적 | 데이터거버넌스 관점의 주의점 |
|---|---|---|
| 서버 백신 | 악성코드 차단 | 대량 스캔 경로·임시파일과 충돌하지 않도록 예외를 최소 범위로 승인 |
| 계정 관리 | 계정 수명주기·권한 통제 | 서비스/배치/수집 계정 분리, 개인계정 공유 금지 |
| 서버 보안 | 취약점·접근 통제 | 관리 포트 제한, 패치 기준과 예외 이력 관리 |
| 개인정보 | 민감정보 보호 | 메타 샘플, 품질 오류값, APM·로그의 값 마스킹 |
| 백업 관리 | 복구 가능성 | 설정·규칙·메타·계보 저장소의 RPO/RTO와 복구훈련 |
| 인프라 통합관제 | 중앙 이벤트 수집 | 두 노드 및 하부 자원의 장애 상관분석 |
| 서버 모니터링 | 자원·프로세스 관측 | CPU·메모리·디스크·JVM·WAS·배치 지표 연결 |
| 서버운영관리 | 변경·장애·구성 관리 | 동일 템플릿과 노드별 설정 차이를 형상화 |

```text
                    [인프라 통합관제]
                       ▲    ▲
      알람/상태 ┌──────┘    └──────┐ 알람/상태
               │                   │
[비즈메타/품질 WAS]             [데이터 흐름 WAS]
   ▲ APM/JVM/Job                   ▲ APM/JVM/Job
   └──── [서버 모니터링·운영관리] ─┘
```

## 11. 장애·재처리 메커니즘

```text
[작업 시작]
    │
    ▼
[Checkpoint N] ── 성공 ──▶ [Checkpoint N+1] ──▶ [완료/대사]
    │ 실패                        │ 실패
    ▼                             ▼
[오류 분류] → 재시도 가능? ─Yes→ [Backoff 재시도]
                 │ No
                 ▼
           [격리 큐/수동 조치]
```

- 기술 오류와 데이터 오류를 분리한다. 연결 단절은 재시도할 수 있지만 문법 불명 SQL은 격리·수동 보정 대상이다.
- 재실행이 중복 객체나 중복 계보를 만들지 않도록 upsert와 멱등 키를 적용한다.
- 부분 성공 시 성공 범위와 실패 범위를 식별해 전체 재처리 대신 선택 재개가 가능해야 한다.
- 외부 원천 장애가 데이터거버넌스 WAS 전체 장애로 전파되지 않게 타임아웃·회로차단·동시성 제한을 둔다.

## 12. 보안과 개인정보

```text
[사용자/운영자] → [SSO·역할] → [Business Service] → [권한 검사]
                                              │
                         ┌────────────────────┼───────────────────┐
                         ▼                    ▼                   ▼
                    메타 조회             규칙 변경            원천 수집
                    최소 권한          승인·감사 필수        읽기전용 계정
```

- Steward, 품질관리자, 계보관리자, 운영자, 조회자의 역할을 분리한다.
- 표준·규칙·매핑 변경은 변경 전후 값, 승인자, 시각, 사유를 감사 로그로 남긴다.
- 비밀번호와 토큰은 설정 파일에 평문 보관하지 않고 비밀관리 체계에서 주입한다.
- 원천 데이터 샘플은 최소 수집하고 민감도에 따라 마스킹·암호화·접근통제를 적용한다.

## 13. 가용성·성능·격리

- 두 노드의 독립 배포 단위와 자원 한도를 유지해 품질 스캔이 계보 조회를 방해하지 않게 한다.
- 조회 API와 배치 Worker의 스레드·커넥션 풀을 분리한다.
- 계보 그래프 탐색은 깊이·결과 수·시간 제한과 캐시를 둔다.
- 대량 품질 결과는 페이지 처리하고 원문 샘플과 집계 결과의 저장 정책을 분리한다.
- WAS 다중화 여부, 배치 Active/Standby, 저장소 HA, RTO/RPO는 별도 물리 설계에서 확정한다.

## 14. 배포와 변경관리

```text
[소스/설정] → [Build] → [보안·계약 검사] → [배포 승인]
                                           │
                     ┌─────────────────────┴────────────────────┐
                     ▼                                          ▼
             비즈메타/품질 WAS                           데이터 흐름 WAS
                     │                                          │
                     └──────── 버전·상태·롤백 검증 ─────────────┘
```

- 동일 기반 스택은 공통 이미지/템플릿으로 관리하되 Business Service와 설정은 노드별로 독립 버전 관리한다.
- DB 스키마 변경은 전·후방 호환, 롤백, 데이터 이행, 계보·품질 규칙 영향도를 함께 검토한다.
- eCAMS Agent와 배치자동화 Agent 자체의 버전 호환성도 배포 기준에 포함한다.

## 15. 관측성과 운영 지표

| 영역 | 핵심 지표 |


## 17. 이미지 사실 / 해석 / 확인 필요사항

### 이미지에서 직접 확인되는 사실

- 상위 영역은 `데이터거버넌스`이다.
- 노드는 `비즈메타/데이터품질 WAS`, `데이터 흐름 WAS` 두 개이다.
- 두 노드의 애플리케이션·런타임·공통 운영 컴포넌트가 동일하다.
- 두 노드 모두 VM 기반이며 하부 순서는 `OS → VM → Cloud`로 표현된다.

### 아키텍처 해석

- 두 노드는 서로 다른 거버넌스 책임을 독립 배포·운영하기 위한 분리 구조이다.
- `배치자동화 Agent`는 대량·주기 작업, APM/eCAMS는 관측·운영 제어에 사용된다.
- JDBC는 거버넌스 저장소 또는 수집 대상 DB 연결에 사용될 가능성이 높다.

### 반드시 별도 문서로 확정할 사항

- 거버넌스 DB, 원천 시스템, UI, 인증, API Gateway의 실제 배치와 연결 방향
- WAS/VM 수량, 이중화, 네트워크 Zone, 방화벽, 포트, 인증서
- eCAMS·APM·배치자동화 제품명, 기능 범위, 버전과 호환성
- 메타·품질·계보 스키마, API/이벤트 계약과 데이터 소유권
- 수집 주기, SLA, RTO/RPO, 백업 주기, 보존·파기 정책
- 개인정보 등급, 마스킹 범위, 감사로그 보존기간

## 18. 종합 평가

이 도면은 데이터거버넌스를 하나의 거대한 애플리케이션으로 만들지 않고, **비즈메타·품질 통제**와 **데이터 흐름·영향도 가시성**을 두 WAS로 분리하면서 동일한 Java/WAS/운영 표준을 적용한 구조다. 장점은 기술 표준 재사용, 책임과 장애 범위 분리, 독립 확장이다. 성공 조건은 두 노드 사이의 불변 식별자·버전 계약, 장시간 작업의 비동기화, 원천 읽기 최소권한, 개인정보 마스킹, 멱등 재처리, 계보 최신성 관리이다.
