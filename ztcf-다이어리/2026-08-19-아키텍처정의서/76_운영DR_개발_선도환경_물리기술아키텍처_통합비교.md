# 3. 서버 구성 원칙 추출

환경별 장표를 종합하면 다음 물리 배치 원칙을 추출할 수 있다.

1. **운영은 다중 노드/이중 센터**, 개발·선도는 단일 센터 중심이다.
2. **운영 마케팅/BI WEB-WAS는 다중화**, 개발/선도는 단일 노드로 축소한다.
3. **미니싱글뷰는 운영에서는 물리 분리, 개발/선도에서는 마케팅 WEB/WAS에 통합**된다.
4. **운영 DB는 ADW/RDW 분리**, 개발은 통합 Appliance, 선도는 CRM DB를 사용한다.
5. **DR은 전체 운영환경의 1:1 복제가 아니다.** 일부 핵심 서비스와 RDW DB Standby만 명시되어 있다.
6. **RDW DR은 Data Guard**, 센터 연결은 DCI, 서비스 전환 계층에는 GSLB가 표시된다.
7. 데이터 이행 자원은 환경 목적에 따라 임시/전용으로 구성한다.

# 4. 환경 승격 관점

```text
선도
  │  핵심 마케팅/배포체계 선행검증
  ▼
개발
  │  전체 기능 개발 + BI/거버넌스 + 데이터이행
  ▼
운영
  │  다중노드/고가용성/전용 DB Appliance
  ▼
DR
     핵심 서비스 및 DB 재해복구
```

# 5. 아키텍처 검증 포인트

| 검증 영역 | 핵심 질문 |
|---|---|
| WEB/WAS | 운영 노드수와 실제 L4/Apache/Tomcat 배치가 일치하는가 |
| JVM | 컨테이너/인스턴스당 JVM 기준이 서버 인벤토리와 일치하는가 |
| 미니싱글뷰 | 개발/선도 통합 방식과 운영 분리 방식의 설정차이는 무엇인가 |
| DR | BI/거버넌스/실시간 AP의 복구전략이 별도 존재하는가 |
| DB | ADW DR 미표시가 의도인지 누락인지 |
| Data Guard | RDW RPO/RTO 및 Sync/Async 정책 |
| DCI/GSLB | 센터 전환 및 네트워크 장애 시 동작 |
| 이행 | 임시 AP/DB의 Lifecycle과 폐기시점 |
| Hostname | 장표와 최종 서버 인벤토리의 이름/번호 정합성 |

# 6. 결론

물리 아키텍처는 **선도 → 개발 → 운영 → DR**로 갈수록 목적이 달라진다.

- **선도:** 핵심 서비스와 배포/운영 도구를 빠르게 검증
- **개발:** 전체 업무 기능 및 데이터 연계를 단일/축소 구성으로 개발
- **운영:** 다중화·전용 DB·대규모 노드로 서비스 제공
- **DR:** 필수 서비스와 RDW DB를 중심으로 재해복구 제공

따라서 네 환경은 동일한 장비 복제 구조가 아니라, **업무 목적과 가용성 수준에 따라 물리 구성을 차등화한 아키텍처**로 이해하는 것이 적절하다.
