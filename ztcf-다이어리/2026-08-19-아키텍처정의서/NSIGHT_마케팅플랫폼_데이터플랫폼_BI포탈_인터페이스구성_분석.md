# NSIGHT 인터페이스 구성도 상세 분석
## 마케팅플랫폼 · 데이터플랫폼 · BI포탈

## 0. 문서 개요

본 문서는 제공된 **인터페이스 아키텍처 구성도 장표 3장(페이지 108~110)**을 기준으로,
다음 세 영역의 인터페이스 구조를 통합 분석한 문서이다.

1. **마케팅플랫폼 인터페이스 구성도**
2. **데이터플랫폼 인터페이스 구성도**
3. **BI포탈 인터페이스 구성도**

> 원본 장표 우측 상단에는 `업무팀 분석 단계 구체화`가 표시되어 있으며,
> 일부 항목은 `확인 필요` 대상으로 관리되는 단계임을 전제로 한다.

### 작성 원칙

- 장표에서 직접 확인되는 명칭과 코드, 연결관계를 우선 보존한다.
- 화살표 방향이 명확하지 않은 경우 양방향/단방향을 임의 확정하지 않는다.
- 원본 코드와 기존 문서의 코드체계가 충돌할 가능성이 있어도 이 문서에서는 **원본 장표 표기 그대로** 기록한다.
- 추가 확인이 필요한 부분은 `GAP`으로 분리한다.

# 4. 마케팅플랫폼 좌측 인터페이스

장표의 좌측 연계는 다음과 같이 구성되어 있다.

## 4.1 통합업무시스템 / 영업점 MCA

```text
통합업무시스템
      │
      ▼
  영업점 MCA
      │
      ▼
마케팅플랫폼 MP
```

장표상 통합업무시스템과 영업점 MCA 사이,
그리고 영업점 MCA와 마케팅플랫폼 사이에 연계선이 표현되어 있다.

### 의미

- 대면 채널의 표준 연계
- 영업점 업무 → 마케팅플랫폼 업무 호출
- 인터페이스 표준 문서의 `영업점 MCA` 연계 원칙과 일치

---

## 4.2 정보단말

```text
정보단말
   │
   └────────────── 마케팅플랫폼 MP
```

장표에서는 정보단말과 마케팅플랫폼 사이에 직접 연계선이 표현되어 있다.

### [ANALYSIS]

앞서 온라인 인터페이스 표준에서 정의된
`정보계 단말 → 정보계 직접거래` 유형과 연결되는 구조로 볼 수 있다.

---

## 4.3 인터넷뱅킹 / 스마트뱅킹 → Kafka

```text
인터넷뱅킹
스마트뱅킹
     │
     ▼
   Kafka
     │
     ▼
마케팅플랫폼 MP
```

### 의미

- 고객 이벤트/행동 이벤트를 Kafka로 수집
- 동기 API 호출과 이벤트 스트리밍을 분리
- 마케팅플랫폼의 실시간 이벤트 기반 처리와 연결

---

## 4.4 SMS / EMAIL / PUSH → UMS

```text
SMS
EMAIL
PUSH
  ▲
  │
 UMS
  │
  ▼
마케팅플랫폼 MP
```

장표상 UMS와 마케팅플랫폼이 연결되며,
UMS는 SMS/EMAIL/PUSH 메시징 채널과 연계된다.

---

## 4.5 보고서

```text
보고서
  │
  └────────────── 마케팅플랫폼 MP
```

장표에는 보고서 영역과 마케팅플랫폼 간 직접 연계가 표현되어 있다.

세부 솔루션/프로토콜은 본 장표에서 확인되지 않는다.

# 5. 마케팅플랫폼 우측 인터페이스

## 5.1 코어뱅킹 연계

```text
마케팅플랫폼
     │
     ▼
 API G/W
     │
     ▼
    EAI
     │
     ▼
 코어뱅킹
```

장표에는 `API G/W + EAI` 조합을 통해 코어뱅킹과 연계하는 구조가 표시된다.

### [ANALYSIS]

이는 앞선 인터페이스 표준에서 제시된:

```text
정보계
→ API Gateway
→ EAI
→ 대내 시스템
```

구조를 마케팅플랫폼 관점으로 구체화한 것이다.

# 6. 알림 서비스 연계

장표 우측에는 `아리톡(알림 서비스)`가 두 곳에 표현되어 있으며,
API Gateway를 통해 마케팅플랫폼과 연결된다.

```text
마케팅플랫폼
     │
     ▼
 API G/W
     │
     ▼
아리톡
(알림 서비스)
```

### 확인 필요

- 동일 `아리톡(알림 서비스)`가 기능별로 두 번 표시된 것인지
- 서로 다른 Endpoint/업무인지
- 단순 도식 중복인지

원본만으로는 확정하기 어렵다.

# 8. RDW / ADW 데이터 연계

장표 우측에는 마케팅플랫폼과 데이터플랫폼 간 다음 연계가 표현된다.

## 8.1 ETL → RDW

```text
마케팅플랫폼
    │
    ▼
   ETL
    │
    ▼
   RDW
```

## 8.2 ETL → ADW

```text
마케팅플랫폼
    │
    ▼
   ETL
    │
    ▼
   ADW
```

### [ANALYSIS]

마케팅플랫폼 업무 데이터 또는 산출 데이터가
배치성 데이터 동기화 방식으로 RDW/ADW와 연계되는 구조가 존재한다.

세부 Source/Target Schema와 적재주기는 본 장표에서 확인되지 않는다.

# 13. RDW 업무구성

| No | 업무/데이터 영역 | 코드 |
|---:|---|:---:|
| 1 | 공통 | `CO` |
| 2 | 실시간SoR | `SR` |
| 3 | 준실시간요약집계 | `ZD` |

```text
├─ 실시간SoR SR

├─ 준실시간보고서마트 RM
└─ 피드백 FA
```

# 14. RDW 역할 해석

### [ANALYSIS]

RDW 내부 구조는 실시간 및 준실시간 중심으로 계층화되어 있다.

```text
실시간 Source
    │
    ▼
실시간SoR (SR)
    │
    ▼
준실시간요약집계 (ZD)
    │
    ▼
준실시간보고서마트 (RM)
    │
    ▼
피드백 (FA)
```

`공통(CO)`은 위 데이터 영역에서 공통적으로 사용되는 데이터/기능 영역으로 볼 수 있다.

# 15. ADW 업무구성

원본 장표의 `데이터플랫폼 ADW` 영역에는 다음 코드가 표시된다.

| No | 업무/데이터 영역 | 코드 |
|---:|---|:---:|
| 1 | 공통 | `CO` |
| 2 | 분석SoR | `SR` |
| 3 | 분석통합요약집계 | `ZD` |
| 4 | 분석단위업무마트 | `UM` |
| 5 | 분석보고서마트 | `RM` |
| 6 | 피드백 | `FA` |
| 7 | 분석지원 | `DA` |

텍스트 구조:

```text
데이터플랫폼 ADW (AD)
│
├─ 공통 CO
├─ 분석SoR SR
├─ 분석통합요약집계 ZD
├─ 분석단위업무마트 UM
├─ 분석보고서마트 RM
├─ 피드백 FA
└─ 분석지원 DA
```

---

# 16. ADW 역할 해석

```text
분석SoR (SR)
   │
   ▼
분석통합요약집계 (ZD)
   │
   ├──────────────┐
   ▼              ▼
분석단위업무마트  분석보고서마트
    (UM)              (RM)
   │                   │
   └──────────┬────────┘
              ▼
         분석지원 (DA)

피드백 (FA)
→ 별도 Feedback 데이터 영역
```

### [ANALYSIS]

ADW는 분석/집계/마트/분석지원 중심의 계층형 Analytical Data Platform 구조를 가진다.

---

# 17. RDW vs ADW 코드 비교

| 코드 | RDW 의미 | ADW 의미 |
|:---:|---|---|
| `CO` | 공통 | 공통 |
| `SR` | 실시간SoR | 분석SoR |
| `ZD` | 준실시간요약집계 | 분석통합요약집계 |
| `RM` | 준실시간보고서마트 | 분석보고서마트 |
| `FA` | 피드백 | 피드백 |
| `UM` | - | 분석단위업무마트 |
| `DA` | - | 분석지원 |

### 핵심

동일 코드가 RDW와 ADW에서 일부 공통 사용되지만,
업무 의미는 실시간/분석 특성에 따라 달라진다.

본 장표에서는 외부 시스템/DB와의 연결선을 상세하게 표시하지 않고,
BI포탈 내부의 업무 도메인 분류와 코드만 명확히 제시한다.

따라서 이는 상세 인터페이스 Flow보다
**BI Portal Application Domain Boundary 정의** 성격이 강하다.

# 28. 기존 DB/인터페이스 아키텍처와의 정합성

| ADW = 분석 | `ADW AD` 내부에 분석SoR/분석집계/분석마트 |

| EAI 연계 | 코어뱅킹/태블릿 브랜치 |

| 배치 데이터 = ETL | RDW/ADW ETL |
| 파일 = FOS | UMS 연계 FOS |
| DB 접근 = JDBC | 마케팅플랫폼 → RDW |
| 대면채널 = 영업점 MCA | 통합업무시스템 ↔ 영업점 MCA ↔ MP |

# 33. 최종 분석 결론

제공된 3개 장표에서 확인되는 핵심은 다음과 같다.

1. **마케팅플랫폼은 `MP` 시스템 코드로 정의**되고 13개의 세부 업무코드가 표현된다.
2. 마케팅플랫폼은 채널, 정보단말, Kafka, UMS, 보고서, 코어뱅킹, 알림서비스, 태블릿 브랜치, RDW, ADW와 연계된다.
3. 대내 코어 연계는 **API G/W + EAI**, 이벤트 연계는 **Kafka**, 메시징은 **UMS**, 데이터 연계는 **ETL**, 파일 연계는 **FOS**, DB 직접접근은 **JDBC**로 표현된다.
4. 데이터플랫폼은 **RDW(RD)** 와 **ADW(AD)** 로 구분된다.
5. RDW는 `CO / SR / ZD / RM / FA`의 실시간·준실시간 계층을 가진다.
6. ADW는 `CO / SR / ZD / UM / RM / FA / DA`의 분석 계층을 가진다.
7. BI포탈은 **BL** 코드 하위에 `PT / CR / OA / SB`로 업무를 구분한다.
8. 세 장표 모두 상세 인터페이스 스펙보다 **시스템/업무 Domain Boundary와 인터페이스 대상 식별**에 초점을 둔다.
9. 장표에 `업무팀 분석 단계 구체화`가 명시되어 있으므로 현재 내용은 최종 Interface Detail Design 이전의 Working Baseline이다.
10. 특히 `MG=메시지`, `SS=영업지원`, `BL`, `RD/AD` 및 하위 데이터 코드가 기존 Application 코드체계와 충돌하지 않는지 별도 정합성 점검이 필요하다.
11. 최종 설계에서는 각 연결선을 `Interface ID / Source / Mechanism / Target / Direction / Protocol / Data / Security / Timeout / Retry / Monitoring` 수준으로 상세화해야 한다.

본 문서는 제공된 페이지 108~110 장표를 기준으로 한
**NSIGHT Domain-Level Interface Configuration Working Baseline**으로 활용한다.
