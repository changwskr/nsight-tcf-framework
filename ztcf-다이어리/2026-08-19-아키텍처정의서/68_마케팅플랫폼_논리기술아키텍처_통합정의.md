# 마케팅플랫폼 논리 기술 아키텍처 통합 정의
## 이미지 기반 TEXT 아키텍처 · 전체 컴포넌트 표 · 연계 흐름 통합

> 원본 위치: `2. 논리 기술 아키텍처 > 2.4 논리 기술 아키텍처 정의`  
> 원본 페이지: `65`  
> 기준 이미지: `19(1).png`  
> 목적: 마케팅플랫폼 논리 기술 아키텍처를 **텍스트 구조도로 재구성**하고, 이미지에 나타난 채널·애플리케이션·데이터·실시간·배치·운영·대내외 연계 컴포넌트를 하나의 표 체계로 통합한다.  
> 작성 원칙: 이미지에 표시된 명칭과 연결을 우선한다. 선의 방향 또는 소유관계가 이미지에서 명확하지 않은 경우에는 확정적인 호출 방향을 임의로 만들지 않고 `연계`로 표현한다.

---

# 1. 전체 아키텍처 요약

마케팅플랫폼 논리 기술 아키텍처는 크게 다음 영역으로 구성된다.

1. **업무/정보계 채널**
2. **웹 접근 및 마케팅플랫폼 서비스**
3. **마케팅 업무 애플리케이션**
4. **개발·배포·프레임워크 관리**
5. **배치 및 ETL**
6. **RDW/ADW 데이터플랫폼**
7. **고객행동 실시간 수집·처리**
8. **이벤트/메시지 처리**
9. **대내 시스템 연계**
10. **대외 시스템 연계**
11. **계정계/BCV/경영정보 연계**
12. **보고서(RD)**

# 4. 마케팅플랫폼 내부 애플리케이션

이미지에서 마케팅플랫폼 내부의 업무 애플리케이션은 다음 **13개 영역**으로 식별된다.

| No | 애플리케이션 | 역할 분류 |
|---:|---|---|
| 1 | 미니 싱글뷰 | 고객 Single View |
| 2 | 공통 | 공통업무 |
| 3 | 통합고객 | 통합 고객정보 |
| 4 | 개인고객 | 개인 고객업무 |
| 5 | 기업고객 | 기업 고객업무 |
| 6 | 상담판매 | 상담/판매 |
| 7 | 통합상품 | 상품 통합 |
| 8 | 캠페인 | 캠페인 |
| 9 | EBM | Event Based Marketing |
| 10 | 영업지원 | 영업 지원 |
| 11 | CS | Customer Service |
| 12 | 컨텐츠 | 콘텐츠 |
| 13 | 메시지 | 메시지 |

### 내부 실행 구조

```text
13개 업무 Application
        ↓
Application Framework
        ↓
WAS
        ↓
VM
        ↓
IaaS
```

```text
                  [Wise Collector]
                        │
                   publish × N
                        │
                        ▼
             [KAFKA 고객행동 데이터]
                        │
                  subscribe × N
                        │
                        ▼
               [행동정보 처리서버]
                    │         │
                    │         ├─ 이벤트 등록
                    │         └─ Topic 목록
                    │
                    └─ JDBC ─────────► RDW
```

### 구조적 의미

| 단계 | 역할 |
|---|---|
| Capture | WEB/Mobile에서 고객 행동 생성 |
| Collect Proxy | Wise Collector Proxy가 수집 진입점 |
| Collect | Wise Collector가 행동 데이터를 수집 |
| Publish | Kafka에 고객 행동 이벤트 발행 |
| Subscribe | 행동정보 처리서버가 Topic 구독 |
| Process | 행동정보 처리/이벤트 판정 |
| Persist | RDW와 JDBC 연계 |
| Notify | 이벤트 발생 시 UMS 연계 가능 |

# 15. 핵심 아키텍처 특성

## 15.1 서비스와 데이터플랫폼 분리

마케팅 업무는 WAS 기반 서비스로 구성되고, 데이터 저장/분석은 RDW와 ADW로 분리되어 있다.

```text
Marketing Application
       ↓ JDBC
      RDW
       ↓ ETL
      ADW
```

## 15.2 실시간 고객행동 처리는 Kafka Pub/Sub 기반

```text
Channel
 → Wise Collector
 → publish
 → Kafka
 → subscribe
 → 행동정보 처리서버
```

온라인 거래처리와 고객행동 이벤트 처리가 논리적으로 분리되어 있다.

## 15.3 실시간/배치 데이터 처리가 함께 존재

- Online/WAS → JDBC → RDW
- Batch AP → JDBC → RDW
- ETL → RDW/ADW
- Real-time Server → polling/JDBC → RDW
- Kafka → Behavior Processing → JDBC → RDW

즉 RDW가 실시간·온라인·배치·행동 데이터의 중심 데이터 허브 역할을 한다.

## 15.4 통합 연계 수단을 목적별로 분리

- `Cruz APIM`: API
- `EAI`: 내부 애플리케이션 연계
- `FOS`: 파일/시스템 연계
- `MFT`: 관리형 파일 전송
- `MCA`: 대내/대외 온라인 거래
- `CDC`: 변경 데이터
- `JDBC`: DB 직접 연계
- `Kafka`: 실시간 이벤트
- `ETL`: 데이터 변환/적재

# 16. 최종 통합 아키텍처 정의

마케팅플랫폼 논리 기술 아키텍처는 다음과 같이 정의할 수 있다.

```text
채널
  ↓
MCA / JSON / L4 / WEB
  ↓
마케팅 13개 업무 Application
  ↓
Application Framework
  ↓
WAS / VM / IaaS
  ↓
────────────────────────────────────────────
│ 데이터         │ 실시간       │ 배치       │
│ RDW → ADW      │ Kafka        │ Batch AP   │
│ JDBC / ETL     │ Event        │ Control-M  │
│ CDC            │ UMS          │ ETL        │
────────────────────────────────────────────
  ↓
대내 APIM/EAI/FOS/MFT
대외 FOS/MCA/MFT
계정계 / BCV / 경영정보
```

이 구조의 중심축은 다음 네 가지다.

1. **WAS 기반 마케팅 업무 서비스**
2. **RDW 중심 실시간 데이터 허브**
3. **Kafka 기반 고객행동 이벤트 처리**
4. **APIM/EAI/MCA/FOS/MFT/CDC/ETL을 통한 다중 통합 체계**
