# NSIGHT 인터페이스 아키텍처 표준 정의 분석
## 온라인 · 데이터 · 파일 인터페이스 통합 기준

## 0. 문서 개요

본 문서는 사용자가 제공한 **인터페이스 아키텍처 장표 5장**을 기준으로
차세대 정보계의 **온라인 인터페이스, 데이터 인터페이스, 파일 인터페이스 표준과 시스템 간 연계 원칙**을 통합 분석한 문서이다.

대상 장표:

- 정보계 인터페이스 표준 정의
- 온라인 인터페이스 표준 정의
- 파일 인터페이스 표준 정의
- 데이터 인터페이스 표준 정의

> 본 문서는 장표에 표현된 내용을 우선적으로 보존한다.  
> 장표에 없는 상세 구현방식·포트·전문 규격·Timeout·보안정책 등은 임의로 확정하지 않는다.

# 1. 전체 인터페이스 아키텍처 핵심 메시지

원본 장표의 최상위 목적은 다음과 같다.

> **시스템 간 자원 결합을 최소화함으로써 플랫폼 독립성을 유지할 수 있도록  
> 차세대 정보계의 온라인, 데이터, 파일 연계를 수행할 인터페이스 원칙을 수립함**

이를 구조화하면 다음과 같다.

```text
                         차세대 정보계 인터페이스

                  시스템 간 자원 결합 최소화
                           │
                           ▼
                      플랫폼 독립성
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
       온라인            데이터            파일
          │                │                │
          ▼                ▼                ▼
 JSON/HTTP + API G/W     CDC / ETL          FOS
 Kafka Streaming
```

# 2. 차세대 정보계 시스템 구축 기준

원본 장표는 다음 문구를 시스템 구축 기준으로 제시한다.

> **“도메인 특성을 고려한 서비스 플랫폼 독립 정의”**

구체적인 기준은 다음과 같다.

| 구분 | 원본 정의 |
|---|---|
| 온라인 AP / 배치 AP 자원 분리 | 온라인 실시간 거래와 배치 처리 자원 충돌 방지 |
| ETL 서버 독립 서버 구성 | DataStage 기반 대량 배치 데이터 가공/정제 전용 공간으로 대량 배치 공간 마련 |
| 이벤트 서버 분리 | Kafka 이벤트 스트리밍 전용 고속 실시간 고객 오퍼링 |
| CDC 중계서버 제공 | 계정계 원천 DB의 변경사항 실시간 캡처, 원천 DB 부하 분산 |
| ADW | 전략 분석 전용 대용량 데이터 관리 |
| RDW | 실시간 OLTP 운영 관리로 CDC로 수집된 데이터 관리 |

# 3. 인터페이스 3대 분류

장표는 인터페이스를 다음 3개 유형으로 분리한다.

```text
Interface
│
├─ Online Interface
│
├─ Data Interface
│
└─ File Interface
```

각 유형의 기본 처리수단은 다음과 같다.

| 인터페이스 유형 | 표준 처리수단 |
|---|---|
| 온라인 | JSON/HTTP, API Gateway, Kafka |
| 데이터 | CDC, ETL |
| 파일 | FOS |

# 4. 온라인 인터페이스 원칙

원본의 온라인 인터페이스 원칙은 다음과 같다.

## 4.1 프로토콜 표준화

> **정보계 어플리케이션 시스템은 json/http 방식으로 프로토콜 일원화**

즉 온라인 업무 Application 간 기본 연계방식은 다음과 같이 표현된다.

```text
Application
    │
    │ JSON / HTTP
    ▼
Application / System
```

---

## 4.2 GUID 기반 전문 적용

> **GUID 기반 전문 적용으로 거래 모니터링**

원본 장표에서 GUID는 온라인 거래 모니터링의 표준 식별수단으로 정의된다.

```text
Request
  │
  ├─ GUID
  │
  ▼
거래 추적 / 모니터링
```

> GUID 필드 구조, 생성주체, 전달구간, 저장위치는 본 장표에서 상세 정의하지 않는다.

---

## 4.3 이벤트 데이터 Streaming

> **이벤트 데이터 Streaming은 Kafka로 처리**

```text
Event Producer
      │
      ▼
    Kafka
      │
      ▼
Event Consumer
```

원본 구축 기준에서도 Kafka는 **이벤트 스트리밍 전용 고속 실시간 고객 오퍼링**을 위한 독립 이벤트 서버로 설명된다.

---

## 4.4 시스템 간 온라인 연계

> **시스템 간 연계는 API Gateway (Cruz APIM)로 일원화**

```text
정보계
   │
   ▼
API Gateway
(Cruz APIM)
   │
   ▼
대내/대외 시스템
```

추가 원칙:

> **API Gateway와 EAI 간 연계는 인터페이스 솔루션 내부에서 처리**

---

# 5. 데이터 인터페이스 원칙

|---|---|
| 실시간 데이터 동기화 | CDC |

```text
      │
      ▼
     ETL
```

# 33. 결론

제공된 인터페이스 장표에서 확인되는 핵심은 다음과 같다.

1. 차세대 정보계는 **시스템 간 자원 결합을 최소화하고 플랫폼 독립성을 유지하는 것**을 인터페이스의 최상위 목표로 한다.
2. 인터페이스는 **온라인 / 데이터 / 파일**의 3개 유형으로 구분한다.
3. 온라인 Application 프로토콜은 **JSON/HTTP 방식으로 일원화**한다.
4. 온라인 거래 추적에는 **GUID 기반 전문**을 적용한다.
5. 이벤트 데이터 Streaming은 **Kafka**로 처리한다.
6. 시스템 간 표준 온라인 연계는 **API Gateway(CruzAPIM)** 로 일원화한다.
7. 대면채널은 **영업점 MCA**, 비대면채널은 **MCI**를 경유한다.
8. 타 법인 연계는 **GSE**를 사용한다.
9. 일부 정보계 단말과 패키지 UI는 인터페이스 시스템을 거치지 않는 직접거래 유형으로 정의된다.
10. 실시간 데이터 동기화는 **CDC**, 배치 데이터 동기화는 **ETL**로 구분한다.
11. **RDW → ADW 데이터 동기화는 ETL 방식**으로 명확히 표시되어 있다.
12. 파일 인터페이스는 **FOS로 일원화**한다.
13. FOS와 MFT, API Gateway와 EAI 간 연계는 각 인터페이스 솔루션 내부 연동기능을 활용한다.
14. Online AP, Batch AP, ETL Server, Event Server, CDC Relay Server를 기능별로 분리하여 자원충돌을 최소화한다.
15. 원본 장표에는 상세 전문 Schema, Timeout, Retry, 보안, 포트, 장애복구 기준이 포함되어 있지 않으므로 이후 상세 인터페이스 설계에서 추가 정의가 필요하다.

본 문서는 제공된 인터페이스 표준 장표를 기준으로 한 **NSIGHT Interface Architecture Working Baseline**으로 활용한다.
