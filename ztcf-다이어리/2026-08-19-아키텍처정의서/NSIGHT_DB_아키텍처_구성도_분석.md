# NSIGHT DB 아키텍처 구성도 분석

## 0. 문서 목적

본 문서는 사용자가 제공한 **「DB 아키텍처 구성도」 장표**를 기준으로,
NSIGHT의 **RDW(Real-time Data Warehouse) / ADW(Analytical Data Warehouse)** 역할,
주요 업무 배치, 데이터 유입 구조, BI·데이터거버넌스·IT서비스 배치 관계를 분석하여
아키텍처 기준으로 정리한 문서이다.

> 원본 장표의 핵심 문구  
> **“RDW, ADW는 EXADATA RAC 각 1식 이중화 구성”**

### 작성 원칙

- 장표에서 직접 확인되는 명칭과 구조를 우선 기록한다.
- 원본 장표에 없는 상세 구현방식은 임의로 확정하지 않는다.
- 아키텍처적 해석이 필요한 부분은 **[분석]**으로 구분한다.
- CDC, RDW→ADW 전달방식, RAC 세부 노드 구성 등 장표에서 확정되지 않는 부분은 **확인 필요**로 관리한다.

# 2. 원천 시스템 및 데이터 유입 구조

원본 장표의 좌측에는 RDW로 유입되는 주요 원천 영역이 다음과 같이 표현되어 있다.

| 상위 영역 | 원천/연계 시스템 | RDW 유입 관계 |
|---|---|---|
| 계정계 | 코어뱅킹 | CDC 중계를 통한 유입 구조로 표현 |
| 계정계 | 연계뱅킹 | CDC 중계 영역과 연결 |
| 계정계 | BCV | 원천 데이터 영역 |
| 계정계 | 연계업무 | 원천 데이터 영역 |
| 비대면채널 | 인터넷뱅킹 | 원천/채널 데이터 영역 |
| 비대면채널 | 스마트뱅킹 | 원천/채널 데이터 영역 |

### [분석]

장표는 **계정계 및 채널계 데이터가 CDC 중계를 거쳐 RDW로 유입되는 구조**를 핵심으로 표현한다.

즉 RDW의 데이터 유입 방향은 다음과 같이 이해할 수 있다.

```text
원천 시스템
   ↓
CDC 중계
   ↓
RDW 실시간/준실시간 영역
```

다만 다음 내용은 원본 장표만으로는 확정할 수 없다.

- CDC 제품명
- Source DB별 CDC 방식
- Topic/Queue 사용 여부
- CDC 중계 DB 존재 여부
- Exactly-once / At-least-once 정책
- 장애 복구 및 재처리 방식
- 초기 Full Load와 증분 CDC의 관계

# 3. RDW 아키텍처

## 3.1 RDW의 물리 구조

원본 장표에서는 다음과 같이 정의한다.

> **RDW는 EXADATA RAC 1식 이중화 구성**

따라서 RDW는 단일 DB 인스턴스가 아니라,
Oracle Exadata 기반 RAC 구조를 전제로 한 데이터 플랫폼으로 정의되어 있다.

### [분석]

RDW는 장표의 배치상 다음 두 책임을 동시에 수행한다.

1. **실시간/준실시간 데이터 플랫폼**
2. **마케팅 업무 실행 데이터 영역**

---

# 4. 데이터플랫폼 RDW 구성

원본 장표에 표시된 `데이터플랫폼 RDW`의 구성요소는 다음과 같다.

| 구분 | 구성요소 | 의미/역할 해석 |
|---|---|---|
| 공통 | 공통 | RDW 공통 데이터/기능 영역 |
| SoR | 실시간SoR | 실시간 기준성/원천성 데이터 영역 |
| 집계 | 준실시간요약집계 | 준실시간 요약 데이터 |
| 마트 | 준실시간보고서마트 | 준실시간 보고/조회용 마트 |
| Feedback | 피드백 | 결과/반응 데이터의 환류 영역 |

### [분석]

이 구조는 RDW가 단순한 데이터 적재소가 아니라 다음의 데이터 계층을 갖는 것을 의미한다.

```text
실시간 Source Data
        ↓
    실시간SoR
        ↓
준실시간 요약집계
        ↓
준실시간 보고서마트
        ↓
     피드백
```

다만 `피드백`의 정확한 대상 시스템과 데이터 흐름 방향은 원본 장표에서 상세히 표시하지 않는다.

## 5.2 [분석] 마케팅플랫폼과 RDW의 관계

원본 구성상 마케팅플랫폼은 ADW가 아니라 **RDW에 배치**되어 있다.

이는 마케팅플랫폼의 주요 업무가 다음 성격을 가진다는 것을 보여준다.

- 고객정보 실시간/준실시간 조회
- 고객 행동 데이터 반영
- 캠페인/상담/영업 지원
- Single View 제공
- 실시간 처리
- 피드백 데이터 반영

따라서 아키텍처 책임을 다음처럼 정리할 수 있다.

```text
RDW
=
실시간/준실시간 데이터
+
Operational Marketing Data
+
고객 행동/반응 데이터
+
마케팅 업무 실행 지원
```

# 6. ADW 아키텍처

## 6.1 ADW의 물리 구조

원본 장표는 ADW 역시 다음과 같이 정의한다.

> **ADW는 EXADATA RAC 1식 이중화 구성**

ADW 내부는 크게 네 영역으로 나뉜다.

```text
ADW
│
├─ 데이터플랫폼 ADW
├─ BI 포탈
├─ 데이터거버넌스
└─ IT서비스 및 업무지원
```

# 7. 데이터플랫폼 ADW 구성

| No | 구성요소 | 역할 해석 |
|---:|---|---|
| 1 | 공통 | 분석 플랫폼 공통 |
| 2 | 분석SoR | 분석 기준 데이터 |
| 3 | 분석통합요약집계 | 통합 분석용 집계 |
| 4 | 분석단위업무마트 | 업무단위 분석 마트 |
| 5 | 분석보고서마트 | 보고/분석용 마트 |
| 6 | 피드백 | 분석 결과 환류 |
| 7 | 분석지원 | 분석 지원 데이터/서비스 |

### [분석]

ADW 내부 데이터 흐름은 개념적으로 다음 계층으로 이해할 수 있다.

```text
분석SoR
   ↓
분석통합요약집계
   ↓
분석단위업무마트
   ↓
분석보고서마트
   ↓
BI / OLAP / Self BI
```

다만 원본에서는 실제 ETL Job, Batch Schedule, DB Schema, 데이터 적재 주기를 표시하지 않는다.

# 8. BI 포탈 구성

원본 장표의 `BI 포탈` 구성요소는 다음과 같다.

| No | 구성요소 |
|---:|---|
| 1 | BI포탈 |
| 2 | 신용실적 |
| 3 | OLAP |
| 4 | Self BI |
| 5 | 신포털UI/UX |

### [분석]

BI 포탈은 ADW에 위치하므로,
주요 서비스 성격은 **분석·집계·보고·사용자 분석**에 가깝다.

RDW의 마케팅 업무와 비교하면 다음과 같다.

| 비교 | RDW / 마케팅플랫폼 | ADW / BI 포탈 |
|---|---|---|
| 주요 목적 | 업무 실행·조회 | 분석·보고 |
| 데이터 시점 | 실시간/준실시간 중심 | 분석·집계 중심 |
| 대표 서비스 | 미니싱글뷰, 캠페인, 실시간처리 | BI포탈, OLAP, Self BI |
| 데이터 모델 | Operational/Real-time | Analytical/Mart |

# 9. 데이터거버넌스 구성

ADW 내부의 `데이터거버넌스` 영역은 다음과 같다.

| No | 구성요소 | 주요 책임 해석 |
|---:|---|---|
| 1 | 공통 | 거버넌스 공통 |
| 2 | 비즈메타 | 비즈니스 메타데이터 |
| 3 | 데이터품질 | 품질 관리 |
| 4 | 데이터흐름 | 데이터 Lineage/Flow 관리 |

### [분석]

장표는 데이터거버넌스를 별도 독립 DB가 아닌,
ADW 아키텍처 영역 내 주요 기능으로 배치하고 있다.

이는 분석계 데이터에 대해 다음 관리 기능을 제공하는 구조로 해석할 수 있다.

```text
메타데이터 관리
+
데이터 품질
+
데이터 흐름/Lineage
=
ADW 데이터 거버넌스
```

# 11. RDW와 ADW의 책임 분리

원본 장표를 기준으로 가장 중요한 아키텍처 경계는 **RDW와 ADW의 역할 분리**이다.

| 구분 | RDW | ADW |
|---|---|---|
| 물리 DB | Exadata RAC | Exadata RAC |
| 목적 | 실시간/준실시간 업무 데이터 | 분석/집계/BI 데이터 |
| 데이터 유입 | CDC 중계가 명시됨 | 장표에서 상세 미표기 |
| 핵심 SoR | 실시간SoR | 분석SoR |
| 집계 | 준실시간요약집계 | 분석통합요약집계 |
| 마트 | 준실시간보고서마트 | 분석단위업무마트 / 분석보고서마트 |
| 주요 업무 | 마케팅플랫폼 | BI 포탈 |
| 주요 기능 | 고객/마케팅/행동/실시간 처리 | BI/OLAP/Self BI/분석 |
| 거버넌스 | 별도 표시 없음 | 데이터거버넌스 배치 |
| 운영지원 | 별도 표시 없음 | IT서비스 및 업무지원 배치 |
| 이중화 | RAC | RAC |

# 12. 데이터 흐름 관점 분석

원본 장표에서 명확하게 보이는 흐름은 다음이다.

```text
계정계 / 비대면채널
        │
        ▼
     CDC 중계
        │
        ▼
       RDW
        │
        ├─ 실시간SoR
        ├─ 준실시간요약집계
        ├─ 준실시간보고서마트
        └─ 마케팅플랫폼
```

반면 다음 흐름은 장표에서 화살표나 인터페이스 방식으로 구체화되어 있지 않다.

```text
RDW
  ?
  ?
  ▼
ADW
```

따라서 아래 사항은 별도 설계자료에서 확인해야 한다.

- RDW → ADW 전달 주기
- ETL/Batch/CDC 사용 여부
- Full/Incremental Load 방식
- 데이터 변환 위치
- 실패/재처리 정책
- 피드백 데이터의 역방향 흐름
- 데이터 품질 검증 시점
- 배치와 실시간 경계

# 13. HA 관점 분석

장표 제목은 다음을 명확히 정의한다.

```text
RDW : EXADATA RAC 1식 이중화
ADW : EXADATA RAC 1식 이중화
```

따라서 DB 고가용성의 최소 구성은 다음과 같이 볼 수 있다.

```text
RDW
┌─────────────────────┐
│ Exadata RAC         │
│  ├─ RAC Node        │
│  └─ RAC Node        │
└─────────────────────┘

ADW
┌─────────────────────┐
│ Exadata RAC         │
│  ├─ RAC Node        │
│  └─ RAC Node        │
└─────────────────────┘
```

### 확인 필요

원본 장표만으로는 다음이 확정되지 않는다.

- RAC Node 정확한 개수
- DB Service 구성
- SCAN/VIP
- Instance Affinity
- Service Failover 정책
- Data Guard 구성
- DR 센터 구성
- RAC와 DR 간 역할 분리

# 17. 최종 아키텍처 해석

이번 장표에서 가장 중요한 구조는 다음 세 가지이다.

## 17.1 RDW와 ADW의 명확한 분리

```text
RDW
= 실시간 / 준실시간 / 마케팅 실행

ADW
= 분석 / BI / 데이터거버넌스
```

이를 통해 **실시간 온라인 서비스와 대용량 분석 서비스의 책임 및 자원 경합을 분리**하는 구조로 해석할 수 있다.

## 17.2 RDW는 마케팅플랫폼의 실시간 데이터 기반

마케팅플랫폼의 16개 주요 업무가 RDW 안에 배치되어 있으므로
RDW는 단순 DW가 아니라 **마케팅 실행을 지원하는 Operational Data Platform**의 성격을 가진다.

## 17.3 ADW는 분석과 거버넌스의 중심

ADW에는 데이터플랫폼 ADW뿐 아니라
BI 포탈, 데이터거버넌스, IT서비스 및 업무지원이 배치되어 있으므로
분석 데이터의 활용·품질·메타·운영을 함께 지원하는 구조로 볼 수 있다.

# 19. 결론

원본 DB 아키텍처 구성도는 NSIGHT 데이터 플랫폼을 다음과 같이 정의하고 있다.

1. **RDW와 ADW를 각각 Exadata RAC 기반으로 이중화한다.**
2. **계정계 및 채널계 데이터는 CDC 중계를 통해 RDW로 유입한다.**
3. **RDW는 실시간/준실시간 데이터와 마케팅플랫폼을 담당한다.**
4. **ADW는 분석SoR, 집계, 업무마트, 보고서마트를 담당한다.**
5. **BI 포탈은 ADW 분석 데이터 위에서 동작한다.**
6. **데이터거버넌스는 비즈메타·데이터품질·데이터흐름을 관리한다.**
7. **IT서비스 및 업무지원은 아키텍처·프레임워크·SCM·배포·배치·단말·데이터 적재·보고서 기능을 지원한다.**
8. **RDW→ADW의 실제 데이터 전달 메커니즘은 별도 상세 설계 확인이 필요하다.**
9. **RAC 이중화와 센터 DR은 별개의 가용성 설계로 관리해야 한다.**

본 문서는 제공된 장표를 기준으로 한 **NSIGHT DB Architecture Working Baseline**으로 활용한다.
