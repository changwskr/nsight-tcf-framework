정확히는 `sv-service`가 **Public Key로 JWT의 서명(Signature)을 검증**하기 때문에 위·변조 여부를 알 수 있습니다. Public Key로 토큰 내용을 “복호화”하는 것이 아닙니다.

JWT를 단순화하면 다음 3부분입니다.

```text
JWT
=
Header
.
Payload
.
Signature
```

예를 들어:

```text
Header
{
  "alg": "RS256",
  "kid": "nsight-key-01"
}

Payload
{
  "userId": "E12345",
  "branchId": "10001",
  "role": "USER",
  "exp": ...
}

Signature
= tcf-jwt가 Private Key로 만든 전자서명
```

### 1. tcf-jwt가 토큰을 만들 때

`tcf-jwt`는 먼저 Header와 Payload를 가지고 서명 대상 데이터를 만듭니다.

```text
Base64Url(Header)
       +
       "."
       +
Base64Url(Payload)

          ↓

SHA-256 Hash 계산

          ↓

Private Key로 전자서명

          ↓

Signature
```

그래서 최종적으로:

```text
Header.Payload.Signature
```

가 됩니다.

Private Key는 `tcf-jwt`만 가지고 있습니다.

---

### 2. sv-service가 JWT를 받는다

사용자가 거래를 호출합니다.

```http
POST /sv/online
Authorization: Bearer eyJ...
```

`sv-service`의 JWT Filter가 토큰을 세 부분으로 분리합니다.

```text
JWT
 ↓
┌─────────┬─────────┬───────────┐
│ Header  │ Payload │ Signature │
└─────────┴─────────┴───────────┘
```

그리고 Header에서 `kid`를 확인합니다.

```json
{
  "alg": "RS256",
  "kid": "nsight-key-01"
}
```

`kid`는 쉽게 말해서:

> "이 토큰은 어느 키로 서명했는가?"

를 알려주는 Key ID입니다.

---

### 3. sv-service가 Public Key를 찾는다

`sv-service`는 JWKS 등을 통해 해당 `kid`의 Public Key를 가지고 있습니다.

```text
kid = nsight-key-01
        ↓
JWKS Cache 조회
        ↓
Public Key #01
```

NSIGHT에서 Gateway가 없다면 각 업무 WAR가 이 Public Key를 조회·캐시하여 JWT를 검증하는 구조를 사용할 수 있습니다.

---

### 4. sv-service가 자기 쪽에서도 Header + Payload를 계산한다

여기가 핵심입니다.

`sv-service`는 받은 JWT의 Header와 Payload를 이용하여 **자기 스스로 SHA-256 값을 계산**합니다.

```text
받은 Header
+
받은 Payload

      ↓

SHA-256

      ↓

검증 기준값 A
```

그리고 JWT에 포함되어 온 Signature를 Public Key로 검증합니다.

```text
JWT Signature
      +
Public Key
      ↓
서명 검증 결과 B
```

암호 라이브러리가 결국 확인하는 것은 개념적으로 다음과 같습니다.

```text
현재 Header + Payload의 Hash
              ==
Private Key를 가진 발급자가
Signature를 만들 때 사용한 Hash인가?
```

같으면:

```text
VALID
```

다르면:

```text
INVALID
```

입니다.

### 5. 누군가 Payload를 바꾸면 어떻게 되는가

원래 `tcf-jwt`가 발급한 것이:

```json
{
  "userId": "E12345",
  "role": "USER"
}
```

라고 하겠습니다.

공격자가 Payload를 다음처럼 바꿉니다.

```json
{
  "userId": "E12345",
  "role": "ADMIN"
}
```

문자 하나라도 바뀌었기 때문에 SHA-256 결과가 완전히 달라집니다.

```text
원본

Header + role=USER
       ↓
Hash = AAAA
       ↓
Private Key
       ↓
Signature XYZ
```

그런데 공격자는 Payload만 변경했습니다.

```text
변조본

Header + role=ADMIN
       ↓
Hash = BBBB

하지만 Signature는
여전히 XYZ
```

`sv-service`가 Public Key로 검증하면:

```text
현재 데이터의 Hash
BBBB

        ≠

Signature XYZ가 증명하는
원래 데이터의 Hash
AAAA
```

따라서:

```text
JWT Signature verification failed
        ↓
401 Unauthorized
```

가 됩니다.

### 6. 공격자가 Signature도 새로 만들면 되지 않는가?

이게 Public/Private Key 방식의 핵심입니다.

공격자가 Payload를:

```text
USER → ADMIN
```

으로 바꾸는 것은 어렵지 않습니다.

하지만 변경된 Payload에 맞는 **정상 Signature를 새로 만들려면 Private Key가 필요합니다.**

```text
공격자

Payload 변경
   ↓
새 Signature 필요
   ↓
Private Key 필요
   ↓
Private Key 없음
   ↓
정상 JWT 생성 불가능
```

Public Key를 가지고 있어도 할 수 있는 것은:

```text
Public Key
  └─ 서명이 맞는지 검증 O

Public Key
  └─ 새로운 서명 생성 X
```

입니다.

---

### 7. sv-service에서 실제 검증 순서

NSIGHT에서는 대략 다음 구조가 됩니다.

```text
사용자
  │
  │ Authorization: Bearer JWT
  ▼
SV WAR
  │
  ▼
TcfJwtAuthenticationFilter
  │
  ├─ ① JWT 형식 확인
  │
  ├─ ② Header의 alg 확인
  │       RS256 ?
  │
  ├─ ③ kid 확인
  │       nsight-key-01
  │
  ├─ ④ JWKS Cache에서 Public Key 조회
  │
  ├─ ⑤ Public Key로 Signature 검증
  │
  ├─ ⑥ exp 만료 확인
  │
  ├─ ⑦ iss 발급자 확인
  │
  ├─ ⑧ aud 대상 시스템 확인
  │
  └─ ⑨ Claim 추출
          userId
          branchId
          roles
          ...
          ↓
       인증 Context
          ↓
       TCF / STF
          ↓
       Handler
          ↓
       업무 처리
```

여기서 **⑤번이 위·변조 여부를 확인하는 핵심 단계**입니다.

하지만 Signature만 정상이라고 거래를 바로 허용하는 것은 아닙니다.

```text
Signature 정상
= 이 토큰을 신뢰하는 발급자가 서명했고
  Header/Payload가 서명 이후 변경되지 않았다.

그러나 추가로

exp  → 아직 유효한가?
iss  → 우리가 신뢰하는 발급자인가?
aud  → NSIGHT용 Token인가?
jti  → 폐기된 Token은 아닌가?
권한 → 이 거래를 수행할 권한이 있는가?

등도 확인해야 한다.
```

### 가장 쉽게 이해하는 비유

종이 증명서로 생각하면 매우 쉽습니다.

```text
tcf-jwt
= 증명서 발급기관

Private Key
= 발급기관만 가진 인감도장

JWT
= 발급된 증명서

Signature
= 증명서에 찍힌 특수 인감

Public Key
= 그 인감이 진짜인지 확인하는 검증도구

sv-service
= 증명서를 확인하는 기관
```

누군가 증명서의

```text
권한: USER
```

를

```text
권한: ADMIN
```

으로 고쳐도 **도장과 문서 내용의 관계가 깨집니다.**

`sv-service`는 Public Key를 이용해서 바로:

```text
"이 문서는 도장이 찍힌 이후 내용이 변경되었군."
```

이라고 판단할 수 있습니다.

따라서 가장 중요한 관계는 이것입니다.

```text
                 tcf-jwt
                    │
              Header + Payload
                    │
              Private Key
                    ↓
                 Signature
                    │
              JWT 발급
                    ↓
               sv-service
                    │
       Header + Payload + Signature
                    │
               Public Key
                    ↓
              서명 검증
             /         \
          성공          실패
           │             │
     위변조되지 않음    위변조/잘못된 키
           │             │
     Claim 추가검증      401 차단
```

**즉, Public Key가 “원래 토큰 내용을 기억하고 있어서 비교하는 것”이 아닙니다. 전자서명의 수학적 특성 때문에 `sv-service`가 현재 Header/Payload와 Signature가 서로 일치하는지를 확인할 수 있는 것입니다.**
