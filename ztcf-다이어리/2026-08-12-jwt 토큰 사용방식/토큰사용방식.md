토큰을 쓰는 이유는 **매 요청마다 사용자의 아이디와 비밀번호를 다시 확인하지 않고, “이 사용자는 이미 인증되었다”는 사실을 안전하게 전달하기 위해서**입니다.

가장 핵심만 먼저 보면 이렇습니다.

```text
로그인/SSO 인증
  ↓
토큰 발급
  ↓
사용자가 API 호출할 때 토큰 전달
  ↓
서버가 Public Key로 토큰이 진짜인지 검증
  ↓
정상이면 사용자 요청 처리
```

즉,

```text
Token
= 인증이 끝났다는 증명서

Private Key
= 그 증명서에 도장을 찍는 도구

Public Key
= 그 도장이 진짜인지 검사하는 도구
```

### 왜 토큰을 사용하는가

예를 들어 사용자가 SSO 로그인을 한 번 했다고 하겠습니다.

토큰이 없다면 매 거래마다 이런 식이 됩니다.

```text
고객조회 클릭
→ 사용자 다시 인증

상품조회 클릭
→ 사용자 다시 인증

캠페인조회 클릭
→ 사용자 다시 인증
```

이건 비효율적입니다.

그래서 최초 인증 후 다음과 같은 토큰을 발급합니다.

```text
사용자 E12345는
SSO 인증을 완료했고
10001 지점 소속이며
SV_USER 권한을 가지고 있고
이 인증은 22:30까지 유효하다.
```

이 내용을 JWT Token에 담아 사용자에게 줍니다.

이후에는:

```text
사용자
 ↓
Authorization: Bearer eyJ...
 ↓
SV WAR
```

처럼 거래마다 토큰만 보내면 됩니다.

---

### Public Key는 정확히 무엇을 하는가

중요한 부분입니다.

Public Key는 **토큰 내용을 암호 해독하는 키가 아니라, JWT 서명이 위조되지 않았는지 검사하는 키**입니다.

예를 들어 `tcf-jwt`가 다음 Token을 만들었다고 하겠습니다.

```text
Header
{
  alg: RS256,
  kid: nsight-2026-01
}

Payload
{
  userId: E12345,
  branchId: 10001,
  role: SV_USER,
  exp: 22:30
}
```

`tcf-jwt`는 이 내용에 Private Key로 서명합니다.

```text
Header + Payload
       ↓
Private Key
       ↓
Signature 생성
```

최종 JWT는 개념적으로:

```text
Header.Payload.Signature
```

입니다.

업무 WAR가 이 Token을 받으면 Public Key를 가지고 다음을 확인합니다.

```text
Header + Payload + Signature
          ↓
      Public Key
          ↓
"이 Signature가
 tcf-jwt의 Private Key로 만들어진 것이 맞는가?"
```

결과가 맞으면:

```text
VALID
```

틀리면:

```text
INVALID
```

이 됩니다.

---

### 누군가 Token 내용을 바꾸면?

예를 들어 원래 토큰이:

```json
{
  "userId": "E12345",
  "role": "USER"
}
```

라고 합시다.

사용자가 임의로:

```json
{
  "userId": "E12345",
  "role": "ADMIN"
}
```

으로 바꾼다고 해보겠습니다.

그러면 기존 Signature와 Payload가 맞지 않습니다.

```text
원래
USER
 ↓
Signature ABC

변조
ADMIN
 ↓
Signature ABC
```

Public Key로 검증하면:

```text
Payload가 변경됨
→ Signature 불일치
→ JWT INVALID
→ 요청 차단
```

됩니다.

그래서 JWT의 중요한 보안 목적은 **내용을 숨기는 것보다 변조를 막는 것**입니다.

---

### Public Key로 할 수 있는 것과 없는 것

| Public Key로 가능한 것      | 가능 여부 |
| --------------------------- | --------: |
| JWT 서명 검증               |         O |
| 누가 발급한 토큰인지 검증   |         O |
| Payload 변조 여부 확인      |         O |
| JWT 새로 발급               |         X |
| JWT 서명                    |         X |
| Private Key 복원            |         X |
| 다른 사용자의 정상 JWT 생성 |         X |

따라서 Public Key는 업무 WAR 여러 곳에 배포해도 됩니다.

```text
                     tcf-jwt
                 Private Key
                     │
                 JWT 발급
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      SV WAR       IC WAR       OM WAR
   Public Key    Public Key    Public Key
        │            │            │
      JWT 검증      JWT 검증      JWT 검증
```

NSIGHT 설계에서도 Private Key는 `tcf-jwt`만 보유하고, Gateway나 업무 WAR는 Public Key로 JWT를 검증하는 구조를 기준으로 두고 있습니다.

### 그런데 JWT 안에 사용자 정보가 있는데 믿어도 되나?

**Public Key 검증을 먼저 통과했다면**, 그 JWT의 Claim은 `tcf-jwt`가 서명한 정보라고 볼 수 있습니다.

그래서 업무 서버는 보통:

```text
Authorization: Bearer JWT
        ↓
Public Key 서명검증
        ↓
exp 만료 확인
        ↓
iss 발급자 확인
        ↓
aud 대상 시스템 확인
        ↓
userId / branchId / roles 추출
        ↓
업무 처리
```

합니다.

즉 Public Key 검증을 하지 않고 JWT의 `userId`, `role`만 읽는 것은 의미가 없습니다.

---

### 토큰을 쓰면 서버 세션이 없어도 된다

이게 JWT를 사용하는 또 하나의 큰 이유입니다.

세션 방식:

```text
사용자
 ↓
JSESSIONID
 ↓
서버
 ↓
Session DB 또는 Memory 조회
 ↓
사용자 확인
```

JWT 방식:

```text
사용자
 ↓
JWT
 ↓
업무 WAR
 ↓
Public Key로 직접 검증
 ↓
사용자 확인
```

따라서 여러 업무 WAR가 있을 때:

```text
SV
IC
PC
MG
OM
```

모두 같은 Public Key를 이용하면 중앙 Session을 매 거래마다 조회하지 않고도 인증을 확인할 수 있습니다.

이것이 NSIGHT처럼 업무 WAR가 많은 구조에서 JWT가 특히 유용한 이유입니다.

---

한 문장으로 정리하면:

> **토큰은 “이미 인증된 사용자의 신원·권한을 다음 요청에서도 증명하기 위한 인증 증표”이고, Public Key는 “그 토큰이 진짜 토큰 발급 시스템의 Private Key로 서명되었고 중간에 위조·변조되지 않았는지 확인하는 검증키”입니다.**

따라서 전체 구조는 이것만 기억하시면 됩니다.

```text
SSO
 ↓
사용자 인증
 ↓
tcf-jwt
 ↓
Private Key로 JWT 서명
 ↓
사용자에게 Token 전달
 ↓
업무 WAR 호출
 ↓
Public Key로 JWT 검증
 ↓
정상 → 업무 처리
위조 → 차단
```
