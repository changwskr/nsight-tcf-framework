## 1. 마케팅 플랫폼 기본 Character Set 의사결정

원본 이미지: `KakaoTalk_20260827_160324873_01.jpg` · Page 1

### 1.1 Character Set 영향

- 외부매체(파일, DB, 단말기계연동문, 시내채널연동문, 외부기관대행전송 등)에 데이터를 읽고 쓸 때 데이터의 실제 Byte 값이 Character Set 종류에 따라 상이함. Character Set이 맞지 않을 경우, 한글이 정상적으로 표시되지 않음.
- 시스템 기본 Character Set과 다른 데이터를 읽거나 쓰는 경우에는 해당 데이터의 Character Set을 명시적으로 지정하여 읽고 써야 함.
- Character Set을 명시하지 않으면 시스템 기본 설정을 따름. 채널·영역 간 Character Set을 통일하면 공통 로직 처리가 용이함.

| 매체 | 처리 방식 (원본) |
|---|---|
| **파일** | 어플리케이션 변수 형식 혹은 파라미터로 Character Set 지정 필요 (모든 파일의 Character Set이 동일하다면 공용 옵션으로 지정 가능) |
| **전문** | 프레임워크 또는 공용 모듈에서 변환 처리 (어플리케이션 영향 없음 / 어플리케이션별 정의 가능) |
| **DB** | JDBC 연결 설정에서 Character Set 지정 가능 (어플리케이션 영향 없음, 클라이언트 측 설정) |

### 1.2 고려 가능 Character Set

| 구분 | 표준 | 특징 |
|---|---|---|
| **UTF-8** | 국제표준 (유니코드 기반) | • 문자의 종류에 따라 1~4바이트로 처리 (가변 바이트)<br>• 모든 문자를 동시에 표현 가능<br>• 저장 데이터의 크기가 큼 |
| **EUC-KR** | 한국표준 (KSC5601 기반) → 한글(2,350자), 한자, 기호<br>(KSC5601 한글 + KSC5636 영문·숫자) | • 한글 관련 문자(한글, 한자, 영문, 기호) 위주 표현<br>• 영문·기호 1바이트, 한글·한자 2바이트 (고정 길이)<br>• Fixed Length 전문에서 사용 용이<br>• 국내어 데이터 저장 크기가 상대적으로 작음<br>• (단, 한글과 타 외국어를 동시에 표기할 수 없음) |
| **MS949** | 마이크로소프트사에서 한글 완성형(EUC-KR) 확장 | • EUC-KR에서 지원하지 않는 일부 한글 추가 지원<br>• 공식 표준은 아니나 Windows 환경에서 널리 사용 (일부 환경 미지원)<br>• EUC-KR로 세팅된 문자는 변함없이 읽을 수 있음 |

### 1.3 Character Set 결정을 위한 고려사항

- 시스템이 수용하는 문자의 종류 (외국어 유무)와 한글 처리
- 타 시스템과 주고받는 데이터의 Character Set 호환성
  - 정보단말: **EUC-KR**
  - JSON표준전문: **UTF-8**
  - FEP전문: **EUC-KR**
  - EAI 전문: **UTF-8 / EUC-KR**
  - 배치 FILE: **UTF-8**
  - 입출력파일: **EUC-KR**
  - EXA: **UTF-8 / EUC-KR**
  - Cloud 환경: **UTF-8**

### 1.4 결정 및 판단 근거 (원문 요지)

연계 시스템 간 Character Set 불일치는 데이터 깨짐·표시 오류를 유발한다. 마케팅 플랫폼은 정보단말(EUC-KR), JSON(UTF-8), FEP(EUC-KR), EXA·Cloud 등 **이질적 Character Set이 교차하는 접점**이다.

원문에서 읽히는 판단 축:

1. **레거시 정합 축**: 다국어를 하지 않는 한, 전행 표준·단말·FEP와의 정합을 위해 기본값으로 **EUC-KR**이 유리하다.
2. **통합 접점 축**: 온라인/모바일·JSON·Cloud·외부 API가 UTF-8이므로, 플랫폼이 허브이면 **UTF-8 기본 + 레거시 변환** 또는 **이중 영역(§2)** 이 검토된다.

> **점검**: §1만으로는 “기본 Character Set = EUC-KR | UTF-8”이 **단일 확정문**으로 닫히지 않는다. §2 Backup이 이중 영역을 제시하므로, 최종 확정은 §8 옵션 표와 ADR(의사결정 기록)로 닫아야 한다.

## 2. [Backup] 캐릭터셋에 따른 영향도  
### (시스템 영역간 Character Set 영향도)

원본 이미지: `KakaoTalk_20260827_160324873.jpg` · Page 2

마케팅 플랫폼에 대한 캐릭터셋 결정은 온라인/배치(매체)/마케팅 정보 수집/배포 등의 관점에서 가장 효율적인 방안을 도출해야 함.

### 2.1 마케팅 플랫폼 Character 구성 방안 (TEXT)

```text
                    ┌──────────── 내/외부 플랫폼 ────────────┐
                    │                                        │
   계정계(EUC-KR)   │  [1] EUC-KR          [2] UTF-8        │  채널 플랫폼(UTF-8)
        │           │      ▲                  ▲             │       │
        └───────────┼──────┤                  ├─────────────┼───────┘
                    │      │   (영역 간 변환)  │             │
 EDW(EUC-KR)        │      │                  │             │  대외 DC(운영)(UTF-8)
 빅데이터(EUC-KR)   │      │                  │             │  Web Connector(UTF-8)
 DB(EUC-KR)         │      │                  │             │  하둡(M-K)(운영)(UTF-8)
 대상 DC(운영)      │      │                  │             │  CDP(운영)(UTF-8)
 마케팅 DW(운영)    │      │                  │             │  타겟팅(MS-SQL)(UTF-8)
        │           │      │                  │             │
        ▼           └──────┴──────────────────┴─────────────┘
  하나머니(EUC-KR)
  SMS(EUC-KR)

  대고객 서비스 · 영업점 단말 · 콜센터 · LMS/PUSH
  배치 처리 · 빅데이터 플랫폼
```

> 원본 도식은 마케팅 통합 DB(또는 내/외부 플랫폼) 안에 **[1] EUC-KR** / **[2] UTF-8** 두 영역을 두고, 레거시·전행 표준 계열과 디지털·외부 매체 계열을 각각 연결한다.

### 2.2 구성 내용

**① EUC-KR**

- 마케팅 플랫폼의 원천 데이터가 EUC-KR(전행 표준)인 상황에서 가장 효율적인 데이터 수집 및 배포 방법
- 기존 시스템과의 연계 시 캐릭터셋 변환 없이 데이터 적재/추출 가능
- 명시적 캐릭터셋 변환 불필요 (단, 시스템 간 데이터 연계 시 지정된 캐릭터셋이 있다면 명시적으로 변경해야 함)

**② UTF-8**

- 마케팅 플랫폼의 성격상 온라인/모바일 등 다양한 매체와 연동하기 위해 UTF-8을 기본 캐릭터셋으로 설정
- 외부 연동 시 UTF-8 변환 과정이 필요하며, 기존 레거시 시스템 연동 시 별도의 변환 작업 필요
- 단말이 EUC-KR을 사용하므로 온라인거래 시 캐릭터셋 변환 수행 필요
- 기존 하둡(하나드림), 모바일 등을 고려하여 파일 생성 시 명시적 캐릭터셋 지정 필요

### 2.3 고려사항

- 데이터 정합성 / 정확성 확보를 위한 테스트 및 검증 필요
- 향후 전행 표준 캐릭터셋 전환(EUC-KR → UTF-8) 계획에 따른 단계적 전환 고려
- B2C 서비스 매체별 영향도 파악 및 대응 방안 수립
- 마케팅 수집 / 적재 관련 시스템은 다양한 캐릭터셋 수용 필요
- BDW 관련 영역에 대한 변환 작업 필요

## 6. 변환 책임 경계 (설계 규칙)

원문 §1.1을 shall 형태로 보완한다. (**ANALYSIS / 권고**)

```text
[채널·외부·파일·DB]
        │
        ▼
 ┌─ Integration / Message Boundary ─┐  ← 전문: FW·공용모듈만 변환
 │  (EAI / FEP / JSON / 단말전문)     │
 └──────────────┬───────────────────┘
                ▼
        [마케팅 AP 내부]  ← 업무 코드에서 getBytes()/임의 인코딩 금지
                │
 ┌─ DB Access Boundary ─────────────┐  ← JDBC·세션·NLS 측만 변환
 │  (EXA / 마케팅 DW / 타겟팅 DB)     │
 └──────────────┬───────────────────┘
                ▼
 ┌─ File / Batch Boundary ──────────┐  ← 파일 open 시 CS 파라미터 필수
 │  (배치 UTF-8 · 입출력 EUC-KR)     │
 └──────────────────────────────────┘
```

| 규칙 ID | 내용 |
|---|---|
| CS-R1 | 변환은 **경계에서 1회만**. 앱+드라이버 이중 변환 금지 |
| CS-R2 | Platform Default Charset(`getBytes()` 무인자) 금지 |
| CS-R3 | 파일은 Layout/파라미터에 CS **명시**. 미지정 금지 |
| CS-R4 | 전문 CS는 IF 정의서(또는 08 전문 표준)와 **동일 키**로 관리 |
| CS-R5 | DB는 JDBC URL/세션 NLS와 **스키마 실측**을 문서화 |
| CS-R6 | MS949 미지원·대체문자(`?`)를 정상으로 묵시 처리 금지 — 오류/모니터링 |
| CS-R7 | 영역[1]↔[2] 이동 시 변환 주체·실패 시 재처리 정책을 배치/온라인 각각 정의 |

---

## 7. 이중 영역(EUC-KR / UTF-8) 운영 모델

§2를 운영 관점으로 풀어 쓴다. (**ANALYSIS**)

```text
옵션 A — 단일 CS
  마케팅 AP/DB 전부 EUC-KR 또는 전부 UTF-8
  → 반대편 매체만 경계 변환

옵션 B — 논리 이중 영역 (원문 §2에 가장 가까움)
  [1] EUC-KR 존: 계정계·EDW(EUC)·마케팅DW·SMS·하나머니…
  [2] UTF-8 존: 채널플랫폼·CDP·하둡(M-K)·타겟팅·대외DC…
  → 존 간 이동 = 명시적 변환 파이프 (온라인 FW / 배치 ETL)
```

이중 영역 채택 시 필수 산출물:

| 산출물 | 내용 |
|---|---|
| 존 소속 카탈로그 | 테이블·토픽·파일경로·API가 [1]/[2] 중 어디인지 |
| 변환 파이프 목록 | 온라인/배치별 Source존→Target존, 도구, 실패코드 |
| 길이·정합 테스트 | 동일 문자열의 byte 길이·왕복(round-trip) 결과 |
| 단계적 전환 계획 | 전행 EUC-KR→UTF-8 시 [1] 축소 순서 |

## 9. NSIGHT(08) 캐릭터셋 표준과의 교차

| 항목 | 프로젝트 ONE 본 장표 (하나은행) | NSIGHT 정의서 08 |
|---|---|---|
| 채널/단말 | 정보단말 **EUC-KR** | 정보단말 · Package UI **UTF-8** |
| 업무 AP | 미확정 (EUC-KR 유리 ↔ UTF-8 검토) | 마케팅 등 업무 **UTF-8** |
| DB | EUC-KR / UTF-8 (이중 가능), EXA 혼재 | RDW·ADW **MS949**(실측 확정) |
| 변환 위치 | 파일=앱파라미터, 전문=FW, DB=JDBC | DB Access Boundary 중앙 통제 |

```text
[금지] 같은 산출물에 EUC-KR(본 장표)와 UTF-8(NSIGHT 08)을
       근거 없이 섞어 “둘 다 표준”으로 쓰지 말 것.
[권고] 프로젝트ONE 마케팅은 본 문서를 SSOT로 두고,
       NSIGHT 08은 차세대/다른 법인 표준 참조로만 인용.
```
