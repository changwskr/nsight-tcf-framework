다시 정리하면, **PDMG의 실제 JWT 인증 구조는 `pdmg-ui → pdmg-jwt → pdmg-ui → pdmg-service`, 그리고 공통 인증 검증은 `pdmg-fw`가 담당하는 구조**입니다.

이번 설명은 요청하신 대로 아래 5개만 기준으로 했습니다.

```text
pdmg-ui
pdmg-jwt
pdmg-fw
pdmg-service
pdmg-om
```

현재 제공된 압축본에서는 `pdmg-om` 소스 디렉터리가 확인되지 않으므로 **`pdmg-om = UNKNOWN`**으로 두고, `om-service`, `tcf-om`으로 대신 해석하지 않았습니다.

# 2. `pdmg-ui` — 사용자가 로그인한다

실제 파일:

```text

```

파일 상단에 아예 다음과 같이 적혀 있습니다.

```javascript

 * PDMG JWT 인증 포털 공통 유틸
 * 브라우저가 pdmg-jwt(:8110) 를 POST /online · JWKS 로 직접 호출한다.
 */
```

실제 JWT 서버 주소:

```javascript
const DEFAULT_JWT_BASE = "http://localhost:8110";
```

로그인 ServiceId:

```javascript

    serviceId: 'mgjwa1000C0',
    transactionCode: 'JWT-AUT-0001',
    serviceName: 'JWT 로그인'
}
```

따라서 UI에서 로그인을 하면:

```text
pdmg-ui
   │
   │ serviceId = mgjwa1000C0
   ▼
http://localhost:8110/online
```

을 직접 호출합니다.

실제 코드:

```javascript
const res = await fetch(base + "/online", {
  method: "POST",
  headers: {
    "Content-Type": "application/json;charset=UTF-8",
    Accept: "application/json",
```

여기서 중요한 점은 **로그인 요청에는 아직 Authorization Bearer Token이 없습니다.**

당연합니다.

```text
로그인 전
   ↓
JWT가 아직 없음
   ↓
ID / Password로 Token 요청
```

# 5. 그런데 로그인 시에는 JWT 검사를 하지 않는다

`pdmg-jwt/application.yml`의 local 설정:

```yaml
jwt:
  enabled: false
```

`ServicePreventionInterceptor` 실제 코드:

```java
private boolean validateJwt(
        HttpServletRequest request,
        HttpServletResponse response) throws Exception {

    if (!jwtEnabled) {
        return true;
    }
```

즉:

```text
pdmg-jwt

jwt.enabled=false
       │
       ▼
JWT 검증 생략
       │
       ▼
로그인 처리 가능
```

입니다.

이게 중요합니다.

로그인하려면 JWT가 필요한 구조로 만들면:

```text
JWT를 받으려면 로그인 필요
        ↑
        ↓
로그인하려면 JWT 필요
```

라는 모순이 생기므로 JWT 발급 서비스에서는 이를 끈 것입니다.

# 7. Handler 다음은 Facade

# 12. Private Key는 어디 있는가

실제 클래스:

```text
pdmg-jwt/.../config/JwtKeyConfiguration.java
```

현재 구현:

```java
RSAKey key =
    new RSAKeyGenerator(2048)
        .keyID(KEY_ID)
        .generate();
```

즉 현재 AS-IS:

```text
pdmg-jwt 기동
      ↓
RSA 2048 Key Pair 생성
      ├─ Private Key
      └─ Public Key
```

입니다.

따라서 **현재 소스에는 KMS 연동이 없습니다.**

이 부분은 중요한 운영 GAP입니다.

```text
[AS-IS]

pdmg-jwt 재기동
       ↓
새 RSA Key 생성 가능
       ↓
기존 토큰 검증 문제 가능


[TO-BE]

KMS / HSM
또는
영속 KeyStore
```

가 적절합니다.

```java
    return userId;

return claims.getSubject();
```

입니다.

# 35. 그런데 실제 중요한 GAP이 있다

`pdmg-jwt`에는:

```java

```

가 있습니다.

즉 Denylist 조회 기능 자체는 존재합니다.

그러나 이번 4개 실제 모듈 소스를 검색한 결과:

```text

```

호출은 다른 곳에서 확인되지 않았습니다.

특히 `pdmg-fw JwtProvider`는:

```text

Expiration
Access Type
```

는 검사하지만:

```text

```

를 조회하지 않습니다.

따라서 현재 구조:

```text

   ↓

   ↓
Denylist 조회 X
```

입니다.

### [GAP]

즉 **폐기된 Access Token을 `pdmg-service`에서 즉시 차단하는 Closed Loop가 현재 소스상 연결되지 않았습니다.**

# 36. 또 하나의 중요한 GAP — issuer / audience 검증


입니다.

## 최종적으로 가장 중요한 4가지

현재 PDMG JWT 구조는 기본 흐름 자체는 잘 잡혀 있습니다.

```text
pdmg-ui
   ↓
pdmg-jwt
   ↓
RS256 Token 발급
   ↓
pdmg-ui
   ↓ Bearer
pdmg-service
   ↓
pdmg-fw JWT 검증
   ↓
TCF
   ↓
업무
```

다만 운영 아키텍처 기준으로는 다음 4가지를 우선 보완하는 것이 좋습니다.

```text
1. JwtProvider에서 issuer / audience 검증 추가

2. JwtProvider 또는 인증계층에서
   jti Denylist 검증 연결

3. pdmg-jwt RSA Key의
   기동 시 생성 방식 → KMS/HSM/영속 Key 방식 전환

4. pdmg-om 실제 Source를 확보하여
   SSO → JWT 발급 경로 확정
```

특히 현재 구조에서 **JWT 인증의 핵심 위치는 `pdmg-service`가 아니라 `pdmg-fw`의 `ServicePreventionInterceptor + JwtProvider`**라고 이해하면 전체 구조가 가장 쉽게 정리됩니다.
