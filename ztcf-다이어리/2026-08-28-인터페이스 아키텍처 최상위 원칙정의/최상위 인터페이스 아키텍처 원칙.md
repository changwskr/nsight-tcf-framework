전행 시스템간 인터페이스 방안」도 실제로는 단순 프로토콜 목록이 아니라 **대상 정의 → 구성유형 → 인터페이스 유형 → 기본정책 → 예외 → 처리방식 → SYNC/ASYNC → 크기 → 패턴** 순서로 인터페이스 설계 원칙을 정하고 있습니다.

제가 권하는 **일반적인 인터페이스 아키텍처 가이드**의 최상위 구조는 아래 정도가 적절합니다.

---

# 1. 인터페이스 아키텍처 가이드의 역할

```text
                [Business / System Requirement]
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│             Interface Architecture Guide                     │
│                                                              │
│  ① 무엇을 연결할 것인가                                      │
│  ② 어떤 방식으로 연결할 것인가                               │
│  ③ SYNC / ASYNC 중 무엇을 선택할 것인가                      │
│  ④ API / Message / Event / File / CDC 중 무엇을 쓸 것인가    │
│  ⑤ 어떤 데이터 형식과 계약을 사용할 것인가                   │
│  ⑥ 장애·Timeout·Retry·중복을 어떻게 처리할 것인가            │
│  ⑦ 보안·로그·추적·운영을 어떻게 할 것인가                    │
│  ⑧ 표준을 벗어날 때 어떻게 승인할 것인가                     │
└──────────────────────────────────────────────────────────────┘
                            │
                            ▼
                  [Interface Detailed Design]
```

즉 이 문서는 **제품 사용법**이 아니라 프로젝트 전반의 **인터페이스 설계 의사결정 기준서**입니다.

---

# 2. 최상위 인터페이스 설계 원칙

이 정도가 가장 핵심적인 상위 원칙입니다.

| No    | 설계 원칙                                               | 결정 기준                                                            |
| ----- | ------------------------------------------------------- | -------------------------------------------------------------------- |
| IF-01 | **업무 목적에 따라 인터페이스 방식을 선택한다**         | 거래, 조회, 이벤트, 대량데이터, 파일을 동일 방식으로 처리하지 않는다 |
| IF-02 | **Point-to-Point 연결을 최소화한다**                    | 시스템 간 직접 연결보다 표준 Integration Layer를 우선한다            |
| IF-03 | **서비스 간 연계는 Service-to-Service를 원칙으로 한다** | 타 시스템 DB 직접접근, DB-Link는 제한한다                            |
| IF-04 | **SYNC/ASYNC는 업무 응답 필요성으로 결정한다**          | 즉시 결과가 필요한 경우만 SYNC, 그 외 ASYNC 우선                     |
| IF-05 | **온라인 거래와 대량 데이터 연계를 분리한다**           | API/전문과 ETL/File/CDC를 별도 처리                                  |
| IF-06 | **인터페이스 계약을 먼저 정의한다**                     | Source/Target, Schema, Error, Timeout, Version을 구현 전에 확정      |
| IF-07 | **장애가 다른 시스템으로 전파되지 않도록 한다**         | Timeout, Isolation, Retry, Circuit, DLQ 적용                         |
| IF-08 | **모든 인터페이스는 추적 가능해야 한다**                | Interface ID, Transaction ID, GUID/Correlation ID 적용               |
| IF-09 | **변경은 버전 단위로 관리한다**                         | Breaking Change는 신규 Version                                       |
| IF-10 | **예외는 Architecture 승인 대상으로 관리한다**          | P2P, Direct DB 등은 ADR/예외승인 필요                                |

과거 문서에서도 P2P는 구축이 쉽지만 연계가 늘면 장애 가능성과 유지보수 비용이 증가한다고 보고, Hub & Spoke 방식의 통합관리를 지향했습니다. 또한 실시간 DB 직접 Read/Write보다 **서비스-to-서비스 방식을 기본**으로 제한했습니다.

---

# 3. 가장 중요한 것은 “인터페이스 유형 선택 기준”

인터페이스 아키텍처 가이드에서 실제 개발자와 설계자가 가장 많이 보는 부분입니다.

| 업무 특성                          | 권장 인터페이스             | 처리방식   | 대표 용도          |
| ---------------------------------- | --------------------------- | ---------- | ------------------ |
| 즉시 거래 처리                     | API / Transaction Interface | SYNC       | 조회, 등록, 거래   |
| 시스템 간 서비스 호출              | API / Service               | SYNC       | 업무서비스 호출    |
| 처리 결과가 즉시 필요하지 않음     | Message / Event             | ASYNC      | 후처리, 알림       |
| 하나의 이벤트를 여러 시스템이 사용 | Event / Pub-Sub             | ASYNC      | 고객행동, 상태변경 |
| 원천 DB 변경을 지속 반영           | CDC                         | ASYNC      | RDW, 실시간 데이터 |
| 대량 데이터 변환·적재              | ETL / Batch                 | ASYNC      | DW, Mart           |
| 파일 단위 교환                     | MFT / File                  | ASYNC      | 대량파일, 외부기관 |
| Legacy 전용 전문                   | Adapter / 전문연계          | SYNC/ASYNC | Host, Legacy       |

이를 의사결정 그림으로 보면 더 명확합니다.

```text
                   [Interface Requirement]
                            │
                            ▼
                    즉시 응답이 필요한가?
                       │           │
                     YES           NO
                       │           │
                       ▼           ▼
                 거래/조회인가?    이벤트인가?
                  │       │          │
                 YES      NO        YES
                  │       │          │
                  ▼       ▼          ▼
               API/MCA   API      Event/Kafka
                                   │
                                   │ NO
                                   ▼
                         DB 변경분 전달인가?
                           │             │
                          YES            NO
                           │             │
                           ▼             ▼
                          CDC        대량 데이터인가?
                                      │       │
                                     YES      NO
                                      │       │
                                      ▼       ▼
                                     ETL     File/MFT
```

이것이 **인터페이스 아키텍처 가이드의 중심 페이지**가 되어야 합니다.

# 4. SYNC / ASYNC 결정 원칙

과거 문서도 SYNC 거래의 장기 대기가 Lock, Hang, 자원 비효율을 만들 수 있다고 보고 처리시간이 길거나 여러 시스템을 경유하는 경우 ASYNC를 고려하도록 했습니다.

현재 가이드에서는 다음처럼 단순화하는 것이 좋습니다.

| 판단 항목                           | SYNC   | ASYNC           |
| ----------------------------------- | ------ | --------------- |
| 사용자 즉시 응답                    | 필요   | 불필요          |
| Target 결과가 현재 거래 완료에 필수 | 필수   | 필수 아님       |
| 장시간 처리                         | 부적합 | 적합            |
| 다수 시스템 연계                    | 주의   | 적합            |
| 장애 격리                           | 어려움 | 용이            |
| 재처리                              | 복잡   | 상대적으로 용이 |
| 대량 처리                           | 부적합 | 적합            |

핵심 원칙은 한 문장으로 정할 수 있습니다.

> **“현재 업무 트랜잭션을 완료하기 위해 Target의 결과가 반드시 필요한 경우만 SYNC를 사용한다.”**

---

# 5. Point-to-Point 정책

이 부분도 반드시 별도 정책으로 있어야 합니다.

```text
[원칙]

System A
   │
   ▼
Standard Integration Layer
   │
   ▼
System B
```

다음은 제한 대상으로 두는 것이 좋습니다.

```text
System A ──────────────▶ System B
        직접 TCP

System A ──────────────▶ System B DB
        JDBC

System A DB ─DB-Link───▶ System B DB
```

다만 **같은 시스템 내부**, 기술적으로 하나의 Runtime/Domain으로 관리되는 경우에는 예외가 가능합니다.

과거 문서도 시스템 도메인 내부에서는 EAI를 사용하지 않고 해당 미들웨어의 인터페이스를 사용할 수 있도록 예외를 두고 있습니다.

# 6. DB 인터페이스 원칙

이것은 매우 중요합니다.

| 유형                       | 정책               |
| -------------------------- | ------------------ |
| 자기 시스템 DB 접근        | 허용               |
| 승인된 정보계 조회 DB 접근 | 조건부 허용        |
| 타 시스템 DB 직접 Read     | 제한               |
| 타 시스템 DB 직접 DML      | 금지 원칙          |
| DB-Link                    | 금지 또는 특별승인 |
| 원격 DB 분산 Transaction   | 금지 원칙          |
| 데이터 복제 목적           | CDC/ETL 우선       |

과거 문서 역시 DB 직접 Interface와 DB-Link에 대해 **원격 Lock, 네트워크 Pending, 성능저하, 변경 결합, 운영·패치 어려움**을 이유로 사용을 제한하고 있습니다.

# 7. Interface Contract 가이드

인터페이스를 만들기 전에 최소한 아래가 결정되어야 합니다.

| 구분     | 필수 설계항목                     |
| -------- | --------------------------------- |
| 식별     | Interface ID, Interface Name      |
| 관계     | Source System, Target System      |
| 업무     | 업무 목적, Service ID             |
| 방식     | API / Event / CDC / ETL / File    |
| 통신     | Protocol, Endpoint                |
| 처리     | SYNC / ASYNC                      |
| 데이터   | Request / Response / Event Schema |
| 공통정보 | Header, GUID, Transaction ID      |
| 오류     | Error Code, Error Message         |
| 시간     | Timeout                           |
| 복구     | Retry, Replay                     |
| 중복     | Idempotency                       |
| 보안     | 인증, 인가, 암호화                |
| 운영     | SLA, Monitoring                   |
| 관리     | Owner, Version                    |

여기서 중요한 개념은:

```text
Interface
≠ 단순 연결

Interface
= 연결
+ 계약
+ 오류처리
+ 장애처리
+ 보안
+ 추적
+ 운영
+ 변경관리
```

입니다.

# 8. Timeout / Retry 정책

### Timeout

```text
Client
  │
  │ 5s
  ▼
Gateway
  │
  │ 4s
  ▼
Target
  │
  │ 3s
```

상위 Timeout이 하위 Timeout보다 짧아지는 구조는 피해야 합니다.

### Retry

```text
일시적 장애
   ↓
Retry 가능
   ↓
Backoff
   ↓
Max Retry
   ↓
DLQ / Manual Recovery
```

반대로 다음은 무작정 Retry하면 안 됩니다.

```text
금융거래 DML
중복위험 거래
Validation Error
권한 Error
Business Reject
```

# 10. 인터페이스 패턴 가이드

실무 가이드는 최소 다음 패턴을 정의하면 좋습니다.

```text
P01  Sync Request / Response

Source ──Request──▶ Target
Source ◀─Response── Target
```

```text
P02  One-way Async

Producer ──Event──▶ Consumer
```

```text
P03  Pub/Sub

                    ┌─▶ Consumer A
Producer ─▶ Event ──┼─▶ Consumer B
                    └─▶ Consumer C
```

```text
P04  Async Request / Reply

Requester ─▶ Request Queue
Responder ◀─┘
Responder ─▶ Reply Queue
Requester ◀─┘
```

```text
P05  CDC

Source DB
   ↓
CDC
   ↓
Target DB
```

```text
P06  ETL

Source
 ↓
Extract
 ↓
Transform
 ↓
Load
 ↓
Target
```

```text
P07  File

Sender
 ↓
MFT
 ↓
Landing
 ↓
Validation
 ↓
Receiver
```

과거 문서에도 단방향, 다중통신, 양방향 비동기, 양방향 동기, 집합전송, 다중전송, DB-to-File, File-to-File 등 패턴이 정의되어 있습니다.

# 11. 인터페이스 운영 가이드

설계 완료의 기준은 **“연결된다”가 아니라 “운영할 수 있다”**가 되어야 합니다.

```text
Interface
   │
   ├─ Log
   ├─ Metric
   ├─ Trace
   ├─ Alert
   ├─ Retry
   ├─ Replay
   ├─ Reconciliation
   └─ Runbook
```

운영자가 최소한 다음 질문에 답할 수 있어야 합니다.

| 질문                    | 필요정보            |
| ----------------------- | ------------------- |
| 현재 정상인가?          | 상태/성공률         |
| 어디서 느린가?          | 구간별 Latency      |
| 어디서 실패했나?        | Error/Trace         |
| 어떤 거래였나?          | GUID/Transaction ID |
| 다시 처리할 수 있는가?  | Retry/Replay        |
| 누락된 데이터가 있는가? | Reconciliation      |
| 담당자는 누구인가?      | Owner               |
| 현재 버전은 무엇인가?   | Version             |

# 13. 결국 인터페이스 아키텍처 가이드의 목차는 이것이면 됩니다

저라면 프로젝트 공식 **「인터페이스 아키텍처 가이드」**를 다음 구조로 잡겠습니다.

```text
1. 개요
   - 목적
   - 범위
   - 용어

2. 인터페이스 아키텍처 원칙
   - 표준 연계
   - P2P 최소화
   - Service-to-Service
   - SYNC/ASYNC
   - 데이터/파일 분리

3. 인터페이스 유형
   - Transaction
   - API
   - Event
   - CDC
   - ETL
   - File
   - External

4. 인터페이스 선택 기준
   - Decision Tree
   - 유형별 적용 기준

5. 인터페이스 설계 표준
   - Interface ID
   - Contract
   - Header
   - Schema
   - Encoding
   - Error
   - Version

6. Runtime 처리 기준
   - Timeout
   - Retry
   - Idempotency
   - Transaction
   - Compensation

7. 인터페이스 패턴
   - Sync
   - Async
   - Pub/Sub
   - CDC
   - ETL
   - File

8. 보안
   - 인증
   - 인가
   - 암호화

9. 운영 및 관측성
   - Log
   - Metric
   - Trace
   - Monitoring
   - Replay
   - Reconciliation

10. 성능 / 용량
    - TPS
    - Payload
    - Batch Volume
    - SLA

11. 예외 및 변경관리
    - Exception
    - ADR
    - Version
    - Deprecation

12. 설계/개발/운영 Checklist
```

핵심은 **“EAI를 쓸 것인가 API를 쓸 것인가”를 정하는 문서가 아니라, 어떤 업무 조건에서 어떤 인터페이스 유형을 선택하고, 그것이 지켜야 할 설계·Runtime·운영 규칙을 정의하는 문서**로 만드는 것입니다.

현재 올려주신 「전행 시스템간 인터페이스 방안」은 이 가이드를 만드는 좋은 과거 기준 자료이고, 그중 **원칙·패턴·예외·SYNC/ASYNC·DB 직접연계 제한**은 그대로 계승할 가치가 있습니다. 반면 SNA, X.25, NDM, EUC-KR 같은 구체 기술은 당시 환경에 대한 구현 선택이므로 현재 프로젝트에서는 별도의 TO-BE 기술표준으로 재정의하는 것이 맞습니다.
