좋습니다. 이제 **21번째 설명 — NSIGHT Architecture Deliverable Map**으로 진행하겠습니다.

20번에서는 Architecture WBS를 통해 **“누가 언제 무엇을 수행하는가”**를 정리했습니다. 21번에서는 그 결과가 실제로 어떤 문서로 남아야 하며, AA·DA·TA·IA·Security·Runtime·ADR·Gate를 **서로 분리하면서도 하나의 Architecture Baseline으로 연결하는 방법**을 정리하겠습니다.

현재 통합분석 마스터 기준에는 이미 `00-EXECUTIVE-SUMMARY`부터 `38-EXECUTION-ROADMAP`, 그리고 이를 통합하는 `99-MASTER-ARCHITECTURE`까지의 최종 산출물 체계가 정의되어 있습니다. 특히 `99-MASTER-ARCHITECTURE.md`는 다른 문서를 복사해 붙인 문서가 아니라 **현재 NSIGHT Architecture Source of Truth를 한 번에 이해하기 위한 통합 View**로 정의됩니다.

# 21. NSIGHT Architecture Deliverable Map

## 21.1 가장 먼저 — “아키텍처 정의서 한 권”으로 끝내면 안 됩니다

전통적으로는 다음과 같이 가기 쉽습니다.

```text
NSIGHT_아키텍처정의서_v1.0.docx
              │
              ├─ AA
              ├─ DA
              ├─ TA
              ├─ Interface
              ├─ Security
              └─ Operations
```

문제는 프로젝트가 진행되면서 한 영역만 변경되어도 전체 문서를 다시 수정해야 한다는 것입니다.

예를 들어:

```text
Tomcat 구조 변경
       ↓
300페이지 정의서 수정

JWT 정책 변경
       ↓
300페이지 정의서 재배포

RDW/ADW 정책 변경
       ↓
300페이지 또 수정
```

이렇게 되면 어느 장이 최신인지 관리하기 어려워집니다.

따라서 NSIGHT는:

```text
독립 Architecture Document
        +
공통 Traceability
        +
Master Architecture View
        +
Baseline Version
```

구조가 적절합니다.

현재 통합 정의서에서도 AA·DA·TA/Physical·Interface·Traceability·ADR을 각각 P0 독립 산출물로 두도록 요구하고 있습니다.

# 21.30 특히 이 Registry들을 하나로 합치면 안 됩니다

   ↓

   ↓

   ↓

처럼 연결합니다.

# 21.50 이번 단계의 핵심 결론

**NSIGHT Architecture Deliverable Map은 “아키텍처 정의서 한 권”을 만드는 체계가 아니라, Vision·Big Picture·Logical·Physical·AA·DA·TA·IA·Security·Capacity·Migration·Operations·Runtime·Traceability·Rule·Model·ADR·Gate를 각각 책임 있는 독립 문서로 관리하고, 이를 공통 ID와 Traceability로 연결하여 `99-MASTER-ARCHITECTURE`에서 하나의 Architecture로 보여주는 문서 구조입니다.**

가장 중요한 원칙은 세 가지입니다.

> **하나의 사실은 하나의 Canonical 문서에서 정의한다.**
> **다른 문서는 복사하지 말고 참조한다.**
> **모든 문서는 동일 Architecture Baseline 아래에서 버전·Evidence·ADR·Gate와 연결한다.**

현재 NSIGHT 방법론이 각 단계마다 독립 산출물을 요구하는 것과도 일치하며, 현재 통합분석 기준이 제시하는 00~38 + 99 산출물 구조를 그대로 **Architecture Documentation Baseline**으로 발전시키는 것이 가장 안정적입니다.

이제 1번부터 21번까지를 놓으면:

```text
01~14  Architecture 자체를 정의
15     Architecture Rulebook
16     Review / Gate
17     Model / Traceability
18     Drift / GAP / ADR
19     Orchestration
20     WBS
21     Deliverable / Document System
```

까지 연결되었습니다.

**22번째에서는 이제 이 모든 산출물을 실제 프로젝트에서 언제 “작성완료”, “설계승인”, “구현완료”, “Runtime 승인”, “Baseline 완료”로 볼 것인지 — 즉 `Architecture Definition of Done(DoD) + 품질검증 체크리스트`로 내려가는 것이 자연스럽습니다.** 여기까지 정리하면 “문서는 다 만들었는데 아키텍처 작업은 끝난 것인가?”라는 질문을 객관적인 기준으로 판정할 수 있게 됩니다.
