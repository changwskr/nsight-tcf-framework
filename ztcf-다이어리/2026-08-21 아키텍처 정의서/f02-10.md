좋습니다. 이번부터는 **소스 메커니즘이 아니라 NSIGHT 구축전략을 최상위 기준**으로 놓고 설명하겠습니다. 그리고 `TCF / ServiceId / Tomcat / Hikari` 같은 내용은 전략을 구현하는 하위 수단으로만 연결하겠습니다.

전략 브리핑의 목차 자체가 `전략적 배경 → Vision/NFR → 6단계 방법론 → Big Picture → Logical → Physical → DR → Mechanism → Runtime → Data Platform → Marketing Platform → BI Portal → 유지관리` 순서로 되어 있습니다. 즉 이 순서가 NSIGHT를 이해하는 올바른 상위 흐름입니다.

# 1. NSIGHT는 무엇을 구축하는 사업인가

가장 먼저 이 질문부터 다시 잡아야 합니다.

NSIGHT는

```text
새로운 DW 구축
```

이 아닙니다.

또한

```text
Spring Framework 표준화 사업
```

도 아닙니다.

전략자료가 말하는 변화는 이것입니다.

```text
기존 정보계

데이터 저장
    ↓
야간 Batch
    ↓
익일 조회
    ↓
사후 분석


                ↓  패러다임 전환


NSIGHT

데이터 발생
    ↓
실시간 수집
    ↓
즉시 반응
    ↓
심층 분석
    ↓
경영 판단
```

발표자료 3~4쪽에서는 이 변화를 **“창고에서 살아있는 플랫폼으로”**라고 표현합니다. AS-IS의 야간 배치·단순 DW·서버별 독립운영·분석부하 문제를, TO-BE의 CDC Near Real-time·Kafka 기반 반응·도메인 분리·RDW/ADW 분리로 바꾸는 것이 핵심입니다.

따라서 NSIGHT의 최상위 구조는 제가 다음과 같이 보는 것이 정확합니다.

```text
                     NSIGHT

                   DATA
                    │
                    ▼
              데이터가 흐른다
                    │
                    ▼
                 REACTION
                    │
                    ▼
              고객에게 반응한다
                    │
                    ▼
                 DECISION
                    │
                    ▼
               조직이 판단한다
```

**Data → Reaction → Decision**을 가능하게 하는 정보계 플랫폼을 만드는 것입니다.

# 2. 전략의 세 단어 — Scalable, Resilient, Data-Centric

전략 브리핑 첫 장표가 이 세 단어를 전면에 놓고 있습니다.

이 세 단어를 별개의 구호로 보면 안 됩니다.

```text
                       NSIGHT
                          │
         ┌────────────────┼────────────────┐
         │                │                │
         ▼                ▼                ▼
    DATA-CENTRIC      SCALABLE        RESILIENT
    무엇이 중심?      어떻게 성장?      어떻게 견딤?
         │                │                │
    데이터 흐름        수평 확장          장애 격리
    데이터 책임        독립 확장          HA / DR
    데이터 경계        Resource 분리      회복 가능
```

### Data-Centric

설계의 출발점을 서버나 애플리케이션으로 잡지 않고,

> **데이터가 어디에서 생기고, 어디를 지나고, 누가 소유하고, 어느 시간 안에 도착해야 하는가**

로 잡습니다.

그래서 NSIGHT Data Architecture는 DB 구성도가 아니라 **데이터 목적·소유권·흐름·지연시간·처리유형·자원격리를 강제하는 정책**으로 정의됩니다.

### Scalable

한 번 큰 서버를 만들어 놓고 끝내는 것이 아니라 부하 특성에 따라 독립적으로 확장합니다.

```text
Online Service
      ↓
VM Scale-Out

RDW / ADW
      ↓
Exadata Parallel Scale

FAST
      ↓
FAST만 확장

DEEP
      ↓
DEEP만 확장
```

전략 NFR에도 온라인 서비스는 VM Scale-Out, RDW/ADW는 Exadata 병렬 확장으로 명확히 구분되어 있습니다.

### Resilient

단순히 서버 두 대를 놓는 것이 아닙니다.

```text
장애 발생
   ↓
영향범위를 작은 영역에 제한
   ↓
다른 업무는 계속 서비스
   ↓
Fail-Over
   ↓
복구
   ↓
Fail-Back
```

까지 포함합니다.

즉 **장애가 발생하지 않는 구조**가 아니라 **장애가 발생해도 시스템 전체로 번지지 않는 구조**입니다.

# 3. 이 전략을 5대 NFR로 설계 기준화합니다

전략이 구호로 끝나지 않도록 5개 품질목표로 변환합니다.

발표자료 6쪽은 이를 **“아키텍처를 지탱하는 5개의 기둥”**으로 정의합니다.

| NFR           | 전략적 질문                           | 주요 구축방향               |
| ------------- | ------------------------------------- | --------------------------- |
| Performance   | 고객에게 얼마나 빨리 반응하는가       | FAST Path, 자원격리         |
| Availability  | 장애에도 업무를 계속할 수 있는가      | HA, DR, Fault Isolation     |
| Scalability   | 성장하면 쉽게 늘릴 수 있는가          | VM Scale-Out, Exadata 확장  |
| Security      | 데이터와 사용자를 안전하게 보호하는가 | 망분리, SSO, 암호화, 마스킹 |
| Observability | 지금 무엇이 일어나는지 알 수 있는가   | APM, GUID/Trace, 통합로그   |

여기서 전략자료와 상세 용량자료의 숫자를 구분하는 것도 중요합니다.

### 전략 목표

```text
마케팅 오퍼링       ≤ 1초
Event 처리          ≤ 1초
CDC 데이터 통합     ≤ 30초
RTO                 ≤ 30분
```

### Application Capacity 목표

```text
일반 온라인
p95 ≤ 3초

Working Peak
600 / 1,200 / 1,800 TPS 등
```

`1초`와 `p95 3초`가 충돌하는 것이 아닙니다.

```text
1초
→ FAST Event / Marketing Offering

p95 3초
→ 일반 Online Transaction
```

으로 Scope가 다릅니다. 이 구분은 현재 Vision/NFR 기준에도 명시되어 있습니다.

이것이 중요합니다. **전략 SLA와 WAS 튜닝값을 같은 레벨에서 비교하면 안 됩니다.**

# 4. Vision 다음에는 바로 서버를 설계하지 않습니다

전략자료의 6단계는 다음과 같습니다.

```text
1. Vision
      │
      │ 무엇을 달성할 것인가
      ▼
2. Big Picture
      │
      │ 책임과 공간을 어떻게 나눌 것인가
      ▼
3. Logical
      │
      │ 어떤 정책을 강제할 것인가
      ▼
4. Physical
      │
      │ 실제 어떤 인프라에 배치할 것인가
      ▼
5. Mechanism
      │
      │ 그 정책을 어떻게 실행시킬 것인가
      ▼
6. Runtime
      │
      │ 실제 서비스가 목표를 만족하는가
      ▼
   Baseline
```

발표자료 8쪽에서는 이를 `Vision → Big Picture → Logical → Physical → Mechanism → Runtime`으로 명확하게 정의하고 있습니다.

여기에서 매우 중요한 문장이 있습니다.

> **논리 설계 + 물리 설계 = 메커니즘, 메커니즘 검증 = 런타임**

즉 Mechanism부터 보는 것은 순서가 거꾸로입니다.

# 5. Big Picture의 핵심 — “책임은 공간에 고정한다”

발표자료 9쪽의 메시지가 중요합니다.

> **“책임은 공간에 고정하고, 연결은 경계를 통제한다.”**

이 원칙으로 NSIGHT를 보면 서버보다 먼저 다음 공간이 생깁니다.

```text
                       NSIGHT

 ┌────────────────────────────────────────────┐
 │            DATA PLATFORM                   │
 │                                            │
 │ RDW / ADW / CDC / Kafka / ETL             │
 │ 데이터 수집·저장·가공·제공 책임           │
 └─────────────────┬──────────────────────────┘
                   │
                   ▼
 ┌────────────────────────────────────────────┐
 │          MARKETING PLATFORM                │
 │                                            │
 │ Customer / Single View / Campaign         │
 │ Event / Offering                           │
 │ 고객 행동 반응 책임                       │
 └─────────────────┬──────────────────────────┘
                   │
                   ▼
 ┌────────────────────────────────────────────┐
 │               BI PORTAL                    │
 │                                            │
 │ BI / OLAP / Self BI / Reporting           │
 │ 분석·판단 책임                             │
 └────────────────────────────────────────────┘

 ┌────────────────────────────────────────────┐
 │          DATA GOVERNANCE                   │
 │ 표준 / 품질 / 메타 / 데이터 통제           │
 └────────────────────────────────────────────┘

 ┌────────────────────────────────────────────┐
 │        IT SERVICE / SUPPORT                │
 │ 운영 / SSO / Framework / CI-CD / Monitoring│
 └────────────────────────────────────────────┘
```

즉 5대 서비스 도메인은 단순 조직 구분이 아닙니다.

**책임과 장애영향을 나누는 Architecture Boundary**입니다.

# 6. 이때 가장 중요한 설계전략은 “분리”입니다

전략자료를 관통하는 단어 하나를 고르면 저는 **Isolation**이라고 보겠습니다.

NSIGHT에는 계속해서 다음 분리가 등장합니다.

```text
RDW           ≠ ADW

FAST          ≠ DEEP

Online        ≠ Batch

Service AP    ≠ ETL

Domain A      ≠ Domain B

Main          ≠ DR

운영 조회      ≠ 분석 조회

업무 책임      ≠ 공통 Framework 책임
```

왜 이렇게 나누느냐가 중요합니다.

단순하게 구조를 예쁘게 만들기 위해서가 아닙니다.

```text
                  분리

                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   성능 격리    장애 격리    변경 격리
       │           │           │
       └───────────┼───────────┘
                   ▼
              독립 확장 가능
```

이것이 `Scalable + Resilient`의 실제 구현 원리입니다.

# 7. 데이터에서 FAST와 DEEP을 분리하는 이유

이것이 NSIGHT 전략에서 가장 중요한 아키텍처 결정 가운데 하나입니다.

## FAST

```text
고객 행동
   ↓
Event Capture
   ↓
Kafka
   ↓
Real-time Processing
   ↓
Marketing Decision
   ↓
Offering
```

목표는 **즉시 반응**입니다.

## DEEP

```text
Operational Source
   ↓
CDC
   ↓
RDW
   ↓
DataStage / ETL
   ↓
ADW
   ↓
BI / OLAP / Analytics
   ↓
경영 판단
```

목표는 **깊은 분석**입니다.

현재 Data Architecture 기준에서도 FAST/DEEP을 물리·논리적으로 분리하고 `CDC / Kafka / ETL`에 전용 경로를 부여합니다.

이 둘을 같은 자원에서 실행시키면:

```text
                동일 DB / 동일 자원

실시간 고객조회 ─────┐
                     ├─ CPU / IO / Session 경쟁
BI 대량분석 ─────────┘
                     │
                     ▼
              온라인 성능 저하
```

가 됩니다.

그래서:

```text
Online / Near Real-time
          ↓
         RDW


Analytics / BI / ETL
          ↓
         ADW
```

로 물리 분리합니다.

즉 RDW/ADW 분리는 **DB 두 개를 산 것**이 아니라,

> **온라인 업무와 분석 업무가 서로를 죽이지 못하도록 만든 Fault/Performance Boundary**

입니다.

---

# 8. 그렇다면 CDC와 Kafka는 같은 역할인가?

아닙니다.

전략을 정확히 이해하려면 이 차이가 중요합니다.

### CDC

```text
원천 DB 변경
    ↓
변경분 Capture
    ↓
RDW
```

주로 **데이터 상태 변화의 Near Real-time 동기화**입니다.

### Kafka

```text
고객 행동 Event
    ↓
Kafka
    ↓
Real-time Consumer
    ↓
Marketing Action
```

주로 **Event 전달과 실시간 반응**입니다.

### ETL / DataStage

```text
대량 Data
    ↓
정제 / 변환 / 집계
    ↓
ADW
```

분석을 위한 **DEEP 처리**입니다.

따라서 전략적으로:

```text
CDC
= Change Data Flow

Kafka
= Event Flow

ETL
= Bulk Transformation Flow
```

입니다.

이 세 가지를 하나의 Integration 기술처럼 보면 NSIGHT 전략을 잘못 이해하게 됩니다.

---

# 9. Logical Architecture에서는 “길을 정해 줍니다”

Data-Centric Architecture는 데이터를 아무 길로나 보내지 않습니다.

```text
              업무 요구

     "다른 시스템 데이터를 써야 한다"
                    │
                    ▼

              마음대로 연결 X

                    │
                    ▼

              목적별 표준경로
```

예를 들면:

```text
Online API
   ↓
표준 Service / API Integration

DB Change
   ↓
CDC

Event
   ↓
Kafka

Bulk Data
   ↓
ETL / DataStage

File
   ↓
표준 File Transfer
```

이것이 **Integration Control**입니다.

현재 Vision 원칙에도 `P2P/DB Link를 통제하고 표준 연계를 사용`하도록 명시되어 있습니다.

따라서:

```text
MG Service → MK DAO
```

를 금지하는 것은 단순 Java 코딩 스타일 때문이 아닙니다.

상위 전략인:

```text
Domain Separation
       +
Integration Control
       +
Data Ownership
```

이 애플리케이션 코드까지 내려온 결과입니다.

이런 식으로 앞으로 소스 구조를 설명해야 합니다.

---

# 10. Physical은 “Hybrid 전략”으로 내려갑니다

논리적으로 모두 분리한다고 해서 모든 영역을 동일 기술에 올리지 않습니다.

업무 특성이 다르기 때문입니다.

개념적으로는:

```text
                         NSIGHT

        고성능 데이터              유연한 서비스
             │                          │
             ▼                          ▼
         Exadata                 Private Cloud VM
        RDW / ADW                Marketing / BI

             │
             │
       대량처리 특화
             ▼
        Bare Metal
        ETL / IMDG

             │
       안정적 변경수집
             ▼
           UNIX
        CDC Relay
```

처럼 **Workload에 따라 실행공간을 선택하는 Hybrid Architecture**입니다.

즉:

> 모든 것을 Cloud로 옮기는 것이 전략이 아니라, **각 Workload에 가장 적합한 실행공간을 선택하는 것**이 전략입니다.

# 11. 그리고 구축전략은 DR까지 포함해야 완성됩니다

Availability를 단순히:

```text
서버 두 대
```

라고 정의하지 않습니다.

실제 질문은:

```text
WAS 한 대 죽으면?
DB가 죽으면?
센터가 죽으면?
Session은?
Kafka는?
Batch는?
SSO는?
Configuration은?
Data는?
Fail-Back은?
```

입니다.

Vision/NFR 기준에서도 AP Active-Active, 기능/도메인별 독립 분리, DR 활용, RTO 30분 이내, Fail-Over뿐 아니라 **Fail-Back까지 Architecture Scope에 포함**하도록 정의하고 있습니다.

따라서 DR 역시 하나의 별도 구축전략입니다.

# 12. 여기까지가 Mechanism보다 앞에 오는 아키텍처입니다

이제 위치관계를 정확히 보면:

```text
┌─────────────────────────────────────────┐
│ 1. Business / Architecture Strategy     │
│ Data → Reaction → Decision              │
├─────────────────────────────────────────┤
│ 2. Architecture Vision / NFR            │
│ Scalable / Resilient / Data-Centric     │
├─────────────────────────────────────────┤
│ 3. Big Picture                          │
│ 5대 서비스 도메인                       │
├─────────────────────────────────────────┤
│ 4. Logical Architecture                 │
│ Boundary / Data Flow / Integration      │
├─────────────────────────────────────────┤
│ 5. Data Architecture                    │
│ FAST/DEEP / RDW/ADW / CDC/Kafka/ETL    │
├─────────────────────────────────────────┤
│ 6. Physical Architecture                │
│ Hybrid / Resource Isolation             │
├─────────────────────────────────────────┤
│ 7. HA / DR                              │
│ Fault Isolation / Recovery              │
├─────────────────────────────────────────┤
│                 ↓                       │
│ 8. Mechanism                            │
├─────────────────────────────────────────┤
│ Protocol / Integration / Framework      │
│ CDC / Kafka / ETL / Standard Message    │

│                 ↓                       │

│ Handler / Service / DAO                 │
└─────────────────────────────────────────┘
```

**TCF는 8번 아래에 있습니다.**

앞으로는 이 계층을 절대 뒤집지 않겠습니다.

# 13. 그리고 현재 전략은 이미 상당히 명확합니다

자료를 다시 기준화하면 상위 전략은 오히려 상당히 잘 정리되어 있습니다.

| 전략영역               | 현재 상태 | 핵심                                |
| ---------------------- | --------- | ----------------------------------- |
| Vision                 | **명확**  | 실시간 경영 플랫폼                  |
| Architecture Character | **명확**  | Scalable / Resilient / Data-Centric |
| NFR                    | **명확**  | 5대 NFR                             |
| Methodology            | **명확**  | 6단계                               |
| Domain Strategy        | **명확**  | 책임·경계 분리                      |
| Data Strategy          | **명확**  | FAST/DEEP                           |
| RDW/ADW                | **명확**  | 물리·자원 분리                      |
| Integration            | **명확**  | 통제된 경로                         |
| Physical Strategy      | **명확**  | Hybrid                              |
| Scale Strategy         | **명확**  | Scale-Out + Exadata                 |
| Runtime Strategy       | **명확**  | FAST/DEEP 검증                      |
| Maintainability        | **명확**  | 표준 + DevOps + 운영통제            |

반면 아직 상세화가 더 필요한 것은 **상위 전략이 아니라 전략을 실제 구축 기준으로 전개하는 연결부**입니다. 예를 들어 Domain별 데이터 소유 Catalog, RDW/ADW Read/Write Matrix, CDC/Kafka/ETL Interface Registry, 실제 Runtime Evidence 등은 아직 완성이 필요합니다. Data Architecture 문서도 이 부분을 GAP으로 분류하고 있습니다.

## 다음 설명의 방향

이제 다음부터는 **NSIGHT의 5대 서비스 도메인을 하나씩 전략 관점으로 해체**하는 것이 맞습니다.

순서는 이렇게 가겠습니다.

```text
① 데이터플랫폼
   ├─ 왜 RDW/ADW인가
   ├─ CDC/Kafka/ETL 역할
   ├─ FAST/DEEP
   └─ 정보계 전체의 기초공사

② 마케팅플랫폼
   ├─ Customer Single View
   ├─ 고객 행동 Event
   ├─ 실시간 Offering
   └─ "반응하는 두뇌"

③ BI 포탈
   ├─ BI / OLAP
   ├─ Self BI
   ├─ AI/NLP
   └─ "판단하는 공간"

④ 데이터거버넌스
   ├─ 표준
   ├─ 품질
   ├─ Meta
   └─ 데이터 신뢰 통제

⑤ IT서비스 / 업무지원
   ├─ 운영
   ├─ SSO
   ├─ Batch
   ├─ Monitoring
   ├─ Framework
   └─ DevOps
```

그 다음에야 **이 5개 플랫폼을 실제 서버·인터페이스·TCF·WAS·보안·운영 구조가 어떻게 받쳐주는지** 내려가겠습니다.

다음은 **① 데이터플랫폼 구축전략 — “왜 NSIGHT에서 데이터플랫폼이 전체 아키텍처의 기초공사인가”**부터 이어가는 것이 가장 자연스럽습니다.
