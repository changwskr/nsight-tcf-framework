좋습니다. 이제 **19번째 설명 — NSIGHT Architecture Orchestration System**으로 진행하겠습니다.

18번까지는 `Baseline → Model → Rule → Test → Runtime Evidence → Drift → GAP/ADR → New Baseline`이라는 **Closed Loop 자체**를 설명했습니다. 19번에서는 이 과정을 사람이 문서 하나씩 열어 수동으로 수행하는 것이 아니라, **Architecture Orchestrator가 목표를 해석하고 필요한 전문 Agent를 구성하여 Gate 순서대로 실행하는 체계**로 연결하겠습니다.

현재 NSIGHT Orchestration 설계도 사용자의 목표를 먼저 Mission으로 정규화하고, 필요한 Agent만 선택해 `Document → Source → Model → Code → Test → Runtime Evidence → Drift → GAP/ADR` 순으로 작업하도록 설계되어 있습니다. 즉 수십 개 Agent를 항상 가동하는 구조가 아니라 **목적에 맞는 팀을 동적으로 구성하는 방식**입니다.

# 19. NSIGHT Architecture Orchestration System

## 19.1 가장 먼저 Orchestration이 왜 필요한가

현재 NSIGHT에는 이미 많은 자료가 있습니다.

```text
Architecture Strategy
Logical / Physical
Server Inventory
TCF
ServiceId
Standard Message
JWT / SSO
Capacity
HA / DR
Data
Integration
Runtime
Rule
GAP
ADR
```

문제는 자료가 부족한 것이 아닙니다.

오히려 문제는:

```text
어떤 자료를 먼저 봐야 하는가?

어떤 것이 현재 기준인가?

어떤 Source를 검사해야 하는가?

어떤 Rule을 적용해야 하는가?

Runtime Test까지 필요한가?

무엇이 GAP이고 무엇이 단순 Defect인가?

언제 Architecture Board로 넘겨야 하는가?
```

입니다.

그래서 필요한 것이 **Orchestrator**입니다.

---

# 19.2 Orchestrator는 “모든 일을 하는 Agent”가 아닙니다

Orchestrator의 역할은 직접 모든 분석을 하는 것이 아니라:

> **“사용자의 목적을 Architecture Mission으로 해석하고, 필요한 Agent를 선택하고, 작업 순서와 Gate를 통제하며, 결과를 하나의 Architecture Decision으로 통합하는 역할”**

입니다.

```text
                    USER GOAL
                       │
                       ▼
                ORCHESTRATOR
                       │
             목표 / 범위 / 위험 판단
                       │
             ┌─────────┼─────────┐
             │         │         │
             ▼         ▼         ▼
          Agent A   Agent B   Agent C
             │         │         │
             └─────────┼─────────┘
                       ▼
                 RESULT MERGE
                       │
                       ▼
                 ARCHITECTURE GATE
```

현재 Orchestration 설계에서도 Orchestrator는 사용자 요청을 읽고 필요한 Agent 팀을 구성하고 실행 순서를 결정하는 **팀장 역할**로 정의됩니다.

---

# 19.3 모든 요청을 먼저 Mission으로 바꿉니다

사용자가 예를 들어 이렇게 요청할 수 있습니다.

```text
"TCF Timeout 구조를 점검해줘."
```

사람에게는 단순한 문장이지만 Orchestrator는 이것을 실행 가능한 Mission으로 변환해야 합니다.

```text
Mission
─────────────────────────────

Goal
TCF Timeout Architecture 검증

System Scope
PDMG / pdmg-fw / pdmg-service

Architecture Scope
Framework / Timeout / Transaction

Source Required
YES

Runtime Required
필요 여부 판단

Expected Result
Current 구조
Rule
Gap
ADR 필요 여부
Gate 판정
```

현재 단계별 실행 프롬프트도 Mission 시작 시 **목표, System Scope, 대상 시스템/업무/ServiceId, 검증 범위, 기대 결과, Runtime 필요 여부**를 먼저 판단하도록 정의합니다.

---

# 19.4 Mission은 네 가지 유형으로 분류됩니다

현재 Orchestration 체계에서는 요청을 다음 네 종류로 분류합니다.

| Mission Type           | 의미                   | 예                             |
| ---------------------- | ---------------------- | ------------------------------ |
| **QUICK_CHECK**        | 좁은 범위의 빠른 확인  | 특정 ServiceId 구조 확인       |
| **VERTICAL_SLICE**     | 하나의 거래를 E2E 추적 | 화면→ServiceId→SQL→Runtime     |
| **DECISION_REVIEW**    | Architecture 선택 검토 | DeltaManager vs Spring Session |
| **RELEASE_VALIDATION** | 배포/Release Gate 검증 | HG90 후보 Release              |

이 분류가 중요한 이유는 **모든 요청에 같은 Agent와 같은 Gate를 돌리면 낭비가 크기 때문**입니다.

---

# 19.5 QUICK_CHECK와 RELEASE_VALIDATION은 완전히 다릅니다

예를 들어:

```text
"mgcoa9000S0 Handler가 어디인가?"
```

는 QUICK_CHECK입니다.

필요한 것은 대략:

```text
ServiceId
 → Dispatcher
 → Handler
 → Source Evidence
```

입니다.

반면:

```text
"이번 운영배포를 Architecture Baseline으로 승인해도 되는가?"
```

라면 RELEASE_VALIDATION입니다.

필요한 범위는:

```text
Document
Model
Source
Config
Rule
Build
Test
Security
Artifact Hash
Deployment
Runtime Evidence
Drift
GAP
ADR
Human Approval
```

까지 확장됩니다.

즉 Orchestration의 첫 번째 가치가 **작업범위를 정확히 조절하는 것**입니다.

---

# 19.6 Mission이 만들어지면 세 개의 기본 산출물이 생깁니다

현재 설계 기준은 다음입니다.

```text
MISSION.md

RUN-MANIFEST

EXECUTION-PLAN
```

역할은 다음과 같습니다.

| 산출물           | 역할                                   |
| ---------------- | -------------------------------------- |
| `MISSION.md`     | 왜 이 작업을 하는가                    |
| `RUN-MANIFEST`   | 어떤 Source/Agent/Gate를 사용할 것인가 |
| `EXECUTION-PLAN` | 어떤 순서로 실행할 것인가              |

즉 사용자의 자연어 요청이 여기서부터 **재현 가능한 Architecture Run**으로 바뀝니다.

---

# 19.7 그다음 Agent Team을 구성합니다

개념적으로 NSIGHT Agent Team은 다음처럼 보면 가장 쉽습니다.

```text
                   ORCHESTRATOR
                        │
      ┌─────────────────┼─────────────────┐
      │                 │                 │
      ▼                 ▼                 ▼
 Source Agent       Document Agent     Model Agent
      │                 │                 │
      └─────────────────┼─────────────────┘
                        │
             ┌──────────┼───────────┐
             ▼          ▼           ▼
        Rule Agent   Code Agent  Config Agent
             │          │           │
             └──────────┼───────────┘
                        ▼
                  Test / Runtime
                        │
             ┌──────────┼───────────┐
             ▼          ▼           ▼
         Drift Agent  GAP Agent   ADR Agent
             │          │           │
             └──────────┼───────────┘
                        ▼
                     Gate Agent
                        │
                        ▼
                  Architecture Board
```

이것은 현재 Orchestration 자료의 단계별 역할을 이해하기 쉽게 **Agent 관점으로 구조화한 표현**입니다. 원 자료의 핵심은 목표에 맞는 Agent만 차출하는 것입니다.

---

# 19.8 STEP 0 — Orchestrator

첫 번째 Agent는 사실 Orchestrator 자신입니다.

해야 할 일:

```text
사용자 요청 해석
     ↓
Mission Type 선정
     ↓
System Scope 결정
     ↓
Source 필요 여부
     ↓
Runtime 필요 여부
     ↓
필요 Agent 선정
     ↓
Gate Scope 결정
```

절대 하면 안 되는 것은:

```text
정보가 없는데 추정하여 Scope 확정
```

입니다.

현재 Mission 프롬프트 역시 확인되지 않은 정보는 `UNKNOWN`으로 유지하도록 요구합니다.

---

# 19.9 STEP 1 — Source Baseline Agent / G00

그다음은 Source입니다.

```text
Repository
Document
Configuration
Test
Runtime Evidence
```

를 조사합니다.

그리고:

```text
build/
bin/
.gradle/
target/
logs/
generated/
history/
duplicate/
```

같은 생성물·복제물을 현재 Source of Truth에서 분리합니다.

현재 G00 프롬프트도 Branch, Commit, Java/Spring/Gradle 기준, Module 목록과 Source/Config Inventory를 먼저 만들도록 정의합니다.

즉 첫 질문은:

> **“무엇을 분석했는가?”**

입니다.

---

# 19.10 이것이 왜 중요한가

예를 들어 같은 클래스가:

```text
src/
build/
backup/
history/
```

에 네 번 존재할 수 있습니다.

그런데 Agent가 아무 파일이나 읽고:

```text
"현재 구조입니다."
```

라고 하면 잘못된 Architecture Fact가 만들어집니다.

그래서:

```text
G00
Source Baseline
```

없이는 이후 결과를 믿을 수 없습니다.

앞서 Markdown 전체 점검에서도 물리 Markdown 16,639개 중 고유 본문은 3,348개 수준이고 대량 중복·생성물이 존재해, 저장소를 그대로 Source of Truth로 사용하는 것이 위험하다고 판정했습니다.

---

# 19.11 STEP 2 — Document Agent

Document Agent는 전략서·설계서·가이드 등을 읽습니다.

단순 Summary가 목적이 아닙니다.

문장의 상태를 분류해야 합니다.

```text
FACT
CONFIRMED
AS-IS
TO-BE
DECISION
PROPOSED
GAP
DEPRECATED
UNKNOWN
```

예:

```text
"CDC ≤ 30초"
→ TO-BE Candidate


"현재 application.yml은 timeout=5"
→ AS-IS / Evidence


"Spring Session JDBC를 적용한다"
→ Decision인가?
→ Proposed인가?
→ 확인 필요
```

이 상태 분류를 안 하면 문서의 제안문이 공식 Architecture Decision처럼 섞이게 됩니다.

---

# 19.12 STEP 3 — Model Agent

Document와 Source에서 Architecture Entity와 Relation을 추출합니다.

```text
System
Domain
Business
ServiceId
Component
DAO
Mapper
Table
Integration
Server
JVM
Policy
```

그리고 관계를 만듭니다.

```text
ServiceId
  → Handler
  → Facade
  → Service
  → DAO
  → Mapper
  → SQL
  → Table
```

17번에서 설명한 바로 그 **20-MODEL**입니다.

```text
Document
      ↓
Architecture Model
      ↓
Machine-readable 구조
```

현재 Closed Loop도 Document→Model→Code→Test→Runtime Evidence로 발전하도록 설계되어 있습니다.

---

# 19.13 STEP 4 — Rule / Conformance Agent

Model이 생기면:

```text
"정상 구조는 무엇인가?"
```

를 Rule로 만듭니다.

예:

```text
R1
Handler → DAO Direct 금지

R2
ServiceId → Dispatcher → Handler

R3
Private Key Browser 배포 금지

R4
Runtime Evidence 필수

DOMAIN
Cross-Domain DAO 직접 접근 금지

MSG
Header + DTO 분리
```

현재 PDMG Reference Rule도 `R1 Structural / R2 Framework / R3 Security / R4 Runtime-Operational` 네 그룹으로 시작합니다.

---

# 19.14 STEP 5 — Code / Config Agent

이제 실제 Source와 설정을 읽습니다.

예를 들어 Expected Model은:

```text
ServiceId
   ↓
Handler
   ↓
Facade
   ↓
Service
```

인데 Actual Source가:

```text
ServiceId
   ↓
Handler
   ↓
DAO
```

라면:

```text
MODEL ≠ CODE
```

가 됩니다.

설정도 마찬가지입니다.

```text
Model Timeout = 3 sec

Actual Config = 5 sec
```

이면 차이가 발견됩니다.

여기에서는 아직 “누가 틀렸다”고 결론 내리지 않습니다.

---

# 19.15 STEP 6 — Test Agent

다음은 Conformance Test입니다.

예:

```text
Rule
Handler → DAO Direct Call 금지
```

Static Test:

```text
Source Scan
    ↓
Direct Call Count = 0
    ↓
PASS
```

반면:

```text
Timeout 후 Connection 반환
```

같은 규칙은 Static Test로 증명할 수 없습니다.

따라서:

```text
Static Test
       +
Runtime Test
```

를 구분해야 합니다.

현재 Closed Loop 점검에서도 Document와 Code는 상당히 축적됐지만 **Test→Runtime Evidence 연결이 아직 가장 약한 영역**으로 평가되었습니다.

---

# 19.16 STEP 7 — Runtime Evidence Agent

Runtime이 필요한 Mission이라면 실제 실행증적을 가져와야 합니다.

예를 들어:

```text
RUN-P1200
```

이면:

```text
TPS
p95
CPU
Heap
GC
Thread
Hikari
DB Session
SQL
Error Rate
```

를 수집해야 합니다.

Timeout Mission:

```text
Timeout 발생
   ↓
Rollback
   ↓
Connection Return
   ↓
Thread Return
```

을 검증합니다.

DR Mission:

```text
Main Failure
   ↓
GSLB Switch
   ↓
DR Service
   ↓
DB Promotion
   ↓
Business Validation
   ↓
Failback
```

을 증명합니다.

즉 Runtime Agent의 역할은:

> **“설계가 실제로 그렇게 움직였다는 증거를 가져오는 것”**

입니다.

---

# 19.17 STEP 8 — Drift Agent

이제 Expected와 Actual을 비교합니다.

```text
Document ↔ Model

Model ↔ Code

Model ↔ Config

Code ↔ Runtime

Config ↔ Runtime

Test ↔ Runtime
```

차이가 있으면:

```text
DRIFT
```

가 됩니다.

Drift Agent는 해결책을 바로 적용하는 Agent가 아니라 **차이를 객관적으로 기록하는 Agent**라고 보는 것이 좋습니다.

---

# 19.18 STEP 9 — GAP / ADR Agent

Drift 결과를 분석합니다.

```text
DRIFT
  ↓
이것은 무엇인가?

┌──────────────┬───────────────┬─────────────┐
▼              ▼               ▼
문서 오류       Code Defect      Architecture GAP
                                  │
                                  ▼
                              Decision 필요?
                                  │
                           ┌──────┴──────┐
                           ▼             ▼
                          NO            YES
                           │             │
                           ▼             ▼
                          FIX           ADR
```

이 부분이 Agent 시스템에서 가장 조심해야 하는 영역입니다.

특히:

```text
Data Ownership
Transaction Boundary
Session
JWT
HA/DR
Capacity
Security Exception
```

같은 항목은 Agent가 자동 결정해서는 안 되고 Architecture Board로 넘겨야 합니다.

---

# 19.19 Agent는 Decision을 준비하고 사람은 결정합니다

예를 들어 Session 문제라면 Agent는 이렇게 준비할 수 있습니다.

```text
Problem
센터 장애 시 Session Continuity

Option A
DeltaManager

Option B
Spring Session JDBC

Option C
재로그인

Evidence
성능시험
네트워크
운영복잡도
DR

Risk
...
```

하지만 최종:

```text
Decision = B
```

를 내리는 것은 Architecture Board입니다.

즉:

```text
Agent
=
Decision Preparation


Human Architect
=
Decision Accountability
```

입니다.

이 구분이 매우 중요합니다.

---

# 19.20 STEP 10 — Gate Agent

모든 결과를 모아 Gate를 판정합니다.

```text
Architecture Rule
        ↓
Static Test
        ↓
Runtime Evidence
        ↓
Open GAP
        ↓
ADR
        ↓
Exception
        ↓
Approval
```

결과:

```text
PASS

CONDITIONAL PASS

HOLD

REJECT
```

가 됩니다.

여기에서도 Agent가 근거 없이:

```text
"대체로 괜찮으니 PASS"
```

해서는 안 됩니다.

Gate는 Evidence 기반이어야 합니다.

---

# 19.21 Execution Board가 필요한 이유

Agent가 여러 개가 되면 현재 누가 무엇을 하는지 관리해야 합니다.

그래서 Orchestration System에는 **Execution Board** 개념이 중요합니다. 앞서 구성한 Orchestration System도 `Orchestrator + Agent Team + Execution Board` 구조로 만들어졌습니다.

개념적으로:

| Task         | Agent             | Input        | Status  | Gate | Output      |
| ------------ | ----------------- | ------------ | ------- | ---- | ----------- |
| Source Scan  | Source Agent      | Repo         | DONE    | G00  | Inventory   |
| Doc Analysis | Doc Agent         | 전략서       | DONE    | G10  | Fact Matrix |
| Model        | Model Agent       | Doc+Source   | RUNNING | G20  | Model       |
| Rule Test    | Conformance Agent | Model+Source | WAIT    | G40  | Result      |
| Runtime      | Runtime Agent     | Test Env     | BLOCKED | G50  | Evidence    |
| GAP/ADR      | Governance Agent  | Drift        | WAIT    | G70  | GAP/ADR     |

이렇게 하면 Orchestrator가 현재 전체 상태를 관리할 수 있습니다.

---

# 19.22 Agent를 항상 동시에 돌리면 안 됩니다

예를 들어:

```text
"ServiceId 하나의 DAO까지 추적"
```

하는데:

```text
DR Agent
Capacity Agent
JWT Agent
Migration Agent
```

까지 돌릴 필요는 없습니다.

그래서 현재 설계가 강조하는 것이:

> **50개 Agent를 항상 동시에 돌리는 것이 아니라 Mission 목적에 맞는 Agent만 차출한다.**

입니다.

이것은 비용뿐 아니라 정확도에도 중요합니다.

Agent가 많을수록 불필요한 정보가 섞일 수 있기 때문입니다.

---

# 19.23 VERTICAL_SLICE Mission이 가장 중요한 이유

NSIGHT에서 특히 강력한 Mission은 **VERTICAL_SLICE**입니다.

예:

```text
"고객통합조회 ServiceId 하나를
끝까지 검증하라."
```

그러면 Orchestrator는:

```text
Requirement
 ↓
Screen
 ↓
ServiceId
 ↓
Handler
 ↓
Facade
 ↓
Service
 ↓
DAO
 ↓
Mapper
 ↓
SQL
 ↓
Table
 ↓
WAR
 ↓
JVM
 ↓
Server
 ↓
Test
 ↓
Runtime
 ↓
Evidence
```

를 한 줄로 추적합니다.

17번에서 만든 Traceability와 Orchestration이 여기서 직접 만납니다.

---

# 19.24 VERTICAL_SLICE가 PASS하면 무엇이 좋은가

전체 시스템 10만 파일을 모두 읽기 전에:

```text
한 개 ServiceId
```

를 완전히 통과시킬 수 있습니다.

그 과정에서:

```text
Model 문제
Naming 문제
TX 문제
Timeout 문제
Logging 문제
SQL 문제
Deployment 문제
Runtime Trace 문제
```

를 한 번에 확인할 수 있습니다.

그다음 같은 Pattern을 다른 ServiceId에 확장합니다.

```text
Reference Slice
      ↓
Rule 추출
      ↓
자동검사
      ↓
전체 확대
```

이 방식이 대형 프로젝트에서는 매우 효과적입니다.

---

# 19.25 RELEASE_VALIDATION은 가장 무거운 Mission입니다

Release 후보가 들어오면:

```text
Source
 ↓
Model
 ↓
Conformance
 ↓
Build
 ↓
Test
 ↓
Security
 ↓
Artifact Hash
 ↓
Deploy
 ↓
Runtime
 ↓
Drift
 ↓
Critical GAP
 ↓
ADR
 ↓
Approval
 ↓
HG90
```

까지 봅니다.

즉 RELEASE_VALIDATION은 사실 **Architecture Closed Loop 전체 실행**입니다.

현재 Orchestration 마스터 프롬프트도 `Document → Model → Code → Test → Runtime Evidence → Drift → GAP/ADR → Baseline`을 실제 실행 사이클로 구성합니다.

---

# 19.26 Orchestration 실행 디렉터리의 의미

현재 실행체계는 Run별 작업공간을 둡니다.

개념적으로:

```text
RUN/
│
├─ 00-SOURCE
│
├─ 10-DOCUMENT
│
├─ 20-MODEL
│
├─ 30-CONFORMANCE
│
├─ 40-TEST
│
├─ 50-RUNTIME
│
├─ 60-DRIFT
│
├─ 70-GAP-ADR
│
├─ 80-APPROVAL
└─ 90-BASELINE
```

이 구조가 중요한 이유는 **한 Run의 모든 Evidence가 같은 실행 컨텍스트에 남기 때문**입니다.

현재 Closed Loop 마스터 프롬프트도 Run 단위로 Source, Document, Model, Rule, Test, Drift, GAP/ADR을 분리하고 Gate를 진행하도록 구성되어 있습니다.

---

# 19.27 ServiceId는 Orchestration의 공통 Key가 됩니다

예를 들어 Orchestrator에게:

```text
mgcoa9000S0
```

을 주면 여러 Agent가 동일한 Key를 중심으로 움직입니다.

```text
Source Agent
→ Handler 찾기


Model Agent
→ Relation 찾기


Rule Agent
→ 적용 Rule 찾기


Runtime Agent
→ Trace 찾기


Drift Agent
→ Expected/Actual 비교


GAP Agent
→ 관련 GAP 찾기
```

즉 ServiceId는 Application Architecture뿐 아니라 **Agent 협업을 위한 공통 업무키** 역할까지 하게 됩니다.

---

# 19.28 중요한 원칙 — Agent끼리 사실을 만들어내면 안 됩니다

예를 들어 Source Agent가:

```text
Timeout = 5 sec
```

를 찾았다고 합시다.

Document Agent는:

```text
Timeout = 3 sec
```

를 찾았습니다.

Orchestrator가:

```text
"중간값 4초로 하자"
```

라고 해서는 안 됩니다.

정확한 결과는:

```text
Document = 3 sec
Source = 5 sec

        ↓

DRIFT

        ↓

GAP / ADR
```

입니다.

즉 Orchestration의 목적은 **충돌을 없애는 것**이 아니라:

> **충돌을 정확하게 드러내고 통제 가능한 Decision으로 만드는 것**

입니다.

---

# 19.29 Reference Agent와 Target Agent도 분리하는 것이 중요합니다

특히 PDMG와 NSIGHT 관계에서 중요합니다.

```text
PDMG
 ↓
Reference Analysis

          ≠

NSIGHT Target
 ↓
Target Analysis
```

그리고:

```text
Reference Model
       ↕
Target Model
       ↓
Conformance
```

으로 비교해야 합니다.

PDMG Source에서 발견된 구조를 Target Code에 자동 강제하면 안 됩니다.

앞선 인수인계 자료에서도 **NSIGHT TCF 전체 기준과 PDMG AS-IS를 동일 Baseline으로 합치면 안 된다**고 명시되어 있습니다.

---

# 19.30 Orchestration의 최종 목표는 자동 문서작성도 아닙니다

최종 목표는:

```text
Architecture Analysis Automation
```

보다 훨씬 큽니다.

정확하게는:

```text
Architecture Control Automation
```

입니다.

즉:

```text
설계가 맞는가?
 ↓
코드가 맞는가?
 ↓
설정이 맞는가?
 ↓
실제 실행도 맞는가?
 ↓
달라졌는가?
 ↓
Decision이 필요한가?
 ↓
새 Baseline으로 승격 가능한가?
```

를 지속적으로 관리하는 것입니다.

# 19.31 Closed Loop와 Orchestration의 관계

둘은 같은 개념이 아닙니다.

```text
Closed Loop
=
무엇을 반복 검증해야 하는가


Orchestration
=
그 반복 검증을 누가 어떤 순서로 수행하는가
```

합치면:

```text
                       USER
                        │
                        ▼
                  ORCHESTRATOR
                        │
                        ▼
                     MISSION
                        │
                        ▼
                Agent Team 구성
                        │
                        ▼
                   SOURCE G00
                        │
                        ▼
                   DOCUMENT
                        │
                        ▼
                     MODEL
                        │
                        ▼
                      RULE
                        │
                        ▼
                 CODE / CONFIG
                        │
                        ▼
                      TEST
                        │
                        ▼
                    RUNTIME
                        │
                        ▼
                     DRIFT
                        │
                        ▼
                  GAP / ADR
                        │
                        ▼
                HUMAN DECISION
                        │
                        ▼
                      GATE
                        │
               ┌────────┴────────┐
               ▼                 ▼
             HOLD               PASS

               │                 │

```

이것이 NSIGHT Architecture Orchestration의 전체 구조입니다.

# 19.32 사람과 Agent의 책임경계를 명확히 해야 합니다

| 영역             | Agent 중심 | Human 중심     |
| ---------------- | ---------- | -------------- |
| Source Scan      | O          | 검증           |
| Document 비교    | O          | 중요 의미 확인 |
| Model 생성       | O          | Model 승인     |
| Static Rule Test | O          | Rule 승인      |
| Traceability     | O          | Owner 검증     |
| Drift 탐지       | O          | 중요도 판단    |
| GAP 후보         | O          | GAP 확정       |
| ADR 대안분석     | O          | **결정**       |
| Security Risk    | 보조       | **책임 판단**  |
| Data Ownership   | 보조       | **결정**       |
| Exception        | 보조       | **승인**       |
| Baseline 승격    | 검증       | **최종 승인**  |

이 경계를 지켜야 Agent 시스템이 아키텍트를 대체하는 것이 아니라 **아키텍트의 판단력을 증폭시키는 시스템**이 됩니다.

# 19.33 현재 Orchestration은 어디까지 와 있는가

기존 작업에서는 이미:

```text
Architecture Closed Loop Master Prompt
Orchestrator
Agent Team
Execution Board
Mission Type
G00~HG90 Gate
Workspace
Source/Model/Rule/Test 구조
Pilot 실행체계
```

까지 실제 작업공간 형태로 구성한 바 있습니다.

그리고 단계별 Agent 실행용 Prompt도 **Mission → Bootstrap/G00 → 이후 Gate** 식으로 1:1 연결하도록 정의되어 있습니다.

따라서 현재 단계는 개념만 존재하는 상태는 아닙니다.

다만 18번과 마찬가지로 **Runtime Evidence, Full Model SoT, Critical ADR Closure까지 자동으로 닫힌 완전한 운영 Closed Loop는 아직 완료되지 않은 상태**입니다. 기존 전수점검에서도 전체 Closed Loop는 `HOLD`로 평가되었습니다.

# 19.34 Orchestrator의 가장 중요한 출력은 “답변”이 아닙니다

좋은 Orchestrator의 결과는:

```text
"분석해보니 이런 것 같습니다."
```

가 아닙니다.

최종적으로는:

```text
Mission
Source Baseline
Architecture Model
Rule Result
Runtime Evidence
Drift
GAP
ADR Candidate
Gate Result
Next Action
```

이 남아야 합니다.

즉 한 번의 대화가 **Architecture Repository의 다음 상태**를 만들어야 합니다.

# 19.35 한 문장으로 정리하면

**NSIGHT Architecture Orchestration System은 사용자의 Architecture 목표를 Mission으로 변환하고, 필요한 Source·Document·Model·Rule·Code·Test·Runtime·Drift·GAP/ADR Agent를 동적으로 구성하여 Gate 순서대로 실행한 뒤, 자동화 가능한 검증은 기계가 수행하고 Architecture Trade-off와 Risk Acceptance는 사람이 결정하여 최종적으로 검증된 Architecture Baseline을 지속적으로 발전시키는 실행체계입니다.**

그리고 1번부터 19번까지의 관계를 압축하면 이제 이렇게 됩니다.

```text
1~14
Architecture를 정의

15
Rule로 변환

16
Gate로 통제

17
Model/Traceability로 구조화

18
Drift/GAP/ADR로 변화관리

19
Orchestrator + Agent로
전체 과정을 실행
```

**20번째 단계에서는 이 모든 것을 실제 프로젝트 수행체계로 연결해 `Architecture Work Breakdown Structure(WBS)`를 설명하는 것이 가장 자연스럽습니다.** 즉 `Vision → Big Picture → Logical → Physical → Mechanism → Runtime → Rule → Model → Gate → Baseline`을 **실제 Task, 담당 AA/DA/TA/IA/SA, 입력자료, 산출물, 선후행 관계, 완료조건**으로 바꾸어 “누가 언제 무엇을 만들어야 하는가”까지 내려가겠습니다.
