맞습니다. 다시 전략 브리핑, 발표자료, 임원 발표 스크립트, 설계전략 자료를 중심으로 재확인해 보니, 앞선 설명은 **NSIGHT 전체 아키텍처 중 `Mechanism/Application Framework` 쪽에 지나치게 치우쳐 있었습니다.**

특히 `TCF → Dispatcher → Handler → Service → DAO`는 NSIGHT의 **애플리케이션 구현 메커니즘 중 일부**이지, NSIGHT 차세대 정보계의 전체 구축전략을 대표하는 것은 아닙니다. 전략문서의 중심은 훨씬 위에 있습니다.

NSIGHT 전략 브리핑 자체가 전체를 **“Scalable · Resilient · Data-Centric”**으로 정의하고, `Vision → Big Picture → Logical → Physical → Mechanism → Runtime`의 6단계로 구축하도록 되어 있습니다.

# NSIGHT 아키텍처를 다시 정의하면

핵심은 다음 흐름입니다.

```text
                  NSIGHT 구축전략

       "창고에서 살아있는 플랫폼으로"
                       │
                       ▼
        Scalable · Resilient · Data-Centric
                       │
                       ▼
              Vision / 5대 NFR
                       │
                       ▼
              책임과 경계의 분리
                       │
                       ▼
              5대 서비스 도메인
                       │
                       ▼
          Logical Policy 강제화
                       │
                       ▼
           Hybrid Physical 구조
                       │
                       ▼
          현실적인 HA / DR 전략
                       │
                       ▼
             5대 실행 Mechanism
                       │

                       │

                       │

                       │

```

이것이 전략문서를 기준으로 본 **NSIGHT 전체 Architecture Story**입니다.

---

# 1. 출발점은 “시스템 교체”가 아닙니다

전략자료의 첫 메시지는 상당히 분명합니다.

기존 정보계를 단순히 새 DW로 교체하는 사업이 아니라:

> **데이터를 저장하는 창고에서, 데이터가 흐르고 반응하고 판단하는 살아있는 플랫폼으로 전환한다.**

는 것입니다.

발표자료 4쪽에서도 AS-IS와 TO-BE를 이렇게 대비합니다.

| 기존 정보계                | 차세대 NSIGHT            |
| -------------------------- | ------------------------ |
| 야간 Batch 후 익일 데이터  | CDC 기반 Near Real-time  |
| 정해진 시간에 마케팅       | Kafka 기반 1초 이내 반응 |
| 단순 DW                    | 실시간 의사결정 플랫폼   |
| 서버별 독립 운영           | Domain 분리 + 장애 격리  |
| 분석 쿼리로 운영 성능 영향 | RDW/ADW 분리             |

즉 이 프로젝트의 첫 번째 전략은 **“Batch를 빠르게 하는 것”이 아니라 정보계의 역할 자체를 바꾸는 것**입니다.

---

# 2. 전체 구축전략의 세 축은 Scalable · Resilient · Data-Centric입니다

전략보고서의 결론은 세 단어로 압축됩니다.

```text
                  NSIGHT

       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
   Scalable     Resilient    Data-Centric
   확장 가능      강건함       데이터 중심
```

### Scalable

서비스 영역은 VM 기반 **Scale-Out**, 데이터 영역은 Exadata의 노드·랙 기반 병렬 확장을 사용합니다. 모든 영역에 같은 확장방식을 쓰지 않습니다.

### Resilient

이론적으로 가장 화려한 구조보다 **실제로 운영 가능한 강건함**을 선택합니다. DR에서도 이 철학이 그대로 나타납니다.

### Data-Centric

애플리케이션이나 서버가 중심이 아니라 **데이터가 어떻게 발생하고, 이동하고, 가공되고, 실행과 판단으로 이어지는가**가 전체 구조를 결정합니다. 전략문서의 최종 목표 역시 데이터 중심 경영입니다.

---

# 3. Big Picture의 핵심은 “5대 플랫폼 구축”입니다

전략 문서에서 NSIGHT는 5개의 서비스 도메인으로 나뉩니다.

| 서비스 도메인        | 전략적 책임                               |
| -------------------- | ----------------------------------------- |
| **데이터플랫폼**     | RDW/ADW, CDC/Kafka/ETL 등 데이터 기반     |
| **마케팅플랫폼**     | 고객 행동에 실시간 반응하는 실행 두뇌     |
| **BI 포탈**          | Self-BI·AI/NLP 기반 의사결정 공간         |
| **데이터거버넌스**   | 데이터 표준·품질·메타 관리                |
| **IT서비스 및 지원** | SSO, 배치, APM, 로그, DevOps 등 운영 기반 |

발표자료의 Big Picture는 이를 다시 **세 가지 통제 정책**과 연결합니다.

```text
5대 Service Domain
        │
        ├─ 규격 표준 통제
        ├─ Interface 경계 통제
        └─ Resource 분리 통제
```

즉 Big Picture의 목적은 서버나 제품 박스를 예쁘게 배치하는 것이 아니라,

> **“책임은 공간에 고정하고, 연결은 경계에서 통제한다.”**

입니다. 발표자료 10쪽에서도 `Channel → Interface → Data Platform → Analytics → Service` End-to-End 흐름과 5대 도메인을 이 구조로 표현합니다.

---

# 4. 그래서 NSIGHT 구축의 핵심전략은 “Boundary First”입니다

전략자료를 다시 읽어보면 실제로 가장 반복되는 원칙은 **분리**입니다.

```text
업무 책임 분리
데이터 책임 분리
실시간 / 분석 분리
온라인 / 배치 분리
AP / ETL 분리
RDW / ADW 분리
CDC / Kafka 역할 분리
Main / DR 역할 분리
```

즉 NSIGHT는 많은 기술을 통합하는 아키텍처이면서 동시에,

> **서로 다른 성격의 것을 의도적으로 분리하는 아키텍처**

입니다.

이것이 앞서 제가 TCF 중심으로 설명하면서 충분히 살리지 못한 가장 중요한 부분입니다.

---

# 5. 논리 구축전략 — “무엇을 허용하고 무엇을 금지하는가”

Logical Architecture는 제품 선택 단계가 아닙니다.

전략문서에서는 이를 **정책 수립**이라고 정확히 정의합니다.

대표 정책을 정리하면 다음과 같습니다.

| 정책         | NSIGHT 전략                  |
| ------------ | ---------------------------- |
| Domain       | 기능/책임별 독립 Domain      |
| Data         | 지정된 데이터 흐름 강제      |
| Integration  | P2P 직접연계 금지            |
| Online/Batch | 완전 분리                    |
| RDW/ADW      | 운영/분석 책임 분리          |
| Protocol     | HTTP/JSON 표준               |
| Trace        | GUID 기반 End-to-End 추적    |
| Resource     | 기능별 독립 서버와 자원 격리 |

특히 Integration은 강합니다.

```text
금지

System A
   ───── 직접 DB Link ─────▶ System B

System A
   ───── 임의 P2P ────────▶ System B
```

대신:

```text
API 거래       → CruzAPIM
파일           → FOS
대외 파일      → MCA + MFT
실시간 DB 변화 → CDC
Event          → Kafka
계정계 내부    → GSE
대용량 처리    → DataStage
```

처럼 **연계 목적마다 승인된 길을 지정**합니다.

따라서 `ServiceId Dispatcher` 같은 것은 이 상위 Integration/Standardization 전략이 Application 내부로 내려온 하나의 구현형태라고 보는 것이 정확합니다.

---

# 6. 데이터 구축전략이 NSIGHT의 가장 중요한 전략입니다

전략자료에는 매우 중요한 질문이 있습니다.

> **“FAST와 DEEP이라는 서로 다른 흐름을 하나의 창고에 담을 수 있는가?”**

결론은 **NO**입니다.

이 결정 때문에 RDW와 ADW를 물리적으로 분리합니다.

```text
                  DATA PLATFORM

          FAST                     DEEP
           │                        │
           ▼                        ▼
     ┌──────────┐             ┌──────────┐
     │   RDW    │             │   ADW    │
     │Real-time │             │Analytics │
     └──────────┘             └──────────┘
           │                        │
      실시간 서비스              BI / 분석
      마케팅 대응               대량 집계
```

발표자료 26쪽에서도 RDW와 ADW를 **Oracle Exadata 기반 독립 물리 장비**로 분리하고, 목적을 `성능 간섭 차단`, `장애 전이 방지`, `독립 SLA 확보`로 정의합니다.

이것은 단순 DB 설계가 아닙니다.

> **NSIGHT 전체 시스템의 Fault Isolation과 Performance Isolation 전략**

입니다.

---

# 7. 물리 구축전략은 Hybrid입니다

이 부분도 앞서 제가 충분히 설명하지 않았습니다.

NSIGHT는 모든 것을 Cloud VM으로 만들지도 않고, 모든 것을 Bare Metal로 만들지도 않습니다.

전략은:

> **“속도는 전용자원으로, 유연성은 클라우드로.”**

입니다.

구체적으로는:

| 영역                    | 물리 구축 전략      | 이유                    |
| ----------------------- | ------------------- | ----------------------- |
| RDW / ADW               | Oracle Exadata      | 고성능 I/O, 병렬 확장   |
| 마케팅 / BI / Online AP | NH Private Cloud VM | Scale-Out, 유연성       |
| ETL / IMDG              | Bare Metal          | 가상화 오버헤드 최소화  |
| CDC 중계                | UNIX                | 안정적인 원천 변경 캡처 |

즉:

```text
                  HYBRID

       성능 중심               탄력성 중심

        Exadata              Private Cloud VM
       RDW / ADW             Marketing / BI
            │                      │
            │               Horizontal Scale-Out
            │
    Bare Metal
     ETL / IMDG

    UNIX
    CDC Relay
```

입니다.

따라서 NSIGHT Physical Architecture는 “어떤 제품이 좋은가?”보다 **업무 특성에 맞는 실행 공간을 다르게 선택하는 전략**입니다.

---

# 8. DR 전략도 “현실적인 강건함”입니다

전략문서는 DB까지 Main/DR 양쪽에서 Active-Active로 쓰는 이론적 구조를 선택하지 않습니다.

DB Active-Active는 데이터 충돌, 정합성, 운영복잡도를 높인다고 판단합니다.

선택한 방향은:

```text
                       GSLB
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
       Main센터                       DR센터

      AP : Active                   AP : Active
      DB : Active                   DB : Standby
```

입니다.

이 전략의 철학은 매우 중요합니다.

> **Availability의 목표는 “가장 복잡한 구조”가 아니라 “실제로 장애 때 작동하는 구조”다.**

즉 Resilient라는 단어를 단순 이중화가 아니라 **운영 가능성까지 포함한 회복탄력성**으로 정의합니다.

---

# 9. Mechanism도 TCF만을 뜻하지 않습니다

제가 앞서 가장 많이 좁혀 설명했던 부분입니다.

전략 브리핑의 Mechanism은 **5대 실행 메커니즘**입니다.

| Mechanism               | 내용                                       |
| ----------------------- | ------------------------------------------ |
| ① 규격 표준화           | HTTP/JSON, 표준 전문, GUID                 |
| ② Framework 통일        | NH Cloud Framework, WebTopSuite, DataStage |
| ③ Integration 통제      | No P2P, 승인된 연계 경로                   |
| ④ Data Transport 이원화 | CDC / Kafka / FOS 역할 분리                |
| ⑤ 대용량 경로 최적화    | ADW + DataStage 전용 처리                  |

발표자료 21쪽에서도 정확히 이 5개를 “설계 의도를 실제 시스템에서 강제화하는 실행 수단”이라고 정의합니다.

그러므로:

```text
NSIGHT Mechanism
   │
   ├─ Protocol
   ├─ Standard Message
   ├─ Framework
   ├─ Integration
   ├─ CDC
   ├─ Kafka
   ├─ FOS
   ├─ DataStage
   └─ Application Framework
            │
            └─ TCF / ServiceId / Dispatcher ...
```

로 보는 것이 맞습니다.

**TCF는 전체 Mechanism 안의 Application Runtime Mechanism입니다.**

---

# 10. Runtime의 핵심은 FAST / DEEP 이중트랙입니다

이 또한 소스 Runtime보다 훨씬 상위 개념입니다.

```text
FAST
고객 행동
   ↓
Kafka
   ↓
Marketing Rule Engine
   ↓
Real-time Offering
   ↓
1초 이내 반응
```

그리고:

```text
DEEP
원천 DB
   ↓
CDC
   ↓
RDW
   ↓
DataStage
   ↓
ADW
   ↓
BI / Analytics
   ↓
경영 판단
```

전략문서에서는 이를 **“실시간과 분석의 절대 격리”**라고 표현합니다. 분리를 통해 성능 보호, 독립 확장, 장애 격리를 동시에 확보합니다.

따라서 NSIGHT Runtime Architecture의 본질은 Tomcat Thread가 아닙니다.

> **FAST와 DEEP이라는 서로 다른 비즈니스 흐름이 실제 운영에서 각각의 SLA로 동작하는지를 검증하는 것**

이 먼저입니다.

Tomcat/Hikari/TCF/SQL은 그 FAST 또는 Online Runtime을 구현하고 검증하는 상세 하위항목입니다.

---

# 11. 데이터플랫폼 → 마케팅플랫폼 → BI포탈의 전략적 연결

전략자료의 아주 중요한 부분입니다.

```text
          DATA
           │
           ▼
    데이터플랫폼
      "기초공사"
           │
           ▼
    마케팅플랫폼
     "반응하는 두뇌"
           │
           ▼
       BI 포탈
    "의사결정 공간"
```

### 데이터플랫폼

> **데이터는 틀리지 않는다는 신뢰를 생산**

RDW/ADW와 데이터 흐름을 책임집니다.

### 마케팅플랫폼

기존의 사후 Batch Marketing에서 벗어나 **Real-time Reaction Brain**으로 전환합니다.

Customer Single View와 Kafka Event Engine이 핵심 두 축입니다.

### BI 포탈

단순 조회 시스템이 아니라 **AI가 지원하는 자율적 의사결정 공간**입니다.

Self-BI, AI/NLP 자연어 질의, Reporting 표준화를 통해 “즉시 판단”을 지원합니다. 발표자료 30쪽에서도 이 3대 혁신을 명확히 정의합니다.

즉 NSIGHT의 비즈니스 흐름은:

```text
데이터가 정확하게 흐른다
          ↓
고객 행동에 즉시 반응한다
          ↓
조직이 즉시 판단한다
```

입니다.

이것이 전략문서의 **Data → Reaction → Decision** 구조입니다.

---

# 12. 구축이 끝이 아니라 유지관리까지 아키텍처입니다

전략설명서의 13장은 매우 중요합니다.

> **“아키텍처의 완성은 구축이 아니라 유지관리에서 결정난다.”**

라고 정의합니다.

구조는:

```text
             Standardization

 Interface
     ↕
 Data Standard
     ↕
 Application Standard
     ↕
 Development Standard

             +

             DevOps

 GitLab
   ↓
GitLab Runner
   ↓
 DEV / TEST
   ↓
 eCAMS
   ↓
 PROD
```

입니다.

발표자료 32쪽에서도 Interface/Data/Application 표준과 GitLab, GitLab Runner, eCAMS, IaaS 환경 일관성을 하나의 **“지속 가능한 Engineering Factory”**로 정의합니다.

즉 표준화의 목적은 문서를 만드는 것이 아닙니다.

> **사람의 숙련도 대신 구조가 품질을 보장하게 만드는 것**

입니다.

                          │

# 가장 중요한 정정

앞으로 NSIGHT를 설명할 때는 **다음 순서가 맞습니다.**

> **① 사업·비즈니스 전환 전략 → ② 데이터 중심 구축전략 → ③ 책임·경계 전략 → ④ Logical 정책 → ⑤ Hybrid Physical 전략 → ⑥ HA/DR 전략 → ⑦ Integration/Data/Framework Mechanism → ⑧ FAST/DEEP Runtime → ⑨ 표준·DevOps 유지관리 → 마지막에 Application/TCF 상세 구현**

입니다.

즉 제가 앞서 설명했던:

```text
TCF
→ Dispatcher
→ Handler
→ Service
→ DAO
```

는 전체 NSIGHT에서 보면 아래 위치에 있습니다.

```text
NSIGHT Strategy
   ↓
Big Picture
   ↓
Logical
   ↓
Physical
   ↓
Mechanism
   ↓
Application Framework
   ↓
TCF
   ↓
ServiceId
   ↓
Dispatcher / Handler / Service / DAO
```

**이제부터는 이 상위 전략 구조를 기준축으로 놓고, TCF·소스·WAS·JWT·용량산정은 그 전략을 실제로 구현하는 하위 아키텍처로 연결해서 설명하는 것이 정확합니다.**
