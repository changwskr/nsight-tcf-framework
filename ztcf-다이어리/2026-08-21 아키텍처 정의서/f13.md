좋습니다. 이제 **13번째 설명 — NSIGHT Runtime Architecture**로 진행하겠습니다.

앞에서 `Vision → Big Picture → Logical → Physical → HA/DR → Mechanism`까지 만들었습니다. Runtime은 단순히 마지막 그림을 하나 더 그리는 단계가 아닙니다. 전략 정리본에서는 **논리·물리·메커니즘이 실제 비즈니스 시나리오에서 살아 움직이는지 확인하는 아키텍처의 완성 지점**이라고 정의합니다.

# 13. NSIGHT Runtime Architecture

## 13.1 Runtime은 “설계”보다 “증명”에 가깝습니다

6단계를 다시 놓아보겠습니다.

```text
Vision
  │  무엇을 달성할 것인가
  ▼
Big Picture
  │  어떤 책임과 공간인가
  ▼
Logical
  │  무엇을 허용/금지할 것인가
  ▼
Physical
  │  실제 어디에 배치할 것인가
  ▼
Mechanism
  │  어떤 실행규칙으로 강제할 것인가
  ▼
Runtime
     실제로 그렇게 동작하는가?
```

발표자료에서도 정확히:

> **논리 설계 + 물리 설계 = 메커니즘 / 메커니즘 검증 = 런타임**

이라고 표현합니다.

따라서 Runtime에서 가장 중요한 질문은 이것입니다.

```text
"우리가 아키텍처 문서에 써놓은 이야기가
실제 요청·부하·장애 상황에서도 사실인가?"
```

---

# 13.2 Runtime은 두 레벨로 봐야 합니다

NSIGHT 자료를 전체적으로 보면 Runtime에는 사실 두 가지 의미가 같이 있습니다.

```text
                  RUNTIME ARCHITECTURE

             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
     Business Runtime          Engineering Runtime
             │                         │
       FAST / DEEP              Transaction / Thread
       실제 데이터 흐름          DB / Pool / Timeout
       고객 반응 / 분석          Failure / DR / Trace
```

전략 브리핑에서 직접 설명하는 Runtime은 주로 **FAST/DEEP Business Runtime**입니다.

현재 프로젝트에서 후속으로 발전시킨 것은 여기에서 더 내려간:

> **Runtime Evidence Architecture**

입니다.

즉 `FAST가 1초라고 썼다`에서 끝나는 것이 아니라 **실제로 1초 안에 처리된 Metric과 Trace가 있는가**까지 보려는 것입니다. 현재 Vision/NFR도 Runtime Evidence가 없는 항목은 최종 PASS를 금지하도록 정의합니다.

---

# 13.3 첫 번째 Runtime — FAST

FAST는 NSIGHT에서 가장 중요한 실시간 Business Runtime입니다.

```text
                 FAST RUNTIME

고객
 │
 │ Click / Search / Action
 ▼
Mobile / Channel
 │
 ▼
Event Capture
 │
 ▼
Kafka
 │
 ▼
Marketing Rule Engine
 │
 ▼
Decision
 │
 ▼
Realtime Offering
 │
 ▼
Customer
```

전략자료의 목표는 **이벤트 처리와 오퍼링 실행 1초 이내**입니다. 또한 Event-Driven, DB 비의존 처리, 경량화를 핵심 조건으로 정의합니다.

여기서 핵심은 단순히 Kafka를 사용한다는 것이 아닙니다.

```text
Customer Event
      ↓
Kafka
      ↓
Rule
      ↓
Offering
```

이라는 **고속도로 자체가 DB 저장경로와 독립적**이어야 한다는 것입니다.

---

# 13.4 FAST에서 무엇을 검증해야 하는가

문서에는:

```text
1초 이내
```

라고 적을 수 있습니다.

Runtime에서는 실제로:

```text
T0 = 고객 행동 발생
T1 = Event Collector 수신
T2 = Kafka Publish
T3 = Consumer 수신
T4 = Rule Decision
T5 = Offering 실행

T5 - T0 ≤ 1 sec ?
```

를 측정해야 합니다.

그리고 1초를 초과했다면:

```text
Collector?
Kafka?
Consumer Lag?
Rule Engine?
DB Dependency?
외부 Offering Interface?
```

어디에서 시간이 소요됐는지 추적할 수 있어야 합니다.

이것이 **Observability가 Runtime Architecture의 일부인 이유**입니다.

---

# 13.5 FAST에서 가장 중요한 검증 — DB 비의존성이 실제인가

전략에서는 FAST를 명확하게 **DB 비의존 처리**라고 정의합니다.

따라서 실제 Runtime이:

```text
Kafka
  ↓
RDW INSERT
  ↓
RDW Polling
  ↓
Realtime Engine
  ↓
Offer
```

라면 반드시 확인해야 합니다.

왜냐하면 이것은:

```text
Event Fast Path
        ↓
DB Dependency
```

가 되기 때문입니다.

반대로 전략에 가장 잘 맞는 형태는:

```text
                Kafka Event
                    │
          ┌─────────┴──────────┐
          │                    │
          ▼                    ▼
 FAST Decision            Async Persistence
 Rule / Context                 │
          │                     ▼
          ▼                    RDW
       Offering
```

입니다.

이 부분은 앞에서 발견했던 마케팅플랫폼의 중요한 Architecture Decision Point와 동일합니다.

---

# 13.6 두 번째 Runtime — DEEP

DEEP은 FAST와 목적이 완전히 다릅니다.

```text
                   DEEP RUNTIME

계정계 / Source DB
        │
        ▼
       CDC
        │
        ▼
   CDC Relay
        │
        ▼
       RDW
        │
        ▼
 DataStage / ETL
        │
        ▼
       ADW
        │
        ▼
 BI / OLAP / Analytics
        │
        ▼
경영 판단 / Risk / Reporting
```

DEEP의 목적은 **가장 빠른 응답이 아니라 정확성과 안정성, 깊은 분석**입니다. 전략자료는 이를 FAST와 엄격히 분리하고 `CDC → RDW → DataStage → ADW → BI` 경로로 정의합니다.

---

# 13.7 FAST와 DEEP의 중요한 차이

| 구분        | FAST                 | DEEP                  |
| ----------- | -------------------- | --------------------- |
| 목적        | 즉시 반응            | 깊은 분석             |
| Trigger     | 고객/업무 Event      | Source 데이터 변화    |
| 핵심 기술   | Kafka                | CDC + DataStage       |
| 주요 데이터 | Event / Context      | 대량 데이터           |
| 중심 SLA    | **1초**              | Freshness / Batch SLA |
| 저장 의존   | 최소화               | 데이터 저장/가공 중심 |
| 대표 소비자 | Marketing            | BI / Analytics        |
| 확장방식    | Event 처리 Scale-Out | ETL/DB 병렬 확장      |

그리고 전략의 가장 중요한 문장은:

> **“FAST와 DEEP은 절대 섞지 않는다.”**

입니다.

발표자료에서는 이 분리를 통해 **성능 보호 + 독립 확장 + 장애 격리**를 얻는다고 명시합니다.

---

# 13.8 그런데 CDC SLA는 아직 하나의 기준으로 닫히지 않았습니다

이 부분은 다시 명확히 남겨야 합니다.

2026-03-29 발표자료의 Runtime 장표에는:

```text
CDC ≤ 3초
```

가 표시되어 있습니다.

반면 전략 정리본과 2026-05 문서는:

```text
CDC ≤ 30초
```

를 사용합니다.

따라서 현재 상태는:

```text
CDC Freshness SLA

3초
  vs
30초

→ 아직 Architecture Baseline 확정 필요
```

입니다.

제가 임의로 둘 중 하나를 삭제해서는 안 됩니다. 최종 Runtime Gate를 수행하려면 **먼저 SLA ADR을 닫아야 합니다.**

---

# 13.9 Runtime은 FAST/DEEP 두 그림만 검증하면 끝나는 것이 아닙니다

실제 정보계에서는 훨씬 많은 거래가 존재합니다.

전략 Runtime을 실제 구축 검증으로 확장하면 최소 다음과 같은 대표 시나리오를 검증해야 합니다.

| Runtime Scenario | 핵심 검증                              |
| ---------------- | -------------------------------------- |
| 정상 조회        | Client→WEB→WAS→TCF→DB→Response E2E     |
| 변경 거래        | TX Begin→DB 변경→Commit                |
| Paging           | 전체 조회 없이 DB Paging 수행          |
| Domain 간 호출   | 표준 Service/Interface 경계 준수       |
| JWT 인증         | Token 검증→User Context→Authorization  |
| Timeout          | Deadline 초과→Rollback→Connection 반환 |
| DB 오류          | Rollback→표준 오류→자원 반환           |
| 외부연계 장애    | Timeout/CB→장애전파 차단               |
| WAS 장애         | L4/Peer JVM→N-1 지속서비스             |
| DB Failover      | DB 장애→재연결→정합성                  |
| Center DR        | GSLB→DR→DB 승격→서비스 복원            |

이 표는 전략 장표의 FAST/DEEP을 **현재 프로젝트에서 실행 가능한 Architecture Validation Scenario로 확장한 것**입니다. 원 전략 장표가 이 11개 항목을 그대로 열거하는 것은 아닙니다.

---

# 13.10 일반 온라인 조회 Runtime

이제 실제 한 건의 일반 조회를 흘려보겠습니다.

```text

  │ JWT
  │ Standard Message
  ▼
GSLB / L4
  ▼
Apache
  ▼
Tomcat JVM
  ▼
Filter / Interceptor
  │
  ├─ JWT
  ├─ GUID
  └─ Context
  ▼
Controller
  ▼
TCF
  ▼
STF
  ▼
Timeout Executor
  ▼

  ▼
ServiceId Dispatcher
  ▼
Handler
```

ServiceId는 이 흐름에서 Handler뿐 아니라 Timeout, 거래통제, 로그, SQL, Runtime Evidence까지 연결하는 거래의 논리적 Key로 발전하도록 설계되어 있습니다.

# 13.11 정상 조회에서 Runtime이 검증해야 하는 것

성공했다고 해서 단순 HTTP 200만 보면 안 됩니다.

아키텍처적으로는:

```text
HTTP 정상
+
표준전문 정상
+
JWT 정상
+
ServiceId 정상
+
Transaction 정상
+
SQL 정상
+
p95 SLA 정상
+
Thread 정상
+
Pool 정상
+
GUID Trace 정상
```

이어야 합니다.

즉 Runtime PASS는:

```text
"기능이 됐다"
```

가 아니라:

```text
"아키텍처가 의도한 방식으로 기능이 됐다"
```

입니다.

---

# 13.12 변경 거래에서는 Transaction Evidence가 중요합니다

변경 거래:

```text
TX BEGIN
   ↓
Service
   ↓
DAO
   ↓
UPDATE #1
   ↓
UPDATE #2
   ↓
INSERT #3
   ↓

모두 성공
  → COMMIT
```

중간에 문제가 생기면:

```text
UPDATE #1  성공
UPDATE #2  성공
INSERT #3  실패
      │
      ▼
   ROLLBACK

결과:
#1 취소
#2 취소
#3 미반영
```

까지 실제 DB 결과로 확인해야 합니다.

Runtime에서는 `@Transactional이 있다`를 확인하는 것이 아니라:

> **실제 장애를 주입했을 때 DB 상태가 원상복귀되었는가**

를 확인합니다.

---

# 13.13 Timeout Scenario가 특히 중요합니다

현재 Working Runtime 기준에는 SQL Timeout, Transaction Timeout, 외부연계 Timeout 등 계층별 Deadline이 존재합니다.

예를 들어 자료에서는 일반 조회 SQL 2~3초, Spring Transaction 약 4~5초, CruzAPIM Connect 1~2초·Read 3~5초 같은 Working 기준을 제시합니다.

핵심 구조는:

```text
SQL Timeout
     <
Transaction Deadline
     <
Server / Client Deadline
```

입니다.

실제 Runtime에서는 단순히 Timeout Exception이 발생했는지가 아니라:

```text
Timeout
  ↓
Worker 종료
  ↓
TX Rollback
  ↓
Connection 반환
  ↓
Thread 반환
  ↓
Error Mapping
  ↓
GUID Trace 유지
```

까지 봐야 합니다.

---

# 13.14 Timeout 후 Connection이 안 돌아오면 실패입니다

예를 들어:

```text
1,200 TPS
      ↓
느린 SQL 발생
      ↓
Timeout 발생
      ↓
Connection 미반환
      ↓
Hikari Pending 증가
      ↓
Pool 고갈
      ↓
Thread 고갈
      ↓
전체 WAS 장애
```

가 될 수 있습니다.

따라서 Timeout Runtime Test는:

```text
"5초 후 Error가 왔다"
```

만으로 PASS가 아닙니다.

반드시:

```text
TX rollback
Connection Return
Thread Return
Pool Recovery
다음 거래 정상 처리
```

까지 확인해야 합니다.

실제 Runtime Evidence Registry에도 `RUN-TIMEOUT`을 **Rollback / Connection Return** 검증 Run으로 정의해 두고 있습니다.

---

# 13.15 External Failure도 장애가 전파되지 않아야 합니다

```text
NSIGHT
  ↓
CruzAPIM
  ↓
Target System
        X
```

Target 시스템이 느려졌다고:

```text
External
   ↓
NSIGHT Thread
   ↓
Hikari
   ↓
모든 Service
```

가 연쇄적으로 죽어서는 안 됩니다.

정상 Runtime:

```text
External 장애
   ↓
Connect / Read Timeout
   ↓
Circuit Breaker
   ↓
해당 거래 실패
   ↓
Resource 반환
   ↓
다른 거래 정상
```

입니다.

이것이 Logical의 **Fault Isolation**이 Runtime에서 증명되는 방식입니다.

---

# 13.16 WAS N-1도 단순 Health Check가 아닙니다

예를 들어 WAS 2대가 있습니다.

```text
             L4

        ┌────┴────┐
        ▼         ▼
      WAS01     WAS02
```

정상 상태에서는 둘이 부하를 받습니다.

WAS01 장애:

```text
WAS01 X
       │
       ▼
Health Check
       │
       ▼
Pool 제외
       │
       ▼
WAS02가 전체 부하 수용
```

여기서 실제 질문은:

> **WAS02가 살아 있느냐?**

가 아니라:

> **WAS02가 목표 TPS와 p95를 유지하면서 살아 있느냐?**

입니다.

현재 용량산정 구조에도 **센터 장애 시 잔여 TPS가 목표 TPS보다 낮으면 위험**이라는 `CAP-DR-001` 검증 규칙이 들어 있습니다.

---

# 13.17 Center Failure Runtime은 아키텍처의 종합시험입니다

가장 큰 Runtime Test입니다.

```text
                정상

Client
   ↓
GSLB
   ↓
의왕 MAIN
   ↓
WEB / WAS
   ↓
RDW Active


              장애 발생

의왕 CENTER X
       ↓
Detection
       ↓
Isolation
       ↓
GSLB
       ↓
안성 DR
       ↓
WEB / WAS
       ↓
RDW Standby 승격
       ↓
Business Validation
       ↓
Service Restore
```

이 한 테스트에서 동시에 검증되는 것이 많습니다.

```text
GSLB
Network
WEB
WAS
Session
DB
Data Guard
Capacity
Authentication
Logging
Business
RTO
```

즉 **DR Test는 Infrastructure Test가 아니라 Business Runtime Test**입니다.

# 13.18 그리고 반드시 Fail-Back까지 가야 합니다

Runtime을:

```text
MAIN 장애
→ DR 성공
```

에서 끝내면 절반입니다.

실제 완전한 시나리오는:

```text

  ↓
DR 전환
  ↓
DR 서비스
  ↓
MAIN 복구
  ↓
Replication 재정립
  ↓

  ↓
MAIN Application 준비

Traffic 일부 이동

업무 검증

```

입니다.

# 13.19 Runtime Architecture에서 성능도 증명해야 합니다

현재 Vision/NFR는 일반 온라인의 Application Capacity Target을 다음과 같이 관리합니다.

| 구분            | 현재 Working Target |
| --------------- | ------------------: |
| 일반 온라인 p95 |           **≤ 3초** |
| 일반 Peak       |         **600 TPS** |
| 설계 Peak       |       **1,200 TPS** |
| Stress          |       **1,800 TPS** |

여기서 매우 중요한 점은 이 값들이 단순 계산값으로 끝나면 안 된다는 것입니다.

```text
Capacity Calculation
       ↓
Environment Configuration
       ↓
Load Test
       ↓
Runtime Metric
       ↓
PASS / FAIL
```

로 닫혀야 합니다.

# 13.20 Runtime에서 Thread와 DB Pool을 같이 봐야 하는 이유

WAS가 느리다고 Thread만 늘려서는 안 됩니다.

```text
TPS
 ↓
Tomcat Thread
 ↓
Hikari Pool
 ↓
DB Session
 ↓
SQL
```

이 하나의 Chain입니다.

현재 용량산정 설계도 `사용자 → 동시요청자 → TPS → AP 수량 → WAS Thread → DB Pool/Session → 장애 잔여 처리량`을 하나의 산정 체인으로 정의합니다.

또 Runtime 판정 기준에는 VM당 Thread가 maxThreads의 70% 이하면 정상, 70~85%는 주의, 85% 초과는 위험 등의 Rule도 정의되어 있습니다.

즉:

```text
Thread 많이 남음
```

만으로 정상이라고 볼 수 없습니다.

```text
CPU
Heap
GC
Busy Thread
Hikari Active
Hikari Pending
DB Session
SQL
p95
```

를 같이 봐야 합니다.

# 13.21 Observability가 Runtime의 눈입니다

Runtime Evidence에서 거래 하나의 Identity는 다음처럼 잡는 것이 좋습니다.

```text
RunId
+

+

```

현재 Runtime Evidence Registry도 이 식별 체계를 사용합니다.

즉:

```text

```

라는 거래가 어느:

```text

```

를 거쳤는지 볼 수 있어야 합니다.

Logging Architecture도 `GUID + ServiceId → Apache → JVM/Thread → TCF → Service → SQL → External → Response/Error → OM`의 E2E 관계를 요구합니다.

# 13.22 Thread가 바뀌어도 Trace가 끊기면 안 됩니다

TCF Timeout 구조에서는:

```text
Tomcat Request Thread
       ↓
Timeout Executor
       ↓
Worker Thread
```

로 Thread가 변경될 수 있습니다.

그러므로:

```text
Request Thread
GUID=A001
ServiceId=MG001
      ↓
Thread switch
      ↓
Worker Thread
GUID=?
ServiceId=?
```

가 되어서는 안 됩니다.

정상:

```text
Worker Thread
GUID=A001
ServiceId=MG001
```

이어야 합니다.

현재 Observability 기준은 Thread 전환 후 GUID/ServiceId가 소실되면 Runtime Evidence Gate에서 FAIL하도록 정의합니다.

```text

        ↓

        ↓

        ↓
```

# 13.27 여기까지가 6단계 아키텍처 방법론의 완성입니다

이제 처음 시작했던 구조가 전부 연결되었습니다.

```text
① Vision
"어떤 정보계를 만들 것인가"

       ↓

② Big Picture
"누가 어디에서 책임질 것인가"

       ↓

③ Logical
"무엇을 허용하고 금지할 것인가"

       ↓

④ Physical
"어떤 자원에 실제 배치할 것인가"

       ↓

⑤ Mechanism
"정책을 어떻게 강제할 것인가"

       ↓

⑥ Runtime
"실제로 그렇게 동작하는가"
```

전략자료에서도 Runtime의 공식 산출물을 **“런타임 검증 결과”**라고 정의하고 있습니다.

---

## 현재 NSIGHT Runtime의 가장 중요한 현실적 상태

전략은 상당히 잘 정의되어 있지만 **실제 Evidence 측면에서는 아직 완료가 아닙니다.**

현재 `31-RUNTIME-EVIDENCE`의 전체 상태 자체가:

> **`OPEN / G80 BLOCKING`**

입니다.

즉 Load, Failover, Timeout, Trace 등의 **실제 실행 원본이 충분히 연결되지 않았기 때문에 Runtime 성질을 주장하는 Rule을 아직 PASS시킬 수 없다**고 명시되어 있습니다.

따라서 지금 NSIGHT의 상태를 정확히 말하면:

```text
Architecture Strategy         상당히 정립
Logical / Physical            상당히 정립
Mechanism                     상당히 정립
Runtime Scenario              정의 진행
Runtime Evidence              미완료
Final Architecture Baseline   아직 조건부
```

입니다.

이것이 매우 중요한 판단입니다.

# 13.28 한 문장으로 정리하면

**NSIGHT Runtime Architecture는 FAST와 DEEP이라는 두 비즈니스 흐름을 실제 서비스에서 검증하는 것을 출발점으로 하되, 온라인 거래·Transaction·Timeout·DB·외부연계·WAS 장애·센터 DR까지 실제로 실행하고, 그 결과를 GUID·ServiceId·Metric·Log·Trace로 증명하여 Vision·Logical·Physical·Mechanism이 실제 운영에서도 성립하는지를 판정하는 최종 검증 아키텍처입니다.**

그리고 이것이 앞서 연속성 프로젝트에서 정의한:

```text
Architecture as Document
        ↓
Architecture as Model
        ↓
Architecture as Code
        ↓
Architecture as Test
        ↓
Architecture as Runtime Evidence
```

의 마지막 단계와 정확하게 연결됩니다.

**다음 14번째 설명에서는 이 6단계 전체를 다시 반복하지 않고, 이제 `Data → Reaction → Decision → Governance → Operation`이 실제 비즈니스 가치로 어떻게 연결되는지를 중심으로 NSIGHT 전체 아키텍처를 “한 장짜리 통합 Architecture Story”로 정리하는 단계로 넘어가겠습니다.**
