좋습니다. **12번째 설명**으로 이어가겠습니다.
앞에서 `Vision → Big Picture → Logical → Physical → HA/DR`까지 내려왔으므로, 이번에는 **NSIGHT Mechanism Architecture — 설계 원칙을 실제 시스템에서 강제로 동작시키는 방법**을 설명하겠습니다.

전략 브리핑은 Mechanism을 6단계 방법론의 5번째 단계로 정의하며, 핵심을 **규격 통제, 프레임워크 통일, Integration 통제, 데이터 전송 이원화**로 잡고 있습니다. 특히 발표자료 8장에서는 이를 **“아키텍처를 살아 움직이게 하는 5대 실행 메커니즘”**, 즉 “설계 의도를 실제 시스템에서 강제화하는 실행 수단”이라고 표현합니다.

# 12. NSIGHT Mechanism Architecture

## 12.1 먼저 Mechanism이 무엇인지부터 정확히 잡겠습니다

Logical Architecture에서 우리는 정책을 정했습니다.

```text
Logical Policy

RDW ≠ ADW
Online ≠ Batch
P2P 금지
도메인 직접 DB 접근 금지
CDC ≠ Kafka
표준 전문 사용
모든 거래 추적 가능
```

Physical에서는 그 정책을 실제 자원으로 바꿨습니다.

```text
Physical

RDW Exadata
ADW Exadata

Online AP VM
Batch/ETL 전용 자원

Apache
Tomcat JVM

의왕 MAIN
안성 DR
```

그런데 이것만으로는 개발자가 실제로 정책을 지킨다는 보장이 없습니다.

예를 들어 Logical에서:

```text
P2P 연결 금지
```

라고 문서에 써 놓았는데 개발자가:

```text
MG Service
    │
    └────────────→ MK DB 직접 접근
```

해버리면 아키텍처가 깨집니다.

그래서 Mechanism이 필요합니다.

```text
Architecture Policy
        ↓
Mechanism
        ↓
실제로 우회할 수 없게 강제
```

즉,

> **Mechanism Architecture는 Logical에서 정한 정책과 Physical에서 만든 구조가 개발자·시스템·운영환경에서 실제로 동일하게 실행되도록 만드는 표준 실행 규칙입니다.**

수행방법론 문서도 이를 “논리·물리가 집의 구조라면 메커니즘은 전기·배관과 같다”고 설명합니다.

---

# 12.2 전략자료의 NSIGHT 5대 실행 Mechanism

전략 발표자료에 명확하게 나오는 5가지는 다음입니다.

|    No | Mechanism             | 핵심 목적                                              |
| ----: | --------------------- | ------------------------------------------------------ |
| **1** | 규격 표준화           | 모든 온라인 거래를 동일한 통신·전문·추적 규칙으로 처리 |
| **2** | Framework 통일        | 개발자/프로젝트별 구현 편차 제거                       |
| **3** | Integration 통제      | P2P를 막고 승인된 연계경로만 사용                      |
| **4** | Data Transport 이원화 | CDC와 Kafka 등 데이터 이동 책임 분리                   |
| **5** | 대용량 처리 최적화    | 온라인과 분석/ETL의 성능 충돌 제거                     |

이것을 하나의 구조로 보면:

```text
                 NSIGHT MECHANISM

┌──────────────────────────────────────────────┐
│ ① Protocol / Standard                       │
│ HTTP + JSON + Standard Message + GUID       │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────▼───────────────────────────┐
│ ② Framework                                 │
│ NH Cloud Framework / TCF / WebTopSuite      │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────▼───────────────────────────┐
│ ③ Integration Control                       │
│ CruzAPIM / FOS / MFT / 표준 Interface       │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────▼───────────────────────────┐
│ ④ Data Transport                            │
│ CDC / Kafka / File                          │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────▼───────────────────────────┐
│ ⑤ Bulk / Analytics                          │
│ DataStage → ADW                             │
└──────────────────────────────────────────────┘
```

여기서 아주 중요합니다.

> **TCF가 NSIGHT Mechanism 전체가 아닙니다.**

TCF는 ② Framework 통일 영역 안에 들어가는 **온라인 애플리케이션 거래 처리 Mechanism**입니다.

앞에서 설명이 소스 쪽으로 치우쳤던 가장 큰 이유가 이 둘을 같은 크기로 봤기 때문입니다.

# 12.3 첫 번째 — 규격 표준화 Mechanism

전략자료의 첫 번째 실행 규칙은:

```text
HTTP / JSON
+
표준전문
+
GUID / Trace-ID
```

입니다.

즉 모든 개발자가 자기 방식대로:

```text
/api/getCustomer
/api/customer/find
/customer.do
/customerSearch
```

같이 거래 규칙을 제멋대로 만드는 것이 아니라,

```text
Client
   │
   │ HTTP / JSON
   ▼
Standard Message
   │
   ├─ Header
   │   ├─ GUID
   │   ├─ ServiceId
   │   ├─ User
   │   ├─ Branch
   │   └─ System
   │
   └─ Business DTO
```

라는 동일한 계약을 사용하도록 만드는 것입니다.

현재 PDMG에서 분석된 구조로 내려가면:

```text
hdr_nhnis
+
dto
```

형태이고, 공통 Header는 Framework/Context가 담당하고 업무 프로그램에는 업무 DTO만 전달하는 방식입니다.

즉 전략의:

```text
표준 전문
```

이 실제 Application Mechanism에서는:

```text
hdr_nhnis + dto
        │
        ├─ Header → ServiceContext
        └─ DTO    → Business Layer
```

로 구현되는 것입니다.

# 12.4 GUID는 단순 ID가 아닙니다

전략 NFR의 하나가 **Observability**입니다.

전략 정리본에는:

- 전구간 거래 추적
- 이상 감지
- APM 기반 관측
- Trace-ID(GUID)
- 전사 통합 로그

가 포함되어 있습니다.

따라서 GUID는:

```text
Request ID
```

정도가 아니라,

```text
Channel
  ↓
Apache
  ↓
Tomcat
  ↓
TCF
  ↓
ServiceId
  ↓
Service
  ↓
DAO / SQL
  ↓
External Interface
  ↓
Response
```

를 하나의 거래로 묶는 **전구간 Correlation Key**입니다.

그래서 최종 목표는:

```text
GUID
 +
ServiceId
 +
Timestamp
 +
System
 +
ErrorCode
```

만 있으면 운영자가 거래 한 건을 처음부터 끝까지 추적할 수 있어야 합니다.

현재 PDMG Logging 구조도 `GUID + ServiceId`를 기준으로 시스템 진입 → TCF → 업무 → DB → 오류 → 응답을 연결하도록 정의되어 있습니다.

# 12.5 두 번째 — Framework 통일 Mechanism

전략 발표자료에서는 Framework 통일 대상으로 다음을 제시합니다.

```text
Server
→ NH Cloud Framework

Client
→ WebTopSuite

ETL
→ DataStage
```

여기서 Framework 통일의 목적은 단순 개발편의가 아닙니다.

```text
개발자 A
개발자 B
업체 C
업체 D
```

가 모두 자기 방식으로 구현하면:

```text

Error 방식 다름
Logging 방식 다름
Timeout 방식 다름
인증 처리 다름
Integration 방식 다름
```

이 됩니다.

따라서 Framework는:

> **“아키텍처 결정사항을 모든 개발자에게 강제로 동일하게 적용하는 실행 플랫폼”**

이어야 합니다.

# 12.6 여기에서 TCF가 등장합니다

이제 TCF를 위치시켜 보겠습니다.

을 동일하게 처리하는 실행 엔진입니다.

# 12.8 ServiceId가 왜 중요하냐

# 12.9 세 번째 — Integration 통제 Mechanism

전략자료가 가장 강하게 금지하는 패턴 중 하나입니다.

```text
NO P2P
```

입니다.

```text
CruzAPIM
FOS
MCA + MFT
GSE
```

등 승인된 Integration 경로를 사용하고 **DB Link 같은 직접 연결을 금지**하도록 정의합니다.

즉 이것은 금지입니다.

```text
MG Application
       │
       ├──────────────→ MK DAO
       │
       ├──────────────→ MK Mapper
       │
       └──────────────→ MK Table
```

허용되는 방향은:

```text
MG
 │
 ▼

 │
 ▼
CruzAPIM / 표준 Service

 ▼

```

입니다.

현재 MG↔MK 규칙에서도 **다른 도메인의 DAO·Mapper·Table 직접 접근 금지**를 명확하게 잡고 있습니다.

# 12.10 왜 P2P를 금지하는가

단순히 인터페이스 관리가 편하기 때문이 아닙니다.

P2P가 많아지면:

```text
A → B
A → C
A → D
B → D
C → B
D → A
```

처럼 됩니다.

그러면 장애 발생 시:

```text
B 장애
 ↓
A 장애
 ↓
C Timeout
 ↓
Thread 증가
 ↓
Connection 고갈
 ↓
전체 서비스 장애
```

가 될 수 있습니다.

그래서 Integration Gateway가:

```text
Routing
Authentication
Authorization
Timeout
Circuit Breaker
Monitoring
Logging
Version
```

을 통제해야 합니다.

Logical의:

```text
Domain Boundary
```

가 Mechanism 단계에서는:

```text
Integration Gateway / Published Contract
```

로 강제되는 것입니다.

# 12.11 연계 유형에 따라 길도 달라야 합니다

수행 방법론 자료에는 다음과 같이 명확히 정리되어 있습니다.

```text
시스템 거래
      → CruzAPIM

일반 File
      → FOS / MFT

DB 변화
      → CDC

Event
      → Kafka

대용량 Batch
      → DataStage
```

즉:

> **“모든 연계를 REST 하나로 해결한다”**

도 NSIGHT 철학이 아닙니다.

업무 특성별로 표준 전송방식을 다르게 둡니다.

---

# 12.12 네 번째 — Data Transport 이원화

NSIGHT 전략에서 특히 중요한 부분입니다.

```text
CDC
≠
Kafka
```

둘 다 실시간처럼 보이지만 책임이 다릅니다.

### CDC

```text
Source DB
   ↓
Change Capture
   ↓
CDC
   ↓
Relay
   ↓
RDW
```

목적:

> **“DB에서 변한 데이터를 빠르게 복제한다.”**

### Kafka

```text
Customer Action
   ↓
Event
   ↓
Kafka
   ↓
Marketing Processing
   ↓
Realtime Offering
```

목적:

> **“발생한 이벤트를 빠르게 전달해 행동을 일으킨다.”**

수행 방법론도 CDC를 **데이터 변화의 실시간 전달**, Kafka를 **이벤트 스트리밍 및 실시간 반응**으로 구분합니다.

이를 다시 정리하면:

| 구분      | CDC                      | Kafka              |
| --------- | ------------------------ | ------------------ |
| 중심      | **Data Change**          | **Business Event** |
| Source    | DB                       | Application/Event  |
| 목적      | 동기화                   | 반응               |
| 대표 대상 | RDW                      | Marketing          |
| 성격      | State 전달               | Event 전달         |
| Runtime   | DEEP/Near-RT 데이터 기반 | FAST               |

---

# 12.13 이 차이를 무시하면 어떤 문제가 생기는가

예를 들어 고객이 상품 화면을 조회했다고 합시다.

잘못된 구조:

```text
행동 Event
   ↓
DB 저장
   ↓
CDC
   ↓
RDW
   ↓
다시 Marketing Engine
   ↓
Offer
```

이렇게 하면 실시간 반응을 위해 DB를 돌아가야 합니다.

반면 FAST 구조에서는:

```text
고객 행동
   ↓
Kafka Event
   ↓
Realtime Rule
   ↓
Offering
```

으로 갑니다.

그리고 필요하면 별도로:

```text
행동 데이터
   ↓
저장
   ↓
CDC / ETL
   ↓
RDW / ADW
```

가 됩니다.

즉:

```text
Reaction Path
≠
History / Analysis Path
```

입니다.

이것이 FAST / DEEP 분리의 출발점입니다.

# 12.14 다섯 번째 — 대용량 처리 Mechanism

대용량 분석을 온라인과 같은 길로 처리하지 않습니다.

전략자료에서는:

```text
분석 Query의 온라인 영향 차단
```

을 5번째 Mechanism으로 제시합니다.

구조는:

```text
                  ONLINE

   ↓
WAS
   ↓
RDW

빠른 조회
짧은 Transaction


──────────────────────────


                  ANALYTICS

RDW / Source
   ↓

   ↓
ADW
   ↓

대량
집계
분석
```

입니다.

따라서 다음은 금지 방향입니다.

```text

```

또는:

```text

온라인 AP 자원 공유
```

입니다.

# 12.15 Transaction + Timeout도 Mechanism입니다

온라인 Framework의 핵심입니다.

거래를 하나의 실행 경계로 묶어:

```text
START
  ↓
Transaction BEGIN
  ↓
업무
  ↓
DB
  ↓

정상
→ COMMIT

오류
→ ROLLBACK

시간초과
→ Timeout 처리
```

합니다.

NSIGHT/PDMG에서 확인한 Timeout 구조는:

```text
Tomcat Request Thread
      ↓
TCF
      ↓
Timeout Executor
      ↓
Worker Thread
      ↓
TransactionTemplate
      ↓
TX BEGIN
      ↓
Dispatcher
      ↓
Handler
      ↓
Facade
      ↓
Service
      ↓
DAO
      ↓
DB
```

형태입니다.

여기서 중요한 전략적 의미는:

> **“느린 업무 하나가 WAS 자원을 끝없이 점유하도록 허용하지 않는다.”**

입니다.

즉 Timeout은 기능이 아니라 **Resilience Mechanism**입니다.

---

# 12.16 Timeout에는 계층이 있습니다

현재 Spring 설정 자료에서도 온라인 Transaction Timeout을 약 `4~5초` 수준의 Working 기준으로 두고, 장시간 거래는 비동기/배치로 전환하도록 정리되어 있습니다.

개념적으로는:

```text
DB Query Timeout
       <
Transaction Timeout
       <
Server Request Timeout
       <
Client Timeout
```

이어야 합니다.

왜냐하면 바깥쪽보다 안쪽 Timeout이 더 늦으면:

```text
사용자는 이미 Timeout
      ↓
그런데 DB Query 계속 실행
      ↓
Thread 계속 점유
      ↓
Connection 계속 점유
      ↓
Zombie Transaction
```

이 발생할 수 있기 때문입니다.

---

# 12.17 인증도 공통 Mechanism입니다

업무마다 로그인 코드를 구현하지 않습니다.

```text
User
 ↓
SSO
 ↓
JWT 발급
 ↓
Access Token
 ↓
Backend
 ↓
JWT Validation
 ↓
User Context
 ↓
Business
```

현재 관련 자료에는 `SSO + KMS + JWT Access/Refresh + Spring Security` 구조가 확인됩니다.

즉 Security 정책이:

```text
인증해야 한다
권한을 확인해야 한다
```

에서 끝나는 것이 아니라,

```text
SSO
JWT
KMS
JWKS
Spring Security
Context
```

라는 실행 Mechanism으로 내려오는 것입니다.

---

# 12.18 Logging과 ImageLog도 Mechanism입니다

일반 애플리케이션 로그:

```text
log.info(...)
```

만으로는 금융 거래를 복구하거나 조사하기 어렵습니다.

그래서:

```text
GUID
+
ServiceId
+
Request
+
Response
+
Error
+
Timing
```

을 거래 증적으로 연결합니다.

현재 ImageLog 구조에서는:

```text
PRE
POST
EXCEPTION
```

시점을 구분하여 요청·응답·예외의 거래 증적을 남기도록 되어 있습니다.

이것이 나중에 Runtime Evidence로 연결됩니다.

# 12.20 반면 FAST 데이터 흐름의 Mechanism은 다릅니다

입니다.

# 12.22 가장 중요한 개념 — Logical Policy와 Mechanism의 매핑

최종 아키텍처 정의서에는 반드시 이런 표가 있어야 합니다.

| Logical Policy                      | Mechanism                               |
| ----------------------------------- | --------------------------------------- |
| P2P 금지                            | CruzAPIM / 표준 Interface               |
| Domain 직접 DB 접근 금지            | Service Contract + ServiceId            |
| 모든 거래 추적                      | GUID + ServiceId + MDC                  |
| 업무 프로그램의 직접 TX 관리 최소화 | TCF / Transaction Framework             |
| 장시간 거래 통제                    | Timeout Mechanism                       |
| 업무별 임의 오류전문 금지           | Exception Framework + Standard Response |
| 데이터 변화 실시간 전달             | CDC                                     |
| 이벤트 실시간 전달                  | Kafka                                   |
| 대용량 분석 온라인 격리             | DataStage + ADW                         |
| 사용자 인증 통합                    | SSO + JWT                               |
| 장애 분석 가능                      | Logging + ImageLog + APM                |
| 시스템별 임의 통신 규격 금지        | HTTP/JSON + 표준전문                    |

이 표가 바로 **Architecture Policy → Implementation Mechanism Traceability**입니다.

# 12.27 이번 단계의 핵심 한 문장

> **NSIGHT Mechanism Architecture는 Logical Architecture에서 정한 분리·표준·통제 정책을 HTTP/JSON·표준전문·GUID·Framework·TCF·ServiceId·CruzAPIM·CDC·Kafka·FOS·DataStage·SSO/JWT·Logging 등의 실행 수단으로 강제하여, 설계자의 의도가 개발자의 임의 구현에 의해 무너지지 않도록 만드는 아키텍처입니다.**

그리고 이것이 중요한 이유는:

```text
Architecture Document
        ↓
Mechanism
        ↓
실제 시스템 동작
```

으로 넘어가는 **결정적인 연결 단계**이기 때문입니다.

## 다음 13번째 설명

이제 6단계에서 마지막 하나가 남았습니다.

```text
Vision                 ✓
Big Picture            ✓
Logical                ✓
Physical               ✓
HA / DR                ✓
Mechanism              ✓ ← 지금
        ↓
★ Runtime Architecture
```

**13번째는 `NSIGHT Runtime Architecture`**입니다.

여기서는 더 이상 “이렇게 설계한다”가 아니라 실제로:

```text
FAST 시나리오
DEEP 시나리오
온라인 정상조회
온라인 변경거래
도메인 간 호출
Paging
JWT 인증
Timeout
DB 장애
외부연계 장애
WAS 장애
DB Failover
Center DR
```

를 처음부터 끝까지 흘려보면서 **Vision → Logical → Physical → Mechanism이 실제 서비스에서 맞는지 검증**하겠습니다. Runtime 단계가 최종 검증이면서 다시 앞 단계로 피드백하는 단계라는 것이 NSIGHT 방법론의 핵심입니다.
