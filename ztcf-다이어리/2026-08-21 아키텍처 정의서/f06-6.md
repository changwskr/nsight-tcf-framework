좋습니다. 이제 **④ 데이터거버넌스 구축전략**으로 진행하겠습니다.

이번 영역은 앞의 데이터플랫폼·마케팅플랫폼·BI포탈과 성격이 조금 다릅니다. 전략자료에서 데이터거버넌스의 책임은 **“IT 메타 시스템 기반 데이터 표준·품질 관리, 용어 정의 및 데이터 모델 일관성 유지”**로 정의되어 있습니다. 즉 직접 고객에게 서비스를 제공하기보다는 **다른 플랫폼이 사용하는 데이터의 의미와 품질을 통제하는 영역**입니다.

# 1. 데이터거버넌스가 왜 별도 플랫폼이어야 하는가

지금까지 세 플랫폼을 이렇게 설명했습니다.

```text
DATA PLATFORM
데이터를 공급한다
        │
        ▼
MARKETING PLATFORM
데이터로 고객에게 반응한다
        │
        ▼
BI PORTAL
데이터로 판단한다
```

그런데 여기에는 전제가 있습니다.

> **“모두가 같은 데이터를 같은 의미로 이해한다.”**

예를 들어 `고객`이라는 단어 하나만 봐도 실제 업무에서는 여러 정의가 나올 수 있습니다.

```text
전체고객
활동고객
거래고객
유효고객
마케팅대상고객
휴면고객
```

만약 시스템마다 정의가 다르면:

```text
마케팅플랫폼 고객수 = 10,000명

BI 보고서 고객수 = 10,800명

경영보고 고객수 = 9,700명
```

이 됩니다.

그러면 데이터가 아무리 빨리 움직여도:

```text
빠른 데이터
     +
틀린 정의
     =
빠르게 틀린 의사결정
```

이 됩니다.

그래서 NSIGHT는 데이터거버넌스를 5대 서비스 도메인 중 하나로 별도 분리합니다. 전략 자료에서도 데이터거버넌스를 `데이터플랫폼 / 마케팅플랫폼 / BI 포탈 / IT서비스 및 업무지원`과 동일한 상위 도메인으로 식별합니다.

---

# 2. 전략적으로 보면 데이터거버넌스의 역할은 “신뢰의 규칙”입니다

전략자료의 직접적인 정의는 다음입니다.

```text
데이터거버넌스

IT 메타 기반
데이터 품질
데이터 표준
데이터 모델 일관성
```

이걸 지금까지의 세 플랫폼에 연결하면:

```text
                        DATA GOVERNANCE
                 "데이터 의미와 신뢰 통제"
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
    DATA PLATFORM    MARKETING         BI PORTAL
          │           PLATFORM             │
          │               │                │
      데이터 저장      고객 판단          경영 판단
          │               │                │
          └───────────────┼────────────────┘
                          │
                      같은 정의
                      같은 표준
                      같은 품질
```

여기서 **“Control Plane”이라는 표현은 제 해석**입니다. 원본 전략자료가 데이터거버넌스를 직접 Control Plane이라고 명명하지는 않습니다.

다만 역할상으로 보면:

> 데이터 자체를 업무처럼 처리하는 Data Plane보다는, 데이터의 **정의·품질·흐름·일관성을 통제하는 Governance Plane**에 가깝습니다.

# 3. 실제 상세 아키텍처에서는 3개 핵심 영역으로 구성됩니다

업로드한 데이터거버넌스 논리 기술 아키텍처를 확인하면 핵심 업무 영역은 정확히 다음 세 가지입니다.

```text
                DATA GOVERNANCE

       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
    비즈메타      데이터 품질    데이터 흐름
```

이 세 영역을 따로 이해해야 합니다.

# 4. 첫 번째 — 비즈메타

상세 아키텍처에서 비즈메타는 다음 기능으로 구성됩니다.

```text
비즈메타
 ├─ 업무 용어
 └─ 표준 계수
      ↓
     WAS
```

여기서 가장 중요한 것은 **업무 용어**입니다.

예를 들어:

```text
용어 : 고객

정의 :
금융거래 관계를 보유하거나
마케팅/상담 대상이 되는 개인 또는 법인

관련 데이터 :
CUSTOMER_ID
CUSTOMER_TYPE
STATUS
...
```

와 같은 연결이 있어야 합니다.

다른 예로:

```text
"월간 실적"
"잔액"
"신규고객"
"캠페인 성공"
"활동고객"
```

같은 용어를 시스템마다 제멋대로 정의하지 않도록 하는 것입니다.

즉:

```text
업무 언어
   ↓
표준 정의
   ↓
데이터 항목
   ↓
모델
```

을 연결하는 역할입니다.

---

# 5. 왜 이것이 BI 포탈에 중요한가

앞서 BI 포탈 전략에서 다음 기능을 확인했습니다.

```text
"지난달 실적 보여줘"
        ↓
AI/NLP
        ↓
SQL
```

전략 발표자료는 AI/NLP 자연어 질의를 BI 포탈의 핵심 혁신으로 명시합니다.

그런데 여기서 문제가 발생합니다.

AI가:

```text
"실적"
```

이라는 말을 들었을 때 어떤 데이터를 조회해야 할까요?

```text
영업실적?
상품판매실적?
조합실적?
고객실적?
월평균실적?
누적실적?
```

업무 용어와 데이터 정의가 정리되어 있지 않으면 AI/NLP도 정확한 질의를 만들기 어렵습니다.

여기까지는 **아키텍처적 추론**입니다. 현재 전략자료는 `데이터거버넌스 → AI/NLP Semantic Layer`를 직접 설계하지는 않습니다.

따라서 향후 상세설계에서는 다음 연결을 정의할 필요가 있습니다.

```text
Business Term
      ↓
Business Metadata
      ↓
Data Model / Column
      ↓
Semantic Mapping
      ↓
BI / AI Query
```

즉 이것은 **향후 구축 보완사항**이지 현재 자료에서 확정된 구현은 아닙니다.

---

# 6. 두 번째 — 데이터 품질

실제 논리 기술 아키텍처에서 데이터품질은 네 가지 핵심 기능입니다.

```text
데이터 품질

├─ CTQ
├─ DQI
├─ 프로파일링
└─ 업무규칙(BR)
      ↓
     WAS
```

각 항목은 역할이 다릅니다.

| 항목         | 자료상 역할             |
| ------------ | ----------------------- |
| CTQ          | 중요 품질관리 대상      |
| DQI          | 데이터 품질지표         |
| 프로파일링   | 데이터 상태 분석        |
| 업무규칙(BR) | 업무규칙 기반 품질 검증 |

이를 쉽게 설명하면:

```text
데이터가 존재하는가?
        ↓
Profiling

중요한 데이터인가?
        ↓
CTQ

품질 수준은 얼마인가?
        ↓
DQI

업무적으로 올바른 값인가?
        ↓
Business Rule
```

입니다.

---

# 7. 데이터 품질은 “오류 찾기”가 아니라 신뢰도를 관리하는 것입니다

예를 들어 RDW에 고객 데이터가 있다고 합시다.

```text
고객번호       정상
고객명         정상
휴대전화번호   NULL
생년월일       2099-01-01
성별코드       X
```

SQL은 정상적으로 조회될 수 있습니다.

하지만 업무적으로는 품질 문제가 있습니다.

```text
Technical Success
      ≠
Data Quality
```

따라서 품질 규칙은 예를 들면:

```text
고객번호 NULL 불가

생년월일 미래일 불가

상품코드는 상품마스터에 존재

조합코드는 유효한 조합만 허용
```

처럼 데이터 의미를 검사하게 됩니다.

중요한 것은, 이 예시는 **개념 설명을 위한 예시**이고 현재 자료에 이 구체 규칙들이 확정되어 있다는 뜻은 아닙니다.

---

# 8. 품질이 무너지면 세 플랫폼 모두 영향을 받습니다

```text
          잘못된 데이터
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
     RDW    Marketing    ADW
      │        │          │
      ▼        ▼          ▼
SingleView  Wrong Offer   BI
                         │
                         ▼
                    Wrong Decision
```

그래서 데이터 품질은 단순 운영지원 기능이 아닙니다.

전략 전체의:

```text
DATA
 ↓
REACTION
 ↓
DECISION
```

중 **DATA의 신뢰도를 보증하는 기반**입니다.

---

# 9. 세 번째 — 데이터 흐름

실제 상세 아키텍처에는 `데이터 흐름`이 별도의 업무 영역으로 존재합니다.

```text
데이터 흐름

├─ 흐름 수집/파싱
└─ 흐름 분석/검색
      ↓
     WAS
```

이 부분은 NSIGHT 전략과 매우 잘 연결됩니다.

왜냐하면 NSIGHT의 핵심 논리전략 자체가:

> **데이터 흐름 강제화**

이기 때문입니다.

전략자료에서는 데이터가 목적별 경로를 타도록 합니다.

```text
DB Change → CDC

Customer Event → Kafka

Bulk Data → ETL

File → FOS/MFT

API → CruzAPIM
```

그렇다면 거버넌스 관점에서는:

> **“실제로 데이터가 그 경로로 이동하고 있는가?”**

를 볼 수 있어야 합니다.

---

# 10. 데이터 흐름 관리가 필요한 이유

예를 들어 한 BI 보고서의 숫자가 틀렸다고 합시다.

단순히 마지막 ADW 테이블만 보면 원인을 찾기 어렵습니다.

필요한 것은:

```text
Source
  ↓
CDC
  ↓
RDW
  ↓
ETL
  ↓
ADW
  ↓
Mart
  ↓
BI Report
```

전체 흐름입니다.

즉 질문이:

```text
"이 값은 어디서 왔는가?"
```

일 때 거꾸로 찾아갈 수 있어야 합니다.

```text
BI Report
   ↑
Data Mart
   ↑
ADW
   ↑
ETL
   ↑
RDW
   ↑
Source
```

일반적으로 이런 개념을 Data Lineage라고 부르지만, **현재 자료의 직접적인 명칭은 `흐름 수집/파싱`, `흐름 분석/검색`입니다.**

따라서 현 단계에서는 자료의 표현을 우선해 **데이터 흐름 관리**라고 보는 것이 맞습니다.

---

# 11. IT 메타와 비즈메타는 구분해야 합니다

상세 구성에는 `IT 메타`가 별도로 존재합니다.

```text
데이터거버넌스
      │
     FOS
      │
      ▼
    IT 메타
```

IT 메타는 **시스템/기술 메타데이터**를 담당하고, FOS가 연계수단으로 표시되어 있습니다.

따라서 자료를 그대로 놓고 보면:

```text
              METADATA

       ┌────────┴─────────┐
       ▼                  ▼
   비즈메타              IT 메타

 업무 용어             시스템 정보
 표준 기준             기술 메타
```

정도로 구분할 수 있습니다.

이 두 영역 사이의 최종 통합 모델이나 동기화 책임까지는 현재 자료에서 구체적으로 정의되어 있지 않습니다.

이 부분은 상세 메타 아키텍처에서 추가 확정이 필요합니다.

---

# 12. 데이터거버넌스는 RDW와 ADW 모두를 봅니다

실제 논리 기술 아키텍처에서 데이터거버넌스는 RDW와 ADW에 연결되어 있습니다.

```text
           DATA GOVERNANCE
              │       │
           JDBC     연계
              │       │
              ▼       ▼
             RDW ─ETL─▶ ADW
```

자료에서는:

| 연결             | 의미                         |
| ---------------- | ---------------------------- |
| Governance ↔ RDW | 메타/품질/흐름 관련 연계     |
| RDW → ADW        | ETL                          |
| Governance ↔ ADW | 분석영역 메타/품질/흐름 연계 |

로 정리되어 있습니다.

다만 원본 이미지의 일부 선은 방향이 명확하지 않기 때문에, 업로드된 분석문서 자체도 `조회`, `갱신` 같은 구체적 호출방향을 임의로 확정하지 않고 **“연계”**라고 표현합니다.

이 구분을 유지하는 것이 맞습니다.

---

# 13. 그래서 거버넌스는 RDW/ADW 위에 별도의 데이터 복사본을 만드는 영역이 아닙니다

개념적으로 보면:

```text
           Governance
              │
    ┌─────────┼──────────┐
    │         │          │
    ▼         ▼          ▼
 Metadata   Quality     Flow
    │         │          │
    └─────────┼──────────┘
              │
      ┌───────┴───────┐
      ▼               ▼
     RDW             ADW
```

즉 RDW/ADW가:

> **업무 데이터를 저장하고 제공**

한다면 거버넌스는:

> **그 데이터가 무엇인지, 품질이 어떤지, 어디서 왔는지를 관리**

하는 역할입니다.

---

# 14. 실제 물리 실행기반도 별도 공간으로 분리되어 있습니다

데이터거버넌스 상세 아키텍처에서는 세 업무가 다음 공통 실행기반을 사용합니다.

```text
비즈메타 / 데이터품질 / 데이터흐름
                │
               WAS
                │
               VM
                │
              IaaS
```

이는 NSIGHT의 Hybrid 전략과도 맞습니다.

전략자료에서:

```text
RDW / ADW
→ Exadata

마케팅 / BI / 데이터거버넌스
→ NH Cloud IaaS
```

방향을 제시하고 있습니다.

즉 거버넌스 자체도 독립된 서비스 도메인으로 **서비스 영역의 VM Scale-Out 전략** 아래에 위치합니다.

---

# 15. 서버 인벤토리에도 데이터거버넌스가 실제로 독립 구성됩니다

현재 서버 인벤토리 자료에서도 데이터거버넌스 서버군이 별도로 식별됩니다.

예를 들면:

```text
데이터거버넌스
 ├─ 비정형/데이터품질 WAS #01
 ├─ 비정형/데이터품질 WAS #02
 ├─ 데이터표준 WAS #01
 └─ 데이터표준 WAS #02
```

가 확인됩니다. 다만 한 항목은 `재검토` 상태로 보여 최종 Physical Baseline에서는 별도 확인이 필요합니다.

즉 전략의:

```text
5대 Domain 분리
```

가 실제 서버구성에도 내려와 있는 것입니다.

---

# 16. 대내·대외 연계도 임의 연결하지 않습니다

데이터거버넌스 상세 구조에는 대내 연계가 다음으로 표시됩니다.

```text
대내

Cruz APIM
EAI
FOS
MFT
```

대외는:

```text
FOS
대외 MCA
MFT
```

입니다.

즉 데이터거버넌스도 NSIGHT 전체 Integration Control 원칙 밖에 존재하는 독립 시스템이 아닙니다.

```text
DATA GOVERNANCE
       │
       ▼
표준 Integration Boundary
```

를 따라야 합니다.

이는 전략 브리핑의 `No P2P`, `CruzAPIM`, `FOS`, `CDC`, `Kafka` 등 승인된 경로를 사용한다는 전체 Integration 정책과 연결됩니다.

# 17. 개발·운영도 별도의 거버넌스 대상입니다

상세 아키텍처에는 다음 개발·운영 구성도 포함되어 있습니다.

```text
개발자
 │
 ├─ GitLab
 ├─ Git Runner
 ├─ eCAMS
 ├─ Nexus
 └─ FWK Manager
       │
       ▼
Data Governance
```

이것은 중요한 의미가 있습니다.

```text

개발표준과 배포통제를 안 받아도 된다"
```

가 아닙니다.

다른 NSIGHT 서비스처럼 동일한 개발·배포·운영 표준 하에서 관리됩니다.

# 19. 특히 BI/AI와 데이터거버넌스의 관계는 향후 매우 중요합니다

다만 이 부분은 **확정된 Source Fact와 향후 설계 방향을 구분해서 봐야 합니다.**

### 현재 자료에서 확정된 내용

```text
BI Portal
→ AI/NLP 자연어 질의

Data Governance
→ 업무용어
→ 데이터 표준
→ 품질
→ IT Meta
```

### 현재 자료에서 아직 직접 연결이 정의되지 않은 부분

```text
업무용어
   ↓
Semantic Layer
   ↓
AI/NLP
   ↓
SQL
```

이 연결은 현재 전략자료에서 상세 아키텍처로 확정되어 있지 않습니다.

하지만 BI의 AI/NLP 전략을 실제 구축하려면 향후 반드시 검토해야 할 연결입니다.

즉 현재 상태는:

```text
전략 방향은 존재

하지만

Governance Metadata
        ↕
AI Semantic Model

상세 설계 필요
```

라고 보는 것이 정확합니다.

# 20. 데이터거버넌스의 성공 여부는 관리 화면 숫자로 판단하면 안 됩니다

예를 들어:

```text
표준용어 50,000개 등록
품질규칙 10,000개 등록
```

했다고 해서 자동으로 거버넌스가 성공한 것은 아닙니다.

전략 관점에서는 다음 질문을 해야 합니다.

```text
BI의 "고객"과
Marketing의 "고객"이
같은 정의인가?

        ↓

RDW와 ADW에서
같은 의미인가?

        ↓

품질 오류가 발생하면
어떤 서비스가 영향을 받는지 알 수 있는가?

        ↓

잘못된 데이터가
어디서 왔는지 추적할 수 있는가?
```

즉 성공조건은 **등록량**보다:

```text
정의 일관성
+
품질 가시성
+
흐름 추적성
```

입니다.

# 21. 현재 자료를 보면 추가 상세화가 필요한 영역도 분명합니다

자료에 없는 내용을 확정하지 않고, 현재 확인 가능한 GAP을 정리하면 다음과 같습니다.

| 추가 상세화 대상                         | 현재 자료 상태       |
| ---------------------------------------- | -------------------- |
| 비즈메타 ↔ IT메타 통합모델               | 상세 미확정          |
| 업무용어 ↔ 데이터모델 매핑               | 구체 Rule 미확정     |
| 품질 Rule 적용 대상 Table/Column Catalog | 미확인               |
| RDW/ADW 품질관리 범위                    | 상세 Matrix 필요     |
| 데이터흐름 End-to-End Registry           | 세부 목록 필요       |
| 데이터 Owner / Steward                   | 자료에서 상세 미확인 |
| AI/NLP ↔ Metadata 연계                   | 상세 미정            |
| 품질 결과 → 운영 Gate                    | 연결방식 미정        |
| 데이터 변경 시 영향도 분석               | 상세 구현 확인 필요  |

즉 전략은 분명하지만 **운영 가능한 Governance Baseline**으로 만들려면 이 부분이 추가되어야 합니다.

# 22. 지금까지 4개 플랫폼의 역할

이제 상위 전략이 매우 명확해졌습니다.

```text
① DATA PLATFORM

"신뢰할 수 있는 데이터를 공급한다"

          ↓


② MARKETING PLATFORM

"그 데이터와 Event로 즉시 반응한다"

          ↓


③ BI PORTAL

"그 데이터를 이용해 즉시 판단한다"

          ↓


④ DATA GOVERNANCE

"그 데이터의 의미·품질·흐름이
모든 곳에서 일관되도록 통제한다"
```

그런데 여기까지는 **업무와 데이터 플랫폼**입니다.

실제로 이 시스템 전체가 매일 살아서 운영되려면 하나가 더 필요합니다.

```text
인증은 누가 하는가?
Batch는 누가 관리하는가?
Framework는 누가 관리하는가?
Git은?
배포는?
APM은?
로그는?
장애는?
단말은?
공통 운영도구는?
```

이 책임을 담당하는 것이 마지막 5번째 도메인인 **IT서비스 및 업무지원**입니다.

# 23. 다음 단계 — ⑤ IT서비스 및 업무지원 구축전략

다음은 5대 플랫폼의 마지막입니다.

```text
                    IT SERVICE / SUPPORT

      ┌───────────────┼────────────────┐
      │               │                │
     인증            운영             개발
   SSO/JWT          APM/Log       GitLab/Runner
      │               │                │
      ├────────── Batch / Control-M ────┤
      │               │                │
      └────── Framework / Deployment ───┘
```

전략 브리핑에서는 이 영역을 **SSO 통합인증, Control-M 배치관리, APM·대시보드·통합로그, DevOps 환경지원(GitLab/eCAMS)**을 담당하는 서비스 도메인으로 정의합니다.

다음 설명에서는 이것을 단순 “공통 운영 서버 모음”으로 보지 않고, **왜 IT서비스/업무지원이 NSIGHT 전체 5개 플랫폼의 Architecture Consistency와 운영 지속성을 지탱하는 기반인지**, 그리고 `SSO → Framework → CI/CD → Batch → APM → Logging → 운영통제`를 어떻게 하나의 **Engineering & Operations Platform**으로 보아야 하는지를 전략자료 기준으로 연결하겠습니다.
