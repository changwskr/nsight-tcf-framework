좋습니다. 이번에는 **소스/TCF가 아니라 전략 브리핑을 기준**으로 첫 번째 핵심 플랫폼인 **NSIGHT 데이터플랫폼 구축전략**부터 보겠습니다.

전략자료에서 데이터플랫폼은 단순히 `RDW + ADW`를 구축하는 영역이 아닙니다. 문서에서는 데이터플랫폼을 **“집의 기초공사”, “모든 정보가 모이는 심장”, “데이터는 틀리지 않는다는 신뢰를 생산하는 구조적 기반”**으로 정의합니다.

# 1. 데이터플랫폼을 왜 가장 먼저 이해해야 하는가

NSIGHT의 전체 비즈니스 흐름은 사실 이렇게 연결됩니다.

```text
                     NSIGHT

             ① DATA
                │
                ▼
         정확한 데이터 확보
                │
                ▼
             ② REACTION
                │
                ▼
       고객 행동에 즉시 반응
                │
                ▼
             ③ DECISION
                │
                ▼
          즉시 분석·판단
```

이 중 첫 단추가 데이터플랫폼입니다.

```text
데이터플랫폼
     ↓
"신뢰할 수 있는 데이터"

마케팅플랫폼
     ↓
"고객에게 반응"

BI 포탈
     ↓
"조직이 판단"
```

발표자료도 이를 `데이터플랫폼 → 마케팅플랫폼 → BI 포탈`로 연결하고, 각각 **기초공사 → 반응형 두뇌 → 의사결정 공간**으로 정의합니다.

따라서 데이터플랫폼이 잘못되면 뒤의 마케팅과 BI가 아무리 좋아도 의미가 없습니다.

---

# 2. 데이터플랫폼 전략의 출발 질문

전략보고서가 던지는 질문이 매우 중요합니다.

> **FAST와 DEEP이라는 성격이 전혀 다른 두 데이터 흐름을 하나의 창고에 담을 수 있는가?**

NSIGHT의 판단은 **NO**입니다. 이것이 RDW와 ADW를 물리적으로 분리하는 출발점입니다.

쉽게 말하면 이런 문제입니다.

```text
하나의 DW

실시간 고객조회 ─────────┐
                         │
마케팅 실시간 조회 ──────┤
                         ├── CPU / MEM / IO / Session 경쟁
BI 대량 분석 ────────────┤
                         │
10년치 데이터 집계 ──────┘

             ↓

       결국 서로 방해
```

그래서 NSIGHT에서는 아예 공간을 나눕니다.

```text
                  DATA PLATFORM

          ┌──────────────────────┐
          │        RDW           │
          │ Real-time DW         │
          │                      │
          │ 실시간 / 온라인       │
          │ FAST 지원            │
          └──────────────────────┘

                    ≠

          ┌──────────────────────┐
          │        ADW           │
          │ Analytical DW        │
          │                      │
          │ 분석 / 집계 / BI      │
          │ DEEP 지원            │
          └──────────────────────┘
```

발표자료 26페이지도 두 저장소를 **Oracle Exadata 기반 독립 물리 장비**로 구성하고, 이 분리의 목적을 성능 간섭 차단·장애 전이 방지·독립 SLA 확보라고 정의합니다.

---

# 3. 핵심은 RDW/ADW가 아니라 “Resource Isolation”입니다

이 부분이 데이터플랫폼 전략에서 가장 중요합니다.

표면적으로 보면:

```text
RDW 하나
ADW 하나
```

처럼 DB를 두 개 만든 것처럼 보입니다.

그런데 전략의 실제 목적은:

> **Resource Isolation, 즉 자원격리**

입니다.

예를 들어 ADW에서 대량 분석을 수행한다고 하겠습니다.

```text
ADW
│
├─ 수년치 데이터 조회
├─ 대량 JOIN
├─ 대규모 GROUP BY
└─ BI / OLAP 병렬처리
```

이 부하가 RDW와 같은 자원을 사용하면:

```text
ADW 분석부하
      │
      ▼
CPU / IO / Session 점유
      │
      ▼
RDW 영향
      │
      ▼
SingleView 지연
      │
      ▼
마케팅 서비스 지연
```

이 됩니다.

물리적으로 분리하면:

```text
RDW                              ADW

Online                           Analytics
SingleView                       BI
Marketing                        OLAP
Near Real-time                   대량집계

   │                               │
   │         물리 자원 분리         │
   X───────────────────────────────X
```

가 됩니다.

그래서 RDW/ADW 분리는 동시에 세 가지를 얻기 위한 전략입니다.

| 전략효과                  | 의미                                  |
| ------------------------- | ------------------------------------- |
| **Performance Isolation** | 분석 쿼리가 온라인을 방해하지 않음    |
| **Fault Isolation**       | ADW 장애가 RDW 서비스로 전파되지 않음 |
| **Scale Isolation**       | RDW와 ADW를 서로 다른 기준으로 확장   |

NSIGHT Data Architecture도 이 결정을 `온라인/Near Real-time Read`와 `Large Analytics/BI/ETL Result`의 물리 분리 정책으로 정의하고 있습니다.

---

# 4. RDW는 무엇을 위한 것인가

RDW는 **Real-time Data Warehouse**, 즉 전략자료에서 말하는 **실시간 운영창고**입니다.

```text
                  RDW

          "실시간을 지키는 창고"

                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   CDC 적재    SingleView   Marketing
       │           │           │
       └───────────┼───────────┘
                   ▼
         Online / Near Real-time
```

전략자료에서 RDW의 역할은 다음으로 명확하게 정의됩니다.

- OLTP 성격의 실시간 데이터 서비스
- CDC 기반 실시간 데이터 통합
- 온라인 서비스 지원
- 마케팅 이벤트 대응 데이터
- 지연 없는 실시간 응답 지원

또 실제 데이터플랫폼 업무구성 자료를 보면 RDW 안에서도 단순 테이블 집합이 아니라:

```text
RDW

├─ CO  공통
├─ SR  실시간 SoR
├─ ZD  준실시간 요약집계
├─ RM  준실시간 보고서마트
└─ FA  피드백
```

처럼 실시간·준실시간 중심의 데이터 영역을 나누고 있습니다.

즉 RDW는 단순 조회 DB가 아니라 **실시간 정보계 서비스가 바라보는 핵심 데이터 기반**입니다.

---

# 5. ADW는 무엇을 위한 것인가

ADW는 **Analytical Data Warehouse**, 즉 전략적 분석창고입니다.

```text
                  ADW

           "깊이를 만드는 창고"

                   │
          ┌────────┼─────────┐
          ▼        ▼         ▼
        BI       OLAP     Analytics
          │        │         │
          └────────┼─────────┘
                   ▼
           전략적 의사결정
```

전략자료에서 ADW는:

- 대용량 집계
- 전략경영 분석
- BI
- Data Mart
- ETL 정제 결과 저장

을 담당합니다.

실제 업무 분류 역시 RDW보다 분석 단계가 더 많습니다.

```text
ADW

├─ CO  공통
├─ SR  분석 SoR
├─ ZD  분석통합요약집계
├─ UM  분석단위업무마트
├─ RM  분석보고서마트
├─ FA  피드백
└─ DA  분석지원
```

즉:

```text
RDW
= "지금 무슨 일이 일어나고 있는가?"

ADW
= "무슨 의미이며 앞으로 어떻게 판단할 것인가?"
```

정도로 이해하면 좋습니다. ADW의 분석·집계·마트·분석지원 구조는 데이터플랫폼 구성자료에서도 확인됩니다.

---

# 6. FAST와 DEEP은 DB 구분보다 더 큰 개념입니다

여기서 중요한 구분을 하나 해야 합니다.

```text
FAST = RDW
DEEP = ADW
```

라고 단순화하면 정확하지 않습니다.

FAST와 DEEP은 **Runtime Flow**입니다.

## FAST — 고객에게 반응하는 길

```text
고객 행동
   │
   ▼
Event Capture
   │
   ▼
Kafka
   │
   ▼
Real-time Processing
   │
   ▼
Marketing Rule
   │
   ▼
Offering
```

목표:

> **고객 행동에 즉시 반응**

전략 장표에서는 이벤트 처리 및 오퍼링 실행 **1초 이내**를 FAST의 목표로 제시합니다.

그리고 중요한 특징은:

```text
Event Driven
+
Kafka
+
DB 비의존 Fast Path
+
경량 처리
```

입니다.

즉 고객이 행동했는데:

```text
Kafka
 → DB 적재
 → Batch
 → 조회
 → 분석
 → 오퍼링
```

을 기다리는 구조가 아닙니다.

고객 행동 Event 자체가 **고속레인**을 타는 것입니다.

---

# 7. DEEP — 정확하고 깊게 판단하는 길

DEEP은 반대로 속도만이 목표가 아닙니다.

```text
계정계 / 원천
      │
      ▼
     CDC
      │
      ▼
     RDW
      │
      ▼
 DataStage / ETL
      │
      ▼
     ADW
      │
      ▼
  BI / Analytics
      │
      ▼
 전략적 의사결정
```

목적은:

> **정확한 데이터에 기반한 깊이 있는 분석과 경영 판단**

입니다.

따라서:

```text
FAST
= 속도

DEEP
= 깊이
```

라고 보면 됩니다.

그리고 NSIGHT의 매우 강한 정책은:

> **두 길을 절대로 섞지 않는다.**

입니다.

전략자료는 이를 **“실시간과 분석의 절대 격리”**라고 표현합니다.

---

# 8. CDC, Kafka, ETL은 서로 대체 관계가 아닙니다

이 부분도 데이터플랫폼 구축에서 중요합니다.

세 기술이 모두 “데이터를 옮기는 것”처럼 보여도 책임은 완전히 다릅니다.

```text
                 DATA TRANSPORT

         ┌──────────┼───────────┐
         │          │           │
         ▼          ▼           ▼
        CDC       Kafka        ETL
         │          │           │
         ▼          ▼           ▼
      DB Change    Event      Bulk Data
         │          │           │
       RDW       FAST AP       ADW
```

### CDC

```text
Source DB
   ↓
변경 데이터 Capture
   ↓
CDC 중계
   ↓
RDW
```

책임은 **원천 데이터의 변경분 전달**입니다.

전략자료에서는 CDC 중계 서버를 둬 원천 DB 부하를 줄이고 실시간 데이터 갭을 관리하도록 정의합니다.

### Kafka

```text
Customer Event
   ↓
Kafka
   ↓
Consumer
   ↓
Real-time Reaction
```

책임은 **Event Streaming**입니다.

전략문서도 CDC와 Kafka를 같은 길로 사용하지 않고 **데이터 변화와 이벤트를 분리**합니다.

### ETL / DataStage

```text
RDW / Source
     ↓
정제
변환
집계
     ↓
ADW
```

책임은 **대량 데이터 정제·변환·분석 적재**입니다.

특히 대용량 데이터는 `ADW–DataStage` 기반 전용 배치 경로를 사용하도록 강제하는 것이 전략입니다.

따라서:

```text
CDC   = 변화의 길
Kafka = 사건의 길
ETL   = 대량가공의 길
```

이라고 이해하는 것이 가장 쉽습니다.

---

# 9. 왜 “데이터 경로 강제화”라는 표현을 사용하는가

이것도 NSIGHT 전략의 특징입니다.

일반적으로는:

```text
필요하면 개발자가
편한 방법으로 연결
```

하는 경우가 많습니다.

NSIGHT는 반대입니다.

```text
데이터 성격 판단
       │
       ├─ DB Change → CDC
       ├─ Event     → Kafka
       ├─ Bulk      → ETL
       ├─ Online    → RDW
       └─ Analytics → ADW
```

처럼 **길을 미리 정합니다.**

전략설명서에는 이것을 “데이터 흐름 강제 정의”라고 명확히 표현하고 있으며, 이 강제화가 장기적으로 기술부채를 줄이는 수단이라고 설명합니다.

이 정책이 없으면 5년 후에는 이런 구조가 생깁니다.

```text
System A ─DB Link──▶ System B
System A ─File─────▶ System C
System A ─Socket───▶ System D
System E ─직접SQL──▶ RDW
System F ─임의ETL──▶ ADW
```

그러면 데이터가 어디서 왔는지, 누가 책임지는지, 장애 영향이 어디까지인지 알 수 없습니다.

NSIGHT는 이것을 구조적으로 막으려는 것입니다.

---

# 10. 데이터플랫폼과 Integration 전략도 연결됩니다

데이터를 분리해 놓고 인터페이스를 무제한 허용하면 의미가 없습니다.

그래서 상위 Logical Architecture에서는:

```text
P2P
DB Link
임의 직접연계
```

를 통제하고 목적별 승인 경로를 사용합니다.

```text
API           → CruzAPIM
내부 계정계   → GSE
File          → FOS / MFT
대외          → MCA / MFT
DB Change     → CDC
Event         → Kafka
Bulk          → DataStage
```

전략 브리핑에서 실제로 이 연계 통제를 Logical Architecture의 핵심 정책으로 규정하고 있습니다.

즉:

> **데이터플랫폼 구축 = DB 구축 + Data Flow 구축 + Integration 통제**

입니다.

---

# 11. 물리 인프라 전략과도 직접 연결됩니다

왜 RDW와 ADW를 Exadata 같은 고성능 데이터 전용 인프라로 분리하고, 서비스 영역은 VM Scale-Out 구조로 가져가는지도 여기서 이해할 수 있습니다.

```text
                 WORKLOAD

          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
     Data Intensive       Service Intensive
          │                   │
          ▼                   ▼
    RDW / ADW         Marketing / BI AP
          │                   │
          ▼                   ▼
       Exadata         Private Cloud VM
          │                   │
   Parallel Scale          Scale-Out
```

즉 기술을 좋아해서 Exadata와 VM을 혼합한 것이 아닙니다.

> **Workload의 성격이 다르기 때문에 물리전략을 다르게 선택한 것**

입니다.

NFR 기준에도 서비스 서버는 VM Scale-Out, RDW/ADW는 Exadata 노드/병렬 확장으로 명시되어 있습니다.

---

# 12. 데이터플랫폼은 마케팅플랫폼과 이렇게 연결됩니다

이제 다음 플랫폼과 연결해 보면 전략이 더 명확해집니다.

```text
                    DATA PLATFORM

            CDC            Kafka
             │               │
             ▼               ▼
            RDW          Customer Event
             │               │
             └──────┬────────┘
                    ▼

                MARKETING
                PLATFORM

              Single View
                   +
              Event Context
                   +
              Marketing Rule
                   │
                   ▼
              Real-time Offer
```

즉 마케팅플랫폼은 자체적으로 모든 데이터를 만들지 않습니다.

**데이터플랫폼이 신뢰할 수 있는 고객 데이터를 공급하고, Kafka가 행동 Event를 공급하면, 마케팅플랫폼이 둘을 결합해 반응합니다.**

이것이 다음에 설명할 **“마케팅플랫폼 = 반응형 두뇌”**의 기반입니다.

---

# 13. 그리고 BI 포탈과는 이렇게 연결됩니다

```text
원천
 │
 ▼
CDC
 │
 ▼
RDW
 │
 ▼
DataStage
 │
 ▼
ADW
 │
 ├─ 집계
 ├─ Data Mart
 ├─ 분석
 └─ Reporting
 │
 ▼
BI Portal
 │
 ├─ Self-BI
 ├─ OLAP
 ├─ AI/NLP
 └─ Reporting
 │
 ▼
경영 판단
```

즉 BI 포탈이 데이터를 직접 수집하고 정제하는 구조가 아닙니다.

데이터플랫폼에서:

```text
신뢰
+
정제
+
분석 가능 구조
```

를 만들어 주고 BI 포탈은 그것을 **판단 가능한 정보로 소비**합니다.

# 14. 전략자료 기준으로 본 데이터플랫폼의 완성 조건

여기서 중요한 점이 있습니다.

전략 방향은 상당히 명확하지만 **구축 Baseline이 전부 닫힌 상태는 아닙니다.**

현재 Data Architecture 점검 결과는 `CONDITIONAL PASS`입니다. 이유는 RDW/ADW 물리분리, FAST/DEEP, CDC/Kafka/ETL 역할은 정립되어 있지만, 실제 데이터 소유권과 인터페이스 카탈로그까지 완성되어 있지는 않기 때문입니다.

특히 남아 있는 핵심은 다음입니다.

| 필요한 구축 상세화                | 현재 의미                               |
| --------------------------------- | --------------------------------------- |
| Domain별 Table/View Owner Catalog | “이 데이터의 주인은 누구인가”           |
| RDW/ADW Read/Write Matrix         | “누가 어느 DB를 읽고 쓸 수 있는가”      |
| CDC/Kafka/ETL Interface Registry  | “실제 모든 데이터 경로는 무엇인가”      |
| Data Freshness SLA Catalog        | “데이터마다 몇 초/몇 분까지 허용하는가” |
| 개인정보 Classification/Masking   | “누가 어떤 데이터를 볼 수 있는가”       |
| Runtime Data Metric → Gate        | “실제 SLA를 지켰다는 증거가 있는가”     |

이것이 **전략설명서에서 구축설계서로 넘어가면서 반드시 채워야 할 부분**입니다.

# 15. 그리고 자료 간 한 가지 중요한 기준값 충돌이 있습니다

이것도 그냥 넘어가면 안 됩니다.

대부분의 전략자료에서는:

```text
CDC 지연 ≤ 30초
```

를 사용합니다. 예를 들어 Vision/NFR 문서와 전략 정리본이 30초를 제시합니다.

그런데 한 발표자료 Runtime 장표에는:

```text
CDC ≤ 3초
```

라고 되어 있습니다.

따라서 현재는 이것을 임의로 하나로 합치면 안 됩니다.

```text
CDC SLA

30초
  vs
3초

→ Architecture Decision 필요
```

제가 현재 자료만으로 판단하면 **30초가 반복적으로 등장하는 전략 기준이고 3초는 별도 버전 장표에 존재하는 값**이지만, 최종 Baseline에서는 반드시 ADR/SLA 승인으로 하나를 확정해야 합니다.

이런 충돌을 찾아내는 것이 바로 전략자료를 실제 구축 기준으로 전환하는 작업입니다.

## 핵심 결론

NSIGHT 데이터플랫폼의 핵심은 **“큰 DW를 하나 더 만드는 것”이 아닙니다.**

> **데이터의 성격에 따라 FAST와 DEEP을 분리하고, RDW와 ADW를 물리적으로 격리하며, CDC·Kafka·ETL에 각기 다른 책임을 부여하고, 데이터가 반드시 정해진 길로 흐르도록 통제하는 아키텍처입니다.**

그리고 이것을 통해 얻으려는 가장 중요한 결과는 단순 성능 향상이 아니라:

> **“데이터는 틀리지 않는다”는 신뢰 + “실시간은 늦지 않는다”는 성능 + “분석이 온라인을 흔들지 않는다”는 강건함**

입니다. 전략 브리핑의 마지막 표현인 **“멈추지 않고, 늦지 않으며, 데이터가 틀리지 않는 실제 운영 가능한 데이터 중심 경영 플랫폼”**이 바로 이 전략을 가장 잘 압축합니다.

다음은 이 기반 위에 올라가는 **② 마케팅플랫폼 구축전략**으로 이어집니다. 여기서는 소스 계층보다 먼저 **왜 기존 Batch Marketing을 Real-time Reaction 구조로 바꾸는지, Customer Single View와 고객행동 Kafka Event가 어떻게 결합되는지, 그리고 왜 마케팅플랫폼을 ‘반응형 두뇌’라고 정의했는지**를 전략자료 중심으로 설명하는 것이 맞습니다.
