좋습니다. 이제 **20번째 설명 — NSIGHT Architecture WBS · 역할 · 산출물 · 완료조건 체계**로 진행하겠습니다.

19번까지는 Architecture Orchestrator가 전체 Closed Loop를 **어떻게 실행할 것인가**를 설명했습니다. 이제 그것을 실제 프로젝트 일정으로 내려야 합니다. 즉 이번에는:

> **“누가, 언제, 무엇을 수행하고, 어떤 문서를 만들며, 무엇을 확인해야 그 Task가 끝났다고 할 것인가?”**

를 정의하겠습니다.

실제 NSIGHT WBS 원본을 보면 아키텍처 영역은 **2025-12-08부터 2028-01-07까지** 이어지며, `현행분석 → 요구사항 → 방향성 → 설계/가이드 → 분석·설계 확립 → 구현/테스트 평가 → 운영/DR → 이행`으로 진행됩니다. 특히 초기 설계는 `Application / Logical / Physical / Interface / Data`를 병렬적으로 정의하도록 되어 있습니다.

# 20. NSIGHT Architecture WBS

## 20.1 먼저 중요한 관점 — WBS와 6단계 방법론은 같은 것이 아닙니다

우리가 지금까지 설명한 방법론은:

```text
Vision
   ↓
Big Picture
   ↓
Logical
   ↓
Physical
   ↓
Mechanism
   ↓
Runtime
```

입니다.

반면 WBS는:

```text
언제
누가
무엇을
어떤 순서로
어떤 산출물로
완료할 것인가
```

입니다.

따라서 관계는:

```text
Architecture Methodology
        │
        │ "무엇을 설계할 것인가"
        ▼
Architecture Work Package
        │
        │ "어떤 Task로 수행할 것인가"
        ▼
Project WBS
        │
        │ "언제/누가 수행할 것인가"
        ▼
Deliverable / Gate
```

라고 이해하면 됩니다.

---

# 20.2 실제 NSIGHT WBS의 큰 흐름

원본 일정 기준으로 주요 단계는 다음과 같습니다.

| WBS     | 실제 단계                      | 계획기간                | 대표 산출물         |
| ------- | ------------------------------ | ----------------------- | ------------------- |
| **1.1** | 사전분석                       | 2025-12-08 ~ 2026-04-03 | 분석 준비           |
| **1.2** | 현행 시스템 분석               | 2025-12-15 ~ 2026-01-30 | 현행 시스템 분석서  |
| **1.3** | 아키텍처 요구사항 정의         | 2026-01-26 ~ 2026-02-20 | 요구사항 정의서     |
| **1.4** | 아키텍처 방향성 분석           | 2026-02-02 ~ 2026-03-27 | 아키텍처 정의서     |
| **1.5** | 아키텍처 설계 및 가이드        | 2026-02-19 ~ 2026-03-31 | 각종 정의서/가이드  |
| **2.x** | 분석·설계 Architecture 확립    | 2026-04-06 ~ 2026-10-30 | 고도화 Architecture |

# 20.3 이것을 Architecture 수행모델로 다시 묶으면 9개 Workstream입니다

실제 WBS와 지금까지 만든 NSIGHT Architecture Methodology를 합치면 다음 9개 Workstream으로 관리하는 것이 가장 명확합니다.

```text
WS-01 Architecture Foundation
WS-02 Application Architecture
WS-03 Data Architecture
WS-04 Technical / Physical Architecture
WS-05 Interface Architecture
WS-06 Security Architecture
WS-07 Operation / HA-DR Architecture
WS-08 Runtime / Capacity / Validation
WS-09 Governance / Model / Gate
```

각 Workstream은 독립적으로 문서를 만드는 것이 아니라 아래처럼 연결됩니다.

```text
                     WS-01
               Vision / Big Picture
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
       WS-02        WS-03        WS-04
        AA            DA            TA
         │            │            │
         └──────┬─────┴─────┬──────┘
                ▼           ▼
              WS-05       WS-06
               IA        Security
                │           │
                └─────┬─────┘
                      ▼
                    WS-07
                Operation/HA-DR
                      │
                      ▼
                    WS-08
                 Runtime/Test
                      │
                      ▼
                    WS-09
                 Gate/Baseline
```

# 20.16 선후행 관계가 굉장히 중요합니다

예를 들어 Physical을 먼저 확정하면 안 됩니다.

잘못된 순서:

```text
서버 구매
   ↓
어떤 업무를 올릴지 결정
```

정상:

```text
Vision
   ↓
Domain
   ↓
Workload
   ↓
NFR
   ↓
Logical
   ↓
Capacity
   ↓
Physical Resource
```

같은 이유로:

```text
Hikari Pool 결정
```

보다 먼저:

```text
TPS
SQL Hold Time
DB Session
AP 수량
```

이 있어야 합니다.

# 20.17 Task의 완료조건은 “문서 작성 완료”가 아닙니다

```text
   ↓

   ↓

   ↓
Runtime Evidence
   ↓
Gate
```

따라서 완료상태도 나눠야 합니다.

```text

  ↓

  ↓
RUNTIME PROVEN
```

**작성 100%와 Architecture 완료 100%는 다른 개념**입니다.

# 20.31 20번의 핵심 결론

**NSIGHT Architecture WBS는 `Vision → Big Picture → Logical → Physical → Mechanism → Runtime`을 단순 일정으로 나열하는 것이 아니라, 이를 AA·DA·TA·IA·Security·Operation의 실제 Task로 분해하고 각 Task마다 입력자료, 책임자, 산출물, 선후행 관계, 완료조건과 Architecture Gate를 붙여 최종적으로 `Requirement → Design → Code/Config → Test → Runtime Evidence → Baseline`까지 닫히게 만드는 수행계획이어야 합니다.**

실제 NSIGHT WBS도 이미 `현행분석 → 요구사항 → 방향성 → Application/Logical/Physical/Interface/Data → 개발환경 → 운영/DR → 통합테스트`라는 큰 수행축을 갖추고 있습니다. 따라서 우리가 지금까지 만든 Closed Loop를 **기존 WBS를 대체하는 것이 아니라 완료조건과 검증체계를 보강하는 방식**으로 연결하는 것이 맞습니다.

그리고 현재 통합 Architecture Baseline의 관리원칙도 **WBS 결과를 지속 반영하고 AA/DA/TA/Interface를 독립 산출물로 관리하되 Big Picture와 Traceability를 유지하며, 성능·HA/DR·보안·Timeout은 Runtime Evidence와 Human Gate로 최종 승인한다**고 정의합니다.

**21번째 단계에서는 이 WBS를 다시 산출물 중심으로 바꾸어 `NSIGHT Architecture Deliverable Map`을 설명하겠습니다.** 즉 “아키텍처 정의서 한 권”이 아니라 **Vision, Big Picture, AA, DA, TA, IA, Security, HA/DR, Capacity, Migration, Runtime, Rulebook, Traceability, ADR, Gate Report를 어떤 문서체계와 디렉터리 구조로 관리하고 서로 어떻게 참조해야 하는가**를 정리하는 단계입니다.
