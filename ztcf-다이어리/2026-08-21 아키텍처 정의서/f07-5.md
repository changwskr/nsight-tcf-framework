좋습니다. 이제 5대 서비스 도메인의 마지막인 **⑤ IT서비스 및 업무지원 구축전략**으로 진행하겠습니다.

이번 영역은 특히 중요합니다. 자료를 다시 보면 IT서비스 및 업무지원은 단순히 `SSO`, `Control-M`, `GitLab` 같은 공통 솔루션을 모아 놓은 영역이 아닙니다. **NSIGHT 전체가 같은 표준으로 개발되고, 같은 방식으로 배포되고, 인증되고, 실행되고, 관측되고, 장애가 났을 때 복구될 수 있도록 만드는 공통 기반**입니다.

전략 브리핑은 NSIGHT를 `데이터플랫폼 · 마케팅플랫폼 · BI포탈 · 데이터거버넌스 · IT서비스 및 인프라 지원`의 **5개 플랫폼으로 구축**한다고 정의하며, IT지원 영역 안에 Control-M, SSO 등 독립 책임 공간을 둡니다.

# 1. 먼저 5대 플랫폼 전체에서 위치를 보겠습니다

지금까지 설명한 네 플랫폼은 각각 명확한 비즈니스 책임이 있었습니다.

```text
① DATA PLATFORM
   "데이터를 신뢰할 수 있게 공급"

② MARKETING PLATFORM
   "고객 행동에 즉시 반응"

③ BI PORTAL
   "현업과 경영진이 즉시 판단"

④ DATA GOVERNANCE
   "데이터의 의미·품질·흐름 통제"
```

그런데 이 네 플랫폼이 실제로 돌아가려면 다음 질문에 답할 영역이 필요합니다.

```text
누가 사용자를 인증하는가?
누가 Batch를 통제하는가?
누가 Framework 표준을 관리하는가?
소스는 어디서 관리하는가?
Library는 어디서 관리하는가?
배포는 누가 통제하는가?
단말은 누가 관리하고 배포하는가?
시스템 상태는 어떻게 관측하는가?
장애 때 운영자는 어디서 통제하는가?
DR에서도 어떤 공통기능이 살아 있어야 하는가?
```

그 역할이 바로:

```text
⑤ IT SERVICE / SUPPORT
```

입니다.

```text
          │ DevOps                  │
```

다만 **“Platform for Platforms”는 제 해석**이고, 원본 자료의 공식 명칭은 IT서비스 및 업무지원입니다.

어플리케이션 분류체계를 보면 IT서비스 및 업무지원은 **13개 업무영역**으로 나뉩니다.

# 5. 첫 번째 전략 — “Architecture Consistency”

NSIGHT는 여러 플랫폼이 독립적으로 구축됩니다.

```text
Data
Marketing
BI
Governance
```

그런데 독립적으로 만든다는 것이 각 팀이 제각각 만들라는 뜻은 아닙니다.

반대로:

```text
독립적인 Business Responsibility
             +
공통 Engineering Standard
```

이 동시에 있어야 합니다.

즉:

```text
Marketing Team
      │
BI Team
      │
Governance Team
      │
Data Team
      │
      ▼
──────────────────────
Common Architecture
Common Framework
Common Deployment
Common Logging
Common Security
──────────────────────
```

가 되어야 합니다.

이것이 IT서비스 영역에서 Framework와 Architecture Management가 존재하는 중요한 이유입니다.

전략 브리핑에서도 Mechanism 단계에서 **HTTP/JSON 규격통제, 표준 전문, Framework 통일, Integration 통제**를 통해 논리설계를 실행규칙으로 강제하도록 정의합니다.

# 6. NH Cloud Framework Master Solution의 전략적 위치

이것은 단순 Framework Runtime과는 역할이 다릅니다.

개념적으로는:

```text
                  Architecture Standard
                          │
                          ▼
               Framework Standard
                          │
                          ▼
              FWK Master Solution
                          │
             ┌────────────┼─────────────┐
             ▼            ▼             ▼
         Marketing       BI        Governance
```

처럼 **Framework 일관성 관리 기반**으로 보는 것이 자연스럽습니다.


즉 단순 도구의 집합이 아니라 **Software Supply Chain**을 만들려는 구조로 해석할 수 있습니다.

# 8. NEXUS는 왜 아키텍처에 포함되는가

선도환경 장표에는 `NEXUS`가 독립 구성요소로 들어 있습니다.

단순히 Java Library 다운로드용이라 생각하면 안 됩니다.

개념적으로:

```text

   │
   ▼

   │
   ├── 외부/공통 Library
   │
   ▼
NEXUS
   │
   ▼
Controlled Artifact
```

구조를 만들 수 있습니다.

즉:

> 개발환경마다 다른 Library를 임의로 사용하는 문제를 줄이고, 배포 대상과 Dependency를 관리하는 기반

입니다.

다만 현재 장표에서는 NEXUS의 Repository 정책이나 버전정책까지는 정의하지 않습니다.

# 9. 세 번째 전략 — 배치는 별도의 실행 공간으로 분리합니다

전략 브리핑에서는 명확하게:

```text
Online AP
   ≠
Batch AP
```

를 정의합니다.

그리고 `Control-M`을 **배치작업 관리 공간**으로 별도 정의합니다.

왜 분리하는지 보면:

```text
온라인
   │
   │ 고객 응답 SLA
   ▼

   │
   │ 대량 처리
   ▼
Throughput / Schedule
```

두 Workload의 목표가 다르기 때문입니다.

# 10. Control-M은 단순 Scheduler가 아니라 Batch Control Plane입니다

자료상 확인되는 직접 사실은:

```text
Control-M
= 배치/스케줄 구성요소
```

입니다. 선도환경에도 독립 구성요소로 포함됩니다.

전략관점에서는 이를:

```text
                BATCH

Job A ──┐
Job B ──┼──▶ Control-M
Job C ──┘        │
                 ├─ 실행순서
                 ├─ Schedule
                 └─ Job Control
                       │
                       ▼
                    Batch AP
```

와 같은 **Batch 실행 통제 공간**으로 볼 수 있습니다.

세부 Retry/Dependency/SLA 정책은 현재 인용 자료만으로 확정하지 않겠습니다.

---

# 11. 이것이 FAST / DEEP 분리와도 연결됩니다

앞에서 NSIGHT의 핵심을:

```text
FAST
≠
DEEP
```

이라고 설명했습니다.

IT서비스 영역에서는 이 전략이 운영 자원으로 내려옵니다.

```text
FAST
│
├─ Online AP
├─ Event Server
└─ RDW


DEEP
│
├─ Batch AP
├─ ETL
└─ ADW
```

그리고 각각을:

```text
Online Runtime
Control-M
ETL Control
```

등으로 독립 운영합니다.

즉 **IT서비스 영역은 FAST/DEEP 분리를 실제 운영에서 유지하게 만드는 지원체계**입니다.

# 12. 네 번째 전략 — CDC와 ETL도 IT서비스 분류 안에 들어 있습니다

어플리케이션 분류체계를 자세히 보면 흥미로운 부분이 있습니다.

```text
CD = CDC Gateway
DT = Data Transform Load
```

가 `IM` 영역에 포함되어 있습니다.

이것은 데이터플랫폼과 IT서비스의 책임을 구분해서 봐야 합니다.

### Data Platform

```text
데이터의 논리적 소유/활용
RDW / ADW
```

### IT Service / Support

```text
데이터 이동을 수행·지원하는
실행 인프라/운영 기능
CDC / ETL
```

정도로 이해할 수 있습니다.

즉:

```text
                DATA PLATFORM
                 RDW / ADW
                     ▲
                     │
          ┌──────────┴───────────┐
          │                      │
         CDC                    ETL
          │                      │
          └──────────┬───────────┘
                     │
              IT SERVICE SUPPORT
```

입니다.

이렇게 보면 데이터플랫폼과 IT서비스가 겹치는 것이 아니라 **Data Responsibility와 Data Movement Runtime Responsibility를 분리**한 구조로 해석할 수 있습니다.

# 13. 다섯 번째 전략 — SSO를 공통 인증공간으로 둡니다

전략 브리핑은 보안을 하나의 기능이 아니라 **구조**라고 정의합니다.

또한 SSO 통합인증 준수를 명시합니다.

선도환경에도 실제로:

```text
SSO
```

가 공통 플랫폼 요소로 배치되어 있습니다.

따라서 구조는:

```text
                     SSO
                      │
             통합 Authentication
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   Marketing          BI        Governance
```

가 기본 방향입니다.

중요한 것은:

```text
각 Application마다
독자 Login 구현
```

을 피하고,

```text
통합 Authentication
       +
업무별 Authorization
```

으로 책임을 나누는 것입니다.

JWT/KMS 같은 상세 Mechanism은 이 상위 보안전략 아래에서 설명해야 합니다.

---

# 14. 즉 JWT는 SSO 전략의 하위 Mechanism입니다

위치 관계를 다시 정확히 잡으면:

```text
NSIGHT Security Strategy
         │
         ▼
통합 Authentication
         │
         ▼
        SSO
         │
         ▼
Authentication Mechanism
         │
         ├─ JWT
         ├─ Access Token
         ├─ Refresh Token
         ├─ KMS
         └─ JWKS
```

입니다.

앞서 제가 JWT부터 먼저 설명했던 것도 사실 순서가 반대였습니다.

상위 전략은 **통합 인증과 보안 내재화**이고, JWT는 이를 구현하는 하위 기술입니다.

# 15. 여섯 번째 전략 — “관측되지 않으면 운영할 수 없다”

전략 브리핑의 5대 NFR 중 하나가 **Observability**입니다.

원문은 매우 강합니다.

> **“측정되지 않는 시스템은 운영할 수 없다.”**

그리고 다음을 요구합니다.

- APM 차원의 시스템 단위 관측성
- 전사 통합로그 관리
- Trace ID 기반 전문 추적

즉:

```text
Application
     │
     ├─ Performance
     ├─ Log
     ├─ Trace
     ├─ Error
     └─ Runtime State
           │
           ▼
       Operation
```

으로 가야 합니다.

라고 볼 수 있습니다.

---

# 18. 일곱 번째 전략 — 단말 역시 중앙관리 대상입니다

IT서비스 분류에서 단말은 두 개로 명확히 분리됩니다.

```text
XM = 정보단말 관리
XD = 정보단말 배포
```

실제 선도환경에도:

```text
단말관리 WEB
단말관리 WAS

단말배포 WEB
단말배포 WAS

단말개발도구 AP
```

가 존재합니다.

즉 단말은 사용자 PC에 설치해 끝나는 Client가 아닙니다.

```text
개발
 ↓
단말 Artifact
 ↓
배포
 ↓
단말
 ↓
버전관리
 ↓
운영관리
```

라는 **관리 Lifecycle**의 대상입니다.

---

# 19. 단말관리와 단말배포를 왜 분리하는가

자료에서는 두 시스템을 실제로 별도 WEB/WAS로 분리합니다.

```text
Terminal Management
        ≠
Terminal Deployment
```

이는 책임이 다르다는 뜻입니다.

개념적으로:

```text
단말관리
=
현재 단말 상태 관리


단말배포
=
새 Version / Artifact 전달
```

로 보는 것이 자연스럽습니다.

다만 원자료에서 두 시스템의 상세 업무기능까지는 제시하지 않으므로 이 이상의 세부 동작은 확정하지 않겠습니다.

---

# 20. 선도환경을 보면 IT서비스 구축 순서가 보입니다

이 부분이 매우 중요합니다.

선도환경은 전체 NSIGHT를 다 만드는 환경이 아닙니다.

그런데 IT서비스 영역에는 이미 다음이 들어갑니다.

```text
SSO
Control-M
NH Cloud FWK Master Solution
eCAMS
NEXUS
단말관리
단말배포
단말개발도구
소스관리
```

왜 업무 전체가 준비되기 전부터 이 기능들을 먼저 구성할까요?

전략적으로는:

> **본 개발이 시작되기 전에 개발·Framework·인증·배포의 공통 레일을 먼저 만들어야 하기 때문**

이라고 해석할 수 있습니다.

---

# 21. 이것이 중요한 구축전략입니다

잘못된 프로젝트 순서는:

```text
각 팀 개발 시작
      ↓
나중에 Framework 통합
      ↓
나중에 Git 규칙 통합
      ↓
나중에 배포 표준화
      ↓
대규모 재작업
```

입니다.

NSIGHT 선도환경 구성에서 읽히는 방향은 오히려:

```text
공통 개발기반
    │
    ├─ Source
    ├─ Framework
    ├─ Library
    ├─ Authentication
    └─ Deployment
         │
         ▼
      Pilot 검증
         │
         ▼
    본 개발 확대
```

에 가깝습니다.

이것이 IT서비스 영역을 **선행 구축해야 하는 이유**입니다.

---

# 22. 개발·운영·선도·DR에 공통적으로 존재하는 요소도 있습니다

선도환경 분석자료를 보면 다음 네 요소는 운영·개발·선도·DR 모두 `O`로 정리되어 있습니다.

```text
SSO
Control-M
NH Cloud FWK Master Solution
eCAMS
```

이것은 상당히 중요한 신호입니다.

이 네 요소는 단순 개발 편의 도구가 아니라 **환경 전체를 가로지르는 핵심 공통서비스**에 가깝습니다.

---

# 23. DR에서도 IT서비스가 필요한 이유

센터가 장애나도 업무 Application 서버만 살아있다고 서비스가 가능한 것이 아닙니다.

예를 들어:

```text
Marketing WAS 살아있음
RDW 살아있음
```

이어도:

```text
SSO 없음
→ Login 불가

공통 Framework 운영기반 없음
→ 관리 제한

운영통제 없음
→ 복구/운영 난이도 증가
```

가 될 수 있습니다.

따라서 DR에서도 공통 기반의 일부를 유지해야 합니다.

실제 DR 보완자료에서도:

- SSO
- Control-M
- NH Cloud FWK Master Solution
- eCAMS

가 DR 공통기반에 포함되는 것으로 확인됩니다.

---

# 24. 다만 DR은 운영 전체를 1:1 복제하지 않습니다

이 부분도 중요한 전략입니다.

운영 IT서비스에는 더 많은 요소가 있습니다.

예를 들어 자료상 운영에는:

```text
Batch AP
CDC
ETL
Report Designer
UNO Dashboard
Terminal Management
Terminal Deployment
...
```

등이 나타납니다.

반면 DR에는 운영의 모든 요소가 동일하게 표시되지 않습니다. DR 통합분석에서도 IT서비스 영역이 **운영 대비 축소 구성**으로 나타납니다.

즉:

```text
PROD
= Full Operation Capability

DR
= Minimum Business Continuity Capability
```

에 가까운 구조입니다.

다만 **최종 DR 범위는 상세 DR 기준과 다시 대조해야 합니다.** 자료 자체도 일부 장표 사이에 구성요소 표시 차이가 있습니다.

---

# 25. 따라서 IT서비스 DR에서는 “서비스 중요도”를 정의해야 합니다

운영과 동일하게 다 복제하지 않는다면 반드시 다음 분류가 필요합니다.

```text
IT Service Component
       │
       ├─ Tier 0 : DR 필수
       ├─ Tier 1 : 조기 복구
       └─ Tier 2 : 사후 복구
```

예를 들어 현재 자료만 보면:

```text
SSO
Control-M
FWK Master
eCAMS
```

는 DR에도 표시되는 공통요소입니다.

하지만 전체 Tier 체계 자체는 아직 자료에서 확정되지 않았습니다.

따라서 **DR Service Criticality Matrix**는 후속 설계가 필요합니다.

---

# 26. IT서비스를 “Engineering & Operations Lifecycle”로 보면 전체가 연결됩니다

지금까지 요소를 따로 보았지만, 사실 하나의 순환구조입니다.

```text
              ARCHITECTURE
                   │
                   ▼
               STANDARD
                   │
                   ▼
               FRAMEWORK
                   │
                   ▼
                 SOURCE
                   │
                   ▼
                 BUILD
                   │
                   ▼
                LIBRARY
                   │
                   ▼
                DEPLOY
                   │
                   ▼
                RUNTIME
                   │
            ┌──────┼──────┐
            ▼      ▼      ▼
          SSO    Batch  Terminal
            │      │      │
            └──────┼──────┘
                   ▼
              OPERATION
                   │
              APM / Log
                   │
                   ▼
                FEEDBACK
                   │
                   └────────────→ ARCHITECTURE
```

저는 이 구조가 **NSIGHT IT서비스 및 업무지원의 본질**이라고 봅니다.

원자료가 위 순환구조를 한 장으로 명시한 것은 아니지만, 개별 분류와 구성요소를 통합하면 이렇게 해석할 수 있습니다.

---

# 27. 더 중요한 것은 Architecture Management가 실제로 IM에 들어 있다는 점입니다

IT서비스 업무분류의 첫 항목이:

```text
AM = Architecture Management
```

입니다.

이건 의미가 큽니다.

아키텍처가 프로젝트 초기에 설계서 한번 작성하고 사라지는 것이 아니라,

```text
Architecture
   ↓
Standard
   ↓
Implementation
   ↓
Deployment
   ↓
Operation
```

Lifecycle 속에서 관리돼야 한다는 방향과 연결될 수 있습니다.

현재 프로젝트에서 추진해 온:

```text
Architecture as Document
        ↓
Model
        ↓
Code
        ↓
Test
        ↓
Runtime Evidence
```

도 이 `Architecture Management` 영역과 향후 연결할 수 있습니다.

다만 현재 원본 시스템 장표 자체가 Closed Loop 구현까지 정의하고 있는 것은 아닙니다. 이 부분은 후속 아키텍처 발전안입니다.

---

```text
 │                 DATA GOVERNANCE                          │

     ┌───────────────────┼───────────────────┐
     │                   │                   │
     ▼                   ▼                   ▼

┌───────────────┐ ┌────────────────┐ ┌────────────────┐
│ DATA PLATFORM │ │ MARKETING      │ │ BI PORTAL      │
│               │ │ PLATFORM       │ │                │
```

위 그림에서 아래의 `Engineering & Operations Foundation`이라는 명칭은 제가 역할을 설명하기 위해 붙인 표현입니다.

원본의 공식 도메인은 **IT서비스 및 업무지원**입니다.

# 29. 5개 도메인을 한 문장씩 정의하면

이제 전략설명서의 전체 구조를 다음처럼 기억하면 됩니다.

| 도메인                   | 한 문장 정의                                                      |
| ------------------------ | ----------------------------------------------------------------- |
| **데이터플랫폼**         | 데이터를 실시간·분석 목적에 맞게 신뢰할 수 있도록 공급한다        |

| **IT서비스 및 업무지원** | 나머지 모든 플랫폼이 같은 표준으로 개발·배포·인증·운영되게 만든다 |

# 31. 여기서 현재 전략자료의 중요한 GAP도 보입니다

IT서비스 영역은 구성요소는 상당히 구체적입니다. 하지만 **구성요소 간 운영 책임과 Lifecycle 계약**은 아직 더 구체화할 필요가 있습니다.

현재 자료를 기준으로 추가 정의가 필요한 것은 다음과 같습니다.

| 상세화 대상                             | 필요한 이유                           |
| --------------------------------------- | ------------------------------------- |
| Architecture Management 상세 기능       | `AM`의 실제 관리범위 확정             |
| Git/Build/Artifact/Deploy 전체 Pipeline | End-to-End 개발·배포 표준             |
| eCAMS 책임범위                          | 배포/운영/승인 역할 명확화            |
| FWK Master 책임범위                     | Framework 관리·배포·버전 통제         |
| Library/NEXUS 정책                      | Artifact·Dependency Version 통제      |
| Batch 표준                              | Control-M Job/SLA/Dependency 운영규칙 |
| SSO/JWT 책임경계                        | Authentication/Authorization 경계     |
| Observability 모델                      | APM/Log/Trace/Alert 통합              |
| DR Criticality Matrix                   | 공통서비스별 DR 우선순위              |
| Terminal Lifecycle                      | 개발→배포→회수/Version 관리           |
| CDC/ETL 운영 책임                       | Data Platform과 IM 책임경계           |
| 운영권한 모델                           | 누가 무엇을 변경할 수 있는가          |

즉 **제품 배치는 상당히 보이지만, 운영모델을 Architecture Baseline으로 닫는 작업이 남아 있습니다.**

# 32. 이제 5대 플랫폼 설명은 한 사이클 끝났습니다

우리는 전략 브리핑의 핵심 5개 플랫폼을 모두 연결했습니다.

```text
1. DATA PLATFORM
      ↓
   데이터 신뢰

2. MARKETING PLATFORM
      ↓
   실시간 반응

3. BI PORTAL
      ↓
   즉시 판단

4. DATA GOVERNANCE
      ↓
   의미·품질 통제

5. IT SERVICE / SUPPORT
      ↓
   개발·배포·운영 지속성
```

그리고 이것들이:

```text
Scalable
+
Resilient
+
Data-Centric
```

이라는 NSIGHT의 상위 Architecture Character를 구현합니다. 전략 브리핑은 이러한 도메인 분리와 책임 공간의 독립화를 통해 성능·장애격리·확장성을 확보하도록 정의하고 있습니다.

**이제 다음 단계부터가 매우 중요합니다.** 5개 플랫폼을 개별적으로 설명하는 단계에서 벗어나, 이들을 하나의 **NSIGHT 전체 구축 아키텍처**로 합쳐야 합니다.

다음 설명에서는 `① 채널 → ② 채널통합 → ③ 5대 서비스 도메인 → ④ 대내통합 → ⑤ FAST/DEEP 데이터 흐름 → ⑥ Main/DR → ⑦ 개발·선도·운영 환경`을 한 장의 **NSIGHT Big Picture 구축전략**으로 통합해서 설명하겠습니다. 이것이 그다음 Logical·Physical Architecture를 이해하는 기준점이 됩니다.
