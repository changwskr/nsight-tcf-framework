좋습니다. 이제 **② 마케팅플랫폼 구축전략**을 전략설명서와 실제 논리 기술 아키텍처를 함께 놓고 보겠습니다.

이번에는 특히 중요한 점이 하나 있습니다. 전략 브리핑에서 정의한 **“반응형 두뇌”**와 상세 논리 아키텍처의 `Wise Collector → Kafka → 행동정보처리 → RDW → 실시간처리/EBM` 구조를 대조해 보면, **최종 구축 전에 반드시 정리해야 할 Architecture GAP도 하나 보입니다.** 이 부분까지 같이 설명하겠습니다.

# 1. 마케팅플랫폼은 무엇을 바꾸려는 것인가

전략자료에서 마케팅플랫폼의 목적은 단순한 캠페인 기능 고도화가 아닙니다.

> **“배치형 마케팅에서 고객 행동에 즉시 반응하는 Reaction Brain으로 전환한다.”**

는 것이 핵심입니다. 전략 정리본은 기존 마케팅이 고객이 떠난 뒤 데이터를 모아 분석하는 사후 대응 방식이었다면, 차세대는 고객의 찰나 행동에 즉시 대응하는 실시간 지능형 플랫폼이라고 정의합니다.

이를 가장 쉽게 비교하면 다음과 같습니다.

| 기존 Batch Marketing  | NSIGHT Real-time Reaction |
| --------------------- | ------------------------- |
| 데이터를 모은 뒤 분석 | 행동 발생 즉시 Event 수집 |
| 수시간 또는 익일 실행 | **1초 이내 오퍼링 목표**  |
| 정해진 시간 Push      | 행동 기반 Reaction        |
| 고객이 떠난 뒤 대응   | 고객이 행동하는 순간 대응 |
| 데이터는 분석용 자산  | 데이터는 실행 자산        |

발표자료도 이를 `Batch Marketing → Real-time Reaction Marketing` 전환으로 명확하게 설명합니다.

즉 마케팅플랫폼의 사업적 의미는:

```text
기존

고객 행동
   ↓
데이터 저장
   ↓
Batch
   ↓
분석
   ↓
다음날 Campaign


                ↓


NSIGHT

고객 행동
   ↓
즉시 감지
   ↓
맥락 판단
   ↓
Offer 결정
   ↓
즉시 실행
```

입니다.

---

# 2. 그래서 마케팅플랫폼을 “반응형 두뇌”라고 합니다

앞에서 데이터플랫폼을 **기초공사**라고 했습니다.

이제 역할이 이렇게 연결됩니다.

```text
              NSIGHT

     DATA PLATFORM
     "신뢰할 수 있는 데이터"
             │
             ▼
     MARKETING PLATFORM
       "반응하는 두뇌"
             │
             ▼
         고객 Action
```

데이터플랫폼이 데이터를 공급한다고 해서 고객에게 가치가 자동으로 생기는 것은 아닙니다.

마케팅플랫폼이 해야 하는 것은:

```text
데이터
 +
고객 행동
 +
현재 맥락
 +
마케팅 정책

      ↓

"지금 이 고객에게
 무엇을 해야 하는가?"
```

를 판단하는 것입니다.

전략자료가 마케팅플랫폼을 단순 보고 시스템이 아니라 **실행하는 비즈니스 두뇌(Reaction Brain)**라고 표현하는 이유입니다.

---

# 3. 반응형 두뇌를 만드는 2대 핵심 역량

전략설명서는 이를 정확히 두 가지로 정의합니다.

```text
             REACTION BRAIN

       ┌──────────┴──────────┐
       │                     │
       ▼                     ▼
Customer Single View     Kafka Event Engine
 "고객을 이해"            "행동을 즉시 감지"
       │                     │
       └──────────┬──────────┘
                  ▼
            Next Best Action
                  │
                  ▼
             Real-time Offer
```

두 가지 중 하나라도 없으면 실시간 마케팅이 제대로 성립하지 않습니다.

---

# 4. 첫 번째 핵심 — Customer Single View

실시간 반응에서 가장 중요한 것은 단순히 이벤트를 빨리 받는 것이 아닙니다.

예를 들어:

```text
고객 A가
대출상품 페이지를 클릭했다.
```

라는 이벤트만 받았다고 하겠습니다.

이 정보만으로는 어떤 Offer를 해야 할지 모릅니다.

필요한 것은 **고객의 맥락(Context)**입니다.

전략문서가 Customer Single View에 통합하려는 정보는 크게 다음 네 범주입니다.

```text
                CUSTOMER 360

       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
금융거래정보    디지털 행동     채널 접점
       │            │            │
       └────────────┼────────────┘
                    │
              Campaign History
                    │
                    ▼
               고객 Context
```

예를 들어 고객 A를 보면:

```text
Customer A

예금       5천만원
대출       없음
최근 조회   주택담보대출 5회
모바일      금리계산기 사용
영업점      상담 이력 존재
Campaign   대출 Offer 미반응
```

이렇게 여러 정보를 합쳐야 합니다.

그제야:

```text
"고객이 지금 주택자금에 관심이 높다"

        ↓

Next Best Action
```

같은 판단이 가능해집니다.

그래서 Single View는 단순한 고객 조회 화면이 아니라 **실시간 의사결정을 위한 Context Provider**입니다.

---

# 5. 두 번째 핵심 — Kafka 기반 고객행동 Event Engine

Customer Single View가 고객의 **맥락**이라면 Kafka는 고객의 **지금 행동**을 알려주는 신경망입니다.

```text
고객
 │
 │ Click / Search / Visit / Action
 ▼
Web / Mobile / Channel
 │
 ▼
Event Collector
 │
 ▼
Kafka
 │
 ▼
Marketing Processing
```

전략자료는 Kafka의 역할을 대량 이벤트 병렬 처리, 이벤트 순서 보장, 수평 확장, 장애 격리, DB 비의존 처리 등으로 설명합니다.

이 구조의 중요한 의미는:

```text
Polling
```

이 아니라

```text
Event Driven
```

이라는 것입니다.

기존:

```text
"무슨 일이 생겼나?"
DB를 계속 조회
```

차세대:

```text
"일이 생겼다!"
Event가 즉시 전달
```

입니다.

---

# 6. NSIGHT FAST 경로와 마케팅플랫폼

앞에서 설명했던 FAST가 바로 마케팅플랫폼의 핵심 Runtime입니다.

전략자료에는 이 흐름이 매우 명확합니다.

```text
고객 행동
   │
   ▼
Kafka
   │
   ▼
Marketing Rule Engine
   │
   ▼
Offer 결정
   │
   ▼
1초 이내 실행
```

그리고 FAST의 핵심 원칙은:

```text
Event Driven
+
DB 비의존
+
경량 처리
+
1초 이내
```

입니다.

이것이 중요한 이유가 있습니다.

만약 실시간 Offer를 만들기 위해 매번:

```text
Event
 ↓
DB
 ↓
여러 SQL
 ↓
대량 Join
 ↓
Batch 계산
 ↓
Offer
```

를 해야 한다면 **1초 Reaction Architecture가 아닙니다.**

FAST Path에서는 미리 준비된 고객 Context와 Event를 조합해 빠르게 판단해야 합니다.

# 7. 실제 논리 기술 아키텍처에는 어떻게 구현되어 있는가

이제 여기부터 전략을 실제 구축자료와 연결해 보겠습니다.

업로드된 마케팅플랫폼 논리 기술 아키텍처에는 다음 구조가 실제로 정의되어 있습니다.

```text
[고객 / Channel]
       │
       ▼
WEB / Mobile
       │
       ▼
Wise Collector Proxy
       │
       ▼
Wise Collector
       │
       │ publish
       ▼
Kafka 고객행동 데이터
       │
       │ subscribe
       ▼
행동정보 처리서버
       │
       ├─────▶ RDW
       │
       ▼
실시간 처리 / Event
       │
       ▼
EBM
       │
       ▼
Offer / Message
       │
       ▼
UMS
       │
       ├─ SMS
       ├─ PUSH
       └─ MAIL
```

즉 전략의 추상개념이 실제 구축에서는 다음 컴포넌트로 내려갑니다.

| 전략개념       | 상세 구축 컴포넌트                    |
| -------------- | ------------------------------------- |
| 고객행동 수집  | Wise Collector Proxy / Wise Collector |
| Event Backbone | Kafka                                 |
| 행동 해석/처리 | 행동정보 처리서버                     |
| 고객 Context   | RDW / Single View                     |
| 실시간 마케팅  | 실시간 처리서버 / EBM                 |
| 고객 전달      | UMS / SMS / PUSH / MAIL               |

이제야 **전략 → 논리 구축 → 기술 컴포넌트**가 연결됩니다.

# 8. 실제 업무 처리유형에서도 별도의 마케팅 Event 흐름으로 정의되어 있습니다

업로드된 업무처리유형 장표에서는 전체 NSIGHT 거래를 12개 유형으로 분류하고 있습니다.

그중 마케팅은 별도로:

```text
⑥ 실시간 고객 반응형 정보 수집
⑦ 실시간 고객 오퍼링 제공
```

두 유형으로 분리합니다.

## ⑥ 고객 반응 수집

```text
고객 행동
   ↓
Wise Collector
   ↓
Kafka
```

즉 **Inbound Event Flow**입니다.

## ⑦ 고객 Offer

```text
Kafka Event
   ↓
행동정보 처리
   ↓
Realtime EBM
   ↓
Offer
```

즉 **Decision / Outbound Flow**입니다.

이 분리가 상당히 중요합니다.

```text
COLLECT
   ≠
DECIDE
   ≠
DELIVER
```

입니다.

# 9. 즉 실시간 마케팅은 3개의 책임으로 분리해야 합니다

제가 전략과 실제 구축자료를 함께 보면 다음 구조가 가장 명확합니다.

```text
               REAL-TIME MARKETING

① SENSE
고객 행동 감지
     │
     ▼
Wise Collector
     │
     ▼
Kafka

──────────────────────────────────

② THINK
고객 Context
      +
Event
      +
Marketing Rule
     │
     ▼
Realtime / EBM

──────────────────────────────────

③ ACT
Offer
     │
     ▼
UMS / Channel
     │
     ▼
Customer
```

즉:

> **Sense → Think → Act**

구조입니다.

이것이 마케팅플랫폼을 **Reaction Brain**이라고 부르는 가장 정확한 설명입니다.

# 11. 데이터플랫폼과 마케팅플랫폼의 역할을 섞으면 안 됩니다

이 부분도 중요합니다.

```text
DATA PLATFORM
```

은:

> **고객 데이터를 신뢰할 수 있게 준비**

하는 곳이고,

```text
MARKETING PLATFORM
```

은:

> **그 데이터를 이용해 행동을 결정**

하는 곳입니다.

따라서:

```text
          DATA PLATFORM

계정계 ─CDC─▶ RDW
                │
                │ Customer Context
                ▼
        MARKETING PLATFORM
                ▲
                │ Event
              Kafka
                ▲
                │
            고객 행동
```

입니다.

즉 마케팅플랫폼이 직접 거대한 데이터 정제 플랫폼이 되어서는 안 됩니다.

이는 Big Picture의 기본 철학인:

> **“채널은 채널의 역할만, 플랫폼은 플랫폼의 역할만 수행해야 한다.”**

와도 정확히 연결됩니다.

# 12. BI와 마케팅의 차이도 아주 중요합니다

둘 다 데이터를 사용하지만 목적은 다릅니다.

```text
MARKETING

"이 고객에게 지금 무엇을 할 것인가?"

        ↓

ACTION
```

반면:

```text
BI

"우리 사업에서 지금 무슨 일이 일어나고 있고,
어떤 판단을 해야 하는가?"

        ↓

DECISION
```

따라서 NSIGHT의 사업 흐름은:

```text
Data Platform
   │
   │ TRUST
   ▼
Marketing
   │
   │ REACTION
   ▼
Customer Action


Data Platform
   │
   │ INSIGHT
   ▼
BI Portal
   │
   │ DECISION
   ▼
Management Action
```

두 경로가 존재합니다.

# 13. 마케팅플랫폼도 Resource Isolation 대상입니다

전략자료에는 이벤트 서버를 별도 기능 공간으로 구성한다고 명시되어 있습니다.

```text
Online AP
   ≠
Batch AP
   ≠
ETL
   ≠
Event Server
```

입니다.

왜 Event를 별도로 분리하느냐 하면:

```text
일반 온라인 거래 급증
        X
실시간 Event 처리

Batch 폭주
        X
Marketing Reaction
```

을 만들기 위해서입니다.

즉 Event Server 분리는 기술 선택이 아니라 **1초 SLA 보호를 위한 Resource Isolation 전략**입니다.

# 14. 여기서 중요한 Architecture GAP이 하나 발견됩니다

전략자료와 상세 논리 아키텍처를 대조해 보면 반드시 확인해야 할 부분이 있습니다.

전략은 FAST를 이렇게 정의합니다.

```text
고객 Event
   ↓
Kafka
   ↓
Marketing Rule Engine
   ↓
Offer

★ DB 비의존
★ 1초 이내
```

그런데 상세 논리 기술 아키텍처에는 다음도 존재합니다.

```text
Kafka
 ↓
행동정보 처리서버
 ↓
RDW

그리고

실시간 처리서버
 ↓
polling / JDBC
 ↓
RDW
```

여기에는 중요한 질문이 생깁니다.

> **최종 Offer 결정이 RDW Polling을 기다리는가?**

만약 **YES**라면 전략의:

```text
DB 비의존 Fast Path
```

와 충돌할 가능성이 있습니다.

# 15. 이 부분은 반드시 설계결정으로 닫아야 합니다

제가 현재 자료에서 제안이 아니라 **확인이 필요하다고 보는 핵심 Decision Point**는 이것입니다.

```text
                      EVENT
                        │
                      Kafka
                        │
        ┌───────────────┴────────────────┐
        │                                │
        ▼                                ▼
   FAST Decision                   Async Persistence
        │                                │
  Rule / Context                         RDW
        │
        ▼
      Offer
```

이 구조인지,

아니면:

```text
Kafka
 ↓
RDW 저장
 ↓
Polling
 ↓
Realtime Server
 ↓
EBM
 ↓
Offer
```

구조인지 명확히 결정해야 합니다.

첫 번째라면 전략의 **DB 비의존 1초 Fast Path**와 잘 맞습니다.

두 번째라면 **1초 SLA를 어떻게 보장하는지 별도의 Runtime Evidence가 반드시 필요합니다.**

현재 업로드 자료만으로는 어느 것이 최종 확정 Baseline인지 단정하면 안 됩니다.

이것은 실제 Architecture Review에서 **P0/P1급 확인사항**으로 보겠습니다.

# 17. 마케팅플랫폼의 구축 성공조건

전략자료와 상세구성도를 함께 보면 실제 구축 성공 여부는 단순히 “Kafka가 설치되었는가”로 판단할 수 없습니다.

아키텍처적으로 확인해야 할 것은 다음과 같습니다.

| 검증대상         | 질문                                                   |
| ---------------- | ------------------------------------------------------ |
| Customer Context | Single View가 의사결정에 필요한 고객 맥락을 제공하는가 |
| Event Collection | 고객 행동이 유실 없이 Kafka까지 도달하는가             |
| Event Latency    | 행동 발생→Kafka→Decision 시간이 얼마인가               |
| Decision         | Event+Context+Rule로 즉시 판단 가능한가                |
| DB Dependency    | FAST Path가 DB 병목에 종속되는가                       |
| Offering         | 전체 End-to-End가 1초 목표를 만족하는가                |
| Fault Isolation  | Kafka/EBM 장애가 일반 온라인에 전파되는가              |
| Scalability      | Event 폭증 시 독립 Scale-Out 가능한가                  |
| Observability    | GUID/Event ID로 전체 경로 추적 가능한가                |
| Feedback         | Offer 결과가 다시 고객 Context로 반영되는가            |

여기까지 충족되어야 **“Reaction Brain이 구축됐다”**고 볼 수 있습니다.

---

# 18. 그리고 가장 중요한 것은 “선순환”입니다

마케팅이 Offer를 보낸다고 끝나는 것이 아닙니다.

```text
Customer
   │
   │ 행동
   ▼
Event
   │
   ▼
Understand
   │
   ▼
Decide
   │
   ▼
Offer
   │
   ▼
Customer Reaction
   │
   ▼
Feedback
   │
   ▼
Customer Context 갱신
   │
   └───────────────→ 다시 판단
```

즉:

> **Observe → Understand → Decide → Act → Learn**

의 반복 구조가 되어야 합니다.

그래야 데이터가 단순 저장 자산이 아니라 **비즈니스 실행 자산**으로 바뀝니다.

# 19. 데이터플랫폼과 마케팅플랫폼까지 연결하면

현재까지 두 장을 한 번에 보면 이렇게 됩니다.

```text
                    NSIGHT

                DATA PLATFORM
               "기초공사 / 신뢰"

     Source
       │
      CDC
       │
      RDW
       │
       │ Customer Context
       │
       ▼
              MARKETING PLATFORM
               "Reaction Brain"

Customer Event
       │
Wise Collector
       │
     Kafka
       │
       ├──── Customer Context
       │              │
       └──────┬───────┘
              ▼
          Decision
              │
          Next Best Action
              │
              ▼
             Offer
              │
              ▼
           Customer
```

전략 브리핑에서 말하는 **Data → Reaction**이 여기까지입니다.

그리고 이제 다음 단계에서 이것이:

```text
Data
 ↓
Reaction
 ↓
Decision
```

으로 완성됩니다.

그 역할을 하는 것이 **③ BI 포탈**입니다.

다음 설명에서는 **BI 포탈을 단순 조회/리포팅 시스템이 아니라 “AI가 지원하는 자율적 의사결정 공간”으로 왜 재정의했는지**, `Self-BI`, `AI/NLP 자연어 질의`, `Reporting 표준화`, 그리고 **ADW와 BI의 책임 경계**까지 전략설명서 기준으로 연결하겠습니다.
