좋습니다. 이제 **14번째 설명 — NSIGHT 전체 통합 Architecture Story**로 진행하겠습니다.

13번까지는 `Vision → Big Picture → Logical → Physical → HA/DR → Mechanism → Runtime`을 각각 분해해서 봤습니다. 14번에서는 이것을 다시 기술영역별로 설명하지 않고, **“NSIGHT가 왜 존재하고, 데이터가 어떻게 비즈니스 가치로 바뀌며, 이를 어떤 구조가 지탱하는가”**라는 하나의 이야기로 합치겠습니다.

전략자료가 반복해서 강조하는 핵심은 NSIGHT가 단순 DW 고도화가 아니라, **배치 중심의 정보계를 데이터가 흐르고 고객에게 반응하며 의사결정을 지원하는 살아있는 플랫폼으로 전환하는 사업**이라는 점입니다.

# 14. NSIGHT 통합 Architecture Story

## 14.1 NSIGHT를 가장 짧게 표현하면

NSIGHT의 전체 아키텍처는 사실 다음 다섯 단어로 압축할 수 있습니다.

```text
DATA
  ↓
REACTION
  ↓
DECISION

   +

GOVERNANCE
   +

OPERATION
```

전략 발표 스크립트에서는 과거와 미래 정보계를 비교하면서 특히 **“데이터, 반응, 판단”**이라는 세 단어를 핵심 변화로 제시합니다. 과거 정보계가 데이터를 모아 정해진 시간에 가공하고 보고했다면, 미래 정보계는 데이터가 살아 움직이고 고객 행동에 반응하며 경영 판단까지 지원해야 한다는 것입니다.

여기에 실제 기업 시스템으로 지속시키기 위해 **Data Governance와 IT Service/Operation**이 붙습니다.

---

# 14.2 한 장으로 보면 이런 구조입니다

```text
                 NH 농협 상호금융 NSIGHT
            Scalable · Resilient · Data-Centric

                           │
                           ▼
                ┌──────────────────┐
                │       DATA       │
                │                  │
                │ 신뢰할 수 있는   │

                └────────┬─────────┘
                         │

      │ 고객 행동에   │       │ 데이터를 보고 │
      │ 즉시 반응     │       │ 즉시 판단     │
      └───────┬───────┘       └───────┬───────┘
              │                       │
              ▼                       ▼
        Marketing Platform          BI Portal


────────────────────────────────────────────────────

                   GOVERNANCE
                       │
            의미 / 표준 / 품질 / 흐름
                       │

```

이 그림이 NSIGHT의 기술 목록보다 훨씬 중요합니다.

---

# 14.3 첫 번째 이야기 — DATA

모든 것은 데이터에서 시작합니다.

기존 정보계의 전형적인 구조는:

```text
계정계
  ↓
야간 Batch
  ↓
DW
  ↓
다음날 조회
```

였습니다.

NSIGHT는 이를:

```text
Source
   │
   ├──── CDC ─────▶ RDW
   │
   └──── Batch ───▶ ETL ───▶ ADW
```

로 바꿉니다.

전략자료가 설명하는 핵심 변화도 **배치 단독 구조에서 실시간과 배치를 병행하는 구조로의 전환**입니다. CDC와 Kafka 기반 Near Real-time 구조를 사용해 단순 저장소였던 정보계를 실시간 경영 플랫폼으로 바꾸는 것이 목표입니다.

그런데 여기서 가장 중요한 결정이 있습니다.

```text
RDW
 ≠
ADW
```

입니다.

RDW는 온라인·실시간 서비스의 안정성을 책임하고,

```text
RDW
→ 실시간 조회
→ SingleView
→ Marketing Context
```

ADW는 깊은 분석을 담당합니다.

```text
ADW
→ BI
→ OLAP
→ 대량 분석
→ Reporting
```

즉 RDW와 ADW를 분리하는 이유는 DB 이름을 두 개 만들기 위해서가 아니라 **온라인과 분석이 서로의 CPU·I/O·Session을 침범하지 못하게 하기 위해서**입니다.

전략 발표 스크립트도 실시간과 배치, 운영과 분석을 명확히 분리하고 RDW와 ADW의 자원경합을 제거하는 것을 핵심 전략으로 설명합니다.

---

# 14.4 두 번째 이야기 — REACTION

데이터가 빨리 도착한다고 고객에게 가치가 생기는 것은 아닙니다.

다음 질문이 필요합니다.

> **“고객이 지금 무엇을 하고 있으며, 우리는 지금 무엇을 해야 하는가?”**

그래서 마케팅플랫폼이 필요합니다.

```text
                 Customer Context
                       ▲
                       │
                      RDW
                       │
                       │
Customer Action        │
      │                │
      ▼                │
Wise Collector         │
      │                │
      ▼                │
    Kafka ─────────────┘
      │
      ▼
Decision / Rule
      │
      ▼
Realtime Offering
      │
      ▼
Customer
```

즉 두 종류의 정보를 결합합니다.

```text
"고객이 누구인가?"
       +
"고객이 지금 무엇을 했는가?"
       ↓
"지금 무엇을 제안할 것인가?"
```

이것이 마케팅플랫폼을 **Reaction Brain**, 즉 반응하는 두뇌라고 보는 이유입니다.

전략자료의 핵심 메시지 역시 기존의 Batch Marketing을 넘어 고객 행동을 실시간으로 받아 즉시 대응하는 플랫폼으로 전환하는 것입니다.

---

# 14.5 FAST의 의미도 여기서 명확해집니다

실시간 마케팅의 목표는 데이터를 먼저 저장하고 나중에 판단하는 것이 아닙니다.

```text
Customer Action
      ↓
Kafka
      ↓
Rule / Decision
      ↓
Offer
```

이라는 **FAST Path**가 존재해야 합니다.

반면 분석을 위한 이력은 별도의 길로 갑니다.

```text
Event / Source
      ↓
CDC / ETL
      ↓
RDW / ADW
      ↓
Analysis
```

그래서:

```text
FAST
 ≠
DEEP
```

입니다.

이것은 단순 데이터 처리 방식 차이가 아니라 NSIGHT 전체의 **성능 격리, 장애 격리, 독립 확장 전략**입니다.

---

# 14.6 세 번째 이야기 — DECISION

고객에 대한 반응만 빨라져서는 데이터 중심 경영이 완성되지 않습니다.

조직도 빨리 판단할 수 있어야 합니다.

그래서 BI Portal이:

```text
Dashboard
+
Self-BI
+
OLAP
+
Reporting
+
AI / NLP
```

를 이용해 의사결정 시간을 줄이는 역할을 합니다.

```text
                 ADW
                  │
                  ▼
               BI Portal
                  │
      ┌───────────┼───────────┐
      ▼           ▼           ▼
  Dashboard    Self-BI      OLAP
      │           │           │
      └───────────┼───────────┘
                  ▼
              Analysis
                  │
                  ▼
              Decision
```

전략자료에서 BI Portal은 단순 조회 포털이 아니라 **AI가 지원하는 자율적 의사결정 공간**, 즉 현업이 데이터에 직접 접근하여 판단하는 플랫폼으로 정의됩니다.

따라서:

```text
Marketing
=
고객에게 무엇을 할 것인가?


BI
=
조직이 무엇을 판단할 것인가?
```

라는 차이가 있습니다.

---

# 14.7 이 세 개를 합치면 Data → Reaction → Decision입니다

이제 NSIGHT의 비즈니스 핵심 흐름이 연결됩니다.

```text
                  SOURCE DATA
                      │
                      ▼
              ┌───────────────┐
              │ DATA PLATFORM │
              │               │
              │ RDW / ADW     │
              │ CDC / ETL     │
              └───────┬───────┘
                      │
                 TRUSTED DATA
                      │
             ┌────────┴────────┐
             │                 │
             ▼                 ▼
       MARKETING              BI
       PLATFORM             PORTAL
             │                 │
          REACTION          DECISION
             │                 │
             ▼                 ▼
         Customer          Organization
           Action             Action
```

이것이 NSIGHT의 가장 중요한 비즈니스 Architecture Story입니다.

> **데이터를 빠르게 모으는 것이 목적이 아니라, 신뢰할 수 있는 데이터가 고객에 대한 실행과 조직의 판단으로 연결되게 만드는 것이 목적입니다.**

---

# 14.8 그런데 데이터가 틀리면 전체가 무너집니다 — GOVERNANCE

여기서 네 번째 영역이 등장합니다.

예를 들어:

```text
Marketing의 "활동고객"
            ≠
BI의 "활동고객"
            ≠
ADW의 "활동고객"
```

이면 아무리 실시간 시스템이어도 신뢰할 수 없습니다.

그래서 Data Governance가:

```text
Business Metadata
Data Standard
Data Quality
Data Flow
IT Metadata
```

를 관리합니다.

```text
                  DATA GOVERNANCE
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
    Data Platform   Marketing       BI Portal
          │             │             │
          └─────────────┼─────────────┘
                        │
                    같은 의미
                    같은 품질
                    같은 흐름
```

전략자료에서 데이터거버넌스는 IT 메타 기반의 **데이터 표준·품질·용어·모델 일관성**을 관리하는 별도 서비스 도메인으로 정의되어 있습니다.

즉 Governance는 데이터를 직접 “서비스”하기보다는:

> **데이터가 믿을 만하다는 것을 통제하는 체계**

입니다.

---

# 14.9 마지막은 OPERATION입니다

아무리 좋은 데이터와 애플리케이션이 있어도 운영되지 않으면 의미가 없습니다.

그래서 다섯 번째 서비스 도메인이:

```text
IT SERVICE / BUSINESS SUPPORT
```

입니다.

여기에는 단순 운영도구뿐 아니라:

```text
Architecture Management
Framework
Source Management
Library
Deployment
SSO
Batch
CDC / ETL Runtime
Terminal Management
Monitoring
DR
```

같은 공통 기반이 포함됩니다.

업무 분류체계에서도 `AM, SC, DP, FW, LB, SM, XM, XD, BJ, CD, DT, RD, IG` 등 IT서비스 및 업무지원 영역이 별도 대그룹으로 관리됩니다.

이 영역의 역할을 한 문장으로 표현하면:

> **“모든 플랫폼이 같은 표준으로 개발되고, 같은 방식으로 배포되고, 인증되고, 관측되고, 복구되게 만든다.”**

입니다.

---

# 14.10 그래서 5대 서비스 도메인은 이렇게 역할이 나뉩니다

| 서비스 도메인            | 핵심 질문                                 | 제공가치     |
| ------------------------ | ----------------------------------------- | ------------ |
| **Data Platform**        | 데이터를 어떻게 신뢰성 있게 공급할 것인가 | **TRUST**    |
| **Marketing Platform**   | 고객 행동에 어떻게 즉시 대응할 것인가     | **REACTION** |
| **BI Portal**            | 데이터를 어떻게 즉시 판단으로 바꿀 것인가 | **DECISION** |
| **Data Governance**      | 데이터 의미·품질을 어떻게 일치시킬 것인가 | **GOVERN**   |
| **IT Service / Support** | 이 구조를 어떻게 지속 운영할 것인가       | **OPERATE**  |

이렇게 놓으면 5개의 서로 다른 시스템이 아니라 **하나의 비즈니스 가치사슬**로 보입니다.

---

# 14.11 그리고 이 가치사슬의 바깥에는 Boundary가 있습니다

NSIGHT가 모든 시스템과 마음대로 연결되는 구조는 아닙니다.

상위 Big Picture의 기본은:

```text
Channel
   ↓
Channel Integration
   ↓
NSIGHT Service Zone
   ↓
Internal Integration
   ↓
Core / Other Systems
```

입니다.

즉:

```text
책임은 Domain 안에 고정
연결은 Boundary에서 통제
```

합니다.

이 원칙이 실제 Mechanism에서는:

```text
Online Service  → CruzAPIM
File            → FOS / MFT
DB Change       → CDC
Event           → Kafka
Bulk Data       → DataStage
```

와 같은 표준 경로로 구현됩니다.

전략 브리핑의 논리/메커니즘 장에서도 기술을 나열하는 대신 **도메인 분리, 데이터 흐름 정의, Integration 통제, 규격 표준화**를 먼저 결정하도록 되어 있습니다.

---

# 14.12 이 논리구조를 물리적으로 지탱하는 것이 Hybrid Architecture입니다

서비스와 데이터의 Workload가 다르기 때문에 동일 인프라를 강제하지 않습니다.

```text
                 NSIGHT HYBRID

Service
Marketing / BI / Governance
        ↓
Private Cloud / IaaS
Scale-Out


Data
RDW / ADW
        ↓
Exadata
Dedicated Resource


Bulk Processing
ETL
        ↓
전용 고성능 자원


Change Data
CDC
        ↓
독립 중계 영역
```

즉:

> **유연해야 하는 것은 Scale-Out하고, 성능과 정합성이 중요한 데이터는 전용 자원으로 보호한다.**

이런 구조가 `Scalable`을 구현합니다.

---

# 14.13 Resilient는 HA/DR로 구현됩니다

또 다른 상위 전략은 Resilient입니다.

```text
센터 내부
WEB / WAS HA
       ↓
작은 장애는 작은 영역에서 해결


센터 장애
       ↓
GSLB
       ↓
DR Center
```

그리고 DB는:

```text
MAIN DB Active
       │
       │ Replication
       ▼
DR DB Standby
```

구조로 안정성과 정합성을 우선합니다.

즉 Resilient의 의미는:

```text
장애가 없다
```

가 아니라:

```text
장애가 발생한다
   ↓
영향을 격리한다
   ↓
우회한다
   ↓
복구한다
   ↓
정상화한다
```

입니다.

현재 Physical/HA-DR 작업에서도 Main/DR, WEB/WAS, RDW Active/Standby 구조를 별도의 운영 기준으로 관리하고 있습니다.

---

# 14.14 이 모든 것을 실행하는 것이 Mechanism입니다

지금까지 전략이 훌륭하다고 해도 개발자가 마음대로 구현하면 아무 의미가 없습니다.

그래서:

```text
Architecture Policy
       ↓
Mechanism
       ↓
실제 구현 강제
```

가 필요합니다.

여기에서:

```text
HTTP / JSON
Standard Message
GUID
Framework
TCF
ServiceId
Transaction
Timeout
SSO / JWT
Logging
CDC
Kafka
DataStage
CruzAPIM
FOS
```

등이 등장합니다.

즉 TCF의 위치도 이제 명확합니다.

```text
NSIGHT Strategy
      ↓
Logical Policy
      ↓
Mechanism
      ↓
Application Framework
      ↓
TCF
      ↓
ServiceId / Dispatcher
      ↓
Business Application
```

**TCF는 NSIGHT 전체 전략이 아니라 그 전략을 온라인 Application Runtime에서 강제하는 하위 메커니즘**입니다.

---

# 14.15 그리고 마지막은 Runtime입니다

모든 것이 결국 여기서 증명됩니다.

```text
"FAST 1초"
        ↓
실제 측정했는가?


"RDW/ADW 분리"
        ↓
ADW 분석이 RDW에 영향이 없는가?


"WAS 이중화"
        ↓
한 대를 실제로 죽여봤는가?


"DR 30분"
        ↓
센터를 실제 전환했는가?


"GUID 전구간 추적"
        ↓
실제 한 거래를 끝까지 찾을 수 있는가?
```

따라서 NSIGHT의 Architecture Story는 문서작성으로 끝나지 않습니다.

```text
Strategy
   ↓
Design
   ↓
Implementation
   ↓
Runtime
   ↓
Evidence
```

가 되어야 합니다.

수행방법론 문서도 Runtime을 단순 마지막 단계가 아니라 **Logical·Physical·Mechanism을 실제 서비스 흐름으로 다시 검증하고 보완하는 단계**로 정의합니다.

---

# 14.16 그래서 6단계 방법론과 5대 플랫폼은 서로 다른 이야기가 아닙니다

둘을 합치면 이렇게 됩니다.

```text
                   WHY
                    │
                    ▼
                  VISION
      Scalable / Resilient / Data-Centric
                    │
                    ▼
               BIG PICTURE
              5대 서비스 도메인
                    │
                    ▼
                 LOGICAL
     Responsibility / Boundary / Data Flow
                    │
                    ▼
                PHYSICAL
    VM / Exadata / WEB / WAS / AP / Main / DR
                    │
                    ▼
               MECHANISM
 Protocol / Framework / Integration / Data Transport
                    │
                    ▼
                RUNTIME
      FAST / DEEP / Online / Failure / DR
                    │
                    ▼
                 EVIDENCE
                    │
                    ▼
                BASELINE
```

6단계는 **어떻게 설계하는가**이고,

5대 플랫폼은 **무엇을 구축하는가**입니다.

이 둘을 동시에 봐야 NSIGHT 전체가 이해됩니다.

# 14.17 임원에게 한 장으로 설명한다면

제가 지금까지의 전략자료를 기반으로 임원에게 설명한다면 다음과 같이 압축할 수 있습니다.

> **“NSIGHT는 기존의 배치 중심 정보계를 실시간 데이터 기반 경영 플랫폼으로 전환하는 사업입니다. 데이터플랫폼은 신뢰할 수 있는 데이터를 만들고, 마케팅플랫폼은 고객 행동에 즉시 반응하며, BI포탈은 현업과 경영진의 즉시 판단을 지원합니다. 데이터거버넌스가 데이터의 의미와 품질을 통제하고, IT서비스 및 업무지원이 표준·개발·배포·보안·운영을 공통으로 지탱합니다. 이 구조는 RDW/ADW, FAST/DEEP, Online/Batch를 의도적으로 분리하여 성능과 장애를 격리하고, 표준 인터페이스와 Framework 메커니즘으로 설계정책을 강제하며, 최종적으로 Runtime Evidence를 통해 실제 운영에서도 아키텍처가 성립하는지를 증명하는 구조입니다.”**

이 내용은 전략자료가 말하는 **“단순 시스템 교체가 아니라 미래를 담을 집을 다시 짓는 일”**이라는 표현과 가장 잘 맞습니다.

## 14번의 핵심 결론

NSIGHT의 본질을 `Apache`, `Tomcat`, `TCF`, `Kafka`, `Exadata` 같은 제품명으로 설명하면 아키텍처의 핵심을 놓칩니다.

NSIGHT는 본질적으로:

> **“데이터를 신뢰할 수 있게 만들고(DATA), 그 데이터로 고객에게 즉시 반응하며(REACTION), 조직이 즉시 판단할 수 있게 하고(DECISION), 데이터의 의미와 품질을 통제하며(GOVERNANCE), 이 모든 구조를 표준화된 개발·운영 체계로 지속시키는(OPERATION) 차세대 데이터 중심 경영 플랫폼”**

입니다.

그리고 이것을 **Scalable · Resilient · Data-Centric**하게 만들기 위해 `Boundary → Isolation → Standardization → Mechanism → Runtime Evidence`가 붙는 것이 NSIGHT 아키텍처입니다. 전략 브리핑에서 제시한 `Vision → Big Picture → Logical → Physical → Mechanism → Runtime`의 6단계가 바로 이 전체 구조를 구축하고 검증하는 방법입니다.

**15번째 단계에서는 여기서 한 단계 더 실무적으로 내려가, 지금까지의 모든 전략을 `아키텍처 원칙 → 설계전략 → 정상패턴 → 금지패턴 → 검증 Rule`의 형태로 변환해 보겠습니다.** 이것이 실제 개발자·설계자·인프라팀·DA·TA·AA가 따라야 하는 **NSIGHT Architecture Rulebook**의 시작점입니다.
