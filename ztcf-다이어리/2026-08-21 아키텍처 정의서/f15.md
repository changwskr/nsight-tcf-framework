좋습니다. 이제 **15번째 설명 — NSIGHT Architecture Rulebook**으로 진행하겠습니다.

14번까지는 “NSIGHT 전체가 어떤 아키텍처인가”를 설명했습니다. 15번부터는 그것을 **프로젝트 구성원이 실제로 지켜야 하는 규칙**으로 바꾸겠습니다.

중요한 전제가 하나 있습니다. 전략 브리핑에서 직접 확인되는 상위 정책은 `도메인 분리`, `데이터 흐름 강제`, `Integration 통제`, `HTTP/JSON·표준전문·GUID`, `Online/Batch·RDW/ADW 자원분리` 등입니다. 반면 `R1~R4`, `MSG`, `DOMAIN`, `GOV` 규칙체계는 PDMG Reference/Conformance 작업에서 구체화된 체계입니다. 따라서 **PDMG 소스에서 발견된 규칙을 곧바로 NSIGHT 전체 표준으로 승격해서는 안 되고 `VERIFIED / CANDIDATE / VARIANT / DEPRECATED` 상태를 거쳐야 합니다.**

# 15. NSIGHT Architecture Rulebook

## 15.1 왜 Rulebook이 필요한가

아키텍처 전략서가 이렇게만 되어 있다고 하겠습니다.

```text
도메인을 분리한다.
RDW와 ADW를 분리한다.
P2P를 금지한다.
표준 전문을 사용한다.
```

방향은 맞지만 실제 프로젝트에서는 부족합니다.

개발자는 다음 질문을 합니다.

```text
그래서 MG에서 MK DAO를 호출해도 됩니까?

Self-BI가 RDW를 직접 조회해도 됩니까?

Kafka 대신 DB Polling을 써도 됩니까?

Controller에서 SQL 호출하면 안 됩니까?

P2P가 정확히 어디까지입니까?

예외가 있으면 누가 승인합니까?
```

그래서 전략을 다음 구조로 변환해야 합니다.

```text
Architecture Principle
        ↓
Design Strategy
        ↓
Normal Pattern
        ↓
Prohibited Pattern
        ↓
Validation Rule
        ↓
Evidence
        ↓
PASS / FAIL / EXCEPTION
```

즉 **Rulebook은 전략설명서와 실제 구축 사이의 계약서**입니다.

---

# 15.2 Rule 하나는 최소 8개 정보를 가져야 합니다

앞으로 NSIGHT Rule은 이런 형태가 가장 적절합니다.

| 항목               | 의미                                  |
| ------------------ | ------------------------------------- |
| Rule ID            | 고유 식별자                           |
| Principle          | 어떤 아키텍처 원칙에서 나온 것인가    |
| Strategy           | 어떤 설계전략으로 구현하는가          |
| Normal Pattern     | 허용되는 정상구조                     |
| Prohibited Pattern | 금지구조                              |
| Validation         | 어떻게 검사하는가                     |
| Evidence           | 어떤 증적이 있어야 하는가             |
| Status             | VERIFIED/CANDIDATE/VARIANT/DEPRECATED |

그리고 Severity/Priority를 붙입니다.

```text
P0 = 반드시 막아야 하는 Hard Rule
P1 = Architecture Contract
P2 = 운영품질 / 지속관리 Rule
```

현재 PDMG Conformance 체계에서도 P0에는 ServiceId 중복, Layer 금지규칙, Private Key 노출, Runtime Evidence, Artifact Hash, Approval 같은 항목을 두고, P1은 Transaction/Timeout/Session 등의 실행계약, P2는 Capacity·Thread·Hikari·GC 같은 운영품질 규칙으로 구분합니다.

# 15.4 RULE 01 — DATA-CENTRIC

### Principle

> **시스템보다 데이터의 발생·이동·소유·활용 흐름을 먼저 설계한다.**

전략자료는 실시간과 배치를 분리하고, 데이터 흐름을 `CDC / Kafka / ETL`로 강제로 정의하는 것을 핵심 원칙으로 둡니다.

### Design Strategy

```text
DB Change   → CDC
Event       → Kafka
Bulk        → ETL
Online Read → RDW
Analytics   → ADW
```

### 정상패턴

```text
Source DB
   ↓
CDC
   ↓
RDW
   ↓
DataStage
   ↓
ADW
```

또는:

```text
Customer Action
   ↓
Kafka
   ↓
Realtime Marketing
```

### 금지패턴

```text
Event
  ↓
임의 DB Polling
  ↓
실시간 반응
```

```text
Bulk Data
  ↓
Online WAS에서 대량가공
```

### Validation Rule

```text
DATA-001
모든 Data Flow는
CDC / Kafka / ETL / 승인된 File/API
중 하나로 분류되어야 한다.
```

### Evidence

- Data Flow Registry
- CDC Interface List
- Kafka Topic List
- ETL Job Catalog

이 Rule ID 자체는 **이번 Rulebook 구조화를 위해 부여한 제안 ID**입니다. 상위 정책은 전략자료에서 직접 확인됩니다.

# 15.5 RULE 02 — RDW / ADW 책임분리

### Principle

> **실시간 운영과 분석성 대량 처리를 같은 데이터 자원에 경쟁시키지 않는다.**

전략자료는 RDW를 실시간/온라인 영역, ADW를 분석 대량처리 영역으로 나누고 물리적으로 자원을 분리하도록 정의합니다.

### 정상패턴

```text
Online / SingleView
        ↓
       RDW


BI / OLAP / Analytics
        ↓
       ADW
```

### 금지패턴

```text
Self-BI
   ↓
RDW 전 테이블
   ↓
무제한 Ad-hoc Query
```

또는:

```text
Online Transaction
   ↓
ADW 대량 집계
```

### Validation

```text
DATA-002
Application별 RDW/ADW
Read/Write Matrix가 존재해야 한다.
```

```text
DATA-003
분석성 대량질의는 RDW Online SLA에
영향을 주어서는 안 된다.
```

### Evidence

- DB Access Matrix
- SQL Workload
- RDW/ADW Resource Metric
- Load Test

# 15.8 RULE 05 — NO P2P / Integration Control

전략자료가 직접적으로 강하게 말하는 Rule입니다.

> **P2P 인터페이스를 금지하고 표준 인터페이스를 강제한다.**

다만 여기서 뜻은:

```text
모든 직접 연결 금지
```

가 아니라:

> **정의되지 않은 임의 직접 연결 금지**

입니다.

### 정상패턴

| 연계 유형             | 정상 경로 |
| --------------------- | --------- |
| 시스템 거래           | CruzAPIM  |
| 시스템간 File         | FOS/MFT   |
| 대외 File             | MCA + MFT |
| DB Change             | CDC       |
| Event                 | Kafka     |
| 대량 Batch            | DataStage |
| 계정계 관련 표준 경계 | GSE       |

전략자료의 Mechanism에도 No P2P와 이 표준경로가 직접 정의되어 있습니다.

### 금지패턴

```text
System A
   ↓
DB Link
   ↓
System B
```

```text
System A
  ── 임의 Socket ──▶ System B
```

### Validation

```text
INT-001
모든 Interface는 Interface Registry에 존재해야 한다.

INT-002
모든 Interface는 승인된 Integration Type을 가져야 한다.

INT-003
미등록 P2P / DB Link는 Architecture Violation이다.
```

# 15.9 RULE 06 — RESOURCE ISOLATION

> **성격이 다른 Workload는 같은 자원에서 경쟁하지 않는다.**

```text
Online AP ≠ Batch AP
ETL 별도
Event Server 별도
IMDG 별도
RDW ≠ ADW
```

입니다.

### 정상

```text
Online → Online AP
Batch  → Batch AP
Event  → Event Server
ETL    → ETL Server
BI     → ADW
```

### 금지

```text
Online WAS
   ├─ 고객 Transaction
   ├─ 대용량 Batch
   └─ ETL
```

### Validation

```text
PHY-001
Workload Class와 Physical Resource가
1:N 또는 독립 Pool로 명시되어야 한다.

PHY-002
Online SLA와 Batch Resource가
동일 Failure/Contention Domain이면 경고/FAIL.
```

# 15.10 RULE 07 — SCALE-OUT 우선

NSIGHT 전략은 서비스 성격 서버를 Private Cloud VM 기반 Scale-Out으로 확장하고 RDW/ADW는 Exadata 노드·랙 병렬확장을 사용하도록 구분합니다.

### 정상

```text
Online AP

VM01
VM02
VM03
VM04
```

### 비권장 패턴

```text
하나의 초대형 VM
     ↓
모든 온라인 Application 집중
```

현재 온라인 AP 비교자료에서도 같은 총 Core라면 16Core 소수 VM보다 **8Core 다수 VM Scale-Out이 장애 영향도·Rolling 배포·RDW 보호 측면에서 유리**하다는 Working 전략을 제시하고 있습니다.

다만 **8Core 자체를 NSIGHT 전 시스템의 절대 표준값으로 확정하면 안 됩니다.** 이는 특정 온라인 AP 용량산정 Working 기준입니다.

# 15.11 RULE 08 — STANDARD CONTRACT

### Principle

> **비표준 전문은 원칙적으로 허용하지 않는다.**

전략자료는 온라인 규격으로 `HTTP/JSON`, 표준전문, GUID 기반 Trace를 명시합니다.

PDMG에서는 이 원칙이 더 구체화되어 `MSG-001~MSG-012`로 정의되어 있습니다.

대표 규칙은:

```text
MSG-001
Header + Business Payload 분리

MSG-002
ServiceId는 공통 Header에서 관리

MSG-003
GUID는 전 거래에 유지

MSG-004
업무 계층에 전체 전문 전달 금지

MSG-005
업무에는 필요한 DTO만 전달

MSG-006
Framework 공통정보는 Context 사용

MSG-007
업무가 응답 JSON 직접 조립 금지

MSG-008
오류는 Exception 기반 전달

MSG-011
민감정보 Log Masking
```

### 정상패턴

```text
Request

hdr_nhnis
    +
dto
```

Framework:

```text
Header
  ↓
Context
```

Business:

```text
DTO
  ↓
Handler / Service
```

### 금지

```text
Service
  ↓
전체 HTTP Request/Header 직접 파싱
```

또는:

```text
업무 Service
  ↓
Response JSON 직접 조립
```

# 15.14 RULE 11 — TRANSACTION / TIMEOUT

### Principle

> **거래 하나가 끝없이 자원을 점유하지 못하게 한다.**

### 정상

```text
SQL Deadline
     <
Transaction Deadline
     <
Request Deadline
```

Timeout 시:

```text
Timeout
 ↓
Rollback
 ↓
Connection Return
 ↓
Thread Return
 ↓
표준 Error
```

### 금지

```text
Client Timeout
     ↓

서버에서는 SQL 계속 실행
Thread 계속 점유
Connection 계속 점유
```

PDMG R2/R4 규칙에는 Transaction Owner, Timeout Executor, TX BEGIN/COMMIT/ROLLBACK Evidence 등을 별도로 검사하도록 되어 있습니다.

특정 4~5초 등의 값은 현재 Spring Working 설정이며, **전 서비스에 적용되는 최종 절대 SLA로 취급해서는 안 됩니다.**

```text
Center Failure
  ↓
DR
```

즉:

```text
JVM 장애 → Peer JVM
WAS 장애 → Peer WAS
DB Node → DB HA
센터 장애 → GSLB / DR
```

로 Failure Domain을 단계적으로 처리해야 합니다.

### 금지패턴

```text
Tomcat 하나 장애
   ↓
센터 DR 전환
```

또는:

```text
DR 서버는 있음
   ↓
전환시험 없음
```

### Validation

- N-1 Test
- Center Failure Test
- RTO/RPO
- Failover
- Failback
- 잔여 Capacity

Runtime Evidence가 없는 경우 PASS하지 않는다는 Governance 원칙과도 연결됩니다.

---

# 15.18 RULE 15 — RUNTIME EVIDENCE MANDATORY

이 규칙은 현재 Architecture Closed Loop에서 가장 중요한 것 중 하나입니다.

```text
"그렇게 설계했다"
         ≠
"그렇게 동작한다"
```

### P0 Rule

> **Runtime Evidence 없는 Runtime 주장은 PASS할 수 없다.**

현재 Conformance 체계에서도 `Runtime Evidence Mandatory`가 P0입니다.

예:

```text
p95 ≤ 3초
```

라고 문서에 있으면:

```text
Load Test
+
APM
+
TPS
+
p95
+
CPU
+
Thread
+
DB Pool
```

증적이 있어야 합니다.

```text
DR RTO ≤ 30분
```

이면 실제:

```text
센터 장애 발생 시각
        ↓
DR 전환 시각
        ↓
업무 정상 확인 시각
```

이 필요합니다.

---

# 15.19 RULE 16 — ARCHITECTURE CONFORMANCE CLOSED LOOP

Rulebook을 문서로 만들어놓고 사람에게 “지켜주세요”라고 하는 것으로 끝내지 않습니다.

현재 Architecture Orchestration이 목표로 하는 구조는:

```text
SOURCE
  ↓
MODEL
  ↓
RULE
  ↓
CONFORMANCE TEST
  ↓
RUNTIME EVIDENCE
  ↓
DRIFT
  ↓
GAP / ADR
  ↓
APPROVAL
  ↓
BASELINE
```

입니다.

실제 실행 시스템도 `R00/R10/.../R90` Reference Lane과 `G00/.../HG90` Target Lane을 두고, Source→Model→Rule→Test→Runtime→Drift→GAP/ADR→Approval→Release 순서를 정의합니다.

---

# 15.20 단순 PASS/FAIL보다 4가지 판정이 필요합니다

Reference와 Target을 비교할 때 현재 설계는 다음 상태를 사용합니다.

```text
MATCH

ALLOWED_VARIANT

GAP

EXCEPTION
```

이것이 중요합니다.

예를 들어 모든 업무가 동일 구조일 필요는 없습니다.

```text
Reference
Handler → Facade → Service

Target
특수 배치 Application
→ 다른 Pattern
```

이라고 해서 무조건 FAIL로 만들면 안 됩니다.

먼저:

```text
정말 Architecture Violation인가?

아니면 업무특성상 허용된 Variant인가?
```

를 판단해야 합니다.

---

# 15.21 Rule 자체도 상태가 필요합니다

특히 PDMG 소스에서 추출하는 Rule은:

```text
VERIFIED
CANDIDATE
VARIANT
DEPRECATED
```

를 가져야 합니다.

예를 들어:

```text
pdmg-service와 pdmg-jwt에서
Handler → Facade → Service → DAO
```

가 반복된다고 해서:

```text
"NSIGHT 전체 반드시 이 구조"
```

라고 즉시 선언해서는 안 됩니다.

정확한 과정은:

```text
Source Pattern 발견
      ↓
CANDIDATE
      ↓
Reference Project 간 검증
      ↓
충돌 여부 확인
      ↓
ADR / Architecture Review
      ↓
VERIFIED
      ↓
Rulebook 등록
```

입니다.

이 점이 앞으로 Rulebook을 만드는 데 굉장히 중요합니다.

# 15.25 Rulebook과 Gate 연결

최종적으로 Rule은 Gate까지 연결됩니다.

```text
P0 Violation
   ↓
GATE BLOCK

P1 Violation
   ↓
GAP / ADR 필요

P2 Violation
   ↓
Warning / Improvement
```

Reference/Target 실행 시스템에서도 최종 Release Gate는 단순 문서완료가 아니라 **Model↔Source Conformance, Architecture Rule Evidence, Build/Test/Security, Artifact Hash, Deployment Evidence, Runtime Evidence, Critical Drift/GAP 0, Human Approval**까지 요구합니다.

따라서 Architecture Gate를 사람이 “괜찮아 보인다”라고 통과시키는 구조에서:

```text
Evidence
+
Rule
+
Machine Check
+
Human Decision
```

구조로 바꾸는 것이 최종 목표입니다.

---

# 15.26 NSIGHT Rulebook의 핵심 철학

최종적으로 이렇습니다.

```text
Architecture Strategy
        ↓
Architecture Principle
        ↓
Design Rule
        ↓
Normal Pattern
        ↓
Prohibited Pattern
        ↓
Conformance Test
        ↓
Runtime Evidence
        ↓
GAP / ADR
        ↓
Baseline
```

즉 **“좋은 아키텍처를 설명하는 문서”에서 “잘못된 아키텍처를 실제로 막는 시스템”으로 발전시키는 것**입니다.

이 단계가 특히 중요합니다. 현재 PDMG Reference Orchestration도 4개 프로젝트의 실제 Source를 바로 표준이라고 보지 않고 `L0 Raw Source → L1 Verified Baseline → L2 Reference Architecture`로 검증 후 승격하도록 설계되어 있습니다.

## 15번의 최종 결론

**NSIGHT Architecture Rulebook은 `Scalable · Resilient · Data-Centric`이라는 전략을 추상적인 구호로 남겨두지 않고, `도메인 분리 · 데이터 흐름 강제 · Integration 통제 · 자원격리 · RDW/ADW · FAST/DEEP · 표준전문 · Framework · Security · HA/DR · Observability · Runtime Evidence`를 정상패턴·금지패턴·자동검증 Rule로 전환하는 체계입니다.**

그리고 기존 PDMG Reference에서 구체화한:

```text
R1  Structural
R2  Framework
R3  Security
R4  Runtime / Operational
MSG Standard Message
DOMAIN
GOV
```

를 하위 Conformance Rule 체계로 연결하면 전략에서 코드·운영까지 하나의 일관된 Rule Chain을 만들 수 있습니다.

**16번째 단계에서는 이 Rulebook을 실제 Architecture Review에 사용하는 방식으로 내려가겠습니다.** 즉 `설계안 접수 → Rule 자동검사 → 정상/금지패턴 판정 → P0/P1/P2 → GAP → ADR → 예외승인 → Runtime Evidence → Gate PASS`의 **NSIGHT Architecture Review & Gate 운영체계**를 설명하면 지금까지 만든 전략이 실제 프로젝트 통제 프로세스로 완성됩니다.
