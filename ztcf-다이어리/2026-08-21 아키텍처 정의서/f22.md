좋습니다. 이제 **22번째 설명 — NSIGHT Architecture Definition of Done(DoD) · 품질검증 체크리스트**로 진행하겠습니다.

21번까지는 어떤 산출물을 만들 것인지 정했습니다. 이제 가장 중요한 질문이 남습니다.

> **“문서를 다 작성하면 아키텍처 작업이 끝난 것인가?”**

NSIGHT 기준에서는 **아닙니다.** 전략 방법론에서도 최종 단계는 Runtime의 “서비스 검증”이며, Closed Loop 기준에서는 `Document Baseline → Model → Source → Rule → Test → Deployment → Runtime Evidence → Drift → Human Approval → HG90`까지 통과해야 최종 완료로 인정합니다.

# 22. NSIGHT Architecture Definition of Done

## 22.1 가장 먼저 “완료”를 6단계로 나누겠습니다

NSIGHT에서 Architecture 완료상태는 다음처럼 보는 것이 적절합니다.

```text
① DOCUMENTED
   문서가 작성되었다
        ↓

② DESIGN APPROVED
   설계가 Architecture Review를 통과했다
        ↓

③ IMPLEMENTED
   Source / Config / Infrastructure에 구현되었다
        ↓

④ VERIFIED
   Rule / Test로 구현 정합성을 검증했다
        ↓

⑤ RUNTIME PROVEN
   실제 실행환경에서 증명했다
        ↓

⑥ BASELINED
   Drift/GAP/ADR를 닫고
   Human Gate를 통과하여
   공식 Architecture Baseline이 되었다
```

이 구분이 앞으로 매우 중요합니다.

예를 들어:

```text
HA/DR 문서 작성 완료 = DOCUMENTED

센터 전환시험 성공 = RUNTIME PROVEN

HG90 승인 = BASELINED
```

입니다.

따라서 **“아키텍처 정의서 100% 작성”과 “아키텍처 완료 100%”는 완전히 다른 의미**입니다.

---

# 22.2 Architecture 전체 DoD

가장 상위 수준의 완료조건부터 정의하면 다음과 같습니다.

| DoD 영역          | 완료조건                                                     |
| ----------------- | ------------------------------------------------------------ |
| **Document**      | Canonical Architecture 문서 존재, 상태/Version/Baseline 식별 |
| **Requirement**   | 요구사항 → Architecture 설계 추적 가능                       |
| **Decision**      | Critical Architecture Decision이 ADR로 승인됨                |
| **Model**         | Machine-readable Architecture Model이 Schema 검증됨          |
| **Traceability**  | Requirement→ServiceId→Code→DB→Runtime 역·정방향 추적 가능    |
| **Source**        | 승인 Architecture와 실제 Source가 Conformance                |
| **Configuration** | 설계값과 실제 Effective Config 연결                          |
| **Security**      | 보안 Rule/Test 및 Critical Key/Session/JWT 정책 검증         |
| **Build**         | 승인된 Source에서 Build 성공                                 |
| **Artifact**      | Artifact ID/Hash가 고정됨                                    |
| **Deployment**    | Tested Artifact와 Deployed Artifact가 동일                   |
| **Runtime**       | 필수 Runtime Scenario PASS                                   |
| **Observability** | GUID+ServiceId E2E Trace 가능                                |
| **Resilience**    | N-1, Failover, Failback 증적                                 |
| **Performance**   | 목표 TPS/p95 및 자원 임계치 검증                             |
| **Drift**         | Critical Drift OPEN = 0                                      |
| **GAP**           | Critical GAP OPEN = 0 또는 승인된 Exception                  |
| **Approval**      | 필요한 Human Approval 완료                                   |
| **Gate**          | HG90 PASS                                                    |

현재 Closed Loop 마스터도 최종 완료조건을 `Document Baseline Valid → Model Schema Valid → Model↔Source Match → Architecture Rules PASS → Build/Test/Security/Deployment PASS → Runtime Evidence → Critical Drift=0 → Human Approval → HG90 PASS`로 명시하고 있습니다.

---

# 22.3 ① DOCUMENTED — 문서작성 완료의 DoD

이 단계는 가장 낮은 수준의 완료입니다.

문서가 단순히 파일로 존재한다고 완료가 아닙니다.

예를 들어 `22-HA-DR.md`의 작성 완료조건이라면:

| 검증         | 완료조건                           |
| ------------ | ---------------------------------- |
| 목적         | 왜 이 Architecture가 필요한지 명시 |
| 범위         | 대상 시스템/환경/센터 명시         |
| AS-IS        | 현재 구조 식별                     |
| TO-BE        | 목표 구조 식별                     |
| 책임         | Component별 Owner 명시             |
| 정상패턴     | 정상 설계 표현                     |
| 금지패턴     | 허용하지 않는 구조 표현            |
| NFR          | 관련 성능/가용성/보안 조건         |
| GAP          | 미확정사항 별도 표시               |
| ADR          | 결정 필요사항 ID 연결              |
| Evidence     | 근거 Source 연결                   |
| Traceability | Requirement/Rule/Gate 연결         |
| 상태         | DRAFT/REVIEW/APPROVED 등 표시      |

즉:

```text
"내용이 많다"
≠
"문서 품질이 좋다"
```

입니다.

---

# 22.4 ② DESIGN APPROVED — 설계승인의 DoD

다음 단계는 Architecture Review입니다.

```text
Document
   ↓
Architecture Review
   ↓
Normal / Prohibited Pattern
   ↓
Requirement/NFR 정합성
   ↓
Critical GAP
   ↓
ADR
   ↓
Design Approval
```

여기서는 아직 Runtime까지 필요하지 않을 수 있습니다.

하지만 최소:

| 검증         | 기준                                       |
| ------------ | ------------------------------------------ |
| Vision/NFR   | NSIGHT Vision과 충돌 없음                  |
| Big Picture  | 책임과 경계 일치                           |
| Logical      | Domain/Data/Integration 정책 일치          |
| Physical     | Logical Boundary가 실제 자원으로 구현 가능 |
| Mechanism    | 정책 강제 수단 존재                        |
| Security     | 보안구조 포함                              |
| Operations   | 운영·장애·관측 고려                        |
| Alternatives | 중요 선택은 대안 비교                      |
| ADR          | 중요 결정은 ADR화                          |
| Rule         | 자동검증 가능한 항목 Rule 정의             |
| Review       | EA/관련 Architect 검토 완료                |

여기까지 오면 상태를:

```text
APPROVED DESIGN
```

으로 볼 수 있습니다.

아직:

```text
RUNTIME APPROVED
```

는 아닙니다.

---

# 22.5 ③ IMPLEMENTED — 구현완료의 DoD

설계서가 승인되었다고 실제 시스템이 그렇게 만들어졌다는 보장은 없습니다.

그래서:

```text
Approved Architecture
        ↓
Source
Config
Infrastructure
DB
Middleware
Deployment
```

에 실제로 구현됐는지 확인합니다.

Application이라면:

```text
ServiceId
 ↓
Handler
 ↓
Facade
 ↓
Service
 ↓
DAO
 ↓
Mapper
```

가 Source에 존재해야 합니다.

Physical이라면:

```text
Application
 ↓
WAR
 ↓
Tomcat JVM
 ↓
WAS
 ↓
Apache Route
 ↓
L4
```

가 실제로 존재해야 합니다.

현재 G30에서도 71대 Physical Server Baseline과 Apache/Tomcat 구조 자체는 기준화됐지만, **71대 Server↔JVM↔Application/WAR 전수 매핑, 실제 Apache Routing Config, Tomcat server.xml/setenv.sh 등의 증적은 아직 완료조건으로 남아 있습니다.**

따라서:

```text
서버가 구축됨
≠
Physical Architecture 구현완료
```

입니다.

---

# 22.6 ④ VERIFIED — 구현정합성 검증의 DoD

이제 15번 Rulebook이 실제로 사용됩니다.

```text
Architecture Model
       ↓
Rule
       ↓
Source / Config Scan
       ↓
Conformance Result
```

예:

```text
Rule:
Handler → DAO Direct Call 금지

Actual:
0건

Result:
PASS
```

또는:

```text
Rule:
ServiceId Unique

Actual:
Duplicate 2건

Result:
FAIL
```

검증 대상은 크게:

| 분류             | 검증 예                      |
| ---------------- | ---------------------------- |
| Structural       | 패키지/계층/ServiceId/Mapper |
| Framework        | TCF/STF/ETF/Dispatcher       |
| Message          | Header/DTO/Context           |
| Domain           | 타 Domain DAO/Table 접근     |
| Security         | Private Key/JWT/Auth         |
| Configuration    | Timeout/Pool/JVM             |
| Runtime Contract | TX/Timeout/Trace             |
| Governance       | Evidence/Hash/Approval       |

현재 Closed Loop에서는 P0 Rule로 ServiceId Unique, ServiceId→Handler, Handler/Controller→DAO 직접호출 금지, Mapper SQL ID Unique, JWT Private Key Exposure 금지, Runtime Evidence/Artifact Hash/Approval 필수를 우선 구현하도록 정의합니다.

# 22.7 ⑤ RUNTIME PROVEN — 이것이 가장 중요한 DoD입니다

여기서부터 Architecture가 진짜 증명됩니다.

예를 들어 설계에:

```text
p95 ≤ 3초
```

라고 적혀 있다면 완료조건은:

```text
문서에 3초라고 적혀 있음
```

이 아닙니다.

실제로:

```text
Load Test
  ↓
Target TPS
  ↓
p95
  ↓
CPU / Heap / Thread
  ↓
Hikari / DB Session
  ↓
SQL
  ↓
Error
  ↓
PASS
```

가 되어야 합니다.

Runtime DoD의 대표 Matrix는 다음과 같습니다.

| Runtime 검증     | 완료기준                          |
| ---------------- | --------------------------------- |
| 정상조회         | E2E 거래 성공 및 Trace            |
| 변경거래         | Commit/Rollback 정합성            |
| Timeout          | Rollback + Connection/Thread 반환 |
| Slow SQL         | Deadline 적용 및 시스템 회복      |
| Pool Pressure    | Hikari Pending/Session 안정성     |
| Peak             | 목표 TPS/p95                      |
| Stress           | 자원한계 및 Graceful Degradation  |
| N-1              | 노드 장애 후 SLA 유지 여부        |
| Session Failover | 정책에 따른 세션 결과             |
| Center Failover  | DR 전환/RTO                       |
| Failback         | Main 복귀 및 정합성               |
| Rolling Deploy   | 잔여 Capacity 유지                |
| JWT Rotation     | Key Rotation/Validation           |
| Trace            | GUID+ServiceId E2E 유지           |

현재 G80의 Blocking Condition에도 정확히 **Transaction/Timeout Fault Runtime Evidence, P600/P1200/S1800/N-1, Center/Session Failover/Failback, GUID+ServiceId E2E Trace**가 P0로 남아 있습니다.

# 22.8 Runtime Test가 PASS했는데 Evidence가 없으면?

NSIGHT에서는 완료가 아닙니다.

예를 들어 담당자가:

```text
"지난주에 DR 테스트했습니다.
잘 됐습니다."
```

라고 말한다고 합시다.

필요한 것은:

```text
Run ID
Start Time
Failure Time
Switch Time
Service Recovery Time
RTO
DB State
Application State
Business Validation
Failback
Log
Metric
Approver
```

입니다.

즉:

```text
시험 수행
≠
Runtime Evidence 확보
```

입니다.

Closed Loop 기준에서도 Runtime Evidence가 없으면 HG90 PASS를 명시적으로 금지합니다.

# 22.9 ⑥ BASELINED — 최종 완료

이 단계가 실제 Architecture DoD의 끝입니다.

```text
Document Valid
       ↓
Model Valid
       ↓
Source Conformance
       ↓
Rule PASS
       ↓
Test PASS
       ↓
Runtime PASS
       ↓
Evidence Captured
       ↓
Drift Check
       ↓
Critical GAP/ADR Closure
       ↓
Human Approval
       ↓
HG90
       ↓
BASELINED
```

현재 HG90 재심 조건은 구체적으로:

```text
P0 FAIL_TARGET = 0

P0 OPEN_RUNTIME = 0
또는 approved exception

Critical ADR approved

Model Schema PASS

Mandatory Runs complete

Evidence Manifest complete
```

입니다.

이 단계까지 와야:

> **“NSIGHT Architecture가 완료됐다.”**

고 말할 수 있습니다.

# 22.10 중간 Gate의 CONDITIONAL PASS는 완료가 아닙니다

현재 NSIGHT Gate 상태가 이를 잘 보여줍니다.

| Gate | 현재 상태        |
| ---- | ---------------- |
| G00  | CONDITIONAL PASS |
| G10  | **PASS**         |
| G20  | CONDITIONAL PASS |
| G30  | CONDITIONAL PASS |
| G40  | CONDITIONAL PASS |
| G50  | CONDITIONAL PASS |
| G60  | CONDITIONAL PASS |
| G70  | CONDITIONAL PASS |
| G80  | **HOLD**         |
| HG90 | **HOLD**         |

즉 여러 단계가 `CONDITIONAL PASS`라고 해서:

```text
Architecture 거의 완료
```

라고 해석하면 안 됩니다.

CONDITIONAL PASS의 뜻은:

> **“현재 단계의 방향은 수용 가능하지만 후속 완료조건이 남아 있다.”**

입니다.

# 22.11 G20 Logical DoD

현재 실제 Gate 조건을 이용하면 Logical Architecture의 완료조건도 명확해집니다.

| DoD              | 현재 요구                                      |
| ---------------- | ---------------------------------------------- |
| Domain Catalog   | 전체 Domain/Owner 확정                         |
| Data Ownership   | Domain별 Table/View 소유 확정                  |
| Service Contract | Public ServiceId/Integration Contract Registry |
| Physical Link    | 71 Server↔JVM↔WAR                              |
| Routing          | Apache→Tomcat 실제 Route                       |
| Timeout          | ServiceId별 Deadline/Timeout Metadata          |
| OM Boundary      | Runtime Evidence 책임경계                      |

현재 이 항목들이 G20 Conditional Pass 조건으로 실제 관리되고 있습니다.

즉 Logical Architecture 문서 자체는 있어도 **Domain/Data/Contract Catalog가 완성되지 않으면 Logical DoD는 닫히지 않습니다.**

# 22.13 Application Architecture 품질체크

# 22.17 Security 품질체크

# 22.18 HA/DR DoD

# 22.25 “P0가 하나 남았는데 거의 끝났습니다”는 어떻게 볼 것인가

NSIGHT에서는 특히 마지막 단계에서 이렇게 보면 안 됩니다.

```text
P0 100개 중
99개 완료

1개 미완료

→ 99% 완료
```

Critical Architecture에서는:

```text
P0 1개 OPEN
        ↓
Production Risk 존재
        ↓
HG90 HOLD
```

일 수 있습니다.

예를 들어:

```text
JWT Private Key 안전성 미확정
```

은 다른 99개 문서가 완료됐다고 무시할 수 없습니다.

그래서 Architecture Completion은 단순 평균 진행률이 아니라 **Gate 기반**이어야 합니다.

# 22.26 권장 Architecture 진행률 모델

프로젝트 관리용으로는 다음처럼 분리하는 것이 좋습니다.

| Progress               | 의미               |
| ---------------------- | ------------------ |
| Document %             | 문서 작성량        |
| Review %               | 설계 Review 완료   |
| Implementation %       | 실제 반영          |
| Static Verification %  | Rule/Test 완료     |
| Runtime Verification % | 실측 검증          |
| P0 Closure %           | Critical GAP/ADR   |
| Baseline %             | Gate/Approval 완료 |

예를 들어 현재:

```text
Document              90%
Design Review          80%
Implementation         70%
Static Verification    65%
Runtime Verification   30%
P0 Closure             40%
Baseline               HOLD
```

처럼 표현하는 것이 단순히:

```text
Architecture 진행률 85%
```

라고 하는 것보다 훨씬 정확합니다.

위 숫자는 설명을 위한 예시이지 현재 프로젝트 실측 진행률은 아닙니다.

# 22.30 22번의 핵심 결론

**NSIGHT의 Architecture Definition of Done은 “아키텍처 문서를 작성했다”가 아니라, 요구사항과 NFR이 Architecture에 반영되고, 그 Architecture가 Model과 Rule로 구조화되며, 실제 Source·Configuration·Infrastructure에 구현되고, Static/Functional/Security Test와 Runtime Scenario에서 검증되고, GUID·ServiceId·Metric·Log·Artifact Hash 등의 Evidence로 증명되며, Critical Drift·GAP·ADR가 종료되고 Human Gate인 HG90을 통과해 공식 Baseline으로 승격된 상태입니다.**

따라서 앞으로 “아키텍처 작업이 완료됐습니까?”라는 질문에는 단순히 문서 개수로 답하지 않고:

```text
Documented?
Design Approved?
Implemented?
Verified?
Runtime Proven?
Baselined?
```

**이 여섯 단계로 답하는 것이 NSIGHT 기준에서 가장 정확합니다.**

현재 자료 기준으로 NSIGHT는 **전략·설계·Static Architecture 측면에서는 상당히 성숙했지만, `G80=HOLD`, `HG90=HOLD`이며 Mandatory Runtime Evidence와 Critical P0 Closure가 남아 있으므로 최종 `BASELINED / Architecture Done` 상태는 아닙니다.**

이제 **23번째 단계에서는 “그렇다면 현재 NSIGHT를 실제로 완료시키려면 무엇부터 해야 하는가?”를 다루는 것이 자연스럽습니다.** 즉 지금까지의 모든 GAP을 다시 늘어놓는 것이 아니라, **P0 Closure Plan — 1차 Baseline 확정 → Traceability → Server/JVM/WAR → Critical ADR → Runtime Test → G80 → HG90** 순으로 실제 완료 로드맵을 만들겠습니다.
