좋습니다. 이제 **18번째 설명 — NSIGHT Architecture Drift → GAP → ADR → New Baseline**으로 진행하겠습니다.

17번에서 `Baseline → Model → Traceability`를 만들었습니다. 그런데 실제 프로젝트에서는 문서·모델·소스·설정·운영환경이 계속 바뀝니다. 따라서 18번의 핵심 질문은 이것입니다.

> **“기준과 실제가 달라졌을 때, 무엇을 오류로 고치고 무엇을 새로운 아키텍처 결정으로 받아들일 것인가?”**

NSIGHT Closed Loop는 이를 `Runtime Evidence → Drift Detection → GAP/ADR → New Baseline`으로 관리하도록 정의합니다.

# 18. Drift → GAP → ADR → New Baseline

## 18.1 먼저 Drift는 “문제”와 동일한 말이 아닙니다

Drift의 가장 정확한 뜻은:

> **기대했던 Architecture와 실제 상태 사이에서 발견된 차이**

입니다.

```text
Expected
Architecture / Model
        │
        │ 비교
        ▼
Actual
Code / Config / Runtime
        │
        ▼
    Difference
        │
        ▼
      DRIFT
```

여기서 바로:

```text
DRIFT = 오류
```

라고 판단해서는 안 됩니다.

실제 Source가 잘못됐을 수도 있지만 반대로 **기존 Model이나 문서가 오래되었을 수도 있기 때문**입니다.

NSIGHT Closed Loop도 Drift가 발견되면 자동 수정하지 않고 Evidence와 함께 분류하도록 명시합니다. Critical/High/Medium/Low로 심각도를 관리하고, Evidence가 없는 차이는 FACT가 아니라 UNKNOWN/Candidate로 유지합니다.

---

# 18.2 NSIGHT가 검사하는 Drift는 6가지가 핵심입니다

현재 Closed Loop 실행 기준에는 다음 D1~D6가 직접 정의되어 있습니다.

| Drift  | 비교             | 예                                                |
| ------ | ---------------- | ------------------------------------------------- |
| **D1** | Document ↔ Model | 문서에 ServiceId는 있는데 Model에는 없음          |
| **D2** | Model ↔ Code     | Model의 Handler와 실제 Handler가 다름             |
| **D3** | Model ↔ Config   | Model Timeout 3초, 설정 5초                       |
| **D4** | Code ↔ Runtime   | 예상 TX Owner와 실제 Runtime TX Owner가 다름      |
| **D5** | Config ↔ Runtime | Hikari 설정 120, 실제 Runtime Max 80              |
| **D6** | Test ↔ Runtime   | Test에서는 Timeout PASS, 운영에서는 SQL 계속 실행 |

이 표가 굉장히 중요합니다.

17번에서 만든 Traceability가 있어야 이 비교가 가능합니다.

---

# 18.3 여기에 NSIGHT 전체 아키텍처 관점의 Drift가 더 있습니다

통합 Architecture 마스터 기준에서는 다음도 Drift 대상으로 봅니다.

```text
Document ↔ Source

Source ↔ Configuration

Configuration ↔ Runtime

Architecture Rule ↔ Code

Model ↔ Code

Inventory ↔ 실제 배치

Capacity Design ↔ 실제 설정

Requirement ↔ 구현

OM Catalog ↔ 실제 ServiceId

Guide ↔ Current Code
```

즉 Drift는 Application Source에만 있는 개념이 아닙니다.

예를 들어:

```text
Architecture 그림
WAS01 → App A
```

인데 실제 서버를 보니:

```text
WAS01
 └─ Tomcat JVM #1
      └─ App B
```

라면 이것도 **Physical Architecture Drift**입니다.

---

# 18.4 Drift와 GAP은 다릅니다

이 차이를 꼭 구분해야 합니다.

```text
DRIFT
=
"차이가 발견되었다"


GAP
=
"그 차이를 분석한 결과,
현재 상태와 목표 상태 사이에
해결해야 할 Architecture 차이가 있다"
```

예를 들어:

```text
Model
Timeout = 3초

Config
Timeout = 5초
```

를 찾았습니다.

이 순간은 아직:

```text
DRIFT
```

입니다.

그다음 분석합니다.

```text
3초가 승인된 표준인가?

5초가 운영상 필요한 값인가?

문서가 오래된 것인가?

Config가 잘못된 것인가?
```

그 결과:

```text
TO-BE = 3초
Actual = 5초
```

로 판단되면:

```text
Architecture GAP
```

으로 승격합니다.

Closed Loop에서는 `AS-IS ≠ TO-BE`, `Model ≠ Code`, `Code ≠ Config`, `Config ≠ Runtime`, `Test PASS ≠ Runtime Result`, `Document ≠ Source` 등을 GAP 등록 후보로 정의합니다.

---

# 18.5 그래서 Drift가 발견되면 6가지로 분류해야 합니다

현재 실행 프로세스에서는 Drift를 다음과 같은 조치 유형으로 분류합니다.

```text
DRIFT
  │
  ├─ 단순 문서 오류
  │
  ├─ Code Defect
  │
  ├─ Configuration Drift
  │
  ├─ Architecture GAP
  │
  ├─ ADR 필요사항
  │
  └─ Exception
```

이것이 핵심입니다.

예를 들어 Source가 Model과 다르다고 해서 무조건 Source를 고치는 것이 아닙니다.

---

# 18.6 첫 번째 예 — 문서가 잘못된 경우

문서:

```text
Tomcat maxThreads = 1,500
```

그런데 현재 승인된 Architecture Decision과 실제 설정은:

```text
maxThreads = 900
```

이고 성능시험도 900에서 정상이라고 하겠습니다.

그러면:

```text
Document = Old
Code/Config/Runtime = Correct
```

일 수 있습니다.

이 경우 조치는:

```text
Code 변경 X

Document Update O
```

입니다.

즉 Drift가 오히려 **문서가 현실을 따라가지 못하고 있음을 발견한 것**입니다.

---

# 18.7 두 번째 예 — Code Defect

Expected Model:

```text
Handler
   ↓
Facade
   ↓
Service
   ↓
DAO
```

Actual Source:

```text
Handler
   ↓
DAO
```

이라면 기존 Architecture Rule과 충돌합니다.

이 경우 특별한 Architecture 이유가 없다면:

```text
DRIFT
  ↓
Code Defect
  ↓
Source 수정
```

입니다.

이때는 굳이 새로운 ADR을 만들 필요가 없습니다.

---

# 18.8 세 번째 예 — Configuration Drift

Expected:

```text
Hikari
maximumPoolSize = 120
```

실제 Runtime:

```text
maximumPoolSize = 80
```

이라면 D5 유형입니다. 이 예시는 Closed Loop 정의에도 직접 사용됩니다.

이때:

```text
application.yml은 120인데
운영 환경변수가 80을 Override
```

했을 수도 있습니다.

그러면:

```text
Model
  ↓
Config File
  ↓
Environment Variable
  ↓
Runtime Effective Config
```

까지 확인해야 합니다.

Architecture에서는 **파일에 무엇이 써 있는지보다 실제 Runtime Effective Value가 더 중요**합니다.

---

# 18.9 네 번째 예 — NSIGHT 실제 Capacity 충돌

현재 Current Baseline에는 이런 값들이 함께 관리되고 있습니다.

| 항목              |          Working | Historical / Alternative |
| ----------------- | ---------------: | -----------------------: |
| Session Idle      |             90분 |                     60분 |
| 16Core Capacity   |       약 855 TPS |                  500 TPS |
| Tomcat maxThreads |        800~1,000 |              1,200~1,500 |
| Hikari            | 120~150 또는 150 |                   80~100 |

그리고 이를 **Versioned Baseline으로 유지하면서 최종 검증이 필요**하다고 명시합니다.

여기에서 매우 중요한 점은:

```text
855 TPS
vs
500 TPS
```

가 있다고 해서 바로:

```text
855가 정답
500은 틀림
```

이라고 하면 안 된다는 것입니다.

현재 상태는:

```text
Baseline Conflict Candidate
```

에 가깝습니다.

이를 닫으려면:

```text
동일 Hardware
동일 Application
동일 Data
동일 SQL
동일 Runtime Config
동일 Test Scenario
```

조건에서 Runtime Test를 해야 합니다.

그 뒤에야:

```text
Approved Capacity
```

로 승격할 수 있습니다.

---

# 18.10 이 경우 GAP은 이렇게 작성합니다

Closed Loop에서 GAP 객체는 다음 정보를 갖습니다.

```yaml

systemScope:
title:
asIs:
toBe:

impact:
severity:

```

```text

855 TPS Working 기준이 병존

Runtime Test로 승인된
단일 Capacity Baseline

Impact

N-1 Capacity

Tomcat Thread

Severity
CRITICAL

P600

```

처럼 관리해야 합니다.

이렇게 하면 단순한 “숫자 논쟁”이 **Architecture 관리객체**가 됩니다.

---

# 18.11 GAP과 ADR의 차이

이것도 중요합니다.

```text
GAP
=
"차이를 해결해야 한다"


ADR
=
"그 차이를 해결하기 위해
여러 선택지 가운데 무엇을 선택할 것인가"
```

예를 들어 Session 문제가 있습니다.

```text
센터 장애 시 Session 연속성을
어떻게 보장할 것인가?
```

이것은 단순 Code Defect가 아닙니다.

선택지가 있습니다.

```text
Option A
DeltaManager

Option B
Spring Session JDBC

Option C
DR 전환 시 재로그인 허용
```

이런 것은 **ADR**입니다.

---

# 18.12 어떤 항목이 ADR 대상인가

현재 Closed Loop는 다음과 같은 항목을 ADR 후보로 직접 정의합니다.

```text

Retry
Session
JWT Verification Location
Gateway
WAR Split
Cache
DB Pool
Masking
Encryption
EAI

Package

```

NSIGHT 통합 Architecture 기준에서는 여기에:

```text
Apache/Tomcat Instance
1 JVM : 1 Application 여부
8Core / 16Core / 32Core
RDW / ADW 경계
Domain Integration
OM 통합
HA / DR
Architecture Model SoT
```

등도 주요 ADR 후보로 잡고 있습니다.

---

# 18.13 ADR은 “결론 한 줄”이 아닙니다

NSIGHT ADR의 권장 구조는 다음처럼 상당히 엄격합니다.

```text

Constraints

Alternatives

Comparison

Decision

Rationale

Impact

Risk

Implementation Location

Test Method

Rollback / Migration

Deprecation Condition
```

왜 이렇게까지 하느냐 하면 Architecture Decision은 몇 달 뒤에:

> **“왜 이 선택을 했습니까?”**

라는 질문에 답해야 하기 때문입니다.

---

# 18.14 Session ADR을 예로 보면

```text
ADR-SES-001

Problem
센터/WAS 장애 시 Session 전략

Requirement
로그인 사용자 연속성
성능
보안

운영복잡도

Option A
DeltaManager

Option B
Spring Session JDBC

Option C
DR 전환 시 재로그인

성능 / 구현난이도 / DR / 비용 / 장애범위

미결정

```

현재 Current Baseline에서도 Session Strategy와 Timeout ADR은 다음 확정대상으로 남아 있습니다.

즉 **Working Candidate를 Approved Architecture로 착각하면 안 됩니다.**

---

# 18.15 ADR은 AI가 임의로 승인하면 안 됩니다

현재 Orchestration 지침은 중요한 Architecture 선택을 AI가 자동 확정하지 말고 **Human Approval 대상**으로 넘기도록 명시합니다. 특히 업무규칙, 데이터 소유권, 개인정보, 보안, Transaction Boundary, Session/JWT, 장애전파, Architecture Exception, Baseline 승격이 여기에 해당합니다.

따라서:

```text
AI
"Option B가 좋아 보입니다."
```

와:

```text
Architecture Board
"Option B를 공식 Baseline으로 승인합니다."
```

는 완전히 다른 상태입니다.

---

# 18.16 Exception도 별도의 관리대상입니다

어떤 GAP을 지금 당장 해결할 수 없을 수도 있습니다.

예를 들어:

```text
Legacy System 때문에
DB Link를 당장 제거할 수 없음
```

이라면:

```text
Architecture Rule 위반
```

이지만 즉시 제거가 불가능할 수 있습니다.

이 경우:

```text
Exception
```

으로 관리합니다.

그러나 Exception에는 반드시:

```text
왜 필요한가
위험은 무엇인가
누가 책임지는가
Compensating Control은 무엇인가
언제 만료되는가
언제 제거할 것인가
```

가 있어야 합니다.

Closed Loop에서도 **예외에는 만료일이 반드시 있어야 한다**고 규정합니다.

즉 Exception은:

```text
영구적인 표준 우회
```

가 아닙니다.

---

# 18.17 결국 Drift 하나의 생명주기는 이렇게 됩니다

```text
             DRIFT 발견
                  │
                  ▼
             Evidence 확인
                  │
                  ▼
              분류
                  │
     ┌────────────┼─────────────┐
     │            │             │
     ▼            ▼             ▼
Document       Code/Config  Architecture
 Error           Defect        GAP
     │            │             │
     ▼            ▼             ▼
  수정           수정        Decision 필요?
                                  │
                         ┌────────┴────────┐
                         │                 │
                        NO                YES
                         │                 │
                         ▼                 ▼
                       수정               ADR
                                           │
                                      Human Approval
                                           │
                                           ▼
                                      Implementation
                                           │
                                           ▼
                                         Test
                                           │
                                           ▼
                                  Runtime Evidence
```

그리고 모두 검증되면 다음 단계로 갑니다.

---

# 18.18 여기서 바로 New Baseline을 만들면 안 됩니다

아주 중요한 부분입니다.

```text
ADR 승인
   ↓
New Baseline
```

이 아닙니다.

정확한 순서는 현재 Closed Loop에 다음과 같이 정의되어 있습니다.

```text
Resolved GAP
      ↓
Approved ADR
      ↓
Architecture Model Update
      ↓
Schema Validation
      ↓
Source / Test Verification
      ↓
Document Baseline Update
      ↓
New Baseline ID
```

그리고 Runtime 성질을 가진 결정이라면 당연히 Runtime Evidence도 필요합니다.

즉:

> **Decision을 했다는 것과 Decision이 성공적으로 구현됐다는 것은 다릅니다.**

---

# 18.19 New Baseline은 하나의 Version Package입니다

예를 들어:

```text
Architecture Baseline
ARCH-2026.08.17-03

Model Version
MODEL-3.1.0

Source Commit
a8f27c1

Build
BUILD-20260817-142

Deploy
DEPLOY-DEV-20260817-09
```

처럼 연결합니다.

여기에 17번에서 설명한:

```text
Artifact Hash
Test Run
Runtime Evidence
ADR
Approval
```

도 연결되어야 합니다.

그래야 새 Baseline의 실제 의미가 생깁니다.

---

# 18.20 과거 Baseline은 삭제하지 않습니다

이것도 매우 중요합니다.

새 Baseline이 만들어졌다고:

```text
ARCH-01 삭제
ARCH-02 삭제
ARCH-03 CURRENT
```

해서는 안 됩니다.

Closed Loop 기준은:

```text
CURRENT
SUPERSEDED
DEPRECATED
```

상태로 보존하도록 명시합니다.

예:

```text
ARCH-001
SUPERSEDED

ARCH-002
SUPERSEDED

ARCH-003
CURRENT
```

그러면 나중에 특정 장애 시점에:

```text
당시에는 어떤 Architecture가 운영 중이었는가?
```

를 역추적할 수 있습니다.

---

# 18.21 즉 Architecture에도 형상관리가 필요합니다

Software에는 당연히:

```text
v1.0
v1.1
v2.0
```

이 있습니다.

Architecture도 마찬가지여야 합니다.

```text
ARCH-001
   │
   ├─ ADR-01
   │
   ▼
ARCH-002
   │
   ├─ ADR-02
   ├─ ADR-03
   │
   ▼
ARCH-003
```

그리고 각 Architecture Baseline에는:

```text
왜 바뀌었는가?
무엇이 바뀌었는가?
어떤 ADR 때문인가?
어떤 Source에서 구현됐는가?
어떤 Test를 통과했는가?
```

가 남습니다.

이것이 **Architecture Change History**입니다.

---

# 18.22 전체 과정에서 Gate의 역할

이제 16번 Gate와 연결해보겠습니다.

실행 시스템에서는:

```text
G50 Runtime
      ↓
G60 Drift
      ↓
G70 GAP / ADR
      ↓
G80 Human Approval
      ↓
HG90 Release
```

구조로 정의됩니다.

즉:

```text
G60
"차이가 무엇인가?"

G70
"그 차이를 어떻게 해결할 것인가?"

G80
"그 결정을 승인할 것인가?"

HG90
"검증된 결과를 새 기준으로 승격할 것인가?"
```

라고 이해하면 됩니다.

---

# 18.23 HG90에는 아주 강한 조건이 있습니다

New Baseline으로 승격하려면 다음과 같은 Final Hard Blocker를 통과해야 합니다.

```text
Document Baseline
Model Schema
Model ↔ Source / Conformance
Architecture Rule Evidence
Build PASS
Test PASS
Security PASS
Artifact SHA-256
Deployment Evidence
Tested Hash == Deployed Hash
Runtime Evidence
Critical Drift OPEN = 0
Critical GAP OPEN = 0
Required Human Approval
```

현재 Execution System Map에서 HG90/RHG90은 이 조건을 평가기가 직접 확인하고 **수동 PASS Override를 허용하지 않는 구조**로 정의됩니다.

이것이 매우 중요합니다.

---

# 18.24 실제 NSIGHT의 한 사이클을 예로 들어보겠습니다

예를 들어 **Hikari Pool**을 보겠습니다.

### ① Current Baseline

```text
Hikari = 120
```

### ② Runtime

```text
Peak 1,200 TPS에서
Pending 증가
Pool 95%
```

### ③ Drift

```text
Capacity Model과
Runtime Behavior 불일치
```

### ④ GAP

```text
GAP-DBPOOL-001
```

# 18.25 Transaction Owner도 같은 방식입니다

Expected:

```text
Facade
=
Transaction Owner
```

그런데 Source Scan에서:

```text
Service에도 @Transactional 존재
```

를 발견했다고 합시다.

바로:

```text
@Transactional 삭제
```

하면 안 됩니다.

먼저:

```text
의도된 Inner TX인가?

Propagation 분리가 필요한가?
```

를 봅니다.

그 뒤:

```text

```

이면 수정하고,

```text
Architecture Trade-off
```

이면 ADR을 만듭니다.

이것이 Source를 정답으로 취급하지도 않고, Model을 무조건 정답으로 취급하지도 않는 NSIGHT Closed Loop의 중요한 특징입니다.

# 18.27 GAP Register는 Drift Register와 분리해야 합니다

Drift는 “발견” 중심이고 GAP은 “조치” 중심입니다.

```text
DRIFT REGISTER
        │
        │ 분석
        ▼
     GAP REGISTER
```

예를 들어 Drift 5개가 사실 하나의 GAP일 수도 있습니다.

```text
DRIFT-01
Thread 설정 불일치

DRIFT-02
Hikari 설정 불일치

DRIFT-03
DB Session 불일치

        ↓

GAP-CAP-001
"온라인 Capacity Baseline 미확정"
```

입니다.

즉:

```text
Drift 1 : GAP 1
```

관계만 존재하는 것이 아닙니다.

```text
N Drift
  ↓
1 Architecture GAP
```

일 수 있습니다.

# 18.28 Risk와 GAP도 구분해야 합니다

```text
GAP
=
현재 존재하는 차이


RISK
=
앞으로 발생할 가능성이 있는 위험
```

예를 들어:

```text
DR 서버 Capacity가
1,200 TPS보다 작음
```

이 사실로 확인됐다면:

```text
GAP
```

입니다.

반면:

```text
현재 Capacity는 충분하지만
N-1 + 추가 장애 시 부족할 가능성
```

이라면:

```text
Risk
```

일 수 있습니다.

통합 Architecture 기준도 GAP, Risk, Open Issue, ADR을 별도 Register로 관리하도록 정의합니다.

# 18.29 OPEN/UNKNOWN도 억지로 닫으면 안 됩니다

예를 들어 현재 자료에서:

```text
Session Idle
90분 vs 60분
```

이 있습니다.

근거 없이:

```text
최신 문서가 90분이니 90분 확정
```

이라고 해버리면 위험합니다.

정확한 상태는:

```text
OPEN
```

또는 Evidence가 부족하면:

```text
UNKNOWN
```

이어야 합니다.

Orchestration의 공통 상태도:

```text
FACT
CONFIRMED
AS-IS
TO-BE
DECISION
PROPOSED
GAP
DEPRECATED
UNKNOWN
OPEN
```

을 사용하고, `AS-IS != TO-BE`는 임의로 보정하지 않도록 정의합니다.

# 18.31 이것이 왜 중요한가

전통적인 Architecture Management는 보통:

```text
초기 설계
 ↓
문서 승인
 ↓
개발
 ↓
끝
```

이었습니다.

그러면 몇 년 지나면:

```text
Document
≠
Code
≠
Server
≠
Runtime
```

이 됩니다.

NSIGHT가 지향하는 것은:

```text
Document
↕
Model
↕
Code
↕
Config
↕
Runtime
```

의 차이를 계속 탐지하고,

```text
Drift
 ↓
Decision
 ↓
New Baseline
```

으로 진화시키는 것입니다.

그래서 Closed Loop의 최종 방향도:

> **Architecture as Document → Model → Code → Test → Runtime Evidence → Drift Detection → Decision → New Baseline**

으로 정의됩니다.

---

## 현재 NSIGHT 관점에서 가장 중요한 현실적 의미

현재 Baseline 자료도 Closed Loop의 방향은 TO-BE로 명확하지만, **Model/Code는 상당히 존재하는 반면 `Test → Runtime Evidence → Gate` 연결은 아직 미완성 GAP**이라고 명시하고 있습니다.

따라서 지금의 중요한 목표는 문서를 더 많이 만드는 것이 아니라:

```text
현재 Baseline 확정
       ↓
Drift 전수 탐지
       ↓
Critical GAP 식별
       ↓
P0 ADR 결정
       ↓
Runtime 검증
       ↓
HG90
       ↓
New Approved Baseline
```

으로 가는 것입니다.

# 18.32 18번의 핵심 결론

**Drift는 기대 Architecture와 실제 상태 사이의 ‘차이’, GAP은 그 차이를 분석해 해결해야 할 Architecture 문제로 정의한 것, ADR은 GAP을 해결하기 위해 중요한 선택을 공식적으로 결정한 기록이며, New Baseline은 그 결정이 Model·Source·Config·Test·Runtime에서 실제로 검증된 뒤 승인된 새로운 Architecture 기준점입니다.**

즉:

```text
Drift
=
"다르다"


GAP
=
"해결해야 한다"


ADR
=
"이렇게 해결한다"


New Baseline
=
"해결됐고 검증됐으므로
이제 이것이 새로운 공식 기준이다"
```

입니다.

그리고 이것으로 17번의 **Baseline/Model/Traceability**와 16번의 **Architecture Gate**, 15번의 **Rulebook**이 하나의 운영체계로 완전히 연결됩니다.

**19번째 단계에서는 이제 이 Closed Loop를 실제 사람이 수행하는 절차가 아니라 `Architecture Orchestrator + 전문 Agent`들이 어떻게 자동 실행하는지, 즉 `Mission → Agent Team → Document/Source/Model/Test/Runtime → Drift → GAP/ADR → Gate`의 NSIGHT Architecture Orchestration 실행체계로 연결하는 것이 자연스럽습니다.**
