좋습니다. 이제 **NSIGHT Logical Architecture**를 전략설명서 기준으로 설명하겠습니다.

여기서 가장 먼저 잡아야 할 것은 이것입니다.

> **Logical Architecture는 서버나 제품을 고르는 단계가 아니라, NSIGHT 안에서 무엇을 허용하고 무엇을 금지할지 결정하는 ‘정책 아키텍처’입니다.**

NSIGHT 수행방법론도 Logical 단계를 **“허용하는 것 + 금지하는 것 + 책임지는 주체 + 데이터가 이동하는 표준 경로”**를 정의하는 단계라고 명확히 설명합니다.

---

# 1. Big Picture와 Logical Architecture의 차이

앞에서 Big Picture에서는 공간을 만들었습니다.

```text
Channel
   ↓
Channel Integration
   ↓
┌──────────────────────────────┐
│       NSIGHT Service Zone    │
│                              │
│ Data Platform                │
│ Marketing Platform           │
│ BI Portal                    │
│ Data Governance              │
│ IT Service / Support         │
└──────────────────────────────┘
   ↓
Internal Integration
```

Big Picture의 질문은:

> **“누가 어디에 있는가?”**

입니다.

Logical Architecture는 한 단계 더 내려가:

> **“그 공간 안에서 누가 무엇을 할 수 있고, 서로 어떻게 연결되어야 하는가?”**

를 결정합니다.

따라서 관계는 다음과 같습니다.

```text
Big Picture
공간 + 책임 + 경계
       │
       ▼
Logical Architecture
정책 + 허용 + 금지 + 표준 경로
       │
       ▼
Physical Architecture
실제 서버 / DB / VM 배치
       │
       ▼
Mechanism
실제 기술로 정책 강제
```

이 순서가 중요합니다.

---

# 2. NSIGHT Logical Architecture의 핵심 정책

올려주신 전략자료를 다시 종합하면 핵심은 다음 **6개 축**으로 보는 것이 가장 명확합니다.

```text
                 NSIGHT LOGICAL ARCHITECTURE

                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
① Domain              ② Responsibility    ③ Data Flow
  Separation              Boundary           Control

       │                   │                   │
       └───────────────────┼───────────────────┘
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
④ Integration        ⑤ Resource /         ⑥ Standard
  Control               Runtime Isolation     Contract
```

이 여섯 가지가 서로 독립적인 것이 아니라 하나로 연결됩니다.

---

# 3. 정책 ① — Domain Separation

첫 번째가 **도메인 분리**입니다.

전략자료에서는 NSIGHT를 다음 5대 도메인으로 분리합니다.

| 도메인               | 핵심 책임                    |
| -------------------- | ---------------------------- |
| Data Platform        | 정보계 데이터 기반           |
| Marketing Platform   | 고객행동 기반 실시간 오퍼링  |
| BI Portal            | 분석·의사결정                |
| Data Governance      | 데이터 표준·품질·모델 일관성 |
| IT Service / Support | 아키텍처·운영 일관성         |

중요한 것은 단순히 조직이나 메뉴를 나눈 것이 아니라는 점입니다.

```text
             Domain Separation

Data                Marketing
 │                     │
 │ 데이터 관리          │ 고객 반응
 │                     │
 X─────────────────────X
 서로 책임을 침범하지 않음


BI                  Governance
 │                     │
 │ 분석/판단            │ 의미/품질 통제
 │                     │
 X─────────────────────X
```

즉 각 영역에 **Owner**가 생깁니다.

---

# 4. Domain Separation의 진짜 목적

왜 굳이 나누느냐가 중요합니다.

세 가지 때문입니다.

```text
Domain Separation
        │
        ├─ Responsibility Isolation
        │    책임 격리
        │
        ├─ Fault Isolation
        │    장애 격리
        │
        └─ Change Isolation
             변경 영향 격리
```

예를 들어 BI 기능을 수정했다고 마케팅 실시간 서비스까지 같이 배포해야 한다면 도메인 분리가 제대로 된 것이 아닙니다.

마찬가지로:

```text
BI 대량 분석 장애
       ↓
Marketing 장애
```

가 발생한다면 논리적 경계가 물리적으로 제대로 구현되지 않은 것입니다.

Vision/NFR에서도 `Domain Separation`, `Fault Isolation`, `FAST/DEEP Isolation`을 핵심 Architecture Principle로 명시합니다.

---

# 5. 정책 ② — Responsibility Boundary

도메인을 만들었으면 각 도메인이 무엇을 **소유**하는지도 정해야 합니다.

예를 들어:

```text
Data Platform
 ├─ RDW
 ├─ ADW
 ├─ 데이터 흐름
 └─ 데이터 저장 책임


Marketing Platform
 ├─ Customer Context 소비
 ├─ Event 처리
 ├─ Marketing Rule
 └─ Offering


BI Portal
 ├─ Dashboard
 ├─ Self-BI
 ├─ OLAP
 └─ Reporting
```

이 구조에서 Marketing Platform이:

```text
Marketing
   ↓
ADW 내부 테이블을 임의 갱신
```

하면 안 됩니다.

BI가:

```text
BI
 ↓
Marketing 업무 Table 직접 변경
```

하는 것도 안 됩니다.

즉 경계란 단순 박스가 아니라:

> **“누가 읽고, 누가 쓰고, 누가 변경할 권한을 갖는가”**

까지 포함해야 합니다.

---

# 6. 그래서 Logical Architecture에는 정상패턴과 금지패턴이 같이 있어야 합니다

이 부분이 매우 중요합니다.

아키텍처 문서가:

> “도메인을 분리한다.”

에서 끝나면 실제 개발에서는 거의 지켜지지 않습니다.

따라서 다음과 같이 정의해야 합니다.

### 정상

```text
Domain A
   │
   ▼
Standard Interface
   │
   ▼
Domain B Service
   │
   ▼
Domain B Data
```

### 금지

```text
Domain A
   │
   ├────────▶ Domain B DAO
   │
   ├────────▶ Domain B Mapper
   │
   └────────▶ Domain B Table 직접 갱신
```

이후 제가 설명했던 `MG → MK DAO 직접호출 금지` 같은 애플리케이션 Rule은 바로 이 **상위 Responsibility Boundary가 코드 레벨로 내려간 결과**입니다.

즉 소스 규칙이 먼저가 아닙니다.

```text
Domain Strategy
      ↓
Responsibility Boundary
      ↓
Integration Rule
      ↓
Application Dependency Rule
      ↓
DAO / Mapper 직접호출 금지
```

순서입니다.

---

# 7. 정책 ③ — Data Flow Control

NSIGHT 논리 아키텍처에서 아주 중요한 특징은:

> **데이터가 움직이는 길을 미리 정해놓는다.**

는 것입니다.

전략자료에서는 다음처럼 역할을 분리합니다.

```text
데이터 성격
    │
    ├─ DB 변경
    │      ↓
    │     CDC
    │
    ├─ Event
    │      ↓
    │    Kafka
    │
    ├─ 대량 데이터
    │      ↓
    │     ETL
    │
    └─ 파일
           ↓
          FOS
```

이것이 **데이터 흐름 강제화**입니다.

---

# 8. 왜 “강제화”까지 하는가

개발자가 원하는 방식으로 연결하게 두면 처음에는 편합니다.

하지만 시간이 지나면:

```text
System A ─ DB Link ─▶ System B
System A ─ File ────▶ System C
System A ─ Socket ──▶ System D
System E ─ 직접SQL ─▶ RDW
System F ─ 임의ETL ─▶ ADW
```

같은 구조가 생깁니다.

그러면:

```text
이 데이터는 어디서 왔지?
누가 책임지지?
누가 수정하지?
장애 나면 어디까지 영향이지?
```

를 알 수 없게 됩니다.

그래서 NSIGHT는 데이터 유형별 **승인된 길**을 정합니다.

---

# 9. 특히 CDC / Kafka / ETL은 역할이 다릅니다

이 세 가지를 모두 “데이터 이동 기술”로 취급하면 안 됩니다.

```text
CDC
────────────────
Database Change
        ↓
Near Real-time Data


Kafka
────────────────
Business / Customer Event
        ↓
Event-driven Reaction


ETL
────────────────
Bulk Data
        ↓
Transform / Aggregate / Analytics
```

따라서:

> **CDC = 변화의 길**
> **Kafka = 사건의 길**
> **ETL = 대량 가공의 길**

입니다.

인터페이스 표준자료도 실시간 데이터 동기화는 `CDC`, 배치·대량 데이터는 `ETL`, 이벤트 스트리밍은 `Kafka`로 분리합니다.

---

# 10. 정책 ④ — Integration Control

이것은 NSIGHT Logical Architecture에서 가장 강력한 정책 중 하나입니다.

전략자료의 표현은:

> **NO P2P 강제화**

입니다.

그러나 여기서 `NO P2P`를 “모든 직접통신 금지”라고 지나치게 단순화하면 안 됩니다.

정확한 뜻은:

> **시스템 간 임의의 직접 결합을 허용하지 않고, 연계유형별 표준 경로를 사용한다.**

입니다.

---

# 11. 인터페이스는 3종류로 분류합니다

인터페이스 표준 정의자료는 이를 정확히 세 가지로 구분합니다.

```text
              Interface

       ┌─────────┼─────────┐
       │         │         │
       ▼         ▼         ▼
     Online     Data      File
```

그리고 표준 수단은 다음과 같습니다.

| 유형   | 표준                          |
| ------ | ----------------------------- |
| Online | JSON/HTTP, API Gateway, Kafka |
| Data   | CDC / ETL                     |
| File   | FOS                           |

즉 먼저:

> **“연계가 무슨 종류인가?”**

를 판단하고 그 다음 기술을 선택합니다.

---

# 12. 온라인 시스템 간 연계

대내 시스템 온라인 연계는:

```text
NSIGHT
   │
   ▼
API Gateway
CruzAPIM
   │
   ▼
대내 시스템
```

입니다.

반대 방향도 동일합니다.

```text
대내 시스템
   │
   ▼
CruzAPIM
   │
   ▼
NSIGHT
```

인터페이스 표준자료는 정보계와 대내 시스템의 전사 표준 온라인 인터페이스를 **API G/W(CruzAPIM) 경유**로 정의합니다.

---

# 13. 타 법인은 별도 경계입니다

타 법인과의 연계는:

```text
타 법인
   │
   ▼
  GSE
   │
   ▼
NSIGHT
```

로 정의되어 있습니다.

즉:

```text
내부 시스템
      ≠
타 법인
      ≠
외부기관
```

입니다.

같은 HTTP 요청이라고 같은 연계경계를 사용하는 것이 아닙니다.

---

# 14. 파일은 FOS라는 별도 경로를 사용합니다

```text
Application A
      │
      │ File
      ▼
     FOS
      │
      ▼
Application B
```

인터페이스 표준자료에서는 파일 연계를 **FOS로 일원화**하는 것을 기본원칙으로 둡니다. 대외 연계 시에는 FOS와 대외 MCA/MFT 연계구조가 함께 나타납니다.

이것이 중요한 이유는:

```text
Online Transaction
      ≠
File Transfer
```

이기 때문입니다.

파일을 API로 억지로 보내거나, 온라인 업무를 파일처럼 처리하는 구조를 피합니다.

---

# 15. 중요한 예외 — 정보계 단말과 Package UI

인터페이스 표준 자료를 보면 모든 호출이 반드시 API Gateway를 거치는 것은 아닙니다.

자료상 다음 두 경우는 별도의 인터페이스 시스템 없이 직접 처리하도록 정의되어 있습니다.

### 정보계 단말

```text
정보계 단말
     │
     ▼
   정보계
```

### Package UI

```text
Package UI
     │
     ▼
정보계 Solution
```

따라서 NSIGHT의 원칙을 정확히 표현하면:

> **“모든 직접통신 금지”가 아니라 “정의되지 않은 P2P 금지”**

가 더 정확합니다.

승인된 Architecture Pattern으로 정의된 직접접속은 허용될 수 있습니다.

이런 예외까지 Architecture Rule에 들어가야 나중에 자동검사에서도 오판하지 않습니다.

---

# 16. 정책 ⑤ — Online / Batch / Event / Analysis 분리

이제 Resource Boundary입니다.

NSIGHT는 서비스 특성이 다른 Workload를 같은 공간에 올리지 않습니다.

```text
Online
    ≠
Batch
    ≠
ETL
    ≠
Event
    ≠
Analytics
```

전략 장표에서 직접 정의하는 것은 다음입니다.

- Online AP / Batch AP 분리
- ETL 독립 서버
- CDC 중계 서버
- Event 서버
- IMDG 서버
- RDW / ADW 분리

즉 Logical 단계에서 이미:

> **“같이 쓰지 않는다.”**

를 결정합니다.

Physical 단계에서 실제 서버를 분리하는 것은 그 다음입니다.

---

# 17. RDW와 ADW 분리도 먼저 Logical Policy입니다

처음부터 “Exadata 두 대를 산다”가 아닙니다.

먼저 논리적으로:

```text
RDW
=
Online / Near Real-time


ADW
=
Large Analytics / BI / ETL
```

라고 역할을 분리합니다.

그리고 정책을 선언합니다.

```text
대량 분석 Query
          X
RDW 실시간 처리 Resource
```

그다음 Physical 단계에서:

```text
RDW Exadata
        ≠
ADW Exadata
```

로 실제 자원을 분리합니다.

전략자료 역시 RDW를 실시간 OLTP 운영영역, ADW를 대용량 전략분석 영역으로 정의하고 자원 경합을 차단합니다.

---

# 18. 이것이 FAST / DEEP 분리로 확장됩니다

논리 아키텍처의 최종적인 Runtime 경계가 FAST / DEEP입니다.

### FAST

```text
Customer Action
      ↓
Wise Collector
      ↓
Kafka
      ↓
Behavior Processing
      ↓
Real-time Marketing
      ↓
Offer
```

### DEEP

```text
Source DB
    ↓
   CDC
    ↓
   RDW
    ↓
   ETL
    ↓
   ADW
    ↓
BI / Analytics
```

전략자료에서 두 Runtime 흐름은 별도로 정의되어 있습니다.

논리적 정책은:

> **FAST와 DEEP의 Resource와 Processing Path를 섞지 않는다.**

입니다.

---

# 19. 정책 ⑥ — Standard Contract

영역을 나누고 길을 정했으면 그 길을 통해 어떤 형식으로 통신할지도 정해야 합니다.

온라인 거래 기준:

```text
HTTP
 +
JSON
 +
Standard Message
 +
GUID
```

입니다.

전략자료의 원칙은:

- 거래 통신 HTTP/JSON 표준
- 비표준 전문 차단
- Header + Data 표준
- GUID 기반 관측성 확보

입니다.

따라서:

```text
Application A
      │
      │ 제각각 JSON
      ▼
Application B
```

가 아니라:

```text
Application A
      │
      │ HTTP / JSON
      │ Standard Message
      │ GUID
      ▼
Application B
```

를 지향합니다.

---

# 20. GUID의 의미도 상위 정책에서 봐야 합니다

GUID는 단순 Header Field가 아닙니다.

상위 Logical Architecture에서는:

> **“거래가 여러 경계를 지나도 하나의 거래로 추적 가능해야 한다.”**

는 Observability Policy입니다.

```text
Channel
  │
 GUID
  ▼
Framework
  │
 GUID
  ▼
Service
  │
 GUID
  ▼
Integration
  │
 GUID
  ▼
Target
```

이후 Mechanism 단계에서 이 정책이 실제 표준전문 Header, MDC, Log, Trace 등에 구현됩니다.

즉:

```text
Logical
GUID 기반 Traceability

      ↓

Mechanism
Header / MDC / Logging 구현
```

입니다.

---

# 21. NSIGHT Logical Architecture를 한 장으로 합치면

```text
                      NSIGHT LOGICAL ARCHITECTURE

┌───────────────────────────────────────────────────────────────┐
│                     DOMAIN BOUNDARY                           │
│                                                               │
│ DATA │ MARKETING │ BI │ GOVERNANCE │ IT SERVICE              │
│                                                               │
│         책임과 데이터 소유권 분리                             │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────────┐
│                   INTEGRATION CONTROL                         │
│                                                               │
│ Online    → HTTP/JSON / API G/W                              │
│ Data      → CDC / ETL                                        │
│ Event     → Kafka                                            │
│ File      → FOS                                              │
│ 법인      → GSE                                              │
│                                                               │
│ ★ Undefined P2P / DB Link 통제                              │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────────┐
│                     DATA FLOW CONTROL                         │
│                                                               │
│ DB Change → CDC                                               │
│ Event     → Kafka                                             │
│ Bulk      → ETL                                               │
│ File      → FOS                                               │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────────┐
│                    RESOURCE ISOLATION                         │
│                                                               │
│ Online ≠ Batch                                               │
│ Event  ≠ ETL                                                 │
│ RDW    ≠ ADW                                                 │
│ FAST   ≠ DEEP                                                │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────────┐
│                    STANDARD CONTRACT                          │
│                                                               │
│ HTTP / JSON                                                   │
│ Standard Message                                              │
│ GUID                                                          │
│ Standard Interface                                            │
└───────────────────────────────────────────────────────────────┘
```

이것이 NSIGHT 전략자료를 기준으로 본 **Logical Architecture의 중심 구조**입니다.

---

# 22. 정상패턴과 금지패턴으로 다시 정리하면 더 쉽습니다

| 영역        | 정상 패턴                 | 금지/통제 패턴             |
| ----------- | ------------------------- | -------------------------- |
| Domain      | 책임별 독립 Domain        | 다른 Domain 내부 구현 침범 |
| Online      | HTTP/JSON, 승인된 Gateway | 임의 P2P                   |
| Data Change | CDC                       | 임의 DB Link               |
| Event       | Kafka                     | DB Polling으로 Event 대체  |
| Bulk        | ETL/DataStage             | Online AP에서 대량가공     |
| File        | FOS                       | 서버 간 임의 SCP/공유경로  |
| RDW         | Online/Near Real-time     | 무제한 대량 분석           |
| ADW         | BI/OLAP/Analytics         | 온라인 Transaction 처리    |
| Runtime     | FAST/DEEP 분리            | 동일 자원에서 혼합처리     |
| Message     | Standard Header/Data      | 업무별 제각각 전문         |
| Trace       | GUID                      | 추적불가능한 호출          |

다만 `DB Polling으로 Event 대체`, `임의 SCP` 같은 일부 표현은 전략 원칙을 실제 금지패턴 형태로 **제가 구조화한 것**입니다. 원본 장표에 동일 문구가 그대로 있는 것은 아닙니다.

반면 `No P2P`, DB Link 통제, HTTP/JSON, CDC, Kafka, ETL, FOS, RDW/ADW 분리는 자료에 직접 정의되어 있습니다.

---

# 23. 이 Logical Architecture가 Physical로 내려가면

이제 정책이 실제 서버로 변환됩니다.

예를 들어 Logical에서:

```text
Online ≠ Batch
```

라고 했으면 Physical에서는:

```text
Online AP Server
        ≠
Batch AP Server
```

가 됩니다.

Logical:

```text
RDW ≠ ADW
```

Physical:

```text
RDW Exadata
      ≠
ADW Exadata
```

Logical:

```text
Event는 Kafka
```

Physical:

```text
Kafka Event Server
독립 구성
```

Logical:

```text
ETL 독립
```

Physical:

```text
DataStage Baremetal
```

이런 식입니다.

전략자료는 실제로 Online/Batch AP, ETL, CDC 중계, Event, IMDG, RDW/ADW를 독립 기능서버로 분리하도록 정의합니다.

---

# 24. 그다음 Mechanism에서 비로소 TCF 같은 것이 나옵니다

이제 앞서 제가 너무 일찍 설명했던 TCF의 정확한 위치를 알 수 있습니다.

```text
Logical Policy

Online은 표준 거래
Domain Boundary 준수
표준 Message
Traceability
Timeout / Transaction 통제

          ↓

Mechanism

NH Cloud Framework
Standard Message
TCF
ServiceId
Dispatcher
Timeout
Transaction
Logging
```

즉 TCF가 아키텍처 전략을 만드는 것이 아닙니다.

> **Logical Architecture에서 정한 정책을 Application Runtime에서 강제하기 위한 하나의 Mechanism이 TCF입니다.**

수행방법론도 Mechanism을 “Logical Policy와 Physical Structure가 실제로 동일하게 동작하도록 만드는 표준 실행규칙”으로 정의합니다.

---

# 25. 현재 Logical Architecture의 완성도를 보면

전체 방향은 상당히 명확합니다.

현재 통합 Architecture Gate에서도 `Big Picture/Logical`은 **CONDITIONAL PASS**로 평가되어 있습니다. 핵심 전략은 정립되어 있지만 Domain/Data/Contract 전수 Catalog가 아직 필요하다는 의미입니다.

특히 상세화가 필요한 것은 다음입니다.

| 추가 정의 필요                   | 이유                                   |
| -------------------------------- | -------------------------------------- |
| Domain Responsibility Matrix     | 실제 소유 기능 확정                    |
| Domain별 Data Owner              | Table/View 소유권                      |
| Read/Write Matrix                | 어떤 Domain이 무엇을 읽고 쓰는지       |
| Interface Registry               | 모든 연계 전수 목록                    |
| FAST/DEEP Service Classification | 실제 Service별 경로 지정               |
| Direct Access Exception Catalog  | 단말/Package UI 등 예외관리            |
| Prohibited Pattern Catalog       | 개발자가 무엇을 하면 안 되는지 명시    |
| Conformance Rule                 | 소스/설정 자동검증                     |
| Runtime Evidence                 | 정책이 실제 운영에서도 지켜지는지 확인 |

즉 전략은 이미 상당히 강합니다.

이제 남은 핵심은:

> **전략문서에 적힌 정책을 “각 시스템·업무·인터페이스·데이터 단위의 실행 가능한 Rule”로 전개하는 것**

입니다.

---

## 한 문장으로 정리하면

NSIGHT Logical Architecture는:

> **“5대 서비스 도메인의 책임과 데이터 소유권을 분리하고, 온라인·데이터·파일·이벤트별 표준 연계경로를 강제하며, RDW/ADW·FAST/DEEP·Online/Batch의 자원을 격리하고, HTTP/JSON·표준전문·GUID를 공통 계약으로 사용하여 플랫폼 독립성·장애격리·확장성을 확보하는 정책 아키텍처”**

입니다.

그리고 이제 다음 단계는 자연스럽게 **Physical Architecture**입니다. 여기에서는 방금 정의한 Logical 정책이 실제로 **Exadata / NH Cloud IaaS / Baremetal / UNIX / WEB / WAS / AP / ETL / CDC / Kafka / Main / DR**에 어떻게 배치되는지를 전략자료와 서버 인벤토리를 연결해 설명해야 합니다.
