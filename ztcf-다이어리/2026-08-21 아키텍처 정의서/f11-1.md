좋습니다. 앞의 **Physical Architecture**에서 바로 이어서 이번에는 전략 브리핑의 **7장, NSIGHT HA/DR Architecture**로 진행하겠습니다.

이번 장에서는 서버를 “두 대씩 둔다”는 수준이 아니라, **어디까지는 자동 우회하고, 언제 센터를 전환하며, 세션과 데이터는 어떻게 다루고, 정상화 후 어떻게 Fail-Back 하는가**를 하나의 서비스 연속성 구조로 보겠습니다. 현재 HA/DR 기준문서도 이를 `탐지 → 격리 → 우회 → 복구 → Failback → 증적`까지 포함한 아키텍처로 정의합니다.

# 1. 먼저 HA와 DR은 완전히 다른 문제입니다

둘을 섞으면 안 됩니다.

```text
HA
=
"의왕 운영센터 안에서
서버/JVM 하나가 죽었을 때 계속 서비스하는 것"


DR
=
"의왕 센터 자체를 사용할 수 없을 때
안성 DR센터에서 업무를 계속하는 것"
```

구조적으로는 다음과 같습니다.

```text
                       GSLB
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼

        의왕 MAIN                  안성 DR
        ─────────                  ───────

           L4                        L4
            │                         │
      ┌─────┴─────┐             ┌────┴────┐
      ▼           ▼             ▼         ▼
    WEB01       WEB02          WEB51     WEB52
      │  \       / │             │         │
      │   \     /  │             ▼         ▼
      ▼    ▼   ▼   ▼           WAS51     WAS52
    WAS01       WAS02

        ↑
     센터 내 HA


의왕 전체 사용 불가
        │
        ▼
      GSLB
        │
        ▼
      안성 DR

        ↑
    센터 간 DR
```

전략 브리핑의 Availability 목표도 **주요 시스템 이중화 + DR센터 AP 레벨 Active-Active + 기능별 장애격리 + RTO 30분 이내**를 기본 방향으로 제시합니다.

---

# 2. NSIGHT가 선택한 DR의 핵심은 AP Active-Active + DB Active-Standby입니다

이것이 이번 DR 전략의 핵심 결정입니다.

```text
                       GSLB
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼

         MAIN Center              DR Center

          AP ACTIVE               AP ACTIVE
              │                       │
              │                       │
              ▼                       ▼
          DB ACTIVE  ─────────→   DB STANDBY
                       복제
```

즉 애플리케이션 계층은 두 센터 모두 서비스 가능한 상태로 준비하지만, **데이터베이스는 양쪽 센터에서 동시에 Write하지 않습니다.**

전략자료는 센터 간 DB Active-Active를 명시적으로 미채택하고, AP Active-Active + DB Active-Standby 방식을 금융거래 안정성을 고려한 현실적 최적안으로 제시합니다. 그 이유로 동시쓰기 충돌, 네트워크 지연에 따른 데이터 불일치, 복구·운영 복잡도 증가를 들고 있습니다.

이것을 아주 쉽게 표현하면:

> **애플리케이션은 양쪽 센터가 준비하고, 데이터의 최종 Write 권한은 한쪽만 가진다.**

입니다.

---

# 3. 왜 DB Active-Active를 사용하지 않는가

이론적으로는 이런 구조가 가장 좋아 보입니다.

```text
MAIN DB ACTIVE
      ↕
DR DB ACTIVE

양쪽에서 동시에 Write
```

그러면 센터 하나가 죽어도 다른 센터가 바로 처리하므로 RTO가 거의 0처럼 보입니다.

하지만 금융 거래에서는 다른 문제가 생깁니다.

```text
MAIN
계좌/고객 데이터 Update
       │
       │ 거의 동시에
       ▼
DR
같은 데이터 Update
```

이때 필요한 것은 단순 서버 가용성이 아니라:

```text
어느 거래가 먼저인가?
양쪽 값이 다르면 무엇이 정본인가?
네트워크가 잠시 끊겼다면?
Split-Brain이면?
중복거래는?
Rollback은?
```

입니다.

그래서 NSIGHT 전략은:

```text
Infrastructure Idealism
        ↓
DB Active-Active

          X

Financial Transaction Stability
        ↓
DB Active-Standby
```

를 선택합니다.

전략 문서가 표현하는 핵심도 **“이론적인 완벽함보다 실제 운영 가능한 현실적인 강건함”**입니다.

---

# 4. 중요한 점: AP Active-Active가 반드시 트래픽 50:50을 뜻하지는 않습니다

여기에서 흔히 오해합니다.

```text
AP Active-Active
=
반드시 MAIN 50%
DR 50%
```

가 아닙니다.

정확한 뜻은:

> **두 센터의 AP가 서비스할 준비가 되어 있고, 필요하면 트래픽을 받을 수 있는 상태**

입니다.

예를 들어 실제 운용정책은:

```text
정상

MAIN 100
DR     0
```

일 수도 있고,

```text
MAIN 80
DR    20
```

일 수도 있습니다.

전략 브리핑에서도 타 금융사 사례를 언급하면서 AP Active-Active 구조를 갖췄더라도 실제 운영 트래픽은 `100:0` 방식이 사용될 수 있음을 설명합니다.

따라서 최종적으로 별도로 결정해야 할 것은:

```text
Architecture Mode
AP Active-Active

        ≠

Traffic Policy
100:0 / 80:20 / 50:50
```

입니다.

---

# 5. 센터 내부 HA는 더 작은 장애를 처리합니다

센터가 살아있는데 Tomcat 하나가 죽었다고 DR로 넘겨서는 안 됩니다.

센터 내부에서 해결해야 합니다.

현재 HA Working Architecture는 다음처럼 잡혀 있습니다.

```text
                   L4
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       WEB01                WEB02
      Apache               Apache
          │ \                 / │
          │  \               /  │
          ▼   ▼             ▼   ▼
        WAS01               WAS02

     ┌───────────┐       ┌───────────┐
     │ JVM App A │       │ JVM App A │
     │ JVM App B │       │ JVM App B │
     └───────────┘       └───────────┘
```

핵심은:

```text
WEB01 → WAS01만
WEB02 → WAS02만
```

이라는 고정 구조보다는, 장애 발생 시 Peer WAS/JVM으로 우회 가능한 구조를 가져야 한다는 것입니다.

다만 **실제 `httpd.conf`, L4 Pool, Health Check 설정은 아직 Runtime Evidence가 필요한 상태**입니다. 이것은 확정 Fact가 아니라 Working Architecture입니다.

---

# 6. NSIGHT는 장애를 계층별로 처리해야 합니다

장애를 모두 같은 Failover로 처리하면 안 됩니다.

| 장애                  | 정상적인 대응 수준     |
| --------------------- | ---------------------- |
| Apache Process 장애   | Peer WEB으로 우회      |
| WEB VM 장애           | Peer WEB               |
| Tomcat JVM 장애       | Peer JVM               |
| WAS VM 장애           | Peer WAS               |
| 특정 Application 장애 | 동일 Application Peer  |
| Thread 고갈           | 해당 JVM 격리·원인해소 |
| Hikari Pool 고갈      | SQL/DB/Pool 조치       |
| DB Node 장애          | RAC/DB HA              |
| 외부 시스템 장애      | Timeout/CB/Fail-fast   |
| **센터 장애**         | **GSLB → DR센터**      |

이 Failure Domain 분류가 현재 HA/DR Architecture에도 직접 정의되어 있습니다.

즉 아키텍처의 중요한 원칙은:

> **작은 장애를 큰 장애로 확대하지 않는다.**

입니다.

```text
JVM 장애
  ↓
JVM에서 해결

WAS 장애
  ↓
WAS HA에서 해결

DB Node 장애
  ↓
DB HA에서 해결

센터 장애
  ↓
DR
```

이것이 **Fault Isolation**입니다.

---

# 7. Session HA가 생각보다 중요한 문제입니다

AP와 DB만 살아난다고 서비스가 완전히 이어지는 것은 아닙니다.

사용자가 로그인해 있다면 세션이 있습니다.

현재 용량·세션 자료에서 가장 많이 확인되는 구조는:

```text
GSLB
  ↓
센터 L4
  ↓
Sticky Session
  ↓
Tomcat JVM #1
     ↕
DeltaManager
     ↕
Tomcat JVM #2
```

입니다.

그리고 중요한 정책은:

```text
센터 내부 세션 복제     O
센터 간 세션 복제       기본 X
```

입니다. 세션자료는 DeltaManager를 **센터 내부**에 적용하고 센터 간 복제를 기본 미적용으로 정의하고 있습니다.

---

# 8. 그러면 센터 전체 장애 때 세션은 어떻게 되는가

이게 아직 **결정이 필요한 중요한 Architecture Decision**입니다.

현재 구조가:

```text
의왕
Tomcat A ↔ Tomcat B
DeltaManager
```

이고 안성까지 세션을 복제하지 않는다면:

```text
의왕 전체 장애
     ↓
안성으로 전환
     ↓
기존 의왕 Session 없음
```

이 됩니다.

따라서 선택지는 크게 다음과 같습니다.

```text
A. DR 전환 시 재로그인 허용

B. Spring Session JDBC / 외부 Store 사용

C. 별도의 센터 간 Session Replication 도입
```

현재 프로젝트에서는 **DeltaManager vs Spring Session JDBC 등 Session Strategy 자체가 아직 P0 ADR**입니다. 센터장애 시 재로그인 허용 여부도 미결정 상태입니다.

따라서 이 부분을 이미 확정된 아키텍처처럼 설명하면 안 됩니다.

현재 상태는:

```text
센터 내부
DeltaManager + Sticky
= Working Candidate

센터간 Session Continuity
= OPEN / ADR
```

입니다.

---

# 9. 세션에는 고객 데이터를 넣으면 안 됩니다

DR과 HA 때문에 더욱 중요합니다.

현재 세션 기준은 세션 객체를 작게 유지하도록 되어 있습니다.

```text
Session OK

userId
branchId
role
authLevel
maskingLevel
```

반면:

```text
Session 금지

고객조회 결과
SingleView 전체 결과
거래 목록
대형 DTO
```

입니다.

세션 크기의 Working 기준도 **목표 2KB 이하, 최대 5KB 이하**로 제시되어 있습니다. 이유는 DeltaManager 복제부하와 메모리 사용량을 줄이기 위해서입니다.

즉 HA 관점에서 Session은:

> **“업무 데이터를 저장하는 공간”이 아니라 “사용자 상태를 최소한으로 유지하는 공간”**

이어야 합니다.

---

# 10. 이제 실제 센터 장애 시나리오를 보겠습니다

정상 상태를 먼저 보면:

```text
                정상 운영

Client
   │
   ▼
 GSLB
   │
   ▼
 의왕
   │
   ▼
  L4
   │
 WEB / WAS
   │
   ▼
 RDW ACTIVE

                    안성
                     │
                 AP Ready
                     │
                 RDW Standby
```

이제 의왕 전체에 장애가 발생합니다.

```text
              의왕 CENTER DOWN
                       X

Client
   │
   ▼
 GSLB
   │
   └──────────────────────┐
                          ▼
                        안성
                          │
                          ▼
                         L4

                          ▼
                      WEB / WAS
                          │

                  RDW Standby 승격
                          │
                          ▼
                      DB ACTIVE
```

이때 중요한 것은 단순 DNS 전환 하나가 아닙니다.

# 11. Failover는 하나의 통제된 절차입니다

현재 HA/DR 문서에서 정의한 기본 흐름은 다음입니다.

```text
Detect
장애 감지
   ↓
Impact Scope
영향도 판단
   ↓
Isolation
장애 Node/Center 격리
   ↓
Traffic Reroute
GSLB/L4 우회
   ↓
Session / Data Consistency
세션·데이터 상태 확인
   ↓
Residual Capacity
잔여 용량 확인
   ↓
Business Validation
업무 정상 확인
   ↓
Service Restore
서비스 복구 선언
```

그리고 여기에서 끝나는 것이 아닙니다.

```text
원인 복구
   ↓
Failback Plan
   ↓
Controlled Failback
   ↓
Post Validation
   ↓
Evidence 저장
```

까지 해야 합니다.

즉:

> **Failover보다 Failback이 더 위험할 수도 있습니다.**

장애센터가 살아났다고 즉시 원복하면 데이터 정합성이나 세션, Routing 문제가 발생할 수 있기 때문입니다.

---

# 12. Failback은 “다시 MAIN으로 돌리는 작업”이 아닙니다

정확하게는:

```text
DR 운영 중
   ↓
MAIN 복구
   ↓
DB 상태 확인
   ↓
Replication 재구성
   ↓
Data Consistency 검증
   ↓
AP 기동
   ↓
Health Check
   ↓
Traffic 일부 전환
   ↓
업무 검증
   ↓
Traffic 정상화
   ↓
DR Standby 재설정
```

과 같은 통제된 과정이 필요합니다.

따라서 최종 아키텍처 산출물에는 반드시:

```text
Failover Runbook
+
Failback Runbook
```

두 개가 있어야 합니다.

현재 프로젝트에서도 Failback Runbook과 데이터 정합성 절차가 미완료 GAP으로 관리되고 있습니다.

---

# 13. RTO는 전략이 있지만 RPO는 아직 닫히지 않았습니다

현재 전략자료에서는 Availability 목표로:

> **RTO 30분 이내**

를 제시합니다.

하지만 이를 모든 시스템의 확정 RTO라고 보면 안 됩니다.

현재 상태를 정확하게 표현하면:

| 시스템      | RTO                   | RPO                  | 현재 상태 |
| ----------- | --------------------- | -------------------- | --------- |
| Online AP   | 전략상 30분 이내 기준 | 미확정               | OPEN      |
| RDW         | 상세확정 필요         | 상세확정 필요        | OPEN      |
| ADW         | 상세확정 필요         | 상세확정 필요        | OPEN      |
| Batch / ETL | 상세확정 필요         | 상세확정 필요        | OPEN      |
| 운영관리    | 상세확정 필요         | 정책데이터 기준 필요 | OPEN      |

현재 HA/DR Baseline도 RPO는 시스템별 근거가 부족해 `UNKNOWN`으로 유지합니다.

이것은 매우 중요한 점입니다.

```text
"RTO 30분"
```

하나만 있다고 DR 설계가 완료된 것이 아닙니다.

---

# 14. RTO와 RPO는 역할이 다릅니다

쉽게 말하면:

```text
RTO
=
"얼마나 빨리 다시 서비스할 것인가?"


RPO
=
"얼마나 많은 데이터를 잃어도 되는가?"
```

예:

```text
장애 발생 10:00

서비스 재개 10:20
→ RTO = 20분


복구된 데이터가 09:59:50까지
→ RPO = 10초
```

금융권에서는 특히 RDW와 업무데이터에 대해 이 값이 매우 중요합니다.

따라서 최종 DR 설계서는:

```text
System
→ Service
→ Data
→ RTO
→ RPO
→ Replication
→ Failover Method
→ Validation Method
```

까지 내려가야 합니다.

---

# 15. DR 용량도 반드시 검증해야 합니다

DR센터에 서버가 있다고 충분한 것이 아닙니다.

센터 하나가 없어졌을 때 남은 서버가 전체 부하를 받아야 합니다.

현재 Working Capacity 문서에는 16Core 기준으로:

```text
산정 Capacity       = 855 TPS/VM
운영 80% Capacity   = 684 TPS/VM
```

라는 Working 값이 있습니다.

그 값을 예로 사용하면 DR에서 VM 2대가 남을 경우:

```text
684 × 2
=
1,368 TPS
```

가 됩니다.

현재 설계 피크 `1,200 TPS`는 산술상 수용 가능합니다. 그러나:

```text
센터 장애
+
남은 센터의 VM 1대 추가 장애
```

까지는 여유가 없습니다. 이 점이 현재 HA/DR 문서에 명확히 지적되어 있습니다.

단, **855 TPS는 아직 Runtime Approved 값이 아니라 Working Capacity**이므로 운영 확정치로 사용하면 안 됩니다.

---

# 16. 그래서 2+2냐 3+3이냐가 단순 서버 숫자 문제가 아닙니다

예를 들어:

```text
2 + 2

MAIN 2 VM
DR   2 VM
```

은 자원 효율은 좋습니다.

하지만 Main 장애 후에는:

```text
DR 2 VM
```

만 남습니다.

여기서 하나 더 장애가 발생하면:

```text
DR 1 VM
```

이 됩니다.

반면:

```text
3 + 3
```

이라면 센터 장애 후에도:

```text
3 VM
```

이 남고 N-1 이후에도:

```text
2 VM
```

이 남습니다.

따라서 현재 프로젝트의 `ADR-HA-001`은 **2+2 / 3+3 / 8Core Scale-Out** 중 어느 구조가 맞는지를 P0 의사결정으로 남겨두고 있습니다.

---

# 17. 왜 8Core Scale-Out 전략이 HA와 연결되는가

앞에서 Physical Architecture에서 보았던 8Core VM 전략도 사실 DR과 직접 관련됩니다.

같은 총 64Core라도:

```text
16Core × 4
```

보다

```text
8Core × 8
```

은 장애 단위가 작습니다.

한 노드가 죽을 때:

```text
16Core × 4
→ 전체 자원의 25% 장애


8Core × 8
→ 전체 자원의 12.5% 장애
```

이므로:

```text
Scale-Out
    ↓
Failure Unit 축소
    ↓
HA 안정성 향상
    ↓
Rolling 배포 용이
    ↓
DR 잔여용량 조절 용이
```

라는 효과가 있습니다.

NSIGHT 온라인 AP 전략자료 역시 단순 TPS보다 **장애 영향도, RDW 보호, GC 안정성, 배포·복구 유연성**을 이유로 작은 VM 단위의 Scale-Out을 선호합니다.

# 19. 현재 무엇이 확정이고 무엇이 아직 미결정인가

이 구분이 중요합니다.

| 영역                              | 현재 판단                    |
| --------------------------------- | ---------------------------- |
| 센터 내 WEB/WAS 이중화            | **Working Baseline 성립**    |
| AP 레벨 센터간 Active-Active 전략 | **전략 확정 방향**           |
| DB 센터간 Active-Standby          | **전략 확정 방향**           |
| DB Active-Active 미채택           | **전략 명시**                |
| RTO 30분 이내                     | **전략 목표**                |
| 센터 내부 DeltaManager            | **Working Candidate**        |
| 센터간 Session 복제               | **기본 미적용 Working 기준** |
| 센터 장애 시 재로그인 여부        | **OPEN**                     |
| Spring Session JDBC 적용 여부     | **OPEN**                     |
| 서비스별 RPO                      | **OPEN**                     |
| 2+2 / 3+3 / 8Core                 | **OPEN ADR**                 |
| 전체 PROD↔DR Pair                 | **부분완료**                 |
| 실제 GSLB/L4/httpd 설정           | **Evidence 필요**            |
| Center Failure 실측시험           | **미완료**                   |
| Failback Runbook                  | **미완료**                   |

따라서 현재 HA/DR Architecture의 Gate 판정은 **CONDITIONAL PASS**입니다. 전수 Pair Catalog, RTO/RPO 승인, Session ADR, Center Failure/N-1 Test, 실제 Routing 설정, Failover/Failback Evidence가 있어야 최종 PASS가 가능합니다.

# 20. 이 장에서 가장 중요한 메시지

NSIGHT의 DR 전략을 한 문장으로 압축하면:

> **“센터 간 모든 것을 동시에 Active로 만들어 이론적 무중단을 추구하기보다, AP는 양 센터에서 서비스 가능한 상태로 준비하고 DB Write는 단일 Active로 통제하며, 센터 내부에서는 작은 장애를 HA로 격리하고 센터 전체 장애일 때만 GSLB 기반 DR 전환을 수행하는 현실적 금융권 Resilience Architecture”**

입니다.

그리고 이것은 앞서 이야기한 NSIGHT의 세 단어 가운데 정확히 **Resilient**를 구현하는 구조입니다.

```text
Scalable
   → Scale-Out

Resilient
   → HA + DR + Fault Isolation

Data-Centric
   → RDW / ADW + Data Consistency
```

## 이제 다음 단계

이제 6단계 방법론을 다시 놓으면:

```text
Vision                 ✓
   ↓
Big Picture            ✓
   ↓
Logical Architecture   ✓
   ↓
Physical Architecture  ✓
   ↓
HA / DR                ✓ 상세화
   ↓
★ Mechanism Architecture
   ↓
Runtime Architecture
```

다음은 **Mechanism Architecture**로 넘어가는 것이 맞습니다.

여기서는 이제 처음으로 `TCF`가 제대로 등장합니다. 다만 TCF부터 시작하는 것이 아니라 먼저 **NSIGHT 전체 5대 실행 메커니즘 — ① 규격/표준, ② 거래처리 Framework, ③ 데이터 흐름(CDC/Kafka/ETL), ④ Integration 통제(CruzAPIM/FOS), ⑤ 운영 공통(SSO/Session/Control-M/Logging)**을 설명하고, 그 안에서 TCF·ServiceId·표준전문·Transaction·Timeout이 어디에 위치하는지를 연결하겠습니다. 전략자료도 Mechanism을 Logical/Physical을 실제 동작시키는 실행규칙으로 정의하고 있습니다.
