좋습니다. 이제 **16번째 설명 — NSIGHT Architecture Review & Gate 운영체계**로 진행하겠습니다.

15번까지는 “어떤 규칙을 지켜야 하는가”를 만들었습니다. 16번에서는 그 Rulebook을 실제 프로젝트 통제에 사용하는 방법, 즉 **설계안이 들어오면 누가 무엇을 검사하고, 어떤 근거로 PASS/HOLD하고, GAP과 ADR을 어떻게 처리하며, 최종적으로 무엇을 Architecture Baseline으로 승인하는가**를 설명하겠습니다.

현재 NSIGHT 연속성 기준도 Gate 완료를 “문서가 작성되었다”로 판단하지 않습니다. `요구사항 ↔ 설계 ↔ 코드 ↔ 설정 ↔ DB ↔ 테스트 ↔ 배포 ↔ 운영 증적`이 서로 일치해야 하며 Gate 상태는 `PASS / CONDITIONAL PASS / HOLD / REJECT`로 관리하도록 정의합니다.

# 16. NSIGHT Architecture Review & Gate

## 16.1 Architecture Review의 목적부터 바꿔야 합니다

일반적인 Architecture Review는 흔히 이런 형태입니다.

```text
설계서 제출
   ↓
아키텍트 검토
   ↓
회의
   ↓
"큰 문제 없어 보임"
   ↓
승인
```

NSIGHT가 지향하는 것은 이것과 다릅니다.

```text
설계안
   ↓
Architecture Baseline 확인
   ↓
Model 비교
   ↓
Rule 자동검사
   ↓
Source / Config 검증
   ↓
Runtime Evidence
   ↓
Drift / GAP
   ↓
ADR / Exception
   ↓
Human Approval
   ↓
Gate
```

즉 Architecture Review는 **사람의 경험만으로 설계도를 심사하는 행위가 아니라, 예상 아키텍처와 실제 구현을 Evidence로 비교하는 통제 프로세스**입니다.

후속 프로젝트의 발전 방향 역시 `Architecture as Document → Model → Code → Test → Runtime Evidence`로 명확하게 잡혀 있습니다.

---

# 16.2 전체 Architecture Gate 체계

현재 NSIGHT Gate는 다음 흐름으로 구성되어 있습니다.

```text
G00
Source Baseline
   │
   ▼
G10
Vision / NFR
   │
   ▼
G20
Big Picture / Logical
   │
   ▼
G30
Physical
   │
   ▼
G40
Mechanism / Source Conformance
   │
   ▼
G50
Security / Data / Integration
   │
   ▼
G60
Capacity / Runtime
   │
   ▼
G70
Operations / HA-DR / Deployment
   │
   ▼
G80
Closed Loop / Drift
   │
   ▼
HG90
Final Human Gate
   │
   ▼
Approved Architecture Baseline
```

현재 Gate 문서에서 이 체계가 실제 운영 기준으로 사용되고 있으며, G10만 PASS이고 G00·G20~G70은 대부분 `CONDITIONAL PASS`, G80과 HG90은 아직 HOLD 상태입니다.

---

# 16.3 각 Gate가 무엇을 질문하는가

| Gate                              | 핵심 질문                                              |
| --------------------------------- | ------------------------------------------------------ |
| **G00 Source Baseline**           | 우리가 무엇을 기준 Source라고 보는가                   |
| **G10 Vision/NFR**                | 이 설계가 NSIGHT 전략·NFR에 맞는가                     |
| **G20 Logical**                   | 책임·Domain·Data·Interface 경계가 맞는가               |
| **G30 Physical**                  | 실제 서버·JVM·DB·HA 구조가 정책과 일치하는가           |
| **G40 Mechanism**                 | Framework·TCF·TX·Timeout 등이 실제 코드에서 지켜지는가 |
| **G50 Security/Data/Integration** | 인증·데이터 소유·연계 계약이 안전하고 일관적인가       |
| **G60 Capacity/Runtime**          | TPS·Thread·Pool·Timeout이 실제 부하에서 성립하는가     |
| **G70 Operations/HA-DR**          | 장애·배포·운영·DR에서 실제 서비스 가능한가             |
| **G80 Closed Loop**               | Document/Model/Code/Runtime 차이가 모두 통제되는가     |
| **HG90 Human Gate**               | 이것을 공식 Architecture Baseline으로 승격할 것인가    |

즉 뒤로 갈수록 단순한 “설계 검토”에서 **실제 운영 가능성 검증**으로 바뀝니다.

---

# 16.4 G00 — 먼저 Source를 고정해야 합니다

Architecture Review를 하기 전에 가장 먼저 해야 하는 것은:

> **“무엇을 사실로 볼 것인가?”**

입니다.

예를 들어 같은 Timeout 정책에 대해:

```text
과거 설계서       5초
현재 Source       4초
application.yml   3초
운영환경           ?
```

라면 바로 5초를 표준이라고 할 수 없습니다.

그래서 G00에서:

```text
Source Repository
Branch
Commit
Configuration
Document Version
Environment
Artifact
```

을 기준화합니다.

현재 G00도 Source Scope와 Canonical 기준은 잡혀 있지만 일부 Branch/Commit과 운영 Config는 아직 `UNKNOWN`으로 관리되어 `CONDITIONAL PASS`입니다.

이 단계가 없으면 이후 Review 결과 자체가 재현되지 않습니다.

---

# 16.5 G10 — “좋은 설계인가”보다 먼저 “NSIGHT 설계인가”

G10은 전략 Gate입니다.

예를 들어 새 설계가 기술적으로 매우 좋아 보여도:

```text
하나의 거대한 DB
Online + Analytics 통합
P2P 자유연계
```

라면 NSIGHT의:

```text
Data-Centric
Scalable
Resilient

RDW / ADW 분리
FAST / DEEP 분리
Boundary Control
```

과 충돌합니다.

따라서 G10은 기술 제품의 우열보다:

```text
Vision
5대 NFR
FAST / DEEP
Domain / Isolation
```

에 대한 정합성을 먼저 봅니다.

현재 G10은 NSIGHT Gate 중 **PASS**로 평가되어 있습니다. Vision, 5대 NFR, FAST/DEEP 원칙 자체는 기준화되었다는 의미입니다.

---

# 16.6 G20 — 설계안을 Domain과 Contract로 검사합니다

예를 들어 개발팀이 다음 설계를 제출했다고 하겠습니다.

```text
MG Service
   ↓
MK DAO
   ↓
MK Table
```

기능은 동작할 수 있습니다.

하지만 G20에서는:

```text
Domain Boundary 위반
Data Ownership 위반
Integration Contract 부재
```

를 먼저 봅니다.

현재 G20의 P0 조건에도:

- 전체 Domain Catalog/Owner
- Domain별 Owned Table/View
- Public ServiceId/Integration Contract Registry
- ServiceId Deadline/Timeout Metadata

등이 들어가 있습니다.

즉 Architecture Review에서 “호출이 되는가?”보다 먼저:

> **“이 호출을 할 권리가 있는 Domain인가?”**

를 묻습니다.

---

# 16.7 G30 — 그림과 실제 서버를 일치시킵니다

G30에서는:

```text
마케팅 WAS #01
마케팅 WAS #02
```

가 있다고 끝나지 않습니다.

실제로는:

```text
Server
 ↓
Tomcat JVM
 ↓
Connector Port
 ↓
Application / WAR
 ↓
Apache Route
 ↓
HA Peer JVM
 ↓
DB
```

까지 연결되어야 합니다.

현재 G30에서 이미 71대 Physical Server Baseline, Apache/Tomcat 구분, `Container = Tomcat JVM Instance`, 운영/DR 대표 Pair 등의 모델은 정립되었습니다. 하지만 **71대 Server↔JVM↔Application/WAR 전수 매핑, 실제 Apache Routing Config, server.xml/setenv.sh, HA Peer Catalog, RTO/RPO**가 아직 P0 조건으로 남아 있습니다.

따라서:

```text
"서버가 두 대 있습니다"
```

는 Evidence가 아닙니다.

```text
"이 ServiceId의 WAR가
어느 JVM에서 실행되고,
그 JVM의 Peer가 무엇이며,
Apache가 실제로 어떻게 Route한다"
```

까지 내려가야 합니다.

---

# 16.8 G40 — 여기서 Rulebook이 실제 Source와 만납니다

G40은 **Mechanism / Source Conformance Gate**입니다.

예를 들어 Rulebook에는:

```text
Facade = Transaction Owner
```

라고 되어 있다고 합시다.

실제 Source Scan을 수행하면:

```text
Facade @Transactional    53개
Service @Transactional    4개
```

처럼 예외가 발견될 수 있습니다.

현재 G40 실제 Source Scan에서도 Transaction Owner 예외, Timeout Late Commit, DB Query Timeout, Worker RequestAttributes, Standard Message Contract 등의 P0 GAP이 식별되었습니다.

여기서 중요한 점은:

```text
Source에 존재한다
       ≠
올바른 Architecture다
```

입니다.

---

# 16.9 Conformance 결과는 무조건 PASS/FAIL 두 가지가 아닙니다

Reference Architecture와 실제 Target을 비교할 때 현재 Orchestration 설계는 다음 네 가지 판정을 사용합니다.

```text
REFERENCE EXPECTED
        ↕
TARGET ACTUAL
        ↓

MATCH
ALLOWED_VARIANT
GAP
EXCEPTION
```

예를 들어:

```text
일반 Online
Handler → Facade → Service → DAO
```

가 표준이라고 하더라도 특정 특수 Batch는 다른 구조가 필요할 수 있습니다.

그 경우 무조건 FAIL하는 것이 아니라:

```text
ALLOWED_VARIANT?
        ↓
Architecture 근거 존재?
        ↓
등록/승인
```

으로 처리합니다.

이 점이 중요합니다. **표준화와 획일화는 다릅니다.**

---

# 16.10 P0/P1/P2를 Gate에서 어떻게 처리하는가

여기에는 중요한 운영 원칙이 있습니다.

| Priority | 의미                          | Gate 처리              |
| -------- | ----------------------------- | ---------------------- |
| **P0**   | Architecture/보안/정합성 핵심 | 최종 HG90 Hard Block   |
| **P1**   | 중요 계약·운영 규칙           | GAP/ADR 또는 보완 필수 |
| **P2**   | 운영품질·튜닝·개선            | Warning/개선관리 가능  |

특히 중간 Gate에서는 P0가 남아 있어도 **후속조치가 명확하면 `CONDITIONAL PASS`**가 가능할 수 있습니다.

예를 들어 현재 G60도 P0 조건을 여러 개 가지고 있지만 `CONDITIONAL PASS`입니다.

하지만 **HG90은 다릅니다.**

```text
P0 FAIL_TARGET = 0

P0 OPEN_RUNTIME = 0
또는 공식 승인된 Exception
```

이 되어야 최종 승인 가능합니다.

즉:

> **CONDITIONAL PASS를 계속 쌓아서 Production Ready라고 선언하는 구조가 아닙니다.**

---

# 16.11 GAP이 발견되면 바로 수정하는 것도 아닙니다

예를 들어 Source에서:

```text
Service @Transactional
```

이 발견됐는데 표준은:

```text
Facade = TX Owner
```

라고 합시다.

그러면 바로 코드를 지우지 않습니다.

```text
Expected
Facade TX

        ≠

Actual
Service TX
```

먼저:

```text
단순 Code Defect인가?
업무 특수성인가?
Reference 자체가 잘못됐나?
표준 예외가 필요한가?
중요 Architecture Decision인가?
```

를 판단합니다.

그 결과가:

```text
GAP
ADR
EXCEPTION
```

중 하나가 됩니다.

---

# 16.12 중요한 선택은 ADR로 넘깁니다

NSIGHT에서 사람이 결정해야 하는 대표 Architecture Decision에는:

```text
Transaction Boundary
Timeout
Session
JWT
HA Topology
RTO/RPO
DB Pool
Domain Integration
WAR/JVM 분리
Data Ownership
```

등이 있습니다.

현재 ADR Register에는 실제로 JWT Key SoT, Session Strategy, Transaction Owner, Timeout Model, HA Topology, DR Continuity, RTO/RPO, VM Capacity, RDW/ADW Ownership, Deployment Pipeline 등 **16개의 P0 ADR**이 관리되고 있습니다. `OPEN`은 미결정, `WORKING`은 현재 설계방향일 뿐 최종 승인 상태가 아닙니다.

즉:

```text
WORKING
≠
APPROVED
```

입니다.

---

# 16.13 ADR 하나는 이렇게 처리되어야 합니다

예를 들어 `Session Strategy`라고 하겠습니다.

```text
Problem
센터/WAS 장애 시 Session을 어떻게 유지할 것인가
   ↓
Requirements
HA / 성능 / 보안 / 운영
   ↓
Alternatives

A. DeltaManager
B. Spring Session JDBC
C. 재로그인 허용
   ↓
Comparison
   ↓
Runtime Test
   ↓
Risk
   ↓
Decision
   ↓
Approval
```

현재 `ADR-SES-001`은 여전히 OPEN이며, Architecture Board 자료에서도 **Owner Input과 Runtime Evidence가 필요해 Deferred**되는 항목으로 분류되어 있습니다.

즉 설계 문서에서 “DeltaManager를 사용한다”고 적은 것과 **프로젝트 Architecture Decision으로 승인된 것**은 다릅니다.

---

# 16.14 Exception은 “예외니까 그냥 허용”이 아닙니다

특히 P0 예외는 엄격하게 처리합니다.

현재 HG90 정책은 P0를 해소하지 못하고 예외로 열어두려면 최소 다음 정보를 요구합니다.

```text
Exception ID
Risk Owner
Business Owner
Technical Owner
Reason
Impact
Compensating Control
Expiration Date
Rollback / Contingency
Evidence
Formal Approval
```

보안 Key, Transaction Consistency, Data Integrity처럼 Critical한 영역은 단순 Risk Acceptance로 우회해서는 안 된다고 명시되어 있습니다.

즉:

> **Exception은 표준을 지키지 않아도 되는 면허가 아니라, 위험이 명시되고 기한과 책임자가 존재하는 통제 객체입니다.**

---

# 16.15 G50·G60·G70에서 “문서 검토”가 “운영 검증”으로 바뀝니다

G50부터는 Source만 봐서는 충분하지 않습니다.

예를 들어 JWT 구조가 코드에 있어도:

```text
Private Key는 어디에 있는가?
Rotation이 실제 되는가?
Revoke가 적용되는가?
```

를 봐야 합니다.

G60에서는:

```text
1,200 TPS 설계
```

를 문서에서 확인하는 것이 아니라 실제 Load Test로 증명합니다.

현재 G60의 조건에는:

```text
500 vs 855 TPS 승인
Tomcat Runtime 승인
Hikari 검증
Heap 검증
1,800 TPS Stress Evidence
Session Failover Test
실제 Runtime Config Snapshot
```

등이 P0로 남아 있습니다.

G70은 더 나아가:

```text
RTO/RPO
Center Failover
Failback
Session
Rolling Deploy
Rollback
Alert→Runbook→Evidence
```

를 요구합니다.

---

# 16.16 Architecture Review에서 “Evidence”란 무엇인가

단순 Screenshot 하나가 아닙니다.

최종적으로는 다음 연결이 필요합니다.

```text
Architecture Baseline
       ↓
Model Version
       ↓
Source Commit
       ↓
Build ID
       ↓
Artifact
       ↓
Artifact Hash
       ↓
Deployment ID
       ↓
Environment
       ↓
ServiceId
       ↓
TraceId / GUID
       ↓
Runtime Evidence
```

현재 Closed Loop 문서도 Runtime Evidence를 정확히 이 Chain으로 정의하고 있습니다.

이렇게 해야:

> **“이 성능시험은 정확히 어느 Source와 어느 Architecture Baseline을 검증한 것인가?”**

에 답할 수 있습니다.

---

# 16.17 사람이 승인해도 Artifact가 바뀌면 승인은 무효가 되어야 합니다

Human Approval도 단순 회의록 서명이 아닙니다.

현재 Closed Loop 설계에서는 Approval Object에:

```yaml
approvalId:
gateRunId:
artifactIds:
artifactHashes:
decision:
approver:
role:
approvedAt:
comment:
expiresAt:
```

같은 식별정보를 두고, **승인된 Artifact Hash와 실제 Artifact Hash가 일치할 때만 승인을 유효하게 인정**하도록 설계합니다.

이것은 굉장히 중요한 통제입니다.

```text
Version A 승인
   ↓
Version B 수정
   ↓
A의 승인서를 그대로 사용

        X
```

를 막는 것입니다.

---

# 16.18 G80은 지금까지의 모든 결과를 다시 묶는 Gate입니다

G80은 Closed Loop / Drift Gate입니다.

현재 G80에서 이미 완료된 것은:

- Architecture Rule Registry
- Machine-readable Rule
- Static Source Conformance
- Partial Architecture Model
- Runtime Evidence Registry
- Drift/GAP/Risk/ADR/Open Issue 통합

입니다.

하지만 현재 판정은 **HOLD**입니다.

왜냐하면 다음 P0들이 남아 있기 때문입니다.

| 주요 Blocker            | 의미                               |
| ----------------------- | ---------------------------------- |
| JWT Key SoT/Rotation    | 운영 Signing Key 미확정            |
| Timeout Fault Evidence  | Late Commit/Connection 반환 미증명 |
| P600/P1200/S1800/N-1    | 성능 Runtime 미완료                |
| Center/Session Failover | DR Runtime 미완료                  |
| Server→JVM→WAR→Route    | Physical E2E 미완료                |
| GUID+ServiceId Trace    | 실제 전구간 Trace 미완료           |
| Model Full Traceability | Model SoT 미완성                   |
| Deploy Rollback         | 배포 안전성 미증명                 |
| Migration Go/No-Go      | 이행 증적 미완료                   |
| Critical ADR            | Human Decision 미종료              |

---

# 16.19 그래서 HG90은 Architecture Review의 최종 결재입니다

HG90은:

```text
설계서 완료 승인
```

가 아닙니다.

정확하게는:

> **“현재 Document + Model + Code + Config + Test + Deployment + Runtime Evidence 전체 묶음을 새로운 공식 Architecture Baseline으로 승격해도 되는가?”**

를 판단하는 Gate입니다.

Closed Loop 실행 기준은 다음과 같습니다.

```text
Document Baseline Valid
      ↓
Model Schema Valid
      ↓
Model ↔ Source Match
      ↓
Architecture Rules PASS
      ↓
Build PASS
      ↓
Unit / Integration PASS
      ↓
Security PASS
      ↓
Deployment PASS
      ↓
Runtime Scenario PASS
      ↓
Runtime Evidence Captured
      ↓
Model ↔ Runtime Drift Check
      ↓
Critical Drift = 0
      ↓
Human Approval
      ↓
HG90 PASS
```

이것이 Architecture Review의 최종 모습입니다.

# 16.23 Architecture Board가 판단해야 할 것

현재 프로젝트의 방법론에서도 AI나 자동검사에 맡기면 안 되는 분야를 명확하게 구분합니다.

자동검사가 잘하는 것은:

```text
ServiceId Duplicate
Layer Dependency
Naming
Mapper SQL ID
Private Key Exposure
Runtime Evidence 존재 여부
Artifact Hash
```

같은 것입니다.

반면 사람이 반드시 판단해야 하는 것은 **업무규칙, 데이터 소유권, 보안, 개인정보, Transaction Boundary, 장애전파, Session/JWT 정책, Architecture Exception, 운영 위험, Baseline 승격**입니다.

즉 Architecture Board는 자동검사를 대신하는 조직이 아니라:

> **기계가 결정할 수 없는 Architecture Trade-off를 책임지고 승인하는 조직**

이어야 합니다.

# 16.24 현재 ADR도 실제 Board Decision 대상으로 준비되고 있습니다

현재 Architecture Board Decision Pack에서는 16개 P0 ADR 가운데 **11개가 Human Decision Ready**, 나머지 Session/HA/DR/RTO-RPO/Capacity 등은 Runtime 또는 Owner Input이 필요해 Deferred 대상으로 분류되어 있습니다.

> **ADR 승인만으로 G80/HG90 PASS를 선언하지 않는다. Runtime/P0 Closure 후 Re-Gate를 수행한다.**

즉 사람이 “이 방향으로 합시다”라고 승인했다고 시스템 검증까지 끝난 것이 아닙니다.

# 16.26 그래서 Architecture Gate는 품질검수보다 더 큰 개념입니다

QA는 일반적으로:

```text
기능이 동작하는가?
```

를 많이 봅니다.

Architecture Gate는 추가로:

```text
정해진 구조로 동작하는가?
정해진 자원경계를 지키는가?
정해진 데이터를 사용하는가?
정해진 인증경로를 타는가?
장애를 격리하는가?
설계한 SLA를 실제 만족하는가?
실제 구현이 승인 Artifact와 같은가?
```

를 봅니다.

따라서:

```text
Functional Test PASS
          ≠
Architecture Gate PASS
```

입니다.

# 16.27 한 문장으로 정리하면

**NSIGHT Architecture Review & Gate는 설계문서를 사람이 한번 검토하고 승인하는 절차가 아니라, Source Baseline에서 시작해 Vision·Logical·Physical·Mechanism·Security·Capacity·HA/DR을 Rule과 Evidence로 검증하고, 불일치를 GAP·ADR·Exception으로 관리한 뒤 Runtime Evidence와 Human Approval까지 완료된 결과만 공식 Architecture Baseline으로 승격시키는 지속적 통제체계입니다.**

현재 프로젝트는 이 체계의 뼈대와 Static Conformance까지 상당히 만들어졌지만 **G80과 HG90은 아직 HOLD**이며, Mandatory Runtime Evidence와 Critical ADR Closure가 최종 관문입니다.

그리고 이 단계까지 오면 앞의 15개 설명이 실제 프로젝트 운영으로 연결됩니다.

```text
1~14
"어떤 아키텍처를 만들 것인가"

15
"어떤 규칙으로 지킬 것인가"

16
"그 규칙을 어떻게 심사하고
공식 Baseline으로 승인할 것인가"
```

**17번째에서는 여기서 더 실무적으로 내려가 `Architecture Baseline · Model · Traceability`를 설명하는 것이 가장 자연스럽습니다.** 즉 `요구사항 → 화면 → ServiceId → Handler → Service → SQL → Table → Server/JVM → Build → Deploy → Runtime Evidence`를 하나의 추적성 체인으로 묶고, 왜 이것이 NSIGHT Architecture Closed Loop의 핵심 데이터 모델인지 설명하겠습니다.
