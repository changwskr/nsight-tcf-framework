좋습니다. 이제 **17번째 설명 — NSIGHT Architecture Baseline · Model · Traceability**로 진행하겠습니다.

16번까지는 **“설계안을 어떻게 검토하고 Gate를 통과시킬 것인가”**를 설명했습니다. 이제 한 단계 더 들어가서, 그 Gate가 실제로 무엇을 기준으로 비교하는지 설명해야 합니다.

핵심은 세 가지입니다.

```text
Architecture Baseline
        ↓
Architecture Model
        ↓
Traceability
```

이 셋이 있어야 비로소

> **“이 요구사항이 어떤 설계로 구현됐고, 어느 코드·DB·서버에서 동작하며, 실제 운영에서도 그렇게 동작했다는 것을 어떻게 증명할 것인가?”**

에 답할 수 있습니다.

현재 NSIGHT Closed Loop의 목표도 `Architecture as Document → Architecture as Model → Architecture as Code → Architecture as Test → Architecture as Runtime Evidence`이며, 모든 요소를 추적 가능하게 만드는 것을 최종 방향으로 정의합니다.

# 17. NSIGHT Architecture Baseline · Model · Traceability

## 17.1 먼저 세 개의 차이를 이해해야 합니다

가장 쉽게 정리하면 다음과 같습니다.

| 개념                      | 한 문장 정의                                 | 사람이 주로 보는 것 | 기계가 주로 보는 것        |
| ------------------------- | -------------------------------------------- | ------------------- | -------------------------- |
| **Architecture Baseline** | 현재 공식적으로 인정하는 아키텍처 기준점     | 정의서, ADR, 승인   | Baseline ID, Version, Hash |
| **Architecture Model**    | Baseline을 기계가 이해할 수 있게 구조화한 것 | 모델 View           | Entity, Relation, Schema   |
| **Traceability**          | 요구부터 운영 증적까지의 연결관계            | 추적성 표           | ID/Relation Graph          |

즉:

```text
Baseline
=
"무엇이 현재 기준인가?"


Model
=
"그 기준을 어떤 구조로 표현할 것인가?"


Traceability
=
"그 구조의 요소들이 서로 어떻게 연결되어 있는가?"
```

입니다.

---

# 17.2 Architecture Baseline은 “최신 문서 한 개”가 아닙니다

여기부터 중요합니다.

많은 프로젝트에서 Baseline을:

```text
아키텍처 정의서_v1.0.docx
```

정도로 생각합니다.

NSIGHT Closed Loop가 지향하는 Baseline은 훨씬 넓습니다.

개념적으로:

```text
           ARCHITECTURE BASELINE

┌────────────────────────────────────┐
│ Architecture Document              │
│ ADR / Decision                     │
│ Architecture Model                 │
│ Architecture Rule                  │
│ Source Baseline                    │
│ Configuration Baseline             │
│ Build/Test Result                  │
│ Deployment Information             │
│ Runtime Evidence                   │
│ Approval                           │
└────────────────────────────────────┘
```

을 하나의 버전으로 묶어야 합니다.

현재 Closed Loop 문서도 예시로 `Architecture Baseline = ARCH-2026.08.17-03`, `Model Version = MODEL-3.1.0`, `Source Commit`, `Build`, `Deploy`를 서로 연결하고, Baseline 변경 시 과거 것을 삭제하지 않고 `CURRENT / SUPERSEDED / DEPRECATED` 상태로 유지하도록 정의합니다.

즉 Baseline은:

> **“특정 시점에 승인된 Architecture의 재현 가능한 Snapshot”**

이라고 이해하는 것이 가장 정확합니다.

---

# 17.3 왜 Baseline ID가 중요한가

예를 들어 3월에 성능시험을 했다고 하겠습니다.

```text

PASS
```

그런데 6월에:

```text
Source 변경
Tomcat 변경
Hikari 변경
SQL 변경
```

이 일어났다면 3월의 2.1초는 현재 아키텍처의 증거가 아닐 수 있습니다.

그래서:

```text
Architecture Baseline
ARCH-001
      ↓
Model
MODEL-003
      ↓
Git Commit
a8f27c1
      ↓
Build
BUILD-142
      ↓
Artifact
marketing.war
      ↓
SHA-256
xxxx...
      ↓
Deploy
DEPLOY-PRD-09
      ↓
Runtime Test
RUN-P1200
```

처럼 연결해야 합니다.

현재 자료에서도 Runtime Evidence는 반드시:

```text
architectureBaselineId
→ architectureModelVersion
→ sourceCommit
→ buildId
→ artifactHash
→ deploymentId
→ serviceId
→ traceId
→ runtime evidence
```

Chain을 가져야 한다고 명시합니다.

그래야:

> **“이 Runtime 결과가 어느 Architecture 버전을 증명하는 것인가?”**

에 답할 수 있습니다.

# 17.4 다음은 Architecture Model입니다

Baseline을 Markdown이나 Word 문서로만 관리하면 사람은 읽을 수 있지만 컴퓨터는 관계를 정확하게 이해하기 어렵습니다.

예를 들어 문서에:

> “고객조회 거래는 MG 도메인에서 처리되며 Handler를 통해 Service가 RDW를 조회한다.”

라고 적혀 있을 수 있습니다.

기계가 검사하려면 이것을 구조화해야 합니다.

```text
Domain = MG
ServiceId = ...
Handler = ...
Service = ...
DAO = ...
Mapper = ...
Table = ...
DB = RDW
```

그리고 관계도 명확해야 합니다.

```text

  HANDLED_BY

Handler
  CALLS
Facade

Facade
  CALLS
Service

Service
  USES
DAO

DAO
  EXECUTES
Mapper / SQL

  ACCESSES

```

이것이 **Architecture Model**입니다.

# 17.5 NSIGHT Model에는 어떤 Entity가 들어가는가

Closed Loop 설계에서 최소 Entity가 상당히 구체적으로 정의되어 있습니다.

핵심만 그룹으로 다시 묶으면 다음과 같습니다.

| 모델 영역      | 주요 Entity                                   |
| -------------- | --------------------------------------------- |
| Business       | System, Business, Domain, Function            |
| UI             | Program, Screen, ScreenEvent                  |
| Transaction    | ServiceId, Controller, TCF, STF, ETF          |
| Application    | Handler, Facade, Service, Rule                |
| Data           | DAO, Mapper, SqlId, Table, View               |
| Integration    | Integration, GatewayRoute                     |
| Security       | JwtPolicy, SessionPolicy                      |
| Runtime Policy | TransactionPolicy, TimeoutPolicy, CachePolicy |
| Operation      | BatchJob, OmCatalog                           |
| Delivery       | TestCase, BuildArtifact, Deployment           |
| Runtime        | RuntimeTrace, Evidence                        |
| Governance     | ADR, GAP                                      |

즉 Architecture Model은 **Java Class Diagram만을 의미하지 않습니다.**

비즈니스부터 운영까지 포함합니다.

# 17.6 Model의 핵심은 Entity보다 Relation입니다

예를 들어 `Handler` 100개와 `Table` 1,000개 목록만 가지고 있어도 아키텍처 모델이라고 보기 어렵습니다.

핵심은:

> **“누가 누구와 어떤 관계인가?”**

입니다.

Closed Loop 모델에서는 대표 Relation으로:

```text

HAS_FUNCTION

TRIGGERS

CALLS
USES
EXECUTES
ACCESSES

TESTED_BY

DEPLOYED_AS
OBSERVED_BY
EVIDENCED_BY

```

등을 정의합니다.

Runtime 관계까지 들어가면:

```text

CALLS_SQL
CALLS_EXTERNAL
```

까지 연결됩니다.

이전에 `20-MODEL`이 어렵다고 하셨던 이유가 바로 여기 있습니다.

가장 쉽게 말하면:

> **20-MODEL은 “아키텍처 정의서를 컴퓨터가 읽을 수 있는 관계도”로 만든 것**입니다.

# 17.8 Model을 왜 굳이 만드는가

이 질문이 가장 중요합니다.

문서만 있으면 사람이:

```text
"Handler에서 DAO를 직접 호출하면 안 됩니다."
```

라고 읽을 수 있습니다.

Model이 있으면 컴퓨터가:

```text
Handler
  CALLS
DAO
```

라는 관계를 찾아서:

```text
Architecture Rule Violation
```

으로 판정할 수 있습니다.

즉:

```text
Document
"이렇게 해야 한다"

        ↓

Model
"현재 기대구조는 이것이다"

        ↓

Source Scan
"실제 구조는 이것이다"

        ↓

Compare

Expected
≠
Actual

        ↓

Drift / GAP
```

가 됩니다.

이것이 Architecture as Code/Test로 가는 핵심입니다.

# 17.9 Model Schema도 반드시 필요합니다

JSON/YAML 파일이 있다고 자동으로 좋은 모델은 아닙니다.

예를 들어:

```yaml
serviceId: ABC
```

만 있고 Handler가 없다면 문제가 됩니다.

따라서 Model Schema가 필요합니다.

Closed Loop 설계에서는 다음 Schema를 별도로 두도록 정의합니다.

```text
system-model.schema.json
service-model.schema.json
component-model.schema.json
runtime-policy.schema.json
traceability.schema.json
```

그리고 단순 문법뿐 아니라 Semantic Validation을 수행합니다. 예를 들어 `ServiceId 존재 → Handler 존재`, `DAO 존재 → Mapper 또는 허용된 Adapter 연결`, `Mapper SqlId 존재 → SQL/Table 연결`, `Timeout 정책 → Config/OM Source 연결` 같은 의미검증입니다.

즉:

```text
JSON 문법 정상
      ≠
Architecture Model 정상
```

입니다.

# 17.13 정방향 Trace는 이렇게 사용합니다

예를 들어 요구사항 하나가 있습니다.

```text
REQ-001
"고객의 최근 거래현황을 조회한다."
```

추적하면:

```text
REQ-001
   ↓
화면
   ↓
조회 버튼 Event
   ↓
ServiceId
   ↓
Handler
   ↓
Facade
   ↓
Service
   ↓
DAO
   ↓
Mapper
   ↓
SQL
   ↓
CUSTOMER_xxx Table
```

그리고 개발 이후:

```text
Test Case
   ↓
Build
   ↓
WAR
   ↓
Deployment
   ↓
Runtime Trace
   ↓
Evidence
```

까지 갑니다.

이렇게 되면 요구사항 담당자가:

> **“이 요구사항이 실제 운영까지 구현됐나요?”**

라고 물었을 때 코드 리뷰를 처음부터 다시 할 필요가 없습니다.

---

# 17.14 역방향 Trace가 더 중요할 때도 많습니다

운영 중 SQL 하나가 문제가 생겼다고 하겠습니다.

```text
Slow SQL
SQL_ID = XYZ
```

역방향으로:

```text
SQL XYZ
   ↑
Mapper
   ↑
DAO
   ↑
Service
   ↑
Facade
   ↑
Handler
   ↑
ServiceId
   ↑
Screen Event
   ↑
Screen
   ↑
Requirement
```

를 찾을 수 있습니다.

그러면 운영자가 바로 알 수 있습니다.

```text
어느 업무인가?
어느 화면인가?
어느 사용자가 영향을 받는가?
누가 Owner인가?
어떤 NFR이 영향을 받는가?
어떤 Test를 다시 해야 하는가?
```

이것이 **Impact Analysis**의 기반입니다.

실제 Orchestration 도구도 변경 파일을 입력하면 Traceability Index를 통해 영향받는 ServiceId와 재검증 범위를 계산하도록 설계되어 있습니다.

---

# 17.15 Server/JVM도 Trace에 반드시 들어가야 합니다

현재 NSIGHT에서 특히 보완해야 하는 부분입니다.

논리 Trace가:

```text
ServiceId
→ Handler
→ Service
→ SQL
→ Table
```

까지 끝나면 운영 Architecture에는 충분하지 않습니다.

다음까지 가야 합니다.

```text
ServiceId
   ↓
Application / WAR
   ↓
Tomcat JVM Instance
   ↓
WAS Server
   ↓
Apache Route
   ↓
L4
   ↓
Center / Environment
```

왜냐하면 장애 때 가장 먼저 묻는 것은:

> “이 서비스가 어느 JVM에서 돌고 있습니까?”

이기 때문입니다.

현재 Gate에서도 `71대 Server ↔ JVM ↔ Application/WAR 실제 매핑`이 P0 미완료 조건으로 남아 있습니다.

즉 이 부분은 **아직 최종 Traceability가 닫히지 않은 영역**입니다.

---

# 17.16 Build와 Deployment를 추적하는 이유

다음 상황을 생각해 보겠습니다.

```text
Source에서는 문제를 수정함

그런데 Production에서는
여전히 같은 장애 발생
```

이유가:

```text
Production에 옛 WAR가 배포됨
```

일 수 있습니다.

그래서:

```text
Source Commit
   ↓
Build
   ↓
Artifact
   ↓
SHA-256
   ↓
Deployment
   ↓
Runtime
```

연결이 반드시 있어야 합니다.

현재 Orchestration 시스템도 Build Artifact의 SHA-256을 고정하고, Deployment를 별도로 기록한 뒤 Runtime Evidence와 연결하도록 실제 실행 절차를 정의합니다.

즉:

> **“소스가 맞다”와 “운영에 그 소스가 올라갔다”는 전혀 다른 증명입니다.**

---

# 17.17 Artifact Hash가 중요한 이유

예를 들어:

```text
BUILD-001
marketing.war
```

를 테스트해서 PASS했습니다.

그런데 운영 배포 직전에 누군가 WAR를 다시 만들었다면:

```text
Tested WAR
SHA256 = AAAA


Deployed WAR
SHA256 = BBBB
```

입니다.

그러면 테스트 결과는 운영 Artifact의 증거가 아닙니다.

따라서 최종 Gate에서는:

```text
Tested Artifact Hash
        ==
Deployed Artifact Hash
```

여야 합니다.

현재 Execution System의 최종 Hard Blocker에도 `Artifact SHA-256`, Deployment Evidence, `Tested Artifact Hash == Deployed Artifact Hash`가 포함되어 있습니다.

---

# 17.18 Runtime Trace와 Evidence도 서로 다릅니다

이 부분도 중요합니다.

```text
Log
≠
Trace
≠
Runtime Evidence
```

입니다.

예를 들어 로그에:

```text
Customer search completed
```

가 있다고 해서 Architecture Evidence는 아닙니다.

Runtime Evidence에는 최소:

```text
architectureBaselineId
architectureModelVersion
sourceCommit
buildId
artifactHash
deploymentId
environment
serviceId
traceId
capturedAt
evidenceHash
```

가 연결되어야 합니다. Evidence Manifest의 필수 구조도 이 식별자를 사용합니다.

그래야 증거가 **어떤 Architecture Version과 연결되는지** 알 수 있습니다.

---

# 17.19 Traceability가 Drift Detection의 기반입니다

Trace가 없다면 문서와 코드가 다른 것은 발견할 수 있어도 영향도를 알기 어렵습니다.

Trace가 있으면:

```text
Expected Model
     ↓
ServiceId A
     ↓
Handler A
     ↓
Service A
```

그런데 Source에서는:

```text
ServiceId A
     ↓
Handler B
```

가 발견됩니다.

그러면:

```text
Model vs Code Drift
```

입니다.

다른 예:

```text
Model Timeout = 3 sec
Config Timeout = 5 sec
```

이면:

```text
Model vs Config Drift
```

Runtime에서:

```text
Model Hikari Max = 120
Runtime = 80
```

이면:

```text
Config/Model vs Runtime Drift
```

입니다.

Closed Loop는 실제로 Document↔Model, Model↔Code, Model↔Config, Code↔Runtime, Config↔Runtime, Test↔Runtime의 차이를 Drift로 분류합니다.

---

# 17.20 그래서 Model은 “정답 DB”가 아니라 비교 기준입니다

이것도 중요합니다.

실제 Source가 Model과 다르다고:

```text
Model을 Source대로 자동 수정
```

하면 안 됩니다.

왜냐하면:

```text
Source가 잘못 구현됐을 수도 있기 때문
```

입니다.

정확한 흐름은:

```text
Expected Model
       ↕
Actual Source
       │
       ├─ 동일 → MATCH
       │
       └─ 다름
             ↓
           Drift
             ↓
     Architecture GAP?
     Code Defect?
     허용 Variant?
     Model 오류?
             ↓
           ADR
```

입니다.

Closed Loop의 절대 원칙도 실제 Source와 프로젝트 표준이 다르면 Source를 정답으로 덮어쓰지 말고 `AS-IS ≠ TO-BE → GAP`으로 관리하도록 명시합니다.

---

# 17.21 Baseline 갱신도 자동 덮어쓰기가 아닙니다

GAP이 해결됐다고 바로 Model을 CURRENT로 바꾸는 것도 아닙니다.

정상 흐름은:

```text
Resolved GAP
      ↓
Approved ADR
      ↓
Model Update
      ↓
Schema Validation
      ↓
Source Verification
      ↓
Test
      ↓
Runtime Evidence
      ↓
Human Approval
      ↓
New Architecture Baseline
```

입니다.

현재 Closed Loop도 `Resolved GAP → Approved ADR → Architecture Model Update → Schema Validation → Source/Test Verification → Document Baseline Update → New Baseline ID` 순서로 정의합니다.

즉 Baseline은:

> **현재 상태를 자동 복사한 것이 아니라 검증·결정·승인을 거친 상태**

입니다.

---

# 17.22 Reference Model과 Target Model도 구분해야 합니다

이 부분이 NSIGHT/PDMG 구조에서 중요합니다.

PDMG Reference는:

```text
Reference Lane

R00 Source
 ↓
R10 Document
 ↓
R20 Model
 ↓
R30 Rule
 ↓
R40 Test
 ↓
R50 Runtime
 ↓
R60 Drift
 ↓
R70 GAP/ADR
 ↓
R80 Approval
 ↓
R90 Reference Release
```

로 Reference Baseline을 만듭니다.

그리고 신규 Target 프로젝트는:

```text
Target Source
 ↓
Target Model
 ↓
Reference ↔ Target Comparison
 ↓
Conformance
 ↓
Runtime
 ↓
GAP / ADR
 ↓
Target Baseline
```

으로 검증합니다. 이 두 Lane은 Orchestration 실행시스템에도 별도로 정의되어 있습니다.

이것이 중요한 이유는:

> **PDMG 소스를 그대로 NSIGHT 정답으로 복사하는 것이 아니라, 검증된 Reference Model과 Target Model을 비교해야 하기 때문입니다.**

# 17.23 20-MODEL과 30-CONFORMANCE, 40-TEST의 관계

이제 과거에 질문하셨던 폴더 관계도 쉽게 설명할 수 있습니다.

```text
20-MODEL
"정상이라고 기대하는 구조"
        │
        ▼

30-CONFORMANCE
"무엇을 검사할 것인가"
        │
        ▼

40-TEST
"실제로 검사해보니 결과가 어땠는가"
```

예를 들면:

```text
20-MODEL

Handler
 ↓
Facade
 ↓
Service
 ↓
DAO
```

그 다음:

```text
30-CONFORMANCE

Rule:
Handler → DAO Direct Call 금지
```

그 다음:

```text
40-TEST

Source Scan
→ Handler→DAO direct import = 0
→ PASS
```

실제로 현재 Conformance Test에서도 ServiceId Unique, Handler→DAO/Mapper 직접호출 금지 등은 STATIC PASS가 나왔지만, Runtime Trace와 Timeout, N-1 등은 실제 증적이 없어 `NOT_RUN`입니다. Architecture Model Schema 역시 `PARTIAL` 상태입니다.

즉 **정적 모델과 정적 검증은 상당히 진행됐지만 Runtime까지 닫힌 상태는 아닙니다.**

# 17.24 실제 현재 Model 완성도

현재 자료에서 중요한 사실이 하나 있습니다.

G80 Conformance 결과에는 Draft Model이:

```text
380 nodes
380 edges
```

수준까지 작성되어 있지만 **Full Schema Gate가 미완료**되어 `PARTIAL`로 평가되어 있습니다.

또 Logical Architecture GAP에는:

```text

Owned Table/View Catalog
Public/Internal ServiceId
Integration Contract
Deadline/Timeout Metadata
Screen→ServiceId→SQL→Table 자동 Trace
```

등이 아직 P0 미완성으로 남아 있습니다.

따라서 현재 상태를 정확하게 표현하면:

```text
Model Concept             상당히 정립
Model Draft               존재
ServiceId Source Trace    상당부분 가능
Schema Validation         부분완료
Full Business Trace       미완료
Physical Trace            미완료
Runtime Trace             미완료
Model SoT                 아직 최종승격 전
```

입니다.

# 17.30 이 단계에서 특히 중요한 P0 과제

현재 자료를 기준으로 보면 17번 영역에서 최우선으로 닫아야 할 것은 다음 표에 집중됩니다.

## 17번의 핵심 결론

**Architecture Baseline은 “현재 공식적으로 인정하는 Architecture Version”, Architecture Model은 “그 Architecture를 기계가 읽고 검증할 수 있도록 표현한 구조”, Traceability는 “요구사항부터 코드·DB·서버·배포·Runtime Evidence까지 모든 요소를 하나의 연결망으로 묶는 체계”입니다.**

그리고 NSIGHT에서는 그 연결망의 중심을 **ServiceId**로 두는 것이 핵심입니다. 최종적으로:

```text
Requirement
 → Screen
 → ServiceId
 → Handler
 → Facade
 → Service
 → Rule
 → DAO
 → Mapper
 → SQL
 → Table
 → WAR
 → JVM
 → Server
 → Source Commit
 → Build
 → Artifact Hash
 → Deployment
 → TraceId / GUID
 → Runtime Evidence
 → GAP / ADR
```

가 **정방향과 역방향으로 모두 추적 가능**해야 합니다.

이 상태가 되면 Architecture는 더 이상 “잘 그린 설계도”가 아니라 **실제 프로젝트와 운영시스템을 탐색·검증·통제할 수 있는 디지털 모델**이 됩니다.

그리고 이 지점에서 다음 **18번째 설명**으로 자연스럽게 이어집니다. 18번에서는 **`Drift → GAP → ADR → New Baseline`**, 즉 **문서·모델·코드·설정·Runtime이 서로 달라졌을 때 NSIGHT가 그 차이를 어떻게 발견하고, 어떤 것은 오류로 고치며, 어떤 것은 Architecture Decision으로 받아들여 새로운 Baseline으로 발전시키는지**를 설명하겠습니다.
