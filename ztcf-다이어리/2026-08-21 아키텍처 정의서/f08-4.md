좋습니다. 이제부터는 지금까지 개별적으로 본 5대 플랫폼을 **하나의 NSIGHT 전체 구축 Big Picture**로 합치겠습니다. 이 단계가 중요합니다. 자료를 다시 대조해 보면 NSIGHT의 Big Picture는 단순히 “5개 플랫폼을 나열한 그림”이 아니라, **① 전사 IT Zone, ② 5대 서비스 도메인, ③ 표준 연계 경계, ④ FAST/DEEP 데이터 흐름, ⑤ 운영·개발·선도·DR 환경**이 겹쳐진 구조입니다.

전략 발표자료에서도 Big Picture의 핵심을 **“책임은 공간에 고정하고, 연결은 경계를 통제한다”**라고 정의하고, End-to-End 흐름을 `Channel → Interface → Data Platform → Analytics → Service`로 설명합니다.

# 2. 따라서 “5대 플랫폼”은 전체 Big Picture의 한가운데입니다

이 부분이 중요합니다.

앞서 5개 플랫폼을 하나씩 설명했지만 이것들은 NSIGHT 전체의 바깥 경계가 아닙니다.

정확히는:

```text
채널
 ↓
채널 통합
 ↓
┌──────────────────────────────┐
│      서비스 제공 Zone        │
│                              │
│ Data Platform                │
│ Marketing Platform           │
│ BI Portal                    │
│ Data Governance              │
│ IT Service / Support         │
└──────────────────────────────┘
 ↓
대내 통합
 ↓
타 시스템
```

입니다.

Zone 구성자료에서도 서비스 제공 Zone의 주요 시스템을 정확히 **마케팅플랫폼, 데이터플랫폼, BI포탈, 데이터거버넌스, IT서비스 및 업무지원**으로 명시합니다.

즉 **5대 플랫폼은 NSIGHT가 실제 업무와 데이터를 처리하는 핵심 서비스 공간**입니다.

# 3. 채널과 서비스 사이에 왜 별도의 채널 통합 Zone을 두는가

NSIGHT 전략에서 중요한 것은 채널이 업무 애플리케이션을 직접 소유하지 않는다는 것입니다.

잘못된 구조는:

```text
인터넷뱅킹 ───────▶ Marketing WAS
스마트뱅킹 ───────▶ Marketing WAS
영업점단말 ───────▶ Marketing WAS
외부기관 ─────────▶ Marketing WAS
```

입니다.

이렇게 되면 채널이 추가될 때마다 서비스가 영향을 받고, 서비스가 변경될 때 채널도 영향을 받습니다.

NSIGHT의 방향은:

```text
Channel
   ↓
Channel Integration
   ↓
Service
```

입니다.

Zone 분석자료에서도 채널과 서비스의 직접 결합을 방지하기 위해 **채널 통합 Zone을 사이에 두며**, 영업점 MCA, MCI, 대외 MCA 등이 여기에 위치한다고 설명합니다.

즉 전략적으로 말하면:

> **채널의 변화가 서비스와 데이터 구조를 흔들지 않게 만든다.**

전략 브리핑도 “모바일이 바뀌어도 데이터 구조는 흔들리지 않아야 하고, 채널은 채널 역할만, 플랫폼은 플랫폼 역할만 해야 한다”고 설명합니다.

# 4. 반대편에는 대내 통합 Zone이 있습니다

채널 통합과 대내 통합은 서로 다른 책임입니다.

```text
          사용자 방향

Channel
   ↓
Channel Integration
   ↓
NSIGHT Service


          시스템 방향

NSIGHT Service
   ↓
Internal Integration
   ↓
계정계 / 타 시스템
```

즉 하나는 **Inbound Channel Boundary**, 다른 하나는 **System Integration Boundary**입니다.

자료에서 대내 통합 Zone은 내부 시스템 간 인터페이스 통합을 지원하며 `API Gateway / EAI / FOS / MFT` 등을 사용하도록 정의합니다.

이것이 Logical Architecture의 **No P2P** 정책과 연결됩니다.

```text
금지

Service A ───────────────▶ Service B DB
Service A ─── DB Link ───▶ 타 시스템
Service A ─ 임의 Socket ─▶ 외부
```

대신:

```text
API       → API Gateway / CruzAPIM
거래연계   → EAI / GSE
File      → FOS / MFT
DB Change → CDC
Event     → Kafka
Bulk Data → ETL / DataStage
```

처럼 목적별 통제된 경로를 사용합니다. 전략 설계자료 역시 `P2P 직접 연결 금지`, `CruzAPIM`, `GSE`, `FOS`, `CDC`, `Kafka`를 핵심 Integration 정책으로 제시합니다.

# 5. 그래서 NSIGHT Big Picture에는 “세 가지 통제”가 같이 들어갑니다

전략 발표자료의 Big Picture 장표에는 5대 플랫폼만 있는 것이 아닙니다.

그 옆에 **3대 통제 정책**이 명확히 있습니다.

| 통제                     | 무엇을 통제하는가               | 대표 전략                             |
| ------------------------ | ------------------------------- | ------------------------------------- |
| **규격 표준 통제**       | 시스템이 어떤 언어로 통신하는가 | HTTP/JSON, 표준전문, GUID             |
| **인터페이스 경계 통제** | 시스템끼리 어떻게 연결하는가    | No P2P, API/FOS/CDC/Kafka             |
| **자원 분리 통제**       | 어떤 업무가 어떤 자원을 쓰는가  | RDW/ADW, Online/Batch, ETL/Event 분리 |

따라서 Big Picture는 사실:

```text
5대 Domain
      +
3대 Control Policy
```

로 구성됩니다.

이게 매우 중요합니다.

**5개 플랫폼만 나눠놓고 연결과 자원을 통제하지 않으면 NSIGHT 전략은 완성되지 않습니다.**

# 6. 서비스 제공 Zone 안에는 두 개의 서로 다른 Runtime 세계가 있습니다

그것이 지금까지 계속 설명한 **FAST / DEEP**입니다.

```text
                      SERVICE ZONE

          FAST                         DEEP
           │                            │
           ▼                            ▼
       Customer                       Source
        Event                           DB
           │                            │
           ▼                            ▼
         Kafka                         CDC
           │                            │
           ▼                            ▼
 Real-time Marketing                  RDW
           │                            │
           ▼                            ▼
         Offer                      DataStage
                                        │
                                        ▼
                                       ADW
                                        │
                                        ▼
                                   BI / Analytics
```

Vision/NFR 자료에서도 FAST를 `Customer Action → Kafka Event → Marketing Rule → Real-time Offering`, DEEP을 `Source DB → CDC → RDW → DataStage → ADW → BI/Analytics`로 정의합니다.

따라서 이것들은 별도의 시스템 그림 두 개가 아니라 **하나의 Big Picture 안에서 목적이 다른 두 데이터 고속도로**입니다.

# 7. 여기에서 RDW/ADW 분리가 다시 등장합니다

왜 NSIGHT가 RDW와 ADW를 강하게 분리하는지 이제 전체 Big Picture에서 이해할 수 있습니다.

```text
FAST / Online
      │
      ▼
     RDW
      │
실시간 서비스 보호


DEEP / Analytics
      │
      ▼
     ADW
      │
대량분석 자유도
```

이 둘을 합치면:

```text
Online
   │
   ├──── 같은 DB ──── BI / ETL
   │
   ▼
Resource Conflict
```

가 됩니다.

그래서 전략자료는 RDW/ADW 물리 분리, Online AP/Batch AP 분리, ETL·Event·IMDG 독립 서버 구성을 **자원 분리 통제**의 핵심으로 둡니다.

즉:

> **Big Picture의 경계가 Physical Architecture에서는 실제 자원 격리로 변환됩니다.**

# 8. 이제 여기에 Main / DR을 겹쳐야 합니다

여기에서 중요한 개념이 하나 있습니다.

**DR은 새로운 6번째 서비스 도메인이 아닙니다.**

DR은 기존 서비스 구조 위에 씌워지는 **Availability Overlay**입니다.

전략자료가 선택한 기본 방향은:

```text
                  GSLB

           ┌───────┴───────┐
           ▼               ▼

        MAIN             DR CENTER

       AP Active          AP Active
          │                 │
          └──── Service ─────┘

       DB Active        DB Standby
          │                 │
          └── Replication ──┘
```

입니다.

전략 발표자료에서는 DB 레벨 Active-Active를 채택하지 않고, **AP Active-Active + DB Active-Standby**를 현실적인 금융권 최적안으로 선택했다고 명시합니다. 이유는 DB 동시 쓰기의 정합성 문제와 운영복잡도를 피하면서 AP는 양 센터에서 활성화할 수 있기 때문입니다.

# 9. 그런데 DR 자료를 보면 “모든 시스템을 똑같이 복제”하는 구조는 아닙니다

이 부분도 매우 중요합니다.

현재 Physical 자료에서 의왕 운영과 안성 DR을 비교하면 마케팅 WEB/WAS, Mini SingleView WEB/WAS, RDW 등은 DR 구성이 확인되지만, BI포탈·Self-BI·데이터거버넌스·ADW·일부 Event/ETL/CDC는 이미지상 DR 구성이 명확하지 않습니다.

따라서 현재 자료가 직접 뒷받침하는 구조는:

```text
운영
= Full Service Environment

DR
= Selective Business Continuity Environment
```

에 더 가깝습니다.

Zone 원본의 환경 표도 운영/개발에는 5대 플랫폼 모두를 표시하지만, DR에는 **마케팅플랫폼 + 데이터플랫폼 + IT서비스 및 업무지원**만 표시합니다.

따라서 최종 DR Architecture에서는 반드시:

```text
DR 대상
DR 비대상
DR 축소구성
공유자원
복구우선순위
RTO/RPO
```

를 시스템별로 확정해야 합니다.

# 10. 그리고 Big Picture 위에 또 하나의 축이 있습니다 — 환경 Lifecycle

NSIGHT의 전체 구조를 운영 그림 하나로만 보면 부족합니다.

자료에는 실제로:

```text
선도개발
   ↓
개발
   ↓
시험/검증
   ↓
운영
   ↓
DR
```

이라는 환경 Lifecycle이 존재합니다.

선도개발 자료를 보면 전체 운영환경을 축소 복제한 것이 아니라 **MP + RDW + IM** 중심의 최소 Reference 환경입니다. 여기에는 마케팅 WEB/WAS, 개발 RDW, GitLab, GitRunner, Framework 관리, Nexus, 단말관리/배포 등이 포함됩니다.

즉 선도개발은:

```text
Architecture / Framework Design
           ↓
      선도개발
    Reference 검증
           ↓
Architecture Baseline
           ↓
        개발
           ↓
      통합 / 시험
           ↓
        운영
```

의 위치입니다.

# 11. 이것은 단순 환경 구분이 아니라 구축전략입니다

이 순서에는 중요한 의미가 있습니다.

잘못된 방식은:

```text
전체 개발 시작
    ↓
Framework 나중 통합
    ↓
배포환경 나중 구축
    ↓
성능검증
    ↓
대규모 수정
```

입니다.

NSIGHT의 선도개발 구성을 보면 오히려:

```text
Architecture
     ↓
Framework
     ↓
WEB/WAS
     ↓
RDW
     ↓
CI/CD
     ↓
단말
     ↓
Reference Implementation
     ↓
Validation
     ↓
Baseline
     ↓
전체 개발 확대
```

로 읽는 것이 자연스럽습니다.

선도개발 구성 자체가 `Application Plane + Data Plane + DevOps/Management Plane`을 먼저 검증하는 구조로 분석되어 있습니다.

즉 **아키텍처를 먼저 작게 증명한 뒤 크게 확장하는 전략**입니다.

# 12. 따라서 NSIGHT Big Picture는 사실 “3차원 구조”입니다

이 부분은 자료들을 통합한 **제 구조화**입니다.

원본 장표가 “3차원 아키텍처”라는 용어를 직접 쓰지는 않습니다. 그러나 자료를 전체적으로 겹쳐 보면 가장 이해하기 쉬운 방식입니다.

```text
                  [축 1 : SPACE]

Channel
 ↓
Channel Integration
 ↓
Service Provision
 ↓
Internal Integration


                  [축 2 : DOMAIN]

Data
Marketing
BI
Governance
IT Service


                  [축 3 : ENVIRONMENT]

Pilot
Development
Test
Production
DR
```

그리고 이 모든 축을 관통하는 것이:

```text
NFR

Performance
Availability
Scalability
Security
Observability
```

입니다.

즉 Big Picture의 진짜 의미는 **서버 박스를 많이 그리는 것이 아니라 “어떤 책임이 어느 공간·도메인·환경에 존재하는지”를 확정하는 것**입니다. 전략 수행방법론에서도 Big Picture의 목적을 전체 시스템 공간을 나누고 책임과 경계를 명확히 하는 것이라고 설명합니다.

```text
        Pilot → Dev → Test → Prod → DR
```

이 그림이 지금까지 올려주신 **전략 설명서 + Zone 구성 + 시스템 구성 + DR + 선도개발 자료를 합친 NSIGHT의 상위 구축 Big Picture**라고 보는 것이 가장 적절합니다.

# 14. 여기서 중요한 점은 “구축 순서”까지 Big Picture에 포함된다는 것입니다

NSIGHT를 실제 프로젝트 수행순서로 바꾸면:

```text
WHY / Vision
      ↓
NFR
      ↓
전사 Zone
      ↓
5대 Service Domain
      ↓
책임 / Boundary
      ↓
Data Flow
      ↓
Integration Policy
      ↓
FAST / DEEP
      ↓
Physical Resource
      ↓
Main / DR
      ↓
선도개발 검증
      ↓
전체 개발
      ↓
Runtime 검증
      ↓
운영 Baseline
```

이것이 자료에서 정의한 6단계 방법론과 실제 구축환경을 결합한 수행 흐름입니다. 원 수행방법론 역시 `비즈니스 변화 → Vision → NFR → Big Picture → Domain/Boundary → Logical Policy → Physical Mapping → Mechanism → Runtime → Gap → 운영 표준 반영` 순으로 정리되어 있습니다.

TCF, ServiceId, Apache/Tomcat, HikariCP, JWT 등은 이 전체 그림의 훨씬 아래에 위치합니다.

```text
      ↓

      ↓

      ↓

      ↓

      ↓
────────────────────────
여기부터 Application 상세
────────────────────────
```

따라서 앞으로의 설명은 **전략 → 공간 → 정책 → 물리 → 실행 메커니즘** 순서를 계속 유지하겠습니다.

다음 단계에서는 이 Big Picture에서 바로 한 단계 내려가 **NSIGHT Logical Architecture를 상세하게 설명하는 것이 맞습니다.** 특히 `① Domain Separation → ② Responsibility Boundary → ③ Data Flow 강제 → ④ Integration 통제 → ⑤ Online/Batch·FAST/DEEP 분리 → ⑥ 정상패턴/금지패턴`을 하나의 **정책 아키텍처**로 연결하면, 지금까지의 전략이 실제 설계 기준으로 어떻게 변환되는지 볼 수 있습니다.
