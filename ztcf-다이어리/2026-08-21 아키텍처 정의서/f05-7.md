좋습니다. 이제 **③ BI 포탈 구축전략**으로 넘어가겠습니다. 이번에도 소스 메커니즘이 아니라 **아키텍처 전략 브리핑을 최상위 기준**으로 보고, 실제 BI 포탈 논리 기술 아키텍처를 그 전략의 구현 구조로 연결하겠습니다.

전략 브리핑의 BI 포탈 장표는 역할을 아주 명확하게 정의합니다.

> **데이터플랫폼 = 기초공사 → 마케팅플랫폼 = 반응하는 두뇌 → BI 포탈 = 의사결정 공간**

그리고 BI 포탈의 목표는 단순 조회나 리포팅이 아니라 **“AI가 지원하는 자율적 의사결정 공간”**, 즉 데이터 중심 경영의 마침표인 **“즉시 판단”**입니다.

# 1. 왜 BI 포탈이 별도의 전략 영역인가

앞에서 두 플랫폼을 이렇게 설명했습니다.

```text
데이터플랫폼
    ↓
데이터를 신뢰할 수 있게 만든다
    ↓
TRUST

마케팅플랫폼
    ↓
고객 행동에 반응한다
    ↓
REACTION
```

그런데 이것만으로는 데이터 중심 경영이 완성되지 않습니다.

조직 구성원이 데이터를 보고 판단하는 시간이 여전히 오래 걸린다면:

```text
데이터는 실시간
마케팅도 실시간
        │
        ▼
보고서는 3일 후
분석 요청은 1주 후
        │
        ▼
경영 판단은 느림
```

이라는 문제가 남습니다.

그래서 세 번째 축이 필요합니다.

```text
                  NSIGHT

             DATA PLATFORM
                  │
                  │ TRUST
                  ▼
          MARKETING PLATFORM
                  │
                  │ REACTION
                  ▼

────────────────────────────────

               BI PORTAL
                  │
                  │ DECISION
                  ▼
             즉시 판단
```

전략문서는 바로 이 이유 때문에 **“시스템 실행이 빠르더라도 판단이 느리다면 진정한 데이터 중심 경영이 아니다”**라고 설명합니다.

---

# 2. 기존 BI의 문제를 무엇으로 보는가

기존 BI는 대체로 다음 흐름입니다.

```text
현업
 │
 │ "지난달 상품별 실적 뽑아주세요"
 ▼
IT 요청
 │
 ▼
요건 협의
 │
 ▼
SQL 작성
 │
 ▼
데이터 추출
 │
 ▼
보고서 작성
 │
 ▼
현업 확인

수시간 ~ 수일
```

문제의 핵심은 BI 도구가 느린 것이 아니라 **의사결정 과정에서 IT 부서가 병목이 되는 구조**입니다.

NSIGHT 전략은 이를:

```text
Request Driven BI
        ↓
Self-Service Decision
```

으로 바꾸려 합니다.

즉:

> **“IT가 데이터를 만들어 주는 구조”에서 “현업이 직접 데이터를 탐색하고 판단하는 구조”로 전환**

하는 것입니다.

# 3. BI 포탈의 3대 혁신

전략 브리핑과 최종 전략 정리본은 BI 포탈 혁신을 정확히 세 가지로 정의합니다.

```text
              BI PORTAL
          "의사결정 공간"

        ┌───────┼────────┐
        │       │        │
        ▼       ▼        ▼
     Self-BI  AI/NLP  Reporting
        │       │        │
        ▼       ▼        ▼
      직접     쉽게      일관되게
      분석     질문      보고
```

하나씩 보면 전략의 의도가 훨씬 명확해집니다.

---

# 4. 첫 번째 — Self-BI

Self-BI의 목표는 단순히 BI Tool을 한 개 더 설치하는 것이 아닙니다.

핵심은:

> **IT 병목 제거**

입니다.

기존에는:

```text
현업
 ↓
IT 요청
 ↓
SQL
 ↓
추출
 ↓
Excel / 보고서
```

였다면,

Self-BI에서는:

```text
현업
  │
  ▼
BI Portal
  │
  ▼
데이터 탐색
  │
  ├─ 조건 선택
  ├─ Drill Down
  ├─ 시각화
  └─ 비정형 분석
  │
  ▼
즉시 판단
```

으로 바뀝니다.

전략문서는 현업 담당자가 IT 부서의 데이터 추출·개발을 기다리지 않고 **직접 데이터를 탐색하고 시각화**하도록 하는 것을 Self-BI의 본질로 정의합니다.

---

# 5. 실제 구축에서는 BI-Matrix가 Self-BI 영역입니다

전략 개념을 실제 논리 기술 아키텍처와 연결하면 더 명확합니다.

BI 포탈 논리 기술 아키텍처에는:

```text
Self-BI Application
        │
     BI-Matrix
        │
   ┌────┴─────┐
   │          │
자연어 질의   비정형 보고서
```

가 명시되어 있습니다.

즉 전략과 실제 구축을 연결하면:

| 전략            | 구현영역        |
| --------------- | --------------- |
| Self-BI         | BI-Matrix       |
| 현업 직접 탐색  | 비정형 분석     |
| 자연어 접근     | 자연어 질의     |
| 사용자 실행기반 | WAS / VM / IaaS |

가 됩니다.

---

# 6. 두 번째 — AI/NLP 자연어 질의

전략자료에서 가장 혁신적인 부분 가운데 하나입니다.

예시는 매우 단순합니다.

```text
"지난달 실적 보여줘"
```

라는 자연어를 사용자가 입력하면:

```text
자연어
   ↓
AI / NLP
   ↓
SQL 변환
   ↓
데이터 조회
   ↓
결과
```

가 되는 구조입니다.

의도는 명확합니다.

기존에는 사용자가:

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
```

를 알아야 하거나 IT에게 요청해야 했습니다.

차세대에서는 사용자가 **업무 언어로 질문**합니다.

```text
"지난달 지역별 수신 실적 보여줘"

"전년 대비 증가율이 높은 조합은?"

"지난 3개월 고객 유입이 감소한 지역은?"
```

그리고 BI가 데이터 질의로 변환합니다.

즉:

> **기술 언어(SQL)를 업무 언어로 바꾸는 것**

이 전략의 핵심입니다.

---

# 7. 그런데 AI/NLP는 아직 전략 수준이 강합니다

여기에서 하나는 명확히 짚어야 합니다.

업로드 자료는 다음까지는 분명히 정의합니다.

```text
Natural Language
      ↓
AI/NLP
      ↓
SQL
      ↓
Result
```

하지만 현재 확인한 전략/논리 자료에는 다음 세부 구현이 최종 확정되어 있지 않습니다.

```text
어떤 LLM을 사용하는가?
어디서 실행하는가?
Semantic Layer가 있는가?
Table/Column 정보를 AI에 어떻게 제공하는가?
SQL 허용범위는?
SELECT만 허용하는가?
개인정보 권한은 어떻게 적용하는가?
Hallucination SQL은 어떻게 차단하는가?
비용/Timeout은?
질의 Audit은?
```

따라서 이 부분은 제가 임의로 RAG나 특정 AI 제품을 붙이면 안 됩니다.

현재 상태를 정확히 표현하면:

```text
[전략 확정]

AI/NLP 자연어 질의
   ↓
현업 Self-BI 지원


[구축 상세 필요]

NL2SQL Architecture
Security
Semantic Model
Query Governance
Validation
Audit
```

입니다.

이것은 향후 BI 상세 아키텍처에서 반드시 닫아야 할 중요한 GAP입니다.

---

# 8. 세 번째 — Reporting 표준화

Self-BI가 자유로운 분석을 제공한다고 모든 보고서를 Self-BI로 만들면 안 됩니다.

은행 정보계에는:

```text
정형 경영보고서
실적 보고
감사/통제 보고
공식 업무 보고
```

처럼 **정확한 형식과 결과가 반복적으로 보장되어야 하는 보고서**가 많습니다.

그래서 전략자료는 별도로:

> **M2SOFT Report Designer 기반 Reporting 표준화**

를 정의합니다.

구조적으로 보면:

```text
                   BI

      ┌─────────────┴─────────────┐
      │                           │
      ▼                           ▼
   자유 분석                   공식 보고
   Self-BI                    Reporting
      │                           │
      ▼                           ▼
 탐색 / 질문                 표준 Layout
 비정형 분석                 정형 Report
```

입니다.

즉 둘은 경쟁 관계가 아닙니다.

# 9. 실제 BI 포탈에는 4개의 분석 실행영역이 있습니다

상세 논리 기술 아키텍처를 보면 BI 포탈은 하나의 프로그램이 아닙니다.

크게 다음과 같이 나뉩니다.

```text
                    BI PORTAL

 ┌────────────────────────────────────┐
 │ ① BI Portal / Data Eye             │
 │                                    │
 │ 계정/권한                          │
 │ 결재                               │
 │ 통합검색                           │
 │ 데이터 활용                        │
 │ 보고서 관리                        │
 │ 관련 시스템 연계                   │
 └────────────────────────────────────┘

 ┌────────────────────────────────────┐
 │ ② Dashboard                        │
 │                                    │
 │ 경영 Dashboard                     │
 │ Governance Dashboard               │
 └────────────────────────────────────┘

 ┌────────────────────────────────────┐
 │ ③ Self-BI / BI-Matrix              │
 │                                    │
```

그리고 별도로 **신용실적 Application**도 존재합니다.

즉 BI 포탈은 사실 하나의 화면이 아니라 **분석·보고·검색·권한·의사결정을 통합하는 플랫폼 영역**입니다.

입니다.

# 11. BI 포탈과 ADW의 책임 경계

여기서 아주 중요한 아키텍처 원칙이 있습니다.

BI 포탈이 분석을 한다고 해서 **BI 포탈이 데이터를 소유하는 것**은 아닙니다.

전략 구조상:

```text
ADW
=
분석 데이터 관리


BI Portal
=
분석 데이터 소비 + 의사결정
```

입니다.

즉:

```text
          DATA PLATFORM

RDW
 │
 │ ETL
 ▼
ADW
 │
 │ 분석용 데이터
 ▼
────────────────────────
         BI PORTAL
────────────────────────
 │
 ├─ Dashboard
 ├─ Self-BI
 ├─ OLAP
 └─ Reporting
```

로 보는 것이 맞습니다.

전략 브리핑의 RDW/ADW 분리도 이 역할 차이를 전제로 합니다. RDW는 온라인/실시간 운영창고, ADW는 대용량 분석 전용 창고입니다.

---

# 12. 그런데 실제 논리 아키텍처에서는 RDW와 ADW 모두 연결되어 있습니다

상세 논리 기술 아키텍처를 보면 BI 포탈, Self-BI, OLAP이 데이터 영역과 연계되고, `RDW → ETL → ADW` 구조도 존재합니다.

그래서 구축 단계에서는 반드시 아래 Matrix를 만들어야 합니다.

| BI 기능          |  RDW Read |  ADW Read |     Write | 원칙                 |
| ---------------- | --------: | --------: | --------: | -------------------- |
| 실시간 Dashboard |      검토 |      검토 |         X | Freshness 기준 결정  |
| Self-BI          | 제한 검토 |   주 대상 |         X | 분석 부하 보호       |
| OLAP             |    최소화 |   주 대상 |         X | ADW 중심             |
| Reporting        |    목적별 |    목적별 |         X | 보고서별 Source 확정 |
| 신용실적         | 확인 필요 | 확인 필요 | 확인 필요 | 업무 상세 확인       |

이 표의 값은 **현재 자료만으로 전부 확정할 수 없습니다.**

하지만 Architecture Rule은 명확해야 합니다.

> **대량 Self-BI/OLAP 분석이 RDW 온라인 성능을 침범하면 안 된다.**

왜냐하면 RDW/ADW 분리 자체가 분석 부하의 온라인 전파를 막기 위해 만들어진 전략이기 때문입니다.

---

# 13. 따라서 BI 포탈에서 가장 위험한 금지패턴

전략을 구축 Rule로 바꾸면 다음과 같습니다.

```text
금지 패턴 ①

Self-BI
   ↓
RDW 전체 테이블
   ↓
무제한 Ad-hoc SQL
```

이렇게 되면:

```text
대량 Query
   ↓
RDW CPU / IO / Session
   ↓
SingleView 영향
   ↓
Marketing 영향
```

이 되어 RDW/ADW 분리 전략 자체가 무너집니다.

따라서 분석성 대량 질의의 기본 방향은:

```text
Self-BI / OLAP
        ↓
       ADW
```

가 되어야 하고, RDW 조회가 필요하다면 **실시간성·조회범위·부하제한 정책**을 별도로 정의해야 합니다.

# 14. 두 번째 위험 — Self-BI와 OLAP, Reporting의 역할 중복

논리 아키텍처를 보면:

```text
Self-BI
 └─ 비정형 보고서

OLAP
 ├─ 정형 보고서
 └─ 비정형 보고서

Reporting
 └─ 정형 Report
```

처럼 일부 기능이 겹칩니다.

따라서 구축 전에 책임을 명확히 해야 합니다.

예를 들어 아키텍처상 다음과 같은 구분표가 필요합니다.

| 요구유형            | 담당 영역    |
| ------------------- | ------------ |
| 현업 즉석 탐색      | Self-BI      |
| 자연어 질의         | Self-BI / AI |
| 다차원 분석         | OLAP         |
| 공식 정형 보고서    | Reporting    |
| KPI 상시 모니터링   | Dashboard    |
| 통합 진입/검색/권한 | BI Portal    |

현재 전략자료의 방향과는 잘 맞지만, **세부 기능 소유권은 최종 기준으로 더 명확히 해야 합니다.**

# 15. BI 포탈의 성공 조건은 “보고서 수”가 아닙니다

전략 관점에서 잘못된 KPI는 이런 것입니다.

```text
보고서 2,000개 구축
Dashboard 300개
Self-BI 화면 100개
```

물론 구축 물량은 필요하지만 전략의 성공 여부는 다른 데 있습니다.

```text
질문
 ↓
데이터 접근
 ↓
분석
 ↓
이해
 ↓
판단

이 시간을 얼마나 줄였는가?
```

즉 BI 포탈의 핵심 SLA는 개념적으로:

> **Time to Decision**

입니다.

전략 브리핑이 계속해서 **“즉시 판단”**을 강조하는 이유입니다.

# 16. 데이터플랫폼·마케팅플랫폼·BI 포탈을 이제 완전히 연결할 수 있습니다

세 플랫폼의 역할이 드디어 하나의 구조가 됩니다.

```text
                     NSIGHT

                SOURCE SYSTEM
                      │
                      ▼
              ┌──────────────┐
              │ DATA PLATFORM│
              │              │
              │ CDC          │
              │ Kafka        │
              │ RDW          │
              │ ADW          │
              └──────┬───────┘
                     │
               TRUSTED DATA
                     │
        ┌────────────┴────────────┐
        │                         │
        ▼                         ▼

┌──────────────────┐      ┌──────────────────┐
│ MARKETING        │      │ BI PORTAL        │
│ PLATFORM         │      │                  │
```


의 완성입니다.

# 17. 그런데 여기에는 네 번째 축이 반드시 필요합니다

여기까지 보면:

```text
데이터 있음
마케팅 가능
BI 가능
```

합니다.

하지만 문제가 하나 있습니다.

예를 들어:

```text
"고객수"
"활동고객"
"거래고객"
"유효고객"
```

이라는 용어를 각 부서가 서로 다르게 정의한다면 어떻게 될까요?

BI의 자연어 질의가 아무리 좋아도:

```text
"지난달 활동고객 보여줘"
```

의 **“활동고객”** 정의 자체가 부서마다 다르면 결과를 신뢰할 수 없습니다.

그래서 다음 플랫폼이 반드시 필요합니다.

```text
          DATA GOVERNANCE

용어
표준
Meta
품질
모델
Definition

          ↓

"같은 말을 하면
 같은 데이터를 의미한다"
```

전략 브리핑에서는 데이터거버넌스를 5대 서비스 도메인 중 하나로 두고, **IT 메타시스템 기반 데이터 표준·품질관리, 용어 정의 및 데이터 모델 일관성 유지**를 책임으로 정의하고 있습니다.

# 18. 지금까지 세 플랫폼의 관계

여기까지의 NSIGHT를 한 문장씩만 기억하면 됩니다.

```text
DATA PLATFORM
──────────────────────
"데이터를 믿게 만든다"

       ↓


MARKETING PLATFORM
──────────────────────
"데이터로 즉시 실행한다"

       ↓


BI PORTAL
──────────────────────
"데이터로 즉시 판단한다"
```

그리고 다음:

```text
DATA GOVERNANCE
──────────────────────
"그 데이터의 의미와 품질을
 모든 곳에서 동일하게 만든다"
```

가 세 플랫폼의 **신뢰 기반**을 담당합니다.

# 19. BI 포탈 전략의 핵심 결론

BI 포탈을 단순히 이렇게 보면 안 됩니다.

```text
BI Portal
=
조회 화면 + 보고서
```

전략자료 기준의 정확한 정의는:

> **“신뢰할 수 있는 ADW/RDW 데이터를 기반으로 현업이 IT의 도움 없이 직접 탐색·질의·분석하고, AI/NLP를 이용해 기술 장벽을 낮추며, 정형 Reporting을 표준화하여 조직 전체의 Time-to-Decision을 단축하는 자율적 의사결정 플랫폼”**

입니다.

그리고 현재 자료를 전략 → 구축 관점으로 검토하면 **추가 정의가 필요한 중요한 항목**은 다음입니다.

| GAP                                | 왜 필요한가                         |
| ---------------------------------- | ----------------------------------- |
| AI/NLP 상세 Architecture           | 자연어→SQL을 안전하게 실행하기 위해 |
| Semantic/Metadata 연계             | 업무용어와 실제 데이터 연결         |
| Query Authorization                | 사용자가 허용된 데이터만 조회       |
| RDW/ADW Access Matrix              | 분석 부하가 RDW를 침범하지 않도록   |
| Self-BI/OLAP/Reporting 책임 Matrix | 기능 중복 제거                      |
| Query Resource Governance          | 대량 Ad-hoc Query 통제              |
| Audit/Trace                        | 누가 어떤 데이터를 조회했는지 추적  |
| Data Quality 표시                  | 분석 결과의 신뢰성 확보             |

특히 **AI/NLP와 Data Governance는 따로 설계하면 안 됩니다.** 자연어 질의가 올바른 SQL을 만들려면 “고객”, “실적”, “조합”, “거래” 등의 업무용어와 실제 데이터 모델 사이의 관계가 먼저 정립되어야 하기 때문입니다. 다만 이 연계의 구체 구현방식은 현재 전략자료에서 아직 확정되어 있지 않으므로 후속 설계 대상으로 봐야 합니다.

다음 단계는 **④ 데이터거버넌스 구축전략**입니다. 여기서는 `IT Meta → Business Meta → Data Standard → Data Quality → Data Model → BI/AI`가 어떻게 연결되어야 하는지, 그리고 왜 데이터거버넌스가 별도의 관리시스템이 아니라 **Data·Marketing·BI 전체의 신뢰 통제(Control Plane)**인지 전략자료와 실제 데이터거버넌스 논리구조를 함께 놓고 설명하겠습니다.
