## 1. 핵심 결론

이 PDF는 KDB산업은행 차세대 정보시스템 **인터페이스 아키텍처 정의서(IA)** 의 **표지·이력·목차와 제1장 기본정책(개요·원칙·설계기준 앞부분)** 이다.

장표가 직접 제시하는 핵심은 다음과 같다.

```text
차세대 시스템 모델
        │  인터페이스 아키텍처 관점
        ▼
기본정책 ──► 아키텍처 설계 ──► 아키텍처 관리체계 ──► 구현(기초 데이터 활용)
   │              │                    │
   │              ├─ 연계 아키텍처 구성
   │              ├─ 연계 표준
   │              ├─ 연계 패턴
   │              └─ 상세 아키텍처
   │                    × 보안 / 로그관리 (횡단)
   └─ 원칙 → 설계기준
```

목적은 문서를 쌓는 것이 아니라, **구현의 기준 데이터(Reference Data)** 로 쓰는 것이다.

원문이 고정하는 레이어는 네 층이다.

```text
채널 Layer
        │
채널통합 Layer   (대내MCI / 대외MCI / FEP / EAI)
        │
비즈니스 Layer   (계정계 / 정보계 / 경영지원·통제  + 대내 EAI)
        │
인터페이스 Layer (CDC / ETL / EIMS 전문공통관리)
```

솔루션 역할은 한 문장으로 고정된다.

| 솔루션 | 원문의 역할 (FACT) |
|---|---|
| 대내 MCI | 내부·고객채널 ↔ 백엔드 **온라인** |
| 대외 MCI | 대외기관 ↔ 백엔드 **온라인/배치** |
| EAI | 백엔드 ↔ 백엔드. 채널–백엔드 **배치**. 대외 송신 시 백엔드–대내MCI. **DB-LINK 금지** |
| MFT | 내부 **서버–서버 파일** 전송만 |

한 문장으로 말하면, 이 PDF는 **“어떤 구간에 어떤 솔루션·프로토콜을 쓸지”를 제1장에서 고정**하고,  
**구성도·표준전문·유형별 패턴·로그·관리체계(2~6장)는 후속 장(본 PDF 밖)에 위임**한다.

# 5. 목적 영역 상세 분석  — 목차 1.1.1

## 5.1 원본 FACT

- 정의 관점: **인터페이스 아키텍처**
- 산출의 쓰임: 차세대 시스템 **구현의 기준 데이터**
- 문서 골격: 기본정책 → 설계(구성·표준·패턴·상세) → 관리체계 → 구현
- 횡단 관심사: **보안**, **로그관리** (설계 화살표와 교차)

## 5.2 아키텍처 문서의 성격 (ANALYSIS)

이 문서는 솔루션 매뉴얼이 아니라 **IA Baseline** 이다.

```text
원칙이 없으면 설계기준이 흔들린다
설계기준이 없으면 구간별 프로토콜이 제각각이 된다
관리체계가 없으면 표준전문이 장표에서 끝나 버린다
```

「기준 데이터」는 서버 BOM이 아니다. 개발·연계 설계가 **어느 솔루션을 경유할지**를 고르는 참조표에 가깝다.

### 의미

VISION 개요 장표가 AA/TA/DA를 선언하듯, 이 장표는 **Interface Architecture를 독립 축으로 선언**한다.  
차세대 정보계 개요의 Scope 3축 밖에 자주 빠지는 Interface를, 산업은행 IA는 **1번 문서 목적**으로 올려 둔다.

# 6. 아키텍처 구성 개요 (1/2) — 목차 1.1.2

## 6.1 원본 FACT

- 레이어를 **연계 특성·용도**에 따라 분리한다.
- 지향점: **확장성**, **안정성**.
- 채널은 내부 / 비대면 고객 / 기관으로 나뉜다.
- 채널통합은 대내MCI, 대외MCI, FEP, EAI가 게이트웨이 역할을 한다.
- 비즈니스는 계정계·정보계·경영지원을 두고, 대내 EAI로 모듈 간 연계한다.
- 인터페이스 층은 CDC, ETL, EIMS(전문공통관리)로 데이터 이동·전문 관리를 담당한다.
- 주석: MCA·인터페이스가 HTTP, TCP/IP, SOAP 등으로 내외 데이터를 교환한다.

## 6.2 설계 의미 (ANALYSIS)

레이어 분리는 “박스를 많이 그리는 것”이 아니라 **장애·확장의 단위를 나누는 것**이다.

| 레이어 | 바꾸면 영향이 멈추는 선 | 섞이면 생기는 증상 |
|---|---|---|
| 채널 | 단말·앱 교체 | 채널 변경이 계정계 전문까지 흔들림 |
| 채널통합 | 어댑터·프로토콜 | 채널마다 백엔드 프로토콜이 다름 |
| 비즈니스 | 상품·계정 로직 | EAI 없이 직접 호출·DB-LINK |
| 인터페이스 | 복제·배치·전문저장 | 온라인이 ETL을 타거나, 파일이 MCI 세션에 실림 |

### 6.3 후속 문서에서 채워야 할 최소 항목 (ANALYSIS)

- [ ] 채널 유형별 공식 목록(표지 다이어그램 vs 1.3.1 채널 목록 정합)
- [ ] 대내MCI와 문서의 “대내MCA” 표기 동일 여부
- [ ] FEP가 대외MCI 내부 구성요소인지 독립 노드인지
- [ ] EIMS의 소유(인터페이스계 vs IT내부관리)

# 8. 인터페이스 원칙 — 목차 1.2.1

## 8.1 원본 FACT — 정의

> 인터페이스는 다른 서버 또는 동일 서버 내 다른 미들웨어에 있는 다른 애플리케이션(업무)과의 메시지(데이터) 연계를 의미함

동일 서버라도 **미들웨어가 다르면 I/F**다. 프로세스 내부 호출은 이 정의 밖이다.

## 8.2 원본 FACT — 기본 원칙

| No | 구분 | 원칙 |
|---|---|---|
| 1 | 공통 | 한 거래 흐름에는 연계 솔루션을 **하나만** 사용 (대내/대외 MCI, EAI, MFT 등) |
| 2 | 대내 MCI | 내부·고객채널 ↔ 백엔드 **온라인** |
| 3 | 대외 MCI | 대외기관 ↔ 백엔드 **온라인/배치** |
| 4 | EAI | 백엔드 ↔ 백엔드 |
| 5 | EAI | 내부·고객채널 ↔ 백엔드 **배치(데이터)** |
| 6 | EAI | 대외 송신 시 백엔드 ↔ **대내 MCI 서버** 연계 |
| 7 | EAI | 시스템 간 **직접 DB-LINK 금지** |
| 8 | 예외 | 통합로그인·ESSO 구간은 **직접 연계** |
| 9 | 예외 | 워크플로우는 업무/BPM 서버 간 **AP(API)** 연계 |
| 10 | 예외 | 단말 솔루션 데이터는 단말 화면이 솔루션 **API 서버와 직접** 연계 |
| 11 | 예외 | Legacy(AS-IS)는 기존 연계 방식 **유지 가능** |

도식 참여자(FACT): 내부채널(단말관리서버, 웹통합, 내부PC), 고객채널(인뱅 WEB/BIZ, 스마트, 모바일/웹, Open API, IVR), 대외채널(대외기관, SWIFT, 인터넷PC), 백엔드(계정계·정보계·인프라), 솔루션(대내/대외 MCI, EAI, MFT).

## 8.3 설계 의미 (ANALYSIS)

원칙 1은 **홉(hop) 최소화**다. 채널→MCI→EAI→계정계처럼 솔루션을 겹치면 장애점·추적이 두 배가 된다.

원칙 6은 직관과 어긋나 보이므로 별도 고정이 필요하다.

```text
대외로 나가는 어떤 흐름
   백엔드 ──EAI──► 대내MCI ──► (이후 대외 경로)
```

ANALYSIS: “대외인데 왜 대내MCI인가”는 1.3.1 (4/4)의 대외MCI HTTP 경로와 **역할이 다른 유스케이스**일 수 있다. 후속 장에서 시나리오를 나눠야 한다.

원칙 7은 TA/DA와 충돌하기 쉬운 조항이다. CDC/ETL(인터페이스 Layer)은 DB 복제이지 DB-LINK 애플리케이션 결합이 아니다. **금지 대상은 앱이 상대방 테이블을 직접 보는 것**으로 읽는 것이 안전하다.

### 8.4 예외 4항의 위치 (ANALYSIS)

목차 1.4가 비어 있는 본 PDF에서, 예외는 이미 1.2에 들어와 있다. 1.4는 예외의 **승인·기간·대상 시스템 목록**을 담는 장으로 보는 것이 자연스럽다.

## 9.2 온라인 연계 1.3.1 (2/4) — 채널 ↔ 대내MCI

### FACT

> 채널–대내MCI 구간 온라인 프로토콜은 업무 요건·시스템 구성 환경에 따라 표준 TCP/IP와 HTTP로 정의·사용함.

| No | From | To | 프로토콜 | 세션 유지 | 역방향 거래 |
|---|---|---|---|---|---|
| 1 | 영업점·콜센터·범용 단말 | 대내MCI | TCP Socket | 유지 | 역방향 |
| 2 | 자동화기기 (ATM/CD) | 대내MCI | TCP Socket | 유지 | 역방향 |
| 3 | 텔레뱅킹 (IVR) | 대내MCI | TCP Socket | 없음 | 없음 |
| 4 | 전자금융(인뱅/모바일, 웹비즈, 홈페이지, 퇴직연금, Pioneer Branch) | 대내MCI | HTTP | 없음 | 없음 |
| 5 | 범용단말 (솔루션 Web Page) | Web Application Server | HTTP | 없음 | 없음 |

주석(\*): 통합단말에서 솔루션 웹페이지를 브라우저 링크로 쓰면 **대내MCI를 거치지 않고 WAS에 직접** 접속한다. → 원칙 10과 정합.

### 핵심 포인트 (ANALYSIS)

- 창구·ATM은 **세션+역방향(BID/푸시류)** 이 필요한 동기 채널이다.
- 전자금융은 HTTP·세션 없음 → 연결 유지형 푸시는 이 표만으로는 부족하다. 후속 4.2 패턴에서 보완해야 한다.
- 행 5는 MCI 표준이 아니라 **예외 경로를 표준 표에 넣은 것**이다.

## 9.3 온라인 연계 1.3.1 (3/4) — 대내MCI ↔ 내부시스템

### FACT

> 대내MCI–내부시스템 구간 온라인 프로토콜은 HTTP를 표준으로 한다. 표준 HTTP를 지원하지 못하면 예외 프로토콜을 적용한다.

| No | From | To | 프로토콜 | 세션 | 역방향 |
|---|---|---|---|---|---|
| 1 | 대내MCI | 계정계 | HTTP | 없음 | 역방향 |
| 2 | 대내MCI | 정보계 | HTTP | 없음 | 없음 |
| 3 | 대내MCI | 전행지원 및 통제 | HTTP | 없음 | 없음 |
| 4 | 대내MCI | IT 인프라 | HTTP | 없음 | 없음 |
| 5 | 대내MCI | 표준 예외 대상 | ETC Protocol | 없음 | 없음 |

주석(\*): HTTP 미지원 대상은 시스템 요건에 따른 업무 정의 후 다른 프로토콜 적용.

### ANALYSIS

역방향이 **계정계만** 허용된다. 채널 측 단말 역방향(9.2)과 맞추려면, 푸시/책임자승인 류는 계정계(또는 MCI 자체 Local)에서 끝나야 한다. 정보계로 역방향을 열면 이 표를 개정해야 한다.

## 9.4 온라인 연계 1.3.1 (4/4) — 내부시스템 ↔ 대외MCI / 직접 대외

### FACT

> 내부시스템–대외MCI 구간 온라인은 HTTP 표준. SWIFT, EDI, 행정망 IF 서버는 대외MCI를 **거치지 않고** 시스템에서 직접 연계한다.

| No | From | To | 프로토콜 | 세션 | 역방향 |
|---|---|---|---|---|---|
| 1 | 계정계 | 대외MCI | HTTP | 없음 | 없음 |
| 2 | 정보계 | 대외MCI | HTTP | 없음 | 없음 |
| 3 | SWIFT | SWIFT | ETC | 없음 | 없음 |
| 4 | EDI | 대외기관 EDI | ETC | 없음 | 없음 |
| 5 | 행정망 IF | 행정자치 관련 기관 | ETC | 없음 | 없음 |

ANALYSIS: 표 제목이 “채널과 내부 MCI”로 남은 오기가 스캔에 있을 수 있다. 내용은 대외/기관 구간이다.

직접 경로(3~5)는 원칙 1(솔루션 단일)과 원칙 3(대외MCI가 대외 온라인/배치)의 **공식 예외**다. 1.4에 기관 목록·승인자가 없으면 현업이 유사 기관을 임의 직행할 위험이 있다.

## 9.5 파일 연계 1.3.2 — 구간별 흐름 (단말 ↔ 업무)

### FACT

> 차세대 정보시스템 파일을 송신하는 구간 중, **MFT를 이용한 파일전송은 내부 서버 TO 서버 구간에만** 적용함.

공통 주석:

- MFT Agent를 서버에 설치할 수 없으면 **EAI SFTP**로 전송
- 추후 단말 파일전송 표준 적용 여부에 따라 변경 가능

**업로드 (1/2)** 레인: 통합단말 · 단말관리서버 · 대내MCI · 업무시스템 · 대외MCI

```text
통합단말 ──솔루션 Upload(예: Image Engine)──► 단말관리서버
통합단말 ──단말 Upload 기능────────────────► 단말관리서버
단말관리서버 ↔ 대내MCI   (핸드셰이크 2~4)
단말관리서버 READ ──MFT──► 업무시스템 WRITE
```

**다운로드 (2/2)**

```text
업무시스템 READ ──MFT──► 단말관리서버 WRITE
단말관리서버 ↔ 대내MCI   (핸드셰이크)
단말관리서버 ──단말 Download / 솔루션 Download──► 통합단말
```

### ANALYSIS

파일 바이트는 MCI 세션에 태우지 않고 **MFT가 서버 간을 담당**한다. MCI는 통제·통지(핸드셰이크)에 가깝다.  
국민은행 IA의 “본거래는 MCI, 파일은 MFT”와 같은 패턴이다.

대외MCI 레인이 도식에 있으나 본 페이지 화살표의 주 경로는 내부다. 대외 파일은 1.3.3·후속 4장에서 닫아야 한다.

## 9.6 파일 연계 1.3.3 — 서버 간 흐름

### FACT (1/2) MFT

참여자: 송신 서버(MFT Agent) · MFT 서버 · 수신 서버(MFT Agent)

```text
1 파일생성
2 파일전송 API 호출 (로컬 Agent)
3 Agent → MFT 서버 전송 요청
4 MFT 서버 → 수신 Agent 파일전송
```

- 송수신 서버 모두 Agent 설치
- 요건에 따라 흐름 변경 가능

### FACT (2/2) EAI SFTP (Agent 불가)

```text
1 파일생성
2 파일전송 API 호출
3 파일거래 정보 → EAI
4 EAI(SFTP Client) GET  ← 송신 sFTP Server
5 EAI PUT               → 수신 sFTP Server
```

- 송수신에 sFTP 서버 환경 필요

### 논리와 물리의 관계 (ANALYSIS)

| 조건 | 경로 | 추가 전제 |
|---|---|---|
| Agent 설치 가능 | MFT | 원칙 1: 이 구간은 MFT만 |
| Agent 불가 | EAI SFTP | sFTP 서버·방화벽·계정. 원칙 4~5와 정합 |
| 단말↔단말관리 | 솔루션/단말 기능 | MFT 적용 구간이 아님 (1.3.2) |
