#### 4.1 인터페이스 유형

##### 4.1.1~4.1.4 (1/2)

본 PDF 미수록. 앞 구간(`195104`)에 있다. 장표 번호는 **4.1.4 배치 (1/2)** 다음이 **4.1.5 배치 (2/2)** 이다.

##### 4.1.5 배치 전송 (2/2) — 원문 p.61

**FACT**

배치 유형 중 **DB to DB (단방향 동시전송)** 은 **확장 유형**이다. **연계솔루션 담당자와 협의 후 사용**하도록 권고한다.

- 송신 테이블 → **다중** 수신 테이블
- 수신 테이블은 **Insert Only 또는 Upsert만** 가능

```text
배치 스케줄러 ──①──► 연계솔루션
연계솔루션 ──②③──► Source 송신테이블 (추출)
연계솔루션 ──⑤──► Target1, Target2 수신테이블 (동시)
연계솔루션 ──⑥──► 배치 스케줄러 (결과)
```

> **ANALYSIS:** 4.1.1의 「확장 유형 DB2DB 동시전송」의 그림이다. 기본 유형(단일 Target, 앞 PDF 4.1.4)과 달리 기본값이 아니다. 다중 적재의 부분 실패·재처리 규칙은 이 장에 없다. Insert/Upsert 제약은 기본 유형과 같다.

##### 4.1.6 디퍼드(Deferred) 전송 — 원문 p.62

**FACT**

시스템 간 **속보성**이 필요할 때 **실시간에 준하는** 전송 방식을 정의한다. 다이어그램 허브는 **polling** 이며, 배치 스케줄러 상자는 없다.

**DB to DB 단방향**

- 송신 테이블 → 단일 수신 테이블로 **여러 건을 준실시간** 전송
- 수신: Insert Only 또는 Upsert만

**DB to DB 양방향**

- 준실시간 전송 후 **결과 컬럼을 송신 측에 반영**
- 수신: Insert Only 또는 Upsert만
- 적용 예: **고객정보의 송수신 상호 간 Deferred**

```text
[단방향] Source ──①──► 연계솔루션(polling) ──②──► Target

[양방향] Source ──①──► 연계솔루션(polling) ──②──► Target
         Source ◄──④── 연계솔루션 ◄──③── Target (결과 컬럼)
```

> **ANALYSIS:** Deferred의 처리방법 코드는 3.2의 **D**다. 배치는 스케줄러가 때리고, Deferred는 솔루션이 테이블을 polling한다. 양방향은 온라인 동기 응답이 아니라 **소스 테이블 컬럼 갱신**이다. 1장의 DB-LINK 금지와 맞추면, polling도 **연계 솔루션 경유**여야 한다.

#### 4.2 거래처리 패턴

##### 4.2.1 대내MCI 패턴 (1/4~4/4) — 원문 p.64~p.67

**FACT — 정의 (p.64)**

대내MCI는 **채널과 업무시스템 간 온라인성 거래 연계**를 담당한다.

| 구간 | 번호 | 거래유형 | 설명 (FACT) |
|---|---|---|---|
| 채널–대내MCI–백엔드 | 1 | 일반거래 | 요청 전문 1 : 응답 전문 1 |
| | 2 | 대량전문거래 | 요청 후 **여러 건의 응답**이 나뉘어 채널로 여러 번 송신 |
| | 3 | 역방향(Push)거래 | 백엔드 → 채널 **일방** 메시지 |
| 채널–대내MCI | 4 | 인증거래 | 거래 전 **통합단말/자동화기기 등록정보** 확인 |
| | 5 | 로컬거래 | 백엔드로 안 감. **대내MCI와 채널** 간 |
| | 6 | 대내MCI 발생거래 | MCI **내부에서 만든 메시지**를 채널로 송신 |

**FACT — 일반거래 (p.65)**

채널(통합단말, 자동화기기, 텔레뱅킹, 전자금융)에서 조회·화면 호출 등 **단기거래**. 요청 1 / 응답 1.

```text
채널 ──요청──► 대내MCI ──► 백엔드
채널 ◄──응답── 대내MCI ◄── 백엔드
```

**FACT — 대량전문거래 (p.65)**

- 한 번 또는 다수의 요청, 한 번 또는 다수의 응답. 통합단말로 송신
- **용량이 큰 데이터를 여러 회**에 걸쳐 전송
- **분해/조립은 채널 및 백엔드**가 수행 (MCI가 조각내지 않음)

```text
채널 ──요청──► 대내MCI ──► 백엔드
채널 ◄──응답×N── 대내MCI ◄── 백엔드
```

**FACT — 역방향 Push (p.66)**

백엔드가 일방 메시지를 보낸다. 장표 채널 예: **통합단말, 자동화기기**.

```text
백엔드 ──► 대내MCI ──► 채널
```

**FACT — 인증 · 로컬 · MCI발생 (p.67)**

- **인증:** 통합단말/자동화기기 ↔ 대내MCI (백엔드 미경유). 등록정보 확인
- **로컬:** 통합단말/자동화기기 ↔ 대내MCI. 백엔드로 안 보냄
- **대내MCI 발생:** MCI가 일방 송신. 예: **장애 메시지**. 대상: 통합단말, 자동화기기, 텔레뱅킹, 전자금융

> **ANALYSIS:** 1~3은 백엔드를 타고, 4~6은 MCI에서 끝난다. 대량의 분해/조립을 MCI가 안 하므로, 3.1의 `DTL_TP`(대량 시작/중간/마지막)와 `LQN_TGR_SEQ`는 **채널·계정계 약속**이다. Push 대상이 p.66은 단말·ATM, p.67 MCI발생은 텔레·전자금융까지다. 인증은 「로그인」이 아니라 **단말 등록정보**다.

##### 4.2.2 대내MCI 주요패턴 다이어그램 (1/5~5/5) — 원문 p.68~p.73

**FACT — 단말 대량거래처리 (p.68)**

응답이 커서 한 번에 못 그릴 때, **단위로 나눠 수신·출력**한다.

1. 단말 → MCI → 계정계 요청
2. 계정계가 응답을 만들고, 대량이면 **「다음 데이터 있음」 Set**
3. 단말이 화면 출력. 더 필요하면 **GUID의 진행번호를 증가**시켜 재요청
4. 반복. 마지막은 **「최종 데이터임」 Set**

주: 다음 데이터 유무는 **일반적으로 표준 전문 헤더부**. 세부 방식은 유관팀 협의.

> **ANALYSIS:** 진행번호는 시스템공통부 `PRG_NO`다. 단말 주도 페이징이지, MCI가 스트림을 자르는 패턴이 아니다. 「다음 있음」 비트의 정확한 필드명은 이 장에 없고 협의 항목이다.

**FACT — 단말 역방향거래처리 (p.69)**

업무시스템이 단말로 데이터를 보낸다. **나중에 응답하는 경우**와 **요청 없이 일방 송신**을 포함한다.

- **일방 Push:** 계정계가 요청 데이터를 만들고 **송신할 단말 정보를 전문에 Set** → MCI가 **단말 접속상태**를 확인 → 단말 화면 출력. 단말 정보는 표준 전문 헤더. 세부 협의.
- **대외 후속 응답:** 단말이 요청 → 계정계가 **Dummy 응답** → 단말은 **본 응답 대기** → 계정계가 **대외MCI 경유**로 대외기관과 처리 → 결과를 단말 정보와 함께 Push.

주: 대외기관 연계는 **대외MCI**를 경유한다.

```text
[Push]     계정계 ──(단말정보 Set)──► 대내MCI ──(접속확인)──► 단말

[대외후속] 단말 ──요청──► … ──► 계정계 ──Dummy──► 단말(대기)
           계정계 ──► 대외MCI ──► 대외기관 ──► … ──► 계정계
           계정계 ──본응답 Push──► 대내MCI ──► 단말
```

> **ANALYSIS:** Dummy 응답은 거래공통부 세부유형 **D**와 맞는다. 4.1.3 양방향 비동기(별도 포트 응답)의 채널 쪽 구현이다. MCI는 접속 안 된 단말에 Push하지 않는다(접속상태 확인).

**FACT — 단말 책임자승인거래처리 (p.70)**

책임자 단말이 **원격**이라 **P2P가 안 될 때** 대내MCI가 중계한다.

1. 일반 단말 → MCI → 계정계 (거래 요청)
2. 계정계가 승인 필요를 판단, **승인 가능 책임자 목록**을 헤더에 담아 응답
3. MCI가 목록 중 **현재 로그인 책임자**를 반영해 일반 단말에 전달
4. 일반 단말이 책임자를 고르고 승인 요청 → MCI → 책임자 단말
5. 책임자 승인 응답 → MCI → 일반 단말
6. 일반 단말이 **승인 정보를 포함해 거래를 재요청** → 계정계가 승인 확인 후 완료

주: 승인 정보는 표준 전문 헤더. 승인 사유 등 세부는 협의.

> **ANALYSIS:** 3.1 책임자승인공통부(상태·명단)와 개별부 과정정보(지정 책임자·메시지)의 런타임이다. 「MCI가 로그인 여부를 얹는다」는 채널공통이 아니라 **세션 상태**를 MCI가 갖고 있다는 뜻이다. P2P가 가능한 점내 승인은 이 그림의 바깥이다.

**FACT — 단말 로컬거래처리 (p.71)**

백엔드(계정계 등)를 **호출하지 않고** 대내MCI 내부 정보로 응답한다. 예: **단말 로그인 상태 정보 조회**.

```text
통합단말 ──거래시작──► 대내MCI (내부 정보 조회 → 응답 생성)
통합단말 ◄──거래종료── 대내MCI
```

**FACT — 자동화기기 개국거래 (p.72~p.73, 다이어그램 1/2~2/2)**

자동화기기는 **개국거래를 마쳐야 사용 가능**하다. **관리서버가 SESSION KEY를 주고**, 이후 전문 암·복호에 쓴다.

구간은 **자동화기기 ↔ 관리서버 ↔ 계정계**다. 시퀀스는 (1) 관리서버가 세션을 열고 단말을 인지한 뒤 계정계로 넘기고, (2) 계정계가 기기번호 등으로 인증·개국 처리를 한 뒤 응답이 관리서버를 거쳐 기기로 돌아가 **사용 가능 상태**가 된다. 장표 시퀀스에는 구간별 암호·MAC·압축 단계가 표시된다.

> **ANALYSIS:** 개국은 4.2.1의 **인증거래**를 ATM에 풀어 쓴 것이다. 업무 거래 전에 관리서버 세션이 없으면 1.3.1 TCP 단말이라도 계정계에 못 간다. 암호 알고리즘·키 유도의 구현 세부는 이 분석의 대상이 아니고, 원문 시퀀스 장표를 따른다.

##### 4.2.3 대외MCI 패턴 (1/4~4/4) — 원문 p.74~p.77

**FACT — 유형 표 (p.74)**

대외MCI는 **대외기관과의 연계**를 담당한다.

| 서비스 | 세부 | 패턴 | 거래 유형 (FACT) |
|---|---|---|---|
| 온라인 | 당발(취급) | 요청 | 내부 → 대외기관 요청 송신 |
| | | 응답 | 대외기관 → 내부 응답 수신 |
| | 타발(개설) | 요청 | 대외기관 → 내부 요청 수신 |
| | | 응답 | 내부 → 대외기관 응답 송신 |
| | 당발(취급) | 통지 | 내부 → 대외 일방 통지 |
| | 타발(개설) | 통지 | 대외 → 내부 일방 통지 |
| 일괄전송 | 송신 | 파일 | 대외MCI가 대외기관에 **접속(개시/로그인) 후** 파일 송신 |
| | 수신 | 파일 | 대외기관이 대외MCI에 **접속(개시/로그인) 후** 파일 수신 |

**FACT — 온라인 양방향 (p.75)**

- 요청–응답 양방향
- 대외기관 거래요청은 **Async**
- **코어뱅킹은 대외MCI와 직접** 연계
- **그 외 단위시스템은 EAI** 경유
- **당발:** 타임아웃·전문 유효성 오류 시 **대외MCI가 대행응답**

```text
[당발 코어] 코어뱅킹 ↔ 대외MCI ↔ 대외기관
[당발 단위] 단위시스템 ↔ EAI ↔ 대외MCI ↔ 대외기관
[타발 코어] 대외기관 ↔ 대외MCI ↔ 코어뱅킹
[타발 단위] 대외기관 ↔ 대외MCI ↔ EAI ↔ 단위시스템
```

**FACT — 온라인 단방향 통지 (p.76)**

필요 시 전송 확인용 **dummy Ack**를 쓴다.

```text
[당발 통지] 내부(코어 또는 EAI←단위) ──► 대외MCI ──► 대외기관
[타발 통지] 대외기관 ──► 대외MCI ──► 내부
```

**FACT — 일괄전송 (p.77)**

- 내부 업무시스템 ↔ 대외MCI 파일: **EAI**
- 대외기관 ↔ 대외MCI: 협약에 따라 **TCP/IP 일괄전송 또는 sFTP**
- 인터넷(공용망): **대외 IF** 경유
- 파일: **DAT + CHK**. 송신은 MCI가 CHK 확인 후 DAT 송신. 수신은 업무가 CHK 확인 후 처리
- 송·수신 결과는 **대외MCI DB**에 관리

```text
[송신] 업무 --EAI--> 대외MCI --(전용선 | 공용망+대외IF)--> 대외기관
[수신] 대외기관 --(전용선 | 공용망+대외IF)--> 대외MCI --EAI--> 업무
```

> **ANALYSIS:** 거래공통부 대외구분 1~4(개설요청/응답, 취급요청/응답)가 이 표의 타발/당발 요청·응답이다. 코어만 대외MCI 직행은 1장 「거래당 솔루션 1개」와 맞는다. 단위시스템이 대외MCI에 직접 붙이면 패턴 위반이다. 대행응답은 대외 타임아웃을 내부가 무한 대기하지 않게 한다. DAT/CHK는 1.3.6~1.3.7 「파일 완료 후 전문」과 같은 완료 신호다. 내부 파일 기본이 MFT인 1.3과 겹치면, **대외 구간 파일은 EAI**로 읽는 것이 이 장표다.

##### 4.2.4 EAI 패턴 (1/4) — 원문 p.78

**FACT**

- **동기** 온라인: **TCP/IP 또는 HTTP Connector**
- **비동기** 온라인: **Socket Connector**

**동기거래**

```text
송신(Client Adapter, TCP/IP 또는 HTTP)
    ↔ EAI (Flow Controller, Source/Target Connector)
    ↔ 수신(Server Adapter, TCP/IP 또는 HTTP)
```

- 수신 장애·타임아웃 시 **EAI가 송신에 대행응답**
- EAI는 수신시스템에 **주기적 헬스체크**

**비동기거래**

```text
송신(Client Adapter, TCP/IP)
    → EAI (Source Connector → Queue → Target Connector)
    → 수신(Server Adapter, TCP/IP)
```

- 내부 **Queue로 전송 보장**
- 송신은 **EAI 통신 오류 외에는 확인 불가**. **수신 확인이 필요한 거래에는 사용하지 않는다.**

**본 PDF에 없는 것:** 4.2.4 (2/4)~(4/4) — 배치·파일·Deferred의 EAI 쪽 패턴으로 추정.

> **ANALYSIS:** 4.1.2 양방향 동기의 「정합성」은 여기 헬스체크·대행응답과 한 세트다. 4.1.3 단방향 비동기의 「타임아웃 없음」은 EAI Queue fire-and-forget과 같다. 수신확인이 필요하면 동기이거나, 별도 양방향 비동기(원 거래 GUID)를 써야 한다.

## 4. GAP 및 리스크

| 구분 | 내용 |

| 배치 확장 | 동시전송은 권고가 「협의 후」뿐이라, 미협의 다중 Target이 운영에 들어갈 수 있다. |
| Deferred vs 온라인 | 고객정보 Deferred를 온라인 동기처럼 설계하면 polling 지연이 SLA를 깨뜨린다. |
| 대량 + 진행번호 | GUID 진행번호를 안 올리면 같은 페이지가 반복되거나 유실된다. 헤더 플래그 미합의 시 채널마다 다르게 구현된다. |

## 5. 설계 시 체크리스트 (원문 기준)

원문 문장을 설계 질문으로 바꾼 것이다. 장표에 없는 항목은 넣지 않았다.

- [ ] DB2DB 다중 Target이면 확장 유형으로 솔루션 담당자와 협의했는가
- [ ] 수신 테이블이 Insert 또는 Upsert뿐인가 (배치·Deferred 공통)
- [ ] Deferred면 스케줄러가 아니라 polling인가. 양방향이면 결과 컬럼 반영인가
- [ ] 대내 거래가 6유형(일반/대량/Push/인증/로컬/MCI발생) 중 어디에 속하는가
- [ ] 대량이면 분해/조립이 채널·백엔드이고, 단말이 GUID 진행번호를 올리는가
- [ ] Push면 MCI가 단말 접속을 확인하는가. 대외 후속이면 Dummy 후 본응답 Push인가
- [ ] 책임자 원격이면 MCI 중계 후, 승인 정보를 넣어 **재요청**하는가
- [ ] 로컬이면 계정계를 안 치는가 (로그인 상태 조회 등)
- [ ] ATM이면 개국·SESSION KEY 이후 업무 거래인가
- [ ] 대외 온라인이 당발/타발 × 요청응답/통지 중 어디인가. 요청은 Async인가
- [ ] 코어는 대외MCI 직접, 단위시스템은 EAI인가
- [ ] 당발 타임아웃·유효성 오류에 대외MCI 대행응답이 있는가
- [ ] 통지에 dummy Ack가 필요하면 쓰는가
- [ ] 대외 파일이 DAT+CHK인가. 내부 EAI, 대외 TCP/IP 일괄 또는 sFTP, 인터넷이면 대외 IF인가
- [ ] EAI 동기가 TCP/IP 또는 HTTP이고, 장애 시 대행응답·헬스체크가 있는가
- [ ] EAI 비동기는 Queue이며, 수신확인 필요 거래에는 안 쓰는가
