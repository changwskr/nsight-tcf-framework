## 1. 핵심 결론

이 PDF는 같은 IA 정의서의 **4.2.4 EAI 패턴 나머지(파일·DB·Deferred)와 제5장 로그, 제6장 관리체계** 이다. 워터마크는 `KB S010781 / 2020-09-11 16:01`이다.

장표가 직접 제시하는 핵심은 다음과 같다.

```text
EAI 4.2.4 (이 PDF)
  파일 : FTP/sFTP 또는 MFT. 스케줄러 → Get → Queue → Put
  DB   : JDBC Fetch → 파일 → 송신 Flag Update → Upsert (Read/Upsert 반복)
  Deferred : DB2DB만. File2File은 배치.
             트리거는 스케줄러가 아니라 Deferred Controller
             이후 JDBC 흐름은 DB 배치와 동일

로그 (5장)
  4지점 × GUID : 요청 수신 즉시 / 요청 전달 직전 / 응답 수신 즉시 / 응답 전달 직전
  온라인 성능에 영향 없게. 채널접속이력은 EAI DB2DB로 업무 저장소
  대내MCI: 전문 / 시스템 / 에러. DB+파일. 시간 단위 rollover → YYYY-MM-DD
  정책: 일 단위, 영구. 은행 정책으로 변경 가능
        전문=파일/DB·전문전체, 에러=파일/DB·평문, 시스템=파일·평문

관리 (6장)
  개발: 요건→협의→EIMS 등록→MCI/EAI 적용→단위/종합 테스트
  표준전문: 시스템 헤더 vs 거래 헤더. AA·EAMS·요청팀.
            타당성 N이면 미반영. 반영은 EIMS 배포 후 업무 설계
            시스템 헤더는 기술혁신위원회 소집
```

1장의 MFT 우선과 4.2.4 파일 패턴의 「FTP/sFTP **또는 MFT**」가 여기서 만난다. Deferred는 4.1.6 polling과 같이 **준실시간 DB2DB**이고, 구현은 JDBC+임시파일+Flag다.

### 4. 유형별 인터페이스 방식

#### 4.2.4 EAI 패턴 (2/4~4/4)

(1/4 온라인 Sync/Async는 앞 PDF p.78.)

##### 파일 연계 패턴 (2/4) — 원문 p.79

**FACT**

실시간 전문으로 처리할 수 없는 FILE을 전송한다. **FTP/sFTP 방식 또는 MFT 방식**으로 데이터를 전달한다. 장표 다이어그램은 **FTP/sFTP, EAI 허브 경유**다.

```text
배치 스케줄러 ──①──► EAI Batch Service
Batch Service ──②──► Source Connector (FTP/sFTP)
Source Connector ──③ Get──► 송신 FTP/sFTP Server
Source Connector ──④──► EAI 내부 Queue
Batch Service ──⑤──► Target Connector (FTP/sFTP)
Target Connector ──⑥ Read──► Queue
Target Connector ──⑦ Put──► 수신 FTP Server
```

> **ANALYSIS:** 1.3은 내부 파일을 **MFT 우선, 불가 시 EAI sFTP**로 둔다. 이 장표는 둘 다 허용하고, 그린 것은 EAI Get/Put이다. MFT를 타면 Queue 그림이 그대로 적용되지 않을 수 있다. 디렉터리 전체 전송(4.1.4)과 Get/Put 한 건은 운영에서 맞춰야 한다.

##### 디비 연계 패턴 (3/4) — 원문 p.80

**FACT**

실시간 전문으로 처리할 수 없는 DB 데이터. **다량 레코드 Insert**, 또는 변경분 **Upsert**.

```text
배치 스케줄러 ──①──► Batch Service ──②──► JDBC Source Connector
JDBC Source ──③ Fetch──► 송신 Table (Query)
         ──④──► 임시 파일 (건수는 EAI 관리정보)
         ──⑤──► 송신 레코드 Flag Update
Batch Service ──⑥──► JDBC Target Connector
JDBC Target ──⑦ Read 파일 ──⑧ Upsert──► 수신 Table
              (건수·작업량에 따라 ⑦⑧ 반복)
```

> **ANALYSIS:** 4.1.4의 Insert/Upsert only와 같다. Flag를 Fetch 성공 후 올리므로, Target Upsert 실패 시 소스는 이미 처리됨으로 남을 수 있다. 재처리·보상은 이 장에 없다. DB-LINK가 아니라 JDBC 커넥터다.

##### 디퍼드 연계 패턴 (4/4) — 원문 p.81

**FACT**

송신 DB **변경분**을 **준실시간**으로 받을 때 쓴다. **DB to DB만.** **File to File은 배치**로 처리한다.

흐름은 DB 배치(p.80)와 같고, 트리거만 **배치 스케줄러 → Deferred Controller** 로 바뀐다. 소스 테이블에 Key / Data / Flag. Fetch 후 Flag Update, Target Upsert, ⑦⑧ 반복.

p.82는 목차에서 **5. 로그 관리 · 5.1 로그 구성** 강조.

> **ANALYSIS:** 4.1.6 polling과 이 JDBC 루프가 같은 Deferred다. Controller가 주기적으로 Batch Service를 때리는 것이 polling의 구현이다. 파일 Deferred는 없다고 못 박았으므로, 준실시간 파일은 이 패턴 밖이다.

### 5. 로그 관리

#### 5.1 로그 구성 — 원문 p.83

**FACT**

연계 시스템을 경유하는 **요청/응답(In/Outbound) 전송 정보와 채널 접속 이력**을 기록하고, 연계 저장소와 업무 시스템으로 전달한다.

```text
요청: inbound Adapter ──변환/매핑──► outbound Adapter
응답: (반대 방향, 동일 Adapter)
        │  로그 기록 × 4
        ▼
   로그처리기 ──► 연계솔루션 DB
                    ├─ 인터페이스 로그 저장소 ──► 관리/모니터링
                    └─ 채널접속이력 저장소 ──EAI DB2DB──► 업무 접속이력 조회
```

**연계 절차**

1. 로그 정보 기록. 고려: **온라인 거래 처리에 영향이 없게.** 채널 접속 이력은 로그에서 **분리 추출**
2. 연계시스템 DB에 로그·접속 이력 저장
3. 채널 접속 이력은 **EAI DB2DB** 등으로 업무 저장소 전송
4. 운영자는 관리도구로 전송 이력 확인
5. 업무 담당자는 업무 시스템 접속이력 저장소에서 확인

**관리방안 — 4지점, GUID 추적**

1. 요청 전문을 **전달받은 즉시**
2. 요청 전문을 **목적지로 전달하기 직전**
3. 응답 전문을 **전달받은 즉시**
4. 응답 전문을 **요청지로 전달하기 직전**

p.84는 목차(5장 강조).

> **ANALYSIS:** 4지점은 5.3의 SRC수신 / TGT송신 / TGT수신 / SRC송신과 같다. GUID는 3.1 시스템공통부 38자다. 접속이력을 전문 로그와 분리하고 DB2DB로 넘기는 것은, 채널 감사와 I/F 추적을 저장소를 나눈 것이다. 「온라인에 영향 없게」는 동기 경로에서 로그 I/O를 빼라는 설계 제약이다.

#### 5.2 로그 생성 (1/2~2/2) — 원문 p.85~p.86

**FACT — 대내MCI**

로깅은 **DB/파일 기반**. 종류:

| 번호 | 로그종류 | 대상 (FACT) |
|---|---|---|
| ① | 전문로그 (입출력) | 입출력전문 |
| ② | 시스템로그 | 솔루션 내부 로그 |
| ③ | 에러로그 | 발생한 에러 정보 (오류 처리용) |

구성: 채널(고객/내부) ↔ **MCI Core** (Log Manager, Error HDR) ↔ 업무시스템. 저장: **DB Log / File Log**.

**FACT — 파일 디렉터리 (원문 표기)**

| 경로 (원문) | 종류 | 설명 |
|---|---|---|
| `chanel.log` | ① 입출력 | 현재시간 입출력 |
| `adaptor.log` | ① 입출력 | 현재시간 입출력 |
| `gateway.log` | ② 시스템 | 현재시간 시스템 |
| `controller.log` | ② 시스템 | 현재시간 시스템 |
| `error_handler.log` | ③ 에러 | 현재시간 에러 |
| `YYYY-MM-DD/` | ①②③ | **1시간 단위 rollover** 후 이동·백업 |

> **ANALYSIS:** 5.2는 **대내MCI**만 디렉터리까지 푼다. EAI·대외MCI 경로명은 5.3 정책 표에만 있다. `chanel.log`는 원문 철자다. rollover가 1시간인데 5.3 작성 단위는 **일**이라, 파일 쪼개기와 보관 단위가 다르다.

#### 5.3 로그 관리 정책 — 원문 p.87~p.88

p.87 목차에서 **5.3** 강조.

**FACT (p.88)**

로그 저장 대상·매체·작성 단위·보관 주기는 아래와 같으며 **KDB산업은행 정책에 따라 변경이 가능**하다.

| 종류 | 시스템 | 저장 대상 | 매체 | 보안 적용 | 작성 단위 | 보관 |
|---|---|---|---|---|---|---|
| 전문 로그 | EAI / 대내MCI / 대외MCI | SRC수신, TGT송신, TGT수신, SRC송신 | 파일/DB | 송수신 **전문전체** | 일 | **영구** |
| 에러 로그 | 동상 | 오류 처리분 | 파일/DB | **평문** | 일 | 영구 |
| 시스템 로그 | 동상 | 각 솔루션 내부로그 | **파일** | **평문** | 일 | 영구 |

> **ANALYSIS:** 전문 로그에만 「전문전체」보안이 걸리고, 에러·시스템은 평문이다. 오류 전문이 에러 로그로만 남으면 마스킹이 빠질 수 있다. 영구 보관은 용량·개인정보 정책과 충돌할 수 있어, 장표 자체가 은행 정책으로 바꿀 수 있다고 열어 두었다. MFT 전용 로그 행은 없다.

### 6. 연계 아키텍처 관리체계

#### 6.1 개발 프로세스 — 원문 p.89~p.90

p.89 목차에서 **6.1** 강조.

**FACT — 연계업무 개발 절차 (p.90)**

| 단계 | 내용 (FACT) | 주 수행 |
|---|---|---|
| 1 | 연계 요건 정의 | 업무담당 개발자 → MCI/EAI 담당 |
| 2 | 연계 요건 협의 | MCI/EAI 담당 ↔ 연계대상 시스템담당 |
| 3 | 연계 방안 정의 | 연계대상 시스템담당 |
| 4 | 연계 방안 협의·확정 | MCI/EAI 담당 ↔ 업무담당 개발자 |
| 5 | 연계 정보 등록 | 업무담당 개발자 → **EIMS** |
| 6 | 연계 정보 적용 | EIMS → MCI/EAI |
| 7 | 개발요건 적용 | MCI/EAI 담당 |
| 8 | 단위 테스트 | 업무 시스템 |
| 9 | 종합 테스트 | 업무 + MCI/EAI + 연계 대상 |

> **ANALYSIS:** 1.3.9 EIMS 등록→형상관리 배포와 6.1 5~7이 같다. 개발자가 EIMS에 먼저 넣고, 솔루션 담당자가 관리도구 설정(복합거래·인코딩)을 적용한다. 종합 테스트 없이 운영 배포하면 6.1을 건너뛴 것이다.

#### 6.2 표준전문 관리 — 원문 p.91~p.95

p.91 목차에서 **6.2** 강조.

두 갈래다. **시스템 헤더부** 신규/변경(p.92 흐름, p.93 표)과 **거래 헤더부** 신규/변경(p.94 흐름, p.95 표). 단계는 19개로 같고, 위원회 소집 문구가 갈린다.

**FACT — 공통 골격**

```text
요청팀 신규/변경 요청
    → EAMS: AA/DA/TA/SA 영역 검토
    → AA: 필요성·영향도, 검토 요청
    → 타당성 검토 ──N──► 미반영 통보 (종료)
                    └──Y──► 전문변경의뢰서 → EAMS 전달 → AA 수신
    → AA: 설계 반영, 전행 일정 통보
    → 관련팀 확인, 요청팀 수용여부 ──N──► 의뢰 보정 루프
                                    └──Y──► AA: EIMS 등록·배포
    → 테스트 확인 → 업무 시스템 설계 반영
```

**FACT — 수행 역할**

| 역할 | 하는 일 (FACT) |
|---|---|
| 요청팀 | 요청, 의뢰서, 수용 판단, 업무 설계 반영 |
| 관련팀 | 검토, 변경 확인, 테스트, 업무 반영 |
| EAMS 담당 | 아키텍처 영역 검토, 의뢰서 전달 |
| AA (표준전문관리자) | 영향도, 회의/위원회 소집, 산출물, EIMS 배포 |
| 기술혁신위원회 | **시스템 헤더** 표에서 검토·소집·타당성 회의에 명시 |

**FACT — 시스템 헤더 vs 거래 헤더 (차이)**

| 항목 | 시스템 헤더부 (p.93) | 거래 헤더부 (p.95) |
|---|---|---|
| 6번 | **기술혁신위원회 소집** | **회의 소집** |
| 5·7·8번 수행 | 요청팀 / **기술혁신위원회** / 관련팀 | 요청팀 / 관련팀 |
| 17번 | **EIMS** 전문 적용 및 배포 (통합전문관리 시스템) | 동일 |

p.96은 본문 없는 공란.

> **ANALYSIS:** 시스템공통부(200) 변경은 전 채널에 파급되므로 위원회가 붙고, 거래공통부(250)는 관련팀 회의로 낮춘 읽기가 장표와 맞다. 개별부 업무 IO 변경은 이 19단계의 대상이 아니다(6.1 EIMS 등록에 가깝다). EAMS는 영향도·문서 전달, EIMS는 런타임 배포다. 1.3.9 형상관리 승인은 17번 배포 안에 들어가는 것으로 읽는 것이 자연스럽다.

## 3. 원문 장표에 없는 것 (명시)

- MFT 파일 패턴의 별도 시퀀스 (허용만 명시, 그림은 FTP/sFTP)
- DB/Deferred Flag 실패 시 재처리, 중복 Upsert 키
- EAI·대외MCI 로그 디렉터리명, MFT 로그 행
- 전문 로그 「전문전체」보안의 알고리즘·키
- 영구 보관의 매체 계층(디스크/테이프)
- 6.1과 ITSM/형상관리 티켓의 매핑

## 4. GAP 및 리스크

| 구분 | 내용 |
|---|---|
| 파일 이중 경로 | MFT와 EAI sFTP가 둘 다 열려 원칙 1(구간당 솔루션 1개)과 충돌할 수 있다. |
| Flag 선행 | Fetch 후 Flag Update, 그다음 Upsert. Target 실패 시 소스 재추출이 안 된다. |
| Deferred vs 배치 | 흐름이 거의 같아 Controller만 바꾸면 배치로 오인하기 쉽다. File Deferred 없음. |
| 로그 성능 | 4지점 전문전체를 동기로 쓰면 5.1 「온라인 영향 없게」를 깨뜨린다. |
| 평문 에러로그 | 오류 전문이 에러 로그에 평문으로 남을 수 있다. |
| 보관 영구 vs 1시간 파일 | rollover 파일과 영구 DB의 삭제/이관 규칙이 없다. |
| 시스템 헤더 | 위원회를 건너뛴 헤더 변경은 전 거래 파싱을 깨뜨린다. |
| EIMS 없이 적용 | 6.1·6.2 배포를 운영기 수동 반영하면 Dev/Test/Prod가 갈라진다. |

## 5. 설계 시 체크리스트 (원문 기준)

- [ ] EAI 파일이 FTP/sFTP Get–Queue–Put인가, MFT인가 (한 거래에 둘 다 아닌가)
- [ ] DB 배치가 Fetch→파일→Flag→Upsert이고, ⑦⑧을 건수만큼 반복하는가
- [ ] Deferred면 DB2DB만인가. 트리거가 Deferred Controller인가. File은 배치인가
- [ ] 로그 4지점(요청 입·출, 응답 입·출)이 GUID로 붙는가
- [ ] 로깅이 온라인 거래 지연을 안 만드는가. 접속이력은 DB2DB로 업무에 가는가
- [ ] 대내MCI 전문/시스템/에러가 DB+파일이고, 시간 rollover 후 일자 디렉터리인가
- [ ] 전문 로그는 파일/DB·전문전체 보안, 에러는 평문, 시스템은 파일 평문인가
- [ ] 보관이 일 단위·영구인가. 은행 정책 변경을 반영했는가
- [ ] 신규 I/F가 요건 협의 → EIMS → 솔루션 적용 → 단위/종합 테스트인가
- [ ] 시스템 헤더 변경에 기술혁신위원회가 있는가. 타당성 N이면 미반영인가
- [ ] 반영이 EIMS 배포 후 테스트·업무 설계까지 갔는가
