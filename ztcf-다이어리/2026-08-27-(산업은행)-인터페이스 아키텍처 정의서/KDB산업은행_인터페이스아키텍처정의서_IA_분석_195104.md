## 1. 핵심 결론

이 PDF는 같은 IA 정의서의 **제3장 연계 표준(3.1 표준전문 레이아웃, 3.2 인터페이스 ID)과 제4장 유형의 앞부분(4.1.1~4.1.4 1/2)** 이다. 워터마크는 `KB S010781 / 2020-09-11 16:01`이다.

장표가 직접 제시하는 핵심은 다음과 같다.

```text
표준전문 (전부 FLAT)
  입력:  시스템(200) + 거래(250) + 채널(500) + 책임자승인(가변)
         + 개별(입력, 가변) + 종료(2, @@)
  출력:  위와 동일 + 메시지공통(가변)  [헤더 안, 개별부 앞]

채번
  인터페이스 ID  12 = 시스템(3) + 처리(1: O/B/D/E) + 일련(8, EIMS)
  입출력(IO) ID  12 = 구분(1: M대내/E대외) + 시스템(3) + S/T(1) + 일련(7, EIMS)

유형 (4.1)
  온라인 동기   : 양방향 / 양방향 집합(머지)
  온라인 비동기 : 단방향 / 단방향 다중 / 양방향(대외계, 별도 포트 응답)
  배치          : FILE2FILE, DB2DB, DB2DB 동시전송
  Deferred      : DB To DB 단방향 / 양방향(결과 컬럼)
```

숫자 필드는 **leading-zero**, 문자 필드는 **trailing-space**다. 반복 데이터가 없으면 건수를 **`00`**으로 두고 **반복 컬럼은 채우지 않는다.**

추적 키는 시스템공통부의 GUID다. `전문생성시스템(3)+작성일(8)+시분초(9)+생성고유ID(10)+전문고유ID(8) = 38`. 비동기면 **원 거래 GUID(38)** 에 최초 거래 GUID를 넣는다.

4.1은 **연계 솔루션을 허브로 둔 패턴 카탈로그**다. 1장의 「어느 구간에 MCI/EAI/MFT인가」와 맞춰 읽어야 한다. **4.1.4 배치 (2/2)·Deferred 다이어그램·4.2 거래처리 패턴은 본 PDF에 없다.**

**FACT — 제약**

- 숫자 필드: **leading-zero**
- 문자 필드: **trailing-space**
- 반복부 데이터가 없으면 건수 **`00`**, 해당 반복 컬럼은 세팅하지 않음

**FACT — 필수여부 기호**

| 기호 | 의미 (원문) |
|---|---|
| ○ | 데이터 생성 |
| ● | 생성된 데이터 유지 |
| △ | 필요 시 데이터 생성 |
| ▲ | 생성된 데이터 유지 (필요 시) |

표의 필수 열은 **요청 / 응답** 쌍이다.

> **ANALYSIS:** 표준전문은 XML/JSON이 아니라 **고정 오프셋 FLAT**이다. 가변부는 책임자승인·메시지·개별부다. 출력만 메시지공통부가 있는 것은, 오류/안내를 응답 헤더에 싣는 모델이다. 반복 `00`+미설정은 길이 계산(`WHL_TGR_LEN`, `STN_HED_LEN`)과 한 세트다. 앞 PDF 1.3.8의 Meta IO 길이(UTF-8 1.5배)는 이 FLAT 필드 길이에 바로 붙는다.

#### 3.2 인터페이스 ID 구성 — 원문 p.55

**FACT — 인터페이스 ID (12)**

```text
[시스템코드 3][처리방법 1][일련번호 8]
     │              │            └─ EIMS 채번
     │              └─ O 온라인 / B 배치 / D 디퍼드 / E 기타
     └─ 코드관리시스템 등록 3자리
예: FRWO00000001 , FRWB00000002 , FRWD00000003
```

**FACT — 입출력(IO) ID (12)**

```text
[구분 1][시스템코드 3][소스/타겟 1][일련번호 7]
   │         │            │            └─ EIMS 채번
   │         │            └─ S 소스 / T 타겟
   │         └─ 코드관리시스템 등록 3자리
   └─ M 대내 I/O / E 대외연계 I/O
예: MFRWT0000001 , MFRWS0000002
```

p.56은 목차(4장 강조).

> **ANALYSIS:** 채번은 EIMS다. 1.3.9의 「등록→형상관리 배포」와 3.2는 같은 원장이다. 처리방법 O/B/D는 4.1 유형과 대응하고, **E 기타**는 1.4 예외 경로의 ID 여지다. 거래공통부 `IF_ID` 10자와 여기 12자의 절단·별도키 여부는 원문에 없다. IO ID의 S/T는 EAI 매핑 단위이고, 인터페이스 ID는 거래/배치 단위로 읽는 것이 자연스럽다.

### 4. 유형별 인터페이스 방식

p.56 목차에서 **4. 유형별 인터페이스 방식**이 강조된다.

#### 4.1 인터페이스 유형

##### 4.1.1 인터페이스 유형 정의 — 원문 p.57

**FACT**

| 구분 | 상위 | 하위 | 설명 (FACT) |
|---|---|---|---|
| 온라인 | 동기 전송 | 양방향 동기전송 | 요청한 포트/서비스로 수신측이 응답 |
| | | 양방향 동기 집합전송 | 한 요청에 여러 수신 응답을 **머지**해 송신측에 **EAI가** 전송 |
| | 비동기 전송 | 단방향 비동기 전송 | 송신→수신 단방향 전문 |
| | | 단방향 비동기 다중전송 | 한 송신→여러 수신 |
| | | 양방향 비동기 전송 | 요청 후 **다른 포트/서비스**로 응답. 예: **대외계** |
| 배치 | 기본 | FILE2FILE 단방향 | 파일 배치 |
| | 기본 | DB2DB 단방향 | 송신 DB → 단일 수신 DB |
| | 확장 | DB2DB 단방향 동시전송 | 송신 DB → **다중** 수신 DB |
| Deferred | DB To DB | 단방향 | 준실시간, 단일 수신 |
| | | 양방향 | 준실시간 후 **결과 컬럼 반영** |

비고: **연계 솔루션별로 유형 지원에 차이가 있을 수 있다.**

##### 4.1.2 온라인 동기 전송 — 원문 p.58

**FACT — 양방향 동기**

- 요청한 포트/서비스로 응답
- **정합성 보장이 필요한 요건**

```text
Source ──①──► 연계솔루션 ──①──► Target
Source ◄──②── 연계솔루션 ◄──②── Target
```

**FACT — 양방향 동기 집합전송**

- 한 요청 → 다수 Target → 솔루션이 응답 머지 → Source

```text
Source ──► 연계솔루션 ──①──► Target1, Target2
           연계솔루션 ◄──②── Target1 (응답1)
           연계솔루션 ◄──③── Target2 (응답2)
Source ◄──  (머지 후 1건)
```

##### 4.1.3 온라인 비동기 전송 — 원문 p.59

**FACT — 단방향 비동기**

- 송신→수신 단방향
- **타임아웃 관리 없음.** Target **ACK**를 받으면 타임아웃 관리 가능

**FACT — 단방향 비동기 다중**

- 한 Source → 여러 Target (동일하게 타임아웃 없음, ACK 시 가능)

**FACT — 양방향 비동기**

- 수신 측이 요청을 받은 **즉시 세션 종료**
- 처리 결과는 **다른 포트/서비스**로 응답
- **대외기관 전문 송·수신에 주로 적용**

```text
Source ──①요청──► 연계솔루션 ──► Target     (세션 종료)
Source ◄──②응답── 연계솔루션 ◄── Target     (별도 포트)
```

##### 4.1.4 배치 전송 (1/2) — 원문 p.60

**FACT — DB to DB 단방향**

- 송신 테이블 → 단일 수신 테이블
- 수신 테이블은 **Insert Only 또는 Upsert만** 가능

**FACT — File to File**

- 송신 시스템 → 수신 시스템 파일 배치
- **Directory 단위** 전송 가능. 디렉터리 안 **일부 선택 전송은 불가**(전체 파일)

**FACT — 공통 흐름 (스케줄러 + 연계 솔루션)**

```text
배치 스케줄러 ──①──► 연계솔루션
연계솔루션 ──②──► Source (추출/읽기)
Source ──③──► 연계솔루션 ──④──► Target (적재/쓰기)
연계솔루션 ──⑤──► 배치 스케줄러 (결과)
```

**본 PDF에 없는 것:** 4.1.4 장표 번호의 (2/2)는 후속 장표에서 **4.1.5 배치 전송 (2/2)** 로 이어진다. Deferred 다이어그램도 후속.

## 5. 설계 시 체크리스트 (원문 기준)

원문 문장을 설계 질문으로 바꾼 것이다. 장표에 없는 항목은 넣지 않았다.

- [ ] 입력이 시스템200+거래250+채널500+책임자(가변)+개별+`@@` 인가
- [ ] 출력에 메시지공통부(가변)가 헤더에 들어가는가
- [ ] 숫자는 leading-zero, 문자는 trailing-space 인가
- [ ] 반복 없으면 건수 `00`이고 반복 컬럼을 안 넣는가
- [ ] GUID 38자(생성시스템+일시+생성고유+전문고유)가 요청에서 생성되고 응답에서 유지되는가
- [ ] Async이면 원 거래 GUID에 최초 GUID를 넣는가
- [ ] 환경코드가 L/D/T/R 중 실제 구간과 맞는가
- [ ] 요청/응답/푸시(Q/R/P)와 세부유형(대량 1/2/3/9, Dummy D, Push S/M)이 맞는가
- [ ] Sync/Async(S/A)가 4.1 유형과 같은가
- [ ] 결과 0/1/3 중 Timeout을 MCI가 넣는가
- [ ] 대외면 개설/취급(1~4)과 1·2차 기관코드, 대외거래ID를 채우는가
- [ ] IF_ID·EAI 노드(비동기)·MCI 세션ID가 해당 솔루션 경로에 있는가
- [ ] 인터페이스 ID 12자가 시스템3+O/B/D/E+EIMS 일련8인가
- [ ] IO ID 12자가 M/E + 시스템3 + S/T + EIMS 일련7인가
- [ ] 온라인 집합전송이면 EAI가 다수 응답을 머지하는가
- [ ] 비동기는 기본 타임아웃 없음인가, ACK가 있으면 타임아웃을 쓰는가
- [ ] 대외 양방향 비동기는 요청 세션 종료 후 다른 포트로 응답하는가
- [ ] DB2DB 수신이 Insert 또는 Upsert 뿐인가
