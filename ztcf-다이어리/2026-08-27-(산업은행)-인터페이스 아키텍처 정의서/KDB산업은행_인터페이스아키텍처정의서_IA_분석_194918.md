## 1. 핵심 결론

이 PDF는 같은 IA 정의서의 **제1장 설계기준 나머지(파일 연계 1.3.4~1.3.7, 인코딩 1.3.8, EIMS 1.3.9)와 예외(1.4), 제2장 연계 구성도(2.1.1~2.1.3)** 이다. 표지 워터마크는 `KB S010781 / 2020-09-11 16:00`으로 앞 PDF와 같다.

장표가 직접 제시하는 핵심은 다음과 같다.

```text
파일 연계 (구간별)
  단말 ──► 단말관리서버 ──► [MFT 우선 / 불가 시 EAI sFTP] ──► 업무서버
  업무서버 ──► [MFT / EAI] ──► 대외MCI (──► 대외중계서버, 인터넷 대외)
  대외 ──► 대외중계서버 GET ──► 대외MCI ──► [MFT / EAI] ──► 업무서버

인코딩
  기본 변환 = I/F 솔루션 (필드 단위 설정)
  복합필드·업무로직 = 업무팀
  Meta IO 길이: KSC5601 주소 20 → UTF-8 30 (1.5배) 등

전문 배포
  EIMS 등록 → 형상관리 승인·배포 → 각 시스템 적용 → 테스트
```

채널 파일은 **단말이 솔루션에 직접 PUT/GET하지 않는다.** 단말관리서버가 중간 저장소이고, 서버 구간만 MFT 또는 EAI가 담당한다.

예외는 두 갈래다. **범용단말(IBOS)에서 솔루션 웹을 링크하면 MCI를 건너뛰고 HTTP로 WAS에 직행**할 수 있다. **신규·재구축이 아닌 부분개발·대응개발·유지 도메인**은 표준 전문·프로토콜을 강제하지 않는다.

제2장 구성도는 앞 PDF 1.1.2 레이어를 **모듈 단위 그리드**로 펼친다. 대내MCI는 창구·자동화·인터넷·모바일·콜센터·파트너 채널을, 대외MCI는 X.25·TCP/IP와 대외기관을, EAI는 백엔드 간 허브를 그린다. 파일 경로는 구성도에서 **EAI 쪽**으로 묶여 있다.

##### 1.3.4 파일 연계 방식 — 단말 → 서버 (1/2, 2/2) — 원문 p.21~p.22

**FACT — 공통 흐름 (1/2·2/2)**

원문 설명:

1. 단말에서 파일 업로드 후 파일전송 요청 거래전문을 송신한다.
2. 대내MCI가 단말관리서버로부터 파일을 가져와 업무서버로 전송한다.
3. 파일전송이 완료되면 대내MCI가 파일전송 요청 거래전문을 업무서버로 송신한다.
4. 업무서버는 파일을 처리한 뒤 처리 결과를 거래전문으로 응답한다.

**FACT — 1/2 MFT (p.21)**

```text
[창구단말 / 자동화기기 / 인터넷 / 모바일 / 콜센터]
        │  파일 업로드 후 거래전문
        ▼
   대내 MCI
        │  파일전송 완료 후 거래전문
        ▼
   업무서버 (파일 처리)
        ▲
        │  MFT: 단말관리서버 → 업무서버
   단말관리서버
        ▲
        │  업로드
      단말
```

하단 주석: **채널에서 업무서버로 파일을 전송하는 경우, 대내MCI는 파일전송 완료 후 거래전문을 송신한다.**

**FACT — 2/2 EAI sFTP (p.22)**

동일 거래 순서이나 파일 이동은 **EAI Adapter(sFTP)** 가 단말관리서버와 업무서버 사이를 잇는다. 하단 주석: **채널에서 업무서버로 파일을 전송하는 경우, EAI는 파일전송 완료 후 거래전문을 송신한다.**

> **ANALYSIS:** 앞 PDF 1.3.2의 「내부 파일 = MFT, 불가 시 EAI SFTP」가 단말 업로드에 그대로 적용된다. 거래전문은 항상 대내MCI가 업무서버에 전달하고, 파일 바이트는 MFT 또는 EAI가 담당한다. 「EAI가 거래전문을 송신한다」는 2/2 주석은, 파일 경로를 EAI로 탄 경우의 완료 통지를 EAI 측 관점으로 쓴 표현으로 읽는 것이 자연스럽다. 단말↔단말관리서버 구간은 솔루션 밖이다.

##### 1.3.5 파일 연계 방식 — 서버 → 단말 (1/2, 2/2) — 원문 p.23~p.24

**FACT — 공통 흐름**

원문 설명:

1. 단말이 파일목록 조회 전문을 송신하고, 대내MCI가 업무서버에 전달한다.
2. 업무서버가 파일목록을 거래전문으로 응답한다.
3. 단말이 파일 다운로드 요청 거래전문을 송신하고, 대내MCI가 업무서버에 전달한다.
4. 업무서버가 파일을 단말관리서버로 전송한다. **(1/2는 MFT, 2/2는 EAI)**
5. 파일전송이 완료되면 업무서버가 처리 결과를 거래전문으로 응답한다.
6. 단말이 단말관리서버에서 파일을 다운로드한다.

**FACT — 1/2 MFT (p.23) / 2/2 EAI (p.24)**

```text
단말 ──조회/다운로드 요청──► 대내MCI ──► 업무서버
단말 ◄──목록/완료 응답────── 대내MCI ◄── 업무서버
업무서버 ──MFT 또는 EAI──► 단말관리서버 ──GET──► 단말
```

하단 주석(1/2): 업무서버에서 채널로 파일을 전송하는 경우, **MFT는 파일을 단말관리서버로 전송**한다.  
하단 주석(2/2): 동일 문장에서 **EAI는 파일을 단말관리서버로 전송**한다.

> **ANALYSIS:** 다운로드도 PUT/GET의 주체는 단말이 아니라 **단말↔단말관리서버**와 **업무서버↔단말관리서버(MFT/EAI)** 로 분리된다. 앞 PDF 1.3.3의 서버 간 파일 규칙이, 경로의 한쪽이 단말관리서버로 바뀐 형태다.

##### 1.3.6 파일 연계 방식 — 업무서버 → 대외MCI (1/2, 2/2) — 원문 p.25~p.26

**FACT — 공통 흐름**

원문 설명:

1. 업무서버가 대외기관 앞으로 파일전송 요청 거래전문을 송신한다.
2. 대외MCI가 업무서버로부터 파일을 가져와 대외기관으로 전송한다.
3. 파일전송이 완료되면 대외MCI가 파일전송 요청 거래전문을 대외기관으로 송신한다.
4. 대외기관은 파일을 처리한 뒤 처리 결과를 거래전문으로 응답한다.

**인터넷 대외기관**이면 업무서버가 대외중계서버로 파일을 전송하고, 대외중계서버가 대외기관에 PUT한다.

**FACT — 1/2 MFT (p.25)**

```text
업무서버 ──거래전문──► 대외MCI ──거래전문──► 대외기관
업무서버 ──MFT──────► 대외MCI ──파일─────► 대외기관
         (인터넷) ──► 대외중계서버 PUT ──► 대외기관
```

**FACT — 2/2 EAI (p.26)**

파일 경로는 **EAI Adapter** 가 업무서버와 대외MCI(및 필요 시 대외중계서버)를 잇는다. 거래전문은 대외MCI가 대외기관에 전달한다.

> **ANALYSIS:** 대외 파일도 「전문은 MCI, 파일은 MFT 또는 EAI」 분리와 같다. 인터넷 구간만 대외중계서버가 추가된다. 앞 PDF 원칙 9(거래당 솔루션 1개)와 맞추면, 한 파일 거래에서 MFT와 EAI를 동시에 쓰지 않는다.

##### 1.3.7 파일 연계 방식 — 대외MCI → 업무서버 (1/2, 2/2) — 원문 p.27~p.28

**FACT — 공통 흐름**

원문 설명:

1. 대외기관이 파일전송 요청 거래전문을 송신한다.
2. 대외MCI가 대외기관으로부터 파일을 가져와 업무서버로 전송한다.
3. 파일전송이 완료되면 대외MCI가 파일전송 요청 거래전문을 업무서버로 송신한다.
4. 업무서버는 파일을 처리한 뒤 처리 결과를 거래전문으로 응답한다.

**인터넷 대외기관**이면 대외중계서버가 대외기관에서 GET한 뒤 대외MCI로 넘긴다.

**FACT — 1/2 MFT (p.27) / 2/2 EAI (p.28)**

방향만 1.3.6의 역이고, 파일 솔루션은 각각 MFT·EAI다.

> **ANALYSIS:** 대외 수신도 완료 후 전문 전달이다. 인터넷 GET은 중계서버가 맡고, 내부 배송은 MFT/EAI가 맡는다. 대외MCI가 「파일을 가져와 전송한다」는 문장은 오케스트레이션 주체를 MCI로 둔 것이고, 실제 바이트 이동은 1/2·2/2 다이어그램의 MFT/EAI 화살표다.

##### 1.3.8 인코딩 변환 방식 (1/3~3/3) — 원문 p.29~p.31

**FACT — 1/3 기본 원칙 (p.29)**

- 한글코드 변환은 **I/F 솔루션이 기본 수행**한다. 변환 대상은 **필드 단위로 설정**한다.
- **복합필드·업무로직이 필요한 변환은 업무팀**이 수행한다.
- 변환 시 **Meta IO 길이를 고려**한다. 원문 예: 주소 필드 KSC5601 20자리 → UTF-8 30자리 (약 1.5배).

```text
채널 (창구 / 자동화 / 인터넷·모바일 / 콜센터)
        │
   대내 MCI     ←── 인코딩 변환(해당 시)
        │
   업무서버
        │
     EAI        ←── 인코딩 변환(해당 시)
        │
   업무서버
        │
   대외 MCI     ←── 인코딩 변환(해당 시)
        │
   대외기관
```

**FACT — 2/3 배치 (p.30)**

| 구분 | 변환 주체 (FACT) |
|---|---|
| 배치-파일 | **업무팀**이 인코딩 변환 |
| 배치-DB | **EAI**가 인코딩 변환 |

다이어그램은 업무서버 간 파일/DB 경로에 EAI Adapter와 업무팀 변환을 나란히 둔다.

**FACT — 3/3 온라인 (p.31)**

원문 요지:

- **표준채널은 UTF-8**이며 **인코딩 변환을 하지 않는다.**
- **비표준채널(KSC5601 등)** 은 **대내MCI에서 전문 변환과 인코딩 변환을 함께** 수행한다.
- **차세대 시스템 ↔ MCI/EAI** 는 **표준전문**을 사용한다.
- **대외MCI**는 **대외기관 한글코드**에 맞춰 변환한다.

> **ANALYSIS:** 인코딩은 「솔루션이 전부 한다」가 아니라 **IO 메타에 걸린 필드 변환**이다. 길이를 안 늘리면 한글 잘림이 설계 결함이다. 배치-파일만 업무팀에 둔 것은, 파일 레이아웃이 솔루션 메타 밖에 있는 경우가 많기 때문이다. 표준채널 UTF-8 무변환은 앞 PDF 1.3.1 HTTP·표준전문과 한 세트다. 비표준 단말(TCP 등)만 MCI가 코드셋까지 흡수한다.

##### 1.3.9 전문관리 방식 (EIMS) — 원문 p.32

**FACT**

```text
개발자 ──등록──► EIMS (전문공통관리)
                    │
                    ▼
              형상관리 (승인·배포)
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      개발         테스트        운영
   (각 시스템 적용 후 테스트)
```

- MCI/EAI **관리도구**로 **복합거래·인코딩** 등을 설정한다.
- 환경은 **개발 / 테스트 / 운영**으로 나뉜다.

하단 주석 요지: EIMS에 등록한 전문은 형상관리를 거쳐 각 시스템에 배포되고, 적용 후 테스트한다.

> **ANALYSIS:** EIMS는 앞 PDF 인터페이스 Layer의 「전문공통관리」 구현체다. 전문 원장과 런타임(MCI/EAI)과 형상관리를 분리한 것이 핵심이다. 인코딩·복합거래는 EIMS 등록만으로 끝나지 않고 **솔루션 관리도구 설정**이 별도 작업이다. 운영 배포 없이 개발기만 고치면 환경 불일치가 바로 장애가 된다.

#### 1.4 아키텍처 예외사항

##### 1.4.1 범용단말 예외사항 — 원문 p.33~p.34

**FACT — 원칙 (양쪽 장표 공통 취지)**

비대면채널·IBOS의 **온라인 거래는 대내MCI를 경유**한다.

**FACT — 예외 (p.33 등)**

IBOS에서 **솔루션의 웹 화면을 링크**하여 호출하는 경우, **대내MCI를 경유하지 않고 HTTP로 해당 WAS에 직접** 접속한다.

```text
[원칙] IBOS/비대면 ──► 대내MCI ──► 업무 WAS/서버

[예외] IBOS ──HTTP 링크──► 솔루션 WAS
              (MCI 미경유)
```

> **ANALYSIS:** 「모든 온라인은 MCI」 원칙(1.2)의 공식 예외다. 범위는 **솔루션 웹 UI를 IBOS에 붙이는 경우**로 한정하는 것이 원문에 가깝다. 일반 업무 API를 HTTP로 WAS에 붙이는 근거로 확장하면 1.4.1을 넘는 해석이다. 보안·SSO·로깅은 MCI를 안 타므로 솔루션 WAS 쪽에서 따로 설계해야 한다.

##### 1.4.2 표준 통신프로토콜 예외사항 — 원문 p.35

**FACT**

**신규 개발 또는 재구축이 아닌** 도메인 — 원문이 드는 예: **부분개발, 대응개발, 유지** — 은 **표준 전문 및 표준 통신프로토콜을 준수하지 않을 수 있다.**

장표 범례(원문):

| 표시 | 의미 (FACT) |
|---|---|
| 빨강 | 신규 / 재구축 |
| 파랑 | 부분개발 |
| 검정 | 대응개발 |

(유지 도메인은 본문에 문구로 포함되고, 색 범례는 위 세 가지가 장표에 명시된다.)

> **ANALYSIS:** 앞 PDF 1.3.1의 HTTP·표준전문 강제는 **차세대 신규/재구축 면**에 먼저 적용된다. AS-IS 잔존·부분개발은 TCP/구전문을 유지할 수 있다는 면죄부다. 반대로 빨강으로 칠한 영역을 파랑 관행으로 가져가면 예외 남용이다. 이행 계획에서 도메인 색칠과 I/F 표준 적용 범위를 같은 표로 맞춰야 한다.

### 2. 연계 아키텍처 구성도

본 PDF p.36 목차에서 **2. 연계 아키텍처 구성도**, **2.1 연계 대상 및 범위**가 강조된다.

#### 2.1 연계 대상 및 범위

##### 2.1.1 대내 MCI 구성도 — 원문 p.37

**FACT**

대내 MCI를 중심으로 한 채널·백엔드 배치. 채널 측(원문 모듈명, 판독 가능한 범위):

- 창구, 자동화기기(ATM 등), 인터넷, 모바일, 콜센터, 파트너/제휴 채널
- 범용단말(IBOS) 등 내부 사용자 채널

백엔드 그리드(원문에 계정계·정보계·전행지원·IT인프라 등으로 구분된 모듈 박스). 파일 경로는 구성도에서 **EAI**와 연결되는 형태로 표시된다.

> **ANALYSIS:** 1.1.2의 「대내MCI = 내부·고객채널 온라인」을 시스템 목록으로 펼친 장표다. 파일은 이 그림에서 EAI로 모이므로, 1.3.4~1.3.5의 MFT는 「내부 파일 전용 경로」로 구성도와 병기해야 한다. 구성도만 보면 MFT가 안 보일 수 있다.

##### 2.1.2 대외 MCI 구성도 — 원문 p.38

**FACT**

- 대외 통신: **X.25**, **TCP/IP**
- 대외 MCI가 대외기관·FEP 성격의 경로와 백엔드를 중계
- AS-IS로 장표에 남는 예: **로이터 IF**, **SWIFT/EDI**, **인터넷PC**, **행정정보공동이용**
- 파일 연계는 **EAI** 쪽으로 표시

> **ANALYSIS:** 대외는 프로토콜이 채널보다 다양하다(X.25 잔존). AS-IS 고유명사는 「차세대가 흡수할 대상」이지 표준 패턴 이름이 아니다. 인터넷 대외는 1.3.6~1.3.7의 대외중계서버와 이 그림의 인터넷PC 경로를 같은 선으로 읽는다.

##### 2.1.3 EAI 구성도 — 원문 p.39

**FACT**

EAI를 허브로 한 **백엔드(업무서버) 간** 연계 구성. 계정계·정보계·지원 영역 모듈이 허브에 붙는다. 파일 연계 표시는 EAI 어댑터 경로와 함께 나타난다.

> **ANALYSIS:** 원칙 3·5(백엔드 간 EAI, 내부 파일 MFT)와 겹친다. 구성도의 파일 화살표가 EAI만 보이면, MFT 불가 시 대체와 「파일+전문 분리」를 설계서에 주석으로 남겨야 한다. 허브-앤-스포크이므로 업무서버 간 직접 연결은 이 그림의 바깥이다.

## 5. 설계 시 체크리스트 (원문 기준)

원문 문장을 설계 질문으로 바꾼 것이다. 장표에 없는 항목은 넣지 않았다.

- [ ] 단말→서버 파일: 업로드 후 전문인가, 파일 완료 후 MCI(또는 EAI 경로)가 업무서버에 전문을 보내는가
- [ ] 서버→단말 파일: 목록조회 → 다운로드요청 → MFT/EAI로 단말관리서버 적재 → 단말 GET 인가
- [ ] 내부 파일 경로가 MFT인가, 불가 시 EAI sFTP인가 (한 거래에 둘 다 쓰지 않는가)
- [ ] 대외 파일이 인터넷이면 대외중계서버 PUT/GET을 타는가
- [ ] 인코딩이 필드 단위 솔루션 변환인가, 복합필드·업무로직이라 업무팀인가
- [ ] Meta IO 길이가 코드셋 변환 후 충분한가 (원문 예: 주소 20→30)
- [ ] 배치-파일 변환 주체가 업무팀인가, 배치-DB는 EAI인가
- [ ] 표준채널 UTF-8은 무변환인가, 비표준 KSC5601은 대내MCI에서 전문+인코딩인가
- [ ] 차세대↔MCI/EAI가 표준전문인가, 대외MCI가 대외 한글코드인가
- [ ] 전문이 EIMS 등록 → 형상관리 배포 → 각 시스템 적용 → 테스트 순인가
- [ ] 복합거래·인코딩이 MCI/EAI 관리도구에 설정되는가
- [ ] IBOS 솔루션 웹 링크만 MCI 미경유 HTTP인가 (그 외 온라인은 대내MCI인가)
- [ ] 해당 도메인이 신규/재구축(빨강)인가, 부분·대응·유지라 표준 프로토콜 예외인가
