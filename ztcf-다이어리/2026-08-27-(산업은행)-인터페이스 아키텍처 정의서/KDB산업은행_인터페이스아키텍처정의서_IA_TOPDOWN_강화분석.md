# 1. L0 — 전체 Interface Context

## 1.1 한 문장 Architecture Definition

원문 1.1.1이 고정하는 문장:

> **차세대 시스템 모델을 인터페이스 아키텍처 관점에서 상세히 기술하고, 관리체계를 정의하여 차세대 시스템 구현의 기준 데이터로 활용한다.**

이를 TOP-DOWN 한 문장으로 다시 쓰면 다음과 같다.

> **채널에서 발생한 온라인·파일·배치·Deferred 거래를, 구간당 하나의 솔루션(대내MCI / 대외MCI / EAI / MFT)이 표준전문·GUID로 중계하고, 로그 4지점과 EIMS 배포로 추적·관리하는 차세대 인터페이스 아키텍처**

# 2. L1 — 핵심 Architecture Domain

원문 1.1.2가 고정하는 Domain은 네 층 + 네 솔루션이다.

```text
1. Channel Domain
2. Channel Integration Domain   (대내MCI / 대외MCI / FEP / EAI)
3. Business Domain              (계정계 / 정보계 / 지원 + 대내 EAI)
4. Interface Foundation Domain  (CDC / ETL / EIMS)
```

```text
Channel
  │
  ▼
Channel Integration ──┬── 대내MCI ──► 온라인 채널
                      ├── 대외MCI ──► 대외 온라인/배치
                      ├── EAI     ──► 백엔드 간 · 배치 · 파일(대체)
                      └── MFT     ──► 내부 서버 파일
  │
  ▼
Business (계정계 / 정보계 / 지원)
  │
  ▼
Interface Foundation (표준전문 · EIMS · CDC/ETL)
  │
  ▼
Log / Governance
```

원문: 레이어를 **연계 특성·용도**에 따라 분리해 **확장성·안정성**을 지향한다.

### ANALYSIS

레이어 분리는 박스를 늘리는 것이 아니라 **장애·확장의 단위**를 나누는 것이다. 채널을 바꿔도 계정계 전문이 안 흔들리고, 온라인이 ETL을 타지 않으며, 파일이 MCI 세션에 실리지 않게 하는 선이다.

# 3. L1-1 — Channel Domain

## 3.1 Channel TOP-DOWN TEXT

```text
사용자
│
├─ 내부 사용자
│  ├─ 본부 / 영업점 창구
│  ├─ 통합단말 (IBOS)
│  ├─ 상담 / 콜센터 단말
│  └─ 범용단말 (솔루션 Web 링크 가능)
│
├─ 고객 / 비대면
│  ├─ 인터넷뱅킹 / 웹비즈 / 홈페이지
│  ├─ 모바일 / 스마트
│  ├─ 자동화기기 (ATM/CD)
│  └─ 텔레뱅킹 (IVR / ARS)
│
└─ 기관 / 대외
   ├─ SWIFT / EDI
   ├─ 금결원 / 한국은행 / VAN / 신용정보
   └─ 행정망 · 인터넷PC · 로이터(AS-IS)
```

## 3.2 FACT

원문 채널 레이어는 내부 / (비대면)고객 / 기관으로 나뉜다. 보안 상자(WAF·IPS·전자금융 보안)가 채널 옆에 있다.

온라인 표(1.3.1)의 채널 목록은 위와 같다. 구성도(2.1.1)는 창구·자동화·인터넷·모바일·콜센터·파트너를 대내MCI에 붙인다.

## 3.3 Channel의 3가지 진입

```text
A. 세션형 온라인     창구 · ATM     TCP + 세션 + 역방향 → 대내MCI
B. HTTP 온라인       전자금융       HTTP, 세션 없음      → 대내MCI
C. 예외 직행         IBOS 솔루션웹  HTTP                 → WAS (MCI 미경유)
D. 기관              SWIFT/EDI/행정  ETC                 → 대외MCI 미경유(공식 예외)
```

채널은 UI 목록이 아니라 **프로토콜·세션·역방향의 진입점**이다.

# 4. L1-2 — Channel Integration Domain

## 4.1 솔루션 역할 TEXT

```text
                    ┌──────────── 채널 ────────────┐
                    │ 단말  ATM  인뱅  모바일  IVR │
                    └──────────────┬───────────────┘
                                   │ 온라인
                                   ▼
                             ┌───────────┐
                             │  대내MCI  │
                             └─────┬─────┘
                                   │ HTTP 표준
          ┌────────────────────────┼────────────────────────┐
          ▼                        ▼                        ▼
     ┌─────────┐             ┌─────────┐              ┌─────────┐
     │ 계정계  │◄──역방향───►│ 정보계  │              │  지원   │
     └────┬────┘             └────┬────┘              └────┬────┘
          │                       │                        │
          └───────────┬───────────┴────────────┬───────────┘
                      │ EAI (백엔드 간)         │
                      ▼                        ▼
                ┌───────────┐            ┌───────────┐
                │    EAI    │            │    MFT    │
                │ 허브·배치 │            │서버 파일  │
                └─────┬─────┘            └───────────┘
                      │
                      ▼
                ┌───────────┐     인터넷 대외: 대외중계/대외IF
                │  대외MCI  │◄──► 대외기관 (X.25 / TCP/IP)
                └───────────┘     코어는 대외MCI 직접
                                  단위시스템은 EAI 경유
```

## 4.2 FACT — 솔루션 한 줄

| 솔루션 | 원문의 역할 |
|---|---|
| 대내 MCI | 내부·고객채널 ↔ 백엔드 **온라인** |
| 대외 MCI | 대외기관 ↔ 백엔드 **온라인/배치** |
| EAI | 백엔드 ↔ 백엔드. 채널–백엔드 **배치**. 대외 송신 시 백엔드–대내MCI. **DB-LINK 금지** |
| MFT | 내부 **서버–서버 파일**만. Agent 불가 시 **EAI sFTP** |

원칙 1: **한 거래 흐름에 연계 솔루션은 하나만.**

## 4.3 접근 유형 분리

```text
[채널 온라인]     Channel → 대내MCI → Business
[백엔드 간]       Business → EAI → Business
[내부 파일]       Server → MFT (or EAI sFTP) → Server
[대외 온라인]     Core → 대외MCI → 기관
                  단위 → EAI → 대외MCI → 기관
[대외 파일]       업무 → EAI → 대외MCI → (전용선 | 공용망+대외IF) → 기관
[기관 직행 예외]  SWIFT / EDI / 행정망 IF  (대외MCI 없음)
```

### ANALYSIS

모든 요청을 하나의 Gateway로 모으지 않는다. **업무 성격별 진입 경로를 분리**한다. 채널 온라인을 EAI에 태우거나, 백엔드 간을 대내MCI에 태우면 원칙 2~4를 깬다. 원칙 6(대외 송신 시 백엔드–EAI–대내MCI)은 대외MCI 직행(4.2.3 코어)과 유스케이스가 다를 수 있어, 설계 시 시나리오를 나눠야 한다. `확인 필요`

# 5. L1-3 — Business Domain

```text
비즈니스 Layer
│
├─ 계정계 (코어뱅킹)
│  └─ 고객 · 여신 · 수신 · 외환 · 자금 · 채널관리 …
│     대내MCI 역방향 허용. 대외MCI 직접.

   └─ DW · IT보안
```

구성도(2.1)는 위 모듈을 그리드로 펼친다. EAI가 백엔드 허브다.

### ANALYSIS

역방향(Push, 책임자승인)은 온라인 표에서 **계정계만** 열린다. 정보계 Push는 이 Baseline 밖이다.

# 7. L2 — 인터페이스 원칙

## 7.1 원칙 TOP-DOWN TEXT

```text
정의: 다른 서버, 또는 동일 서버라도 다른 미들웨어에 있는
      다른 애플리케이션과의 메시지(데이터) 연계
      (프로세스 내부 호출은 I/F가 아님)

[공통]
  1  한 거래 = 솔루션 1개

[역할]
  2  대내MCI = 채널 온라인
  3  대외MCI = 대외 온라인/배치
  4  EAI    = 백엔드 간
  5  EAI    = 채널–백엔드 배치
  6  EAI    = 대외 송신 시 백엔드–대내MCI
  7  DB-LINK 금지

[예외 — 원칙에 이미 들어 있음]
  8  통합로그인 / ESSO 직접
  9  BPM API
 10  단말 솔루션 API · 브라우저→WAS 직행
 11  AS-IS 기존 방식 유지 가능
```

## 7.2 FACT / ANALYSIS

동일 서버라도 미들웨어가 다르면 I/F다.

원칙 1은 홉 최소화다. 채널→MCI→EAI→계정계처럼 솔루션을 겹치면 장애점과 GUID 추적이 두 배가 된다.

원칙 7의 금지 대상은 **앱이 상대방 테이블을 직접 보는 것**이다. CDC/ETL·EAI JDBC는 솔루션 경유 복제/적재로 읽는다.

# 8. L2 — 온라인 구간 설계기준

## 8.1 구간 지도 TEXT

```text
내부 온라인 프로토콜 표준 = HTTP
(구간별로 TCP / HTTP / ETC를 표로 고정)

[채널 → 대내MCI]
  창구·콜센터·범용단말     TCP Socket   세션 유지   역방향
  ATM/CD                   TCP Socket   세션 유지   역방향
  텔레뱅킹 IVR             TCP Socket   세션 없음   역방향 없음
  전자금융(인뱅/모바일 등) HTTP         세션 없음   역방향 없음
  IBOS 솔루션 Web          HTTP → WAS   MCI 없음    (예외를 표에 수록)

[대내MCI → 내부시스템]
  계정계                   HTTP         세션 없음   역방향 있음
  정보계 / 지원 / IT       HTTP         세션 없음   역방향 없음
  HTTP 미지원              ETC          (업무 정의 후)

[내부 → 대외]
  계정계 / 정보계 → 대외MCI   HTTP
  SWIFT / EDI / 행정망 IF     ETC, 대외MCI 미경유
```

## 8.2 FACT

원문 1.3.1 (1/4)~(4/4). 내부 시스템 간 온라인은 HTTP 표준. 채널–대내MCI는 요건에 따라 TCP 또는 HTTP.

## 8.3 ANALYSIS

(1/4)는 지도, (2/4)~(4/4)는 구간 규격이다. 창구·ATM은 동기 세션 채널이고, 전자금융은 연결 유지형 푸시가 이 표만으로는 부족하다. 후속 4.2 Dummy 응답 + Push가 그 빈칸을 채운다.

IBOS 솔루션 웹은 원칙 10을 **표준 표 5행에 넣은 것**이다. 일반 업무 API를 WAS 직행으로 확장하면 예외 남용이다.

# 9. L3 — 파일 연계

## 9.1 파일 전체 TEXT

```text

      MFT는 내부 서버 TO 서버에만.
      Agent 불가 → EAI sFTP.
      파일 바이트와 거래전문을 분리한다. (완료 후 전문)
```

## 9.2 FACT

원문 1.3.2~1.3.7. 업로드는 「업로드 후 전문 → (파일 이동) → 완료 후 전문을 업무에 전달」. 다운로드는 목록조회 → 다운로드요청 → 단말관리서버 적재 → 단말 GET.

대외 일괄(4.2.3): 내부 **EAI**, 대외는 협약에 따라 **TCP/IP 일괄 또는 sFTP**, **DAT+CHK**, 결과는 대외MCI DB. 공용망은 대외 IF.

## 9.3 ANALYSIS

MCI는 파일 바이트의 주체가 아니라 **오케스트레이션·완료 통지**에 가깝다. 단말관리서버 HA가 없으면 채널 파일이 전부 멈춘다.

구성도(2.1)는 파일을 EAI로 모은다. 1.3은 MFT 우선이다. 두 장표를 같이 안 보면 EAI-only로 오해한다.

4.2.4 EAI 파일 그림은 FTP/sFTP Get–Queue–Put이고 「또는 MFT」만 적는다. 원칙 1과 맞추면 **한 파일 거래에 MFT와 EAI를 동시에 쓰지 않는다.**

```text
  타발(개설)  요청/응답   기관 → 내부 요청, 내부 → 기관 응답   Async
  당발        통지        내부 → 기관 일방   (필요 시 dummy Ack)
  타발        통지        기관 → 내부 일방

일괄
  송신  대외MCI가 기관에 로그인 후 파일
  수신  기관이 대외MCI에 로그인 후 파일

경로
  코어뱅킹     ──► 대외MCI ──► 기관          (직접)
  단위시스템 ──► EAI ──► 대외MCI ──► 기관

당발 타임아웃 · 전문 유효성 오류 → 대외MCI 대행응답
```

## 15.2 대외 파일 TEXT

```text
업무 ──DAT/CHK──► EAI ──► 대외MCI ──►
        │                    │
        │                    ├─ 전용선 TCP/IP 일괄 또는 sFTP
        │                    └─ 공용망 → 대외IF → 기관
결과: 대외MCI DB
수신은 반대. 업무는 CHK 확인 후 처리.
```

거래공통부 대외구분 1~4가 이 표의 개설/취급 요청·응답이다.

### ANALYSIS

단위시스템이 대외MCI에 직접 붙이면 코어-only 직행 규칙을 깬다. 내부 파일 기본 MFT(1.3)와 대외 파일 EAI(4.2.3)는 **구간이 다르다.**

# 16. L6 — EAI 거래 패턴

## 16.1 온라인 TEXT

```text
[동기] TCP/IP 또는 HTTP Connector
  송신 Client Adapter ↔ EAI Flow (Source/Target Connector) ↔ 수신 Server Adapter
  수신 장애·타임아웃 → EAI 대행응답
  EAI는 수신 헬스체크

[비동기] Socket + 내부 Queue
  송신 → EAI Queue → 수신     (응답 경로 없음)
  Queue로 전송 보장
  송신은 EAI 통신오류 외 확인 불가
  → 수신확인이 필요한 거래에는 사용 금지
```

## 16.2 파일 / DB TEXT

```text
[파일] 스케줄러 → Batch Service
  Source FTP/sFTP Get → EAI Queue → Target FTP Put
  (또는 MFT)

[DB] 스케줄러 → JDBC
  Fetch Query → 임시파일 → 송신 Flag Update → Target Upsert
  ⑦⑧ 반복

[Deferred] Deferred Controller가 Batch Service를 때림
  이후는 DB 배치와 동일. DB2DB만.
```

### ANALYSIS

4.1.2 정합성 = 여기 헬스체크·대행응답. 4.1.3 타임아웃 없음 = Queue fire-and-forget. 이체성·수신확인 거래에 Async Queue를 쓰면 장표가 금지한 사용이다.

# 17. L7 — 로그

## 17.1 로그 구성 TEXT

```text
요청: inbound Adapter ──변환/매핑──► outbound Adapter
응답: (반대, 동일 4지점)

로그처리기
  ├─ 인터페이스 로그 저장소 ──► 관리/모니터링
  └─ 채널접속이력 ──EAI DB2DB──► 업무 접속이력 조회

4지점 × GUID
  1 요청을 받은 즉시          (SRC수신)
  2 요청을 목적지에 주기 직전 (TGT송신)
  3 응답을 받은 즉시          (TGT수신)
  4 응답을 요청지에 주기 직전 (SRC송신)

제약: 온라인 거래 성능에 영향 없게.
      접속이력은 전문 로그에서 분리 추출.
```

## 17.2 대내MCI 생성 TEXT

```text
채널 ↔ MCI Core (Log Manager, Error HDR) ↔ 업무
         │
         ├─ ① 전문/입출력   DB + 파일
         ├─ ② 시스템        솔루션 내부
         └─ ③ 에러          Error HDR

파일 (원문 표기)
  chanel.log / adaptor.log      입출력 (현재)
  gateway.log / controller.log  시스템
  error_handler.log             에러
  YYYY-MM-DD/                   1시간 rollover 백업
```

## 17.3 정책 TEXT

```text
은행 정책에 따라 변경 가능.

전문 로그   EAI·대내MCI·대외MCI   4지점   파일/DB   전문전체 보안   일   영구
에러 로그   동상                   오류분   파일/DB   평문           일   영구
시스템 로그 동상                   내부     파일만    평문           일   영구
```

### ANALYSIS

GUID가 로그와 전문과 대량 진행번호를 잇는다. 4지점을 동기로 디스크에 쓰면 5.1 「온라인 영향 없게」를 깬다.

에러·시스템은 평문이라, 오류 전문이 에러 로그로만 남으면 마스킹이 빠질 수 있다. MFT 전용 로그 행은 없다. 1시간 파일 vs 일·영구 DB의 이관 규칙 없음. `확인 필요`

```text
요청팀 신규/변경
```

# 19. Runtime Scenario (ANALYSIS, 원문 시퀀스를 시나리오로 접음)

```text
S1 창구 일반조회

   대외 후속이면 Dummy 후 Push

   개국(관리서버 SESSION) 후 업무 TCP+역방향

S6 백엔드 간 동기
   EAI HTTP/TCP · 헬스체크 · 타임아웃 시 대행응답

S7 백엔드 비동기
   EAI Queue. 수신확인 필요하면 사용 금지 → S6 또는 양방향 비동기+원거래GUID

S8 내부 파일
   단말관리서버 + MFT (또는 EAI sFTP) + 완료 후 전문

S9 대외 취급
   코어→대외MCI Async / 단위→EAI→대외MCI
   오류 시 대외MCI 대행응답

S10 대외 파일
    DAT+CHK, 내부 EAI, 대외 일괄/sFTP, 인터넷이면 대외IF

S11 Deferred 고객정보
    Controller polling · Flag · Upsert · 결과 컬럼
```

# 22. 설계 검증 체크리스트 (원문 기준)

원문 문장을 질문으로 바꾼 것이다. 장표에 없는 항목은 넣지 않았다.

```text
[구간]
  □ 이 거래의 솔루션이 하나인가 (MCI / EAI / MFT / 직행 예외 중 하나)
  □ 채널 온라인인가 → 대내MCI. 백엔드 간인가 → EAI. 내부 파일인가 → MFT
  □ 코어 대외인가 → 대외MCI 직접. 단위 대외인가 → EAI 경유
  □ DB-LINK로 상대 테이블을 보지 않는가

[온라인]
  □ 창구·ATM이면 TCP+세션+역방향인가
  □ 전자금융이면 HTTP인가
  □ IBOS 솔루션 웹만 WAS 직행인가
  □ 계정계만 역방향인가

[파일]
  □ 단말이 단말관리서버를 경유하는가. 완료 후 전문인가
  □ Agent 없으면 EAI sFTP인가
  □ 대외면 DAT+CHK, 내부 EAI, 인터넷이면 대외IF인가

[전문]
  □ 입력/출력 FLAT 구조와 @@ 인가
  □ GUID 38자가 요청에서 생성되고 응답에서 유지되는가
  □ Async면 원거래 GUID인가. 대량이면 진행번호를 올리는가
  □ ID가 시스템3+O/B/D/E+EIMS 일련인가
  □ UTF-8 표준채널은 무변환, Meta IO 길이는 충분한가

[패턴]
  □ 6유형(일반/대량/Push/인증/로컬/MCI발생) 중 어디인가
  □ 책임자면 재요청까지 갔는가. ATM이면 개국 후인가
  □ EAI Async를 수신확인 거래에 쓰지 않았는가
  □ DB 수신이 Insert/Upsert뿐인가. Deferred면 DB2DB+Controller인가

[로그·관리]
  □ 로그 4지점이 GUID로 붙고 온라인을 안 막는가
  □ EIMS 등록 → 배포 → 단위/종합 테스트인가
  □ 시스템 헤더 변경에 위원회가 있는가
```

# 24. 최종 평가

이 정의서는 단순 솔루션 배치도가 아니라 다음 View를 한 문서에 담는다.

```text
1. Policy View     원칙 1~11 · 예외 1.4
```
