# 인터페이스 아키텍처 — 데이터 플랫폼 분석

## 1. 핵심 결론

장표는 데이터 플랫폼을 **RDW**와 **ADW**의 두 논리 영역으로 분리하고, 각 영역의 데이터 인터페이스 업무군을 코드로 정의한다.

```text
데이터 플랫폼
├─ RDW (코드 RD)
│  ├─ 공통 CO
│  ├─ 실시간 SoR SR
│  ├─ 준실시간 요약집계 ZD
│  ├─ 준실시간 보고서마트 RM
│  └─ 피드백 FA
└─ ADW (코드 AD)
   ├─ 공통 CO
   ├─ 분석 SoR SR
   ├─ 분석 통합요약집계 ZD
   ├─ 분석 단위업무마트 UM
   ├─ 분석 보고서마트 RM
   ├─ 피드백 FA
   └─ 분석지원 DA
```

RDW는 실시간·준실시간 데이터 공급과 운영성 조회를, ADW는 대량 분석·집계·업무마트·분석지원을 담당한다. 공통, SoR, 요약집계, 보고서마트, 피드백 코드가 양쪽에서 재사용되므로 `플랫폼 코드 + 업무 코드`의 복합 식별자가 필요하다.

예:

- `RD-CO`: RDW 공통
- `RD-SR`: RDW 실시간 SoR
- `AD-SR`: ADW 분석 SoR
- `AD-UM`: ADW 분석 단위업무마트

장표에는 “업무명 분석 대상 구체화”와 “확인 필요”가 명시되어 있으므로, 현재 코드는 최종 물리 인터페이스 목록이 아니라 **분석·분류 단계의 논리 업무군**으로 보는 것이 안전하다.

|---:|---|---|---|---|

|---:|---|---|---|---|
| 1 | ADW | AD | 공통 | CO |

### 2.3 장표 메모

- “업무명 분석 대상 구체화”
- 점선 범례: “확인 필요”

이미지에서는 점선 처리된 개별 업무가 뚜렷하지 않지만, 장표 자체가 업무명과 분석 범위를 추가 구체화해야 함을 알리고 있다.

## 3. 논리 데이터 관계도

```text
                 ┌────────────── 원천 시스템 ───────────────┐
                 │ 계정계 CDC │ BCV/ETL │ 대내외 업무 DB    │
                 └───────────────┬──────────────────────────┘
                                 v
┌────────────────────────────── RDW (RD) ──────────────────────────┐
│ CO 공통                                                          │
│ SR 실시간 SoR ← CDC/실시간 변경                                  │
│      │                                                           │
│      ├→ ZD 준실시간 요약집계                                     │
│      ├→ RM 준실시간 보고서마트                                   │
│      └→ FA 피드백                                                 │
└───────────────────────────────┬──────────────────────────────────┘
                                │ ETL/데이터 동기화
                                v
┌────────────────────────────── ADW (AD) ──────────────────────────┐
│ CO 공통                                                          │
│ SR 분석 SoR                                                      │
│      ├→ ZD 분석 통합요약집계                                     │
│      ├→ UM 분석 단위업무마트                                     │
│      ├→ RM 분석 보고서마트                                       │
│      └→ DA 분석지원                                               │
│ FA 피드백 ────────────────────────────────> RDW/업무 시스템       │
└───────────────────────────────────────────────────────────────────┘
```

장표에는 RDW↔ADW 연결선이 직접 표현되어 있지 않으므로 위 흐름은 기존 데이터 플랫폼 역할과 명칭에 근거한 논리적 분석이다. 실제 Source-to-Target은 ETL 목록에서 확정해야 한다.

## 4. RDW 역할 분석

RDW는 실시간·준실시간 데이터 공급을 위한 운영형 정보계 저장소로 해석된다. 원천 변경을 빠르게 수용하고 온라인 조회와 단기 집계를 지원한다.

### 4.1 RD-CO — 공통

공통 영역은 RDW 전반에서 공유하는 기준 구조를 제공한다.

- 공통 코드와 기준정보
- 업무일자·캘린더
- 조직·채널·상품 기준
- 공통 고객 식별키
- 인터페이스 실행·대사 메타데이터

공통 영역을 범용 적재 공간으로 사용하면 소유권이 불명확해진다. 데이터 도메인과 책임자를 명시하고 변경 승인 절차를 적용해야 한다.

### 4.2 RD-SR — 실시간 SoR

SoR(System of Record)은 해당 분석·정보계 문맥에서 신뢰 가능한 실시간 기준 데이터 영역을 의미한다. 계정계 원장 자체와 동일한 법적 원장으로 단정해서는 안 된다.

주요 입력:

- 코어뱅킹 DB 변경분(CDC)
- 실시간 채널·고객 행동 이벤트
- 즉시 반영이 필요한 업무 상태

주요 통제:

- 커밋 순서와 트랜잭션 경계
- Capture Lag·Apply Lag
- 원천 키와 변경 버전
- 삭제·취소·정정 반영
- 체크포인트와 로그 보존

### 4.3 RD-ZD — 준실시간 요약집계

실시간 SoR의 상세 데이터를 온라인 조회에 적합한 수준으로 미리 집계한다.

- 고객·계좌·상품 단위 요약
- 당일 거래·잔액·접촉 현황
- 캠페인 반응과 실시간 지표
- 시간창 기반 집계

요약집계는 원천 상세와 재계산 가능해야 한다. 집계 기준 시각, Watermark, 지연 허용치와 정정 반영 정책을 정의해야 한다.

### 4.4 RD-RM — 준실시간 보고서마트

보고서 응답을 위해 준실시간으로 갱신되는 정형 마트다.

- 보고서별 데이터셋과 기준 시각
- 조회 조건·권한·행 수준 보안
- 보고서 집계와 상세 Drill-down 연결
- 정정 데이터 재반영
- 통계정보와 인덱스 관리

보고서마다 유사 마트를 중복 생성하지 않도록 공통 지표와 데이터 제품을 재사용해야 한다.

### 4.5 RD-FA — 피드백

피드백 영역은 정보계 분석·캠페인·업무 결과를 원천 또는 운영 서비스로 되돌리는 폐루프 구조를 지원한다.

```text
RDW/ADW 분석·판단
  → 피드백 데이터 생성
  → 품질·승인·고객 동의 검증
  → 운영 시스템 전달
  → 적용 결과 수신
  → 피드백 상태 갱신
```

분석 결과를 원천 데이터와 혼합하지 말고, 권고·점수·캠페인·모델 버전과 적용 상태를 별도 관리해야 한다.

## 5. ADW 역할 분석

ADW는 대량 분석과 통합 집계, 업무별 마트 및 분석 지원을 위한 분석형 데이터웨어하우스로 해석된다.

### 5.1 AD-CO — 공통

ADW의 공통 영역은 분석 전반에서 재사용되는 차원·코드·지표 정의를 제공한다.

- 고객·상품·조직 공통 차원
- 시간·업무일자 차원
- 전사 지표와 계산식
- 데이터 품질·Lineage 메타
- 모델·Feature 공통 정의

RD-CO와 동일한 `CO` 코드를 사용하더라도 물리 데이터와 갱신 주기는 다를 수 있다. 두 공통 영역의 Master/Replica 관계를 명시해야 한다.

### 5.2 AD-SR — 분석 SoR

분석 SoR은 여러 원천을 통합·정제한 분석 기준 상세 데이터다.

- 장기 이력과 Slowly Changing Dimension
- 분석용 통합 고객·거래·상품 데이터
- 원천 및 변환 Lineage
- 정정·재처리 이력
- 스냅샷과 유효기간

### 5.3 AD-ZD — 분석 통합요약집계

전사 분석과 경영지표를 위한 통합 집계 영역이다.

- 전사 KPI와 공통 지표
- 기간·조직·고객·상품별 집계
- 다차원 분석용 Aggregate
- 대용량 분석 성능 최적화

지표 정의는 데이터거버넌스의 비즈메타와 연결하고 동일 명칭의 중복 계산을 차단해야 한다.

### 5.4 AD-UM — 분석 단위업무마트

단위업무별 분석 목적에 맞춘 데이터마트다.

- 마케팅, 신용, 리스크, 영업, 고객 등 업무별 마트
- 업무 전용 파생지표
- 사용자·조직별 접근 통제
- 갱신 주기와 보존 정책

단위업무마트가 원천의 복제 사일로가 되지 않도록 AD-SR과 AD-ZD를 공식 공급원으로 사용해야 한다.

### 5.5 AD-RM — 분석 보고서마트

경영·분석 보고서를 위한 확정형 데이터마트다.

- 월·분기·연도 확정 실적
- 공식 보고서 지표
- 재현 가능한 마감 Snapshot
- 승인·확정·재공시 이력

RD-RM은 준실시간 조회, AD-RM은 분석·확정 보고라는 책임 차이를 계약에 명확히 해야 한다.

### 5.6 AD-FA — 피드백

모델 점수, 세그먼트, 추천, 캠페인 대상과 분석 결과를 운영 영역으로 제공한다.

- 모델 ID·버전·학습 기준일
- 고객·대상 키
- 점수·등급·추천 사유
- 유효 시작·종료 시각
- 적용 채널과 목적
- 고객 동의·설명 가능성

### 5.7 AD-DA — 분석지원

분석가·데이터사이언티스트를 위한 탐색·Feature·Sandbox 지원 영역으로 해석된다.

- 승인된 분석 Dataset
- 비식별·가명 데이터
- 모델 개발·검증용 Feature
- 임시 결과와 만료 정책
- 자원 Quota와 쿼리 통제

분석지원 영역의 임시 데이터를 공식 지표나 운영 피드백에 바로 사용하지 않도록 승격 절차가 필요하다.

## 6. 코드 체계 분석

### 6.1 복합 코드 필요성

`CO`, `SR`, `ZD`, `RM`, `FA`는 RDW와 ADW 양쪽에서 반복된다. 업무 코드만 사용하면 다음과 같은 충돌이 발생한다.

```text
SR = RDW 실시간 SoR ? ADW 분석 SoR ?
RM = 준실시간 보고서마트 ? 분석 보고서마트 ?
FA = 운영 피드백 ? 분석 피드백 ?
```

권장 식별 규칙:

```text
<플랫폼 코드>-<업무 코드>-<인터페이스 유형>-<순번>

예:
RD-SR-CDC-001   # RDW 실시간 SoR CDC 수신
RD-RM-ETL-001   # RDW 준실시간 보고서마트 적재
AD-SR-ETL-001   # ADW 분석 SoR 적재
AD-UM-ETL-015   # ADW 단위업무마트 적재
AD-FA-API-003   # ADW 분석 피드백 제공
```

### 6.2 코드 의미 확인 대상

`ZD`, `FA`, `DA`는 한글 업무명과 연결되지만 영문 약어의 공식 확장은 장표에 없다. 임의로 확장하지 말고 애플리케이션 코드 정의서에서 확정해야 한다.

## 7. RDW와 ADW의 책임 경계

| 항목 | RDW | ADW |
|---|---|---|
| 목적 | 실시간·준실시간 운영 정보 제공 | 통합 분석·대량 집계·마트 |
| 갱신 | CDC, Micro-batch, 준실시간 ETL | 배치 ETL 중심 |
| 지연 | 초·분 단위 | 시간·일 단위 중심 |
| 데이터 | 최신 상태·단기 이력 | 장기 이력·통합·파생 데이터 |
| 조회 | 온라인·운영 보고 | 분석·BI·Self-BI·모델링 |
| 집계 | 경량·준실시간 | 대량·다차원·확정 집계 |
| 자원 | 낮은 지연과 안정성 우선 | 처리량과 병렬성 우선 |
| 피드백 | 운영 결과 수신·근실시간 제공 | 모델·세그먼트·추천 생성 |

RDW를 대규모 자유 분석에 사용하거나 ADW를 실시간 운영 조회에 사용하면 자원 경합과 SLA 위반이 발생할 수 있다.

## 8. 예상 인터페이스 흐름

### 8.1 원천 → RD-SR

```text
코어뱅킹/대내 시스템
  → CDC 또는 실시간 이벤트
  → RD-SR Staging
  → 스키마·순서·중복 검증
  → RD-SR 본 영역 반영
  → 체크포인트 저장
```

### 8.2 RD-SR → RD-ZD/RD-RM

```text
RD-SR
  → Watermark 기준 증분 추출
  → 준실시간 집계
  ├→ RD-ZD 요약집계
  └→ RD-RM 보고서마트
  → Source/Target 대사
```

### 8.3 RDW → AD-SR

```text
RDW 상세·준실시간 데이터
  → ETL 추출
  → 표준화·이력화·품질 검증
  → AD-SR 분석 상세
  → Lineage 기록
```

### 8.4 AD-SR → AD-ZD/UM/RM/DA

```text
AD-SR
  ├→ AD-ZD 통합요약집계
  ├→ AD-UM 단위업무마트
  ├→ AD-RM 분석보고서마트
  └→ AD-DA 분석지원 Dataset
```

### 8.5 AD-FA/RD-FA → 운영 시스템

```text
분석 결과/운영 반응
  → FA 영역 등록
  → 목적·동의·품질 승인
  → API/파일/ETL로 운영 시스템 제공
  → 적용 결과 및 오류 회신
```

## 9. 데이터 인터페이스 계약

| 분류 | 필수 항목 |
|---|---|
| 식별 | Interface ID, 플랫폼 코드, 업무 코드, 버전 |
| Source | 시스템, DB, 스키마, 테이블·뷰, 소유자 |
| Target | 플랫폼, 업무영역, 스키마, 테이블·마트 |
| 방식 | CDC/ETL/API/File, 전체/증분, Push/Pull |
| 데이터 | 컬럼 매핑, 업무키, 코드, 타입, 유효기간 |
| 시간 | 업무일자, 기준 시각, 주기, Watermark |
| 품질 | 필수값, 중복, 참조무결성, 허용 범위 |
| 정합성 | 건수, 합계, 해시, Source/Target 대사 |
| 보안 | 개인정보 등급, 마스킹, 권한, 암호화 |
| 운영 | SLA, 체크포인트, 재처리, RACI, DR |

```yaml
interfaceId: RD-SR-CDC-001
platform: RD
domain: SR
version: 1.0.0
source:
  system: core-banking
  object: CUSTOMER_TX
target:
  system: RDW
  area: real-time-sor
  object: RT_CUSTOMER_TX
load:
  type: CDC
  key: [TX_ID]
  ordering: commit_scn
quality:
  checks: [not_null, duplicate_key, code_validity]
reconciliation:
  checks: [row_count_by_operation, amount_sum]
operations:
  lagSlaSeconds: 60
  owner: data-platform-rdw
  drEnabled: true
```

## 10. 정합성 및 데이터 품질

### 기술 정합성

- Source 추출 건수와 Target 반영 건수
- Insert·Update·Delete별 건수
- PK·업무키 중복
- Null·타입·코드 오류
- 합계·최솟값·최댓값·해시
- CDC SCN 또는 ETL Watermark

### 업무 정합성

- 고객·상품·조직 기준정보 참조
- 거래 금액·잔액·성과 지표
- 업무일자와 마감 상태
- 취소·정정·삭제 반영
- RD/RM과 AD/RM의 지표 기준 차이

품질 실패 데이터는 본 영역에 공개하지 않고 Quarantine 또는 오류 Staging에 격리한다.

## 11. 시간 계층과 최신성

| 데이터 계층 | 목표 최신성 예시 | 완료 기준 |
|---|---:|---|
| RD-SR | 수초~수분 | CDC Apply Checkpoint |
| RD-ZD | 수분 | 집계 Window 완료 |
| RD-RM | 수분~시간 | 보고서 Dataset 대사 완료 |
| AD-SR | 시간~일 | 배치 적재·품질 완료 |
| AD-ZD/UM | 일/업무 주기 | 집계·마트 대사 완료 |
| AD-RM | 마감 주기 | 승인·확정 Snapshot |
| AD-DA | 요청/프로젝트 주기 | Dataset 승인·만료 등록 |

실제 SLA는 업무별로 확정해야 하며, 화면·보고서·API에는 데이터 기준 시각을 표시해야 한다.

## 12. 피드백 아키텍처

RD-FA와 AD-FA가 동일 코드로 존재하므로 피드백 종류를 분리해야 한다.

| 구분 | RD-FA | AD-FA |
|---|---|---|
| 성격 | 운영 반응·실시간 결과 | 분석 결과·모델 점수·세그먼트 |
| 입력 | 채널·캠페인·업무 처리 결과 | ADW 분석·모델·마트 |
| 출력 | RDW 집계·서비스 | 운영 시스템·마케팅 플랫폼 |
| 지연 | 실시간·준실시간 | 배치·요청 기반 |
| 핵심 키 | Event/Transaction ID | Model/Segment/Customer ID |

피드백은 순환 데이터이므로 원천과 파생 결과를 구분하고, 피드백이 다시 모델 입력으로 사용될 때 데이터 누수와 자기강화 편향을 점검해야 한다.

## 13. 접근 및 보안

- RD-SR은 운영 조회 계정과 적재 계정을 분리한다.
- AD-DA는 분석가별 Workspace·Quota·만료를 적용한다.
- 개인정보는 용도에 따라 가명화·마스킹한다.
- Self-BI와 보고서는 행·열 수준 권한을 적용한다.
- 서비스 계정은 인터페이스별 최소 권한을 사용한다.
- ETL Credential은 Vault에서 참조한다.
- 데이터 다운로드·피드백 제공·모델 점수 사용을 감사한다.
- 개발·검증 환경에는 운영 개인정보를 직접 복제하지 않는다.

## 14. 성능 및 자원 분리

- RDW의 실시간 적재와 온라인 조회 자원을 분리한다.
- ADW의 대량 ETL, BI, Self-BI, 분석지원 자원 그룹을 분리한다.
- RDW→ADW 추출은 파티션·업무일자 단위로 병렬화한다.
- 집계·마트 갱신 후 통계정보를 관리한다.
- 분석가 Ad-hoc SQL에 CPU·I/O·시간 Quota를 적용한다.
- 대량 재처리가 실시간 CDC Apply를 방해하지 않게 한다.
- 데이터 보존·압축·파티션 정책을 최신성과 함께 설계한다.

## 15. 장애 복구 및 멱등성

### CDC

- 마지막 SCN·체크포인트부터 재개한다.
- 로그 보존 한계를 감시한다.
- 장기 단절 시 기준 데이터 재적재 후 CDC를 연결한다.

### ETL

- Job·Step·파티션 단위 체크포인트를 사용한다.
- Staging 적재 후 멱등 Merge 또는 Partition Exchange를 수행한다.
- 동일 Interface ID·업무일자·실행 버전의 중복을 방지한다.

### 집계·마트

- 집계 Window를 재계산 가능하게 유지한다.
- 마감 Snapshot은 승인 전 교체하고 승인 후 불변으로 관리한다.
- 정정 재처리는 이전 버전과 영향 범위를 기록한다.

## 17. DR 기준

- RDW·ADW 복제 및 복구 순서를 정의한다.
- CDC의 Capture/Apply 방향과 체크포인트를 전환한다.
- ETL 스케줄러는 주센터와 DR센터 중 한 곳만 Active로 둔다.
- 마트 갱신 중 전환 시 부분 결과를 폐기·재처리한다.
- 피드백의 중복 제공을 Active Lock으로 방지한다.
- DR 데이터 최신성이 각 영역의 RPO를 충족하는지 검증한다.
- 원복 후 RD-SR, RD-ZD/RM, AD-SR/마트 순서로 대사한다.

1. “업무명 분석 대상 구체화”의 대상 업무와 완료 기준
2. 점선 범례가 적용되는 실제 항목

## 22. 최종 평가

데이터 플랫폼 장표는 RDW를 실시간·준실시간 공급 계층, ADW를 분석·통합·마트 계층으로 구분하고 공통적인 데이터 업무 패턴을 코드화했다. `RD-SR → RD-ZD/RM`, `RDW → AD-SR → AD-ZD/UM/RM/DA`, `FA → 운영 피드백` 구조로 구체화하면 온라인 운영과 대량 분석의 자원·책임을 효과적으로 분리할 수 있다.

다만 현재 장표는 인터페이스 연결보다 업무 분류에 가깝고 스스로 “구체화·확인 필요”를 표시한다. 따라서 플랫폼+업무 복합 코드, Source-to-Target, 실제 스키마, 처리 방식, 최신성 SLA, 피드백 방향과 데이터 소유자를 인터페이스 등록부로 확정해야 한다. 특히 RDW·ADW에서 반복되는 `CO·SR·ZD·RM·FA`는 단독 코드로 사용하지 말고 `RD-SR`, `AD-SR`처럼 플랫폼 문맥을 포함해야 한다.
