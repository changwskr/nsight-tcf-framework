# 논리기술아키텍처 — 레이어드 아키텍처 — 선도개발 구조 분석

## 1. 분석 개요

첨부 장표의 **선도개발 표준 아키텍처 구성**을 기준으로 선도개발(Pilot Development / Pilot) 환경을 다음 5개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer
5. 형상·배포 Layer

장표 상단 설명에 따르면, 정보계 차세대는 IaaS 기반의 **서비스 개발**로 추진하며, **단말관리·배포를 위한 UI 영역**과 **NH Cloud Framework 영역**으로 구현한다. 선도개발 장표는 운영·확산 단계의 마케팅플랫폼 전체 구성보다 **범위가 축소된 초기 검증 환경**을 표현한다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 제품 버전, 노드 수, 실제 네트워크 구간, 연계 프로토콜, 선도 범위에 포함·제외된 기능의 최종 목록은 구축 명세와 선도개발 범위서에서 확인해야 한다.

## 2. 핵심 결론

- **선도 범위의 축소 구성**: 운영형 마케팅플랫폼 대비 Client·I/F·실시간 이벤트·운영 배포 경로가 의도적으로 단순화되어 있다.
- **접근 경로 단일화**: 전용 Browser(선도개발) → L4 → WEB으로 진입하며, 통합단말·MCA·싱글뷰 경로는 장표에 나타나지 않는다.
- **서비스 이원화 유지**: UI 서비스플랫폼(WebTopSuite: 단말관리·단말배포)과 마케팅플랫폼(NH Cloud Framework: 마케팅 WAS)의 분리는 유지한다.
- **프레임워크 표준 검증**: 선도 단계에서 NH Cloud Framework 기반 온라인 WAS 실행을 검증하는 것이 핵심 목적이다.
- **상태 공유 최소 구성**: 공통인프라 Node의 IMDG로 Session/Data Cache를 제공하여 다중 WAS 전제 또는 세션 공유를 검증한다.
- **인터페이스 최소 집합**: FOS, MFT, IT메타, Nexus만 명시되어 파일 연계·메타·산출물 저장 중심의 최소 I/F를 전제한다.
- **데이터 역할 분리**: 단말관리 DB, RDW(Oracle Exadata), 마케팅플랫폼 DB를 목적별로 분리한다. 장표상 ADW는 보이지 않는다.
- **개발 배포 중심**: GitLab → GitLab Runner → 취약점 점검/Dev Pipeline → 개발환경 경로만 표현되며(eCAMS·운영 Pipeline 없음).

## 4. 레이어별 구조 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 설계 의미 |
|---|---|---|
| 전용 Browser (선도개발) | 선도개발 전용 UI 접근 | 선도 범위 화면·브라우저 정책을 통제한다. |
| L4 | WEB 노드 부하분산·가상 서비스 주소 | 물리 WEB 노드를 은닉하고 장애 우회 진입점을 제공한다. |

선도개발 장표에는 **범용 Browser, 통합단말, MCA, 싱글뷰**가 없다. 운영·확산 단계의 채널 다양성은 선도 검증 범위 밖이거나 후속 단계로 미룬 것으로 해석된다. 클라이언트가 WAS·DB에 직접 접속하지 않도록 L4·WEB 경계를 유지한다.

### 4.2 Service Layer — UI 서비스플랫폼

```text
전용 Browser → L4 → UI WEB → WebTopSuite Service Node
                              ├─ 단말관리 WAS
                              └─ 단말배포 WAS
```

| 구성요소 | 책임 |
|---|---|
| WEB | 정적 자원 제공, WAS 요청 전달, 접근 제어 |
| 단말관리 WAS | 단말 등록·정책·운영 정보 관리 |
| 단말배포 WAS | 화면·패키지·리소스 배포 관리 |
| WebTopSuite | 단말 UI 관리·배포 기능의 실행 기반 |

UI 서비스플랫폼은 마케팅 업무 로직을 직접 수행하기보다 **단말 운영·배포 수명주기**를 담당한다. 선도 단계에서도 업무 WAS와 배포·단말 관리 영향을 분리해 검증할 수 있다.

### 4.3 Service Layer — 마케팅플랫폼

```text
전용 Browser → L4 → 마케팅 WEB → NH Cloud Framework → [마케팅플랫폼] WAS
                                                      ↕ Session/Data Cache
                                              공통인프라 Node: IMDG
```

| 구성요소 | 책임 | 데이터/연계 |
|---|---|---|
| 마케팅플랫폼 WEB | 온라인 요청 수신 및 WAS 전달 | L4, WAS |
| [마케팅플랫폼] WAS | 선도 범위의 마케팅 온라인 업무 처리 | NH Cloud Framework, 마케팅플랫폼 DB |
| IMDG | Session/Data Cache | 복수 WAS 전제 또는 세션 공유 검증 |

#### NH Cloud Framework의 위치

NH Cloud Framework는 마케팅 WAS 내부의 공통 실행 골격이다. 시스템 선·후처리, 업무 선·후처리, Service·DTO·DAO, 공통 라이브러리를 제공하여 **선도 업무 모듈의 구현 방식 표준화**를 검증한다.

#### 운영형 마케팅플랫폼과의 차이

운영·표준 마케팅플랫폼 장표에 흔히 포함되는 다음 요소가 **선도개발 장표에는 보이지 않는다.**

| 운영·확산 구성(일반) | 선도개발 장표 | 해석 |
|---|---|---|
| [마케팅허브]/미니싱글뷰 WAS | 없음 | 통합단말·싱글뷰 검증은 후속 |
| Kafka / EBM 실시간 이벤트 | 없음 | 실시간 마케팅은 선도 범위 외 또는 단계적 확장 |
| 배치 AP / RD / ETL 브리지 | 없음 | 배치·분석 연계는 I/F·Data로 최소화 |
| 넓은 I/F(SSO, APIM, EAI, MCA 등) | FOS·MFT·IT메타·Nexus만 | 최소 연계 집합 |
| ADW | 없음(RDW만) | 분석 마트 확장은 후속 |
| eCAMS·운영 Pipeline | 없음 | 개발환경 배포만 검증 |

선도개발은 **“표준 골격(UI 플랫폼 + NH Cloud + IMDG + 최소 I/F + RDW/업무 DB + Dev CI)”** 을 먼저 세우는 단계로 보는 것이 타당하다.

### 4.4 I/F Layer

| 구성요소 | 용도 | 선도 단계 의미 |
|---|---|---|
| FOS | 표준 파일 송수신 | 파일 기반 연계 경로 검증 |
| MFT | 외부·대용량 파일 중계 | 파일 무결성·재전송 정책 검증 |
| IT메타 | IT 메타데이터 관리 | 서비스·데이터 메타 등록 기반 |
| Nexus | 라이브러리·배포 산출물 저장소 | 빌드 Artifact와 의존성 통제 |

SSO, Cruz APIM, EAI, CDC, 대내·대외 MCA, 통합관제, 배치작업관리 등은 이 장표에 없다. 선도 단계에서 온라인 API·채널 전문·관제 체계를 **전면 적용하지 않거나**, 별도 장표·후속 단계로 분리했을 가능성이 있다. 최소 I/F만으로도 파일 연계와 Artifact 관리 경로를 확보한다.

### 4.5 Data Layer

| 저장소 | 역할 | 비고 |
|---|---|---|
| 단말관리 DB | 단말·배포 관련 운영 데이터 | UI 서비스플랫폼 전용 |
| RDW (Oracle Exadata) | 준실시간·분석·조회 원천 | 선도에서 공통 데이터 원천으로 표현 |
| 마케팅플랫폼 DB | 선도 마케팅 온라인 업무 데이터 | 업무 트랜잭션 저장소 |

ADW가 장표에 없으므로, 선도 구간에서는 **업무 DB + RDW** 중심 조회·적재로 해석한다. RDW와 마케팅플랫폼 DB 간 동기화 방식(배치·CDC·직접 JDBC)은 장표에 명시되지 않아 구축 명세 확인이 필요하다.

### 4.6 형상·배포 Layer

```text
개발자 → GitLab(코드버전관리)
       → dev merge
       → GitLabRunner(빌드)
       → 취약점점검 / Dev Pipeline
       → 개발환경
```

| 단계 | 역할 |
|---|---|
| GitLab | 소스 버전 관리, 브랜치·머지 통제 |
| GitLab Runner | 빌드·테스트 실행 |
| 취약점점검 | 배포 전 보안 점검 |
| Dev Pipeline | 개발환경 배포 자동화 |
| 개발환경 | 선도 검증 실행 환경 |

운영 승격(eCAMS, 운영 Pipeline, Master merge 통제)은 장표에 없다. 선도개발은 **개발환경까지의 CI 경로 검증**에 초점을 둔다. 다만 Nexus가 I/F에 있으므로 Artifact 저장·의존성 관리는 선도부터 적용하는 것이 자연스럽다.

## 5. 주요 컴포넌트 분석

| 컴포넌트 | 주요 책임 | 핵심 연계 | 운영·선도 주의사항 |
|---|---|---|---|
| L4 | 진입점·부하분산 | Browser ↔ WEB | 헬스체크, TLS 종료 위치, 세션 고정 최소화 |
| UI WEB / 마케팅 WEB | 정적 콘텐츠·프록시 | L4 ↔ WAS | 보안 헤더, 접근로그, WAS 직접 노출 금지 |
| 단말관리·단말배포 WAS | 단말 수명주기 | 단말관리 DB, WebTopSuite | 배포 권한, 패키지 무결성 |
| 마케팅플랫폼 WAS | 선도 온라인 업무 | NH Cloud Framework, IMDG, 업무 DB | Timeout·TX·권한·감사 표준 적용 |
| IMDG | Session/Data Cache | WAS ↔ 원본 DB | TTL, 복제, 장애 시 Fail 정책 |
| FOS/MFT | 파일 연계 | 외부·내부 시스템 | 암호화, 재전송, 완료 마커 |
| IT메타 | 메타 등록·조회 | 개발·운영 자산 | 서비스ID·테이블·인터페이스 식별 |
| Nexus | Artifact·의존성 | GitLab Runner, 배포 | 버전·서명·승격 규칙 |
| RDW | 조회·분석 원천 | WAS, 적재 경로 | 읽기 부하, 최신성 SLA |
| 마케팅플랫폼 DB | 온라인 트랜잭션 | WAS | 백업, 스키마 버전, 롤백 |
| GitLab/Runner | 빌드·배포 | Dev Pipeline, Nexus | 브랜치 보호, 취약점 Fail 시 차단 |

## 6. 주요 처리 흐름

### 6.1 선도 온라인 조회·거래 흐름

```text
전용 Browser(선도개발)
  → L4
  → 마케팅 WEB
  → NH Cloud Framework / 마케팅플랫폼 WAS
  → (필요 시) SSO·권한 — 장표 미표시, 구축 시 별도 확인
  → IMDG Session/Data Cache
      ├─ Hit  → 결과 조립
      └─ Miss → 마케팅플랫폼 DB 또는 RDW 조회 → 캐시 갱신
  → 결과 반환
```

### 6.2 단말관리·배포 흐름

```text
전용 Browser
  → L4 → UI WEB → 단말관리 WAS / 단말배포 WAS
  → 단말관리 DB
  → (배포 산출물) Nexus 또는 배포 저장소
  → 단말/패키지 반영
```

### 6.3 파일 연계 흐름

```text
선도 업무 또는 배치 주체
  → FOS 또는 MFT
  → 파일 송수신·무결성 검증
  → 필요 시 마케팅플랫폼 DB / RDW 적재
```

### 6.4 형상·배포 흐름

```text
개발자 → GitLab → dev merge → GitLab Runner → 빌드
       → 취약점점검 → Dev Pipeline → 개발환경
       → (Artifact) Nexus 보관
```

개발 Artifact를 운영으로 승격하는 경로는 본 장표 범위 밖이다. 선도 완료 후 운영 장표의 eCAMS·운영 Pipeline과 연결해야 한다.

## 7. 레이어 간 호출 원칙

1. Browser는 L4와 WEB을 경유하며 WAS·DB에 직접 접속하지 않는다.
2. WEB은 화면·프록시에 집중하고 업무 로직을 보유하지 않는다.
3. 마케팅 WAS는 NH Cloud Framework 표준 경계를 따르며, 승인된 계정으로만 DB·RDW에 접근한다.
4. UI 서비스플랫폼과 마케팅플랫폼은 장애·배포 영향 범위를 분리한다.
5. 파일 교환은 FOS/MFT를 우선 사용한다.
6. 빌드 산출물은 Nexus에 버전 관리하고, 개발환경 배포와 연결한다.
7. IMDG는 원본 데이터의 소유자가 아니며, 캐시 실패 시 원본 조회 또는 명시적 오류로 전환한다.
8. 선도 범위에 없는 채널·실시간·운영 배포 경로는 임의로 우회 구현하지 않고 후속 단계에서 확장한다.
9. 요청 추적을 위해 GUID/Trace ID를 WEB·WAS·DB·파일 연계 로그에 유지한다(관제 컴포넌트가 장표에 없어도 선도부터 권장).

## 8. 품질 속성 평가

### 8.1 가용성

- L4와 다중 WEB/WAS 전제는 노드 장애 우회에 유리하다.
- IMDG·DB 단일 장애가 선도 전체 로그인·조회에 영향을 줄 수 있으므로 최소 이중화 기준을 선도 초기에 합의해야 한다.
- I/F가 최소화되어 있어 외부 연계 장애 면적은 작지만, FOS/MFT 장애 시 파일 기반 시나리오는 중단된다.

### 8.2 확장성

- WEB/WAS는 수평 확장이 가능하다.
- 선도 단계에서는 실시간 Kafka/EBM이 없어 이벤트 부하 확장은 후속 과제다.
- RDW 조회 폭주가 선도 성능의 병목이 될 수 있으므로 읽기 계정·쿼리 제한을 미리 둔다.

### 8.3 보안

- 장표에 SSO가 없더라도 선도 환경에 인증·인가를 생략해서는 안 된다. 별도 인증 방식 또는 SSO 선행 적용 여부를 범위서에 명시해야 한다.
- 단말배포 경로는 패키지 서명·권한·감사로그가 필요하다.
- Nexus·GitLab 접근 권한과 비밀정보는 소스와 분리한다.
- 취약점 점검 실패 시 Dev Pipeline 배포 차단 정책을 권장한다.

### 8.4 관측성

- 통합관제가 장표에 없으므로 선도 기간에는 최소 로그·메트릭·GUID 추적을 자체 구성해야 한다.
- 핵심 지표: 로그인/거래 성공률, WAS 응답시간, IMDG 적중률, DB 대기, 파이프라인 성공률, 취약점 Fail 건수.

### 8.5 선도 목적 적합성

- **적합**: NH Cloud Framework 표준 실행, UI/업무 분리, IMDG 세션, 최소 I/F, Dev CI, RDW·업무 DB 분리 검증.
- **제한**: 채널 다양성, 실시간 EBM, 광역 API/관제, ADW, 운영 배포 거버넌스는 본 장표만으로 검증 완료로 보기 어렵다.

## 9. 주요 위험과 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|

| IMDG 단일 구성 | 로그인·세션 장애 | 복제·TTL·원본 대체 경로를 선도 전에 정의한다. |
| RDW와 업무 DB 기준 불명확 | 조회 원천 혼선 | 선도 거래별 읽기 원천·SLA를 정의한다. |

| 단말배포 권한 미흡 | 잘못된 패키지 배포 | 승인·서명·롤백 절차를 WebTopSuite 운영에 포함한다. |
| 실시간 기능 후순위 | 선도 후 요구 폭증 | Kafka/EBM 확장 로드맵과 인터페이스 계약을 미리 초안화한다. |

## 10. 설계·운영 점검 체크리스트

- [ ] 전용 Browser URL, L4 VIP, 헬스체크·장애 우회 정책이 정의되어 있는가?

- [ ] NH Cloud Framework 공통 선·후처리·Timeout·TX 정책이 선도 WAS에 적용되는가?
- [ ] IMDG 키 네임스페이스·TTL·장애 시 Fail 정책이 정의되어 있는가?
- [ ] 단말관리 DB / 마케팅플랫폼 DB / RDW의 소유권과 접근 계정이 분리되어 있는가?
- [ ] FOS/MFT 파일 암호화·재전송·완료 확인 절차가 있는가?
- [ ] IT메타에 선도 서비스ID·인터페이스·테이블이 등록되는가?
- [ ] GitLab 브랜치 보호, Runner 빌드, 취약점 Fail 시 배포 차단이 동작하는가?
- [ ] Nexus Artifact 버전과 개발환경 배포가 연결되는가?
- [ ] 인증·인가가 장표 밖 구성이라도 선도 환경에 적용되어 있는가?
- [ ] GUID 기반 WEB·WAS·DB·파일 로그 추적이 가능한가?
- [ ] 선도 완료 후 운영형 마케팅플랫폼·채널·실시간·운영 Pipeline으로의 확장 계획이 있는가?
- [ ] DR/백업은 선도 범위에 포함하는지, 포함 시 RDW·업무 DB·IMDG 복구 순서가 있는가?

## 11. 종합 평가

이 아키텍처는 정보계 차세대의 **선도개발용 축소형 레이어드 구성**이다. UI 서비스플랫폼(WebTopSuite)과 마케팅플랫폼(NH Cloud Framework)의 이원화, IMDG 세션 공유, 단말·업무·RDW 데이터 분리, GitLab 기반 Dev CI라는 **표준 골격**을 먼저 검증하도록 설계되어 있다.

운영형 마케팅플랫폼·BI·데이터플랫폼 장표와 비교하면 Client·I/F·실시간·분석(ADW)·운영 배포가 빠져 있다. 이는 결함이라기보다 **선도 단계의 의도적 범위 축소**로 보는 것이 맞다. 선도 성공 기준은 기능 완결보다 **표준 실행 경로(Browser→L4→WEB→Framework/WAS→DB/RDW)와 배포·파일·메타 최소 거버넌스의 재현성**에 두어야 하며, 이후 채널·실시간·광역 I/F·운영 Pipeline을 동일 레이어 모델 위에 확장하는 로드맵이 필요하다.
