# 인터페이스 아키텍처 — BI포털 연관관계도 분석

## 1. 핵심 결론

이 장표는 **BI포털(BL)을 하나의 단일 애플리케이션으로 보지 않고, BI포탈·신용실적·OLAP·Self-BI의 4개 기능영역으로 분리한 내부 연관관계도**다.

원본 이미지에서 직접 확인되는 핵심 구조는 다음과 같다.

```text
BI포탈 BL
 ├─ BI포탈 PT
 ├─ 신용실적 CR
 ├─ OLAP OA
 └─ Self-BI SB
```

즉 장표의 핵심 메시지는 **BI포털이라는 상위 서비스 영역 아래에 서로 다른 분석·조회 목적의 하위 업무/서비스 모듈을 분리한다**는 것이다.

| 구분 | 원본 표기 | 아키텍처 의미 |
|---|---|---|
| 상위 영역 | BI포탈 BL | BI/분석 서비스 플랫폼 경계 |
| 하위 모듈 1 | BI포탈 PT | 포털/통합 진입 및 BI 서비스 |
| 하위 모듈 2 | 신용실적 CR | 신용·실적 관련 조회/분석 영역 |
| 하위 모듈 3 | OLAP OA | 다차원 분석 영역 |
| 하위 모듈 4 | Self-BI SB | 사용자 주도 분석 영역 |

이 그림만으로는 외부 시스템, DB, API Gateway, ETL 등의 세부 연계 경로가 직접 표현되지 않는다. 따라서 본 장표는 **상세 인터페이스 흐름도라기보다 BI포털 내부의 업무/기능 분류와 책임 경계를 나타내는 상위 연관관계도**로 해석하는 것이 적절하다.

2. BI포탈 내부 세부 업무단위 또는 분석단위가 **추가 상세화 대상**임

# 5. 모듈별 상세 분석

## 5.1 BI포탈 PT

### 원본 FACT

- 명칭: `BI포탈`
- 코드: `PT`
- BI포탈 BL 하위 모듈로 표시

### ANALYSIS

BI포탈 PT는 다음과 같은 역할을 수행하는 영역으로 해석할 수 있다.

- BI 서비스 통합 진입점
- 대시보드/리포트 메뉴 제공
- 사용자별 BI 콘텐츠 접근
- 분석 서비스 네비게이션
- 공통 조회·검색·메뉴 연계
- 권한 기반 콘텐츠 노출

### 인터페이스 관점

상세 인터페이스 구성도에서는 다음 항목을 추가 확인해야 한다.

- 인증/SSO 연계
- 사용자/권한 연계
- RDW/ADW 데이터 접근
- 리포트 엔진 연계
- OLAP 엔진 연계
- Self-BI 연계
- 메타데이터/데이터거버넌스 연계

---

## 5.2 신용실적 CR

### 원본 FACT

- 명칭: `신용실적`
- 코드: `CR`
- BI포탈 BL 하위 모듈

### ANALYSIS

신용실적 CR은 신용 관련 실적 데이터를 조회·분석하는 독립 기능영역으로 해석할 수 있다.

가능한 책임은 다음과 같다.

- 신용 관련 실적 조회
- 기간별/조직별/지점별 실적 분석
- 목표 대비 실적 비교
- 요약/집계 데이터 조회
- BI포탈 내 실적 화면 제공

### 확인 필요

- 실제 데이터 소스가 RDW인지 ADW인지
- 실적 데이터의 적재주기
- 온라인 조회인지 배치성 마트 기반 조회인지
- 신용실적 전용 마트 존재 여부
- 타 업무 시스템과의 직접 연계 여부

---

## 5.3 OLAP OA

### 원본 FACT

- 명칭: `OLAP`
- 코드: `OA`
- BI포탈 BL 하위 모듈

### ANALYSIS

OLAP OA는 BI포탈의 **정형·다차원 분석 기능**을 담당하는 영역으로 해석할 수 있다.

대표적인 책임은 다음과 같다.

- 다차원 분석
- Slice / Dice
- Drill-down / Roll-up
- Pivot 분석
- 집계 데이터 탐색
- 경영지표 분석
- 정형 분석 리포트

### 인터페이스 관점

OLAP은 일반적으로 다음과 같은 데이터 흐름을 필요로 한다.

```text
ADW / 분석마트
      ↓
OLAP Engine
      ↓
BI포탈 / 사용자
```

> 위 흐름은 일반적 구조에 기반한 **ANALYSIS**이며, 원본 이미지에 ADW 또는 OLAP Engine 연결선이 직접 표시된 것은 아니다.

---

## 5.4 Self-BI SB

### 원본 FACT

- 명칭: `Self-BI`
- 코드: `SB`
- BI포탈 BL 하위 모듈

### ANALYSIS

Self-BI SB는 사용자 주도형 분석 기능으로 볼 수 있다.

대표적인 책임은 다음과 같다.

- 사용자가 직접 데이터 선택
- Drag & Drop 기반 분석
- 사용자 정의 보고서
- 사용자 정의 차트/대시보드
- 개인/조직 공유 분석
- Ad-hoc Query
- 사용자 분석 결과 저장

### 중요 아키텍처 이슈

Self-BI는 자유도가 높은 만큼 다음 통제가 필요하다.

- 대용량 쿼리 통제
- 분석용 데이터셋 제한
- 민감정보 접근통제
- 사용자별 자원쿼터
- 장기쿼리 취소
- 데이터 반출통제
- 공유 리포트 권한관리

# 7. 인터페이스 아키텍처 관점

이 장표는 외부 인터페이스를 직접 표현하지 않지만, BI포털이라는 플랫폼 특성상 다음 인터페이스 유형이 반드시 존재해야 한다.

```text
사용자/채널
   ↓
BI포탈 PT
   ├─ 신용실적 CR
   ├─ OLAP OA
   └─ Self-BI SB
        ↓
분석 데이터
        ↓
RDW / ADW / 데이터마트
```

추가로 다음 연계가 필요할 가능성이 높다.

- 인증/SSO
- 사용자/조직/권한
- 데이터플랫폼
- 메타데이터
- 데이터품질
- 리포트/출력
- 로그/감사
- 운영관리

> 단, 위 항목들은 원본 장표에 직접 표시되지 않았으므로 **후속 인터페이스 상세도에서 확인 필요**하다.

# 8. 데이터 접근 원칙

BI포털은 대부분 조회/분석 플랫폼이므로 다음 원칙을 적용하는 것이 적절하다.

## 8.1 권장

```text
BI포탈
   ↓
승인된 분석 데이터셋 / View / Mart
   ↓
RDW / ADW
```

## 8.2 금지 또는 주의

```text
Self-BI
   ↓
운영 원천 테이블 직접 Full Scan
```

```text
OLAP
   ↓
온라인 업무 DB 직접 대량 조회
```

```text
사용자
   ↓
권한 없는 Raw Data 직접 추출
```

핵심은 BI부하가 온라인 업무의 안정성을 침해하지 않도록 **분석 데이터와 자원을 분리**하는 것이다.

# 9. 데이터플랫폼과의 관계 분석

앞서 데이터플랫폼 장표에서 확인된 구조와 연결하면, BI포털은 다음과 같은 관계를 가질 가능성이 높다.

```text
RDW
 ├─ 준실시간 보고서마트 RM
 └─ 준실시간 요약집계 ZD
          │
          └────────▶ BI포탈 PT / 신용실적 CR

ADW
 ├─ 분석통합요약집계 ZD
 ├─ 분석단위업무마트 UM
 ├─ 분석보고서마트 RM
 └─ 분석지원 DA
          │
          ├────────▶ OLAP OA
          └────────▶ Self-BI SB
```

> 이 연결은 **현재 장표와 직전 데이터플랫폼 장표를 함께 본 ANALYSIS**이며, 현재 이미지 자체에 RDW/ADW 연결선은 없다.

### 의미

- BI포탈/신용실적은 비교적 정형화된 보고/실적 조회 성격
- OLAP/Self-BI는 분석 중심의 ADW 활용 성격
- BI포털 전체는 데이터플랫폼의 **소비자 영역**으로 볼 수 있음

---

# 10. 보안 아키텍처 관점

BI포털은 다양한 사용자가 분석 데이터에 접근하기 때문에 다음 보안 통제가 중요하다.

| 영역 | 핵심 통제 |
|---|---|
| BI포탈 PT | 로그인/SSO/권한 |
| 신용실적 CR | 조직·업무 권한 |
| OLAP OA | Cube/Dimension 권한 |
| Self-BI SB | Dataset/Column/Row 권한 |
| 다운로드 | 데이터 반출 통제 |
| 공유 | 사용자/조직별 공유권한 |
| 로그 | 조회/다운로드/공유 감사 |

특히 Self-BI에는 다음이 필요하다.

- Column Level Security
- Row Level Security
- 개인정보 마스킹
- 다운로드 제한
- 공유 승인
- 외부 반출 차단

# 11. 성능 및 용량 관점

BI포털은 기능별 부하 특성이 다르다.

| 모듈 | 부하 특성 | 주요 성능 지표 |
|---|---|---|
| BI포탈 PT | 사용자 동시접속, 대시보드 조회 | 응답시간, 세션, TPS |
| 신용실적 CR | 집계/실적조회 | 조회시간, 집계 SQL |
| OLAP OA | 대규모 다차원 분석 | Cube 응답, CPU/MEM |
| Self-BI SB | 비정형/Ad-hoc 분석 | 장기쿼리, 동시쿼리, Temp |

### 핵심 원칙

```text
정형 BI 조회 부하 ≠ OLAP 부하 ≠ Self-BI Ad-hoc 부하
```

즉 모든 기능을 동일한 자원풀에서 무제한 처리하면 안 된다.

### 권고

- OLAP/ Self-BI 자원격리
- 장기쿼리 제한
- 사용자별 Query Timeout
- 사용자별/조직별 동시쿼리 제한
- 분석 전용 DB Resource Group
- 캐시/요약마트 활용

# 13. 오류 및 재처리 관점

BI포털은 데이터 적재보다 조회/분석 중심이므로 오류 대응은 다음이 중요하다.

- Mart 갱신 지연
- Query Timeout
- 권한 오류
- 분석엔진 오류

### OLAP 오류

- Cube 미갱신
- Dimension 불일치
- 집계 오류

### Self-BI 오류

- 쿼리 실패
- 사용자 정의 계산식 오류
- Dataset 권한 오류
- 장기쿼리 제한 초과

### 공통 대응

- 사용자 친화적 오류메시지
- Query/Report ID 로깅
- 원천 데이터 적재 상태 조회
- 재실행 가능 여부 제공

# 19. 최종 평가

이 장표는 BI포털을 단일 화면 시스템이 아니라 **4개의 독립된 분석 서비스 영역으로 나누는 상위 구조**를 보여준다.

```text
BI포탈 BL
  ├─ PT : BI포탈
  ├─ CR : 신용실적
  ├─ OA : OLAP
  └─ SB : Self-BI
```

구조적으로는 매우 단순하지만, 아키텍처 관점에서는 중요한 의미가 있다.

1. **정형 BI, 실적, OLAP, Self-BI의 책임을 분리한다.**
2. **사용자 분석 패턴별로 다른 실행·성능 특성을 관리할 수 있다.**
3. **향후 RDW/ADW 데이터플랫폼과의 인터페이스를 모듈별로 분리할 수 있다.**
4. **분석단위는 업무팀과 협의하여 추가 구체화해야 한다.**

특히 후속 상세설계에서는 반드시 다음이 필요하다.

```text
BI포탈 모듈
   ↓
데이터소스
   ↓
RDW / ADW / Mart
   ↓
Query / Report / Cube / Dataset
   ↓
권한 / 성능 / 운영
```

결론적으로 이 장표는 **BI포털의 업무영역을 구조화하는 상위 연관관계도**이며, 후속 BI 상세 인터페이스 설계, 데이터마트 매핑, 분석권한 설계, 성능·용량 설계의 기준점으로 활용할 수 있다.
