# 운영환경 마케팅플랫폼폼 시스템 구성 분석

## 0. 분석 범위와 판독 원칙

- 분석 대상: `운영환경 마케팅플랫폼폼 시스템 구성` 이미지
- 원본 분류: 환경별 Physical Architecture
- 이미지 설명: 마케팅플랫폼은 `서비스 제공 Zone`에 배치되며, 채널·채널통합·대내통합 Zone은 업무 연계 대상을 표시한다.
- 판독 원칙:
  - 명칭과 Zone 배치는 **이미지 사실**로 취급한다.
  - 화살표가 없는 배치도이므로 세부 방향·프로토콜·주기는 **해석**으로 구분한다.
  - 왼쪽·오른쪽 연계 시스템을 마케팅플랫폼 내부 컴포넌트로 오인하지 않는다.
  - WEB/WAS/AP/DB 블록은 논리 역할이며 서버 대수를 의미하지 않는다.

---

## 1. 핵심 결론

1. 마케팅플랫폼의 소유 경계는 **서비스 제공 Zone**이며, 채널·채널통합·대내통합은 인바운드/아웃바운드 연계 경계다.
2. 온라인 실행계는 `마케팅플랫폼 WEB/WAS`와 `미니 싱글뷰 WEB/WAS`로 분리되며, 이는 마케팅 업무와 고객 통합 조회의 부하·SLA·변경주기를 분리하려는 구조다.
3. `실시간 처리 AP`, `행동정보 처리 AP`, `고객 행동 데이터 AP`는 실시간 응답·이벤트 정제·고객 단위 서비싱을 분리한 전용 처리계다.
4. `마케팅플랫폼 DB(RDW)`는 서비스 핵심 데이터 경계다. 다만 이 이미지만으로 DB 소유 테이블과 Read/Write 권한을 확정할 수는 없다.
5. 대내 온라인 연계는 `API G/W·EAI·GSE`, 파일 연계는 `FOS·MFT`, 데이터 연계는 `ETL`로 분리된다.
6. `SSO`, `Control-M`, `NH Cloud FWK Master Solution`, `eCAMS`, 단말관리/배포, RD, 배치, UNO Dashboard는 마케팅 업무 로직이 아니라 **공통 인프라·운영 제어면**이다.
7. 구조의 핵심은 마케팅 업무를 하나의 대형 앱으로 합치는 것이 아니라, 채널·통합·업무·데이터·운영 책임을 Zone과 실행 컴포넌트로 격리하는 것이다.

## 2. Zone별 구성요소 전수 정리

| Zone | 하위 영역 | 이미지 구성요소 | 마케팅플랫폼과의 관계 |
|---|---|---|---|
| 채널 | 대내 채널 | 통합업무시스템, 정보계 단말 | 내부 사용자 요청 유입 |
| 채널 | 대고객 채널 | 인터넷뱅킹(콕뱅킹), 모바일(스마트뱅킹) | 고객 요청/이벤트 유입 |
| 채널 | 대외 채널 | 세부 시스템 미표시 | 대외 기관 연계 확장 경계 |
| 채널통합 | 온라인 통합(대내) | 영업점 MCA | 영업점 온라인 요청 통합·중계 |
| 채널통합 | 파일 통합(대내) | FOS | 대내 파일 전송·저장 중계 |
| 채널통합 | 데이터 통합 | 세부 시스템 미표시 | 대내 데이터 수집/제공 확장 경계 |
| 서비스 제공 | 마케팅플랫폼 | 마케팅플랫폼 WEB/WAS, 미니 싱글뷰 WEB/WAS, 3개 AP, DB(RDW) | 핵심 업무 소유 경계 |
| 서비스 제공 | 인프라 | SSO, Control-M, NH Cloud FWK Master Solution, eCAMS, 단말관리 WEB, 단말관리 WAS, 단말배포 WEB, 단말배포 WAS, 출력물(RD) WAS, 배치 AP, UNO Dashboard | 공통 인프라·운영 지원 |
| 대내통합 | 온라인 통합 | API G/W, API G/W↔EAI, GSE | 내부 시스템 API/전문 연계 |
| 대내통합 | 파일 통합 | FOS, FOS↔MFT | 파일·대량 자료 연계 |
| 대내통합 | 데이터 통합 | ETL | 배치·대량 데이터 이동 |

> 영문/한글이 혼용된 `WEB`, `WAS`, `AP`, `DB`, `API G/W`, `FOS`, `MFT`, `ETL`은 원본 라벨을 보존했다. 제품명·버전·서버 대수는 이미지에 표시되지 않는다.

## 3. 전체 아키텍처 텍스트 그림

### 3.1 Zone과 소유 경계

```text
┌───────────┐  ┌───────────────┐  ┌───────────────────── 서비스 제공 Zone ────────────────────┐  ┌───────────┐
│ 채널 Zone  │  │ 채널통합 Zone  │  │                                                         │  │ 대내통합  │
│            │  │               │  │  ┌─ 마케팅플랫폼 소유 경계 ────────────────────────┐  │  │ Zone       │
│ 통합업무  │  │ 영업점 MCA    │  │  │ 마케팅 WEB → 마케팅 WAS                         │  │  │ API G/W    │
│ 정보계단말  ├→│ FOS           ├→│  │ 미니 싱글뷰 WEB → 미니 싱글뷰 WAS             │  │←├─│ EAI / GSE  │
│ 인터넷/모바일│  │ 데이터통합   │  │  │ 실시간 AP | 행동정보 AP | 고객 행동데이터 AP   │  │  │ FOS / MFT  │
│ 대외채널   │  │               │  │  │                 ↕                                    │  │  │ ETL        │
└───────────┘  └───────────────┘  │  │            마케팅플랫폼 DB(RDW)                    │  │  └───────────┘
                                  │  └─────────────────────────────────────────────────────┘  │
                                  │                                                         │
                                  │  ┌─ 공통 인프라·운영 제어면 ───────────────────────────┐  │
                                  │  │ SSO | Control-M | NH Cloud FWK Master | eCAMS       │  │
                                  │  │ 단말관리/배포 WEB·WAS | RD WAS | 배치 AP | UNO     │  │
                                  │  └─────────────────────────────────────────────────────┘  │
                                  └─────────────────────────────────────────────────────────┘
```

### 3.2 온라인 요청 흐름

```text
[대내 단말 / 인터넷·모바일 채널]
                  │
                  ▼
       [영업점 MCA / 채널통합]
                  │  인증·전문·라우팅
                  ▼
       [마케팅 WEB / 미니 싱글뷰 WEB]
                  │
                  ▼
       [마케팅 WAS / 미니 싱글뷰 WAS]
                  │
          ┌───────├───────┐
          ▼       ▼       ▼
   [실시간 AP] [행동정보 AP] [고객행동 AP]
          └───────├───────┘
                  ▼
             [DB(RDW)]
                  │
                  ▼
[응답 → WAS → WEB → 채널통합 → 원 채널]
```

> 이 순서는 일반적인 요청 흐름을 장표의 배치에 대입한 **해석**이다. 실제로 모든 요청이 3개 AP를 경유한다고 확정하면 안 된다.

### 3.3 대내 통합별 아웃바운드 흐름

```text
온라인/API : WAS/AP → API G/W → EAI 또는 GSE → 내부 대상 시스템
파일       : WAS/AP → FOS → MFT → 내부/대외 대상
데이터   : DB/RDW ↔ ETL ↔ 내부 데이터플랫·시스템
출력물     : WAS → 출력물(RD) WAS → 보고서/파일 응답
배치       : Control-M → 배치 AP → 업무/AP/DB 작업
```

## 4. 마케팅플랫폼 핵심 컴포넌트 분석

### 4.1 마케팅플랫폼 WEB/WAS

| 컴포넌트 | 책임 | 포함하면 안 되는 책임 |
|---|---|---|
| 마케팅플랫폼 WEB | TLS 종단 또는 Reverse Proxy, 정적 자원, WAS 라우팅, 접속 제어 | 업무 DB 직접 접근, 마케팅 판단 로직 |
| 마케팅플랫폼 WAS | 마케팅 업무로직, 인증/권한 적용, AP·DB·연계 조합 | 대량 ETL, 장시간 배치, 임의 파일 전송 |

WEB→WAS는 무상태 라우팅을 우선하되, SSO/세션이 필요하면 공유 세션 저장소나 토큰 기반으로 인스턴스 종속성을 최소화해야 한다.

### 4.2 미니 싱글뷰 WEB/WAS

- 고객 식별자를 기준으로 고객·계좌·상품·행동 요약을 조합하는 조회 접점으로 해석한다.
- 읽기 집약적 부하가 마케팅 쓰기/관리 거래를 침해하지 않도록 커넥션풀·타임아웃·자원그룹을 분리한다.
- 개인정보·신용정보에 대한 화면 마스킹, 조회 이력, 역할/조직별 인가가 필수다.
- RDW 지연 시 최종 갱신시각 표시, 부분 정보 제공, 재시도 제한 등 저하 모드를 정의한다.

### 4.3 전용 AP 3종

| AP | 주요 역할 | 처리 특성 | 장애 시 우선 조치 |
|---|---|---|---|
| 실시간 처리 AP | 채널/이벤트 기반 실시간 판단·응답 | 낮은 지연, 높은 TPS | 유실방지, 빠른 우회/저하 |
| 행동정보 처리 AP | 행동 이벤트 정제·분류·집계 | 스트림/미니배치 가능 | 체증 허용, 재처리 큐 보전 |
| 고객 행동 데이터 AP | 고객 단위 행동 데이터 조회·제공 | 읽기 집약, 고객 키 기반 | Cache/RDW 저하 모드 |

AP 간 데이터를 공유 DB 테이블에 임의로 쓰는 방식은 결합도를 높인다. API, 이벤트, 승인된 View/테이블 계약 중 하나로 소유권을 명확히 해야 한다.

### 4.4 마케팅플랫폼 DB(RDW)

**권고 경계**

- 신선도가 중요한 고객·행동·마케팅 조회를 제공한다.
- 온라인 질의와 AP 읽기가 대량 ETL/자유분석에 의해 침해되지 않도록 자원을 격리한다.
- Domain/Table/View Owner와 서비스별 Read/Write Matrix를 정의한다.
- 업무 WAS/AP의 직접 접속은 전용 서비스 계정, 최소권한, 쿼리 타임아웃으로 통제한다.

**미확인**

- `DB(RDW)`가 마케팅 전용 스키마인지, 전사 RDW의 논리 영역인지
- 주소재·복제·백업·HA·DR 구성
- 쓰기 Source of Truth와 동기화 방향

## 5. 연계 아키텍처 분석

### 5.1 채널→마케팅플랫폼

| 경로 | 주요 통제 | 금지 사항 |
|---|---|---|
| 대내 단말→영업점 MCA→WEB/WAS | 사용자/단말 인증, 전문 표준화, GUID, timeout | 단말의 WAS/DB 직접 접근 |
| 대고객 채널→채널통합→WEB/WAS | 채널 인증, Rate Limit, 위변조 방지, 멱등성 | 채널별 전문/보안 규칙을 WAS에 개별 하드코딩 |
| 대외 채널→통합→WEB/WAS | 기관 인증서, IP/네트워크, 재전송, 대사 | 대외 원문을 업무 로직이 직접 파싱 |

### 5.2 마케팅플랫폼→대내통합

| 연계 유형 | 표준 경로 | 실패 처리 |
|---|---|---|
| 동기 API | WAS/AP→API G/W→내부 서비스 | 연결/Read timeout, Circuit Breaker, 제한 재시도 |
| 전문/EAI | WAS/AP→API G/W→EAI→대상 | 상관 ID, 오류전문, DLQ/재처리, 대사 |
| GSE | WAS/AP→GSE→대상 | 거래 기한·오류코드·재시도 정책 확정 필요 |
| 파일 | WAS/AP→FOS→MFT→대상 | 파일 ID, 해시, 사이즈, 암호화, 재전송, 완료 통지 |
| 데이터 | DB/RDW↔ETL↔대상 | 체크포인트, 건수/합계, 중복·누락 대사 |

`API G/W`, `EAI`, `GSE`, `FOS`, `MFT`, `ETL`은 서비스 제공 Zone의 마케팅 앱이 아니라 대내통합 Zone의 공통 연계 자산으로 관리해야 한다.

### 5.3 파일 처리

```text
업로드: 채널 → FOS/파일통합 → 업무 메타데이터 등록 → 후속 처리
다운로드: 업무 → FOS GET → Stream 응답 → 채널
대량전송: 업무 → FOS → MFT → 대상 + 완료/해시 대사
```

파일 바이너를 온라인 전문 DB에 직접 저장하기보다 FOS/Object Storage에 보관하고 업무 DB는 파일 ID·소유자·해시·보존기간을 관리하는 구조가 적합하다.

## 6. 공통 인프라·운영 컴포넌트

| 컴포넌트 | 해석된 역할 | 핵심 운영 통제 |
|---|---|---|
| SSO | 단일인증·세션/토큰 연계 | nonce/replay 방지, 세션 만료, 권한 재확인 |
| Control-M | 배치 스케줄·의존성·재시작 제어 | Job ID, 영업일, 중복방지, 재시작점 |
| NH Cloud FWK Master Solution | 프레임워크 마스터/운영 관리 솔루션으로 해석 | 구성 배포, 서비스 카탈로그, 변경이력 |
| eCAMS | 정확한 제품/기능은 이미지만으로 미확인 | 소유팀, 연계, 계정, 장애영향 확인 |
| 단말관리 WEB/WAS | 단말·정책·상태·이력 관리 | 최소권한, 감사, 대상 오선택 방지 |
| 단말배포 WEB/WAS | 단말 소프트웨어/정책 배포 | 서명, 버전, Canary, Rollback |
| 출력물(RD) WAS | 보고서 렌더링·출력 | 대용량 제한, 워터마크, 임시파일 정리 |
| 배치 AP | 업무·집계·수집 배치 | JobRepository, 멱등성, 재시작 |
| UNO Dashboard | 서비스·배치·장애 가시화로 해석 | 실패/지연 알람, 데이터 신선도, 권한 |

`eCAMS`의 약어·제품 의미는 이미지에서 확인되지 않으므로 임의로 확장하지 않는다.

## 7. 보안·가용성·운영 원칙

### 7.1 보안 경계

```text
채널 신뢰 경계
  → 채널통합 신뢰 경계
    → WEB 접점 경계
      → WAS/AP 업무 경계
        → DB/RDW 데이터 경계
          → 대내통합 API/파일/데이터 반출 경계
```

- 각 경계에서 주체 인증, 요청 무결성, 인가, 감사, timeout을 다시 적용한다.
- WEB은 DB에, 채널은 WAS/DB에, 대외 시스템은 AP/DB에 직접 접근하지 않는다.
- FOS/MFT의 파일은 암호화·악성코드 검사·해시·보존기간·반출 승인을 적용한다.
- 고객 행동데이터는 수집 목적, 항목 최소화, 마스킹, 보존/파기, 조회 이력을 통제한다.

### 7.2 가용성과 장애 반경

| 장애 | 주요 영향 | 저하/복구 원칙 |
|---|---|---|
| 채널통합/MCA | 대내 요청 유입 중단 | 채널 재시도 폭주 제어, 우회 경로 |
| 마케팅 WEB | 접속 불가 | L4 제외, 복수 인스턴스 |
| 마케팅 WAS | 업무 오류/세션 영향 | 무상태화, 공유세션, Circuit Breaker |
| 실시간 AP | 실시간 마케팅 중단 | 기본/미제공 응답, 이벤트 보전 |
| 행동정보 AP | 지표 신선도 저하 | 큐 적체, 체크포인트 재처리 |
| RDW | 싱글뷰·행동 조회 저하 | 읽기 복제본, 최종갱신 표시, 부분 응답 |
| API G/W/EAI | 내부 연계 실패 | timeout, 적합한 재시도, 비동기 보상 |
| FOS/MFT | 파일 연계 지연 | 상태 조회, 멱등 재전송, 해시 대사 |
| ETL | 데이터 신선도 저하 | 체크포인트 재개, 건수/합계 대사 |

### 7.3 관측성

모든 경로에 `GUID/상관 ID`, `채널 ID`, `serviceId`, `사용자/고객 비식별화 ID`, `배치/파일 ID`를 적절히 전파해야 한다.

```text
채널 → MCA/Gateway → WEB → WAS → AP → DB
          │          │      │      │     │
          └──────────└──────└──────└─────┘
               동일 GUID/상관 ID로 거래로그·메트릭·오류를 결합
```

## 8. 현재 TCF 저장소와의 대응

### 8.1 논리 대응

| 이미지 구성 | TCF 근거 | 판정 |
|---|---|---|
| 채널 Relay | `tcf-ui`, `tcf-uj` | 부분 대응; 실제 영업점 MCA와 동일 제품은 아님 |
| API G/W | `tcf-gateway` | 구조 대응 |
| EAI | `tcf-eai`, serviceId 기반 HTTP 연계 | 구조 대응 |
| 마케팅 WAS/AP | `sv-service`, `ic-service`, `mg-service` 등 독립 업무 WAR | 부분 대응 |
| 온라인 프레임워크 | `tcf-core`, `tcf-web`, `tcf-cache` | 설계 정합 |
| SSO/인증 | `tcf-jwt`, `tcf-gateway`, Spring Session | 구조 대응; 이미지 SSO 제품과 동일성은 미확인 |
| 파일 | `tcf-om` UD, `/ud/files`, Object Storage/FOS 연계 설계 | 구조 대응 |
| 배치 AP | `tcf-batch` | 부분 대응 |
| 운영 대시보드 | `tcf-om`, `tcf-batch`, `/ui/om/admin/dashboard.html` | UNO와 개념 대응, 제품 동일성 미확인 |
| RD 출력 | `/rd/{serviceId}` 연계 설계 | 구조 대응 |
| RDW | 업무 WAR Datasource/Mapper hook, 운영 Oracle RDW 목표 | 현재 샘플/H2 중심, 운영 매핑 미확인 |

### 8.2 현행 저장소의 논리 흐름

```text
브라우저/채널
  → tcf-uj(채널 Relay)
  → tcf-gateway(라우팅·세션/JWT 관문)
  → 업무 독립 WAR(sv/ic/mg/...)
  → TCF Handler → Service → DAO/Mapper → RDW/ADW hook

업무 간 연계
  → tcf-eai + HTTP/serviceId

운영
  tcf-batch → AP/DB/세션/배포 상태 수집
            → OM 테이블 MERGE
  tcf-om    → 운영 대시보드 조회·관리
```

### 8.3 구현 판정의 한계

- 저장소는 소스·로컬/샘플 구성으로 논리 정합성을 확인할 수 있다.
- 실제 `영업점 MCA`, `GSE`, `FOS`, `MFT`, `ETL`, `eCAMS`, `Control-M`의 운영 엔드포인트·계정·토폴로지는 확인되지 않는다.
- `Server → JVM → WAR → ServiceId → Datasource/RDW → HA/DR`는 실제 배포·런타임 증적으로 별도 확정해야 한다.
- `code-understand` 자동 추출기는 로컬 설정 권한 문제로 이전 실행에서 사용할 수 없었고, 이번 분석은 `rg` 교차 검색과 근거 문서 열람으로 대체했다.

## 9. 운영 지표와 알람

| 영역 | 핵심 지표 | 주요 알람 |
|---|---|---|
| 채널/MCA | TPS, 성공률, p95/p99, 전문 변환 시간 | 오류율, timeout, 큐 적체 |
| WEB | Active connection, 4xx/5xx, upstream latency | 5xx 증가, 후단 제외, TLS 만료 |
| WAS | TPS, p95/p99, JVM Heap/GC/Thread, DB Pool | GC 지연, Thread/Pool 고갈 |
| 실시간 AP | Event lag, 판단 시간, 유실/중복 | Lag, 재처리 큐, 에러율 |
| 행동 AP | 수집건수, 지연, 품질오류 | 누락/스키마 오류 |
| RDW | Query p95, connection, lock, replication/freshness | Slow Query, 세션 고갈, 신선도 저하 |
| API/EAI | 호출량, 성공률, downstream latency | Circuit open, timeout, DLQ |
| FOS/MFT | 전송량, 성공률, 재전송, 해시 일치 | 용량, 무결성, 체증 |
| ETL/배치 | 시작/종료, 처리건수, 재시작, 정합성 | SLA 초과, 중복/누락 |
| SSO | 인증 성공률, 응답시간, 세션 수 | nonce/ticket 검증 실패, 세션 저장소 장애 |

## 11. 사실·해석·미확인 분리

### 11.1 이미지에서 확정 가능한 사실

- 마케팅플랫폼은 서비스 제공 Zone에 배치된다.
- 마케팅플랫폼은 WEB 2종, WAS 2종, AP 3종, DB(RDW) 블록으로 표시된다.
- 채널, 채널통합, 대내통합의 대상 시스템이 별도 Zone에 표시된다.
- 서비스 제공 Zone 하단에 공통 인프라 구성요소가 표시된다.

### 11.2 아키텍처 해석

- 일반 요청은 채널→채널통합→WEB→WAS/AP→DB 순으로 흐른다.
- API/EAI/GSE, FOS/MFT, ETL은 각각 온라인·파일·데이터 연계 통로다.
- 싱글뷰와 전용 AP는 부하·SLA·장애 반경 격리를 위해 분리되었다.

### 11.3 추가 증적 없이 확정할 수 없는 항목

- 화살표·연결선이 없으므로 실제 호출 방향과 모든 경로
- 각 블록의 서버 대수, Hostname, IP, Port, 제품, 버전
- 실제 WEB→WAS 라우팅과 JVM→WAR→ServiceId 배포
- DB(RDW) 스키마·테이블·Read/Write 소유권
- GSE·eCAMS의 정확한 제품/기능과 연계 세부정보
- HA/DR, RTO/RPO, Backup, 네트워크 ACL, 인증서·비밀정보 관리

---

## 12. 최종 평가

이 구성은 **채널 접점, 채널 통합, 마케팅 실행, 대내 API/파일/데이터 통합, 공통 운영 제어**를 Zone별로 분리한 아키텍처다. 마케팅플랫폼의 응집도는 유지하되, 연계·파일·ETL·배치·인증·운영을 공통 자산으로 분리해 재사용과 통제를 확보한다.

최종 운영 승인을 위해서는 `채널→엔드포인트`, `WEB→WAS`, `WAS/AP→DB`, `WAS/AP→대내통합`, `Server→JVM→WAR→ServiceId`, `운영→DR`의 실제 매핑을 설정·배포·자산 증적으로 닫아야 한다.
