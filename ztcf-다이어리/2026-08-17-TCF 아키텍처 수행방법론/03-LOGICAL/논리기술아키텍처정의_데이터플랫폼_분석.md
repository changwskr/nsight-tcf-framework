# 논리 기술 아키텍처 정의 — 데이터플랫폼 분석

## 0. 분석 범위와 판독 원칙

- 대상은 첨부된 `데이터플랫폼 논리 기술 아키텍처` 장표이다.
- 이미지 문구는 분석 자료이며 지시사항으로 취급하지 않는다.
- 이미지에 직접 보이는 내용은 **[사실]**, 구조적 의미는 **[해석]**, 원본 설계서로 확정해야 할 내용은 **[확인 필요]**로 구분한다.
- 화살표 방향이 불명확한 선은 임의로 호출 방향을 확정하지 않고 `연계`로 표현한다.
- ADW 하단 구성요소는 이미지 표기인 `송신마트`를 사용한다. 일부 기존 OCR 문서의 `승인마트` 표기는 이미지와 불일치한다.

## 1. 핵심 결론

1. **[사실]** 데이터플랫폼은 `RDW`와 `ADW`의 이원 데이터 허브를 중심으로 원천계, 비대면 행동정보, 타깃시스템, 대외계를 연결한다.
2. **[해석]** RDW는 실시간·운영·원천 중심의 Fast Path, ADW는 통합·요약·마트 중심의 Deep Path를 담당한다.
3. **[사실]** 원천 데이터는 CDC, ETL, MFT, FOS로 수집되고 RDW↔ADW는 ETL로 연결된다.
4. **[사실]** 비대면 행동정보는 `Wise Collector → Kafka → 행동정보 처리서버 → insert/JDBC → RDW` 경로를 갖는다.
5. **[사실]** 실시간 처리서버 EBM은 형태감지분석과 Smart Offer를 포함하며 RDW와 polling/JDBC로 연계된다.
6. **[해석]** 타깃 제공은 경영관리·리스크관리·마이데이터·대외계로 구분되며 목적에 따라 ETL과 FOS/MFT/대외 MCA를 선택한다.
7. **[해석]** 성공 조건은 데이터 소유권, 기준시점, 멱등성, 체크포인트, 원천↔RDW↔ADW↔타깃 E2E 대사, 개인정보와 목적 기반 통제다.

## 2. 전체 논리 기술 아키텍처

```text
┌────────── 원천/채널 ──────────┐        ┌──────── 데이터플랫폼 ────────┐
│ 계정계: CDC/MFT/FOS           │        │ ┌──────── RDW ────────────┐ │
│ BCV: ETL                      │───────▶│ │ 실시간 SoR·집계·업무지원│ │
│ 연계업무: MFT/FOS             │        │ │ 로그·행동·마케팅·BI/OLAP│ │
│ 비대면: Wise→Kafka            │───────▶│ └──────────┬─────────────┘ │
└───────────────────────────────┘        │            │ ETL          │
                                         │ ┌──────────▼─────────────┐ │
                                         │ │ ADW                    │ │
                                         │ │ 통합·요약·마트·송신마트│ │
                                         │ └──────────┬─────────────┘ │
                                         └────────────┼───────────────┘
                                                      │
                 ┌────────────────────────────────────┼─────────────────────┐
                 ▼                                    ▼                     ▼
        [경영관리/리스크관리]                  [마이데이터]             [대외계]
                ETL                              FOS/MFT            FOS/MFT/대외 MCA
```

## 3. 논리 계층

```text
L1 원천·채널
   계정계 / 코어뱅킹 / 연계뱅킹 / BCV / 연계업무 / 인터넷·스마트뱅킹
                                  │
                                  ▼
L2 수집·전송
   CDC / CDC 중계 / ETL / MFT / FOS / Wise Collector / Kafka
                                  │
                                  ▼
L3 실시간 처리
   행동정보 처리서버 / 실시간처리서버 EBM / insert / polling / JDBC
                                  │
                                  ▼
L4 운영 데이터 허브
   RDW: 실시간 SoR / 집계·분석 / 업무지원 / 로그·행동 / BI·OLAP·품질
                                  │ ETL
                                  ▼
L5 분석 데이터 허브
   ADW: 실시간 SoR / 통합·요약·집계 / 통합·분석·보고서·송신 마트
                                  │
                                  ▼
L6 제공·소비
   경영관리 / 리스크관리 / 마이데이터 / 대외계
```

## 4. 원천·수집 영역

| 원천 | 방식 | 데이터 성격 | 핵심 통제 |
|---|---|---|---|
| 코어뱅킹 | 실시간 CDC | 계정계 변경데이터 | 로그 위치, 순서, 중복, 유실, DDL 호환성 |
| 코어뱅킹 | MFT/FOS | 파일·대량 데이터 | 해시, 건수, 암호화, 완료표식, 재수신 |
| 연계뱅킹 | 연계 | 업무 연계 데이터 | 인터페이스 ID, 기준시점, 오류코드 |
| BCV | ETL | 집합·배치 데이터 | 기준일, 체크포인트, 재처리, 대사 |
| 연계업무 | MFT/FOS | 파일 데이터 | 송수신 확인, 중복 파일, 보존 |
| 인터넷/스마트뱅킹 | Wise Collector/Kafka | 고객 행동 이벤트 | eventId, 동의, 순서, 스키마, 보존 |

### 4.1 계정계 수집

```text
[코어뱅킹 DB Log]
      │ CDC Capture
      ▼
[CDC 중계]
      │ position/checkpoint
      ▼
[RDW 실시간 SoR]
      │
      └─ 원천건수·적용건수·키·시점 대사

[코어뱅킹/연계업무] ─ MFT/FOS ─▶ [긴급성 파일/적재 영역]
```

- CDC와 파일은 같은 데이터를 다른 속도로 제공할 수 있으므로 중복 공급 범위와 우선순위를 확정해야 한다.
- 소스 로그 보존기간은 최대 장애·복구 시간을 초과해야 한다.
- 파일 적재는 `도착→해시검증→건수검증→적재→대사→완료` 상태를 가져야 한다.

### 4.2 BCV·연계업무 수집

```text
[BCV] ── ETL ──▶ [Stage] ── Validate/Transform ──▶ [RDW/ADW]

[연계업무] ── FOS/MFT ──▶ [Landing] ── Load ──▶ [RDW]
```

- ETL은 원천 스냅샷과 규칙 버전을 보존해 재현 가능해야 한다.
- 수신 파일 이름만 믿지 않고 인터페이스 ID, 업무일자, sequence, checksum으로 식별한다.

## 5. RDW 구조와 책임

### 5.1 내부 구성요소

| # | RDW 구성요소 | 책임 |
|---:|---|---|
| 1 | 실시간 SoR | 실시간 원천성 데이터의 기준 상태 |
| 2 | 실시간 집계/분석 | 최신 데이터의 집계·판단 |
| 3 | 업무 지원 | 업무서비스용 조회·지원 데이터 |
| 4 | 로그 분석 | 업무·채널·시스템 로그 분석 |
| 5 | 긴급성 파일 | 긴급 또는 파일성 데이터 수용 |
| 6 | 마케팅 플랫폼 | 마케팅 업무 데이터 영역 |
| 7 | 원천행동 로그 | 고객 행동 원본 이벤트 저장 |
| 8 | Feedback | 분석·실행 결과의 환류 |
| 9 | BI 포탈 | BI 소비 데이터 |
| 10 | OLAP | 다차원 분석 영역 |
| 11 | 데이터 품질 | 품질 규칙·측정·결과 영역 |

```text
┌──────────────────────────── RDW ────────────────────────────┐
│ [실시간 SoR] → [실시간 집계/분석] → [업무 지원]           │
│ [긴급성 파일]                 [로그 분석]                   │
│ [마케팅 플랫폼] ◀── Feedback ── [원천행동 로그]             │
│                                                            │
│ [BI 포탈]              [OLAP]              [데이터 품질]    │
└────────────────────────────────────────────────────────────┘
```

### 5.2 RDW의 아키텍처 역할

- **[해석]** 실시간 유입과 운영 업무가 사용하는 최신 상태 및 원천에 가까운 데이터를 보유한다.
- JDBC insert, CDC, 파일, ETL이 집중되므로 온라인·수집·배치·보고서 워크로드를 계정·세션·자원 그룹으로 격리해야 한다.
- 원천행동 로그는 재처리를 위한 원본을 보존하되 개인정보·보존기간·파티션 삭제 정책이 필요하다.
- Feedback은 모델·캠페인·실시간 판단 결과를 다시 학습·업무 데이터로 환류시키는 폐루프를 만든다.

### 5.3 실시간 SoR 의미

```text
Source Change/Event
       │
       ▼
[수집 시점·원천키·원천버전 보존]
       │
       ▼
[RDW 실시간 SoR]
       │
       ├─ 현재 상태 조회
       ├─ 실시간 집계
       └─ ADW 분석 이관
```

SoR이라는 명칭만으로 RDW가 계정계의 법적 원장 역할을 대신한다고 해석해서는 안 된다. 어떤 항목의 최종 권위가 계정계인지 RDW인지 데이터 소유권 표로 확정해야 한다.

## 6. ADW 구조와 책임

### 6.1 내부 구성요소

| # | ADW 구성요소 | 책임 |
|---:|---|---|
| 1 | 실시간 SoR | 분석영역의 최신 원천성 데이터 |
| 2 | 통합/요약/집계 | 주제별 통합과 파생 지표 산출 |
| 3 | 통합마트 | 전사 공통 분석 마트 |
| 4 | 분석/보고서마트 | 분석·정형 보고서 소비 모델 |
| 5 | 송신마트 | 외부·타깃 제공용 데이터셋 |
| 6 | Feedback | 소비·분석 결과의 환류 |

```text
┌────────────────────────── ADW ───────────────────────────┐
│ [실시간 SoR]                                             │
│       │                                                  │
│       ▼                                                  │
│ [통합/요약/집계] → [통합마트] → [분석/보고서마트]       │
│       │                │                                 │
│       └────────────▶ [송신마트] ─────▶ 타깃/대외 제공    │
│                         ▲                                │
│                      Feedback                            │
└──────────────────────────────────────────────────────────┘
```

### 6.2 ADW의 아키텍처 역할

- RDW의 운영 모델을 분석 목적의 차원·집계·이력 모델로 변환한다.
- 통합마트는 공통 정의를, 분석/보고서마트는 소비 목적 최적화를, 송신마트는 인터페이스 계약을 담당한다.
- 지표 정의, 기준시점, SCD 처리, 결측·중복·지연 정책을 메타데이터로 관리해야 한다.
- Feedback은 분석 결과가 원천 데이터와 뒤섞이지 않도록 별도 계보와 버전을 갖는다.

## 7. RDW ↔ ADW 관계

```text
               Fast Path                          Deep Path
원천/이벤트 → [RDW] ─────── ETL ───────▶ [ADW] → 마트/타깃
               │   ▲                         │
               │   └──── Feedback ───────────┘
               └─ 운영·실시간                 └─ 통합·분석·제공
```

| 관점 | RDW | ADW |
|---|---|---|
| 주목적 | 운영·실시간·원천 수용 | 분석·통합·요약·제공 |
| 유입 | CDC, JDBC, MFT/FOS, ETL, Kafka 처리 결과 | RDW ETL 및 확정 원천 |
| 모델 | 원천·업무·최신 상태 중심 | 차원·이력·집계·마트 중심 |
| 소비 | 업무지원, 실시간분석, BI/OLAP, 품질 | 경영/리스크/마이데이터/대외 제공 |
| 지연 | 초·분·근실시간 | 배치·준실시간·기준시점 |
| 정합성 | 원천 위치·이벤트·파일 대사 | RDW→ADW→타깃 E2E 대사 |

### 7.1 ETL 경계

```text
[RDW Snapshot/Delta]
        │ extractWatermark
        ▼
[Validate] → [Transform] → [Load ADW] → [Reconcile]
     │             │             │             │
 ruleVersion   mappingVersion  runId       counts/amounts
```

- `runId + businessDate + target`을 실행 식별자로 사용한다.
- 재실행 방식은 append, merge/upsert, partition reload 중 하나로 작업별 고정한다.
- 완료 표시는 ADW 적재 성공뿐 아니라 건수·금액·키 대사 통과 이후에 기록한다.

## 8. 실시간 고객행동 처리

```text
[인터넷뱅킹 / 스마트뱅킹]
             │
             ▼
       [Wise Collector]
             │ publish
             ▼
          [KAFKA]
             │ subscribe
             ▼
  [실시간 행동정보 처리서버]
             │ insert/JDBC
             ▼
 [RDW 원천행동 로그 / 마케팅 플랫폼]
```

### 8.1 행동 이벤트 계약

```text
BehaviorEvent {
  eventId, eventType, occurredAt, receivedAt,
  customerRef, anonymousRef, sessionId, channel,
  action, attributes, consentScope,
  schemaVersion, traceId
}
```

- `eventId`로 중복을 제거하고 발생시각과 수신시각을 분리해 지연·역순을 처리한다.
- 고객 식별 전에는 익명 ID를 사용하고, 동의 범위 내에서만 고객 ID와 결합한다.
- Kafka Topic, Partition Key, 보존기간, Schema Registry, Retry Topic, DLQ 정책을 확정해야 한다.

```text
publish → partition append → consumer poll → process → JDBC insert → offset commit
                                  │ 실패
                                  ▼
                         retry topic → DLQ
```

처리 성공 전에 offset을 commit하지 않고 DB 저장과 offset 사이의 중복 가능성은 멱등 insert/upsert로 흡수한다.

## 9. 실시간 처리서버 EBM

```text
                    polling/JDBC
[RDW 최신 데이터] ───────────────▶ [실시간처리서버 EBM]
                                     ├─ 형태감지분석
                                     └─ Smart Offer(발송제어관리)
                                                │
                                                ▼
                                         [마케팅 실행/Feedback]
```

- **[사실]** 장표에 polling, 형태감지분석, Smart Offer(발송제어관리)가 보인다.
- polling은 구현이 단순하지만 지연·중복·RDW 부하를 만든다. 워터마크, 조회 범위, 폴링 주기, 소비 완료 상태를 명시해야 한다.
- 형태감지 규칙과 Offer 모델은 버전을 고정하고 판단 입력 스냅샷·결과·사유를 기록한다.
- 동일 고객에 대한 중복 Offer는 `rule/model + customer + action + timeWindow` 멱등 키로 통제한다.

## 10. Feedback 폐루프

```text
원천/행동 → RDW → 분석·판단 → ADW/마트 → 타깃 실행
    ▲                                           │
    └──────────── Feedback(성과·결과·반응) ─────┘
```

- Feedback은 어떤 캠페인·모델·규칙·데이터 버전으로 나온 결과인지 추적 가능해야 한다.
- 학습/성과 데이터는 원천 사실과 분리하고 생성 주체·시각·신뢰도를 기록한다.
- Feedback 지연이나 누락은 모델 성능과 업무 평가를 왜곡하므로 별도 SLA와 대사가 필요하다.

## 11. 타깃시스템 제공

### 11.1 경영관리·리스크관리

```text
[ADW 통합/분석/송신마트]
             │ ETL
             ├────────▶ [경영관리]
             │            종합수익관리·결산관리·업적평가·감사관리
             │            환원자료·금융정보제공·재무회계·기타
             │
             └────────▶ [리스크관리]
                          종합수익관리·결산관리·업적평가·감사관리
                          환원자료·금융정보제공·재무회계
```

- 장표의 세부 목록은 대상 업무 범주를 나타내며 실제 소유 시스템과 인터페이스는 확인이 필요하다.
- 회계·리스크 데이터는 기준일, 결산 상태, 재처리 잠금, 승인 이력을 강화해야 한다.

### 11.2 마이데이터

```text
[ADW 송신마트] ─ FOS/MFT ─▶ [마이데이터 / 개인자산관리]
```

- 목적·동의·제공항목·제공기간을 계약과 데이터셋에 반영한다.
- 송신 파일은 암호화, 해시, 레코드 수, 재전송, 보존·파기와 감사 기준을 적용한다.

### 11.3 대외계

```text
[ADW/RDW 송신영역] ─ FOS/MFT/대외 MCA ─▶ [대외계]
                                                 ├─ 농협범용솔루션(판독명)
                                                 ├─ 농협자산관리(판독명)
                                                 └─ 농협경제(판독명)
```

작은 글씨의 정확한 시스템명은 **[확인 필요]**다. 전문·파일별 인터페이스 ID, 레이아웃 버전, 문자셋, 암호화, ACK/NAK, 재전송 정책을 명세해야 한다.

## 12. 연계 방식 선택 기준

| 방식 | 사용 목적 | 지연 특성 | 핵심 복구 기준 |
|---|---|---|---|
| CDC | DB 변경의 실시간/준실시간 복제 | 낮음 | log position, 중복 제거, 대사 |
| Kafka | 행동 이벤트 스트리밍 | 낮음 | offset, eventId, DLQ |

| ETL | 대량 변환·적재·마트 생성 | 배치/준실시간 | runId, checkpoint, 대사 |
| FOS | 파일/오브젝트 전달 | 비동기 | checksum, complete marker |
| MFT | 관리형 대량 파일 전송 | 비동기 | 송수신 확인, 재전송, 감사 |
| 대외 MCA | 외부기관 전문 거래 | 동기/비동기 | 원거래 ID, 응답코드, 타임아웃 |
| Polling | 상태·대상 주기 조회 | 주기 의존 | watermark, 중복방지, lag |

```text
DataContract {
```

- 같은 지표는 RDW·ADW·타깃에서 동일한 비즈니스 정의와 계산 버전을 공유한다.


## 14. 데이터 품질과 대사

| 구간 | 대사 항목 |
|---|---|
| 원천→CDC 중계 | 시작/종료 position, transaction, 변경건수 |
| CDC→RDW | 키, insert/update/delete, commit 시점, 누락·중복 |
| 파일→RDW | 파일 수, checksum, header/trailer, 레코드 수 |
| Kafka→RDW | publish/consume 수, offset, eventId, DLQ |
| RDW→ADW | 기준일, partition, 건수, 금액, 핵심 지표 |
| ADW→타깃 | 송신/수신 수, ACK, 레이아웃, 기준시점 |
| Feedback | 실행 대상, 성공·실패·반응, 미매핑 건수 |

```text
INGESTED → VALIDATED → TRANSFORMED → LOADED → RECONCILED → PUBLISHED
               │              │          │             │
               └──── 실패 격리·재시도·선택 재개 ──────┘
```

## 15. 보안·개인정보·감사

```text
[원천/채널]
     │ 암호화·인증
     ▼
[Landing/RDW] ─ 목적·역할·행/열 통제 ─▶ [ADW/마트]
     │                                       │
     ├─ 행동로그: 동의·가명·보존             └─ 송신마트: 제공항목 최소화
     │
     └─ Audit: who / what / when / purpose / result
```

- 원천 수집, 분석, 마케팅 활용, 외부 제공은 서로 다른 처리 목적과 권한으로 분리한다.
- 행동 로그·Feedback·마이데이터는 민감도가 높으므로 가명화, 동의, 최소수집, 파기 증적이 필요하다.
- JDBC 계정은 원천 읽기, 적재, 조회, 운영을 분리하고 Secret을 코드·ETL 설정에 평문 저장하지 않는다.
- 개발·검증 환경에는 운영 원문을 그대로 복제하지 않고 가명·합성 데이터를 사용한다.

## 16. 성능·가용성·용량

### 16.1 워크로드 격리

```text
RDW
 ├─ CDC/Streaming ingest pool
 ├─ 업무지원 online query pool
 ├─ EBM polling pool
 ├─ ETL/Batch pool
 └─ BI/OLAP/품질 query pool

ADW
 ├─ ETL load pool
 ├─ 분석/보고서 pool
 └─ 타깃 송신 extract pool
```

- RDW에 다수 워크로드가 집중되므로 동시성·CPU·메모리·I/O·쿼리 시간 한도를 분리한다.
- Kafka lag, CDC lag, ETL 적재 지연, ADW 마트 완료시각을 하나의 데이터 신선도 체인으로 본다.
- 파티션은 업무일자·이벤트시각과 조회 패턴을 함께 고려하고 작은 파일·과다 파티션을 피한다.
- RDW/ADW HA, 백업, DR, RPO/RTO는 데이터 등급과 재생성 가능성을 기준으로 차등화한다.

## 17. 장애·재처리

```text
[장애 유형]
   ├─ CDC 단절 → position 보존 → 재연결 → 중복/유실 대사
   ├─ Kafka 소비 실패 → retry topic → DLQ → offset 재처리
   ├─ JDBC 실패 → timeout/rollback → 멱등 재시도
   ├─ ETL 실패 → checkpoint → 부분 재개 → 전체 대사
   ├─ 파일 오류 → 격리 → 재수신 → checksum/건수 검증
   ├─ Polling 중단 → watermark부터 재개 → 중복 제거
   └─ 타깃 장애 → 송신 보류 → 재전송 → ACK 대사
```

복구 완료는 프로세스 재기동이 아니라 원천·RDW·ADW·타깃 데이터 정합성의 확인으로 판단한다.

## 20. 이미지 사실 / 해석 / 확인 필요사항

### 이미지에서 직접 확인되는 사실

- 계정계 측에 코어뱅킹, 연계뱅킹, BCV, 연계업무가 표시된다.
- 수집 기술로 실시간 CDC, CDC 중계, MFT, FOS, ETL이 표시된다.
- RDW에는 실시간 SoR, 실시간 집계/분석, 업무지원, 로그분석, 긴급성 파일, 마케팅플랫폼, 원천행동로그, Feedback, BI포탈, OLAP, 데이터품질이 표시된다.
- ADW에는 실시간 SoR, 통합/요약/집계, 통합마트, 분석/보고서마트, 송신마트, Feedback이 표시된다.
- 비대면 채널, Wise Collector, Kafka, 행동정보 처리서버, 실시간처리서버 EBM이 표시된다.
- 타깃시스템은 경영관리, 리스크관리, 마이데이터, 대외계로 구분된다.

### 아키텍처 해석

- RDW는 실시간·운영 중심, ADW는 통합·분석·제공 중심이다.
- 실시간 고객행동과 계정계 변경을 RDW에 수용한 뒤 ADW 마트로 정제한다.
- Feedback은 분석·마케팅 실행 결과를 데이터 허브로 환류하는 폐루프이다.
- 타깃별 요구에 맞춰 ETL과 파일·전문 연계를 분리한다.

### 반드시 확인할 사항

- 모든 선의 실제 방향·프로토콜·포트·인증·주기·SLA
- RDW/ADW의 DBMS, 스키마, 데이터 소유권, 워크로드·용량·HA
- 실시간 SoR의 법적·업무적 권위 범위와 계정계 관계
- CDC 대상 테이블, 로그 보존, DDL 처리, 재처리·대사 정책
- Kafka Topic/Partition/Key/보존/Schema Registry/DLQ 정책
- polling 주기·워터마크와 EBM 규칙·모델·발송 통제
- RDW→ADW 적재 기준일, 증분 키, SCD, 늦은 데이터 처리
- 송신마트와 타깃별 계약·개인정보·보존·파기 기준
- 대외계 하위 시스템의 정확한 명칭과 인터페이스 방식
- 서버 수량, Zone, 방화벽, RTO/RPO, 백업·DR 구성

## 21. 종합 평가

이 장표는 데이터플랫폼을 단일 데이터베이스가 아니라 **다중 원천 수집, RDW 실시간 운영 허브, ADW 분석·마트 허브, Kafka 행동 이벤트, EBM 실시간 처리, 타깃별 데이터 제공**이 결합된 데이터 흐름 제어 체계로 정의한다. 구조적 장점은 Fast Path와 Deep Path의 분리, 다양한 수집·제공 방식의 명시, Feedback 폐루프다. 핵심 위험은 RDW 부하 집중, CDC/Kafka 중복·유실, polling 지연, RDW↔ADW 정합성, 송신 데이터 개인정보다. 데이터 계약, 워크로드 격리, 멱등 처리, 체크포인트, E2E 대사와 신선도 관측으로 이를 통제해야 한다.
