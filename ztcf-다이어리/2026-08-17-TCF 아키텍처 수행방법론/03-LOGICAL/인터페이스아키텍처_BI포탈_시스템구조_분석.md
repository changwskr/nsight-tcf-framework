# 인터페이스 아키텍처 — BI포탈 시스템 구조 분석

## 1. 분석 개요

첨부 장표의 **BI 포탈** 시스템·인터페이스 구성을 기준으로, BI 포탈 내부 모듈과 주요 연계 시스템 사이의 **연계 경계·프로토콜·중계 경로**를 분석한다.

장표는 좌측 **BI 포탈 내부 모듈**, 중앙 **API G/W(CruzAPIM)**, 우측 **주요 연계 시스템·Object Storage**로 구성된다. 기존 BI포털 **연관관계도**(BL 아래 PT/CR/OA/SB 분류)와 달리, 본 장표는 **모듈별 외부 연계 경로**를 직접 표현한 **시스템 구조·인터페이스 구성도**다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. `BL BP`/`BL BC`의 조직·배포 단위 의미, `MSTR` 제품 버전, CruzAPIM 정책, Object Storage 제품명은 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **내부 모듈 분리**: BI 포탈을 단일 WAS로 보지 않고, 포탈·엑셀 다운로드·빅데이터 시각화·웹정형 보고서·데이터 거버넌스 등 **기능 모듈로 분리**한다.
- **BL BP / BL BC 이원화**: 장표상 BI 포탈 영역이 **BL BP**와 **BL BC**로 나뉜다. BP는 다수 기능 모듈을, BC는 BI 포탈 모듈을 별도 박스로 둔다(배포·계층·역할 구분은 명세 확인 필요).
- **연계 중계의 표준화**: 엑셀 다운로드·시각화·웹정형 보고서의 외부 호출은 **Rest API + API G/W(CruzAPIM)** 를 경유한다.
- **OLAP은 UI Link**: BI 포탈 ↔ OLAP(MSTR)는 Rest가 아니라 **UI Link**로 연결된다. 화면·세션 문맥 기반 제품 연계로 해석한다.
- **거버넌스는 Object Storage 직결**: 데이터 거버넌스관리는 Object Storage와 **Rest API**로 연결되며, 장표상 CruzAPIM 박스와는 별도 경로로 그려져 있다.
- **연계 대상의 역할 분리**: OLAP(분석 UI), 데이터품질관리, 빅데이터, 코어뱅크, Object Storage가 목적별로 분리된다.

## 3. 장표 구성요소 전사

### 3.1 BI 포탈 내부 — BL BP

| 모듈 | 장표 표기 | 역할(해석) |
|---|---|---|
| BI 포탈 | BI 포탈 | 포털 진입·메뉴·통합 UI |
| 엑셀 다운로드 전용 | 엑셀 다운로드 전용 | 대용량·전용 엑셀 반출 처리 |
| 빅데이터 시각화포탈 | 빅데이터 시각화포탈 | 빅데이터 시각화·탐색 UI/서비스 |
| 웹정형 보고서 | 빅데이터 시각화포탈 (웹정형 보고서) | 웹 정형 보고서 생성·조회 |
| 데이터 거버넌스관리 | 데이터 거버넌스관리 | 데이터 정책·메타·거버넌스 관리 |

### 3.2 BI 포탈 내부 — BL BC

| 모듈 | 장표 표기 | 역할(해석) |
|---|---|---|
| BI 포탈 | BI 포탈 | BC 영역의 포탈 모듈(BP 포탈과 별도 박스) |

> `BL BP`/`BL BC`는 Business Process / Business Component, 또는 배포·계층 구분으로 추정되나 장표만으로 확정하지 않는다. 동일 명칭 `BI 포탈`이 BP·BC에 각각 있으므로 **동일 서비스의 계층 분리**인지 **별도 인스턴스**인지 명세 확인이 필요하다.

### 3.3 인터페이스 중계

| 구성요소 | 표기 | 역할 |
|---|---|---|
| API Gateway | API G/W (CruzAPIM) | Rest API 중계·정책(인증·할당량·라우팅) |
| UI Link | UI Link | 포탈 화면과 OLAP(MSTR) UI 연계 |
| Rest API | Rest API | 모듈↔게이트웨이 또는 모듈↔스토리지 HTTP API |

### 3.4 주요 연계 시스템·저장소

| 대상 | 역할(해석) |
|---|---|
| OLAP (MSTR) | 다차원 분석·보고서 실행(MicroStrategy 계열) |
| 데이터품질관리 | 데이터 품질 규칙·측정·결과 제공 |
| 빅데이터 | 빅데이터 저장·처리·조회 API |
| 코어뱅크 | 계정계·핵심 금융 데이터 연계 |
| Object Storage | 객체 저장(파일·산출물·거버넌스 자산 등) |

## 5. 인터페이스 매핑 (모듈 → 중계 → 대상)

| # | 출발 모듈 (BL BP) | 프로토콜 | 중계 | 도착 시스템 | 설계 의미 |
|---|---|---|---|---|---|
| 1 | BI 포탈 | UI Link | (직접 UI 연계) | OLAP (MSTR) | 분석 화면·세션 문맥 연결. 제품 UI 종속성. |
| 2 | 엑셀 다운로드 전용 | Rest API | CruzAPIM | 데이터품질관리 | 품질 결과·메타 조회 후 반출 통제에 활용 가능. |
| 3 | 빅데이터 시각화포탈 | Rest API | CruzAPIM | 빅데이터 | 시각화용 데이터·질의 API. |
| 4 | 빅데이터 시각화포탈 (웹정형 보고서) | Rest API | CruzAPIM | 코어뱅크 | 정형 보고서용 계정계·핵심 데이터 조회. |
| 5 | 데이터 거버넌스관리 | Rest API | (장표상 직결) | Object Storage | 거버넌스 산출물·파일·객체 저장. |
| — | BI 포탈 (BL BC) | (장표 미표시) | — | — | 외부 화살표 없음. 내부 컴포넌트 또는 별도 계층으로 해석. |

### 5.1 매핑에서 읽히는 설계 의도

1. **반출·시각화·보고서는 API 표준화**, **OLAP은 UI 제품 연계**로 이원화한다.
2. 엑셀 전용 모듈을 분리해 **대용량 다운로드가 포탈 본연 거래에 미치는 영향**을 줄인다.
3. 웹정형 보고서가 코어뱅크와 연결되므로 **계정계 조회 권한·트래픽·개인정보** 통제가 보고서 경로에 필수다.
4. 거버넌스 ↔ Object Storage는 분석 API 경로와 분리된 **자산·파일 저장 경로**다.

## 6. 주요 처리 흐름

### 6.1 포탈 → OLAP (UI Link)

```text
사용자 → BI 포탈(BL BP)
       → UI Link
       → OLAP (MSTR) 화면/세션
       → 분석·보고서 실행
```

- URL·토큰·사용자 문맥 전달 방식과 위변조 방지가 필요하다.
- OLAP 장애가 포탈 전체 로그인 장애로 번지지 않도록 격리한다.

### 6.2 엑셀 다운로드 → 데이터품질관리 (Rest + APIM)

```text
엑셀 다운로드 전용
  → Rest API
  → API G/W (CruzAPIM)
  → 데이터품질관리
  → 품질 결과/허용 여부 반영
  → 파일 생성·다운로드
```

- 대용량 응답은 동기 Rest 한도·타임아웃을 넘길 수 있으므로 비동기 생성·다운로드를 권장한다.
- 다운로드 감사로그(사용자, 데이터셋, 행 수, 사유)를 남긴다.

### 6.3 빅데이터 시각화 → 빅데이터 (Rest + APIM)

```text
빅데이터 시각화포탈
  → Rest API → CruzAPIM → 빅데이터
  → 질의/집계 결과 → 시각화 렌더링
```

### 6.4 웹정형 보고서 → 코어뱅크 (Rest + APIM)

```text
웹정형 보고서 모듈
  → Rest API → CruzAPIM → 코어뱅크
  → 조회 결과 → 보고서 조립
```

- 코어뱅크 호출은 읽기 전용·허용 API·쿼터·차단기를 강제한다.
- 개인정보 마스킹과 목적 외 재사용 금지.

### 6.5 데이터 거버넌스 → Object Storage (Rest)

```text
데이터 거버넌스관리
  → Rest API → Object Storage
  → 객체 업로드/다운로드/메타 갱신
```

- 버킷·경로·권한·암호화·보존 주기 정책이 필요하다.
- APIM 미경유라면 인증·감사·위협 탐지를 스토리지 접근 계층에서 보완한다.

## 7. 인터페이스 설계 원칙

1. **브라우저/포탈 모듈은 연계 시스템에 직접 JDBC/DB 접속하지 않는다.** (본 장표는 Rest·UI Link 중심)
2. **Rest 연계는 CruzAPIM을 기본 경로로 한다.** (인증, 라우팅, 할당량, 버전, Trace ID)
3. **OLAP 제품 종속 UI는 UI Link로 격리**하고, 데이터 API와 혼용하지 않는다.
4. **엑셀·대용량 반출은 전용 모듈**에서만 수행하고 포탈 본 거래 스레드와 분리한다.
5. **코어뱅크 연계는 최소 권한·읽기 중심·쿼터**를 적용한다.
6. **Object Storage 접근 계정은 거버넌스 전용**으로 분리하고, 분석 API 계정과 공유하지 않는다.
7. 모든 Rest 호출에 **GUID/Trace ID**를 전파하여 포탈·APIM·대상 시스템 로그를 연결한다.
8. BL BC의 BI 포탈에 외부 연계가 없다면, **내부 컴포넌트 경계**로 두고 BP 모듈의 연계만 외부 계약으로 관리한다.

## 8. BL BP / BL BC 해석 메모

| 가설 | 설명 | 확인 포인트 |
|---|---|---|
| A. 프로세스 vs 컴포넌트 | BP=업무 기능 묶음, BC=공통·기반 컴포넌트 | 배포 단위, 패키지, 담당 팀 |
| B. 프레젠테이션 vs 비즈 컴포넌트 | BC가 공통 BI 포탈 엔진, BP가 기능 UI | 호출 방향(BC→BP 여부) |
| C. 이중 표기 | 동일 포탈의 다른 뷰 | 인스턴스·URL·WAR 수 |

장표만으로는 A~C를 확정할 수 없다. **연관관계도(PT/CR/OA/SB)** 와 본 시스템 구조도를 매핑할 때도, PT≈포탈, OA≈OLAP UI Link, 시각화·보고서≈Self-BI/포털 확장으로 **느슨히 대응**할 수 있으나 1:1 동치는 아니다.

## 9. 품질·위험과 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| UI Link의 느슨한 세션 결합 | 위변조·SSO 불일치 | 단기 서명 토큰, 허용 URL, 로그아웃 연동 |
| 엑셀 동기 Rest | APIM·대상 시스템 타임아웃 | 비동기 Job + 다운로드 URL, 용량·행 제한 |
| 웹정형→코어뱅크 직접성 | 계정계 부하·정보 유출 | APIM 쿼터, 캐시/마트 경유, 필드 최소화 |
| 거버넌스→Storage APIM 우회 | 정책·감사 공백 | APIM 경유 또는 Storage 게이트웨이·감사 강제 |
| 모듈 수 증가 | 중복 인증·중복 캐시 | 공통 인증 라이브러리, 공유 세션 정책 |
| BL BP/BC 모호성 | 배포·장애 책임 불명 | 배포 단위·의존 방향을 아키텍처 결정으로 고정 |
| 품질관리↔엑셀만 연결 | 다른 모듈 품질 미검증 | 시각화·보고서 경로에도 품질 게이트 적용 검토 |

## 11. 종합 평가

이 장표의 BI 포탈 시스템 구조는 **기능 모듈을 분리하고, 외부 연계를 UI Link와 Rest(APIM)로 이원화한 인터페이스 아키텍처**다. OLAP은 제품 UI 경로로, 엑셀·시각화·보고서는 CruzAPIM 경유 Rest로, 거버넌스 자산은 Object Storage Rest로 연결한다.

안정성과 보안은 모듈 수보다 **APIM 정책 일관성, 코어뱅크 보호, 대용량 반출 통제, UI Link 문맥 보호, Storage 접근 감사**에 좌우된다. BL BP/BC 구분과 거버넌스 경로의 APIM 경유 여부는 후속 확정이 필요한 핵심 모호점이다.
