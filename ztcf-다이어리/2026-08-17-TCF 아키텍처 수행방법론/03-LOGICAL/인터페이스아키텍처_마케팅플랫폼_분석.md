# 인터페이스 아키텍처 — 마케팅 플랫폼 분석

## 1. 핵심 결론

장표의 마케팅 플랫폼은 크게 두 처리 영역으로 구성된다.

1. **온라인 애플리케이션**: 채널 요청을 JSON/HTTP 또는 표준전문으로 수용하고 미니 싱글뷰, 고객·상품·상담·캠페인 등의 서비스를 제공한다.
2. **행동정보 처리**: 인터넷·스마트뱅킹의 고객 행동 로그를 Kafka로 수집하고, 행동정보 DB와 EBM을 통해 실시간 마케팅 이벤트를 처리한 뒤 UMS로 메시지를 발송한다.

```text
온라인 업무
대내 업무/MCA·정보 단말·MCI
        → JSON/HTTP·표준전문
        → 마케팅 플랫폼 온라인 애플리케이션
        ↔ API G/W·EAI·GSE
        ↔ 대내 연계업무

행동 이벤트
인터넷/스마트뱅킹
        → 비대면 로그
        → Wise Collector Proxy → Wise Collector
        → Kafka → 고객 행동 데이터 → 행동정보처리 → 행동정보 DB
        → 실시간 처리 EBM → UMS → SMS/PUSH/e-Mail
```

이 아키텍처의 핵심은 **고객의 동기 온라인 거래와 비동기 행동 이벤트 처리를 분리**하는 것이다. 행동정보 수집·분석 장애가 고객 거래 응답에 영향을 주지 않도록 격리하고, 온라인·이벤트·메시지 전 과정은 GUID와 Event ID로 연결해야 한다.

## 2. 장표 영역 및 구성요소 전사

### 2.1 채널

- 대내 채널: 업무 시스템
- 정보 단말
- 대고객 채널: 인터넷 뱅킹, 스마트 뱅킹
- 비대면 로그
- SMS, PUSH, e-Mail

### 2.2 채널 통합

- 영업점 MCA
- MCI
- Wise Collector Proxy
- Wise Collector
- UMS

### 2.3 차세대 정보계 — 마케팅 플랫폼

온라인 애플리케이션:

- 미니 싱글뷰
- 공통
- 상담판매
- 통합상품
- 통합고객
- 개인고객
- 기업고객
- 행동정보
- 캠페인
- 컨텐츠
- 메시지
- 영업지원
- CS
- EBM
- `데모`로 표기된 별도 구성요소

행동정보 처리:

- 고객 행동 데이터
- 행동정보처리
- 행동정보 DB
- 실시간 처리 EBM

### 2.4 대내 통합

- 온라인 통합: API G/W + EAI, API G/W, GSE
- 파일 통합: FOS, FOS+MFT, FOS-MFT-CDC로 표시된 조합
- 데이터 통합: ETL

### 2.5 연계업무

- 대내 연계 계정계 AP 등
- 장표 오른쪽 일부는 화면 밖으로 잘려 있어 전체 대상 시스템을 확인할 수 없음

> `데모`의 업무 의미와 `FOS-MFT-CDC` 표기의 정확한 제품·처리 조합은 장표만으로 확정하지 않는다. 상세 인터페이스 목록과 원본 설계서에서 확인해야 한다.

## 4. 온라인 요청 흐름

### 4.1 업무 시스템 → 영업점 MCA → 마케팅 플랫폼

영업점 업무 시스템은 싱글뷰 또는 표준전문으로 영업점 MCA에 요청하고, MCA는 이를 마케팅 플랫폼의 미니 싱글뷰와 관련 서비스로 중계한다.

```text
업무 시스템
  → 영업점 MCA
      → 채널 인증·전문 검증
      → JSON/HTTP 또는 표준전문 변환
      → 미니 싱글뷰 Service
      → 고객 통합 조회
  ← 표준 응답
```

핵심 통제 사항:

- 원거래 번호와 GUID를 함께 전달한다.
- 조회 범위와 개인정보 노출을 직무별로 통제한다.
- MCA와 마케팅 플랫폼의 전문 변환 책임을 중복시키지 않는다.
- 정보계 장애가 계정계 거래에 전파되지 않도록 짧은 타임아웃과 차단기를 적용한다.
- 조회 결과의 기준 시각과 최신성 수준을 화면에 전달한다.

### 4.2 업무 시스템 → 미니 싱글뷰 직접 연계

장표에는 업무 시스템에서 미니 싱글뷰로 직접 연결되는 JSON/HTTP 경로도 표시된다. MCA 경유 경로와 직접 경로가 병존하므로 호출 조건을 명확히 해야 한다.

- 채널·업무 유형별 경유 기준
- 인증 주체와 권한 검증 위치
- 동일 API의 중복 공개 여부
- 버전 및 오류 코드 일관성
- 감사 로그와 호출량 집계 기준

### 4.3 정보 단말 → 온라인 애플리케이션

정보 단말은 JSON/HTTP 기반으로 온라인 거래 처리를 요청한다.

- 단말 인증과 사용자 인증을 구분한다.
- 세션·토큰 만료와 재인증 정책을 적용한다.
- 요청 크기, Content-Type, 문자셋과 날짜 형식을 표준화한다.
- GUI 오류 메시지와 서버 오류 전문을 분리한다.

### 4.4 인터넷·스마트뱅킹 → MCI → 마케팅 플랫폼

대고객 채널은 MCI를 통해 마케팅 플랫폼의 조회·개인화·캠페인 기능을 호출한다.

- 고객 거래 응답 경로와 행동 로그 수집 경로를 분리한다.
- 개인화 결과가 늦을 경우 기본 콘텐츠로 Fallback한다.
- 채널별 고객 식별자를 통합 고객 키로 안전하게 매핑한다.
- 과도한 마케팅 호출을 Cache·Rate Limit으로 제어한다.

## 5. 마케팅 온라인 애플리케이션 구조

| 서비스군 | 역할 | 주요 인터페이스 고려사항 |
|---|---|---|
| 미니 싱글뷰 | 핵심 고객 요약 조회 | 응답시간, 최신성, 개인정보 최소화 |
| 공통 | 코드·공통 기능 | 캐시, 버전, 공통 오류 |
| 상담판매 | 상담·제안 업무 | 상담 이력, 상품 적합성 |
| 통합상품 | 상품 통합 조회 | 상품 버전·판매 기간 |
| 통합고객 | 전사 고객 통합 | 식별키, 병합·분리 이력 |
| 개인/기업고객 | 고객 유형별 서비스 | 권한·데이터 모델 차이 |
| 행동정보 | 고객 행동 조회·활용 | 이벤트 최신성·동의 |

| 컨텐츠/메시지 | 마케팅 소재와 메시지 | 승인, 템플릿, 유효기간 |
| 영업지원/CS | 영업·고객 응대 | 업무 이력·접근 통제 |
| EBM | 이벤트 기반 마케팅 | 규칙 버전, 판단 추적 |

서비스 간에는 DB 테이블 직접 접근보다 소유 API 또는 이벤트를 사용해 결합도를 낮춰야 한다.

## 6. 행동정보 수집 흐름

### 6.1 수집 단계

```text
인터넷/스마트뱅킹
  → 비대면 로그 생성
  → Wise Collector Proxy
  → Wise Collector
  → Kafka Topic 발행
  → 고객 행동 데이터 Consumer
```

Wise Collector Proxy는 채널과 수집기의 장애·네트워크 경계를 완충하고, Wise Collector는 이벤트 정규화·버퍼링·전송을 담당하는 구조로 해석된다.

필수 이벤트 필드:

| 분류 | 필드 예시 |
|---|---|
| 식별 | eventId, eventType, schemaVersion |
| 추적 | guid, sessionId, parentEventId |
| 고객 | customerKey 또는 가명 식별자 |
| 채널 | channelId, deviceType, screenId |
| 시간 | occurredAt, collectedAt, publishedAt |
| 행위 | action, objectType, objectId |
| 동의 | consentVersion, purposeCode |
| 품질 | sourceSequence, retryCount |

### 6.2 Kafka 처리 기준

- Topic은 업무 도메인과 보존 등급에 따라 분리한다.
- 고객·세션 단위 순서가 필요하면 해당 키로 파티셔닝한다.
- Schema Registry 또는 동등한 계약 저장소를 사용한다.
- Producer는 `acks`, 재시도, 멱등 전송을 설정한다.
- Consumer는 Event ID로 중복 처리를 방지한다.
- Retry Topic과 DLQ를 분리한다.
- Consumer Lag과 유실·중복 지표를 감시한다.

### 6.3 거래와 행동 로그의 장애 격리

행동 수집 실패 때문에 인터넷·스마트뱅킹 거래가 실패해서는 안 된다.

```text
고객 거래 성공 ───────────────> 즉시 응답
       └─ 행동 로그 비동기 전송
              ├─ 성공 → Kafka
              └─ 실패 → 로컬 버퍼/재전송/폐기 정책
```

단, 규제·감사상 반드시 남겨야 하는 이벤트는 일반 행동 로그와 별도 신뢰성 등급을 적용한다.

## 7. 행동정보 처리 및 저장

고객 행동 데이터는 행동정보처리 컴포넌트에서 정제·분류·집계된 뒤 행동정보 DB에 저장된다.

처리 단계:

1. 이벤트 스키마와 필수 필드를 검증한다.
2. 고객·세션·캠페인 키를 매핑한다.
3. 봇·중복·비정상 이벤트를 필터링한다.
4. 동의 목적과 보존 정책을 확인한다.
5. 실시간 특성·집계값을 계산한다.
6. 행동정보 DB에 멱등 저장한다.
7. EBM 판단 대상 이벤트를 발행 또는 호출한다.

행동정보 DB는 원시 이벤트, 정제 이벤트, 실시간 Feature, 캠페인 반응을 논리적으로 분리해야 한다.

## 8. EBM 실시간 처리

실시간 처리 EBM은 행동정보 DB 또는 처리 이벤트를 기반으로 마케팅 규칙을 평가한다.

```text
행동 이벤트
  → 고객 상태·동의 조회
  → EBM 규칙 평가
  → 대상/비대상 결정
  → 오퍼·메시지 생성
  → UMS 발송 요청
  → 판단 결과·규칙 버전 저장
```

필수 통제:

- 규칙 ID와 버전을 결과에 기록한다.
- 고객 동의·수신 거부·접촉 빈도를 최종 발송 직전에 확인한다.
- 동일 이벤트의 중복 판단과 중복 발송을 방지한다.
- 지연된 이벤트의 만료 시간을 적용한다.
- Rule Engine 장애 시 거래와 무관한 흐름은 격리·재처리한다.

## 9. UMS 메시지 발송

UMS는 EBM이 결정한 메시지를 SMS·PUSH·e-Mail 채널로 전달한다.

| 상태 | 의미 |
|---|---|
| REQUESTED | 발송 요청 수신 |
| VALIDATED | 동의·템플릿·수신처 검증 |
| QUEUED | 채널 발송 대기 |
| SENT | 외부 채널에 전달 |
| DELIVERED | 수신 확인 |
| FAILED | 기술 실패 |
| REJECTED | 정책·동의 위반 |
| EXPIRED | 유효시간 경과 |

`SENT`와 `DELIVERED`를 구분하고, UMS Message ID를 원 GUID·Event ID·Campaign ID와 연결해야 한다.

## 10. 대내 온라인 통합 관계

마케팅 플랫폼은 API G/W, EAI, GSE를 통해 대내 연계업무에 접근한다.

```text
마케팅 Service
  ↔ API G/W
      ├↔ EAI ↔ 계정계 AP/레거시 전문
      └↔ 표준 REST API

마케팅 Service
  ↔ GSE ↔ 지정 표준망 또는 계정계 서비스
```

### 책임 분리

- API G/W: 인증, 인가, 라우팅, 버전, Rate Limit, 감사
- EAI: 레거시 전문·프로토콜 변환, 중재, 큐잉
- GSE: 지정된 은행·기관 표준 연계
- 마케팅 Service: 업무 규칙과 데이터 소유

장표의 `데모` 박스는 API G/W에서 마케팅 플랫폼 내부로 연결된 것으로 보이나, 데모 API·테스트용 서비스·업무 기능 중 무엇인지 확정할 수 없다. 운영 구성이라면 비운영용 데모 엔드포인트의 노출 여부와 접근 통제를 반드시 확인해야 한다.

## 11. 파일 및 데이터 통합 관계

장표에는 마케팅 플랫폼 우측에 FOS·MFT 기반 파일 통합과 ETL 기반 데이터 통합이 배치되어 있다. 직접 연결선은 일부 생략되거나 화면 밖으로 이어지므로 적용 대상은 상세 목록으로 확정해야 한다.

### 파일

- FOS: 내부 표준 파일 접수·전달
- MFT: 보안 전송, 재개, 추적이 필요한 구간
- 완료 신호: Atomic Rename 또는 Manifest
- 무결성: 파일 크기, 건수, SHA-256
- 멱등성: File ID + 업무일자 + Sequence
- 오류: Quarantine과 승인된 재전송

### 데이터

- ETL: 고객·상품·캠페인·성과 데이터의 대량 동기화
- Source/Target 매핑과 전체·증분 기준
- 워터마크와 체크포인트
- Staging 후 원자적 Merge
- 건수·금액·해시·업무 규칙 대사

## 12. 종단 추적 모델

```text
GUID / Correlation ID
├─ 채널 Request ID
├─ MCA/MCI 전문번호
├─ API Gateway Request ID
├─ WAS Trace ID
├─ DB Client Identifier
├─ Kafka Event ID
├─ EBM Decision ID
├─ Campaign ID
├─ UMS Message ID
├─ File/Transfer ID
└─ ETL Execution ID
```

각 하위 ID는 `parentGuid`로 원거래와 연결한다. 이를 통해 고객의 화면 행동부터 캠페인 판단과 메시지 수신 결과까지 추적할 수 있다.

인터페이스별로 채널 소유자, 마케팅 업무 소유자, MCA/MCI·API G/W·Kafka·UMS 운영자와 개인정보 책임자를 **RACI**로 지정해 변경 승인과 장애 대응 책임을 명확히 해야 한다.

## 14. 신뢰성 및 재처리

### 온라인

- 비멱등 갱신 호출은 자동 재시도하지 않는다.
- Timeout 후 결과 미확정 상태를 조회하는 API를 제공한다.
- Circuit Breaker와 Bulkhead로 대내 장애를 격리한다.

### 행동 이벤트

- Offset과 업무 처리 체크포인트를 원자적으로 관리한다.
- 동일 Event ID는 한 번만 업무 반영한다.
- 독성 이벤트는 DLQ로 이동하고 정상 파티션 처리를 지속한다.

### 메시지

- 발송 재시도는 채널별 정책과 메시지 만료시간 내에서 수행한다.
- 동일 Campaign·Customer·Offer의 중복 발송을 방지한다.
- 수신 거부가 발생하면 대기 메시지에도 즉시 반영한다.

### 파일·ETL

- 실패 파일·Step·파티션 단위로 재처리한다.
- 원본과 체크포인트를 보존한다.
- 재처리 전후 정합성 대사를 수행한다.

## 15. 보안 및 개인정보

- 고객 식별자는 Kafka와 행동정보 DB에서 가명 키 사용을 우선한다.
- 행동 수집 목적·동의 버전을 이벤트에 포함한다.
- 민감 이벤트와 위치·기기정보의 수집을 최소화한다.
- 캠페인 대상 추출과 Self-Service 조회 권한을 분리한다.
- API G/W, MCA/MCI, UMS 서비스 계정에 최소 권한을 적용한다.
- 로그에 주민번호·계좌번호·연락처 원문을 남기지 않는다.
- 운영자 조회·대상 추출·메시지 발송을 감사한다.
- 비운영 `데모` 기능이 존재하면 운영 데이터 접근과 외부 공개를 차단한다.

## 16. 성능 및 용량

- 온라인 서비스와 행동 이벤트 Consumer의 자원 풀을 분리한다.
- 미니 싱글뷰는 응답 크기와 하위 호출 수를 제한한다.
- Kafka 파티션은 피크 행동 이벤트량과 키 순서를 함께 고려한다.
- 행동정보 DB 쓰기 처리량과 보존 기간을 기준으로 용량을 산정한다.
- EBM 규칙 평가 시간과 UMS 발송량에 백프레셔를 적용한다.
- 캠페인 대량 처리와 온라인 고객 조회의 DB 자원 그룹을 분리한다.
- 외부 API 지연이 P95/P99 응답 SLA에 미치는 영향을 감시한다.

## 18. 가용성 및 DR

- 영업점 MCA, MCI, API G/W, Kafka, 행동정보 처리, UMS를 다중화한다.
- Kafka 복제 계수와 최소 ISR을 중요도에 맞춘다.
- DR 전환 후 Consumer Offset과 Event ID 중복 방지를 검증한다.
- EBM의 규칙·캠페인·동의 데이터가 DR에 동기화되어야 한다.
- UMS 전환 시 대기 메시지의 소유권과 중복 발송을 통제한다.
- FOS/MFT 및 ETL 스케줄러의 Active 센터를 단일화한다.
- 원복 후 온라인 거래, 행동 이벤트, 발송 결과, DB 적재를 종단 대사한다.

## 22. 최종 평가

마케팅 플랫폼 인터페이스는 채널 기반 온라인 서비스와 이벤트 기반 행동정보 처리를 하나의 업무 경계 안에 배치하면서도, 처리 파이프라인은 동기·비동기로 분리한 구조다. 영업점 MCA·MCI를 통한 채널 통합, API G/W·EAI·GSE를 통한 대내 통합, Kafka·EBM·UMS를 통한 실시간 마케팅 흐름은 역할이 비교적 명확하다.

운영 품질을 확보하려면 MCA 경유와 직접 HTTP 경로의 적용 기준, Kafka 이벤트 계약, EBM 판단·UMS 발송의 멱등성과 고객 동의, 행동정보 개인정보 통제, FOS·MFT·ETL 대상 관계를 상세 인터페이스 등록부로 구체화해야 한다. 이미지에서 의미가 확정되지 않는 `데모`와 일부 파일 통합 표기는 운영 노출·보안 관점에서 반드시 원본 설계와 교차 검증해야 한다.
