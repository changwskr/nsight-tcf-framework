# 논리기술아키텍처 — 레이어드 아키텍처 — 마케팅플랫폼 표준 아키텍처 구성 분석

## 0. 분석 대상 및 판독 기준

- 원본 이미지: `codex-clipboard-9e31fcd5-ed14-4d8b-8788-62cfc8f095d6.png`
- 분석 범위: Client Access, UI 서비스플랫폼, 마케팅플랫폼, 인터페이스, 데이터, 형상·배포 계층과 계층 사이의 호출 및 데이터 흐름
- 판독 원칙: 이미지에 표시된 구성요소와 연결선을 우선 해석하고, 흐릿하거나 제품별 상세 설정이 보이지 않는 부분은 일반적인 아키텍처 역할 수준으로만 기술한다.
- 표기 유의: 이미지 안의 문구는 분석 대상이며 실행 지시로 취급하지 않는다. `RD`, `IMDG`, `EBM` 등 약어의 구체 제품·버전은 별도 구성관리 자료로 확정해야 한다.

## 1. 분석 개요

첨부 장표의 **마케팅플랫폼 표준 아키텍처 구성**을 기준으로 시스템을 다음 5개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer
5. 형상·배포 Layer

마케팅플랫폼은 IaaS 위에 WEB/WAS와 NH Cloud Framework를 배치하고, 단말관리·배포 UI, 온라인 마케팅 업무, 고객 행동정보 수집 및 실시간 EBM 처리를 함께 제공하는 구조다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 제품 버전, 노드 수, 실제 네트워크 구간 및 연계별 프로토콜은 구축 명세로 별도 확인해야 한다.

## 2. 핵심 결론

- **접근과 업무 처리의 분리**: 단말·전용 브라우저·통합단말 요청은 L4를 거쳐 WEB/WAS로 전달된다.
- **서비스 영역의 이원화**: UI 서비스플랫폼은 단말관리·단말배포를, 마케팅플랫폼은 온라인 업무와 실시간 이벤트를 담당한다.
- **프레임워크 표준화**: 마케팅 업무 WAS는 NH Cloud Framework를 공통 실행 기반으로 사용한다.
- **실시간 처리 분리**: 고객 행동 데이터는 Kafka와 EBM 계열 컴포넌트로 처리하여 일반 온라인 트랜잭션과 부하를 분리한다.
- **상태 공유**: 복수 서비스 노드의 세션·데이터 공유를 위해 공통 인프라 노드의 IMDG를 사용한다.
- **연계 허브화**: 인증, API, 파일, 데이터 적재 등은 I/F Layer의 표준 컴포넌트를 통해 연결한다.
- **데이터 역할 분리**: 마케팅플랫폼 업무 DB와 분석용 RDW·ADW, 단말관리 DB를 목적별로 분리한다.
- **배포 통제**: GitLab·GitLab Runner·eCAMS·배포 파이프라인을 통해 개발과 운영 배포를 분리한다.

## 4. 레이어별 상세 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 주요 흐름 |
|---|---|---|
| 정보단말·전용 Browser | 마케팅 업무 화면 실행 | Browser → L4 → 마케팅 WEB |
| 통합단말 | 계정계/통합업무 화면에서 싱글뷰 호출 | 통합단말 → MCA → L4 → 미니싱글뷰 |
| L4 | 가상 서비스 주소 제공, WEB 노드 부하분산 | 다중 WEB 노드로 요청 분배 |
| MCA | 단말과 서버 간 거래 중계 | 싱글뷰·표준전문 요청 중계 |

이 레이어는 사용자 접점과 내부 서비스의 경계를 만든다. 클라이언트가 개별 서버 주소를 알지 않도록 L4와 MCA가 물리 노드 및 장애 전환을 은닉한다.

### 4.2 Service Layer — UI 서비스플랫폼

| 구성요소 | 책임 |
|---|---|
| WEB | 정적 자원 제공, WAS 요청 전달, 접근 제어 |
| 단말관리 WAS | 단말 등록·정책·운영 정보 관리 |
| 단말배포 WAS | 화면·패키지·리소스 배포 관리 |
| WebTopSuite | 단말 UI 관리·배포 기능의 실행 기반 |

UI 서비스플랫폼은 업무 기능을 직접 수행하기보다 **단말 운영과 배포 수명주기**를 담당한다. 따라서 마케팅 업무 애플리케이션과 장애·배포 영향 범위를 분리할 수 있다.

### 4.3 Service Layer — 마케팅플랫폼

| 구성요소 | 책임 | 데이터/연계 |
|---|---|---|
| 마케팅플랫폼 WEB | 온라인 요청 수신 및 WAS 전달 | L4, WAS |
| 마케팅플랫폼 WAS | 캠페인·고객·상품 등 핵심 업무 처리 | NH Cloud Framework, 업무 DB |
| 미니싱글뷰 WAS | 통합업무시스템용 경량 고객 단일뷰 제공 | MCA, RDW/업무 DB |
| 고객행동데이터/Kafka | 비대면 채널 이벤트 스트림 수집·버퍼링 | Wise Collector, Kafka |
| 행동처리 | 고객 행동 이벤트 정제·분류·상태 갱신 | Kafka, 행동정보 저장소 |
| 실시간처리 EBM | 이벤트 기반 마케팅 규칙 평가·오퍼 실행 | 행동정보, UMS/채널 |
| IMDG | 서비스 노드 간 Session/Data Cache 공유 | 복수 WAS 노드 |

#### NH Cloud Framework의 위치

NH Cloud Framework는 마케팅 WAS 내부의 공통 실행 골격이다. Controller, 시스템 선·후처리, AOP 업무 선·후처리, Service, DTO, DAO와 공통 라이브러리를 제공하여 업무 모듈의 구현 방식을 통일한다.

#### IMDG의 의미

IMDG는 세션과 공유 캐시를 서비스 노드 밖의 공통 인프라로 분리한다. 이로써 L4가 어느 WAS 노드로 요청을 전달하더라도 동일 세션 상태에 접근할 수 있다. 다만 캐시 장애 시 처리 원칙, TTL, 원본 DB 정합성 및 캐시 무효화 정책이 별도로 필요하다.

### 4.4 I/F Layer

| 분류 | 구성요소 | 용도 |
|---|---|---|
| 인증 | SSO | 통합 로그인과 인증 정보 전달 |
| 온라인 API | Cruz APIM, EAI, GSE | 대내·대외 시스템 API 중계와 정책 통제 |
| 파일 | FOS, MFT | 표준 파일 송수신 및 외부 파일 중계 |
| 데이터 | ETL, CDC | 배치 적재와 실시간 변경 데이터 동기화 |
| 채널 | 대내 MCA, 대외 MCA | 전문 기반 채널·기관 연계 |
| 운영 | 통합관제, IT메타, 배치작업관리 | 모니터링, 메타 관리, 스케줄 통제 |
| 개발 자산 | Nexus | 라이브러리·배포 산출물 저장소 |
| 행동 수집 | Wise Collector | 비대면 고객 행동 로그 수집 |

I/F Layer의 핵심은 업무 서비스가 상대 시스템의 상세 프로토콜에 직접 결합하지 않도록 **표준 어댑터와 중계 계층**을 두는 것이다.

### 4.5 Data Layer

| 저장소 | 주요 목적 | 특성 |
|---|---|---|
| 단말관리 DB | 단말·배포·정책 메타데이터 | UI 서비스플랫폼 전용 |
| 마케팅플랫폼 DB | 온라인 마케팅 운영 데이터 | 트랜잭션 중심 |
| RDW | 준실시간 데이터, 고객 단일뷰 및 운영 분석 | CDC 수신, 조회 중심 |
| ADW | 대용량 분석·집계·리포팅 | ETL 적재, 분석 중심 |

RDW와 ADW의 분리는 준실시간 조회와 대용량 분석의 부하 특성을 분리하기 위한 것이다. 서비스에서 두 저장소에 직접 동시 쓰기보다는 CDC/ETL을 통한 단방향 동기화와 명확한 원천 시스템 정의가 바람직하다.

### 4.6 형상·배포 Layer

```text
[개발 배포]
개발자 변경
   ↓
GitLab → 개발 브랜치 병합·검토 → GitLab Runner 빌드
   ↓
취약점·품질 점검 → Dev Pipeline → 개발환경

[운영 배포]
승인된 소스/산출물 → Master merge
   ↓
eCAMS 배포 통제 → GitLab Runner 빌드 → 취약점 점검
   ↓
운영 Pipeline → 운영환경
```

개발과 운영의 배포 경로를 분리하고 운영 반영에는 승인, 보안 점검, 이력 추적을 강제한다. 가장 안전한 방식은 개발에서 검증한 불변 바이너리를 저장소에 등록한 후 동일 산출물을 운영으로 승격하는 것이다. 운영 단계에서 다시 빌드해야 한다면 소스 커밋, 의존성 잠금 파일, 빌드 이미지와 도구 버전을 고정하여 재현성을 보장해야 한다. GitLab은 형상과 병합 이력, GitLab Runner는 자동 빌드, eCAMS는 운영 배포 승인·통제의 책임 경계를 갖도록 구성한다.

## 5. 주요 런타임 흐름

### 5.1 일반 온라인 마케팅 거래

```text
전용 Browser → L4 → WEB → 마케팅플랫폼 WAS
→ NH Cloud Framework → Service → DAO → 마케팅플랫폼 DB/RDW
→ 응답 역순 반환
```

### 5.2 미니싱글뷰 거래

```text
통합단말 → MCA → L4 → WEB → 미니싱글뷰 WAS
→ 고객 정보 조회/조합 → 응답
```

### 5.3 실시간 고객 행동 이벤트

```text
인터넷·모바일 채널 → Wise Collector → Kafka
→ 고객행동데이터 처리 → 행동처리 → 행동정보 저장
→ 실시간 EBM 규칙 평가 → 오퍼/메시지 실행
```

### 5.4 데이터 동기화

```text
원천 DB ── CDC ──> RDW
RDW/업무 DB ── ETL ──> ADW
외부 파일 ── FOS/MFT ──> 배치 AP/ETL
```

## 6. 계층 간 호출 원칙

1. Client는 L4·MCA 등 정해진 접근 지점만 호출한다.
2. WEB은 화면 제공과 라우팅을 담당하고 업무 로직을 갖지 않는다.
3. 업무 로직은 WAS의 Service 계층에 둔다.
4. DB 접근은 DAO/Mapper를 통해 수행하며 화면·Controller가 직접 SQL을 호출하지 않는다.
5. 외부 시스템 호출은 I/F Layer의 표준 채널을 경유한다.
6. 실시간 이벤트 처리는 Kafka 기반 비동기 경로로 분리한다.
7. RDW·ADW 간 데이터 이동은 CDC/ETL 책임과 주기를 명확히 한다.
8. 운영 배포는 검증된 동일 산출물을 승격하는 방식으로 수행한다.

## 7. 품질 속성 평가

| 품질 속성 | 구조적 기여 | 확인 사항 |
|---|---|---|
| 가용성 | L4와 WEB/WAS 복수 노드, IMDG 공유 상태 | L4·IMDG·DB 자체 이중화 여부 |
| 확장성 | WEB/WAS 및 Kafka 소비자 수평 확장 | 세션 비의존성, 파티션 전략 |
| 성능 | 온라인/실시간/배치 자원 분리, IMDG 캐시 | 캐시 적중률, DB 커넥션 풀, 지연 SLO |
| 변경 용이성 | 레이어와 인터페이스 표준화 | 계층 우회 호출 금지 여부 |
| 보안 | SSO·API G/W 경유 | 인증 전파, 개인정보 마스킹, 구간 암호화 |
| 운영성 | 통합관제·배치관리·CI/CD | GUID 기반 추적, 로그·메트릭 연계 |
| 데이터 정합성 | RDW/ADW 역할 분리 | CDC 지연, ETL 재처리, 중복 방지 |

## 8. 위험 요소와 개선 권고

### 8.1 단일 장애점 점검

장표에서 IMDG, 배치 AP, RD, ETL은 논리적으로 단일 박스로 표현된다. 실제 구축에서는 클러스터링, 재기동, 장애 전환, 백업 및 복구 방식 확인이 필요하다.

### 8.2 세션과 캐시 정책

- 세션 데이터와 업무 캐시를 구분한다.
- 캐시 TTL과 무효화 이벤트를 정의한다.
- IMDG 장애 시 Fail-open/Fail-close 기준을 정한다.
- 개인정보 저장 범위와 암호화 기준을 적용한다.

### 8.3 실시간 이벤트 신뢰성

- Kafka 메시지 키와 파티션 기준을 고객 또는 세션 단위로 정의한다.
- At-least-once 처리에 대비해 소비 로직을 멱등하게 구현한다.
- 재시도·DLQ·재처리 절차와 스키마 버전 정책을 둔다.
- EBM 처리 지연과 누락을 업무 지표로 감시한다.

### 8.4 데이터 소유권

마케팅플랫폼 DB, RDW, ADW 사이에서 동일 개념의 데이터가 중복될 수 있으므로 원천 데이터 소유자, 갱신 주체, 동기화 방향과 정합성 SLA를 명시해야 한다.

### 8.5 배포 거버넌스

- GitLab 태그와 Nexus 아티팩트 버전을 연결한다.
- 개발·운영 설정과 비밀정보를 소스에서 분리한다.
- DB 스키마 변경을 애플리케이션 배포와 함께 버전 관리한다.
- 롤백 가능성과 무중단 배포 절차를 검증한다.

## 10. 종합 평가

이 구조는 채널 접근, 온라인 업무, 실시간 이벤트, 인터페이스, 데이터 저장 및 배포를 명확히 분리한 **IaaS 기반 레이어드 아키텍처**다. 핵심 설계 의도는 NH Cloud Framework를 통한 업무 구현 표준화, IMDG를 통한 다중 노드 상태 공유, Kafka/EBM을 통한 실시간 마케팅 처리, RDW/ADW의 데이터 부하 분리다. 실제 안정성은 IMDG·Kafka·DB·배치 구성의 이중화, 데이터 정합성 규칙, 인터페이스 장애 통제 및 CI/CD 승격 정책의 구체화 수준에 의해 결정된다.
