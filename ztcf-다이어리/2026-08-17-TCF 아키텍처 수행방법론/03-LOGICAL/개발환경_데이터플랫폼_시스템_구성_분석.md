# 개발환경 데이터플랫폼 시스템 구성 분석

> 분석 대상: 제공 이미지 `개발환경 데이터플랫폼 시스템`  
> 분석 관점: Zone 배치, 데이터 유입·처리 경로, 개발환경 통제, 구성요소 책임  
> 주의: 이미지에서 직접 확인되는 사실과 저장소 문서를 근거로 한 해석·권고를 구분한다.

## 0. 분석 범위와 판독 원칙

- **이미지 사실**: 그림에 표시된 명칭, Zone, 구성요소만 확정 사실로 기술한다.
- **구조 해석**: 화살표가 생략된 개념도이므로 실제 호출 방향과 프로토콜은 설계 검증 대상으로 둔다.
- **개발환경 원칙**: 운영 데이터·계정·엔드포인트를 직접 사용하지 않고 합성 또는 비식별 데이터를 사용한다.
- **문서 근거**: 저장소의 데이터 흐름·전송·배포 정책은 보완 근거이며 이미지 자체의 명세로 간주하지 않는다.

## 1. 핵심 결론

1. 데이터플랫폼은 **서비스 제공 Zone**에 배치되고, `RDW 어플라이언스`와 `ADW 어플라이언스`가 핵심 실행·저장 축이다.
2. 데이터 유입은 온라인(`API G/W`, `대외 MCA`), 파일(`FOS`, `MFT`), 데이터(`CDC`, `ETL`)의 세 경로로 분리된다.
3. RDW는 실시간·준실시간 조회 및 최신 상태 제공, ADW는 이력·집계·분석 및 대량 처리에 적합한 역할로 해석된다. 실제 적재 대상과 SLA는 별도 매핑표로 확정해야 한다.
4. 개발환경에서는 운영 연계와 구조는 유사하게 검증하되, **개발 전용 엔드포인트·계정·토픽·파일 경로·DB 스키마**를 사용해야 한다.
5. `CDC → RDW`를 Fast Path, `ETL → ADW`를 Deep Path로 설계하면 최신성과 분석 정합성을 분리할 수 있다. 단, 동일 대상 테이블에 CDC와 ETL이 동시에 쓰는 이중 Writer는 금지한다.
6. 이미지의 공통 인프라는 인증, 스케줄, 프레임워크, 형상·배포, 단말관리, 배치, 출력물 실행을 지원한다.
7. 개발환경 성능 결과는 기능·회귀 검증의 근거이지 운영 용량을 직접 보증하지 않는다.

## 2. 전체 Zone 및 구성요소

| 대분류 | 세부 Zone | 이미지 표시 구성요소 | 분석 |
|---|---|---|---|
| 채널 | 대내 채널 | 없음 | 데이터플랫폼 직접 채널이 그림에 명시되지 않음 |
| 채널 | 대고객 채널 | 없음 | 고객 UI보다 시스템 간 데이터 공급이 중심 |
| 채널 | 대외 채널 | 중앙회, 경제, 유통, 농협자산관리, 농협신용보증, 농정원(AgriX) | 대외 원천·소비 기관 후보 |
| 채널 통합 | 온라인 통합(대외) | API G/W, 대외 MCA, API G/W | 동기/준동기 인터페이스 진입점 |
| 채널 통합 | 파일 통합(대외) | FOS, MFT, FOS | 대용량·정기 파일 교환 |
| 채널 통합 | 데이터 통합 | 없음 | 개발환경 외부측 데이터 통합 도구는 그림에 미표시 |
| 서비스 제공 | 데이터플랫폼 시스템 | RDW 어플라이언스, ADW 어플라이언스 | 실시간 계열과 분석 계열의 핵심 데이터 플랫폼 |
| 서비스 제공 | 인프라 | SSO, Control-M, NH Cloud FWK Master Solution, eCAMS | 인증·스케줄·표준 프레임워크·관리 지원 |
| 서비스 제공 | 인프라 | 단말관리 WEB, 단말관리 WAS, 단말배포 WEB, 단말배포 WAS | 단말 관리 및 배포 |
| 서비스 제공 | 인프라 | 단말개발도구 AP, 소스관리 AP, 출력물(RD) WAS, 배치 AP | 개발·형상·보고서·배치 실행 지원 |
| 대내 통합 | 온라인 통합 | 없음 | 내부 온라인 연계 대상은 그림에 미표시 |
| 대내 통합 | 파일 통합 | FOS, FOS, MFT | 내부 파일 송수신·중계 |
| 대내 통합 | 데이터 통합 | CDC, ETL | 변경 데이터 전파와 배치성 데이터 가공 |

## 4. 핵심 컴포넌트 분석

### 4.1 RDW 어플라이언스

- 최신성 중심 데이터와 저지연 조회를 담당하는 계층으로 해석한다.
- CDC 지연시간, 마지막 반영 시각, offset/checkpoint, 중복·역전 이벤트를 측정해야 한다.
- 개발 스키마와 계정은 운영과 물리적 또는 최소 논리적으로 분리한다.
- 읽기 부하와 적재 부하가 경합하지 않도록 Resource Group, Queue, Connection Pool을 분리한다.

### 4.2 ADW 어플라이언스

- 이력, 집계, 분석, 대량 스캔 및 BI 제공용 계층으로 해석한다.
- ETL Job 단위로 입력 건수, 성공 건수, 오류 건수, 기준일, 소요시간을 기록한다.
- 차원·팩트·집계 테이블 변경은 버전이 있는 마이그레이션으로 수행한다.
- RDW와 동일 지표를 제공할 때 기준시점과 집계 규칙을 명시하여 숫자 불일치를 방지한다.

### 4.3 API G/W와 대외 MCA

- API G/W: 인증, 인가, 라우팅, Rate Limit, 호출 추적, 오류 표준화를 담당한다.
- 대외 MCA: 대외 인터페이스 중계 및 전문 변환·채널 어댑터 역할 후보이다.
- 개발환경은 Stub/Mock 또는 개발 대외계를 사용하고 운영 인증서·운영 DNS를 사용하지 않는다.

### 4.4 FOS와 MFT

- FOS: 파일 저장·송수신 인터페이스의 종단으로 해석한다.
- MFT: 대용량 파일의 보안 전송, 재시도, 무결성, 이력 관리를 담당한다.
- 파일명만으로 거래를 식별하지 말고 interfaceId, 기준일, sequence, checksum을 함께 관리한다.

### 4.5 CDC와 ETL

| 구분 | CDC | ETL |
|---|---|---|
| 목적 | 변경분의 신속한 전달 | 대량 추출·변환·집계·적재 |
| 주요 대상 | RDW 후보 | ADW 후보 |
| 핵심 상태 | offset, lag, ordering | Job/Step, 건수, 기준일 |
| 재처리 | checkpoint 이후 재개 | 실행 단위 재수행/보상 |
| 주요 위험 | 중복·유실·순서 역전·DDL | 중복 적재·부분 성공·대사 불일치 |

### 4.6 공통 인프라

| 구성요소 | 책임 | 개발환경 검증 포인트 |
|---|---|---|
| SSO | 사용자 인증·세션 | 개발 Realm, 최소권한, 퇴직/변경 반영 |
| Control-M | Job 스케줄·의존성 | Calendar, 선후행, 재처리, 동시 실행 |
| NH Cloud FWK Master Solution | 표준 애플리케이션 기반 | 공통 설정·로깅·예외·배포 표준 |
| eCAMS | 구성·운영 관리 지원 | 개발 구성과 운영 구성의 분리 |
| 단말관리 WEB/WAS | 단말 관리 | 개발 단말군·정책 분리 |
| 단말배포 WEB/WAS | 단말 배포 | 서명, 버전, 롤백, 배포 대상 분리 |
| 단말개발도구 AP | 단말 개발 도구 | SDK/플러그인 버전 고정 |
| 소스관리 AP | 소스·버전 관리 | Branch 보호, Review, Tag, 감사 이력 |
| 출력물(RD) WAS | 보고서 생성 | 개발 데이터 연결, 템플릿 버전 |
| 배치 AP | 배치/ETL 실행 | 멱등성, 재시작, 대사, 자원 제한 |

## 5. 데이터 흐름 계약(Data Flow Contract)

각 인터페이스는 다음 항목을 계약으로 관리해야 한다.

| 영역 | 필수 항목 |
|---|---|
| 식별 | interfaceId, owner, producer, consumer |
| 스키마 | 필드명, 타입, 길이, nullable, 코드 도메인, schemaVersion |
| 시간 | eventTime, processingTime, 기준일, timezone |
| 품질 | 필수값, 허용범위, 중복 기준, 참조 무결성 |
| 보안 | 데이터 등급, 마스킹 규칙, 암호화, 보존기간 |
| 운영 | SLA, 재시도, DLQ/격리, 재처리 방법, 연락체계 |
| 추적 | GUID/correlationId, fileId, batchId, offset |

호환되지 않는 변경은 새 버전을 발행하고, Producer와 Consumer의 병행 호환 기간을 둔다.

## 6. 개발환경 데이터 보호·격리

1. 운영 데이터의 직접 복제 대신 합성 데이터 또는 승인된 비식별 데이터를 사용한다.
2. 주민번호·계좌·연락처·고객식별자는 비가역 마스킹 또는 토큰화한다.
3. 개발 계정, 인증서, Secret, 네트워크 ACL, DB Service Name을 운영과 분리한다.
4. CDC 원천은 개발 DB 또는 승인된 복제·마스킹 구간으로 한정한다.
5. 파일 경로와 MFT Partner ID도 개발 전용으로 분리한다.
6. 테스트 종료 후 데이터 만료·초기화 정책과 증적을 남긴다.

## 7. 장애·재처리 메커니즘

| 장애 | 탐지 | 복구 원칙 |
|---|---|---|
| API 장애 | 5xx, timeout, circuit 상태 | 제한 재시도 후 격리, 동일 idempotency key 유지 |
| 파일 누락/손상 | checksum, recordCount, SLA | 원본 재전송, 중복 적재 방지 |
| CDC 지연/중단 | lag, heartbeat, offset 정체 | checkpoint 기반 재개, gap 대사 |
| ETL 부분 실패 | Step 상태, 건수 대사 | Commit 경계부터 재시작 또는 보상 |
| 스키마 불일치 | Contract Test, DDL 감지 | 배포 차단, 호환 버전 적용 |
| RDW/ADW 경합 | CPU/IO/Queue/Pool | Workload 격리, 동시성·일정 조정 |

재처리의 핵심은 단순 재실행이 아니라 **멱등성 키, 처리 이력, Commit 경계, 대사 결과**를 함께 보존하는 것이다.

## 8. 관측성 및 운영 지표

- 공통 추적키: correlationId/GUID, interfaceId, batchId, fileId, schemaVersion.
- 온라인: TPS, p95/p99 응답시간, 4xx/5xx, timeout, retry.
- 파일: 도착 지연, 전송 성공률, checksum 오류, 미처리 파일 수.
- CDC: source/target offset, lag, 이벤트 처리율, 중복·실패 수.
- ETL: Job/Step 상태, 처리 건수, 오류 건수, 소요시간, 기준일.
- DB: CPU, IO, 세션, Connection Pool, Queue, 장기 SQL, Lock.
- 품질: Null, 중복, 참조 무결성, RDW↔ADW 대사 차이.

## 9. 운영환경과 개발환경의 차이

| 항목 | 운영환경 | 개발환경 적용 |
|---|---|---|
| 데이터 | 실제 업무 데이터 | 합성/비식별 데이터 |
| 외부 연계 | 실 대외기관 | Stub/Mock 또는 개발 대외계 |
| 계정·Secret | 운영 Vault/계정 | 개발 Vault/계정 |
| 규모 | 실 트래픽·용량 | 축소 데이터와 제한 자원 |
| 목적 | 가용성·서비스 제공 | 기능·계약·회귀·장애 시나리오 검증 |
| 성능 해석 | 용량 계획 근거 | 상대 비교 및 병목 발견; 운영 용량 보증 불가 |
| 배포 | 승인된 Release | 반복 배포·초기화 가능하되 이력 유지 |

이미지에는 운영환경 그림에서 보이던 `UNO Dashboard`가 표시되지 않는다. 따라서 개발 데이터플랫폼의 필수 구성이라고 단정하지 않으며, 통합 모니터링 도구의 실제 배치 여부는 별도 확인이 필요하다.

## 10. 저장소 근거와 현재 설계의 연결

- 저장소의 `DATA-FLOW-POLICY.md` 관점에서는 흐름별 소유자, 계약, 품질, 재처리를 명시해야 한다.
- `DATA-TRANSPORT-STANDARD.md` 관점에서는 온라인·파일·CDC·ETL별 전송 표준과 추적정보를 통일해야 한다.
- `23-CI-CD-DEPLOYMENT.md` 관점에서는 DB/ETL 변경도 애플리케이션과 동일하게 버전·승인·롤백 가능한 배포 단위여야 한다.
- 저장소에는 개발 Appliance를 `Exadata X11M`, RDW·ADW 개발 증설 구조로 설명하는 자료가 있으나, 이는 **저장소 근거**이며 제공 이미지에서 직접 판독된 제품·버전 정보는 아니다.

## 11. 권고 보완사항

1. 이미지에 생략된 실제 연결선을 `원천 → 통합 → 서비스 → 소비자` 단위로 명시한다.
2. RDW/ADW별 Database, Schema, Service, Resource Group, Owner를 확정한다.
3. CDC·ETL 대상 테이블 소유권과 Writer를 하나로 지정한다.
4. 개발 전용 Endpoint/Port/DNS/Certificate/Account 목록을 운영 목록과 교차 검증한다.
5. 데이터 계약과 스키마 변경 호환성 검사를 CI/CD Gate에 넣는다.
6. 테스트 데이터 생성·마스킹·초기화·폐기 절차를 자동화한다.
7. Fast/Deep Path 간 기준시점 대사와 지연 허용치를 정의한다.
8. 개발 자원 제한과 성능시험 결과의 사용 범위를 문서화한다.

## 14. 최종 평가

이 구조는 개발환경에서도 운영과 유사한 온라인·파일·데이터 연계 경로를 검증하면서 RDW와 ADW의 워크로드를 분리하려는 데이터플랫폼 구성이다. 완성도를 좌우하는 요소는 장비 명칭보다 **개발/운영 격리, 데이터 계약, CDC·ETL 소유권, 테스트 데이터 통제, 재처리와 대사, 관측성**이다. 이 항목들이 배포 파이프라인과 검증 시나리오로 구현되어야 개발환경이 운영 전환의 신뢰 가능한 관문이 된다.
