# 인터페이스 아키텍처 — 마케팅플랫폼 연관관계도 분석

## 1. 핵심 결론

이 장표는 **마케팅플랫폼(MP)을 중심으로 좌측의 채널/사용자 접점, 우측의 대내 시스템 및 데이터 저장소를 연결하는 연관관계도**를 보여준다.

이 그림의 핵심은 단순한 시스템 목록이 아니라, 다음 4가지 인터페이스 축을 동시에 보여준다는 점이다.

| 인터페이스 축 | 주요 대상 | 핵심 의미 |
|---|---|---|
| 채널 입력 축 | 통합업무시스템, 정보단말, 인터넷/스마트뱅킹, SMS/EMAIL/PUSH, 보고서 | 마케팅플랫폼의 입력·출력 접점 |
| 내부 업무기능 축 | CO, IC, PC, BC, MS, SA, PD, CM, EB, SS, CS, CT, MG | 마케팅플랫폼 내부 업무 도메인 분해 |
| 대내 연계 축 | API G/W, EAI, 코어뱅킹, 아리톡, 태블릿 브랜치 | 업무별 외부 시스템 연계 |
| 데이터 연계 축 | ETL, FOS, JDBC, RDW, ADW, UMS | 데이터 적재/조회/메시지 전송 방식 구분 |

즉 이 장표는 **“채널 → 마케팅플랫폼 업무모듈 → 대내 시스템/데이터 저장소”**의 관계를 모듈 단위로 풀어낸 **연관관계 중심 인터페이스 맵**이다.

특히 구조상 중요한 해석은 다음과 같다.

1. **좌측 채널은 하나의 MP 공통 진입점으로 수렴한다.**  
2. **MP 내부는 업무코드 기반으로 세분화되어 있다.**  
3. **우측 대내 연계는 API G/W와 EAI를 통해 연결되는 방식이 우세하다.**  
4. **데이터 연계는 ETL / FOS / JDBC로 구분된다.**  
5. **채널성 인터페이스와 데이터성 인터페이스를 섞지 않고 분리한 구조다.**

## 4. 상세 텍스트 그림

## 4.1 좌측 채널/입력 연계 상세 그림

```text
┌─────────────────────────────── 좌측 연계 주체 ────────────────────────────────┐
│                                                                               │
│  1) 통합업무시스템                                                            │
│                                                                               │
│     [통합업무시스템] ↔ [영업점 MCA] ↔ [마케팅플랫폼 MP]                       │
│                                                                               │
│  2) 정보단말                                                                  │
│                                                                               │
│     [정보단말] ↔ [마케팅플랫폼 MP]                                            │
│                                                                               │
│  3) 인터넷뱅킹 / 스마트뱅킹                                                   │
│                                                                               │
│     [인터넷뱅킹/스마트뱅킹] ↔ [Kafka] ↔ [마케팅플랫폼 MP]                     │
│                                                                               │
│  4) SMS / EMAIL / PUSH                                                        │
│                                                                               │
│     [SMS/EMAIL/PUSH] ↔ [UMS] ↔ [마케팅플랫폼 MP]                              │
│                                                                               │
│  5) 보고서                                                                     │
│                                                                               │
│     [보고서] ↔ [마케팅플랫폼 MP]                                              │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 해석

- **통합업무시스템**은 영업점 MCA를 통해 MP와 연결된다.
- **정보단말**은 별도 중계 컴포넌트 없이 MP와 직접 연결되는 구조로 표현된다.
- **인터넷뱅킹/스마트뱅킹**은 Kafka를 사이에 둔 비동기성 또는 이벤트성 구조로 보인다.
- **SMS/EMAIL/PUSH**는 UMS를 통해 MP와 연결된다.
- **보고서**는 별도 중계 없이 MP와 직접 연결된 것으로 그려져 있다.

## 4.3 우측 대내 연계 상세 그림

```text
┌──────────────────────────── 우측 대내 서비스 연계 ────────────────────────────┐
│                                                                               │
│  [공통 CO] ──▶ [API G/W] ──▶ [EAI] ──▶ [코어뱅킹]                             │
│                                                                               │
│  [개인고객 PC] ──▶ [API G/W] ─────────▶ [아리톡(알림 서비스)]                 │
│                                                                               │
│  [미니싱글뷰 MS] ──▶ [API G/W] ──▶ [EAI] ──▶ [태블릿 브랜치]                  │
│                                                                               │
│  [상담판매 SA] ──▶ [API G/W] ─────────▶ [아리톡(알림 서비스)]                 │
│                                                                               │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 해석 포인트

- 모든 대내 연계가 동일 방식은 아니다.
- 일부는 **API G/W만 경유**한다.
- 일부는 **API G/W + EAI**를 함께 사용한다.
- 즉 장표는 **업무별 인터페이스 방식이 다름**을 보여준다.

### 설계적 의미

- API Gateway는 대내 서비스 호출의 공통 진입점이다.
- EAI는 전문중계/변환/연계중재 성격의 역할을 수행할 가능성이 높다.
- 코어뱅킹과 태블릿브랜치는 EAI가 필요한 시스템으로 표현된다.
- 아리톡(알림 서비스)은 API G/W 단독 연계로 보인다.

## 4.4 데이터 연계 상세 그림

```text
┌──────────────────────────── 데이터 / 저장소 연계 ────────────────────────────┐
│                                                                               │
│  [캠페인 CM] ─────▶ [ETL] ─────────────▶ [RDW]                                │
│                                                                               │
│  [EBM EB] ───────▶ [ETL] ─────────────▶ [ADW]                                │
│                                                                               │
│  [CS CS 또는 메시지성 기능] ─▶ [ETL] ─▶ [FOS] ─▶ [UMS]                        │
│                                                                               │
│  [메시지 MG] 또는 하단 모듈 ─────▶ [JDBC] ─────────▶ [RDW]                    │
│                                                                               │
└───────────────────────────────────────────────────────────────────────────────┘
```

> 주의: 원본 그림의 선은 하단 모듈들과 ETL/FOS/JDBC 사이를 직접 정확히 1:1로 판독하기 어려운 부분이 있다.  
> 따라서 위 텍스트 그림은 **하단 업무모듈군이 데이터/메시지 연계 축과 연결된다**는 구조를 설명하기 위한 재구성이다.

### 해석 포인트

- **RDW / ADW 연계는 ETL 중심**으로 표현된다.
- **UMS 연계는 ETL + FOS**가 결합된 형태로 표현된다.
- **하단 RDW는 JDBC 직접접속성 구조**를 보여준다.

### 설계적 의미

| 연계 방식 | 대상 | 의미 |
|---|---|---|
| ETL | RDW / ADW | 배치성 적재/가공/분석 데이터 이동 |
| ETL + FOS | UMS | 파일성 또는 중계성 메시지 연계 가능성 |
| JDBC | RDW | 직접 조회/직접 DB 인터페이스 성격 |

```text
② 내부 단말 축
[정보단말] ↔ [MP]

④ 메시지 채널 축
[SMS/EMAIL/PUSH] ↔ [UMS] ↔ [MP]

⑤ 업무 기능 축
[MP] → [CO|IC|PC|BC|MS|SA|PD|CM|EB|SS|CS|CT|MG]

⑥ 대내 시스템 연계 축
[업무모듈] → [API G/W] → ([EAI]) → [코어뱅킹/아리톡/태블릿브랜치]

⑦ 데이터 적재 축
[업무모듈] → [ETL] → [RDW/ADW]

⑧ 메시지/파일 연계 축
[업무모듈] → [ETL] → [FOS] → [UMS]

⑨ 직접 조회/DB 연계 축
[업무모듈] → [JDBC] → [RDW]
```

## 5. 인터페이스 관점 상세 분석

## 5.1 채널 연계 관점

이 장표는 마케팅플랫폼의 채널 연계를 5가지로 구분한다.

| 채널 | 중계 컴포넌트 | 성격 |
|---|---|---|
| 통합업무시스템 | 영업점 MCA | 영업점/내부업무 채널 |
| 정보단말 | 직접 연결 | 내부 업무 단말 |
| 인터넷/스마트뱅킹 | Kafka | 디지털/이벤트 기반 채널 |
| SMS/EMAIL/PUSH | UMS | 메시지 채널 |
| 보고서 | 직접 연결 | 리포팅/산출물 연계 |

### 분석

- **채널마다 같은 연결 방식을 쓰지 않는다.**  
  → 이는 채널 특성별 표준 인터페이스를 구분하려는 의도다.
- **영업점 채널은 MCA**, **디지털 채널은 Kafka**, **메시지 채널은 UMS**를 사용한다.  
  → 즉 채널 특성별 중계구조가 분리돼 있다.
- 보고서는 실시간 조회결과, 배치산출, 또는 내부 출력물일 가능성이 있다.

## 5.2 업무모듈 분해 관점

장표는 MP를 단일 블록으로 두지 않고, 업무모듈을 세분화한다.

이는 다음 의미를 가진다.

1. **인터페이스 책임을 업무모듈 단위로 분리**하려는 의도  
2. **모듈별 외부 시스템 연계가 다름**을 표현  
3. **고객·상품·캠페인·메시지·EBM·영업지원이 분리된 구조**를 보여줌

## 5.3 대내 시스템 연계 관점

우측 상단 연계는 API G/W와 EAI가 핵심이다.

### 구조적 의미

- **API G/W**: 대내 서비스 호출의 표준 진입점
- **EAI**: 전문 변환, 레거시 연계, 기존 시스템 중재
- **코어뱅킹**: 핵심 업무시스템 연계 대상
- **태블릿 브랜치**: 채널/업무확장 시스템
- **아리톡**: 알림·통지 계열 시스템

### 분석

- 코어뱅킹과 태블릿브랜치는 EAI를 경유하는 구조다.
- 아리톡은 API G/W 단독 연계로 표현된다.
- 따라서 MP는 외부 시스템을 직접 호출하기보다, **API / EAI 표준 경계**를 통해 연계한다.

---

## 5.4 데이터 연계 관점

RDW와 ADW가 분리되어 있고, 둘 다 ETL로 연결된다.

### 의미

- **RDW**: 실시간 또는 운영지원용 데이터 활용 저장소 성격
- **ADW**: 분석/배치/집계용 데이터 활용 저장소 성격
- **JDBC→RDW**: 일부 기능은 DB 직접 접근 구조를 가질 수 있음

### 분석

- ETL과 JDBC가 동시에 존재하는 것은 **데이터 접근 패턴이 하나가 아님**을 의미한다.
- 운영/실시간성 기능은 JDBC 또는 직접조회 성격일 수 있다.
- 분석/배치 적재는 ETL이 담당한다.
- UMS 연계는 파일성 또는 배치성 메시지 전달 구조를 가질 가능성이 있다.

## 5.5 메시지 / 알림 연계 관점

장표에는 아리톡(알림 서비스)과 UMS가 동시에 등장한다.

이는 알림 연계가 단일 경로가 아님을 의미한다.

| 컴포넌트 | 해석 |
|---|---|
| 아리톡(알림 서비스) | 대내 알림 서비스 또는 직원/업무 알림 채널 |
| UMS | SMS/EMAIL/PUSH 통합 메시징 채널 |
| 메시지 MG | 메시지 업무 기능 모듈 |
| EBM EB | 이벤트 기반 마케팅 또는 반응형 발송 판단 |

즉 MP는 **업무 알림**과 **대고객 메시징**을 서로 다른 인터페이스 방식으로 처리할 수 있다.

## 15. 장표 해석 시 유의사항

이 그림은 **연관관계도**이므로, 모든 화살표가 실시간 호출방향을 의미한다고 단정할 수는 없다.

특히 다음은 추가 상세설계 확인이 필요하다.

- 보고서의 실제 생성 방식(직접 조회 vs 배치 결과)
- RDW와 JDBC 연결의 정확한 업무모듈 범위
- ETL + FOS + UMS 연결의 구체적 처리 시나리오
- 아리톡 2개 표기의 의미(서로 다른 서비스인지 동일 서비스 반복인지)
- 업무모듈별 외부 시스템 1:1 대응 관계
- Kafka가 이벤트 수집인지, 이벤트 소비인지, 양방향인지 여부

따라서 이 문서는 **장표에서 식별 가능한 FACT를 우선 정리하고, 인터페이스 아키텍처 관점에서 해석을 보강한 문서**로 봐야 한다.

## 16. 최종 평가

이 장표는 마케팅플랫폼을 다음과 같은 구조로 정의한다.

```text
채널(영업점/단말/디지털/메시지/보고서)
        ↓
마케팅플랫폼 MP
        ↓
업무모듈(CO, IC, PC, BC, MS, SA, PD, CM, EB, SS, CS, CT, MG)
        ↓
대내 시스템 / 데이터 저장소 / 메시지 서비스
```

즉 MP는 단순한 마케팅 기능 집합이 아니라,

- **고객/상품/캠페인/메시지/미니싱글뷰를 포함한 업무플랫폼**이며,
- **코어뱅킹/태블릿브랜치/아리톡과 대내 연계**하고,
- **RDW/ADW/UMS와 데이터·메시지 연계**하며,
- **Kafka/UMS/MCA/API/EAI/ETL/JDBC/FOS**를 함께 사용하는 복합 인터페이스 허브다.

가장 중요한 아키텍처적 포인트는 다음이다.

1. **인터페이스 방식을 채널 특성별로 구분했다.**  
2. **업무모듈 단위로 플랫폼을 분해했다.**  
3. **대내 서비스 연계와 데이터 연계를 분리했다.**  
4. **실시간 / 비동기 / 배치 / 파일 / DB직접조회가 공존하는 구조를 표현했다.**

따라서 후속 설계에서는 반드시 다음이 필요하다.

- 업무모듈별 Interface Catalog 작성
- 외부 시스템별 API/EAI/ETL/JDBC/FOS 사용기준 명문화
- Kafka/UMS/아리톡/보고서의 세부 시나리오 정의
- RDW/ADW/UMS 연계 데이터 계약 구체화
- 종단 추적, 오류복구, 운영모니터링 기준 수립

이 장표는 **마케팅플랫폼의 “무엇과 연결되는가”를 보여주는 상위 연관관계도**로서 매우 유용하며, 이후 상세 인터페이스 목록과 인터페이스 정의서의 출발점이 된다.
