# 논리기술아키텍처 — 레이어드 아키텍처 — BI 포탈 구조 분석

## 1. 분석 개요

첨부 장표의 **BI 포탈 표준 아키텍처 구성**을 기준으로 BI 포탈을 다음 5개 논리 레이어로 분해한다.

1. Client Access Layer
2. Service Layer
3. I/F Layer
4. Data Layer
5. 형상·배포 Layer

BI 포탈은 IaaS 위에 신용실적, BI 포털, OLAP, Self-BI를 독립 실행영역으로 배치하고, 각 솔루션의 특성에 맞는 프레임워크와 저장소를 사용하는 복합 분석 서비스다. 공통 인프라의 IMDG가 세션과 캐시를 지원하고, Oracle Exadata의 RDW·ADW가 주요 분석 데이터 원천을 제공한다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. `DataEye`, `MSTR`, `IMDG`, `LLM`, `Nexux` 등 장표 표기는 원문을 우선 반영했다. `Nexux`는 Nexus를 의미할 가능성이 있으며, 실제 제품명·버전·라이선스·연계 프로토콜과 데이터 저장 위치는 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **분석 기능별 런타임 분리**: 신용실적, BI 포털, OLAP, Self-BI가 각각 별도 WEB·WAS 또는 AP 실행영역을 사용한다.
- **제품 종속성 격리**: NH Cloud Framework, DataEye Framework, OLAP Engine, Self-BI Engine의 경계를 분리해 장애와 변경 영향을 제한한다.
- **접근 경로 표준화**: 전용 또는 범용 Browser가 L4와 WEB 계층을 거쳐 각 분석 서비스에 접근한다.
- **세션·데이터 캐시 분리**: 공통 인프라 IMDG가 신용실적과 BI 포털의 Session/Data Cache를 제공한다.
- **분석 데이터 중심 구조**: RDW와 ADW를 공통 데이터 원천으로 사용하되 BI 포털, OLAP, Self-BI 전용 저장소도 목적별로 분리한다.
- **표준 인터페이스 적용**: SSO, CruzAPIM, FOS, MFT, 통합관제, IT 메타, 배치작업관리, UMS 등이 업무 서비스와 외부 시스템의 직접 결합을 완화한다.
- **전용 연계 방식 사용**: OLAP은 Adapter로 MSTR와 연결하고, Self-BI는 REST API로 LLM 서비스와 연계한다.
- **형상·배포 경로 분리**: 개발은 GitLab·GitLab Runner·Dev Pipeline, 운영은 eCAMS·운영 Pipeline을 중심으로 통제한다.

## 4. 레이어별 구조 분석

### 4.1 Client Access Layer

| 구성요소 | 역할 | 설계 의미 |
|---|---|---|
| 전용 Browser | 특정 BI 또는 신용실적 화면 접근 | 전용 UI 기능과 브라우저 정책을 통제한다. |
| 범용 Browser | BI 포털, OLAP, Self-BI 화면 접근 | 표준 웹 접근성을 제공한다. |
| 화면연계 | 서로 다른 분석 화면 사이의 이동 | URL, 토큰, 메뉴 문맥을 전달한다. |
| L4 | WEB 노드 부하분산과 장애 우회 | 다중 WEB 노드의 고가용성 진입점을 제공한다. |

화면연계는 단순 링크가 아니라 인증 문맥, 사용자 권한, 조회 조건을 전달할 수 있으므로 파라미터 위변조 방지와 허용 목록 검증이 필요하다.

### 4.2 Service Layer

#### 4.2.1 공통 인프라와 IMDG

공통 인프라 영역의 IMDG는 Session/Data Cache를 제공한다. 장표상 신용실적 WAS와 BI 포털 전용 노드가 캐시를 사용한다.

- 세션 공유를 통해 WEB/WAS 다중 노드 간 사용자 상태를 유지한다.
- 반복 조회 데이터와 공통 코드를 캐시해 DB 부하를 줄인다.
- 캐시 장애가 전체 로그인 또는 조회 장애로 확대되지 않도록 복제, 만료, 원본 조회 대체 경로가 필요하다.
- 서비스별 키 네임스페이스와 TTL을 분리해 데이터 충돌과 오염을 방지해야 한다.

#### 4.2.2 신용실적 영역

```text
Browser → L4 → 신용실적 WEB → NH Cloud Framework → 신용실적 WAS
                                      ↕
                              IMDG Session/Data Cache
```

신용실적은 표준 온라인 프레임워크 기반의 업무 서비스다. WEB은 정적 자원과 요청 전달을, WAS는 인증된 업무 요청과 실적 조회 로직을 처리한다.

#### 4.2.3 BI 포털 영역

```text
Browser → L4 → BI포털 WEB → DataEye Framework → BI포털 WAS
                                            ↕
                                     BI포털 전용 IMDG
```

BI 포털은 보고서, 대시보드, 통합검색과 관리 기능을 제공하는 진입 허브다. 전용 IMDG를 두어 포털 세션과 데이터 캐시를 다른 업무와 격리한 것으로 해석된다.

#### 4.2.4 OLAP 영역

```text
Browser → L4 → OLAP WEB ─┬→ OLAP WAS
                         └→ Adapter → OLAP MSTR
                                      └→ OLAP Engine
```

OLAP은 다차원 분석과 정형·비정형 보고서 실행을 담당한다. Adapter는 포털 요청 모델과 MSTR 또는 OLAP Engine의 제품별 호출 규격 사이를 변환하는 경계다.

#### 4.2.5 Self-BI 영역

```text
Browser → L4 → Self-BI WEB → Self-BI WAS ── REST API ──▶ LLM
```

Self-BI는 사용자가 직접 데이터셋, 분석 조건, 시각화를 구성하는 서비스다. LLM 연계는 자연어 질의나 분석 보조 기능으로 추정되며 다음 통제가 필요하다.

- 허용된 메타데이터와 집계 데이터만 프롬프트에 포함
- 개인정보 및 민감정보 마스킹
- 생성 SQL의 읽기 전용·스키마 허용 목록 검증
- 응답 근거, 사용 모델, 프롬프트와 결과 감사로그 기록
- 타임아웃, 토큰 한도, 재시도 및 대체 응답 적용

## 5. 주요 컴포넌트 분석

| 컴포넌트 | 주요 책임 | 핵심 연계 | 운영 주의사항 |
|---|---|---|---|
| L4 | 서비스 진입점과 부하분산 | Browser ↔ WEB | 헬스체크, 세션 고정 최소화, TLS 종료 위치 |
| WEB | 정적 콘텐츠, 역방향 프록시 | L4 ↔ WAS | 보안 헤더, 업로드 제한, 접근로그 |
| 신용실적 WAS | 신용실적 업무 처리 | IMDG, DB, I/F | 거래 권한, 응답시간, 개인정보 통제 |
| BI포털 WAS | 포털·대시보드 업무 | DataEye, IMDG, DB | 캐시 정합성, 동시 접속, 보고서 실행 제한 |
| OLAP WAS/MSTR | 다차원 분석 실행 | Adapter, OLAP Engine | 쿼리 폭주, 큐잉, 메모리·세션 제한 |
| Self-BI WAS | 사용자 주도 분석 | ADW/RDW, LLM | 데이터 권한, SQL 통제, 결과 반출 통제 |
| IMDG | 세션 및 데이터 캐시 | WAS ↔ 원본 DB | 복제, TTL, Eviction, 캐시 미스 대응 |
| CruzAPIM | API 표준화와 정책 적용 | 내부·외부 API | 인증, 할당량, 추적 ID, 버전 관리 |
| FOS/MFT | 파일 연계 | 외부/내부 시스템 | 무결성, 암호화, 재전송, 완료 마커 |
| 통합관제 | 상태·성능·로그 관제 | 전 계층 | GUID 기반 상관분석, 알람 중복 억제 |
| RDW | 준실시간 운영·분석 원천 | CDC/JDBC/ETL | 읽기 부하, 최신성, 원천 정합성 |
| ADW | 통합·집계·분석 데이터 | ETL, BI 도구 | 배치 윈도우, 자원그룹, 마트 품질 |

## 6. 주요 처리 흐름

### 6.1 사용자 조회 흐름

```text
사용자 Browser
  → L4
  → 대상 WEB
  → 대상 WAS/Engine
  → SSO 및 권한 검증
  → IMDG 캐시 조회
      ├─ Hit  → 결과 조립
      └─ Miss → RDW/ADW/전용 저장소 조회 → 캐시 갱신
  → 결과 반환
```

### 6.2 BI 포털 보고서 흐름

```text
BI포털 화면 → BI포털 WEB → DataEye Framework → BI포털 WAS
            → 사용자/조직/메뉴 권한 검증
            → RDW 또는 ADW 조회
            → 보고서/대시보드 렌더링
            → 감사·성능 로그 기록
```

### 6.3 OLAP 분석 흐름

```text
OLAP 화면 → OLAP WEB → OLAP WAS
          → Adapter 변환 → MSTR/OLAP Engine
          → OLAP 저장소 또는 ADW 조회
          → 집계 결과 반환
```

Adapter는 제품 종속 API와 데이터 형식을 격리해야 하며, 직접 DB 접속 정보가 WEB 또는 사용자 단말에 노출되어서는 안 된다.

### 6.4 Self-BI와 LLM 연계 흐름

```text
사용자 자연어 질의
  → Self-BI WEB/WAS
  → 사용자 데이터 권한 확인
  → 메타데이터·스키마 범위 축소
  → REST API로 LLM 요청
  → 생성 결과/SQL 정책 검증
  → 읽기 전용 분석 실행
  → 근거와 함께 결과 반환
```

### 6.5 형상·배포 흐름

```text
개발자 → GitLab → 코드 병합 → GitLab Runner → 빌드
       → 보안취약점 점검 → Dev Pipeline → 개발환경

승인 형상 → eCAMS → 운영 빌드 → 보안취약점 점검
          → 운영 Pipeline → 운영환경
```

개발 산출물을 운영에서 다시 임의 빌드하기보다 동일 Artifact의 승격을 권장한다. 빌드 해시, SBOM, 취약점 결과와 배포 승인 이력이 함께 보존되어야 한다.

## 7. 레이어 간 호출 원칙

1. Browser는 L4와 WEB을 경유하며 WAS 또는 DB에 직접 접속하지 않는다.
2. WEB은 화면 제공과 프록시 역할에 집중하고 업무 로직을 보유하지 않는다.
3. WAS와 분석 Engine은 승인된 서비스 계정으로만 RDW·ADW에 접근한다.
4. 포털 간 화면연계는 URL 직접 결합보다 표준 라우팅과 단기 토큰을 사용한다.
5. OLAP 제품 종속 호출은 Adapter에 격리한다.
6. LLM 연계는 Self-BI 서비스 경계에서만 수행하며 DB 자격증명을 전달하지 않는다.
7. 파일 교환은 FOS/MFT, API 연계는 CruzAPIM을 우선 사용한다.
8. 모든 요청은 GUID 또는 Trace ID를 유지하여 WEB·WAS·DB·외부 API 로그를 연결한다.
9. 캐시는 원본 데이터의 소유자가 아니며 캐시 실패 시 원본 조회 또는 명시적 오류로 전환한다.

## 8. 품질 속성 평가

### 8.1 가용성

- L4와 다중 WEB/WAS 구성은 노드 장애를 우회할 수 있다.
- IMDG와 전용 분석 Engine도 클러스터 또는 복제 구성이 필요하다.
- 제품별 장애 격리는 장점이지만 공통 SSO, IMDG, ADW 장애가 전체 서비스에 영향을 줄 수 있다.

### 8.2 확장성

- WEB/WAS는 수평 확장이 가능하다.
- OLAP·Self-BI는 쿼리 큐, 동시 실행 수, 메모리와 DB 자원그룹을 함께 확장해야 한다.
- 대용량 보고서는 온라인 요청과 분리해 비동기 생성 및 다운로드 방식으로 제공하는 것이 안전하다.

### 8.3 보안

- SSO 인증 이후에도 데이터셋·행·열 수준 권한을 재검증해야 한다.
- 보고서 내 개인정보는 마스킹하고 다운로드·메일·파일 반출을 감사해야 한다.
- Self-BI와 LLM은 프롬프트 유출, 과도한 SQL, 데이터 외부전송을 차단해야 한다.
- 서비스 계정과 DB 계정은 솔루션·환경·읽기/쓰기 권한별로 분리한다.

### 8.4 관측성

- 통합관제는 L4, WEB, WAS, Engine, IMDG, DB 지표를 하나의 서비스 맵으로 연결해야 한다.
- 핵심 지표는 로그인 성공률, 캐시 적중률, 보고서 실행시간, DB 대기시간, 큐 길이, 실패율이다.
- 제품별 로그 형식을 표준 필드(GUID, 사용자, 서비스, 데이터셋, 소요시간, 결과코드)로 정규화해야 한다.

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| 여러 BI 제품의 중복 기능 | 비용 증가와 사용자 혼란 | 포털·OLAP·Self-BI 기능 책임과 사용 대상을 명문화한다. |
| IMDG 장애 또는 캐시 오염 | 로그인·조회 장애, 잘못된 결과 | 캐시 복제, TTL, 원본 대체와 캐시 무효화 표준을 적용한다. |
| 화면연계의 URL·세션 결합 | 제품 변경과 보안에 취약 | 중앙 라우팅, 단기 서명 토큰, 파라미터 허용 목록을 사용한다. |
| 장시간·대용량 쿼리 | ADW/RDW 자원 고갈 | DB Resource Manager, 쿼리 큐, 시간·행 제한을 적용한다. |
| LLM의 임의 SQL 생성 | 정보 유출과 과부하 | 의미 계층, 읽기 전용 계정, SQL Parser와 승인 정책을 둔다. |
| RDW와 ADW 사용 기준 불명확 | 정합성 논쟁과 중복 적재 | 데이터 최신성·용도·SLA에 따른 조회 원천 기준을 정의한다. |
| 개발·운영 빌드 불일치 | 재현 불가와 배포 사고 | Immutable Artifact 승격, SBOM과 서명 검증을 적용한다. |
| 제품별 독립 모니터링 | 장애 원인 추적 지연 | GUID 기반 E2E 추적과 공통 대시보드를 구축한다. |

## 10. 설계·운영 점검 체크리스트

## 11. 종합 평가

이 아키텍처는 BI 기능을 신용실적, 포털, OLAP, Self-BI로 분리하고 각 제품에 적합한 프레임워크와 실행 Engine을 배치한 **다중 솔루션 기반 분석 서비스 플랫폼**이다. 공통 L4·SSO·IMDG·인터페이스 계층과 Exadata 데이터 계층을 재사용하면서도 제품 종속성을 서비스 노드 내부에 격리한 점이 강점이다.

다만 전체 안정성은 제품 수보다 **공통 인증, 데이터 권한, 캐시 일관성, RDW/ADW 조회 기준, 쿼리 자원 통제와 배포 Artifact 관리**에 좌우된다. 특히 Self-BI와 LLM 연계는 편의성보다 데이터 보호와 실행 통제를 우선해야 하며, 모든 분석 경로에 동일한 데이터 계약·감사·관측성 기준을 적용해야 한다.
