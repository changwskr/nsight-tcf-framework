# 인터페이스 아키텍처 — 마케팅 플랫폼 연관도 분석

## 1. 핵심 결론

장표는 마케팅 플랫폼(MP)을 중심으로 채널, 계정계, 알림·영업 시스템, 데이터 플랫폼, 메시징 및 보고서의 인터페이스 관계를 표현한다. 마케팅 플랫폼 내부에는 13개 업무 모듈이 있고, 연계 특성에 따라 표준 중계가 구분된다.

```text
채널 계층
통합업무시스템 ↔ 영업점 MCA ↔ MP
정보단말       ↔──────────── MP
인터넷/스마트뱅킹 ↔ Kafka ─── MP
SMS/EMAIL/PUSH ← UMS ←──────── MP
보고서         ↔──────────── MP

대내·데이터 계층
MP ↔ API G/W ↔ EAI ↔ 코어뱅킹
MP ↔ API G/W ────── 아리톡(알림 서비스)
MP ↔ API G/W ↔ EAI ↔ 태블릿 브랜치
MP ─ ETL ─────────> RDW
MP ─ ETL ─────────> ADW
MP ─ ETL ─ FOS ───> UMS
MP ─ JDBC ───────── RDW   # 장표상 방향 화살표 미표시
```

이 구조의 핵심 원칙은 다음과 같다.

- 동기 온라인 연계는 API G/W와 필요 시 EAI를 경유한다.
- 행동 이벤트는 Kafka로 비동기 전달한다.
- 대량 데이터 이동은 ETL, 파일성 전달은 FOS를 결합한다.
- 애플리케이션 데이터 접근은 JDBC를 사용하되 읽기·쓰기 책임을 제한한다.
- 메시지 발송은 UMS로 통합한다.

## 2. 마케팅 플랫폼 내부 업무 모듈 전사

| No. | 업무 모듈 | 코드 | 핵심 역할 |
|---:|---|---|---|
| 1 | 공통 | CO | 공통 코드, 기준 기능, 플랫폼 공통 서비스 |
| 2 | 통합고객 | IC | 전사 고객 통합 조회 및 식별 |
| 3 | 개인고객 | PC | 개인고객 정보와 서비스 |
| 4 | 기업고객 | BC | 기업고객 정보와 서비스 |
| 5 | 미니싱글뷰 | MS | 영업 현장의 고객 핵심 요약 조회 |
| 6 | 상담판매 | SA | 상담·추천·판매 지원 |
| 7 | 통합상품 | PD | 상품 기준과 판매 정보 통합 |
| 8 | 캠페인 | CM | 캠페인 기획, 대상, 실행, 성과 |
| 9 | EBM | EB | 이벤트 기반 마케팅 판단·처리 |
| 10 | 영업지원 | SS | 영업 활동 및 현장 지원 |
| 11 | CS | CS | 고객 서비스·응대 지원 |
| 12 | 컨텐츠 | CT | 마케팅 콘텐츠와 소재 관리 |
| 13 | 메시지 | MG | 메시지 생성·템플릿·발송 연계 |

모듈 코드는 Interface ID, API 경로, 데이터 소유자와 배포 단위의 기준으로 활용할 수 있다. 단, 장표가 동일 런타임 또는 독립 마이크로서비스 여부를 보여주지는 않으므로 물리 배포 구조로 단정해서는 안 된다.

## 3. 장표 관계 전사

| No. | 외부 시스템/채널 | 중계·프로토콜 | 마케팅 플랫폼 관계 | 장표상 방향 |
|---:|---|---|---|---|
| 1 | 통합업무시스템 | 영업점 MCA | 온라인 업무·미니싱글뷰 | 양방향 화살표 |
| 2 | 정보단말 | 직접 온라인 접점 | 정보계 업무 처리 | 양방향 화살표 |
| 3 | 인터넷뱅킹·스마트뱅킹 | Kafka | 고객 행동 이벤트 | 양방향처럼 표시되나 실제 발행·소비 방향 확인 필요 |
| 4 | SMS·EMAIL·PUSH | UMS | 메시지 발송 | 플랫폼/UMS에서 채널 방향으로 해석 |
| 5 | 보고서 | 직접 접점 | 보고서 생성·조회 | 양방향 화살표 |
| 6 | 코어뱅킹 | EAI + API G/W | 계정계 온라인 연계 | 양방향 화살표 |
| 7 | 아리톡(알림 서비스) | API G/W | 알림 서비스 연계 | 양방향 화살표 |
| 8 | 태블릿 브랜치 | EAI + API G/W | 태블릿 영업 연계 | 양방향 화살표 |
| 9 | 아리톡(알림 서비스) | API G/W | 별도 업무 연계 | 양방향 화살표 |
| 10 | RDW | ETL | 데이터 적재·동기화 | RDW 방향 화살표 |
| 11 | ADW | ETL | 분석 데이터 적재·동기화 | ADW 방향 화살표 |
| 12 | UMS | ETL + FOS | 배치·파일성 메시지 연계 | UMS 방향 화살표 |
| 13 | RDW | JDBC | 온라인 또는 직접 DB 접근 | 방향 화살표 없음 |

> 아리톡이 두 번 표시된 것은 서로 다른 마케팅 모듈 또는 API 업무를 나타낼 가능성이 있다. 장표만으로 API 명칭과 대상 모듈을 확정할 수 없으므로 별도 Interface ID로 등록해 확인해야 한다.

## 5. 채널 관계 분석

### 5.1 통합업무시스템 ↔ 영업점 MCA ↔ MP

영업점 MCA는 통합업무시스템과 마케팅 플랫폼 사이의 채널 표준 접점이다. 주로 미니싱글뷰, 통합고객, 상담판매, 통합상품, 영업지원 모듈을 호출할 것으로 해석된다.

```text
통합업무 화면
  → 영업점 MCA
      → 사용자·점포·단말 인증
      → 표준전문/JSON 변환
      → MP API 호출
      → 응답 전문 변환
  ← 화면 표시
```

통제 기준:

- MCA 전문 번호와 MP GUID를 연결한다.
- 직무·점포별 조회 권한을 적용한다.
- 고객 통합정보의 기준 시각과 출처를 응답에 포함한다.
- 마케팅 플랫폼 장애가 영업점 핵심 거래를 차단하지 않도록 Fallback한다.
- MCA와 MP 양쪽에 동일 업무 변환 로직을 중복하지 않는다.

### 5.2 정보단말 ↔ MP

정보단말은 중계 제품 표기가 없이 마케팅 플랫폼과 직접 연결된다. 실제 운영에서는 WEB/L4/API 접점, 인증 방식과 경로를 명시해야 한다.

- HTTPS와 사용자 SSO 적용
- CSRF·세션 고정·입력 검증
- 화면별 API Scope와 행 수준 권한
- 응답 데이터 마스킹
- 직접 DB 접근 금지

### 5.3 인터넷·스마트뱅킹 ↔ Kafka ↔ MP

이 관계는 고객 행동 이벤트를 Kafka로 전달하는 비동기 흐름이 핵심이다. 장표에는 양방향 화살표처럼 보이지만, 일반적인 처리 기준으로는 채널이 이벤트를 발행하고 MP가 소비한다. 반대 방향 이벤트가 필요하면 별도 Topic과 계약으로 분리해야 한다.

```text
채널 행동 발생
  → 행동 이벤트 발행
  → Kafka Topic
  → MP Consumer
  → 행동정보/EBM 처리
```

거래 응답 경로와 이벤트 발행 경로를 분리하여 Kafka 장애가 고객 거래에 영향을 주지 않아야 한다.

### 5.4 MP → UMS → SMS·EMAIL·PUSH

메시지 모듈(MG), 캠페인(CM), EBM(EB)이 발송을 요청하고 UMS가 채널별 전송을 담당한다.

- 캠페인·고객·오퍼 기준 중복 발송 방지
- 동의·수신 거부·접촉 빈도 확인
- 템플릿 승인과 유효기간 검증
- Message ID와 GUID·Campaign ID 연결
- 요청, 큐잉, 발송, 전달, 실패, 거부, 만료 상태 분리

### 5.5 MP ↔ 보고서

보고서 관계는 보고서 생성 요청과 결과 조회·다운로드로 해석된다. 구체적인 RD 제품 또는 프로토콜은 장표에 없다.

- 보고서 템플릿 ID와 버전 관리
- 비동기 생성 시 Job ID와 상태조회 제공
- 대용량 보고서 다운로드 권한·만료 적용
- 생성 데이터의 기준 시각과 조회 조건 감사
- 개인정보 포함 보고서의 암호화·워터마크 적용

## 6. 대내 온라인 관계 분석

### 6.1 MP ↔ API G/W ↔ EAI ↔ 코어뱅킹

코어뱅킹 연계는 API G/W와 EAI를 순차 경유한다.

- API G/W: 인증, 인가, API 버전, Rate Limit, Routing, 감사
- EAI: 레거시 전문과 프로토콜 변환, 시스템 중재
- 코어뱅킹: 계정계 업무와 원장 데이터 소유
- MP: 마케팅 업무 규칙과 고객 접점 데이터 소유

이 경로는 여러 중계 단계를 거치므로 종단 타임아웃 예산을 계층별로 배분해야 한다.

```text
전체 SLA 3초 예시
MP 처리           300ms
API G/W           100ms
EAI 변환·중재     200ms
코어뱅킹 처리   1,800ms
네트워크·여유     600ms
```

### 6.2 MP ↔ API G/W ↔ 아리톡

아리톡은 알림 서비스로 표기되어 있다. MP의 메시지·캠페인·영업지원 모듈과 연계될 가능성이 높다.

- 알림 요청 API와 결과 Callback 분리
- 수신자 식별자·연락처 최소 전달
- 템플릿·버튼·딥링크 검증
- 중복·재시도·만료 정책
- 아리톡 장애 시 UMS 또는 대체 채널 적용 여부

장표에 두 개의 아리톡 연결이 있으므로 API별 Source 모듈과 업무 목적을 별도로 식별해야 한다.

### 6.3 MP ↔ API G/W ↔ EAI ↔ 태블릿 브랜치

태블릿 브랜치는 현장 영업 채널로 해석된다. 상담판매, 통합상품, 통합고객, 영업지원과 관계가 높다.

- 단말 인증과 사용자 인증을 동시에 적용한다.
- 분실 단말 원격 차단과 토큰 만료를 지원한다.
- 오프라인 입력의 동기화·충돌 규칙을 정의한다.
- 태블릿에 저장되는 개인정보를 최소화·암호화한다.
- EAI 변환이 필요한 이유와 제거 가능성을 검토한다.

## 7. 데이터 플랫폼 관계 분석

### 7.1 MP → ETL → RDW

장표의 화살표는 마케팅 플랫폼에서 RDW 방향이다. 캠페인, 상담, 고객 반응, 메시지 결과 등의 운영 데이터를 정보계 저장소에 적재하는 경로로 해석된다.

- Source 테이블과 변경 기준
- 업무일자·워터마크
- 고객·캠페인·상품 키 표준화
- Staging 후 원자적 적재
- 건수·합계·해시 대사

### 7.2 MP → ETL → ADW

ADW에는 분석·성과·모델링에 필요한 마케팅 데이터가 적재된다.

- 캠페인 대상·반응·전환·비용
- 고객 접촉·채널 성과
- 상품 추천·오퍼 성과
- EBM 판단과 실제 발송·반응 결과

RDW와 ADW에 같은 데이터가 중복 적재될 경우 데이터 소유권과 공식 지표 산출 위치를 명확히 해야 한다.

### 7.3 MP — JDBC — RDW

장표의 JDBC 선에는 방향 화살표가 없다. 온라인 조회인지, Feedback 쓰기인지, 양방향인지 상세 설계 확인이 필요하다.

안전한 기본 원칙:

- 온라인은 읽기 전용 DB Service를 우선한다.
- 쓰기는 소유 스키마 또는 승인된 프로시저로 제한한다.
- Connection Pool과 Query Timeout 상한을 둔다.
- GUID를 DB Client Identifier로 전달한다.
- 대량 쿼리는 ETL 또는 별도 분석 경로로 분리한다.
- RDW 스키마 변경이 MP 배포에 직접 영향을 주지 않도록 뷰·API 계약을 사용한다.

## 8. ETL + FOS → UMS 관계

이 경로는 대량 메시지 대상 또는 발송 파일을 ETL로 생성하고 FOS를 통해 UMS로 전달하는 배치성 연계로 해석된다.

```text
캠페인 대상 추출
  → ETL 파일 생성
  → 건수·해시·동의 검증
  → FOS 전송
  → UMS 접수
  → 채널 발송
  → 결과 파일/데이터 회신
```

필수 파일 계약:

- File ID, Campaign ID, 업무일자, Sequence
- 파일명, Layout, 문자셋, 압축·암호화
- Manifest 또는 Atomic Rename 완료 신호
- 레코드 건수와 SHA-256
- 수신·검증·발송·결과 상태
- 중복 방지와 재전송 정책
- 개인정보 보존·폐기 시점

아래는 장표의 배치 위치와 업무 성격을 기반으로 한 설계 검토용 추론이며, 확정 매핑은 아니다.

| PC | 코어뱅킹, 정보단말 | 온라인 API |
| BC | 코어뱅킹, 태블릿 브랜치 | 온라인 API |

| PD | 코어뱅킹, RDW/ADW | API, ETL |

## 11. 종단 추적

```text
GUID
├─ 영업점 MCA 전문번호
├─ API G/W Request ID
├─ EAI Message ID
├─ Core Transaction ID
├─ Kafka Event ID
├─ Campaign/EBM Decision ID
├─ UMS Message ID

└─ JDBC Client Identifier
```

하위 ID는 `parentGuid`로 연결한다. 각 인터페이스의 업무 소유자, 송·수신 담당자, 중계 운영자, 개인정보 책임자와 장애 승인자를 **RACI**로 지정한다.

## 12. 오류·재시도·멱등성

### 온라인 API

- 비멱등 갱신 요청은 자동 재시도하지 않는다.
- Timeout 후 결과조회 또는 동일 Idempotency Key 재호출을 지원한다.
- 표준 HTTP 오류와 업무 오류를 분리한다.
- API G/W와 EAI 오류 코드를 MP 표준 오류로 매핑한다.

### Kafka

- At-least-once 전달을 전제로 Consumer를 멱등하게 만든다.
- 이벤트 계약은 **Schema Registry** 또는 동등한 저장소에서 버전과 호환성을 관리한다.
- Retry Topic과 DLQ를 사용한다.
- Offset 재설정은 승인·감사 대상이다.

### ETL/FOS

- 실행 ID와 파일 ID로 중복을 방지한다.
- 실패 Step·파티션·파일 단위로 재처리한다.
- 전송 완료와 업무 반영 완료를 별도 상태로 관리한다.

### JDBC

- DB Failover 후 중간 Commit 여부를 확인한다.
- 무조건 재실행하지 않고 트랜잭션 상태를 조회한다.
- 장기 쿼리는 취소·격리한다.

## 13. 보안 및 개인정보

- MCA·정보단말·태블릿은 단말과 사용자를 모두 인증한다.
- API G/W에서 mTLS, OAuth2/JWT, Scope, Rate Limit을 적용한다.
- EAI 전문의 민감 필드를 마스킹하고 감사한다.
- Kafka에는 원문 고객식별자 대신 가명 키 사용을 우선한다.
- UMS 전달 전 고객 동의와 수신 거부를 확인한다.
- ETL/FOS 파일은 암호화하고 수신 후 안전하게 폐기한다.
- JDBC 계정은 인터페이스·모듈별 최소 권한으로 분리한다.
- 보고서의 행·열 권한과 다운로드 감사를 적용한다.

## 14. 성능 및 용량

- MCA·API G/W·EAI의 단계별 Timeout 합이 전체 SLA를 넘지 않게 한다.
- 코어뱅킹 호출에 Circuit Breaker와 Bulkhead를 적용한다.
- Kafka 파티션은 고객·세션 순서와 피크 이벤트량을 함께 고려한다.
- 캠페인 대량 ETL과 MP 온라인 JDBC 조회의 RDW 자원을 분리한다.
- JDBC Pool 총합을 DB 최대 세션과 연동해 산정한다.
- UMS 대량 파일 생성·전송·발송에 Backpressure를 적용한다.
- 보고서 생성은 비동기화하고 대용량 결과를 별도 저장한다.

## 15. 관측성

| 경로 | 핵심 지표 |
|---|---|
| MCA ↔ MP | TPS, 응답시간, 전문 오류, Fallback |
| API G/W/EAI ↔ 코어 | 계층별 지연, Timeout, 변환 오류 |
| Kafka ↔ MP | 발행량, Consumer Lag, DLQ, 중복 |
| MP → UMS | 요청·발송·전달·실패·거부·만료 |
| ETL → RDW/ADW | 처리량, 실행시간, 대사 차이 |
| ETL/FOS → UMS | 생성·전송·검증·접수 건수 |
| JDBC ↔ RDW | Pool, 세션, SQL 지연, Lock, 오류 |
| 보고서 | 생성시간, 크기, 실패, 다운로드 |

## 16. DR 및 가용성

- MCA, API G/W, EAI, Kafka, UMS, FOS를 다중화한다.
- DR 전환 시 API 라우팅·인증서·EAI 상대 주소를 검증한다.
- Kafka Offset과 Event ID를 보존해 중복 소비를 방지한다.
- ETL 스케줄러와 FOS 전송 주체는 한 센터만 Active로 유지한다.
- UMS 대기 메시지의 소유권을 펜싱해 중복 발송을 막는다.
- RDW JDBC 서비스의 Failover와 Connection Pool 재연결을 검증한다.
- 원복 후 온라인 거래, 이벤트, 파일, 데이터 적재를 대사한다.

## 21. 최종 평가

마케팅 플랫폼 연관도는 13개 업무 모듈을 중심으로 영업점·정보단말·디지털 채널, 코어뱅킹·알림·태블릿 시스템, RDW·ADW 및 UMS를 표준 중계 방식으로 연결한다. API G/W/EAI, Kafka, ETL/FOS, JDBC를 인터페이스 성격에 맞춰 구분한 방향은 합리적이다.

다만 실제 설계로 사용하려면 장표의 선을 Interface ID 단위로 구체화해야 한다. 특히 Kafka 방향, 두 아리톡 연계의 차이, MP 모듈별 Source/Target, JDBC 읽기·쓰기 권한, ETL+FOS→UMS의 데이터 의미를 확정해야 한다. GUID 종단 추적, 멱등성, 고객 동의, 최소 권한, 정합성 대사, 관측성과 DR을 모든 관계에 공통 적용해야 운영 가능한 아키텍처가 된다.
