# 아키텍처 표준화 — 정보단말 패키지 구성 분석

## 1. 핵심 결론

이 장표는 WebTop/WebSquare 기반 정보단말 프로젝트의 Web Root를 **빌드 산출물, 전사 공통, 엔진 리소스, 정보단말 공통, 레이아웃, 업무 화면**으로 분리한 패키지 표준이다.

```text
Web Root
├── _wpack_       화면 XML 빌드 결과 JavaScript
├── cm            전사/기본 공통 XML·정적 리소스
├── websquare     WebSquare 엔진 리소스·설정
└── webTop
    ├── cm        정보단말 전용 공통 XML·정적 리소스
    ├── layout    정보단말 공통 Layout XML
    └── screen    업무 코드별 화면 XML
```

핵심 표준화 원칙은 다음과 같다.

1. 원본 화면 XML과 빌드된 JavaScript를 분리한다.
2. 기본 공통과 정보단말 공통을 별도 계층으로 둔다.
3. 엔진 제공 리소스와 업무 개발 리소스를 분리한다.
4. 화면은 업무 코드 계층에 따라 배치한다.
5. 파일명만으로 소속 업무와 화면 성격을 식별할 수 있게 한다.

## 4. 계층별 역할 분석

### 4.1 `_wpack_` — 빌드 산출물 계층

- 화면 XML을 브라우저 실행용 JavaScript로 변환한 결과를 둔다.
- 개발자가 직접 수정하는 원본 영역이 아니다.
- CI/CD 파이프라인에서 재생성 가능해야 한다.
- 소스 저장소 포함 여부는 빌드·배포 정책으로 일관되게 정한다.

직접 수정하면 XML 원본과 산출물이 불일치하므로 배포 재현성이 깨진다.

### 4.2 `cm` — 기본 공통 계층

- 여러 화면 또는 솔루션 영역이 공유하는 공통 함수·UDC·정적 리소스를 둔다.
- 특정 업무나 정보단말만의 규칙을 넣지 않는다.
- 변경 영향 범위가 크므로 공통 컴포넌트 소유자의 검토가 필요하다.

### 4.3 `websquare` — 엔진 계층

- WebSquare 런타임 리소스와 설정을 둔다.
- 제품 제공 파일과 프로젝트 사용자 정의 파일을 구분한다.
- 제품 업그레이드 시 덮어쓰기 위험을 줄이기 위해 업무 코드를 두지 않는다.

### 4.4 `webTop/cm` — 정보단말 공통 계층

- 정보단말 화면에 공통 적용되는 함수, UDC, CSS, 이미지, 폰트를 둔다.
- 기본 공통 계층을 확장하되 같은 기능을 복제하지 않는다.
- 정보단말 전용 인증 컨텍스트, 화면 유틸리티, 공통 위젯 등이 배치될 수 있다.

### 4.5 `webTop/layout` — 레이아웃 계층

- 헤더·메뉴·업무 탭·상태영역 등 공통 화면 골격을 정의한다.
- 업무 로직을 포함하지 않고 조립과 배치 책임에 집중한다.
- 접근성·반응형·표준 크기 정책을 중앙 적용한다.

### 4.6 `webTop/screen` — 업무 화면 계층

- 실제 업무 화면 XML 원본을 업무 코드별로 배치한다.
- 디렉터리 코드와 파일명 코드가 일치해야 한다.
- 화면별 데이터셋, 이벤트, 서비스 호출과 UI 컴포넌트를 관리한다.

## 5. 공통 영역의 이중 계층 해석

```text
cm                    전사/기본 공통
 └─ 모든 적용 대상이 공유

webTop/cm             정보단말 공통
 └─ 정보단말 화면에서만 공유

webTop/screen         개별 업무
 └─ 특정 대구분·업무·화면에서 사용
```

공통화 판단 순서는 다음과 같다.

1. 한 화면에서만 쓰이면 `screen` 내부에 둔다.
2. 정보단말 여러 화면에서 쓰이면 `webTop/cm`으로 승격한다.
3. 다른 애플리케이션까지 공유하면 기본 `cm`으로 승격한다.

역방향 의존은 금지하는 것이 바람직하다. 즉 기본 공통이 정보단말 공통이나 특정 업무 화면을 참조하면 안 된다.

## 6. 화면 코드와 파일 명명규칙 분석

장표 예시는 다음 구조를 암시한다.

```text
[대구분 2자][업무구분 2자][화면분류 1자][일련번호][화면유형].xml

MP + CO + A + 0000 + M0  → mpcoa0000M0.xml
BI + CR + A + 0000 + M0  → bicra0000M0.xml
```

이는 이미지에서 추론한 구조이며 공식 자리수는 확인이 필요하다.

권고 검증 규칙:

- 경로의 대구분·업무구분·화면분류와 파일명 접두부가 일치해야 한다.
- 파일명은 영문·숫자만 사용하고 공백과 임의 특수문자를 금지한다.
- 화면 ID는 저장소 전체에서 유일해야 한다.
- 대소문자 규칙을 고정해 Linux 배포 시 오류를 방지한다.
- 폐기 화면 ID는 재사용하지 않고 상태를 별도 관리한다.

## 7. 빌드·배포 흐름

```text
개발자
  │ 화면 XML / 공통 XML / 리소스 변경
  ▼
Git 저장소
  │ 정적 검증·리뷰
  ▼
CI Build
  ├── XML 문법/참조 검증
  ├── 화면 코드·경로 검증
  ├── WebSquare 빌드
  └── _wpack_ JavaScript 생성
  ▼
배포 패키지
  │ 해시·버전·Manifest
  ▼
단말배포 WEB/WAS 또는 정적 서비스
  ▼
Smoke Test / Rollback
```

- `_wpack_`은 동일 소스와 도구 버전에서 재생성 가능해야 한다.
- 엔진·공통·업무 리소스 버전을 배포 Manifest에 기록한다.
- 정적 리소스 캐시 무효화를 위해 콘텐츠 해시 또는 버전 경로를 사용한다.
- 배포 실패 시 이전 패키지로 원자적 Rollback할 수 있어야 한다.

## 8. 의존성 및 변경 통제

허용 의존 방향:

```text
screen → layout → webTop/cm → cm → websquare/runtime
```

실제 구현에서는 layout과 공통 계층의 관계가 다를 수 있으나, 특정 업무가 공통 계층에 역으로 의존성을 강요해서는 안 된다.

| 변경 영역 | 영향도 | 필수 통제 |
|---|---|---|
| `screen` | 해당 화면 중심 | 업무 리뷰·화면 테스트 |
| `layout` | 전체 정보단말 화면 | 회귀·접근성·해상도 테스트 |
| `webTop/cm` | 정보단말 전체 | 공통 소유자 리뷰·전체 회귀 |
| 기본 `cm` | 다수 애플리케이션 | 영향분석·버전 호환성 검증 |
| `websquare` | 런타임 전체 | 제품 업그레이드 계획·호환성 시험 |
| `_wpack_` | 배포 실행물 | 자동 생성·무결성 검증 |

## 9. 보안 기준

- Web Root에 Secret, DB 접속정보, 개인키를 두지 않는다.
- Source Map과 디버그 설정은 운영환경에서 제한한다.
- 허용 확장자와 MIME Type을 통제한다.
- SVG·HTML·업로드 리소스의 스크립트 삽입을 검사한다.
- 공통 JavaScript에서 DOM 입력을 출력할 때 XSS 방어를 적용한다.
- CSP, 보안 Header, 정적 리소스 무결성 정책을 적용한다.
- 엔진 및 라이브러리 버전의 취약점을 정기 점검한다.

## 10. 품질 및 테스트 기준

1. 모든 화면 XML이 문법·스키마 검증을 통과한다.
2. 경로 코드와 파일명 코드가 일치한다.
3. 화면 ID와 UDC ID가 저장소에서 중복되지 않는다.
4. 참조하는 CSS·이미지·폰트·공통함수가 존재한다.
5. Linux에서 대소문자 불일치가 발생하지 않는다.
6. 빌드 후 `_wpack_` 산출물을 원본으로 재현할 수 있다.
7. 공통 변경 시 영향받는 화면 목록과 회귀 결과가 생성된다.
8. Layout이 표준 해상도·확대·키보드 조작에서 정상 동작한다.
9. 정적 리소스 캐시 갱신과 Rollback을 검증한다.
10. Web Root에 비밀정보와 불필요한 개발 파일이 포함되지 않는다.

## 13. 최종 평가

이 패키지 구조는 엔진·공통·단말 공통·업무 화면·빌드 산출물을 분리해 변경 영향과 배포 책임을 통제하려는 표준이다. 구조 자체는 합리적이지만 실제 효과를 얻으려면 **공통 계층 소유권, 화면 코드 사전, 자동 경로 검증, 생성 산출물 통제와 공통 변경 회귀시험**이 함께 운영되어야 한다.
