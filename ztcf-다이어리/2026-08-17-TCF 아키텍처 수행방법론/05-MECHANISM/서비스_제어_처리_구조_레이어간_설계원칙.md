# 서비스 제어 처리 구조 — 레이어 간 호출·경계 설계원칙

> **문서 성격**: 첨부된 「호출 구조 정의」 아키텍처 도식을 기준으로 재구성한 상세 설계원칙  
> **적용 관점**: Application Group → Application → Function → Controller → Service → DAO → Table  
> **상태 구분**  
> - **[IMAGE-FACT]**: 이미지에서 직접 확인되는 내용  
> - **[ARCH-INTERPRETATION]**: 도식의 호출선·금지선·호출 매트릭스를 종합한 아키텍처 해석  
> - **[RECOMMENDATION]**: 구현 표준으로 명확히 하기 위해 추가한 권고사항

# 1. 문서 목적

본 문서는 첨부된 **「호출 구조 정의」** 그림을 기준으로 다음을 명확히 정의한다.

1. 애플리케이션 내부의 계층별 호출 허용 범위
2. 기능 간 호출 규칙
3. 업무공통 유틸리티 호출 규칙
4. 타 애플리케이션 호출 규칙
5. 타 애플리케이션 그룹 호출 규칙
6. Controller / Service / DAO의 역할과 책임
7. 데이터 및 Table 접근 경계
8. 직접 호출 금지 패턴
9. 설계·개발·코드리뷰 시 검증 가능한 Architecture Rule
10. 구현 단계에서 별도로 확정해야 할 미정의 사항

이 문서의 핵심은 단순히 `Controller → Service → DAO`의 3계층 구조를 설명하는 것이 아니다.

> **호출 대상이 멀어질수록 진입점을 더 상위 계층으로 제한하고, 데이터 접근은 소유 기능 내부에 가둔다.**

는 것이 이 아키텍처의 핵심이다.

---

# 2. 원본 도식의 전체 구조

## 2.1 계층적 분류

[IMAGE-FACT]

도식은 다음과 같은 계층 구조를 사용한다.

```text
Application Group
    │
    ├─ MP : 마케팅 플랫폼
    │
    │   ├─ Application CM : 캠페인
    │   │   ├─ Function A
    │   │   └─ Function B
    │   │
    │   ├─ 업무공통 유틸리티
    │   │
    │   ├─ Application CO : 공통
    │   │   └─ Function C
    │   │
    │   └─ Application MG : 메시지
    │       └─ Function D
    │
    └─ BL : BI 포털
        └─ Application CR : 신용실적
            └─ Function E
```

각 업무 Function 또는 Application 내부에는 기본적으로 다음 계층이 존재한다.

```text
Controller
    ↓
Service
    ↓
DAO
    ↓
Table
```

단, **업무공통 유틸리티는 외부에서 접근할 때 Controller를 거치지 않고 Service가 공식 진입점**으로 표현되어 있다.

---

# 3. 이 그림을 읽는 가장 중요한 방법

## 3.1 하단 호출 매트릭스의 의미

[ARCH-INTERPRETATION]

하단 표는 단순한 계층 정의표가 아니라:

> **“현재 호출 주체의 Layer가 대상 영역의 어느 Layer까지 직접 진입할 수 있는가?”**

를 정의한 **호출 허용 매트릭스**로 읽어야 한다.

즉 아래와 같은 의미이다.

```text
호출 주체
Controller / Service / DAO

        ↓

피호출 대상의 경계
① 기능 내
② 타 기능
③ 업무공통 유틸리티
④ 타 애플리케이션
⑤ 타 애플리케이션 그룹
```

중요한 점은 다음과 같다.

> 이 표는 **대상 컴포넌트의 내부 실행 체인**을 금지하는 표가 아니다.

예를 들어:

```text
다른 Application Controller에 진입
        ↓
대상 Application 내부에서는
Controller → Service → DAO → DB
```

의 내부 흐름은 정상이다.

표가 금지하는 것은:

```text
Source Controller → Target Service 직접 호출
Source Controller → Target DAO 직접 호출
```

처럼 **대상 경계를 건너뛰는 직접 진입**이다.

---

# 4. 호출 경계 5단계

원본 그림의 번호 ①~⑤를 구조적으로 정리하면 다음과 같다.

| 번호 | 경계 | 예시 | 공식 진입 계층 |
|---:|---|---|---|
| **1** | 기능 내 | Function A 내부 | `Service` |
| **2** | 타 기능 | Function A → Function B | `Service` |
| **3** | 업무공통 유틸리티 | Function → Utility | `Service` |
| **4** | 타 애플리케이션 | CM → CO / MG | `Controller` |
| **5** | 타 애플리케이션 그룹 | MP → BL | `Controller` |

이를 한 줄로 요약하면 다음과 같다.

```text
경계가 작음
   │
   │  기능 내
   │      → Service
   │
   │  타 기능
   │      → Service
   │
   │  공통 Utility
   │      → Service
   │
   │  타 Application
   │      → Controller
   │
   │  타 Application Group
   │      → Controller
   ▼
경계가 큼
```

즉:

> **Application 경계를 넘는 순간 Service 직접 호출을 금지하고 Controller/API 경계로 되돌아간다.**

# 5. 원본 호출 허용 매트릭스

[IMAGE-FACT]

원본 하단 표를 그대로 논리화하면 다음과 같다.

## 5.1 Controller가 호출 주체인 경우

| 피호출 영역 | Controller | Service | DAO | 판정 |
|---|:---:|:---:|:---:|---|
| **① 기능 내** | X | **O** | X | Service만 직접 호출 |
| **② 타 기능** | X | **O** | X | 타 기능 Service 직접 호출 허용 |
| **③ 업무공통 유틸리티** | - | **O** | X | Utility Service만 호출 |
| **④ 타 애플리케이션** | **O** | X | X | 대상 Controller만 호출 |
| **⑤ 타 애플리케이션 그룹** | **O** | X | X | 대상 Controller만 호출 |

핵심:

```text
Controller
   ├─ 같은 기능 Service              O
   ├─ 다른 기능 Service              O
   ├─ 업무공통 Utility Service       O
   ├─ 다른 Application Controller    O
   └─ 다른 Group Controller          O
```

그 외 직접 호출은 금지한다.

---

## 5.2 Service가 호출 주체인 경우

| 피호출 영역 | Controller | Service | DAO | 판정 |
|---|:---:|:---:|:---:|---|
| **① 기능 내** | X | X | **O** | 같은 기능 DAO만 허용 |
| **② 타 기능** | X | X | X | 직접 호출 전부 금지 |
| **③ 업무공통 유틸리티** | - | X | X | 직접 호출 금지 |
| **④ 타 애플리케이션** | X | X | X | 직접 호출 금지 |
| **⑤ 타 애플리케이션 그룹** | X | X | X | 직접 호출 금지 |

핵심:

```text
Service
   └─ 같은 기능 DAO   O

나머지는 모두 X
```

따라서 이 구조에서 Service는 **업무 간 Orchestrator가 아니라 자기 기능 내부의 업무처리 계층**으로 제한된다.

---

## 5.3 DAO가 호출 주체인 경우

| 피호출 영역 | Controller | Service | DAO | 판정 |
|---|:---:|:---:|:---:|---|
| **① 기능 내** | X | X | X | 상위/동급 Layer 호출 금지 |
| **② 타 기능** | X | X | X | 전부 금지 |
| **③ 업무공통 유틸리티** | - | X | X | 전부 금지 |
| **④ 타 애플리케이션** | X | X | X | 전부 금지 |
| **⑤ 타 애플리케이션 그룹** | X | X | X | 전부 금지 |

DAO는 사실상 **최종 Data Access Leaf Layer**이다.

```text
DAO
   ↓
자기 기능이 소유한 Table

DAO
   ├─ Controller 호출 X
   ├─ Service 호출    X
   ├─ 다른 DAO 호출  X
   ├─ 타 기능 호출   X
   ├─ 타 App 호출    X
   └─ 타 Group 호출  X
```

# 6. 전체 핵심 설계원칙

## 원칙 1. 호출은 항상 “허용된 공식 진입점”으로만 들어간다

[ARCH-INTERPRETATION]

호출 대상의 경계에 따라 공식 진입계층을 고정한다.

```text
기능 내부/타 기능/Utility
        ↓
     Service

Application 경계 이상
        ↓
    Controller
```

즉 모든 Layer를 서로 호출 가능한 객체로 보지 않는다.

각 Layer는 **경계별 Entry Point** 역할을 가진다.

---

## 원칙 2. Controller는 호출 조정 계층이다

원본 그림에서는 Controller가 가장 많은 외부 호출 권한을 가진다.

Controller가 수행할 수 있는 호출은:

```text
Controller
   ├─ 기능 내 Service
   ├─ 타 기능 Service
   ├─ 공통 Utility Service
   ├─ 타 Application Controller
   └─ 타 Application Group Controller
```

이다.

따라서 이 구조에서 Controller는 단순 HTTP Parameter Binding 역할에만 머물지 않는다.

[ARCH-INTERPRETATION]

> **Controller는 기능 내부 및 외부 경계를 연결하는 호출 제어·진입 조정 Layer**이다.

---

## 원칙 3. Service는 자기 기능의 Business Execution Layer이다

Service가 외부의 다른 Service를 호출하는 구조는 금지되어 있다.

```text
Service A → Service B       X
Service A → Utility Service X
Service A → 타 App Service  X
```

Service가 허용받는 직접 하향호출은:

```text
Service → same Function DAO
```

뿐이다.

따라서 Service의 책임은 다음과 같이 한정된다.

- 자기 기능의 업무 로직
- 자기 기능의 입력 검증
- 자기 기능의 처리 규칙
- 자기 기능의 DAO 호출
- 자기 기능 데이터 처리

그리고 다음 책임은 가지지 않는다.

- 타 기능 업무 조정
- 타 Application 호출
- 타 Group 호출
- 공통 Utility 호출 조정
- 타 기능 DAO 접근

---

## 원칙 4. Service 간 직접 연결을 금지한다

[IMAGE-FACT]

같은 Function 안에서도 `Service → Service`는 X로 표시되어 있다.

즉 다음 패턴이 금지된다.

```text
Service A
   ↓
Service B
```

호출 체인이 다음처럼 늘어나는 것을 방지하는 목적의 구조로 해석된다.

```text
Service A
   ↓
Service B
   ↓
Service C
   ↓
Service D
```

[ARCH-INTERPRETATION]

이 구조는 Service Dependency Graph가 복잡하게 얽히는 것을 원천적으로 차단한다.

---

## 원칙 5. DAO는 데이터 접근 전용 계층이다

DAO는 어떤 상위 Layer도 호출하지 않는다.

```text
DAO → Service       X
DAO → Controller    X
DAO → DAO           X
```

DAO는 자신의 SQL / Mapper / Table 접근만 책임져야 한다.

이를 구조적으로 표현하면:

```text
Business Flow
    ↓
Service
    ↓
DAO
    ↓
Table

데이터 흐름은 여기서 종료
```

이다.

---

## 원칙 6. DAO를 공유하지 않는다

다른 기능 또는 다른 Application에서 DAO를 직접 호출하는 것은 모두 금지이다.

```text
Function A Service
        ↓
Function B DAO       X

Application CM
        ↓
Application CO DAO   X

MP Group
        ↓
BL Group DAO         X
```

즉 DAO는 **공유 서비스가 아니다.**

DAO 재사용보다 **데이터 소유권과 업무 경계 유지**를 우선한다.

---

## 원칙 7. Table도 기능/애플리케이션 소유 경계를 가진다

[IMAGE-FACT]

상단 도식의 파란색 정상경로는 각 기능의 DAO가 자기 영역의 Table로 내려간다.

반면 기능 또는 Application 경계를 가로질러 다른 Table에 직접 접근하려는 선은 X로 표시되어 있다.

예시:

```text
Function A DAO
    ↓
TB_MPCMA*          O

Function A DAO
    ↓
Function B Table   X
```

따라서 핵심은:

> **타 기능의 데이터를 사용하려면 그 기능의 공식 Service/API를 통해야 하며, Table을 공유경로로 사용하지 않는다.**

# 7. 경계별 상세 설계원칙

# 7.1 ① 기능 내 호출

## 허용 구조

```text
Controller
    ↓
Service
    ↓
DAO
    ↓
Function-owned Table
```

하나의 Function 안에 복수 Controller Method, Service, DAO가 있을 수 있으며, 원본 그림의 파란 교차선은 다음을 의미한다.

```text
Controller Method A
   ├─ Service 1
   └─ Service 2

Controller Method B
   ├─ Service 1
   └─ Service 2
```

또한:

```text
Service 1
   ├─ DAO 1
   └─ DAO 2

Service 2
   ├─ DAO 1
   └─ DAO 2
```

형태의 동일 기능 내부 조합은 허용되는 것으로 표현되어 있다.

단:

```text
Controller → DAO
Service    → Service
DAO        → Service
DAO        → DAO
```

는 금지이다.

---

# 7.2 ② 타 기능 호출

예:

```text
CM Application

Function A
    │
    │ Controller
    ▼
Function B Service
```

## 허용

```text
Function A Controller
        ↓
Function B Service
```

## 금지

```text
Function A Service
        ↓
Function B Service        X

Function A Service
        ↓
Function B DAO            X

Function A Controller
        ↓
Function B DAO            X

Function A DAO
        ↓
Function B DAO            X
```

핵심은:

> **같은 Application 내부의 Function 간 조정 책임은 Controller에 있다.**

---

# 7.3 ③ 업무공통 유틸리티 호출

원본에서 업무공통 유틸리티는 독립 `Utility Service`를 공식 진입점으로 사용한다.

## 허용

```text
Business Controller
        ↓
Utility Service
```

Utility 내부는:

```text
Utility Service
        ↓
Utility DAO
        ↓
Utility-owned Table
```

형태로 동작한다.

## 금지

```text
Business Controller → Utility DAO    X
Business Service    → Utility Service X
Business Service    → Utility DAO     X
Business DAO        → Utility Service X
```

즉 Utility는 어디에서나 호출하는 무제한 Helper가 아니다.

> **Controller에서만 접근할 수 있는 관리된 공통 기능 경계**이다.

---

# 7.4 ④ 타 애플리케이션 호출

예:

```text
MP Group

CM Application
        ↓
CO Application
```

또는:

```text
CM Application
        ↓
MG Application
```

## 허용

```text
Source Controller
       ↓
Target Controller
       ↓
Target Service
       ↓
Target DAO
       ↓
Target Table
```

## 금지

```text
Source Controller → Target Service X
Source Controller → Target DAO     X
Source Service    → Target Controller X
Source Service    → Target Service    X
Source DAO        → Target DAO        X
```

핵심:

> **Application 경계는 Controller 경계로 보호한다.**

---

# 7.5 ⑤ 타 애플리케이션 그룹 호출

예:

```text
MP Group
   ↓
BL Group
```

## 허용

```text
MP Controller
      ↓
BL Controller
      ↓
BL Service
      ↓
BL DAO
      ↓
BL Table
```

## 금지

```text
MP Controller → BL Service  X
MP Controller → BL DAO      X
MP Service    → BL Service  X
MP Service    → BL DAO      X
MP DAO        → BL DAO      X
MP DAO        → BL Table    X
```

가장 큰 경계이므로 가장 엄격하게 공식 진입점을 제한한다.

# 8. 경계 크기에 따른 호출정책

이 구조를 하나의 정책으로 일반화하면 다음과 같다.

```text

Controller
   ↓
Service
   ↓
DAO
   ↓
Table


[같은 Application의 다른 Function]
Controller
   ↓
Target Function Service
   ↓
Target DAO
   ↓
Target Table


[업무공통 Utility]
Controller
   ↓
Utility Service
   ↓
Utility DAO
   ↓
Utility Table


[다른 Application]
Controller
   ↓
Target Controller
   ↓
Target Service
   ↓
Target DAO
   ↓
Target Table


[다른 Application Group]
Controller
   ↓
Target Group Controller
   ↓
Target Service
   ↓
Target DAO
   ↓
Target Table
```

# 9. 핵심 Boundary Principle

## 9.1 Function Boundary

```text
Function A
   │
   │ 직접 진입 가능
   ▼
Function B Service
```

Function은 같은 Application 내부이므로 Controller가 Target Service에 직접 진입할 수 있다.

---

## 9.2 Application Boundary

```text
Application A
   │
   │ Service 직접 진입 금지
   ▼
Application B Controller
```

Application 경계는 반드시 대상 Controller에서 시작한다.

---

## 9.3 Application Group Boundary

```text
Group A
   │
   │ 내부 Layer 직접 접근 금지
   ▼
Group B Controller
```

Group 경계는 Application 경계보다 더 강한 격리경계로 본다.

---

## 9.4 Data Boundary

```text
업무경계
   ↓
Service/API를 통해 접근

DB/Table
   ↓
직접 공유 금지
```

즉 데이터 공유가 필요하다고 해서 DAO/Table을 공유 경로로 사용하지 않는다.

# 13. 데이터 소유권 설계원칙

원본 그림의 Table 배치를 기준으로 보면 데이터는 Function/Application별 소유영역으로 나뉜다.

예시:

```text
Function A
    ↓
TB_MPCMA*

Function B
    ↓
TB_MPCMB*

Common Utility
    ↓
TB_MPCOC*

Application CO
    ↓
TB_MPCOC*

Application MG
    ↓
TB_MPMGD*

Application CR
    ↓
TB_BLCRE*
```

※ 실제 Table Prefix의 정확한 소유정책은 별도 데이터 표준에서 확정해야 한다.

핵심 원칙은 다음과 같다.

1. Table은 자유롭게 공유하는 공용 자원이 아니다.
2. Table 접근은 소유 DAO를 통해서만 수행한다.
3. 타 기능의 데이터를 필요로 하면 타 기능의 Service 경계를 이용한다.
4. 타 Application의 데이터를 필요로 하면 Application의 공식 진입점을 이용한다.
5. 타 Group의 데이터는 Group 공개 인터페이스를 통해 접근한다.

# 18. “Controller → Controller”의 구현 해석 주의

[IMAGE-FACT]

원본 그림은 타 Application 및 타 Application Group 호출 시 **Controller → Controller**를 허용 패턴으로 표시한다.

그러나 그림 자체만으로는 이것이 다음 중 무엇인지 명시되지 않는다.

1. 동일 JVM 안의 Java Controller Bean 직접 메서드 호출
2. HTTP/API 호출
3. 내부 Service Gateway
4. Framework Dispatcher를 통한 논리적 Controller 진입
5. 기타 RPC/Integration 메커니즘

따라서 구현표준에서는 이를 단순 Java 객체 호출로 확정하면 안 된다.

[RECOMMENDATION]

가장 안전한 표준화 표현은 다음과 같다.

> **“타 Application 또는 타 Application Group 호출은 대상 Application의 공식 Inbound Entry Point(Controller/API)를 통해 진입한다.”**

즉 설계문서에는:

```text
Source Controller
       ↓
Target Public Entry
(Controller / API)
       ↓
Target Service
```

로 표현하는 것을 권장한다.

---

# 19. Transaction / Timeout / Exception 관점에서의 주의사항

첨부된 그림만으로는 다음 항목은 정의되어 있지 않다.

- Transaction 시작 위치
- Transaction 전파정책
- Timeout 위치
- 예외 변환 위치
- Retry 정책
- Circuit Breaker
- 동기/비동기 여부
- 원격호출 Protocol
- 인증/인가
- Logging/Trace
- ServiceId

따라서 이 문서에서는 이를 확정하지 않는다.

다만 호출 경계가 정해졌으므로 향후 별도 표준은 다음 경계와 맞춰 정의해야 한다.

```text
Function Boundary
Application Boundary
Application Group Boundary
```

특히 Application 또는 Group을 넘는 호출은 **동일 Local Method 호출과 동일한 Transaction으로 간주해서는 안 되는지 여부를 별도 ADR로 확정**해야 한다.

# 24. 아키텍처적 의미

[ARCH-INTERPRETATION]

이 구조는 일반적인 단순 3-Tier보다 **호출 통제(Call Governance)**에 더 초점을 둔 구조다.

핵심 통제축은 다음 세 가지이다.

```text
① Layer Control
Controller / Service / DAO 역할 제한

② Boundary Control
Function / Application / Group 경계별 진입점 제한

③ Data Ownership Control
DAO / Table 직접 공유 금지
```

이를 통해 기대하는 효과는 다음과 같다.

- 기능 간 의존성 감소
- Application 내부구조 은닉
- DAO 공유 방지
- Table 직접공유 방지
- 호출경로 예측 가능성 향상
- 영향도 분석 단순화
- 장애 범위 식별 용이
- 코드리뷰 자동화 가능
- Architecture Conformance Rule로 전환 가능

# 26. 최종 설계원칙

본 서비스 제어 처리 구조의 최종 원칙은 다음과 같이 정리한다.

> **기능 내부에서는 Controller → Service → DAO의 단방향 호출을 유지한다.**

> **같은 Application의 타 기능은 Controller가 대상 Service를 호출한다.**

> **업무공통 유틸리티는 Controller가 Utility Service를 호출한다.**

> **Application 경계를 넘으면 대상 Application의 공식 Controller/API Entry로 다시 진입한다.**

> **Application Group 경계를 넘을 때도 동일하게 공식 Entry를 통한다.**

> **Service는 다른 Service를 호출하지 않으며 자기 기능 DAO만 사용한다.**

> **DAO는 최종 Data Access Layer이며 다른 Layer 또는 다른 DAO를 호출하지 않는다.**

> **데이터는 소유 Function/Application의 DAO를 통해서만 접근하고, 타 업무의 Table을 직접 공유하지 않는다.**

이 원칙을 지키면 전체 호출흐름은 다음 공식으로 정리된다.

```text
Function 내부
Controller → Service → DAO → Table

Function 간
Controller → Target Service → Target DAO → Target Table

공통 Utility
Controller → Utility Service → Utility DAO → Utility Table

Application 간
Controller → Target Controller/API
           → Target Service
           → Target DAO
           → Target Table

Application Group 간
Controller → Target Group Controller/API
           → Target Service
           → Target DAO
           → Target Table
```

# 27. 문서 적용 상태

본 문서는 첨부 이미지에 직접 표현된 호출 허용/금지 구조를 우선 반영하였다.

특히 다음 내용은 **이미지 기반 확정사항**으로 취급할 수 있다.

- Controller → 기능 내 Service 허용
- Controller → 타 기능 Service 허용
- Controller → 공통 Utility Service 허용
- Controller → 타 Application Controller 허용
- Controller → 타 Application Group Controller 허용
- Service → 기능 내 DAO 허용
- Controller → DAO 금지
- Service → Service 금지
- Service → 타 기능/타 Application/타 Group 직접 호출 금지
- DAO → 다른 Layer 호출 금지
- 타 영역 DAO/Table 직접 접근 금지

반면 다음은 **이미지만으로 확정할 수 없다.**

- 원격호출 Protocol
- Controller→Controller의 실제 기술 구현
- Transaction/Timeout/Error/Retry
- 인증/인가
- ServiceId
- DTO/전문 계약
- Runtime/운영통제

따라서 후속 설계에서는 이 호출구조를 **Application Architecture Baseline**으로 두고,
`ServiceId / Standard Message / Transaction / Timeout / Error / Logging / Security`
설계와 연결하는 방식이 적절하다.
