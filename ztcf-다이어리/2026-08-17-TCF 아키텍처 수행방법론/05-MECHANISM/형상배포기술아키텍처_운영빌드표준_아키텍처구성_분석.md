# 형상배포기술아키텍처 — 운영 빌드 배포 표준 아키텍처 구성 분석

## 1. 분석 개요

첨부 장표의 **운영 빌드 배포 표준 아키텍처 구성**을 기준으로, **로컬 PC → GitLab(형상) → Jenkins(CI/CD) → Nexus → IaaS(운영서버·컨테이너·Backing)** 로 이어지는 **운영 관점의 표준 빌드·배포 흐름**을 분석한다.

장표 상단 요약은 개발 표준과 동일하게 다음 두 축이다.

- **개발**: GitLab Feature Branch 생성·Checkout 후, 완료 시 GitLab Push.
- **배포**: 베이스 브랜치(`dev`, `master`) 병합 기준 → Jenkins Pipeline → **TAS 환경 컨테이너 서비스** 배포.

[`형상배포기술아키텍처_개발빌드표준_아키텍처구성_분석.md`](./형상배포기술아키텍처_개발빌드표준_아키텍처구성_분석.md)와 **단계 ①~⑥·5레인·Pipeline 3단이 동형**이다. 본 문서는 동일 흐름을 **운영서버(IaaS) 착지·운영 통제** 관점으로 해석·보강한다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. 개발/운영 장표의 도식 차이(승인·CAB·롤백 박스 등)가 시각적으로 거의 없다면, **제목·적용 범위(운영)** 로 구분된 쌍 표준으로 본다. `master`→PRD 전용 Job, 변경관리(ITSM/eCAMS), 롤백 Evidence는 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **운영 표준 = 동일 파이프의 운영 착지 규약**: 도구·단계 구조는 개발 표준과 같고, 착지 레인이 **IaaS(운영서버)** 로 명시된다.
- **5열 구성 유지**: 로컬 PC · GitLab · Jenkins · Nexus · IaaS(운영서버).
- **Feature → 베이스 병합 후 Deploy**: 운영에서도 로컬 직접 배포가 아니라 **원격 B(`dev`/`master`) 병합 → Pipeline** 이 전제다.
- **Pipeline 3단 불변**: Build → Test → Deploy. Nexus Maven이 Build에 Dependencies를 공급한다.
- **운영 완료 조건**: Deploy 후 **컨테이너 생성 + Backing 서비스 결합** 까지가 장표상 종료점이다.
- **베이스 브랜치가 환경 스위치**: 장표는 `dev`·`master`를 함께 적시하므로, **운영 표준의 핵심 통제는 어느 베이스가 어느 TAS/운영 공간에 매핑되는지**다.
- **개발 표준과의 관계**: 개발 표준이 “어떻게 빌드·배포하는가”의 절차도라면, 운영 표준은 같은 절차를 **운영서버·가용성·변경 추적**에 묶은 적용본으로 읽는다.

## 3. 장표 구성요소 전사

### 3.1 상단 요약 문장

| 구분 | 장표 요지 | 운영 해석 |
|---|---|---|
| 개발 | Feature → Checkout → Push | 운영 반영 전에도 동일 Feature 규율 |
| 배포 | `dev`/`master` → Jenkins → TAS 컨테이너 | **운영서버** 컨테이너·Backing까지 포함 |

### 3.2 수직 레인(도구)

| 레인 | 표기 | 역할(해석) | 운영 가중치 |
|---|---|---|---|
| 로컬 PC | 로컬 PC | 개발·커밋 | 운영 자격·직접 Deploy 금지 |
| 형상 관리 | GitLab | 이슈·브랜치·병합 | Protected branch · 승인 |
| CI/CD | Jenkins | Build/Test/Deploy | 운영 Job·시크릿·감사 로그 |
| 라이브러리 저장소 | Nexus | Maven Dependencies | 승인 라이브러리·취약점 |
| IaaS | **운영서버** | 컨테이너 · Backing 결합 | 본 표준의 착지점 |

### 3.3 단계 ①~⑥ (개발 표준과 동형)

| # | 행위 | 위치 | 결과 상태(장표) |
|---|---|---|---|
| ① | 브랜치 생성 | GitLab | 원격 저장소 A (이슈 선행) |
| ② | git clone/checkout | GitLab → 로컬 | 로컬 저장소 A |
| ③ | git commit | 로컬 PC | 로컬 저장소 A' |
| ④ | git push | 로컬 → GitLab | 원격 저장소 A' |
| ⑤ | 코드 병합 | GitLab | 원격 저장소 B (`dev`/`master`) |
| ⑥ | Pipeline 실행 | GitLab → Jenkins | CI/CD 접속 · Pipeline 기동 |

### 3.4 Pipeline · 운영 착지

| 단계 | 표기 | 연계 | 운영 의미 |
|---|---|---|---|
| Build | Build | Nexus → Dependencies | 재현 빌드 |
| Test | Test | — | 운영 전 품질 게이트 |
| Deploy | Deploy | → IaaS | **운영서버** 반영 |
| 컨테이너 생성 | 컨테이너 생성 | TAS | 서비스 인스턴스 |
| Backing 결합 | Backing 서비스 결합 | Data Store 등 | 운영 의존성 연결 완료 |

```text
[로컬 PC]          [형상관리 GitLab]       [CI/CD Jenkins]        [Nexus]        [IaaS = 운영서버]
    │                    │                       │                    │               │
    │              이슈 생성                     │                    │               │
    │              ① 브랜치 생성 / 원격 A        │                    │               │
    │◀── ② clone/checkout ─┘                     │                    │               │
 ③ commit (로컬 A')     │                       │                    │               │
    └── ④ push ─────────▶│ 원격 A'               │                    │               │
                         │ ⑤ 병합 → 원격 B       │                    │               │
                         │    (dev / master)     │                    │               │
                         └── ⑥ Pipeline ────────▶│ Build ◀── deps ────┤ Maven         │
                                                 │ Test               │               │
                                                 │ Deploy ───────────────────────────▶│ 컨테이너 생성
                                                 │                                    │ Backing 서비스 결합
                                                 │                                    │ ※ 운영 착지 완료
```

## 5. 개발 표준 vs 운영 표준

| 항목 | 개발 빌드 표준 | 운영 빌드 표준(본 장표) |
|---|---|---|
| 도식 골격 | 5레인 · ①~⑥ · Build/Test/Deploy | **동형** |
| IaaS 표기 | 운영서버(동일 계열) | **운영서버**를 표준 제목과 결합해 강조 |
| 베이스 브랜치 | `dev`, `master` | 동일. **운영은 보통 `master`(또는 release) 가중** |
| 통제 초점 | 절차·재현성 | 절차 + **변경승인·롤백·Backing·감사** |
| 실패 영향 | 개발/검증 환경 | **대고객·대내 업무 중단** |

> 장표 픽셀 단위로 개발본과 거의 같다면, 문서는 **쌍 표준(개발/운영)** 으로 관리하고, 차이 규칙(승인·환경 매핑·롤백)은 운영 런북·CI/CD Evidence로 보완한다.

## 6. 인터페이스 · 흐름 매핑

| # | 출발 | 행위 | 도착 | 운영 설계 의미 |
|---|---|---|---|---|
| 1 | 개발자 | 이슈·브랜치 | GitLab 원격 A | 변경 추적 ID |
| 2~4 | 로컬 ↔ GitLab | clone/commit/push | 원격 A' | Feature만 갱신 |
| 5 | 원격 A' | 코드 병합 | 원격 B | 운영 후보 코드 고정 |
| 6 | GitLab | Pipeline 실행 | Jenkins | 자동 운영 배포 기동 |
| 7 | Nexus | Dependencies | Build | 승인 의존성 |
| 8 | Jenkins | Deploy | IaaS 운영서버 | 컨테이너 서비스 |
| 9 | 컨테이너 | Backing 결합 | Backing Service | 운영 의존 연결 |

### 6.1 운영에서 특히 읽히는 의도

1. **운영 반영의 유일한 문은 Pipeline Deploy** 이다.
2. **병합(⑤) 이전에는 운영에 닿지 않는다.**
3. **Test는 운영 Deploy의 전제**로 순서상 고정된다.
4. **Backing 미결합 = 배포 미완료**로 취급한다.
5. `dev`와 `master`를 한 장표에 둔 것은 **환경 매핑 표를 별도 필수**로 만든다.

## 7. 주요 처리 흐름 (운영 관점)

### 7.1 Feature 개발 (운영 반영 전)

```text
이슈 → ① 브랜치(원격 A) → ② checkout → ③ commit → ④ push(원격 A')
```

- 운영 표준에서도 개발 절차는 동일하다. 차이는 **이후 병합 승인 강도**.

### 7.2 운영 후보 확정 · Pipeline

```text
원격 A' → ⑤ 병합(원격 B: 주로 master 또는 승인된 release)
       → ⑥ Pipeline
       → Build ← Nexus
       → Test (실패 시 중단)
       → Deploy → 운영서버 컨테이너
       → Backing 서비스 결합
```

- `dev` 병합 Pipeline과 `master` 병합 Pipeline을 **Job·대상 TAS 공간·승인자**로 분리하는 것이 운영 표준의 실무 핵심이다.
- 장표에 승인 박스가 없어도, 운영에서는 **병합 전 CAB/ITSM·병합 후 배포 승인**을 권고한다.

### 7.3 운영 완료 · 롤백 전제

```text
배포 성공 = 컨테이너 Ready + Backing Bound + (권고) Smoke OK
롤백 = 직전 컨테이너 버전/이미지 재Deploy + Backing 호환 확인
```

- Nexus에 이미지/아티팩트 publish가 장표에 없으므로, **롤백 원천**(이전 태그)을 CI/CD 문서에서 확정한다.

## 8. 운영 형상배포 설계 원칙

1. **운영서버 변경은 Jenkins Deploy만** 허용한다.
2. **`master`(또는 지정 release) Protected branch** 없이 운영 Deploy를 열지 않는다.
3. **Test 실패 시 Deploy 금지**.
4. **Build는 Nexus Maven Dependencies**만 사용한다.
5. **배포 완료 = 컨테이너 + Backing 결합** (+ 스모크).
6. **`dev` Pipeline과 운영 Pipeline을 분리**하고 매핑표를 공개한다.
7. 로컬 PC·개발자 계정에 **운영 TAS 배포 자격을 부여하지 않는다.**
8. 개발 빌드 표준·통합개발환경·본 운영 표준의 **도구·단계 용어를 일치**시킨다.

## 9. 레인별 운영 특성

| 레인 | 장점 | 운영 위험 | 통제 |
|---|---|---|---|
| 로컬 PC | 빠른 수정 | 핫픽스 우회 배포 | 자격 차단·감사 |
| GitLab | 이력·병합 | 강제 머지 | Protected · 2인 승인 |
| Jenkins | 자동 Deploy | 잘못된 Job 실행 | Job RBAC·환경 분리 |
| Nexus | 재현 빌드 | 취약 라이브러리 | 스캔·허용 목록 |
| IaaS 운영서버 | 컨테이너·Backing | 장애·설정 드리프트 | 헬스·롤백·관측 |

## 10. 품질·위험과 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| 개발/운영 장표 동형으로 혼동 | 잘못된 환경 배포 | 브랜치→환경→Job 매핑표 |
| `dev`가 운영에 직결 | 미성숙 코드 착지 | `master`/release만 PRD |
| Test 스킵 | 운영 장애 | 게이트 필수·우회 감사 |
| Backing 결합 누락 | 기동 실패·부분 장애 | Deploy 후 자동 검증 |
| 롤백 원천 부재 | MTTR 증가 | 이미지 태그·보관·재Deploy 런북 |
| 시크릿 평문 | 유출 | Vault/자격증명 바인딩 |
| 변경관리 미연동 | 감사 부적합 | ITSM/eCAMS 티켓↔Pipeline ID |

## 11. 점검 체크리스트

- [ ] 본 장표가 **운영서버(TAS)** Deploy Job과 1:1로 연결되어 있는가?
- [ ] `dev`/`master` 각각 대상 환경이 문서화되어 있는가?
- [ ] 운영 병합에 Protected branch·승인자가 있는가?
- [ ] Build→Test→Deploy이며 Test 실패 시 운영 Deploy가 막는가?
- [ ] Nexus Dependencies·취약점 정책이 운영 Build에 적용되는가?
- [ ] 컨테이너 Ready + Backing Bound Evidence가 Pipeline에 남는가?
- [ ] 롤백 절차·이전 버전 재배포가 검증되었는가?
- [ ] 개발 빌드 표준·통합개발환경·`23-CI-CD-DEPLOYMENT`와 용어가 정합하는가?

## 12. 종합 평가

운영 빌드 배포 표준은 개발 표준과 **같은 5레인·①~⑥·Build/Test/Deploy** 골격을 유지한 채, 착지를 **IaaS 운영서버의 컨테이너·Backing 결합**으로 못 박은 형상배포 아키텍처다. 도식이 동형인 만큼, 운영 품질은 그림 자체가 아니라 **브랜치-환경 매핑, 승인, Test 게이트, Backing 검증, 롤백·감사**에서 갈린다.

개발 빌드 표준과 **쌍으로 관리**하고, 통합개발환경·CI/CD 산출물과 함께 읽어야 운영 E2E 배포가 닫힌다.
