# 메커니즘 — 통합개발환경 시스템 연계 구조 분석

## 1. 분석 개요

첨부 장표의 **통합 개발 환경 표준 아키텍처 구성**을 기준으로, **NEXT 통합개발환경**(IaaS·DevOps 기반)에서 **런타임 플랫폼 ↔ 외부지원 ↔ 개발·배포 파이프** 사이의 **시스템 연계 경계·프로토콜·산출물 흐름**을 분석한다.

장표는 상단에 **단말 접속 · UI 서비스 플랫폼 · 어플리케이션 서비스 플랫폼(정보계 차세대) · Backing Service · 외부지원**, 하단에 **Developer IDE · 버전관리(Git) · 배포관리(Pipe) · Nexus Repository** 로 나뉜다. 부제는 아키텍처 일관성을 위해 **IaaS DevOps 기반 개발환경**을 NEXT 통합개발환경으로 구성한다는 취지다.

온라인 프레임워크·선도개발 레이어드·CI/CD 산출물과 맞물려, 본 장표는 **개발→빌드→배포→런타임→대내외 연계**를 한 그림에 묶은 **메커니즘 축약도**다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. Git/Pipe 제품명(GitLab·Jenkins 등), 환경(DEV/STG/PRD) 분리, 단말소스 배포 매체, IMDG 제품, MFT·FOS 계약 세부는 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **런타임과 DevOps가 동일 장표에 공존**: 운영 플랫폼(UI·App·Backing·외부지원)과 개발·배포(IDE·Git·Pipe·Nexus)를 **한 표준 구성**으로 본다.
- **UI / App 플랫폼 이원화**: Front(단말관리·단말배포)와 Backend(Service A/B/C + Application Framework)를 분리하고, 둘 다 **WAS · VM · IaaS** 위에 둔다.
- **접속 경로 표준화**: 단말 → **인증 관리** → **L4** → UI 서비스 플랫폼.
- **백엔드는 정보계 차세대 영역**: WEB · IMDG · Application Framework를 포함한 백엔드 묶음이 차세대 핵심이다.
- **외부 연계는 매체별 분리**: HTTP→Cruz APIM(계정계/정보계), MFT→파일공유(대외 MCA·대외계), FOS→오브젝트 스토리지, 메타→IT 메타.
- **배포 파이프가 양 플랫폼에 deploy**: Git commit/merge → Pipe(trig) → Build/Deploy → UI·App 플랫폼.
- **Nexus가 의존성·산출물 허브**: Pipe와 **dependency/publish**, Backend IDE와 **dependency**로 연결된다.
- **IT 메타가 개발 생산성에 직접 연결**: Backend IDE(및 메타용어 경로)로 **메타용어**를 공급한다.

| 2 | UI 플랫폼 | (내부/호출) | — | App 서비스 플랫폼 | Front→Backend 업무 호출 |

| 12 | UI 플랫폼 | 단말소스 배포 | — | 단말 | 클라이언트 산출물 배포 |

### 5.1 매핑에서 읽히는 설계 의도

1. **런타임 연계(HTTP/MFT/FOS/connection)** 와 **개발 연계(Git/Pipe/Nexus/메타용어)** 를 계층으로 분리한다.
2. **UI와 App을 별도 배포 단위**로 두어 Front·Backend 릴리즈를 독립시킬 수 있다.
3. 대내 API는 **APIM**, 대외·파일은 **MFT**, 객체는 **FOS** 로 매체 표준을 맞춘다.
4. Nexus를 중심에 둬 **빌드 재현성·공통 라이브러리 통제**를 강화한다.
5. IT 메타를 IDE에 붙여 **런타임 거버넌스와 개발 산출물의 용어 정합**을 맞춘다.

## 6. 주요 처리 흐름

### 6.1 단말 → UI → App (런타임 요청)

```text
단말
  → 인증 관리
  → L4
  → UI 서비스 플랫폼 (Front / WAS)
  → 어플리케이션 서비스 플랫폼 (WEB · App FWK · Service)
  → Data Store / Cruz APIM / MFT / FOS (필요 시)
  → 응답
```

- 인증 실패·L4 장애·WAS 장애의 영향 범위를 UI/App별로 분리 관측한다.
- App Framework 선·후처리·GUID 등 온라인 메커니즘과 정합시킨다.

### 6.2 대내 HTTP (Cruz APIM)

```text
Backend Application
  → HTTP
  → Cruz APIM
  → 계정계 / 정보계
```

- Product·쿼터·타임아웃·감사는 APIM 정책으로 일원화한다.
- 정보계 내부 호출과 계정계 호출을 동일 APIM이라도 **정책 세트**로 나눈다.

### 6.3 MFT · FOS · Data Store

```text
Backend
  ├── connection → Data Store
  ├── MFT → 파일공유 → 대외 MCA / 대외계
  └── FOS → 오브젝트 스토리지
```

- MFT와 FOS를 혼용하지 않도록 **파일 성격(전송 vs 객체보관)** 을 계약으로 고정한다.
- Data Store 직접 connection은 커넥션 풀·타임아웃·Statement cancel 등 프레임워크 표준을 따른다.

### 6.4 개발 → Git → Pipe → Deploy

```text
UI IDE / Backend IDE
  → Merge/Commit
  → Git (Configuration Management)
  → trig
  → Pipe (Build)
  → Nexus publish / dependency 해소
  → Deploy → UI 서비스 플랫폼
  → Deploy → 어플리케이션 서비스 플랫폼
```

- UI·App 파이프를 **단일 Pipe 다중 스테이지**로 둘지, **파이프 분리**할지를 명세로 확정한다.
- Configuration Management에 환경별 시크릿·매니페스트 소유권을 명확히 한다.

### 6.5 메타용어 · Nexus dependency

```text
IT 메타 ──메타용어──▶ Backend IDE
Nexus ◀──dependency── Backend IDE
Nexus ◀──dependency/publish── Pipe
```

- 메타용어 변경이 빌드/DTO/매퍼에 미치는 파급(재생성·재배포)을 정의한다.
- Nexus 그룹·버전 정책으로 프레임워크·업무 라이브러리 충돌을 막는다.

### 6.6 단말소스 배포

```text
UI 서비스 플랫폼 (단말배포)
  → 단말소스 배포
  → 단말
```

- 서버 배포(Pipe→WAS)와 **클라이언트 배포**를 별도 승인·버전 체계로 관리한다.
- 단말·서버 API 계약(호환 버전)을 깨지 않도록 게이트를 둔다.

## 7. 인터페이스 · 메커니즘 설계 원칙

1. **UI 플랫폼과 App 플랫폼을 배포·장애·스케일 단위로 분리**한다.
2. **대내 API는 Cruz APIM 경유 HTTP만** 허용하고 DB 직접 교차 접속을 금지한다(계정계).
3. **파일은 MFT, 객체는 FOS, 구조화 DB는 connection** 으로 매체를 고정한다.
4. **모든 런타임 배포는 Git→Pipe를 통과**하고, 수동 WAS 복사 배포를 예외로 둔다.
5. **Nexus 미등록 의존성으로 프로덕션 빌드하지 않는다.**
6. **IT 메타 용어를 우회한 하드코딩 컬럼/필드**를 개발 표준에서 금지한다.
7. IaaS·VM 위에서 WAS를 운영하되, **환경(DEV/STG/PRD)별 네트워크·시크릿 격리**를 전제한다.
8. 단말소스 배포와 서버 Deploy의 **버전 매트릭스**를 릴리즈 노트로 관리한다.

## 10. 점검 체크리스트

- [ ] 단말→인증→L4→UI 경로의 인증·세션·TLS가 정의되어 있는가?
- [ ] UI Front와 App Backend의 호출 계약(URL·전문·타임아웃)이 문서화되어 있는가?
- [ ] Data Store connection 풀·타임아웃·취소 정책이 프레임워크 표준과 일치하는가?
- [ ] Cruz APIM에 계정계/정보계 Product·쿼터가 등록되어 있는가?
- [ ] MFT·FOS·대외 MCA 각각의 소유·재처리·암호화가 있는가?
- [ ] Git→Pipe→Deploy가 UI·App 양쪽에 Evidence로 남는가?
- [ ] Nexus dependency/publish 정책·취약점 스캔이 적용되는가?
- [ ] IT 메타 메타용어가 Backend IDE/빌드에 반영되는가?
- [ ] 단말소스 배포와 서버 Deploy 버전 매트릭스가 관리되는가?
- [ ] 온라인 프레임워크·CI/CD·선도개발 레이어드 문서와 용어가 정합하는가?

## 11. 종합 평가

이 장표의 통합개발환경은 **IaaS 위 UI·App 이원 런타임**과 **Git·Pipe·Nexus DevOps**, 그리고 **APIM·MFT·FOS·IT 메타 외부지원**을 한 표준으로 묶은 구조다. 시스템 연계의 핵심은 **런타임 매체 분리(connection/HTTP/MFT/FOS)** 와 **개발 산출물 통제(Git/Pipe/Nexus/메타용어)** 의 이중 축이다.

운영 품질은 **배포 재현성, APIM 우회 금지, 단말·서버 버전 정합, 메타·Nexus 동기화**에 좌우된다. 온라인 프레임워크 구성·단말↔앱 프레임워크 연계·CI/CD 산출물과 함께 읽어야 E2E 메커니즘이 닫힌다.
