# 메커니즘·아키텍처 표준 — 거래 처리 구조 분석

## 1. 핵심 결론

이 장표는 NH Cloud Framework의 온라인 거래를 **8단계 템플릿 메서드 구조**로 표준화한다. 모든 거래에 강제되는 시스템 선·후처리가 바깥 경계를 형성하고, 애플리케이션·서비스별 선택형 확장 지점이 그 안에 배치된다.

```text
거래 요청
   │
   ▼
[1 시스템 선처리] ──────────────────────────────── 프레임워크 강제
   │  자원 할당, 거래 통제, 입력 로그
   ▼
[2 공통 선처리] ── 필요 시 ───────────────────── 애플리케이션 확장
   ▼
[3 업무 선처리] ── 필요 시 ───────────────────── 서비스 확장
   ▼
[4 업무 본처리 Controller] ── DTO ── [5 Biz 로직 Service]
          │                                  │
          │                                  └─ DAO/SQL ── 데이터베이스
          │
          ▼
[6 업무 후처리] ── 필요 시 ───────────────────── 서비스 확장
   ▼
[7 공통 후처리] ── 필요 시 ───────────────────── 애플리케이션 확장
   ▼
[8 시스템 후처리] ──────────────────────────────── 프레임워크 강제
   │  Commit/Rollback, 출력 조립·로그, 자원 해제
   ▼
거래 응답
```

따라서 이 구조의 본질은 단순한 계층 분리가 아니라 다음 세 가지다.

1. **강제 골격**: 시스템 선처리와 후처리는 모든 거래에 동일하게 적용한다.
2. **제어된 확장**: 공통 및 업무 선·후처리는 정해진 훅(hook)에서만 선택적으로 구현한다.
3. **책임 분리**: Controller는 흐름을 제어하고 Service는 비즈니스 로직을 수행하며 DAO가 데이터 접근을 캡슐화한다.

## 2. 원본 장표 FACT 전사

### 2.1 단계별 처리 내용

| 단계 | 원본 명칭 | 처리 범위 | 원본 주요 내용 | 적용 성격 |
|---:|---|---|---|---|
| 1 | 시스템 선처리 | 애플리케이션 그룹 | 시스템 자원 할당, 거래 통제, 입력 로그 처리 | 필수 |
| 2 | 공통 선처리 | 애플리케이션 | 공통 업무 담당자가 공통 영역 로직을 필요 시 구현 | 선택 |
| 3 | 업무 선처리 | 서비스 ID, Controller 내 서비스 메서드 | 개별 업무 담당자가 공통 로직을 필요 시 구현 | 선택 |
| 4 | 업무 본처리 | Controller 메서드와 1:1 | 업무 거래 처리와 메인 처리 흐름 제어, Biz 로직 0~n개 호출 | 필수 |
| 5 | Biz 로직 | Service Class | 업무 처리를 위한 비즈니스 로직 구현체 | 업무별 |
| 6 | 업무 후처리 | 서비스 ID, Controller 내 서비스 메서드 | 업무 처리 후 필수 처리요건 검증 등을 필요 시 수행 | 선택 |
| 7 | 공통 후처리 | 애플리케이션 | 업무 처리 후 필수 처리요건 검증 등을 수행 | 선택 |
| 8 | 시스템 후처리 | 애플리케이션 그룹 | Commit/Rollback, 출력 조립, 출력 로그, 시스템 자원 해제 | 필수 |

### 2.2 계층 간 연결

- 업무 본처리 Controller와 Biz 로직 Service 사이의 전달 객체는 `DTO`로 표시되어 있다.
- Service는 `DAO`를 거쳐 `SQL`을 실행하고 데이터베이스에 접근한다.
- Controller 메서드와 서비스 ID는 1:1 대응한다.
- 하나의 Controller 본처리는 Service의 Biz 로직을 0개 이상 호출할 수 있다.
- 2·3·6·7단계는 장표에 `필요 시`로 표시된 선택형 처리다.

## 3. 전체 거래 메커니즘

### 3.1 정상 처리 경로

```text
Client
  │ Request
  ▼
Framework Dispatcher
  ├─ [1] SystemPreProcessor
  ├─ [2] ApplicationCommonPreProcessor?  (optional)
  ├─ [3] ServicePreProcessor?            (optional)
  ├─ [4] Controller.serviceMethod()
  │       ├─ 입력 DTO 검증·변환
  │       └─ [5] Service.bizMethod() 0..n
  │               └─ DAO → SQL Mapper → DB
  ├─ [6] ServicePostProcessor?           (optional)
  ├─ [7] ApplicationCommonPostProcessor? (optional)
  └─ [8] SystemPostProcessor
          ├─ commit
          ├─ 출력 전문/DTO 조립
          ├─ 출력 및 거래 로그
          └─ 자원 해제
  │
  ▼
Client Response
```

정상 경로에서는 업무 본처리가 완료되었다고 바로 성공 응답을 반환하지 않는다. 업무·공통 후처리의 검증을 통과하고 시스템 후처리가 커밋과 출력 조립을 끝낸 뒤에야 거래가 완료된다.

### 3.2 예외 처리 경로

```text
어느 단계에서든 Exception 발생
        │
        ▼
프레임워크 예외 분류
  ├─ 업무 예외: 표준 업무 오류코드·메시지 변환
  ├─ 시스템 예외: 내부 장애정보 기록 + 외부 메시지 마스킹
  └─ 연계/DB 예외: 원인·대상·재시도 가능성 분류
        │
        ▼
[8 시스템 후처리]
  ├─ rollback
  ├─ 오류 응답 조립
  ├─ 실패 거래·출력 로그
  └─ 자원 해제
        │
        ▼
표준 오류 응답
```

후처리 자체에서 예외가 나더라도 원래 업무 예외를 잃지 않도록 `primary exception`과 `cleanup exception`을 분리 기록해야 한다.

## 4. 단계별 상세 분석

### 4.1 시스템 선처리 — 거래 실행 컨텍스트 생성

시스템 선처리는 업무 코드보다 먼저 실행되는 프레임워크 경계다. 장표의 자원 할당·거래 통제·입력 로그를 운영 가능한 기능으로 풀면 다음과 같다.

- 거래 식별자(`GUID`, `traceId`, `transactionId`) 생성 또는 전파
- 서비스 ID와 Controller 메서드 매핑
- 사용자·채널·세션·권한 정보 확인
- 입력 전문 파싱, 크기·형식·필수 헤더 검증
- DB 연결과 트랜잭션 컨텍스트 준비
- 시작시각 및 타임아웃 설정
- 입력 로그와 감사 이벤트 기록
- MDC/로깅 컨텍스트 설정

이 단계는 애플리케이션 개발자가 우회할 수 없는 공통 필터 또는 인터셉터 계층이어야 한다.

### 4.2 공통 선처리 — 애플리케이션 단위 정책

공통 선처리는 애플리케이션 전체에서 공유하지만 다른 애플리케이션에는 강제하지 않는 정책을 담당한다.

- 애플리케이션 공통 사용자·조직·영업일 검증
- 공통 코드와 기준정보 적재
- 애플리케이션별 요청 정규화
- 공통 한도·권한·채널 정책 적용

공통 선처리에 개별 서비스 분기를 계속 추가하면 거대한 조건문과 숨은 결합이 생긴다. 애플리케이션 공통성 여부를 명확히 검토하고, 서비스 고유 조건은 3단계로 내려야 한다.

### 4.3 업무 선처리 — 서비스별 사전조건

업무 선처리는 서비스 ID별 사전조건을 본처리 전에 검사한다.

- 필수 업무 값과 값 범위 검증
- 중복 요청 및 멱등키 확인
- 업무 상태 전이 가능 여부 확인
- 사전 조회 및 입력 DTO 보강
- 처리 대상 존재 여부 검증

읽기만 하는 검증과 상태를 변경하는 선처리를 구분해야 한다. 상태 변경이 필요하면 본 트랜잭션에 포함하고 재실행 안전성을 확보한다.

### 4.4 업무 본처리 Controller — 오케스트레이션 경계

Controller의 책임은 업무 흐름 제어다.

- 서비스 ID에 대응하는 메서드 제공
- 요청 DTO를 Service 입력 계약으로 전달
- 0~n개의 Biz 로직 호출 순서 제어
- 처리 결과를 응답 DTO로 집계
- 업무 예외를 프레임워크 표준 예외로 전달

Controller에 SQL, 복잡한 계산, 장기 트랜잭션 로직을 직접 구현하면 안 된다. 얇은 Controller를 유지해야 단위 테스트와 재사용, 트랜잭션 경계가 명확해진다.

### 4.5 Biz 로직 Service — 업무 규칙과 트랜잭션 작업

Service는 업무 불변식과 상태 변경을 구현한다.

- 업무 규칙 및 계산
- 엔티티·DTO 변환
- 여러 DAO 호출의 조합
- 외부 서비스 호출이 필요한 경우 순서와 실패 정책 결정
- 업무 결과 생성

그림에서 최종 Commit/Rollback은 시스템 후처리에 있지만, Service는 어떤 작업이 하나의 원자적 거래인지 선언해야 한다. 즉 **트랜잭션 정책은 Service에서 정의하고 실행 완료는 프레임워크가 통제**하는 형태가 적합하다.

### 4.6 DAO·SQL — 영속성 경계

DAO는 DB 접근을 캡슐화한다.

- C/R/U/D 쿼리 실행
- SQL Mapper의 SQL ID 호출
- 결과 행을 DTO 또는 도메인 객체로 변환
- DB 오류를 표준 데이터 접근 예외로 변환

DAO는 업무 의사결정을 해서는 안 되며, 동적 SQL과 대량 조회에는 바인드 변수, 실행계획, 페이징, 타임아웃 기준을 적용해야 한다.

### 4.7 업무 후처리 — 서비스 결과 검증

업무 후처리는 본처리 이후 서비스 고유 완료 조건을 검사한다.

- 처리 건수와 금액 합계 대사
- 상태 전이 결과 검증
- 응답 DTO 필수 값 확인
- 서비스별 후속 이벤트 준비

DB 변경 이후 검증 실패 시 전체 거래가 롤백되어야 하므로 커밋보다 앞에 위치한다. 메시지 발행 같은 외부 부수효과는 DB 커밋과 불일치하지 않도록 Outbox 또는 커밋 후 이벤트 방식이 필요하다.

### 4.8 공통 후처리 — 애플리케이션 완료 정책

공통 후처리는 애플리케이션 차원의 완료 요건을 적용한다.

- 공통 결과 코드와 메시지 정규화
- 애플리케이션 공통 대사·감사 값 생성
- 공통 응답 헤더 및 부가정보 생성
- 공통 후속 이벤트 등록

업무 후처리와 공통 후처리는 검증 실패가 롤백을 유발하는지, 경고만 남기는지를 정책으로 명시해야 한다.

### 4.9 시스템 후처리 — 원자성 확정과 정리

시스템 후처리는 거래의 최종 성공·실패를 확정한다.

- 정상: Commit
- 예외 또는 후처리 검증 실패: Rollback
- 표준 출력 전문과 응답 DTO 조립
- 처리시간, 결과코드, 출력 로그 기록
- DB 연결·파일·세션 등 시스템 자원 해제
- 로깅 컨텍스트 정리

자원 해제는 성공·실패와 관계없이 `finally` 의미로 반드시 실행되어야 한다.

## 5. 책임 및 호출 관계

| 구성요소 | 핵심 책임 | 하면 안 되는 일 |
|---|---|---|
| Framework | 실행 순서, 거래 컨텍스트, 예외·트랜잭션·자원 통제 | 업무별 규칙 내장 |
| 공통 처리기 | 애플리케이션 공통 정책 | 서비스별 조건 분기 남발 |
| Controller | 요청 접수, 호출 조합, 결과 집계 | SQL 실행, 핵심 업무 계산 |
| Service | 비즈니스 규칙과 상태 변경 | HTTP/UI 세부사항 의존 |
| DAO | 영속성 접근과 결과 매핑 | 업무 흐름 결정 |
| DTO | 계층 간 데이터 계약 | DB 연결, 로직 수행 |
| SQL Mapper | SQL과 바인딩 정의 | 애플리케이션 제어 흐름 구현 |

호출 방향은 항상 `Controller → Service → DAO → SQL → DB`로 유지하고, 하위 계층이 상위 계층을 역호출하지 않도록 한다.

## 6. 트랜잭션 경계와 실패 정책

### 6.1 권장 트랜잭션 범위

```text
트랜잭션 시작
  → 업무 선처리(상태 변경이 있다면 포함)
  → Controller / Service / DAO
  → 업무 후처리 검증
  → 공통 후처리 검증
  → 성공 시 Commit, 실패 시 Rollback
트랜잭션 종료
```

시스템 선처리의 인증·입력 검증과 시스템 후처리의 로그·자원 정리는 DB 트랜잭션과 분리할 수 있지만, 업무 데이터 변경과 완료 검증은 같은 원자성 범위에 두는 것이 안전하다.

### 6.2 외부 연계 주의점

DB 트랜잭션 중 외부 API를 호출하면 잠금 시간이 길어지고 부분 실패 가능성이 커진다. 다음을 적용한다.

- 짧은 연결·응답 타임아웃
- 재시도 대상 오류의 명시적 분류
- 멱등키와 중복 방지
- Circuit Breaker와 Bulkhead
- DB 커밋 후 Outbox 이벤트 발행
- 보상 거래가 필요하면 Saga 상태 관리

## 7. 확장 지점 설계 원칙

2·3·6·7단계는 선택형이지만 임의 코드를 삽입하는 영역이 아니다.

```java
interface TransactionHook<I, O> {
    default void before(I input, TransactionContext context) {}
    default void after(I input, O output, TransactionContext context) {}
}
```

- 실행 순서를 명시하고 동일 우선순위 등록을 금지한다.
- 훅의 적용 범위를 애플리케이션 또는 서비스 ID로 선언한다.
- 훅 입력·출력과 변경 가능 범위를 제한한다.
- 훅 실패 시 중단·롤백·경고 중 어떤 정책인지 정의한다.
- 훅 수행시간을 별도 메트릭으로 관찰한다.

## 8. 관측성·보안·운영 표준

### 8.1 로그와 추적

모든 단계에 동일한 `traceId`, 서비스 ID, 사용자/채널 식별자, 시작·종료시각, 결과코드를 연결한다. 단계별 소요시간을 기록하면 공통 처리와 업무 로직 중 병목 위치를 구분할 수 있다.

입출력 로그에는 비밀번호, 인증 토큰, 주민번호, 계좌번호 등 민감정보를 원문으로 남기지 않고 필드 단위 마스킹과 접근 통제를 적용한다.

### 8.2 핵심 메트릭

- 서비스 ID별 TPS, 성공률, 오류율, p95/p99 지연시간
- 1~8단계별 실행시간
- Commit/Rollback 건수
- DB 연결 풀 사용률과 대기시간
- SQL별 수행시간과 영향 행 수
- 타임아웃·재시도·중복 차단 건수

### 8.3 보안 경계

- 시스템 선처리에서 인증과 기본 권한을 검증한다.
- Controller/Service에서 업무 객체 수준 권한을 다시 검증한다.
- DAO는 바인드 변수를 사용해 SQL Injection을 방지한다.
- 출력 조립 시 불필요한 내부 필드와 상세 예외를 제거한다.
- 감사 로그는 일반 애플리케이션 로그와 분리 보존한다.

| 테스트 수준 | 검증 대상 |
|---|---|

## 10. 장점과 구조적 위험

### 10.1 장점

- 모든 거래의 라이프사이클이 동일해 개발·운영 방식이 일관된다.
- 횡단 관심사를 업무 코드에서 분리한다.
- 공통 로직의 중복을 줄이고 변경 적용 범위를 통제한다.
- 트랜잭션·예외·로그·자원 해제를 프레임워크가 보장한다.
- 서비스 ID를 기준으로 추적과 장애 분석이 가능하다.

### 10.2 위험

- 선·후처리가 많아지면 실제 실행 흐름이 숨겨지고 지연시간이 누적된다.
- 공통 처리기가 개별 업무 조건문으로 비대해질 수 있다.
- Controller가 여러 Service를 무분별하게 조합하면 거대한 오케스트레이터가 된다.
- 최종 커밋 시점이 개발자에게 불명확하면 외부 부수효과와 DB 상태가 어긋날 수 있다.
- 후처리 실패 정책이 없으면 성공한 본처리가 예상치 않게 롤백될 수 있다.

## 11. 개선 권고

### 우선순위 1 — 거래 계약 명시

- 서비스 ID, Controller 메서드, 입력·출력 DTO, 타임아웃, 트랜잭션 속성을 메타데이터로 관리한다.
- 서비스 ID 중복과 미등록 메서드를 빌드 시 검출한다.

### 우선순위 2 — 실행 순서와 실패 정책 표준화

- 각 Hook의 순서, 적용 범위, 실패 시 Rollback 여부를 선언형으로 정의한다.
- 선택형 Hook이 없을 때는 불필요한 동적 탐색을 생략한다.

### 우선순위 3 — 트랜잭션과 외부 이벤트 정합성 확보

- DB 작업은 Service 단위로 원자성을 정의한다.
- 메시지·외부 API 부수효과는 Outbox, 멱등 처리 또는 보상 트랜잭션을 사용한다.

### 우선순위 4 — 단계별 관측성 제공

- 1~8단계 구간별 span과 메트릭을 자동 생성한다.
- 오류 응답에는 외부 공개용 오류코드와 추적 가능한 GUID만 제공한다.

### 우선순위 5 — 공통 로직 거버넌스

- 공통 처리 등록 시 공통성, 성능 영향, 소유팀, 버전 호환성을 심사한다.
- 애플리케이션·업무 로직이 공통 계층으로 역류하지 않도록 정기 점검한다.

## 12. FACT·ANALYSIS·확인 필요

### FACT — 그림에서 직접 확인되는 내용

- 거래는 시스템 선처리부터 시스템 후처리까지 8단계로 구성된다.
- 시스템 선·후처리는 NH Cloud Framework 영역이다.
- 공통 및 업무 선·후처리는 `필요 시` 적용한다.
- Controller와 Service는 DTO로 연결된다.
- Service는 DAO/SQL을 통해 데이터베이스에 접근한다.
- Controller 메서드와 서비스 ID는 1:1 관계다.
- 시스템 후처리는 Commit/Rollback, 출력 조립·로그, 자원 해제를 수행한다.

### ANALYSIS — 구조로부터 도출한 해석

- 전체 구조는 Template Method와 Hook 확장 패턴의 결합이다.
- Controller는 오케스트레이션, Service는 업무 규칙, DAO는 영속성 책임을 가진다.
- 업무·공통 후처리는 커밋 전 완료 조건 검증 지점으로 해석하는 것이 안전하다.
- 프레임워크가 최종 트랜잭션 완료를 통제하므로 외부 부수효과의 정합성 설계가 중요하다.

### 확인 필요

- DB 트랜잭션의 실제 시작 시점과 Service의 트랜잭션 선언 방식
- 2·3·6·7단계 Hook의 인터페이스, 실행 우선순위와 다중 등록 허용 여부
- 후처리 실패 시 전체 Rollback 여부와 경고 처리 조건
- 비동기 메시지·외부 API 호출의 Commit 연계 방식
- 읽기 전용 거래와 조회 거래에서 Commit/Rollback 처리 차이
- 서비스 ID와 Controller 메서드 매핑 설정 저장소

## 13. 최종 평가

이 거래 처리 구조는 **프레임워크가 거래 생명주기를 장악하고 업무 코드는 정해진 확장 지점과 계층에만 구현하도록 제한하는 표준 온라인 처리 아키텍처**다. 시스템 선·후처리를 강제함으로써 거래 통제, 로그, 트랜잭션, 자원 정리를 일관되게 적용하고, 공통·업무 선후처리를 통해 애플리케이션과 서비스의 차이를 수용한다.

성공적인 적용의 관건은 Hook을 많이 만드는 것이 아니라 **실행 순서·실패 정책·트랜잭션 범위·관측성을 명시적으로 관리하는 것**이다. 이 네 가지가 보장되면 업무 개발자는 Service의 비즈니스 규칙에 집중하면서도 운영 환경에서 예측 가능한 거래 처리 품질을 확보할 수 있다.
