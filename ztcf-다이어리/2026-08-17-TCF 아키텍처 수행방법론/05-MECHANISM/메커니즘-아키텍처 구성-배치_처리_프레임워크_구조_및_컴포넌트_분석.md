# 배치 처리 프레임워크 구조 및 컴포넌트 분석

> **분석 대상**: 제공 이미지 `배치 프레임워크`  
> **범위**: 작업자동화·Control-M·Shell·Spring Batch 실행 구조, Chunk/Tasklet Step, JobRepository 및 원장 DB  
> **분석 일자**: 2026-08-22  
> **분석 원칙**: 이미지의 목표 구조, Spring Batch 일반 메커니즘, 현재 저장소 구현을 구분한다.

---

## 1. 핵심 결론

이미지는 배치 업무를 두 계층으로 분리한다.

- **운영 오케스트레이션 계층**: 관리 담당자, 작업자동화 관리, 작업 스케줄러, Control-M Agent와 Shell이 배치 등록·조회·모니터링·정기/수시 기동을 담당한다.
- **배치 실행 계층**: Spring Batch의 `JobLauncher → Job → Step`이 실제 업무를 실행하고, JobRepository가 실행 이력과 재시작 상태를 저장한다.

Job은 하나 이상의 Step으로 구성된다. 그림의 Step #1은 `ItemReader → ItemProcessor → ItemWriter`가 반복되는 **Chunk 지향 Step**이고, Step #2는 한 번의 업무 단위를 수행하는 **Tasklet Step**이다. Reader/Writer와 Tasklet은 원장 Database와 직접 또는 DAO를 통해 데이터를 주고받는다.

이 구조의 핵심은 “스케줄을 언제 실행할지”와 “실행된 Job을 어떻게 처리·복구할지”를 분리하는 것이다. Control-M은 외부 스케줄·선후행·운영 통제를 담당하고 Spring Batch는 Job Instance, 실행 상태, Step checkpoint, commit/rollback, 재시작을 책임진다.

현재 저장소의 `tcf-batch`는 이름과 달리 Spring Batch 구현이 아니다. `build.gradle`에 `spring-batch` 의존성이 없으며 `@EnableScheduling`, `@Scheduled`, Service, JdbcTemplate과 자체 `OM_BATCH_HISTORY` 테이블로 AP/DB/Session/Deploy 상태를 수집한다. 따라서 원본의 JobLauncher, Job/Step, ItemReader/Writer, JobRepository 메타데이터와 자동 재시작 기능은 현행 모듈에서 확인되지 않는다.

### 2.2 제어 흐름과 데이터 흐름

```text
제어 흐름
관리자 → 자동화관리 → Scheduler → Control-M Agent → Shell
       → JobLauncher → Job → Step → 종료코드 → Control-M → 모니터링

메타데이터 흐름
JobLauncher/Job/Step ↔ JobRepository
  ├─ JobInstance 식별
  ├─ 실행 상태·시각·ExitStatus
  ├─ JobParameters
  └─ ExecutionContext/checkpoint

업무 데이터 흐름
원장 DB → ItemReader → ItemProcessor → ItemWriter → 원장 DB
원장 DB ↔ Tasklet
```

제어 데이터, 실행 메타데이터, 업무 원장 데이터는 목적이 다르므로 논리적·물리적으로 분리하는 것이 안전하다.

## 4. 컴포넌트별 상세 분석

### 4.1 관리 담당자

| 항목 | 분석 |
|---|---|
| 책임 | 작업 승인, 일정·선후행·운영 파라미터 관리, 실패 재처리 판단 |
| 입력 | 배치 등록 요청, 업무일정, 운영 승인, 장애 알림 |
| 출력 | 작업 정의, 기동 승인, 재실행·중단 명령 |
| 위험 | 운영자가 같은 업무일자로 중복 기동, 임의 파라미터 변경 |
| 통제 | RBAC, 4-eyes 승인, 변경이력, 재실행 runbook |

관리 담당자는 코드 실행자가 아니라 배치 실행 정책의 운영 주체다. 운영 UI와 스케줄러 명령은 감사 로그를 남겨야 한다.

### 4.2 작업 자동화 관리

이미지에 배치작업 등록·조회·모니터링 기능이 명시되어 있다.

```text
작업 정의
├─ jobName / application
├─ schedule / calendar
├─ predecessor / successor
├─ parameters / environment
├─ timeout / retry
├─ owner / alert route
└─ command or script
```

이 계층은 실행 엔진의 JobRepository와 다르다. 자동화 관리는 “언제·어떤 조건으로 기동할지”를 저장하고, JobRepository는 “실행된 Job이 어디까지 갔는지”를 저장한다.

### 4.3 작업 스케줄러

| 역할 | 설명 |
|---|---|
| 정기 기동 | cron·영업일·휴일 달력에 따른 실행 |
| 수시 기동 | 운영 승인에 따른 ad-hoc 실행 |
| 선후행 | 파일 도착, 이전 Job 성공, 업무 마감 조건 |
| 동시성 통제 | 같은 Job/업무일자의 중복 실행 방지 |
| SLA | 예상 시작·종료, 지연·미실행 감지 |
| 알림 | 실패·지연·timeout·재시도 결과 통보 |

스케줄러가 Job 내부 처리상태까지 임의로 판단하면 Spring Batch Repository와 상태가 갈라질 수 있다. 프로세스 exit code와 JobExecution 결과를 표준 매핑해야 한다.

### 4.4 작업실행정보 DB

이 DB는 외부 작업자동화 솔루션의 작업 정의와 실행 이력을 저장하는 영역으로 보인다.

```text
Scheduler Execution Record
├─ scheduleId / runId
├─ plannedAt / startedAt / endedAt
├─ command / host / agent
├─ predecessor state
├─ process exit code
├─ retry count
└─ operator action
```

Spring JobRepository의 `JobExecution`과 1:1 또는 N:1 대응 키를 남겨 외부 실행과 내부 실행을 함께 추적해야 한다.

### 4.5 Control-M Agent

| 항목 | 분석 |
|---|---|
| 책임 | 배치 서버에서 명령 실행, stdout/stderr·exit code 반환, 프로세스 감시 |
| 신뢰 경계 | 중앙 Control-M과 배치 서버 OS 사이 |
| 필수 통제 | Agent 인증, 명령 allowlist, 실행 계정 최소권한, 전송구간 암호화 |
| 실패 | Agent down, 네트워크 단절, 명령 수신 후 결과 미회신 |
| 운영 | heartbeat, zombie process 탐지, 재기동 시 중복 실행 방지 |

Agent timeout이 실제 Job 실패를 의미하지는 않는다. 서버에서 Job이 계속 실행 중일 수 있으므로 JobRepository 상태를 확인한 뒤 재실행해야 한다.

### 4.6 Shell Script

```text
Shell 책임
├─ profile/JAVA_HOME/working directory 설정
├─ jobName과 JobParameters 검증
├─ secret은 안전한 참조로 전달
├─ JVM option·로그 경로 설정
├─ Java process 실행
└─ BatchStatus/ExitStatus를 OS exit code로 변환
```

Shell에서 업무 로직이나 DB 갱신을 수행하면 재시작 메타데이터 밖에서 변경이 발생한다. Shell은 bootstrap과 종료코드 변환에 한정하는 것이 좋다.

### 4.7 JobLauncher

JobLauncher는 `Job`과 `JobParameters`를 받아 실행을 시작하고 JobExecution을 반환하는 진입점이다.

```text
run(job, parameters)
├─ JobInstance 식별
├─ 이미 완료된 동일 instance인지 검사
├─ JobExecution 생성
├─ Job 실행
└─ BatchStatus/ExitStatus 반환
```

동기 Launcher라면 Shell process가 Job 완료까지 대기하고, 비동기 Launcher라면 별도 상태 조회가 필요하다. Control-M 연계에서는 완료 exit code가 중요하므로 동기 실행이 단순하다.

### 4.8 Job

Job은 하나의 배치 업무 단위이자 Step 실행 그래프다.

| 구성 | 설명 |
|---|---|
| Job name | Job 정의 식별자 |
| JobParameters | JobInstance를 결정하는 식별/비식별 파라미터 |
| Step flow | 순차, 조건분기, 실패 전이, stop/restart |
| Listener | 시작·종료 공통 처리와 알림 |
| Incrementer/Validator | 파라미터 생성·검증 |

Job은 업무 데이터를 직접 반복 처리하기보다 Step 흐름을 조정해야 한다.

### 4.9 JobExecution

JobExecution은 JobInstance의 한 번의 실행 시도다.

```text
JobInstance(jobName + identifying parameters)
├─ JobExecution #1 : FAILED
└─ JobExecution #2 : COMPLETED  ← 재시작
```

시작·종료 시각, BatchStatus, ExitStatus, 오류 목록과 ExecutionContext를 보유한다. 같은 업무일자의 재시작과 새로운 업무일자의 신규 실행을 구분하는 핵심 개념이다.

### 4.10 Step

Step은 독립적인 실행·트랜잭션·재시작 단위다. 각 StepExecution은 read/write/skip/commit/rollback count와 상태를 저장한다.

좋은 Step은 입력·출력과 완료 조건이 명확하고, 재시작 시 앞 Step을 불필요하게 반복하지 않는다.

### 4.11 Chunk-oriented Step

```text
repeat until EOF
  ├─ read item × chunkSize
  ├─ process each item
  ├─ write List<item>
  ├─ COMMIT
  └─ checkpoint ExecutionContext
```

chunkSize가 너무 크면 lock·메모리·rollback 비용이 증가하고 너무 작으면 commit overhead가 증가한다. 데이터 크기, DB 부하, 재처리 단위를 기준으로 결정해야 한다.

### 4.12 ItemReader

| 책임 | 한 번에 한 item을 읽고 EOF에서 null 반환 |
|---|---|
| 입력원 | DB cursor/paging, flat file, message, API |
| 상태 | 현재 offset/page/key를 ExecutionContext에 저장 가능 |
| 재시작 | 정렬키와 checkpoint가 안정적이어야 함 |
| 위험 | 처리 중 원천 데이터 변경, 비결정적 정렬, cursor 장기 유지 |

DB paging Reader는 반드시 유일하고 안정적인 sort key를 사용해야 누락·중복이 줄어든다.

### 4.13 ItemProcessor

Processor는 읽은 item을 검증·변환하고 출력 item을 만든다. `null` 반환은 일반적으로 해당 item 필터링을 뜻한다.

```text
InputItem
  → validation
  → enrichment/reference lookup
  → calculation/transformation
  → OutputItem or null(filtered)
```

가능하면 side effect 없이 순수 변환으로 유지해야 skip/retry와 재시작이 예측 가능하다.

### 4.14 ItemWriter

Writer는 chunk 단위 List를 원장 DB·파일·외부 시스템에 기록한다.

| 고려사항 | 설명 |
|---|---|
| 멱등성 | 동일 chunk 재처리 시 중복 결과 방지 |
| Batch SQL | 단건 반복 대신 batch insert/update |
| Upsert 기준 | 업무키와 변경 정책 명확화 |
| 외부 호출 | DB TX와 원자성 불가하므로 outbox/보상 검토 |
| 오류 | 부분 성공 여부와 retry/skip 기준 정의 |

### 4.15 Tasklet

Tasklet은 Step 실행당 비교적 단일한 작업을 수행한다.

적합한 예:

- 파일 이동·압축·검증
- staging table truncate
- 저장 프로시저 호출
- 집계 SQL 한 번 실행
- 사전·사후 상태 전환

대량 row를 Tasklet 내부 for-loop로 처리하면 chunk checkpoint와 skip/retry 장점을 잃는다. 대량 반복은 Chunk Step이 적합하다.

### 4.16 Spring JobRepository

JobRepository는 업무 데이터 저장소가 아니라 배치 실행 상태 저장소다.

```text
JobRepository
├─ BATCH_JOB_INSTANCE
├─ BATCH_JOB_EXECUTION
├─ BATCH_JOB_EXECUTION_PARAMS
├─ BATCH_JOB_EXECUTION_CONTEXT
├─ BATCH_STEP_EXECUTION
└─ BATCH_STEP_EXECUTION_CONTEXT
```

이미지의 `BATCH_JOB_CONTEXT`는 표준 Spring Batch 테이블명이라기보다 단순화 또는 표기 오류로 보인다. 표준 명칭은 보통 `BATCH_JOB_EXECUTION_CONTEXT`다. 그림에는 `BATCH_JOB_EXECUTION`도 생략되어 있으나 실제 JobRepository에는 핵심 테이블이다.

### 4.17 원장 Database

원장 DB는 Reader의 입력과 Writer/Tasklet의 출력 대상이다. JobRepository와 목적이 다르다.

- 최소 권한의 배치 계정 사용
- 업무일자·partition key 인덱스
- 대량 DML의 undo/redo와 lock 관리
- 온라인 서비스와의 경합 시간대 통제
- 재실행을 고려한 상태·처리 플래그 설계
- DB 백업·복구 시 JobRepository와 원장 정합성 고려

---

## 5. JobRepository 테이블 분석

| 테이블 | 역할 | 주요 관계 |
|---|---|---|
| `BATCH_JOB_INSTANCE` | Job 이름과 식별 파라미터 조합 | 1:N JobExecution |
| `BATCH_JOB_EXECUTION` | 한 번의 실행 시도와 상태 | JobInstance 소속 |
| `BATCH_JOB_EXECUTION_PARAMS` | 실행 파라미터와 식별 여부 | JobExecution 소속 |
| `BATCH_JOB_EXECUTION_CONTEXT` | Job 범위 재시작 상태 | JobExecution 1:1 |
| `BATCH_STEP_EXECUTION` | Step 실행 상태와 처리 count | JobExecution 소속 |
| `BATCH_STEP_EXECUTION_CONTEXT` | Reader offset 등 Step checkpoint | StepExecution 1:1 |

운영자가 이 테이블을 직접 UPDATE해 상태를 COMPLETED로 바꾸는 행위는 재시작 정합성을 훼손한다. 표준 API와 운영 도구를 통해 stop/restart/abandon해야 한다.

## 6. 실패·재시작 메커니즘

### 6.1 Chunk 실패

```text
Chunk 1: read 1~100 → write → COMMIT
Chunk 2: read 101~200 → item 173 오류
  ├─ retry 가능 → 재시도
  ├─ skip 가능  → 173 skip, 나머지 처리
  └─ fatal      → Chunk 2 ROLLBACK, Step FAILED

재시작
ExecutionContext checkpoint → 101부터 또는 마지막 commit 이후 재개
```

재시작 안전성은 Reader 상태 저장뿐 아니라 Writer 멱등성과 원장 데이터의 안정된 정렬에 달려 있다.

### 6.2 Tasklet 실패

Tasklet의 작업이 단일 DB Transaction이면 rollback 후 재실행이 단순하다. 파일 이동이나 외부 호출처럼 rollback 불가능한 작업은 완료 marker, 임시 파일 rename, 보상 처리로 멱등성을 확보해야 한다.

### 6.3 외부 스케줄러 재실행

```text
Control-M 실패 감지
   │
   ├─ Process가 실제 종료되었는가?
   ├─ JobExecution status는 무엇인가?
   ├─ 같은 identifying parameters인가?
   ├─ 이전 실행이 STOPPING/RUNNING으로 남았는가?
   └─ 재시작 가능한 Step인가?
          │
          └─ 확인 후 restart
```

exit code만 보고 즉시 동일 명령을 다시 실행하면 중복 JobExecution과 원장 중복 처리가 발생할 수 있다.

## 7. 현재 저장소의 `tcf-batch` 구조

### 7.1 실제 실행 구조

```text
Spring Boot Application (@EnableScheduling)
       │
       ▼
ThreadPoolTaskScheduler(poolSize=2)
       │
       ├─ ApStatusCollectScheduler      cron 5분
       ├─ DbStatusCollectScheduler      cron 5분 offset
       ├─ SessionStatusCollectScheduler cron 5분 offset
       └─ DeployStatusCollectScheduler  cron 5분 offset
              │
              ▼
ScheduledCollectSupport
├─ warmup 중 skip
└─ shutdown 중 skip
              │
              ▼
CollectService
├─ Client로 상태 조회
├─ target별 성공/실패 snapshot
├─ Repository upsert
└─ OM_BATCH_HISTORY 실행 결과 insert
              │
              ▼
OM Dashboard DB
├─ OM_AP_STATUS
├─ OM_DB_STATUS
├─ OM_SESSION_STATUS
├─ OM_DEPLOY_STATUS
└─ OM_BATCH_HISTORY
```

### 7.2 원본과 현행 대응표

| 원본 Spring Batch 구조 | 현재 `tcf-batch` | 판단 |
|---|---|---|
| Control-M Agent/Shell | 구현 확인 안 됨 | 외부 운영 영역 또는 공백 |
| JobLauncher | 없음 | 비대응 |
| Job/JobExecution | Scheduler method + 자체 history | 단순 대체 |
| Step/StepExecution | Service method 내부 순차 처리 | 메타데이터 없는 대체 |
| ItemReader | Metrics Client 호출 | 개념적 입력 adapter |
| ItemProcessor | Service 계산/상태 판정 | 개념적 처리 대응 |
| ItemWriter | Repository upsert | 개념적 출력 대응 |
| Tasklet | startup migration/cleanup runner | 유사 단일 작업 |
| Spring JobRepository | 없음 | 자체 `OM_BATCH_HISTORY`만 존재 |
| BATCH_* 메타테이블 | 없음 | 재시작 checkpoint 미지원 |
| 작업 스케줄러 | Spring `@Scheduled` | 직접 대응하지만 분산 lock 미확인 |

### 7.3 코드 근거

| 파일·라인 | 확인 내용 |
|---|---|

| `tcf-batch/.../service/ApStatusCollectService.java:31-75` | 대상 반복 수집, upsert, 성공/실패 집계, history 저장 |

### 7.4 현행 방식의 의미

현행은 짧고 멱등적인 상태 수집 작업에는 단순하고 적합하다. 그러나 다음 요구가 생기면 Spring Batch 또는 동등한 실행 메타데이터 계층이 필요하다.

- 수백만 건 chunk 처리
- 실패 지점 checkpoint와 재시작
- Step별 상태·처리 count
- skip/retry 정책
- JobParameters 기반 중복 방지
- 복잡한 Step flow/partition
- Control-M과 내부 JobExecution 상태 연계

## 8. 현행 `tcf-batch`의 주요 위험

| 위험 | 영향 | 권고 |
|---|---|---|
| 다중 인스턴스에서 `@Scheduled` 동시 실행 | 중복 수집·중복 history | 분산 lock 또는 단일 scheduler 인스턴스 |
| Step/Checkpoint 없음 | 중간 실패 후 전체 재실행 | 작업이 커지면 Spring Batch 도입 |
| target별 즉시 upsert | 부분 성공 상태 발생 | PARTIAL 계약과 재처리 대상을 명시 |
| 자체 history가 최소 필드만 보유 | 원인·파라미터·회차 추적 부족 | runId, parameters, counts, error detail 추가 |
| pool size 2 | 장기 Job이 다른 일정 지연 | Job별 SLA·격리 executor 검토 |
| startup DDL/cleanup | 기동 시 데이터 변경 위험 | Flyway/Liquibase와 승인된 migration으로 이전 |
| cron만으로 일정 관리 | 휴일·선후행·수시 승인 부족 | Control-M 등 enterprise scheduler 연계 |
| shutdown 대기 10초 | 장기 작업 강제 종료 가능 | graceful checkpoint/timeout 정책 |

## 9. 아키텍처 적용 판단

### 9.1 `@Scheduled`가 충분한 경우

- 짧고 빈번한 상태 수집
- 전체 재실행 비용이 낮음
- upsert로 멱등성 확보
- 복잡한 선후행 없음
- 개별 item skip/retry 불필요

### 9.2 Spring Batch가 필요한 경우

- 대량 데이터 처리
- chunk transaction과 checkpoint 필요
- 실패 지점 재시작 필수
- item별 retry/skip 및 처리 count 필요
- Job/Step 운영 이력과 상태 조회 필요
- partition/parallel Step 필요

### 9.3 Control-M 연계가 필요한 경우

- 전사 업무 달력과 선후행
- 여러 서버·애플리케이션에 걸친 workflow
- 파일 도착·외부 시스템 완료 조건
- 운영 승인 기반 수시 기동
- 중앙 SLA·알림·재처리 통제

세 도구는 경쟁 관계가 아니다. Control-M은 외부 orchestration, Spring Batch는 내부 execution engine, `@Scheduled`는 단순한 애플리케이션 내 timer에 가깝다.

## 10. 보안 및 운영 통제

| 영역 | 통제 항목 |
|---|---|
| 작업 등록 | RBAC, 승인, 변경 이력, 운영/개발 분리 |
| Control-M Agent | mTLS/인증, 최소권한 OS 계정, 명령 allowlist |
| Shell | 인자 injection 방지, secret 비노출, 절대경로, umask |
| JobParameters | 개인정보·비밀번호 저장 금지, 검증·길이 제한 |
| JobRepository | 업무 사용자 접근 차단, 백업, 정리 정책 |
| 원장 DB | read/write 최소권한, 시간대별 resource 통제 |
| 로그 | job/instance/execution ID, 파라미터 마스킹 |
| 운영 재실행 | 4-eyes 승인, 멱등성 점검, 실행 증적 |

JobRepository의 ExecutionContext에는 직렬화된 상태가 저장될 수 있으므로 secret이나 대형 객체를 넣지 않아야 한다.

## 11. 권장 배치 표준

### 11.1 JobParameters

```text
식별 파라미터
├─ businessDate
├─ sequence/runType
└─ targetScope

비식별 파라미터
├─ operatorId
├─ requestId/controlMRunId
└─ requestedAt
```

단순히 현재 timestamp를 매번 식별 파라미터로 넣으면 항상 새 JobInstance가 되어 재시작이 아니라 신규 실행으로 처리된다.

### 11.2 Exit code 매핑

```text
COMPLETED                  → 0
COMPLETED WITH SKIPS       → 조직 정책상 0 또는 경고 코드
FAILED                     → 1
INVALID PARAMETERS         → 2
ALREADY RUNNING            → 3
TIMEOUT / STOPPED          → 4
INFRASTRUCTURE FAILURE     → 5
```

Control-M의 성공 조건과 Spring Batch의 BatchStatus/ExitStatus를 명시적으로 매핑해야 한다.

### 11.3 관측성

```text
batch_job_started_total{job}
batch_job_completed_total{job,status}
batch_job_duration_seconds{job}
batch_step_read_total{job,step}
batch_step_write_total{job,step}
batch_step_skip_total{job,step,type}
batch_step_rollback_total{job,step}
batch_job_last_success_timestamp{job}
```

외부 scheduler runId, JobExecution ID, 업무일자를 로그와 trace에 함께 넣으면 운영 도구 사이의 대조가 쉬워진다.

## 13. 검증 시나리오

1. 정기·수시 기동이 동일 JobParameters 정책을 따르며 의도치 않은 중복 JobInstance를 만들지 않는지 확인한다.
2. Control-M runId와 Spring JobExecution ID를 상호 추적할 수 있는지 확인한다.
3. Shell이 Job 종료 상태를 올바른 OS exit code로 반환하는지 확인한다.
4. Chunk commit 후 다음 chunk가 실패했을 때 재시작이 마지막 checkpoint부터 진행되는지 확인한다.
5. Reader의 정렬키가 유일하고 원천 데이터 변경에도 누락·중복이 발생하지 않는지 확인한다.
6. Processor의 filter, retry, skip count가 StepExecution에 정확히 기록되는지 확인한다.
7. Writer가 같은 chunk를 재처리해도 중복 원장 데이터가 생성되지 않는지 확인한다.
8. Tasklet이 중간 실패 후 재실행돼도 파일·외부 시스템에 중복 side effect가 없는지 확인한다.
9. 실패 Job을 같은 식별 파라미터로 재시작하고 완료 Job은 중복 실행이 차단되는지 확인한다.
10. JobRepository 장애 시 원장 DB commit과 실행 상태가 불일치하지 않는지 확인한다.
11. 다중 배치 서버에서 같은 일정이 동시에 실행되지 않는지 확인한다.
12. timeout·stop·서버 kill 후 상태가 RUNNING으로 영구 잔존하지 않고 운영 복구 가능한지 확인한다.
13. 온라인 부하 시간에 원장 DB lock·connection pool·I/O SLA를 침해하지 않는지 확인한다.
14. JobParameters, Shell 명령, 로그, ExecutionContext에 secret과 개인정보가 남지 않는지 확인한다.
15. 현재 `tcf-batch`의 PARTIAL 결과가 history에 기록되고 실패 target만 재처리 가능한지 확인한다.
16. 현재 scheduler 두 개 이상이 오래 실행될 때 pool size 2에서 다음 일정의 지연을 감지하는지 확인한다.
17. startup/shutdown gate가 준비 전·종료 중 실행을 막고 누락된 일정에 대한 보상 정책이 있는지 확인한다.

## 14. 최종 정리

원본 배치 프레임워크는 Control-M을 중심으로 한 외부 작업 자동화와 Spring Batch의 내부 실행·재시작 엔진을 결합한다. 관리·스케줄 계층은 등록, 일정, 선후행, 기동과 모니터링을 담당하고, JobLauncher/Job/Step은 Chunk 또는 Tasklet 방식으로 업무를 실행한다. JobRepository는 실행 상태와 checkpoint를, 원장 DB는 실제 업무 데이터를 보관한다.

현재 `tcf-batch`는 Spring Batch가 아니라 Spring Scheduling 기반의 경량 상태 수집 애플리케이션이다. 짧고 멱등적인 대시보드 수집에는 적합하지만 원본 그림이 제공하는 Step checkpoint, JobInstance 중복 방지, 실패 재시작, item retry/skip과 표준 BATCH_* 메타데이터는 없다. 대량·중요 업무 배치로 범위를 확장하려면 Control-M과 Spring Batch의 책임을 분리한 원본 구조를 도입하고, 현행 scheduler는 단순 주기 작업으로 제한하는 것이 적합하다.
