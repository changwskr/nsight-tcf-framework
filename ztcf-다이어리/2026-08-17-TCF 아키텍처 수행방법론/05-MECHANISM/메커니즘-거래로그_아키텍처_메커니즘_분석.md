# 거래로그 아키텍처 메커니즘 분석

> **분석 대상**: 제공 이미지 `거래로그`  
> **범위**: 시스템 선·후처리와 오류처리에서 Console/App Metric 및 업무별 DB에 거래로그를 적재하는 메커니즘  
> **분석 일자**: 2026-08-22  
> **분석 원칙**: 이미지에서 확인되는 목표 구조, 운영 관점 해석, 현재 저장소 구현을 구분한다.

---

## 1. 핵심 결론

이미지는 온라인 거래의 시작·정상 종료·오류 종료를 프레임워크 공통 라이브러리가 가로채서 두 종류의 저장소에 기록하는 **이중 거래 관측 구조**를 보여준다.

- **App Metric/Console**: 사람이 즉시 읽고 로그 수집기가 수집할 수 있는 실행 흐름, 요청·응답·오류 로그를 출력한다.
- **업무 DB 거래로그**: GUID와 서비스 ID를 기준으로 요청 시점, 응답 시점, 소요시간, 사용자, 단말 IP, 요청 전문, 결과코드와 오류내용을 구조화해 저장한다.

Controller의 시스템 선처리는 `SystemProcessor`를 통해 거래입력로그를 출력하고 DB 거래행을 생성한다. Service가 정상 완료되면 시스템 후처리에서 거래출력로그와 응답 정보를 기록한다. 예외가 발생하면 `ErrorProcessor`가 오류전문·오류로그를 만들고 같은 거래행에 오류코드와 오류내용을 반영한다.

따라서 DB 거래로그는 요청과 응답을 별개 레코드로 무조건 쌓는 것이 아니라, 원본 구조상 **거래 시작 시 생성하고 종료 시 완성하는 lifecycle record**로 해석된다. GUID/거래일련번호가 양쪽 이벤트를 결합하는 핵심 키다.

현재 PDMG는 이 개념을 `ServicePreventionInterceptor + PdmgTxLog + ImageLogHandler + ResponseBodyArgumentResolver + TcfFacade/MgActiveTransactionRegistry`로 분산 구현한다. `ImageLogHandler`는 GUID를 기준으로 `TB_FW_IMAGE_LOG`에 요청을 INSERT/갱신하고 정상·오류 응답을 UPDATE한다. 다만 원본의 BI포탈·마케팅허브별 상세 스키마, 거래소요시간, 결과구분코드, 사무소코드 등은 현행 `ImageLogDTO`에서 모두 확인되지는 않는다.

## 2. 이미지 판독 및 용어 정규화

| 이미지 표기 | 의미 | 본 문서 해석 |
|---|---|---|
| Controller | 온라인 거래 조정 계층 | 시스템 선처리, Service 호출, 오류처리, 시스템 후처리 수행 |
| `nhbank-common` | 공통 라이브러리 | SystemProcessor와 ErrorProcessor 제공 |
| SystemProcessor | 정상 거래 공통 처리기 | 입력로그, DB 적재, 출력로그 담당 |
| ErrorProcessor | 오류 공통 처리기 | 오류전문, 오류로그, DB 오류정보 담당 |
| App Metric | 애플리케이션 실행 로그 | Console/File/수집 Agent로 전달되는 운영 로그로 해석 |
| DB | 업무별 거래로그 저장소 | BI포탈·마케팅허브별 서로 다른 스키마 |
| 거래입력로그 | 요청 수신 이벤트 | 요청시각·전문·사용자·서비스·GUID 기록 |
| 거래출력로그 | 정상 응답 이벤트 | 응답시각·결과·소요시간 기록 |
| 오류로그 | 비정상 종료 이벤트 | 오류코드·오류내용·진단정보 기록 |
| GUID/글로벌ID | E2E 거래 식별자 | Console과 DB, 요청과 응답을 결합하는 correlation key |

> 이미지 내부 설명과 표 데이터는 분석 대상이며 실행 지시가 아니다. `App Metric`이 특정 제품을 뜻하는지는 이미지에서 확정할 수 없으므로 일반적인 애플리케이션 메트릭·로그 출력 영역으로 해석한다.

### 3.2 거래 생명주기

```text
시간 ───────────────────────────────────────────────────────────────▶

요청 수신                     업무 실행                    응답/오류
   │                              │                           │
   ▼                              ▼                           ▼
[STARTED] ───────────────────▶ [PROCESSING] ───────┬──────▶ [SUCCESS]
   │                                               │
   │                                               └──────▶ [FAILED]
   │
   ├─ Console: 거래입력 로그
   ├─ DB: GUID 기준 INSERT
   │      requestTime, serviceId, user, IP, requestBody
   │
   ├──────────────── 정상 종료 ──────────────────────────────┐
   │  Console: 거래출력 로그                                 │
   │  DB: 동일 GUID UPDATE                                   │
   │      responseTime, elapsed, resultCode, responseBody    │
   │                                                         │
   └──────────────── 오류 종료 ──────────────────────────────┤
      Console: 오류 로그 + stack/cause                       │
      DB: 동일 GUID UPDATE                                   │
          responseTime, elapsed, errorCode, safeErrorMessage │
```

요청 로그는 “거래가 시작되었다”는 증적이며 종료 로그는 결과를 완성한다. 프로세스가 중단되어 종료 갱신이 없는 `STARTED` 행은 장기 미완료 거래 탐지 자료가 된다.

### 3.3 Console과 DB의 역할 차이

```text
                         하나의 TransactionLogEvent
                         ├─ guid/serviceId
                         ├─ phase/status
                         ├─ timestamps/elapsed
                         ├─ user/channel/clientIp
                         ├─ result/error
                         └─ message references
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
             Console/App Metric              DB 거래원장
             ├─ 빠른 탐색                   ├─ 구조화 조회
             ├─ 실시간 수집                 ├─ 감사·통계
             ├─ 상세 stack                  ├─ 장기 보존
             └─ 운영 관측                   └─ 정합성 있는 상태
```

두 저장소에 서로 다른 이벤트를 임의 조립하면 값이 어긋난다. 하나의 논리 이벤트에서 sink별 표현을 파생해야 GUID, 시간, 결과코드가 일치한다.

## 4. 원본 DB 스키마 분석

### 4.1 BI포탈 거래로그

| 필드 | 의미 | 분류 |
|---|---|---|
| GUID | 전 구간 거래 식별자 | 추적 키 |
| 업무로그일시 | 업무 로그 발생 시각 | 시간 |
| 서비스ID | 호출 업무 식별자 | 라우팅·통계 |
| 조작자 개인번호 | 거래 사용자 | 감사 |
| BI포탈 전문내용 | 요청 또는 응답 전문 | Payload |
| 정보계최초등록자개인번호 | 최초 생성 주체 | 감사 |
| 정보계최초등록프로그램ID | 최초 생성 프로그램 | 감사 |
| 정보계최초등록일시 | 최초 생성 시각 | 감사 |
| 정보계최종변경자개인번호 | 최종 갱신 주체 | 감사 |
| 정보계최종변경프로그램ID | 최종 갱신 프로그램 | 감사 |
| 정보계최종변경일시 | 최종 갱신 시각 | 감사 |

BI포탈은 비교적 단순한 전문 이미지와 감사 필드 중심 구조다. 요청·응답 구분 컬럼이 화면에 명확하지 않으므로 하나의 컬럼을 단계별로 갱신하는지, 별도 행을 생성하는지 실제 테이블 정의가 필요하다.

### 4.2 마케팅허브 거래로그

| 필드 | 의미 | 분류 |
|---|---|---|
| 거래일련번호 | 업무 거래 sequence | PK/정렬 |
| 거래일자 | 거래 업무일자 | Partition/조회 |
| 마케팅허브ID | 업무 시스템 식별 | 시스템 |
| 거래서비스ID | 서비스 식별자 | 라우팅·통계 |
| 글로벌ID | E2E GUID | 상관관계 |
| 거래요청일시 | 요청 시작 시각 | 성능 |
| 거래응답일시 | 응답 완료 시각 | 성능 |
| 거래소요시간 | 요청~응답 경과 | 성능 |
| 거래입력내용 | 요청 전문 | Payload |
| 거래자개인번호 | 사용자 식별 | 감사 |
| 거래사무소코드 | 소속·거점 | 감사/통계 |
| 거래단말기IP주소 | 요청 단말 IP | 보안/감사 |
| 거래결과구분코드 | 성공·실패 구분 | 결과 |
| 에러코드 | 표준 오류코드 | 결과 |
| 에러내용 | 오류 메시지 | 결과 |
| 최초/최종 등록자·프로그램·일시 | 생성·수정 이력 | 감사 |

마케팅허브 구조는 거래 감사뿐 아니라 성능 분석과 오류 통계까지 지원한다. `글로벌ID`와 `거래일련번호`의 역할을 구분해 전자는 E2E correlation, 후자는 로컬 저장소 PK로 사용하는 것이 자연스럽다.

### 4.3 공통 Canonical 모델

```text
TransactionLog
├─ identity
│  ├─ transactionSequence
│  ├─ guid / traceId
│  ├─ serviceId / systemId
│  └─ businessDate
├─ actor
│  ├─ userId
│  ├─ officeCode
│  ├─ clientIp
│  └─ channel
├─ timing
│  ├─ requestAt
│  ├─ responseAt
│  └─ elapsedMs
├─ result
│  ├─ status : STARTED | SUCCESS | FAILED | TIMEOUT
│  ├─ resultCode
│  ├─ errorCode
│  └─ safeErrorMessage
├─ payload
│  ├─ requestRef/requestBody
│  └─ responseRef/responseBody
└─ audit
   ├─ createdByProgram/createdAt
   └─ updatedByProgram/updatedAt
```

업무별 DB 스키마가 다르더라도 공통 라이브러리는 canonical event를 만들고 adapter가 각 테이블에 매핑하는 구조가 확장에 유리하다.

## 5. 로그 기록 시점

| 시점 | Console/App Metric | DB | 필수 여부 |
|---|---|---|---|
| 요청 수신 | GUID·서비스·요청 단계 | STARTED INSERT | 필수 |
| 시스템 선처리 완료 | 인증·거래제어 결과 | 필요 시 header 보강 UPDATE | 권장 |
| Service 시작/종료 | 업무 구간과 시간 | 보통 최종 결과에 집계 | 권장 |
| 정상 후처리 | 응답·성공·소요시간 | SUCCESS UPDATE | 필수 |
| 업무 예외 | 오류코드·예외 | FAILED UPDATE | 필수 |
| Timeout | 제한시간·경과시간 | TIMEOUT UPDATE | 필수 |
| 프로세스 비정상 종료 | 마지막 진행 단계 | 종료 UPDATE 불가 가능 | Reaper/배치 필요 |

DB 로그 저장 실패가 본 거래의 commit/rollback을 바꾸면 로그 장애가 업무 장애로 확대된다. 감사 요구와 가용성 요구를 고려해 독립 트랜잭션, outbox, 비동기 큐 또는 fail-safe 정책 중 하나를 명확히 선택해야 한다.

## 6. 현재 저장소 실행 메커니즘

### 6.1 현행 전체 흐름

```text
DefaultFilter / ServicePreventionInterceptor
       │
       ├─ GUID 생성·MDC 설정
       ├─ PdmgTxLog.systemPreStart / request 원문 Console 출력
       └─ ImageLogHandler.preImagelog
             └─ TB_FW_IMAGE_LOG GUID 기준 UPDATE 우선 → 없으면 INSERT
                    requestTime, requestMsg, serviceId,
                    screenId, optrEno, clientIp
       │
       ▼
TcfFacade
├─ MgActiveTransactionRegistry.begin
├─ STF → Worker/Transaction → Dispatcher/Handler
└─ outcome 표시
   ├─ markClientSuccess
   ├─ markClientError
   └─ markClientTimeout
       │
       ▼
ResponseBodyArgumentResolver / afterCompletion
├─ PdmgTxLog.onlineResponseAsIs Console 출력
├─ 정상: ImageLogHandler.postImagelog
│    └─ responseTime/responseMsg UPDATE
├─ result 오류: exception 필드 동시 UPDATE
└─ throw된 예외: exceptionImagelog
     └─ exceptionType/code/message/responseMsg UPDATE
```

### 6.2 원본과 현행 대응

| 원본 이미지 | 현재 PDMG 구현 | 대응 수준 |
|---|---|---|
| SystemProcessor 입력로그 출력 | `PdmgTxLog.onlineRequestAsIs` + Interceptor logging | 직접 대응 |
| SystemProcessor 거래로그 적재 | `ImageLogHandler.preImagelog` | 직접 대응 |
| SystemProcessor 출력로그 출력 | `PdmgTxLog.onlineResponseAsIs` + Response Advice | 직접 대응 |
| ErrorProcessor 오류로그 출력 | Interceptor/GlobalExceptionHandler logger | 분산 대응 |
| ErrorProcessor 오류로그 적재 | `ImageLogHandler.exceptionImagelog` | 직접 대응 |
| App Metric | SLF4J/Log4j Console/File 로그 | 개념 대응 |
| BI포탈·마케팅허브별 DB | 공통 `TB_FW_IMAGE_LOG` | 단일화·축소 구현 |
| GUID | `ImageLogDTO.guid`, MDC/ServiceContext | 직접 대응 |
| 거래요청/응답일시 | `requestTime`, `responseTime` | 직접 대응 |
| 거래소요시간 | active evidence에 존재 가능, ImageLogDTO에는 없음 | 부분 대응 |

| 감사 등록/변경 필드 | ImageLogDTO에서 미확인 | 구현 공백 |

## 7. 거래로그와 다른 로그의 구분

| 로그 종류 | 목적 | 보존 특성 | 주요 내용 |
|---|---|---|---|
| 거래로그 | 거래 단위 감사·추적 | 구조화·장기 | GUID, 서비스, 사용자, 시간, 결과 |
| 전문/이미지로그 | 요청·응답 재현 | 민감·대용량 | request/response payload |
| 애플리케이션로그 | 장애 분석 | 검색 중심 | 실행 단계, class/method, stack |
| 메트릭 | 추세·알림 | 집계 중심 | TPS, latency, error rate, saturation |
| 감사로그 | 사용자 행위 증명 | 불변성·접근통제 | 누가 무엇을 언제 수행했는가 |
| Trace | 분산 호출 관계 | 샘플링 가능 | trace/span, downstream latency |

원본은 이 중 거래로그, 전문로그, 애플리케이션 로그를 하나의 그림에 담는다. 실제 구현에서는 목적별 저장·보존·권한을 분리하되 GUID/traceId로 연결해야 한다.

## 8. 정합성 및 장애 메커니즘

### 8.1 로그 DB와 업무 DB의 트랜잭션

```text
선택 A: 업무 TX와 동일
업무 rollback → 거래로그도 rollback
장점: 원자성 / 단점: 실패 거래 증적 소실

선택 B: 로그 독립 TX(REQUIRES_NEW)
업무 rollback → 오류 거래로그는 commit
장점: 실패 증적 보존 / 단점: 로그 DB 장애가 지연 유발 가능

선택 C: Event/Outbox 비동기
업무 → durable event → log consumer → 거래로그 DB
장점: 결합도·지연 감소 / 단점: 최종 일관성과 운영 복잡도
```

금융 거래 감사 목적이라면 실패 거래도 남아야 하므로 동일 업무 TX만 사용하는 방식은 부적합할 가능성이 높다. 현재 `ImageLogHandler`의 JdbcTemplate 호출이 어느 transaction manager에 결합되는지는 DataSource 구성과 호출 시점으로 추가 검증해야 한다.

### 8.2 미완료 거래 탐지

```text
SELECT STARTED rows
 WHERE request_time < now - timeout_threshold
   AND response_time IS NULL

→ 프로세스 crash / 강제 종료 / 후처리 누락 / DB update 실패 후보
→ active registry, application log, trace와 GUID로 대조
→ ABORTED 또는 UNKNOWN 상태 보정
```

메모리 기반 active registry는 프로세스 재시작 시 사라지므로 장기 미완료 탐지는 DB 거래로그나 외부 telemetry 저장소에서 수행해야 한다.

### 8.3 중복 GUID

현행 코드는 동일 GUID가 존재하면 요청 필드를 갱신하고, INSERT 경쟁 시 다시 UPDATE한다. 이는 PK 오류를 줄이지만 서로 다른 거래가 같은 GUID를 잘못 재사용하면 기존 원장을 덮어쓸 수 있다.

권장 정책은 다음과 같다.

- 동일 GUID + 동일 idempotency fingerprint: 재시도 이벤트로 기록
- 동일 GUID + 다른 serviceId/body hash: 충돌로 차단·경보
- 요청 회차(`attemptNo`) 또는 별도 거래일련번호 저장
- 원본 요청을 단순 overwrite하지 않고 변경 이력 보존

## 9. 보안·개인정보 위험

| 위험 | 영향 | 권고 |
|---|---|---|
| 요청·응답 전문 전체 저장 | 개인정보·계좌정보 노출 | schema 기반 마스킹·암호화·필드 allowlist |
| Console에 원문 출력 | 중앙 로그로 광범위 복제 | 운영 환경 payload 로그 비활성/부분 마스킹 |
| 사용자 개인번호 평문 | 내부자 조회 위험 | 접근통제, 표시 마스킹, 감사 조회로그 |
| 단말 IP 무기한 보존 | 개인정보 과다 보존 | 목적·보존기간·파기정책 정의 |
| 오류내용에 SQL/stack 포함 | 내부 구조 유출 | DB에는 안전 메시지와 내부 진단 참조 분리 |
| 로그 위·변조 | 감사 신뢰성 상실 | append-only/WORM, hash chain 또는 서명 검토 |
| 로그 인젝션 | 검색·파서 교란 | 개행·제어문자 정규화, 구조화 JSON logger |
| 과도한 동기 DB 기록 | 거래 지연·장애 전파 | timeout, bulk/async, circuit breaker와 fallback |

로그에는 운영에 필요한 최소 정보만 저장해야 한다. “나중에 필요할 수 있음”은 전문 원문을 무기한 보존할 정당한 근거가 되지 않는다.

## 10. 운영 메트릭과 알림

거래로그 이벤트에서 다음 메트릭을 파생할 수 있다.

```text
transaction_started_total{serviceId, channel}
transaction_completed_total{serviceId, result}
transaction_duration_ms{serviceId} histogram
transaction_error_total{serviceId, errorCode, type}
transaction_timeout_total{serviceId}
transaction_log_write_failure_total{sink, operation}
transaction_incomplete_current{serviceId}
```

권장 알림:

- 특정 서비스 오류율 급증
- p95/p99 소요시간 임계치 초과
- STARTED 대비 완료 이벤트 누락
- 거래로그 DB write failure 발생
- 동일 GUID 충돌
- 민감정보 마스킹 실패 탐지
- App log와 DB 결과 상태 불일치

App Metric 영역은 개별 로그 행뿐 아니라 이 집계 지표를 제공해야 운영자가 전체 상태를 빠르게 판단할 수 있다.

## 11. 권장 거래로그 기록 계약

### 11.1 이벤트 모델

```text
TransactionLogEvent
├─ eventId          이벤트 자체의 중복 제거 키
├─ guid             거래 correlation key
├─ attemptNo        재시도 회차
├─ phase            RECEIVED | COMPLETED | FAILED | TIMED_OUT
├─ serviceId
├─ occurredAt
├─ elapsedMs
├─ actor/channel/clientIp
├─ resultCode/errorCode
├─ requestHash/responseHash
├─ payloadReference 암호화 전문 저장소 참조
└─ schemaVersion
```

### 11.2 저장 Adapter

```text
TransactionLogPublisher
  ├─ ConsoleLogSink
  ├─ MetricSink
  ├─ BiPortalTransactionLogAdapter
  ├─ MarketingHubTransactionLogAdapter
  └─ ImageLogAdapter
```

공통 처리기가 업무별 테이블 SQL을 직접 포함하기보다 adapter 인터페이스를 사용하면 스키마 차이와 장애 정책을 격리할 수 있다.

### 11.3 로그 실패 정책

| 로그 | 저장 실패 시 | 이유 |
|---|---|---|
| Console/App 로그 | 업무 계속, fallback stderr/health 경고 | 관측 sink 장애가 업무를 중단하지 않도록 함 |
| 운영 Metric | 업무 계속, drop counter 증가 | 집계는 재구성 가능 |
| 일반 전문로그 | 정책에 따라 계속, 민감 전문은 재시도 큐 | 중요도와 비용 균형 |
| 법적·감사 필수 거래로그 | fail-close 또는 durable queue | 조직 규정에 따라 유실 불가 |

감사 필수 여부는 기술팀이 임의로 결정할 수 없으므로 업무·보안·준법 부서와 거래 유형별 정책을 확정해야 한다.

## 13. 검증 시나리오

1. 정상 거래에서 요청 로그가 먼저 생성되고 동일 GUID 행에 정상 응답이 갱신되는지 확인한다.
2. 업무 예외에서 동일 GUID 행에 오류코드·오류내용·응답시각이 기록되는지 확인한다.
3. Timeout과 Overload가 각각 구분된 상태와 코드로 기록되는지 확인한다.
4. Console 요청·응답 로그와 DB 거래로그의 GUID·서비스 ID·시간·결과가 일치하는지 확인한다.
5. 거래 소요시간이 서버 측 monotonic clock 기준으로 정확히 계산되는지 확인한다.
6. 같은 GUID의 동일 재시도와 충돌 요청이 구분되는지 확인한다.
7. 동시 INSERT 경쟁에서도 중복 행이나 기존 다른 거래 overwrite가 발생하지 않는지 확인한다.
8. 프로세스 강제 종료 후 responseTime이 없는 거래를 미완료로 탐지할 수 있는지 확인한다.
9. 로그 DB 장애 시 업무 거래의 계속/중단 정책과 fallback이 설계대로 작동하는지 확인한다.
10. 업무 DB rollback 후에도 실패 거래 감사로그가 보존되는지 확인한다.
11. 계좌번호·주민번호·비밀번호·token 등 민감정보가 Console과 DB에서 마스킹되는지 확인한다.
12. 대형 요청·응답에서 로그 크기 제한과 truncation 표식이 적용되는지 확인한다.
13. 보존기간 만료 후 payload와 개인정보가 파기되며 감사 메타데이터는 정책대로 유지되는지 확인한다.
14. 서비스별 TPS, 오류율, p95/p99, 미완료 거래 알림을 거래로그에서 재현할 수 있는지 확인한다.
15. 로그 기록 자체의 예외가 최초 업무 예외를 덮거나 응답을 지연시키지 않는지 확인한다.

## 14. 최종 정리

원본 거래로그 아키텍처는 시스템 선처리에서 거래 시작을 기록하고, 시스템 후처리 또는 오류처리에서 결과를 완성하여 Console/App Metric과 업무 DB 양쪽에 남기는 구조다. GUID, 서비스 ID, 사용자, 요청·응답 시각, 소요시간, 결과·오류코드가 거래 추적의 중심이며 요청·응답 전문은 재현을 지원한다.

현재 PDMG의 `ImageLogHandler`는 이 lifecycle 패턴을 GUID 기반 INSERT/UPDATE로 구현하고, `PdmgTxLog`는 Console 실행 흐름을, `MgActiveTransactionRegistry`는 실행 중·최근 거래 상태를 제공한다. 다만 원본 업무별 스키마보다 필드가 축소되어 있고 전문 원문 저장 및 GUID overwrite 정책에는 보안·정합성 위험이 있다. 향후에는 canonical 거래 이벤트와 sink adapter, 명시적 상태·소요시간, 중복 방지, 마스킹·보존 정책을 표준 계약으로 고정하는 것이 적합하다.
