# 형상배포기술아키텍처 — 개발 빌드 배포 표준 아키텍처 구성 분석

## 1. 분석 개요

첨부 장표의 **개발 빌드 배포 표준 아키텍처 구성**을 기준으로, **로컬 PC → GitLab(형상) → Jenkins(CI/CD) → Nexus → IaaS(컨테이너·Backing)** 로 이어지는 **표준 개발·빌드·배포 흐름**을 분석한다.

장표 상단 요약은 다음 두 축이다.

- **개발**: GitLab에서 Feature Branch를 생성·Checkout 후, 개발 완료 시 GitLab으로 Push한다.
- **배포**: GitLab의 베이스 브랜치(`dev`, `master`) 병합을 기준으로 Jenkins Pipeline이 **TAS 환경에 컨테이너 서비스**로 배포한다.

통합개발환경 시스템연계(IDE·Git·Pipe·Nexus)와 맞물려, 본 장표는 **개발자 단위 작업부터 운영 서버 착지까지의 단계 번호(①~⑥) 표준**이다.

> 이 문서는 이미지에서 판독한 논리 구조를 분석한 것이다. TAS 제품·프로젝트명, Jenkins Job 트리거(Webhook/Poll), Nexus 그룹·배포 정책, `dev`/`master` 외 브랜치 전략, 환경(DEV/STG/PRD)별 Pipeline 분기는 구축 명세에서 확인해야 한다.

## 2. 핵심 결론

- **5열 표준 구성**: 로컬 PC · 형상관리(GitLab) · CI/CD(Jenkins) · 라이브러리 저장소(Nexus) · IaaS(운영서버).
- **Feature Branch 개발**: 이슈 → 브랜치(원격 A) → clone/checkout → commit → push(원격 A') → **베이스 병합(원격 B)**.
- **병합이 Pipeline을 기동**: 코드 병합(⑤) 후 Pipeline 실행(⑥)으로 Jenkins에 접속한다.
- **Pipeline 3단**: **Build → Test → Deploy**.
- **Nexus는 Build 의존성**: Maven Repository에서 **Dependencies Libraries**를 Build 단계로 공급한다.
- **배포 착지는 컨테이너**: IaaS에서 **컨테이너 생성** 후 **Backing 서비스 결합**.
- **베이스 브랜치 고정**: 배포 트리거의 기준은 장표상 **`dev`, `master`**.
- **형상과 배포의 분리**: GitLab은 소스·병합, Jenkins는 빌드·테스트·배포, Nexus는 라이브러리, IaaS는 런타임.

## 3. 장표 구성요소 전사

### 3.1 상단 요약 문장

| 구분 | 장표 요지 |
|---|---|
| 개발 | Feature Branch 생성 → 로컬 Checkout → 개발 완료 후 GitLab Push |
| 배포 | `dev`/`master` 병합 기준 → Jenkins Pipeline → TAS 환경 **컨테이너 서비스** 배포 |

### 3.2 수직 레인(도구)

| 레인 | 표기 | 역할(해석) |
|---|---|---|
| 로컬 PC | 로컬 PC | 개발자 작업·로컬 저장소 |
| 형상 관리 | GitLab | 이슈·브랜치·원격 저장소·병합 |
| CI/CD | Jenkins | Pipeline · Build/Test/Deploy |
| 라이브러리 저장소 | Nexus Repository | Maven · Dependencies Libraries |
| IaaS | 운영서버 | 컨테이너 생성 · Backing 서비스 결합 |

### 3.3 단계 ①~⑥

| # | 행위 | 위치 | 결과 상태(장표) |
|---|---|---|---|
| ① | 브랜치 생성 | GitLab | 원격 저장소 A (이슈 생성 선행) |
| ② | git clone/checkout | GitLab → 로컬 | 로컬 저장소 A |
| ③ | git commit | 로컬 PC | 로컬 저장소 A' |
| ④ | git push | 로컬 → GitLab | 원격 저장소 A' |
| ⑤ | 코드 병합 | GitLab | 원격 저장소 B (베이스) |
| ⑥ | Pipeline 실행 | GitLab → Jenkins | CI/CD 접속 · Pipeline 기동 |

### 3.4 Pipeline · 배포

| 단계 | 표기 | 연계 |
|---|---|---|
| Build | Build | Nexus Maven → Dependencies Libraries |
| Test | Test | (장표상 후속 단계) |
| Deploy | Deploy | → IaaS 컨테이너 생성 |
| 런타임 결합 | Backing 서비스 결합 | 컨테이너 ↔ Backing Service |

## 5. 인터페이스 · 흐름 매핑

| # | 출발 | 행위/프로토콜 | 도착 | 설계 의미 |
|---|---|---|---|---|
| 1 | (개발자) | 이슈 생성 | GitLab | 작업 단위·추적 ID |
| 2 | GitLab | 브랜치 생성 | 원격 저장소 A | Feature Branch |
| 3 | GitLab | clone/checkout | 로컬 저장소 A | 로컬 작업 시작 |
| 4 | 로컬 | commit | 로컬 저장소 A' | 변경 확정 |
| 5 | 로컬 | push | 원격 저장소 A' | 원격 Feature 갱신 |
| 6 | 원격 A' | 코드 병합 | 원격 저장소 B | 베이스(`dev`/`master`) 반영 |
| 7 | GitLab | Pipeline 실행 | Jenkins | 자동 CI/CD 기동 |
| 8 | Nexus Maven | Dependencies | Jenkins Build | 빌드 재현·의존성 통제 |
| 9 | Jenkins Deploy | 배포 | IaaS | 컨테이너 서비스 착지(TAS) |
| 10 | 컨테이너 | Backing 결합 | Backing Service | DB 등 런타임 의존 연결 |

### 5.1 매핑에서 읽히는 설계 의도

1. **Feature에서만 개발**하고, **베이스 병합 후에야** 배포 파이프가 돈다.
2. **로컬 단독 배포를 표준 경로에서 제외**한다(반드시 GitLab→Jenkins).
3. **라이브러리는 Nexus 경유**로 빌드해 로컬/사설 jar 난입을 줄인다.
4. **런타임은 컨테이너 + Backing 바인딩**으로 앱과 인프라 의존을 분리한다.
5. 통합개발환경의 Pipe·Nexus와 **동일 축**(형상→빌드→산출물→배포)을 단계 번호로 구체화한다.

## 6. 주요 처리 흐름

### 6.1 개발 (Feature Branch)

```text
이슈 생성
  → ① 브랜치 생성 (원격 A)
  → ② clone/checkout (로컬 A)
  → 개발
  → ③ commit (로컬 A')
  → ④ push (원격 A')
```

- 브랜치 명명·이슈 링크·MR/MR 승인 규칙은 장표 밖이므로 표준으로 보강한다.
- 로컬 A → A'는 **커밋 단위 이력**이 Git에 남아야 한다.

### 6.2 병합 · Pipeline 기동

```text
원격 A'
  → ⑤ 코드 병합 → 원격 B (dev / master)
  → ⑥ Pipeline 실행
  → Jenkins CI/CD 접속
```

- Feature를 베이스에 넣기 전 **리뷰·품질 게이트**(장표 미표시)를 두는 것이 운영상 필요하다.
- `dev`와 `master` Pipeline 차이(대상 환경·승인)를 명세로 분리한다.

### 6.3 Build · Test · Deploy

```text
Jenkins Pipeline
  → Build ← Nexus (Dependencies Libraries)
  → Test
  → Deploy
  → IaaS: 컨테이너 생성
  → Backing 서비스 결합
```

- Test 실패 시 Deploy 차단이 표준이다(장표 순서상 Test가 Deploy 앞).
- Deploy 산출물(이미지·패키지)의 Nexus publish 여부는 본 장표에 **명시되지 않음**(의존성 화살표만 Build←Nexus). publish 정책은 통합개발환경·CI/CD 문서와 대조한다.

### 6.4 TAS · 컨테이너 · Backing

```text
Deploy
  → TAS 환경 컨테이너 서비스
  → Backing 서비스 결합 (Data Store 등)
```

- 통합개발환경 장표의 Backing Service(Data Store)·외부지원과 **런타임 결합점**이 맞닿는다.
- 시크릿·서비스 바인딩·헬스체크는 배포 표준의 운영 게이트로 둔다.

## 7. 형상배포 설계 원칙

1. **소스 진실의 원천은 GitLab**이다. 운영 서버에 수동 복사 배포를 표준에서 배제한다.
2. **Feature → 베이스 병합 후에만** Jenkins Deploy가 수행된다.
3. **베이스 브랜치는 `dev`/`master`** 를 배포 트리거 기준으로 관리한다.
4. **Build는 Nexus Maven 의존성**을 사용한다.
5. **Pipeline 순서는 Build → Test → Deploy** 를 지킨다.
6. **IaaS 착지는 컨테이너**이며, 완료 조건에 **Backing 서비스 결합**을 포함한다.
7. 로컬 PC는 **개발·커밋** 역할에 한정하고, 프로덕션 자격 증명을 두지 않는다.
8. 통합개발환경의 Git·Pipe·Nexus·IaaS 표기와 **제품·경로를 일치**시킨다.

## 8. 레인별 특성 요약

| 레인 | 장점 | 위험 | 통제 포인트 |
|---|---|---|---|
| 로컬 PC | 빠른 개발 사이클 | 미푸시·로컬만 테스트 | pre-commit·MR 필수 |
| GitLab | 이력·브랜치·병합 | 강제푸시·권한 | Protected branch·승인 |
| Jenkins | 자동 Build/Test/Deploy | Job 권한·시크릿 | RBAC·자격증명 금고 |
| Nexus | 의존성 재현 | 구버전·취약 라이브러리 | retention·스캔 |
| IaaS/TAS | 컨테이너·Backing | 잘못된 바인딩 | 환경별 매니페스트·헬스 |

## 9. 품질·위험과 개선 권고

| 위험 | 영향 | 개선 권고 |
|---|---|---|
| Feature 직접 Deploy | 미검증 코드 착지 | Protected branch + 병합만 트리거 |
| Test 스킵 Deploy | 장애 유입 | 파이프 게이트 필수화 |
| Nexus 외 의존성 | 빌드 비재현 | settings.xml·미러 강제 |
| `dev`/`master` 혼동 | 잘못된 환경 배포 | 브랜치→환경 매핑표 |
| Backing 미결합 | 기동 실패 | Deploy 후 스모크·바인딩 검증 |
| 산출물 publish 미정 | 롤백 어려움 | 이미지/아티팩트 버전·보관 정책 |
| 통합개발환경 Pipe와 Job 불일치 | 이중 표준 | 단일 Pipeline 카탈로그 |

## 10. 점검 체크리스트

- [ ] 이슈→브랜치→MR→병합 절차가 문서·권한으로 강제되는가?
- [ ] `dev`/`master` Protected branch와 배포 트리거가 연결되는가?
- [ ] Jenkins Pipeline이 Build→Test→Deploy 순이며 Test 실패 시 중단되는가?
- [ ] Build가 Nexus Maven Dependencies만 사용하는가?
- [ ] Deploy 대상이 TAS 컨테이너이며 환경별 Job이 분리되는가?
- [ ] 컨테이너 생성 후 Backing 서비스 결합·헬스체크 Evidence가 남는가?
- [ ] 로컬에 운영 배포 자격이 없는가?
- [ ] 통합개발환경·`23-CI-CD-DEPLOYMENT`·본 표준의 용어/도구가 정합하는가?

## 11. 종합 평가

이 장표의 개발 빌드 배포 표준은 **GitLab Feature 개발 → 베이스(`dev`/`master`) 병합 → Jenkins Pipeline(Build/Test/Deploy) → Nexus 의존성 → IaaS 컨테이너·Backing 결합**으로 정리된 형상배포 아키텍처다. 개발자 로컬과 운영 착지를 단계 ①~⑥으로 분리해, **형상의 단일 원천**과 **파이프라인 배포**를 표준화한다.

운영 품질은 **Protected branch, Test 게이트, Nexus 의존성 통제, 브랜치-환경 매핑, Backing 결합 검증**에 좌우된다. 통합개발환경 시스템연계·CI/CD 산출물과 함께 읽어야 E2E 형상배포가 닫힌다.
