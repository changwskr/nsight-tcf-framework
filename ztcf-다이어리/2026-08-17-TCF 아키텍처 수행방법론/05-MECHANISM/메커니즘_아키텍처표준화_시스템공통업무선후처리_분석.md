# 메커니즘·아키텍처 표준화 — 시스템·공통·업무 선후처리 범위 분석

## 1. 핵심 결론

이 장표는 온라인 거래의 선·후처리를 **업무 분류 계층에 맞춰 적용 범위를 달리하는 중첩 실행 구조**로 정의한다.

```text
애플리케이션 그룹(대구분)
└─ 애플리케이션(업무구분)
   └─ 기능(세부업무구분)
      └─ Controller.method = 개별 서비스/거래
         ├─ Service
         ├─ DAO
         └─ 업무 테이블
```

각 처리의 적용 범위는 다음과 같다.

| 처리 유형 | 적용 범위 | 대표 예시 |
|---|---|---|
| 시스템 선·후처리 | 애플리케이션 그룹 전체 | 마케팅플랫폼 `MP`, BI포털 `BL` |
| 공통 선·후처리 | 애플리케이션 단위 | 캠페인 `CM`, 신용실적 `CR` |
| 업무 선·후처리 | 기능 또는 개별 서비스 단위 | `A` 업무, `E` 업무 및 Controller 메서드 |

핵심 원칙은 **범위가 넓을수록 기술적이고 안정적인 정책만 배치하고, 업무에 가까울수록 구체적인 규칙을 배치**하는 것이다. 시스템 처리에 개별 업무 규칙을 넣거나 업무 처리에 전사 공통 자원 관리를 중복 구현하면 계층 분리의 효과가 사라진다.

## 2. 원본 그림 FACT 전사

### 2.1 마케팅플랫폼 사례

| 계층 | 코드/예시 | 그림의 구성 |
|---|---|---|
| 애플리케이션 그룹 | `MP = 마케팅 플랫폼` | 마케팅플랫폼 시스템 선·후처리 범위 |
| 애플리케이션 | `CM = 캠페인` | 캠페인 공통 선·후처리 범위 |
| 기능 | `A 업무` | 업무 선·후처리 범위 |
| 거래 구현 | Controller의 복수 `method` | 복수 Service·DAO 및 `TB_MPCMA*` 계열 테이블 |

### 2.2 BI포털 사례

| 계층 | 코드/예시 | 그림의 구성 |
|---|---|---|
| 애플리케이션 그룹 | `BL = BI 포털` | BI포털 시스템 선·후처리 범위 |
| 애플리케이션 | `CR = 신용실적` | 신용실적 공통 선·후처리 범위 |
| 기능 | `E 업무` | 업무 선·후처리 범위 |
| 거래 구현 | `Controller.method()` | 단일 Service·DAO 및 `TB_BLCRE*` 계열 테이블 |

### 2.3 그림에서 확인되는 범위 관계

- 시스템 선·후처리 선은 애플리케이션 그룹 전체를 감싼다.
- 공통 선·후처리 선은 특정 애플리케이션을 감싼다.
- 업무 선·후처리 선은 기능과 그 내부 구현을 감싼다.
- 동일 계층 구조는 마케팅플랫폼과 BI포털에 반복 적용된다.
- 기능 안에서 Controller, Service, DAO, 데이터베이스 테이블로 내려가는 전형적인 계층 구조를 사용한다.
- 기능 하나에 Controller 메서드, Service, DAO가 하나 또는 여러 개 존재할 수 있다.

## 3. 범위 중심 텍스트 아키텍처

### 3.1 마케팅플랫폼 예시

```text
┌──────────────────── [MP] 시스템 선·후처리 ────────────────────┐
│  적용 대상: 마케팅플랫폼 애플리케이션 그룹 전체                │
│                                                               │
│  ┌───────────────── [CM] 공통 선·후처리 ───────────────────┐  │
│  │  적용 대상: 캠페인 애플리케이션 전체                    │  │
│  │                                                         │  │
│  │  ┌──────────────── [A] 업무 선·후처리 ────────────────┐ │  │

│  │  │    ├─ method #1 ── Service #1 ── DAO #1 ──┐       │ │  │
│  │  │    └─ method #2 ── Service #2 ── DAO #2 ──┼─ DB    │ │  │
│  │  │                              TB_MPCMA* ────┘       │ │  │
│  │  └─────────────────────────────────────────────────────┘ │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 BI포털 예시

```text
┌──────────────────── [BL] 시스템 선·후처리 ────────────────────┐
│  적용 대상: BI포털 애플리케이션 그룹 전체                     │
│                                                               │
│  ┌───────────────── [CR] 공통 선·후처리 ───────────────────┐  │
│  │  적용 대상: 신용실적 애플리케이션 전체                  │  │
│  │                                                         │  │
│  │  ┌──────────────── [E] 업무 선·후처리 ────────────────┐ │  │
│  │  │  Controller.method()                               │ │  │
│  │  │       → Service → DAO → TB_BLCRE*                  │ │  │
│  │  └─────────────────────────────────────────────────────┘ │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 런타임 실행 순서

```text
요청
 │
 ├─ System Before     애플리케이션 그룹 정책
 │   └─ Common Before 애플리케이션 정책
 │       └─ Biz Before 기능/서비스 정책
 │           └─ Controller.method
 │               └─ Service → DAO → DB
 │       ┌─ Biz After
 │   ┌─ Common After
 ├─ System After
 │
응답
```

후처리는 선처리의 역순으로 실행하는 스택 구조가 자연스럽다. 안쪽의 업무 완료 조건을 먼저 검사한 뒤 애플리케이션 공통 결과를 정리하고, 가장 바깥 시스템 후처리가 Commit/Rollback과 자원 해제를 확정한다.

## 4. 시스템 선·후처리 분석

### 4.1 적용 범위

시스템 처리는 `MP`, `BL` 같은 애플리케이션 그룹 전체에 적용된다. 같은 그룹에 속한 모든 애플리케이션·기능·서비스가 반드시 통과하는 가장 바깥 실행 경계다.

### 4.2 시스템 선처리 책임

- 요청 식별자(`GUID`, `traceId`, 거래번호) 생성·전파
- 서비스 ID와 Controller 메서드 라우팅
- 인증 토큰, 세션, 채널 및 기본 권한 검증
- 입력 전문 파싱과 공통 스키마 검증
- 처리 시작시간과 타임아웃 설정
- DB 연결 및 트랜잭션 컨텍스트 준비
- 입력·감사 로그와 MDC 컨텍스트 생성
- 시스템 자원 할당과 거래량 통제

### 4.3 시스템 후처리 책임

- 정상 거래 Commit, 실패 거래 Rollback
- 공통 응답 헤더와 출력 전문 조립
- 결과 코드, 소요시간, 출력·감사 로그 기록
- 연결, 스트림, 세션 등 시스템 자원 해제
- 메트릭·분산 추적 span 종료
- 내부 예외를 외부 표준 오류로 변환하고 민감정보 제거

### 4.4 배치하면 안 되는 로직

- 캠페인 상태, 신용실적 계산 같은 도메인 규칙
- 특정 화면이나 서비스 ID만을 위한 조건 분기
- 개별 테이블 구조를 전제로 한 조회·갱신

시스템 처리기는 변경 영향이 그룹 전체로 퍼지므로 가장 보수적으로 관리해야 한다.

## 5. 공통 선·후처리 분석

### 5.1 적용 범위

공통 처리는 `CM`, `CR` 같은 애플리케이션 단위다. 동일 애플리케이션 안의 여러 기능이 공유하지만, 다른 애플리케이션 그룹이나 업무에는 자동 적용되지 않는다.

### 5.2 공통 선처리 후보

- 애플리케이션 공통 업무일·기준일 확인
- 공통 사용자·조직·권한 보강
- 공통 코드와 기준정보 로딩
- 캠페인 또는 신용실적 영역의 공통 요청 정규화
- 애플리케이션 공통 한도·상태 검증

### 5.3 공통 후처리 후보

- 애플리케이션 공통 결과 코드 정규화
- 공통 대사 값과 감사정보 생성
- 공통 응답 부가정보 조립
- 공통 후속 이벤트 등록
- 애플리케이션별 처리 결과 검증

### 5.4 공통화 판단 기준

다음 질문에 모두 가까운 경우에만 공통 계층에 둔다.

1. 같은 애플리케이션의 다수 기능이 실제로 사용하는가?
2. 기능별 분기 없이 동일한 정책으로 실행 가능한가?
3. 변경 주기와 소유팀이 같은가?
4. 전체 기능에 추가되는 지연시간을 수용할 수 있는가?
5. 실패 시 동일한 Rollback 정책을 적용할 수 있는가?

## 6. 업무 선·후처리 분석

### 6.1 적용 범위

업무 처리는 `A`, `E` 같은 기능 또는 Controller 서비스 메서드에 가장 가까운 확장 지점이다. 개별 거래의 사전조건과 완료조건을 담당한다.

### 6.2 업무 선처리 후보

- 입력 DTO의 업무 필수 값과 범위 검증
- 업무 객체 존재 여부 및 현재 상태 확인
- 허용된 상태 전이인지 확인
- 중복 요청과 멱등키 검증
- 사전 조회를 통한 DTO 보강
- 거래별 객체 권한 검증

### 6.3 업무 후처리 후보

- 갱신 건수, 금액, 합계 대사
- 상태 전이 결과 및 업무 불변식 검증
- 출력 DTO의 필수 값 확인
- 후속 이벤트 또는 알림 발행 준비
- 업무별 결과 코드 결정

### 6.4 Controller 메서드와의 관계

그림의 마케팅플랫폼 예시처럼 기능 하나가 복수 Controller 메서드와 Service·DAO를 포함할 수 있다. 이때 업무 선·후처리의 실제 적용 키는 다음처럼 세분할 수 있다.

```text
applicationGroup = MP
application      = CM
function         = A
serviceId        = Controller.method
```

기능 전체 공통 규칙은 `function=A`에 적용하고 거래별 규칙은 `serviceId`에 적용하는 이중 수준이 필요하다.

## 7. 중첩 범위와 상속 메커니즘

### 7.1 범위 해석

안쪽 거래는 바깥 범위의 정책을 상속한다.

```text
MP/CM/A/service-01 실행 정책
  = MP 시스템 정책
  + CM 공통 정책
  + A 기능 정책
  + service-01 거래 정책
```

BI포털도 같은 방식으로 `BL + CR + E + serviceId`의 합성 정책을 갖는다.

### 7.2 정책 해석 우선순위

권장 원칙은 다음과 같다.

- 보안, 감사, 자원 제한 같은 강제 시스템 정책은 하위에서 해제할 수 없다.
- 타임아웃 등 조정 가능한 값은 더 구체적인 범위가 더 엄격한 값으로만 재정의한다.
- 같은 유형의 Hook이 여러 개면 등록 순서 또는 명시적 우선순위로 결정한다.
- 상충하는 정책은 런타임이 아니라 배포 전 검증에서 차단한다.

### 7.3 실행 순서 규칙

```text
Before: System → Common → Function → Service
Main:   Controller → Service → DAO → DB
After:  Service → Function → Common → System
```

후처리는 역순이어야 각 범위가 자신보다 안쪽 처리의 결과를 관찰하고 정리할 수 있다.

## 8. Controller·Service·DAO 경계

| 계층 | 책임 | 선후처리와의 관계 |
|---|---|---|
| Controller | 서비스 ID 수신, 흐름 제어, DTO 전달·집계 | 업무 Hook을 호출하거나 프레임워크 호출에 참여 |
| Service | 비즈니스 규칙과 트랜잭션 작업 | 업무 선후처리에서 검증할 핵심 결과 생성 |
| DAO | SQL 실행과 결과 매핑 | 선후처리 정책을 알지 않아야 함 |
| DB 테이블 | 영속 상태 보관 | `TB_MPCMA*`, `TB_BLCRE*`처럼 업무 소유권 표현 |

Controller나 DAO가 시스템·공통 처리기를 직접 호출하면 실행 순서가 깨질 수 있다. 프레임워크 디스패처가 범위 메타데이터를 해석해 Hook을 조합하고 호출해야 한다.

## 9. 구현 모델

### 9.1 범위 메타데이터 예시

```yaml
serviceId: mp.cm.a.0001
applicationGroup: MP
application: CM
function: A
controllerMethod: mpcoaController.service0001
hooks:
  system: required
  common: campaignCommonPolicy
  business: campaignCreatePolicy
transaction:
  readOnly: false
  timeoutSeconds: 5
```

### 9.2 Hook 계약 예시

```java
interface ProcessingHook<I, O> {
    Scope scope();
    int order();
    void before(I input, TransactionContext context);
    void after(I input, O output, TransactionContext context);
}
```

Hook은 상태 없는 컴포넌트로 구현하고 거래별 데이터는 `TransactionContext`에 저장한다. 공유 인스턴스 필드에 요청 상태를 보관하면 동시성 오류가 발생한다.

## 10. 트랜잭션 및 예외 처리

### 10.1 권장 경계

```text
System Before(인증·파싱)
  → Transaction Begin
    → Common Before
    → Biz Before
    → Main Service/DAO
    → Biz After
    → Common After
  → Commit 또는 Rollback
System After(응답·로그·자원 해제)
```

공통·업무 후처리가 완료조건을 검증한다면 Commit보다 앞에 있어야 한다. 로그와 자원 해제는 트랜잭션 성공 여부와 무관하게 실행한다.

### 10.2 예외 정책

| 발생 위치 | 기본 정책 |
|---|---|
| 시스템 선처리 | 본처리 미실행, 표준 시스템 오류 응답 |
| 공통/업무 선처리 | 본처리 미실행, 업무 또는 정책 오류 응답 |
| Service/DAO | Rollback, 표준 업무·DB 오류 변환 |
| 업무/공통 후처리 | 완료조건 실패 시 Rollback |
| 시스템 후처리 | 원 예외 보존, 정리 예외 별도 기록 |

후처리 실패를 경고로 끝낼지 Rollback할지는 Hook별로 명시하며 암묵적으로 처리하지 않는다.

## 11. 관측성·보안·성능

### 11.1 관측성

모든 로그와 span에 다음 범위 키를 남긴다.

```text
traceId / serviceId / applicationGroup / application / function
hookType / hookName / executionOrder / elapsedMs / resultCode
```

이를 통해 `MP` 전체 장애인지, `CM` 공통 처리 장애인지, `A` 기능 또는 단일 서비스 장애인지 즉시 구분할 수 있다.

### 11.2 보안

- 인증·기본 권한은 시스템 선처리에서 강제한다.
- 애플리케이션 공통 권한은 공통 선처리에서 검사한다.
- 객체 수준 권한은 업무 선처리 또는 Service에서 검사한다.
- 입력·출력 로그는 범위와 무관하게 민감정보를 마스킹한다.
- 하위 정책이 상위 보안 정책을 비활성화하지 못하게 한다.

### 11.3 성능

중첩 Hook은 모든 거래에 누적 비용을 만든다. 각 Hook의 p95/p99 수행시간, DB 호출 수, 캐시 적중률을 측정하고 조회 전용 거래에서는 불필요한 Hook을 등록하지 않는다.

## 13. 구조적 장점과 위험

### 장점

- 업무 분류 체계와 런타임 정책 범위가 일치한다.
- 시스템·애플리케이션·기능별 공통성을 단계적으로 재사용한다.
- 변경 영향 범위와 정책 소유팀을 명확히 할 수 있다.
- Controller·Service·DAO 업무 코드를 횡단 관심사에서 분리한다.
- 신규 애플리케이션 그룹에도 동일한 실행 모델을 적용할 수 있다.

### 위험

- 중첩 범위가 많아지면 실제 실행 경로가 코드만으로 보이지 않는다.
- 상위 처리기에 업무별 조건문이 누적되면 변경 영향이 폭발한다.
- 동일 검증을 시스템·공통·업무에서 중복 수행할 수 있다.
- Hook 순서와 실패 정책이 불명확하면 환경별 결과가 달라진다.
- 공통 후처리의 외부 부수효과가 DB Commit과 불일치할 수 있다.

## 14. 개선 권고

### 우선순위 1 — 범위 레지스트리 구축

서비스 ID별 애플리케이션 그룹·애플리케이션·기능·Controller 메서드·Hook을 단일 메타데이터로 관리한다.

### 우선순위 2 — 공통화 승인 기준 운영

시스템 또는 공통 Hook 추가 시 적용 대상, 성능 영향, 실패 정책, 소유팀, 롤백 방안을 검토한다.

### 우선순위 3 — 실행 계획 가시화

배포 시 서비스별 최종 실행 체인을 출력한다.

```text
mp.cm.a.0001
  SystemBefore[auth, tracing, tx]
  CommonBefore[campaignPolicy]
  BizBefore[createValidation]
  Main[mpcoaController.service0001]
  BizAfter[createReconcile]
  CommonAfter[campaignAudit]
  SystemAfter[commit, response, cleanup]
```

### 우선순위 4 — 외부 부수효과 분리

메시지·알림·외부 API 호출은 Outbox, 멱등키, 커밋 후 이벤트를 활용해 DB 상태와 일치시킨다.

### 우선순위 5 — 단계별 SLO 관리

Hook별 지연시간 예산을 설정하고 공통 처리 추가가 그룹 전체 SLO에 미치는 영향을 사전에 검증한다.

## 15. FACT·ANALYSIS·확인 필요

### FACT — 그림에서 직접 확인되는 내용

- 애플리케이션 그룹, 애플리케이션, 기능, Controller/Service/DAO/DB의 중첩 구조다.
- 마케팅플랫폼은 `MP → CM → A`, BI포털은 `BL → CR → E` 예시를 사용한다.
- 시스템 선·후처리는 애플리케이션 그룹, 공통 선·후처리는 애플리케이션, 업무 선·후처리는 기능 내부를 감싼다.
- 마케팅 예시는 복수 메서드·Service·DAO, BI포털 예시는 단일 흐름을 보여준다.
- 업무 테이블 예시는 각각 `TB_MPCMA*`, `TB_BLCRE*`로 표시된다.

### ANALYSIS — 구조로부터 도출한 해석

- 범위가 중첩된 Template Method/Interceptor Chain 구조다.
- 하위 거래는 상위 범위 정책을 상속·합성한다.
- Before는 바깥에서 안쪽, After는 안쪽에서 바깥 순으로 실행하는 것이 자연스럽다.
- 분류 코드가 패키지 구조, 서비스 ID, 정책 적용 키의 공통 기반이 될 수 있다.

### 확인 필요

- 장표 제목의 `[Backup]`이 폐기안, 보충안 또는 현행 표준 중 무엇을 의미하는지
- 시스템·공통·업무 Hook의 실제 인터페이스와 등록 방식
- 기능 수준과 Controller 메서드 수준 업무 Hook의 구분 여부
- 동일 범위에 복수 Hook 등록 시 우선순위 규칙
- 후처리 실패 시 Rollback과 경고 처리 기준
- `TB_MPCMA*`, `TB_BLCRE*`가 실제 물리 테이블 접두어인지 개념 예시인지
- 읽기 전용 거래와 비동기 거래에도 동일한 범위가 적용되는지

## 16. 최종 평가

이 구조는 업무 분류 체계를 런타임 정책의 적용 범위로 직접 활용한다. 애플리케이션 그룹 수준의 시스템 안정성, 애플리케이션 수준의 업무 공통성, 기능·서비스 수준의 개별 거래 규칙을 중첩함으로써 재사용성과 업무 독립성을 함께 확보한다.

다만 성공 조건은 범위를 많이 만드는 데 있지 않다. **각 Hook의 소유 범위, 실행 순서, 실패 정책, 트랜잭션 참여 여부를 선언하고 최종 실행 체인을 가시화**해야 한다. 이 원칙을 지키면 마케팅플랫폼과 BI포털처럼 구조가 다른 업무도 동일 프레임워크 안에서 일관된 거래 통제와 유연한 업무 확장을 달성할 수 있다.
