# 물리기술아키텍처 — 시스템 표준 — 파일 시스템 구성 분석

## 1. 핵심 결론

장표는 Linux 서버의 표준 파일 시스템을 **OS Volume Group(`/dev/mapper/vg_os`) 아래의 시스템 영역과 업무·솔루션 영역**으로 구분하는 기준을 제시한다. 핵심 의도는 다음과 같다.

- 운영체제 핵심 디렉터리와 사용자·임시·로그·덤프 영역의 역할을 표준화한다.
- 업무 계정의 홈은 `/userdir`로 분리한다.
- WEB, WAS, 서버보안, 관제 등 시스템 소프트웨어는 별도의 소프트웨어 마운트 영역에 설치한다.
- 업무 특성에 따라 파일 시스템 명칭과 할당 위치를 조정할 수 있다.

다만 장표의 `Volume Group` 열이 모든 항목에 `/dev/mapper/vg_os`를 포괄 적용하는 모양으로 표현되어 있어, 이를 실제 블록 디바이스 매핑으로 그대로 해석해서는 안 된다. `/dev`, `/tmp` 일부, 런타임 영역은 가상·임시 파일시스템일 수 있고 `/boot`는 일반적으로 부팅 방식에 따라 LVM 외부 파티션으로 구성될 수 있다. 따라서 장표는 **논리적 표준 디렉터리 목록**으로 보고 실제 설계에서는 각 마운트의 소스 장치, 파일시스템 유형, 논리 볼륨 및 옵션을 별도로 확정해야 한다.

## 2. 장표 원문 전사

| Volume Group | Mount Point | 장표 설명 | 분류 |
|---|---|---|---|
| `/dev/mapper/vg_os` | `/` | root 디렉터리, 모든 디렉터리의 시작점 | OS 핵심 |
| `/dev/mapper/vg_os` | `/boot` | 부트 로더 디렉터리 | 부팅 |
| `/dev/mapper/vg_os` | `/etc` | 시스템 전역 설정 파일 | 설정 |
| `/dev/mapper/vg_os` | `/dev` | 시스템 디바이스(장치 파일) | 가상 장치 파일시스템 |
| `/dev/mapper/vg_os` | `/root` | root 계정 홈 디렉터리 | 관리자 홈 |
| `/dev/mapper/vg_os` | `/usr` | 일반 사용자를 위한 공통 파일 | OS 프로그램·공유 데이터 |
| `/dev/mapper/vg_os` | `/home` | 사용자 계정의 홈 디렉터리 | 일반 사용자 홈 |
| `/dev/mapper/vg_os` | `/tmp` | 임시 파일 저장소 | 임시 데이터 |
| `/dev/mapper/vg_os` | `/var` | 시스템 운용 중 생성되는 임시 데이터 및 로그 저장소 | 가변 데이터·로그 |
| `/dev/mapper/vg_os` | `/var/crash` | 시스템 덤프 파일 저장소 | 장애 덤프 |
| `/dev/mapper/vg_os` | `/userdir` | 업무 계정 홈 저장소 | 업무 사용자 홈 |
| `/dev/mapper/vg_os` | `/그 외 SW명` | WEB, WAS, 서버보안, 관제 등 시스템 소프트웨어 설치 디렉터리 | 솔루션 설치 영역 |

> 장표 주석: 업무 구분 및 특성에 따라 파일시스템 명명 규칙 및 할당 위치는 변경될 수 있다.

## 3. 논리 구성도

```text
Linux Server
└─ OS 저장영역 / vg_os
   ├─ /                  시스템 루트
   ├─ /boot              부트 로더·커널 관련 파일
   ├─ /etc               시스템 전역 설정
   ├─ /dev               장치 파일(devtmpfs 등, 실제 블록 LV와 구분)
   ├─ /root              root 계정 홈
   ├─ /usr               OS 프로그램·라이브러리·공유 파일
   ├─ /home              일반 사용자 홈
   ├─ /tmp               임시 데이터
   ├─ /var               로그·캐시·스풀·가변 데이터
   │  └─ /var/crash      커널/시스템 덤프
   ├─ /userdir           업무 계정 홈
   └─ /<SW명>            WEB·WAS·보안·관제 솔루션 설치/운영 영역
```

물리 구현은 다음과 같이 이해해야 한다.

```text
Physical/Virtual Disk
  ├─ EFI/boot partition ─────────────> /boot 또는 /boot/efi
  └─ LVM PV
      └─ VG: vg_os
          ├─ LV: root  ──────────────> /
          ├─ LV: var   ──────────────> /var
          ├─ LV: crash ──────────────> /var/crash
          ├─ LV: tmp   ──────────────> /tmp
          ├─ LV: user  ──────────────> /userdir
          └─ LV: sw_*  ──────────────> /<SW명>

Kernel-managed pseudo filesystems
  ├─ devtmpfs/udev ──────────────────> /dev
  ├─ proc ───────────────────────────> /proc
  ├─ sysfs ──────────────────────────> /sys
  └─ tmpfs ──────────────────────────> /run (필요 시 /tmp)
```

위 구성은 권장 해석 예이며 실제 LV 분리 여부와 명칭은 서버 역할·용량·복구 정책에 따라 결정한다.

## 4. 마운트 포인트별 상세 분석

### 4.1 `/` — 루트 파일 시스템

- 모든 경로의 최상위이며 부팅에 필요한 최소 OS 파일을 포함한다.
- 별도 마운트가 실패해도 유지보수 모드로 진입할 수 있도록 필수 도구를 보유해야 한다.
- 업무 데이터나 대용량 로그를 루트에 저장하면 용량 고갈이 시스템 전체 장애로 확대된다.
- `/var`, `/tmp`, `/userdir`, 소프트웨어 데이터 영역의 분리는 루트 보호 관점에서 중요하다.

### 4.2 `/boot` — 부팅 영역

- 커널, initramfs, 부트로더 관련 파일을 저장한다.
- BIOS/UEFI, 암호화 및 LVM 지원 조건에 따라 별도 파티션이 필요할 수 있다.
- 장표의 `vg_os` 표시는 논리적 분류일 가능성이 높으므로 실제 디바이스는 설치 표준과 대조해야 한다.
- 불필요한 구형 커널을 정리하되 현재·직전 정상 커널을 보존한다.

### 4.3 `/etc` — 시스템 설정

- 네트워크, 계정, 서비스, 보안 정책 등 시스템 전역 설정을 포함한다.
- 일반적으로 `/`와 같은 파일시스템에 두며 별도 마운트로 분리하지 않는 경우가 많다.
- 설정 백업, 형상관리, 변경 승인 및 무결성 감시 대상이다.
- 비밀번호 해시, 인증 키 등 민감 파일의 권한을 엄격히 통제한다.

### 4.4 `/dev` — 장치 파일

- 커널과 udev가 관리하는 블록·문자 장치 노드를 제공한다.
- 일반적인 영구 LVM 데이터 파일시스템이 아니라 `devtmpfs` 계열의 가상 파일시스템이다.
- 임의 백업·복사·용량 증설 대상이 아니며 마운트 상태와 udev 동작을 점검한다.

### 4.5 `/root` — 관리자 홈

- root 계정의 스크립트와 관리 파일을 저장한다.
- 개인 업무 데이터나 공용 배포 파일 저장소로 사용하지 않는다.
- 최소 권한과 강한 감사 정책을 적용하고 비밀키·인증정보의 평문 방치를 금지한다.

### 4.6 `/usr` — OS 프로그램 및 공유 파일

- 실행 파일, 라이브러리, 공통 읽기 전용 데이터의 주요 위치다.
- 장표의 “일반사용자를 위한 공통 파일”은 넓은 의미의 설명이며 사용자 문서 저장소로 해석하면 안 된다.
- 패키지 관리자를 통한 변경을 원칙으로 하고 수동 설치 파일은 `/opt` 또는 표준 SW 영역을 권장한다.

### 4.7 `/home` — 일반 사용자 홈

- OS 일반 계정의 홈을 제공한다.
- 업무 서비스 계정은 장표상 `/userdir`를 사용하므로 `/home`과 책임 범위를 구분해야 한다.
- 실행파일 허용 여부, 쿼터, 백업 및 장기 미사용 계정 정리 정책이 필요하다.

### 4.8 `/tmp` — 임시 파일

- 프로세스 간 임시 파일과 단기 작업 데이터를 저장한다.
- 다중 사용자가 쓰는 영역이므로 sticky bit(`1777`)와 심볼릭 링크 공격 방어가 중요하다.
- 가능하면 `nodev,nosuid,noexec` 옵션을 검토하되, 설치 프로그램 등 실행 요구가 있는지 사전 검증한다.
- 정리 주기, 최대 사용량, tmpfs 사용 시 메모리 압박을 함께 관리한다.

### 4.9 `/var` — 로그 및 가변 데이터

- `/var/log`, 캐시, 스풀, 패키지 상태, 애플리케이션 런타임 데이터가 증가한다.
- 로그 폭증이 루트 장애로 전파되지 않도록 별도 LV 분리가 효과적이다.
- `logrotate`/journald 보존, 중앙 로그 전송, 사용량 임계치 및 inode 감시가 필요하다.
- 컨테이너 런타임이나 에이전트가 `/var`를 대량 사용한다면 별도 하위 파일시스템을 검토한다.

### 4.10 `/var/crash` — 시스템 덤프

- kdump 등의 커널 크래시 덤프를 저장한다.
- 덤프는 메모리 크기에 비례해 매우 클 수 있으므로 RAM 용량, 압축률, 보존 세대를 기준으로 산정한다.
- `/var`와 같은 파일시스템이면 덤프 생성이 로그 영역을 고갈시킬 수 있어 별도 LV가 바람직하다.
- 민감정보가 포함될 수 있으므로 접근 통제·암호화·반출 승인 정책을 적용한다.

### 4.11 `/userdir` — 업무 계정 홈

- 업무 서비스 계정의 홈과 운영 스크립트를 일반 사용자 홈에서 분리한다.
- 계정별 디렉터리, 소유권, umask, 쿼터, 백업·복구 기준을 표준화해야 한다.
- 배포 바이너리, 로그, 데이터, 비밀정보를 한 디렉터리에 혼합하지 않는다.
- 서비스 중단 없이 증설·복구할 수 있도록 별도 LV 구성의 우선순위가 높다.

### 4.12 `/<SW명>` — 시스템 소프트웨어 영역

- WEB, WAS, 서버보안, 관제 등 솔루션별 설치 디렉터리를 의미한다.
- 실제 표준 경로는 제품명이 아니라 기능·소유조직·수명주기를 고려해 결정한다.
- 권장 내부 분리는 `app`, `config`, `logs`, `data`, `tmp`, `backup` 등이다.
- 설치 바이너리와 변경 데이터의 백업·복구 방식이 다르므로 같은 파일시스템에 무분별하게 혼합하지 않는다.

## 5. 권장 영역 분리 모델

| 영역 | 권장 분리 수준 | 이유 |
|---|---|---|
| `/` | 필수 | OS 핵심 영역 보호 |
| `/boot` 또는 `/boot/efi` | 설치 방식에 따라 필수 | 부트로더 요구사항 |
| `/var` | 높음 | 로그·캐시 폭증의 루트 전파 방지 |
| `/var/crash` | 높음 | 대용량 덤프 격리 |
| `/tmp` | 높음 | 임시 데이터 고갈·보안 위험 격리 |
| `/home` | 계정 사용 시 권장 | 사용자 데이터 격리·쿼터 |
| `/userdir` | 높음 | 업무 계정 데이터의 증설·백업 독립성 |
| `/<SW명>` | 서비스 중요도에 따라 높음 | 배포·로그·데이터 수명주기 분리 |
| `/etc`, `/root`, `/usr` | 보통 `/`에 포함 | 부팅·패키지 정합성과 단순성 |
| `/dev` | LV 분리 대상 아님 | 커널 관리 가상 파일시스템 |

### 권장 논리 볼륨 예시

```text
vg_os
├─ lv_root       → /
├─ lv_var        → /var
├─ lv_crash      → /var/crash
├─ lv_tmp        → /tmp
├─ lv_home       → /home          (필요 시)
├─ lv_userdir    → /userdir
└─ lv_<swname>   → /<SW명>        (솔루션별 또는 역할별)
```

VG에 미할당 여유 공간을 남기면 장애 시 긴급 증설이 쉬워진다. 다만 여유율은 서버별 총 디스크, 성장률과 스토리지 증설 방식에 따라 정해야 한다.

## 6. 용량 산정 원칙

장표에는 용량 수치가 없으므로 다음 산식으로 별도 산정해야 한다.

```text
요구 용량 = 초기 설치량
          + (일 증가량 × 보존 일수)
          + 업그레이드/롤백 여유
          + 장애·덤프 버퍼
          + 운영 안전 여유
```

| 영역 | 주요 산정 요소 |
|---|---|
| `/` | OS·패키지 설치량, 커널 업그레이드, 패치 임시 공간 |
| `/var` | 일 로그량, 보존 기간, journald, 패키지 캐시, 에이전트 데이터 |
| `/var/crash` | 물리 메모리 크기, 덤프 압축률, 동시/보존 세대 |
| `/tmp` | 최대 동시 작업 임시량, 설치·압축·정렬 작업 피크 |
| `/userdir` | 계정 수, 계정별 쿼터, 스크립트·산출물 증가량 |
| `/<SW명>` | 설치본, 배포본 세대, 로그·데이터·백업 분리 여부 |

평균 사용량보다 **피크 사용량과 증가 속도**를 기준으로 하며 inode 소진 가능성도 함께 계산한다.

## 7. 파일시스템 및 마운트 옵션

실제 파일시스템 형식은 Linux 배포판 표준과 복구 요구에 따라 XFS 또는 ext4 등을 선택한다.

| 영역 | 검토할 옵션 | 주의사항 |
|---|---|---|
| `/` | 기본 안전 옵션 | 과도한 제한은 부팅·패키지 동작 방해 |
| `/boot` | `nodev`, `nosuid`, `noexec` 검토 | 부트로더·업데이트 호환성 검증 필요 |
| `/home`, `/userdir` | `nodev`, `nosuid`, 쿼터 | 사용자 실행 파일 요구 시 `noexec` 영향 검증 |
| `/tmp` | `nodev,nosuid,noexec` 검토 | WAS/설치 도구의 임시 실행 여부 확인 |
| `/var/crash` | `nodev,nosuid,noexec` 검토 | kdump 쓰기 및 분석 도구 호환성 확인 |
| `/<SW명>` | 역할별 최소 옵션 | 실행 바이너리가 있으면 `noexec` 사용 불가 |

마운트 옵션은 보안 기준을 기계적으로 적용하지 말고 애플리케이션 사전 테스트 후 확정한다.

## 8. 권한·보안 기준

- root 소유 시스템 영역과 서비스 계정 소유 업무 영역을 분리한다.
- `/tmp`는 sticky bit를 유지하고 정기 정리를 적용한다.
- `/etc`, `/boot`, 실행 바이너리에는 무결성 감시를 적용한다.
- `/userdir`와 솔루션 설정의 비밀정보는 최소 권한, 암호화 또는 Vault 연계를 적용한다.
- 일반 사용자가 시스템 소프트웨어 디렉터리에 쓰지 못하게 한다.
- 서비스별 umask와 그룹 권한을 정의하고 `777` 권한을 금지한다.
- 덤프·로그에 개인정보와 인증정보가 포함될 수 있으므로 보존·마스킹·반출 통제를 적용한다.

## 9. 백업·복구 및 변경 관리

| 데이터 유형 | 예시 | 권장 처리 |
|---|---|---|
| 재설치 가능한 OS 바이너리 | `/usr` | 이미지/패키지 기준 복구, 전체 파일 백업 최소화 검토 |
| 핵심 설정 | `/etc`, 솔루션 `config` | 형상관리 + 주기적 백업 + 변경 감사 |
| 업무 계정 데이터 | `/userdir` | 서비스 RPO/RTO에 따른 백업·복구 시험 |
| 로그 | `/var/log`, SW `logs` | 중앙 수집 후 로컬 보존 최소화 |
| 크래시 덤프 | `/var/crash` | 제한된 기간 보존, 필요 시 별도 반출 |
| 배포 바이너리 | SW `app` | 아티팩트 저장소에서 재배포 가능하게 관리 |
| 업무 데이터 | SW `data` | 별도 파일시스템과 서비스별 백업 정책 적용 |

`/etc/fstab`, LVM 변경, 파일시스템 확장은 표준 변경 절차와 재부팅 검증을 거쳐야 한다. 스냅샷은 백업 대체가 아니며 애플리케이션 정합성을 보장하는 방식으로 사용한다.

## 10. 모니터링 기준

### 필수 지표

- 파일시스템별 사용률과 가용 바이트
- inode 사용률
- 일/주 단위 증가율과 예상 고갈 시점
- read-only 재마운트 및 I/O 오류
- LVM PV/VG/LV 상태와 VG 여유 공간
- `/var`, `/tmp`, `/var/crash`, `/userdir`, SW 영역의 상위 사용 디렉터리
- 로그 회전 실패, 삭제됐으나 프로세스가 점유 중인 파일
- 마운트 누락 및 `/etc/fstab` 정의와 실제 마운트의 불일치

### 권장 경보

```text
주의: 사용률 70~80% 또는 예상 고갈 30일 이내
경고: 사용률 80~90% 또는 예상 고갈 14일 이내
위험: 사용률 90% 이상, inode 90% 이상, read-only/I/O 오류 발생
```

정확한 임계치는 영역별 증가 특성과 증설 소요시간을 반영한다. `/`, `/var`, `/tmp`는 같은 사용률이라도 업무 데이터 영역보다 낮은 임계치를 적용할 수 있다.

## 11. 프로비저닝 자동화 권고

```text
서버 역할 선택
  → 표준 파일시스템 프로파일 결정
  → 디스크/PV/VG/LV 생성
  → 파일시스템 포맷
  → 마운트 포인트·소유권 생성
  → /etc/fstab 등록
  → 마운트 옵션·SELinux 컨텍스트 적용
  → 용량·권한·재부팅 검증
  → CMDB·모니터링·백업 정책 등록
```

프로파일에는 최소한 다음 속성이 있어야 한다.

```yaml
mount_point: /userdir
source: /dev/mapper/vg_os-lv_userdir
filesystem: xfs
size_gb: <산정값>
owner: root
group: root
mode: '0755'
mount_options: defaults,nodev,nosuid
backup_policy: <정책ID>
monitoring_policy: <정책ID>
growth_owner: <담당조직>
```

## 12. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 모든 디렉터리를 단일 LV로 구성 | 로그·덤프 폭증이 루트 장애로 확산 | `/var`, `/tmp`, `/var/crash`, 업무 영역 분리 |
| 장표의 VG 표기를 실제 소스로 오해 | `/dev`, `/boot`의 부적절한 구성 | 실제 `findmnt`, `lsblk`, LVM 설계로 확정 |
| `/var/crash` 용량 부족 | 장애 시 핵심 덤프 미생성 | 메모리 기반 산정·사전 kdump 시험 |
| `/tmp` 무제한 사용 | 서비스 장애·보안 취약점 | 별도 영역, 정리 정책, 옵션·쿼터 검토 |
| 업무 홈과 SW 데이터 혼합 | 백업·권한·배포 복잡성 증가 | `/userdir` 및 SW 내부 역할별 분리 |
| 이름이 제품명에 종속 | 제품 교체 시 경로·자동화 변경 | 기능 중심 경로와 심볼릭 링크 정책 검토 |
| 마운트 누락 | 데이터가 루트 하위에 기록되어 장애 | 부팅 후 마운트 선검증 및 서비스 의존성 설정 |
| inode 고갈 미감시 | 여유 용량이 있어도 파일 생성 불가 | inode 지표 및 소파일 증가율 감시 |

## 14. 최종 평가

이 구성은 Linux 서버에서 OS, 사용자, 임시 데이터, 로그·덤프, 업무 계정 및 솔루션 설치 영역을 표준화하려는 기본 골격이다. 운영 안정성을 확보하려면 이를 단순 디렉터리 목록이 아니라 **독립 장애 도메인, 보안 경계, 용량 성장 단위, 백업·복구 단위**로 구체화해야 한다. 특히 `/dev`와 `/boot`의 실제 구현, `/var`·`tmp`·`crash` 분리, `/userdir` 및 솔루션 데이터의 수명주기 관리가 핵심 검증 대상이다.
