# 물리기술아키텍처 — 시스템 표준 — 서버 포트 현황 분석

## 1. 핵심 결론

장표는 서버 접속 및 서버 간 서비스에 필요한 방화벽 포트의 기준 목록을 제시한다. 총 17개 제품·서비스 항목 중 포트가 명시된 항목은 다음 5개다.

| 서비스 | 포트 | 핵심 용도 |
|---|---:|---|
| SSH/SFTP | `22` | 서버 관리 접속 및 파일 송수신 |
| Apache | `80` | WEB 서비스 |
| Tomcat | `8080` | WAS 서비스 |
| Oracle | 운영 `15310`, 개발 `1531` | DBMS Listener 서비스 |
| GitLab | `80`, `443` | 소스 저장소 HTTP/HTTPS 서비스 |

나머지 12개 제품은 장표에서 포트가 공란이다. 이는 “포트를 사용하지 않는다”는 뜻이 아니라 **제품 구성, 설치 모드, 버전, 환경 및 연계 방식에 따라 확정해야 하는 미정 항목**으로 해석해야 한다. 보안을 위해 인터넷상의 일반적인 기본 포트를 장표 값인 것처럼 임의 기입하지 않고, 실제 설정 파일·리스닝 소켓·제품 설계서·방화벽 정책을 대조하여 등록해야 한다.

또한 포트 목록만으로 방화벽 정책을 만들 수 없다. 최소한 출발지, 목적지, 프로토콜, 포트, 방향, 환경, 용도, 소유자, 유효기간을 포함해야 한다.

```text
방화벽 정책 = Source + Destination + Protocol + Port
             + Direction + Environment + Purpose
             + Owner + Validity + Approval
```

## 3. 네트워크 계층별 해석

```text
관리자/운영망
   └─ TCP 22 ───────────────> Linux 서버 SSH/SFTP

사용자/채널 또는 L4
   └─ TCP 80/443 ───────────> Apache WEB / GitLab

WEB 계층
   └─ TCP 8080 ─────────────> Tomcat WAS

WAS·배치·ETL·BI 계층
   └─ TCP 15310(운영)
      TCP 1531(개발) ───────> Oracle Listener

제품 간 연계
   └─ 미기재 포트 ──────────> 제품별 실제 구성 확인 필요
```

포트는 가능하면 직접 외부에 노출하지 않고 계층별 통신 경로를 고정한다. 예를 들어 Tomcat `8080`은 WEB/L4에서만, Oracle Listener는 승인된 WAS·배치·ETL·관리 서버에서만 접근하게 한다.

## 4. 명시 포트 상세 분석

### 4.1 SSH/SFTP — TCP 22

#### 용도

- 운영자의 SSH 원격 관리
- SFTP 기반 파일 송수신
- 자동화·배포 도구의 제한된 원격 작업

#### 통제 원칙

- 인터넷이나 전체 업무망에 개방하지 않고 Bastion/PAM/관리망 출발지만 허용한다.
- root 직접 로그인을 차단하고 개인 계정·MFA·승인된 역할 전환을 사용한다.
- 비밀번호 인증보다 개인 SSH 인증서 또는 관리형 키를 우선한다.
- SFTP 계정은 필요 시 chroot, 읽기/쓰기 경로, 명령 실행을 제한한다.
- 관리 SSH와 대량 파일전송을 같은 계정·정책으로 운영하지 않는다.
- 실패 로그인, 비정상 원천, 키 변경 및 세션 명령을 중앙 감사한다.

### 4.2 Apache — TCP 80

#### 용도

장표상 WEB 서버 서비스 포트다.

#### 위험과 권고

- `80`은 평문 HTTP이므로 인증정보·개인정보·세션 데이터가 노출될 수 있다.
- 사용자 서비스는 원칙적으로 TLS `443`으로 제공하고 `80`은 HTTPS 리다이렉트 또는 내부 헬스체크 등 제한된 목적으로 사용한다.
- TLS 종료 위치가 L4/L7, Reverse Proxy 또는 Apache 중 어디인지 명시한다.
- 외부 접근은 WAF·L7·Reverse Proxy를 경유하고 WEB 서버 직접 접근을 제한한다.
- 관리 URL과 상태 페이지는 별도 접근제어를 적용한다.

### 4.3 Tomcat — TCP 8080

#### 용도

장표상 WAS 서버 서비스 포트다.

#### 통제 원칙

- 외부 사용자나 채널이 Tomcat에 직접 접근하지 않고 WEB/L4/API Gateway를 경유하게 한다.
- 출발지는 승인된 Apache·L4·연계 서버로 최소화한다.
- Tomcat Manager, JMX, AJP 등 관리·보조 포트는 서비스 포트와 별도 관리한다.
- WEB–WAS 구간도 민감도가 높으면 TLS 또는 mTLS를 적용한다.
- 다중 인스턴스가 한 서버에 있으면 포트 중복 방지와 인스턴스별 관리 대장이 필요하다.

### 4.4 Oracle — 운영 TCP 15310 / 개발 TCP 1531

장표는 운영 DBMS 포트를 `15310`, 개발환경 서비스 포트를 `1531`로 구분한다. 둘 다 일반적으로 널리 알려진 Oracle 기본 Listener 포트와 다른 사용자 정의 값이므로 실제 `listener.ora`, SCAN Listener, Service 및 방화벽 정책을 확인해야 한다.

#### 접근 원칙

- 운영 `15310`은 운영 WAS·배치·ETL·BI 등 승인된 서버에서만 접근한다.
- 개발 `1531`은 개발 서버 그룹에 한정하고 운영 DB로의 우회 연결을 금지한다.
- DB VIP/SCAN과 개별 노드 IP 중 방화벽 목적지를 서비스 설계에 맞게 등록한다.
- RAC 환경에서는 SCAN, Local Listener, 노드 간 클러스터 통신을 업무 Listener와 구분한다.
- DB 관리 포트와 애플리케이션 서비스 포트를 분리한다.
- TLS Native Network Encryption 또는 mTLS 적용 가능성을 검토한다.

### 4.5 GitLab — TCP 80 / 443

#### 용도

- GitLab Web UI와 HTTP(S) 기반 Git 접근
- API, Webhook, CI/CD 연계

#### 통제 원칙

- 운영 표준은 `443` HTTPS를 사용하고 `80`은 리다이렉트로 제한한다.
- GitLab Runner에서 GitLab로의 통신 방향과 Webhook의 역방향 통신을 각각 등록한다.
- SSH 방식 Git을 사용하면 별도 SSH 포트가 필요할 수 있으나 장표에는 기재되지 않았으므로 실제 설정을 확인한다.
- Container Registry, Package Registry, Pages 등 부가 기능의 별도 포트를 사용한다면 추가 등록한다.
- 관리자 UI는 일반 사용자 UI보다 강한 접근제어와 MFA를 적용한다.

## 5. 미기재 제품 포트 관리

미기재 항목은 다음 절차로 실제 포트를 확인한다.

```text
제품/연계 식별
  → 논리 아키텍처의 호출 방향 확인
  → 제품 설치·네트워크 설계서 확인
  → 설정 파일 및 서비스 정의 확인
  → 서버 listening socket 확인
  → 방화벽·L4·DNS 현행 정책 대조
  → 패킷/접속 시험
  → 소유자 승인
  → CMDB·포트 대장 등록
```

### 확인 근거의 우선순위

1. 실제 운영 설정과 승인된 구성관리 저장소
2. 해당 버전의 제품 설치·네트워크 설계서
3. 현재 서버의 `ss -lntup`, systemd, 컨테이너·Kubernetes Service 설정
4. 방화벽·L4·WAF·보안그룹의 현행 정책
5. 제품 기본값 문서

제품 기본 포트는 실제 설정이 변경될 수 있으므로 참고값일 뿐 최종 근거가 아니다.

## 6. 방화벽 정책 데이터 모델

단순 `제품–포트` 표 대신 다음 속성을 가진 정책 객체로 관리한다.

| 속성 | 예시 | 설명 |
|---|---|---|
| Rule ID | `FW-APP-0001` | 변경·감사 추적용 식별자 |
| 환경 | 운영/개발/DR | 정책 적용 환경 |
| 출발지 | WEB 서버 그룹 | IP보다 CMDB 서버 그룹 우선 |
| 목적지 | WAS VIP/서버 그룹 | 서비스 엔드포인트 |
| 방향 | Inbound/Outbound | 연결 개시 방향 |
| 프로토콜 | TCP/UDP | 전송 계층 |
| 목적지 포트 | `8080` | 서버 Listener 포트 |
| 출발지 포트 | Ephemeral | 특별 요구가 없으면 고정하지 않음 |
| 암호화 | TLS/mTLS/SSH | 전송 보호 방식 |
| 용도 | WEB→WAS 서비스 호출 | 업무 목적 |
| 소유자 | 시스템/보안 담당 | 승인·재인증 책임 |
| 유효기간 | 시작·만료일 | 임시 정책 자동 회수 |
| 근거 | 설계서/변경번호 | 승인 추적 |

### 예시 정책

```yaml
- rule_id: FW-WEB-WAS-8080
  environment: production
  source_group: approved_apache_web
  destination_group: approved_tomcat_was
  protocol: tcp
  destination_port: 8080
  direction: outbound_from_web
  purpose: web_to_was_service
  action: allow
  owner: <시스템담당>
  expires: null

- rule_id: FW-WAS-DB-15310
  environment: production
  source_group: approved_app_clients
  destination_service: oracle_scan_or_vip
  protocol: tcp
  destination_port: 15310
  purpose: oracle_db_service
  action: allow
  owner: <DB담당>
```

## 7. 권장 통신 매트릭스

| 출발지 | 목적지 | 포트 | 허용 원칙 |
|---|---|---:|---|
| PAM/Bastion/관리망 | Linux 서버 | TCP 22 | 개인 인증·승인된 관리 대상만 |
| 사용자/L4/WAF | Apache WEB | TCP 443 권장, 80 제한 | 외부 노출은 보안 계층 경유 |
| Apache/L4 | Tomcat WAS | TCP 8080 | WEB 서버 그룹만 |
| WAS·배치·ETL·BI | Oracle 운영 Service | TCP 15310 | 승인된 업무 클라이언트만 |
| 개발 AP·도구 | Oracle 개발 Service | TCP 1531 | 개발 서버 그룹만 |
| 개발자·Runner | GitLab | TCP 443, 80 리다이렉트 | 인증·프로젝트 권한 적용 |
| GitLab Runner | 배포 대상/Nexus/Registry | 미확정 | Job과 Executor 유형별 최소 허용 |

정책의 기본값은 Deny이며 필요한 연결만 화이트리스트로 허용한다.

## 8. 운영·개발·DR 분리

- 운영 DB 포트 `15310`과 개발 DB 포트 `1531`을 방화벽 객체와 모니터링에서 구분한다.
- 개발 서버가 운영 DB 포트에 접근하는 예외는 원칙적으로 금지하고, 불가피하면 기간·계정·쿼리 권한을 제한한다.
- DR 전환 시 목적지 IP/VIP가 바뀌어도 서비스 객체 또는 DNS 기반 정책이 일관되게 작동하는지 시험한다.
- 운영과 DR 간 복제·상태 동기화 포트는 사용자 서비스 포트와 별도 정책으로 관리한다.
- DR 정책은 평상시 차단/대기인지 상시 허용인지 복구 절차에 명시한다.
- 동일 포트 번호라도 환경별 소유자와 위험 수준을 독립 평가한다.

## 9. 암호화와 인증

| 구간 | 현재 장표 포트 | 권고 |
|---|---:|---|
| 관리 SSH/SFTP | 22 | SSH 인증서/관리형 키, MFA·PAM |
| HTTP WEB | 80 | 443 TLS로 전환 또는 리다이렉트 전용 |
| WEB–WAS | 8080 | 내부 제한, 필요 시 TLS/mTLS |
| AP–Oracle | 15310/1531 | DB 암호화·서버 인증서·Wallet 검토 |
| GitLab | 80/443 | 443 강제, 신뢰 체인·인증서 자동 갱신 |

포트 변경만으로 보안이 강화되는 것은 아니다. 비표준 포트는 스캐닝 노출을 조금 줄일 수 있으나 인증, 암호화, 최소 허용 원천과 취약점 관리가 핵심 통제다.

## 10. 서버 로컬 방화벽과 네트워크 방화벽

```text
Client
  → Network Firewall / Security Group
    → L4/L7/WAF (해당 시)
      → Host Firewall
        → Listening Process
```

모든 계층의 정책이 일치해야 한다.

- 네트워크 방화벽은 시스템·Zone 간 접근을 통제한다.
- 보안그룹은 IaaS 인스턴스 단위의 동적 자산을 통제한다.
- Host Firewall은 서버에서 최종 수신 포트를 제한한다.
- 애플리케이션 인증은 네트워크 연결 이후 사용자·서비스 권한을 검증한다.
- L4 헬스체크와 모니터링 포트는 서비스 트래픽과 별도 원천으로 등록한다.

## 11. 포트 충돌과 다중 인스턴스

한 서버에 여러 Tomcat, Kafka Broker, Agent 또는 개발 도구 인스턴스를 구성하면 포트 충돌이 발생할 수 있다.

```text
포트 할당 키 = 환경 + 서버/컨테이너 + 제품 + 인스턴스 + 프로토콜
```

- 동일 IP의 같은 TCP/UDP 포트를 두 프로세스가 동시에 바인딩하지 못한다.
- 인스턴스별 서비스·관리·JMX·Shutdown 포트 세트를 함께 예약한다.
- 컨테이너 내부 포트와 Host/Service/Ingress 노출 포트를 구분한다.
- 포트 범위를 임의로 증가시키지 않고 중앙 포트 레지스트리에서 할당한다.
- 폐기 포트는 방화벽·L4·모니터링·문서에서 함께 회수한다.

## 12. 모니터링과 감사

### 서버 측

- 승인된 포트와 실제 Listening Socket의 차이
- 프로세스명·PID·실행 계정·바인딩 IP
- `0.0.0.0`/`::` 전체 인터페이스 바인딩 여부
- 미승인 신규 포트와 승인 포트의 서비스 중지
- TLS 인증서 만료·프로토콜·암호군
- 접속 실패율, 비정상 원천 및 대량 스캔

### 네트워크 측

- 허용·차단 로그와 정책 Hit Count
- 장기간 미사용 정책
- Any Source/Destination/Port 규칙
- 임시 정책 만료와 예외 재승인
- 운영–개발–DR 간 비정상 교차 접속
- 방화벽 정책과 CMDB 서비스 관계의 불일치

### 정합성 검사

```text
승인 포트 대장
   ↕ 비교
서버 Listening Socket
   ↕ 비교

   ↕ 비교
Network Firewall / L4 / WAF
   ↕ 비교

```

## 13. 변경 및 수명주기 관리

```text
포트 요청
  → 업무 흐름·Source/Destination 확인
  → 기존 포트 중복·보안 영향 검토
  → 제품 설정 반영
  → 방화벽/L4/Host 정책 반영
  → 연결·암호화·Failover 시험
  → CMDB/포트 대장 등록
  → 정기 재인증
  → 서비스 폐기 시 전 계층 정책 회수
```

임시 포트는 만료일을 필수로 두고, 폐기된 서비스의 잔존 방화벽 규칙을 자동 탐지한다.

## 16. 최종 평가

장표는 SSH, WEB, WAS, Oracle 및 GitLab의 핵심 포트를 명시하지만 전체 17개 항목 중 12개가 공란이므로 그대로는 완전한 서버 간 방화벽 기준으로 사용할 수 없다. 실제 운영 표준으로 완성하려면 제품별 서비스·관리·클러스터·연계 포트를 실구성에서 수집하고, 이를 **출발지–목적지–방향–환경–소유자 기반 화이트리스트 정책**으로 전환해야 한다. 가장 우선할 조치는 HTTP 80 최소화, Tomcat 8080 직접 노출 차단, Oracle 운영·개발 포트 분리 검증, 미기재 제품 포트의 현행화다.
