# 물리기술아키텍처 — 하드웨어 구성도 — 개발환경 분석

> 원본 범위: `3. 물리 기술 아키텍처 > 3.1 하드웨어 구성도`  
> 원본 페이지/이미지: 72쪽, `85737/26.png`  
> 분석 원칙: 장표의 역할명·노드 번호·배치를 확인 사실로 기록한다. 흐릿한 Hostname, 논리 인스턴스 구성, 개발 데이터 정책은 상세설계 확인사항으로 분리한다.

---

## 1. 핵심 결론

개발환경은 **의왕 센터(주 센터)** 한 곳에 마케팅, 실적/분석, 데이터거버넌스/운영관리, 저장소/DB를 배치한 축소형 물리 구성이다.

- 대부분의 WEB, WAS, AP가 `#1` 단일 노드다.
- 미니싱글뷰 WEB/WAS는 별도 서버 없이 마케팅플랫폼 WEB/WAS에 통합된다.
- 운영에서 분리된 ADW와 RDW가 개발에서는 `ADW/RDW DB Appliance #1,#2`로 통합된다.
- 단말개발도구, 소스관리, 라이브러리, ETL, 배치 등 개발·운영 지원 도구가 함께 배치된다.
- `원천 데이터 이행 영역/임시`에는 `SQL품질/이행 AP #1`이 별도로 표시된다.
- DR 센터와 센터 간 복제는 이 장표에 표시되지 않는다.

```text
                     의왕 센터(주 센터)
┌─────────────────────────────────────────────────────────────┐
│ 1) 마케팅: WEB/WAS + 실시간/행동정보/고객행동 AP            │
├─────────────────────────────────────────────────────────────┤
│ 2) 실적/분석: BI포탈 + 신용실적 + Self-BI                   │
├─────────────────────────────────────────────────────────────┤
│ 3) 거버넌스/운영관리: 메타·품질·흐름·RD·단말·배치·ETL·도구  │
│                         └─ 원천 데이터 이행 영역/임시        │
├─────────────────────────────────────────────────────────────┤
│ 4) 저장소/DB: 정보계 스토리지 + ADW/RDW Appliance #1,#2     │
├─────────────────────────────────────────────────────────────┤
│ 원천: 디지털금융 / 코어뱅킹 원천DB / 복제DB / FOS           │
└─────────────────────────────────────────────────────────────┘
```

## 2. 근거 수준

| 수준 | 내용 |
|---|---|
| 확인 사실 | 의왕 센터(주 센터)의 단일 센터 구성이 표시됨 |
| 확인 사실 | 마케팅, 실적/분석, 데이터거버넌스/운영관리, 저장소/DB 4개 영역이 표시됨 |
| 확인 사실 | 대부분의 개발 노드는 #1로 표시됨 |
| 확인 사실 | 미니싱글뷰 WEB/WAS의 마케팅플랫폼 서버 통합 주석이 표시됨 |
| 확인 사실 | ADW/RDW DB Appliance #1,#2와 정보계 스토리지가 표시됨 |
| 확인 사실 | SQL품질/이행 AP가 원천 데이터 이행 임시 영역에 표시됨 |
| 설계 해석 | 단일 노드는 비용·운영 단순화를 우선한 개발 전용 축소 구성으로 해석 |
| 설계 해석 | 통합 DB Appliance는 물리 자원 공유이며 논리 DB까지 통합됐다는 뜻은 아님 |
| 미확정 | 미니싱글뷰의 동일 JVM/별도 인스턴스 여부 |
| 미확정 | ADW/RDW의 DB·스키마·서비스·계정 분리 수준 |
| 미확정 | 일부 Hostname, CPU·Memory·Disk·NIC 사양 |
| 미확정 | 개발 데이터 마스킹·갱신·보존·폐기 정책 |

## 3. 전체 물리 계층

```text
[개발자/테스터]
        │
        ▼
[WEB 계층] ── [WAS 계층] ── [AP/도구 계층]
                               │
                               ├─ ETL/배치/이행
                               └─ JDBC/File/API
                                      │
                                      ▼
                    [ADW/RDW 통합 DB Appliance #1,#2]
                                      │
                              [정보계 스토리지]
                                      │
                       [원천 DB / 복제DB / FOS]
```

범례에는 AP, DB, WEB, WAS, ETL, 베어메탈, IaaS가 구분되어 있다. 장표상 대부분의 애플리케이션 노드는 IaaS 영역에 배치되며 DB Appliance는 별도 DB 자원으로 표현된다.

## 4. 마케팅 영역

| 역할 | 번호 | 수량 |
|---|---:|---:|
| 마케팅플랫폼 WEB | #1 | 1 |
| 마케팅플랫폼 WAS | #1 | 1 |
| 실시간처리 AP | #1 | 1 |
| 행동정보처리 AP | #1 | 1 |
| 고객행동데이터 AP | #1 | 1 |

```text
                ┌─ [마케팅플랫폼 기능]
[WEB #1] ─ [WAS #1]
                └─ [미니싱글뷰 기능: 동일 서버 통합]
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
[실시간처리 AP] [행동정보처리 AP] [고객행동데이터 AP]
       #1              #1               #1
```

### 통합 배치 해석

```text
물리 서버 통합
  ├─ WEB 서버 #1: 마케팅 WEB + 미니싱글뷰 WEB
  └─ WAS 서버 #1: 마케팅 WAS + 미니싱글뷰 WAS

확인 필요
  ├─ 동일 Process/JVM인가?
  ├─ 별도 Instance/Port인가?
  └─ CPU·Memory·Log·배포 단위가 분리되는가?
```

통합은 자원 절감에 유리하지만 한 기능의 메모리 누수·배포 실패·로그 폭증이 다른 기능에 영향을 줄 수 있다. 개발 편의 때문에 운영의 독립 배치 전제를 훼손하지 않도록 배포 산출물과 설정은 분리해야 한다.

## 5. 실적/분석 영역

| 역할 | 번호 | 수량 |
|---|---:|---:|
| BI포탈 WEB | #1 | 1 |
| BI포탈 WAS | #1 | 1 |
| 신용실적 WEB | #1 | 1 |
| 신용실적 WAS | #1 | 1 |
| Self-BI WEB | #1 | 1 |
| Self-BI WAS | #1 | 1 |
| Self-BI AP | #01 | 1 |

```text
[BI포탈 WEB #1] ───── [BI포탈 WAS #1] ─────┐
[신용실적 WEB #1] ─── [신용실적 WAS #1] ───┼─ ADW/RDW
[Self-BI WEB #1] ───── [Self-BI WAS #1] ────┤
                                └─ AP #01 ───┘
```

모든 노드가 단일 구성이라 HA 검증보다는 기능·연계·쿼리 회귀검증이 주 목적이다. 다만 단일 장애가 공동 개발을 중단시킬 수 있으므로 VM Snapshot, 자동 재배포, DB 복구 절차가 필요하다.

## 6. 데이터거버넌스/운영관리 영역

| 분류 | 역할 | 번호 |
|---|---|---:|
| 거버넌스 | 비즈메타/데이터품질 WAS | #1 |
| 거버넌스 | 데이터흐름관리 WAS | #1 |
| 출력 | 출력물(RD) WAS | #1 |
| 단말 | 단말관리 WEB/WAS | 각 #1 |
| 단말 | 단말배포 WEB/WAS | 각 #1 |
| 개발 | 단말개발도구 AP | #1 |
| 처리 | 배치 AP | #1 |
| 처리 | ETL AP | #1 |
| 형상 | 소스관리 AP | #1 |
| 제어 | 마스터솔루션 | #1 |
| 지원 | 라이브러리 | #1 |
| 관측 | UNO Dashboard | #1 |

물리 역할을 개별 자산으로 풀면 `단말관리 WEB`, `단말관리 WAS`, `단말배포 WEB`, `단말배포 WAS`가 각각 #1 노드로 구성된다.

```text
거버넌스: [비즈메타/품질 WAS] [데이터흐름관리 WAS]
업무지원: [RD WAS] [배치 AP] [ETL AP]
단말개발: [관리 WEB/WAS] [배포 WEB/WAS] [개발도구 AP]
개발통제: [소스관리 AP] [마스터솔루션] [라이브러리]
관측:     [UNO Dashboard]
                     모두 #1
```

### 개발 공급망

```text
개발자 → 소스관리 AP → Build/Test → 라이브러리/산출물
                │                    │
                └── 마스터솔루션 ────┤
                                     ▼
                         단말배포 WEB/WAS → 개발 단말
```

장표의 `라이브러리`가 물리 서버인지 논리 서비스인지 명확하지 않다. 저장소 제품, 불변성, 접근권한, 취약점 점검은 별도 확인해야 한다.

## 7. 원천 데이터 이행 영역/임시

```text
┌────── 원천 데이터 이행 영역/임시 ──────┐
│ [SQL품질/이행 AP #1]                   │
│   ├─ SQL 품질 검사                     │
│   └─ 이행 실행/검증                    │
└────────────────────────────────────────┘
```

### 목표 처리 흐름

```text
[원천DB/복제DB/FOS]
       │ 추출
       ▼
[SQL품질/이행 AP]
       │ 변환·검증·적재
       ▼
[ADW/RDW 개발 DB]
       │ 건수·합계·Hash 대사
       ▼
  승인 또는 재처리
```

임시 영역은 수명주기와 종료 기준을 가져야 한다. 테스트 데이터와 로그를 방치하면 개인정보·용량·비용 위험이 생긴다.

## 8. 저장소/DB

| 구성 | 번호 | 비고 |
|---|---:|---|
| 정보계 스토리지 | 미표시 | 공용 개발 저장소 |
| ADW/RDW DB Appliance | #1, #2 | 개발 통합 구성 |

```text
운영: [ADW Appliance #1~#6] + [RDW Appliance #1,#2]
                         ↓ 축소·통합
개발:       [ADW/RDW Appliance #1,#2]
```

### 권장 논리 격리

```text
ADW/RDW 공용 물리 Appliance
  ├─ ADW 서비스/DB/스키마/계정/Resource Group
  ├─ RDW 서비스/DB/스키마/계정/Resource Group
  └─ 공통 운영: Backup / Monitoring / Patch
```

물리 통합으로 인한 자원 경합을 막기 위해 CPU/IO/세션/동시 쿼리 한도와 Tablespace/Quota를 분리해야 한다. 개발 쿼리가 다른 팀 테스트를 방해하지 않도록 Resource Manager 정책이 필요하다.

---

## 9. 원천 시스템 연계

```text
[디지털금융] ─┐
[코어뱅킹 원천DB] ─┼─ 개발 수집/이행 ─ ADW/RDW
[코어뱅킹 복제DB] ─┤
[FOS] ─────────────┘
```

개발환경이 운영 원천에 직접 부하를 주지 않도록 복제DB·추출 파일·가상화 데이터 우선 원칙을 적용해야 한다. 운영 데이터 반입 시 비식별화, 승인, 목적 제한, 보존기간, 폐기가 필수다.

## 10. 개발 배포 경로

```text
Commit → Build → Unit Test → Artifact 생성 → 취약점 검사
 → 개발 WEB/WAS/AP 배포 → DB Migration → Smoke Test → 회귀 테스트
```

### DB 변경 경로

```text
DDL/DML Script → 정적검사 → 개발 ADW/RDW 적용
 → 호환성·성능·Rollback 검증 → 승인된 이행 산출물 생성
```

- 애플리케이션과 DB 변경은 동일 릴리스 ID로 추적한다.
- 통합 서버의 한 애플리케이션 배포가 다른 애플리케이션을 재기동하지 않도록 한다.
- 개발 전용 설정과 운영 설정의 차이는 코드가 아니라 환경 구성으로 관리한다.

## 11. 운영환경 대비 구조 차이

| 항목 | 개발 | 운영/DR |
|---|---|---|
| 센터 | 의왕 단일 | 의왕 운영 + 안성 DR |
| WEB/WAS | 대부분 각 1 | 운영 다중, 일부 DR 배치 |
| 미니싱글뷰 | 마케팅 서버 통합 | 별도 WEB/WAS |
| 실시간/행동 AP | 각 1 | 다중 노드 |
| 분석계 | 단일 노드 | 다중 WEB/WAS |
| 단말관리/배포 | 각 1 | 운영·DR 다중 노드 |
| ADW/RDW | 통합 Appliance #1,#2 | 역할별 분리 |
| 이행 | SQL품질/이행 AP #1 | 변환·이행·품질·추출 확장 |
| DR | 미표시 | GSLB/DCI/Data Guard |

```text
개발 목표: 빠른 변경·기능/계약 검증·저비용
운영 목표: 처리량·가용성·격리·복구

따라서 개발 단일 노드 성공 ≠ 운영 다중 노드 성공
```

## 12. 보안과 테스트 데이터

```text
운영 원천 → 승인 → 추출 → 비식별/마스킹 → 품질검사
        → 개발 적재 → 접근통제 → 사용기간 만료 → 폐기 증적
```

- 주민번호, 계좌번호, 연락처 등 직접 식별자는 원문 반입을 금지한다.
- 참조 무결성과 분포를 유지하는 일관된 가명처리가 필요하다.
- 개발자, 배치, ETL, 애플리케이션 계정을 분리한다.
- FOS 파일은 수신·검증·처리·보관·폐기 상태를 관리한다.
- 로그와 Dump에도 개인정보가 남지 않도록 한다.

## 13. 가용성·백업·복구

```text
단일 노드 장애
  → 모니터링 탐지 → VM/프로세스 재기동
  → 필요 시 IaC/배포 자동화로 재생성
  → 데이터 복구 → Smoke Test → 개발 재개
```

개발은 운영 수준의 HA가 없어도 될 수 있지만 복구 불가능해도 된다는 뜻은 아니다. 소스, Artifact, DB Schema, 기준 데이터, 환경 설정을 재생성 가능한 형태로 관리해야 한다.

| 자산 | 권장 복구 수단 |
|---|---|
| WEB/WAS/AP | 자동 배포, 이미지, 설정 저장소 |
| DB | 백업, Point-in-Time Recovery, Schema Migration |
| 소스/라이브러리 | 원격 복제, 불변 Artifact |
| 테스트 데이터 | 재생성 스크립트, 마스킹 파이프라인 |
| 이행 결과 | Checkpoint, 대사 결과, 재처리 키 |

## 14. 관측과 자원 통제

| 영역 | 지표 |
|---|---|
| WEB/WAS | 요청량, 오류율, JVM, Thread, Connection Pool |
| AP | 처리량, 큐 적체, 실패/재처리 |
| 통합 DB | CPU, IOPS, 세션, 서비스별 소비량, 장기 SQL |
| ETL/배치 | 실행시간, 성공률, Checkpoint, 중복 실행 |
| 이행 | 추출/적재 건수, 대사 차이, SQL품질 결과 |
| 스토리지 | 사용률, 증가율, Snapshot, 만료 데이터 |
| 개발 공급망 | 빌드·배포 성공률, Artifact 버전 불일치 |

```text
공용 자원 포화 → 소비 주체 식별 → 한도/우선순위 적용
              → 장기 쿼리 종료 → 원인 개선 → 재발 감시
```

5. SQL품질/이행 AP의 생성·사용·폐기 시점

## 17. 최종 평가

이 개발환경은 운영 시스템의 기능 영역을 모두 포함하되 노드 수와 물리 자원을 축소·통합한 구조다. 단일 노드, 미니싱글뷰 통합, ADW/RDW 통합은 비용과 관리 복잡도를 낮추지만 장애격리·성능 대표성·운영 동등성을 약화시킬 수 있다.

따라서 개발환경의 품질 기준은 운영 규모를 복제하는 것이 아니라 **동일한 배포 산출물·인터페이스·DB 변경·보안정책을 검증하면서 공유 자원과 테스트 데이터를 엄격히 격리하는 것**이다. 임시 이행 영역의 수명주기와 통합 DB의 자원 경계를 명확히 해야 운영 이행 위험을 줄일 수 있다.
