# 런타임 아키텍처 — 연계 업무 처리 유형 상세 분석

## 1. 핵심 결론

이 장표는 차세대 정보계 전체 런타임 아키텍처 중에서 **연계 업무 처리 유형**만을 확대하여 설명한 상세 장표다.

원본 장표의 상단 설명은 다음 의미를 가진다.

> **차세대 정보계 시스템과 대내 시스템, 대외기관, 농협은행 간 연계를 처리하는 업무 유형**

즉 이 장표의 초점은 **화면/채널 거래가 아니라 시스템 대 시스템(System-to-System) 연계**에 있다. 장표는 이를 다음 두 가지로 구분한다.

```text
④ 대내 시스템간 연계
⑤ 대외 시스템간 연계
```

핵심 메시지는 아래와 같다.

```text
정보계 Application
      ↓
API Gateway (Cruz APIM)
      ↓
대내 시스템 / 대외기관 / 농협은행 / 대외MCA / 인터페이스 시스템
```

또한 원본 우측 설명은 연계 처리의 기준을 비교적 명확하게 제시한다.

- 대내 시스템 연계는 **API Gateway(CruzAPIM)** 를 통해 처리
- 농협은행과 법인간 거래는 **GSE** 를 통해 처리
- 인터페이스 시스템간 연계는 **인터페이스 시스템 내부** 에서 처리
  - 예) **EAI → API Gateway**
  - 예) **API Gateway → EAI**
- 대외 시스템 연계는 **API Gateway(CruzAPIM)** 를 통해 처리
- 대외 인터페이스 연계는 **대외MCA ↔ API Gateway** 경로를 사용
- 통신 방식은 **동기(Sync), Json/Http, 요청/응답**

즉 이 장표는 차세대 정보계의 연계 구조를 **API Gateway 중심형 연계 아키텍처**로 정의하고, 농협은행용 **GSE**, 대외기관용 **대외MCA**, 내부 통합용 **EAI** 를 구분해 놓은 것이 핵심이다.

## 5.3 APIM / EAI / GSE 역할 분해

### API Gateway (Cruz APIM)

- 정보계의 **표준 대내 연계 관문**
- 서비스 호출의 **정책 집행 지점**
- 인증·라우팅·호출제어·모니터링 중심 가능성

### EAI

- 내부 인터페이스 시스템간 **연계/중재/변환** 성격
- 전문변환 또는 레거시 연계 처리 가능성
- 원본에서 `EAI → API Gateway`, `API Gateway → EAI` 예시 명시

### GSE

- **농협은행과 법인간 거래** 전용 연계 경로
- API Gateway와는 다른 목적의 별도 연계 채널
- 은행계 통합/그룹사 인터페이스 관문 역할 가능성

## 5.5 대내 연계의 아키텍처 의미

이 장표는 대내 연계를 단순 “API 호출”로 보지 않는다. 실제로는 다음 3가지 연계 경계를 구분한다.

```text
1) APIM 기반 일반 대내 시스템 연계
2) GSE 기반 농협은행/법인간 연계
3) EAI 기반 인터페이스 시스템 내부 연계
```

즉 후속 설계에서는 단순히 “대내연계” 하나의 표준으로 묶으면 안 되고, **연계 유형별 표준**을 분리해야 한다.

## 6.5 대외 연계의 아키텍처 의미

대외 연계는 대내 연계보다 보안과 가용성 요구가 더 강할 가능성이 높다.

### 주요 특성

- 외부 회선/기관 응답시간 의존
- 기관별 API 규격 상이 가능
- 장애 전파 위험 큼
- 인증/암호화/허용목록 관리 필요

### 설계적 시사점

- 대외기관 직접 호출을 애플리케이션에 흩어두지 말고 **APIM + 대외MCA** 경계에 집중해야 한다.
- 기관별 SLA / Timeout / Retry / Circuit Breaker 정책을 분리할 필요가 있다.

## 8. 정보계 내부 시스템과 연계의 관계

원본 좌측에는 연계 요청 주체가 단일 시스템이 아니라 다음과 같이 넓게 배치되어 있다.

```text
정보계 내부
 ├─ 어플리케이션 / 마케팅플랫폼
 │   ├─ 미니 싱글뷰 Service
 │   └─ 마케팅플랫폼 Service
 ├─ BI포탈
 │   ├─ BI Portal
 │   ├─ 신용실적 Service
 │   ├─ Self BI
 │   └─ OLAP
 ├─ 데이터거버넌스
 └─ 데이터플랫폼(RDW / ADW)
```

### 의미

연계는 특정 한 서비스만 수행하는 것이 아니라, **정보계 전반의 업무 기능과 데이터 활용 기능이 공통으로 의존하는 런타임 기반 기능**이다.

즉 APIM, EAI, GSE, 대외MCA는 **공통 연계 인프라**로 해석하는 것이 맞다.

## 9. 데이터플랫폼 / 파일연계와의 접점

비록 이 장표의 주제는 연계 업무 처리 유형이지만, 중앙 하단에는 다음이 함께 표시되어 있다.

- CDC
- JDBC / Database
- MFT
- FOS
- ETL
- RDW / ADW
- Legacy / Big Data

이는 연계 업무가 단순 온라인 API에만 국한되지 않고, **데이터 연계 및 파일 연계와 런타임적으로 연결**될 수 있음을 시사한다.

```text
Online System Integration
         │
         ├─ APIM / EAI / GSE / 대외MCA
```

다만 이 장표의 우측 설명은 ④·⑤를 **Sync / JSON/HTTP / 요청응답**으로 정의하므로, 본 문서에서는 ④·⑤의 핵심을 온라인 연계 관점으로 해석한다.

## 10. Timeout 계층 설계

연계 업무는 모두 동기 호출이므로 Timeout 계층 설계가 필수다.

```text
Caller Application Timeout
        >
API Gateway Timeout
        >
EAI / GSE / 대외MCA Timeout
        >
Target System Timeout
```

### 예시 원칙

- Application Timeout: 3초
- APIM Backend Timeout: 2.5초
- EAI / 대외MCA Timeout: 2.0초
- Target System Timeout: 1.5초

### 이유

상위 호출이 이미 종료된 뒤 하위 연계가 계속 살아 있으면 스레드 고갈, 좀비 처리, 중복 호출 위험이 발생할 수 있다.

## 20. 최종 평가

이 장표는 차세대 정보계의 연계 업무를 다음 두 축으로 표준화한다.

```text
④ 대내 시스템간 연계
⑤ 대외 시스템간 연계
```

구조적으로는 다음 원칙을 보여준다.

```text
정보계 내부 시스템
   ↓
API Gateway (Cruz APIM)
   ↓
[EAI | GSE | 대외MCA]
   ↓
대내 시스템 / 농협은행 / 대외기관
```

이 구조의 가장 중요한 아키텍처 기준은 다음과 같다.

1. **연계의 중심 관문은 API Gateway(Cruz APIM)이다.**
2. **대내 연계와 대외 연계를 분리한다.**
3. **농협은행 연계는 GSE라는 별도 경계로 다룬다.**
4. **인터페이스 내부 중재는 EAI와 대외MCA가 담당한다.**
5. **전체 연계는 동기식 JSON/HTTP 요청·응답 패턴을 따른다.**

후속 상세설계에서는 반드시 다음이 이어져야 한다.

```text
Caller System
   ↓
APIM Policy
   ↓
EAI / GSE / 대외MCA
   ↓
Target System Contract
   ↓
Timeout / Error / Retry / Trace
```

결론적으로 이 장표는 **차세대 정보계의 대내·대외 연계 런타임을 APIM 중심으로 구조화한 핵심 Integration Runtime Architecture**다.
