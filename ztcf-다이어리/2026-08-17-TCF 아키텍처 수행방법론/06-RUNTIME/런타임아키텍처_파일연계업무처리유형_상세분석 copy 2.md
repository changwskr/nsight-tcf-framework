# 런타임 아키텍처 — 파일 연계 업무 처리 유형 상세 분석

## 1. 핵심 결론

이 장표는 차세대 정보계의 전체 런타임 아키텍처 가운데 **파일 기반 인터페이스를 FOS 중심으로 표준화하는 업무 처리 유형**을 상세화한 자료다.

원본 장표의 상단 설명은 다음과 같다.

> **차세대 정보계 파일 연계 기준을 FOS로 일원화해서 연계하며, FOS는 기존 MFT와 내부적으로 연계 구성 처리 가능**

즉 이 장표의 핵심 메시지는 다음 두 가지다.

```text
1. 차세대 정보계의 파일 연계 표준 = FOS
2. 기존 MFT는 제거하는 것이 아니라 FOS와 내부 연계 가능
```

원본 우측 처리 유형은 다음 한 가지를 강조한다.

```text
⑪ FOS 파일 처리 연계
```

이 구조를 런타임 관점에서 정리하면 다음과 같다.

```text
정보계 Application / Data Platform
              │
              │ 파일 송수신 요청
              ▼
             FOS
              │
              ├─ 내부 파일 연계
              ├─ Legacy 파일 연계
              ├─ 대내 시스템 파일 연계
              └─ 필요 시 MFT 연계
                      │
                      ▼
                  대외기관
```

따라서 이 장표는 단순한 “파일 전송 도구” 설명이 아니라, **파일 인터페이스의 표준 진입점을 FOS로 통합하고, 기존 MFT를 보조/하위 전송 메커니즘으로 연계하는 File Integration Runtime Architecture**를 설명한다.

---

## 2.2 상단 설명

원본에서 확인되는 설명:

```text
차세대 정보계 파일 연계 기준을 FOS로 일원화해서 연계하며,
FOS는 기존 MFT와 내부적으로 연계 구성 처리 가능
```

### 의미

이 문장은 파일 연계의 아키텍처 기준을 명확하게 제시한다.

```text
TO-BE 파일 연계 표준
      =
     FOS
```

그리고 기존 파일전송 수단인 MFT는 다음처럼 처리한다.

```text
FOS
  ↔
MFT
```

즉 MFT를 직접 개별 시스템이 호출하는 구조보다, **FOS를 상위 표준 경계로 두고 MFT를 연계 수단으로 활용하는 구조**로 해석하는 것이 자연스럽다.

---

## 2.3 업무 처리 유형 ⑪ — FOS 파일 처리 연계

원본 우측 설명:

- **정보계 시스템과 대내시스템 또는 대외기관과 FOS 솔루션을 통해 파일을 연계 처리**
- **FOS와 MFT는 설정을 통해 연계 처리**
- **배치, Control-M, 데이터 적재/변환**

마지막 항목은 원본 장표에 그대로 기재된 내용으로, FOS 파일처리가 **배치/Control-M/데이터 적재·변환 프로세스와 운영적으로 연결**될 수 있음을 시사한다.

# 5. FOS 중심 파일 연계 아키텍처

이 장표의 핵심은 아래 구조다.

```text
                ┌──────────────────────┐
                │   정보계 시스템      │
                │ App / BI / Data      │
                └──────────┬───────────┘
                           │
                           │ File Interface
                           ▼
                    ┌─────────────┐
                    │     FOS     │
                    │   Standard  │
                    │ File Hub    │
                    └──────┬──────┘
                           │
              ┌────────────┼──────────────┐
              │            │              │
              ▼            ▼              ▼
        대내 시스템     Legacy/File      MFT
                                           │
                                           ▼
                                        대외기관
```

### 아키텍처 의미

- FOS가 **파일 연계 표준 진입점**
- MFT는 필요 시 FOS 내부/하위 연계
- Application이 개별적으로 MFT를 직접 사용하는 것을 줄이는 방향
- 대내/대외/Legacy 파일 흐름을 공통 표준으로 통합

## 6.3 FOS ↔ MFT 대외 파일 연계

원본 장표 상단 설명은 `FOS는 기존 MFT와 내부적으로 연계 구성 처리 가능`이라고 명시한다.

따라서 대외 파일 연계는 다음과 같은 구조로 해석할 수 있다.

```text
정보계
  │
  ▼
 FOS
  │
  │ 내부 설정 기반 연계
  ▼
 MFT
  │
  ▼
대외기관
```

역방향:

```text
대외기관
  │
  ▼
 MFT
  │
  ▼
 FOS
  │
  ▼
정보계
```

### 핵심 의미

```text
Application
   X
   └── 직접 MFT 호출

Application
   O
   └── FOS → MFT
```

즉 **FOS가 파일 통합 아키텍처의 표준 경계**가 된다.

# 7. FOS와 MFT 책임 분리

| 구분 | FOS | MFT |
|---|---|---|
| 아키텍처 위치 | 정보계 파일연계 표준 허브 | 기존/대외 전송 메커니즘 |
| 책임 | 파일 인터페이스 표준화/라우팅 | 파일 전송/전송보안 |
| 호출 주체 | 정보계 시스템 | FOS 또는 연계계층 |
| 업무 관점 | Interface 표준 | Transport 중심 |
| 대상 | 대내/Legacy/대외 | 주로 대외/보안 전송 가능성 |
| TO-BE 기준 | 상위 표준 | 하위 연계 가능 |

> MFT의 실제 책임 범위는 제품/운영 설계서에서 확인해야 한다. 위 비교표 중 `전송보안`, `주로 대외`는 **ANALYSIS** 성격을 포함한다.

# 8. FOS / ETL / Batch 관계

원본 우측 설명에는 다음 표현이 있다.

```text
배치, Control-M, 데이터 적재/변환
```

그리고 중앙에는 FOS 아래에 ETL이 배치되어 있다.

이를 런타임 구조로 풀면 다음과 같다.

```text
File Arrive
   ↓
  FOS
   ↓
File Landing
   ↓
Control-M / Batch Trigger
   ↓
  ETL
   ↓
Transform / Load
   ↓
RDW / ADW
```

즉 FOS는 **파일의 전송/수신**, ETL은 **파일의 내용 처리/적재**를 담당한다고 보는 것이 적절하다.

# 11. 파일 상태 모델

원본에는 파일 상태값을 직접 명시하지 않지만, FOS를 표준 파일 허브로 사용하려면 다음 상태 모델이 필요하다.

```text
CREATED
   ↓
READY
   ↓
SENDING / RECEIVING
   ↓
TRANSFERRED
   ↓
VALIDATED
   ↓
CONSUMED
```

오류 흐름:

```text
SENDING
   ↓
FAILED
   ↓
RETRY
```

또는:

```text
VALIDATED
   ↓
INVALID
   ↓
QUARANTINE
```

# 12. 파일 식별 표준

파일 연계가 표준화되려면 단순 파일명만으로 관리하면 안 된다.

권고 추적키:

```text
Interface ID
File ID
Transfer ID
Batch Job ID
Source System
Target System
Business Date
Sequence
Checksum
```

예:

```text
Interface ID : IF-DATA-FILE-001
File ID      : F-20260823-000001
Source       : LEGACY-A
Target       : RDW
BusinessDate : 20260823
Sequence     : 001
Checksum     : SHA256(...)
```

```text
file.dat
file.done
```

소비자는 `.done` 파일 확인 후 처리한다.

## 14.3 Control File

```text
DATA FILE
+
CONTROL FILE
```

Control File에는 건수/크기/Checksum 등을 기록한다.

# 33. 장표 해석 시 유의사항

이 장표는 **파일 처리 런타임의 상위 구조**를 보여주는 자료이지, 상세 파일 인터페이스 명세서는 아니다.

원본에서 확실히 확인되는 핵심은 다음이다.

```text
FOS = 차세대 정보계 파일 연계 표준
FOS ↔ MFT 연계 가능
⑪ = FOS 파일 처리 연계
```

반면 다음은 별도 상세설계가 필요하다.

- 실제 파일 프로토콜
- 파일 Layout
- 문자셋
- 압축/암호화
- 파일명 규칙
- 완료신호
- 재처리 정책
- 보존기간
- FOS/MFT 제품 상세 설정
- Control-M Job 연계
- ETL 대상 테이블

따라서 본 문서의 `FACT`와 `ANALYSIS`를 구분해서 사용해야 한다.

```text
  ├── 실패 ──▶ Quarantine + 감사 로그 + 운영 알림
  │
  └── 성공 ──▶ 원자적 완료 처리
                 │ 필요 시 MFT
                 ▼
              Landing
                 │ Control-M
                 ▼
                ETL ──▶ RDW / ADW
```

FOS는 표준 정책·추적 경계, MFT는 필요한 구간의 전송 실행 수단으로 책임을 분리해야 한다. 동일 기능을 양쪽에서 중복 수행하면 장애 위치와 재처리 주체가 불명확해진다.

> 본 절은 원본 장표를 바탕으로 수행한 2차 운영 관점 분석이며, 제품별 실제 기능과 설정은 상세설계에서 확인해야 한다.

# 34. 최종 평가

이 장표는 차세대 정보계의 파일 인터페이스 전략을 매우 명확하게 정의한다.

```text
AS-IS 가능 구조

System A → MFT
System B → 개별 File Transfer
System C → FTP
System D → Batch File


             ↓ 표준화


TO-BE

System
  ↓
 FOS
  ├─ 내부 파일 연계
  ├─ Legacy 연계
  └─ MFT 연계
        ↓
      대외기관
```

즉 핵심은 **“파일을 보내는 도구를 하나로 만드는 것”이 아니라, 파일 인터페이스의 관리·추적·정책 경계를 FOS로 일원화하는 것**이다.

이 구조의 주요 장점은 다음과 같다.

1. **파일 연계 표준을 FOS로 통합**
2. **기존 MFT 자산을 유지하면서 TO-BE 표준과 연계 가능**
3. **ETL/Control-M과 연결하여 데이터 적재까지 운영자동화 가능**
4. **대내/대외/Legacy 파일 연계를 한 관리체계로 통합 가능**
5. **File ID 기반 종단 추적체계 구축 가능**

후속 상세설계에서는 반드시 다음 구조가 구체화되어야 한다.

```text
Source
  ↓
Interface / File Contract
  ↓
FOS
  ↓
MFT (필요 시)
  ↓
Landing
  ↓
Control-M
  ↓
ETL
  ↓
RDW / ADW
  ↓
Archive / Audit
```

결론적으로 이 장표는 **차세대 정보계의 파일 연계를 FOS 중심으로 표준화하고 기존 MFT·배치·ETL과 통합하는 핵심 File Integration Runtime Architecture**다.
