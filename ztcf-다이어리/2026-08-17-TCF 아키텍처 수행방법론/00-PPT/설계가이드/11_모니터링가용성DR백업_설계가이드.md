# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 성능·가용·DR·백업·모니터·확장을 **지표·절차·RACI·증거**로 설계한다.  
“고가용” 문구만으로 개통하지 않는다.

```text
“고가용” 문구
        │
        ▼
지표 · RTO/RPO · Owner · 절차
        │
        ▼
Drill · Runtime Evidence
        │
        ▼
개통 Gate 통과
```

```text
운영 품질 · HA/DR · 백업 (11장)
        │
        ├─ NFR / SLA / Timeout
        ├─ HA · DR (Integrity First)
        ├─ 장애 시나리오 8종
        ├─ 백업 · 복구 검증
        ├─ 모니터 · 알람 RACI
        └─ 확장 · VALIDATION Gate
```

### PPT Gap (절차용)

PPT 11장 본문이 약하면 Gap 문구 + Baseline(NFR/SLA · HA-DR/용량 · NFR-VALIDATION)을 쓴다.  
복사용 문구: **정의서 11 §B1**.

### 이 가이드가 답하는 것 / 답하지 않는 것

| 답하는 것 (절차) | 답하지 않는 것 |
|---|---|
| NFR/SLA·HA/DR **기입 순서** | shall 원문 → **정의서 11 Part B** |
| 8시나리오·백업·RACI **작성법** | Hostname 조립 → 05 · Zone/IF 표 → 02·06 |
| Gate·미니 예제·실수 | 거래 8단계 → 08 · SQL 상세 → 04 |

### 읽는 순서

```text
A1 → A2 큰 그림 → A3 용어 → Part B Step 1~8 → 예제·실수 → 정의서 Part B로 규범 확인
```

## B2. Step 2 — HA / DR 표 · 구축 범위 · Failover

전략(절차 요약): **AP Active-Active + 현실적 DB DR · Integrity First**.  
이론적 DB AA를 그대로 채택하지 않는다. 규범: **정의서 §B4 · §B4.5~B4.7**.

| 구분 | 대상 | 절차 Owner | RTO | RPO | 전환 요약 |
|---|---|---|---|---|---|
| HA | (예) WAS 쌍 | | | | |
| DR | AP | | | | |
| DR | DB | | | | |
| DR | Batch | | | | |
| DR | IF / File / Kafka | | | | |

```text
DR 완성 조건
  │
  ├─ 03 운영↔DR Host 대응 일치
  ├─ AP·DB·Batch·IF·File·Kafka 각각 절차
  └─ Host만 있고 앱·DNS 없으면 → 미완성
```

### B2.1 DR 구축 범위 표 기입 (§B4.5)

DR = 운영 전체 복제가 아니라 **고객·단말 연속성 최소 기능의 선택적 DR**.

| 우선 | 시스템 | DR 즉시 구축 구성요소 | 본 프로젝트 ☐ | RTO(승인값) |
|---:|---|---|---|---|
| 1 | 마케팅플랫폼 | WEB/WAS · 미니싱글뷰 · 마케팅 DB | | |
| 2 | 데이터플랫폼 | **RDW** (ADW는 즉시 대상 아님) | | |
| 3 | IT서비스·업무지원 | 단말관리/배포 WEB/WAS | | |

전략 `30분` RTO는 참조값 — 시스템별 승인 RTO로 자동 적용 **금지**.  
SSO·Control-M·CDC/ETL 등 Tier1 의존성은 장표에 없어도 **Runbook 보완** ☐

### B2.2 빈 박스 BI / DG (§B4.7)

| 장표 상태 | 시스템 | 해석 | 후순위 계획 기입 |
|---|---|---|---|
| 빈 박스 | **BI포탈** · **DG** | 즉시 기동 **미표시** ≠ DR 불필요·백업 면제 | Tier3 복구·백업·대체조회: |
| 점선 빈 박스 | 이행 임시 | 상시 DR 아님 · 이행 후 폐기 | |

빈 박스를 “백업 불필요”로 Gate 통과 **금지**.

### B2.3 Failover / Failback 순서 체크 (§B4.6)

**Failover** — 단계마다 승인자·시각·증적·되돌림 조건 must:

| Step | 내용 | Owner | 시각 | Evidence ☐ |
|---:|---|---|---|---|
| 0 | 재해 선언·변경 동결 | | | |
| 1 | Network/DNS/GSLB/L4/FW/SSL | | | |
| 2 | DB 정합성 (Marketing promote · RDW · fencing) | | | |
| 3 | 공통 의존성 (SSO·Secret·Route·관측) | | | |
| 4 | Marketing WAS → WEB → Mini SingleView | | | |
| 5 | 단말관리/배포 | | | |
| 6 | Health/Smoke/업무 검증 | | | |
| 7 | Traffic 전환 · 강화 모니터 · 복구 선언 | | | |

**Failback**: 원센터 검증 → 역동기화(Lag=0/승인 손실) → RO Smoke → DR Writer 차단·Delta → Promote+Traffic 원복 → DR Standby 재구성.  
운영·DR **동시 Writer** 금지(합의된 다중 Writer 없을 때) ☐
