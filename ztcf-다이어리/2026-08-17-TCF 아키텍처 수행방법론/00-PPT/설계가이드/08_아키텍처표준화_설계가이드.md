# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 온라인 거래를 **같은 뼈대(8단계)·같은 전문·같은 GUID**로 흘려 E2E 추적과 업무 경계를 지키게 한다.

```text
패키지=분류코드 → ServiceId 1:1 → 8단계 → 전문 → GUID → Charset → 호출 매트릭스
```

```text
분류(01) · IF(06) · 런타임#(07)
        │
        ▼
표준화 (본 장)
  계층 · 8단계 · 전문 · GUID · Charset · 호출
        │
        ▼
진입 URL·Upload·SSO (09)
```

### 이 가이드가 답하는 것 / 답하지 않는 것

| 답하는 것 (절차) | 답하지 않는 것 |
|---|---|
| 8단계·GUID·전문 **기입 순서** | shall 원문 → **정의서 08 Part B** |
| 워크시트·미니 예제·실수표 | IF 표준표 행 → 06 · Hostname → 03·05 |
| PPT vs MD 정합 절차 | 런타임 시퀀스 상세 → 07 |

### 읽는 순서

```text
A1 → A2 큰 그림 → Part B Step 1~7 → 예제·실수 → 정의서 Part B · 메커니즘 MD
```

PPT가 두 번 보이면 **메커니즘 분석 MD 한 벌**만 따른다.

## A2. 큰 그림

```text
어플리케이션 그룹(대구분)     예: MP
  └─ 어플리케이션(업무구분)  예: IC
       └─ 기능
            ├─ Controller  ←── ServiceId 1:1
            ├─ Service
            ├─ DAO
            └─ resource
```

```text
[1 시스템 선] FW필수
[2 공통 선]   앱 선택
[3 업무 선]   서비스 선택
[4 Controller] → [5 Biz] → DAO
[6 업무 후]   선택
[7 공통 후]   선택
[8 시스템 후] FW필수 · Commit/Rollback·로그
```

```text
채널 → 채널통합 → AP → 연계 → … → 복귀
GUID 진행번호 1 ── +1 ──▶ … ──▶ 7
```

| 축 | 이 장에서 할 일 | 상세 위임 |
|---|---|---|
| 계층·ServiceId | 분류 코드와 1:1 | 정의서 B3 · 09 `/ins`·`/nb` |
| 8단계 | 워크시트 배치 | 정의서 B4 |
| 전문·GUID | 적용/예외·진행번호 책임 | 정의서 B5~B6 |

## A3. 용어 (설계 시 암기)

| 용어 | 설명 |
|---|---|
| 표준전문 | 논리 전문 · 표현은 FLAT 또는 JSON/HTTP |
| GUID | 노드 간 Correlation Key |
| 진행번호 | 노드 통과마다 +1 (왕복 1~7) |
| 원거래글로벌ID | 로그 E2E 조회 키 |
| ServiceId | Controller 메서드와 **1:1** |
| Package UI 예외 | 전문·(일부) GUID 제외 가능 — **명시 필수** |

# Part B — 설계 절차 (How-to)

## B0. 전체 Step 맵

```text
① 패키지·계층 = 분류코드
② ServiceId ↔ Controller 1:1
③ 거래 8단계 워크시트
④ 표준전문 적용/예외 · FLAT/JSON (정의서 B5)
⑤ GUID R1~R5 · 진행번호 1→7 책임 (정의서 B6)
⑥ 캐릭터셋 UTF-8/MS949 · CHAR-001~005 (정의서 B7)
⑦ 호출 매트릭스 ①~⑤ · 완료 (정의서 B7)
```

규범·전체 shall 표 원문: [`정의서 08 Part B`](../정의서/08_아키텍처표준화_정의서.md) **§B5~B7** (가이드에 전문 shall 표 복붙 금지).

## B1. Step 1 — 패키지 · 계층

1. 01에서 `대구분 / 업무구분 / 기능` 가져오기  
2. 패키지·resource 명이 **같은 언어**인지 확인  
3. 타 그룹 코드 혼입 금지  

**확인**: “폴더만 보고 MP인지 BI인지 알 수 있는가?”

## B2. Step 2 — ServiceId 1:1

| 규칙 | 절차 |
|---|---|
| 1:1 | ServiceId ↔ Controller 메서드 |
| 합류 | `/ins/{ServiceId}` 와 `/nb/{ServiceId}` → **같은 Biz** (09) |
| 금지 | ServiceId 없는 임의 URL |

산출 표:

| ServiceId | Controller 메서드 | 런타임# | 표준전문 |
|---|---|---|---|
| | | | 적용/예외 |

## B3. Step 3 — 거래 8단계 배치

| Step | 필수 | 담당 | 넣어도 됨 | 넣으면 안 됨 |
|---:|---|---|---|---|
| 1 | ○ | FW | (수용) | 업무 if |
| 2 | | 앱 | 앱 공통 정책 | ServiceId별 if 폭주 |
| 3 | | 서비스 | 필수값·사전조건 | DB 커밋 |
| 4 | ○ | 개발 | 흐름·Service 호출 | SQL·DAO |
| 5 | ○* | 개발 | 업무 규칙 | 화면 전용만 |
| 6 | | 서비스 | 사후 검증 | 수동 커밋 |
| 7 | | 앱 | 앱 공통 사후 | |
| 8 | ○ | FW | Commit/Rollback·로그 | 업무가 커밋 가로채기 |

정상 완료 = 사용한 6·7 통과 + **8까지**. 4~5만 응답하면 미완료.  
예외 시 8 Rollback · primary exception 유지.

워크시트(복사):

```text
ServiceId:
[1] FW 시스템 선 — (수용)
[2] 공통 선 — □ / 내용:
[3] 업무 선 — □ / 사전조건:
[4] Controller — 호출 Service:
[5] Service — 업무 요약:
[6] 업무 후 — □ /
[7] 공통 후 — □ /
[8] FW 시스템 후 — (수용)
DTO · DAO/소유 테이블:
```

## B4. Step 4 — 표준전문 적용/예외 (정의서 B5)

규범 적용범위·논리 헤더: **정의서 §B5** (전체 shall 표는 정의서만).

| 구간 | 표준전문 | 형식 요지 |
|---|---|---|
| 통합업무·MCA | 적용 | FLAT ↔ JSON 변환(MCA) |
| 정보단말 Direct | 적용 | JSON/HTTP · GUID·로그 동일 |
| **패키지 UI** | **예외** | 비표준 · 06 Direct와 **함께** 명시 |
| MCI·APIM·MP/BI AP | 적용 | JSON/HTTP |
| GSE | 적용 | FLAT 중심 |

FLAT와 JSON = **다른 전문이 아니라** 구간별 표현.

설계서 한 줄:

```text
표준전문: 적용 | 예외(Package UI)
구간형식: FLAT|JSON · 변환 책임: (MCA|…|해당없음)
논리 헤더 블록: 정의서 B5 헤더 요약 참조(버전·GUID·진행번호·…)
```

## B5. Step 5 — GUID · 진행번호 1→7 책임 (정의서 B6)

규범 R1~R5·금지: **정의서 §B6**.

| ID | 규칙 (절차 해석) |
|---|---|
| R1 | 표준 거래에 GUID 필드 사용 (Package 제외 가능) |
| R2 | **채널**이 최초 생성 — AP가 뒤늦게 만들지 않음 |
| R3 | 로그 = 원거래글로벌ID로 E2E |
| R4 | 노드 경유 시 진행번호 **+1** 후 전달 |
| R5 | 응답 복귀까지 키 유지 |

### 왕복 1→7 · 책임 기입 (정의서 B6 표 요지)

| Step | 구간 | 진행번호 | +1 책임(기입) | ☐ |
|---:|---|---:|---|---|
| 1 | 채널 출발 | 1 | 채널(GUID 생성) | |
| 2 | 채널통합(MCA/MCI) | 2 | 채널통합 | |
| 3 | 정보계 AP | 3 | FW/AP 인바운드 | |
| 4 | 대내통합/연계 | 4 | APIM·GSE·어댑터 | |
| 5 | 연계→업무 복귀 | 5 | 복귀 경로 노드 | |
| 6 | 채널통합 복귀 | 6 | 채널통합 | |
| 7 | 최초 채널 응답 | 7 | 채널(+요청 GUID 일치) | |

- GUID 값 **변경 금지** · 진행번호만 증가.  
- 동일 시스템 내부 Ctrl→Svc→DAO는 진행번호 대신 span/로그.

**Gap**: TCF/`pdmg-fw`에 진행번호 자동 +1 API가 없을 수 있음 → “누가 +1?”을 프로젝트에서 확정·Gap 등록.

```text
GUID: 채널 생성 / 원거래글로벌ID: ○
진행번호 +1 책임표: 위 1→7 기입 완료 ☐
Package UI 예외: □예 □아니오
중간 노드 GUID 재발급: 금지
```

## B6. Step 6 — 캐릭터셋 UTF-8/MS949 · CHAR 체크리스트 (정의서 B7)

규범: **정의서 §B7** — 한 줄 *채널·업무 UTF-8 / RDW·ADW MS949 / API G/W·GSE=전사 IF*.

| 영역 | 기준(정의서) | 본 거래 기입 |
|---|---|---|
| 채널 | UTF-8 | |
| 업무 AP | UTF-8 | |
| RDW/ADW | MS949 (NLS Evidence) | |
| API G/W·GSE | 전사 IF | |
| File/Batch | 06 Layout과 일치 | |

변환 책임(경계만 · 앱/화면 임의 변환 금지):

| 흐름 | 변환 | 책임 Boundary |
|---|---|---|
| 채널↔업무 · 업무↔업무 | 없음(UTF-8) | — |
| 업무 ↔ RDW/ADW | UTF-8↔MS949 | **DB Access**(JDBC/세션) |
| → API G/W·GSE | UTF-8→전사 | **Integration** |

CHAR 체크리스트:

| ID | 확인 | ☐ |
|---|---|---|
| CHAR-001 | 채널 UTF-8 | |
| CHAR-002 | 업무 AP UTF-8/Unicode | |
| CHAR-003 | RDW/ADW MS949 · NLS 실측 | |
| CHAR-004 | DB 변환=접근 경계 중앙 통제 | |
| CHAR-005 | API G/W·GSE=전사 IF 우선 | |

금지 감각: 이중 변환 · Platform Default Charset · Char/Byte 길이 혼동 · MS949 `?` 묵시 정상 · 06 Layout 불일치.

## B7. Step 7 — 호출 매트릭스 ①~⑤ · 완료 (정의서 B7)

규범 허용/금지 전체표: **정의서 §B7 업무 간 호출** (①~⑤). 가이드는 **어떤 매트릭스를 쓰는지**만 기입.

| # | 범위 | 절차 요지 | 본 ServiceId 적용 |
|---|---|---|---|
| ① | 같은 기능 내부 | Ctrl→Svc→DAO만 · Ctrl→DAO·Svc→Svc × | ☐ |
| ② | 타 기능(같은 앱) | Ctrl→상대 **공개 Service**만 | ☐ |
| ③ | 공통 유틸리티 | Ctrl→Utility Service · Utility DAO 직결 × | ☐ |
| ④ | 타 애플리케이션 | 공개 Controller/API만 | ☐ |
| ⑤ | 타 그룹·외부 | **06 표준 IF**(APIM 등) | ☐ |

공통 금지: 타 업무 DAO/테이블 직접 · Service→Service 연쇄(승인 없는 오케스트레이션) · 원격을 로컬 TX로 묶음 → 멱등·타임아웃·보상.

| 표준전문 적용/예외 · 형식(B5) | | 정의서 §B5 |
| GUID R1~R5 · 1→7 책임 · Package(B6) | | 정의서 §B6 |

## B8. 미니 예제

```text
정보단말 → 마케팅 고객요약 조회 (런타임 1)
  │
  ├─ 분류: MP / 통합고객 / 조회
  ├─ ServiceId · Controller 1:1
  ├─ 8단계: 업무선(고객번호) + Ctrl + Service + FW 후처리
  ├─ 표준전문: 적용 · JSON · Direct라도 GUID·로그 동일
  ├─ GUID: 채널 생성 · 1→7 책임표 기입 · 원거래글로벌ID
  ├─ Charset: 채널·업무 UTF-8 · RDW면 DB Boundary에서 MS949
  └─ 계정계 필요 시: 매트릭스 ⑤ → 06 APIM (DAO로 원장 금지)
```
