# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 **어디서 들어가고 무엇이 FW 책임인가**를 고정한다. IF 전문·런타임 시퀀스 전체를 쓰기 전에, 아래를 먼저 잡는다.

```text
/ins 인가 /nb 인가?
같은 ServiceId로 Biz가 합류하는가?
FW vs 업무 경계를 그렸는가?
메커니즘·배치는 재사용·Control-M인가?
```

```text
Client / Channel
        │
        ▼
진입점 (/ins · /nb) ──▶ Framework
        │                    │
        │                    ├─ 라우팅 · 8단계 · TX · 로그
        │                    └─ 메커니즘 부품
        ▼
   Biz Service (동일 ServiceId 합류)
```

목표 한 줄: **프레임워크가 하는 일을 업무 코드에 다시 만들지 않는다.**

### 이 가이드가 답하는 것 / 답하지 않는 것

| 답하는 것 (절차) | 답하지 않는 것 |
|---|---|
| `/ins`·`/nb` 선택 · 합류 · 메커니즘 체크 순서 | shall 문장 자체 → **정의서 09 Part B** |
| FW vs 업무 표 · 배치 4계층 **기입 방법** | 8단계 본문 → 08 · IF 표 → 06 |
| 초보자 실수·미니 예제 | 런타임 #1~#11 시퀀스 → 07 · Hostname → 03·05 |

### 읽는 순서

```text
A1 → A2 큰 그림 → Part B Step 1~7 → 예제·실수 → 정의서 Part B로 규범 확인
```

## B1. Step 1 — 진입 경로 선택

| 항목 | `/ins/{ServiceId}` (단말) | `/nb/{ServiceId}` (JSON) |
|---|---|---|
| 클라이언트 | xFrame | JSON 호출자 |
| Wire | **xDataSet** | **JSON** (표준전문) |
| 입력 변환 | xDataSet → **Map** | JSON → **DTO** |
| Context | Map → ServiceContext | DTO + hdr |
| Service 입력 | DTO Dummy · **Map이 실데이터** | **DTO가 실데이터** |
| 출력 | Map → xDataSet | DTO → JSON |

설계 규칙:

1. **같은 ServiceId = 같은 Biz Service** (경로만 다름).  
2. 단말 전용 로직을 `/nb`에, JSON 전용을 `/ins`에 넣지 않는다. **합류점(Service)** 에서 처리.  
3. ServiceId ↔ Controller 메서드 **1:1**(08).  
4. 임의 서블릿·비표준 URL 금지.

워크시트:

| 항목 | 기입 |
|---|---|
| 주 진입 | `/ins` / `/nb` / 둘 다 |
| ServiceId | |
| 합류 Biz Service명 | |
| 보조 채널 계획 | |

## B2. Step 2 — 단말 10단계 · JSON 변환

NHINS(단말) 설계 시 따라가기:

| Step | 처리 | 계층 |
|---:|---|---|
| ① | xDataSet 전달 | PT→BT |
| ② | URL에서 ServiceId 인식 | BT |
| ③ | xDataSet → Map | BT |
| ④ | Map → ServiceContext | BT |
| ⑤ | Service 호출 (DTO Dummy) | BT→Svc |
| ⑥ | ServiceContext에서 Map 조회 | Svc |
| ⑦ | Map 컬럼 → DTO 매핑 | Svc |
| ⑧ | 결과 Map 반환 | Svc→BT |
| ⑨ | Map → xDataSet | BT |
| ⑩ | xFrame 응답 | BT→PT |

xDataSet 헤더 의식: `version` · `screennno(화면번호)` · `datasets[]` · Charset **UTF-8**(08 정합).  
JSON 경로는 JSON→DTO→Service→DTO→JSON과 시스템 선·후(08)를 명시한다.

## B3. Step 3 — FW vs 업무 책임

| FW(프레임워크) | 업무 개발 |
|---|---|
| ServiceId 라우팅 · 8단계 골격 | 도메인 규칙 · DTO 필드 |
| 시스템 선·후 · 공통 예외 훅 | 업무 메시지·화면 문구 |
| 거래통제·입출력 로그 훅 | 업무 검증(3·6단계) |
| 트랜잭션 경계(커밋/롤백) | 원격 호출 멱등·보상 |

**하면 안 됨**: FW가 이미 하는 로깅·TX·라우팅을 업무에서 재구현.

## B5. Step 5 — 배치 프레임워크 (#12) · 재시작 체크리스트

> [`배치_처리_프레임워크_구조_및_컴포넌트_분석.md`](../../05-MECHANISM/배치_처리_프레임워크_구조_및_컴포넌트_분석.md)  
> 규범: **정의서 §B6 · §B6.1~B6.4**

| 계층 | 역할 | 도구 |
|---|---|---|
| 오케스트레이션 | 등록·일정·선후행·기동·모니터링 | **Control-M** |
| 실행 엔진 | Job/Step · commit · 재시작 | Spring Batch / 표준 배치 FW |
| 상태 저장 | JobInstance·checkpoint | **JobRepository** |
| 업무 데이터 | 원장·마트 | 원장 DB (**상태 DB ≠ 원장**) |

```text
Control-M Agent → Shell(환경·exit) → JobLauncher
  → Job → Step(Chunk|Tasklet) → JobRepository ↔ 원장DB
```

절차:

1. 배치 작업 **등록**  
2. 선후행·달력·수시 승인을 Control-M에  
3. Shell → JobLauncher · ExitStatus ↔ Control-M 매핑 (Shell에서 업무 DB 갱신 **금지**)  
4. 재시작 시 **중복 적재 방지**(업무키·멱등)  
5. 온라인 WAS·앱 `@Scheduled`만으로 **운영 배치 금지**

### B5.1 배치 재시작 체크리스트 (§B6.3)

| 점검 | ☐ | 기입 |
|---|---|---|
| JobParameters로 JobInstance 식별(업무일자·회차) | | |
| 완료 instance 동일 파라미터 **중복 신규 실행 없음** | | |
| 실패 Step = JobRepository checkpoint부터 재개 | | |
| Writer **멱등**(업무키) | | |
| BATCH_*를 운영자가 직접 COMPLETED UPDATE **안 함** | | 표준 restart/abandon만 |
| Control-M ↔ BatchStatus/ExitStatus 매핑표 | | |
| Agent timeout ≠ Job 실패 단정 · JobRepository 확인 | | |
| 원장 DB ≠ JobRepository | | |

배치 설계서 기입:

```text
Job명 / 업무일자 파라미터:
선후행 / Control-M 잡 ID:
Shell / Launcher / Step 목록:
재시작 전략 / 종료코드 매핑:
원장 vs JobRepository DB:
런타임 유형: #12 / SLO 완료시각:
```

금지 패턴(정의서 §B6.4): WAS 장기 Batch · 앱 내부 Scheduler만 · 재실행 중복 · 초대형 단일 TX · 업무일자=System Date 하드코딩 · JobRepository↔원장 혼용.
