## B1. 준수 의무 · PPT Gap

1. 설계서에 **지표·측정 구간·Owner**를 must로 기입한다.

## B4. HA / DR 전략

근거: [`HA-DR.md`](../../04-PHYSICAL/HA-DR.md)

### B4.1 전략 (shall)

**AP Active-Active + 현실적 DB DR · Integrity First**  
이론적 DB Active-Active의 운영 복잡성을 그대로 채택하지 않는다.

```text
Center A AP Active  ←Traffic(L4/GSLB)→  Center B AP Active
              └──── DB Strategy (정합성 우선) ────┘
```

### B4.2 HA 원칙

- AP 무상태/세션 전략 · Scale-Out  
- VM 1대 장애가 처리량을 **급락시키지 않음**  
- L4/GSLB · Rolling 배포 가능  
- 기능별 자원 분리 · Fault Isolation  

### B4.3 DR 원칙

- **RTO/RPO** 정의(서비스·구성요소별)  
- 03 운영↔DR Host 대응과 **일치**  
- **AP · DB · Batch · Integration · File · Kafka** 각각 전환 시나리오  
- 물리 Host만 있고 앱·배치·DNS 절차 없으면 **미완성**

### B4.4 HA/DR 표 (must 필드)

| 구분 | 대상 | 절차 Owner | RTO | RPO | 전환 요약 |
|---|---|---|---|---|---|
| HA | (예) WAS 쌍 | | | | |
| DR | AP / DB / 배치 / IF / Kafka | | | | |

### B4.5 DR 구축 범위 (08-22)

근거: [`DR환경_구축_대상_시스템_및_주요_구성요소_분석.md`](../../../../2026-08-22-아키텍처이미지%20원본%20본석/분석/DR환경_구축_대상_시스템_및_주요_구성요소_분석.md)

DR은 운영 전체 복제가 아니라 **고객·단말 연속성 최소 기능의 선택적 DR**이다.

| 우선 | 시스템 | DR 즉시 구축 구성요소 | 비고 |
|---:|---|---|---|
| 1 | 마케팅플랫폼 | 마케팅 WEB/WAS · 미니싱글뷰 WEB/WAS · 마케팅 DB | 핵심 서비스 |
| 2 | 데이터플랫폼 | **RDW** 어플라이언스 | ADW는 본 장표 즉시 대상 **아님** |
| 3 | IT서비스·업무지원 | 단말관리 WEB/WAS · 단말배포 WEB/WAS | 단말 운영·배포 |

| 장표 상태 | 시스템 | 해석 (shall) |
|---|---|---|
| 빈 박스 | **BI포탈** · **데이터거버넌스(DG)** | 즉시 기동 범위 **미표시** — DR 불필요·백업 면제로 해석 **금지** |
| 점선 빈 박스 | 이행용 임시 구성 | 상시 DR 대상 아님 · 이행 후 폐기 |

SSO·Control-M·CDC/ETL·배치 AP 등은 요약 장표에 없어도, Tier1 기동에 필요하면 **의존성 보완**(별도 Runbook)한다. 전략 `30분` RTO는 참조값이며 시스템별 승인 RTO로 자동 적용 **금지**.

### B4.6 Failover / Failback 순서 (shall)

**Failover**

```text
0 재해 선언·변경 동결
→ 1 Network/DNS/GSLB/L4/FW/SSL
→ 2 DB 정합성 (Marketing DB promote · RDW 역할 확정 · Split-Brain 방지/fencing)
→ 3 공통 의존성 (SSO·Secret·Route·FW 설정·관측)
→ 4 Marketing WAS → WEB → Mini SingleView
→ 5 단말관리/배포
→ 6 Health/Smoke/업무 검증
→ 7 Traffic 전환 · 강화 모니터 · 복구 선언
```

**Failback**: 원 센터 인프라·DB·AP 검증 → DR→원센터 역동기화(Lag=0 또는 승인 손실) → 원센터 RO Smoke → DR Writer 차단·최종 Delta → 원센터 Promote+Traffic 원복 → DR Standby 재구성.

운영·DR **동시 Writer** 활성화 금지(합의된 다중 Writer 설계 없을 때). 각 전이에 승인자·시각·증적·되돌림 조건을 **must** 기록.

### B4.7 빈 박스 정책

1. 빈 박스 = **즉시 DR 기동 구성 미표시**.  
2. BI/DG는 후순위(Tier3) 복구·대체조회·메타/품질 DB **백업·복구 계획**을 별도로 둔다.  
3. 빈 박스를 “백업 불필요”로 Gate 통과시키지 **않는다**.

## B6. 백업

| 대상 | 요구 (must) |
|---|---|
| DB | 주기 · 보존 · **복구 검증** |
| 파일·스토리지 | 동일 |
| 설정·이미지·배포 산출물 | 동일 |

1. 복구 Drill 없는 백업 정책은 **미완료**로 본다.  
2. 백업 성공 ≠ 복구 가능. **복구 검증 일자·결과**를 남긴다.  
3. DR 전환과 백업 복구의 Owner·순서를 혼동하지 않는다.

## B7. 모니터링 · 알람 RACI

| 대상 | 신호(예) | Owner (R) | 알람 | 에스컬레이션 (A/C) |
|---|---|---|---|---|
| 온라인 | APM·GUID·거래로그 | | 필수 | |
| 배치 | Control-M·실행정보 | | 필수 | |
| IF | APIM/FOS/CDC 지연 | | 필수 | |
| 인프라 | CPU/Mem/Disk | | 필수 | |

1. **알람 없는 메트릭**은 운영 통제로 인정하지 않는다.  
2. 모니터는 **오픈 후 추가**가 아니라 설계 시 RACI에 포함한다.  
3. Observability NFR과 GUID/APM이 끊기면 Gate 미통과.

## B8. 확장 (Scale)

| 축 | 트리거 조건 | 근거 |
|---|---|---|
| WEB/WAS Scale-out | TPS 등 용량 임계 | 시스템용량 MD |
| 데이터 | 적재·쿼리 부하 | 04 · 용량 |
| Kafka/이벤트 | 수집·오퍼 폭주 | 런타임 #6~7 |

1. 임계치는 [`물리기술아키텍처_시스템용량_분석.md`](../../04-PHYSICAL/물리기술아키텍처_시스템용량_분석.md)를 근거로 한다.  
2. 감(感) Scale-out·근거 없는 감축을 금지한다.  
3. 확장 후 모니터·알람·DR 대응을 **재검증**한다.

## B9. 검증 Gate (must)

개통·중요 릴리스 전:

- [`NFR-VALIDATION.md`](../../06-RUNTIME/NFR-VALIDATION.md)  
- FAST/DEEP Validation  
- RUNTIME-SCENARIOS  
- **DR Drill + Runtime Evidence**  

증거 없이 오픈하지 않는다.

### B9.1 HA-DR 완료 Gate

- [ ] AP 장애 전환 절차

- [ ] 구성요소별 DR 시나리오 (AP/DB/Batch/IF/File/Kafka)  
- [ ] 장애 시나리오 8종 필수 필드 완비  
- [ ] DR Drill / Evidence  

## B10. 금지

- RTO/RPO 없는 “고가용” 문구만  
- DR 서버만 있고 앱·배치·DNS 전환 없음  
- 빈 박스(BI/DG)를 백업·복구 면제로 처리  
- 오픈 후 모니터·알람 추가 전제  
- 검증·Evidence 없는 개통  
- Timeout 계층 역전  
- 시나리오 8종 중 일부만 “해당 없음”으로 공란 처리(사유·ADR 없이)
