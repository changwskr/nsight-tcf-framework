# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 차세대 정보계 아키텍처 문서의 **최상위 개요이자 적용 기준선(Baseline Entry Point)** 을 정의한다.

```text
차세대 정보계 아키텍처 정의
        │
        ├─ Application Architecture
        ├─ Technical Architecture
        └─ Data Architecture
```

목적(한 줄):

```text
인프라 · 개발 · 업무 프로그램 · 유관 담당자
        │
        ▼
아키텍처를 빠르게 파악
        │
        ▼
업무 / 설계 / 개발 / 운영에 적용
```

| 아키텍처 영역 | 장표의 정의 초점 | 핵심 대상 |
|---|---|---|
| Technical Architecture | 논리/물리 구성, 기술요소, SW, 센터, 백업, 가용성 | 인프라 / 기술 플랫폼 |
| Application Architecture | 구성·분류·동작 원리·표준화 | 업무 애플리케이션 / 개발 |
| Data Architecture | 데이터 주제영역 정의 | 데이터 구조 / 분류 |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 (개요 수준) | 답하지 않는 것 (후속 정의서) |
|---|---|
| 아키텍처를 왜 정의하는가 | 서버 사양·Hostname·BOM (03·05) |
| T / A / D로 무엇을 나눌 것인가 | Zone·레이어드 상세 (02) |
| 누가 어떤 목적으로 이 정의를 쓰는가 | IF 매체·계약 (06) · 런타임 시퀀스 (07) |
| 구성·표준·동작원리를 **함께** 정의하는 원칙 | 8단계·GUID·전문 (08·09) |
| 개편 4대 방향 · NFR 5축 · 분류 MP~IM | RAC·OGG·장애 Drill (04·11) |

한 문장: **“무엇을 어떤 범위로 아키텍처라고 부를지”를 고정**하고, **“어떻게 구현·운영할지”는 영역별 정의서에 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 결론 → A3 장표 구조 재현 → A4 계층 트리
        │
        ├─ 역할이 분명하면 A6
        ├─ 정의 5축이 궁금하면 A7~A8
        ├─ T/A/D 범위가 궁금하면 A9
        ├─ NFR·분류 확정이 필요하면 A10~A11
        └─ 적용·검증은 Part B
```

## A2. 원본 장표 메타정보

```text
1. 아키텍처 정의
1.1 개요
```

원본 상단 핵심 문장 (FACT):

> 차세대 정보계 시스템의 어플리케이션 정의, 기술 아키텍처 설계, 데이터 주제 영역의 정의를 기술하고 인프라 담당자, 개발자 및 유관 담당자가 아키텍처를 빠르게 파악하고 업무에 적용함

구조화:

```text
차세대 정보계 시스템
   │
   ├─ 어플리케이션 정의
   ├─ 기술 아키텍처 설계
   └─ 데이터 주제 영역 정의
          │
          ▼
   문서화 / 기준화
          │
          ▼
인프라 / 개발 / 유관 담당자
          │
          ▼
빠른 파악 → 업무 적용
```

| 상단 문장의 조각 | 본문에서의 전개 |
|---|---|
| 어플리케이션 정의 | Application · 구성/분류/동작원리/표준 |
| 기술 아키텍처 설계 | Technical · 논리/물리/센터/백업/가용성 |
| 데이터 주제 영역 정의 | Data · Subject Area |
| 인프라·개발·유관 | A6 사용자 관점 |
| 빠르게 파악·적용 | 공통 참조 문서 · Governance |

## A4. 계층적으로 재작성

```text
Architecture Definition
│
├─ 목적
│   └─ 관계자가 이해하고 업무에 활용할 정보 제공
│
├─ 정의 (5축)
│   ├─ ① Application 구성/분류 체계
│   ├─ ② 논리적 시스템 구성 (+ 기술요소/SW)
│   ├─ ③ 물리적 시스템 구성 + Inventory
│   ├─ ④ 아키텍처 표준 + 구성요소 동작원리
│   └─ ⑤ 업무영역별 Application 동작원리
│
└─ 적용 범위
    ├─ Technical Architecture
    │   ├─ 논리 · 물리 · 시스템/SW
    │   └─ 센터 · 백업 · 가용성
    ├─ Application Architecture
    │   ├─ 구성 · 분류 · 동작 원리
    │   └─ 아키텍처 표준화
    └─ Data Architecture
        └─ 데이터 주제 영역
```

후속 산출물을 받을 때: **새 내용이 이 트리의 어느 가지인가?** 를 먼저 묻는다.  
가지에 넣기 어려운 내용(보안·인터페이스·운영 등)은 GAP으로 기록하고 별도 Domain/정의서에 위임한다. (**ANALYSIS**)

## A8. 정의 축별 최소 골격

### ① Application 구성·분류

```text
Application Group (대구분)
   → Application (업무구분)
      → Function (기능)
         → 실행 시스템(논리) 위치
```

### ② 논리 · ③ 물리

```text
운영환경별 Logical System
   → Technical Component / Software
      → Physical System / Inventory
         → Center · HA · Backup 단위
```

환경이 비면: 개발=운영 가정 · DR 누락 · 선도 축소 범위 혼동. (**ANALYSIS**)

### ④ 표준 · 구성요소 동작원리

```text
Standard (무엇을 지켜야 하는가)
   +
Component Behavior (정상 · 오류 · Timeout)
```

### ⑤ 업무영역별 동작원리

```text
업무영역 → 정상경로 → 오류/예외 → (필요시 Timeout) → 연계 시스템
```

정상 경로 문구만 있으면 **미완성**. (**ANALYSIS**)


한 질문이라도 “문서에 없다”면 Traceability 단절.



### Timeout 계층 (깨지지 않게)

```text
DB Query  <  Transaction  <  외부 Integration  <  Client/Channel
```

### 어플리케이션 분류 3단

```text
대구분(2) → 업무구분(2) → 기능(1)
예: MP + IC + A = MPICA

MP  RD  AD  BI  DG  IM
```

### 최상위 박스 (위치만)

```text
[채널] → [마케팅·BI] → [RDW/ADW·거버넌스]
```

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다. Part A와 표현이 다르면 Part B의 shall/must/금지를 따른다.

## B1. 준수 의무

1. 신규 요구·기능·에픽은 **대구분 · 4대 방향 · NFR**에 매핑한 뒤 상세 설계한다.  
2. 분류 코드의 **임의 약어·별칭·임시 코드** 사용을 금지한다.  
3. 본 정의서와 충돌하는 설계는 **ADR 또는 Gap 등록·승인 전** 적용하지 않는다.  
4. 1장 산출물만으로 Hostname·SQL·IF 매체를 “확정”한 것처럼 서술하지 않는다.

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| Technical / Application / Data | A1 표와 동일 |
| NFR 5축 | Perf · Avail · Scale · Sec · Obs |
| FAST / DEEP | 저지연·이벤트 경로 vs 분석·대량 경로 |
| 대구분 | MP / RD / AD / BI / DG / IM |
| 시스템 그룹 | WEB/WAS/AP/DB/ETL/CDC/Batch 등 **배치 역할** 묶음 |
| SLA Baseline | 프로젝트 수치 확정 전 전략 기준선 |

## B3. 3축 · 4대 방향

| 축 | shall |
|---|---|
| Technical | 설계서에 T축 기여 범위 명시 |
| Application | 대구분·업무구분·기능 헤더 기입 |
| Data | RDW/ADW·주제영역 위치 혼동 금지 |

| # | 방향 | 설계 질문(must 답) |
|---:|---|---|
| 1 | 고객 중심 서비스 강화 | 채널·접점·UI 개선이 있는가? |
| 2 | 데이터 기반 의사결정 강화 | 준실시간/실시간 활용이 있는가? |
| 3 | 통합 정보 활용 기반 | 통합 조회·단일 뷰가 있는가? |
| 4 | 유연·안정 운영체계 | 표준·확장·장애격리에 기여하는가? |

요구/에픽마다 방향 번호(1~4, 복수 허용)를 **shall** 기입. 해당 없으면 ADR. 방향만 있고 NFR/SLA 없으면 **미완료**.

## B4. NFR · SLA · Timeout

| NFR | 목표 (shall) | 설계 전략 (must) |
|---|---|---|
| Performance | 온라인이 대량 분석에 침해되지 않음 | FAST/DEEP · 온/배 · RDW/ADW · Kafka vs ETL 분리 |
| Availability | 이중화·영향 최소화·현실적 DR | Fault Isolation · AP Active-Active · Integrity First DB DR |
| Scalability | 부하·서비스 증가 대응 | VM Scale-Out · 데이터 병렬 · 도메인 독립 |
| Security | 인증·권한·개인정보·전송 | SSO/JWT · 마스킹 · 전송암호 · 감사 |
| Observability | 평시 측정·E2E | GUID · APM · 거래로그 · Evidence |

설계서는 NFR 5축마다 **적용 여부 · 지표(초안) · 측정 구간**을 must 기입. “빠르게/안정적으로”만으로 갈음 금지.

| 구분 | Baseline 예 | 비고 |
|---|---|---|
| 일반 온라인/마케팅 | 약 **3초** | 측정 구간 명시 |
| FAST 이벤트·오퍼링 | 약 **1초** | FAST만 |
| 일배치 | **오전 6시 이전** | 윈도우·Owner |
| CDC 등 | 문서 간 충돌 가능 | ADR로 측정 구간 확정 |

Timeout: `DB < TX < Integration < Client`. **상위가 하위보다 짧으면 금지.**

## B5. 분류 · 시스템 그룹 · 주제영역

### B5.3 데이터 주제영역 6개 트리

```text
차세대 정보계 데이터 주제영역
├─ 데이터플랫폼 RDW     … CO·SR·ZD·RM·FA
├─ 데이터플랫폼 ADW     … CO·SR·ZD·UM·RM·FA·DA
├─ BI포탈               … PT·CR·OA·SB·UI
├─ 마케팅플랫폼         … MP 업무구분 집합
├─ 데이터 거버넌스      … BM·DQ·DL(+CO)
└─ IT서비스 및 업무지원 … IM 업무구분 집합
```

주제영역 ≠ 순수 EDW Subject Area. 플랫폼·업무·관리 영역을 **데이터 관리 관점**으로 묶은 상위 박스이며, 빅픽처에서 RDW/ADW 박스 위치를 문장으로 명시한다.

## B6. 금지

- 분류 코드 없는 패키지·거래·ServiceId 신설  
- NFR/SLA·측정 구간 없이 “빠르게/고가용”만 기술  
- 4대 방향 태그 누락  
- RD/AD 미구분 “그냥 DW”  
- 1장에서 Hostname·SQL·IF 매체를 확정 본문으로 대체  
- Timeout 계층 역전  
- CMDB에 없는 약어 임의 사용
