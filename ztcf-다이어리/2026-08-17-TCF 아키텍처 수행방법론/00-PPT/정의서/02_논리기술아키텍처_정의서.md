# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 Technical Architecture의 **논리 구성(Logical Technical Architecture)** 을 고정한다. Hostname·랙 배치 이전에, **어디에 무엇을 두는가**를 동일 언어로 합의한다.

```text
Vision(방향·NFR) → Big Picture(분류·그룹)
        │
        ▼
【본 장: Logical】
  Zone · 논리 시스템 · 레이어드 · 환경별 구축 범위
        │
        ▼
Physical → Mechanism → Runtime
```

목적(한 줄):

```text
운용환경별 논리 시스템
  + 전사 6 Zone 배치
  + 플랫폼 레이어드 책임
  + Zone·시스템·데이터 경계/금지
        │
        ▼
인프라·개발·업무·유관이 동일 기준으로 식별·설계·검증
```

| 고정하는 것 | 한 줄 |
|---|---|
| 6 Zone | 유입·중계·처리·내부 연계 책임의 논리 경계 |
| 표준 요청 경로 | 채널 → 채널통합 → 서비스제공 → (필요시) 대내통합 |
| 논리 시스템 ↔ 대구분 | MP·(RD/AD)·BI·DG·IM 배치 |
| 환경 범위 | 운영 5 · 개발 5 · DR 즉시기동 3 · 선도 3 |
| 레이어드 | Client → Service → I/F → Data (→ 형상·배포) |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 (논리 수준) | 답하지 않는 것 (후속·타 장) |
|---|---|
| Zone 구성·표준 요청 경로 | Hostname·센터 랙·BOM (03·05) |
| 환경별 논리 시스템 집합 | IF 매체 표준표 상세 (06) |
| 레이어드 계층 책임 | 거래 8단계·GUID·전문 (08) |
| RDW/ADW 논리 소유 분리 | RAC·OGG·용량 (04) |
| 허용·금지 연결 | 런타임 유형 1~12 시퀀스 (07) |

한 문장: **“어느 Zone·어느 논리 시스템·어느 레이어에 두는가”를 고정**하고, **물리·IF·메커니즘·런타임은 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 결론 → A3 표준 경로 → A4 계층 트리
        │
        ├─ Zone 경계가 궁금하면 A5~A6
        ├─ 환경(5/3)이 궁금하면 A7
        ├─ 레이어드·소유가 궁금하면 A8~A9
        └─ 적용·검증은 Part B
```

|---:|---|---|---|
| 1 | 대내 채널 | 내부 사용자 고객 업무 접근 | 통합업무시스템, 정보포털 |
| 2 | 대고객 채널 | 고객 채널 요청 유입 | 인터넷·스마트·콕뱅킹 등 |
| 3 | 대외 채널 | 외부 기관 연계 유입 | 공공·금융·계열 |

## A6. 허용·금지 연결 — 도식

```text
허용:
  채널(3종) ──인증후──▶ 채널통합 ──계약요청──▶ 서비스제공
  서비스제공 ↔ 대내통합 (등록 IF·상호인증)
  서비스제공 → 자기 소유 Data

금지 (Zone 붕괴):
  채널 ──X──▶ 서비스제공 직접
  채널 ──X──▶ 원장/코어 DB
  업무A ──X──▶ 업무B DAO/DB 공유
  외부   ──X──▶ 서비스 DB 직접
  Gateway/EAI에 업무로직·업무DB
  온라인 AP에 대량 ETL 혼재
```

경계 통과 시: serviceId·발신·권한·스키마·GUID를 **수신 Zone에서 재검증**. (FACT)  
상세 전문·GUID는 08. (**ANALYSIS**: 논리 경계와 메커니즘 분리)

## A7. 환경별 구축 범위

```text
운영 ──── 5체계 (상시) + 이행용 임시(상시 수 미포함)
개발 ──── 5체계 (운영과 동일 체계 · 데이터·계정·대외 격리)
DR   ──── 즉시 기동 3 (마케팅·DP·IT지원) · BI·DG 즉시기동 제외
선도 ──── 3 (마케팅·DP·IT지원) · ADW 등 축소 가능
```

| 환경 | 상시 수 | 구축 대상 |
|---|---:|---|
| 운영 | 5 | 마케팅 · 데이터플랫폼 · BI · DG · IT지원 |
| 개발 | 5 | 운영과 동일 5 |
| DR | 3 | 마케팅 · 데이터플랫폼 · IT지원 (RDW 우선) |
| 선도 | 3 | 마케팅 · 데이터플랫폼 · IT지원 |

축소 사유로 “PPT에 없어서”는 인정하지 않음. (**ANALYSIS**: RTO·용량·우선순위 문서화)

## A8. 레이어드 — 공통 골격

```text
Client Access  →  Service  →  I/F  →  Data  →  (형상·배포)
     │              │          │       │
  단말·Browser   UI·업무·엔진  표준연계  소유 DB
```

|---|---|---|
| 마케팅 | WEB/WAS·미니싱글뷰·Kafka/행동·EBM·IMDG | 마케팅 DB · 단말 DB · RDW/ADW 참조 계약 |

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다. Part A와 표현이 다르면 Part B의 shall/must/금지를 따른다.

## B1. 준수 의무

1. 신규·변경 논리 노드는 Zone·시스템·레이어에 **매핑한 뒤** 물리·IF를 확정한다.  
2. 본 정의서와 충돌하는 설계는 **ADR 또는 Gap 등록·승인 전** 적용하지 않는다.  
3. 장표·PPT에 없는 구성을 이유로 축소·금지 조항을 무시하지 않는다.  
4. 한 도면에 운영·DR·개발·선도를 **혼재 표기하지 않는다**.

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| Zone | 유입·중계·처리·내부 연계 책임의 **논리 경계**. subnet/VLAN과 동일 개념 아님 |
| 서비스 제공 Zone | 마케팅·DP·BI·DG·IT지원이 로직·데이터를 처리·저장하는 핵심 Zone |
| 채널 통합 Zone | 대내·대외·대고객 요청 통합·중계 (MCA, MCI, 대외 MCA) |
| 대내 통합 Zone | 내부 IF·라우팅·파일·연계 (APIM, EAI, FOS, MFT) |
| 논리 시스템 | 서비스 제공 Zone 내 상시 구축 단위 |
| 논리 노드 | Hostname 이전 역할 단위. 물리 1대 ≠ 노드 1개 |
| 기술 컴포넌트 | WEB/WAS/AP/DB/Appliance 등 기술 덩어리 |
| 레이어드 | Client Access → Service → I/F → Data (→ 형상·배포) |
| 선도(Pilot) | 동일 Zone 체계 · **축소된 구축 범위** |
| 이행용 임시 | 시한부. **상시 시스템 수에 미포함** |

## B3. Zone 구성 · 표준 경로 (shall)

Zone 체계는 운영·개발·DR·선도 **공통**. 환경 차이는 **구축 범위만**.

| # | Zone | 책임 | 대표 구성(예) |
|---:|---|---|---|
| 1 | 대내 채널 | 내부 사용자 고객 업무 접근 | 통합업무시스템, 정보포털 |
| 2 | 대고객 채널 | 고객 채널 요청 유입 | 인터넷뱅킹, 스마트뱅킹, 콕뱅킹 등 |
| 3 | 대외 채널 | 외부 기관 업무 연계 유입 | 공공·금융·계열 기관 등 |
| 4 | 채널 통합 | 접속·인증 연계·프로토콜·통합·중계 | 영업점 MCA, MCI, 대외 MCA |
| 5 | 서비스 제공 | 업무 로직·데이터 처리·저장 | 마케팅·DP·BI·DG·IT지원 |
| 6 | 대내 통합 | 내부 IF 통합·라우팅·파일·연계 운영 | Cruz APIM, EAI, FOS, MFT |

업무 요청은 다음 경로를 **shall** 따른다. 응답은 동일 경계를 역방향 통과.

```text
[대내|대고객|대외 채널] → [채널 통합] → [서비스 제공] →(필요시)→ [대내 통합]
```

| 개념 | 취급 |
|---|---|
| subnet/VLAN | Zone 구현 수단일 수 있으나 Zone 자체 아님 |
| API G/W·EAI 제품 | 대내 통합 **구성요소** · Zone 명칭 아님 |
| 조직 | 한 조직이 여러 Zone 운영 가능 |
| 마케팅·BI 도메인 | 주로 **서비스 제공** 내부 |

## B4. Zone 허용·금지 연결

### 허용

| 연결 | 조건 |
|---|---|
| 채널(3종) → 채널 통합 | 각 채널 인증·통제 후 |
| 채널 통합 → 서비스 제공 | serviceId(동등 식별자)·스키마·timeout·trace 계약 |
| 서비스 제공 ↔ 대내 통합 | **등록 IF 계약**·상호 인증 |
| 서비스 제공 → **자기 소유** Data | 해당 시스템 소유 DB/스키마에 한함 |

### 금지 (Zone 붕괴) — 예외는 ADR·보안·아키텍처 승인·증적 필수

| 금지 | 설명 |
|---|---|
| 채널 → 서비스 제공 **직접** | 승인 예외 경로 아닌 한 금지 |
| 채널 → **원장/코어 DB 직접** | 절대 금지에 가깝게 취급 |
| 업무A → 업무B **DAO/DB 공유·직접** | 공개 API·표준 IF(대내 통합)만 |
| 외부 기관 → 서비스 DB 직접 | 금지 |
| API G/W(대내 통합 구성요소)가 **업무 로직·업무 DB** 보유 | 금지 |
| 온라인 AP에 **대량 ETL** 혼재 | 데이터 IF·배치 경로 사용 |

Zone 경계 통과 호출: 서비스 식별자·발신·권한·스키마·추적키를 **수신 Zone에서 재검증** (shall). 상세는 08.

### B6.1 공통 골격 + 플랫폼별 ASCII (shall)

공통 패턴: `Client → Service → I/F → Data`(필요 시 `형상·배포`). 설계서는 플랫폼 델타만 명시하고 **계층 우회를 금지**한다.

**마케팅(MP)**

```text
Client:  정보단말/Browser→L4 · 통합단말→MCA→L4
Service: UI(WebTopSuite) ∥ 마케팅WAS+Kafka/EBM+IMDG
I/F:     SSO·CruzAPIM·EAI·FOS·MFT·ETL·CDC·MCA·GSE
Data:    단말DB · 마케팅DB · RDW · ADW
Deploy:  GitLab/eCAMS
```

**데이터플랫폼(DP)** — Client는 UI가 아닌 **운영 제어**

```text
Client:  Control-M ↔ ETL Scheduler → Job Shell
Service: CDC/JDBC/ETL → RDW(Exadata) → ETL → ADW(Exadata)
I/F:     SSO·FOS·MFT·ETL·CDC·대외MCA·통합관제·IT메타
Data:    RDW=준실시간 SoR · ADW=분석 SoR/마트
```

**BI**

```text
Client:  Browser → L4
Service: BI포털WAS · 신용실적WAS · OLAP(+Adapter) · Self-BI · IMDG
I/F:     SSO·CruzAPIM·FOS·MFT·UMS·통합관제
Data:    BI/OLAP/Self-BI 저장소 · RDW/ADW 참조(계약)
```

**DG** — BI는 오케스트레이션, DG WAS는 **처리 대체 아님**

```text
Client:  Browser → L4
Service: (BI포털 API) → 품질·비즈메타·데이터흐름 WAS
I/F:     SSO·CruzAPIM·EAI·FOS·MFT·ETL·대외MCA
Data:    거버넌스 저장소 + RDW/ADW 메타 연계
```

### B6.2 계층 호출 · Fast/Deep Path (shall)

**공통 호출 shall**

1. Client는 L4·MCA·스케줄러 등 **정해진 진입점만** 호출한다.  
2. WEB은 화면·라우팅만 · **업무 로직은 Service(WAS)**.  
3. DB는 DAO/Mapper만 · Controller·화면 **직접 SQL 금지**.  
4. 외부 호출은 **I/F Layer 표준 매체**만 경유한다.  
5. 실시간 이벤트는 Kafka/EBM 등 **비동기 경로 분리**.  
6. 계층 우회·타 시스템 DAO 공유·Gateway에 업무 로직 = **금지**(B7).

**DP Fast / Deep Path (shall)**

```text
원천 변경 ── Fast Path ─ OGG/CDC ──▶ RDW ──▶ 최신 조회·싱글뷰
원천/BCV  ── Deep Path ─ ETL/Batch ─▶ ADW ──▶ BI·OLAP·통계
RDW ─────── ETL Dataset 발행 ─────▶ ADW   (별도 계약)
```

- Fast와 Deep의 **Owner·SLA·Writer**를 분리한다. 동일 Target에 OGG와 ETL **이중 Writer 금지**.  
- 스케줄러 → Job Shell → ETL/DB Job. 원천 → **CDC 중계** → RDW.  
- 원천·외부의 ADW/RDW **직접 갱신·직결 JDBC** 금지.

### B6.3 컴포넌트 패턴 · 카탈로그 must

- VM: `솔루션 → 스택 → JVM → 횡단 → OS → VM → Cloud`  
- Appliance: `업무데이터 → (OGG*) → DBSafer → DBMS → 횡단 → OS → Appliance`  
  (\* OGG/CDC는 **RDW Baseline**. ADW는 이미지상 OGG 미표시 → ETL·Batch 적재)  
- 횡단(양 패턴 must): 서버 백신 · 계정 · 서버 보안 · 개인정보 · 백업 · 인프라 통합관제 · 서버 모니터링 · 서버운영관리  

**노드 기술 카탈로그 must-fields** (공통 기술컴포넌트 분석 7.1)

| 분류 | 필수 항목 |
|---|---|
| 식별 | nodeId, systemId, environment, owner, criticality |
| 실행 | solution, artifactVersion, technologyStack, JVM/DBMS version |
| 기반 | OS image/version, VM flavor 또는 Appliance model, Cloud zone |
| 보안 | account source, vaccine/security agent, 개인정보 등급, 예외 |
| 운영 | monitoring profile, backup policy, runbook, patch group |
| 복구 | HA, backup target, RPO, RTO, restore evidence |
| 연결 | endpoint, port, upstream/downstream, dependency |

**DP Baseline 컴포넌트 (shall 등록)**

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| **OGG/CDC** | 원천 변경 → Downstream → RDW 준실시간 반영 | Capture/Apply·Lag·Checkpoint |
| **ETL** | BCV·RDW→ADW·대내외 대량 적재 | Watermark·재시작·대사 |
| **DBSafer** | DB 접근통제·감사 | App/ETL/OGG/DBA 우회 금지 |
| **FOS/MFT** | 파일 송수신 표준 경로 | 완료신호·Manifest (06) |
| **Control-M / ETL Scheduler / Job Shell** | 배치 오케스트레이션 | 스케줄러 직호출 상시화 금지 |
| **Exadata RDW/ADW** | 준실시간 SoR / 분석 SoR | 역할 혼재 금지 |

### B6.4 데이터 소유

1. 각 논리 시스템은 **소유 Data**만 직접 접근.  
2. RDW(준실시간·운영성)와 ADW(분석·대량) 역할 혼재 금지.  
3. BI·마케팅의 RDW/ADW는 **허용된 조회·연계 계약**만 · DAO 공유 금지.  
4. DG는 원장·마트 **대체 처리자 아님**.  
5. Read/Write Matrix는 데이터·IF 상세에서 확정하되 본 원칙 위반 금지.
