## 1. 목적과 적용 범위

### 1.1 목적

본 정의서는 차세대 정보계의 **논리기술아키텍처(Logical Technical Architecture)** 를 고정하여, 인프라·개발·업무·유관 담당자가 다음을 **동일 기준으로** 식별·설계·검증하도록 한다.

1. 운용환경(운영·DR·개발·선도 등)별 **구축 대상 논리 시스템**
2. 전사 IT **6 Zone** 상 논리 노드 배치
3. 플랫폼별 **레이어드 책임**과 **기술 컴포넌트**
4. Zone·시스템·데이터 **경계 및 금지 연결**

### 1.2 적용 범위

| 포함 | 제외(타 정의서·장으로 위임) |
|---|---|
| Zone 구성·표준 요청 경로 | 물리 Hostname·센터 랙 배치 (`04-PHYSICAL` / 03·05장) |
| 환경별 논리 시스템·컴포넌트 | IF 매체 표준표 상세 (`03-LOGICAL` IF / 06장) |
| 레이어드 계층 책임 | 거래 8단계·GUID·전문 (`05-MECHANISM` / 08장) |
| RDW/ADW 논리 소유 분리 | RAC·OGG 물리·용량 (`04-PHYSICAL` / 04장) |
| 금지·허용 연결 | 런타임 유형 1~12 시퀀스 (`06-RUNTIME` / 07장) |

### 1.3 상위 아키텍처 축과의 관계

Vision 개요에 따른 3축 중, 본 정의서는 **Technical Architecture의 논리 구성**을 주로 다루며, Application 분류코드(MP/RD/AD/BI/DG/IM)와 Data 주제영역의 **배치 위치**를 논리 시스템·Zone에 고정한다.

```text
Vision(방향·NFR) → Big Picture(분류·그룹) → 【본 정의서: Logical】
 → Physical → Mechanism → Runtime
```

### 1.4 준수 의무

1. 신규·변경 논리 노드는 본 정의서의 Zone·시스템·레이어에 **매핑한 뒤** 물리·IF를 확정한다.  
2. 본 정의서와 충돌하는 설계는 **ADR(Architecture Decision Record)** 또는 Gap 등록 후 승인받기 전에는 적용하지 않는다.  
3. 장표·PPT에 없는 구성을 이유로 본 정의서의 축소·금지 조항을 무시하지 않는다.

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| **Zone** | 서비스 요청의 **유입·중계·처리·내부 연계 책임**을 기준으로 나눈 **논리 경계**. 동일 책임·신뢰 수준·보안/가용 정책·In/Out 계약·장애 영향·운영 소유를 묶는다. **subnet/VLAN과 동일 개념이 아니다.** |
| **서비스 제공 Zone** | 마케팅플랫폼·데이터플랫폼·BI포탈·데이터거버넌스·IT서비스 및 업무지원이 업무 로직과 데이터를 처리·저장하는 핵심 Zone |
| **채널 통합 Zone** | 대내·대외·대고객 채널 요청을 통합·중계하는 Zone (예: 영업점 MCA, MCI, 대외 MCA) |
| **대내 통합 Zone** | 내부 시스템 간 인터페이스 통합·라우팅·파일·연계 운영 Zone (예: API G/W, EAI, FOS, MFT) |
| **논리 시스템** | 서비스 제공 Zone 내 상시 구축 단위(마케팅·데이터플랫폼·BI·거버넌스·IT지원) |
| **논리 노드** | Hostname 이전의 역할 단위(예: 마케팅 WEB, 행동정보 AP). 단일 물리 서버 1대를 의미하지 않는다. |
| **기술 컴포넌트** | 논리 노드를 구성하는 WEB/WAS/AP/DB/Appliance 등 기술 덩어리 |
| **레이어드 아키텍처** | Client Access → Service → I/F → Data (→ 형상·배포)로 책임을 나눈 계층 구조 |
| **선도(Pilot)** | 운영 전 일부 범위만 선행 구축하는 환경. 운영과 **동일 Zone 체계**, **축소된 구축 범위** |
| **이행용 임시 구성** | 전환·추출·이행·SQL 품질 등 시한부 구성. **상시 시스템 수에 포함하지 않는다** |

## 3. Zone 구성 기준 (6 Zone)

### 3.1 Zone 목록

전사 IT는 다음 6개 Zone으로 구분한다. Zone 체계는 **운영·개발·DR·선도 모든 환경에 공통** 적용한다. 환경별 차이는 **구축 범위**에만 둔다.

| # | Zone | 책임 | 대표 구성(예) |
|---:|---|---|---|
| 1 | 대내 채널 | 내부 사용자가 고객 업무를 처리하기 위해 접근 | 통합업무시스템, 정보포털 |
| 2 | 대고객 채널 | 고객 채널에서 업무 요청 유입 | 인터넷뱅킹, 스마트뱅킹, 콕뱅킹 등 |
| 3 | 대외 채널 | 외부 기관과의 업무 연계 유입 | 공공·금융·계열 기관 등 |
| 4 | 채널 통합 | 대내·대외·대고객 요청의 접속·인증 연계·프로토콜 수용·통합·중계 | 영업점 MCA, MCI, 대외 MCA |
| 5 | 서비스 제공 | 업무 로직·데이터 처리·저장 | 마케팅·데이터플랫폼·BI·DG·IT지원 |
| 6 | 대내 통합 | 내부 시스템 간 IF 통합·라우팅·파일 전송·연계 운영 | API Gateway(Cruz APIM), EAI, FOS, MFT |

### 3.2 표준 요청 경로

업무 요청은 다음 경로를 **shall** 따른다. 응답은 동일 경계를 역방향으로 통과한다.

```text
[대내|대고객|대외 채널]
        │
        ▼
[채널 통합 Zone]  ── 표준 채널/업무 요청 ──▶
        │
        ▼
[서비스 제공 Zone] ── 필요 시 ──▶ [대내 통합 Zone] ──▶ 내부 시스템/데이터/솔루션
```

### 3.3 Zone과 혼동 금지

| 개념 | 본 정의서에서의 취급 |
|---|---|
| Network subnet/VLAN | Zone 구현 수단일 수 있으나 Zone 자체가 아님 |
| API Gateway·EAI 제품 | 대내 통합 Zone의 **구성요소**이지 Zone 명칭이 아님 |
| 조직 | 한 조직이 여러 Zone을 운영할 수 있음 |
| 마케팅·BI 등 업무 도메인 | 주로 **서비스 제공 Zone** 내부 범위 |

## 4. Zone 허용·금지 연결

### 4.1 허용 연결

| 연결 | 조건 |
|---|---|
| 채널(3종) → 채널 통합 | 각 채널의 인증·통제를 거친 후 |
| 채널 통합 → 서비스 제공 | serviceId(또는 동등 식별자)·스키마·timeout·trace가 계약된 요청 |
| 서비스 제공 ↔ 대내 통합 | **등록된 IF 계약**·상호 인증 하에 중계 |
| 서비스 제공 → **자기 소유** Data | 해당 시스템이 소유한 DB/스키마에 한함 |

### 4.2 금지 연결 (Zone 붕괴)

다음 연결은 **금지**한다. 예외는 ADR·보안·아키텍처 승인 및 증적 없이 허용하지 않는다.

| 금지 | 설명 |
|---|---|
| 채널 → 서비스 제공 **직접** | 승인된 예외 경로가 아닌 한 금지 |
| 채널 → **원장/코어 DB 직접** | 절대 금지에 가깝게 취급 |
| 업무A → 업무B **DAO/DB 공유·직접 접근** | 공개 API·표준 IF(대내 통합)로만 연계 |
| 외부 기관 → 서비스 DB 직접 | 금지 |
| API Gateway(또는 대내 통합 구성요소)가 **업무 로직·업무 DB**를 보유 | 금지 |
| 온라인 AP에 **대량 ETL** 혼재 | 자원·책임 분리 (데이터 IF·배치 경로 사용) |

### 4.3 경계 통과 시 재검증

Zone 경계를 넘는 호출은 서비스 식별자·발신 주체·권한·스키마·추적키(GUID 등)를 **수신 Zone에서 재검증**한다. 상세 전문·GUID 규칙은 Mechanism(08장) 정의·분석을 따른다.

## 5. 논리 시스템과 대구분 매핑

Big Picture 어플리케이션 대구분과 서비스 제공 Zone의 논리 시스템은 다음과 같이 **고정**한다.

| 대구분 코드 | 명칭 | 논리 시스템 |
|---|---|---|
| **MP** | 마케팅플랫폼 | 마케팅플랫폼 시스템 |
| **RD** + **AD** | 데이터플랫폼 RDW / ADW | **데이터플랫폼 시스템** (코드는 RD·AD로 분리, 논리 시스템은 하나) |
| **BI** | BI포탈 | BI포탈 시스템 |
| **DG** | 데이터거버넌스 | 데이터거버넌스 시스템 |
| **IM** | IT서비스 및 업무지원 | IT서비스 및 업무지원 시스템 |

App Group과 System Group(WEB/WAS/AP/DB 등 배치 역할)은 1:1이 아닐 수 있다. 배포·서버 역할 매핑은 Big Picture 시스템 그룹 정의를 따른다.

## 6. 환경별 구축 범위

### 6.1 환경 분리 원칙

1. 운영·DR·개발·선도·검증은 **환경별로 절·표를 분리**하여 기술한다. 한 도면에 환경을 혼재하지 않는다.  
2. Zone 명칭·경로는 전 환경 동일하다.  
3. **구축하는 논리 시스템의 집합**만 환경별로 다를 수 있다.

### 6.2 구축 범위 정의

| 환경 | 상시 논리 시스템 수 | 구축 대상 | 비고 |
|---|---:|---|---|
| **운영** | 5 | 마케팅 · 데이터플랫폼 · BI포탈 · 데이터거버넌스 · IT서비스 및 업무지원 | 이행용 임시는 상시 수 **미포함** |
| **개발** | 5 | 운영과 동일 5체계 | 소스관리·단말개발도구 등 개발 특화 노드 추가 가능. **운영 데이터·계정·대외와 격리**(합성/Stub) |
| **DR** | 3 (즉시 기동) | 마케팅 · 데이터플랫폼 · IT서비스 및 업무지원 | BI·DG는 즉시 기동 대상에서 **제외**(백업 부재를 의미하지 않음). 데이터는 **RDW 우선**, ADW는 장표상 즉시 기동 미표시 |
| **선도(Pilot)** | 3 | 마케팅 · 데이터플랫폼 · IT서비스 및 업무지원 | ADW·일부 채널통합·운영 Pipeline 등은 축소·미표시될 수 있음 |

### 6.3 DR·선도 축소 정의

1. DR·선도의 축소는 **고객 서비스 복구·선행 검증 우선순위**에 따른 선택적 구성이다. 운영 전체의 단순 복제가 아니다.  
2. 제외 시스템(예: BI·DG)에 대해 **사유(RTO·용량·우선순위)** 와 **백업·후순위 복구** 방침을 설계서에 명시한다.  
3. “PPT/장표에 없어서”는 축소 사유로 인정하지 않는다.

### 6.4 이행용 임시 구성

전환 AP·추출 DB·이행 AP·SQL 품질 AP 등은 **시한부**이며 개통 후 제거·전환한다. 상시 5(또는 3) 시스템 카운트에 넣지 않는다.

## 7. 환경별·시스템별 주요 논리 구성요소

> WEB/WAS/AP/DB는 **논리 역할**이다. 대수·Hostname은 물리 정의서에서 확정한다.

### 7.1 운영환경 (5체계 + 임시)

| 논리 시스템 | 주요 구성요소 | 주요 책임 |
|---|---|---|
| 마케팅플랫폼 | 마케팅 WEB/WAS, 미니싱글뷰 WEB/WAS, 실시간 처리 AP, 행동정보 처리 AP, 고객 행동 데이터 AP, 마케팅 DB | 마케팅 업무·고객 뷰·실시간 반응·행동 데이터 |
| 데이터플랫폼 | RDW Appliance, ADW Appliance | 준실시간·운영성 및 분석·대량 데이터 저장·제공 |
| BI포탈 | BI 포털 WEB/WAS, 신용실적 WEB/WAS, OLAP AP/WEB/WAS, Self-BI AP/WEB/WAS, 경영실적 DB, BI포털 DB | 정형·비정형 분석, OLAP, Self-BI, 포털 |
| 데이터거버넌스 | 비즈메타/데이터 품질 WAS, 데이터 흐름 WAS, 거버넌스 DB | 메타·품질·리니지(흐름) 통제·가시성 |
| IT서비스 및 업무지원 | 단말관리·단말배포 WEB/WAS, 배치 AP, CDC 중계 DB, ETL, UNO Dashboard, 출력물(RD) WAS, 단말관리 DB | 단말·배치·CDC/ETL·출력·운영 공통 |
| (임시) 이행 | 전환/이행/SQL 품질 AP, 추출 DB | 개통 전후 이행·검증 |

### 7.2 DR환경 (즉시 기동 요지)

| 논리 시스템 | 즉시 기동 구성요소(장표 기준) |
|---|---|
| 마케팅플랫폼 | WEB/WAS, 미니싱글뷰 WEB/WAS, 마케팅 DB |
| 데이터플랫폼 | **RDW** |
| IT서비스 및 업무지원 | 단말관리·단말배포 WEB/WAS |

### 7.3 개발환경

운영과 동일한 5체계를 **개발·시험 목적**으로 구축한다. 개발 환경의 데이터·비밀·대외 연결은 운영과 **동일시하지 않는다**.

### 7.4 서비스 제공 Zone 배치

마케팅·데이터·BI·DG·IT지원의 **소유 Zone은 서비스 제공**이다.  
채널·채널 통합·대내 통합에 표시되는 박스는 다수가 **연계 대상 표시**이며, 해당 환경에서 정보계가 “소유”하는 상시 시스템으로 해석하지 않는다.

## 8. 레이어드 아키텍처 규범

### 8.1 공통 계층

서비스 제공 Zone의 플랫폼은 다음 계층 책임을 **shall** 준수한다.

| 계층 | 책임 |
|---|---|
| **Client Access** | 단말·Browser·운영 제어 클라이언트 유입, L4 등 진입 |
| **Service** | UI 서비스·업무 서비스·이벤트/분석 엔진. NH Cloud Framework 등 온라인 골격 |
| **I/F** | 표준 온라인·파일·데이터 연계 진입(매체 상세는 IF 정의) |
| **Data** | 시스템 소유 DB·Appliance. **타 시스템 DAO 공유 금지** |
| **형상·배포** | (해당 시) Dev/Ops 파이프라인. 선도·일부 플랫폼은 축소 가능 |

데이터플랫폼은 형상·배포 계층이 약하게 표현될 수 있으나, Control-M·ETL Scheduler 등 **운영 제어**는 Client/Service 측에 정의한다.

### 8.2 마케팅플랫폼 레이어 (요지)

| Layer | 핵심 정의 |
|---|---|
| Client | 정보단말/Browser→L4; 통합단말→MCA→L4 |
| Service | 단말관리/배포·WebTopSuite ∥ 마케팅 WEB/WAS·미니싱글뷰·Kafka/행동·EBM·IMDG; NH Cloud FW |
| I/F | SSO, Cruz APIM, EAI, FOS, MFT, ETL, CDC, MCA, GSE 등 |
| Data | 단말관리 DB, 마케팅플랫폼 DB, RDW, ADW |
| 배포 | GitLab/Runner(Dev), eCAMS 등(Ops) |

### 8.3 데이터플랫폼 레이어 (요지)

| Layer | 핵심 정의 |
|---|---|
| Client(운영제어) | Control-M ↔ ETL Scheduler → Job Shell |
| Service | RDW/ADW Exadata; CDC→RDW; JDBC; ETL/FOS/MFT |
| I/F | SSO, FOS, MFT, ETL, CDC, 대외MCA, 배치관리 등 |
| Data | **RDW**: 실시간 SoR·집계·로그 등 / **ADW**: 분석 SoR·마트·송신마트 등 |

**RDW와 ADW는 단순 이중화가 아니라 준실시간·운영성 조회와 분석·대량 조회의 부하·책임 분리**로 정의한다.

### 8.4 BI포탈 레이어 (요지)

| Layer | 핵심 정의 |
|---|---|
| Client | Browser → L4 |
| Service | BI Portal, 신용실적, OLAP(+MSTR 등), Self-BI; NH Cloud; IMDG |
| I/F | SSO, Cruz APIM, FOS, MFT, UMS 등 |
| Data | BI DB, 경영실적 DB, OLAP/Self-BI 저장소, RDW/ADW 참조(소유권 준수) |

### 8.5 데이터거버넌스 레이어 (요지)

| Layer | 핵심 정의 |
|---|---|
| Client | Browser → L4 |
| Service | 비즈메타·데이터품질·데이터흐름 WAS (업무 데이터 **처리 대체가 아닌** 통제·가시성) |
| I/F | SSO, APIM, EAI, FOS, MFT, ETL 등 |
| Data | 거버넌스 저장소 + RDW/ADW 메타·흐름 연계 |

### 8.6 선도개발 레이어 (요지)

축소 구성: Browser(선도)→L4→ UI(단말) ∥ 마케팅 WAS+IMDG; I/F·Data는 RDW·마케팅 DB·단말 DB 중심(**ADW 미구축 가능**); 배포는 Dev Pipeline 중심.

## 9. 공통 기술 컴포넌트 표준

모든 업무 논리 노드는 다음 두 표준 패턴 중 하나에 매핑한다.

### 9.1 VM 노드

```text
솔루션 → 기술스택 → JVM → (횡단 통제) → OS → VM → Cloud/IaaS
```

### 9.2 DB Appliance 노드

```text
업무데이터 → 기술스택 → DBMS → (횡단 통제) → OS → DB Appliance
```

### 9.3 횡단 공통 (양 패턴 must)

서버 백신 · 계정 관리 · 서버 보안 · 개인정보 · 백업 관리 · 인프라 통합관제 · 서버 모니터링 · 서버운영관리  

정책은 공통이며, Agent·Patch·Backup·HA의 **구현 세부**는 플랫폼·물리 정의에서 확정한다.

---

## 10. 데이터 소유 원칙

1. 각 논리 시스템은 **소유 Data**만 직접 접근한다.  
2. RDW는 준실시간·운영성, ADW는 분석·대량의 **논리 소유·역할**을 혼재하지 않는다.  
3. BI·마케팅의 ADW/RDW 접근은 **허용된 조회·연계 계약**에 한하며, 타 시스템 DAO를 공유하지 않는다.  
4. 데이터거버넌스는 업무 원장·마트의 **대체 처리자가 아니며**, 메타·품질·흐름을 관리한다.  
5. 테이블/뷰 단위 Read·Write Matrix는 데이터·IF 상세 설계에서 확정하되, 본 조의 소유 원칙을 위반하지 않는다.

---

## 11. 금지 패턴 체크리스트 (규범)

설계·구현·리뷰 시 다음을 확인하고, 위반 시 배포·개통하지 않는다.

- [ ] 채널 → 원장/코어 DB 직접 접근 없음  
- [ ] 업무 간 DAO/DB 공유 없음  
- [ ] 채널 → 서비스 무단 직접 호출 없음  
- [ ] Gateway/EAI에 업무 로직·업무 DB 없음  
- [ ] 온라인 AP에 대량 ETL 혼재 없음  
- [ ] Event 처리를 Online WAS 스레드에만 의존하지 않음(이벤트 경로 분리)  
- [ ] RDW/ADW 역할 혼재로 분석 부하가 준실시간 경로를 침해하지 않음  
- [ ] DR/선도 축소 사유·복구 방침이 문서화됨  
- [ ] 이행용 임시가 상시 시스템으로 잔존하지 않음

## 13. 변경 관리

1. Zone 추가·삭제, 허용/금지 연결 변경, 환경별 구축 범위 변경, 논리 시스템·소유 Data 변경은 **영향 분석 → ADR 또는 Gap → 승인 → 본 정의서 개정** 순으로 한다.  
2. 개정 시 PPT 통합본·`03-LOGICAL` 분석·설계가이드 02와의 **정합**을 함께 갱신한다.  
3. 구현 저장소(`tcf-*` 등)와의 차이는 본 정의서 위반이 아니라 **구현 Gap**으로 관리하고, 정의서 문구를 구현에 맞추어 임의 완화하지 않는다.
