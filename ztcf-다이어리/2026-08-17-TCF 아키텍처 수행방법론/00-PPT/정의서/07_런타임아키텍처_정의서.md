# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 차세대 정보계의 **업무 처리 런타임을 대유형 6 · 소유형 12로 고정**하고, 유형별 Owner·IF·SLO·재처리·모니터링·검증 기준을 둔다.

```text
업무 / 채널 / 연계 / 이벤트 / 데이터 / 파일 / 배치
        │
        ▼
런타임 유형 # (1~12)
        │
        ▼
시퀀스 · IF · SLO · 재처리 · Evidence
```

목적(한 줄):

```text
유형 번호 없는 거래·배치·연계 신설 금지
        │
        ▼
설계서에 주/보조 유형 · 시퀀스 · Gate 필수
        │
        ▼
정상 / 지연 / 장애 Evidence로 개통
```

| 축 | 장표의 정의 초점 | 핵심 대상 |
|---|---|---|
| 유형 체계 | 대유형 6 · 소유형 12 | 업무·개발·운영 |
| 경로·IF | 대표 IF(06) · ServiceId | 인터페이스·앱 |
| 품질 | SLO · 재시도·보상 · Gate | NFR·검증 |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 (개요 수준) | 답하지 않는 것 (후속·인접) |
|---|---|
| 런타임 유형 #1~#12 정의 | IF 표준표 전문 (06) |
| 유형별 shall·위험 감각 | 8단계·GUID 본문 (08) |
| 설계서 필수 항목 · 검증 Gate | Control-M Job 내부 상세 (09) |
| 주/보조 유형 분리 원칙 | Hostname·용량 (03·05) |
| FAST/DEEP·채널 P95 감각 | RTO/RPO Drill 전문 (11) |

한 문장: **“어느 런타임 유형으로 흐르는가”를 고정**하고, **매체·표준·배치 FW 상세는 인접 정의서에 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 → A3 장표 재현 → A4 유형 트리
        │
        ├─ 채널·연계면 A5~A6
        ├─ 이벤트·데이터면 A7~A8
        ├─ 파일·배치면 A9
        ├─ 설계서 골격이 필요하면 A10
        └─ 적용·검증은 Part B
```

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다. Part A와 표현이 다르면 Part B의 shall/must/금지를 따른다.

## B1. 준수 의무

1. 신규 거래·배치·연계·파일·이벤트는 **유형 #**를 지정한 뒤 상세 설계한다.  
2. 유형 번호 없는 신설을 **금지**한다.  
3. 본 정의서와 충돌하는 설계는 **ADR 또는 Gap 등록·승인 전** 적용하지 않는다.  
4. IF 표준표·8단계·Control-M 내부를 본 장만으로 “확정”한 것처럼 서술하지 않는다.

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| 대유형 | 채널 · 연계 · 마케팅이벤트 · 데이터분석/제공 · 파일 · 배치 |
| 소유형 | 대유형 하위 #1~#12 |
| 주/보조 유형 | 한 업무가 복수 유형일 때 주 흐름과 보조 흐름을 분리 기록 |
| SLO | 유형별 응답·지연·완료 목표(01과 확정) |
| Evidence | Gate 통과를 증명하는 Runtime 산출물 |

## B4. 유형별 shall

> 08-22 상세분석(`런타임아키텍처_*업무처리유형_*`)의 E2E·Timeout·책임분리를 **규범 골격**으로 고정한다. 수치 SLO는 01과 확정.

### B4.1 채널 (#1~#3)

| # | shall | 위험 |
|---:|---|---|
| 1 | `/ins/{ServiceId}` · GUID 로그 · 08 8단계 · Direct면 앱 보안 직접 | 세션/브라우저 |
| 2 | MCA 경유 · FLAT↔JSON 변환은 MCA | MCA 장애=대면 중단 |
| 3 | 미니싱글뷰 Service(NH Cloud) · 동기 웹 | C/S·Web Context 혼재 |

채널은 사용자가 기다리는 **동기 거래**이므로 **P95 응답**을 핵심 지표로 한다. #2·#3도 동일 Timeout 계층 원칙을 쓴다(진입만 MCA/WebView).

#### B4.1.1 E2E 골격 — #1 정보계 단말 (대표)

```text
사용자 → 웹전용브라우저/Package UI
      → JSON/HTTP (+GUID)
      → 정보계 App (/ins/{ServiceId} · 08 8단계)
      → (필요) RDW/ADW · 대내 API
      → Sync Response → 단말
```

#### B4.1.2 Timeout budget (채널 · shall)

```text
Client/브라우저 Timeout
  > 채널·MCA·WebView Timeout
  > Application TX Timeout
  > 대내 API Timeout
  > DB Query Timeout
```

- **내부 ≤ 외부**: 하위 Timeout이 상위(사용자)보다 길면 **금지**(서버만 돌고 UI는 이미 포기).  
- 설계서에 **계층별 ms·측정 구간**을 기입한다(01 P95와 정합).  
- #2는 MCA 구간, #3은 WebView 구간을 별도 예산으로 분리한다.

| # | shall |
|---:|---|
| 11 | FOS 계약(06) · 완료 전 소비 금지 · ready→processing→done(또는 CREATED→…→CONSUMED) |
| 12 | **Control-M 중앙 통제** · FW 배치 표준. 온라인 WAS·앱 cron만으로 운영 배치 금지. 재기동 시 중복 적재 방지 |

#### B4.5.1 E2E 골격 — #11 FOS 파일

```text
App/Batch/DP → Staging/Landing
            → FOS (표준 진입·라우팅·상태)
            ├─ 대내/Legacy 직접 송수신
            └─ 대외 → MFT → 대외기관   (역방향: 대외→MFT→FOS→정보계)
            → (완료신호 후) ETL/Batch → RDW/ADW
```

**FOS ↔ MFT 책임 (shall)**

| 구분 | FOS | MFT |
|---|---|---|
| 위치 | 정보계 파일 IF **표준 허브** | 전송/Transport(주로 대외·기존) |
| 책임 | 계약·라우팅·상태·완료신호 | 전송·전송보안(제품 범위는 운영설계 확정) |
| 호출 | App/Batch → **FOS만** | App의 **직접 MFT 호출 금지** |

FOS=전달, ETL=내용 처리/적재, Batch=#12 실행 — 세 책임을 한 시퀀스에 뭉개지 않는다.

#### B4.5.2 E2E 골격 — #12 배치 (Control-M ↔ BatchStatus)

```text
Control-M (Calendar·선후행·SLA)
    → Batch AP / Agent
    → NH Cloud Batch FW (Job/Step · Checkpoint)
    → JDBC/ETL/FOS·API
    → BatchStatus/ExitStatus → OS exit → Control-M 성공조건
```

- Control-M 성공조건 ↔ FW **BatchStatus/ExitStatus**를 **표로 매핑**(09와 정합).  
- Agent timeout ≠ Job 실패로 단정하지 말고 **JobRepository·BatchStatus**를 확인한다.  
- 장애 복구 시 `업무 데이터` · `FW 메타` · `Control-M 상태` **삼자 일치** 후에만 완료로 본다.  
- Timeout budget: 배치 Window·Critical Path(분/시간)를 설계서에 명시(채널 초 단위와 혼용 금지).

## B5. 유형 설계서 필수 항목 (must)

```text
주 유형 # · 보조 # · 한 줄 목적 · 액터
시퀀스(1..n) · E2E 골격(ASCII 허용) · IF·표준표 No. · ServiceId/진입 URL
GUID·원거래글로벌ID · Owner · SLO(수치·측정구간)
Timeout budget(계층별) · 재시도·보상·재기동 · 모니터링 신호
(#11) FOS 상태모델·완료신호 · FOS/MFT 책임표
(#12) Control-M Job명 · BatchStatus/ExitStatus 매핑 · 선후행·멱등
상세분석 MD · VALIDATION 시나리오 ID
```

2. Runtime Evidence 보관.
