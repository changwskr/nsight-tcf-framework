# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 시스템 간 연계의 **표준 매체·계약·금지**를 고정한다. “어떤 IF를 고를지 절차”가 아니라 **표준표에서 행을 선택**하는 기준선이다.

```text
정보계 연계
        │
        ├─ 온라인 IF  (요청/응답 · API · 전문)
        ├─ 파일 IF    (파일 단위 송수신)
        └─ 데이터 IF  (DB↔DB · CDC · ETL)
```

목적(한 줄):

```text
자원 경합 최소화 + 플랫폼 독립성
        │
        ▼
표준 매체 · 계약 · 금지로 상시 경로 고정
```

| 축 | 고정 내용 |
|---|---|
| 구축 원칙 4줄 | 온/배 분리 · ETL 독립 · 이벤트 분리 · CDC 중계 |
| 온라인 표준표 | MCA·MCI·Direct·Cruz APIM·대외 APIM·GSE |
| 파일 표준표 | FOS 일원화 · 대외=FOS+대외MCA |
| 데이터 표준표 | CDC(실시간) · ETL(대량·보정·RDW→ADW) |
| 계약 | Interface ID · 멱등 · Timeout · RACI · Context |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 | 답하지 않는 것 |
|---|---|
| 3유형 분류 · 표준표(온/파일/데이터) | Zone 배치 상세 (02) |
| 경로별 shall/금지 · 계약 필수항목 | Hostname (05) |
| Context·연관도 갱신 의무 | 거래 8단계·GUID 스키마 (08) |
| 런타임 유형# 매핑 위치 | 런타임 시퀀스 전문 (07) |
| CDC vs ETL 책임 분리 | DB RAC 물리 (04) |

한 문장: **“어느 표준표 행으로 연계하는가”를 고정**하고, **전문·GUID·시퀀스는 08·07에 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 결론 → A3 3유형 → A4~A6 온/파일/데이터 도식
        │
        ├─ 계약·등록이 궁금하면 A7
        ├─ 07·08 연결이 궁금하면 A8
        └─ 적용·검증은 Part B
```

## A5. 온라인 경로 — 한눈에

```text
대면     통합업무 ── MCA ──────────────▶ 정보계
비대면   채널     ── MCI ──────────────▶ 정보계
정보단말          ── Direct ───────────▶ 정보계
Package UI        ── Direct ───────────▶ 정보계 솔루션
정보계 ↔ 대내     ── Cruz APIM (양방향)
정보계 ↔ 대외     ── API G/W   (양방향)
타법인 → 정보계   ── GSE
```

| No. | 소스 → IF → 타깃 | 성격 |
|---:|---|---|
| 1 | 통합업무 → **영업점 MCA** → 정보계 | 대면 전사 표준 |
| 2 | 비대면 → **MCI** → 정보계 | 비대면 전사 표준 |
| 3 | 정보계 단말 → **Direct** → 정보계 | 중계 없음 · 앱이 검증 |
| 4 | 패키지 UI → **Direct** → 솔루션 | **예외** 한정 |
| 5~6 | 정보계 ↔ **Cruz APIM** ↔ 대내 | 양방향 대칭 |
| 7~8 | 정보계 ↔ **API G/W** ↔ 대외 | 양방향 · DMZ 별도 |
| 9 | 타 법인 → **GSE** → 정보계 | 법인 간 표준 |

Direct ≠ 검증 생략. Package Direct는 08 표준전문 예외와 **함께** 기입. (**ANALYSIS**)

## A6. 파일 · 데이터 경로

### 파일

```text
단말 / 패키지 UI ── FOS ──▶ 정보계(솔루션)
정보계 ↔ 대내     ── FOS
정보계 ↔ 대외     ── FOS + 대외MCA

수신 상태: ready → processing → done
                         ↘ error (원본 보존 · 승인 후 재처리)
```

완료 전 소비 금지 = **Completion Signal** 이전 업무 반영 금지. (FACT)

### 데이터

```text
코어 DB ── CDC(실시간) ──▶ 정보계 DW
코어 BCV ── ETL ─────────▶ 정보계 DW
RDW ───── ETL ─────────▶ ADW
DW ↔ 타 시스템 DB ── ETL
```

| | CDC | ETL |
|---|---|---|
| 목적 | 커밋 변경 저지연 전파 | 대량·초기·마감·모델링 |
| 금지 | 대량 배치 책임 혼재 | “실시간처럼” 가장 |

## A7. 계약 · Context · Traceability

```text
유형 + 표준표 No. + 소스/IF/타깃
   + Interface ID + 프로토콜/전문
   + 멱등 · Timeout · 재시도 · 보상
   + SLA · RACI · 런타임# · Context 갱신일
   (+ ADR if 표준 외)
```

플랫폼 연관도(마케팅·데이터·BI·거버넌스·신용실적 등)는 연계 추가와 **동시 갱신**.  
코드만 넣고 Context 미갱신 = 개통 미충족. (FACT)

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다.

## B1. 준수 의무

1. 신규·변경 연계는 표준표에서 **행을 선택한 뒤** 구현한다.  
2. 표준표에 없는 매체는 **ADR 또는 표준 개정 승인 전** 상시 경로로 쓰지 않는다.  
3. 임시 FTP·직접 JDBC·공유폴더 직결을 상시화하지 않는다.  
4. 유형(온/파일/데이터) 미분류 연계의 개통·배포를 금지한다.  
5. 한 요구에 여러 유형이면 **표준표 행을 복수** 등록한다(시퀀스·계약을 섞지 않음).

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| 온라인 IF | 요청/응답형 화면·API·전문 연계 |
| 파일 IF | 파일 단위 송수신 연계 |
| 데이터 IF | DB↔DB 변경 전파·적재 연계 |
| IF 시스템 | MCA, MCI, Cruz APIM, GSE, FOS, CDC, ETL 등 표준 중계 |
| Direct | IF 시스템 미경유 — **예외·책임 가중** |
| Interface ID | 연계 계약 키 |
| Completion Signal | 파일 전송·준비 완료 신호. 이전 소비 금지 |
| 논리 API | API G/W 등록 호출 단위. 물리 서버 URL 아님 |

## B3. 정보계 구축 원칙 (must)

1. **온라인 AP / 배치 AP 자원 분리** — 실시간과 대량 자원 충돌 방지  
2. **ETL 서버 독립** — 대량 가공·정제 전용  
3. **이벤트 서버 분리** — Kafka 등 고속 실시간 오퍼링·수집  
4. **CDC 중계 제공** — 계정계 원천 변경 캡처·부하 분산  

## B4. 온라인 인터페이스 표준

### 표준표 (Baseline)

| No. | 소스 | IF 시스템 | 타깃 | 설명 |
|---:|---|---|---|---|
| 1 | 통합업무시스템 | **영업점 MCA** | 정보계 | 대면 채널 전사 표준 |
| 2 | 비대면 채널 | **MCI** | 정보계 | 비대면 채널 전사 표준 |
| 3 | 정보계 단말 | **없음(Direct)** | 정보계 | 중계 없이 거래 처리 |
| 4 | 패키지 UI | **없음(Direct)** | 정보계 솔루션 | 패키지 UI — **예외** |
| 5 | 정보계 | **API G/W (Cruz APIM)** | 대내 시스템 | 정보계→대내 |
| 6 | 대내 시스템 | **API G/W (Cruz APIM)** | 정보계 | 대내→정보계 |
| 7 | 정보계 | **API G/W** | 대외 기관 | 대외 전문 연계 |
| 8 | 대외 기관 | **API G/W** | 정보계 | 대외→정보계 |
| 9 | 타 법인 | **GSE** | 정보계 | 법인 간 전사 표준 |

정보계↔대내(No.5↔6), 정보계↔대외(No.7↔8)는 **동일 표준 매체**를 양방향 적용 (shall).

### 경로별 규범

| 경로 | shall | 금지 |
|---|---|---|
| MCA / MCI | 채널 표준 전문·세션 존중. 정보계는 논리 서비스만 노출 | 채널이 정보계 Hostname 직접 호출 |
| Direct(단말) | 인증·인가·입력검증·Rate Limit·감사·오류를 **앱이 직접** | “중계 없음 = 검증 생략” |
| Direct(Package) | 08 표준전문 **예외** 명시. 표 No.4만 | 신규 일반 API에 Direct 확대 |
| Cruz APIM | Gateway **등록 논리 API**만 호출 | 대내 서버 IP:port 하드코딩 |
| 대외 APIM | DMZ·인증서·암호화·재전송·대사·타임아웃 **별도** 정의 | “Gateway만 통과하면 끝” |
| GSE | 법인 코드·권한·전문 버전·장애 책임 **별도 계약** | 일반 대내 API와 동일 취급 |

| Hash | 무결성 검증 |
| Completion Signal | 완료 전 소비 금지 |
| Retry | 횟수·간격·상한 |
| 중복 방지 | File ID + 업무키 |
| 보존 | 위치·기간·파기 |
| SLA | 전송·처리 완료 시각 |
| RACI | 송신·수신·FOS(·대외MCA) Owner |

### B5.1 파일명 표준 구조 (shall)

```text
<interface-id>_<business-date>_<sequence>_<schema-version>.<extension>
예: FILEINFO001_20260823_0001_v1.dat
    FILEINFO001_20260823_0001_v1.dat.manifest
```

1. 파일명만으로 시스템·인터페이스·기준일·순번·버전을 식별할 수 있게 한다.  
2. 공백·제어문자·경로 구분자·OS 종속 특수문자 **금지**.  
3. 개인정보·계좌·고객명 등 **민감정보를 파일명에 포함 금지**.  
4. 동일 이름 덮어쓰기 금지 · 작성 중은 `.part`/`.tmp` 후 원자적 확정.  
5. 대소문자 정책·최대 길이를 계약에 명시한다.

### B5.2 Layout 유형 (shall)

| 유형 | shall |
|---|---|
| **Fixed Length** | Byte/문자 길이·Padding·숫자/날짜 형식·Header/Trailer 건수·합계 대사 |
| **CSV(Delimited)** | 구분자·Quote·Escape·Header·개행·Null/빈문자 구분 · Formula Injection 방지 |
| **JSON/XML** | Schema/XSD·버전 호환 · 대용량 Streaming · XXE·과도 중첩 방어 |
| **Binary** | 제품·버전·Endian·압축·Checksum · 전용 Reader/Writer·장기 호환 |

계약의 Layout 항목은 위 유형 중 하나를 명시하고 **버전·호환 정책**을 함께 둔다.

### B5.3 완료 신호 — Atomic Rename / Manifest (shall)

작성 중 파일 소비 **금지**. 아래 중 하나(또는 병행)를 **must**로 계약한다.

**A. Atomic Rename**

```text
<file>.part → 쓰기·fsync → Hash → 동일 FS 내 Rename → <file>.dat
```

**B. Manifest / Control File**

```text
Data File 전송 → Hash·건수 검증 → Manifest 마지막 전송
→ 수신자는 Manifest 존재 시에만 처리
```

Creating/Receiving과 Ready는 **동일 파일시스템**에 두어 Atomic Rename을 보장한다.

### B5.4 처리 상태 모델 (shall)

기존 요약 `ready → processing → done / error`를 확장한 **정식 상태**(전송≠업무 반영):

```text
CREATED → REGISTERED → TRANSFERRING → DELIVERED
  → VALIDATING → READY → PROCESSING → CONSUMED → ARCHIVED

실패: … → RETRY_WAIT → RETRYING → FAILED | QUARANTINED
```

| 상태 구간 | 대표 책임 |
|---|---|
| CREATED | 송신 업무 |
| REGISTERED~DELIVERED | FOS/대외MCA |
| VALIDATING~READY | 수신 Adapter/FOS |
| PROCESSING~CONSUMED | 수신 업무 |
| ARCHIVED | 계약상 보존 책임자 |
| FAILED/QUARANTINED | 원인별 송신·중계·수신 공동 |

전송 성공과 업무 반영 성공을 **분리 대사**(파일명+크기+Hash / Header·건수 / 업무키·합계).

### 경로별 shall

| 경로 | shall |
|---|---|
| 단말→FOS | 공유폴더/SFTP **직접 접근 금지**. 임시영역→완료 후 노출. 확장자·MIME·악성코드 검사 |
| 패키지→FOS | 제품 내부 경로에 타 시스템 의존 금지. 업그레이드 시 Adapter 회귀 |
| 정보계↔대내 | Manifest·완료신호 후 소비. 재전송 중복 반영 금지 |
| 대외 | 암호화·스케줄·대사에 대해 FOS vs 대외MCA **RACI 확정** |

### CDC vs ETL

| 구분 | CDC | ETL |
|---|---|---|
| 목적 | 커밋 변경의 낮은 지연 전파 | 대량·초기·마감·모델링 적재 |
| 금지 | 대량 배치 책임 혼재 | “실시간처럼” 가장 |

### CDC must

캡처 대상 · DDL 대응 · 커밋 순서 · 중계(Trail/큐) · I/U/D · 체크포인트 · 지연 SLA(측정 구간 ADR).  
계정계 과부하 방지: **Downstream 중계** 원칙.

### ETL must

추출 기준 시점 · BCV 완료→ETL 시작 선후 · Full/Incremental · CDC와 겹칠 때 우선순위·정합 시점 · RDW→ADW 시 품질검사.

명칭: `정보계 DW` / `DW` / `RDW`는 등록부에서 **논리명·물리·스키마·소유**로 매핑 (04와 정합).
