# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 모든 온라인 거래를 **동일 뼈대(8단계)·동일 전문·동일 GUID·동일 호출 규칙**으로 묶는다. End-to-End 추적과 업무 경계를 보장하는 Mechanism 기준선이다.

```text
어플리케이션 그룹(대구분 MP~IM)
  └─ 어플리케이션(업무구분)
       └─ 기능
            ├─ Controller  ←── ServiceId 1:1
            ├─ Service
            ├─ DAO
            └─ resource
```

목적(한 줄):

```text
동일 8단계 + 표준전문 + GUID + 호출 매트릭스
        │
        ▼
E2E 추적 · 업무 경계 · 채널~AP~대내통합 공통 언어
```

| 축 | 고정 내용 |
|---|---|
| 패키지 계층 | 대구분→앱→기능 · ServiceId↔Controller 1:1 |
| 거래 8단계 | 필수 1·4·8 · 선택 2·3·6·7 · 완료=8까지 |
| 표준전문 | FLAT↔JSON 동일 표준 · Package UI 예외 |
| GUID | R1~R5 · 채널 최초 설정 · 진행번호 +1 |
| 호출 | Controller→Service→DAO · 타 DAO 직접 금지 |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 | 답하지 않는 것 |
|---|---|
| 패키지·ServiceId · 8단계 | `/ins`·`/nb` 변환 상세 (09) |
| 표준전문 적용/예외 범위 | IF 매체표 (06) |
| GUID R1~R5 · 왕복 진행번호 | 런타임 유형 시퀀스 전문 (07) |
| 캐릭터셋 구간 원칙 | 물리 Hostname (05) |
| 업무 간 호출 매트릭스 | 분류 코드 사전 자체 (01·CMDB) |

한 문장: **“한 거래가 어떤 뼈대·전문·키로 흐르는가”를 고정**하고, **URL 변환·IF 매체·런타임 시퀀스는 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 결론 → A3 8단계 도식 → A4 패키지 트리
        │
        ├─ 전문이 궁금하면 A5
        ├─ GUID가 궁금하면 A6
        ├─ 호출 경계가 궁금하면 A7
        └─ 적용·검증은 Part B
```

## A5. 거래 8단계 — 한눈에

```text
[1 시스템 선] ████  자원·통제·입력로그·ServiceId 매핑
[2 공통 선]   ░░░░  앱 공통 정책
[3 업무 선]   ░░░░  서비스 사전조건
[4 Controller] ████  흐름 제어 · Service 0~n
[5 Biz Service]████* 업무 규칙 (*통상 존재)
[6 업무 후]   ░░░░
[7 공통 후]   ░░░░
[8 시스템 후] ████  Commit/Rollback · 출력·로그 · 자원 해제
```

완료 정의 (한 줄):

```text
4~5만 끝나고 응답 = 미완료
사용한 6·7 통과 + 8 커밋·출력 = 완료
예외 → 8에서 Rollback · primary vs cleanup 예외 분리 기록
```

| Step | 금지 (요지) |
|---:|---|
| 1·8 | 업무 if문으로 FW 경계 대체 |
| 2 | ServiceId별 거대 조건문 (고유→3) |
| 3·6 | DB 커밋·트랜잭션 가로채기 |
| 4 | SQL·DAO 직접 |
| 5 | 화면 전용 로직만 Service에 방치 |

## A6. 표준전문 · GUID

### 표준전문

```text
동일 표준전문 (논리)
   ├─ 구간 표현: FLAT  또는  JSON/HTTP
   ├─ MCA: FLAT ↔ JSON 변환·오류 매핑 책임
   ├─ Direct(단말): 인증·GUID·오류·거래로그 **동일 적용**
   └─ Package UI: 예외 (06 Direct No.4와 함께 명시)
```

| 대영역 | 적용 | 형식 요지 |
|---|---|---|
| 통합업무 · MCA | 적용 | FLAT → JSON/HTTP |
| 정보단말 · MCI · MP/BI AP · APIM | 적용 | JSON/HTTP |
| 패키지 UI | **예외** | 비표준 JSON/HTTP |
| GSE | 적용·중계 | FLAT 중심 |

설계서 한 줄 (must 개념):

```text
표준전문: 적용 | 예외(Package UI) · 구간형식: FLAT|JSON · 변환 책임 노드: …
```

### GUID

```text
채널 시스템 ──(R2 최초 설정)──▶ GUID
     │
     ▼ 노드 경유마다 진행번호 +1 (R4)
채널통합(2) → 정보계 AP(3) → 연계(4) → 복귀(5~7)
     │
     └─ 각 시스템 로그: 원거래글로벌ID로 E2E 조회 (R3)
```

| ID | 규칙 (요지) |
|---|---|
| R1 | 표준전문 내 GUID = 노드 간 식별자 (Package 제외 가능) |
| R2 | **채널**이 거래 시작 시 GUID 설정 |
| R3 | 로그는 원거래글로벌ID로 E2E 조회 가능 |
| R4 | 노드 경유 시 진행번호 +1 후 전달 |
| R5 | 응답 복귀까지 키 유지·전달 |

Gap (**ANALYSIS**): TCF/`pdmg-fw`에 진행번호 자동 +1 API가 없을 수 있음 → 누가 +1 하는지(어댑터 vs AP) **확정·Gap 등록**.

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다. PPT와 충돌하면 **본 정의서·메커니즘 MD**.

## B1. 준수 의무

1. 신규 ServiceId·기능은 계층·8단계·전문·GUID를 **충족**해야 한다.  
2. PPT 장표만 수정하고 메커니즘 MD·본 정의서를 갱신하지 않는 변경을 **금지**한다.  
3. 예외(Package UI 등)는 설계서에 **명시**한다.  
4. ServiceId 없이 URL만 있는 진입을 금지한다.  
5. 본 정의서와 충돌하는 설계는 **ADR/Gap 승인 전** 적용하지 않는다.

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| 표준전문 | 채널~AP~대내통합이 공유하는 논리 전문. 물리 표현은 FLAT 또는 JSON/HTTP |
| GUID | 거래를 노드 간 묶는 Correlation Key |
| 진행번호 | 노드 통과마다 +1 (왕복 모델 1~7) |
| 원거래글로벌ID | 각 시스템 로그에서 동일 거래 조회 키 |
| ServiceId | 서비스 식별자. Controller 메서드와 **1:1** |
| DTO | Controller ↔ Service 전달 객체 |
| Package UI 예외 | 표준전문·(일부) GUID에서 제외 가능 — **명시 필수** |

## B3. 패키지 · 계층 (shall)

```text
어플리케이션 그룹(대구분)     ← 01 정의서 MP/RD/AD/BI/DG/IM
  └─ 어플리케이션(업무구분)
       └─ 기능
            ├─ Controller  ←── ServiceId 1:1
            ├─ Service
            ├─ DAO
            └─ resource
```

1. 패키지 경로·resource 명은 분류 코드와 **동일 언어**.  
2. 타 그룹 코드를 패키지에 혼입하지 않는다.  
3. 단말 `/ins/{ServiceId}` 와 JSON `/nb/{ServiceId}` 는 **동일 Biz Service**로 합류 (09).

## B4. 거래 처리 8단계 (shall)

> 근거: `메커니즘_아키텍처표준_거래처리구조_분석.md`

| Step | 이름 | 필수 | 담당 | 책임(요지) |
|---:|---|---|---|---|
| 1 | 시스템 선처리 | **필수** | Framework | 자원 할당·거래 통제·입력 로그·ServiceId 매핑 |
| 2 | 공통 선처리 | 선택 | 애플리케이션 | 앱 공통 정책(타 앱에 강제하지 않음) |
| 3 | 업무 선처리 | 선택 | 서비스 | 서비스별 사전조건·필수값 |
| 4 | Controller 본처리 | **필수** | 개발 | 흐름 제어 · Service 0~n 호출 |
| 5 | Biz Service | **필수*** | 개발 | 업무 규칙 (*호출 0개 가능하나 통상 존재) |
| 6 | 업무 후처리 | 선택 | 서비스 | 처리 후 검증 |
| 7 | 공통 후처리 | 선택 | 애플리케이션 | 앱 공통 사후 검증 |
| 8 | 시스템 후처리 | **필수** | Framework | Commit/Rollback · 출력 조립·로그 · 자원 해제 |

### 완료 · 예외

1. 4~5만 끝나고 응답하면 **미완료**. 사용한 6·7 통과 + **8 커밋·출력**까지 끝나야 완료.  
2. 예외 시 8에서 Rollback.  
3. 후처리 예외가 나도 **primary exception**을 잃지 않도록 cleanup과 분리 기록.

### 단계별 금지

| Step | 금지 |
|---:|---|
| 1·8 | 업무 if문으로 FW 경계 대체 |
| 2 | ServiceId별 거대 조건문 폭주(고유 조건은 3으로) |
| 3·6 | DB 커밋·트랜잭션 가로채기 |
| 4 | SQL·DAO 직접 호출 |
| 5 | 화면 전용 로직만 Service에 방치(계층 혼선) |

### Controller ↔ Service

- 전달 객체는 **DTO**.  
- Controller 메서드 ↔ ServiceId **1:1**.  
- 한 Controller는 Service Biz를 0개 이상 호출할 수 있다.

| 채널 | **패키지 UI** | **예외** | 비표준 JSON/HTTP |
| 대고객 | 비대면 | 적용 | MCI 이후 JSON/HTTP |
| 채널통합 | 영업점 MCA | 적용·중계 | **FLAT ↔ JSON/HTTP** |
| 채널통합 | MCI | 적용·중계 | JSON/HTTP |
| 업무 | MP / BI 온라인 AP | 적용 | 표준 JSON/HTTP |
| 대내통합 | API Gateway | 적용·중계 | JSON/HTTP |
| 대내통합 | GSE | 적용·중계 | FLAT 중심 |
| 연계 | 대내 업무시스템 | 적용 | 유형별 표준 |

### 표현 원칙

1. FLAT와 JSON은 **서로 다른 전문이 아니라** 동일 표준의 구간별 표현.  
2. MCA는 FLAT↔JSON **변환·오류 매핑** 책임.  
3. Direct(정보단말)라도 인증·GUID·오류전문·거래로그 규칙은 **동일 적용**.  
4. Package 예외는 06 Direct 예외와 **함께** 설계서에 기입.

### 논리 전문 헤더 요약 (shall)

> 근거: `메커니즘_아키텍처표준화_전문표준화_분석.md` · 상세 필드명은 별도 필드정의서 확정

| 블록 | 최소 포함(개념) |
|---|---|
| **Header** | 전문 버전 · 거래 GUID · 진행번호 · 채널·기관 코드 · 서비스 코드 · 요청 일시 · 사용자·단말 · 길이/페이지/연속거래 |
| **Body** | 서비스별 요청/응답 데이터 |
| **Result/Error** | 성공 여부 · 표준 응답 코드 · 업무 오류 코드 · 사용자 메시지·추적 정보 |

```text

```

## B6. GUID (shall)

> 근거: `메커니즘_아키텍처_GUID관리체계정의_분석.md` · `GUID_관리_체계_분석.md`

### 5대 규칙

| ID | 규칙 |
|---|---|
| **R1** | 표준전문 내 GUID를 시스템 노드 간 식별자로 사용 (**Package UI 제외** 가능) |
| **R2** | **채널 시스템**이 최초 거래 시작 시 GUID를 규칙에 따라 설정 |
| **R3** | 각 시스템 로그는 **원거래글로벌ID**로 E2E 조회 가능해야 함 |
| **R4** | 시스템 노드 경유 시 GUID 내 **진행번호 +1** 후 다음 노드 전달 |
| **R5** | 응답 복귀까지 키를 유지·전달한다 |

### 왕복 진행번호 1→7 · 책임

| Step | 구간 | 진행번호 | +1 / 유지 책임(개념) |
|---:|---|---:|---|
| 1 | 채널 출발 | 1 | **채널**이 GUID 생성 · 진행번호=1 |
| 2 | 채널통합(MCA/MCI) | 2 | 채널통합이 검증·전달 · **+1** |
| 3 | 정보계 AP | 3 | Framework/AP 인바운드 경계 · **+1** |
| 4 | 대내통합/연계 | 4 | APIM·GSE·연계 어댑터 · **+1** |
| 5 | 연계→업무 복귀 | 5 | 복귀 경로 노드 · **+1** |
| 6 | 채널통합 복귀 | 6 | 채널통합 · **+1** |
| 7 | 최초 채널 응답 | 7 | 채널 · **+1** · 요청 GUID 일치 검증 |

- GUID 값 자체는 **변경 금지**. 진행번호만 노드 경유 시 증가.  
- 동일 시스템 내부 Controller→Service→DAO는 진행번호 대신 **span/로그**로 추적.  
- 단계 수는 토폴로지에 따라 달라질 수 있으나, **요청·응답 왕복에서 진행번호 단조 증가**는 유지.

### Gap · 확정 의무

메커니즘 분석상 TCF/`pdmg-fw`에 **진행번호 자동 +1 API가 없을 수 있다**.  
프로젝트는 “누가 +1 하는가”(MCA/MCI/APIM/GSE 어댑터 vs AP)와 스키마를 **확정**하고 Gap이면 Gap 문서에 등록한다.

### GUID 금지

- 채널 개시 거래에서 AP가 GUID를 **뒤늦게 생성**하여 채널 구간 추적이 끊기는 것  
- Package 예외를 문서화하지 않고 GUID를 생략하는 것  
- 중간 노드의 GUID **재발급·교체**(외부 GUID 매핑이 필요하면 별도 보존)

## B7. 캐릭터셋 · 업무 간 호출

### 캐릭터셋 (shall)

> 근거: `메커니즘_아키텍처표준화_캐릭터셋_분석.md` · `NSIGHT_캐릭터셋_정의_분석.md`  
> 한 줄: **채널·업무 UTF-8 / RDW·ADW MS949 / API G/W·GSE는 전사 IF 표준**

#### 영역별 기준

| 영역 | 구성요소 예 | Charset |
|---|---|---|
| 채널 | 정보단말 · Package UI | **UTF-8** |
| 업무 AP | 마케팅 · 신용실적 · BI/Self-BI/OLAP | **UTF-8** |
| DB | RDW · ADW | **MS949** (실제 NLS는 Runtime Evidence로 확정) |
| 전사 연계 | API G/W · GSE | **전사 인터페이스 기준** |

#### 변환 책임

| 흐름 | Source → Target | 변환 책임 |
|---|---|---|
| 채널↔업무 · 업무↔업무 | UTF-8 → UTF-8 | 변환 없음 |
| 업무 → RDW/ADW | UTF-8 → MS949 | **DB Access Boundary**(JDBC/세션) |
| RDW/ADW → 업무/BI | MS949 → UTF-8 | DB Access / 솔루션 Boundary |
| NSIGHT → API G/W·GSE | UTF-8 → 전사기준 | **Integration Boundary** |
| File/Batch | 규격별 명시 | Batch/File Adapter · 06 Layout과 일치 |

#### CHAR 규칙 (요약)

| ID | 규칙 |
|---|---|
| **CHAR-001** | 채널 UTF-8 |
| **CHAR-002** | 업무 애플리케이션 UTF-8/Unicode |
| **CHAR-003** | RDW/ADW는 장표 기준 MS949 · NLS 실측 확정 |
| **CHAR-004** | DB 변환은 데이터 접근 경계에서 **중앙 통제**(Controller/Service/화면 임의 변환 금지) |
| **CHAR-005** | API G/W·GSE는 전사 IF Charset 우선 |

#### 캐릭터셋 금지

- **이중 변환**(앱 수동 변환 + Driver/DB 재변환)  
- `getBytes()` 등 **Platform Default** Charset 의존  
- Character Length와 **Byte Length** 혼동(전문·DB·DTO 길이 단위 미구분)  
- MS949 미지원 문자를 `?`/대체문자로 **묵시 정상 처리**  
- 파일 IF Charset을 06 Layout과 **불일치**하게 운영
