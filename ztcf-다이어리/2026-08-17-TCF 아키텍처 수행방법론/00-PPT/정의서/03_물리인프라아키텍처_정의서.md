# Part A — Top-down 구조 이해

## A1. 핵심 결론

이 장은 논리기술아키텍처(02)의 논리 노드·컴포넌트를 **센터·환경·Hostname·HW/SW·용량**으로 매핑하고, 운영↔DR 대응을 표로 남겨 **동일 인벤토리**를 쓰게 한다.

```text
Logical Node (02)
        │
        ▼
Center · Env · Hostname · HW/SW · Capacity
        │
        ▼
Inventory (DNS / CMDB / IaaS / 모니터 / 백업 일치)
```

목적(한 줄):

```text
논리 없는 물리 신설 금지
환경별 구성도 분리
운영↔DR 대응 · SW·용량 근거 인용
```

| 축 | 장표의 정의 초점 | 핵심 대상 |
|---|---|---|
| 센터 | 의왕(주) · 안성(DR) · 순번 대역 | 인프라 |
| 매핑 | 논리→물리 must 필드 | 인벤토리·개통 |
| HA/DR 전제 | AP AA · L4 · 대응표 | 운영·11 |

### 이 문서가 답하는 것과 답하지 않는 것

| 답하는 것 (개요 수준) | 답하지 않는 것 (후속·인접) |
|---|---|
| 논리→물리 매핑 must | Hostname 12자리 코드표 상세 (05) |
| 센터·환경별 구성도 분리 | DB RAC/OGG·CDC 물리 세부 (04) |
| 운영↔DR Host 대응 | Zone·레이어드 논리 (02) |
| SW 종·버전 동기화 · 용량 인용 | 장애 Drill·RTO/RPO 전문 (11) |
| Inventory 일치 원칙 | 랙/케이블 시공 도면 |

한 문장: **“어느 논리가 어느 물리·센터인가”를 고정**하고, **명명·DB·Drill 상세는 인접 정의서에 위임**한다.

### 읽는 순서 권장

```text
A1 핵심 → A3 장표 재현 → A4 계층 트리
        │
        ├─ 센터·순번이면 A5
        ├─ 매핑·환경이면 A6~A7
        ├─ DR·HA면 A8
        ├─ SW·용량·인벤토리면 A9~A10
        └─ 적용은 Part B
```

## A5. 센터 · 순번 대역

```text
        의왕 (주센터)                 안성 (DR센터)
   ┌─────────────────────┐      ┌─────────────────────┐
   │ 운영 · 개발 · 선도  │      │ DR 인스턴스         │
   │ 검증 기본 배치      │      │                     │
```

## A6. 논리→물리 매핑 — 도식

```text
논리: 마케팅 WEB
  │
  ├─ 운영  의왕  sb….wb01 / wb02
  └─ DR    안성  sb….wb51 / wb52   ← 순번 51~99 (05)
```

| must 필드 | 검증 |
|---|---|
| 논리 노드명 (02와 동일) | 02에 존재 |
| 환경 | 구성도와 일치 |
| 센터 | 순번 대역과 정합 |
| Hostname (05 12자리) | 형식·사전·중복 |
| 대수 · Type | 용량 근거 |
| OS/플랫폼 | Hostname 플랫폼 코드 |
| 시스템 그룹 | Big Picture·논리 |
| SW 종·버전 | 목록과 일치 |

```text
규칙 감각:
  논리 1 → 물리 N (Scale-out) OK · 행마다 역할·그룹·환경 반복
  한 Host 복수 역할 → 대표 논리 + CMDB 부가
  선도 = 동일 Zone·논리 · 축소 대수만 · 사유 문서화
```

# Part B — 적용 규범

> 설계·구현·검토 시 **Part B를 우선**한다. Part A와 표현이 다르면 Part B의 shall/must/금지를 따른다.

## B1. 준수 의무

1. 논리기술아키텍처(02)에 **없는 논리 노드**로 물리 서버를 신설하지 않는다(예외 ADR).  
2. 환경(운영/DR/개발/선도/검증)별 구성도를 **혼재하지 않는다**.  
3. SW 구성도와 SW 목록의 제품·버전을 **동기화**한다.  
4. 대수·Mem·Scale-out은 용량 문서·인벤토리를 **근거로 인용**한다.

## B2. 용어 (규범용)

| 용어 | 정의 |
|---|---|
| 주센터 | 의왕 — 운영·개발·선도 중심 |
| DR센터 | 안성 — DR 인스턴스 |
| 논리 노드 | Hostname 이전 역할 단위. 물리 1대와 동일하지 않음 |
| Active-Active (AP) | AP를 동시에 살려 부하·장애 대비 |
| Inventory | Hostname·스펙·역할·SW가 일치하는 서버 목록 |
| IaaS | VM 위에 SW를 올리는 구성 전제 |

## B3. 센터 정의

| 센터 | 코드/위치 | 역할 (shall) |
|---|---|---|
| 의왕(주) | 주센터 | 운영·개발·선도·검증의 기본 배치. 순번 **01~49** |
| 안성(DR) | DR센터 | 운영 서비스의 재해복구 인스턴스. 순번 **51~99** |

1. 물리 행의 **센터** 필드는 의왕/안성(또는 승인된 센터명)으로 must 기입한다.  
2. DR Host를 주센터 순번 대역(01~49)에 두지 않는다.  
3. 개발/검증 Host에 DR 순번(51~99)을 할당하지 않는다(05와 동일).

## B4. 논리→물리 매핑

### B4.1 매핑표 must 필드

모든 물리 서버 행은 다음을 **must** 포함한다. 하나라도 없으면 인벤토리·개통 미완료로 본다.

| 항목 | 설명 | 검증 |
|---|---|---|
| 논리 노드명 | 02 정의서·컴포넌트와 **동일 명칭** | 02에 존재 |
| 환경 | 운영 / DR / 개발 / 선도 / 검증 | 구성도와 일치 |
| 센터 | 의왕 / 안성 등 | 순번 대역과 정합 |
| Hostname | 05 정의서 **12자리** 규칙 | 형식·사전·중복 |
| 대수 · Type | 대수, IaaS/x86/Exadata 등 | 용량 근거 |
| OS/플랫폼 | Linux/Windows/Exadata 등 | Hostname 플랫폼 코드 |
| 시스템 그룹 | Big Picture·논리 시스템 | App≠System 1:1 가능 |
| SW 종·버전 | 목록과 일치 | 구성도↔목록 |

### B4.2 매핑 규칙

1. 논리 1노드 → 물리 N대(Scale-out)는 허용하되, **역할·그룹·환경**을 행마다 반복한다.  
2. 한 Host에 복수 논리 역할을 올리면 **대표 논리 노드**를 Hostname 용도에 맞추고, 부가 역할은 CMDB 속성으로 남긴다.  
3. 선도(Pilot)는 운영과 **동일 Zone·논리 체계**, **축소된 대수**만 허용한다. 축소 사유를 문서화한다.

## B5. 환경별 구성도 분리

1. 운영 / DR / 개발 / 선도(및 검증) **구성도를 한 장에 섞지 않는다**.  
2. 참고 장표 계열: `물리기술아키텍처_하드웨어구성도_*` · `소프트웨어구성도_*`.  
3. 환경 간 복사 시 Hostname·순번·센터를 **반드시 재검증**한다.

## B6. 운영↔DR 대응

### B6.1 대응표 (must)

| 역할 | 운영 Host | DR Host | Traffic/전환 비고 |
|---|---|---|---|
| (예) 마케팅 WEB #1 | …01 | …51 | L4/GSLB 등 |

1. DR 서버는 운영 역할에 대한 **대응 관계**를 표로 유지한다.  
2. 법인·앱코드·플랫폼·환경(`o`)·용도는 동일하고, **순번만 DR 대역**(05).  
3. `01↔51` 식 1:1이 정책이면 할당표에 명시하고, 아니면 ADR로 할당 규칙을 고정한다.  
4. **물리 Host만 있고 앱·배치·DNS 전환 절차가 없으면** DR 미완성이다(11과 연계).

### B6.2 HA 연결 전제

- AP는 Active-Active 전제와 정합한다.  
- Traffic는 L4/GSLB 등 전환 구조를 갖춘다.  
- Rolling 배포 가능 여부를 HA-DR·11에서 확인한다.  
세부 RTO/RPO·장애 시나리오는 [`11_모니터링가용성DR백업_정의서.md`](./11_모니터링가용성DR백업_정의서.md).

1. 운영 SW 목록(제품 **종·버전**)을 변경관리 대상으로 둔다.  
2. 구성도에만 / 목록에만 있는 제품·버전을 **금지**(유령 SW).  
3. 버전 변경은 영향분석 → 변경관리 → 구성도·목록·인벤토리 **동시 갱신**.  
4. 용량은 시스템용량 분석 MD 및 인벤토리를 **근거로 인용**. 근거 없는 감 산정·임의 감축 금지.  
5. BI·마케팅 등 **개발/운영 분리 산정**을 존중한다.  
6. Gateway/Registry 등 공통은 HA 대수(예: 2)를 용량·구성도에 반영.  
7. 물리 확정 행은 `NSIGHT_서버_인벤토리_*`와 **일치**. DNS/CMDB/IaaS/모니터/백업 Hostname 불일치 시 **배포·개통 금지**.

### B7.1 Capacity Baseline 요약 (shall 인용)

산식: `환경 합계 ≈ 단일 구성 × 대수(인스턴스)`. 합계 행을 조달·할당 Baseline으로 쓴다. 앱 표 **CPU=0**은 무제한이 아니라 본 장표 범위 밖 산정으로 취급한다.

| 플랫폼 | 환경 | 대수/인스턴스 | Mem 합계 | Disk 합계 | 비고 |
|---|---|---:|---:|---:|---|
| BI포탈 | 개발 | 28 | 90 GB | 56 GB | CP·EX 고Mem |
| BI포탈 | 운영 | 28 | 102 GB | 56 GB | CP×5=40GB |
| 마케팅 | 개발 | 26 | 48 GB | 48 GB | |
| 마케팅 | 운영(허브+GW) | 31 | 92 GB | 62 GB | WAS Mem 상향 |
| 마케팅 | 운영(IMDG) | 7 | 280 GB | 80 GB | Gemfire VM · CPU 19 |
| 마케팅 | 운영(합산) | 38 | 372 GB | 142 GB | 허브+IMDG **항상 합산 보고** |

Registry·Gateway는 플랫폼별 **컨테이너 HA×2**. IMDG는 **VM**. 세부 행은 용량 MD·인벤토리 SSOT.

### B7.2 SW 범주 목록 → 인벤토리 SSOT

버전 확정값은 **소프트웨어목록·구성도·인벤토리**가 SSOT. 미기재 버전은 OPEN으로 두고 개통 전 확정.

| 범주 | 대표 제품(장표) | 버전(장표) |
|---|---|---|
| OS | Red Hat(IaaS) / AIX(물리) / Oracle Linux(Appliance) | 9.4 / 7.X / 미기재 |
| JAVA · WEB · WAS · F/W | JDK · Apache · Tomcat · NH F/W | 21 / 미기재 |
| DBMS | Oracle (Appliance) | 21Ai |
| 단말·BI·마케팅 | WebTopSuite · BI Matrix · Kafka | Kafka **4.X** · 그 외 미기재 |
| 거버넌스 | DQ Miner · Meta Miner · Data Hawk | 미기재 |
| CDC · ETL | GoldenGate(물리) · DataStage(개발 IaaS/운영 물리) | 미기재 |
| DevOps·품질·보고·이행 | GitLab · Runner · RD · OpenPOP · SQL Canvas | 미기재 |

## B8. 금지

- Hostname만 있고 논리 그룹·역할·환경 없음  
- 02에 없는 논리 노드로 서버 신설(ADR 없음)  
- 운영↔DR 대응표 없음 · DR Host만 존재  
- 구성도 ≠ 목록 버전 · 유령 SW  
- 용량 근거 없는 Scale-out/감축  
- 환경별 구성도 혼재  
- 개발 Host에 DR 순번 할당  

## B9. 검증 체크리스트

- [ ] 논리→물리 매핑표 must 필드 완비  
- [ ] 환경별 HW/SW 구성도 분리  
- [ ] 운영↔DR 대응표 · 순번 대역 정합  
- [ ] SW 종·버전 동기화(구성도↔목록↔인벤토리 SSOT)  
- [ ] Capacity Baseline 표·마케팅 허브+IMDG 합산 인용  
- [ ] SW 범주(미기재=OPEN) 개통 전 확정  
- [ ] 05 Hostname·계정·포트 교차 검증  
- [ ] HA/DR(11) 연결 전제 확인  
- [ ] 금지 항목 위반 없음
