# BOOK-WRITING-RULE.md

# PDMG 애플리케이션 아키텍처와 개발 가이드 — 집필 규칙

> 이 문서는 Codex가 `PDMG 애플리케이션 아키텍처와 개발 가이드`를 장기간 집필할 때 반드시 따라야 하는 최상위 집필 규칙이다.
> 목적은 자료를 요약하거나 파일 순서대로 재배열하는 것이 아니라, **현재 PDMG 구현을 근거로 독자가 이해하고 개발·운영·판단할 수 있는 전문 기술서**를 만드는 것이다.

---

## 1. 책의 정체성

도서명:

**PDMG 애플리케이션 아키텍처와 개발 가이드**

부제:

**pdmg-ui, pdmg-fw, pdmg-service, pdmg-jwt 기반 온라인 거래 시스템의 설계와 구현**

이 책은 다음 세 가지 성격을 동시에 가진다.

1. **아키텍처 설명서** — PDMG 전체 구조와 설계 의도를 설명한다.
2. **개발 가이드** — 신규 프로그램을 실제로 구현할 수 있도록 설명한다.
3. **운영·장애 대응서** — 거래 흐름, 트랜잭션, 로그, Timeout, JWT 등을 추적할 수 있도록 설명한다.

단순 API 레퍼런스, 소스 목록, 문서 요약집으로 작성하지 않는다.

---

## 2. 대상 독자

다음 독자를 동시에 고려한다.

- PDMG를 처음 접하는 신규 개발자
- 업무 Service 개발자
- Framework 개발자
- Application Architect
- 운영 및 장애 대응 담당자

초급자가 흐름을 따라갈 수 있어야 하지만, 아키텍트가 읽었을 때도 설계 판단 근거를 얻을 수 있어야 한다.

---

## 3. 가장 중요한 집필 원칙

### 3.1 요약하지 않는다

장이 뒤로 갈수록 설명을 짧게 만드는 것을 금지한다.

다음은 본문으로 인정하지 않는다.

```text
## Service의 책임

Service는 업무 로직을 처리한다.

- 입력값 검증
- Rule 호출
- DAO 호출
- DTO 반환
```

위 형태는 책 본문이 아니라 요약 노트다.

핵심 개념은 최소한 다음 질문에 답해야 한다.

```text
무엇인가?
→ 왜 필요한가?
→ 전체 구조의 어디에 있는가?
→ 누가 호출하는가?
→ 누구를 호출하는가?
→ 어떤 데이터를 받는가?
→ 내부에서 어떤 순서로 동작하는가?
→ 정상일 때 어떻게 끝나는가?
→ 실패하면 어떻게 되는가?
→ 실제 구현은 어디에 있는가?
→ 잘못 구현하면 어떤 문제가 생기는가?
→ 운영 시 무엇을 확인해야 하는가?
```

### 3.2 앞 장의 설명 깊이를 다음 장의 최소 하한선으로 사용한다

후반부라고 설명을 압축하지 않는다.

특히 다음 주제는 앞 장보다 오히려 더 깊게 작성한다.

- Transaction
- Thread
- Timeout
- TCF ON/OFF
- JWT
- RS256 / JWKS
- Exception
- ImageLog / GUID
- 환경설정
- CRUD 실전 개발
- Test / Quality

장의 길이를 기계적으로 맞출 필요는 없지만, **주제가 더 복잡한데 설명 밀도가 급격히 떨어지는 것은 실패**로 판단한다.

### 3.3 목차를 채우는 것이 목표가 아니다

제목 아래에 텍스트를 넣었다고 절이 완료된 것이 아니다.

절의 완료 기준은 다음과 같다.

> 독자가 해당 절을 읽고 Why, Where, Flow, How, Failure를 자신의 말로 설명할 수 있어야 한다.

## 4. 기본 자료에 대한 판단과 사용 원칙

현재 자료 세트에는 다음 유형이 함께 존재한다.

- 기본 설명 문서
- `-1.md` 재분석·정정 문서
- 아키텍처/흐름 다이어그램 문서
- 특정 기술 이슈 분석 문서
- 설계안 및 개선안
- 네이밍/개발 규칙
- CRUD 프롬프트 및 개발 가이드
- 트랜잭션/Timeout/JWT/Exception 등 심화 문서
- 책 전체 목차

이 자료 구성은 책 집필의 원천자료로 충분히 가치가 있다.

그러나 **파일을 그대로 이어 붙이면 안 된다.**

원본과 재분석본 사이에 구현 기준의 정정이 존재할 수 있고, 다이어그램은 설명을 돕는 자료이지 항상 사실 판정의 최종 근거가 아니다.

따라서 반드시 다음의 사실 우선순위를 적용한다.

---

## 5. 사실 판정 우선순위

### Priority 1 — 실제 소스 코드와 실행 설정

가능한 경우 가장 높은 우선순위를 가진다.

예:

- Java source
- `application.yml`
- `application-*.yml`
- Spring Configuration
- TransactionManager 설정
- Mapper XML
- Gradle 설정
- Bean 조건
- Test

현재 실제 구현을 설명하는 AS-IS는 가능한 한 소스와 설정으로 확인한다.

### Priority 2 — 소스 기반 재분석 문서 (`*-1.md`)

재분석 문서는 기존 설명을 현재 구현과 대조하여 정정한 자료로 취급한다.

기본 문서와 재분석본이 충돌하면 무조건 기본 문서를 따르지 않는다.

다음 순서로 판단한다.

```text
실제 소스/설정 확인
        ↓
재분석본의 근거 확인
        ↓
기본 문서와 차이 비교
        ↓
AS-IS 결정
```

### Priority 3 — 기본 설명 문서

개념, 설계 의도, 용어, 기본 흐름을 이해하기 위한 자료로 사용한다.

단, 현재 구현을 단정하는 근거로 사용할 때는 재분석본 및 소스와 충돌 여부를 확인한다.

### Priority 4 — 아키텍처/다이어그램 문서

다음 용도로 사용한다.

- 전체 구조를 한눈에 보여주기
- 실행 흐름 설명
- Thread 경계 설명
- Transaction 경계 설명
- 모듈 및 계층 관계 설명

다이어그램이 소스 또는 최신 분석과 충돌하면 다이어그램을 정답으로 취급하지 않는다.

필요하면 최신 구현에 맞게 다시 그린다.

### Priority 5 — 특정 이슈 분석·설계·Q&A 문서

예:

- Timeout 설계
- Rollback 분석
- TCF ON/OFF 분석
- JWT 검증 분석
- 성능감시
- 환경설정 영향도

이 자료는 심화 설명, 위험요소, TO-BE, 설계 판단을 보강하는 데 사용한다.

### Priority 6 — 프롬프트/작성 보조 자료

예:

- CRUD 서비스 프롬프트
- 범용 CRUD 프롬프트

이 자료는 책의 실전 개발부 또는 부록에 활용한다.

아키텍처 AS-IS의 최종 근거로 사용하지 않는다.

---

## 6. 소스를 확인할 수 없는 경우

소스 코드가 현재 작업 환경에 없으면 소스에서 확인한 것처럼 쓰지 않는다.

다음 중 하나로 표시한다.

- `문서 기준`
- `재분석 문서 기준`
- `설계안`
- `권장안`
- `확인 필요`

추측한 내용을 AS-IS로 단정하지 않는다.

---

## 7. AS-IS / TO-BE / 일반 기술 설명 분리

책 전체에서 다음 네 가지를 명확히 구분한다.

### AS-IS

현재 실제 PDMG 구현.

### TO-BE

향후 목표 구조 또는 개선 제안.

### 검토안

아직 결정되지 않은 설계 대안.

### 일반 기술 원리

Spring, MyBatis, JWT 등의 일반적인 기술 설명.

필요한 경우 다음 형식을 사용한다.

| 구분 | 내용 |
|---|---|
| AS-IS | 현재 구현 |
| 문제/제약 | 현재 구조에서 발생할 수 있는 문제 |
| TO-BE | 목표 구조 |
| 변경 영향 | 변경 시 영향 범위 |

AS-IS와 TO-BE를 하나의 사실처럼 섞어서 작성하지 않는다.

## 9. 장 집필 전 반드시 수행할 조사

N장을 작성할 때 최소 다음을 확인한다.

```text
전체 목차
N-2 장
N-1 장
N 장 목차
N 장 관련 문서
N 장 관련 다이어그램
관련 실제 소스 및 설정
N+1 장 목차
```

목적:

- 이전 장과 중복 방지
- 현재 장의 역할 확인
- 필요한 선행 개념 보완
- 다음 장의 영역을 미리 과도하게 침범하지 않기
- 앞 장과 설명 밀도 비교

## 10. 장별 Source Map을 내부적으로 만든다

집필 전에 현재 장의 근거를 다음처럼 정리한다.

```text
Chapter Source Map

[기본 문서]
- xx.md

[재분석 문서]
- xx-1.md

[다이어그램]
- xx.다이어그램.md

[실제 소스]
- package.Class
- application.yml
- Mapper.xml

[심화/설계 자료]
- xxx-design.md

[충돌 사항]
- 기존 문서 A 설명
- 재분석 문서 B 정정
- 실제 소스 판정
```

이 Source Map은 집필을 위한 내부 작업물이다.

책 본문에 파일 목록을 그대로 복사하지 않는다.

---

## 11. 원본과 재분석본 병합 규칙

기본 문서와 `-1.md`를 다음 방식으로 통합한다.

```text
기본 문서
   → 개념과 설계 의도

재분석 문서
   → 현재 구현 검증
   → 잘못된 설명 정정
   → 예외 조건
   → 운영/장애 관점

실제 소스
   → 최종 AS-IS 확인
```

두 문서를 순서대로 붙이지 않는다.

하나의 자연스러운 본문으로 재구성한다.

---

## 12. 자료를 읽은 순서대로 쓰지 않는다

다음 방식은 금지한다.

```text
문서 A 설명
→ 문서 B 설명
→ 문서 C 설명
→ 다이어그램 설명
```

독자가 이해하기 좋은 다음 구조로 재구성한다.

```text
문제
→ 개념
→ 전체 구조
→ 실제 실행 흐름
→ AS-IS 구현
→ 설정/소스
→ 정상 시나리오
→ 실패 시나리오
→ 주의사항
→ TO-BE 또는 판단
→ 체크리스트
```

## 13. 한 개념을 설명하는 표준 패턴

핵심 개념은 가능한 한 다음 순서로 설명한다.

### 13.1 What

무엇인지 정의한다.

### 13.2 Why

왜 필요한지 설명한다.

### 13.3 Where

전체 PDMG 아키텍처에서 어디에 위치하는지 설명한다.

### 13.4 Responsibility

무엇을 책임지고 무엇은 책임지지 않는지 구분한다.

### 13.5 Caller / Callee

누가 호출하고 누구를 호출하는지 설명한다.

### 13.6 Data

어떤 Header, DTO, Context, Service ID를 사용하는지 설명한다.

### 13.7 Flow

실제 실행 순서를 설명한다.

### 13.8 Implementation

실제 클래스, 패키지, 설정, Mapper 등을 연결한다.

### 13.9 Success

정상 종료 흐름을 설명한다.

### 13.10 Failure

예외, Timeout, Rollback, 오류 응답을 설명한다.

### 13.11 Anti Pattern

잘못된 구현 방법과 문제점을 설명한다.

### 13.12 Operation

로그, GUID, Service ID, 성능지표, 장애 추적 관점을 설명한다.

### 13.13 Architecture Decision

대안이 있는 경우 판단 기준을 설명한다.

## 14. 반드시 Why를 설명한다

다음처럼 규칙만 선언하고 끝내지 않는다.

```text
Facade에 @Transactional을 선언한다.
```

최소 다음 질문을 검토한다.

```text
왜 Facade인가?
현재 실제 최외곽 Transaction은 어디에서 시작되는가?
TCF ON/OFF에 따라 달라지는가?
Timeout ON/OFF에 따라 달라지는가?
기존 Transaction에 참여하는가?
업무 선후처리는 어느 Transaction에 참여하는가?
예외가 발생하면 어디까지 Rollback되는가?
```

## 15. 실행 흐름을 중심으로 작성한다

PDMG는 구조보다 **실제 실행 경로**가 중요한 시스템이다.

가능한 경우 다음과 같이 Caller → Callee 흐름을 보여준다.

```text
Browser
   ↓
pdmg-ui
   ↓
DefaultFilter
   ↓
ServicePreventionInterceptor
   ↓
OnlineTransactionController
   ↓
TcfFacade
   ↓
OnlineTimeoutExecutor
   ↓
TransactionDispatcher
   ↓
TransactionHandler
   ↓
Business Facade
   ↓
Business Service
   ├─ Rule
   └─ DAO
        ↓
      Mapper
        ↓
        DB
```

다이어그램 아래에는 반드시 단계별 해설을 작성한다.

---

## 16. Thread 경계를 숨기지 않는다

Thread가 바뀌는 곳은 반드시 표시한다.

예:

```text
Tomcat Request Thread
        │
        │ submit
        ▼
OnlineTimeoutExecutor
        │
        ▼
Worker Thread
        │
        ▼
TransactionTemplate
```

Thread가 변경되면 최소 다음을 확인한다.

- ServiceContext
- TransactionContext
- ThreadLocal
- MDC
- Spring Transaction
- JDBC Connection
- interrupt
- Future.cancel
- Deadline

무엇이 자동 전파되고 무엇을 명시적으로 전달해야 하는지 설명한다.

---

## 17. Transaction은 경계로 설명한다

`@Transactional` Annotation 자체를 설명하는 것으로 끝내지 않는다.

최소 다음 구조를 보여준다.

```text
TX BEGIN
   │
   ├─ Handler 또는 Facade 진입
   ├─ 업무 선처리
   ├─ Service
   ├─ Rule
   ├─ DAO / Mapper
   ├─ 업무 후처리
   │
   └─ COMMIT / ROLLBACK
```

다음 질문에 반드시 답한다.

- 누가 Transaction을 시작하는가?
- 어느 Thread에서 시작되는가?
- 어떤 TransactionManager를 사용하는가?
- Facade의 `@Transactional`은 새 TX인가 기존 TX 참여인가?
- Timeout ON/OFF에서 경계가 달라지는가?
- TCF ON/OFF에서 경계가 달라지는가?
- 업무 선후처리가 TX에 참여하는가?
- 시스템 선후처리는 TX 밖인가 안인가?
- 예외를 삼키면 어떤 문제가 생기는가?
- `REQUIRES_NEW`가 필요한 경우는 무엇인가?

---

## 18. Timeout은 단순 시간값으로 설명하지 않는다

Timeout 장에서는 다음을 분리한다.

- 요청 Thread의 대기 제한
- Worker Thread의 업무 실행
- Future timeout
- `cancel(true)`
- interrupt의 한계
- JDBC 작업 중단 가능성
- Deadline 재검사
- Rollback 조건
- Pool 포화와 Queue 포화
- Timeout(예: 504)과 Overload(예: 503)의 차이

"4초가 지나면 DB가 즉시 멈춘다"와 같은 단정은 실제 구현과 JDBC 특성을 확인하지 않고 사용하지 않는다.

---

## 19. TCF ON / OFF는 별도 실행 경로로 설명한다

TCF ON과 OFF는 단순 설정값 비교표로 끝내지 않는다.

각각 다음을 보여준다.

- HTTP 진입점
- Controller/Handler 사용 여부
- TcfFacade/Dispatcher 사용 여부
- Transaction 시작 위치
- Timeout 처리
- 업무 선후처리
- 예외 처리
- ImageLog
- 호환 목적

필요하면 두 실행 흐름을 나란히 비교한다.

---

## 20. JWT 장의 특별 규칙

JWT 관련 설명은 특히 AS-IS와 TO-BE를 분리한다.

다음을 혼합하지 않는다.

```text
현재 실제 검증 방식
목표 RS256 구조
JWKS 기반 Public Key 검증
SSO 연계 설계안
```

Private Key는 서명 시스템 밖으로 노출되지 않는 방향을 기본 원칙으로 설명하되, PDMG의 실제 구현 여부는 소스/설정으로 확인한다.

Token, Secret, Private Key, 개인정보를 로그 예제로 노출하지 않는다.

---

## 21. 환경설정은 실행 코드까지 연결한다

설정값을 나열하는 것으로 끝내지 않는다.

반드시 다음 흐름을 연결한다.

```text
application.yml
      ↓
Spring Environment
      ↓
@ConfigurationProperties / @Value
      ↓
Configuration / Conditional Bean
      ↓
생성되는 Component
      ↓
실제 요청 처리 변화
```

환경설정 장의 핵심은 **키 이름 암기**가 아니라 **설정 변경이 어떤 Bean과 실행 경로를 바꾸는지 이해하는 것**이다.

하지만 다음을 지킨다.

- 온라인 요청 흐름
- Layer
- Package
- TCF
- Transaction
- Thread
- Timeout

- Exception

### 금지

### 권장 방식

## 23. 표 사용 규칙

## 33. 정상 시나리오와 실패 시나리오를 모두 쓴다

중요 기능은 최소 다음 두 흐름을 보여준다.

### 정상

```text
Request
→ Validation
→ Execution
→ DB
→ Commit
→ Post Processing
→ Response
```

### 실패

```text
Request
→ Execution
→ Exception / Timeout
→ Rollback
→ Error Mapping
→ Logging
→ Error Response
```

JWT, Timeout, DB, 외부 Client 등은 주제별 실패 흐름을 별도로 설명한다.

## 42. 최종 성공 기준

이 책의 성공 기준은 Markdown 파일 33개를 만드는 것이 아니다.

독자가 1장부터 끝까지 읽었을 때 다음을 할 수 있어야 한다.

```text
PDMG 전체 구조 설명
        ↓
온라인 거래 경로 추적
        ↓
Service ID 해석/설계
        ↓
Handler / Controller 이해
        ↓
Facade / Service / Rule 구현
        ↓
DAO / Mapper 구현
        ↓
Transaction 경계 판단
        ↓
Timeout / Thread 동작 판단
        ↓
JWT 인증 흐름 이해
        ↓
Exception / GUID / ImageLog로 장애 추적
        ↓
환경설정 변경 영향 분석
        ↓
신규 CRUD 프로그램 구현 및 테스트
```

따라서 항상 다음을 기억한다.

> **목차를 채우지 말고 설명하라.**
>
> **문서를 요약하지 말고 독자가 이해하도록 재구성하라.**
>
> **무엇인지만 말하지 말고 왜 그렇게 설계되었는지 설명하라.**
>
> **구조만 보여주지 말고 실제 실행 흐름을 설명하라.**
>
> **정상 동작만 쓰지 말고 실패했을 때의 동작도 설명하라.**
>
> **코드를 보여주는 데서 끝내지 말고 아키텍처에서의 의미를 설명하라.**
>
> **앞 장보다 뒤 장을 이유 없이 얕게 쓰지 마라.**
>
> **책을 끝내는 것이 아니라 독자를 PDMG 개발자로 만드는 것이 목표다.**

## 43. Codex 장별 실행 명령의 기본 해석

사용자가 다음처럼 짧게 요청해도:

```text
23장을 집필해.
```

Codex는 이를 다음과 같이 해석한다.

```text
BOOK-WRITING-RULE.md를 최우선으로 적용한다.
전체 목차를 확인한다.
이전 2개 장과 다음 장 목차를 확인한다.
현재 장 관련 기본/재분석/다이어그램 자료를 모두 확인한다.
실제 소스와 설정을 확인할 수 있으면 반드시 확인한다.
AS-IS와 TO-BE를 분리한다.
요약본이 아니라 출판 가능한 본문을 작성한다.
이전 장의 설명 깊이를 최소 하한선으로 사용한다.
작업 완료 전에 품질 게이트를 수행하고 부족한 절을 보강한다.
```

이 규칙은 모든 장에 기본 적용된다.
