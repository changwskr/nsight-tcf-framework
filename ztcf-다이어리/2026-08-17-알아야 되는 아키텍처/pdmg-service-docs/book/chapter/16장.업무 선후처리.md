# 제4부 업무 진입과 유스케이스 경계

# 16장. 업무 선후처리

업무 Service마다 동일한 시작·종료 로그를 직접 작성하면 형식이 빠르게 달라지고, 신규 메서드에서 누락되기 쉽다. 반대로 공통 처리를 너무 강하게 만들면 모든 Service 호출에 DB 변경이나 예외 변환이 숨어 들어가 업무 흐름을 이해하기 어려워진다. PDMG는 Service 메서드 전후에 AOP를 적용해 업무 처리 구간을 관찰한다. 그 구현이 `BizPrePostAspect`다.

이 장에서 가장 중요한 구분은 **현재 구현과 확장 가능한 설계의 차이**다. AS-IS Aspect는 GUID·Service ID·호출 메서드·BRC와 정상 반환 DTO를 기록한다. 업무 검증, 후처리 UPDATE, 오류 이력 INSERT는 현행 코드에 들어 있지 않다. 다만 Pointcut이 Service이고 실행 시점이 일반적으로 업무 트랜잭션 안이므로, 향후 DB 후처리를 추가한다면 어떤 거래에 참여하는지 정확히 설계해야 한다.

## 이 장에서 해결할 질문

- `BizPrePostAspect`는 어떤 Bean이며 언제 생성되는가?
- 현재 Pointcut은 어느 패키지의 어떤 메서드에 적용되는가?
- 선처리와 정상 후처리는 실제로 무엇을 기록하는가?
- Service가 예외를 던질 때 오류 후처리가 실행되는가?
- 후처리 UPDATE를 추가하면 본 업무와 같은 트랜잭션으로 묶이는 조건은 무엇인가?
- 오류 이력을 `REQUIRES_NEW`로 분리해야 하는 경우와 그 비용은 무엇인가?
- 자기 호출과 비동기 Thread에서 Aspect·Transaction·Context는 어떻게 달라지는가?

## 전체 실행 위치

```text
Handler 또는 Controller
        │
        ▼
Business Facade / Service Transaction Proxy
        │
        ▼
Service Proxy
   ├─ PdmgBizTxFlowAspect(@Order 50)
   └─ BizPrePostAspect(@Order 100)
        ├─ @Before: 업무 선처리 로그
        ├─ Business Service
        │    └─ Rule → DAO → Mapper → DB
        └─ @AfterReturning: 정상 업무 후처리 로그
        │
        ▼
Facade 또는 상위 Worker TX로 반환
```

이 그림은 “Aspect가 트랜잭션을 시작한다”는 뜻이 아니다. `BizPrePostAspect`에는 `@Transactional`이나 `TransactionTemplate`이 없다. Transaction은 Timeout ON이면 Worker Executor, Timeout OFF에서 Facade를 통과하면 Facade 프록시, Service 자체 Annotation이 있는 우회 경로라면 Service 프록시가 맡을 수 있다. Aspect는 호출 시점에 이미 활성화된 트랜잭션이 있으면 그 Thread에서 함께 실행될 뿐이다.

## 16.1 BizPrePostAspect의 목적

`BizPrePostAspect`의 목적은 업무 Service라는 일관된 경계에 공통 관찰 코드를 결합하는 것이다. 시스템 Filter와 Interceptor가 HTTP 요청 전체를 보며 GUID와 전문을 다룬다면, 업무 Aspect는 “실제로 어느 Service 메서드가 시작되고 정상 종료했는가”를 기록한다. 두 계층을 구분해야 시스템 요청 수명과 업무 실행 수명을 혼동하지 않는다.

클래스는 `nhnis.mg.co.a.entry.aspect` 패키지에 있고 `@Aspect`, `@Component`, `@Order(100)`을 사용한다. Bean 생성 조건은 다음과 같다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.commons.legacy-web.enabled",
    havingValue = "true",
    matchIfMissing = true
)
```

따라서 해당 설정이 명시적으로 false이면 Aspect Bean이 생성되지 않는다. `matchIfMissing=true`이므로 키가 없으면 활성 쪽이다. 이 조건이 꺼진다고 Service 업무 자체가 중단되는 것은 아니다. 공통 업무 선후 로그가 사라진다. 설정 이름이 `legacy-web`인데 Service AOP까지 제어한다는 결합은 운영자가 영향 범위를 오해할 수 있는 AS-IS 제약이다. 향후 독립적인 업무 관찰 설정으로 분리하는 것은 TO-BE 검토 대상이다.

현행 책임은 로그와 추적이다. 트랜잭션 BEGIN·COMMIT, SQL, ImageLog 저장, Service ID 라우팅, 오류 응답 변환은 하지 않는다. Aspect를 “모든 공통 업무를 넣는 장소”로 사용하면 보이지 않는 부작용과 결합이 커진다.

## 16.2 현재 Service 포인트컷

실제 Pointcut은 다음과 같다.

```java
@Pointcut("execution(public * nhnis.mg.co.a.application.service..*(..))")
public void mgBizBoundary() {
}
```

`execution`은 메서드 실행 join point를 선택한다. `public *`는 모든 반환형의 public 메서드를, `application.service..*`는 해당 Service 패키지와 하위 패키지의 클래스를, `(..)`는 모든 인자 목록을 의미한다. 클래스 이름이 `Service`로 끝나는지를 검사하는 표현이 아니다. 패키지와 접근 제한자가 실제 적용 조건이다.

따라서 `nhnis.mg.co.a.application.service.mgcoa9000Service`의 public 메서드는 적용된다. 같은 클래스의 private helper는 외부 join point 대상이 아니며, `application.rule` 또는 다른 모듈의 Service는 이름이 같아도 이 Pointcut에 들어오지 않는다. 신규 업무 Service를 다른 패키지에 만들면 업무는 실행되지만 공통 선후 로그는 조용히 빠질 수 있다.

Pointcut을 Service에 둔 이유는 업무 실행 경계를 일관되게 잡기 위해서다. Facade에 두면 DTO 변환 실패까지 업무 시작으로 기록되고, TCF OFF Controller가 Service를 직접 호출할 때 선후처리가 빠진다. Handler에 두면 라우팅과 업무 실행이 섞이고 하나의 Handler 내부 분기를 Service 단위로 관찰하기 어렵다.

Pointcut이 넓기 때문에 같은 Service의 조회 helper public 메서드도 외부·내부 프록시 호출 방식에 따라 대상이 될 수 있다. 공개 메서드를 무분별하게 늘리지 말고 업무 진입 메서드와 내부 구현 메서드의 가시성을 의도적으로 결정해야 한다.

## 16.3 Facade 트랜잭션과 실행 순서

TCF ON + Timeout OFF 또는 Controller가 Facade를 호출하는 구조에서는 다음 순서가 일반적이다.

```text
Facade Transaction Proxy
   ├─ TX BEGIN
   ├─ DTO 변환
   └─ Service Proxy
        ├─ BizPrePostAspect.before
        ├─ Service 본문
        └─ BizPrePostAspect.after (정상 반환만)
   └─ COMMIT 또는 ROLLBACK
```

선처리와 정상 후처리가 같은 거래에 참여하는 이유는 `@Order(100)` 자체가 아니다. Facade 프록시가 Service 호출 전에 거래를 시작하고, Aspect Advice가 같은 Thread에서 실행되기 때문이다. 같은 `rdwTransactionManager`, 같은 DataSource, 기본 `REQUIRED`, 비동기 전환 없음이라는 조건도 유지되어야 한다.

TCF ON + Timeout ON에서는 Worker `TransactionTemplate`이 Dispatcher보다 바깥에서 TX를 시작한다. Handler와 Facade, Service Aspect는 모두 그 Worker Thread 안에서 실행되므로 같은 거래에 참여한다. Facade의 Annotation은 새 거래를 만들기보다 기존 거래에 참여한다.

TCF OFF Controller가 Service를 직접 호출하면 Facade TX가 없다. Service 메서드 자체에 `@Transactional`이 있으면 그 프록시 경계를 사용할 수 있지만, 선언이 없으면 Aspect가 실행되어도 DB 원자성은 보장되지 않는다. “업무 선후 로그가 보인다”와 “업무 트랜잭션이 존재한다”는 별개의 사실이다.

## 16.4 업무 선처리

현행 `before` Advice는 순서대로 업무 선처리 시작, 진행 정보, 선처리 종료, 업무처리 시작 로그를 남긴다. 진행 정보는 `ServiceContextHolder`에서 GUID와 Header의 `rms_svc_c`를 읽고, JoinPoint의 MethodSignature에서 `ServiceClass.method`를 만든다.

BRC는 메서드 인자를 순회하면서 `getTrtBrc`, `getBrc`, `getBRC`, `getL5104` 이름의 public getter를 반사 호출해 찾는다. Getter가 없거나 호출에 실패하면 다음 후보를 시도하고, 최종적으로 null일 수 있다. 이 방식은 여러 DTO 이름을 호환하지만 컴파일 시점 계약이 아니다. DTO getter 이름이 새로 바뀌면 업무는 정상 실행되면서 BRC 로그만 비게 될 수 있다.

```text
@Before
   ├─ bizPreStart
   ├─ GUID
   ├─ Service ID
   ├─ 호출 Service.method
   ├─ BRC
   ├─ bizPreEnd
   └─ bizProcessStart
```

선처리에서 ServiceContext가 없으면 코드가 null을 허용하므로 GUID와 Service ID가 null로 기록될 수 있다. Aspect가 Context를 새로 만들지 않는다. Context 생성·전파는 앞선 시스템 경계와 Worker Context의 책임이다.

현재 선처리는 입력 유효성 검증, 거래 통제, 사전 이력 INSERT를 수행하지 않는다. 이런 기능은 다이어그램의 확장 가능성일 수 있지만 AS-IS로 서술해서는 안 된다. 공통 업무 검증을 추가한다면 모든 Service 호출을 차단할 수 있으므로 대상, 예외 유형, 성능, ON/OFF 동등성, 테스트를 먼저 정의해야 한다.

## 16.5 Business Service 실행

`@Before`가 정상 종료되면 Spring이 실제 Service 메서드를 호출한다. Aspect는 Service 인자나 반환값을 업무적으로 변경하지 않는다. Service는 DTO를 받아 Rule과 DAO를 호출하며 자신의 업무 결과를 만든다. 세부 Service와 Rule의 책임은 다음 장에서 다룬다.

Service가 다른 Service Bean을 호출하면 호출 대상이 프록시를 통과하는 한 Aspect가 다시 적용될 수 있다. 이때 한 HTTP 거래 안에 업무 선후 로그가 여러 쌍 나타나는 것은 오류가 아닐 수 있다. 반면 같은 객체의 `this.method()` 호출은 프록시를 우회하므로 별도 쌍이 생기지 않는다.

Service 본문에서 RuntimeException 또는 checked Exception이 전파되면 `@AfterReturning`은 실행되지 않는다. 이 사실은 로그 해석에 중요하다. `bizProcessStart`는 있지만 `bizProcessEnd`와 `bizPostEnd`가 없다면 Service 실행 중 실패 가능성을 의심해야 한다. 단, 로그 설정이나 Aspect 비활성도 함께 배제해야 한다.

## 16.6 정상 업무 후처리

정상 후처리는 `@AfterReturning` Advice다.

```java
@AfterReturning(pointcut = "mgBizBoundary()", returning = "result")
public void after(JoinPoint joinPoint, Object result) {
    // 처리 종료, 후처리 시작, 응답 DTO, 후처리 종료 로그
}
```

Service가 정상 반환한 뒤 `bizProcessEnd`, `bizPostStart`, 업무 응답 메시지와 `PdmgMessagePrinter.businessDto(result)`, `bizPostEnd`가 출력된다. 결과가 null이어도 Advice 호출 자체는 정상 반환 흐름이다. DTO 출력은 로깅 유틸의 마스킹과 크기 제한 정책을 함께 확인해야 하며 Token, 개인정보, 비밀번호를 그대로 남겨서는 안 된다.

후처리는 Facade가 반환되기 전이다. 따라서 Facade가 시작한 TX 또는 Worker TX가 활성화된 상태에서 실행된다. 하지만 AS-IS 후처리에는 DAO 호출이 없다. “후처리가 같은 거래 안에 있다”는 실행 위치 판정과 “현재 후처리가 UPDATE한다”는 기능 사실을 구분해야 한다.

후처리 로그가 출력되었다고 커밋 완료를 뜻하지 않는다. Advice 뒤에 Facade 코드가 실패하거나 Worker deadline이 초과되면 최외곽 거래는 롤백될 수 있다. 운영 로그에서 `bizPostEnd`는 Service 정상 반환의 증거이지 DB COMMIT의 최종 증거가 아니다.

## 16.7 오류 업무 후처리

현재 Aspect에는 `@AfterThrowing`이나 예외를 감싸는 `@Around`가 없다. 따라서 Service 예외 시 별도의 업무 오류 후처리는 실행되지 않는다. `@AfterReturning`도 실행되지 않고 예외는 호출자 방향으로 전파된다. 오류 기록과 표준 응답은 다른 예외 처리 계층이 맡는다.

```text
Service 예외
   ├─ @AfterReturning 실행 안 함
   ├─ BizPrePostAspect가 예외를 삼키지 않음
   ├─ Facade/Worker까지 예외 전파
   └─ Transaction ROLLBACK 판정
```

향후 오류 후처리를 추가하려면 `@AfterThrowing` 또는 재전파를 보장하는 `@Around`를 사용할 수 있다. 이는 TO-BE 설계다. 오류 메타데이터 수집에 실패하더라도 원래 예외를 잃지 않아야 하고, 원인 체인과 GUID를 보존해야 한다. 오류 Advice에서 빈 응답을 반환하거나 원래 예외를 덮어쓰면 롤백과 장애 원인 분석이 왜곡된다.

오류 후처리의 목적도 구분한다. 실패 로그는 기존 로깅 채널로 남길 수 있지만, DB 오류 이력은 원거래 롤백과 함께 사라질 수 있다. 외부 모니터링 전송은 다시 실패하거나 지연될 수 있다. 모든 오류 동작을 Aspect 한 곳에 넣기보다 필수성, 원자성, 성능을 기준으로 나눈다.

## 16.8 후처리 UPDATE의 트랜잭션 참여

업무 정상 후처리에서 한 건을 UPDATE하고 본 업무와 같이 커밋·롤백하려면 다음 조건이 필요하다.

```text
동일 Thread
+ 이미 활성화된 업무 TX
+ 동일 rdwTransactionManager/DataSource
+ REQUIRED 참여
+ Service 정상 반환 뒤, 최외곽 COMMIT 전 실행
+ 후처리 예외를 숨기지 않음
= 본 업무와 후처리 UPDATE의 원자성
```

```text
TX BEGIN
   BizPre
   Service
      └─ 본 업무 UPDATE
   BizPost
      └─ 후처리 UPDATE
   정상 → 둘 다 COMMIT
   후처리 실패 → 예외 전파 → 둘 다 ROLLBACK
```

후처리 DAO가 `REQUIRES_NEW`를 사용하거나 다른 DataSource를 사용하면 같은 물리 거래가 아니다. `@Async`나 별도 Executor로 넘겨도 Thread-bound Spring Transaction이 전달되지 않는다. 후처리 코드가 SQLException을 catch하고 로그만 남기면 Service 호출은 정상 반환한 것으로 남아 본 업무만 커밋될 수 있다.

현재 Aspect에 UPDATE를 바로 추가하는 것은 신중해야 한다. 모든 Service 정상 반환마다 실행되므로 조회에도 쓰기 부작용이 생기고 readOnly 거래와 충돌할 수 있다. 어떤 서비스와 행위에서만 필요한지 Pointcut 또는 명시적 Annotation 계약을 설계하는 편이 안전하다.

## 16.9 오류 이력과 `REQUIRES_NEW`

실패 거래의 이력을 같은 TX에 INSERT하면 원거래 롤백과 함께 이력도 사라진다. 장애 감사상 오류 레코드가 반드시 남아야 한다면 별도 Spring Bean의 public 메서드에 `REQUIRES_NEW`를 적용해 독립 거래로 저장할 수 있다.

```text
원 업무 TX
   ├─ Service 실패
   ├─ ErrorHistoryService Proxy
   │     └─ REQUIRES_NEW BEGIN → INSERT → COMMIT
   ├─ 원래 예외 재전파
   └─ 원 업무 ROLLBACK
```

이 방식은 만능 해법이 아니다. 새 Connection이 필요해 Pool 압력을 높이고, 원거래가 잡은 Lock과 독립 이력이 접근하는 자원이 충돌하면 대기가 생길 수 있다. 원 업무가 최종 롤백되므로 이력에는 커밋되지 않은 업무 상태를 사실처럼 저장하지 않아야 한다. 오류 이력 저장 자체가 실패했을 때 원래 업무 예외를 덮을지도 정책으로 정해야 한다.

`REQUIRES_NEW` 메서드를 같은 Aspect 안에서 자기 호출하면 프록시를 통과하지 않아 독립 거래가 적용되지 않는다. 별도 Bean으로 분리해야 한다. 또한 DB 장애 자체가 원인이라면 같은 DB의 독립 거래도 성공하지 못할 수 있다. 반드시 남겨야 하는 운영 신호는 별도 로그·메트릭·외부 수집 경로와 함께 설계한다.

## 16.10 예외 재전파

트랜잭션 관리자는 경계 밖으로 전달된 예외와 롤백 규칙을 기준으로 완료를 결정한다. 오류 Advice가 다음처럼 예외를 정상 결과로 바꾸면 최외곽 경계는 성공으로 판단할 수 있다.

```java
try {
    return joinPoint.proceed();
} catch (Throwable cause) {
    saveError(cause);
    return new EmptyOutput(); // 금지: 실패 신호 소실
}
```

권장되는 개념 구조는 원래 예외를 보존해 다시 던지는 것이다.

```java
try {
    return joinPoint.proceed();
} catch (Throwable cause) {
    recordFailureSafely(cause);
    throw cause;
}
```

위 코드는 오류 후처리를 도입할 때의 개념 예제이며 현행 Aspect 구현은 `@Around`가 아니다. 재전파할 때 새로운 일반 예외로 무조건 감싸면 표준 오류 코드와 원인 타입이 사라질 수 있다. 필요한 맥락만 추가하고 cause를 유지한다.

오류 이력 저장 실패와 원래 업무 실패가 동시에 일어날 때 무엇을 우선할지도 결정해야 한다. 보통 클라이언트와 롤백에는 원래 업무 예외를 유지하고, 이력 실패는 별도 운영 로그로 남기는 편이 원인 보존에 유리하다. 보안 정보와 입력 전문 전체는 예외 메시지에 포함하지 않는다.

## 16.11 자기 호출과 AOP

Service 프록시가 `methodA()`를 가로챈 뒤 실제 객체 안에서 `this.methodB()`를 호출하면 `methodB()`는 프록시를 다시 통과하지 않는다.

```text
외부 → Service Proxy → BizPre → methodA
                              └─ this.methodB
                                 Aspect 재적용 없음
                        BizPost
```

따라서 두 메서드가 모두 public이고 Pointcut 표현식에 맞아도 자기 호출에는 별도 선후 로그가 생기지 않는다. `methodB`의 별도 Transaction Annotation도 같은 이유로 적용되지 않을 수 있다. 한 유스케이스 내부 helper라면 선후처리가 한 번만 실행되는 것이 오히려 맞을 수 있다.

반대로 `methodB`가 독립 업무 경계여서 별도 관찰과 거래 정책이 필요하다면 다른 Bean으로 분리한다. 자기 프록시 주입으로 우회하는 기술보다 도메인 책임과 유스케이스 경계를 먼저 명확히 하는 것이 중요하다.

## 16.12 비동기 실행 시 제약

Spring Transaction과 `ServiceContextHolder`, MDC는 기본적으로 Thread에 결합된다. Service나 후처리에서 `@Async`, `CompletableFuture`, 임의 Executor를 사용하면 호출 Thread의 상태가 자동으로 동일하게 이어진다고 가정할 수 없다.

```text
업무 Worker Thread                  Async Thread
TX / Context / MDC
   │ submit ───────────────────────▶ 기본적으로 별도 상태
   ├─ 원 업무 계속
   └─ COMMIT/ROLLBACK               독립 성공/실패
```

같은 트랜잭션에 반드시 묶어야 하는 후처리는 비동기로 보내지 않는다. 독립 실행이 맞다면 필요한 GUID와 최소 Context를 값으로 캡처하고, 새 Thread에서 설치·정리하며, 별도 Transaction과 재시도·중복 정책을 정의한다. mutable `ServiceContext` 객체 자체를 두 Thread가 공유하면 동시 변경과 정리 시점 문제가 생길 수 있다.

AS-IS Timeout Executor는 요청 Context를 Worker로 명시적으로 캡처·설치·정리한다. 이것이 임의 비동기 작업까지 자동 전파한다는 뜻은 아니다. 개발자가 추가한 Executor는 별도의 전파 전략이 필요하다.

## End-to-End 정상·실패 흐름

```text
정상
Facade/Worker TX → @Before 로그 → Service → DAO
                 → @AfterReturning 결과 로그 → COMMIT

Service 실패
Facade/Worker TX → @Before 로그 → Service 예외
                 → @AfterReturning 없음 → 예외 전파 → ROLLBACK

선처리 실패(향후 로직 추가 시)
Facade/Worker TX → @Before 중 예외 → Service 미실행
                 → 예외 전파 → ROLLBACK

후처리 UPDATE 실패(향후 로직 추가 시)
Facade/Worker TX → Service 정상 → 후처리 UPDATE 예외
                 → 예외 전파 → 본 업무와 함께 ROLLBACK
```

## 두 Aspect의 실행 순서를 로그로 읽기

업무 Service에는 `BizPrePostAspect`뿐 아니라 `PdmgBizTxFlowAspect`도 적용될 수 있다. 후자는 Handler, Facade, Service, DAO 계층의 시작·종료 흐름을 관찰하는 `@Around` Advice이며 `@Order(50)`이다. 숫자가 작은 Advisor가 일반적으로 바깥쪽에서 감싸므로 Service 호출을 개념적으로 다음처럼 읽을 수 있다.

```text
PdmgBizTxFlowAspect 진입(@Order 50)
   └─ BizPrePostAspect.before(@Order 100)
        └─ 실제 Service 메서드
   └─ BizPrePostAspect.afterReturning
PdmgBizTxFlowAspect 정상 종료
```

그러나 Order 숫자만으로 Transaction Advisor와의 절대 순서를 단정해서는 안 된다. Transaction은 Facade나 Worker라는 다른 호출 경계에서 이미 시작될 수도 있고, Service 자체 Annotation과 여러 Advisor가 겹치면 실제 프록시 체인을 확인해야 한다. 테스트에서는 `TransactionSynchronizationManager.isActualTransactionActive()`를 관찰용으로 사용해 Advice 시점의 활성 여부를 검증할 수 있다. 이 값을 운영 업무 로직의 분기 조건으로 사용하면 테스트와 프록시 구성에 결합되므로 권장하지 않는다.

로그가 정상이라면 계층 흐름 시작, 업무 선처리, 업무 처리, 업무 후처리, 계층 흐름 종료가 논리 순서로 보인다. Service 예외라면 업무 후처리 로그가 없고 바깥 `@Around`의 실패 종료 로그 또는 공통 예외 로그로 이어져야 한다. 같은 GUID에서 시작 로그만 반복되고 종료 로그가 없다면 장시간 SQL, Thread 중단, 프로세스 종료, 비동기 분리 가능성을 함께 살핀다.

`log.info`는 `BizPrePostAspect` 클래스에서 직접 호출된다. 로그 패턴의 `%C.%M`에 실제 Aspect 위치를 남기려는 의도다. `PdmgTxLog`가 문자열을 조립하더라도 Logger 호출 주체는 Aspect다. 운영 검색은 메시지 문구 하나에만 의존하지 말고 logger class, GUID, Service ID, Thread를 조합해야 문구 변경에 견딜 수 있다.

## Context와 인자 추출의 실패 경계

선처리 로그의 데이터는 두 경로에서 온다. GUID와 Service ID는 Thread-bound `ServiceContextHolder`에서 오며, BRC는 Service 메서드 인자의 getter에서 온다. 이 출처를 구분하면 빈 로그의 원인을 빠르게 좁힐 수 있다.

```text
ServiceContextHolder
   ├─ guid
   └─ header.sys_comm.rms_svc_c

JoinPoint.args
   └─ getTrtBrc / getBrc / getBRC / getL5104
```

GUID와 Service ID가 함께 null이면 HTTP 앞단에서 Context가 생성되지 않았거나 Worker 전파·설치가 실패했을 가능성이 있다. GUID는 정상인데 BRC만 null이면 해당 DTO가 후보 getter를 제공하는지, 인자가 null인지 확인한다. BRC null이 곧 업무 오류를 뜻하지는 않는다. 현재 추출 로직은 로그 보강을 위한 best-effort다.

반사 호출은 `ReflectiveOperationException`을 무시하고 다음 이름을 시도한다. 이 때문에 getter 내부 예외나 접근 문제도 로그 누락으로 보일 수 있다. 공통 관찰이 본 업무를 막지 않게 한 선택이지만, 반복 누락을 운영자가 감지하기 어렵다는 대가가 있다. TO-BE에서는 공통 인터페이스, 명시적 메타데이터, 안전한 DTO Accessor를 검토할 수 있다. 다만 모든 DTO에 BRC가 존재한다는 전제를 강제하기 전에 거래별 계약을 분류해야 한다.

Context를 Advice에서 수정하는 것도 피해야 한다. 같은 mutable 객체가 Facade, Service, DAO 로그와 Worker 정리에 사용되므로 선후처리에서 Service ID나 GUID를 바꾸면 요청 전체의 추적 연결이 깨진다. Context는 관찰용으로 읽고, 업무 결과는 DTO와 명시적 반환값으로 전달하는 편이 안전하다.

## 후처리 기능을 추가하기 전의 설계 질문

공통 후처리 요구가 생기면 곧바로 `after()`에 DAO를 주입하기보다 네 가지 질문을 먼저 답한다. 첫째, 모든 Service 정상 반환에 필요한가 아니면 특정 Annotation이 붙은 유스케이스에만 필요한가. 둘째, 후처리 실패가 본 업무를 실패시켜야 하는가. 셋째, 조회의 readOnly 거래에서도 실행 가능한가. 넷째, 중첩 Service 호출에서 한 번만 실행해야 하는가 또는 매번 실행해야 하는가.

예를 들어 “모든 변경 거래의 처리 건수를 감사 테이블에 저장한다”는 요구는 조회를 제외하고 최외곽 유스케이스당 한 번 실행되어야 할 수 있다. 현재 패키지 public 메서드 Pointcut에 단순 INSERT를 넣으면 하나의 Facade가 Service A와 Service B를 호출할 때 두 건이 저장되고, Service A가 다른 Service Bean을 호출하면 더 늘어날 수 있다. Service ID 행위 코드나 명시적 Annotation, 중첩 깊이를 판정하는 설계가 필요하다.

후처리 결과가 본 업무의 정합성 일부라면 같은 TX에서 실패를 전파한다. 단순 통계나 비핵심 로그라면 DB 실패 때문에 고객 거래를 롤백할지 신중해야 한다. 독립화할 경우에는 `REQUIRES_NEW`, 이벤트, 메시지, 커밋 후 callback 중 요구에 맞는 방식을 고른다. 각 선택은 실패 시점과 관찰 가능성이 다르다.

커밋 후 처리가 필요하면 `@AfterReturning`만으로는 충분하지 않다. 이 Advice는 Service 정상 반환 뒤이지만 물리 커밋 전일 수 있다. 실제 커밋 성공 뒤에만 외부 알림을 보내려면 Transaction synchronization 또는 Outbox 같은 구조를 검토해야 한다. 이 역시 현재 구현이 아니라 설계 선택이다.

## 장애 증상별 추적 절차

“업무 선처리 로그가 없다”면 먼저 Aspect Bean 조건을 확인한다. 다음으로 Service 클래스의 실제 package와 public 여부, Spring Bean 호출인지, 자기 호출인지 확인한다. Handler·Facade 로그도 없다면 더 앞선 라우팅 실패일 수 있다. Service 실행 결과는 있는데 로그만 없다면 Pointcut 또는 설정 문제 가능성이 높다.

“선처리는 있는데 후처리가 없다”면 Service 예외와 Timeout을 먼저 찾는다. 현재 후처리는 정상 반환 전용이다. 예외 로그가 없더라도 Worker가 아직 SQL에서 실행 중이거나 프로세스가 중단됐을 수 있다. 동일 GUID의 Request Thread와 Worker Thread 타임라인을 나란히 본다.

“후처리 로그가 있는데 DB가 롤백됐다”는 현행 구조에서 가능한 결과다. 후처리 로그 이후 Facade 또는 Worker deadline 검사에서 실패할 수 있기 때문이다. 후처리 완료를 Commit 완료 지표로 사용한 모니터링 규칙을 수정해야 한다.

“오류 이력이 없다”면 저장 Transaction을 확인한다. 원거래 TX 안에서 INSERT했다면 전체 롤백으로 사라지는 것이 정상이다. `REQUIRES_NEW`인데도 없다면 별도 Bean 프록시 호출 여부, 같은 DB 장애, Pool 고갈, 이력 Service 내부 예외 삼킴을 차례로 본다.

## 책임과 경계

| 구성 요소 | Caller | 책임 | 다음 호출 | 금지 책임 |
|---|---|---|---|---|
| Facade/Worker TX | Handler·TcfFacade | 유스케이스 원자성 | Service | 업무 로그를 거래마다 복제 |
| `BizPrePostAspect` | Service Proxy | Service 전후 공통 관찰 | Service 실행 | SQL·커밋·응답 변환 |
| `PdmgBizTxFlowAspect` | AOP Proxy | 계층 TX-FLOW 로그 | 대상 메서드 | 업무 정책 |
| Business Service | Facade | 업무 흐름 | Rule·DAO | 공통 HTTP 처리 |
| 오류 이력 Service(TO-BE) | 오류 Advice | 독립 오류 저장 | DAO | 원래 예외 대체 |

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | Service 패키지 public 메서드에 `@Before`, `@AfterReturning` 적용 |
| AS-IS | GUID·Service ID·메서드·BRC와 정상 결과 DTO 로그 |
| AS-IS | 오류 Advice, DB 선후처리, `REQUIRES_NEW` 오류 저장 없음 |
| AS-IS | `legacy-web.enabled`가 Bean 생성까지 제어 |
| 제약 | getter 이름 반사 탐색으로 BRC 계약이 컴파일 시점에 보장되지 않음 |
| TO-BE 검토 | 독립 enable 속성, 명시적 업무 경계 Annotation, 민감정보 로깅 정책 |
| TO-BE 검토 | 오류 이력이 필수일 때 별도 Bean과 독립 TX, 실패 격리 정책 |

## Anti Pattern

첫째, Aspect에 모든 업무 검증과 DB 변경을 넣는 방식이다. 호출부에서는 보이지 않는 부작용이 모든 Service에 생기고 조회도 쓰기로 변할 수 있다. 둘째, 오류를 catch한 뒤 빈 결과를 반환하는 방식이다. 롤백 신호와 표준 오류가 사라진다.

셋째, `@Order(100)`이 트랜잭션 참여를 보장한다고 믿는 것이다. 참여 여부는 외부 TX, Advisor 순서, Thread, Manager와 전파 속성의 조합이다. 넷째, 자기 호출과 비동기 호출에도 Aspect가 자동 적용된다고 가정하는 것이다. 둘 다 프록시·Thread 경계를 확인해야 한다.

다섯째, DTO 결과 전체를 항상 로그로 남기는 방식이다. 개인정보·Token·대용량 목록이 포함될 수 있다. 마스킹과 크기 제한, 환경별 로그 수준이 필요하다. 여섯째, 실패 이력을 같은 거래에 저장하면서 롤백 후에도 남을 것으로 기대하는 방식이다.

## 실전 검증 시나리오

정상 Service 호출 테스트에서는 선처리 시작·종료, 업무처리 시작·종료, 후처리 시작·종료의 상대 순서와 GUID·Service ID를 확인한다. Service가 예외를 던지는 테스트에서는 `@AfterReturning` 로그가 없고 예외가 동일 원인으로 외부까지 전파되는지 확인한다.

설정 테스트에서는 `legacy-web.enabled=false`일 때 Aspect Bean과 로그만 사라지고 Service 결과는 유지되는지 본다. 신규 Service 패키지 테스트에서는 Pointcut 포함 여부를 검증한다. BRC getter가 없는 DTO와 여러 getter 후보가 있는 DTO도 로그 값 판정이 예상과 같은지 확인한다.

후처리 DB 변경을 도입할 때는 정상 동시 커밋, 후처리 실패 전체 롤백, checked Exception 롤백, readOnly 조회 충돌, 다른 DataSource 사용을 검증한다. 오류 `REQUIRES_NEW`를 도입하면 원거래 롤백 후 이력만 남는지, 이력 저장 실패 때 원래 예외가 보존되는지, Connection Pool 포화 시 영향을 확인한다.

비동기 테스트는 호출 Thread와 실행 Thread 이름, Transaction 활성 상태, GUID·MDC 전파와 finally 정리를 검증한다. Timeout ON에서는 Worker 안에서 Aspect가 실행되는지, deadline 초과 후 정상 후처리 로그가 나타났더라도 최종 롤백되는 경우를 구분한다.

## 개발자·운영자 체크리스트

- 신규 Service가 Pointcut 대상 패키지의 public 메서드인가?
- `legacy-web.enabled`의 환경별 값과 영향 범위를 확인했는가?
- GUID와 Service ID가 ServiceContext에서 올바르게 읽히는가?
- BRC getter 이름이 현재 추출 규칙과 맞는가?
- 정상 반환에서만 후처리 로그가 나온다는 점을 모니터링 규칙에 반영했는가?
- 선후처리 로그와 실제 COMMIT 로그를 동일시하지 않는가?
- DB 후처리는 조회를 포함한 모든 Service에 적용되지 않도록 범위를 제한했는가?
- 본 업무와 함께 롤백할 후처리가 같은 Thread·Manager·DataSource를 쓰는가?
- 오류 이력의 생존 요구를 먼저 정의한 뒤 `REQUIRES_NEW`를 선택했는가?
- 오류 처리 후 원래 예외를 반드시 재전파하는가?
- 자기 호출 또는 직접 생성 Bean으로 프록시를 우회하지 않는가?
- 비동기 작업에 Context·MDC·TX가 자동 전파된다고 가정하지 않는가?
- 결과 DTO 로그에 민감정보와 대용량 데이터가 노출되지 않는가?

## 아키텍처 판단 포인트

공통 처리를 AOP에 둘지는 횡단성, 가시성, 실패 의미로 결정한다. 거의 모든 Service에 동일하고 업무 결과를 바꾸지 않는 관찰은 AOP에 적합하다. 특정 유스케이스만의 검증과 상태 변경은 명시적 Service·Facade 호출이 더 읽기 쉽다.

후처리 DB 작업은 원자성 요구가 핵심이다. 본 업무의 일부라면 같은 TX에서 실패를 전파한다. 실패해도 본 업무 성공을 유지해야 한다면 독립 실행과 재처리 정책이 필요하다. 오류 이력은 원거래 롤백 후 생존해야 하는지에 따라 `REQUIRES_NEW`를 결정하며, 단지 “이력 테이블이니까” 독립시키지 않는다.

Pointcut은 패키지 규약을 강제하는 보이지 않는 계약이다. 패키지 기반 선택은 단순하지만 이동에 취약하다. 규모가 커지면 명시적 Annotation이나 인터페이스를 검토할 수 있으나, 누락 방지 테스트와 운영 가시성을 함께 설계해야 한다.

## 핵심 정리

현행 `BizPrePostAspect`는 업무 Service public 메서드 전후의 로깅 Aspect다. `@Before`는 GUID·Service ID·호출 메서드·BRC와 구간 로그를 남기고, `@AfterReturning`은 정상 결과와 후처리 종료를 기록한다. 오류 후처리와 DB 변경은 현재 구현되어 있지 않다.

업무 선처리·Service·정상 후처리가 같은 트랜잭션에 참여하는 것은 외부 거래가 먼저 시작되고 같은 Thread에서 실행되기 때문이다. TCF ON + Timeout ON에서는 Worker TX, Timeout OFF에서는 Facade TX가 대표 경계다. Facade를 우회하면 Service 자체 TX 여부를 다시 확인해야 한다.

후처리 UPDATE를 추가한다면 실패를 재전파해야 본 업무와 함께 롤백된다. 반드시 남겨야 하는 오류 이력은 별도 Bean의 `REQUIRES_NEW`를 검토할 수 있지만 Connection, Lock, 원인 보존과 저장 실패 정책을 함께 다뤄야 한다. 다음 장에서는 이 Aspect가 감싸는 Business Service와 Rule이 실제 업무 흐름과 계산 책임을 어떻게 나누는지 살펴본다.
