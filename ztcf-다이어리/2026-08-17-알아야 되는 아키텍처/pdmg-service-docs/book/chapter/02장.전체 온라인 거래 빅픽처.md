# 2장. 전체 온라인 거래 빅픽처

1장은 PDMG를 구성하는 모듈과 핵심 용어를 한 장의 지도처럼 펼쳐 보였다. 이제 그 지도 위에서 요청 한 건이 실제로 움직이는 과정을 따라갈 차례다. 이 장은 사용자가 화면에서 거래를 실행한 순간부터 업무 DB 처리와 HTTP 응답이 끝날 때까지를 시간순으로 추적한다.

한 줄로 그리면 Browser → UI → HTTP → Filter → Interceptor → TCF → Handler → Facade → Service → DAO → DB → Response다. 그러나 이 한 줄만 외우면 장애를 제대로 설명할 수 없다. 어느 구간이 Request Thread에서 실행되는지, 어디에서 Worker Thread로 바뀌는지, 온라인 요청의 생명주기와 DB 트랜잭션이 어디서 겹치고 갈라지는지까지 알아야 한다.

> **현행 기준**
> 이 장은 `nhnis.fw.tcf.enabled=true`, `nhnis.fw.timeout.enabled=true`, `nhnis.fw.commons.legacy-web.enabled=true`, `nhnis.fw.commons.filter.enabled=true`인 로컬 AS-IS를 주 흐름으로 삼는다. 원천 다이어그램과 실제 구현이 충돌하면 `pdmg-fw`, `pdmg-service`, `pdmg-ui`의 현재 소스와 `application.yml`을 우선한다.

### 이 장에서 해결할 질문

- Browser에서 시작한 요청은 어떤 순서로 업무 DB까지 이동하는가?
- HTTP 요청, 시스템 선처리, TCF, 업무 처리와 시스템 후처리의 경계는 어디인가?
- 정상 결과와 예외는 어떤 경로로 응답 전문이 되는가?
- Request Thread와 Worker Thread는 어디에서 바뀌며 무엇을 전달해야 하는가?
- 온라인 거래와 DB 트랜잭션은 왜 같은 개념이 아닌가?
- 타임아웃 ON과 OFF에서 실행 스레드와 트랜잭션 시작점은 어떻게 달라지는가?

## 2.1 한눈에 보는 전체 요청 흐름

다음 그림은 TCF와 온라인 타임아웃이 모두 켜진 현행 기본 경로다. 바깥 상자는 HTTP 요청의 생명주기이고, 가운데 Worker 상자는 별도 스레드에서 실행되는 TCF와 업무 처리다. DB 트랜잭션은 Worker 안에서만 열린다.

```text
Browser
  │ 화면에서 거래 실행
  ▼
pdmg-ui :8090
  │ POST http://localhost:8080/{serviceId}
  │ JSON { hdr_nhnis, dto }
  ▼
════════════════════ HTTP Request Thread ════════════════════
DefaultFilter
  │ Body 캐시 · Header/GUID · ServiceContext · 조건부 JWT
  ▼
ServicePreventionInterceptor.preHandle
  │ 요청 로그 · ImageLog 선처리
  ▼
OnlineTransactionController
  │ Service ID 결정 · dto 분리
  ▼
TcfFacade
  │ TransactionContext 생성
  ▼
OnlineTimeoutExecutor ── capture/submit ────────────────┐
  │ Request Thread: Future.get(timeout) 대기            │
  │                                                     ▼
  │                         ┌──── Worker Thread ─────────────────────┐
  │                         │ ServiceContext/MDC 설치               │
  │                         │ TransactionTemplate(rdw) BEGIN        │
  │                         │   → TransactionDispatcher            │
  │                         │   → TransactionHandler               │
  │                         │   → Facade(@Transactional REQUIRED)  │
  │                         │   → BizPrePostAspect.before          │
  │                         │   → Service → DAO → Mapper → DB      │
  │                         │   → BizPrePostAspect.afterReturning  │
  │                         │ COMMIT 또는 ROLLBACK                 │
  │                         │ ServiceContext/MDC 정리               │
  │                         └───────────────────────────────────────┘
  ◀──────────────────────── 결과 또는 예외 ───────────────────┘
  ▼
GlobalExceptionHandler(알려진 예외인 경우)
  ▼
ResponseBodyArgumentResolver
  │ 성공 { hdr_nhnis, dto } / 알려진 실패 { hdr_nhnis, result }
  ▼
ServicePreventionInterceptor.afterCompletion
  │ ImageLog 후처리 또는 예외 기록
  ▼
DefaultFilter.finally
  │ Request Thread의 ServiceContext/MDC 정리
════════════════════════ HTTP Response ═══════════════════════
  ▼
pdmg-ui → Browser 화면 반영
```

이 흐름에서 가장 중요한 사실은 세 가지다. 첫째, Filter부터 TcfFacade까지와 응답 후처리는 Servlet Request Thread에서 실행된다. 둘째, 타임아웃이 활성화되면 Dispatcher 이하가 `pdmg-online-*` Worker Thread에서 실행된다. 셋째, 업무 DB 트랜잭션은 HTTP 요청 전체를 감싸지 않고 Worker의 `TransactionTemplate` 안에서 시작되어 업무 결과가 확정될 때 끝난다.

1장의 구조도가 “누가 존재하는가”를 설명했다면, 이 그림은 “누가 먼저 실행되고 어느 경계에서 다음 책임으로 넘기는가”를 보여 준다. 이후 절은 이 그림을 구간별로 확대한다.

## 2.2 UI에서 업무 DB까지의 호출

실제 사례로 거래 파라미터 목록 조회 `mgcoa9000S0`를 따라가 보자. 사용자가 PDMG 화면에서 조회를 실행하면 UI는 검색 조건과 페이징 정보를 `dto`에 넣고 업무 서버로 POST 요청을 보낸다. 현행 `service-client.js`의 기본 경로는 브라우저가 `http://localhost:8080/mgcoa9000S0`를 직접 호출하는 방식이다.

```text
사용자 조회 실행
  → pdmg-ui JavaScript
  → POST /mgcoa9000S0
  → OnlineTransactionController
  → mgcoa9000Handler
  → mgcoa9000Facade.mgcoa9000S0(Object)
  → mgcoa9000Service.mgcoa9000S0(mgcoa9000S0DTOin)
  → mgcoa9000DAO
  → rdw.mg.co.a/mgcoa9000-ORA.xml
  → H2(local) 또는 RDW DB
```

UI는 직접 호출 외에도 `/api/relay/{id}` 호환 경로를 제공한다. Relay를 쓰면 Browser → `pdmg-ui` Controller → `TransactionRelayService` → `pdmg-service`로 HTTP 경계가 하나 더 생긴다. 업무 실행 경로는 같지만 네트워크 오류와 타임아웃의 관찰 지점이 달라진다. 이 장의 주 흐름은 현행 기본인 브라우저 직접 호출이며, Relay를 사용하는 경우 UI 서버 구간을 앞에 하나 추가해서 읽으면 된다.

요청 본문은 공통 헤더 `hdr_nhnis`와 업무 데이터 `dto`의 봉투 구조를 사용한다. 로컬 프로파일에서는 공통 헤더가 없더라도 Filter가 기본 Header를 만들 수 있지만, 비-local 환경에서는 누락 시 400으로 종료될 수 있다. 로컬 편의 동작을 외부 계약으로 사용해서는 안 되는 이유다.

Controller는 Service ID를 확정하고 `dto` 노드만 TCF에 넘긴다. Dispatcher는 `mgcoa9000S0`를 등록한 `mgcoa9000Handler`를 선택한다. Handler는 Service ID에 따라 Facade 메서드를 고르고, Facade가 `Object` 형태의 dtoBody를 `mgcoa9000S0DTOin`으로 변환한다. Service는 조회 조건과 페이징 값을 구성하고 DAO를 호출한다. DAO와 Mapper XML이 SQL을 실행한 뒤 결과를 DTOout으로 조립한다.

이 단계별 위임은 긴 호출 체인을 만들기 위한 것이 아니다. HTTP 계약, 거래 선택, 유스케이스 경계, 업무 절차와 데이터 접근을 분리하여 어느 지점의 실패인지 식별하기 위한 구조다. 각 계층의 세부 책임과 허용 의존 방향은 3장에서 설명한다.

## 2.3 HTTP 요청 구간

HTTP 요청 구간은 브라우저가 요청을 전송한 시점부터 응답 Body가 전송되고 Servlet 처리가 끝날 때까지다. PDMG 온라인 거래와 DB 트랜잭션은 이 구간 안에 포함되지만, HTTP 구간 전체와 동일하지는 않다.

브라우저 직접 호출에서는 서로 다른 Origin인 8090에서 8080으로 요청하므로 CORS 검사가 선행된다. `pdmg-service`의 로컬 설정은 `http://localhost:8090`과 `http://127.0.0.1:8090`을 허용한다. CORS가 실패하면 요청이 업무 Controller에 도달하지 않거나 브라우저가 응답을 화면 코드에 노출하지 않는다. 이 경우 서버 업무 로그보다 브라우저 개발자 도구의 Network와 Console을 먼저 봐야 한다.

AS-IS의 `service-client.js`는 `Content-Type`과 `Accept`를 보내지만 `Authorization`을 자동으로 구성하지 않는다. local 프로파일은 Filter에서 JWT 검증을 생략하므로 이 차이가 드러나지 않는다. 같은 UI를 비-local 환경에서 사용하면 올바른 토큰을 발급받았더라도 요청에 Bearer Token이 실리지 않아 Filter에서 401로 끝날 수 있다. 로그인 성공, 토큰 보관, HTTP Header 전달과 서비스 검증은 하나의 연속된 인증 흐름으로 확인해야 한다.

HTTP Body는 다음 처리 단계에서도 다시 읽어야 한다. Servlet 요청 스트림은 기본적으로 한 번 읽으면 소진되므로 `DefaultFilter`는 Body를 캐시하는 Wrapper를 사용한다. Filter가 파싱한 원문은 ServiceContext와 Request attribute에 보관되고, Interceptor의 요청 로그와 Controller의 JSON 역직렬화가 같은 요청을 일관되게 볼 수 있다.

```text
[HTTP 요청 시작]
  Browser fetch
    → CORS
    → Servlet Filter Chain
    → Spring MVC HandlerMapping
    → HandlerInterceptor.preHandle
    → Controller 호출
    → ReturnValue 처리 / ResponseBodyAdvice
    → HandlerInterceptor.afterCompletion
  Filter finally
[HTTP 요청 종료]
```

HTTP 상태는 처리 구간을 알려 주는 단서다. 400 또는 401이 Filter에서 즉시 반환되면 TCF와 업무 코드는 실행되지 않았다. 503은 타임아웃 작업 풀 포화로 Worker 작업이 수락되지 않았을 가능성이 있다. 504는 Request Thread가 제한 시간 안에 Worker 결과를 받지 못했음을 뜻한다. 500은 Handler 미등록, 업무 예외 또는 그 밖의 서버 오류일 수 있으므로 오류 전문과 GUID를 함께 봐야 한다.

HTTP 구간의 종료와 DB 작업의 종료가 항상 동시에 일어나는 것은 아니다. 특히 Future timeout 후 `cancel(true)`는 Worker에 interrupt를 요청할 뿐, JDBC 드라이버와 SQL이 즉시 중단된다는 보장은 없다. 클라이언트가 504를 받은 뒤에도 Worker 정리 로그를 확인해야 하는 이유다.

## 2.4 시스템 선처리 구간

시스템 선처리는 업무 종류와 관계없이 요청을 안전하게 실행할 준비를 하는 구간이다. 현행 AS-IS에서는 하나의 STF 호출로 모여 있지 않고 `DefaultFilter`와 `ServicePreventionInterceptor.preHandle`에 나뉘어 있다.

### DefaultFilter: HTTP 요청을 공통 실행 상태로 바꾸는 단계

Filter는 요청 Body를 캐시하고 JSON을 읽어 `hdr_nhnis`를 구한다. GUID와 Service ID, 요청 URI, 사용자·IP 관련 정보를 ServiceContext와 Log4j2 ThreadContext에 반영한다. 현재 프로파일이 local이면 JWT 검증을 건너뛰고, 비-local이면 `Authorization: Bearer ...`를 확인하여 `JwtProvider`로 검증한다.

검증 실패는 업무 예외와 경로가 다르다. 토큰이 없거나 유효하지 않으면 `sendError(401)`, Body가 비었거나 JSON/Header가 잘못되면 `sendError(400)`로 Filter Chain을 끝낸다. Controller가 호출되지 않으므로 TCF의 `GlobalExceptionHandler`나 표준 `{hdr_nhnis, result}` 조립을 항상 기대할 수 없다.

### ServicePreventionInterceptor.preHandle: 거래 직전의 관찰 지점

Spring MVC가 대상 Controller를 찾은 뒤 Interceptor의 `preHandle`이 실행된다. 이 단계는 ServiceContext와 GUID를 보완하고 요청 전문을 로그에 출력하며 `ImageLogHandler.preImagelog`를 호출한다. 따라서 업무가 실패하더라도 “어떤 전문이 들어왔는가”를 남길 수 있는 위치다.

```text
DefaultFilter
  ├─ 요청 형식과 인증 단계에서 거부 가능
  ├─ ServiceContextHolder.setInstance(...)
  └─ filterChain.doFilter(...)
       ↓
ServicePreventionInterceptor.preHandle
  ├─ GUID 확인·보정
  ├─ 요청 전문 로그
  └─ ImageLog 선처리
       ↓
Controller 진입 허용
```

시스템 선처리는 업무 DB 트랜잭션 밖에서 실행된다. 그 목적은 업무 commit 여부와 무관하게 요청을 검증하고 추적 정보를 남기는 것이다. 반대로 선처리에서 업무 테이블을 변경하면 나중의 업무 rollback과 원자적으로 묶이지 않을 수 있다. 시스템 감사 데이터와 업무 데이터의 일관성 요구를 구분해야 한다.

원천자료 일부는 `TcfFacade`가 `stf.preProcess()`를 호출하는 그림을 사용한다. 현행 `TcfFacade`에는 해당 호출이 없다. 이 장에서 “시스템 선처리”는 실제 Filter와 Interceptor 실행 구간을 뜻하며, STF는 개념적 이름으로만 사용한다.

## 2.5 TCF 거래 실행 구간

TCF 구간은 HTTP 요청을 Service ID 기반 업무 실행으로 전환한다. `OnlineTransactionController`, `TcfFacade`, `OnlineTimeoutExecutor`, `TransactionDispatcher`와 업무 `TransactionHandler`가 이 연결을 만든다.

`OnlineTransactionController`는 `/online`, `/{businessCode}/online`, `/{serviceId}`를 받을 수 있다. Service ID는 공통 Header의 `rms_svc_c`, 요청 JSON, Path 순으로 결정한다. 둘 이상의 값이 달라도 현행은 불일치를 거부하지 않고 우선순위가 높은 값을 사용한다. Controller는 dtoBody를 분리해 `TcfFacade.process(serviceId, dtoBody)`를 호출한다.

`TcfFacade`는 Request Thread의 현재 ServiceContext와 Service ID를 묶어 `TransactionContext`를 만든다. 그 다음 실제 Dispatcher 호출을 `OnlineTimeoutExecutor.execute()`에 Callable로 전달한다. 여기까지는 아직 업무 Handler를 실행하지 않았다.

타임아웃이 활성화된 현재 설정에서 Executor는 다음 순서로 동작한다.

```text
Request Thread
  1. ServiceContext와 MDC 스냅샷 capture
  2. Worker Pool에 Callable submit
  3. Future.get(5000ms)로 결과 대기

Worker Thread(pdmg-online-*)
  4. ServiceContext와 MDC install
  5. TransactionTemplate(rdwTransactionManager, REQUIRED) BEGIN
  6. TransactionDispatcher.dispatch(...)
  7. serviceId에 대응하는 TransactionHandler.handle(...)
  8. 결과 반환 또는 예외 전파
  9. deadline/interrupt 재검사
 10. COMMIT 또는 ROLLBACK
 11. ServiceContext와 MDC clear
```

Dispatcher는 애플리케이션 시작 시 모든 `TransactionHandler`의 `serviceIds()`를 읽어 Map을 구성한다. 같은 Service ID가 두 번 등록되면 시작 단계에서 실패하고, 요청 시 등록되지 않은 Service ID를 받으면 `ServiceHandlerNotFound`를 던진다. Handler는 다시 Service ID를 분기하여 해당 Facade 메서드를 호출한다.

이 설계에서 Handler까지 Worker의 외곽 트랜잭션 안에 들어간다. 다만 Handler의 책임은 라우팅이며 업무 SQL을 직접 실행해서는 안 된다. 외곽 TransactionTemplate이 존재하더라도 Facade를 우회하면 DTO 변환과 유스케이스 경계가 흐려지고 TCF OFF 경로와의 일관성도 깨진다.

현행 `TcfFacade`는 `stf.preProcess()`와 `etf.postProcess()`를 명시적으로 호출하지 않는다. 오래된 다이어그램의 STF → Dispatcher → ETF 흐름은 목표 개념으로 읽어야 하며, AS-IS 실행 순서는 위 소스 흐름을 기준으로 한다.

## 2.6 업무 처리 구간

업무 처리 구간은 Handler가 Facade를 선택한 뒤 Service와 DAO가 결과를 만드는 구간이다. `mgcoa9000S0` 조회에서는 Facade가 dtoBody를 입력 DTO로 바꾸고, Service가 페이징 조건을 계산하며, DAO와 Mapper가 count와 목록 SQL을 실행한다.

```text
mgcoa9000Handler
  → mgcoa9000Facade.mgcoa9000S0(Object dtoBody)
      → ObjectMapper.convertValue(..., mgcoa9000S0DTOin.class)
      → mgcoa9000Service.mgcoa9000S0(input)
          → mgcoa9000DAO.mgcoa9000S0_S0_count(param)
          → mgcoa9000DAO.mgcoa9000S0_S0(param)
              → mgcoa9000-ORA.xml
                  → DB
      ← mgcoa9000S0DTOout
```

Facade의 `@Transactional(transactionManager="rdwTransactionManager", readOnly=true)`는 `PROPAGATION_REQUIRED` 기본 전파 속성을 가진다. 타임아웃 ON에서는 Worker의 TransactionTemplate이 이미 같은 TransactionManager로 트랜잭션을 시작했으므로 Facade는 새 트랜잭션을 만들지 않고 기존 트랜잭션에 참여한다. 등록·수정·삭제 Facade는 `rollbackFor=Exception.class`를 선언하여 checked Exception도 rollback 대상으로 삼는다.

Service public 메서드에 진입하기 직전에 `BizPrePostAspect.before`가 실행되고 정상 반환 뒤 `afterReturning`이 실행된다. 이 Aspect는 Facade 트랜잭션 안에서 Service를 감싸므로, 선후처리에서 같은 DataSource를 사용해 SQL을 수행한다면 활성 트랜잭션에 참여할 수 있다. 다만 후처리는 예외 반환 시 실행되는 `finally`가 아니라 정상 반환 시점의 Advice이므로 실패 시 호출 여부를 코드 기준으로 판단해야 한다.

업무 구간의 경계를 지키는 이유는 rollback 범위를 예측하기 위해서다. Controller나 Handler에서 DAO를 직접 호출하면 Facade의 변환·조정 책임을 우회한다. 타임아웃 OFF 또는 TCF OFF에서는 외곽 TransactionTemplate이 없을 수 있으므로 이런 우회가 곧 무트랜잭션 데이터 변경으로 이어질 수 있다.

3장에서는 Framework, Entry, Application, Rule, DTO와 Persistence를 책임 관점에서 분해한다. 이 장에서는 그 컴포넌트들이 요청 시간축에서 어떤 순서로 호출되는지만 기억하면 된다.

## 2.7 시스템 후처리 구간

업무 결과가 Worker에서 돌아오면 Request Thread의 `Future.get()`이 해제되고 TcfFacade와 Controller가 결과를 반환한다. 이후 Spring MVC의 응답 처리와 Interceptor 완료 처리가 실행된다. 이 구간은 업무 DB 트랜잭션이 commit 또는 rollback된 뒤다.

`ResponseBodyArgumentResolver`는 이름과 달리 `ResponseBodyAdvice` 역할을 한다. ServiceContext의 Header를 `hdr_nhnis`에 넣고, 정상 업무 객체는 `dto`, `NH_NIS_ERR_DTO`는 `result`에 넣는다. 만들어진 응답 원문은 ServiceContext에 저장되어 후속 ImageLog가 사용할 수 있다.

```text
업무 결과 반환
  → 정상 객체인가?
      ├─ 예 → { hdr_nhnis, dto }
      └─ 아니오, 알려진 오류 DTO인가? → { hdr_nhnis, result }
  → 응답 전문 로그
  → ServiceContext.responseBody 저장
  → Interceptor.afterCompletion
      ├─ 정상/처리된 오류 → postImagelog
      └─ 미처리 예외 → exceptionImagelog
  → Filter.finally에서 Request Thread Context 정리
```

`postHandle`은 응답 Body가 이미 작성되는 순서 문제 때문에 실질적인 시스템 후처리를 하지 않는다. 응답 전문 조립과 출력은 ResponseBodyAdvice에서, 최종 ImageLog 처리는 `afterCompletion`에서 수행한다. 실행 순서를 클래스 이름만으로 추측해서는 안 되는 사례다.

시스템 후처리는 업무 DB 트랜잭션 밖에 있다. 응답 직렬화나 ImageLog 후처리가 실패했다고 이미 commit된 업무 데이터가 자동으로 rollback되지는 않는다. 반대로 업무 rollback이 발생해도 선처리 ImageLog까지 함께 사라진다고 가정해서는 안 된다. 운영 추적 기록과 업무 원자성은 서로 다른 경계다.

마지막으로 `DefaultFilter.finally`가 Request Thread의 ServiceContextHolder와 ThreadContext를 정리한다. Worker는 `OnlineTimeoutWorkerContext.clear()`로 별도 정리한다. 두 스레드가 각각 자기 ThreadLocal을 제거해야 스레드 풀 재사용 시 이전 거래 정보가 다음 요청에 섞이지 않는다.

## 2.8 정상 거래 흐름

정상 시나리오는 단순히 HTTP 200을 받는 과정이 아니다. 업무 결과가 만들어지고 DB 트랜잭션이 정상 종료되며, 표준 응답과 거래 추적 정보까지 완성되는 과정이다.

`mgcoa9000S0` 조회를 기준으로 정상 흐름은 다음과 같다.

1. UI가 Service ID와 `{hdr_nhnis, dto}` 요청을 8080으로 전송한다.
2. Filter가 Body를 캐시하고 GUID와 ServiceContext를 준비한다.
3. Interceptor가 요청 전문과 ImageLog 선처리를 수행한다.
4. Controller가 Service ID를 결정하고 dtoBody를 TcfFacade에 전달한다.
5. Executor가 Worker에 작업을 제출하고 Request Thread는 결과를 기다린다.
6. Worker가 컨텍스트를 설치하고 RDW 트랜잭션을 시작한다.
7. Dispatcher가 `mgcoa9000Handler`를 찾아 Handler가 조회 Facade를 호출한다.
8. Facade는 기존 트랜잭션에 참여하고 입력 DTO를 만든다.
9. 업무 선처리 후 Service와 DAO/Mapper가 DB를 조회한다.
10. Service가 DTOout을 반환하고 업무 후처리가 실행된다.
11. Worker의 deadline 재검사를 통과하면 트랜잭션이 commit된다. 조회의 경우에도 트랜잭션 컨텍스트는 정상 종료된다.
12. 결과가 Request Thread로 돌아와 `{hdr_nhnis, dto}`로 조립된다.
13. ImageLog 후처리와 Context 정리가 끝난 뒤 브라우저가 화면을 갱신한다.

```text
Request accepted
  → Context ready
  → Worker/TX begin
  → Handler selected
  → Business success
  → Deadline valid
  → TX commit
  → Standard response
  → ImageLog complete
  → Context clear
```

운영자가 정상 거래를 확인할 때는 HTTP 상태만 보지 않는다. GUID가 요청·응답 로그에 일관되게 나타나는지, Service ID가 의도한 Handler로 라우팅되었는지, Worker에서 commit 또는 정상 종료가 확인되는지, 응답의 dto가 화면 기대와 맞는지를 함께 본다.

## 2.9 실패 거래 흐름

실패 흐름은 실패한 위치에 따라 모양이 달라진다. 모든 오류가 GlobalExceptionHandler를 거쳐 같은 result로 반환된다고 이해하면 Filter 조기 실패나 일반 예외를 놓치게 된다.

### 진입 전 실패

잘못된 JSON, 빈 Body, 비-local에서 Header 누락, 토큰 누락·검증 실패는 Filter에서 400 또는 401로 종료된다. Worker와 DB 트랜잭션은 시작되지 않는다. 이 경로는 표준 오류 DTO와 ResponseBodyAdvice를 지나지 않을 수 있고, CORS 응답도 항상 보장되지 않는다.

### 라우팅 실패

Service ID가 없거나 Dispatcher에 등록되지 않으면 `ServiceHandlerNotFound`가 발생한다. 타임아웃 ON에서는 Worker 트랜잭션이 rollback되고 예외가 Future를 통해 Request Thread로 전달된다. TCF용 `GlobalExceptionHandler`가 이를 `E9999` 오류 DTO와 HTTP 500으로 바꾸고 ResponseBodyAdvice가 result 봉투로 조립한다.

### 업무·DB 실패

Service가 `BizException`을 던지거나 DAO/Mapper에서 RuntimeException이 발생하면 Worker의 TransactionTemplate이 rollback-only를 설정하고 rollback한다. Facade의 쓰기 메서드는 `rollbackFor=Exception.class`를 선언하므로 checked Exception도 rollback된다. 예외를 잡아서 정상 값으로 반환하면 트랜잭션 관리자가 실패를 알 수 없어 commit될 수 있으므로, rollback이 필요한 예외를 삼켜서는 안 된다.

### 타임아웃과 포화

Request Thread가 설정된 5초 안에 결과를 받지 못하면 Future에 `cancel(true)`를 요청하고 `OnlineTimeoutException`을 던진다. 알려진 타임아웃은 HTTP 504와 `FW_TIMEOUT`으로 변환된다. Worker가 interrupt 또는 deadline을 감지하면 rollback한다. 그러나 JDBC 호출이 interrupt에 즉시 반응하지 않으면 작업 정리가 늦어질 수 있다.

Worker Pool 20개와 Queue 100개가 모두 수용 한도를 넘으면 submit이 거부된다. 이때는 Worker 트랜잭션이 시작되지 않으며 `OnlineOverloadException`이 HTTP 503과 `FW_OVERLOADED`로 변환된다. 504는 “수락했지만 시간 내 완료하지 못함”, 503은 “실행할 용량이 없어 수락하지 못함”이라는 차이가 있다.

```text
실패 위치             Worker/TX        대표 응답        우선 점검
────────────────────────────────────────────────────────────────────
Filter 형식·인증      시작 안 함       400 / 401        Body·Header·Token
Handler 미등록        시작 후 rollback 500 / E9999      Service ID 등록
업무 예외             rollback         500 / 업무코드   GUID·업무 로그
Pool/Queue 포화        시작 안 함       503 / OVERLOADED Pool·Queue·부하
시간 제한 초과        취소 요청/rollback 504 / TIMEOUT   Worker·SQL 종료 여부
응답 직렬화 실패      업무 TX 종료 후  일관 형식 미보장 응답 Advice·로그
```

현행 `GlobalExceptionHandler`는 `ServiceHandlerNotFound`, `BizException`, `OnlineTimeoutException`, `OnlineOverloadException`을 명시적으로 처리한다. 모든 일반 `Exception`을 처리하는 catch-all 메서드는 없다. 따라서 알려지지 않은 예외의 응답 형식과 상태는 Spring MVC 기본 처리 또는 다른 Advice의 영향을 받을 수 있다.

## 2.10 트랜잭션과 온라인 거래의 차이

PDMG에서 “거래”라는 말은 두 뜻으로 사용된다. 온라인 거래는 사용자 요청 한 건의 업무 생명주기이고, DB 트랜잭션은 데이터 변경을 commit 또는 rollback하는 기술적 경계다. 둘은 겹치지만 시작점과 종료점이 다르다.

```text
HTTP 요청
├─────────────────────────────────────────────────────────────┤
    시스템 선처리
    ├────────── 온라인 거래 실행 ──────────────────────┤
                  ├── DB Transaction ──────────────┤
                  BEGIN  Handler→Facade→Service→DAO  COMMIT/ROLLBACK
                                                   시스템 후처리
```

| 구분 | 온라인 거래 | DB 트랜잭션 |
|---|---|---|
| 식별 | Service ID, GUID | TransactionManager가 관리하는 상태 |
| 시작 | 요청 수신과 거래 식별 과정 | Timeout ON: Worker TransactionTemplate |
| 종료 | 응답·후처리·Context 정리까지 | 업무 성공 commit 또는 예외 rollback |
| 포함 대상 | Filter, Interceptor, TCF, 업무, 응답 | 같은 RDW TransactionManager에 참여한 DB 작업 |
| 실패 의미 | HTTP·인증·라우팅·업무·응답 실패 모두 포함 | 원자성을 지킬 수 없어 rollback |

타임아웃 ON에서는 `DefaultOnlineTimeoutExecutor`가 `rdwTransactionManager`로 외곽 TransactionTemplate을 연다. Facade의 `@Transactional(REQUIRED)`는 여기에 참여한다. 따라서 Handler와 업무 선후처리, Service와 DAO가 같은 Worker 트랜잭션 안에서 실행된다.

타임아웃 OFF에서는 `SyncOnlineTimeoutExecutor`가 현재 Request Thread에서 `action.call()`만 수행한다. 외곽 TransactionTemplate이 없으므로 Facade 프록시에 진입할 때 Facade의 `@Transactional`이 트랜잭션을 시작한다. Handler는 이 Facade 트랜잭션 밖에 있고, Service와 DAO 및 Service 포인트컷의 업무 선후처리는 안에 들어간다.

```text
[Timeout ON]
Worker TransactionTemplate BEGIN
  → Dispatcher → Handler → Facade(REQUIRED 참여)
  → Aspect → Service → DAO
COMMIT / ROLLBACK

[Timeout OFF]
Request Thread: Dispatcher → Handler
  → Facade Proxy BEGIN
     → Aspect → Service → DAO
    COMMIT / ROLLBACK
```

TCF OFF에서 업무 Controller가 Service를 직접 호출하면 Facade 트랜잭션을 우회할 수 있다. 직접 경로에서도 Controller → Facade → Service를 유지해야 TCF ON/OFF의 데이터 원자성을 맞출 수 있다. TCF와 트랜잭션은 서로 관련되어 있지만, TCF를 켰다고 모든 코드가 자동으로 올바른 트랜잭션 경계에 들어가는 것은 아니다.

## 2.11 요청 Thread와 Worker Thread

Servlet Container는 요청마다 Request Thread를 할당한다. 타임아웃이 켜진 PDMG는 장시간 업무가 이 Thread를 직접 점유하지 않도록 별도 Worker Pool에 Dispatcher 이하 작업을 제출한다. Request Thread는 사라지는 것이 아니라 Future 결과를 제한 시간 동안 기다린다.

```text
Tomcat Request Thread
  Filter → Interceptor → Controller → TcfFacade
                          │
                          │ capture + submit
                          ▼
                   pdmg-online-Worker
                   Context install
                   TX BEGIN
                   Dispatcher → DB
                   TX END
                   Context clear
                          │
                          │ Future result/exception
                          ▼
Tomcat Request Thread
  Response Advice → afterCompletion → Filter finally
```

ThreadLocal 값은 스레드를 바꾸면 자동으로 전달되지 않는다. 현행 `OnlineTimeoutWorkerContext.capture()`는 Request Thread의 ServiceContext 참조와 Log4j2 ThreadContext Map을 복사한다. Worker는 실행 전에 이를 설치하고 finally에서 제거한다. Servlet request와 response 객체는 WorkerContext에 보관하지 않는다. HTTP 객체를 Worker로 넘겨 비동기 처리하면 요청 수명과 작업 수명이 엇갈릴 수 있기 때문이다.

| 상태 | Worker 전달 방식 | 주의점 |
|---|---|---|
| ServiceContext | 명시적 capture/install | 같은 객체 참조의 동시 변경 주의 |
| GUID·Service ID | Context와 MDC에서 추출 | 로그 상관관계 유지 |
| Log4j2 ThreadContext | Map 복사 후 `putAll` | Worker 종료 시 `clearAll` |
| TransactionContext | Callable 인자로 전달 | TcfFacade에서 Worker 제출 전에 생성 |
| Spring Transaction | 전달하지 않음 | Worker에서 새 TransactionTemplate 시작 |
| JDBC Connection | 전달하지 않음 | Worker TX가 새로 획득·바인딩 |
| Servlet request/response | 전달하지 않음 | Request Thread 소유 상태 |

Spring Transaction은 ThreadLocal 기반이므로 Request Thread에서 열린 트랜잭션이 Worker로 자동 이동하지 않는다. 현행 구조가 Worker 안에서 TransactionTemplate을 시작하는 이유다. 반대로 Worker 트랜잭션을 시작한 뒤 별도의 비동기 작업을 다시 만들면 그 하위 스레드에도 트랜잭션이 자동 전파되지 않는다.

타임아웃 시 Request Thread는 `future.cancel(true)`를 호출하고 오류 응답 경로로 이동한다. Worker가 interrupt를 관찰하여 예외를 던지거나 action 반환 후 deadline 검사에 걸리면 rollback한다. 그러나 블로킹 JDBC가 interrupt를 무시하면 Request Thread의 응답과 Worker의 실제 종료 사이에 시간차가 생긴다. “504 반환”과 “DB 작업 중단 완료”는 별도 사실로 관찰해야 한다.

Thread 경계에서 가장 위험한 안티패턴은 Context 정리 누락이다. Tomcat과 Worker Pool의 스레드는 재사용된다. 이전 GUID나 사용자 정보가 남으면 다음 요청 로그와 권한 판단이 오염될 수 있다. Filter와 WorkerContext가 각각 finally에서 정리하는 것은 기능적 부가 작업이 아니라 보안과 추적성의 필수 조건이다.

## 2.12 전체 흐름에서 반드시 기억할 경계

온라인 거래를 설계하거나 장애를 분석할 때는 클래스 이름보다 경계를 먼저 찾는 편이 빠르다. 동일한 예외라도 경계의 안과 밖에서 결과가 달라지기 때문이다.

### 다섯 개의 실행 경계

```text
① Process/HTTP 경계
   Browser ──HTTP── pdmg-service

② 시스템 선처리 경계
   DefaultFilter → Interceptor.preHandle

③ Thread 경계
   TcfFacade/Executor(Request) ──submit── Worker

④ DB Transaction 경계
   Worker TransactionTemplate 또는 Facade Proxy

⑤ 시스템 후처리 경계
   Response Advice → afterCompletion → Filter finally
```

HTTP 경계에서는 포트, CORS, Body와 인증을 본다. 시스템 선처리 경계에서는 GUID, ServiceContext와 ImageLog 입력을 본다. Thread 경계에서는 Context 전파와 타임아웃을 본다. DB 트랜잭션 경계에서는 같은 TransactionManager 참여 여부와 rollback 조건을 본다. 시스템 후처리 경계에서는 표준 응답, ImageLog 완료와 ThreadLocal 정리를 본다.

### AS-IS와 TO-BE를 혼동하지 않기

현행 흐름에는 과거 또는 목표 다이어그램과 다른 지점이 있다.

| 주제 | AS-IS | TO-BE 판단 시 고려할 점 |
|---|---|---|
| STF/ETF | TcfFacade에서 직접 호출하지 않음 | 단일 오케스트레이션으로 묶을 경우 기존 Filter/Advice와 중복 제거 |
| 시스템 전후처리 | Filter·Interceptor·Advice에 분산 | 실패 시 후처리 보장과 정리 책임 명확화 |
| Service ID 다중 입력 | Header → JSON → Path 우선순위 | 값 불일치 거부 정책 |
| Filter 조기 오류 | `sendError(400/401)` | 표준 오류 봉투와 CORS 일관성 |
| Timeout 취소 | interrupt 요청과 deadline 재검사 | JDBC query timeout과 취소 가능성 연계 |
| TCF OFF | 업무 Controller 경로 | Facade 경유를 강제해 TX 의미 통일 |

TO-BE는 현행이 이미 그렇게 동작한다는 설명이 아니다. 변경을 결정할 때는 호환성, 응답 계약, 로그 중복과 운영 관측성을 함께 검토해야 한다.

### 개발자 체크리스트

- Service ID가 UI 요청, 공통 Header와 Handler 등록에서 일치하는가?
- 업무 요청이 Controller/Handler에서 Facade를 거쳐 Service로 들어가는가?
- 데이터 변경이 `rdwTransactionManager`의 활성 트랜잭션 안에서 실행되는가?
- Timeout ON/OFF에서 같은 업무 원자성을 유지하는가?
- Worker로 필요한 ServiceContext와 MDC가 전달되고 양쪽 스레드에서 정리되는가?
- Filter 조기 실패와 Controller 이후 실패의 응답 차이를 클라이언트가 처리하는가?
- 504 발생 후 Worker와 SQL이 실제 종료·rollback됐는지 GUID로 확인하는가?
- ImageLog에 토큰, 비밀번호와 개인정보가 노출되지 않는가?

### 아키텍처 판단 포인트

공통 타임아웃을 Worker와 외곽 트랜잭션으로 묶는 방식은 요청 대기 제한과 rollback 지점을 하나로 모으는 장점이 있다. 대신 ThreadLocal 전파, 풀 용량과 JDBC 취소라는 새로운 운영 책임이 생긴다. 타임아웃을 끄면 구조는 단순해지지만 Request Thread가 업무 실행을 직접 담당하고 제한 시간 통제가 약해진다. 설정 선택은 기능 유무가 아니라 동시성, 데이터 원자성, 취소 가능성과 장애 관측성의 선택이다.

### 핵심 정리

1. PDMG 요청은 Browser → UI → Filter → Interceptor → TCF → Handler → Facade → Service → DAO/DB → Response 순으로 이동한다.
2. 시스템 선처리와 후처리는 업무 DB 트랜잭션 밖에서 요청을 준비하고 기록한다.
3. 타임아웃 ON에서는 Dispatcher 이하가 Worker Thread에서 실행되고 TransactionTemplate이 외곽 트랜잭션을 시작한다.
4. Facade의 `@Transactional(REQUIRED)`는 타임아웃 ON에서 기존 Worker 트랜잭션에 참여하고, OFF에서는 스스로 트랜잭션을 시작한다.
5. 온라인 거래는 HTTP와 공통 처리를 포함하는 생명주기이며 DB 트랜잭션은 그 안의 데이터 원자성 경계다.
6. 알려진 예외는 표준 result로 변환되지만 Filter 조기 실패와 일반 예외는 같은 형식을 보장하지 않는다.
7. Timeout은 Request Thread의 대기 종료이지 JDBC 작업의 즉시 중단을 보장하는 신호가 아니다.
8. Request Thread와 Worker Thread는 ServiceContext·MDC를 명시적으로 전달하고 각각 정리해야 한다.
9. 현행 TcfFacade는 STF/ETF를 직접 호출하지 않으므로 개념 다이어그램과 실제 호출을 구분해야 한다.
