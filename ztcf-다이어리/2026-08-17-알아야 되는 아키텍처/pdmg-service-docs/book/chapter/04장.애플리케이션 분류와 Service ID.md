# 4장. 애플리케이션 분류와 Service ID

PDMG에서 `mgcoa5530S0`은 단순한 메서드 이름이 아니다. 이 문자열은 어느 애플리케이션 그룹의 어느 업무가 어떤 프로그램에서 무슨 거래를 수행하는지를 나타내는 식별자이며, 온라인 요청을 올바른 Handler로 보내는 런타임 라우팅 키다. 동시에 로그, 거래통제, 타임아웃, 화면과 전문을 연결하는 공통 언어이기도 하다.

따라서 Service ID를 잘못 만들면 이름만 어색해지는 데 그치지 않는다. 요청이 다른 Handler로 전달되거나 등록되지 않은 거래로 거절될 수 있고, 화면의 샘플 전문과 백엔드가 서로 다른 거래를 가리킬 수 있다. 거래통제 대상이 빗나가거나 장애 로그를 검색하지 못하는 문제도 생긴다. 이 장의 목표는 독자가 분류표를 읽고 새로운 Service ID를 설계한 뒤, 요청·Handler·운영 정책까지 일관되게 연결할 수 있게 하는 것이다.

이 장은 2026년 8월 13일 현재 저장소의 구현을 AS-IS 기준으로 설명한다. 문서가 제시하는 표준과 소스가 실제로 강제하는 규칙이 다르면 이를 구분한다. 개선 방향은 TO-BE로 따로 표시한다.

## 4.1 애플리케이션 코드 분류체계

애플리케이션 코드 분류체계는 업무 시스템을 계층적으로 주소화한다. PDMG의 프로그램 식별자는 다음 네 축으로 시작한다.

```text
애플리케이션 그룹  업무구분  세부업무  프로그램 식별번호
       mg             co        a             5530
       └──────────── 프로그램 ID: mgcoa5530 ────────────┘
```

각 축은 서로 다른 질문에 답한다.

| 구분 | 길이 | 질문 | `mgcoa5530`의 값 |
|---|---:|---|---|
| 대구분 코드 | 2 | 어느 애플리케이션 그룹인가 | `mg` |
| 업무구분 코드 | 2 | 어느 업무 영역인가 | `co` |
| 세부업무 코드 | 1 | 그 업무의 어느 하위 영역인가 | `a` |
| 프로그램 식별번호 | 4 | 그 영역 안의 어느 프로그램인가 | `5530` |

분류체계의 목적은 짧은 이름을 만드는 데 있지 않다. 패키지 `nhnis.mg.co.a`, 프로그램 `mgcoa5530`, 거래 `mgcoa5530S0`가 같은 분류축을 공유하게 하여 소스 위치와 런타임 식별자를 함께 추적하도록 만드는 데 있다. 운영자는 Service ID만 보고도 대략적인 소유 영역을 알 수 있고, 개발자는 장애 ID에서 검색할 패키지와 Handler를 좁힐 수 있다.

분류 코드는 임의로 만들지 않는다. `00.NSIGHT 애플리케이션 코드 분류표.md`에서 승인된 대구분·업무·세부업무 조합을 선택해야 한다. 표에 없는 조합이 필요하면 개인이 먼저 코드를 점유하는 것이 아니라 분류표의 관리 주체와 신규 코드의 의미, 소유 조직, 충돌 여부를 합의해야 한다.

분류체계는 디렉터리 정리 규칙 이상의 아키텍처 계약이다. 예를 들어 장애 통계가 `mg.co.a` 단위로 집계되고 있는데 실제 업무 소유는 다른 영역이라면 조직별 장애율과 용량 계획이 왜곡된다. 권한이나 거래통제가 업무 코드에서 상위 범위를 계산하는 경우에는 더 직접적인 문제가 된다. 잘못된 분류로 시작한 ID는 데이터가 축적된 뒤에 고치기 어렵다. URL, 호출자 설정, 통제 테이블, 로그 색인, 모니터링 대시보드가 모두 이전 값을 참조할 수 있기 때문이다.

새 ID를 정할 때는 다음 세 관점을 동시에 만족시켜야 한다.

- **업무 관점:** 식별자가 실제 업무 소유와 행위를 설명하는가.
- **개발 관점:** 패키지와 구성요소를 일관되게 찾을 수 있는가.
- **운영 관점:** 통제, 추적, 타임아웃과 장애 집계의 안정된 키로 쓸 수 있는가.

이 세 관점 중 하나라도 빠지면 Service ID는 사람이 보기 좋은 이름에 머물고 플랫폼의 공통 식별자 역할을 하지 못한다.

## 4.2 대구분 코드

대구분 코드는 애플리케이션 그룹을 나타내는 두 자리 코드다. 분류표에는 여러 그룹이 정의되어 있으며 PDMG 업무 예제는 `MG`, 즉 Market Group Platform 영역을 사용한다. 실제 Java 패키지와 Service ID에서는 이를 소문자 `mg`로 표현한다.

```text
분류표 표기: MG
패키지 표기: nhnis.mg...
ID 표기:    mg...
```

대문자와 소문자는 장식의 차이가 아니다. 현재 Handler Registry는 문자열 키를 그대로 비교하므로 `mgcoa5530S0`과 `MGCOA5530S0`을 같은 값으로 정규화하지 않는다. 표준 Service ID는 분류 영역을 소문자로, 거래구분 코드를 대문자로 쓴다.

대구분은 배포 모듈명과 반드시 일치하는 값이라고 단정해서는 안 된다. `pdmg-service`는 배포 단위이고 `mg`는 업무 분류축이다. 현재 두 개념이 밀접하게 대응하지만, 런타임 Dispatcher는 모듈 이름을 해석하지 않고 Handler가 등록한 Service ID 문자열만 사용한다.

대구분 변경은 신규 이름 부여가 아니라 계약 마이그레이션으로 다루어야 한다. 이미 운영 중인 `mg...` 거래를 다른 그룹으로 옮기면 새 Handler 등록뿐 아니라 모든 호출자, UI 카탈로그, 거래통제 대상, ImageLog 검색 조건과 운영 대시보드를 함께 전환해야 한다. 호환 기간에 구 ID와 신 ID를 동시에 등록할 수는 있지만, 이중 등록이 같은 업무를 두 번 노출한다는 점과 정책 누락 위험을 고려해야 한다. 단순 패키지 이동만으로 대구분을 바꾸지 않는 이유다.

## 4.3 업무구분 코드

업무구분 코드는 대구분 아래의 업무 영역을 나타내는 두 자리 코드다. 현재 예제의 `co`는 공통 업무 영역을 의미하며 패키지의 세 번째 구간에 놓인다.

```text
nhnis . mg . co . a . entry.handler
        │    │    │
        │    │    └─ 세부업무
        │    └────── 업무구분
        └─────────── 대구분
```

업무구분을 고를 때는 화면 메뉴의 명칭보다 업무 책임과 데이터 소유권을 먼저 본다. 같은 화면에서 여러 업무를 호출할 수 있기 때문이다. 화면이 공통 포털에 노출된다는 이유만으로 모든 거래를 `co`에 넣으면 분류체계가 소유 영역을 설명하지 못한다.

현재 소스의 `mgcoa5530`, `mgcoa8888`, `mgcoa9000`, `mgcoa9001`, `mgcoa9100`, `mgcoa9999`는 모두 `mg.co.a` 아래에 있다. 이는 현재 샘플과 관리 기능의 배치 현황이지, 앞으로의 모든 PDMG 거래가 `co`여야 한다는 규칙은 아니다.

업무구분은 거래통제의 상위 범위를 계산할 때도 의미를 갖는다. 서비스 단위 규칙이 없을 때 업무 단위 규칙으로 폴백하는 설계라면 Service ID에서 해석한 업무코드가 정확해야 한다. 다만 현재 구현이 문자열의 특정 위치를 어떻게 해석하는지는 해당 통제 컴포넌트의 계약을 확인해야 한다. 분류표의 의미와 런타임 파서가 서로 다른 길이나 위치를 기대하지 않도록 테스트해야 한다.

업무구분을 검토하는 실용적인 질문은 “이 거래가 실패했을 때 어느 업무팀이 원인을 판단하고 복구 결정을 내리는가?”이다. 메뉴를 만든 팀보다 데이터와 규칙을 책임지는 팀이 답이 되는 경우가 많다. 공통 UI가 여러 업무를 묶더라도 백엔드 거래의 업무구분은 각 업무 소유권을 유지할 수 있다.

## 4.4 세부업무 코드

세부업무 코드는 업무구분을 한 단계 더 나누는 한 자리 영문 코드다. `mgcoa5530`의 `a`가 여기에 해당한다. 한 자리라는 제약 때문에 의미 없는 순번처럼 사용하기 쉽지만, 실제로는 패키지 경계와 프로그램 번호의 유효 범위를 정하는 중요한 축이다.

세부업무 코드는 다음 원칙으로 선택한다.

1. 분류표에서 대구분과 업무구분 아래에 정의된 코드를 확인한다.
2. 신규 프로그램의 업무 책임이 해당 세부업무 설명과 일치하는지 확인한다.
3. 같은 분류축에서 이미 사용 중인 프로그램 식별번호를 조사한다.
4. 패키지, Program ID, Service ID가 같은 코드 조합을 사용하게 한다.

예를 들어 분류가 `MG / CO / A`로 승인되었다면 Java 패키지는 `nhnis.mg.co.a`를 기준으로 하고 식별자는 `mgcoa`로 시작한다. 패키지는 `mg.co.a`인데 ID를 `mgcob`로 만드는 식의 불일치는 현재 Registry가 자동 검출하지 않는다. 그래서 코드 리뷰와 검증 검색이 필요하다.

## 4.5 프로그램 식별번호

프로그램 식별번호는 분류축 안에서 프로그램을 구별하는 네 자리 숫자다. 앞의 다섯 문자와 결합하면 아홉 자리 Program ID가 된다.

```text
mg + co + a + 5530 = mgcoa5530
```

Program ID는 하나의 프로그램 영역을 나타낸다. 현재 저장소에서는 다음과 같은 Program ID를 확인할 수 있다.

| Program ID | 현재 용도 | 대표 Service ID |
|---|---|---|
| `mgcoa5530` | 마케팅희망고객 조회 | `mgcoa5530S0` |
| `mgcoa8888` | 이미지로그 조회·삭제 | `mgcoa8888S0`, `mgcoa8888D0` |
| `mgcoa9000` | 거래 파라미터 관리 | `mgcoa9000S0/C0/U0/D0` |
| `mgcoa9001` | 거래통제 관리 | `mgcoa9001S0/C0/U0/D0` |
| `mgcoa9100` | 런타임 진단 | `mgcoa9100S0` |
| `mgcoa9999` | 영업팁 실적 조회 | `mgcoa9999S0` |

네 자리 번호는 같은 `대구분+업무구분+세부업무` 안에서 중복되지 않아야 한다. 그러나 현재 소스에는 중앙 번호 발급기나 Program ID 형식 검증기가 없다. 개발자가 새 번호를 정할 때 Handler, Controller, UI, 샘플 전문, 문서를 저장소 전체에서 검색하여 충돌을 확인해야 한다.

중복 판단은 현재 브랜치만 검색하는 것으로 끝나지 않을 수 있다. 병렬 개발 중인 다른 브랜치가 같은 번호를 선택하면 각각의 로컬 검색은 통과하지만 통합 시 충돌한다. 번호 배정 기록을 PR이나 작업 이슈에 남기고 통합 전에 다시 검색하는 절차가 필요한 이유다. 장기적으로는 승인된 Program ID와 Service ID 목록을 기계 판독 가능한 카탈로그로 관리하고 CI가 중복과 미등록을 검사하는 방식이 바람직하다.

번호에 업무 의미를 과도하게 인코딩하는 것도 피한다. 번호가 조직개편이나 메뉴 변경에 따라 의미를 잃으면 식별자가 불안정해진다. 식별자는 한 번 외부 계약과 운영 데이터에 사용되면 변경 비용이 크므로, 이름보다 수명주기를 길게 보아야 한다.

## 4.6 거래구분 코드

Program ID 뒤에는 한 자리 거래구분 코드와 한 자리 거래 순번이 붙는다. 거래구분은 해당 요청이 수행하는 업무 행위의 성격을 나타낸다.

| 코드 | 의미 | 현재 PDMG 예 | 적용 판단 |
|---|---|---|---|
| `S` | 조회(Search/Select) | `mgcoa9000S0` | 상태를 조회하며 업무 데이터를 변경하지 않음 |
| `C` | 등록(Create) | `mgcoa9001C0` | 새로운 업무 상태나 레코드를 생성 |
| `U` | 수정(Update) | `mgcoa9001U0` | 기존 상태를 변경 |
| `D` | 삭제(Delete) | `mgcoa8888D0` | 기존 상태를 제거 |
| `A` | 업무 실행(Action) | 현재 Handler 예 없음 | CRUD로 표현하기 어려운 명령성 업무 |
| `R` | 보고서(Report) | 현재 Handler 예 없음 | 보고서 생성·출력 성격의 거래 |

`A`와 `R`은 표준에서 사용할 수 있는 코드지만 현재 `pdmg-service` Handler에는 등록 사례가 없다. 그러므로 이를 “이미 구현된 거래”가 아니라 신규 업무에서 의미가 맞을 때 선택할 수 있는 분류로 이해해야 한다.

마지막 한 자리는 같은 Program ID와 거래구분 안에서 거래를 구별한다. 기본 거래는 보통 `0`을 사용하고 추가 거래가 필요하면 `1`부터 `9`, 이후 `A`부터 `Z`까지 확장할 수 있다. 예를 들어 한 프로그램에 서로 다른 조회가 있다면 `S0`, `S1`로 분리할 수 있다. 다만 순번을 늘리기 전에 두 요청이 정말 같은 프로그램 수명주기를 공유하는지 확인해야 한다.

거래 코드는 실제 부수효과와 일치해야 한다. `S0`이 내부에서 업무 테이블을 갱신한다면 모니터링과 통제 정책이 이름만 보고 잘못 판단할 수 있다. 조회 과정의 기술 로그 기록처럼 프레임워크가 담당하는 부수효과와 업무 상태 변경은 구분하되, 핵심 업무 행위가 수정이라면 `U` 또는 `A`가 더 적절하다.

`A`는 “나머지 모든 것”을 담는 코드가 아니다. 승인, 확정, 계산 실행, 재처리처럼 결과 상태 전이가 업무의 핵심이고 CRUD 하나로 설명하기 어려울 때 사용한다. `R` 역시 일반 목록 조회와 구분되는 보고서 생성, 출력 형식 조립, 대용량 산출물 생성의 성격을 나타낸다. 코드 선택은 HTTP 메서드가 아니라 업무 의미를 기준으로 한다. PDMG 온라인 거래는 대부분 POST를 사용하므로 HTTP POST라는 사실만으로 `C`를 선택해서는 안 된다.

순번은 버전 번호로 사용하지 않는다. `S0`의 응답 필드가 바뀌었다고 무조건 `S1`을 만드는 것은 적절하지 않다. `S0`과 `S1`은 동시에 식별 가능한 서로 다른 거래라는 의미가 강하다. 계약 버전 전략이 필요하다면 전문 버전이나 API 호환 정책과 함께 별도로 설계해야 한다.

## 4.7 Service ID 구성 공식

PDMG Service ID는 다음 공식으로 구성한다.

```text
Service ID
= 대구분(2) + 업무구분(2) + 세부업무(1)
  + 프로그램 식별번호(4) + 거래구분(1) + 거래순번(1)
= 총 11자

mg + co + a + 8888 + S + 0 = mgcoa8888S0
```

문서상 일반 검증식은 다음과 같이 표현할 수 있다.

```regex
^[a-z]{2}[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

PDMG의 `mg` 그룹만 엄격하게 검사한다면 다음과 같다.

```regex
^mg[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

이 정규식은 설계·리뷰·테스트에 사용할 표준이다. AS-IS `TransactionDispatcher` 등록 과정은 이 형식을 공통 검증하지 않는다. 형식이 틀린 문자열도 Handler가 같은 값으로 등록하면 라우팅될 수 있다. “실행된다”와 “표준에 맞는다”는 별개의 판정이다.

정규식만으로도 모든 오류를 잡을 수는 없다. `mgzza1234S0`이 형식상 통과하더라도 `zz/a` 조합이 분류표에 없으면 유효한 Service ID가 아니다. 반대로 분류표에 존재하는 코드라도 이미 다른 프로그램이 `1234`를 사용하면 충돌한다. 올바른 검증은 문법, 분류 의미, 유일성, 구현 등록이라는 네 층으로 구성된다.

```text
문법 검증 → 분류표 검증 → Program ID 유일성 → Handler Registry 유일성
```

이 순서로 검증하면 오류 메시지도 구체적으로 만들 수 있다. 모든 실패를 “잘못된 Service ID”로만 반환하면 개발자는 철자, 미승인 분류, 번호 충돌, Handler 누락 중 무엇을 고쳐야 할지 알 수 없다.

식별자를 읽을 때는 뒤에서부터 자르면 쉽다. 마지막 두 자리가 거래구분과 순번이고, 그 앞 네 자리가 프로그램 번호다. 남은 앞 다섯 자리가 분류축이다. 이 구조를 알면 로그의 `mgcoa9001U0`만 보고도 `mg/co/a`, 프로그램 `9001`, 수정 거래 `U0`으로 해석할 수 있다.

## 4.8 프로그램 ID와 Service ID의 차이

Program ID와 Service ID는 포함 관계지만 목적이 다르다.

| 항목 | Program ID | Service ID |
|---|---|---|
| 예 | `mgcoa9001` | `mgcoa9001U0` |
| 길이 | 9자 | 11자 |
| 식별 대상 | 프로그램 영역 | 실행 가능한 개별 거래 |
| 주요 사용처 | 화면·클래스 계열·소스 묶음 | 요청 라우팅·Handler Registry·로그·통제 |
| 관계 | 하나의 프로그램 | 한 프로그램에 여러 거래 가능 |

`mgcoa9001`은 거래통제 관리라는 프로그램 영역을 가리킨다. 그 안에는 조회 `S0`, 등록 `C0`, 수정 `U0`, 삭제 `D0`가 있다. 런타임 Dispatcher는 Program ID로 분기하지 않고 완전한 Service ID로 Handler를 찾는다.

Program ID는 소스 탐색의 시작점으로 유용하다. `mgcoa9001`을 검색하면 네 거래의 Handler, Facade, Service, DTO, DAO, Mapper와 UI 화면을 한 묶음으로 찾을 수 있다. Service ID는 그 결과에서 특정 거래만 좁힌다. 운영 로그에서 `mgcoa9001U0` 장애를 받았다면 먼저 정확한 거래를 찾고, 프로그램 전체의 공통 로직을 볼 때 접미사 `U0`를 제거해 검색 범위를 넓히는 방식이다.

클래스 이름에 Program ID가 반복된다고 해서 그것이 런타임 계약이라는 뜻은 아니다. 현재 실제 계약은 Handler의 `serviceIds()`가 반환한 값이다. DTO·Facade·Service 메서드가 같은 Service ID 접두어를 쓰는 것은 추적성과 일관성을 위한 개발 표준이며, Dispatcher가 해당 클래스 이름을 반사적으로 찾아가는 구조는 아니다.

## 4.9 화면번호와 Service ID 관계

화면번호, Program ID, Service ID를 동일한 값으로 취급하면 안 된다. 현재 UI의 정적 화면 디렉터리와 `data-program-id`는 `mgcoa9001`처럼 Program ID를 화면 식별에 활용한다. 하지만 개념적으로 화면은 사용자 인터페이스 단위이고 Program ID는 업무 프로그램 단위다.

```text
화면 mgcoa9001
  ├─ 조회 버튼  ──> mgcoa9001S0
  ├─ 등록 버튼  ──> mgcoa9001C0
  ├─ 수정 버튼  ──> mgcoa9001U0
  └─ 삭제 버튼  ──> mgcoa9001D0
```

한 화면이 여러 Service ID를 호출할 수 있고, 한 Service ID를 여러 화면이나 배치성 도구가 재사용할 수도 있다. 화면이 없는 백엔드 API도 가능하다. 따라서 화면번호와 Service ID의 관계는 보통 1:N이지만 시스템 전체에서 고정된 카디널리티는 아니다.

전문의 `sys_comm.scid`는 화면 식별자를 담고 `rms_svc_c`는 Service ID를 담는다. 샘플 전문은 `scid: mgcoa9001`, `rms_svc_c: mgcoa9001S0`처럼 둘을 분리한다. 공통 처리에서 `scid`를 Service ID 앞부분으로 보정하는 기능이 있더라도 이는 누락값을 채우는 편의 동작이지 두 식별자가 본질적으로 같다는 선언이 아니다.

화면과 거래의 변경 주기도 다르다. 사용성 개선으로 화면을 합치거나 나누어도 백엔드 거래 계약은 유지할 수 있다. 반대로 업무 규칙 때문에 Service ID를 추가해도 기존 화면 안에 버튼 하나만 추가될 수 있다. 두 식별자를 독립적으로 관리하면 UI 개편이 운영 통제 키를 불필요하게 흔들지 않는다.

ImageLog를 조회할 때도 두 값의 차이가 유용하다. Service ID는 어느 거래가 실행됐는지를, 화면번호는 사용자가 어느 화면 문맥에서 요청했는지를 설명한다. 동일 거래가 여러 화면에서 호출될 때 두 필드를 함께 보면 업무 로직 문제와 특정 화면 조립 문제를 구분할 수 있다.

## 4.10 Service ID와 URL

TCF가 켜진 AS-IS `OnlineTransactionController`는 세 종류의 POST 진입점을 제공한다.

```text
POST /online
POST /{businessCode}/online
POST /{serviceId}
```

`POST /mgcoa5530S0`처럼 URL에 Service ID를 넣을 수 있지만 URL이 언제나 최종 선택값은 아니다. Controller의 실제 우선순위는 다음과 같다.

1. `ServiceContext.header.sys_comm.rms_svc_c`
2. 요청 JSON의 `hdr_nhnis.sys_comm.rms_svc_c`
3. URL 경로의 `{serviceId}`

Filter가 전문 헤더를 `ServiceContext`에 올려놓았다면 첫 번째 값이 사용된다. Context에 없을 때 요청 Map의 헤더를 보고, 두 곳 모두 비어 있을 때 경로 값을 사용한다. 경로로 들어온 값을 선택한 경우 `ensureRmsSvcC`가 비어 있는 Context 헤더에 값을 보정한다.

여기서 중요한 AS-IS 제약은 헤더와 경로가 다를 때 불일치 오류를 발생시키지 않는다는 점이다. 예를 들어 URL은 `/mgcoa5530S0`인데 헤더가 `mgcoa9001S0`이면 헤더 값이 우선되어 거래통제 조회가 실행될 수 있다. 클라이언트는 두 위치에 같은 값을 보내야 하며, TO-BE에서는 두 값이 모두 존재하면 일치 여부를 입구에서 검증하는 편이 안전하다.

세 진입점의 사용 의도도 다르다. `/{serviceId}`는 사람이 URL만 보아도 거래를 알기 쉽고 기존 업무 Controller 스타일과 호환된다. `/online`은 표준 전문의 헤더가 거래를 결정하는 단일 엔드포인트 방식이다. `/{businessCode}/online`은 업무 라우팅 정보를 경로에 보조적으로 나타낸다. 어떤 방식을 쓰더라도 최종 Handler 키는 Controller가 확정한 Service ID 하나여야 한다.

요청 예시는 다음처럼 URL과 헤더를 일치시킨다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9001S0",
      "scid": "mgcoa9001"
    }
  },
  "dto": {}
}
```

이 전문을 `/mgcoa9001S0`으로 전송하면 경로와 헤더가 같은 거래를 가리킨다. `/online`으로 전송할 때는 경로에 Service ID가 없으므로 헤더가 필수적인 거래 선택 정보가 된다.

TCF가 꺼지면 `OnlineTransactionController`, `TcfFacade`, Handler 경로가 비활성화되고 업무 Controller의 `@PostMapping("/mgcoa..." )`이 요청을 받는다. 이때는 URL 매핑이 거래 진입점을 결정한다. 같은 Service ID라도 TCF ON은 Registry 라우팅 키이고, TCF OFF는 Spring MVC 매핑 문자열이라는 차이가 있다.

## 4.11 Service ID와 Handler Registry

TCF ON에서 Service ID의 핵심 역할은 Handler Registry의 키다. 애플리케이션 시작 시 `TransactionDispatcher`는 모든 `TransactionHandler` Bean을 수집하고 각 Handler의 `serviceIds()`를 읽어 Map을 만든다.

```text
애플리케이션 시작
  TransactionHandler Bean 수집
        │
        ├─ mgcoa5530Handler → [mgcoa5530S0]
        ├─ mgcoa8888Handler → [mgcoa8888S0, mgcoa8888D0]
        └─ ...
              ↓
       Map<ServiceId, Handler>

요청 serviceId → Map 조회 → Handler.handle(...) → 업무 Facade
```

현재 Handler 소스에서 확인되는 등록 거래는 총 13개다.

| Handler | 등록 Service ID |
|---|---|
| `mgcoa5530Handler` | `mgcoa5530S0` |
| `mgcoa8888Handler` | `mgcoa8888S0`, `mgcoa8888D0` |
| `mgcoa9000Handler` | `mgcoa9000S0`, `C0`, `U0`, `D0` |
| `mgcoa9001Handler` | `mgcoa9001S0`, `C0`, `U0`, `D0` |
| `mgcoa9100Handler` | `mgcoa9100S0` |
| `mgcoa9999Handler` | `mgcoa9999S0` |

표의 축약 표기 `C0`, `U0`, `D0`에는 같은 행의 Program ID 접두어가 붙는다. 이전 분석 문서에 8개라고 기록된 부분은 과거 시점 정보이며 현재 Handler 소스가 우선한다.

두 Handler가 같은 Service ID를 등록하면 시작 과정에서 중복 예외가 발생한다. 반대로 요청 ID가 비어 있거나 Registry에 없으면 `ServiceHandlerNotFound`가 발생한다. Registry는 문자열의 대소문자와 공백을 자동 교정하지 않으므로 완전히 같은 값을 써야 한다.

UI의 `TransactionCatalog`는 별도 목록이다. 현재 그 카탈로그는 5530, 8888, 9999, 9000 계열 8개를 등록하고 있어 백엔드의 9001·9100 거래를 모두 반영하지 않는다. UI에는 별도의 정적 화면과 호출 코드가 있어 동작할 수 있지만, 카탈로그와 Registry가 하나의 원천에서 생성되는 구조는 아니다. 신규 거래를 추가할 때 양쪽을 독립적으로 확인해야 한다.

Handler 등록에는 두 단계의 일관성이 필요하다. 첫째, `serviceIds()` 목록에 값이 있어야 Dispatcher가 Handler를 찾는다. 둘째, `handle()`의 분기가 같은 값을 처리해야 한다. 목록에는 추가했지만 switch 분기를 빼면 Registry 조회는 성공한 뒤 Handler 내부에서 실패한다. 반대로 switch만 추가하고 목록에 등록하지 않으면 그 분기에는 도달할 수 없다.

Handler 이름과 Program ID의 일치는 현재 런타임이 강제하지 않는다. `mgcoa9001Handler`가 이론상 다른 프로그램 ID를 등록할 수도 있다. 하지만 그러면 도메인마다 하나의 Handler라는 구조와 소스 추적성이 깨진다. 리뷰 시 Handler의 Program ID 접두어, 등록 목록, 분기 상수가 같은지 확인해야 한다.

UI 카탈로그와 Registry의 차이는 단순 표시 누락으로 끝나지 않는다. 테스트 도구가 UI 카탈로그를 기준으로 샘플 전문을 만들면 신규 백엔드 거래가 통합시험 대상에서 빠질 수 있다. TO-BE에서는 백엔드가 읽는 선언형 거래 카탈로그에서 UI 메타데이터를 생성하거나, CI가 두 목록의 차이를 명시적으로 허용 목록과 비교하는 방법을 고려할 수 있다.

## 4.12 Service ID와 거래 통제

거래통제는 특정 거래를 서비스별, 업무별, 채널별, 영업점별, 사용자별, IP별 또는 전역으로 허용·차단하는 기능이다. 이때 Service ID는 가장 구체적인 통제 대상이자 요청을 설명하는 기준값이다.

```text
요청 rms_svc_c
   ↓
ServiceContext / TransactionContext
   ↓
STF preProcess
   ↓
MgTxControlService.check(header)
   ↓
TB_MG_TX_CONTROL 규칙 평가
```

`mgcoa9001S0/C0/U0/D0`은 `TB_MG_TX_CONTROL`을 관리하는 CRUD 거래다. 실제 통제 판정은 `pdmg-fw`의 `MgTxControlService`가 담당하고 STF의 `preProcess`가 이를 호출한다. 관리 거래 자체가 통제되어 복구할 수 없는 상황을 막기 위한 면제 규칙도 별도로 관리한다.

그러나 AS-IS 호출 연결을 반드시 구분해야 한다. `stf.preProcess()`에는 통제 호출이 구현되어 있지만 현재 `TcfFacade.process()`는 `TransactionContext`를 만든 뒤 곧바로 `OnlineTimeoutExecutor`와 Dispatcher를 호출한다. 즉, 주 TCF 경로에서 STF가 실제로 호출되지 않는다. 거래통제 구성요소와 관리 화면은 존재하지만 이 소스 상태만 보면 일반 온라인 거래 앞에서 통제가 강제된다고 단정할 수 없다.

TO-BE에서는 `TcfFacade`의 단일 선처리 지점에서 STF를 호출하고, 통과한 요청만 타임아웃 실행기와 Handler로 전달해야 한다. Filter나 각 업무 Service에 같은 검사를 복제하면 TCF ON/OFF와 직접 호출 경로에 따라 통제 결과가 달라진다. Service ID를 한 번 확정한 뒤 동일 값을 통제, Registry, 로그에 전달하는 것이 핵심이다.

거래통제의 대상값도 정확한 수준을 사용해야 한다. 전역 차단은 모든 거래, 업무 차단은 업무코드 범위, 서비스 차단은 완전한 11자 Service ID를 대상으로 한다. Program ID 아홉 자리를 서비스 통제값으로 저장하면 완전 일치 구현에서는 규칙이 매칭되지 않을 수 있다. `mgcoa9001`과 `mgcoa9001S0`을 혼용하지 말고 통제 유형별 데이터 계약을 지킨다.

통제 관리 거래의 면제는 운영 복구성을 위한 장치지만 범위를 무제한으로 넓히면 안 된다. 관리 화면을 호출한다는 이유만으로 모든 `mgcoa9001` 관련 요청을 인증·통제에서 제외하는 식의 확장은 우회 경로가 된다. 어떤 계층에서 무엇을 면제하는지, Service ID 목록이 실제 Handler 등록과 일치하는지 별도 보안 검토가 필요하다.

## 4.13 Service ID와 타임아웃

온라인 타임아웃 실행기는 Handler 이하 작업을 Worker Pool과 `TransactionTemplate` 안에서 실행한다. `OnlineTimeoutWorkerContext`가 GUID와 Service ID를 Worker Thread로 전달하므로 완료, 초과, 과부하 로그와 예외에서 어느 거래가 문제였는지 식별할 수 있다.

```text
TcfFacade.process(serviceId)
   ↓
OnlineTimeoutExecutor.execute
   ├─ WorkerContext: GUID + Service ID
   ├─ Worker Pool
   ├─ TransactionTemplate
   └─ Future.get(timeout)
```

현재 실행기에서 실제 제한시간은 `nhnis.fw.timeout.milliseconds` 공통값이다. `application.yml`의 AS-IS 값은 5,000ms이며 Pool 크기는 20, Queue 용량은 100이다. Service ID는 로그와 `OnlineTimeoutException`에 포함되지만, 이 실행기 구현은 Service ID별 제한시간을 선택하지 않는다.

`mgcoa9000`이 관리하는 `TB_MG_TX_PARAM`에는 `TX_ID`가 저장되지만 현재 검색 가능한 사용처는 해당 CRUD Service와 Mapper다. 타임아웃 실행기가 이 테이블을 조회해 정책을 결정하는 연결은 확인되지 않는다. 따라서 관리 테이블에 값을 넣는 것만으로 특정 Service ID의 제한시간이 바뀐다고 설명해서는 안 된다.

특정 거래만 10초로 운영하려면 TO-BE로 `serviceId → timeoutMs` 정책 해석기를 실행기 앞에 두고, 미등록 거래는 공통값으로 폴백하도록 설계할 수 있다. 이 경우 설정 또는 테이블 값의 범위 검증, 캐시 갱신, 장애 시 기본값, 운영 변경 이력까지 함께 정의해야 한다. 타임아웃의 Thread 중단과 트랜잭션 롤백 상세는 뒤 장에서 다룬다.

Service ID별 타임아웃을 도입할 때는 제한시간을 Worker 제출, `Future.get`, Worker 내부 마감시각, 예외 메시지에 동일하게 사용해야 한다. 한 지점만 10초로 바꾸고 다른 지점이 공통 5초를 유지하면 호출 Thread는 먼저 실패했는데 Worker가 계속 실행되는 불일치가 생긴다. 선택된 정책값을 한 번 계산하여 실행 전 과정에 전달해야 한다.

타임아웃 로그에는 Service ID와 GUID가 함께 있어야 한다. Service ID는 같은 유형의 느린 거래를 집계하고, GUID는 한 번의 요청을 Filter부터 DB까지 추적한다. 같은 Service ID에서 반복 초과가 발생하면 거래 자체의 쿼리와 제한시간을 검토하고, 여러 Service ID가 같은 시점에 초과하면 Pool 포화나 DB 장애 같은 공통 원인을 의심할 수 있다.

## 4.14 신규 Service ID 생성 절차

다음 절차는 신규 조회 거래를 `mgcoa9010S0`으로 만든다는 개념 예시다. `9010`이 실제로 배정 가능한 번호라는 뜻은 아니며 반드시 충돌과 분류 승인을 확인해야 한다.

### 1단계: 업무 경계를 먼저 정의한다

요청의 사용자 목적, 주요 입력과 출력, 상태 변경 여부, 소유 업무를 한 문장으로 정의한다. 기존 Program ID에 새 거래를 추가할지 새 프로그램을 만들지 이 단계에서 결정한다. 화면이 새로 생긴다는 이유만으로 새 프로그램을 만들거나, URL을 줄이기 위해 무관한 거래를 기존 프로그램에 넣지 않는다.

### 2단계: 분류 코드를 선택한다

분류표에서 대구분, 업무구분, 세부업무를 순서대로 고른다. PDMG 공통관리라면 `MG/CO/A`가 후보가 되어 소문자 접두어 `mgcoa`가 된다. 업무가 다르면 실제 분류표에 맞는 조합을 사용한다.

### 3단계: 프로그램 번호를 배정한다

같은 분류축에서 네 자리 번호의 사용 여부를 확인한다.

```powershell
rg -n "mgcoa9010" pdmg-service pdmg-fw pdmg-ui
```

검색 범위에는 Java뿐 아니라 Mapper XML, 샘플 JSON, 정적 화면, 문서가 포함되어야 한다. 검색 결과가 없다는 사실만으로 조직 차원의 배정이 끝나는 것은 아니므로 별도 관리대장이 있다면 함께 확인한다.

### 4단계: 거래구분과 순번을 정한다

조회는 `S`, 등록은 `C`, 수정은 `U`, 삭제는 `D`, 명령성 업무는 `A`, 보고서는 `R`을 후보로 삼는다. 같은 종류의 첫 거래는 `0`을 사용한다. 그 결과 개념 예시는 `mgcoa9010S0`이 된다.

### 5단계: 형식과 의미를 검증한다

11자 길이, 소문자 분류축, 네 자리 숫자, 허용 거래구분, 영숫자 순번을 검사한다. 정규식 통과만 보지 말고 선택한 분류 코드가 분류표의 의미와 맞는지, `S` 거래가 업무 상태를 변경하지 않는지도 리뷰한다.

### 6단계: Handler 계약을 등록한다

해당 도메인의 `TransactionHandler.serviceIds()`에 완전한 Service ID를 등록하고 `handle()` 분기에서 업무 Facade를 호출한다. PDMG 원칙상 업무 도메인마다 하나의 Handler를 두고 Handler는 분기와 Facade 호출만 담당한다.

```java
private static final String S0 = "mgcoa9010S0";

@Override
public Collection<String> serviceIds() {
    return List.of(S0);
}

@Override
public Object handle(String serviceId, Object dtoBody, TransactionContext context)
        throws Exception {
    return switch (serviceId) {
        case S0 -> facade.mgcoa9010S0(dtoBody);
        default -> throw new ServiceHandlerNotFound(serviceId);
    };
}
```

### 7단계: 업무 구성요소를 같은 식별축으로 연결한다

Facade, Service, DTO, DAO, Mapper Statement와 샘플 전문에서 같은 Program ID와 Service ID를 사용한다. Dispatcher가 이름을 자동 연결하지는 않지만, 운영 추적을 위해 식별축을 일치시켜야 한다. 세부 클래스·메서드 네이밍 규칙은 5장에서 다룬다.

### 8단계: 요청과 UI를 연결한다

TCF ON 요청은 URL과 `hdr_nhnis.sys_comm.rms_svc_c`에 같은 값을 보낸다. `scid`에는 화면 식별자를 넣는다. UI에서 거래 선택 기능을 제공한다면 `TransactionCatalog`, 샘플 요청, 정적 화면의 호출 URL과 도움말을 함께 갱신한다. UI 카탈로그 등록만으로 백엔드 Handler가 생기지 않으며 그 반대도 마찬가지다.

### 9단계: 운영 정책의 영향을 확인한다

거래통제의 서비스별 규칙, 면제 목록, 로그 검색 기준, 타임아웃 정책을 확인한다. AS-IS 타임아웃은 공통값이고 STF 연결은 미완료 상태이므로 “정책 데이터를 등록했다”와 “요청 경로에서 집행된다”를 별도로 검증해야 한다.

### 10단계: 실행 경로를 검증한다

최소한 다음을 확인한다.

- 애플리케이션 시작 시 중복 Service ID 오류가 없는가.
- TCF ON에서 헤더와 URL이 같은 값으로 Handler에 도달하는가.
- 헤더가 없는 경로 호출에서 ServiceContext가 올바르게 보정되는가.
- 미등록 ID가 정상 거래로 처리되지 않는가.
- TCF OFF를 지원한다면 업무 Controller URL이 같은 업무를 수행하는가.
- 응답 전문과 ImageLog에 Service ID와 GUID가 일관되게 남는가.
- UI 카탈로그, 샘플 요청, 도움말이 새 거래를 가리키는가.

신규 Service ID의 완료 기준은 “문자열을 정했다”가 아니라 “분류, Registry, 업무 구현, 요청 계약, 운영 정책과 검증이 한 식별자로 연결되었다”이다.

개발 리뷰에서는 다음 질문에 모두 답할 수 있어야 한다.

- 이 ID의 각 구간이 분류표의 어느 항목을 의미하는가.
- 기존 Program ID에 추가한 이유 또는 새 Program ID가 필요한 이유는 무엇인가.
- 거래구분이 실제 업무 부수효과와 일치하는가.
- URL과 전문 헤더 중 어디에서 값이 들어오며 불일치는 어떻게 방지하는가.
- 어느 Handler가 등록하고 어느 Facade가 유스케이스를 시작하는가.
- TCF OFF 경로도 지원해야 하는가.
- 거래통제와 타임아웃에서 이 ID는 현재 어떻게 취급되는가.
- UI, 샘플 전문, 로그와 운영 문서가 같은 값을 사용하는가.

이 질문에 답하지 못한 상태에서 코드 파일부터 복제하면 기존 샘플 ID가 일부 위치에 남는 복사 오류가 발생하기 쉽다. 먼저 식별자 계약을 한 줄로 확정하고 그 값을 기준으로 구성요소를 생성하는 편이 안전하다.

## 4.15 Service ID 오류 처리

Service ID 오류는 발생 시점에 따라 원인이 다르다. 빠르게 진단하려면 문자열 자체, 요청 해석, Registry, 정책 집행을 순서대로 나누어 본다.

| 증상 | 주요 원인 | 확인 위치 |
|---|---|---|
| 애플리케이션 시작 실패 | 두 Handler가 같은 ID 등록 | 각 Handler의 `serviceIds()` |
| `ServiceHandlerNotFound` | ID 누락 또는 Registry 미등록 | 요청 헤더, URL, Dispatcher Map |
| 예상과 다른 업무 실행 | 헤더와 URL 불일치, 헤더 우선 선택 | `rms_svc_c`, Controller 우선순위 |
| UI에는 보이나 호출 실패 | UI Catalog만 등록 | 백엔드 Handler 등록 여부 |
| 백엔드는 되나 UI 목록에 없음 | Handler만 등록 | `TransactionCatalog`, 화면 라우트 |
| 통제 규칙이 적용되지 않음 | STF 미호출 또는 대상값 불일치 | `TcfFacade`, STF, 통제 데이터 |
| 공통 제한시간으로 종료 | 서비스별 정책 연결이 없음 | `OnlineTimeoutExecutor`, YAML |
| 대소문자 변경 시 미등록 오류 | Registry가 문자열을 정확 비교 | 요청과 Handler 상수 |

미등록 거래는 현재 공통 예외 처리에서 `ServiceHandlerNotFound`로 식별되고 표준 오류 응답으로 변환된다. 다만 형식이 틀렸다는 이유만으로 Registry 등록 전에 거절하는 공통 Validator는 없다. 형식 오류와 미등록 오류가 런타임에서는 같은 “Handler를 찾을 수 없음”으로 보일 수 있으므로 로그에서 실제 선택된 Service ID를 먼저 확인해야 한다.

운영 장애 시에는 다음 순서가 효과적이다.

```text
1. GUID로 요청 로그 검색
2. Controller가 확정한 serviceId 확인
3. hdr_nhnis.rms_svc_c와 URL 비교
4. Handler.serviceIds() 등록 확인
5. Handler 내부 분기 확인
6. 거래통제·타임아웃 로그 확인
7. UI Catalog와 샘플 전문 비교
```

TO-BE 품질 기준으로는 시작 시 Registry를 만들 때 Service ID 형식, Handler 소유 Program ID, 중복을 함께 검증하고, CI에서 UI 카탈로그와 백엔드 등록 목록의 차이를 탐지하는 것이 좋다. 요청 입구에서는 헤더와 URL이 모두 있으면 불일치를 거절해야 한다. 이러한 검증은 정상 경로의 모호성을 줄이고 장애를 배포 전으로 앞당긴다.

오류 응답에는 내부 Handler 클래스나 전체 Registry 내용을 노출하지 않는다. 클라이언트에는 표준 오류코드와 추적용 GUID를 제공하고, 서버 로그에는 선택된 Service ID, 진입 URL, 통제와 Dispatcher 단계처럼 진단에 필요한 문맥을 남긴다. 입력 전문 전체나 인증 토큰을 오류 로그에 남기는 것은 피한다.

Service ID를 변경해야 하는 경우에는 삭제보다 단계적 전환이 안전하다. 신 ID를 등록하고 호출자를 이전한 뒤 구 ID 사용량을 로그로 관찰하며, 거래통제와 타임아웃 정책도 두 ID에 일시적으로 적용한다. 구 ID 호출이 사라진 것을 확인한 후 Registry와 문서를 제거한다. 단, 두 ID가 동일한 변경 거래를 가리키는 기간에는 중복 요청과 멱등성 위험을 검토해야 한다.

이 장의 핵심은 세 문장으로 정리할 수 있다. Program ID는 프로그램 영역을 식별하고 Service ID는 실행 가능한 거래를 식별한다. TCF ON에서 Service ID는 Controller가 헤더 우선순위로 확정하여 Handler Registry를 조회하는 키다. 같은 값이 화면, 전문, Handler, 거래통제, 타임아웃과 로그에서 일관되게 사용될 때 비로소 PDMG의 식별체계가 작동한다.

다음 장에서는 이 식별체계를 클래스, 메서드, DTO, DAO, Mapper와 SQL 이름으로 확장하는 구체적인 네이밍 규칙을 다룬다.
