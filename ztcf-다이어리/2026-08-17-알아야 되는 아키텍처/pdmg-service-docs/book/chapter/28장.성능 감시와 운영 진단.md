# 28장. 성능 감시와 운영 진단

성능 장애는 “응답이 느리다”라는 한 문장으로 해결되지 않는다. HTTP 대기, Filter와 TCF, Worker Queue, 업무 Transaction, Service, SQL 가운데 시간이 어디에서 소비되었는지 나누고, GUID와 Service ID로 같은 요청의 증거를 연결해야 한다. PDMG에는 구간 로그, ImageLog 시각, timeout 로그, SQL 실행 로그와 단일 JVM Runtime 스냅샷이 존재한다. 그러나 분산 Metric·Trace 플랫폼까지 구현된 것은 아니다.

## 28.1 성능 감시 대상

관측 대상은 요청량·응답시간·오류율뿐 아니라 Tomcat Thread, timeout Worker Pool과 Queue, 활성 거래, Hikari Connection, JVM Heap·GC·CPU, DAO/SQL이다. 평균만 보면 일부 장기 거래와 꼬리 지연을 숨긴다. Service ID별 p95/p99와 동시 실행량, timeout·거부 건수를 함께 봐야 한다.

AS-IS `MgRuntimeMonitor`는 현재 인스턴스의 JVM MXBean, Tomcat JMX Probe, Hikari MXBean과 활성 거래 Registry를 조회한다. Actuator, Micrometer, Prometheus 의존성과 `management` endpoint 설정은 build/config에서 확인되지 않았다. 따라서 장기 시계열과 인스턴스 통합은 현행 기능으로 단정하지 않는다.

## 28.2 HTTP 전체 처리시간

HTTP 전체시간은 서버가 요청을 수신해 응답 전송을 완료할 때까지다. Filter, Interceptor, Controller, Worker 대기·실행, 응답 조립과 ImageLog 후처리를 포함한다. 현행 ImageLog REQUEST_TIME과 RESPONSE_TIME은 문자열 시각이며 초 이하 정밀도와 Network 구간을 보장하지 않는다. 정확한 latency histogram용 Metric은 별도로 필요하다.

클라이언트 시간과 서버 시간을 비교하면 Network/Browser 지연을 추정할 수 있지만 시계 동기화가 전제다. 운영 진단에서는 Load Balancer access log의 duration, 애플리케이션 GUID, ImageLog 시각을 함께 본다.

## 28.3 TCF 구간별 처리시간

`TransactionContext`는 생성 시 `System.nanoTime()`을 기록하고 `elapsedMs()`로 TCF 경과시간을 계산한다. `TcfFacade`는 종료 시 이를 debug 로그에 남긴다. 이 값은 HTTP 전체가 아니라 Context 생성 이후 Dispatcher 결과까지다. Filter와 초기 Interceptor 시간, 최종 응답 전송시간은 포함하지 않는다.

`PdmgTxFlowLog`와 계층별 시작·종료 로그는 순서를 보여주지만 모든 구간을 구조화된 duration Metric으로 집계하지는 않는다. 로그 timestamp 차이는 단서이지 정확한 중첩 구간 합계로 간주하면 안 된다.

## 28.4 업무 트랜잭션 시간

timeout 활성 경로에서는 `OnlineTimeoutExecutor`가 Worker에서 TransactionTemplate로 Dispatcher 이하를 감싼다. 측정하려면 Queue 대기와 Transaction 실행을 분리해야 한다. 요청 Thread가 Future 결과를 기다린 총시간은 두 구간을 모두 포함하지만 DB Transaction 시간은 Worker가 Connection을 얻고 Transaction을 시작한 뒤부터다.

Facade의 `@Transactional`과 Worker TransactionTemplate가 중첩될 수 있으므로 로그에서 단순히 Service 시작·종료를 Transaction 시간으로 부르면 안 된다. Connection Pool pending 증가가 보이면 SQL보다 Transaction 시작 전 대기를 먼저 의심한다.

## 28.5 Service 실행시간

업무 Service에 공통 elapsed Metric을 기록하는 구현은 확인되지 않았다. Aspect의 시작·종료 로그와 Controller/Facade/Service 로그 timestamp로 추정할 수 있지만, 메서드별 histogram이나 Service ID별 집계는 없다. TO-BE에서는 예외가 나도 finally에서 기록하고 GUID, Service ID, 결과 분류만 tag로 사용한다. 사용자 ID처럼 cardinality와 개인정보가 큰 값은 Metric label로 쓰지 않는다.

## 28.6 SQL 실행시간

`MybatisLogInterceptor`는 query/update 전 `sqlId`를 MDC에 넣고 현재시간을 저장한다. finally에서 경과 ms와 parameter를 debug 로그로 출력하고 `sqlId`를 제거한다. 예외가 발생해도 제거되므로 다음 SQL에 MDC가 누출되지는 않는다.

이 구현은 SQL duration을 로그로 남기지만 Slow SQL Registry나 Metric을 채우지는 않는다. 더구나 parameter 전체 출력은 개인정보·Token 노출 위험이 있다. 운영에서는 parameter를 제거·마스킹하고 sqlId, duration, row count, 결과 상태 중심으로 기록해야 한다.

## 28.7 타임아웃 로그

`DefaultOnlineTimeoutExecutor`는 nanoTime으로 대기 경과를 측정해 완료, timeout, interrupt, overload를 구분한다. timeout warn에는 GUID, Service ID, 제한시간, 경과시간, cancel 요청 결과가 있다. Global Handler도 504 응답 정보를 남긴다.

```text
요청 Thread: timeout 감지 → future.cancel(true) → 504 응답 가능
Worker Thread: interrupt 전달 → JDBC/업무 코드 반응 → rollback·종료
```

timeout 응답 로그는 Worker 종료 로그가 아니다. cancelRequested가 true여도 DB Driver가 interrupt에 반응하지 않으면 작업이 잠시 계속될 수 있다. 같은 GUID의 Worker 로그, 활성 거래 Registry 감소, DB Session 상태까지 확인해야 종료를 판정한다.

## 28.8 GUID와 Service ID 로그

`DefaultFilter`는 GUID, userId, Service ID, IP를 ThreadContext에 넣고 finally에서 정리한다. WorkerContext는 MDC를 복사해 Worker에 설치하고 종료 시 제거한다. MyBatis Interceptor는 그 위에 sqlId를 잠시 추가한다. 이 조합으로 `GUID → Service ID → sqlId` 순서로 느린 요청을 좁힐 수 있다.

GUID가 재사용되면 ImageLog 행은 덮일 수 있으므로 timestamp와 Thread 이름을 함께 확인한다. Service ID는 집계 축이고 GUID는 단건 추적 축이다. GUID를 Metric tag로 쓰면 cardinality가 폭증하므로 Trace/Log field로만 사용한다.

## 28.9 실시간 거래 진단

`MgActiveTransactionRegistry`는 TransactionContext 시작 시 GUID 또는 대체키로 활성 거래를 등록하고 종료 시 제거한다. snapshot에는 Service ID, 업무 코드, GUID, Thread ID/이름, 시작 이후 elapsedMs, currentStep이 있다. 현재 currentStep은 생성 시 `RUNNING`으로 고정되고 갱신 API가 없어 DB 대기·SQL 실행·외부 대기를 실제로 구분하지 못한다.

`mgcoa9100Service`는 `MgRuntimeMonitor` 결과를 운영 화면 형태로 조립한다. 단일 `pdmg-service` JVM 기준이며 다중 인스턴스 합산이 아니다. 장애 시 먼저 status checkedAt과 instance를 확인하고, active transaction의 GUID를 로그·ImageLog로 이어간다.

실전에서는 원인을 하나의 카드로 단정하지 않는다. Thread busy가 높고 Hikari pending도 높다면 DB Connection 대기가 Thread를 점유했을 수 있다. Thread busy는 높지만 pending이 0이고 CPU가 높다면 계산 과부하나 과도한 직렬화가 후보가 된다. Heap 비율과 GC 시간이 함께 증가하면 메모리 압박을 의심한다. 이 판정은 인과관계의 증명이 아니라 다음 확인 대상을 줄이는 가설이다. Thread dump, DB Session, SQL 실행계획 같은 외부 증거로 교차 검증해야 한다.

## 28.10 로그 파일 구성

log4j2 설정은 CORE, BIZ, IO, SQL, IF, ERR, MONITOR 유형의 Header 패턴을 정의한다. 공통 Header에는 GUID, 사용자, Service ID, IP가 있고 SQL Header에는 sqlId가 추가된다. 어떤 Appender가 실제 파일 또는 Console에 연결되는지는 배포 설정과 함께 확인해야 한다.

진단 순서는 ERR/timeout에서 GUID 확보, CORE 흐름 확인, BIZ 메서드 구간 확인, SQL sqlId와 elapsed 확인, ImageLog 전문 확인이다. 로그 시간대와 포맷을 통일해야 서로 다른 인스턴스의 순서를 비교할 수 있다.

## 28.11 현재 감시의 한계

`createStatusSnapshot()`은 slowTransactions와 slowSql을 빈 목록으로 넣고 summary count도 0으로 고정한다. 따라서 화면에 “Slow SQL 없음”이 표시되어도 실제 측정 결과가 아니라 미수집 상태일 수 있다. Tomcat Probe 실패 시 max와 busy를 추정값으로 채우며 `maxSource=estimated`로 표시한다. Hikari로 unwrap하지 못하면 Pool 목록은 비어 있다.

GC “last minute” 값도 호출 간 누적 window가 60초를 넘을 때 baseline을 갱신하는 방식이므로 정교한 sliding window Metric이 아니다. 프로세스 재시작과 조회 주기에 따라 해석이 달라진다.

Registry는 메모리 Map이므로 프로세스가 종료되면 기록이 사라지고 다른 인스턴스의 거래를 볼 수 없다. GUID가 같은 두 실행은 같은 key를 사용해 한 항목이 다른 항목을 덮을 수 있다. snapshot의 최대 행 수는 제한되며 정렬도 보장되지 않으므로 가장 오래된 거래가 반드시 표시된다고 볼 수 없다. 모니터링 조회 자체도 애플리케이션 자원을 사용한다는 점을 감안해 호출 주기와 권한을 제한해야 한다.

## 28.12 운영 지표 권장안

TO-BE 최소 지표는 Service ID별 request count, error count, p50/p95/p99, timeout/overload, Worker active/queue/rejection, Tomcat busy/max, Hikari active/idle/pending/max, JVM heap/GC/CPU다. SQL은 sqlId별 count·p95·error·slow count를 수집한다. Metric에는 제한된 label만 두고 GUID는 exemplar 또는 Log/Trace 연결값으로 사용한다.

Actuator/Micrometer를 도입한다면 endpoint 공개 범위와 인증을 먼저 설계하고, Prometheus scraping 또는 승인된 수집기로 시계열화한다. 알람은 평균이 아니라 지속시간과 비율을 사용한다. 예컨대 Pool pending과 timeout이 함께 증가할 때 DB Pool 병목으로 판정한다.

## 28.13 개인정보와 Token 로그 금지

현재 SQL debug는 parameter를 출력하고 Interceptor는 요청 전문 원문을 로그로 남긴다. 이곳에 비밀번호, JWT, 계좌·개인정보가 포함될 수 있다. 운영 debug 활성화만으로 민감값이 유출되지 않도록 코드 단계에서 field 기반 마스킹과 parameter 비출력을 적용해야 한다.

Authorization, Access/Refresh Token, Secret, Private Key는 어떤 로그에도 남기지 않는다. 사용자 ID와 IP도 접근통제·보존기간 대상이다. 성능 분석에 필요한 것은 값의 내용이 아니라 GUID, Service ID, sqlId, duration과 결과 분류다.

### End-to-End 진단 흐름

```text
HTTP 지연 감지
  → Service ID별 p95/p99 확인                    [TO-BE Metric]
  → 느린 GUID 확보
  → CORE: Filter/TCF/응답 경계
  → Runtime: Tomcat busy, Worker/active TX, Hikari pending
  → BIZ: Facade/Service 구간
  → SQL: sqlId + elapsed
  → timeout이면 Worker 종료 여부 별도 확인
  → ImageLog 요청/응답과 오류 코드 대조
```

### 책임·정상·실패 비교

| 신호 | AS-IS 책임 | 정상 해석 | 주의할 실패 해석 |
|---|---|---|---|
| TCF elapsed | TransactionContext | Dispatcher 완료시간 | HTTP 전체시간 아님 |
| SQL debug | MyBatis Interceptor | sqlId별 실행시간 | parameter 민감정보 위험 |
| active TX | Registry | 현재 실행 목록 | currentStep은 RUNNING 고정 |
| Runtime snapshot | Monitor | 단일 JVM 순간값 | slow 목록은 미구현 빈 값 |
| timeout warn | Executor | 요청 Thread 제한 초과 | Worker 종료 보장 아님 |

### Anti Pattern과 체크리스트

- 평균 응답시간만 보고 정상이라 판단한다.
- timeout 504를 Worker·DB 작업 종료로 해석한다.
- 빈 slowSql 목록을 측정된 0건으로 보고한다.
- GUID와 사용자 ID를 Metric label로 넣어 cardinality를 폭증시킨다.
- 성능 분석을 이유로 SQL parameter와 Token을 기록한다.

장애 시나리오별 첫 확인점도 표준화할 수 있다. 503 overload가 급증하면 timeout Executor Queue와 rejection을 먼저 보고, 504가 증가하지만 Hikari pending이 0이면 외부 호출이나 CPU 작업을 좁힌다. DB pending과 SQL elapsed가 함께 상승하면 Connection 부족과 느린 SQL을 분리하기 위해 DB 활성 Session과 실행계획을 확인한다. 응답은 빨리 504로 끝났는데 active transaction이 오래 남으면 interrupt 비반응 작업을 의심한다.

- [ ] timeout 후 Worker와 DB Session 종료를 확인하는가?
- [ ] Tomcat 값이 JMX 실측인지 estimated인지 구분하는가?
- [ ] Hikari pending과 Worker Queue를 함께 보는가?
- [ ] slowTransactions/slowSql 미구현 상태를 화면에 명시하는가?
- [ ] MDC가 모든 finally 경로에서 제거되는가?
- [ ] 전문과 SQL parameter가 마스킹되는가?

### 아키텍처 판단과 다음 장

관측성 도구를 선택할 때는 단일 인스턴스 화면의 편의보다 다중 인스턴스 집계, 장기 보존, cardinality 비용, 민감정보 통제를 기준으로 삼는다. 현재 스냅샷은 현장 진단의 출발점이지만 SLA와 추세 분석의 근거가 되려면 Metric과 Trace가 필요하다.

수집 결과는 설정에 의해 크게 달라진다. timeout 시간, Worker Pool, 로그 레벨, DataSource와 Profile이 바뀌면 같은 코드도 다른 운영 특성을 보인다. 다음 장에서는 이러한 Runtime 동작을 결정하는 Spring 환경구성의 로딩과 Profile 우선순위를 살펴본다.
