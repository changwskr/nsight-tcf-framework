# 제3부 온라인 요청과 TCF 프레임워크

# 10장. Interceptor와 시스템 선처리

Filter가 HTTP Body를 다시 읽을 수 있게 만들고 ServiceContext를 준비했다고 해서 업무 Controller를 바로 실행해도 되는 것은 아니다. Spring MVC가 요청에 맞는 Handler를 선택한 뒤에는 그 Handler를 호출하기 직전에 공통 요청 정보를 확정하고, 요청 전문과 감사 시작점을 남기며, 실행을 허용하거나 차단할 마지막 MVC 경계가 필요하다. PDMG에서는 `ServicePreventionInterceptor`가 이 위치에 있다.

다만 이름과 과거 설계도만 보고 현재 동작을 추정해서는 안 된다. 현행 Interceptor의 `preHandle`은 Header와 GUID를 보완하고 요청 전문을 기록한 뒤 Pre ImageLog를 저장하지만 거래통제를 직접 실행하지 않는다. 거래통제 코드는 STF와 `MgTxControlService`에 존재하지만 현재 `TcfFacade` 호출선에 STF가 연결되지 않았다. 따라서 “거래통제 기능이 구현되어 있다”와 “온라인 요청이 실제로 통제된다”는 서로 다른 문장이다.

이 장은 Spring MVC가 호출하는 Interceptor 생명주기와 직접 Java 호출이 필요한 STF를 구분한다. 시스템 선처리의 실제 책임, 거래통제의 미연결 상태, ImageLog의 정상·예외 흐름, Controller 허용·차단과 업무 트랜잭션 바깥 경계를 소스 기준으로 설명한다.

## 이 장에서 해결할 질문

- Filter가 요청을 준비한 뒤 Interceptor는 무엇을 추가로 처리하는가?
- `preHandle`은 어떤 순서로 Header, GUID와 요청 원문을 확정하는가?
- 현행 Interceptor가 Controller 진입을 실제로 차단하는 조건은 무엇인가?
- 서비스·사용자·IP·영업점·채널·시간대 거래통제는 현재 모두 적용되는가?
- 거래통제 코드가 존재해도 실제 요청에서 실행되지 않을 수 있는 이유는 무엇인가?
- Pre ImageLog와 Post/Exception ImageLog는 언제 기록되는가?
- 시스템 선후처리와 Facade 업무 트랜잭션은 왜 같은 경계가 아닌가?
- 통제와 ImageLog가 실패했을 때 업무 요청은 어떻게 달라지는가?

## 전체 실행 지도

```text
DefaultFilter
  │ Body/Context/MDC 준비
  ▼
DispatcherServlet
  │ HandlerMapping
  ▼
ServicePreventionInterceptor.preHandle          Request Thread
  ├─ multipart 여부
  ├─ ServiceContext 확인
  ├─ Header/sys_comm 보장
  ├─ GUID 생성·MDC 반영
  ├─ Service ID/IP/User 보완
  ├─ 요청 원문 로그
  └─ preImagelog
  │ true
  ▼
Controller → TCF → Handler → Facade TX → Service/DAO
  │
  ▼
ResponseBodyAdvice
  │ 응답 봉투와 responseBody
  ▼
ServicePreventionInterceptor.afterCompletion
  ├─ 정상: postImagelog
  └─ 예외: exceptionImagelog
  ▼
DefaultFilter finally
  └─ Request Thread Context 정리
```

현재 이 흐름에는 `stf.preProcess()`가 없다. STF Bean과 거래통제 Service는 존재하지만 `TcfFacade.process()`가 `TransactionContext`를 만든 뒤 곧바로 `OnlineTimeoutExecutor`와 Dispatcher를 호출한다. 이 사실은 10.6에서 자세히 다룬다.

## 10.1 Interceptor 실행 시점

`ServicePreventionInterceptor`는 Spring MVC의 `HandlerInterceptor` 구현이다. Servlet Filter처럼 코드가 직접 호출하는 것이 아니라 `WebConfiguration`이 MVC Registry에 등록하면 DispatcherServlet의 HandlerExecutionChain이 생명주기에 따라 호출한다.

```java
registry.addInterceptor(servicePreventionInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/error");
```

`WebConfiguration`은 `nhnis.fw.commons.legacy-web.enabled=true`일 때 생성되며 이 설정은 누락돼도 true로 간주된다. Interceptor는 모든 MVC Path에 적용되고 `/error`만 제외한다. TCF ON 공통 Controller뿐 아니라 TCF OFF 업무 Controller와 같은 애플리케이션의 다른 MVC Endpoint도 대상이 될 수 있다.

호출 순서는 HandlerMapping 이후, Controller 메서드 이전이다. 따라서 Interceptor는 선택된 Handler 객체를 받을 수 있지만 Controller 인자를 만드는 ArgumentResolver보다 앞서 실행된다. Filter가 저장한 원문과 Context는 사용할 수 있으나 typed 업무 DTO를 전제로 해서는 안 된다.

| 확장 지점 | 실행 시점 | 알 수 있는 것 | 적합한 책임 |
|---|---|---|---|
| DefaultFilter | DispatcherServlet 전 | 원 HTTP 요청 | Body/JWT/Context 준비 |
| Interceptor.preHandle | Handler 선택 후·호출 전 | Request, Handler, Context | 시스템 선처리·허용 판단 |
| Controller/TCF | 인자 변환 후 | Service ID, 업무 입력 | 라우팅·업무 실행 |
| ResponseBodyAdvice | 반환값 직렬화 전 | 응답 Body | 표준 응답 조립 |
| Interceptor.afterCompletion | 요청 완료 시 | 최종 예외·상태 | 완료 감사·ImageLog |

이 시점 차이 때문에 Interceptor에서 Body Wrapper를 처음 만들거나 Filter에서 Handler Annotation을 검사하는 구조는 맞지 않는다. 각 확장 지점은 필요한 정보가 처음 안정적으로 확보되는 위치에 책임을 둔다.

## 10.2 `preHandle` 처리

현행 `preHandle()`은 TX-FLOW 시작·종료 로그를 감싸고 실제 처리를 `preHandleInternal()`에 위임한다. 처리 순서는 다음과 같다.

```text
preHandle
  1. 시스템 선처리 시작 로그
  2. multipart이면 종료 로그 후 true
  3. ServiceContext가 없으면 WARN 후 true
  4. hdr_nhnis와 sys_comm 보장
  5. GUID 보장, Context와 ThreadContext 동기화
  6. Path/Request에서 Service ID·화면·IP·사용자 보완
  7. 요청 전문 원문 로그
  8. ImageLogHandler.preImagelog
  9. 시스템 선처리 종료 로그
 10. true 반환
```

이 흐름은 “검증에 실패하면 false를 반환한다”는 일반적인 Interceptor 예제와 다르다. multipart와 Context null도 허용하고, 일반 경로의 마지막 반환도 true다. `preImagelog()` 역시 내부 DB 오류를 잡아 로그만 남기므로 보통 false를 만들지 않는다. 현행 Interceptor의 실질적 역할은 차단보다는 공통 정보 보완과 감사 시작 기록이다.

예외 가능성이 전혀 없는 것은 아니다. `ensureHeader`, Header 보완이나 예상하지 못한 RuntimeException이 바깥으로 전파되면 Controller는 실행되지 않는다. 하지만 이것은 명시적인 거래통제 차단이 아니라 시스템 선처리 실패다. 의도한 정책 차단과 구현 오류를 운영 로그에서 구분해야 한다.

multipart 요청은 시스템 선처리 시작·종료 로그만 남기고 Header 보완, 요청 전문 로그와 Pre ImageLog를 모두 건너뛴다. Filter의 multipart JWT 비대칭과 함께 보면 파일 요청은 일반 온라인 JSON과 다른 감사·보안 경로를 가진다. 파일 Endpoint가 운영 대상이면 별도 인증과 감사 계약을 검증해야 한다.

### 한 건의 요청으로 보는 preHandle

예를 들어 `/mgcoa5530S0`로 JSON 요청이 들어왔고 Filter가 `ServiceContext`와 요청 원문을 준비했지만 Header의 GUID와 Service ID가 비어 있다고 하자. Interceptor는 먼저 Context의 Header 구조가 존재하는지 확인한다. 이어 GUID를 새로 만들고 Header, Context, Log4j ThreadContext에 같은 값을 넣는다. Service ID는 URI 마지막 Segment에서 `mgcoa5530S0`을 얻어 Header에 보완한다. 화면 ID가 없다면 현재 정규식으로 뒤의 `S0`을 제거한 값을 후보로 만들고, IP와 사용자도 비어 있을 때만 보완한다. 마지막으로 Filter에서 보존한 JSON을 Pre ImageLog에 전달한 뒤 true를 반환한다.

이 예시에서 중요한 것은 “빈 값을 채운다”는 조건이다. Client 또는 앞선 Filter가 이미 값을 넣었다면 Interceptor가 그 값의 진위를 다시 인증하거나 무조건 교체하지 않는다. 그러므로 Header 보완은 신뢰성 검증과 같은 뜻이 아니다. 사용자 ID가 Header에 있다는 이유만으로 인증된 사용자가 되지 않고, `X-Forwarded-For`가 있다는 이유만으로 그 IP를 신뢰할 수도 없다. 인증된 JWT Claim, 신뢰 Proxy가 정리한 주소와 Header 값의 일치 여부는 별도의 보안 계약이 필요하다.

반대로 Filter 설정이 꺼져 Context가 만들어지지 않은 요청은 Warning 이후 그대로 Controller로 이동한다. 이때 Controller가 단순 값을 반환하면 HTTP 성공처럼 보이지만 GUID 연계, 요청 ImageLog와 공통 Header 보완은 수행되지 않았다. 운영 점검에서는 HTTP Status만 보지 말고 같은 GUID의 TX-FLOW, ImageLog와 Context 생성 로그가 함께 있는지 확인해야 한다.

## 10.3 요청 전문 확인

Interceptor는 Servlet InputStream을 무조건 다시 읽지 않는다. Filter가 준비한 여러 위치에서 다음 우선순위로 요청 원문을 찾는다.

```text
ServiceContext.requestBody
  ↓ 없거나 공백
Request Attribute "PDMG_REQUEST_BODY"
  ↓ 없음
CachedBodyHttpServletRequest.cachedBody
  ↓ 없음
"(empty-request-body)"
```

Wrapper가 다른 Servlet Wrapper 안에 중첩될 수 있으므로 현재 Request에서 내부 Request를 따라가며 `CachedBodyHttpServletRequest`를 찾는다. 발견한 byte 배열은 UTF-8 문자열로 바꾼다. 이 설계는 Interceptor가 원 Stream을 다시 소비하지 않고 Filter와 동일한 메시지를 감사하도록 한다.

요청 원문은 `PdmgMessagePrinter.asIs()`로 정리된 뒤 CORE 로그와 `preImagelog()`에 전달된다. 로그 출력 자체는 try/catch로 감싸 실패해도 업무 흐름을 계속한다. 그러나 원문 전체 저장은 Token·개인정보·대용량 데이터 위험을 만든다. Authorization은 HTTP Header라 Body 원문에는 없지만 DTO 안의 고객·계좌·식별정보는 포함될 수 있다.

운영 정책은 최소한 다음을 정해야 한다.

- 기록 가능한 거래와 제외 거래
- 최대 전문 크기와 절단 표시
- 필드 기반 마스킹과 중첩 배열 처리
- 암호화·보존 기간·조회 권한
- ImageLog 삭제와 감사 보존의 충돌
- 로그 실패가 업무를 차단할지 여부

원문이 비어 있다는 로그만으로 Client가 빈 Body를 보냈다고 단정하지 않는다. Filter 비활성, Wrapper 미전달, Context 누락도 같은 증상을 만든다. Filter 로그와 Context 생성 여부를 함께 본다.

### 요청 전문 장애를 추적하는 순서

요청 값이 Controller DTO에는 들어왔는데 ImageLog에는 `(empty-request-body)`로 남는다면 JSON 역직렬화 문제부터 의심할 상황이 아니다. Controller가 DTO를 받았다는 사실은 Spring이 읽을 Body가 있었다는 증거다. 먼저 `ServiceContext.requestBody`, `PDMG_REQUEST_BODY` Request Attribute와 Cached Wrapper가 어느 단계에서 사라졌는지 확인한다. Custom Filter가 원래 Request를 다시 Chain에 넘겼거나 Wrapper 순서가 바뀌면 이런 비대칭이 생길 수 있다.

반대로 ImageLog에는 JSON이 있는데 Controller가 400을 반환한다면 Body 보존은 성공했지만 DTO 구조, Content-Type 또는 역직렬화 규칙이 맞지 않을 가능성이 높다. Interceptor가 남긴 원문은 이때 Client가 실제로 보낸 형태를 확인하는 근거가 된다. 단, 운영 원문을 개발자가 무제한 열람하는 방식은 피하고 권한·마스킹 정책 안에서 진단해야 한다.

대용량 요청에서는 동일한 문자열이 Cached byte 배열, Context 문자열, 일반 로그와 ImageLog에 중복 존재할 수 있다. 이는 Heap과 DB I/O를 함께 증가시킨다. “전문을 기록한다”는 요구는 최대 크기, 초과 시 절단 또는 Hash 기록, Binary/multipart 제외와 민감필드 Masking까지 포함한 계약이어야 한다. 제한 없이 `toString()` 결과를 저장하는 것은 감사 기능이 아니라 새로운 장애 원인이 된다.

## 10.4 Service ID 결정

Interceptor는 최종 거래를 Dispatcher처럼 결정하지 않는다. `sys_comm.rms_svc_c`가 비어 있을 때 Request URI의 마지막 Segment를 보조값으로 채운다. 값이 이미 있으면 덮어쓰지 않는다.

```text
sys_comm.rms_svc_c 존재
  → 그대로 유지

누락
  → requestURI 마지막 segment
  → rms_svc_c
```

화면 ID `scid`가 비면 Service ID에서 `[SD]\d+$` Pattern을 제거한다. 이 Pattern은 S와 D 유형만 처리하므로 C/U와 다른 처리 유형까지 일반적으로 제거한다고 단정해서는 안 된다. IP는 `X-Forwarded-For` 첫 값이나 Remote Address, 조작자는 ThreadContext의 `userId` 또는 `LOCAL`로 보완한다.

최종 Service ID 우선순위는 뒤의 `OnlineTransactionController`가 적용한다. Context Header → 요청 JSON Header → Path 순이다. Interceptor가 값을 보완했다는 사실과 값의 출처를 검증했다는 사실은 다르다. Path와 Header가 다를 때 현행 코드는 불일치를 차단하지 않는다.

```text
Path   /mgcoa9000S0
Header rms_svc_c=mgcoa9000D0
  → Header 우선 가능
```

신규 표준에서는 복수 위치의 Service ID가 모두 존재하면 일치 여부를 검사하고, 변경 거래에서는 불일치를 반드시 거절하는 편이 안전하다. 이 검증을 Interceptor에 둘지 Controller의 Service ID Resolution에 둘지는 TCF ON/OFF 공통성과 오류 응답 계약을 기준으로 결정한다.

## 10.5 시스템 공통 검증

현행 `preHandle`이 수행하는 검증은 “모든 필드의 업무 유효성 검사”가 아니다. Header 객체와 `sys_comm`이 없으면 생성하고 GUID가 없으면 UUID를 발급하며, ImageLog에 필요한 Service ID·화면·IP·사용자를 가능한 범위에서 보완한다. 인증은 앞선 Filter 책임이고 업무 입력 검증은 Service/Rule 책임이다.

GUID 보완은 Header, `ServiceContext.guid`, Log4j ThreadContext의 `guid`를 함께 갱신한다. 이 값이 일치해야 요청 로그와 ImageLog를 연결할 수 있다. 자세한 Context 구조와 Worker Thread 전파는 다음 장에서 다룬다.

| 항목 | AS-IS preHandle | 의미 |
|---|---|---|
| Header/sys_comm | 없으면 생성 | Null 접근 방지 |
| GUID | 없으면 UUID 생성 | 추적키 보장 |
| Service ID | 비면 Path 후보 | ImageLog·후속 라우팅 보조 |
| 화면 ID | 비면 Service ID에서 파생 | 운영 추적 보조 |
| IP | 비면 Forwarded/Remote | 감사 입력, 신뢰 검증은 별도 |
| 사용자 | 비면 MDC 또는 LOCAL | 감사 입력, 인증 증거 아님 |
| 업무 DTO | 검사하지 않음 | 업무 계층 책임 |
| JWT | 검사하지 않음 | Filter 책임 |

Context가 null이면 Warning만 남기고 true를 반환한다. 따라서 Filter를 꺼도 단순 Controller가 실행될 수 있지만 Header·GUID·ImageLog가 없는 축소 동작이 된다. “Controller가 성공했다”는 결과만으로 시스템 공통 검증이 적용됐다고 판단하면 안 된다.

## 10.6 거래 통제

거래통제는 특정 조건에 맞는 온라인 거래를 업무 실행 전에 거절하는 정책이다. 서비스 장애, 사용자 제한, 특정 IP·영업점·채널 차단과 긴급 전체 통제에 사용할 수 있다. Boolean 하나가 아니라 입력값 추출, Rule 우선순위, 예외 대상, 정책 저장소 장애와 차단 결과를 함께 설계해야 한다.

### 구현된 거래통제 구조

현행 코드의 의도된 구조는 다음과 같다.

```text
stf.preProcess(TransactionContext)
  → MgTxControlService.check(hdr_nhnis)
      → MgTxControlRequest 생성
      → 예외 Service ID 확인
      → GLOBAL 허용 확인
      → MgTxControlRepository.findBlockingRule
      → 차단 Rule이면 BizException FW0410
      → 조회 실패면 BizException FW0411, fail-close
```

`nhnis.fw.txcontrol.enabled`의 기본값은 true다. 그러나 Property가 true라는 사실만으로 검사되지 않는다. 호출자 `stf.preProcess()`가 실행되어야 한다.

### AS-IS 핵심: 현재 호출선에 미연결

현행 `TcfFacade` 생성자는 Dispatcher와 OnlineTimeoutExecutor만 주입받는다. `process()`는 TransactionContext를 만든 뒤 Executor 안에서 Dispatcher를 호출한다. STF를 주입하거나 `preProcess()`를 부르는 코드가 없다. Interceptor 역시 `MgTxControlService`를 주입하지 않는다.

```text
현재 실제 TCF ON

Controller
  → TcfFacade
      → TransactionContext.fromCurrent
      → OnlineTimeoutExecutor
          → Dispatcher
              → Handler

존재하지만 미연결

stf.preProcess → MgTxControlService → Repository
```

그러므로 현재 온라인 요청은 `TB_MG_TX_CONTROL` Rule 때문에 Controller 직전에서 차단된다고 말할 수 없다. 관리 화면에서 차단 Rule을 등록해도 실행 호출선이 없으면 효과가 없다. 운영 적용 전에는 로그의 `[stf] transaction control check`와 실제 차단 통합 테스트로 연결을 증명해야 한다.

### 지원하는 통제 축과 시간대의 차이

Repository SQL은 다음 통제 유형을 조회한다.

| 통제 축 | AS-IS 입력 | SQL 지원 |
|---|---|---:|
| GLOBAL | 전체 Rule | O |
| BUSINESS | Service ID 앞 문자에서 업무코드 파생 | O |
| SERVICE | `rms_svc_c` | O |
| CHANNEL | `tr_sysid`, 없으면 `scid` | O |
| BRANCH | `tr_brc` | O |
| USER | `optr_eno` | O |
| IP | `tr_trm_ipadr`를 `SERVICE_NAME`과 비교 | O, Schema 의미 점검 필요 |
| 시간대 | 현재 시각·시작/종료 시각 | X |

요구 목차에는 시간대별 통제가 포함되지만 현재 Repository SQL에는 시간 조건이 없다. 시간대 통제를 AS-IS라고 기술해서는 안 된다. TO-BE로 추가하려면 Timezone, 자정을 넘는 구간, 휴일, 시작·종료 경계 포함 여부와 DB/애플리케이션 시각 기준을 정해야 한다.

IP Rule이 `SERVICE_NAME` Column과 비교되는 점도 Schema와 관리 UI 계약을 확인해야 한다. 이름이 기대와 다르므로 단순히 올바른 IP Column이라고 가정하지 않는다. Channel은 전용 Header가 아니라 `tr_sysid` 또는 `scid`에서 파생된다. 통제 축 이름과 실제 데이터 출처를 정확히 문서화해야 한다.

### 예외와 실패 정책

`mgcoa9001*` 거래통제 관리, `mgcoa9100*` Runtime 진단, `mgjwa*` 인증과 Health 거래는 Exemption이다. 관리 거래까지 차단해 해제 불가능해지는 상황을 막기 위한 선택이다. 면제 범위를 넓힐 때는 인증 우회 경로가 되지 않는지 검토한다.

GLOBAL Rule에 `BLOCK_YN=N`이 있으면 개별 차단을 무시한다. Repository 조회 실패는 Service에서 FW0411로 차단하려는 fail-close 정책이지만, `isGlobalUnblockActive()` 조회 자체는 오류를 false로 바꾸고 개별 조회를 계속한다. 연결 시 이 실패 의미를 운영 절차와 맞춰야 한다.

### 연결 위치의 설계 선택

```text
안 A: STF → OnlineTimeoutExecutor → Dispatcher
  - 통제는 업무 TX와 Timeout 밖
  - 빠른 차단, 통제 DB 지연은 온라인 제한에서 제외

안 B: OnlineTimeoutExecutor → STF → Dispatcher
  - 통제도 Worker·온라인 시간 예산 안
  - TransactionTemplate 안이면 통제 조회가 업무 TX에 참여할 수 있음
```

통제는 업무 DML 전에 차단해야 하지만 업무 트랜잭션과 같은 DB Connection을 쓸 필요는 없다. 감사·가용성과 제한시간 정책을 먼저 정하고 위치를 선택한다. 어떤 안이든 TCF OFF에도 같은 정책이 필요한지 별도 Entry Adapter를 설계해야 한다.

### 통제 판정 한 건을 끝까지 추적하기

가령 인증 사용자가 영업점 `001`, 채널 `MOBILE`, 단말 IP `10.20.30.40`에서 `mgcoa5530S0`을 호출한다고 하자. STF가 연결됐다는 전제에서 `MgTxControlService`는 Header로 통제 요청을 만들고 먼저 면제 거래인지 확인한다. 면제가 아니면 GLOBAL 해제 Rule을 조회하고, 활성화된 전체 허용 Rule이 없을 때 개별 차단 Rule을 찾는다. Repository는 GLOBAL뿐 아니라 업무, 서비스, 채널, 영업점, 사용자와 IP 조건 중 요청에 맞는 활성 Rule을 조회한다. 차단 Rule이 발견되면 FW0410 예외를 발생시켜 Dispatcher와 업무 Facade로 진행하지 않는 것이 의도다.

이 과정에서 어느 한 식별자가 비었다고 모든 통제가 무효가 되는 것은 아니다. Service ID가 있으면 SERVICE 또는 BUSINESS Rule은 평가할 수 있지만 사용자 ID가 비면 USER Rule과 일치하지 않을 수 있다. 문제는 누락을 “통제 대상 아님”으로 볼지 “식별 불가능하므로 차단”할지 정책이 명시돼 있지 않으면 보안 결과가 데이터 품질에 좌우된다는 점이다. 특히 사용자, 영업점과 IP는 Client가 임의로 제공한 값이 아니라 인증·접속 인프라가 확정한 값이어야 한다.

여러 Rule이 동시에 맞는 경우도 생각해야 한다. 예를 들어 전체 허용 Rule과 특정 서비스 차단 Rule이 같이 있으면 현행 Service는 GLOBAL unblock을 먼저 확인해 개별 조회를 생략한다. 따라서 운영자는 “더 구체적인 Rule이 항상 우선”이라고 가정해서는 안 된다. 우선순위는 화면 배치가 아니라 Service와 SQL 실행 순서로 결정된다. Rule 등록 UI에는 이 의미를 명확히 보여주고, 충돌 Rule을 사전 탐지하는 검증이 필요하다.

통제 저장소 장애도 업무 오류와 다르다. Rule 조회가 실패했을 때 fail-close로 모든 거래를 막으면 보안적으로 보수적이지만 통제 DB 장애가 온라인 전체 장애가 될 수 있다. fail-open은 가용성을 보장하지만 긴급 차단이 작동하지 않을 수 있다. 현행 코드의 FW0411 의도를 채택한다면 통제 DB 이중화, 짧은 조회 Timeout, 장애 경보와 승인된 비상 우회 절차가 함께 있어야 한다. 오류 코드를 하나 추가하는 것만으로 운영 가능한 fail-close가 되지는 않는다.

### 시간대 통제를 추가할 때 결정할 것

시간대 Rule은 단순히 `start <= now <= end` 조건 하나를 붙이는 기능이 아니다. `23:00~02:00`처럼 자정을 넘는 구간, 주말·공휴일, 서버와 사용자 지역의 Timezone, 시작과 종료 시각을 포함할지, 이미 시작한 장기 거래를 어떻게 할지를 정해야 한다. 여러 인스턴스의 Clock이 다르면 같은 요청이 Node마다 다르게 판정될 수 있으므로 기준 시각도 통일해야 한다.

TO-BE 구현에서는 Rule의 유효기간과 일중 허용시간을 분리하는 편이 이해하기 쉽다. 유효기간은 정책 자체가 적용되는 날짜 범위이고, 일중 시간은 각 적용일의 차단 구간이다. 운영 화면은 계산된 “현재 차단 여부”와 다음 상태 변경 시각을 보여줘야 한다. 테스트는 경계 직전·정각·직후, 자정 통과와 Clock 관련 사례를 고정 Clock으로 재현해야 한다. 그러나 이것들은 목표 설계이며 현행 Repository에 구현된 동작으로 읽어서는 안 된다.

## 10.7 이미지로그 요청 등록

`preHandle`은 GUID를 확정한 뒤 `ImageLogHandler.preImagelog(header, requestRaw)`를 호출한다. Handler는 Header에서 GUID, Service ID, 화면 ID, 조작자와 IP를 꺼내고 서버 현재 시각과 요청 원문을 저장한다. Header의 업무 일시가 아니라 서버 수신 시각을 Request Time으로 사용한다.

```text
preHandle
  → GUID 보장
  → 요청 원문 확보
  → ImageLogDTO
  → 기존 GUID UPDATE 시도
      ├─ 존재: Pre Field 갱신
      └─ 없음: INSERT
```

같은 GUID가 재전송되면 무조건 Primary Key 오류를 내기보다 기존 행을 갱신한다. 동시 INSERT 경합에는 DuplicateKeyException을 잡아 다시 UPDATE한다. 이는 운영 오류 로그를 줄이지만 동일 GUID 재사용이 서로 다른 호출을 덮어쓸 수 있다는 뜻이므로 Client의 GUID 생성 규칙이 중요하다.

ImageLog 저장 메서드는 DB 예외를 내부에서 catch하고 Error 로그만 남긴다. 따라서 현행 Pre ImageLog DB 장애는 보통 Controller 진입을 막지 않는 fail-open 성격이다. 감사 로그가 필수인 업무에서는 이 정책이 적절한지 규제·운영 기준으로 판단해야 한다. 반대로 DB 장애 때 모든 온라인 업무를 차단하면 ImageLog 장애가 전체 서비스 장애로 확대된다.

전문 원문을 저장하므로 개인정보 Masking, 크기 제한, 보존과 접근통제가 필요하다. ImageLog는 편리한 전문 복제 저장소가 아니라 장애 추적과 감사 목적의 제한된 데이터여야 한다.

### ImageLog 행의 상태 전이

ImageLog 한 행은 업무 트랜잭션의 상태표가 아니라 HTTP 거래 관찰 기록이다. Pre 단계에서는 “요청을 받았고 Controller 진입을 준비했다”는 사실을 남긴다. 정상 응답 이후 Post 단계는 응답 원문과 결과 정보를 보완하고, 예외 단계는 확인 가능한 오류 정보를 같은 GUID에 남긴다. 따라서 Pre만 있고 Post·Exception이 없는 행은 무조건 업무가 실패했다는 뜻이 아니라 프로세스 강제 종료, 응답 후처리 누락, multipart Skip, GUID 불일치 또는 ImageLog DB 장애까지 포함하는 조사 신호다.

```text
행 없음
  └─ preImagelog 성공 → PRE 기록
                         ├─ postImagelog 성공      → 정상/업무오류 응답 보완
                         ├─ exceptionImagelog 성공 → 예외 정보 보완
                         └─ 후속 기록 실패         → PRE만 잔존
```

동일 GUID 재사용 때 UPDATE 우선 정책은 재시도 친화적으로 보이지만 요청 원문과 시각이 갱신되면 최초 시도의 증거가 희석될 수 있다. GUID를 멱등키로 볼지 각 시도 식별자로 볼지 먼저 정해야 한다. 동일 업무를 재시도해도 새 GUID를 발급하고 원 업무 키를 별도 필드로 연결하면 시도별 감사가 선명해진다. 반대로 같은 GUID를 유지한다면 시도 횟수와 변경 이력을 별도 보존해야 한다.

ImageLog 장애 경보는 Error 로그 건수만으로 충분하지 않다. Pre 대비 완료 기록 비율, 일정 시간 이상 PRE 상태인 행, Duplicate GUID 갱신 빈도, 저장 지연과 원문 크기 분포를 함께 관찰해야 한다. 업무 성공률이 정상이어도 감사 저장소가 조용히 실패할 수 있기 때문이다. fail-open 선택은 실패를 무시한다는 뜻이 아니라 업무와 분리해 더 강하게 감시한다는 뜻이다.

## 10.8 Controller 진입 허용·차단

Spring MVC에서 `preHandle`이 true를 반환하면 다음 Interceptor 또는 Controller로 진행하고 false면 Chain이 중단된다. 예외가 발생해도 Controller는 실행되지 않는다. 하지만 이 일반 원리와 PDMG AS-IS를 구분해야 한다.

현행 `ServicePreventionInterceptor`는 다음 경로에서 true를 반환한다.

- multipart 요청
- ServiceContext null
- 일반 JSON 선처리 완료

명시적으로 false를 반환하는 코드는 없다. 거래통제도 호출하지 않는다. 따라서 “Rule이 차단이면 preHandle false”라는 설명은 현재 사실이 아니다. 향후 거래통제를 Interceptor에 연결한다면 false 반환보다 표준 예외를 발생시켜 이유와 오류 코드를 일관되게 전달하는 방법을 검토할 수 있다.

| 실패·조건 | Controller | 업무 TX | AS-IS 결과 |
|---|---:|---:|---|
| Filter JWT 실패 | 미진입 | 시작 안 함 | 401 |
| Context null | 진입 | 경로에 따라 | Warning 후 허용 |
| multipart | 진입 | 경로에 따라 | 시스템 선처리 대부분 Skip |
| Pre ImageLog DB 실패 | 대체로 진입 | 이후 시작 | Error 로그 후 허용 |
| Interceptor 예상 밖 예외 | 미진입 | 시작 안 함 | MVC 예외 경로 |
| 거래통제 차단 Rule | 현재 검사 안 됨 | 영향 없음 | STF 연결 필요 |
| Facade/Service 예외 | 이미 진입 | Rollback 후보 | 업무 예외 처리 |

차단 지점은 가능한 한 업무 트랜잭션 전에 위치해야 불필요한 Connection과 DML을 만들지 않는다. 차단 이유는 GUID, Service ID, 통제 유형과 오류 코드로 추적하되 사용자·IP 전체를 과도하게 로그에 노출하지 않는다.

## 10.9 `afterCompletion`

`afterCompletion`은 Handler 실행과 응답 처리 완료 단계에서 호출된다. `postHandle`은 TX-FLOW만 기록하고 응답 전문 조립을 하지 않는다. `@ResponseBody` 반환값은 `ResponseBodyAdvice.beforeBodyWrite()`가 표준 응답으로 만들고 `ServiceContext.responseBody`에 저장한다. 그 뒤 `afterCompletion`이 ImageLog를 완료한다.

정상 경로에서는 multipart가 아니고 Context가 있으면 `postImagelog(header,responseBody)`를 호출한다. 응답 전문에 `result.stdErrCode`가 있으면 같은 ImageLog 행에 예외 정보도 보완한다. DB UPDATE가 실패하거나 행이 없으면 로그를 남기지만 예외를 밖으로 전파하지 않는다.

예외 경로에서는 시스템 오류·후처리 로그를 남기고 `exceptionImagelog()`를 호출한다. Context에서 Header와 가능하면 Response Body를 가져온다. 이후 Holder를 제거하고 `throw ex`로 예외를 다시 던진다.

```text
정상
  Advice: responseBody 생성
  → afterCompletion(ex=null)
      → postImagelog

예외
  afterCompletion(ex!=null)
      → exceptionImagelog
      → ServiceContextHolder.removeInstance
      → throw ex
```

`afterCompletion`에서 원 예외를 다시 던지는 구조는 이미 진행 중인 예외 처리와 중복 로그를 만들 가능성이 있다. 응답이 Commit된 뒤 새 오류 응답으로 바꿀 수도 없다. TO-BE에서는 원 예외 보존, ImageLog 실패 격리와 중복 전파 여부를 통합 테스트로 검토해야 한다.

Filter의 finally도 Context를 정리한다. 예외 경로의 Interceptor 제거는 방어적 보조 정리이며 정상 경로의 최종 소유자는 Filter다. Filter 단계에서 막힌 요청에는 afterCompletion이 호출되지 않으므로 Interceptor 정리만으로 충분하지 않다.

### 완료 Callback을 해석할 때의 주의점

`afterCompletion`은 업무 Commit Callback이 아니다. Spring MVC Handler Chain이 완료될 때 호출되는 Web Lifecycle Callback이다. Facade가 이미 Commit된 뒤 응답 변환에서 실패할 수도 있고, 업무가 Rollback된 뒤 공통 예외 응답을 정상적으로 직렬화할 수도 있다. 그러므로 `ex == null`만으로 업무 성공을 판정하지 말고 표준 응답의 결과 코드와 Transaction 로그를 함께 봐야 한다.

또한 ResponseBodyAdvice가 실행되지 않는 응답 유형이나 예외 경로에서는 `ServiceContext.responseBody`가 비어 있을 수 있다. 이때 Exception ImageLog에 응답 원문이 없다고 해서 예외가 없었던 것은 아니다. 원 예외, 공통 예외 Handler, Response Commit 시점과 Context 저장 순서를 함께 추적해야 한다. Redirect, Streaming, 파일 응답처럼 일반 JSON 변환과 다른 Endpoint는 별도의 완료 감사 전략이 필요하다.

`throw ex`는 원인을 숨기지 않는다는 장점이 있지만 Container가 이미 처리 중인 예외를 완료 Callback에서 다시 던지면 중복 오류 로그와 다른 예외 Handler 동작을 만들 수 있다. 변경하려면 단위 테스트만으로 결론내지 말고 Controller 예외, 응답 변환 예외, Client 연결 종료와 ImageLog DB 실패를 실제 MVC 통합 테스트로 검증해야 한다. 핵심은 감사 실패가 원 업무 예외를 덮지 않고 최초 원인이 관찰되는 것이다.

## 10.10 시스템 선후처리와 업무 트랜잭션 관계

시스템 선처리는 Controller와 Facade보다 앞에 있고 시스템 후처리는 Facade가 반환한 뒤에 있다. 따라서 Facade의 `@Transactional`이 만든 업무 트랜잭션에 자동 포함되지 않는다.

```text
Request Thread

Interceptor.preHandle
  └─ Pre ImageLog                         업무 TX 밖

Controller → TcfFacade
  → Worker Thread 가능
      → TransactionTemplate / Facade TX BEGIN
          → Handler
          → BizPre
          → Service → DAO
          → BizPost
        COMMIT / ROLLBACK

ResponseBodyAdvice
Interceptor.afterCompletion
  └─ Post/Exception ImageLog              업무 TX 밖
```

Timeout이 활성화되면 업무 트랜잭션은 Worker Thread에서 시작할 수 있어 Thread 경계도 다르다. Request Thread의 Interceptor가 수행한 JDBC 작업은 나중에 Worker에서 시작한 업무 TX에 소급 참여하지 않는다. 같은 HTTP 요청이라는 사실은 같은 Spring Transaction이라는 뜻이 아니다.

ImageLogHandler는 `JdbcTemplate`을 직접 사용하지만 이 위치에는 Interceptor를 감싸는 업무 `@Transactional`이 없다. 각 호출은 DataSource 자동 커밋 또는 별도 Transaction 설정에 의존한다. 실패 기록을 업무 Rollback과 무관하게 남기려는 목적에는 분리가 맞지만, 두 데이터가 원자적으로 일치한다고 기대해서는 안 된다.

```text
업무 ROLLBACK  ≠ Pre ImageLog 자동 ROLLBACK
업무 COMMIT    ≠ Post ImageLog 성공 보장
ImageLog 성공  ≠ 업무 성공
```

시스템 기록을 반드시 독립 커밋하려면 명시적 별도 TransactionManager와 `REQUIRES_NEW` 경계를 둘 수 있다. 반대로 업무 DML과 반드시 같이 Rollback해야 하는 데이터는 Interceptor가 아니라 Facade TX 내부의 업무 책임으로 옮겨야 한다. 감사 로그와 업무 데이터의 목적을 섞지 않는다.

### 정상·실패 End-to-End

```text
정상
Filter → preHandle → Pre ImageLog
  → Controller/TCF → Facade TX COMMIT
  → Advice 표준 응답 → postImagelog
  → Filter 정리

업무 실패
Filter → preHandle → Pre ImageLog
  → Controller/TCF → Facade TX ROLLBACK
  → 예외 처리 → exception/post ImageLog
  → Filter 정리

시스템 선처리 실패
Filter → preHandle 예외
  → Controller 미진입, 업무 TX 미시작
  → 가능한 예외 ImageLog/공통 오류
  → Filter 정리

통제 Rule 등록(현재)
Filter → preHandle 허용 → STF 미호출
  → 차단 Rule이 실제 업무를 막지 못함
```

### 로그로 경계를 증명하는 방법

트랜잭션 경계는 호출 순서 그림만으로 확정하지 않는다. 테스트 거래 한 건에 고정 GUID를 넣고 Request Thread 이름, Worker Thread 이름, Transaction 활성 여부와 ImageLog 시각을 함께 비교한다. 기대되는 순서는 Request Thread의 Pre ImageLog, Worker의 TX Begin과 Service/DAO, Commit 또는 Rollback, Request Thread의 Post/Exception ImageLog다. Timeout Executor가 꺼져 같은 Thread에서 실행되더라도 Begin 이전과 종료 이후의 JDBC 작업은 업무 트랜잭션 밖이라는 점은 변하지 않는다.

업무 Service가 예외를 던지는 통합 테스트에서는 업무 Table 변경이 Rollback되고 Pre 또는 Exception ImageLog가 남는지 확인한다. 이 두 결과가 동시에 관찰되면 ImageLog와 업무 DML이 원자적이지 않다는 현재 경계를 증명한다. 반대로 ImageLog까지 사라진다면 우연히 같은 TransactionManager와 Connection에 참여했는지, Test 자체가 상위 `@Transactional`로 모든 작업을 감쌌는지 확인해야 한다. Test Framework의 Rollback이 운영 경계를 왜곡할 수 있다.

Timeout 테스트에서는 Worker가 늦게 종료되는 상황도 본다. Request Thread가 Timeout 응답과 후처리를 끝낸 뒤 Worker가 DB 작업을 계속하면 “완료 ImageLog 이후 업무 SQL”이라는 역전이 나타날 수 있다. 목표가 작업 취소와 Rollback이라면 JDBC Statement Timeout, Thread Interrupt 반응과 Transaction Rollback까지 증명해야 한다. 단순히 Client가 Timeout 응답을 받았다는 사실은 Worker 작업이 중단됐다는 증거가 아니다.

### 실전 검증 시나리오

| 시나리오 | 주입 조건 | 확인할 결과 |
|---|---|---|
| 정상 JSON | 유효 Header와 Body | 동일 GUID의 Pre/Post, 업무 Commit |
| GUID 누락 | Header GUID 제거 | 생성 GUID가 Header·MDC·ImageLog에서 일치 |
| Context 누락 | Filter 비활성 또는 Test Stub | Warning과 Controller 허용, ImageLog 부재 |
| multipart | 파일 요청 | 선처리 Skip 범위와 별도 인증·감사 결과 |
| ImageLog DB 오류 | Log Table 접근 실패 | 업무 허용 여부와 Error 경보 |
| 업무 예외 | Service에서 Rollback 예외 | 업무 DML Rollback, 실패 ImageLog 유지 |
| 차단 Rule | SERVICE 차단 등록 | AS-IS 미차단 재현, 연결 후 FW0410 |
| 통제 DB 오류 | Repository Timeout/SQL 오류 | 연결 후 FW0411과 fail-close 영향 |
| Service ID 불일치 | Path와 Header를 다르게 전송 | 현재 우선순위와 목표 거절 정책 비교 |
| 온라인 Timeout | 느린 DAO/SQL | 응답뿐 아니라 Worker 취소·Rollback 확인 |

이 Test Matrix는 Controller 응답만 Assert해서는 부족하다. DB의 업무 행, ImageLog 행, GUID별 로그 순서, Thread 이름과 Transaction 상태를 같이 수집해야 한다. 거래통제를 연결하기 전과 후의 결과를 별도 Baseline으로 보관하면 “Rule은 등록됐는데 왜 거래가 실행됐는가” 같은 운영 논쟁을 호출선 증거로 해결할 수 있다.

## 책임과 경계 표

| 구성요소 | Caller | 책임 | Callee | 금지 책임 |
|---|---|---|---|---|
| DefaultFilter | Servlet Container | Body/JWT/Context 준비 | MVC Chain | 거래통제 DB·업무 검증 |
| Interceptor.preHandle | Spring MVC | Header/GUID 보완, 요청 감사 | Controller Chain | Service/DAO 실행 |
| STF | TcfFacade가 호출해야 함 | 거래통제 의도 | MgTxControlService | Web Body 처리 |
| MgTxControlService | STF | 통제 Request·차단 판정 | Repository | 업무 DML |
| ImageLogHandler | Interceptor | 요청·응답·예외 감사 | JDBC | 업무 성공 결정 |
| ResponseBodyAdvice | Spring MVC | 응답 봉투·원문 저장 | Converter | 최종 완료 감사 단독 처리 |
| afterCompletion | Spring MVC | 완료·예외 ImageLog | Container | 새 업무 트랜잭션 시작 |

## Anti Pattern

1. `ServicePreventionInterceptor`가 현재 거래통제를 수행한다고 문서만 보고 단정한다.
2. STF Bean이 존재하므로 자동 실행된다고 생각한다. 직접 호출부가 없으면 실행되지 않는다.
3. 시간대 통제 요구를 현재 Repository가 지원한다고 표현한다.
4. Interceptor에서 업무 Service나 DAO를 호출해 데이터 변경을 수행한다.
5. Pre ImageLog가 Facade 업무 TX와 같이 Rollback된다고 가정한다.
6. Client의 사용자·IP·영업점 값을 인증된 Context와 비교하지 않고 통제에 사용한다.
7. ImageLog 저장 실패를 무조건 삼키거나 반대로 모든 업무를 차단하도록 이유 없이 바꾼다.
8. 요청 전문과 Token·개인정보를 Masking 없이 저장한다.
9. `preHandle=false`와 예외를 혼용하면서 오류 응답 계약을 정의하지 않는다.
10. `afterCompletion`에서 응답이 이미 Commit된 뒤 새 응답을 작성하려 한다.
11. Filter·Interceptor·STF에 같은 검증을 복제해 어느 결과가 최종인지 불명확하게 만든다.
12. TCF ON만 통제하고 OFF Controller 우회 경로를 남긴다.

## 아키텍처 판단 포인트

공통 검증을 추가할 때 먼저 필요한 정보와 차단 시점을 묻는다. 원 HTTP 인증과 Body 준비는 Filter, 선택된 Handler 기반 허용 판단과 요청 감사는 Interceptor, Service ID 기반 거래 실행 직전 정책은 STF/TCF 경계, 업무 규칙은 Service/Rule에 둔다. 이름에 “선처리”가 들어간다는 이유로 같은 클래스에 모으지 않는다.

거래통제의 핵심은 Rule Table보다 실행 호출선이다. 설정, Bean, Service, Repository와 관리 UI가 모두 있어도 `TcfFacade → STF` 호출이 없으면 운영 효과가 없다. 연결할 때는 Timeout 포함 여부, Thread, Transaction, 정책 DB 장애, ON/OFF 공통 적용과 면제 거래를 함께 결정한다.

ImageLog는 업무 데이터와 다른 일관성 목표를 가진다. 실패 요청도 남겨야 한다면 업무 TX 바깥이 적합하지만 저장 실패를 모니터링해야 한다. 규제상 감사 실패 시 업무를 차단해야 한다면 명시적인 fail-close와 가용성 대책을 설계한다. 현재처럼 예외를 삼키는 동작은 fail-open이라는 사실을 운영자가 알아야 한다.

## 핵심 정리

현행 Interceptor는 Filter 다음, Controller 직전에 Header와 GUID를 보완하고 요청 원문과 Pre ImageLog를 기록한다. 모든 정상 분기에서 true를 반환하며 거래통제를 직접 호출하지 않는다. 시스템 선처리는 Controller가 사용할 공통 상태와 감사 시작점을 만드는 경계이지 업무 Service를 실행하는 계층이 아니다.

거래통제는 STF, `MgTxControlService`와 Repository에 구현돼 있지만 현재 `TcfFacade` 호출선에 STF가 연결되지 않았다. 서비스·사용자·IP·영업점·채널 등의 Rule이 있어도 실제 요청을 차단하지 못한다. 시간대 통제는 현행 SQL에 없다. AS-IS와 목표 기능을 구분해야 한다.

Pre/Post/Exception ImageLog는 업무 Facade 트랜잭션 바깥에서 실행된다. 업무가 Rollback돼도 요청 감사가 남을 수 있고, 업무가 Commit돼도 Post ImageLog는 실패할 수 있다. 같은 HTTP 요청, 같은 Thread처럼 보이는 구간도 Spring Transaction 경계가 아니면 자동으로 묶이지 않는다.

다음 장에서는 이 선처리가 읽고 보완하는 ServiceContext와 GUID를 집중적으로 다룬다. Context가 어느 Thread에 저장되고 계층별로 어떻게 사용되며 Worker Thread로 이동할 때 무엇을 명시적으로 전파하고 정리해야 하는지 살펴본다.
