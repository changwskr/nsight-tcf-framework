# 24장. JWT 인증 전체 구조

PDMG의 JWT 인증은 단순히 로그인 응답에 문자열 하나를 추가하는 기능이 아니다. 사용자의 자격 증명을 확인하는 주체, 토큰에 업무 신원을 담는 주체, 전자서명을 만드는 주체, 업무 요청에서 그 서명을 검증하는 주체가 서로 다른 보안 경계를 이룬다. 이 장은 `pdmg-ui`의 로그인 한 건이 `pdmg-jwt`를 거쳐 Access Token과 Refresh Token으로 바뀌고, 공개키 배포와 폐기 정보가 후속 요청에 어떤 의미를 갖는지 설명한다.

먼저 가장 중요한 현행 판정을 밝혀 둔다. `pdmg-jwt`는 RSA Private Key로 RS256 Access Token을 발급하고 공개키를 JWKS로 노출한다. 그러나 `pdmg-fw`의 `JwtProvider`는 `jwt.secret`으로 HMAC 서명을 검증한다. 따라서 두 구현은 현재 서로 호환되지 않는다. 또한 RSA 키는 외부 키 저장소에서 로딩하지 않고 애플리케이션 기동 때 새로 생성된다. 이 장에서 완성형 JWKS 검증 구조는 TO-BE로, 실제 클래스에서 확인한 동작은 AS-IS로 구분한다.

## 24.1 JWT 인증의 목적

JWT의 목적은 로그인 상태를 서버 세션에 묶어 두는 것이 아니라, 서명된 제한 수명의 증표로 만들어 여러 업무 요청에서 검증할 수 있게 하는 것이다. PDMG Access Token에는 사용자 ID뿐 아니라 영업점, 권한 그룹, 채널 같은 업무 식별 정보가 들어간다. 발급자가 서명하므로 검증자는 토큰이 변조되지 않았는지 확인할 수 있다. 다만 서명이 유효하다는 사실은 그 사용자가 해당 거래를 수행할 권한까지 갖는다는 뜻이 아니다. 인증은 신원을 확인하고, 인가와 거래 통제는 그 신원으로 무엇을 할 수 있는지 결정한다.

Access Token과 Refresh Token의 책임도 다르다. Access Token은 짧게 살아 있으며 업무 API에 제시한다. Refresh Token은 Access Token을 다시 얻기 위한 장기 자격 증명이며 업무 API에 보내지 않는다. 현재 기본 정책은 Access Token 15분, Refresh Token 8시간이다. 이 값은 `JwtSecurityProperties`의 초기값과 `application.yml`에 정의되고, `JwtRuntimePolicy`가 DB 정책 행으로 갱신될 수 있다.

## 24.2 `pdmg-ui` 로그인 화면

AS-IS 로그인 화면은 `/jwt/admin/login.html`이며 `jwt-admin.js`의 `login()`이 `mgjwa1000C0` 거래를 호출한다. TCF가 켜진 현재 JWT 모듈 설정에서는 브라우저가 `pdmg-jwt`의 `/online`으로 표준 전문을 보내고, 전문의 Service ID로 Handler가 선택된다. 로그인 성공 응답은 `pdmg.jwt.session`이라는 키로 브라우저 `sessionStorage`에 저장된다. Access Token, Refresh Token, 토큰 유형과 사용자 정보가 JavaScript가 읽을 수 있는 형태로 함께 보관된다.

이 방식은 개발·관리 UI의 흐름을 확인하기에는 단순하지만 XSS가 발생하면 두 토큰이 함께 노출될 수 있다. 운영 TO-BE에서는 Access Token의 수명을 짧게 유지하고, Refresh Token은 `HttpOnly`, `Secure`, 적절한 `SameSite` 속성을 가진 쿠키로 옮기는 방안을 우선 검토해야 한다. 쿠키 방식은 CSRF 방어와 갱신 API 설계까지 함께 결정해야 하므로 저장 위치 하나만 바꾸는 문제가 아니다.

## 24.3 `pdmg-jwt` 인증 요청

TCF ON 흐름은 다음과 같다.

```text
Browser /jwt/admin/login.html
  → jwt-admin.js: mgjwa1000C0 표준 전문 생성
  → POST pdmg-jwt /online
  → DefaultFilter: GUID·ServiceContext 준비
  → OnlineTransactionController
  → TransactionDispatcher
  → mgjwa1000Handler
  → mgjwa1000Facade
  → mgjwa1000Service.mgjwa1000C0()
```

`mgjwa1000Controller`에도 `/mgjwa1000C0` 직접 경로가 있지만 `nhnis.fw.tcf.enabled=false`일 때만 Bean으로 등록된다. 따라서 운영자가 TCF 설정을 바꾸면 URL과 진입 경로도 함께 확인해야 한다. JWT 모듈의 Spring Security 설정은 모든 요청을 `permitAll()`로 두고 있다. 로그인과 JWKS가 공개되어야 한다는 요구만으로 관리 조회·정책 변경 거래까지 자동으로 보호되는 것은 아니므로, 이것은 별도의 인가 보완 대상이다.

## 24.4 사용자와 비밀번호 검증

`mgjwa1000Service.mgjwa1000C0()`는 입력의 `userId`와 `password` 존재 여부를 먼저 검사한다. DAO가 사용자를 조회하고 `useYn`이 `Y`인지 확인한 뒤, Spring `PasswordEncoder.matches()`로 입력 평문과 저장된 해시를 비교한다. 사용자 없음, 비활성 사용자, 해시 없음, 불일치는 모두 같은 인증 오류 코드 계열로 처리하여 사용자 존재 여부가 쉽게 드러나지 않게 한다.

성공하면 최종 로그인 시간을 갱신하고 성공 이력을 기록한다. 실패하면 예외 코드 메시지로 실패 이력을 남긴 뒤 원래 `BizException`을 다시 던진다. 소스에서 계정 잠금 횟수 증가나 잠금 해제 정책은 확인되지 않았으므로 현행 기능으로 단정해서는 안 된다. 비밀번호 원문은 토큰 Claim, DB 토큰 테이블, 로그 어디에도 남기지 않아야 한다.

## 24.5 Access Token 발급

사용자 검증 뒤 `issueTokenPair()`가 새 `jti`를 만들고 `JwtTokenIssuer.issueAccessToken()`을 호출한다. 발급기는 현재 시각을 `iat`, 정책의 분 단위를 더한 시각을 `exp`로 설정한다. 결과 JWT 원문은 로그인 응답으로 반환되고, 별도의 토큰 관리 행에는 token ID, `jti`, issuer, 사용자·영업점·채널·권한 그룹, 발급·만료 시각과 클라이언트 정보가 저장된다.

이 저장 행이 JWT 자체를 대신 검증하는 것은 아니다. JWT 전자서명은 위조 여부를 판단하고, 관리 테이블은 발급·폐기·감사를 지원한다. 둘 중 하나만 구현하면 만료 전 강제 폐기나 운영 추적 같은 요구를 충족하기 어렵다.

## 24.6 Refresh Token 발급

Refresh Token은 JWT가 아니라 `JwtSupport.newRefreshTokenPlain()`이 만드는 불투명한 난수 문자열이다. 원문은 클라이언트에 한 번 반환하지만 DB에는 SHA-256 해시만 저장한다. 저장 정보에는 사용자, token family, 발급·만료 시각, 클라이언트 정보가 포함된다. DB 유출 시 저장된 해시만으로 Refresh Token을 바로 사용할 수 없게 하는 구조다.

갱신 거래 `mgjwa1000U0`는 입력 원문을 해시하여 행을 찾고, 폐기·회전·만료 상태와 사용자 활성 상태를 차례로 검사한다. 이때 Access Token이 만료되었다고 Refresh Token의 유효성까지 자동으로 끝나는 것은 아니다. 반대로 Refresh Token이 유효해도 비활성 사용자의 새 토큰은 발급하지 않는다.

## 24.7 JWT Header와 Claim

현재 Access Token Header와 Payload의 핵심은 다음과 같다.

| 구역 | 필드 | AS-IS 의미 |
|---|---|---|
| Header | `alg` | RS256 |
| Header | `typ` | JWT |
| Header | `kid` | `nsight-jwt-rs256` 고정 식별자 |
| 표준 Claim | `iss`, `aud` | 발급자와 대상 서비스 |
| 표준 Claim | `sub`, `jti` | 사용자 ID와 토큰 고유 ID |
| 표준 Claim | `iat`, `exp` | 발급·만료 시각 |
| 업무 Claim | `type` | `ACCESS` |
| 업무 Claim | `userId`, `userName` | 사용자 식별·표시 정보 |
| 업무 Claim | `branchId`, `channelId`, `authGroupId` | 영업점·채널·권한 그룹 |

Claim은 Base64URL 인코딩될 뿐 암호화되지 않는다. 따라서 비밀번호, 주민번호, 내부 비밀값을 넣어서는 안 된다. `userName`처럼 업무상 꼭 필요하지 않은 개인정보도 최소화 여부를 검토해야 한다. 검증자는 서명뿐 아니라 `iss`, `aud`, `exp`, `type`을 정책과 비교해야 한다. 현행 HMAC `JwtProvider`는 파싱 과정의 서명·만료와 `type`만 확인하며 issuer와 audience를 명시적으로 제한하지 않는다.

## 24.8 RS256 서명

RS256은 RSA Private Key로 서명하고 대응 Public Key로 검증하는 비대칭 방식이다. `JwtTokenIssuer`는 Nimbus `SignedJWT`를 만들고 `RSASSASigner`에 Private Key를 전달한다. 이 구조의 이점은 업무 서비스에 서명 권한을 배포하지 않아도 된다는 점이다. 검증 서비스가 탈취되어도 공개키만으로 새 정상 토큰을 만들 수 없다.

```text
Claims + Header
  → pdmg-jwt Private Key로 서명
  → Header.Payload.Signature
  → pdmg-service는 Public Key로 검증
  → 원문 변경 또는 다른 키 서명 시 거부
```

알고리즘 설정에는 `RS256` 값이 있지만 발급 코드도 `JWSAlgorithm.RS256`으로 고정되어 있다. DB 정책에서 algorithm 문자열만 바꿔도 실제 서명 알고리즘은 바뀌지 않는다. 정책 화면의 값과 실행 코드가 일치한다고 가정하면 안 되는 이유다.

## 24.9 RSA Private Key

Private Key는 오직 `pdmg-jwt` 발급 경계 안에 있어야 한다. 그러나 AS-IS `JwtKeyConfiguration`은 2048비트 RSAKey를 애플리케이션 기동 때 메모리에서 새로 생성한다. 파일, 환경변수, KMS/HSM 또는 Secret Store에서 로딩하지 않는다. 프로세스가 재시작되면 동일한 `kid` 아래 실제 키가 바뀌므로 재시작 전에 발급한 미만료 Access Token은 새 공개키로 검증할 수 없다. 여러 인스턴스를 동시에 실행하면 인스턴스마다 같은 `kid`에 서로 다른 키를 가질 위험도 있다.

TO-BE에서는 Private Key를 승인된 키 관리 체계에 보관하고, 인스턴스들이 동일한 활성 키를 안전하게 참조해야 한다. 키 회전 시에는 새 `kid`로 발급을 시작하되 기존 토큰이 만료될 때까지 이전 Public Key를 JWKS에 유지하는 중첩 기간이 필요하다. Private Key 원문이나 PEM 내용을 설정 예제, Git, 로그에 남겨서는 안 된다.

## 24.10 JWKS Public Key

`JwkSetController`는 `GET /.well-known/jwks.json`에서 `JWKSet`을 JSON으로 반환한다. Bean은 `jwtSigningKey.toPublicJWK()`로 만들어지므로 공개되는 것은 RSA 공개 파라미터와 `kid`이며 Private Key는 포함되지 않는다. 공개키는 비밀이 아니지만 배포 경로의 무결성과 가용성은 중요하다.

완성형 검증자는 토큰 Header의 `kid`를 읽고 JWKS에서 같은 키를 선택한 뒤 RS256 서명을 확인한다. JWKS는 매 요청마다 원격 조회하기보다 TTL과 키 미발견 시 재조회 정책을 둔 캐시가 필요하다. 그러나 AS-IS `pdmg-service`/`pdmg-fw`에는 JWKS 기반 Decoder가 연결되어 있지 않다. `application.yml`의 `jwk-set-uri`는 발급 모듈 설정일 뿐 현재 업무 서비스 검증기를 자동으로 바꾸지 않는다.

## 24.11 Refresh Token Rotation

Rotation이 활성화되면 갱신에 사용한 기존 Refresh Token을 `rotatedYn` 상태로 바꾸고 같은 family ID로 새 Refresh Token을 저장한다. 이미 사용했거나 폐기된 토큰을 다시 제시하면 `E-JWT-AUTH-0002`로 거부한다. 이로써 단순 재사용은 막는다.

다만 탈취된 이전 토큰의 재사용을 발견했을 때 family 전체를 즉시 폐기하는 로직은 현재 서비스에서 확인되지 않는다. 강한 Rotation TO-BE는 재사용 탐지 시 해당 family의 모든 Refresh Token을 폐기하고 보안 이벤트를 남긴다. 회전 상태 변경과 새 토큰 저장이 하나의 DB 트랜잭션인지도 Facade 경계를 포함해 테스트해야 한다.

## 24.12 로그아웃과 토큰 폐기

로그아웃 거래 `mgjwa1000D1`은 Access Token이 있으면 그 `jti`를 denylist에 넣고, Refresh Token이 있으면 해시로 찾아 폐기 시각을 기록한다. UI는 서버 호출을 시도한 뒤 최종적으로 `sessionStorage`를 지우고 로그인 화면으로 이동한다. 브라우저 저장소 삭제만으로 로그아웃을 끝내면 유출된 토큰은 만료까지 사용할 수 있으므로 서버 폐기가 중요하다.

폐기 거래 `mgjwa1000D0`은 Access Token 원문 또는 `jti`를 받는다. 원문 경로는 JWT를 파싱해 `jti`, `exp`, `sub`를 꺼내지만 `denylistFromAccessToken()` 자체에서 전자서명을 검증하지 않는다. 신뢰되지 않은 호출자가 이 API에 접근할 수 있다면 임의 `jti` 등록과 감사 데이터 오염 가능성을 검토해야 한다. 현재 모든 요청 `permitAll()` 설정과 함께 관리·폐기 API의 인증과 인가를 보완해야 한다.

## 24.13 Denylist

Denylist는 아직 만료되지 않은 Access Token을 강제로 무효화하기 위한 저장소다. `JwtTokenStore.isDenied()`는 정책이 켜져 있을 때 issuer와 `jti`로 DB를 조회한다. 하지만 발급 모듈에 저장·조회 기능이 존재한다는 것과 업무 요청 검증 과정에서 실제로 호출된다는 것은 다르다. AS-IS `pdmg-fw.JwtProvider`는 denylist를 조회하지 않으므로 업무 서비스에서 강제 폐기가 효력을 갖는 연결은 완성되지 않았다.

TO-BE 검증 순서는 서명과 기본 Claim 검증을 먼저 수행하고, 신뢰할 수 있는 `jti`에 대해 denylist를 조회하는 것이다. 조회 장애 때 무조건 허용할지 거부할지는 보안 등급과 가용성 요구에 따라 명시적으로 정해야 한다. 결과를 캐시한다면 폐기 즉시성이 TTL만큼 늦어질 수 있음을 운영 기준에 반영해야 한다.

## 24.14 SSO 연계

SSO 발급 거래 `mgjwa1000C1`은 외부 SSO 토큰을 직접 검증하는 일반 OIDC Callback이 아니다. 내부 호출 Header, 허용 서비스, timestamp, HMAC 서명과 호출 IP를 검증한 뒤 전달받은 사용자 정보를 사용한다. 저장 사용자가 있으면 그 정보를 우선하고, 없으면 issuer 문자열이 지정 접두사로 시작하는 경우 입력 정보를 신뢰 사용자 Map으로 구성한다.

따라서 “SSO 로그인 성공 시 자동으로 PDMG JWT가 생긴다”가 아니라, 신뢰된 내부 연계자가 검증 가능한 요청을 보내고 `pdmg-jwt`가 별도의 PDMG 토큰 쌍을 발급하는 구조다. 외부 IdP의 issuer, audience, nonce, state, 전자서명을 이 서비스가 직접 검증하는 코드는 확인되지 않는다. 그런 OIDC 검증은 상위 SSO 연계 계층의 책임인지 명확히 문서화해야 한다.

## 24.15 내부 호출 공유 비밀키

내부 공유 비밀키는 RS256 Private Key나 `pdmg-fw`의 `jwt.secret`과 전혀 다른 자격 증명이다. `JwtInternalCallValidator`는 요청 본문의 정규화 문자열과 timestamp를 공유 비밀키로 HMAC 검증한다. 허용 서비스 이름, 시간 오차, IP allowlist도 함께 확인한다. 목적은 SSO 연계 발급 API를 호출한 내부 시스템의 신뢰를 확인하는 것이다.

AS-IS 설정에는 개발용 기본 문자열이 직접 들어 있고 Properties 클래스에도 기본값이 있다. 운영에서는 환경변수나 Secret Store로 주입하고 기본값 없이 시작 실패하도록 강화해야 한다. 같은 공유 비밀키를 JWT HMAC 검증이나 다른 서비스 간 통신에 재사용하면 사고 영향 범위가 커진다. 로그에는 비밀키, HMAC 입력 전체, 토큰 원문을 남기지 않는다.

### End-to-End 흐름과 현재 단절점

```text
[정상 발급 AS-IS]
사용자 → pdmg-ui → /online(mgjwa1000C0) → 사용자/BCrypt 검증
      → JwtTokenIssuer → RS256 Private Key 서명 → Access Token
      → 난수 Refresh Token 생성 → 해시만 DB 저장
      → sessionStorage에 토큰 쌍 저장

[의도한 업무 검증 TO-BE]
pdmg-ui → Authorization: Bearer Access Token → pdmg-fw
      → kid 선택 → JWKS Public Key → RS256/iss/aud/exp/type 검증
      → denylist 확인 → 검증된 신원을 업무 처리로 전달

[현재 단절 AS-IS]
RS256 Access Token → pdmg-fw JwtProvider(HMAC jwt.secret) → 알고리즘/키 불일치
```

### 책임과 경계

| 구성요소 | Caller | 핵심 책임 | 호출/의존 대상 | 맡기면 안 되는 책임 |
|---|---|---|---|---|
| `pdmg-ui` | 사용자 | 로그인 입력, 토큰 사용·갱신 | `pdmg-jwt`, 업무 API | 비밀번호 검증, JWT 서명 |
| `mgjwa1000Service` | Handler/Controller | 사용자 검증, 발급·갱신·폐기 조정 | DAO, Issuer, Store | Private Key 공개 |
| `JwtTokenIssuer` | 인증 Service | Claim 구성과 RS256 서명 | RuntimePolicy, Private Key | 사용자 인증 |
| `JwtTokenStore` | 인증 Service | 토큰 메타데이터·해시·denylist | JWT DAO | 공개키 검증 대행 |
| JWKS endpoint | 검증자/UI | Public Key 집합 공개 | Public JWKSet | Private Key 반환 |
| `pdmg-fw` 검증기 | 업무 요청 Filter | 토큰·Claim·폐기 검증 | TO-BE JWKS/denylist | 토큰 발급 |

### 정상과 실패 비교

| 상황 | 정상 흐름 | 실패 시 결과와 확인점 |
|---|---|---|
| 로그인 | 활성 사용자와 비밀번호 일치 후 토큰 쌍 발급 | 동일 계열 인증 오류, 실패 이력 확인 |
| Access 발급 | 정책 Claim 구성 후 RS256 서명 | 키 Bean·서명 예외, 토큰 원문 로그 금지 |
| 갱신 | 해시 일치, 미만료·미폐기 후 Rotation | 재사용·만료·비활성 사용자 거부 |
| JWKS 검증 | `kid`에 맞는 Public Key로 검증 | 키 미발견 시 제한적 재조회 후 거부 |
| 로그아웃 | Access denylist와 Refresh 폐기 | 부분 실패 시 서버 상태와 UI 삭제를 분리 점검 |
| 재기동 | TO-BE 지속 키로 기존 토큰 유지 | AS-IS 새 키 생성으로 기존 Access Token 무효화 |

### Anti Pattern

- Private Key를 `pdmg-service`나 브라우저에 배포한다. 검증자가 곧 발급자가 되어 침해 범위가 전체로 확대된다.
- JWKS JSON에 개인키 파라미터가 포함되어도 된다고 생각한다. 공개 endpoint에는 Public JWK만 있어야 한다.
- Access Token과 Refresh Token을 같은 저장소·수명·API에 사용한다. 장기 자격 증명이 업무 요청마다 노출된다.
- `kid`는 유지한 채 인스턴스별 키를 생성한다. 검증 결과가 요청이 도착한 인스턴스에 따라 달라진다.
- JWT Payload를 디코딩한 결과만 보고 로그인 상태로 인정한다. 디코딩은 서명 검증이 아니다.
- HMAC `jwt.secret`과 내부 호출 공유 비밀키를 하나로 합친다. 목적별 키 분리와 회전이 불가능해진다.
- 토큰 원문이나 비밀번호를 장애 로그에 출력한다. 로그 저장소가 곧 자격 증명 유출 경로가 된다.

### 개발자·운영자 체크리스트

- [ ] 로그인 Service ID와 TCF ON/OFF 진입 URL이 배포 설정과 일치하는가?
- [ ] 비밀번호는 `PasswordEncoder.matches()`로 검증하고 평문을 저장·로그하지 않는가?
- [ ] Access Token의 `iss`, `aud`, `exp`, `type`, `kid` 정책이 발급·검증 양쪽에서 같은가?
- [ ] Private Key는 승인된 저장소에서 로딩하며 여러 인스턴스가 일관된 키를 쓰는가?
- [ ] JWKS에는 Public Key만 있고 회전 중 이전 키 유지 기간이 정의되어 있는가?
- [ ] Refresh Token은 DB에 원문이 아닌 해시로 저장되는가?
- [ ] Rotation 재사용 탐지와 token family 폐기 정책이 테스트되었는가?
- [ ] 로그아웃 후 Access denylist와 Refresh 폐기가 모두 반영되는가?
- [ ] 업무 검증 경로가 실제로 JWKS와 denylist를 사용하는가?
- [ ] 운영 설정에 개발용 비밀 기본값이 남아 있지 않은가?
- [ ] 브라우저 저장 방식에 대한 XSS·CSRF 위협 모델이 합의되었는가?
- [ ] 인증 API와 JWT 관리 API에 별도 인가 정책이 적용되는가?

### 아키텍처 판단 포인트와 다음 장

키 관리 방식은 단일 프로세스 편의가 아니라 재기동, 다중 인스턴스, 무중단 회전, 사고 시 폐기 요구로 결정한다. 토큰 저장 방식은 UI 구현 편의보다 XSS·CSRF 위험과 갱신 UX를 함께 본다. denylist의 동기 조회 여부는 즉시 폐기 보안성과 DB·네트워크 장애 시 가용성 사이의 선택이다. 무엇을 선택하든 발급 정책과 검증 정책이 동일한 계약을 사용해야 한다.

현재 가장 먼저 해결할 경계는 RS256 발급과 HMAC 검증의 불일치다. 다음 장에서는 업무 요청의 `Authorization` Header를 `DefaultFilter`가 어디서 읽는지, 현행 `JwtProvider`가 실제로 무엇을 검증하고 무엇을 놓치는지, 검증된 사용자 정보가 Context로 어떻게 이어져야 하는지를 코드 실행 순서로 좁혀 살펴본다.
