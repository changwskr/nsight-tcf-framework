# 제5부 데이터 접근과 대용량 처리

# 19장. DAO와 MyBatis Mapper

Service가 업무 순서를 결정한 뒤 데이터베이스에 도달하려면 Java 메서드와 SQL 문장을 정확히 연결해야 한다. PDMG는 DAO 인터페이스와 MyBatis Mapper XML을 이 경계로 사용한다. 구현 클래스를 직접 작성하지 않고 MyBatis가 DAO Proxy를 생성하며, 호출된 인터페이스의 전체 이름과 메서드 이름으로 XML Statement를 찾는다.

이 구조의 장점은 업무 코드와 SQL을 분리하는 데 있다. 그러나 namespace 한 글자, Statement ID 하나 또는 Map 키 하나가 어긋나면 컴파일이 성공해도 실행 시 실패한다. 이 장은 등록, 연결, 바인딩, 결과 반환과 예외 전파를 한 SQL의 흐름으로 추적한다.

## 이 장에서 해결할 질문

- `@RDWMapper` 인터페이스는 어떻게 실제 Spring Bean이 되는가?
- DAO FQCN, XML namespace, DAO 메서드와 Statement ID는 어떻게 연결되는가?
- Java 패키지 Scan과 XML resource loading은 왜 별개의 축인가?
- `#{}`와 `${}`는 실행 SQL과 보안에서 무엇이 다른가?
- SELECT와 CUD 반환값을 Service가 어떻게 해석해야 하는가?
- DB 예외를 DAO에서 숨기면 Transaction에 어떤 문제가 생기는가?

## 전체 Persistence 흐름

```text
Business Service
   │ Map parameter
   ▼
DAO Interface Proxy
   │ FQCN + method
   ▼
Mapper XML
   │ namespace + statement id
   ▼
SqlSessionTemplate
   ▼
RDW DataSource / JDBC Connection
   ▼
PreparedStatement → DB
   ▼
List<Map> 또는 처리 건수
   ▼
Service → DTOout
```

## 19.1 Persistence 계층의 책임

Persistence 계층은 업무 데이터 접근 계약을 SQL 실행으로 바꾼다. DAO는 Java 시그니처를 제공하고 Mapper XML은 SQL, 동적 조건, 파라미터 바인딩과 결과 타입을 정의한다. Service는 필요한 조건 Map을 완성해 DAO를 호출하고 반환된 행·건수를 업무 결과로 해석한다.

DAO가 하지 않는 일도 중요하다. 필수값·업무 상태 검증, 페이지 기본값, Service ID 라우팅, DTOout 조립과 Transaction 시작은 DAO 책임이 아니다. 이 경계를 지키면 SQL 변경과 업무 정책 변경을 별도로 검토할 수 있다.

현행 DAO에는 일반적으로 `@Transactional`이 없다. 같은 RDW DataSource를 사용하는 상위 Facade 또는 Worker Transaction에 참여한다. DAO가 거래를 소유하는 것이 아니라 현재 Thread에 결합된 Connection을 SqlSessionTemplate이 사용한다.

## 19.2 DAO Interface

DAO는 `nhnis.mg.co.a.persistence.dao` 아래의 Java 인터페이스다. 현재 `mgcoa5530DAO`, `mgcoa8888DAO`, `mgcoa9000DAO`, `mgcoa9001DAO`, `mgcoa9999DAO` 다섯 개가 확인된다. 과거 분석 문서의 “네 개” 목록에는 이후 추가된 `mgcoa9001DAO`가 빠져 있으므로 실제 소스를 기준으로 현행화해야 한다.

메서드는 주로 `Map<String,Object>`를 받고, 목록 SELECT는 `List<Map<String,Object>>`, count·exists·INSERT·UPDATE·DELETE는 `int`를 반환한다. 별도의 `DAOImpl`은 없다. Spring/MyBatis가 런타임 Proxy를 생성한다.

한 프로그램에 DAO 하나를 두고 S0·C0·U0·D0 Statement를 메서드로 추가하는 패턴이다. DAO 이름에 거래 구분자를 넣어 인터페이스를 거래마다 쪼개지 않는다.

## 19.3 `@RDWMapper`

DAO에는 사용자 정의 `@RDWMapper`가 붙는다. 이 Annotation은 런타임 TYPE 대상이며 MyBatis `@Mapper`를 메타 Annotation으로 포함한다.

```java
@RDWMapper
public interface mgcoa9000DAO {
    int mgcoa9000C0_C0(Map<String, Object> input) throws Exception;
}
```

`@Inherited`도 선언되어 있지만 Java의 Annotation 상속은 클래스 상속에 관한 것이므로 인터페이스 Mapper 등록의 핵심은 아니다. 중요한 것은 Mapper Scan 범위 안에 인터페이스가 있고 MyBatis Mapper로 인식된다는 점이다.

## 19.4 Mapper Scan

`RdwDataSourceConfig`에는 다음 Scan이 있다.

```java
@MapperScan(
    basePackages = "nhnis.mg.co.a.persistence.dao",
    sqlSessionTemplateRef = "rdwSqlSessionTemplate"
)
```

애플리케이션 기동 시 이 패키지의 DAO 인터페이스를 찾아 Proxy Bean을 만들고 RDW SqlSessionTemplate에 연결한다. Service가 주입받는 것은 구현 클래스가 아니라 이 Proxy다.

Scan은 Java 인터페이스 발견과 Proxy 생성을 담당한다. Mapper XML을 디렉터리에서 읽는 기능과 혼동해서는 안 된다. Java DAO가 Scan되어도 XML이 로드되지 않으면 Statement not found로 실패할 수 있다.

## 19.5 Mapper XML 경로

같은 Configuration은 `classpath*:rdw.*/*.xml` 패턴으로 Mapper resource를 로드한다. 실제 파일은 `src/main/resources/rdw.mg.co.a/` 아래의 `mgcoa5530-ORA.xml`, `mgcoa8888-ORA.xml`, `mgcoa9000-ORA.xml`, `mgcoa9001-ORA.xml`, `mgcoa9999-ORA.xml`이다.

폴더명 `rdw.mg.co.a`는 운영 규약과 탐색 패턴에 맞지만 MyBatis가 폴더명만으로 Java 인터페이스와 연결하는 것은 아니다. 최종 논리 연결은 XML namespace와 statement id가 담당한다.

새 XML이 패턴 밖에 있으면 빌드 산출물에 포함되어도 Factory가 읽지 못할 수 있다. 기동 테스트에서 `SqlSessionFactory`의 mapped statement 목록을 확인하는 자동 검증이 유용하다.

## 19.6 DAO FQCN과 Namespace

XML의 `<mapper namespace>`는 DAO의 Fully Qualified Class Name과 완전히 같아야 한다.

```text
DAO FQCN
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
                     ║ 일치
Mapper namespace
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
```

패키지를 옮기고 namespace를 수정하지 않으면 Proxy가 찾는 Statement key와 XML 등록 key가 달라진다. 대소문자까지 계약 일부다. 리팩터링은 Java import만 자동 수정된다고 끝나지 않는다.

AS-IS 다섯 Mapper XML의 namespace는 대응 DAO FQCN과 일치한다. 이 사실은 정적 검색으로 확인했지만 DB 연결 성공까지 의미하지는 않는다.

## 19.7 DAO 메서드와 Statement ID

DAO 메서드명은 같은 namespace의 XML `id`와 일치해야 한다. MyBatis가 만드는 최종 key는 `namespace.id`다.

```text
mgcoa9000DAO.mgcoa9000S0_S0(param)
  → nhnis.mg.co.a.persistence.dao.mgcoa9000DAO.mgcoa9000S0_S0
  → <select id="mgcoa9000S0_S0">
```

현행 관례는 `{ServiceId}_{DML구분}{순번}`이며 count·exists는 suffix를 붙인다. 실제 등록은 `mgcoa9000C0_C0`, 수정은 `mgcoa9000U0_U0`, 삭제는 `mgcoa9000D0_D0`다. 문서 예시의 INSERT `I0`와 실제 `C0_C0`가 다를 수 있으므로 생성 코드는 현행 인터페이스와 XML을 기준으로 해야 한다.

## 19.8 SELECT

목록 조회는 동적 WHERE, 정렬과 페이징을 XML에서 실행하고 `List<Map>`을 반환한다. 같은 조건의 count Statement가 전체 건수를 반환하는 사례가 많다. `mgcoa9000Where` 같은 `<sql>` 조각을 count와 목록이 함께 include해 조건 불일치를 줄인다.

SELECT 컬럼은 대문자 alias 또는 quoted camelCase alias를 사용한다. Service는 Map 키를 Sub DTO로 옮긴다. 컬럼 추가·alias 변경은 Service 매핑과 테스트까지 영향을 준다.

count와 list가 같은 Transaction·격리 수준에 있어도 두 문장 사이 동시 변경은 정책에 따라 보일 수 있다. 대용량 페이징의 SQL 구조와 성능은 다음 장에서 상세히 다룬다.

## 19.9 INSERT

INSERT Statement는 Map의 필드를 `#{}`로 VALUES에 바인딩하고 영향받은 행 수를 반환한다. `mgcoa9000C0_C0`와 `mgcoa9001C0_C0`가 실제 사례다.

Service는 중복 사전 조회만 믿지 않는다. 동시 요청은 조회 뒤 INSERT 사이에 들어올 수 있으므로 DB 유일 제약과 예외 처리가 최종 방어선이다. 처리 건수 1을 기대하는 등록에서 0이 반환되면 정상 성공으로 간주할지 계약을 정한다.

## 19.10 UPDATE

UPDATE는 식별 조건과 변경 필드를 분리한다. `mgcoa9000U0_U0`는 `TX_ID`를 WHERE에 두고 이름·앱·URL·HTTP 메서드와 변경 감사값을 SET한다. 반환 `int`가 0이면 대상 없음 또는 조건 불일치, 2 이상이면 WHERE 범위를 의심해야 한다.

Service가 처리 건수를 확인하지 않으면 “성공 응답이지만 아무 것도 바뀌지 않음”이 생긴다. 낙관적 잠금을 추가한다면 version을 WHERE에 넣고 0건을 충돌로 해석한다. 이는 현행 공통 구현이 아니라 TO-BE 선택이다.

## 19.11 DELETE

단건 삭제는 식별키를 바인딩하고, 다건 삭제는 `<foreach>`로 IN 목록을 만든다. `mgcoa8888D0_D0`는 GUID 목록, `mgcoa9000D0_D0`는 txId 목록을 사용한다. 각 item도 `#{}`로 바인딩된다.

빈 목록은 Service에서 차단해야 잘못된 SQL을 피한다. 현행 코드에는 다건 목록 상한이 명시적으로 보이지 않으므로 Oracle IN 항목 제한과 SQL 크기를 고려한 분할·상한 정책이 필요하다. 실제 정책은 DB 버전과 요구사항으로 검증한다.

물리 삭제 대신 논리 삭제가 필요한지는 감사·복구 요구가 결정한다. DAO가 임의로 판단하지 않고 Service 정책과 Mapper가 일치해야 한다.

## 19.12 MyBatis 파라미터 바인딩

`#{value}`는 PreparedStatement의 `?` 파라미터로 변환되고 JDBC Type Handler가 값을 설정한다. 문자열 값이 SQL 구조로 해석되지 않으므로 입력값 바인딩의 기본 방식이다.

```xml
WHERE T1.TX_ID = #{txId}
```

Map 키가 없거나 이름이 다르면 null 바인딩 또는 동적 조건 누락이 생길 수 있다. `RdwDataSourceConfig`는 `jdbcTypeForNull`을 `NULL`로, `callSettersOnNulls`를 true로 설정한다. 하지만 이 설정이 잘못된 Map 키를 찾아 주지는 않는다.

`<if test>`와 `#{}`는 같은 키를 사용해야 한다. Service의 `param.put("txId", ...)`, XML의 `test="txId..."`, `#{txId}` 세 지점을 함께 검증한다.

## 19.13 `${}` 사용 시 위험

`${value}`는 값을 SQL 문자열에 그대로 치환한다. 사용자 입력을 넣으면 따옴표 탈출, 조건 추가와 SQL Injection이 가능하다. 값 바인딩 용도로 권장해서는 안 된다.

동적 ORDER BY 컬럼처럼 SQL 식별자를 바꿔야 할 때 `#{}`를 사용할 수 없다는 이유로 `${}`가 필요할 수 있다. 이 경우 클라이언트 문자열을 직접 넣지 않고 서버가 관리하는 allowlist에서 실제 컬럼 토큰으로 변환한다.

현행 업무 Mapper XML 검색에서는 `${}` SQL 치환이 발견되지 않았고 값은 `#{}`로 바인딩된다. log4j2의 `${...}` 속성 문법은 MyBatis SQL 치환과 무관하므로 검색 결과를 구분해야 한다.

## 19.14 Result Mapping

현행 XML은 주로 `resultType="java.util.HashMap"`을 사용하고 SELECT alias를 Map 키로 반환한다. Service가 대문자와 camelCase 키를 읽어 DTO를 조립한다. `mgcoa9001`은 quoted camelCase alias를 사용하고 다른 Mapper는 대문자 alias를 사용한다.

Map 방식은 유연하지만 타입 안전성이 낮다. 명시적 `resultMap`이나 typed result model은 컴파일과 테스트 가시성을 높일 수 있다. 다만 외부 DTO를 Mapper resultType으로 직접 결합하면 Persistence와 API 계약이 강하게 묶일 수 있어 별도 row model을 검토한다.

null setter 호출 설정은 결과 객체 매핑에 영향을 줄 수 있지만 Map 키·alias 계약은 실제 DB와 통합 테스트로 확인해야 한다.

## 19.15 DB 예외 전파

SQL 문법, 제약 위반, 타입 변환, 연결 실패와 Lock timeout은 MyBatis·Spring 예외로 호출자에게 전파된다. DAO가 예외를 catch해 0이나 빈 목록으로 바꾸면 Service는 “데이터 없음”과 “DB 장애”를 구분하지 못하고 상위 Transaction이 커밋할 수 있다.

```text
DB/JDBC 실패
  → MyBatis Proxy
  → DAO 호출 예외
  → Service 중단
  → Facade/Worker Transaction ROLLBACK
  → 공통 오류 응답
```

원인 SQL과 바인딩 값 전체를 클라이언트에 노출하지 않는다. SQL 로그도 개인정보·Token을 마스킹해야 한다. Timeout 응답 시 Worker SQL이 즉시 중단됐다고 단정하지 않으며 최종 Rollback 로그와 DB 상태를 확인한다.

## 19.16 DAO에서 금지하는 처리

DAO default 메서드에 업무 if, 결과 코드 조립, 여러 외부 호출을 넣지 않는다. Handler·Controller·Facade가 DAO를 직접 부르면 Service 검증과 결과 해석이 우회된다. DAO에 `@Transactional`을 붙여 SQL마다 독립 경계를 만들면 유스케이스의 여러 변경이 분리될 수 있다.

예외를 숨기거나 SQL 문자열을 Java에서 사용자 입력으로 조립하지 않는다. 페이지 기본값과 최대 크기, 삭제 가능 여부, 0건 처리 의미는 Service·Rule 책임이다. DAO는 데이터 접근 계약을 명확히 유지한다.

## End-to-End 사례: `mgcoa9000U0`

```text
Service
  └─ Map(txId, txName, appId, pathUrl, httpMethod, chgUserId, chgDtm)
      → mgcoa9000DAO Proxy.mgcoa9000U0_U0
      → namespace = ...mgcoa9000DAO
      → id = mgcoa9000U0_U0
      → #{...} PreparedStatement binding
      → TB_MG_TX_PARAM UPDATE
      → 영향 행 수 int
      → Service 결과 DTO
      → 정상 COMMIT / 예외 ROLLBACK
```

## 책임과 경계

| 구성 요소 | 책임 | Caller/Callee | 금지 책임 |
|---|---|---|---|
| Service | 파라미터 구성·결과 해석 | Facade/DAO | SQL 세부 문자열 |
| DAO Interface | Java 데이터 접근 계약 | Service/MyBatis Proxy | 업무 정책·TX 시작 |
| Mapper XML | SQL·동적 조건·바인딩 | Proxy/DB | HTTP·DTOout 조립 |
| SqlSessionTemplate | Session·TX Connection 연계 | Proxy/Factory | 업무 성공 판정 |
| TransactionManager | RDW Connection TX | 상위 경계/DataSource | SQL ID 라우팅 |

## 정상과 실패 비교

정상 경로는 Proxy가 정확한 mapped statement를 찾고 모든 값을 바인딩해 목록 또는 처리 건수를 반환한다. Service가 건수를 업무 결과로 해석하고 상위 경계가 커밋한다.

namespace/id 불일치는 SQL 실행 전에 Binding 오류가 난다. Map 키 불일치는 조건 누락이나 null 바인딩, SQL 오류는 실행 단계 예외가 된다. 어느 경우든 예외를 숨기지 않아야 Rollback과 표준 오류가 유지된다.

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | 5개 `@RDWMapper` DAO와 대응 ORA XML 존재 |
| AS-IS | `@MapperScan`은 persistence.dao, XML pattern은 `classpath*:rdw.*/*.xml` |
| AS-IS | namespace=DAO FQCN, method=statement id가 대응 |
| AS-IS | Map 입력·List&lt;Map&gt;/int 출력, `#{}` 바인딩 |
| 제약 | DAO/XML 계약 자동 검증 테스트와 SQL별 timeout이 명확하지 않음 |
| 제약 | 다건 IN 목록 상한이 보이지 않음 |
| TO-BE | mapped statement 정합성·DB 통합 테스트, typed row model 검토 |

## Anti Pattern

`DAOImpl`을 임의로 만들고 Mapper Proxy와 중복 등록하거나, Java package 이동 뒤 namespace를 방치하는 패턴이 대표적이다. `${}`에 정렬·검색 입력을 직접 넣는 것은 Injection 경로가 된다. DAO에서 예외를 0으로 바꾸거나 업무 결과 코드를 만들면 장애와 무데이터가 섞인다.

DTO를 Mapper에 직접 넘기는 것이 항상 잘못은 아니지만 현행 Map 계약과 혼용하면 XML 키와 Service 변환 책임이 불명확해진다. 변경은 프로그램 단위로 일관되게 수행한다.

## 실전 검증과 체크리스트

기동 테스트에서 DAO Bean 생성, XML resource 로딩, namespace·id 전체 목록을 확인한다. 각 Statement는 최소 정상, 0건, null 조건, 제약 위반과 Rollback을 DB 통합 테스트로 검증한다. 다건 삭제는 빈 목록, 중복, 허용 최대, 초과를 검사한다.

- DAO가 Scan 패키지 안에 있고 `@RDWMapper`인가?
- XML이 mapper location pattern에 포함되는가?
- namespace가 DAO FQCN과 대소문자까지 같은가?
- 모든 DAO 메서드에 같은 id의 Statement가 있는가?
- Service Map 키, `<if test>`, `#{}` 이름이 일치하는가?
- 사용자 값은 모두 `#{}`로 바인딩하는가?
- `${}`가 있다면 서버 allowlist를 거치는가?
- CUD 처리 건수 0·1·복수 의미를 Service가 검사하는가?
- DB 예외를 빈 목록·0으로 숨기지 않는가?
- 동일 RDW DataSource와 TransactionManager에 참여하는가?
- SQL 로그에 민감정보가 노출되지 않는가?

## 아키텍처 판단 포인트와 다음 장

DAO의 추상화 수준은 SQL 계약을 숨기지 않으면서 Service가 DB 세부사항에 묶이지 않도록 정한다. Map은 유연하지만 규모가 커지면 typed parameter/result로 계약을 강화할 수 있다. 어떤 방식을 택하든 namespace·id·필드 이름을 자동 검증해야 한다.

동적 SQL은 값 바인딩과 구조 치환을 구분한다. 값은 `#{}`, 구조는 가능하면 XML 분기와 allowlist로 제한한다. Transaction은 Statement가 아니라 유스케이스 성공 조건에 맞춰 상위에서 관리한다.

다음 장에서는 현재 Mapper의 ROWNUM 기반 목록 SQL과 count/list 계약을 토대로, 대용량 조회에서 페이지 크기 제한, 정렬 안정성, 인덱스와 Timeout을 어떻게 설계하는지 살펴본다.
