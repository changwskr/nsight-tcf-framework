# 제3부 온라인 요청과 TCF 프레임워크

# 9장. Filter와 Spring MVC

8장에서는 클라이언트가 보내는 HTTP 요청과 `hdr_nhnis`, `dto`로 구성된 표준 전문을 살펴보았다. 하지만 네트워크로 전달된 JSON은 그 자체로 Controller의 Java DTO가 되지 않는다. Servlet Container가 요청을 받아 Filter Chain을 실행하고, PDMG의 `DefaultFilter`가 Body와 요청 Context를 준비한 뒤에야 Spring MVC가 URL에 맞는 Handler를 선택하고 메서드 인자를 만든다.

이 장은 그 경계를 한 건의 요청이 이동하는 순서로 설명한다. 핵심은 Filter와 Spring MVC가 모두 “전처리”를 한다는 피상적인 공통점이 아니라, 서로 다른 시점과 객체를 책임진다는 사실이다. Filter는 Controller가 무엇인지 아직 모르는 Servlet 경계에서 요청을 재사용 가능한 형태로 만들고 인증·추적 Context의 수명을 연다. Spring MVC는 그 준비된 요청을 특정 Controller와 Java 인자에 연결하고 반환값을 HTTP 응답으로 바꾼다.

## 이 장에서 해결할 질문

- Servlet Filter는 Spring MVC의 어디에서 실행되며 어떤 정보까지 알 수 있는가?
- Filter가 JSON Body를 읽고도 Controller가 같은 Body를 다시 읽을 수 있는 이유는 무엇인가?
- JWT, GUID, ServiceContext와 MDC는 어느 시점에 생성되고 누가 정리하는가?
- TCF ON 공통 Controller와 TCF OFF 업무 Controller의 인자 변환은 어떻게 다른가?
- ResponseBodyAdvice는 왜 Interceptor의 `postHandle`을 대신하지 않는가?
- Filter와 Interceptor를 하나로 합치면 어떤 정상·실패 경로가 깨지는가?
- Filter를 끄면 로그 기능만 사라지는가, 요청 실행 계약 전체가 달라지는가?

## 전체 실행 지도

```text
HTTP Request
    │
    ▼
Servlet Container
    │
    ▼
DefaultFilter                                      Servlet 경계
    ├─ OPTIONS 제외
    ├─ Request Body 캐시(JSON)
    ├─ JWT 검사(비-local JSON)
    ├─ hdr_nhnis 파싱·local 합성
    ├─ GUID/Service ID/IP/User를 MDC에 설정
    └─ ServiceContextHolder.setInstance
    │
    ▼ filterChain.doFilter(cachedRequest, response)
DispatcherServlet                                  Spring MVC 경계
    │
    ├─ HandlerMapping
    ├─ ServicePreventionInterceptor.preHandle
    ├─ HandlerAdapter
    ├─ ArgumentResolver / MessageConverter
    ▼
Controller
    │
    ▼
TCF 또는 업무 실행
    │
    ▼
Controller 반환
    │
    ├─ ResponseBodyAdvice
    ├─ HttpMessageConverter
    └─ Interceptor.afterCompletion
    │
    ▼
DefaultFilter finally
    ├─ ServiceContextHolder.removeInstance
    └─ ThreadContext.clearAll
```

이 그림에서 가장 중요한 경계는 `filterChain.doFilter()`다. 호출 전에는 PDMG가 Servlet 요청을 준비한다. 호출 안쪽에서는 Spring MVC가 Controller를 선택하고 업무를 실행한다. 호출이 정상 반환되든 예외로 빠져나오든 Filter의 `finally`가 요청 Thread의 Context를 닫는다.

## 9.1 Servlet Filter의 위치

Servlet Filter는 Spring MVC의 `DispatcherServlet`보다 앞에 있다. Spring MVC Controller도 Servlet Container 관점에서는 DispatcherServlet 하나 뒤에 배치된 Handler다. 그러므로 Filter가 실행될 때는 HTTP method, URI, Header, Content-Type과 InputStream은 볼 수 있지만 최종 Controller 메서드와 그 Annotation, 변환된 업무 DTO는 아직 알 수 없다.

이 위치는 Filter의 적합한 책임을 결정한다. 원시 Body를 Wrapper로 교체하거나 인증되지 않은 요청을 MVC 진입 전에 거절하고, 요청 전체에서 사용할 ThreadLocal Context를 여는 작업은 Filter에 적합하다. 반대로 Service ID별 업무 검증, DAO 호출, 선택된 Controller Annotation 기반 통제는 부적합하다.

```text
Servlet 영역                           Spring MVC 영역

Container
  → Filter Chain
      → DefaultFilter
          → DispatcherServlet
              → HandlerMapping
                  → Interceptor
                      → Controller
```

현행 `DefaultFilter`는 `OncePerRequestFilter`를 상속한다. 이 기반 클래스는 하나의 요청 Dispatch에서 Filter가 불필요하게 중복 실행되는 것을 막는 데 도움을 준다. 별도의 `FilterRegistrationBean`은 DispatcherType을 `REQUEST`로 제한하므로 FORWARD나 ERROR Dispatch에 같은 PDMG 초기화를 반복하지 않는다.

Filter는 업무 트랜잭션보다 바깥에 있다. 이곳에서 데이터베이스 트랜잭션을 시작하면 인증 실패와 Body 파싱 실패까지 DB Connection을 점유하고, Controller 이후의 응답 변환·ImageLog까지 업무 트랜잭션에 섞일 수 있다. PDMG에서 Filter는 실행 환경을 준비할 뿐 업무 COMMIT/ROLLBACK을 소유하지 않는다.

### Filter에서 사용할 수 있는 정보

| 정보 | Filter 진입 시 | MVC Handler 선택 후 |
|---|---:|---:|
| HTTP method, URI, Header | 가능 | 가능 |
| 원시 InputStream | 가능 | 이미 소비됐을 수 있음 |
| 최종 Controller 메서드 | 알 수 없음 | 가능 |
| 메서드 Annotation | 알 수 없음 | 가능 |
| 변환된 업무 DTO | 없음 | ArgumentResolver 이후 가능 |
| 업무 실행 결과 | 없음 | Controller 반환 이후 가능 |

이 차이가 Filter와 Interceptor를 분리하는 첫 번째 근거다.

## 9.2 DefaultFilter 생성 조건

`DefaultFilter`는 `pdmg-fw`의 `nhnis.fw.commons.filter.DefaultFilter`다. 클래스와 등록 Configuration 모두 다음 조건을 가진다.

```java
@ConditionalOnProperty(
    name = "nhnis.fw.commons.filter.enabled",
    havingValue = "true"
)
```

`pdmg-service`의 현재 설정은 이 값을 `true`로 둔다.

```yaml
nhnis:
  fw:
    commons:
      filter:
        enabled: true
```

조건을 만족하면 `DefaultFilter` Bean과 `FilterConfiguration`이 생성된다. 등록 정보는 다음과 같다.

| 항목 | AS-IS 값 |
|---|---|
| Filter 이름 | `pdmgDefaultFilter` |
| URL pattern | `/*` |
| DispatcherType | `REQUEST` |
| 순서 | `Ordered.HIGHEST_PRECEDENCE + 20` |
| OPTIONS | `shouldNotFilter()`에서 제외 |

Filter 설정과 `nhnis.fw.tcf.enabled`는 독립적이다. TCF를 OFF로 바꾸더라도 Filter가 자동으로 꺼지지 않는다. 이것이 올바른 분리다. TCF ON은 공통 Controller·Dispatcher·Handler 경로를 선택하는 설정이고, Filter는 ON/OFF 양쪽 요청에 공통 HTTP 준비를 제공한다.

`legacy-web.enabled`도 다른 축이다. 이 값은 `WebConfiguration`, Interceptor 등록, 커스텀 ArgumentResolver와 ResponseBodyAdvice 같은 MVC 구성을 제어한다. 세 설정을 하나의 “프레임워크 ON/OFF”로 이해하면 장애 원인을 잘못 찾게 된다.

```text
commons.filter.enabled  → DefaultFilter와 Servlet 등록
commons.legacy-web.enabled → Interceptor/Resolver/Advice 중심 MVC 구성
tcf.enabled             → Online Controller/Dispatcher/Handler 경로
```

Filter의 URL pattern은 `/*`이므로 OPTIONS를 제외한 모든 일반 요청이 대상이 된다. 현행 JSON 분기는 빈 Body를 400으로 거절한다. 따라서 Health Check, favicon, 정적 리소스나 Body 없는 GET이 같은 애플리케이션에 들어오면 온라인 거래가 아닌데도 막힐 수 있다. AS-IS의 적용 범위를 운영 Endpoint까지 확장할지, 온라인 거래 경로만 포함하거나 명시적 제외 목록을 둘지는 별도 설계 판단이다.

### 생성·등록 장애 진단

Filter 시작 로그가 없다면 업무 Controller부터 디버깅하지 않는다. 활성 Profile에서 설정 키가 실제로 `true`인지, Component Scan이 `nhnis.fw`를 포함하는지, `FilterRegistrationBean`이 생성되었는지, 요청 URL이 현재 Web Application으로 들어왔는지 확인한다. 반대로 Filter 로그가 두 번 보인다면 Component 자동 등록과 RegistrationBean 중복 여부를 조사한다.

## 9.3 Request Body 캐싱

Servlet 요청 Body는 파일처럼 필요할 때마다 처음부터 읽는 객체가 아니다. 기본 `ServletInputStream`은 한 번 소비하면 다시 읽을 수 없다. PDMG Filter는 `hdr_nhnis`를 파싱하기 위해 MVC보다 먼저 Body를 읽어야 한다. 원 요청을 그대로 넘기면 뒤의 ArgumentResolver나 MessageConverter가 빈 Stream을 읽게 된다.

```text
캐싱하지 않은 경우

DefaultFilter ── read InputStream ──▶ EOF
DispatcherServlet / Resolver ───────▶ 읽을 데이터 없음
Controller DTO ─────────────────────▶ null·빈 값·파싱 실패

캐싱한 경우

원 요청 ──▶ CachedBodyHttpServletRequest(byte[])
              ├─ Filter getReader()      새 Stream #1
              ├─ Interceptor/Attribute   원문 참조
              └─ Resolver getReader()    새 Stream #2
```

현행 `CachedBodyHttpServletRequest` 생성자는 `request.getInputStream().readAllBytes()`로 Body 전체를 `byte[]`에 보관한다. `getInputStream()`을 호출할 때마다 그 배열을 읽는 새 `ByteArrayInputStream`을 만들고, `getReader()`는 UTF-8 Reader로 감싼다. Filter는 반드시 원 요청이 아니라 이 Wrapper를 `filterChain.doFilter(wrapper, response)`로 전달한다.

Filter는 캐시된 Body를 문자열로 읽어 Jackson으로 전체 JSON을 Map으로 파싱한다. 원문은 `PDMG_REQUEST_BODY` request attribute와 `ServiceContext.requestBody`에도 저장된다. Wrapper는 MVC의 재읽기를, 문자열 원문은 시스템 선처리 로그와 ImageLog의 입력을 제공한다. 같은 정보를 목적에 맞게 다른 위치에 보관하는 것이다.

### 메모리와 성능

현행 구현은 Body 크기 제한 없이 전체를 메모리에 올리고, `byte[]`, String, Jackson Tree/Map 등 여러 표현을 만들 수 있다. 작은 온라인 JSON에는 단순하고 효과적이지만 큰 목록이나 대용량 전문에서는 요청 수만큼 메모리 사용이 늘어난다. 예를 들어 10MB Body가 동시에 100건 들어오면 캐시 배열만으로도 약 1GB가 필요하고 문자열·객체 비용이 추가된다.

따라서 신규 대용량 API는 Servlet 또는 Gateway 요청 크기 제한, 허용 전문 크기, 전문 로그 절단·마스킹 정책을 함께 정해야 한다. 파일 업로드를 일반 JSON 캐시 경로로 보내지 않는 것도 같은 이유다. 현행 Filter는 Content-Type이 `multipart/`로 시작하면 Wrapper를 만들지 않고 별도 분기로 전달한다.

### 실패 흐름

Body가 비면 Filter는 400을 보내고 MVC에 진입하지 않는다. JSON 문법이 잘못돼도 400으로 종료한다. 이 오류는 `@ControllerAdvice`나 ResponseBodyAdvice를 거치지 않으므로 업무 오류 전문과 모양이 다를 수 있다. Controller 입력이 비었는데 Filter 파싱 로그는 성공했다면 Wrapper 대신 원 요청을 Chain에 넘겼는지, 커스텀 Resolver가 Wrapper를 읽는지 확인한다.

## 9.4 JWT 토큰 추출

현행 일반 JSON 경로에서 JWT 검증 여부는 `jwt.enabled`가 아니라 `spring.profiles.active`로 결정된다. 활성 Profile 문자열이 `local`이면 검증을 생략하고, 그 외 Profile에서는 `Authorization: Bearer <token>`이 필요하다.

```text
비-local JSON 요청
  → Authorization Header 확인
  → "Bearer " 접두 확인
  → JwtProvider.validate(token)
  → JwtProvider.isAccessToken(token)
  → JwtProvider.getSsoId(token)
  → request.setAttribute("ssoId", ssoId)
```

`JwtProvider`는 `jwt.secret`을 UTF-8 byte로 바꿔 HMAC SecretKey를 만들고 JJWT Parser로 서명된 Claim을 검증한다. `type` Claim이 `ACCESS`인지 검사하고 Subject를 SSO ID로 읽는다. 토큰 원문은 ServiceContext에 저장하지 않으며 로그에도 남겨서는 안 된다.

여기서 AS-IS 설정상의 주의점이 있다. dev Profile에 `jwt.enabled=false`가 있어도 `DefaultFilter`는 이 값을 읽지 않는다. Profile이 local이 아니면 JWT를 요구한다. 운영자가 `jwt.enabled`만 보고 인증이 비활성이라고 판단하면 실제 동작과 어긋난다. TO-BE에서는 인증 사용 여부를 명시적 Property 하나로 통일하고 local 면제도 승인된 개발 환경에서만 허용하는 편이 명확하다.

### JSON과 multipart의 비대칭

현행 코드는 multipart 여부를 JWT 검사보다 먼저 판단한다. multipart 분기는 X-GUID 기반 최소 Context를 만든 뒤 바로 Chain을 호출한다. 따라서 비-local multipart 요청은 DefaultFilter의 Bearer 검증을 통과하지 않고도 MVC로 갈 수 있다. 다른 Security Filter나 Endpoint 자체 권한 검사가 이를 보완한다고 확인되지 않는 한 인증 우회 위험으로 취급해야 한다.

| 요청 | local | 비-local AS-IS |
|---|---|---|
| JSON | JWT 생략 | Bearer Access Token 필수 |
| multipart | 별도 최소 Context | DefaultFilter JWT 검사 없음 |
| OPTIONS | Filter 제외 | Filter 제외 |

TO-BE의 안전한 순서는 OPTIONS 같은 명시적 예외를 먼저 제외하고, 인증이 필요한 모든 Content-Type에 공통 JWT 검증을 수행한 뒤 JSON/multipart 준비를 분기하는 것이다. 변경 시에는 실제 업로드 Endpoint와 Gateway 인증을 함께 조사해야 한다.

### 오류와 보안

토큰 누락, 서명·만료 검증 실패, ACCESS가 아닌 토큰은 401 `sendError()`로 종료한다. Filter가 거절했으므로 Controller와 Interceptor 로그가 없는 것이 정상이다. 토큰 값을 디버그 로그나 예외 메시지에 출력하지 않고, 필요하면 검증 실패 유형과 GUID 후보 정도만 기록한다. Secret은 환경변수나 승인된 Secret Store에서 주입해야 한다.

## 9.5 GUID 생성·보완

GUID는 한 요청을 전 계층 로그에서 연결하는 식별자다. `DefaultFilter`는 전문의 `hdr_nhnis.sys_comm.std_gbl_id`를 읽어 ServiceContext와 Log4j ThreadContext의 `guid`에 넣는다. local에서 Header 자체가 없으면 `syntheticLocalHeader()`가 하이픈을 제거한 UUID를 생성한다.

GUID 처리에는 두 경로가 있다.

```text
local + hdr_nhnis 없음
  → Filter가 UUID 생성
  → 합성 sys_comm.std_gbl_id
  → Context/MDC에 동일 값 설정

hdr_nhnis 존재
  → Filter가 기존 std_gbl_id 사용
  → 기타 sys_comm 필드만 보완
```

현행 `fillSysCommFromRequest()`는 Service ID, 화면 ID, IP, 조작자, 시스템 ID는 보완하지만 GUID는 생성하지 않는다. 따라서 Header 객체는 존재하지만 `std_gbl_id`만 비어 있으면 Filter에서 완전한 GUID를 보장하지 못한다. 뒤의 `ServicePreventionInterceptor.preHandle()`가 누락 GUID를 강제 채번해 Header, ServiceContext와 MDC를 맞추는 보완 경로가 있다.

이 AS-IS는 정상 거래에서는 최종적으로 GUID를 확보할 수 있지만 Filter와 Interceptor 사이 구간의 로그에는 GUID가 없을 수 있다는 뜻이다. 또한 `ThreadContext.put()`에 null이 들어가는 라이브러리 동작에 따라 Filter 예외가 날 가능성도 고려해야 한다. TO-BE에서는 Filter가 Header 유무와 무관하게 GUID를 보장한 뒤 Context를 여는 것이 수명주기상 더 단순하다.

GUID는 Service ID와 다르다. URI 마지막 세그먼트로 얻은 Service ID는 임시값이고 전문의 `rms_svc_c`가 있으면 MDC 값을 교체한다. GUID는 요청 한 건을 구분하고 Service ID는 실행할 거래 종류를 구분한다. 재호출에는 같은 Service ID라도 새 GUID가 필요하다.

### IP와 사용자 보완

Filter는 IP가 비면 `X-Forwarded-For`의 첫 값 또는 `remoteAddr`를 사용하고, local 조작자가 비면 `LOCAL`을 넣는다. Proxy Header를 무조건 신뢰하면 외부 사용자가 IP 기반 거래통제를 우회할 수 있다. 운영에서는 승인된 Proxy가 Header를 덮어쓰게 하고 애플리케이션은 신뢰 가능한 구간에서만 이를 사용해야 한다.

## 9.6 ServiceContext 생성

`ServiceContext`는 요청 처리 동안 여러 계층이 공유할 공통 상태를 한 객체로 묶는다. 생성자에는 애플리케이션 이름, GUID, 활성 Profile, 복사한 HTTP Header, 현재 Request와 Response, typed `hdr_nhnis`가 전달된다. 이후 요청 원문, 사용자 Context와 응답 원문이 생명주기 중 보완된다.

```java
ServiceContext serviceContext = new ServiceContext(
    applicationName,
    guid,
    active,
    requestHeaders,
    wrapper,
    response,
    header
);
serviceContext.setRequestBody(requestBody);
ServiceContextHolder.setInstance(serviceContext);
```

이 코드는 현재 실제 생성자 형태를 단순화하지 않고 보여 준 것이다. no-argument 생성자로 임의 Context를 만든다는 예시는 현행 소스와 맞지 않는다.

`ServiceContextHolder`는 정적 `ThreadLocal<ServiceContext>`를 사용한다. 같은 Request Thread에서 실행되는 Interceptor, Controller, Advice와 업무 Aspect는 Holder를 통해 같은 객체를 읽을 수 있다. 객체를 메서드 인자로 계속 전달하지 않아도 되는 장점이 있지만, Thread 수명과 요청 수명이 다르다는 위험을 동반한다.

```text
Tomcat Thread-17
  ├─ Filter: Context 생성·set
  ├─ Interceptor: Header/GUID 보완
  ├─ Controller: Service ID 조회
  ├─ Advice: responseBody 기록
  └─ Filter finally: remove
```

ServiceContext는 업무 DTO 저장소나 전역 Session이 아니다. 한 요청의 공통 정보만 담고, 비밀번호·토큰·대용량 업무 객체를 넣지 않는다. 업무 Service가 Context를 새로 만들어 기존 값을 덮어쓰는 것도 금지한다. 테스트에서 직접 Controller를 호출하면 Filter가 실행되지 않아 Context가 없을 수 있으므로 필요한 Context를 Test Fixture에서 명시적으로 설치하고 `finally` 또는 `@AfterEach`에서 제거한다.

### Thread 변경

TCF Timeout이 활성화되면 실제 업무는 Worker Thread에서 실행될 수 있다. ThreadLocal은 자동 전파되지 않는다. PDMG의 `OnlineTimeoutWorkerContext`는 Request Thread의 ServiceContext와 MDC를 캡처해 Worker에 설치하고 종료 시 정리한다. 이 구조가 없으면 Worker 로그의 GUID가 사라지고 ServiceContext를 사용하는 업무 선후처리가 null을 보게 된다.

Filter가 관리하는 것은 Request Thread의 Context 수명이다. Worker Thread의 설치·정리는 Timeout 컴포넌트 책임이다. 하나의 Holder를 사용한다고 해서 두 Thread가 자동으로 같은 상태를 공유하는 것은 아니다.

## 9.7 MDC와 로그 Context

MDC는 로그 레코드마다 GUID와 Service ID를 명시적으로 전달하지 않아도 로그 Pattern에서 공통 필드를 출력하도록 돕는다. 현행 Filter는 SLF4J MDC가 아니라 Log4j의 `ThreadContext`에 다음 값을 넣는다.

| Key | 값의 출처 | 목적 |
|---|---|---|
| `guid` | `std_gbl_id` | 요청 한 건 추적 |
| `serviceId` | URI 후보, 이후 `rms_svc_c` 우선 | 거래 종류 추적 |
| `ip` | `tr_trm_ipadr` | 단말·접속 위치 추적 |
| `userId` | `optr_eno` | 사용자·감사 추적 |

MDC는 로그를 위한 복제 Context이고 ServiceContext가 원본 업무 Context다. 두 값을 따로 갱신하면 불일치할 수 있다. Interceptor가 GUID를 보완할 때 Header, `ServiceContext.guid`와 ThreadContext의 GUID를 함께 맞추는 이유다.

로그 Context는 편리하지만 보안 경계를 대신하지 않는다. `userId`가 전문에 있다고 해서 인증된 사용자라고 볼 수 없고, MDC 값으로 권한을 판단해서도 안 된다. MDC에는 검색에 필요한 최소 식별자만 넣고 Token, Secret, 주민번호나 전문 원문을 넣지 않는다.

### Thread Pool 오염

Servlet Container는 요청이 끝난 Thread를 폐기하지 않고 Pool에 돌려준다. 정리하지 않으면 다음 요청이 이전 사용자의 GUID와 사용자 ID로 로그를 남길 수 있다.

```text
요청 A → Thread-17 → guid=A → 정리 누락
요청 B → Thread-17 재사용 → 초기 로그에 guid=A 노출
```

따라서 정상·인증 실패·JSON 오류·Controller 예외 어느 경로에서도 `finally` 정리가 필요하다. Worker Thread도 동일하다. 장애 테스트는 응답만 확인하지 말고 같은 Pool Thread를 재사용했을 때 MDC가 비어 있는지 검증해야 한다.

## 9.8 Spring MVC 요청 변환

`DefaultFilter`가 `filterChain.doFilter()`를 호출하면 DispatcherServlet이 요청을 받는다. 여기서부터 Spring MVC가 URL과 HTTP method에 맞는 Handler를 찾고, HandlerAdapter가 Controller 메서드를 호출할 준비를 한다.

```text
DispatcherServlet
  → HandlerMapping
      ├─ TCF ON: OnlineTransactionController
      └─ TCF OFF: mgcoa*Controller
  → HandlerExecutionChain
      └─ ServicePreventionInterceptor.preHandle
  → RequestMappingHandlerAdapter
      ├─ HandlerMethodArgumentResolver
      └─ HttpMessageConverter
  → Controller method invoke
```

HandlerMapping이 끝나야 Interceptor는 어느 Controller가 선택되었는지 알 수 있다. `preHandle`은 이 시점에 실행되고 시스템 선처리와 ImageLog를 담당한다. 거래통제의 상세 규칙은 10장에서 다룬다. 이 장에서 중요한 것은 Interceptor가 Filter가 만든 ServiceContext와 캐시된 원문을 소비한다는 의존 순서다.

TCF ON의 `OnlineTransactionController`는 Spring 표준 `@RequestBody Map<String,Object>`로 전체 JSON을 받는다. Spring의 기본 RequestResponseBodyMethodProcessor와 Jackson HttpMessageConverter가 Wrapper Body를 Map으로 변환한다. Controller는 그 Map에서 `dto`를 꺼내 TcfFacade에 전달한다.

TCF OFF 업무 Controller는 프로젝트 커스텀 `nhnis.fw.commons.resolver.RequestBody` Annotation을 사용한다. 이 경우 `RequestBodyArgumentResolver`가 전체 JSON을 읽고 `dto` 노드만 거래별 DTOin으로 변환한다. 같은 이름의 Annotation처럼 보여도 Spring 표준 `org.springframework.web.bind.annotation.RequestBody`와 import가 다르다.

### 변환 실패를 구간별로 보기

| 실패 구간 | 대표 원인 | Controller 진입 |
|---|---|---:|
| Filter JSON 파싱 | 문법 오류, 빈 Body | 안 함 |
| HandlerMapping | URL/HTTP method 불일치 | 안 함 |
| ArgumentResolver | DTO 타입 불일치, 읽기 오류 | 안 함 |
| Controller 내부 | Service ID·업무 검증 | 진입함 |
| 업무 실행 | Service/DAO 예외 | 진입함 |

“Controller가 호출되지 않았다”는 현상만으로 Mapping 오류라고 결론 내리지 않는다. Filter 시작·종료, 401/400 응답, Interceptor 시작, Resolver TX-FLOW 로그 순서로 마지막 성공 지점을 찾는다.

## 9.9 ArgumentResolver

`RequestBodyArgumentResolver`는 Controller 파라미터에 PDMG 커스텀 `@RequestBody`가 있고 Content-Type이 multipart가 아닐 때만 지원한다. `WebConfiguration.addArgumentResolvers()`가 이를 MVC Resolver 목록에 추가하며, 이 Configuration은 `legacy-web.enabled=true`일 때 기본 생성된다.

Resolver의 실제 동작은 다음과 같다.

```text
Cached request.getReader()
  → ObjectMapper.readTree(전체 JSON)
  → root.get("dto")
  → dto가 없으면 빈 ObjectNode
  → parameter.getParameterType()
  → treeToValue(dtoNode, DTOin.class)
```

ObjectMapper는 알 수 없는 필드를 무시하고 빈 배열을 null 객체로 수용하도록 설정된다. 이 정책은 구버전 클라이언트의 여분 필드에 관대하지만 오타도 조용히 무시할 수 있다. 필수 입력은 별도 Validation이나 업무 Rule로 확인해야 한다.

`dto`가 없을 때 오류를 내지 않고 빈 객체로 바꾸는 점도 중요하다. 모든 필드가 선택적인 DTO라면 요청이 통과할 수 있다. Controller가 non-null DTO를 받았다는 사실은 전문이 올바르다는 보장이 아니다. 필수값, 범위, 길이와 상호 관계는 업무 경계에서 검증한다.

### TCF ON/OFF 변환 비교

| 항목 | TCF ON | TCF OFF |
|---|---|---|
| Controller 입력 | 전체 JSON Map | 거래별 DTOin |
| Annotation/Resolver | Spring 표준 Body 처리 | PDMG 커스텀 Resolver |
| `dto` 추출 | OnlineTransactionController | RequestBodyArgumentResolver |
| typed DTO 변환 | 업무 Facade | Resolver |
| Handler 사용 | 사용 | 사용하지 않음 |

이 차이는 전문 모양이 같아도 실행 경로가 같지 않음을 보여 준다. Controller 코드를 복사할 때 import를 잘못 선택하면 TCF OFF DTO에 전체 JSON을 매핑하려 하거나 커스텀 Resolver가 적용되지 않을 수 있다.

## 9.10 응답 변환

Controller가 Java 객체를 반환하면 Spring MVC는 ReturnValueHandler와 HttpMessageConverter를 통해 응답을 쓴다. 그 사이에서 `ResponseBodyArgumentResolver`가 `ResponseBodyAdvice<Object>`로 동작한다. 클래스 이름에 ArgumentResolver가 들어 있지만 요청 인자가 아니라 응답 Body를 공통 전문으로 조립한다.

```text
Controller 반환 DTOout
  → ResponseBodyAdvice.supports() = true
  → beforeBodyWrite()
      ├─ ServiceContext.header → hdr_nhnis
      ├─ 정상 객체 → dto
      ├─ NH_NIS_ERR_DTO → result
      ├─ 응답 전문 로그
      └─ ServiceContext.setResponseBody
  → HttpMessageConverter JSON 직렬화
  → HTTP Response
```

Advice는 `legacy-web.enabled=true`일 때 생성되고 `supports()`가 항상 true다. 따라서 적용 대상이 특정 온라인 Controller로 제한되지 않는다. 같은 애플리케이션의 Health API나 문자열·파일 응답도 Advice 대상이 될 수 있으며, multipart Content-Type만 원 Body를 반환하는 예외가 있다. 신규 비온라인 Endpoint를 추가하면 이 전역 Advice가 응답을 감싸는지 반드시 테스트해야 한다.

정상 Body는 `dto`, `NH_NIS_ERR_DTO`는 `result`에 넣는다. Context가 있으면 Header도 포함한다. JSON Tree를 재귀적으로 순회하며 `dtoLogicalName`, `fieldPropertyMap`과 이름이 `List`, `Array`로 끝나는 필드를 제거한다. 마지막 규칙은 실제 업무 필드까지 제거할 가능성이 있으므로 DTO 이름을 설계할 때와 회귀 테스트에서 데이터 손실을 확인해야 한다.

응답 조립 중 예외는 현행 코드에서 `printStackTrace()` 후 계속 진행될 수 있다. 이 방식은 서버 로그 체계를 우회하고 불완전한 응답을 정상처럼 반환할 위험이 있다. TO-BE에서는 표준 Logger로 GUID와 Service ID를 남기고, 이미 Response가 Commit되지 않았다면 일관된 시스템 오류로 변환해야 한다. 내부 Stack Trace를 클라이언트 응답에 포함해서도 안 된다.

### Advice와 Interceptor 순서

`@ResponseBody` Controller에서는 `ModelAndView`가 없으므로 `postHandle`에서 최종 JSON Body를 안정적으로 얻기 어렵다. Advice가 Java 반환값을 표준 전문으로 바꾸고 `ServiceContext.responseBody`에 저장한 뒤, Interceptor의 `afterCompletion`이 ImageLog를 완료한다. 응답 조립을 Interceptor에 억지로 합치지 않는 이유다.

## 9.11 Filter 종료 정리

Filter는 요청 Context를 가장 먼저 열고 가장 마지막에 닫는다. `filterChain.doFilter()`가 정상 반환해도, Controller가 예외를 던져도, Filter 내부에서 400/401로 조기 반환해도 `finally`가 실행된다.

```java
finally {
    if (ServiceContextHolder.getInstance() != null) {
        ServiceContextHolder.removeInstance();
    }
    if (!ThreadContext.isEmpty()) {
        ThreadContext.clearAll();
    }
}
```

정리 순서는 응답 Advice와 Interceptor 완료 이후여야 한다. Filter가 Chain 안쪽 호출이 끝나기 전에 Context를 지우면 응답 Header 조립과 ImageLog 후처리가 정보를 잃는다. 반대로 너무 늦게 지우거나 예외 경로를 빠뜨리면 Thread Pool이 오염된다.

Interceptor의 `afterCompletion`에도 보조 정리가 존재하지만 Filter 정리를 대체한다고 가정하지 않는다. Filter 단계에서 거절된 요청은 Interceptor에 들어가지 않기 때문이다. Context 소유자가 Filter이므로 최종 정리 책임도 Filter에 있어야 한다. 여러 계층의 방어적 정리는 멱등해야 하며, 먼저 정리됐다는 이유로 NullPointerException을 만들어서는 안 된다.

Worker Thread는 별도다. Request Thread Filter가 Worker의 ThreadLocal을 지울 수 없다. Timeout Executor가 Worker에 Context를 설치했다면 Worker의 `finally`에서 제거해야 한다. 장애 테스트에서는 Request Thread와 Worker Thread 양쪽을 관찰한다.

### 종료 시나리오 비교

| 시나리오 | MVC 진입 | Advice | Interceptor 완료 | Filter finally |
|---|---:|---:|---:|---:|
| 정상 JSON | O | O | O | O |
| JWT 실패 | X | X | X | O |
| JSON 파싱 실패 | X | X | X | O |
| Controller 업무 예외 | O | 예외 처리 결과에 따름 | O | O |
| OPTIONS | Filter 제외 | CORS/MVC 경로에 따름 | 경로에 따름 | DefaultFilter 정리 없음 |

## 9.12 Filter와 Interceptor를 합치면 안 되는 이유

두 구성요소는 모두 요청 전후에 코드를 실행할 수 있지만 대체 관계가 아니다. Filter는 Servlet Chain을 감싸고 Interceptor는 Spring이 선택한 Handler 실행을 감싼다. 사용할 수 있는 정보와 실패 지점, 응답 처리 방식이 다르다.

| 구분 | DefaultFilter | ServicePreventionInterceptor |
|---|---|---|
| 실행 위치 | DispatcherServlet 전 | HandlerMapping 후 |
| Body Wrapper 교체 | 적합 | 늦음 |
| JWT/원시 HTTP 거절 | 적합 | MVC 비용 이후 |
| Controller 정보 | 없음 | HandlerMethod 접근 가능 |
| 요청 ImageLog | Context 준비 후 전달 | `preHandle` 책임 |
| 최종 응답 Body | 직접 알기 어려움 | `postHandle`도 제한적, Advice 사용 |
| Context 수명 | 생성·최종 제거 | 소비·보완 |

### 모든 기능을 Filter로 옮기면

Filter에서 ImageLog INSERT/UPDATE, 응답 전문 조립과 거래통제까지 수행하면 HTTP 파싱 실패와 업무 실패가 한 클래스에 섞인다. 최종 응답은 Advice가 조립하므로 Response Wrapper까지 추가해야 하고, Controller Annotation이나 선택된 Handler 정보가 필요한 정책은 다시 MVC 내부를 추측해야 한다. Filter가 거대해질수록 한 오류가 모든 URL을 막는다.

### 모든 기능을 Interceptor로 옮기면

Interceptor가 실행될 때는 DispatcherServlet이 이미 요청을 받았다. 원 InputStream을 Filter가 소비한 뒤라면 Wrapper 교체가 늦고, JWT가 없는 요청도 HandlerMapping까지 진행한다. Controller를 찾지 못한 요청에는 Interceptor가 기대대로 적용되지 않을 수 있다. Servlet 수준의 CORS·multipart·Body 준비와 MVC 수준의 Handler 전후 처리를 한 생명주기로 묶기 어렵다.

### 응답까지 한곳에 합치면

Interceptor `postHandle`은 `@ResponseBody`가 실제 JSON으로 직렬화되기 전후의 최종 원문을 소유하지 않는다. ResponseBodyAdvice는 반환값을 바꿀 수 있는 정식 확장 지점이다. 현행 책임 분리는 다음과 같이 유지하는 편이 명확하다.

```text
Filter       : HTTP/Body/JWT/Context 생성·해제
Interceptor  : 선택된 MVC Handler 전후 시스템 처리·ImageLog
Advice       : 표준 응답 조립과 응답 원문
TCF          : Service ID 라우팅과 실행
Facade/TX    : 업무 트랜잭션
```

중복 제거는 클래스를 합치는 것이 아니라 한 관심사의 소유자를 하나로 만드는 것이다. Filter와 Interceptor가 모두 요청 전문을 저장하거나 Advice와 `postHandle`이 모두 응답을 조립하는 중복은 제거해야 한다. 그러나 Body Wrapper와 Handler 기반 통제를 한 클래스로 합치는 것은 책임 통합이 아니라 경계 파괴다.

## 9.13 Filter 비활성화 영향

`nhnis.fw.commons.filter.enabled=false`로 바꾸면 DefaultFilter Bean과 등록 Bean이 생성되지 않는다. 단순히 시작·종료 로그만 사라지는 것이 아니다. 현행 요청 계약에서 Filter가 제공하던 여러 전제도 함께 사라진다.

```text
Filter OFF
  ├─ CachedBodyHttpServletRequest 없음
  ├─ hdr_nhnis 선파싱·local 합성 없음
  ├─ 비-local JWT 검증 없음
  ├─ ServiceContext 생성 없음
  ├─ GUID/Service ID/IP/User MDC 없음
  ├─ PDMG_REQUEST_BODY attribute 없음
  └─ Filter finally Context 정리 경로 없음
```

Spring MVC 자체는 계속 기동할 수 있다. Spring 표준 `@RequestBody`는 원 Stream을 한 번 읽어 Map이나 DTO로 변환할 수 있으므로 단순 Controller는 동작할 수 있다. 하지만 Interceptor, OnlineTransactionController, ResponseBodyAdvice와 ImageLog가 ServiceContext 존재를 전제로 하는 기능은 Header·GUID·원문을 잃거나 축소 동작한다. TCF ON 여부와 Filter ON 여부를 독립적으로 테스트해야 하는 이유다.

TCF OFF 업무 Controller의 커스텀 Resolver도 원 Body를 직접 한 번 읽을 수 있어 DTO 변환만 보면 성공할 수 있다. 그렇더라도 JWT와 Context, MDC가 사라진다. “업무 조회가 성공했다”는 결과 하나로 Filter OFF가 호환된다고 판단하면 안 된다.

### Filter OFF가 필요한 경우의 선행 조건

Filter를 제거하거나 대체하려면 다음 책임의 새 소유자를 먼저 정해야 한다.

| 사라지는 책임 | 대체 후보 | 검증 |
|---|---|---|
| JWT 검증 | Spring Security/Gateway | 누락·변조·만료·multipart |
| Body 재읽기 | 다른 Servlet Filter/Wrapper | ON/OFF Controller 바인딩 |
| ServiceContext | 새 Context Filter | 정상·예외·Thread 전파 |
| GUID/MDC | Trace Filter | 로그·ImageLog 일치 |
| Header 합성 | 클라이언트 계약 또는 Adapter | local/통합 환경 분리 |
| 원문 저장 | 제한된 Logging Filter | 크기·마스킹·보존 |

대체 없이 끄는 것은 기능 비활성화가 아니라 실행 계약 해체다. TO-BE에서 Spring Security로 인증을 옮기더라도 Body 캐시와 Context 수명은 여전히 별도 Filter가 필요할 수 있다.

## End-to-End 정상 시나리오

`mgcoa9000S0` 조회 요청 한 건을 따라가 보자.

1. Servlet Container가 POST 요청을 받고 등록 순서에 따라 `DefaultFilter`를 호출한다.
2. Filter는 URI 마지막 값을 임시 Service ID로 MDC에 넣고 HTTP Header를 복사한다.
3. JSON 요청을 `CachedBodyHttpServletRequest`로 감싼다.
4. local이 아니면 Bearer Access Token을 검증하고 SSO ID를 request attribute에 둔다.
5. 캐시 Body를 Map으로 파싱하고 `hdr_nhnis`를 typed Header로 변환한다. local Header 누락이면 합성한다.
6. GUID, IP, 사용자, Service ID를 ThreadContext에 넣고 ServiceContext를 Holder에 설치한다.
7. Wrapper를 DispatcherServlet에 전달한다.
8. HandlerMapping이 TCF ON 공통 Controller를 선택하고 Interceptor가 시스템 선처리를 수행한다.
9. Spring MessageConverter가 Wrapper Body를 Map으로 변환해 Controller에 전달한다.
10. Controller와 TCF가 Service ID에 맞는 Handler·Facade·Service를 실행한다.
11. Controller 반환값을 ResponseBodyAdvice가 `{hdr_nhnis, dto}`로 감싸고 Context에 응답 원문을 기록한다.
12. Interceptor 완료 처리 뒤 Chain이 Filter로 돌아온다.
13. Filter가 Holder와 ThreadContext를 제거하고 Container가 응답을 전송한다.

이 시나리오에서 Filter가 만든 Wrapper와 Context는 Controller 이전부터 응답 Advice 이후까지 유지된다. 반면 업무 트랜잭션은 이 전체 구간이 아니라 TCF/Facade 실행 경계에서 시작하고 끝난다.

## 실패 시나리오와 진단 기준

### 토큰이 없는 비-local 요청

Filter는 401을 보내고 Chain을 호출하지 않는다. Interceptor·Controller·업무 트랜잭션·Advice 로그가 없는 것이 정상이다. 브라우저에서 CORS 오류처럼 보이면 Filter가 Security CORS 처리보다 먼저 응답했는지 확인한다.

### Body가 잘못된 요청

빈 Body 또는 JSON 문법 오류는 Filter 400으로 끝난다. 표준 `result` 응답을 기대하면 클라이언트 파서가 다시 실패할 수 있다. Filter 오류와 MVC 업무 오류의 응답 계약을 통합할지 TO-BE 정책이 필요하다.

### Header는 있지만 GUID가 없는 요청

Filter의 GUID 보완이 불완전하므로 Filter 구간 로그가 비거나 예외가 날 수 있다. Interceptor에 도달하면 GUID를 보완하지만, 도달 전 장애까지 해결하지는 못한다. Filter에서 GUID를 항상 보장하도록 개선하고 회귀 테스트해야 한다.

### Controller 인자가 빈 객체인 요청

TCF OFF 커스텀 Resolver는 `dto`가 없으면 빈 ObjectNode를 만든다. Mapping 성공만 확인하지 말고 DTO 필수값 검증 결과를 확인한다. Wrapper가 누락된 경우에는 Reader가 이미 소모되어 파싱 자체가 실패할 수 있다.

## 책임과 경계 표

| 구성요소 | Caller | 책임 | Callee | 금지 책임 |
|---|---|---|---|---|
| DefaultFilter | Servlet Container | Body 캐시, JWT, Header/Context/MDC | Filter Chain | 업무 SQL·거래별 검증 |
| DispatcherServlet | Filter Chain | MVC 요청 조정 | HandlerMapping/Adapter | 업무 로직 |
| ServicePreventionInterceptor | MVC Chain | Handler 전후 시스템 처리 | Controller Chain | Body Wrapper 최초 생성 |
| RequestBodyArgumentResolver | HandlerAdapter | `dto`→DTOin | Controller | 인증·트랜잭션 |
| OnlineTransactionController | MVC | Service ID·dto 전달 | TcfFacade | DAO 직접 호출 |
| ResponseBodyAdvice | MVC 반환 처리 | Header+Body 표준 응답 | MessageConverter | 업무 DB 갱신 |
| Filter finally | Chain 복귀 | Request Thread Context 정리 | Container | Worker Thread 정리 대행 |

## Anti Pattern

1. Filter가 Body를 읽고 원 요청을 Chain에 넘긴다. MVC 바인딩이 빈 Body를 만나게 된다.
2. Filter에서 Controller Annotation이나 Service ID별 업무 규칙을 판단한다. Handler가 정해지기 전 계층에 업무 결합이 생긴다.
3. Interceptor에서 Wrapper를 처음 만든다. InputStream 소비와 MVC 처리 시점상 너무 늦다.
4. `jwt.enabled=false`만 보고 비-local 인증이 꺼졌다고 판단한다. 현행 Filter는 Profile로 분기한다.
5. multipart도 JSON과 같은 인증을 받는다고 가정한다. 현행 분기 순서상 DefaultFilter JWT가 적용되지 않는다.
6. ServiceContext에 토큰과 대용량 DTO를 보관한다. ThreadLocal 누수와 민감정보 노출 위험이 커진다.
7. Filter와 Worker가 같은 Thread라고 가정한다. Timeout 활성 시 Context와 MDC는 명시적 전파가 필요하다.
8. 응답 전문을 Interceptor `postHandle`에서 조립한다. `@ResponseBody` 직렬화 확장 지점을 우회한다.
9. Filter OFF 뒤 조회 API 하나만 성공했다고 호환 완료로 판단한다. 인증·GUID·ImageLog·응답 Header를 함께 검증해야 한다.
10. 전문이나 Authorization Header를 마스킹 없이 로그에 출력한다. 운영 Secret과 개인정보를 노출한다.

## 아키텍처 판단 포인트

공통 기능을 어디에 둘지는 “요청 전인가 후인가”만으로 정하지 않는다. 원시 Servlet 객체를 바꿔야 하면 Filter, 선택된 Handler 정보가 필요하면 Interceptor, Controller 파라미터를 만들면 ArgumentResolver, 반환 Body를 바꾸면 ResponseBodyAdvice가 맞다. 업무 트랜잭션과 Service ID 라우팅은 이 MVC 준비 계층보다 안쪽에 둔다.

Filter는 모든 요청의 장애 반경을 가진다. 새 검사를 추가할 때 온라인 JSON, multipart, OPTIONS, Health Endpoint, TCF ON/OFF와 오류 응답을 함께 검토한다. Context를 추가하면 생성 위치만큼 정리 위치와 Worker 전파도 설계한다. 요청 Body 로깅을 강화할 때는 편의보다 크기 제한과 마스킹을 먼저 정한다.

AS-IS에서 우선 검토할 개선은 multipart 인증 비대칭, 기존 Header의 GUID 누락, `/*`에 대한 Body 강제, Filter 오류의 비표준 응답, ResponseBodyAdvice의 전역 적용과 예외 은폐다. 이들은 현재 구현 사실과 분리된 TO-BE 과제이며 변경 시 호환성 테스트가 필요하다.

## 핵심 정리

`DefaultFilter`는 Spring MVC보다 앞선 Servlet 경계에서 요청 Body를 캐시하고 비-local JSON 요청의 JWT를 확인하며 Header, ServiceContext와 MDC를 준비한다. `DispatcherServlet` 이후에는 HandlerMapping이 Controller를 선택하고 Interceptor와 Resolver가 그 요청을 Java 호출로 바꾼다. Controller 반환 뒤에는 ResponseBodyAdvice가 표준 응답을 조립한다.

Request Body 캐시는 선택적 로그 기능이 아니라 Filter와 MVC가 같은 단일 소비 InputStream을 함께 사용하기 위한 실행 장치다. ServiceContext와 MDC도 Filter에서 열고 `finally`에서 닫아야 Thread Pool 오염을 막을 수 있다. Thread가 바뀌면 자동 전파되지 않으므로 Worker에서 별도로 설치하고 정리한다.

Filter와 Interceptor를 합치면 안 되는 이유는 취향이 아니라 실행 경계가 다르기 때문이다. Filter는 Controller를 모르는 대신 원 요청을 바꿀 수 있고, Interceptor는 Handler를 아는 대신 Body를 처음부터 준비하기에는 늦다. 응답 Body는 Advice가 소유한다. 각 확장 지점에 맞는 책임을 두는 것이 PDMG 요청 생명주기를 안정적으로 유지하는 방법이다.

다음 장에서는 Filter가 준비한 ServiceContext와 캐시 원문을 받은 `ServicePreventionInterceptor`가 무엇을 보완하고 어떤 시스템 선처리와 거래 통제를 수행하는지 살펴본다. Filter가 “요청을 실행 가능한 상태로 만드는 계층”이라면 Interceptor는 “선택된 MVC 거래가 업무로 진입해도 되는지 판단하고 감사 시작점을 남기는 계층”이다.
