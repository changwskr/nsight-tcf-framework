# 5장. 네이밍 규칙

PDMG의 이름은 소스에 붙이는 표찰이 아니다. `mgcoa9000S0`이라는 거래 식별자가 패키지, Handler, Facade, Service, DTO, DAO와 Mapper Statement까지 이어지면서 한 건의 요청을 끝까지 추적하게 만드는 구조적 연결 장치다. 이름이 규칙을 따르면 개발자는 URL 하나로 Java 진입점과 SQL을 찾을 수 있다. 규칙이 깨지면 같은 업무가 여러 이름으로 흩어지고, 컴파일에 성공해도 MyBatis 바인딩이나 운영 추적 단계에서 실패한다.

이 장은 4장에서 만든 Program ID와 Service ID를 실제 소스 이름으로 투영하는 방법을 설명한다. 패키지 디렉터리와 Spring Scan의 상세는 6장에 맡기고, 여기서는 “어떤 코드를 이름의 어느 부분에 넣으며 계층별 책임을 어떻게 드러내는가”에 집중한다.

## 이 장에서 해결할 질문

- Service ID에서 패키지와 각 클래스 이름을 어떻게 유도하는가?
- Handler, Controller, Facade, Service, Rule과 DAO는 이름만으로 어떻게 구별하는가?
- DTOin, DTOout, DTOSub는 데이터 흐름을 어떻게 표현하는가?
- DAO FQCN, Mapper namespace, DAO 메서드와 Statement ID는 왜 완전히 일치해야 하는가?
- Java 필드와 DB 컬럼은 현재 소스에서 실제로 어떻게 연결되는가?
- 현재 소스의 예외적 이름과 신규 개발 표준을 어떻게 구분하는가?
- 신규 프로그램 하나의 이름을 어떤 순서로 결정하고 검증하는가?

이 장의 관통 예제는 실제 소스가 완전하게 존재하는 거래 파라미터 관리 프로그램 `mgcoa9000`이다. 조회·등록·수정·삭제 네 거래, Handler와 TCF OFF Controller, Facade, Service, DTO, DAO와 Mapper를 모두 가지고 있어 이름의 연결을 한 흐름으로 확인할 수 있다.

## 5.1 네이밍 규칙의 목적

네이밍 규칙의 첫 번째 목적은 업무를 식별하는 것이다. `mgcoa9000`을 보면 `mg/co/a` 분류축의 프로그램 번호 `9000`임을 알 수 있고, `mgcoa9000C0`을 보면 그 프로그램의 등록 거래임을 알 수 있다. 이름을 해독하는 데 별도 목록이 필요하지 않으므로 신규 개발자도 검색 범위를 빠르게 좁힐 수 있다.

두 번째 목적은 계층 책임을 드러내는 것이다. `mgcoa9000Handler`와 `mgcoa9000DAO`는 프로그램 접두가 같지만 접미사가 다르다. 전자는 TCF 라우팅 진입점이고 후자는 영속성 계약이다. 같은 접두는 동일 프로그램임을, 다른 접미사는 서로 다른 책임을 나타낸다. 접미사를 제거하거나 `Manager`, `Processor`처럼 포괄적인 단어로 바꾸면 어느 계층인지 알 수 없다.

세 번째 목적은 추적 비용을 낮추는 것이다.

```text
이름
  ↓
업무 식별
  ↓
Program ID와 거래 식별
  ↓
계층 식별
  ↓
Handler → Service → DAO 추적
  ↓
Mapper namespace → SQL ID 추적
  ↓
Service ID·GUID 기반 운영 장애 추적
```

운영 로그에 `mgcoa9000U0`가 남으면 같은 문자열로 Handler 분기, Facade와 Service 메서드, DTO, DAO 메서드와 Mapper Statement를 찾을 수 있다. 프로그램 전체를 보고 싶을 때는 거래 접미사 `U0`를 제거한 `mgcoa9000`으로 검색 범위를 넓힌다. 이 탐색 전략은 이름이 일관될 때만 성립한다.

네 번째 목적은 영향도 분석과 자동화다. 정형화된 이름은 Code Review가 누락을 찾도록 돕고, 템플릿이 한 거래의 기본 파일을 생성할 수 있게 한다. ArchUnit이나 Gradle 검증 Task는 클래스 접미사와 패키지의 대응을 검사할 수 있고, CI는 DAO 메서드와 XML Statement의 차이를 탐지할 수 있다. Codex나 LLM을 이용한 CRUD 생성에서도 Program ID와 Service ID가 명확하면 같은 이름을 모든 산출물에 안정적으로 전파할 수 있다.

다만 자동 생성은 이름의 의미를 대신 결정하지 않는다. 잘못 배정된 업무코드로 완벽하게 일관된 파일을 생성하면 오류가 더 넓게 복제된다. 업무 소유권과 거래 성격을 사람이 먼저 확정하고, 자동화는 그 결정을 기계적으로 적용하고 검증하는 역할을 맡아야 한다.

네이밍은 변경 비용을 통제하는 호환성 계약이기도 하다. public URL과 Service ID는 호출자가 참조하고, Mapper namespace와 Statement ID는 런타임 Proxy가 참조한다. Java private 변수명을 바꾸는 리팩터링과 달리 이 이름들은 저장소 밖의 UI, 통제 데이터, 로그 대시보드 또는 운영 절차에 남을 수 있다. 이름 변경을 단순 Rename으로 처리하지 않고 참조 범위와 전환 절차를 먼저 조사해야 하는 이유다.

좋은 네이밍 규칙은 두 방향 탐색을 모두 지원한다. 요구사항에서 출발하면 업무코드와 Program ID를 거쳐 필요한 파일 이름을 생성할 수 있어야 한다. 반대로 운영 오류에서 출발하면 Service ID를 분해해 Handler와 SQL까지 찾아갈 수 있어야 한다. 생성 방향만 정의하고 역추적이 불가능하다면 운영 가능한 규칙이라고 보기 어렵다.

## 5.2 프로그램 접두어

프로그램 접두어는 9자리 Program ID다. 4장에서 설명한 분류축과 네 자리 프로그램 번호를 결합한다.

```text
대그룹  업무  세부  프로그램 번호
  mg  + co +  a  +    9000
                  ↓
              mgcoa9000
```

프로그램 접두어는 동일한 수명주기를 공유하는 클래스와 파일을 묶는다. `mgcoa9000Handler`, `mgcoa9000Facade`, `mgcoa9000Controller`, `mgcoa9000Service`, `mgcoa9000DAO`, `mgcoa9000-ORA.xml`이 그 예다. 이들 이름에는 `S0`, `C0` 같은 거래구분을 넣지 않는다. 한 프로그램의 여러 거래를 하나의 프로그램 단위 클래스가 함께 담당하기 때문이다.

```text
mgcoa9000S0 ┐
mgcoa9000C0 ├─> mgcoa9000Handler / Facade / Service / DAO
mgcoa9000U0 ┤
mgcoa9000D0 ┘
```

이 규칙은 파일 폭증을 막으려는 편의만을 위한 것이 아니다. 조회와 등록이 같은 거래 파라미터 프로그램의 정책과 영속성 모델을 공유한다는 사실을 표현한다. 반대로 서로 다른 업무 책임을 억지로 같은 번호 아래에 넣으면 하나의 Service와 DAO가 비대해진다. 먼저 프로그램 경계를 올바르게 정한 뒤 접두어를 공유해야 한다.

PDMG 업무 타입은 일반 Java PascalCase 규칙의 예외로 프로그램 접두를 소문자로 시작한다. 현재 표준은 `Mgcoa9000Service`가 아니라 `mgcoa9000Service`다. 전문 생성기, 기존 타입, Mapper namespace와의 호환을 유지하기 위한 프로젝트 규칙이다. `RdwDataSourceConfig`, `BizPrePostAspect`, `GlobalExceptionHandler`처럼 프로그램 접두를 사용하지 않는 공통·프레임워크 타입은 일반 PascalCase를 따른다.

| 대상 | 현재 적용 형태 | 판단 |
|---|---|---|
| 업무 프로그램 타입 | `mgcoa9000Service` | PDMG 호환 예외, 소문자 시작 |
| 공통 프레임워크 타입 | `GlobalExceptionHandler` | 일반 PascalCase |
| 설정 타입 | `RdwDataSourceConfig` | 책임명 + `Config` |
| Aspect | `BizPrePostAspect` | 역할명 + `Aspect` |

## 5.3 Service ID 명명법

Service ID는 Program ID에 거래구분과 순번을 붙인 11자리 런타임 식별자다. 5장에서는 자리 규칙을 반복하기보다 이 값이 이름 Chain에서 어디에 사용되는지에 초점을 둔다.

```text
mgcoa9000 + S + 0 = mgcoa9000S0
  Program ID │ │
             │ └─ 동일 거래구분 내 순번
             └─── 조회 거래
```

현재 `mgcoa9000`의 실제 거래는 `S0`, `C0`, `U0`, `D0`이다. 완전한 Service ID는 다음 위치에 사용된다.

- Handler의 거래 상수와 `serviceIds()` 등록값
- Handler의 분기와 Facade·Service 거래 메서드명
- TCF OFF Controller의 `@PostMapping` URL과 메서드명
- DTO 타입명의 접두
- DAO 메서드와 Mapper Statement ID의 첫 구간
- 요청 전문의 `rms_svc_c`, 로그와 운영 검색 키

프로그램 접두와 Service ID를 혼동하면 계층의 단위가 깨진다. `mgcoa9000S0Service`를 만들면 같은 프로그램의 등록과 수정마다 Service가 갈라진다. 반대로 `mgcoa9000DTOin`을 만들면 어느 거래의 입력 계약인지 알 수 없다. 프로그램 단위 구성요소에는 Program ID를, 거래 단위 계약과 메서드에는 Service ID를 사용한다.

Service ID 거래 메서드는 일반 Java의 동사형 camelCase 규칙에 대한 명시적 예외다. 보통 `findTransactionParameters`가 자연스럽지만 PDMG 거래 진입 메서드는 `mgcoa9000S0`를 사용한다. 이를 통해 로그, 요청 ID와 호출 메서드를 직접 연결한다. 거래 내부에서 사용하는 일반 보조 메서드는 `trimToNull`, `putIfHasText`처럼 의미 있는 동사형 camelCase를 사용한다.

## 5.4 Java 패키지 명명법

업무 패키지의 분류축은 Service ID의 앞 다섯 글자와 대응한다.

```text
Service ID: mg co a 9000 S0
Java:       nhnis.mg.co.a
Mapper:     rdw.mg.co.a
```

Java 업무 루트는 `nhnis.mg.[업무].[세부]` 형식이다. `mgcoa9000`은 `nhnis.mg.co.a` 아래에 놓인다. 그 뒤에는 책임 계층을 나타내는 `entry`, `application`, `dto`, `persistence` 등의 소문자 세그먼트가 이어진다. Mapper 리소스도 같은 분류축을 `rdw.mg.co.a`로 유지한다.

패키지명은 모두 소문자이며 의미 없는 `common`, `misc`, `etc`, `temp`로 업무 책임을 숨기지 않는다. 여러 계층이 쓸 기술 보조 기능은 승인된 `support` 경계에 구체적인 책임명으로 둔다. 단지 두 클래스가 함께 사용한다는 이유로 `common`으로 옮기면 의존 방향과 소유권이 흐려진다.

현재 PDMG AS-IS Facade는 `nhnis.mg.co.a.application.facade`에 있다. 저장소 상위 아키텍처 지침은 `entry/facade` 방향을 제시하므로 두 기준에는 차이가 있다. 이 책에서 현재 구현을 설명할 때는 `application.facade`를 사용하되, `entry.facade`를 일반적으로 금지된 이름이라고 단정하지 않는다. 신규 구조 변경은 6장의 패키지 아키텍처 결정과 함께 수행해야 한다.

5장에서 기억할 핵심은 경로 전체가 아니라 이름 유도 관계다. 패키지의 `mg.co.a`와 Service ID의 `mgcoa`가 같은 업무축이어야 한다. Component Scan, Mapper Scan과 전체 디렉터리 배치는 다음 장에서 상세히 다룬다.

## 5.5 클래스·파일 명명법

PDMG 클래스명은 “식별 단위 + 책임 접미사”로 만든다. 프로그램 단위 클래스는 Program ID에 계층 접미사를 붙이고, 거래 단위 DTO는 Service ID에 데이터 역할 접미사를 붙인다.

| 식별 단위 | 공식 | 실제 예 |
|---|---|---|
| 프로그램 단위 | `[Program ID][Role]` | `mgcoa9000Facade` |
| 거래 입력 | `[Service ID]DTOin` | `mgcoa9000C0DTOin` |
| 거래 출력 | `[Service ID]DTOout` | `mgcoa9000C0DTOout` |
| 반복 하위 구조 | `[Service ID]DTOSub[n]` | `mgcoa9000S0DTOSub0` |
| Mapper 파일 | `[Program ID]-ORA.xml` | `mgcoa9000-ORA.xml` |

Java 파일명과 public 타입명은 완전히 일치한다. `mgcoa9000Service.java` 안의 public 타입은 `mgcoa9000Service`다. 같은 파일에 여러 업무 public 타입을 섞지 않는다. 접미사는 꾸밈이 아니라 계층 계약이므로 `ServiceImpl`, `DaoImpl`을 관성적으로 추가하지 않는다. 현재 MyBatis DAO는 구현 클래스가 아니라 Mapper Interface이기 때문에 `mgcoa9000DAOImpl`이 필요하지 않다.

여기서 클래스 이름과 런타임 등록 키의 차이를 이해해야 한다. Dispatcher는 `mgcoa9000Handler`라는 클래스명을 분석해 거래를 자동 등록하지 않는다. Handler가 `serviceIds()`에서 반환한 문자열을 Registry Key로 사용한다. MyBatis도 Mapper 파일명만 보고 DAO를 연결하지 않고 namespace와 Statement ID를 사용한다. 네이밍 표준은 런타임의 암묵적 마법이 아니라 여러 명시적 계약을 사람이 일관되게 유지하도록 만드는 규칙이다.

따라서 클래스 이름이 표준에 맞아도 내부 계약이 틀릴 수 있다. `mgcoa9000Handler`가 다른 Service ID를 등록하거나 `mgcoa9000-ORA.xml`이 다른 DAO namespace를 선언하면 파일 목록은 그럴듯하지만 실행은 실패한다. 리뷰에서는 파일명, 선언된 타입명, 등록 문자열과 XML 속성을 함께 확인한다.

일반 보조 타입은 책임을 직접 표현한다. 설정 조립은 `Config`, 외부 설정 바인딩은 `Properties`, 외부 호출은 `Client`, 횡단 관심사는 `Aspect`로 끝낸다. 이름에 계층 접미사를 붙였다고 책임이 자동으로 생기는 것은 아니다. `CustomerManagerService`처럼 모호한 본체에 `Service`만 덧붙이면 어떤 Use Case인지 설명하지 못한다.

## 5.6 Handler 명명법

Handler는 `[Program ID]Handler`로 이름을 만든다. 실제 예제는 `nhnis.mg.co.a.entry.handler.mgcoa9000Handler`다. 이 이름은 TCF ON에서 `mgcoa9000` 프로그램의 Service ID들을 Registry에 등록하고 Facade로 분기한다는 뜻이다.

```java
private static final String S0 = "mgcoa9000S0";
private static final String C0 = "mgcoa9000C0";
private static final String U0 = "mgcoa9000U0";
private static final String D0 = "mgcoa9000D0";

public Collection<String> serviceIds() {
    return List.of(S0, C0, U0, D0);
}
```

현재 구현의 `handle(Object dtoBody, TransactionContext context)`는 `context.getServiceId()`로 분기해 같은 접두의 Facade 메서드를 호출한다. Handler 이름, 등록 상수, 분기 대상과 Facade 접두가 일치해야 한다. 목록에는 등록했지만 switch 분기를 빼면 Registry 조회 이후 실패하고, 분기만 만들고 `serviceIds()`에 등록하지 않으면 그 코드에는 도달하지 못한다.

Handler는 라우팅 계층이므로 Service나 DAO 이름을 직접 참조하지 않는다. `mgcoa9000Handler`가 주입받는 업무 객체는 `mgcoa9000Facade`다. DTO 변환을 위해 `ObjectMapper`를 넣거나 SQL 실행 메서드를 추가하면 `Handler`라는 이름과 실제 책임이 달라진다.

TCF ON에서 공통 `OnlineTransactionController`가 요청을 받아 Handler Registry를 이용한다. 따라서 업무별 Handler는 HTTP Controller가 아니다. 클래스명을 `mgcoa9000ControllerHandler`처럼 중복 표현하지 않고, TCF 진입 역할은 `Handler`라는 단일 접미사로 나타낸다.

## 5.7 Controller 명명법

업무 Controller는 `[Program ID]Controller`로 이름을 만든다. AS-IS `mgcoa9000Controller`는 `nhnis.fw.tcf.enabled=false`일 때 활성화되는 TCF OFF 호환 진입점이다. 같은 프로그램의 네 거래를 한 Controller가 제공한다.

```java
@PostMapping("/mgcoa9000C0")
public mgcoa9000C0DTOout mgcoa9000C0(
        @RequestBody mgcoa9000C0DTOin input) throws Throwable
```

URL, 메서드명, 입력 DTO와 출력 DTO가 모두 `mgcoa9000C0`를 공유한다. URL은 일반 REST 자원명 규칙보다 PDMG Service ID 계약을 우선하므로 거래구분 `C`가 대문자다. `/transaction-parameters/create`와 `/mgcoa9000C0`를 같은 프로그램 안에서 혼용하지 않는다.

Handler와 Controller는 프로그램 접두를 공유하지만 진입 모드가 다르다.

```text
TCF ON
/online 또는 /{serviceId}
  → OnlineTransactionController
  → mgcoa9000Handler
  → mgcoa9000Facade

TCF OFF
/mgcoa9000C0
  → mgcoa9000Controller
  → mgcoa9000Service
```

현재 TCF OFF Controller는 Facade가 아니라 Service를 직접 호출한다. 이는 AS-IS 호환 경로이며 `Controller`라는 이름이 트랜잭션 경계를 의미하지는 않는다. 신규 코드에서 Handler와 Controller의 로직을 복사해 두 곳에 업무 판단을 넣으면 ON/OFF 결과가 달라진다. 두 진입점은 라우팅과 입력 전달만 담당하고 핵심 업무 이름과 로직은 Service 이하에서 공유해야 한다.

## 5.8 Facade 명명법

Facade는 `[Program ID]Facade`로 이름을 만든다. `mgcoa9000Facade`는 Handler가 전달한 비정형 `dtoBody`를 거래별 typed DTO로 변환하고 동일 Service ID의 Service 메서드를 호출한다.

```text
mgcoa9000Handler
   → mgcoa9000Facade.mgcoa9000C0(Object)
      → ObjectMapper → mgcoa9000C0DTOin
         → mgcoa9000Service.mgcoa9000C0(DTOin)
```

클래스는 프로그램 단위, public 거래 메서드는 Service ID 단위다. 조회 `mgcoa9000S0`와 등록 `mgcoa9000C0`는 같은 Facade에 있지만 서로 다른 DTO와 트랜잭션 속성을 가진다. `execute`, `process`, `doWork` 같은 이름으로 거래 메서드를 감추지 않는 이유다.

AS-IS Facade에는 `@Transactional(transactionManager = "rdwTransactionManager")`이 선언되어 있다. 조회는 `readOnly=true`, 쓰기는 `rollbackFor=Exception.class`를 사용한다. 그러나 이름만 보고 Facade가 항상 최외곽 Transaction을 시작한다고 판단하면 안 된다. Timeout ON에서는 `DefaultOnlineTimeoutExecutor`의 `TransactionTemplate`이 Worker Thread에서 외곽 Transaction을 만들고 Facade의 REQUIRED가 참여한다. 네이밍은 책임 위치를 알려주지만 실행 조건에 따른 실제 경계 판정은 트랜잭션 장에서 다룬다.

Facade 이름을 `mgcoa9000ServiceFacade`로 만들 필요는 없다. Facade 자체가 Service 호출 조정 책임을 뜻한다. 반대로 여러 프로그램을 한 `CommonFacade`에 모으면 Program ID로 업무 진입점을 찾는 연결이 끊어진다.

## 5.9 Service·Rule 명명법

Service는 `[Program ID]Service`로 이름을 만들고 public 거래 메서드는 Service ID를 사용한다. `mgcoa9000Service.mgcoa9000C0()`는 입력 검증, 중복 확인, DAO 등록 호출, 처리 결과 DTO 조립이라는 하나의 등록 Use Case를 수행한다.

Service 클래스명은 프로그램 경계를, 메서드명은 개별 거래 경계를 표현한다. `TransactionParameterService` 같은 의미 중심 이름도 일반 Java에서는 자연스럽지만, 현재 PDMG는 Program ID 추적성을 우선해 `mgcoa9000Service`를 표준으로 사용한다. 대신 Javadoc과 로그에서 “거래 파라미터 관리”라는 업무 의미를 보완한다.

Rule은 재사용하거나 독립 시험할 가치가 있는 업무 검증·계산 규칙을 표현한다. 이름에는 결과나 판단을 드러내는 구체적인 업무 용어를 사용하고 `Rule` 접미사를 붙인다. 예를 들어 “거래 ID 중복 허용 여부”라는 규칙이 분리된다면 의미 중심 본체가 필요하다. 단, 이는 설명을 위한 명명 예이며 현재 `mgcoa9000` 소스에는 별도 Rule 클래스가 없다.

Rule을 무조건 프로그램 접두만으로 `mgcoa9000Rule`이라고 만들면 어떤 판단을 하는지 알 수 없다. `Util`, `Helper`, `Manager`로 이름을 바꾸는 것도 해결책이 아니다. Service는 Use Case의 순서를 조정하고, Rule은 한 업무 정책을 검증하거나 계산한다. 이름이 이 책임 차이를 보여야 한다.

현재 `pdmg-service`에는 `application.rule` 구현이 확인되지 않는다. 그러므로 Rule 분리를 AS-IS라고 설명하지 않는다. 신규 업무가 단순 검증 몇 줄이라면 Service 내부의 의미 있는 private 메서드로 충분할 수 있다. 복수 Use Case에서 공유되거나 정책 변경과 독립 테스트가 중요한 경우에 Rule로 승격한다.

## 5.10 DTO 명명법

DTO는 거래 데이터의 방향과 구조를 이름에 포함한다.

```text
Request dto
  → mgcoa9000C0DTOin
     → Business Processing
        → mgcoa9000C0DTOout

목록 반복 행
  → mgcoa9000S0DTOSub0
```

`DTOin`은 거래 입력, `DTOout`은 거래 출력이다. `DTOSub0`은 목록이나 반복되는 하위 구조의 첫 번째 타입이다. 하위 구조가 여러 종류라면 순번을 늘리되, 단순히 파일을 나누기 위한 번호로 사용하지 않는다. 모든 DTO는 완전한 Service ID를 포함하므로 `mgcoa9000S0DTOin`과 `mgcoa9000C0DTOin`은 같은 프로그램이어도 별도 계약이다.

PDMG의 `DTOin`, `DTOout`, `DTOSub` 표기는 일반적인 `DtoIn`, `DtoOut`, `SubDto`와 다르다. 현재 `DataObject` 생성 패턴 및 기존 전문 계약과 호환하기 위한 프로젝트 예외다. 신규 코드가 일반 Java 스타일을 선호하더라도 한 프로그램 안에서 두 표기를 혼용하지 않는다.

AS-IS 생성 DTO에는 일반 camelCase 규칙의 예외가 있다. 목록 DTO의 `getmgcoa9000S0DTOSub0List`, `addmgcoa9000S0DTOSub0` 같은 생성 메서드는 일반 JavaBeans 형태와 다르다. 등록 결과에는 `PROC_CNT`, `RSLT_CD`, `RSLT_MSG` 같은 대문자 필드도 존재한다. 이를 현재 표준의 이상적인 예로 일반화해서는 안 된다.

신규 수기 DTO의 권장 기준은 Java 필드를 camelCase로 두고 외부 전문이 대문자 물리명을 요구하면 `@JsonProperty`나 명시적 메타데이터로 계약을 분리하는 것이다.

```java
@JsonProperty("PROC_CNT")
private Integer procCnt;
```

다만 생성기가 만드는 `DataObject`는 생성기 계약을 우선한다. 생성 결과를 수동으로 일부만 이름 변경하면 `clone`, `FieldProperty`, 직렬화와 화면 계약이 어긋날 수 있으므로 생성 템플릿을 함께 변경하거나 레거시 DTO는 그대로 유지한다.

## 5.11 DAO 명명법

DAO Interface는 `[Program ID]DAO`로 이름을 만든다. 실제 `mgcoa9000DAO`는 `nhnis.mg.co.a.persistence.dao`에 있고 `@RDWMapper`가 붙는다. 클래스 접두는 프로그램 단위이지만 메서드는 SQL Statement 단위다.

```java
List<Map<String, Object>> mgcoa9000S0_S0(Map<String, Object> input);
int mgcoa9000S0_S0_count(Map<String, Object> input);
int mgcoa9000S0_S0_exists(Map<String, Object> input);
int mgcoa9000C0_C0(Map<String, Object> input);
```

Service가 DAO를 호출할 때 이름만으로 어느 거래의 몇 번째 SQL인지 알 수 있다. `selectList`, `insertData`처럼 일반적인 이름을 쓰면 Java 호출부에서 Service ID와 SQL의 관계가 사라진다. PDMG DAO 메서드는 일반 저장소 메서드의 동사형 네이밍보다 SQL ID와의 기계적 일치를 우선한다.

DAO는 업무 판단을 이름에 숨기지 않는다. `validateAndInsertTransaction` 같은 메서드는 검증과 영속성 책임을 섞는다. 중복 여부 판단과 처리건수 판정은 Service나 Rule이 담당하고, DAO는 조회·등록·수정·삭제 Statement 호출 계약을 제공한다.

## 5.12 Mapper 파일명

Mapper XML 파일은 `[Program ID]-[DBMS].xml` 형식이다. 현재 RDW Oracle Mapper는 `mgcoa9000-ORA.xml`이며 `resources/rdw.mg.co.a/`에 있다. Program ID 단위로 한 파일에 네 거래의 Statement가 함께 존재한다.

`-ORA`는 대상 DBMS 방언을 표시한다. 이름만 `ORA`로 붙이고 다른 DB 문법을 혼용하면 파일명이 거짓 정보를 준다. DBMS별 Mapper를 분리해야 할 때 같은 Program ID를 유지하고 접미사로 방언을 구별하는 방식이 추적에 유리하다.

Mapper의 핵심 연결은 namespace다.

```xml
<mapper namespace="nhnis.mg.co.a.persistence.dao.mgcoa9000DAO">
```

namespace는 DAO의 FQCN과 완전히 일치해야 한다. 패키지를 옮기거나 DAO 이름을 바꾸면서 XML을 수정하지 않으면 MyBatis가 Interface 메서드에 대응하는 Statement를 찾지 못한다. 파일명은 사람이 찾는 규칙이지만 namespace와 Statement ID는 런타임 바인딩 계약이다.

## 5.13 SQL Statement ID

Statement ID는 기본적으로 `[Service ID]_[DML 코드][순번]`이다.

```text
mgcoa9000S0_S0
│             └─ 첫 번째 SELECT
└────────────── 조회 Service ID

mgcoa9000C0_C0   첫 번째 INSERT
mgcoa9000U0_U0   첫 번째 UPDATE
mgcoa9000D0_D0   첫 번째 DELETE
```

DAO 메서드명과 XML의 `id`는 한 글자도 다르면 안 된다.

```text
DAO FQCN
  nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
          ║ 완전 일치
Mapper namespace
  nhnis.mg.co.a.persistence.dao.mgcoa9000DAO

DAO method mgcoa9000S0_S0_count
          ║ 완전 일치
XML id     mgcoa9000S0_S0_count
```

현재 소스에는 기본 Statement 외에 `_count`와 `_exists` 보조 접미사가 있다. `_count`는 목록 전체 건수, `_exists`는 존재 여부 확인을 나타낸다. 원천 네이밍 문서 일부에는 `_exists`가 빠져 있으나 실제 `mgcoa9000DAO`와 Mapper에 존재하므로 AS-IS 규칙에 포함해야 한다.

Mapper 내부의 재사용 `<sql id="mgcoa9000Where">`는 DAO가 직접 호출하는 Statement가 아니다. 재사용 Fragment는 프로그램 접두와 역할을 결합한 의미 있는 이름을 사용한다. 호출 Statement와 같은 형식을 억지로 적용해 DAO 메서드가 있다고 오해하게 만들지 않는다.

바인딩 실패 시에는 세 값을 순서대로 확인한다. DAO Interface의 FQCN, Mapper namespace, DAO 메서드와 XML Statement ID다. 파일 위치만 맞다고 MyBatis 바인딩이 성립하는 것은 아니다.

장애 메시지에 `Invalid bound statement (not found)`가 나타나면 SQL 문법부터 수정하지 않는다. 먼저 오류에 표시된 `namespace.statementId`를 DAO 호출과 비교한다. namespace가 과거 패키지를 가리키는지, 메서드 이름의 대소문자나 `_count` 접미사가 다른지, 해당 Mapper 리소스가 실제 빌드 산출물에 포함됐는지를 차례로 확인한다. 이름 계약을 먼저 확인하면 SQL 실행 이전의 바인딩 오류와 DB가 반환한 SQL 오류를 빠르게 구분할 수 있다.

Statement를 이름만 바꾸는 변경도 DAO와 XML을 원자적으로 수정해야 한다. 한쪽만 먼저 배포할 수 있는 구조라면 구·신 Statement를 일정 기간 함께 제공하는 호환 전략이 필요하지만, 일반적인 단일 애플리케이션 빌드에서는 두 파일을 같은 변경 단위로 검증하는 것이 가장 단순하다.

## 5.14 Java 필드와 DB 컬럼

신규 Java 필드의 기본 표기는 camelCase이고 DB 컬럼은 UPPER_SNAKE_CASE다.

```text
DB TX_ID       ↔ Java txId
DB TX_NAME     ↔ Java txName
DB HTTP_METHOD ↔ Java httpMethod
DB REG_DTM     ↔ Java regDtm
```

그러나 현재 `mgcoa9000` 조회는 Mapper가 `resultType="java.util.HashMap"`을 반환한다. SQL Alias도 `TX_ID`, `TX_NAME`처럼 대문자 컬럼명이며, Service가 `asString(row, "TX_ID", "txId")` 같은 명시적 접근으로 값을 읽어 `mgcoa9000S0DTOSub0`의 camelCase 필드에 설정한다.

```text
TB_MG_TX_PARAM.TX_ID
   → SQL alias TX_ID
      → Map<String,Object>["TX_ID"]
         → Service 명시 변환
            → DTOSub0.txId
```

현재 확인 범위에서는 이 흐름을 DTO에 자동 변환하는 `mapUnderscoreToCamelCase` 설정에 의존하지 않는다. 따라서 “MyBatis가 모든 컬럼을 자동으로 camelCase DTO에 매핑한다”고 단정하면 안 된다. Mapper가 DTO resultType을 직접 사용할 경우에는 별도의 resultMap, Alias 또는 MyBatis 설정을 확인해야 한다.

쓰기 흐름은 반대다. Service가 camelCase Map Key `txId`, `txName`, `pathUrl`을 구성하고 Mapper의 `#{txId}`가 이를 DB 컬럼에 바인딩한다. Java 필드명, Map Key, Mapper 파라미터 이름이 다르면 값이 null로 전달되거나 BindingException이 발생할 수 있다.

레거시 출력 DTO의 `PROC_CNT` 같은 대문자 Java 필드는 DB 컬럼 규칙을 Java에 그대로 가져온 예외다. 신규 코드는 Java와 외부 물리명의 경계를 분리하는 편이 유지보수에 유리하지만, 기존 전문 호환이 필요한 필드는 무작정 변경하지 않는다.

## 5.15 오류 코드 명명법

오류 코드는 어느 계층에서 발생했는지보다 누가 소유하고 어떻게 운영할지를 식별해야 한다. 발생한 예외는 `exceptionCode.yml`의 코드와 메시지로 연결되고 공통 예외 처리기가 표준 오류 응답을 만든다. 5장에서는 전체 예외 흐름보다 코드 이름의 안정성과 유일성에 집중한다.

AS-IS `exceptionCode.yml`에는 세 형식이 함께 존재한다.

| 형식 | 현재 예 | 용도 해석 |
|---|---|---|
| 공통 숫자형 | `FW0001`, `FW0401`, `FW9999` | 공통·HTTP 성격 시스템 오류 |
| 업무 숫자형 | `MP0404`, `MP0409` | 특정 업무 영역 오류 |
| 기술 상태형 | `FW_TIMEOUT`, `FW_OVERLOADED` | 타임아웃·과부하 상태 |

따라서 “모든 오류는 `FW`+숫자 4자리”라고 쓰면 현재 구현과 충돌한다. 숫자형 코드는 소유 영역 접두와 고정 자릿수를 유지하고, 기술 상태형은 `FW_` 뒤에 UPPER_SNAKE_CASE를 사용한다. 신규 형식을 추가하기 전에 기존 코드 체계의 관리 원칙과 중복 여부를 확인해야 한다.

`mgcoa9000` Service는 현재 등록·수정 실패를 `RSLT_CD`, `RSLT_MSG` 결과 필드로 표현하며 전용 `exceptionCode.yml` 코드는 확인되지 않는다. 이 사실을 근거로 모든 업무 오류가 결과 DTO를 사용해야 한다고 일반화하지 않는다. 오류 코드와 정상 결과코드의 경계를 정하고, 예외를 표준화할 때는 26장의 예외처리 정책을 따른다.

좋은 오류 코드는 메시지 문장을 이름에 복사하지 않고 안정적인 원인을 나타낸다. `ERROR1`, `TEMP_ERROR`, `NEW_FW_ERROR`는 시간이 지나면 의미를 잃는다. 코드가 바뀌지 않아도 메시지는 다국어·운영 안내에 따라 변경될 수 있으므로 코드와 표현 문자열을 분리한다.

오류 코드 번호를 HTTP 상태코드처럼 보이게 정했다면 실제 의미와의 대응을 문서화해야 한다. `0404`가 언제나 HTTP 404를 뜻하는지, 단지 업무 미존재 범주를 뜻하는지 합의가 없으면 개발자마다 다르게 해석한다. 접두는 소유 영역, 숫자 또는 상태명은 오류 범주를 나타내고, 메시지는 사용자 안내를 담당하도록 각 역할을 분리한다.

코드를 폐기할 때도 즉시 다른 의미로 재사용하지 않는다. 과거 ImageLog나 운영 문서에 같은 코드가 남아 있으면 시점에 따라 의미가 달라진다. 오류 코드는 Service ID처럼 장기 추적 키이므로 유일성, 변경 이력과 폐기 상태를 관리할 필요가 있다.

## 5.16 금지하는 이름

금지와 지양을 구분해야 한다. `Util`이라는 문자열이 들어갔다는 이유만으로 모든 클래스를 오류로 판정하는 것이 아니라, 이름이 책임과 소유권을 설명하지 못할 때 문제다.

| 지양 이름 | 문제 | 권장 방향 |
|---|---|---|
| `Common`, `Etc`, `Misc` | 소유 업무와 경계가 없음 | 실제 업무 또는 기술 책임을 명시 |
| `Util`, `Utils`, `Helper` | 무엇을 돕는지 알 수 없음 | `DateRangeValidator`, `ServiceIdParser`처럼 기능 명시 |
| `Manager`, `Processor` | 조회·검증·조정·저장 중 책임 불명 | Use Case나 정책 행위를 표현 |
| `Data`, `Info`, `Object`, `Map` | 데이터 의미와 생명주기 불명 | `TransactionParameter`, `ControlRule`처럼 업무 명사 사용 |
| `Temp`, `Test`, `New`, `Old` | 시간에 의존하고 영구 코드에 남음 | 버전·역할·전환 목적을 명시 |
| `process1`, `doIt`, `handleData` | 입력과 결과를 예측할 수 없음 | 거래 메서드는 Service ID, 보조 메서드는 동사+대상 |

`CustomerManager`가 나쁜 이유는 “Manager가 금지어라서”가 아니다. 고객을 조회하는지, 상태를 변경하는지, 거래를 조정하는지, 외부 시스템과 동기화하는지 알 수 없기 때문이다. `Manager`가 프레임워크의 확립된 기술 역할이라면 예외가 될 수 있지만 업무 코드에서는 더 구체적인 책임을 선택한다.

PDMG에서 구조적으로 금지하거나 강하게 피해야 할 패턴은 다음과 같다.

- 프로그램 단위 클래스에 거래접미사를 넣은 `mgcoa9000S0Service`
- 거래 DTO에서 거래접미사를 뺀 `mgcoa9000DTOin`
- Handler에서 Service·DAO를 직접 호출하면서 이름만 `Handler`로 유지하는 구조
- DAO 메서드와 XML Statement ID를 다르게 작성하는 것
- Mapper namespace를 DAO FQCN과 다르게 작성하는 것
- Java 업무축 `mg.co.a`와 Mapper 축 `rdw.mg.co.b`를 다르게 두는 것
- 같은 프로그램 안에서 `DTOin`과 `DtoIn`, `DAO`와 `Dao`를 혼용하는 것
- 레거시 예외 이름을 근거 없이 신규 표준으로 복제하는 것

좋은 이름도 과도하게 길면 읽기 어렵다. 모든 구현 세부를 클래스명에 넣기보다 프로그램 접두와 계층 접미사를 표준대로 사용하고, 업무 의미는 Javadoc과 메서드 내부의 의미 있는 변수·Rule 이름으로 보완한다.

## 5.17 신규 프로그램 네이밍 체크리스트

신규 프로그램 이름은 파일을 복사하면서 하나씩 고치는 방식보다 위에서 아래로 결정해야 한다. 다음 절차는 각 단계의 입력, 판단, 결과와 검증 방법을 함께 제시한다.

### STEP 1. 업무 영역을 확정한다

입력은 업무 요구사항과 데이터 소유권이다. 어느 조직이 규칙과 장애 복구를 책임지는지를 기준으로 대그룹·업무·세부업무 코드를 정한다. 결과는 `mg/co/a` 같은 분류축이며 분류표에 실제로 존재하는지 검증한다.

### STEP 2. Program ID를 배정한다

분류축 안에서 네 자리 번호를 선택해 `mgcoa9010` 같은 Program ID를 만든다. 이 값은 개념 예시이며 실제 배정 가능 번호가 아니다. 저장소 전체와 병렬 개발 목록에서 중복을 검색하고 프로그램 경계가 기존 Program ID에 속하지 않는지 검토한다.

### STEP 3. Service ID를 만든다

핵심 행위가 조회·등록·수정·삭제·실행·보고서 중 무엇인지 판단해 거래구분과 순번을 붙인다. 조회 예시는 `mgcoa9010S0`이다. 11자 형식뿐 아니라 거래구분과 실제 부수효과가 일치하는지 검증한다.

### STEP 4. 패키지 업무축을 결정한다

Service ID 앞 다섯 글자에서 `nhnis.mg.co.a`와 `rdw.mg.co.a`를 유도한다. 현재 모듈이 사용하는 계층 패키지를 선택하되 6장의 구조와 Scan 범위를 확인한다. Java와 Mapper 업무축이 같은지 비교한다.

### STEP 5. 프로그램 단위 타입을 결정한다

TCF ON Handler는 `mgcoa9010Handler`, 현재 PDMG Facade는 `mgcoa9010Facade`, Service는 `mgcoa9010Service`, DAO는 `mgcoa9010DAO`다. TCF OFF 호환이 필요하면 `mgcoa9010Controller`를 추가한다. 클래스명에는 `S0`를 넣지 않는다.

### STEP 6. 거래 메서드와 URL을 결정한다

Handler 상수·분기, Facade와 Service public 메서드, Controller 메서드와 URL에 완전한 `mgcoa9010S0`를 사용한다. 요청 헤더 `rms_svc_c`와 샘플 전문도 같은 값인지 검색으로 검증한다.

### STEP 7. DTO 이름을 결정한다

입력은 `mgcoa9010S0DTOin`, 출력은 `mgcoa9010S0DTOout`, 목록 행이 필요하면 `mgcoa9010S0DTOSub0`이다. 필드는 camelCase를 기본으로 하고 외부 물리명이 다르면 명시적 매핑을 설계한다. 생성 DTO라면 생성기 계약을 먼저 확인한다.

### STEP 8. Rule 필요성을 판단한다

독립적인 업무 검증이나 계산이 재사용·독립 시험될 가치가 있는지 본다. 필요하면 행위를 설명하는 구체적인 이름에 `Rule`을 붙인다. 단순히 Service가 길다는 이유만으로 `mgcoa9010Rule`이나 `CommonHelper`를 만들지 않는다.

### STEP 9. DAO와 Mapper 이름을 결정한다

Mapper 파일은 `mgcoa9010-ORA.xml`, namespace는 DAO FQCN이다. 조회 Statement 첫 번째는 `mgcoa9010S0_S0`, 건수는 `_count`, 존재 확인은 `_exists`를 붙인다. DAO 메서드와 XML ID를 문자 단위로 비교한다.

### STEP 10. 필드와 컬럼 매핑을 정의한다

요구 전문의 Java 필드, DAO Map Key, Mapper 파라미터, DB 컬럼을 한 표로 만든다. 자동 camelCase 변환을 가정하지 말고 실제 resultType, Alias, resultMap과 설정을 확인한다.

### STEP 11. 오류 코드를 결정한다

정상 결과코드인지 예외 오류코드인지 먼저 구분한다. `exceptionCode.yml`의 기존 접두와 번호를 검색하고 소유 업무에 맞는 형식을 사용한다. 현재 혼재 형식을 새로 늘리지 않도록 아키텍처 승인을 받는다.

### STEP 12. 전체 Chain을 검증한다

Program ID로 검색해 모든 프로그램 단위 타입을 확인하고, Service ID로 검색해 URL·메서드·DTO·Statement·샘플 전문을 확인한다. 애플리케이션 기동으로 Handler 중복을, MyBatis 통합 테스트로 namespace와 Statement 바인딩을 확인한다. UI 카탈로그와 운영 통제 대상도 함께 점검한다.

TO-BE 자동 검증은 한 번에 거대한 규칙을 만들기보다 실패 비용이 큰 계약부터 시작한다. 첫째, Handler Service ID의 11자 형식과 중복을 검사한다. 둘째, DAO FQCN과 Mapper namespace, DAO 메서드와 Statement ID의 차이를 검사한다. 셋째, Program ID 접두와 패키지 업무축의 일치를 검사한다. 마지막으로 UI 카탈로그와 백엔드 Registry의 차이를 허용 목록과 비교한다.

ArchUnit은 패키지와 클래스 접미사의 관계 및 금지 의존을 검사하는 데 적합하고, Gradle 사용자 Task는 XML과 Java 선언을 교차 검증하는 데 적합하다. 코드 생성기는 검사를 대체하지 않는다. 템플릿 자체가 오래되었거나 생성 후 수동 변경이 들어갈 수 있으므로 CI에서 최종 산출물을 다시 검사해야 한다.

| 생성 DTO 메서드 | 비표준 camelCase 존재 | 생성기 계약 유지, 템플릿 단위 개선 |
| SQL 보조 ID | `_count`, `_exists` 사용 | 문서·검증 규칙에 모두 반영 |

### 아키텍처 판단 포인트

- 이름만 보고 업무축, Program ID, Service ID와 계층 책임을 설명할 수 있는가?
- 프로그램 단위 클래스와 거래 단위 DTO·메서드를 구분했는가?
- Handler와 Controller가 TCF ON/OFF 진입 책임만 갖는가?
- Service와 Rule의 책임이 `Util`, `Manager` 같은 모호한 이름으로 숨지 않았는가?
- DAO FQCN과 namespace, DAO 메서드와 Statement ID가 완전히 일치하는가?
- DB 컬럼과 Java 필드의 변환 방법을 실제 Mapper 설정으로 확인했는가?
- 레거시 DTO와 오류 코드의 예외를 신규 표준으로 복제하지 않았는가?

네이밍은 코드가 완성된 뒤 맞춤법처럼 검사하는 마지막 단계가 아니다. 업무 요구를 Program ID와 Service ID로 고정하고, 그 식별자를 모든 계층에 일관되게 투영하는 설계의 첫 단계다. 이 Chain이 명확하면 사람과 자동화 도구 모두 같은 방식으로 소스를 생성하고 추적할 수 있다.

다음 장에서는 여기서 결정한 `nhnis.mg.co.a`, `entry.handler`, `application.service`, `persistence.dao` 같은 이름이 실제 프로젝트 디렉터리와 Spring Scan 경계 안에 어떻게 배치되는지 살펴본다.
