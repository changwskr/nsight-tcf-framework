# 제5부 트랜잭션과 타임아웃

# 22장. PDMG 트랜잭션 경계

PDMG에서 “트랜잭션은 어디서 시작되는가”라는 질문에는 하나의 답이 없다. TCF와 Timeout 설정, 실제 호출한 Controller, 대상 Service의 Annotation에 따라 최외곽 경계가 달라진다. 특히 TCF ON + Timeout ON에서는 Facade보다 먼저 Worker Thread의 `TransactionTemplate`이 거래를 시작한다.

이 장은 HTTP 요청 범위와 DB Transaction 범위를 구분한다. Filter와 Interceptor가 먼저 실행됐다고 해서 그 작업이 업무 DB 거래에 포함되는 것은 아니다. 반대로 Handler에 Annotation이 없어도 Worker가 바깥 거래를 열었다면 Handler는 Transaction 안에서 실행될 수 있다.

## 이 장에서 해결할 질문

- 세 가지 주요 실행 조건에서 실제 최외곽 BEGIN과 완료 주체는 누구인가?
- Facade의 `@Transactional`은 언제 시작점이고 언제 참여자인가?
- BizPrePostAspect의 선처리·정상 후처리는 어떤 조건에서 업무 TX 안에 있는가?
- 시스템 선후처리와 ImageLog는 업무 데이터 변경과 함께 Rollback되는가?
- TCF OFF의 Service 직접 호출은 모두 같은 Transaction 정책을 가지는가?
- 여러 DataSource와 새 Thread를 하나의 로컬 거래라고 볼 수 있는가?

## 실행 조건별 결론

| 조건 | 실행 Thread | 최외곽 DB TX | Facade 역할 |
|---|---|---|---|
| TCF ON + Timeout ON | Worker | `DefaultOnlineTimeoutExecutor`의 `TransactionTemplate` | REQUIRED 참여 |
| TCF ON + Timeout OFF | Request | 업무 Facade Proxy | 새 TX 시작 가능 |
| TCF OFF, Controller→Facade | Request | 업무 Facade Proxy | 새 TX 시작 가능 |
| TCF OFF, Controller→Service | Request | Service Annotation에 따라 다름 | 실행되지 않음 |

이 표는 “Annotation이 보이는 위치”가 아니라 실제 호출선과 Proxy·Thread를 기준으로 판정한 결과다.

## 22.1 트랜잭션은 어디에서 시작되는가

TCF ON 요청은 `OnlineTransactionController → TcfFacade → OnlineTimeoutExecutor → Dispatcher → Handler → 업무 Facade`로 이동한다. `TcfFacade.process` 자체에는 Transaction Annotation이 없고 Executor에 Callable을 전달한다.

Timeout ON의 `DefaultOnlineTimeoutExecutor`는 Worker Pool에 작업을 submit하고 Worker의 `runInWorker`에서 `transactionTemplate.execute`를 호출한다. 그 안의 `action.call()`이 Dispatcher 이하 전체다.

```text
Request Thread                   Worker Thread
TcfFacade
  └─ submit ───────────────────▶ TransactionTemplate BEGIN
                                  Dispatcher → Handler → Facade
                                  → Service → DAO
                                  COMMIT / ROLLBACK
```

Timeout OFF의 `SyncOnlineTimeoutExecutor`는 현재 Thread에서 `action.call()`만 실행하며 Transaction을 만들지 않는다. 따라서 Handler가 Facade Proxy에 진입할 때 Facade Annotation이 시작점이 된다.

TCF OFF는 업무 Controller의 실제 호출 대상을 봐야 한다. 현행 대부분은 Service를 직접 호출하고 `mgcoa9100Controller`는 Facade를 호출한다. 직접 호출 Service에 Annotation이 없다면 명시적 업무 Transaction이 없을 수 있고, `mgcoa9001Service`처럼 Annotation이 있으면 Service Proxy가 경계가 된다.

## 22.2 Facade 트랜잭션

주요 Facade는 `rdwTransactionManager`를 지정하고 조회 readOnly 또는 쓰기 rollbackFor를 선언한다. 기본 propagation은 REQUIRED다.

Timeout ON에서는 Worker가 같은 manager로 이미 TX를 열었으므로 Facade는 새 물리 거래를 만들지 않고 참여한다. Facade가 반환해도 Commit은 아직 Worker TransactionTemplate가 결정한다. Worker는 Facade 이후 deadline과 interrupt도 검사한다.

Timeout OFF에서는 외부 TX가 없으므로 Facade Proxy가 새 거래를 시작한다. DTO 변환도 Proxy 내부이므로 변환 실패는 거래 완료 판단에 들어간다. OFF Controller가 Facade를 호출할 때도 같은 원리다.

Facade라는 클래스명만으로 경계를 보장하지 않는다. Spring Bean Proxy 외부 호출이어야 하며, `new`로 만든 객체나 자기 호출은 Annotation을 적용하지 못한다.

## 22.3 업무 선처리의 트랜잭션 참여

현행 BizPrePostAspect Pointcut은 Service public 메서드다. `@Before`가 실행될 때 외부 거래가 이미 존재하는 조건이면 선처리는 그 Thread의 Transaction 안에 있다.

```text
Worker/Facade TX BEGIN
  → Facade DTO 변환
  → Service Proxy
      → BizPre @Before
      → Service
      → BizPost @AfterReturning
  → TX 완료
```

Aspect의 `@Order(100)`이 참여를 만드는 것은 아니다. Transaction이 먼저 열렸고 같은 Thread에서 Service Proxy를 호출하기 때문에 참여한다. OFF Service 직접 호출에서 Service 자체 TX가 없다면 선처리 로그는 실행되어도 업무 TX는 없을 수 있다.

현재 선처리는 DB 작업이 아니라 로그다. 향후 사전 UPDATE를 넣으면 readOnly 조회와 모든 Service 적용 범위를 검토하고 예외를 전파해야 한다.

## 22.4 Service와 DAO의 참여

Service가 호출하는 DAO Proxy는 `rdwSqlSessionTemplate`을 사용한다. 이 Template과 TransactionManager가 동일 `rdwDataSource`를 사용하므로 현재 Thread의 RDW Connection에 참여한다.

Service에 별도 REQUIRED Annotation이 있어도 외부 Worker 또는 Facade TX가 있으면 일반적으로 참여한다. 외부가 없으면 Service가 새 경계를 만들 수 있다. `mgcoa9001Service`의 Annotation은 TCF OFF 직접 호출에서 특히 의미가 있다.

DAO 예외가 밖으로 전파되면 최외곽 소유자가 Rollback한다. DAO가 예외를 0이나 빈 목록으로 바꾸면 Service가 정상 반환하고 Commit될 가능성이 있다.

## 22.5 업무 후처리의 참여

현재 업무 후처리는 `@AfterReturning`이므로 Service 정상 반환 때만 실행된다. 외부 거래가 있다면 Service가 반환된 뒤이면서 Commit 전이라 같은 거래 안이다.

후처리에서 같은 RDW DAO로 UPDATE를 추가하면 같은 Thread·Manager·DataSource·REQUIRED 조건에서 본 업무와 함께 Commit/Rollback된다. 후처리 UPDATE 실패를 catch해 숨기면 본 업무만 Commit될 수 있다.

Service 예외 시 현행 정상 후처리는 실행되지 않는다. 오류 이력 저장은 현재 Aspect에 구현되어 있지 않다. 독립 이력이 필요하면 별도 Bean과 REQUIRES_NEW를 설계하되 원래 예외를 재전파한다.

## 22.6 시스템 선처리와 트랜잭션

DefaultFilter와 `ServicePreventionInterceptor.preHandle`은 Controller·TcfFacade 이전 Request Thread에서 실행된다. GUID·Header·ServiceContext 보완, 요청 로그와 ImageLog 사전 처리를 수행하지만 업무 Worker Transaction은 아직 시작되지 않았다.

따라서 시스템 선처리를 업무 데이터 변경과 같은 TX로 간주하지 않는다. 시스템 선처리에서 업무 테이블을 갱신하면 뒤 업무가 Rollback되어도 그 변경이 자동으로 함께 Rollback되지 않을 수 있다.

TCF의 STF 클래스가 존재하더라도 현재 `TcfFacade` 호출선에는 STF 호출이 보이지 않는다. 설계 다이어그램의 STF를 AS-IS Transaction 범위에 넣지 않는다.

## 22.7 시스템 후처리와 트랜잭션

응답 조립과 시스템 후처리 로그는 ResponseBodyAdvice와 Interceptor 완료 구간에서 이루어진다. TCF 업무 실행이 정상 반환했다면 Worker 또는 Facade 거래는 이미 완료되는 방향으로 진행한 뒤 HTTP 응답 계층으로 돌아온다.

시스템 후처리를 업무 Commit 전의 같은 DB 거래라고 가정해서는 안 된다. Response 직렬화 실패가 이미 Commit된 업무를 자동 Rollback하지 못할 수 있다. 응답 생성 오류와 업무 DB 원자성을 하나로 묶으려면 완전히 다른 경계 설계가 필요하다.

현행 TcfFacade에는 ETF 직접 호출도 없다. 문서의 STF/ETF 흐름은 설계 의도와 현재 호출선을 구분한다.

## 22.8 이미지로그 트랜잭션

ImageLog의 pre 처리는 Interceptor preHandle, post/exception 처리는 afterCompletion 등 시스템 요청 수명에서 호출된다. 업무 Worker TX의 안쪽 Service Advice가 아니다.

`ImageLogHandler`는 저장 예외를 catch하고 로그를 남기는 fail-open 성격이 확인된다. 이미지로그 실패가 업무 성공을 Rollback시키지 않도록 분리된 것이다. 반대로 업무 실패와 함께 이미지로그가 자동 취소된다고 기대해서도 안 된다.

같은 RDW DataSource를 사용한다는 사실만으로 같은 Transaction은 아니다. 호출 Thread와 시점에 활성 거래가 있는지 확인해야 한다. Request Thread의 ImageLog와 Worker Thread의 업무 Transaction은 특히 분리해 본다.

## 22.9 여러 DAO를 묶는 방법

여러 DAO 작업을 원자적으로 묶으려면 가장 바깥 유스케이스 경계 안에서 순서대로 호출하고 예외를 숨기지 않는다.

```text
TX BEGIN
  Service
    ├─ DAO A UPDATE
    ├─ DAO B INSERT
    └─ DAO C UPDATE
  하나라도 실패 → 예외 전파
COMMIT 또는 전체 ROLLBACK
```

모든 DAO가 동일 RDW DataSource와 Manager, 같은 Thread를 사용해야 한다. 두 번째 실패를 결과 코드로만 바꾸면 첫 번째가 Commit될 수 있다. 처리 건수 0을 업무 실패로 볼 때도 Service가 예외 또는 rollback-only 정책을 명확히 해야 한다.

## 22.10 여러 DataSource 처리

현행 업무 축에서 확인된 로컬 관리자는 RDW `DataSourceTransactionManager`다. 이 관리자는 하나의 DataSource를 관리한다. 다른 DataSource의 Connection은 자동으로 같은 물리 거래에 묶이지 않는다.

여러 DB를 원자적으로 처리하려면 JTA/XA 같은 분산 Transaction 또는 Saga·Outbox·보상 설계가 필요할 수 있다. 현재 JTA가 구현되었다는 근거는 확인되지 않으므로 AS-IS라고 쓰지 않는다.

외부 HTTP 호출도 RDW Rollback 대상이 아니다. 원격 성공 후 로컬 실패를 대비해 멱등과 보상 정책을 둔다.

## 22.11 전파 속성

현행 주요 Annotation과 Worker TransactionTemplate는 REQUIRED를 사용한다. 외부 거래가 있으면 참여하고 없으면 새 거래를 만든다. 이것이 ON/Timeout 조합에서 같은 Facade가 다른 역할을 하는 원인이다.

REQUIRES_NEW는 기존 거래를 보류하고 독립 거래를 만든다. 원거래 Rollback 후에도 남아야 하는 오류 이력에 사용할 수 있지만 새 Connection, Lock 대기와 실패 격리를 고려한다. 현행 업무 선후 Aspect에는 이 기능이 없다.

SUPPORTS, NOT_SUPPORTED 등 다른 전파는 일반 원리로 존재하지만 현재 핵심 업무 경계에서 확인되지 않는다. 필요 없이 추가해 경계를 복잡하게 만들지 않는다.

## 22.12 자기 호출 문제

Facade 또는 Service 안에서 `this.inner()`로 다른 Transaction 메서드를 호출하면 Spring Proxy를 다시 통과하지 않는다. inner의 REQUIRES_NEW, readOnly 또는 timeout이 적용되지 않는다.

독립 경계가 필요하면 다른 Spring Bean으로 분리하고 외부 Proxy 호출을 만든다. 자기 자신 주입으로 우회하기보다 유스케이스와 책임을 분리한다.

현행 주요 Facade에서 Transaction 자기 호출 패턴은 확인되지 않았지만 신규 복합 업무에서 반드시 점검한다.

## 22.13 비동기 Thread와 트랜잭션

Spring Transaction은 Thread-bound다. Facade TX 안에서 임의 비동기 작업을 submit하면 새 Thread가 기존 Connection과 rollback 상태를 자동 공유하지 않는다.

```text
Thread A: TX BEGIN → async submit → COMMIT/ROLLBACK
Thread B:                 독립 실행, 기존 TX 없음
```

PDMG Timeout ON은 이 제약을 회피하는 것이 아니라 Worker Thread 안에서 처음부터 새 TransactionTemplate를 시작하는 구조다. Request Thread에는 그 업무 Connection이 없다. Context는 별도 WorkerContext가 캡처·설치한다.

비동기 후처리가 원 업무와 원자적이어야 한다면 비동기로 분리하면 안 된다. 독립 작업이라면 별도 거래, 재시도와 중복 방지 정책을 둔다.

## 22.14 TCF ON/OFF 비교

### TCF ON + Timeout ON

```text
Request: Filter → Interceptor → Controller → TcfFacade → Future.get
Worker : TX BEGIN → Dispatcher → Handler → Facade(join)
         → BizPre → Service → DAO → BizPost
         → deadline 검사 → COMMIT/ROLLBACK
Request: ResponseBodyAdvice → afterCompletion
```

### TCF ON + Timeout OFF

```text
Request Thread
Filter → Interceptor → Controller → TcfFacade → Sync Executor
→ Dispatcher → Handler → Facade TX BEGIN
→ BizPre → Service → DAO → BizPost → COMMIT/ROLLBACK
→ ResponseBodyAdvice → afterCompletion
```

### TCF OFF

```text
대부분: 업무 Controller → Service Proxy → DAO
        TX는 Service Annotation별 판정

일부:   업무 Controller → Facade Proxy → Service → DAO
        Facade가 TX 시작 가능
```

OFF라고 해서 항상 무트랜잭션도, 항상 Service TX도 아니다. Controller별 실제 호출 대상과 Service Annotation을 검사한다.

## 정상·실패 타임라인

정상 Timeout ON은 Worker가 모든 업무와 정상 후처리를 끝내고 deadline을 통과한 뒤 Commit한다. Request Thread는 Future 결과를 받아 시스템 응답을 조립한다.

Service 또는 DAO 예외는 Worker TransactionTemplate까지 전파되어 rollback-only와 Rollback으로 이어진다. Request Thread Timeout은 `cancel(true)`를 요청하지만 DB 작업이 즉시 멈추고 Rollback이 완료됐다고 단정할 수 없다. 이 상세는 다음 장에서 다룬다.

시스템 ImageLog 실패는 일반적으로 업무 예외로 전파되지 않는다. 업무 성공과 관찰 로그 성공은 별도 상태가 될 수 있다.

## 책임과 경계 표

| 구성 요소 | Thread | 업무 TX 관계 | 책임 |
|---|---|---|---|
| Filter/Interceptor | Request | 밖 | 시스템 요청 선처리 |
| Default Timeout Executor | Worker | 소유 | Dispatcher 이하 최외곽 TX |
| Sync Executor | Request | 생성 안 함 | 동기 Callable 실행 |
| Business Facade | 호출 Thread | 시작 또는 참여 | 유스케이스 TX 선언 |
| BizPrePostAspect | Service Thread | 조건부 참여 | 업무 전후 로그 |
| DAO | Service Thread | 현재 RDW TX 참여 | SQL 실행 |
| Response Advice/afterCompletion | Request | 일반적으로 밖 | 응답·시스템 후처리 |

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | Timeout ON Worker TransactionTemplate가 Dispatcher 이하를 감쌈 |
| AS-IS | Timeout OFF Sync Executor는 TX를 만들지 않아 Facade가 시작 가능 |
| AS-IS | OFF 다수 Controller는 Service 직행, mgcoa9100은 Facade 호출 |
| AS-IS | BizPre/@AfterReturning은 Service Pointcut, 외부 TX 조건에서 참여 |
| AS-IS | Filter·Interceptor·Response Advice와 ImageLog는 업무 Worker TX 밖 |
| AS-IS | TcfFacade에 STF·ETF 직접 호출 없음 |
| TO-BE | OFF Controller를 Facade로 수렴하고 모드별 동등성 테스트 |
| TO-BE | 거래 메타데이터로 Worker readOnly 등 TX 속성 선택 검토 |

## Anti Pattern

모든 그림에 Facade BEGIN을 고정하거나 Handler에 Annotation이 없으므로 TX 밖이라고 결론 내리면 안 된다. HTTP 요청 수명 전체가 DB Transaction이라고 가정해 시스템 후처리 실패로 업무가 Rollback될 것이라 믿는 것도 오류다.

Future 취소만으로 DB Rollback 완료를 선언하거나, 새 Thread가 기존 TX에 참여한다고 가정하지 않는다. 여러 DataSource를 동일 Manager 이름만으로 원자적으로 묶을 수도 없다. 예외를 catch해 성공값으로 바꾸면 경계 설계가 무너진다.

## 실전 검증 시나리오

네 경로별로 실제 Transaction 활성 상태, Thread 이름과 Manager를 기록하는 통합 테스트를 만든다. Timeout ON에서는 Dispatcher·Handler·Facade·Service·DAO가 같은 Worker TX인지 확인한다. Timeout OFF에서는 Facade 진입 전후를, OFF에서는 Controller별 호출 대상과 Service Annotation을 검증한다.

업무 후처리 UPDATE를 추가한 테스트는 Service 정상 시 함께 Commit, 후처리 실패 시 본 업무까지 Rollback되는지 확인한다. 시스템 ImageLog 실패는 업무 DB 결과에 영향을 주지 않는지 확인한다. 여러 DAO 두 번째 실패와 checked Exception도 포함한다.

## 개발자·운영자 체크리스트

- TCF·Timeout 설정과 실제 Executor Bean을 확인했는가?
- Request와 Worker Thread 로그를 GUID로 연결했는가?
- 최외곽 owner와 내부 REQUIRED 참여자를 구분했는가?
- OFF Controller의 실제 Facade/Service 호출을 확인했는가?
- BizPrePost가 Service Pointcut이며 정상 후처리만 있다는 점을 반영했는가?
- 시스템 선후·ImageLog를 업무 TX로 오해하지 않는가?
- 여러 DAO가 같은 RDW DataSource·Thread를 사용하는가?
- 다른 DataSource·외부 호출에 보상 정책이 있는가?
- 자기 호출과 비동기 분리로 Proxy/TX를 우회하지 않는가?
- 예외·Timeout에서 DB 상태를 통합 테스트로 확인했는가?

## 아키텍처 판단 포인트와 다음 장

최외곽 Transaction은 코드 위치가 아니라 원자성 요구, Thread와 timeout 취소 모델로 결정한다. PDMG Timeout ON은 Worker 안에서 전체 업무를 묶어 늦은 Commit을 방어한다. OFF 경로는 같은 Facade로 수렴시킬수록 경계 차이가 줄어든다.

시스템 관찰 데이터는 업무 원자성과 분리할지 의도적으로 결정한다. 반드시 남아야 하는 로그는 원거래와 독립해야 하지만, 실패 격리와 저장 신뢰성을 별도로 보장해야 한다.

다음 장에서는 Request Thread의 대기 제한, Worker의 실제 실행, `Future.cancel(true)`, interrupt와 JDBC 중단 한계, deadline 재검사와 Rollback 완료 시점을 분석한다.
