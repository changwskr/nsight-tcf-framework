# 제5부 데이터 접근과 대용량 처리

# 20장. 대용량 조회와 페이징

목록 조회는 데이터가 적을 때는 단순해 보인다. 하지만 행 수가 수백만 건으로 늘어나면 전체 결과를 애플리케이션으로 읽은 뒤 일부만 자르는 방식은 DB, Heap, 네트워크와 응답 시간을 동시에 소모한다. PDMG는 요청받은 페이지 범위만 DB에서 잘라 반환하는 Offset 기반 페이징을 사용한다.

현재 구현은 pageNo와 pageSize를 Service에서 보정하고 `offset`을 계산한 다음 COUNT와 목록 SQL을 차례로 호출한다. Mapper는 Oracle ROWNUM 이중 래핑을 사용한다. 기본적인 서버 페이징은 적용되어 있지만 int overflow, 깊은 페이지, COUNT 비용, 동시 변경에 따른 페이지 흔들림과 큰 행 크기는 별도의 운영 한계다.

## 이 장에서 해결할 질문

- 현재 PDMG의 입력·출력 페이징 계약은 무엇인가?
- 목록과 COUNT가 같은 검색 조건을 사용해야 하는 이유는 무엇인가?
- Oracle ROWNUM 이중 Query는 정렬 후 어떤 행을 잘라 내는가?
- `offset = (pageNo - 1) * pageSize`가 언제 overflow하는가?
- pageSize 100 제한만으로 모든 대용량 위험을 막을 수 있는가?
- Offset 대신 Keyset·Cursor를 선택해야 하는 기준은 무엇인가?
- 정렬과 복합 Index는 결과 안정성과 성능에 어떻게 연결되는가?

## 전체 실행 흐름

```text
요청 DTO(pageNo, pageSize, 검색조건)
  → Service 보정
  → offset 계산
  → DAO COUNT
  → DAO 목록
  → Oracle ORDER BY + ROWNUM 범위
  → DTOSub 목록
  → DTOout(size, pageNo, pageSize, totalCount, totalPages)
  → SQL 시간·응답 크기 검증
```

## 20.1 페이징 계약

PDMG의 기본 목록 계약은 페이지 번호 방식이다. 클라이언트는 1부터 시작하는 pageNo와 한 페이지 행 수 pageSize를 보낸다. Service는 실제 적용값을 결정하고 DB 전용 offset을 만든다. 응답은 현재 페이지 목록과 전체 건수·페이지 수를 함께 제공한다.

현행 페이징 구현은 `mgcoa5530S0`, `mgcoa8888S0`, `mgcoa9000S0`, `mgcoa9001S0` 네 거래에서 확인된다. 이전 문서의 세 거래 목록에는 이후 거래통제 조회가 빠져 있다. 실제 패키지 검색을 기준으로 현행화해야 한다.

이 계약은 임의 페이지 이동과 “전체 N건 중 M페이지” UI에 적합하다. 대신 매 요청 COUNT와 깊은 Offset 비용을 감수한다. 모든 데이터를 DAO에서 받은 뒤 Java `subList`로 자르는 것은 이 계약이 아니다.

## 20.2 입력 DTO

목록 DTOin은 업무 검색조건과 `Integer pageNo`, `Integer pageSize`를 가진다. offset은 외부 입력이 아니다. 클라이언트가 offset을 직접 조작하게 두면 pageNo와 모순되고 내부 SQL 전략을 공개 계약으로 고정하게 된다.

Service는 null 또는 0 이하 pageNo를 1로 보정한다. pageSize도 null·0 이하면 거래별 기본값을 사용하고 100을 넘으면 100으로 제한한다. 실제 기본값은 동일하지 않다.

| 거래 | 기본 pageSize | 최대 |
|---|---:|---:|
| `mgcoa5530S0` | 20 | 100 |
| `mgcoa8888S0` | 20 | 100 |
| `mgcoa9000S0` | 10 | 100 |
| `mgcoa9001S0` | 20 | 100 |

따라서 “PDMG 기본은 항상 20”이라고 단정하지 않는다. mgcoa9000의 10이 업무 의도인지 오래된 불일치인지 결정한 뒤 문서·UI 기본값을 맞춰야 한다.

검색조건은 COUNT와 LIST에 동일하게 적용되어야 한다. trim, 기간 상한, boolean 필터 같은 정규화를 Service가 한 번 수행해 같은 Map을 두 DAO 호출에 전달하는 현재 방식은 조건 불일치 위험을 줄인다.

## 20.3 출력 DTO

목록 DTOout은 `DTOSub0` 목록, `size`, 실제 pageNo·pageSize, `totalCount`, `totalPages`를 가진다. size는 이번 응답의 행 수이고 totalCount는 검색조건 전체의 행 수다. 마지막 페이지에서는 size가 pageSize보다 작을 수 있다.

전체 페이지는 다음 식으로 계산한다.

```text
totalPages = (totalCount + pageSize - 1) / pageSize
```

현행 코드는 덧셈을 long으로 승격한 뒤 int로 변환해 중간 덧셈 overflow를 일부 피한다. 다만 DAO count 반환과 일부 DTO total 표현이 int 범위에 묶인 경우 초대용량 전체 건수에는 한계가 있다.

0건은 보통 오류가 아니라 빈 목록, size 0, totalCount 0, totalPages 0이다. 생성형 DTO의 목록이 null로 직렬화될지 빈 배열이 될지는 실제 Advice 결과와 UI 계약으로 고정해야 한다.

## 20.4 전체 건수 조회

COUNT Statement는 페이지 제한 없이 같은 WHERE의 전체 행 수를 구한다. 화면의 페이지 수 계산에는 필요하지만 대형 테이블과 낮은 선택도의 검색에서는 목록보다 COUNT가 더 비쌀 수 있다.

현행 Mapper는 `<sql id="...Where">` 조각을 COUNT와 LIST에서 함께 include한다. 조건을 한쪽에만 추가해 “totalCount는 100인데 목록은 3건” 같은 불일치를 막는 좋은 구조다. 다만 동적 SQL뿐 아니라 JOIN과 보안 조건도 같아야 한다.

정확한 전체 건수가 항상 필요한지 업무와 합의한다. 무한 스크롤이라면 `hasNext`를 위해 pageSize+1건만 읽을 수 있고, 매우 큰 관리 화면은 상한 표시·캐시된 통계·비동기 집계를 사용할 수 있다. 이는 TO-BE 대안이며 현재 네 거래는 별도 COUNT를 실행한다.

## 20.5 목록 조회

LIST SQL은 검색 집합을 정렬한 다음 `offset + pageSize`까지만 내부에서 번호를 매기고 offset 이하를 바깥에서 제거한다. DB가 현재 페이지 행만 애플리케이션에 반환하므로 Heap과 네트워크를 제한한다.

행 크기도 중요하다. `mgcoa8888S0`는 요청·응답 전문처럼 큰 문자열 컬럼을 포함한다. 100행 제한이라도 각 행이 크면 응답 JSON과 메모리가 커진다. 목록에는 요약 필드만 제공하고 상세 전문은 단건 조회로 분리하는 설계를 검토할 수 있다.

목록 SELECT에서 필요한 컬럼만 지정하고 안정적인 ORDER BY를 사용한다. `SELECT *`는 ROWNUM 래핑의 외부 Query 구조에는 쓰이지만 실제 내부 업무 컬럼은 명시되어 있다.

## 20.6 Oracle ROWNUM 페이징

현행 SQL의 핵심은 세 단계다.

```sql
SELECT * FROM (
  SELECT a.*, ROWNUM rnum
    FROM (
      SELECT 필요한_컬럼
        FROM 업무테이블
       WHERE 검색조건
       ORDER BY 고정정렬
    ) a
   WHERE ROWNUM <= #{offset} + #{pageSize}
)
WHERE rnum > #{offset}
```

가장 안쪽에서 먼저 정렬해야 페이지 순서가 결정된다. 중간 Query는 필요한 끝 행까지만 ROWNUM을 붙인다. 바깥 Query가 이전 페이지의 행을 버린다. pageNo 2, pageSize 20이면 40행까지 만들고 rnum 20 이하를 제외해 21~40번째 행을 반환한다.

ROWNUM 조건과 ORDER BY 위치가 뒤바뀌면 임의로 자른 행을 정렬하는 결과가 되어 페이지 의미가 달라진다. Oracle 버전이 OFFSET/FETCH를 지원해도 현행은 ROWNUM 패턴이며 전환 시 실행계획과 호환 DB를 검증해야 한다.

## 20.7 Offset 계산

현행 Service는 다음 int 계산을 사용한다.

```java
int offset = (pageNo - 1) * pageSize;
```

정상 범위에서는 단순하다. 하지만 pageNo가 매우 크면 곱셈이 `Integer.MAX_VALUE`를 넘어 음수 또는 잘못된 양수로 wrap될 수 있다. 예를 들어 pageSize가 100이면 약 2천만 페이지 이후 위험 영역에 들어간다. 현실적인 UI 페이지는 그보다 작더라도 공격적 입력과 잘못된 자동 호출을 방어해야 한다.

TO-BE에서는 `Math.multiplyExact(long, long)` 또는 long 계산을 사용하고 최대 pageNo·offset을 검증한다. DB bind type과 DTO total도 long으로 맞춘다. overflow 시 첫 페이지처럼 실행하거나 전체 범위를 조회하지 말고 명확한 입력 오류로 거부한다.

pageNo가 totalPages보다 큰 경우 현행은 COUNT 후 빈 목록을 반환할 수 있다. 오류로 볼지 빈 페이지로 볼지는 UI 계약으로 정한다.

## 20.8 pageSize 제한

현재 hard cap 100은 한 요청이 가져오는 행 수를 제한해 DB fetch, 객체 생성과 JSON 크기를 통제한다. 클라이언트가 10,000을 보내도 Service가 100으로 낮추고 응답에 실제 100을 표시한다.

상한은 필수지만 충분하지 않다. 큰 CLOB 컬럼 100건, 복잡한 JOIN 100건, 넓은 기간의 COUNT는 여전히 비쌀 수 있다. 검색 기간, 필수 분할키, 응답 바이트 상한, SQL timeout과 Index를 함께 설계한다.

배치 추출을 pageSize 상한 해제로 해결하지 않는다. 대량 다운로드는 비동기 파일 생성, 전용 배치나 스트리밍 거래로 분리해 온라인 Worker Pool과 Timeout을 보호한다.

## 20.9 깊은 페이지 문제

Offset 방식은 pageNo가 커질수록 앞의 offset 행을 찾아 정렬하고 버리는 비용이 증가한다. 1만 번째 페이지의 20건을 얻으려고 앞선 약 20만 건을 처리할 수 있다. 결과로 반환하지 않는 행도 DB 작업에는 포함된다.

동시 INSERT·DELETE도 문제다. 사용자가 1페이지를 본 뒤 앞쪽에 새 행이 삽입되면 2페이지에서 이전 마지막 행이 다시 보이거나 다른 행이 건너뛸 수 있다. 같은 Transaction에서 COUNT와 LIST를 호출한다고 항상 스냅샷 일관성이 보장되는 것은 아니며 실제 isolation과 DB MVCC를 확인해야 한다.

깊은 페이지 요청 비율, scanned rows, sort spill, buffer gets와 응답 시간을 측정한다. 단순 평균 시간은 앞 페이지가 대부분이면 문제를 숨긴다. pageNo 구간별 percentile을 본다.

## 20.10 키셋·Cursor 페이징

Keyset은 “몇 행을 건너뛴다”가 아니라 “이전 페이지 마지막 키 다음부터”를 조회한다. 예를 들어 이미지로그의 정렬이 `REQUEST_TIME DESC, GUID DESC`라면 두 값을 Cursor로 사용할 수 있다.

```text
WHERE REQUEST_TIME < :lastTime
   OR (REQUEST_TIME = :lastTime AND GUID < :lastGuid)
ORDER BY REQUEST_TIME DESC, GUID DESC
ROWNUM <= :pageSize
```

이는 개념적인 Oracle 조건이다. tuple 비교 문법과 null·문자 정렬은 실제 DB에서 검증해야 한다. 현행 Mapper에는 Keyset이 구현되어 있지 않으며 Offset 방식이 AS-IS다.

Keyset은 깊이에 관계없이 Index의 마지막 위치부터 읽을 수 있고 동시 삽입에 상대적으로 안정적이다. 대신 임의 N페이지 점프와 정확한 totalPages에 맞지 않는다. Cursor 위변조를 막으려면 값을 검증·서명하거나 서버 계약으로 제한하고, 정렬 방향·필터가 바뀌면 기존 Cursor를 무효화한다.

## 20.11 정렬 기준과 인덱스

페이징 ORDER BY는 유일하고 결정적이어야 한다. 동일 값이 많은 컬럼 하나만 정렬하면 DB가 동률 행 순서를 바꿀 수 있다. `mgcoa8888`은 REQUEST_TIME 뒤 GUID, `mgcoa9000`은 REG_DTM 뒤 TX_ID를 사용해 tie-breaker를 둔다. `mgcoa5530`의 L5101이 유일한지는 테이블 제약을 확인해야 한다.

복합 Index는 WHERE의 선택도와 ORDER BY 방향을 함께 고려한다. 함수 `UPPER(column)`, 앞에 `%`가 붙는 LIKE, 날짜 문자열 가공은 일반 Index 사용을 제한할 수 있다. 함수 기반 Index나 검색 전략 변경은 실행계획으로 판단한다.

Index가 있어도 넓은 COUNT와 큰 Offset 비용이 사라지는 것은 아니다. 실제 bind 값으로 실행계획, 예상·실제 행 수와 sort 방식을 확인한다. Index hint가 있는 Mapper는 환경별 통계와 함께 검증해야 한다.

## 20.12 조회 트랜잭션

Facade 조회 메서드는 `readOnly=true`를 선언한다. Timeout OFF에서는 Facade가 조회 Transaction을 시작할 수 있고 COUNT와 LIST가 같은 경계에 실행된다. Timeout ON에서는 Worker의 외부 TransactionTemplate이 먼저 일반 거래를 시작하므로 내부 readOnly 속성이 물리 거래를 바꾸지 못할 수 있다.

동일 Transaction은 Connection과 실패 경계를 묶지만 COUNT와 LIST의 완전한 동일 스냅샷을 자동 보장한다고 단정할 수 없다. isolation 수준과 DB 동작을 확인한다. 목록 중 예외가 발생하면 count 결과만 클라이언트에 반환하지 않고 전체 요청이 실패해야 한다.

긴 조회 Transaction은 Connection을 오래 점유한다. 깊은 페이지, 느린 COUNT와 큰 응답 조립이 Worker Timeout·Pool 포화로 확산될 수 있으므로 SQL 성능과 Transaction 시간을 함께 본다.

## 20.13 성능 검증

성능 검증은 빈 개발 DB의 첫 페이지 한 번으로 끝내지 않는다. 운영 분포와 유사한 행 수, 검색 선택도, 큰 문자열 크기와 동시 요청으로 pageNo 1·중간·깊은 페이지를 나눠 측정한다.

COUNT와 LIST 시간을 별도로 수집하고 GUID·Service ID·SQL ID로 연결한다. 실행계획에서는 Index range scan 여부, sort와 temporary space, buffer gets, 반환 행 대비 읽은 행을 본다. 애플리케이션에서는 Worker queue, Hikari active/pending, Heap, JSON 응답 바이트와 Timeout을 함께 관찰한다.

회귀 기준은 p50만이 아니라 p95·p99, 최대 허용 pageNo·pageSize와 동시성에서 정한다. 검색조건 없음 요청을 허용한다면 최악 조건으로 별도 시험한다.

## End-to-End 경계 사례

```text
pageNo=2, pageSize=20
  → offset=20
  → COUNT=95
  → ROWNUM<=40, rnum>20
  → rows=20
  → totalPages=5, size=20

pageNo=6, pageSize=20
  → COUNT=95
  → rows=0
  → totalPages=5, size=0

pageNo=1, pageSize=10000
  → Service cap=100
  → 최대 100행 반환

pageNo가 int 곱셈 범위를 초과
  → AS-IS overflow 위험
  → TO-BE: long exact 계산 후 입력 거부
```

## 책임과 경계

| 계층 | 책임 | 금지 책임 |
|---|---|---|
| UI/DTOin | pageNo·pageSize·검색조건 전달 | offset 계산·무제한 요청 |
| Service | 보정·offset·count/list·출력 조립 | 전체 목록 메모리 절단 |
| DAO | count/list Statement 계약 | 페이지 업무 정책 |
| Mapper | 공통 WHERE·ORDER BY·ROWNUM | 사용자 정렬 문자열 직접 치환 |
| DB/Index | 범위·정렬 효율 | UI totalPages 결정 |

## 정상과 실패 비교

정상은 COUNT와 LIST 조건이 같고 고정 정렬로 현재 페이지를 반환한다. 0건과 범위 밖 페이지는 계약에 따른 빈 결과다. COUNT 성공 뒤 LIST가 실패하면 전체 요청 예외로 처리한다.

실패에는 SQL timeout, offset overflow, sort memory 부족, Connection 대기, 응답 직렬화 과다가 있다. 애플리케이션 Timeout 응답과 DB 작업 중단 시점은 다를 수 있으므로 Worker 종료와 Rollback을 확인한다.

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | 4개 S0 거래가 Service int offset + COUNT + ROWNUM LIST 사용 |
| AS-IS | pageSize 최대 100, 기본은 10 또는 20 |
| AS-IS | 공통 WHERE include와 고정 ORDER BY 사용 |
| 제약 | int offset/count, 깊은 페이지 비용, 동시 변경 중복·누락 가능 |
| 제약 | 이미지로그의 큰 전문 필드로 행 수 외 응답 크기 위험 |
| TO-BE | long exact 계산·최대 pageNo 검증, SQL별 timeout 검토 |
| TO-BE | 깊은 페이지/무한 스크롤에 Keyset·Cursor 또는 전용 추출 |

## Anti Pattern

전체 SELECT 후 Java에서 `subList`하는 방식, ORDER BY 없는 페이징, count와 list에 서로 다른 WHERE를 쓰는 방식은 금지한다. pageSize 상한을 UI에만 두면 직접 호출로 우회할 수 있으므로 서버에서 강제한다.

Offset과 Cursor 필드를 한 DTO에서 애매하게 동시에 허용하거나, `${sortField}`에 요청값을 직접 넣는 것도 위험하다. 정확한 COUNT가 필요하지 않은 화면에서 매번 대형 COUNT를 실행하는 것은 요구 없는 비용이다.

## 개발자·운영자 체크리스트

- pageNo 1-based와 pageSize 기본·상한이 UI와 일치하는가?
- offset을 서버에서 계산하고 overflow를 검증하는가?
- COUNT와 LIST가 같은 WHERE·권한 조건을 공유하는가?
- ORDER BY가 결정적이며 tie-breaker가 있는가?
- 검색조건과 ORDER BY에 맞는 Index를 실행계획으로 확인했는가?
- 0건, 마지막, 범위 밖, 최대 pageSize를 테스트했는가?
- 깊은 pageNo의 읽은 행·sort·응답 시간을 측정했는가?
- 큰 컬럼을 목록에서 제외할 수 있는가?
- COUNT 생략·근사·캐시가 업무상 가능한가?
- Keyset은 AS-IS가 아니라 별도 계약으로 설계했는가?
- Timeout과 DB Rollback 완료 시점을 구분해 관찰하는가?

## 아키텍처 판단 포인트와 다음 장

Offset은 임의 페이지 이동과 totalPages가 중요한 관리 화면에 적합하다. Keyset은 순차 탐색과 깊은 페이지 성능이 중요한 무한 스크롤에 적합하다. 대량 전체 추출은 둘 중 하나의 pageSize 확대가 아니라 별도 비동기 거래로 분리한다.

페이징 성능은 행 수 제한 하나가 아니라 검색 선택도, 정렬 안정성, Index, COUNT, 행 너비, Transaction과 Timeout의 합이다. 측정 없이 방식만 교체하지 않는다.

다음 장에서는 COUNT와 LIST, 여러 CUD SQL을 하나의 성공·실패 단위로 묶는 Spring Transaction의 기본 원리와 Proxy·전파·Rollback 규칙을 다룬다.
