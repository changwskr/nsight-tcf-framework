# 32장. CRUD 구현 패턴

CRUD는 네 글자의 반복이지만 각 행위가 요구하는 계약은 다르다. 목록은 안정된 정렬과 count 정합성이 필요하고, 상세은 0건과 다건을 구분해야 한다. 등록은 중복 경쟁을 견뎌야 하며 수정·삭제는 처리 행 수와 동시 변경을 판정해야 한다. PDMG의 공통 호출선은 DTO → 진입점 → Facade → Service/Rule → DAO/Mapper지만, 그 안의 검증·SQL·오류·Transaction은 행위별로 설계한다.

이 장은 실제 `mgcoa9001` 거래통제 구현을 기준으로 AS-IS를 판정한다. 이 프로그램에는 목록 S0, 등록 C0, 수정 U0, 삭제 D0가 있고 단건 상세 전용 거래는 없다. 따라서 상세 패턴은 현재 구현이라고 단정하지 않고 TO-BE 권장으로 설명한다.

## 32.1 목록 조회

목록 입력은 검색조건과 pageNo/pageSize를 가진다. `mgcoa9001Service`는 controlType과 blockYn을 정규화하고 targetKeyword를 만들며, pageNo 기본 1, pageSize 기본 20·최대 100으로 제한한다. offset은 `(pageNo-1)*pageSize`다. DAO의 count와 list에 같은 Map을 넘겨 totalCount와 현재 page rows를 얻고 출력에 totalPages를 계산한다.

Mapper는 공통 `mgcoa9001Where`를 count와 list에서 재사용한다. 이 구조는 화면에 표시한 총 건수와 목록 조건이 갈라지는 오류를 줄인다. 안쪽 쿼리에서 controlType·businessCode·serviceId·userId로 정렬한 뒤 Oracle ROWNUM 범위를 적용한다. 페이지 사이 데이터가 변경되면 offset 방식은 중복·누락이 생길 수 있으므로 대용량·고변경 데이터는 keyset 방식을 검토한다.

목록의 “0건”은 오류가 아니라 빈 rows와 totalCount 0인 정상 결과다. SQL에서 `SELECT *`를 업무 DTO에 직접 노출하지 않고 명시 Alias를 Map→행 DTO로 변환한다. 검색 Keyword LIKE는 넓은 OR 조건이어서 Index 효율과 대소문자 함수 비용을 실행계획으로 확인해야 한다.

## 32.2 상세 조회

상세 조회는 목록 필터를 재사용하는 것이 아니라 식별키 하나로 최대 한 행을 반환하는 계약이다. 입력 DTO에는 완전한 복합키나 공개 식별자를 요구하고, DAO 반환은 Optional 또는 nullable 단건으로 표현한다. 0건은 미존재 업무 오류 또는 선택적 조회의 empty로 계약에 따라 구분한다. 2건 이상은 데이터 무결성 장애다.

`mgcoa9001`에는 exists count만 있고 상세 조회 전용 S1이 없다. exists 후 별도 조회를 두 번 실행하면 그 사이 상태가 바뀔 수 있다. 상세값이 필요하다면 한 번의 SELECT로 행을 가져오고 null을 판정하는 편이 낫다. 민감한 상세은 검증된 사용자 권한과 영업점 범위를 WHERE 또는 Service 인가에서 적용한다.

상세 응답은 저장 Entity나 Mapper Map을 그대로 노출하지 않는다. 화면에 필요한 필드만 출력 DTO로 옮기고, 등록자·내부 상태처럼 권한에 따라 달라지는 필드는 계약에서 제외하거나 별도 인가 후 채운다. 복합키 중 일부만 받은 상태로 `selectOne`을 호출하면 우연히 첫 행을 반환하거나 MyBatis의 다건 예외가 발생할 수 있으므로 Service에서 키 완전성을 먼저 검증한다. 다건 결과를 `LIMIT 1`로 감추는 구현은 무결성 문제를 정상처럼 보이게 하므로 금지한다.

## 32.3 등록

등록 C0는 controlType, blockYn, changeReason과 target을 검증하고 `MgTxControlRowSupport`로 저장 복합키를 만든다. exists count가 0인지 확인한 뒤 감사 사용자·시각을 채우고 INSERT한다. 중복이면 `MP0409`, 잘못된 입력은 `MP0401` 또는 `MP0403` 계열 BizException으로 실패한다.

AS-IS의 exists-then-insert는 동시 요청에 안전하지 않다. 두 Transaction이 동시에 exists=0을 읽고 둘 다 INSERT할 수 있다. DB Unique Constraint가 최종 방어선이어야 하며 DuplicateKeyException을 안정된 중복 코드로 변환해야 한다. Unique 제약이 없다면 중복 데이터가 생긴다. 등록 결과 `cnt`를 출력에 넣지만 정확히 1건인지 검사하지 않는다. 단건 등록 계약이면 1이 아니면 예외로 rollback하는 편이 안전하다.

감사 `regUserId`는 입력값 또는 `LOCAL` fallback을 쓴다. TO-BE에서는 클라이언트 입력보다 검증된 ServiceContext 사용자 ID를 사용해야 한다. 업무 데이터와 감사값을 같은 Transaction에서 저장해 commit 여부를 일치시킨다.

## 32.4 수정

수정 U0는 완전한 복합키를 만들고 controlType·blockYn·사유를 검증한다. exists가 0이면 미존재 오류를 내고 UPDATE 후 `cnt<=0`도 다시 미존재로 처리한다. Mapper WHERE는 일곱 개 키를 모두 사용해 수정 범위를 제한한다. 변경 가능 필드는 통제유형, 차단 여부, 변경사유와 감사 수정정보다.

AS-IS는 `cnt>1`을 오류로 보지 않는다. DB 키 무결성이 깨졌다면 여러 행을 바꾸고도 성공한다. 단건 수정은 `cnt==1`을 요구해야 한다. exists와 update 사이 다른 Transaction이 삭제하거나 변경할 수 있으므로 exists는 친절한 사전 메시지일 뿐 동시성 보장이 아니다. 최종 UPDATE 행 수가 권위 있는 판정이다.

수정 DTO에 이전 version 또는 최종수정시각이 없고 SQL WHERE에도 version 조건이 없어 lost update를 막지 못한다. TO-BE optimistic locking은 `WHERE key AND version=:expected`와 `SET version=version+1`을 사용하고 0건을 동시수정 오류로 변환한다.

부분 수정과 전체 수정의 계약도 구분한다. 전체 수정은 누락 필드를 기본값이나 null로 덮을 수 있지만 부분 수정은 전달 여부와 값 null을 구별해야 한다. PDMG의 명시적인 U0 DTO에서는 변경 가능 필드를 계약으로 고정하는 편이 추적하기 쉽다. 동적 SQL을 사용한다면 모든 필드가 누락되어 실제 변경이 없는 요청을 성공 처리할지, 입력 오류로 거절할지 먼저 정한다. 감사 수정시각만 바뀌는 UPDATE를 업무 성공으로 세지 않도록 검증 순서도 일관되어야 한다.

## 32.5 삭제

삭제 D0는 키와 변경사유를 검증하고 exists 확인 뒤 물리 DELETE한다. SQL은 완전한 복합키를 바인딩하고 Service는 0건을 미존재로 처리한다. 그러나 입력받은 changeReason은 검증만 하고 삭제 SQL이나 별도 감사 저장에 사용하지 않는다. 물리 삭제 뒤에는 사유와 삭제 주체가 업무 Table에서 사라진다.

단건 삭제 역시 `cnt==1`이어야 한다. 삭제 전에 상세을 읽어 응답하거나 이력을 남겨야 한다면 동일 Transaction에서 처리하고 민감정보를 최소화한다. 다른 Table이 참조한다면 FK 오류를 업무 오류로 변환하거나 삭제 금지 규칙을 Service/Rule에 둔다. DAO가 임의로 cascade 정책을 결정하지 않는다.

## 32.6 논리 삭제와 물리 삭제

논리 삭제는 `USE_YN`, `DELETE_YN`, deletedAt/by 같은 컬럼을 UPDATE하고 기본 조회에서 제외한다. 복구·감사·참조 유지가 중요하면 적합하지만 모든 조회와 Unique 조건이 삭제 상태를 고려해야 한다. 물리 삭제는 저장공간과 조회가 단순하지만 복구와 행 자체 감사가 어렵다.

`mgcoa9001D0_D0`는 실제 DELETE이므로 AS-IS는 물리 삭제다. 변경사유 보존 요구가 있다면 별도 불변 감사 Table 또는 논리 삭제로 전환해야 한다. ImageLog에 요청 전문이 남는다는 이유로 업무 감사 요구를 대체해서는 안 된다. ImageLog는 보존·마스킹·실패 정책이 다르다.

## 32.7 처리 건수 검증

처리 건수는 DB가 실제로 바꾼 행의 수이며 성공 판단의 핵심이다. 단건 C/U/D는 일반적으로 정확히 1건이어야 한다. 0건은 미존재, 동시 변경, 조건 불일치 중 하나이고 2건 이상은 키·WHERE·데이터 무결성 문제다. Bulk 거래만 입력 건수와 허용 Partial 결과 계약을 별도로 둔다.

```text
cnt == 1 → 단건 성공
cnt == 0 → 미존재 또는 optimistic conflict
cnt > 1  → 무결성/WHERE 결함, rollback
```

AS-IS U0/D0는 0건만 실패시키며 C0는 cnt를 검증하지 않는다. 신규 CRUD는 공통 `assertSingleRow()` Rule처럼 의미를 명시할 수 있지만 코드 하나로 모든 Bulk 행위를 강제하지 않는다. 예외는 Transaction 경계를 벗어나야 rollback된다.

## 32.8 동시성 처리

동시성은 exists 사전조회로 해결되지 않는다. 등록은 Unique Constraint가 두 동시 INSERT 중 하나를 막아야 한다. 수정은 version, 최종수정시각 또는 업무 상태를 WHERE에 포함하는 optimistic locking이 기본 선택이다. 꼭 필요한 재고·한도 같은 갱신은 원자적 조건 UPDATE나 제한적인 pessimistic lock을 검토한다.

```sql
UPDATE business_table
   SET value = #{value}, version = version + 1
 WHERE id = #{id}
   AND version = #{expectedVersion}
```

결과 0건은 “없음”과 “다른 사용자가 먼저 변경”을 구분할 필요가 있다. 별도 조회로 메시지를 정교하게 만들 수 있지만 correctness는 조건 UPDATE가 보장한다. Lock 선택은 충돌 빈도, Transaction 길이, deadlock 위험과 사용자 재시도 UX를 기준으로 한다.

## 32.9 트랜잭션 적용

조회는 readOnly, 쓰기는 rollbackFor Exception과 명시 `rdwTransactionManager`를 사용한다. `mgcoa9001`은 Facade와 Service 양쪽에 Transaction Annotation이 있다. TCF timeout ON에서는 바깥 Worker TransactionTemplate까지 존재해 기본 REQUIRED 참여로 같은 물리 Transaction이 될 수 있다. 중복 Annotation이 곧 중첩 commit을 의미하지는 않지만 경계 소유권을 흐린다.

TO-BE는 유스케이스 조정 경계인 Facade 또는 합의된 한 계층을 주 경계로 정한다. 검증, 존재 확인, 쓰기와 업무 후처리를 동일 Transaction에 포함할지 명시한다. catch 후 성공 DTO를 반환하면 rollback되지 않는다. 외부 호출을 DB Transaction 안에 오래 두면 Lock과 Connection 점유가 커진다.

## 32.10 입력 검증

입력 검증은 형식, 업무 의미, 데이터 상태 세 층이다. DTO/Controller는 null·길이·문법, Rule은 허용 통제유형과 Y/N·변경사유, Service는 중복·미존재와 권한을 검사한다. DAO/DB Constraint는 최종 무결성 방어선이다.

예제는 문자열 trim, 허용 Set, YN 정규식과 사유 최소 길이를 Service private 메서드로 구현한다. 반복되거나 독립 테스트 가치가 있으면 Rule로 분리한다. 검색조건의 빈 값은 생략하지만 쓰기 키의 빈 값은 오류다. 사용자·감사 필드는 Client DTO보다 인증 Context를 우선한다.

## 32.11 오류 코드

CRUD 오류는 입력 누락, 형식 오류, 미존재, 중복, 동시수정, 권한, 참조 무결성과 시스템 DB 장애를 구분한다. 같은 “0건”도 상세 조회에서는 미존재, optimistic update에서는 충돌일 수 있다. 안정된 코드가 UI의 재조회·재시도·입력 수정 행동을 결정한다.

현재 `MP0404`가 미존재, `MP0409`가 중복에 사용된다. 오류를 삼키지 않고 BizException을 재전파한다. 다만 Global Handler와 exceptionCode 메시지 연결의 현행 결함은 별도 검증한다. SQL Exception message를 UI에 직접 반환하지 않는다.

## 32.12 보안과 감사

CRUD 권한은 화면 노출이 아니라 서버에서 Service ID와 사용자 권한으로 검사한다. Mapper는 입력을 `#{}`로 바인딩하고 동적 컬럼·정렬은 allowlist를 사용한다. 목록은 사용자에게 허용된 영업점·업무 범위를 WHERE에 적용한다.

등록·수정·삭제 감사에는 검증된 사용자, 시각, 변경사유와 필요한 이전/이후값을 남긴다. 현재 입력의 regUserId/chgUserId와 LOCAL fallback은 운영 신뢰원으로 부족하다. 전문 로그에는 Token, 비밀번호와 개인정보를 마스킹하고 삭제 이력은 보존정책에 따른다.

## 32.13 CRUD 테스트

목록은 0건, 한 페이지, 마지막 페이지, pageSize 상한, count/list 조건과 안정 정렬을 검증한다. 상세은 0·1·다건 무결성을 검사한다. 등록은 정상과 DB Unique 동시 경쟁, 수정은 1건·0건·version 충돌, 삭제는 FK·0건·다건 방지를 테스트한다.

Service 단위 테스트는 DAO 반환 건수별 예외와 DTO 조립을 확인한다. Mapper 통합 테스트는 실제 H2/대상 DB 차이와 SQL Binding을 실행한다. Transaction 테스트는 두 번째 단계 실패 시 첫 번째 변경 rollback을 확인한다. TCF ON/OFF HTTP 계약과 UI `dto/result` 처리도 포함한다.

동시성 테스트는 순차 Mock만으로 증명할 수 없다. 두 실행 흐름이 같은 키의 exists를 모두 통과하도록 Barrier를 둔 뒤 INSERT를 경쟁시켜 하나만 commit되는지 확인한다. Optimistic update는 같은 version을 읽은 두 요청 가운데 하나의 행 수가 0이 되고 정의된 충돌 코드로 변환되는지 검사한다. 물리 삭제는 삭제 후 조회 0건뿐 아니라 감사 기록과 참조 무결성 정책도 함께 확인한다. 테스트 데이터 정리 실패가 다음 사례에 영향을 주지 않도록 각 사례의 Transaction과 Cleanup 경계도 명시한다.

### End-to-End CRUD 흐름

```text
Request DTO
  → Handler/Controller
  → Facade Transaction
  → Service/Rule: 형식·업무·상태 검증
  → DAO/Mapper: bind SQL
  → count/row count/version 판정
  → commit 또는 BizException rollback
  → dto/result + 감사·GUID
```

### CRUD별 책임과 정상·실패 비교

| 행위 | 정상 | 실패 핵심 | 동시성 방어 |
|---|---|---|---|
| 목록 | rows+totalCount | 잘못된 범위·불안정 정렬 | 안정 정렬/keyset |
| 상세 | 정확히 한 행 | 0건·다건 | Snapshot 요구 판단 |
| 등록 | insert 1건 | 중복·제약 위반 | Unique Constraint |
| 수정 | update 1건 | 0건·다건·lost update | version 조건 |
| 삭제 | delete/update 1건 | 참조·미존재·감사 손실 | 상태/version 조건 |

### Anti Pattern

- S/C/U/D를 한 Service 메서드와 거대한 DTO로 분기한다.
- UPDATE/DELETE가 0건 또는 다건이어도 성공을 반환한다.
- exists 조회만으로 동시 등록·수정을 해결했다고 본다.
- 삭제사유를 검증만 하고 어디에도 보존하지 않는다.
- 감사 사용자 ID를 Client 입력 그대로 신뢰한다.
- DAO에서 권한·업무 오류·Transaction을 임의 결정한다.
- 목록 count와 list에 서로 다른 WHERE를 복사한다.

### 개발자 체크리스트와 아키텍처 판단

- [ ] CRUD별 DTO와 Service ID가 분리되어 있는가?
- [ ] 목록 정렬·페이지 상한·count 조건이 일치하는가?
- [ ] 상세의 0·1·다건 계약이 명확한가?
- [ ] 단건 쓰기는 `cnt==1`을 검증하는가?
- [ ] 등록 Unique Constraint와 예외 변환이 있는가?
- [ ] 수정 version/상태 기반 충돌 탐지가 있는가?
- [ ] 논리·물리 삭제 선택과 감사·복구 정책이 있는가?
- [ ] Transaction 경계와 rollback 재전파가 명확한가?
- [ ] 권한·감사 사용자가 검증된 Context에서 오는가?
- [ ] Mapper Binding, SQL Injection, DB별 SQL을 검증했는가?
- [ ] 정상·경계·오류·동시성 테스트가 있는가?

논리삭제와 물리삭제, optimistic과 pessimistic locking, offset과 keyset paging은 관행이 아니라 데이터 수명과 충돌 특성으로 선택한다. 31장이 프로그램 전체의 완성 절차였다면 이 장은 CRUD 행위별 불변조건을 정리했다. 다음 장에서는 이 불변조건과 Framework 경계를 Handler, Facade, Service, Mapper, Controller, Timeout, JWT와 UI 테스트로 증명하는 최종 품질 Gate를 다룬다.
