# 26장. 예외처리와 표준 오류

PDMG의 예외처리는 오류 문구를 만드는 기능이 아니라 실패한 거래의 의미를 보존하는 구조다. 발생 계층은 Filter, Interceptor, Controller, TCF, 업무, DAO처럼 다양하지만 클라이언트는 일관된 HTTP 상태와 오류 전문을 받아야 하고, 변경 중이던 DB 작업은 rollback되어야 한다. 이를 위해 예외는 필요한 정보만 담아 트랜잭션 경계 밖으로 재전파되고 최종 변환 지점에서 응답으로 바뀌어야 한다.

현행은 하나의 완성된 변환 파이프라인이 아니다. TCF ON일 때 `GlobalExceptionHandler`가 일부 예외를 `NH_NIS_ERR_DTO`로 바꾸고 `ResponseBodyArgumentResolver`가 이를 `result` 노드에 넣는다. 반면 `DefaultFilter`는 `sendError()`로 직접 종료하고, 등록되지 않은 일반 예외를 처리하는 catch-all Handler도 확인되지 않는다. YAML 메시지 사전인 `ExceptionCodeProperties`와 DB 메시지 캐시인 `MessageCache` 역시 서로 다른 체계다.

## 26.1 예외처리 원칙

업무 코드에서는 실패 원인에 가장 가까운 곳에서 의미 있는 예외를 만들고, 복구할 수 없으면 삼키지 않는다. 변환은 HTTP 경계를 아는 계층 한 곳에서 수행한다. 로그에는 GUID와 오류 코드, 안전한 원인을 남기되 SQL, Stack Trace, 비밀번호와 Token을 응답에 내보내지 않는다. HTTP 상태는 전송 결과이고 업무 오류 코드는 도메인 의미이므로 별도로 결정한다.

## 26.2 계층별 예외

| 발생 위치 | 대표 실패 | AS-IS 포착·변환 |
|---|---|---|
| Filter | JSON, Header, JWT | `sendError()` 400/401, MVC Advice 우회 |
| Interceptor | 시스템 선처리·거래통제 | 일부 `BizException`, MVC 방향 재전파 |
| Controller/TCF | Service ID, Handler | `ServiceHandlerNotFound` Handler |
| 업무 Service | 검증·중복·미존재 | `BizException` Handler |
| DAO/DB | SQL·제약·접속 | 명시 Translator 확인 안 됨 |
| Timeout Worker | 시간초과·과부하 | 전용 Handler 504/503 |

예외가 어느 선에서 끝나는지에 따라 응답 형식과 rollback 가능성이 달라진다. Filter 실패는 업무 트랜잭션이 시작되기 전이므로 rollback 대상이 없지만, 업무 내부 예외는 반드시 TransactionTemplate 또는 `@Transactional` 경계를 빠져나가야 한다.

## 26.3 입력 검증 예외

요청 Body가 비거나 JSON 파싱이 실패하거나 non-local에서 공통 Header가 없으면 `DefaultFilter`가 400을 직접 보낸다. Controller DTO 변환 전에 끝나므로 `GlobalExceptionHandler`와 `ResponseBodyArgumentResolver`의 표준 `result` 조립을 거치지 않는다. 업무 필드 검증은 Service에서 `BizException`으로 발생하는 사례가 있어 같은 “입력 오류”라도 응답 모양과 상태가 다를 수 있다. TO-BE에서는 Filter 오류도 공통 오류 작성기를 사용해야 한다.

## 26.4 인증 예외

Bearer 누락, HMAC 검증 실패, `type != ACCESS`는 Filter에서 401로 끝난다. 내부 토큰 값은 응답과 로그에 포함하지 않는다. 반면 JWT 모듈의 로그인 실패는 `BizException`이며 TCF ON Handler는 현재 이를 500으로 응답한다. 잘못된 자격 증명은 일반적으로 401에 대응시키되 사용자 존재 여부는 동일한 외부 메시지로 숨기는 정책이 필요하다.

## 26.5 인가 예외

거래통제는 차단 규칙이 일치하면 `FW0410` BizException을 던지고, 저장소 오류는 `FW0411`로 바꾼다. 업무 예제에는 `MP0403` 권한 오류도 있다. 현행 Global Handler는 모든 BizException을 500으로 처리하므로 인증된 사용자의 권한 부족을 403으로 구분하지 않는다. 오류 코드별 HTTP 상태 매핑 표를 중앙화하는 것이 TO-BE다.

## 26.6 Service ID 오류

요청의 Service ID로 Handler를 찾지 못하면 `ServiceHandlerNotFound`가 발생하고 Global Handler는 코드 `E9999`, 유형 SERVICE, HTTP 500을 반환한다. 존재하지 않는 거래는 요청 오류로 볼 수도 있고 배포 Catalog 결함으로 볼 수도 있다. 외부에 클래스명이나 등록 목록을 노출하지 않으면서 운영 로그에는 요청 Service ID와 GUID를 남겨야 한다.

## 26.7 업무 예외

`BizException`은 RuntimeException이며 code와 메시지 인자만 보관한다. 생성자의 `super(code)` 때문에 `e.getMessage()`는 사람이 읽는 메시지가 아니라 코드다. 그런데 현행 Global Handler는 `e.getMessage()`를 그대로 `stdErrMsgCntn`에 넣어 YAML 메시지를 해석하지 않는다. 즉 `MP0404`를 던져도 TCF ON 응답 메시지가 코드 문자열일 수 있다. `ExceptionCodeProperties.message(code,args)`를 Handler에서 호출하도록 연결해야 설정 메시지가 실제 응답에 반영된다.

## 26.8 DAO·DB 예외

MyBatis/JDBC 예외를 PDMG 표준 코드로 변환하는 전용 Translator는 확인되지 않았다. DataAccessException이나 제약 위반이 일반 RuntimeException으로 올라오면 catch-all Handler가 없어 컨테이너 기본 500으로 갈 수 있다. 업무적으로 예상 가능한 중복은 Service가 `MP0409`처럼 변환할 수 있지만, SQL 문장과 DB 오류 메시지를 클라이언트에 그대로 전달해서는 안 된다.

## 26.9 외부 연계 예외

외부 호출은 연결 실패, 응답 지연, 원격 4xx/5xx, 전문 변환 실패를 구분해야 한다. 저장소에서 이들을 통합하는 현행 표준 Translator는 확인되지 않았다. TO-BE에서는 원인 예외를 보존하면서 외부 응답 본문과 URL의 민감 정보를 제거하고, 재시도 가능 여부를 코드에 포함해야 한다. 무조건 재시도하면 중복 처리를 만들 수 있다.

## 26.10 타임아웃 예외

`OnlineTimeoutException`은 504, `OnlineOverloadException`은 503으로 별도 처리된다. 응답 부가정보에는 Service ID, GUID, 제한·경과시간 또는 Pool 상태가 들어간다. Worker TransactionTemplate은 timeout·overload·RuntimeException·checked Exception에서 rollback-only를 설정하고 다시 던진다. Future 취소만으로 DB 작업이 즉시 멈춘다고 단정하지 않으며 23장의 취소 조건을 함께 본다.

## 26.11 GlobalExceptionHandler

이 Advice는 `nhnis.fw.tcf.enabled=true`일 때만 등록된다. 처리 대상은 ServiceHandlerNotFound, BizException, OnlineTimeoutException, OnlineOverloadException 네 종류다. 범용 Exception Handler는 없고 TCF OFF에서 같은 Advice가 동작하지도 않는다. 따라서 ON/OFF와 예외 종류에 따라 오류 계약이 달라지는 것이 AS-IS다.

Advice의 로그 전략도 예외별로 다르다. BizException은 코드만 warn으로 남기고, timeout과 overload는 GUID와 실행 상태를 남긴다. ServiceHandlerNotFound는 예외 message를 기록한다. 이 정도 정보로 원인 분석이 가능한지, 사용자 입력이 message에 섞일 가능성은 없는지를 코드 리뷰에서 확인해야 한다. 예상하지 못한 예외용 Handler를 추가할 때는 서버 로그에는 원인 체인을 보존하되 응답은 `FW9999` 같은 일반 코드로 축소해야 한다.

```text
처리 대상 예외 → GlobalExceptionHandler → ResponseEntity<NH_NIS_ERR_DTO>
             → ResponseBodyArgumentResolver → { hdr_nhnis, result }

Filter sendError / 미등록 Exception → 위 경로를 보장하지 않음
```

## 26.12 `exceptionCode.yml`

서비스 설정은 `classpath:exceptionCode.yml`을 import하고 `nhnis.exception` Map으로 바인딩한다. `ExceptionCodeProperties`는 대소문자를 무시해 코드를 찾고 `MessageFormat` 인자를 적용하며, 미등록 코드는 `FW9999` 메시지로 fallback한다. 그러나 이 Properties가 Global Handler에 주입되지 않았으므로 “YAML 정의가 곧 모든 응답 메시지”는 아니다. 코드 등록, throw 지점, 변환 Handler의 세 연결을 함께 테스트해야 한다.

## 26.13 MessageCache

`MessageCache`는 YAML이 아니라 DB 메시지 번들용 ConcurrentHashMap이다. `MessageLoader`가 기동 시 설정된 DataSource와 테이블을 UNION 조회하여 채운다. `ResponseBodyArgumentResolver.errorProcessor()`는 Legacy `NhBaseException`의 SERVICE/BIZ 유형에 이 캐시를 사용한다. 반면 새 `BizException` Handler는 MessageCache를 쓰지 않는다. 문서에서 YAML → MessageCache라고 단일 흐름으로 설명하면 현행과 다르다.

## 26.14 HTTP 상태 결정

현행 매핑은 BizException과 Handler 미발견이 500, timeout 504, overload 503, Filter 입력 400, Filter 인증 401이다. 업무 오류 코드와 HTTP 상태가 중앙 정책으로 연결되어 있지 않다. TO-BE에서는 잘못된 입력 400, 미인증 401, 권한 부족 403, 미존재 404, 충돌 409, 예상하지 못한 서버 오류 500처럼 의미를 정하되 기존 클라이언트 호환성을 검토한다.

## 26.15 표준 오류 응답

TCF ON Advice가 만든 `NH_NIS_ERR_DTO`는 성공의 `dto`가 아니라 `result` 키에 들어간다. 표준 Header가 Context에 있으면 함께 반환된다. 오류 DTO에는 코드, 메시지, 유형과 선택적 부가 메시지가 있다. Legacy `NhBaseException` 변환은 파일·클래스·라인과 상위 Stack Trace를 DTO에 싣는 코드가 있으므로 운영 외부 응답에서 제거해야 한다.

응답 조립 자체가 실패하는 경우도 고려해야 한다. `ResponseBodyArgumentResolver`는 전용 Marshal이 실패하면 ObjectMapper 변환으로 fallback한다. 이 fallback에서도 최소 오류 필드가 유지되는지 테스트해야 한다. 이미 응답이 commit된 뒤 발생한 후처리 예외는 새 오류 전문으로 바꿀 수 없으므로, 후처리는 가능한 한 응답 commit 전 완료하고 실패 정책을 명시해야 한다.

## 26.16 오류 이력의 독립 트랜잭션

현행 `TransactionManagerHolder`는 기본 begin에 REQUIRES_NEW를 사용하지만 이것이 오류 이력 전용 Service로 연결된 증거는 없다. 오류 이력을 원 거래와 같은 Transaction에 저장하면 원 거래 rollback 때 이력도 사라진다. TO-BE는 별도 Spring Bean의 public 메서드에 `REQUIRES_NEW`를 적용해 프록시를 거쳐 호출하고, 최소 정보만 기록한다. 이력 저장 실패가 원래 예외를 덮어쓰지 않도록 별도로 처리해야 한다.

## 26.17 내부정보 노출 방지

클라이언트에는 안정된 코드와 안전한 메시지, 추적용 GUID만 제공한다. SQL, DB 계정, 파일 경로, 내부 URL, Token, Secret, 전체 Stack Trace는 서버의 접근 통제된 로그에만 필요한 범위로 남긴다. 특히 `ServiceHandlerNotFound.getMessage()`와 timeout detail처럼 내부값을 응답에 넣는 현행 코드는 외부 계약과 운영 진단 정보를 분리할 필요가 있다.

## 26.18 UI 오류 팝업

UI는 HTTP 성공 여부만 보지 말고 표준 응답의 `result`를 해석해 사용자 메시지를 보여야 한다. 인증 오류는 로그인 이동, 권한 오류는 접근 불가 안내, 입력 오류는 수정 가능 필드 안내, 서버 오류는 GUID와 문의 문구로 구분한다. 원격 message나 Stack Trace를 `innerHTML`로 출력하면 정보 노출과 XSS 위험이 생긴다. Filter의 비표준 오류 응답도 안전한 fallback으로 처리해야 한다.

### End-to-End 흐름과 책임 경계

```text
업무/DAO 실패 → 예외 재전파 → TX rollback
  → GlobalExceptionHandler(처리 대상인 경우)
  → 코드별 안전한 메시지와 HTTP 상태 결정
  → NH_NIS_ERR_DTO → ResponseBodyAdvice → result
  → GUID 기반 서버 로그·선택적 독립 오류 이력

Filter 실패 → sendError → 별도 컨테이너 응답        [AS-IS 단절]
일반 Exception → catch-all 없음                     [AS-IS 단절]
```

| 책임 | 해야 할 일 | 하지 말아야 할 일 |
|---|---|---|
| 업무/Rule | 의미 있는 코드로 실패 선언 | HTTP 응답 직접 생성 |
| DAO | 원인 예외 보존 | SQL 상세를 사용자 메시지로 반환 |
| TX 경계 | 실패 재전파와 rollback | catch 후 성공 반환 |
| Exception Handler | 상태·표준 DTO 변환 | 비밀값과 Stack Trace 노출 |
| 오류 이력 Service | 독립 TX로 최소 감사정보 저장 | 원 예외를 덮어쓰기 |
| UI | 코드별 안전 UX와 GUID 표시 | 서버 메시지를 무검증 HTML 출력 |

### 정상·실패 비교와 Anti Pattern

정상 요청은 업무 DTO가 `dto`에 들어가며 Transaction이 commit된다. BizException은 재전파되어 rollback된 뒤 `result` 오류로 변환되어야 한다. Filter 실패는 Transaction 시작 전 종료되고, timeout은 Worker Transaction을 rollback-only로 만든 뒤 504로 수렴한다.

| 사례 | DB 결과 | HTTP/본문 AS-IS | 운영 확인 |
|---|---|---|---|
| 정상 조회·변경 | commit | 성공 `dto` | GUID, Service ID, 처리시간 |
| 업무 중 BizException | RuntimeException이면 rollback | 500 + `result` | 코드가 메시지로 노출되는지 확인 |
| checked Exception | `rollbackFor=Exception` 또는 Worker 경계에서 rollback | 처리 Handler 유무에 따라 차이 | 원인 체인과 rollback 로그 |
| 인증 실패 | TX 시작 전 | Filter 401 `sendError` | 표준 전문과 다른 응답 확인 |
| JSON 오류 | TX 시작 전 | Filter 400 `sendError` | 요청 원문을 로그에 남기지 않음 |
| DB 제약 위반 | rollback 예상 | catch-all 부재 시 기본 500 가능 | SQL 원문 외부 노출 여부 |
| timeout | Worker rollback-only | 504 + `result` | GUID로 Worker 종료 상태 추적 |

- `catch (Exception)` 후 빈 DTO를 반환하면 rollback과 오류 변환이 모두 사라진다.
- 모든 BizException을 500으로 고정하면 인증·권한·충돌을 클라이언트가 구분하지 못한다.
- YAML 코드만 추가하고 Handler 연결을 확인하지 않으면 응답에는 코드 자체가 메시지로 남는다.
- 오류 이력을 같은 Transaction에 저장하면 가장 필요한 실패 시점에 이력이 rollback된다.
- Legacy Stack Trace 필드를 외부 응답에 유지하면 내부 구조가 노출된다.

### 아키텍처 판단과 다음 장

표준화의 기준은 모든 오류를 같은 상태로 만드는 것이 아니라, 같은 의미의 실패가 발생 위치와 TCF 설정에 관계없이 같은 계약으로 수렴하게 하는 것이다. PDMG는 우선 YAML Properties, DB MessageCache, 새 BizException, Legacy NhBaseException을 어떤 기준으로 통합할지 결정해야 한다. 그다음 Filter까지 공통 오류 작성기를 적용하고 코드별 상태 정책을 고정해야 한다.

오류 계약이 일관되어도 운영자가 특정 실패 요청을 찾지 못하면 장애 분석은 끝나지 않는다. 다음 장에서는 GUID가 Filter부터 Worker와 이미지로그까지 어떻게 이어지는지, 정상·실패 전문을 어떤 시점에 저장하고 검색하는지 살펴본다.
