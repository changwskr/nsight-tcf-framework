# 6장. 패키지와 프로젝트 구조

Service ID와 클래스 이름을 정했다. 그렇다면 Handler, Facade, Service와 DAO를 프로젝트의 어느 디렉터리에 만들어야 할까? Spring이 Bean만 찾아준다면 아무 패키지에 두어도 되는 것일까?

PDMG에서 패키지는 파일을 보기 좋게 분류하는 폴더가 아니다. 패키지는 업무 경계와 계층 책임을 표현하고, Spring Component Scan과 MyBatis Mapper Scan, AOP Pointcut과 XML namespace가 적용되는 런타임 경계다. 클래스를 잘못된 패키지로 옮기면 컴파일은 되더라도 Bean이 등록되지 않거나 업무 선후처리가 실행되지 않을 수 있다. DAO Proxy가 만들어지지 않고 Mapper Statement가 끊어질 수도 있다.

5장이 “무엇이라고 이름을 지을 것인가”에 답했다면 이 장은 “그 이름의 파일을 어디에 둘 것인가”에 답한다. 3장의 논리적 Layer를 실제 Source Tree로 투영하되, 도메인 간 호출 정책과 외부 호출 방식의 상세는 7장에 맡긴다.

## 이 장에서 해결할 질문

- PDMG는 업무 중심 패키지와 계층 중심 패키지를 어떻게 결합하는가?
- `entry`, `application`, `dto`, `persistence`, `client`, `config`, `support`에는 무엇을 두는가?
- 실제 Base Package와 현재 업무축은 무엇인가?
- Component Scan, Mapper Scan과 AOP Pointcut은 어느 범위를 대상으로 하는가?
- Java DAO 패키지와 Mapper XML 경로는 어떻게 연결되는가?
- 새 업무축을 추가할 때 어떤 설정과 테스트까지 함께 바꾸어야 하는가?
- 잘못된 패키지 배치는 어떤 컴파일·기동·런타임 장애를 만드는가?

이 장은 2026년 8월 13일 현재 `pdmg-service`와 `pdmg-fw` 소스를 AS-IS로 삼는다. 대표 프로그램은 앞 장과 같은 `mgcoa9000`을 사용한다. 저장소 공통 권장 구조와 현재 PDMG 배치가 다른 부분은 표준 또는 TO-BE로 분리한다.

## 6.1 패키지 설계 원칙

PDMG 패키지는 먼저 업무를 묶고 그 안을 계층과 컴포넌트로 나눈다. 전역 루트 아래에 모든 Controller를 모으는 순수 기술 중심 구조도 아니고, 한 업무 폴더 안에 모든 클래스를 평면 배치하는 순수 기능 중심 구조도 아니다.

```text
Base Package
   ↓
업무축: 대그룹 / 업무 / 세부업무
   ↓
Layer: entry / application / persistence ...
   ↓
Component: handler / facade / service / dao ...
```

이 결합은 두 가지 탐색을 동시에 지원한다. `nhnis.mg.co.a`를 기준으로 공통관리 업무 전체를 볼 수 있고, 그 아래 `application.service`를 기준으로 업무 Service만 볼 수 있다. 장애 Service ID `mgcoa9000S0`의 앞부분을 해석하면 `nhnis.mg.co.a`로 이동한 뒤 Handler에서 DAO까지 같은 업무축 안에서 추적할 수 있다.

패키지가 제공하는 경계는 단순한 가독성보다 넓다.

```text
Package
  ├─ Java 접근과 import
  ├─ 업무 소유권과 변경 영향도
  ├─ Spring Component Scan
  ├─ ConfigurationProperties Scan
  ├─ MyBatis Mapper Scan
  ├─ AOP Pointcut
  ├─ Mapper namespace
  └─ Test Source 대응
          ↓
       Runtime 동작
```

패키지 규칙을 지키면 의존 방향을 리뷰하기 쉽다. Handler는 Facade를 호출하고, Service는 DAO나 Client를 호출하며, persistence는 application이나 entry를 역참조하지 않는다. Java가 이 방향을 자동으로 모두 금지하지는 않지만, 패키지 이름이 위반을 드러내므로 정적 분석과 Code Review가 경계를 검사할 수 있다.

코드 생성에도 패키지는 핵심 입력이다. 업무축과 컴포넌트 역할이 확정되면 Codex나 템플릿이 파일의 목적지를 계산할 수 있다. 반대로 “적당한 service 폴더”처럼 경계가 모호하면 자동 생성기가 기존 구조를 복제하면서 잘못된 의존을 확산시킨다.

패키지를 바꾸는 작업은 파일 이동으로 끝나지 않는다. Java package 선언과 import, Component Scan, Mapper Scan, AOP Pointcut, XML namespace, 테스트 package를 하나의 변경 단위로 보아야 한다. 일부만 바꾸면 기동 실패나 조용한 횡단 기능 누락이 발생한다.

패키지 설계는 변경 영향도를 가두는 수단이기도 하다. 거래 파라미터 프로그램을 수정했을 때 `co.a`의 Service와 DAO만 조사하면 되는 구조와, 루트 `common`에 업무 규칙이 흩어진 구조는 장애 대응 비용이 다르다. 물리적 응집도가 높으면 코드 소유자, 테스트 범위와 배포 리뷰 범위를 결정하기 쉽다. 반대로 여러 업무가 같은 내부 클래스를 직접 참조하면 작은 변경도 저장소 전체 회귀시험을 요구한다.

운영자는 Java Package를 직접 호출하지 않지만 로그의 클래스명과 Stack Trace에서 Package를 본다. `nhnis.mg.co.a.application.service`는 장애가 업무 실행 중 발생했음을, `nhnis.mg.co.a.persistence.dao`는 MyBatis 경계에 도달했음을 알려준다. 패키지가 책임을 정확히 표현하면 Stack Trace 자체가 실행 경로 지도 역할을 한다.

## 6.2 업무 패키지 기본 형식

`pdmg-service`의 Boot 클래스는 `nhnis.mg`에 있다. `PdmgApplication`은 `nhnis`를 Scan Base로 선언하며, 실제 업무 코드는 `nhnis.mg.co.a` 단일 업무축 아래에 있다.

```java
@SpringBootApplication(scanBasePackages = "nhnis")
@ConfigurationPropertiesScan("nhnis")
public class PdmgApplication { ... }
```

현재 물리 구조는 다음과 같다.

```text
pdmg-service/src/
├─ main/
│  ├─ java/nhnis/mg/
│  │  ├─ PdmgApplication.java
│  │  ├─ ServletInitializer.java
│  │  └─ co/a/
│  │     ├─ entry/
│  │     │  ├─ handler/
│  │     │  └─ aspect/
│  │     ├─ application/
│  │     │  ├─ controller/
│  │     │  ├─ facade/
│  │     │  └─ service/
│  │     ├─ dto/
│  │     ├─ persistence/
│  │     │  └─ dao/
│  │     ├─ client/
│  │     ├─ config/
│  │     └─ support/
│  └─ resources/
│     ├─ rdw.mg.co.a/
│     ├─ db/h2/
│     ├─ application.yml
│     └─ exceptionCode.yml
└─ test/java/
   ├─ nhnis/mg/co/a/
   └─ nhnis/fw/exception/
```

파일시스템에 `entry/web`과 `persistence/file` 디렉터리가 보일 수 있지만 현재 Java 클래스나 `package-info.java`는 확인되지 않는다. 이를 AS-IS 구현 패키지라고 설명하지 않는다. `client`에는 현재 `package-info.java`만 있고, `support`에는 패키지 설명과 함께 실제 `MgTxControlRowSupport`가 존재한다.

업무 패키지 공식은 다음과 같다.

```text
nhnis.mg.[업무코드].[세부업무코드].[계층].[컴포넌트]
```

`mgcoa9000`은 `MG/CO/A`이므로 Java 업무 루트가 `nhnis.mg.co.a`다. 앞의 `nhnis.mg`는 모듈과 애플리케이션 그룹, `co.a`는 업무축, 그 뒤는 기술적 책임을 나타낸다. 업무축 없는 `nhnis.mg.application.service`는 현재 소스에서 제거되었고 신규 표준도 아니다.

`pdmg-fw`는 다른 소유 경계를 가진다. 주요 루트는 `nhnis.fw.commons`, `nhnis.fw.tcf`, `nhnis.fw.exception`이며 레거시 전문 호환 타입은 `com.ims.superspring` 아래에 있다. `pdmg-service`가 공통 Filter나 TCF 클래스를 자기 업무축에 복제하지 않고 이 프레임워크 모듈을 의존하는 이유다.

모듈 경계와 Package 경계를 함께 보아야 한다. `nhnis.fw.tcf.timeout`의 클래스를 `nhnis.mg.co.a.config`로 복사하면 업무 모듈 안에서도 Component Scan은 성공할 수 있다. 그러나 Framework 업그레이드와 업무 배포가 분리되지 않고 같은 기능의 Bean이 중복될 위험이 생긴다. 공통 실행 정책은 `pdmg-fw`, 업무 프로그램과 업무별 인프라 연결은 `pdmg-service`가 소유한다는 기준을 유지한다.

`com.ims.superspring`은 `nhnis` Scan Root 밖에 있지만 대부분 DTO 기반 타입이므로 Spring Component로 발견될 필요는 없다. “Scan 밖에 있다”가 곧 오류는 아니다. 객체가 Bean이어야 하는지, 단순 Java 타입으로 import되는지를 먼저 구분해야 한다.

## 6.3 `entry` 패키지

`entry`는 시스템 외부 또는 프레임워크 라우팅에서 업무 애플리케이션으로 들어오는 Inbound 경계를 담는다. 현재 `nhnis.mg.co.a.entry` 아래에는 `handler`와 `aspect`가 있다. 업무 Controller는 현재 `entry`가 아니라 `application.controller`에 있다는 점을 AS-IS로 구분해야 한다.

TCF ON에서 실제 업무 진입 컴포넌트는 `entry.handler.mgcoa9000Handler`다. 공통 `OnlineTransactionController`와 `TransactionDispatcher`가 Service ID로 Handler를 선택하면 Handler가 같은 업무축의 Facade를 호출한다.

```text
TCF ON 요청
  → pdmg-fw OnlineTransactionController
  → TransactionDispatcher
  → nhnis.mg.co.a.entry.handler.mgcoa9000Handler
  → nhnis.mg.co.a.application.facade.mgcoa9000Facade
```

Handler 패키지에는 HTTP 전문 조립, DTO 변환, 업무 계산과 SQL을 넣지 않는다. 라우팅과 Facade 호출만 두어 Inbound 경계가 업무 실행 세부에 오염되지 않게 한다. Handler가 DAO를 직접 주입하면 `entry → persistence`의 지름길이 생기고 Facade의 DTO 변환과 트랜잭션 선언을 우회한다.

`entry.aspect`에는 `BizPrePostAspect`와 `PdmgBizTxFlowAspect`가 있다. Aspect는 다른 패키지의 메서드를 가로채는 횡단 컴포넌트이므로 물리적으로 entry 아래에 있지만 일반 Handler의 호출 대상은 아니다. Service가 Aspect를 import하거나 직접 호출해서도 안 된다.

저장소 공통 아키텍처는 Controller를 `entry.web`, Facade를 `entry.facade`에 두는 방향을 권장한다. 현재 PDMG에는 `entry.web` 구현이 없고 `application.controller`, `application.facade`를 사용한다. 따라서 현행 유지 개발은 AS-IS 위치를 따르되, 구조 전환을 할 때는 이름만 옮기지 말고 Pointcut과 ON/OFF 경로, 테스트를 함께 변경해야 한다.

## 6.4 `application` 패키지

`application`은 한 거래의 유스케이스를 조정하고 업무 절차를 실행하는 중심 영역이다. 현재 PDMG에는 `controller`, `facade`, `service` 세 하위 패키지가 있으며 `rule`은 없다.

```text
nhnis.mg.co.a.application
├─ controller   TCF OFF 호환 HTTP 진입
├─ facade       DTO 변환 + Service 호출 + @Transactional 선언
└─ service      업무 절차 + DAO 호출 + 응답 조립
```

AS-IS `application.controller`는 TCF OFF일 때만 활성화되는 업무 Controller다. 외부 요청을 받는 성격만 보면 entry 계층에 가깝지만 현재 소스의 물리적 위치는 application이다. 이 차이를 무시하고 일부 Controller만 `entry.web`에 추가하면 Component 역할과 AOP 로그 범위가 두 구조로 갈라진다.

`application.facade`는 Handler와 Service 사이의 프로그램 진입 경계다. `mgcoa9000Facade`는 Object 형태의 DTO Body를 typed DTO로 변환하고 Service를 호출한다. 현재 `@Transactional` 선언도 Facade 메서드에 있다. 다만 Timeout ON에서는 외부 `TransactionTemplate`이 Worker Thread에서 최외곽 Transaction을 만들 수 있으므로 패키지 위치만으로 실제 BEGIN 지점을 단정하지 않는다.

`application.service`는 업무 절차를 수행한다. `mgcoa9000Service`는 입력을 검사하고 조건을 구성하며 DAO를 호출한 뒤 DTO를 조립한다. Service는 entry를 역호출하지 않고, persistence와 필요한 client, dto를 사용한다. HTTP Servlet 타입이나 Spring MVC 응답 타입을 Service에 넣으면 application이 Web 기술에 종속된다.

저장소 권장 구조에는 `application.rule`이 있지만 현재 `co.a`에는 Rule 클래스가 없다. 업무 검증과 계산은 Service가 직접 수행한다. 신규 업무에서 독립 정책이 재사용되거나 단위시험 가치가 있다면 `application.rule`을 도입할 수 있지만, 이를 현재 존재하는 AS-IS처럼 그리지 않는다.

허용 방향은 다음과 같이 이해할 수 있다.

```text
entry.handler
    ↓
application.facade
    ↓
application.service
    ├─→ application.rule  (현재 미구현, 권장 확장)
    ├─→ persistence.dao
    ├─→ client
    └─→ dto

금지 예
persistence ─X→ application
service     ─X→ controller
rule        ─X→ entry
```

## 6.5 `dto` 패키지

`nhnis.mg.co.a.dto`는 거래 입출력 계약을 계층과 분리하여 둔다. Controller와 Facade가 입력 DTO를 사용하고, Service가 입력을 읽어 출력 DTO를 만든다. 조회 목록은 `DTOSub` 타입을 통해 반복 구조를 표현한다.

```text
Request dto
  → dto.mgcoa9000S0DTOin
     → application.service
        → dto.mgcoa9000S0DTOout
           └─ List<dto.mgcoa9000S0DTOSub0>
```

DTO를 `application.dto` 아래에 넣지 않는 현재 규칙은 입출력 계약이 Controller, Facade, Service에서 함께 사용된다는 사실을 드러낸다. DTO가 특정 Service의 private 구현 객체가 아니라 거래 계약이라는 의미다.

그러나 모든 데이터 클래스를 dto에 넣는 것은 아니다. DB 테이블 모델, 외부 API 전용 요청, 설정 Properties와 도메인 내부 Value Object는 수명주기와 소유권이 다르다. 현재 PDMG는 DAO 입출력에 `Map<String,Object>`를 많이 사용하고 별도 persistence model은 확인되지 않는다. 이 AS-IS를 근거로 모든 신규 DB 모델도 Map이어야 한다고 일반화하지 않는다.

DTO에는 Service나 DAO를 주입하지 않는다. DTO가 실행 동작을 가지면 직렬화와 복제, 테스트가 업무 컨테이너에 의존한다. DTO는 데이터를 운반하고 전문 메타데이터를 제공하되 거래 흐름을 시작하지 않는다.

잘못된 패키지에 DTO를 만들면 컴파일 import로는 해결될 수 있지만 코드 생성, 전문 검색과 테스트 대응 구조가 깨진다. 생성기 계약을 사용하는 `DataObject` DTO는 파일 이동 시 package 선언뿐 아니라 FieldProperty 참조와 JSON 계약도 함께 검증해야 한다.

DTO 분리는 의존성의 완충 지점이기도 하다. Controller가 DAO의 `Map`을 그대로 반환하면 DB Alias 변경이 HTTP 응답 계약으로 전파된다. Service가 DAO 결과를 거래 DTO로 변환하면 persistence 내부 표현과 외부 전문을 분리할 수 있다. 현재 DTO가 모든 의미에서 순수한 Domain Model은 아니지만, 적어도 SQL Map이 입구와 출구에 직접 노출되는 것을 줄이는 경계로 작동한다.

## 6.6 `persistence` 패키지

`persistence`는 애플리케이션의 영속성 Outbound 경계다. 현재 구현 컴포넌트는 `persistence.dao`의 MyBatis Mapper Interface다. `persistence.file`은 구현 클래스가 없어 확장 후보로만 볼 수 있다.

```text
application.service
   → persistence.dao.mgcoa9000DAO
      → MyBatis Proxy
         → rdw.mg.co.a/mgcoa9000-ORA.xml
            → RDW Database
```

DAO Interface에는 `@RDWMapper`가 붙고, 메서드 이름은 Mapper Statement ID와 일치한다. persistence의 책임은 DB 접근 계약까지다. HTTP Header를 읽거나 업무 승인 여부를 판단하고 응답 DTO를 조립하는 책임은 넣지 않는다.

Transaction은 Service가 DAO를 호출하는 Thread의 Spring Transaction Context에 참여한다. DAO가 persistence에 있다는 이유만으로 새 Transaction을 만들지는 않는다. `rdwSqlSessionTemplate`이 현재 Thread에 바인딩된 Connection을 사용하므로 실제 트랜잭션 경계는 Facade나 Timeout Executor 등 호출 경로를 함께 봐야 한다.

의존 방향은 application에서 persistence로 향한다. DAO가 Service를 호출하면 영속성 구현이 상위 유스케이스에 의존하는 순환 구조가 된다. MyBatis XML은 Java를 import하지 않지만 namespace로 DAO FQCN과 연결되므로 DAO 이동은 XML 계약 변경이다.

## 6.7 `client` 패키지

`client`는 HTTP, EAI 또는 다른 외부 시스템을 호출하는 Outbound Adapter의 위치다. 현재 `nhnis.mg.co.a.client`에는 `package-info.java`만 있고 실제 Client 구현은 확인되지 않는다. 따라서 Client 호출을 AS-IS 흐름에 포함하지 않는다.

새 외부 연계가 필요하면 Business Service가 `RestTemplate`이나 `WebClient`를 직접 구성하기보다 구체적인 `*Client`를 호출하도록 격리한다.

```text
application.service
   → client.CustomerProfileClient
      → HTTP/EAI
         → 외부 시스템
```

위 클래스명은 구조 설명을 위한 예시이며 현재 소스가 아니다. Client 경계를 두면 인증 Header, URL, 재시도, 직렬화와 외부 오류 변환을 업무 절차에서 분리할 수 있다. 테스트에서는 Client를 대체하여 Service의 업무 흐름만 검증하기도 쉽다.

Client는 다른 도메인의 DAO를 우회 호출하는 수단이 아니다. 같은 저장소에 클래스가 있다는 이유로 업무 A Service가 업무 B DAO를 직접 주입하면 B의 내부 데이터 구조에 결합된다. 도메인 간 호출 계약과 동기·비동기 정책은 다음 장에서 상세히 다룬다.

## 6.8 `config` 패키지

`config`는 Spring Bean과 기술 인프라를 조립하는 위치다. 현재 `nhnis.mg.co.a.config`에는 `RdwDataSourceConfig`, `RDWMapper`, `MybatisLogInterceptor`, `SecurityConfig`, `WebMvcConfig`, `CorsProperties`가 있다.

`RdwDataSourceConfig`는 RDW DataSource, `SqlSessionFactory`, `SqlSessionTemplate`, `rdwTransactionManager`를 등록하고 DAO Scan과 Mapper XML 위치를 결합한다. `WebMvcConfig`와 `CorsProperties`는 Web 설정, `SecurityConfig`는 업무 모듈의 보안 조립을 담당한다.

config에 업무 분기나 DTO 조립을 넣으면 안 된다. 설정 클래스는 어떤 Bean을 만들고 연결할지를 결정하지, 고객 상태나 거래 허용 여부를 판단하지 않는다. 반대로 공통 Filter, TCF Timeout, 공통 예외 설정은 `pdmg-fw`의 소유이므로 업무축 config에 복사하지 않는다.

새 업무축을 추가할 때 `RdwDataSourceConfig`를 그대로 복제하면 동일 Bean 이름이 충돌할 수 있다.

```text
rdwDataSource
rdwSqlSessionFactory
rdwSqlSessionTemplate
rdwTransactionManager
```

같은 DB를 사용한다면 기존 DataSource 조립을 공유하고 Mapper Scan 범위를 확장하는 편이 단순하다. 다른 DB를 사용한다면 Bean 이름, Qualifier, SqlSessionTemplate와 TransactionManager를 업무축별로 분리해야 한다. 설정 위치는 폴더 복제가 아니라 인프라 소유권과 DB 경계로 결정한다.

동일 DB 전략에서는 하나의 Connection Pool과 TransactionManager를 공유하므로 서로 다른 업무축 DAO가 같은 Transaction에 참여할 수 있다. 별도 DB 전략에서는 각 DAO가 어느 SqlSessionTemplate에 연결되는지와 분산 트랜잭션 요구를 별도로 판단해야 한다. 단지 업무축이 다르다는 이유로 DataSource를 분리하거나, DB가 다르면서 Bean 이름만 공유하는 두 극단 모두 피한다.

Config 변경은 Profile 설정과 함께 검증한다. `spring.datasource.rdw` 바인딩이 어느 Profile에서 제공되는지, 새 Properties가 `@ConfigurationPropertiesScan` 범위에 있는지, 조건부 Bean의 기본값이 무엇인지 확인한다. Config 클래스가 존재하는 것과 운영 환경에서 필요한 값으로 Bean이 생성되는 것은 다른 문제다.

## 6.9 `support` 패키지

`support`는 분류하기 어려운 코드를 버리는 장소가 아니다. 여러 컴포넌트가 사용하지만 특정 입출력 기술이나 DB에 속하지 않는 제한된 보조 기능을 둔다. 현재 실제 예는 `MgTxControlRowSupport`다. 이 타입은 거래통제 유형과 저장 Row 사이의 순수 변환을 제공하며 Spring Bean이나 DB 접근을 갖지 않는다.

Support에 적합한 코드는 입력과 출력이 명확하고, 상태와 외부 자원 의존이 없으며, 핵심 Use Case를 시작하지 않는 보조 기능이다. 업무 규칙을 `CommonUtil`로 옮겨 Service 경계를 우회하거나, Client 호출과 DAO 접근을 Support에서 수행하면 안 된다.

```text
support/
  ├─ CommonUtil
  ├─ Helper
  ├─ EtcUtil
  ├─ DataUtil
  └─ TempUtil
```

이 구조는 각 클래스의 소유권과 변경 이유를 설명하지 못한다. 클래스가 어디에도 맞지 않는다면 support로 보내기 전에 새로운 업무 정책, Client, persistence adapter 또는 config인지 다시 판단해야 한다. 이름과 패키지 모두 구체적인 책임을 설명할 수 있어야 한다.

Support가 커지면 소비자와 변경 이유를 기준으로 분리한다. 업무 정책이면 Rule, 외부 연계면 Client, 포맷 변환이 특정 전문에 종속되면 해당 Adapter 경계가 더 적절하다.

## 6.10 Mapper 리소스 경로

Mapper XML은 Java Source Package에 들어가지 않지만 동일 업무축을 리소스 디렉터리 이름에 투영한다. 현재 `co.a` DAO의 XML은 `src/main/resources/rdw.mg.co.a/`에 있다.

```text
Java DAO
nhnis.mg.co.a.persistence.dao.mgcoa9000DAO
              │
              │ namespace = DAO FQCN
              ▼
Resource
rdw.mg.co.a/mgcoa9000-ORA.xml
              │
              │ statement id = DAO method
              ▼
SQL
```

`RdwDataSourceConfig`의 실제 리소스 패턴은 다음과 같다.

```java
private static final String MAPPER_LOCATION_PATTERN
        = "classpath*:rdw.*/*.xml";
```

이는 문서의 과거 `classpath*:rdw.mg.co.a/**/*.xml` 설명과 다르다. 현재 패턴은 `rdw.`로 시작하는 한 단계 디렉터리 바로 아래의 XML을 찾으며 재귀 `**`가 아니다. `rdw.mg.co.a/sub/mgcoa9000.xml`처럼 하위 폴더를 더 만들면 현 패턴에 잡히지 않는다.

XML 파일이 로딩되어도 namespace가 DAO FQCN과 다르면 Statement를 찾지 못한다. 반대로 namespace가 맞더라도 XML이 리소스 패턴 밖에 있으면 등록되지 않는다. 경로, namespace와 Statement ID를 세 개의 별도 계약으로 점검해야 한다.

## 6.11 Component Scan

`PdmgApplication`은 `scanBasePackages="nhnis"`를 지정한다. 따라서 `pdmg-service`의 `nhnis.mg.*`뿐 아니라 의존 모듈의 `nhnis.fw.*` Component도 같은 ApplicationContext에 등록된다.

```text
PdmgApplication
  → Component Scan: nhnis
     ├─ nhnis.mg.*
     │  └─ nhnis.mg.co.a.*
     └─ nhnis.fw.*
        ├─ commons.*
        ├─ tcf.*
        └─ exception.*
```

`@Component`, `@Service`, `@RestController`, `@Configuration`, `@Aspect`와 메타 애노테이션 대상이 Scan 범위 안에서 Bean 후보가 된다. `@ConditionalOnProperty`가 붙은 Handler나 Controller는 후보가 된 뒤 환경설정에 따라 실제 등록 여부가 달라진다.

클래스를 `com.company.feature`처럼 `nhnis` 밖으로 옮기면 별도 Scan 설정이 없는 한 Bean이 되지 않는다. 주입 대상 Bean이 없으면 ApplicationContext 기동 시 `NoSuchBeanDefinitionException` 계열 오류가 발생할 수 있다. 호출되지 않는 Component라면 기동은 되어도 기능이 조용히 누락될 수 있다.

넓은 `nhnis` Scan은 Framework와 업무를 함께 발견하는 장점이 있지만 신규 업무축에 Config를 복제하면 같은 기본 Bean 이름이 충돌할 수 있다. Scan 범위 안이라는 사실과 안전하게 등록된다는 사실은 다르다. Bean 이름과 조건, Primary와 Qualifier까지 확인해야 한다.

`@ConfigurationPropertiesScan("nhnis")`도 같은 루트의 Properties 타입을 찾는다. Properties를 다른 루트에 만들면 일반 Component와 마찬가지로 자동 바인딩되지 않을 수 있다.

## 6.12 Mapper Scan

MyBatis DAO는 일반 Component Scan과 다른 경로로 Proxy Bean이 된다. `RdwDataSourceConfig`의 `@MapperScan`이 현재 다음 패키지를 지정한다.

```java
@MapperScan(
    basePackages = "nhnis.mg.co.a.persistence.dao",
    sqlSessionTemplateRef = "rdwSqlSessionTemplate"
)
```

```text
@MapperScan
  → nhnis.mg.co.a.persistence.dao
     → @RDWMapper DAO Interface 발견
        → MyBatis Proxy 생성
           → Spring Bean 등록
              → Service 주입
```

현재 DAO에는 custom `@RDWMapper`가 붙어 있지만 실제 Scan 범위를 결정하는 핵심은 위 `basePackages`다. 새 업무축 `nhnis.mg.ic.b.persistence.dao`를 만들기만 하면 Component Scan에는 포함될 수 있어도 현재 Mapper Scan 범위에는 포함되지 않는다. 그 DAO Proxy는 생성되지 않아 Service 주입이 실패한다.

업무축을 확장할 때는 하나의 `@MapperScan`에 여러 Base Package를 지정하거나 축별 Config를 만들 수 있다. 같은 DB와 SqlSessionTemplate을 쓴다면 범위를 통합하는 방식이 Bean 충돌을 줄인다. 다른 DB라면 각 Scan에 올바른 `sqlSessionTemplateRef`를 연결해야 한다.

Mapper Scan이 성공해도 XML 경로와 namespace가 틀리면 메서드 호출 시 `Invalid bound statement`가 발생한다. Proxy 생성과 Statement 등록은 별도 단계다.

Mapper 관련 실패는 시점을 나누면 빠르게 진단할 수 있다.

```text
기동 시 DAO 주입 실패
  → Mapper Scan / SqlSessionTemplate / Bean 충돌 확인

호출 시 Invalid bound statement
  → XML 리소스 패턴 / namespace / statement id 확인

SQL 실행 후 DB 오류
  → SQL 문법 / 파라미터 / Schema 확인
```

세 장애는 모두 DAO 호출 근처에서 보이지만 원인이 다르다. Package와 Scan 계약을 먼저 확인하면 SQL 자체를 불필요하게 수정하는 일을 줄일 수 있다.

## 6.13 Aspect Pointcut와 패키지

현재 업무 선후처리는 애노테이션이 아니라 Package 기반 Pointcut으로 Service public 메서드를 선택한다.

```java
@Pointcut(
  "execution(public * nhnis.mg.co.a.application.service..*(..))"
)
```

`BizPrePostAspect`의 이 표현식은 `co.a.application.service` 아래의 public 메서드만 대상으로 한다. Service를 `nhnis.mg.ic.b.application.service`나 `nhnis.mg.co.a.service`로 옮기고 Pointcut을 확장하지 않으면 Bean은 정상 등록되고 업무 메서드도 실행되지만 업무 선처리와 정상 반환 후 후처리가 실행되지 않는다. 컴파일이나 기동 단계에서 잡히지 않는 조용한 런타임 결함이다.

`PdmgBizTxFlowAspect`는 더 넓은 다섯 구간을 대상으로 한다.

```text
nhnis.mg.co.a.entry.handler..
nhnis.mg.co.a.application.facade..
nhnis.mg.co.a.application.controller..
nhnis.mg.co.a.application.service..
nhnis.mg.co.a.persistence.dao..
```

클래스를 표준 패키지 밖으로 옮기면 TX-FLOW 시작·종료 로그도 사라진다. 패키지 리팩터링 후 기능 결과만 확인하면 이런 관측성 손실을 놓칠 수 있다. 선후처리 로그와 Pointcut 적용 테스트까지 확인해야 한다.

Aspect 자신은 `entry.aspect`에 있지만 대상은 application과 persistence다. 물리적 위치와 적용 대상은 다르다. 또한 현재 두 Aspect는 `nhnis.fw.commons.legacy-web.enabled` 조건에 의해 Bean 등록 여부가 결정된다. 패키지와 설정 조건을 함께 봐야 실제 AOP가 동작하는지 판단할 수 있다.

새 업무축을 추가할 때 Pointcut 문자열을 매번 복제하는 방식은 누락 위험이 크다. TO-BE로 공통 marker 애노테이션이나 승인된 상위 패키지 규칙을 검토할 수 있지만, 적용 범위를 넓히면 원치 않는 공통 Service까지 가로챌 수 있으므로 테스트와 성능 영향을 함께 판단해야 한다.

Package 기반 Pointcut은 구조 규율을 강제하는 장점과 리팩터링에 취약한 단점을 함께 가진다. 애노테이션 기반 Pointcut은 위치 변경에 강하지만 개발자가 애노테이션을 빼먹을 수 있다. 어느 방식을 선택하더라도 CI가 대상 Bean 목록이나 Advice 실행을 검증해야 한다. 현재 AS-IS는 Package 기반이므로 신규 업무축 작업에 Pointcut 변경을 필수 산출물로 포함한다.

업무 선처리는 정상 반환에 `@AfterReturning`을 사용한다. Service를 Pointcut 밖으로 이동하면 예외가 발생하지 않더라도 응답 로그와 후처리가 빠진다. 기능 데이터만 비교하는 테스트보다 Advice 실행 횟수나 기대 로그 구간을 확인하는 통합시험이 필요한 이유다.

## 6.14 신규 업무축 추가 방법

다음 절차는 분류표에 승인된 `IC/B` 업무축을 추가한다는 개념 예시다. 실제 코드 배정과 Program ID는 별도 승인이 필요하다.

### STEP 1. 업무코드와 소유권을 확정한다

입력은 업무 요구사항과 분류표다. 결과는 `MG/IC/B` 같은 승인된 축이다. 기존 `co.a`에 속할 업무를 새 축으로 분리하지 않았는지 검토한다.

### STEP 2. 업무 Root Package를 만든다

Java Root는 `nhnis.mg.ic.b`, Mapper Root는 `rdw.mg.ic.b`가 된다. 두 축의 철자와 소문자를 맞춘다. `nhnis.mg.ic`나 `nhnis.mg.business.ic.b`처럼 임의 단계를 추가하지 않는다.

### STEP 3. 필요한 Inbound와 application 구조를 만든다

TCF ON이면 `entry.handler`, 현행 PDMG 배치를 유지하면 `application.facade`와 `application.service`가 필요하다. TCF OFF 호환이 요구될 때만 `application.controller`를 추가한다. 독립 Rule이 필요하면 저장소 권장 `application.rule`을 검토한다.

### STEP 4. DTO와 persistence를 배치한다

거래 DTO는 `nhnis.mg.ic.b.dto`, DAO는 `nhnis.mg.ic.b.persistence.dao`에 둔다. Mapper XML은 `resources/rdw.mg.ic.b/`에 둔다. DAO package와 XML namespace를 완전히 일치시킨다.

### STEP 5. Client·Config·Support 필요성을 판단한다

외부 연계가 있을 때만 client를 만들고, 독립 인프라 조립이 필요할 때만 config를 만든다. 같은 RDW를 사용한다면 `RdwDataSourceConfig`를 복사하지 말고 기존 Mapper Scan 확장을 우선 검토한다. Support는 구체적인 순수 보조 기능이 있을 때만 만든다.

### STEP 6. Component Scan을 검증한다

`nhnis.mg.ic.b`는 현재 `scanBasePackages="nhnis"` 아래이므로 일반 Component 후보가 된다. 기동 테스트에서 Handler, Facade, Service Bean과 조건부 Controller의 ON/OFF 상태를 확인한다.

### STEP 7. Mapper Scan과 XML 로딩을 확장한다

현재 고정된 `nhnis.mg.co.a.persistence.dao`에 새 DAO Package를 추가한다. XML 디렉터리는 `classpath*:rdw.*/*.xml` 패턴에 맞는지 확인한다. Proxy Bean 생성과 Statement 호출을 각각 테스트한다.

### STEP 8. AOP Pointcut을 확장한다

`BizPrePostAspect`와 `PdmgBizTxFlowAspect`의 현재 `co.a` 표현식은 새 축을 포함하지 않는다. 새 Service와 Handler, DAO가 어느 Advice 대상이어야 하는지 결정하고 Pointcut 및 테스트를 변경한다.

### STEP 9. Test Package를 대응시킨다

`src/test/java/nhnis/mg/ic/b/...`에 Production Package와 같은 구조의 테스트를 둔다. 단위테스트뿐 아니라 Spring Context, Mapper Proxy와 AOP 적용을 검증하는 통합시험을 포함한다.

### STEP 10. Build와 Boot를 검증한다

컴파일, 해당 모듈 Test, 애플리케이션 기동 순으로 확인한다. Bean 중복, 누락, Mapper Statement 미등록, Pointcut 미적용과 TCF ON/OFF 라우팅을 점검한다. 파일이 올바른 디렉터리에 있다는 것만으로 완료하지 않는다.

검증은 실패를 의도적으로 포함해야 한다. 존재하지 않는 Statement 호출이 표준 MyBatis 오류로 드러나는지, 신규 Service가 업무 선후처리 대상인지, TCF ON에서 Handler만 활성화되고 OFF에서 Controller가 활성화되는지를 확인한다. 조건부 Bean은 한 Profile의 성공만으로 두 경로를 검증했다고 볼 수 없다.

업무축 추가 Diff에는 Java 파일 외에도 Mapper XML, Config 또는 Scan 변경, Pointcut, 테스트와 문서가 함께 나타나야 한다. 그중 하나가 없다면 “필요 없어서 제외”인지 “누락”인지 리뷰에서 명시한다.

신규 업무축 추가의 핵심은 Tree 복제가 아니다. Package 축을 Scan, AOP, MyBatis와 테스트의 동일한 축으로 확장하는 작업이다.

## 6.15 테스트 패키지

테스트 Source는 Production FQCN을 거울처럼 따라간다. 현재 실제 테스트는 다음과 같다.

```text
src/test/java/
├─ nhnis/mg/co/a/
│  ├─ application/service/mgcoa5530ServiceTest.java
│  ├─ config/SecurityConfigTest.java
│  └─ dto/mgcoa8888D0DTOinBindTest.java
└─ nhnis/fw/exception/ExceptionCodePropertiesTest.java
```

현재 Handler, Facade, DAO와 Controller 전용 테스트는 확인되지 않는다. 배치 원칙상 추가한다면 Production Package와 같은 상대 경로를 사용한다. `mgcoa9000HandlerTest`는 `nhnis.mg.co.a.entry.handler`, `mgcoa9000DAOTest`는 `nhnis.mg.co.a.persistence.dao`가 자연스럽다.

동일 package를 사용하면 package-private 멤버 접근이 필요한 단위시험과 클래스 탐색이 쉬워진다. 그러나 테스트 편의를 위해 Production 접근제어를 약화시키거나 모든 테스트를 한 `test` 패키지에 몰아서는 안 된다.

패키지 장에서 중요한 테스트는 위치뿐 아니라 구조 계약이다. `@SpringBootTest`는 Component Scan과 조건부 Bean을, MyBatis 통합시험은 Mapper Scan과 XML namespace를, AOP 시험은 Pointcut이 실제 대상에 적용되는지를 검증한다. 상세 테스트 전략은 33장에서 다룬다.

새 업무축 테스트가 `nhnis` 밖의 임의 패키지에 있더라도 JUnit은 실행할 수 있지만 Spring의 자동 구성이나 package 기반 테스트 설정을 다르게 받을 수 있다. Production과 대응시키는 규칙은 테스트 실행 문맥을 예측 가능하게 한다.

## 6.16 금지 패키지 패턴

첫 번째 Anti Pattern은 업무축을 잃은 기술별 Dump다.

```text
nhnis.mg/
├─ controller/
├─ service/
└─ dao/
```

이 구조는 `CO/A`와 다른 업무의 소유권을 구분하지 못한다. 클래스 수가 늘면 같은 이름 충돌과 순환 의존을 부르고, Service ID에서 Source 위치를 역산할 수 없다.

두 번째는 비대한 `common`이다. 여러 업무에서 한 번씩 사용한다는 이유만으로 코드를 `common`에 옮기면 공통 모듈이 모든 업무를 의존하는 역전이 발생한다. 공통화는 사용 횟수가 아니라 안정된 책임과 의존 방향으로 판단한다.

세 번째는 support의 쓰레기통화다. `Helper`, `Manager`, `TempUtil`을 support에 쌓으면 업무 규칙, 외부 호출과 변환 로직이 한 곳에 섞인다. Support 코드는 순수하고 제한된 보조 책임을 가져야 한다.

네 번째는 역방향 의존이다.

```text
persistence ─X→ application
DAO         ─X→ Controller
DTO         ─X→ Service 호출
Rule        ─X→ Web Request
```

하위 계층이 상위 실행 흐름을 호출하면 테스트와 교체가 어려워지고 순환 참조가 생긴다. Spring Bean 순환 의존으로 기동이 실패하거나, Transaction Proxy를 우회하는 호출이 생길 수도 있다.

다섯 번째는 다른 업무의 내부 DAO를 직접 호출하는 구조다. 업무 A Service가 업무 B DAO를 주입하면 B의 테이블과 SQL 변경이 A에 전파된다. 공개된 Facade나 Client 계약을 사용할지, 공통 소유로 옮길지는 7장의 도메인 호출 정책으로 결정한다.

여섯 번째는 패키지만 이동하고 런타임 문자열을 남기는 변경이다. Java import를 모두 고쳐 컴파일이 성공해도 다음이 남을 수 있다.

- `@MapperScan`의 과거 Base Package
- Mapper XML의 과거 namespace
- `BizPrePostAspect`와 TX-FLOW Pointcut
- 테스트 package와 Mock 대상 FQCN
- 문서와 코드 생성 템플릿

이러한 문자열 참조는 IDE의 일반 Rename이 모두 찾아주지 못할 수 있다. 패키지 이동 전후에 이전 FQCN을 `rg`로 검색하고, XML과 설정, Markdown까지 확인한다. 빌드 성공은 컴파일 계약을 증명하지만 아직 호출되지 않은 Mapper와 AOP 적용을 증명하지 않는다.

일곱 번째는 Production과 Test의 패키지 구조 불일치다. 테스트를 한곳에 모으면 어떤 업무축의 규칙을 검증하는지 불명확해지고 package-private 접근 또는 Slice Test 구성이 달라질 수 있다. 테스트 공통 Fixture가 필요하면 업무 테스트를 이동시키는 대신 별도 Test Support 책임을 구체적으로 정의한다.

현재 문서가 과거에 금지했던 `entry.facade`와 `entry.controller`는 맥락을 구분해야 한다. `entry.facade`는 저장소 공통 권장 구조이므로 절대 금지가 아니다. 현재 PDMG AS-IS와 섞어 일부 클래스만 옮기는 비일관성이 문제다.

### 신규 업무축 생성 체크리스트

- 업무·세부업무 코드가 분류표에 승인되었는가?
- Java 업무 Root와 Mapper Resource 축이 일치하는가?
- Handler, application, dto와 persistence가 책임에 맞게 배치되었는가?
- 필요하지 않은 client, config, support를 관성적으로 복제하지 않았는가?
- Component Scan 범위 안에 있으며 Bean 이름 충돌이 없는가?
- Mapper Scan이 신규 DAO를 포함하고 올바른 SqlSessionTemplate을 사용하는가?
- XML 경로가 `classpath*:rdw.*/*.xml`에 포함되는가?
- DAO FQCN과 namespace가 일치하는가?
- 업무 선후처리와 TX-FLOW Pointcut이 신규 축을 포함하는가?
- Production과 대응하는 Test Package와 기동·통합시험이 있는가?

### 아키텍처 판단 포인트

패키지에서 업무 경계와 계층 책임이 동시에 드러나야 한다. 의존이 entry에서 application, application에서 persistence나 client로 흐르는지 확인한다. Component Scan 안에 있다는 이유만으로 안전하다고 판단하지 말고 Bean 조건과 이름 충돌을 본다. Mapper Scan, XML 패턴과 namespace는 각각 검증한다. Package 기반 AOP가 조용히 누락되지 않았는지 로그와 테스트로 확인한다. Support와 Common이 커지거나 다른 업무의 내부 DAO를 직접 참조하면 경계를 다시 설계한다.

이 장의 핵심은 Package가 Source 위치와 Runtime 선택 규칙을 동시에 표현한다는 점이다. 올바른 Tree는 사람의 탐색을 돕고, Spring과 MyBatis, AOP가 같은 구조를 해석하게 만든다. 신규 업무축은 폴더를 복사하는 작업이 아니라 이 해석 규칙 전체를 일관되게 확장하는 작업이다.

지금까지는 프로그램의 클래스가 어느 Package에 위치해야 하는지를 살펴보았다. 하지만 Package를 잘 나누었다고 해서 업무 간 호출 관계가 자동으로 올바르게 만들어지는 것은 아니다. 다음 장에서는 PDMG의 도메인 경계를 정의하고 하나의 도메인이 다른 도메인을 어떤 방식으로 호출해야 하는지 살펴본다.
