# 27장. 이미지로그와 GUID 추적

온라인 장애를 분석할 때 “오후에 오류가 났다”는 정보만으로는 부족하다. 요청을 받은 시점의 전문, 실행한 Service ID, 사용자와 단말, 최종 응답과 예외를 한 건으로 연결해야 한다. PDMG는 표준 Header의 `std_gbl_id`를 GUID로 사용하고 `TB_FW_IMAGE_LOG`에 요청과 응답의 스냅샷을 남긴다. 이 데이터는 업무 결과를 재현하는 원장이 아니라, 한 거래가 시스템 경계를 어떻게 통과했는지 추적하는 운영 증거다.

현행 구현의 핵심은 `ServicePreventionInterceptor`와 `ImageLogHandler`다. Interceptor의 preHandle이 업무 실행 전에 요청 행을 만들고, afterCompletion이 정상·표준 오류 응답을 갱신하거나 전달된 예외를 기록한다. 저장 실패는 catch하여 로그만 남기는 fail-open 방식이다. 이 선택은 본거래 가용성을 보호하지만 감사 공백을 허용하므로 운영 경보가 반드시 필요하다.

## 27.1 이미지로그의 목적

이미지로그는 세 질문에 답한다. 어떤 요청이 들어왔는가, 어느 거래가 이를 처리했는가, 어떤 응답 또는 실패로 끝났는가. GUID는 애플리케이션 로그, ServiceContext, TransactionContext, 요청·응답 전문과 이미지로그 행을 연결하는 상관관계 키다. 하지만 GUID 그 자체가 사용자 인증이나 업무 데이터의 기본키는 아니다. 클라이언트가 같은 GUID를 재사용할 수도 있으므로 유일한 물리 행과 실제 거래 시도의 개념을 구분해야 한다.

## 27.2 `TB_FW_IMAGE_LOG`

H2 Schema에서 GUID는 VARCHAR(64) PK다. 나머지 컬럼은 SERVICE_ID, SCREEN_ID, OPTR_ENO, CLIENT_IP, REQUEST_TIME, RESPONSE_TIME, EXCEPTION_TYPE, EXCEPTION_CODE, EXCEPTION_MSG다. `ImageLogHandler`는 기동 시 REQUEST_MSG와 RESPONSE_MSG 컬럼 존재 여부를 H2 또는 Oracle Catalog로 확인하고 없으면 CLOB으로 추가하려 한다. 이 런타임 DDL은 편리하지만 운영 계정 권한과 Schema 변경 통제에 맞는지 검토해야 한다.

| 컬럼군 | 의미 | 주요 생성 시점 |
|---|---|---|
| GUID·Service·Screen | 거래 상관관계와 호출 대상 | 시스템 선처리 |
| OPTR_ENO·CLIENT_IP | 조작자와 단말 단서 | 시스템 선처리 |
| REQUEST_TIME·REQUEST_MSG | 서버 수신시각과 요청 전문 | pre image log |
| RESPONSE_TIME·RESPONSE_MSG | 서버 종료시각과 응답 전문 | post/exception image log |
| EXCEPTION_* | 실패 유형·코드·메시지 | 표준 오류 또는 예외 종료 |

## 27.3 요청 ImageLog INSERT

`DefaultFilter`가 ServiceContext와 요청 원문을 준비한 뒤 Interceptor preHandle이 Header를 보정한다. GUID가 없으면 생성하고, 전문을 CORE 로그에 출력한 다음 `preImagelog(header, requestRaw)`을 호출한다. 요청시각은 클라이언트 Header의 업무일시가 아니라 서버 현재시각으로 설정된다.

메서드 이름은 INSERT이지만 실제 영속화는 update-first다. 동일 GUID 행이 있으면 서비스·화면·사용자·IP·요청시각·요청 전문을 덮어쓰고 이전 응답·예외 컬럼을 null로 초기화한다. 0건일 때 INSERT하며, 동시 INSERT 경합으로 DuplicateKeyException이 나면 다시 UPDATE한다. 재전송의 PK 오류는 줄이지만 동일 GUID의 이전 감사 흔적을 소거하는 결과가 있다.

## 27.4 업무 처리

preHandle이 true를 반환한 뒤 Controller, TCF, Handler, Facade, Service, DAO가 실행된다. 이 구간의 로그 MDC와 ServiceContext는 같은 GUID를 참조한다. timeout이 활성화되면 업무는 Worker Thread로 이동하며 `OnlineTimeoutWorkerContext`가 ServiceContext, MDC, request attributes를 캡처하고 Worker에 설치한 뒤 finally에서 제거한다. 따라서 업무 로그의 GUID는 이어질 수 있다.

이미지로그의 pre/post 콜백 자체는 Servlet 요청 Thread의 Interceptor에서 실행된다. Worker 업무 Transaction이 끝난 뒤 결과 또는 예외가 요청 Thread로 돌아와야 afterCompletion이 최종 행을 갱신한다. 취소 후 Worker가 계속 실행되는 비정상 상황에서는 클라이언트 응답시점과 실제 DB 작업 종료시점이 다를 수 있음을 GUID 분석에 포함해야 한다.

## 27.5 응답 ImageLog UPDATE

`ResponseBodyArgumentResolver`가 조립한 응답 원문을 ServiceContext에 저장한다. Interceptor postHandle은 로깅 위치만 유지하고 ImageLog를 쓰지 않는다. 실제 정상 후처리는 afterCompletion의 `postImagelog()`다. RESPONSE_TIME과 RESPONSE_MSG를 GUID 행에 UPDATE하고 요청 전문이 null이면 Context의 요청 원문으로 보완한다.

응답 JSON에 `result.stdErrCode`가 있으면 정상 post가 아니라 exception 컬럼 갱신 경로를 사용한다. UPDATE가 0건이면 정상 post는 경고만 남기지만 예외 post는 새 행을 INSERT한다. pre 저장 실패 뒤에도 예외 기록은 남길 기회를 갖지만, 정상 응답은 행이 없으면 복구 INSERT하지 않는 비대칭이 존재한다.

## 27.6 정상 거래 이미지로그

정상 흐름에서 pre가 행을 생성하고 업무가 commit된 뒤 응답 Advice가 `{hdr_nhnis, dto}`를 만든다. afterCompletion에는 보통 `ex=null`이고 postImagelog가 응답시각과 전문을 채운다. EXCEPTION 컬럼은 null로 남는다. 조회 화면은 REQUEST_TIME 내림차순, GUID 내림차순으로 보여준다.

```text
Filter: GUID/Context
  → Interceptor.preHandle: UPDATE-first 또는 INSERT 요청행
  → Worker/업무 TX: commit
  → ResponseBodyAdvice: 응답 원문을 Context에 저장
  → Interceptor.afterCompletion(ex=null)
  → UPDATE response fields
```

## 27.7 실패 거래 이미지로그

실패에는 두 경로가 있다. 예외가 MVC까지 미처리 상태로 전달되면 afterCompletion의 `ex`가 존재하여 `exceptionImagelog()`가 Throwable 유형과 코드를 기록하고 예외를 다시 던진다. 예외 Handler가 이미 오류 응답을 만들었다면 afterCompletion의 `ex`는 null일 수 있고, postImagelog가 `result.stdErrCode`를 파싱해 예외 컬럼을 채운다.

BizException은 코드와 message를 기록하지만 현재 message가 코드 자체일 수 있다. 일반 Throwable에는 코드가 없고 message만 제한 길이로 저장된다. timeout과 overload는 각각 표준 코드를 부여한다. 예외 메시지에 SQL이나 개인정보가 포함될 가능성이 있으므로 truncate만으로는 충분하지 않고 저장 전 sanitizing이 필요하다.

## 27.8 업무 트랜잭션과의 분리

이미지로그 JDBC는 Handler가 주입받은 DataSource로 직접 실행한다. pre는 업무 Transaction이 시작되기 전 Servlet Thread에서 호출되고, post는 업무 Transaction 완료 후 요청 Thread에서 호출된다. timeout Worker의 TransactionTemplate과도 Thread가 다르다. 따라서 일반 실행에서는 이미지로그가 업무 Transaction과 같은 물리 Transaction에 묶인다고 볼 수 없으며, 각 JDBC 호출은 별도로 완료될 가능성이 높다.

명시적인 이미지로그용 TransactionManager나 REQUIRES_NEW Annotation은 없다. “완전히 보장된 독립 Transaction”이라고 표현하기보다는 호출 위치상 업무 TX 외부이며 실패를 삼키는 별도 JDBC 기록이라고 판정하는 것이 정확하다. 로그 DB가 업무 DB와 같은 DataSource라는 점도 자원 고갈 영향까지 격리한다는 뜻은 아니다.

## 27.9 이미지로그 조회 `mgcoa8888S0`

조회 거래는 GUID, Service ID, Screen ID, 조작자, 예외 여부, 요청시간 범위, 최소 경과초 조건을 지원한다. Mapper는 count와 Oracle ROWNUM 페이징 조회를 수행하며 전문 CLOB을 DTO 문자열로 변환한다. Facade에는 readOnly `rdwTransactionManager`가 선언되어 있다.

조회 자체도 일반 온라인 거래이므로 Interceptor pre/post를 통과해 자기 이미지로그를 만든다. 결과 전문에 다른 행들의 요청·응답 전문이 포함되면 조회 거래의 RESPONSE_MSG가 다시 커지고 민감정보가 복제될 수 있다. 관리 거래의 ImageLog 정책과 응답 크기 제한을 별도로 정할 필요가 있다.

## 27.10 이미지로그 삭제 `mgcoa8888D0`

삭제 거래는 입력 GUID 목록을 정리하고 MyBatis foreach 바인딩으로 해당 행들을 삭제한다. Facade는 rollbackFor Exception의 쓰기 Transaction을 사용한다. 삭제 요청 역시 pre에서 자기 GUID 행을 만든다. 대상 목록에 현재 요청 GUID가 포함되면 업무 중 자신의 pre 행을 지울 수 있고, 정상 afterCompletion은 UPDATE 0건 경고만 남겨 최종 로그가 사라진다.

감사 데이터 삭제는 단순 CRUD가 아니다. 보존기간, 법적 보존, 승인자, 삭제 주체와 사유, 삭제 자체의 별도 불변 감사 이력이 필요하다. 현행 Service에서 그러한 승인 워크플로는 확인되지 않았다.

## 27.11 자기 자신에 대한 로그 생성

조회와 삭제 거래를 이미지로그 대상에서 제외하는 조건은 Interceptor에 없다. 따라서 `mgcoa8888S0`와 `mgcoa8888D0`도 일반 거래처럼 기록된다. 이는 관리자 활동을 감사할 수 있다는 장점이 있지만 조회 응답 전문의 재귀적 복제, 테이블 증가, 자기 삭제 같은 부작용이 있다. TO-BE 선택지는 메타데이터만 기록하거나 전문을 생략하는 전용 정책이지, 관리 거래 전체를 흔적 없이 면제하는 것이 아니다.

## 27.12 감사 로그 보존

저장소에는 자동 보존기간, Partition, Archive, 배치 삭제 정책이 확인되지 않는다. REQUEST/RESPONSE CLOB은 빠르게 증가하므로 용량과 조회 성능을 함께 관리해야 한다. 보존 등급은 거래 유형과 개인정보 민감도별로 나누고, 만료 삭제는 승인된 배치와 별도 감사 이력을 사용한다. 운영자는 pre만 있고 response가 없는 고아 행을 장애 신호로 탐지해야 한다.

## 27.13 민감정보 마스킹

현행 `resolveWireMsg()`는 전문 길이를 최대 20,000자로 제한하지만 비밀번호, Access/Refresh Token, 계좌·개인정보를 필드별 마스킹하는 코드가 확인되지 않았다. Interceptor의 요청 CORE 로그도 원문을 그대로 출력한다. 잘라내기는 마스킹이 아니다. 민감값이 앞부분에 있으면 그대로 저장된다.

마스킹은 로그 저장 직전에 공통 JSON field 정책으로 수행하고 요청·응답·텍스트 로그에 동일하게 적용해야 한다. 구조 파싱 실패 시 원문을 저장하는 fallback보다 전문 미저장과 보안 경보가 안전할 수 있다. 마스킹 전 원문을 debug 로그에 남기지 않으며 운영 조회 API에도 접근통제와 추가 마스킹을 적용한다.

## 27.14 GUID 기반 장애 추적

장애 분석은 클라이언트가 받은 GUID로 시작한다. 이미지로그에서 요청·응답 시각과 Service ID, 예외 코드를 확인하고 같은 GUID의 CORE/BIZ/SQL 로그를 시간순으로 연결한다. response가 없으면 Filter 이후 중단, 프로세스 종료, post 저장 실패, timeout 경계를 후보로 본다. pre 행 자체가 없으면 GUID 누락, multipart 면제, Interceptor 미등록 또는 ImageLog DB 실패를 점검한다.

동일 GUID 재사용 시 행은 최신 pre 정보로 덮이므로 로그 파일의 timestamp와 대조해야 한다. GUID 하나가 거래 시도 하나라는 가정이 깨질 수 있기 때문이다. TO-BE에서는 서버가 외부 correlation ID와 내부 attempt ID를 분리하거나 중복 GUID를 거부·버전화하는 방안을 검토한다.

### End-to-End 흐름과 현재 경계

```text
Request
  → DefaultFilter: GUID·ServiceContext·MDC
  → Interceptor pre: UPDATE-first → 0건 INSERT
  → 업무 Worker: Context/MDC 전파 + 업무 TX
  → 정상 dto 또는 표준 result 생성
  → afterCompletion
       ├─ ex != null       → exception UPDATE → 0건 INSERT
       ├─ result error     → exception UPDATE → 0건 INSERT
       └─ normal response  → response UPDATE → 0건 경고
  → mgcoa8888S0 조회 / 보존·삭제 운영
```

### 책임·정상·실패 비교

| 구간 | 책임 | 정상 | 실패 영향 |
|---|---|---|---|
| Filter/Interceptor | GUID와 선처리 행 준비 | 요청 추적 시작 | 저장 실패를 삼키고 업무 계속 |
| 업무 Worker | 같은 Context로 업무 실행 | commit/rollback | timeout 시 응답과 실제 종료 차이 가능 |
| Response Advice | Wire 응답을 Context에 저장 | post가 전문 사용 | 조립 전 실패면 응답 전문 부족 |
| ImageLogHandler | update/insert, 예외 분류 | 단일 행 완성 | fail-open, 운영 경보 필요 |
| 관리 거래 | 조회·삭제 | 운영 추적 | 자기 로그 생성·삭제 부작용 |

### Anti Pattern

- GUID를 업무 DB 기본키나 인증 증표로 사용한다.
- 같은 GUID 재사용이 안전하다고 본다. 현행 update-first는 이전 기록을 덮어쓴다.
- 업무 rollback이면 이미지로그도 함께 rollback된다고 단정한다. 호출 Thread와 TX 경계가 다르다.
- 전문 길이 제한을 개인정보 마스킹으로 오해한다.
- ImageLog DB 오류를 삼키고 경보도 내지 않는다. 감사 공백이 장기간 발견되지 않는다.
- 조회/삭제 거래의 응답 전문을 무제한 다시 ImageLog에 넣는다.

- [ ] 정상, BizException, timeout, Handler 오류가 각기 행을 완성하는가?
- [ ] pre 실패 뒤 정상 post 0건이 모니터링되는가?
- [ ] 동일 GUID 순차 재전송과 동시 경합 결과를 테스트했는가?
- [ ] 요청·응답과 CORE 로그에 동일 마스킹 정책이 적용되는가?
- [ ] 이미지로그 장애가 업무 DB Pool까지 소진시키지 않는가?
- [ ] 관리 거래의 자기 로그와 자기 삭제 정책이 정의되어 있는가?
- [ ] 보존기간, Archive, 삭제 승인과 불변 삭제 이력이 있는가?
- [ ] 조회 권한과 전문 필드 접근이 최소화되어 있는가?

### 아키텍처 판단과 다음 장

이미지로그를 fail-open으로 둘지는 거래 가용성과 감사 의무의 균형으로 결정한다. 같은 DB를 쓰는 단순성, 별도 DB·Queue를 쓰는 격리성, 동기 저장의 즉시성과 비동기 저장의 내구성 사이에서 요구사항을 먼저 정해야 한다. 어떤 방식이든 전문 마스킹, 중복 GUID 의미, 저장 실패 감지는 선택 사항이 아니다.

GUID와 ImageLog가 한 건의 사실을 추적한다면, 다음 단계는 여러 거래의 지연·Pool·Thread 상태를 묶어 시스템 징후를 찾는 것이다. 다음 장에서는 이 추적 정보를 성능 감시와 운영 진단 지표로 확장하는 방법을 실제 Runtime Monitor와 조회 구조를 중심으로 살펴본다.
