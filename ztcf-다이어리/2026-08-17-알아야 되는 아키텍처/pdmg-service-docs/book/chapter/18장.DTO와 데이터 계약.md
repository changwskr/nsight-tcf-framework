# 제4부 업무 진입과 유스케이스 경계

# 18장. DTO와 데이터 계약

온라인 거래는 JSON, Java 객체, SQL 파라미터와 화면 상태 사이를 이동한다. 각 구간이 같은 `Map`을 공유하면 빠르게 만들 수 있지만 필드 오타와 타입 변화가 실행 중에야 드러나고, 시스템 공통값과 업무 입력의 신뢰 경계도 흐려진다. PDMG의 DTO는 단순 값 보관 객체가 아니라 Service ID별 요청·응답 계약을 Java 타입으로 고정하는 장치다.

PDMG 표준 전문은 `hdr_nhnis`와 `dto`를 분리한다. Header는 Framework가 해석해 ServiceContext로 관리하고, `dto`는 업무 모듈의 `DTOin`으로 변환된다. Service가 만든 `DTOout`은 공통 ResponseBodyAdvice가 다시 표준 응답 봉투의 `dto`에 넣는다. 이 장은 그 변환 경계와 DTOin·DTOout·DTOSub의 책임을 실제 구현 기준으로 설명한다.

## 이 장에서 해결할 질문

- DTOin, DTOout, DTOSub는 각각 어떤 계약을 표현하는가?
- Service ID 전체를 DTO 이름에 넣는 이유는 무엇인가?
- TCF ON과 OFF에서 JSON이 DTOin으로 바뀌는 위치는 어떻게 다른가?
- 현재 Bean Validation은 실제 적용되어 있는가?
- Header·ServiceContext와 업무 DTO를 왜 분리해야 하는가?
- DAO Map, 도메인 모델과 업무 DTO를 어디까지 공유할 수 있는가?
- DataObject의 메타 필드는 최종 JSON에서 어떻게 정리되는가?

## 데이터의 전체 이동 경로

```text
pdmg-ui
  │ { hdr_nhnis, dto }
  ▼
Filter / Interceptor
  ├─ hdr_nhnis → ServiceContext
  └─ dto → 요청 본문에 유지
  ▼
TCF Handler(Object) 또는 OFF Controller(DTOin)
  ▼
Business Facade
  └─ Object/Map → DTOin
  ▼
Business Service
  ├─ DTOin → DAO parameter Map
  ├─ DB row Map → DTOSub
  └─ DTOout 조립
  ▼
ResponseBodyAdvice
  └─ { hdr_nhnis, dto: DTOout }
  ▼
pdmg-ui
```

이 흐름에서 표준 Header와 업무 DTO, DAO Map은 서로 목적이 다르다. 한 객체로 합치지 않는 것이 변경 영향과 보안 경계를 명확하게 한다.

## 18.1 DTO의 역할

DTO는 계층 사이에서 전달할 데이터의 이름, 타입과 구조를 명시한다. PDMG 업무 DTO는 `nhnis.mg.co.a.dto` 패키지에 있으며 대부분 `{ServiceId}DTOin`, `{ServiceId}DTOout`, `{ServiceId}DTOSub0` 형식을 따른다. 예를 들어 `mgcoa9000S0` 조회는 `mgcoa9000S0DTOin`, `mgcoa9000S0DTOout`, `mgcoa9000S0DTOSub0`을 사용한다.

Service ID를 이름에 포함하면 같은 프로그램의 S0·C0·U0·D0 계약이 섞이지 않는다. 등록 필드를 조회 DTO에 계속 추가하는 만능 타입보다 거래별 변경 영향을 좁힐 수 있다. Handler 분기, Facade 변환 대상, Service 시그니처와 UI 샘플의 키를 하나의 식별 체계로 추적할 수 있다는 운영상 이점도 있다.

DTO 자체는 업무를 실행하거나 Transaction을 관리하지 않는다. 요청 DTO가 유효하다는 판정, 현재 상태를 이용한 규칙, DAO 호출 순서는 Service·Rule 책임이다. DTO에 ServiceContext 조회나 Mapper 호출을 넣으면 데이터 계약이 실행 객체로 변질된다.

현행 DTO 구현은 일관된 단일 기반 클래스로만 구성되지 않는다. `mgcoa9000S0DTOout`처럼 `DataObject`를 상속하고 `FieldProperty` 메타·clone·목록 helper를 가진 생성형 DTO가 있는 반면, `mgcoa9001C0DTOout`처럼 단순 POJO인 타입도 있다. 모든 DTO가 DataObject라는 문서 일반화는 정확하지 않다.

## 18.2 `DTOin`

`DTOin`은 표준 전문의 `dto` 노드가 표현하는 거래별 업무 입력이다. 조회는 검색 조건과 `pageNo`, `pageSize`를 가질 수 있고, 생성은 등록 필드, 수정은 식별키와 변경값, 삭제는 단건 키 또는 목록을 가진다.

입력 DTO에는 클라이언트가 결정할 수 있는 값만 둔다. DB용 `offset`은 Service가 pageNo·pageSize로 계산하므로 와이어 계약에 노출하지 않는다. 감사 사용자처럼 인증된 시스템 값은 임의 요청 필드보다 Header와 ServiceContext를 우선해야 한다.

TCF Facade는 null 본문을 빈 Map으로 바꾼 뒤 DTOin으로 변환하는 사례가 있다. 그 결과 필드가 전부 null인 DTO가 만들어질 수 있다. DTO 생성 성공과 입력 유효성 성공은 다르므로 필수키와 범위 검증이 필요하다.

DTOin을 변경하면 Java만 수정해서는 안 된다. UI 요청 키, 샘플 전문, Facade 변환, Service 조건 Map, Mapper 파라미터와 테스트를 함께 검색한다. 필드 삭제는 구버전 UI와의 호환 정책도 정해야 한다.

## 18.3 `DTOout`

`DTOout`은 성공한 업무 결과의 계약이다. 조회 출력은 목록, 현재 목록 크기, 페이지 정보, 전체 건수와 전체 페이지를 담는다. 생성·수정·삭제 출력은 처리 건수나 결과 정보를 담는다.

현행 출력 계약에도 차이가 있다. 일부 생성형 쓰기 DTO는 `PROC_CNT`, `RSLT_CD`, `RSLT_MSG` 같은 대문자 레거시 필드를 사용하고, `mgcoa9001C0DTOout`은 camelCase `procCnt` 하나를 가진다. 책이나 UI가 모든 쓰기 응답을 하나의 형식으로 가정해서는 안 된다. API 계약을 통일하려면 호환 영향과 마이그레이션을 먼저 분석해야 한다.

업무 오류는 성공 DTO의 결과 코드와 공통 오류 전문 중 어느 것으로 표현할지 기준이 필요하다. 현행 Framework ResponseBodyAdvice는 정상 Body를 `dto`, `NH_NIS_ERR_DTO` 계열 오류를 별도의 오류 키로 구분한다. 내부 예외를 빈 DTOout으로 바꿔 성공처럼 반환하면 HTTP·Transaction 의미가 깨진다.

DTOout은 Service가 조립한 뒤 정상 반환할 때만 응답으로 사용된다. 최외곽 Transaction이 이후 Timeout이나 예외로 Rollback되면 만들어진 DTOout을 성공 응답으로 보내서는 안 된다.

## 18.4 `DTOSub`

`DTOSub0`은 반복 목록의 한 행 또는 하위 반복 구조를 표현한다. 조회 Service는 DAO가 반환한 각 Map을 Sub DTO로 바꾸고 DTOout 목록에 추가한다. `Sub1`, `Sub2`가 필요하다면 서로 다른 반복 구조를 순번으로 구분할 수 있다.

생성형 DataObject 출력에는 `get...List`, `get...Array`, `add...`, `size...`와 같은 helper가 함께 존재할 수 있다. 이는 Java 사용과 전문 엔진 메타를 위한 메서드다. 최종 JSON 계약은 모든 helper 이름을 그대로 노출하는 것이 아니다. ResponseBodyAdvice가 메타 및 `*List`, `*Array` 파생 필드를 제거한다.

Sub DTO는 DB Entity와 동일하지 않다. 화면에 필요한 컬럼만 가지며 표시 형식이나 업무 명칭이 DB 컬럼과 다를 수 있다. DB 스키마 변경을 그대로 외부 계약 변경으로 전파하지 않는 완충 역할을 한다.

## 18.5 TCF ON DTO 변환

TCF ON에서는 공통 Controller가 표준 요청을 받고 Dispatcher가 Service ID로 Handler를 찾는다. Handler 계약의 본문은 구체 DTO가 아니라 `Object`다. 선택된 Facade만 해당 거래의 DTO 타입을 알고 `ObjectMapper.convertValue`를 실행한다.

```text
POST 공통 온라인 URL
  → OnlineTransactionController
  → TcfFacade / Dispatcher
  → TransactionHandler.handle(serviceId, Object dtoBody)
  → Business Facade.convert(dtoBody, DTOin.class)
  → Business Service(DTOin)
```

이 지연 변환은 공통 TCF가 모든 업무 DTO 클래스에 의존하지 않게 한다. 잘못된 숫자·객체 구조는 Facade 변환 시 예외가 될 수 있다. 변환 실패는 Service와 업무 선후처리에 도달하기 전 발생하며 공통 예외 경로로 전파되어야 한다.

Header 전체를 DTOin으로 변환하지 않는다. Filter와 Interceptor가 Header를 ServiceContext로 관리하고 Handler에는 업무 `dto`를 전달한다. Service ID는 Header의 `rms_svc_c`와 라우팅 과정에서 사용되지만 DTOin 클래스 선택은 Handler가 호출한 Facade 메서드로 확정된다.

## 18.6 TCF OFF DTO 변환

TCF OFF 업무 Controller는 Spring MVC의 `@RequestBody DTOin`으로 직접 바인딩한다. 실제 Controller 소스의 대부분은 DTOin을 Service에 직접 전달하며, `mgcoa9100Controller`는 Facade를 호출한다.

```text
업무 URL
  → Spring MVC/Jackson
  → @RequestBody mgcoa9000C0DTOin
  → Controller
  → Service 직접 호출(현행 다수)
```

따라서 문서의 “OFF Controller가 항상 Facade를 통해 변환한다”는 설명은 AS-IS와 다르다. OFF에서는 Spring MVC가 DTO를 만들기 때문에 Facade의 Object 변환이 필요하지 않을 수 있지만, Service 직접 호출은 Facade의 Transaction 경계도 우회한다.

ON/OFF의 타입 결과는 같아도 변환 실패 위치와 예외 형태가 달라질 수 있다. 동등성을 보장하려면 누락 필드, 알 수 없는 필드, 숫자 변환과 null 정책을 양쪽 경로에서 테스트한다. OFF도 Facade로 수렴시킬 때 Facade가 이미 Typed DTO를 다시 `convertValue`하는지와 불필요한 변환 부작용을 확인한다.

## 18.7 Bean Validation

Bean Validation은 `@NotBlank`, `@Size`, `@Min` 같은 선언으로 입력 제약을 표현하고 `@Valid` 경계에서 실행하는 일반적인 방식이다. 그러나 현재 업무 DTO와 Controller를 검색한 결과 Jakarta/Javax validation Annotation과 `@Valid` 사용은 확인되지 않았다.

따라서 원천 문서의 Validation 코드는 권장 예이지 현행 구현이 아니다. 현재 일부 Service가 null·범위 값을 직접 보정하거나 결과 코드로 처리한다. 필수값 검증이 빠진 거래도 있을 수 있으므로 DTO Annotation만 존재한다고 가정해서는 안 된다.

TO-BE로 Validation을 적용한다면 OFF Controller의 `@Valid`만 추가해서는 TCF ON Facade 변환 경로가 같은 검증을 받지 못할 수 있다. Facade 또는 공통 Validator에서 두 경로가 공유할 검증 시점을 정하고, 형식 검증과 DB 상태를 사용하는 업무 검증을 분리한다.

검증 실패는 DAO 전에 중단하고 표준 오류로 매핑한다. 민감한 실제 값은 오류 메시지에 포함하지 않는다. 수정 그룹·등록 그룹을 사용할 때 복잡성이 이득보다 큰지도 판단한다.

## 18.8 표준 Header와 업무 DTO 분리

`hdr_nhnis`와 그 안의 `sys_comm`은 Framework DTO다. GUID, Service ID, 사용자, 영업점, 채널과 거래 시각 같은 시스템 공통 정보가 들어간다. 업무 DTO는 검색 조건, 등록값 등 유스케이스 입력만 가진다.

```text
표준 전문
├─ hdr_nhnis / sys_comm       Framework 계약
│   ├─ std_gbl_id
│   ├─ rms_svc_c
│   ├─ optr_eno
│   └─ tr_brc
└─ dto / *DTOin               업무 계약
    ├─ keyword
    ├─ pageNo
    └─ pageSize
```

분리하지 않으면 클라이언트가 업무 DTO의 userId를 조작했을 때 Header 인증값과 충돌한다. GUID가 두 위치에 있으면 로그가 어느 값을 사용할지도 불명확해진다. 업무상 조회 조건으로 GUID나 Service ID가 필요한 `mgcoa8888S0DTOin` 같은 사례는 시스템 추적값과 검색 대상 필드를 의미로 구분해야 한다.

## 18.9 DTO와 ServiceContext

ServiceContext는 현재 요청의 공통 Header와 GUID를 Thread 범위에서 보유한다. DTO는 메서드 인자로 명시적으로 전달되는 업무 값이다. DTO가 직렬화 가능한 계약이라면 Context는 실행 환경의 부가 맥락이다.

Context 전체를 DTOin에 복사하면 데이터 중복과 신뢰 경계 혼란이 생긴다. 필요한 감사 필드만 서버가 Context에서 읽어 DAO 파라미터에 넣거나 내부 Command로 명시적으로 옮긴다. 현재 주요 CRUD Service가 Context를 직접 읽는 구현은 일반적으로 확인되지 않았으므로 일괄 AS-IS라고 말할 수 없다.

Thread가 바뀌면 DTO 인자는 명시적으로 전달되지만 ThreadLocal Context는 별도 캡처·설치가 필요하다. Timeout Executor는 Worker Context 전파를 구현하지만 임의 비동기 작업까지 자동 보장하지 않는다.

## 18.10 DTO와 DAO

현행 Service는 DTOin을 DAO에 직접 넘기기보다 `HashMap<String,Object>` 파라미터로 변환한다. 조회 결과도 `List<Map<String,Object>>`로 받은 뒤 Sub DTO로 조립하는 사례가 많다.

```text
DTOin
  → Service가 SQL용 조건 Map 구성
  → DAO
  → MyBatis Mapper
  → List<Map>
  → Service가 DTOSub/DTOout 조립
```

이 방식은 와이어 계약과 SQL 계약을 분리하지만 Map 키 오타가 컴파일에서 잡히지 않는다. Mapper의 `#{txId}`와 Service의 키가 정확히 맞아야 한다. DTO를 Mapper에 직접 넘기는 대안은 단순하지만 SQL 필요 필드가 외부 계약에 새어 나갈 수 있다. typed parameter/result 모델은 타입 안전성을 높이는 TO-BE 대안이다.

## 18.11 DTO와 도메인 모델

DTO는 외부 경계의 데이터 모양이고 도메인 모델은 업무 상태와 행위를 표현한다. 단순 CRUD에서는 DTO→Map→DAO가 충분할 수 있다. 복잡한 상태 전이, 불변식과 여러 채널 계약이 생기면 DTO를 Command와 Domain으로 변환해 외부 변경으로부터 핵심 규칙을 보호한다.

현재 `application.rule`과 뚜렷한 도메인 모델 계층은 확인되지 않는다. 따라서 Domain 변환 흐름은 TO-BE 설계 선택이다. 모든 단순 조회에 별도 모델을 강제하면 매핑 비용만 늘 수 있다. 업무 복잡도, 재사용성과 계약 수명으로 결정한다.

DTO를 JPA Entity처럼 영속 상태와 지연 로딩을 가진 객체로 취급하지 않는다. PDMG는 MyBatis Map 기반 접근을 사용하며 DTO는 요청·응답 수명에 머문다.

## 18.12 필드 네이밍

Java 업무 필드는 대체로 camelCase를 사용하고 DB의 snake upper case는 Service 매핑에서 변환한다. `SERVICE_ID`는 `serviceId`, `PAGE_NO`는 `pageNo`가 된다. 서비스 식별자 접두어가 들어간 DTO 클래스명은 프로젝트 네이밍 규칙을 따른다.

다만 일부 레거시 결과 DTO에는 `PROC_CNT`, `RSLT_CD`, `RSLT_MSG` 대문자 필드가 있고 다른 신규 DTO는 `procCnt`다. 실제 소스를 확인하지 않고 하나의 JSON 키를 추정하면 UI가 깨진다. 기존 공개 필드 이름을 바꿀 때는 Jackson 직렬화 결과와 UI 사용처, 샘플 전문을 함께 검증한다.

`data1`, `temp`, `obj` 같은 의미 없는 이름은 피한다. 목록 필드는 생성형 DataObject 관례 때문에 클래스명과 동일한 이름을 가질 수 있으므로 Response Advice 정리 결과까지 계약 테스트로 고정한다.

## 18.13 응답 DTO 조립

Service는 DAO 행을 Sub DTO로 바꾸고 DTOout 목록에 추가한 뒤 `size`, `pageNo`, `pageSize`, `totalCount`, `totalPages`를 설정한다. 쓰기는 DAO 처리 건수와 업무 결과를 출력에 담는다.

ResponseBodyAdvice는 반환 객체를 JSON Tree로 바꾸고 성공이면 `dto`에 배치하며 Header를 함께 구성한다. DataObject가 노출하는 `dtoLogicalName`, `fieldPropertyMap`, `*List`, `*Array` 같은 엔진 메타를 재귀적으로 제거한다. 그러므로 Java getter 목록과 최종 와이어 필드는 같지 않을 수 있다.

오류 객체는 성공 `dto`와 분리된다. DTOout 조립 중 예외가 나거나 최외곽 거래가 실패하면 공통 오류 계약을 사용한다. 응답 전문 전체를 Service가 직접 Map으로 만들면 Header와 메타 정리, 오류 규칙이 중복되므로 피한다.

## End-to-End 사례

```text
요청 { hdr_nhnis, dto: { pageNo:1, pageSize:10 } }
  → Header는 ServiceContext
  → TCF ON: dto Map → Facade → mgcoa9000S0DTOin
     TCF OFF: Jackson → Controller DTOin
  → Service: 조건 Map·page offset
  → DAO count/list
  → 각 행 mgcoa9000S0DTOSub0
  → mgcoa9000S0DTOout + 페이지 메타
  → ResponseBodyAdvice 메타 제거·봉투 조립
  → 응답 { hdr_nhnis, dto }
```

## 책임과 경계

| 구성 요소 | 계약 | 책임 | 금지 책임 |
|---|---|---|---|
| Header DTO | 시스템 전문 | GUID·Service ID 등 공통값 | 업무 검색·등록 필드 |
| ServiceContext | 실행 맥락 | 검증된 Header의 Thread 범위 제공 | 전체 업무 DTO 복제 |
| DTOin | 업무 요청 | 거래별 입력 타입 | SQL offset·Transaction |
| DTOout | 업무 성공 응답 | 결과와 페이지 메타 | 공통 오류 숨김 |
| DTOSub | 반복 행 | 목록 요소 구조 | DB Entity 일반화 |
| DAO Map | Persistence 계약 | SQL 파라미터·결과 | 외부 JSON 계약 |

## 정상과 실패 비교

정상 흐름은 업무 body가 정확한 DTOin으로 바뀌고 검증을 통과한 뒤 Service가 DTOout을 완성한다. Response Advice가 표준 Header와 DTO를 결합한다. 변환 실패는 Service 전에, 검증 실패는 DAO 전에, SQL 실패는 DTOout 반환 전에 공통 예외로 전파되어야 한다.

ON과 OFF는 같은 잘못된 JSON에서도 실패 위치가 다를 수 있다. ON은 Facade `convertValue`, OFF는 MVC Argument Resolution에서 실패한다. 두 경로가 동일한 표준 오류를 내는지 계약 테스트가 필요하다.

## AS-IS와 TO-BE

| 구분 | 내용 |
|---|---|
| AS-IS | Service ID 기반 DTOin/out/Sub 타입이 `nhnis.mg.co.a.dto`에 존재 |
| AS-IS | DataObject 생성형 DTO와 단순 POJO가 혼재 |
| AS-IS | TCF ON Facade Object 변환, OFF Controller 직접 DTO 바인딩 |
| AS-IS | 업무 DTO·Controller에 Bean Validation Annotation이 확인되지 않음 |
| AS-IS | Service가 DAO Map을 만들고 결과 Map을 DTOout으로 조립 |
| 제약 | 레거시 대문자 결과 필드와 camelCase 계약 혼재 |
| TO-BE | ON/OFF 공통 Validation과 계약 테스트 |
| TO-BE | 복잡한 업무에 typed persistence model·domain model 검토 |

## Anti Pattern

표준 Header 전체를 DTOin에 복사하면 조작 가능한 값과 검증된 값이 충돌한다. 하나의 Map을 Controller부터 Mapper와 응답까지 공유하면 키 오타와 과다 노출을 막기 어렵다. DTO에 DAO 호출이나 Context 변경을 넣으면 데이터 계약이 실행 객체가 된다.

DataObject의 모든 getter가 JSON에 노출된다고 가정하거나, 반대로 단순 POJO도 메타 정리 대상이라고 가정해서는 안 된다. OFF에만 `@Valid`를 붙이고 ON도 검증된다고 믿는 것, 변환 예외를 빈 DTOout으로 바꾸는 것도 위험하다.

## 실전 검증 시나리오

각 DTOin은 정상 JSON, 누락, null, 타입 불일치, 알 수 없는 필드와 경계값을 ON/OFF 양쪽에서 테스트한다. DTOout은 실제 직렬화 결과를 스냅샷 또는 JSON Path로 검증해 메타 필드가 빠지고 목록·페이지 키가 기대와 일치하는지 확인한다.

필드 변경 시 UI 요청, Handler/Facade, Service, DAO Map, Mapper XML과 샘플 전문 검색 결과를 점검한다. 쓰기 DTO는 레거시 대문자와 camelCase를 실제 JSON으로 확인한다. Validation 도입 시 Controller와 Facade 경로의 동일 실패 코드를 테스트한다.

## 개발자 체크리스트

- 클래스명이 Service ID + DTOin/out/Sub 규칙을 따르는가?
- Header와 업무 필드를 중복 정의하지 않았는가?
- DTOin에 DB 전용 offset이나 내부 상태를 노출하지 않았는가?
- null body와 필수 필드 누락을 구분하는가?
- ON Facade와 OFF MVC 변환 결과가 동등한가?
- Bean Validation이 실제 어느 경로에서 실행되는지 확인했는가?
- DAO Map 키와 Mapper placeholder가 일치하는가?
- 목록 size와 totalCount를 혼동하지 않는가?
- DataObject 메타가 최종 JSON에서 제거되는가?
- 오류를 성공 DTOout으로 숨기지 않는가?
- 필드 변경 시 UI·샘플·테스트까지 갱신했는가?
- 민감한 Header·DTO 값이 로그에 노출되지 않는가?

## 아키텍처 판단 포인트와 다음 장

DTO 분리 수준은 계약의 독립성과 변경 주기로 결정한다. 거래별 요청·응답은 Service ID 단위로 분리하고, 복잡한 핵심 규칙은 Domain 모델로 보호할 수 있다. Persistence 전용 요구가 많아지면 typed parameter/result 모델을 추가하되 단순 CRUD에 불필요한 매핑 계층을 강제하지 않는다.

Header와 업무 DTO의 분리는 보안과 운영 추적의 경계다. 동일 이름의 필드가 필요해도 시스템 추적값과 업무 검색값의 의미를 문서화한다. ON/OFF 변환 방식이 달라도 최종 DTO 계약과 표준 오류는 같도록 테스트한다.

다음 장에서는 Service가 DTOin에서 만든 파라미터를 DAO가 어떻게 Mapper namespace와 statement로 연결하고, DB 행을 어떤 Map 계약으로 반환하는지 Persistence 경계를 살펴본다.
