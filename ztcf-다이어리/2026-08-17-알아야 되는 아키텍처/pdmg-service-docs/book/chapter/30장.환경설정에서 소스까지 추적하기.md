# 30장. 환경설정에서 소스까지 추적하기

설정 변경의 영향도는 YAML의 한 줄만 보아서는 알 수 없다. 같은 키가 Java 객체의 숫자를 바꾸기도 하고, Bean 전체를 생성하거나 제거하기도 하며, 아무 코드도 읽지 않아 실제로는 아무 효과가 없을 수도 있다. 이 장은 설정 키에서 출발해 정의, 최종값, 주입, Bean, Caller, 실행 결과와 검증까지 이어지는 증거 사슬을 만드는 실전 방법을 다룬다.

## 30.1 설정 키를 읽는 방법

첫 단계는 저장소 전체에서 정확한 키와 prefix를 검색하는 것이다. YAML 정의만 찾지 말고 `@Value`, `@ConfigurationProperties`, `@ConditionalOnProperty`, `spring.config.import`와 테스트를 함께 찾는다. 하이픈 표기와 Java camelCase의 relaxed binding도 고려한다. 예를 들어 `pool-size`는 `OnlineTimeoutProperties.poolSize`에 바인딩된다.

두 번째는 최종값의 원천을 판정하는 것이다. 공통 문서, 활성 Profile, 외부 환경변수와 실행 인자 중 무엇이 이겼는지 확인한다. 세 번째는 소비자가 실제로 등록되는지 본다. Properties 클래스가 있어도 이를 Enable하거나 Scan하지 않으면 쓰이지 않을 수 있고, 파일이 classpath에 있어도 Import 근거가 없으면 로딩되지 않는다.

```text
키 검색 → 정의·override → 최종 Environment
→ 주입/Binding → Bean 조건 → Caller
→ 요청 Flow → 로그·응답·DB 결과 → 테스트
```

이 절차의 산출물은 “값이 5초다”가 아니라 “이 값이 어떤 실행 경계를 5초로 만들며 실패 시 어떤 로그와 상태를 남기는가”라는 설명이다.

## 30.2 설정값과 Java Bean 관계

설정 소비 방식은 영향 범위를 결정한다. `@Value`는 생성된 Bean의 필드를 채운다. `@ConfigurationProperties`는 관련 값을 타입 객체로 묶어 여러 Bean이 공유한다. `@ConditionalOnProperty`는 Bean 존재 자체를 결정한다. 따라서 변경 검토표에는 값의 타입뿐 아니라 “재시작 필요”, “Bean graph 변경”, “요청 계약 변경”을 표시해야 한다.

PDMG 설정은 기본적으로 시작 시 평가된다. 외부 설정 파일을 수정했다고 실행 중 Bean이 자동 교체된다고 가정해서는 안 된다. `JwtRuntimePolicy`처럼 DB 행을 명시적으로 적용하는 예외가 있지만 모든 Properties가 동적 갱신되는 것은 아니다. 재시작 없이 바뀐다고 주장하려면 Refresh 메커니즘과 Thread safety를 소스에서 확인해야 한다.

| 소비 방식 | 실제 사례 | 변경 영향 |
|---|---|---|
| `@Value` | `jwt.secret`, active Profile | 필드·분기 변경 |
| Properties binding | Timeout, RDW, JWT 정책 | 객체 값과 하위 Bean 구성 |
| Conditional Bean | TCF, Filter, Timeout | 호출 경로 생성·제거 |
| Config Import | `exceptionCode.yml` | 메시지 PropertySource 추가 |
| 미연결 파일 | `application-fw-defaults.yml` | AS-IS 자동 효과 근거 없음 |

## 30.3 TCF 활성화 값과 생성 Bean

추적 시작점은 `nhnis.fw.tcf.enabled`다. true 조건은 `OnlineTransactionController`, `TransactionDispatcher`, `TcfFacade`, STF/ETF, GlobalExceptionHandler와 업무 `TransactionHandler`를 활성화한다. 업무별 직접 Controller는 false 또는 누락 조건에서 등록된다. 따라서 true에서 false로 바꾸면 단순 프레임워크 기능 하나가 꺼지는 것이 아니라 HTTP 진입점과 예외 처리, Handler dispatch가 교체된다.

```text
enabled=true
  Filter → Interceptor → OnlineTransactionController
  → TcfFacade → Executor → TransactionDispatcher → Handler → Facade

enabled=false
  Filter → Interceptor → 업무별 Controller → Service/Facade
```

검증은 ApplicationContext에서 ON Bean과 OFF Bean의 상호 배타성을 확인하고, `/online`과 `/{serviceId}` 요청, Service ID Header 우선순위, 표준 응답, 업무 선후처리와 Transaction 경계를 비교한다. 키 오타나 누락은 직접 Controller의 `matchIfMissing=true` 때문에 조용히 OFF로 갈 수 있다. 운영에서는 명시값을 필수로 하고 기대 모드가 시작 로그에 나타나는지 확인한다.

## 30.4 Filter 활성화 값과 요청 처리

`nhnis.fw.commons.filter.enabled=true`는 `DefaultFilter` Component와 `FilterConfiguration`의 Registration Bean을 활성화한다. Registration은 REQUEST Dispatcher와 모든 URL, 높은 우선순위를 사용한다. Filter는 Body 캐싱, JWT 비-local 검증, Header 변환, GUID·MDC와 ServiceContext를 준비한다. false이면 이 모든 책임이 함께 사라진다.

Interceptor가 후속 단계에서 GUID를 보완할 수 있다고 해서 Filter OFF가 호환된다고 단정할 수 없다. 요청 원문, HttpHeaders와 JWT 신원 준비가 달라진다. 또한 local Profile은 enabled와 별개로 JWT 검증을 건너뛰고 multipart도 별도 분기에서 JWT를 검사하지 않는다. 변경 테스트에는 일반 JSON, OPTIONS, multipart, local/non-local, Header 누락과 Filter finally의 Context 정리를 포함한다.

장애 증상은 GUID 없는 로그, null ServiceContext, 인증 없이 업무 진입 또는 Filter Bean 중복 등록이다. `FilterConfiguration`은 Component 자동 등록과 중복되지 않도록 Registration Bean을 의도하지만 실제 Servlet Filter 목록을 기동 테스트로 확인해야 한다.

## 30.5 Timeout 값과 Executor

`nhnis.fw.timeout` prefix는 `OnlineTimeoutProperties`에 바인딩된다. enabled=false 또는 누락이면 `SyncOnlineTimeoutExecutor`, true이면 `pdmgOnlineTimeoutTaskExecutor`와 `DefaultOnlineTimeoutExecutor`가 생성된다. Properties의 PostConstruct는 milliseconds 1 이상, pool-size 1 이상, queue-capacity 0 이상을 강제하여 잘못된 값은 기동 실패로 만든다.

true 경로는 Pool 크기를 core/max에 동일하게 적용하고 Queue 용량과 AbortPolicy를 설정하며 `rdwTransactionManager`를 주입받는다. milliseconds는 요청 Thread의 Future 대기와 Worker deadline 판단에 쓰인다. Pool/Queue 변경은 처리량뿐 아니라 Hikari Connection 경쟁, 503 overload와 504 timeout 비율을 바꾼다.

검증은 세 층으로 한다. Context Test로 올바른 Executor Bean 하나만 생성되는지 확인한다. 단위 테스트로 경계값과 timeout/interrupt/ExecutionException을 확인한다. 부하 테스트로 Queue 포화, rejection, rollback과 timeout 후 Worker 종료 여부를 검증한다. timeout 로그는 Worker 종료 증거가 아니라는 판정도 유지한다.

## 30.6 DataSource 값과 TransactionManager

`spring.datasource.rdw`는 `RdwDataSourceConfig.rdwDataSource()`의 HikariDataSource로 바인딩된다. 같은 설정에서 Driver, JDBC URL, 사용자, 비밀번호와 Pool 속성이 결정된다. 이 Bean은 Primary이고 MyBatis SqlSessionFactory, SqlSessionTemplate, Mapper Scan과 `rdwTransactionManager`로 이어진다. Timeout Executor도 이름으로 이 TransactionManager를 요구한다.

```text
spring.datasource.rdw.*
  → HikariDataSource(rdW, Primary)
  ├→ SqlSessionFactory + Mapper XML + MybatisLogInterceptor
  ├→ SqlSessionTemplate → DAO Proxy
  ├→ DataSourceTransactionManager
  └→ ImageLogHandler / MgRuntimeMonitor
```

URL 변경은 DAO만 바꾸는 것이 아니다. ImageLog와 Runtime Monitor도 Primary DataSource를 사용하므로 같은 DB·Pool 영향을 받는다. Driver나 Mapper Location 오류는 기동 시, 잘못된 자격 증명은 Pool 초기화 또는 첫 요청에서 나타날 수 있다. Profile별 SQL init이 운영 Schema를 변경하지 않는지도 점검한다. 비밀번호는 값 자체를 출력하지 않고 주입 여부와 연결 결과만 검증한다.

## 30.7 JWT 설정과 Token Issuer

발급 측 추적은 `nsight.security.jwt`에서 시작한다. `JwtSecurityProperties`가 issuer, audience, Access/Refresh 수명, clock skew, algorithm, JWKS URI, denylist와 rotation 설정을 받는다. `JwtRuntimePolicy`가 기본값을 보관하고 DB 정책 행을 적용할 수 있으며 `JwtTokenIssuer`가 issuer/audience/수명으로 Claim을 구성한다.

그러나 algorithm Property를 바꾸면 서명 코드도 자동으로 바뀐다고 볼 수 없다. `JwtTokenIssuer`는 RS256을 코드에 고정한다. Private Key도 설정에서 로딩하지 않고 기동 시 생성한다. 따라서 정책 화면의 algorithm 문자열과 실제 서명이 다를 수 있고 재기동 시 키가 바뀐다. 설정 영향 분석은 문자열 소비가 실제 암호 연산까지 이어지는지 확인해야 한다.

Refresh 수명과 rotation 값은 갱신 서비스와 저장소 동작에 영향을 준다. 변경 테스트는 Access/Refresh 만료, 재사용, 사용자 비활성, token family와 재기동 전후 검증을 포함한다. 토큰과 키의 실제값은 어떤 진단 결과에도 남기지 않는다.

## 30.8 JWKS 설정과 Token Decoder

`jwk-set-uri`는 pdmg-jwt Properties에 존재하고 `JwkSetController`는 실제 Public JWK를 `/.well-known/jwks.json`으로 공개한다. 그러나 저장소에서 `pdmg-fw`의 Decoder가 이 URI를 소비하는 연결은 없다. 업무 검증기는 `jwt.secret`을 `@Value`로 받아 HMAC SecretKey를 만든다. 즉 JWKS 값을 올바르게 설정해도 현행 업무 검증 Flow에는 효과가 없다.

이 사례는 미사용 또는 잘못된 소유권 설정을 찾는 전형이다. TO-BE 전환은 업무 서비스에 JWKS 기반 RS256 Decoder를 만들고 허용 algorithm, issuer, audience, exp, type, sub와 denylist를 검증해야 한다. Context Test로 Decoder Bean과 HMAC Bean의 배타성을 확인하고, 발급기의 실제 Token으로 성공·키 불일치·알 수 없는 kid·만료·회전 시나리오를 통합 검증한다. Private Key를 검증 서비스에 배포하는 방식은 금지한다.

## 30.9 Exception Code와 오류 응답

`spring.config.import: classpath:exceptionCode.yml`은 파일을 실제 PropertySource로 연결한다. `ExceptionCodeProperties`가 `nhnis.exception` Map을 받고 코드별 template과 fallback을 제공한다. 하지만 `GlobalExceptionHandler.handleBizException()`은 현재 Properties를 주입하지 않고 `BizException.getMessage()`를 응답에 넣는다. BizException message는 생성자상 코드 자체다.

따라서 YAML에 메시지를 추가하는 것만으로 TCF ON 응답 문구가 바뀐다고 보장할 수 없다. Legacy `NhBaseException`의 SERVICE/BIZ는 별도 DB `MessageCache`를 사용한다. 추적은 코드 등록 → 예외 throw → Handler 선택 → 메시지 Resolver → `NH_NIS_ERR_DTO` → Response Advice의 `result`까지 이어져야 한다. HTTP 상태도 코드 사전이 아니라 Handler에서 결정되므로 함께 검증한다.

정상 테스트는 등록 코드와 인자 치환, 미등록 fallback이다. 실패 테스트는 Import 누락, Handler 미연결, Filter `sendError`처럼 MVC Advice를 우회하는 경로와 내부 Stack Trace 비노출을 포함한다.

## 30.10 UI 설정과 대상 URL

UI는 업무 Target, JWT Target과 Ontology Target을 구분한다. Browser config가 값을 제공하고 JavaScript에는 localhost fallback이 있다. `service-client.js`는 업무 Base URL과 path를 결합하고, `jwt-admin.js`는 JWT Base URL의 `/online`과 JWKS endpoint를 호출한다. 서버 CORS의 allowed origins·methods·headers가 이 Browser Origin과 일치해야 한다.

Target 변경 영향은 UI만의 문제가 아니다. 잘못된 업무 URL은 Network 오류, 잘못된 JWT URL은 로그인·갱신 실패, CORS 불일치는 preflight 차단으로 나타난다. config 조회 실패가 localhost fallback으로 숨지 않도록 운영에서는 fail-fast 화면을 사용한다. 테스트는 최종 생성 URL, HTTP/HTTPS mixed content, Reverse Proxy path, CORS OPTIONS와 Authorization Header를 확인한다.

## 30.11 설정 변경 시 영향도 점검

변경 전에는 소유 모듈, 기본값, Profile override, 외부 주입, 소비 Symbol과 조건부 Bean을 기록한다. 변경 중에는 정상·경계·오류값과 조합을 테스트한다. 변경 후에는 기동 Bean 목록, 요청 흐름, 로그·Metric, DB 결과와 rollback을 확인하고 되돌릴 설정과 재시작 순서를 준비한다.

### End-to-End 영향도 분석 예

```text
변경 요청: timeout 5초 → 10초
  1. application/Profile/외부 override 검색
  2. OnlineTimeoutProperties binding·validation 확인
  3. TimeoutConfiguration Bean 조건 확인
  4. DefaultOnlineTimeoutExecutor 소비 위치 확인
  5. 요청 Thread 대기, Worker deadline, TX rollback 확인
  6. Pool/Queue/Hikari 점유 영향 부하 테스트
  7. timeout 로그·504 비율·Worker 잔존 관찰
  8. 이전 값으로 rollback 절차 확인
```

### 변경 전후 책임·실패 비교

| 변경 | 생성/실행 변화 | 대표 장애 | 확인 증거 |
|---|---|---|---|
| TCF true→false | 단일 Controller/Handler 제거, 직접 Controller 생성 | URL·선후처리·오류 계약 차이 | Bean/Mapping, 호출 로그 |
| Filter true→false | JWT·GUID·Context 준비 제거 | 인증 우회, null Context | Filter 목록, GUID 로그 |
| Timeout false→true | Worker Pool·TX Executor 생성 | Queue 거부, Thread/DB 점유 | Executor 로그, 503/504 |
| RDW URL 변경 | DAO·ImageLog·Monitor 자원 변경 | 연결·Schema·Pool 장애 | Hikari, Mapper, 검증 Query |
| JWKS URI 변경 | AS-IS 업무 Decoder 변화 없음 | 잘못된 안전 기대 | 실제 소비 Symbol 부재 |
| 오류 코드 추가 | 사전만 변경 | Handler 미연결로 코드 노출 | 실제 오류 응답 |

### Anti Pattern

- YAML의 키 이름과 값만 보고 영향도 분석을 끝낸다.
- 같은 이름의 설정이 있으면 반드시 소비된다고 가정한다.
- 조건부 Bean 변경을 재시작 없이 적용된다고 생각한다.
- TCF만 테스트하고 Filter·legacy-web·Timeout 조합을 무시한다.
- JWKS URI 설정만으로 HMAC 검증기가 RS256으로 바뀐다고 주장한다.
- 설정 확인을 위해 Secret, Token, JDBC 비밀번호를 로그에 출력한다.
- 단건 성공만 확인하고 Queue 포화, DB 실패, rollback을 검증하지 않는다.

### 개발자·운영자 체크리스트

- [ ] 키의 모든 정의와 Profile·외부 override를 찾았는가?
- [ ] `@Value`, Properties, Conditional 소비자를 찾았는가?
- [ ] 미사용·중복·fallback 설정을 구분했는가?
- [ ] 변경 전후 Bean graph와 URL을 비교했는가?
- [ ] Caller에서 응답·로그·DB까지 실행 흐름을 추적했는가?
- [ ] 잘못된 값이 시작 실패인지 런타임 실패인지 확인했는가?
- [ ] Thread, Transaction, Context 경계 변화를 검증했는가?
- [ ] Secret을 노출하지 않는 진단 방법을 사용했는가?
- [ ] 부하·오류·보안 회귀 테스트와 rollback 절차가 있는가?

### 아키텍처 판단과 다음 장

좋은 설정은 동작을 유연하게 만들면서도 지원하지 않는 조합을 허용하지 않는다. 동적 변경이 꼭 필요한 정책과 재시작을 요구하는 구조 설정을 구분하고, 후자는 Bean graph와 의존 자원의 일관성을 우선한다. 설정 키의 소유자와 소비자가 다르면 계약 테스트를 둔다.

다음 장에서는 이 영향도 추적법을 신규 프로그램 개발에 적용한다. Service ID, Handler, Facade, Service, DAO/Mapper, 오류 코드와 UI 요청을 만들 때 기존 설정과 조건부 실행 경로를 어떻게 함께 검증하는지 단계별로 살펴본다.
