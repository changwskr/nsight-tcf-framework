# 제3장. 레이어드 아키텍처와 컴포넌트

> **집필 기준**
>
> 이 장은 현재 `pdmg-service`의 `nhnis.mg.co.a.*` 패키지와 `pdmg-fw` 실행 구조를 AS-IS 기준으로 설명한다.
> 저장소 공통 아키텍처가 제시하는 `entry.facade`, `application.rule` 구조는 현재 구현과 구분하여 TO-BE로 설명한다.
>
> 특히 다음 사실을 기준으로 한다.
>
> - 현재 업무 코드는 `nhnis.mg.co.a.*` 단일 축으로 정리되어 있다.
> - 현재 `Handler`는 `entry.handler`에 있다.
> - 현재 `Controller`, `Facade`, `Service`는 `application.*`에 있다.
> - 현재 별도 `Rule` 계층은 구현되어 있지 않다.
> - 현재 DAO는 MyBatis Mapper 인터페이스 역할을 수행한다.
> - TCF ON + Timeout ON의 최외곽 DB Transaction은 `DefaultOnlineTimeoutExecutor`의 Worker `TransactionTemplate`이 시작한다.
> - Facade의 `@Transactional(REQUIRED)`는 Timeout ON에서는 기존 Worker Transaction에 참여한다.
> - TCF OFF AS-IS 일부 Controller는 Service를 직접 호출하므로 Facade 경계를 우회할 수 있다.
>
> 따라서 이 장에서 “레이어”를 설명한다고 해서 물리 패키지, 런타임 호출, Transaction 경계가 항상 정확히 같은 모양이라고 단정하지 않는다.

# 3.1 제2장의 실행 흐름을 구조의 관점으로 다시 본다

제2장에서는 한 건의 온라인 요청을 시간순으로 따라갔다.

```text
Browser
  ↓
DefaultFilter
  ↓
Interceptor
  ↓
OnlineTransactionController
  ↓
TcfFacade
  ↓
OnlineTimeoutExecutor
  ↓
TransactionDispatcher
  ↓
Handler
  ↓
Facade
  ↓
Service
  ↓
DAO / Mapper
  ↓
DB
```

이 흐름을 처음 보면 자연스럽게 이런 생각을 하게 된다.

> “호출 순서가 위에서 아래로 내려가니까, 이것이 곧 레이어인가?”

절반은 맞고 절반은 틀리다.

레이어드 아키텍처는 단순히 **호출 순서**를 예쁘게 나열하는 방법이 아니다.  
핵심은 **서로 다른 변경 이유를 가진 코드를 분리하고, 의존 방향을 통제하는 것**이다.

예를 들어 HTTP URL이 바뀌었다고 SQL이 바뀌어서는 안 된다.  
Oracle SQL이 바뀌었다고 Handler가 바뀌어서는 안 된다.  
화면이 React에서 다른 채널로 바뀌었다고 업무 계산 규칙을 다시 작성해서도 안 된다.

### 그림 3-1. 호출 순서와 레이어는 같은 개념이 아니다

```text
[호출 순서]

A → B → C → D

"누가 다음에 실행되는가?"


[레이어]

┌────────────────────┐
│ Entry              │  외부 요청 변화
├────────────────────┤
│ Application        │  유스케이스 변화
├────────────────────┤
│ Persistence        │  데이터 접근 변화
└────────────────────┘

"왜 이 코드가 바뀌는가?"
"누구를 의존해도 되는가?"
```

레이어를 나누는 이유는 코드 파일을 여러 폴더로 나누기 위해서가 아니다.

```text
변경 이유 분리
      ↓
의존 방향 통제
      ↓
변경 파급 축소
      ↓
테스트 범위 명확화
      ↓
운영 안정성 향상
```

# 3.2 레이어와 컴포넌트를 먼저 구분한다

PDMG를 이해할 때 `Handler`, `Facade`, `Service`, `DAO`를 모두 “레이어”라고 부르는 경우가 많다.

엄밀히 말하면 조금 다르다.

- **레이어(Layer)**: 책임과 의존 방향을 묶는 큰 경계
- **컴포넌트(Component)**: 그 레이어 안에서 구체적인 역할을 수행하는 클래스 유형

### 그림 3-2. 레이어 안에 컴포넌트가 존재한다

```text
┌─────────────────────────────────────────────┐
│ Entry Layer                                 │
│                                             │
│   Handler          Aspect                   │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ Application Layer                           │
│                                             │
│   Controller       Facade       Service     │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ Persistence Layer                           │
│                                             │
│   DAO              Mapper XML               │
└─────────────────────────────────────────────┘
```

같은 레이어 안의 컴포넌트도 책임은 서로 다르다.

| 레이어 | 컴포넌트 | 핵심 책임 |
|---|---|---|
| Entry | Handler | Service ID를 업무 유스케이스로 연결 |
| Entry | Aspect | Service 실행 전후의 횡단 처리 |
| Application | Controller | TCF OFF HTTP 진입 |
| Application | Facade | 입력 변환, 유스케이스 경계, TX 선언 |
| Application | Service | 업무 절차와 판단 |
| Persistence | DAO | MyBatis 데이터 접근 계약 |
| Persistence Resource | Mapper XML | SQL |

따라서 다음 문장은 지나치게 단순하다.

```text
"Handler Layer"
"Facade Layer"
"Service Layer"
"DAO Layer"
```

책에서는 편의를 위해 그렇게 부를 수 있지만, 실제 설계 판단에서는 **레이어와 컴포넌트를 구분**해야 한다.

# 3.4 모든 패키지가 수직 레이어는 아니다

현재 `nhnis.mg.co.a` 아래에는 다음과 같은 패키지가 존재한다.

### 그림 3-4. 현재 업무 패키지 구조

```text
nhnis.mg
├─ PdmgApplication
├─ ServletInitializer
└─ co.a
   ├─ entry
   │  ├─ handler
   │  └─ aspect
   │
   ├─ application
   │  ├─ controller
   │  ├─ facade
   │  └─ service
   │
   ├─ dto
   │
   ├─ persistence
   │  └─ dao
   │
   ├─ config
   ├─ client
   └─ support
```

이 트리를 그대로 세로 Layer로 해석하면 문제가 생긴다.

### 그림 3-5. 수직 레이어와 옆 경계

```text
                         ┌──────────────┐
                         │     DTO      │
                         │   Contract   │
                         └──────┬───────┘
                                │ 공유
                                │
Channel → FW → Entry → Application → Persistence → DB
                       │              │
                       │              │
                       ├───────┐      │
                       │       │      │
                       ▼       ▼      ▼
                    Client   Support  Mapper XML
                       │
                       ▼
                 External System


Config
  └─ 위 컴포넌트를 실행하는 Bean을 "조립"
     수직 업무 호출선의 한 단계가 아님
```

각각을 구분하면 다음과 같다.

| 요소 | 성격 |
|---|---|
| `dto` | 경계를 건너는 데이터 계약 |
| `config` | Spring/DataSource/MyBatis Bean 조립 |
| `client` | 외부 시스템으로 나가는 Outbound 경계 |
| `support` | 제한적으로 사용하는 보조 기능 |
| `aspect` | 특정 Join Point에 개입하는 횡단 관심사 |

# 3.5 현재 패키지 구조는 과거 구조와 다르다

과거 분석 시점에는 축 없는 구 패키지와 `co.a` 패키지가 공존했던 시점이 있었다.

현재 소스에서는 구 패키지가 제거되어 업무 코드는 `nhnis.mg.co.a.*`로 통합되어 있다.

### 그림 3-6. 제거된 과거 패키지와 현재 구조

```text
[과거 - 제거됨]

nhnis.mg
├─ application.*
├─ entry.*
├─ persistence.*
└─ config.*


             X 현재 사용하지 않음


[현재]

nhnis.mg
├─ PdmgApplication
├─ ServletInitializer
└─ co.a
   ├─ entry.*
   ├─ application.*
   ├─ dto
   ├─ persistence.*
   ├─ config
   ├─ client
   └─ support
```

따라서 과거 분석 문서에 등장했던 “구·신 패키지가 동시에 스캔되어 동일 Bean 이름이 충돌한다”는 문제를 **현재 AS-IS 문제처럼 반복해서 서술하면 안 된다.**

현재 기준은 다음과 같다.

```text
현재
  nhnis.mg 바로 아래 = Boot
  업무 코드          = nhnis.mg.co.a.*

결과
  과거의 동일 클래스 중복 Bean 문제는 해소
```

다만 새로운 업무축을 추가하면서 같은 이름의 Config Bean을 복제하면 다른 형태의 충돌 위험은 다시 생길 수 있다.

# 3.6 Boot는 레이어가 아니라 애플리케이션 조립의 시작점이다

`PdmgApplication`은 업무 Layer 안의 한 단계라기보다 Spring Boot Application Context를 만드는 시작점이다.

### 그림 3-7. Boot와 Component Scan

```text
PdmgApplication
      │
      │ @SpringBootApplication(scanBasePackages = "nhnis")
      │ @ConfigurationPropertiesScan("nhnis")
      ▼

┌──────────────────────────────────────────┐
│ Spring Component Scan                    │
├──────────────────────────────────────────┤
│ nhnis.fw.*                               │
│ nhnis.mg.*                               │
│   └─ nhnis.mg.co.a.*                     │
└──────────────────────────────────────────┘
```

이 구조는 `pdmg-fw`의 공통 Bean과 `pdmg-service`의 업무 Bean이 같은 Application Context 안에서 함께 동작할 수 있게 한다.

### 그림 3-8. 같은 JVM 안의 FW와 업무 Bean

```text
┌────────────────── Spring Application Context ────────────────┐
│                                                               │
│  pdmg-fw Beans                 pdmg-service Beans             │
│                                                               │
│  DefaultFilter                  mgcoa9000Handler              │
│  TcfFacade                      mgcoa9000Facade               │
│  Dispatcher                     mgcoa9000Service              │
│  TimeoutExecutor                mgcoa9000DAO                  │
│  ServiceContext                 BizPrePostAspect              │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

즉 다음처럼 이해하면 안 된다.

```text
pdmg-fw  ──HTTP──> pdmg-service
```

실제 업무 서버 안에서는 공통 FW와 업무 Bean이 같은 Spring 실행 환경에 참여한다.

# 3.7 Framework는 업무보다 바깥쪽 실행 환경이다

Framework 영역은 개별 마케팅 업무를 수행하지 않는다.  
업무가 실행되는 공통 조건을 만든다.

### 그림 3-9. Framework가 감싸는 업무 실행

```text
┌──────────────────────── pdmg-fw ────────────────────────────┐
│                                                             │
│ DefaultFilter                                               │
│    ↓                                                        │
│ Interceptor                                                 │
│    ↓                                                        │
│ OnlineTransactionController                                 │
│    ↓                                                        │
│ TcfFacade                                                   │
│    ↓                                                        │
│ OnlineTimeoutExecutor                                       │
│    ↓                                                        │
│ TransactionDispatcher                                       │
│    │                                                        │
│    │ 공통 TransactionHandler 계약                           │
│    ▼                                                        │
│ ┌──────────────────── pdmg-service ───────────────────────┐ │
│ │ Handler → Facade → Service → DAO                      │ │
│ └─────────────────────────────────────────────────────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

Framework가 알아야 하는 것은 다음과 같다.

```text
Service ID
TransactionHandler 계약
ServiceContext
Timeout 정책
공통 예외
공통 로그
```

Framework가 알아서는 안 되는 것은 다음과 같다.

```text
특정 고객 조회 조건
거래통제 업무 분기
마케팅 계산 규칙
특정 테이블 컬럼
특정 프로그램 DTO 세부 필드
```

# 3.8 FW가 업무 Handler를 호출하는데도 의존 방향을 뒤집지 않는 이유

`TransactionDispatcher`는 업무 Handler를 실행한다.  
그렇다면 `pdmg-fw`가 업무 구현에 의존하는 것처럼 보일 수 있다.

실제 구조는 “구체 업무 클래스를 직접 참조”하는 방식이 아니다.

### 그림 3-10. Dependency Inversion을 이용한 Handler 연결

```text
           pdmg-fw
┌───────────────────────────────┐
│ TransactionHandler            │
│        Interface              │
└──────────────▲────────────────┘
               │ implements
               │
        pdmg-service
┌──────────────┴────────────────┐
│ mgcoa5530Handler              │
│ mgcoa8888Handler              │
│ mgcoa9000Handler              │
│ mgcoa9999Handler              │
└───────────────────────────────┘
```

Spring은 구현체 목록을 주입할 수 있다.

```text
Spring Context
   │
   ├─ TransactionHandler 구현 검색
   │
   ├─ serviceIds() 읽기
   │
   └─ Registry 구성
```

이 때문에 신규 업무 Handler를 추가하더라도 Dispatcher 코드에 다음과 같은 직접 import를 계속 추가할 필요가 없다.

```text
X import mgcoa5530Handler
X import mgcoa8888Handler
X import mgcoa9000Handler
X import 신규Handler...
```

# 3.9 런타임 호출 방향과 컴파일 의존 방향은 다를 수 있다

이 부분은 레이어드 아키텍처를 이해할 때 중요하다.

### 그림 3-11. Runtime Call vs Compile Dependency

```text
[Runtime Call]

pdmg-fw Dispatcher
       │
       ▼
pdmg-service Handler
       │
       ▼
Facade → Service → DAO


[Compile Dependency]

pdmg-service Handler
       │
       │ implements
       ▼
pdmg-fw TransactionHandler Interface
```

런타임에는 FW가 Handler 구현체를 호출한다.

그러나 Java 컴파일 관점에서는 업무 Handler가 FW의 인터페이스를 구현한다.

```text
Runtime 제어 방향
  FW → 업무 Handler

Source 의존 방향
  업무 Handler → FW 계약
```

이것이 전형적인 제어 역전이다.

따라서 “런타임에 A가 B를 호출하므로 A 모듈이 B 모듈을 compile dependency로 가져야 한다”라고 단순 판단해서는 안 된다.

# 3.10 Entry는 외부 실행 모델을 유스케이스로 연결한다

현재 TCF ON에서 업무측 첫 진입 컴포넌트는 Handler다.

### 그림 3-12. Entry Handler의 위치

```text
Framework
TransactionDispatcher
       │
       │ serviceId
       ▼
┌────────────────────────┐
│ Entry Handler          │
│                        │
│ "어느 거래인가?"      │
│ "어느 Facade인가?"    │
└────────────┬───────────┘
             ▼
          Facade
```

Handler의 책임은 좁아야 한다.

### 그림 3-13. Handler 책임 경계

```text
Handler

O 한다
  Service ID 등록
  Service ID 분기
  Facade 호출

X 하지 않는다
  SQL 실행
  DAO 직접 호출
  상세 업무 계산
  Commit/Rollback 결정
  HTTP Response 조립
```

Handler가 Service나 DAO를 직접 호출하면 Facade가 담당하는 유스케이스 경계를 건너뛴다.

# 3.11 Handler 하나는 Program ID 단위의 여러 Service ID를 가질 수 있다

Handler는 “서비스 ID 하나당 클래스 하나”로만 이해하면 안 된다.

### 그림 3-14. Program Handler와 Service ID

```text
Program ID
mgcoa9000
    │
    ▼
mgcoa9000Handler
    │
    ├─ mgcoa9000S0
    │      └─ 조회
    │
    ├─ mgcoa9000C0
    │      └─ 등록
    │
    ├─ mgcoa9000U0
    │      └─ 수정
    │
    └─ mgcoa9000D0
           └─ 삭제
```

Handler는 각 Service ID를 해당 Facade 메서드에 연결한다.

```text
mgcoa9000S0 → facade.mgcoa9000S0()
mgcoa9000C0 → facade.mgcoa9000C0()
mgcoa9000U0 → facade.mgcoa9000U0()
mgcoa9000D0 → facade.mgcoa9000D0()
```

---

# 3.12 Aspect는 Entry에 있지만 일반 호출 레이어는 아니다

현재 `entry.aspect`에는 `BizPrePostAspect`와 같은 횡단 요소가 위치한다.

Aspect는 Handler 다음에 항상 명시적으로 호출되는 일반 Java 단계가 아니다.

### 그림 3-15. 일반 호출과 AOP 개입의 차이

```text
[명시적 Java 호출]

Handler
   │
   ▼
Facade
   │
   ▼
Service


[AOP 개입]

Facade
   │
   ▼
Spring Proxy / Join Point
   │
   ├─ BizPre
   │
   ▼
Service
   │
   └─ 정상 반환 → BizPost
```

따라서 다음 두 화살표의 의미는 다르다.

```text
Handler ──Java call──> Facade

Aspect ──Pointcut──> Service
```

Pointcut 관계를 일반 컴파일 의존 관계와 같은 것으로 보면 안 된다.

# 3.13 Application은 “한 거래를 어떻게 수행할 것인가”를 다룬다

Application의 핵심은 유스케이스다.

### 그림 3-16. Application의 관심사

```text
사용자 의도
"거래통제 목록을 조회한다"
          │
          ▼
┌────────────────────────────┐
│ Facade                     │
│ 입력 계약 + 유스케이스 경계│
└────────────┬───────────────┘
             ▼
┌────────────────────────────┐
│ Service                    │
│ 업무 절차                  │
│ 검증                       │
│ DAO/Client 조정            │
└────────────────────────────┘
```

Application이 직접 신경 쓰지 않아야 할 것은 다음이다.

```text
HTTP CORS
Servlet Filter 순서
JSON raw body cache
Mapper XML namespace 세부 구현
DB Connection Pool 생성
```

이 관심사는 각각 다른 경계에 둔다.

# 3.14 Facade는 Handler와 Service 사이의 유스케이스 경계다

현재 Facade는 `application.facade`에 위치한다.

### 그림 3-17. Facade의 역할

```text
Handler
   │ Object dtoBody
   ▼
┌───────────────────────────────┐
│ Facade                        │
│                               │
│ 1. DTOin 변환                 │
│ 2. 유스케이스 진입            │
│ 3. @Transactional 선언        │
│ 4. Service 호출               │
└───────────────┬───────────────┘
                ▼
             Service
```

Facade가 필요한 이유는 단순히 “Service 앞에 한 계층을 더 두기 위해서”가 아니다.

```text
Handler의 라우팅 책임
        │
        ▼
Facade의 유스케이스·TX 계약
        │
        ▼
Service의 업무 절차
```

세 책임을 분리하기 위해서다.

# 3.15 Facade의 @Transactional과 실제 TX BEGIN은 같은 말이 아니다

레이어드 아키텍처 설명에서 가장 쉽게 잘못되는 부분이다.

현재 Facade에는 `@Transactional`이 존재하지만 실행 모드에 따라 실제 Transaction 시작점이 다르다.

### 그림 3-18. TCF ON + Timeout ON

```text
Worker Thread

TransactionTemplate
      │
      │ TX BEGIN
      ▼
Dispatcher
      ▼
Handler
      ▼
Facade Proxy
@Transactional(REQUIRED)
      │
      │ 기존 TX 존재
      ▼
   JOIN
      │
      ▼
Service → DAO
      │
      ▼
COMMIT / ROLLBACK
```

이 모드에서는 다음 표현이 정확하다.

```text
최외곽 TX 소유
  = TimeoutExecutor Worker TransactionTemplate

Facade
  = 유스케이스 TX 선언
  = 기존 TX 참여
```

---

# 3.16 Timeout OFF에서는 Facade가 실제 TX 시작점이 될 수 있다

### 그림 3-19. TCF ON + Timeout OFF

```text
Request Thread

Controller
   ↓
TcfFacade
   ↓
Sync Executor
   ↓
Dispatcher
   ↓
Handler
   ↓
Facade Proxy
   │
   │ @Transactional(REQUIRED)
   ▼
TX BEGIN
   ↓
Service
   ↓
DAO
   ↓
COMMIT / ROLLBACK
```

따라서 “Transaction은 어느 레이어 책임인가?”와 “어느 클래스가 현재 물리 BEGIN을 실행하는가?”를 구분한다.

### 그림 3-20. 논리적 TX 경계와 물리 TX 시작점

```text
논리적 유스케이스 TX 계약
          │
          ▼
        Facade
          │
          │
          ├──── Timeout OFF ──> Facade Proxy가 BEGIN
          │
          └──── Timeout ON ───> Worker 외곽 TX에 JOIN
```

이 차이는 22장에서 다시 상세히 다룬다.

# 3.17 Service는 업무 절차를 읽을 수 있는 곳이어야 한다

Service는 “무엇을 해야 하는가”를 순서대로 표현한다.

### 그림 3-21. Service의 정상 역할

```text
Service Method
     │
     ├─ 입력 검증
     │
     ├─ 조회/변경 조건 계산
     │
     ├─ DAO 호출
     │
     ├─ 필요 시 Client 호출
     │
     └─ 결과 조립
```

좋은 Service 코드는 다음처럼 읽힌다.

```text
검증한다
   ↓
기존 데이터를 조회한다
   ↓
업무 조건을 판단한다
   ↓
변경한다
   ↓
결과를 만든다
```

Service가 다음까지 모두 떠안기 시작하면 경계가 무너진다.

```text
HTTP Header 파싱
JSON Envelope 조립
JDBC Connection 직접 관리
Mapper XML 문자열 작성
CORS 판단
Servlet Response 쓰기
```

# 3.18 현재는 별도 Rule 계층이 구현되어 있지 않다

저장소 공통 아키텍처에서는 `application.rule`을 권장한다.

그러나 현재 PDMG AS-IS에는 별도 Rule 패키지를 실행 구조의 실제 계층처럼 넣으면 안 된다.

### 그림 3-22. AS-IS와 TO-BE의 Rule 차이

```text
[AS-IS]

Facade
   ↓
Service
   ├─ 검증
   ├─ 업무 판단
   ├─ 계산
   └─ DAO
        ↓
       DB


[TO-BE / 설계 방향]

Facade
   ↓
Service
   ├─ Rule
   │    ├─ 검증
   │    └─ 계산
   │
   └─ DAO
        ↓
       DB
```

Rule은 모든 Service에서 기계적으로 만들어야 하는 계층이 아니다.

다음과 같은 경우 후보가 된다.

```text
여러 Service에서 반복되는 업무 규칙인가?
        │
        ├─ 예
        │   ↓
        │ 독립 테스트 가치가 큰가?
        │   ├─ 예 → Rule 후보
        │   └─ 아니오 → Service 내부 판단 가능
        │
        └─ 아니오 → Service에 유지 검토
```

# 3.19 DTO는 수직 실행 레이어라기보다 데이터 계약이다

DTO는 Handler, Facade, Service, DAO에서 사용될 수 있다.

그렇다고 DTO를 “Application 아래, Persistence 위”에 있는 일반 실행 Layer로 보면 어색하다.

### 그림 3-23. DTO는 여러 경계를 건너는 계약

```text
                  ┌──────────────────┐
                  │      DTO         │
                  │   Data Contract  │
                  └───────┬──────────┘
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
        ▼                 ▼                 ▼
     Facade            Service             DAO
        │                 │                 │
        └─────────────────┴─────────────────┘
```

DTO의 핵심은 데이터를 전달하는 것이다.

```text
DTO

O 필드
O Getter/Setter
O 생성도구 계약

X Service 주입
X DAO 주입
X SQL 실행
X Transaction 시작
X 외부 API 호출
```

현재 DTO는 기술적으로 `DataObject` 계열 의존 등 기존 계약을 포함할 수 있으므로 “완전히 순수한 Domain Object”라고 부르면 안 된다.

# 3.20 DAO는 현재 MyBatis Mapper 인터페이스 역할을 한다

PDMG에서 `DAO`라고 부르는 컴포넌트를 전통적인 구현 클래스형 DAO로만 이해하면 안 된다.

현재 구조에서는 DAO 인터페이스가 MyBatis Mapper 계약으로 동작한다.

### 그림 3-24. DAO와 MyBatis 실제 연결

```text
Service
   │
   ▼
DAO Interface
   │
   │ MyBatis Proxy
   ▼
Mapper XML
   │
   ├─ namespace = DAO FQCN
   │
   └─ statement id = DAO method
   ▼
SQL
   │
   ▼
DB
```

따라서 DAO의 책임은 다음처럼 좁힌다.

```text
DAO

O Mapper statement 연결

X 업무 분기
X HTTP 응답 생성
X Commit/Rollback 직접 수행
X Service 재호출
```

# 3.21 Mapper XML은 Java 패키지와 다른 리소스 경계다

### 그림 3-25. Java DAO와 Mapper Resource

```text
Java
src/main/java
└─ nhnis/mg/co/a/persistence/dao
   └─ mgcoa9000DAO.java
             │
             │ namespace / method
             ▼
Resource
src/main/resources
└─ rdw.mg.co.a
   └─ mgcoa9000-ORA.xml
             │
             ▼
            SQL
```

현재 Mapper 검색은 Java 패키지 구조와 동일한 디렉터리 복제가 아니라 설정된 Mapper Location 패턴에 의해 동작한다.

따라서 Java 파일을 이동했다고 Mapper XML이 자동으로 따라 이동하거나 namespace가 자동 수정되는 것은 아니다.

# 3.22 Client는 Persistence 아래가 아니다

외부 WAS나 API 호출을 DB 접근과 같은 것으로 보고 DAO에 넣는 경우가 있다.

둘은 다른 Outbound 경계다.

### 그림 3-26. DB와 외부 시스템은 서로 다른 Outbound Port

```text
                 Service
               /         \
              /           \
             ▼             ▼
      Persistence        Client
          │                │
          ▼                ▼
     DAO / Mapper      External API
          │                │
          ▼                ▼
          DB            Other WAS
```

즉 다음 구조는 피한다.

```text
X DAO
   ├─ DB 조회
   └─ 외부 REST API 호출
```

현재 `client` 패키지는 실제 구현이 풍부한 상태가 아니라 placeholder/package-info 수준인 부분이 있으므로, 이 그림은 **책임 방향**을 설명하는 것이지 이미 모든 외부연동 Client가 구현됐다는 뜻은 아니다.

# 3.23 Config는 업무 호출선의 단계가 아니라 조립 책임이다

### 그림 3-27. Config가 하는 일

```text
             Config
               │
       ┌───────┼─────────┐
       │       │         │
       ▼       ▼         ▼
  DataSource   TM    SqlSession
       │       │         │
       └───────┴────┬────┘
                    ▼
             업무 Bean이 사용
```

   ↓
  Config

# 3.24 Support는 “무엇이든 넣는 Common”이 되어서는 안 된다

Support는 작은 보조 기능을 둘 수 있지만 책임이 불명확한 코드의 피난처가 되어서는 안 된다.

### 그림 3-28. Support가 커질 때 나타나는 문제

### 그림 3-38. AS-IS와 TO-BE 패키지 비교

```text
[AS-IS - 현재 PDMG]

entry
  ├─ handler
  └─ aspect

application
  ├─ controller
  ├─ facade
  └─ service

dto

persistence
  └─ dao


[TO-BE / 저장소 권장]

entry
  ├─ web
  ├─ handler
  └─ facade

application
  ├─ service
  └─ rule

dto / contract

persistence
  ├─ dao
  └─ mapper
```

이를 표로 보면 다음과 같다.

| 관심사 | AS-IS | TO-BE 방향 |
|---|---|---|
| HTTP Controller | `application.controller` | `entry.web` |
| Handler | `entry.handler` | 유지 |
| Facade | `application.facade` | `entry.facade` |
| Service | `application.service` | 유지 |
| Rule | 없음 | `application.rule` |
| DAO | `persistence.dao` | 유지 또는 정비 |
| Mapper | XML Resource 중심 | Mapper 경계 명시 강화 |

TO-BE를 이유로 AS-IS 문서를 현재 코드와 다르게 써서는 안 된다.

# 3.33 패키지 이동은 단순한 파일 이동이 아니다

Facade를 `application.facade`에서 `entry.facade`로 옮기는 일은 IDE에서 폴더 하나 옮기는 작업으로 끝나지 않는다.

### 그림 3-39. 패키지 이동 영향

```text
Java Package 변경
      │
      ├─ Import
      ├─ Component Scan
      ├─ AOP Pointcut
      ├─ MyBatis Namespace
      ├─ ResultType / ParameterType
      ├─ @MockBean FQCN
      ├─ Test Package
      ├─ Reflection
      ├─ Log Category
      └─ 문서 / 추적성
```

따라서 AS-IS와 TO-BE가 다르다고 즉시 일부 클래스만 이동하면 오히려 구조가 더 불안정해질 수 있다.

### 그림 3-40. 안전한 구조 변경 순서

```text
현재 호출 계약 확인
      ↓
목표 패키지 정의
      ↓
Java Import 영향
      ↓
Spring Scan 영향
      ↓
AOP Pointcut 영향
      ↓
Mapper/XML 영향
      ↓
Test 영향
      ↓
일괄 변경
      ↓
아키텍처 + 통합 검증
```

# 3.34 Layer와 Transaction Boundary는 겹치지만 동일하지 않다

레이어 다이어그램을 Transaction 다이어그램처럼 읽으면 안 된다.

### 그림 3-41. 논리 레이어와 기술 TX 범위

```text
[논리 구조]

FW
 ↓
Entry
 ↓
Application
 ↓
Persistence


[TCF ON + Timeout ON 실제 TX]

FW Request Thread
   Filter / Interceptor / Controller / TcfFacade
                     │
                     │ TX 밖
─────────────────────┼────────────────────────
                     ▼
Worker Thread
╔══════════════════════════════════╗
║ FW Dispatcher                   ║
║      ↓                          ║
║ Entry Handler                   ║
║      ↓                          ║
║ Application Facade / Service    ║
║      ↓                          ║
║ Persistence DAO                 ║
╚══════════════════════════════════╝
```

즉 FW 컴포넌트인 Dispatcher가 Transaction 안에 있을 수 있다.

```text
"어느 Layer인가?"
       ≠
"TX 안인가?"
```

이 두 질문은 별도로 답해야 한다.

# 3.35 Layer와 Thread Boundary도 동일하지 않다

# 3.36 Layer와 Module Boundary도 동일하지 않다

# 3.37 PDMG를 클린 아키텍처 관점으로 보면 어디까지 왔는가

PDMG는 레이어드 아키텍처다.

그렇다고 엄격한 의미에서 “클린 아키텍처가 완성되어 있다”고 단정하기는 어렵다.

### 그림 3-44. PDMG를 클린 아키텍처 언어로 번역

```text
┌───────────────────────────────────────────────────────┐
│ Framework / Drivers                                   │
│ pdmg-fw / Spring / MyBatis                            │
│                                                       │
│   ┌───────────────────────────────────────────────┐   │
│   │ Adapters                                      │   │
│   │ Controller / Handler / DAO / Client           │   │
│   │                                               │   │
│   │    ┌─────────────────────────────────────┐    │   │
│   │    │ Use Case                            │    │   │
│   │    │ Facade / Service                    │    │   │
│   │    │                                     │    │   │
│   │    │   [TO-BE] Rule / Domain Policy     │    │   │
│   │    └─────────────────────────────────────┘    │   │
│   └───────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────┘
```

대응 관계는 다음과 같이 볼 수 있다.

| PDMG | 클린 아키텍처 관점 |
|---|---|
| Controller / Handler | Inbound Adapter |
| Facade / Service | Use Case |
| Rule | Domain Policy 후보 — 현재 별도 계층 없음 |
| DAO / Mapper | Outbound Adapter |
| Client | Outbound Adapter |
| DTO | Boundary Data Contract |
| pdmg-fw | Framework / Driver |

현재 Service는 구체 DAO와 DTO에 직접 의존하고, DAO는 MyBatis 기술에 결합되어 있다.

따라서 더 정확한 표현은 다음이다.

> **PDMG는 레이어드 구조를 기반으로 의존성 규칙을 강화해 가는 구조다.**

| 컴포넌트 | 해야 할 것 | 하지 말아야 할 것 |
|---|---|---|
| Handler | Service ID 등록·분기, Facade 호출 | SQL, 상세 업무검증, DAO 직접호출 |
| Controller | HTTP 입력 Adapter | SQL, 업무 핵심규칙 |
| Facade | DTO 변환, 유스케이스 경계, TX 계약 | Mapper 직접 호출, 상세 SQL |
| Service | 업무 절차·검증·결과 조립 | HTTP Response 조립, Servlet 의존 |
| Rule | TO-BE: 독립 업무 규칙 | DB/외부 부수효과 |
| DTO | 데이터 계약 | Bean 주입, 업무 실행 |
| DAO | 데이터 접근 계약 | 업무 분기, HTTP |
| Mapper XML | SQL | 인증·거래 흐름 판단 |
| Client | 외부 시스템 연동 | DB 영속 책임 |
| Config | Bean 조립 | 업무 유스케이스 실행 |
| Support | 작은 순수 보조 | 이름 없는 대형 업무 Service |
| Aspect | 횡단 처리 | 프로그램별 if/switch 업무 분기 |

# 3.47 제3장에서 기억해야 할 아홉 가지

첫째, **레이어는 호출 순서가 아니라 책임과 의존 방향의 경계다.**

둘째, **Handler·Facade·Service·DAO는 레이어 자체라기보다 레이어 안에서 역할을 수행하는 컴포넌트다.**

셋째, **현재 PDMG 업무 코드는 `nhnis.mg.co.a.*` 단일 축으로 정리되어 있으며, 과거 축 없는 구 패키지는 제거되었다.**

넷째, **현재 AS-IS는 `entry.handler → application.facade → application.service → persistence.dao`가 중심 흐름이다.**

다섯째, **`DTO`, `Config`, `Client`, `Support`, `Aspect`를 모두 하나의 수직 실행 Layer처럼 표현하면 안 된다.**

여섯째, **TCF ON + Timeout ON에서는 외곽 Worker Transaction이 Dispatcher와 Handler까지 감싸므로 Layer Boundary와 Transaction Boundary는 동일하지 않다.**

일곱째, **Runtime Call 방향과 Compile Dependency 방향도 항상 같지 않다. `TransactionHandler` 계약이 대표적인 Dependency Inversion 사례다.**

여덟째, **현재 별도 Rule 계층은 없으며, `application.rule`은 TO-BE 설계 방향으로 구분한다.**

아홉째, **좋은 레이어드 아키텍처는 클래스를 많이 만드는 구조가 아니라 변경 이유와 책임이 서로 침범하지 않는 구조다.**

---

# 3.48 다음 장으로

제3장에서는 PDMG 프로그램을 “책임과 의존 방향”으로 분해했다.

이제 다음 문제가 남는다.

```text
Handler가 여러 개 생기면
어떤 Handler가 어떤 거래를 담당하는가?

mgcoa9000은 무엇이고
mgcoa9000S0은 무엇인가?

화면 ID와 Program ID는 같은가?

Service ID의 각 자리는 무엇을 의미하는가?

Service ID는 URL뿐 아니라
Handler / DTO / SQL과 어떻게 연결되는가?
```

### 그림 3-54. 제4장으로 이어지는 질문

```text
제3장
"코드는 어디에 두는가?"

Entry
  ↓
Application
  ↓
Persistence


          │
          │ 이제 식별체계를 본다
          ▼


제4장
"그 코드가 어떤 프로그램과 거래인가?"

MG
 ↓
업무코드
 ↓
세부업무
 ↓
Program ID
 ↓
Service ID
```

다음 장에서는 PDMG 애플리케이션 코드 분류표와 Service ID를 이용해 **화면·프로그램·거래·Handler·SQL을 하나의 식별체계로 연결하는 방법**을 살펴본다.
