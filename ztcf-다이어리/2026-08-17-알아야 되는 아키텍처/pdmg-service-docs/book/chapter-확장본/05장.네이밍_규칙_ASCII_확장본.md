# 제5장. 네이밍 규칙

> **집필 기준**
>
> 이 장에서 PDMG 명명 규칙의 정본은 **`MG-NAMING_CONVENTION.md`** 이다.
> `06.네이밍 형식.md`는 정본을 설명하는 상세 해설 자료로 사용한다.
> 재분석 자료에서 현재 소스와 다른 항목이 확인된 경우에는 실제 소스와 정본의 차이를 구분한다.
>
> 특히 다음 사항을 기준으로 한다.
>
> - Service ID는 11자리다.
> - Program ID는 9자리다.
> - Handler / Facade / Service / Controller / DAO / Mapper 파일은 **Program ID 단위**로 묶는다.
> - URL / DTO / Facade 메서드 / Service 메서드 / SQL ID 앞부분은 **Service ID 단위**다.
> - 현재 PDMG 업무 타입은 일반 Java PascalCase가 아니라 `mgcoa8888Facade`처럼 **소문자로 시작하는 프로젝트 호환 규칙**을 사용한다.
> - 일반 FW / Config / Aspect 클래스는 PascalCase를 사용한다.
> - 현재 Facade 패키지는 `application.facade`다. 저장소 공통 권장 구조의 `entry.facade`와 구분한다.
> - SQL ID는 Service ID와 DML 구분을 이용해 DAO 메서드 및 Mapper statement를 연결한다.
> - DTO 필드는 camelCase가 원칙이지만 실제 자동 생성 DTO에는 UPPER_SNAKE_CASE 필드와 생성 메서드 예외가 존재한다.
> - 오류코드 네이밍은 현재 소스에서 완전히 한 형식으로 통일되어 있지 않다.
>
> 따라서 이 장의 목적은 “예쁜 이름을 만드는 법”이 아니다.
>
> **Service ID 하나를 기준으로 Package → Class → Method → DTO → DAO → Mapper → SQL → Log까지 추적 가능한 이름 체계를 만드는 것**이 목적이다.

# 5.1 네이밍은 장식이 아니라 아키텍처 연결 규칙이다

제4장에서는 다음 Service ID를 예로 들었다.

```text
mgcoa9000S0
```

이 문자열은 단순한 거래 코드가 아니다.

PDMG에서는 이 한 값을 기준으로 소스의 여러 이름이 연쇄적으로 결정된다.

### 그림 5-1. Service ID에서 시작되는 Naming Tree

```text
                         mgcoa9000S0
                              │
                 ┌────────────┴────────────┐
                 │                         │
                 ▼                         ▼
           Program ID                  거래 ID
           mgcoa9000                  mgcoa9000S0
                 │                         │
     ┌───────────┼───────────┐             ├─ URL
     │           │           │             ├─ DTO
     ▼           ▼           ▼             ├─ Facade Method
 Handler      Facade      Service           ├─ Service Method
 mgcoa9000*  mgcoa9000*  mgcoa9000*        └─ SQL ID Prefix
     │
     ├─ DAO
     └─ Mapper File
```

이 구조가 잘 지켜지면 운영 로그에서 `mgcoa9000S0` 하나만 발견해도 개발자는 프로그램 파일을 빠르게 좁힐 수 있다.

### 그림 5-2. 이름이 좋을 때의 소스 추적

```text
운영 로그
mgcoa9000S0
     │
     ▼
Program ID
mgcoa9000
     │
     ├─ mgcoa9000Handler
     ├─ mgcoa9000Facade
     ├─ mgcoa9000Service
     ├─ mgcoa9000DAO
     └─ mgcoa9000-ORA.xml
     │
     ▼
다시 Service ID 검색
     │
     ├─ mgcoa9000S0DTOin
     ├─ mgcoa9000S0DTOout
     ├─ facade.mgcoa9000S0()
     ├─ service.mgcoa9000S0()
     └─ mgcoa9000S0_S0
```

네이밍이 무너지면 같은 작업이 다음처럼 바뀐다.

### 그림 5-3. 이름이 무너졌을 때

```text
운영 로그
mgcoa9000S0
     │
     ▼
?
     │
     ├─ TxParameterController?
     ├─ CommonManagementService?
     ├─ TxParamRepository?
     ├─ selectParameterList?
     └─ transaction-param.xml?
```

“검색하면 찾을 수 있다”와 “이름 자체가 구조를 설명한다”는 완전히 다르다.

# 5.2 PDMG 명명 규칙에는 우선순위가 있다

현재 네이밍 관련 문서는 여러 개 존재한다.

### 그림 5-4. 네이밍 기준 문서의 역할

```text
00.NSIGHT 애플리케이션 코드 분류표
        │
        │ 업무 의미의 최상위 기준
        ▼
MG-NAMING_CONVENTION.md
        │
        │ PDMG 구현 네이밍 정본
        ▼
06.네이밍 형식.md
        │
        │ 형식/예제/해설
        ▼
네이밍원칙 / 재분석 문서
        │
        └─ 일반 Java 원칙 / 차이 분석
```

따라서 규칙이 충돌한다면 다음 순서로 판단한다.

```text
현재 실행 소스
      ↓
MG-NAMING_CONVENTION
      ↓
06.네이밍 형식
      ↓
일반 네이밍 설명
      ↓
과거 분석 자료
```

일반 Java 관례를 이유로 현재 PDMG 정본을 임의로 바꾸지 않는다.

# 5.3 PDMG Naming의 출발점은 Service ID다

### 그림 5-5. Service ID 11자리

```text
[대그룹2][업무2][세부1][식별4][구분1][순번1]

    mg      co     a    9000    S     0

2 + 2 + 1 + 4 + 1 + 1
          =
         11자
```

### 그림 5-6. Program Prefix와 Service ID

```text
mgcoa9000S0
└────┬───┘││
     │    │└─ 순번
     │    └── 거래구분
     │
     └────── Program Prefix
             mgcoa9000
```

PDMG Naming을 이해하는 가장 중요한 구분은 다음이다.

```text
Program Prefix
  mgcoa9000

Service ID
  mgcoa9000S0
```

# 5.4 Program Prefix가 붙는 것과 Service ID가 붙는 것을 구분한다

### 그림 5-7. Program 단위와 거래 단위 Naming

```text
Program Prefix
mgcoa9000
   │
   ├─ mgcoa9000Handler
   ├─ mgcoa9000Facade
   ├─ mgcoa9000Service
   ├─ mgcoa9000Controller
   ├─ mgcoa9000DAO
   └─ mgcoa9000-ORA.xml


Service ID
mgcoa9000S0
   │
   ├─ /mgcoa9000S0
   ├─ mgcoa9000S0DTOin
   ├─ mgcoa9000S0DTOout
   ├─ Facade.mgcoa9000S0()
   ├─ Service.mgcoa9000S0()
   └─ mgcoa9000S0_S0
```

이 규칙 때문에 동일 프로그램에 CRUD 거래가 늘어도 프로그램 클래스는 늘어나지 않는다.

### 그림 5-8. 거래가 늘어날 때 파일 증가 방식

```text
기존
mgcoa9000S0
     │
     ├─ Handler 1
     ├─ Facade 1
     ├─ Service 1
     ├─ DAO 1
     └─ Mapper 1


C0/U0/D0 추가
     │
     ├─ Handler 그대로
     ├─ Facade 그대로
     ├─ Service 그대로
     ├─ DAO 그대로
     ├─ Mapper 그대로
     │
     └─ 거래별
          ├─ DTO 추가
          ├─ 메서드 추가
          └─ SQL statement 추가
```

# 5.5 왜 클래스명에 S0/C0/U0를 붙이지 않는가

다음은 PDMG 프로그램 단위 통합 원칙과 맞지 않는다.

```text
mgcoa9000S0Handler
mgcoa9000C0Handler
mgcoa9000U0Handler
mgcoa9000D0Handler
```

### 그림 5-9. 잘못된 거래별 클래스 분리

```text
             mgcoa9000
        /       |       |       \
       ▼        ▼       ▼        ▼
 S0Handler  C0Handler U0Handler D0Handler
 S0Service  C0Service U0Service D0Service

          클래스 수 폭증
```

현재 표준은 다음과 같다.

### 그림 5-10. Program 단위 통합

```text
             mgcoa9000
                 │
         mgcoa9000Handler
                 │
   ┌─────────────┼─────────────┐
   ▼             ▼             ▼
  S0            C0/U0          D0
   │             │             │
   └─────────────┼─────────────┘
                 ▼
         mgcoa9000Facade
                 ▼
         mgcoa9000Service
                 ▼
          mgcoa9000DAO
```

# 5.6 PDMG는 일반 Java Naming에 프로젝트 예외가 있다

일반 Java에서는 클래스명이 PascalCase인 것이 보통이다.

예:

```text
CustomerService
TransactionController
RdwDataSourceConfig
```

그러나 현재 PDMG 업무 프로그램 타입은 다음 형태를 사용한다.

```text
mgcoa8888Handler
mgcoa8888Facade
mgcoa8888Service
mgcoa8888DAO
```

### 그림 5-11. 일반 Java와 PDMG 업무 타입 차이

```text
일반 Java Type
──────────────────────────
CustomerService
GlobalExceptionHandler
SecurityConfig
BizPrePostAspect

       PascalCase


PDMG 업무 Type
──────────────────────────
mgcoa8888Handler
mgcoa8888Facade
mgcoa8888Service
mgcoa8888DAO

       소문자 시작
```

따라서 다음과 같이 “교정”하면 현재 PDMG 정본과 달라진다.

```text
X Mgcoa8888Handler
X MgCoa8888Facade
X MGCOA8888Service
```

# 5.7 일반 FW·Config·Aspect는 PascalCase를 사용한다

# 5.11 현재 `application.facade`와 저장소 권장 `entry.facade`를 구분한다

현재 PDMG의 Facade는:

```text
nhnis.mg.co.a.application.facade
```

다른 저장소 공통 아키텍처 권장에서는 `entry.facade` 구조를 제시할 수 있다.

### 그림 5-16. 패키지 기준의 AS-IS / TO-BE 구분

```text
[현재 PDMG AS-IS]

entry.handler
      ↓
application.facade
      ↓
application.service


[저장소 공통 권장 방향]

entry.handler
      ↓
entry.facade
      ↓
application.service
```

따라서 다음 문장을 일반 규칙처럼 쓰면 안 된다.

```text
"entry.facade는 무조건 금지한다."
```

정확한 표현:

```text
현재 PDMG 배치 기준
  Facade = application.facade

향후 공통 구조 정비 시
  entry.facade 이동은 별도 마이그레이션 과제
```

# 5.12 Handler Naming

Handler 형식:

```text
mgcoa[식별4]Handler
```

예:

```text
mgcoa8888Handler
mgcoa9000Handler
mgcoa9999Handler
```

### 그림 5-17. Handler 이름 생성

```text
Service ID
mgcoa8888S0
     │
     ├─ S0 제거
     ▼
Program Prefix
mgcoa8888
     │
     └─ + Handler
          ▼
mgcoa8888Handler
```

Handler 메서드는 일반 역할명을 쓴다.

```text
serviceIds()
handle(...)
```

거래 메서드명을 Handler에 직접 생성하는 것이 아니라 `handle()` 내부에서 Service ID로 Facade를 분기한다.

# 5.13 Handler 이름과 Service ID 등록값은 서로 다른 계약이다

### 그림 5-18. Handler의 네이밍 계약과 런타임 계약

```text
[네이밍 계약]

Class
mgcoa9000Handler
      │
      └─ Program ID = mgcoa9000


[런타임 계약]

serviceIds()
  mgcoa9000S0
  mgcoa9000C0
  mgcoa9000U0
  mgcoa9000D0
```

둘 다 맞아야 한다.

```text
이름만 맞음 + 등록 틀림
       = 실행 오류

등록만 맞음 + 이름 틀림
       = 추적성/표준 오류
```

# 5.14 Facade Naming

Facade 형식:

```text
mgcoa[식별4]Facade
```

메서드명:

```text
Service ID 전체
```

### 그림 5-19. Facade 클래스와 거래 메서드

```text
mgcoa8888Facade
   │
   ├─ mgcoa8888S0(Object dtoBody)
   └─ mgcoa8888D0(Object dtoBody)
```

PDMG 거래 메서드에는 일반 업무 의미의 동사형 이름보다 Service ID를 사용한다.

```text
O mgcoa8888S0()
O mgcoa8888D0()

X selectImageLogList()
X deleteImageLog()
X processS0()
X execute()
```

이 규칙은 읽기 좋은 비즈니스 영어 이름보다 **전체 거래 추적성**을 우선한다.

# 5.15 일반 메서드와 거래 메서드를 구분한다

모든 메서드를 Service ID로 부르는 것은 아니다.

### 그림 5-20. Method Naming 두 종류

```text
거래 진입 메서드
────────────────────────
mgcoa9000S0()
mgcoa9000C0()
mgcoa9000U0()
mgcoa9000D0()

= Service ID 그대로


일반 보조 메서드
────────────────────────
validateInput()
calculateOffset()
resolveServiceId()
buildResponse()

= 동사형 camelCase
```

따라서 다음도 나쁜 설계다.

```text
private void mgcoa9000Helper1()
private int mgcoa9000Calc()
```

Service ID는 **거래 진입점**에 쓰고 내부 구현은 의미 있는 일반 메서드명을 사용한다.

# 5.16 Facade의 Naming과 Transaction 책임을 혼동하지 않는다

Facade 이름 규칙은 안정적이지만 Transaction 시작점 설명은 실행 모드에 따라 달라진다.

### 그림 5-21. 같은 Facade 이름, 다른 TX 시작

```text
mgcoa9000Facade.mgcoa9000U0()
         │
         ├─ Timeout OFF
         │    └─ Facade Proxy가 TX 시작
         │
         └─ Timeout ON
              └─ Worker TransactionTemplate의
                 기존 TX에 REQUIRED 참여
```

따라서 Naming 문서에서 다음처럼 단정하지 않는다.

```text
X "Facade가 항상 물리 Commit/Rollback의 유일한 주체"
```

더 정확한 설명은 다음이다.

> Facade는 PDMG 업무 유스케이스의 기본 Transaction 선언 지점이며, Timeout ON에서는 외곽 Worker Transaction에 참여한다.

# 5.17 Service Naming

Service 형식:

```text
mgcoa[식별4]Service
```

거래 메서드:

```text
Service ID 전체
```

### 그림 5-22. Facade와 Service Method 이름 일치

```text
Handler
   │
   ▼
mgcoa9000Facade
   │
   └─ mgcoa9000S0()
          │
          ▼
mgcoa9000Service
   │
   └─ mgcoa9000S0()
          │
          ▼
DAO
```

이 일치는 검색과 추적을 매우 단순하게 만든다.

```text
로그에 mgcoa9000S0
   ↓
IDE 전체 검색
   ↓
Facade + Service + DTO + SQL
```

# 5.18 Controller Naming

TCF OFF 호환 Controller 형식:

```text
mgcoa[식별4]Controller
```

예:

```text
mgcoa8888Controller
```

메서드 매핑:

```text
@PostMapping("/mgcoa8888S0")
```

### 그림 5-23. TCF OFF Controller Naming

```text
Program ID
mgcoa8888
     │
     └─ mgcoa8888Controller
             │
             ├─ POST /mgcoa8888S0
             └─ POST /mgcoa8888D0
```

현재 PDMG 표준은 다음 REST 스타일을 주 API 규칙으로 쓰지 않는다.

```text
X /api/image-log/list
X /api/mg/co/a/8888/list
X GET /mgcoa8888
```

PDMG 온라인 전문 호출의 중심은 Service ID다.

# 5.19 DTO Naming

DTO는 Program ID가 아니라 **Service ID 전체**를 포함한다.

형식:

```text
[Service ID]DTOin
[Service ID]DTOout
[Service ID]DTOSub[n]
```

### 그림 5-24. DTO 이름 생성

```text
Service ID
mgcoa8888S0
     │
     ├─ + DTOin
     │    └─ mgcoa8888S0DTOin
     │
     ├─ + DTOout
     │    └─ mgcoa8888S0DTOout
     │
     └─ + DTOSub0
          └─ mgcoa8888S0DTOSub0
```

거래가 달라지면 DTO도 구분한다.

### 그림 5-25. 같은 Program, 다른 DTO 계약

```text
mgcoa8888
  │
  ├─ S0
  │    ├─ mgcoa8888S0DTOin
  │    └─ mgcoa8888S0DTOout
  │
  └─ D0
       ├─ mgcoa8888D0DTOin
       └─ mgcoa8888D0DTOout
```

# 5.20 DTO 접미사의 대소문자도 계약이다

현재 표준:

```text
DTOin
DTOout
DTOSub
```

따라서 다음은 다른 이름이다.

```text
X DtoIn
X DTOIn
X DtoOut
X DtoSub
```

### 그림 5-26. DTO Type Case

```text
mgcoa8888S0 + DTO + in
                 │
                 ▼
       mgcoa8888S0DTOin
```

자동 생성기, 설계서, 테스트 파일이 모두 같은 문자열을 사용해야 한다.

# 5.21 DTO 필드는 camelCase가 원칙이다


```text

totalCount
```

### 그림 5-27. DB Column에서 DTO 필드로

```text

   │
   │ Java Mapping
   ▼
DTO
trtBrc
   │
   ▼
JSON
"trtBrc"
```

```text

UPPER_SNAKE → camelCase
```

# 5.22 그러나 실제 생성 DTO에는 예외가 있다

현재 소스 재분석에서는 일부 자동 생성 결과 DTO에 다음과 같은 필드가 확인된다.

```text

RSLT_CD
RSLT_MSG
```

또 생성된 Accessor 이름이 일반 JavaBeans 규칙과 다를 수 있다.

### 그림 5-28. DTO Naming의 원칙과 실제 예외

```text
[표준 원칙]

private String rsltCd;

setRsltCd()


[현재 생성 DTO 예외]

```

이것을 손으로 임의 교정하면 생성 계약과 직렬화 계약이 깨질 수 있다.

# 5.23 생성 DTO는 일반 Java Code Style과 구분한다

### 그림 5-29. 생성 코드의 예외 처리 원칙

```text
이 파일은 자동 생성물인가?
        │
     ┌──┴──┐
    YES   NO
     │     │
     ▼     ▼
생성기 계약  일반 Java
우선        camelCase
     │
     ▼
직렬화/Mapper/화면 계약 확인
```

즉 다음 원칙을 적용한다.

```text
일반 개발 코드
  → camelCase

자동 생성 DTO
  → 현재 생성기 계약을 우선 확인
  → 변경하려면 생성기부터 변경
```

생성 결과만 손으로 바꾸는 것은 피한다.

# 5.25 SQL ID는 Service ID + SQL 동작으로 만든다

기본 패턴:

```text
[Service ID]_[DML][순번]
```

### 그림 5-31. SQL ID 해부

```text
mgcoa8888S0_S0
└─────┬─────┘││
      │      │└─ SQL 순번
      │      └── DML 구분 S
      │

```

예:

```text

mgcoa9000U0_U0
```

# 5.26 Service Operation과 SQL DML은 서로 다른 층의 표현이다

다음 SQL ID를 보자.

```text
mgcoa9000S0_S0
```

앞의 `S0`와 뒤의 `S0`는 위치가 다르다.

### 그림 5-32. Service 구분자와 SQL DML 구분자

```text
mgcoa9000 S0 _ S0
           │    │
           │    └─ 이 거래 안의 SQL 동작
           │       Select #0
           │
           └────── 온라인 거래 타입
                   Select #0
```

복합 거래라면 둘이 다를 수도 있는 설계 여지가 있다.

예를 들어 Action 거래에서 내부적으로 조회와 변경 SQL이 여러 개 필요할 수 있다.

> **설계 예시**

```text
mgcoa7777A0_S0
mgcoa7777A0_U0
```

현재 실제 사용 여부는 각 프로그램 Mapper를 확인해야 한다.

# 5.31 SQL 보조 접미사는 실제 소스를 반영한다

기본 문서에는 주로 다음 형태가 설명되어 있다.

```text
_S0
_C0
_U0
_D0
_COUNT / _count
```

현재 재분석에서는 실제 소스에 `_exists` 같은 보조 statement도 확인된다.

### 그림 5-37. 주 SQL과 보조 SQL

```text
Service
mgcoa9000C0
    │
    ├─ 존재 여부 확인
    │    └─ ..._exists
    │
    └─ 등록
         └─ mgcoa9000C0_C0
```

따라서 SQL Naming을 “오직 `_S0/_C0/_U0/_D0`만 허용”으로 단정하지 않는다.

정확한 기준은 다음이다.

```text
주 statement
  → Service ID + DML + 순번

보조 statement
  → 의미를 잃지 않는 명시적 접미사 사용
  → 실제 정본/샘플과 일치
```

---

# 5.32 Count SQL Naming은 한 가지 문서 표기만 믿지 않는다

자료에 따라:

```text
mgcoa8888S0_S0_count
```

또는 프로그램별 실제 구현에서:

```text
mgcoaXXXXS0_COUNT
```

같은 표기가 존재할 수 있다.

### 그림 5-38. Count Naming의 관리 원칙

```text
Count Statement
      │
      ▼
현재 Program 실제 Mapper 확인
      │
      ▼
DAO Method와 XML ID 완전 일치
      │
      ▼
신규 개발은 정본/기준 Sample에 맞춰 통일
```

이 장에서는 존재하지 않는 단일 형식을 임의로 확정하지 않는다.

장기적으로는 Count/Exists 접미사까지 정본에 명시하는 것이 좋다.

```text
     │
     ▼

```

```text

   │
   ├─ FW0001 / FW9999
   ├─ FW_TIMEOUT
   ├─ FW_OVERLOADED
   ├─ MP....
   └─ Business Code
```

# 5.47 오류코드 TO-BE Naming은 별도 정책이 필요하다

> **TO-BE**

### 그림 5-53. 오류코드 체계화 방향


# 5.48 서비스 ID와 메서드 이름은 추적을 위한 의도적 중복이다

일반적인 Clean Code 관점에서는 다음이 더 읽기 좋아 보일 수 있다.

```text

```

그러나 PDMG는 다음을 선택한다.

```text

```

### 그림 5-54. 의미 가독성과 운영 추적성의 Trade-off

```text
Business Verb

   │
   └─ 사람에게 의미가 바로 보임


Service ID
mgcoa8888S0()
   │
   └─ URL / Log / Handler / DTO / SQL과
      동일 키로 추적 가능
```

PDMG는 온라인 거래 진입 메서드에서 후자를 택한다.

본문 설명과 JavaDoc, 설계서가 거래의 업무 의미를 보완해야 한다.

# 5.49 이름만으로 업무 의미를 전부 담으려 하지 않는다

# 5.77 제5장에서 기억해야 할 열다섯 가지

첫째, **PDMG Naming 정본은 `MG-NAMING_CONVENTION.md`다.**

둘째, **모든 업무 이름은 애플리케이션 분류와 Service ID에서 파생된다.**

셋째, **Program ID는 9자리, Service ID는 11자리다.**

넷째, **Handler / Facade / Service / Controller / DAO / Mapper 파일은 Program 단위다.**

다섯째, **URL / DTO / Facade·Service 거래 메서드 / SQL ID는 Service ID 단위다.**

여섯째, **현재 PDMG 업무 타입은 `mgcoa9000Service`처럼 소문자로 시작하는 프로젝트 예외를 사용한다.**

일곱째, **일반 FW·Config·Aspect 타입은 PascalCase다.**

여덟째, **거래 메서드는 Service ID, 내부 보조 메서드는 의미 있는 camelCase를 사용한다.**

아홉째, **DTO는 `DTOin`, `DTOout`, `DTOSub` 접미사를 사용한다.**

열째, **DTO 필드는 camelCase가 원칙이지만 자동 생성 DTO에는 현재 예외가 존재한다.**

열한째, **DAO 메서드와 Mapper statement ID는 정확히 같아야 한다.**

열두째, **Mapper namespace는 DAO FQCN과 정확히 같아야 한다.**

열셋째, **SQL 보조 접미사와 오류코드는 현재 실제 소스의 혼재를 숨기지 말고 별도 표준화 과제로 관리한다.**

열넷째, **현재 PDMG Facade는 `application.facade`에 있으며, `entry.facade`는 다른 공통 권장 구조와 구분한다.**

열다섯째, **Naming 규칙의 최종 목적은 검색 가능성, 변경 영향 분석, Runtime Routing, SQL 추적, 운영 진단을 하나의 식별체계로 묶는 것이다.**
