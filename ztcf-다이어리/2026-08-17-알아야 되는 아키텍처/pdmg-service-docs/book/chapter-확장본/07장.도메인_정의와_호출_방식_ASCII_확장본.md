# 제7장. 도메인 정의와 호출 방식

> **집필 기준**
>
> 이 장에서 사용하는 “도메인”이라는 말은 반드시 두 수준으로 구분한다.
>
> 1. **현재 PDMG AS-IS의 도메인**
>    - `MG → 업무코드 → 세부업무 → Program ID → Service ID`로 이어지는 **기술적 업무분류와 호출 경계**
>    - 현재 소스는 `Handler → Facade → Service → DAO/Mapper` 중심의 Transaction Script 성격이 강하다.
>    - 현재 일반 업무 소스에서 `domain` 패키지, Aggregate, Entity, Value Object, Domain Service, Repository 추상화가 일관되게 적용되어 있다고 단정하지 않는다.
>
> 2. **NSIGHT TCF의 확장 도메인 설계 방향**
>    - 복잡한 상태변경과 업무 규칙이 필요한 경우 Entity, Value Object, Aggregate, Rule, Domain Service 등을 도입할 수 있다.
>    - 이는 현재 PDMG의 모든 프로그램이 이미 DDD로 구현되어 있다는 뜻이 아니다.
>
> 또한 이 장은 다음 현재 실행 사실을 유지한다.
>
> - 현재 주 업무축은 `nhnis.mg.co.a.*`다.
> - 프로그램 단위 Handler가 여러 Service ID를 등록한다.
> - TCF ON + Timeout ON에서는 Worker의 `TransactionTemplate`이 Dispatcher/Handler 앞에서 외곽 DB TX를 시작한다.
> - TCF ON + Timeout OFF에서는 Facade가 TX 시작점이 될 수 있다.
> - TCF OFF AS-IS의 일부 Controller는 Facade가 아니라 Service를 직접 호출한다.
> - 같은 `pdmg-service` 안에서 프로그램이 다르다는 이유만으로 자기 자신을 HTTP 호출하는 것을 기본 원칙으로 삼지 않는다.
> - 같은 모듈 안의 공통 업무 규칙은 공통 Application Service, 명시적 내부 Port/Interface, 향후 Rule 등으로 분리하는 것이 더 적절할 수 있다.
> - 다른 WAR·시스템 호출은 `client` 경계와 표준 Service ID/전문 계약을 사용한다.
> - `support`는 업무 규칙의 저장소가 아니라 순수 보조 기능에 제한한다.
>
> 이 장의 목표는 “도메인이라는 용어를 정의하는 것”을 넘어,
>
> **누가 이 업무와 데이터를 소유하고, 다른 프로그램과 다른 시스템이 어느 경계를 통해 호출해야 하는지 판단할 수 있게 만드는 것**이다.

---

# 7.1 제6장에서 패키지를 나눴다면, 이제 경계를 나눠야 한다

제6장에서는 다음과 같은 구조를 보았다.

```text
nhnis.mg.co.a
├─ entry
├─ application
├─ dto
├─ persistence
├─ client
├─ config
└─ support
```

패키지가 잘 나뉘었다고 해서 도메인 경계가 자동으로 만들어지는 것은 아니다.

예를 들어 같은 JVM 안에서는 기술적으로 다음 호출도 가능하다.

### 그림 7-1. 기술적으로 가능한 호출

```text
mgcoa9000Service
       │
       ▼
mgcoa8888DAO
       │
       ▼
ImageLog Table
```

Spring Bean으로 주입될 수 있고 컴파일도 될 수 있다.

그러나 이 질문이 남는다.

```text
"호출할 수 있는가?"
       ≠
"호출해도 되는가?"
```

도메인 설계는 바로 두 번째 질문에 답하는 작업이다.

---

# 7.2 PDMG에서 “도메인”이라는 말부터 정확히 잡는다

일반적인 DDD에서는 도메인을 다음처럼 이야기한다.

### 그림 7-2. 일반적인 DDD 표현

```text
Business Domain
      │
      ├─ Entity
      ├─ Value Object
      ├─ Aggregate
      ├─ Domain Service
      ├─ Repository
      └─ Domain Event
```

하지만 현재 PDMG AS-IS의 일반 프로그램 구조는 다음에 더 가깝다.

### 그림 7-3. 현재 PDMG의 실제 중심 구조

```text
Service ID
    │
    ▼
Handler
    │
    ▼
Facade
    │
    ▼
Service
    │
    ├─ 입력 검증
    ├─ 업무 판단
    ├─ 파라미터 조립
    ├─ DAO 호출
    └─ DTO 결과 조립
    │
    ▼
DAO / Mapper
```

즉 현재 PDMG에서 도메인은 다음 의미로 읽는 것이 정확하다.

> **PDMG의 업무 코드, 프로그램 식별번호, Service ID를 기반으로 기능의 업무 소유권과 호출 경계를 분류한 기술적 업무 단위**

---

# 7.3 현재 PDMG 도메인과 DDD 도메인은 같은 말이 아니다

### 그림 7-4. 현재 PDMG와 DDD의 차이

```text
PDMG AS-IS
────────────────────────────────

MG
 └─ CO/A
     └─ Program
         └─ Service ID
             └─ Handler/Facade/Service/DAO


DDD
────────────────────────────────

Business Problem
 └─ Bounded Context
     └─ Aggregate
         ├─ Entity
         ├─ Value Object
         └─ Domain Rule
```

둘이 완전히 무관한 것은 아니다.

PDMG의 업무축을 장기적으로 명확한 업무 경계로 발전시킬 수 있다.

하지만 현재 구조를 다음처럼 과장해서 설명하면 안 된다.

```text
X co.a = 완성된 Bounded Context
X mgcoa9000 = Aggregate
X mgcoa9000DTO = Entity
X DAO = DDD Repository
```

현재 소스는 이런 의미를 보장하지 않는다.

# 7.4 이 책에서 사용할 도메인 계층

PDMG를 설명할 때 다음 다섯 수준을 구분하면 편리하다.

### 그림 7-5. PDMG 도메인 계층

```text
PDMG / MG Application
        │
        ▼
업무·세부업무 축
CO / A
        │
        ▼
Program
mgcoa9000
        │
        ▼
Transaction / Service
mgcoa9000S0
        │
        ▼
Runtime Invocation
Handler → Facade → Service → DAO
```

이 중 “도메인”이라는 말은 문맥에 따라 범위가 달라질 수 있으므로 이 책에서는 가능한 한 구체적으로 부른다.

```text
업무축
Program
Service ID
업무 소유권
데이터 소유권
```

# 7.5 애플리케이션 수준 — MG

### 그림 7-6. MG Application

```text
MG
│
├─ pdmg-service
│   └─ 업무 실행
│
├─ pdmg-ui
│   └─ 화면
│
├─ pdmg-fw
│   └─ 공통 실행 Framework
│
└─ pdmg-jwt
    └─ 인증/토큰
```

`pdmg-fw`는 MG 업무 규칙을 소유하지 않는다.

### 그림 7-7. Framework와 업무 도메인의 관계

```text
┌────────────── Framework ──────────────┐
│ Filter / Context / TCF / Timeout      │
│ Transaction / Error / Logging         │
│                                      │
│       "어떻게 안전하게 실행할까?"   │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────── Business Domain ─────────┐
│ Handler / Facade / Service / DAO     │
│                                      │
│       "무슨 업무를 수행할까?"       │
└──────────────────────────────────────┘
```

업무 Service가 Framework 내부 DAO나 구현 클래스를 직접 가져다 쓰는 구조는 피한다.

# 7.6 업무·세부업무 축

현재 PDMG의 주 업무축은 다음이다.

```text
MG / CO / A
```

Java:

```text
nhnis.mg.co.a
```

Mapper:

```text
rdw.mg.co.a
```

Service Prefix:

```text
mgcoa
```

### 그림 7-8. 하나의 업무축이 여러 표현으로 투영된다

```text
업무분류
MG / CO / A
    │
    ├────────────┬─────────────┐
    ▼            ▼             ▼
Java           Mapper       Service Prefix
nhnis.mg.co.a  rdw.mg.co.a  mgcoa
```

---

# 7.7 업무축은 단순 폴더보다 더 큰 책임 경계다

같은 업무축이라는 말은 단순히 패키지 문자열이 같다는 뜻으로 끝나서는 안 된다.

### 그림 7-9. 업무축이 가져야 할 책임

```text
업무축
  │
  ├─ 프로그램 소유
  ├─ 데이터 소유
  ├─ 업무 규칙
  ├─ 운영 책임
  ├─ 장애 복구 책임
  ├─ 변경 승인
  └─ Service ID 범위
```

현재 PDMG가 이 모든 책임을 코드로 강제하는 것은 아니다.

따라서 아키텍처와 개발 방법론에서 보완해야 한다.

# 7.8 같은 업무축 안에도 여러 Program이 있다

현재 `co.a` 아래에는 서로 성격이 다른 여러 Program이 존재한다.

### 그림 7-10. 현재 `co.a` Program 예

```text
co.a
│
├─ mgcoa5530
│   └─ 마케팅희망고객
│
├─ mgcoa8888
│   └─ 이미지로그
│
├─ mgcoa9000
│   └─ 거래 파라미터
│
├─ mgcoa9001
│   └─ 거래통제
│
├─ mgcoa9100
│   └─ 런타임 진단
│
└─ mgcoa9999
    └─ 영업팁 실적
```

이 구조는 한 가지 중요한 사실을 보여준다.

> 같은 업무축 아래에 있다고 해서 모든 Program이 서로의 내부 구현을 자유롭게 사용해도 된다는 뜻은 아니다.

# 7.9 Program은 실행 구현의 응집 단위다

Program ID는 다음 클래스 가족을 묶는다.

### 그림 7-11. Program `mgcoa9000`

```text
mgcoa9000
│
├─ mgcoa9000Handler
├─ mgcoa9000Facade
├─ mgcoa9000Service
├─ mgcoa9000DAO
├─ mgcoa9000-ORA.xml
│
└─ Service IDs
    ├─ mgcoa9000S0
    ├─ mgcoa9000C0
    ├─ mgcoa9000U0
    └─ mgcoa9000D0
```

Program은 화면과 항상 1:1이 아니다.

---

# 7.10 Program과 화면은 서로 다른 경계다

### 그림 7-12. 하나의 화면이 여러 거래를 호출

```text
거래 파라미터 관리 화면
       │
       ├─ 조회 ──► mgcoa9000S0
       ├─ 등록 ──► mgcoa9000C0
       ├─ 수정 ──► mgcoa9000U0
       └─ 삭제 ──► mgcoa9000D0
```

반대도 가능하다.

### 그림 7-13. 하나의 거래를 여러 채널이 호출

```text
화면 A ───────┐
화면 B ───────┤
Postman ──────┼────► mgcoa5530S0
외부 Client ──┤
Test ─────────┘
```

따라서 Program 경계를 화면 메뉴 구조로만 정의하지 않는다.

---

# 7.11 Service ID는 호출 가능한 최소 거래 단위다

### 그림 7-14. Program과 Transaction

```text
Program
mgcoa9000
    │
    ├─ S0 ──► 조회 Use Case
    ├─ C0 ──► 등록 Use Case
    ├─ U0 ──► 수정 Use Case
    └─ D0 ──► 삭제 Use Case
```

Service ID는 다음을 연결한다.

### 그림 7-15. Service ID의 계약 범위

```text
mgcoa9000U0
    │
    ├─ HTTP Path
    ├─ Header rms_svc_c
    ├─ Handler Registry
    ├─ Facade Method
    ├─ Service Method
    ├─ DTO
    ├─ SQL ID
    ├─ Logging
    └─ 운영 정책
```

---

# 7.12 Service ID는 “DB Transaction 하나”와 같은 말이 아니다

기존 문서에서 거래와 DB TX를 너무 강하게 동일시하면 오류가 생긴다.

### 그림 7-16. Service ID와 DB TX의 관계

```text
Service ID
mgcoa9000U0
      │
      ▼
업무 Use Case
      │
      ├─ TCF ON + Timeout ON
      │     └─ Worker TransactionTemplate TX
      │
      ├─ TCF ON + Timeout OFF
      │     └─ Facade TX
      │
      └─ TCF OFF AS-IS
            └─ 동일 TX 보장 안 될 수 있음
```

정확한 표현은 다음이다.

> 하나의 Service ID 호출은 하나의 업무 유스케이스와 대응한다. DB Transaction 경계는 실행 모드와 Transaction 설정에 따라 달라진다.

---

# 7.13 도메인 소유권을 먼저 묻는다

호출 설계에서 가장 중요한 질문은 “어떤 클래스를 호출할까?”가 아니다.

### 그림 7-17. 호출 전에 묻는 질문

```text
필요한 기능
   │
   ▼
누가 이 업무 규칙을 소유하는가?
   │
   ▼
누가 이 데이터를 변경할 권한이 있는가?
   │
   ▼
누가 실패 시 복구 책임을 지는가?
   │
   ▼
그 경계를 통과하는 공개 계약은 무엇인가?
```

이 질문을 건너뛰고 가장 가까운 DAO를 주입하면 구조가 빠르게 무너진다.

---

# 7.14 데이터 소유권은 Table 접근권과 다르다

DB 계정이 테이블을 읽을 수 있다는 것과 업무가 그 데이터를 소유한다는 것은 다른 말이다.

### 그림 7-18. 기술 접근권 vs 업무 소유권

```text
DB 권한
SELECT 가능
    │
    └─ 기술적으로 접근 가능


업무 소유권
    │
    ├─ 생성 규칙
    ├─ 변경 규칙
    ├─ 삭제 규칙
    ├─ 정합성
    └─ 운영 책임
```

다른 도메인의 Table을 SQL로 읽을 수 있다고 해서 업무적으로 허용된 것은 아니다.

---

# 7.15 다른 Program의 DAO 직접 호출을 피해야 하는 이유

### 그림 7-19. DAO 직접 침범

```text
mgcoa9001Service
        │
        └────────────► mgcoa9000DAO
                            │
                            ▼
                       TX Parameter Table
```

이 구조는 매우 편해 보인다.

하지만 다음 경계를 우회한다.

### 그림 7-20. DAO 직접 호출이 우회하는 것

```text
정상 경로
Program B
Facade
  ↓
Service
  ├─ Validation
  ├─ Business Rule
  ├─ Permission
  ├─ State Check
  └─ DAO


Program A → B.DAO 직접
          │
          ├─ Validation 우회
          ├─ Business Rule 우회
          ├─ State Check 우회
          └─ Ownership 우회
```

따라서 원칙:

```text
다른 Program/도메인의 DAO
  = 내부 구현

다른 Program이 직접 사용하지 않음
```

# 7.16 Handler가 다른 Program의 Facade를 한곳에 몰아넣지 않는다

### 그림 7-21. Mega Handler Anti Pattern

```text
mgcoa9000Handler
   │
   ├─ 9000S0 → mgcoa9000Facade
   ├─ 8888S0 → mgcoa8888Facade
   ├─ 5530S0 → mgcoa5530Facade
   └─ 9999S0 → mgcoa9999Facade

          X
```

Handler는 자신이 소유한 Program Service ID 집합을 담당한다.

### 그림 7-22. Program Handler 원칙

```text
mgcoa9000Handler
   │
   ├─ mgcoa9000S0
   ├─ mgcoa9000C0
   ├─ mgcoa9000U0
   └─ mgcoa9000D0
```

# 7.17 같은 Program 내부 호출

같은 Program 안에서는 계층 경계를 따른다.

### 그림 7-23. 같은 Program 정상 호출

```text
mgcoa9000Handler
        ↓
mgcoa9000Facade
        ↓
mgcoa9000Service
        ↓
mgcoa9000DAO
        ↓
mgcoa9000-ORA.xml
```

각 단계의 책임:

```text
Handler
  → 거래 분기

Facade
  → DTO 변환 / Use Case 경계 / TX 선언

Service
  → 업무 절차

DAO
  → 데이터 접근

Mapper
  → SQL
```

# 7.18 같은 Program에서 거래끼리 호출할 때도 조심한다

예를 들어 U0 수정 거래가 내부에서 S0 메서드를 다시 호출하고 싶을 수 있다.

### 그림 7-24. 거래 메서드 상호 호출

```text
mgcoa9000U0()
      │
      └────► mgcoa9000S0()
```

이 호출이 항상 나쁜 것은 아니다.

하지만 다음을 확인한다.

```text
S0가 "재사용 가능한 내부 조회 로직"인가?
     │
     ├─ YES → 내부 Private/Public 업무 메서드 분리 검토
     │
     └─ NO
         │
         └─ 온라인 거래 전체 Use Case 재호출은 지양
```

온라인 진입 거래 메서드와 내부 재사용 메서드를 구분하면 책임이 명확해진다.

# 7.51 원격 쓰기 조합에는 분산 업무 설계가 필요하다

```text
    ▼

    │
    ▼
```

> **설계 방향**

### 그림 7-62. Compensation

```text
   │
   ▼

   │
   ▼
```


# 7.113 제7장에서 반드시 기억할 열여덟 가지

첫째, **현재 PDMG의 “도메인”은 DDD Domain Model이 아니라 업무코드·Program ID·Service ID를 기반으로 한 기술적 업무분류의 의미가 강하다.**

둘째, **현재 PDMG를 완성된 Aggregate/Entity 기반 DDD 구조라고 설명하면 안 된다.**

셋째, **업무축, Program, Service ID는 서로 다른 크기의 책임·실행 단위다.**

넷째, **Program은 화면과 반드시 1:1이 아니다.**

다섯째, **Service ID는 공개 실행 거래의 최소 식별자지만 DB Transaction 자체와 동일한 개념은 아니다.**

여섯째, **같은 Program 내부는 Handler → Facade → Service → 자기 DAO 방향을 따른다.**

일곱째, **다른 Program의 DAO/Mapper를 직접 호출하지 않는다.**

여덟째, **같은 모듈이라고 무조건 Self HTTP를 사용하지 않는다.**

아홉째, **같은 Transaction에서 공유해야 하는 업무 로직은 공통 Application Service, 내부 Port, 향후 Rule 등을 검토한다.**

열째, **Support에는 업무 규칙을 넣지 않는다.**

열한째, **다른 업무축은 공개 Application 계약으로 경계를 보호한다.**

열두째, **다른 WAR/WAS는 Client + Service ID/표준 전문으로 호출한다.**

열셋째, **원격 호출은 호출자의 Spring 로컬 Transaction을 공유하지 않는다.**

열넷째, **데이터 변경은 데이터 소유 도메인이 수행하는 것이 기본 원칙이다.**

열다섯째, **조회 조합은 Read Model, Query Contract, Orchestrator 같은 별도 설계를 검토할 수 있다.**

열여섯째, **TCF ON/OFF에 따라 진입점과 Transaction 경계가 달라진다.**

열일곱째, **GUID는 도메인 간 추적을 연결하지만 DB 원자성을 연결하지 않는다.**

열여덟째, **도메인 호출 설계의 핵심은 기술적으로 가능한 호출이 아니라 책임·데이터·트랜잭션·장애 경계를 보존하는 호출을 선택하는 것이다.**
