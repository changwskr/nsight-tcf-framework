# 제12장. TCF 온라인 거래 프레임워크 — ASCII 확장본 상세 목차

> **목차 작성 기준**
>
> 이 장은 `book.zip`의 제12장 원문, `16.TCF-OnlineTransactionController-1.md`, `17.TCF-TcfFace-Dispatcher-1.md`, `18.Business-Handler-1.md`, `20.타임아웃-1.md`, `20.Tranaactional-rdwTransactionManager-Begin-1.md`, `26.시스템후처리-1.md`를 중심으로 확장한다.
>
> 다음 사실을 고정한다.
>
> - 현재 TCF ON 실제 중심 호출선은 `OnlineTransactionController → TcfFacade → OnlineTimeoutExecutor → TransactionDispatcher → TransactionHandler → Business Facade`다.
> - `TransactionContext`는 `serviceId + ServiceContext 참조 + startedAtNanos`를 가진 TCF 실행 문맥이며 DB Transaction 객체가 아니다.
> - `TcfFacade.process()` 자체에는 `@Transactional`이 없고 현재 Timeout ON에서는 Worker `TransactionTemplate`이 최외곽 DB Transaction을 시작한다.
> - `TransactionDispatcher`는 모든 `TransactionHandler` Bean의 `serviceIds()`를 기동 시 Map으로 구성하며 중복 Service ID는 Startup Fail이다.
> - 현재 Handler는 4개이고 등록 Service ID는 8개다.
> - Handler는 프로그램 식별번호 단위로 여러 처리유형 Service ID를 묶고 Business Facade만 호출한다.
> - Registry 등록 Service ID는 trim/case/format 정규화를 하지 않으므로 기동 검증 보완이 필요하다.
> - 미등록 Service ID는 현재 `ServiceHandlerNotFound → HTTP 500 / E9999`로 처리되며 400/404 재분류가 개선 대상이다.
> - Timeout ON에서는 Handler 존재 확인도 Worker TransactionTemplate BEGIN 이후 수행되어 불필요한 TX 생성이 가능하다.
> - 과거/설계 다이어그램의 `STF → Dispatcher → ETF`는 현재 실행선이 아니다. 현행 `TcfFacade`는 STF/ETF를 주입하거나 호출하지 않는다.
> - 거래통제 STF 코드는 존재하지만 온라인 TCF 호출선 미연결이며 현재 시스템 후처리는 ResponseBodyAdvice와 Interceptor.afterCompletion이 실제 역할을 수행한다.
> - Timeout `cancel(true)`는 Worker 강제종료가 아니므로 JDBC/업무 인터럽트와 Statement Timeout을 함께 검증해야 한다.
> - TCF OFF 상세 구조는 다음 장에서 다루며 이 장에서는 조건부 Bean과 실행선 차이까지만 설명한다.
