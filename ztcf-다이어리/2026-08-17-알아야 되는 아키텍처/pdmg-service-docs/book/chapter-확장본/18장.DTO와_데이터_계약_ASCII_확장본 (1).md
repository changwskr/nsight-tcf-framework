# 제18장. DTO와 데이터 계약

> **AS-IS 핵심**
>
> - `hdr_nhnis`와 `dto`는 분리된 계약이다.
> - TCF ON은 `Map/Object → Facade convertValue → DTOin`, OFF는 typed MVC Binding이다.
> - 핵심 DTO 재분석 Snapshot은 **8개 거래 / 20 업무 DTO / 모두 DataObject 기반**이다.
> - `mgcoa9999`의 `*MsgJson` 3개는 특수 메시지 경로이며 일반 온라인 필수는 아니다.
> - Bean Validation은 현재 확인되지 않는다.
> - `guidList/txIdList` 일부 DTO는 `@JsonAlias`로 legacy/new 요청 이름을 함께 지원한다.
> - Response Advice의 `*List/*Array` suffix 제거는 legitimate 업무 출력필드까지 삭제할 수 있다.
> - 성공/업무결과는 `dto`, Exception은 `result`; Filter `sendError()`는 별도 예외 경로다.
> - `NH_NIS_ERR_DTO`의 Stack/Class/File/Line 외부노출은 보안 개선대상이다.


---

## 이 장을 시작하며

```text
HTTP JSON
   ↓
표준 전문 { hdr_nhnis, dto }
   ├─ Header → ServiceContext
   └─ dto    → DTOin
                  ↓
            Business Service
             ↓         ↓
          DAO Map    Rule/Command(필요시)
             ↓
          DB Row Map
             ↓
          DTOSub/DTOout
             ↓
        ResponseBodyAdvice
             ↓
 { hdr_nhnis, dto } 또는 { hdr_nhnis, result }
```

이 장에서 DTO는 단순 값 객체가 아니라 **외부 계약, 신뢰경계, 호환성, 직렬화 결과를 함께 관리하는 아키텍처 요소**다.

# 18.1 DTO를 데이터 계약으로 보는 이유

DTO는 단순 Java Bean이 아니라 Service ID별 요청·응답의 이름, 타입, 반복구조와 외부 호환성을 고정하는 계약이다.

전문·Header·DTO·Persistence 계약을 분리하는 기준을 고정한다.


### 그림 18-1. DTO를 데이터 계약으로 보는 이유 — 구조

```text
HTTP {hdr_nhnis,dto}
      ↓
Header → ServiceContext
dto    → DTOin → Service → DTOout/Sub
      ↓
Response Advice → {hdr_nhnis,dto/result}
```


### 그림 18-2. DTO를 데이터 계약으로 보는 이유 — 실행·검증 관점

```text
Header = Framework trust
DTO    = Business wire
DAO Map= Persistence
Context= Runtime thread scope
Domain = Optional internal model
```


**아키텍처 판단**


이 데이터가 어느 경계의 계약인지, Source of Truth가 누구인지, 최종 Wire에서 어떤 이름과 타입으로 보이는지를 기준으로 책임을 배치한다.

Response Advice 이후 최종 JSON을 성공/오류 계약의 근거로 삼는다.

업무 `RSLT_CD` 실패는 정상 DTOout return이므로 `result`가 아니라 `dto`에 남을 수 있다. 반대로 Biz/Framework Exception은 `NH_NIS_ERR_DTO`로 변환되어 `result`를 사용한다.


### 그림 18-333. 업무 RSLT 실패는 dto — 구조

```text
Success DTOout
→ Advice
→ {hdr_nhnis,dto}

Exception
→ NH_NIS_ERR_DTO
→ {hdr_nhnis,result}
```


### 그림 18-334. 업무 RSLT 실패는 dto — 실행·검증 관점

```text
Filter sendError
→ Advice 이전 종료 가능
→ 표준 Envelope 예외

Error Stack/Class/File
→ 외부 최소화
```


**아키텍처 판단**


최종 HTTP JSON과 운영 보안·호환성 영향이 직접 발생하는 영역이므로 단위 Source 판단만으로 완료하지 않고 실제 Wire Contract Test를 필수로 둔다.
