# 제8장. HTTP 요청과 표준 전문

> **집필 기준**
>
> 이 장은 `book.zip`의 제8장 원문과 `10.전문`, `11.Http CORS적용`, `12.http요청`, `27.전문 DTO` 및 각 재분석본, `54.http호출 다이어그램`을 기준으로 다시 확장한다.
> 제6장 ASCII 확장본과 동일하게 **현재 구현(AS-IS), 프로젝트 표준(STANDARD), 개선 방향(TO-BE), 설계 예시**를 분리한다.
>
> 다음 사항을 사실 기준으로 유지한다.
>
> - PDMG 온라인 요청은 HTTP POST와 JSON 전문을 결합해 전달한다.
> - HTTP Header와 JSON의 `hdr_nhnis`는 이름만 비슷할 뿐 서로 다른 계층의 계약이다.
> - 요청 전문의 기본 구조는 `hdr_nhnis.sys_comm + dto`다.
> - `rms_svc_c`는 Service ID, `std_gbl_id`는 GUID 추적 식별자다.
> - 현재 TCF ON에서는 `OnlineTransactionController`가 공통 진입점이며 `dto`만 분리해 `TcfFacade`로 넘긴다.
> - Service ID 결정은 현재 구현상 `ServiceContext.header.sys_comm.rms_svc_c → 요청 JSON의 rms_svc_c → URL path` 순으로 해석된다.
> - local Profile에서는 `DefaultFilter`가 누락 Header를 합성할 수 있으나, 이는 개발 편의 기능이지 운영 전문 표준을 완화한다는 뜻이 아니다.
> - 성공 응답은 `hdr_nhnis + dto`, Controller/TCF 이후 표준 오류 응답은 `hdr_nhnis + result(NH_NIS_ERR_DTO)` 구조다.
> - Filter에서 `sendError()`로 조기 종료되는 400/401은 동일한 표준 오류 봉투가 보장되지 않는다.
> - 현재 샘플 UI의 주 경로는 `pdmg-ui:8090` 브라우저에서 `pdmg-service:8080`으로 직접 `fetch`하는 구조이며 CORS가 필요하다. Relay는 남아 있는 대안 경로다.
> - 현재 local UI Client는 `Content-Type`, `Accept` 중심으로 호출하고, non-local 환경에서는 `DefaultFilter` JWT 계약을 만족하도록 Authorization 전달을 별도로 보완해야 한다.
> - Client Timeout과 서버 TCF Timeout은 서로 다르며, 현재 문서 기준 기본값은 UI 10초, 서버 5초다.
> - `X-Forwarded-For`와 클라이언트가 채운 사용자·IP·Service ID는 신뢰 경계를 고려해야 한다.
>
> 이 장의 목표는 JSON 필드 목록을 외우는 것이 아니다. **한 HTTP 요청이 브라우저에서 만들어져 Filter·Interceptor·Spring MVC·TCF·업무 DTO로 변환되고, 성공 또는 오류 전문으로 다시 조립되는 전체 메시지 생명주기**를 이해하는 것이다.

## 이 장을 시작하며

사용자가 화면에서 조회 버튼을 누르면 브라우저는 단순히 “조회”라는 의도를 보내는 것이 아니다. 서버가 거래를 실행하려면 적어도 다음 정보가 서로 다른 위치에 담겨야 한다.

```text
어디로 보낼 것인가?        → URL
어떤 형식인가?             → Content-Type
누가 요청했는가?           → Authorization / 인증 문맥
어떤 거래인가?             → Service ID
이번 요청 한 건은 무엇인가? → GUID
업무 입력은 무엇인가?       → dto
```

PDMG는 이 정보를 HTTP와 표준 JSON 전문에 나누어 담는다.

```text
HTTP Request
   = Transport
   + Authentication
   + Transaction Identity
   + Trace Identity
   + Common Context
   + Business Contract
```

이 장은 제7장까지 정의한 Service ID와 업무 경계를 실제 네트워크 요청으로 연결하는 장이며, 제9장의 `DefaultFilter`와 Spring MVC가 읽게 될 입력 계약을 확정하는 장이다.

# 8.1 HTTP 요청은 PDMG 거래의 외부 경계다

HTTP는 PDMG 업무가 외부 채널과 만나는 첫 번째 실행 경계다. 이 경계에서는 네트워크 연결, URL, Method, Header, Body가 결정되지만 DB Transaction은 아직 별개의 문제다. TCF ON+Timeout ON의 DB Transaction은 뒤에서 Worker Thread의 TransactionTemplate이 시작한다.

이 단계에서 가장 중요한 것은 **전송 정보와 업무 정보를 한 객체로 뭉개지 않는 것**이다. 어느 값이 어느 계층의 책임인지 먼저 정하면 이후 Filter·TCF·업무 코드의 역할도 자연스럽게 정리된다.

### 그림 8-1. Browser에서 업무 실행까지의 HTTP 경계

```text
Browser / pdmg-ui
      │ HTTP POST
      ▼
pdmg-service
      │
      ├─ Filter / Interceptor
      ├─ Spring MVC
      ├─ TCF
      └─ Business → DB
```

### 그림 8-2. HTTP 경계와 DB Transaction 경계의 차이

```text
HTTP Request Boundary
Browser ───────────────→ Controller

DB Transaction Boundary
Worker Thread : TX BEGIN → Business → DB → COMMIT/ROLLBACK

HTTP 연결 ≠ DB Transaction
```

# 8.2 HTTP 요청 한 건을 구성하는 여섯 가지 정보

한 요청을 하나의 JSON으로만 보면 책임 경계가 흐려진다. 전송, 인증, 거래 식별, 추적, 공통 문맥, 업무 계약을 분리해 보면 장애 지점을 훨씬 빠르게 좁힐 수 있다.

이 단계에서 가장 중요한 것은 **전송 정보와 업무 정보를 한 객체로 뭉개지 않는 것**이다. 어느 값이 어느 계층의 책임인지 먼저 정하면 이후 Filter·TCF·업무 코드의 역할도 자연스럽게 정리된다.

### 그림 8-3. Transport·Authentication·Transaction·Trace·Context·Business Contract

```text
HTTP Request
├─ Transport       URL / Method
├─ Authentication  Authorization
├─ Transaction     Service ID
├─ Trace           GUID
├─ Context         hdr_nhnis.sys_comm
└─ Business        dto
```

### 그림 8-4. HTTP Request의 계층별 정보 분해

```text
[HTTP Line]   POST /mgcoa9000S0
[HTTP Header] Content-Type / Authorization / Origin
[JSON Header] hdr_nhnis.sys_comm
[JSON Body]   dto
[Runtime]     ServiceContext + DTOin
```

# 8.5 현재 TCF ON에서 지원하는 HTTP URL 형태

현재 TCF ON 공통 Controller는 `/{serviceId}`, `/online`, `/{businessCode}/online` 세 POST Mapping을 제공한다. 세 URL 모두 결국 같은 `handle(...)` 흐름으로 수렴하지만 Service ID 확보 조건은 다르다.

| URL | 실제 Service ID 확보 관점 | 주의사항 |
|---|---|---|
| `POST /{serviceId}` | Header 우선, path fallback | URL/Header 불일치 검증 필요 |

| `POST /{businessCode}/online` | Header 사실상 필수 | businessCode가 거래 검증 키로 쓰이지 않음 |

이 단계에서 가장 중요한 것은 **전송 정보와 업무 정보를 한 객체로 뭉개지 않는 것**이다. 어느 값이 어느 계층의 책임인지 먼저 정하면 이후 Filter·TCF·업무 코드의 역할도 자연스럽게 정리된다.

### 그림 8-9. `/online`, `/{businessCode}/online`, `/{serviceId}` 진입 구조

```text

/online ───────────┼─→ OnlineTransactionController.handle()
/{businessCode}/online ─┘
                         ↓
                    TcfFacade
```

### 그림 8-10. 세 URL이 공통 Controller로 수렴하는 구조


# 8.11 왜 공통 Header와 업무 Body를 분리하는가

이 단계에서 가장 중요한 것은 **전송 정보와 업무 정보를 한 객체로 뭉개지 않는 것**이다. 어느 값이 어느 계층의 책임인지 먼저 정하면 이후 Filter·TCF·업무 코드의 역할도 자연스럽게 정리된다.

# 8.12 `hdr_nhnis`는 시스템 공통 전문의 Root다

`hdr_nhnis`는 `pdmg-fw`가 소유하는 공통 Header 루트다. 업무 계층은 이 객체를 파라미터로 전달받기보다 `ServiceContext`를 통해 읽는다.

### 그림 8-51. Unknown Property Ignore

```text

```

# 8.76 Client Timeout과 서버 Timeout은 서로 다르다

UI Timeout 10초와 서버 TCF Timeout 5초는 서로 다른 시계다. 현재 기본은 서버가 먼저 504를 반환하고 UI가 그 응답을 받을 수 있는 순서다.

```text
Server Timeout : 5s
        ↓ 504
UI Timeout     : 10s

현재 기본 순서
서버가 먼저 Timeout 결과를 만들고
UI가 그 결과를 받을 수 있도록 구성
```

운영에서는 HTTP 상태, 응답 Body, CORS Header, 인증 로그를 동시에 확인한다. 하나의 증상만 보고 원인을 단정하면 실제 실패 경계를 놓치기 쉽다.

> **아키텍처 판단: 외부 Client Timeout은 내부 Transaction Timeout보다 길게 잡아 서버의 표준 오류를 수신할 여지를 둔다.**

### 그림 8-151. Browser/HTTP Client Timeout

```text
UI wait 10s
   │
   ├─────────────┐
   │ Server TCF 5s
   │     ↓ 504
   └─ UI receives response before own timeout
```

### 그림 8-152. TCF Worker Transaction Timeout

```text
UI wait 10s
   │
   ├─────────────┐
   │ Server TCF 5s
   │     ↓ 504
   └─ UI receives response before own timeout
```

정리하면 다음과 같다.

```text
Server 5s < UI 10s
→ 서버 표준 Timeout 응답을 UI가 받을 수 있는 기본 순서
```

이 장에서 기억할 것은 필드명보다 경계다. 전송과 업무, HTTP Header와 전문 Header, Service ID와 GUID, 성공과 오류, CORS와 인증, Client Timeout과 서버 Timeout을 구분하는 것이 핵심이다.

이 규칙은 문서에만 남기지 않고 Contract Test·설정 검증·CI Gate로 자동화할 수 있어야 한다. 사람이 기억해야만 지켜지는 전문 규칙은 프로젝트가 커질수록 쉽게 무너진다.

# 8.107 다음 장으로 — Filter와 Spring MVC

다음 장은 이 표준 HTTP 요청을 가장 먼저 읽는 `DefaultFilter`와 Spring MVC를 확대한다. 제8장이 '무엇이 들어오는가'를 정의했다면 제9장은 '누가 어떻게 읽는가'를 설명한다.

이 규칙은 문서에만 남기지 않고 Contract Test·설정 검증·CI Gate로 자동화할 수 있어야 한다. 사람이 기억해야만 지켜지는 전문 규칙은 프로젝트가 커질수록 쉽게 무너진다.
