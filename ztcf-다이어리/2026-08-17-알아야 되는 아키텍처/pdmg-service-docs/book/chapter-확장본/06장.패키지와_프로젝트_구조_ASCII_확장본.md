# 제6장. 패키지와 프로젝트 구조

> **집필 기준**
>
> 이 장은 현재 `pdmg-service`, `pdmg-fw`, `pdmg-ui`, `pdmg-jwt`의 패키지 자료와 PDMG 네이밍 정본을 기준으로 작성한다.
> 특히 `pdmg-service`의 현재 AS-IS 업무 패키지는 `nhnis.mg.co.a.*` 단일 축이다.
>
> 다음 사항을 사실 기준으로 유지한다.
>
> - `nhnis.mg` 바로 아래에는 Boot 진입 클래스만 둔다.
> - 업무 코드는 `nhnis.mg.[업무].[세부].*` 아래에 둔다.
> - 현재 업무축은 `nhnis.mg.co.a.*`다.
> - 현재 Handler는 `entry.handler`, Aspect는 `entry.aspect`에 있다.
> - 현재 Controller / Facade / Service는 `application.*`에 있다.
> - DTO는 `dto`, DAO는 `persistence.dao`에 있다.
> - `application.rule`은 저장소 권장 구조에는 존재하지만 현재 PDMG AS-IS의 일반 실행 패키지로 확인되지 않는다.
> - `persistence.file`은 현재 실제 Java 구현 패키지로 보지 않는다.
> - `client`는 현재 구현이 제한적이며, 실구현이 확인되지 않은 Client를 AS-IS 실행 흐름에 넣지 않는다.
> - `support`에는 현재 제한적인 실제 Support 구현이 존재한다.
> - 실제 Mapper XML 로딩 패턴은 `classpath*:rdw.*/*.xml`이다.
> - 현재 `@MapperScan`의 주 대상은 `nhnis.mg.co.a.persistence.dao`다.
> - 업무 선후처리 Pointcut은 `nhnis.mg.co.a.application.service..*`를 기준으로 한다.
> - 과거 축 없는 `nhnis.mg.application.*`, `nhnis.mg.entry.*` 구조는 현재 소스에서 제거되었다.
>
> 따라서 이 장에서는 **현재 패키지 위치**, **Spring/MyBatis/AOP가 그 패키지를 어떻게 해석하는지**, 그리고 **새 업무축을 추가할 때 같이 변경해야 하는 실행 계약**을 하나의 구조로 설명한다.

# 6.1 패키지는 파일을 정리하는 폴더가 아니다

제5장에서는 `mgcoa9000S0`이라는 Service ID에서 다음 이름이 파생된다는 사실을 보았다.

```text
mgcoa9000Handler
mgcoa9000Facade
mgcoa9000Service
mgcoa9000DAO
mgcoa9000S0DTOin
mgcoa9000-ORA.xml
```

이제 남은 질문은 단순하다.

> **이 파일들을 프로젝트의 어디에 두어야 하는가?**

Spring은 클래스에 `@Service`가 붙어 있기만 하면 어디에 있어도 찾아줄 것처럼 보인다.  
MyBatis 역시 DAO 인터페이스와 XML만 존재하면 알아서 연결될 것처럼 보인다.

실제 PDMG에서는 그렇지 않다.

패키지 경로는 다음과 같은 실행 규칙의 입력값이 된다.

### 그림 6-1. 패키지가 영향을 주는 실행 규칙

```text
Java Package
     │
     ├─ Spring Component Scan
     ├─ ConfigurationProperties Scan
     ├─ MyBatis @MapperScan
     ├─ Mapper XML namespace
     ├─ AOP Pointcut
     ├─ Log Category
     ├─ Test Package
     └─ Architecture Rule
```

따라서 파일을 다른 폴더로 옮기는 일은 단순한 정리가 아니다.

### 그림 6-2. 잘못된 Package Move의 결과

```text
Class Move
   │
   ├─ Compile 성공
   │
   ├─ Spring Bean 누락 가능
   │
   ├─ AOP Pointcut 누락 가능
   │
   ├─ Mapper Proxy 누락 가능
   │
   ├─ XML namespace 불일치 가능
   │
   └─ 운영 로그 구간 누락 가능
```

이 장의 핵심은 다음 한 문장이다.

> **PDMG의 패키지는 소스 위치이면서 동시에 Runtime 선택 규칙이다.**

# 6.2 프로젝트 전체에서 먼저 모듈 경계를 본다

PDMG는 하나의 `src/main/java` 아래에 모든 코드를 넣는 구조가 아니다.

### 그림 6-3. PDMG 주요 모듈

```text
nsight-tcf-framework
│
├─ pdmg-ui
│   └─ 화면 / Browser Client
│
├─ pdmg-service
│   └─ 마케팅 업무 애플리케이션
│
├─ pdmg-fw
│   └─ 공통 Web / TCF / Context / Timeout / Exception
│
└─ pdmg-jwt
    └─ 인증 / JWT 발급 / Token 관리
```

각 모듈은 서로 다른 변경 이유를 가진다.

### 그림 6-4. 모듈별 변경 이유

```text
pdmg-ui
  └─ 화면/UX/브라우저 호출 변화

pdmg-service
  └─ 업무 Program/SQL/DTO 변화

pdmg-fw
  └─ 공통 거래 실행 정책 변화

pdmg-jwt
  └─ 인증/키/토큰 정책 변화
```

같은 기능이 필요하다고 해서 공통 FW 코드를 업무 모듈로 복사하지 않는다.

---

# 6.3 모듈 경계와 프로세스 경계는 같은 말이 아니다

`pdmg-fw`는 별도 모듈이지만 `pdmg-service`가 HTTP로 원격 호출하는 외부 서버라고 이해하면 안 된다.

### 그림 6-5. Build Module과 Runtime 관계

```text
[Build 관점]

pdmg-service
     │
     └─ dependency
          │
          ▼
       pdmg-fw


[Runtime 관점]

┌──────────────── Spring ApplicationContext ────────────────┐
│                                                           │
│ pdmg-fw Bean             pdmg-service Bean                │
│                                                           │
│ DefaultFilter            mgcoa9000Handler                 │
│ TcfFacade                mgcoa9000Facade                  │
│ Dispatcher               mgcoa9000Service                 │
│ TimeoutExecutor          mgcoa9000DAO                     │
└───────────────────────────────────────────────────────────┘
```

즉:

```text
Module Boundary
    ≠
Process Boundary
    ≠
Spring Context Boundary
```

이 차이를 이해해야 패키지와 의존 구조를 정확히 읽을 수 있다.

# 6.4 PDMG Service의 Java Root

현재 `pdmg-service`의 Java Root는 `nhnis.mg`다.

그러나 `nhnis.mg` 바로 아래에 업무 Service나 DAO를 두지 않는다.

### 그림 6-6. `nhnis.mg` Root의 역할

```text
nhnis.mg
│
├─ PdmgApplication
├─ ServletInitializer
│
└─ co
   └─ a
      └─ 실제 업무 코드
```

현재 원칙:

```text
nhnis.mg
  = Boot / Application Root

nhnis.mg.co.a
  = 업무 Root
```

# 6.5 현재 과거의 축 없는 업무 패키지는 제거되었다

과거 분석 시점에는 다음과 같은 구조가 함께 존재한 적이 있었다.

### 그림 6-7. 과거 구조 — 현재 제거됨

```text
nhnis.mg
├─ application
│  ├─ dto
│  └─ service
├─ entry
│  ├─ controller
│  ├─ facade
│  ├─ handler
│  └─ aspect
├─ persistence
│  └─ dao
├─ config
├─ client
└─ support
```

현재는 이 축 없는 업무 구조를 AS-IS로 보지 않는다.

### 그림 6-8. 현재 구조

```text
nhnis.mg
├─ PdmgApplication
├─ ServletInitializer
│
└─ co
   └─ a
      ├─ entry
      ├─ application
      ├─ dto
      ├─ persistence
      ├─ config
      ├─ client
      └─ support
```

즉 다음 위험은 **과거 문제**다.

```text
nhnis.mg.application.service.mgcoaXXXXService
        +
nhnis.mg.co.a.application.service.mgcoaXXXXService
        │
        ▼
동일 Bean Name 충돌
```

현재 소스에서는 구 패키지가 제거되어 이 중복을 현재 문제로 다시 기술하지 않는다.

# 6.6 패키지는 업무축을 먼저 가진다

패키지 기본 형식:

```text
nhnis.mg.[업무코드].[세부업무코드].[책임]
```

### 그림 6-9. Package Segment 해부

```text
nhnis.mg.co.a.application.service
│     │  │ │      │         │
│     │  │ │      │         └─ Component
│     │  │ │      └─────────── Layer
│     │  │ └────────────────── 세부업무 A
│     │  └──────────────────── 업무 CO
│     └─────────────────────── 대그룹 MG
└───────────────────────────── 프로젝트 Root
```

패키지 이름 하나에서 두 가지 정보를 동시에 읽는다.

```text
co.a
  → 어느 업무인가?

application.service
  → 어떤 책임인가?
```

```text
│ └── co
```

```text
                X
```

`application.rule`은 저장소의 향후 구조 자료에서 권장할 수 있지만 현재 PDMG 일반 AS-IS 패키지로 넣지 않는다.

# 6.10 `entry.handler` — TCF 업무 진입점

TCF ON에서 업무 쪽 첫 컴포넌트는 Handler다.

### 그림 6-14. Handler Package

```text
nhnis.mg.co.a
└─ entry
   └─ handler
      ├─ mgcoa5530Handler
      ├─ mgcoa8888Handler
      ├─ mgcoa9000Handler
      └─ ...
```

Handler의 책임:

```text
Service ID 등록
       ↓
Service ID 분기
       ↓
Facade 호출
```

### 그림 6-15. Handler가 의존하는 방향

```text
entry.handler
      │
      ▼
application.facade

O
```

금지:

```text
entry.handler ─────► application.service
entry.handler ─────► persistence.dao

X
```

Facade를 건너뛰면 유스케이스와 Transaction 계약을 우회할 수 있다.

# 6.11 `entry.aspect` — 횡단 관심사의 위치

현재 업무 Aspect는 `entry.aspect`에 있다.

### 그림 6-16. Aspect Package

```text
nhnis.mg.co.a.entry.aspect
│
├─ BizPrePostAspect
└─ PdmgBizTxFlowAspect
```

Aspect는 그 패키지 아래의 클래스만 호출하는 일반 계층이 아니다.

### 그림 6-17. Aspect의 물리 위치와 적용 대상

```text
Aspect 위치
entry.aspect
      │
      │ Pointcut
      ├────────────► application.service
      │
      └────────────► handler / facade / controller / dao
                     (Aspect별 대상 다름)
```

즉:

```text
Aspect가 어디에 있는가?
        ≠
Aspect가 어디에 적용되는가?
```

# 6.15 `application.rule` — 현재 일반 AS-IS가 아니다

향후 업무 규칙 분리를 위해 `application.rule` 구조를 도입할 수 있다.

> **TO-BE**

### 그림 6-24. Rule 도입 방향

```text
application.service
       │
       ├─► application.rule
       │      ├─ 검증
       │      ├─ 정책
       │      └─ 계산
       │
       └─► persistence.dao
```

하지만 현재 PDMG를 설명하는 그림에서 다음처럼 `Rule`을 실제 실행 필수 단계로 넣지 않는다.

```text
Handler
  ↓
Facade
  ↓
Service
  ↓
Rule
  ↓
DAO

X 현재 일반 AS-IS 단정
```

# 6.16 `dto` — 계층 공통 데이터 계약

DTO는 `application.dto`가 아니라 업무 Root 바로 아래 `dto`에 둔다.

### 그림 6-25. DTO Package

```text
nhnis.mg.co.a
├─ application
│  ├─ facade
│  └─ service
│
└─ dto
   ├─ mgcoa9000S0DTOin
   ├─ mgcoa9000S0DTOout
   └─ mgcoa9000S0DTOSub0
```

DTO가 별도 Root인 이유는 여러 컴포넌트가 데이터 계약을 공유하기 때문이다.

### 그림 6-26. DTO 사용 범위

```text
        DTO
       / | \
      /  |  \
     ▼   ▼   ▼
Facade Service DAO
```

DTO는 실행 계층이 아니라 계약이다.

# 6.18 `persistence.file`은 현재 구현처럼 설명하지 않는다

패키지 설계 자료에는 파일 영속 확장 위치로 `persistence.file`이 등장할 수 있다.

### 그림 6-29. Persistence AS-IS와 확장 후보

```text
persistence
│
├─ dao

└─ file
    └─ TO-BE / 확장 후보
```

# 6.71 Package와 Transaction Boundary는 같지 않다

TCF ON + Timeout ON에서는 `nhnis.fw.tcf.core.dispatch`의 Dispatcher도 Worker DB Transaction 내부에 실행된다.

### 그림 6-88. Package와 TX Boundary

```text
Request Thread

nhnis.fw.commons.*
nhnis.fw.tcf.web
nhnis.fw.tcf.core.facade
       │
       │ TX 밖
───────┼────────────────────────────────

Worker Thread / TX 안

nhnis.fw.tcf.core.dispatch
       ↓
nhnis.mg.co.a.entry.handler
       ↓
nhnis.mg.co.a.application.facade
       ↓
nhnis.mg.co.a.application.service
       ↓
nhnis.mg.co.a.persistence.dao
```

즉:

```text
Framework Package
   ≠
항상 TX 밖

Business Package
   ≠
항상 TX 시작점
```

Package는 책임을 말하고, Transaction은 실행 경계를 말한다.

# 6.85 제6장에서 기억해야 할 열여섯 가지

첫째, **PDMG 패키지는 업무축과 책임 계층을 동시에 표현한다.**

둘째, **현재 `pdmg-service`의 업무 Root는 `nhnis.mg.co.a.*`다.**

셋째, **`nhnis.mg` 바로 아래에는 Boot 진입 클래스만 둔다.**

넷째, **과거 축 없는 `nhnis.mg.application.*`, `nhnis.mg.entry.*` 업무 패키지는 현재 제거되었다.**

다섯째, **Handler는 `entry.handler`, Aspect는 `entry.aspect`다.**

여섯째, **Controller / Facade / Service는 현재 `application.*`에 있다.**

일곱째, **Rule과 `persistence.file`을 현재 일반 실행 구현처럼 설명하지 않는다.**

여덟째, **DTO는 업무 Root의 `dto`, DAO는 `persistence.dao`다.**

아홉째, **Java 업무축과 Mapper `rdw.mg.[업무].[세부]` 축은 맞아야 한다.**

열째, **현재 Mapper XML 로딩 패턴은 `classpath*:rdw.*/*.xml`이다.**

열한째, **Component Scan과 Mapper Scan은 서로 다른 메커니즘이다.**

열두째, **Package 기반 AOP는 패키지 이동 시 조용히 빠질 수 있다.**

열셋째, **새 업무축은 Java 디렉터리만 추가해서는 안 되고 MapperScan·Pointcut·Config·Test까지 함께 확장해야 한다.**

열넷째, **공통 FW 코드는 `pdmg-fw`가 소유하며 업무축에 복제하지 않는다.**

열다섯째, **Package Boundary와 Thread/Transaction Boundary는 같은 개념이 아니다.**

열여섯째, **패키지 리팩터링은 Source Move가 아니라 Runtime Contract Migration으로 관리해야 한다.**

# 6.86 다음 장으로

이 장에서는 프로그램 파일이 어디에 위치해야 하는지와 그 위치가 Runtime에 어떤 의미를 가지는지 살펴보았다.

하지만 다음 문제가 남는다.

```text
nhnis.mg.co.a
        │
        └─ 공통관리 업무


nhnis.mg.ic.b
        │
        └─ 통합고객 업무
```

두 업무축이 존재할 때 다음 질문이 생긴다.

```text
co.a Service가 ic.b DAO를 직접 호출해도 되는가?

업무 A가 업무 B의 DTO를 그대로 가져다 써도 되는가?

다른 업무가 필요하면 Facade를 호출해야 하는가,
Service를 호출해야 하는가,
Client를 통해야 하는가?

공통 데이터와 도메인 소유권은 어떻게 구분하는가?
```

### 그림 6-102. 제7장으로 이어지는 질문

```text
제6장
"파일은 어디에 두는가?"

nhnis.mg.co.a
nhnis.mg.ic.b
      │
      │ 이제 업무축 사이 관계를 본다
      ▼

제7장
"서로 다른 업무는 어떻게 호출하는가?"

Domain / Ownership
      │
      ├─ 허용 호출
      ├─ 금지 호출
      ├─ DTO 계약
      ├─ Client
      └─ 의존 방향
```

다음 장에서는 PDMG에서 말하는 도메인이 무엇인지부터 다시 정의하고, 업무축 사이의 호출 경계를 다룬다.
