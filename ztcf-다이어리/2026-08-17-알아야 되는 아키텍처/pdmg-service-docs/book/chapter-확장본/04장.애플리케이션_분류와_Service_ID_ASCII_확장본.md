# 제4장. 애플리케이션 분류와 Service ID

> **집필 기준**
>
> 이 장은 다음 자료를 우선 기준으로 재구성하였다.
>
> - `00.NSIGHT 애플리케이션 코드 분류표`
> - `MG-NAMING_CONVENTION`
> - `09.서비스ID`
> - `09.서비스ID-1`
> - `61.Service ID 아키텍처 다이어그램`
> - `62.화면번호-Service ID-Controller-Service 관계 다이어그램`
> - 현재 제4장 원고의 소스 재검증 결과
>
> 현재 구현 사실과 표준 규칙을 구분한다.
>
> - **현재 구현:** 실제 Handler Registry, Controller의 Service ID 결정 우선순위, 현재 패키지와 거래 등록
> - **표준:** 11자리 Service ID, 분류표 코드, S/C/U/D/A/R, 네이밍 연결 규칙
> - **TO-BE:** URL/Header 일치 검증, 중앙 거래 카탈로그, Service ID별 Timeout 정책 등
>
> `A`, `R`은 표준에서 허용하지만 현재 모든 업무에서 실제 등록되어 있다고 단정하지 않는다.
> 또한 과거 분석 문서에 기록된 Handler/Service ID 개수는 시점 차이가 있으므로 현재 확인된 소스 기준과 구분한다.

---

# 4.1 PDMG에서는 “이름”이 실행 구조를 연결한다

제3장에서는 PDMG 코드를 책임과 레이어의 관점에서 보았다.

```text
Handler
  ↓
Facade
  ↓
Service
  ↓
DAO
  ↓
Mapper
```

그러나 프로그램이 수백 개로 늘어나면 새로운 문제가 생긴다.

```text
어떤 Handler가 어느 업무인가?

어떤 Facade가 어느 프로그램인가?

이 요청이 조회인지 수정인지 어떻게 식별하는가?

화면에 표시된 프로그램과 서버 거래는 어떤 관계인가?

운영 로그의 ID 하나로 소스와 SQL까지 찾을 수 있는가?
```

PDMG는 이 문제를 **애플리케이션 분류체계 + Program ID + Service ID**로 해결한다.

### 그림 4-1. PDMG 식별체계의 전체 계층

```text
대그룹
 MG
  │
  ▼
업무코드
 CO
  │
  ▼
세부업무
 A
  │
  ▼
프로그램 식별번호
 9000
  │
  ▼
Program ID
 mgcoa9000
  │
  ├─ 조회  S0 ──> mgcoa9000S0
  ├─ 등록  C0 ──> mgcoa9000C0
  ├─ 수정  U0 ──> mgcoa9000U0
  └─ 삭제  D0 ──> mgcoa9000D0
```

이 구조에서 가장 중요한 개념은 다음 두 문장이다.

> **Program ID는 프로그램 영역을 식별한다.**

> **Service ID는 실행 가능한 개별 거래를 식별한다.**

---

# 4.2 식별체계는 단순한 이름 규칙이 아니다

Service ID가 잘못되면 파일 이름만 어색해지는 것이 아니다.

### 그림 4-2. Service ID가 연결하는 영역

```text
                       Service ID
                    mgcoa9000U0
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
      HTTP 요청        Handler Registry   운영 로그
          │               │                │
          ▼               ▼                ▼
   전문 rms_svc_c       Handler          거래통제
          │               │                │
          ▼               ▼                ▼
       Facade           Service         Timeout/통계
          │               │
          └───────┬───────┘
                  ▼
               DAO/SQL
```

따라서 식별체계를 잘못 잡으면 다음 문제가 동시에 발생할 수 있다.

```text
잘못된 분류
   ↓
잘못된 Program ID
   ↓
잘못된 Service ID
   ↓
┌───────────────────────────────┐
│ Handler 라우팅 불일치         │
│ UI 요청 불일치                │
│ 거래통제 정책 누락            │
│ 로그 검색 어려움              │
│ SQL 추적 어려움               │
│ 운영 통계 왜곡                │
└───────────────────────────────┘
```

---

# 4.3 애플리케이션 코드 분류표가 최상위 기준이다

PDMG의 ID를 개발자가 임의로 조합해서는 안 된다.

분류 의미의 상위 기준은 `00.NSIGHT 애플리케이션 코드 분류표`다.

### 그림 4-3. 분류표에서 Service ID까지 내려가는 흐름

```text
애플리케이션 코드 분류표
          │
          ▼
대그룹 MG
          │
          ▼
업무코드 CO
          │
          ▼
세부기능 A
          │
          ▼
프로그램 번호 9000
          │
          ▼
Program ID mgcoa9000
          │
          ▼
거래구분 + 순번
          │
          ▼
Service ID mgcoa9000S0
```

즉 분류표와 Service ID는 별개의 문서가 아니다.

```text
분류표
  = 의미의 기준

Naming Convention
  = 그 의미를 코드/패키지/ID에 투영하는 규칙
```

# 4.4 대그룹 MG

PDMG에서 사용하는 대그룹은 `MG`, 즉 **Market Group Platform**이다.

실제 Service ID와 Java 패키지에서는 소문자 `mg`로 표현한다.

### 그림 4-4. 대그룹 코드의 표현 방식

```text
업무 분류표
   MG
   │
   │ 코드 표현 변환
   ▼
Java Package
   nhnis.mg...
   │
   ▼
Service ID
   mg...
```

다음 세 개는 비슷해 보이지만 서로 다른 개념이다.

```text
MG
  = 애플리케이션 분류 코드

pdmg-service
  = 배포/프로젝트 모듈명

PD
  = 분류표의 "통합상품(Product)" 업무코드
```

### 그림 4-5. MG / pdmg / PD를 혼동하지 않는다

```text
MG
│
├─ Market Group Platform
│
├─ CO
├─ IC
├─ PC
├─ ...
└─ PD  ← 통합상품 업무코드


pdmg-service
     │
     └─ 프로젝트/배포 모듈명
        분류표의 PD와 다른 개념
```

# 4.5 MG 아래의 업무코드

분류표에는 MG 아래 여러 업무 영역이 정의되어 있다.

### 그림 4-6. MG 업무코드 전체 지도

```text
MG  Market Group Platform
│
├─ CO  공통
├─ IC  통합고객
├─ PC  개인고객
├─ BC  기업고객
├─ MS  미니싱글뷰
├─ SA  상담판매
├─ PD  통합상품
├─ CM  캠페인
├─ EB  EBM
├─ EP  실시간처리
├─ BP  행동정보처리
├─ BD  고객행동데이터
├─ SS  영업지원
├─ CS  Customer Service
├─ CT  컨텐츠
└─ MM  메시지
```

각 업무코드는 단순한 메뉴 그룹이 아니라 **업무 소유 영역**을 나타낸다.

### 그림 4-7. 업무코드 선택 기준

```text
"어느 메뉴에서 실행되는가?"
            │
            └─ 보조 정보


"어느 업무가 데이터를 소유하는가?"
            │
            ▼
"실패 시 어느 업무가 복구 결정을 하는가?"
            │
            ▼
        업무코드 선택
```

화면이 공통 포털에 있다는 이유만으로 모든 거래를 `CO`로 분류하면 안 된다.

# 4.6 세부업무 코드의 의미는 업무마다 다르다

세부업무 코드는 1자리 기능코드다.

중요한 점은 **A/B/C/D의 의미가 모든 업무에서 동일하지 않다**는 것이다.

### 그림 4-8. 기능코드의 업무별 의미

```text
CO
├─ A = 공통관리
├─ B = 사용자관리
├─ C = 메뉴관리
└─ D = 로그관리


IC
├─ A = 고객통합조회
├─ B = 고객통합관리
├─ C = 고객통합검색
└─ D = 고객식별


MM
├─ A = SMS
├─ B = LMS
├─ C = PUSH
└─ D = EMAIL
```

따라서 이런 해석은 잘못이다.

```text
X A는 모든 업무에서 "조회"
X B는 모든 업무에서 "등록"
```

A/B/C/D는 **세부업무 분류 코드**이며, S/C/U/D는 뒤에서 설명할 **거래 행위 코드**다.

### 그림 4-9. 세부업무 코드와 거래구분 코드는 완전히 다르다

```text
mg co a 9000 S 0
      │        │
      │        └─ 거래구분 S = 조회
      │
      └────────── 세부업무 A = CO의 공통관리

A ≠ Action 코드 위치
```

같은 문자라도 자리와 의미를 구분해야 한다.

---

# 4.7 현재 샘플 업무축은 MG / CO / A다

현재 PDMG 샘플과 관리 프로그램은 주로 `MG + CO + A` 축을 사용한다.

### 그림 4-10. MG/CO/A의 세 가지 투영

```text
분류체계
MG / CO / A
     │
     ├───────────────┐
     │               │
     ▼               ▼
Java Package       Mapper Resource
nhnis.mg.co.a      rdw.mg.co.a
     │               │
     └───────┬───────┘
             ▼
Service ID Prefix
mgcoa
```

따라서 다음 세 값이 같은 분류축을 가져야 한다.

```text
Java Package   : nhnis.mg.co.a
Mapper Resource: rdw.mg.co.a
Service Prefix : mgcoa
```

---

# 4.8 다른 업무축으로 확장하면 어떻게 되는가

분류표는 CO/A 하나만을 위한 규칙이 아니다.

### 그림 4-11. 다른 업무축으로의 확장 예

```text
통합고객 관리

MG
 └─ IC
     └─ B
         │
         ├─ Java
         │   nhnis.mg.ic.b.*
         │
         ├─ Mapper
         │   rdw.mg.ic.b/
         │
         └─ Service ID Prefix
             mgicb
```

또 다른 예:

```text
메시지 SMS

MG
 └─ MM
     └─ A
         │
         └─ Service Prefix
             mgmma
```

이 예는 분류체계 적용 방법을 설명하는 것이며, 해당 업무의 실제 프로그램 번호와 구현이 현재 존재한다는 뜻은 아니다.

# 4.9 Program ID는 9자리다

대그룹 2자리 + 업무 2자리 + 세부업무 1자리 + 프로그램 식별번호 4자리를 합치면 Program ID가 된다.

### 그림 4-12. Program ID 해부

```text
mgcoa9000
│ │ ││
│ │ │└──── 9000 : 프로그램 식별번호 4자리
│ │ └────── a    : 세부업무 1자리
│ └──────── co   : 업무코드 2자리
└────────── mg   : 대그룹 2자리
```

수식으로 표현하면:

```text
mg + co + a + 9000
 2    2    1     4
──────────────────
       9자
```

---

# 4.10 Program ID는 “프로그램 가족”을 나타낸다

Program ID 하나 아래 여러 거래가 존재할 수 있다.

### 그림 4-13. Program ID 하나에 여러 Service ID

```text
                    mgcoa9000
                   Program ID
                       │
      ┌────────────────┼────────────────┬────────────────┐
      │                │                │                │
      ▼                ▼                ▼                ▼
mgcoa9000S0       mgcoa9000C0      mgcoa9000U0      mgcoa9000D0
    조회              등록              수정              삭제
```

따라서 다음과 같이 이해한다.

```text
mgcoa9000
  = 프로그램

mgcoa9000S0
  = 그 프로그램의 조회 거래

mgcoa9000U0
  = 그 프로그램의 수정 거래
```

# 4.11 현재 확인되는 대표 Program ID

현재 자료에서는 다음 Program ID들이 확인된다.

| Program ID | 현재 용도 | 대표 Service ID |
|---|---|---|
| `mgcoa5530` | 마케팅희망고객 조회 | `mgcoa5530S0` |
| `mgcoa8888` | 이미지로그 조회·삭제 | `mgcoa8888S0`, `mgcoa8888D0` |
| `mgcoa9000` | 거래 파라미터 관리 | `mgcoa9000S0/C0/U0/D0` |
| `mgcoa9001` | 거래통제 관리 | `mgcoa9001S0/C0/U0/D0` |
| `mgcoa9100` | 런타임 진단 | `mgcoa9100S0` |
| `mgcoa9999` | 영업팁 실적 조회 | `mgcoa9999S0` |

이 목록은 현재 소스와 책 원고의 재검증 결과를 기준으로 한다. 과거 분석 자료에는 더 적은 거래 수가 기록된 시점이 있으므로 그 수치를 현재 정본처럼 사용하지 않는다.

### 그림 4-14. Program ID별 거래 폭

```text
mgcoa5530
  └─ S0

mgcoa8888
  ├─ S0
  └─ D0

mgcoa9000
  ├─ S0
  ├─ C0
  ├─ U0
  └─ D0

mgcoa9001
  ├─ S0
  ├─ C0
  ├─ U0
  └─ D0

mgcoa9100
  └─ S0

mgcoa9999
  └─ S0
```

# 4.12 프로그램 번호는 같은 분류축에서 유일해야 한다

예를 들어 `mgcoa9000`과 동일 분류축에서 또 다른 프로그램이 9000을 사용하면 충돌한다.

### 그림 4-15. Program ID 충돌

```text
MG / CO / A
     │
     ├─ 9000 → 거래 파라미터 관리
     │
     └─ 9000 → 신규 업무
                  │
                  ▼
                충돌
```

현재 중앙 자동 발급기가 있다고 단정할 수 없으므로 신규 번호는 저장소와 관리 절차를 함께 확인해야 한다.

### 그림 4-16. 프로그램 번호 배정 절차

```text
업무 분류 승인
     │
     ▼
MG / 업무 / 세부기능 확정
     │
     ▼
기존 Program ID 검색
     │
     ├─ Java
     ├─ Mapper
     ├─ UI
     ├─ Sample JSON
     ├─ 문서
     └─ 병렬 개발/관리대장
     │
     ▼
미사용 번호 확인
     │
     ▼
Program ID 승인
```

번호는 화면 메뉴 순서나 조직개편 의미를 과도하게 인코딩하지 않는 것이 좋다.

# 4.13 Service ID는 11자리다

Program ID 뒤에 거래구분 1자리와 순번 1자리를 붙이면 Service ID가 된다.

### 그림 4-17. Service ID 기본 구조

```text
┌─────────┬─────────┬─────────┬────────────┬──────────┬─────────┐
│ 대그룹  │ 업무    │ 세부업무│ 프로그램   │ 거래구분 │ 순번    │
│ 2       │ 2       │ 1       │ 4          │ 1        │ 1       │
└────┬────┴────┬────┴────┬────┴─────┬──────┴────┬─────┴────┬────┘
     │         │         │          │           │          │
     ▼         ▼         ▼          ▼           ▼          ▼
    mg        co         a         9000         S          0
```

조합 결과:

```text
mg + co + a + 9000 + S + 0
              │
              ▼
        mgcoa9000S0
```

# 4.14 11자리 Service ID를 한 글자씩 읽는다

### 그림 4-18. `mgcoa9000S0` 해부

```text
m g c o a 9 0 0 0 S 0
│ │ │ │ │ └───┬───┘ │ │
│ │ │ │ │     │     │ └─ 순번 0
│ │ │ │ │     │     └─── 거래구분 S
│ │ │ │ │     └───────── 프로그램 번호 9000
│ │ │ │ └─────────────── 세부업무 a
│ │ └─┴───────────────── 업무코드 co
└─┴───────────────────── 대그룹 mg
```

더 짧게 읽는 방법은 뒤에서부터 자르는 것이다.

### 그림 4-19. Service ID를 뒤에서 읽는 방법

```text
mgcoa9000S0
         ││
         │└─ 순번
         └── 거래구분

mgcoa9000
     │
     └──── Program ID

mgcoa
 │
 └──────── 분류축
```

# 4.15 거래구분 코드

표준 거래구분은 다음과 같다.

| 코드 | 의미 | 대표 성격 |
|---|---|---|
| `S` | Select/Search | 조회 |
| `C` | Create | 등록 |
| `U` | Update | 수정 |
| `D` | Delete | 삭제 |
| `A` | Action | CRUD 하나로 표현하기 어려운 업무 실행 |
| `R` | Report | 보고서/출력 |

### 그림 4-20. 거래구분 선택

```text
업무 상태를 읽기만 하는가?
   ├─ YES → S
   └─ NO
       │
새 상태를 생성하는가?
   ├─ YES → C
   └─ NO
       │
기존 상태를 변경하는가?
   ├─ YES → U
   └─ NO
       │
기존 상태를 제거하는가?
   ├─ YES → D
   └─ NO
       │
명령성 업무 실행인가?
   ├─ YES → A
   └─ NO
       │
보고서/산출물인가?
   └─ R 검토
```

HTTP 메서드가 POST라고 해서 `C`가 되는 것은 아니다.

PDMG 온라인 거래는 조회도 POST를 사용할 수 있다.

```text
HTTP POST
    ≠
Create 거래
```

# 4.16 `A`와 `R`은 “기타” 코드가 아니다

### 그림 4-21. A/R의 사용 판단

```text
A
└─ 승인
└─ 확정
└─ 재처리
└─ 계산 실행
└─ 상태 전이 중심 명령

R
└─ 보고서
└─ 대용량 산출물
└─ 출력 중심 처리


X A = 분류하기 귀찮은 모든 거래
X R = 일반 조회 S의 대체 코드
```

현재 Handler 예에서 A/R 사용이 제한적이거나 없더라도 표준상 예약된 의미는 유지한다.

# 4.17 순번은 같은 거래유형 안의 세부 거래를 구분한다

마지막 한 자리는 순번이다.

### 그림 4-22. 동일 프로그램의 여러 조회

```text
Program ID
mgcoa7777
   │
   ├─ S0 : 목록 조회
   ├─ S1 : 상세 조회
   ├─ S2 : 통계 조회
   └─ S3 : 조건 조회
```

순번은 일반적으로 다음 범위를 사용한다.

```text
0 ~ 9
A ~ Z
```

하지만 순번을 API 버전처럼 사용해서는 안 된다.

### 그림 4-23. 거래 순번과 버전의 차이

```text
S0 ──────► 거래 A
S1 ──────► 거래 B

O 서로 다른 거래


S0 v1
S1 v2

X 단순 버전 번호 대체
```

계약 버전이 필요하면 API/전문 호환성 정책과 별도로 설계한다.

# 4.18 Service ID의 형식 규칙

표준 형식을 정규식으로 표현하면 다음과 같다.

```regex
^[a-z]{2}[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

MG 그룹만 더 엄격히 보면:

```regex
^mg[a-z]{2}[a-z][0-9]{4}[SCUDAR][0-9A-Z]$
```

### 그림 4-24. Service ID 문법 검증

```text
mgcoa9000S0
│
├─ mg          소문자 2
├─ co          소문자 2
├─ a           소문자 1
├─ 9000        숫자 4
├─ S           SCUDAR
└─ 0           0-9 / A-Z
       │
       ▼
   문법 통과
```

그러나 정규식만 통과했다고 유효한 Service ID는 아니다.

# 4.19 Service ID 검증은 네 단계가 필요하다

### 그림 4-25. Service ID 4단계 검증

```text
1. 문법
   │
   │ 11자리/문자종류
   ▼
2. 분류표
   │
   │ MG/업무/세부기능이 승인됐는가?
   ▼
3. 유일성
   │
   │ Program 번호가 충돌하지 않는가?
   ▼
4. 실행 등록
   │
   │ Handler Registry에 정확히 등록됐는가?
   ▼
사용 가능
```

예를 들어:

```text
mgzza1234S0
```

은 형식은 맞을 수 있지만 `ZZ/A`가 승인된 분류가 아니라면 의미상 잘못된 ID다.

```text

  ├─ 11자리
  ├─ 분류표 준수
```

# 4.21 Program ID와 Service ID의 차이

### 그림 4-27. Program ID vs Service ID

```text
Program ID
mgcoa9000
│
│ 프로그램 가족
│
├───────────────┐
│               │
▼               ▼
Service ID      Service ID
mgcoa9000S0     mgcoa9000U0
조회 거래         수정 거래
```

| 항목 | Program ID | Service ID |
|---|---|---|
| 예 | `mgcoa9000` | `mgcoa9000U0` |
| 길이 | 9자 | 11자 |
| 의미 | 프로그램 영역 | 개별 실행 거래 |
| 주요 사용 | 클래스 묶음·소스 탐색 | 런타임 라우팅·로그·통제 |
| 관계 | 1 | 1:N |

# 4.24 `scid`와 `rms_svc_c`도 서로 다르다

# 4.31 Registry에서 중요한 것은 클래스명이 아니라 등록값이다

예를 들어 클래스명이 `mgcoa9000Handler`라고 해서 Dispatcher가 자동으로 `mgcoa9000*`를 찾는 것은 아니다.

### 그림 4-38. 런타임 계약과 네이밍 계약

```text
클래스명

  "mgcoa9000U0",

      ▼
TransactionDispatcher
```


# 4.32 중복 Service ID는 기동 시 실패해야 한다

# 4.33 Handler 등록과 내부 분기는 둘 다 맞아야 한다

### 그림 4-40. Handler의 두 계약

```text
1. serviceIds()

mgcoa9000S0
mgcoa9000C0
mgcoa9000U0
mgcoa9000D0
      │
      ▼

C0 → facade.C0
U0 → facade.U0
D0 → facade.D0
```

```text

  └─ mgcoa9000C0
       │
       ▼

       │
       ▼

  C0 case 없음
       │
       ▼
Handler 내부 실패
```

반대도 문제다.

```text
handle()에는 U0 있음
       │
       ▼
serviceIds()에는 U0 없음
       │
       ▼
Dispatcher가 도달 불가
```

# 4.34 Service ID는 Handler에서 Facade로 이어진다

### 그림 4-42. Program 단위 Handler의 거래 분기

```text
mgcoa9000Handler
      │
      ├─ mgcoa9000S0
      │       ↓
      │  facade.mgcoa9000S0()
      │
      ├─ mgcoa9000C0
      │       ↓
      │  facade.mgcoa9000C0()
      │
      ├─ mgcoa9000U0
      │       ↓

      │
```

```text

```

```text
          ▼
```

```text
          │
          ├─ Service A
          ├─ Service B
          └─ Service C
```

### 그림 4-55. Service ID별 Timeout TO-BE

# 4.63 제4장에서 반드시 기억할 열두 가지

첫째, **애플리케이션 코드 분류표가 업무 코드 의미의 최상위 기준이다.**

둘째, **현재 PDMG의 대그룹은 MG이며 실제 ID와 패키지에서는 `mg`로 표현한다.**

셋째, **업무코드와 세부기능 코드는 업무 책임을 나타내며 임의로 만들지 않는다.**

넷째, **A/B/C/D 기능코드의 의미는 업무코드마다 다르다.**

다섯째, **Program ID는 9자리이고 프로그램 영역을 식별한다.**

여섯째, **Service ID는 11자리이고 실행 가능한 거래를 식별한다.**

일곱째, **Service ID의 거래구분은 S/C/U/D/A/R이며 실제 업무 부수효과와 맞아야 한다.**

여덟째, **TCF ON에서 Service ID는 Dispatcher의 Handler Registry Key다.**

아홉째, **현재 Controller는 Context Header → 요청 Header → URL Path 순으로 Service ID를 결정하므로 복수 값 불일치를 주의해야 한다.**

열째, **화면번호, Program ID, `scid`, Service ID는 비슷하게 보일 수 있지만 서로 다른 계약이다.**

열한째, **Service ID는 URL뿐 아니라 Handler, Facade, Service, DTO, DAO, Mapper, 통제, Timeout, 로그를 연결하는 추적 키다.**

열두째, **런타임에서 등록 문자열이 동작한다고 해서 표준까지 만족한 것은 아니다. 형식·분류·유일성·등록을 별도로 검증해야 한다.**
