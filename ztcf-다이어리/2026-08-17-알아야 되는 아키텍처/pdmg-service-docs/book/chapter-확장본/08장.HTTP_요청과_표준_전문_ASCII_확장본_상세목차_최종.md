# 제8장. HTTP 요청과 표준 전문 — ASCII 확장본 상세 목차

> **목차 작성 기준**
>
> 이 목차는 `book.zip`의 제8장 **「HTTP 요청과 표준 전문」**과 해당 장의 Source Map에 지정된 기본·재분석·다이어그램 자료를 기준으로 구성한다.
>
> 최종 본문은 `06장.패키지와_프로젝트_구조_ASCII_확장본`과 같은 편집 밀도와 형식을 적용한다.
>
> 다음 사항을 사실 기준으로 유지한다.
>
> - PDMG 온라인 거래의 기본 메시지는 HTTP 전송계약과 JSON 표준 전문을 함께 사용한다.
> - HTTP Header와 JSON의 `hdr_nhnis`는 서로 다른 계층의 Header다.
> - JSON Body는 `hdr_nhnis.sys_comm`과 `dto`를 기본 축으로 본다.
> - `rms_svc_c`는 Service ID, `std_gbl_id`는 GUID 추적 식별자로 구분한다.
> - TCF ON에서는 공통 `OnlineTransactionController`를 거쳐 `TcfFacade`로 진입한다.
> - TCF ON Controller는 전체 JSON에서 `dto`를 분리하여 업무 실행부로 전달한다.
> - TCF OFF에서는 업무 Controller와 PDMG 전용 `RequestBodyArgumentResolver`가 DTO 변환을 담당한다.
> - local Profile의 Header 합성은 개발 편의 기능이며 운영 표준 전문 자체로 해석하지 않는다.
> - 성공 응답과 오류 응답의 Body 구조는 동일하다고 가정하지 않는다.
> - 현재 오류 응답은 `dto`가 아니라 `result` 영역을 사용하는 경우가 있으므로 실제 구현 기준을 명확히 구분한다.
> - Filter 단계에서 발생한 오류가 항상 동일한 표준 오류 전문으로 변환되는 것은 아니다.
> - CORS와 인증은 서로 다른 문제다.
> - 문서상의 UI Relay 경로와 현재 실제 UI 직접 호출 경로가 다를 수 있으므로 AS-IS와 대안 구조를 구분한다.
> - Client Timeout과 서버 TCF Timeout은 서로 다른 Timeout이다.
> - `X-Forwarded-For`, 전문의 사용자·IP·Service ID 등 클라이언트 제공값에는 신뢰 경계가 필요하다.
>
> 이 장의 목표는 JSON 예제를 외우는 것이 아니라 **브라우저에서 만들어진 HTTP 요청이 Filter·Interceptor·Spring MVC·TCF·업무 DTO로 변환되고 다시 표준 응답으로 돌아오는 전체 메시지 생명주기**를 이해하는 것이다.

# 8.106 제8장에서 기억해야 할 핵심 사항

- HTTP Header와 전문 Header를 분리한다.
- `hdr_nhnis.sys_comm`과 `dto`의 책임을 분리한다.
- Service ID와 GUID의 역할을 혼동하지 않는다.
- TCF ON/OFF의 URL과 DTO 변환 경로를 구분한다.
- local Header 합성을 운영 표준으로 오해하지 않는다.
- 성공 `dto`와 오류 `result`를 동일 구조로 가정하지 않는다.
- Filter 오류와 MVC 이후 오류를 구분한다.
- CORS와 인증을 분리해서 진단한다.
- UI 직접 호출과 Relay를 AS-IS/대안으로 구분한다.
- Client Timeout과 서버 TCF Timeout을 구분한다.
- 클라이언트가 제공한 IP·사용자·Service ID의 신뢰 경계를 정의한다.
- 전문은 단순 JSON이 아니라 시스템 간 버전 관리 대상 Contract다.
