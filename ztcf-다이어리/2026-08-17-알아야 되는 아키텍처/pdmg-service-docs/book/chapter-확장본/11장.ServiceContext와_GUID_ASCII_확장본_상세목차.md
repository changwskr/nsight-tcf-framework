# 제11장. ServiceContext와 GUID — ASCII 확장본 상세 목차

> **목차 작성 기준**
>
> 이 장은 `book.zip`의 제11장 원문과 `16.Service Context.md`, `16.Service Context-1.md`, `41.시스템 컨텍스트 정보는 어디서 생성되는가.md`, `69.GUID 아키텍처 다이어그램.md`, `70.Service Context 다이어그램.md`를 중심으로 확장한다.
>
> 다음 사실을 고정한다.
>
> - ServiceContext는 DefaultFilter에서 생성되어 ServiceContextHolder의 ThreadLocal에 등록되고 Request Thread 종료 시 Filter finally에서 제거된다.
> - 최신 DefaultFilter 재분석 기준 `shouldNotFilter()`는 OPTIONS만 제외한다. 일부 심화 문서의 GET/actuator 제외 설명은 현재 AS-IS로 사용하지 않는다.
> - ServiceContext는 HTTP/표준 Header/GUID/원문 공통정보를 담지만 DB Transaction이나 인증 정책을 직접 관리하지 않는다.
> - ServiceContextHolder의 `getInstance()`는 null을 반환할 수 있으며 ThreadLocal은 다른 Thread로 자동 전파되지 않는다.
> - Log4j2 ThreadContext(MDC)와 ServiceContext는 서로 다른 저장소이며 명시적으로 동기화·정리해야 한다.
> - GUID는 `std_gbl_id`와 ServiceContext.guid, MDC, ImageLog, TransactionContext, 외부 추적을 연결하지만 DB Transaction ID나 인증 Credential이 아니다.
> - JWT 검증 성공 시 확인된 AS-IS는 Request Attribute `ssoId` 저장이다. JWT Claim 전체가 Header/userContext에 자동 반영된다고 쓰지 않는다.
> - TransactionContext는 현재 ServiceContext의 불변 Snapshot이 아니라 동일 객체 참조를 보유한다.
> - OnlineTimeoutWorkerContext는 MDC는 복사하지만 ServiceContext는 원본 객체를 Worker에 설치한다.
> - 따라서 Worker는 ServiceContext 내부 HttpServletRequest/Response와 mutable header/userContext/responseBody를 간접 공유할 수 있다.
> - Timeout 후 Worker가 계속 실행되면 Request Thread와 동일 Context를 동시에 사용할 가능성이 현행 P0 위험이다.
> - TO-BE는 Servlet 객체가 없는 불변 Worker Snapshot 또는 필요한 값의 명시적 인자 전달을 우선 검토한다.
> - Request Thread와 Worker Thread는 각각 자기 Holder/MDC를 finally에서 정리해야 한다.
