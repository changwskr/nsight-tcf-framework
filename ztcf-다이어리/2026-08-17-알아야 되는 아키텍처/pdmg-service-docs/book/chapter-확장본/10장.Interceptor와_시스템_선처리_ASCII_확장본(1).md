# 제10장. Interceptor와 시스템 선처리

> **집필 기준**
>
> 제9장에서 Filter와 Spring MVC의 경계를 이해했다면, 제10장에서는 Handler가 선택된 뒤 Controller가 실행되기 직전과 요청 완료 시점에 PDMG가 어떤 공통 선·후처리를 수행하는지 추적한다.
>
> 이 장은 특히 **문서상 설계 의도와 실제 호출선의 차이**를 엄격히 구분한다.
>
> **AS-IS 핵심**
>
> - `ServicePreventionInterceptor.preHandle()`은 Header/GUID 보완, 요청 전문 로그, Pre ImageLog 중심이다.
> - 정상 분기에서 명시적 `false` 차단은 없고 대체로 `true`를 반환한다.
> - 거래통제 관련 STF/Service/Repository 코드는 존재하지만 현재 `TcfFacade.process()` 실행선에 STF가 연결되지 않았다.
> - 시간대 통제는 요구에 존재하지만 현재 Repository SQL 지원으로 확인되지 않는다.
> - ImageLog는 업무 Transaction 바깥에서 동작하며 저장 실패는 대체로 fail-open이다.
> - `afterCompletion`은 MVC 완료 Callback이며 업무 Commit Callback이 아니다.
> - Request Thread 시스템 선후처리와 Worker Thread 업무 Transaction을 분리해서 본다.


---

## 이 장을 시작하며

Filter가 Body를 다시 읽을 수 있게 만들고 ServiceContext를 준비했다고 해서 Controller를 바로 실행해도 되는 것은 아니다.

Spring MVC가 요청에 맞는 Handler를 고른 뒤에는 다음 질문을 처리할 마지막 공통 MVC 경계가 필요하다.

```text
공통 Header가 완전한가?
GUID가 있는가?
어떤 Service ID인가?
누가 요청했는가?
어느 IP·영업점·채널인가?
요청 전문을 감사에 남겼는가?
이 거래를 실행해도 되는가?
업무 완료 뒤 어떤 결과를 감사에 남길 것인가?
```

PDMG에서는 `ServicePreventionInterceptor`가 이 위치에 있다.

그러나 클래스 이름만 보고 “Service Prevention = 거래통제”라고 이해하면 현재 코드를 잘못 설명하게 된다.

```text
현재 preHandle
= Header/GUID 보완
+ 요청 전문 로그
+ Pre ImageLog

거래통제 코드
= STF + MgTxControlService + Repository에 존재

현재 온라인 실행선
= STF 호출이 확인되지 않음
```

따라서 이 장의 가장 중요한 학습 목표는 다음이다.

```text
코드가 존재하는가?
        ≠
실제 Runtime 호출선에 연결되어 있는가?
        ≠
운영에서 검증된 정책으로 동작하는가?
```

# 10.1 Interceptor는 왜 Filter 다음에 필요한가

Filter가 HTTP Body·JWT·ServiceContext를 준비한 뒤에도 Spring MVC가 선택한 Handler 직전에 공통 요청 정보를 확정하고 감사 시작점을 남길 경계가 필요하다. PDMG에서는 ServicePreventionInterceptor가 이 MVC 경계를 담당한다.

이 구간은 Spring MVC가 선택한 Handler를 호출하기 직전의 **시스템 선처리 경계**를 설명한다. Filter 단계와 중복해 보이더라도 Handler 정보를 알 수 있는 시점과 감사 시작 시점이 다르므로 실행 위치를 먼저 본다.


### 그림 10-1. Interceptor는 왜 Filter 다음에 필요한가 — 구조


```text
HTTP Request
   ↓
DefaultFilter
   ↓
DispatcherServlet
   ↓
HandlerMapping
   ↓
ServicePreventionInterceptor.preHandle
   ↓
Controller
```


### 그림 10-2. Interceptor는 왜 Filter 다음에 필요한가 — 실행·검증 관점


```text
Filter               Interceptor
──────               ───────────
Servlet 앞단          Handler 선택 후
Body/Auth/Context     MVC 선처리/감사
Handler 모름          Handler 알 수 있음
```


**아키텍처 판단**


이 책임이 Interceptor에 있어야 하는 이유를 실행 시점과 정보 가용성으로 설명하고, Filter·STF·Business 계층과 중복되지 않게 유지한다.

# 10.10 Interceptor는 업무 트랜잭션 밖에서 실행된다

preHandle과 afterCompletion은 업무 Facade·Worker TransactionTemplate 밖이다. 같은 HTTP 요청 안에 있어도 같은 Spring Transaction이라고 보면 안 된다.

이 구간은 Spring MVC가 선택한 Handler를 호출하기 직전의 **시스템 선처리 경계**를 설명한다. Filter 단계와 중복해 보이더라도 Handler 정보를 알 수 있는 시점과 감사 시작 시점이 다르므로 실행 위치를 먼저 본다.


### 그림 10-19. Interceptor는 업무 트랜잭션 밖에서 실행된다 — 구조


```text

   ↓
Controller → TcfFacade
              │ submit
              ▼
          Worker Thread
          TransactionTemplate
          TX BEGIN
          Handler→Facade→Service→DAO
          COMMIT/ROLLBACK

              ▼

```

이 구간은 거래통제의 가장 중요한 사실판단 영역이다. 문서 요구사항, 구현된 클래스, 실제 호출선, 운영 적용 여부를 각각 분리해 설명한다.


### 그림 10-207. 자정을 넘는 시간대 Rule — 구조


```text

   ↓
MgTxControlService.check
   ↓
Repository
   ↓
Rule match?
 ├─ YES → FW0410 차단
 └─ NO  → Dispatcher
```


### 그림 10-208. 자정을 넘는 시간대 Rule — 실행·검증 관점


```text
[현재 AS-IS]

  ↓
TimeoutExecutor
  ↓
Dispatcher

= 코드 존재
= 호출선 미연결
```


**아키텍처 판단**

# 10.108 Pre ImageLog는 언제 기록되는가

GUID와 요청 원문을 확정한 뒤 Controller 진입 직전에 `ImageLogHandler.preImagelog`가 호출된다.

ImageLog는 업무 데이터 자체가 아니라 요청·응답·예외를 관찰하는 감사 데이터다. 업무 Transaction과 독립된다는 장점과 비원자성의 위험을 함께 본다.


| ImageLog 상태 | 의미 |
|---|---|
| 행 없음 | 아직 Pre 기록 없음 |
| PRE | 요청 수신/Controller 진입 준비 |
| POST | 응답 정보 보완 |
| EXCEPTION | 예외 정보 보완 |
| PRE 장기잔존 | 후처리 실패/프로세스 종료/추적 불일치 조사 |


### 그림 10-215. Pre ImageLog는 언제 기록되는가 — 구조


```text
preImagelog
  ↓
GUID UPDATE
 ├─ row 있음 → 갱신
 └─ 없음     → INSERT
                 └─ Duplicate → UPDATE retry
```


### 그림 10-216. Pre ImageLog는 언제 기록되는가 — 실행·검증 관점


```text
ImageLog 상태
없음
 ↓
PRE
 ├─ POST 정상
 ├─ EXCEPTION
 └─ 후속 실패 → PRE 잔존
```


**아키텍처 판단**


감사 데이터는 업무 결과와 원자적이지 않다. fail-open/fail-close를 업무 중요도와 규제 기준으로 정하고 실패율을 별도 모니터링한다.

이 구간은 Request Thread와 Worker Thread, 업무 Transaction과 ImageLog Transaction을 분리해 End-to-End 증적을 만드는 방법을 다룬다.


### 그림 10-321. Timeout 테스트는 Worker 종료까지 본다 — 구조


```text
Request Thread
preHandle / Pre ImageLog
   ↓
Controller → TcfFacade
              │ submit
              ▼
          Worker Thread
          TransactionTemplate
          TX BEGIN
          Handler→Facade→Service→DAO
          COMMIT/ROLLBACK
              │
              ▼
Request Thread
Advice → afterCompletion / ImageLog
```


### 그림 10-322. Timeout 테스트는 Worker 종료까지 본다 — 실행·검증 관점


```text
업무 ROLLBACK
   ≠ Pre ImageLog ROLLBACK

업무 COMMIT
   ≠ Post ImageLog 성공 보장
```


**아키텍처 판단**


Request Thread의 시스템 선후처리와 Worker Thread의 업무 Transaction을 분리한다. 같은 HTTP 요청이라는 이유로 같은 Transaction이라고 해석하지 않는다.
