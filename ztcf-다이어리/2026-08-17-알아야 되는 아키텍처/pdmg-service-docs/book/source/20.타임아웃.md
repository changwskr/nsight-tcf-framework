## 0. 정책 한눈에 (현행)

**TCF 온라인 거래의 Dispatcher~DAO 구간**에 공통 타임아웃이 **적용되어 있다.**

| 항목 | 값 |
|------|-----|
| 스위치 | `nhnis.fw.timeout.enabled=true` |
| 기본 제한시간 | **5000 ms** |
| serviceId별 | `overrides` (예: `mgcoa5530S0: 10000`) |
| min-start-budget | **1000 ms** (미달 시 TX 미개시 Timeout) |
| sql-safety | **10 s** (Deadline 없을 때 MyBatis ceiling) |
| Pool | size **20**, queue **100**, `pdmg-online-` |
| 진입점 | `TcfFacade` → `ExecutionDeadline` → `OnlineTimeoutExecutor` |
| 외부 TX | Worker `TransactionTemplate` + ServiceId별 Policy |
| JDBC 취소 | `ActiveJdbcStatementRegistry.cancelAll` → **`Statement.cancel()`** |
| sub-second | remaining &lt; 1s 이면 deadline 시각에 cancel 예약 |
| 타임아웃 응답 | HTTP **504**, `FW_TIMEOUT` |
| 과부하 응답 | HTTP **503**, `FW_OVERLOADED` |
| 검증 | 단위 PASS + 라이브 E2E `cancelInvoked=1` (2026-08-25) |

```text
요청 Thread (HTTP)
  Filter → Interceptor.pre → OnlineController → TcfFacade
      │
      ├─ ExecutionDeadline.bind
      ├─ OnlineTimeoutExecutor
      │     timeoutMs = resolveMilliseconds(serviceId)
      │     Future.get(remainingMs)
      │     on timeout:
      │       cancelAll(evidenceKey)  → Statement.cancel()
      │       future.cancel(true)     → Worker interrupt
      │
      └─ Worker (pdmg-online-*)
            bind Registry
            TransactionTemplate BEGIN (Policy)
              Dispatcher → Handler → Facade → BizPrePost → Service → DAO
              MyBatis: setQueryTimeout + TrackingStatement 등록
            COMMIT 또는 ROLLBACK
            unbind Registry
  → (OnlineTimeoutException 이면 etf skip) → Advice → Response
```

**범위 밖:** DefaultFilter, 시스템 선·후처리, ImageLog, ResponseBodyAdvice.  
**전제:** `nhnis.fw.tcf.enabled=true`.

## 2. 설정

### 2.1 현행 (`application.yml`)

```yaml
nhnis:
  fw:
    timeout:
      enabled: true
      milliseconds: 5000
      overrides:
        mgcoa5530S0: 10000
      pool-size: 20
      queue-capacity: 100
      min-start-budget-ms: 1000
      sql-safety-timeout-seconds: 10
    transaction:
      default-manager: rdwTransactionManager
      default-mode: RDW_READ_WRITE
      services:
        mgcoa5530S0:
          mode: RDW_READ_ONLY
```

### 2.2 제한시간 결정

```text
resolveMilliseconds(serviceId)
  1. overrides 에 있으면 → 해당 ms
  2. 없으면 → milliseconds

Future.get 대기 = ExecutionDeadline.remainingMillis() (최소 1ms)
Worker TX 개시 전 remaining < min-start-budget-ms → 즉시 OnlineTimeoutException
```

### 2.3 규칙

| 키 | 제약 |
|----|------|
| `milliseconds` / overrides | `>= 1` (기동 시 검증) |
| `min-start-budget-ms` | `>= 1` |
| `sql-safety-timeout-seconds` | `>= 1` |
| `pool-size` | `>= 1` |
| `queue-capacity` | `>= 0` (포화 시 Abort → 503) |

## 3. 실행 정책

### 3.1 정상

```text
요청 Thread: Deadline + submit + Future.get(remaining)
Worker: budget OK → TX BEGIN → 업무 → COMMIT
요청 Thread: 결과 반환
```

### 3.2 제한시간 초과

```text
요청 Thread: Future.get timeout
  → evidence markCancelRequested
  → statementRegistry.cancelAll  → Statement.cancel()  [JDBC-CANCEL 로그]
  → future.cancel(true)
  → OnlineTimeoutException → 504 FW_TIMEOUT
Worker: interrupt / SQLException(cancel) / Deadline 재검사
  → setRollbackOnly → ROLLBACK (TX가 시작된 경우)
```

### 3.3 JDBC cancel · QueryTimeout · interrupt

| 수단 | 역할 |
|------|------|
| `Statement.cancel()` | 등록된 활성 Statement 강제 취소 시도 |
| `setQueryTimeout` | 초 단위 JDBC safety (remaining 기반, 최소 1초 floor) |
| sub-second schedule | remaining &lt; 1s 에서 cancel로 floor 보완 |
| `future.cancel(true)` | Worker interrupt |

**검증됨:** cancel 가능한 SQL(또는 등록된 Statement)에서 `cancelInvoked>=1`.  
**best-effort:** 드라이버/DB가 cancel을 즉시 반영하지 않을 수 있음 → interrupt + rollback이 병행.

데모:

- sleep만: Statement 미등록 → `cancelInvoked=0` (설계상)
- `--nhnis.demo.mgcoa5530-jdbc-hold-ms>0`: cancelable SQL + Registry → `cancelInvoked=1`

### 3.4 Executor 포화

`RejectedExecutionException` → `OnlineOverloadException` → **503** `FW_OVERLOADED`.

### 3.5 컨텍스트 전파

`OnlineTimeoutWorkerContext`: ServiceContext + MDC 스냅샷 → Worker install → finally clear.  
evidenceKey는 `ExecutionEvidenceKey` / guid 우선 (cancel·evidence 일치).

## 4. 오류 응답

| 예외 | HTTP | `stdErrCode` |
|------|------|--------------|
| `OnlineTimeoutException` | **504** | `FW_TIMEOUT` |
| `OnlineOverloadException` | **503** | `FW_OVERLOADED` |

로그 예:

```text
[ONLINE-TIMEOUT][JDBC-CANCEL] evidenceKey=… candidates=1 cancelInvoked=1
[ONLINE-TIMEOUT] cancel dispatched … jdbcCancelInvoked=1 futureCancel=true
[ONLINE-TIMEOUT] guid=… serviceId=… timeoutMs=10000 elapsedMs=… cancelRequested=true
```

`OnlineTimeoutException`이면 `TcfFacade`가 **etf를 건너뛴다**.

## 5. 트랜잭션과의 관계

| 층 | 역할 |
|----|------|
| **OnlineTimeoutExecutor** | Worker에서 Policy 기반 `TransactionTemplate`으로 **외부 TX** |
| **Facade `@Transactional`** | `REQUIRED` → 외부 TX **참여** |
| **Service `@Transactional`** | 참여 (또는 TCF OFF 시 BEGIN 가능) |
| Policy `RDW_READ_ONLY` 등 | **최외곽** TX 속성에 반영 |

Facade `@Transactional(timeout=초)`는 보조·샘플 미사용.  
주 정책은 `resolveMilliseconds(serviceId)` + Deadline이다.

## 6. 다른 계층

| 계층 | 현행 |
|------|------|
| Filter~Advice wall-clock kill | 없음 |
| MyBatis queryTimeout + Tracking | **적용** (Interceptor) |
| Hikari connection-timeout | 풀 대기용 (SQL 실행 제한 아님) |
| UI `pdmg.ui.timeout-ms` | 브라우저 Abort. **서버와 별개** → 서버 최대값 이상 권장 |

## 7. 운영 방침

```text
1. 기본 SLA          → milliseconds
2. 거래별 연장       → overrides.<serviceId>
3. TX readOnly 등    → nhnis.fw.transaction.services
4. Pool              → pool-size / queue-capacity (503 감시)
5. JDBC 강제 취소    → Registry + cancel (현행 적용)
6. UI Abort          → pdmg.ui.timeout-ms ≥ 서버 최대 timeout
7. E2E cancel 확인   → jdbc-hold 데모 (운영 기본값 0)
```

## 8. 하지 말 것

1. Controller/Handler/Service에 타임아웃 복제  
2. UI Abort만으로 서버 cancel이 된다고 가정  
3. sleep 데모만으로 `cancelInvoked=0`을 버그로 단정  
4. Worker에서 Context/MDC 정리 생략  
5. override 키를 `rms_svc_c` / serviceId와 다르게 두기  
6. Facade `readOnly`만으로 최외곽 TX readOnly가 바뀐다고 가정
