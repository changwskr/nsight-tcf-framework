# 33. 요청 Thread와 Worker Thread 분리 아키텍처

> **현행화 (2026-08-25):** `Statement.cancel` · Registry · Deadline · TX Policy 반영.  
> 정책 본문: [20.타임아웃.md](../../20.타임아웃.md) · FW: [../../../pdg-fw-docs/01.timeout.md](../../../pdg-fw-docs/01.timeout.md)  
> 원본: [`33.요청쓰레드와 Work쓰레드 분리아키텍처 - 원본.md`](./33.요청쓰레드와%20Work쓰레드%20분리아키텍처%20-%20원본.md)

**맞습니다.** `nhnis.fw.timeout.enabled=true` 일 때 요청 Thread와 Worker Thread가 나뉩니다.

### 역할

| 스레드 | 하는 일 |
| --- | --- |
| **요청 스레드** (Tomcat/HTTP) | Filter·시스템 선처리 → Controller → `TcfFacade` → `Future.get(remaining)` 대기 → (Timeout 시 cancel) → 응답·시스템 후처리·ImageLog |
| **Worker 스레드** (`pdmg-online-*`) | Registry.bind → **TX BEGIN**(Policy) → Handler → Facade → Service → DAO → COMMIT/ROLLBACK → Registry.unbind |

```text
요청 스레드:
  TcfFacade
    → ExecutionDeadline.bind
    → submit(Worker)
    → Future.get(remaining)
         Timeout 시:
           cancelAll → Statement.cancel()
           future.cancel(true) → interrupt
           OnlineTimeoutException → 504 FW_TIMEOUT
           (etf skip)

Worker:
  bind(evidenceKey)
  TransactionTemplate(Policy) {
    Dispatcher → Handler → Facade → Service → DAO
    MyBatis: queryTimeout + TrackingStatement 등록
  }
  unbind
```

### 참고

- `timeout.enabled=false` 이면 `SyncOnlineTimeoutExecutor`라 **분리 없이** 요청 스레드에서 동기 실행합니다. 최외곽 TX는 Facade `@Transactional`.
- 타임아웃 시 요청 스레드는 바로 `FW_TIMEOUT`을 주고, Worker는 cancel/interrupt 후에도 **잠시** 더 돌 수 있습니다. **늦은 커밋은 Deadline 재검사로 막습니다.**
- JDBC가 Registry에 등록된 경우 `Statement.cancel()`을 먼저 시도합니다 (라이브 `cancelInvoked=1` 검증).
- 순수 `Thread.sleep` 구간만 있으면 Statement가 없어 `cancelInvoked=0`일 수 있습니다 (설계상). JDBC hold 데모로 cancel 경로를 확인합니다.

---

## TIMEOUT 경로에서 로그가 섞여 보이는 이유

**시스템 후처리는 요청 Thread에서 먼저 끝날 수 있습니다.** Worker의 업무 후처리 로그는 **다른 스레드**가 늦게 찍은 것일 수 있습니다.

| 스레드 | TIMEOUT 시 |
| --- | --- |
| **요청 스레드** | `Future.get` 초과 → cancel → `FW_TIMEOUT` → **시스템 후처리** → ImageLog |
| **Worker** | cancel/interrupt 처리 중 또는 SQL 반환 후 Deadline 재검사 → ROLLBACK. 업무 후처리 로그가 **뒤에** 남을 수 있음 |

### 정리

- “시스템 후처리가 마지막이어야 한다”는 **한 스레드 정상 성공 경로** 기준입니다.
- TIMEOUT 경로는 **요청 스레드가 먼저 시스템 후처리로 응답**하고, Worker 로그가 **뒤에 섞여** 보일 수 있습니다.
- 이상 동작이 아니라 `OnlineTimeoutExecutor`의 특성입니다.  
  **응답 종료 ≠ Worker 즉시 종료 ≠ cancel 100% 성공** 을 분리해서 봅니다.
- 현행 보완: Registry `Statement.cancel` + QueryTimeout + sub-second complement + interrupt + rollback.
