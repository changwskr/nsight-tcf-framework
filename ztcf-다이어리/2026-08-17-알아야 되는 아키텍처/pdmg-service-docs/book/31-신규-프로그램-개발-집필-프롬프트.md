# 31장 집필 프롬프트 — 신규 프로그램 개발

## 0. 작업 명령

**31장 「신규 프로그램 개발」을 집필하라.**

이 작업은 요약, 초안, 기존 문서 재정리, 목차 항목 채우기가 아니다.  
**「PDMG 애플리케이션 아키텍처와 개발 가이드」의 실제 출판 가능한 31장 본문을 작성하는 작업이다.**

이 장의 역할은 다음과 같다.

> **요구사항 한 건을 Service ID부터 DTO·Handler/Controller·Facade·Service/Rule·DAO/Mapper·오류·UI·테스트·빌드까지 완성하는 실전 개발 절차 장**

## 1. 집필 전에 반드시 수행할 조사

본문부터 작성하지 마라. 다음 순서를 지킨다.

```text
AGENTS.md
   ↓
BOOK-WRITING-RULE.md
   ↓
BOOK-TOC.md
   ↓
SOURCE-MAP.md의 31장
   ↓
29장 / 30장 완성본
   ↓
31장 관련 기본자료
   ↓
*-1.md 재분석·검증 자료
   ↓
다이어그램·심화자료
   ↓
실제 Source / Configuration / Test
   ↓
32 목차 확인
```

집필 전에 반드시 **현재 구현 사실, 문서 설명, 설계안**을 구분한다. 문서끼리 충돌하면 원문을 억지로 합치지 말고 실제 Source와 설정으로 판정한다.

## 3. 이 장에서 반드시 유지할 중심 실행 흐름

다음 Flow를 장 전체의 중심 Story로 사용하되 실제 Source를 확인하여 정확하게 수정한다.

```text
요구사항 → 업무축/프로그램번호 → Service ID → API/DTO → Handler/Controller → Facade → Service/Rule → DAO/Mapper → 오류코드 → UI 요청 → Test → Build/WAR 검증
```

구성요소를 따로따로 설명하고 끝내지 말고, 실제 요청 또는 처리 한 건이 위 흐름을 따라 어떻게 이동하는지 계속 연결한다.

## 5. 이 장에서 특히 깊게 설명할 사항

1. 실제 예제 프로그램 하나를 장 전체에 사용해 파일 생성 순서와 추적성을 보여준다.
2. 5~7장의 네이밍/패키지/도메인 규칙과 14~19장의 계층 규칙을 실제 개발 체크리스트로 통합한다.
3. TCF ON/OFF에서 필요한 진입점과 공통 Business 계층을 구분한다.
4. 완료 기준에 코드뿐 아니라 오류코드·샘플요청·테스트·빌드·문서 정합성을 포함한다.

각 항목은 단순 정의가 아니라 다음 질문에 답하도록 작성한다.

```text
무엇인가?
→ 왜 필요한가?
→ PDMG 전체 구조에서 어디에 있는가?
→ 누가 호출하고 누구를 호출하는가?
→ 어떤 데이터/Context를 주고받는가?
→ 정상 흐름은 무엇인가?
→ 실패하면 무엇이 달라지는가?
→ 실제 Source/설정은 어디에 있는가?
→ 잘못 구현하면 어떤 장애가 생기는가?
→ 운영/테스트에서는 무엇으로 검증하는가?
```

## 6. 실제 Source 검증 규칙

가능한 한 다음 근거를 실제 저장소에서 확인한다.

- 실제 package / class / interface / method
- Spring Annotation과 Bean 생성 조건
- `application*.yml` 및 기타 설정
- Mapper XML / namespace / statement
- DTO 구조
- Transaction / Thread / Timeout 실행 위치
- JWT/보안 관련 키·검증 구성(해당 장인 경우)
- 예외·로그·테스트 코드(해당 장인 경우)

소스에서 확인되지 않은 내용은 `현재 구현`이라고 쓰지 않는다. 필요한 경우 `문서 기준`, `설계안`, `TO-BE 권장`, `확인 필요`, `예시`로 표시한다.

## 8. 이 장에서 금지할 설명 패턴

- 기존 샘플 복사=개발 완료로 처리
- Controller→DAO 직결 CRUD
- 테스트/오류/설정 없이 컴파일만 되면 완료로 판단
- 실제 구현에서 확인하지 않은 동작을 Spring/Java 일반론으로 보충해 PDMG 사실처럼 작성
- “앞 장에서 설명했으므로 생략”을 이유로 현재 장 이해에 필요한 흐름까지 제거
- 장 후반부로 갈수록 설명을 제목+짧은 문단+표 형태로 축약

## 9. 장 후반에 반드시 포함할 실전 산출물

장 주제에 맞게 최소 다음을 포함한다.

- **End-to-End 흐름도**: 이 장의 핵심 실행 과정을 한 화면에서 추적할 수 있게 작성
- **책임/경계 표**: 주요 구성요소의 책임, Caller, Callee, 금지 책임
- **정상/실패 비교**: 성공과 오류 시 실행 흐름 차이
- **Anti Pattern**: 실제 개발자가 자주 할 수 있는 잘못된 구현과 영향
- **개발자 체크리스트**: 신규 개발/수정 시 바로 사용할 수 있는 점검 항목
- **아키텍처 판단 포인트**: 여러 선택지가 있을 때 무엇을 기준으로 결정하는지
- **다음 장 연결**: 다음 장이 왜 필요한지 자연스럽게 연결

## 10. 작성 완료 후 자체 품질검사

BOOK-WRITING-RULE의 품질 Gate와 함께 다음을 검사한다.

- [ ] SOURCE-MAP에 지정된 필수·재분석·심화 자료를 확인했는가?
- [ ] 실제 Source/Configuration/Test로 중요한 AS-IS를 검증했는가?
- [ ] 이전 장 내용을 반복 복사하지 않고 현재 장 관점으로 심화했는가?
- [ ] 다음 장의 상세 내용을 과도하게 침범하지 않았는가?
- [ ] 핵심 절에 Why와 실행 Flow가 있는가?
- [ ] 정상 시나리오와 실패 시나리오가 모두 있는가?
- [ ] Thread/Transaction/Context 경계가 관련된 경우 명시했는가?
- [ ] AS-IS / 표준 / Legacy / TO-BE / 예시가 구분되어 있는가?
- [ ] 실제 확인하지 않은 클래스·설정·URL·필드를 만들어내지 않았는가?
- [ ] 표와 다이어그램이 본문을 대체하지 않았는가?
- [ ] 제목 아래 몇 줄과 불릿으로 끝난 핵심 절이 없는가?
- [ ] 앞 장보다 설명 밀도가 이유 없이 낮아지지 않았는가?
- [ ] 독자가 이 장의 핵심 기능을 실제 개발·장애추적·설계 판단에 사용할 수 있는가?

부족한 항목이 있으면 보고만 하지 말고 본문을 직접 수정하고 보강한 뒤 완료한다.
