## 3. 이 장에서 반드시 유지할 중심 실행 흐름

다음 Flow를 장 전체의 중심 Story로 사용하되 실제 Source를 확인하여 정확하게 수정한다.

```text
실행조건 분기 → Request Thread/Worker Thread → TransactionTemplate 또는 Facade Proxy → BizPrePost → Service → DAO → Commit/Rollback + 시스템 선후처리/ImageLog 별도 경계
```

구성요소를 따로따로 설명하고 끝내지 말고, 실제 요청 또는 처리 한 건이 위 흐름을 따라 어떻게 이동하는지 계속 연결한다.

## 5. 이 장에서 특히 깊게 설명할 사항

1. TCF ON+Timeout ON, TCF ON+Timeout OFF, TCF OFF를 각각 별도 시퀀스로 작성한다.
2. Worker Thread의 TransactionTemplate이 최외곽 TX인지 실제 구현을 최우선 검증한다.
3. Facade @Transactional은 새 TX인지 기존 TX 참여인지 propagation과 호출 Thread 기준으로 설명한다.
4. 시스템 선후처리·ImageLog·오류이력이 업무 TX와 동일/분리인지 근거를 명시한다.
5. 여러 DataSource/JTA 여부는 실제 구현 근거 없이 추측하지 않는다.

각 항목은 단순 정의가 아니라 다음 질문에 답하도록 작성한다.

→ 누가 호출하고 누구를 호출하는가?
→ 어떤 데이터/Context를 주고받는가?
→ 정상 흐름은 무엇인가?
→ 실패하면 무엇이 달라지는가?

## 8. 이 장에서 금지할 설명 패턴

- 모든 경우 Transaction은 Facade에서 시작된다고 단정
- HTTP/온라인 거래 경계를 DB Transaction 경계와 동일시
- Future 취소만으로 DB Transaction이 자동 Rollback된다고 연결
- 실제 구현에서 확인하지 않은 동작을 Spring/Java 일반론으로 보충해 PDMG 사실처럼 작성
- “앞 장에서 설명했으므로 생략”을 이유로 현재 장 이해에 필요한 흐름까지 제거
- 장 후반부로 갈수록 설명을 제목+짧은 문단+표 형태로 축약

## 9. 장 후반에 반드시 포함할 실전 산출물

장 주제에 맞게 최소 다음을 포함한다.

- **End-to-End 흐름도**: 이 장의 핵심 실행 과정을 한 화면에서 추적할 수 있게 작성
- **책임/경계 표**: 주요 구성요소의 책임, Caller, Callee, 금지 책임
- **정상/실패 비교**: 성공과 오류 시 실행 흐름 차이
- **Anti Pattern**: 실제 개발자가 자주 할 수 있는 잘못된 구현과 영향
- **개발자 체크리스트**: 신규 개발/수정 시 바로 사용할 수 있는 점검 항목

- **다음 장 연결**: 다음 장이 왜 필요한지 자연스럽게 연결

### 22장 특별 금지 규칙

- **TCF ON + Timeout ON에서 `Facade @Transactional`을 최외곽 Transaction 시작점이라고 먼저 결론내리지 마라.**
- Worker Thread 내부 `TransactionTemplate`이 최외곽 DB Transaction을 여는지 실제 소스를 최우선 확인한다.
- `Facade @Transactional`은 실행조건에 따라 기존 Transaction 참여일 수 있으므로 Proxy/Propagation/Thread를 함께 설명한다.
