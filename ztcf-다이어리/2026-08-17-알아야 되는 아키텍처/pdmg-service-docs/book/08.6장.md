# 2. 사실 판정 우선순위

자료가 서로 다르면 다음 순서로 판단한다.

```text
실제 Source / Configuration
        ↓
*-1.md 재분석·검증 문서
        ↓
현재 패키지 기준 문서
        ↓
레이어드 아키텍처 문서
        ↓
기본 설명 문서
        ↓
다이어그램
```

실제 Source에 Legacy 구조가 존재한다고 해서 그것을 신규 개발 표준으로 자동 채택하지 않는다.

필요하면 반드시 구분한다.

| 구분   | 의미                        |
| ------ | --------------------------- |
| AS-IS  | 현재 실제 프로젝트에 존재   |
| 표준   | 신규 개발 시 적용할 기준    |
| Legacy | 기존 호환을 위해 남은 구조  |
| TO-BE  | 향후 정비 또는 권장 구조    |
| 예외   | 특별한 이유로 허용되는 구조 |

# 3. 6장의 핵심 역할

5장은 다음 질문에 답했다.

> "무엇이라고 이름을 지을 것인가?"

6장은 다음 질문에 답해야 한다.

> **"그 이름의 클래스와 파일을 프로젝트 어디에 둘 것인가?"**

따라서 6장의 핵심 흐름은 다음과 같다.

```text
업무
 ↓
Service ID / 프로그램 ID
 ↓
Java Package
 ↓
Layer
 ↓
Component
 ↓
Class
 ↓
Resource
 ↓
Spring Scan
 ↓
Runtime Bean
```

독자가 6장을 읽은 후 신규 프로그램의 클래스와 파일을 **어느 디렉토리와 패키지에 만들어야 하는지 스스로 판단할 수 있어야 한다.**

# 4. 5장과 6장의 경계를 명확히 한다

5장:

```text
무엇이라고 이름을 지을 것인가?
```

6장:

```text
그 이름의 파일을 어디에 둘 것인가?
```

예:

```text
5장
CustomerSearchService라는 이름 결정
        ↓

6장
그 Service를
어느 업무 Package의
application/service 영역에 둘 것인가?
```

5장의 네이밍 규칙을 다시 길게 설명하지 않는다.

필요한 부분만 연결한다.

---

# 5. 3장과 6장의 차이도 분명히 한다

3장은 **논리적 Layer와 Component 책임**을 설명하는 장이다.

6장은 그 논리적 구조가 **실제 Source Tree로 어떻게 구현되어 있는지** 설명하는 장이다.

예:

```text
3장

Application Layer
Persistence Layer
Entry Layer

        ↓

6장

src/main/java
   └─ ...
       ├─ entry
       ├─ application
       ├─ dto
       └─ persistence
```

즉,

> Logical Architecture → Physical Source Structure

의 전환을 설명한다.

---

# 6. 7장과의 경계를 지킨다

7장은 도메인 정의와 호출 방식이다.

따라서 6장에서는

- 업무별 Package가 어떻게 나뉘는가
- 동일 도메인의 Component가 어디에 위치하는가
- 업무축을 어떻게 추가하는가

까지 설명한다.

하지만

- 도메인 간 호출 정책
- TCF ON/OFF 호출 방식
- UI Relay
- 외부 시스템 호출
- 동기·비동기 호출 정책

등은 7장에서 상세하게 다룬다.

# 9. 6.1 패키지 설계 원칙

> "관심사를 분리하기 위해 패키지를 나눈다."

라고 쓰지 마라.

최소 다음 관점에서 설명한다.

- 업무 응집도
- Layer 책임
- 의존성 방향
- 코드 탐색성
- 변경 영향도
- Component Scan
- AOP 적용 범위
- Mapper Scan
- Test 구조
- 신규 업무 확장
- 운영 장애 추적
- Codex/LLM 기반 코드 생성

특히 다음 질문을 설명한다.

> 패키지 구조가 단순히 개발자가 보기 좋도록 만든 폴더 구조인가?

아니다.

```text

   ↓

   ↓

Spring Component Scan
   ↓
AOP Pointcut
   ↓
Mapper Scan
   ↓
Runtime 동작
```

이 점을 충분히 설명한다.

# 10. 업무 중심 + Layer 중심 구조를 설명한다

PDMG의 실제 구조를 확인하여 다음 관점을 설명한다.

```text
Base Package
   ↓
업무 영역
   ↓
Layer / Component
```

또는 실제 구현이 다른 구조라면 실제 Source를 따른다.

가상의 Package 구조를 현재 구현처럼 쓰지 않는다.

가능하면 실제 예제를 이용해 다음을 보여준다.

```text
[Base Package]
   └─ [업무]
       ├─ entry
       ├─ application
       ├─ dto
       ├─ persistence
       ├─ client
       ├─ config
       └─ support
```

실제 Source와 차이가 있다면 AS-IS와 표준안을 구분한다.

---

# 11. Source Tree를 반드시 보여준다

6장은 Source Tree가 핵심이다.

실제 Source를 확인하여 대표 업무 하나를 선정하고 다음 수준으로 보여준다.

```text
src/
├─ main/
│  ├─ java/
│  │  └─ [base-package]/
│  │      └─ [업무]/
│  │          ├─ entry/
│  │          ├─ application/
│  │          ├─ dto/
│  │          ├─ persistence/
│  │          ├─ client/
│  │          ├─ config/
│  │          └─ support/
│  │
│  └─ resources/
│      └─ mapper/
│
└─ test/
   └─ java/
```

하지만 Source Tree만 제시하고 끝내지 않는다.

각 디렉토리가 **왜 존재하며 무엇을 넣어야 하는지** 설명한다.

# 12. entry 패키지

`entry`는 단순히 Controller가 들어가는 폴더라고 설명하지 않는다.

실제 PDMG 소스를 확인하고 다음을 설명한다.

- 시스템의 Inbound Entry Point
- TransactionHandler
- Controller
- TCF ON 진입점
- TCF OFF 진입점
- 입력 변환
- Facade 호출
- 허용되는 책임
- 금지되는 책임

다음 관계를 보여준다.

```text
외부 요청
   │
   ├─ TCF ON
   │    ↓
   │  Handler
   │
   └─ TCF OFF
        ↓
      Controller

          ↓

        Facade
```

단, Handler/Controller 자체 상세는 14장에서 다룬다.

6장에서는 **어디에 배치하는가와 Package 책임**에 집중한다.

---

# 13. application 패키지

이 절은 매우 중요하다.

실제 PDMG 구조를 확인하여 다음을 설명한다.

```text
application
   ├─ facade
   ├─ service
   └─ rule
```

실제 하위 패키지명이 다르면 Source를 따른다.

다음 관계를 설명한다.

```text
Facade
   ↓
Service
   ↓
Rule / DAO / Client
```

그리고 반드시 다음 질문에 답한다.

- Facade와 Service를 같은 패키지에 평면 배치하는가?
- 하위 Package로 분리하는가?
- Rule은 Domain 성격인가 Application 성격인가?
- 실제 PDMG에서는 어떻게 구성되어 있는가?
- 표준 구조에서는 어떻게 권장하는가?

---

# 14. dto 패키지

DTO를 단순 POJO 저장소처럼 설명하지 않는다.

다음을 설명한다.

```text
Request
   ↓
DTOin
   ↓
Application
   ↓
DTOout
   ↓
Response
```

필요하면 `DTOSub` 구조도 설명한다.

그리고 다음을 판단한다.

- Controller DTO
- Service DTO
- DAO Parameter
- Result DTO
- Domain Model

이 모든 것을 하나의 DTO Package에 넣어도 되는가?

현재 PDMG 기준을 실제 Source로 확인하여 설명한다.

---

# 15. persistence 패키지

다음 관계를 반드시 설명한다.

```text
application
    ↓
DAO Interface
    ↓
MyBatis Mapper
    ↓
SQL
    ↓
Database
```

이 패키지에는 최소 다음 관점을 설명한다.

- DAO
- Mapper Interface 여부
- Persistence Model 여부
- DB 접근 책임
- SQL과의 연결
- Transaction 참여

다만 DAO/MyBatis 상세 구현은 19장에서 다루므로 6장에서는 **물리적 위치와 의존 방향**을 중심으로 한다.

---

# 16. client 패키지

`client`는 외부 시스템 또는 다른 도메인 호출을 담당하는 Outbound Adapter 관점에서 설명한다.

예:

```text
Business Service
      ↓
    Client
      ↓
HTTP / API / 외부 시스템
```

실제 PDMG Client 구현을 확인한다.

다음과 같은 코드를 업무 Service에 직접 넣는 구조와 비교한다.

```text
Service
  └─ RestTemplate/WebClient 직접 사용
```

왜 Client 계층으로 격리하는 것이 필요한지 설명한다.

단, 외부 호출 정책 상세는 7장과 연계한다.

---

# 17. config 패키지

`config`에 모든 설정 관련 코드를 몰아넣는다고 설명하지 않는다.

실제 구조를 확인하여 다음을 구분한다.

- DataSource Configuration
- TransactionManager
- MyBatis
- Security
- Web MVC
- TCF
- Timeout
- Bean 등록
- Conditional Bean

그리고 다음을 설명한다.

> 어떤 설정은 Framework에 있어야 하고 어떤 설정은 업무 모듈에 있어야 하는가?

공통 Framework 설정과 업무별 설정을 구분한다.

---

# 18. support 패키지

이 절은 특히 모호해지기 쉽다.

`support = 기타 코드`라고 설명하면 안 된다.

다음을 반드시 설명한다.

- support의 존재 목적
- 어떤 코드까지 허용되는가
- 업무 핵심 로직을 넣어도 되는가
- util과 어떤 차이가 있는가
- helper dump package가 되는 것을 어떻게 막는가

다음 Anti Pattern을 경고한다.

```text
support/
   ├─ CommonUtil
   ├─ Helper
   ├─ EtcUtil
   ├─ DataUtil
   └─ TempUtil
```

`support`가 **쓰레기통 패키지**가 되지 않도록 책임 기준을 설명한다.

---

# 19. Mapper Resource 경로

6.10에서는 반드시 Java Source와 Resource의 관계를 연결한다.

```text
DAO Java Package
        │
        │ namespace
        ▼
Mapper XML
        │
        ▼
Statement ID
```

그리고 실제 Mapper XML 경로를 확인한다.

예를 들어 실제 구조가 다음과 같다면:

```text
src/main/resources/mapper/...
```

어떤 규칙으로 업무별 Mapper가 배치되는지 설명한다.

가상의 경로를 만들지 않는다.

---

# 20. Component Scan은 반드시 Runtime과 연결한다

다음처럼 설명하지 않는다.

> Component Scan은 Component를 검색한다.

실제 Bootstrap 또는 Configuration을 확인하여 다음 흐름을 설명한다.

```text
Application Bootstrap
        ↓
@ComponentScan
        ↓
Base Package
        ↓
Controller / Service / Component
        ↓
Spring Bean 등록
```

그리고 잘못 배치하면 어떤 일이 생기는지도 설명한다.

예:

```text
Package가 Scan 범위 밖
        ↓
Bean 미등록
        ↓
NoSuchBeanDefinitionException
또는
ApplicationContext 시작 실패
```

---

# 21. Mapper Scan도 Runtime 관점으로 설명한다

다음 흐름을 보여준다.

```text
@MapperScan
    ↓
DAO / Mapper Package
    ↓
MyBatis Proxy 생성
    ↓
Spring Bean
    ↓
Service에서 주입
```

실제 PDMG에서 사용하는 Annotation이 별도로 있다면 반드시 확인한다.

예:

- `@MapperScan`
- `@RDWMapper`
- 기타 Custom Annotation

추측하지 않는다.

# 22. Aspect Pointcut와 Package 구조

이 절은 6장의 중요한 심화 부분이다.

AOP가 Package를 기준으로 적용된다면 다음을 설명한다.

```text
Package 구조
      ↓
Pointcut Expression
      ↓
Target Method
      ↓
BizPrePostAspect 등
      ↓
업무 선후처리 실행
```

즉,

> 패키지를 잘못 옮기는 것이 단순 정리 문제가 아니라 AOP가 적용되지 않는 Runtime 장애로 이어질 수 있다.

는 점을 설명한다.

실제 Pointcut Expression을 확인한다.

가상의 Pointcut을 현재 구현처럼 쓰지 않는다.

# 26. 금지 패키지 패턴

6.16은 강하게 작성한다.

다음과 같은 구조가 존재하는지 실제 기준과 비교한다.

```text
common/
util/
utils/
helper/
misc/
etc/
temp/
manager/
processor/
```

무조건 금지라고 일반화하지 않는다.

PDMG 표준에서 허용되는지 확인한다.

지양해야 한다면 이유를 설명한다.

특히 다음 Anti Pattern을 설명한다.

### Anti Pattern 1 — 기능 없는 기술별 Dump

```text
service/
controller/
dao/
```

만 Root에 몰아두고 업무 경계를 잃는 구조.

### Anti Pattern 2 — common 비대화

```text
common/
   └─ 모든 업무 코드
```

### Anti Pattern 3 — support 쓰레기통화

```text
support/
   └─ 분류하기 어려운 모든 코드
```

### Anti Pattern 4 — 역방향 의존

```text
persistence
     ↓
application
```

### Anti Pattern 5 — 다른 업무 내부 구현 직접 참조

```text
업무 A Service
       ↓
업무 B DAO 직접 호출
```

현재 PDMG 규칙과 7장 도메인 호출 정책을 고려하여 설명한다.

# 27. 의존 방향을 반드시 시각화한다

```text
  │

  │
```

```text
DTO ─X─► Service 호출
```

# 29. Package와 Runtime을 연결하라

6장의 가장 중요한 메시지 중 하나다.

패키지는 단순 디렉토리가 아니다.

다음 관계를 독자가 이해해야 한다.

```text

  │
  ├─ Java Compile
  │
  ├─ Import
  │
  ├─ Component Scan
  │
  ├─ Mapper Scan
  │
  ├─ AOP Pointcut
  │
  ├─ Namespace
  │
```

```text
런타임 오류
```

등으로 이어질 수 있음을 실제 근거가 있는 범위에서 설명한다.

# 38. 최종 집필 명령

**폴더 목록을 설명하지 마라.**

**Package가 왜 아키텍처 경계인지 설명하라.**

**논리적 Layer가 실제 Source Tree로 어떻게 구현되는지 보여라.**

**Package와 Component Scan, Mapper Scan, AOP를 연결하라.**

**파일 위치가 Runtime 동작에 어떤 영향을 미치는지 설명하라.**

**잘못된 Package 구조가 어떤 장애를 만드는지도 설명하라.**

**실제 PDMG Source를 확인하지 않은 Package를 현재 표준처럼 만들어내지 마라.**

작성 → Source 검증 → 자체검수 → 부족한 절 보강 → 최종 파일 저장까지 완료하라.
