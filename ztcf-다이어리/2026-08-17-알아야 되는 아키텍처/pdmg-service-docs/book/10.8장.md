# 8장 집필 지시 — HTTP 요청과 표준 전문

8장을 집필하라.

대상 장:

**8장. HTTP 요청과 표준 전문**

이 작업은 기존 전문 문서를 요약하거나 JSON 구조를 나열하는 작업이 아니다.

**「PDMG 애플리케이션 아키텍처와 개발 가이드」의 실제 출판 가능한 8장 본문을 작성하는 작업이다.**

8장의 핵심 질문은 다음이다.

> 7장에서 도메인 간 호출 경계를 결정했다면, 실제 온라인 거래 한 건은 HTTP를 통해 어떤 메시지 구조로 전달되고, PDMG는 그 메시지를 어떻게 해석하여 업무 처리로 연결하는가?

# 2. 사실 판정 우선순위

자료가 다르면 다음 우선순위를 적용한다.

```text
실제 Source / Configuration
        ↓
*-1.md 재분석·검증 문서
        ↓
현재 전문/HTTP 기준 문서
        ↓
기본 문서
        ↓
다이어그램
        ↓
과거 설계안
```

필요하면 다음을 구분한다.

| 구분   | 의미                    |
| ------ | ----------------------- |
| AS-IS  | 현재 실제 구현          |
| 표준   | 신규 개발 기준          |
| Legacy | 과거 또는 호환 구조     |
| TO-BE  | 목표 구조               |
| 예시   | 설명을 위한 가상 데이터 |

**예제 JSON을 실제 운영 전문이라고 오해할 수 있도록 작성하지 마라.**

# 3. 8장의 역할

7장은 다음 질문을 다뤘다.

> 누가 누구를 어떤 경계로 호출할 것인가?

8장은 다음 질문을 다룬다.

> **그 호출을 HTTP 메시지로 어떻게 표현할 것인가?**

즉 다음 전환을 설명한다.

```text
7장

Domain A
   ↓
호출 경계 결정
   ↓
Domain B

        ↓

8장

HTTP Request
   ↓
표준 전문
   ↓
공통 Header
   ↓
Service ID / GUID
   ↓
업무 DTO
   ↓
PDMG Runtime
```

8장의 중심 개념은 **“PDMG 온라인 거래의 메시지 계약(Message Contract)”**이다.

# 4. 9장과의 경계를 지켜라

9장은 Filter와 Spring MVC를 상세히 설명한다.

따라서 8장에서는

- 요청이 HTTP로 들어온다.
- JSON이 전달된다.
- 전문 구조가 존재한다.
- Spring MVC가 JSON을 Java 객체로 변환한다.
- Filter에서 일부 값이 활용될 수 있다.

정도까지 설명한다.

다음 상세는 9장으로 넘긴다.

- DefaultFilter 내부 구현
- Request Body Cache 구현
- Filter Chain
- JWT Token 추출 상세
- MDC 생성
- ServiceContextHolder
- ArgumentResolver 상세
- Filter 종료 정리

즉 8장은 **메시지와 계약**, 9장은 **그 메시지를 Web Runtime이 어떻게 처리하는가**에 집중한다.

# 7. 장 도입부는 실제 온라인 거래로 시작한다

추상적인 HTTP 설명으로 시작하지 마라.

예를 들어 다음 상황으로 시작한다.

> 사용자가 PDMG 화면에서 고객 조회 버튼을 클릭했다고 가정하자. 화면에서는 단순히 조회 버튼 하나를 눌렀지만 서버에는 누가 요청했는지, 어떤 업무인지, 어떤 Service ID인지, 어떤 거래를 수행해야 하는지, 실제 조회 조건이 무엇인지가 하나의 HTTP 요청 안에 담겨 전달되어야 한다.

이를 다음 구조로 확장한다.

```text
사용자
  ↓
Browser
  ↓
pdmg-ui
  ↓
HTTP Request
  ↓
PDMG 표준 전문
  ├─ 공통 영역
  │
  └─ 업무 영역
  ↓
pdmg-service
```

# 8. 8.1 HTTP 호출 구조

단순히 HTTP POST라고 쓰고 끝내지 마라.

실제 구조를 확인하여 다음을 설명한다.

```text
Browser
   ↓
pdmg-ui
   ↓
HTTP
   ↓
Tomcat
   ↓
pdmg-service
   ↓
Spring MVC
```

필요하면 실제 네트워크 구조도 설명하되 확인되지 않은 Apache/L4 구조를 임의 추가하지 않는다.

다음 항목을 설명한다.

- HTTP Method
- URL
- Request Header
- Authorization
- Content-Type
- Request Body
- Response
- HTTP Status

---

# 9. HTTP Header와 PDMG 전문 Header를 혼동하지 않는다

이 부분을 반드시 명확하게 작성한다.

다음은 서로 다른 개념이다.

```text
HTTP Header

Authorization: Bearer ...
Content-Type: application/json
Accept: application/json

             ≠

JSON Body 내부의
hdr_nhnis / sys_comm
```

독자가 다음을 혼동하지 않게 한다.

> HTTP Header라고 부르는 영역과 PDMG 표준 전문 내부의 Header 영역은 동일한 것인가?

아니다.

실제 전문 구조에 맞춰 명확하게 구분한다.

---

# 10. 8.2 표준 요청 전문

표준 전문의 필요성을 충분히 설명한다.

단순 업무 JSON:

```json
{
  "customerNo": "..."
}
```

와 표준 전문을 비교한다.

개념적으로:

```text
Standard Request
    │
    ├─ System/Common Information
    │
    └─ Business Data
```

왜 공통 Envelope가 필요한지 설명한다.

- Service ID
- GUID
- 사용자
- 채널
- 영업점
- 시간
- 거래 식별
- Trace
- 업무 Body

실제 필드만 사실로 기술한다.

---

# 11. 실제 전문 예제를 사용한다

관련 문서와 실제 DTO를 확인하여 **실제 구조에 가까운 하나의 전문 예제**를 장 전체에서 사용한다.

예:

```json
{
  "hdr_nhnis": {
    "...": "..."
  },
  "sys_comm": {
    "...": "..."
  },
  "data": {
    "...": "..."
  }
}
```

단 위 구조도 실제 Source 확인 후 수정한다.

가상의 필드명을 실제 표준 필드처럼 만들지 않는다.

예제 값은 개인정보나 실 운영 Secret을 사용하지 않는다.

# 12. 전문을 Tree 형태로도 설명한다

```text
Request
 │
 ├─ hdr_nhnis
 │    └─ ...
 │
 ├─ sys_comm
 │    ├─ Service ID
 │    ├─ GUID
 │    ├─ User
 │    ├─ Channel
 │    └─ ...
 │
 └─ Business Body
      └─ DTOin
```

실제 구조와 일치하도록 수정한다.

JSON만 보여주지 말고 **각 영역의 책임**을 설명한다.

# 13. 8.3 hdr_nhnis 구조

실제 문서와 DTO를 확인한다.

다음 형식으로 설명한다.

| 필드 | 의미 | 생성 주체 | 필수 여부 | 사용 위치 |
| ---- | ---- | --------- | --------- | --------- |

하지만 모든 필드를 표 하나로 던지고 끝내지 않는다.

중요 필드는 각각 설명한다.

다음 질문에 답한다.

- 누가 값을 생성하는가?
- UI가 생성하는가?
- Framework가 보완하는가?
- 서버에서 신뢰해도 되는 값인가?
- 어느 처리 단계에서 사용되는가?

# 14. 8.4 sys_comm 공통 Header

`sys_comm`은 특히 **거래 실행에 필요한 공통 Context** 관점으로 설명한다.

실제 필드를 확인하여 다음과 연계한다.

```text
sys_comm
   │
   ├─ Service ID
   ├─ GUID
   ├─ 사용자 정보
   ├─ 채널
   ├─ 영업점
   ├─ 거래 시간
   └─ 기타 공통 정보
           ↓
Filter
           ↓
Interceptor
           ↓
ServiceContext
           ↓
TCF
           ↓
업무
```

실제로 사용되지 않는 필드는 사용된다고 단정하지 않는다.

# 15. Client가 보낸 값을 모두 신뢰한다고 쓰지 않는다

중요한 보안 관점이다.

다음 질문을 다룬다.

> 사용자가 JSON의 userId, branchCode 또는 권한 정보를 변경해 보내면 서버는 그대로 믿어도 되는가?

반드시 다음을 구분한다.

```text
Client Provided Data
        ↓
Validation / Authentication
        ↓
Trusted Server Context
```

JWT Claim이나 인증 Context로 재검증하는 항목이 실제 존재하면 설명한다.

없으면 TO-BE로 분리한다.

---

# 16. 8.5 업무 DTO Body

공통 Header와 업무 데이터를 명확히 구분한다.

```text
공통 영역
   ↓
Framework / System에서 사용

업무 DTO
   ↓
Business에서 사용
```

DTO Body에 다음을 넣지 않도록 책임 관점에서 설명한다.

- Framework 내부 제어 값
- 불필요한 인증 정보
- Transaction 제어용 내부 정보

실제 PDMG 계약을 따른다.

---

# 17. DTO를 단순 JSON 필드 묶음으로 설명하지 않는다

다음 흐름으로 설명한다.

```text
JSON
 ↓
Request DTO
 ↓
Facade / Service
 ↓
Business Processing
 ↓
Response DTO
 ↓
JSON
```

DTO 상세 네이밍은 18장에서 다루므로 여기서는 **HTTP 계약에서 DTO가 어떤 역할을 하는지**에 집중한다.

# 18. 8.6 GUID와 Service ID

매우 중요한 절이다.

둘의 차이를 명확히 한다.

```text
Service ID
   =
"무슨 거래인가?"

GUID
   =
"이 요청 한 건은 무엇인가?"
```

그리고 다음 구조로 설명한다.

```text
Request
   │
   ├─ Service ID
   │      ↓
   │   Handler 선택
   │   거래통제
   │   Timeout 정책
   │   로그
   │
   └─ GUID
          ↓
       Trace
       ImageLog
       장애 추적
```

실제 사용처를 Source로 확인한다.

# 19. Service ID와 URL의 차이를 설명한다

특히 TCF ON에서 중요하다.

```text
URL
   =
어느 HTTP Entry Point로 갈 것인가?

Service ID
   =
Entry Point 안에서 어느 업무 거래를 실행할 것인가?
```

TCF ON의 개념적 구조:

```text
POST /online
      +
Service ID
      ↓
TransactionDispatcher
      ↓
Handler
```

실제 구현을 확인하여 수정한다.

# 20. 8.7 TCF ON /online 호출

TCF ON에서 다음을 설명한다.

```text
pdmg-ui
   ↓
POST /online
   ↓
표준 전문
   ↓
Service ID
   ↓
OnlineTransactionController
   ↓
TCF
   ↓
Handler
```

여기에서는 `/online`의 HTTP 계약에 집중한다.

TCF 내부 STF/Dispatcher/ETF 상세는 12장에서 다룬다.

---

# 21. TCF ON에서는 URL만으로 업무를 결정하지 않는 점을 강조한다

일반적인 REST API와 차이를 설명할 필요가 있다.

일반적 패턴:

```text
/customer/search
/customer/register
/customer/update
```

TCF ON 개념:

```text
/online
    +
Service ID
```

왜 이런 방식이 사용되는지 PDMG 설계 근거 범위 안에서 설명한다.

장단점도 다룬다.

# 22. 8.8 TCF OFF 직접 URL 호출

실제 Controller Mapping을 확인한다.

개념적으로:

```text
TCF ON

UI
 ↓
/online
 ↓
Service ID Routing


TCF OFF

UI
 ↓
Business URL
 ↓
Business Controller
```

다음을 비교한다.

| 구분      | TCF ON                | TCF OFF               |
| --------- | --------------------- | --------------------- |
| URL       | `/online` 중심        | 업무 URL              |
| 업무 식별 | Service ID            | URL + 요청            |
| Entry     | TCF Controller        | Business Controller   |
| Handler   | 사용                  | 조건에 따라 미사용    |
| 업무 DTO  | 공통화 가능 여부 확인 | 공통화 가능 여부 확인 |

실제 구조를 확인하여 수정한다.

---

# 23. TCF ON/OFF 전문의 공통성과 차이를 설명한다

가장 중요한 설계 질문 중 하나다.

> TCF OFF라고 해서 업무 DTO까지 완전히 다른 구조를 만들어야 하는가?

가능하면 공통 계약을 유지하는 방향이 어떤 장점이 있는지 설명한다.

다만 이것이 실제 적용인지 권장안인지 반드시 구분한다.

# 24. 8.9 JSON 역직렬화

단순히

> Jackson이 JSON을 DTO로 바꾼다.

라고 끝내지 마라.

다음 흐름을 보여준다.

```text
HTTP Body
    ↓
Servlet Request
    ↓
Spring MVC
    ↓
HttpMessageConverter
    ↓
Jackson ObjectMapper
    ↓
Java DTO
```

실제 구현에서 Custom Resolver/Converter가 있다면 반영한다.

다음 실패 사례도 설명한다.

- JSON Syntax 오류
- Type mismatch
- 필수 필드 누락
- 알 수 없는 Field
- Date/Number 변환 문제
- Validation 실패

단, 예외 매핑 상세는 26장으로 넘긴다.

# 25. Request Body를 여러 번 읽는 문제는 9장과 연결한다

Servlet Request Body는 일반적으로 한 번 소비되는 특성이 있으므로, 실제 `DefaultFilter`에서 Body Cache 처리를 하는지 확인한다.

8장에서는 문제를 소개하고,

> 왜 다음 장에서 Request Body Cache가 필요한가?

정도까지 연결한다.

구현 상세는 9장으로 넘긴다.

# 26. 8.10 표준 응답 전문

Request만 설명하고 Response를 짧게 끝내지 않는다.

다음 구조를 실제 기준으로 설명한다.

```text
Business Result
      ↓
DTOout
      ↓
표준 Response Wrapper
      │
      ├─ Result / Error Information
      └─ Business Data
      ↓
JSON
      ↓
HTTP Response
```

정상 응답과 오류 응답을 각각 제시한다.

---

# 27. 정상 응답과 업무 오류 응답을 비교한다

예:

```text
정상

HTTP 200
  +
업무 성공
  +
DTOout


업무 오류

HTTP Status
  +
표준 오류 코드
  +
오류 메시지
```

실제 PDMG 오류 정책을 확인한다.

HTTP 200으로 모든 업무 오류를 반환하는지, HTTP 상태를 구분하는지 추측하지 않는다.

---

# 28. 8.11 HTTP 상태 코드

**HTTP Status와 업무 Error Code를 반드시 분리해서 설명한다.**

```text
HTTP Status
   =
HTTP 요청 처리 결과

Business Error Code
   =
PDMG 업무/시스템 처리 결과
```

예를 들어 개념적으로:

| 상황        | HTTP 관점 | PDMG 관점    |
| ----------- | --------- | ------------ |
| 정상        | 2xx       | 성공         |
| 잘못된 요청 | 4xx 가능  | 입력 오류    |
| 인증 실패   | 401 가능  | 인증 오류    |
| 인가 실패   | 403 가능  | 권한 오류    |
| 미존재 API  | 404 가능  | Routing 오류 |
| 서버 오류   | 5xx 가능  | 시스템 오류  |

실제 정책을 확인하여 정확하게 작성한다.

---

# 29. HTTP 200 = 업무 성공이라고 단정하지 않는다

반대로

> 업무 오류는 반드시 HTTP 4xx/5xx여야 한다.

라고도 일반화하지 않는다.

PDMG의 실제 표준을 확인한다.

AS-IS와 권장 구조가 다르면 분리한다.

# 31. CORS를 서버 간 HTTP 문제라고 설명하지 않는다

CORS는 기본적으로 **Browser 보안 정책**임을 분명히 한다.

```text
Server → Server HTTP
       ≠
Browser CORS
```

이 차이를 실전 장애 관점에서도 설명한다.

# 32. Authorization Header와 CORS 관계도 확인한다

JWT를 `Authorization` Header로 전달한다면 Preflight와 Allowed Header 설정에 영향을 줄 수 있다.

실제 PDMG 설정에서 이를 확인한다.

확인되지 않은 설정은 현재 적용처럼 쓰지 않는다.

# 42. Anti Pattern을 설명한다

## Anti Pattern 1 — 공통 정보와 업무정보 혼합

```json

  "customerNo": "...",
  "userId": "...",
  "serviceId": "...",
  "branchCode": "...",
  "jwt": "..."
}
```

모든 정보를 평면적으로 업무 DTO에 넣는 구조.

왜 문제가 되는지 설명한다.

---

## Anti Pattern 2 — URL과 Service ID 불일치

```text

Service ID는 거래 B
```

어느 값을 신뢰하는지 실제 정책을 확인한다.

## Anti Pattern 3 — Client 값 무조건 신뢰

```text

     ↓

     ↓

## Anti Pattern 4 — 업무 오류와 HTTP 오류 혼동

```

또는

```text

```

을 무조건 정답으로 일반화하지 않는다.

실제 표준에 따라 설명한다.

## Anti Pattern 5 — 전문 전체 로그 출력

- [ ] Client가 보내는 사용자/권한 정보를 무조건 신뢰하도록 쓰지 않았는가?
- [ ] 민감정보가 예제에 포함되지 않았는가?
- [ ] 실제 하나의 거래를 Request부터 Response까지 추적했는가?
- [ ] 표와 JSON 예제만 나열하고 본문 설명을 생략하지 않았는가?
- [ ] 7장의 도메인 호출 내용을 반복하지 않았는가?
- [ ] 9장의 Filter 구현을 과도하게 침범하지 않았는가?
- [ ] AS-IS / 표준 / TO-BE를 구분했는가?
- [ ] 실제 Source에서 확인하지 않은 필드를 표준처럼 만들지 않았는가?
- [ ] 앞 장보다 설명 밀도가 낮아지지 않았는가?

하나라도 충족하지 못하면 보고만 하지 말고 해당 절을 직접 수정하고 보강한다.

# 48. 8장 최종 완료 기준

8장이 완료되었다는 것은 8.1~8.13에 텍스트가 있다는 뜻이 아니다.

독자가 다음 과제를 스스로 수행할 수 있어야 한다.

> 새로운 PDMG 조회 거래 하나를 HTTP로 호출하려고 한다.
>
> Target URL과 TCF ON/OFF 방식을 판단하고,
> Authorization Header를 구성하고,
> 표준 전문에 필요한 공통정보와 Service ID, GUID를 넣고,
> 업무 DTO를 구성하여 JSON Request를 만들고,
> 서버에서 어떤 방식으로 DTO로 변환되는지 이해하고,
> 정상 응답과 업무 오류, HTTP 오류를 구분하여 처리하라.

독자가 이 과제를 수행할 수 있을 정도로 구체적으로 작성한다.

# 49. 최종 집필 명령

**JSON 필드 목록을 나열하는 장으로 만들지 마라.**

**PDMG 온라인 거래의 메시지 계약을 설명하라.**

**HTTP Header와 전문 Header를 혼동하지 마라.**

**공통정보와 업무정보를 왜 분리하는지 설명하라.**

**Service ID는 거래 식별, GUID는 요청 추적이라는 차이를 명확히 하라.**

**TCF ON의 `/online + Service ID` 구조와 TCF OFF의 직접 URL 구조를 비교하라.**

**JSON이 Java DTO로 변환되는 Runtime 흐름까지 연결하라.**

**HTTP Status와 PDMG 업무 오류 코드를 동일한 개념처럼 설명하지 마라.**

**CORS는 Browser 보안 정책이라는 점을 정확히 설명하라.**

**UI 직접 호출과 Relay 호출을 메시지·인증·GUID·Timeout·오류 전달 관점에서 비교하라.**

**Client가 전달한 사용자 및 권한 관련 값을 무조건 신뢰하는 구조로 설명하지 마라.**

**실제 Source와 원천자료로 확인되지 않은 Header, Field, URL을 현재 표준처럼 만들어내지 마라.**

**Request가 만들어져 Response가 돌아오기까지 실제 거래 하나를 끝까지 추적하라.**

작성 → 원천자료 확인 → 실제 Source 검증 → 본문 집필 → 자체 품질검수 → 부족한 절 보강 → 최종 파일 저장까지 완료하라.
