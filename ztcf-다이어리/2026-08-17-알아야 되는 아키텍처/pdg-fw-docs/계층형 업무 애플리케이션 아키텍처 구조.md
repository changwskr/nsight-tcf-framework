# 6. 계층형 업무 애플리케이션 아키텍처 구조

현재 업로드된 PDMG 소스를 기준으로 보면, **계층형 업무 애플리케이션 아키텍처의 중심은 `pdmg-service`**이며 `pdmg-fw`의 TCF/Dispatcher가 그 앞단을 담당합니다. 프로젝트 기준에서도 Handler → Facade → Service → Rule/DAO → Mapper의 책임 분리를 기본 방향으로 잡고 있습니다.

가장 먼저 알아야 할 핵심은 다음 구조입니다.

```text
TCF / Framework 영역
─────────────────────────────────────────────

HTTP Request
     │
     ▼
OnlineTransactionController
     │
     ▼
TcfFacade
     │
     ├─ STF
     ├─ Timeout
     │
     ▼
TransactionDispatcher
     │ ServiceId
     ▼

업무 Application 영역
─────────────────────────────────────────────

Handler
     │
     ▼
Facade
     │
     ▼
Service
     │
     ├───────────────┐
     │               │
     ▼               ▼
업무규칙          DAO
(Rule 성격)          │
                     ▼
                  Mapper
                     │
                     ▼
                    SQL
                     │
                     ▼
                    DB
```

쉽게 말하면:

> **Handler가 업무를 찾아주고, Facade가 하나의 업무 Use Case를 조립하고, Service가 실제 업무를 처리하며, DAO/Mapper가 DB를 담당한다.**

---

## 1. 실제 PDMG 소스의 계층

현재 `pdmg-service`에서 실제 확인되는 구조는 다음과 같습니다.

```text
pdmg-service
└─ nhnis.mg.co.a
    │
    ├─ application
    │   ├─ controller
    │   │   ├─ mgcoa5530Controller
    │   │   ├─ mgcoa8888Controller
    │   │   ├─ mgcoa9000Controller
    │   │   ├─ mgcoa9001Controller
    │   │   └─ ...
    │   │
    │   ├─ facade
    │   │   ├─ mgcoa5530Facade
    │   │   ├─ mgcoa8888Facade
    │   │   ├─ mgcoa9000Facade
    │   │   ├─ mgcoa9001Facade
    │   │   └─ ...
    │   │
    │   └─ service
    │       ├─ mgcoa5530Service
    │       ├─ mgcoa8888Service
    │       ├─ mgcoa9000Service
    │       ├─ mgcoa9001Service
    │       └─ ...
    │
    ├─ entry
    │   ├─ handler
    │   │   ├─ mgcoa5530Handler
    │   │   ├─ mgcoa8888Handler
    │   │   ├─ mgcoa9000Handler
    │   │   ├─ mgcoa9001Handler
    │   │   └─ ...
    │   │
    │   └─ aspect
    │       ├─ BizPrePostAspect
    │       └─ PdmgBizTxFlowAspect
    │
    ├─ dto
    │   ├─ mgcoa9001S0DTOin
    │   ├─ mgcoa9001S0DTOout
    │   ├─ mgcoa9001C0DTOin
    │   └─ ...
    │
    ├─ persistence
    │   └─ dao
    │       ├─ mgcoa5530DAO
    │       ├─ mgcoa8888DAO
    │       ├─ mgcoa9000DAO
    │       └─ mgcoa9001DAO
    │
    └─ support
        └─ MgTxControlRowSupport


resources
└─ rdw.mg.co.a
    ├─ mgcoa5530-ORA.xml
    ├─ mgcoa8888-ORA.xml
    ├─ mgcoa9000-ORA.xml
    ├─ mgcoa9001-ORA.xml
    └─ ...
```

따라서 **현재 AS-IS에서는 별도의 `rule` 패키지가 명확하게 존재하지 않습니다.**

이 점은 목표 아키텍처와 구분해야 합니다.

```text
[AS-IS]

Handler
 → Facade
 → Service
 → DAO
 → Mapper XML
 → DB


[TO-BE 확장 모델]

Handler
 → Facade
 → Service
     ├─ Rule
     ├─ DAO
     └─ Integration
 → Mapper
 → DB
```

# 2. 실제 거래 하나로 보면 훨씬 쉽습니다

예를 들어 거래통제 프로그램인:

```text
mgcoa9001
```

을 보겠습니다.

ServiceId는 다음과 같이 여러 개가 존재합니다.

```text
mgcoa9001S0   조회
mgcoa9001C0   등록
mgcoa9001U0   수정
mgcoa9001D0   삭제
```

TCF ON일 때 처리 구조는:

```text
Request

  serviceId = mgcoa9001S0

       │
       ▼
TransactionDispatcher
       │
       ▼
mgcoa9001Handler
       │
       ▼
mgcoa9001Facade
       │
       ▼
mgcoa9001Service
       │
       ▼
mgcoa9001DAO
       │
       ▼
mgcoa9001-ORA.xml
       │
       ▼
TB_MG_TX_CONTROL
```

이 구조가 **PDMG 계층형 업무 구조를 이해하는 대표적인 Vertical Slice**입니다.

---

# 3. Handler 계층

실제 `mgcoa9001Handler`는 대략 이런 역할을 합니다.

```java
private static final String S0 = "mgcoa9001S0";
private static final String C0 = "mgcoa9001C0";
private static final String U0 = "mgcoa9001U0";
private static final String D0 = "mgcoa9001D0";
```

그리고:

```text
mgcoa9001S0
     ┐
mgcoa9001C0
     ├──→ mgcoa9001Handler
mgcoa9001U0
     │
mgcoa9001D0
     ┘
```

Handler 내부에서는:

```text
serviceId 확인
      │
      ├─ S0 → facade.mgcoa9001S0()
      ├─ C0 → facade.mgcoa9001C0()
      ├─ U0 → facade.mgcoa9001U0()
      └─ D0 → facade.mgcoa9001D0()
```

처럼 Facade로 보냅니다.

### Handler 책임

```text
ServiceId
    ↓
어느 Use Case를 실행할지 결정
    ↓
Facade 호출
```

따라서 Handler가 하면 안 되는 것은:

```text
Handler → DAO       X
Handler → Mapper    X
Handler → SQL       X
Handler → DB        X
```

입니다.

앞서 살펴본 ServiceId Dispatcher에서도 **Dispatcher는 Handler를 찾고 Handler가 Use Case를 연결하는 구조**가 핵심입니다.

---

# 4. Facade 계층

다음은 `mgcoa9001Facade`입니다.

Facade는 상당히 중요한 계층입니다.

실제 구조는:

```text
Handler

  Object dtoBody
      │
      ▼
Facade
      │
      ├─ DTO 변환
      ├─ Use Case 조립
      ├─ Transaction 선언
      │
      ▼
Service
```

예를 들어 조회:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    readOnly = true
)
public mgcoa9001S0DTOout mgcoa9001S0(Object dtoBody)
```

등록은:

```java
@Transactional(
    transactionManager = "rdwTransactionManager",
    rollbackFor = Exception.class
)
public mgcoa9001C0DTOout mgcoa9001C0(Object dtoBody)
```

형태입니다.

즉 Facade의 의미는:

> **하나의 업무 Use Case를 외부 실행구조와 내부 업무처리 사이에서 조립하는 계층**

입니다.

---

# 5. Facade와 Service를 왜 나누는가

초보자가 가장 많이 묻는 부분입니다.

둘을 합쳐도 프로그램은 돌아갑니다.

하지만 역할이 다릅니다.

```text
Facade
──────────────────────
"이번 거래를 어떻게 조립할 것인가?"


Service
──────────────────────
"실제 업무를 어떻게 처리할 것인가?"
```

예를 들어 고객통합조회가 있다고 합시다.

```text
Facade
 │
 ├─ 고객기본 Service
 ├─ 계좌 Service
 ├─ 상품 Service
 └─ 상담 Service
```

처럼 여러 업무 기능을 묶을 수 있습니다.

즉:

```text
Facade
= Use Case Orchestrator

Service
= Business Logic Executor
```

로 보는 것이 좋습니다.

---

# 6. Service 계층

실제 업무 로직 대부분은 현재 `Service`에 있습니다.

`mgcoa9001Service`를 보면 조회 시:

```text
입력값 검증
   ↓
검색조건 생성
   ↓
Paging 계산
   ↓
DAO Count 조회
   ↓
DAO 목록 조회
   ↓
Map → DTO 변환
   ↓
Output DTO 생성
```

등록은 더 명확합니다.

```text
Input DTO
   │
   ▼
필수값 검증
   │
   ▼
Control Type 검증
   │
   ▼
저장용 데이터 생성
   │
   ▼
기존 데이터 존재?
   │
   ├─ YES → BizException("MP0409")
   │
   ▼
DAO INSERT
   │
   ▼
결과 DTO
```

따라서 Service가 현재 실질적인 **업무 중심 계층**입니다.

---

# 7. Rule 계층은 어떻게 봐야 하는가

여기서 중요한 AS-IS/GAP이 있습니다.

프로젝트 목표 구조는:

```text
Service
 ├─ Rule
 ├─ DAO
 └─ Integration
```

이지만 현재 `pdmg-service`에는 독립적인:

```text
application/rule
domain/rule
```

패키지가 확인되지 않습니다.

현재는 일부 규칙이 Service 안에 있습니다.

예:

```text
Service

├─ 필수값 체크
├─ Y/N 검증
├─ ControlType 검증
├─ 중복여부 판단
├─ 변경사유 검증
└─ DAO 호출
```

그리고 일부 공통 규칙은:

```text
MgTxControlRowSupport
```

같은 Support 클래스로 빠져 있습니다.

따라서:

```text
[AS-IS]

Service
 ├─ 업무 흐름
 ├─ 업무 Rule
 └─ DAO 호출
```

입니다.

규칙이 복잡해지면 다음 구조로 분리하는 것이 좋습니다.

```text
Service
   │
   ├─────────────┐
   ▼             ▼
Rule            DAO
   │             │
업무판단          DB
```

예:

```text
mgcoa9001Service
       │
       ▼
TransactionControlRule
       │
       ├─ 통제유형 검증
       ├─ 대상값 검증
       ├─ 변경가능 검증
       └─ 중복 정책
```

다만 **현재 실제 소스가 이미 그렇게 되어 있다고 설명하면 안 됩니다.**

---

# 8. DAO 계층

현재 DAO는 MyBatis Mapper 인터페이스 역할을 함께 합니다.

예:

```java
@RDWMapper
public interface mgcoa9001DAO {

    List<Map<String,Object>>
        mgcoa9001S0_S0(...);

    int mgcoa9001S0_S0_count(...);

    int mgcoa9001C0_C0(...);

    int mgcoa9001U0_U0(...);

    int mgcoa9001D0_D0(...);
}
```

책임은 아주 명확합니다.

```text
Service
   │
   ▼
DAO Interface
   │
   ▼
MyBatis
   │
   ▼
Mapper XML
```

DAO에서는:

```text
업무 Rule             X
화면 분기             X
ServiceId Routing     X
Transaction 통제      X
```

를 하면 안 됩니다.

---

# 9. Mapper / SQL 계층

DAO 인터페이스의 메서드는 실제 XML에 연결됩니다.

```text
mgcoa9001DAO
       │
       │ namespace
       ▼
mgcoa9001-ORA.xml
```

실제 namespace는:

```xml
<mapper namespace=
 "nhnis.mg.co.a.persistence.dao.mgcoa9001DAO">
```

이고 다음과 같이 연결됩니다.

```text
DAO Method
mgcoa9001S0_S0()
        │
        ▼
<select id="mgcoa9001S0_S0">
        │
        ▼
SELECT ...
FROM TB_MG_TX_CONTROL
```

등록:

```text
mgcoa9001C0_C0()
      ↓
INSERT
      ↓
TB_MG_TX_CONTROL
```

수정:

```text
mgcoa9001U0_U0()
      ↓
UPDATE
      ↓
TB_MG_TX_CONTROL
```

삭제:

```text
mgcoa9001D0_D0()
      ↓
DELETE
      ↓
TB_MG_TX_CONTROL
```

따라서 추적성은:

```text
ServiceId
mgcoa9001U0
      │
      ▼
mgcoa9001Handler
      │
      ▼
mgcoa9001Facade.mgcoa9001U0
      │
      ▼
mgcoa9001Service.mgcoa9001U0
      │
      ▼
mgcoa9001DAO.mgcoa9001U0_U0
      │
      ▼
mgcoa9001-ORA.xml
id=mgcoa9001U0_U0
      │
      ▼
UPDATE TB_MG_TX_CONTROL
```

까지 한 줄로 추적되어야 합니다.

# 10. DTO 계층

PDMG는 거래별 DTO도 명시적으로 분리되어 있습니다.

예:

```text
조회

mgcoa9001S0DTOin
        ↓
Service
        ↓
mgcoa9001S0DTOout
        │
        └─ mgcoa9001S0DTOSub0
```

등록:

```text
mgcoa9001C0DTOin
        ↓
mgcoa9001C0DTOout
```

수정:

```text
mgcoa9001U0DTOin
        ↓
mgcoa9001U0DTOout
```

즉 원칙적으로:

```text
전문
 ↓
DTO
 ↓
업무계층
```

으로 전달하는 것이 좋습니다.

다만 현재 Handler → Facade 입구에서는 `Object dtoBody`를 받아 Facade에서 ObjectMapper로 DTO로 변환하고 있습니다.

---

# 11. 업무 공통 선·후처리는 Service 경계에 있습니다

업무 계층에서 또 하나 알아야 할 부분입니다.

현재:

```text
BizPrePostAspect
```

가 Service 메서드를 Pointcut으로 잡습니다.

따라서 실제 업무 흐름은:

```text
Handler
   ↓
Facade
   ↓
┌──────────────────────┐
│ BizPrePostAspect     │
│      @Before         │
└──────────┬───────────┘
           ▼
         Service
           │
           ▼
          DAO
           │
           ▼
           DB
           │
           ▼
┌──────────────────────┐
│ BizPrePostAspect     │
│  @AfterReturning     │
└──────────────────────┘
```

입니다.

즉 STF와는 역할이 다릅니다.

```text
STF
= 거래 전체 공통 선처리

BizPrePostAspect
= 업무 Service 공통 선·후처리
```

이 구분은 TCF 공통 선·후처리 구조에서도 확인됩니다.

---

# 12. Transaction까지 합치면 전체 계층은 이렇게 됩니다

앞서 살펴본 Timeout/Transaction 구조까지 합치면 PDMG의 핵심 구조가 완성됩니다.

```text
                  HTTP Thread
                       │
                       ▼
            OnlineTransactionController
                       │
                       ▼
                    TCF
                       │
                       ▼
                     STF
                       │
                       ▼
              Timeout Executor
                       │
                 Thread 전환
                       ▼
                 Worker Thread
                       │
                       ▼
              TransactionTemplate
                       │
                  TX BEGIN
                       │
                       ▼
                  Dispatcher
                       │
                  ServiceId
                       ▼
                    Handler
                       │
                       ▼
                    Facade
               @Transactional
                       │
                       ▼
                 Biz Pre AOP
                       │
                       ▼
                    Service
                 ┌─────┴─────┐
                 ▼           ▼
             업무 Rule       DAO
                              │
                              ▼
                           Mapper
                              │
                              ▼
                             SQL
                              │
                              ▼
                             DB
                              │
                       COMMIT / ROLLBACK
```

여기에서 Timeout ON이라면 최외곽 Physical Transaction의 실제 Owner는 앞서 확인한 것처럼 **Worker의 `TransactionTemplate`**입니다.

---

# 13. TCF OFF에서는 구조가 달라집니다

현재 PDMG에는 레거시 호환을 위한 Controller도 존재합니다.

예를 들어 `mgcoa9001Controller`는:

```java
@ConditionalOnProperty(
    name = "nhnis.fw.tcf.enabled",
    havingValue = "false",
    matchIfMissing = true
)
```

입니다.

즉 TCF OFF이면:

```text
HTTP
 ↓
mgcoa9001Controller
 ↓
mgcoa9001Service
 ↓
DAO
 ↓
Mapper
 ↓
DB
```

로 갑니다.

중요합니다.

```text
TCF ON
────────────────────────────────
Controller(TCF)
 → Dispatcher
 → Handler
 → Facade
 → Service
 → DAO


TCF OFF
────────────────────────────────
업무 Controller
 → Service
 → DAO
```

따라서 현재 PDMG에는 **두 개의 실행 경로가 공존**합니다.

---

# 14. 이것은 아키텍처적으로 관리가 필요합니다

TCF ON 구조에서는:

```text
Handler
→ Facade
→ Service
```

인데 TCF OFF에서는:

```text
Controller
→ Service
```

로 Facade가 빠집니다.

그래서 동일한 업무인데도 실행모드에 따라 경계가 달라질 수 있습니다.

```text
             TCF ON
               │
            Handler
               │
            Facade
               │
               ├────────┐
               ▼        │
             Service    │
               ▲        │
               │        │
           Controller   │
               │        │
             TCF OFF ───┘
```

장기적인 최종 구조에서는 가능하면:

```text
TCF ON

Handler
 → Facade
 → Service


TCF OFF

Controller
 → Facade
 → Service
```

처럼 **Facade 아래는 동일하게 유지하는 것이 더 깨끗합니다.**

이 부분은 현재 AS-IS와 목표구조 사이의 개선 후보입니다.

---

# 15. 각 계층을 한 문장으로 기억하면

| 계층        | 한 문장으로 설명                     |
| ----------- | ------------------------------------ |
| Controller  | HTTP 요청을 받는다                   |
| Dispatcher  | ServiceId 담당 Handler를 찾는다      |
| Handler     | ServiceId를 업무 Use Case로 연결한다 |
| **Facade**  | 하나의 Use Case를 조립한다           |
| **Service** | 실제 업무를 처리한다                 |
| **Rule**    | 업무 판단 규칙을 담당한다            |
| **DAO**     | DB 접근을 추상화한다                 |
| **Mapper**  | SQL을 실행한다                       |
| DTO         | 계층 간 데이터를 전달한다            |

그리고 가장 중요한 금지 규칙은:

```text
Controller → DAO        금지
Handler    → DAO        금지
Facade     → Mapper     금지
Service    → Mapper     지양/금지
DAO        → Service    금지
Mapper     → 업무 Rule  금지
```

입니다.

---

# 16. 초보자라면 이렇게 기억하면 됩니다

은행 창구에 비유하면 쉽습니다.

```text
ServiceId
= 업무 번호표

Dispatcher
= 안내 데스크

Handler
= 담당 창구 선택

Facade
= 업무 책임자

Service
= 실제 실무 담당자

Rule
= 업무 규정집

DAO
= DB 담당 직원

Mapper
= 실제 조회/등록 명령

DB
= 금고/원장
```

예를 들어:

```text
"mgcoa9001U0 거래를 해주세요."
          │
          ▼
      Dispatcher
 "9001 담당자는?"
          │
          ▼
  mgcoa9001Handler
 "수정 업무군이군."
          │
          ▼
   mgcoa9001Facade
 "수정 Use Case 실행"
          │
          ▼
   mgcoa9001Service
 "입력 검증·업무 판단"
          │
          ▼
    mgcoa9001DAO
          │
          ▼
  mgcoa9001-ORA.xml
          │
          ▼
UPDATE TB_MG_TX_CONTROL
```

# 17. 현재 구조의 핵심 GAP

실제 소스와 목표 계층 구조를 비교하면 세 가지가 눈에 띕니다.

| 항목        | AS-IS                           | 판단                           |
| ----------- | ------------------------------- | ------------------------------ |
| Handler     | 존재                            | 적절                           |
| Facade      | 존재                            | 적절                           |
| Service     | 존재                            | 적절                           |
| **Rule**    | 독립 계층 없음                  | **분리 후보**                  |
| DAO         | 존재                            | 적절                           |
| Mapper      | XML 존재                        | 적절                           |
| TCF OFF     | Controller → Service            | **Facade 우회**                |
| Transaction | Facade + Service에도 Annotation | Outer TX와 역할 표준화 필요    |
| DTO         | 사용                            | 일부 내부 Map 사용은 개선 가능 |

특히 현재 `mgcoa9001Service`처럼 Service가 커지면:

```text
Service
 ├─ Input Validation
 ├─ Business Rule
 ├─ Paging
 ├─ Data Conversion
 ├─ DAO
 ├─ Error Decision
 └─ Output Assembly
```

까지 모두 담당하게 됩니다.

이 상태에서 업무가 커지면 Service가 비대해질 가능성이 높습니다.

# 18. PDMG의 권장 최종 계층형 구조

제가 PDMG의 최종 표준으로 권장하는 모습은 다음입니다.

```text
                    TCF
                     │
                     ▼
                Dispatcher
                     │
                     ▼
                  Handler
                     │
                     ▼
                  Facade
          Use Case / TX Boundary
                     │
                     ▼
                  Service
           업무 Process 책임
               ┌─────┼────────┐
               │     │        │
               ▼     ▼        ▼
             Rule   DAO   Integration
               │     │        │
          업무판단   │     외부시스템
                     ▼
                  Mapper
                     │
                     ▼
                    SQL
                     │
                     ▼
                    DB
```

패키지도 장기적으로는 다음 정도가 명확합니다.

```text
nhnis.mg.co.a
│
├─ entry
│   └─ handler
│
├─ application
│   ├─ facade
│   └─ service
│
├─ domain
│   └─ rule
│
├─ persistence
│   └─ dao
│
├─ integration
│
└─ dto
```

## 최종 핵심

**PDMG 계층형 업무 애플리케이션 아키텍처의 기준선은 다음 한 줄로 기억하면 됩니다.**

```text
ServiceId
   ↓
Dispatcher
   ↓
Handler
   ↓
Facade
   ↓
Service
   ├─ Rule
   ├─ DAO → Mapper → SQL → DB
   └─ Integration
```

다만 **현재 실제 PDMG AS-IS는 `Rule` 계층이 별도 패키지로 분리되어 있지 않고 주로 Service 내부에 존재하며, TCF OFF에서는 Controller가 Facade를 거치지 않고 Service를 직접 호출하는 호환 경로가 존재합니다.**

따라서 이 6번 아키텍처에서 가장 중요한 설계 원칙은 **“계층을 많이 만드는 것”이 아니라, 각 계층이 자기 책임만 갖게 만드는 것**입니다.
