PDMG를 이해하려면 모든 클래스를 외우는 것보다 **“요청이 어디서 시작해서 어디서 끝나는가”와 “공통 통제가 어디서 이루어지는가”**를 먼저 알아야 합니다. 지금 기준인 `pdmg-ui / pdmg-jwt / pdmg-fw / pdmg-service / pdmg-om`만 놓고 보면, 아래 **8개 아키텍처**를 반드시 이해하는 것이 좋습니다.

### 1. 가장 먼저: 전체 온라인 거래 아키텍처

이게 PDMG의 뼈대입니다.

```text
[pdmg-ui]
    │
    │ HTTP / JSON
    ▼
[pdmg-service]
    │
    ▼
[pdmg-fw]
 DefaultFilter
    │
 ServicePreventionInterceptor
    │
 OnlineTransactionController
    │
    ▼
   TCF
    │
   STF
    │
 Timeout
    │
 Transaction
    │
 Dispatcher
    ▼
[pdmg-service]
 Handler
    │
 Facade
    │
 Service
    │
 Rule
    │
 DAO
    │
 Mapper
    ▼
   DB
```

이 구조를 모르면 이후 Timeout, Transaction, JWT, ServiceId를 따로 배워도 서로 연결되지 않습니다.

---

### 2. ServiceId 기반 Dispatcher 아키텍처

PDMG에서 상당히 중요한 개념입니다.

예를 들어:

```text
mgcoa5530S0
```

라는 ServiceId가 들어오면:

```text
ServiceId
   ↓
TransactionDispatcher
   ↓
mgcoa5530Handler
   ↓
Facade
   ↓
Service
```

로 연결됩니다.

즉 PDMG에서는 URL이나 Controller가 업무 프로그램을 직접 결정하는 것이 아니라 **ServiceId가 업무 실행의 중심키**라고 이해하는 것이 중요합니다.

```text
화면 이벤트
   ↓
ServiceId
   ↓
Handler
   ↓
Facade
   ↓
Service
   ↓
DAO / Mapper
```

---

### 3. TCF 공통 선·후처리 아키텍처

업무 개발자가 만든 Handler가 바로 실행되는 것이 아닙니다.

그 전에 `pdmg-fw`가 거래를 통제합니다.

```text
Request
  │
  ▼
DefaultFilter
  │
  ▼
ServicePreventionInterceptor
  │
  ▼
TCF
  │
  ├─ STF
  │   ├─ 공통검증
  │   ├─ 거래통제
  │   ├─ Timeout 정책
  │   └─ 거래로그
  │
  ▼
Dispatcher
  │
  ▼
업무
  │
  ▼
ETF / 후처리
```

쉽게 말하면:

> **업무 프로그램 앞뒤를 Framework가 감싸고 있는 구조**

입니다.

---

### 4. Transaction + Timeout 아키텍처

PDMG에서 특히 중요합니다.

TCF ON + Timeout ON인 경우 기본적으로 이해해야 할 구조는:

```text
HTTP Thread
    │
    ▼
Timeout Executor
    │
    ▼
Worker Thread
    │
    ▼
TransactionTemplate
    │
    ├─ TX BEGIN
    │
    ▼
Dispatcher
    ↓
Handler
    ↓
Facade
    ↓
Service
    ↓
DAO / Mapper
    ↓
DB
    │
    ├─ 정상 → COMMIT
    │
    └─ 오류 → ROLLBACK
```

그리고 Facade의:

```java
@Transactional
```

은 일반적으로 이미 존재하는 외부 Transaction에 참여하게 됩니다.

따라서 PDMG Transaction에서 꼭 이해할 질문은:

```text
누가 실제 Physical Transaction을 시작하는가?
          ↓
Timeout Executor / TransactionTemplate

@Transactional은 무엇을 하는가?
          ↓
이미 만들어진 Transaction에 참여
```

입니다.

이 부분은 PDMG를 이해하는 핵심 축 중 하나입니다.

---

### 5. JWT 인증 아키텍처

방금 살펴본 구조입니다.

```text
pdmg-ui
   │
   │ ID/PW
   ▼
pdmg-jwt
   │
   ├─ 사용자 인증
   ├─ Access Token
   └─ Refresh Token
   │
   │ RS256
   ▼
pdmg-ui
   │
   │ Authorization: Bearer JWT
   ▼
pdmg-service
   │
   ▼
pdmg-fw
ServicePreventionInterceptor
   │
JwtProvider
   │
   ├─ JWKS
   ├─ RSA Public Key
   ├─ Signature
   └─ exp
   │
   ▼
인증 성공
   │
   ▼
TCF
```

여기서 반드시 기억할 것은:

```text
Private Key
= pdmg-jwt에서 서명

Public Key
= pdmg-fw에서 검증
```

입니다.

또 **JWT 인증 성공과 업무 권한 성공은 다른 문제**입니다.

---

### 6. 계층형 업무 애플리케이션 아키텍처

`pdmg-service`에서 개발자가 가장 자주 접하는 구조입니다.

```text
Handler
   │
   ▼
Facade
   │
   ▼
Service
   ├──────────┐
   ▼          ▼
 Rule        DAO
              │
              ▼
            Mapper
              │
              ▼
              DB
```

책임을 간단히 보면:

| 계층    | 반드시 알아야 할 책임           |
| ------- | ------------------------------- |
| Handler | ServiceId와 Use Case 연결       |
| Facade  | Use Case 조립, Transaction 경계 |
| Service | 업무 처리                       |
| Rule    | 업무 규칙                       |
| DAO     | DB 접근 추상화                  |
| Mapper  | 실제 SQL                        |

특히 금지해야 할 구조는:

```text
Handler → DAO       X
Controller → DAO    X
Controller → SQL    X
```

입니다.

---

### 7. 표준전문 + Context 아키텍처

UI가 단순 JSON Body만 보내는 것이 아닙니다.

```text
Request
 ├─ hdr_nhnis
 │    └─ sys_comm
 │         ├─ GUID
 │         ├─ ServiceId
 │         ├─ 사용자
 │         ├─ 시스템
 │         └─ 거래정보
 │
 └─ dto
      └─ 업무 데이터
```

그리고 `DefaultFilter`가 이 정보를 읽어 공통 Context로 만듭니다.

```text
표준전문
   ↓
DefaultFilter
   ↓
ServiceContext
   ↓
TCF / Log / Timeout / Dispatcher
```

따라서 PDMG를 공부할 때 DTO만 보면 절반만 보는 것입니다. **Header + DTO를 하나의 거래 전문으로 이해해야 합니다.**

---

### 8. 운영·통제 아키텍처

마지막으로 `pdmg-om`이 담당해야 하는 영역입니다.

현재 제공된 소스에서는 `pdmg-om` 구현을 확인하지 못했으므로 세부 AS-IS는 확정할 수 없지만, PDMG 전체에서는 다음 정보를 운영 기준정보로 관리해야 합니다.

```text
ServiceId
   │
   ├─ Timeout
   ├─ 거래통제
   ├─ 사용자/권한
   ├─ 오류코드
   ├─ 환경설정
   ├─ 거래로그
   └─ Runtime 상태
```

궁극적으로는:

```text
어느 ServiceId가 느린가?
        ↓
어느 Thread인가?
        ↓
어느 SQL인가?
        ↓
Transaction은 어디까지 진행됐나?
        ↓
Timeout이 왜 발생했나?
```

를 운영자가 추적할 수 있어야 합니다.

---

## 우선순위를 정하면

처음부터 전부 공부할 필요는 없습니다. 저는 다음 순서를 권합니다.

```text
1. 전체 온라인 거래 흐름
        ↓
2. ServiceId / Dispatcher
        ↓
3. Handler → Facade → Service → DAO
        ↓
4. TCF / STF
        ↓
5. Transaction + Timeout
        ↓
6. JWT
        ↓
7. 표준전문 / Context
        ↓
8. OM / 운영통제
```

특히 **처음 5개가 PDMG 핵심 아키텍처**입니다.

```text
             PDMG 핵심 5대 구조

                   ServiceId
                      │
                      ▼
             ┌─────────────────┐
             │       TCF       │
             └───────┬─────────┘
                     │
             Timeout / TX
                     │
                     ▼
                  Handler
                     │
                  Facade
                     │
                  Service
                     │
               DAO / Mapper
```

한 문장으로 요약하면 **PDMG에서 가장 먼저 알아야 하는 아키텍처는 `ServiceId를 중심으로 TCF가 거래를 통제하고, Timeout/Transaction 안에서 Dispatcher가 Handler를 찾아 Handler → Facade → Service → DAO/Mapper로 업무를 실행하는 구조`**입니다.

JWT는 이 핵심 거래 구조 **앞에서 사용자를 인증하는 보안 아키텍처**라고 위치를 잡으면 전체 PDMG가 훨씬 쉽게 이해됩니다.
