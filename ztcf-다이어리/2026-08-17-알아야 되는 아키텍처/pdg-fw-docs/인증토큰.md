NSIGHT/PDMG 관점에서 **JWT 토큰 인증 처리 구조**는 크게 **① 로그인·토큰 발급, ② 요청 시 토큰 검증, ③ 업무 권한 검증, ④ 만료·재발급**으로 나누어 이해하면 됩니다. 현재 NSIGHT 기준에서는 **Private Key는 토큰 발급 주체만 사용하고, Gateway 또는 업무 WAR는 Public Key/JWKS로 JWT를 검증**하는 구조가 기본 방향입니다.

### 1. 전체 구조

```text
┌──────────────────────────────────────────────────────────────┐
│                     ① 로그인 / 인증                          │
└──────────────────────────────────────────────────────────────┘

[사용자 / Browser]
        │
        │ 로그인 / SSO
        ▼
[SSO / IdP]
        │
        │ 인증 성공
        ▼
[Token 발급 시스템]
        │
        │ Private Key
        │ RS256 서명
        ▼
 ┌──────────────────────┐
 │ Access Token (JWT)   │
 │ Refresh Token        │
 └──────────────────────┘
        │
        ▼
     Browser


┌──────────────────────────────────────────────────────────────┐
│                 ② 업무 요청 / JWT 인증                      │
└──────────────────────────────────────────────────────────────┘

Browser
   │
   │ Authorization: Bearer <JWT>
   ▼
Apache / Gateway
   │
   ▼
JWT Authentication Filter
   │
   ├─ 토큰 존재 확인
   ├─ 서명 검증
   ├─ issuer 검증
   ├─ audience 검증
   ├─ exp 검증
   ├─ 필요 시 blacklist / logout 상태 확인
   └─ 사용자 인증정보 생성
          │
          ▼
     SecurityContext
          │
          ▼
         TCF
          │
          ▼
         STF
          │
          ├─ 사용자 문맥 확인
          ├─ ServiceId 확인
          ├─ 사용자/권한 확인
          └─ 거래통제
          │
          ▼
      Dispatcher
          │
          ▼
       Handler
          │
          ▼
       Facade
          │
          ▼
       Service
```

핵심은 **JWT 인증과 업무 권한을 동일하게 생각하면 안 된다는 것**입니다.

```text
JWT 검증
   =
"이 토큰이 정상적인 인증서버에서 발급된
 위변조되지 않은 토큰인가?"

          ↓

업무 권한 검증
   =
"이 사용자가 이 ServiceId를
 실행해도 되는가?"
```

### 2. JWT를 발급하는 구조

가장 중요한 부분은 **Private Key**입니다.

```text
                  Token Server
                       │
             ┌─────────┴─────────┐
             │                   │
       사용자 인증정보       Private Key
             │                   │
             └─────────┬─────────┘
                       ▼
                JWT Payload 생성

                {
                  sub: "user001",
                  iss: "NSIGHT-AUTH",
                  aud: "NSIGHT",
                  exp: ...,
                  roles: [...],
                  jti: ...
                }

                       │
                       ▼
                    RS256
                       │
                       ▼
                  JWT Access Token
```

예를 들면 토큰 내부에는 개념적으로 다음 정보가 들어갑니다.

```text
Header
─────────────────────────
alg = RS256
kid = NSIGHT-KEY-001


Payload
─────────────────────────
sub      = 사용자 ID
iss      = 발급자
aud      = 사용 대상
iat      = 발급시간
exp      = 만료시간
jti      = Token 고유 ID
roles    = 권한정보


Signature
─────────────────────────
Private Key로 생성
```

**Private Key는 Token 발급 시스템 밖으로 배포하면 안 됩니다.** 브라우저가 가져서도 안 됩니다. 반대로 검증용 Public Key는 Gateway나 각 업무 WAR에 배포할 수 있습니다.

### 3. 업무 요청이 들어왔을 때

예를 들어 사용자가 고객조회 서비스를 호출한다고 하겠습니다.

```text
POST /api/online

Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
```

처리는 다음과 같습니다.

```text
Browser
   │
   │ JWT
   ▼
┌───────────────────────┐
│ Gateway / JWT Filter  │
└───────────┬───────────┘
            │
            ├─ ① JWT 형식 정상?
            ├─ ② Signature 정상?
            ├─ ③ exp 만료 안 됨?
            ├─ ④ issuer 정상?
            ├─ ⑤ audience 정상?
            └─ ⑥ 필요 시 Token 상태 정상?
                    │
             ┌──────┴──────┐
             │             │
            실패           성공
             │             │
             ▼             ▼
       401 Unauthorized  사용자정보 추출
                           │
                           ▼
                    Authentication
                           │
                           ▼
                     SecurityContext
                           │
                           ▼
                          TCF
```

여기서 **Public Key가 어떻게 위변조를 알아내는가**가 핵심입니다.

```text
Token Server

Payload
   │
   + Private Key
   │
   ▼
Signature 생성
   │
   ▼
JWT


업무 서버

JWT
 │
 ├─ Payload
 └─ Signature
        │
        + Public Key
        │
        ▼
   Signature 검증
```

중간에서 공격자가

```text
role = USER
```

를

```text
role = ADMIN
```

으로 바꾸면 Signature와 내용이 더 이상 일치하지 않으므로 검증에 실패합니다.

```text
변조 JWT
   ↓
Public Key 검증
   ↓
Signature 불일치
   ↓
401 Unauthorized
```

### 4. NSIGHT에서는 JWT 검증 뒤에 TCF/STF 검증이 이어지는 게 중요합니다

JWT가 정상이라고 바로 Handler를 호출하는 구조로 만들면 부족합니다.

```text
JWT Authentication
       │
       ▼
      TCF
       │
       ▼
      STF
       │
       ├─ User Context
       ├─ ServiceId
       ├─ Authorization
       ├─ 거래통제
       ├─ Timeout Policy
       ├─ 중복거래
       └─ Transaction Log
       │
       ▼
   Dispatcher
       │
       ▼
    Handler
```

즉 책임을 다음과 같이 나누는 것이 좋습니다.

| 영역               | 책임                               |
| ------------------ | ---------------------------------- |
| SSO/IdP            | 사용자 본인 인증                   |
| Token Server       | Access/Refresh Token 발급          |
| Private Key/KMS    | JWT Signature 생성                 |
| Gateway/JWT Filter | JWT 서명·만료·issuer·audience 검증 |
| SecurityContext    | 인증된 사용자 정보 보관            |
| TCF/STF            | 거래 실행 전 공통 통제             |
| Authorization      | ServiceId에 대한 업무 권한 검증    |
| Handler 이후       | 실제 업무 수행                     |

### 5. Gateway가 있느냐 없느냐에 따라 두 구조가 가능합니다

**A안 — Gateway 중앙검증**은 다음과 같습니다.

```text
Browser
  │ JWT
  ▼
Gateway
  │
  ├─ JWT 검증
  └─ 인증 Context 생성
       │
       ▼
    업무 WAR
       │
       ▼
      TCF
```

중앙 관리가 쉽다는 장점이 있습니다.

하지만 NSIGHT에서 특히 주의해야 할 부분은:

```text
Gateway 우회
      │
      ▼
업무 WAR 직접 접근
```

입니다.

그래서 보안 요구 수준에 따라 업무 WAR에도 최소한의 토큰 검증 방어를 둘 수 있습니다.

**B안 — 업무 WAR 자체 검증**은 다음과 같습니다.

```text
Browser
  │ JWT
  ▼
Apache
  │
  ▼
업무 WAR
  │
  ▼
JWT Filter
  │
  ▼
TCF
```

프로젝트 기준에서도 **Gateway가 없는 경우 업무 WAR의 공통 JWT Filter에서 검증**하는 원칙을 두고 있습니다.

### 6. Access Token이 만료되면

```text
업무 API 호출
     │
     ▼
Access Token
     │
     ├──── 유효 ─────────────→ 업무처리
     │
     └──── 만료
              │
              ▼
          401 응답
              │
              ▼
       Refresh Token 제출
              │
              ▼
        Token Server
              │
        Refresh 검증
              │
        ┌─────┴─────┐
        │           │
       정상         비정상
        │           │
        ▼           ▼
 새 Access Token   재로그인
```

Refresh Token은 Access Token보다 훨씬 민감하게 관리해야 합니다.

### 7. NSIGHT에 적용한 최종 권장 구조

```text
                        [SSO / IdP]
                             │
                      사용자 본인인증
                             │
                             ▼
                    ┌─────────────────┐
                    │ Token Service   │
                    │                 │
                    │ Private Key/KMS │
                    └────────┬────────┘
                             │
                      RS256 JWT 발급
                             │
                             ▼
                         Browser
                             │
                 Authorization: Bearer
                             │
                             ▼
                         Apache
                             │
                             ▼
                         Gateway
                             │
                    ┌────────┴────────┐
                    │ JWT Filter      │
                    │                │
                    │ Signature      │
                    │ Expiration     │
                    │ Issuer         │
                    │ Audience       │
                    └────────┬────────┘
                             │
                      Authentication
                             │
                             ▼
                    SecurityContext
                             │
                             ▼
                           TCF
                             │
                             ▼
                           STF
                  ┌──────────┼──────────┐
                  │          │          │
               인증문맥    권한검증    거래통제
                  │          │          │
                  └──────────┼──────────┘
                             ▼
                         Dispatcher
                             │
                             ▼
                          Handler
                             │
                             ▼
                          Facade
                             │
                             ▼
                          Service
                             │
                    ┌────────┴────────┐
                    ▼                 ▼
                  DAO              외부연계
                    │
                  Mapper
                    │
                    ▼
                    DB
```

따라서 **NSIGHT의 JWT 구조를 한 문장으로 정리하면**:

> **SSO가 사용자를 인증하고 → Token 시스템이 Private Key로 JWT를 발급하며 → Gateway/업무 WAR가 Public Key로 위변조와 유효기간을 검증하고 → TCF/STF가 ServiceId 기반 업무 권한과 거래통제를 수행한 뒤 → Handler/Facade/Service를 실행하는 구조**입니다.

그리고 여기서 특히 중요한 원칙은 **`JWT 인증 성공 ≠ 업무 실행 권한 성공`**이라는 점입니다. JWT는 신원을 증명하는 1차 관문이고, 실제 `SV.Customer.xxx` 같은 ServiceId 실행 권한은 TCF/STF 영역에서 별도로 통제하는 것이 NSIGHT 구조에 더 적합합니다.
