# 도메인 정의 아키텍처 구조

현재 **PDMG 기준**에서 도메인은 단순히 `https://xxx.com` 같은 인터넷 도메인만 의미하지 않습니다. 아키텍처에서는 **네트워크 도메인 → 애플리케이션 → 업무 도메인 → 프로그램 → ServiceId → 실행 계층**을 하나의 체계로 연결해서 보는 것이 적절합니다.

PDMG의 핵심은 **URL 자체가 업무를 결정하는 구조보다 `ServiceId`가 실제 거래의 논리적 주소가 되는 구조**입니다. 현재 Dispatcher 역시 ServiceId를 기준으로 Handler와 Use Case를 선택합니다.

---

## 1. 전체 도메인 아키텍처

```text
                         [NETWORK DOMAIN]
                    https://<service-domain>
                              │
                              ▼
                    GSLB / L4 / Apache
                              │
                              ▼
                         Tomcat
                              │
                              ▼
                    pdmg-service.war
                              │
               ┌──────────────┴──────────────┐
               │                             │
               ▼                             ▼
       [TCF 공통 진입]                 [Legacy/직접 진입]
          POST /online                  POST /{serviceId}
               │                             │
               └──────────────┬──────────────┘
                              ▼
                       ServiceId 결정
                              │
                              ▼
                     mgcoa9000S0
                              │
                 ┌────────────┼────────────┐
                 │            │            │
                 ▼            ▼            ▼
               MG            CO            A
             대그룹          업무         세부업무
                 │
                 ▼
                       Program 9000
                              │
                              ▼
                         거래 S0
                              │
                              ▼
                 TransactionDispatcher
                              │
                              ▼
                     mgcoa9000Handler
                              │
                              ▼
                      mgcoa9000Facade
                              │
                              ▼
                      mgcoa9000Service
                              │
                              ▼
                        mgcoa9000DAO
                              │
                              ▼
                     mgcoa9000-ORA.xml
                              │
                              ▼
                             DB
```

PDMG 전체 실행구조에서도 `pdmg-fw`가 HTTP 공통 처리와 TCF를 담당하고, `pdmg-service`가 Handler 이후의 업무 계층을 담당하는 구조입니다.

---

# 2. 도메인은 5단계로 정의하는 것이 좋습니다

| 계층 | 도메인             | 예                         | 역할                 |
| ---- | ------------------ | -------------------------- | -------------------- |
| L1   | Network Domain     | `https://<service-domain>` | 시스템 외부 접속주소 |
| L2   | Application Domain | `pdmg-service`             | WAR/Application 경계 |
| L3   | Business Domain    | `MG / CO / A`              | 업무 소유영역        |
| L4   | Program Domain     | `mgcoa9000`                | 프로그램 단위        |
| L5   | Transaction Domain | `mgcoa9000S0`              | 실제 거래 ServiceId  |

핵심 관계는 다음입니다.

```text
Network Domain
      ↓
Application
      ↓
Business Domain
      ↓
Program
      ↓
ServiceId
      ↓
Runtime Execution
```

즉 **ServiceId가 가장 작은 실행 가능한 도메인 단위**라고 볼 수 있습니다.

---

# 3. 업무 도메인 정의

PDMG의 업무 도메인은 다음과 같은 계층입니다.

```text
대그룹
 MG
 │
 ▼
업무
 CO
 │
 ▼
세부업무
 A
 │
 ▼
프로그램
 9000
 │
 ▼
거래
 S0
```

이를 합치면:

```text
MG + CO + A + 9000 + S0
 │    │    │      │     │
 │    │    │      │     └─ 거래
 │    │    │      └─────── 프로그램
 │    │    └────────────── 세부업무
 │    └─────────────────── 업무
 └──────────────────────── 대그룹

              ↓

         mgcoa9000S0
```

이 분류체계는 Java 패키지와 Mapper까지 같은 축으로 연결됩니다.

```text
업무 도메인
MG / CO / A

     │
     ├──────────────────────────┐
     ▼                          ▼

Java                       Mapper Resource
nhnis.mg.co.a              rdw.mg.co.a

     │                          │
     ▼                          ▼
Handler/Facade/...         mgcoa9000-ORA.xml
```

# 4. Program Domain과 ServiceId Domain을 구분해야 합니다

예를 들어:

```text
mgcoa9000
```

은 **Program Domain**입니다.

하나의 프로그램 안에 여러 거래가 있습니다.

```text
                     mgcoa9000
                    Program Domain
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼

 mgcoa9000S0       mgcoa9000C0       mgcoa9000U0
     조회               등록               수정
        │
        └────────────────┬────────────────┘
                         ▼
                  ServiceId Domain
```

따라서:

```text
Program ID
mgcoa9000
    ↓
클래스 / 파일 단위

ServiceId
mgcoa9000S0
    ↓
실제 거래 / 실행 단위
```

라고 구분하는 것이 좋습니다. PDMG 네이밍 체계도 프로그램과 ServiceId를 별도로 관리하면서 클래스·DTO·메서드·SQL까지 추적하도록 되어 있습니다.

# 5. URL 호출 아키텍처 — TCF ON

현재 `pdmg-service` 설정은 **TCF ON**을 기본 실행구조로 잡고 있으므로, 구조적으로 가장 중요한 호출 방식은 공통 TCF Endpoint입니다.

```text
Client
   │
   │ POST
   ▼
/online
   │
   │ hdr_nhnis.sys_comm.rms_svc_c
   │ = mgcoa9000S0
   ▼
OnlineTransactionController
   │
   ▼
TcfFacade
   │
   ▼
STF
   │
   ▼
Timeout Executor
   │
   ▼
Dispatcher
   │
   │ serviceId
   ▼
mgcoa9000Handler
```

즉 외부 호출을 개념적으로 보면:

```text
POST https://<domain>/<context>/online
```

그리고 전문에서:

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "rms_svc_c": "mgcoa9000S0"
    }
  },
  "dto": {
    "...": "..."
  }
}
```

처럼 처리합니다.

표준전문 역시 `hdr_nhnis`의 공통정보와 업무 `dto`를 분리하는 구조입니다.

---

# 6. 공통 URL을 사용하는 이유

일반 REST 방식은 URL이 업무를 표현합니다.

```text
/customer/search
/customer/create
/customer/update
/product/search
```

반면 PDMG/TCF 방식은:

```text
POST /online
```

이라는 공통 입구를 두고,

```text
ServiceId = mgcoa9000S0
```

가 업무를 결정합니다.

```text
              /online
                 │
                 ▼
             ServiceId
                 │
        ┌────────┼─────────┐
        │        │         │
        ▼        ▼         ▼
mgcoa9000S0  9001S0    5530S0
        │        │         │
        ▼        ▼         ▼
 Handler A   Handler B  Handler C
```

따라서 **URL은 물리적 진입 주소이고 ServiceId는 논리적 업무 주소**입니다. 이 원칙이 ServiceId 기반 Dispatcher의 핵심입니다.

---

# 7. 현재 소스는 3가지 호출 형태를 지원합니다

현재 `OnlineTransactionController` 기준으로는 구조적으로 다음 진입형태가 존재합니다.

```text
① 공통 URL
POST /online
Header ServiceId 사용

② 업무코드 포함 공통 URL
POST /{businessCode}/online
Header ServiceId 사용

③ ServiceId Path
POST /{serviceId}
```

그리고 TCF를 사용하지 않는 레거시 업무 Controller에는 다음과 같은 직접 Endpoint도 존재합니다.

```text
POST /mgcoa5530S0

POST /mgcoa8888S0
POST /mgcoa8888D0

POST /mgcoa9000S0
POST /mgcoa9000C0
POST /mgcoa9000U0
POST /mgcoa9000D0
```

따라서 현재 구조를 AS-IS와 TO-BE로 나누는 것이 중요합니다.

```text
[AS-IS]

/online
/{businessCode}/online
/{serviceId}
업무 Controller 직접 URL

       모두 존재 가능


[권장 TO-BE]

공통 Transaction Endpoint
        ↓
     ServiceId
        ↓
    Dispatcher
        ↓
     Handler
```

# 9. 특히 수정해야 할 현재 GAP

현재 자료에서 중요한 문제가 하나 있습니다.

ServiceId 결정 우선순위가:

```text
1. ServiceContext / Header rms_svc_c
2. 요청 JSON의 rms_svc_c
3. URL Path ServiceId
```

형태로 되어 있습니다.

그래서 다음 요청은 위험합니다.

```text
POST /mgcoa9000S0

Header
rms_svc_c = mgcoa9000D0
```

URL은 조회인데 Header는 삭제입니다.

현재 Header가 우선하면:

```text
URL
mgcoa9000S0
      │
      │ 불일치
      ▼
Header
mgcoa9000D0
      │
      ▼
Dispatcher
      │
      ▼
DELETE Use Case
```

처럼 될 수 있습니다.

따라서 Architecture Rule은 명확해야 합니다.

```text
R-DOMAIN-001

ServiceId Identity는
한 거래에서 하나만 존재해야 한다.
```

그리고 Path 방식도 유지한다면:

```text
Path ServiceId
      =
Header ServiceId
      =
Context ServiceId
```

를 강제 검증해야 합니다.

더 좋은 방향은 **업무 Identity를 Header의 ServiceId 하나로 표준화하고 `/online`을 공통 Endpoint로 사용하는 것**입니다.

# 10. 최종 도메인 표준

PDMG의 도메인 아키텍처를 한 줄로 정리하면 다음과 같습니다.

```text
Physical Domain
https://<domain>
        │
        ▼
Application Context
        │
        ▼
POST /online
        │
        ▼
Logical Domain
ServiceId = mgcoa9000S0
        │
        ▼
Business Domain
MG / CO / A
        │
        ▼
Program Domain
mgcoa9000
        │
        ▼
Use Case
S0
        │
        ▼
Dispatcher
        │
        ▼
Handler
        │
        ▼
Facade
        │
        ▼
Service
        │
        ▼
DAO → Mapper → DB
```

따라서 **도메인은 URL에 업무 의미를 반복해서 넣는 체계가 아니라, `ServiceId`를 중심으로 업무분류·패키지·소스·SQL·운영통제를 연결하는 논리적 아키텍처**로 정의하는 것이 PDMG 구조에 가장 잘 맞습니다. `pdmg-fw`의 commons가 HTTP/Context/JWT 등의 시스템 공통 계층을 담당하고 TCF가 이 ServiceId 거래를 실제로 실행시키는 구조입니다.

**권장 표준은 `Domain → Application → /online → ServiceId → Dispatcher → Handler → Facade → Service`입니다.**
