# 8. 운영·통제 아키텍처 구조

앞의 1~7장이 **“온라인 거래가 어떻게 실행되는가”**를 설명했다면, 8장은 그 거래를 **운영자가 어떻게 통제하고, 현재 상태를 어떻게 관찰하며, 장애 발생 시 어떤 ServiceId가 원인인지 추적하는가**를 설명하는 구조입니다.

현재 PDMG 실제 소스를 기준으로 하면 운영·통제는 별도의 한 모듈에만 존재하지 않습니다. **`pdmg-fw`가 실행 시점의 통제·관측 엔진**, **`pdmg-service`가 관리·진단 ServiceId**, **`pdmg-ui`가 운영자 화면**을 담당하는 형태입니다. 현재 ZIP에는 독립적인 `pdmg-om` 모듈이 없으므로, 여기서는 현재 구현된 AS-IS와 향후 OM으로 통합할 TO-BE를 명확히 나누겠습니다. 이는 프로젝트의 “실제 소스 우선, AS-IS와 TO-BE 구분” 원칙에도 맞습니다.

---

## 8.1 전체 Big Picture

운영·통제 아키텍처는 크게 **Control Plane**과 **Runtime/Data Plane** 두 축으로 이해하면 쉽습니다.

```text
                         PDMG 운영·통제 아키텍처

 ┌──────────────────────────────────────────────────────────────┐
 │                   CONTROL PLANE                              │
 │                   운영자 관리 영역                           │
 │                                                              │
 │  pdmg-ui                                                     │
 │                                                              │
 │  ┌────────────────────┐      ┌───────────────────────────┐   │
 │  │ 거래통제 관리       │      │ Runtime 진단              │   │
 │  │ /txcontrol         │      │ Dashboard / Diagnosis    │   │
 │  └─────────┬──────────┘      └────────────┬──────────────┘   │
 │            │                              │                  │
 │            ▼                              ▼                  │
 │     mgcoa9001*                      mgcoa9100S0              │
 │            │                              │                  │
 │            ▼                              ▼                  │
 │      Handler/Facade                 Handler/Facade           │
 │            │                              │                  │
 │            ▼                              ▼                  │
 │   mgcoa9001Service               mgcoa9100Service            │
 │            │                              │                  │
 │            ▼                              ▼                  │
 │ TB_MG_TX_CONTROL              MgRuntimeMonitor               │
 └────────────┬──────────────────────────────┬───────────────────┘
              │                              │
              │ 정책                         │ 상태
              ▼                              ▲
 ┌──────────────────────────────────────────────────────────────┐
 │                   RUNTIME PLANE                              │
 │                   실제 거래 실행 영역                        │
 │                                                              │
 │ HTTP Request                                                 │
 │      │                                                       │
 │      ▼                                                       │
 │ Filter / Interceptor                                         │
 │      │                                                       │
 │      ▼                                                       │
 │ TcfFacade                                                    │
 │      │                                                       │
 │      ▼                                                       │
 │ STF                                                          │
 │      │                                                       │
 │      ▼                                                       │
 │ ★ MgTxControlService                                        │
 │      │                                                       │
 │      ├─ GLOBAL                                               │
 │      ├─ BUSINESS                                             │
 │      ├─ SERVICE                                              │
 │      ├─ CHANNEL                                              │
 │      ├─ BRANCH                                               │
 │      ├─ USER                                                 │
 │      └─ IP                                                   │
 │      │                                                       │
 │      ├── BLOCK → BizException(FW0410)                        │
 │      │                                                       │
 │      └── ALLOW                                               │
 │             │                                                │
 │             ▼                                                │
 │       Timeout Executor                                       │
 │             │                                                │
 │             ▼                                                │
 │       Dispatcher                                             │
 │             │                                                │
 │             ▼                                                │
 │       Handler → Facade → Service → DAO → DB                 │
 │                                                              │
 │                  ┌────────────────────┐                      │
 │                  │ Runtime Evidence   │                      │
 │                  ├────────────────────┤                      │
 │                  │ Active Transaction │                      │
 │                  │ Tomcat Thread      │                      │
 │                  │ JVM / GC / CPU     │                      │
 │                  │ Hikari Pool        │                      │
 │                  │ ImageLog           │                      │
 │                  │ Error / Timeout    │                      │
 │                  └────────────────────┘                      │
 └──────────────────────────────────────────────────────────────┘
```

핵심은 다음 한 줄입니다.

```text
운영자가 정책을 등록
       ↓
DB에 통제정책 저장
       ↓
STF가 매 거래마다 정책 조회
       ↓
허용/차단 결정
       ↓
실행된 거래의 상태를 Runtime Monitor가 관찰
       ↓
운영자가 다시 확인·조치
```

즉 **운영 → 통제 → 실행 → 관측 → 분석 → 운영조치**가 하나의 폐쇄 루프가 되어야 합니다.

# 8.2 가장 중요한 구조: 통제 관리와 통제 실행을 분리한다

운영자가 거래통제 화면에서 규칙을 등록하는 것과 실제 거래를 차단하는 것은 서로 다른 경로입니다.

### 관리 경로

```text
운영자
   │
   ▼
pdmg-ui
/txcontrol
   │
   ▼
ServiceId
mgcoa9001S0 / C0 / U0 / D0
   │
   ▼
mgcoa9001Handler
   │
   ▼
mgcoa9001Facade
   │
   ▼
mgcoa9001Service
   │
   ▼
mgcoa9001DAO
   │
   ▼
mgcoa9001-ORA.xml
   │
   ▼
TB_MG_TX_CONTROL
```

반면 실제 업무거래에서는 다음과 같습니다.

### 실행 경로

```text
업무 Request
   │
   ▼
TCF
   │
   ▼
STF.preProcess()
   │
   ▼
MgTxControlService.check()
   │
   ▼
MgTxControlRepository
   │
   ▼
TB_MG_TX_CONTROL
   │
   ├─ 허용
   │    ↓
   │  Timeout
   │    ↓
   │  Dispatcher
   │    ↓
   │  업무 실행
   │
   └─ 차단
        ↓
   BizException
     FW0410
        ↓
   업무 실행 안 함
```

이 분리가 매우 중요합니다.

**`mgcoa9001`은 정책을 관리하고, `MgTxControlService`가 정책을 집행합니다.**

# 8.3 거래통제는 STF에 위치한다

현재 실제 소스에서 거래통제는 `Interceptor`가 아니라 TCF의 `STF`에 들어 있습니다.

```text
Filter
   ↓
Interceptor
   ↓
Controller
   ↓
TcfFacade
   ↓
STF.preProcess()
   ↓
★ MgTxControlService.check()
   ↓
Timeout Executor
   ↓
Dispatcher
   ↓
Handler
```

이 구조가 좋은 이유는 업무 Handler에 진입하기 전에 거래를 막을 수 있기 때문입니다. 이전에 정리한 공통 선·후처리 구조에서도 STF는 **“이 거래를 실행해도 되는가?”**를 판단하는 Framework 영역으로 정의됩니다.

예를 들어:

```text
ServiceId = mgcoa5530S0

STF
 ↓
SERVICE 차단규칙 존재?
 ↓
YES
 ↓
FW0410
 ↓
Dispatcher 진입 X
 ↓
Facade 호출 X
 ↓
DB 업무 SQL 실행 X
```

입니다.

즉 차단할 거래라면 **가급적 업무 자원을 소비하기 전에 막습니다.**

---

# 8.4 현재 구현된 거래통제 기준

실제 `MgTxControlService`와 `mgcoa9001Service`에서 확인되는 통제 유형은 다음과 같습니다.

| 통제유형   | 의미        | 실제 판단 정보      |
| ---------- | ----------- | ------------------- |
| `GLOBAL`   | 시스템 전체 | 전체 허용/차단 정책 |
| `BUSINESS` | 업무코드    | `MG` 등             |
| `SERVICE`  | ServiceId   | `mgcoa5530S0`       |
| `CHANNEL`  | 채널/시스템 | `tr_sysid`, `scid`  |
| `BRANCH`   | 지점        | `tr_brc`            |
| `USER`     | 사용자      | `optr_eno`          |
| `IP`       | IP          | `tr_trm_ipadr`      |

따라서 ServiceId를 중심으로 다음과 같은 통제가 가능합니다.

```text
                    거래 요청

ServiceId = mgcoa5530S0
Business  = MG
User      = E000123
Channel   = DATAEYE
Branch    = 10001
IP        = 10.10.20.31

                       │
                       ▼
               MgTxControlService
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       GLOBAL       BUSINESS      SERVICE
          │            │            │
          ├────────────┼────────────┤
          ▼            ▼            ▼
       CHANNEL       BRANCH        USER
                       │
                       ▼
                      IP
                       │
                       ▼
               Blocking Rule?
                  │         │
                 YES        NO
                  │         │
                  ▼         ▼
               FW0410     실행
```

다만 **시간대별 통제, 단말종류별 통제 등은 현재 이 Repository 평가식에서 확인되지 않습니다.** 따라서 그런 기능을 현재 AS-IS라고 설명하면 안 되며, 필요하다면 TO-BE 확장사항입니다.

---

# 8.5 `GLOBAL 허용`은 일종의 비상 우회 정책이다

현재 소스에는 조금 특이하면서 중요한 동작이 있습니다.

```text
GLOBAL
BLOCK_YN = N
```

인 규칙이 활성화되면:

```text
GLOBAL 허용
     ↓
개별 BUSINESS 차단
개별 SERVICE 차단
개별 USER 차단
개별 BRANCH 차단
...
     ↓
모두 무시
     ↓
거래 허용
```

합니다.

실제 `pdmg-ui` 화면에도:

> 전체 허용이 켜져 있으면 개별 차단이 무시됩니다.

라는 의미가 구현되어 있습니다.

따라서 이것은 단순한 설정값이라기보다 **운영 비상조치 기능**으로 관리해야 합니다.

TO-BE에서는 최소한 다음이 필요합니다.

```text
GLOBAL 허용/해제

     ↓

권한 확인
     ↓
변경사유 필수
     ↓
승인자
     ↓
변경시각
     ↓
Audit Log
     ↓
자동 만료시간
```

현재 `changeReason`, 변경 사용자 등의 데이터는 존재하지만, **2인 승인·자동 만료 같은 강한 운영통제는 별도의 보완 대상**으로 보는 것이 좋습니다.

---

# 8.6 통제 시스템 자체는 차단되면 안 된다

운영·통제 아키텍처에서 상당히 중요한 코드가 `MgTxControlExemptions`입니다.

현재 다음 ServiceId는 거래통제 검사 대상에서 제외됩니다.

```text
mgcoa9001*
    거래통제 관리

mgcoa9100*
    Runtime 진단

mgjwa*
    로그인 / JWT 관리

HealthCheck
*.healthCheck
health
    Health Check
```

이 이유는 매우 명확합니다.

예를 들어 `mgcoa9001` 자체를 SERVICE 통제로 막아버리면:

```text
거래통제 화면
   ↓
mgcoa9001 차단됨
   ↓
차단 규칙 삭제 불가
   ↓
운영자 복구 불가
```

라는 문제가 발생합니다.

따라서 현재 구조는:

```text
                    거래통제

일반 업무 ServiceId ──────────────→ 검사

운영 복구 ServiceId
 ├─ mgcoa9001*
 ├─ mgcoa9100*
 ├─ mgjwa*
 └─ Health
             ──────────────→ EXEMPT
```

형태입니다.

이것은 **운영 Control Plane을 업무 Data Plane에서 보호하는 구조**라고 볼 수 있습니다.

---

# 8.7 통제 정보 조회 실패 시 Fail-Closed 한다

은행 시스템에서는 이것도 중요한 설계입니다.

`MgTxControlRepository` 조회 중 장애가 발생하면 현재 `MgTxControlService`는:

```text
거래통제 DB 조회 실패
       ↓
"통제 여부를 모르겠다"
       ↓
그냥 거래 허용
       X
```

하지 않습니다.

실제 구현은:

```text
TB_MG_TX_CONTROL 조회 실패
       ↓
FW0411
       ↓
거래 차단
```

입니다.

즉 기본 정책은:

```text
통제 판단 성공 + 허용
        → 실행

통제 판단 성공 + 차단
        → FW0410

통제 판단 자체 실패
        → FW0411
```

입니다.

**안전 측면에서는 Fail-Closed 구조**입니다.

금융 거래통제에는 적절한 방향입니다.

# 8.8 Runtime 운영진단은 `mgcoa9100S0`

통제만으로 운영이 완성되는 것은 아닙니다.

운영자는 다음 질문에 답할 수 있어야 합니다.

```text
지금 시스템이 느린가?

        ↓

왜 느린가?

        ↓

Thread 문제인가?
JVM 문제인가?
DB Pool 문제인가?
어느 ServiceId가 점유하는가?
```

현재 실제 소스에서는:

```text
mgcoa9100S0
```

가 그 역할을 담당합니다.

```text
pdmg-ui / 운영화면
       │
       ▼
mgcoa9100S0
       │
       ▼
mgcoa9100Handler
       │
       ▼
mgcoa9100Facade
       │
       ▼
mgcoa9100Service
       │
       ▼
MgRuntimeMonitor
```

입니다.

# 8.9 `MgRuntimeMonitor`가 현재 보는 것

현재 Runtime Monitor는 단일 `pdmg-service` 인스턴스 기준으로 다음 정보를 수집합니다.

```text
                   MgRuntimeMonitor

                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼

   Tomcat Thread       JVM / GC        DB Pool
        │                │                │
        │                │                │
        ▼                ▼                ▼
 maxThreads           Heap Used        active
 currentThreads       Heap Max         idle
 busyThreads          Heap Ratio       pending
 busyRatio            CPU             total
 deadlock             GC Count        maximum
                      GC Time

                         │
                         ▼

                Active Transaction
                         │
                         ├─ ServiceId
                         ├─ GUID
                         ├─ Thread ID
                         ├─ Thread Name
                         └─ Elapsed Time
```

즉 운영자는 단순히:

```text
CPU = 90%
```

만 보는 것이 아니라:

```text
Thread 90%
   +
Active Transaction 40개
   +
특정 ServiceId 60% 점유
   +
DB Pool pending 증가
```

처럼 **업무거래와 인프라자원을 함께 분석할 수 있는 방향**입니다.

프로젝트 연속성 기준에서도 운영자가 “어느 Tomcat → 어느 WAR → Thread/GC/Pool → 어느 ServiceId → 어느 SQL”인지 좁혀갈 수 있어야 한다고 정의하고 있습니다.

# 8.10 Active Transaction Registry

현재 중요한 기반 클래스가:

```text
MgActiveTransactionRegistry
```

입니다.

거래가 시작되면:

```text
TcfFacade
   ↓
TransactionContext
   ↓
registry.begin()
```

하고 종료 시:

```text
registry.end()
```

합니다.

Registry에는 대략:

```text
GUID
ServiceId
BusinessCode
ThreadId
ThreadName
StartedAt
CurrentStep
```

정보가 들어갑니다.

그래서 운영 관점에서는:

```text
Active Transactions
────────────────────────────────────────────

GUID       ServiceId       Thread      Elapsed
------------------------------------------------
A001       mgcoa5530S0     pdmg-01      310 ms
A002       mgcoa8888S0     pdmg-02     2210 ms
A003       mgcoa5530S0     pdmg-03     4810 ms
A004       mgcoa5530S0     pdmg-04     4950 ms
```

와 같은 상태를 만들 수 있습니다.

여기서 한 단계 더 나아가면:

```text
mgcoa5530S0
     ↓
현재 25건 실행
     ↓
전체 Active TX 40건
     ↓
62.5% 점유
     ↓
Tomcat Busy 88%
     ↓
SERVICE_DOMINANCE
```

같은 진단이 가능해집니다.

# 8.11 Runtime 진단 로직도 일부 구현되어 있다

현재 `MgRuntimeMonitor`에는 원인 추정도 일부 들어 있습니다.

개념적으로:

```text
Deadlock?
   ↓ YES
THREAD_DEADLOCK
   ↓ NO

DB Pool 고갈?
   ↓ YES
DB_POOL_EXHAUSTED
   ↓ NO

Heap 높음 + GC 증가?
   ↓ YES
GC_PRESSURE
   ↓ NO

CPU 높음?
   ↓ YES
CPU_OVERLOAD
   ↓ NO

Thread Busy + Active TX 증가?
   ↓ YES
THREAD_SATURATION
   ↓ NO

NORMAL
```

입니다.

따라서 단순 Metric Collector보다 조금 더 나아가:

```text
Metric
   ↓
Cause Analysis
   ↓
Operator Message
```

까지 시도하고 있습니다.

---

# 8.12 그러나 Runtime 진단은 아직 완성되지 않았다

여기에는 중요한 AS-IS 한계가 있습니다.

현재 `MgRuntimeMonitor` 코드를 보면:

```text
slowTransactions = []
slowSql          = []
```

로 아직 비어 있습니다.

따라서 현재 구조는:

```text
Thread        ✅
JVM           ✅
CPU           ✅
GC            ✅
Hikari        ✅
Active TX     ✅

Slow TX       △
Slow SQL      △
외부연계 대기 △
SQL ID 연계   △
```

수준입니다.

즉 최종 운영진단 목표는 다음까지 가야 합니다.

```text
장애 발생

   ↓

Tomcat Busy Thread 95%

   ↓

Active Transaction
mgcoa5530S0 = 62%

   ↓

ServiceId
mgcoa5530S0

   ↓

DAO
mgcoa5530DAO

   ↓

SQL ID
mgcoa5530S0_S0

   ↓

Elapsed
8.2 sec

   ↓

DB Session / SQL
   ↓

Root Cause
SLOW_SQL
```

이렇게 되어야 **ServiceId 중심 운영진단**이 완성됩니다.

# 8.13 ImageLog는 운영 Evidence 역할을 한다

`pdmg-fw`에는 `ImageLogHandler`도 실제 존재합니다.

현재 구조는:

```text
Request
   ↓
Pre ImageLog
   ↓
업무 실행
```

입니다.

를 통해 동일 거래를 추적할 수 있습니다.

# 8.14 Timeout도 운영통제의 일부다

Timeout은 단순 Framework 기술기능이 아닙니다.

운영 관점에서는 **ServiceId별 자원독점을 막는 통제정책**입니다.

현재 예를 들면:

```text
기본
5 sec

mgcoa5530S0
10 sec
```

형태의 ServiceId별 정책이 있습니다.

따라서 최종적으로는:

```text
                    ServiceId

                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼

    거래통제          Timeout        Runtime
    Policy            Policy         Metrics

        │               │               │
        └───────────────┼───────────────┘
                        ▼

                      OM
```

로 묶어야 합니다.

Transaction + Timeout 구조에서는 Worker와 `TransactionTemplate`의 관계까지 함께 고려해야 한다는 점도 앞서 확인했습니다.

# 8.19 초보자가 꼭 기억할 구조

운영·통제 아키텍처는 어렵게 생각할 필요가 없습니다.

```text
① 운영자가 규칙을 만든다

pdmg-ui
   ↓
mgcoa9001
   ↓
TB_MG_TX_CONTROL


② 거래가 들어온다

Request
   ↓
TCF
   ↓
STF


③ 통제정책을 확인한다

MgTxControlService
   ↓
ALLOW / BLOCK


④ 허용된 거래만 실행한다

Timeout
   ↓
Dispatcher
   ↓
Handler
   ↓
Business


⑤ 실행 상태를 계속 본다

Active Transaction
Thread
JVM
DB Pool
ImageLog


⑥ 문제가 생기면 다시 통제한다

Runtime Diagnosis
   ↓
ServiceId 확인
   ↓
운영자 판단
   ↓
거래통제
```

결국 전체 구조는 이것 하나로 기억하면 됩니다.

```text
                 ┌─────────────────┐
                 │    운영자       │
                 └────────┬────────┘
                          │
                          ▼
                 ┌─────────────────┐
                 │   OM / pdmg-ui  │
                 └────────┬────────┘
                          │
                    정책 등록/변경
                          │
                          ▼
                TB_MG_TX_CONTROL
                          │
                          ▼
Request → TCF → STF → 거래통제
                          │
                 ┌────────┴────────┐
                 │                 │
               BLOCK             ALLOW
                 │                 │
                 ▼                 ▼
              오류응답         Timeout
                                  │
                                  ▼
                              Dispatcher
                                  │
                                  ▼
                              업무 실행
                                  │
                                  ▼
                         Runtime Evidence
                                  │
                   ┌──────────────┼──────────────┐
                   ▼              ▼              ▼
                Thread           JVM          DB Pool
                   │              │              │
                   └──────────────┼──────────────┘
                                  ▼
                             ServiceId
                                  │
                                  ▼
                          운영 진단 / 조치
                                  │
                                  └──────────→ 거래통제
```

**8장 운영·통제 아키텍처의 핵심은 “ServiceId를 중심으로 정책을 걸고, 실행 상태를 관찰하고, 문제가 생기면 동일 ServiceId를 다시 통제하는 Closed Loop”입니다.**

앞서 정리한 **Transaction·Timeout, Dispatcher, TCF 선후처리, 에러처리, 계층형 업무 구조, 표준전문·Context**가 모두 이 운영·통제 구조에서 하나로 연결됩니다.

그리고 현재 소스 기준으로는 **`pdmg-fw`가 Runtime Control Engine, `pdmg-service`의 `mgcoa9001/mgcoa9100`이 관리·진단 업무, `pdmg-ui`가 운영자 UI**라고 이해하는 것이 가장 정확합니다. 독립 `pdmg-om`은 이번 Source Baseline에는 없으므로, 별도의 현재 구현으로 가정해서는 안 됩니다.
