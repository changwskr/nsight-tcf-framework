> MyBatis `TrackingStatement`/`queryTimeout` · ServiceId TX Policy · `min-start-budget` 반영.  
> 상세: [01.timeout.md](./01.timeout.md) · [PDMG Transaction + Timeout 아키텍처 구조.md](./PDMG%20Transaction%20+%20Timeout%20아키텍처%20구조.md) ·

> 원본: [`온라인 거래 아키텍처 - 원본.md`](./온라인%20거래%20아키텍처%20-%20원본.md)

현재 프로젝트 기준으로 **전체 온라인 거래 아키텍처**를 한 장으로 보면 다음 구조가 핵심입니다. 현재 PDMG 분석에서는 온라인 거래의 중심축을 **`ServiceId`** 로 보는 것이 가장 정확합니다. PDMG 기준 프로젝트군에서 `pdmg-fw`가 공통 실행 프레임워크를, `pdmg-service`가 업무 애플리케이션을, `pdmg-ui`가 화면/호출을, `pdmg-jwt`가 토큰 발급·관리 영역을 담당하는 구조가 확인되어 있습니다.

## 2. 가장 중요한 것은 `ServiceId`

전체 구조를 클래스 기준으로 외우기보다는 **ServiceId가 어디로 이동하는가**를 이해하는 것이 좋습니다.

```text
화면 이벤트
    │
    ▼
ServiceId
예: mgcoa5530S0
    │
    ▼
HTTP Request
    │
    ▼
OnlineTransactionController
    │
    ▼
TransactionContext
    │
    ▼
TransactionDispatcher
    │
    │ handlerMap[serviceId]
    ▼
TransactionHandler
    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

```

즉 `ServiceId`는 단순 URL 코드가 아니라 앞으로 다음을 연결하는 **온라인 거래 Architecture Key**가 되어야 합니다.

```text
                 ServiceId
                    │
       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
    Handler       Timeout      거래통제
       │            │            │
       ▼            ▼            ▼
    Facade      TX Policy      권한정책
       │
       ▼

       ▼

       │
       ▼
     Test
       │
       ▼

       │
       ▼

       │
       ▼

```

실제로 ServiceId는 거래통제의 식별키와 Timeout 진단·집계축으로 사용하도록 설계되고 있습니다.

## 3. 요청이 들어오면 첫 번째로 하는 일 — Filter

온라인 요청의 가장 앞단은 업무 Service가 아닙니다.

```text
HTTP
 ↓
DefaultFilter
 ↓
Interceptor
 ↓
Controller
```

Filter 영역에서는 대략 다음 공통 관심사를 담당합니다.

| 항목           | 의미                            |
| -------------- | ------------------------------- |
| Request 검증   | Header/Body 형식                |
| JWT            | 인증 Token 확인                 |
| ServiceContext | 요청 단위 공통 Context          |
| 사용자 정보    | 인증 사용자 Context             |
| Client 정보    | IP 등                           |
| 오류 차단      | Controller까지 보내지 않을 오류 |

특히 여기서 오류가 발생하면 업무 Transaction은 아직 시작되지 않았습니다.

```text
JWT 오류
Header 오류
JSON 오류

    ↓

Filter에서 종료

    X
TX BEGIN 없음
    X
Handler 호출 없음
    X
DB 호출 없음
```

현재 예외처리 분석에서도 Filter의 JSON/Header/JWT 오류는 업무 트랜잭션 이전에 처리되는 것으로 분류되어 있습니다.

## 4. Controller는 업무를 처리하는 곳이 아니다

`OnlineTransactionController`의 핵심 역할은 매우 좁게 유지해야 합니다.

```text
Controller
   │
   ├─ ServiceId 결정
   ├─ dto 추출
   └─ TcfFacade 호출
```

### 하면 안 되는 것

```text
Controller
 ├─ 고객 조회          X
 ├─ SQL 실행           X
 ├─ DAO 호출           X
 ├─ 거래별 switch 남발 X
 └─ 업무 Transaction   X
```

현재 PDMG에서는 요청의 ServiceId 후보를 Context Header, JSON Header, Path 등에서 해석하고 DTO 부분을 TCF로 전달하는 구조가 확인되어 있습니다.

# 5. TCF는 온라인 거래의 실행 통제기

TCF의 핵심 역할은 다음입니다.

```text
                      TCF

            "어떤 업무인가?"가 아니라
            "어떻게 실행할 것인가?"

                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
     Context          Timeout        Dispatcher
        │               │                │
        ▼               ▼                ▼
    공통정책         실행시간통제      Handler 선택
```

따라서 다음처럼 구분하는 것이 중요합니다.

| 영역    | 책임                      |
| ------- | ------------------------- |
| TCF     | 거래 실행 방식            |
| Handler | ServiceId → Use Case 연결 |
| Facade  | Use Case 조립             |
| Service | 업무 로직                 |
| DAO     | 데이터 접근               |
| Mapper  | SQL                       |

# 6. Timeout ON이면 구조가 크게 달라진다

현재 PDMG에서 특히 중요한 부분입니다.

최신 Timeout 분석 기준으로 `nhnis.fw.timeout.enabled=true`이면 Dispatcher 이하가 별도의 Worker Thread에서 실행되며, Worker 내부에서 `TransactionTemplate`이 외곽 Transaction을 시작합니다.

```text
Tomcat Request Thread
        │
        ▼
TcfFacade
        │
        ▼
Timeout Executor
        │
        ├──────────── Future.get(remaining)
        │                 Timeout 시:
        │                   cancelAll → Statement.cancel()
        │                   future.cancel(true) → interrupt
        │                   → 504 FW_TIMEOUT (etf skip)
        ▼
   Worker Thread (pdmg-online-*)
        │ Registry.bind(evidenceKey)
        ▼
TransactionTemplate (+ ServiceId Policy)
        │
        ├──── TX BEGIN (min-start-budget 미달 시 TX 미개시 Timeout)
        │
        ▼
   Dispatcher → Handler → Facade → Service → DAO / Mapper
        │
        │ MyBatis: queryTimeout + TrackingStatement 등록
        ▼
       DB
        │
        ▼
 ┌──────────────┐
 │ 정상         │ → COMMIT
 ├──────────────┤
 │ Exception    │ → ROLLBACK
 ├──────────────┤
 │ Deadline 초과│ → ROLLBACK (늦은 커밋 차단)
 └──────────────┘
```

이 구조에서 아주 중요한 점은:

```text
Tomcat Request Thread
        ≠
DB Transaction Thread
```

이라는 것입니다.

**Timeout ON에서는 Worker Thread가 실제 DB Transaction Thread가 됩니다.**

---

# 7. Facade의 `@Transactional`은 어떻게 되는가

여기서 많이 혼동합니다.

```text
Worker Thread
      │
TransactionTemplate
      │
      ├── Physical TX BEGIN
      │
      ▼
Handler
      ▼
Facade
@Transactional(REQUIRED)
      │
      ▼
Service
```

동일한 TransactionManager이고 기본 `REQUIRED`라면:

```text
TransactionTemplate TX
           │
           ▼
Facade @Transactional(REQUIRED)

새 TX 생성 X
기존 TX 참여 O
```

즉 Timeout ON PDMG 구조에서는 **최외곽 Physical Transaction이 Worker의 `TransactionTemplate`에서 만들어지고, Facade의 REQUIRED Transaction은 그 Transaction에 참여하는 형태**로 이해하는 것이 현재 구조와 가장 잘 맞습니다. 최신 Timeout 설계서에서도 Worker 외곽 TransactionTemplate 구조를 AS-IS로 명시하고 있습니다.

# 8. Dispatcher와 Handler의 차이

두 개를 같은 것으로 보면 안 됩니다.

### Dispatcher

```text
ServiceId
    │
    ▼
Handler Registry
    │
    ├─ mgcoa9000S0 → Handler A
    ├─ mgcoa9001S0 → Handler A
    └─ mgcoa5530S0 → Handler B
```

역할은 **찾는 것**입니다.

### Handler

```text
Handler
   │
   ├─ ServiceId A → Facade.methodA()
   ├─ ServiceId B → Facade.methodB()
   └─ ServiceId C → Facade.methodC()
```

역할은 **업무 Use Case와 연결하는 것**입니다.

따라서:

```text
Dispatcher = Routing Infrastructure
Handler    = Application Adapter
```

라고 이해하면 쉽습니다.

# 9. 업무 계층

PDMG 업무 처리의 중심 구조는 다음입니다.

```text
Handler
   │
   ▼
Facade
   │
   ▼
Service
 ┌─┴───────────────┐
 ▼                 ▼
Rule              DAO
                   │
                   ▼
                 Mapper
                   │
                   ▼
                  SQL
                   │
                   ▼
                  DB
```

PDMG Reference 분석에서도 `pdmg-service`의 기준 업무 구조를 `Handler → Facade → BizPrePostAspect → Service → DAO → Mapper/SQL → DB`로 정리하고 있습니다.

각 책임은 다음과 같이 잡는 것이 좋습니다.

| 계층    | 책임                      |
| ------- | ------------------------- |
| Handler | 거래와 Use Case 연결      |
| Facade  | 하나의 업무 Use Case 조립 |
| Service | 핵심 업무 처리            |
| Rule    | 업무 규칙·판단            |
| DAO     | DB 접근 캡슐화            |
| Mapper  | SQL Mapping               |
| DB      | 데이터 저장·조회          |

# 10. JWT는 온라인 업무 Transaction보다 앞에 있다

인증 구조는 업무 거래와 분리해서 봐야 합니다.

### Token 발급

```text
pdmg-ui
   │
   ▼
Login / SSO
   │
   ▼
pdmg-jwt
   │
   ▼
Private Key
   │
   ▼
JWT Sign
   │
   ▼
Access Token
```

### 업무 요청

```text
pdmg-ui
   │
   │ Authorization: Bearer <JWT>
   ▼
pdmg-service
   │
   ▼
pdmg-fw Filter
   │
   ▼
JWT Validation
   │
   ├─ 실패 → 401
   │
   └─ 성공
        ↓
```

```text

   ↓

   ↓
업무 Transaction
```

이어야 하지,

```text

   ↓
JWT 검증
```

이 되어서는 안 됩니다.

# 12. 오류 거래

오류는 어느 위치에서 발생했느냐가 중요합니다.

```text
[Filter 오류]
JWT/Header/JSON
     ↓
400 / 401
     ↓
TX 없음


[ServiceId 오류]
Dispatcher
     ↓
Handler 미등록
     ↓
표준 오류


[업무 오류]
Service
     ↓
BizException
     ↓
TX ROLLBACK
     ↓
오류 응답


[DB 오류]
Mapper / JDBC
     ↓
Exception
     ↓
TX ROLLBACK
     ↓
500 계열


[Timeout]
Request Thread: Future.get 초과
     ↓
cancelAll → Statement.cancel()   ← Registry에 등록된 JDBC
     ↓
future.cancel(true) → interrupt
     ↓
504 FW_TIMEOUT (etf skip)
     │
     └─ Worker: cancel/interrupt 처리 후 Deadline 재검사 → ROLLBACK
        (응답 종료 ≠ Worker 즉시 종료 ≠ cancel 100% 성공)
```

PDMG 예외 분석에서도 Filter, Controller/TCF, Service, DAO/DB, Timeout Worker의 실패 경로가 서로 다르며, 업무 내부 예외는 반드시 Transaction 경계 밖까지 전파되어 rollback되어야 한다고 정리되어 있습니다.

# 13. `pdmg-om`은 업무 호출선의 다음 계층이 아니다

운영관리에서 이것도 매우 중요합니다.

잘못된 그림은:

```text
Service
 ↓
pdmg-om
 ↓
DB
```

입니다.

OM은 일반적으로 **Control Plane / Operations Plane**으로 보는 것이 맞습니다.

```text
                         ┌───────────────┐
                         │    pdmg-om    │
                         │               │
                         │ ServiceCatalog│
                         │ Timeout Policy│
                         │ 거래통제      │
                         │ Tx Log        │
                         │ Error/Runtime │
                         │ Dashboard     │
                         └───────┬───────┘
                                 │
             ┌───────────────────┼──────────────────┐
             │                   │                  │
             ▼                   ▼                  ▼
        정책/기준정보        Runtime 수집        운영 조회
             │                   ▲
             ▼                   │
──────────────────── 온라인 거래 실행 영역 ────────────────────

 Controller → TCF → Handler → Service → DB
                     │
                     ├──────── ServiceId
                     ├──────── GUID/TraceId
                     ├──────── Timeout
                     ├──────── TX 상태
                     └──────── Error/Elapsed
```

즉 **온라인 거래를 처리하는 Data Plane과 이를 관리·관측하는 OM Control Plane을 분리**해야 합니다.

# 14. 현재 반드시 구분해야 하는 AS-IS / TO-BE

여기에는 한 가지 중요한 Drift가 있습니다.

8월 14일 실제 호출선 분석 문서에서는:

```text
TcfFacade
 ↓
TimeoutExecutor
 ↓
Dispatcher

STF/ETF 직접 호출 없음
```

으로 분석되어 있습니다.

반면 8월 17일 Timeout 개선 분석에서는 AS-IS `TcfFacade.process()`에 `STF.preProcess()`가 포함된 구조로 기술되어 있습니다.

따라서 이 부분은 현재 다음처럼 관리하는 것이 안전합니다.

```text
[CONFIRMED]
Controller
→ TcfFacade
→ TimeoutExecutor
→ Dispatcher
→ Handler
→ Business

[DRIFT / 재확인 필요]
STF가 최신 실제 TcfFacade에 연결됐는가?

[DRIFT / 재확인 필요]
ETF가 정상/실패 경로에 실제 연결됐는가?
```

즉 **STF/ETF가 클래스 또는 Bean으로 존재한다는 것과 실제 온라인 거래 호출선에 들어가 있다는 것은 별개의 문제**입니다.

### 한 문장으로 정리하면

> **PDMG 온라인 거래 아키텍처는 `pdmg-ui`가 만든 ServiceId 기반 요청을 `pdmg-fw`가 인증·공통 Context·Timeout·Transaction·Dispatcher로 통제하고, `pdmg-service`의 Handler→Facade→Service→DAO→Mapper가 실제 업무와 DB를 처리한 뒤 표준 응답으로 반환하며, `pdmg-jwt`는 인증 토큰 생명주기를, `pdmg-om`은 ServiceId 중심 운영·통제·증적을 담당하는 구조**로 이해하면 됩니다.

그리고 실제 아키텍처를 볼 때는 **`ServiceId → Handler → Facade → Service → DAO → Mapper → SQL → DB → Transaction/Timeout → Runtime Evidence`**를 하나의 세로축으로 추적하는 것이 가장 중요합니다.
