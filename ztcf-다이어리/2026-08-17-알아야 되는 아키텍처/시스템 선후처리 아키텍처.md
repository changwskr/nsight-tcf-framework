# 시스템 선·후처리 아키텍처 구조

현재 **PDMG 기준 시스템 선·후처리**는 업무 로직이나 TCF 거래 통제를 수행하는 영역이 아니라, **HTTP 요청이 시스템에 들어오는 순간부터 응답이 나갈 때까지 요청 공통정보·인증·Context·로그·표준전문을 관리하는 Framework 공통 계층**입니다.

현재 구조에서는 주로 `pdmg-fw`의 `commons` 영역에 위치하며, `DefaultFilter → ServicePreventionInterceptor → Resolver`가 중심입니다. TCF의 `STF/ETF`, 업무의 `BizPrePostAspect`와는 책임을 분리해야 합니다.

---

# 2. 선·후처리는 3종류를 반드시 구분해야 합니다

PDMG에서 가장 헷갈리기 쉬운 부분입니다.

| 구분                   | 위치                            | 핵심 질문                                               |
| ---------------------- | ------------------------------- | ------------------------------------------------------- |
| **System 선·후처리**   | Filter / Interceptor / Resolver | 요청을 시스템이 처리할 수 있는가?                       |
| **TCF 선·후처리**      | STF / ETF                       | 이 거래를 실행해도 되는가? 거래를 어떻게 종료할 것인가? |
| **Business 선·후처리** | Aspect / Facade 주변            | 업무 공통규칙을 어떻게 적용할 것인가?                   |

구조적으로는:

```text
SYSTEM
Filter / Interceptor
       │
       ▼
TCF
STF
       │
       ▼
BUSINESS
Handler → Facade → Service
       │
       ▼
TCF
ETF
       │
       ▼
SYSTEM
Interceptor / Resolver
```

입니다. 현재 PDMG 자료에서도 시스템 공통, TCF 거래 공통, 업무 공통을 별도 계층으로 분리하고 있습니다.

---

# 3. 시스템 선처리 ① — `DefaultFilter`

`DefaultFilter`는 HTTP Request가 PDMG Framework에 들어왔을 때 가장 앞쪽에서 동작합니다.

```text
HTTP Request
      │
      ▼
┌─────────────────────────────┐
│ DefaultFilter               │
│                             │
│ Request Body Cache          │
│ Header Parsing              │
│ GUID 준비                   │
│ ServiceContext 생성         │
│ MDC 구성                    │
└──────────────┬──────────────┘
               ▼
        Interceptor
```

주요 책임은 다음과 같습니다.

| 기능               | 설명                                        |
| ------------------ | ------------------------------------------- |
| Request Body Cache | 뒤 단계에서도 JSON Body를 읽을 수 있게 보관 |
| 표준전문 Parsing   | `hdr_nhnis` 공통 Header 추출                |
| GUID               | 거래 추적 ID 초기화                         |
| ServiceContext     | 요청 단위 공통 Context 생성                 |
| MDC                | 로그에서 GUID/ServiceId/User 등을 자동 연결 |
| finally 정리       | 요청 종료 후 ThreadLocal/MDC 제거           |

따라서 Filter에 다음 로직을 넣으면 안 됩니다.

```text
Filter
 ├─ 고객 조회       X
 ├─ 거래통제 판단   X
 ├─ DAO 호출        X
 ├─ Mapper 호출     X
 └─ 업무 Rule       X
```

Filter는 **업무가 아니라 시스템 실행환경을 준비하는 계층**입니다.

---

# 4. 시스템 선처리 ② — `ServicePreventionInterceptor`

Filter가 기본 실행환경을 준비했다면 Interceptor는 **요청이 실제 Controller로 들어가기 전에 시스템 공통 검증을 수행**합니다.

```text
DefaultFilter
      │
      ▼
ServicePreventionInterceptor
      │
      ├─ JWT 검증
      ├─ 사용자 식별
      ├─ GUID 보정
      ├─ ServiceId 확인
      ├─ Client IP 확인
      ├─ 요청전문 로그
      └─ PRE ImageLog
      │
      ▼
Controller
```

특히 책임 경계를 이렇게 두는 것이 중요합니다.

```text
JWT Token 검증
        ↓
System Interceptor        O

거래 중지 여부 판단
        ↓
STF / 거래통제            O

고객 업무규칙 검증
        ↓
Service / Rule            O
```

즉 Interceptor가 모든 선처리를 독점하면 안 됩니다.

# 5. 표준전문을 Context와 DTO로 분리한다

외부 요청은 하나의 JSON입니다.

```json
{
  "hdr_nhnis": {
    "sys_comm": {
      "std_gbl_id": "GUID-001",
      "rms_svc_c": "mgcoa9000S0",
      "tr_sysid": "PDMG",
      "optr_eno": "E00001"
    }
  },
  "dto": {
    "customerId": "C100001"
  }
}
```

하지만 Framework 내부에서는 다음처럼 분리합니다.

```text
                Standard Request
                      │
          ┌───────────┴───────────┐
          │                       │
          ▼                       ▼
     hdr_nhnis                   dto
          │                       │
          ▼                       ▼
  ServiceContext          Business DTO
          │                       │
          │                       ▼
          │                    Handler
          │                       ↓
          │                    Facade
          │                       ↓
          └──────────────────► Service
```

즉:

```text
공통 Header
→ Context

업무 데이터
→ DTO
```

입니다.

업무 계층이 `hdr_nhnis` 전체를 메서드 파라미터로 계속 전달하는 구조는 피하는 것이 좋습니다.

# 6. 시스템 선처리와 TCF STF의 경계

여기가 가장 중요합니다.

### 시스템 선처리

```text
"이 요청이 우리 시스템에서 정상적으로 처리될 수 있는가?"
```

예:

```text
JWT가 유효한가?
GUID가 있는가?
사용자를 식별할 수 있는가?
ServiceId가 있는가?
요청 전문을 추적할 수 있는가?
```

### STF

```text
"이 거래를 지금 실행해도 되는가?"
```

예:

```text
서비스가 거래중지 상태인가?
현재 사용자에게 거래가 허용되는가?
지점이 차단돼 있는가?
Timeout 정책은 얼마인가?
중복거래인가?
```

따라서:

```text
JWT Authentication
       ↓
SYSTEM PRE

Transaction Control
       ↓
STF

Business Validation
       ↓
SERVICE / RULE
```

로 나누는 것이 올바른 책임 분리입니다.

# 7. 시스템 후처리

업무 처리가 끝났다고 시스템 처리가 끝난 것은 아닙니다.

```text
Service
   ↓
Return / Exception
   ↓
ETF
   ↓
System Post Processing
```

시스템 후처리의 핵심은 **업무 결과를 외부 표준 응답으로 다시 만드는 것**입니다.

### 정상

```text
Business DTO
    ↓
Response Resolver
    ↓

{
  hdr_nhnis : {...},
  dto       : {...}
}
```

### 오류

```text
Exception
    ↓
GlobalExceptionHandler
    ↓
표준 오류 DTO
    ↓
Response Resolver
    ↓

{
  hdr_nhnis : {...},
  result     : {...}
}
```

즉 원칙은:

```text
정상
→ hdr_nhnis + dto

오류
→ hdr_nhnis + result
```

입니다.

# 8. Interceptor의 후처리 책임

응답 시점에는 다음 처리가 필요합니다.

```text
Business 완료
     │
     ▼
ETF
     │
     ▼
Response 생성
     │
     ▼
Interceptor.afterCompletion()
     │
     ├─ 처리 결과 Logging
     ├─ POST ImageLog
     ├─ Exception ImageLog
     └─ 수행시간 등 기록
     │
     ▼
Filter finally
```

그리고 마지막에는 반드시 요청 단위 상태를 정리해야 합니다.

```text
ServiceContextHolder.remove()

MDC.clear()
```

이 처리가 중요한 이유는 Tomcat Thread가 재사용되기 때문입니다.

```text
Thread-101
 거래 A
   ↓
Context 정리 안 함
   ↓
Thread Pool 반환
   ↓
거래 B가 Thread-101 재사용
   ↓
거래 A의 User/GUID가 남음        ← 위험
```

정상 구조는:

```text
거래 A
 ↓
finally
 ↓
Context / MDC CLEAR
 ↓
Thread Pool
 ↓
거래 B
새 Context 생성
```

이어야 합니다.

# 9. 예외 발생 시에도 후처리가 보장되어야 한다

정상 거래만 생각하면 안 됩니다.

```text
              업무 실행
                 │
         ┌───────┴────────┐
         │                │
       정상              예외
         │                │
         ▼                ▼
       DTO            Exception
         │                │
         │          GlobalExceptionHandler
         │                │
         └───────┬────────┘
                 ▼
        Standard Response
                 │
                 ▼
          afterCompletion
                 │
                 ▼
         Filter finally
                 │
                 ▼
       Context / MDC Clear
```

즉 **예외가 발생해도 시스템 공통 후처리는 반드시 실행**되어야 합니다.

# 11. 권장 패키지 아키텍처

현재 `pdmg-fw` 기준에서는 개념적으로 다음과 같이 정리할 수 있습니다.

```text
pdmg-fw
└─ nhnis.fw.commons
   │
   ├─ configuration
   │
   ├─ filter
   │    └─ DefaultFilter
   │
   ├─ interceptor
   │    └─ ServicePreventionInterceptor
   │
   ├─ resolver
   │    ├─ RequestBodyArgumentResolver
   │    └─ ResponseBodyArgumentResolver
   │
   ├─ context
   │    ├─ ServiceContext
   │    └─ ServiceContextHolder
   │
   ├─ jwt
   │
   ├─ log
   │
   ├─ imagelog
   │
   └─ exception
```

그리고 TCF는 별도 책임입니다.

```text
pdmg-fw
└─ nhnis.fw.tcf
   │
   ├─ OnlineTransactionController
   ├─ TcfFacade
   ├─ STF
   ├─ Timeout
   ├─ Dispatcher
   └─ ETF
```

즉 아키텍처적으로는:

```text
commons
   =
System Runtime

tcf
   =
Transaction Runtime

pdmg-service
   =
Business Runtime
```

라고 보면 이해가 가장 쉽습니다.

# 12. 권장 시스템 선·후처리 표준

최종적으로 PDMG/NSIGHT에서 다음 원칙으로 고정하는 것이 좋습니다.

```text
SYSTEM PRE

01 Request 수신
02 Request Body Cache
03 Header Parsing
04 ServiceContext 생성
05 GUID / MDC 구성
06 JWT 검증
07 User / IP / ServiceId 보정
08 Request Logging
09 PRE ImageLog
10 Controller 진입

          ↓

TCF / BUSINESS

          ↓

SYSTEM POST

11 정상/오류 결과 수신
12 표준 응답 조립
13 Response Logging
14 POST / EXCEPTION ImageLog
15 수행시간 기록
16 ServiceContext 제거
17 MDC 제거
18 HTTP Response
```

그리고 **절대로 System 선·후처리에 업무 로직이나 DAO 접근을 넣지 않는 것**이 핵심 Architecture Rule입니다.

```text
System Common
      │
      ├─ 인증
      ├─ Context
      ├─ Header
      ├─ Trace
      └─ Logging

TCF
      │
      ├─ 거래통제
      ├─ Timeout
      ├─ Transaction 실행
      └─ Dispatch

Business
      │
      ├─ 업무 Rule
      ├─ Service
      └─ DAO / DB
```

따라서 지금까지 정리한 전체 구조에서 **시스템 선·후처리 → TCF 선·후처리 → 업무 선·후처리의 3중 경계를 명확히 유지하는 것**이 PDMG 애플리케이션 아키텍처의 중요한 기준입니다.
