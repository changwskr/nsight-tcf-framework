### 3.3 정책

1. 업무도메인 기준으로 클러스터를 구성한다.
2. ACM(Hub Cluster)에 공유노드(dns/quay/odf)를 구성한다.
3. 클러스터의 워커노드는 NSXI 또는 ACI 네트워크 중 하나로 구성된다.
4. AS-IS 기준 최대 5개 업무도메인으로 구분되며 각각 균등하게 5개 클러스터가 생성됨. (단, 현재 사업 기준으로 3개 클러스터가 생성됨)
5. 타 시스템 협의 필요:
   - quay 단독 구성 → CICD팀 협의
   - 멀티 클라우드 매싱 클라우드 보안솔루션(microsegmentation/cwpp) 설치 협의

## 4. 하나은행 디지털뱅킹플랫폼 MVP 구성도(안)

원본 이미지: `…152528342_10.jpg` · 원본 쪽 **5**

1. 하나 1Q PT와 EIC 연계
2. POD → POD 거래 연계 (동기)

4. EIC를 통한 상품처리 시스템 연계
5. 디지털뱅킹플랫폼과 상품처리DB 연계
6. EIC를 통한 금융결제원 연계 (오픈API)
7. 테스트 서비스를 이용한 로그인 서비스 테스트

- Lib: 고객/공통지원/업무공통

### 8.2 시스템코드 정의 (원본 문구)

- 시스템코드는 반드시 하나 이상의 서비스그룹(업무) 코드와 연관되어야 한다.
- 시스템코드 신설: **DPN** (Digital Banking Platform MVP Namespace)

### 9.1 서비스 코드

채널에서 요청한 온라인 전문을 실행 프로그램에 매핑하는 표준 헤더 키. 프레임워크에서는 **API ID**라고도 함.

구조:

```text
유형분류코드(1) + 서비스그룹코드 AA Level2(3) + 화면일련번호(4) + 서비스구분(1) + 거래구분코드(3)
```

### 9.2 적용구조 ABBBCCCCDEEE

| 구분 | 내용 |
|---|---|
| 적용구조 | **ABBBCCCCDEEE**<br>• A[1] : 유형분류코드 (S:서비스)<br>• B[2-4] : 서비스그룹코드(AA 2 Level) (3)<br>• C[5-8] : 화면일련번호(4)<br>• D[9] : 서비스구분<br>• E[10-12] : 거래구분코드 |
| 명명 규칙 | • 구분값: 온라인 서비스 → `S`<br>• 서비스 그룹 코드: 영문대문자 3자리<br>• 화면일련번호: 화면 번호 뒤 4자리. 화면 없는 프로그램은 가상 4자리 부여<br>• 서비스 구분: 한 화면에 Controller 1단계면 `A`, 복수면 두 번째부터 `B`…<br>• 거래구분코드: Controller 내 method에 따라 `001`~`999` |
| 예시 | MIA시스템 내 MCN(마케팅콘텐츠 관리)<br>온라인 서비스: **SMCN1200A001** |

### 10.2 서비스코드 부여안

**1안) LEVEL3 컨테이너 + 업무 단위**

```text
Online/Batch ID(1) + LEVEL2(3) + _(1) + LEVEL3(3) + Service Type(1) + Transaction Type(3)
예: SLDM_LDMB001
  LDM = 여신수신 컨테이너
  B   = 여신수신 관리 업무코드
  001 = DevonBoot SD Operation Number
```

- LEVEL3가 없으면 LEVEL2 사용
- 제약: 컨테이너 업무당 거래 최대 999

**2안) DevonBoot SD 코드 기준**

```text
Online/Batch ID(1) + LEVEL3(3) + Package No(3) + Service Class No(2) + Operation No(3)
예: SAPUD0101001
```

- 문제: LEVEL2 단위로 부여하면 관련 프로그램 찾기 어려움

### 10.3 LEVEL2·플랫폼 코드 (원본)

- 외부서비스연계(ESI): 하나 API뱅크(중계) `APU`, 상품처리연계 `PPL`
- 플랫폼서비스-중계(PSI): 하나 e-플랫폼 `EPP` / `EPF`
- LEVEL2 업무: `LDM` 여신수신관리, `BCP`/`BCF` 뱅크, `FIX` 통합모바일, `SBM` 실적/수수료관리

### 10.4 디지털플랫폼 (PaaS) 시스템코드 DPN (원본 도식)

```text
LEVEL2 LDM (여신수수료)
LEVEL2 BC (뱅크) · LEVEL3 FIX · LEVEL2 SBM
POD44 테스트
API 이용 → LEVEL3 PPL(상품처리연계) → Kafka/SAGA → LEVEL3 EPP(E-플랫폼)
```

## 14. 요청방안

원본 이미지: `…152528342.jpg` · 원본 쪽 **15**

### 14.1 서비스코드

**1안) 서비스코드 LEVEL3 사용**

```text
온라인/배치구분(1) + LEVEL3(3) + 패키지번호(3) + 서비스클래스번호(2) + 오퍼레이션번호(3)
예: SAPU00101001
```

- 장점: DevonBoot SD 거래 기준으로 프로그램 확인 가능
- 단점: LEVEL2 단위로 관련 프로그램 확인 어려움 · 메소드 거래 최대 999

**2안) LEVEL2만 존재 대상을 LEVEL3로 동일하게 구분**

- 장점: LEVEL2만 있는 대상과 LEVEL3까지 있는 대상을 동일 기준으로 처리
- 단점: 컨테이너 추가 시 LEVEL2 코드 미신청 · 서비스코드 정의 문제

**3안) LEVEL2를 컨테이너 단위로 등록**

- 장점: 서비스코드 매칭 명확화
- 단점: 컨테이너 신규마다 LEVEL2 신규 코드 신청

**4안) 3안 방식으로 LEVEL2 코드 변경 후, 1안 방식에서 LEVEL3를 LEVEL2로 표기**

### 14.2 매핑 예시 (원본 표 요지)

**3안 관점 — LEVEL2 ≈ 컨테이너**

| 업무 | 시스템코드(예) | AA Level1 | AA Level2 | AA Level3 |
|---|---|---|---|---|
| 하나플랫폼 | EPF (또는 epi) | SIF | (컨테이너) | — |
| 하나API뱅크(이용) | APU | SIF | AA | — |
| 상품처리연계 | PPL | SIF | AA | — |
| 테스트 | TST | SIF | AA | — |
| 여수신 | LDM | … | AA | — |
| 펀드 | BCF | … | AA | — |
| 외환 | FFX | … | AA | — |
| 퇴직연금 | RPM | … | AA | — |

**2안/4안 관점 — 시스템코드 DPN 유지 · LEVEL 세분**

|---|---|---|---|---|---|
