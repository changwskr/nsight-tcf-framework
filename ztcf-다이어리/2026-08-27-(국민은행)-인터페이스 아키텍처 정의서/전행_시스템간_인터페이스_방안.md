## 1.1 목적

FACT: 블루프린트에서 정의한 31개 시스템도메인 간의 인터페이스 개발 및 유지보수를 효율적으로 하기 위해 인터페이스 표준을 설계하였으며, 31개 시스템도메인을 구축하거나 유지보수하는 프로젝트 및 IT운영부서에서 인터페이스 설계/구축/운영 시에 활용이 된다.

확인: 같은 원문이 대상은 **33개**(Channel·MCI/EAI 포함, 2.1·2.2)와 **31개**(채널·MCI 제외, 1.1·3.2.1)를 함께 쓴다. 채널·MCI를 뺀 업무 도메인이 31개다.

# 3. 인터페이스 유형 정의

## 3.1 인터페이스 구성 유형

### 1) Point to Point

```text
Sys A ←──────────► Sys B
Sys A ←──────────► Sys C
Sys B ←──────────► Sys C
```

FACT: 송수신 시스템 간 1:1 연계로 Message를 전달한다. 인터페이스 구성이 용이하다. 다수 시스템 연계를 하나의 트랜잭션으로 처리하기 어렵고, 연동 시스템 수가 늘면 장애 가능성과 유지보수 비용이 증가한다.

### 2) Hub & Spoke

```text
  Spoke A          Spoke B
      \              /
       \            /
        └── Hub ───┘
       /            \
      /              \
  Spoke C          Spoke D
```

FACT: 허브를 경유하는 중앙집중 형태로 송신/변환/전달한다. Queuing 방식을 기반으로 한 Message 라우팅도 가능하다. 데이터 전송보증 및 정합성 우수, 인터페이스 통합 운영관리가 용이하다.

ANALYSIS: TA 기본 정책의 EAI = Hub. 예외의 P2P = 4.2.

# 4. 인터페이스 처리방안

## 4.1 TA 인터페이스 정책

FACT: 채널들은 채널의 표준화를 구현하기 위한 MCI를 사용하여 시스템도메인과 인터페이스를 구현하며, 시스템도메인 간의 인터페이스는 전문, 처리방법 및 연결방식 표준화를 지원하는 EAI를 적용해야 한다. “아키텍처원칙”의 인터페이스 정책에 기술된 내용은 다음과 같다.

```text
1. 단말, 자동화기기, 인터넷뱅킹 등의 채널은
   MCI를 경유하여 시스템도메인과 인터페이스 한다.

2. 시스템도메인 간의 인터페이스는 EAI를 사용한다.

3. 대외 기관과의 인터페이스는 EAI를 사용한다.
```

```text
채널 ──MCI──► 도메인
도메인 ──EAI──► 도메인
도메인 ──EAI──► 대외
```

### 4.2.1 시스템도메인 내 인터페이스

### 4.3.5 EAI 거래 처리 방식

#### 전문 온라인 거래 방식

FACT: EAI를 경유하는 전문거래의 경우 서비스 to 서비스, 서비스 to DB, DB to 서비스, DB to DB 방식으로 처리가 가능하다. 그러나 source 데이터를 실시간으로 read/write하는 방식이 데이터 관리 정책에 위배되고, 시스템에 부하를 주는 관계로 **서비스 to 서비스 방식으로 제한**한다.

```text
[허용]   송신 서비스 ──► EAI ──► 수신 서비스
[제한]   AP 우회, DB 직접 R/W (서비스 to DB, DB to 서비스, DB to DB)
```

처리 가능한 인터페이스 패턴은 4.4를 참조한다.

#### ETL 거래 방식

FACT: EAI를 통해 처리할 수 있는 ETL 거래 방식으로는 DB to File, File to File 방식이며 자세한 내용은 4.4를 참조한다.

```text
DB To File
  송신시스템의 DB를 대량으로 Read하여 수신 시스템에 파일을 전송
  일정시간마다 체크하다 데이터 변화가 생기면 Read
  또는 일정 시간에 DB를 Read

File To File
  송신시스템 File을 수신 시스템에 전송
  송신시스템 File 생성이 완료되면 전송
```

### 4.3.6 전문 인코딩

FACT: XML 전문형식의 인터페이스 시 사용할 수 있는 인코딩에는 EUC-KR, MS949, UTF-8/UTF-16 등이 있으며, 각 인코딩들의 특징을 비교한 결과 유니코드의 인코딩으로 표준이며, 다국어 처리가 가능한 UTF-8 인코딩이 장점이 많은 반면 2Byte 체계인 관계로 전문 크기가 커지는 단점이 있어, **EUC-KR 인코딩을 권장**한다.


### 4.3.7 전문거래 인터페이스 시 SYNC/ASYNC 처리

FACT: 시스템도메인 간 혹은 대외기관과의 인터페이스 시 SYNC 거래를 사용할 경우 서비스를 요청한 시스템과 EAI 시스템은 서비스를 제공하는 시스템에서 응답이 올 때까지 대기하게 되며, 이 대기 시간이 길어지거나 서비스를 제공하는 시스템에 장애가 발생할 경우 서비스를 요청한 시스템에 Table Lock 등에 의한 성능저하 및 Hang 현상이 발생할 개연성이 높다. 특히 SYNC 거래는 LU, 세션을 유지하고 있어야 하는 관계로 시스템 자원에 대한 효율성도 떨어지는 측면이 있다.

```text
31개 시스템도메인 간의 전문거래
  업무요건에 따라 SYNC, ASYNC 가능
  다만 다음이면 안정성·성능 보장을 위해 ASYNC 고려
    · M/F CICS 처리시간 기준 3초 이상
    · 3군데 이상의 시스템도메인 경유

대외기관
  경유 구간이 많고 대외기관 특성을 감안하여 ASYNC
  예외: 대외기관에서 들어오는 개설거래는 SYNC 요건으로 SYNC 처리
```

ANALYSIS: `_22` 원칙 3, `_38` Full Sync / Async Response / Half Sync. IF-P03.

### 4.3.8 전문 Size 제약

#### 1) M/F

FACT: LU0의 특성상 32K로 제한이 된다. M/F 계정계나 카드계와 전문을 주고 받는 경우에는 32K로 처리해야 한다. 32K를 초과하는 경우 32K로 나누어 처리를 한다.

#### 2) UNIX

FACT: UNIX 시스템 간 인터페이스에 따른 전문크기 제약은 없으므로 MCI와 시스템도메인 간의 전문크기는 제한이 없다. BMT 사례를 참고로 하여 단말/자동화기기와 MCI 간, **MCI를 사용하지 않는 업무인 경우에는 단말/자동화기기와 서버 간**의 전문크기를 다음과 같이 제한한다.

```text
단말/자동화기기 ↔ MCI 구간
  계정계 업무  32K
  정보계 업무  100K
  이미지       256K

XML 전문크기는 parsing 시간을 고려하여 최대한 적게 한다.
KB BMT 결과 256K XML 데이터 생성에 16 ms (0.016초) 소요
```

#### 3) BMT 사례 — 영업점 DM 9MB를 32K 분할

FACT: 영업점 DM발송업무 서비스 오픈 시 대량 데이터 전송에 의한 기존 서비스의 안정성 검증, DM발송업무의 데이터 전송 시 어플리케이션 및 network 에러 발생 여부 등을 검증하기 위한 BMT 사례이다. 대량 데이터(9Mbyte)를 32K로 나누어 전송하며, 전송시마다 Time Delay를 0초, 0.5초, 1초로 조정하여 영업점 네트워크 상태를 측정함.

[표 4.2-5] BMT 사례 (FACT):

| 유형 | Bytes | Duration | Client | Server | Network |
|---|---:|---:|---:|---:|---:|
| delay 0초 | 12,901K | 226.7s | 0.9s | 16.8s | 221.3s |
| delay 0.5초 | 12,911K | 243.2s | 1.2s | 18.2s | 223.6s |
| delay 1초 | 13,000K | 412.0s | 36.4s | 2.3s | 393.2s |

FACT 당행 기준: 당행 영업점 네트워크 환경(512K)에서 대량 데이터를 전송할 경우 계정계 업무 서비스 등 기존 서비스의 지연 처리가 발생하지 않도록 1 거래당 32K로 나누어 전송하며, 적정한 Time Delay를 주도록 권장하고 있음. Time Delay 0초, 0.5초의 경우 속도가 거의 비슷하며, 통신대역폭을 100% 점유하는 관계로 기존 업무서비스에 영향을 미칠 것으로 판단됨. Time Delay 1초의 경우 9Mbyte 전송 시 통신대역폭의 50% 가량 점유하고 약 6분30초가 소요되며 기존업무 서비스에 영향이 적을 것으로 판단됨.

## 4.4 인터페이스 패턴 유형

### 4.4.1 EAI 적용 시 인터페이스 패턴

FACT: 송신시스템에서 수신시스템으로 전송되는 자료의 연계를 인터페이스라 하며, 해당 인터페이스의 유형을 분류하고 정의한 것을 인터페이스 패턴이라 한다.

표 4.4-1 인터페이스 패턴:

```text
전문거래 유형
  단방향 통신
  단방향 이중통신      ← 본문은 「단방향 다중통신」
  양방향 비동기 전송 1  (DAST1)
  양방향 비동기 전송 2  (DAST2)
  양방향 동기전송
  양방향 동기 집합전송
  양방향 동기 다중전송

ETL 유형
  DB To File
  File To File
```

원문 표는 「이중통신」, 이어서 본문은 「다중통신」이다. 둘 다 한 송신에서 여러 수신으로 보내는 패턴이다.

#### 단방향 통신

```text
송신 ──전문──► 수신
     (응답 없음)
```

#### 단방향 다중통신

```text
        ┌──► 수신1
송신 ───┼──► 수신2
        └──► 수신3
```

#### 양방향 비동기 DAST1

```text
송신 요청포트 ──req──► 수신 요청포트
송신 응답포트 ◄─res──  수신 같은 포트/서비스
```

요청 후 **다른 포트/서비스가 답을 기다림**. 수신은 **요청받은 포트로 응답**.

#### 양방향 비동기 DAST2

```text
송신 요청포트 ──req──► 수신 요청 서비스
송신 응답포트 ◄─res──  수신 다른 포트/서비스
```

수신이 **요청과 다른 포트/서비스로 응답**.

#### 양방향 동기전송

```text
송신 포트 A ──req──► 수신
송신 포트 A ◄─res──  수신
        (같은 포트, 대기)
```

#### 양방향 동기 집합전송

```text
송신 ──req──► EAI ──┬──► 수신1 ──res─┐
                    ├──► 수신2 ──res─┼── merge ──► 송신
                    └──► 수신3 ──res─┘
```

FACT: Target 장애 시 **보상거래**를 고려한다.

#### 양방향 동기 다중전송 (BPA)

```text
송신 ──req──► 수신1 ──res──►
                EAI가 2nd 전문 생성
              ──req──► 수신2 ──res──►
                EAI가 3rd 전문 생성
              ──► 송신에 최종 응답
```

Business Process Automation에 적용.

#### ETL DB To File / File To File

```text
[DB2FL]  송신테이블 일괄 Read ──변환──► 수신 파일
[FL2FL]  송신파일 완료 ──변환/전송──► 수신파일

실시간에 가까운 배치. 수신 방식에 따라 변환.
```

ANALYSIS: 후속 `_38` Full Sync ≈ 양방향 동기, Async Response ≈ DAST, Async 다중 ≈ 단방향 다중.

### 4.4.2 EAI 미 적용 시 인터페이스 패턴

FACT: 기술적 제약, KB 정책, 데이터 ownership 등의 사유로 사용할 수 없는 패턴이 있을 수 있으며, EAI 팀과 협의 중임 (원문 시점).

#### 1) MQ 활용

```text
송신서비스 → 송신 Queue ──MQ──► 수신 Queue → 수신서비스 → 수신테이블
```

FACT: 송신 서비스가 송신시스템의 queue에 전문을 넣으면 MQ 미들웨어에 의해 수신시스템의 queue에 전문을 전달하고, 전달된 전문은 수신서비스에 의해 수신테이블에 반영이 되는 방식이다. M/F과 UNIX 간 통신 시 코드 변환이 필요하다.

#### 2) DRDA 활용

```text
요청 시스템 ──직접 접속──► M/F DB2
```

FACT: M/F의 데이터를 필요로 하는 시스템에서 M/F의 DB2에 직접 connection을 하여 데이터를 처리하는 방식이다. M/F DB2에 세션 접속 및 데이터 처리에 부하가 걸려 M/F 계정계나 정보계의 성능 저하를 유발시킬 수 있으므로 제한적으로 사용이 되어야 한다.

#### 3) DB 인터페이스 활용 (SQL*Net 등)

```text
요청 시스템 ──DB Client──► 상대 DB   (AP 서버 우회)
```

FACT: 상대방 AP 서버를 거치지 않고 DB Client (SQL*Net 등) 모듈을 이용하여 DB에 직접 접속하여 원하는 Data을 가져오는 형태이다. 별도의 프로그램 없이 데이터를 가지고 오는 장점은 있으나, 상대방 테이블이 변경되어도 그 내용을 인지할 수 없어 장애가 발생할 수 있으며, 업무요건에 의해 DB를 변경하고자 할 경우에도 임의적으로 할 수 없어 업무에 영향을 미칠 수 있다. 네트워크에 문제가 발생할 경우 트랜잭션 pending에 걸릴 수 있다.

#### 4) DB-Link 활용 (원문 표기 DB-Kink)

FACT: DBMS 간에 사전에 Link를 걸어두고, 자신의 DB를 처리하는 형태로 상대편의 DB도 처리할 수 있는 방식으로 이기종 DB 간에는 문제가 발생할 수 있으며, Join 등에 의하여 시스템 부하를 유발하여 성능저하 및 문제를 야기할 수 있으므로 사용을 제한한다.

장점 (FACT):

```text
· 이기종 간 분산데이터 처리 편리 (테이블 조인 등 코딩 편의)
· DB에 한번 접속으로 여러 DB를 핸들링
```

단점 (FACT, 사용 제한):

```text
· 큰 Batch + 네트워크 장애 → 대량 rollback
· 실시간 DML → Local+Remote Lock, 지연
· 이기종 Join 시 인덱스·plan 불리 → 성능
· pending → DBMS Restart 가능
· Remote 참조무결성·통계·권한 관리 불가
· 업그레이드/패치 리스크 (Link명, 계정, 권한)
```

ANALYSIS: 후속 원칙 **금지 H** (DB-LINK 상시). IF-P12 유형 미분류 개통 금지와 같은 취지.
