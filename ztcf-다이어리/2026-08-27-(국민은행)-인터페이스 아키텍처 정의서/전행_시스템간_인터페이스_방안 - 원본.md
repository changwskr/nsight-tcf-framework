# 1. 개요

원문은 33개(채널·MCI/EAI 포함)와 31개(채널·MCI 제외)를 함께 쓴다. 본 문서는 원문 그대로 둔다.

# 3. 인터페이스 유형 정의

## 3.1 인터페이스 구성 유형

### 1) Point to Point

```text
Sys A ←──────────► Sys B
Sys A ←──────────► Sys C
Sys B ←──────────► Sys C
        … 연결 수 n(n-1)/2
```

FACT: 1:1 구성이 쉽다. 다수 시스템을 한 트랜잭션으로 묶기 어렵고, 연동 수가 늘면 장애·유지보수 비용이 증가한다.

### 2) Hub & Spoke

```text
  Spoke A          Spoke B
      \              /
       \            /
        └── Hub ───┘
       /            \
      /              \
  Spoke C          Spoke D
```

FACT: 허브 경유 송신/변환/전달. Queuing 기반 라우팅 가능. 전송 보증·정합성·통합 운영이 유리하다.

ANALYSIS: TA 기본 정책의 EAI = Hub. 예외의 P2P = 4.2.

# 4. 인터페이스 처리방안

## 4.1 TA 인터페이스 정책

FACT — 아키텍처원칙의 인터페이스 정책:

```text
1. 단말 · 자동화기기 · 인터넷뱅킹 등 채널
     → MCI 경유 → 시스템도메인

2. 시스템도메인 간
     → EAI

3. 대외 기관
     → EAI
```

```text
채널 ──MCI──► 도메인
도메인 ──EAI──► 도메인
도메인 ──EAI──► 대외
```

ANALYSIS: 후속 IA `_22` 원칙 1·2와 동일. IF-P02.

---

## 4.2 인터페이스 정책 예외 요건

다음 요건은 TA 정책의 **예외**다 (FACT).

---

### 4.2.1 시스템도메인 내 인터페이스

```text
도메인 내부
  원칙: 미들웨어 제공 IF  (EAI 안 탐)
  동일 도메인 안에도 Integration 기능은 있어야 함

EAI를 쓸 수 있는 경우
  A. 독립 트랜잭션
     노드별 이기종 MW + 타 도메인/대외와도 분리된 Tx 단위
  B. 전행 서비스 제공
     특정 노드가 전행에 서비스를 제공 = 사실상 별도 도메인
```

ANALYSIS: IA `_23` 예외 1 · IF-P10 Direct.

---

### 4.2.2 대외 인터페이스

기술·업무 제약이 있으면 **대외기관 요건**을 따르고 P2P를 쓸 수 있다.

```text
예외 허용
  · 대외 전용 시스템이 IF 서버 역할  (신용카드승인)
  · 대외 제공 시스템 · API 사용
  · EAI Adapter 미지원
      → 개발팀 × EAI팀 × TA팀 협의
      → Adapter 신규 효과 · 타팀 영향 · 일 처리량 · 공수 · 응답속도
```

---

### 4.2.3 KESA를 사용하는 시스템도메인 간의 인터페이스

```text
원칙: KESA 도메인 간도 EAI

허용: KESA Framework 표준 IF를 쓸 수 있다
      (KESA가 표준화된 인터페이스를 제공하기 때문)
```

후속 장표의 n-KESA / z-KESA / u-KESA는 이 그룹의 제품군 표기다.

---

### 4.2.4 파일 전송

```text
KB 내부 물리 노드 간 파일
  → NDM 또는 FTP+ Client
  → Point-to-Point

이유: EAI 경유 시 EAI 역할이 작고, EAI 서버 부하로
      전문 온라인 성능을 떨어뜨릴 수 있음
```

ANALYSIS: 후속 IA는 내부 파일을 **MFT**로 표준화하고 전송 내역만 EAI 관리 (IF-P09). 2008 원문은 NDM/FTP+.

---

### 4.2.5 DW 데이터 전송

```text
원칙대로면 DW도 EAI
예외 사유:
  DBMS만 있고 AP 없음
  로그 실시간 + 대량 전송/변환/적재가 전제

→ DW에 맞는 전송 방식
→ 상세는 「DW 데이터 전송 방안」
```

ANALYSIS: 후속 `_14` ③ CDC/ETL/EAI · IF-P04. 구조도 SIS ODS ≠ EDW.

### 4.3.5 EAI 거래 처리 방식

#### 전문 온라인

가능: 서비스↔서비스, 서비스↔DB, DB↔서비스, DB↔DB.

FACT: 원천을 실시간 read/write하면 데이터 관리 정책 위배·부하 → **서비스 to 서비스로 제한.**

```text
[허용]  송신 서비스 ──► EAI ──► 수신 서비스
[비권고] AP 우회 DB 직접 R/W
```

패턴 상세는 4.4.

#### ETL 거래

EAI로 가능한 ETL: **DB to File**, **File to File**.

```text
DB To File
  송신 DB 대량 Read → 수신에 파일
  주기 체크 후 변화 시 Read  /  정시 Read

File To File
  송신 파일 생성 완료 후 전송
```

### 4.3.7 전문거래 인터페이스 시 SYNC/ASYNC 처리

```text

  대기 장기 · 제공측 장애 → Table Lock · Hang
```

```text
31개 도메인 간: 업무요건에 따라 SYNC 또는 ASYNC

다음이면 ASYNC를 고려
  · M/F CICS 기준 처리시간 3초 이상
  · 3개 이상 도메인 경유

대외: 경유 구간 多 · 대외 특성 → ASYNC
예외: 대외에서 들어오는 개설거래 → SYNC
```

ANALYSIS: `_22` 원칙 3, `_38` Full Sync / Async Response / Half Sync. IF-P03.

## 4.4 인터페이스 패턴 유형

### 4.4.1 EAI 적용 시 인터페이스 패턴

표 4.4-1:

```text
전문거래
  단방향 통신
  단방향 이중(다중)통신
  양방향 비동기 전송 1  (DAST1)
  양방향 비동기 전송 2  (DAST2)
  양방향 동기전송
  양방향 동기 집합전송
  양방향 동기 다중전송

ETL
  DB To File
  File To File
```

#### 단방향 통신

```text
송신 ──전문──► 수신
     (응답 없음)
```

#### 단방향 다중통신

```text
        ┌──► 수신1
송신 ───┼──► 수신2
        └──► 수신3
```

#### 양방향 비동기 DAST1

```text
송신 요청포트 ──req──► 수신 요청포트
송신 응답포트 ◄─res──  수신 같은 포트/서비스
```

요청 후 **다른 포트/서비스가 답을 기다림**. 수신은 **요청받은 포트로 응답**.

#### 양방향 비동기 DAST2

```text
송신 요청포트 ──req──► 수신 요청 서비스
송신 응답포트 ◄─res──  수신 다른 포트/서비스
```

수신이 **요청과 다른 포트/서비스로 응답**.

#### 양방향 동기전송

```text
송신 포트 A ──req──► 수신
송신 포트 A ◄─res──  수신
        (같은 포트, 대기)
```

#### 양방향 동기 집합전송

```text
송신 ──req──► EAI ──┬──► 수신1 ──res─┐
                    ├──► 수신2 ──res─┼── merge ──► 송신
                    └──► 수신3 ──res─┘
```

FACT: Target 장애 시 **보상거래**를 고려한다.

#### 양방향 동기 다중전송 (BPA)

```text
송신 ──req──► 수신1 ──res──►
                EAI가 2nd 전문 생성
              ──req──► 수신2 ──res──►
                EAI가 3rd 전문 생성
              ──► 송신에 최종 응답
```

Business Process Automation에 적용.

#### ETL DB To File / File To File

```text
[DB2FL]  송신테이블 일괄 Read ──변환──► 수신 파일
[FL2FL]  송신파일 완료 ──변환/전송──► 수신파일

실시간에 가까운 배치. 수신 방식에 따라 변환.
```

후속 `_38` Full Sync ≈ 양방향 동기, Async Response ≈ DAST, Async 다중 ≈ 단방향 다중.

### 4.4.2 EAI 미 적용 시 인터페이스 패턴

기술 제약·정책·ownership으로 못 쓰는 패턴이 있다. EAI팀 협의 (원문).

#### 1) MQ

```text
송신서비스 → 송신 Queue ──MQ──► 수신 Queue → 수신서비스 → 수신테이블
```

FACT: M/F–UNIX 간 **코드 변환** 필요.

#### 2) DRDA

```text
요청 시스템 ──직접 접속──► M/F DB2
```

FACT: M/F DB2 세션·처리 부하 → 계정계/정보계 성능 저하. **제한적 사용.**

#### 3) DB 인터페이스 (SQL*Net 등)

```text
요청 시스템 ──DB Client──► 상대 DB   (AP 서버 우회)
```

장점: 별도 프로그램 없이 데이터 취득.  
단점: 상대 테이블 변경을 모름 → 장애. DB 변경이 제멋대로 안 됨. 네트워크 문제 시 Tx pending.

#### 4) DB-Link (원문 표기 DB-Kink)

사전에 Link를 걸고 자기 DB처럼 상대 DB를 처리.

장점: 이기종 Join·코딩 편의, 한 접속으로 여러 DB.

단점 (FACT, 사용 제한):

```text
· 큰 Batch + 네트워크 장애 → 대량 rollback
· 실시간 DML → Local+Remote Lock, 지연
· 이기종 Join 시 인덱스·plan 불리 → 성능
· pending → DBMS Restart 가능
· Remote 참조무결성·통계·권한 관리 불가
· 업그레이드/패치 리스크 (Link명, 계정, 권한)
```

ANALYSIS: 후속 원칙 **금지 H** (DB-LINK 상시). IF-P12 유형 미분류 개통 금지와 같은 취지.
